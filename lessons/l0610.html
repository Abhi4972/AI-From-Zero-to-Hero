About the model on this page

Every node here is a plain Python function, so the graphs run identically every time. LangGraph does not need a model at all; models are just one thing a node can call (Lesson 14.102).

uv add langgraph
Why this came about

Agents built with simple chains could not branch, loop or wait, so in January 2024 LangChain released LangGraph, describing agents as graphs of nodes over shared state, with reducers to merge updates safely.

The problem: your engine merges state with dict.update

The engine you wrote in Lesson 14.100 ran one node at a time and merged each node's output into the state with {**state, **update}. That is fine until two things happen. Two nodes run in parallel and write the same key: which value wins? And some keys should accumulate rather than be replaced, like a conversation's messages or a list of checks. LangGraph's answer is a typed state with a reducer per key, and it gives you the rest of the engine, checkpoints, interrupts and streaming, on the same model.

In plain words first
A shared case file and a rule per field

A LangGraph graph is a set of functions (nodes) that work on one shared dictionary (the state), connected by edges that say what runs next. A node never returns the whole state; it returns only the keys it changed, and LangGraph merges them in. For most keys, merging means "replace". For some, such as a list of messages or log lines, it should mean "add to the end"; the per-key rule that decides is a reducer. Your Lesson 14.100 engine merged with dict.update; reducers are what make parallel nodes and chat histories work.

Idea 1 · State, nodes, edges

The refund workflow from Lesson 14.100, its first three steps, in LangGraph:

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class RefundState(TypedDict, total=False):
    msg: str
    intent: str
    order: dict
    needs_approval: bool

def classify(state: RefundState) -> dict:
    return {"intent": "refund" if "refund" in state["msg"].lower() else "other"}

def lookup(state: RefundState) -> dict:
    return {"order": {"id": "A-1077", "amount": 7999}}          # an order service call in real life

def decide(state: RefundState) -> dict:
    return {"needs_approval": state["order"]["amount"] > 5000}

builder = StateGraph(RefundState)
builder.add_node("classify", classify)
builder.add_node("lookup", lookup)
builder.add_node("decide", decide)
builder.add_edge(START, "classify")
builder.add_edge("classify", "lookup")
builder.add_edge("lookup", "decide")
builder.add_edge("decide", END)
graph = builder.compile()

print(graph.invoke({"msg": "I want a refund for A-1077"}))
What you should see
{'msg': 'I want a refund for A-1077', 'intent': 'refund', 'order': {'id': 'A-1077', 'amount': 7999}, 'needs_approval': True}

Four parts, and you have seen each one before. The state schema (RefundState) names the keys the graph carries. Each node is a function that takes the current state and returns only the keys it changes, a partial update. Edges say what runs next; START and END are the entry and the exit. compile() checks the structure (an edge to a missing node fails here, like your engine's lint) and returns a runnable, with invoke, stream and batch (Lesson 14.94).

Idea 2 · Watch the state change

graph.stream runs the graph and hands you something after every step. Ask for values and you get the whole state each time; ask for updates and you get only what the node that just ran returned. Run the same input both ways and compare:

for snapshot in graph.stream({"msg": "I want a refund for A-1077"}, stream_mode="values"):
    print(sorted(snapshot))
print("---")
for update in graph.stream({"msg": "I want a refund for A-1077"}, stream_mode="updates"):
    print(update)
What you should see
['msg']
['intent', 'msg']
['intent', 'msg', 'order']
['intent', 'msg', 'needs_approval', 'order']
---
{'classify': {'intent': 'refund'}}
{'lookup': {'order': {'id': 'A-1077', 'amount': 7999}}}
{'decide': {'needs_approval': True}}

stream_mode="values" yields the whole state after each step; stream_mode="updates" yields only what each node returned, keyed by node name. The updates view is the one to read when debugging: it shows exactly which node wrote which value. You can also draw the graph:

mermaid = graph.get_graph().draw_mermaid()          # paste into any Mermaid viewer to see the picture
print("\n".join(line.strip() for line in mermaid.splitlines() if "-->" in line))
What you should see
__start__ --> classify;
classify --> lookup;
lookup --> decide;
decide --> __end__;

Idea 3 · Parallel nodes and reducers

After the lookup, ShopKart wants two independent checks, fraud and stock, which can run at the same time. Two edges out of one node make both targets run in the same step, and a list of sources on an edge waits for all of them:

from langgraph.errors import InvalidUpdateError

class CheckState(TypedDict):
    order_id: str
    checks: list

def fraud_check(state):  return {"checks": ["fraud: clear"]}
def stock_check(state):  return {"checks": ["stock: returned to warehouse"]}

def build(state_type):
    b = StateGraph(state_type)
    b.add_node("fraud_check", fraud_check)
    b.add_node("stock_check", stock_check)
    b.add_edge(START, "fraud_check")                      # two edges from START: both run in the same step
    b.add_edge(START, "stock_check")
    b.add_edge(["fraud_check", "stock_check"], END)       # END waits for both
    return b.compile()

try:
    build(CheckState).invoke({"order_id": "A-1077", "checks": []})
except InvalidUpdateError as e:
    print("InvalidUpdateError:", str(e).splitlines()[0])
What you should see
InvalidUpdateError: At key 'checks': Can receive only one value per step. Use an Annotated key to handle multiple values.

Both nodes wrote checks in the same step, and LangGraph refuses to guess which one wins. That is better than your engine, where the last one silently overwrote the first. Say how the updates combine with a reducer, a function from (old value, new value) to the merged value, attached to the key with Annotated:

import operator
from typing import Annotated

class CheckState(TypedDict):
    order_id: str
    checks: Annotated[list, operator.add]                 # the reducer: how two updates to this key combine

print(build(CheckState).invoke({"order_id": "A-1077", "checks": []}))
What you should see
{'order_id': 'A-1077', 'checks': ['fraud: clear', 'stock: returned to warehouse']}

Without a reducer, a key's new value replaces the old one. With operator.add on a list, updates are appended. Any two-argument function works, for example a dictionary merge or "keep the maximum".

Idea 4 · The messages reducer

Conversations need a smarter reducer than appending, so LangGraph ships add_messages:

from langchain_core.messages import AIMessage, HumanMessage, RemoveMessage
from langgraph.graph.message import add_messages

history = [HumanMessage("Where is A-1001?", id="1"), AIMessage("Checking…", id="2")]
history = add_messages(history, [AIMessage("A-1001 has shipped.", id="3")])        # append
history = add_messages(history, [AIMessage("Let me check that order.", id="2")])   # same id: replace
print([(m.id, m.content) for m in history])
history = add_messages(history, [RemoveMessage(id="2")])                           # delete
print([(m.id, m.content) for m in history])
What you should see
[('1', 'Where is A-1001?'), ('2', 'Let me check that order.'), ('3', 'A-1001 has shipped.')]
[('1', 'Where is A-1001?'), ('3', 'A-1001 has shipped.')]

It appends new messages, replaces a message that has the same ID (useful when a streamed message is finished, or a person edits a tool call before approving it), and deletes on RemoveMessage, which is how you trim history (Lesson 14.105). MessagesState is a ready-made state with messages: Annotated[list, add_messages], and create_agent's state is built on it.

Idea 5 · A public interface, private internals

A graph's callers should not depend on its internal keys. Give it an input schema and an output schema:

class Ask(TypedDict):
    msg: str

class Answer(TypedDict):
    needs_approval: bool

public = StateGraph(RefundState, input_schema=Ask, output_schema=Answer)
for name, fn in [("classify", classify), ("lookup", lookup), ("decide", decide)]:
    public.add_node(name, fn)
public.add_edge(START, "classify"); public.add_edge("classify", "lookup")
public.add_edge("lookup", "decide"); public.add_edge("decide", END)
print(public.compile().invoke({"msg": "I want a refund for A-1077"}))
What you should see
{'needs_approval': True}

Callers send a message and get a decision; intent and order stay inside. This matters when the graph becomes a node inside another graph (Lesson 14.107) or a deployed API (Lesson 14.108), where internal keys would otherwise become part of the contract.

Check your mental model
  • ✗ "A node returns the full new state."
    ✓ It returns only the keys it changes; LangGraph merges them using each key's reducer.
  • ✗ "Two parallel nodes writing the same key is fine."
    ✓ Without a reducer it is an error, because LangGraph will not guess which value wins.
  • ✗ "add_messages always appends."
    ✓ It appends new IDs, replaces messages with an existing ID, and deletes on RemoveMessage.

Exercises

Predict before you run

In Idea 3's graph with the reducer, you start with checks: ["received"]. What is checks at the end, and does the order of the two new entries depend on which check finishes first? (Solution P1.)

Break it on purpose

Remove Annotated[..., operator.add] from checks and run the parallel graph again. Then make the two checks run one after the other instead of in parallel. Does the error come back? What is checks at the end? (Solution B1.)

Debugging exercise
Debugging exercise: every entry appears twice

An audit log should read received, checked order, approved:

class AuditState(TypedDict):
    log: Annotated[list, operator.add]

def step_one(state):
    state["log"].append("checked order")
    return {"log": state["log"]}

def step_two(state):
    return {"log": ["approved"]}

b = StateGraph(AuditState)
b.add_node("step_one", step_one); b.add_node("step_two", step_two)
b.add_edge(START, "step_one"); b.add_edge("step_one", "step_two"); b.add_edge("step_two", END)
print(b.compile().invoke({"log": ["received"]})["log"])

What it printed:

['received', 'checked order', 'received', 'checked order', 'approved']

Find the bug. (Solution D1.)

Make it your own

Combine everything: classify, then lookup, then the fraud and stock checks in parallel, then a decide node that reads both checks and the amount and returns "refund" or "hold for review". (Solution M1.)

Solutions

SolutionP1 · Reducers apply in a fixed order

["received", "fraud: clear", "stock: returned to warehouse"]. Updates from one step are applied in a deterministic order, not in the order the nodes finish, so runs are reproducible. Do not rely on that order for meaning, though: if order matters, sort in the node that reads the list.

SolutionB1 · The error is about the same step

Run in sequence, there is no error: each step has one writer, so each update simply replaces the key, and checks ends as ["stock: returned to warehouse"]. The first check's result is lost, silently. The error only protects you when two writers share a step; a reducer is what you want whenever a key should accumulate.

SolutionD1 · The node returned the whole list

step_one appended to the list in the state and returned the whole list. The reducer then added that list to the old one, so "received" and "checked order" appear twice. Nodes should return only what they add, and should not mutate the state they were given:

def step_one(state):
    return {"log": ["checked order"]}                      # return only what this node adds

b = StateGraph(AuditState)
b.add_node("step_one", step_one); b.add_node("step_two", step_two)
b.add_edge(START, "step_one"); b.add_edge("step_one", "step_two"); b.add_edge("step_two", END)
print(b.compile().invoke({"log": ["received"]})["log"])

['received', 'checked order', 'approved']
SolutionM1 · Fan out, then join
class FullState(RefundState, total=False):
    checks: Annotated[list, operator.add]
    decision: str

def decide_all(state):
    risky = any("flagged" in c for c in state["checks"])
    return {"decision": "hold for review" if risky or state["order"]["amount"] > 5000 else "refund"}

b = StateGraph(FullState)
for name, fn in [("classify", classify), ("lookup", lookup), ("fraud_check", fraud_check),
                 ("stock_check", stock_check), ("decide", decide_all)]:
    b.add_node(name, fn)
b.add_edge(START, "classify"); b.add_edge("classify", "lookup")
b.add_edge("lookup", "fraud_check"); b.add_edge("lookup", "stock_check")          # fan out
b.add_edge(["fraud_check", "stock_check"], "decide"); b.add_edge("decide", END)   # join
out = b.compile().invoke({"msg": "I want a refund for A-1077", "checks": []})
print(out["checks"], "->", out["decision"])

['fraud: clear', 'stock: returned to warehouse'] -> hold for review

The checks ran in parallel after lookup, and decide waited for both. The amount, 7,999, is over the limit, so the refund is held; Lesson 14.104 turns "hold for review" into a real pause for a person's decision.

Check your understanding

Explain the mechanismWhat are state, nodes, edges and reducers in LangGraph?

Worked answer. The state is a typed dictionary that the graph carries from step to step. Nodes are functions that read the state and return a partial update. Edges decide which nodes run next, fixed or conditional, and several edges from one node run their targets in parallel in the same step. Reducers decide how an update is merged into a key: by default it replaces, and with a reducer such as operator.add or add_messages it accumulates. Two parallel writes to a key without a reducer are an error rather than a silent overwrite.

A plausible wrong answer. "Nodes pass their output to the next node." Nodes write to the shared state; any later node can read any key.

Follow-ups. When would you write a custom reducer?

Debug a failureA key in your state keeps growing with duplicate entries. Where do you look?

Worked answer. At the nodes that write that key. With an appending reducer, a node that returns the whole current list instead of only its new entries duplicates everything, and a node that mutates the state in place makes it worse. I would stream with stream_mode="updates" to see which node returned which value, then fix the node to return only its additions.

A plausible wrong answer. "LangGraph is replaying steps." The duplicates come from what the nodes return, not from the runtime.

Follow-ups. How would you remove old entries from such a key?

Defend a designWhy use LangGraph's state model instead of passing values between functions?

Worked answer. Because the runtime needs to own the state to do the hard parts: save it after every step so a run can resume after a crash or a pause for approval, run nodes in parallel and merge their results deterministically, stream each update, and replay or fork from any earlier step. Passing values between functions is simpler for a short fixed pipeline, and there I would use plain code or LCEL. Once a workflow is long-running, branching or needs approvals, a shared, typed, checkpointed state is what makes those features possible.

A plausible wrong answer. "It is just the LangGraph way of writing code." The state model exists because checkpointing and parallelism need it.

Follow-ups. What should and should not go into graph state (Lesson 14.103)?
