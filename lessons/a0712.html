In plain words first
The idea in one line

Training is parallel and FLOP-bound. Inference is serial and memory-bound. Different bottleneck, different tricks.

Terms you'll hear
Term What people say What it actually means
KV cache "The trick that makes decoding fast" Stored K and V from every prefix token; new queries attend to them instead of recomputing.
HBM "GPU main memory" High Bandwidth Memory; 80 GB on H100, 192 GB on B200. ~3 TB/s bandwidth.
SRAM "On-chip memory" Per-SM fast memory, ~256 KB per SM on H100. ~30 TB/s bandwidth.
Flash Attention "Tiled attention kernel" Computes attention without materializing N×N in HBM.
Continuous batching "No-wait batching" Swap finished sequences out, new ones in, without draining the batch.
PagedAttention "vLLM's headline" KV cache allocated in fixed blocks with a page table; eliminates fragmentation.
Prefix caching "Reuse long prompts" Cache KV for a shared prefix across requests; major cost cut for agents.
Speculative decoding "Draft + verify" Cheap draft model proposes tokens; big model verifies k in one pass.

The problem

In plain words first

When a language model writes, it produces one token at a time, and each new token must attend to every earlier one. Recomputing the keys and values of all earlier tokens at every step would be wasteful, because they never change; the KV cache stores them, so each step only computes the new token's own. The cache then becomes the main user of memory during long conversations. Attention itself has a second problem: the full table of scores between all pairs of tokens is huge, and moving it in and out of a GPU's main memory is slower than the arithmetic. FlashAttention computes attention in tiles that stay in fast on-chip memory and never builds the whole table, while giving exactly the same result. This lesson runs the lesson's cache and tiled softmax, measures a real model's generation with and without the cache, checks the cache's size against the formula, and compares full, tiled and fused attention on 4,096 tokens. Nothing is trained.

A naive autoregressive decoder does O(N2) work to generate N tokens: at each step it recomputes attention over the full prefix. For a 4K-token response that is 16M attention operations, most of them redundant. Every hidden state of a prefix token is deterministic once computed — you only need to run the new token's query against the cached keys and values of everything before.

On top of that, attention itself moves a lot of data. Standard attention materializes an N×N score matrix, N×d softmax output, N×d final output — too many reads and writes to HBM. For N≥2K, attention becomes memory-bound before it becomes FLOP-bound. Classic attention kernels underuse modern GPUs by 4–10×.

Two optimizations pushed frontier inference from "slow" to "fast":

  1. KV cache. Store the K and V vectors of every prefix token. Each new token's attention is one query against the cached keys, and each step computes keys and values for one new token instead of recomputing them for the whole prefix: over a generation of N tokens, N token states instead of about N²/2.
  2. Flash Attention (Dao et al., 2022). Tile the attention computation so the full N×N matrix never hits HBM. All of softmax + matmul happens in SRAM. FlashAttention-2 roughly doubled the first version's speed; FlashAttention-3 reaches up to about 740 TFLOP/s in FP16 on an H100, about 75% of the chip's peak.

By 2026 both are universal. Every production inference stack (vLLM, TensorRT-LLM, SGLang, llama.cpp) assumes them. Every frontier model ships with Flash Attention enabled.

The idea

Idea 1 · KV cache math

Per decoder layer, per token, across all KV heads:

bytes_per_token_per_layer = 2 * n_kv_heads * d_head * dtype_size
                          ^
                          K and V

For a 7B model with 32 layers, 32 heads (all used for K and V), d_head=128, fp16:

per token per layer = 2 * 32 * 128 * 2 = 16384 bytes (16 KiB)
per token (32 layers) = 512 KiB
per 32K context = 16 GiB

For Llama 3 70B (80 layers, d_head=128, GQA with 8 KV heads):

per token per layer = 2 * 8 * 128 * 2 = 4096 bytes (4 KiB)
per 32K context = 10 GiB

That 10 GiB at 32K grows to 40 GiB at 128K, which is the whole of a 40 GB A100 just for KV cache at batch size 1.

GQA is the KV-cache win. MHA with 64 KV heads would be 8x larger, about 80 GiB at 32K. MLA compresses even further.

Idea 2 · Flash Attention — the tiling trick

Standard attention:

S = Q @ K^T          (HBM read, N×N, HBM write)
P = softmax(S)       (HBM read, HBM write)
O = P @ V            (HBM read, HBM write)

Three HBM round trips. On H100, HBM bandwidth is 3 TB/s; SRAM is 30 TB/s. Every HBM trip is a factor-of-10 slowdown vs keeping everything on-chip.

Flash Attention:

for each block of Q (tile size ~128 × 128):
    load Q_tile into SRAM
    for each block of K, V:
        load K_tile, V_tile into SRAM
        compute S_tile = Q_tile @ K_tile^T     (SRAM)
        running softmax aggregation             (SRAM)
        accumulate into O_tile                  (SRAM)
    write O_tile to HBM

One HBM trip per tile. Total memory footprint drops from O(N2) to O(N). Backward pass recomputes some values from the forward pass instead of storing them — another memory win.

Numerical trick. Running softmax maintains (max, sum) across tiles so the final normalization is exact. Not an approximation — Flash Attention computes bit-identical output to standard attention (modulo fp16 non-associativity).

Version evolution:

Version Year Key change Speedup on reference hardware
Flash 1 2022 Tiled SRAM kernel 2× on A100
Flash 2 2023 Better parallelism, causal-first ordering 3× on A100
Flash 3 2024 Hopper asynchrony, FP8 1.5–2× on H100 (~740 TFLOPs FP16)
Flash 4 2025 Blackwell (B200) kernels, software exponential Forward pass first; see the repository for current support

FlashAttention-4 targets Blackwell GPUs and launched with the forward pass first; check the repository for what it supports today. Training on Hopper GPUs uses FlashAttention-3 or -2.

Idea 3 · Speculative decoding — the other latency win

Cheap model proposes N tokens. Big model verifies all N in parallel. If verification accepts k tokens, you paid 1 big-model forward pass for k generations. Typical k=3–5 on code and prose.

2026 defaults: - EAGLE 2 / Medusa. Integrated draft heads that share the verifier's hidden states. 2–3× speedup with no quality loss. - Speculative decoding with draft model. 2–4× speedup on consumer hardware. - Lookahead decoding. Jacobi iteration; no draft model needed. Niche but free.

Idea 4 · Continuous batching

Classic batched inference: wait for the slowest sequence to finish, then start a new batch. Wastes GPU when short responses finish early.

Continuous batching (first shipped in Orca, now in vLLM, TensorRT-LLM, SGLang): swap new requests into the batch as soon as old ones finish. 5–10× throughput gain for typical chat workloads.

Idea 5 · PagedAttention — KV cache as virtual memory

vLLM's headline feature. KV cache is allocated in 16-token blocks; a page table maps logical positions to physical blocks. Lets you share KV across parallel samples (beam search, parallel sampling), hot-swap prefixes for prompt caching, and defragment memory. The vLLM paper reports 2–4× higher throughput than the serving systems it compared against.

The same idea as a formula

What decoding computes. At step t the new token's query qt​ attends over all keys and values so far:

ot​=softmax(d​qt​K≤t⊤​​)V≤t​,K≤t​=[k1​;…;kt​],V≤t​=[v1​;…;vt​]

ki​,vi​ depend only on tokens ≤i, so they never change once computed. Without a cache, step t recomputes all t of them in every layer: ∑t=1N​t=N(N+1)/2 token states for N tokens. With a cache, each is computed once: N token states. The attention dot products, N(N+1)/2 in total, are the same either way.

Cache size in bytes, for L layers, hkv​ key/value heads of size dh​, n tokens, batch B and b bytes per number:

MKV​=2⋅L⋅hkv​⋅dh​⋅n⋅B⋅b

It grows linearly with context and batch, and grouped-query attention divides it by the ratio of query to KV heads.

Why decoding is memory-bound. Each step reads every weight once (≈2Nparams​ bytes in bf16) plus the whole cache, for about 2Nparams​ FLOPs: roughly one FLOP per byte, far below a GPU's ratio of compute to bandwidth (about 300 FLOPs per byte on an H100). Batching many users shares the weight reads; the cache cannot be shared.

Online softmax (FlashAttention's core). Processing keys in blocks, keep a running maximum m, a running sum ℓ and an unnormalised output o. For a new block of scores s:

m′=max(m,maxs),ℓ′=ℓem−m′+∑es−m′,o′=oem−m′+j∑​esj​−m′vj​,ofinal​=o/ℓ

The rescaling by em−m′ makes the result exactly equal to the one-shot softmax, while only one block of scores exists at a time: memory O(N) instead of O(N2).

Worked example
Cache sizes by hand

Llama 3.1 8B in bf16: 32 layers, 8 KV heads of size 128.

  • Per token: 2×32×8×128×2=131,072 bytes = 128 KiB.
  • One 8,192-token conversation: 128KiB×8192=1 GiB. Sixteen such users at once: 16 GiB, as much as the model's own weights.
  • With full multi-head attention (32 KV heads) it would be 4 GiB per conversation.

DeepSeek-V3 with MLA: 61 layers, one compressed vector of 512 plus a 64-dimensional rotary key per token and layer: 576×2×61=70,272 bytes, about 69 KiB per token, half of Llama 3.1 8B's for a model 80 times larger.

Recomputation without a cache: generating 200 tokens after a 7-token prompt recomputes ∑t=8207​t≈21,500 token states per layer instead of 207.

  • ✗ "The KV cache changes the model's output."
    ✓ It stores exactly the values that would be recomputed; the run under "Use it" produces identical tokens with and without it.
  • ✗ "FlashAttention is an approximation of attention."
    ✓ It is exact up to floating-point rounding; it changes the order of operations and the memory traffic, not the result.
  • ✗ "The KV cache makes attention O(N) overall."
    ✓ Each step still attends over all t previous tokens; the cache removes the recomputation of their keys and values, not the attention itself.

Step 1 · KV cache

See code/main.py, or its Rust port code/main.rs. To run the Rust version: rustc --edition 2021 -O code/main.rs -o /tmp/lesson && /tmp/lesson. We implement:

  1. A naive O(N2) incremental decoder.
  2. A O(N) KV-cached decoder.
  3. A tiled softmax that simulates Flash Attention's running-max algorithm.
class KVCache:
    def __init__(self, n_layers, n_heads, d_head):
        self.K = [[[] for _ in range(n_heads)] for _ in range(n_layers)]
        self.V = [[[] for _ in range(n_heads)] for _ in range(n_layers)]

    def append(self, layer, head, k, v):
        self.K[layer][head].append(k)
        self.V[layer][head].append(v)

    def read(self, layer, head):
        return self.K[layer][head], self.V[layer][head]

Simple: keep growing per-token K, V vectors in per-layer, per-head lists.

Step 2 · tiled softmax

def tiled_softmax_dot(q, K, V, tile=4):
    """Flash-attention-style softmax(qK^T)V with running max/sum."""
    m = float("-inf")
    s = 0.0
    out = [0.0] * len(V[0])
    for start in range(0, len(K), tile):
        k_block = K[start:start + tile]
        v_block = V[start:start + tile]
        scores = [sum(qi * ki for qi, ki in zip(q, k)) for k in k_block]
        new_m = max(m, *scores)
        exp_old = math.exp(m - new_m) if m != float("-inf") else 0.0
        exp_new = [math.exp(sc - new_m) for sc in scores]
        s = s * exp_old + sum(exp_new)
        for j in range(len(out)):
            out[j] = out[j] * exp_old + sum(e * v[j] for e, v in zip(exp_new, v_block))
        m = new_m
    return [o / s for o in out]

Bit-identical output to softmax(qK) V in one shot, but at any time the working set is a tile × d_head block, not the full N × d_head.

Step 3 · compare naive vs cached decoding

Count attention operations. Both decoders make the same query-key comparisons: step t attends over t tokens, so the total is 1 + 2 + ... + N = N(N+1)/2. The code uses N = 10 and prints 55 for each decoder. For a 100-token generation, both make 5050 comparisons. The cache saves the K and V projections. Without a cache, every step computes K and V again for the full prefix, so a 100-token generation computes 5050 token states. With the cache, each token's K and V are computed once, so the same generation computes 100 token states.

Use it: the same idea with real libraries

# transformers enables the KV cache in generate() for decoder-only models.
import time, torch
from transformers import AutoModelForCausalLM, AutoTokenizer

repo = "HuggingFaceTB/SmolLM-135M"        # meta-llama/Llama-3.2-3B is gated and FlashAttention-2 needs a CUDA GPU
tok = AutoTokenizer.from_pretrained(repo)
model = AutoModelForCausalLM.from_pretrained(repo, attn_implementation="sdpa", dtype=torch.float32).eval()

ids = tok("The history of the printing press begins", return_tensors="pt").input_ids
for use_cache in (True, False):
    t = time.perf_counter()
    out = model.generate(ids, max_new_tokens=200, do_sample=False, use_cache=use_cache, pad_token_id=tok.eos_token_id)
    print(f"use_cache={use_cache!s:5}: 200 new tokens in {time.perf_counter() - t:5.1f} s")
    if use_cache: first = out
print("identical tokens with and without the cache:", torch.equal(first, out))

Full, tiled and fused attention on 4,096 tokens

Causal attention with 8 heads of size 64 on 4,096 tokens: the textbook version that builds every score matrix, the online-softmax version from the formula box in blocks of 512 keys, and PyTorch's fused scaled_dot_product_attention. For each: the difference from the textbook result, the time, and the largest single memory allocation recorded by PyTorch's profiler.

import time, torch, torch.nn.functional as F
from torch.profiler import profile, ProfilerActivity
torch.manual_seed(0)

B, H, N, D = 1, 8, 4096, 64
q, k, v = (torch.randn(B, H, N, D) for _ in range(3))

def naive(q, k, v):                     # materialises the full N x N score matrix for every head
    s = (q @ k.transpose(-1, -2)) / D ** 0.5
    s = s.masked_fill(torch.ones(N, N, dtype=torch.bool).triu(1), float("-inf"))
    return s.softmax(-1) @ v

def tiled(q, k, v, tile=512):           # FlashAttention's running max and running sum, one key block at a time
    out = torch.zeros_like(q); m = torch.full(q.shape[:-1] + (1,), float("-inf")); l = torch.zeros_like(m)
    for j in range(0, N, tile):
        s = (q @ k[..., j:j + tile, :].transpose(-1, -2)) / D ** 0.5
        mask = torch.arange(N)[:, None] < torch.arange(j, j + tile)[None, :]
        s = s.masked_fill(mask, float("-inf"))
        m_new = torch.maximum(m, s.amax(-1, keepdim=True))
        p = torch.exp(s - m_new); scale = torch.exp(m - m_new)
        l = l * scale + p.sum(-1, keepdim=True)
        out = out * scale + p @ v[..., j:j + tile, :]
        m = m_new
    return out / l

def peak_mb(f):
    with profile(activities=[ProfilerActivity.CPU], profile_memory=True) as prof:
        f()
    return max(e.cpu_memory_usage for e in prof.events()) / 2**20

def timed(f):
    f(); t = time.perf_counter(); f(); return (time.perf_counter() - t) * 1000

ref = naive(q, k, v)
for name, f in [("naive (full score matrix)", lambda: naive(q, k, v)),
                ("tiled, 512 keys at a time", lambda: tiled(q, k, v)),
                ("PyTorch scaled_dot_product_attention", lambda: F.scaled_dot_product_attention(q, k, v, is_causal=True))]:
    with torch.no_grad():
        err = (f() - ref).abs().max().item()
        print(f"{name:38s} max difference {err:.1e}   time {timed(f):7.0f} ms   largest single allocation {peak_mb(f):6.0f} MB")
print(f"\none {N} x {N} float32 score matrix per head x {H} heads = {H * N * N * 4 / 2**20:.0f} MB")
What you should see
naive (full score matrix)              max difference 0.0e+00   time    1487 ms   largest single allocation    512 MB
tiled, 512 keys at a time              max difference 6.0e-07   time    1248 ms   largest single allocation     64 MB
PyTorch scaled_dot_product_attention   max difference 7.7e-07   time     105 ms   largest single allocation      8 MB

Reading this output

All three give the same result to within 10−6. The textbook version's largest allocation is exactly the 512 MB of score matrices (8 heads × 40962 × 4 bytes); the tiled version never holds more than one block of 512 keys, 64 MB, an eighth, and would need even less with smaller tiles. In pure PyTorch on a CPU the tiled loop runs at about the speed of the textbook version, because each block is a separate set of operations. The fused kernel does the same tiling inside one compiled loop: more than ten times faster here and with no allocation larger than 8 MB (the output itself). On a GPU the gap is larger still, because there the cost of moving the score matrix through main memory dominates, which is FlashAttention's whole point.

Break it on purpose

In tiled_softmax_dot, drop the rescaling: replace exp_old = math.exp(m - new_m) with exp_old = 1.0. For tile sizes that cover the whole sequence in one block the output is still correct. What goes wrong with smaller tiles, and on what kind of input is the error largest? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Serving engines manage the cache. vLLM (PagedAttention), SGLang (RadixAttention prefix sharing), TensorRT-LLM and llama.cpp all page the KV cache, batch continuously and reuse cached prefixes; FP8 KV caches are a common option to halve its memory.
  • Prompt caching is a product feature. Anthropic, OpenAI and Google bill cached input tokens at a fraction of the normal price when a long prefix (system prompt, tools, documents) repeats across calls.
  • FlashAttention-2 and -3 are the default kernels behind training and serving on NVIDIA GPUs (FlashInfer is a common serving alternative); PyTorch's scaled_dot_product_attention selects a fused kernel automatically.

Sources: vLLM, SGLang, FlashAttention, FlashInfer, Anthropic prompt caching, OpenAI prompt caching.

Recap
What to keep from this lesson
  • Keys and values of earlier tokens never change: cache them, compute one new token's per step.
  • Cache size =2Lhkv​dh​nBb; it grows with context and users, and GQA or MLA shrink it.
  • Decoding reads all weights per token, so it is memory-bound; batching shares weights, not caches.
  • FlashAttention's online softmax is exact and never stores the N×N scores.

hard40 minresearch

Standard attention builds the full matrix of scores, of size Tq​×Tk​. FlashAttention never builds that matrix. It reads the keys and values in blocks and keeps a running softmax for each query row. The result is exact, not an approximation. Here you write that running softmax in numpy.

Task

Write two functions.

  1. online_softmax_step(m, l, acc, scores, v_block) adds one block of keys to the running state of each query row.
  2. flash_attention(Q, K, V, block_size, causal=False) runs the step over the key blocks and returns the attention output and the log-sum-exp of each row.

The state of query row i has three parts: the running max mi​, the running sum li​, and the accumulator ai​, a vector of size dv​. At the start, mi​=−∞, li​=0 and ai​=0. For a block with scores sij​ and value rows vj​, the step computes:

mi′​=max(mi​,jmax​sij​),ci​=emi​−mi′​

li′​=ci​li​+j∑​esij​−mi′​,ai′​=ci​ai​+j∑​esij​−mi′​vj​

A score of −∞ is a blocked key. When mi′​ is −∞, the row has no allowed key yet. Then use 0 in place of mi′​ inside both exponentials, so that ci​=0 and each term is 0. The step then returns mi′​=−∞, li′​=0 and ai′​=0.

In flash_attention, the scores of a block are QKbT​/d​, where Kb​ holds the key rows from start to start + block_size and d is the size of the last axis of Q. The blocks start at 0, block_size, 2 * block_size and so on. The last block can be shorter. With causal=True, key j is blocked for query i when j>i. The indices i and j are global row indices, not indices inside a block. After the last block, the output row is ai​/li​ and the log-sum-exp is mi​+logli​.

Common mistakes the checks catch
  • Sets the running max to the max of the current block only, so scores far apart in two blocks overflow.
  • Blocks key j when j >= i, so each query also blocks itself and the first row has no allowed key.
  • Uses a running max of minus infinity inside the exponentials, so a fully masked block gives NaN.
  • Forgets to scale the old accumulator by exp(old max minus new max).
  • Forgets to scale the old running sum by exp(old max minus new max).
  • Stops the loop before a last block that is shorter than block_size.
Hint 1

Write the step first and test it by hand. Start each row with m=−∞, l=0 and an accumulator of zeros.

Hint 2

The old sum and the old accumulator were computed relative to the old max. When the max grows, multiply both by em−m′ to move them to the new max. Forget this factor on one of them and the output is wrong.

Hint 3

np.exp(-np.inf) is exactly 0, but -np.inf - (-np.inf) is NaN. Use np.where(np.isneginf(m_new), 0.0, m_new) as the max inside the exponentials.

Hint 4

import numpy as np


def online_softmax_step(m, l, acc, scores, v_block):
    block_max = np.max(scores, axis=-1)
    m_new = np.maximum(m, block_max)
    safe_max = np.where(np.isneginf(m_new), 0.0, m_new)
    exp_old = np.exp(m - safe_max)
    exp_new = np.exp(scores - safe_max[:, None])
    l_new = exp_old * l + np.sum(exp_new, axis=-1)
    acc_new = exp_old[:, None] * acc + exp_new @ v_block
    return m_new, l_new, acc_new


def flash_attention(Q, K, V, block_size, causal=False):
    Tq, d = Q.shape
    Tk = K.shape[0]
    scale = 1.0 / np.sqrt(d)
    m = np.full(Tq, -np.inf)
    l = np.zeros(Tq)
    acc = np.zeros((Tq, V.shape[1]))
    rows = np.arange(Tq)[:, None]
    for start in range(0, Tk, block_size):
        stop = min(start + block_size, Tk)
        scores = Q @ K[start:stop].T * scale
        if causal:
            cols = np.arange(start, stop)[None, :]
            scores = np.where(cols > rows, -np.inf, scores)
        m, l, acc = online_softmax_step(m, l, acc, scores, V[start:stop])
    return acc / l[:, None], m + np.log(l)

Why the result is exact

Softmax does not change when you subtract a constant from every score in a row. The step keeps l and a relative to the current max. When the max changes from m to m′, the factor em−m′ moves every earlier term to the new reference. After the last block, l is the exact softmax denominator relative to the final max, and a/l is the exact output. The only difference from standard attention is the order of the floating point additions.

Why it is fast

The full score matrix has Tq​Tk​ entries. On a GPU it does not fit in the fast on-chip memory, so standard attention writes it to slow memory and reads it back. The tiled form keeps one block of scores on the chip at a time. The memory for the scores falls from O(T2) to O(T), and the kernel reads the slow memory far less often. The paper calls this IO awareness.

The log-sum-exp

The kernel also stores m+logl for each row. The backward pass uses it to compute the softmax again, block by block, in place of a stored matrix of probabilities.

A difference from the paper

The first version of the paper keeps the output divided by l after every block. The second version keeps the accumulator unscaled and divides once at the end, as you did here. This form uses fewer operations. Both forms give the same result.

A decoder makes one token at a time. Without a cache, each new token computes the keys and values of the whole prefix again. A KV cache stores the key and the value of each step once. Then each new token needs only one query against the stored keys and values.

Task

Write a class KVCache and a function decode_step.

KVCache(max_len, d_k, d_v) makes an empty cache with room for max_len steps. It has these methods:

  1. append(k, v) adds one or more steps after the steps that are already in the cache. A 1D k of shape (d_k,) is one step. A 2D k of shape (n, d_k) is n steps. The same rule applies to v.
  2. keys() returns the stored keys, in the order of the appends, with shape (len, d_k).
  3. values() returns the stored values with shape (len, d_v).
  4. len(cache) returns the number of stored steps.

append raises ValueError in two cases:

  • the new steps do not fit, that is, len(cache) + n > max_len;
  • k and v have different numbers of steps.

When append raises, the cache does not change.

decode_step(q, cache) computes the attention of one query over the cache. Let K be cache.keys() and V be cache.values(). The scores are s=Kq/dk​​. The weights are the softmax of s. The output is the weights times V.

import numpy as np


class KVCache:
    def __init__(self, max_len, d_k, d_v):
        self.max_len = max_len
        self.K = np.zeros((max_len, d_k))
        self.V = np.zeros((max_len, d_v))
        self.length = 0

    def append(self, k, v):
        k = np.atleast_2d(np.asarray(k, dtype=float))
        v = np.atleast_2d(np.asarray(v, dtype=float))
        n = k.shape[0]
        if v.shape[0] != n:
            raise ValueError("k and v must have the same number of steps")
        if self.length + n > self.max_len:
            raise ValueError("the cache is full")
        self.K[self.length:self.length + n] = k
        self.V[self.length:self.length + n] = v
        self.length += n

    def keys(self):
        return self.K[:self.length]

    def values(self):
        return self.V[:self.length]

    def __len__(self):
        return self.length


def softmax(x):
    shifted = x - np.max(x, axis=-1, keepdims=True)
    exp_x = np.exp(shifted)
    return exp_x / np.sum(exp_x, axis=-1, keepdims=True)


def decode_step(q, cache):
    q = np.asarray(q, dtype=float)
    scores = cache.keys() @ q / np.sqrt(q.shape[-1])
    weights = softmax(scores)
    return weights @ cache.values(), weights

Why the cache gives the same answer

In a causal decoder, step t attends only to steps 0 to t. The keys and values of those steps do not change when new tokens come. So the cache can store them once. The output of step t with the cache equals row t of full causal attention. The check that compares the two is the main test of any cache.

Why a fixed capacity

A serving engine allocates the cache memory before it runs a request. It does not grow an array at each step, because a copy of a large cache at each step is slow. So the cache has a fixed max_len, and an append past the end is an error. The check before the write keeps the cache valid after the error.

The cost of the cache

Each layer stores one key and one value for each token and each key and value head. The memory is 2×N×layers×headskv​×dhead​×bytes. At long context this memory is often larger than the weights. Grouped query attention reduces the number of key and value heads for this reason.

Solutions

SolutionP1 · About 4 times here, and growing

About 4 times slower here: roughly 9 seconds with the cache and 35 without, for identical tokens. Without the cache, step t reprocesses all t tokens, about 21,500 token states per layer over the 200 steps instead of 207; the gap is "only" 4× because for a model this small each step's fixed overhead (Python, launching operations) is large compared with the arithmetic. The ratio grows with the length of the text: at thousands of tokens, recomputation dominates completely, which is why no serving system decodes without a cache.

SolutionB1 · Blocks weighted on different scales

Each block's exponentials are computed relative to the maximum seen so far. Without rescaling, contributions accumulated under an old, smaller maximum are not shrunk when a larger score arrives, so earlier blocks keep weights computed on a different scale from later ones and the output becomes a wrongly weighted mixture. With one block there is only one maximum, so the bug is invisible. The error is largest when a much higher score appears late in the sequence: the early blocks' terms are then too large by a factor of emnew​−mold​, which can be enormous, and the sum can even overflow. Testing a tiled kernel only with inputs whose maximum comes first would never catch it.

Estimate itYou serve Qwen/Qwen3-8B on one GPU with a maximum model length of 8,192 tokens. At startup the server prints a maximum concurrency of 2.94, and a manager asks if the GPU can serve only three users at a time. Your users send about 512 prompt tokens and get about 128 tokens back. How do you answer?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. The startup number assumes that every user fills the full maximum model length, and real users hold much less. Count the KV bytes for one token, divide the KV pool by that number, and then divide the pool by the context that one user really holds. On the L4 in the vLLM manual, the pool of 24,096 tokens fits 37 users with 640 tokens each.

Bytes for one token.

Every token in a running request keeps its keys and values in GPU memory until the request ends:

KV bytes per token = layers x KV heads x head size x 2 x bytes per value

The factor 2 counts the key and the value. Qwen/Qwen3-8B has 36 layers, 8 KV heads and a head size of 128. In BF16 a value takes 2 bytes, so one token takes 144 KiB. The KV heads decide this number, not the parameter count: Qwen/Qwen3-30B-A3B-Instruct-2507 has more weights but takes 96 KiB for each token.

From bytes to users.

The server gives the KV cache the memory that is left after the weights and the startup profile. The pool line in the log gives the result in tokens:

GPU KV cache size: 24,096 tokens, Maximum concurrency for 8,192 tokens per request: 2.94x

The 2.94 divides the pool by the full 8,192 tokens. A user with 512 prompt tokens and 128 output tokens holds 640 tokens at the end of the answer. The same pool holds 37 such users. During the load sweep the log showed 40 running requests with the cache 99.5 percent full, because users early in their answer hold fewer tokens.

What to change if it is still too small.

  1. Lower the maximum model length to the longest context that users send. This keeps one long request from taking a large share of the pool. It does not add users here, because the pool stays the same.
  2. Use an FP8 KV cache. It halves the bytes per token.
  3. Use FP8 weights to free memory for the cache.
  4. Use a GPU with more memory, or split the model across GPUs.

Plausible wrong answers.

  • "Divide the GPU memory by the model size." The weights are only one part. The users that fit depend on the KV pool and on the context per user.
  • "The maximum concurrency in the log is the user limit." It assumes that each user fills the maximum model length, which real users do not.
  • "More parameters always mean more KV memory per token." The bytes per token depend on the layers, the KV heads and the head size.

  • (level 2) What happens to a request that needs more blocks than are free? Expected: it waits in the queue. A running request that needs a block when none is free is stopped and computed again later.
  • (level 2) Why does the mixture-of-experts model use less KV memory per token than the dense model? Expected: it has fewer KV heads, and the KV heads, not the weights, set the bytes per token.
  • (level 3) How do you check your count after a start? Expected: read the memory line and the pool line in the startup log, and compare them with the count from the model config.

Estimate itA decoder generates 100 tokens one at a time from an empty prompt. Count the token states each loop computes for the prefix: a naive loop, and a loop that caches the key and value vectors of earlier tokens. Then count the query-key comparisons that remain with the store, and name what the store deliberately leaves out.

Level 1 of 4 · about 6 minutes to answer well.

Short answer. The naive loop runs every prefix token through the layer again at every step, so it computes 1 plus 2 plus 3 and so on up to 100 token states, which is 5050 and grows with the square of the length. With the stored keys and values, each step computes the state of the new token only, 100 in total. The new query still meets every stored key, so the cached loop still makes 5050 query-key comparisons: the store removes the recomputed key and value vectors, not the comparisons. The store holds no queries, because a past token never asks a question again; only the newest token does.

Why the prefix can be reused.

Every hidden state of a prefix token is deterministic once it is computed, and the causal mask means it never depends on a later token. So the key and the value of token t are the same at step t plus one as they were at step t. Recomputing them is pure waste.

The two loops.

naive:   step t recomputes t token states       -> 1 + 2 + ... + N = N (N + 1) / 2
cached:  step t computes one new token state    -> N
cached:  its one query meets t stored keys      -> N (N + 1) / 2 comparisons

For N equal to 100 the naive count is 5050 token states and the cached count is 100. The lesson's code runs a ten-token example and counts query-key comparisons instead: it prints the same count for both loops and confirms that the outputs match. At 100 tokens those comparisons total 5050 in both loops, so the attention step itself still grows with the length at each step. For a response of a few thousand tokens the naive count of token states is in the millions, most of them redundant.

What is stored.

Per layer and per head, two growing lists: the keys and the values of every token so far.

class KVCache:
    def append(self, layer, head, k, v):
        self.K[layer][head].append(k)
        self.V[layer][head].append(v)

The memory grows linearly with the generated length; that is the price for not recomputing the prefix.

Why queries are not stored.

The query of a token is used once, at the step where that token is the newest one. After that, the token is only ever looked up, never looking. Storing queries would cost memory and buy nothing.

What does not go away.

Generation is still serial: step t needs the token from step t minus one. The lesson calls this the autoregressive tax. Training avoids it by processing the whole sequence in one masked pass; inference cannot.

Plausible wrong answers.

  • "The store keeps the attention weights." It keeps keys and values; the weights are recomputed from the new query every step.
  • "The store saves memory." It costs memory and saves compute; the trade is memory for the recomputed key and value vectors.
  • "Queries must be stored too." A past token's query is never used again.

Follow-ups an interviewer may ask.

  • (level 1) What grows in memory as generation proceeds? Expected: the stored keys and values, per layer and per head, one entry per generated token.
  • (level 2) Why is a prefix token's key still valid after new tokens arrive? Expected: the causal mask means its hidden state only ever depended on earlier tokens, so later tokens cannot change it.
  • (level 2) You edit one word in the middle of the prompt. What happens to the store? Expected: everything from that position on is invalid and must be recomputed; the part before it stays valid.
  • (level 3) When does attention become bound by memory traffic instead of arithmetic? Expected: when the N by N score matrix is large enough that moving it through memory dominates; the lesson puts that at about 2K tokens and beyond.

Explain the mechanismA colleague refuses to enable Flash Attention on a quality-sensitive model because "approximate attention changes the outputs". Is it an approximation? Explain what the kernel changes and what it keeps, with the memory argument that motivated it.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. It is exact. The kernel tiles the computation so the full N by N score matrix never lands in the GPU's main memory; each tile is scored, exponentiated and accumulated in on-chip memory with a running maximum and a running sum, and the final normalization matches the single-pass softmax up to floating-point reordering. What changes is the memory traffic: three round trips to main memory become one write per output tile, and the footprint drops from N squared to N. The numbers that leave the kernel are the same as standard attention.

Why standard attention is slow.

S = Q @ K^T       read Q and K, write an N x N matrix
P = softmax(S)    read N x N, write N x N
O = P @ V         read N x N and V, write N x d

Three round trips through high-bandwidth memory. On the reference accelerator that memory moves about 3 TB/s while the on-chip memory moves about 30 TB/s, so every round trip is a factor-of-ten slowdown against keeping the data on chip. From about 2K tokens, attention becomes memory-bound before it becomes compute-bound, and classic kernels underuse the hardware by 4 to 10 times.

The tiling.

for each block of Q (about 128 x 128):
    load the Q tile on chip
    for each block of K, V:
        load the K and V tiles on chip
        scores for the tile
        running softmax aggregation
        accumulate into the output tile
    write the output tile once

The score matrix exists only one tile at a time. The backward pass recomputes some values instead of storing them, which is a second memory win.

Why the result is exact.

The softmax needs the global maximum and the global sum over a row, and the kernel only sees one tile at a time. It keeps a running pair, maximum and sum, and whenever a new tile raises the maximum it rescales the earlier sum and the earlier partial output by the exponential of the old maximum minus the new one. At the end every term is expressed against the same global maximum and divided by the same global sum. The lesson's description is "bit-identical output to standard attention", with the caveat that 16-bit arithmetic is not associative, so reordering can move the last bits.

What to tell the colleague.

Run the two kernels on the same inputs and compare the outputs. The difference is at the level of 16-bit rounding, the same noise you get from a different batch size, not a change to the model.

Plausible wrong answers.

  • "It drops small attention weights to save work." Nothing is dropped; every key contributes through the running sum.
  • "It only helps at very long context." It helps whenever attention is memory-bound, and the lesson reports 2 to 4 times on the earlier accelerator for ordinary lengths.
  • "It reduces the FLOPs of attention." The arithmetic is the same; the saving is in memory traffic.

Follow-ups an interviewer may ask.

  • (level 3) Why does the kernel keep a running maximum and not just a running sum? Expected: numerical stability; exponentials of raw scores overflow, so every exponential is taken relative to the maximum seen so far and rescaled when it changes.
  • (level 3) Why recompute values during training instead of storing the softmax output? Expected: storing it would mean materializing the N by N matrix, which is the thing the kernel avoids.
  • (level 4) The newest version is forward-only at launch. What does that mean for your stack? Expected: serving can use it, training keeps the previous version until the backward kernel ships.
  • (level 4) Is the output identical across batch sizes? Expected: not bit for bit, because the reduction order changes in 16-bit arithmetic; that is a determinism question, not an approximation.

It computes the attention output for one query against keys and values in blocks of four. python def tiled_softmax_dot(q, K, V, tile=4): m = float("-inf") s = 0.0 out = [0.0] * len(V[0]) for start in range(0, len(K), tile): k_block = K[start:start + tile] v_block = V[start:start + tile] scores = [sum(qi * ki for qi, ki in zip(q, k)) for k in k_block] new_m = max(m, *scores) exp_old = math.exp(m - new_m) if m != float("-inf") else 0.0 exp_new = [math.exp(sc - new_m) for sc in scores] s = s * exp_old + sum(exp_new) for j in range(len(out)): out[j] = out[j] * exp_old + sum(e * v[j] for e, v in zip(exp_new, v_block)) m = new_m return [o / s for o in out] Explain the role of exp_old, argue that the result equals the one-shot softmax(qK^T) V, and point at the input that makes this code produce a NaN.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The loop keeps a running maximum m and a running sum s over the blocks seen so far. When a block raises the maximum, exp_old is the exponential of the old maximum minus the new one, and it rescales the sum and the partial output so that every earlier term is expressed against the new maximum; a block that does not raise the maximum gives exp_old of one. At the end each weight is the exponential of its score minus the global maximum, divided by the global sum, which is exactly the stable softmax. The fragile input is a first block whose scores are all minus infinity, as a fully masked block would be: new_m stays minus infinity, and exp_new evaluates minus infinity minus minus infinity, which is NaN.

The invariant.

After each block, out holds the sum over all keys seen so far of exp(score - m) * v, and s holds the sum of exp(score - m), both relative to the current m. The identity that makes the rescale correct is

exp(score - m_new) = exp(score - m_old) * exp(m_old - m_new)

so multiplying the old accumulators by exp(m_old - m_new) moves them to the new reference point without touching any individual score again. The first block has no old reference, which is why exp_old is zero when m is still minus infinity: the empty accumulators contribute nothing.

Why the final division is exact.

Division by s happens once, at the end, with the global maximum in every exponential. That is the definition of a numerically stable softmax over the whole row, computed without ever holding the whole row. The working set is one block of keys and values and one output vector. The real kernel does this per block of queries, with blocks of keys and values streamed through on-chip memory, and writes each output tile once.

The NaN.

A causal kernel skips blocks that lie entirely above the diagonal; a kernel that applies the mask by setting scores to minus infinity must guard the case where every score in the block is minus infinity. Here max(-inf, -inf, ...) is minus infinity, and exp(-inf - (-inf)) is NaN, which then poisons s and out. The guard: skip a block whose maximum is minus infinity, or test new_m before computing exp_new.

What a reviewer tests.

  1. Equality with the one-shot softmax on random inputs, within floating-point tolerance.
  2. A second block whose scores are all lower than the first block's maximum, so that the rescale path with exp_old equal to one is exercised.
  3. A block whose scores are all higher, so that exp_old is less than one and the earlier terms shrink.
  4. A fully masked first block, which must not produce NaN.

Plausible wrong answers.

  • "exp_old is a decay factor like a learning rate." It is an exact change of reference point; the output is identical to the one-shot formula.
  • "You could store the scores and normalize at the end." That stores the full row, which is the memory cost the kernel exists to avoid.
  • "Each block should be normalized by its own sum." A per-block normalization breaks the global softmax; only the final division is correct.

Follow-ups an interviewer may ask.

  • (level 3) What does a smaller tile cost and buy? Expected: more rescale steps and more loop overhead against a smaller working set on chip; the real kernel picks the tile to fit on-chip memory.
  • (level 3) Why is exp_old set to zero and not one on the first block? Expected: there is no earlier term to carry; the accumulators are empty, and exp(-inf - new_m) would be zero anyway for a finite new_m.
  • (level 4) How does the causal mask change the loop in a production kernel? Expected: blocks fully above the diagonal are skipped rather than masked, and partially masked blocks apply minus infinity per entry before the maximum is taken.
  • (level 4) Where does the backward pass get the softmax values it needs? Expected: it recomputes them from the stored row maximum and row sum instead of storing the N by N matrix.
