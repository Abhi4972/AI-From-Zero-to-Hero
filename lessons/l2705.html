Why this came about

Until 2022, using a strong language model meant calling one company's API. In February 2023 Meta released LLaMA's weights to researchers; they leaked within a week, and a wave of open-weight models followed: Llama 2 and 3, Mistral, Qwen, Gemma, DeepSeek and many more, some close to the best closed models. At the same time, tools like llama.cpp (2023) and Ollama made it easy to run quantised models on ordinary laptops. Teams now choose among hosted frontier modelslater · 10.43, cheaper hosted small models, and open models they run themselves, and often use several at once.

In plain words first
Renting a chef or hiring one

Using a hosted API is like ordering from a top restaurant: excellent food, no kitchen to run, you pay per dish, and the recipe is theirs. Running an open model is like hiring a cook for your own kitchen: you pay for the kitchen whether it is busy or not, you control everything, and nothing leaves the building, but quality depends on the cook you can afford. For most dishes the restaurant is simpler; at very high volume, or when the ingredients must not leave your premises, your own kitchen can make sense.

Step 2 · Estimating cost

APIs charge per million tokens, with output tokens usually several times more expensive than input tokens. A support assistant's monthly bill, with example prices (check each provider's current pricing page):

def monthly_cost(requests_per_day, input_tokens, output_tokens, price_in, price_out, days=30):
    """Prices in dollars per million tokens."""
    per_request = (input_tokens * price_in + output_tokens * price_out) / 1e6
    return per_request, per_request * requests_per_day * days

example_prices = {"large frontier model": (3.00, 15.00), "small fast model": (0.25, 1.25)}   # illustrative only
for name, (p_in, p_out) in example_prices.items():
    per, month = monthly_cost(requests_per_day=5_000, input_tokens=3_000, output_tokens=400, price_in=p_in, price_out=p_out)
    print(f"{name:<22} ${per:.4f} per request   ${month:>9,.0f} per month")
What you should see
large frontier model   $0.0150 per request   $    2,250 per month
small fast model       $0.0013 per request   $      188 per month
Reading this output
  • With 3,000 input tokens per request (instructions, retrieved documents and conversation history) and 400 output tokens, input dominates the bill for the small model and is a large share for the big one. Context design (Lesson 11.27) and prompt cachinglater · 11.23 (Lesson 11.23) are often the biggest cost levers.
  • A twelvefold price difference between models is common. Routing easy requests to a small model and hard ones to a large model (Lesson 14.136) can cut costs a lot.

Self-hosting changes the shape of the cost: you pay for GPUs by the hour, so the cost per token depends on how busy they are:

def self_host_cost_per_million(gpu_dollars_per_hour, tokens_per_second, utilisation):
    tokens_per_hour = tokens_per_second * 3600 * utilisation
    return gpu_dollars_per_hour / tokens_per_hour * 1e6

for util in [0.05, 0.25, 0.75]:
    cost = self_host_cost_per_million(gpu_dollars_per_hour=4.0, tokens_per_second=2_500, utilisation=util)
    print(f"GPU busy {util:>4.0%} of the time: ${cost:.2f} per million output tokens")
What you should see
GPU busy   5% of the time: $8.89 per million output tokens
GPU busy  25% of the time: $1.78 per million output tokens
GPU busy  75% of the time: $0.59 per million output tokens

A server handling many requests in parallel can produce thousands of tokens per second (the figure above is an assumption for a mid-sized model on one data-centre GPU). Busy, it can be cheap; mostly idle, it is expensive. Add engineering time, monitoring and spare capacity, and self-hosting usually pays off only at high, steady volume or when data rules require it.

Step 3 · Will it fit?

From Lesson 3.20: weights need parameters × bytes per parameter, plus room for the KV cache and the runtime.

def fits(params_billion, bytes_per_param, memory_gb, overhead_gb=2.0):
    need = params_billion * bytes_per_param + overhead_gb
    return need, need <= memory_gb

machines = {"laptop, 16 GB RAM": 16, "gaming GPU, 24 GB": 24, "data-centre GPU, 80 GB": 80}
for model, params in [("3B", 3), ("8B", 8), ("32B", 32), ("70B", 70)]:
    cells = []
    for fmt, b in [("bf16", 2), ("4-bit", 0.55)]:          # 4-bit files also store scales, so a little over 0.5 bytes
        need = params * b + 2.0
        where = [m for m, mem in machines.items() if need <= mem]
        cells.append(f"{fmt}: {need:5.1f} GB -> {where[0] if where else 'needs several GPUs'}")
    print(f"{model:>4}  " + "   |   ".join(cells))
What you should see
  3B  bf16:   8.0 GB -> laptop, 16 GB RAM   |   4-bit:   3.7 GB -> laptop, 16 GB RAM
  8B  bf16:  18.0 GB -> gaming GPU, 24 GB   |   4-bit:   6.4 GB -> laptop, 16 GB RAM
 32B  bf16:  66.0 GB -> data-centre GPU, 80 GB   |   4-bit:  19.6 GB -> gaming GPU, 24 GB
 70B  bf16: 142.0 GB -> needs several GPUs   |   4-bit:  40.5 GB -> data-centre GPU, 80 GB

On a laptop, models up to about 8 billion parameters in 4-bit run comfortably (unified-memory Macs can go further); 70B models need serious hardware even when quantised. Speed matters as much as fit: generation speed is limited by how fast memory can be read (Lesson 3.20), so the same model runs much faster on a GPU than from laptop RAM.

Step 4 · Running a small model locally in Python

The instruction-tuned SmolLM2 from Lesson 10.36 runs on any laptop CPU. Here is a minimal chat loop that keeps the conversation history, so the model sees earlier turns:

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

name = "HuggingFaceTB/SmolLM2-360M-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)
model.eval()

history = [{"role": "system", "content": "You are a friendly support agent for an online shop. Keep answers short."}]

def chat(user_message, max_new_tokens=50):
    history.append({"role": "user", "content": user_message})
    ids = tok.apply_chat_template(history, add_generation_prompt=True, return_tensors="pt", return_dict=True)
    with torch.no_grad():
        out = model.generate(**ids, max_new_tokens=max_new_tokens, do_sample=False, pad_token_id=tok.eos_token_id)
    reply = tok.decode(out[0][ids["input_ids"].shape[1]:], skip_special_tokens=True).strip()
    history.append({"role": "assistant", "content": reply})       # remember the reply for the next turn
    return reply

for message in ["Hi, my name is Ravi. My parcel SK-48213 is two days late.", "What is my name and my order number?"]:
    print("USER:", message)
    print("BOT: ", chat(message))
print("messages in the history:", len(history))
What you should see
USER: Hi, my name is Ravi. My parcel SK-48213 is two days late.
BOT:  Hi Ravi, I'm sorry to hear that your parcel is delayed. Can you please provide me with the order number and the estimated delivery date so I can check if it's been sent?
USER: What is my name and my order number?
BOT:  My name is Ravi, and your order number is SK-48213.
messages in the history: 5

The second answer recalls the name and the order number, though with a small slip ("My name is Ravi" instead of "Your name is Ravi"), and the first answer asks for an order number the customer already gave: a 360-million-parameter model is easily confused. The important part is how it could recall anything: the model has no memory of its own, and "remembering" the first message works only because the whole history is sent again every turn. That is also why long conversations cost more (Lesson 14.64 covers memory in agents). The same code works with any chat model from the Hub, given enough memory.

Step 5 · Ollama and llama.cpp

For everyday local use, Ollama downloads quantised models and runs a local server with one command (install it from ollama.com first):

ollama pull llama3.2          # a 3B model, about 2 GB in 4-bit
ollama run llama3.2 "Write a two-sentence apology for a late delivery."

The server listens on localhost:11434 and also offers an OpenAI-compatible endpoint, so code written for hosted APIs (the Talking to models: APIs, messages, prompts and context section) can point at it by changing the base URL:

import requests

reply = requests.post("http://localhost:11434/api/chat", json={
    "model": "llama3.2",
    "messages": [{"role": "user", "content": "Where is my order?"}],
    "stream": False,
}).json()
print(reply["message"]["content"])

llama.cpp is the engine underneath many such tools; its GGUF files hold quantised weights (Lesson 3.20) in variants such as Q4_K_M (about 4.8 bits per weight) and Q8_0. LM Studio and similar desktop apps put a graphical interface on the same engine. For serving many users, engines such as vLLMlater · 3.25 and SGLang are used instead (Lesson 14.137).

Step 6 · How to actually choose

  1. Write down what good looks like: 20 to 100 real examples of the task with expected answers or grading rules.
  2. Try a strong model first to learn whether the task is solvable at all.
  3. Try cheaper and smaller candidates on the same examples; keep the cheapest that passes.
  4. Check the non-quality needs: latency, data rules, cost at your volume, licence (for open weights).
  5. Re-test when models change. Providers update and retire models; your examples become your regression test (Lesson 14.143).

Public leaderboards and benchmarks are a useful first filter, but your own examples decide.

The same idea as a formula
  • API cost per request = (input tokens × input price + output tokens × output price) / 10⁶
  • self-hosted cost per million tokens = (GPU cost per hour) / (tokens per second × 3,600 × utilisation) × 10⁶
  • memory needed ≈ parameters × bytes per parameter + KV cache + runtime overhead
Check your mental model
  • ✗ "Open-weight models are free."
    ✓ The weights are free to download (under their licence); running them costs hardware, energy and engineering time.
  • ✗ "A chat model remembers earlier conversations."
    ✓ It sees only what is sent in the current request; memory is built by your code resending history or retrieving it.
  • ✗ "The best model on a public leaderboard is the best model for my task."
    ✓ Leaderboards measure general tasks. Your own examples, costs and constraints decide.

Practice
Apply it

Your team handles 2,000 requests a day, each with 1,500 input and 300 output tokens. Using the example prices, compare the large and small models' monthly costs. If the small model passes your tests on 85% of requests and the rest are routed to the large model, what is the blended monthly cost? (Solution X1.)

Solutions

SolutionP1 · Bigger prompts

For the small model, input cost per request rises from 3,000 × 0.25 / 10⁶ = $0.00075 to 12,000 × 0.25 / 10⁶ = $0.003, while output stays at $0.0005. The total per request goes from $0.00125 to $0.0035, about 2.8 times as much: from about $188 to about $525 a month. Prompt size is often the biggest cost driver.

SolutionM1 · A growing history

Each turn adds the user's message and the reply, so the history grows by tens of tokens per turn here, and every request resends all of it. Over a long conversation this adds up quickly, which is why chat products summarise or trim older turns (Lessons 11.27 and 14.64).

SolutionX1 · Routing

Large model only: (1,500 × 3 + 300 × 15) / 10⁶ = $0.009 per request, × 2,000 × 30 = $540 a month. Small model only: (1,500 × 0.25 + 300 × 1.25) / 10⁶ = $0.00075, about $45 a month. Blended: 85% small and 15% large = 0.85 × 45 + 0.15 × 540 ≈ $38 + $81 = $119 a month, plus the cost of deciding which requests to route (Lesson 14.136).

Recap
  • Options range from hosted frontier APIs to hosted open models, self-hosted open models and local quantised models; each trades quality, cost, privacy, control and effort differently.
  • API cost is tokens × price; input tokens often dominate, so context size matters. Self-hosting pays per GPU-hour and is only cheap when busy.
  • Memory needed is parameters × bytes per parameter plus cache and overhead; 4-bit quantisation brings 8B models to laptops.
  • Local models run through transformers in Python, or through Ollama and llama.cpp with OpenAI-compatible servers.
  • Choose by testing candidates on your own examples and keeping the cheapest that passes.

Q1A request has 4,000 input and 200 output tokens. Input costs $1 and output $5 per million tokens. What does one request cost?

(4,000 × 1 + 200 × 5) / 1,000,000 = $0.005.

Q2Why does a self-hosted model's cost per token rise when traffic is low?

Fixed hourly cost divided by fewer tokens.

Q3How does a chat model "remember" earlier turns of a conversation?

Memory lives in the request, not in the model.
