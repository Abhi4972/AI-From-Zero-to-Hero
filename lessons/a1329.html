In plain words first
The idea in one line

A request ID correlates a message. It does not make a side effect safe, stop a worker, or protect a stream from a slow consumer.

Terms you'll hear
Term Meaning
Request cancellation Abandonment of one in-flight MCP request
Cancellation race Competition between terminal completion and cancellation events
Idle timeout Limit since the last useful request activity
Maximum timeout Absolute limit from request start, unaffected by progress
Idempotency key Application identifier that deduplicates one business intent
Atomic ledger Durable boundary that commits the key claim, effect record, and result as one unit
Backpressure Control applied when producers outpace consumers
Progress coalescing Replacing older progress with a newer authoritative value
Refetch Reading current state again after a stream gap
Jitter Deliberate variation that spreads retries across time

The problem

In plain words first

Real tool calls fail in the middle. A user gives up and cancels; a request takes too long; a network connection drops after the server already did the work but before the answer arrived. Each case needs a precise rule. Cancelling means telling the server to stop (on stdio with a message, on HTTP by closing the response stream), and both sides must accept that the server might finish anyway. A timeout needs two clocks: one that progress updates can reset, and one hard deadline that nothing resets. Retrying is only safe for reads, or for changes that carry an idempotency key, a name the server uses to recognise a repeat. This lesson cancels real calls to an SDK server under a two-clock policy and then retries a payment through the lesson's durable ledger, with and without a key.

The happy path hides the most expensive distributed-systems bugs.

A client calls a tool. The server starts work. Progress arrives. A proxy buffers the stream. The client reaches its timeout and disconnects. The server finishes one millisecond later. The client retries with a new JSON-RPC id. The mutation runs twice.

Every component behaved locally. The system failed globally.

MCP defines message and transport behavior, but your application still owns:

  • time budgets;
  • business idempotency;
  • bounded queues;
  • retry classification;
  • durable task state;
  • reconnect and refetch policy.

This lesson builds those decisions into a deterministic simulator. There are no sleeps, sockets, or random failures. You control cancellation event order directly. One synchronized thread test forces two ledger clients to compete for the same idempotency key.

Request Cancellation Is Transport-Specific

The intent is the same on every transport: the client no longer needs an in-flight result. The wire signal is different.

stdio

stdio uses one shared bidirectional channel. A client sends a notification:

{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": 41,
    "reason": "User closed the operation"
  }
}

The notification is fire-and-forget. The server emits no JSON-RPC response to it.

The server should stop work, free resources, and avoid sending a response for the cancelled request. It may ignore cancellation when the request is unknown, already finished, or cannot be stopped safely.

Malformed, unknown, and already completed cancellation notifications are ignored. Turning those races into new errors would create more races.

Streamable HTTP

Modern Streamable HTTP gives each request its own HTTP response or SSE response stream. The client cancels by closing that request's response stream.

Do not POST notifications/cancelled for an ordinary HTTP request. Stream closure is the cancellation signal.

Once the server observes the disconnect, it should stop work and must not send more messages for that request.

Server-sent cancellation is narrow

A server does not use notifications/cancelled to cancel arbitrary client calls. On stdio, server-sent cancellation is reserved for terminating a subscriptions/listen request. Keep that path separate from ordinary client-request cancellation.

Cancellation Is a Race

Two event orders are both valid.

Cancellation wins

request starts
client sends cancellation signal
server marks request cancelled
worker reaches completion
server suppresses the response

Completion wins

request starts
worker commits the result
server sends the response
cancellation arrives late
server ignores the late notification

The client must also ignore a late response for a request it already abandoned. Network latency means neither side can prove which event the other side observed first.

The lesson's RequestCoordinator stores one terminal state. complete() returns no response after cancellation. A late cancellation cannot change a completed record.

Timeouts Need Two Clocks

A single inactivity timer is not enough.

Use two limits:

  1. Idle timeout. How long the request may produce no useful activity.
  2. Maximum timeout. The absolute wall-clock budget from request start.

Progress may reset the idle clock. It must never remove the maximum deadline.

start: 0 ms
progress: 400 ms
progress: 800 ms
progress: 1200 ms
idle timeout: 500 ms
maximum timeout: 2000 ms

At 1500 ms, the request is still active because the latest progress is only 300 ms old. At 2000 ms, the maximum deadline cancels it even if another progress event arrived at 1999 ms.

Progress is optional. A server can accept a progress token and emit no updates. Never turn the presence of a token into an infinite timeout.

MCP progress values must increase. Notifications stop after completion or cancellation. Rate-limit progress so a fast worker cannot flood the transport.

Request Cancellation Is Not tasks/cancel

These mechanisms solve different lifetimes.

Mechanism Target Signal What success means
Request cancellation on stdio One in-flight RPC notifications/cancelled Client abandoned the request; server should stop if practical
Request cancellation on HTTP One in-flight response stream Close the stream Client abandoned the request; server should stop if practical
tasks/cancel One durable Task Ordinary MCP request Server acknowledged cancellation intent

A successful tasks/cancel result does not prove the worker stopped. The task may remain working until a worker checkpoint observes the flag. Work may complete before that checkpoint.

Do not erase durable task state when the HTTP connection closes. The reason to create a Task is that its lifecycle outlives one request and one connection.

A New JSON-RPC ID Is Not Idempotency

JSON-RPC ids correlate requests and responses. They do not identify a business operation.

Suppose a client submits a charge with id 41, loses the response, and retries with id 42. The server sees two different messages. Without an application key, it cannot know they represent one checkout.

An idempotency key identifies the business intent:

{
  "name": "charge_account",
  "arguments": {
    "account": "acct-7",
    "cents": 1200,
    "idempotencyKey": "checkout-7"
  }
}

The server stores:

  • the key;
  • a fingerprint of operation arguments;
  • the committed result.

The same key and same arguments return the stored result. The same key with different arguments is rejected. This prevents accidental key reuse from mutating a different business operation.

The ledger boundary must be atomic and durable

This sequence is unsafe:

check key
run mutation
store result

Two workers can both observe a missing key and both run the mutation. A crash after the effect but before the store creates the same ambiguity on retry.

The lesson uses a file-backed SQLite ledger. BEGIN IMMEDIATE serializes the key check, simulated business effect, execution counter, and stored result into one transaction. Two independent ledger connections racing with the same key therefore observe one committed result and one execution. Closing and reopening the ledger keeps that record.

Every return value is reconstructed from stored JSON. The caller never receives the mutable object held by the ledger, so changing a returned dictionary cannot corrupt later replay results.

The simulator's business effect is the receipt and execution counter inside the same SQLite transaction. A real payment, deployment, or external API call is not made atomic merely by writing a local table. Production needs a durable shared database transaction, a transactional outbox, or an upstream provider that enforces the same idempotency key. A process lock alone does not protect multiple replicas or survive a restart.

Retry matrix

Classify retries before implementing them.

Class Example Retry rule
Safe Deterministic read with no side effect Retry with a new JSON-RPC id after the failure boundary is understood
Conditional Mutation with a durable idempotency key Retry with the same key and identical arguments
Unsafe Mutation without business deduplication Do not retry automatically; reconcile first

Tool annotations such as readOnlyHint and idempotentHint remain untrusted hints. The application contract and server implementation decide retry safety.

Backpressure Is Part of Correctness

An SSE producer can generate progress faster than a client, proxy, or network can consume it. An unbounded queue converts slowness into memory exhaustion.

Use a bounded queue and define what can be lost.

Progress is replaceable. A later progress value supersedes an earlier one for the same token. A final JSON-RPC response is not replaceable.

The lesson buffer applies this policy:

  1. Coalesce adjacent progress for the same token.
  2. Drop the oldest progress when capacity is reached.
  3. Mark the stream as needing authoritative refetch.
  4. Preserve the final response.
  5. Refuse a state where preserving the final response would require dropping another final response.

This is bounded loss with explicit recovery. Silent loss is not a strategy.

Proxy buffering

A server can stream correctly while a reverse proxy holds events in a buffer.

For an SSE response, send:

Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

The 2026 Streamable HTTP specification recommends X-Accel-Buffering: no so compatible proxies deliver events immediately.

For quiet long-lived streams, periodically emit an SSE comment:

:

The client ignores comment lines. Intermediaries see traffic and are less likely to close an idle connection.

Keepalive is not progress. Do not reset an operation's semantic idle timeout merely because a transport comment arrived.

Reconnect Means Refetch

Modern Streamable HTTP does not support resumable SSE through Last-Event-ID.

After a subscriptions/listen stream drops:

  1. Open a new listen request with a new JSON-RPC id.
  2. Restore the desired subscription filter.
  3. Refetch affected tools, resources, prompts, or Tasks from authoritative methods.
  4. Deduplicate application state by stable identifiers.
  5. Do not replay an unsafe mutation just because its response was lost.

The sample recovery plan explicitly sets sendLastEventId to false and lists resources to refetch.

Prevent a reconnect herd

If 10,000 clients reconnect at exactly one second, the recovering server fails again.

Use exponential backoff with jitter and a cap. The lesson computes deterministic jitter from client id and attempt number so tests remain reproducible:

attempt 0: up to 250 ms
attempt 1: up to 500 ms
attempt 2: up to 1000 ms
...
cap: 8000 ms

Production can use cryptographically secure or runtime randomness. The invariant is distribution, not a specific formula.

The same idea as a formula

Two clocks. With request start t0​, last progress time tp​, idle limit I and maximum D, the request stays alive at time t only if

t−tp​<Iandt−t0​<D.
Progress moves tp​ forward; nothing moves t0​. So the latest cancellation time is t0​+D, however chatty the server is.

Idempotency. A mutation with key k and arguments a is applied at most once:

charge(k,a)=⎩⎨⎧​stored result(k)errorapply, then store (k,a,result) atomically​if k seen with the same aif k seen with different aotherwise.​
A new JSON-RPC id is not a key: it identifies the message, not the business operation.

Backoff with jitter. Attempt n waits a random time in [21​cn​,cn​] with cn​=min(8000,250⋅2n) ms, so clients that failed together do not all reconnect together.

Worked example
Applying the two clocks to three jobs
  • Idle limit 0.5 s, maximum 2.0 s. Each row takes 0.2 s.
  • 5 rows with progress after each: done at about 1.0 s, both clocks fine → completes.
  • 30 rows with steady progress: the idle clock never fires (gaps of 0.2 s), but at 2.0 s the maximum fires → cancelled during row 11.
  • 30 rows, progress stops after row 3 (0.6 s): the idle clock fires at about 0.6 + 0.5 = 1.1 s → cancelled, while the server is in row 6.
  • A lost-response retry of a 500-cent charge: with key order-77 there is 1 side effect; without a key, 2; reusing the key for 900 cents is rejected.
Check your mental model
  • ✗ "After I cancel, the server did not do the work."
    ✓ Cancellation races completion; the work may already be committed.
  • ✗ "Progress updates mean the request may run forever."
    ✓ Progress resets only the idle clock; the maximum deadline always applies.
  • ✗ "Retrying with a new JSON-RPC id is safe."
    ✓ For side effects, only a durable idempotency key with identical arguments makes a retry safe.
  • ✗ "tasks/cancel returning success means the work stopped."
    ✓ It acknowledges the intent; the worker stops at its next checkpoint, or finishes first.

Cancelling real calls under two clocks

The official SDK client starts the server below as a subprocess over stdio. A watchdog cancels each call when either clock expires; on stdio the SDK then sends notifications/cancelled, and the server's task is cancelled. The server writes where each export stopped. About 5 seconds.

# Real stdio cancellation with the official SDK, under a two-clock policy: an idle timeout that
# progress resets, and a maximum deadline that nothing resets. The server logs where it stopped.
import anyio, pathlib, sys, time
from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client
pathlib.Path("slow_server.py").write_text('''
import anyio, time
from mcp.server import MCPServer
from mcp.server.mcpserver import Context
s = MCPServer("slow", log_level="WARNING")
def log(m):
    with open("server.log", "a") as f: f.write(m + "\\n")
@s.tool()
async def export(rows: int, stall_after: int, ctx: Context) -> str:
    """Export rows, reporting progress; stops reporting after stall_after rows."""
    done = 0
    try:
        for done in range(1, rows + 1):
            await anyio.sleep(0.2)
            if done <= stall_after: await ctx.report_progress(done, rows)
        log(f"export(rows={rows}): finished"); return f"exported {rows} rows"
    except BaseException as e:
        log(f"export(rows={rows}): stopped during row {done} ({type(e).__name__})"); raise
s.run()
''')
open("server.log", "w").close()

async def call_with_two_clocks(c, args, idle=0.5, maximum=2.0):
    t0 = time.monotonic(); last = [t0]; why = [None]
    async def on_progress(progress, total, message): last[0] = time.monotonic()
    async with anyio.create_task_group() as tg:
        async def watchdog():
            while True:
                await anyio.sleep(0.05); now = time.monotonic()
                if now - t0 >= maximum: why[0] = "maximum deadline"; tg.cancel_scope.cancel(); return
                if now - last[0] >= idle: why[0] = "idle timeout"; tg.cancel_scope.cancel(); return
        tg.start_soon(watchdog)
        result = await c.call_tool("export", args, progress_callback=on_progress)
        tg.cancel_scope.cancel()                   # finished first: stop the watchdog
        return f"completed in {time.monotonic() - t0:.1f}s: {result.content[0].text}"
    return f"cancelled by {why[0]} after {time.monotonic() - t0:.1f}s"

async def main():
    params = StdioServerParameters(command=sys.executable, args=["slow_server.py"])
    async with Client(stdio_client(params, errlog=sys.__stderr__)) as c:
        for label, args in [("short job, steady progress", {"rows": 5, "stall_after": 5}),
                            ("long job, steady progress", {"rows": 30, "stall_after": 30}),
                            ("job that stalls after 3 rows", {"rows": 30, "stall_after": 3})]:
            print(f"{label:<30} -> {await call_with_two_clocks(c, args)}")
        await anyio.sleep(0.4)                     # let the server write its last log line
anyio.run(main)
print("\nserver log:", *open("server.log").read().split("\n")[:-1], sep="\n   ")
What you should see
short job, steady progress     -> completed in 1.0s: exported 5 rows
long job, steady progress      -> cancelled by maximum deadline after 2.0s
job that stalls after 3 rows   -> cancelled by idle timeout after 1.1s

server log:
   export(rows=5): finished
   export(rows=30): stopped during row 11 (CancelledError)
   export(rows=30): stopped during row 6 (CancelledError)
Reading this output

The short job finishes. Five rows take about 1.1 s with progress after each, well inside both clocks.

Steady progress cannot buy unlimited time. The 30-row job keeps reporting every 0.2 s, so the idle clock never fires, but the maximum deadline cancels it at 2.0 s. The server log shows it was stopped during row 11: the SDK client sent notifications/cancelled over stdio, and the server's task received CancelledError.

A stalled job is caught early. After three progress updates the job keeps running silently; 0.5 s after the last update the idle clock cancels it, at about 1.1 s, while the server was in row 6. Without the idle clock the client would have waited for the full maximum.

Cancellation is cooperative. The server stopped because its code awaits regularly; a tool that blocks in a long CPU loop or an external call would keep running until its next await, and might finish the work anyway.

Retrying a payment after a lost response

This block continues from the one above. An MCPServer tool charge is backed by the lesson's MutationLedger, an SQLite table that stores each idempotency key with its arguments and result in one transaction. Each case calls the tool, treats the answer as lost, and retries. Then classify_retry and the reconnect backoff from code/main.py. Instant.

# Continues from the block above. A charge tool backed by the lesson's MutationLedger (SQLite):
# the response is "lost" and the client retries, with and without an idempotency key.
import json, tempfile
from mcp.server import MCPServer
from main import MutationLedger, ReliabilityError, classify_retry, retry_delay_ms
ledger = MutationLedger(pathlib.Path(tempfile.mkdtemp()) / "ledger.sqlite3")
pay = MCPServer("payments", log_level="WARNING")
@pay.tool()
def charge(account: str, cents: int, idempotency_key: str | None = None) -> str:
    """Charge an account once per idempotency key."""
    try: return json.dumps(ledger.charge(account, cents, rpc_id="mcp", idempotency_key=idempotency_key))
    except ReliabilityError as e: return json.dumps({"error": str(e)})

async def retries():
    async with Client(pay) as c:
        async def call(**a): return json.loads((await c.call_tool("charge", a)).content[0].text)
        for label, first, retry in [
            ("same key, same arguments", dict(account="acct-1", cents=500, idempotency_key="order-77"), None),
            ("no key (new JSON-RPC id only)", dict(account="acct-2", cents=500), None),
            ("same key, different amount", dict(account="acct-3", cents=500, idempotency_key="order-78"),
                                            dict(account="acct-3", cents=900, idempotency_key="order-78"))]:
            before = ledger.executions
            await call(**first)                    # suppose this response is lost in transit
            again = await call(**(retry or first)) # the client retries
            print(f"{label:<32} side effects: {ledger.executions - before}  retry answer: {again}")
anyio.run(retries)

print()
for side, key in [(False, None), (True, "order-79"), (True, None)]:
    d = classify_retry(side_effect=side, idempotency_key=key)
    print(f"side_effect={side!s:<5} key={key!s:<9} -> {d.classification:<11} {d.reason}")
print("\nreconnect delays (ms) for attempts 0-4, five clients:")
for cid in ("c1", "c2", "c3", "c4", "c5"): print(f"   {cid}: {[retry_delay_ms(cid, a) for a in range(5)]}")

Reading this output

With a key, a retry is a replay. The first call charged 500 cents; the retry with the same key and arguments returned the stored receipt (charge-001) and made no new charge: 1 side effect.

Without a key, the retry charges again. The second call is a new request with a new JSON-RPC id, so the ledger cannot know it is a repeat: 2 side effects, receipt charge-003. This is the double charge that idempotency keys exist to prevent.

Reusing a key for different arguments is refused. The ledger binds the key to the account and amount; a retry asking for 900 cents under the same key is an error, not a silent second operation.

The classification follows from the contract, not from tool hints: reads are safe, keyed mutations are conditional, unkeyed mutations are unsafe. The backoff table shows each client's delays doubling with attempts while spreading out within each band, so five clients that fail together do not reconnect together.

Build · RequestCoordinator

code/main.py builds five small reliability components.

  • starts an in-flight request with idle and maximum deadlines;
  • emits monotonic progress notifications;
  • produces the correct stdio or HTTP cancellation signal;
  • ignores invalid cancellation notifications;
  • makes cancellation and completion terminal races explicit;
  • reserves server-sent cancellation for stdio subscriptions.

Build · MutationLedger

  • proves that two JSON-RPC ids execute twice without a business key;
  • uses a file-backed SQLite transaction for the key check, simulated effect, execution counter, and result commit;
  • deduplicates matching arguments under one idempotency key across independent ledger connections;
  • rejects one key reused with different arguments;
  • returns defensive copies and preserves committed records across reopen.

Build · DurableTaskService

  • acknowledges a cancellation request;
  • keeps the task working until a worker checkpoint;
  • demonstrates why acknowledgement is not final status.

Build · BoundedSseBuffer

  • coalesces or drops progress under pressure;
  • records that authoritative refetch is required;
  • never drops the final response.

Build · Recovery helpers

  • return proxy-safe SSE headers and keepalive comments;
  • create a reconnect and refetch plan;
  • spread retries with deterministic exponential backoff and jitter.

Break it on purpose

An agent framework wraps every tool call in "retry up to 3 times on timeout, with a new request each time", and its HTTP client closes the stream when the user presses Stop but keeps the server's task id in memory only. What can happen to a send_invoice tool and to a long-running Task? (Solution B1.)

Industry practice
What's current (2024–2026)
  • 2026-07-28 cancellation: on stdio, notifications/cancelled; on Streamable HTTP, closing the request's SSE stream is the cancellation, and no notification is sent. Durable work uses the Tasks extension's tasks/cancel, which is a request for cancellation, not a guarantee.
  • SDK support: the Python SDK 2.x maps anyio cancellation to these signals, as the run shows, and supports progress_callback and read timeouts per call.
  • Idempotency in production follows the payment-API pattern (Stripe-style Idempotency-Key headers), stored transactionally with the result; for remote effects, a transactional outbox keeps the local record and the remote call consistent.
  • Proxies: servers send X-Accel-Buffering: no on SSE and periodic comment keep-alives so buffering proxies do not delay progress or close idle streams.
  • On your laptop: nothing here needs a GPU; the timings are wall-clock sleeps.

Sources: MCP cancellation, 2026-07-28, Streamable HTTP, Stripe idempotent requests.

Recap
What to keep from this lesson
  • Cancellation is transport-specific and races completion; both sides handle late messages.
  • Use two clocks: idle (reset by progress) and maximum (never reset).
  • Request cancellation and tasks/cancel have different lifetimes.
  • Retry reads freely; retry mutations only with the same idempotency key and arguments.
  • Bound buffers, keep progress small, reconnect with jitter, and refetch state after reconnecting.

Solutions

SolutionP1 · Cancelled at the maximum; idle fires near 1.1 s

It will not finish. The progress every 0.2 s keeps the idle clock (0.5 s) from firing, but the maximum deadline of 2.0 s still applies, so the job is cancelled at 2.0 s, about 10 rows in, of 30.

The stalling job reports its last progress at about 0.6 s (after row 3). The idle clock fires 0.5 s later, at about 1.1 s, long before the maximum. The run shows exactly these two outcomes.

SolutionB1 · Three invoices and an orphaned task

send_invoice can run up to four times. A timeout does not mean the server did nothing: the first call may have sent the invoice and only the response was slow or lost. Each retry is a new request, so without an idempotency key the server cannot tell it is a repeat, and the customer gets duplicate invoices (or duplicate charges, emails, tickets). Retries of side effects need the same idempotency key and identical arguments, and many should not be automatic at all.

The long-running Task is orphaned. Closing the HTTP stream cancels only the in-flight request, not the durable Task, which keeps running on the server. Because the client kept the task id only in memory, a restart loses it: the work continues (and is billed) with nobody polling, and the user cannot cancel it. Store task ids durably, call tasks/cancel when the user means "stop the job", and poll or refetch its state after reconnecting.

Verify It

The lesson is complete when these statements are true:

  • stdio cancellation sends notifications/cancelled and receives no response.
  • Streamable HTTP cancellation closes the request stream and sends no cancellation POST.
  • Cancel-before-complete suppresses the final response.
  • Complete-before-cancel preserves the response and ignores the late cancellation.
  • Progress can reset idle timeout but never maximum timeout.
  • A new JSON-RPC id alone executes the mutation again.
  • One idempotency key and identical arguments execute once under a concurrent two-connection race.
  • A committed record survives reopen and replay returns a defensive copy.
  • Mutating one returned result cannot alter the stored result.
  • The bounded buffer stays within capacity and preserves the final response.
  • Reconnect uses a new request, does not send Last-Event-ID, and refetches affected state.
  • tasks/cancel acknowledgement leaves the task non-terminal until the worker observes it.

Capstone Connection

The tool-ecosystem capstone should treat reliability as executable evidence, not a paragraph in an architecture diagram.

Require these artifacts:

  • one cancellation race transcript for each transport;
  • a retry table for every exposed mutation;
  • an idempotency-key record and mismatch fixture;
  • a concurrent same-key transcript, a reopen check, and a mutation-alias check;
  • a bounded-buffer overload result;
  • reverse-proxy SSE headers and idle policy;
  • a reconnect plan that names authoritative refetch methods;
  • a durable Task cancellation trace when the capstone uses Tasks.

A green request in a local process proves only the happy path. The capstone is production-ready when lost responses, late cancellation, slow consumers, and reconnect herds have deterministic outcomes.
