The problem

In plain words first

A vision-language-action model (VLA) is a vision-language model whose answer is a movement instead of a sentence. It looks at the camera image, reads an instruction like "put the apple in the bowl", and outputs what the robot arm should do next: how far to move the gripper, how to turn it, whether to close it. The hard part is turning continuous movements into something a language model can produce, fast enough for a robot that needs new commands 5 to 120 times a second. RT-2 and OpenVLA write each number as a token from 256 bins. FAST compresses a whole second of motion into a few dozen tokens. π0 and GR00T add a small "action expert" that produces a whole chunk of smooth motion at once by flow matching. This lesson explains the four designs and their data, then tokenizes synthetic robot trajectories both ways and times each output style on a small random model. No model is trained, and no robot model is downloaded.

A robot that does chores from natural language instructions has been a research target since the 1970s. The 2020s answer: a vision-language-action (VLA) model. Same VLM architecture used for VQA, but output is actions (joint torques, end-effector poses, discrete commands) instead of text.

Challenges specific to VLAs:

  1. Action spaces are continuous and fast. A typical single-arm action is 7 numbers (a 6-DoF end-effector move plus the gripper), sent 5 to 50 times a second; a two-arm robot like ALOHA has 14, and a humanoid dozens.
  2. Robot-specific training data is scarce. Open X-Embodiment has about 1M trajectories; web image–text datasets have billions of pairs (LAION-5B has 5.85B).
  3. Control frequency matters. 30 Hz control loop means 33ms budget per action.
  4. Safety. A wrong action damages hardware, humans, or property.

Idea 1 · Action tokenization (RT-2)

RT-2's trick: write the action as text. Its action is 8 numbers: a 6-DoF change in end-effector position and rotation, the gripper extension, and a "terminate" flag. Each continuous number is discretized into 256 uniform bins, and each bin is a vocabulary token: for PaLI-X the bins are simply its number tokens, for PaLM-E the 256 least-used tokens are overwritten. One action is 8 tokens at each control step.

Co-fine-tune a VLM (PaLI-X at 5B and 55B, or PaLM-E at 12B) on a mixture:

  • Web image-text pairs (captioning, VQA).
  • Robot demonstrations, action as tokens: about half of the mixture for RT-2-PaLI-X and two thirds for RT-2-PaLM-E.

The model sees an image and an instruction and outputs the action tokens. Web pretraining carries over: RT-2 followed instructions such as "move apple to 3" and "move coke can to person with glasses", whose concepts never appeared in its robot data. On unseen objects, backgrounds and environments it averaged 62% success against RT-1's 32%.

Inference: about 1–3 Hz for the 55B model and about 5 Hz for the 5B model, served from a multi-TPU cloud service that the robot queries over the network.

Idea 2 · OpenVLA — the open 7B reference

OpenVLA (Kim et al., June 2024) is the open-weights RT-2 equivalent. It is built on the Prismatic-7B VLM: a Llama 2 7B language model, SigLIP and DINOv2 vision encoders whose patch features are concatenated (about 600M parameters together), and a 2-layer MLP projector. Each of the 7 action dimensions is cut into 256 bins spanning the 1st to 99th percentile of the training actions, so outliers do not stretch the bins, and the 256 least-used Llama tokens are overwritten as action tokens. The loss is cross-entropy on the action tokens only.

Trained on about 970k episodes from Open X-Embodiment (a 27-dataset mixture with weights taken from Octo) for 14 days on 64 A100 GPUs, with robot data only: no web data is mixed in. It beat the 55B RT-2-X by 16.5 points absolute across 29 tasks. LoRA at rank 32 trains 1.4% of the weights (97.6M) and nearly matched full fine-tuning (68.2% against 69.7%).

Inference: about 6 Hz on one RTX 4090 in bf16, using about 15 GB of GPU memory. 4-bit quantization brings memory to 7.0 GB with the same success rate (71.9% against 71.3%). One action per call is fast enough for slow manipulation, not for high-frequency control. OpenVLA-OFT (February 2025) fixed the speed with action chunks decoded in parallel as continuous values: about 26 times the throughput.

Idea 3 · FAST tokenizer — faster action decode

Pertsch et al. (January 2025) showed that per-step bin tokens break down at high control rates: consecutive tokens become nearly identical, so the model can reach a low loss by copying the previous token, and learns little. FAST (Frequency-space Action Sequence Tokenization) normalises each dimension (1st–99th percentile to [−1, 1]), applies a discrete cosine transform (DCT) to each dimension over a one-second chunk, scales and rounds the coefficients, flattens them lowest frequencies first, and compresses the integer sequence with byte-pair encoding (BPE) into a 1,024-token vocabulary.

Smooth chunks have few large coefficients, so the compression grows with the control rate. The paper reports 35 → 20 tokens per chunk for BridgeV2 (5 Hz), 140 → 28 for table bussing (20 Hz) and 700 → 53 for two-arm T-shirt folding (50 Hz): about 30 tokens per arm, whatever the rate. The gain is in training: π0-FAST matched diffusion π0 with about 5 times fewer GPU hours. Inference is slower, because 30–60 tokens are decoded one by one with the 2B backbone: about 750 ms per chunk against about 100 ms for π0 on an RTX 4090.

Idea 4 · π0 and flow-matching actions

Physical Intelligence's π0 (Black et al., October 2024) replaces discrete action tokens with a flow-matching action expert:

  • A 300M-parameter action expert, a second set of transformer weights inside the same model, processes the robot state and action tokens. Through shared attention, these tokens read the VLM's tokens (PaliGemma, 3B), for about 3.3B in total. The output is a continuous 50-step action chunk, produced by flow matching.
  • Training uses a flow-matching loss on the actions. The VLM starts from PaliGemma and is trained along with the expert on over 10,000 hours of robot data: 68 tasks on 7 of Physical Intelligence's own robot configurations, plus about 9% open data (OXE, Bridge, DROID).
  • Inference: 10 Euler integration steps from noise. The observation's keys and values are cached, so each step reruns only the 50 action tokens. Control runs at up to 50 Hz.

π0 beat OpenVLA and Octo out of the box on all five evaluation tasks; the paper attributes OpenVLA's weakness to its lack of action chunking. Continuous chunks keep motion smooth, which per-step discretisation struggles with at high rates.

π0-FAST (January 2025) is the same backbone trained on FAST tokens and decoded autoregressively, without flow matching. π0.5 (April 2025) co-trains on web data (captioning, VQA, object detection), high-level subtask labels and robot data from several robots. It first predicts a text subtask, then the action chunk by flow matching, and it cleaned kitchens and bedrooms in homes it had never seen. Weights for π0, π0-FAST and π0.5 are open in Physical Intelligence's openpi repository.

The same idea as a formula

Bin tokens (RT-2, OpenVLA). Each action value is first normalised to [−1,1] (OpenVLA maps the 1st and 99th percentiles of the training data to the ends), then

k=⌊2a+1​⋅256⌋∈{0,…,255},a^=256k+0.5​⋅2−1.
The bin width is w=2/256, so the worst rounding error is w/2≈0.0039 and the root-mean-square error is w/12​≈0.0023. An action chunk of H steps and D dimensions costs H⋅D tokens.

FAST. For each dimension d, take the DCT over the chunk, scale by s and round:

Ck,d​=t=0∑H−1​at,d​cos(Hπ​(t+21​)k)⋅ck​,qk,d​=round(sCk,d​).
Here ck​ is the orthonormal scale factor. Flatten q lowest frequency first (q0,1​,…,q0,D​,q1,1​,…) and compress with BPE. Smooth motion puts almost all its energy in small k, so most q are 0. Decoding inverts the DCT; the error is set by s, not by the rate.

Flow matching (π0, GR00T). With a clean chunk A, noise ϵ∼N(0,I) and τ∈[0,1]:

Aτ=τA+(1−τ)ϵ,L=E​vθ​(Aτ,o,τ)−(A−ϵ)​2.
At inference, start from A0=ϵ and integrate Aτ+δ=Aτ+δvθ​(Aτ,o,τ); π0 uses δ=0.1 (10 steps), GR00T N1 uses 4 steps. Each step is one pass over all H action tokens at once.

Throughput of a policy that returns H actions per call of latency ℓ: H/ℓ actions per second, which must exceed the robot's control rate.

Worked example
What each design delivers per second
  • Bin tokens at 50 Hz with 7 dimensions: 50⋅7=350 tokens for one second of motion, decoded one after another.
  • OpenVLA returns 1 action per call at about 6 Hz: 1/0.167 s=6 actions per second. That is enough for the 5 Hz WidowX arm in Bridge, about a tenth of what a 50 Hz arm needs.
  • π0 returns 50 actions in about 100 ms: 50/0.1=500 actions per second, 10 times what its 50 Hz robots need. It can afford to re-plan before a chunk runs out.
  • π0-FAST returns the same 50 actions in about 750 ms: 50/0.75≈67 per second, just above 50, and every chunk is three quarters of a second old when it starts.
  • GR00T N1 returns 16 actions in about 64 ms: 16/0.064=250 per second against 120 needed.
  • Bin rounding error: (2/256)/12​=0.0023 in normalised units; the run below measures 0.0026.

  • ✗ "Flow matching needs hundreds of denoising steps."

Bin tokens and FAST tokens on robot-like trajectories

Smooth synthetic 7-dimensional trajectories (6 end-effector values made of slow sine waves, plus an open or closed gripper), in one-second chunks at 5, 15 and 50 Hz. Each chunk is tokenized RT-2 style (256 bins per value) and FAST style (DCT per dimension, scale 10, rounding, then a 1,024-token BPE trained on 1,500 chunks). The table shows tokens per chunk, how close consecutive bin tokens are, and the reconstruction error. A few seconds.

import numpy as np
from scipy.fft import dct, idct
from tokenizers import Tokenizer, models, trainers

rng = np.random.default_rng(0)
D = 7  # 6 end-effector deltas + gripper, as in RT-2 and OpenVLA

def chunk(hz, fast_motion=False):
    """One second of a smooth 7-dim action trajectory sampled at `hz`."""
    t = np.arange(hz) / hz
    a = np.zeros((hz, D))
    for d in range(6):
        for _ in range(3):                      # a few slow components, 0.2-1.5 Hz
            f = rng.uniform(0.2, 1.5)
            a[:, d] += rng.normal(0, 0.4) * np.sin(2 * np.pi * f * t + rng.uniform(0, 6.3))
        if fast_motion:                         # an 8 Hz "drumming" component
            a[:, d] += 0.5 * np.sin(2 * np.pi * 8 * t)
        a[:, d] += rng.normal(0, 0.002, hz)   # small sensor noise
    a[:, 6] = 1.0 if rng.random() < 0.5 else -1.0  # gripper open or closed
    if rng.random() < 0.3:
        a[rng.integers(hz):, 6] *= -1                # gripper switches mid-chunk
    return a

def norm_fit(chunks):
    allv = np.concatenate(chunks)
    return np.percentile(allv, 1, axis=0), np.percentile(allv, 99, axis=0)

def normalise(a, lo, hi):
    return np.clip(2 * (a - lo) / (hi - lo) - 1, -1, 1)

# --- RT-2 / OpenVLA style: 256 bins per value -------------------------------
def bin_tokens(a):                       # a in [-1, 1], shape (H, D)
    return np.clip(np.floor((a + 1) / 2 * 256), 0, 255).astype(int)

def bin_decode(tok):
    return (tok + 0.5) / 256 * 2 - 1      # bin centres

# --- FAST: DCT per dimension, scale, round, flatten low frequencies first, BPE
SCALE = 10
def fast_ints(a):
    c = dct(a, axis=0, norm="ortho")       # (H, D): row k = frequency k
    return np.round(c * SCALE).astype(int).reshape(-1)   # c0d0..c0d6, c1d0, ...

def fast_decode(ints, hz):
    return idct(ints.reshape(hz, D) / SCALE, axis=0, norm="ortho")

OFF = 0x4E00 + 512                        # map each integer to one character
to_str = lambda ints: "".join(chr(OFF + int(v)) for v in ints)

print(f"{'rate':>6} {'values':>7} | {'bin tokens':>10} {'≤2 bins':>8} {'RMSE':>7} | "
      f"{'FAST tokens':>11} {'RMSE':>7} {'ratio':>6}")
for hz in (5, 15, 50):
    train = [chunk(hz) for _ in range(1500)]
    test = [chunk(hz) for _ in range(200)]
    lo, hi = norm_fit(train)
    train_n = [normalise(c, lo, hi) for c in train]
    test_n = [normalise(c, lo, hi) for c in test]

    # 256-bin tokens: one token per value; how often does a token repeat the previous step's?
    b = [bin_tokens(c) for c in test_n]
    step = np.concatenate([np.abs(np.diff(t[:, :6], axis=0)).ravel() for t in b])
    near = np.mean(step <= 2)              # next token within 2 bins of the previous one
    rmse_bin = np.sqrt(np.mean([np.mean((bin_decode(t) - c) ** 2) for t, c in zip(b, test_n)]))

    # FAST: train a 1,024-entry BPE on the flattened integer sequences
    tok = Tokenizer(models.BPE())
    tok.train_from_iterator((to_str(fast_ints(c)) for c in train_n),
                            trainers.BpeTrainer(vocab_size=1024, show_progress=False))
    n_fast = np.mean([len(tok.encode(to_str(fast_ints(c))).ids) for c in test_n])
    rmse_fast = np.sqrt(np.mean([np.mean((fast_decode(fast_ints(c), hz) - c) ** 2) for c in test_n]))
    print(f"{hz:>4}Hz {hz*D:>7} | {hz*D:>10} {near:>8.0%} {rmse_bin:>7.4f} | "
          f"{n_fast:>11.1f} {rmse_fast:>7.4f} {hz*D/n_fast:>5.1f}x")

    if hz == 50:
        fast_test = [normalise(chunk(hz, fast_motion=True), lo, hi) for _ in range(200)]
        n_fm = np.mean([len(tok.encode(to_str(fast_ints(c))).ids) for c in fast_test])
        rmse_fm = np.sqrt(np.mean([np.mean((fast_decode(fast_ints(c), hz) - c) ** 2) for c in fast_test]))
        print(f"  50 Hz with an 8 Hz drumming motion: FAST {n_fm:.1f} tokens, RMSE {rmse_fm:.4f}")
        ints = fast_ints(test_n[0])
        print(f"  one 50 Hz chunk: {np.count_nonzero(ints)} of {ints.size} rounded DCT coefficients are non-zero")

Reading this output

Bin tokens grow with the rate. One second costs 35 tokens at 5 Hz, 105 at 15 Hz and 350 at 50 Hz: one token per value, always. The error stays at 0.0026, close to the 0.0023 that the bin width predicts. It is slightly higher because the few values beyond the 1st and 99th percentiles are clipped.

Consecutive bin tokens become near-copies. At 5 Hz only 5% of tokens land within 2 bins of the previous step's token; at 50 Hz, 39% do. The faster the robot, the more "repeat the last token, roughly" works as a cheap way to reduce the loss. That is the failure the FAST paper describes for naive binning at high rates.

FAST tokens grow slowly. 16, 27 and 41 tokens per chunk: compression of 2.2×, 3.9× and 8.5×, the same trend as the paper's real datasets (1.75× at 5 Hz up to 13.2× for a 50 Hz two-arm robot). At 50 Hz only 45 of the 350 rounded DCT coefficients are non-zero; BPE packs the runs of zeros.

The price is precision. FAST's error is 0.015 to 0.028, about 6 to 10 times the bin error. The rounding scale (10 here) sets it: a larger scale is more precise and costs more tokens.

Fast motion is kept, and paid for. Adding an 8 Hz drumming component raises the count to 108 tokens, while the error stays at 0.022. FAST does not drop high frequencies; it spends tokens on them.

Three ways to produce one second of actions, timed

A random 27M-parameter Llama-style decoder (no weights downloaded) stands in for a VLA backbone, with a 300-token prefix for image and instruction. It produces actions three ways: autoregressive bin tokens, autoregressive FAST tokens, and flow matching with 10 or 4 Euler passes over 50 action tokens that reuse the cached prefix. The published latencies of the real models follow. Timing depends on the machine, so the block is not run on this page; the output below was recorded from a run of exactly this code.

import time, torch
from transformers import LlamaConfig, LlamaForCausalLM

torch.manual_seed(0); torch.set_num_threads(2)
# A small random decoder standing in for a VLA backbone (no weights are downloaded).
cfg = LlamaConfig(vocab_size=2048, hidden_size=512, intermediate_size=1376,
                  num_hidden_layers=8, num_attention_heads=8, num_key_value_heads=8)
m = LlamaForCausalLM(cfg).eval()
print(f"backbone: {sum(p.numel() for p in m.parameters())/1e6:.0f}M random parameters, CPU")

PREFIX = 300          # image tokens + instruction
H, D = 50, 7          # a one-second chunk at 50 Hz, 7 action dimensions
prefix = torch.randint(0, 2048, (1, PREFIX))

def timed(fn, reps=3):
    fn(); t0 = time.perf_counter()
    for _ in range(reps): fn()
    return (time.perf_counter() - t0) / reps

@torch.no_grad()
def autoregressive(n_new):
    m.generate(prefix, max_new_tokens=n_new, min_new_tokens=n_new, do_sample=False,
               pad_token_id=0)

@torch.no_grad()
def flow(steps):
    out = m.model(prefix, use_cache=True)            # the observation is encoded once
    cache = out.past_key_values
    x = torch.randn(1, H, cfg.hidden_size)            # 50 noisy action tokens
    for _ in range(steps):                            # each Euler step: one pass over all 50
        v = m.model(inputs_embeds=x, past_key_values=cache, use_cache=True).last_hidden_state
        cache.crop(-H)                                # reuse the prefix, drop the action keys
        x = x + v / steps

@torch.no_grad()
def prefill():
    m.model(prefix, use_cache=True)

rows = [("prefill only: encode the 300-token prefix", prefill, 0),
        ("1 step, 7 bin tokens (OpenVLA)", lambda: autoregressive(D), 1),
        ("50 steps, 350 bin tokens", lambda: autoregressive(H * D), H),
        ("50 steps, ~41 FAST tokens", lambda: autoregressive(41), H),
        ("50 steps, flow, 10 Euler passes (π0)", lambda: flow(10), H),
        ("50 steps, flow, 4 passes (GR00T N1)", lambda: flow(4), H)]
print(f"{'output per call':<44}{'latency':>9}{'actions/s':>11}")
for name, fn, n_actions in rows:
    t = timed(fn)
    print(f"{name:<44}{t*1000:>7.0f}ms{n_actions/t:>11.0f}")

print("\nPublished latencies (one call, one GPU):")
pub = [("OpenVLA, bf16, RTX 4090", 1, 1/6, 5),
       ("OpenVLA, same, on a 50 Hz arm", 1, 1/6, 50),
       ("OpenVLA-OFT+, chunk of 25, ALOHA", 25, 0.321, 25),
       ("π0, chunk of 50, RTX 4090", 50, 0.100, 50),
       ("π0-FAST, chunk of 50, RTX 4090", 50, 0.750, 50),
       ("GR00T N1, chunk of 16, L40", 16, 0.0639, 120)]
print(f"{'model':<32}{'latency':>9}{'actions/s':>11}{'robot Hz':>10}{'keeps up':>10}")
for name, n, lat, need in pub:
    print(f"{name:<32}{lat*1000:>7.0f}ms{n/lat:>11.0f}{need:>10}{'yes' if n/lat >= need else 'no':>10}")

Reading this output

Encoding the observation is a fixed cost. The 300-token prefix takes about 100 ms on this CPU, and every design pays it once per call. A one-action call (OpenVLA style) is mostly that cost: 168 ms for 7 tokens, 6 actions per second.

Decoding a whole chunk as bin tokens is far too slow. 350 tokens one by one take 3.5 s for one second of motion: 14 actions per second, against 50 needed.

FAST and flow cost about the same here, on a CPU. 41 FAST tokens take 478 ms; 10 flow passes over 50 action tokens take 484 ms, and 4 passes take 249 ms. On a CPU, one pass over 50 tokens costs several times a one-token pass, so 10 passes are roughly 41 decode steps.

On a GPU, flow wins clearly. A pass over 50 tokens costs about as much as a pass over one, because both are limited by reading the weights. π0's action expert (300M) is also much smaller than its 2B-class backbone, while here one model does both jobs. Hence the published numbers: π0 needs about 100 ms per chunk, π0-FAST about 750 ms.

Throughput is not the only test. In the published table, OpenVLA keeps up with a 5 Hz arm but not a 50 Hz one. π0-FAST produces enough actions (67 per second), but each chunk is 750 ms old when it starts, which is fine for folding laundry and poor for catching anything. GR00T N1's 64 ms chunks give 250 actions per second against the 120 it needs.

Idea 5 · GR00T N1 — dual-system for humanoids

NVIDIA's GR00T N1 (March 2025) is an open model for humanoid robots and other embodiments. GR00T-N1-2B has 2.2B parameters:

  • System 2: an Eagle-2 VLM (1.34B, built from SmolLM2 and SigLIP 2) reads the camera images (64 tokens per 224-pixel frame) and the instruction, at 10 Hz on an L40 GPU. Its 12th-layer (middle) embeddings are passed on, not text subgoals.
  • System 1: a diffusion transformer trained with flow matching cross-attends to those embeddings and produces 16-action chunks in 4 denoising steps (about 64 ms), for closed-loop motor actions at 120 Hz. Small per-embodiment encoders and decoders handle different state and action sizes.

The split maps to Kahneman's fast-and-slow thinking: System 2 plans, System 1 acts. Benefits: slow VLM-sized planning does not block fast control; System 1 stays small for latency.

Later releases (N1.5, N1.6, and N1.7 at about 3B) keep the design. N1.7 switches the VLM to Cosmos-Reason2-2B (a Qwen3-VL model), lengthens the action chunk from 16 to 40 and adds 20k hours of human video. The training data form a pyramid: human videos with inferred latent actions at the base, 780k simulated trajectories and generated videos in the middle, and real robot teleoperation at the top.

Idea 6 · Open X-Embodiment

The training data. The Open X-Embodiment collaboration (October 2023) pooled existing robot datasets from 21 institutions: over 1M trajectories from 22 robot types, demonstrating 527 skills. RT-1-X and RT-2-X, trained on it, beat models trained on each robot's own data. It keeps growing (over 2M trajectories in 70+ datasets by mid-2024) and is the usual starting corpus:

  • Bridge V2, Google's RT-1 data, Language Table, bimanual ALOHA sets and, since 2024, DROID.
  • Each sample: (robot state, camera views, instruction, action sequence).
  • Training hygiene: unify action space, normalize joint ranges, resize cameras.

OpenVLA trains on it, and π0 uses a subset as about 9% of its mixture. The gap to a specific robot is closed by fine-tuning on that robot's demonstrations; OpenVLA's experiments used 10–150 per task.

Idea 7 · Co-fine-tuning vs robot-only

Co-fine-tuning mixes web VQA data with robot trajectories. The ratio matters: too much VQA and the model forgets actions; too much robot data and the model loses general knowledge.

RT-2's mixture is about half robot data (PaLI-X) or two thirds (PaLM-E). OpenVLA and π0 use no web data during robot training and rely on what the VLM learned before; π0.5 and GR00T mix web and other non-robot data back in. The ratio is a hyperparameter to tune.

Models trained from scratch on robot data alone fail more often on unfamiliar objects and instructions: RT-2 roughly doubled RT-1's success in unseen conditions (62% against 32%). Web knowledge is what lets a model follow a novel phrasing like "move coke can to person with glasses".

Idea 8 · Safety and action limits

A deployed VLA should sit inside checks like these:

  • Hard joint limits (can't torque past spec).
  • Velocity limits (soft clipping).
  • Workspace bounds (end-effector cannot leave the table).
  • Human-in-the-loop approval for novel tasks.

These sit outside the VLA as control-layer checks. The VLA's output is a suggestion, not a command.

Industry practice
What's current (2024–2026)
  • π0 and π0.5 are the most used open VLAs: Physical Intelligence's openpi repository has base and fine-tuned checkpoints for π0, π0-FAST and π0.5 (released September 2025), in JAX and PyTorch, and they are also in Hugging Face LeRobot. Inference needs more than 8 GB of GPU memory, LoRA fine-tuning more than 22.5 GB.
  • NVIDIA Isaac GR00T N1.x for humanoids and other robots: N1.7 (about 3B) uses Cosmos-Reason2-2B as its VLM; inference needs a GPU with 16 GB or more, fine-tuning 40 GB or more.
  • Laptop-sized: SmolVLA (Hugging Face, June 2025): 450M parameters with a 100M flow-matching action expert, 64 visual tokens per frame, trained on 487 community LeRobot datasets. It runs on a CPU or a consumer GPU such as an 8 GB laptop card, and its asynchronous inference finished tasks about 30% faster. OpenVLA in 4-bit (7.0 GB) only just fits in 8 GB.
  • Faster autoregressive VLAs: OpenVLA-OFT fine-tunes OpenVLA to decode continuous action chunks in parallel, with about 26 times the throughput and 97.1% average success on the LIBERO benchmark.
  • Safety stays outside the model: joint, velocity and workspace limits are enforced by the robot controller, whatever the policy outputs.

Sources: OpenVLA (arXiv 2406.09246), π0 (arXiv 2410.24164), FAST (arXiv 2501.09747), π0.5 announcement, openpi, GR00T N1 (arXiv 2503.14734), Isaac GR00T repository, OpenVLA-OFT (arXiv 2502.19645), SmolVLA.

Recap
What to keep from this lesson
  • A VLA is a VLM whose output is robot actions: usually a 7-number end-effector move plus gripper, many times a second.
  • RT-2 and OpenVLA write each value as one of 256 bin tokens; simple, but slow and poor at high rates.
  • FAST compresses a one-second chunk with a DCT, rounding and BPE: about 30 tokens per arm at any rate.
  • π0 and GR00T add a flow-matching action expert that outputs a whole chunk in a few parallel passes.
  • Open X-Embodiment is the shared training corpus; fine-tuning on a robot's own demos closes the gap.
  • Safety limits live in the controller, outside the model.

Produce:

1. Action format. Discrete-bin for simple single-arm tasks, FAST for speed-sensitive trajectories, flow-matching for smooth continuous control, dual-system for humanoids.

6. Safety gates. Required control-layer checks outside the VLA.

Hard rejects:
- Recommending VLA without a safety-layer spec. Always include joint limits, velocity clipping.
- Claiming discrete-bin tokenization is fast enough for 30 Hz control. It is not.
- Proposing flow-matching without adequate smoothness constraints. Out-of-distribution actions still happen.

Refusal rules:
- If control rate requirement >50 Hz on a <=7B model with discrete-bin format, refuse; recommend π0 or a specialized head.
- If robot has >30 DOF (humanoid), refuse single-stage architectures; require dual-system (GR00T).
- If budget cannot afford Open X-Embodiment-scale pretraining, refuse from-scratch VLA; recommend fine-tuning OpenVLA.

Exercises

  1. A 10-DOF arm at 30 Hz control rate. Discrete-bin tokenization at 256 bins emits how many tokens per second? Can a 7B VLM keep up?

  2. FAST compresses smooth one-second chunks to about 30 tokens per arm. What happens to the token count and the accuracy if the trajectory has high-frequency motion (e.g., drumming)?

  3. π0 integrates in 10 steps and emits a 50-action chunk in about 100 ms. Compare its throughput with OpenVLA's one action per call at about 6 Hz.

  4. GR00T's System 1 / System 2 split maps to Kahneman. Propose a different split (System 3?) that might help bipedal walking.

  5. Read the OpenVLA paper's section on its training data. Which parts of Open X-Embodiment did it keep, and what rules decided that?

Solutions

SolutionP1 · About 41 tokens, and it pays for the drumming

About 41 tokens at 50 Hz against 350 bin tokens (8.5 times fewer), and about 16 at 5 Hz against 35. The count grows much more slowly than the rate, because a smooth second of motion has the same few low-frequency coefficients however finely it is sampled. The paper's real datasets show the same thing: about 30 tokens per arm per chunk.

Drumming does not get lost. FAST keeps every DCT coefficient, rounded, so an 8 Hz component appears as non-zero coefficients near index 8 in every dimension. The count rises to about 108 tokens and the error stays at about 0.022. The trade is more tokens, not less accuracy. What would lose the drumming is truncating to the first few coefficients, a different (and worse) compressor.

SolutionB1 · Stop, go, and a second without looking

The robot moves for one second, stops for about 100 ms while the next chunk is computed, then lurches into the next one. It is jerky, and for every one-second chunk it acts blind. If the object slips or a person reaches in after the image was taken, the policy cannot react until the chunk is finished.

Real systems overlap planning and acting:

  • Execute only part of each chunk. For example, run the first 25 of 50 actions, then re-plan from a new image. Fewer steps run blind, at the cost of more calls. openpi and GR00T expose this as a setting (GR00T calls it the execution horizon).
  • Compute the next chunk while the current one runs (asynchronous inference). SmolVLA's async mode finished tasks about 30% faster with the same success.
  • Smooth the hand-over between overlapping chunks, for example by averaging the predictions for the same time step (temporal ensembling, from the ACT policy), so the arm does not jump when a new chunk starts.

The latency budget decides how much of this is possible. π0's 100 ms per 50-action chunk leaves room to re-plan every 0.2 to 0.5 s; π0-FAST's 750 ms does not.
