The problem

In plain words first

In most agent code one agent calls another like a function and waits; if the callee crashes, the caller crashes too. The actor model, used by AutoGen v0.4 and later, works differently. Each agent is an actor: it keeps its own state private, has an inbox, and reacts to one message at a time. Agents never call each other directly; they send messages, and a runtime delivers them. A crash in one actor's handler stays in that actor, many messages can be in flight at once, and moving an actor to another machine only changes how messages travel. This lesson builds a small actor runtime in plain Python, then runs the same reviewer as a real AutoGen actor and gives it a language-model twin.

Most agent frameworks are synchronous: one agent produces, one agent consumes, in a call stack. Failures crash the stack. Concurrency is bolted on. Distribution requires rewriting.

AutoGen v0.4's answer: the actor model. Each agent is an actor with a private inbox. Messages are the only interaction. The runtime decouples delivery from handling. Failures isolate to one actor. Concurrency is native. Distribution is just different transport.

Idea 1 · Actors

An actor has:

  • A private state (never directly touched from outside).
  • An inbox (message queue).
  • A handler: receive(message) -> effects where effects can be "reply," "send to other actor," "spawn new actor," "update state," "stop self."

Two actors cannot share memory. They can only send messages.

Idea 2 · Three API layers

AutoGen v0.4 splits its surface into three:

  1. Core. Low-level actor framework. AgentRuntime, Agent, Message, Topic. Async message exchange, event-driven.
  2. AgentChat. Task-driven high-level API (replacement for v0.2's ConversableAgent). AssistantAgent, UserProxyAgent, RoundRobinGroupChat, SelectorGroupChat.
  3. Extensions. Integrations — OpenAI, Anthropic, Azure, tools, memory.

Idea 3 · Why decoupling matters

In the v0.2 model, calling agent_a.chat(agent_b) synchronously blocks agent_a until agent_b returns. In v0.4, send(agent_b, msg) puts the message in agent_b's inbox and returns. The runtime delivers later. Three consequences:

  • Fault isolation. Agent B crashing does not crash Agent A — the runtime catches the failure in B's handler and decides what to do (log, retry, dead-letter).
  • Natural concurrency. Many messages in flight at once; actors process their inbox concurrently.
  • Distribution-ready. Inbox + transport is the same abstraction whether the actor is in-process or on another host.

Idea 4 · Topologies

  • RoundRobinGroupChat. Agents take turns in a fixed rotation.
  • SelectorGroupChat. A selector agent picks who goes next based on conversation context.
  • Magentic-One. Reference multi-agent team for web browsing, code execution, file handling. Built on AgentChat.

Idea 5 · Observability

OpenTelemetry support is built in. Every message emits a span; tool calls carry gen_ai.* attributes per the 2026 OTel GenAI semantic conventions (Lesson 14.23).

Idea 6 · Status: maintenance mode

Early 2026: AutoGen v0.7.x is stable for research and prototyping. Microsoft has shifted active development to the Microsoft Agent Framework, the production successor (public preview from 1 October 2025; version 1.0 shipped in April 2026). AutoGen patterns port forward cleanly — the actor model is the durable idea.

The same idea as a formula

An actor is a state σ and a handler h. A message m produces a new state and a set of outgoing messages:

(σ′,{m1​,…,mk​})=h(σ,m).
The runtime is the only thing that moves messages between inboxes.

Two delivery styles. A direct send is a request with a reply, r=hB​(σB​,m), and an exception in hB​ becomes an exception at the sender. A publish to a topic delivers m to every subscriber with no reply; a failure stays with the subscriber that failed.

Why many messages in flight helps. With n independent requests that each wait w on something slow (a model call, a network round trip) and a worker pool of size c, the elapsed time drops from about nw to about ⌈n/c⌉w, if the waiting really can overlap.

Worked example
What the reviewer's crash costs in each style
  • Direct send of CrashMe: the reviewer raises; the runtime hands the RuntimeError back to the sender, which must catch it. Every other request is unaffected.
  • Publish of Review, CrashMe, Review: the crash is logged by the runtime and dropped; the publisher sees nothing, and both reviews are handled.
  • So "fault isolation" means different things: with send, the failure is isolated and reported; with publish, it is isolated and silent unless you watch the logs or route failures to a dead-letter queue, as the lesson's runtime does.
  • Concurrency here: ten model reviews of about 1.5 s each, sent at once, still take about 15 s, because two CPU cores run one model call at a time. Overlap needs a resource that can actually serve requests in parallel, such as a model server with batching.
Check your mental model
  • ✗ "Actors make agents smarter."
    ✓ They make the plumbing safer: isolation, concurrency, distribution. The quality is in the handlers.
  • ✗ "A crash in an actor is always swallowed."
    ✓ A direct send returns it to the caller; a publish leaves it in the logs.
  • ✗ "Sending ten messages at once makes ten model calls ten times faster."
    ✓ Only if the model can serve them in parallel.
  • ✗ "AutoGen is the place to start new work."
    ✓ It is in maintenance; Microsoft Agent Framework is the successor, and the actor ideas carry over.

# The lesson's reviewer as a real AutoGen actor (autogen-core 0.7, SingleThreadedAgentRuntime). The same
# rules as the lesson's ReviewerAgent; one message type makes the handler crash. Two ways to talk to an
# actor are compared: direct send (request/response) and publish to a topic (fire and forget).
import asyncio, logging
from dataclasses import dataclass, field
from autogen_core import (AgentId, DefaultTopicId, MessageContext, RoutedAgent, SingleThreadedAgentRuntime,
                          default_subscription, message_handler)
logging.getLogger("autogen_core").setLevel(logging.CRITICAL)      # keep the runtime's own error logs quiet
@dataclass
class Review:
    code: str
@dataclass
class Verdict:
    ok: bool
    issues: list = field(default_factory=list)
@dataclass
class CrashMe:
    note: str = ""
SEEN = []
def rule_review(code):                                   # the lesson's ReviewerAgent rules, verbatim
    issues = []
    if "eval(" in code:
        issues.append("uses eval")
    if "except:" in code:
        issues.append("bare except")
    return issues
@default_subscription
class Reviewer(RoutedAgent):
    def __init__(self):
        super().__init__("checks a code snippet")
    @message_handler
    async def on_review(self, message: Review, ctx: MessageContext) -> Verdict:
        issues = rule_review(message.code); SEEN.append((message.code.split("(")[0], issues))
        return Verdict(ok=not issues, issues=issues)
    @message_handler
    async def on_crash(self, message: CrashMe, ctx: MessageContext) -> None:
        raise RuntimeError("simulated handler failure")
SNIPPETS = ["def add(a, b): return a + b", "def hazard(): return eval('1+1')",
            "def silent():\n    try:\n        f()\n    except:\n        pass"]
async def main_async():
    runtime = SingleThreadedAgentRuntime()
    await Reviewer.register(runtime, "reviewer", lambda: Reviewer())
    runtime.start()
    rid = AgentId("reviewer", "default")
    print("direct send (request/response):")
    for code in SNIPPETS:
        v = await runtime.send_message(Review(code), rid)
        print(f"  {code.split('(')[0]:<12} -> {v}")
    try:
        await runtime.send_message(CrashMe(), rid)
    except Exception as exc:
        print(f"  CrashMe      -> the sender receives the exception: {type(exc).__name__}: {exc}")
    print("\npublish to the default topic (fire and forget), crash in the middle:")
    SEEN.clear()
    await runtime.publish_message(Review(SNIPPETS[0]), DefaultTopicId())
    await runtime.publish_message(CrashMe(), DefaultTopicId())
    await runtime.publish_message(Review(SNIPPETS[1]), DefaultTopicId())
    await runtime.stop_when_idle()
    print("  publisher saw no exception; the reviewer handled:", SEEN)
asyncio.run(main_async())

Published messages keep going. With CrashMe published between two reviews, the publisher gets no exception and the reviewer still handles both reviews.        "Answer with ISSUE or OK first, then a few words.")
def llm_review(code):
    ids = tok.apply_chat_template([{"role": "user", "content": ASK.format(c=code)}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=16, do_sample=False)
    text = " ".join(tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).split())
    return text.lstrip("*# ").upper().startswith("ISSUE"), text       # also "**ISSUE**"
@default_subscription
class LLMReviewer(RoutedAgent):
    def __init__(self):
        super().__init__("reviews code with a language model")
    @message_handler
    async def on_review(self, message: Review, ctx: MessageContext) -> Verdict:
        flagged, text = await asyncio.to_thread(llm_review, message.code)
        return Verdict(ok=not flagged, issues=[text] if flagged else [])
async def compare():
    runtime = SingleThreadedAgentRuntime()
    await Reviewer.register(runtime, "rules", lambda: Reviewer())
    await LLMReviewer.register(runtime, "llm", lambda: LLMReviewer())
    runtime.start()
    t0 = time.perf_counter()
    rules = await asyncio.gather(*[runtime.send_message(Review(c), AgentId("rules", "default")) for c, _ in CASES])
    model = await asyncio.gather(*[runtime.send_message(Review(c), AgentId("llm", "default")) for c, _ in CASES])
    secs = time.perf_counter() - t0
    await runtime.stop()
    print(f"{'snippet':<40}{'truth':<8}{'rules':<8}{'model'}")
    for (code, bad), r, m in zip(CASES, rules, model):
        tag = lambda v: "issue" if not v.ok else "ok"
        print(f"{' '.join(code.split())[:38]:<40}{'issue' if bad else 'ok':<8}{tag(r):<8}{tag(m)}")
    score = lambda vs: sum((not v.ok) == bad for v, (_, bad) in zip(vs, CASES))
    print(f"\ncorrect: rules {score(rules)}/10, model {score(model)}/10   ({secs:.0f} s for all 20 requests)")
    print("model flags everything:", all(not v.ok for v in model), "| model flags nothing:", all(v.ok for v in model))
asyncio.run(compare())

Reading this output

Two rules and a small model score the same, 4 of 10, and miss different things. The rules catch eval and the bare except, falsely flag my_eval (it contains eval(), and miss exec, shell injection, SQL built from input, a hard-coded password and pickle.loads on network data. The model flags only the hard-coded password and calls everything else "OK", including eval and exec, sometimes in a sentence that goes on to say the code is not secure.

Sending all twenty requests at once took about 15 seconds. The rule reviews finish instantly; the ten model calls run one after another on two CPU cores. The actor runtime allowed concurrency; the hardware did not provide it.

The actor model is the plumbing, not the judgement. Isolation and messaging work the same whether the handler is good or bad; the handler's quality needs its own evaluation, as here, before any reviewer gates a merge.

Part 1 of 4 · Message, Actor, Runtime

"""A stdlib actor runtime modeled on AutoGen v0.4 Core.

Actors have private state and an inbox. Messages are the only interaction.
Failures in one actor are caught by the runtime and routed to a dead-letter
queue; other actors keep running.
"""

from __future__ import annotations

from collections import deque
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class Message:
    sender: str
    recipient: str
    topic: str
    body: Any
    mid: int = 0


class Actor:
    def __init__(self, name: str) -> None:
        self.name = name

    def receive(self, message: Message, runtime: "Runtime") -> None:
        raise NotImplementedError


@dataclass
class Runtime:
    actors: dict[str, Actor] = field(default_factory=dict)
    queue: deque[Message] = field(default_factory=deque)
    dead_letters: list[tuple[Message, str]] = field(default_factory=list)
    counter: int = 0
    trace: list[str] = field(default_factory=list)
    max_messages: int = 100

    def register(self, actor: Actor) -> None:
        self.actors[actor.name] = actor

    def send(self, sender: str, recipient: str, topic: str, body: Any) -> None:
        self.counter += 1
        msg = Message(sender=sender, recipient=recipient,
                      topic=topic, body=body, mid=self.counter)
        self.queue.append(msg)
        self.trace.append(
            f"[send m{msg.mid:03d}] {sender} -> {recipient} topic={topic} body={body}"
        )

    def run_until_idle(self) -> None:
        processed = 0
        while self.queue and processed < self.max_messages:
            msg = self.queue.popleft()
            actor = self.actors.get(msg.recipient)
            if actor is None:
                self.dead_letters.append((msg, f"no actor {msg.recipient!r}"))
                self.trace.append(f"[DLQ m{msg.mid:03d}] no actor {msg.recipient!r}")
                continue
            try:
                actor.receive(msg, self)
                self.trace.append(
                    f"[recv m{msg.mid:03d}] {actor.name} handled topic={msg.topic}"
                )
            except Exception as e:
                self.dead_letters.append((msg, f"{type(e).__name__}: {e}"))
                self.trace.append(
                    f"[FAIL m{msg.mid:03d}] {actor.name} raised "
                    f"{type(e).__name__}: {e}  (others keep running)"
                )
            processed += 1

Part 2 of 4 · ReviewerAgent, ChecklistAgent

class ReviewerAgent(Actor):
    def __init__(self, name: str) -> None:
        super().__init__(name)
        self.verdicts: list[tuple[str, bool]] = []

    def receive(self, message: Message, runtime: Runtime) -> None:
        if message.topic == "review":
            code = str(message.body)
            issues = []
            if "eval(" in code:
                issues.append("uses eval")
            if "except:" in code:
                issues.append("bare except")
            ok = len(issues) == 0
            self.verdicts.append((code, ok))
            runtime.send(
                sender=self.name,
                recipient=message.sender,
                topic="review_result",
                body={"ok": ok, "issues": issues},
            )
        elif message.topic == "crash_me":
            raise RuntimeError("simulated handler failure")


class ChecklistAgent(Actor):
    def __init__(self, name: str, partner: str) -> None:
        super().__init__(name)
        self.partner = partner
        self.results: list[dict[str, Any]] = []
        self.consensus: bool | None = None

    def receive(self, message: Message, runtime: Runtime) -> None:
        if message.topic == "start":
            for snippet in message.body:
                runtime.send(
                    sender=self.name, recipient=self.partner,
                    topic="review", body=snippet,
                )
        elif message.topic == "review_result":
            self.results.append(dict(message.body))
            if all(r["ok"] for r in self.results):
                self.consensus = True
            if len(self.results) == 3:
                self.consensus = all(r["ok"] for r in self.results)

def main() -> None:
    print("=" * 70)
    print("AUTOGEN V0.4 ACTOR RUNTIME (STDLIB): Phase 14, Lesson 14")
    print("=" * 70)

    runtime = Runtime()
    reviewer = ReviewerAgent("reviewer")
    checklist = ChecklistAgent("checklist", partner="reviewer")
    runtime.register(reviewer)
    runtime.register(checklist)

    runtime.send(
        sender="__user__",
        recipient="checklist",
        topic="start",
        body=[
            "def add(a, b): return a + b",
            "def hazard(): eval('1+1')",
            "def silent(): \n    try:\n        f()\n    except:\n        pass",
        ],
    )

    runtime.send(
        sender="__user__",
        recipient="reviewer",
        topic="crash_me",
        body={},
    )

    runtime.run_until_idle()

    print("\nmessage trace")
    for line in runtime.trace:
        print(f"  {line}")

    print(f"\nchecklist consensus: {checklist.consensus}")
    print(f"dead-letter queue:   {len(runtime.dead_letters)} message(s)")
    for msg, reason in runtime.dead_letters:
        print(f"  DLQ m{msg.mid:03d} ({reason}) "
              f"{msg.sender} -> {msg.recipient} topic={msg.topic}")

    print()
    print("property: reviewer's crash on 'crash_me' did not stop")
    print("the 'review' messages from being processed. fault isolation.")

Use it: the same idea with real libraries

  • AutoGen v0.4/v0.7 (maintenance) — stable for research, prototyping, multi-agent patterns.
  • Microsoft Agent Framework — the production successor (1.0 in April 2026, Python and .NET); same actor-model ideas in a refreshed API.
  • LangGraph swarm topology (Lesson 14.13) — similar pattern via shared-tool handoffs.
  • Custom actor runtime — when you need specific transport (NATS, RabbitMQ, gRPC).
Break it on purpose

A team publishes every review request to a topic and never looks at the runtime's logs. The reviewer starts failing on snippets longer than its model's context. What does the team see, and what should they add? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Microsoft Agent Framework (1.0 in April 2026, Python and .NET) is Microsoft's agent SDK, combining AutoGen's multi-agent patterns with Semantic Kernel's enterprise features; AutoGen itself is in maintenance.
  • Actor and message-passing runtimes for agents: Ray (actors at cluster scale), Akka and Orleans in the JVM and .NET worlds, and queue-based designs (NATS, Kafka, RabbitMQ) where each agent is a consumer.
  • Observability: OpenTelemetry spans per message and per tool call, using the GenAI semantic conventions (lesson 14.23), are built into AutoGen and Agent Framework.
  • On your laptop: an in-process runtime is enough to learn the patterns; real concurrency for model calls needs a server that batches requests (vLLM, llama.cpp server or Ollama) on the RTX 4060, rather than calling the model in each handler.

Sources: AutoGen documentation, AutoGen core concepts, Microsoft Agent Framework 1.0 (Visual Studio Magazine), Microsoft Agent Framework, Ray actors.

Recap
What to keep from this lesson
  • Actors: private state, an inbox, one message at a time.
  • Send returns failures to the caller; publish keeps them local and quiet.
  • Route failures somewhere visible: a dead-letter queue, alerts.
  • Concurrency helps only when the slow part can run in parallel.
  • The reviewer's judgement is a separate problem; measure it.

Given a multi-agent task, produce an actor runtime and the agent actors needed.

Produce:

1. A `Message` type with `sender`, `recipient`, `topic`, `body`, `mid`.
2. An `Actor` base class with `receive(message, runtime)`. Actor state is private.
3. A `Runtime` with a shared queue, `send()`, `run_until_idle()`, and a dead-letter queue. Exceptions in handlers go to DLQ; do not propagate.
4. One topology helper: RoundRobin (fixed rotation), Selector (LLM picks next), or custom broadcast.
5. Observability hooks per message: emit OTel spans with `gen_ai.agent.name` and `gen_ai.operation.name` per Lesson 23.

Hard rejects:

- Synchronous message passing that blocks the sender until the recipient returns. That is the v0.2 model; it breaks fault isolation.
- Shared mutable state across actors. Actors read state via messages or not at all.
- A runtime that propagates handler exceptions. Failures belong in the DLQ; let other actors keep running.

Refusal rules:

- If the task has only two actors with a fixed back-and-forth, refuse the actor framing and suggest a prompt chain (Lesson 12). Actors earn cost when there are >=3 actors or async concurrency.
- If the user wants "synchronous mode" for "easier debugging," refuse. Suggest logging + tracing (Lesson 23) instead.
- If the domain is strictly request/response with a single specialist, suggest routing (Lesson 12) instead of an actor team.

Output: `message.py`, `actor.py`, `runtime.py`, `teams.py`, `README.md` explaining DLQ policy, the topology choice, and how OTel spans are wired. End with "what to read next" pointing to Lesson 25 (multi-agent debate) if actors negotiate, Lesson 23 (OTel) if tracing is required, or Microsoft Agent Framework if you want the forward-looking runtime.

Exercises

  1. Add a dead-letter queue: when a handler raises, park the failing message for human inspection. How often does DLQ get hit in your toy?
  2. Implement SelectorGroupChat: a selector actor picks who processes the next message based on conversation state.
  3. Add distributed transport: swap the in-process queue for a JSON-over-HTTP server so actors can run in separate processes.
  4. Wire an OTel span per message (or a no-op stand-in). Emit gen_ai.agent.name, gen_ai.operation.name per Lesson 23.
  5. Read AutoGen v0.4's architecture post. Port your toy to the real autogen_core API. What did you skip that matters in production?

Solutions

SolutionP1 · Reported on send, silent on publish

On a direct send, the caller gets the exception: await runtime.send_message(CrashMe(), ...) raises RuntimeError: simulated handler failure, and it must be caught. On publish, the publisher sees nothing; the runtime logs the failure, drops that message, and the reviews before and after it are still handled. Both are fault isolation; only the first tells you about the fault.

SolutionB1 · Silent failures

They see nothing wrong. Every publish returns normally, the long snippets simply get no verdict, and any dashboard that counts "reviews requested" looks healthy. Unreviewed code then flows through as if it had been checked, which is worse than an outage because nobody knows.

Make failures visible: catch exceptions in the handler and publish an explicit failure message (or a verdict of "not reviewed"), collect them in a dead-letter queue with the original message, alert on its size, and have downstream steps treat "no verdict" as "not approved". For this specific failure, check the input length before calling the model and split or reject long inputs explicitly.
