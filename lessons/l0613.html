The nodes are plain functions and the "person" is a value passed in code. In an application, the interrupt's payload goes to a UI or a message, and the answer comes back from an API call.

Why this came about

Companies wanted people to approve risky agent actions, which means pausing for hours without losing state. LangGraph's interrupt and Command(resume=...) (2024) built that on top of checkpoints.

The problem: a decision that only a person may make

A refund of INR 7,999 is above what ShopKart lets an agent approve alone. The run must stop, show a person what it wants to do, wait, possibly for hours, and continue with their decision, even if the process restarts in between. Your Lesson 14.100 engine did this with an interrupt flag in the state and a resume that patched the state by hand. LangGraph's interrupt function does it inside a node.

The idea in plain words

In plain words first
Save the case and wait for a signature

Human in the loop means: stop before the risky step, save everything, show a person what you want to do, and wait. When they answer, possibly hours later on another server, continue with their answer. Two consequences explain every rule in this lesson. Pausing needs somewhere to save the run while it waits: the checkpointer and thread from Lesson 14.103. And LangGraph cannot freeze a Python function halfway through, so the paused node starts again from its first line when the run continues; the second time, the pause call returns the answer instead of stopping.

The mechanism in plain Python, with an exception doing the stopping and a dictionary doing the saving:

class Pause(Exception):                           # how a pause travels: as an exception
    def __init__(self, question):
        self.question = question

saved = {"answers": []}                           # what the checkpointer keeps for the thread

def ask(question):                                # a toy interrupt()
    if saved["answers"]:                          # resuming: an answer is waiting
        return saved["answers"].pop(0)
    raise Pause(question)                         # first time: stop and ask

def approval_node():
    print("approval_node started")                # runs again on resume
    return "refunded" if ask("Approve INR 7,999 for A-1077?") else "declined"

try:
    approval_node()
except Pause as p:
    print("paused, asking:", p.question)
saved["answers"].append(True)                     # a person answers, maybe hours later
print("result:", approval_node())                 # resume = run the node again from its first line
What you should see
approval_node started
paused, asking: Approve INR 7,999 for A-1077?
approval_node started
result: refunded

Idea 1 · Pause inside a node

Calling interrupt(...) inside a node stops the run at that line and hands its argument back to whoever called the graph. The state is checkpointed, so the pause can last a second or a week. Here a refund above a limit asks for approval:

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver

class RefundState(TypedDict, total=False):
    order_id: str
    amount: int
    approved: bool
    note: str
    done: str

def approval(state):
    answer = interrupt({"question": "Approve this refund?", "order_id": state["order_id"], "amount": state["amount"]})
    return {"approved": answer["approved"], "note": answer.get("note", "")}

def finish(state):
    return {"done": f"refunded INR {state['amount']:,}" if state["approved"] else f"declined: {state['note']}"}

b = StateGraph(RefundState)
b.add_node("approval", approval); b.add_node("finish", finish)
b.add_edge(START, "approval"); b.add_edge("approval", "finish"); b.add_edge("finish", END)
graph = b.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "refund-A-1077"}}
out = graph.invoke({"order_id": "A-1077", "amount": 7999}, cfg, version="v2")
print("paused with:", out.interrupts[0].value)
print("next:", graph.get_state(cfg).next)
What you should see
paused with: {'question': 'Approve this refund?', 'order_id': 'A-1077', 'amount': 7999}
next: ('approval',)
Reading this output
  • version="v2" makes invoke return an object with two parts: out.value (the state so far) and out.interrupts (the pauses). Each interrupt has .value, exactly the dictionary passed to interrupt(...), and .id, which you need when several pauses wait at once (Idea 4).
  • next: ('approval',) means the run stopped inside approval and will re-enter it on resume. finish has not run.

Calling interrupt(payload) stopped the run: the checkpointer saved the state, the payload came back to the caller (in out.interrupts with version="v2", or under the __interrupt__ key with the default output), and the snapshot shows approval as the next node. The payload can be any serializable value; make it everything the person needs to decide, because they will see nothing else.

Idea 2 · Resume with the person's answer

To continue, call the graph again on the same thread with Command(resume=...). The value you pass becomes the return value of the interrupt call inside the node, and the node carries on from there. One refund is approved, a second is refused:

print(graph.invoke(Command(resume={"approved": True}), cfg)["done"])

cfg_b = {"configurable": {"thread_id": "refund-A-1078"}}
graph.invoke({"order_id": "A-1078", "amount": 12000}, cfg_b)
print(graph.invoke(Command(resume={"approved": False, "note": "above the agent's limit"}), cfg_b)["done"])
What you should see
refunded INR 7,999
declined: above the agent's limit

Command(resume=value) continues the thread, and value becomes the return value of interrupt inside the node. The same graph handles approval and rejection, and the decision is now in the state, where it is checkpointed and visible in traces: an audit trail of who approved what.

The most important rule of interrupt: on resume, the node runs again from its first line. LangGraph cannot resume in the middle of a Python function. The second time, interrupt returns the resume value instead of pausing:

RUNS = []

def approval_counted(state):
    RUNS.append("node started")                                # code before interrupt() runs again on resume
    answer = interrupt({"amount": state["amount"]})
    RUNS.append(f"got answer {answer}")
    return {"approved": answer}

b = StateGraph(RefundState)
b.add_node("approval", approval_counted); b.add_edge(START, "approval"); b.add_edge("approval", END)
counted = b.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "count"}}
counted.invoke({"amount": 7999}, c)
counted.invoke(Command(resume=True), c)
print(RUNS)
What you should see
['node started', 'node started', 'got answer True']

So code before interrupt runs twice. Reading state there is fine; sending a message or charging a card is not, which is the debugging exercise.

Idea 3 · Edit, and validate the answer

People make mistakes too. Put interrupt in a loop to ask again until the answer is valid, and let the reviewer change a value instead of only approving:

def review_amount(state):
    while True:                                                # ask again until the answer is valid
        answer = interrupt({"question": "Approve, or give a new amount", "amount": state["amount"]})
        if answer == "approve":
            return {"approved": True}
        if isinstance(answer, int) and 0 < answer <= state["amount"]:
            return {"approved": True, "amount": answer}         # the reviewer edited the amount
        state = {**state, "note": f"invalid answer {answer!r}"}

b = StateGraph(RefundState)
b.add_node("review", review_amount); b.add_node("finish", finish)
b.add_edge(START, "review"); b.add_edge("review", "finish"); b.add_edge("finish", END)
editable = b.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "edit"}}
editable.invoke({"order_id": "A-1077", "amount": 7999}, c)
out = editable.invoke(Command(resume=99999), c, version="v2")        # too much: asked again
print("asked again:", bool(out.interrupts))
print(editable.invoke(Command(resume=4999), c)["done"])
What you should see
asked again: True
refunded INR 4,999

The reviewer first typed an amount larger than the order, so the node asked again; the second answer, a reduced amount, was accepted and used. Several interrupt calls in one node are matched to resume values by their order, so keep that order the same on every run: do not call interrupt inside a condition whose result can change between the pause and the resume.

Idea 4 · Several sign-offs at once

When parallel nodes each interrupt, the run pauses once with all the requests, and you answer them together, keyed by interrupt ID:

class SignOff(TypedDict, total=False):
    finance: str
    legal: str

def finance(state): return {"finance": interrupt("Finance: approve the INR 7,999 refund?")}
def legal(state):   return {"legal": interrupt("Legal: any hold on this customer?")}

b = StateGraph(SignOff)
b.add_node("finance", finance); b.add_node("legal", legal)
b.add_edge(START, "finance"); b.add_edge(START, "legal"); b.add_edge(["finance", "legal"], END)
two = b.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "signoff"}}
out = two.invoke({}, c, version="v2")
for i in sorted(out.interrupts, key=lambda i: i.value):          # parallel interrupts arrive in any order
    print(i.value)
answers = {i.id: ("approved" if i.value.startswith("Finance") else "no hold") for i in out.interrupts}
print(two.invoke(Command(resume=answers), c))
What you should see
Finance: approve the INR 7,999 refund?
Legal: any hold on this customer?
{'finance': 'approved', 'legal': 'no hold'}

This is how a refund can wait for finance and legal at the same time, rather than one after the other.

Idea 5 · Breakpoints for debugging

interrupt_before and interrupt_after stop the graph before or after named nodes, without changing node code. They are for development: stop, inspect or edit the state, continue:

b = StateGraph(RefundState)
b.add_node("finish", finish); b.add_edge(START, "finish"); b.add_edge("finish", END)
debug = b.compile(checkpointer=InMemorySaver(), interrupt_before=["finish"])   # a breakpoint, for debugging
c = {"configurable": {"thread_id": "dbg"}}
debug.invoke({"amount": 7999, "approved": True}, c)
print("stopped before:", debug.get_state(c).next)
debug.update_state(c, {"amount": 5000})                       # inspect or change state, then continue
print(debug.invoke(None, c)["done"])
What you should see
stopped before: ('finish',)
refunded INR 5,000

For approvals in production, use interrupt in the node, where the payload and the logic live together.

Idea 6 · In the loop, on the loop, out of the loop

Everything so far makes a person approve a step before it runs. That is one of three ways to involve people, and production systems combine them.

In plain words first
Signing every order, or watching the dashboard
  • Human in the loop: the agent stops and waits for a person before a step. Like a manager who must sign every purchase order.
  • Human on the loop: the agent runs on its own while people supervise: alerts, sampled reviews, the power to correct or stop a run. Like a manager watching a dashboard who can cancel an order or press stop.
  • Human out of the loop: fully autonomous; tests, limits and audits carry the whole load. Rare for anything risky.
In the loop On the loop
The agent Waits for a decision Keeps running
The person Approver or editor Supervisor or auditor
Blocks the work? Yes No
Catches mistakes Before they happen During or after
Best for Irreversible, costly or regulated actions Reversible, low-impact, high-volume actions

In LangGraph, in the loop is interrupt in a node or HumanInTheLoopMiddleware (Lesson 14.97), with a durable checkpointer. On the loop is not one feature: it is built from tracing (Lesson 14.108), alerts on errors and spend, a review queue fed by sampled runs, and the ability to cancel a run or correct its state with update_state (Lesson 14.103).

How production systems use both:

  1. Risk tiers. Reading data and drafting replies run on their own and are monitored. Medium-risk actions run with sampled review afterwards. Refunds above a limit, cancellations of shipped orders, deletes and emails to customers need approval.
  2. Conditional gates. A when function (Lesson 14.97) or a check in the node pauses only the risky cases, such as refunds above INR 5,000.
  3. Escalation on doubt. The agent pauses when a validator or guardraillater · 15.23 flags its output, not on every step.
  4. Asynchronous review. The pause is saved in Postgres; the request goes to a dashboard, Slack or email; someone answers hours later, and the run resumes on the same thread.
  5. Sampling audits. Reviewers check a share of autonomous actions; findings become evaluation cases and can tighten or relax the tiers.
  6. Controls for unattended work. A kill switchlater · 15.26, rate limits, spend and action budgets, anomaly alerts, and an audit log of who approved what.
  7. A trust ladder. Start with approval on most actions, collect the decisions, and move an action to on-the-loop only when it is approved almost every time and errors stay rare.

Each mode has a typical failure. In the loop: delays, and reviewer fatigue, where people approve the fiftieth request without reading it; every pause needs a timeout and a safe default (deny or escalate). On the loop: a mistake lands before anyone notices, so it suits only actions that can be undone, and only when someone actually watches the alerts.

Before pausing, the approval node notifies the manager on Slack. Managers complain that every request arrives twice, the second time right after they answer.

Make it your own

Solutions

SolutionP1 · Nothing was written yet

No: the node paused before returning, so its update has not been applied, and approved is not in the state. After the resume, approval and finish run, and next is (), meaning the run is finished.

SolutionB1 · New input starts a new run

Invoking a thread with input, rather than a Command, starts a new run on that thread from START. The new run reached approval and paused again with a new interrupt, so the thread is still waiting and nothing was approved. Approvals must resume with Command(resume=...); the approval API should take the thread ID and the decision, and nothing else.

SolutionD1 · Code before interrupt runs on every resume

The Slack message is sent before interrupt, and the node reruns from its start on resume, so the manager is notified again when they answer. Move the side effect into its own node before the waiting node; that node completes and is checkpointed, so it is not repeated:

SENT.clear()

def notify_manager(state):
    SENT.append(f"Slack message to manager about {state['order_id']}")
    return {}

def wait_for_manager(state):
    return {"approved": interrupt({"order_id": state["order_id"], "amount": state["amount"]})}

b = StateGraph(RefundState)
b.add_node("notify_manager", notify_manager); b.add_node("wait_for_manager", wait_for_manager)
b.add_edge(START, "notify_manager"); b.add_edge("notify_manager", "wait_for_manager"); b.add_edge("wait_for_manager", END)
notify = b.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "slack-2"}}
notify.invoke({"order_id": "A-1077", "amount": 7999}, c)
print(notify.invoke(Command(resume=True), c)["approved"], "|", SENT)

True | ['Slack message to manager about A-1077']

The same rule applies to anything with an effect: database writes, payments, emails. Before interrupt, only read.

SolutionM1 · Pause only when needed
LIMIT = 5000

def maybe_approve(state):
    if state["amount"] <= LIMIT:
        return {"approved": True, "note": "auto-approved"}
    answer = interrupt({"question": "Approve this refund?", "order_id": state["order_id"], "amount": state["amount"]})
    return {"approved": answer["approved"], "note": answer.get("note", "approved by a person")}

b = StateGraph(RefundState)
b.add_node("approval", maybe_approve); b.add_node("finish", finish)
b.add_edge(START, "approval"); b.add_edge("approval", "finish"); b.add_edge("finish", END)
gated = b.compile(checkpointer=InMemorySaver())
for oid, amount in [("A-3001", 1200), ("A-3002", 7999)]:
    c = {"configurable": {"thread_id": oid}}
    out = gated.invoke({"order_id": oid, "amount": amount}, c, version="v2")
    if out.interrupts:
        out = gated.invoke(Command(resume={"approved": True}), c, version="v2")
    print(oid, "->", out.value["done"], "|", out.value["note"])

A-3001 -> refunded INR 1,200 | auto-approved
A-3002 -> refunded INR 7,999 | approved by a person

The node decides whether to interrupt from the state, which does not change between the pause and the resume, so the rerun takes the same branch. That is the safe way to make an interrupt conditional.

Check your understanding

Explain the mechanismHow does interrupt work in LangGraph?

Worked answer. Calling interrupt(payload) inside a node raises a special signal; the runtime saves a checkpoint, records the pending interrupt and returns the payload to the caller. The run is then finished from the process's point of view. To continue, the caller invokes the same thread with Command(resume=value); the runtime reruns the node from its start, and this time interrupt returns value. It requires a checkpointer, and because the node reruns, code before the interrupt must have no side effects.

A plausible wrong answer. "The node waits on a blocking call until someone answers." Nothing blocks; the run ends and restarts from the checkpoint, which is why approvals can take days.

Follow-ups. How are several interrupts in one node matched to answers?

Debug a failureApprovals sometimes apply to the wrong refund. What would you check?

Worked answer. How the approval reaches the run: the decision must resume the exact thread that paused, so the approval request must carry the thread ID, and the resume must be a Command, not new input. Then the payload: the person must see the order ID and amount from the state at the moment of the pause, not values looked up again later. Finally, conditional interrupts: a node whose branch changes between pause and resume can match an answer to a different interrupt. I would log thread ID, interrupt ID, payload and decision for every approval.

A plausible wrong answer. "Two people clicked at the same time." Possible, but the common causes are a missing thread ID or a payload that did not show what was being approved.

Follow-ups. How would you expire an approval that nobody answered?

Defend a designinterrupt in your own graph, or HumanInTheLoopMiddleware on create_agent?

Worked answer. The middleware when the thing to approve is an agent's tool call: it already offers approve, edit, reject and respond, per tool, with a standard payload. interrupt in my own node when the decision is part of a workflow rather than a tool call, for example a refund over a limit, a missing piece of information only the customer has, or several sign-offs in parallel, or when the payload or validation is specific to the business. Both use the same mechanism and both need a checkpointer and an approval service.

A plausible wrong answer. "Middleware for everything." Some decisions are not tool calls and have nothing for the middleware to hook into.
