Why this came about

LangGraph runs a graph the way Google's Pregel system (2010) ran large graph computations: in rounds called supersteps, where every active node runs and all their messages are delivered together at the end of the round. That design makes parallel work predictable and gives a natural place to save a checkpoint. In 2025 and 2026, teams running agents for days and over thousands of steps found the edges of that design: write collisions that break a thread, side effects that repeat after a crash, and checkpoints that grow with the square of the conversation. LangGraph 1.2 (May 2026) added DeltaChannel and durability controls to address the last two.

The problem: the graph works in tests and fails in production

Three surprises reach every team that runs LangGraph for real. Two parallel nodes write the same key, and from then on every read of that thread fails, even the admin page that tries to look at it. A refund tool runs, the process is killed by a deploy a moment later, and the resumed run refunds the customer a second time. A long research thread that holds 100 KB of messages turns out to use 5 MB in the database. None of these are bugs in your nodes. They come from how the runtime plans, merges and saves each step, and each one has a clear fix once you can see the machinery.

In plain words first
A meeting with minutes

Picture a meeting where everyone works at the same time, then the secretary collects all the notes at once and writes the minutes. That round is a superstep. Each topic in the minutes has a rule for combining notes: some topics keep one answer and complain if two people wrote different ones (LastValue), others add every note to a list (a reducer). After each round the minutes are filed (a checkpoint). If the building is evacuated mid-round, whoever had not handed in their note does that part of the work again, which is fine for thinking and not fine for sending money. And if every set of minutes is a full copy of all earlier minutes, the filing cabinet fills fast (DeltaChannel files only the new notes).

Idea 1 · One superstep: plan, run, update

Every LangGraph run is a loop of supersteps. Plan: find the nodes whose input changed since they last ran. Run: execute all of them, in parallel. Update: apply all their writes at once, then save a checkpoint. A node never sees a write from its own superstep; it reads the state as it was at the end of the previous one.

The update phase has a rule worth testing. Two nodes run in parallel and each appends to one list. One is slow and one is fast:

import operator, time
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class Lookup(TypedDict, total=False):
    found: Annotated[list, operator.add]          # a reducer: every write is appended

finished = []
def make(name, seconds):
    def node(state):
        time.sleep(seconds)
        finished.append(name)                     # the order the nodes really finished in
        return {"found": [name]}
    return node

for slow in ("a", "b"):
    finished.clear()
    g = (StateGraph(Lookup).add_node("a", make("a", 0.3 if slow == "a" else 0.01))
         .add_node("b", make("b", 0.3 if slow == "b" else 0.01))
         .add_edge(START, "a").add_edge(START, "b").compile())
    out = g.invoke({"found": []})
    print(f"slow node {slow}: finished in order {finished} -> state {out['found']}")
What you should see
slow node a: finished in order ['b', 'a'] -> state ['a', 'b']
slow node b: finished in order ['a', 'b'] -> state ['a', 'b']

The nodes finished in different orders, and the state was ['a', 'b'] both times. Before applying anything, the update phase sorts the tasks by their task path, a stable name the planner gave each task, and hands the writes to each reducer in that order. So the result never depends on which node was faster: you can test it, and two replicas of your service compute the same state. The other side of the rule: if your reducer keeps only the last value, the winner is the task whose path sorts last, not the one that finished last.

Idea 2 · Watch an agent's supersteps

create_agent (Lesson 14.96) is a graph too, so its run is a series of supersteps. A checkpointer records one checkpoint per superstep, with the nodes planned for the next one:

from mockllm import start                                    # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain.agents import create_agent
from langgraph.checkpoint.memory import InMemorySaver

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock", temperature=0)
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

agent = create_agent(chat, tools=[get_order_status], checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "t1"}}
agent.invoke({"messages": [{"role": "user", "content": "Where are A-1001 and A-1002?"}]}, cfg)
for snap in reversed(list(agent.get_state_history(cfg))):
    print(f"step {snap.metadata['step']:>2}  next {snap.next}  messages so far {len(snap.values.get('messages', []))}")
What you should see
step -1  next ('__start__',)  messages so far 0
step  0  next ('model',)  messages so far 1
step  1  next ('tools', 'tools')  messages so far 2
step  2  next ('model',)  messages so far 4
step  3  next ()  messages so far 5

Five checkpoints for one question. Step -1 holds the input, step 0 the question in the state, step 1 the model's reply with two tool calls. Look at next after step 1: ('tools', 'tools'). create_agent turns each tool call into its own task with Send (Lesson 14.107), so both lookups run in the same superstep, side by side, and both results land together at step 2. Step 3 has nothing next: the model answered without asking for a tool, so the loop stopped. The animated plate in Lesson 14.96 draws this same run.

Idea 3 · Channels: how each key combines writes

Every key of the state is stored in a channel, an object with one job: take all the writes for that key in one superstep and produce the new value. A key with no reducer gets a LastValue channel; a key with a reducer gets a BinaryOperatorAggregate. LangGraph also uses channels internally: a Topic collects the Send tasks, and an EphemeralValue carries the input and routing signals, then clears. You can drive them directly:

from langgraph.channels import LastValue, BinaryOperatorAggregate, Topic, EphemeralValue
from langgraph.errors import InvalidUpdateError

for name, ch in [("LastValue", LastValue(int)), ("BinaryOperatorAggregate(add)", BinaryOperatorAggregate(int, operator.add)),
                 ("Topic", Topic(int)), ("EphemeralValue", EphemeralValue(int))]:
    row = []
    for writes in ([1], [], [2, 3]):                     # one write, no write, two writes in one step
        try:
            ch.update(writes)
            try:
                value = ch.get()
            except Exception as e:
                value = type(e).__name__
            row.append(f"{writes}->{value}")
        except InvalidUpdateError:
            row.append(f"{writes}->InvalidUpdateError")
    print(f"{name:30} " + "   ".join(row))
What you should see
LastValue                      [1]->1   []->1   [2, 3]->InvalidUpdateError
BinaryOperatorAggregate(add)   [1]->1   []->1   [2, 3]->6
Topic                          [1]->[1]   []->EmptyChannelError   [2, 3]->[2, 3]
EphemeralValue                 [1]->1   []->EmptyChannelError   [2, 3]->InvalidUpdateError

Read the rows as the rules of the state. A plain key keeps its value when no node writes it, and refuses two writes in one step. A key with a reducer folds every write in (here 1 + 2 + 3 = 6). A Topic holds a step's items and clears when nobody writes. An EphemeralValue lives for one step only. The row to remember is the first one: two nodes that write a plain key in the same superstep raise InvalidUpdateError.

Idea 4 · A collision that breaks a thread, and the repair

The error itself is easy to understand. What happens to the thread afterwards is not. Two shipping nodes run in parallel and both set carrier, a key with no reducer, on a graph with a checkpointer:

from langgraph.checkpoint.memory import InMemorySaver

ran = []
def bluedart(state): ran.append("bluedart"); return {"carrier": "BlueDart"}
def delhivery(state): ran.append("delhivery"); return {"carrier": "Delhivery"}

class Shipment(TypedDict, total=False):
    carrier: str                                           # no reducer: a LastValue channel

saver = InMemorySaver()
cfg = {"configurable": {"thread_id": "ship-1"}}
def build(schema):
    return (StateGraph(schema).add_node("bluedart", bluedart).add_node("delhivery", delhivery)
            .add_edge(START, "bluedart").add_edge(START, "delhivery")
            .add_edge("bluedart", END).add_edge("delhivery", END).compile(checkpointer=saver))

broken = build(Shipment)
try:
    broken.invoke({"carrier": ""}, cfg)
except InvalidUpdateError as e:
    print("invoke:", type(e).__name__, "-", str(e).split(".")[0])
try:
    broken.get_state(cfg)
except InvalidUpdateError as e:
    print("get_state:", type(e).__name__, "(the saved writes still collide)")
print("nodes that ran:", sorted(ran))
What you should see
invoke: InvalidUpdateError - At key 'carrier': Can receive only one value per step
get_state: InvalidUpdateError (the saved writes still collide)
nodes that ran: ['bluedart', 'delhivery']

Both nodes ran before the error, because the collision is found in the update phase. Their outputs were already saved as pending writes of the checkpoint the step started from. Now every read of the thread replays those two writes into the same LastValue channel and raises again: get_state fails, a resume fails, a new message to the thread fails. Retrying does not help, and editing the state with update_state does not either, because the pending writes are still there.

The repair is a schema with a reducer for that key, compiled against the same checkpointer:

def keep_both(old, new):
    return f"{old} / {new}" if old else new

class FixedShipment(TypedDict, total=False):
    carrier: Annotated[str, keep_both]                     # a reducer: both writes are allowed

ran.clear()
fixed = build(FixedShipment)
print("get_state with a reducer:", fixed.get_state(cfg).values)
print("resume:", fixed.invoke(None, cfg), "| nodes run again:", ran)
What you should see
get_state with a reducer: {'carrier': 'BlueDart / Delhivery'}
resume: {'carrier': 'BlueDart / Delhivery'} | nodes run again: []

The saved writes now combine, the thread reads again, and the resume finished without running either node again: no model call or tool call was paid twice. The lesson for production: give a reducer to every key that two nodes can write in the same superstep, before you deploy, and add a test that runs parallel branches on a checkpointer.

Idea 5 · What a checkpoint saves, and when

A checkpointer has two write calls. put_writes saves the output of one finished task, as soon as it finishes. put saves the whole checkpoint at the end of the superstep. The durability mode of a run (durability= on invoke and stream) decides when they happen:

class Order(TypedDict, total=False):
    steps: Annotated[list, operator.add]

def check_stock(state): return {"steps": ["stock ok"]}
def reserve(state): return {"steps": ["reserved"]}

class CountingSaver(InMemorySaver):                         # counts the two kinds of write
    def __init__(self):
        super().__init__(); self.puts = self.put_writes_calls = 0
    def put(self, config, checkpoint, metadata, new_versions):
        self.puts += 1
        return super().put(config, checkpoint, metadata, new_versions)
    def put_writes(self, config, writes, task_id, task_path=""):
        self.put_writes_calls += 1
        return super().put_writes(config, writes, task_id, task_path)

for mode in ("sync", "async", "exit"):
    saver = CountingSaver()
    g = (StateGraph(Order).add_node("check_stock", check_stock).add_node("reserve", reserve)
         .add_edge(START, "check_stock").add_edge("check_stock", "reserve").add_edge("reserve", END)
         .compile(checkpointer=saver))
    cfg = {"configurable": {"thread_id": "o-1"}}
    g.invoke({"steps": []}, cfg, durability=mode)
    steps = [h.metadata["step"] for h in g.get_state_history(cfg)]
    print(f"durability={mode:5}  put calls {saver.puts}  put_writes calls {saver.put_writes_calls}  history steps {steps}")
What you should see
durability=sync   put calls 4  put_writes calls 3  history steps [2, 1, 0, -1]
durability=async  put calls 4  put_writes calls 3  history steps [2, 1, 0, -1]
durability=exit   put calls 1  put_writes calls 0  history steps [2]
Mode What is saved during the run What the run waits for After a crash
"exit" Nothing until the run ends, fails or pauses at an interrupt Nothing The whole run starts again from the input; there is no history for time travel
"async" (the default) Every checkpoint and every task's writes, in the background Nothing Repeats a task that had just finished, and any step after the last saved checkpoint
"sync" The same as async Each checkpoint's put, before the next step starts Repeats a task that had just finished

sync is the safest of the three, and it is still not a guarantee. put_writes for a finished task runs in the background in every mode, and sync only waits for the checkpoint at the end of the step. A task that returned a few milliseconds before the process died can lose its writes and run again on resume. The AI Engineering from Scratch LangChain manual measured exactly this: with a crash right after a node returned, the node ran again in 97 of 100 trials in sync mode and 95 of 100 in async mode; with 0.2 seconds between the return and the crash, it never did. One more trap from the same source: durability="sync" on a graph with no checkpointer raises an AttributeError instead of warning, so pass it only with a checkpointer.

Idea 6 · Side effects: a checkpoint cannot undo them

So a node can run twice. That is harmless for thinking and harmful for anything that changes the world: a refund, an email, a stock reservation. The script below pays a refund and is killed right after the payment, before the node returns, the way a deploy or an out-of-memory kill would do it. Save it next to your code:

# save as: refund_job.py
import os, sys, operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.config import get_config

class Refund(TypedDict, total=False):
    order_id: str
    log: Annotated[list, operator.add]

def already_paid(key):
    return os.path.exists("ledger.txt") and key in open("ledger.txt").read().split()

def pay(state):
    key = f"{get_config()['configurable']['thread_id']}:pay"       # one key per thread and step
    if sys.argv[2] == "keyed" and already_paid(key):
        return {"log": ["pay skipped, already done"]}
    with open("ledger.txt", "a") as f:
        f.write(f"{key} refund {state['order_id']}\n")            # the side effect: money moves
    if sys.argv[1] == "crash":
        os._exit(1)                                               # the process dies before the node returns
    return {"log": ["paid"]}

def notify(state):
    return {"log": ["customer told"]}

with SqliteSaver.from_conn_string("refunds.db") as saver:
    graph = (StateGraph(Refund).add_node("pay", pay).add_node("notify", notify)
             .add_edge(START, "pay").add_edge("pay", "notify").add_edge("notify", END)
             .compile(checkpointer=saver))
    cfg = {"configurable": {"thread_id": "refund-A-1077"}}
    print(graph.invoke({"order_id": "A-1077", "log": []} if sys.argv[1] == "crash" else None, cfg, durability="sync")["log"])

Now crash it, resume it in a new process, and count the payments, first without a key and then with one:

import os, subprocess, sys

def run(*args):
    p = subprocess.run([sys.executable, "refund_job.py", *args], capture_output=True, text=True)
    return p.stdout.strip() or f"(process died, exit code {p.returncode})"

for mode in ("plain", "keyed"):
    for f in ("refunds.db", "ledger.txt"):
        if os.path.exists(f):
            os.remove(f)
    print(mode, "| first run:", run("crash", mode), "| resume:", run("resume", mode))
    print("      ledger rows:", len(open("ledger.txt").read().splitlines()))
What you should see
plain | first run: (process died, exit code 1) | resume: ['paid', 'customer told']
      ledger rows: 2
keyed | first run: (process died, exit code 1) | resume: ['pay skipped, already done', 'customer told']
      ledger rows: 1

Without a key, the resume ran pay from its first line, because its writes were never saved, and the customer was refunded twice even in sync mode. With a key, the node first checked its own records, found the payment and skipped it. The rules, the same as Lesson 14.59's:

  • Give every side effect an idempotency key built from things that are the same on a re-run: the thread ID, the node, the order ID. Never use a timestamp or a random number.
  • Check your records before acting, or let the service do it: most payment APIs accept an idempotency key and refuse a duplicate.
  • Keep approvals and model calls out of the node that acts. A node that asks for approval with interrupt() and then pays will, after a crash, ask the reviewer again and may pay again (Lesson 14.104).

Idea 7 · Checkpoints grow with the square of a thread

A checkpoint stores the state as it is after the step, so a list key is stored in full in every checkpoint. A thread of 100 steps that adds one item per step stores 1 + 2 + ... + 100 items in total. Measure it with a reader that adds one 1 KB page per step:

import sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.channels import DeltaChannel

PAGE = "x" * 1000                                     # one tool result of about 1 KB
def append_all(old, batches):                         # a DeltaChannel reducer gets every write of a step at once
    return (old or []) + [item for batch in batches for item in batch]

def read_page(state):
    return {"pages": [f"page {len(state['pages']) + 1}: {PAGE}"]}

def more(state):
    return "read_page" if len(state["pages"]) < 100 else END

def run(label, pages_type):
    class Doc(TypedDict):
        pages: pages_type
    path = f"growth_{label}.db"
    if os.path.exists(path):
        os.remove(path)
    with SqliteSaver.from_conn_string(path) as saver:
        g = (StateGraph(Doc).add_node("read_page", read_page).add_edge(START, "read_page")
             .add_conditional_edges("read_page", more).compile(checkpointer=saver))
        out = g.invoke({"pages": []}, {"configurable": {"thread_id": "long-doc"}, "recursion_limit": 200})
        db = sqlite3.connect(path)
        rows, size = db.execute("select count(*), sum(length(checkpoint)) from checkpoints").fetchone()
        wsize = db.execute("select sum(length(value)) from writes").fetchone()[0]
        print(f"{label:6} pages={len(out['pages'])}  checkpoint rows={rows}  checkpoints about {round(size / 10000) * 10:,} KB  writes about {round(wsize / 10000) * 10:,} KB")

run("plain", Annotated[list, operator.add])
run("delta", Annotated[list, DeltaChannel(append_all)])
What you should see
plain  pages=100  checkpoint rows=102  checkpoints about 5,170 KB  writes about 100 KB
delta  pages=100  checkpoint rows=102  checkpoints about 160 KB  writes about 100 KB

The content was about 100 KB (the writes table stores each page once). The plain thread's checkpoints held about 5.2 MB, fifty times the content, and the number grows with the square of the thread's length. DeltaChannel, new in LangGraph 1.2 and still marked beta, stores only each step's writes plus a full snapshot every snapshot_frequency steps (100 by default), and rebuilds the value on read: about 160 KB here, a thirtieth of the plain thread. Its reducer receives every write of a step in one call, which is why append_all takes a list of batches. For an agent, swap the message channel by passing create_agent(..., state_schema=...) a subclass of AgentState whose messages key uses a DeltaChannel. Summarising long threads (Lesson 14.105) helps too, because it shortens what every checkpoint has to hold.

In the same manual's measurements, the framework's own work (planning, merging, saving) took under half a percent of a real agent's time; the model took the rest. Spend optimisation effort on bytes and model calls, not on the loop.

Idea 8 · What survives a round trip through a checkpoint

Everything in the state goes through the checkpointer's serializer (JsonPlusSerializer, which writes msgpack) and comes back on the next step, after a resume, or on another server. Most values come back as they went in. Some do not:

import logging; logging.disable(logging.WARNING)      # hide the loader's warnings for this demo
from collections import Counter, defaultdict
from datetime import datetime
from decimal import Decimal
from zoneinfo import ZoneInfo
from langgraph.checkpoint.serde.jsonplus import JsonPlusSerializer

serde = JsonPlusSerializer()
class Plain:
    def __init__(self, n): self.n = n

values = {"tuple": (1, 2), "set of ints": {1, 2}, "set of tuples": {(1, 2)}, "Counter": Counter("abca"),
          "defaultdict": defaultdict(list, {"k": [1]}), "Decimal": Decimal("7999.00"),
          "datetime in Asia/Kolkata": datetime(2026, 11, 22, 21, 0, tzinfo=ZoneInfo("Asia/Kolkata")), "plain class": Plain(3)}
for name, v in values.items():
    try:
        back = serde.loads_typed(serde.dumps_typed(v))
        same = type(back) is type(v) and back == v and getattr(back, "tzinfo", None) == getattr(v, "tzinfo", None)
        shown = back.tzinfo if isinstance(back, datetime) else back
        print(f"{name:26} -> {type(back).__name__:9} {'same' if same else 'CHANGED'}  {shown!r}")
    except Exception as e:
        print(f"{name:26} -> {type(e).__name__}: {e}")
What you should see
tuple                      -> list      CHANGED  [1, 2]
set of ints                -> set       same  {1, 2}
set of tuples              -> list      CHANGED  [[1, 2]]
Counter                    -> dict      CHANGED  {'a': 2, 'b': 1, 'c': 1}
defaultdict                -> dict      CHANGED  {'k': [1]}
Decimal                    -> Decimal   same  Decimal('7999.00')
datetime in Asia/Kolkata   -> datetime  CHANGED  datetime.timezone(datetime.timedelta(seconds=19800))
plain class                -> TypeError: Type is not msgpack serializable: Plain

A node that calls .most_common() on a Counter works on the first step and fails after a resume, because what came back is a plain dict. A time zone comes back as a fixed offset, which is wrong across a daylight-saving change. A plain class cannot be saved at all. Keep state to plain JSON-like values, Pydantic models, dataclasses, enums and LangChain messages, and convert at the edges.

Loading also has a security side. A checkpoint row names the type to rebuild, so whoever can write to your checkpoint database can choose what your process constructs. Treat the checkpoint store as trusted infrastructure, never as user input, and in production set LANGGRAPH_STRICT_MSGPACK=true, which makes the loader return raw fields instead of building classes that are not on its allow list.

Putting it together

Symptom Cause Fix
InvalidUpdateError: At key 'x': Can receive only one value per step, then every read of the thread fails Two tasks wrote a key with no reducer in one superstep Add a reducer to the key and recompile on the same checkpointer; add a parallel-branch test
Parallel results in an unexpected order The update phase applies writes in task-path order, not finish order Do not depend on which task finished first; sort explicitly if order matters
A refund or email happened twice after a crash or deploy A node with a side effect ran again on resume An idempotency key and a records check in the node, or at the service
No history to go back to The run used durability="exit" Use "async" (the default) or "sync"
The checkpoint database grows far faster than the conversation Every checkpoint holds the whole message list DeltaChannel for long lists, summarisation, retention policies
A value has the wrong type after a resume The serializer cannot round-trip that type Plain JSON-like types, Pydantic models, dataclasses
In production
The runtime in production
  • Test with a checkpointer: many of these failures appear only when state is saved and reloaded. Run your graph tests on InMemorySaver and at least one test that resumes in a new process on SQLite or Postgres.
  • Deploys are crashes: a rolling deploy kills processes mid-step. Combine RunControl.request_drain() on shutdown (Lesson 14.109), which stops at the next superstep boundary with a resumable checkpoint, with idempotent side effects for the steps that were running.
  • Retention: decide how long to keep checkpoint history per thread, and prune old checkpoints, or the database grows without limit even with DeltaChannel.
  • Watch the bytes: alert on checkpoint size per thread, the same way you alert on token usage.

Check your mental model
  • ✗ "Parallel writes land in the order the nodes finish."
    ✓ They are applied in task-path order, the same on every run.
  • ✗ "InvalidUpdateError only fails the run that caused it."
    ✓ The colliding writes are saved, so every later read of the thread fails until the schema gets a reducer.
  • ✗ "durability=\"sync\" means a node never runs twice."
    ✓ A task that just finished can still lose its writes in a crash; keys on side effects are still needed.
  • ✗ "A checkpoint stores only what changed."
    ✓ By default it stores each changed channel in full; DeltaChannel stores only the writes.

Debugging exercise: a Counter that stopped counting

This node tallies how often each reason appears in returns. It works in a single run and fails when the thread is resumed from its checkpoint:

def tally(state):
    reasons = state.get("reasons", Counter())
    reasons.update({state["reason"]: 1})
    return {"reasons": reasons, "top": reasons.most_common(1)[0][0]}

print("first step:", tally({"reason": "damaged"})["top"])
saved = serde.loads_typed(serde.dumps_typed(Counter({"damaged": 1})))   # what the checkpoint gives back
try:
    tally({"reasons": saved, "reason": "late"})
except AttributeError as e:
    print("AttributeError:", e)

What it printed:

first step: damaged
AttributeError: 'dict' object has no attribute 'most_common'

Explain why, and fix the node so it works before and after a resume. (Solution D1.)

Make it your own

Change refund_job.py so the idempotency key also includes the order ID, and make pay record the key in a SQLite table with a UNIQUE constraint instead of a text file, so two processes that race cannot both insert it. (Solution M1.)

Solutions

SolutionP1 · The last task path wins

['b'] in both runs. The reducer receives the writes in task-path order, and b's path sorts after a's, so b's write is applied last whichever node was slow. If you need "the latest by time", put a timestamp in the value and choose explicitly in the reducer.

SolutionB1 · Sync needs a checkpointer

With no checkpointer, every mode warns that durability has no effect. "async" and "exit" then run normally, but "sync" raises an AttributeError from inside the loop, because it waits for a checkpoint write that was never started (reported in LangGraph issue #9267). Pass durability="sync" only to a graph compiled with a checkpointer.

SolutionD1 · Store plain values, rebuild rich ones

The checkpointer saved the Counter as a plain dict, so after a resume reasons has no most_common. Store a plain dictionary in the state and build the Counter inside the node:

def tally(state):
    reasons = Counter(state.get("reasons", {}))          # rebuild from the plain dict
    reasons.update({state["reason"]: 1})
    return {"reasons": dict(reasons), "top": reasons.most_common(1)[0][0]}

print(tally({"reasons": {"damaged": 2, "late": 1}, "reason": "late"}))

{'reasons': {'damaged': 2, 'late': 2}, 'top': 'damaged'}
SolutionM1 · Let the database refuse the duplicate
import sqlite3

def pay_once(key, order_id):
    db = sqlite3.connect("ledger.db")
    db.execute("create table if not exists refunds (key text unique, order_id text)")
    try:
        with db:
            db.execute("insert into refunds values (?, ?)", (key, order_id))   # fails if the key exists
        return "paid"
    except sqlite3.IntegrityError:
        return "already paid"

if os.path.exists("ledger.db"):
    os.remove("ledger.db")
print(pay_once("refund-A-1077:pay:A-1077", "A-1077"), "|", pay_once("refund-A-1077:pay:A-1077", "A-1077"))

paid | already paid

In pay, call pay_once(f"{thread_id}:pay:{state['order_id']}", state['order_id']) before moving money, and move money only when it returns "paid". A unique constraint holds even when two processes race, which a "check, then write" in Python does not. With a real payment provider, pass the same key as its idempotency key.

Check your understanding

Explain the mechanismHow does LangGraph execute a graph, step by step?

Worked answer. In supersteps, after Google's Pregel model. Each superstep plans the tasks whose trigger channels changed since they last ran (plus one task per pending Send), runs them in parallel, then applies all their writes at once through each key's channel, sorted by task path, and saves a checkpoint. A node reads the state as of the previous superstep, never a sibling's write from the same one. The run ends when a step plans no task, or at the recursion limit, which counts supersteps.

A plausible wrong answer. "Nodes run one after another along the edges, and each sees the previous node's output immediately." That misses parallel steps and the all-at-once update.

Follow-ups. Why does the update phase sort tasks before applying their writes?

Debug a failureAfter adding a second branch, one customer's thread fails on every request with InvalidUpdateError, even reads. What happened, and how do you fix it without losing the conversation?

Worked answer. Two tasks wrote a key with no reducer in the same superstep. The runtime raised in the update phase after both had run, and their writes were saved as pending writes, so every read replays the collision. Fix the schema with a reducer for that key (or make only one branch write it), recompile against the same checkpointer, and the thread reads and resumes without rerunning the nodes. Add a test that runs the parallel branches on a checkpointer.

A plausible wrong answer. "Delete the thread." That loses the customer's history and does not stop the next thread from breaking.

Follow-ups. Why does update_state not repair it?

Defend a designIs durability="sync" enough to make a refund agent safe to retry after crashes?

Worked answer. No. sync waits for each checkpoint, but a task that finished just before a crash can still lose its writes and run again, and a model can also simply ask for the same action twice. Safety comes from the side effect: an idempotency key built from stable values, checked against your records or passed to a provider that refuses duplicates, with the approval step in a separate node. Choose sync when losing a completed step is expensive, and keep the key either way.

A plausible wrong answer. "Yes, sync writes every checkpoint before continuing." That confuses the checkpoint with the task's own writes.

Follow-ups. Where should the idempotency key come from?
