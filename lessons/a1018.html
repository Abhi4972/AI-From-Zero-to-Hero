In plain words first
The idea in one line

Every autoregressive LLM from GPT-2 to Llama 3 trains on one loss per position: predict the next token. DeepSeek-V3 added a second loss per position: predict the token after that. The extra 14B of parameters (on a 671B model) got distilled back into the main model through gradient flow, and the trained MTP heads were repurposed at inference as speculative-decoding drafters with 80%+ acceptance. 1.8× generation throughput came for free. Terms you'll hear
Term What people say What it actually means
MTP module "Extra loss block" A small transformer block plus projection that predicts a token k positions ahead of the main model
Prediction depth "Which offset" The integer k such that module k predicts t_{i+k+1} from prefix through position i (the main model is depth 0 and predicts t_{i+1})
Parallel MTP "Gloeckle-style" D independent heads on the same backbone hidden state, no conditional chain
Sequential MTP "DeepSeek-V3 style" Each module conditions on the previous depth's hidden state plus the next token's embedding; preserves causal chain
Shared output head "Reuse the main head" The MTP modules call the main model's LM head, not a separate output projection
Shared embedding "Reuse the main table" Same vocabulary embedding table is used everywhere; no duplicate parameters
Projection matrix $M_k$ "Combine hidden + next-token" An h x 2h linear layer that folds the previous hidden state and the target-token embedding into the next depth's input
Joint loss $L_{\text{MTP}}$ "Averaged extra losses" Arithmetic mean of per-depth cross-entropy losses, scaled by lambda
Acceptance rate at depth 1 "How often MTP draft is right" The rate at which the D=1 MTP module's top-1 prediction equals the main model's top-1 prediction; 80%+ on DeepSeek-V3
Lambda weighting "Extra-loss importance" Per-depth scaling factor; 0.3 at start of training, 0.1 later on DeepSeek-V3

The problem

In plain words first

A language model is normally trained to predict only the next token. Multi-token prediction (MTP) adds a small extra module that, at every position, also predicts the token after next, given the main model's hidden state and the actual next token. Training on this harder second target gives the model a denser learning signal, and at inference the same module is a ready-made draft for speculative decoding (Lesson 10.15): it guesses one extra token per step, the main model checks it, and DeepSeek-V3 gets 1.8× more tokens per second. This lesson runs the lesson's toy module, counts DeepSeek-V3's real MTP module from its config, works out exactly why the module must see the next token, and measures that effect with a real model. No model is trained.

Next-token prediction is the standard LLM training objective. Every hidden state is supervised to predict exactly one thing: the immediately following token. That is a surprisingly weak signal. Most of the information in a sequence extends beyond one token — structure, coherence, factuality, arithmetic flow. The model has to learn those by accumulating many one-token signals over trillions of tokens.

MTP asks: what if every hidden state were supervised to predict multiple future tokens at once? Gloeckle et al. (Meta, 2024) showed this helps. Their implementation put several independent output heads on top of the backbone, each predicting a different offset. Parallel and simple, but every head sees the same hidden state and none knows what the earlier heads predicted. (They can still serve as drafts: Gloeckle et al. report up to 3× faster inference with 4-token heads used for self-speculative decoding.)

DeepSeek-V3 (December 2024) re-designed MTP as sequential modules that keep the causal chain at each prediction depth. The model predicts t+1 from h_i^(0), then predicts t+2 from a new hidden state h_i^(1) that combined h_i^(0) with the E(t+1) embedding, and so on. Each depth is its own small transformer block. The shared embedding and shared output head keep parameter overhead modest. At DeepSeek-V3's scale, 14B extra parameters across MTP modules on top of 671B main-model weights. That 2% overhead bought denser training signals AND a ready-made speculative-decoding draft at inference.

This lesson builds a single MTP module and the D-depth loss from scratch. The math is tidy. The implementation is 150 lines.

Idea 1 · The sequential MTP recipe

DeepSeek-V3 adds D MTP modules on top of the main model. The main model predicts t_{i+1}. Each module k (for k = 1..D) predicts the token k steps further out, t_{i+k+1}, given a prefix through position i.

Module k consists of:

  • A transformer block T_k with its own attention and MLP.
  • A projection matrix M_k that combines the previous-depth hidden state with the embedding of the next-depth ground-truth token.
  • The shared embedding E (same as the main model).
  • The shared output head Out (same as the main model).

At training, for a prefix through position i, the per-depth hidden state is:

hi(0)​hi(k)​​=main model backbone at position i=Tk​(Mk​⋅concat(RMSNorm(hi(k−1)​),RMSNorm(E(ti+k​))))for k≥1​

The per-depth prediction is:

logitsi+k+1​=Out(hi(k)​)for k=1,…,D

The per-depth loss is cross-entropy against the ground-truth t_{i+k+1}:

Lk​=CE(logitsi+k+1​,ti+k+1​)

The joint loss across depths:

LMTP​=Dλ​k=1∑D​Lk​

lambda is a small weighting factor: DeepSeek-V3 uses 0.3 for the first 10T training tokens and 0.1 for the remaining 4.8T. DeepSeek-V3 uses D = 1, so the joint loss is a single extra cross-entropy. The total training loss is L_main + L_MTP.

Idea 2 · Why sequential, not parallel

Gloeckle's original parallel MTP had D output heads, each directly applied to h_i^(0). Each head predicts t_{i+k} from the same backbone hidden state. That trains fine, but the predictions are not conditioned on each other. You cannot use head_1's output to help head_2 — the heads fire in parallel.

DeepSeek-V3's sequential design builds h_i^(k) from h_i^(k-1) plus the actual next-token embedding E(t_{i+k}). That preserves the causal chain: to predict t_{i+k+1}, the module at depth k sees what was at t_{i+k}. This is structurally identical to how an autoregressive decoder consumes its own output, which makes the MTP modules directly usable as speculative-decoding drafters.

At inference: feed h_i^(k-1) and the drafted t_{i+k} into module k, get a prediction for t_{i+k+1}. Repeat. That is exactly an EAGLE-style draft, using the trained MTP module as the draft network. DeepSeek-V3 reports 85–90% acceptance of the second token and 1.8× more tokens per second.

Idea 3 · Parameter accounting

For a model with hidden h and vocabulary V:

  • Main model: billions of parameters, plus one output head of size V * h.
  • Shared output head: reuse the main model's head. No extra params.
  • Shared embedding: reuse the main model's embedding. No extra params.
  • Per-MTP module:
  • Projection M_k: (2h) * h = 2h^2.
  • Transformer block T_k: attention (4h^2 for MHA) plus MLP (typically 8h^2 for SwiGLU with ratio 8/3). About 12h^2 per block.

Total extra per module: ~14h^2. For DeepSeek-V3's h = 7168, D = 1 module: ~14 * 7168^2 = ~720M parameters on paper. DeepSeek-V3 reports 14B: its MTP block is a full MoE layer with 256 experts, 11.5B parameters on its own (counted from the config after Build it), and the count includes the shared embedding and output head.

Idea 4 · The speculative-decoding payoff

During pre-training, an MTP module adds one more transformer layer and one more pass through the output head per token: for DeepSeek-V3 about 4% more forward compute (computed after Build it). The payoff is two-fold:

  1. Denser training signal. Each hidden state sees D+1 supervision targets. Measured effect on MMLU, GSM8K, MATH, HumanEval: consistent few-percentage-point improvements in DeepSeek-V3's ablations.

  2. Free speculative decoding draft at inference. The MTP module is already trained to predict the token after next. Used as a one-token draft, it is accepted 85–90% of the time, so each main-model step yields 1.85 to 1.9 tokens: DeepSeek reports 1.8× more tokens per second.

Idea 5 · Relation to EAGLE

EAGLE trains a small draft model SEPARATELY after pre-training. MTP bakes the draft into pre-training. The two approaches converge on similar accept rates but via different pipelines:

Dimension EAGLE-3 MTP (DeepSeek-V3)
When trained Post-pre-training During pre-training
Backward-compatible with existing weights Yes No (need to re-train)
Draft params 1-2 transformer layers 1 transformer block + projection
Acceptance rate 0.88-0.92 0.85-0.90 for the second token
Benefit beyond speedup Speculative decoding only Denser training signal + speedup

The same idea as a formula

For position i and depth k=1,…,D (depth 0 is the main model):

hi(k)​=Tk​(Mk​[RMSNorm(hi(k−1)​); RMSNorm(Emb(ti+k​))]),Pi+k+1(k)​=softmax(Out(hi(k)​)).
Lk​=−T1​i∑​logPi+k+1(k)​[ti+k+1​],L=Lmain​+Dλ​k=1∑D​Lk​.

Why the module needs ti+k​. A parallel head predicting two tokens ahead must average over the unknown next token: its best possible loss is the conditional entropy H(ti+2​∣t≤i​), which is at least H(ti+2​∣t≤i+1​), the sequential module's best loss, because conditioning never increases entropy.

As a draft with D=1: tokens per main-model step =1+α, with α the acceptance rate of the drafted token.

Worked example
DeepSeek-V3's numbers
  • Projection M1​: $2h \times h = 2 \times 7{,}168^2 = 103$M parameters.
  • One MoE transformer block: attention plus 256 routed experts and one shared expert, 11.5B (counted after Build it). Only 8 experts run per token, so about 0.59B of it is active.
  • Output head, reused: $129{,}280 \times 7{,}168 = 0.93$B, all of it active.
  • Extra forward compute per token: $0.59 + 0.10 + 0.93 = 1.6$B active parameters against 37B, about 4%.
  • At inference with α=0.85 to 0.90: 1.85 to 1.9 tokens per step; DeepSeek measures 1.8× tokens per second after the verification overhead.

Step 1 · shared embedding table

code/main.py builds a single MTP module end to end: shared embedding, projection, transformer block, shared output head. It then computes the per-depth cross-entropy loss on a short synthetic sequence and prints the parameter count by component. A toy vocabulary of 32 tokens keeps the numbers readable.

A single vocab_size x hidden table is used by the main model AND by every MTP module at every depth. Not a second copy — literally the same tensor.

Step 2 · the per-depth combination

def combine(prev_hidden, next_token_embed, M_k):
    # concat along feature dim, then project down to hidden
    concat = rms_norm(prev_hidden) + rms_norm(next_token_embed)  # vector addition stand-in
    projected = matvec(M_k, concat)
    return projected

Real DeepSeek-V3 concatenates the two RMSNormed vectors to [2h] and projects with an h x 2h matrix. The toy uses vector addition for stdlib brevity.

Step 3 · the transformer block at depth k

Self-attention plus MLP. In the toy, a one-layer linear attention block and a SwiGLU MLP keep the structure visible without numpy.

Step 4 · the shared output head

Reuse the main model's output projection. Logits over the vocabulary.

Step 5 · per-depth loss

Cross-entropy of softmax(logits) against the ground-truth token at offset k+1. Aggregate across depths with the lambda / D scaling factor.

Step 6 · parameter accounting

Print the total parameter count, the shared (embedding, head) count, and the per-module extra count. Show the ratio of MTP extra to main-model size.

Step 1. The modules have random weights, so the losses (3.26 and 3.39) sit just below the 3.47 of a uniform guess over 32 tokens: the toy shows the data flow (normalise, combine, transform, shared head, cross-entropy at offset k+1, then λ/D times the sum), not learning. Step 3 is not training either. It makes the synthetic "backbone" hidden states less noisy while keeping the same random modules, and the losses move only from 3.31 to 3.27. Real MTP losses fall because the modules and the backbone are trained together on trillions of tokens.

print("C. Why condition on the next token: a sparse random Markov chain, exact entropies (nats)")
rng = np.random.default_rng(0)
S = 50
P = np.zeros((S, S))
for s in range(S):
    nxt = rng.choice(S, 3, replace=False)            # each state has 3 likely successors
    P[s, nxt] = rng.dirichlet([1, 1, 1])
pi = np.ones(S) / S
for _ in range(500): pi = pi @ P                       # stationary distribution
H = lambda M: -(np.where(M > 0, M * np.log(np.where(M > 0, M, 1)), 0)).sum(1)
P2 = P @ P                                             # two steps ahead, t_{i+1} marginalised out
print(f"  next token, H(t+1 | t)                 : {pi @ H(P):.3f}   (what the main head learns)")
print(f"  parallel head, H(t+2 | t)              : {pi @ H(P2):.3f}   (must average over the unknown t+1)")
print(f"  sequential module, H(t+2 | t, t+1)     : {pi @ H(P):.3f}   (sees the embedding of t+1)")

Reading this output

A. Built from the published config, DeepSeek-V3's single MTP module is one MoE transformer layer of 11.51B parameters, almost all of it (11.27B) in its 256 routed experts, plus the 0.10B projection. Counting the embedding and output head it shares with the main model (1.85B) gives 13.5B, close to the 14B on the model card. Because only 8 of the 256 experts run per token, the module's forward cost is far smaller than its size: about 1.6B active parameters including the output head, roughly 4% more forward compute than the 37B-active main model.

B. With one draft token per step, tokens per main-model step are simply 1+α. DeepSeek's 85–90% acceptance gives 1.85 to 1.9, and the measured 1.8× tokens per second is that minus the cost of running the module and verifying.

C. On a Markov chain where each state has three likely successors, predicting the next token costs 0.84 nats. A parallel head predicting two ahead must spread its bets over all the possible intermediate states: 1.64 nats, almost twice as much. A sequential module that sees the embedding of ti+1​ is back to 0.84: in a Markov chain, knowing ti+1​ makes ti​ irrelevant, so its task is exactly a next-token task. Real text is not Markov, but the effect is the same in kind; the next run measures it on a real model.

Use it: the same idea with real libraries

MTP is integrated into DeepSeek-V3 (December 2024) and the DeepSeek-R1 series. At inference:

  • vLLM uses the MTP module as a draft with --speculative-config '{"method": "mtp", "num_speculative_tokens": 1}'.
  • SGLang runs it through its EAGLE speculative-decoding path, with DeepSeek-V3's MTP weights as the draft.
  • Later open models ship MTP layers for the same purpose: Qwen3-Next, GLM-4.5 and Xiaomi's MiMo.

When to use MTP in a new pre-training run:

  • You control the full pre-training pipeline and want to bank denser training signal.
  • You know you will serve the model at scale and want speculative decoding for free.
  • Your hidden size is at least 4096. At 1B-scale the overhead hurts more than the gain helps.

When not to:

  • Fine-tuning an existing pre-trained dense model. The MTP module is not trained.
  • Research models where you want a clean baseline to compare against. MTP changes the architecture.

What a real model gains from seeing the next token

SmolLM2-360M on 200 positions of Wikipedia text. For each position: the next-token loss; the loss of the token two ahead when the next token is summed out over its 16 most likely values (the best a parallel head could do with this model's knowledge); and the loss two ahead given the true next token (what a sequential module sees in training). Inference only, about a minute on CPU.

import copy, math, torch, transformers, datasets
from transformers import AutoTokenizer, AutoModelForCausalLM
transformers.logging.disable_progress_bar(); transformers.logging.set_verbosity_error(); datasets.disable_progress_bars()
name = "HuggingFaceTB/SmolLM2-360M"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float32).eval()
wiki = datasets.load_dataset("Salesforce/wikitext", "wikitext-2-raw-v1", split="test")
text = " ".join(t.strip() for t in wiki["text"][1:60] if t.strip())
ids = tok(text)["input_ids"][:400]
K = 16                                                    # candidates for the unknown next token
with torch.no_grad():
    full = model(torch.tensor([ids]), use_cache=True)
    lp1 = torch.log_softmax(full.logits[0].float(), -1)                       # log p(t_{i+1} | <= i)

rows = []
positions = range(100, 300)
for i in positions:
    top = lp1[i].topk(K)
    cand = top.indices.tolist()
    if ids[i + 1] not in cand:                            # make sure the true next token is a candidate
        cand[-1] = ids[i + 1]
    with torch.no_grad():                                 # reuse the prefix cache, then run all candidates as one batched step
        cache = copy.deepcopy(full.past_key_values); cache.crop(-(len(ids) - i - 1))   # keep the prefix's cache, reused
        cache.batch_repeat_interleave(len(cand))
        lp2 = torch.log_softmax(model(torch.tensor(cand)[:, None], past_key_values=cache).logits[:, -1].float(), -1)
    w = lp1[i, cand]
    cover = w.exp().sum().item()
    marg = torch.logsumexp(w[:, None] + lp2, 0) - math.log(cover)                # p(t_{i+2} | <= i), t_{i+1} summed out
    j = cand.index(ids[i + 1])
    greedy1 = lp1[i].argmax().item()
    rows.append(dict(next=-lp1[i, ids[i + 1]].item(), cond=-lp2[j, ids[i + 2]].item(), marg=-marg[ids[i + 2]].item(),
                     cover=cover, top_marg=marg.argmax().item() == ids[i + 2],
                     top_cond=lp2[j].argmax().item() == ids[i + 2], top_next=greedy1 == ids[i + 1]))
avg = lambda k: sum(r[k] for r in rows) / len(rows)
print(f"{name} on {len(rows)} positions of Wikipedia text; t+1 summed over its {K} most likely values "
      f"(covering {avg('cover'):.0%} of the probability on average)")
print()
print(f"{'prediction':<52} {'loss (nats)':>11} {'top-1 right':>12}")
print(f"{'t+1 from the prefix (next-token head)':<52} {avg('next'):>11.2f} {avg('top_next'):>11.0%}")
print(f"{'t+2 from the prefix, t+1 unknown (parallel)':<52} {avg('marg'):>11.2f} {avg('top_marg'):>11.0%}")
print(f"{'t+2 from the prefix and the true t+1 (sequential)':<52} {avg('cond'):>11.2f} {avg('top_cond'):>11.0%}")

Reading this output

Predicting the token after next without knowing the next one is much harder: 4.14 nats against 2.88 for ordinary next-token prediction, and the best guess is right 32% of the time instead of 52%. Given the true next token, the two-ahead prediction is as easy as a next-token prediction again (2.86 nats, 52%): with ti+1​ in its input, it is a next-token prediction one step later.

That is the sequential module's training situation. In training it always receives the true next token, so its target is "the next token, one step later", from a hidden state of the main model that has not yet seen that token. A parallel head must learn the much harder averaged prediction. At inference the module receives the main model's own prediction of ti+1​ (correct about half the time for this small model, more often for large ones), which is why its drafts are accepted at high rates.

The middle row is an estimate: the unknown next token is summed over its 16 most likely values, which hold 76% of the probability on average, and the sum is renormalised.

Recap
What to keep from this lesson
  • MTP: an extra module predicts the token after next from the hidden state plus the next token's embedding.
  • Extra loss λ/D·ΣL_k; DeepSeek-V3 uses D = 1, λ = 0.3 then 0.1.
  • The module conditions on the next token, so its best loss is a next-token loss, not a two-ahead one.
  • DeepSeek-V3's module: an 11.5B MoE layer, about 4% more forward compute.
  • As a one-token draft: 85–90% accepted, 1.8× tokens per second.

Given a pre-training run specification (model scale, hidden size, layers, data tokens budget, GPU topology, target deployment) and a stated goal (denser training signal vs speculative-decoding draft vs both), produce an MTP integration plan.

Produce:

1. Depth D. Pick 1 or 2. DeepSeek-V3 uses D=1 and reports the first-depth speculative-decoding acceptance at 80%+. D=2 is diminishing-returns territory for most runs. Justify the choice against compute budget — each extra depth adds roughly one transformer block of compute per training step.
2. Lambda schedule. Default: 0.3 for the first 10% of training, 0.1 afterward. Adjust up to 0.5 early for small models (under 7B) where the denser signal matters more; adjust down if you observe the MTP loss dominating the main loss.
3. Parameter budget. Report per-module parameter count against the main model. Confirm overhead is under 5% of main parameters (dense) or under 3% (MoE).
4. Memory and compute overhead. Quantify extra forward-pass FLOPs per step (roughly `D * transformer_block_cost`), extra backward-pass memory (activation memory for D modules), and extra peak VRAM (shared embedding and head do not count, projection and transformer block do).
5. Inference-time wiring. Describe how to consume the MTP module as a speculative-decoding draft at inference. Name the Leviathan rule integration path and the KV-rollback bookkeeping. Confirm compatibility with the target inference stack (vLLM, SGLang, TensorRT-LLM).

Hard rejects:
- Adding MTP to a dense model pre-trained without it. Cannot retrofit — the MTP modules are not trained.
- D > 2 for a first integration. Gain over D=1 is small; complexity grows quickly.
- MTP on a model under 1B active parameters. Signal is weaker than the overhead cost at that scale.
- Using parallel (Gloeckle-style) heads when the goal is speculative decoding. They do not chain causally.

Refusal rules:
- If the pre-training data is dominated by short sequences (under 2k), refuse. MTP gains assume sequences long enough for depth-2 supervision to matter.
- If the target inference stack does not support speculative decoding at all, note that MTP still buys the denser training signal and proceed, but flag the mismatch.
- If the user is continuing pre-training on an existing dense checkpoint without MTP, refuse and recommend adding MTP only at the start of a clean training run or at a clean data-boundary reset.

Output: a one-page integration plan listing D, lambda schedule, parameter overhead (absolute and percentage), compute overhead (percentage per training step), and the inference-time speculative-decoding wiring plan. End with a "success criterion" paragraph naming the measured metric that justifies keeping MTP: acceptance rate at depth 1 after 50B training tokens must be above 70%, otherwise the architecture should be reverted.

Solutions

SolutionP1 · About 1.4 times as high

About 1.4 times: 4.14 nats against 2.88, and the most likely guess is right 32% of the time instead of 52%. Without the next token, a prediction two ahead must average over every possible next token, and the uncertainty of both steps adds up. Given the true next token, the loss falls back to 2.86, the same as next-token prediction. This is why DeepSeek-V3's module receives the next token's embedding: its task stays learnable, and its drafts, conditioned on the main model's own next-token prediction, are accepted 85–90% of the time.

SolutionB1 · The loss collapses and the draft is useless

The training loss collapses toward zero: the module receives the answer as input and only has to copy it through the projection and the output head. The main model learns nothing useful from this extra loss, and at inference the module cannot work, because the token it would need as input is exactly the one it is supposed to predict. Fed the drafted ti+1​ instead, it has never learned to predict anything and its drafts are almost always rejected. This is the same bug as a causal mask that is shifted by one: check offsets with a test where the input and target positions are printed side by side.

Defend a designYou are about to pretrain a model that will later serve a large volume using speculative decoding. Three ways to get a draft are on the table: bake sequential multi-token modules into pretraining, train a hidden-state draft head after pretraining, or reuse a small model of the same family. Give the decision with its costs, and name the gate you measure before you ship the flag.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. If I control pretraining and the hidden size is at least 4096, I bake in the sequential modules: about 10 percent slower training buys a denser supervision signal and a draft that accepts 80 percent or more at depth one. If the weights already exist, I train a post-hoc head on the verifier's features with about 60 to 200B tokens; it is backward compatible and reaches 0.88 to 0.92 acceptance on general chat. A same-family small model needs no training and sits around 0.55 to 0.70. Whatever I pick, the gate is measured acceptance on my own traffic mix at production concurrency, with the flag off below about 0.55 and the tail latency watched, not the mean.

The three options.

Option When trained Works with existing weights Draft parameters Acceptance Extra benefit
Sequential modules in pretraining during pretraining no one block plus a projection per depth 0.80 and above at depth one denser training signal
Post-hoc head on verifier features after pretraining yes one or two layers, trained on about 60 to 200B tokens 0.88 to 0.92 on chat none beyond speed
Same-family small model none yes a whole small model 0.55 to 0.70 none, and it costs memory

The decision tree.

  1. Do you own pretraining? If yes and the model is large enough, the modules are the only option that improves the model and the serving at once; the report that introduced them measured about 1.8 times generation throughput from the draft alone. At a 1B scale the overhead hurts more than it helps.
  2. Do the weights already exist? Then the post-hoc head. It is a light training job compared with the verifier, and it does not touch the verifier's outputs.
  3. No training budget at all? The small model, as a prototype, knowing the acceptance ceiling is low and the second model takes memory.

The gate.

Speculation is opt-in on the production engine, and the production lesson's rule is that flipping the flag without measuring acceptance on real traffic is an anti-pattern. The plan:

  1. Serve the target plain and record time to first token, inter-token latency and throughput at the target concurrency.
  2. Enable the draft and rerun the same benchmark.
  3. Read accepted draft tokens and proposed draft tokens per request from the engine and divide the first by the second to get acceptance.
  4. Below about 0.55 at production concurrency, disable the flag or train a domain-specific head.
  5. Confirm that the tail inter-token latency did not get worse, because a rejected draft costs a verify and a re-roll.

Traffic mix.

A head trained on general chat sits at 0.6 to 0.8 there and falls to 0.4 to 0.6 on code, medical or legal traffic. Weight the acceptance by traffic share before you decide, and measure each slice on its own; a blended number can hide a slice where speculation is net negative. The capstone's exercise asks exactly this for a 70 percent chat and 30 percent code mix with acceptances of 0.7 and 0.4.

Operate it.

Acceptance drifts when the target changes version and the draft does not, so alert on it per slice, and keep a draft-free or n-gram fallback for the slices where the head stops paying.

Plausible wrong answers.

  • "Always use the latest hidden-state draft; it is strictly best." It needs training against your target and its acceptance on domain traffic can fall to 0.4; the baked-in modules give you a draft and a better model if you own pretraining.
  • "Bake the modules in later with a fine-tune." They are a pretraining choice; an existing dense model gets a post-hoc head instead.
  • "Pick by the speedup on a public benchmark." Acceptance depends on your traffic; the gate is measured on your own mix at your concurrency.

Follow-ups an interviewer may ask.

  • (level 3) The traffic is 70 percent chat at 0.7 acceptance and 30 percent code at 0.4. How do you decide? Expected: weight by traffic share, then check each slice against the floor; code alone is below it, so route code to a plain decode or train a code head.
  • (level 4) The target gets a new version next quarter. What happens to each option? Expected: the baked-in modules move with the model; the post-hoc head must be retrained against the new target; the small model drifts further; alert on acceptance per version.
  • (level 4) What does a hidden-state head read in the current generation? Expected: features from several target layers, not only the last, which is part of why acceptance rose.
  • (level 4) Where does the small-model option still win? Expected: a prototype with no training budget, or a CPU deployment where the engine ships only the plain draft path.

Explain the mechanismA pretraining team wants to supervise each position on more than the next token. One design puts several independent output heads on the backbone. Another chains small modules, one per extra depth. Which design gives you a usable speculative draft at inference, and what does it cost during training?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. The chained design. Module k takes the previous depth's hidden state and the embedding of the actual next token, runs its own small transformer block, and reuses the shared embedding and the shared output head, so its prediction of the token at t plus k plus 1 is conditioned on the token at t plus k, which is the same causal chain a decoder follows and lets the module draft tokens at inference with acceptance at depth one of 80 percent or more for about 1.8 times throughput. Independent heads all read the same hidden state and cannot condition on each other. The training cost is about 10 percent slower pretraining and about 14 h squared parameters per module, with a loss weight of 0.3 early and 0.1 later.

The sequential recipe.

For a prefix through position i, depth zero is the main backbone, and depth k builds on depth k minus 1:

h_i^(k) = T_k( M_k · concat( RMSNorm(h_i^(k-1)), RMSNorm(E(t_{i+k})) ) )
logits_{i+k+1} = Out( h_i^(k) )
L_k = cross-entropy( logits_{i+k+1}, t_{i+k+1} )
L_MTP = (lambda / D) · sum over k of L_k

E is the embedding table and Out is the output head, both shared with the main model. M_k folds the previous hidden state and the next token's embedding into one vector. T_k is one transformer block. The total loss is the main next-token loss plus L_MTP, with lambda at 0.3 for the first 10 percent of training and 0.1 afterward.

Why the chain matters.

To predict two tokens ahead, module one sees what the next token actually was. At inference you feed it the drafted token instead, and it predicts the one after. That is exactly how a hidden-state draft works, so the trained module is a draft network for free. Parallel heads fire from one hidden state, so head two cannot use head one's answer. A verifier can still check their guesses, but they are accepted less often.

The accounting.

Per module: the projection is 2 h^2, the block is about 12 h^2 for attention and a gated MLP, so about 14 h^2. At a hidden size of 7168 and one module that is about 720M on paper; the published figure is 14B on a 671B main model, about 2 percent, because the module's MLP inherits the expert structure of the main model. The embedding and head add nothing, because they are shared.

What you get.

  1. A denser training signal: every hidden state is supervised on D plus 1 targets, and the report shows consistent gains on reasoning, math and code evaluations.
  2. A draft at inference with 80 percent or more acceptance at depth one, for about 1.8 times generation throughput, and the training-time cost is paid back the first time the model serves.

Against a post-hoc draft.

Post-hoc hidden-state draft Baked-in modules
When trained after pretraining during pretraining
Works with existing weights yes no, retrain
Draft parameters one or two layers one block plus a projection
Acceptance 0.88 to 0.92 0.80 and above at depth one
Benefit beyond speed none denser training signal

Use the baked-in design when you control pretraining and the hidden size is at least 4096; at a 1B scale the overhead hurts more than it helps. Use the post-hoc draft when the weights already exist.

Plausible wrong answers.

  • "The extra loss replaces next-token prediction." It is added to the main loss with a small weight; the main objective stays.
  • "The module can be bolted onto a trained model with a quick fine-tune." The design is a pretraining choice; existing weights get a post-hoc draft instead.

Follow-ups an interviewer may ask.

  • (level 3) Why share the embedding and the output head with the main model? Expected: no extra parameters, and the module predicts in the same vocabulary space as the backbone.
  • (level 3) Why is the published parameter overhead larger than the 14 h^2 estimate? Expected: the module's MLP has the same expert structure as the main model, which multiplies its parameters.
  • (level 4) With two modules, what does the second one take as input? Expected: the first module's hidden state and the embedding of the token two ahead, to predict the token three ahead.
  • (level 4) A team wants to add this to an existing dense model by fine-tuning a new head. Your answer? Expected: the module is not trained and the backbone was not shaped by the extra loss; the lesson's position is that it needs a pretraining run, and a post-hoc draft is the right tool for existing weights.
