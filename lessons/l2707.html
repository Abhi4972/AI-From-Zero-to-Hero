Why this came about

As machine learning moved into hiring, lending, policing and healthcare in the 2010s, its failures became public: a recruiting model that downgraded CVs mentioning women's organisations (reported in 2018), commercial face analysis that was far less accurate for darker-skinned women (the Gender Shades study, 2018), and risk scores whose errors fell unevenly across groups. Generative AI added new problems: convincing misinformation, leaked personal data, prompt injectionlater · 15.24, and questions about the text and images models were trained on. Governments responded with rules (the EU AI Actlater · 15.26, adopted in 2024 with obligations phasing in over the following years) and frameworks (such as the US NIST AI Risk Management Framework, 2023). Responsible practice is now part of normal engineering, like security and testing.

In plain words first
The model is not the whole system

A model is a component. Whether it treats people fairly, keeps their data safe and stays under control depends mostly on the system around it: what data goes in, what it is allowed to do, who checks its outputs, and what happens when something goes wrong. Responsible AI is the habit of asking, before and after launch: who could this hurt, how would we know, and what would we do?

Step 1 · Measuring fairness

Suppose a model scores job applicants and the top scorers are invited to interview. Here are 1,000 simulated applicants from two groups. Half of each group is genuinely qualified, but the model's scores for group B run slightly lower, as happens when the training data or features carry historical patterns (Lesson 5.33 showed how such associations get into embeddings):

import random

rng = random.Random(0)
applicants = []
for i in range(1000):
    group = "A" if i % 2 == 0 else "B"
    qualified = rng.random() < 0.5
    score = (0.65 if qualified else 0.35) + rng.gauss(0, 0.12) - (0.08 if group == "B" else 0)
    applicants.append((group, qualified, score))

THRESHOLD = 0.5
for g in ["A", "B"]:
    members = [a for a in applicants if a[0] == g]
    qualified = [a for a in members if a[1]]
    selected = [a for a in members if a[2] >= THRESHOLD]
    caught = [a for a in qualified if a[2] >= THRESHOLD]
    print(f"group {g}: {len(qualified) / len(members):.0%} qualified, "
          f"{len(selected) / len(members):.0%} invited, "
          f"{len(caught) / len(qualified):.0%} of qualified people invited")
What you should see
group A: 49% qualified, 51% invited, 90% of qualified people invited
group B: 50% qualified, 36% invited, 72% of qualified people invited
Reading this output
  • Both groups are equally qualified (about 49% and 50%), yet group A is invited 51% of the time and group B only 36%. The selection rate differs.
  • Among qualified people, 90% of group A are invited but only 72% of group B. This is a gap in recall (Lesson 2.25), also called the true positive rate: qualified people in group B are missed much more often.
  • Overall accuracy could look fine and hide all of this. Fairness problems only show up when you break results down by group.
  • There are several definitions of fairness (equal selection rates, equal true positive rates, equal precision), and when groups differ in reality they cannot all be satisfied at once. Choosing which matters is a decision for the organisation, with legal advice in regulated areas such as hiring and lending, not something the model can decide.

Generative models need the same habit: test prompts that differ only in a name, gender, dialect or language, and compare the outputs (quality, tone, refusals). Lesson 15.26 covers such evaluations.

Step 2 · Privacy: keep personal data out of places it should not be

Text sent to a hosted model, written to logs or used for training can contain names, emails, phone numbers and payment details. A common first defence is to redact obvious personal data before the text leaves your system or is stored:

import re

def luhn_valid(number):
    """Card numbers pass the Luhn checksum; random digit strings usually do not."""
    digits = [int(d) for d in number if d.isdigit()][::-1]
    total = sum(d if i % 2 == 0 else (d * 2 - 9 if d * 2 > 9 else d * 2) for i, d in enumerate(digits))
    return total % 10 == 0

def redact(text):
    text = re.sub(r"[\w.+-]+@[\w-]+\.[\w.]+", "[EMAIL]", text)
    text = re.sub(r"(?:\+91[\s-]?)?\b[6-9]\d{4}[\s-]?\d{5}\b", "[PHONE]", text)       # Indian mobile numbers
    def card(m):
        return "[CARD]" if luhn_valid(m.group(0)) else m.group(0)
    text = re.sub(r"\b\d(?:[ -]?\d){12,18}\b", card, text)                         # 13 to 19 digits
    return text

ticket = ("Hi, I'm Asha (asha.k@example.com, +91 98765 43210). I paid with card 4111 1111 1111 1111 "
          "for order SK-48213, tracking number 1234 5678 9012 3456.")
print(redact(ticket))
What you should see
Hi, I'm Asha ([EMAIL], [PHONE]). I paid with card [CARD] for order SK-48213, tracking number 1234 5678 9012 3456.
Reading this output
  • The email, phone number and card number are replaced; the order number and the tracking number survive. The tracking number has the right length for a card but fails the Luhn checksum, so it is kept: checksums cut down false alarms.
  • The name "Asha" is not redacted. Names, addresses and free-text details are much harder to catch with rules; production systems add named-entity recognition models (Lesson 5.30's token labelling) or dedicated PII services, and still treat redaction as one layer among several.
  • Better than redacting is not collecting: send a model only the fields it needs, keep logs for a limited time, and check what your provider does with your data (retention, training use, region).
Go deeper (optional)
Privacy techniques you will hear named

Redaction and data minimisation cover most day-to-day needs. Four more techniques come up when models are trained on sensitive data:

  • Differential privacy: add carefully measured noise during training (or to query results) so that the output would be almost the same whether or not any one person's record was included. It gives a mathematical privacy guarantee at some cost in accuracy.
  • Federated learning: train on data where it lives (phones, hospitals, branches) and send only weight updates to a central server, never the raw data. Usually combined with differential privacy, because updates can leak too.
  • Synthetic data: generate artificial records with the statistical shape of the real ones, for testing and sometimes training. It is only as private as the generator: a model that memorised real records can reproduce them.
  • Machine unlearning: removing the influence of specific data from a trained model without retraining from scratch. It matters for deletion requests and is still an open research problem; the reliable approach today is to keep personal data out of training sets, or to retrain.

A related infrastructure idea is confidential computing: running the model inside hardware-protected memory so that even the cloud operator cannot read the data in use.

Step 3 · Security and control

Lesson 10.38 showed that any text a model reads can try to instruct it. The defences that work are mostly outside the model:

Principle In practice
Least privilege an assistant that answers questions has no tool that can issue refunds or delete data
Human approval for consequential actions payments, sending emails to customers, changing records go to a person first (Lesson 14.148)
Separate trusted and untrusted text mark retrieved documents and user uploads as data, never as instructions (Lesson 15.25)
Validate outputs check structured outputslater · 11.21 against schemas (Lesson 11.21); check generated code and queries before running them
Log and monitor keep records of inputs, outputs and tool callslater · 14.56, with personal data redacted, so problems can be found and investigated (Lesson 14.145)

Step 4 · Other responsibilities

  • Honesty with users: tell people when they are talking to an AI or reading AI-generated content, and make it easy to reach a person.
  • Intellectual property: check the licences of models and datasets you use, and your provider's terms on the outputs. Some open-weight licences restrict commercial use or very large deployments.
  • Energy and cost: training and serving large models uses significant electricity. A training run of 500,000 GPU-hours at about 0.7 kW per GPU uses roughly 350 MWh before cooling overheads. For everyday use, the most effective step is right-sizing: do not use a frontier modellater · 10.43 where a small one passes your tests (Lesson 10.39).
  • Over-reliance: people tend to trust fluent answers. Show sources, signal uncertainty, and design workflows where a human stays responsible for important decisions.

Step 5 · A checklist before launch

The ideas in this lesson, as questions to answer before a system meets real users. It is written as data so that a team can keep it in the repository, record the answers next to each question, and refuse to launch while any answer is missing.

checklist = {
    "purpose": "Is the use case written down, including what the system must never do?",
    "evaluation": "Has it been tested on realistic examples, including hard and adversarial ones?",
    "fairness": "Are results broken down by relevant groups, languages and user types?",
    "privacy": "Is personal data minimised, redacted in logs, and handled under the provider's terms?",
    "security": "Do tools follow least privilege, with approval for consequential actions?",
    "transparency": "Do users know they are dealing with AI, and can they reach a person?",
    "monitoring": "Are outputs and incidents monitored, with an owner and a way to switch it off?",
}
for key, question in checklist.items():
    print(f"[ ] {key:<13} {question}")

The same idea as a formula
  • selection rate for group g: P(selected | group = g); demographic parity asks these to be equal
  • true positive rate for group g: P(selected | qualified, group = g); equal opportunitylater · 15.26 asks these to be equal
  • disparate impact ratio: selection rate of the lower group ÷ selection rate of the higher group (a common rule of thumb flags ratios below 0.8)
Check your mental model
  • ✗ "If we remove the group column from the data, the model cannot be biased."
    ✓ Other features (postcode, school, wording) can carry the same information. Measure outcomes by group to find out.
  • ✗ "Redacting emails and phone numbers makes text anonymous."
    ✓ Names, addresses and details in free text can still identify people. Redaction is one layer; collecting less is better.
  • ✗ "Responsible AI is the model provider's job."
    ✓ Providers make models safer, but most risks depend on how you deploy them: your data, your tools, your users.

Exercises

Predict before you run

In Step 1, what happens to the gap between groups if you lower THRESHOLD to 0.4? Will both groups' invitation rates rise, and will the gap close? (Solution P1.)

Make it your own

Add a rule to redact for twelve-digit numbers written in groups of four (for example "1234 5678 9012"), replacing them with "[ID]". Test that order numbers like "SK-48213" and the card number still behave as before. (Solution M1.)

Practice
Apply it

Compute the disparate impact ratio for Step 1's results (selection rate of B ÷ selection rate of A). Is it below the common 0.8 rule of thumb? (Solution X1.)

Solutions

SolutionP1 · A lower threshold

Both groups' invitation rates rise (group A to 66%, group B to 51%), but the gap stays at about 15 percentage points: the scores themselves are shifted, so moving one threshold for everyone moves both groups together. The ratio between the rates improves (from 0.71 to 0.78) only because both are higher. Moving one threshold for everyone trades more invitations for more unqualified invitations; fixing the cause (the features or data that shift group B's scores) is the better path. Some organisations use group-specific thresholds, which raises its own legal and ethical questions.

SolutionM1 · Another identifier

For example, add text = re.sub(r"\b\d{4} \d{4} \d{4}\b", "[ID]", text) after the card rule, so that 16-digit card numbers are handled first. Test with several strings: each new rule can catch things it should not, so keep a small set of test sentences and check them whenever the rules change.

SolutionX1 · Disparate impact

0.36 ÷ 0.51 ≈ 0.71, below 0.8, so this screening model would be flagged for review under that rule of thumb. The ratio is a warning sign, not a verdict; what to do about it is a legal and organisational question.

Recap
  • Risks fall on people (bias, privacy, over-reliance), information (falsehoods, misinformation), security (injection, leakage, misuse) and organisations and society (IP, energy, accountability).
  • Fairness problems only appear when results are broken down by group; selection rates and true positive rates can differ even when groups are equally qualified.
  • Redact personal data before logging or sending it on, using rules with checks such as Luhn, but collect less in the first place.
  • Least privilege, human approval, separation of trusted and untrusted text, output validation and monitoring keep systems under control.
  • A short launch checklist turns these into habits; the Safety, security and governance section goes deeper.
