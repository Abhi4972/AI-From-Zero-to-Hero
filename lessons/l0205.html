Why this came about

By 2024 most teams used more than one model provider, for cost, quality or resilience, and each API had its own shape. Writing a thin adapter per provider, and later using libraries that do it, became the standard way to keep application code independent of any one vendor.

The problem: one feature, four APIs

ShopKart runs Claude for customers, OpenAI for an internal tool, Gemini through Google Cloud for a regional team, and Bedrock because one business unit is AWS-only. Every one of them answers the same question with a different request shape, and code written against one breaks on another in quiet ways.

In plain words first
Four plugs, one adapter

Every provider's API does the same jobs (messages in, a reply out, tool callslater · 14.56, streaming) with different field names and shapes. An adapter per provider translates each one into a single shape your code uses everywhere, like a travel adapter for different wall sockets. Then switching or adding a provider changes one adapter, not the whole application.

The calls, side by side

To compare providers without three API keys, this lesson uses small labelled stand-ins that copy each provider's call and response shape exactly. Read them as documentation: the class and method names, the names of the arguments and the path to the text in the reply are the real ones. Then the same question is sent through each, and you can see how differently the three are spelled.

from dataclasses import dataclass
from types import SimpleNamespace as NS
from fake_claude import FakeAnthropic                  # labeled stand-in for Claude (Lesson 3.1's appendix)

class FakeOpenAI:
    """A LABELED stand-in for the OpenAI Responses API: same call and response shape, answers from FakeAnthropic's rules."""
    def __init__(self):
        self.responses = self
        self._claude = FakeAnthropic()

    def create(self, model, instructions, input, max_output_tokens):
        r = self._claude.messages.create(model=model, max_tokens=max_output_tokens, system=instructions,
                                         messages=[{"role": "user", "content": input}])
        status = "incomplete" if r.stop_reason == "max_tokens" else "completed"
        return NS(output_text=r.content[0].text, status=status,
                  incomplete_details=NS(reason="max_output_tokens") if status == "incomplete" else None,
                  usage=NS(input_tokens=r.usage.input_tokens, output_tokens=r.usage.output_tokens))

SYSTEM = ("You are ShopKart's support assistant. Customers can return most items within 7 days of delivery. "
          "Damaged items can be returned within 30 days. Refunds reach UPI in 2 days and cards in 5 to 7 business days.")
print(FakeOpenAI().responses.create(model="gpt-5.5", instructions=SYSTEM, input="How long does a UPI refund take?",
                                    max_output_tokens=300).output_text)

Idea · An adapter per provider, one shape for your code

The fix is an old one: decide on a single shape that the rest of your program reads, and write one small function per provider that translates that provider's reply into it. Such a function is called an adapter. Reply below is the single shape; each adapter fills it in from a different response format.

@dataclass
class Reply:
    """One shape for every provider: what the rest of your code reads."""
    text: str
    finished: bool            # False when the reply was cut off
    input_tokens: int
    output_tokens: int
    provider: str

def ask_claude(client, model, system, question, max_tokens=300):
    r = client.messages.create(model=model, max_tokens=max_tokens, system=system,
                               messages=[{"role": "user", "content": question}])
    return Reply(r.content[0].text, r.stop_reason == "end_turn", r.usage.input_tokens, r.usage.output_tokens, "anthropic")

def ask_openai(client, model, system, question, max_tokens=300):
    r = client.responses.create(model=model, instructions=system, input=question, max_output_tokens=max_tokens)
    return Reply(r.output_text, r.status == "completed", r.usage.input_tokens, r.usage.output_tokens, "openai")

PROVIDERS = {"anthropic": (ask_claude, FakeAnthropic(), "claude-sonnet-5-5"),
             "openai": (ask_openai, FakeOpenAI(), "gpt-5.5")}

def ask(provider, question, max_tokens=300):
    fn, client, model = PROVIDERS[provider]
    return fn(client, model, SYSTEM, question, max_tokens)

for p in PROVIDERS:
    print(ask(p, "How long does a UPI refund take?"))
What you should see
Reply(text='Refunds reach UPI in 2 days and cards in 5 to 7 business days.', finished=True, input_tokens=70, output_tokens=15, provider='anthropic')
Reply(text='Refunds reach UPI in 2 days and cards in 5 to 7 business days.', finished=True, input_tokens=70, output_tokens=15, provider='openai')

The rest of the application reads Reply and never touches a provider's response. The differences that matter are handled in exactly one place each, and the most important one is the meaning of "finished":

# The same cut-off reply, reported two different ways, read one way
for p in PROVIDERS:
    r = ask(p, "How long does a UPI refund take?", max_tokens=10)
    print(f"{p:<9} finished={r.finished} text={r.text!r}")
What you should see
anthropic finished=False text='Let me'
openai    finished=False text='Let me'

Both providers cut the reply off, and they report it differently (stop_reason against status). The adapter translates both into finished=False, so the calling code can refuse to show "Let me" to a customer whichever model answered.

In production
What breaks when you switch providers

The shapes look alike, but the behavior differs: whether parallel tool calls are on by default, how tool errors are returned, default and maximum output tokens, which JSON Schema features are supported, how refusals and safety blocks are signaled, and how rate limits are reported. Teams that switch providers painlessly keep one internal message format with an adapter per provider (or a gateway, Lesson 14.136), and run the same eval suite against each provider before moving traffic.

On the platforms
Model access on each cloud
  • AWS: Amazon Bedrock (many vendors, including Anthropic, Meta, Mistral, Amazon Nova and others) via bedrock-runtime. Some models need a cross-region inference profile ID rather than a plain model ID.
  • Azure: Microsoft Foundrylater · 14.155 Models, including Azure OpenAI and a catalog of other vendors, via the OpenAI SDK pointed at your Azure endpoint, or the Foundry SDK.
  • Google Cloud: Vertex AI, with Gemini plus partner and open models in Model Garden, via google-genai with vertexai=True.
  • Databricks: Foundation Model APIs and external models behind Model Serving, with OpenAI-compatible endpoints.

Make it your own
Make it your own: a fallback provider

Write ask_with_fallback that tries providers in order and moves to the next one when a provider is down or cuts the reply off, and returns which providers it tried. (Solution M1.)

Solutions

SolutionP1 · Finished, according to the text

It reports finished=True for a two-word reply:

Reply(text='Let me', finished=True, input_tokens=70, output_tokens=1, provider='openai')

Any text at all looks like success. "Finished" has to come from the provider's own signal, status == "completed" here, or the cut-off reply reaches the customer as if it were the answer.

SolutionD1 · Reasoning blocks come first

With reasoning on, the first content block is a reasoningContent block, which has no "text" key, so content[0]["text"] fails. Never assume the first block is the answer. Collect the text blocks:

def ask_bedrock(response):
    """Read the text blocks only; reasoning and other blocks are kept out of the customer's answer."""
    msg = response["output"]["message"]
    text = "".join(b["text"] for b in msg["content"] if "text" in b)
    return Reply(text, response["stopReason"] == "end_turn",
                 response["usage"]["inputTokens"], response["usage"]["outputTokens"], "bedrock")
print(ask_bedrock(recorded))

Reply(text='UPI refunds arrive in about 2 days.', finished=True, input_tokens=71, output_tokens=40, provider='bedrock')

The same rule holds on every provider: Claude returns thinking blocks before text when extended thinking is on, and OpenAI returns reasoning items. Keep reasoning out of what the customer sees, and test adapters against responses from every model you plan to run.

SolutionM1 · A fallback provider
# Solution M1: fall back to a second provider when the first one fails or cuts off
class ProviderDown(Exception):
    pass

def ask_with_fallback(question, order=("anthropic", "openai"), max_tokens=300, down=()):
    tried = []
    for p in order:
        try:
            if p in down:
                raise ProviderDown(f"{p} returned 529 overloaded")
            r = ask(p, question, max_tokens)
            if r.finished:
                return r, tried
            tried.append(f"{p}: cut off")
        except ProviderDown as e:
            tried.append(str(e))
    raise RuntimeError(f"no provider answered: {tried}")

r, tried = ask_with_fallback("How long does a UPI refund take?", down={"anthropic"})
print(r.provider, "answered after:", tried)

openai answered after: ['anthropic returned 529 overloaded']

A fallback is only safe if every provider in the list passes your eval suite, because the customer will get whichever answers. Gateways do the same with health checks and budgets (Lesson 14.136).

Check your understanding

Explain the mechanismWhat is the same and what differs between the major model APIs?

Worked answer. All of them take a model ID, instructions, a conversation and an output limit, and return text, a reason the reply ended and token usage. The names and nesting differ: system against instructions against system_instruction; stop_reason against status against finish_reason against stopReason; content as blocks, items or parts. The behavior differs more than the shapes: how a cut-off or refused reply is signaled, defaults such as output limits and parallel tool calls, supported schema features, and error codes for rate limits and overload. I keep one internal reply type and one adapter per provider.

A plausible wrong answer. "They are all OpenAI-compatible now, so there is no difference." Many providers offer an OpenAI-compatible endpoint, but features, defaults and error behavior still differ, and those differences are where bugs live.

Follow-ups. Which differences would you expose in your internal reply type, and which would you hide?

Debug a failureAfter switching to a new model, a small share of customers see half-finished answers. What happened?

Worked answer. The new model, or its provider, ends replies differently. Either its outputs are longer and hit the output limit more often, or the code that checks "finished" reads a field the new provider does not set the same way. Check the stop or finish reason on the affected runs, confirm the adapter maps every value correctly, raise the output limit if needed, and treat any unknown value as "not finished". Add cut-off cases to the eval suite for every provider.

A plausible wrong answer. "The new model is worse at finishing sentences." The model stopped where it was told to; the code did not notice.

Follow-ups. How would you catch this before switching traffic?

Defend a designShould a team standardize on one provider, or design for several?

Worked answer. Design the code for several even if you run one: a neutral internal format and one adapter per provider cost little and make the eventual switch, or a fallback during an outage, a configuration change. Standardize operationally on as few as possible, because each provider means its own evals, contracts, data-processing terms, quotas and monitoring. The real decision is driven by data residency, which models win on your eval set, price, and which cloud contracts already exist.

A plausible wrong answer. "Always multi-provider for resilience." Resilience only helps if every provider in the rotation has passed the same evals; otherwise failover silently changes quality.

Follow-ups. What would you put in an eval suite that gates a provider switch?
