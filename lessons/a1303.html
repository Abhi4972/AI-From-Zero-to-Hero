In plain words first
The idea in one line

Three independent weather lookups serialized is three round trips. Run them in parallel and total time collapses to the slowest single call. Every frontier provider now emits multiple tool calls in a single turn. The payoff is real; the plumbing is subtle. This lesson walks both halves: the parallel fan-out and the streamed-argument reassembly, with emphasis on the id-correlation trap.

The problem

In plain words first

"What's the weather in Bengaluru, Tokyo and Zurich?" needs three tool calls. If the model asks for them one at a time, the program waits for each answer before the model asks for the next. Modern models can instead ask for all three in one turn (parallel tool calls), and the program runs them at the same time, so the wait is the slowest call, not the sum. Two things then need care. Every result must carry the id of the call it answers, because results come back in any order. And when the model's output streams in, each call's arguments arrive in small pieces that must be put back together before they can be parsed. This lesson streams a real 0.5B model that asks for three calls in one turn, runs each call as soon as it is complete, and reassembles interleaved argument pieces from OpenAI-style and Anthropic-style streams. No model is trained.

Without parallel calls, an agent answering "what is the weather in Bengaluru, Tokyo, and Zurich" does this:

user -> LLM
LLM -> call get_weather(Bengaluru)
host -> run executor, reply with result
LLM -> call get_weather(Tokyo)
host -> run executor, reply with result
LLM -> call get_weather(Zurich)
host -> run executor, reply with result
LLM -> final text answer

Three LLM round trips, each of which also pays the executor latency. Roughly 4x the ideal wall-clock time.

With parallel calls:

user -> LLM
LLM -> call get_weather(Bengaluru); call get_weather(Tokyo); call get_weather(Zurich)
host -> run all three executors concurrently, reply with three results
LLM -> final text answer

One LLM round trip. Executor time is the maximum of the three, not the sum. How much this saves depends on how many calls fan out and how slow they are; with several slow tools, it is most of the wait.

The price is correlation complexity. When the three calls complete out of order, your results must carry the matching tool_call_id so the model can line them up. When results stream, you must assemble partial argument fragments into complete JSON before executing. Without ids, two parallel calls to the same tool can only be told apart by their order, which is fragile.

Idea 1 · Enabling parallel

  • OpenAI. parallel_tool_calls: true on by default. Set false to force serial.
  • Anthropic. Parallel by default. Set disable_parallel_tool_use: true (inside tool_choice) for at most one call per turn.
  • Gemini. Always parallel-capable; tool_config.function_calling_config.mode = "AUTO" lets the model decide.

Disable parallel when tools have ordering dependencies (create_file then write_file), when one call's output informs another's input, or when the rate limiter cannot handle fan-out.

Idea 2 · Id correlation

Every call the model emits has an id. Every result the host returns must include the same id. Without this, results are ambiguous.

  • OpenAI. tool_call_id on each tool-role message.
  • Anthropic. tool_use_id on each tool_result block.
  • Gemini. id on each functionResponse, matching the id of its functionCall. Open models served without ids (Qwen's chat template, for example) match results to calls by order, which is exactly the fragility ids remove.

Idea 3 · Running calls concurrently

The host runs each call's executor on its own thread, coroutine, or remote worker. The simplest harness uses a thread pool; production uses asyncio with asyncio.gather or structured concurrency. Order of completion is unpredictable — the id is the identifier.

One common bug: reply with results in call-list order instead of completion order. This usually works because the model only cares about tool_call_id, but if a result is dropped or duplicated, a reply list that is reordered away from the order the results arrived in makes the gap harder to find in logs. Prefer to reply in completion order with explicit ids.

Idea 4 · Streaming tool calls

When the model streams, arguments arrive in pieces. Three separate streams of chunks for three parallel calls interleave on the wire. You need one accumulator per id.

Shape by provider:

  • OpenAI. Each chunk is choices[0].delta.tool_calls[i].function.arguments (partial string). The chunk carries index (position in the call list). You accumulate per-index, read id when it first appears, and parse JSON when finish_reason = "tool_calls".
  • Anthropic. Stream events are message_start, then one content_block_start per block with type tool_use (containing id, name, empty input). content_block_delta events carry input_json_delta chunks. content_block_stop closes each block.
  • Gemini. Each function call normally arrives whole within the stream. Streaming one call's arguments in pieces (stream_function_call_arguments, returned in partial_args) is a Vertex AI option that the Gemini API does not support.

Idea 5 · Partial JSON and the parse-early trap

You cannot parse arguments until it is complete. Partial JSON such as {"city": "Beng is not valid and will raise. The correct gate is the provider's end-of-call signal: OpenAI's finish_reason = "tool_calls", Anthropic's content_block_stop, or Gemini's stream-end event. Only then attempt json.loads. A more robust approach uses an incremental JSON parser that yields events as structure completes; OpenAI's streaming guide recommends this for UX that shows a live "thinking" indicator. Brace-counting is unreliable as a completeness test (braces inside quoted strings or escaped content cause false positives) and should only be used as an informal debug heuristic.

Idea 6 · Out-of-order completion

call_A: fast API, returns first
call_B: slow API, returns second
call_C: median API, returns third

The host reply must still cite the ids:

[{role: "tool", tool_call_id: "call_A", content: ...},
 {role: "tool", tool_call_id: "call_B", content: ...},
 {role: "tool", tool_call_id: "call_C", content: ...}]

Order in the reply does not matter for correctness on OpenAI or Anthropic. Gemini accepts any order so long as ids match.

Idea 7 · Benchmark: sequential vs parallel

The harness in code/main.py simulates three executors with 400, 600, and 800 ms latency. Sequential runs it in 1800 ms total. Parallel runs it in max(400, 600, 800) = 800 ms. The difference is constant, not proportional, so the savings grow with tool count.

Real-world caveat: parallel calls stress downstream APIs. A 10-way fan-out to a rate-limited service will fail. Phase 13 · 17 covers gateway-level backpressure; retry semantics are planned for a future phase.

Idea 8 · Streaming fan-out wall-clock

If the model itself streams, you can start executing as soon as one call's arguments are complete, rather than waiting for all calls to finalize. This is an optimization OpenAI documents but not all SDKs expose. The harness in this lesson does it: as soon as the simulated stream yields a complete argument object, the host kicks off that call.

The same idea as a formula

Let call i have executor latency ei​, let one model turn take g to generate, and let si​ be the moment call i's arguments are complete in the stream (si​≤g).

One call per turn (no parallelism), with n calls: Tseq​≈∑i=1n​(gi​+ei​)+gfinal​.

One turn, calls run in parallel after the stream ends: Tpar​=g+maxi​ei​+gfinal​.

One turn, each call dispatched as soon as it is complete in the stream:

Tstream​=max(g,imax​(si​+ei​))+gfinal​.

Completeness test. A prefix b of an argument string is safe to parse only after the provider's end-of-call signal; json.loads(b) succeeding earlier, or braces balancing, does not prove the string is finished.

Worked example
Three cities, three ways

Executor latencies 0.4, 0.6 and 0.8 s, as in the run below. - Parallel tools after the stream: the slowest call, 0.8 s, instead of 0.4+0.6+0.8=1.8 s one after another. Saved: 1.0 s. - Dispatch on completion: in the run, the three calls complete in the stream at about 2.6, 4.7 and 6.9 s. Their results are ready at about 3.0, 5.3 and 7.7 s, so only the last call's 0.8 s extends past the stream. - One call per turn would add two more model turns, each with a prefill and a generated call: with about 2 s per call on this CPU, roughly 4 s or more, plus the tool waits. - So on a slow model, parallel calls save mostly model turns; on a fast model with slow tools, they save mostly tool time.

Check your mental model
  • ✗ "Parallel tool calls mean the model generates the calls simultaneously."
    ✓ The model writes them one after another in one turn; the host runs them at the same time.
  • ✗ "Results must go back in the order of the calls."
    ✓ Any order works when each result carries its call's id.
  • ✗ "When the braces balance, the arguments are complete."
    ✓ Braces inside strings fool that test; wait for the end-of-call signal.
  • ✗ "Parallel is always better."
    ✓ Not when one call depends on another's result, or when fan-out overwhelms a rate-limited API.

See it drawn
Parallel calls from a real model, dispatched while it streams

Qwen2.5-0.5B-Instruct streams its reply through TextIteratorStreamer. The host watches the text, and the moment a <tool_call> block closes it parses the call and submits it to a thread pool. The weather executors sleep 0.4, 0.6 and 0.8 s to stand in for real APIs. Then all results go back and the model writes the final answer. Timing depends on the machine, so the block is not run on this page; the output below was recorded from a run of exactly this code on a 2-core CPU.

import json, re, time, threading, torch
from concurrent.futures import ThreadPoolExecutor
from transformers import AutoTokenizer, AutoModelForCausalLM, TextIteratorStreamer, logging
logging.set_verbosity_error(); torch.manual_seed(0)

M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); model = AutoModelForCausalLM.from_pretrained(M).eval()
LATENCY = {"Bengaluru": 0.4, "Tokyo": 0.6, "Zurich": 0.8}       # seconds each weather API takes
TEMP = {"Bengaluru": 28, "Tokyo": 12, "Zurich": 4}
def get_weather(city, units="celsius"):
    time.sleep(LATENCY.get(city, 0.5))
    return {"city": city, "temp": TEMP.get(city, 20)}
spec = [{"type": "function", "function": {"name": "get_weather", "description": "Current temperature in one city.",
         "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}}}]
msgs = [{"role": "user", "content": "What is the weather in Bengaluru, Tokyo and Zurich?"}]
ids = tok.apply_chat_template(msgs, tools=spec, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]

# Stream the model's output; dispatch each call the moment its <tool_call> block closes.
streamer = TextIteratorStreamer(tok, skip_prompt=True, skip_special_tokens=False)
threading.Thread(target=model.generate, kwargs=dict(input_ids=ids, max_new_tokens=150, do_sample=False,
                                                     streamer=streamer)).start()
pool, futures, buf, t0, n_chunks = ThreadPoolExecutor(8), {}, "", time.time(), 0
for piece in streamer:
    buf += piece; n_chunks += 1
    while (m := re.search(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", buf, re.S)):
        call = json.loads(m.group(1)); buf = buf[m.end():]
        cid = f"call_{len(futures)}"
        futures[cid] = (call, time.time() - t0, pool.submit(get_weather, **call["arguments"]))
        print(f"{time.time() - t0:5.2f}s  {cid} complete in the stream -> dispatched {call['arguments']}")
t_stream = time.time() - t0
print(f"{t_stream:5.2f}s  stream ended ({n_chunks} text chunks)")
for cid, (call, t_disp, fut) in futures.items():
    res = fut.result()
    print(f"{time.time() - t0:5.2f}s  {cid} result {res}  (dispatched at {t_disp:.2f}s)")
t_par = time.time() - t0

print(f"\none turn with {len(futures)} parallel calls, overlapped with generation: {t_par:.2f}s total")
lat = [LATENCY[c[0]['arguments']['city']] for c in futures.values()]
print(f"tools run one after another after the stream: {t_stream:.2f} + {sum(lat):.1f} = {t_stream + sum(lat):.2f}s")
print(f"tools run in parallel after the stream:       {t_stream:.2f} + {max(lat):.1f} = {t_stream + max(lat):.2f}s")

# Observe: one assistant turn with all calls, then one tool message per call (any order, ids attached).
calls_text = "\n".join(f"<tool_call>\n{json.dumps(c)}\n</tool_call>" for c, _, _ in futures.values())
msgs += [{"role": "assistant", "content": calls_text}] + \
        [{"role": "tool", "content": json.dumps(f.result())} for _, _, f in futures.values()]
ids = tok.apply_chat_template(msgs, tools=spec, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
t1 = time.time()
with torch.no_grad():
    out = model.generate(ids, max_new_tokens=80, do_sample=False)
print(f"\nfinal answer after {time.time() - t1:.1f}s more: {tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)}")

Reading this output

The model asked for all three cities in one turn. Three <tool_call> blocks came out of a single generation. Each took about 2 seconds of generation on this CPU, so the calls completed in the stream at about 2.6, 4.7 and 6.9 s.

Each call started while the model was still writing. Bengaluru's call was dispatched at 2.6 s and its 0.4 s of tool time was over long before the stream ended; the same for Tokyo. Only Zurich's call, the last one written, ran after the stream: its 0.8 s is the only tool time the user waited for (7.65 s in total).

Compared with the alternatives: running the three tools one after another after the stream would have taken 8.65 s, and running them in parallel after the stream 7.65 s, the same as here because the last call was also the slowest. With a slow first call, dispatching mid-stream would win clearly.

Qwen's template has no call ids. The results went back as three tool messages in call order, and the model matched them by position, correctly this time. Provider APIs attach ids so that order stops mattering. The final answer then took another 5.9 s of generation: on a slow model, model turns dominate, which is why one turn with three calls beats three turns.

Reassembling interleaved argument pieces

Three calls' argument strings are cut into pieces and interleaved on one stream, in the exact chat.completion.chunk format of the OpenAI SDK (validated by its ChatCompletionChunk model). One accumulator per index rebuilds them. Then the same pieces show why brace counting and early json.loads are unreliable. Last, an Anthropic tool_use block streamed as start, input_json_delta pieces and stop, validated by the Anthropic SDK's event types. Instant.

import json, random
from pydantic import TypeAdapter
from openai.types.chat import ChatCompletionChunk
from anthropic.types import RawMessageStreamEvent

# Three parallel calls, their argument strings cut into small pieces and interleaved on one stream,
# exactly as OpenAI's chat.completion.chunk deltas carry them (index = position in the call list).
calls = [("call_A", '{"city": "Bengaluru"}'), ("call_B", '{"city": "Tokyo", "note": "say \\"}\\" twice"}'),
         ("call_C", '{"city": "Zurich"}')]
pieces = []
for i, (cid, args) in enumerate(calls):
    cuts = [0] + sorted(random.Random(i).sample(range(1, len(args)), 3)) + [len(args)]
    parts = [args[a:b] for a, b in zip(cuts, cuts[1:])]
    pieces.append([(i, cid if k == 0 else None, p) for k, p in enumerate(parts)])
order = []                                           # round-robin: A1 B1 C1 A2 B2 ...
while any(pieces):
    for q in pieces:
        if q: order.append(q.pop(0))
chunks = [ChatCompletionChunk.model_validate({"id": "x", "object": "chat.completion.chunk", "created": 0, "model": "m",
          "choices": [{"index": 0, "finish_reason": None, "delta": {"tool_calls": [{"index": i, "id": cid,
          "type": "function" if cid else None, "function": {"name": "get_weather" if cid else None, "arguments": p}}]}}]})
          for i, cid, p in order]
print(f"{len(chunks)} chunks on the wire, interleaved: " + " ".join(f"{c.choices[0].delta.tool_calls[0].index}"
                                                                   for c in chunks))

acc = {}                                             # one accumulator per index (the id appears only once)
for c in chunks:
    d = c.choices[0].delta.tool_calls[0]
    a = acc.setdefault(d.index, {"id": None, "args": ""})
    a["id"] = a["id"] or d.id
    a["args"] += d.function.arguments
# finish_reason "tool_calls" arrives last: only now is every argument string known to be complete.
print("\nafter finish_reason = 'tool_calls':")
for i, a in sorted(acc.items()):
    print(f"  index {i}  id {a['id']}  args {json.loads(a['args'])}")

# The parse-early trap and the brace-counting trap, on call_B's pieces.
b = ""
for _, cid, p in [x for x in order if x[0] == 1]:
    b += p
    depth = b.count("{") - b.count("}")
    try:
        json.loads(b); verdict = "valid JSON"
    except json.JSONDecodeError as e:
        verdict = f"JSONDecodeError ({e.msg})"
    print(f"\n  call_B so far: {b!r}\n    brace count says {'complete' if depth == 0 else 'incomplete'}; json.loads: {verdict}",
          end="")
print()

# Anthropic streams each tool_use block as start -> input_json_delta pieces -> stop, one block at a time.
events = [{"type": "content_block_start", "index": 1, "content_block": {"type": "tool_use", "id": "toolu_1",
           "name": "get_weather", "input": {}}}] + \
         [{"type": "content_block_delta", "index": 1, "delta": {"type": "input_json_delta", "partial_json": p}}
          for p in ('{"ci', 'ty": "Tok', 'yo"}')] + [{"type": "content_block_stop", "index": 1}]
blocks = {}
for e in (TypeAdapter(RawMessageStreamEvent).validate_python(x) for x in events):
    if e.type == "content_block_start":
        blocks[e.index] = {"id": e.content_block.id, "json": ""}
    elif e.type == "content_block_delta":
        blocks[e.index]["json"] += e.delta.partial_json
    elif e.type == "content_block_stop":
        print(f"\nAnthropic block {e.index} stopped -> {blocks[e.index]['id']} {json.loads(blocks[e.index]['json'])}")

Reading this output

The pieces arrive interleaved. The 12 chunks alternate between calls 0, 1 and 2, as parallel calls can on OpenAI's stream. The call id appears only in each call's first chunk; later chunks carry only the index. One accumulator per index, filled until finish_reason says the calls are done, rebuilds all three argument objects exactly, including the awkward "say \"}\" twice".

Brace counting is wrong in both directions. On call B's pieces, after {"city": "Tokyo", "note": "say \"}\" the braces balance, so a brace counter says "complete", but the string is unfinished and json.loads fails. On the final, complete string the counter says "incomplete", because the } inside the quoted text unbalanced it. Only the provider's end-of-call signal is reliable.

Anthropic streams one block at a time. The tool_use block opens with its id and name, its input_json_delta pieces build {"city": "Tokyo"}, and content_block_stop marks the moment it is safe to parse.

Use it: the same idea with real libraries

code/main.py has two halves. The first runs three simulated weather calls sequentially and in parallel using concurrent.futures.ThreadPoolExecutor and prints wall-clock time. The second half replays a fake streaming response — chunks of arguments for three parallel calls interleaved on one stream — and reassembles them per-id with StreamAccumulator. No LLM, no network, just the reassembly logic.

What to look at:

  • The sequential timer hits 1.8 seconds. The parallel timer hits 0.8 seconds on the same fake latencies.
  • The accumulator handles chunks arriving out of order by buffering per-id and parsing only when each call's JSON is complete.
  • The executor kicks off as soon as an id's arguments finalize, not after all streams end.

Industry practice
What's current (2024–2026)
  • Parallel calls are on by default in the OpenAI, Anthropic and Gemini APIs; each offers a switch to turn them off (parallel_tool_calls: false, disable_parallel_tool_use: true).
  • Streamed tool arguments: OpenAI sends function.arguments deltas per call index (and response.function_call_arguments.delta events in the Responses API); Anthropic sends input_json_delta events per content block; the SDKs' stream helpers reassemble them for you.
  • Async executors (asyncio.gather, task groups) are the usual way to run a fan-out; agent SDKs such as the OpenAI Agents SDK and LangGraph's ToolNode run parallel calls concurrently.
  • Open models on a laptop (Qwen2.5 and Qwen3, Llama 3.2) can emit several calls in one turn through their chat templates, as shown here; serving stacks such as vLLM and llama.cpp parse them into OpenAI-style tool_calls with ids.

Sources: Claude parallel tool use, OpenAI function calling, Anthropic streaming, Gemini function calling.

Recap
What to keep from this lesson
  • Parallel calls: one model turn, several calls, run at the same time.
  • Results can come back in any order; the id ties each to its call.
  • Streamed arguments arrive in pieces, interleaved by call: one buffer per call.
  • Parse only after the end-of-call signal; brace counting is not a test.
  • Keep dependent or rate-limited tools sequential.

---
name: parallel-call-safety-check
description: Audit a tool registry for safe parallelization. Mark each tool parallel_safe, note ordering dependencies, and flag downstream rate-limit risk.
version: 1.0.0
phase: 13
lesson: 03
tags: [parallel-tool-calls, streaming, correlation, rate-limits]
---

Given a tool registry (list of tools with names, descriptions, and executors), return an annotated copy with `parallel_safe: bool`, `ordering_deps: [tool_name]`, and `rate_limit_group: name` fields added.

Produce:

1. Per-tool classification. For each tool, decide: safe to run in parallel within the same turn (pure reads, different resources); unsafe (mutations, shared resources, external rate limits).
2. Dependency graph. Identify pairs where one tool's output should feed another's input. Cannot parallelize within a turn. Mark with `ordering_deps`.
3. Rate-limit grouping. Tools that hit the same downstream API share a group. Host should cap per-group concurrency, not per-tool.
4. Safety recommendations. For each unsafe tool, state whether to disable parallel for that turn, queue, or shard by resource.
5. Provider-specific flags. Recommend `parallel_tool_calls=false` on OpenAI or `disable_parallel_tool_use=true` on Anthropic when any unsafe tool is in the set.

Hard rejects:
- Any registry with no classification after the audit. Default-deny; unknown means unsafe.
- Any write-path tool on a shared resource marked `parallel_safe: true`. Race conditions.
- Any tool that hits a rate-limited external API without a `rate_limit_group`.

Refusal rules:
- If asked to mark all tools parallel-safe without inspection, refuse.
- If the registry includes consequential tools on the same resource (`delete_file` and `write_file` on the same path), refuse to parallelize and direct to Phase 14 · 09 for sandbox-level serialization.
- If the user argues that their tools never race, refuse and ask for the proof (tests, logs, or a formal argument). Racing happens silently in production.

Solutions

SolutionP1 · All three in one turn; only the last call's wait remains

Yes: the model wrote three <tool_call> blocks in one turn. Dispatching each as soon as it appeared hid the first two calls' tool time inside the model's own generation, so of the 1.8 s of total tool latency the user waited only for Zurich's 0.8 s, because that call came last in the stream.

On this CPU the model's generation (about 2 s per call, about 6 s for the final answer) costs far more than the tools. That is the stronger argument for parallel calls here: one model turn instead of three.

SolutionB1 · A race on the same file

Run in parallel, the two calls race. If write_file runs first, it may fail because the file does not exist yet, or create the file itself and then have create_file truncate or reject it. The outcome depends on thread timing, so it changes from run to run: the worst kind of bug to debug.

What to do:

  • Declare the dependency: mark tools that touch the same resource as not parallel-safe, and have the host run calls on the same resource in the order the model wrote them.
  • Turn off parallel calls for such agents: parallel_tool_calls: false on OpenAI, disable_parallel_tool_use: true on Anthropic, so the model issues one call, sees the result, then issues the next.
  • Design better tools: one write_file(path, text, create=True) removes the dependency altogether.
