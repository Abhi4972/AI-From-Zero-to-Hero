Why this came about

Each model provider has its own API, and switching between them meant rewriting code. LangChain, created in late 2022, began by offering a common interface to many models, which remains its most-used part. This lesson shows that interface as it stands after LangChain 1.0 (2025).

The problem: you already wrote this adapter once

In Lesson 2.5 you wrote one adapter per provider so the rest of ShopKart's code could read a single Reply shape, whichever provider answered. Every team that talks to more than one model writes that code, and then maintains it: new response fields, new streaming events, new error types. LangChain's chat model classes are that adapter, maintained by the provider integrations. This lesson shows what they return, so you can trust them instead of rewriting them.

In plain words first
One remote control for many televisions

Every model provider has its own API: different request fields, different reply shapes, different names for the same thing. A LangChain chat model is a universal remote control: you press the same buttons (invoke, stream, batch) whatever the brand, and you always get back the same kind of reply, an AIMessage with content, tool_calls, usage_metadata and response_metadata. Underneath, each provider package translates. Lesson 2.5 built that translation by hand; this lesson shows the maintained version.

Idea 1 · A chat model object, and what it returns

Create one chat model object and send it one question. The object here is ChatOpenAI, pointed at the lab rig instead of a paid service; the comment shows the one-line change for a real model. Then print the reply's type and its fields, because the reply object is what the rest of this chapter passes around.

from mockllm import start                      # the lab rig from Lesson 6.1: a scripted, OpenAI-compatible server
from langchain_openai import ChatOpenAI

BASE = start()
model = ChatOpenAI(model="mock-model", base_url=BASE, api_key="mock")   # live: ChatOpenAI(model="gpt-5.5")

reply = model.invoke("Where is my order A-1001?")
print(type(reply).__name__)
print("content:       ", reply.content)
print("finish_reason: ", reply.response_metadata["finish_reason"])
print("usage_metadata:", reply.usage_metadata)
What you should see
AIMessage
content:        I can check order status and cancel orders. Please share your order ID, like A-1002.
finish_reason:  stop
usage_metadata: {'input_tokens': 50, 'output_tokens': 20, 'total_tokens': 70, 'input_token_details': {}, 'output_token_details': {}}

invoke sent one request and returned an AIMessage, LangChain's provider-neutral reply. Compare it with Lesson 2.5's Reply:

Your Chapter 2 code The LangChain chat model
Reply.text reply.content (a string, or a list of content blocks; reply.content_blocks is always the list)
Reply.finished reply.response_metadata["finish_reason"] (the provider's own value)
Reply.input_tokens, output_tokens reply.usage_metadata, with the same keys for every provider
One adapter per provider One integration package per provider: langchain-openai, langchain-anthropic, langchain-google-genai, langchain-aws

Notice what the model did not do: it could not look up order A-1001, because it has no tools. That is Lesson 6.4.

Idea 2 · Messages are the whole conversation

A chat model is as stateless as the API under it (Lesson 2.1). You send the whole history every time, as a list of messages:

from langchain_core.messages import SystemMessage, HumanMessage, AIMessage

history = [
    SystemMessage("You are ShopKart support. Be brief."),
    HumanMessage("hi"),
    AIMessage("Hello! How can I help?"),
    HumanMessage("What can you do?"),
]
reply = model.invoke(history)
history.append(reply)                           # you keep the history; the model keeps nothing (Lesson 2.1)
for m in history:
    print(f"{m.type:6} | {m.content[:50]}")
What you should see
system | You are ShopKart support. Be brief.
human  | hi
ai     | Hello! How can I help?
human  | What can you do?
ai     | I can check order status and cancel orders. Please

Four message types cover almost everything: SystemMessage (instructions), HumanMessage (the user), AIMessage (the model, including any tool calls it asked for) and ToolMessage (a tool's result, matched to a call by tool_call_id, Lesson 6.4). LangChain translates them into each provider's format: on Anthropic the system message moves to the top-level system parameter; on OpenAI it stays in the list.

You will see two shorthand forms in examples and docs. Both turn into the same messages:

same = model.invoke([("system", "You are ShopKart support. Be brief."),
                     {"role": "user", "content": "What can you do?"}])
print(same.content == reply.content)
What you should see
True

Idea 3 · One string picks the provider

init_chat_model builds the right class from a "provider:model" string, so switching providers is a configuration change:

from langchain.chat_models import init_chat_model

chat = init_chat_model("openai:mock-model", base_url=BASE, api_key="mock", temperature=0, stream_usage=True)
print(type(chat).__name__, "|", chat.invoke("hello").content[:30])
What you should see
ChatOpenAI | I can check order status and c

With a real key: init_chat_model("anthropic:claude-sonnet-5-5"), "openai:gpt-5.5", "google_genai:gemini-3.5-flash", "bedrock_converse:<model or inference-profile ID>", or "openai:<model>" with a base_url for vLLMlater · 11.8, Ollama or your gateway (Lesson 12.4). Keyword arguments such as temperature and max_tokens are passed to the provider class.

A chat model knows its limits: the profile

Since LangChain 1.0, a chat model built from a known model name carries a profile: data about the model, such as its context window and whether it supports tool calling and structured output. Building the object sends no request, so you can read profiles without a key that works:

import os
os.environ.setdefault("OPENAI_API_KEY", "not-used"); os.environ.setdefault("ANTHROPIC_API_KEY", "not-used")   # no request is sent

for name in ["anthropic:claude-sonnet-5-5", "openai:gpt-5.5", "openai:mock-model"]:
    p = init_chat_model(name).profile
    print(f"{name:28}", None if p is None else {k: p.get(k) for k in ("max_input_tokens", "tool_calling", "structured_output")})
try:
    init_chat_model("qwen3:4b")
except ValueError as e:
    print("qwen3:4b ->", str(e).split(".")[0])
What you should see
anthropic:claude-sonnet-5-5  {'max_input_tokens': 1000000, 'tool_calling': True, 'structured_output': True}
openai:gpt-5.5               {'max_input_tokens': 1050000, 'tool_calling': True, 'structured_output': True}
openai:mock-model            None
qwen3:4b -> Unable to infer model provider for model='qwen3:4b'

LangChain itself reads profiles: summarisation middleware uses max_input_tokens to decide when a thread is too long (Lesson 6.6), and structured output uses structured_output to choose how to ask for an object (Lesson 6.4). A model the profile data does not know, like the lab rig, has None; pass profile={...} to init_chat_model to supply your own. Two more rules from the last example: only the text before the first colon names the provider, so an Ollama model is "ollama:qwen3:4b"; and a bare name works only when it starts with a prefix LangChain recognises, such as gpt- or claude, otherwise it fails before any request is sent.

Idea 4 · invoke, stream and batch

Every chat model, and every chain built from one (Lesson 6.3), has the same three ways to call it, plus async versions (ainvoke, astream, abatch).

Stream returns AIMessageChunk objects as tokens arrive. Chunks add up with +, which merges text, tool-call fragments and usage correctly, so you never have to stitch the pieces together by hand:

chunks = list(chat.stream("hello"))
print(len(chunks), "chunks:", [c.content for c in chunks[:6]])

full = chunks[0]
for c in chunks[1:]:
    full = full + c                             # chunks add up into one message
print(type(full).__name__, "|", full.content[:42], "|", full.usage_metadata)
What you should see
19 chunks: ['', 'I ', 'can ', 'check ', 'order ', 'status ']
AIMessageChunk | I can check order status and cancel orders | {'input_tokens': 50, 'output_tokens': 20, 'total_tokens': 70, 'input_token_details': {}, 'output_token_details': {}}

The first chunk is empty: it carries the role, as the first server-sent event does in Lesson 2.3. Batch sends many inputs in parallel threads; max_concurrency caps how many requests are in flight, which matters for rate limits. A usage callback totals tokens across every call inside the with block:

from langchain_core.callbacks import get_usage_metadata_callback

with get_usage_metadata_callback() as usage:
    answers = chat.batch(["Where is A-1001?", "Where is A-1002?", "hello"], config={"max_concurrency": 2})
for a in answers:
    print(a.response_metadata["finish_reason"], "|", a.content[:40] or a.tool_calls)
print({k: v for k, v in sorted(usage.usage_metadata["mock-model"].items()) if "details" not in k})   # totals across the three calls
What you should see
stop | I can check order status and cancel orde
stop | I can check order status and cancel orde
stop | I can check order status and cancel orde
{'input_tokens': 150, 'output_tokens': 60, 'total_tokens': 210}

When the provider is down

Providers have outages, rate limits and timeouts. Here is a model pointed at a port where nothing is listening:

import openai

down = ChatOpenAI(model="mock-model", base_url="http://127.0.0.1:9/v1", api_key="mock", max_retries=0, timeout=2)
try:
    down.invoke("hello")
except openai.APIConnectionError as e:
    print(type(e).__name__, "|", e)
What you should see
OpenAIConnectionError | Connection error.

max_retries=0 turned off the SDK's own retries (two by default) so the failure shows at once. LangChain wraps the provider's error in a subclass of it (OpenAIConnectionError is an openai.APIConnectionError), so code that catches the SDK's exceptions keeps working. A fallback tries the next model when one raises:

safe = down.with_fallbacks([chat])
print(safe.invoke("hello").content[:42])
What you should see
I can check order status and cancel orders

with_fallbacks works on any runnable, including whole chains. The production caveat from Lesson 2.5 applies: a fallback model is a different model, so it must pass the same evals, and you should log which one answered. Gateways (Lesson 12.4) usually own this policy for every app; in-code fallbacks suit a single app with no gateway.

Check your mental model
  • ✗ "A chat model object remembers the conversation."
    ✓ It is stateless, like the API underneath. You send the whole message list every call.
  • ✗ "usage_metadata keys differ by provider."
    ✓ They are normalized: input_tokens, output_tokens, total_tokens everywhere. response_metadata keeps the provider's own fields.
  • ✗ "stream gives a different answer from invoke."
    ✓ Same request, same answer; stream hands it over in pieces as it is written.

What the library replaces

You wrote in Chapter 2 LangChain gives you
A Reply dataclass and one adapter per provider (Lesson 2.5) AIMessage with content_blocks, response_metadata and usage_metadata
Converting history between provider formats Message classes translated by each integration
Joining streamed text pieces AIMessageChunk addition
A thread pool for many calls batch with max_concurrency
ask_with_fallback (Lesson 2.5) with_fallbacks, or ModelFallbackMiddleware on agents (Lesson 6.6)

What it does not replace: deciding what "finished" means for your product, checking finish_reason before you show a reply, and evaluating every model you might fall back to.

Exercises

Predict before you run

chat.batch above sent three questions, two of them about orders. Why did all three get the same generic reply, and what one change would make the order questions get real answers? (Solution P1.)

Break it on purpose

Set max_retries=0, timeout=2 on a model whose base_url points at a port with nothing listening, call it inside with_fallbacks([chat]), and then once more without the fallback. Which exception class do you get, and is it caught by except openai.APIConnectionError? (Solution B1.)

Debugging exercise
Debugging exercise: streamed calls cost nothing?

ShopKart's cost dashboard shows zero tokens for every streamed reply since the team moved behind its own gateway. Non-streamed calls are fine. This is the code that records usage:

gateway = ChatOpenAI(model="mock-model", base_url=BASE, api_key="mock")    # the team's gateway URL in real life

text = "".join(c.content for c in gateway.stream("hello"))
total = None
for c in gateway.stream("hello"):
    total = c if total is None else total + c
print(repr(text[:30]), "| usage:", total.usage_metadata)

What it printed:

'I can check order status and c' | usage: None

Find the cause and fix it. (Solution D1.)

Make it your own

Write ask_first_available(question, models) that takes a list of (name, model) pairs, returns the first answer, and also returns the names it tried, so the caller can log which model answered. (Solution M1.)

Solutions

SolutionP1 · No tools, no lookups

The model has no tools, so it cannot look anything up; the lab rig's rule for a question with no tools is the generic reply, and a real model would answer that it cannot see order systems. Bind a tool (chat.bind_tools([get_order_status]), Lesson 6.4) and the order questions come back as tool calls instead of text.

SolutionB1 · The wrapped error

Without the fallback you get OpenAIConnectionError, which is LangChain's subclass of openai.APIConnectionError, so except openai.APIConnectionError catches it. With the fallback, the error is caught inside with_fallbacks and the backup model answers. Fallbacks catch every exception by default; pass exceptions_to_handle=(...) to fall back only on errors another provider can fix, such as connection errors and rate limits, and not on invalid requests.

SolutionD1 · Usage in streams is opt-in behind a custom endpoint

ChatOpenAI only asks for usage in streams (stream_options.include_usage) by default when it talks to OpenAI's own endpoint. With a custom base_url, many OpenAI-compatible servers reject that option, so the default is off and the merged chunk has no usage_metadata. Turn it on explicitly if your gateway supports it:

gateway = ChatOpenAI(model="mock-model", base_url=BASE, api_key="mock", stream_usage=True)
total = None
for c in gateway.stream("hello"):
    total = c if total is None else total + c
print(total.usage_metadata)

{'input_tokens': 50, 'output_tokens': 20, 'total_tokens': 70, 'input_token_details': {}, 'output_token_details': {}}

Also make the dashboard alert on missing usage instead of recording zero: silent zeros hid this bug.

SolutionM1 · Try models in order
def ask_first_available(question, models):
    """Try each (name, model) in order; return the answer and which model gave it."""
    tried = []
    for name, m in models:
        tried.append(name)
        try:
            return m.invoke(question).content, tried
        except openai.APIConnectionError:
            continue
    raise RuntimeError(f"every model failed: {tried}")

print(ask_first_available("hello", [("primary", down), ("backup", chat)]))

('I can check order status and cancel orders. Please share your order ID, like A-1002.', ['primary', 'backup'])

Catch only the errors that another model can fix. A BadRequestError (an invalid request) will fail on every provider, so retrying it elsewhere only hides the bug.

Check your understanding

Explain the mechanismWhat does a LangChain chat model give you over calling a provider's SDK directly?

Worked answer. One interface across providers: the same message types in, an AIMessage out with standard usage_metadata and content blocks, and the same invoke, stream and batch methods, plus fallbacks, rate limiters and callbacks for tracing. That makes switching providers a configuration change and lets the rest of LangChain and LangGraphlater · 6.10 work with any model. The cost is a layer between you and the provider: a brand-new provider feature may arrive in the SDK before the integration supports it, and debugging means knowing what the integration sent.

A plausible wrong answer. "It makes every model behave the same." It makes the interface the same. Models still differ in tool use, output limits and quality, so you still evaluate each one.

Follow-ups. How would you use a provider feature that the integration does not support yet?

Debug a failureToken usage is missing for some calls in your traces. Where do you look?

Worked answer. First, which calls: if only streamed calls are missing, the stream probably did not request usage. With ChatOpenAI behind a custom base_url, stream_usage is off by default and has to be set. Second, how the code reads usage: joining chunk text loses metadata, so merge chunks with + or use a usage callback. Third, whether the endpoint returns usage at all; some local servers do not. I would also make the pipeline fail loudly on missing usage instead of recording zero.

A plausible wrong answer. "The provider is not billing streamed calls." They are billed; you just did not ask for the numbers.

Follow-ups. How would you total cost per user across many calls?

Defend a designShould a new project use LangChain chat models or the provider SDK directly?

Worked answer. If the project will use LangChain or LangGraph for agents, or needs several providers, the chat model classes are the natural boundary, and I keep provider-specific features behind them where possible. If it is a single-provider service with a few calls and no framework, the SDK directly is simpler and gets new features first. Either way I keep one internal place where models are created, so the choice can change later.

A plausible wrong answer. "Always use the SDK; frameworks are bloat." For a multi-provider agent you would end up rebuilding the same adapters, fallbacks and tracing hooks.

Follow-ups. What would you log for every model call, whichever you choose?
