Terms you'll hear
Term What people say What it actually means
API Gateway "The frontend" The entry point that handles authentication, rate limiting, CORS, and request routing before any LLM logic runs
Prompt Router "Template selector" Logic that picks the right prompt template based on request type, A/B experiment assignment, and user context

Shadow Mode "Dark launch" Running a new prompt or model on real traffic but only logging results, not showing them to users -- risk-free A/B testing
Health Check "Readiness probe" An endpoint that returns the status of all dependencies (cache, LLM availability, guardrails) -- used by load balancers and Kubernetes to route traffic

Idea 1 · Production Architecture

Every serious LLM application follows the same flow. The details vary. The structure does not.

The request enters through an API gateway that handles authentication and rate limiting. Input guardrails check for prompt injection and banned content before the prompt router selects the right template. A semantic cache checks if a similar question was answered recently. On a cache miss, the LLM is called with streaming enabled. Output guardrails validate the response. The eval logger records quality metrics. The cost tracker accounts for every token. The response streams back to the client.

Seven components. Each one is a lesson you already completed. The engineering is in the wiring.

Idea 3 · Streaming: Why It Matters

A 500-token answer from a hosted model takes several seconds to generate in full, longer when the model reasons first. Without streaming, the user stares at a spinner for the entire duration. With streaming, the first visible token arrives after the prompt is processed (and any reasoning is done), usually well under a second for a chat model. The total time is the same; the wait the user perceives is the time to first token. The run below measures both on a small local model.

Three protocols for streaming:

Protocol Latency Complexity When to Use
Server-Sent Events (SSE) Low Low Most LLM apps. Unidirectional, HTTP-based, works everywhere
WebSockets Low Medium Bidirectional needs: voice, real-time collaboration
Long Polling High Low Legacy clients that cannot handle SSE or WebSockets

SSE is the default choice. OpenAI, Anthropic, and Google all stream via SSE. Your server receives chunks from the LLM API and forwards them to the client as SSE events. The client uses EventSource (browser) or httpx (Python) to consume the stream.

Idea 4 · Error Handling: The Three Layers

Production LLM apps fail in three distinct ways. Each requires a different recovery strategy.

Layer 1: API failures. The LLM provider returns 429 (rate limit), 500 (server error), or times out. Solution: exponential backoff with jitter. Start at 1 second, double each retry, add random jitter to prevent thundering herd. Maximum 3 retries.

Attempt 1: immediate
Attempt 2: 1s + random(0, 0.5s)
Attempt 3: 2s + random(0, 1.0s)
Attempt 4: 4s + random(0, 2.0s)
Give up: return fallback response

Layer 2: Model failures. The model returns malformed JSON, hallucinates a function name, or produces an output that fails validation. Solution: retry with a corrected prompt. Include the error in the retry message so the model can self-correct.

Layer 3: Application failures. A downstream service is unreachable, the vector store is slow, a guardrail throws an exception. Solution: graceful degradation. If RAG context is unavailable, proceed without it. If the cache is down, bypass it. Never let a secondary system crash the primary flow.

Failure Retry? Fallback User Impact
API 429 (rate limit) Yes, with backoff Queue the request "Processing, please wait..."
API 500 (server error) Yes, 3 attempts Switch to fallback model Transparent to user
API timeout (>30s) Yes, 1 attempt Shorter prompt, smaller model Slightly lower quality
Malformed output Yes, with error context Return raw text Minor formatting issues
Guardrail block No Explain why request was blocked Clear error message
Vector store down No retry on vector store Skip RAG context Lower quality, still functional
Cache down No retry on cache Direct LLM call Higher latency, higher cost

Fallback model chain. When your primary model is unavailable, fall through a chain:

claude-sonnet-5-5 -> gpt-6.2-sol (another provider) -> claude-haiku-5-5 (smaller, faster) -> cached response -> "Service temporarily unavailable"

Each step trades quality for availability. The user always gets something.

The same idea as a formula

Latency of a streamed answer of n output tokens:

Ttotal​=TTFTTqueue​+Tprefill​​​+(n−1)ttoken​,
where prefill grows with the prompt length and ttoken​ is the time per generated token. Streaming does not change Ttotal​; it shows text from TTFT onwards.

Exponential backoff with full jitter for attempt a=0,1,2,…:

waita​∼U(0, min(c, b⋅2a)),
with base b (here 1 s) and cap c. Without jitter every client waits exactly b⋅2a, so clients that failed together retry together.

Availability of a fallback chain whose providers fail independently with probabilities f1​,f2​,…: 1−∏i​fi​.

Worked example
Two providers and a retry budget
  • Primary provider available 99.5% of the time, fallback 99.0%, failing independently: both down 0.005×0.010=0.00005, so the chain is available 99.995% of the time.
  • Retry waits without jitter for attempts 1 to 4: 1, 2, 4, 8 s; the fourth retry fires 15 s after the first failure for every client at once.
  • With full jitter each wait is random between zero and its cap, so the fourth retry lands anywhere from 0 to 15 s after the first failure, and the first retries are spread over a whole second instead of one instant.
  • A 160-token answer at 50 ms per token: 8 s in total; streamed, the first words appear after the TTFT, a fraction of a second.
Check your mental model
  • ✗ "Streaming makes generation faster."
    ✓ It makes the wait visible sooner; the last token arrives at the same time.
  • ✗ "Retrying immediately is the fastest way to recover."
    ✓ Synchronised retries hit the provider in bursts and keep it overloaded; backoff with jitter spreads them out.
  • ✗ "A fallback model is a free safety net."
    ✓ It answers differently; evaluate it on your test suite like the primary.
Predict before you run

200 clients are rate-limited at the same instant and retry with exponential backoff (1, 2, 4, 8 s). The provider accepts 30 requests per 100 ms. How many get served without jitter, and with full jitter? (Solution P1.)

Idea 5 · Observability: What to Measure

You cannot improve what you cannot see. Every production LLM app needs three pillars of observability.

Structured logging. Every request produces a JSON log entry with: request ID, user ID, prompt template name, model used, input tokens, output tokens, latency (ms), cache hit/miss, guardrail pass/fail, cost (USD), and any errors.

Tracing. A single user request touches 5-8 components. OpenTelemetry traces let you see the full journey: how long did embedding take? Was it a cache hit? How long was the LLM call? Did the guardrail add latency? Without tracing, debugging production issues is guesswork.

Metrics dashboard. The five numbers every LLM team watches:

Metric Target Why
P50 latency < 2s Median user experience
P99 latency < 10s Tail latency drives churn
Cache hit rate > 30% Direct cost savings
Guardrail block rate < 5% Too high = false positives annoying users
Cost per request < $0.01 Unit economics viability

Idea 6 · A/B Testing Prompts in Production

Your prompt is not finished when it works. It is finished when you have data proving it outperforms the alternative.

Shadow mode. Run a new prompt on 100% of traffic but only log the results -- do not show them to users. Compare quality metrics against the current prompt. No user risk, full data.

Percentage rollout. Route 10% of traffic to the new prompt. Monitor metrics. If quality holds, increase to 25%, then 50%, then 100%. If quality drops, instant rollback.

Use a deterministic hash of the user ID, not random selection. This ensures each user gets a consistent experience across requests within the same experiment.

Idea 8 · Scaling

Scale Architecture Infra
0-1K DAU Single FastAPI server, sync calls 1 VM, $50/month
1K-10K DAU Async FastAPI, semantic cache, queue 2-4 VMs + Redis, $500/month
10K-100K DAU Horizontal scaling, load balancer, async workers Kubernetes, $5K/month
100K+ DAU Multi-region, model routing, dedicated inference Custom infra, $50K+/month

Key scaling patterns:

  • Async everywhere. Never block a web server thread on an LLM call. Use asyncio and httpx.AsyncClient.
  • Queue-based processing. For non-real-time tasks (summarization, analysis), push to a queue (Redis, SQS) and process with workers. Return a job ID, let the client poll.
  • Connection pooling. Reuse HTTP connections to LLM providers. Creating a new TLS connection per request adds 100-200ms.
  • Horizontal scaling. LLM apps are I/O bound, not CPU bound. A single async server handles 100+ concurrent requests. Scale servers, not cores.

def select_prompt(template_name, user_id, variables):
    versions = PROMPT_TEMPLATES.get(template_name)
    if not versions:
        raise ValueError(f"Unknown template: {template_name}")

    version = "v1"
    for exp_name, exp in AB_EXPERIMENTS.items():
        if exp["template"] == template_name:
            bucket = int(hashlib.md5(f"{user_id}:{exp_name}".encode()).hexdigest(), 16) % 100
            if bucket < exp["traffic_pct"]:
                version = exp["variant"]
            else:
                version = exp["control"]
            break

    template = versions.get(version, versions["v1"])
    rendered = template.template.format(**variables)
    return template, rendered

Step 3 · Semantic Cache

Embedding-based cache that matches semantically similar queries. Two questions phrased differently but meaning the same thing will hit the cache.

def simple_embedding(text, dim=64):
    h = hashlib.sha256(text.lower().strip().encode()).hexdigest()
    raw = [int(h[i:i+2], 16) / 255.0 for i in range(0, min(len(h), dim * 2), 2)]
    while len(raw) < dim:
        ext = hashlib.sha256(f"{text}_{len(raw)}".encode()).hexdigest()
        raw.extend([int(ext[i:i+2], 16) / 255.0 for i in range(0, min(len(ext), (dim - len(raw)) * 2), 2)])
    raw = raw[:dim]
    norm = math.sqrt(sum(x * x for x in raw))
    return [x / norm if norm > 0 else 0.0 for x in raw]


def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(x * x for x in b))
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return dot / (norm_a * norm_b)


class SemanticCache:
    def __init__(self, similarity_threshold=0.92, max_entries=10000, ttl_seconds=3600):
        self.threshold = similarity_threshold
        self.max_entries = max_entries
        self.ttl = ttl_seconds
        self.entries = []
        self.hits = 0
        self.misses = 0

    def get(self, query):
        query_emb = simple_embedding(query)
        now = time.time()

        best_score = 0.0
        best_entry = None

        for entry in self.entries:
            if now - entry["timestamp"] > self.ttl:
                continue
            score = cosine_similarity(query_emb, entry["embedding"])
            if score > best_score:
                best_score = score
                best_entry = entry

        if best_entry and best_score >= self.threshold:
            self.hits += 1
            return {
                "response": best_entry["response"],
                "similarity": round(best_score, 4),
                "original_query": best_entry["query"],
                "cached_at": best_entry["timestamp"],
            }

        self.misses += 1
        return None

    def put(self, query, response):
        if len(self.entries) >= self.max_entries:
            self.entries.sort(key=lambda e: e["timestamp"])
            self.entries = self.entries[len(self.entries) // 4:]

        self.entries.append({
            "query": query,
            "embedding": simple_embedding(query),
            "response": response,
            "timestamp": time.time(),
        })

    def stats(self):
        total = self.hits + self.misses
        return {
            "entries": len(self.entries),
            "hits": self.hits,
            "misses": self.misses,
            "hit_rate_pct": round(self.hits / max(total, 1) * 100, 2),
        }

Step 4 · Guardrails

Input validation catches prompt injection and PII before the LLM sees it. Output validation catches unsafe content before the user sees it. Two walls. Nothing passes unchecked.

INJECTION_PATTERNS = [
    r"ignore\s+(all\s+)?previous\s+instructions",
    r"ignore\s+(all\s+)?above",
    r"you\s+are\s+now\s+DAN",
    r"system\s*:\s*override",
    r"<\s*system\s*>",
    r"jailbreak",
    r"\bpretend\s+you\s+have\s+no\s+(restrictions|rules|guidelines)\b",
]

PII_PATTERNS = {
    "ssn": r"\b\d{3}-\d{2}-\d{4}\b",
    "credit_card": r"\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b",
    "email": r"\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b",
    "phone": r"\b\d{3}[-.]?\d{3}[-.]?\d{4}\b",
}

BANNED_OUTPUT_PATTERNS = [
    r"(?i)(DROP|DELETE|TRUNCATE)\s+TABLE",
    r"(?i)rm\s+-rf\s+/",
    r"(?i)(sudo\s+)?(chmod|chown)\s+777",
    r"(?i)exec\s*\(",
    r"(?i)__import__\s*\(",
]


@dataclass
class GuardrailResult:
    passed: bool
    blocked_reason: str | None = None
    pii_detected: list = field(default_factory=list)
    modified_text: str | None = None


def check_input_guardrails(text):
    for pattern in INJECTION_PATTERNS:
        if re.search(pattern, text, re.IGNORECASE):
            return GuardrailResult(
                passed=False,
                blocked_reason=f"Potential prompt injection detected",
            )

    pii_found = []
    for pii_type, pattern in PII_PATTERNS.items():
        if re.search(pattern, text):
            pii_found.append(pii_type)

    if pii_found:
        redacted = text
        for pii_type, pattern in PII_PATTERNS.items():
            redacted = re.sub(pattern, f"[REDACTED_{pii_type.upper()}]", redacted)
        return GuardrailResult(
            passed=True,
            pii_detected=pii_found,
            modified_text=redacted,
        )

    return GuardrailResult(passed=True)


def check_output_guardrails(text):
    for pattern in BANNED_OUTPUT_PATTERNS:
        if re.search(pattern, text):
            return GuardrailResult(
                passed=False,
                blocked_reason="Response contained potentially unsafe content",
            )
    return GuardrailResult(passed=True)

async def call_llm_with_retry(prompt, model, max_retries=3):
    for attempt in range(max_retries + 1):
        try:
            failure_chance = 0.15 if attempt == 0 else 0.05
            if random.random() < failure_chance:
                raise ConnectionError(f"API error from {model.value}: 500 Internal Server Error")

            await asyncio.sleep(random.uniform(0.1, 0.3))

            if "code" in prompt.lower() or "review" in prompt.lower():
                response_text = SIMULATED_RESPONSES["code_review"]
            elif "context" in prompt.lower():
                response_text = SIMULATED_RESPONSES["rag"]
            else:
                response_text = SIMULATED_RESPONSES["general"]

            return {
                "text": response_text,
                "model": model.value,
                "input_tokens": estimate_tokens(prompt),
                "output_tokens": estimate_tokens(response_text),
            }

        except (ConnectionError, TimeoutError) as e:
            if attempt < max_retries:
                backoff = min(2 ** attempt + random.uniform(0, 1), 10)
                await asyncio.sleep(backoff)
            else:
                raise

    raise ConnectionError(f"All {max_retries} retries exhausted for {model.value}")


async def call_with_fallback(prompt, preferred_model=None):
    chain = list(FALLBACK_CHAIN)
    if preferred_model and preferred_model in chain:
        chain.remove(preferred_model)
        chain.insert(0, preferred_model)

    last_error = None
    for model in chain:
        try:
            return await call_llm_with_retry(prompt, model)
        except ConnectionError as e:
            last_error = e
            continue

    return {
        "text": "I apologize, but I am temporarily unable to process your request. Please try again in a moment.",
        "model": "fallback",
        "input_tokens": estimate_tokens(prompt),
        "output_tokens": 20,
        "error": str(last_error),
    }


async def stream_response(text):
    words = text.split()

Why retries need jitter

A simulation of 200 clients that hit a rate limit at the same moment and retry up to 4 times with exponential backoff, against a provider that accepts 30 requests per 100 ms: once with fixed waits, once with full jitter. Pure Python, instant.

import random

# 200 clients hit a rate limit at the same moment (one provider hiccup); each retries up to 4 times.
# The provider accepts at most 30 requests in any 100 ms window; the rest get another 429.
def simulate(jitter, clients=200, capacity=30, window=0.1, retries=4, seed=0):
    rng = random.Random(seed)
    pending = [(0.0, c, 0) for c in range(clients)]              # (time of next attempt, client, attempt number)
    done, failed, retry_peak, last = 0, 0, 0, 0.0
    while pending:
        pending.sort()
        t0 = pending[0][0]
        batch = [p for p in pending if p[0] < t0 + window]      # every request landing in this window
        pending = [p for p in pending if p[0] >= t0 + window]
        if t0 > 0: retry_peak = max(retry_peak, len(batch))
        rng.shuffle(batch)
        for i, (t, c, a) in enumerate(batch):
            if i < capacity:
                done += 1; last = max(last, t)
            elif a == retries:
                failed += 1
            else:
                base = 1.0 * 2 ** a                              # waits of 1, 2, 4 and 8 s
                delay = rng.uniform(0, base) if jitter else base
                pending.append((t + delay, c, a + 1))
    return done, failed, retry_peak, last

Without jitter every client waits exactly 1 s, then 2, 4 and 8 s, so the failed clients return together: 170 requests land in the same 100 ms at the first retry, the provider accepts 30, and the same thing repeats at 3 s, 7 s and 15 s. After four retries 50 clients give up, and the last success comes 15 seconds after the outage.

With full jitter each wait is random between zero and its cap, so the retries spread out: the largest burst is 24 requests, under the provider's limit, and all 200 clients are served within about a second. Same number of retries, same backoff caps; the only difference is randomness. This is why the AWS SDKs, and most provider SDKs, add jitter to their retry loops.

class ProductionLLMService:
    def __init__(self):
        self.cache = SemanticCache(similarity_threshold=0.92, ttl_seconds=3600)
        self.cost_tracker = CostTracker()
        self.request_logs = []
        self.eval_results = []

    async def handle_request(self, user_id, query, template_name="general_chat", variables=None):
        request_id = str(uuid.uuid4())[:12]
        start_time = time.time()
        variables = variables or {}
        variables["query"] = query

        input_check = check_input_guardrails(query)
        if not input_check.passed:
            return self._blocked_response(request_id, user_id, template_name, input_check, start_time)

        effective_query = input_check.modified_text or query
        if input_check.modified_text:
            variables["query"] = effective_query

        cached = self.cache.get(effective_query)
        if cached:
            self.cost_tracker.total_cache_hits += 1
            log = RequestLog(
                request_id=request_id,
                user_id=user_id,
                timestamp=datetime.now(timezone.utc).isoformat(),
                prompt_template=template_name,
                prompt_version="cached",
                model="cache",
                input_tokens=0,
                output_tokens=0,
                latency_ms=round((time.time() - start_time) * 1000, 2),
                cache_hit=True,
                guardrail_input_pass=True,
                guardrail_output_pass=True,
                cost_usd=0.0,
            )
            self.request_logs.append(log)
            self.cost_tracker.record(user_id, "cache", 0, 0, 0.0)
            return {
                "request_id": request_id,
                "response": cached["response"],
                "cache_hit": True,
                "similarity": cached["similarity"],
                "latency_ms": log.latency_ms,
                "cost_usd": 0.0,
            }

        template, rendered_prompt = select_prompt(template_name, user_id, variables)
        result = await call_with_fallback(rendered_prompt, template.model)

        output_check = check_output_guardrails(result["text"])
        if not output_check.passed:
            result["text"] = "I cannot provide that response as it was flagged by our safety system."
            result["output_tokens"] = estimate_tokens(result["text"])

        cost = calculate_cost(
            ModelName(result["model"]) if result["model"] != "fallback" else ModelName.GPT_4O_MINI,
            result["input_tokens"],
            result["output_tokens"],
        )

        latency_ms = round((time.time() - start_time) * 1000, 2)

        log = RequestLog(
            request_id=request_id,
            user_id=user_id,
            timestamp=datetime.now(timezone.utc).isoformat(),
            prompt_template=template_name,
            prompt_version=template.version,
            model=result["model"],
            input_tokens=result["input_tokens"],
            output_tokens=result["output_tokens"],
            latency_ms=latency_ms,
            cache_hit=False,
            guardrail_input_pass=True,
            guardrail_output_pass=output_check.passed,
            cost_usd=cost,
            error=result.get("error"),
        )
        self.request_logs.append(log)
        self.cost_tracker.record(user_id, result["model"], result["input_tokens"], result["output_tokens"], cost)

        self.cache.put(effective_query, result["text"])

        self._log_eval(request_id, template_name, template.version, result, latency_ms)

        return {
            "request_id": request_id,
            "response": result["text"],
            "model": result["model"],
            "cache_hit": False,
            "input_tokens": result["input_tokens"],
            "output_tokens": result["output_tokens"],
            "latency_ms": latency_ms,
            "cost_usd": cost,
            "pii_detected": input_check.pii_detected,
            "guardrail_output_pass": output_check.passed,
        }

    async def handle_streaming_request(self, user_id, query, template_name="general_chat"):
        result = await self.handle_request(user_id, query, template_name)
        if result.get("cache_hit"):
            return result

        tokens = []
        async for token in stream_response(result["response"]):
            tokens.append(token)
        result["streamed"] = True
        result["stream_tokens"] = len(tokens)
        return result

    def _blocked_response(self, request_id, user_id, template_name, guardrail_result, start_time):
        log = RequestLog(
            request_id=request_id,
            user_id=user_id,
            timestamp=datetime.now(timezone.utc).isoformat(),
            prompt_template=template_name,
            prompt_version="blocked",
            model="none",
            input_tokens=0,
            output_tokens=0,
            latency_ms=round((time.time() - start_time) * 1000, 2),
            cache_hit=False,
            guardrail_input_pass=False,
            guardrail_output_pass=True,
            cost_usd=0.0,
            error=guardrail_result.blocked_reason,
        )
        self.request_logs.append(log)
        return {
            "request_id": request_id,
            "blocked": True,
            "reason": guardrail_result.blocked_reason,
            "latency_ms": log.latency_ms,
            "cost_usd": 0.0,
        }

    def _log_eval(self, request_id, template_name, version, result, latency_ms):
        self.eval_results.append({
            "request_id": request_id,
            "template": template_name,
            "version": version,
            "model": result["model"],
            "output_length": len(result["text"]),
            "latency_ms": latency_ms,
            "timestamp": datetime.now(timezone.utc).isoformat(),
        })

    def health_check(self):
        return {
            "status": "healthy",
            "timestamp": datetime.now(timezone.utc).isoformat(),
            "cache": self.cache.stats(),
            "cost": self.cost_tracker.summary(),
            "total_requests": len(self.request_logs),
            "eval_entries": len(self.eval_results),
        }

## Quick diagnostic

If something is wrong in production, check in this order:

1. **Users complaining about errors?** Check health endpoint, then error rate in logs, then LLM provider status page
2. **Responses are slow?** Check P99 latency, then cache hit rate, then LLM response times in traces
3. **Cost spiking?** Check cost-per-request trend, then cache hit rate, then top users by cost, then look for prompt template changes that increased token count
4. **Quality dropped?** Check if a new prompt version was deployed, check if RAG retrieval accuracy changed, check if model provider changed default model version
5. **Security incident?** Check guardrail block rate (sudden drop = guardrails disabled), check request logs for unusual patterns, rotate API keys immediately

Solutions

SolutionP1 · Jitter served everyone

Without jitter, 150 of 200 are served and 50 give up: every retry wave arrives at the same instant (170 requests at the first retry against a capacity of 30), so only 30 get through per wave, and four retries are not enough. With full jitter all 200 are served, the largest retry burst is 24, and the last success comes after about one second instead of fifteen.

SolutionB1 · Timeouts shorter than the work multiply the cost

Every attempt is cut off at 2 seconds, so all four attempts (the first plus 3 retries) fail and the user waits about 8 seconds plus backoff for an error message, longer than the 6 seconds the answer needed. You typically pay for all four partial generations, since providers still bill the tokens generated before the connection closed, and the provider sees four times the load. Set timeouts from measured latency (for example the 99th percentile plus a margin), stream so slow answers still show progress, and treat a timeout as a reason to fall back to a faster model, not to repeat the same slow request.

Level 3 of 4 · about 15 minutes to answer well.

Short answer. Instrument every model call with GenAI-convention spans and ship them over OTLP to a collector. The alert chain.

Eval scores land as eval spans linked to the parent trace. A metrics exporter aggregates them, an alert rule fires when the leak score in a window crosses the threshold, and the alert manager routes warnings to chat and critical breaches to the pager.

Read the codeThis function from the production app picks the prompt version for a request. Explain what it does, why it hashes the user id together with the experiment name, and what the number 10 in the experiment config means for one user over a week. python AB_EXPERIMENTS = { "general_chat_v2_test": { "template": "general_chat", "control": "v1", "variant": "v2", "traffic_pct": 10, }, } def select_prompt(template_name, user_id, variables): versions = PROMPT_TEMPLATES.get(template_name) if not versions: raise ValueError(f"Unknown template: {template_name}") version = "v1" for exp_name, exp in AB_EXPERIMENTS.items(): if exp["template"] == template_name: bucket = int(hashlib.md5(f"{user_id}:{exp_name}".encode()).hexdigest(), 16) % 100 if bucket < exp["traffic_pct"]: version = exp["variant"] else: version = exp["control"] break template = versions.get(version, versions["v1"]) return template, template.template.format(**variables)

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The code hashes the user id plus the experiment name, takes the result modulo 100, and sends the users whose bucket falls below the traffic percentage to the variant. The hash is deterministic, so one user lands in the same arm on every request for the life of the experiment. The experiment name in the hash keeps the buckets of two experiments independent, so the users who saw the variant in one test are not the same users in the next. With a traffic percentage of 10, about a tenth of the users see the variant on every request all week, and the others never do.

Line by line.

  1. The default version is v1, so a template with no experiment always resolves.
  2. The loop finds the experiment for this template and stops at the first match. One experiment per template at a time.
  3. The bucket is a hash of user_id:exp_name, read as an integer and reduced modulo 100. That gives a value from 0 to 99.
  4. A bucket below traffic_pct gets the variant, and every other bucket gets the control.
  5. The template renders with the request variables.

Why the hash is deterministic.

The lesson is explicit: hash the user id, do not draw at random. A random draw per request would flip one user between the two prompts, so the user would see two behaviors and the per-user metrics would mix both arms. A stable arm per user also makes the exposure count a count of users, which the experiment analysis needs.

Why the experiment name is in the key.

Without it, the bucket of a user is the same in every experiment, so the same tenth of the users would be the variant group every time. Experiments would be correlated, and the effects of one would carry into the next. The experiment name acts as a salt that gives each experiment its own split.

What to watch.

  • The modulo 100 gives steps of one percent. A smaller share needs a larger modulus.
  • The demo runs 1000 synthetic user ids through the selector and prints the control and variant shares. That is a cheap sample ratio check, and it belongs in a test.
  • The break means that a second experiment on the same template never runs. The config shape makes that visible, but nothing warns you.

Plausible wrong answers.

  • "A random draw below the percentage would be simpler and the same." It assigns per request, so one user flips between arms and sees both prompts.
  • "The hash function is weak, so the assignment is broken." The hash is not a security control here. It only has to be deterministic and well spread.
  • "The percentage is the share of requests." It is the share of users, because the bucket is per user and stays fixed.

Follow-ups an interviewer may ask.

  • (level 2) Why does a user stay in the same arm across requests? Expected: the hash of the same user id and experiment name gives the same bucket every time.
  • (level 2) Two experiments are configured for the same template. What happens? Expected: the loop takes the first match and breaks, so the second experiment never assigns anyone.
  • (level 3) Why not hash the user id alone? Expected: the same users would land in the variant of every experiment, so the experiments would be correlated and carry-over effects would mix the results.
  • (level 3) How does the demo check the split, and what would you add? Expected: it runs 1000 synthetic ids through the selector and prints both shares. Add the same check on real exposure logs as a sample ratio check.

Debug a failureDuring a provider slowdown, the provider began to return rate-limit errors. Within minutes your own service ran out of memory and crashed, although your incoming traffic had not changed. Reconstruct what happened, and fix the retry policy.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The gateway retried every rate-limited call, and each waiting retry kept its connection, its buffers and its request state in memory. The retries multiplied the in-flight concurrency several times over the real traffic, and the memory went with it. Fix the policy with exponential backoff and jitter, a small fixed number of attempts, a cap on in-flight requests, and a fallback chain that fails over instead of waiting.

The chain of events.

  1. The provider returns 429 for a share of the calls.
  2. The gateway retries each one. Each retry holds a connection, a buffer and the request state while it waits.
  3. In-flight requests become the traffic multiplied by the attempts. The chaos lesson names this retry-amplified concurrency.
  4. Memory follows the in-flight count, and the service that was healthy a minute ago runs out.

The retry policy in the production application capstone.

Exponential backoff with jitter: wait about 1 second, then 2, then 4, with a random spread added to each wait, and give up after 3 retries with a fallback response. The lesson's table separates the cases:

Failure Retry Fallback
429, rate limit yes, with backoff queue the request and tell the user it is in progress
500, server error yes, 3 attempts switch to the fallback model
timeout over 30 seconds yes, 1 attempt a shorter prompt or a smaller model

The jitter matters as much as the backoff. Without it, every client retries at the same instant and the provider sees a wave on each cycle.

Bound the concurrency, not only the attempts.

Attempts bound the retries of one request. Nothing bounds how many requests wait at once. Add a cap on in-flight requests at the gateway and a retry budget as a share of traffic. When the cap is reached, fail fast into the queue or the fallback instead of holding memory.

The fallback chain.

Primary model, then a secondary model, then a cached response, then a short unavailable message. Each step trades quality for availability, and the user always gets something.

Test it before the next slowdown.

The chaos lesson's first model-specific experiment injects a provider rate-limit for a few minutes and watches the fallback. Most teams learn there that the fallback was never fully exercised.

Plausible wrong answers.

  • "Retry faster so the queue drains before memory runs out." Faster retries raise the request rate against a provider that is already limiting you.
  • "Raise the maximum retries so users never see an error." Each attempt holds memory. More attempts multiply the in-flight state.
  • "The provider caused the outage, there is nothing to fix here." The provider caused the errors. The retry policy turned them into an outage.

Follow-ups an interviewer may ask.

  • (level 3) Why does backoff alone not stop the memory growth? Expected: backoff spreads the retries in time, and each waiting retry still holds its state. The fix needs a bound on in-flight requests.
  • (level 3) What does a queue do that a retry does not? Expected: it stores the request without a connection or a worker, and it gives the user a progress message instead of a timeout.
  • (level 4) The fallback model is cheaper and weaker. Who decides that it is acceptable, and how do you watch it? Expected: the product owner names the paths that may degrade. Log the fallback rate per path, and alert when it stays high.

Where it is taught. The production app lesson gives the backoff, the retry limits and the fallback chain, and the chaos engineering lesson names the retry storm as the failure to test.

Debug a failureAn experiment assigns users evenly to control and variant. After a week the dashboard shows 47 percent of users in control and 53 percent in the variant, and the variant is ahead on the primary metric. What do you conclude, and what do you do next?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Do not read the result. A configured even split that delivers 47 to 53 over a week of traffic is a sample ratio mismatch, which means the assignment or the logging is broken and the two groups are no longer comparable. Find the cause in the assignment path, fix it, and start the experiment again.

What the check says.

An assignment hash puts each user into an arm. Over a week, the delivered split should sit very close to the configured one. When it does not, the lesson's answer is blunt: something is broken. Both experiment platform types in the lesson run this check for you, and it belongs in front of every readout.

Why the win is void.

Whatever lost users from one arm can be correlated with the outcome. If slow clients fail before they log an exposure in one arm, that arm looks faster and happier. The measured lift is then the dropout, not the variant. No correction after the fact restores the randomization.

Where to look.

  1. The assignment function. The production application capstone assigns with a deterministic hash of the user id, so that one user stays in one arm. A random draw per request, or a hash on a field that changes, breaks the split.
  2. Exposure logging. One arm may drop events, for example when the variant path logs after a call that can fail.
  3. Client errors. A variant that crashes before it logs removes its users from the count.
  4. Bots and retries. A bot or a retry loop that lands in one arm inflates it.
  5. Caches. A cache in front of the assignment can serve one arm's decision to many users.

Then.

Fix the cause, discard the data, and restart. Pre-register the mismatch check so that it blocks the readout automatically, and nobody has to argue about a winning variant.

Plausible wrong answers.

  • "Three percent is within noise." Over a week of traffic, that gap under a fair split is very unlikely, and the mismatch check exists to flag exactly this case.
  • "The variant wins by more than the gap, so ship it." The gap can be correlated with the outcome, so the lift can be the dropout itself.
  • "Drop variant users until the groups match." Removing users after the fact adds a second bias on top of the first.

Follow-ups an interviewer may ask.

  • (level 2) Why hash the user id instead of drawing an arm at random on each request? Expected: the same user lands in the same arm on every request, so the experience is consistent and the exposure count is per user.
  • (level 3) Name two causes that put more users in the variant than in control. Expected: a logging failure that drops control exposures, or a variant path that treats bots or retries differently.
  • (level 3) Can you correct the mismatch statistically and keep the result? Expected: no. The mismatch shows that the groups are not comparable, and no correction restores the randomization.

Defend a designA new version of a chat prompt looks better in a notebook. Design how it reaches users: the stages, how users are assigned, what you measure at each stage, and when it rolls back automatically.

Level 2 of 4 · about 12 minutes to answer well.

Short answer. Run it in shadow first, on all traffic, logging its answers without showing them, and compare quality metrics with the current prompt. Then route a small share of users to it, 10% in the lesson, and widen in steps to 25%, 50% and 100% while the metrics hold. Assign by a deterministic hash of the user id so each user sees one version, and roll back automatically when the new version's error rate reaches twice the old one over a window of requests.

Shadow mode.

The new prompt runs on 100% of traffic but only its logs are kept. Nobody sees its output. This gives a full comparison of latency, cost per request, guardrail block rate and quality scores against the current version, and users never see a shadow answer. Shadow calls can share the provider quota with live calls, so give them a separate quota or key; otherwise a quota limit can slow or fail live requests. It is the same first stage that the ML design lesson calls shadow deployment for a model.

Percentage rollout.

Route 10% of traffic to the new version. If quality holds, raise it to 25%, then 50%, then 100%. If quality drops, switch back at once. Both versions stay deployed and the switch is configuration, so a rollback takes minutes, which is the lesson's rule for every stage.

Deterministic assignment.

Hash the user id combined with the name of the experiment and take it modulo 100. Buckets below the traffic share get the variant, the rest get the control. A user then sees the same version across requests inside one experiment, and the assignment can be recomputed later from the log. Random assignment per request mixes versions inside one conversation and makes the comparison noisy.

What to measure.

Per prompt version: latency percentiles, user ratings where they exist, error rate, guardrail block rate and cost per request. The eval logger records the template name and version with every request, so the metrics split by version without extra plumbing.

Automatic rollback.

The lesson's exercise sets the rule: when a new version shows 2x the error rate of the previous version over 100 requests, revert automatically. The window matters; a handful of requests is noise, and waiting for thousands lets a bad prompt run too long.

A note on the business metric.

Shadow and canary protect the user. Whether the new prompt improves the outcome that matters, such as task completion, needs a randomized split with enough traffic and time, which is the A/B stage from the ML design lesson.

Plausible wrong answers.

  • "Ship to everyone and watch the dashboard." A regression then hits every user before the dashboard moves.
  • "Assign per request at random for a cleaner statistic." Users see both versions in one conversation and the logged metrics mix them.
  • "Shadow mode is enough; skip the canary." Shadow mode never shows the output to a user, so it cannot measure user reaction.

Follow-ups an interviewer may ask.

  • (level 2) Why hash the user id and not pick randomly per request? Expected: a user then gets one consistent version across a session and the assignment is reproducible from the log.
  • (level 2) What does shadow mode not tell you? Expected: how users react to the new answers; it only compares logged outputs and system metrics.
  • (level 3) The new prompt costs more per request but scores higher. Who decides? Expected: a guardrail on cost per request decides whether it can ship at all; the quality gain against the cost is then a product decision with both numbers on the table.
  • (level 3) How do you keep the control and the variant from sharing a cache entry? Expected: include the prompt version in the cache key, otherwise a hit returns the other version's answer and the comparison is corrupted.

Defend a designDesign the service behind a chat product with 10,000 daily active users who send about 5 queries each, with roughly 1,500 input tokens and 400 output tokens per query. Users must see a response start quickly, the tail must stay bounded, and the product has a unit cost target. Lay out the request path, the components, the budgets you hold each one to, and how you would scale it.

Level 3 of 4 · about 25 minutes to answer well.

Short answer. The request enters through a gateway that authenticates and rate limits per user, passes input guardrails, is matched against a semantic cache, and on a miss goes to the model with streaming, then through output guardrails, an eval logger and a cost tracker. The budgets are a median under 2s, a p99 under 10s, a cache hit rate above 30%, a guardrail block rate under 5%, and a cost per request under $0.01. At 50,000 queries a day this runs on a few async servers behind a load balancer; the servers are I/O bound, so a single async process holds a hundred or more concurrent requests and scaling means more servers, not more cores.

The path.

Gateway for authentication, rate limits of 10-50 requests a minute per user and CORS; input guardrails for injection patterns and personal data; a prompt router that picks the template and version; a semantic cache keyed by query embedding with a similarity threshold and a time to live; the model call with streaming and a fallback chain; output guardrails; an eval logger; a cost tracker; a server-sent events response. Seven components, each one a known piece; the engineering is the wiring and the budgets.

Budgets.

Metric Target Why
Median latency Under 2s The typical experience
p99 latency Under 10s The tail drives churn
Cache hit rate Above 30% Direct cost savings
Guardrail block rate Under 5% Higher means false positives
Cost per request Under $0.01 Unit economics

Streaming puts the first token inside the median budget even when the full answer takes seconds. Maximum token limits on input and output bound both the cost and the tail. Every external call has a timeout.

Load and capacity.

Traffic is 50,000 queries a day, and with the measured cache hit rate about 32,500 reach the model. Peak matters more than the average; size for the busiest minute. The servers wait on network I/O, so one async process serves 100+ concurrent requests and a box with four workers serves 400+. The lesson's scaling table puts this tier at a few async servers with a cache and a queue, for about $500 a month of infrastructure, with the model bill on top. Connection pooling to the provider avoids a new TLS handshake per request, which costs 100-200ms. Work that is not interactive, such as summarization, goes to a queue with workers and a job id the client polls.

Observability.

Every request writes one structured log line with the request id, the user, the template and version, the model, the input and output token counts, the latency, the cache result, the guardrail results and the cost. Traces across the components show where the time went. The five numbers in the table sit on one dashboard.

If the model is self-hosted.

The pipeline lesson's serving stage adds continuous batching, speculative decoding, and KV cache eviction, with quantized weights for serving and the eval gate rerun on the quantized model. The same gateway, cache and guardrails sit in front of it.

Before launch.

The deployment checklist has fifteen items; the ones people skip are per-user rate limits, maximum token limits, a health endpoint that reports dependency status, timeouts on every external call, and a load test with 100 concurrent users.

Plausible wrong answers.

  • "Scale the model servers first." The service is I/O bound at this traffic; the gateway, cache and async servers are the design, and the model is a dependency.
  • "Skip the cache; the model is the product." A third of the traffic repeats, and the cache is the largest single saving in the bill.
  • "The p99 is a vendor problem." Timeouts, maximum tokens, streaming and the fallback chain are what bound the tail on your side.

  • (level 3) A user pastes a document far longer than the context window. Where is that caught? Expected: at the maximum input token limit before the model call, with a clear error, not at the provider.
  • (level 3) Why does cost per user matter when cost per request is already under target? Expected: a few heavy users dominate the bill; per-user tracking and a daily cap move them to a cheaper model or stop them.
  • (level 4) The provider has a regional outage during the daily peak. Walk the request path. Expected: backoff and retries on the primary, fall through the chain to a second model, then cached answers for repeated queries, then an unavailable message; the cost tracker shows the fallback's price and the dashboard shows the step that answered.
  • (level 4) How do you prove the service meets its budgets before the first user? Expected: a load test at 100 concurrent users against the staging stack with the dashboard metrics as pass criteria, plus a shadow run of the prompts on logged traffic.

Explain the mechanismYou built a small web demo of a model for reviewers. Three months later a colleague asks whether it is "production". How do you tell, and what changes when the answer is yes?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. A demo serves known people in short sessions from one process. It has become a product when people outside the team use it every week, when someone asks for an uptime target or reports an outage, when users want to sign in or see history, when the weekly model cost is a budget line, or when the input is covered by a contract or a law. At that point the demo moves onto the production stack with authentication, fallback models, tracing, and cost tracking per user.

The five signals.

  • People outside your team use it every week.
  • Someone asks for an uptime target, or reports an outage.
  • Users ask to sign in, save results, or see their history.
  • The weekly model cost is a line in a budget.
  • The input includes data that a contract or a law covers.

What changes.

Property Demo Product
Users Known people, short sessions Unknown people, daily use
State None Accounts, history, saved results
Availability Best effort, one process A written target, replicas, an on-call owner
Cost control One daily usage cap Per-user quotas and billing
Observability One log record per request Traces, metrics, and alerts

What the demo already had.

A good demo already had the small versions of these controls: an input limit, a per-client rate limit, a daily cap, and a log that keeps the input length and not the text. The product stack adds real authentication at the gateway, a fallback model chain for provider failures, traces across the components, and cost accounting per request and per user. The input limit and the log privacy carry over unchanged.

Why the question matters.

The dangerous state is the middle: a demo with product traffic and demo controls. One daily cap does not stop one tenant from using the whole budget, and one process has no replica to take over when it dies.

Plausible wrong answers.

  • "It is production when it runs on a server instead of a laptop." Where it runs does not decide; who depends on it does.
  • "Add a disclaimer that it is a demo." A disclaimer does not stop traffic, cost or outages.
  • "Keep the demo and build the product separately later." The signals mean the demo already carries product risk now.

Follow-ups an interviewer may ask.

  • (level 1) Which single signal is the strongest? Expected: an outage report, because it means someone depends on the demo and expects availability.
  • (level 2) The weekly model cost appears in a budget. What control replaces the daily cap? Expected: per-user quotas and billing, so the total is attributed and limited per tenant.
  • (level 2) Regulated data starts arriving in the input. What must the log do? Expected: keep no input text and no client address, with a retention period and access control on the records.

Estimate itA chat feature expects 10,000 daily active users with 5 queries each, about 1,500 input tokens and 400 output tokens per query, at $2.50 per million input tokens and $10.00 per million output tokens. Measured cache metrics give a 35% hit rate. Walk me through the monthly estimate, and say which number you would attack first.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. The traffic is 50,000 queries a day, and a 35% cache hit rate leaves 32,500 that reach the model. Over 30 days that is $3,656 of input and $3,900 of output, about $7,556 a month, against $11,625 without the cache, so the cache saves about $4,070. Output tokens cost four times more per token, so after the hit rate the output length is the number to attack, with a maximum output tokens limit and tighter prompts.

The sheet.

Variable Value
Daily active users 10,000
Queries per user per day 5
Input tokens per query 1,500
Output tokens per query 400
Input price per million $2.50
Output price per million $10.00
Cache hit rate 35%
Effective daily queries 32,500

Input: 32,500 queries a day times 1,500 tokens times 30 days, divided by a million, times $2.50 gives $3,656. Output: the same with 400 tokens and $10.00 gives $3,900. The total is $7,556 a month.

Why the cache matters this much.

The same traffic without caching costs $11,625. A 35% hit rate removes 35% of the model calls, so it removes 35% of the token cost. The cache is an embedding lookup with a similarity threshold and a time to live, so two differently phrased versions of one question return one answer. The hit rate is measured from the cache metrics, not assumed.

Which number to attack.

  • Hit rate first: every point of hit rate is a point off the whole bill.
  • Output length second: output tokens are priced four times higher than input, and a maximum output tokens limit per template bounds the worst case.
  • Input length third: the system prompt and retrieved context sit in every call; a provider-side cache of the fixed prefix and tighter retrieval cut it.
  • Model routing last: a smaller model for simple templates cuts the per-token price, with an eval to prove quality holds.

Where the estimate goes wrong.

The averages hide a tail. A few users who paste long documents or run scripts can dominate the bill, which is why the production checklist tracks cost per user and per request, and why the cost alerting exercise moves a heavy user to a cheaper model past a daily threshold. The target in the lesson's dashboard is a cost per request under $0.01.

Plausible wrong answers.

  • "Multiply users by a cost per user from a vendor page." The bill comes from tokens per query, queries per user and the hit rate; each is measured.
  • "Caching saves money only on exact repeats." A semantic cache matches similar queries by embedding, which is why the hit rate reaches a third of traffic.
  • "Input tokens dominate because there are more of them." At these prices and lengths the output line is larger even though there are fewer output tokens.

Follow-ups an interviewer may ask.

  • (level 2) Which single metric on the dashboard tells you the estimate holds? Expected: cost per request, which combines token counts and prices and has a target under $0.01.
  • (level 2) The cache hit rate drops to zero after a prompt template change. Why? Expected: the cache key is the query embedding and the response was generated with the old template; stale entries are invalid or the time to live cleared them.
  • (level 3) How does prompt caching on the stable prefix change the input line? Expected: the system prompt and fixed instructions are billed at a discount when they repeat, so the effective input price per query falls without changing the token count.
  • (level 3) What does a per-user daily cap protect that a per-request cost target does not? Expected: the total from one heavy user; many cheap requests still sum to a large bill.

Defend a designAn engineering organization wants to ask questions across 10 repositories with about 2M lines of code and get answers that cite file and line. The index must stay fresh on every push. Design the ingestion, the retrieval, the answer step, the freshness path, and the evaluation, with the budgets you would commit to.

Level 3 of 4 · about 25 minutes to answer well.

Short answer. Parse each file into function and class nodes and chunk at those boundaries, give each chunk a dense embedding, sparse terms and a one-sentence summary, and store a graph of imports and calls between chunks. A query runs dense and sparse search in parallel, merges and deduplicates, reranks the top 50 with a cross-encoder to keep 10, and hands those to a long-context model that must cite every claim by file and line; uncited claims are dropped. A push triggers a symbol-level diff so only changed chunks re-embed, with a budget of under 60 seconds for a 50-file push. Quality is measured on 100 labeled cross-repo questions with MRR@10, nDCG@10, citation faithfulness and p50 and p99 latency.

Ingestion.

  • A push webhook starts a worker that collects the changed files.
  • A parser with grammars for the languages in the fleet extracts function and class nodes with their full source span. Chunks follow node boundaries, not fixed token windows.
  • Each chunk gets three representations: a dense code embedding, sparse terms in a field-weighted index with symbol names weighted 4, bodies 1 and summaries 2, and a one-sentence summary written by a small model with the system preamble cached.
  • A symbol graph records imports, calls and inheritance across files and repositories, used at query time to expand retrieval across repo boundaries.

The summary is the third retrievable modality: a user asks how something is authorized, the code says check_permission, and the summary says authorization.

Retrieval and answer.

  1. Fire dense and sparse search in parallel, deduplicate by repository, path and symbol.
  2. Rerank the top 50 with a cross-encoder and keep the top 10.
  3. Call the synthesizer with the reranked chunks and a cached system prompt, requiring a file and line anchor on every claim.
  4. Parse the output and check each anchor against the span at the indexed commit; a claim without an anchor, or with a span that is missing or does not support it, is re-asked or dropped. Only verified claims return.

Naive cosine search alone is poisoned by generated boilerplate, monorepo duplication and rarely imported symbols, which is why the hybrid search, the reranker and the graph exist.

Freshness.

On each webhook compute the symbol-level diff. Re-embed only the chunks whose text changed, recompute the import, call and inheritance edges of the changed symbols, and delete the chunks, summaries and edges of removed files and symbols from every store. The budget is a 50-file push searchable in under 60 seconds for the whole fleet, without reprocessing the 2M lines.

Evaluation and budgets.

Weight Criterion Measure
25 Retrieval quality MRR@10 and nDCG@10 on 100 held-out questions
20 Citation faithfulness Share of claims with a verifiable file and line anchor
20 Latency and scale p95 query latency at 10k QPS on the indexed corpus
20 Incremental indexing Time from push to searchable on a 50-file commit
15 Answer formatting Clickable citations, snippet previews, follow-up affordance

A weekly rerun of the 100 questions with an alert on an MRR@10 drop above 5% catches drift in the index or the models.

The service around it.

The query path sits inside the production stack from the application lesson: a gateway with per-user limits, guardrails on input and output, streaming of the answer, structured logs per retrieval and synthesis step, and cost tracking that attributes the summary model, the embeddings, the reranker and the synthesizer separately.

Plausible wrong answers.

  • "A million-token context window replaces retrieval." Context helps but does not rank; cross-repo questions still need retrieval and citations.
  • "Dense embeddings alone are enough for code." Exact symbol names need the sparse index, and the summary catches intent that the code text does not state.
  • "Re-index the fleet on every push to keep it simple." Reprocessing 2M lines per commit blows the freshness budget; the diff keeps the index consistent at a fraction of the work.

Follow-ups an interviewer may ask.

  • (level 3) Why chunk at syntax nodes instead of fixed token windows? Expected: a window cuts functions in half and mixes neighbors; a node is one coherent unit with a stable symbol name to cite and deduplicate on.
  • (level 3) What does the reranker add that the two retrievers cannot? Expected: it scores each query and candidate pair together, which is more accurate than cosine on separate embeddings, at a cost that only the top 50 can afford.
  • (level 4) Generated boilerplate makes up a fifth of the corpus. What happens and what do you change? Expected: retrieval poisoning, where near-duplicate generated code crowds the results; flag generated chunks in the payload and down-weight them.
  • (level 4) A question needs code from four repositories. Which component carries that? Expected: the symbol graph expands the candidate set across import and call edges, so the reranker sees chunks from repositories the first search missed.

Defend a designDesign the request path of a chat service that calls a hosted model. Users leave when nothing appears for a few seconds, the provider returns rate limits and server errors at night, and the vector store behind retrieval sometimes times out. Cover what the user sees, how you retry, and what happens when each part fails.

Level 2 of 4 · about 15 minutes to answer well.

Short answer. Stream tokens over server-sent events so the first token appears in a few hundred milliseconds even though the full answer takes seconds. Retry provider failures with exponential backoff and jitter, capped at three retries, then fall through an ordered chain of models to a cached answer and finally a short unavailable message. Secondary systems degrade instead of failing the request: no retrieval context when the vector store is down, a direct model call when the cache is down, and a clear message when a guardrail blocks.

Streaming.

A response of a few hundred output tokens takes 3-8 seconds to finish. Without streaming the user watches a spinner for all of it. With streaming the first token arrives in 200-500ms, the total time is the same, and the perceived latency drops. Server-sent events are the default: one direction, over plain HTTP, consumed by the browser's event source or any HTTP client. Websockets are for two-way needs such as voice, and long polling is for clients that cannot do either.

Three layers of failure.

Layer Example Recovery
Provider 429 rate limit, 500 server error, timeout Backoff with jitter, then the fallback chain
Model Malformed JSON, invented function name Retry once with the error in the prompt
Application Vector store slow, cache down, guardrail exception Degrade: skip the secondary system

Backoff starts at one second, doubles on each attempt and adds random jitter so that many clients do not retry in step. Three retries is the cap; after that the request moves to the next model. Every external call has a timeout, with a default around 30s.

The fallback chain.

Primary model, then a cheaper or more available model, then a smaller one, then a cached response, then the unavailable message. Each step trades quality for availability. The user always gets something, and the log records which step answered so the cost tracker and the quality dashboard can attribute it.

Degradation table.

  • 429: retry with backoff; queue the request and tell the user it is processing.
  • 500: retry up to three times, then switch model; transparent to the user.
  • Timeout: one retry with a shorter prompt or a smaller model.
  • Malformed output: retry with the error attached, else return the raw text.
  • Guardrail block: no retry; explain why the request was blocked.
  • Vector store down: no retry on the store; answer without retrieval context.
  • Cache down: no retry on the cache; call the model directly.

The user-visible contract.

The dashboard targets are a median under 2s and a p99 under 10s. Streaming moves the first-token time inside the median target even when the full response does not. A streamed response has one trap: the status line is sent before the first token, so a failure after that must be sent as an error event inside the stream.

Plausible wrong answers.

  • "Retry until the provider answers." Unbounded retries pile up during an outage; cap them and fall through the chain.
  • "If retrieval is down, fail the request so the answer stays grounded." A secondary system must not take down the primary flow; answer with reduced context and log it.
  • "Buffer the whole response and send it at once for simplicity." The user sees nothing for seconds and leaves; the total time is the same either way.

Follow-ups an interviewer may ask.

  • (level 2) Why add jitter to the backoff? Expected: many clients that fail at once would otherwise retry at the same instants and reproduce the overload.
  • (level 2) Why is a guardrail block not retried? Expected: the input is the problem; retrying the same input gives the same block and spends a call.
  • (level 3) The fallback model has a different price. Where does that show up? Expected: in the cost tracker per request and per model, so the dashboard shows the cost of the outage, not only its rate.
  • (level 3) The stream has started and the model fails. What can the server still do? Expected: send an error event inside the stream, because the HTTP status is already committed.

Q1What is the biggest gap between an LLM demo and a production LLM application?

A demo calls an API and prints the response. Production must handle timeouts, provider outages, concurrent users, cost budgets, streaming delivery, logging, and graceful degradation. The model is the easy part.

Q2Why is streaming token delivery important in production LLM applications?

Without streaming, users wait 3-10 seconds seeing nothing before the full response appears. With streaming, the first token arrives in ~200ms and text flows continuously, making the experience feel responsive.

Q3What should happen when your LLM API provider has an outage?

Production systems need fallback strategies: try Provider B if Provider A fails, serve cached responses for common queries, or return a helpful 'temporarily unavailable' message. Never let a provider outage crash your application.

Q4What observability metrics should a production LLM application track?

Comprehensive observability covers: latency percentiles (for SLA compliance), cost tracking (for budget management), error rates (for reliability), token usage (for optimization), and quality metrics (for regression detection).

Q5Why should you implement rate limiting in your LLM application?

Without rate limiting, a single user (or bot) can exhaust your daily API budget in minutes. Rate limiting protects your costs, prevents abuse, and ensures all users get reasonable response times during peak load.
