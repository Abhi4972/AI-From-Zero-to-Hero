In plain words first
The idea in one line

The terminal is where AI engineers live. Get comfortable here.

Terms you'll hear
Term What people say What it actually means
Shell "The terminal" The program that interprets your commands (bash, zsh, fish)
tmux "Terminal multiplexer" A program that lets you run multiple terminal sessions inside one window, and detach/reattach
Pipe "The bar thing" The \| operator that sends one command's output as input to another
PID "Process ID" A unique number assigned to every running process, used to monitor or kill it
nohup "No hangup" Runs a command immune to the hangup signal, so closing the terminal won't kill it
SSH "Connecting to the server" Secure Shell, an encrypted protocol for running commands on a remote machine

The problem

In plain words first

Every command reads from one stream (stdin) and writes to two: stdout for results and stderr for errors and warnings. The shell lets you connect them: | feeds one command's stdout into the next, > sends it to a file. Small tools joined this way answer most questions about a training log. And a training run should never depend on your terminal staying open, which is what nohup and tmux are for.

You will spend more time in the terminal than in any editor. Training runs, GPU monitoring, log tailing, remote SSH sessions, environment management. Every AI workflow touches the shell. If you're slow here, you're slow everywhere.

This lesson covers the terminal skills that matter for AI work. No history of Unix. No deep-dive into Bash scripting. Just what you need.

The idea

Three things running at once. One terminal. You can detach, go home, SSH back in, and reattach. The training keeps running.

The same idea as a formula

A pipe a | b | c sends the output of a into b and the output of b into c: it is function composition, c(b(a(input))), with each program reading lines and writing lines. The programs run at the same time; b starts working on the first lines while a is still producing the rest, so a pipeline over a 50 GB log never holds all of it in memory.

Costs of common pieces for a file of n lines:

  • grep, awk, cut, wc, head: one pass, O(n) time and constant memory (head even stops reading early).
  • sort: O(nlogn) time and it must see all the input before printing anything; it spills to disk for large inputs.
  • sort | uniq -c: counts duplicates in O(nlogn); uniq alone only merges adjacent duplicates, which is why the sort comes first.

Streams. Every program has standard output (1) and standard error (2); > redirects 1, 2> redirects 2, and 2>&1 sends 2 wherever 1 is going.

Worked example
Reading a pipeline by hand

grep 'loss:' train.log | awk '{print $NF}' | sort -n | head -1 on a 10-line log:

  1. grep keeps the 10 lines containing loss: (the warning line is dropped).
  2. awk '{print $NF}' prints the last field of each: ten numbers such as 1.0000, 0.5000, 0.3333.
  3. sort -n sorts them numerically; without -n, it sorts as text, where 10.5 comes before 9.1.
  4. head -1 prints the first: the lowest loss, 0.1000.
Check your mental model
  • ✗ "python train.py & keeps training after I close the laptop."
    ✓ & only frees the prompt. Closing the terminal sends a hang-up signal that stops the job. Use nohup ... &, or better, run it inside tmux.
  • ✗ "> train.log captures everything the script prints."
    ✓ Only stdout. Tracebacks and most warnings go to stderr and still land on your screen, then vanish. Add 2>&1.
  • ✗ "tmux is only for remote servers."
    ✓ It helps locally too: one window with training, GPU monitor and log tail side by side, and nothing dies if the terminal app crashes.

Step 2 · Piping and redirects

Piping connects commands together. This is how you process logs, filter output, and chain tools. You will use this constantly.

# Count how many times "loss" appears in a log
cat train.log | grep "loss" | wc -l

# Extract just the loss values from training output
grep "loss:" train.log | awk '{print $NF}' > losses.txt

# Watch a log file update in real time, filtering for errors
tail -f train.log | grep --line-buffered "ERROR"

# Sort experiments by final accuracy
grep "final_accuracy" results/*.log | sort -t= -k2 -n -r

# Redirect stdout and stderr to separate files
python train.py > output.log 2> errors.log

# Redirect both to the same file
python train.py > train_full.log 2>&1

The four redirects and the pipe you need:

Symbol What it does
> Write stdout to file (overwrite)
>> Append stdout to file
2> Write stderr to file
2>&1 Send stderr to same place as stdout
\| Send stdout of one command as stdin to the next
See it drawn
Pipes on a real log

These are the commands from this step, run on a ten-epoch log written by the first lines of the cell:

import subprocess

def sh(cmd):
    print("$", cmd)
    print(subprocess.run(["bash", "-c", cmd], capture_output=True, text=True).stdout.rstrip())

with open("train.log", "w") as f:
    for epoch in range(1, 11):
        f.write(f"epoch {epoch} loss: {1 / epoch:.4f}\n")
        if epoch == 7:
            f.write("WARNING gradient norm 812.3\n")

sh("grep -c 'loss' train.log")
sh("grep 'loss:' train.log | awk '{print $NF}' | tail -3")
sh("grep 'loss:' train.log | sort -k4 -n | head -1")
sh("python3 -c \"import sys; print('to stdout'); print('to stderr', file=sys.stderr)\" > out.log 2> err.log; "
   "echo out.log: $(cat out.log); echo err.log: $(cat err.log)")
What you should see
$ grep -c 'loss' train.log
10
$ grep 'loss:' train.log | awk '{print $NF}' | tail -3
0.1250
0.1111
0.1000
$ grep 'loss:' train.log | sort -k4 -n | head -1
epoch 10 loss: 0.1000
$ python3 -c "import sys; print('to stdout'); print('to stderr', file=sys.stderr)" > out.log 2> err.log; echo out.log: $(cat out.log); echo err.log: $(cat err.l
out.log: to stdout
err.log: to stderr

awk '{print $NF}' prints the last field of each line; sort -k4 -n sorts numerically on the fourth field, so head -1 is the lowest loss.

Predict before you run

The log has 11 lines. Why does grep -c 'loss' train.log print 10, not 11? And what would grep -c 'WARNING' train.log print? (Solution P1.)

Break it on purpose

Run python3 -c "import sys; print('to stdout'); print('to stderr', file=sys.stderr)" 2>&1 > both.log and then cat both.log. Is the error line in the file? Swap the two redirects and try again. (Solution B1.)

Step 3 · Background processes

Training runs take hours. You don't want to keep your terminal open the whole time.

# Run in background (output still goes to terminal)
python train.py &

# Run in background, immune to hangup (closing terminal won't kill it)
nohup python train.py > train.log 2>&1 &

# Check what's running in background
jobs
ps aux | grep train.py

# Bring a background job to foreground
fg %1

# Kill a background process
kill %1
# or find its PID and kill that
kill $(pgrep -f "train.py")

The difference between &, nohup, and screen/tmux:

Method Survives terminal close? Can reattach?
command & No No
nohup command & Yes No (check log file)
screen / tmux Yes Yes

For anything longer than a few minutes, use tmux.

Step 4 · tmux

tmux lets you create persistent terminal sessions with multiple panes. This is the single most useful tool for managing training runs.

# Install
# macOS
brew install tmux
# Ubuntu
sudo apt install tmux

# Start a named session
tmux new -s training

# Split horizontally
# Ctrl+B then "

# Split vertically
# Ctrl+B then %

# Navigate between panes
# Ctrl+B then arrow keys

# Detach (session keeps running)
# Ctrl+B then d

# Reattach
tmux attach -t training

# List sessions
tmux ls

# Kill a session
tmux kill-session -t training

A typical AI workflow session:

tmux new -s train

# Pane 1: start training
python train.py --epochs 100 --lr 1e-4

# Ctrl+B, " to split, then run GPU monitor
watch -n1 nvidia-smi

# Ctrl+B, % to split vertically, tail the logs
tail -f logs/experiment.log

# Now detach with Ctrl+B, d
# SSH out, go get coffee, come back
# tmux attach -t train
Reading this output
Reading this screen

A tmux window shows a green status bar at the bottom: the session name in brackets on the left ([train]), then the windows (0:python*, where * marks the current one). tmux ls lists sessions with (attached) next to the one you are in. If tmux attach -t train says no sessions, the server was restarted or the session was killed, and the run inside it stopped too.

Step 5 · Monitoring with htop and nvtop

# System processes (better than top)
htop

# GPU processes (if you have NVIDIA GPU)
# Install: sudo apt install nvtop (Ubuntu) or brew install nvtop (macOS)
nvtop

# Quick GPU check without nvtop
nvidia-smi

# Watch GPU usage update every second
watch -n1 nvidia-smi

# See which processes are using the GPU
nvidia-smi --query-compute-apps=pid,name,used_memory --format=csv

htop keybindings you'll use: - F6 or > to sort by column (sort by memory to find memory leaks) - F5 to toggle tree view (see child processes) - F9 to kill a process - / to search for a process name

Step 6 · SSH for remote GPU boxes

When you rent a cloud GPU (Lambda, RunPod, Vast.ai), you connect via SSH.

# Basic connection
ssh user@gpu-box-ip

# With a specific key
ssh -i ~/.ssh/my_gpu_key user@gpu-box-ip

# Copy files to remote
scp model.pt user@gpu-box-ip:~/models/

# Copy files from remote
scp user@gpu-box-ip:~/results/metrics.json ./

# Sync a whole directory (faster for many files)
rsync -avz ./data/ user@gpu-box-ip:~/data/

# Port forward (access remote Jupyter/TensorBoard locally)
ssh -L 8888:localhost:8888 user@gpu-box-ip
# Now open localhost:8888 in your browser

# SSH config for convenience
# Add to ~/.ssh/config:
# Host gpu
#     HostName 192.168.1.100
#     User ubuntu
#     IdentityFile ~/.ssh/gpu_key
#
# Then just:
# ssh gpu

Step 8 · Common AI terminal patterns

These come up repeatedly in practice:

# Run training, log everything, notify when done
python train.py 2>&1 | tee train.log; echo "DONE" | mail -s "Training complete" you@email.com

# Compare two experiment logs side by side
diff <(grep "accuracy" exp1.log) <(grep "accuracy" exp2.log)

# Find the largest model files (clean up disk space)
find . -name "*.pt" -o -name "*.safetensors" | xargs du -h | sort -rh | head -20

# Download a model from Hugging Face
wget https://huggingface.co/model/resolve/main/model.safetensors

# Untar a dataset
tar xzf dataset.tar.gz -C ./data/

# Count lines in all Python files (see how big your project is)
find . -name "*.py" | xargs wc -l | tail -1

# Check disk space (training data fills disks fast)
df -h
du -sh ./data/*

# Environment variable check before training
env | grep -i cuda
env | grep -i torch
Recap
What to keep from this lesson
  • stdout and stderr are separate: > file, 2>&1 both, | tee file to watch and save at once.
  • grep, awk, sort, head, tail and wc answer most questions about logs without opening an editor.
  • Long runs go in tmux (or nohup ... &), never in a bare terminal.
  • Watch the machine with htop and nvtop or watch -n1 nvidia-smi; move files with scp and rsync over SSH.

Solutions

SolutionP1 · Counting lines

grep -c counts lines that match, and the warning line does not contain "loss", so 10 of the 11 lines match. grep -c 'WARNING' train.log prints 1. To count matches rather than lines (when a pattern can appear twice on one line), use grep -o 'loss' train.log | wc -l.

SolutionB1 · Redirect order

The file holds only to stdout, and to stderr appears on the screen. Redirects are applied left to right: 2>&1 first points stderr at wherever stdout points now, the terminal; then > both.log moves stdout alone to the file. Written as > both.log 2>&1, stdout moves to the file first and stderr follows it, so both lines land in the file.

What's current (2024–2026)
