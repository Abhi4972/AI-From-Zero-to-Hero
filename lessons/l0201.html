About the model on this page
The model on this page is a labeled stand-in

FakeAnthropic is a rule-based stand-in with the same interface as anthropic.Anthropic(). It answers by picking the sentence of the system prompt that best matches the question, so its wording is fixed. It is not a language model. Its code is in Lesson 14.2's appendix; save it as fake_claude.py. The real thing below runs the same calls on the real Anthropic and OpenAI SDKs.

Frameworks hide these APIs, but every framework bug you debug will eventually be a question about what was actually sent to the model and what came back. An hour with the raw request and response pays back for years.

Why this came about

Models became available to developers as web APIs, first as plain text completion and, from 2023, as chat APIs with roles (system, user, assistant). That design is stateless: each request is complete in itself. Everything else in this course builds on this one call, so understanding exactly what goes in and comes out comes first.

The problem: getting a reliable answer out of a model

A ShopKart customer asks how long a UPI refund takes. The answer is in ShopKart's policy, and the policy has to reach the model with the question. Then your code has to read the reply correctly, including when it is incomplete.

from fake_claude import FakeAnthropic                  # a labeled, rule-based stand-in (code in Lesson 3.2's appendix)

client = FakeAnthropic()                               # later: the real client, in "The real thing"
MODEL = "claude-sonnet-5-5"
SYSTEM = ("You are ShopKart's support assistant. Customers can return most items within 7 days of delivery. "
          "Damaged items can be returned within 30 days. Refunds reach UPI in 2 days and cards in 5 to 7 business days.")

response = client.messages.create(
    model=MODEL,                                       # which model; pin an exact ID in production
    max_tokens=300,                                    # the most output tokens you will accept
    system=SYSTEM,                                     # instructions that apply to the whole conversation
    messages=[{"role": "user", "content": "How long does a UPI refund take?"}],
)
print("stop_reason:", response.stop_reason)
print("content:    ", response.content)
print("usage:      ", response.usage)
print("answer:     ", response.content[0].text)
What you should see
stop_reason: end_turn
content:     [TextBlock(type='text', text='Refunds reach UPI in 2 days and cards in 5 to 7 business days.')]
usage:       namespace(input_tokens=70, output_tokens=15)
answer:      Refunds reach UPI in 2 days and cards in 5 to 7 business days.

Everything you send and get back, in one place:

In the request What it does
model Which model answers. Pin an exact model ID in production, so behavior does not change under you
max_tokens The most output tokens you accept. The reply stops there even if it is mid-sentence
system Instructions and background for the whole conversation, sent as its own parameter, not as a message
messages The conversation so far: alternating user and assistant turns, ending with the new user turn. On the newest Claude models a system message may also appear after a user turn, to add an instruction partway through
In the response What it tells you
content A list of content blocks. Here one text block; later you will meet tool_use blocks (Lesson 14.2) and others
stop_reason Why the model stopped. end_turn means it finished; Lesson 14.3 lists all seven values
usage Input and output tokens for this request: what you pay for, and what grows as conversations get longer

Read the answer from content, not from a convenience property, and always check stop_reason before trusting it.

Predict before you run

You make a first call asking "Can I return a phone after 10 days?". Then you make a second call with a fresh messages list containing only "What did I just ask you?". What will the second call answer? (Solution P1.)

In plain words first
A letter, not a phone call

Calling a model API is like sending a letter, not having a phone call: each request must contain everything the model should know (the instructions, the whole conversation so far and the new question), because the model keeps nothing between letters. The reply says how it ended (finished, cut off by the length limit, or asking for a tool) and how many tokens were used. Your code is responsible for keeping the conversation and sending it again next time.

Idea 1 · The API remembers nothing

The experiment below makes three calls. The first asks a question. The second, sent as a fresh list, asks "What did I just ask you?" and the model cannot say, because nothing from the first call exists for it. The third sends the first question, the first answer and the new question together, and now the model can answer. Nothing changed on the server between the second and third calls; only the list you sent did.

# The API keeps no memory between calls. A conversation is a list YOU keep and send every time.
first = client.messages.create(model=MODEL, max_tokens=300, system=SYSTEM,
                               messages=[{"role": "user", "content": "Can I return a phone after 10 days?"}])
print("turn 1:", first.content[0].text)

forgetful = client.messages.create(model=MODEL, max_tokens=300, system=SYSTEM,
                                   messages=[{"role": "user", "content": "What did I just ask you?"}])
print("turn 2, new list:     ", forgetful.content[0].text)

history = [{"role": "user", "content": "Can I return a phone after 10 days?"},
           {"role": "assistant", "content": first.content},          # the model's reply goes back in as-is
           {"role": "user", "content": "What did I just ask you?"}]
remembered = client.messages.create(model=MODEL, max_tokens=300, system=SYSTEM, messages=history)
print("turn 2, full history: ", remembered.content[0].text)
print("input tokens:", forgetful.usage.input_tokens, "without history,", remembered.usage.input_tokens, "with it")
What you should see
turn 1: Customers can return most items within 7 days of delivery.
turn 2, new list:      I don't have any earlier messages in this conversation.
turn 2, full history:  You asked: "Can I return a phone after 10 days?"
input tokens: 68 without history, 117 with it

Each call is independent. A "conversation" is a list that your code keeps and sends in full every time: earlier user turns, the model's earlier replies exactly as they came back, and the new question. That has two consequences you will meet in every lesson of this course. Every turn costs more input tokens than the last (here 68 without history, 117 with one earlier exchange). And whatever is not in the list does not exist for the model: no memory of yesterday's chat, no knowledge of the logged-in customer, no access to your systems, unless you put it there.

Two provider features let the server hold the history for you. Anthropic's message threads (public beta since 2 November 2026) keep it for a few minutes, so each request sends only new messages. OpenAI's Responses API accepts a previous_response_id. Both are optimizations. The model still reads the whole conversation and you are billed for it, and you still need your own copy for when a stored thread expires.

Idea 2 · How a reply ends

Every reply carries a field that says why the model stopped writing. There are two ordinary reasons: it finished what it wanted to say, or it reached the max_tokens limit you set and was cut off in the middle of a sentence. The same question is asked twice, with a generous limit and a tiny one, so that you see both:

# Two ways a reply can end: finished, or cut off by your max_tokens
for limit in (300, 10):
    r = client.messages.create(model=MODEL, max_tokens=limit, system=SYSTEM,
                               messages=[{"role": "user", "content": "How long does a UPI refund take?"}])
    print(f"max_tokens={limit:<3} stop_reason={r.stop_reason:<10} text={r.content[0].text!r}")
What you should see
max_tokens=300 stop_reason=end_turn   text='Refunds reach UPI in 2 days and cards in 5 to 7 business days.'
max_tokens=10  stop_reason=max_tokens text='Let me'

With max_tokens=10 the reply stops after two words, and stop_reason says max_tokens. Code that only reads the text would show the customer "Let me". Set max_tokens to comfortably more than the longest answer you expect, and treat max_tokens as an incomplete reply, never as an answer.

Idea 3 · A small helper that owns the conversation

Most applications wrap these rules in a small class, so callers send text and get text back:

class Chat:
    """A tiny conversation helper: it owns the history, so callers just send text."""
    def __init__(self, system, max_tokens=300):
        self.system, self.max_tokens, self.messages, self.tokens = system, max_tokens, [], 0

    def say(self, text):
        self.messages.append({"role": "user", "content": text})
        r = client.messages.create(model=MODEL, max_tokens=self.max_tokens, system=self.system, messages=self.messages)
        self.tokens += r.usage.input_tokens + r.usage.output_tokens
        if r.stop_reason == "max_tokens":
            raise RuntimeError("reply was cut off; raise max_tokens or ask for a shorter answer")
        self.messages.append({"role": "assistant", "content": r.content})
        return r.content[0].text

chat = Chat(SYSTEM)
for q in ["Can I return a phone after 10 days?", "What if it arrived damaged?", "What did I just ask you?"]:
    print(f"> {q}\n  {chat.say(q)}")
print("messages kept:", len(chat.messages), "| tokens so far:", chat.tokens)
What you should see
> Can I return a phone after 10 days?
  Customers can return most items within 7 days of delivery.
> What if it arrived damaged?
  Damaged items can be returned within 30 days.
> What did I just ask you?
  You asked: "What if it arrived damaged?"
messages kept: 6 | tokens so far: 384

The helper sends six messages by the third question, and the total token count keeps climbing. That growth is why long conversations get trimmed or summarized (Lesson 11.8), and why agents, which make several requests per question, feel it first (Lesson 14.3).

The real thing

The same request through the real SDKs. These ran against the local test server described in Lesson 14.2, which returns each API's documented response format; with a real key, only the wording and the token counts would change.

import anthropic

client = anthropic.Anthropic()                         # reads ANTHROPIC_API_KEY from the environment
r = client.messages.create(model=MODEL, max_tokens=300, system=SYSTEM,
                           messages=[{"role": "user", "content": "How long does a UPI refund take?"}])
print(r.stop_reason, "|", r.content[0].text, "|", r.usage.input_tokens, "in,", r.usage.output_tokens, "out")
What you should see
end_turn | Refunds reach UPI in 2 days and cards in 5 to 7 business days. | 70 in, 15 out

from openai import OpenAI

oai = OpenAI()                                         # reads OPENAI_API_KEY
r = oai.responses.create(model="gpt-5.5", instructions=SYSTEM, input="How long does a UPI refund take?",
                         max_output_tokens=300)
print(r.status, "|", r.output_text, "|", r.usage.input_tokens, "in,", r.usage.output_tokens, "out")
What you should see
completed | Refunds reach UPI in 2 days and cards in 5 to 7 business days. | 400 in, 30 out

OpenAI's Responses API uses different names for the same ideas: instructions for the system prompt, input for the messages, output_text for the reply, max_output_tokens, and status (completed or incomplete) where Claude has stop_reason. Lesson 11.5 puts four providers side by side.

What changes with a real model: the same question can get different wording on every call (Lesson 11.22), so test the facts in an answer, not its exact text. Responses take hundreds of milliseconds to seconds (Lesson 11.21). And errors are real: rate limits (HTTP 429), overload (529 on Anthropic) and timeouts. The SDKs retry some of these for you, twice by default (Lesson 14.5).

Make it your own
Make it your own: a window on the history

Long conversations get expensive. Extend Chat so it sends only the last two exchanges, plus the new question, and compare the total tokens over five questions with the full-history version. (Solution M1.)

Solutions

SolutionP1 · A fresh list on the second call

"I don't have any earlier messages in this conversation." The second request contained only the second question, so as far as the model is concerned there was no first question. The API is stateless. Memory is the list you send.

SolutionP2 · A system message first

The stand-in rejects it with a 400 error, as the real Messages API does when a system message is the first entry:

400: a system message cannot be the first entry in messages; use the top-level system field for instructions that apply from the start

The stand-in's wording is its own. The fix is the top-level system parameter. On the newest Claude models (Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1 and others), a system message is accepted later in the conversation, after a user turn, to add an instruction partway through; because it comes after the earlier messages, it does not invalidate their prompt cachelater · 11.4 (Lesson 11.4). When you port code between providers, this is one of the first differences to handle: OpenAI's Chat Completions API takes a system (or developer) message first, its Responses API takes instructions, and Claude takes system.

SolutionD1 · A new list on every turn

say starts with self.messages = [...], so every call throws the history away and sends only the newest question. Build the list once in __init__ and append to it, as Chat does. The tell-tale sign in a trace: input tokens stay flat from turn to turn, when they should grow.

SolutionM1 · A window on the history
# Solution M1: keep only the last few exchanges, so cost per turn stops growing
class WindowedChat(Chat):
    def __init__(self, system, keep_turns=2, **kw):
        super().__init__(system, **kw)
        self.keep_turns = keep_turns

    def say(self, text):
        self.messages = self.messages[-2 * self.keep_turns:]     # whole user/assistant pairs only
        return super().say(text)

questions = ["Can I return a phone after 10 days?", "What if it arrived damaged?", "How long does a UPI refund take?",
             "And for cards?", "What did I just ask you?"]
for cls in (Chat, WindowedChat):
    c = cls(SYSTEM)
    replies = [c.say(q) for q in questions]
    print(f"{cls.__name__:<13} tokens {c.tokens:>4} | messages sent last turn: {len(c.messages) - 1} | last reply: {replies[-1]}")

Chat          tokens  875 | messages sent last turn: 9 | last reply: You asked: "And for cards?"
WindowedChat  tokens  733 | messages sent last turn: 5 | last reply: You asked: "And for cards?"

The window cuts tokens and still answers the last question correctly, because it only needed the previous turn. The price is that anything older than the window is gone: a question about the first turn would fail. Lesson 11.8 replaces the hard cut with a summary of what was dropped, which keeps the gist at a fraction of the tokens.

Check your understanding

Explain the mechanismWhat actually happens in a call to a chat model API?

Worked answer. The client sends the model ID, a max_tokens limit, the system prompt and the whole conversation as a list of user and assistant messages. The provider tokenizes all of it, the model reads it (prefill) and generates a reply one token at a time (decode) until it finishes, hits max_tokens or a stop sequence, or asks for a tool. The response contains content blocks, a stop reason and token usage. Nothing is stored between calls unless you opt into a provider feature, so the application keeps the conversation and resends it every time, and the cost of each turn grows with its length.

A plausible wrong answer. "The model remembers the conversation on the server." That leads to missing history, wrong answers on follow-up questions, and confusion about why costs grow.

Follow-ups. Why does a long system prompt slow the first token down? What is prompt caching for (Lesson 11.4)?

Debug a failureUsers say the assistant "forgets" what they said two messages ago. What do you check?

Worked answer. Look at the exact request the application sent for that turn. Is the earlier exchange in messages at all? Common causes are a history list rebuilt on every call, history kept per server process (so a load balancer sends the next turn to a replica that never saw it), and a trimming rule that drops too much. Confirm from the trace by checking input tokens per turn: they should grow. Fix it by storing conversations by ID in shared storage, and test with a multi-turn case that asks about an earlier turn.

A plausible wrong answer. "The model's context window is too small." A few turns are nowhere near any modern context limit; the history simply was not sent.

Follow-ups. How would you keep the full history but bound its cost? What should never be stored in the history?

Defend a designWould you call the provider's SDK directly, or put a model-neutral layer in front of it?

Worked answer. For a product that must outlive one model, a thin neutral layer: one internal message format, one adapter per provider, or a library such as LiteLLM or a gateway, so switching models is configuration and every call is logged in one place. I would still go direct to a provider's SDK for a feature the layer does not support yet, behind the same interface. The deciding questions are how many providers you will run, how quickly you need new features, and who owns the layer. A layer that hides important differences, such as stop reasons or error types, is worse than none.

A plausible wrong answer. "Always use the raw SDK, abstractions only slow you down." That works until the first model switch, which then touches every file.

Follow-ups. Which differences between providers must the layer expose rather than hide? How do you test that a switch did not change behavior?
