Why this came about

Basic RAG reached a ceiling on harder questions. A wave of techniques from 2023 and 2024 improved either the query (rewriting, decomposition, hypothetical answers) or the passages (contextual chunks, parent documents, summaries), each aimed at a specific failure.

In plain words first
Better questions, better pieces

When basic retrieval falls short, two kinds of fixes help. Improve the question: rewrite it, split it into sub-questions, or generate a hypothetical answer to search with. Improve the pieces: add context to each chunk before embedding it, keep small chunks for matching but return their larger parent section, or store summaries. Each fix targets a specific failure, so measure before adopting it.

Contextual retrieval

A chunk like "Express delivery costs INR 99" loses its context once it is cut out of the document. Anthropic's contextual retrieval (2024) asks a model to write a short context for each chunk ("This is from ShopKart's shipping policy, about delivery charges") and prepends it before embedding and keyword indexing. In their tests, failed retrievals dropped by 35% with contextual embeddings, 49% when combined with contextual BM25, and up to 67% with reranking added. Prompt caching makes the per-chunk model calls affordable, since the whole document is the cached prefix.

The cheapest version prepends the document title and section heading, and already helps:

# Contextual retrieval, the cheap version: prepend each chunk's document context before indexing.
# (Anthropic's version asks an LLM to write 50 to 100 tokens of context per chunk; a title is the minimum.)
TITLES = {d: DOCS[d].split(".")[0] for d in DOCS}             # first sentence is the title here
CONTEXT_CHUNKS = [(cid, doc, f"{TITLES[doc]}. {text}") for cid, doc, text in CHUNKS]

bm25_ctx = BM25Okapi([tokenize(c[2]) for c in CONTEXT_CHUNKS])
def search_bm25_ctx(query: str, k: int = 3) -> list[str]:
    scores = bm25_ctx.get_scores(tokenize(query))
    return [CONTEXT_CHUNKS[i][0] for i in sorted(range(len(CHUNKS)), key=lambda i: scores[i], reverse=True)[:k]]

# Multi-query: ask a model for rewrites, search each, fuse. The rewrites below are what a model might produce.
REWRITES = {
    "What does faster delivery cost?": ["express delivery price", "how much is express delivery", "faster delivery cost"],
}
def search_multi(query: str, k: int = 3) -> list[str]:
    queries = REWRITES.get(query, [query])
    return rrf([search_bm25(q, 10) for q in queries])[:k]

q = "What does faster delivery cost?"
print("plain BM25:  ", search_bm25(q))
print("multi-query: ", search_multi(q))
for name, fn in [("BM25", search_bm25), ("BM25 + context", search_bm25_ctx)]:
    print(f"{name:15} MRR = {sum(reciprocal_rank(fn(q, 10), g) for q, g in GOLD) / len(GOLD):.2f}")
What you should see
plain BM25:   ['shipping#0', 'shipping#1', 'refund-policy#0']
multi-query:  ['shipping#1', 'shipping#0', 'refund-policy#0']
BM25            MRR = 0.64
BM25 + context  MRR = 0.78

A one-line context header raised keyword MRR from 0.64 to 0.78 on this set, and rewriting the user's vague "faster delivery" into the corpus's word "express" moved the right chunk to the top.

Query transformation

Users write short, vague or compound questions. Transform them before retrieval:

Technique What the model does Helps when
Multi-query (above) Writes several phrasings; results are fused Vocabulary mismatch between users and documents
HyDE (hypothetical document embeddings) Writes a fake answer and searches with that Short questions against long technical documents
Step-back prompting Asks a more general question first ("what is the refund policy?") Specific questions that need general rules
Query decomposition Splits "compare A and B" into sub-questions Multi-part and comparative questions
Self-query / metadata extraction Turns "laptop policies from 2025" into a filter year=2025 plus a search Structured attributes hidden in natural language

Each adds a model call and latency. Add them when your eval shows a matching failure type, not by default.

In production
Query transformation in production

Rewrites help most on short, vague questions and hurt on precise ones: a rewrite of "error E-4012 on checkout" may drop the code that mattered. Keep the user's original query as one of the searches, cache rewrites for repeated questions, and log the rewritten queries so you can see when they drift. For conversations, the most valuable rewrite is often the simplest: turn a follow-up ("and for COD orders?") into a standalone question before searching.

Small-to-big retrieval

Small chunks match precisely; big chunks give the model enough context to answer. Small-to-big (also called parent-document retrieval) gets both: index sentences or small chunks, but when one matches, return its parent section or a window of neighbors to the model. Store a parent_id with every chunk to make this a lookup.

In production
When small-to-big backfires

Returning whole parent sections can multiply prompt size, and with it cost and the chance that the model latches onto the wrong paragraph. Cap the parent size, return a window of neighboring chunks instead of a whole section for long documents, and check faithfulness, not just recall, after switching it on.

Long context or RAG?

Context windows of a million tokens or more make it tempting to put everything in the prompt. Cache-augmented generation (CAG) does exactly that for small, stable corpora: load the whole knowledge base once, cache it, and answer from it.

Choose long context or CAG when Choose RAG when
The corpus is small (fits comfortably) and stable The corpus is large or changes often
Questions need the whole document (summaries, cross-references) Questions need a few specific facts
You can cache the prefix You need per-user permissions on content
Latency of a long prefill is acceptable Cost per question must be low

In practice they combine: retrieve a few relevant whole documents rather than tiny chunks, and let a long-context model read them.

The retrieval improvement loop

Improving RAG is a loop, not a one-time choice: measure, find the biggest failure type, apply the matching fix, measure again. The table is the loop's lookup step. Work down it in order, because the early rows are cheap and do not require re-indexing, while the later ones do.

Choose by scenario
Accuracy is not good enough: what to try, in what order

Change one thing at a time, re-run the same labeled questions, and keep a short log of what each change did. That log becomes your team's playbook for the next system.

Step by step: the advanced techniques in code

The blocks below continue the lab from Lessons 4.3 to 4.7. Each technique is measured on the same GOLD questions, so you can see what it buys on this corpus, and the habit carries over to yours.

Step 1 · Reranking the top candidates

The two-stage retrieval pattern: retrieve generously with hybrid search, then rerank the candidates with a more expensive scorer and keep the best few. A real reranker is a cross-encoder model (Cohere Rerank, Voyage, BGE reranker, Bedrock or Azure semantic ranking). The stand-in below scores each candidate by IDF-weighted overlap with the query plus a phrase bonus, which is enough to show the mechanics and the measurement.

import math

N_CHUNKS = len(CHUNKS)
DF = {}
for _, _, text in CHUNKS:
    for w in set(tokenize(text)):
        DF[w] = DF.get(w, 0) + 1
STOP = {"the", "a", "an", "is", "i", "my", "can", "do", "what", "how", "it", "to", "of", "on", "for", "when", "if", "there"}

def rerank_score(query: str, text: str) -> float:
    """Stand-in for a cross-encoder: rewards rare query words found in the passage, and adjacent word pairs."""
    q = [w for w in tokenize(query) if w not in STOP]
    t = tokenize(text)
    tset = set(t)
    score = sum(math.log(1 + N_CHUNKS / DF.get(w, 0.5)) for w in q if w in tset)
    pairs = set(zip(t, t[1:]))
    score += sum(1.5 for pair in zip(q, q[1:]) if pair in pairs)            # phrase matches count extra
    return score

def search_reranked(query: str, k: int = 3, candidates: int = 10) -> list[str]:
    pool = search_hybrid(query, candidates)                                # stage 1: cheap, high recall
    return sorted(pool, key=lambda cid: rerank_score(query, TEXT[cid]), reverse=True)[:k]   # stage 2

for name, fn in [("Hybrid", search_hybrid), ("Hybrid + rerank", search_reranked)]:
    mrr_ = sum(reciprocal_rank(fn(q, 10), g) for q, g in GOLD) / len(GOLD)
    r1 = sum(recall_at_k(fn(q, 1), g) for q, g in GOLD) / len(GOLD)
    print(f"{name:16} recall@1 = {r1:.2f}   MRR = {mrr_:.2f}")
What you should see
Hybrid           recall@1 = 0.62   MRR = 0.79
Hybrid + rerank  recall@1 = 0.62   MRR = 0.81

The crude stand-in leaves recall@1 unchanged and lifts MRR a little, by moving correct chunks up within the top few. That matters because the top few passages are what the model reads most carefully, and because a better top-3 lets you send fewer chunks (cheaper, less distraction). A real cross-encoder reads meaning, not just shared words, so expect clearly larger gains on paraphrased questions; its cost is a model call over every candidate, so keep the candidate pool to 20 to 100.

Step 2 · HyDE and query decomposition

HyDE (hypothetical document embeddings) searches with a model-written answer instead of the question, because an answer looks more like the documents than a question does. Query decomposition splits a compound question into parts, retrieves for each, and fuses the results so no part is crowded out.

def hyde(question: str) -> str:
    """Stands in for: 'Write a short passage from a help centre that answers this question.'"""
    return {"Is there an extra charge if I pay cash when it arrives?":
            "Cash on delivery orders carry a COD handling fee of INR 30."}.get(question, question)

def decompose(question: str) -> list[str]:
    """Stands in for: 'Split this into independent sub-questions, one per line.'"""
    return {"How do I cancel and how long until I get my money?":
            ["How do I cancel an order?", "When will my refund arrive?"]}.get(question, [question])

q1 = "Is there an extra charge if I pay cash when it arrives?"
print("question as query:", search_bm25(q1))
print("HyDE passage as query:", search_bm25(hyde(q1)))

q2 = "How do I cancel and how long until I get my money?"
print("compound as one query:", search_hybrid(q2))
print("decomposed, RRF-fused:", rrf([search_hybrid(sub, 5) for sub in decompose(q2)])[:3])
print("decomposed, top 2 each:", list(dict.fromkeys(c for sub in decompose(q2) for c in search_hybrid(sub, 2))))
What you should see
question as query: ['shipping#1', 'cancellation#0', 'cod#0']
HyDE passage as query: ['cod#0', 'refund-policy#0', 'warranty#0']
compound as one query: ['cancellation#0', 'shipping#1', 'refund-policy#0']
decomposed, RRF-fused: ['cancellation#0', 'shipping#0', 'warranty#0']
decomposed, top 2 each: ['cancellation#0', 'shipping#1', 'refund-policy#0', 'refund-policy#1']

Two lessons. HyDE fixed the first question: the plain query ranked the shipping chunk first, while the hypothetical answer, written in the corpus's own words ("cash on delivery", "fee"), put the COD chunk on top. Decomposition shows a trap: fusing the sub-question results with RRF lost the refund chunks, because RRF rewards documents that appear in several lists, and generic chunks (shipping, warranty) matched both halves weakly. For decomposed questions, take the top results of each part instead, as the last line does. Each technique adds a model call, so turn it on for the question types your eval shows failing.

Step 3 · Small-to-big (parent-document) retrieval

Index small pieces for precise matching, but return the larger parent to the model so it has enough context to answer.

SENTENCES = []                                            # (sentence_id, parent_chunk_id, text)
for cid, _, text in CHUNKS:
    for i, s in enumerate(re.split(r"(?<=[.!?])\s+", text)):
        SENTENCES.append((f"{cid}/s{i}", cid, s))
bm25_sent = BM25Okapi([tokenize(s[2]) for s in SENTENCES])

def search_small_to_big(query: str, k: int = 2) -> list[tuple[str, str]]:
    """Match single sentences, return their parent chunks (deduplicated, best first)."""
    scores = bm25_sent.get_scores(tokenize(query))
    parents = []
    for i in sorted(range(len(SENTENCES)), key=lambda i: -scores[i]):
        sid, parent, _ = SENTENCES[i]
        if parent not in [p for p, _ in parents]:
            parents.append((parent, sid))
        if len(parents) == k:
            break
    return parents

for parent, matched in search_small_to_big("How long does a UPI refund take?"):
    print(f"matched {matched} -> return {parent}: {TEXT[parent][:70]}...")
What you should see
matched refund-policy#0/s0 -> return refund-policy#0: Refund policy. Customers can request a refund within 7 days of deliver...
matched refund-policy#1/s2 -> return refund-policy#1: Damaged or defective items are always refundable, even after 7 days, i...

The best match was the precise sentence about UPI refunds (refund-policy#1/s2, second here because BM25 also liked the word "refund" in the first chunk); in both cases the model receives the whole chunk around the matched sentence, not just one line.

Step 4 · Metadata filters from the question (self-query)

Questions often contain structured constraints: a document type, a date, a product category. Self-query retrieval extracts them into a filter and searches only the matching subset, which is both more precise and cheaper.

META = {cid: {"doc": doc, "topic": "payments" if doc in ("refund-policy", "cod") else
              "orders" if doc in ("shipping", "cancellation") else "other"} for cid, doc, _ in CHUNKS}

def extract_filter(question: str) -> tuple[dict, str]:
    """Stands in for an LLM that returns {"filter": {...}, "query": "..."} as structured output."""
    if re.search(r"\bpayment|refund|cash|cod\b", question, re.I):
        return {"topic": "payments"}, question
    return {}, question

def search_filtered(question: str, k: int = 3) -> list[str]:
    flt, query = extract_filter(question)
    allowed = [cid for cid in META if all(META[cid].get(f) == v for f, v in flt.items())]
    scores = bm25.get_scores(tokenize(query))
    ranked = sorted((i for i, c in enumerate(CHUNKS) if c[0] in allowed), key=lambda i: -scores[i])
    return [CHUNKS[i][0] for i in ranked[:k]], flt

print(search_filtered("Which payment methods get the fastest refund?"))
What you should see
(['refund-policy#0', 'refund-policy#1', 'cod#0'], {'topic': 'payments'})

The filter ran inside the search (only payment chunks were scored), which is the same rule that made permission filtering safe in Lesson 4.8: filter first, then rank.

Step 5 · Diversity with maximal marginal relevance

When several chunks say nearly the same thing (overlapping chunks, the same policy copied into an FAQ page, old and new versions of a document), the top-k wastes slots on repeats. Maximal marginal relevance (MMR) picks each next result to be relevant to the query but different from what is already selected.

from sklearn.feature_extraction.text import TfidfVectorizer

POOL = {cid: text for cid, _, text in CHUNKS}
POOL["refund-faq#0"] = ("Refund FAQ. Customers can request a refund within 7 days of delivery. "   # a near-duplicate page,
                        "Damaged or defective items are refundable if reported within 30 days.")  # common in real wikis
ids = list(POOL)
tfidf = TfidfVectorizer(stop_words="english").fit(POOL.values())
V = tfidf.transform(POOL.values()).toarray()

def mmr(query: str, k: int = 3, lam: float = 0.5) -> list[str]:
    """Pick results that are relevant to the query but not redundant with those already picked."""
    q = tfidf.transform([query]).toarray()[0]
    relevance = V @ q
    selected, pool = [], list(range(len(ids)))
    while pool and len(selected) < k:
        best = max(pool, key=lambda i: lam * relevance[i] - (1 - lam) * max((V[i] @ V[j] for j in selected), default=0))
        selected.append(best); pool.remove(best)
    return [ids[i] for i in selected]

q = "refund for damaged item and how it is paid"
print("relevance only:", mmr(q, lam=1.0))
print("MMR, lam=0.5:  ", mmr(q, lam=0.5))
print("FAQ vs policy similarity:", round(float(V[ids.index("refund-faq#0")] @ V[ids.index("refund-policy#0")]), 2))
What you should see
relevance only: ['refund-faq#0', 'refund-policy#0', 'cod#0']
MMR, lam=0.5:   ['refund-faq#0', 'cod#0', 'warranty#0']
FAQ vs policy similarity: 0.89

The FAQ page and the policy chunk are 89% similar, so relevance-only ranking spent two of three slots on the same content. MMR kept one, then used the freed slot for the warranty chunk, which covers dead-on-arrival replacements. lam trades relevance (1.0) against diversity (0.0): tune it on your eval set, because too low a value starts pulling in irrelevant chunks. Most vector stores and LangChainlater · 6.2 retrievers offer MMR as a search option.

Step 6 · Diagnose, then choose the fix

The loop above starts with a diagnosis, and one test separates the two big families of failure. Retrieve wide (top 10 here; top 50 on a real corpus). If the right chunk appears in the wide list but not in the top 3, it is a ranking problem (rows 2, 9 and 11 of the loop). If it is not in the wide list at all, it is a recall problem, and the fix is upstream: content, vocabulary, search type or chunking (rows 1, 3 to 8, 10 and 12).

def diagnose(search_fn, questions=GOLD, top: int = 3, wide: int = 10) -> dict:
    """Classify each labeled question: answered in the top results, ranked too low, or not retrieved at all."""
    report = {"ok": [], "ranking": [], "recall": []}
    for question, gold in questions:
        results = search_fn(question, wide)
        if gold in results[:top]:
            report["ok"].append(question)
        elif gold in results:
            report["ranking"].append((question, results.index(gold) + 1))
        else:
            report["recall"].append(question)
    return report

QUESTIONS = GOLD + [("Do you deliver to the Andaman Islands?", "delivery-areas#0")]   # no such page exists yet

NEXT = {"ranking": "rerank a wider candidate list (loop row 2)",
        "recall": "check the content, then hybrid search or metadata prepend (rows 1, 3, 4)"}

for name, fn in [("BM25", search_bm25), ("hybrid", search_hybrid), ("hybrid + rerank", search_reranked)]:
    r = diagnose(fn, QUESTIONS)
    print(f"{name:16} ok {len(r['ok'])}/{len(QUESTIONS)} | ranked too low: {[rank for _, rank in r['ranking']]} | "
          f"not retrieved: {len(r['recall'])}")
r = diagnose(search_bm25, QUESTIONS)
for kind in ("ranking", "recall"):
    for item in r[kind]:
        question = item[0] if kind == "ranking" else item
        print(f"BM25 {kind} miss: {question[:42]!r} -> {NEXT[kind]}")
What you should see
BM25             ok 7/9 | ranked too low: [4] | not retrieved: 1
hybrid           ok 8/9 | ranked too low: [] | not retrieved: 1
hybrid + rerank  ok 8/9 | ranked too low: [] | not retrieved: 1
BM25 ranking miss: 'Do I pay for shipping on a 600 rupee order' -> rerank a wider candidate list (loop row 2)
BM25 recall miss: 'Do you deliver to the Andaman Islands?' -> check the content, then hybrid search or metadata prepend (rows 1, 3, 4)

BM25 ranked one answer fourth: a ranking problem, which hybrid search and reranking both fixed. The Andaman question fails for every retriever, because the corpus has no delivery-areas page: an inventory problem, row 1 of the loop, and no amount of tuning will fix it. On a real system, run this over your full labeled set after every change, and track the three counts over time.

Industry practice
Inventory problems versus capability problems

Jason Liu, whose Systematically Improving RAG Applications course is widely followed, separates failures into inventory problems (the information is not in the index at all: add or fix content) and capability problems (it is there but the system cannot find or combine it: improve retrieval, add tools such as date filters or comparisons). He recommends clustering real user questions into segments, measuring satisfaction per segment, and fixing the high-volume, low-satisfaction segments first. Fixing an inventory problem with a better retriever wastes weeks.

From the field
Anthropic: what contextual retrieval and reranking bought, in numbers

Anthropic's contextual retrieval write-up (September 2024) measured the failure rate of top-20 retrieval across several datasets. The baseline failed 5.7% of the time. Prepending model-written context to each chunk before embedding cut failures to 3.7%; adding the same context to BM25 cut them to 2.9%; and reranking the results cut them to 1.9%, a 67% reduction overall. The context costs about $1.02 per million document tokens to generate once, using prompt caching. The lesson that generalizes: the cheap ingestion-time fix and the reranker stack, so measure each step rather than picking one. Source: Anthropic Engineering, "Introducing Contextual Retrieval".

Go deeper (optional)
Other retrieval techniques you will hear named

The methods in this lesson are the ones that most often pay off. A few more appear in papers, talks and vendor documentation:

  • RAPTOR: cluster the chunks, summarise each cluster with a model, cluster the summaries, and so on, building a tree. Index every level. Broad questions match the summaries and specific ones match the leaves. Useful for long documents where the answer is spread across sections; the cost is many summarisation calls at indexing time.
  • RAG-Fusion: generate several rewrites of the question, search for each, and merge the results with reciprocal rank fusion (Lesson 4.6). It is multi-query retrieval with RRF.
  • Late chunking: embed the whole document with a long-context embedding model first, then pool the token vectors per chunk, so each chunk's vector carries context from the rest of the document (Lesson 4.3).
  • Late interaction (ColBERT, ColPalilater · 9.2): one vector per token or image patch, matched at query time (Lessons 4.6 and 9.2).
  • Learned sparse retrieval (SPLADE, ELSER): a model-made keyword index that also matches related words (Lesson 4.4).
  • Self-RAGlater · 4.11 and corrective RAGlater · 4.11: the model judges whether retrieval was needed and whether the results are good enough, and searches again if not (Lesson 4.11).
  • GraphRAGlater · 5.6 and LightRAG: retrieval over entities and relationships extracted from the documents (Lesson 5.6).
  • Cache-augmented generation: put a small, stable corpus in the prompt and cache it, with no retrieval at all (Lesson 4.13).

Treat each as a hypothesis to test on your evaluation set, not as an upgrade to install.

Exercises

Predict before you run

Contextual retrieval adds a one-line header to each chunk before indexing. Will it help BM25, vector search, or both? (Solution P1.)

Break it on purpose

Use HyDE (embed a hypothetical answer instead of the question) for "What is ShopKart's COD fee?". What happens if the model's guess says INR 50? (Solution B1.)

Debugging exercise

Query decomposition splits "Compare COD and UPI refunds" into two sub-queries, but the final answer only covers UPI. Where do you look? (Solution D1.)

Make it your own

Implement small-to-big: match on sentence-level chunks, then return the whole parent section to the model, and compare answer completeness on questions with conditions. (Solution M1.)

Solutions

SolutionP1 · Both, for different reasons

Both: BM25 gains the header's words ("Refund policy"), and the embedding gains the topic the chunk's sentences assumed. The lesson's measurement shows the keyword gain; measure the vector gain on your own data.

SolutionB1 · HyDE embeds a guess

The hypothetical answer is only used for matching, so a wrong number usually still finds the COD chunk. But the guess can steer retrieval toward wrong topics for unfamiliar domains. Never show the hypothetical answer, and compare HyDE with plain retrieval on the eval.

SolutionD1 · Each sub-query must be answered

Check what each sub-query retrieved: the COD sub-query may have retrieved nothing relevant, and the generator answered with what it had. Require an answer per sub-question, and show missing parts explicitly.

SolutionM1 · Match small, read big

Keep a parent ID on each small chunk, retrieve by small chunks, deduplicate parents, and pass parents to the model. Expect better completeness on rules with conditions, at the cost of more context tokens.

Check your understanding

Explain the mechanismName advanced retrieval techniques and when each helps.

Worked answer. Contextual chunk headers or contextual retrieval (chunks lack context), query rewriting and expansion (vocabulary mismatch), HyDE (short or abstract questions), decomposition (multi-part questions), small-to-big (precise matching with complete context), metadata filters from the question (self-query), and MMR for diversity. Each fixes a specific failure; pick by diagnosing failures first (Step 8).

A plausible wrong answer. "Use all of them." Each adds latency and cost and can hurt other questions.

Follow-ups. How do you decide which technique to try first?

Debug a failureAfter adding query rewriting, some answers got worse. Why?

Worked answer. The rewrite changed the meaning (dropped a constraint, added an assumption) or translated a Hinglish question badly. Log original and rewritten queries, compare retrieval for both on the eval, and retrieve with both and fuse rather than replacing the original.

A plausible wrong answer. "Rewriting always helps." It helps vague queries and can damage precise ones.

Follow-ups. How would you evaluate a rewriter on its own?

Defend a designLong context or RAG for a 500-page policy manual?

Worked answer. If the manual is stable and questions are occasional, long context with caching can be simpler and comparable in quality. For frequent questions, many users, permissions, citations and updates, RAG is cheaper and easier to maintain. Many teams combine them: retrieve sections, then give the model whole sections.

A plausible wrong answer. "Long context makes RAG obsolete." Cost, latency and the lost-in-the-middle effect remain.

Follow-ups. How would you compare them fairly?

Q1What does contextual retrieval add to each chunk?

The chunk keeps its context after being cut out, which helps both BM25 and vectors.

Q2When is cache-augmented generation (long context with caching) a better choice than RAG?

Long context suits small, stable, holistic tasks.

Q3Users ask about a product launched last week and the bot says it doesn't know. The launch notes were never ingested. What kind of problem is this?

The content is missing; no retriever can find it.

Q4When fusing results for a decomposed question, why can RRF lose the right chunks?

Take the top results of each sub-question instead.

Q5What does maximal marginal relevance trade off?

It stops near-duplicates from filling the top-k.
