Why this came about

By 2025 there were more agent frameworks than any team could evaluate. Choosing among them by features alone proved unreliable, so this lesson frames the choice by what a system needs most and by the team's platform.

In plain words first
Choosing by the job, not by popularity

All the frameworks in the LangChain and LangGraph and Other agent frameworks, compared sections can build an agent. The choice depends on what your system needs most: explicit workflows and durability (LangGraph), a fast path on one vendor's models and cloud (the vendor SDKs), retrieval at the core (LlamaIndex), typed Python (Pydantic AI), role-based crews (CrewAI), or a ready-made workspace harness (Claude Agent SDK). Also weigh your team's platform, observability, and how easy it is to leave.

How the framework landscape got here

The tools in the LangChain and LangGraph and Other agent frameworks, compared sections make more sense when you know what they replaced.

When What appeared What it taught the field
Late 2022 LangChain and LlamaIndex: chains of prompts, the first "agents" that parsed tool calls out of model text Composing model calls is useful; parsing free text for actions is fragile
Spring 2023 AutoGPT and BabyAGI: a model in an open-ended loop that writes its own task list Autonomy without checks wanders, repeats itself and burns money. The demos were famous and almost nobody ran them in production
Mid 2023 Function calling in model APIs Tool requests as structured data made agents dependable (Lesson 14.2)
2023 AutoGen (Microsoft Research), MetaGPT, ChatDev, CrewAI: several agents with roles talking to each other Role-play is intuitive, but conversations between agents multiply tokens and errors; structure and hand-offs matter more than personas
2023 Semantic Kernel (Microsoft): plugins and planners for enterprise applications Enterprises want typed plugins, telemetry and governance. It merged with AutoGen's ideas into the Microsoft Agent Framework (Lesson 14.85)
2023 to 2024 OpenAI's Assistants API: threads, tools and files managed by the provider Hosted state is convenient and limiting. It was replaced by the Responses API and the Agents SDK (Lesson 14.81)
2024 LangGraph: agents as explicit graphs with persisted state; OpenAI's experimental Swarm: agents and hand-offs in a few dozen lines Durable state, human approval and explicit control flow are what production needs (the LangChain and LangGraph section)
Late 2024 Anthropic's Building effective agents; the Model Context Protocol Start with simple workflows; standardise how tools are connected (the Protocols section)
2025 Vendor agent SDKs (OpenAI Agents SDK, Google ADK, Strands, Claude Agent SDK); harnesses for long-running coding agents; A2A and AG-UI The model providers ship the loop themselves; the differentiation moves to context, tools, evaluation and operations
2026 Protocols and tooling consolidate under open foundations; "agent platforms" on every cloud (the Cloud platforms, compared section) Frameworks are converging on the same parts. Learn the parts (the Agents from first principles section) and any framework is quick to pick up

Two names from this history still come up in conversation as cautionary shorthand: "an AutoGPT-style loop" means unbounded autonomy with no checks, and "agents chatting to each other" means multi-agent role-play without typed hand-offs.

How to choose

Answer these in order. The first strong constraint usually decides.

  1. Where must it run, and what does the company already own? An AWS-first enterprise saves months with Strands and AgentCore; an Azure and .NET shop with Microsoft Agent Framework and Foundry; a Google shop with ADK and Agent Engine; data that lives in Databricks pulls toward its native agents.
  2. How much control flow is fixed? Mandatory steps, approvals, long-running and resumable processes call for a runtime (LangGraph, MAF workflows, ADK graph workflows, or a durable engine). Open-ended conversations suit a lighter framework.
  3. What language does the team write? Python has every option; .NET narrows to MAF; TypeScript to the Agents SDK, Strands, ADK, LangGraph.js, Vercel AI SDK and Mastra.
  4. What must be observable and evaluated? Check native OpenTelemetrylater · 14.117 support and how traces reach your existing tools.
  5. How fast is the project moving? Check release frequency and breaking changes. Every framework here shipped breaking changes in the last year.
Industry practice
Keep the seams clean, whatever you pick

Teams that switch frameworks painlessly have one thing in common: the framework touches little. Write tools as plain functions (or serve them over MCP), keep prompts in files or a registry, put models behind a gateway, emit OpenTelemetry traces, and keep the eval suite independent of the framework. Then the framework is just the loop, and replacing a loop is a week's work, not a rewrite. The 12-Factor Agents principles (HumanLayer, 2025) make the same argument: own your prompts, your context window and your control flow.

In production
Framework regrets seen in production
  • Chosen for the demo, not the runtime: a framework that made the prototype quick but has no durable state, interrupts or tracing, so all three get bolted on later. Check the production features before the API.
  • Business logic inside framework abstractions: rules hidden in chains, callbacks or agent instructions are hard to test and impossible to migrate. Keep them in plain functions and tools.
  • Unpinned versions: frameworks in this space ship breaking changes monthly. Pin exact versions and upgrade deliberately, with the eval suite.
  • Two frameworks for one system because two teams prototyped separately: choose one runtime per system, and connect systems with MCP or A2A instead.

In production
What tends to go wrong with each, in production
  • CrewAI: role-play prompts and verbose agent chatter inflate tokens; tasks without precise expected outputs drift. Give every task an exact expected_output, and prefer Flows for anything that must run the same way every time.
  • Pydantic AI: validation failures trigger retries that cost model calls; a schema the model often fails is a schema to simplify, not a retry limit to raise.
  • LlamaIndex: defaults (chunk sizes, top-k, response modes) are tuned for demos; set them explicitly and measure (Lesson 14.27).
  • DSPy: optimizers overfit small training sets; keep a held-out set and re-run it after every compile.
  • smolagents: code agents execute what the model writes, so use a sandboxed executor, never the local one, outside development.
  • Claude Agent SDK: the harness can read files and run commands; restrict allowed tools and directories, and require permission for writes.

Building agents without writing code

Much agent building in companies happens outside Python, in visual and low-code tools. You should know they exist, what they are good for, and where they stop.

Kind Examples Good for Limits to check
Workflow automation with AI steps n8n, Zapier, Make, Microsoft Power Automate Connecting business apps: "when a form arrives, classify it, look up the customer, draft a reply" Mostly fixed workflows with a model step; testing, versioning and evaluation are weak
Visual agent and RAG builders Dify, Flowise, Langflow, OpenAI's Agent Builder Prototyping an agent or a RAG pipeline on a canvas; demos; handing a working sketch to engineers Complex logic becomes a tangle of boxes; check export to code, self-hosting and observability
Agent builders inside business suites Microsoft Copilot Studio, Salesforce Agentforce, ServiceNow AI Agents, Google's Gemini Enterprise Agents that live where the business data and permissions already are (Microsoft 365, the CRM, the service desk) Tied to the suite's data model, pricing and release pace; limited control of prompts, models and evaluation
Cloud agent consoles The agent builders in Amazon Bedrock, Microsoft Foundry and Google's agent platform (the Cloud platforms, compared section) A managed path from prototype to production on one cloud Portability; what you can and cannot inspect

A sensible division of labour: business teams prototype and own simple automations in a low-code tool; anything customer-facing, high-volume or risky is rebuilt in code where it can be tested, versioned, evaluated and reviewed (the Production engineering and AI system design section). Whichever tool is used, the questions of this course still apply: what can the agent do, who approves it, how is it evaluated, and what does it cost per run?

Check your mental model
  • ✗ "There is a best framework."
    ✓ There is a best fit for a given problem, team and platform.
  • ✗ "Switching frameworks later is easy."
    ✓ Prompts and tools move easily; state, persistence and deployment do not.
  • ✗ "A framework decision is permanent."
    ✓ Keep tools, prompts and evaluations framework-neutral so you can change.

Solutions

SolutionP1 · Shortlist by requirements

LangGraph (durability, interrupts, streaming) and one provider SDK that supports approvals, such as the OpenAI Agents SDK, for comparison. The requirements decide the shortlist.

SolutionB1 · Popularity is not fit

It may lack a required feature (durable approvals, your language, your provider), or its abstractions may fight your design.

SolutionD1 · Spike the hardest path

A spike implementing the hardest requirements (approval and resume, multi-agent routing, streaming) before committing, plus an exit plan.

SolutionM1 · A justified matrix

Criteria such as durability, approvals, streaming, provider support, observability, team skills; scores from spike evidence, not reading.

Check your understanding

Explain the mechanismHow do you choose an agent framework?

Worked answer. From requirements: control-flow complexity, durability and human-in-the-loop, providers, language, deployment target, observability and team skills. Shortlist two or three, build the hardest path in each, compare code, behavior and operations, and keep business logic portable.

A plausible wrong answer. "Pick the most popular one." Popularity does not match your requirements.

Follow-ups. What do you still own whichever you pick?

Debug a failureTwo teams chose different frameworks, and integration is painful. What do you do?

Worked answer. Integrate at clear boundaries (tools via MCP, agents via A2A or APIs), standardize tracing and evals, and converge on one framework for new work if the costs justify it.

A plausible wrong answer. "Force a rewrite." Boundaries are cheaper first.

Follow-ups. What standards would you set?

Defend a designShould a company standardize on one agent framework?

Worked answer. On a default with a paved path (templates, platform integration), allowing exceptions with reasons. Standardizing shared layers (tools, identity, tracing, evals) matters more than the framework.

A plausible wrong answer. "Yes, one framework only." It blocks good fits for some problems.
