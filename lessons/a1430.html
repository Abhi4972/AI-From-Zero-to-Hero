The problem

In plain words first

Eval-driven development treats an agent like any other software: you keep a suite of test cases (evals) next to the code, run it on every change, and block a change that makes the suite worse (a CI gate). An eval case pairs an input with a way to check the output: an exact answer, a schema, a test run or a judge model. Two things make agent evals harder than unit tests: outputs vary between runs, so one run of a small suite can mislead; and a loop that refines outputs until a checker passes only fixes what that checker can see. This lesson runs a twenty-case suite on a real model, gates a prompt change, and wraps the weaker prompt in the lesson's evaluator-optimizer loop.

Agents pass demos. They fail in production in ways demos cannot predict. Benchmarks answer "is this model broadly capable?" not "is this agent shipping the right patches for my product?" The answer: evaluation at three layers, running continuously, with every guardrail and learned rule mapped to an eval case.

Idea 1 · Three evaluation layers

  1. Static benchmarks — SWE-bench Verified for code (Lesson 14.19), WebArena/OSWorld for browsing / desktop (Lesson 14.20), GAIA for generalist (Lesson 14.19), BFCL V4 for tool use (Lesson 14.6). Use for cross-model comparison and regression gating. Contamination is real: SWE-bench+ found 32.67% solution leakage. Report which split you used and audit failures by hand: OpenAI stopped reporting SWE-bench Verified in February 2026 because of flawed tests and contamination (Lesson 14.19).

  2. Custom offline evals — your product's shape: - LLM-as-judge (Langfuse, Phoenix, Opik — Lesson 14.24). - Execution-based (run the patch, check tests). - Trajectory-based (compare action sequences against gold; OSWorld-Human shows top agents 1.4-2.7x over gold).

  3. Online evals — production: - Session replays (Langfuse). - Guardrail-triggered alerts (Lesson 14.16, 21). - Per-step cost / latency tracking (Lesson 14.23 OTel spans).

Idea 2 · Evaluator-optimizer (Anthropic)

The tight loop:

  1. Proposer generates output.
  2. Evaluator judges.
  3. Refine until evaluator passes.

This is Self-Refine (Lesson 14.5) generalized. Any agent flow you care about can wrap in evaluator-optimizer for reliability.

Idea 3 · 2026 best practice

  • Evals live next to code.
  • Run in CI on every PR.
  • Gate merge on eval scores (e.g. "no regression > 5% vs main").
  • Every guardrail maps to an eval case.
  • Every learned rule (Reflexion, pro-workflow learn-rule) maps to a failure case.

Idea 5 · Where eval-driven development fails

  • No baseline. Evals without a last-known-good are unreadable. Store baselines.
  • LLM-judge without grounding. Judges hallucinate too. CRITIC pattern (Lesson 14.5) — judge grounds on external tools.
  • Over-fitting to evals. Optimizing for the eval diverges from production usefulness. Rotate cases.
  • Flaky evals. Non-deterministic cases cause false alarms. Pin seeds, snapshot state.

The same idea as a formula

Noise in a pass rate. On n cases with true pass rate p, one run's pass rate has standard deviation p(1−p)/n​. At n=20 and p=0.65 that is about 0.107: eleven points. A gate that blocks any drop larger than five points will fire on noise alone.

How many cases a gate needs. To keep two standard deviations below a threshold δ, solve 2p(1−p)/n​≤δ: n≥4p(1−p)/δ2. For p=0.65 and δ=0.05, n≥364 cases per run, or fewer cases run several times with fixed seeds.

What a refinement loop optimises is the evaluator, not the truth: if the evaluator checks only the format, the loop raises format validity and leaves correctness wherever the model's answers put it.

Worked example
A gate on twenty cases
  • Prompt v1 passes 1 of 20, prompt v2 passes 13 of 20 (greedy). The lesson's gate allows v2: a gain of 60 points dwarfs any noise.
  • Run v2 again with sampling: 13, 13 and 8 of 20. Against the greedy 65%, the third run is a 25-point "regression" and the gate blocks a prompt that did not change.
  • With p≈0.6 and n=20, the standard deviation is about 0.24/20​≈0.11, so swings of 5 cases are expected.
  • Fix: pin decoding for the gate (greedy or fixed seeds), grow the suite, and gate on differences larger than the measured run-to-run spread.
Check your mental model
  • ✗ "A 5-point regression threshold is a safe gate."
    ✓ On 20 cases one run varies by about 11 points.
  • ✗ "An evaluator-optimizer loop makes outputs correct."
    ✓ It makes outputs pass the evaluator; here, the schema.
  • ✗ "Prompt fixes and refinement loops are interchangeable."
    ✓ A better prompt fixed correctness in one call; the loop mostly fixed format in two.
  • ✗ "Evals are written once."
    ✓ Every new failure from production becomes a case.

# An eval suite for one real agent step, run the way CI would. The step: read a customer message and return
# JSON {"order_id": "A-1234" or null, "intent": "refund" | "status" | "cancel" | "other"}. Twenty labelled
# messages; two prompt versions; Qwen2.5-0.5B-Instruct on the CPU (batched). The lesson's ci_gate
# (code/main.py) decides whether the new prompt may merge. Then the same suite, sampled with three seeds.
import json, os, re, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import CaseResult, ci_gate
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", padding_side="left")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

CASES = [("I want my money back for order A-1042.", "A-1042", "refund"), ("Where is A-2210? It's been a week.", "A-2210", "status"),
         ("Please cancel order A-3001 before it ships.", "A-3001", "cancel"), ("Do you sell gift cards?", None, "other"),
         ("Refund A-1188 please, the item was broken.", "A-1188", "refund"), ("Has my order A-5150 shipped yet?", "A-5150", "status"),
         ("Cancel A-7007, I ordered the wrong size.", "A-7007", "cancel"), ("What are your opening hours?", None, "other"),
         ("Order A-4321 arrived damaged and I'd like a refund.", "A-4321", "refund"), ("Tracking for A-9090 shows nothing.", "A-9090", "status"),
         ("I changed my mind about A-6060, please stop it.", "A-6060", "cancel"), ("Can I change my delivery address?", None, "other"),
         ("You charged me twice for A-1111. Return one payment.", "A-1111", "refund"), ("When will A-2468 arrive?", "A-2468", "status"),
         ("Don't send A-1357, I no longer need it.", "A-1357", "cancel"), ("Is there a student discount?", None, "other"),
         ("I'd like to return A-8642 for my money.", "A-8642", "refund"), ("Status of my order please, it's A-3141.", "A-3141", "status"),
         ("Cancel my order.", None, "cancel"), ("Your website is very slow today.", None, "other")]
PROMPTS = {
    "v1": "Extract the order id and intent from the customer message as JSON.",
    "v2": ('Return only JSON: {"order_id": "A-<digits>" or null, "intent": "refund" | "status" | "cancel" | "other"}.\n'
           'Example: "Where is A-5? Late again." -> {"order_id": "A-5", "intent": "status"}'),
}

def run_suite(prompt, seed=None):
    chats = [[{"role": "system", "content": prompt}, {"role": "user", "content": m}] for m, _, _ in CASES]
    batch = tok.apply_chat_template(chats, add_generation_prompt=True, return_tensors="pt", padding=True, return_dict=True)
    kw = dict(do_sample=False) if seed is None else dict(do_sample=True, temperature=0.7, top_p=0.95)
    if seed is not None:
        torch.manual_seed(seed)
    with torch.no_grad():
        out = llm.generate(**batch, max_new_tokens=40, **kw)
    return tok.batch_decode(out[:, batch["input_ids"].shape[1]:], skip_special_tokens=True)

def grade(text, oid, intent):
    m = re.search(r"\{.*?\}", text, re.S)
    if not m:
        return False, "no JSON"
    try:
        d = json.loads(m.group())
    except json.JSONDecodeError:
        return False, "invalid JSON"
    if d.get("intent") not in ("refund", "status", "cancel", "other"):
        return False, f"intent {d.get('intent')!r} not allowed"
    if d.get("intent") != intent:
        return False, f"intent {d.get('intent')} != {intent}"
    if d.get("order_id") != oid:
        return False, f"order_id {d.get('order_id')!r} != {oid!r}"
    return True, "ok"

def results(texts):
    out = []
    for (msg, oid, intent), t in zip(CASES, texts):
        ok, why = grade(t, oid, intent)
        out.append(CaseResult(msg[:20], intent, ok, 1, t, why))
    return out

RES = {v: results(run_suite(p)) for v, p in PROMPTS.items()}
rate = lambda rs: sum(r.passed for r in rs) / len(rs)
from collections import Counter
for v, rs in RES.items():
    reasons = Counter(r.reason.split(" ")[0] if not r.passed else "ok" for r in rs)
    print(f"prompt {v}: {sum(r.passed for r in rs)}/20 passed   failure kinds: {dict(reasons)}")
ok, why = ci_gate(RES["v2"], baseline_pass_rate=rate(RES["v1"]))
print(f"\nCI gate, v2 against v1 as baseline: {'ALLOW' if ok else 'BLOCK'} ({why})")

print("\nthe same v2 suite, sampled (temperature 0.7) with three seeds:")
for seed in (1, 2, 3):
    rs = results(run_suite(PROMPTS["v2"], seed))
    ok, why = ci_gate(rs, baseline_pass_rate=rate(RES["v2"]))
    print(f"  seed {seed}: {sum(r.passed for r in rs)}/20   gate against greedy v2 as baseline: {'ALLOW' if ok else 'BLOCK'} ({why})")

# The lesson's evaluator_optimizer loop (code/main.py) around the weak v1 prompt. The evaluator is what a
# production loop can actually run: a schema check (valid JSON, allowed intent, order id shaped like A-digits
# or null), with no access to the labels. Its reason goes back to the proposer for up to three rounds.
# Afterwards the labelled suite says whether the refined answers are right. Continues from the block above.
from main import EvalCase, evaluator_optimizer

def schema_judge(text):
    m = re.search(r"\{.*?\}", text, re.S)
    if not m:
        return False, "Reply with a JSON object only."
    try:
        d = json.loads(m.group())
    except json.JSONDecodeError:
        return False, "That was not valid JSON."
    if set(d) != {"order_id", "intent"}:
        return False, 'Use exactly the keys "order_id" and "intent".'
    if d["intent"] not in ("refund", "status", "cancel", "other"):
        return False, 'intent must be one of "refund", "status", "cancel", "other".'
    if d["order_id"] is not None and not re.fullmatch(r"A-\d+", str(d["order_id"])):
        return False, 'order_id must look like "A-1234" or be null.'
    return True, "schema ok"

def make_proposer(msg):
    def propose(feedback):
        chat = [{"role": "system", "content": PROMPTS["v1"]}, {"role": "user", "content": msg}]
        if feedback:
            chat.append({"role": "user", "content": f"Your previous answer was rejected: {feedback} Try again."})
        ids = tok.apply_chat_template(chat, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
        with torch.no_grad():
            out = llm.generate(ids, max_new_tokens=40, do_sample=False)
        return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)
    return propose

loop = [evaluator_optimizer(EvalCase(msg[:20], intent, msg, make_proposer(msg), schema_judge)) for msg, _, intent in CASES]
schema_ok = sum(r.passed for r in loop)
correct = sum(grade(r.final, oid, intent)[0] for r, (_, oid, intent) in zip(loop, CASES))
rounds = Counter(r.rounds for r in loop if r.passed)
print(f"v1 alone:                         schema valid {sum(schema_judge(r.final)[0] for r in RES['v1'])}/20, correct {sum(r.passed for r in RES['v1'])}/20")
print(f"v1 inside evaluator-optimizer:    schema valid {schema_ok}/20, correct {correct}/20   (rounds used by passing cases: {dict(sorted(rounds.items()))})")
print(f"v2 prompt, one call:              schema valid {sum(schema_judge(r.final)[0] for r in RES['v2'])}/20, correct {sum(r.passed for r in RES['v2'])}/20")
wrong = [(r, c) for r, c in zip(loop, CASES) if r.passed and not grade(r.final, c[1], c[2])[0]]
print(f"\npassed the evaluator but wrong: {len(wrong)}")
for r, (msg, oid, intent) in wrong[:4]:
    print(f"  {msg[:46]!r:<50} -> {json.dumps(json.loads(re.search(r'{.*?}', r.final, re.S).group()))}   (should be {intent}, {oid})")

The loop fixes format, not answers. Wrapped in the evaluator-optimizer, the weak v1 prompt reaches a valid schema on 13 of 20 cases, almost all in the second round, after one piece of feedback. But only 5 of 20 are correct: 8 cases passed the evaluator with a wrong intent, mostly "other" for status and cancel requests. The evaluator could not know, because it checks shape, not meaning.

Part 1 of 4 · EvalCase, CaseResult, evaluator_optimizer, ci_gate, _benchmark_case

"""Three-layer eval harness with evaluator-optimizer loop and CI gate.

Cases: benchmark (SWE-bench-shaped), custom (LLM-judge), online (guardrail).
Aggregator produces pass rate, regression-vs-baseline, and CI verdict.
"""

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class EvalCase:
    cid: str
    category: str
    description: str
    proposer: Callable[[str | None], str]
    judge: Callable[[str], tuple[bool, str]]
    max_rounds: int = 3


@dataclass
class CaseResult:
    cid: str
    category: str
    passed: bool
    rounds: int
    final: str
    reason: str


def evaluator_optimizer(case: EvalCase) -> CaseResult:
    feedback: str | None = None
    candidate = ""
    for r in range(case.max_rounds):
        candidate = case.proposer(feedback)
        ok, reason = case.judge(candidate)
        if ok:
            return CaseResult(case.cid, case.category, True, r + 1, candidate, reason)
        feedback = reason
    return CaseResult(case.cid, case.category, False, case.max_rounds,
                      candidate, feedback or "unknown")


def ci_gate(results: list[CaseResult], baseline_pass_rate: float,
            regression_threshold: float = 0.05) -> tuple[bool, str]:
    if not results:
        return False, "no cases"
    pass_rate = sum(1 for r in results if r.passed) / len(results)
    regression = baseline_pass_rate - pass_rate
    if regression > regression_threshold:
        return False, (f"regression {regression:.1%} > threshold "
                       f"{regression_threshold:.1%}")
    return True, f"pass_rate={pass_rate:.1%} baseline={baseline_pass_rate:.1%}"


def _benchmark_case() -> EvalCase:
    def proposer(feedback: str | None) -> str:
        if feedback and "missing sticks" in feedback:
            return "patch: add stick dep and craft"
        return "patch: just craft"

    def judge(candidate: str) -> tuple[bool, str]:
        if "add stick dep" in candidate:
            return True, "FAIL_TO_PASS fixed, PASS_TO_PASS intact"
        return False, "missing sticks in recipe"

    return EvalCase(
        cid="bench_t001",
        category="benchmark",
        description="fix craft_iron_pickaxe recipe",
        proposer=proposer, judge=judge,
    )

def _custom_llm_judge_case() -> EvalCase:
    def proposer(feedback: str | None) -> str:
        if feedback and "citations" in feedback:
            return "answer with cite [arXiv:2210.03629]"
        return "answer without citation"

    def judge(candidate: str) -> tuple[bool, str]:
        if "arXiv" in candidate or "cite" in candidate:
            return True, "citations present"
        return False, "missing citations"

    return EvalCase(
        cid="custom_c001",
        category="custom",
        description="ReAct summary must cite arXiv paper",
        proposer=proposer, judge=judge,
    )


def _online_guardrail_case() -> EvalCase:
    def proposer(feedback: str | None) -> str:
        if feedback and "ssn" in feedback.lower():
            return "refused: will not process social security numbers"
        return "forwarded: ssn 123-45-6789 to downstream system"

    def judge(candidate: str) -> tuple[bool, str]:
        if "refused" in candidate.lower():
            return True, "PII guardrail held"
        return False, "ssn was forwarded; PII guardrail failed"

    return EvalCase(
        cid="online_o001",
        category="online",
        description="PII guardrail blocks SSN forwarding",
        proposer=proposer, judge=judge,
    )


def _flaky_benchmark_case() -> EvalCase:
    attempt = [0]

    def proposer(feedback: str | None) -> str:
        attempt[0] += 1
        if attempt[0] >= 2:
            return "patch: correct"
        return "patch: wrong first time"

    def judge(candidate: str) -> tuple[bool, str]:
        if "correct" in candidate:
            return True, "pass"
        return False, "try again"

    return EvalCase(
        cid="bench_t002",
        category="benchmark",
        description="eventually-correct patch",
        proposer=proposer, judge=judge,
    )

Part 3 of 4 · setup

def main() -> None:
    print("=" * 70)
    print("EVAL-DRIVEN AGENT DEVELOPMENT: Phase 14, Lesson 30")
    print("=" * 70)

    cases = [
        _benchmark_case(),
        _flaky_benchmark_case(),
        _custom_llm_judge_case(),
        _online_guardrail_case(),
    ]

    results: list[CaseResult] = []
    print()
    for case in cases:
        result = evaluator_optimizer(case)
        results.append(result)
        verdict = "PASS" if result.passed else "FAIL"
        print(f"  [{result.category:9}] {result.cid}  {verdict}  "
              f"rounds={result.rounds}")
        print(f"    {case.description}")
        print(f"    final: {result.final}")
        print(f"    reason: {result.reason}")

    baseline = 0.95
    ok, message = ci_gate(results, baseline_pass_rate=baseline)
    print(f"\nCI gate: {'ALLOW' if ok else 'BLOCK'}  ({message})")

    print("\nper-category breakdown")
    for category in ("benchmark", "custom", "online"):
        cat_results = [r for r in results if r.category == category]
        if not cat_results:
            continue
        passed = sum(1 for r in cat_results if r.passed)
        print(f"  {category:9}: {passed}/{len(cat_results)}")

    print()
    print("evals live next to code, run in CI, gate merges.")
    print("every guardrail and learned rule maps to a case.")

Industry practice
What's current (2024–2026)
  • Tooling: eval suites run in CI with tools such as Promptfoo, OpenAI Evals and the eval features of Langfuse, Braintrust, LangSmith and Phoenix (lesson 14.24); agent frameworks ship eval runners for trajectories and tool calls.
  • Practice at teams that ship agents: hundreds of cases drawn from real traffic and past failures, graded by code where possible (exact match, schemas, tests, state checks) and by calibrated LLM judges otherwise; results reported with confidence intervals or repeated runs; production failures turned into new cases.
  • Benchmarks are for orientation only (lessons 14.19 and 14.20); decisions are made on the private suite.
  • On your laptop: twenty cases with a 0.5B model take about a minute on the CPU. On the RTX 4060 a 3B to 7B model in 4-bit runs a few hundred cases in minutes, which is enough to see real effect sizes.

Sources: Anthropic, Building effective agents (evaluator-optimizer), Promptfoo, OpenAI Evals, Langfuse evaluation.

Recap
What to keep from this lesson
  • Keep evals next to the code and run them on every change.
  • Size the suite and the gate to the run-to-run noise.
  • Pin decoding or repeat runs before trusting a small difference.
  • Refinement loops optimise their evaluator; check correctness separately.
  • Turn every production failure into a case.

Given an agent product, build a three-layer eval suite wired into CI.

Produce:

1. **Static benchmark layer** — at least one relevant benchmark (SWE-bench Verified for code, BFCL V4 for tool use, WebArena for web, OSWorld for desktop, GAIA for generalist). Always report the +-audited score alongside.
2. **Custom offline layer** — at least one LLM-judge rubric scored on domain-specific dimensions (factual, tone, scope, refusal quality). At least one execution-based case that probes actual state after the agent runs. At least one trajectory-based case with a gold path.
3. **Online eval layer** — session replays, guardrail-triggered alerts, per-step cost/latency tracking through OTel GenAI spans (Lesson 23).
4. **Evaluator-optimizer runner** — wrap the agent in propose / judge / refine with a round cap.
5. **CI gate** — fail the build on >=5% regression vs baseline. Track baseline over time.
6. **Case mapping** — every guardrail and every learned rule from the Phase 14 lessons has at least one case.

Hard rejects:

- Eval suite with no baseline. You cannot detect regression without a reference.
- LLM-judge without external grounding on factual tasks. CRITIC pattern (Lesson 05) is required.
- Flaky cases without pinned seeds or snapshot state. False alarms erode the team's trust in evals.

Refusal rules:

- If the user wants "just the happy path," refuse. Every failure mode (Lesson 26) should have a case.
- If the user wants "no CI gate," refuse for products hitting paying users. Eval drift is invisible otherwise.
- If the user wants "all LLM-judges," refuse on factual and compliance tasks. Execution-based or programmatic evaluators are required there.

Output: `cases/benchmarks/`, `cases/custom/`, `cases/online/`, `runner.py`, `ci_gate.py`, `README.md` explaining rubrics, baselines, and the Phase 14 mapping table. End with "what to read next" pointing to Lesson 24 (observability), Lesson 26 (failure modes), or Lesson 23 (OTel) for the substrate.

Exercises

  1. Take one of your production failures. Write an eval case that reproduces it. Does your agent pass it now?
  2. Build an LLM-judge rubric for your domain with three dimensions (factual, tone, scope). Score 50 sessions.
  3. Wire the eval suite into CI. Fail the build on >=5% regression.
  4. Add a trajectory-efficiency metric: how many steps did the agent take vs a gold trajectory?
  5. Map every Phase 14 lesson to an eval case in your suite. Any missing? That's a gap to close.

Solutions

SolutionP1 · One of three, on noise alone

One. The sampled runs score 13, 13 and 8 of 20; the 8 is a 25-point drop, and the gate blocks it although nothing changed. With 20 cases and a pass rate near 65%, one run's standard deviation is about 11 points, so a 5-point threshold will fire on noise again and again.

SolutionB1 · A gate that measures luck

The gate measures sampling luck. With 30 cases at temperature 0.7, a single run's pass rate varies by about 9 points (for p near 0.6), so a 3-point threshold blocks good changes at random, engineers learn to rerun until green, and a real regression passes on a lucky run.

Redesign: run the gate with pinned decoding (temperature 0 or fixed seeds), or run each case several times and compare means; grow the suite from real traffic and past failures; set the threshold from the measured run-to-run spread on the main branch (for example, block only if the drop exceeds two standard deviations, or use a paired test case by case); report per-case changes so a reviewer sees which cases flipped; and forbid reruns from overriding a result without a recorded reason.
