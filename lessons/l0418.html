RAG and knowledge

JuniorWhat is RAG and why use it instead of fine-tuning?

Retrieval-augmented generation retrieves relevant documents at question time and puts them in the prompt. It keeps answers current, cites sources, respects document permissions and is cheap to update. Fine-tuning changes behavior and style, not reliably knowledge. Most teams use RAG for knowledge and fine-tuning only for format, tone or narrow skills.

MidWhy hybrid search, and what does a reranker add?

Vector search finds paraphrases; keyword search (BM25) finds exact terms like product codes and names. Combining them, usually with reciprocal rank fusion, beats either alone. A cross-encoder reranker then reads the query and each candidate together and reorders the top results much more accurately, at extra latency. Retrieve wide, rerank narrow.

MidHow do you evaluate a RAG system?

Separately evaluate retrieval (recall and precision at k, MRR, against labeled relevant chunks) and generation (faithfulness to the retrieved context, answer relevance, correctness against a reference). Build the labeled set from real questions, segmented by type. Tools: RAGAS, DeepEval, platform evaluators, or your own judges calibrated against experts.

SeniorWhat are agentic RAG and vectorless RAG, and when are they worth it?

Agentic RAG lets the model plan queries, call retrieval several times, check results and iterate, which helps multi-hoplater · 14.88 and comparative questions. Vectorless RAG navigates document structure (a table of contents tree, as in PageIndex) or uses keyword and SQL tools instead of embeddings, which helps long, well-structured documents such as filings and manuals. Both cost more tokens and latency, so measure the gain over a tuned hybrid baseline first. Managed versions exist: Bedrock and AgentCore managed knowledge bases, Foundry IQlater · 14.155, Agent Searchlater · 14.157.

JuniorHow do you choose a chunk size?

There is no universal number; 200 to 800 tokens with some overlap is a common start. Small chunks retrieve precisely but lose context; large chunks keep context but dilute similarity and cost more tokens. Better than fixed size: split on document structure (headings, sections, tables), keep tables and code blocks whole, and add the document title and section path to each chunk (contextual headers). Then tune on recall at k for your questions.

MidHow does HNSW work, and what do its parameters trade off?

HNSW (hierarchical navigable small world) builds a layered graph in which each vector links to near neighbors; a search enters at the sparse top layer and greedily descends to the dense bottom layer. M (links per node) and ef_construction set graph quality and memory; ef_search sets how many candidates a query explores, trading latency for recall. Alternatives: IVF partitions vectors into clusters and searches a few (nprobe); product quantization compresses vectors to save memory at some recall cost. Always measure recall against exact search on a sample.

MidHow do you handle metadata filters and document permissions in vector search?

Store tenant, access groups, document type and dates as metadata and filter at query time, ideally inside the index search (filtered HNSW or pre-filtering) rather than after it, because post-filtering can return too few results when the filter is selective. Permissions must be enforced by the retrieval service using the user's identity, never by asking the model to ignore documents. For many tenants, separate indexes or namespaces give stronger isolation.

MidWhat are contextual retrieval and query rewriting?

Contextual retrieval (Anthropic, 2024) prepends a short, model-written description of where each chunk sits in its document before embedding and BM25 indexing; it reduced retrieval failures substantially in their tests, especially combined with reranking. Query rewriting turns the user's question into better search queries: expanding abbreviations, splitting multi-part questions, generating a hypothetical answer to embed (HyDE), or using conversation history to make follow-ups self-contained. Both are cheap wins to test before more complex architectures.

SeniorHow do you keep a RAG index fresh and consistent?

Incremental ingestion keyed by document ID and content hash: re-embed only changed documents, delete removed ones (including from caches), and record the index version on every answer. Schedule full rebuilds when the chunker or embedding model changes, building the new index side by side and switching an alias after evals pass. Monitor "no result" rates and stale-answer complaints. Propagate deletions for erasure requests.

SeniorHow would you build RAG over scanned PDFs, tables and images?

Parse with a layout-aware tool (Docling, Unstructured, Azure Document Intelligence, Textract, Document AI, or a vision model) that keeps reading order, headings and tables; convert tables to Markdown or rows with headers repeated; caption figures with a vision model. Alternatively index page images directly with multimodal embeddings (ColPalilater · 4.31-style late interaction) and let a vision model read the retrieved pages. Evaluate on questions that need tables and figures, because text-only pipelines fail there silently.

SeniorYour RAG system's answer accuracy is 70% and the business wants 90%. Walk me through what you do.

First find out where the 30% fails, with a labeled set and traces, split by question type. Separate inventory problems (the answer is not in the corpus) from retrieval problems (recall at 50 against recall at 5) and generation problems (good context, bad answer). Then work the cheap fixes in order and re-measure after each: add missing content; hybrid search for codes and names; prepend titles and section paths to chunks; rerank a wide candidate list; rewrite or decompose vague and multi-part questions; filters for product, date and tenant; and only then re-chunk or change the embedding model, side by side behind an alias. For generation failures: grounded prompts with required citations, a refusal path, and a groundedness check. Report progress per segment, because the average can hide the segment that matters.

MidWhat are embeddings, and how do you choose an embedding model?

An embedding is a vector that places text (or images) so that similar meanings are close together, measured by cosine similarity or dot product. Choose on your own retrieval eval, not only on leaderboards such as MTEB: language coverage (Hindi and English, say), domain fit, maximum input length, dimensions (storage and speed; many models support shortened Matryoshka dimensions), price, and where it can run. Changing the embedding model means re-embedding the whole corpus, so version it with the index.

SeniorThe context window is a million tokens. Why not put all the documents in the prompt?

Cost and latency scale with input tokens on every call; accuracy degrades for information in the middle of long contexts and when many distractors are present ("lost in the middle", context rot); and permissions are hard to enforce when everything is in one prompt. Long context is excellent for a few large documents that must be read as a whole, such as one contract. For a knowledge base, retrieval plus a well-curated context is cheaper and usually more accurate. Measure both on your questions; with prompt caching, long context sometimes wins for small, stable corpora.

MidWhat is generative engine optimization, and what actually works?

Making content more likely to be retrieved, quoted and cited in AI answers. The KDD 2024 GEO paper found that adding quotations, statistics and cited sources raised visibility most, and keyword stuffing lowered it, with the largest gains for lower-ranked sources. In practice: allow the right AI search bots, server-render main content, answer first in self-contained passages with specifics, keep facts about the entity consistent, and measure with repeated samples (Lesson 14.81).
