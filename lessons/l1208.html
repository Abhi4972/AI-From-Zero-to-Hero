Why this came about

Agent runs that last minutes or wait days for approval do not fit request-response web servers. Durable execution engines and background workers became the way to run them, along with deployment practices that do not break runs in progress.

In plain words first
Work that survives restarts

Some agent runs take minutes or wait days for a person. Durable execution saves progress after each step, so a crash, a deploy or a long wait does not lose the work, and each step runs effectively once. Deployment then decides where runs execute (request handlers, background workers, queues, scheduled jobs) and how to release new versions without breaking runs already in progress.

Hands-on · A streaming chat endpoint

The interactive shape is the most common. Three rules make it production-shaped: stream events (not just text) so the UI can show progress, keep session state outside the worker, and turn off proxy buffering so tokens are not held back:

import json, threading, time
import requests, uvicorn
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

api = FastAPI()
SESSIONS: dict[str, list[dict]] = {}                 # in production: Redis or a database, never worker memory

class ChatIn(BaseModel):
    session_id: str
    message: str

def agent_events(session_id: str, text: str):
    history = SESSIONS.setdefault(session_id, [])
    history.append({"role": "user", "content": text})
    if "A-1001" in text:                              # a real agent loop goes here (Chapters 6 and 7)
        yield {"type": "status", "text": "looking up your order"}
        yield {"type": "tool", "name": "get_order_status", "result": "A-1001 is shipped"}
        answer = "A-1001 has shipped and should arrive Thursday."
    else:
        answer = "You're welcome! Anything else?"
    for word in answer.split():
        yield {"type": "delta", "text": word + " "}
    history.append({"role": "assistant", "content": answer})
    yield {"type": "done", "turns_in_session": len(history)}

@api.post("/chat")
def chat(body: ChatIn):
    def sse():
        for event in agent_events(body.session_id, body.message):
            yield f"data: {json.dumps(event)}\n\n"         # Server-Sent Events framing
    return StreamingResponse(sse(), media_type="text/event-stream",
                             headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})

threading.Thread(target=uvicorn.run, args=(api,), kwargs={"port": 8792, "log_level": "warning"}, daemon=True).start()
time.sleep(1.5)

for turn in ("Where is A-1001?", "Thanks!"):
    with requests.post("http://127.0.0.1:8792/chat", json={"session_id": "s-42", "message": turn}, stream=True) as r:
        events = [json.loads(line[6:]) for line in r.iter_lines(decode_unicode=True) if line.startswith("data: ")]
    text = "".join(e["text"] for e in events if e["type"] == "delta").strip()
    print([e["type"] for e in events if e["type"] != "delta"], "|", text[:30], "| turns:", events[-1]["turns_in_session"])
What you should see
['status', 'tool', 'done'] | A-1001 has shipped and should  | turns: 2
['done'] | You're welcome! Anything else? | turns: 4

Server-Sent Events work through most load balancers and need no special client; WebSockets suit apps that also push from the client mid-answer, such as voice. The event types here (status, tool, delta, done) are a small version of what AG-UI standardizes (Lesson 16.29). Replace SESSIONS with Redis or a database table keyed by session, and any replica can serve the next turn.

Durable execution: survive the crash

A long agent run will meet a deploy, a crash, a timeout or a provider outage. Durable execution records each completed step in a database; after a failure the workflow resumes from the last completed step instead of starting over, so expensive or irreversible steps are not repeated. LangGraph's checkpointers do this for graph runs (the LangChain and LangGraph section). The same idea exists as general-purpose engines:

Engine Model
Temporal Workflows as code with deterministic replay; activities hold side effects. Widely used for business processes; integrations with the OpenAI Agents SDK, Pydantic AI and others
DBOS A library: decorate functions as workflows and steps; state checkpoints in Postgres (SQLite for development). No separate server
Restate, Inngest Durable functions and event-driven workflows
AWS Step Functions, Lambda durable functions (announced at re:Invent 2025: checkpointed steps, waits and callbacks for up to a year) Managed on AWS
Azure Durable Functions and Durable Task Managed on Azure; Microsoft Agent Framework hosts durable agents on it
Google Cloud Workflows Managed orchestration on Google Cloud

A crash, for real: the program below starts a refund workflow in a child process that dies after the refund call, then restarts and lets DBOS recover.

uv add dbos        # tested with dbos 3.3.0

import os, subprocess, sys, tempfile, textwrap

DB = os.path.join(tempfile.mkdtemp(), "dbos.sqlite")
APP = textwrap.dedent(f'''
    import os, sys
    from dbos import DBOS, SetWorkflowID
    DBOS(config={{"name": "shopkart-refunds", "system_database_url": "sqlite:///{DB}"}})   # Postgres in production

    @DBOS.step()
    def issue_refund(order_id: str) -> str:
        print("  calling the refund API", flush=True)
        return f"RF-{{order_id}}"

    @DBOS.step()
    def email_customer(order_id: str, refund_id: str) -> None:
        if sys.argv[1] == "crash":
            print("  process dies before emailing", flush=True)
            os._exit(1)                       # a real crash: no exception handling, no cleanup
        print(f"  emailing customer about {{refund_id}}", flush=True)

    @DBOS.workflow()
    def refund_workflow(order_id: str) -> str:
        refund_id = issue_refund(order_id)    # each step's result is checkpointed in the database
        email_customer(order_id, refund_id)
        return refund_id

    DBOS.launch()                             # on start-up, DBOS resumes any unfinished workflows
    if sys.argv[1] == "crash":
        with SetWorkflowID("refund-A-1002"):  # the workflow ID doubles as an idempotency key
            refund_workflow("A-1002")
    else:
        print("  result:", DBOS.retrieve_workflow("refund-A-1002").get_result())
''')
with open("refund_app.py", "w") as f:
    f.write(APP)
print("run 1:")
subprocess.run([sys.executable, "refund_app.py", "crash"])
print("run 2 (after restart):")
subprocess.run([sys.executable, "refund_app.py", "recover"])
What you should see
run 1:
  calling the refund API
  process dies before emailing
run 2 (after restart):
  emailing customer about RF-A-1002
  result: RF-A-1002

(DBOS also prints a few start-up log lines.) After the restart, the refund API was not called again: its result came from the checkpoint, and only the unfinished email step ran. Without durable execution, a naive retry would have refunded the customer twice.

Durable execution also gives you durable waits. A workflow can pause for a human decision for days without holding a thread or a process; the wait is a row in the database, and whichever process receives the decision resumes it:

import os, subprocess, sys, tempfile, textwrap
DB = os.path.join(tempfile.mkdtemp(), "dbos.sqlite")
APP = textwrap.dedent(f'''
    import sys, time
    from dbos import DBOS, SetWorkflowID
    DBOS(config={{"name": "shopkart-approvals", "system_database_url": "sqlite:///{DB}"}})

    @DBOS.step()
    def draft_refund(order_id: str) -> dict:
        print("  drafting refund for", order_id, flush=True)
        return {{"order_id": order_id, "amount_inr": 7499}}

    @DBOS.step()
    def issue_refund(draft: dict) -> str:
        print("  refund issued:", draft, flush=True)
        return "RF-" + draft["order_id"]

    @DBOS.workflow()
    def refund_with_approval(order_id: str) -> str:
        draft = draft_refund(order_id)
        DBOS.set_event("status", "waiting for approval")
        decision = DBOS.recv("approval", timeout_seconds=7 * 24 * 3600)   # durable wait: survives restarts
        if decision != "approve":
            return "rejected"
        return issue_refund(draft)

    DBOS.launch()
    mode = sys.argv[1]
    if mode == "start":
        with SetWorkflowID("refund-A-2001"):
            DBOS.start_workflow(refund_with_approval, "A-2001")
        print("  status:", DBOS.get_event("refund-A-2001", "status", timeout_seconds=10), flush=True)
        import os; os._exit(0)                                   # the process exits while the workflow waits
    elif mode == "approve":
        DBOS.send("refund-A-2001", "approve", topic="approval")
        print("  result:", DBOS.retrieve_workflow("refund-A-2001").get_result(), flush=True)
''')
open("approval_app.py", "w").write(APP)
print("day 1: start the workflow, then the server goes away")
subprocess.run([sys.executable, "approval_app.py", "start"])
print("day 3: a manager approves from another process")
subprocess.run([sys.executable, "approval_app.py", "approve"])
What you should see
day 1: start the workflow, then the server goes away
  drafting refund for A-2001
  status: waiting for approval
day 3: a manager approves from another process
  refund issued: {'order_id': 'A-2001', 'amount_inr': 7499}
  result: RF-A-2001

The first process exited while the workflow was waiting. The second process recovered it, skipped the already-checkpointed draft step, delivered the approval with DBOS.send, and the workflow finished. This is the pattern behind "approve in Slack tomorrow": the approval button calls send with the workflow ID. Temporal (signals), Step Functions (task tokens), Durable Functions (external events) and LangGraph (interrupt with a checkpointer) offer the same capability.

Idempotency completes the picture. Steps can still run twice (a step that crashed midway is retried), so every side effect needs an idempotency key the downstream system honors, such as the workflow ID plus step name sent as an Idempotency-Key header to a payments API.

Here is the failure it prevents, the most common way agents double-charge or double-refund: the call succeeds, but the response is lost, so the caller retries:

import random

class PaymentsAPI:
    """A downstream API that honors Idempotency-Key, as Stripe, Razorpay and most payment APIs do."""
    def __init__(self):
        self.refunds, self.seen = [], {}
    def refund(self, order_id: str, amount: int, idempotency_key: str | None = None) -> str:
        if idempotency_key in self.seen:
            return self.seen[idempotency_key]                      # replay: same answer, no new refund
        refund_id = f"RF-{len(self.refunds) + 1:03d}"
        self.refunds.append((order_id, amount))
        if idempotency_key:
            self.seen[idempotency_key] = refund_id
        return refund_id

def flaky_call(api: PaymentsAPI, key: str | None, attempt: int) -> str:
    rid = api.refund("A-1002", 7499, idempotency_key=key)
    if attempt == 0:
        raise TimeoutError("response lost on the way back")       # the refund happened; the reply did not arrive
    return rid

for key in (None, "wf-refund-A-1002:issue_refund"):
    api = PaymentsAPI()
    for attempt in range(3):
        try:
            rid = flaky_call(api, key, attempt)
            break
        except TimeoutError:
            continue
    print(f"key={key!s:32} result {rid}, refunds issued: {len(api.refunds)}")
What you should see
key=None                             result RF-002, refunds issued: 2
key=wf-refund-A-1002:issue_refund    result RF-001, refunds issued: 1

Without a key, the retry created a second refund. With a key built from the workflow ID and step name, the API recognized the retry and returned the first result. If a downstream system does not support idempotency keys, keep your own record of completed side effects and check it before calling.

Releasing safely

Technique How
Shadow Run the new version on copies of real traffic; compare outputs and costs; users see only the old version
Canary Send 1 to 10% of traffic to the new version; watch online evals, errors, cost; then ramp
Feature flags Switch prompts, models or tools per tenant without a deploy
A/B test Measure business outcomes (resolution rate, CSAT) between versions with enough traffic for significance
Rollback Keep the previous release (code, prompts, model aliases, index) one switch away
Version pinning for in-flight runs Long runs started on version N finish on N, or migrate deliberately; durable state schemas must stay compatible

Automate the canary decision (canary analysis), so a bad release rolls back at 3 a.m. without waiting for someone to notice. Compare the canary with the baseline on quality, latency and cost, and require enough traffic before deciding:

import math

def two_proportion_z(fail_a: int, n_a: int, fail_b: int, n_b: int) -> float:
    pa, pb = fail_a / n_a, fail_b / n_b
    pooled = (fail_a + fail_b) / (n_a + n_b)
    se = math.sqrt(pooled * (1 - pooled) * (1 / n_a + 1 / n_b))
    return (pb - pa) / se

def canary_verdict(baseline: dict, canary: dict) -> str:
    """Compare the canary with the baseline on the signals that matter; any clear regression rolls back."""
    reasons = []
    z = two_proportion_z(baseline["judge_fail"], baseline["runs"], canary["judge_fail"], canary["runs"])
    if z > 2.0:
        reasons.append(f"judge fail rate up (z={z:.1f})")
    if canary["p95_s"] > baseline["p95_s"] * 1.2:
        reasons.append(f"p95 latency {baseline['p95_s']}s -> {canary['p95_s']}s")
    if canary["cost_per_run"] > baseline["cost_per_run"] * 1.15:
        reasons.append(f"cost/run ${baseline['cost_per_run']} -> ${canary['cost_per_run']}")
    if canary["runs"] < 500:
        return "WAIT: not enough canary traffic yet"
    return "ROLL BACK: " + "; ".join(reasons) if reasons else "PROMOTE to 50%"

baseline = {"runs": 9_000, "judge_fail": 540, "p95_s": 9.8, "cost_per_run": 0.042}
print(canary_verdict(baseline, {"runs": 300, "judge_fail": 30, "p95_s": 9.9, "cost_per_run": 0.041}))
print(canary_verdict(baseline, {"runs": 1_000, "judge_fail": 63, "p95_s": 10.1, "cost_per_run": 0.043}))
print(canary_verdict(baseline, {"runs": 1_000, "judge_fail": 95, "p95_s": 12.4, "cost_per_run": 0.044}))
What you should see
WAIT: not enough canary traffic yet
PROMOTE to 50%
ROLL BACK: judge fail rate up (z=4.3); p95 latency 9.8s -> 12.4s

The second canary's fail rate (6.3%) is slightly above the baseline's (6.0%), but well within noise, so it promotes. The third (9.5%) is more than four standard errors worse. Tools such as Argo Rollouts and Flagger run this analysis loop for Kubernetes deployments; for prompt and model changes behind feature flags, a scheduled job like this one, reading from your observability store, does the same.

Industry practice
How production teams deploy agents

Teams with mature agent operations separate the agent's "brain" (prompts, model choices, tools) from its infrastructure, so that most changes ship as configuration through the eval gate, not as code deploys. They default to asynchronous, durable execution for anything longer than a few seconds, make every side effect idempotent, and rehearse failure: kill workers mid-run in staging and confirm runs complete correctly.

In production
Deployment problems that bite agents specifically
  • Timeouts at the load balancer: a 60-second idle timeout kills long agent turns mid-stream. Stream progress events, or move long work to a job with polling or webhooks.
  • State in worker memory: a deploy or autoscale drops conversations. Keep sessions and checkpoints in a database from the first release.
  • Retries that repeat side effects: a retried request refunds twice. Idempotency keys on every write (this lesson).
  • Rate limits during traffic spikes: every worker retries at once. Client-side rate limiting, backoff with jitter, and a fallback deployment through the gateway.
  • Model or prompt changes shipped like config, without evals: the most common cause of quality incidents. Put every behavior change through the same gate as code (Lesson 14.147).

Solutions

SolutionP1 · Deploys and running work

With durable execution (checkpoints or a workflow engine), runs resume from their last completed step on new workers. Without, they are lost or must restart from scratch, possibly repeating side effects.

SolutionB1 · Progressive delivery

A regression hits everyone. Use canaries or gradual rollouts with automated checks and rollback (Lesson 14.147).

SolutionD1 · Checkpoint compatibility

Checkpoints reference nodes and state shapes of the old version. Keep old node names during migrations, version graphs, and drain or migrate pending runs.

SolutionM1 · A migration plan

Deploy code that reads both keys, migrate pending checkpoints or let them finish, then remove the old key in a later release. Test resume from old checkpoints.

Worked answer. Execution where progress is persisted so work survives crashes, restarts and long waits: checkpointed graphs (Lesson 14.103) or workflow engines such as Temporal.
