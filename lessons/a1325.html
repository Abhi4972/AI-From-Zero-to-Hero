In plain words first
The idea in one line

Invocation is an authority decision followed by a relevance decision. A good description helps the model choose; a good policy decides whether that choice is allowed.

Terms you'll hear
Term What people say What it actually means
Explicit invocation "Slash command" An actor supplies skill identity directly, subject to policy
Implicit invocation "The model chooses" A router selects from eligible catalog metadata based on task context
User-invocable "Humans can use it" A host-specific menu or direct-invocation property, not a core field
Model-invocable "The agent can use it" Eligibility for implicit model selection under host policy
Invocation adapter "Frontmatter parser" Code that maps a host's fields and APIs into a declared policy model
Near miss "Hard negative" A non-triggering request that resembles a skill's intended inputs
Abstention "No skill selected" A deliberate routing result when evidence is absent or ambiguous

The problem

In plain words first

A skill can be started in several ways: a person types its name, the model decides it fits the request, an application calls it on purpose, or another skill asks for it. Each way needs its own rules. When the model chooses, it is really classifying the request: which skill, if any, fits best? A good router must be allowed to say "none of them", and it must first drop skills that are not allowed for this caller before picking the best one. Testing a router only with obvious examples hides its mistakes; the useful test cases are near misses, requests that share words with a skill but belong elsewhere. This lesson scores three routers (word overlap, embeddings and a small language model) on the same test set with near misses, shows why the eligibility check must come first, and fixes descriptions to improve the score.

You install a database-migration skill. The user can run it by name, but the model also sees its description and selects it when someone asks a general database question. The skill then proposes a schema change for a task that only needed an explanation.

You add user-invocable: false, expecting to block people from running it manually. In another runtime, that field is ignored. You add disable-model-invocation: true, expecting the skill to disappear entirely. In the runtime that understands it, the user can still invoke it explicitly.

Nothing is wrong with the field names. The model is wrong. "User can see it," "model can select it," "application can preload it," and "tools inside it can execute" are separate facts. A single boolean called invocable cannot express them.

Routing has a second failure mode. If descriptions are vague, several skills become plausible. If descriptions are stuffed with keywords, unrelated tasks trigger them. The catalog is a probabilistic interface: compact enough to fit, specific enough to route.

Idea 1 · Five channels can start the lifecycle

Actor Invocation shape Typical use Main risk
Human user Names a skill in the UI or prompt Deliberate workflow selection User expects availability or authority the host does not grant
Model or autonomous agent Selects a catalog entry from task context Automatic expert procedure False-positive routing
Application Activates or preloads a skill through runtime code Fixed product workflow Hidden coupling to one host
Another skill or subagent Requests an exact skill as a workflow dependency Composition Cycles, missing dependency, or context bleed
Evaluation harness Activates an exact skill under a fixed scenario Repeatable measurement Tests the skill while accidentally bypassing the production policy under study

The portable Agent Skills specification defines the package. It does not standardize one universal slash-command UI, implicit-routing flag, application API, or subagent lifecycle.

Idea 2 · The five invocation stages

Use these words precisely:

  • Eligible means policy permits this actor to request the skill.
  • Selected means the user named it or a router judged it relevant.
  • Activated means its instructions entered the working context.
  • Executing means the agent began model or tool work under those instructions.
  • Completed means the output met an independent success check.

A trace that records only skill_used=true hides the boundary where a failure happened.

Idea 3 · Human and model invocation form a 2x2 matrix

Human can invoke Model can invoke Mode Suitable examples
Yes Yes Shared Code explanation, test planning, documentation review
Yes No Human-only Publish preparation, billing export, destructive cleanup plan
No Yes Model-only Internal style guide, domain reference, automatic support procedure
No No Disabled or application-only Staged rollout, deprecated package, programmatic preload

The matrix is a policy model, not standard YAML.

One current host uses disable-model-invocation: true for the human-only row and user-invocable: false for the model-only row. The default is both. Another host uses agents/openai.yaml with allow_implicit_invocation: false to keep explicit invocation while disabling implicit selection. These are runtime adapters. Unknown hosts may ignore them.

The confusing detail matters: user-invocable: false does not mean "the model cannot use this." It removes direct user invocation in the host that defines it. disable-model-invocation: true does not mean "the skill is disabled." It removes model-initiated selection while keeping explicit user access.

Idea 4 · Explicit invocation is identity-first

An explicit invocation supplies identity directly:

/release-readiness v2.4.0

or:

release-readiness check v2.4.0 without publishing

Current Codex interfaces document /skills for selection and plain skill names in requests for explicit invocation. Claude Code documents /skill-name and host-specific argument expansion. The exact syntax, menu visibility, quoting rules, and variable expansion belong to the host.

An explicit request still passes policy. Naming a skill should not bypass missing permissions, workspace constraints, approval gates, or runtime isolation.

Idea 5 · Implicit invocation is description-first

For implicit routing, the model initially sees catalog metadata rather than the full body. The description is therefore the skill's routing interface.

Weak:

description: Helps with releases.

Over-broad:

description: Use for release, version, package, build, deploy, publish, tag, changelog, GitHub, CI, or software tasks.

Bounded:

description: Inspect an already prepared release candidate and produce a readiness report. Use when the user asks whether a version, tag, package, or image is ready to publish; do not use for ordinary build failures or feature development.

The bounded version contains:

  1. Capability: inspect a prepared candidate.
  2. Output: readiness report.
  3. Positive boundary: asks whether a release artifact is ready.
  4. Negative boundary: ordinary builds and development are out of scope.

Negative boundaries are useful when two nearby skills share vocabulary. They are not a replacement for near-miss evals.

Idea 6 · Routing is classification with an abstain option

For a skill s and request x, imagine a router score:

score(s, x) = capability_match + trigger_match + context_match - exclusion_match - ambiguity_penalty

The exact scoring may be an LLM decision rather than arithmetic. The engineering principle still holds: selection should beat a threshold and a competing skill. When evidence is weak, abstain.

For high-impact skills, implicit routing may be inappropriate even with a strong description. Use human-only policy when the cost of a false positive exceeds the convenience of automatic selection.

Idea 7 · Eligibility must precede ranking

Do not score every discovered skill, choose the strongest match, and check that one skill's policy afterward. A blocked top match would incorrectly prevent an eligible lower-scored candidate from being considered.

Use this order for implicit routing:

  1. Filter discovered skills by the requesting actor and the active host adapter.
  2. Score only the eligible candidates.
  3. Select the strongest eligible match if it clears the threshold and ambiguity rules.
  4. Abstain when no candidate is eligible or no eligible score is strong enough.

Suppose incident-triage scores 0.80 but its host extension disables model invocation. incident-review scores 0.55 and allows model invocation. The router should evaluate incident-review as the best eligible candidate. It should not choose incident-triage, deny it, and stop.

This ordering also keeps policy changes from altering the meaning of a relevance score. Eligibility defines the selection set. Relevance ranks that set.

Idea 8 · Routing evals need near misses

Positive cases prove recall:

{"prompt":"Is version 2.4.0 ready to publish?","expected":"release-readiness"}

Clear negatives prove basic precision:

{"prompt":"Explain rotary position embeddings.","expected":null}

Near misses expose boundary quality:

{"prompt":"Why did today's package build fail?","expected":"build-diagnostics"}

The near miss shares package and build with the release skill but belongs elsewhere. A routing set made only of obvious positives and unrelated negatives will overstate quality.

Idea 9 · Arguments have three representations

An invocation argument crosses several boundaries:

At each boundary, preserve intent without treating text as code.

  • The host parser decides command syntax and quoting.
  • The skill receives bound text or variables according to host rules.
  • The instructions validate required values and defaults.
  • A tool call converts values to a typed schema and revalidates them.

Do not interpolate raw arguments into shell commands. Prefer a script invoked with an argument vector or a typed MCP tool.

Idea 10 · Application invocation is explicit orchestration

A product can activate a skill because its workflow already knows the task type. For example, a pull-request review service can preload pull-request-risk-review after the user presses Review.

This removes routing uncertainty but creates a dependency on the runtime API. Keep that adapter outside the portable body:

The skill should remain intelligible when opened by a different compliant client.

Idea 11 · Skill-to-skill invocation is a tool-like edge

Suppose release-readiness asks for security-change-review when dependency files changed.

The caller should provide:

  • the target skill identity;
  • a bounded task and artifact paths;
  • the expected response contract;
  • the reason for invocation;
  • a fallback if unavailable;
  • a maximum depth or cycle rule.
{
  "target_skill": "security-change-review",
  "task": "Review dependency changes in the candidate diff",
  "inputs": ["artifacts/release.diff"],
  "expected": "risk-report.json",
  "max_depth": 2
}

The second skill is not pasted blindly into the first. The host decides how to activate it and whether it shares context, runs in a fork, or returns through a tool result.

Idea 12 · Context lifecycle is host-specific

After activation, the skill body may remain in the conversation, be summarized during compaction, or run in a delegated context. Tool allowances may last one turn while instructions persist longer. A subagent may receive the skill without the parent's entire history.

Do not write a skill that depends on an invisible lifetime assumption. Put durable outputs in files or typed state, make re-entry safe, and state what must be reloaded after interruption.

On resume, read `artifacts/release-readiness.json` if it exists.
Revalidate the candidate commit before continuing.
Do not repeat an external write whose idempotency key is already recorded.
The same idea as a formula

Routing with abstention. For eligible skills E(a) (allowed for actor a) and request x,

s\*=args∈E(a)max​score(s,x),activate s\*⟺score(s\*,x)≥τ∧score(s\*,x)−score(s2​,x)≥δ,
where s2​ is the runner-up. Otherwise abstain. The margin δ refuses ambiguous cases; the threshold τ refuses weak ones.

The lesson's overlap score is the Jaccard index of word sets, J(x,s)=∣Wx​∩Ws​∣/∣Wx​∪Ws​∣. The embedding score is the cosine of normalized vectors, cos(ex​,es​)=ex​⋅es​.

Metrics that matter. Over a labelled set with positives P and negatives N: recall =correct activations/∣P∣; wrong activations count both false positives on N and the wrong skill on P; abstention accuracy =correct abstains/∣N∣. A wrong activation is usually worse than an abstain, because the agent then follows the wrong procedure confidently.

Worked example
Scoring one near miss by hand
  • Request: "Why did today's package build fail?" The words are {why, did, today, s, package, build, fail}: 7 words.
  • build-diagnostics description plus name shares {build, fail}... but "fails" and "failed" are different tokens from "fail", so only {build} matches out of a union of about 25 words: J≈1/25=0.04, below the 0.12 threshold. The overlap router abstains.
  • The embedding router does not need the same word: "build fail" and "a failed build" have close vectors, so it picks build-diagnostics correctly.
  • The opposite case: "Is the release notes draft ready to publish?" shares "ready" and "publish" with release-readiness, and every router picks it, although the user wants the changelog skill. Better descriptions, not a better router, fix this.
Check your mental model
  • ✗ "The strongest match should always be activated."
    ✓ Activate only above a threshold and a margin; otherwise abstain.
  • ✗ "Check permissions after choosing the best skill."
    ✓ Filter by eligibility first, then rank; a blocked top match must not hide an allowed one.
  • ✗ "An LLM router is always more accurate than embeddings."
    ✓ A small model can be worse; measure on your own near misses.
  • ✗ "High accuracy on obvious examples means routing works."
    ✓ Only near misses and negatives reveal the boundaries.

Three routers on one eval with near misses

Four skills, ten labelled requests (5 positives, 3 near misses, 2 clear negatives). Routers: the lesson's route_request with word overlap (threshold 0.12), bge-small-en-v1.5 cosine with threshold 0.62 and margin 0.02, and Qwen2.5-0.5B-Instruct asked to name a skill or "none". About 20 seconds (model load plus ten short generations).

# A routing eval with near misses, scoring three routers on the same catalog:
# the lesson's word-overlap router, an embedding router (bge-small), and a small LLM router (Qwen2.5-0.5B).
import torch
from main import SkillMetadata, InvocationPolicy, InvocationRequest, CorePolicyAdapter, Actor, route_request
from sentence_transformers import SentenceTransformer
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as tlog
tlog.set_verbosity_error()

SKILLS = [SkillMetadata("release-readiness", "Check whether a release candidate is ready to publish. Use when asked if a version or tag can ship."),
          SkillMetadata("build-diagnostics", "Diagnose a failed build or CI run from its logs. Use when a build, compile or pipeline step fails."),
          SkillMetadata("incident-triage", "Triage a live production incident and propose next actions. Use when a service is down or degraded now."),
          SkillMetadata("changelog-writer", "Draft a changelog from merged PRs. Use when release notes or a changelog are requested.")]
EVAL = [("Is version 2.4.0 ready to publish?", "release-readiness"),                 # positives
        ("Can we ship the v3 tag today?", "release-readiness"),
        ("The CI pipeline failed on the compile step, why?", "build-diagnostics"),
        ("Checkout is returning 500s for everyone right now", "incident-triage"),
        ("Write release notes for the merged PRs since 2.3", "changelog-writer"),
        ("Why did today's package build fail?", "build-diagnostics"),                 # near misses
        ("Is the release notes draft ready to publish?", "changelog-writer"),
        ("Write a postmortem for last week's outage", None),
        ("Explain rotary position embeddings.", None),                                 # clear negatives
        ("What's a good name for a cat?", None)]

core = CorePolicyAdapter(InvocationPolicy(model_threshold=0.12))
def overlap_router(q):
    d = route_request(SKILLS, InvocationRequest(Actor.MODEL, q), core); return d.skill_name if d.activated else None

emb = SentenceTransformer("BAAI/bge-small-en-v1.5")
E = emb.encode([s.description for s in SKILLS], normalize_embeddings=True)
def embedding_router(q, tau=0.62, margin=0.02):
    sims = E @ emb.encode([q], normalize_embeddings=True)[0]; order = sims.argsort()[::-1]
    best, second = sims[order[0]], sims[order[1]]
    return SKILLS[order[0]].name if best >= tau and best - second >= margin else None   # abstain when weak or ambiguous

M = "Qwen/Qwen2.5-0.5B-Instruct"; tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
CATALOG = "\n".join(f"- {s.name}: {s.description}" for s in SKILLS)
def llm_router(q):
    msgs = [{"role": "system", "content": "Pick the one skill that fits the request, or answer none. Reply with the skill name only.\n" + CATALOG},
            {"role": "user", "content": q}]
    ids = tok.apply_chat_template(msgs, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad(): out = llm.generate(ids, max_new_tokens=10, do_sample=False)
    text = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip().lower()
    return next((s.name for s in SKILLS if s.name in text), None)

ROUTERS = {"overlap": overlap_router, "embedding": embedding_router, "llm-0.5B": llm_router}
results = {name: [r(q) for q, _ in EVAL] for name, r in ROUTERS.items()}
print(f"{'request':<50}{'expected':<21}" + "".join(f"{n:<21}" for n in ROUTERS))
for i, (q, exp) in enumerate(EVAL):
    cells = "".join(f"{(results[n][i] or 'abstain') + ('' if results[n][i] == exp else ' ✗'):<21}" for n in ROUTERS)
    print(f"{q[:48]:<50}{exp or 'abstain':<21}{cells}")
print()
for n in ROUTERS:
    got = results[n]
    tp = sum(g == e and e is not None for g, (_, e) in zip(got, EVAL)); fp = sum(g is not None and g != e for g, (_, e) in zip(got, EVAL))
    pos = sum(e is not None for _, e in EVAL); acc = sum(g == e for g, (_, e) in zip(got, EVAL))
    print(f"{n:<10} accuracy {acc}/{len(EVAL)}  recall {tp}/{pos}  wrong activations {fp}  correct abstains {sum(g is None and e is None for g, (_, e) in zip(got, EVAL))}/3")

Reading this output

Every router gets the easy cases. All three pick release-readiness for "Is version 2.4.0 ready to publish?", build-diagnostics for the failed CI compile step, and abstain on rotary embeddings and cat names.

They fail in different places. Word overlap abstains on "Why did today's package build fail?" because "fail" and "failed" are different words, and on the outage message, which shares no words with the incident description. The embedding router handles the build question but also misses the outage (its best score is below the threshold).

Near misses catch everyone. "Is the release notes draft ready to publish?" goes to release-readiness in all three: "ready to publish" is in that description. The postmortem request wrongly fires incident-triage for both meaning-based routers.

The small LLM is the worst router here. Qwen2.5-0.5B sends the outage to release readiness, misses the changelog request and fires on the postmortem: 6/10 with three wrong activations. Its answers also changed when one description was reworded ("pull requests" to "PRs"), which is typical of small models. Larger models do much better, but the point stands: measure the router you actually ship, and re-run the eval after every description change.

Eligibility before ranking, then better descriptions

This block continues from the one above. With the lesson's ExtensionPolicyAdapter, incident-triage has disable-model-invocation: true: compare routing that filters first with routing that ranks first. Then three descriptions are rewritten with explicit boundaries and the embedding router is evaluated again. A few seconds.

# Continues from the block above. (1) Eligibility must come before ranking. (2) Fix a boundary, re-run the eval.
from main import ExtensionPolicyAdapter
lib = [SkillMetadata("incident-triage", "Triage a live production incident and propose next actions. Use when a service is down now.",
                     {"disable-model-invocation": True}),                      # humans only: paging people is consequential
       SkillMetadata("incident-review", "Review an incident timeline and list follow-ups. Use when a service incident needs review.")]
ext = ExtensionPolicyAdapter(InvocationPolicy(model_threshold=0.1))
q = "A service incident is happening now, propose next actions"
right = route_request(lib, InvocationRequest(Actor.MODEL, q), ext)
best = max(lib, key=lambda s: __import__("main").relevance_score(q, s))     # the wrong order: rank first, check after
ok, why = ext.allows(best, Actor.MODEL)
print(f"eligibility first : activated={right.activated} skill={right.skill_name} score={right.score}")
print(f"rank first        : top={best.name} -> allowed={ok} ({why}) -> abstain, although an eligible skill matched")
human = route_request(lib, InvocationRequest(Actor.HUMAN, q, explicit_name="incident-triage"), ext)
print(f"human types /incident-triage : activated={human.activated} ({human.reason})\n")

# The two near misses failed because descriptions overlap. Sharpen the boundaries and measure again.
SKILLS[0] = SkillMetadata("release-readiness", "Check whether a software version or tag passes release checks. Use when asked if a version can ship. Not for writing notes.")
SKILLS[2] = SkillMetadata("incident-triage", "Triage a live outage happening now: errors, 500s, downtime. Not for postmortems of past incidents.")
SKILLS[3] = SkillMetadata("changelog-writer", "Draft or review changelogs and release notes from merged PRs, including whether a notes draft is ready.")
E = emb.encode([s.description for s in SKILLS], normalize_embeddings=True)
after = [embedding_router(q) for q, _ in EVAL]
for (q, exp), b, a in zip(EVAL, results["embedding"], after):
    if b != a: print(f"{q[:48]:<50} {b or 'abstain'} -> {a or 'abstain'} ({'right' if a == exp else 'wrong'})")
print(f"embedding router accuracy: {sum(g == e for g, (_, e) in zip(results['embedding'], EVAL))}/10 -> {sum(g == e for g, (_, e) in zip(after, EVAL))}/10")

Build · Why core and extension adapters are separate

code/main.py implements policy and routing as separate adapters.

The model includes:

  • Actor for human, model, autonomous agent, application, skill, and harness callers;
  • SkillMetadata for routing identity;
  • InvocationPolicy for the human/model matrix;
  • InvocationRequest and InvocationDecision for traceable inputs and outcomes;
  • CorePolicyAdapter for portable behavior with no host extensions;
  • ExtensionPolicyAdapter for recognized runtime fields;
  • build_invocation_matrix(policy) for the 2x2 view;
  • route_request(skills, request, adapter) for eligibility filtering before relevance ranking, selection, and denial.

Run it:

cd phases/13-tools-and-protocols/25-skill-invocation-and-routing
python3 code/main.py
npx tsx code/main.ts
python3 -m unittest discover -s code/tests -v

The demo prints one matrix and decisions for explicit human, implicit model, autonomous-agent, application, skill-composition, and harness channels. Its extension-adapter results show a blocked top lexical match being removed before an eligible alternative is ranked. It also includes exact-name allowlists. No model API is required. The deterministic router exists to make policy boundaries inspectable, not to claim that lexical matching reproduces production model routing.

If one parser assigns meaning to every observed frontmatter field, it silently promotes runtime conventions into a fake standard. Separate adapters force the caller to name which host semantics are active.

The CorePolicyAdapter uses only application-supplied policy. The ExtensionPolicyAdapter recognizes an explicit set of host fields and records which field changed the decision.

Use it: the same idea with real libraries

Write an invocation contract before publishing a skill:

actors:
  human: allow
  model: deny
  application: allow
  skill: deny
explicit_name: release-readiness
arguments:
  candidate: required
  publish: fixed_false
ambiguity: ask_user
missing_dependency: stop
context:
  durable_state: artifacts/release-readiness.json
  max_composition_depth: 2

This contract is design documentation for adapters and tests. It is not portable SKILL.md frontmatter unless a standard explicitly adopts it.

Break it on purpose

A team's routing eval has 50 positive prompts, each copied from a skill's own description with small rewordings, and 10 negatives about cooking. The router scores 98%. In production users complain that the wrong skill fires. What was wrong with the eval? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Hosts route with the model itself. Claude, Codex, Copilot and similar hosts put skill names and descriptions in context and let the main model decide; there is no separate router you can tune, so the description is your lever.
  • Explicit invocation (a slash command or $skill-name) and human-only flags such as Claude Code's disable-model-invocation and Codex's per-skill policy exist for consequential skills.
  • Application invocation: agent SDKs (Claude Agent SDK, OpenAI Agents SDK) let code load a named skill explicitly, which skips routing.
  • Routing evals in production replay real anonymized requests, including near misses, against the target host and model; results differ between models, so re-run them when the model changes.
  • On your laptop: embedding routers with bge-small run in milliseconds on the CPU; a 0.5B model is a poor router, while a 4-bit 7B model on the RTX 4060 is much better but slower.

Sources: Agent Skills specification, Codex skills docs, Anthropic Agent Skills best practices.

Recap
What to keep from this lesson
  • Several channels start a skill; each has its own policy.
  • Explicit invocation is by exact name; implicit invocation is a classification with an abstain option.
  • Filter by eligibility, then rank, then apply a threshold and a margin.
  • Evaluate with positives, near misses and negatives, on the real host and model.
  • Most routing errors are fixed by sharper descriptions with stated boundaries.

Ship it

This lesson produces the skill-invocation-router bundle. It includes an invocation-model reference, an example host policy, and a non-executing CLI that evaluates one human, model, autonomous-agent, application, skill-composition, or harness request and returns a JSON decision with channel, adapter, score, and reason.

The one-request CLI is a policy probe, not a full trigger evaluation. Use the labeled positive and near-miss design in Lesson 13.27 to compute confusion counts, precision, recall, and repeated-run stability.

Exercises

  1. Create all four rows of the human/model matrix and write one legitimate use case for each.
  2. Add application-only activation to CorePolicyAdapter. Prove that human and model callers remain denied.
  3. Write ten near misses for a deployment skill. Each prompt must share vocabulary with the skill while belonging to a different workflow.
  4. Add an ambiguity margin between the top two routing scores. Return ask when the margin is too small.
  5. Add a maximum composition depth to skill-to-skill requests and detect a two-skill cycle.
  6. Run the same labeled set through core and extension adapters. Explain every changed decision.

Solutions

SolutionP1 · The meaning-based routers

The embedding router and the 0.5B LLM. "Postmortem", "outage" and "incident" are close in meaning, so the request lands near incident-triage in embedding space, above the threshold, and the small model reads "outage" and picks the incident skill. Only the word-overlap router abstains, and only because the request shares almost no exact words with the description. Meaning-based routers need the boundary written down ("live outage happening now", "not for postmortems"), or a separate postmortem skill, to tell the two apart.

SolutionB1 · An eval that cannot fail

It tested nothing hard. Prompts copied from the descriptions share their exact words, so any router matches them, and cooking negatives share nothing, so any router abstains. There are no near misses (requests that share words with one skill but belong to another, or to none), no ambiguous pairs between skills, no real user phrasing, and no check on the target host and model. A 98% score on that set says nothing about the boundaries where production errors happen.

A useful eval samples real (anonymized) requests, adds near misses for every pair of similar skills and for adjacent out-of-scope tasks, reports wrong activations separately from abstains, and runs on the same host and model as production, again whenever either changes.
