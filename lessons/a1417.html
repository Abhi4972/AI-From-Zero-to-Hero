The problem

In plain words first

Calling a model's API gives you one reply. Everything that makes an agent useful (running tools, connecting to MCP servers, saving the conversation, letting a helper agent do part of the work, stopping dangerous actions) you have to build yourself. The Claude Agent SDK packages the harness that Claude Code uses as a library. It brings built-in tools (read and edit files, run shell commands, search, fetch web pages), subagents (helpers with their own fresh context that return only their result), a session store for conversations, and hooks: your own functions that run at fixed moments, for example just before a tool runs, and can block it. This lesson builds a miniature harness in plain Python, measures what subagents save and lose with a real small model, and exercises the real SDK's hook and tool interfaces.

A raw LLM API gets you one round-trip. A production agent needs tool execution, MCP servers, lifecycle hooks, subagent spawning, session persistence, trace propagation. Claude Agent SDK ships this shape as a library — the same harness Claude Code uses, exposed for custom agents.

Idea 1 · Client SDK vs Agent SDK

  • Client SDK (anthropic). Raw Messages API. You own the loop, the tools, the state.
  • Agent SDK (claude-agent-sdk). Built-in tool execution, MCP connections, hooks, subagent spawning, session store. The Claude Code loop as a library.

Idea 2 · Built-in tools

The SDK ships 10+ tools out of the box: file read/write, shell, grep, glob, web fetch, more. Custom tools register via the standard tool-schema interface.

Idea 3 · Subagents

Two purposes documented by Anthropic:

  1. Parallelization. Run independent work concurrently. "Find the test file for each of these 20 modules" is 20 parallel subagent tasks.
  2. Context isolation. Subagents use their own context window; only results return to the orchestrator. The orchestrator's budget is preserved.

Python SDK recent additions: list_subagents(), get_subagent_messages() for reading subagent transcripts.

Idea 4 · Session store

Protocol parity with TypeScript:

  • append(session_id, message) — add a turn.
  • load(session_id) — restore conversation.
  • list_sessions() — enumerate.
  • delete(session_id) — with cascade to subagent sessions.
  • list_subkeys(session_id) — list subagent keys.

--session-mirror (CLI flag) mirrors the transcript to an external file as it streams, for debugging.

Idea 5 · Hooks

Lifecycle hooks you can register:

  • PreToolUse, PostToolUse — gate or audit tool calls.
  • SessionStart, SessionEnd — set up and tear down.
  • UserPromptSubmit — act on user input before the model sees it.
  • PreCompact — run before context compaction.
  • Stop — cleanup on agent exit.
  • Notification — side-channel alerts.

Hooks are how pro-workflow (Phase 14 curriculum reference) and similar systems add cross-cutting behavior.

Idea 6 · W3C trace context

OTel spans active on the caller propagate into the CLI subprocess via W3C trace context headers. The whole multi-process trace shows up as one trace in your backend.

Idea 7 · Claude Managed Agents

The hosted alternative (beta header managed-agents-2026-04-01). Long-running async work, built-in prompt caching, built-in compaction. Trade control for managed infrastructure.

Idea 8 · Where this pattern goes wrong

  • Subagent over-spawn. Spawning 100 subagents for 100 tiny tasks. Overhead dominates. Batch instead.
  • Hook creep. Every team adds hooks; startup time balloons. Review hooks quarterly.
  • Session bloat. Sessions accumulate; size grows. Use list_sessions + expiry policy.

The same idea as a formula

What the orchestrator reads. With d documents of L tokens each and q questions, an agent that reads everything for every question reads about

Tsingle​=q(dL+c)
tokens, where c is the question. With subagents that each return an s-token summary, the subagents read d(L+c′) once and the orchestrator reads only
Torch​=q(ds+c),s≪L.

What it can lose. The orchestrator can only answer what the summaries contain. If a summary keeps each relevant detail with probability κ, accuracy is bounded by about κ times what the full text allows; question-aware subagents raise κ at the cost of d⋅q subagent calls.

Worked example
The three designs below, by tokens and answers
  • Four documents of 530 to 720 tokens. One agent reading all of them for each of 4 questions: 9,770 prompt tokens, 2 of 4 right.
  • Four summarising subagents and an orchestrator: 3,265 tokens in total, of which the orchestrator read only 722 (≈7% of the single agent's reading). But 1 of 4 right: the summaries said "Four primitives: Agents, Tasks, Crews, and Tools", not "sequential versus hierarchical processes".
  • Sixteen question-aware subagents (one per document and question, yes or no): 10,244 tokens, about the same as the single agent, but 3 of 4 right, and each call reads one document, so the calls can run in parallel and no single context holds more than about 650 tokens.
  • Isolation is a choice about what the parent needs to see, not a free saving.
Check your mental model
  • ✗ "Subagents make an agent smarter."
    ✓ They keep the parent's context small; quality depends on what the subagent returns.
  • ✗ "A summary is as good as the document."
    ✓ A summary written without the question in mind drops what the question needs.
  • ✗ "Hooks are logging."
    ✓ A PreToolUse hook can deny a tool call and tell the model why.
  • ✗ "The harness is the model."
    ✓ It is the loop, tools, sessions and policies around any model.

PROMPT_TOKENS = []
def chat(text, max_new=60):
    ids = tok.apply_chat_template([{"role": "user", "content": text}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    PROMPT_TOKENS.append(ids.shape[1])
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=max_new, do_sample=False)
    return " ".join(tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).split())
def pick(text, n=4):
    """Read the answer as the most likely document number (one forward pass)."""
    ids = tok.apply_chat_template([{"role": "user", "content": text}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    PROMPT_TOKENS.append(ids.shape[1])
    with torch.no_grad():
        logits = llm(ids).logits[0, -1]
    return 1 + int(torch.stack([logits[tok.encode(str(k))[0]] for k in range(1, n + 1)]).argmax())

Reading this output

Reading everything costs three times as much and is only half right. One agent that reads all four documents for each question reads 9,770 prompt tokens and gets 2 of 4. A 0.5B model with 2,400 tokens of context in front of it is easily distracted.

Subagents cut the orchestrator's reading by more than ten times. Its four decisions read 722 tokens; with the four summarising calls the whole run read 3,265. The lesson's store shows the four subagent sessions linked under main, as the SDK's list_subkeys would.

But the summaries lost what the questions needed. The orchestrator answered "3" for every question (1 of 4): summaries such as "Four primitives: Agents, Tasks, Crews, and Tools" do not mention managers, tripwires or checkpoints. Context isolation is only as good as the result the subagent returns.

# Two follow-ups. (1) Question-aware subagents: each subagent reads one document and answers yes or no for
# one question; the orchestrator picks the document with the most confident yes. (2) The real Claude Agent
# SDK's hook contract: a PreToolUse hook and an in-process tool, called directly with the input shapes the
# Claude Code CLI sends. (Running the agent itself needs a logged-in claude CLI and paid model calls, so the
# loop is not run here.) Continues from the block above.
def p_yes(text):
    ids = tok.apply_chat_template([{"role": "user", "content": text}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    PROMPT_TOKENS.append(ids.shape[1])
    with torch.no_grad():
        logits = llm(ids).logits[0, -1]
    yes, no = logits[tok.encode("Yes")[0]], logits[tok.encode("No")[0]]
    return float(torch.sigmoid(yes - no))

Part 1 of 4 · Tool, ToolRegistry, Hooks, Turn, SessionStore, AgentRun

"""Claude Agent SDK harness shape in stdlib.

Built-in tools, subagents with isolated context, lifecycle hooks, session store.
Demonstrates how spawning subagents keeps the orchestrator's context bounded.
"""

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class Tool:
    name: str
    description: str
    fn: Callable[..., str]


class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, Tool] = {}

    def register(self, tool: Tool) -> None:
        self._tools[tool.name] = tool

    def get(self, name: str) -> Tool | None:
        return self._tools.get(name)

    def names(self) -> list[str]:
        return sorted(self._tools)


@dataclass
class Hooks:
    pre_tool_use: list[Callable[[str, dict[str, Any]], None]] = field(default_factory=list)
    post_tool_use: list[Callable[[str, str], None]] = field(default_factory=list)
    session_start: list[Callable[[str], None]] = field(default_factory=list)
    session_end: list[Callable[[str], None]] = field(default_factory=list)


@dataclass
class Turn:
    role: str
    content: str


class SessionStore:
    def __init__(self) -> None:
        self._sessions: dict[str, list[Turn]] = {}
        self._subkeys: dict[str, list[str]] = {}

    def append(self, session_id: str, turn: Turn) -> None:
        self._sessions.setdefault(session_id, []).append(turn)

    def load(self, session_id: str) -> list[Turn]:
        return list(self._sessions.get(session_id, []))

    def list_sessions(self) -> list[str]:
        return sorted(self._sessions)

    def delete(self, session_id: str) -> None:
        self._sessions.pop(session_id, None)
        for sub in self._subkeys.get(session_id, []):
            self._sessions.pop(sub, None)
        self._subkeys.pop(session_id, None)

    def list_subkeys(self, session_id: str) -> list[str]:
        return list(self._subkeys.get(session_id, []))

    def link_sub(self, parent: str, sub: str) -> None:
        self._subkeys.setdefault(parent, []).append(sub)


@dataclass
class AgentRun:
    session_id: str
    context_tokens: int = 0
    tool_calls: list[tuple[str, dict[str, Any], str]] = field(default_factory=list)
    output: str = ""

class Harness:
    def __init__(self, tools: ToolRegistry, hooks: Hooks,
                 store: SessionStore) -> None:
        self.tools = tools
        self.hooks = hooks
        self.store = store
        self._sub_counter = 0

    def _dispatch(self, tool_name: str, args: dict[str, Any]) -> str:
        for hook in self.hooks.pre_tool_use:
            hook(tool_name, args)
        tool = self.tools.get(tool_name)
        if tool is None:
            result = f"error: unknown tool {tool_name!r}"
        else:
            try:
                result = tool.fn(**args)
            except Exception as e:
                result = f"error: {type(e).__name__}: {e}"
        for hook in self.hooks.post_tool_use:
            hook(tool_name, result)
        return result

    def run_agent(self, session_id: str, prompt: str,
                  tool_calls: list[tuple[str, dict[str, Any]]],
                  parent_session: str | None = None) -> AgentRun:
        for hook in self.hooks.session_start:
            hook(session_id)
        if parent_session is not None:
            self.store.link_sub(parent_session, session_id)

        run = AgentRun(session_id=session_id)
        self.store.append(session_id, Turn("user", prompt))
        run.context_tokens += len(prompt.split())

        for tool_name, args in tool_calls:
            result = self._dispatch(tool_name, args)
            run.tool_calls.append((tool_name, args, result))
            self.store.append(session_id, Turn("tool", f"{tool_name}: {result}"))
            run.context_tokens += len(result.split())

        output = f"processed {len(tool_calls)} tools; session={session_id}"
        run.output = output
        self.store.append(session_id, Turn("assistant", output))
        run.context_tokens += len(output.split())

        for hook in self.hooks.session_end:
            hook(session_id)
        return run

    def spawn_subagents(self, parent_session: str,
                        tasks: list[tuple[str, list[tuple[str, dict[str, Any]]]]]
                        ) -> list[AgentRun]:
        runs: list[AgentRun] = []
        for prompt, tool_calls in tasks:
            self._sub_counter += 1
            sub_session = f"{parent_session}.sub{self._sub_counter:02d}"
            run = self.run_agent(sub_session, prompt, tool_calls,
                                 parent_session=parent_session)
            runs.append(run)
        return runs


def _read_file_demo(path: str) -> str:

def _list_dir_demo(path: str) -> str:

    print("\nspawn three subagents (context isolation)")
    sub_runs = harness.spawn_subagents(parent, [
        ("review module a", [("read_file", {"path": "a.py"})]),
        ("review module b", [("read_file", {"path": "b.py"})]),
        ("review module c", [("read_file", {"path": "c.py"})]),
    ])
    for run in sub_runs:
        print(f"  sub {run.session_id}  tokens={run.context_tokens}  "
              f"tool_calls={len(run.tool_calls)}")
    print(f"  orchestrator context tokens remain: "
          f"{orchestrator_run.context_tokens}")

    print("\nsession store")
    for sid in store.list_sessions():
        print(f"  {sid}  turns={len(store.load(sid))}")
    print(f"  subkeys of {parent}: {store.list_subkeys(parent)}")

    print("\nhooks fired")
    for line in hook_log[:10]:
        print(f"  {line}")
    print(f"  ... {len(hook_log)} hook events total")

    print("\ndelete parent (cascades to subs)")
    store.delete(parent)
    print(f"  remaining sessions: {store.list_sessions()}")

    print()
    print("subagent results return to orchestrator; orchestrator context is preserved.")

Industry practice
What's current (2024–2026)
  • Claude Agent SDK (Python and TypeScript, formerly the Claude Code SDK) runs the Claude Code harness in your process: built-in tools, MCP, subagents, hooks, permission modes, sessions with pluggable stores, skills and plugins.
  • Claude Managed Agents (public beta from April 2026) runs the harness on Anthropic's infrastructure for long-running work, trading control for operations you do not have to run.
  • Hooks in practice enforce policies (block writes outside a directory, require approval for network calls), run formatters and tests after edits, and record audit logs; the same hooks exist in the Claude Code CLI's settings.
  • On your laptop: the SDK needs the Claude Code CLI and an Anthropic account or API key; there is no local-model mode, so for local experiments use the patterns (subagents, hooks, sessions) with a framework that accepts OpenAI-compatible endpoints, as in lessons 14.77 and 14.16.

Recap
What to keep from this lesson
  • The Agent SDK is the loop, tools, sessions and policies around the model.
  • Subagents keep the parent's context small; they return only results.
  • What a subagent returns decides what the parent can answer.
  • PreToolUse hooks can deny a call and explain why.
  • Policies match intent, not strings.

Given a product domain and a list of MCP servers, scaffold a Claude Agent SDK app.

Produce:

1. A main agent definition with instructions, built-in tool access (read_file, write_file, shell, grep, glob, web fetch), and custom function tools.
2. Subagent spawner for parallelization and context isolation. Use when the orchestrator would otherwise blow its context budget.
3. Lifecycle hooks registered: PreToolUse + PostToolUse for audit, SessionStart for setup, SessionEnd for teardown, UserPromptSubmit for rule enforcement (see pro-workflow patterns).
4. Session store (SQLite default) with `list_subkeys` wired to render a subagent tree.
5. MCP server attachment for external tool/resource surfaces.
6. W3C trace context propagation so OTel spans from the caller continue through the CLI.

Hard rejects:

- Spawning a subagent for a single-tool task. Subagents are for parallelization or context isolation; not for "one read_file call."
- Hooks with synchronous expensive work. Hooks should be microseconds to milliseconds. Long work belongs in a subagent.
- Session stores without a cascade-delete policy. Orphaned subagent sessions bloat storage.

Refusal rules:

- If the product needs long-running async work (hours-to-days), refuse the self-hosted SDK and route to Claude Managed Agents.
- If the user asks for `--session-mirror` to a shared location, refuse. Session transcripts carry PII; mirror to per-user encrypted storage.
- If the agent depends on raw LLM streaming for UX without tool use, refuse the Agent SDK and recommend the Client SDK directly.

Output: `agent.py`, `tools.py`, `hooks.py`, `session.py`, `README.md` explaining the subagent policy, hook registry, session backend, MCP attachments, and OTel wiring. End with "what to read next" pointing to Lesson 22 for voice handoffs, Lesson 23 for OTel span attribution, or Lesson 18 if product needs production runtime shape.

Solutions

SolutionP1 · Subagents read less and answer worse

The subagent design reads far fewer tokens (the orchestrator's own reading falls from 9,770 to 722 tokens) but answers fewer questions correctly, 1 of 4 against 2 of 4, because summaries written without the questions in mind drop the details the questions ask about. Making the subagents question-aware restores accuracy (3 of 4) at about the single agent's token cost, spread over small, parallel calls.

SolutionB1 · String matching is not a policy

Ways around it: rm -r build/ or rm -fr build (different flags); find build -delete, python -c "import shutil; shutil.rmtree('build')" or git clean -fdx (different programs); a script written with the file-editing tool and then run (a different tool); and r''m -rf, variables or command substitution that only become rm when the shell runs them.

A sturdier policy decides by effect and scope rather than spelling: run the agent in a sandbox or container where the protected paths are read-only; use the SDK's permission modes and allowed_tools to deny shell access unless needed; when shell is allowed, parse the command and allow a short list of known-safe programs instead of blocking a list of bad strings; restrict writes to a working directory with a PostToolUse check of what changed; and require human approval for anything outside it.
