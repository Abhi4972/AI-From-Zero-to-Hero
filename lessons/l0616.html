What is real and what is a stand-in

The graphs and agents are real LangGraph and LangChain. The specialists' model is the lab rig (Lesson 14.92), and the supervisor chooses with a keyword rule where a real system would use a model with structured output.

import operator, re
from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, START, END
Why this came about

As single agents hit their limits, LangGraph added subgraphs, Send for parallel tasks and prebuilt supervisor patterns, so teams could compose larger systems from smaller graphs.

The problem: one graph for everything does not scale

ShopKart's support system grows: refunds, tracking, cancellations, returns, each with its own rules, owned by different teams. One graph with every node becomes hard to read, test and change. And some work is naturally parallel over a list that is only known at run time, such as a customer asking about three orders at once. LangGraph has three tools for this: subgraphs for composition, Send for dynamic fan-out, and multi-agent structures built from both.

In plain words first
Departments, a task list, and a team lead

Three ways to grow beyond one graph. A subgraph is a whole graph used as one node, like a department you hand a case to. Send hands out one task per item in a list, all running in parallel, with results gathered at the end (map-reduce). A supervisor is an agent whose tools are other agents, each with its own instructions and context. Each adds coordination cost, so the lesson ends with how to choose.

Idea 1 · A graph as a node

A compiled graph can be used as a node of another graph. The refunds team builds and tests its own small graph; the support desk's graph then adds it with one line, exactly as it would add a function. When the two graphs share state keys, the values pass in and out without any extra code.

class Case(TypedDict, total=False):
    msg: str
    order_id: str
    amount: int
    done: str

# The refunds team's graph: its own nodes, compiled and tested on its own.
def find_order(state):  return {"order_id": re.search(r"[A-Z]-\d{4}", state["msg"]).group(), "amount": 7999}
def refund(state):      return {"done": f"refund of INR {state['amount']:,} started for {state['order_id']}"}
rb = StateGraph(Case)
rb.add_node("find_order", find_order); rb.add_node("refund", refund)
rb.add_edge(START, "find_order"); rb.add_edge("find_order", "refund"); rb.add_edge("refund", END)
refunds = rb.compile()

# The support graph uses it as one node.
def triage(state) -> dict:  return {}
def route(state) -> Literal["refunds", "general"]:
    return "refunds" if "refund" in state["msg"].lower() else "general"
def general(state):        return {"done": "answered from the FAQ"}

sb = StateGraph(Case)
sb.add_node("triage", triage)
sb.add_node("refunds", refunds)                       # a compiled graph is a node
sb.add_node("general", general)
sb.add_edge(START, "triage"); sb.add_conditional_edges("triage", route)
sb.add_edge("refunds", END); sb.add_edge("general", END)
support = sb.compile()

for ns, update in support.stream({"msg": "Refund A-1077 please"}, stream_mode="updates", subgraphs=True):
    print(ns[0].split(":")[0] if ns else "(top)", "|", update)
What you should see
(top) | {'triage': None}
refunds | {'find_order': {'order_id': 'A-1077', 'amount': 7999}}
refunds | {'refund': {'done': 'refund of INR 7,999 started for A-1077'}}
(top) | {'refunds': {'msg': 'Refund A-1077 please', 'order_id': 'A-1077', 'amount': 7999, 'done': 'refund of INR 7,999 started for A-1077'}}

The refunds team compiled and tested its graph alone; the support graph added it with add_node like any function. Because both use the same state schema, the subgraph reads msg and writes order_id, amount and done directly. With subgraphs=True, the stream includes the subgraph's own steps, labeled with its namespace, so a trace shows inside the box. A subgraph inherits the parent's checkpointer, so an interrupt inside it pauses the whole run.

When the schemas differ, call the subgraph from a node and translate:

class Chat(TypedDict, total=False):
    customer_text: str
    answer: str

def call_refunds(state: Chat) -> dict:
    result = refunds.invoke({"msg": state["customer_text"]})     # translate in...
    return {"answer": result["done"]}                           # ...and out

cb = StateGraph(Chat)
cb.add_node("refunds", call_refunds); cb.add_edge(START, "refunds"); cb.add_edge("refunds", END)
print(cb.compile().invoke({"customer_text": "I need a refund on A-2001"}))
What you should see
{'customer_text': 'I need a refund on A-2001', 'answer': 'refund of INR 7,999 started for A-2001'}

Translation keeps each team's state private: the support graph never depends on find_order's keys, only on what the wrapper returns. This is Lesson 14.101's input and output schemas, applied between teams.

Idea 2 · Fan out with Send

A customer asks about three orders. The number of checks is known only at run time, so fixed parallel edges (Lesson 14.101) cannot express it. A router can return a list of Send objects instead of a node name: each one starts a run of a node with its own input.

from langgraph.types import Send

class Batch(TypedDict, total=False):
    msg: str
    statuses: Annotated[list, operator.add]                    # many workers write here: needs a reducer
    summary: str

ORDERS = {"A-1001": "shipped", "A-1002": "processing", "A-1003": "delivered"}

def fan_out(state):
    return [Send("check_one", {"order_id": oid}) for oid in re.findall(r"[A-Z]-\d{4}", state["msg"])]

def check_one(item: dict):                                     # gets its own small input, not the whole state
    return {"statuses": [f"{item['order_id']}: {ORDERS.get(item['order_id'], 'not found')}"]}

def summarize(state):
    return {"summary": "; ".join(sorted(state["statuses"]))}

bb = StateGraph(Batch)
bb.add_node("check_one", check_one); bb.add_node("summarize", summarize)
bb.add_conditional_edges(START, fan_out, ["check_one"])        # one check_one run per order, in parallel
bb.add_edge("check_one", "summarize"); bb.add_edge("summarize", END)
batch = bb.compile()
print(batch.invoke({"msg": "Where are A-1001, A-1002 and A-1003?", "statuses": []})["summary"])
What you should see
A-1001: shipped; A-1002: processing; A-1003: delivered

Three check_one runs, in parallel, each seeing only its order ID; their results were gathered by the reducer on statuses, and summarize ran once after all of them. This is map-reduce: one worker per item, then a step that combines them. The same shape serves "summarize each of 40 documents, then write one report" and "run each eval caselater · 14.131, then score".

Idea 3 · A supervisor and specialist agents

A supervisor decides who handles a request; each specialist is an agent with its own prompt and only the tools it needs:

from mockllm import start                                      # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.tools import tool
from langgraph.graph import MessagesState

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock")

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

@tool
def cancel_order(order_id: str) -> str:
    """Cancel a ShopKart order that has not shipped yet."""
    return f"{order_id} cancelled"

tracking_agent = create_agent(chat, tools=[get_order_status], system_prompt="You track orders.", name="tracking")
cancel_agent = create_agent(chat, tools=[cancel_order], system_prompt="You cancel orders that have not shipped.", name="cancellations")

class Desk(MessagesState):
    route: str

def supervisor(state):            # a model with structured output would choose here; a rule keeps it predictable
    text = state["messages"][-1].content.lower()
    return {"route": "cancellations" if "cancel" in text else "tracking"}

db = StateGraph(Desk)
db.add_node("supervisor", supervisor)
db.add_node("tracking", tracking_agent)
db.add_node("cancellations", cancel_agent)
db.add_edge(START, "supervisor")
db.add_conditional_edges("supervisor", lambda s: s["route"], ["tracking", "cancellations"])
db.add_edge("tracking", END); db.add_edge("cancellations", END)
desk = db.compile()

for q in ["Where is A-1002?", "Please cancel A-1002"]:
    out = desk.invoke({"messages": [{"role": "user", "content": q}]})
    print(f"{q:22} -> {out['route']:13} | {out['messages'][-1].content}")
What you should see
Where is A-1002?       -> tracking      | Here is what I found: A-1002 is processing
Please cancel A-1002   -> cancellations | Here is what I found: A-1002 cancelled

Each specialist is a create_agent graph used as a node (Idea 1), sharing the messages key, so its whole conversation is added to the desk's history. Specialists with few tools pick tools more reliably and have smaller prompts (Lesson 14.58), and each can be evaluated alone. The langgraph-supervisor package packages this shape, with a model-driven supervisor and handoff tools.

The alternative is agents as tools: the front-desk agent calls specialists through tools, and keeps control of the conversation:

@tool
def ask_tracking(question: str) -> str:
    """Ask the tracking specialist where orders are. Pass the customer's question."""
    result = tracking_agent.invoke({"messages": [{"role": "user", "content": question}]})
    return result["messages"][-1].content                      # only the answer goes back, not the specialist's history

front_desk = create_agent(chat, tools=[ask_tracking, cancel_order], system_prompt="Help customers; ask specialists.")
print(ask_tracking.invoke({"question": "Where is A-1001?"}))
What you should see
Here is what I found: A-1001 is shipped

Here only the specialist's final answer returns to the front desk, not its internal steps, which keeps the front desk's context small. A third shape, handoffs (a "swarm"), lets the active agent transfer the conversation to another with a tool that returns Command(goto=..., graph=Command.PARENT); langgraph-swarm packages it.

Choosing a shape

Shape Who decides Context Fits
One agent with all tools The model, every step One history Up to a modest number of related tools; start here
Supervisor and specialists A router or a supervising model Shared or per specialist Distinct domains, teams owning parts, different policies per domain
Agents as tools The front-desk agent Specialist answers only A main agent that delegates sub-questions
Handoffs The active agent Shared Conversations that move between desks, like a phone transfer
Map-reduce with Send Your code One small input per worker Many independent items

Lesson 14.66's warning holds: every agent boundary adds model calls, latency and a place for context to be lost. Split when one agent fails your evals because of too many tools or conflicting instructions, not before.

Check your mental model
  • ✗ "A supervisor sees all of a specialist's steps."
    ✓ It sees what the specialist returns, usually the final answer. That isolation is the point.
  • ✗ "A Send task gets the whole state."
    ✓ It gets only its own payload; results come back through a reducer.
  • ✗ "More agents give better answers."
    ✓ Each hop adds cost and latency and loses context. Split only when roles, tools or ownership genuinely differ.

Debugging exercise: fine for one order, broken for two

A teammate rewrote the batch state and now questions about two or more orders fail:

from langgraph.errors import InvalidUpdateError

class Broken(TypedDict, total=False):
    msg: str
    statuses: list                                             # the bug is on this line
    summary: str

xb = StateGraph(Broken)
xb.add_node("check_one", check_one); xb.add_node("summarize", summarize)
xb.add_conditional_edges(START, fan_out, ["check_one"])
xb.add_edge("check_one", "summarize"); xb.add_edge("summarize", END)
g = xb.compile()
for msg in ["Where is A-1001?", "Where are A-1001 and A-1002?"]:
    try:
        print(g.invoke({"msg": msg})["summary"])
    except InvalidUpdateError as e:
        print("InvalidUpdateError:", str(e).splitlines()[0])

What it printed:

A-1001: shipped
InvalidUpdateError: At key 'statuses': Can receive only one value per step. Use an Annotated key to handle multiple values.

Find the bug, and explain why one order works. (Solution D1.)

Make it your own

Add a third specialist, returns, with a start_return tool, and route "return" requests to it. (Solution M1.)

Solutions

SolutionP1 · An empty fan-out

fan_out returns an empty list, so no check_one runs. Then summarize does not run either, because nothing leads to it, and the graph ends with no summary: invoke returns the state without summary, and code that reads it fails with a KeyError. Handle the empty case explicitly, for example by routing to a node that asks the customer for an order ID when the list is empty.

SolutionB1 · Shared keys are the connection

A subgraph added directly as a node communicates only through the keys its schema shares with the parent. With text instead of msg, the subgraph gets no message, so find_order fails on a missing key. Either keep a shared key, or wrap the subgraph in a node function that translates (Idea 1's second example), which is safer when the graphs belong to different teams.

SolutionD1 · Parallel writers need a reducer

statuses lost its Annotated[list, operator.add], so it accepts one value per step. With one order, one worker writes it, and that works. With two, two workers write it in the same step, and LangGraph refuses with InvalidUpdateError (Lesson 14.101). Restore the reducer. Test fan-outs with more than one item; the one-item case hides this bug.

SolutionM1 · Three specialists
@tool
def start_return(order_id: str) -> str:
    """Start a return for a ShopKart order that has been delivered."""
    return f"return started for {order_id}"

returns_agent = create_agent(chat, tools=[start_return], system_prompt="You handle returns.", name="returns")

def supervisor3(state):
    text = state["messages"][-1].content.lower()
    return {"route": "cancellations" if "cancel" in text else "returns" if "return" in text else "tracking"}

db = StateGraph(Desk)
db.add_node("supervisor", supervisor3)
for name, agent in [("tracking", tracking_agent), ("cancellations", cancel_agent), ("returns", returns_agent)]:
    db.add_node(name, agent)
    db.add_edge(name, END)
db.add_edge(START, "supervisor")
db.add_conditional_edges("supervisor", lambda s: s["route"], ["tracking", "cancellations", "returns"])
desk3 = db.compile()
out = desk3.invoke({"messages": [{"role": "user", "content": "I want to return A-1003"}]})
print("routed to:", out["route"])

routed to: returns

The lab rig has no rule for start_return, so the returns agent's reply is generic; with a real model it would call the tool. Each new specialist means a routing rule, a prompt and an eval set of its own, which is the ongoing cost of this shape.

Check your understanding

Explain the mechanismWhat are subgraphs and Send in LangGraph, and when do you use each?

Worked answer. A subgraph is a compiled graph used inside another, as a node when they share state keys or called from a node that translates state in and out; it is for composition, letting teams build and test parts separately. Send is returned by a router to start one run of a node per item, each with its own input, decided at run time; with a reducer to collect results, it gives map-reduce. Subgraphs structure a system; Send parallelizes over data.

A plausible wrong answer. "Send is how nodes send messages to each other." Nodes communicate through state; Send schedules extra node runs with custom inputs.

Follow-ups. How does an interrupt inside a subgraph behave?

Debug a failureA supervisor system answers worse than the single agent it replaced. How do you investigate?

Worked answer. Run both on the same eval set and look at where answers differ. Typical causes: the router sends questions to the wrong specialist (check routing accuracy separately), context lost at the boundary (the specialist did not get the earlier turns or the customer's details), specialists that each lack a tool a question needed, and more model calls adding latency and failure points. Fix routing with labeled examples, pass the context the specialist needs, and merge specialists that are too narrow.

A plausible wrong answer. "Multi-agent is always better; tune the specialists' prompts." The structure itself may be the problem.

Follow-ups. How would you evaluate the router on its own?

Defend a designSupervisor and specialists, or one agent with many tools?

Worked answer. One agent first, because it has the fewest calls and no context boundaries. I move to specialists when evals show the single agent failing for structural reasons: too many tools to choose well, instructions for different domains that conflict, different permissions or models per domain, or teams that must own and release parts independently. Then I choose the shape by who should decide and what context each part needs, and keep the number of boundaries small.

A plausible wrong answer. "Specialists from the start, it is cleaner." Cleaner diagrams can mean worse answers and higher cost.

Follow-ups. How do agents-as-tools and handoffs differ in what the user experiences?
