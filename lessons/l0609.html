Why this came about

Workflows with branches, loops and pauses are graphs, an idea from workflow engines and data pipelines. Building a tiny graph engine by hand shows what LangGraph adds before you use it.

In plain words first
A graph is a loop with names on the steps

An agent loop, a workflow, a pipeline with branches: all are steps connected by rules about what runs next. An execution graph writes that down explicitly: nodes are the steps, edges are the rules, and a shared state carries the data between them. Building a tiny engine by hand in this lesson shows what LangGraph really does: run the next node, merge its result into the state, save a checkpoint, decide where to go.

Orchestration graphs: why agents became state machines

An agent loop (Lesson 14.3) lets the model decide every step. A state graph writes the control flow down: nodes are functions that read and update a shared state, edges say what runs next, and conditional edges choose the next node from the state. Cycles allow retries and loops, a checkpoint after each node makes runs resumable, and an interrupt pauses the graph for a person. The model still makes decisions inside nodes, but the shape of the process is code you can test, draw and review. This is the design behind LangGraph, and the reason "least autonomy that works" (Lesson 14.8) is easy to express: a workflow is a graph with few branches, an agent is a graph with a loop.

Hands-on · A state-graph engine, from scratch

Before using LangGraph, build its core yourself. It is about forty lines. A graph holds named nodes (functions that take the state and return an update), edges (what runs next) and conditional edges (a function that looks at the state and picks the next node). The engine starts at the first node and keeps going until it reaches the end. Read the class, then the refund workflow built with it underneath.

import json

class StateGraph:
    """The core of an orchestration framework such as LangGraph, in 40 lines: nodes are functions
    that update a shared state, edges say what runs next, and conditional edges choose by state."""
    def __init__(self):
        self.nodes, self.edges, self.cond = {}, {}, {}
    def node(self, name, fn): self.nodes[name] = fn
    def edge(self, a, b): self.edges[a] = b
    def branch(self, a, chooser, options): self.cond[a] = (chooser, options)

    def lint(self, start):
        """Static checks before anything runs: unreachable nodes, missing targets, no way to END."""
        targets = lambda n: [self.edges[n]] if n in self.edges else list(self.cond.get(n, (None, []))[1])
        seen, todo, issues = set(), [start], []
        while todo:
            n = todo.pop()
            if n in seen or n == "END": continue
            seen.add(n)
            if n not in self.nodes: issues.append(f"edge points to missing node {n}"); continue
            if not targets(n): issues.append(f"{n} has no outgoing edge")
            todo += targets(n)
        issues += [f"{n} is unreachable" for n in self.nodes if n not in seen]
        return issues

    def run(self, state, start, checkpoints, max_steps=12, resume=False):
        node = checkpoints[-1]["next"] if resume else start
        for _ in range(max_steps):
            if node == "END":
                return state
            state = {**state, **self.nodes[node](state)}
            if node in self.edges: nxt = self.edges[node]
            else:
                chooser, options = self.cond[node]; nxt = chooser(state)
                assert nxt in options, f"{node} chose {nxt}, not one of {options}"
            checkpoints.append({"after": node, "next": nxt, "state": json.loads(json.dumps(state))})
            if state.get("interrupt"):
                return state                                   # pause for a person; resume later
            node = nxt
        raise RuntimeError("step budget exhausted: a cycle without an exit")

# A refund workflow with a loop (retry the lookup) and a human approval gate.
g = StateGraph()
g.node("classify", lambda s: {"intent": "refund" if "refund" in s["msg"] else "other"})
g.node("lookup", lambda s: {"tries": s.get("tries", 0) + 1, "order": {"id": "A-1077", "amount": 7999} if s.get("tries", 0) >= 1 else None})
g.node("decide", lambda s: {"needs_approval": s["order"]["amount"] > 5000})
g.node("approve", lambda s: {"interrupt": not s.get("approved"), "approved": s.get("approved", False)})
g.node("refund", lambda s: {"done": f"refunded {s['order']['amount']} on {s['order']['id']}", "interrupt": False})
g.node("handoff", lambda s: {"done": "sent to a person"})
g.node("orphan", lambda s: {})
g.branch("classify", lambda s: "lookup" if s["intent"] == "refund" else "handoff", ["lookup", "handoff"])
g.branch("lookup", lambda s: "decide" if s["order"] else ("lookup" if s["tries"] < 3 else "handoff"), ["decide", "lookup", "handoff"])
g.branch("decide", lambda s: "approve" if s["needs_approval"] else "refund", ["approve", "refund"])
g.branch("approve", lambda s: "refund" if s["approved"] else "approve", ["refund", "approve"])
g.edge("refund", "END"); g.edge("handoff", "END")

print("lint:", g.lint("classify"))
cps = []
s = g.run({"msg": "I want a refund for A-1077"}, "classify", cps)
print("paused:", [c["after"] for c in cps], "| waiting for approval:", s["interrupt"])
# ... the process can stop here. Later, a person approves and the run resumes from the checkpoint.
saved = cps[-1]["state"]; saved.update(approved=True, interrupt=False)
cps[-1]["state"] = saved
s = g.run(saved, None, cps, resume=True)
print("resumed:", [c["after"] for c in cps], "->", s["done"])
What you should see
lint: ['orphan is unreachable']
paused: ['classify', 'lookup', 'lookup', 'decide', 'approve'] | waiting for approval: True
resumed: ['classify', 'lookup', 'lookup', 'decide', 'approve', 'approve', 'refund'] -> refunded 7999 on A-1077

The linter catches the orphan node before anything runs: in a large graph, unreachable nodes, edges to missing nodes and branches with no path to END are real bugs. The run loops once on lookup (the order service failed the first time), decides that 7,999 needs approval and pauses, with every step checkpointed. The process could now stop for hours. When a person approves, the run resumes from the last checkpoint, the approval node runs again and sees the approval, and the refund completes. The step budget turns an accidental infinite cycle into an error instead of a bill.

Check your mental model
  • ✗ "Graphs are only for complex systems."
    ✓ Any workflow is a graph; writing it as one makes steps, branches and checkpoints explicit.
  • ✗ "Nodes call each other."
    ✓ Nodes return updates; the engine decides what runs next.
  • ✗ "A graph engine needs a framework."
    ✓ The core is a short loop; frameworks add persistence, parallelism and tooling.

Exercises

Predict before you run

In the from-scratch engine, the order service fails twice before succeeding. Which nodes appear in the checkpoints before the approval pause? (Solution P1.)

Break it on purpose

Remove the step budget (max_steps). Make approve never set approved. What happens? (Solution B1.)

Debugging exercise

lint reports "orphan is unreachable". Why is that worth catching before running? (Solution D1.)

Make it your own

Add a handoff path when the order amount is above INR 50,000, and show it in a run. (Solution M1.)

Solutions

SolutionP1 · Trace the engine

classify, lookup, lookup, decide, approve: the lookup loop ran twice before the order was found, as the run box shows.

SolutionB1 · Budgets stop cycles

The run cycles through approve until the process is stopped, which in production means cost without progress. Every engine needs a step limit (LangGraph's recursion limit, Lesson 14.61).

SolutionD1 · Static checks

An unreachable node usually means a missing edge, so a path the designer intended can never run. Catching it at build time is cheaper than discovering it in production.

SolutionM1 · Extend the graph

Add a branch from decide to handoff for large amounts, update the options list, and rerun lint. Lesson 14.61 builds the same routing in LangGraph.

Check your understanding

Explain the mechanismWhat is an execution graph, and how is it different from a knowledge graph?

Worked answer. An execution graph controls a workflow: nodes are steps, edges decide what runs next, and a shared state flows through them, with checkpoints for pause and resume. A knowledge graph stores facts as entities and relationships for querying (the Knowledge graphs section). Agent runtimes such as LangGraph are execution graphs.

A plausible wrong answer. "They are the same thing with different names." One controls work, the other stores knowledge.

Follow-ups. Why did agent runtimes become graphs?

Debug a failureA workflow sometimes skips the approval node. What do you check?

Worked answer. The conditional edge that leads to it: the router's condition and the state value it reads, and whether another branch reaches the action without passing approval. Add a test that the action is unreachable without approval.

A plausible wrong answer. "The model skipped it." The graph's edges decide.

Follow-ups. How would you prove the action needs approval?

Defend a designWrite your own small engine or use LangGraph?

Worked answer. Your own to learn the concepts, as here; LangGraph (or another runtime) in production, because persistence, interrupts, streaming, parallelism and tooling are a lot of careful work.

A plausible wrong answer. "Own engine for control." You will rebuild LangGraph slowly.

Follow-ups. What would you keep from your engine?
