Why this came about

Agents made evaluation harder: a correct final answer could hide a bad path, and multi-turn behavior was hard to test. Benchmarks and methods for agents (such as tau-bench, 2024) introduced trajectory checks and simulated users.

In plain words first
Grading the journey as well as the destination

For agents, a right final answer reached by a wrong path is still a problem: too many steps, a skipped approval, an unnecessary risky call. End-to-end agent evaluation scores the outcome and the trajectory (which tools, in what order, with what arguments), often in a simulated environment with a scripted user, and runs each case several times because agents vary.

Lesson 14.117 covers evaluation in depth: error analysis, harnesses, judges and CI. Lesson 14.32 covers RAG. This lesson adds what is specific to agents that act: the answer is not the reply, it is what changed in the world, and the same task can succeed on Monday and fail on Tuesday with the same inputs.

Three things to grade

What Question Grader Example
Outcome Is the world in the right state at the end? Code that inspects the environment The order shows exactly one refund of 1,200 INR; the in-transit order shows none
Trajectory Did it get there in an acceptable way? Rules over the sequence of calls; sometimes a judge Read the order before refunding; never call a forbidden tool; at most 8 steps
Interaction Did the person get what they needed, politely and truthfully? Rubric judge calibrated with people (Lesson 14.117) It explained why the refund was refused and offered the next step

Grade outcomes with code whenever you can: it is cheap, exact and does not drift. This is the core idea of τ-bench and its successor τ²-bench from Sierra: tasks in domains such as retail and airline support, a simulated user, and success judged by comparing the final database state with the expected one.

Reliability is a separate number

Run each task several times. An agent that solves a task in 7 of 10 trials has a 70% pass@1, but the chance that it succeeds on four independent attempts in a row (what four different customers experience) is far lower. τ-bench reports this as pass^k: the probability that all k trials succeed, estimated without bias from n trials with c successes as C(c, k) / C(n, k). Report both: pass@1 says how capable the agent is; pass^k says how dependable it is.

Hands-on · A task suite judged by final state

Grading by the resulting state of the system rather than by the reply text is called final-state grading. The environment below is a tiny order database. Each task is a user request, an expected final state and a "critical" flag. The two agent versions stand in for real ones: correct most of the time, with version-specific mistakes, as real agents have.

import random
from math import comb

# A tiny tau-bench-style environment: tasks are judged by the FINAL STATE of the database
# and by trajectory rules, not by the wording of the reply.
ORDERS = {"A-1001": {"total": 1200, "status": "delivered", "refunded": 0},
          "A-1002": {"total": 18000, "status": "delivered", "refunded": 0},
          "A-1003": {"total": 900, "status": "in_transit", "refunded": 0},
          "A-1004": {"total": 2500, "status": "delivered", "refunded": 2500}}

TASKS = [  # (id, user request, expected final refunds, critical?)
    ("t1", ("refund", "A-1001", 1200), {"A-1001": 1200}, True),
    ("t2", ("refund", "A-1003", 900), {"A-1003": 0}, True),         # in transit: must not refund
    ("t3", ("refund", "A-1004", 2500), {"A-1004": 2500}, True),     # already refunded: no double refund
    ("t4", ("refund", "A-1002", 18000), {"A-1002": 0}, True),       # over limit: escalate, do not refund
    ("t5", ("status", "A-1003", None), {}, False),
    ("t6", ("partial", "A-1001", 400), {"A-1001": 400}, False),
]

def agent(version, request, db, rng):
    """A stand-in for a real agent: correct most of the time, with version-specific mistakes."""
    kind, oid, amount = request
    calls = []
    skip_lookup = version == "v1" and rng.random() < 0.15        # v1 sometimes acts without looking
    if not skip_lookup:
        calls.append("get_order"); order = db[oid]
    else:
        order = {"total": amount or 0, "status": "delivered", "refunded": 0}
    if kind == "status":
        return calls + ["reply"]
    if order["status"] != "delivered" or order["refunded"] >= order["total"]:
        return calls + ["reply"]
    limit = 5000 if version == "v1" or rng.random() > 0.25 else 20000   # v2 sometimes misreads the limit
    if amount > limit:
        return calls + ["escalate"]
    db[oid]["refunded"] += amount
    return calls + ["issue_refund"]

def run_trial(version, task, seed):
    db = {k: dict(v) for k, v in ORDERS.items()}
    tid, req, expect, _ = task
    traj = agent(version, req, db, random.Random(seed))
    state_ok = all(db[o]["refunded"] == v for o, v in expect.items())
    rule_ok = not ("issue_refund" in traj and "get_order" not in traj)   # never act before reading the record
    return state_ok and rule_ok

def evaluate(version, n=10):
    res = {}
    for task in TASKS:
        res[task[0]] = sum(run_trial(version, task, seed=1000 * TASKS.index(task) + i) for i in range(n))
    return res

def pass_hat_k(c, n, k):                     # unbiased estimate of "all k independent trials succeed"
    return comb(c, k) / comb(n, k)

n = 10
for v in ["v1", "v2"]:
    r = evaluate(v, n)
    p1 = sum(c / n for c in r.values()) / len(r)
    p4 = sum(pass_hat_k(c, n, 4) for c in r.values()) / len(r)
    print(f"{v}: pass^1 {p1:.0%} | pass^4 {p4:.0%} | per task " + " ".join(f"{t}:{c}/{n}" for t, c in r.items()))
What you should see
v1: pass^1 93% | pass^4 76% | per task t1:9/10 t2:10/10 t3:9/10 t4:10/10 t5:10/10 t6:8/10
v2: pass^1 98% | pass^4 93% | per task t1:10/10 t2:10/10 t3:10/10 t4:9/10 t5:10/10 t6:10/10

Version 2 looks better on every summary number: pass^1 and pass^4 are both higher, and it fixed v1's habit of acting without reading the order. Look at the per-task line before celebrating.

Hands-on · A release gate that reads per task

Averages hide the one regression that matters. Gate on rules that encode the business risk: no new failures on critical tasks, no drop in reliability, and an honest statement of how much evidence the comparison has.

base, cand = evaluate("v1", n), evaluate("v2", n)
crit = {t[0] for t in TASKS if t[3]}

def sign_test(wins, losses):                 # two-sided exact binomial test on tasks that changed
    m, k = wins + losses, min(wins, losses)
    return min(1.0, 2 * sum(comb(m, i) for i in range(k + 1)) / 2 ** m) if m else 1.0

def gate(base, cand):
    reasons = []
    for t in sorted(crit):
        if cand[t] < n and base[t] == n:
            reasons.append(f"new failures on critical task {t} ({base[t]}/{n} -> {cand[t]}/{n})")
    pk = lambda r: sum(pass_hat_k(c, n, 4) for c in r.values()) / len(r)
    if pk(cand) < pk(base):
        reasons.append("pass^4 dropped")
    wins = sum(cand[t] > base[t] for t in base); losses = sum(cand[t] < base[t] for t in base)
    print(f"tasks better {wins}, worse {losses}, sign-test p = {sign_test(wins, losses):.2f} "
          f"(with {len(base)} tasks, no difference can be significant: add tasks)")
    return ("BLOCK: " + "; ".join(reasons)) if reasons else "PASS"

print(gate(base, cand))
What you should see
tasks better 3, worse 1, sign-test p = 0.62 (with 6 tasks, no difference can be significant: add tasks)
BLOCK: new failures on critical task t4 (10/10 -> 9/10)

Version 2 is blocked: in one trial out of ten it refunded 18,000 INR that should have gone to a person, a failure v1 never had. Three tasks improved, but no amount of improvement elsewhere pays for a new way to lose money. And six tasks cannot show a significant difference between versions in either direction; a real suite needs hundreds of tasks, weighted towards the critical ones.

Public benchmarks, read carefully

Benchmarks tell you how models and harnesses compare on someone else's tasks. Use them to shortlist models and to learn evaluation design; never as evidence that your agent works.

Benchmark What it measures Read it with
SWE-bench (and its human-validated Verified subset) Resolving real GitHub issues, checked by the repository's tests Scores depend heavily on the harness and scaffolding, not only the model; possible contamination
τ-bench / τ²-bench Tool-agent-user interaction in customer-service domains, graded by final state, with pass^k The best template for business agents; build your own version on your tools
Terminal-Bench Hard tasks completed in a terminal Measures the agent harness as much as the model
GAIA General assistant questions needing browsing, tools and reasoning Short answers; little about side effects
WebArena Tasks on realistic, self-hosted websites Sandboxed sites are simpler than the real web
OSWorld Computer-use tasks on real desktop operating systems Slow and expensive to run; huge variance between runs
BFCL (Berkeley Function Calling Leaderboard) Accuracy of function calls: selection, arguments, multi-turn Tool calling in isolation, not end-to-end tasks

Benchmarks saturate, leak into training data and reward harness tricks. The useful habit is to copy their design: realistic environments, outcome grading, repeated trials, and published failure analysis.

Hands-on lab
Lab P5 · An eval suite your release depends on
  1. Turn 30 production conversations (or capstone transcripts) into tasks with an expected final state. Mark the critical ones.
  2. Write two trajectory rules from your spec's "never" list and grade them in code.
  3. Run 5 trials per task for your current version. Report pass^1, pass^3 and the tasks with the most variance; read three failing trajectories and name the failure modes.
  4. Make one change to your agent. Run the gate. If it blocks, explain why in one sentence a product owner would accept.
  5. Write a simulated user for one multi-turn task with an impatient persona, and compare results with a cooperative one.
Check your mental model
  • ✗ "Correct final answers mean a good agent."
    ✓ Check the path too: cost, safety and policy compliance live there.
  • ✗ "One run per case is enough."
    ✓ Run several times and measure how consistently it succeeds.
  • ✗ "Simulations are unrealistic, so skip them."
    ✓ They are the only way to test multi-turn behaviour safely before release.

Exercises

Predict before you run

An agent reaches the right final answer but calls an expensive tool five times unnecessarily. Does an outcome-only eval catch it? (Solution P1.)

Break it on purpose

Evaluate an agent once per case. A case passes. Is the behavior reliable? (Solution B1.)

Debugging exercise

An agent eval uses a simulated user model. Scores are high, real users struggle. Why? (Solution D1.)

Make it your own

Define an end-to-end eval for the refund flow: environment, simulated user, success check in the database, trajectory checks, and k. (Solution M1.)

Solutions

SolutionP1 · Outcomes and trajectories

No. Trajectory evaluation (tool calls, order, count) or cost metrics catch it. Agents need both outcome and process measures.

SolutionB1 · pass@k against pass^k

Not necessarily: agents vary between runs. Run each case several times; pass^k (all k runs pass) measures reliability, pass@k (any run passes) measures capability.

SolutionD1 · Simulators are not users

The simulator is more cooperative, clearer and more consistent than real users. Calibrate the simulator on real conversations and include difficult personas.

SolutionM1 · An environment-based eval

A sandbox with orders, a simulated customer with goals, a check that the refund record is correct and approvals happened, trajectory checks for forbidden actions, run five times per case.

Check your understanding

Explain the mechanismHow do you evaluate agents end to end?

Worked answer. In environments with state: give the agent tasks, simulate users and tools, check final state (did the refund happen correctly) rather than text, check trajectories for forbidden or wasteful actions, repeat runs to measure reliability (pass^k), and track cost and latency. Benchmarks such as tau-bench follow this design.

A plausible wrong answer. "Compare the final answer to a reference." Agents change state; check the state.

Follow-ups. What makes a good simulated user?

Debug a failureAn agent's pass^5 is low while pass@1 is high. What does it mean, and what do you do?

Worked answer. It often succeeds but not consistently. Look at failing runs for the same case: unstable tool choices, ambiguous instructions, or sensitivity to phrasing. Tighten instructions, tools and structure, then re-measure.

A plausible wrong answer. "Run it once and ship." Users get the inconsistent behavior.

Follow-ups. How would you report reliability to stakeholders?

Defend a designPublic agent benchmarks or your own environment?

Worked answer. Your own environment for decisions, because it reflects your tools and tasks; public benchmarks for model shortlisting and for comparing approaches.

A plausible wrong answer. "Benchmarks are enough." They do not have your tools or policies.

Follow-ups. What would your environment simulate?
