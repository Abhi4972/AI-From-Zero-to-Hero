Why this came about

Querying connections with SQL needs many joins that are hard to write and slow to run. Graph query languages such as Cypher (from Neo4j), SPARQL (for RDF) and the new ISO standard GQL (2024) describe patterns of connections directly. Models can now write them too, much like SQL.

In plain words first
Asking the map for a route

Graph query languages describe a pattern of nodes and edges to find, like drawing the shape of the answer: in Cypher, (c:Customer)-[:BOUGHT]->(p:Product) means "customers who bought products". GQL is the new ISO standard close to Cypher; SPARQL queries RDF data. Models can write these queries too, which is text-to-Cypherlater · 14.88, with the same validation needs as text-to-SQL.

Query languages

Four query languages are in use for graphs. You do not need to learn all four. Read the same question in each to see how alike they are, then learn Cypher properly in the hands-on section that follows. The question is "products made by Acme that use a recalled component":

-- Cypher (Neo4j, Memgraph, Neptune via openCypher) and GQL, the ISO standard
MATCH (c:Company {name: $maker})-[:MAKES]->(p:Product)-[:USES]->(part:Component)<-[:RECALLED]-(:Company)
RETURN p.name, part.name LIMIT 50

-- SPARQL (RDF stores)
SELECT ?product ?part WHERE {
  ?maker ex:name "Acme Electronics" ; ex:makes ?product .
  ?product ex:uses ?part . ?supplier ex:recalled ?part .
} LIMIT 50

-- Gremlin (Apache TinkerPop; Neptune, Cosmos DB for Apache Gremlin)
g.V().has('Company','name','Acme Electronics').out('MAKES').as('p')
 .out('USES').where(__.in('RECALLED')).select('p').values('name').limit(50)

-- SQL/PGQ (Part 16 of SQL:2023): a graph pattern inside SQL
SELECT * FROM GRAPH_TABLE (shop
  MATCH (c IS Company WHERE c.name = 'Acme Electronics') -[IS MAKES]-> (p IS Product)
        -[IS USES]-> (x IS Component) <-[IS RECALLED]- (s IS Company)
  COLUMNS (p.name AS product, x.name AS part))

GQL (ISO/IEC 39075) was published in April 2024 as the first ISO standard query language for property graphs since SQL, and SQL/PGQ (ISO/IEC 9075-16:2023) brings read-only graph patterns into SQL itself. Both borrow Cypher's ASCII-art pattern syntax, so learning Cypher teaches you most of both. For AI systems, Cypher matters most today: it is what text-to-query models generate most often for property graphs (Lesson 14.88).

Watch out
Do not reach for a graph by default

A graph database is another system to secure, back up, monitor and keep in sync. If your questions are one or two joins deep and known in advance, SQL is simpler and faster. Start with the questions (Lesson 14.85 calls them competency questionslater · 14.85), and adopt a graph when those questions are about paths and structure.

Cypher, hands-on

Reading query languages side by side shows that they resemble each other. To learn one, you have to run it. This section uses Kuzu, a graph database that runs inside Python: uv add kuzu (tested with 0.11) and there is no server to start. Its query language is Cypher, so everything below runs with small changes on Neo4j, Memgraph or Amazon Neptune.

Cypher draws the pattern you are looking for. A node is written in round brackets, like a circle: (c:Customer) is a node of kind Customer that the query will call c. A relationship is an arrow with its type in square brackets: -[:PLACED]->. So (c:Customer)-[:PLACED]->(o:Purchase) reads "a customer who placed a purchase".

First, create the graph. It is the ShopKart graph of Lesson 14.83. (The order nodes are called Purchase here, because ORDER is a reserved word in Cypher, as it is in SQL.)

import kuzu

db = kuzu.Database(":memory:")                           # an embedded graph database, here kept in memory: no server, no files
conn = kuzu.Connection(db)

def run(query):
    """Run one Cypher query and return its rows as a list of lists."""
    result = conn.execute(query)
    rows = []
    while result.has_next():
        rows.append(result.get_next())
    return rows

# 1. The schema: which kinds of nodes and relationships exist, and their properties.
for statement in [
    "CREATE NODE TABLE Customer(id STRING, name STRING, city STRING, PRIMARY KEY (id))",
    "CREATE NODE TABLE Purchase(id STRING, total INT64, PRIMARY KEY (id))",
    "CREATE NODE TABLE Product(id STRING, name STRING, PRIMARY KEY (id))",
    "CREATE NODE TABLE Supplier(id STRING, name STRING, country STRING, PRIMARY KEY (id))",
    "CREATE REL TABLE PLACED(FROM Customer TO Purchase)",
    "CREATE REL TABLE CONTAINS(FROM Purchase TO Product, qty INT64)",
    "CREATE REL TABLE SUPPLIED_BY(FROM Product TO Supplier)",
    "CREATE REL TABLE SOURCES_FROM(FROM Supplier TO Supplier, component STRING)",
]:
    conn.execute(statement)

# 2. The data: the same ShopKart graph as Lesson 5.1, written as Cypher CREATE statements.
conn.execute("""
CREATE (priya:Customer {id: 'c1', name: 'Priya', city: 'Pune'}), (arjun:Customer {id: 'c2', name: 'Arjun', city: 'Delhi'}),
       (meera:Customer {id: 'c3', name: 'Meera', city: 'Pune'}),
       (o1:Purchase {id: 'o1', total: 7999}), (o2:Purchase {id: 'o2', total: 1299}),
       (o3:Purchase {id: 'o3', total: 2499}), (o4:Purchase {id: 'o4', total: 7999}),
       (phone:Product {id: 'p1', name: 'Phone X'}), (pcase:Product {id: 'p2', name: 'Phone case'}),
       (buds:Product {id: 'p3', name: 'Earbuds'}),
       (acme:Supplier {id: 's1', name: 'Acme Electronics', country: 'IN'}),
       (shenzhen:Supplier {id: 's2', name: 'Shenzhen Parts', country: 'CN'}),
       (priya)-[:PLACED]->(o1), (priya)-[:PLACED]->(o2), (arjun)-[:PLACED]->(o3), (meera)-[:PLACED]->(o4),
       (o1)-[:CONTAINS {qty: 1}]->(phone), (o2)-[:CONTAINS {qty: 1}]->(pcase),
       (o3)-[:CONTAINS {qty: 1}]->(buds), (o4)-[:CONTAINS {qty: 1}]->(phone),
       (phone)-[:SUPPLIED_BY]->(acme), (pcase)-[:SUPPLIED_BY]->(shenzhen), (buds)-[:SUPPLIED_BY]->(acme),
       (acme)-[:SOURCES_FROM {component: 'battery'}]->(shenzhen)
""")
print(run("MATCH (n) RETURN count(n)"), run("MATCH ()-[r]->() RETURN count(r)"))
What you should see
[[12]] [[12]]

Twelve nodes and twelve relationships. Unlike the dictionaries of Lesson 14.83, this graph has a schema: the database knows that PLACED runs from a Customer to a Purchase, and will reject a relationship that does not fit. Neo4j does not require a schema; Kuzu does, which catches mistakes early.

Query 1: a pattern. Every Cypher query has the same three parts: MATCH a pattern, optionally filter with WHERE, and RETURN what you want from the matches.

# Query 1 · A pattern: who bought what?
for row in run("""
    MATCH (c:Customer)-[:PLACED]->(:Purchase)-[:CONTAINS]->(p:Product)
    RETURN c.name, p.name
    ORDER BY c.name, p.name
"""):
    print(row)
What you should see
['Arjun', 'Earbuds']
['Meera', 'Phone X']
['Priya', 'Phone X']
['Priya', 'Phone case']

The pattern has three nodes and two relationships. The middle node, (:Purchase), has no name because the query does not return anything from it; it only has to be there. The database found every place in the graph where the drawing fits: four of them.

Query 2: filter and count. WHERE keeps some matches; count() groups the rest, as GROUP BY does in SQL, except that the grouping is implied by the other columns you return.

# Query 2 · Filter and count: how many purchases does each supplier's stock appear in, for customers in Pune?
for row in run("""
    MATCH (c:Customer)-[:PLACED]->(o:Purchase)-[:CONTAINS]->(:Product)-[:SUPPLIED_BY]->(s:Supplier)
    WHERE c.city = 'Pune'
    RETURN s.name, count(o) AS purchases
    ORDER BY purchases DESC
"""):
    print(row)
What you should see
['Acme Electronics', 2]
['Shenzhen Parts', 1]

Priya and Meera live in Pune and placed three purchases between them: two contained Acme's stock and one Shenzhen Parts'. In SQL this is a four-table join; here it is one line that reads like the sentence.

Query 3: a path of unknown length. This is the question from Lesson 14.83 that was awkward in SQL. [:SOURCES_FROM*1..3] means "follow SOURCES_FROM between one and three times". OPTIONAL MATCH keeps a row even when there is no upstream supplier at all.

# Query 3 · A path of unknown length: which customers depend on a supplier in China, directly or further upstream?
for row in run("""
    MATCH (c:Customer)-[:PLACED]->(:Purchase)-[:CONTAINS]->(p:Product)-[:SUPPLIED_BY]->(first:Supplier)
    OPTIONAL MATCH (first)-[:SOURCES_FROM*1..3]->(upstream:Supplier)
    WITH c, p, first, upstream
    WHERE first.country = 'CN' OR upstream.country = 'CN'
    RETURN DISTINCT c.name, p.name, first.name
    ORDER BY c.name, p.name
"""):
    print(row)
What you should see
['Arjun', 'Earbuds', 'Acme Electronics']
['Meera', 'Phone X', 'Acme Electronics']
['Priya', 'Phone X', 'Acme Electronics']
['Priya', 'Phone case', 'Shenzhen Parts']

Only the phone case is supplied directly from China. The other three rows appear because Acme Electronics sources a component from Shenzhen Parts: the *1..3 followed that link without the query naming it. To look one step further upstream, change a 3 to a 4. That single edit is the reason graph databases exist.

The same question in SPARQL

RDF stores answer the same kind of question with a different language. In RDF there are no node tables and no properties on relationships; every fact is one triple of subject, predicate and object. rdflib is a pure-Python RDF library with a SPARQL engine built in: uv add rdflib.

from rdflib import Graph, Namespace, Literal

EX = Namespace("http://shopkart.example/")
g = Graph()
facts = [("priya", "placed", "o1"), ("priya", "placed", "o2"), ("arjun", "placed", "o3"), ("meera", "placed", "o4"),
         ("o1", "contains", "phoneX"), ("o2", "contains", "phoneCase"), ("o3", "contains", "earbuds"), ("o4", "contains", "phoneX"),
         ("phoneX", "suppliedBy", "acme"), ("phoneCase", "suppliedBy", "shenzhen"), ("earbuds", "suppliedBy", "acme"),
         ("acme", "sourcesFrom", "shenzhen")]
for s, p, o in facts:
    g.add((EX[s], EX[p], EX[o]))                         # every fact is one triple: subject, predicate, object
g.add((EX.acme, EX.country, Literal("IN"))); g.add((EX.shenzhen, EX.country, Literal("CN")))
print(len(g), "triples")

query = """
PREFIX ex: <http://shopkart.example/>
SELECT DISTINCT ?customer ?product WHERE {
    ?customer ex:placed ?order .
    ?order ex:contains ?product .
    ?product ex:suppliedBy ?first .
    ?first ex:sourcesFrom* ?supplier .        # * means: follow this link zero or more times
    ?supplier ex:country "CN" .
} ORDER BY ?customer ?product
"""
for customer, product in g.query(query):
    print(customer.split("/")[-1], product.split("/")[-1])
What you should see
14 triples
arjun earbuds
meera phoneX
priya phoneCase
priya phoneX
Reading this output
Reading the two languages side by side
  • In SPARQL, anything that starts with ? is a variable, and each line ending in a full stop is one triple pattern. The engine finds every way of filling in the variables so that all the patterns are true at once.
  • ex:sourcesFrom* is SPARQL's version of Cypher's *0..: follow the link any number of times, including none. That is why one pattern covers both the direct case and the upstream case.
  • The answers are the same four pairs as Query 3, as they must be: the facts are the same, only the model and the language differ.

For AI systems, Cypher is the one to know well. It is what GraphRAG tools use, and what language models write most reliably when asked to turn a question into a graph query (Lesson 14.88).

Check your mental model
  • ✗ "Graph queries are just SQL with different words."
    ✓ They match patterns of connections, which SQL expresses with many joins.
  • ✗ "A generated Cypher query that runs is correct."
    ✓ It can match the wrong pattern; validate and test like text-to-SQL.
  • ✗ "Variable-length paths are free."
    ✓ Unbounded paths can explode; always limit depth.

Exercises

Predict before you run

In Cypher, MATCH (p:Product)<-[:SUPPLIES*1..3]-(s:Supplier {country: 'X'}) RETURN DISTINCT p — what does *1..3 mean, and why DISTINCT? (Solution P1.)

Break it on purpose

Remove the upper bound: [:SUPPLIES*]. What can happen on a large graph? (Solution B1.)

Debugging exercise

A model-generated Cypher query returns nothing for "suppliers in India". The data uses country: 'IN'. Fix it at the right layer. (Solution D1.)

Make it your own

Write the same question (products exposed to country X within three tiers) in Cypher and in SPARQL, and note what differs. (Solution M1.)

Solutions

SolutionP1 · Variable-length paths

It matches paths of one to three SUPPLIES edges. A product reachable through several paths would appear once per path, so DISTINCT returns each product once.

SolutionB1 · Unbounded traversal

The query can explore an enormous number of paths, especially through cycles and supernodes, and run for a very long time or exhaust memory. Always bound depth in production queries.

SolutionD1 · Values the model cannot know

Give the model the property's allowed values (from the schema or a sample), or map entities in the question to stored values before generating the query. Validate generated queries against the schema.

SolutionM1 · Two languages, one question

Cypher uses ASCII-art patterns with labels and properties, and *1..3 bounds the depth. SPARQL uses triple patterns; SPARQL 1.1 property paths support + and * but not bounded ranges such as {1,3}, so bound the depth with a UNION of one-, two- and three-step patterns. Both need DISTINCT, and both express the same traversal.

Check your understanding

Explain the mechanismCompare Cypher, GQL and SPARQL.

Worked answer. Cypher is the pattern-matching language of property graphs (Neo4j and others); GQL is the ISO standard query language for property graphs, closely based on Cypher; SPARQL queries RDF triple stores with triple patterns and works with shared vocabularies and reasoning. Choice follows the data model and the database.

A plausible wrong answer. "They are interchangeable." They target different data models.

Follow-ups. What does GQL standardization change for teams?

Debug a failureA Cypher query is correct but slow. What do you check first?

Worked answer. The plan (PROFILE): whether the start node is found through an index, whether the pattern expands from the most selective node, and whether variable-length parts are bounded. Add indexes on lookup properties and rewrite to start from selective nodes.

A plausible wrong answer. "Add more memory." The plan, not the hardware, is usually the problem.

Follow-ups. How would you test query performance in CI?

Defend a designShould an LLM write graph queries directly for users?

Worked answer. With guardrailslater · 15.23: a schema description with allowed values, examples, validation of generated queries, read-only access, depth limits and timeouts, and evaluation on known questions. For common questions, prefer predefined, parameterized queries that the model chooses among.

A plausible wrong answer. "Yes, models know Cypher." They know the syntax, not your schema's meaning.
