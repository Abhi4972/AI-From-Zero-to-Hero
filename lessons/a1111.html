In plain words first
The idea in one line

Most AI startups do not die from bad models. They die from bad unit economics. A single GPT-4o call costs fractions of a cent. Ten thousand users making ten calls per day costs $250 in input tokens alone -- before you charge a single dollar. The companies that survive are the ones that treat every API call as a financial transaction, not a function call.

Terms you'll hear
Term What people say What it actually means
Prompt caching "Cache the system prompt" Provider-level caching where repeated prompt prefixes are billed at a small fraction of the input price (5-10% on current Anthropic and OpenAI models) -- automatic for OpenAI, explicit markers for Anthropic
Semantic caching "Smart caching" Embedding the query, computing similarity to past queries, and returning the cached response if similarity exceeds a threshold -- catches paraphrases that exact matching misses
Exact caching "Hash caching" Hashing the full prompt (model + messages + temperature) and returning the cached response for identical inputs -- only works for temperature=0 deterministic calls
Token bucket "Rate limiter" An algorithm where each user has a bucket of N tokens that refills at rate R per second -- allows bursts up to N while enforcing an average rate of R
Model routing "Cheapskate routing" Using a classifier to send simple queries to cheap models (Haiku-class) and complex queries to expensive ones (Opus- or Astra-class) -- often halves model costs at similar quality
Cost tracking "Metering" Logging every API call with model, tokens, latency, cost, and user ID so you know exactly where money goes and which features are expensive
Circuit breaker "Kill switch" Automatically degrading service (cheaper models, cached-only) or stopping requests entirely when spending approaches the budget limit
Batch API "Bulk discount" OpenAI's asynchronous processing at 50% discount -- submit up to 50,000 requests, get results within 24 hours
Prompt compression "Token diet" Rewriting system prompts and context to use fewer tokens while preserving meaning -- shorter prompts cost less and often perform better
Cache hit rate "Cache efficiency" The percentage of requests served from cache instead of calling the LLM -- 40-60% is typical for production chatbots, saves proportionally on cost

The problem

In plain words first

Every call to a hosted model is billed by the token, input and output, and the same text is often paid for again and again: the same system prompt on every request, the same question asked in different words by different users. Cost engineering removes the repeats and sends each request to the cheapest model that can handle it: provider prompt caching for repeated prefixes, your own exact and semantic caches for repeated questions, routing between cheap and expensive models, batch pricing for work that can wait, and rate limits and budgets so a bug cannot spend a month's money in an hour. This lesson builds each piece, recomputes the lesson's cost math with November 2026 prices, and measures the risk inside semantic caching: how often a similarity threshold serves the answer to a different question. No model is trained.

You build a RAG chatbot. It works beautifully. Users love it.

Then the invoice arrives.

In November 2026, OpenAI's GPT-6.2 Sol costs $2 per million input tokens and $10 per million output; Claude Sonnet 5.5 costs the same, Claude Opus 5.5 $4 / $20, GPT-6.2 Astra $8 / $40, and the small models a few cents to a few tens of cents (Claude Haiku 5.5 from $0.10 / $0.50). The math below uses $2 / $10. Prices change often; always check the provider's current pricing page.

Here is the math that kills startups:

  • 10,000 daily active users
  • 10 queries per user per day
  • 1,000 input tokens per query (system prompt + context + user message)
  • 500 output tokens per response

Daily input cost: 10,000 x 10 x 1,000 / 1,000,000 x $2.00 = $200/day Daily output cost: 10,000 x 10 x 500 / 1,000,000 x $10.00 = $500/day Monthly total (30 days): $21,000/month

That is just the LLM. Add embeddings, vector database hosting, infrastructure. You are looking at $30,000/month for a chatbot.

The brutal part: in many support-style applications a large share of queries are near-duplicates. Users ask the same questions in slightly different words. Your system prompt -- identical across every request -- gets billed every single time. Context documents retrieved by RAG repeat across users who ask about the same topic.

You are paying full price for redundant computation.

Idea 1 · The Cost Anatomy of an LLM Call

Every API call has five cost components.

System prompts are the silent killer. At $2 per million input tokens, a 1,500-token system prompt sent with every request costs $0.003 per request, $3,000 per million requests, just for that prefix. At 100K requests per day, that is $300/day -- $9,000/month -- for text that never changes.

Idea 2 · Provider Caching: Built-in Discounts

All three major providers offer provider-side prompt caching in 2026, but the mechanics differ. See Phase 11 · 15 for the deep dive.

Provider Mechanism Price of a cache hit (Nov 2026) Cache writes Cache Duration
Anthropic Explicit cache_control markers 5% of the input price on Opus 5.5 and Sonnet 5.5, 10% on Haiku 5.5 1.25x input price (5-minute cache) or 2x (1-hour cache) 5 min default, refreshed on each hit; 1 h option
OpenAI Automatic prefix matching 5% of the input price on GPT-6.2 Sol and Astra ($0.10 vs $2.00 per million on Sol) no surcharge best effort, minutes to hours
Google Gemini Implicit caching plus an explicit CachedContent API discounted cached tokens (see pricing page) explicit caches pay storage per hour user-configurable TTL for explicit caches

Minimum cacheable prefix lengths differ by model; check the docs before relying on caching for short prompts.

Anthropic's approach is explicit. You mark the end of the reusable prefix with cache_control: {"type": "ephemeral"}. The first request pays a 25% write premium. Subsequent requests with the same prefix pay 5% of the input price on Sonnet 5.5. A 2,000-token system prompt that costs $0.004 normally costs $0.0002 on cache hits. Over 100K requests a day, that saves about $380/day.

OpenAI's approach is automatic. Any prompt prefix that matches a recent request is billed at the cached-input price, 5% of the normal input price on GPT-6.2 Sol. No markers needed; you get less control over what stays cached, with zero implementation effort.

Idea 3 · Semantic Caching: Your Custom Layer

Provider caching only works for identical prefixes. Semantic caching handles the harder case: different queries with the same meaning.

"What is the return policy?" and "How do I return an item?" are different strings but identical intent. A semantic cache embeds both queries, computes cosine similarity, and returns the cached response if similarity exceeds a threshold (typically 0.92-0.95).

The embedding costs are negligible. OpenAI's text-embedding-3-small costs $0.02 per million tokens. Checking the cache costs almost nothing compared to a full LLM call.

The same idea as a formula

Cost of one request with Tin​ input tokens, of which Tc​ hit the provider cache, and Tout​ output tokens:

C=(Tin​−Tc​)pin​+Tc​ρpin​+Tout​pout​,
with ρ the cache-read multiplier (0.05 on Sonnet 5.5 and GPT-6.2 Sol).

With a semantic cache that answers a fraction h of requests at near-zero cost (one embedding):

E[C]≈(1−h)CLLM​+Cembed​.

The price of a wrong hit. With threshold θ, a hit happens when cos(q,q′)≥θ. If a fraction f(θ) of non-duplicate pairs clear the threshold, users receive answers to questions they did not ask. Raising θ lowers f and lowers h together; the run below measures both on real paraphrase data.

Worked example
The lesson's chatbot at November 2026 prices
  • 100,000 requests a day × 1,000 input tokens × $2 per million = $200; × 500 output tokens × $10 per million = $500. $700 a day, $21,000 a month.
  • Cache a 600-token shared prefix with Anthropic or OpenAI at 5%: input becomes 400×2×10−6+600×0.1×10−6=0.00086 per request instead of 0.002: input $86 a day, saving $114.
  • Semantic cache with h=0.3: 30,000 fewer model calls, about $210 a day saved at the uncached price ($0.007 a call), for 100,000 embeddings at $0.02 per million tokens (about 20 tokens each): $0.04.

Check your mental model
  • ✗ "Prompt caching caches answers."
    ✓ It caches the processed prompt prefix; every request still generates a fresh answer. Semantic caching is what reuses answers.
  • ✗ "A 0.95 cosine threshold guarantees the same question."
    ✓ It makes wrong matches rarer, not impossible; the run below counts them.
  • ✗ "Caching only saves money."
    ✓ Hits also cut latency: a cache read skips prefill, a semantic hit skips the model entirely.

Idea 4 · Exact Caching: Hash and Match

For deterministic calls (temperature=0, same model, same prompt), exact caching is simpler and faster. Hash the full prompt, check the cache, return if found.

This works perfectly for: - System prompt + fixed context + identical user queries - Function calling with identical tool definitions - Batch processing where the same document gets processed multiple times

Idea 5 · Rate Limiting: Protecting Your Budget

Rate limiting is not just about fairness. It is about survival.

Token bucket algorithm: each user gets a bucket of N tokens that refills at rate R per second. A request consumes tokens from the bucket. If the bucket is empty, the request is rejected. This allows bursts (use the full bucket at once) while enforcing an average rate.

Per-user quotas: set daily/monthly token limits per user tier.

Tier Daily Token Limit Max Requests/min Model Access
Free 50,000 10 small models only
Pro 500,000 60 mid-size models (Sonnet-, Sol-class)
Enterprise 5,000,000 300 All models

Idea 6 · Model Routing: Right Model for the Right Job

Not every query needs a frontier model.

"What time does the store close?" does not require a $10/M-output model. Claude Haiku 5.5 at $0.50/M output handles it. A simple classifier routes cheap queries to cheap models and complex queries to expensive models.

A well-tuned router saves a large share of model costs: the RouteLLM study (Ong et al. 2024) reported cutting costs by more than half while keeping 95% of GPT-4's quality on its benchmarks. Measure quality on your own traffic before trusting the savings.

Idea 7 · Cost Tracking: Know Where the Money Goes

You cannot optimize what you do not measure. Log every API call with:

  • Timestamp
  • Model name
  • Input tokens
  • Output tokens
  • Latency (ms)
  • Computed cost ($)
  • User ID
  • Cache hit/miss
  • Request category

This data reveals which features are expensive, which users are heavy consumers, and where caching has the most impact.

Idea 8 · Batching: Bulk Discounts

OpenAI's and Anthropic's Batch APIs process requests asynchronously at a 50% discount. You submit a batch of up to tens of thousands of requests, and results come back within 24 hours (usually much sooner).

Use batching for: - Nightly document processing - Bulk classification - Evaluation runs - Data enrichment pipelines

Not for: real-time user-facing queries (latency matters).

Idea 9 · Budget Alerts and Circuit Breakers

A circuit breaker stops spending when you hit a limit. Without one, a bug or abuse can burn through your monthly budget in hours.

Set three thresholds: 1. Warning (70% of budget): send an alert 2. Throttle (85% of budget): switch to cheaper models only 3. Stop (95% of budget): reject new requests, return cached responses only

Idea 10 · The Optimization Stack

Apply these techniques in order. Each layer compounds on the previous ones.

Layer Technique Typical Savings Implementation Effort
1 Provider prompt caching 30-50% Low (add cache markers)
2 Exact caching 10-20% Low (hash + dict)
3 Semantic caching 15-30% Medium (embeddings + similarity)
4 Model routing 40-70% Medium (classifier)
5 Rate limiting Budget protection Low (token bucket)
6 Prompt compression 10-30% Medium (rewrite prompts)
7 Batching 50% on eligible Low (batch API)

The savings in the table are typical ranges, not guarantees, and they do not simply add up: a semantic-cache hit also removes the routing and prompt-caching savings for that request. Measure each layer on your own traffic.

def calculate_cost(model, input_tokens, output_tokens, cached_input_tokens=0):
    if model not in MODEL_PRICING:
        return {"error": f"Unknown model: {model}"}
    pricing = MODEL_PRICING[model]
    non_cached = input_tokens - cached_input_tokens
    input_cost = (non_cached / 1_000_000) * pricing["input"]
    cached_cost = (cached_input_tokens / 1_000_000) * pricing["cached_input"]
    output_cost = (output_tokens / 1_000_000) * pricing["output"]
    total = input_cost + cached_cost + output_cost
    return {
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "cached_input_tokens": cached_input_tokens,
        "input_cost": round(input_cost, 6),
        "cached_input_cost": round(cached_cost, 6),
        "output_cost": round(output_cost, 6),
        "total_cost": round(total, 6),
    }

Step 2 · Exact Cache

Hash the full prompt and return cached responses for identical requests.

class ExactCache:
    def __init__(self, max_size=1000, ttl_seconds=3600):
        self.cache = {}
        self.max_size = max_size
        self.ttl = ttl_seconds
        self.hits = 0
        self.misses = 0

    def _hash(self, model, messages, temperature):
        key_data = json.dumps({"model": model, "messages": messages, "temperature": temperature}, sort_keys=True)
        return hashlib.sha256(key_data.encode()).hexdigest()

    def get(self, model, messages, temperature=0.0):
        if temperature > 0:
            self.misses += 1
            return None
        key = self._hash(model, messages, temperature)
        if key in self.cache:
            entry = self.cache[key]
            if time.time() - entry["timestamp"] < self.ttl:
                self.hits += 1
                entry["access_count"] += 1
                return entry["response"]
            del self.cache[key]
        self.misses += 1
        return None

    def put(self, model, messages, temperature, response):
        if temperature > 0:
            return
        if len(self.cache) >= self.max_size:
            oldest_key = min(self.cache, key=lambda k: self.cache[k]["timestamp"])
            del self.cache[oldest_key]
        key = self._hash(model, messages, temperature)
        self.cache[key] = {
            "response": response,
            "timestamp": time.time(),
            "access_count": 1,
        }

    def stats(self):
        total = self.hits + self.misses
        return {
            "hits": self.hits,
            "misses": self.misses,
            "hit_rate": round(self.hits / total, 4) if total > 0 else 0,
            "cache_size": len(self.cache),
        }

Step 3 · Semantic Cache

Embed queries and return cached responses when similarity exceeds a threshold.

def simple_embed(text):
    words = text.lower().split()
    vocab = {}
    for w in words:
        vocab[w] = vocab.get(w, 0) + 1
    norm = math.sqrt(sum(v * v for v in vocab.values()))
    if norm == 0:
        return {}
    return {k: v / norm for k, v in vocab.items()}


def cosine_similarity(a, b):
    if not a or not b:
        return 0.0
    all_keys = set(a) | set(b)
    dot = sum(a.get(k, 0) * b.get(k, 0) for k in all_keys)
    return dot


class SemanticCache:
    def __init__(self, similarity_threshold=0.85, max_size=500, ttl_seconds=3600):
        self.entries = []
        self.threshold = similarity_threshold
        self.max_size = max_size
        self.ttl = ttl_seconds
        self.hits = 0
        self.misses = 0

    def get(self, query):
        query_embedding = simple_embed(query)
        now = time.time()
        best_match = None
        best_sim = 0.0
        for entry in self.entries:
            if now - entry["timestamp"] > self.ttl:
                continue
            sim = cosine_similarity(query_embedding, entry["embedding"])
            if sim > best_sim:
                best_sim = sim
                best_match = entry
        if best_match and best_sim >= self.threshold:
            self.hits += 1
            best_match["access_count"] += 1
            return {"response": best_match["response"], "similarity": round(best_sim, 4), "original_query": best_match["query"]}
        self.misses += 1
        return None

    def put(self, query, response):
        if len(self.entries) >= self.max_size:
            self.entries.sort(key=lambda e: e["timestamp"])
            self.entries.pop(0)
        self.entries.append({
            "query": query,
            "embedding": simple_embed(query),
            "response": response,
            "timestamp": time.time(),
            "access_count": 1,
        })

    def stats(self):
        total = self.hits + self.misses
        return {
            "hits": self.hits,
            "misses": self.misses,
            "hit_rate": round(self.hits / total, 4) if total > 0 else 0,
            "cache_size": len(self.entries),
        }

Reading this output

"Same topic" and "same question" sit close together. "What's your policy on returns?" is a true paraphrase and scores 0.929. "What is the shipping policy?" is a different question, yet it scores 0.788, higher than "How do I return a gift card balance?" (0.774), which is about returns. "What is the refund policy for digital items?" scores 0.825, close to the real rephrasing "How do I return an item?" (0.848). A threshold that serves the second would also serve the first, and give an answer about physical returns to someone asking about digital refunds.

An exact-string cache would hit nothing. None of the 770 human-labelled duplicate pairs are character-for-character identical. Real users rephrase, which is the case for a semantic cache.

Every threshold is a trade. At 0.80 the cache serves 96% of duplicates, but it also matches 36% of non-duplicates, and only 62.5% of its hits are right. At 0.97 almost every hit is right (95.1%), but it serves only 17.7% of duplicates. Moving the threshold moves errors between "missed savings" and "wrong answers"; it never removes both.

Production is harder than this table. Here 38.5% of pairs are duplicates (770 of 2,000). In real traffic, most incoming queries are not duplicates of a given cached one, so the same false-match rate produces many more wrong hits per correct one. Choose the threshold on your own traffic. Start strict (0.95 or above). Scope the cache, for example by product or user segment, and log hits so a person can review a sample.

Step 4 · Rate Limiter

Token bucket rate limiter with per-user quotas.

class TokenBucketRateLimiter:
    def __init__(self):
        self.buckets = {}
        self.tiers = {
            "free": {"capacity": 50_000, "refill_rate": 500, "max_requests_per_min": 10},
            "pro": {"capacity": 500_000, "refill_rate": 5_000, "max_requests_per_min": 60},
            "enterprise": {"capacity": 5_000_000, "refill_rate": 50_000, "max_requests_per_min": 300},
        }

    def _get_bucket(self, user_id, tier="free"):
        if user_id not in self.buckets:
            tier_config = self.tiers.get(tier, self.tiers["free"])
            self.buckets[user_id] = {
                "tokens": tier_config["capacity"],
                "capacity": tier_config["capacity"],
                "refill_rate": tier_config["refill_rate"],
                "last_refill": time.time(),
                "request_timestamps": [],
                "max_rpm": tier_config["max_requests_per_min"],
                "tier": tier,
                "total_tokens_used": 0,
            }
        return self.buckets[user_id]

    def _refill(self, bucket):
        now = time.time()
        elapsed = now - bucket["last_refill"]
        refill = int(elapsed * bucket["refill_rate"])
        if refill > 0:
            bucket["tokens"] = min(bucket["capacity"], bucket["tokens"] + refill)
            bucket["last_refill"] = now

    def check(self, user_id, tokens_needed, tier="free"):
        bucket = self._get_bucket(user_id, tier)
        self._refill(bucket)
        now = time.time()
        bucket["request_timestamps"] = [t for t in bucket["request_timestamps"] if now - t < 60]
        if len(bucket["request_timestamps"]) >= bucket["max_rpm"]:
            return {"allowed": False, "reason": "rate_limit", "retry_after_seconds": 60 - (now - bucket["request_timestamps"][0])}
        if bucket["tokens"] < tokens_needed:
            deficit = tokens_needed - bucket["tokens"]
            wait = deficit / bucket["refill_rate"]
            return {"allowed": False, "reason": "token_limit", "tokens_available": bucket["tokens"], "retry_after_seconds": round(wait, 1)}
        return {"allowed": True, "tokens_available": bucket["tokens"]}

    def consume(self, user_id, tokens_used, tier="free"):
        bucket = self._get_bucket(user_id, tier)
        bucket["tokens"] -= tokens_used
        bucket["request_timestamps"].append(time.time())
        bucket["total_tokens_used"] += tokens_used

    def get_usage(self, user_id):
        if user_id not in self.buckets:
            return {"error": "User not found"}
        b = self.buckets[user_id]
        return {
            "user_id": user_id,
            "tier": b["tier"],
            "tokens_remaining": b["tokens"],
            "capacity": b["capacity"],

Log every call and compute running totals.

class CostTracker:
    def __init__(self, monthly_budget=1000.0):
        self.logs = []
        self.monthly_budget = monthly_budget
        self.alerts = []

    def log_call(self, model, input_tokens, output_tokens, cached_input_tokens=0, latency_ms=0, user_id="anonymous", cache_status="miss"):
        cost = calculate_cost(model, input_tokens, output_tokens, cached_input_tokens)
        entry = {
            "timestamp": time.time(),
            "model": model,
            "input_tokens": input_tokens,
            "output_tokens": output_tokens,
            "cached_input_tokens": cached_input_tokens,
            "latency_ms": latency_ms,
            "cost": cost["total_cost"],
            "user_id": user_id,
            "cache_status": cache_status,
        }
        self.logs.append(entry)
        self._check_budget()
        return entry

    def _check_budget(self):
        total = self.total_cost()
        pct = total / self.monthly_budget if self.monthly_budget > 0 else 0
        if pct >= 0.95 and not any(a["level"] == "stop" for a in self.alerts):
            self.alerts.append({"level": "stop", "message": f"Budget 95% consumed: ${total:.2f}/${self.monthly_budget:.2f}", "timestamp": time.time()})
        elif pct >= 0.85 and not any(a["level"] == "throttle" for a in self.alerts):
            self.alerts.append({"level": "throttle", "message": f"Budget 85% consumed: ${total:.2f}/${self.monthly_budget:.2f}", "timestamp": time.time()})
        elif pct >= 0.70 and not any(a["level"] == "warning" for a in self.alerts):
            self.alerts.append({"level": "warning", "message": f"Budget 70% consumed: ${total:.2f}/${self.monthly_budget:.2f}", "timestamp": time.time()})

    def total_cost(self):
        return round(sum(e["cost"] for e in self.logs), 6)

    def cost_by_model(self):
        by_model = {}
        for e in self.logs:
            m = e["model"]
            if m not in by_model:
                by_model[m] = {"calls": 0, "cost": 0, "input_tokens": 0, "output_tokens": 0}
            by_model[m]["calls"] += 1
            by_model[m]["cost"] = round(by_model[m]["cost"] + e["cost"], 6)
            by_model[m]["input_tokens"] += e["input_tokens"]
            by_model[m]["output_tokens"] += e["output_tokens"]
        return by_model

    def cache_savings(self):
        cache_hits = [e for e in self.logs if e["cache_status"] == "hit"]
        if not cache_hits:
            return {"saved": 0, "cache_hits": 0}
        saved = 0
        for e in cache_hits:
            full_cost = calculate_cost(e["model"], e["input_tokens"], e["output_tokens"])
            saved += full_cost["total_cost"]
        return {"saved": round(saved, 4), "cache_hits": len(cache_hits)}

    def summary(self):
        if not self.logs:
            return {"total_calls": 0, "total_cost": 0}
        total_latency = sum(e["latency_ms"] for e in self.logs)
        cache_hits = sum(1 for e in self.logs if e["cache_status"] == "hit")
        return {
            "total_calls": len(self.logs),
            "total_cost": self.total_cost(),
            "avg_cost_per_call": round(self.total_cost() / len(self.logs), 6),
            "avg_latency_ms": round(total_latency / len(self.logs), 1),
            "cache_hit_rate": round(cache_hits / len(self.logs), 4),
            "cost_by_model": self.cost_by_model(),
            "cache_savings": self.cache_savings(),
            "budget_remaining": round(self.monthly_budget - self.total_cost(), 2),
            "budget_utilization": round(self.total_cost() / self.monthly_budget, 4) if self.monthly_budget > 0 else 0,
            "alerts": self.alerts,
        }

def classify_complexity(query):
    q = query.lower()
    if len(q.split()) <= 5 or any(kw in q for kw in SIMPLE_KEYWORDS):
        return "simple"
    if any(kw in q for kw in COMPLEX_KEYWORDS):
        return "complex"
    return "medium"


def route_model(query, tier="pro"):
    complexity = classify_complexity(query)
    routing_table = {
        "simple": {"free": "gpt-4.1-nano", "pro": "gpt-4o-mini", "enterprise": "gpt-4o-mini"},
        "medium": {"free": "gpt-4o-mini", "pro": "claude-sonnet-4", "enterprise": "claude-sonnet-4"},
        "complex": {"free": "gpt-4o-mini", "pro": "gpt-4o", "enterprise": "claude-opus-4"},
    }
    model = routing_table[complexity].get(tier, "gpt-4o-mini")
    return {"query": query, "complexity": complexity, "model": model, "tier": tier}

# LLM Cost Optimization Patterns

When building an LLM application that needs to control costs, apply this decision framework.

## When to optimize

**Optimize immediately when:**
- Monthly LLM spend exceeds $500 or 10% of infrastructure budget
- Cost per query is above $0.01 for a consumer product
- Your system prompt is over 1,000 tokens and sent with every request
- More than 30% of queries are duplicates or near-duplicates

**Do not optimize yet when:**
- You have fewer than 100 DAU and are still validating product-market fit

- You are still iterating on prompt design (caching locks you into a prompt)


- Implementation: 30 minutes
- Hit rate: 10-25% for most apps, 40-60% for FAQ bots
- Latency: <1ms (dict lookup)
- Risk: stale responses if underlying data changes

**Skip when:** temperature > 0, every query is unique, real-time data needed.

### Semantic caching

**Use when:** users ask the same question in different words, FAQ-heavy products, customer support.

- Implementation: 2-4 hours (embedding + similarity + storage)
- Hit rate: 15-35% on top of exact cache
- Latency: 10-50ms (embedding + ANN search)
- Risk: false positives (returning wrong cached answer for a similar but different question)

**Threshold guidelines:**
- 0.98+: very conservative, almost no false positives, lower hit rate
- 0.95: good balance for factual Q&A
- 0.90: aggressive, higher hit rate but risk of wrong answers
- 0.85: only for low-stakes applications (suggestions, autocomplete)

**Skip when:** every query has unique context (code generation), responses must reflect latest data, query space is unbounded.

### Provider prompt caching

**Use when:** system prompt > 1,024 tokens (OpenAI) or model-specific minimum, same prefix sent repeatedly.

| Provider | Action | Savings |
|----------|--------|---------|
| Anthropic | Add `cache_control: {"type": "ephemeral"}` to system message | 90% on cached prefix (after 25% write premium) |
| OpenAI | Nothing (automatic) | 50% on cached prefix |
| Google | Use Context Caching API with explicit TTL | ~75% on cached context |

**Skip when:** system prompt changes per request, prompt is under minimum length.

## Common mistakes

| Mistake | Why it hurts | Fix |
|---------|-------------|-----|
| Caching with temperature > 0 | Non-deterministic outputs, stale cache gives wrong variety | Only cache temp=0 calls, or accept that cached responses lose randomness |

Solutions

SolutionP1 · No threshold is both generous and safe

At 0.95 the cache catches 27.1% of real duplicates and wrongly matches 2.7% of non-duplicates, and 86.4% of its hits are correct. No threshold does both jobs. Catching most duplicates (80% at 0.85) means matching one in five non-duplicates. Getting near-zero wrong matches (0.6% at 0.97) means catching fewer than one duplicate in five. Embedding similarity measures closeness of topic and wording, not "the same answer applies".

SolutionB1 · A changing prefix defeats prefix caching

Prompt caching reuses work only for an identical prefix, token for token from the first one. Put the name and date first, and every user and every day gets a different first line. The 2,000 static tokens after it are then never part of a shared prefix, so the hit rate falls to about zero across users, and also across days for the same user. On Anthropic you also pay the 1.25x cache-write price on every request, which is more than not caching. The fix is the layout rule from Lesson 11.26: static instructions, tool definitions and examples first, with the cache breakpoint after them; the name, the date and the conversation after the breakpoint. Then check the cached-token fields in the usage data. Lesson 11.26's run shows the same effect on a real model: a timestamp at the top leaves only a few shared tokens.

Defend a designLast month a bug in a retry loop spent the whole monthly model budget in two days, and nobody saw it until the invoice. Design the controls that stop the next one, with the thresholds and what each threshold does.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. Put a cost tracker on every call and a ladder of thresholds on top of it. At 70 percent of the budget alert, at 85 percent throttle so that every request goes to the cheapest model, and at 95 percent stop so that only cached answers are served and new calls are refused. In front of the ladder, add a rate limit and a daily spend cap per tenant, and a kill switch that pauses a tenant whose spend jumps far above its own history.

The tracker.

Every call logs the timestamp, the model, the input and output tokens, the latency, the computed cost, the user, the cache status and the request category. The running total against the monthly budget is the input of every control below. A check that runs nightly is too slow, because a retry loop spends a day's budget in minutes.

The budget ladder.

Share spent Action
70 percent send an alert
85 percent throttle: route every request to the cheapest model
95 percent stop: serve cached responses only, refuse new requests

Each step buys time for the next. The alert gives people a chance to act, the throttle keeps the service up at lower quality while the spend slows, and the stop protects the budget when nobody acted.

The per-tenant ladder.

The FinOps lesson gives three controls per tenant for a multi-tenant product:

  1. A rate limit at 2 to 3 times the expected peak, with a rate-limit status and a retry header. The tenant feels friction and gets no surprise bill.
  2. A daily spend cap at 1.5 to 3 times the contracted ceiling. Crossing it tightens the rate limit and alerts customer success.
  3. A kill switch when the spend z-score against the tenant's own baseline passes 4. It pauses the tenant and pages on-call.

The z-score matters because tenants differ by orders of magnitude. A fixed amount is noise for a large tenant and a month of budget for a small one.

Test the ladder.

The caching lesson's exercise simulates 1,000 requests against a budget of 1.00 dollars and checks that each threshold fires. Its projection exercise forecasts the month from the trailing 7-day average and alerts when the forecast exceeds the budget by more than 20 percent. Both belong in the test suite, because a circuit breaker that was never tripped on purpose is a hope.

Where it runs.

At the gateway, where every call passes. A control that lives in one application misses the application that has the bug.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. The cache serves deterministic calls only. A positive temperature asks for sampled variation, and a replayed answer would remove that variation without telling the caller, so the cache treats those calls as misses and never stores them. The key is a hash of the model, the full message list and the temperature, serialized with sorted keys so that the same request always produces the same bytes. Before production, the key needs every other field that changes the answer, the eviction needs a least-recently-used policy instead of a full scan for the oldest entry, and the expiry needs a sweep, because an expired entry is only removed when someone reads it.

The temperature guard.

Both get and put return early above zero. The lesson's rule is that exact caching works for deterministic calls: the same model, the same prompt, temperature zero. Serving a stored sample to a caller who asked for variation changes the behavior silently, which is worse than a miss.

What the key holds, and what it misses.

The key covers the model, because the same prompt on another model is another answer, the whole message list, because the system prompt and the context are part of the request, and the temperature. sort_keys=True makes the serialization stable, so two callers who build the same dictionary in a different order still hash alike. The key does not cover other fields that change the answer: the sampling parameters beyond temperature, the output limit, the tool definitions and the response format. Add them, or the cache returns an answer produced under different settings.

Expiry is lazy.

The lifetime is checked on read. An entry past its lifetime stays in memory until a read finds it or an eviction drops it. A periodic sweep, or an expiry check during put, keeps the memory honest.

Eviction is a full scan, oldest first.

At capacity, put scans every entry to find the oldest timestamp. That is linear work on every insert once the cache is full, and it evicts by insertion time, so a popular entry that was inserted early goes first. The lesson's first exercise asks for least-recently-used eviction on the last access time, which the access_count field hints at but does not implement.

Prove that it pays.

The cache counts hits and misses. The lesson's cost tracker logs a cache status on every call and computes the saved cost from the hits with the pricing table. Wire that in before you argue about the hit rate.

Plausible wrong answers.

  • "The temperature check is pointless, a cached answer is a good answer." A positive temperature means the caller wants variation. A replay removes it without telling anyone.
  • "Hash only the user message." The same question under a different system prompt, model or tool set has a different correct answer.
  • "The lifetime removes expired entries." It only hides them on read. The entry stays in memory until a read or an eviction removes it.

Weigh a trade-offYour semantic cache serves 20 percent of requests at a similarity threshold of 0.95. A teammate lowered it to 0.85 in staging. The hit rate rose to 50 percent, and a few cached answers did not fit the question asked. Which threshold do you ship, and how do you decide?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Ship the threshold whose wrong hits you can afford, and measure that instead of guessing. A wrong cached answer is a correctness failure that a user sees, while a miss costs one model call. Keep the strict threshold on the general path, and lower it only where the answers are interchangeable or where a disclaimer is acceptable. A vendor's accuracy figure describes how often a hit was appropriate, not how often your traffic hits, so label pairs from your own traffic at both thresholds.

Two numbers that get confused.

The hit rate is the share of requests served from the cache. The accuracy of a hit is whether the stored answer fits the new question. The lesson warns that a vendor's accuracy claim describes match correctness, and that production hit rates are community telemetry that runs from about 10 percent on open chat to about 70 percent on structured support.

The cost of each error.

A miss costs one model call, which you know to the cent. A wrong hit costs a wrong answer in front of a user, a support ticket and some trust, and only the product can price it. The two thresholds trade one for the other.

Decide with labeled pairs.

Sample pairs of a new question and the cached answer it would receive at each threshold. Label each pair as fitting or not. At 0.85 and at 0.95 you then have a hit rate and a precision of hits. Expected saving is the hit rate times the cost of a call. Expected damage is the wrong-hit rate times the cost of a wrong answer. Ship the threshold where the second number is acceptable to the product owner.

A two-tier scheme.

The earlier caching lesson's exercise uses two thresholds: hits at 0.98 return at once, and hits at 0.90 return with a disclaimer that the answer comes from a similar earlier question. Log the tier that served each hit, and compare satisfaction per tier. This keeps the strict path strict and still takes the cheap wins.

Why some workloads cannot go low.

Code questions hit about 20 to 30 percent at best, because a small change in a code question changes the correct answer. Near-duplicate text is not near-duplicate intent there. Voice agents on a fixed prompt set reach 50 to 80 percent, because the questions really repeat.

The checks around the threshold.

Run the exact-match cache first, because a byte-identical repeat needs no embedding. Set a lifetime so that stale answers expire. The embedding cost is small, the lesson quotes a per-million-token price of 0.02 dollars for a small embedding model, so the threshold is the lever, not the embedding bill.

Plausible wrong answers.

  • "Lower the threshold, the savings are bigger." A wrong hit is a correctness failure that a user sees. Its cost is not one model call.
  • "Raise the threshold until no hit is ever wrong." The hit rate then approaches the exact-match rate, and the cache stops paying for itself.
  • "Use the vendor's accuracy number as the hit rate." The figure describes match correctness, not how often your traffic hits.

Follow-ups an interviewer may ask.

  • (level 2) Why is the accuracy number in a vendor's brochure not your hit rate? Expected: accuracy says how often a returned hit was appropriate. The hit rate says how often there was a hit at all, and it depends on your traffic.
  • (level 2) What does a miss cost, and what does a wrong hit cost? Expected: a miss costs one model call. A wrong hit costs a wrong answer in front of a user, which the product has to price.
  • (level 3) How do you lower the threshold without lowering the correctness of the strict path? Expected: a two-tier scheme, with strict matches served as they are and medium matches served with a disclaimer, and the tier logged so that satisfaction can be compared.
  • (level 3) Why do code questions hit so rarely? Expected: a small variant in a code question changes the correct answer, so similar text is not similar intent.

Explain the mechanismA teammate says the service already has caching, because the provider's prompt cache is on. The bill barely moved. Which two kinds of cache exist in a model service, what does each one skip, and why does one of them do nothing for a question that users keep asking?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. There are two layers. The provider's prefix cache reuses the attention state of a prompt prefix that an earlier request computed, so the repeated opening tokens get cheaper, but the model still runs. An application-level semantic cache embeds the request and returns a stored answer when a similar question was answered before, so the model call is skipped. The prefix cache cannot serve a repeated question, because the user's part of the prompt still differs token by token and the model still generates the answer.

The provider prefix cache.

The provider stores the keys and values of a cacheable prefix. The next request with the same prefix pays a read price instead of a full prefill. The match is prefix only: the first token that differs ends it, so the stable parts of the prompt go first and the user message goes last. The cache lowers the input cost and the time to first token. Output tokens cost the same as before.

The semantic cache.

Before the call, the application embeds the request and searches for a stored request above a similarity threshold, typically 0.95 or higher. On a hit, it returns the stored answer and no model runs. The hit rate depends on the traffic. The lesson's community numbers put open-ended chat near 10 to 15 percent and structured support near 40 to 70 percent. A simpler exact cache hashes the model, the messages and the temperature, and it serves only deterministic calls.

Why the bill did not move.

The prefix cache discounts input tokens on a repeated prefix. If the prefix is short, if something in it changes on every request, or if output tokens dominate the bill, there is little for it to save. Repeated questions are a different kind of reuse, and only the semantic cache addresses them.

Stack them.

Provider caching handles token-identical reuse. Semantic caching handles meaning-identical reuse. The earlier caching lesson combines both, and puts the combined reduction at 50 to 95 percent on a typical application.

Plausible wrong answers.

  • "The prefix cache returns the same answer for the same question." It reuses the attention state of the prefix. The model still generates every token.
  • "A semantic cache is a prefix cache with fuzzy matching." It sits in your application, keys on embeddings and skips the model. The prefix cache sits at the provider and keys on exact tokens.
  • "One cache is enough." They cover different reuse, identical tokens against identical meaning, and the lesson combines them.

Follow-ups an interviewer may ask.

  • (level 1) Which cache returns an answer without running the model? Expected: the semantic cache. The prefix cache still runs the model on the uncached tokens and generates the output.
  • (level 2) Every user asks a different question under the same system prompt. Which cache helps? Expected: the prefix cache, because the shared prefix is identical and the questions are not.
  • (level 2) What decides whether a semantic cache is worth adding? Expected: the hit rate on your own traffic, which ranges from about 10 percent on open chat to about 70 percent on structured support, and the cost of a wrong hit.
  • (level 3) Why does the exact cache refuse to serve a call above temperature zero? Expected: the stored answer was one sample. A call that asks for variation would get a replay instead, which changes the behavior the caller asked for.

Q1Why do AI startups often fail from cost issues rather than model quality?

LLM API costs scale linearly with usage. A feature that costs $0.003 per call seems cheap until it's called 100K times/day ($300/day, $9K/month). Without cost optimization, many AI products are unprofitable at scale.

Q2What is semantic caching for LLM applications?

Exact-match caching only helps with identical queries. Semantic caching embeds queries and serves cached responses when cosine similarity exceeds a threshold. 'What's the weather in NYC?' matches 'NYC weather today?'.

Q3What is model routing as a cost optimization strategy?

Not every query needs GPT-4. A classifier routes simple questions (FAQ, greetings) to a cheap model (GPT-3.5, Haiku) and complex questions (reasoning, analysis) to an expensive model. This can cut costs 50-80%.

Q4What is prompt compression and how does it reduce costs?

Input tokens dominate cost in RAG applications (large retrieved contexts). Prompt compression removes filler words, summarizes verbose passages, and trims low-relevance chunks to reduce token count without losing key information.

Q5What is prefix caching and which provider feature enables it?

If your system prompt + tool definitions are 5000 tokens and identical across requests, prefix caching computes the KV-cache once and reuses it. Anthropic's prompt caching and OpenAI's cached tokens both support this.
