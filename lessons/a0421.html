In plain words first
The idea in one line

A pose is a set of ordered keypoints. A keypoint detector is a heatmap regressor. Everything else is bookkeeping.

Terms you'll hear
Term What people say What it actually means
Keypoint "A landmark" A specific ordered point on an object (joint, corner, feature)
Pose "The skeleton" An ordered set of keypoints belonging to one instance
Top-down "Detect then pose" Two-stage pipeline: person detector + per-crop keypoint model; highest accuracy
Bottom-up "Pose first, group later" Single-pass all-keypoint prediction + grouping; constant time in crowd size
Heatmap "Gaussian target" H x W tensor per keypoint with peak at the true location; the preferred regression target
PAF "Part Affinity Field" 2-channel unit vector field encoding limb directions; used to group keypoints into instances
OKS "Keypoint IoU" Object Keypoint Similarity; the COCO metric for pose
HRNet "High-Resolution Net" A long-standard top-down keypoint architecture that keeps high-resolution features throughout; ViTPose now often scores higher

The problem

In plain words first

Pose estimation finds a fixed list of points on each object, such as the 17 joints COCO uses for a human body (nose, eyes, shoulders, elbows, wrists, hips, knees, ankles), always in the same order. The usual trick is not to predict coordinates directly but to predict one "heat map" per point: an image that is bright where the network thinks that point is. The brightest pixel gives the location. With several people in the picture you either find each person first and then their joints (top-down), or find all joints first and then work out which belong together (bottom-up).

Keypoint tasks hide under many names: human pose (17 body joints), face landmarks (68 or 478 points), hand (21 points), animal pose, robotic object pose, medical anatomy landmarks. Every one of them shares the same structure: detect K discrete points on an object and output their (x, y) coordinates.

Pose estimation is the foundation of motion capture, fitness apps, sports analytics, gesture control, animation, AR try-on, and robotic grasping. The 2D case is mature; 3D pose (estimating joint positions in world coordinates from a single camera) is the current research frontier.

The engineering question is scale. A single-image, single-person pose is a 20ms problem. Multi-person pose in a crowd at 30 fps is a different problem with different architectures.

Idea 1 · Top-down vs bottom-up

  • Top-down — detect people first, then run a per-person keypoint model on each crop. Highest accuracy; scales linearly with number of people.
  • Bottom-up — one forward pass predicts all keypoints plus an association field; group them. Constant time regardless of crowd size.

Top-down (HRNet, ViTPose) is the accuracy leader; bottom-up (OpenPose, HigherHRNet) is the throughput leader for crowded scenes.

Idea 2 · Heatmap regression

Instead of regressing (x, y) directly, predict an H x W heatmap per keypoint with a Gaussian blob centred at the true location.

target[k,y,x]=exp(−2σ2(x−cxk​)2+(y−cyk​)2​)

At inference, the argmax of each heatmap is the predicted keypoint location.

Why heatmaps work better than direct regression: the network's spatial structure (conv feature map) aligns naturally with spatial output. Gaussian targets also regularise — a small localisation error produces a small loss, not zero.

Idea 3 · Sub-pixel localisation

Argmax gives integer coordinates. For sub-pixel precision, refine by fitting a parabola to the argmax and its neighbours, or shift the argmax a quarter pixel toward the higher neighbour: dx = 0.25 * sign(heatmap[y, x+1] - heatmap[y, x-1]), and the same for dy (the rule used by Hourglass and SimpleBaseline). The lesson's code/main.py multiplies by the difference instead of its sign, which moves the estimate only a few hundredths of a pixel; the visual after this idea measures all three.

Worked example
Sub-pixel by hand

A Gaussian heat map with σ=2 has its true peak at x=32.4. The pixel values around it are

  • h(31)=e−1.42/8=0.783, h(32)=e−0.42/8=0.980, h(33)=e−0.62/8=0.956.

Argmax says 32, an error of 0.4. The quarter-pixel rule sees h(33)>h(31) and moves to 32.25 (error 0.15). The lesson's 0.25 * (h(33) - h(31)) moves by 0.25×0.173=0.043, to 32.04 (error 0.36), almost no help. Fitting a parabola to the log values is exact for a clean Gaussian:

Δ=2(2lnh(32)−lnh(33)−lnh(31))lnh(33)−lnh(31)​=2(−0.040+0.045+0.245)−0.045+0.245​=0.40

import matplotlib.pyplot as plt
rng = np.random.default_rng(0)
centres = rng.uniform(16, 48, size=(2000, 2))
errors = {"argmax": [], "0.25 x difference (code/main.py)": [], "0.25 x sign (quarter-pixel)": [], "log-parabola": []}
for cx, cy in centres:
    hm = gaussian_heatmap(64, cx, cy, sigma=2.0)
    y, x = np.unravel_index(hm.argmax(), hm.shape)
    est = {}
    est["argmax"] = (x, y)
    dx, dy = hm[y, x + 1] - hm[y, x - 1], hm[y + 1, x] - hm[y - 1, x]
    est["0.25 x difference (code/main.py)"] = (x + 0.25 * dx, y + 0.25 * dy)
    est["0.25 x sign (quarter-pixel)"] = (x + 0.25 * np.sign(dx), y + 0.25 * np.sign(dy))
    L = np.log(hm[y - 1:y + 2, x - 1:x + 2])
    ox = (L[1, 2] - L[1, 0]) / (2 * (2 * L[1, 1] - L[1, 2] - L[1, 0]))
    oy = (L[2, 1] - L[0, 1]) / (2 * (2 * L[1, 1] - L[2, 1] - L[0, 1]))
    est["log-parabola"] = (x + ox, y + oy)
    for k, (ex, ey) in est.items():
        errors[k].append(np.hypot(ex - cx, ey - cy))
fig, ax = plt.subplots(figsize=(6.5, 2.8))
for i, (k, v) in enumerate(errors.items()):
    print(f"{k:34s} mean error {np.mean(v):.3f} px")
    ax.barh(i, np.mean(v), color=["#b7bfcb", "#b24a1d", "#474d9a", "#24753a"][i])
ax.set_yticks(range(4)); ax.set_yticklabels(errors.keys(), fontsize=8); ax.invert_yaxis()

Reading this output

Plain argmax is off by almost 0.4 pixels on average, which matters when a 64 × 64 heat map is scaled up to a 256-pixel crop (multiply every error by 4). Multiplying by the raw difference barely helps, because neighbouring values of a smooth Gaussian differ by only a few tenths. The quarter-pixel sign rule halves the error, and the log-parabola recovers the centre almost exactly on these clean maps. Real predicted heat maps are noisy, which is why methods such as DARK smooth the map before fitting.

Idea 4 · Part Affinity Fields (PAFs)

OpenPose's trick for bottom-up association. For each pair of connected keypoints (e.g. left shoulder to left elbow), predict a 2-channel field that encodes the unit vector pointing from one to the other. To associate a shoulder with its elbow, integrate the PAF along the line connecting candidate pairs; the pair with the highest integral is matched.

For each connection (limb):
  PAF channels: 2 (unit vector x, y)
  Line integral: sum over sample points of (PAF . line_direction)
  Higher integral = stronger match

Elegant and scales to arbitrary crowd sizes without per-person crops.

Idea 5 · COCO keypoints

The standard body-pose dataset: 17 keypoints per person, PCK (Percentage of Correct Keypoints) and OKS (Object Keypoint Similarity) as metrics. OKS is the keypoint analogue of IoU and is what COCO mAP@OKS reports.

Check your mental model
  • ✗ "A heat map per keypoint is just a fancier way to regress coordinates."
    ✓ It keeps the output spatial like the features, and it can express doubt: two bright spots mean "it is one of these two places".
  • ✗ "Keypoints only need to be visible to be learnable."
    ✓ They must be distinguishable: channel k must be able to tell its point from the others. "Use it" shows what happens when they are not.
  • ✗ "Top-down is always more accurate, so always use it."
    ✓ Its cost grows with the number of people; in a crowd at 30 fps, bottom-up or one-stage models win.

Idea 6 · 2D vs 3D

  • 2D pose — image coordinates; solved at production quality (MediaPipe, HRNet, ViTPose).
  • 3D pose — world / camera coordinates; still active research. Common approaches:
  • Lift 2D predictions to 3D with a small MLP (VideoPose3D).
  • Direct 3D regression from image (PyMAF, MHFormer).
  • Multi-view setups (CMU Panoptic) for ground truth.

The same idea as a formula

Heatmap targets. For a keypoint at (x,y), the network is trained to output, on an h×w grid,

H(u,v)=exp(−2σ2(u−x)2+(v−y)2​)

with σ of 1–3 heatmap pixels, using a mean-squared error. A smooth target gives nearby pixels partial credit, which is easier to learn than one hot pixel.

Sub-pixel decoding. The arg-max is only accurate to one heatmap cell, which at a stride of 4 is 4 image pixels. Fitting a parabola through the peak and its two neighbours h−1​,h0​,h+1​ refines the position by

δ=2(h−1​−2h0​+h+1​)h−1​−h+1​​∈(−21​,21​)

(in each axis), then the position is multiplied by the stride.

Evaluation (COCO). Object keypoint similarity compares predicted and true keypoints i with the object's scale s and a per-keypoint tolerance ki​:

OKS=∑i​1[vi​>0]∑i​exp(−di2​/(2s2ki2​))1[vi​>0]​

It plays the role IoU plays for boxes; AP is computed at OKS thresholds from 0.50 to 0.95. Wrists get a larger tolerance than eyes because annotators disagree more about them.

Step 1 · Gaussian heatmap target

import numpy as np
import torch

def gaussian_heatmap(size, cx, cy, sigma=2.0):
    yy, xx = np.meshgrid(np.arange(size), np.arange(size), indexing="ij")
    return np.exp(-((xx - cx) ** 2 + (yy - cy) ** 2) / (2 * sigma ** 2)).astype(np.float32)

hm = gaussian_heatmap(64, 32, 32, sigma=2.0)
print(f"peak: {hm.max():.3f} at ({hm.argmax() % 64}, {hm.argmax() // 64})")

Step 2 · Tiny keypoint head

A U-Net-style model that outputs K heatmap channels.

import torch.nn as nn
import torch.nn.functional as F

class TinyKeypointNet(nn.Module):
    def __init__(self, num_keypoints=4, base=16):
        super().__init__()
        self.down1 = nn.Sequential(nn.Conv2d(3, base, 3, 2, 1), nn.ReLU(inplace=True))
        self.down2 = nn.Sequential(nn.Conv2d(base, base * 2, 3, 2, 1), nn.ReLU(inplace=True))
        self.mid = nn.Sequential(nn.Conv2d(base * 2, base * 2, 3, 1, 1), nn.ReLU(inplace=True))
        self.up1 = nn.ConvTranspose2d(base * 2, base, 2, 2)
        self.up2 = nn.ConvTranspose2d(base, num_keypoints, 2, 2)

    def forward(self, x):
        h1 = self.down1(x)
        h2 = self.down2(h1)
        h3 = self.mid(h2)
        u1 = self.up1(h3)
        return self.up2(u1)

Input (N, 3, H, W), output (N, K, H, W). Loss is per-pixel MSE against Gaussian targets.

Step 3 · Inference — extract keypoint coordinates

def heatmap_to_coords(heatmaps):
    """
    heatmaps: (N, K, H, W)
    returns:  (N, K, 2) float coordinates in image pixels
    """
    N, K, H, W = heatmaps.shape
    hm = heatmaps.reshape(N, K, -1)
    idx = hm.argmax(dim=-1)
    ys = (idx // W).float()
    xs = (idx % W).float()
    return torch.stack([xs, ys], dim=-1)

coords = heatmap_to_coords(torch.randn(2, 4, 32, 32))
print(f"coords: {coords.shape}")  # (2, 4, 2)

Step 4 · Synthetic keypoint dataset

Simple: draw four points on a white canvas and learn to predict them.

def make_synthetic_sample(size=64):
    img = np.ones((3, size, size), dtype=np.float32)
    rng = np.random.default_rng()
    kps = rng.integers(8, size - 8, size=(4, 2))
    for cx, cy in kps:
        img[:, cy - 2:cy + 2, cx - 2:cx + 2] = 0.0
    hms = np.stack([gaussian_heatmap(size, cx, cy) for cx, cy in kps])
    return img, hms, kps

Quick to train. But read it closely before trusting it: the box after Step 5 explains a problem with this data.

Step 5 · Training

model = TinyKeypointNet(num_keypoints=4)
opt = torch.optim.Adam(model.parameters(), lr=3e-3)

for step in range(200):
    batch = [make_synthetic_sample() for _ in range(16)]
    imgs = torch.from_numpy(np.stack([b[0] for b in batch]))
    hms = torch.from_numpy(np.stack([b[1] for b in batch]))
    pred = model(imgs)
    # Upsample pred to full resolution
    pred = F.interpolate(pred, size=hms.shape[-2:], mode="bilinear", align_corners=False)
    loss = F.mse_loss(pred, hms)
    opt.zero_grad(); loss.backward(); opt.step()
Break it on purpose
The synthetic data has a bug

make_synthetic_sample draws four identical black squares, and heat-map channel k must find square k, the k-th row of a random array. Look at the image as the network does: can anything in it tell channel 0 which of the four squares is "its" square? Predict what a trained model outputs, then check under "Use it". (Solution B1.)

COLOURS = np.array([[0.8, 0.1, 0.1], [0.1, 0.6, 0.1], [0.1, 0.1, 0.8], [0.0, 0.0, 0.0]], dtype=np.float32)
def make_coloured_sample(size=64):                 # same as make_synthetic_sample, but keypoint k has colour k
    img = np.ones((3, size, size), dtype=np.float32)
    kps = np.random.default_rng().integers(8, size - 8, size=(4, 2))
    for k, (cx, cy) in enumerate(kps):
        img[:, cy - 2:cy + 2, cx - 2:cx + 2] = COLOURS[k][:, None, None]
    return img, np.stack([gaussian_heatmap(size, cx, cy) for cx, cy in kps]), kps

def train_keypoints(sampler, steps=300):
    torch.manual_seed(0)
    net = TinyKeypointNet(num_keypoints=4)
    opt = torch.optim.Adam(net.parameters(), lr=3e-3)
    for _ in range(steps):
        batch = [sampler() for _ in range(16)]
        imgs = torch.from_numpy(np.stack([b[0] for b in batch]))
        hms = torch.from_numpy(np.stack([b[1] for b in batch]))
        loss = F.mse_loss(net(imgs), hms)
        opt.zero_grad(); loss.backward(); opt.step()
    return net.eval()

Recap
What to keep from this lesson
  • A pose is an ordered set of keypoints; each keypoint gets its own heat map, and the argmax gives its location.
  • Refine the argmax to sub-pixel precision; a quarter-pixel shift or a log-parabola fit beats plain argmax.
  • Keypoints must be distinguishable for heat-map regression to work, and augmentations must keep left and right consistent.
  • Top-down (detect, then pose each crop) leads on accuracy; bottom-up (keypoints plus grouping, e.g. PAFs) scales to crowds.
  • COCO uses 17 keypoints and OKS-based mAP.

Solutions

SolutionP1 · Twenty pixels versus half a pixel

On the lesson's data the average error is well over 10 pixels (the printed value; the data is random, so it varies a little from run to run), because each channel guesses which square is its own. With colour-coded keypoints it drops to under a pixel. The network, the loss and the training are identical; only whether the task is solvable changed.

SolutionB1 · Nothing identifies the keypoints

Nothing in the image says which square is keypoint 0. The best the network can do under MSE is to put a smaller blob on every square in every channel, the average of the four possibilities. The loss still falls, because blobs in the right places beat a blank map, so the training curve looks healthy while the coordinates are wrong. The fix is to make keypoints distinguishable (colour here; anatomy and context in real images) or to switch to a set-based loss that does not care about order.

You are a pose-estimation stack selector.

## Inputs

- `target`: human_body | face | hand | object_pose_custom
- `dimension`: 2D | 3D
- `max_people`: 1 | small_group (2-10) | crowd (10+)
- `latency_target_ms`: p95 per frame

## Decision

### Human body 2D

- `latency_target_ms < 20` and `stack == mobile | browser` -> **MediaPipe Pose** (Lite / Full / Heavy). Production default.
- `max_people == 1` and `latency_target_ms > 30` -> **ViTPose-B** (accuracy).
- `max_people == small_group` -> **YOLOv8-pose** (top-down with person detector + HRNet head if accuracy matters).
- `max_people == crowd` -> **YOLOv8-pose** (real-time bottom-up) or **HigherHRNet** (accurate bottom-up).

### Human body 3D

- `max_people == 1` and single camera -> lift from 2D using **MotionBERT** or **MHFormer** over a short temporal window.
- multi-camera calibrated -> triangulate 2D predictions per view, then optimise with **SMPL** or **SMPL-X** body model.
- never rely on single-image 3D lifting when absolute depth is required; it predicts only relative pose.

### Face landmarks

- mobile / browser -> **MediaPipe Face Mesh** (478 keypoints, real-time).
- high accuracy, offline -> **3DDFA_V2** or **DECA** (3D face).

### Hand

- real-time -> **MediaPipe Hands** (21 keypoints).
- research-quality -> **MANO-based 3D hand reconstructors**.

### Custom object pose

- `dimension == 2D` -> train an HRNet-style heatmap head on your dataset; 500+ annotated images minimum.
- `dimension == 3D` -> EPnP on detected 2D keypoints + known object model, or learning-based PoseCNN / DeepIM.

# Heatmap to Coords

Turn raw keypoint heatmaps into sub-pixel precise coordinates. The cheapest accuracy upgrade in every pose pipeline.

## When to use

- Deploying a heatmap-based keypoint model.
- Benchmarking pose metrics — OKS is extremely sensitive to sub-pixel accuracy.
- Porting pose code from one framework to another.

## Inputs

- `heatmaps`: `(N, K, H, W)` tensor, per-keypoint heatmaps from the model.
- `confidence_threshold`: discard keypoints whose peak is below this value.

## Steps

1. **Argmax** each heatmap to find the integer peak location.
2. **First-difference offset** — estimate sub-pixel offset from neighbouring pixels. The `0.25` coefficient is a heuristic calibrated for Gaussian heatmaps with `sigma >= 1`; for principled sub-pixel recovery, use a full quadratic fit (DARK) or a Gaussian fit.

```
dx = 0.25 * sign(heatmap[y, x+1] - heatmap[y, x-1])
dy = 0.25 * sign(heatmap[y+1, x] - heatmap[y-1, x])
```

For the DARK / quadratic variant, approximate using a local quadratic:

```
dx = -0.5 * (heatmap[y, x+1] - heatmap[y, x-1])
        / (heatmap[y, x+1] - 2 * heatmap[y, x] + heatmap[y, x-1] + eps)
```

The quadratic fit is more accurate on peaked heatmaps; the sign-based offset is the safer default when heatmaps are noisy.

3. **Add offset** to the integer peak.
4. **Confidence** — return the peak value per keypoint; clients use it to mask low-confidence predictions.
5. **Boundary case** — when the peak lands on the first or last pixel along an axis, one of the neighbours is clamped; the offset collapses to zero, which is the safest fallback.

## Output template

```python
import torch

def heatmap_to_coords_subpixel(heatmaps, threshold=0.2):
    N, K, H, W = heatmaps.shape
    flat = heatmaps.reshape(N, K, -1)
    conf, idx = flat.max(dim=-1)
    ys = (idx // W).float()
    xs = (idx % W).float()

    ys_int = ys.long()
    xs_int = xs.long()

    x_minus = (xs_int - 1).clamp(min=0)
    x_plus = (xs_int + 1).clamp(max=W - 1)
    y_minus = (ys_int - 1).clamp(min=0)
    y_plus = (ys_int + 1).clamp(max=H - 1)

    batch_idx = torch.arange(N).view(-1, 1).expand(-1, K)
    kp_idx = torch.arange(K).view(1, -1).expand(N, -1)

    dx_raw = (heatmaps[batch_idx, kp_idx, ys_int, x_plus]
              - heatmaps[batch_idx, kp_idx, ys_int, x_minus])
    dy_raw = (heatmaps[batch_idx, kp_idx, y_plus, xs_int]
              - heatmaps[batch_idx, kp_idx, y_minus, xs_int])
    dx = 0.25 * torch.sign(dx_raw)
    dy = 0.25 * torch.sign(dy_raw)

    at_left = xs_int == 0
    at_right = xs_int == (W - 1)
    at_top = ys_int == 0
    at_bottom = ys_int == (H - 1)
    dx = torch.where(at_left | at_right, torch.zeros_like(dx), dx)
    dy = torch.where(at_top | at_bottom, torch.zeros_like(dy), dy)

    refined_x = xs + dx
    refined_y = ys + dy
    coords = torch.stack([refined_x, refined_y], dim=-1)
    mask = conf >= threshold
    return coords, conf, mask
```

## Report

```
[subpixel decode]
  keypoints:   K
  threshold:   <float>
  valid_rate:  fraction of keypoints above threshold
```

## Rules

- Always clamp neighbour indices to valid range; off-edge keypoints have zero-difference offset but no crash.
- Return confidence alongside coordinates so clients can mask low-confidence points.
- Sub-pixel refinement only helps when the heatmap is smooth around the peak — check that training used a Gaussian target with sigma >= 1.
- For very small heatmap resolutions (< 48x48), consider upsampling the heatmap to full image size before extracting coordinates; the sub-pixel offset scales with the stride.
