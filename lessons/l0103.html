Why this came about

A model does not compute one fixed answer; it produces probabilities for every possible next token and picks one. That design, inherited from language modeling, is what makes outputs varied and sometimes creative, and also what makes them unpredictable. Settings such as temperature exist to control that randomness, and choosing a model became a trade between quality, speed and cost as the number of available models exploded.

In plain words first
Rolling weighted dice for each word

At every step the model produces a score for every possible next token, turns the scores into probabilities, and then samples: it picks one at random, weighted by those probabilities. Temperature stretches or flattens the weights: low temperature almost always picks the top choice, high temperature takes more chances. Because of that sampling, and because providers' servers are not perfectly deterministic, the same prompt can give different answers. Code that depends on a model must therefore check its outputs rather than expect exact text.

Sampling: why the same prompt gives different answers

How this connects
You have seen this before

Lesson 1.10 introduced softmax and temperature, and Lesson 7.19 built greedy, top-k and top-p decoding on a real model. This lesson does not re-teach them. It takes the engineering consequence, that the same prompt can give different answers, and shows what to do about it. The short code section further down is a recap you can skim.

At each step the model produces a probability for every possible next token, then samples one.

  • Temperature flattens (higher) or sharpens (lower) those probabilities. Use low values for extraction and classification.
  • Top-p (nucleus sampling) samples only from the smallest set of tokens whose probabilities add up to p.

Even at temperature 0, outputs are not guaranteed identical: batching and hardware make tiny numeric differences. Many reasoning models ignore or forbid temperature settings. Design for non-determinism: validate outputs, run evals several times, and never rely on exact wording.

In plain words first
What an "eval" is, since the word appears from here on

An eval (short for evaluation) is a repeatable test for a model or a system built on one. In its simplest form it is a list of inputs, each with a note of what a good answer must contain, and a small program that runs every input and counts how many answers pass. For example: 30 real customer questions, the correct order status for each, and a check that the reply contains that status. The list is called an evaluation set (or eval set, or golden set).

Evals matter more with language models than with ordinary code, for two reasons you have just met: the output varies from run to run, and a change that fixes one case can quietly break another. So you run the whole set after every change, and you run each case several times. The score pass^k ("pass to the k") is the share of cases that pass on all of k runs: a case that passes two times out of three does not count.

You will build evals in stages: tests for prompts in Lesson 11.9, an evaluation set for retrieval in Lesson 14.27, and the full method in Lessons 14.117 and 14.118. Until then, read "your evals" as "your own list of test cases with a pass or fail check".

In production
Non-determinism in production

The symptoms: a test that passes on Monday fails on Tuesday with no change; two customers asking the same question get different answers; a regex that parses the model's output breaks once a week. The fixes are structural, not "set temperature to 0": structured outputslater · 11.2 instead of parsing prose, fixed workflows for paths that must be identical every time, evals run several times per case and reported as pass^k, and caching answers where the same question should always get the same reply.

Sampling: temperature, top-k and top-p

At every step the model outputs a score (a logit) for each token in its vocabulary. Softmax turns scores into probabilities; temperature divides the logits first (low temperature sharpens, high flattens); top-k and top-p cut off the unlikely tail before sampling.

import numpy as np

vocab = ["shipped", "delivered", "delayed", "lost", "banana"]
logits = np.array([3.2, 2.9, 1.5, 0.3, -2.0])          # the model's scores for the next token

def next_token_probs(logits, temperature=1.0, top_k=None, top_p=None):
    z = logits / max(temperature, 1e-6)
    p = np.exp(z - z.max()); p /= p.sum()                # softmax, numerically stable
    order = np.argsort(-p)
    keep = np.ones_like(p, dtype=bool)
    if top_k is not None:
        keep[order[top_k:]] = False
    if top_p is not None:                                # keep the smallest set whose probability reaches top_p
        cum = np.cumsum(p[order])
        keep[order[np.searchsorted(cum, top_p) + 1:]] = False
    p = np.where(keep, p, 0); return p / p.sum()

for setting in [dict(temperature=1.0), dict(temperature=0.2), dict(temperature=1.5), dict(temperature=1.0, top_p=0.8)]:
    p = next_token_probs(logits, **setting)
    print(f"{str(setting):38}", " ".join(f"{w}={x:.2f}" for w, x in zip(vocab, p)))

rng = np.random.default_rng(0)
samples = [vocab[rng.choice(5, p=next_token_probs(logits, temperature=1.0))] for _ in range(10)]
print("ten samples at temperature 1.0:", samples)

This is why the same prompt can say "shipped" one time and "delivered" the next, and why extraction and classification use low temperatures. Top-p removed "delayed", "lost" and "banana" entirely, which is how nucleus sampling avoids rare nonsense while keeping variety.

Choosing a model with a scoring matrix

How this connects
How this builds on Lesson 10.33

Lesson 10.33 gave a four-step method for picking a model (write down what good looks like, try a strong model, try cheaper ones, check the non-quality needs) and showed how to run models yourself. The two sections below turn that method into something you can keep in code and repeat per step of an agent, and add what to do when a choice stops working.

Model choice is a weighted decision over your own eval results, not leaderboard positions. Keep the matrix in code so it is rerun when prices, models or your evals change.

candidates = {                      # your eval set's results, your measured latency, current prices
    "frontier-large": {"quality": 0.93, "p95_s": 9.0, "usd_per_task": 0.041},
    "frontier-mid":   {"quality": 0.90, "p95_s": 4.5, "usd_per_task": 0.012},
    "small-fast":     {"quality": 0.78, "p95_s": 1.8, "usd_per_task": 0.002},
}
MIN_QUALITY = 0.85                  # a hard floor: below it, cost and speed do not matter
weights = {"quality": 0.6, "p95_s": 0.2, "usd_per_task": 0.2}

def score(m):
    best = {k: (max if k == "quality" else min)(c[k] for c in candidates.values()) for k in weights}
    parts = {"quality": m["quality"] / best["quality"],
             "p95_s": best["p95_s"] / m["p95_s"], "usd_per_task": best["usd_per_task"] / m["usd_per_task"]}
    return sum(weights[k] * parts[k] for k in weights)

for name, m in sorted(candidates.items(), key=lambda kv: -score(kv[1])):
    flag = "" if m["quality"] >= MIN_QUALITY else "  (below quality floor)"
    print(f"{name:15} score {score(m):.2f}{flag}")
What you should see
small-fast      score 0.90  (below quality floor)
frontier-mid    score 0.69
frontier-large  score 0.65

The cheapest model scores best on paper but fails the quality floor, so the choice is frontier-mid. A common production answer combines them: route easy requests to the small model and the rest to the mid model, then prove the router with evals (Lesson 14.116).

Choosing a model: a method that lasts

  1. Write 30 to 100 real test cases for the step (Lesson 14.117 shows how). Public leaderboards are a shortlist, not a decision.
  2. Shortlist three models across price tiers, including one small model.
  3. Measure quality, cost per task, p95 latency and failure modes (refusals, bad JSON, wrong tool).
  4. Check the non-functional needs: data residency (for example, an Indian region), context length, tool-calling reliability, rate limits, and whether the model is available on your cloud.
  5. Pick per step, not per product. A router on a small model and a planner on a frontier model is normal.
  6. Pin the exact version and re-run the tests before any upgrade.
Industry practice
Start with the best model, then step down

OpenAI's A practical guide to building agents recommends building the first prototype with the most capable model to set a quality baseline, then swapping in smaller models step by step where the evals stay green. Anthropic's guidance says the same in other words: get it working, measure, then optimize cost.

Solutions

SolutionP1 · Temperature zero is not determinism

It picks the most likely token (greedy). Outputs can still differ because of batching and floating-point effects on the provider's side, model updates and ties. Design for variation.

SolutionB1 · Interacting settings

Top-p keeps only the few most likely tokens, so high temperature has little room to add variety; the combination is hard to reason about. Change one setting at a time and measure.

SolutionD1 · Weights and evidence

The matrix weighted public benchmarks and price over task-specific evals and latency, or scores were guessed rather than measured. Score on your own eval set and real constraints.

SolutionM1 · Measure what matters

For agents, tool-use reliability often decides; adding it can reorder models that look similar on general benchmarks.

Check your understanding

Explain the mechanismHow do temperature, top-k and top-p work?

Worked answer. The model outputs a probability for every next token. Temperature rescales the distribution (lower is sharper, higher is flatter); top-k keeps only the k most likely tokens; top-p keeps the smallest set whose probabilities sum to p. Then a token is sampled. Reasoning models often fix or ignore some of these settings.

A plausible wrong answer. "Temperature controls creativity." It controls randomness; creativity comes from the prompt and model.

Follow-ups. Which settings would you use for extraction?

Debug a failureTests that compare exact model outputs fail randomly. What do you change?

Worked answer. Test facts and structure, not exact text; use structured output; run evals with several samples; and keep exact-match tests for deterministic code with fake models.

A plausible wrong answer. "Set temperature to zero." Helps, but does not guarantee identical outputs.

Follow-ups. How would you test free-text answers?

Defend a designHow do you choose a model for a new product?

Worked answer. Define requirements (quality bar, latency, cost, context, languages, data terms), shortlist with benchmarks and docs, build a task eval, score candidates on it with cost and latency, and keep the decision revisitable with a gateway. Re-run when new models arrive.

A plausible wrong answer. "Use the most capable model." It may be too slow or costly for the task.

Follow-ups. How often would you re-evaluate?
