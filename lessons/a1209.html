The problem

In plain words first

Qwen-VL is Alibaba's family of open vision-language models, and the most widely used open line in 2025–2026. Its designs answer two practical questions. First, how to read an image of any shape without squashing or tiling it: cut it into 14-pixel patches at close to its real size, merge each 2×2 group into one token, and give every token its row and column through a 3D position code called M-RoPE. Second, how to know when something happened in a video: sample frames at a chosen rate and attach each frame's real time, first inside the position code (Qwen2.5-VL), later as plain text like "<3.2 seconds>" (Qwen3-VL). This lesson follows the four generations, then runs the real Qwen preprocessing code (configuration and tokenizer files only, no weights) to count tokens and inspect the time encoding. No model is trained or downloaded.

Qwen-VL shipped in August 2023 as a direct response to LLaVA-1.5 and BLIP-2. The gap the Qwen team targeted was threefold: resolution, video, and structured output.

Resolution: LLaVA-1.5 ran at 336x336. Fine for photos, useless for a Chinese-language invoice or a dense spreadsheet screenshot. Qwen-VL's first innovation was 448x448 and grounded bounding-box output, letting the model point at things.

Video: Video-LLaMA stacked per-frame encoders and fed them to the LLM. It worked for short clips, not for multi-minute videos where the temporal axis is the signal. The Qwen team wanted a single encoder that understood time.

Structured output: LLaVA emitted free-form text. An agent needs JSON. Qwen-VL trained on explicit JSON output formats including bounding-box coordinates as text.

Every Qwen-VL generation extends one of these three axes.

Idea 1 · Qwen-VL (August 2023)

The first generation: a ViT of about 1.9B parameters initialised from OpenCLIP ViT-bigG/14, a single cross-attention layer with 256 learnable queries that compresses each image to 256 tokens (about 0.08B parameters, similar in spirit to a Q-Former), and Qwen-7B as the language model; about 9.6B parameters in all. Contributions:

  • 448x448 resolution (then SOTA for an open VLM).
  • Grounding: trained on image-text pairs with explicit coordinate-token output. "The cat is at (112, 204), (280, 344)".
  • Chinese + English multilingual training from the start.

The grounding supervision was the real headline: boxes written as plain text with coordinates normalised to [0, 1000), between <box> tags, so no new vocabulary was needed.

Idea 2 · Qwen2-VL (September 2024) — M-RoPE and native resolution

Qwen2-VL replaced the fixed-resolution + Q-Former stack with a natively dynamic-resolution ViT encoder. Key changes:

  • Native dynamic resolution. Each image is resized only slightly, to multiples of 28 pixels within a minimum and maximum pixel count (patch 14 with 2x2 spatial merge). An image at 1120x672 (40x24 merged patches) produces 960 visual tokens. No tiling, no thumbnail.
  • M-RoPE (Multimodal RoPE). Each token carries a 3D position (t, h, w) instead of 1D. For images t=0, for video t = frame_index. RoPE rotates query/key vectors by a frequency per axis. No positional embedding table.
  • MLP projector. Drop the Q-Former; use a 2-layer MLP on the merged patch tokens.
  • Video with dynamic FPS. Video sampled at 1-2 FPS by default, but the model accepts arbitrary frame counts.

Result: Qwen2-VL-7B reached 94.5 on DocVQA, and the 72B model was competitive with GPT-4o on many multimodal benchmarks. The architecture change was the decisive move.

Idea 3 · Qwen2.5-VL (February 2025) — dynamic FPS + absolute time

Qwen2.5-VL's big shift was video. Dynamic FPS is not just "sample more frames when needed." The paper formalized:

  • Absolute time in the position IDs. Instead of frame indices (frame 0, 1, 2...), the temporal axis of M-RoPE follows actual timestamps, so the gap between two frames' IDs tracks the seconds between them. "At 0:04, the cat jumps." No extra text tokens carry the time, so the encoding adds no sequence length.
  • Dynamic FPS. Sample at 1 FPS for slow footage, 4+ FPS for action. The user or trainer chooses; M-RoPE adapts.
  • Window attention in ViT. Spatial attention is windowed (local within blocks) for throughput; global attention every few layers.
  • Structured outputs for grounding and agents. Boxes and points are emitted as JSON with absolute pixel coordinates of the resized image (Qwen2-VL used coordinates normalised to 0–1000), and the model was trained on agent and tool-use trajectories.
  • Efficient training and inference at scale: the vision encoder was retrained with window attention, RMSNorm and SwiGLU, so large images and long videos stay affordable.

Benchmarks: the Qwen2.5-VL report places the 72B model level with GPT-4o and Claude 3.5 Sonnet on many document, video and agent benchmarks, and well ahead on some document and GUI-grounding tasks.

Idea 4 · Qwen3-VL (November 2025)

Qwen3-VL (models from September 2025, technical report November 2025) comes in dense 2B, 4B, 8B and 32B sizes and as 30B-A3B and 235B-A22B mixture-of-experts models, with a native 256K-token context. Three architectural changes: interleaved MRoPE (the t, h and w frequencies are interleaved across the dimension instead of split into blocks), DeepStack (features from several ViT layers are fed into the LLM, not just the last one), and text-based timestamps: instead of encoding time in the position ids, each group of frames is preceded by a text marker such as <1.2 seconds> (measured below).

The lineage takeaway: by 2025 the basic recipe (native-resolution ViT, 2x2 merge, MLP, LLM) had stabilized. Later generations change how position and time are encoded and scale data and compute.

Idea 5 · M-RoPE mathematically

Classical RoPE rotates a query q of dimension d by position m using paired coordinates:

qrot​[2i]qrot​[2i+1]θi​​=q[2i]cos(mθi​)−q[2i+1]sin(mθi​)=q[2i]sin(mθi​)+q[2i+1]cos(mθi​)=10000−2i/d​

M-RoPE splits the hidden dim into three bands. Say d = 96. Assign 32 dims to temporal, 32 to height, 32 to width. Each band rotates by its own axis position. A patch at (t=5, h=10, w=20) gets rotations R_t(5), R_h(10), R_w(20) applied to its three bands.

Text tokens use the same value on all three axes, t = h = w = text_index, so for pure text M-RoPE reduces to ordinary 1D RoPE. Image tokens share one t and take their row and column as h and w; video tokens take t from the frame time. Positions after an image or video continue from the largest id used so far.

The benefit: one position encoding handles text, image, and video without branching code or different position tables.

Idea 6 · Dynamic-FPS sampling logic

Given a video of duration T seconds and a target-tokens budget B:

  1. Compute the maximum FPS you can afford: fps_max = B / (T * tokens_per_frame).
  2. Pick a target FPS from {1, 2, 4, 8} that satisfies fps <= fps_max.
  3. If motion is high (optical-flow heuristic or explicit user request), pick higher FPS. If motion is low, pick lower.
  4. Sample uniformly at the chosen FPS; set each frame's M-RoPE temporal ID from its timestamp in seconds.

Qwen2.5-VL trains this logic implicitly; at inference the user controls via fps parameter. A 60-second action sequence at 4 FPS with 81 tokens per frame = 19440 tokens, manageable in a 32k context.

The same idea as a formula

Image tokens. After resizing W×H to multiples of 28 within the pixel limits, with 14-px patches and 2×2 merging:

nimage​=28W​⋅28H​.

Video tokens. Frames are sampled at rate f from a clip of D seconds and merged in pairs (temporal patch 2):

nvideo​=2fD​⋅28W​⋅28H​.

Absolute time in M-RoPE (Qwen2.5-VL). Frame pair k starts at time sk​ seconds; its temporal position id is

tk​=t0​+⌊sk​⋅r⌋,r=2 position units per second,
so ids follow seconds, not frame counts. Qwen3-VL instead writes sk​ as text before each frame pair.

Worked example
A 1920×1080 screenshot and a one-minute clip
  • Screenshot: 1920/28≈68.6 and 1080/28≈38.6; the processor resizes to 1932 × 1092, i.e. 69×39=2,691 tokens. (Claude's image-token rule, also one token per 28 × 28 pixels, gives the same 2,691.)
  • With max_pixels = 512 × 28 × 28 = 401,408, the image is scaled down to fit: about 480 tokens.
  • One minute of 448 × 252 video at 2 fps: 120 frames → 60 frame pairs, each 16×9=144 tokens → 8,640 tokens. At 4 fps, 17,280.
  • Absolute time: at 2 fps, pairs are 1 s apart and the temporal ids step by 2; at 0.5 fps, 4 s apart and the ids step by 8.
Check your mental model
  • ✗ "Native resolution means no resizing at all."
    ✓ Images are rounded to multiples of 28 and kept within min/max pixel limits you control.
  • ✗ "The model sees one token per video frame."
    ✓ Two consecutive frames merge into one temporal step, and every step has many spatial tokens.
  • ✗ "Frame index tells the model the time."
    ✓ Only if the sampling rate is fixed; Qwen2.5-VL ties positions to seconds, and Qwen3-VL writes timestamps as text.

Image and video tokens, from the real processor

Qwen2.5-VL's Hugging Face processor (configuration and tokenizer files of the 3B model, no weights) counts the visual tokens for five image shapes, with and without a max_pixels cap. It does the same for a 60-second video sampled at 0.5 to 4 frames per second. A few seconds.

import warnings; warnings.filterwarnings("ignore")
import numpy as np
from PIL import Image
from transformers import AutoConfig, AutoProcessor, logging
from transformers.video_utils import VideoMetadata
logging.set_verbosity_error()

# Qwen2.5-VL's real processor (config and tokenizer files only, no weights): native resolution, no tiling
repo = "Qwen/Qwen2.5-VL-3B-Instruct"
proc, cfg = AutoProcessor.from_pretrained(repo), AutoConfig.from_pretrained(repo)
ask = lambda kind: proc.apply_chat_template([{"role": "user", "content": [{"type": kind}, {"type": "text", "text": "?"}]}],
                                            add_generation_prompt=True)
print("images: 14-px patches, 2x2 merged -> one token per 28x28 pixels")
print(f"{'image (w x h)':<16}{'patch grid':>12}{'LLM tokens':>12}{'  with max_pixels = 401,408':>28}")
for w, h in [(224, 224), (1120, 672), (1080, 1920), (1920, 1080), (3840, 2160)]:
    img = Image.new("RGB", (w, h))
    x = proc(images=img, text=ask("image"), return_tensors="pt")
    capped = proc(images=img, text=ask("image"), return_tensors="pt", images_kwargs={"max_pixels": 512 * 28 * 28})
    _, gh, gw = x.image_grid_thw[0].tolist()
    print(f"{f'{w} x {h}':<16}{f'{gh} x {gw}':>12}{gh * gw // 4:>12,}{capped.image_grid_thw[0].prod().item() // 4:>28,}")

# video: a 60-second clip (stand-in frames, 448 x 252, source 10 fps) sampled at different rates
src = np.zeros((600, 252, 448, 3), np.uint8)
meta = VideoMetadata(total_num_frames=600, fps=10.0, duration=60.0, video_backend="numpy")
print(f"\nvideo: 60 s at 448 x 252; frames are merged in pairs (temporal patch 2)")
print(f"{'sampling fps':<14}{'frames':>8}{'temporal steps':>16}{'LLM tokens':>12}{'tokens / second':>17}")
for fps in [0.5, 1, 2, 4]:
    x = proc(text=ask("video"), videos=[src], video_metadata=[meta], return_tensors="pt",
             videos_kwargs={"fps": fps, "do_sample_frames": True, "cap_pixels_per_frame": True})
    t, gh, gw = x.video_grid_thw[0].tolist()
    print(f"{fps:<14}{2 * t:>8}{t:>16}{t * gh * gw // 4:>12,}{t * gh * gw // 4 / 60:>17,.0f}")

Reading this output

One token per 28 × 28 pixels, at almost any shape. A 224 × 224 image is 64 tokens, the lesson's 1120 × 672 example is 960, and a 1080 × 1920 phone screenshot is 2,691, the same as its landscape twin. Nothing is tiled or squashed: the grid simply follows the image (138 × 78 patches tall, 78 × 138 wide).

Large images get expensive fast. A 4K screenshot costs 10,549 tokens by default. The processor's default ceiling is very high (about 12.8 megapixels), so in practice you choose the budget.

max_pixels is the budget knob. Capping at 401,408 pixels (512 tokens' worth) shrinks every large image to about 480–493 tokens while keeping its aspect ratio; small images are unaffected. Use a high cap for documents and small text, a low one for photos.

Video cost is linear in frame rate. A minute of 448 × 252 video costs 144 tokens per frame pair: 2,160 tokens at 0.5 fps and 17,280 at 4 fps, 36 to 288 tokens per second of footage. Frames are always merged in pairs, so 30 sampled frames become 15 temporal steps. A 10-minute video at 4 fps would already be about 173,000 tokens at this small size.

How the model learns when a frame happened

Qwen2.5-VL's 3B model is built on PyTorch's meta device (no weights) and asked for the (t, h, w) position ids it gives a 16-frame clip, assuming the clip was filmed at 2 fps and at 0.5 fps. Then Qwen3-VL's processor shows how it writes the same timing into the prompt as text. A few seconds.

import re, torch, numpy as np
from transformers import AutoConfig, AutoProcessor, Qwen2_5_VLForConditionalGeneration
from transformers.video_utils import VideoMetadata
# How the model knows *when* a frame happened. 16 frames of a clip, read at two different source frame rates.

# Qwen2.5-VL: absolute time inside M-RoPE. Build the model on the meta device (no weights) and ask it for the
# 3D position ids (t, h, w) it would give every token.
repo = "Qwen/Qwen2.5-VL-3B-Instruct"
p25, c25 = AutoProcessor.from_pretrained(repo), AutoConfig.from_pretrained(repo)
with torch.device("meta"):
    m25 = Qwen2_5_VLForConditionalGeneration(c25)
text = p25.apply_chat_template([{"role": "user", "content": [{"type": "video"}, {"type": "text", "text": "When?"}]}],
                               add_generation_prompt=True)
frames = np.zeros((16, 224, 224, 3), np.uint8)
print("Qwen2.5-VL: temporal position id of each group of video tokens")
for fps in [2.0, 0.5]:
    meta = VideoMetadata(total_num_frames=16, fps=fps, duration=16 / fps, video_backend="numpy")
    x = p25(text=text, videos=[frames], video_metadata=[meta], return_tensors="pt",
            videos_kwargs={"do_sample_frames": False, "cap_pixels_per_frame": True})
    pos, _ = m25.model.get_rope_index(x.input_ids, x.mm_token_type_ids, None, x.video_grid_thw,
                                      x.second_per_grid_ts, x.attention_mask)
    vid = (x.input_ids[0] == c25.video_token_id).nonzero()[:, 0]
    t_ids = sorted(set(pos[0, 0, vid].tolist()))
    print(f"  clip at {fps} fps ({16 / fps:.0f} s): {x.second_per_grid_ts.item():.0f} s per frame pair, t ids {t_ids}")
    print(f"     first text token (t, h, w) = {tuple(pos[:, 0, 0].tolist())}; "
          f"video tokens of the first frame pair: (t, h, w) from {tuple(pos[:, 0, vid[0]].tolist())} to {tuple(pos[:, 0, vid[63]].tolist())}")

# Qwen3-VL: the time is written into the prompt as text
repo = "Qwen/Qwen3-VL-2B-Instruct"
p3 = AutoProcessor.from_pretrained(repo)
text = p3.apply_chat_template([{"role": "user", "content": [{"type": "video"}, {"type": "text", "text": "When?"}]}],
                              add_generation_prompt=True)
meta = VideoMetadata(total_num_frames=16, fps=2.0, duration=8.0, video_backend="numpy", frames_indices=list(range(16)))
x = p3(text=text, videos=[np.zeros((16, 256, 256, 3), np.uint8)], video_metadata=[meta], return_tensors="pt",
       videos_kwargs={"do_sample_frames": False})
s = p3.tokenizer.decode(x.input_ids[0])
s = re.sub(r"(<\|video_pad\|>)+", lambda m: f"[{m.group(0).count('<|video_pad|>')} tokens]", s)
print("\nQwen3-VL: the same 2-fps clip as the model reads it")
print("  " + s.split("<|im_start|>user\n")[1].split("When?")[0].replace("<|vision_start|>", "").replace("<|vision_end|>", " "))

Reading this output

Qwen2.5-VL: the clip's real duration changes the positions. The 16 frames and pixels are identical in both runs. Only the assumed frame rate differs. At 2 fps each frame pair spans 1 second, and the temporal ids step by 2 (15, 17, 19, …). At 0.5 fps each pair spans 4 seconds, and they step by 8 (15, 23, 31, …). Two position units per second means the model can read elapsed time directly from the distance between ids, whatever rate was used to sample.

Text and images share one coordinate system. The first text token sits at (0, 0, 0): text uses equal t, h and w. The first frame pair's 64 tokens all share t = 15 and span an 8 × 8 grid of h and w (15 to 22). This is M-RoPE: one position code for text, image and video.

Qwen3-VL writes the time as text. The same 2-fps clip arrives as <0.2 seconds> followed by 64 visual tokens, then <1.2 seconds>, and so on. The timestamps are ordinary tokens the model can read and repeat, which makes it easier to answer "at what second does X happen". It costs a few extra tokens per frame pair.

Idea 7 · Structured agent output

Qwen2.5-VL's agent training explicitly targets structured tool calls:

{
  "tool": "mouse_click",
  "coords": [1024, 512],
  "button": "left",
  "modifier": null
}

Parsing is deterministic: JSON.parse over the model's output. Compare to free-form "click at (1024, 512)" which required regex and ambiguity handling. Validate the parsed coordinates against the image size anyway.

Industry practice
What's current (2024–2026)
  • Qwen3-VL (September 2025 onwards): 2B to 32B dense and 30B-A3B / 235B-A22B mixture-of-experts models, 256K context, interleaved MRoPE, DeepStack and text timestamps; "Thinking" variants for reasoning.
  • Laptop-sized models: on an 8 GB GPU, Qwen3-VL-2B (about 4.5 GB of weights in bf16) runs with room for images. Qwen3-VL-4B and Qwen2.5-VL-3B (about 7.5–9 GB in bf16) need 8-bit or 4-bit quantization, and 7B–8B models need 4-bit. Always set max_pixels and the video fps or frame count, since visual tokens also need KV-cache memory.
  • Serving: vLLM and SGLang support Qwen-VL models with per-request image and video limits; llama.cpp and Ollama run quantized versions locally.
  • Grounding and agents: JSON boxes and points, GUI agents and document parsing are standard uses, built on the native-resolution design.

Sources: Qwen-VL (arXiv 2308.12966), Qwen2-VL (arXiv 2409.12191), Qwen2.5-VL technical report (arXiv 2502.13923), Qwen3-VL technical report (arXiv 2511.21631), Hugging Face Qwen2.5-VL documentation.

Recap
What to keep from this lesson
  • Native resolution: one token per 28 × 28 pixels, no tiling; cap it with max_pixels.
  • M-RoPE gives every token (t, h, w); text uses the same value on all three.
  • Video: frames sampled at a chosen fps, merged in pairs; tokens grow with fps × duration × area.
  • Time: Qwen2.5-VL puts seconds into the position ids; Qwen3-VL writes timestamps as text.
  • Budget every request: pixels, fps and frame limits decide cost and whether it fits your GPU.

Given a task description (image QA, video action recognition, UI-agent workflow, OCR-heavy document, security-camera monitoring, streaming live feed) and a deployment constraint (context window, latency budget, GPU class), emit a runnable Qwen2.5-VL or Qwen3-VL configuration.

Produce:

1. Resolution bounds. `min_pixels` and `max_pixels` picked for the task. Documents and UI: max high (>=1,806,336 = 1344x1344 equivalent). Photos: default. Video frames: lower to preserve frame count.
2. FPS policy. Fixed 1 FPS for low-motion; dynamic 2-4 for medium; 4-8 for high. Absolute-time M-RoPE matters whenever the task involves temporal grounding.
3. Frame budget. Total tokens per video = duration * fps * tokens_per_frame. Fit into available context (leave 20% slack for prompt + output).
4. Window attention. Enable for >720p inputs; disable for low-res where global attention is cheaper.
5. Output mode. Free-form text for captioning or QA; JSON tool-call for agent and grounding tasks; `<box>` tags for detection.
6. Inference kwargs. Concrete dict the user passes to `process_vision_info` + model forward.

Hard rejects:
- Proposing Qwen2-VL (original, pre-2.5) as the default for new projects. It lacks dynamic FPS and absolute-time M-RoPE.
- Claiming M-RoPE requires a position table. It does not — that is its entire selling point.
- Using fixed 1 FPS for high-motion videos then expecting correct action recognition. The sampler must adapt.

Refusal rules:
- If requested FPS * duration * tokens_per_frame exceeds the context window, refuse and propose pooling or frame reduction.
- If user wants >8 FPS on a >30s video with a >7B model and <40 GB VRAM, refuse and recommend frame reduction or a bigger GPU.
- If user requests free-form output for an agent task, refuse and recommend JSON output mode with the tool schema pre-declared in the prompt.

Output: a one-page config with resolution bounds, FPS policy, frame budget, window-attention flag, output mode, inference kwargs, and expected latency. End with arXiv 2502.13923 (Qwen2.5-VL) and 2511.21631 (Qwen3-VL) for deeper follow-up.

Exercises

  1. Compute M-RoPE rotations for a patch at (t=3, h=5, w=7) with hidden 48 (16 per band, base theta 10000). Show the rotation angles for the first three pairs in each band.

  2. A 10-minute security-camera recording at 1 FPS produces how many frames? At 384 resolution with 3x pool, how many total tokens? Does Qwen2.5-VL's default 32k context handle it?

  3. Pick FPS for a 30-second tennis rally vs a 30-second recipe demo vs a 30-second UI-agent recording. Justify each with the dynamic-FPS logic.

  4. Qwen2.5-VL drops the Q-Former entirely. Why does a simple MLP work in 2025 but not in 2023? (Hint: data scale and encoder quality.)

  5. Parse three Qwen2.5-VL JSON tool-call outputs into Python dicts. What fails for malformed JSON and what recovery strategy does the Qwen cookbook recommend?

Solutions

SolutionP1 · 10,549 tokens, or 480 with a cap

10,549 tokens with default settings: the 4K image becomes a 154 × 274 patch grid, merged 2×2. With max_pixels = 401,408 it is scaled down to keep its aspect ratio and costs 480 tokens, about 22 times fewer. The default ceiling is so high that large screenshots silently consume most of a context window unless you set the cap yourself.

SolutionB1 · Hundreds of thousands of tokens

At 1920 × 1080 every frame pair is about 69 × 39 = 2,691 tokens, before any per-frame cap the video path may apply. 10 minutes at 4 fps is 2,400 frames, or 1,200 frame pairs: on the order of three million tokens. That is far beyond any context window and far beyond an 8 GB GPU's memory for the KV cache. The request fails, or the serving stack truncates or rejects it. Even a version that fits would take minutes of prefill. Fix it with two settings, then check the token count before sending. Lower the frame rate (1 fps or less for screen recordings, which change slowly) or set a maximum number of frames. Set a per-frame pixel cap, so a frame costs a few hundred tokens instead of thousands. For long recordings, also split the video into segments and summarise each (Lesson 12.18 covers long video).
