About the model on this page
The model on this page is scripted

Each agent uses Lesson 14.58's scripted model, extended to record the tools it is given. The harness, its file tools, subagents, planning and permissions are the real deepagents library.

uv add deepagents

from deepagents import create_deep_agent, FilesystemPermission
from langchain.agents.middleware import TodoListMiddleware
from langchain_core.messages import AIMessage
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel

class ScriptedChatModel(GenericFakeChatModel):          # Lesson 6.8's scripted model, now recording its tools
    seen_tools: list = []
    def bind_tools(self, tools, **kwargs):
        self.seen_tools = [getattr(t, "name", None) or t.get("name") for t in tools]
        return self

def scripted(*replies):
    return ScriptedChatModel(messages=iter(list(replies)))

def call(name, args, id="c1"):
    return AIMessage("", tool_calls=[{"name": name, "args": args, "id": id}])
Why this came about

Coding agents in 2025 showed that long tasks need a harness: files, planning, subagents and context compaction. LangChain released Deep Agents as an open harness built on create_agent and middleware.

The problem: long tasks need more than a loop

"Investigate why last night's refund export failed and write an incident note" is not one question. It needs a plan, notes that outlive the context window, side investigations that should not flood the main conversation with log lines, and limits on what the agent may change. Lesson 14.13 called this a harness: the loop plus planning, files, subagents and context management. deepagents is LangChain's harness, built on create_agent and LangGraph, so everything from this chapter (checkpoints, interrupts, streaming, middleware) still applies.

In plain words first
The engine and the car

The model is an engine; create_agent adds a steering wheel, a loop that lets it call tools. A harness is the rest of the car, the parts long trips need: a place to keep notes and large results (files), the ability to send a helper on an errand who reports back (subagents), a route plan (a to-do list), automatic summarizing when the context fills up, and fences around what it may change (permissions). Deep Agents is LangChain's harness, built from middleware on LangGraph.

Idea 1 · What the harness gives the model

Create a deep agent with no tools of your own and ask what tools the model was offered anyway. The list that prints is the harness: a file system, a to-do list and a way to start subagents, added before you wrote anything.

model = scripted(AIMessage("Hello! What should I look into?"))
agent = create_deep_agent(model=model, tools=[], system_prompt="You are ShopKart's operations assistant.")
agent.invoke({"messages": [{"role": "user", "content": "hi"}]})
print("tools the harness gives the model:", model.seen_tools)
What you should see
tools the harness gives the model: ['ls', 'read_file', 'write_file', 'edit_file', 'delete', 'glob', 'grep', 'task']

File tools (ls, read_file, write_file, edit_file, delete, glob, grep) and task, which delegates work to a subagent. Large tool results can be written to files instead of kept in the conversation, which is the harness's main context-management trick: the agent keeps a short reference and reads back only what it needs.

Idea 2 · Files as working memory

The harness gives the agent files. By default they live in the agent's state, not on your disk, so they are saved with the conversation and cost nothing while they are not being read. The scripted model writes a short report to a file and reads it back:

model = scripted(call("write_file", {"file_path": "/reports/refund-export.md",
                                      "content": "# Refund export, 3 Nov\n- 2 payment timeouts at 02:10\n"}),
                 call("read_file", {"file_path": "/reports/refund-export.md"}, "c2"),
                 AIMessage("I wrote the report to /reports/refund-export.md."))
agent = create_deep_agent(model=model, tools=[])
out = agent.invoke({"messages": [{"role": "user", "content": "Write up last night's refund export."}]})
print("files in the state:", list(out["files"]))
print("read back:", [m.content for m in out["messages"] if m.type == "tool"][1].splitlines()[:2])
What you should see
files in the state: ['/reports/refund-export.md']
read back: ['@@ lines 1-2 of 2 @@', '# Refund export, 3 Nov']

By default the files live in the agent's state (a "state backend"), so they are saved with the thread's checkpoints and survive restarts, but are private to that thread. Other backends store them elsewhere: StoreBackend in the long-term store (Lesson 14.64), so files survive across conversations; FilesystemBackend on a real disk; CompositeBackend to route paths, for example /memories/ to the store and everything else to the state; and sandboxlater · 15.23 backends for running code.

Watch out
Host-access backends: for your laptop, not for a server

Two backends touch the real machine. FilesystemBackend(root_dir="./work") reads and writes real files; LocalShellBackend(root_dir="./work") adds an execute tool that runs shell commands with your user's permissions and no sandbox. They exist so that a coding assistant can edit the project on your own computer. Do not put them behind a web server, an API or anything multi-tenant: the agent can read any file it can reach (.env, keys), and once there is a shell, path rules are no protection at all. In deepagents 0.7.41 virtual_mode defaults to True, which blocks .. and paths outside root_dir; the docs page still describes the older default, so set it explicitly, and treat it as a guardraillater · 15.21, not a sandbox. The library's own advice: approval middleware on every call when you use these locally, and a sandbox backend (Lesson 15.23) when the agent must run code for other people.

Large results are offloaded for you

A tool result above a threshold (20,000 tokens by default) never enters the context. The harness writes it to /large_tool_results/<tool_call_id> and hands the model a short note with a preview and the path; the model reads back only the part it needs. The same happens to conversation history when the harness summarizes: the folded-away messages go to /conversation_history/<session_id>.md.

from langchain.tools import tool
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from langgraph.store.memory import InMemoryStore

@tool
def dump_logs(day: str) -> str:
    """Return the raw application log for one day (large)."""
    return "\n".join(f"{i:06d} INFO request ok latency=12ms" for i in range(6000))

model = scripted(call("dump_logs", {"day": "2026-11-01"}), AIMessage("No failed requests found."))
agent = create_deep_agent(model=model, tools=[dump_logs])
out = agent.invoke({"messages": [{"role": "user", "content": "How many requests failed on 2026-11-01?"}]})
tool_msg = next(m for m in out["messages"] if m.type == "tool")
saved = next(iter(out["files"]))
print("offloaded:", tool_msg.content.startswith("Tool result too large"), "| at:", saved.rsplit("/", 1)[0],
      "| chars:", len(out["files"][saved]["content"]))

backend = CompositeBackend(default=StateBackend(),
                           routes={"/memories/": StoreBackend(namespace=lambda rt: ("ops",))},
                           artifacts_root="/scratch/")              # keep housekeeping files out of the project folders
model = scripted(call("dump_logs", {"day": "2026-11-01"}), AIMessage("No failed requests found."))
agent = create_deep_agent(model=model, tools=[dump_logs], backend=backend, store=InMemoryStore())
out = agent.invoke({"messages": [{"role": "user", "content": "How many requests failed on 2026-11-01?"}]})
print([p.rsplit("/", 1)[0] for p in out["files"]])
What you should see
offloaded: True | at: /large_tool_results | chars: 215999
['/scratch/large_tool_results']

The 216,000-character log was saved, not sent. With artifacts_root="/scratch/" on a CompositeBackend, both offload folders move under /scratch/, so a /memories/ route or a project folder never fills up with logs.

Idea 3 · Subagents with their own context

A subagent is a second agent that the main agent can start with the task tool. It gets its own instructions, its own tools and a fresh, empty context. It does the noisy work, such as reading long logs, and returns only a summary, so the main agent's context stays small. Define one that reads logs, and have the main agent hand it a job:

log_reader = {
    "name": "log-reader",
    "description": "Reads service logs and summarizes the errors in them",
    "system_prompt": "Summarize errors. Report times and services. Do not guess causes.",
    "tools": [],                                                     # fewer tools than the main agent
    "model": scripted(AIMessage("2 timeouts from the payment service at 02:10 and 02:12.")),
}
main = scripted(call("task", {"subagent_type": "log-reader",
                              "description": "Summarize the errors in last night's refund-export logs"}),
                AIMessage("The export failed because the payment service timed out twice."))
agent = create_deep_agent(model=main, tools=[], subagents=[log_reader])
out = agent.invoke({"messages": [{"role": "user", "content": "Why did the refund export fail?"}]})
for m in out["messages"]:
    print(f"{m.type:5} | {m.content or m.tool_calls[0]['name'] + ' -> ' + m.tool_calls[0]['args']['subagent_type']}")
What you should see
human | Why did the refund export fail?
ai    | task -> log-reader
tool  | 2 timeouts from the payment service at 02:10 and 02:12.
ai    | The export failed because the payment service timed out twice.

The main agent called task, the log-reader subagent ran with its own system prompt, tools and model, and only its final answer came back as the tool result. The log lines it read never entered the main conversation. That isolation is the point: each subagent has a clean, focused context, and the main agent stays short. Give subagents fewer tools and narrower prompts than the main agent, and a cheaper model where the task allows (Lesson 14.66 compares this with other multi-agent shapes).

Idea 4 · Planning with a to-do list

Long tasks drift. A to-do list that the agent writes and updates keeps the plan in front of the model at every step. With TodoListMiddleware the model gets a write_todos tool, and the list is stored in the state where your application can show it:

model = scripted(call("write_todos", {"todos": [{"content": "Read the export logs", "status": "in_progress"},
                                                {"content": "Check the payment service status", "status": "pending"},
                                                {"content": "Write the incident note", "status": "pending"}]}),
                 AIMessage("Plan written; starting with the logs."))
agent = create_deep_agent(model=model, tools=[], middleware=[TodoListMiddleware()])   # planning, added explicitly
out = agent.invoke({"messages": [{"role": "user", "content": "Investigate the failed export."}]})
for todo in out["todos"]:
    print(f"[{todo['status']:11}] {todo['content']}")
What you should see
[in_progress] Read the export logs
[pending    ] Check the payment service status
[pending    ] Write the incident note

In deepagents 0.7 the to-do tool is not in the default tool set; add TodoListMiddleware when the work benefits from an explicit plan. The list is part of the state, so it is checkpointed, visible to a UI and readable after a restart, which is what lets a long task continue where it stopped.

Idea 5 · Limit what the agent may change

An agent that can write files needs limits on where. Permissions are a list of rules, checked in order: this one allows writing under /reports/ and denies writing anywhere else. The scripted model tries both a forbidden write and an allowed one:

model = scripted(call("write_file", {"file_path": "/config/payments.yaml", "content": "retries: 99"}),
                 call("write_file", {"file_path": "/reports/note.md", "content": "Incident note"}, "c2"),
                 AIMessage("Done."))
agent = create_deep_agent(model=model, tools=[], permissions=[
    FilesystemPermission(operations=["write"], paths=["/reports/**"], mode="allow"),
    FilesystemPermission(operations=["write"], paths=["/**"], mode="deny"),     # everything else is read-only
])
out = agent.invoke({"messages": [{"role": "user", "content": "Fix the config and write a note."}]})
for m in out["messages"]:
    if m.type == "tool":
        print("tool:", m.content)
print("files written:", list(out["files"]))
What you should see
tool: Error: permission denied for write on /config/payments.yaml
tool: Updated file /reports/note.md
files written: ['/reports/note.md']

FilesystemPermission rules allow, deny or interrupt (ask a person, Lesson 14.63) for reads and writes by path pattern. The agent may write reports and nothing else; its attempt to change the payment config came back as an error it can read. Combine this with interrupt_on for risky tools, and run real file and shell backends inside a sandbox (Lesson 15.23).

Idea 6 · Skills and rules files

Two file conventions from coding agents are built in. A skill is a folder with a SKILL.md: YAML front matter (name, description) and then the procedure. The harness lists only names and descriptions in the system prompt and the model reads the full file when a task matches (progressive disclosure), so long procedures cost nothing until needed. A memory file (AGENTS.md style) is loaded whole into the system prompt on every run, inside an <agent_memory> block, with instructions to update it with edit_file when the user corrects the agent.

from langchain_core.callbacks import BaseCallbackHandler

class PromptPeek(BaseCallbackHandler):
    """Records the system prompt the model actually receives."""
    system = ""
    def on_chat_model_start(self, serialized, messages, **kwargs):
        self.system = str(messages[0][0].text)

SKILL = """---
name: refund-export
description: How to write up a nightly refund export for ShopKart ops.
---
1. List payment timeouts with times.
2. Name the affected orders.
3. End with the next check time.
"""
RULES = "# ShopKart rules\n- Amounts are in INR.\n- Never name customers in reports.\n"

peek = PromptPeek()
model = scripted(call("read_file", {"file_path": "/skills/refund-export/SKILL.md", "limit": 1000}),
                 AIMessage("Written per the refund-export skill."))
agent = create_deep_agent(model=model, tools=[], skills=["/skills/"], memory=["/AGENTS.md"])
out = agent.invoke({"messages": [{"role": "user", "content": "Write up last night's refund export."}],
                    "files": {"/skills/refund-export/SKILL.md": {"content": SKILL}, "/AGENTS.md": {"content": RULES}}},
                   config={"callbacks": [peek]})
print("skill listed:", "- **refund-export**: How to write up a nightly refund export" in peek.system)
print("rules loaded:", "Never name customers" in peek.system)
print([m.type for m in out["messages"]], "| read:", out["messages"][2].content.splitlines()[0])
What you should see
skill listed: True
rules loaded: True
['human', 'ai', 'tool', 'ai'] | read: @@ lines 1-7 of 7 @@

With the default state backend the files come in through invoke(files=...); with FilesystemBackend(root_dir=...) the same paths are read from disk, which is how a team checks its skills and rules into git. Skills are cached per thread; after editing one, invoke with "skills_metadata": None to reload.

Debugging exercise: the agent cannot write its own reports

A teammate set up permissions so the agent may only write reports, but now it cannot write them at all:

model = scripted(call("write_file", {"file_path": "/reports/note.md", "content": "Incident note"}), AIMessage("Done."))
agent = create_deep_agent(model=model, tools=[], permissions=[
    FilesystemPermission(operations=["write"], paths=["/**"], mode="deny"),
    FilesystemPermission(operations=["write"], paths=["/reports/**"], mode="allow"),
])
out = agent.invoke({"messages": [{"role": "user", "content": "Write a note."}]})
print([m.content for m in out["messages"] if m.type == "tool"], "| files:", list(out.get("files", {})))

What it printed:

['Error: permission denied for write on /reports/note.md'] | files: []

Find the bug. (Solution D1.)

Make it your own

Add a second subagent, status-checker, that checks the payment service's status page with one tool, and make the main agent call both subagents before writing the incident note. (Solution M1.)

Solutions

SolutionP1 · Only the answer comes back

Only the subagent's final answer, as one tool result; its prompt, tool calls and intermediate messages stay in its own run. Every later model call of the main agent therefore resends one short message instead of the whole investigation, which keeps both cost and context size down.

SolutionB1 · Subagents make model calls of their own

The shared scripted model is one iterator, so the subagent consumes replies meant for the main agent, and the run fails or answers nonsense. With real models, it shows that subagents are separate model calls with their own context: give each its own model configuration, and count their calls in your cost estimates.

SolutionD1 · The first matching rule wins

Rules are checked in order and the first one that matches decides. /** matched /reports/note.md first, so the write was denied before the allow rule was reached. Put specific rules before general ones:

model = scripted(call("write_file", {"file_path": "/reports/note.md", "content": "Incident note"}), AIMessage("Done."))
agent = create_deep_agent(model=model, tools=[], permissions=[
    FilesystemPermission(operations=["write"], paths=["/reports/**"], mode="allow"),   # specific rules first
    FilesystemPermission(operations=["write"], paths=["/**"], mode="deny"),
])
print(list(agent.invoke({"messages": [{"role": "user", "content": "Write a note."}]})["files"]))

['/reports/note.md']
SolutionM1 · Two subagents

Define status_checker = {"name": "status-checker", "description": "Checks the payment service status page", "system_prompt": "Report the current status and recent incidents.", "tools": [check_status_page]}, pass subagents=[log_reader, status_checker], and script the main agent to call task once for each before write_file. With a real model, the subagents' descriptions are what the main agent uses to choose, so make them distinct.

Check your understanding

Explain the mechanismWhat is a deep agent, and what does the deepagents library add to create_agent?

Worked answer. A deep agent is an agent with a harness for long tasks: a virtual file system for notes and large results, subagents with isolated contexts launched through a task tool, optional planning with a to-do list, pluggable storage backends, permissions on files, and human approval on tools. deepagents packages these as middleware on top of create_agent, so the result is a LangGraph graph with checkpoints, streaming and interrupts.

A plausible wrong answer. "A deep agent uses a bigger model." The difference is the harness, not the model.

Follow-ups. When would you write files to the store instead of the state?

Debug a failureA deep agent's context keeps growing and runs get slow and expensive. What do you check?

Worked answer. Whether large tool results go to files or stay in messages, whether subagents are used for noisy investigations, whether summarization middleware is on for long threads, and whether the agent rereads whole files instead of the lines it needs. Look at token counts per call in traces to find what grows.

A plausible wrong answer. "Use a model with a bigger window." The window is not the problem; what goes into it is.

Follow-ups. How would you cap a deep agent's cost per task?

Defend a designDeep agent or custom graph for ShopKart's refund workflow?

Worked answer. A custom graph: refunds are a known process with business rules, approvals and money, which need explicit control flow and audit. A deep agent fits open-ended work around it, such as investigating why refunds failed overnight and writing the incident note, where the steps are not known in advance.

A plausible wrong answer. "Deep agents for everything, they are the most capable." Capability is not control.

Follow-ups. How would the two be connected?
