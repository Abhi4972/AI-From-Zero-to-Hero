Why this came about

After LangChain, the model providers themselves began shipping agent frameworks. OpenAI's experimental Swarm (2024) became the Agents SDK in March 2025: a small set of primitives (agents, tools, handoffs, guardrails, sessions) with tracing built in. It shows the same loop through a provider's eyes.

In plain words first
The same loop, from another vendor

Every agent framework packages the same ideas you built in the Agents from first principles section: a model with instructions, tools, a loop, memory of the conversation, approvals and guardrails. The OpenAI Agents SDK names them Agent, function tools, Runner, sessions, approvals and guardrails. Reading it as a mapping ("this is the agent loop, this is the checkpointer") makes any framework quick to learn.

What it is

The OpenAI Agents SDK (Python and TypeScript, MIT licensed) is OpenAI's production successor to its experimental Swarm project. It keeps a small set of primitives: agents (a model with instructions and tools), handoffs (one agent passing the conversation to another), guardrails (checks that run alongside the agent), sessions (conversation memory) and tracing (on by default). Since April 2026 it also includes a sandbox harness: agents that read and write files, run shell commands and apply patches inside isolated containers from providers such as E2B, Modal, Daytona, Cloudflare and Vercel, with state stored outside the container so a lost sandboxlater · 15.25 does not lose the run.

It works with any model: OpenAI models natively through the Responses API, and others through any Chat Completions-compatible endpoint or the LiteLLM extension.

uv add openai-agents        # tested with 0.24.0

Step 1 · An agent with tools

The same support agent you have built several times, now in the OpenAI Agents SDK. Three things to notice as you read. @function_tool turns a function into a tool, as @tool did in LangChain. Agent(...) only describes the agent: its name, instructions, model and tools. Runner.run(agent, question) is what runs the loop. The model here is the lab rig, so the code needs no key.

import asyncio
from mockllm import start                                   # lab rig (Lesson 6.1)
from openai import AsyncOpenAI
from agents import Agent, Runner, function_tool, OpenAIChatCompletionsModel, set_tracing_disabled

set_tracing_disabled(True)          # traces go to OpenAI's dashboard by default; off for this offline lab
model = OpenAIChatCompletionsModel(model="mock-model", openai_client=AsyncOpenAI(base_url=start(), api_key="mock"))
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@function_tool                                              # the docstring and type hints become the tool schema
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

@function_tool(needs_approval=True)                         # the run pauses before this tool executes
def cancel_order(order_id: str) -> str:
    """Cancel an order that has not shipped yet."""
    return f"{order_id} cancelled"

agent = Agent(name="ShopKart support", instructions="Help customers with orders. Be brief.",
              model=model, tools=[get_order_status, cancel_order])

result = asyncio.run(Runner.run(agent, "Where are A-1001 and A-1002?"))
print(result.final_output)
What you should see
Here is what I found: A-1001 is shipped; A-1002 is processing

With an OpenAI key, drop the model= argument (the default is a current OpenAI model over the Responses API) or pass model="gpt-5.5". For other providers, point AsyncOpenAI at their OpenAI-compatible endpoint, or install openai-agents[litellm] and use LitellmModel.

Runner.run is the async entry point; Runner.run_sync wraps it, and Runner.run_streamed streams events for a UI. The SDK runs the loop for you: call the model, run tools (in parallel when the model asks for several), repeat until a final answer or max_turns.

Step 2 · Sessions and human approval

Two additions. A session stores the conversation, so that the next message on the same session continues it. And cancel_order was declared with needs_approval=True, so a run that reaches it stops and reports what is waiting. Your code approves or rejects each waiting call and runs the agent again from the saved state:

from agents import SQLiteSession

async def approval_demo():
    session = SQLiteSession("customer-42")                  # conversation memory, stored in SQLite
    r = await Runner.run(agent, "Please cancel A-1002", session=session)
    print("paused for:", [i.name for i in r.interruptions])  # tools waiting for a decision
    state = r.to_state()                                     # serializable: store it and resume hours later
    for item in r.interruptions:
        state.approve(item)                                  # or state.reject(item)
    r = await Runner.run(agent, state, session=session)
    print("after approval:", r.final_output)

asyncio.run(approval_demo())
What you should see
paused for: ['cancel_order']
after approval: Here is what I found: A-1002 cancelled

The run did not block a thread while waiting. to_state() gives you an object you can serialize to a database, which is how approvals survive a restart or wait for a reviewer in another time zone.

Session backends include SQLite, Redis, SQLAlchemy (any SQL database), encrypted sessions, and OpenAIConversationsSession, which stores history in OpenAI's Conversations API.

Step 3 · Guardrails

Guardrails run in parallel with the agent and stop the run when they trip, so they add little latency. Input guardrails check the first agent's input; output guardrails check the final answer; tool guardrails wrap individual tools.

from agents import input_guardrail, GuardrailFunctionOutput, InputGuardrailTripwireTriggered, RunContextWrapper

@input_guardrail
async def no_card_numbers(ctx: RunContextWrapper, agent: Agent, user_input) -> GuardrailFunctionOutput:
    digits = [c for c in str(user_input) if c.isdigit()]
    return GuardrailFunctionOutput(output_info={"digits": len(digits)}, tripwire_triggered=len(digits) >= 12)

guarded = agent.clone(input_guardrails=[no_card_numbers])

try:
    asyncio.run(Runner.run(guarded, "My card is 4111 1111 1111 1111, refund A-1001"))
except InputGuardrailTripwireTriggered:
    print("blocked: never paste card numbers into chat")
What you should see
blocked: never paste card numbers into chat

A real input guardrail usually calls a small, cheap model (for example "is this request about ShopKart orders?") through its own Runner.run, so the expensive agent is stopped as soon as the check fails.

An output guardrail checks the final answer before the customer sees it. Here a tool result leaks a staff email address, and the guardrail stops it:

import re
from agents import output_guardrail, OutputGuardrailTripwireTriggered

@function_tool(name_override="get_order_status")
def leaky_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is shipped; questions to ravi@shopkart.example"     # internal detail in the data

EMAIL = re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+")

@output_guardrail
async def no_email_addresses(ctx: RunContextWrapper, agent: Agent, output) -> GuardrailFunctionOutput:
    found = EMAIL.findall(str(output))
    return GuardrailFunctionOutput(output_info={"emails": found}, tripwire_triggered=bool(found))

leaky_agent = Agent(name="support", instructions="Help with orders.", model=model,
                    tools=[leaky_status], output_guardrails=[no_email_addresses])
try:
    asyncio.run(Runner.run(leaky_agent, "Where is A-1001?"))
except OutputGuardrailTripwireTriggered as e:
    print("answer withheld; found:", e.guardrail_result.output.output_info["emails"])
What you should see
answer withheld; found: ['ravi@shopkart.example']

In production, catch the exception and send a safe fallback ("Let me connect you with a colleague") rather than an error. Tool guardrails (@tool_input_guardrail, @tool_output_guardrail) apply the same idea to one tool's arguments or result, which is the place to stop a leak like this one before the model even sees it.

In production
Guardrail details that matter in production

Input guardrails run only for the first agent in a run, and output guardrails only on the agent that produces the final output, so a check you attach to a specialist that receives a handoff will not run on the user's input. By default guardrails run in parallel with the agent, which saves latency but means the agent may already have spent tokens, or called a tool, before a tripwire fires. For checks that must block side effects, set run_in_parallel=False on that guardrail, or put the check inside the tool itself.

  • ✗ "Guardrails stop every bad action."

Exercises

Predict before you run

The agent has get_order_status and cancel_order(needs_approval=True). For "Where are A-1001 and A-1002? And cancel A-1002", how many tool calls will run before the first pause, and what does result.interruptions contain? (Solution P1.)

Break it on purpose

Resume the paused run with a new SQLiteSession("customer-43") instead of the session the run started with. What does the agent remember, and what happens to the pending approval? (Solution B1.)

Debugging exercise
Debugging exercise: the guardrail that never fires

A teammate added no_card_numbers as an input guardrail on the refunds agent, which receives conversations by handoff from the triage agent. A customer pasted a card number to the triage agent, the conversation was handed off, and the guardrail did not trip. Explain why, and where the check must go. (Solution D1.)

Make it your own

Add an output guardrail that blocks any reply containing an order ID that was not in the customer's message or in a tool result of this run. (Solution M1.)

Solutions

SolutionP1 · Tools run until the approval

The model asks for both status lookups and the cancellation. The lookups run; the cancellation does not, because needs_approval=True pauses the run first. result.interruptions holds one approval item for cancel_order with its arguments, and the run state, saved with result.to_state(), is what you resume after state.approve(...) or state.reject(...).

SolutionB1 · The session is the memory

A new session has none of the conversation, so the agent has no history for that run. The pending approval lives in the run state, not the session, so resuming the saved state still continues the cancellation, but any later turn on the new session starts without context. Keep one session per conversation, keyed by an ID you store, exactly like a LangGraph thread (Lesson 14.103).

SolutionD1 · Input guardrails run only for the first agent

In the Agents SDK, input guardrails run only when their agent is the first agent of the run, and output guardrails only on the agent that produces the final output. The refunds agent was not first, so its input guardrail never ran. Put input checks on the entry agent (or check before calling Runner.run), and use tool guardrails for checks that must run wherever a tool is called.

SolutionM1 · An output guardrail with run data

Collect the order IDs from the input and from the run's tool results (result.new_items, or a run hook that records tool outputs into the run context), then in the guardrail compare them with the IDs in the output and trip on any unknown ID. This catches invented IDs, a common hallucination in support replies, at the cost of one regex pass per reply.

Check your understanding

Explain the mechanismWhat are the core primitives of the OpenAI Agents SDK?

Worked answer. Agents (instructions, a model, tools, handoffs, guardrails and an optional output type), a Runner that executes the loop (run, run_sync, run_streamed), function tools built from Python functions, sessions for conversation memory, guardrails on input, output and tools that can stop a run with a tripwire, handoffs that transfer the conversation to another agent, and built-in tracing. Approvals pause a run before a tool marked needs_approval, with a serializable run state to resume later.

A plausible wrong answer. "It only works with OpenAI models." Through its model interfaces and LiteLLM it can call other providers, though some features are OpenAI-specific.

Follow-ups. How does a handoff differ from calling an agent as a tool?

Debug a failureA run raises InputGuardrailTripwireTriggered for normal questions after a prompt change. How do you investigate?

Worked answer. Look at the guardrail's own output in the trace: guardrails that call a model return a reason along with the tripwire. Check whether the guardrail agent's prompt or model changed, and run it alone on a set of normal and malicious inputs to measure false positives. Then tune it, and in production catch the exception and send a safe reply instead of an error.

A plausible wrong answer. "Remove the guardrail." That hides the false positives and the attacks together.

Follow-ups. How would you run guardrails in parallel with the main agent to save latency?

Defend a designOpenAI Agents SDK or LangGraph for a support agent?

Worked answer. The Agents SDK when the team is on OpenAI models and wants a small, readable API with sessions, guardrails, handoffs and tracing built in. LangGraph when the workflow needs custom control flow, durable pauses that span days with a checkpointed graph state, time travel, or provider-neutral components. Both can do approvals and multi-agent hand-offs; the difference is how much of the control flow you want to own. I would build the hardest path, approval and resume, in both before choosing (Lesson 14.127).

A plausible wrong answer. "The vendor SDK is always better for that vendor's models." It is convenient, not automatically better; requirements decide.

Follow-ups. What would make you switch later, and how expensive would it be?
