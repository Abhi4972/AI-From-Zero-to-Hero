Why this came about

One tool call answers simple questions, but real tasks need several dependent steps. The 2022 ReActlater · 14.9 paper showed that letting a model alternate between reasoning and acting, observing each result, solved such tasks well, and the agent loop became the standard design. Its risks, loops that never end and costs that run away, came with it.

The problem: one request, several dependent steps

A customer writes: "My mixer arrived broken last week. Can I get a refund?" There is no order ID. The assistant has to find the order first, then decide, then act, and each step depends on the result of the one before. You cannot know in advance how many requests that takes. So the code has to keep looping until the model stops asking for tools.

ShopKart now has three tools: find_orders lists the logged-in customer's orders, get_order_status is Lesson 14.2's checked lookup, and issue_refund moves real money.

import json, re
from fake_claude import FakeAnthropic, BadRequestError      # the labeled stand-in from Lesson 3.2 (appendix)

client, MODEL = FakeAnthropic(), "claude-sonnet-5-5"
SESSION = {"customer_id": "C-7"}                              # who is logged in, from your app
ORDERS = {
    "SK-1042": {"customer_id": "C-7", "item": "running shoes", "price": 2499, "status": "out for delivery", "eta": "today by 8 pm"},
    "SK-1077": {"customer_id": "C-7", "item": "mixer grinder", "price": 3899, "status": "delivered", "delivered_on": "2 November"},
    "SK-2001": {"customer_id": "C-9", "item": "electric kettle", "price": 1299, "status": "processing", "eta": "6 November"},
}
REFUNDS = {}                                                  # money that has actually left ShopKart

def find_orders() -> str:
    mine = [{"order_id": k, "item": o["item"], "status": o["status"]} for k, o in ORDERS.items() if o["customer_id"] == SESSION["customer_id"]]
    return json.dumps(mine)

def get_order_status(order_id: str) -> str:                   # Lesson 3.2's checked version
    if not re.fullmatch(r"SK-\d{4}", order_id):
        raise ValueError(f"order_id must look like SK-1234, got {order_id!r}")
    order = ORDERS.get(order_id)
    if order is None or order["customer_id"] != SESSION["customer_id"]:
        raise LookupError(f"no order {order_id} on this customer's account")
    return json.dumps({"order_id": order_id, **{k: v for k, v in order.items() if k != "customer_id"}})

def issue_refund(order_id: str, reason: str) -> str:
    """Moves real money. Irreversible."""
    json.loads(get_order_status(order_id))                    # same format and ownership checks
    REFUNDS[order_id] = {"refund_id": f"R-{len(REFUNDS) + 901}", "amount": ORDERS[order_id]["price"], "reason": reason}
    return json.dumps({"order_id": order_id, "status": "refund issued", **REFUNDS[order_id]})

def tool(name, description, properties, required):
    return {"name": name, "description": description,
            "input_schema": {"type": "object", "properties": properties, "required": required}}

TOOLS = {   # name -> (what the model sees, what your code runs)
    "find_orders": (tool("find_orders", "List the logged-in customer's recent orders with their items. Use it when the customer "
                         "describes an order without giving its ID.", {}, []), find_orders),
    "get_order_status": (tool("get_order_status", "Look up the delivery status of one order. Order IDs look like SK-1042.",
                              {"order_id": {"type": "string"}}, ["order_id"]), get_order_status),
    "issue_refund": (tool("issue_refund", "Refund an order in full to the original payment method.",
                          {"order_id": {"type": "string"}, "reason": {"type": "string", "enum": ["damaged", "wrong item", "changed mind"]}},
                          ["order_id", "reason"]), issue_refund),
}
SYSTEM = "You are ShopKart's support assistant. Use the tools to look things up; never guess an order's status."
print(sorted(TOOLS))

It worked, and that is the problem. The model found the order, asked for a refund, and the code paid INR 3,899 because the model asked. Nobody checked whether a person should approve it. And if the model had needed a fifth request, answer() would have returned a bare "Stopped" that nobody would notice. An agent loop needs three things this code lacks: an exit for every way a response can end, limits that hand the conversation to a person, and a gate in front of risky tools.

In plain words first
Repeat until done, with a stop button

One tool call answers simple questions. Real requests need several dependent steps: look up the order, then check the refund policy, then issue the refund. The agent loop repeats: call the model, run any tools it asked for, send the results back, until it answers without asking for tools. Because the model decides when to stop, the loop needs your limits too: a maximum number of steps, a check for repeated calls, and a record of each step.

Idea 1 · Every way a turn can end

The loop's exit decision is stop_reason. You have used two values. The Messages API documents seven, and a loop needs an answer for each one:

stop_reason What happened What the loop does
end_turn The model finished Return the answer
tool_use The model wants tools Run them, send the results, go round again
max_tokens The reply hit your max_tokens Stop and hand over, or retry with a larger limit; a cut-off tool_use block is unusable
stop_sequence One of your stop sequences appeared Treat as finished, or as your own signal
pause_turn A server-side tool loop (such as web search) hit its iteration limit Send the assistant content back unchanged to let it continue
refusal The model declined Stop; Anthropic's docs suggest retrying on a different Claude model
model_context_window_exceeded The reply filled the context window Treat it as truncated

The Agent below handles the two everyday values, stops cleanly on max_tokens, and stops with a message on anything it does not expect. A loop that falls through on an unknown value either crashes or, worse, keeps going.

Idea 2 · Limits, a gate, and a trace

Python refresher
Python refresher: `dataclasses`

@dataclass writes a class's __init__ for you from annotated fields: Agent(system="...", tools=TOOLS) sets self.system and self.tools, and every other field takes its default. A mutable default such as a set must be made fresh for each object with field(default_factory=set). Otherwise all agents would share one set. __post_init__ runs right after __init__, which makes it the place to check the configuration.

from dataclasses import dataclass, field
from typing import Callable

@dataclass
class Agent:
    system: str
    tools: dict                                    # name -> (definition, function)
    risky: set = field(default_factory=set)        # tools that need a person's yes before they run
    approve: Callable = lambda name, args: False   # who says yes; the default is nobody
    max_steps: int = 6                             # requests to the model per run
    token_budget: int = 6000                       # input + output tokens per run
    repeat_limit: int = 2                          # identical calls allowed per run
    trace: list = field(default_factory=list)

    def __post_init__(self):
        unknown = self.risky - set(self.tools)
        if unknown:                                # fail at start-up, not in production
            raise ValueError(f"risky tools that do not exist: {sorted(unknown)}")

    def run(self, question):
        self.trace = []
        messages, used, seen = [{"role": "user", "content": question}], 0, {}
        for step in range(1, self.max_steps + 1):
            response = client.messages.create(model=MODEL, max_tokens=500, system=self.system,
                                              tools=[d for d, _ in self.tools.values()], messages=messages)
            used += response.usage.input_tokens + response.usage.output_tokens
            calls = [b for b in response.content if b.type == "tool_use"]
            self.trace.append((step, response.stop_reason, [f"{c.name}({c.input})" for c in calls], used))
            if response.stop_reason == "end_turn":
                return response.content[-1].text
            if response.stop_reason == "max_tokens":
                return "Stopped: the reply was cut off by max_tokens. A person will follow up."
            if response.stop_reason != "tool_use":
                return f"Stopped: unexpected stop_reason {response.stop_reason!r}. A person will follow up."
            for c in calls:                        # the same call again and again means the run is stuck
                key = (c.name, json.dumps(c.input, sort_keys=True))
                seen[key] = seen.get(key, 0) + 1
                if seen[key] > self.repeat_limit:
                    return f"Stopped: {c.name} was requested {seen[key]} times with the same input. A person will follow up."
            messages.append({"role": "assistant", "content": response.content})
            messages.append({"role": "user", "content": self.call_tools(calls)})
            if used > self.token_budget:
                return f"Stopped: this run used {used} tokens, over its budget. A person will follow up."
        return f"Stopped: no answer after {self.max_steps} requests. A person will follow up."

    def call_tools(self, calls):                   # one result per call, in the order they were requested
        return [self.call_tool(c) for c in calls]

    def execute(self, name, args):                 # the one line that touches the world
        return self.tools[name][1](**args)

    def call_tool(self, c):
        def result(content, error=False):
            return {"type": "tool_result", "tool_use_id": c.id, "content": content, **({"is_error": True} if error else {})}
        if c.name not in self.tools:
            return result(f"unknown tool {c.name}; available: {sorted(self.tools)}", True)
        if c.name in self.risky and not self.approve(c.name, c.input):
            return result(f"{c.name} for {c.input} needs a person's approval and has not been approved", True)
        try:
            return result(self.execute(c.name, c.input))
        except Exception as e:
            return result(f"{type(e).__name__}: {e}", True)

    def show_trace(self):
        for step, stop, calls, used in self.trace:
            print(f"  step {step}: {stop:<9} {', '.join(calls) or '-':<55} tokens so far {used}")
What you should see

Nothing runs yet. This block only defines the class.

Read run as a list of exits. Each one ends the run with a message a person can act on, never silently:

Exit Trigger Why it exists
Answer end_turn The job is done
Cut-off reply max_tokens Half an answer, or half a tool call, cannot be used
Unknown stop Any other stop_reason Fail loudly instead of looping on something you did not plan for
Repeat check The same tool with the same input a third time A stuck model asks the same question forever
Token budget Input plus output tokens over token_budget A cap on cost per run that does not depend on counting steps
Step limit max_steps requests The last line of defense

And call_tool is the gate. The model can ask for issue_refund, but the function only runs if approve says yes. The default approve says no to everything, so a misconfigured agent fails safe. The model gets a clear error result in place of the action and tells the customer. Notice also the start-up check in __post_init__: a risky tool name that does not exist is an error when the agent is created, not a silent hole in production. The debugging exercise shows why.

Two small methods are there as hooks. call_tools runs one turn's calls, and execute is the single line that touches the world. Lesson 14.5 overrides them to run calls in parallel, put a deadline on each and retry failures, without changing the loop.

To run the same agent on OpenAI's Responses API, write an adapter: an object with the same messages.create(...) method that translates the request on the way out and the reply on the way back. This is the pattern every multi-provider framework and gateway uses.

from types import SimpleNamespace as NS
from openai import OpenAI

class ResponsesAdapter:
    """Lets the Agent talk to OpenAI's Responses API through the same messages.create(...) call.
    It translates tools, history and replies between the two shapes."""
    def __init__(self, oai):
        self.oai, self.raw = oai, {}               # raw output items by call_id, sent back unchanged
        self.messages = self

    def create(self, model, max_tokens, system, tools, messages):
        items = []
        for m in messages:
            blocks = [{"type": "text", "text": m["content"]}] if isinstance(m["content"], str) else m["content"]
            for b in blocks:
                kind = b["type"] if isinstance(b, dict) else b.type
                if kind == "text" and m["role"] == "user":
                    items.append({"role": "user", "content": b["text"] if isinstance(b, dict) else b.text})
                elif kind == "tool_use":
                    items += self.raw.pop(b.id, [])  # the model's own items, reasoning included
                elif kind == "tool_result":
                    items.append({"type": "function_call_output", "call_id": b["tool_use_id"],
                                  "output": ("Error: " if b.get("is_error") else "") + b["content"]})
        fns = [{"type": "function", "name": t["name"], "description": t["description"], "strict": True,
                "parameters": {**t["input_schema"], "additionalProperties": False}} for t in tools]
        r = self.oai.responses.create(model=model, instructions=system, tools=fns, input=items, max_output_tokens=max_tokens)
        content, calls = [], [o for o in r.output if o.type == "function_call"]
        for c in calls:
            self.raw[c.call_id] = [o for o in r.output if o.type != "message"] if c is calls[0] else []
            content.append(NS(type="tool_use", id=c.call_id, name=c.name, input=json.loads(c.arguments)))
        if r.output_text:
            content.insert(0, NS(type="text", text=r.output_text))
        stop = "tool_use" if calls else ("max_tokens" if r.status == "incomplete" else "end_turn")
        return NS(content=content, stop_reason=stop, usage=NS(input_tokens=r.usage.input_tokens, output_tokens=r.usage.output_tokens))

(Same local test server.)

The adapter is where provider differences live. Arguments arrive as a JSON string and must be parsed. Errors have no is_error field, so the adapter writes "Error:" into the output text. The model's own output items, including any reasoning items, are cached and sent back unchanged: OpenAI's docs say reasoning items must be passed back with tool outputs, and rebuilding them from your own history would drop them.

What changes when the model is real:

  • Behavior: a real model may skip find_orders and ask the customer for the order ID, call get_order_status before refunding, or ask whether the item is really broken. Your exits and gate do not depend on which path it takes; that is the point of putting them in the loop.
  • Setup: pick limits from data. Look at the step counts of successful runs in your traces and set max_steps a little above the 99th percentile, not at a round number.
  • Evaluation: run each question several times. A loop that succeeds four times in five on a multi-step task fails one customer in five (pass^k, Lesson 14.118).
  • Cost: tokens per run grow with the square of the steps, so the cheapest optimization is fewer steps: better tool descriptions, tools that return what the next step needs, and prompt caching for the repeated prefix (Lesson 11.4).
Check your mental model
  • ✗ "The model stops when it should."
    ✓ It usually does; a step limit and loop detection make sure it always does.
  • ✗ "An agent loop needs a framework."
    ✓ It is a while loop around one model call and a tool runner; frameworks add persistence, streaming and tooling.
  • ✗ "The final answer is all that matters."
    ✓ Keep a trace of every step; that is how you debug and evaluate the path.

Make it your own: an approval policy

Solutions

SolutionP1 · The refund through the guarded agent

Three requests: find_orders, then issue_refund, then the final answer. REFUNDS stays empty because call_tool returned an error result instead of running the function. The customer reads that the refund needs a colleague's approval. The model still asked for the refund; the decision about whether it happens moved into your code.

SolutionP2 · The cost of a stuck loop

About 57,000 tokens for 40 requests, against under 1,000 for the guarded agent's 3. If you guessed about 13 times as many tokens (40 ÷ 3), you assumed every request costs the same. Each request re-sends everything before it, so total tokens grow roughly with the square of the number of steps.

SolutionP3 · Without the repeat check

With only the repeat check removed, the step limit stops the run at 6 requests (the default max_steps): "no answer after 6 requests". With max_steps=40 as well, the token budget stops it at 11 requests, when the run passes 6,000 tokens. Each limit backs up the one before, which is the point: removing one control should never make a run unbounded. Note which limit fired, because each one points to a different fix.

SolutionD1 · Why the refund went through

risky={"refund", "issue_refunds"} names two tools that do not exist; the real one is issue_refund. call_tool checks c.name in self.risky, which is false for issue_refund, so the refund ran unguarded. Nothing failed loudly because the teammate deleted the start-up check that would have raised "risky tools that do not exist".

Fix in the configuration: risky={"issue_refund"}. Fix in the class: restore __post_init__, and better still, mark risk on the tool definition itself (a risky=True flag next to the function) so a rename cannot separate them. A safety rule that lives in a separate list of names will drift; one that travels with the tool will not.

SolutionM1 · An approval policy
# Solution M1: small refunds are approved by policy, larger ones need a person, and every decision is logged
APPROVALS = []

def refund_policy(name, args, limit_inr=2000):
    amount = ORDERS[args["order_id"]]["price"]
    decision = "auto-approved" if amount <= limit_inr else "needs a person"
    APPROVALS.append((name, args["order_id"], amount, decision))
    return decision == "auto-approved"

ORDERS["SK-1050"] = {"customer_id": "C-7", "item": "steel water bottle", "price": 649, "status": "delivered", "delivered_on": "1 November"}
policy_agent = Agent(system=SYSTEM, tools=TOOLS, risky={"issue_refund"}, approve=refund_policy)
for q in ["My water bottle arrived damaged, please refund it", "My mixer arrived broken last week. Can I get a refund?"]:
    REFUNDS.clear()
    print("-", policy_agent.run(q))
print("approval log:", APPROVALS)
del ORDERS["SK-1050"]

- Refund R-901 of INR 649 for order SK-1050: refund issued.
- I can't issue that refund without a colleague's approval (issue_refund for {'order_id': 'SK-1077', 'reason': 'damaged'} needs a person's approval and has not been approved).
approval log: [('issue_refund', 'SK-1050', 649, 'auto-approved'), ('issue_refund', 'SK-1077', 3899, 'needs a person')]

What to notice: the policy reads the amount from your order data, never from the model's arguments, so a model cannot argue a refund under the limit. Every decision is logged, including automatic ones, because "who approved this?" must always have an answer. The large refund still gets a clear error result, so the conversation continues. Making a person's approval actually reach a person, and resuming the run when they answer, is Lesson 14.6.

Check your understanding

Explain the mechanismWhat is the agent loop, and what are its exit conditions?

Worked answer. The loop sends the conversation and tool definitions to the model, and if the model asks for tools, the application runs them, appends the request and the results, and calls the model again. It repeats until the model answers. A production loop has an exit for every stop_reason: end_turn returns the answer; tool_use continues; max_tokens, refusal and anything unexpected stop with a handoff. It also has its own limits: a step limit, a token or cost budget, and a check for repeated identical calls. Every exit returns something a person can act on.

A plausible wrong answer. "Loop while the response has tool calls, with a maximum of N iterations." It covers the happy path and the runaway case, but not a cut-off reply, a refusal or a stuck model making the same call. Those are exactly the failures that reach customers.

Follow-ups. How do you pick N? Why does cost grow faster than the number of steps? What should the customer see when a limit is hit?

Debug a failureAn agent's bill tripled overnight, but traffic was flat. What do you check?

Worked answer. Look at tokens per run and steps per run in the traces, not total requests. A jump in steps per run usually means a stuck pattern: a tool that started failing or returning empty results, which the model retries. Because each step re-sends the whole history, a few extra steps per run can triple the tokens. Group runs by their last tool call and its result to find the tool, fix it or make it return an explicit error, and add a repeat check and a per-run token budget so the next failure is capped. Then alert on steps per run and tokens per run, not only on total spend.

A plausible wrong answer. "Switch to a cheaper model." That lowers the price per token, but the stuck loop still runs. The cause is the number of steps, not the model.

Follow-ups. How would prompt caching change the cost curve? What would you put on a dashboard to catch this within an hour?

Defend a designWhy gate risky tools in code instead of telling the model in the prompt to ask first?

Worked answer. The prompt influences what the model asks for. The gate controls what happens. A model can misread an instruction, be manipulated by text in a document or a message, or simply make a mistake, and a prompt cannot stop the function from running. A gate in the loop decides whether the function runs, using rules that read your data rather than the model's arguments, and it logs the decision. I would still describe the policy in the prompt, so the model sets expectations with the customer, but the enforcement lives in code.

A plausible wrong answer. "Fine-tune the model so it always asks for confirmation." It makes good behavior more likely. It does not make bad behavior impossible, and nothing records who approved what.

Follow-ups. Where would you put the gate in a multi-agentlater · 14.12 system? How do you approve without making people click "yes" on everything (Lesson 14.123)?
