Why this came about

Full fine-tuning updates every weight and saves a complete copy of the model. For a 135-million-parameter model that is tolerable. For a 7-billion-parameter model it needs tens of gigabytes of GPU memory for training and 14 GB or more of disk for every tuned variant, and a company with fifty tasks would store and serve fifty full models. Researchers looked for ways to train only a small number of new parameters: adapters (2019) inserted small layers, prefix tuning and prompt tuning (2021) learned extra input vectors. In 2021 Edward Hu and colleagues at Microsoft published LoRA: leave every original weight frozen and learn a small low-rank correction beside it. It matched full fine-tuning on many tasks with a thousand times fewer trainable parameters, added no delay at inference, and produced a file of a few megabytes. In 2023 QLoRA combined it with 4-bit quantisation so that large models could be tuned on one consumer GPU. Together they are why fine-tuning open models became something a single engineer can do in an afternoon.

In plain words first
A sticky note on a textbook

Full fine-tuning is rewriting a textbook to add your company's conventions: you get a whole new book. LoRA leaves the printed book untouched and adds a thin sticky note to some pages, saying "on this page, adjust the result like so". The notes are tiny compared with the book, you can peel them off to get the original back, and you can keep several sets of notes for different jobs and swap them over the same book. The surprising finding is that for most tasks a few thin notes are enough.

Step 1 · The idea: a small correction beside a frozen matrix

A linear layer multiplies its input by a weight matrix W (Lesson F2.2). Fine-tuning changes W into W + ΔW. Full fine-tuning learns every entry of ΔW. LoRA makes a bet: the change a task needs is simple enough to be written as the product of two thin matrices, ΔW = B × A, where A squeezes the input down to a handful of numbers (the rank, r) and B expands it back.

The same idea as a formula
  • output of the layer: h = W x + (alpha / r) · B A x
  • W has shape (d_out, d_in) and is frozen; A has shape (r, d_in); B has shape (d_out, r)
  • at the start A holds small random numbers and B holds zeros, so B A = 0 and training begins from exactly the pretrained model
  • trainable parameters: r × (d_in + d_out), instead of d_in × d_out
  • alpha / r (alpha over rank) scales the correction

Here is the whole method as one small PyTorch module, tried on a single layer the size of this model's attention matrices:

from ft_data import *
from ft_model import *
import torch.nn as nn

class LoRALinear(nn.Module):
    """Wraps a frozen nn.Linear and adds a trainable low-rank update: W x + (alpha / r) * B A x."""
    def __init__(self, base: nn.Linear, r=8, alpha=16):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad = False                                   # the pretrained weights never change
        self.A = nn.Parameter(torch.randn(r, base.in_features) * 0.01)   # small random numbers
        self.B = nn.Parameter(torch.zeros(base.out_features, r))         # zeros: the update starts at exactly nothing
        self.scale = alpha / r
    def forward(self, x):
        return self.base(x) + self.scale * (x @ self.A.T @ self.B.T)

torch.manual_seed(0)
layer = nn.Linear(576, 576, bias=False)
wrapped = LoRALinear(layer, r=8)
x = torch.randn(3, 576)
print("same output as the original layer at the start:", torch.allclose(layer(x), wrapped(x)))
print("original weights:", layer.weight.numel(), "| LoRA weights:", wrapped.A.numel() + wrapped.B.numel(),
      f"({(wrapped.A.numel() + wrapped.B.numel()) / layer.weight.numel():.1%})")
What you should see
same output as the original layer at the start: True
original weights: 331776 | LoRA weights: 9216 (2.8%)

The wrapped layer gives the same output as the original, because B is all zeros. And the two thin matrices hold under 3% as many numbers as the matrix they correct.

Reading this output
Reading this code
  • self.base is the original layer. Setting requires_grad = False freezes it: no gradients are stored for it and the optimiser never touches it.
  • x @ self.A.T takes the 576 input numbers down to 8; @ self.B.T takes those 8 back up to 576. Everything the layer learns about your task must pass through those 8 numbers. That bottleneck is the "low rank".
  • self.scale = alpha / r. A common convention is alpha = 2 × r (a scale of 2). Because of this factor, changing r does not also force you to re-tune the learning rate very much.

Step 2 · Add LoRA to the real model

Which layers get a LoRA? The original paper adapted the query and value matrices of every attention layer (Lesson F6.1), and that is still a sensible minimum. Freeze the whole model, then wrap those two layers in each of the 30 blocks:

train_rows, val_rows, test_rows = build()
model = load()
for p in model.parameters():
    p.requires_grad = False                                           # freeze everything first
for block in model.model.layers:                                      # 30 transformer blocks
    block.self_attn.q_proj = LoRALinear(block.self_attn.q_proj, r=8, alpha=16)
    block.self_attn.v_proj = LoRALinear(block.self_attn.v_proj, r=8, alpha=16)
trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
total = sum(p.numel() for p in model.parameters())
print(f"trainable {trainable:,} of {total:,} parameters ({trainable / total:.2%})")
What you should see
trainable 460,800 of 134,975,808 parameters (0.34%)

About one weight in three hundred will be trained. The other 134.5 million stay exactly as they were pretrained.

Step 3 · Train it

The training function is unchanged from Lesson 11.5: it trains whatever parameters have requires_grad = True. The one setting that changes is the learning rate. LoRA matrices start at or near zero and there are few of them, so they need much larger steps: 1e-4 to 1e-3 is typical, where full fine-tuning used 5e-5.

start = time.time()
train(model, train_rows, steps=80, lr=1e-3, val_rows=val_rows)
print(f"\n{(time.time() - start) / 60:.1f} minutes")
print("validation:", evaluate(model, val_rows))
print("test      :", evaluate(model, test_rows))

With one weight in three hundred trainable, the model has learned the output format perfectly (every reply is valid JSON) and copies order numbers without error, exactly as the full fine-tune did. It is weaker on urgency, and on unseen phrasings its intent accuracy is about the same as the full fine-tune's. Two attention matrices per block at rank 8 is a very small adapter; Step 5 gives it more room.

Step 4 · A tiny file, and merging

Only the LoRA matrices changed, so only they need saving. And because W + scale × B A is just another matrix of the same shape as W, the correction can be merged into the frozen weight afterwards, giving a plain model with no extra layers:

import os
adapter = {name: p.detach() for name, p in model.named_parameters() if p.requires_grad}
os.makedirs("shopkart-ft", exist_ok=True)
torch.save(adapter, "shopkart-ft/lora_qv.pt")
print(len(adapter), "tensors,", f"{os.path.getsize('shopkart-ft/lora_qv.pt') / 1e6:.1f} MB (the full model was 538 MB)")

ids, mask, _ = make_batch(test_rows[:4])
with torch.no_grad():
    before = model(input_ids=ids, attention_mask=mask).logits
    for block in model.model.layers:                                  # fold each update into the frozen weight
        for name in ("q_proj", "v_proj"):
            lora = getattr(block.self_attn, name)
            lora.base.weight += lora.scale * (lora.B @ lora.A)
            setattr(block.self_attn, name, lora.base)                 # put the plain layer back
    after = model(input_ids=ids, attention_mask=mask).logits
print("largest difference after merging:", f"{(before - after).abs().max().item():.5f}")
print("parameters after merging:", f"{sum(p.numel() for p in model.parameters()):,}")
What you should see
120 tensors, 1.9 MB (the full model was 538 MB)
largest difference after merging: 0.00013
parameters after merging: 134,515,008

One hundred and twenty small tensors (an A and a B for each of two layers in 30 blocks) in a file almost three hundred times smaller than the model. After merging, the model produces the same outputs to within rounding error and has exactly the original number of parameters, so it runs at exactly the original speed.

Reading this output
Keep adapters separate, or merge them?
  • Merged: one ordinary model. Simplest to serve, and required for some export formats (Lesson 11.8). You lose the ability to remove the adapter.
  • Separate: one base model in memory and many small adapters, chosen per request. Serving systems such as vLLMlater · 11.8 load a base model once and apply the adapter each request names (multi-LoRA serving). This is how one deployment serves many customers' or many tasks' tuned variants.

Step 5 · The same thing with the peft library

Nobody wraps layers by hand in practice. Hugging Face's PEFT library (parameter-efficient fine-tuning) does it from a short configuration, handles saving and loading, and supports many methods besides LoRA. This time, adapt every linear layer in the transformer blocks (attention and feed-forward), which is the current common default, with a higher rank:

from peft import LoraConfig, get_peft_model

config = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, target_modules="all-linear", task_type="CAUSAL_LM")
peft_model = get_peft_model(load(), config)
peft_model.print_trainable_parameters()
start = time.time()
train(peft_model, train_rows, steps=80, lr=5e-4, val_rows=val_rows)
print(f"\n{(time.time() - start) / 60:.1f} minutes")
print("validation:", evaluate(peft_model, val_rows))
print("test      :", evaluate(peft_model, test_rows))

It reaches almost the full fine-tune's score on validation, and on the unseen phrasings of the test set it does clearly better than the full fine-tune did.

Two things stand out. The larger LoRA matches full fine-tuning on the data it was shown, while saving a file 27 times smaller. And it generalises better to phrasings it never saw. That is not a law, but it is a common observation: with fewer weights free to move and the original model held fixed underneath, a LoRA has less room to memorise the training sentences and keeps more of what the base model already understood about language. The full fine-tune drove its training loss to almost exactly zero, which on 320 templated tickets means it memorised them.

None of these models is good enough yet. The intent is still wrong on four test tickets in ten, and Lesson 11.5 already diagnosed why: the training data has too few ways of saying each thing. Lesson 11.7 fixes that.

The rest of the family

Method What is trained Where it is used today
LoRA Low-rank matrices beside chosen weight matrices The default for tuning language and image models
QLoRA LoRA on a base model stored in 4 bits (Lesson 11.8), with the adapters in 16-bit Tuning 7B to 70B models on a single GPU. Slightly slower training, much less memory
DoRA Splits each weight into a direction and a magnitude; LoRA adjusts the direction, a small vector the magnitude Often a little better than LoRA at low ranks. LoraConfig(use_dora=True)
rsLoRA LoRA with the scale alpha / √r, which behaves better at high ranks LoraConfig(use_rslora=True) when r is 64 or more
Adapters Small bottleneck layers inserted after sublayers The original 2019 method. Adds a little inference delay; mostly replaced by LoRA
Prefix tuning Trainable vectors fed to the attention of every layer Rare now
Prompt tuning (soft prompts) A few trainable vectors placed before the input tokens Very few parameters; used by some hosted services; weaker on small models
(IA)³ Vectors that rescale activations Extremely small; niche
Full fine-tuning Everything When you have a lot of data and want the last point of quality, or the model is small

Three facts are enough to navigate this in practice. First, LoRA with all-linear targets and a rank of 16 to 32 is the standard starting point. Second, QLoRA is what you use when the model does not fit in memory; it is the method behind most tutorials for tuning 7B and larger models on a free or single GPU, and tools such as Unsloth and Axolotl wrap it. Third, the quality gap to full fine-tuning is usually small and sometimes zero, so start with LoRA and switch only if your evaluation shows a gap that matters.

Tip
Memory, roughly

Training needs memory for the weights, the gradients of the trainable weights, the optimiser's two running averages per trainable weight (Lesson F4.4), and the activations. Full fine-tuning of a 7B model in 16-bit needs on the order of 60 GB or more. LoRA removes the gradients and optimiser state for 99% of the weights, bringing it to roughly 16 to 24 GB. QLoRA also shrinks the stored weights to about 4 to 5 GB, which is how it fits a 7B model on a 12 to 16 GB consumer GPU. Activations still grow with batch size and sequence length, which is why gradient checkpointing and small batches with gradient accumulation are common.

Check your mental model
  • ✗ "LoRA trains a small separate model."
    ✓ It trains a small correction to the big model's own weight matrices; the base model still does the work.
  • ✗ "A LoRA model is slower because of the extra matrices."
    ✓ Once merged there are no extra matrices. Unmerged, the overhead is small.
  • ✗ "Higher rank is always better."
    ✓ Higher rank has more capacity, including capacity to memorise. On small datasets a modest rank often tests better.
  • ✗ "LoRA cannot forget, because the base weights are frozen."
    ✓ The combined model can still behave worse on other tasks. But you can remove the adapter and have the original back, which full fine-tuning cannot offer.
  • ✗ "An adapter works with any model."
    ✓ It works only with the exact base model it was trained on.

Solutions

SolutionP1 · Parameters scale with rank

Each wrapped layer has r × (576 + 576) parameters, and there are 60 of them. Rank 16 doubles the count to 921,600; rank 1 gives 69,120, about one twentieth of one percent of the model.

SolutionM1 · Rank 1

Create the layers with LoRALinear(..., r=1, alpha=2). On this task even rank 1 learns the output format well, because "answer in this JSON shape and copy the order number" is a simple change in behaviour. It usually does somewhat worse on intent. The lesson is that the rank needed depends on how far the task is from what the model already does, not on the size of the model.

SolutionX1 · Forty customers

Forty full fine-tunes: 40 × 14 GB of storage and, to serve them all, 40 models in GPU memory or slow swapping; clearly impractical. Forty merged LoRA models: the same serving problem, since each merged model is full size. One base model with 40 adapters: about 14 GB plus 40 files of tens of megabytes; one model in GPU memory; the adapter is chosen per request by a multi-LoRA server. When the base model is upgraded, every option needs retraining, because adapters are tied to their exact base; keep the training data and scripts so that retraining is a routine job.

Recap
  • LoRA freezes the model and learns a low-rank correction B × A beside chosen weight matrices; B starts at zero so training starts from the pretrained model.
  • Trainable parameters drop to well under 1% of the model, the saved adapter is a few megabytes, and merging removes any inference overhead.
  • LoRA needs a higher learning rate than full fine-tuning (around 1e-4 to 1e-3).
  • peft does this from a LoraConfig: rank, alpha, dropout and target modules.
  • QLoRA adds 4-bit storage of the base model so large models fit on one GPU; DoRA and rsLoRA are refinements; adapters, prefix and prompt tuning are older or niche relatives.

Check your understanding

Q1Why does a LoRA-wrapped layer give exactly the original output before training?

Freezing keeps W unchanged, but it is B = 0 that makes the added term vanish at the start.

Q2What does merging a LoRA adapter do?

The correction has the same shape as W, so it can be added in and the extra matrices dropped.

Q3You must fine-tune a 13-billion-parameter model on a single 24 GB GPU. Which method fits?

4-bit storage shrinks the weights enough to fit, and LoRA keeps the trainable part small.
