Concept
How the code in Chapter 13 runs without a cloud account

Every AWS call in these modules goes through offline(client, operation, response). It uses botocore's Stubber to replay a recorded response instead of calling AWS. Stubber still checks your request against the real AWS API model, so a misspelled parameter or a wrong type fails here exactly as it would in production. To go live, delete the offline(...) line and run with real credentials. The examples were tested with boto3 1.43.

Why this came about

Cloud providers moved quickly to offer managed AI. AWS launched Bedrock in 2023 for access to many models, and AgentCore in 2025 for running agents in production with managed runtime, memory, identity and tools.

In plain words first
One cloud's agent toolbox

Each cloud offers the same layers: model access, an agent runtime, tools and gateways, identity, memory, observability and evaluation. On AWS, Bedrock gives access to many models plus knowledge bases and guardrails, and AgentCore provides managed pieces for running agents in production: runtime, memory, identity, a tool gateway and observability. Learn each cloud as a map of those layers.

Step 1 · Call a model with the Converse API

Bedrock gives you three ways to call a model:

API Endpoint Use it when
Converse / ConverseStream bedrock-runtime The default for AWS-native code: one message format for every model, with tools, images, documents, guardrails and prompt caching
OpenAI-compatible APIs (Chat Completions, Responses) bedrock-runtime and bedrock-mantle You want to keep OpenAI SDK code and switch the base URL; the Responses API on bedrock-mantle serves OpenAI's models on Bedrock
InvokeModel bedrock-runtime You need a provider's native request format or a feature not yet in Converse; also embeddings 
import io, json, datetime
import boto3
from botocore.stub import Stubber
from botocore.response import StreamingBody

REGION = "ap-south-1"                                  # Mumbai: pick the Region your data must stay in
session = boto3.Session(region_name=REGION)            # credentials come from your profile, SSO or role

_stubs = {}
def offline(client, operation: str, response: dict):
    """Lab mode: queue a recorded response instead of calling AWS. Delete the call to go live.
    Stubber still checks your request against the real AWS API model."""
    if id(client) not in _stubs:
        _stubs[id(client)] = Stubber(client)
        _stubs[id(client)].activate()
    _stubs[id(client)].add_response(operation, response)

brt = session.client("bedrock-runtime")
MODEL = "global.anthropic.claude-sonnet-placeholder-v1:0"   # copy a real model or inference profile ID from the console
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}
TOOL_CONFIG = {"tools": [{"toolSpec": {
    "name": "get_order_status", "description": "Return the shipping status for an order ID like 'A-1001'.",
    "inputSchema": {"json": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}}}]}

# Recorded responses: first the model asks for the tool, then it answers.
offline(brt, "converse", {"output": {"message": {"role": "assistant", "content": [
    {"toolUse": {"toolUseId": "t1", "name": "get_order_status", "input": {"order_id": "A-1001"}}}]}},
    "stopReason": "tool_use", "usage": {"inputTokens": 412, "outputTokens": 38, "totalTokens": 450}, "metrics": {"latencyMs": 620}})
offline(brt, "converse", {"output": {"message": {"role": "assistant", "content": [{"text": "A-1001 has shipped."}]}},
    "stopReason": "end_turn", "usage": {"inputTokens": 470, "outputTokens": 9, "totalTokens": 479}, "metrics": {"latencyMs": 410}})

def ask(question: str) -> str:
    """The same agent loop as Lesson 3.2, in Bedrock's message format."""
    messages = [{"role": "user", "content": [{"text": question}]}]
    for _ in range(5):
        r = brt.converse(modelId=MODEL, messages=messages, toolConfig=TOOL_CONFIG,
                         system=[{"text": "You are ShopKart's support assistant. Be brief."}],
                         inferenceConfig={"maxTokens": 512, "temperature": 0})
        msg = r["output"]["message"]
        messages.append(msg)
        print(f"  stop={r['stopReason']} tokens={r['usage']['totalTokens']} latency={r['metrics']['latencyMs']}ms")
        if r["stopReason"] != "tool_use":
            return msg["content"][0]["text"]
        results = []
        for block in msg["content"]:
            if "toolUse" in block:
                order = block["toolUse"]["input"]["order_id"]
                results.append({"toolResult": {"toolUseId": block["toolUse"]["toolUseId"],
                                               "content": [{"text": f"{order} is {ORDERS.get(order, 'not found')}"}]}})
        messages.append({"role": "user", "content": results})

print(ask("Where is A-1001?"))
What you should see
  stop=tool_use tokens=450 latency=620ms
  stop=end_turn tokens=479 latency=410ms
A-1001 has shipped.

The loop is the one you wrote in Lesson 3.2. Only the message shapes differ: tool results go back as toolResult blocks inside a user message.

Choosing where and how your request runs

Option What it does Use it for
Cross-Region inference (inference profiles) Routes a request to another Region with capacity. Geographic profiles (prefixes like us., eu., apac., and in-country profiles for some countries, including India) keep data in that geography; global profiles (global.) route anywhere for the most capacity Higher throughput; data residency with geographic profiles
Service tiers: Standard, Priority, Flex, Reserved Priority pays more for faster, preferred processing; Flex pays less for work that can wait; Reserved buys guaranteed capacity for a term Match price to urgency: Priority for live chat, Flex for evals and enrichment
Batch inferencelater · 13.2 Submit a file of requests; results land in S3 at about half the on-demand price Large offline jobs
Provisioned Throughput Dedicated model units; needed for some custom models Steady, high, predictable load
Prompt caching Caches a long, repeated prefix (system prompt, documents, tool list) Cuts cost and latency for agents, which resend the same prefix every turn (Lesson 12.10)
Intelligent Prompt Routing Sends each request to the cheaper or stronger model in a family based on predicted difficulty Mixed workloads
Application inference profileslater · 13.2 A profile you create and tag, wrapping a model Cost allocation per team or app (Lesson 13.2)
Watch out
Data and model access

Bedrock does not use your prompts or outputs to train models, and model providers do not see them. You still choose which models an account may use (with IAM and service control policieslater · 13.2), and some models are served only through cross-Region or global profiles, so check the profile's Regions against your residency rules before you ship.

Step 2 · Guardrails

Amazon Bedrock Guardrails is a managed policy layer you can attach to any Bedrock model call, or call on its own with ApplyGuardrail to check text from any model, tool or user (the pattern from Lesson 10.1).

Policy What it catches
Content filters Hate, insults, sexual content, violence, misconduct, and prompt attacks (jailbreaks and injection), with adjustable strength, for text and images
Denied topics Topics you describe in plain language ("investment advice")
Word filters Exact words and phrases, plus a managed profanity list
Sensitive information filters Built-in PII types and your own regular expressions; block or mask
Contextual grounding checks Whether an answer is supported by the retrieved source and relevant to the question (hallucination in RAG)
Automated Reasoning checks Validates answers against rules written as formal logic (for example an HR policy), with a mathematically checkable explanation 
offline(brt, "apply_guardrail", {
    "usage": {"topicPolicyUnits": 1, "contentPolicyUnits": 1, "wordPolicyUnits": 1, "sensitiveInformationPolicyUnits": 1,
              "sensitiveInformationPolicyFreeUnits": 0, "contextualGroundingPolicyUnits": 0},
    "action": "GUARDRAIL_INTERVENED", "actionReason": "Sensitive information",
    "outputs": [{"text": "My card is {CREDIT_DEBIT_CARD_NUMBER}"}], "assessments": []})

g = brt.apply_guardrail(guardrailIdentifier="gr-shopkart", guardrailVersion="1", source="INPUT",
                        content=[{"text": {"text": "My card is 4111 1111 1111 1111"}}])
print("guardrail:", g["action"], "->", g["outputs"][0]["text"])
What you should see
guardrail: GUARDRAIL_INTERVENED -> My card is {CREDIT_DEBIT_CARD_NUMBER}

To apply the same guardrail inside a model call, pass guardrailConfig={"guardrailIdentifier": ..., "guardrailVersion": ...} to converse.

Two features matter at enterprise scale. Guardrail enforcement (PutEnforcedGuardrailConfiguration, or AWS Organizations policies) applies a guardrail to every Bedrock call in an account or across accounts, so a team cannot forget it. IAM condition keys such as bedrock:GuardrailIdentifier let you deny any model call that does not carry the approved guardrail.

Step 3 · Knowledge Bases and retrieval

Bedrock Knowledge Bases is managed RAG (Chapter 4): connect a source, and it parses, chunks, embeds, stores and retrieves.

Choice Options
Sources S3, web crawler, Confluence, SharePoint, Salesforce, custom connectors; structured data (natural language to SQL over Redshift and the Glue catalog)
Parsing Default text parsing, foundation-model parsing, or Bedrock Data Automation for complex PDFs, tables, images, audio and video
Chunking Fixed-size, hierarchical, semantic, none, or a Lambda for your own
Vector stores Amazon S3 Vectors (lowest cost), OpenSearch Serverless, Aurora PostgreSQL (pgvector), Neptune Analytics (GraphRAG), Pinecone, MongoDB Atlas, Redis Enterprise
Retrieval Retrieve (chunks only) or RetrieveAndGenerate (chunks plus an answer with citations); hybrid search, metadata filters, reranking models, query decomposition 
kb = session.client("bedrock-agent-runtime")
offline(kb, "retrieve", {"retrievalResults": [
    {"content": {"text": "Damaged items are refundable within 30 days."},
     "location": {"type": "S3", "s3Location": {"uri": "s3://shopkart-docs/refund-policy.md"}}, "score": 0.81}]})

hits = kb.retrieve(knowledgeBaseId="KBSHOPKART1", retrievalQuery={"text": "refund for a broken mixer"},
                   retrievalConfiguration={"vectorSearchConfiguration": {
                       "numberOfResults": 5,
                       "overrideSearchType": "HYBRID",                       # keyword plus vector (Lesson 4.6)
                       "filter": {"equals": {"key": "doc_type", "value": "policy"}}}})
for h in hits["retrievalResults"]:
    print(f"kb: {h['score']:.2f} {h['location']['s3Location']['uri']} | {h['content']['text']}")

# Or skip the managed pipeline and query an S3 vector index yourself
s3v = session.client("s3vectors")
offline(s3v, "query_vectors", {"vectors": [{"key": "refund-policy#3", "distance": 0.19,
                               "metadata": {"source": "refund-policy.md"}}], "distanceMetric": "cosine"})
q = s3v.query_vectors(vectorBucketName="shopkart-vectors", indexName="policies", topK=3,
                      queryVector={"float32": [0.1] * 1024}, returnMetadata=True, returnDistance=True)
print("s3 vectors:", [(v["key"], v["distance"]) for v in q["vectors"]])
What you should see
kb: 0.81 s3://shopkart-docs/refund-policy.md | Damaged items are refundable within 30 days.
s3 vectors: [('refund-policy#3', 0.19)]

Agentic retrieval (Lesson 4.11) is now built in. AgentCore's managed knowledge bases (generally available in July 2026) plan the search, run several queries, check the results and stream back a cited answer through an agentic retrieve API, so you do not have to build that loop yourself. Amazon S3 Vectors stores vectors directly in S3 at much lower cost than a database, which makes it the default for large, rarely-queried corpora; keep OpenSearch or pgvector when you need low-latency, high-QPS or hybrid search.

Step 4 · Amazon Bedrock AgentCore

AgentCore is AWS's agent platform. It is modular: use one service or all of them, with any framework (Strands, LangGraph, CrewAI, ADK, OpenAI Agents SDK, LlamaIndex, your own loop) and any model, inside AWS or not.

Host any agent on AgentCore Runtime

Runtime needs only an HTTP app with POST /invocations and GET /ping. The bedrock-agentcore package's BedrockAgentCoreApp gives you both. Here is the Strands agent from Lesson 7.3, served the same way it will run in AWS, and tested locally:

from mockllm import start
from strands import Agent, tool
from strands.models.openai import OpenAIModel
from bedrock_agentcore.runtime import BedrockAgentCoreApp
from starlette.testclient import TestClient

# Live: model = BedrockModel(model_id=MODEL)   (from strands.models import BedrockModel)
model = OpenAIModel(client_args={"base_url": start(), "api_key": "mock"}, model_id="mock-model")

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

agent = Agent(model=model, tools=[get_order_status], callback_handler=None,
              system_prompt="You are ShopKart's support assistant. Be brief.")
app = BedrockAgentCoreApp()

@app.entrypoint
def invoke(payload: dict, context) -> dict:
    """AgentCore calls this for every request. The payload is your own JSON."""
    return {"answer": str(agent(payload["prompt"])).strip(), "session": context.session_id}

client = TestClient(app)                                     # live: app.run serves it on port 8080
print("ping:", client.get("/ping").json()["status"])
r = client.post("/invocations", json={"prompt": "Where is A-1001?"},
                headers={"X-Amzn-Bedrock-AgentCore-Runtime-Session-Id": "customer-42-session-0001-abcdefghijk"})
print("invoke:", r.status_code, r.json())
What you should see
ping: Healthy
invoke: 200 {'answer': 'Here is what I found: A-1001 is shipped', 'session': 'customer-42-session-0001-abcdefghijk'}

(You will also see one JSON log line per invocation. Runtime ships those to CloudWatch.)

To deploy, use the AgentCore CLI (npm install -g @aws/agentcore): agentcore create --framework Strands scaffolds a project (also LangChain_LangGraph, GoogleADK, OpenAIAgents, VercelAI; protocols HTTP, MCP, A2A or AG-UI), agentcore dev runs it locally, agentcore deploy creates the infrastructure with the AWS CDK, and agentcore invoke, agentcore logs and agentcore traces let you test and debug it. Callers then use InvokeAgentRuntime:

ac = session.client("bedrock-agentcore")
body = b'{"answer": "A-1001 has shipped."}'
offline(ac, "invoke_agent_runtime", {"runtimeSessionId": "s" * 33, "contentType": "application/json",
                                     "response": StreamingBody(io.BytesIO(body), len(body)), "statusCode": 200})

resp = ac.invoke_agent_runtime(
    agentRuntimeArn="arn:aws:bedrock-agentcore:ap-south-1:123456789012:runtime/shopkart_support-abc123",
    runtimeSessionId="customer-42-session-0001-abcdefghijk",     # 33+ characters; one per conversation
    runtimeUserId="customer-42",                                  # who the agent acts for (Identity)
    payload=json.dumps({"prompt": "Where is A-1001?"}).encode())
print("agentcore:", resp["statusCode"], json.loads(resp["response"].read())["answer"])
What you should see
agentcore: 200 A-1001 has shipped.

The same session ID returns the user to the same isolated microVM, with its files and state, until the session ends.

Give it memory

AgentCore Memory stores raw events (short-term memory) and runs strategies in the background that extract long-term memory records into namespaces you define, such as /customers/{actorId}/preferences (Lesson 3.10's memory types, managed for you).

mem = session.client("bedrock-agentcore")
MEMORY_ID = "shopkart_memory-AbCdEf1234"
now = datetime.datetime.now(datetime.timezone.utc)

offline(mem, "create_event", {"event": {"memoryId": MEMORY_ID, "actorId": "customer-42", "sessionId": "s-1",
        "eventId": "0000000000000#a1b2c3d4", "eventTimestamp": now, "payload": [], "branch": {"name": "main"}}})
mem.create_event(memoryId=MEMORY_ID, actorId="customer-42", sessionId="s-1", eventTimestamp=now,
                 payload=[{"conversational": {"role": "USER", "content": {"text": "Please send refunds to my UPI ID."}}}])

# Later, in a new session, the preference strategy has extracted a record:
offline(mem, "retrieve_memory_records", {"memoryRecordSummaries": [
    {"memoryRecordId": "mem-" + "0" * 36, "content": {"text": "Customer prefers refunds to UPI."},
     "memoryStrategyId": "preferences", "namespaces": ["/customers/customer-42/preferences"],
     "createdAt": now, "score": 0.9}]})
recs = mem.retrieve_memory_records(memoryId=MEMORY_ID, namespace="/customers/customer-42/preferences",
                                   searchCriteria={"searchQuery": "refund method", "topK": 3})
print("memory:", [r["content"]["text"] for r in recs["memoryRecordSummaries"]])
What you should see
memory: ['Customer prefers refunds to UPI.']

Strands, LangGraph and other frameworks have AgentCore Memory session managers and checkpointers, so you rarely call these APIs by hand. Set an event expiry, scope namespaces by actor, and treat memory as a personal-data store (Lesson 10.4).

Tools, identity and policy through the Gateway

The Gateway is where enterprise control lives. A typical setup:

  1. Register targets: a Lambda function, an OpenAPI spec for your order API, and an existing MCP server.
  2. Set inbound auth (your identity provider's JWT, or IAM) so only approved agents and users connect.
  3. Set outbound auth with Identity: the Gateway fetches the right OAuth token or API key for each target from the token vault, so the agent never holds secrets.
  4. Attach a Policy engine. Rules such as "refund_order only when amount <= 5000 and the user's role is support_agent" are checked on every tool call, outside the model, so a prompt injection cannot talk its way past them (Lesson 10.2).
  5. Add interceptors (Lambda functions on request and response) for redaction or custom checks, and turn on semantic tool search when there are hundreds of tools.

The agent sees one MCP server URL. This is the "tool gateway" pattern from Lesson 12.4, as a managed service.

Evaluate it

AgentCore Evaluations scores a session with built-in or custom evaluators. The call below asks whether the agent achieved the user's goal in one session. As everywhere in this chapter, the first lines register a canned response so that the code runs without an AWS account; the call underneath is the real one.

offline(ac, "evaluate", {"evaluationResults": [
    {"evaluatorArn": "arn:aws:bedrock-agentcore:::evaluator/Builtin.GoalSuccessRate", "evaluatorId": "Builtin.GoalSuccessRate",
     "evaluatorName": "Builtin.GoalSuccessRate", "value": 1.0, "label": "Yes",
     "explanation": "The agent looked up the order and reported its status.",
     "context": {"spanContext": {"sessionId": "customer-42-session-0001-abcdefghijk"}}}]})

# Live: read the session's OpenTelemetry spans from CloudWatch (the agent's log group or aws/spans)
spans = [{"name": "execute_tool get_order_status", "attributes": {"session.id": "customer-42-session-0001-abcdefghijk"}}]
ev = ac.evaluate(evaluatorId="Builtin.GoalSuccessRate",
                 evaluationInput={"sessionSpans": spans},
                 evaluationReferenceInputs=[{"context": {"spanContext": {"sessionId": "customer-42-session-0001-abcdefghijk"}},
                                             "expectedTrajectory": {"toolNames": ["get_order_status"]}}])
for res in ev["evaluationResults"]:
    print("eval:", res["evaluatorName"], res["label"], "|", res["explanation"])
What you should see
eval: Builtin.GoalSuccessRate Yes | The agent looked up the order and reported its status.

In production you rarely call Evaluate one session at a time: create an online evaluation configuration that samples live sessions, or a batch evaluation over a dataset before each release (Lesson 12.11). The agentcore run and agentcore evals commands wrap both.

No code: the Harness

A harness is an agent defined as configuration. You create it once (model, system prompt, tools from a Gateway, skills, limits) and call InvokeHarness, which streams events like ConverseStream. It suits simple agents and prototypes, and agentcore export turns a harness into Strands code when you outgrow it.

# RUN_LIVE: needs a real harness, so this block is not run offline
stream = ac.invoke_harness(
    harnessArn="arn:aws:bedrock-agentcore:ap-south-1:123456789012:harness/shopkart-faq",
    runtimeSessionId="customer-42-session-0001-abcdefghijk",
    messages=[{"role": "user", "content": [{"text": "What is the refund window?"}]}],
    maxIterations=5)
for event in stream["stream"]:
    if "contentBlockDelta" in event:
        print(event["contentBlockDelta"]["delta"].get("text", ""), end="")

Distillation Prompts; a large teacher model generates the answers A smaller, cheaper model that behaves like a big one on your task
Continued pre-training Unlabeled domain text Domain vocabulary (selected Amazon models)
Custom Model Import Weights of supported open models (Llama, Mistral, Qwen and others) trained elsewhere Serving your own model serverlessly through the Bedrock API

Bedrock Evaluations run model evaluation and RAG evaluation jobs, with human reviewers or an LLM as judge, and prompt optimization rewrites a prompt for a target model. Use them for model selection; use AgentCore Evaluations for agents.

Industry practice
A reference architecture AWS teams converge on
  • Front door: API Gateway or an ALB with Cognito or your IdP, then AgentCore Runtime (or Lambda or ECS for simple agents).
  • Agent: Strands or LangGraph, models through Bedrock with geographic cross-Region profiles for residency, a guardrail enforced at account level, prompt caching on.
  • Tools: all through one AgentCore Gateway with Policy rules and Identity-managed credentials; no secrets in agent code.
  • Knowledge: Knowledge Bases or managed knowledge bases on S3 Vectors, with OpenSearch where latency matters.
  • State: AgentCore Memory, with DynamoDB for business state; Step Functions or Lambda durable functions for long workflows with human approvals (Lesson 12.8).
  • Ops: ADOTlater · 13.2 traces into CloudWatch, invocation logging to S3 with KMS, CloudTrail, online evaluations, cost tags through application inference profiles (Lesson 13.2).
  • Accounts: separate dev, staging and prod accounts; model access and guardrails set by SCPs and enforced guardrails from the organization's security account.
In production
Production issues teams hit on Bedrock and AgentCore
  • Throttling at launch: on-demand throughput is limited by per-model, per-Region quotas, and a launch-day spike returns throttling errors. Use cross-Region inference profiles, request quota increases weeks ahead, and consider provisioned throughput for steady high volume.
  • Feature and model availability by Region: new models and features often reach US Regions first, and Mumbai availability differs by feature (the rerankers above are one example). Check availability against your data-residency rules before designing around a feature.
  • Knowledge Base syncs are jobs: new documents are not searchable until the ingestion job finishes, and individual files can fail while the job succeeds. Read the ingestion job's statistics and alert on failed documents.
  • Guardrails that are optional: a guardrail only applies to calls that reference it. Enforce it with the IAM condition shown in Lesson 13.2 so a code change cannot drop it.
  • Runtime limits: managed agent runtimes have limits on session duration, payload size and concurrency; check them against your longest tasks and largest documents before committing.

Solutions

SolutionP1 · Managed runtime, your logic

Runtime hosts and scales the agent with session isolation; Memory, Gateway, Identity and Observability replace your own memory store, tool gateway, credentials handling and tracing. The agent's logic, prompts, tools and evals stay yours.

SolutionB1 · Inference profiles

A validation error that the model must be invoked through an inference profile. Profiles route requests across regions for capacity and are required for some models; use the profile ID the console lists.

SolutionD1 · Identity for outbound calls

AgentCore Identity (or your credential setup): the agent lacks a token for the user or service it acts for. Configure the credential provider and scopes, and test with a production-like identity.

SolutionM1 · Map the architecture

The graph in AgentCore Runtime (or a container), models via Bedrock, tools behind AgentCore Gateway, memory in AgentCore Memory, traces in its observability with CloudWatch, guardrails with Bedrock Guardrails. You still build the graph, the approval service and the evals.

Check your understanding

Q1Which Bedrock API should new AWS-native agent code use by default?

Converse works the same for every model and supports tools, guardrails and caching. Use the OpenAI-compatible APIs when you want to keep OpenAI SDK code.

Q2A bank in India needs model requests to stay in the country. What should it use?

Global profiles can route anywhere. Geographic profiles keep requests inside a geography, so check which Regions each one covers.

Q3What does AgentCore Policy do that a system prompt cannot?

A prompt asks the model to behave. A policy at the Gateway stops the call whatever the model decides.

Q4A team wants to start a new managed agent on AWS in late 2026. What should they use?

Bedrock Agents became Agents Classic and closed to new customers in July 2026.

Q5Where does long-term memory come from in AgentCore Memory?

You store events. Strategies distil them into records you can search later.
