In plain words first
The idea in one line

Hybrid memory runs three stores in parallel — vector for semantic similarity, KV for fast fact lookup, graph for entity-relationship reasoning — with a scoring layer that fuses them on retrieval. This is a widely used production pattern for external memory; Mem0 (Chhikara et al., 2025) is one reference implementation.

Terms you'll hear
Term What people say What it actually means
Hybrid memory "Vector plus graph plus KV" Three stores written in parallel, fused on retrieval
Fact extraction "Memory ingestion" LLM step that breaks text into (entity, relation, fact) tuples
Fusion scoring "Relevance ranking" Weighted sum of relevance, importance, recency
Scope "Memory namespace" user / session / agent — determines who sees what
Mem0g "Memory graph" Typed edges with temporal validity for relationship queries
Temporal invalidation "Soft delete" Mark contradicted edges invalid; never delete
Embedding drift "Retrieval rot" Vector quality degrades as corpus grows; re-embed periodically

The problem

In plain words first

Memory questions come in different shapes. "What did we discuss about deadlines?" needs similarity search over past notes (a vector store finds text with similar meaning). "What is her phone number?" needs an exact lookup (a key-value store, like a dictionary). "Who else works on her project?" needs relationships (a graph store of who-is-connected-to-what). Mem0 keeps all three behind one add and one search, uses a language model to pull facts out of each message and decide whether each one is new, an update, or already known, and ranks results by a weighted mix of relevance, importance and recency. This lesson builds the three stores and the ranking in plain Python, then swaps in real embeddings and a real model for the write path, and checks what each change does.

Each store is right for only one of three query classes:

  • Semantic similarity — "what did we discuss about agent drift last week?" Vector wins; KV and graph miss.
  • Fact lookup — "what is the user's phone number?" KV wins; vector is wasteful, graph is overkill.
  • Relationship reasoning — "which customers share the same billing entity?" Graph wins; vector and KV cannot answer.

Production agents issue all three in one session. A single-store memory is always wrong for two of them. Mem0's contribution is wiring all three behind a single add/search surface with a scoring function that fuses them.

Idea 1 · Three stores in parallel

Mem0 (arXiv:2504.19413, April 2025) on add(text, user_id, metadata):

  1. Extract candidate facts from the text (an LLM-driven step).
  2. Write each fact to the vector store (embedding) for semantic search.
  3. Write each fact to the KV store keyed on (user_id, fact_type, entity) for O(1) lookup.
  4. Write each fact to the graph store (Mem0g) as typed edges for relationship queries.

On search(query, user_id):

  1. Vector store returns top-k by embedding cosine.
  2. KV store returns direct hits keyed on query-derived (user_id, type, entity).
  3. Graph store returns subgraph reachable from query entities.
  4. A scoring layer fuses the three.

Idea 2 · Fusion scoring

score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
  • Relevance — vector cosine, KV exact match, graph path weight.
  • Importance — tagged at write time or learned (some facts matter more: names, IDs, policies).
  • Recency — exponential decay over time since last write or read.

Weights are tuned per product. Higher w_recency for chat agents; higher w_importance for compliance agents; higher w_relevance for retrieval agents.

Idea 3 · Mem0g and temporal reasoning

Mem0g adds a conflict detector. When a new fact contradicts an existing edge, the existing edge is marked invalid but not deleted. Temporal queries ("what was the user's city in March?") traverse the valid-at-time subgraph.

This is the compliance-grade behavior Letta's invalidation pattern generalizes.

Idea 4 · Benchmark numbers

Mem0's April 2026 algorithm update reports, from its own evaluation:

  • LoCoMo (long-form conversation memory): 92.5
  • LongMemEval (long-horizon episodic memory): 94.4
  • BEAM (1M-token memory benchmark): 64.1 (48.6 at 10M tokens)

These are vendor-reported numbers. In the 2025 paper's own LOCOMO comparison, answering from the full conversation scored higher than Mem0 (72.9 against 66.9 on the LLM-judge metric) but used about 15 times as many tokens per question. Benchmarks alone don't justify choice — operational shape does — but the numbers show the fusion design is not a rounding error.

Idea 5 · Scope taxonomy

Mem0 splits memory by scope:

  • User memory — persists across sessions, keyed on user_id.
  • Session memory — persists within one thread.
  • Agent memory — per-agent instance state.

Every write picks one scope. Retrieval can query across scopes with per-scope weights. Mixing scopes without thought is how you get "the assistant told Alice about Bob's project" incidents.

Idea 6 · Where this pattern goes wrong

  • Embedding drift. Vector results that look right on the first hundred queries degrade as the corpus grows. Add periodic re-embedding of the top-N-used records.
  • KV schema creep. (user_id, type, entity) looks simple until every team adds their own type. Audit the type set quarterly.
  • Graph explosion. One noisy extractor adds 50 edges per message. Cap graph writes per add call; drop low-confidence edges.

The same idea as a formula

Fused score. For a query q and record r written Δt seconds ago, with half-life h:

s(q,r)=wrel​rel(q,r)+wimp​imp(r)+wrec​2−Δt/h,wrel​+wimp​+wrec​=1.
The lesson uses 0.6,0.2,0.2 and h = one day.

Scale matters. Relevance only decides the ranking if its spread across records is larger than the spread of the other terms. Two records with relevance gap δ and importance gap ι swap order when

wrel​δ<wimp​ι,
so with weights 0.6 and 0.2, an importance gap of 0.3 beats any relevance gap below 0.1.

Write path. For each extracted fact f, Mem0 retrieves the most similar memories N(f) and an LLM chooses op(f,N(f))∈{ADD,UPDATE,DELETE,NONE}.

Worked example
"where does ava live", by hand, with the lesson's word overlap
  • Query words: {where, does, ava, live}. "ava lives in Berlin" shares only {ava} ("live" ≠ "lives"): Jaccard 1/7≈0.14. "ava moved to Lisbon last month" also shares only {ava}: 1/9≈0.11. The curriculum sentence: 1/12≈0.08.
  • Fused with importance and fresh recency (≈1): curriculum 0.6⋅0.08+0.2⋅0.9+0.2=0.43; Lisbon 0.6⋅0.11+0.2⋅0.8+0.2=0.43; Berlin 0.6⋅0.14+0.2⋅0.6+0.2=0.40.
  • Relevance contributes at most 0.09 here; importance contributes up to 0.18. The ranking is decided by importance, not by the question, which is why the curriculum comes first.
  • With embeddings, relevance values sit around 0.6 to 0.8 and differ by a few hundredths between records, so the same imbalance remains; the second lab shows both effects.
Check your mental model
  • ✗ "One store is enough if it is good."
    ✓ Similarity, exact lookup and relationships are different questions with different best stores.
  • ✗ "Fusion weights are a detail."
    ✓ If relevance has a small spread, importance and recency decide the ranking regardless of the query.
  • ✗ "Invalidating a graph edge removes the old fact."
    ✓ Only from the graph; the same fact in the vector and key-value stores must be handled too.
  • ✗ "The extractor writes what the user said."
    ✓ A weak extractor writes noise or invents facts; the write path needs its own checks.

from sentence_transformers import SentenceTransformer
import main
from main import Mem0, VectorStore
emb = SentenceTransformer("BAAI/bge-small-en-v1.5")
class EmbeddingStore(VectorStore):
    """Cosine similarity of bge-small embeddings; same interface as the lesson's VectorStore."""
    def search(self, query, top_k=5):
        recs = list(self._records.values())
        vecs = emb.encode([r.text for r in recs], normalize_embeddings=True)
        q = emb.encode(["Represent this sentence for searching relevant passages: " + query], normalize_embeddings=True)[0]
        scored = sorted(zip((vecs @ q).tolist(), recs), key=lambda x: -x[0])
        return [(round(s, 3), r) for s, r in scored[:top_k]]
class ValidOnly(Mem0):
    """Drop records whose graph edges were all invalidated by a later fact."""
    def search(self, query, **kw):
        stale = {r.rid for r in self.vector._records.values()
                 if any(e.obj in r.text and not e.valid for e in self.graph.all_edges())
                 and not any(e.obj in r.text and e.valid for e in self.graph.all_edges())}
        return [(s, r) for s, r in super().search(query, **kw) if r.rid not in stale]

# Mem0's write path is two LLM steps: extract candidate facts from a message, then for each fact decide
# ADD, UPDATE, DELETE or NONE against the most similar existing memories. Qwen2.5-0.5B-Instruct plays
# both steps (greedy, CPU); the expected decisions are written next to each message.
import json, re, torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
def chat(text, max_new=120):
    ids = tok.apply_chat_template([{"role": "user", "content": text}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=max_new, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
EXTRACT = ('Extract the personal facts about the user from this message as a JSON list of short strings. '
           'If there are none, return []. Output only JSON.\nMessage: "{m}"')
DECIDE = ('Existing memories:\n{mem}\nNew fact: "{fact}"\nChoose one operation: ADD (new information), UPDATE '
          '(replaces an existing memory; give its id), DELETE (contradicts and removes one; give its id), NONE '
          '(already known). Answer as JSON like {{"op": "UPDATE", "id": "m2"}}.')
MESSAGES = [("I live in Berlin and work on a curriculum about agents.", ["ADD", "ADD"]),
            ("Thanks, that helps!", []),
            ("Update: I moved to Lisbon last month.", ["UPDATE m1"]),
            ("I still work on the agent curriculum, by the way.", ["NONE"])]
memories = {}
def ops_for(fact):
    near = sorted(memories.items(), key=lambda kv: -float(emb.encode([kv[1]], normalize_embeddings=True)[0]
                  @ emb.encode([fact], normalize_embeddings=True)[0]))[:3]
    mem_txt = "\n".join(f"{k}: {v}" for k, v in near) or "(none)"
    raw = chat(DECIDE.format(mem=mem_txt, fact=fact), max_new=30)
    m = re.search(r"\{.*?\}", raw, re.S)
    try:
        d = json.loads(m.group(0)) if m else {}
    except json.JSONDecodeError:
        d = {}
    return d.get("op", "?").upper(), d.get("id")
for msg, expected in MESSAGES:
    raw = chat(EXTRACT.format(m=msg))
    try:
        facts = json.loads(re.search(r"\[.*\]", raw, re.S).group(0))
    except (AttributeError, json.JSONDecodeError):
        facts = ["<unparseable: " + raw[:40] + ">"]
    decided = []
    for fact in facts:
        op, mid = ops_for(str(fact))
        decided.append(f"{op}{' ' + mid if mid else ''}")
        if op == "ADD" or (op == "UPDATE" and mid not in memories):
            memories[f"m{len(memories) + 1}"] = str(fact)
        elif op == "UPDATE":
            memories[mid] = str(fact)
        elif op == "DELETE" and mid in memories:
            del memories[mid]
    print(f"message: {msg}\n  extracted: {facts}\n  decided:   {decided}\n  expected:  {expected}")
print(f"\nmemory store at the end: {memories}")

Part 1 of 5 · Record, VectorStore, KVKey, KVStore, Edge

"""Mem0-shaped hybrid memory: vector + KV + graph with fusion scoring.

Stdlib only. Vector store uses token-overlap as an embedding stand-in.
Scope taxonomy: user / session / agent. Fusion: relevance + importance + recency.
"""

from __future__ import annotations

import time
from dataclasses import dataclass, field
from typing import Any


@dataclass
class Record:
    rid: str
    text: str
    scope: str
    user_id: str
    session_id: str
    importance: float = 0.5
    ts: float = field(default_factory=time.time)
    tags: tuple[str, ...] = ()


class VectorStore:
    def __init__(self) -> None:
        self._records: dict[str, Record] = {}

    def add(self, record: Record) -> None:
        self._records[record.rid] = record

    def search(self, query: str, top_k: int = 5) -> list[tuple[float, Record]]:
        q_tokens = set(query.lower().split())
        scored: list[tuple[float, Record]] = []
        for record in self._records.values():
            r_tokens = set(record.text.lower().split())
            if not r_tokens:
                continue
            overlap = len(q_tokens & r_tokens)
            if overlap == 0:
                continue
            score = overlap / (len(q_tokens | r_tokens))
            scored.append((score, record))
        scored.sort(key=lambda x: -x[0])
        return scored[:top_k]


@dataclass(frozen=True)
class KVKey:
    user_id: str
    fact_type: str
    entity: str


class KVStore:
    def __init__(self) -> None:
        self._map: dict[KVKey, Record] = {}

    def put(self, key: KVKey, record: Record) -> None:
        self._map[key] = record

    def get(self, key: KVKey) -> Record | None:
        return self._map.get(key)

    def by_user(self, user_id: str) -> list[Record]:
        return [r for k, r in self._map.items() if k.user_id == user_id]


@dataclass
class Edge:
    subject: str
    relation: str
    obj: str
    valid: bool = True
    ts: float = field(default_factory=time.time)

Part 2 of 5 · GraphStore, Mem0Config

class GraphStore:
    def __init__(self) -> None:
        self._edges: list[Edge] = []

    def add_edge(self, subject: str, relation: str, obj: str) -> None:
        for edge in self._edges:
            if edge.valid and edge.subject == subject and edge.relation == relation:
                edge.valid = False
        self._edges.append(Edge(subject=subject, relation=relation, obj=obj))

    def neighbors(self, subject: str, valid_only: bool = True) -> list[Edge]:
        return [e for e in self._edges
                if e.subject == subject and (e.valid or not valid_only)]

    def all_edges(self) -> list[Edge]:
        return list(self._edges)


@dataclass
class Mem0Config:
    w_relevance: float = 0.6
    w_importance: float = 0.2
    w_recency: float = 0.2
    recency_halflife_s: float = 86400.0

Part 3 of 5 · Mem0

class Mem0:
    def __init__(self, config: Mem0Config | None = None) -> None:
        self.vector = VectorStore()
        self.kv = KVStore()
        self.graph = GraphStore()
        self.config = config or Mem0Config()
        self._counter = 0

    def add(self, text: str, *, user_id: str, session_id: str = "s0",
            scope: str = "user", importance: float = 0.5,
            tags: tuple[str, ...] = (),
            kv_triples: tuple[tuple[str, str], ...] = (),
            graph_triples: tuple[tuple[str, str, str], ...] = ()) -> str:
        self._counter += 1
        rid = f"m{self._counter:03d}"
        record = Record(rid=rid, text=text, scope=scope, user_id=user_id,
                        session_id=session_id, importance=importance, tags=tags)
        self.vector.add(record)
        for fact_type, entity in kv_triples:
            self.kv.put(KVKey(user_id=user_id, fact_type=fact_type, entity=entity), record)
        for subject, relation, obj in graph_triples:
            self.graph.add_edge(subject, relation, obj)
        return rid

    def _recency_score(self, record: Record, now: float) -> float:
        elapsed = max(0.0, now - record.ts)
        half = self.config.recency_halflife_s
        return 0.5 ** (elapsed / half) if half > 0 else 1.0

    def search(self, query: str, *, user_id: str,
               scope: str | None = None, top_k: int = 5) -> list[tuple[float, Record]]:
        now = time.time()
        vector_hits = self.vector.search(query, top_k=top_k * 3)
        fused: dict[str, tuple[float, Record]] = {}
        for rel, record in vector_hits:
            if scope is not None and record.scope != scope:
                continue
            if record.user_id != user_id and record.scope == "user":
                continue
            recency = self._recency_score(record, now)
            score = (self.config.w_relevance * rel
                     + self.config.w_importance * record.importance
                     + self.config.w_recency * recency)
            fused[record.rid] = (score, record)
        for record in self.kv.by_user(user_id):
            if record.rid in fused:
                continue
            recency = self._recency_score(record, now)
            score = (self.config.w_relevance * 0.4
                     + self.config.w_importance * record.importance
                     + self.config.w_recency * recency)
            fused[record.rid] = (score, record)
        ordered = sorted(fused.values(), key=lambda x: -x[0])
        return ordered[:top_k]

Industry practice
What's current (2024–2026)
  • Mem0 (Apache 2.0 library and managed platform) is widely used as a drop-in memory layer; its April 2026 algorithm changed the write path and retrieval and reports the benchmark figures above.
  • Zep builds a temporal knowledge graph (Graphiti) where facts carry validity intervals; LangMem and LangGraph's store, and Letta, cover the same need with different shapes.

  • On your laptop: the whole stack runs locally. bge-small-en-v1.5 or a similar small embedder on the CPU; Qdrant or pgvector in Docker for vectors; a 7B to 8B instruct model in 4-bit on the RTX 4060 for extraction, which a 0.5B model cannot do reliably, as the second lab shows.

Recap
What to keep from this lesson
  • Similarity, exact lookup and relationships need different stores.
  • Fused ranking only follows the query if relevance has enough spread.
  • An update must reach every store, not just the graph.
  • The write path (extract, then decide) is a model step; check it.
  • Never store facts the user did not state.

Given a target runtime, a vector backend (Qdrant, pgvector, Chroma, sqlite-vec), a KV backend (Postgres, Redis, dict), and a graph backend (Neo4j, in-memory edges), produce a fused memory system.

Produce:

1. Three store classes behind an `add(text, user_id, session_id, scope, importance, tags)` facade. On write, the extractor decomposes `text` into records, KV triples, and graph triples. No store is optional.
2. A fusion scorer `score = w_rel * relevance + w_imp * importance + w_rec * recency`. Expose all three weights as config. Tune per product, not per call.
3. Scope taxonomy: `user`, `session`, `agent`. Retrieval MUST respect scope. A user query must never leak another user's records.
4. Temporal invalidation. Contradictions mark old edges/records invalid; never delete. Expose `search(query, as_of=timestamp)` for historical queries.
5. An extractor interface. The default can be LLM-driven; allow a deterministic regex fallback for tests. Cap graph edges per `add()` to prevent explosion.

Hard rejects:

- Single-store memory described as "Mem0-shaped." Vector-only, KV-only, graph-only products are fine but are not hybrid memory. Do not misname them.
- Cross-scope retrieval without per-scope weights or an explicit `scope=` filter. Scope leak is a compliance and privacy incident.
- Deleting on contradiction. Invalidate and time-stamp. Deletion hides bugs and breaks audits.

Refusal rules:

- If the user asks for "no importance weighting," refuse. Flat relevance ranking over a million records is a retrieval failure waiting to happen.
- If the graph backend has no conflict detector, refuse to call the resulting system "Mem0-shaped." Downgrade the name.
- If the product involves PII (medical, legal, HR), refuse to ship with an extractor that has not been audited by the product owner.

Output: one file per store plus `memory.py` (facade), `config.py` (weights), `README.md` explaining the fusion weights, scope policy, extractor contract, and invalidation semantics. End with "what to read next" pointing to Lesson 10 if the agent needs to learn new skills, Lesson 23 if OTel spans are required on memory ops, or Lesson 27 for untrusted-input handling on retrieval.

Solutions

SolutionP1 · Two, then four

2 of 5 with the lesson's word overlap, 4 of 5 with embeddings. Embeddings fix both paraphrases and the lesson's "where does ava live", but lose "what is ava building", because the small embedding model scores "ava lives in Berlin" closer to that question than the curriculum note. Better retrieval is not uniformly better on every query, which is why retrieval changes need an evaluation set rather than a few spot checks.

SolutionB1 · Invented facts in long-term memory

Invented facts become "known" facts. Every later session retrieves them and the assistant tailors answers to a 25-year-old male software developer who may not exist: wrong recommendations, wrong tone, and, because one of the invented facts is a sensitive attribute (gender), a privacy problem if the memory is ever shown to the user or used for decisions. Noise such as "Thanks" also dilutes retrieval, and duplicates such as Berlin and Lisbon side by side make answers contradict each other.

Checks for the write path: require each extracted fact to be supported by a span of the message (reject anything not grounded in the text); use a strict output schema and drop items that fail it; block sensitive categories unless the user explicitly asks you to remember them; require a minimum length and a subject; log the source message and session with every write; and evaluate the extractor on labelled conversations before deploying it, with a capable model if the small one fails, as it does here.

Defend a designYou own the memory layer for three products on one platform: a consumer chat assistant, a compliance review agent and a research retrieval agent. The memory system runs a vector store, a key-value store and a graph store in parallel and fuses their results. How do you configure the fusion for each product, and which one scoping mistake would get you paged?

Level 4 of 4 · about 15 minutes to answer well.

Short answer. The fused score is a weighted sum of relevance, importance and recency, and the weights are tuned per product: recency up for the chat assistant, importance up for the compliance agent, relevance up for the retrieval agent. Each store wins a query class the others miss, so the weights steer which class dominates without dropping a store. The paging mistake is a scope leak: every write picks the user, the session or the agent scope, and a retrieval that mixes scopes without per-scope weights tells one user about another user's project.

Why three stores.

Query class Example Winner
Semantic similarity what did we discuss about drift last week vector
Fact lookup the user's phone number key-value, keyed on user, fact type and entity
Relationship reasoning which customers share a billing entity graph, as typed edges

A single store is wrong for two of the three classes. A write extracts facts from the text and writes each one to all three stores; a search runs all three and fuses.

The fusion.

The score is w_relevance * relevance + w_importance * importance + w_recency * recency. Relevance is the cosine, the exact key match or the graph path weight. Importance is tagged at write time or learned. Recency decays with time since the last write or read. It is a weighted sum and not a hierarchy, because a hierarchy would make two of the three classes wait on the wrong store.

Product Weight to raise Why
Chat assistant recency the last few turns matter most
Compliance agent importance names, ids and policies outrank chatter
Retrieval agent relevance the question decides, not the clock

Temporal truth for compliance.

When a new fact contradicts a graph edge, the old edge is marked invalid and never deleted. A question about what was true in March traverses the edges valid at that time. The compliance agent depends on this.

The scope rule.

Each write picks one scope: user memory persists across sessions, session memory lives in one thread, agent memory is per instance. Retrieval can read across scopes with per-scope weights, but a search that mixes them without thought is how an assistant tells one user about another user's project.

Maintenance that scales with the corpus.

  • Vector results drift as the corpus grows; re-embed the most used records on a schedule.
  • The key-value type set creeps as teams add types; audit it quarterly.
  • A noisy extractor adds dozens of edges per message; cap graph writes per add and drop low-confidence edges.

Plausible wrong answers.

  • "One vector store is enough, embeddings capture everything." A fact lookup is wasteful on a vector store and a relationship query is impossible on one.
  • "Set the weights once for the platform." Chat wants recency, compliance wants importance, retrieval wants relevance; one setting is wrong for two of the three.
  • "Delete the old fact when a new one contradicts it." Mark it invalid and keep it, or the temporal query loses its history.

Follow-ups an interviewer may ask.

  • (level 3) Which query class does each store win? Expected: vector for semantic similarity, key-value for a fact lookup, graph for relationship reasoning.
  • (level 4) Why a weighted sum and not vector first with fallbacks? Expected: each store wins a different class; a hierarchy makes two of three classes wait on the wrong store.
  • (level 4) The compliance agent asks what was true in March. Which store answers, and how? Expected: the graph, by traversing the edges valid at that time; contradicted edges are marked invalid and kept.
  • (level 4) Which failure grows with the corpus, and what is the maintenance? Expected: embedding drift in the vector store; re-embed the most used records periodically, audit the key-value type set quarterly, and cap graph writes per add.
