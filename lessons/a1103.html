In plain words first
The idea in one line

Your LLM returns a string. Your application needs JSON. That gap has crashed more production systems than any model hallucination. Structured output is the bridge between natural language and typed data. Get it right and your LLM becomes a reliable API. Get it wrong and you're parsing free-text with regex at 3am.

Terms you'll hear
Term What people say What it actually means
JSON mode "Returns JSON" API flag that guarantees syntactically valid JSON output, but does not enforce any particular schema
Structured output "Typed JSON" Output that matches a specific JSON Schema with correct keys, types, and constraints
Constrained decoding "Guided generation" At each token position, mask out tokens that would produce invalid output -- guarantees 100% schema compliance
JSON Schema "A JSON template" A declarative language for describing the structure, types, and constraints of JSON data (used by OpenAPI, JSON Forms, etc.)
Pydantic "Python dataclasses+" Python library that defines data models with type validation, used by FastAPI and Instructor to generate JSON Schemas
Function calling "Tool use" LLM outputs a structured function invocation (name + typed arguments) instead of free text -- OpenAI and Anthropic both support this
Instructor "Pydantic for LLMs" Python library that wraps LLM clients to return validated Pydantic instances, with automatic retry on validation failure
Token masking "Filtering the vocabulary" Setting specific token probabilities to zero during generation so the model cannot produce them
Schema compliance "Matches the shape" The output has every required field, correct types, values within constraints, and no extra disallowed fields
Retry loop "Try again until it works" Send validation errors back to the model and ask it to fix the output -- Instructor does this automatically, up to a configurable max

The problem

In plain words first

Programs need data with a fixed shape: these keys, these types, these allowed values. A language model writes text one token at a time, and nothing forces that text to be valid JSON, let alone the right JSON. There are three ways to close the gap: ask nicely in the prompt and check afterwards; let the API enforce a schema; or, underneath both, constrained decoding, which at every step blocks the tokens that would break the schema, so the model can only write valid output. This lesson builds a schema validator and a constrained-decoding simulator, then builds real constrained decoding from scratch on a 0.5B model and runs XGrammar, the engine inside vLLM and SGLang, on the same task. Valid shape is not correct content, and the runs show that too. No model is trained.

You ask an LLM: "Extract the product name, price, and availability from this text." It responds:

The product is the Sony WH-1000XM5 headphones, which cost $348.00 and are currently in stock.

That is a perfectly correct answer. It is also completely useless to your application. Your inventory system needs {"product": "Sony WH-1000XM5", "price": 348.00, "in_stock": true}. You need a JSON object with specific keys, specific types, and specific value constraints. You do not need a sentence.

The naive solution: add "Respond in JSON" to your prompt. This works 90% of the time. The other 10% the model wraps the JSON in markdown code fences, or adds a preamble like "Here's the JSON:", or produces syntactically invalid JSON because it closed a bracket early. Your JSON parser crashes. Your pipeline breaks. You add try/except and a retry loop. The retry sometimes produces different data. Now you have a consistency problem on top of a parsing problem.

This is not a prompt engineering problem. It is a decoding problem. The model generates tokens left to right. At each position, it picks the most likely next token from a vocabulary of 100K+ options. Most of those options would produce invalid JSON at any given position. If the model just emitted {"price":, the next token must be a digit, a quote (for string), null, true, false, or a negative sign. Anything else produces invalid JSON. Without constraints, the model might pick a perfectly reasonable English word that is catastrophically wrong syntactically.

Idea 1 · The Structured Output Spectrum

There are four levels of structured output control, each more reliable than the last.

Prompt-based ("Respond in valid JSON"): no enforcement. The model usually complies but sometimes does not. Reliability: ~90%. Failure mode: markdown fences, preamble text, truncated output, wrong structure.

JSON mode: the API guarantees the output is valid JSON. OpenAI's response_format: { type: "json_object" } enables this. The output will parse without errors. But it may not match your expected schema -- extra keys, wrong types, missing fields.

Schema mode: the API takes a JSON Schema and guarantees the output matches it. Every major provider supports this natively: OpenAI's structured outputs (response_format with type: "json_schema" and strict: true, or text.format in the Responses API, and strict: true on function definitions), Anthropic's structured outputs (output_config.format with type: "json_schema", and strict tool use), and Gemini's response_schema with response_mime_type: "application/json". The output has the exact keys and types you specified; each provider supports a documented subset of JSON Schema keywords, so check which constraints (string formats, minimum, maxItems) are enforced and which are only described.

Constrained decoding: at each token position during generation, the decoder masks out all tokens that would produce invalid output. If the schema requires a number and the model is about to emit a letter, that token is set to probability zero. The model can only produce tokens that lead to valid output. This is what hosted structured-output modes do under the hood, and what open engines implement: XGrammar (the default in vLLM and SGLang), llguidance (behind Guidance), and Outlines.

Idea 2 · JSON Schema: The Contract Language

JSON Schema is how you tell the model (or validation layer) what shape the output must have. Every major structured output system uses it.

{
  "type": "object",
  "properties": {
    "product": { "type": "string" },
    "price": { "type": "number", "minimum": 0 },
    "in_stock": { "type": "boolean" },
    "categories": {
      "type": "array",
      "items": { "type": "string" }
    }
  },
  "required": ["product", "price", "in_stock"]
}

This schema says: the output must be an object with a string product, a non-negative number price, a boolean in_stock, and an optional array of string categories. Any output that does not match gets rejected.

Schemas handle the hard cases: nested objects, arrays with typed items, enums (constrain a string to specific values), pattern matching (regex on strings), and combinators (oneOf, anyOf, allOf for polymorphic outputs).

Idea 3 · The Pydantic Pattern

In Python, you do not write JSON Schema by hand. You define a Pydantic model and it generates the schema for you.

from pydantic import BaseModel

class Product(BaseModel):
    product: str
    price: float
    in_stock: bool
    categories: list[str] = []

This produces the same JSON Schema as above. The Instructor library (and OpenAI's SDK) accept Pydantic models directly: pass the model class, get back a validated instance. If the LLM output does not match, Instructor retries automatically.

The same idea as a formula

At each step the model gives a distribution p(t∣x,y<i​) over the vocabulary V. A grammar (here, a JSON Schema compiled to an automaton) defines the set Ai​⊆V of tokens that keep the output a valid prefix. Constrained decoding samples from the renormalised, masked distribution

p~​(t∣x,y<i​)=∑u∈Ai​​p(u∣x,y<i​)p(t∣x,y<i​)1[t∈Ai​]​.
In practice the logits of disallowed tokens are set to −∞ before the softmax. Every finished output is in the language of the grammar; nothing guarantees the values are right.

Cost. The mask is a bitmask over ∣V∣ tokens, ∣V∣/8 bytes per step (19 KB for a 151,643-token vocabulary). Engines like XGrammar precompute which tokens are allowed in which grammar state, so only a few context-dependent tokens are checked at run time.

Worked example
A price field with a 151,936-entry vocabulary
  • After "price": the schema allows only tokens that can start a JSON number (digits, a minus sign), plus whitespace. In the run below that is 25 tokens of 151,936 (0.02%).
  • Suppose the model, reading "2,499 dollars", puts its highest score on the token "$": it is masked, so the best digit token wins instead.
  • After 2 the model wants , (as in 2,499). With a digits-only mask, as in the from-scratch run, the comma is masked and the next best digits 499 win: 2499, the right value.
  • A full JSON grammar is more permissive: a comma after a number is legal (it ends the number), so the value could become 2: valid, and wrong. In this lesson's runs both decoders wrote 2499, but "valid" never means "right"; say "no thousands separators" in the prompt, give an example, and check values with code.

Idea 4 · Function Calling / Tool Use

An alternative interface for the same problem. Instead of asking the model to produce JSON directly, you define "tools" (functions) with typed parameters. The model outputs a function call with structured arguments. OpenAI calls this "function calling." Anthropic calls it "tool use." The result is the same: structured data.

Tool use is preferred when the model needs to choose which function to call, not just fill in parameters. If you have 10 different extraction schemas and the model must pick the right one based on the input, tool use gives you both the schema selection and the structured output.

Idea 5 · Common Failure Modes

Even with schema enforcement, structured outputs can fail in subtle ways.

Hallucinated values: the output matches the schema but contains invented data. The model produces {"price": 299.99} when the text says $348. Schema validation cannot catch this -- the type is correct, the value is wrong.

Enum confusion: you constrain a field to ["in_stock", "out_of_stock", "preorder"]. The model outputs "available" -- semantically correct, but not in the allowed set. Good constrained decoding prevents this. Prompt-based approaches do not.

Nested object depth: deeply nested schemas (4+ levels) produce more errors. Each level of nesting is another place where the model can lose track of structure.

Array length: the model may produce too many or too few items in an array. Schemas support minItems and maxItems but not all providers enforce them at the decoding level.

Optional field omission: the model omits fields that are technically optional but semantically important for your use case. Set them as required in the schema even if the data is sometimes missing -- force the model to produce null explicitly.

Step 1 · JSON Schema Validator

Build a validator from scratch that checks whether a Python object matches a JSON Schema. This is what runs on the output side to verify compliance.

import json

def validate_schema(data, schema):
    errors = []
    _validate(data, schema, "", errors)
    return errors

def _validate(data, schema, path, errors):
    schema_type = schema.get("type")

    if schema_type == "object":
        if not isinstance(data, dict):
            errors.append(f"{path}: expected object, got {type(data).__name__}")
            return
        for key in schema.get("required", []):
            if key not in data:
                errors.append(f"{path}.{key}: required field missing")
        properties = schema.get("properties", {})
        for key, value in data.items():
            if key in properties:
                _validate(value, properties[key], f"{path}.{key}", errors)

    elif schema_type == "array":
        if not isinstance(data, list):
            errors.append(f"{path}: expected array, got {type(data).__name__}")
            return
        min_items = schema.get("minItems", 0)
        max_items = schema.get("maxItems", float("inf"))
        if len(data) < min_items:
            errors.append(f"{path}: array has {len(data)} items, minimum is {min_items}")
        if len(data) > max_items:
            errors.append(f"{path}: array has {len(data)} items, maximum is {max_items}")
        items_schema = schema.get("items", {})
        for i, item in enumerate(data):
            _validate(item, items_schema, f"{path}[{i}]", errors)

    elif schema_type == "string":
        if not isinstance(data, str):
            errors.append(f"{path}: expected string, got {type(data).__name__}")
            return
        enum_values = schema.get("enum")
        if enum_values and data not in enum_values:
            errors.append(f"{path}: '{data}' not in allowed values {enum_values}")

    elif schema_type == "number":
        if not isinstance(data, (int, float)):
            errors.append(f"{path}: expected number, got {type(data).__name__}")
            return
        minimum = schema.get("minimum")
        maximum = schema.get("maximum")
        if minimum is not None and data < minimum:
            errors.append(f"{path}: {data} is less than minimum {minimum}")
        if maximum is not None and data > maximum:
            errors.append(f"{path}: {data} is greater than maximum {maximum}")

    elif schema_type == "boolean":
        if not isinstance(data, bool):
            errors.append(f"{path}: expected boolean, got {type(data).__name__}")

    elif schema_type == "integer":
        if not isinstance(data, int) or isinstance(data, bool):
            errors.append(f"{path}: expected integer, got {type(data).__name__}")

Step 2 · Pydantic-Style Model to Schema

Build a minimal class-to-schema converter. Define a Python class and generate its JSON Schema automatically.

class SchemaField:
    def __init__(self, field_type, required=True, default=None, enum=None, minimum=None, maximum=None):
        self.field_type = field_type
        self.required = required
        self.default = default
        self.enum = enum
        self.minimum = minimum
        self.maximum = maximum

def python_type_to_schema(field):
    type_map = {
        str: "string",
        int: "integer",
        float: "number",
        bool: "boolean",
    }

    schema = {}

    if field.field_type in type_map:
        schema["type"] = type_map[field.field_type]
    elif field.field_type == list:
        schema["type"] = "array"
        schema["items"] = {"type": "string"}
    elif isinstance(field.field_type, dict):
        schema = field.field_type

    if field.enum:
        schema["enum"] = field.enum
    if field.minimum is not None:
        schema["minimum"] = field.minimum
    if field.maximum is not None:
        schema["maximum"] = field.maximum

    return schema

def model_to_schema(name, fields):
    properties = {}
    required = []

    for field_name, field in fields.items():
        properties[field_name] = python_type_to_schema(field)
        if field.required:
            required.append(field_name)

    return {
        "type": "object",
        "properties": properties,
        "required": required,
    }

Step 3 · Constrained Token Filter

Simulate constrained decoding. Given a partial JSON string and a schema, determine which token categories are valid at the current position.

def next_valid_tokens(partial_json, schema):
    stripped = partial_json.strip()

    if not stripped:
        return ["{"]

    try:
        json.loads(stripped)
        return ["<EOS>"]
    except json.JSONDecodeError:
        pass

    last_char = stripped[-1] if stripped else ""

    if last_char == "{":
        return ['"', "}"]
    elif last_char == '"':
        if stripped.endswith('":'):
            return ['"', "0-9", "true", "false", "null", "[", "{"]
        return ["a-z", '"']
    elif last_char == ":":
        return [" ", '"', "0-9", "true", "false", "null", "[", "{"]
    elif last_char == ",":
        return [" ", '"', "{", "["]
    elif last_char in "0123456789":
        return ["0-9", ".", ",", "}", "]"]
    elif last_char == "}":
        return [",", "}", "]", "<EOS>"]
    elif last_char == "]":
        return [",", "}", "<EOS>"]
    elif last_char == "[":
        return ['"', "0-9", "true", "false", "null", "{", "[", "]"]
    else:
        return ["any"]

def demonstrate_constrained_decoding():
    partial_states = [
        '',
        '{',
        '{"product"',
        '{"product":',
        '{"product": "Sony"',
        '{"product": "Sony",',
        '{"product": "Sony", "price":',
        '{"product": "Sony", "price": 348',
        '{"product": "Sony", "price": 348}',
    ]

    print(f"{'Partial JSON':<45} {'Valid Next Tokens'}")
    print("-" * 80)
    for state in partial_states:
        valid = next_valid_tokens(state, {})
        display = state if state else "(empty)"
        print(f"{display:<45} {valid}")

Constrained decoding from scratch, on a real model

The lesson's simulator, made real: Qwen2.5-0.5B-Instruct writes the JSON for six product texts, once freely with the schema in the prompt, and once with masks built from its own vocabulary (string tokens without quotes, digit-only tokens for the price, and whole-sequence scoring for the boolean and the enum). Both results are checked against the schema by code. About three minutes on CPU (the masks are rebuilt in Python at every step), so the output below was recorded.

import json, re, torch
from transformers import AutoTokenizer, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()
V = model.config.vocab_size                    # logits cover 151,936 ids; the tokenizer defines 151,665
SCHEMA = {"product": "string", "price": "number", "in_stock": "boolean", "condition": ["new", "used", "refurbished"]}
SYSTEM = ("Extract the product as JSON with exactly these keys: product (string), price (number, no currency sign), "
          "in_stock (true or false), condition (one of new, used, refurbished). Output the JSON only.")
TEXTS = ["Sony WH-1000XM5 headphones, $348, in stock, brand new.",
         "Refurbished MacBook Pro 16 for 2,499 dollars, currently sold out.",
         "Selling my used Kindle Paperwhite, 60 bucks, still have it.",
         "Open-box Dyson V15 vacuum (like new), $549.99, available now.",
         "Nintendo Switch OLED, three hundred and forty-nine dollars, back-ordered, new.",
         "Canon EOS R8 body, second-hand, priced at 1199 USD, ready to ship."]

def check(d):                                   # the schema, checked by hand: keys, types, enum
    if not isinstance(d, dict) or sorted(d) != sorted(SCHEMA): return "wrong keys"
    if not isinstance(d["product"], str): return "product not a string"
    if not isinstance(d["price"], (int, float)) or isinstance(d["price"], bool): return f"price {d['price']!r} not a number"
    if not isinstance(d["in_stock"], bool): return f"in_stock {d['in_stock']!r} not a boolean"
    if d["condition"] not in SCHEMA["condition"]: return f"condition {d['condition']!r} not allowed"
    return "valid"

def prompt_ids(text):
    msgs = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": text}]
    return tok(tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True), return_tensors="pt").input_ids

# token classes for the masks: decode every vocabulary entry once
pieces = [tok.decode([i]) if i < len(tok) else "" for i in range(V)]
DIGITS = torch.tensor([bool(re.fullmatch(r"[0-9.]+", p)) for p in pieces])
STRING = torch.tensor([('"' not in p and "\n" not in p and "\\" not in p and len(p) > 0) for p in pieces])
QUOTE = tok.encode('"')[0]
COMMA = tok.encode(",")[0]

def logits_after(text_ids):
    with torch.no_grad():
        return model(text_ids).logits[0, -1]
def push(ids, s):
    return torch.cat([ids, torch.tensor([tok.encode(s)])], 1)

def constrained(text):
    ids, out = push(prompt_ids(text), '{"product": "'), {}
    # string: any token without a quote, newline or backslash, or the closing quote
    s = ""
    for _ in range(24):
        lg = logits_after(ids); mask = STRING.clone(); mask[QUOTE] = True
        t = int(torch.where(mask, lg, torch.tensor(-1e9)).argmax())
        ids = torch.cat([ids, torch.tensor([[t]])], 1)
        if t == QUOTE: break
        s += pieces[t]
    out["product"] = s
    ids = push(ids, ', "price": ')
    # number: digit tokens only, or a comma that ends the number
    s = ""
    for _ in range(8):
        lg = logits_after(ids); mask = DIGITS.clone(); mask[COMMA] = len(s) > 0
        t = int(torch.where(mask, lg, torch.tensor(-1e9)).argmax())
        if t == COMMA: break
        ids = torch.cat([ids, torch.tensor([[t]])], 1); s += pieces[t]
    out["price"] = float(s)
    ids = push(ids, ', "in_stock": ')
    # boolean and enum: score each allowed continuation by its total log-probability
    def pick(options):
        best = None
        for o in options:
            o_ids = torch.tensor([tok.encode(o)]); full = torch.cat([ids, o_ids], 1)
            with torch.no_grad(): lp = torch.log_softmax(model(full).logits[0, ids.shape[1] - 1:-1], -1)
            score = float(lp.gather(1, o_ids[0][:, None]).sum())
            if best is None or score > best[0]: best = (score, o)
        return best[1]
    out["in_stock"] = pick(["true", "false"]) == "true"
    ids = push(ids, ("true" if out["in_stock"] else "false") + ', "condition": ')
    out["condition"] = pick([f'"{c}"' for c in SCHEMA["condition"]]).strip('"')
    return out

def free(text):
    ids = prompt_ids(text)
    with torch.no_grad():
        g = model.generate(ids, max_new_tokens=60, do_sample=False)
    return tok.decode(g[0, ids.shape[1]:], skip_special_tokens=True).strip()

print(f"Vocabulary {V:,} tokens. Allowed inside a string: {int(STRING.sum()):,}; inside a number: {int(DIGITS.sum()):,} "
      f"({DIGITS.float().mean():.2%}); for a boolean or an enum: 2 or 3 whole continuations.\n")
ok_free = ok_con = 0
for t in TEXTS:
    raw = free(t)
    try: verdict = check(json.loads(raw))
    except json.JSONDecodeError: verdict = "not JSON"
    ok_free += verdict == "valid"
    c = constrained(t); vc = check(json.loads(json.dumps(c))); ok_con += vc == "valid"
    print(t)
    print(f"  free:        {raw.replace(chr(10), ' ')[:110]}  -> {verdict}")
    print(f"  constrained: {json.dumps(c)}  -> {vc}")
print(f"\nschema-valid: free {ok_free}/{len(TEXTS)}, constrained {ok_con}/{len(TEXTS)}")

Reading this output

The masks are drastic. Inside a string almost anything is allowed: 148,261 of 151,936 vocabulary entries (everything except tokens containing a quote and a few control tokens). Inside a number, only 25 entries are allowed, 0.02% of the vocabulary. For the boolean and the enum the decoder scores the 2 or 3 complete continuations and picks the most likely, so an invalid value is impossible.

Free generation was nearly valid already. With the schema in the prompt, 5 of 6 answers passed the schema check. The failure is typical: "second-hand" for a field that allows only new, used or refurbished. The constrained run mapped the same text to "used", which is valid and right. That is the guarantee constrained decoding gives: 6 of 6 valid.

Valid is not the same as right, in both directions. Free generation said in_stock: true for the MacBook that is "currently sold out", and for the back-ordered Nintendo. The constrained run, forced to compare true against false as whole options, got both right. But the constrained run also produced the worst answers in the table. Its product strings swallow the rest of the sentence ("…, $348, in stock, brand new. price:") because nothing in a string mask says where a product name ends. The Kindle came out at price: 100.0, condition: "new", when the text says 60 and used. The mask removed every invalid token, and with them the model's usual way of closing the string. What remained was a valid object with wrong content.

This is why production libraries do more than mask. They compile the whole schema into a grammar, so the end of a string is a legal, likely continuation, and they rely on models trained to produce structured output. The next run uses one.

Step 4 · Extraction Pipeline

Combine everything into an extraction pipeline: define a schema, simulate an LLM producing structured output, validate the output, and handle retries.

def simulate_llm_extraction(text, schema, attempt=0):
    if "headphones" in text.lower() or "sony" in text.lower():
        if attempt == 0:
            return '{"product": "Sony WH-1000XM5", "price": 348.00, "in_stock": true, "categories": ["audio", "headphones"]}'
        return '{"product": "Sony WH-1000XM5", "price": 348.00, "in_stock": true}'

    if "laptop" in text.lower():
        return '{"product": "MacBook Pro 16", "price": 2499.00, "in_stock": false, "categories": ["computers"]}'

    return '{"product": "Unknown", "price": 0, "in_stock": false}'

def extract_with_retry(text, schema, max_retries=3):
    for attempt in range(max_retries):
        raw = simulate_llm_extraction(text, schema, attempt)

        try:
            data = json.loads(raw)
        except json.JSONDecodeError as e:
            print(f"  Attempt {attempt + 1}: JSON parse error -- {e}")
            continue

        errors = validate_schema(data, schema)
        if not errors:
            return data

        print(f"  Attempt {attempt + 1}: Schema validation errors -- {errors}")

    return None

product_schema = {
    "type": "object",
    "properties": {
        "product": {"type": "string"},
        "price": {"type": "number", "minimum": 0},
        "in_stock": {"type": "boolean"},
        "categories": {"type": "array", "items": {"type": "string"}},
    },
    "required": ["product", "price", "in_stock"],
}

XGrammar with a Pydantic schema

The production route on the same model: a Pydantic model (with an enum, a minimum and a list of at most three categories) becomes a JSON schema, XGrammar compiles it into a token-level grammar, and Hugging Face generate uses it as a logits processor. Four texts with and without the grammar, validated by Pydantic, then the number of allowed tokens at points inside one answer. About a minute.

import json, time, torch, xgrammar as xgr
from typing import Literal
from pydantic import BaseModel, Field, ValidationError
from transformers import AutoTokenizer, AutoModelForCausalLM, AutoConfig
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

class Product(BaseModel):                     # the contract, written once as a Pydantic model
    product: str
    price: float = Field(ge=0)
    in_stock: bool
    condition: Literal["new", "used", "refurbished"]
    categories: list[str] = Field(max_length=3)

schema = json.dumps(Product.model_json_schema())
info = xgr.TokenizerInfo.from_huggingface(tok, vocab_size=AutoConfig.from_pretrained(name).vocab_size)
t0 = time.time()
compiled = xgr.GrammarCompiler(info).compile_json_schema(schema)
print(f"Pydantic schema -> grammar compiled in {time.time() - t0:.2f} s; vocabulary {info.vocab_size:,} tokens")

TEXTS = ["Sony WH-1000XM5 headphones, $348, in stock, brand new.",
         "Refurbished MacBook Pro 16 for 2,499 dollars, currently sold out.",
         "Open-box Dyson V15 vacuum (like new), $549.99, available now.",
         "Canon EOS R8 body, second-hand, priced at 1199 USD, ready to ship."]
SYSTEM = "Extract the product from the text as JSON matching this schema: " + schema

def run(text, constrained):
    msgs = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": text}]
    ids = tok(tok.apply_chat_template(msgs, tokenize=False, add_generation_prompt=True), return_tensors="pt").input_ids
    kw = {}
    if constrained:
        kw["logits_processor"] = [xgr.contrib.hf.LogitsProcessor(compiled)]
    t = time.time()
    with torch.no_grad():
        g = model.generate(ids, max_new_tokens=120, do_sample=False, **kw)
    n = g.shape[1] - ids.shape[1]
    return tok.decode(g[0, ids.shape[1]:], skip_special_tokens=True).strip(), n, time.time() - t

for constrained in (False, True):
    valid, tps = 0, []
    print("\nwith the grammar" if constrained else "\nwithout the grammar (schema in the prompt only)")
    for text in TEXTS:
        out, n, dt = run(text, constrained); tps.append(n / dt)
        try:
            p = Product.model_validate_json(out); valid += 1; verdict = "valid: " + p.model_dump_json()
        except ValidationError as e:
            err = e.errors()[0]
            verdict = f"invalid: {'.'.join(map(str, err['loc'])) or 'json'}: {err['type']} ({e.error_count()} error(s))"
        print("  " + verdict)
    print(f"  -> {valid}/{len(TEXTS)} pass Pydantic validation | {sum(tps) / len(tps):.1f} tokens/s")

    xgr.apply_token_bitmask_inplace(logits, bitmask)
    n = int(torch.isfinite(logits).sum())
    print(f"  after {p[-34:]!r:38} {n:>7,} of {info.vocab_size:,}" + ("" if accepted else "  (prefix rejected)"))

Reading this output

Without the grammar, 0 of 4 pass. The schema was in the prompt, and the model still wrote categories as a string instead of a list three times, and an invalid condition once. Pydantic catches each one, so in production these would mean retries.

With the grammar, 4 of 4 pass, and the content is cleaner than the from-scratch run. Product names end where they should ("MacBook Pro", "Canon EOS R8 body"), because the grammar knows a string can close after any character and the model's normal closing quote stays available. Prices are numbers, condition is one of the three values, and categories is a short list.

Still valid, still wrong. The MacBook comes out "in_stock": true although the text says sold out. No grammar can check meaning. Validate values against the source where you can, and evaluate extraction accuracy separately from schema validity.

Speed and the size of the mask. At the start only 7 tokens are allowed (an opening brace with optional whitespace). Inside the product string, 147,137 are allowed. In the number and the boolean, a few hundred: the grammar also allows whitespace and the tokens that continue or close the value. On this CPU the grammar run was slower (5.5 against 8.6 tokens per second) because the mask is applied in Python at every step. Inference servers such as vLLM and SGLang compute the mask in optimised native code while the GPU runs the forward pass, so the overhead there is small.

Break it on purpose

Make condition required but leave the text silent about it ("Kindle Paperwhite, $60, in stock"). With constrained decoding the model must still pick one of the three values. What should the schema look like so that "the text does not say" is possible? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Native strict schemas everywhere: OpenAI structured outputs and strict function calling, Anthropic structured outputs and strict tool use, Gemini response_schema. Each enforces a documented subset of JSON Schema.
  • Grammar engines in open serving: vLLM and SGLang use XGrammar by default, with llguidance and Outlines as alternatives; the mask costs little enough to leave on for every request.
  • Pydantic as the contract: SDK helpers (responses.parse, messages.parse) and Instructor turn Pydantic models into schemas and parse the result back.
  • Validation stays: refusals, truncation and wrong values still happen; teams log schema-valid but semantically wrong outputs as their own error class.

Recap
What to keep from this lesson
  • Prompting for JSON gives mostly-valid JSON; production needs a guarantee and a check.
  • Schema mode enforces keys, types and enums; JSON mode only parseability.
  • Constrained decoding masks disallowed tokens at every step; engines precompute the masks.
  • Valid shape is not correct content: validate values, handle refusals and truncation.
  • Design schemas for missing data: nullable fields or an explicit "unknown".

You are a structured data extraction engine. I will provide a JSON Schema and unstructured text. You will extract data that conforms exactly to the schema.

## Extraction Protocol

### 1. Schema Analysis

Before extracting, analyze the schema:

- Identify all required fields and their types
- Note enum constraints, minimum/maximum values, and format requirements
- Identify nested objects and array structures
- Flag fields that may be ambiguous or hard to extract from natural text

### 2. Extraction Rules

**Required fields**: must always be present in the output. If the information is not in the text, use the most reasonable default:
- Strings: use "unknown" or "not specified"
- Numbers: use 0 or null (if the schema allows nullable)
- Booleans: use false as the conservative default
- Arrays: use an empty array []

**Type enforcement**: every value must match the schema type exactly:
- "price" with type "number": extract 348.00, not "$348" or "three hundred"
- "in_stock" with type "boolean": extract true/false, not "yes"/"available"
- "categories" with type "array": extract ["audio", "headphones"], not "audio, headphones"

**Enum fields**: the value must be one of the allowed values. If the text uses a synonym, map it to the closest allowed value.

**Nested objects**: extract each level of nesting separately. Validate inner objects against their sub-schemas.

### 3. Confidence Annotation

For each extracted field, internally assess confidence:
- **High**: the information is explicitly stated in the text
- **Medium**: the information is implied or requires minor inference
- **Low**: the information is guessed based on context or defaults

If more than 2 fields are low confidence, note this in a separate `_extraction_notes` field (only if the schema does not prohibit additional properties).

### 4. Output Format

Return ONLY the JSON object. No markdown fences. No preamble. No explanation. The output must be directly parseable by `JSON.parse()` or `json.loads()`.

## Input Format

**Schema:**
```json
{schema}
```

**Text to extract from:**
```
{text}
```

## Output

A single JSON object matching the schema exactly.

# Structured Output Strategy

When building an LLM application that requires structured data, apply this decision framework.

## When to use each approach

**Prompt-based ("Return JSON"):** Prototyping only. Acceptable for internal tools where occasional parse failures are tolerable. Add a try/except with retry. Never use in production pipelines.

**JSON mode (API flag):** You need guaranteed valid JSON but the schema is simple or flexible. Works when you validate the shape on the application side. Available: OpenAI, Anthropic (via tool use), Google.

**Schema mode (constrained decoding):** Production systems where every output must match a specific schema. Zero parse failures. Zero schema violations. Use this by default for any production extraction or classification task. Available: OpenAI structured outputs, Outlines, Guidance.

**Function calling / tool use:** The model needs to choose which function to call, not just fill parameters. You have multiple schemas and the model selects the appropriate one. Also use when integrating with existing tool/function infrastructure.

**Instructor library:** You want Pydantic validation with automatic retry across any provider. Best DX for Python projects. Wraps OpenAI, Anthropic, Google, and open-source models.

## Provider-specific guidance

**OpenAI:** Use `response_format` with `json_schema` type. Constrained decoding is built in. Pydantic models work directly. Most reliable structured output implementation.

**Anthropic:** Use tool use for structured output. Define a single tool with the desired schema. The model returns tool call arguments matching the schema. Reliable but requires the tool use API pattern.

**Open-source models (vLLM, Ollama):** Use Outlines or Guidance for constrained decoding. These libraries compile JSON Schemas into finite state machines that mask invalid tokens during generation. Requires running inference locally.

## Schema design guidelines

1. Keep schemas flat when possible. Nested objects beyond 2 levels increase extraction errors.
2. Use enums for categorical fields. Do not rely on the model inventing the right string.
3. Make ambiguous fields required with explicit null support rather than optional. Forces the model to make a decision.
4. Add descriptions to schema properties. The model reads these as instructions.
5. Avoid union types (oneOf/anyOf) unless necessary. They increase decoding complexity.
6. Set minimum/maximum on numbers. Catches hallucinated extreme values.
7. Use minItems/maxItems on arrays to prevent empty or unbounded outputs.

## Common failure patterns and fixes

- **Model wraps JSON in markdown fences**: switch from prompt-based to JSON mode or schema mode
- **Schema-valid but factually wrong**: add an LLM-as-judge validation step after extraction
- **Inconsistent enum values**: switch to constrained decoding or add post-processing normalization
- **Missing optional fields**: make them required or add default values in application code
- **Very slow extraction**: constrained decoding adds 5-15% latency, reduce schema complexity if latency-sensitive
- **Large arrays with varied items**: chunk the input and extract per-chunk, then merge results

## Reliability ladder

| Approach | Parse Success | Schema Match | Setup Effort |
|----------|-------------|-------------|-------------|
| Prompt-based | ~90% | ~80% | 1 minute |
| JSON mode | 100% | ~90% | 5 minutes |
| Schema mode | 100% | ~99% | 15 minutes |
| Constrained decoding | 100% | 100% | 30 minutes |
| Instructor + retry | 100% | ~99.5% | 10 minutes |

  2. Build a "schema diff" tool that compares two schemas and identifies breaking changes (removed required fields, changed types) versus non-breaking changes (added optional fields, relaxed constraints). This is essential for versioning your extraction schemas in production.

Solutions

SolutionP1 · 2499, but read the product field

2499.0, the right number. The digits-only mask removed the comma the model wanted after "2", and the next best digits were "499". The same field shows what a mask cannot do, though. The constrained product value for that text is "Refurbished MacBook Pro 16 for 2,499 dollars, currently sold out. Condition: refurbished": the whole sentence. Nothing in a string mask marks the end of a product name. And in the XGrammar run on the same model, the MacBook is valid but "in_stock": true although it is sold out. Constrained decoding guarantees the shape of the answer, not its truth.

SolutionB1 · Give the model a way to say "unknown"

If condition is required and must be one of new, used or refurbished, constrained decoding forces a choice even when the text never says. The model picks the likeliest option, usually "new", and the answer is valid, confident and invented. The from-scratch run shows how readily the forced choice goes wrong: for a Kindle the text calls "used", the constrained decoder wrote "new". Make "not stated" representable. Either make the field optional and nullable (condition: Literal["new", "used", "refurbished"] | None = None), or add an explicit value such as "unknown". Then tell the model in the prompt to use it when the text is silent, and test that path with examples like this one.

Debug a failureA classifier uses constrained decoding with a schema of two fields, answer and reasoning, in that order. The output is always valid JSON and the accuracy is worse than the free-text version was. What is wrong?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The field order. The model commits to the answer before it writes any reasoning, so the reasoning tokens never shape the answer, and you lose the gain that step-by-step gives. Put reasoning first and answer last; the schema stays valid, and no validator will ever flag the difference, because the order is logic and not formatting.

The pitfall.

The constrained decoding lesson calls it the pitfall that costs you. With answer first, the model writes the decision token at the first position where the grammar allows it, and the reasoning that follows is a story about a choice already made. With reasoning first, the chain comes before the decision, and the decision token is conditioned on it. Both documents validate. Only one is right.

The lesson's skill refuses any design that puts an answer or decision field before the reasoning fields.

Neighbors of the same mistake.

Schema choice What goes wrong Fix
A strict pattern for a value that can be missing, such as a date the model invents a value to satisfy the grammar allow null or a sentinel
A field left optional that matters the model omits it when it is inconvenient make it required and allow null, so the absence is explicit
Nesting four levels deep or more each level is one more place to lose the structure flatten
An enum with thousands of options the grammar compiles slowly or times out predict a short list of candidates first, then constrain to it

Why the unconstrained reply did better.

A free-text reply tends to explain before it concludes, so it had the chain by accident. The constrained schema removed it. The fix restores it on purpose.

Plausible wrong answers.

  • "Constrained decoding guarantees a correct output." It guarantees the shape; the lesson shows valid JSON with a wrong answer.
  • "Order does not matter in JSON." It does not matter to the parser; it matters to the model, which writes the fields in order.
  • "Add a check that the reasoning supports the answer." That is an eval, not a fix; the fix is to generate the reasoning first.

Follow-ups an interviewer may ask.

  • (level 2) Why can no validator catch this? Expected: both orders are valid against the schema; the harm is in what the model has seen when it writes the answer token.
  • (level 2) The schema forces a date pattern and the model fills in dates that are not in the text. Which related mistake is that? Expected: a grammar too strict for missing data; allow null or a sentinel so the model does not invent a value.
  • (level 3) A field is optional and the model leaves it out when it matters. What do you change? Expected: make it required and allow null, so the model has to state that the value is missing.
  • (level 3) The schema nests four levels deep and errors rise. What do you do? Expected: flatten, because each level of nesting is one more place to lose track of the structure.

Where it is taught. The lesson constrained decoding names the field order pitfall and the strict grammar pitfall, and the lesson structured outputs covers nesting depth and optional fields.

Explain the mechanismA teammate turned on the provider's JSON mode and says the extraction output is now guaranteed. What does JSON mode guarantee, what does it not, and what do you turn on instead?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. JSON mode guarantees that a finished output parses, nothing more; a response cut at the token limit can still fail, so check the finish reason first. It does not guarantee your keys, your types, your enum values or the absence of extra fields. Turn on the schema mode, where the provider takes a JSON Schema and constrains decoding to it, and keep a check on your side for the values that a schema cannot judge.

Four levels of control.

Level Guarantee Typical failure
A prompt that says "respond in JSON" none; about 90 percent valid code fences, preamble text, truncation, wrong structure
JSON mode valid syntax extra keys, wrong types, missing fields
Schema mode the output conforms to your schema a wrong value with the right type, or a refusal
Constrained decoding every token is valid for the schema the same as schema mode; this is how schema mode is built

The constrained decoding lesson is blunt about it: pure JSON mode guarantees valid JSON, not JSON that is valid for your use case, so always provide a full schema.

What strict schema mode asks of you.

The structured output lesson lists the strict mode rules: every property appears in required, additionalProperties is false everywhere, and there is no unresolved reference. A schema that breaks these is rejected at request time with a 400.

What stays with you.

Under strict enforcement two failures disappear for a response that finishes, the parse error and the schema violation. A response cut at the token limit can still fail to parse, so check the finish reason before you read it. Two more remain. The model can refuse when the input does not fit the schema, which your code treats as a typed outcome. And the model can fill a field with a value that has the right type and the wrong content; no format layer sees that.

Plausible wrong answers.

  • "JSON mode means the keys match my model." It only guarantees syntax; extra keys, wrong types and missing fields still happen.
  • "Adding 'respond in valid JSON' to the prompt is the same thing." A prompt-only approach is about 90 percent reliable and fails with fences, preambles and truncation.
  • "With schema mode I can drop validation." A schema cannot catch a wrong value with the right type; keep a semantic check.

Follow-ups an interviewer may ask.

  • (level 1) Which failure remains under strict schema mode? Expected: a refusal, when the model decides the input does not fit the schema; handle it as a typed outcome, and route a response cut at the token limit to the error path.
  • (level 2) What does strict mode demand of the schema? Expected: every property required, additional properties forbidden, no unresolved references; otherwise the request is rejected with a 400.
  • (level 2) The output matches the schema and the price is wrong. Which layer failed? Expected: none of the format layers; the value is invented, and only a semantic check or an eval catches that.
  • (level 3) A field is sometimes unknown in the source text. How do you write the schema? Expected: allow null or a sentinel; a grammar that forces a value makes the model invent one, such as a date.

Where it is taught. The lesson structured outputs lays out the four levels, the lesson constrained decoding warns against JSON mode without a schema, and the lesson structured output gives the strict mode rules.

Debug a failureAn extraction pipeline with strict schema enforcement has reported zero validation errors for a month. A finance review finds that a share of the extracted invoice totals do not match the source documents, and that a status field often holds a value that is allowed by the enum and wrong for the document. The engineers say the schema guarantees correctness. What do you tell them, and what do you build?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Schema enforcement guarantees shape, not truth. A total with the right type and the wrong number passes every format check, and an enum member can be allowed and still be the wrong one. Build a semantic eval: a labeled set of documents with gold records, exact match and field-level accuracy per field, plus a confidence signal from repeated extraction or token probabilities that sends low-confidence fields to human review.

The failures a schema cannot see.

The structured outputs lesson lists them even with enforcement on:

Failure Example Why the schema passes it
Invented value the text says one amount and the record holds another right type, wrong content
Enum confusion the model picks an allowed member that does not fit the document the member is in the set
Array length too many or too few line items not every provider enforces the item bounds at decode time
Optional omission a field left out when it was inconvenient optional means allowed to be absent

The constrained decoding lesson adds two causes that make the values worse: a grammar too strict for missing data, which pushes the model to invent, and a decision field placed before the reasoning.

What to build.

  1. A labeled set. The lesson's exercise uses 50 documents with hand-labeled records. Label real invoices, including the hard cases.
  2. Field-level metrics. Exact match on the record, accuracy per field, and type compliance as a sanity row that should sit near 100 percent.
  3. A confidence per field. Run the extraction three times and measure agreement, or read the token probabilities, and flag the fields that disagree.
  4. A review queue. Low-confidence records go to a human before they reach accounting.
  5. Schema repairs. Put a reasoning field ahead of the status, give enum members descriptions that make their meaning explicit, and add a null or an "other" member if the source has cases that none of the members fit.

Why size does not fix it.

The structured output lesson notes that grammar enforcement lets a small model beat a much larger one on structured tasks, because the format is decoupled from the model size. The values are not. Only a labeled eval tells you how often they are right.

Plausible wrong answers.

  • "Zero validation errors means zero extraction errors." Validation checks shape; the review found value errors that no shape check can see.
  • "Switch to a bigger model and the values will be right." Size changes the error rate, not the blind spot; without a labeled eval you cannot tell by how much.
  • "Add a tighter pattern to the total field." A tighter grammar does not make the number true; a grammar too strict even pushes the model to invent one.

Follow-ups an interviewer may ask.

  • (level 3) Which failure can a schema never see? Expected: a value with the right type and the wrong content, such as a total copied from the wrong line.
  • (level 3) How do you get a confidence per field without a new model? Expected: run the extraction three times and measure agreement, or read token probabilities, and flag fields that disagree for review.
  • (level 4) The status enum has a member the model keeps picking wrongly. What are the candidate fixes? Expected: describe the members so their meaning is explicit, put a reasoning field before the status, and check whether the source has cases no member fits, which calls for a null or an "other" member.
  • (level 4) What does the finished eval report look like? Expected: schema compliance near 100 percent as a sanity row, then exact match and field-level accuracy per field on the labeled set, with the hardest fields named.

Check your understanding

Q1Why is getting structured JSON output from LLMs challenging?

LLMs generate tokens autoregressively. They might add a trailing comma, forget a closing bracket, include markdown formatting around JSON, or hallucinate extra fields. Each token is independent, so structural validity isn't guaranteed.

Q2What is constrained decoding?

Constrained decoding masks out invalid tokens at each generation step. After an opening brace, only valid JSON keys are allowed. After a colon, only valid value tokens. This guarantees structural validity at the token level.

Q3What is the benefit of using Pydantic models for LLM output validation?

Pydantic enforces types, required fields, value constraints, and nested structures. When the LLM produces invalid output, Pydantic gives specific error messages that can be fed back to the model for self-correction.

Q4What should you do when the LLM returns invalid JSON despite instructions?

A retry loop with error feedback works well: parse the output, catch validation errors, send the error message back as context ('Your output had this error: ... Please fix it'). Most models self-correct on the second attempt.

Q5When should you use the API's native JSON mode vs prompt-based JSON extraction?

Native JSON mode (OpenAI's response_format, Anthropic's tool_use) guarantees valid JSON structure. Prompt-based extraction is more flexible for complex reasoning about which fields to populate. Use native mode when structure matters most.
