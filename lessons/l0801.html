Why this came about

As agents spread, every team wrote its own integration for every system, and nothing was reusable across applications. In November 2024 Anthropic published the Model Context Protocol, a standard way to expose tools and data to any AI application. It was quickly adopted across the industry, including by OpenAI, Google and Microsoft in 2025.

In plain words first
A universal plug for tools

Every agent needs tools, and every team used to write its own connector for every system. The Model Context Protocol (MCP) is a standard plug: a system publishes its tools (and data and prompt templates) once, as an MCP server, and any MCP-capable agent or app, the client, can list them and call them. A tool on an MCP server is described exactly like a local tool: a name, a description and a JSON Schema of its arguments.

What MCP is, precisely

The Model Context Protocol (MCP) is an open standard for connecting AI applications to tools and data. Anthropic introduced it in November 2024; in December 2025 it was donated to the Linux Foundation's Agentic AI Foundation, and it is now supported by every major model provider, framework and cloud.

Three roles:

Role What it is Examples
Host The AI application the user works in Claude Desktop and Claude Code, ChatGPT, VS Code and Copilot, Cursor, your own agent
Client The connector inside the host, one per server Created by the host or your framework
Server A program that exposes capabilities GitHub, Slack, a database, your order system

What a server can offer:

Server feature Controlled by Purpose
Tools The model Actions and lookups the model can call
Resources The application Read-only data (files, records, documents) the app can attach to context
Prompts The user Reusable prompt templates, often shown as slash commands

What a client can offer servers: elicitation (the server asks the user for input mid-call), and, in older versions, sampling (the server borrows the host's model) and roots (which folders it may touch). Sampling, roots and protocol-level logging are deprecated as of the 2026-07-28 specification.

Transports: stdio (the host starts the server as a local process) and Streamable HTTP (a remote server over HTTP). The older HTTP+SSE transport is deprecated.

Step 1 · Build a server

FastMCP is the most popular Python framework for MCP servers; the official Python SDK (mcp) includes a similar high-level API.

uv add fastmcp uvicorn        # tested with fastmcp 4.1.4 and mcp 2.3.0

import asyncio
from fastmcp import FastMCP, Client

mcp = FastMCP("shopkart-orders", instructions="Order lookups and cancellations for ShopKart support.")
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@mcp.tool(annotations={"readOnlyHint": True})           # hints for clients: this tool changes nothing
def get_order_status(order_id: str) -> dict:
    """Return the shipping status for an order ID like 'A-1001'."""
    return {"order_id": order_id, "status": ORDERS.get(order_id, "not found")}   # a dict becomes structured output

@mcp.tool(annotations={"destructiveHint": True, "idempotentHint": True})
def cancel_order(order_id: str) -> str:
    """Cancel an order that has not shipped yet."""
    if ORDERS.get(order_id) == "shipped":
        raise ValueError(f"{order_id} has shipped and cannot be cancelled")
    ORDERS[order_id] = "cancelled"
    return f"{order_id} cancelled"

@mcp.resource("policy://refunds")                        # read-only data, addressed by a URI
def refund_policy() -> str:
    """ShopKart's refund policy."""
    return "Damaged items are refundable within 30 days of delivery."

@mcp.prompt                                               # a reusable template the user can pick
def apology(customer: str, issue: str) -> str:
    """A prompt template for apologizing to a customer."""
    return f"Write a short, sincere apology to {customer} about: {issue}. Offer one concrete next step."

async def try_it():
    async with Client(mcp) as client:                     # in-memory transport: ideal for unit tests
        tools = await client.list_tools()
        print([(t.name, t.annotations.read_only_hint if t.annotations else None) for t in tools])
        r = await client.call_tool("get_order_status", {"order_id": "A-1001"})
        print(r.structured_content)
        try:
            await client.call_tool("cancel_order", {"order_id": "A-1001"})
        except Exception as e:
            print("error:", e)
        print((await client.read_resource("policy://refunds"))[0].text)
        p = await client.get_prompt("apology", {"customer": "Ravi", "issue": "late delivery"})
        print(p.messages[0].content.text[:60])

asyncio.run(try_it())
What you should see
[('get_order_status', True), ('cancel_order', None)]

The server also prints the exception with a traceback on its side; the client only receives the message. cancel_order shows None for read-only because it set other hints. Tool annotations are hints from the server, not guarantees: a client must never trust a third-party server's "read-only" claim for security decisions.

Under the hood: MCP is lines of JSON

Client(mcp) hid the conversation between client and server. It is worth seeing once, because it removes the mystery: an MCP client and server exchange small JSON messages, in a format called JSON-RPC 2.0. There are three kinds.

Message Looks like Meaning
Request {"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": {...}} "Do this and answer me." The id is a number the sender chooses.
Response {"jsonrpc": "2.0", "id": 3, "result": {...}} or "error": {...} The answer to the request with the same id
Notification {"jsonrpc": "2.0", "method": "notifications/initialized"} "For your information." It has no id, so no answer is expected.

To watch real messages, put a one-tool server in its own file. With no arguments, mcp.run() uses the stdio transport: the server reads messages from its standard input and writes replies to its standard output, one JSON object per line.

# save as: orders_stdio.py
from fastmcp import FastMCP

mcp = FastMCP("shopkart-orders")
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@mcp.tool
def get_order_status(order_id: str) -> dict:
    """Return the shipping status for an order ID like 'A-1001'."""
    return {"order_id": order_id, "status": ORDERS.get(order_id, "not found")}

if __name__ == "__main__":
    mcp.run(show_banner=False)                    # stdio is the default transport: read stdin, write stdout

Now play the client by hand. The code starts the server as a child process, as a host application does, and then writes requests to it and reads the replies, with no MCP library on the client side.

import json, subprocess, sys

server = subprocess.Popen([sys.executable, "orders_stdio.py"], text=True,        # start the server as a child process
                          stdin=subprocess.PIPE, stdout=subprocess.PIPE, stderr=subprocess.DEVNULL)

def send(message: dict):
    server.stdin.write(json.dumps(message) + "\n")             # one JSON object per line
    server.stdin.flush()

def ask(id_: int, method: str, params: dict | None = None) -> dict:
    send({"jsonrpc": "2.0", "id": id_, "method": method, "params": params or {}})
    return json.loads(server.stdout.readline())                # the reply carries the same id

# 1. Handshake: agree on a protocol version and learn what the server offers.
reply = ask(1, "initialize", {"protocolVersion": "2025-11-25", "capabilities": {},
                              "clientInfo": {"name": "by-hand", "version": "0.1"}})
print("1 initialize ->", reply["result"]["serverInfo"]["name"], "| offers:", sorted(reply["result"]["capabilities"]))
send({"jsonrpc": "2.0", "method": "notifications/initialized"})    # no id: a notification expects no reply

# 2. Discovery: which tools are there?
tool = ask(2, "tools/list")["result"]["tools"][0]
print("2 tools/list ->", {k: tool[k] for k in ("name", "description", "inputSchema")})

# 3. A tool call, and the two ways a call can go wrong.
print("3 tools/call ->", ask(3, "tools/call", {"name": "get_order_status", "arguments": {"order_id": "A-1001"}}))
print("4 bad tool   ->", ask(4, "tools/call", {"name": "no_such_tool", "arguments": {}}))
print("5 bad method ->", ask(5, "orders/delete_everything"))
server.terminate()
What you should see
1 initialize -> shopkart-orders | offers: ['logging', 'prompts', 'resources', 'tools']
2 tools/list -> {'name': 'get_order_status', 'description': "Return the shipping status for an order ID like 'A-1001'.", 'inputSchema': {'properties': {'order_id': {'type': 'string'}}, 'required': ['order_id'], 'type': 'object', 'additionalProperties': False}}
3 tools/call -> {'jsonrpc': '2.0', 'id': 3, 'result': {'content': [{'text': '{"order_id":"A-1001","status":"shipped"}', 'type': 'text'}], 'isError': False, 'structuredContent': {'order_id': 'A-1001', 'status': 'shipped'}}}
4 bad tool   -> {'jsonrpc': '2.0', 'id': 4, 'result': {'content': [{'text': "Unknown tool: 'no_such_tool'", 'type': 'text'}], 'isError': True}}
5 bad method -> {'jsonrpc': '2.0', 'id': 5, 'error': {'code': -32601, 'message': 'Method not found', 'data': 'orders/delete_everything'}}

Read the five lines in order.

  • Line 2 is the tool description from Lesson 14.58. A name, a description taken from the docstring, and a JSON Schema for the arguments, which FastMCP built from the function's type hints. The host copies these three fields into the tool list it sends to the model. The model never talks to the server. It asks for a tool call, as in Lesson 14.57, and the host turns that request into message 3.
  • Line 3 carries the result twice: as text in content, for the model to read, and as structuredContent, for programs.
  • Lines 4 and 5 are two different kinds of failure. A tool that fails returns a normal result with isError: true and a message in words. The host passes that to the model, which can read it and try something else. A broken request returns an error with a numeric code (-32601 means "no such method"). That one is for the client software, and the model never sees it.

The handshake in step 1 belongs to the protocol revisions up to 2025-11-25, which servers still accept. The 2026-07-28 revision drops it so that any request can go to any copy of a server (Lesson 13.47, Step 4). The tools/list and tools/call messages are the same in both.

Check your mental model
  • ✗ "MCP is a model or an agent framework."
    ✓ It is a protocol between an application and the servers that offer tools and data.
  • ✗ "MCP tools are safer than local tools."
    ✓ They are just as powerful, and the server is code you may not control; review and restrict them.
  • ✗ "The model talks to the MCP server directly."
    ✓ Your application is the client; the model still only proposes tool calls.

Exercises

Predict before you run

The server exposes get_order_status and cancel_order as tools, refund_policy as a resource and apology as a prompt. Which of the three does the model call by itself, and which does the application or the user choose? (Solution P1.)

Break it on purpose

Debugging exercise

A server works in the MCP Inspector, but the agent never calls its tool. The agent's tool list shows the tool. What do you check? (Solution D1.)

Solutions

SolutionP1 · Tools, resources, prompts

Tools are model-controlled: the model decides to call them. Resources are application-controlled: the host decides what context to attach. Prompts are user-controlled templates, typically chosen from a menu. Mixing them up leads to servers that expose data as tools the model calls too often, or actions nobody can trigger.

SolutionB1 · MCP tools are still tools

The model sees a tool it cannot understand, so it calls it wrongly or not at all. Everything from Lesson 14.58 applies: clear names, descriptions with examples, typed parameters. MCP standardizes the connection, not the quality of the tool.

SolutionD1 · The model chooses by description

The tool's description and parameter names against the user's phrasing, overlap with other tools that sound similar, and whether the host filters or defers the tool (tool search). Test the agent with the questions it should answer and read which tools it considered.

SolutionM1 · Paginate large results

Return at most a small page with a next-cursor, plus a total, so the model can ask for more. Large unpaginated results waste context and push the conversation over budget.

Check your understanding

Explain the mechanismWhat is MCP, and what problem does it solve?

Worked answer. The Model Context Protocol is an open standard for connecting AI applications (hosts and their clients) to servers that offer tools, resources and prompts, over standard transports. It replaces one custom integration per pair of application and tool with one server that any compliant host can use, and lets organizations share and govern integrations.

A plausible wrong answer. "MCP is a new way for models to call functions." Function calling is the model API's mechanism; MCP is how the tools are discovered and connected.

Follow-ups. What are the roles of host, client and server?

Debug a failureAn MCP tool works for one user and fails for another with the same input. What do you check?

Worked answer. Authentication and authorization on the server: which identity the call ran as, and that user's permissions in the underlying system. Also per-user configuration, rate limits and session state. Log the identity with each call.

A plausible wrong answer. "The model sent different arguments." Check the identity first when inputs match.

Follow-ups. How should a server get the user's identity (Lesson 13.47)?

Defend a designBuild an MCP server for an internal API, or call the API directly from the agent?

Worked answer. An MCP server when several agents or hosts will use the API, or when you want central governance, discovery and auth; direct calls for a single agent with one integration, where MCP adds a process and a protocol for no reuse. Many teams start direct and extract a server when a second consumer appears.

A plausible wrong answer. "Always MCP, it is the standard." Standards pay off with reuse.

Follow-ups. What would you put in the server's tool descriptions?
