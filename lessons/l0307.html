Why this came about

Once agents existed, teams used them for everything, including tasks with a fixed sequence of steps, and got slow, costly, unpredictable systems. In late 2024 Anthropic's "Building effective agents" summarized what practitioners had learned: start with simple workflows (chaining, routing, parallel steps, orchestrator-workers, evaluator-optimizer) and use agents only when the path cannot be known in advance.

In plain words first
Most problems need a recipe, not a chef who improvises

Before building an agent, check whether a fixed workflow will do: code decides the order of steps and a model fills in each one (classify, then extract, then route). Workflows are cheaper, faster and easier to test. An agent, where the model decides the next step, is for tasks whose path cannot be known in advance. Most production systems are workflows with one agentic step inside, built from a few standard shapes: chaining, routing, parallel steps, orchestrator and workers, and generate-then-evaluate.

Start with the least autonomy that works

How this connects

Lesson 14.1 introduced the idea that systems sit on a scale from "your code decides everything" to "the model decides everything", and Lessons 14.2 to 14.7 built the far end of that scale: an agent loop. This lesson fills in the middle. It names the five standard arrangements of model calls where your code stays in charge, and builds each one in a few lines.

The most cited practical advice in the field comes from Anthropic's Building effective agents (December 2024): find the simplest solution, and add complexity only when it measurably helps. They distinguish workflows, where code decides the path, from agents, where the model decides the path. This workflow vs. agent distinction is the first design decision.

Shape Who decides the next step Use when

Industry practice
The same advice from three directions
  • Anthropic: workflows for predictability, agents for flexibility; most successful implementations used simple, composable patterns rather than complex frameworks.
  • OpenAI (A practical guide to building agents, 2025): maximize a single agent's capabilities first; move to multiple agentslater · 14.12 only when instructions get too complex or tools overlap too much to choose between.
  • Google (Agents whitepaper and its companion): an agent is model + tools + orchestration layer; invest in the orchestration layer (reasoning, memory, planning) before adding agents.

The workflow patterns in code

Each pattern is a few lines of control flow around model calls. To keep the control flow visible and runnable offline, the "model" below is a stand-in function that returns deterministic answers for each kind of request; in your code each llm(...) call is a real model call with its own prompt. What matters is who decides what happens next: in every block below, it is your code, until the last one.

import asyncio, re
from collections import Counter

def llm(task: str, text: str, **kw) -> str:
    """A deterministic stand-in for a model call. Each task would be a separate prompt in real code."""
    t = text.lower()
    if task == "classify":
        return ("refund" if "refund" in t or "money back" in t else
                "delivery" if "where" in t or "late" in t else "other")
    if task == "draft_reply":
        return f"Dear customer, regarding '{text}': we are checking this now."
    if task == "check_policy":                        # a gate: does the draft promise anything we cannot?
        return "fail: promises a date" if "tomorrow" in t else "pass"
    if task == "translate_hi":
        return "Priya grahak, " + text.split(":", 1)[1].strip()
    if task == "sentiment":
        return "negative" if any(w in t for w in ("broken", "angry", "worst")) else "neutral"
    if task == "pii":
        return "contains_pii" if re.search(r"\d{10}|@", t) else "clean"
    if task == "answer_vote":                         # three samples of the same question, one dissenting
        return ["30 days", "30 days", "7 days"][kw["sample"]]
    if task == "plan":
        subtasks = ["check order status"]
        if "refund" in t: subtasks.append("check refund eligibility")
        if "address" in t: subtasks.append("check address change rules")
        return "\n".join(subtasks)
    if task == "worker":
        return {"check order status": "A-1001 delivered 3 days ago",
                "check refund eligibility": "eligible: damaged items, 30-day window",
                "check address change rules": "address changes only before dispatch"}[text]
    if task == "synthesize":
        return "Summary: " + "; ".join(text.splitlines())
    if task == "critique":
        return "pass" if "sorry" in t and "refund" in t else "fail: apologise and state the refund outcome"
    if task == "revise":
        return text + " We are sorry; your refund has been approved."
    raise ValueError(task)

Prompt chaining with a gate

A fixed sequence of steps, with a programmatic check between them. If the gate fails, stop or repair instead of passing a bad draft downstream.

def chain(ticket: str) -> str:
    draft = llm("draft_reply", ticket)                          # step 1
    verdict = llm("check_policy", draft)                        # gate
    if verdict != "pass":
        return f"held for review ({verdict})"
    return llm("translate_hi", draft)                            # step 2

print(chain("my order is late"))
print(chain("deliver it tomorrow"))
What you should see
Priya grahak, we are checking this now.
held for review (fail: promises a date)

Routing

A classifier picks the path; each path can have its own prompt, tools and even model (a cheap model for FAQs, a strong one for disputes).

HANDLERS = {
    "refund":   lambda t: "refund flow: verify order, check policy, open request",
    "delivery": lambda t: "delivery flow: look up tracking",
    "other":    lambda t: "general flow: answer from FAQ or hand off",
}

for ticket in ("I want my money back for A-1001", "where is my parcel", "do you sell phones"):
    route = llm("classify", ticket)
    print(f"{route:8} -> {HANDLERS[route](ticket)}")
What you should see
refund   -> refund flow: verify order, check policy, open request
delivery -> delivery flow: look up tracking
other    -> general flow: answer from FAQ or hand off

Measure the router on its own: a misroute sends the user down the wrong path no matter how good each path is.

Parallelization: sectioning and voting

Sectioning runs independent checks at the same time; voting asks the same question several times and takes the majority, trading cost for confidence.

async def call_async(task, text, **kw):
    await asyncio.sleep(0.1)                       # stands in for network latency of a real model call
    return llm(task, text, **kw)

async def sectioning(ticket: str) -> dict:
    sentiment, pii, route = await asyncio.gather(
        call_async("sentiment", ticket), call_async("pii", ticket), call_async("classify", ticket))
    return {"sentiment": sentiment, "pii": pii, "route": route}

async def voting(question: str, n: int = 3) -> tuple[str, float]:
    answers = await asyncio.gather(*(call_async("answer_vote", question, sample=i) for i in range(n)))
    best, count = Counter(answers).most_common(1)[0]
    return best, count / n                         # the agreement rate doubles as a confidence score

print(asyncio.run(sectioning("The mixer is broken, call me on 9876543210")))
print(asyncio.run(voting("What is the refund window for damaged items?")))
What you should see
{'sentiment': 'negative', 'pii': 'contains_pii', 'route': 'other'}
('30 days', 0.6666666666666666)

Three checks took the time of one. Use the voting agreement rate to decide when to escalate: two out of three is a reason to show sources or ask a human.

Orchestrator-workers

The difference from sectioning: the subtasks are not known in advance. A model plans them from the input, workers run them, and a synthesizer combines the results.

async def orchestrate(request: str) -> str:
    subtasks = llm("plan", request).splitlines()                         # the model decides the subtasks
    results = await asyncio.gather(*(call_async("worker", s) for s in subtasks))
    return llm("synthesize", "\n".join(f"{s}: {r}" for s, r in zip(subtasks, results)))

print(asyncio.run(orchestrate("A-1001 arrived damaged, I want a refund")))
print(asyncio.run(orchestrate("Can I change the address for A-1001?")))
What you should see
Summary: check order status: A-1001 delivered 3 days ago; check refund eligibility: eligible: damaged items, 30-day window
Summary: check order status: A-1001 delivered 3 days ago; check address change rules: address changes only before dispatch

Evaluator-optimizer

One step drafts, another critiques against explicit criteria, and the loop repeats until the critique passes or a limit is hit. It works when the criteria are clear and the critic is reliable.

def evaluator_optimizer(ticket: str, max_rounds: int = 3) -> str:
    draft = llm("draft_reply", ticket)
    for round_ in range(1, max_rounds + 1):
        verdict = llm("critique", draft)
        print(f"round {round_}: {verdict}")
        if verdict == "pass":
            return draft
        draft = llm("revise", draft)
    return draft + " [sent for human review]"

print(evaluator_optimizer("refund for broken mixer"))
What you should see
round 1: fail: apologise and state the refund outcome
round 2: pass
Dear customer, regarding 'refund for broken mixer': we are checking this now. We are sorry; your refund has been approved.

Always bound the loop and decide what happens when it does not converge.

When to hand control to the model

All the patterns above keep your code in charge of the flow. An agent (Lesson 14.3) hands that decision to the model at every step. A useful rule from teams that ship both: if you can draw the flowchart, code it as a workflow; if you cannot, because the next step depends on what the model finds, use an agent, and keep workflows inside it for the parts that are predictable.

One more shape sits between a fixed workflow and a free agent: the model writes a plan, and your code carries it out step by step, asking for a new plan when a step's result changes the picture. That is plan-and-execute. It belongs with the other ways of organising an agent's reasoning, so it is taught, with code, in Lesson 14.9.

From the field: start simple and earn complexity

The patterns above are the middle of the scale. This is the most consistent advice on where to start on it, from Anthropic's Building effective agents (December 2024), OpenAI's A practical guide to building agents (2025), Chip Huyen's Agents (January 2025) and the What we learned from a year of building with LLMs authors (Eugene Yan, Bryan Bischof, Charles Frye, Hamel Husain, Jason Liu and Shreya Shankar, 2024):

Rule What it means in practice
Try the simplest thing first A single well-prompted call with retrieval often beats an agent. Add a fixed workflow before a free agent, and one agent before many
Workflows versus agents Workflows follow code paths you wrote (chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer); agents let the model choose its path. Use agents only where the path cannot be known in advance
Keep the design simple, the planning visible, the tools well documented Anthropic's three principles; the third, the agent-computer interface, is where most of the effort should go
Start with the most capable model, then optimize down OpenAI's guide: set a quality baseline with the best model and evals, then swap in smaller models where they still pass (Lesson 14.114)
Frameworks are optional Understand the loop (Lesson 14.3) before adopting abstractions; if you use a framework, know what it does under the hood
Guardrailslater · 15.21 are layered No single check is enough: input filters, tool risk ratings, output checks, human approval for high-impact actions (Lesson 15.21)

  • ✗ "Agents are the more advanced choice."
    ✓ They are the more flexible and more failure-prone choice; use them only when the path is unknown.
  • ✗ "A workflow cannot use a model."
    ✓ Workflows use models in each step; code just decides the order.

Exercises

Predict before you run

For ShopKart's "summarize a support ticket, then translate the summary to Hindi", which pattern fits: a chain, routing, an orchestrator-workers setup, or an agent? How many model calls does it take? (Solution P1.)

Break it on purpose

Remove the gate from chain (the check between the steps). Feed it a ticket that the first step cannot summarize, such as an empty message. What reaches the second step, and what does the customer see? (Solution B1.)

Debugging exercise
Debugging exercise: an evaluator that always says "good"

evaluator_optimizer stopped improving drafts: every draft passes on the first round. The evaluator is the same model with the prompt "Is this reply good? Answer yes or no." Explain the problem and fix it. (Solution D1.)

Make it your own

Add a routing step in front of chain that sends refund tickets to a refund-specific chain and everything else to the general chain, and count how often each route is taken on ten tickets. (Solution M1.)

Solutions

SolutionP1 · A chain

A chain of two calls: summarize, then translate, with a gate between them that checks the summary exists and is short enough. The steps and their order are known in advance, so nothing needs the model to decide what to do next; an agent would add cost and unpredictability for no benefit.

SolutionB1 · Without a gate, errors flow downstream

The second step translates whatever came out of the first, including an apology or an empty string, and the customer gets a confident Hindi version of nonsense. Gates turn a silent failure into a handled one: stop, retry, or route to a person.

SolutionD1 · A vague evaluator approves everything

"Is this good?" gives the evaluator no criteria, and models tend to approve their own kind of output. Give the evaluator a concrete rubric (mentions the order ID, states a timeline from the policy, under 80 words, no promise the tools did not support), ask for the failing criteria rather than yes or no, and where possible use a checker in code. Measure the evaluator itself on labeled drafts.

SolutionM1 · A router in front of chains

A router is one cheap classification call (or a rule) whose output picks the chain. Count routes over the ten tickets, then read the misrouted ones: routing errors are usually label definitions, fixed with better descriptions and examples. Route an "unsure" class to the general chain or a person.

Check your understanding

Explain the mechanismDescribe the main workflow patterns for LLM applications.

Worked answer. Prompt chaining (fixed steps with gates between them), routing (classify, then send to a specialized path), parallelization (sectioning a task into independent parts, or voting over several attempts), orchestrator-workers (a model splits a task and delegates parts), evaluator-optimizer (draft, critique against criteria, revise), and plan-and-execute with re-planning. They differ in how much control the model has; start with the least autonomy that handles every known path, and give the model more only where the path cannot be known in advance.

A plausible wrong answer. "Always build an agent; it can do all of these." It can, at higher cost and lower predictability.

Follow-ups. When does orchestrator-workers beat a fixed parallel split?

Debug a failureA plan-and-execute workflow keeps executing a stale plan after a step fails. What do you change?

Worked answer. Re-plan on failure: after each step, check the result against the step's success condition, and on failure send the plan, the results so far and the error back to the planner for a revised plan, with a limit on re-plans. Also check that steps report failures as failures instead of plausible text.

A plausible wrong answer. "Make the plan more detailed." A detailed plan still goes stale when the world differs from the plan.

Follow-ups. How would you stop endless re-planning?

Defend a designA stakeholder wants a fully autonomous agent for refunds. What do you propose?

Worked answer. A workflow with the model inside it: route refund requests, look up the order and policy in fixed steps, let the model draft the explanation, decide eligibility in code, and require approval above a limit. Autonomy goes where the path truly varies, such as understanding messy customer messages. That is cheaper, easier to test and audit, and still feels intelligent to the customer. Expand autonomy later if evals show the fixed path is the bottleneck.

A plausible wrong answer. "Yes, agents are the future." Refunds move money; predictability and auditability come first.

Follow-ups. What would you measure to decide whether to give it more autonomy?
