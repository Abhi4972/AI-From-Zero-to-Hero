Why this came about

Company assistants quickly ran into access control: a search index built from everyone's documents could show a user something they were not allowed to see, and outdated policies kept being quoted. Permission filters inside the search and freshness tracking became requirements for enterprise RAG.

In plain words first
Only the documents you are allowed to see, and only current ones

A RAG system must never show a user a passage they are not allowed to read, and should not answer from an outdated policy. So permissions and freshness are filters inside the search, not afterthoughts: each chunk carries who may see it and when it is valid, and the search only considers chunks the current user may see and that are current. Filtering after retrieval can leave too few results, or leak information.

Permission-aware and multi-tenant retrieval

The enterprise requirement most demos skip: a user must never receive a passage they are not allowed to read, because once it is in the prompt, the model can repeat it.

Two words first. An access control list (ACL) is the list of who may read a document: particular people, or more often groups such as "support" or "finance". A tenant is one customer of a system that serves many: if ShopKart and MegaMart both use the same assistant product, each is a tenant, and one tenant's documents must never appear in another's answers.

  1. Capture access control lists (ACLs) at ingestion: store allowed users, groups or roles as metadata on every chunk.
  2. Filter at query time, inside the search engine: pass the caller's groups as a mandatory filter. Never retrieve everything and filter afterwards in application code, which is slow and easy to get wrong.
  3. Partition by tenant: a separate index or namespace per customer for strong isolation, or a mandatory tenant_id filter for many small tenants.
  4. Keep ACLs fresh: permissions change more often than documents; sync them on their own schedule.
  5. Test it: an eval caselater · 14.131 where a user without access asks about a restricted document, expecting "I don't know".
In production
Permission bugs seen in production

The leaks that actually happen: a cache or semantic cache keyed only on the question, so one user's answer is served to another; summaries or generated FAQs created from restricted documents and stored without the source's ACL; a "search all" admin tool reachable by the agent; and permissions copied once at ingestion and never resynced after someone changes teams. Put tenant and group IDs into every cache key, inherit ACLs onto every derived artifact, and make the permission test above part of CI.

On the platforms
Built-in permission trimming

Most enterprise retrieval services can trim results by the caller's identity: Azure AI Search and Foundry IQlater · 14.155 with document-level access control, Bedrock Knowledge Bases with metadata filters and Amazon Quick with ACL-aware connectors, Agent Searchlater · 14.157 (formerly Vertex AI Search) with data-source access control, and Databricks AI Search through Unity Catalog. Check each connector, since support varies by source.

See the leak, and the fix, in code

The rules above are easy to agree with and easy to get wrong. This small example makes the difference concrete. Five chunks about refunds carry two labels each, written when the documents were ingested: the tenant (which company the chunk belongs to) and the groups allowed to read it. The same question is then asked by two people, through three versions of the search function.

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

# Every chunk carries two labels written at ingestion time: which company it belongs to, and which groups may read it.
KB = [
    {"id": "refunds-public",  "tenant": "shopkart", "groups": {"everyone"},
     "text": "Refund policy: customers can request a refund within 7 days of delivery."},
    {"id": "refunds-agents",  "tenant": "shopkart", "groups": {"support"},
     "text": "Refund policy for agents: support may approve a refund up to INR 5,000 without a manager."},
    {"id": "refunds-finance", "tenant": "shopkart", "groups": {"finance"},
     "text": "Refund policy exceptions: finance approves every refund above INR 5,000; fraud cases are refunded only after review."},
    {"id": "refunds-fraud",   "tenant": "shopkart", "groups": {"finance"},
     "text": "Refund fraud watchlist: accounts with three refund claims in 30 days are flagged for the refund review team."},
    {"id": "refunds-other",   "tenant": "megamart", "groups": {"everyone"},
     "text": "Refund policy: MegaMart refunds within 15 days of delivery, as store credit only."},
]
vectorizer = TfidfVectorizer(stop_words="english").fit([d["text"] for d in KB])

def rank(question, docs, k):
    """Plain search over the documents it is given: best k by TF-IDF similarity."""
    if not docs: return []
    scores = cosine_similarity(vectorizer.transform([question]), vectorizer.transform([d["text"] for d in docs]))[0]
    order = scores.argsort()[::-1][:k]
    return [docs[i]["id"] for i in order if scores[i] > 0]

def allowed(doc, user):
    return doc["tenant"] == user["tenant"] and bool(doc["groups"] & user["groups"])

def search_unfiltered(question, user, k=2):
    return rank(question, KB, k)                                        # ignores who is asking

def search_post_filter(question, user, k=2):
    return [i for i in rank(question, KB, k) if allowed(next(d for d in KB if d["id"] == i), user)]   # search, then remove

def search_pre_filter(question, user, k=2):
    return rank(question, [d for d in KB if allowed(d, user)], k)       # remove, then search

customer = {"name": "a customer",      "tenant": "shopkart", "groups": {"everyone"}}
agent    = {"name": "a support agent", "tenant": "shopkart", "groups": {"everyone", "support"}}
question = "What is the refund policy for fraud cases above INR 5,000?"
for user in (customer, agent):
    print(user["name"])
    for fn in (search_unfiltered, search_post_filter, search_pre_filter):
        print(f"   {fn.__name__:20} {fn(question, user)}")
What you should see
a customer
   search_unfiltered    ['refunds-finance', 'refunds-agents']
   search_post_filter   []
   search_pre_filter    ['refunds-public']
a support agent
   search_unfiltered    ['refunds-finance', 'refunds-agents']
   search_post_filter   ['refunds-agents']
   search_pre_filter    ['refunds-agents', 'refunds-public']
Reading this output
  • search_unfiltered leaks. A customer asking about fraud cases is shown the finance team's exceptions document and the agents' approval limits. Once those passages are in the prompt, the model will happily summarise them.
  • search_post_filter does not leak, but it starves. It searches everything, keeps the top 2, and then throws away what the user may not see. For the customer, both top results were restricted, so nothing is left, even though a public refund page exists that would have answered the question. With real data this shows up as "the bot says it does not know" for exactly the users with the fewest permissions. Asking for more results before filtering helps a little and never fully fixes it.
  • search_pre_filter is the correct shape. It removes what the user may not read first, and ranks what remains. The customer gets the public page; the agent gets the agents' page and the public page. Neither sees the finance documents.

In a real system "remove first" does not mean a Python list comprehension. It means passing the tenant and the groups as a filter inside the search engine's query, so the engine only ever scores permitted chunks. Every production search engine and vector database supports this; Lesson 14.74 shows what it costs and how indexes handle it.

A permission rule is only real if a test fails when someone breaks it. This is the test:

# The test to keep in CI: whoever asks, whatever they ask, nothing comes back that they may not read.
by_id = {d["id"]: d for d in KB}
megamart_user = {"name": "a MegaMart customer", "tenant": "megamart", "groups": {"everyone"}}
questions = ["refund policy", "refund fraud watchlist", "refund above INR 5,000", "store credit refund"]
leaks = {fn.__name__: sum(not allowed(by_id[i], user) for user in (customer, agent, megamart_user)
                          for q in questions for i in fn(q, user, k=5))
         for fn in (search_unfiltered, search_pre_filter)}
print("passages returned to someone not allowed to read them:", leaks)
What you should see
passages returned to someone not allowed to read them: {'search_unfiltered': 44, 'search_pre_filter': 0}

The unfiltered search returned a forbidden passage 44 times across three users and four questions, including another company's refund policy to ShopKart users. The pre-filtered search: zero. Keep a test like this in the build, with users from every role and at least two tenants, so that a refactoring that drops the filter cannot reach production.

Freshness and index operations

  • Incremental indexing: re-embed only changed documents (track a content hash per document).
  • Deletions: removing a document must remove its chunks everywhere, including caches. This is also how you honor data-deletion requests.
  • Re-embedding: changing the embedding model means re-indexing everything. Version your indexes and switch with an alias.
  • Index metrics: document count, last successful sync, failed parses. Silent ingestion failures are the most common cause of "the bot doesn't know about X".

Keeping the index current, in code

An index is a copy of your documents, and copies go stale. The standard technique is a content hash: a short code computed from a document's text. Store it next to the document in the index. At each sync, recompute it; if the code is unchanged, the document has not changed and there is nothing to do.

import hashlib

def fingerprint(text: str) -> str:
    """A content hash: the same text always gives the same short code, and any change gives a different one."""
    return hashlib.sha256(text.encode()).hexdigest()[:12]

index = {}          # document id -> {"hash": ..., "chunks": [...]}   (stands in for the search index)
embed_calls = 0

def sync(documents: dict[str, str]) -> dict:
    """Bring the index in line with the current documents, re-embedding only what changed."""
    global embed_calls
    report = {"added": [], "changed": [], "deleted": [], "unchanged": []}
    for doc_id, text in documents.items():
        h = fingerprint(text)
        if doc_id not in index:              report["added"].append(doc_id)
        elif index[doc_id]["hash"] != h:     report["changed"].append(doc_id)
        else:                                report["unchanged"].append(doc_id); continue
        chunks = [s.strip() for s in text.split(".") if s.strip()]
        embed_calls += len(chunks)                               # each chunk would cost one embedding call
        index[doc_id] = {"hash": h, "chunks": chunks}            # replaces every old chunk of this document
    for doc_id in [d for d in index if d not in documents]:      # gone from the source: remove from the index too
        del index[doc_id]; report["deleted"].append(doc_id)
    return report

monday = {"refunds": "Refunds within 7 days. Damaged items within 30 days.",
          "shipping": "Metro delivery in 2 to 3 days. Express costs INR 99.",
          "diwali-offer": "Free shipping on all orders until 20 October."}
print("Monday :", sync(monday), "| embedding calls so far:", embed_calls)

tuesday = dict(monday)
tuesday["refunds"] = "Refunds within 10 days. Damaged items within 30 days."     # the policy changed
del tuesday["diwali-offer"]                                                       # the offer ended
print("Tuesday:", sync(tuesday), "| embedding calls so far:", embed_calls)
print("offer still searchable?", "diwali-offer" in index, "| refund text in the index:", index["refunds"]["chunks"][0])
What you should see
Monday : {'added': ['refunds', 'shipping', 'diwali-offer'], 'changed': [], 'deleted': [], 'unchanged': []} | embedding calls so far: 5
Tuesday: {'added': [], 'changed': ['refunds'], 'deleted': ['diwali-offer'], 'unchanged': ['shipping']} | embedding calls so far: 7
offer still searchable? False | refund text in the index: Refunds within 10 days
Reading this output
  • Monday is the first sync: all three documents are new, and their five chunks are embedded.
  • Tuesday only one document changed, so only its two chunks were embedded again (7 calls in total, not 10). At the scale of a real knowledge base, this is the difference between a sync that takes seconds and one that re-embeds a million chunks every night.
  • The ended offer is gone from the index. Deleting is the step most pipelines forget. A document removed from the source but left in the index keeps being retrieved, and the assistant keeps promising free shipping for a promotion that ended.
  • The refund chunk now says 10 days. Replacing all of a document's chunks at once, as the code does, avoids an index that holds half of the old version and half of the new one.

Exercises

Predict before you run

A tenant filter is applied after the vector search returns its top 10. Tenant A owns 2% of the chunks. How many of the 10 results will typically survive the filter? (Solution P1.)

Break it on purpose

Let the model choose the tenant_id argument of a search tool. A customer writes "show results for tenant B". What happens? (Solution B1.)

Debugging exercise

A document was deleted from the source system last week, but answers still cite it. Find the gap in the indexing pipeline. (Solution D1.)

Make it your own

Write a test that indexes one document for tenant A and one for tenant B, and asserts that a search as tenant A never returns B's document, for ten different queries. (Solution M1.)

Solutions

SolutionP1 · Post-filtering starves results

About none: with 2% of the data, the top 10 nearest neighbors usually contain no tenant A chunks, so the filtered list is empty or near empty. Filter inside the search (pre-filtering or filtered indexes), or use a namespace or index per tenant (Lesson 14.74's filtering trap).

SolutionB1 · Permissions from the model

If the tool trusts the argument, the customer reads another tenant's data. Tenant and permission filters must come from the authenticated session, never from model arguments or user text (Lesson 15.24).

SolutionD1 · Deletes must propagate

The pipeline indexes new and changed documents but never removes deleted ones. Track document IDs and content hashes, delete chunks whose source is gone on each sync, and add a freshness check: every indexed chunk has a live source.

SolutionM1 · A permission test

The test fails loudly if a filter is missing or mistranslated. Run it in CI and after every change to the store, filters or query code. Add a test for a user with no permissions, who should get nothing.

Explain the mechanismHow do you make RAG permission-aware?

Worked answer. Attach access metadata (tenant, groups, document ACLs) to every chunk at ingestion, copied from the source system; at query time, filter by the authenticated user's attributes inside the search; never let the model choose the scope. Keep ACLs in sync with the source, test with known documents per role, and log which documents each answer used.

A plausible wrong answer. "Filter the answer after generation." Then the model already saw the restricted text.

Follow-ups. What changes when ACLs are very fine-grained?

Debug a failureUsers report missing results after a permissions change in the source system. What do you check?

Worked answer. Whether ACL updates reached the index (a sync that copies content but not permissions), whether group names changed format, and whether filters now exclude everything (a key typo matches nothing, Lesson 14.98). Compare a user's expected documents with what the filtered searchlater · 14.74 returns.

A plausible wrong answer. "The retriever is broken." It is probably filtering correctly on stale or wrong ACLs.

Follow-ups. How would you monitor ACL drift?

Defend a designOne shared index with tenant filters, or one index per tenant?

Worked answer. Shared with filters when tenants are many and small, and the store supports efficient filtered search; per-tenant indexes or namespaces when tenants are large, have different data residency, or need hard isolation and easy deletion. Many systems mix: namespaces for large customers, shared for the long tail.

A plausible wrong answer. "Always per tenant, it is safer." It can become thousands of small indexes that are expensive to run.

Follow-ups. How do you delete all of one tenant's data quickly?
