Why this came about

Full fine-tuning of large models was too expensive for most teams. LoRA (2021) made tuning cheap by training small add-on matrices, and distillation let small models learn tasks from large ones, putting model customization within reach of ordinary teams.

In plain words first
Adjusting a model instead of only instructing it

When prompts and retrieval are not enough, you can change the model itself. Fine-tuning trains it further on your examples; LoRA does that cheaply by training small extra matrices instead of all the weights; distillation trains a small model to imitate a large one on your task, cutting cost and latency. Each needs a good dataset and an evaluation that proves the tuned model beats the simpler options.

Step 3 · Where LoRA sits among the methods

You trained a LoRA adapter in Lesson 3.24, so this step is a recap and a map. LoRA (low-rank adaptation) freezes the model's weights and learns a small update for each chosen layer as the product of two thin matrices, B @ A. Training touches a few percent of the parameters, the result is a file of a few megabytes, and one base model can serve many adapters.

LoRA is a way of doing supervised fine-tuning: you show the model inputs with the outputs you want. The rest of this lesson covers what supervised fine-tuning on your own examples does not give you:

You want Supervised fine-tuning needs The method in this lesson
A cheap, fast model for a step that a large model already does well Thousands of labelled examples, which you may not have Distillation (Step 4): the large model writes the labels
Answers in the style people prefer One "correct" answer per input, when really some answers are just better than others Preference tuning (Step 5): learn from pairs of better and worse answers
Better results on a task where answers can be checked by a program Example answers, when all you have is a way to check them Reinforcement fine-tuning (Step 6): learn from a grader's scores

Each of these can be trained with LoRA adapters too: LoRA decides which weights change, and the method decides what signal they learn from.

In production
Fine-tuning projects that disappoint

The usual reasons: the gap was knowledge, which retrieval would have fixed; the training data repeated the system's own mistakes because it came from unreviewed traces; the evaluation set leaked into training, so the gain disappeared in production; or a better base model shipped a month later and beat the tuned one. Start from a held-out, human-labeled eval set, compare against the best prompt-only baseline and the newest base model, and keep the frontier model behind the same alias as a fallback.

Step 4 · Distillation: a small model for a high-volume step

The most common customization that pays for itself: a frontier model labels your traffic for one narrow step (here, intent routing), and a tiny model learns to imitate it:

import random
import numpy as np
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.linear_model import LogisticRegression

random.seed(4)
TEMPLATES = {
    "order_status": ["where is my order {o}", "has {o} shipped yet", "track {o} please", "{o} not delivered, status?",
                     "when will {o} arrive", "is {o} out for delivery"],
    "cancel": ["cancel {o}", "i want to cancel order {o}", "please stop {o}, don't ship it", "cancel my last order {o}"],
    "refund": ["refund for {o}, it arrived broken", "money back for {o}?", "{o} was damaged, i want a refund",
               "when do i get my refund for {o}"],
    "other": ["do you sell insurance", "what are your store hours", "i need help with my account password",
              "can i change my delivery address", "do you have a loyalty program"],
}
def sample(n):
    rows = []
    for _ in range(n):
        intent = random.choice(list(TEMPLATES))
        text = random.choice(TEMPLATES[intent]).format(o=f"A-{random.randint(1000, 9999)}")
        rows.append((text + random.choice(["", "!", " asap", " thanks", "??"]), intent))
    return rows

def teacher(text: str, true_intent: str) -> str:
    """Stand-in for the large model you call today. Simulated: right 97% of the time."""
    return true_intent if random.random() > 0.03 else "other"

data = sample(1200)
train, test = data[:1000], data[1000:]
train_texts = [t for t, _ in train]
teacher_labels = [teacher(t, g) for t, g in train]        # the expensive part, done once
vec = TfidfVectorizer(ngram_range=(1, 2)).fit(train_texts)
student = LogisticRegression(max_iter=2000).fit(vec.transform(train_texts), teacher_labels)

pred = student.predict(vec.transform([t for t, _ in test]))
gold = [g for _, g in test]
teach = [teacher(t, g) for t, g in test]
print(f"student agrees with teacher {np.mean(pred == np.array(teach)):.1%}; student accuracy {np.mean(pred == np.array(gold)):.1%}; "
      f"teacher accuracy {np.mean(np.array(teach) == np.array(gold)):.1%}")
calls = 5_000_000
print(f"per month at {calls:,} calls: teacher ~${calls * 0.0006:,.0f} (API), student ~${calls * 0.000002:,.0f} (CPU)")
What you should see
student agrees with teacher 98.0%; student accuracy 100.0%; teacher accuracy 98.0%
per month at 5,000,000 calls: teacher ~$3,000 (API), student ~$10 (CPU)

The student even beat its teacher here, because a model trained on many labels averages out the teacher's random slips. Do not expect that on real traffic: these template messages are easy, and real students usually land a few points below the teacher. That is why the evaluation set must be labeled by people (the gold labels here), never by the teacher alone. When the student is unsure (low predicted probability), fall back to the teacher: a cascade (Lesson 14.142) that keeps quality while most calls cost nothing. For generative steps, distill into a small LLM with SFT instead of a classifier; Bedrock, Foundry and OpenAI offer managed distillation.

Step 5 · Preference pairs and pre-upload checks

Preference tuning (DPO and its variants) learns from pairs: for the same prompt, which answer was better. Pairs come from A/B comparisons, reviewer choices, or a rejected draft and its human-edited replacement. Whatever the method, validate the file before uploading; a rejected training job after an hour in a queue is the most avoidable delay in fine-tuning:

import json

FEEDBACK = [   # two candidate answers shown to users (or reviewers) for the same prompt, with their verdicts
    {"prompt": "My mixer arrived broken. What now?",
     "a": "Sorry about that! Damaged items are refundable within 30 days. Start a return under Orders > A-1002.", "a_vote": 1,
     "b": "Please contact support.", "b_vote": 0},
    {"prompt": "Where is A-1001?", "a": "A-1001 has shipped and arrives Thursday.", "a_vote": 1,
     "b": "Your package is on the way!", "b_vote": 1},          # both liked: no preference signal, skip
]
pairs = []
for f in FEEDBACK:
    if f["a_vote"] == f["b_vote"]:
        continue
    chosen, rejected = (f["a"], f["b"]) if f["a_vote"] > f["b_vote"] else (f["b"], f["a"])
    pairs.append({"prompt": [{"role": "user", "content": f["prompt"]}],
                  "chosen": [{"role": "assistant", "content": chosen}],
                  "rejected": [{"role": "assistant", "content": rejected}]})
print(len(pairs), "preference pair(s):", json.dumps(pairs[0])[:120], "...")

def validate_sft_row(row: dict, max_chars: int = 32_000) -> list[str]:
    """The checks fine-tuning services run, done before you upload and wait."""
    problems, msgs = [], row.get("messages", [])
    if not msgs or msgs[-1]["role"] != "assistant":
        problems.append("must end with an assistant message")
    roles = [m["role"] for m in msgs if m["role"] != "system"]
    if any(a == b for a, b in zip(roles, roles[1:])):
        problems.append("user and assistant turns must alternate")
    if sum(len(m.get("content") or "") for m in msgs) > max_chars:
        problems.append("too long")
    if any(re.search(r"[\w.+-]+@[\w-]+\.\w+", m.get("content") or "") for m in msgs):
        problems.append("contains an email address")
    return problems

import re
rows = [{"messages": [{"role": "user", "content": "Where is A-1001?"}, {"role": "assistant", "content": "It has shipped."}]},
        {"messages": [{"role": "user", "content": "Hi"}, {"role": "user", "content": "Where is A-1002?"}]},
        {"messages": [{"role": "user", "content": "Email me at ravi@gmail.com"}, {"role": "assistant", "content": "Done."}]}]
for i, row in enumerate(rows):
    print(f"row {i}:", validate_sft_row(row) or "ok")
What you should see
1 preference pair(s): {"prompt": [{"role": "user", "content": "My mixer arrived broken. What now?"}], "chosen": [{"role": "assistant", "conten ...
row 0: ok
row 1: ['must end with an assistant message', 'user and assistant turns must alternate']
row 2: ['contains an email address']

The second feedback item produced no pair: both answers were liked, so there is nothing to prefer. The prompt / chosen / rejected format with chat messages is what TRL's DPOTrainer and most managed services accept.

Step 6 · Reinforcement fine-tuning starts with a grader

Reinforcement fine-tuning (RFT; GRPO is the common open-source algorithm) lets the model try several answers per prompt and rewards the good ones. It needs no example answers at all, only a grader: a function that scores an answer. For SQL, the grader runs the query and compares the rows:

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
CREATE TABLE orders (id TEXT, city TEXT, amount INTEGER, status TEXT);
INSERT INTO orders VALUES ('A-1','Pune',499,'shipped'),('A-2','Pune',1299,'cancelled'),
                          ('A-3','Delhi',899,'shipped'),('A-4','Pune',250,'shipped');
""")
REFERENCE = "SELECT city, SUM(amount) FROM orders WHERE status = 'shipped' GROUP BY city"

def sql_reward(completion: str, reference: str = REFERENCE) -> float:
    """A verifiable reward: 1.0 if the query returns exactly the right rows, partial credit if it runs."""
    try:
        got = sorted(db.execute(completion).fetchall())
    except sqlite3.Error:
        return 0.0                                          # does not run
    want = sorted(db.execute(reference).fetchall())
    if got == want:
        return 1.0
    if "drop" in completion.lower() or "delete" in completion.lower():
        return -1.0                                         # punish destructive SQL hard
    return 0.2                                              # runs, wrong answer

candidates = [
    "SELECT city, SUM(amount) FROM orders WHERE status='shipped' GROUP BY city",
    "SELECT city, SUM(amount) FROM orders GROUP BY city",                 # forgot the filter
    "SELECT city, SUM(amount) FROM order GROUP BY city",                  # wrong table name
    "SELECT city, total FROM (SELECT city, SUM(amount) AS total FROM orders WHERE status='shipped' GROUP BY city)",
]
for c in candidates:
    print(f"{sql_reward(c):+.1f}  {c[:70]}")
What you should see
+1.0  SELECT city, SUM(amount) FROM orders WHERE status='shipped' GROUP BY c
+0.2  SELECT city, SUM(amount) FROM orders GROUP BY city
+0.0  SELECT city, SUM(amount) FROM order GROUP BY city
+1.0  SELECT city, total FROM (SELECT city, SUM(amount) AS total FROM orders

The fourth query is written differently from the reference and still scores 1.0, because the grader checks results, not text. That is what makes RFT powerful for tasks with checkable outcomes (SQL, code that must pass tests, extraction that must match a schema, classification) and useless for tasks without them. Most of the work is the grader: models are very good at finding its loopholes (reward hacking), so test it on wrong answers that look right before training, and keep a held-out eval set that the grader never sees.

Step 7 · The same steps with open-source trainers

On a GPU machine, Hugging Face TRL and PEFT run these methods on open-weight models. This script trains a LoRA adapter with SFT on the JSONL from Step 1, then shows how the Step 6 grader plugs into GRPO:

# RUN_LIVE: needs a GPU and: uv add trl peft datasets transformers torch   (tested against trl 1.16, peft 0.21)
from datasets import load_dataset
from peft import LoraConfig
from trl import GRPOConfig, GRPOTrainer, SFTConfig, SFTTrainer

# 1. Supervised fine-tuning with LoRA on chat-format rows ({"messages": [...]})
data = load_dataset("json", data_files={"train": "train.jsonl", "validation": "val.jsonl"})
sft = SFTTrainer(
    model="Qwen/Qwen3-0.6B",                                 # any causal LM on the Hub, or a local path
    train_dataset=data["train"], eval_dataset=data["validation"],
    args=SFTConfig(output_dir="shopkart-sft", num_train_epochs=3, learning_rate=2e-4,
                   per_device_train_batch_size=8, max_length=2048,
                   assistant_only_loss=True,                 # learn the answers, not the prompts
                   eval_strategy="epoch", logging_steps=10),
    peft_config=LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                           target_modules="all-linear", task_type="CAUSAL_LM"),
)
sft.train()
sft.save_model("shopkart-sft/adapter")                      # a few megabytes of LoRA weights
merged = sft.model.merge_and_unload()                       # fold the adapter into the weights
merged.save_pretrained("shopkart-sft/merged")
sft.processing_class.save_pretrained("shopkart-sft/merged")  # keep the tokenizer and chat template with it

# 2. GRPO with the SQL grader as the reward (rows: {"prompt": [...], "reference": "SELECT ..."})
def sql_reward_fn(completions, reference, **kwargs) -> list[float]:
    return [sql_reward(c[0]["content"], ref) for c, ref in zip(completions, reference)]

sql_tasks = load_dataset("json", data_files="sql_tasks.jsonl", split="train")
grpo = GRPOTrainer(model="shopkart-sft/merged", reward_funcs=sql_reward_fn, train_dataset=sql_tasks,
                   args=GRPOConfig(output_dir="shopkart-grpo", num_generations=8, max_completion_length=256))
grpo.train()

assistant_only_loss needs a chat template that marks assistant turns (most recent instruction models have one). Unsloth and Axolotl wrap the same trainers with faster kernels and YAML configs. Whatever the tool, the evaluation step is not optional: compare the tuned model with the base model and the frontier model on your held-out set before anything ships.

Industry practice
The order mature teams follow

Teams that report good returns from customization almost always did it late and narrowly: a high-volume step (classification, extraction, routing, a specific SQL dialect) where a small tuned model matched a frontier model on their evals at a fraction of the cost and latency. They keep the frontier model behind the same alias as a fallback, re-run the comparison whenever a new base model ships, and treat the training dataset as a governed asset with lineage and retention.

From the field
Checkr: a fine-tuned small model beat GPT-4 on the hard 2%

Checkr classifies records from background checks into 230 categories. A logistic regression model handled 98% of records; the remaining 2% were hard cases. Its engineers compared approaches on those cases (October 2024): GPT-4 with a prompt reached 81.8% accuracy at about 15 seconds per call; adding retrieved examples (RAG) made it worse, 79.3%, because similar-looking examples pulled the model toward wrong labels; a fine-tuned Llama-2 7B reached 85%; and a Llama-3 8B fine-tuned with LoRA reached 90%, with production latency around 0.15 seconds and inference cost about five times lower than GPT-4. Two lessons travel well: RAG is not automatically an improvement for classification, and a narrow, high-volume step is exactly where a small tuned model pays off. Source: Rubrik and Predibase blog.

The gap you see Try first Then Avoid

Solutions

SolutionP1 · Parameter-efficient fine-tuning

A tiny fraction, well under 1%. Training is cheaper, fits on smaller GPUs, and adapters are small files that can be swapped per task on one base model.

SolutionB1 · Distillation data decides coverage

The student never saw hard cases and fails on them. Distill on a representative and challenging input set, including the hard cases the student must handle.

SolutionD1 · Train and serve must match

The chat template, tokenizer and system prompt used in serving against training, whether the adapter was merged or loaded correctly, and quantization differences. Template mismatches are the most common cause.

SolutionM1 · A decision with numbers

Compare accuracy on the eval set, cost per thousand requests, latency and maintenance for each option; choose fine-tuning or distillation only if it meets accuracy at clearly lower cost or latency.

Check your understanding

Explain the mechanismWhen would you fine-tune, distill, or just prompt?

Worked answer. Prompt (with retrieval) first: cheapest to change. Fine-tune when you need consistent format, style or narrow skill that prompting cannot reach, or a smaller model at the same quality. Distill when a large model is accurate but too slow or expensive, training a smaller model on its outputs. Measure each against the eval set and the total cost of ownership.

A plausible wrong answer. "Fine-tune to make it smarter." Fine-tuning shapes behavior; it rarely adds general capability.

Follow-ups. What does QLoRA add to LoRA?

Debug a failureA fine-tuned small model matches the large one on the eval but fails in production. Why?

Worked answer. The eval set does not cover production's variety, so the small model's narrower competence is hidden. Add production samples, especially rare intents, and monitor fallback rates.

A plausible wrong answer. "The small model is unstable." It is narrower; the eval was too narrow to show it.

Follow-ups. When would you route back to the large model?

Defend a designManaged fine-tuning API or self-hosted training?

Worked answer. Managed for speed and simplicity when the provider supports your model and data terms; self-hosted for open models you must run yourself, data that cannot leave, or specialized methods. The deciding factors are data governance, model choice and the team's capacity.

A plausible wrong answer. "Self-hosted is always cheaper." Not counting the team's time.
