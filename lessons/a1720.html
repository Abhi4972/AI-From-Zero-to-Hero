In plain words first
The idea in one line

LLM rollouts combine the hardest parts of software deployment: no unit tests, diffuse failure modes, delayed signals. The sequence is (1) shadow mode — duplicate prod requests to candidate model, log, compare with zero user impact; catches obvious distribution issues but is not a quality guarantee; (2) canary rollout — progressive traffic shift 10% → 25% → 50% → 75% → 100% with gates at each step; track latency percentiles, cost/request, error/refusal rate, output length distribution, user-feedback rate; (3) A/B testing for distinct alternatives after stability confirmed. Non-determinism is irreducible — up to 15% accuracy variation across runs with identical inputs due to GPU FP non-associativity plus batch-size variance. Cost is a variable, not constant — a 20% better model can be 3x more expensive per call. Rollback speed is decisive: if rollback requires redeploy, you are too slow. Policy lives in config/flags; model lives in registry with pinned digests; rollback = flip policy + revert threshold + pin old model in seconds.

The problem

In plain words first

Changing the model behind a product is a release, and releases go wrong. Three practices make it safe. Shadow mode sends real requests to the new model as well as the old one, but only the old one's answers reach users; you compare cost, length, errors and refusals with no risk. A canary rollout then sends a small share of real traffic (1%, then 10%, 25% and so on) to the new model, and at each step checks gates: latency, cost per request, error and refusal rate, answer length and user feedback. If any gate fails, you roll back, which should take seconds: a feature flag flips traffic back and the model version is pinned. LLMs add a twist: the same input does not always give the same output, so a gate must allow for normal run-to-run noise.

You ship a new model. Offline evals show 3% accuracy gain. You flip it on in production. Within 24 hours, cost is up 40%, user thumbs-down is up 8%, three customer tickets report "weird answers." You roll back. Redeploy takes 3 hours. Your weekend is ruined.

Every piece of that was avoidable. Shadow mode would have caught the 40% cost spike before any user saw it. Canary would have stopped at 10% when thumbs-down moved. Policy-flag rollback would have taken 30 seconds. The discipline is what fills in the gap between "offline evals look good" and "real users are happy."

Idea 1 · Shadow mode

Candidate receives the same requests as production; outputs are logged, not returned to users. Zero user impact. Log:

  • Output content (diff against production).
  • Token counts (cost delta).
  • Latency.
  • Refusal and error.

Catches: cost blow-ups, length regressions, obvious refusal changes, hard errors. Does NOT catch: quality delta users would perceive. Shadow is a smoke test, not a quality test.

Idea 2 · Canary rollout

Progressive traffic shift with gates. Typical progression: 1% → 10% → 25% → 50% → 75% → 100%. Gate on 5 metrics at each step:

  1. Latency percentiles — P50, P95, P99. Breach: canary has P99 > 1.5x baseline.
  2. Cost per request — blended $. Breach: >20% above baseline.
  3. Error / refusal rate — 5xx plus explicit refusals. Breach: 2x baseline.
  4. Output length distribution — mean + P99. Breach: distributional shift.
  5. User-feedback rate — thumbs-down / ticket filings. Breach: 1.5x baseline.

Idea 3 · Non-determinism is the new variance

Identical inputs produce non-identical outputs. Reasons:

  • GPU FP non-associativity (floating-point reduction order varies by batch).
  • Batch-size variance (same prompt in a batch of 128 vs batch of 16).
  • Sampling (temperature > 0).

Measured: up to 15% accuracy variation run-to-run on identical eval sets. "Stable" in a rollout means metrics are within expected variance, not identical to baseline. Set gates above the noise floor.

Idea 4 · Cost is a variable

A 20% better model can be 3x more expensive per call. Cost/request is one of the five gates. Shipping a "better" model that breaks unit economics is a rollback case.

Idea 5 · Rollback is the weapon

  • Policy flag (feature flag system): flip percentage in config; takes seconds.
  • Model pinning (registry digest): pinned model does not auto-upgrade.
  • Rollback = revert flag + set pinned digest to previous. Seconds, not hours.

If your stack requires redeploy to rollback, fix that before rolling.

Idea 6 · Tooling

Argo Rollouts / Flagger — Kubernetes progressive delivery controllers. Integrate with Istio/Linkerd weighted routing.

Istio weighted routing — service-mesh-level traffic split.

KServe / Seldon Core — model serving with built-in canary.

Feature flags — LaunchDarkly, Flagsmith, Unleash. Policy-level flip, no redeploy.

Idea 7 · Metrics cadence

Canary gates check every 5-15 minutes depending on traffic volume. 1% of 1,000 req/min (10 req/min to the canary) gives 50-150 data points per 5-15 minute window — enough for latency but noisy for user feedback. 10% gives ~10x more. Progressions should pause long enough to accumulate enough samples at each step.

Idea 8 · The A/B step is optional

If the new model is distinctly different (different behavior, different cost curve, different tone), A/B test it at 50% after canary passes. If it's just an improved version of the same behavior, skip to 100% when canary gates pass. Improved means the offline eval showed the gain. The canary gates do not measure task completion, so the skip trusts the eval for it.

Idea 9 · Numbers you should remember

  • Canary progression: 1% → 10% → 25% → 50% → 75% → 100%.
  • Non-determinism ceiling: up to 15% run-to-run variance on identical inputs.
  • Five canary metrics: latency, cost, error/refusal, output length, user feedback.
  • Cost gate: >20% above baseline is a breach.
  • Rollback: seconds, not hours.

Worked example
How much traffic a gate needs

A canary at 1% of 1,000 requests a minute gets 10 requests a minute. The baseline thumbs-down rate is 3%, and you want to detect a rise to 4.5% (1.5×).

  1. In 15 minutes the canary sees 150 requests: about 4.5 thumbs-down expected at baseline and about 6.75 if worse. A difference of two events is noise.
  2. To tell 3% from 4.5% reliably you need roughly 2,500 requests per arm (standard two-proportion test, 80% power, 5% significance): about 4 hours at 1%, or 25 minutes at 10%.
  3. So: gate latency, cost and errors at 1% (plenty of signal), and wait for user-feedback gates until 10–25%.
Check your mental model

Which statements are right?

  • ✓ Shadow mode catches cost and length regressions with no user impact.
  • ✗ Shadow mode tells you whether users will like the answers. It logs outputs no user saw; quality perception needs canary feedback or an A/B test.
  • ✓ A rollback that needs a redeploy is too slow.
  • ✗ A canary metric must match the baseline exactly. LLM outputs vary run to run; set gates above the noise floor.

Part 1 of 3 · Regression, measure_stage

"""Canary rollout simulator — stdlib Python.

Progressively increases candidate traffic share and checks five gates at each
step. Halts when any gate breaches. Supports injected regressions.
"""

from __future__ import annotations

from dataclasses import dataclass
import random


STAGES = [0.01, 0.10, 0.25, 0.50, 0.75, 1.00]

BASELINE = {
    "latency_p99_ms": 900,
    "cost_per_req": 0.02,
    "error_rate": 0.02,
    "output_len_p99": 450,
    "thumbs_down_rate": 0.03,
}

GATES = {
    "latency_p99_ms": 1.5,
    "cost_per_req": 1.2,
    "error_rate": 2.0,
    "output_len_p99": 1.4,
    "thumbs_down_rate": 1.5,
}


@dataclass
class Regression:
    latency_mult: float = 1.0
    cost_mult: float = 1.0
    error_mult: float = 1.0
    output_len_mult: float = 1.0
    thumbs_down_mult: float = 1.0


def measure_stage(stage: float, reg: Regression, seed: int) -> dict:
    rng = random.Random(seed)
    noise = lambda v: v * rng.uniform(0.92, 1.08)
    return {
        "latency_p99_ms": noise(BASELINE["latency_p99_ms"] * reg.latency_mult),
        "cost_per_req": noise(BASELINE["cost_per_req"] * reg.cost_mult),
        "error_rate": noise(BASELINE["error_rate"] * reg.error_mult),
        "output_len_p99": noise(BASELINE["output_len_p99"] * reg.output_len_mult),
        "thumbs_down_rate": noise(BASELINE["thumbs_down_rate"] * reg.thumbs_down_mult),
    }

Part 2 of 3 · check_gates, rollout, stage_seed, main

def check_gates(metrics: dict) -> list[str]:
    breaches = []
    for k, mult in GATES.items():
        if metrics[k] > BASELINE[k] * mult:
            breaches.append(k)
    return breaches


def rollout(name: str, reg: Regression) -> None:
    print(f"\n{name}")
    print(f"Regression: latency={reg.latency_mult}, cost={reg.cost_mult}, error={reg.error_mult}, len={reg.output_len_mult}, thumbs={reg.thumbs_down_mult}")
    for i, stage in enumerate(STAGES):
        metrics = measure_stage(stage, reg, seed=stage_seed(i))
        breaches = check_gates(metrics)
        status = "PASS" if not breaches else f"HALT ({','.join(breaches)})"
        pct = int(stage * 100)
        print(f"  stage {pct:3}%  "
              f"lat_p99={metrics['latency_p99_ms']:5.0f}  "
              f"cost=${metrics['cost_per_req']:.4f}  "
              f"err={metrics['error_rate']*100:4.1f}%  "
              f"thumbs_dn={metrics['thumbs_down_rate']*100:4.1f}%  "
              f"{status}")
        if breaches:
            print(f"  → ROLLBACK (policy flip, pinned model reverted)")
            return
    print("  → PROMOTED to 100%")


def stage_seed(i: int) -> int:
    return 11 + i * 3


def main() -> None:
    print("=" * 95)
    print("CANARY ROLLOUT — six stages, five gates, injected regressions")
    print("=" * 95)

    rollout("Clean promotion", Regression())
    rollout("Small cost regression (10%) — within gate", Regression(cost_mult=1.10))
    rollout("Cost regression 25%", Regression(cost_mult=1.25))
    rollout("Latency regression 80%", Regression(latency_mult=1.80))
    rollout("Thumbs-down regression 60%", Regression(thumbs_down_mult=1.60))
    rollout("Quality silent + cost creep", Regression(cost_mult=1.15, thumbs_down_mult=1.45))

Recap
What to keep from this lesson
  • Shadow first (cost, length, refusals, errors), then canary, then optionally A/B.
  • Canary stages 1% → 10% → 25% → 50% → 75% → 100%, with five gates each.
  • Gate above the noise floor; small stages cannot judge noisy metrics.
  • Rollback must be a flag flip plus a pinned model version: seconds.
  • Cost per request is a gate, not an afterthought.

Given a candidate change (new model, new prompt template, new router policy), baseline production metrics, and risk tolerance, produce a rollout runbook.

Produce:

1. Shadow plan. Duration (24-72 hours). Metrics logged: outputs, token counts, latency, refusal, error. Alert on: >20% cost shift, >30% output length shift, any schema violation.
2. Canary progression. Stages (1% → 10% → 25% → 50% → 75% → 100%). Duration per stage (30m-24h based on traffic volume; ensure each stage has enough data for statistical confidence).
3. Five gates. Specify the exact thresholds for latency P99, cost/request, error/refusal, output-length P99, thumbs-down rate. Set above noise floor (expect 15% irreducible variance).
4. Tooling. Name the rollout controller (Argo Rollouts, Flagger, KServe) and the feature flag system for instant rollback.
5. Rollback path. Document the three actions: flip flag → revert pinned digest → verify. Target time: under 60 seconds end to end.
6. Skip A/B? Justify. Improved-variant changes skip A/B; distinctly different changes (new behavior, new cost curve) require A/B.

Hard rejects:
- Skipping shadow mode. Refuse — cost spikes and length regressions slip past offline eval.
- Gates tighter than 15% variance. Refuse — false alarms will halt legitimate rollouts.
- Rollback that requires redeploy. Refuse — it is not a rollback, it is a damage report.

Refusal rules:
- If the change is safety-critical (e.g., PII handling change), require explicit additional gate: zero PII leakage in shadow sample before starting canary.
- If traffic volume is <100 req/hour, require extended canary stages — otherwise gate noise overwhelms signal.
- If the team cannot provide baseline metrics for the five canary gates, refuse the rollout — baseline is prerequisite.

Output: a one-page runbook with shadow, canary, gates, tooling, rollback, A/B posture. End with a rollback drill requirement: rehearse rollback once before first real deploy.

Solutions

SolutionP1 · Reading the canary runs

The clean and the 10%-cost runs both promote: 10% is inside the 20% cost gate. The 25% cost regression should fail the cost gate at the first stage. Check the later scenarios in the output: each regression should stop at the stage where its metric first crosses its gate, and the earliest stages catch the strongest signals.

SolutionB1 · No cost gate

Cost per request was never gated, so a model that writes longer answers, or costs more per token, sailed through. Shadow mode would have shown it before any user saw the model: logged token counts per request against production, with a cost delta of +60%. Add cost per request (breach above +20%) and output length as gates.

Interview questions

Defend a designYou run a canary for a new model. The team wants a rule that stops the rollout when the canary and the baseline differ on any metric. Design the gates so that they catch a real regression and let a healthy rollout through.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Write each gate as a multiplier above the baseline, never as equality. Gate on five metrics: latency percentiles, cost per request, error and refusal rate, output length distribution and user feedback rate. Put every threshold above the run-to-run variance, which the lesson measured at up to 15 percent on identical inputs, and hold each step long enough to collect the samples the gate needs.

Why equality fails.

Identical inputs produce different outputs. Floating-point reductions on the GPU run in a different order for each batch shape, the batch size changes between runs, and sampling above temperature zero adds its own randomness. The lesson reports up to 15 percent accuracy variation between runs on the same eval set. "Stable" therefore means inside the expected variance, not identical to the baseline.

The five gates.

Metric Breach
Latency P50, P95, P99 canary P99 above 1.5x the baseline
Cost per request more than 20 percent above the baseline
Error and refusal rate 2x the baseline
Output length, mean and P99 a shift in the distribution
User feedback, thumbs-down and tickets 1.5x the baseline

Measure the noise floor first.

Before the canary, run two arms of the same baseline model and record the spread of each metric between them. That spread is the floor. A gate below it halts every rollout, including a good one. The lesson's exercise asks for the multipliers when the eval noise is plus or minus 7 percent, and the answer is a gate above that band.

Hold each step long enough.

The progression runs 1, 10, 25, 50, 75 and 100 percent. Gates check every 5 to 15 minutes. At 1 percent of a load of 1,000 per minute, the canary sees 10 requests per minute, which is 50 to 150 data points per window. That is enough to read latency and errors, but one or two samples decide the P99, so the P99 gate must hold for more than one window. It is too few for user feedback. Each step must pause until the gate has its samples.

Keep the exit cheap.

A halt is only useful when the rollback is fast. Keep the traffic share in a policy flag and the model in a registry with a pinned digest, so that a breach reverts in seconds.

Plausible wrong answers.

  • "Stop on any difference from the baseline." Two runs of the same model differ, so that rule stops every rollout.
  • "Gate on the mean latency." A mean hides the tail. Gate on the percentiles.
  • "Allow zero cost increase." A better model can cost more. The lesson sets the breach at 20 percent, and the product decides whether the gain pays for it.

Follow-ups an interviewer may ask.

  • (level 3) How do you learn the size of the noise before the canary starts? Expected: run two canary arms of the same baseline and record the spread of each metric between them.
  • (level 3) User feedback at the first step is too thin to gate on. What do you do? Expected: gate the early steps on latency, cost, errors and length, and apply the feedback gate from the step that has enough samples.
  • (level 4) A gate fires at one step, and the metric is normal again on the next check. Continue or halt? Expected: halt and look. A gate that flaps sits inside the noise or sees an intermittent regression, and both need a decision before more users see the model.

Estimate itYour service handles 1,000 requests per minute. The canary opens at one percent, and the gate runs every five minutes. About how many data points does one gate check see, and which gates can you trust at this step?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. One percent of the 1,000 per minute is 10 requests per minute to the canary, so a five-minute window holds about 50 points and a fifteen-minute window about 150. That is enough to read latency and error rates, and far too few to read user feedback. Gate the first step on latency, cost, errors and output length, and apply the feedback gate at a later step.

The arithmetic.

The lesson's cadence is a gate check every 5 to 15 minutes, depending on volume. At 1 percent of a 1,000 per minute load, the canary receives 10 requests per minute, which gives 50 to 150 data points per window.

What each gate needs from those points.

Gate At about 50 points
Latency P50 and P95 readable, with a wide band
Latency P99 one or two samples decide it, so hold more than one window
Cost per request every request reports its tokens, so a large shift shows
Error and refusal rate a baseline of a few percent gives a handful of events, so it is noisy
Output length distribution rough, but a large shift shows
User feedback only some users rate an answer, so a window holds a few ratings at most

The next step changes the picture.

At 10 percent the canary sees about ten times more points per window. The feedback gate becomes usable there. This is why the progression pauses at each step: the pause is not a formality, it is the time the gate needs to collect its samples.

Write the dwell rule down.

For each step, state the number of windows that must pass with every gate green before the share rises. A gate that needs two windows to confirm a breach doubles the exposure of a real regression, so write that trade-off next to the rule.

Plausible wrong answers.

  • "One percent is safe, so the gates work at one percent." The share is safe for users, and most gates are blind at that sample size.
  • "Check every minute for faster detection." A one-minute window at this step holds about ten points, which cannot give a percentile.
  • "Start at 25 percent for better statistics." A quarter of the users see the new model before any gate has fired once.

Follow-ups an interviewer may ask.

  • (level 2) At which step does the user feedback gate become usable? Expected: at 10 percent, where the canary sees about ten times more points per window.
  • (level 2) Why does a longer window not fix the first step? Expected: a longer window adds points slowly, and a regression runs for the whole window before the gate can fire.
  • (level 3) Traffic falls to a tenth at night. How does the plan change? Expected: the same share gives about one request per minute, so lengthen the dwell, start at a higher share, or run the ramp during the day.
  • (level 3) A breach must hold for two windows before the gate fires. What does that cost? Expected: a real regression keeps running through both windows until the halt, so the rule trades fewer false alarms for a longer exposure.

Defend a designLast quarter a bad model launch took three hours to undo, because the only way back was a new deployment. You own the release path now. Design it so that the next time, the way back takes seconds. Name the pieces and say what each one holds.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. Separate the policy from the model. Keep the traffic split in a feature flag that a configuration change flips, and keep the model in a registry under a pinned digest that never upgrades on its own. A rollback is then two actions: revert the flag, and point the pin at the previous digest, which also restores the prompt and template version pinned with that model. Nothing is rebuilt and nothing is redeployed.

Two things change in a launch.

  1. The policy. Which share of traffic goes to which model. It lives in a feature-flag system, and a flip takes seconds.
  2. The model. The artifact itself. It lives in a registry with a content digest. A pinned digest does not move when a new build appears.

A deployment couples the two: to change the policy you ship a new build. The lesson's rule is blunt: if your stack needs a redeploy to roll back, fix that before you roll anything out.

The rollback.

Revert the flag, set the pinned digest to the previous one, and restore the gate thresholds that went with it. The lesson puts the whole sequence at seconds, against hours for a redeploy. In its opening story, the redeploy took three hours and the flag flip would have taken 30 seconds.

The same flag runs the canary.

The canary share lives in the same flag: 1, 10, 25, 50, 75 and then 100 percent. A gate breach sets the share back to zero. That makes the halt and the rollback the same mechanism, so the path you rehearse on every rollout is the path you use in an incident.

The tooling shape.

A progressive delivery controller on the cluster shifts weights at the service mesh or the ingress. A model-serving platform can carry the canary split itself. A feature-flag service holds the policy. Pick one of each, and keep the old model deployed until the new one has held at 100 percent through the gates.

Rehearse it.

The lesson's exercise asks for a rollback under 60 seconds end to end. Time it in staging on every release, and treat a slower result as a release blocker.

Plausible wrong answers.

  • "Roll back by redeploying the previous image." A redeploy takes hours, and the lesson's point is to separate the rollback from the deployment.
  • "Delete the old model a day after the launch." The old model must stay available until the canary has held at full traffic through every gate.
  • "A fast rollback makes the gates unnecessary." The gates decide when to roll back. The fast path only limits the damage once they fire.

Follow-ups an interviewer may ask.

  • (level 2) Why pin the model by digest and not by tag? Expected: a tag can move to a new build. A digest is immutable, so the rollback target is exactly the model that ran before.
  • (level 2) What else must revert together with the model? Expected: the gate thresholds, and any prompt or template version that shipped with the model.
  • (level 3) How do you know the path works before you need it? Expected: rehearse it in staging on every release and time it end to end, against a target such as the lesson's 60 seconds.
  • (level 3) The new model needs a new engine image. Does the flag still work? Expected: yes, when both images run side by side and the flag chooses between them. The old deployment stays alive until the new one has held at 100 percent.

Where it is taught. The progressive delivery lesson separates policy flags from model pins and makes the rollback a configuration change.

Take-homeTake-home. You receive a candidate model, a baseline model, and one week of production request logs with the latency, the token counts and the user feedback of each request. Deliver a rollout plan and a simulator that executes it: a shadow phase, a canary ramp with gates, and a rollback. Inject at least two regressions and show where the plan halts for each one. The logs hold user feedback only for the responses that users saw, so state how the simulator produces feedback for the candidate.

Level 4 of 4 · about 60 minutes to answer well.

Short answer. Build a simulator that replays the logs through both models, computes the five gate metrics per step, and advances the ramp only when every gate holds for the required number of windows. Set each threshold above the baseline's own run-to-run variance, which you measure by replaying the baseline against itself. Inject a cost regression and a quality regression, and show the step at which each one halts and the rollback that follows.

What a complete submission contains.

  1. The noise floor. Replay the baseline against itself and report the spread of each metric. This is the floor under every gate.
  2. The gates. Latency percentiles, cost per request, error and refusal rate, output length distribution, and user feedback rate. Write each as a multiplier above the floor. The lesson's defaults are a P99 above 1.5x, a cost more than 20 percent above the baseline, errors at 2x, a shift in the length distribution, and feedback at 1.5x.
  3. The shadow phase. The candidate sees every request and returns nothing to a user. Report the cost delta, the length distribution, the refusals and the hard errors against the baseline.
  4. The ramp. Steps at 1, 10, 25, 50, 75 and 100 percent. Compute the dwell at each step from the samples per window, so that a gate never decides on a handful of points.
  5. The rollback. Model it as the lesson describes: a flag back to zero and a pin on the previous digest. The simulator shows the step and the time it takes.
  6. Two regressions. The lesson's exercise injects a 25 percent cost regression, and a strong submission shows it halting at the first step. The second regression lives only in the feedback metric, and the submission shows that it stays invisible at the first step and halts only where the sample is large enough.
  7. A written decision. The lesson's second exercise: a candidate with a 3 percent accuracy gain and a cost 18 percent above the baseline. Write both policy paths, ship and do not ship, and name who decides.

What the reviewer looks for.

  • The floor is measured, not assumed.
  • The gates are multipliers, and the thresholds sit above the floor.
  • The dwell is computed from samples, not from the clock.
  • The regression that the first step cannot see is shown, not hidden.
  • The rollback is rehearsed inside the simulation.

What to keep for production.

The gate evaluation code and the noise-floor measurement become the checks of the real canary controller. The replay harness becomes the pre-release test for every future candidate.

Plausible wrong answers.

  • "Use the lesson's thresholds as they are." The lesson's numbers are defaults. The floor comes from your own baseline.
  • "Advance the ramp on a fixed schedule." A ramp that moves on the clock ignores whether a gate had enough samples.
  • "Model the rollback as a redeploy." The simulator should model the mechanism you will use, and a redeploy is the mechanism the lesson tells you to remove.

Follow-ups an interviewer may ask.

  • (level 3) The feedback regression was caught late. Is the plan wrong? Expected: no. It shows the limit of the feedback gate, and the fix is a longer dwell at the step where feedback first has samples, or a proxy metric with more volume.
  • (level 4) The candidate has the same cost and tone as the baseline. What changes in the plan? Expected: skip the A/B step after the canary, which the lesson makes optional for an improved version of the same behavior.
  • (level 4) What from the simulator survives into production? Expected: the gate evaluation code and the noise-floor measurement, which become the canary controller's checks.

Where it is taught. The progressive delivery lesson gives the gates, the ramp and the exercises that this take-home extends.

Explain the mechanismA teammate wants to skip the canary. The new model ran in shadow for a week with no errors and a flat bill, so they call it proven. What does that week show, and what does it leave open?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. Shadow mode copies the production requests to the candidate and logs its outputs, and no user sees them. It shows that the candidate does not crash, does not refuse more often, does not cost more and does not write longer answers. It cannot show that users prefer the answers, because no user read one. Shadow is a smoke test, and the canary is the first quality test.

What shadow records.

For each request, the candidate output is logged next to the production output:

  • the output text, as a diff against production;
  • the token counts, which give the cost delta;
  • the latency;
  • refusals and hard errors.

What it catches.

Cost blow-ups, length regressions, a change in the refusal rate and hard errors. These are the failures that make a launch expensive or embarrassing, and shadow finds them with zero user impact.

What it misses.

A quality change that a user would notice. The candidate output never reaches a person, so there is no thumbs-down, no ticket and no retention signal. A model that gives shorter, cheaper and wrong answers passes shadow.

What comes next.

A canary exposes a growing share of users to the candidate, with a gate at each step. The lesson gates on five metrics: latency percentiles, cost per request, error and refusal rate, the output length distribution, and the user feedback rate. The progression runs from 1 percent to 10, 25, 50, 75 and 100 percent. The first user feedback appears here, not in shadow.

Plausible wrong answers.

  • "Shadow passed, so the quality is fine." Shadow has no user, so it measures cost, length, errors and refusals only.
  • "Shadow is a canary at zero percent." A canary returns the candidate output to real users and gates on their feedback. Shadow never returns an output to a user.
  • "A week in shadow replaces the offline eval." The eval judges correctness on a labeled set. Shadow records behavior on live traffic. They answer different questions.

Follow-ups an interviewer may ask.

  • (level 1) Which signal does shadow give that an offline eval does not? Expected: the behavior of the candidate on the real request mix, including cost and output length per request.
  • (level 2) Shadow shows the cost per request is 40 percent above production. What do you do? Expected: stop before any canary. A cost more than 20 percent above the baseline is a gate breach, and a model that breaks the unit economics is a rollback case.
  • (level 2) Why can shadow not measure user feedback? Expected: no user sees the candidate output, so there is nothing for a user to rate or report.
  • (level 3) Shadow doubles the load on your model service. How do you keep it affordable? Expected: send a fixed share of requests to the candidate instead of all of them, and log the same metrics for that share.

Where it is taught. The progressive delivery lesson defines shadow mode, the five canary gates and the rollback path.
