About the model on this page
The model on this page is a labeled stand-in

FakeAnthropic (Lesson 14.56's appendix) streams in the documented event format. Here it is slowed down on purpose, 0.1 seconds per piece of text, so the timing difference is visible; real models are usually faster per token, with replies hundreds of tokens long. The real thing runs the real SDK.

Why this came about

Long answers take seconds to generate, and waiting for the whole thing felt broken to users. Chat products popularized showing text as it is written, using a long-standing web technique (server-sent events). Agents later made streaming more important still, because users need to see progress across many steps.

The problem: the customer stares at nothing

A model writes its reply one token at a time (Lesson 11.18). Without streaming, your code waits for the last token before it can show the first:

import time
from fake_claude import FakeAnthropic          # the labeled stand-in (Lesson 3.1's appendix)

MODEL = "claude-sonnet-5-5"
SYSTEM = "You are ShopKart support. Refunds reach UPI in 2 days and cards in 5 to 7 business days."
client = FakeAnthropic(seconds_per_piece=0.1)   # stand-in only: each piece of text takes 0.1 s, like a slow model
ASK = [{"role": "user", "content": "How long does a UPI refund take?"}]

start = time.perf_counter()
r = client.messages.create(model=MODEL, max_tokens=300, system=SYSTEM, messages=ASK)
print(f"no streaming: nothing to show for {time.perf_counter() - start:.1f} s, then the whole reply")
What you should see
no streaming: nothing to show for 0.7 s, then the whole reply

For a long reply from a real model, that wait is several seconds, and people abandon a chat that looks frozen. The text existed for most of that time; it was just not sent.

In plain words first
Watching someone type

Without streaming, the user stares at nothing until the whole answer is ready. With streaming, the provider sends the answer in small pieces as it is generated, so text appears word by word. Technically, the reply arrives as a series of events over one HTTP connection (server-sent events): a start event, many small text pieces, then an end event with the stop reason and token counts. Your code must assemble the pieces and handle a stream that breaks halfway.

Idea 1 · Stream the text as it is written

A normal call returns nothing until the whole reply is ready. A streaming call hands you the text in small pieces as the model produces them. The code prints each piece followed by a |, so you can see where the pieces fall, and records how long the first piece took to arrive compared with the last:

start, first = time.perf_counter(), None
with client.messages.stream(model=MODEL, max_tokens=300, system=SYSTEM, messages=ASK) as stream:
    for text in stream.text_stream:
        first = first or time.perf_counter() - start
        print(text, end="|", flush=True)                 # | marks where one piece ends
print()
print(f"streaming: first words after {first:.1f} s, last after {time.perf_counter() - start:.1f} s")
What you should see
Refunds reach |UPI in |2 days |and cards |in 5 |to 7 |business days.|
streaming: first words after 0.1 s, last after 0.7 s

The whole reply took the same time, but the customer saw the first words after a tenth of the time. That gap, time to first token against total time, is what streaming buys, and it is the number to watch in production (Lesson 14.145). messages.stream is the SDK's helper: text_stream yields only the text, and get_final_message() returns the complete message, with stop_reason and usage, once the stream ends, so you never have to rebuild it yourself.

Idea 2 · What actually arrives: server-sent events

Under the helper, the API sends a sequence of server-sent events. With a tool available, the sequence shows every part of Lesson 14.56's tool calllater · 14.56 arriving in pieces:

TOOLS = [{"name": "get_order_status", "description": "Look up a ShopKart order by ID, like SK-1042.",
          "input_schema": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}]
fast = FakeAnthropic()
events = fast.messages.create(model=MODEL, max_tokens=300, system=SYSTEM, tools=TOOLS, stream=True,
                              messages=[{"role": "user", "content": "Where is my order SK-1042?"}])
for e in events:
    detail = {"content_block_delta": lambda: repr(getattr(e.delta, "text", None) or e.delta.partial_json),
              "content_block_start": lambda: e.content_block.type,
              "message_delta": lambda: e.delta.stop_reason}.get(e.type, lambda: "")()
    print(f"{e.type:20} {detail}")
What you should see
message_start        
content_block_start  text
content_block_delta  'Let me '
content_block_delta  'check that '
content_block_delta  'for you.'
content_block_stop   
content_block_start  tool_use
content_block_delta  '{"order_id":'
content_block_delta  ' "SK-1042"}'

The order is always the same: message_start (with input usage), then for each content block a content_block_start, its deltas and a content_block_stop, then message_delta with the stop reason and output usage, then message_stop. Text arrives as text_delta pieces, and a tool call's arguments arrive as input_json_delta pieces of a JSON string that is only valid once the block is complete. The stream can also contain ping events and an error event. OpenAI's Responses API streams typed events too, such as response.output_text.delta, response.function_call_arguments.delta and response.completed.

Idea 3 · When the stream breaks part-way

A stream can fail after it started, for example with an overload error (HTTP 529 on Anthropic) or a dropped connection:

from fake_claude import OverloadedError

flaky = FakeAnthropic(stream_fails_after=3)          # stand-in only: the connection drops after three pieces
shown = ""
try:
    with flaky.messages.stream(model=MODEL, max_tokens=300, system=SYSTEM, messages=ASK) as stream:
        for text in stream.text_stream:
            shown += text
except OverloadedError as e:
    print("failed after showing:", repr(shown))
    print("error:", e)
What you should see
failed after showing: 'Refunds reach UPI in 2 days '
error: Overloaded (529) part-way through the stream

The customer has already seen "Refunds reach UPI in 2 days", and the rest never came. The SDK's automatic retries (Lesson 14.59) cover failures before a response starts, not a stream that breaks in the middle, so this is your code's job. You cannot resume a stream where it stopped; start the request again, and tell the interface to clear what it showed:

def stream_answer(client, messages, retries=1):
    """Stream a reply; if the stream breaks, start the reply again and say so."""
    for attempt in range(retries + 1):
        shown = ""
        try:
            with client.messages.stream(model=MODEL, max_tokens=300, system=SYSTEM, messages=messages) as stream:
                for text in stream.text_stream:
                    shown += text
                final = stream.get_final_message()
            return shown, final.stop_reason, attempt
        except OverloadedError:
            print(f"  attempt {attempt + 1} broke after {len(shown)} characters; the UI clears them and retries")
    return "Sorry, something went wrong. Please try again.", "error", attempt

flaky = FakeAnthropic(stream_fails_after=3)          # stand-in only: the first stream breaks, a retry works
print(stream_answer(flaky, ASK))
What you should see
  attempt 1 broke after 28 characters; the UI clears them and retries
('Refunds reach UPI in 2 days and cards in 5 to 7 business days.', 'end_turn', 1)

Measure it

Without streaming With streaming
Time until the customer sees text The whole generation time (0.7 s here) About one piece (0.1 s here)
Total time The same The same
Tokens and cost The same The same
Code One call, one result Events, partial state, mid-stream errors

Streaming changes how fast the reply feels, not how fast it is or what it costs. When is it no benefit? When no person is waiting: batch jobs, background agents, a classifier whose output feeds code (Lesson 11.21). There it only adds complexity, so use a plain call.

In production
Streaming in production
  • Buffering: proxies and load balancers often buffer responses, so a stream that works locally arrives in one lump behind nginx or an API gateway. Disable buffering for the streaming route and test through the real path.
  • Guardrailslater · 15.23: checks that need the full answer cannot run until generation ends. Either stream and retract (risky for regulated content) or check sentence by sentence.
  • Logging: log the final assembled message and its usage, not the deltas, so traceslater · 14.57 stay readable.
  • Steps after the model: any processing step that needs the whole text stops the stream; LangChainlater · 14.93's version of this bug is in Lesson 14.94.

The real thing

The same request through the real SDK. It ran against the local test server described in Lesson 14.56, which sends the documented event stream:

import anthropic

client = anthropic.Anthropic()                         # reads ANTHROPIC_API_KEY from the environment
with client.messages.stream(model=MODEL, max_tokens=300, system=SYSTEM, messages=ASK) as stream:
    for text in stream.text_stream:
        print(text, end="|", flush=True)
    final = stream.get_final_message()
print()
print(final.stop_reason, "|", final.usage.input_tokens, "in,", final.usage.output_tokens, "out")
What you should see
Refunds reach |UPI in |2 days |and cards |in 5 |to 7 |business days.|
end_turn | 40 in, 15 out

With a real model, pieces are a few characters to a few words, and their number and timing vary. In OpenAI's SDK, client.responses.create(..., stream=True) returns the events, and client.responses.stream(...) gives a helper similar to Anthropic's.

Debugging exercise
Debugging exercise: tool arguments that will not parse

A teammate shows "Looking up order …" in the UI as soon as a tool call starts streaming, by parsing the arguments as they arrive:

import json
events = fast.messages.create(model=MODEL, max_tokens=300, system=SYSTEM, tools=TOOLS, stream=True,
                              messages=[{"role": "user", "content": "Where is my order SK-1042?"}])
try:
    for e in events:
        if e.type == "content_block_delta" and e.delta.type == "input_json_delta":
            args = json.loads(e.delta.partial_json)          # the bug is on this line
            print("tool input:", args)
except json.JSONDecodeError as err:
    print("JSONDecodeError:", err)

Explain the error, and fix it. (Solution D1.)

Make it your own

Write stream_answer, which streams a reply and, if the stream breaks, starts again once and returns the full text, the stop reason and how many retries it needed. (Solution M1.)

Solutions

SolutionP1 · First token against last

With streaming, about 0.5 seconds: the first token. Without it, about 0.5 + 600 × 0.015 = 9.5 seconds. Same total, very different experience. That is why chat interfaces stream, and why time to first token is a separate service level from total latency.

SolutionB1 · A stream is read once

The second loop prints nothing: the pieces were consumed by the first loop, like any iterator. The SDK keeps what it received, so call stream.get_final_message() (or stream.get_final_text()) after the loop for the complete message. If two parts of your code need the pieces, fan them out from one loop.

SolutionD1 · Partial JSON is not JSON

Tool arguments stream as pieces of one JSON string, and '{"order_id":' is not valid JSON on its own, so the first json.loads fails. Collect the pieces per content block and parse when the block's content_block_stop arrives (or use get_final_message()):

events = fast.messages.create(model=MODEL, max_tokens=300, system=SYSTEM, tools=TOOLS, stream=True,
                              messages=[{"role": "user", "content": "Where is my order SK-1042?"}])
parts = {}
for e in events:
    if e.type == "content_block_delta" and e.delta.type == "input_json_delta":
        parts[e.index] = parts.get(e.index, "") + e.delta.partial_json      # collect the pieces of each block
    if e.type == "content_block_stop" and e.index in parts:
        print("tool input:", json.loads(parts[e.index]))                     # parse once the block is complete

tool input: {'order_id': 'SK-1042'}

To show progress earlier, show the tool's name from content_block_start, which arrives first, and the arguments once they are complete.

Check your understanding

Explain the mechanismHow does LLM response streaming work, and what does it improve?

Worked answer. The API keeps the HTTP response open and sends server-sent events as the model generates: a start event with input usage, then per content block a start, deltas and a stop, then a final delta with the stop reason and output usage. Text arrives as text deltas; tool arguments arrive as pieces of a JSON string. It improves time to first token, so people see progress immediately, but not total latency or cost. The client assembles the final message, which the SDK helpers do for you.

A plausible wrong answer. "Streaming makes the model generate faster." Generation speed is the same; the client just stops waiting for the end.

Follow-ups. What happens to usage reporting when you stream (Lesson 14.93's stream_usage gotcha)?

Debug a failureStreaming works locally, but in production users see the whole answer appear at once. What do you check?

Worked answer. Something between the model and the browser is buffering. I would compare timestamps of events leaving the service with their arrival in the browser. Usual causes: a reverse proxy or load balancer buffering responses (nginx needs buffering off for the route), a framework that collects the response before sending, compression that waits for enough data, or a processing step after the model that needs the full text. Fix the layer, and add a synthetic check that measures time to first byte through the real path.

A plausible wrong answer. "The model stopped streaming." The API still streams; the deployment path collects it.

Follow-ups. How would you stream through a serverless platform that buffers responses?

Defend a designShould every model call in an application be streamed?

Worked answer. No. Stream when a person is waiting for the text: chat replies and long generated answers. Do not stream when code consumes the result, such as classification, extraction with a schema, or background jobs: there it adds event handling, partial state and mid-stream error handling for no benefit. In agents, stream the final answer's tokens and show progress events for the tool steps before it (Lesson 14.61).

A plausible wrong answer. "Yes, it is always faster." It is never faster in total; it only shows text sooner.

Follow-ups. How do you run an output guardrail on a streamed answer?
