Why this came about

Every application that used tools wrote its own glue to describe them, send them and parse the calls, differently for each provider. LangChain's tool abstraction and bind_tools unified that, generating the schema from your function and normalizing tool calls across providers.

The problem: the same tool plumbing, again

In Lesson 14.58 you wrote schema_from to build a JSON Schema from a function's signature, a registry so the loop could find a tool by name, validation for the model's arguments, and code to turn errors into results. LangChain's tools do all of that. This lesson maps each piece you wrote to the piece LangChain gives you, so that when an agent misbehaves later you know which layer to look at.

In plain words first
Wrapping a function so a model can ask for it

A model cannot run your functions; it can only ask for them by name, with arguments that match a description it was given. A LangChain tool is your Python function plus that description, built automatically from its name, docstring and type hints. You then give the tools to a model, read its requests, run them and send the results back: Lesson 14.56's round trip, with the plumbing done for you.

Idea 1 · A function becomes a tool

Start with an ordinary Python function that looks up an order. One line above it, @tool, turns it into a tool: the same function, plus a name, a description and a schema that a model can read. Then inspect what the decorator produced.

from langchain.tools import tool

ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

print(type(get_order_status).__name__, "|", get_order_status.name, "|", get_order_status.description)
print(get_order_status.args)
What you should see
StructuredTool | get_order_status | Return the shipping status for a ShopKart order ID like 'A-1001'.
{'order_id': {'title': 'Order Id', 'type': 'string'}}

The @tool decorator read the function's name, docstring and type hints. The docstring is not decoration: it is the tool's description, and the model chooses tools by reading descriptions (Lesson 14.58).

Reading this output
  • StructuredTool is the class LangChain wrapped your function in; you can still call it, with invoke.
  • .args is the JSON Schema of the tool's inputs (Lesson 0.23 explains JSON Schema), and it prints only the per-argument part: one entry per argument.
  • 'type': 'string' came from the hint order_id: str. 'title': 'Order Id' is a label Pydantic made from the argument's name; you did not write it, and it does not help the model.
  • The return type, -> str, is not there. A tool schema describes what the model must send, never what comes back.

This is exactly what goes to the provider, in OpenAI's format:

import json
from langchain_core.utils.function_calling import convert_to_openai_tool

What you should see

  "name": "get_order_status",

langchain-anthropic sends the same information in Claude's format (name, description, input_schema). When an agent picks the wrong tool, this printout is the first thing to read.

Compared with .args, the title labels are gone (LangChain strips them) and required has appeared.

Idea 2 · Bind, call, read the tool calls

bind_tools returns a model that sends the tool definitions with every request:

with_tools = chat.bind_tools([get_order_status])
ai = with_tools.invoke("Where are A-1001 and A-1002?")
print("content:", repr(ai.content), "| finish:", ai.response_metadata["finish_reason"])
for call in ai.tool_calls:
    print({k: call[k] for k in ("name", "args")}, "id:", call["id"][:5] + "…")
What you should see
content: '' | finish: tool_calls
{'name': 'get_order_status', 'args': {'order_id': 'A-1001'}} id: call_…
{'name': 'get_order_status', 'args': {'order_id': 'A-1002'}} id: call_…

The reply has no text and two tool calls, in parallel, one per order. Each tool call's id was made by the provider for that one request; you must return it with the result. LangChain normalizes them across providers: each is a dictionary with name, args (already parsed, even on OpenAI where the wire format is a JSON string) and id. Compare Lesson 14.56, where you read tool_use blocks on Claude and function_call items on OpenAI separately.

Idea 3 · Run the tools and send the results back

A tool invoked with a whole tool call returns a ToolMessage already matched to the call's ID:

from langchain_core.messages import HumanMessage

messages = [HumanMessage("Where are A-1001 and A-1002?"), ai]
for call in ai.tool_calls:
    result = get_order_status.invoke(call)                 # a tool call in, a ToolMessage out
    messages.append(result)
    print(type(result).__name__, "|", result.content, "| matches call:", result.tool_call_id == call["id"])

final = with_tools.invoke(messages)
print("final:", final.content)
What you should see
ToolMessage | A-1001 is shipped | matches call: True
ToolMessage | A-1002 is processing | matches call: True
final: Here is what I found: A-1001 is shipped; A-1002 is processing

That is the complete round trip from Lesson 14.56: the user's message, the model's turn with its tool calls, one ToolMessage per call, then the model's answer. The rule you learned there still holds: every tool call must get a result, matched by ID, before the next request. Lesson 14.96's agent runs this loop for you.

Idea 4 · When tools fail, and when arguments are wrong

A tool can fail for reasons the model can do something about. Raise ToolException for those, and let the tool turn it into a result:

from langchain_core.tools import ToolException

@tool
def cancel_order(order_id: str) -> str:
    """Cancel a ShopKart order that has not shipped yet."""
    if ORDERS.get(order_id) == "shipped":
        raise ToolException(f"{order_id} has already shipped; offer a return instead")
    return f"{order_id} cancelled"

try:
    cancel_order.invoke({"order_id": "A-1001"})
except ToolException as e:
    print("raised:", e)

cancel_order.handle_tool_error = True                      # turn the exception into a result the model can read
print("returned:", cancel_order.invoke({"order_id": "A-1001"}))
What you should see
raised: A-1001 has already shipped; offer a return instead
returned: A-1001 has already shipped; offer a return instead

The first call raised the exception, which would stop an agent. With handle_tool_error=True, the same failure comes back as the tool's result, so the model can read it and offer a return instead (Lesson 14.58's errors-as-results rule). You can also pass a string, or a function that formats the error.

Arguments need checking too. A Pydantic model as args_schema puts constraints in the schema the model sees, and validates the arguments before your function runs:

from pydantic import BaseModel, Field, ValidationError

class RefundArgs(BaseModel):
    order_id: str = Field(pattern=r"^[A-Z]-\d{4}$", description="An order ID like 'A-1001'")
    amount: int = Field(gt=0, le=50000, description="Refund amount in rupees")

@tool(args_schema=RefundArgs)
def issue_refund(order_id: str, amount: int) -> str:
    """Refund part or all of an order to the original payment method."""
    return f"Refunded INR {amount:,} for {order_id}"

print(issue_refund.invoke({"order_id": "A-1002", "amount": 1200}))
try:
    issue_refund.invoke({"order_id": "1002", "amount": 90000})
except ValidationError as e:
    print([f"{err['loc'][0]}: {err['msg']}" for err in e.errors()])
What you should see
Refunded INR 1,200 for A-1002
["order_id: String should match pattern '^[A-Z]-\\d{4}$'", 'amount: Input should be less than or equal to 50000']

Your function never ran with a bad ID or an out-of-range amount. Validation errors raise by default; handle_validation_error turns them into results, which the modify exercise uses.

One class did two jobs. Print what the model is told about issue_refund:

for name, spec in issue_refund.args.items():
    print(name, "→", spec)
What you should see
order_id → {'description': "An order ID like 'A-1001'", 'pattern': '^[A-Z]-\\d{4}$', 'title': 'Order Id', 'type': 'string'}
amount → {'description': 'Refund amount in rupees', 'exclusiveMinimum': 0, 'maximum': 50000, 'title': 'Amount', 'type': 'integer'}
Reading this output

You wrote two fields; Pydantic produced every key you see, by fixed rules:

You wrote Became The model uses it?
order_id: str 'type': 'string' Yes: send text
pattern=r"^[A-Z]-\d{4}$" 'pattern': ... Yes: the shape of a valid ID
amount: int, gt=0, le=50000 'type': 'integer', 'exclusiveMinimum': 0, 'maximum': 50000 Yes: whole numbers in range
description="..." 'description': ... Yes, most of all: your instruction for the field
The field names 'title': 'Order Id', 'title': 'Amount' No: labels, removed before sending

Literal["a", "b"] would become 'enum': ['a', 'b']. The same rules steer the model (they are in the schema it reads) and check its arguments (Pydantic rejected the bad call above). The refund confirmation the tool returns appears nowhere in this schema: describe results in the docstring if the model needs to know.

Idea 5 · Typed output from a model

with_structured_output is Lesson 11.21's idea in LangChain: give a schema, get a validated object back.

from typing import Literal

class Triage(BaseModel):
    category: Literal["refund", "delivery", "cancellation", "other"]
    urgent: bool = Field(description="True if the customer is blocked or angry")

triager = chat.with_structured_output(Triage)
print(repr(triager.invoke("I want a refund for my broken mixer")))

raw = chat.with_structured_output(Triage, include_raw=True).invoke("I want a refund for my broken mixer")
print(sorted(raw), "| parsing_error:", raw["parsing_error"])
What you should see
Triage(category='refund', urgent=False)
['parsed', 'parsing_error', 'raw'] | parsing_error: None

On ChatOpenAI it uses the provider's native structured output by default (method="json_schema"); method="function_calling" uses a forced tool call instead, for models without native support. include_raw=True returns the raw message and any parsing error instead of raising, which is what you want in production, where you log failures and decide what to do. In an agent, the same idea is response_format (Lesson 14.96).

In an agent: three strategies, and how each one fails

When you give create_agent a schema as response_format, it gets the object from the model in one of three ways, from langchain.agents.structured_output:

Strategy How it asks When it fails
ToolStrategy(Schema) Adds one tool per schema and forces a tool call; parses the tool's arguments On a parse error it sends the error back and asks again, with no attempt limit. If the model keeps answering in plain text, the run can loop until the recursion limitlater · 14.96
ProviderStrategy(Schema) Sends the schema as the provider's native response_format, and parses the JSON reply One attempt: bad JSON or a provider that rejects the schema raises. A Union of schemas is refused when the agent is built
AutoStrategy (a bare schema) Chooses before each model call: ProviderStrategy when the model's profile says structured_output is supported (or the model name is on a known list), ToolStrategy otherwise As whichever strategy it chose; a failure never switches strategy mid-run

So the same agent code can behave differently on two providers: the bare schema resolved to a different strategy. In production, choose explicitly, set a recursion limit you can afford for ToolStrategy, and catch the error from ProviderStrategy. Small models are the weak spot: the AI Engineering from Scratch LangChain manual found a 4-billion-parameter local model returned no object from ToolStrategy in 39 of 39 tasks, while a plain extraction call with with_structured_output did as well as the best strategy on every model it tried. When the agent does not need tools for the final step, a separate extraction call is often the most reliable design.

Check your mental model
  • ✗ "The model reads my function to learn its arguments."
    ✓ It reads the name, the docstring and the JSON Schema built from the hints or args_schema.
  • ✗ ".args describes inputs and outputs."
    ✓ Inputs only. The output exists only when the tool runs.
  • ✗ "I must write title and type."
    ✓ Pydantic generates them; you write names, Python types and Field(...) rules.
  • ✗ "Constraints in the schema are only hints."
    ✓ They are sent to the model and enforced by Pydantic before the function runs.

messages = [HumanMessage("Where is A-1001?")]

Make it your own

Write cancel_checked, a version of cancel_order whose order_id must match ^[A-Z]-\d{4}$, and which answers a malformed ID with a message the model can pass to the customer instead of raising. (Solution M1.)

Solutions

SolutionP1 · Constraints in the schema

The tool's parameters include "amount": {"type": "integer", "exclusiveMinimum": 0, "maximum": 50000, "description": "Refund amount in rupees"}. The model reads the schema, so constraints there make a correct call more likely in the first place; your validation is the backstop. Some providers' strict modes do not support every keyword (Lesson 11.21), which is another reason to keep the check in code.

SolutionB1 · No description, no reliable choice

The description is how the model decides when to call the tool. A tool without one would be called at random or never, and the failure would show up much later as a wrong answer. Refusing at definition time makes the mistake impossible to ship. Pass description= explicitly if you cannot add a docstring.

SolutionD1 · A string is not a tool result

get_order_status.invoke(call["args"]) passes only the arguments, so the tool returns its plain string, not a ToolMessage. A string in a message list is read as a human message, so the model saw a user saying "A-1001 is shipped", with no result for its tool call. The lab rig saw an order ID in a user message and asked again. A real OpenAI model rejects the request, because an assistant message with tool calls must be followed by a tool message for each call (Claude has the same rule, Lesson 14.56). Invoke the tool with the whole call:

messages = [HumanMessage("Where is A-1001?")]
ai = with_tools.invoke(messages)
messages += [ai] + [get_order_status.invoke(call) for call in ai.tool_calls]
print([type(m).__name__ for m in messages])
print("second reply:", with_tools.invoke(messages).content)

['HumanMessage', 'AIMessage', 'ToolMessage']
second reply: Here is what I found: A-1001 is shipped
SolutionM1 · Validation errors as results
class CancelArgs(BaseModel):
    order_id: str = Field(pattern=r"^[A-Z]-\d{4}$", description="An order ID like 'A-1001'")

@tool(args_schema=CancelArgs)
def cancel_checked(order_id: str) -> str:
    """Cancel a ShopKart order that has not shipped yet."""
    return cancel_order.invoke({"order_id": order_id})

cancel_checked.handle_validation_error = lambda e: "order_id must look like 'A-1001'; ask the customer for it"
print(cancel_checked.invoke({"order_id": "1002"}))
print(cancel_checked.invoke({"order_id": "A-1002"}))
print(cancel_checked.invoke({"order_id": "A-1001"}))

order_id must look like 'A-1001'; ask the customer for it
A-1002 cancelled
A-1001 has already shipped; offer a return instead

Three cases, three outcomes: a malformed ID becomes a message the model can act on, a valid one cancels, and a business-rule failure comes back from cancel_order's ToolException. In an agent, all three reach the model as results instead of stopping the run.

Check your understanding

Explain the mechanismHow does a LangChain tool get from a Python function to the model, and back?

Worked answer. @tool builds a schema from the function's name, docstring and type hints, or from an args_schema Pydantic model. bind_tools sends those definitions, in the provider's format, with each request. The model replies with tool calls, which LangChain normalizes into AIMessage.tool_calls with a name, parsed arguments and an ID. Invoking the tool with a call validates the arguments, runs the function and returns a ToolMessage carrying the call's ID, and that message goes back in the history for the next request.

A plausible wrong answer. "The model runs the Python function." The model only asks; your process runs the function and sends the result back.

Follow-ups. What happens if one of two parallel tool calls gets no ToolMessage?

Debug a failureAn agent calls the right tool with a wrong argument format about one time in ten. What do you do?

Worked answer. Read the schema the model actually receives (convert_to_openai_tool), and check that the description and the field descriptions say what a valid value looks like, with an example. Add the constraint to the schema, such as a pattern for IDs, and turn on the provider's strict mode if it supports that schema. Keep validation in the tool, return the validation error as a result so the model can retry, and measure the retry rate on a set of real questions before and after.

A plausible wrong answer. "Lower the temperature." It may reduce variety, but it does not tell the model what a valid argument is.

Follow-ups. When would you normalize the argument in code instead of rejecting it?

Defend a designShould tool errors raise, or be returned to the model?

Worked answer. Return errors the model can act on: not found, already shipped, a malformed argument, a rate limit with a retry time. Raise errors that mean the system is broken or the action is unsafe to retry blindly: a missing credential, an unknown internal failure, a refused approval that a person must see. The model can recover from the first kind; the second kind should stop the run and alert someone, because a model retrying against a broken system wastes money and can repeat side effects.

A plausible wrong answer. "Always return errors, so the agent never crashes." An agent that never stops can loop on a broken dependency and hide an outage.

Follow-ups. How would you make a tool with side effects safe to retry (Lesson 14.59)?
