In plain words first
The idea in one line

"Ask the model nicely to return JSON" fails some of the time, and far more often on small models. Structured outputs close that gap with constrained decoding: the model is literally prevented from emitting a token that would violate the schema. OpenAI's strict mode, Anthropic's schema-typed tool use, Gemini's responseSchema, Pydantic AI's output_type, and Zod's .parse are five surface forms of the same idea. This lesson builds the schema validator and the strict-mode contract learners will use for every production

The problem

In plain words first

Programs need data in an exact shape: a field called quantity holding a number, priority being one of three words, and nothing else. Asking a model to "reply in JSON" usually works, but sometimes the model adds a sentence, wraps the JSON in code fences, or invents a field. Structured outputs fix the shape at the source. While the model generates, the decoder only allows tokens that keep the output valid for a JSON Schema, so the result always parses and always fits. This is constrained decoding. It guarantees the format, not the truth: the values can still be wrong. This lesson describes schemas, Pydantic models, refusals and retries. It then runs a real 0.5B model with and without a schema constraint on eight emails, and looks inside the constraint to see which tokens it allows at each step. No model is trained.

An agent reading a purchase-order email needs to turn free text into {customer, line_items, total_usd}. Three approaches.

Approach one: prompt for JSON. "Reply in JSON with fields customer, line_items, total_usd." Works most of the time on frontier models, much less on small ones. Fails in six ways: missing brace, trailing comma, wrong types, hallucinated fields, truncated at token limit, leaked prose or code fences around the JSON (the run below shows the last one on every email).

Approach two: validate after generation. Generate freely, parse, validate against schema, retry on failure. Reliable but expensive — you pay for every retry, and truncation bugs cost one extra turn per occurrence.

Approach three: constrained decoding. The provider enforces the schema at decode time. Invalid tokens are masked out of the sampling distribution. The output is guaranteed to parse and guaranteed to validate. Failure collapses to one mode: refusal (the model decides the input does not fit the schema).

Every 2026 frontier provider ships some form of approach three.

  • OpenAI. response_format: {type: "json_schema", strict: true} plus refusal in the response if the model declines.
  • Anthropic. output_config.format with type: "json_schema" constrains the reply to a schema, and strict: true on a tool constrains its inputs. A declined request ends with stop_reason: "refusal".
  • Gemini. responseMimeType: "application/json" with responseSchema (or responseJsonSchema for plain JSON Schema) at request level.
  • Pydantic AI. output_type=InvoiceModel makes the run result's .output an InvoiceModel instance, using the provider's structured output or a tool call under the hood.
  • Zod (TypeScript). Runtime parser that validates provider output against a Zod schema; OpenAI's Node SDK turns a Zod schema into a response format with zodResponseFormat and parses the reply with .parse().

The common thread: declare the schema once, enforce it end to end.

Idea 1 · JSON Schema 2020-12 — the lingua franca

Every provider accepts JSON Schema 2020-12. The constructs you use most:

  • type: one of object, array, string, number, integer, boolean, null.
  • properties: map of field name to subschema.
  • required: list of field names that must appear.
  • enum: closed set of allowed values.
  • minimum / maximum (numbers), minLength / maxLength / pattern (strings).
  • items: subschema applied to every array element.
  • additionalProperties: false forbids extra fields (default varies by mode).

OpenAI strict mode adds requirements: every property must be listed in required, additionalProperties: false on every object, and an object (not anyOf) at the root; $defs and $ref are fine. If you break these, the API returns 400 at request time. Anthropic's structured outputs likewise need additionalProperties: false and do not enforce minimum, maximum, minLength or maxLength; the SDK helpers move those into descriptions and check them after decoding.

Idea 2 · Pydantic, the Python binding

Pydantic v2 generates JSON Schema from dataclass-shaped models via model_json_schema(). Pydantic AI wraps this so you write:

import json
from decimal import Decimal
from pydantic import BaseModel, Field, ValidationError

class LineItem(BaseModel):
    sku: str
    quantity: int = Field(ge=1)
    unit_price_usd: Decimal

class Invoice(BaseModel):
    customer: str
    line_items: list[LineItem]
    total_usd: Decimal = Field(ge=0)

schema = Invoice.model_json_schema()
print(json.dumps(schema)[:400] + " ...")
ok = Invoice.model_validate_json('{"customer": "Acme", "total_usd": "42.50", '
                                 '"line_items": [{"sku": "A-1", "quantity": 2, "unit_price_usd": 21.25}]}')
print("\nparsed:", repr(ok.total_usd), ok.line_items[0])
try:
    Invoice.model_validate_json('{"customer": "Acme", "total_usd": -5, "line_items": [{"sku": "A-1", "quantity": 0}]}')
except ValidationError as e:
    for err in e.errors():
        print("error at", ".".join(map(str, err["loc"])), "->", err["msg"])

Idea 3 · Zod, the TypeScript binding

Zod (z.object({customer: z.string(), ...})) is the TS equivalent. OpenAI's Node SDK exposes zodResponseFormat(Invoice) which translates to the API's JSON Schema payload.

Idea 4 · Refusals

Strict mode cannot force the model to answer. If the request is declined, OpenAI fills a refusal field and Anthropic ends with stop_reason: "refusal"; your code must handle this as a first-class outcome, not a failure. Note what strict mode does not catch: an input that does not fit the schema ("the email was a poem, not an invoice"). The model will usually produce a well-formed, made-up invoice rather than refuse, so the schema itself must have a way to say "not applicable" (measured below).

Idea 5 · Constrained decoding in the open

Open-weights implementations use three techniques.

  1. Grammar-based decoding (outlines, guidance, lm-format-enforcer): build a deterministic finite automaton from the schema; at every step, mask the logits of tokens that would violate the FSM.
  2. Logit masking with a JSON parser: run a streaming JSON parser in lockstep with the model; at every step, compute the valid-next-token set.
  3. Inference-engine support: vLLM, SGLang and llama.cpp accept a JSON Schema or grammar per request and apply the mask with fast engines such as XGrammar or llguidance.

Commercial providers do this behind the scenes. With precomputed token masks the overhead is small (microseconds per token in the run below), and fixed parts of the output, such as key names, can even be emitted without sampling.

The same idea as a formula

Constrained decoding. Let A(y<t​)⊆V be the set of tokens that keep the output so far a prefix of some string valid under the schema. At each step the model's distribution is renormalised over that set:

p′(yt​∣y<t​)=∑v∈A(y<t​)​p(v∣y<t​)p(yt​∣y<t​)1[yt​∈A(y<t​)]​.
Every complete output is then valid by construction. In practice the logits of disallowed tokens are set to −∞ before sampling.

What it does not change. Within A, the model's preferences are untouched: if the model puts most weight on a wrong but valid value, that value is chosen.

Retries without constraints. If a free-form output is valid with probability p, the expected number of attempts until a valid one is 1/p, and k attempts all fail with probability (1−p)k.

Worked example
How narrow is the mask?
  • Qwen's vocabulary has 151,936 tokens. At the very start of the output the schema allows 7 of them (the forms of {), 0.005%.
  • After "priority": " only 13 tokens remain: pieces of low, normal and urgent. A model that would have written "High" cannot.
  • Inside the free-text customer string, 147,137 tokens (96.8%) are allowed: the schema says nothing about what a name contains.
  • Without constraints, with p=0.9 per attempt, 3 attempts all fail with probability 0.13=0.001, at a cost of about 1.1 attempts on average. With p=0.5: 2 attempts on average and a 12.5% chance that 3 attempts all fail.
Check your mental model
  • ✗ "With a schema, the extracted data is correct."
    ✓ It is well-formed; the values are only as good as the model.
  • ✗ "If the input doesn't fit, a strict model refuses."
    ✓ Usually it fills the schema anyway; give the schema an explicit "not applicable" path.
  • ✗ "Constrained decoding is slow."
    ✓ With precomputed masks it costs microseconds per token, far less than the model itself.
  • ✗ "Pydantic's schema can be sent to any strict mode unchanged."
    ✓ Strict modes have rules (all fields required, additionalProperties: false, limited keywords); check or transform the schema first.

Prompt-only JSON against constrained decoding on a real model

Qwen2.5-0.5B-Instruct extracts is_order, customer, quantity, product and priority from eight short emails. The same prompt runs twice: once free, once with XGrammar's logits processor compiled from the JSON Schema. Each output is parsed, validated with jsonschema and scored on three fields against the expected values; a common repair step (stripping code fences) is also scored. About 80 seconds on CPU.

import json, time, torch, jsonschema, xgrammar as xgr
from transformers import AutoTokenizer, AutoModelForCausalLM, logging
logging.set_verbosity_error()

M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); model = AutoModelForCausalLM.from_pretrained(M).eval()
SCHEMA = {"type": "object", "additionalProperties": False,
          "required": ["is_order", "customer", "quantity", "product", "priority"],
          "properties": {"is_order": {"type": "boolean"}, "customer": {"type": "string"},
                         "quantity": {"type": "integer", "minimum": 0}, "product": {"type": "string"},
                         "priority": {"type": "string", "enum": ["low", "normal", "urgent"]}}}
EMAILS = [  # (text, expected quantity, expected priority, is it an order?)
    ("Hi, this is Priya from Northwind. Please send 40 boxes of A4 paper. Not urgent.", 40, "low", True),
    ("URGENT: Contoso needs 3 replacement drill motors by tomorrow morning. - Sam", 3, "urgent", True),
    ("Order from Fabrikam: 12 safety helmets, standard delivery is fine. Regards, Lee", 12, "normal", True),
    ("Can you ship 250 cable ties to Tailspin? We need them ASAP, production is stopped.", 250, "urgent", True),
    ("Hello! Just saying thanks for the great service last month. Best, Ana", 0, "low", False),
    ("Woodgrove would like 6 ergonomic chairs. No rush at all, whenever convenient.", 6, "low", True),
    ("Our office party is on Friday, everyone is welcome to join.", 0, "low", False),
    ("Litware here: 18 laptop stands please, usual priority. Thanks, Kim", 18, "normal", True)]
PROMPT = ("Extract the order from the email as JSON with keys is_order (boolean), customer (string), "
          "quantity (integer), product (string), priority (one of low, normal, urgent).\nEmail: {}")

info = xgr.TokenizerInfo.from_huggingface(tok, vocab_size=model.config.vocab_size)
compiled = xgr.GrammarCompiler(info).compile_json_schema(json.dumps(SCHEMA))

def extract(email, constrained):
    ids = tok.apply_chat_template([{"role": "user", "content": PROMPT.format(email)}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    kw = {"logits_processor": [xgr.contrib.hf.LogitsProcessor(compiled)]} if constrained else {}
    with torch.no_grad():
        out = model.generate(ids, max_new_tokens=90, do_sample=False, **kw)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()

import re
def score(outputs, label, secs):
    parsed = valid = correct = 0
    for text, (email, qty, prio, is_order) in zip(outputs, EMAILS):
        try:
            obj = json.loads(text); parsed += 1
            jsonschema.validate(obj, SCHEMA); valid += 1
            correct += (obj["quantity"] == qty) + (obj["priority"] == prio) + (obj["is_order"] == is_order)
        except (json.JSONDecodeError, jsonschema.ValidationError):
            pass
    n = len(EMAILS)
    print(f"{label:<38} parses {parsed}/{n}  valid {valid}/{n}  correct fields {correct}/{3 * n}  {secs}")

t = time.time(); free = [extract(e[0], False) for e in EMAILS]; t_free = time.time() - t
t = time.time(); cons = [extract(e[0], True) for e in EMAILS]; t_cons = time.time() - t
print("prompt only, first output:      " + repr(free[0][:120]))
print("constrained, first output:      " + repr(cons[0][:120]) + "\n")
score(free, "prompt only", f"{t_free:.0f} s")
unfence = [re.sub(r"^```(?:json)?\s*|\s*```$", "", x.strip()) for x in free]   # a common repair step
score(unfence, "prompt only, code fences stripped", "")
score(cons, "constrained decoding (xgrammar)", f"{t_cons:.0f} s")
print("\nconstrained outputs, quantity / priority / is_order vs expected:")
for text, (email, qty, prio, is_order) in zip(cons, EMAILS):
    o = json.loads(text)
    print(f"  {o['quantity']:>4} {o['priority']:<7} {str(o['is_order']):<6} expected {qty:>4} {prio:<7} {is_order}"
          f"   {email[:42]}...")

Reading this output

Prompt only: 0 of 8 outputs parse. Every reply wrapped the JSON in a ```json code fence, so json.loads fails on all of them. The JSON inside was fine: after the common repair of stripping fences, all 8 parse and validate. Leaked formatting is the most common way prompted JSON breaks.

Constrained: 8 of 8 parse and validate, with no repair. The grammar never allowed a code fence or any text outside the object. The two modes then agree on the content (16 of 24 fields right in both), and took about the same time: the mask costs almost nothing.

The values are where the errors are. The model labelled "not urgent" and "no rush" as normal instead of low. Worse, it turned the thank-you note and the party invitation into orders with invented quantities (1 and 5) and is_order: true. The schema forced every email into the shape of an order, and a small model filled it in. Constrained decoding guarantees the format; it cannot make a model judge correctly.

Inside the mask

This block continues from the one above and reuses its compiled schema. A grammar matcher is fed different prefixes of an output, and the block counts how many of the 151,936 tokens the schema allows next, with examples. Then it times the mask computation per token. Instant.

# Continues from the block above: tok, model, info (xgrammar TokenizerInfo), compiled and SCHEMA are defined.
import time, numpy as np, xgrammar as xgr

def allowed_after(prefix):
    """Feed the prefix to a grammar matcher and list the tokens the schema allows next."""
    m = xgr.GrammarMatcher(compiled)
    for t in tok(prefix, add_special_tokens=False)["input_ids"]:
        assert m.accept_token(t), f"prefix leaves the grammar at token {tok.decode([t])!r}"
    mask = xgr.allocate_token_bitmask(1, info.vocab_size)
    m.fill_next_token_bitmask(mask)
    bits = np.unpackbits(mask.numpy().view(np.uint8), bitorder="little")[: info.vocab_size]
    ok = np.flatnonzero(bits)
    return len(ok), [tok.decode([int(i)]) for i in ok[:8]]

V = info.vocab_size
print(f"vocabulary: {V:,} tokens\n")
for prefix in ['', '{', '{"is_order": ', '{"is_order": true, "customer": "Pri',
               '{"is_order": true, "customer": "Priya", "quantity": ',
               '{"is_order": true, "customer": "Priya", "quantity": 40, "product": "paper", "priority": "']:
    n, sample = allowed_after(prefix)
    print(f"after {prefix[-34:]!r:<38} {n:>7,} allowed ({100 * n / V:6.3f}%)  e.g. {sample[:6]}")

# What the mask costs per generated token.
m = xgr.GrammarMatcher(compiled); mask = xgr.allocate_token_bitmask(1, V)
ids = tok('{"is_order": true, "customer": "Priya", "quantity": 40, "product": "A4 paper", "priority": "low"}',
          add_special_tokens=False)["input_ids"]
t = time.perf_counter()
for i in ids:
    m.fill_next_token_bitmask(mask); m.accept_token(i)
per_token = (time.perf_counter() - t) / len(ids)
print(f"\nmask computation: {per_token * 1e6:.0f} microseconds per token over {len(ids)} tokens "
      f"(the 0.5B model itself needs tens of milliseconds per token on this CPU)")

Reading this output

The mask is very narrow where the schema is specific. At the start, 7 of 151,936 tokens are allowed: the different ways of writing {. After "quantity": about 430 tokens remain, the digit pieces (plus whitespace). After "priority": " only 13 remain, pieces of low, normal and urgent: a model cannot write "High" here even if it wants to.

It is wide where the schema says little. Inside the customer string, 96.8% of the vocabulary is allowed. The schema constrains the structure, not the content of free text; for that you need enums, patterns, or checks after decoding.

It is cheap. Computing the mask takes about 9 microseconds per token here, thousands of times less than a forward pass of even a 0.5B model on this CPU. That is why inference engines can offer structured output at almost no speed cost.

Idea 6 · The three failure modes

  1. Parse error. The output is not valid JSON. Cannot happen under strict mode. Can still happen on non-strict providers.
  2. Schema violation. The output parses but violates the schema. Cannot happen under strict mode. Common outside it.
  3. Refusal. The model declines. Must be handled as a typed outcome.

Idea 7 · Retry strategy

When you are outside strict mode (non-strict tools, prompt-only JSON, models without constrained decoding), the recovery pattern is:

generate -> parse -> validate -> if fail, inject error and retry, max 3x

One retry is usually enough. Three retries catches weak-model flakes. Beyond three is a sign of a bad schema: the model cannot satisfy it for some inputs, and the prompt or the schema needs fixing.

Idea 8 · Small-model support

Constrained decoding works on small models: it guarantees the shape of the output whatever the model's size. It does not make the values right. In the run below a 0.5B model goes from 0 of 8 parseable outputs to 8 of 8, but still gets a third of the fields wrong and invents orders from emails that contain none. This is the main reason structured outputs matter in production: they turn format failures into content questions you can measure.

Industry practice
What's current (2024–2026)
  • OpenAI Structured Outputs (response_format with json_schema and strict: true, or strict tools): guaranteed schema match, a refusal field, documented schema limits.
  • Anthropic structured outputs (output_config.format with json_schema, and strict: true tools): client.messages.parse(..., output_format=Model) in the Python SDK; numeric and length constraints are checked by the SDK, not enforced by decoding.
  • Gemini responseSchema / responseJsonSchema with responseMimeType: application/json.
  • Open models: XGrammar (used here), llguidance and Outlines power structured output in vLLM, SGLang, llama.cpp and Ollama, so a laptop-sized model (0.5B–4B, or 7B in 4-bit on an 8 GB GPU) gets the same format guarantee.
  • Typed bindings: Pydantic and Pydantic AI in Python, Zod in TypeScript, Instructor across providers.

Sources: OpenAI structured outputs, Claude structured outputs, XGrammar, Pydantic AI output, JSON Schema 2020-12.

Recap
What to keep from this lesson
  • Prompting for JSON fails in ways you must repair; constrained decoding removes format failures.
  • The mask lets through only tokens that keep the output valid; inside strings it allows almost anything.
  • A valid output is not a correct output: score the values.
  • Give the schema a way to say "not applicable", or the model will invent data.
  • Handle refusals as a typed outcome; retry only format errors, and only a few times.

Given a free-text extraction target (invoices, resumes, support tickets, research summaries), produce a production-ready extraction contract: JSON Schema 2020-12, Pydantic model, refusal handler, and retry policy.

Produce:

1. JSON Schema 2020-12. Every property typed. `required` lists every property. `additionalProperties: false` on every object. Enums used for closed value sets. No `$ref`. No ambiguous `oneOf` / `anyOf`. Validated against OpenAI strict-mode requirements.
2. Pydantic v2 BaseModel. Mirror of the schema with Python types. `model_json_schema()` must produce a schema equivalent to (1).
3. Refusal handler. Typed `Refusal(reason: str, category: str)` outcome. List the categories: `safety`, `input_mismatch`, `insufficient_info`.
4. Retry policy. Three retry shapes: (a) inject validation errors and retry once (outside strict mode); (b) accept refusal as final (strict mode); (c) escalate to a stronger model on repeated refusal.
5. Test vectors. Ten inputs covering happy path, adversarial fields, partial input, and a refusal-triggering case. Each with expected outcome.

Hard rejects:
- Any schema with untyped fields. Fails strict mode and validator both.
- Any schema missing `additionalProperties: false`. Leaks hallucinations.
- Any schema using `oneOf` without a discriminator field. Ambiguous decoding.
- Any Pydantic model without its JSON Schema round-trip checked.

Refusal rules:
- If the target domain includes personally identifying data without a documented purpose, refuse and route to Phase 18 (ethics) for the lawful-basis argument.
- If the user asks for a schema that cannot be expressed in JSON Schema 2020-12 (e.g. recursive arbitrary graphs), refuse and propose the closest expressible relaxation.
- If the extraction target is "extract structured data from anything", refuse and ask for the specific domain.

Output: a one-page contract with the schema JSON, the Pydantic class, the refusal and retry policy, and the ten test vectors. End with a note on the first provider to target and why.

Solutions

SolutionP1 · 0 then 8 parse, and both non-orders become orders

Prompt only: 0 of 8 parse, because every reply comes wrapped in a code fence. Stripping the fences rescues all 8. Constrained: 8 of 8 parse and validate as generated.

The constrained version does not notice the non-orders. Both get is_order: true and invented quantities (1 for the thank-you note, 5 for the party invitation). The schema demanded an order-shaped object, and constrained decoding made sure the model produced one. Format correctness and content correctness are separate problems.

SolutionB1 · A made-up order, stored as fact

The pipeline stores a made-up order. Every field must be present and non-null, and decoding is constrained to the schema, so the model has to put some customer name, some quantity and some product into the object, whatever the newsletter says. Nothing fails, nothing is flagged, and the bad record looks exactly like a good one. That is worse than a parse error, which at least stops the pipeline.

Fixes, in the schema itself:

  • A discriminated union: {"kind": "order", ...} or {"kind": "not_an_order", "reason": ...}, so "nothing here" is a valid answer.
  • Nullable fields ("type": ["integer", "null"]) with an instruction to use null when the email does not say.
  • A decision field first, before the details, so the model commits to "is this an order?" before it starts inventing details.

Then measure: run known non-orders through the pipeline and count how many come out as orders. In this lesson's run, a 0.5B model still chose "order" for every email even with these options; a larger model, or a separate classification step, is needed for reliable judgement.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designDesign the extraction service for purchase-order emails. The input is free text; the output is a typed record with a customer, line items and a total. Cover the schema, the enforcement mode, the retry and refusal handling, and how you prove it works before it touches the accounting system.

Level 3 of 4 · about 20 minutes to answer well.

Short answer. Write one JSON Schema 2020-12 with the constraints that matter: required fields, enums for closed sets, a minimum of zero on the total, additional properties forbidden, and any reasoning field ahead of any decision field. Run it in the provider's strict schema mode so that a response that finishes cannot have a parse error or a schema violation, check the stop reason so that a response cut at the token limit goes to the error path, and treat a refusal as a typed outcome that goes to a review queue. Prove it with a labeled set of real emails scored per field, a refusal check on inputs that must not extract, and a run beside the human process before any record is written.

The schema.

  • type, properties and required for the shape; every property listed as required, with null allowed where the source can lack a value.
  • enum for closed sets such as currency or status; minimum on the total; pattern, minLength and maxLength on identifiers; items for the line items.
  • additionalProperties: false everywhere, which blocks invented fields and which strict mode demands.
  • Field order as logic: any reasoning field before total or status, because the model commits to the first field it writes.

In Python, a Pydantic model generates this schema; the service keeps the schema as the contract and the model as its binding.

The enforcement mode.

Situation Pick
A hosted frontier model, a flat schema the provider's strict schema mode
Several providers, retries acceptable a retry library over the Pydantic model, which is portable and does not touch logits
A local model, validity required a grammar engine, finite state for a flat schema and context-free for a recursive one

Strict mode is the default here: a finished output parses and validates by construction. Two failures remain: the refusal, and a response cut at the token limit, which can still fail to parse. Check the stop reason before you read the output, and send an incomplete response to the error path.

Retry and refusal.

Outside strict mode: generate, parse, validate, inject the typed errors and retry, at most three times. More than three means the schema or the prompt is wrong for some inputs. In every mode: a refusal is a first-class outcome with a reason attached. Log it, return it typed, send it to the review queue, and never retry it, because forcing a record on an input that does not fit produces an invented record.

Proof before accounting sees a record.

  1. A labeled set of real emails with gold records; the structured outputs lesson uses 50 documents. Report exact match, accuracy per field and type compliance.
  2. A refusal check. Construct inputs that must not extract, such as a lyric, a proof or a blank email, and count refusals against invented outputs.
  3. A confidence per field from repeated extraction or token probabilities, with low-confidence records routed to a human.
  4. A schema version on every record, and a schema diff that separates breaking changes from non-breaking ones before any deploy.
  5. A side-by-side run against the human process on the labeled set, with the service writing nothing until the field-level numbers clear the bar you set with finance.

Plausible wrong answers.

  • "Prompt for JSON and parse it, the model is good." That works 85 to 95 percent of the time and fails six different ways; accounting needs the contract.
  • "Retry refusals until the model gives a record." A refusal says the input does not fit; forcing a record invents one.
  • "Validation after generation is as good as strict mode." It is reliable but pays for every retry, and a truncated output costs a turn each time.

Follow-ups an interviewer may ask.

  • (level 3) Why forbid additional properties? Expected: it blocks invented fields, and strict mode requires it everywhere.
  • (level 3) You expect to switch providers next year. Which mode do you pick? Expected: a retry library over the Pydantic model for portability, or keep the schema identical across providers so each strict mode receives the same contract.
  • (level 4) How do you version the schema once records exist? Expected: a version field on each record and a schema diff that separates breaking changes from non-breaking ones. Strict mode makes every field required, so an added field is breaking too, because the records written before it do not contain it; removed fields and changed types are breaking, and relaxed constraints are not.
  • (level 4) Which failure can this design not remove, and where does it go? Expected: a wrong value with the right type; it goes to the field-level eval and the confidence flags, and the low-confidence records go to review.

Explain the mechanismAn extraction service turns purchase-order emails into typed records. Name the ways a structured output call can fail, say which of them disappear under strict schema enforcement, and describe how the code should treat what remains.

Level 2 of 4 · about 7 minutes to answer well.

Short answer. Three ways: a parse error, where the output is not JSON; a schema violation, where it parses but breaks a type, a required field, an enum or a range; and a refusal, where the model decides the input does not fit the schema. Strict enforcement removes the first two by construction for a response that finishes. The refusal stays, and it must be a typed outcome that the code logs and returns, never a retry. A response cut at the token limit can still fail to parse, so check the stop reason before you read the output.

Three approaches, three failure profiles.

  1. Prompt for JSON. Works 85 to 95 percent of the time on a frontier model. Fails six ways: a missing brace, a trailing comma, wrong types, invented fields, truncation at the token limit, and leaked prose such as "here is your JSON".
  2. Validate after generation. Generate freely, parse, validate against the schema, and on failure inject the error and retry. Reliable but you pay for every retry.
  3. Constrained decoding. The provider masks invalid tokens at decode time, so a finished output parses and validates by construction. The model-side failure collapses to one mode, refusal; a response cut at the token limit and a request error still need their own error path.

The retry loop, when you are outside strict mode.

generate -> parse -> validate -> if fail, inject the error and retry, at most 3 times

One retry is usually enough. Three catches weak-model flakes. Beyond three means the schema or the prompt is wrong for some inputs, and the fix is there, not in a fourth attempt. The validator should return a typed error list with a path and a message for each failure, which is the shape the retry prompt needs.

The refusal branch.

The model declines because the input does not fit, for example the email was a poem and not an order, or because of a safety reason. The refusal carries the reason. Log it, return it typed, and do not retry. The lesson also uses refusals as a safety signal downstream.

One schema setting that matters.

additionalProperties: false forbids fields the schema did not name, which is how strict mode shuts the door on invented fields. Strict mode requires it everywhere.

Plausible wrong answers.

  • "A refusal is a failed call, retry it." It is a first-class outcome with a reason attached; log it and return it typed.
  • "Strict mode removes every failure." It removes parse errors and schema violations for a finished response; refusals, truncated responses and wrong values with the right type remain.
  • "Retry until it validates." Past three retries the cost grows and the schema is the real problem.

Follow-ups an interviewer may ask.

  • (level 2) How many retries, and what does needing more tell you? Expected: at most three; one is usually enough, and beyond three the schema or the prompt is wrong for some inputs.
  • (level 2) Why must the refusal branch not retry? Expected: the model declined for a reason, often fit or safety; a retry wastes cost and can push a wrong extraction through.
  • (level 3) What does the retry prompt need from the validator? Expected: a typed error list with a path and a message per failure, so the model knows which field to fix.
  • (level 3) Which schema setting blocks invented fields? Expected: additional properties set to false, which strict mode requires everywhere.
