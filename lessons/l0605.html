About the model on this page
The model on this page is the lab rig

chat is a real LangChain chat model pointed at mockllm (Lesson 14.92): one get_order_status call per order ID it sees, a cancel_order call when asked to cancel, and "Here is what I found: …" once it has results. It is not a language model.

from mockllm import start                       # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from langchain.tools import tool

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock", temperature=0)
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

@tool
def cancel_order(order_id: str) -> str:
    """Cancel a ShopKart order that has not shipped yet."""
    return f"{order_id} cancelled"
Why this came about

LangChain's early agent classes were rigid and hard to customize, so in 2024 most teams moved agents to LangGraphlater · 14.101's prebuilt ReAct agent. LangChain 1.0 (2025) made that the standard create_agent, built on LangGraph, so simple agents and complex graphs share one runtime.

The problem: the loop you wrote in Lesson 14.57

Your Agent class called the model, ran the tools it asked for, sent the results back and repeated until the model answered or a limit was hit, with a trace of every step. Every agent framework ships that loop. LangChain's is create_agent, and it runs on LangGraph, so the same agent later gains checkpoints, human approval and streaming without being rewritten.

In plain words first
Your loop, packaged

An agent is a loop: ask the model, run the tools it asks for, send back the results, repeat until it answers in plain text (Lessons 14.56 and 14.57). create_agent is that loop, packaged: it builds a small LangGraph graph with a model node, a tools node and a rule that loops between them. Because it is a graph, the same agent can later save its progress, pause for approval and stream, without being rewritten.

Idea 1 · An agent in one call

create_agent takes a model, a list of tools and a system prompt, and returns a working agent: the whole loop from Lesson 14.57, already written. Ask it about two orders and print every message it produced, so you can see the loop's steps in the result.

from langchain.agents import create_agent

agent = create_agent(chat, tools=[get_order_status], system_prompt="Help ShopKart customers with orders. Be brief.")
state = agent.invoke({"messages": [{"role": "user", "content": "Where are A-1001 and A-1002?"}]})

print(sorted(state))
for m in state["messages"]:
    calls = [c["args"]["order_id"] for c in getattr(m, "tool_calls", [])]
    print(f"{type(m).__name__:12} | {m.content or calls}")
What you should see
['messages']
HumanMessage | Where are A-1001 and A-1002?
AIMessage    | ['A-1001', 'A-1002']
ToolMessage  | A-1001 is shipped
ToolMessage  | A-1002 is processing
AIMessage    | Here is what I found: A-1001 is shipped; A-1002 is processing

The result is the agent's state, a dictionary whose messages key holds the whole run: your question, the model's turn with two tool calls, one ToolMessage per call, and the answer. This is the same sequence you built by hand in Lesson 14.95 and in Lesson 14.56. When an agent gives a wrong answer, this list is the first thing to read.

Idea 2 · The loop is a graph

The agent that create_agent returned is not a special object. It is a small graph, the kind you will build by hand from Lesson 14.100 onward. Ask it for its nodes and edges:

print(type(agent).__name__, "| nodes:", [n for n in agent.get_graph().nodes])
for e in agent.get_graph().edges:
    print(f"  {e.source} -> {e.target}" + ("  (conditional)" if e.conditional else ""))
What you should see
CompiledStateGraph | nodes: ['__start__', 'model', 'tools', '__end__']
  __start__ -> model
  model -> __end__  (conditional)
  model -> tools  (conditional)
  tools -> model  (conditional)

create_agent returned a compiled LangGraph graph with two working nodes. model calls the model. A conditional edgelater · 14.100 then checks the reply: tool calls go to tools, which runs them and goes back to model; no tool calls go to the end. That is Lesson 14.57's while loop drawn as a graph, and Lessons 14.101 and 14.102 build the same graph yourself.

Streaming shows each node's output as it finishes, which is how a UI shows "checking your order…" while the agent works:

for step in agent.stream({"messages": [{"role": "user", "content": "Where is A-1002?"}]}, stream_mode="updates"):
    for node, update in step.items():
        last = update["messages"][-1]
        print(f"{node:6} -> {type(last).__name__}: {last.content or last.tool_calls[0]['name']}")
What you should see
model  -> AIMessage: get_order_status
tools  -> ToolMessage: A-1002 is processing
model  -> AIMessage: Here is what I found: A-1002 is processing

stream_mode="updates" yields what each node changed. Other modes (values for the whole state, messages for tokens) are covered in Lesson 14.106.

Idea 3 · Limits

Your Lesson 14.57 agent had max_steps. A LangGraph run has a recursion limit: the maximum number of steps (node runs) before it stops with an error. One round trip with one tool call takes three steps (model, tools, model), so a limit of 2 cannot finish:

from langgraph.errors import GraphRecursionError

try:
    agent.invoke({"messages": [{"role": "user", "content": "Where is A-1002?"}]}, {"recursion_limit": 2})
except GraphRecursionError as e:
    print("GraphRecursionError:", str(e).split(".")[0])
What you should see
GraphRecursionError: Recursion limit of 2 reached without hitting a stop condition

The default limit is high (10,000 in langgraph 1.2), so set your own per run in config, based on the longest run you expect. For limits on model calls and tool calls per run or per thread, with a graceful ending instead of an error, use the call-limit middleware in Lesson 14.97.

Idea 4 · A typed final answer

response_format makes the agent end with a validated object as well as text, in structured_response:

from typing import Literal
from pydantic import BaseModel
from langchain.agents.structured_output import ProviderStrategy

class OrderAnswer(BaseModel):
    status: Literal["shipped", "processing", "not_found"]
    needs_human: bool

typed = create_agent(chat, tools=[get_order_status], response_format=ProviderStrategy(OrderAnswer))
result = typed.invoke({"messages": [{"role": "user", "content": "Where is A-1001? (shipped)"}]}, {"recursion_limit": 10})
print(repr(result["structured_response"]))
What you should see
OrderAnswer(status='shipped', needs_human=False)

ProviderStrategy uses the provider's native structured output. ToolStrategy asks the model to call a special tool whose arguments are your schema, for models without native support. Passing the Pydantic class directly lets LangChain choose based on the model.

Idea 5 · Conversations: a checkpointer and a thread

The agent keeps nothing between invoke calls unless you give it a checkpointer, which saves the state after every step, and a thread ID, which names the conversation:

from langgraph.checkpoint.memory import InMemorySaver

remembering = create_agent(chat, tools=[get_order_status], checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "customer-42"}}        # one thread per conversation

for question in ["Where is A-1001?", "And A-1002?"]:
    state = remembering.invoke({"messages": [{"role": "user", "content": question}]}, config)
    print(f"{question:18} -> {len(state['messages'])} messages in the thread | {state['messages'][-1].content}")
What you should see
Where is A-1001?   -> 4 messages in the thread | Here is what I found: A-1001 is shipped
And A-1002?        -> 8 messages in the thread | Here is what I found: A-1002 is processing

The second turn started from the four messages of the first. InMemorySaver loses everything when the process stops; Lesson 14.103 covers database checkpointers, resuming after a crash, and going back to an earlier step. A checkpointer is also what lets an agent pause for a person's approval and continue later (Lessons 14.97 and 14.104).

Measure it: what each question costs

The messages show how many model calls and tool calls a run made, which is where its cost and latency come from (Lesson 14.61):

def run_stats(question):
    msgs = agent.invoke({"messages": [{"role": "user", "content": question}]})["messages"]
    model_calls = sum(1 for m in msgs if m.type == "ai")
    tool_calls = sum(len(m.tool_calls) for m in msgs if m.type == "ai")
    return model_calls, tool_calls

for q in ["hello", "Where is A-1001?", "Where are A-1001 and A-1002?"]:
    print(f"{q:30} model calls, tool calls = {run_stats(q)}")
What you should see
hello                          model calls, tool calls = (1, 0)
Where is A-1001?               model calls, tool calls = (2, 1)
Where are A-1001 and A-1002?   model calls, tool calls = (2, 2)

A greeting costs one model call; any question that needs a lookup costs at least two, however many tools run in parallel. That is why an agent is the wrong tool when every request takes the same fixed steps: a chain (Lesson 14.94) makes one call where an agent makes two or more.

    ✓ It is the same loop, built as a graph with a model node, a tools node and a router.
  • ✗ "The agent remembers earlier questions."
    ✓ Only with a checkpointer and the same thread ID; otherwise each invoke starts fresh.
  • ✗ "response_format makes the model's text into JSON afterwards."
    ✓ The schema is sent to the model, which answers in that shape; it is validated into an object in structured_response.

Debugging exercise: "it" means nothing

A customer asks about A-1001, then says "Cancel it please". The agent asks for an order ID as if the first message never happened.

def chat_turn(question):
    state = agent.invoke({"messages": [{"role": "user", "content": question}]})
    return len(state["messages"]), state["messages"][-1].content

print(chat_turn("Where is A-1001?"))
print(chat_turn("Cancel it please"))

What it printed:

(4, 'Here is what I found: A-1001 is shipped')
(2, 'I can check order status and cancel orders. Please share your order ID, like A-1002.')

Find the cause from the numbers in the output, and fix it. (Solution D1.)

Make it your own

Build helpdesk, an agent with both get_order_status and cancel_order and a checkpointer, and stream two turns of one conversation: "Where is A-1002?" then "Please cancel A-1002". Print each node's output. (Solution M1.)

Solutions

SolutionP1 · Count the steps

Both finish. Two parallel tool calls still take three steps (model, tools, model), because the tools node runs all of a turn's calls in one step. "hello" takes one step. A question needing two rounds of tools in sequence, such as "find my orders, then check the kettle one", takes five steps and would fail at 3.

SolutionB1 · State has to belong to a conversation

A checkpointer saves state per thread. Without a thread ID, LangGraph cannot know which conversation to load or save, and a default shared thread would mix different customers' conversations: a privacy bug. Every call to an agent with a checkpointer must say which thread it belongs to.

SolutionD1 · No checkpointer, no history

The second turn's state has 2 messages: only "Cancel it please" and the reply. Each invoke started a new run with no memory, so "it" referred to nothing. Give the agent a checkpointer and use the same thread ID for both turns; the second turn then starts from the first turn's messages, as in Idea 5. (Sending the whole history yourself on every call also works, but then you are building the memory by hand.)

SolutionM1 · Two turns, one thread
helpdesk = create_agent(chat, tools=[get_order_status, cancel_order], checkpointer=InMemorySaver(),
                        system_prompt="Help ShopKart customers with orders. Cancel only orders that have not shipped.")
cfg = {"configurable": {"thread_id": "customer-7"}}
for q in ["Where is A-1002?", "Please cancel A-1002"]:
    for step in helpdesk.stream({"messages": [{"role": "user", "content": q}]}, cfg, stream_mode="updates"):
        for node, update in step.items():
            m = update["messages"][-1]
            print(f"  {node:6} {m.content or [(c['name'], c['args']['order_id']) for c in m.tool_calls]}")

  model  [('get_order_status', 'A-1002')]
  tools  A-1002 is processing
  model  Here is what I found: A-1002 is processing
  model  [('cancel_order', 'A-1002')]
  tools  A-1002 cancelled
  model  Here is what I found: A-1002 cancelled

The cancel went through without anyone approving it. For an action that changes an order, that is what Lesson 14.97's HumanInTheLoopMiddleware is for.

Check your understanding

Explain the mechanismWhat does create_agent actually run?

Worked answer. A LangGraph graph with a model node and a tools node. The model node calls the chat model with the system prompt, the messages and the bound tools. A conditional edge sends a reply with tool calls to the tools node, which runs them, in parallel when there are several, and appends ToolMessages; then control returns to the model. A reply without tool calls ends the run, or, with response_format, produces a structured response. Because it is a graph, checkpointers, streaming, interrupts and middleware all apply to it.

A plausible wrong answer. "It is a chain that calls tools." A chain has a fixed order; the agent decides at every step whether to call more tools.

Follow-ups. Where would you add a step that runs before every model call?

Debug a failureAn agent sometimes fails with GraphRecursionError. What do you check?

Worked answer. Whether the run was legitimately long or looping. In the trace I look for the same tool called with the same arguments again and again, which usually means a result the model cannot use: an empty result, an error it does not understand, or a result message that does not match the call. I fix the tool's result, add a repeat check or call limits, and set recursion_limit from the longest legitimate run plus a margin, so loops fail fast.

A plausible wrong answer. "Raise the recursion limit." That turns a fast failure into a slow, expensive one.

Follow-ups. How would you end a run gracefully at the limit instead of raising (Lesson 14.97)?

Defend a designWhen would you use create_agent, and when would you write your own LangGraph graph?

Worked answer. create_agent when the work is one model choosing among tools in a loop, plus the standard extras that middleware covers: approval, summarization, limits, fallbacks. My own graph when the control flow is mine to decide: fixed steps before or after the agent, routing between specialists, parallel branches that merge, or a workflow where the model only fills in parts. Often both: a custom graph whose nodes include create_agent agents.

A plausible wrong answer. "Always write the graph, prebuilt agents are toys." create_agent is a production agent loop; rebuilding it adds code without adding control.

Follow-ups. How do you put an agent inside a larger graph (Lesson 14.107)?
