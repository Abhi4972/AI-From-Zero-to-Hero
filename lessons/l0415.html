Why this came about

General embedding models do not know a company's vocabulary, acronyms or product names. Fine-tuning embedding models on pairs of queries and relevant passages became practical with open models and libraries, as a way to lift retrieval after the cheaper fixes were exhausted.

In plain words first
Teaching the search your company's vocabulary

General embedding models do not know that "SKU" and "item code" mean the same in your company, or that two product names are related. Fine-tuning an embedding model on pairs of queries and the passages that answer them pulls those together in its space. It can lift retrieval noticeably, but needs good training pairs, re-embedding the whole collection, and careful evaluation against the original model.

Fine-tuning an embedding model

How this connects

Lesson 14.71 used an embedding model as it came. Lesson 7.22 showed where such models come from: a transformer encoder trained so that matching texts get nearby vectors. This lesson trains one further on your own vocabulary. It is the same kind of training as the fine-tuning workshop of the Models: training, evaluation and fine-tuning section (Lessons 7.25 to 3.25), applied to an embedding model instead of a chat model; you do not need that workshop first, only the PyTorch training loop of Lesson 3.17.

Off-the-shelf embedding models are trained on general web text. When your queries use internal jargon, product codes or a specialist domain (legal clauses, part numbers, medical coding), fine-tuning the embedding model on your own query-and-passage pairs often lifts recall more than any index setting.

Embedding models are bi-encoders: the query and the document are embedded separately, so documents can be embedded once and searched fast. (A reranker is a cross-encoder, which reads query and document together: more accurate, too slow to run over a whole corpus; Lesson 5.38.) Bi-encoders are trained with a contrastive loss, usually InfoNCE: in each batch, the matching passage must score higher than every other passage, which act as negatives. The negatives decide how much the model learns. Random passages are too easy; hard negatives, passages on the same topic that do not answer the query, are where the signal is.

import numpy as np
rng = np.random.default_rng(0)
def info_nce(q, docs, pos, temperature=0.05):
    """Contrastive loss used to fine-tune embedding models: the right document must out-score
    every other document in the batch. Lower is better."""
    q = q / np.linalg.norm(q); docs = docs / np.linalg.norm(docs, axis=1, keepdims=True)
    logits = docs @ q / temperature
    logits -= logits.max()
    return -np.log(np.exp(logits[pos]) / np.exp(logits).sum())

d = 32
query = rng.normal(size=d)
positive = query + 0.6 * rng.normal(size=d)                        # the matching passage
easy_negatives = rng.normal(size=(7, d))                           # random passages from other topics
hard_negatives = query + 0.8 * rng.normal(size=(7, d))             # same topic, wrong answer
print(f"loss with random negatives {info_nce(query, np.vstack([positive, easy_negatives]), 0):.3f}")
print(f"loss with hard negatives   {info_nce(query, np.vstack([positive, hard_negatives]), 0):.3f}"
      "  <- far more signal left to learn from")
What you should see
loss with random negatives 0.000
loss with hard negatives   1.636  <- far more signal left to learn from

With random negatives the loss is already near zero, so there is nothing to learn. With hard negatives the loss is large, and reducing it teaches exactly the fine distinctions your search needs.

The practical recipe:

  1. Collect pairs: real queries with the passage a person clicked, accepted or cited; or generate synthetic questions for each chunk with an LLM and filter them.
  2. Mine hard negatives: retrieve the top results for each query with the current model and keep the ones labeled wrong (check they are truly wrong, or you teach the model to push away correct answers).
  3. Train: Sentence Transformers' MultipleNegativesRankingLoss implements in-batch InfoNCE; larger batches give more negatives. A few thousand good pairs and one to three epochs is a typical start.
  4. Evaluate on held-out queries with recall@k and nDCG (Lesson 14.72) against the base model, then re-embed the whole corpus, because vectors from the old and new models are not comparable.

Related ideas: Matryoshka training makes the first dimensions of a vector carry the most meaning, so vectors can be truncated to save memory; late interaction models such as ColBERT keep one vector per token and match token by token, between a bi-encoder and a cross-encoder in cost and accuracy.

Do it for real: teach an embedding model your company's shorthand

The loss at the start of this lesson was computed on made-up vectors. Here is the whole recipe on a real model, in under a minute on a laptop. The setting is one every company has: internal shorthand. ShopKart's operations team talks in codes (RTO, NDR, OFD), while the wiki pages that explain each process are written in plain words and never use the codes. A general embedding model has never seen this vocabulary, so a question that uses a code cannot find its page.

First, measure the problem.

import random, torch, torch.nn.functional as F
from sentence_transformers import SentenceTransformer

torch.manual_seed(0); random.seed(0)
model = SentenceTransformer("all-MiniLM-L6-v2", device="cpu")          # the embedding model from Lesson 4.5

# ShopKart's operations team has its own shorthand. The wiki pages describe each process in plain words
# and never use the shorthand, so a general embedding model has no way to connect the two.
WIKI = {
    "RTO":  "When delivery fails three times, the parcel travels back to the seller's warehouse and the order is closed.",
    "NDR":  "The courier files a note each time a delivery attempt fails, giving the reason, such as nobody home.",
    "FDA":  "The first time the courier tries to hand over the parcel at the customer's address.",
    "OFD":  "The parcel has left the local hub on a van and should reach the customer today.",
    "QC1":  "Returned goods are inspected at the warehouse door for damage before a refund is released.",
    "PRN":  "A printed slip with the pickup address that the customer sticks on a parcel they are sending back.",
    "DTO":  "A customer sends an item back after receiving it; a courier collects it from their home.",
    "SLA":  "The promised number of days within which an order must reach the customer.",
    "WMS":  "The software that tracks where every item sits on the warehouse shelves.",
    "GRN":  "The warehouse records that stock from a supplier has arrived and been counted.",
    "COD":  "The customer pays the courier in cash when the parcel is handed over.",
    "LM":   "The final leg of the journey, from the local hub to the customer's door.",
    "FM":   "The first leg of the journey, from the seller's premises to the first sorting centre.",
    "MPS":  "One order that ships in several boxes, each with its own tracking label.",
    "POD":  "The signature or photo taken as evidence that the parcel was handed over.",
    "EDD":  "The date shown to the customer for when their order should arrive.",
}
codes, pages = list(WIKI), list(WIKI.values())
TRAIN_FORMS = ["what does {} mean", "{} raised on this order, what happens now", "customer is asking about {}",
               "explain {} to a new agent", "order status says {}", "{} process"]
TEST_FORMS  = ["ticket mentions {}, please advise", "what is the {} step", "{} - need details"]     # wordings never trained on

def embed(texts, train=False):
    """Token vectors from the model, averaged over real tokens, scaled to length 1 (Lesson F6.6)."""
    batch = model.tokenize(texts)
    with torch.set_grad_enabled(train):
        tokens = model[0](batch)["token_embeddings"]
    mask = batch["attention_mask"].unsqueeze(-1).float()
    return F.normalize((tokens * mask).sum(1) / mask.sum(1), dim=-1)

def recall_at_1(forms):
    """For every code and wording: is the right wiki page the single closest page?"""
    model.eval()
    page_vecs = embed(pages)
    hits = total = 0
    for form in forms:
        best = (embed([form.format(c) for c in codes]) @ page_vecs.T).argmax(dim=1)
        hits += (best == torch.arange(len(codes))).sum().item(); total += len(codes)
    return hits / total

GENERAL = [("How do I get my money back?", "Refunds go back to the original payment method within 5 to 7 business days."),
           ("Is delivery free?", "Orders above INR 499 ship free."),
           ("I forgot my password", "Reset your password from the login page using your registered mobile number."),
           ("Can I pay when it arrives?", "Cash on delivery is available for orders up to INR 10,000."),
           ("My TV does not switch on", "ShopKart replaces items that are dead on arrival if reported within 10 days.")]

def general_ok():
    """Ordinary customer questions, as a check that fine-tuning has not damaged what the model already did well."""
    model.eval()
    scores = embed([q for q, _ in GENERAL]) @ embed([p for _, p in GENERAL]).T
    return f"{int((scores.argmax(1) == torch.arange(len(GENERAL))).sum())} of {len(GENERAL)}"

print(f"before fine-tuning: recall@1 on trained wordings {recall_at_1(TRAIN_FORMS):.0%}, on new wordings {recall_at_1(TEST_FORMS):.0%}, general questions {general_ok()}")
What you should see
before fine-tuning: recall@1 on trained wordings 6%, on new wordings 6%, general questions 4 of 5

One in sixteen is what random guessing gives: 6%. The model is not weak; on ordinary customer questions it matches four of five. It simply has no idea that "RTO" has anything to do with a parcel travelling back to the seller.

Now train it. The loop is the PyTorch loop of Lesson 3.17 with the InfoNCE loss from above. Each batch holds sixteen questions and their sixteen pages; every question is scored against every page, and the loss pushes the matching page to the top of its row. The other fifteen pages in the batch serve as the negatives, at no extra cost (in-batch negatives).

optimizer = torch.optim.AdamW(model.parameters(), lr=3e-5)
for epoch in range(4):
    model.train(); total = 0.0
    for form in random.sample(TRAIN_FORMS, len(TRAIN_FORMS)):
        q = embed([form.format(c) for c in codes], train=True)       # 16 queries, one per code
        p = embed(pages, train=True)                                 # their 16 pages
        scores = q @ p.T / 0.05                                      # every query against every page; 0.05 is the temperature
        loss = F.cross_entropy(scores, torch.arange(len(codes)))     # InfoNCE: the matching page must win its row
        loss.backward(); optimizer.step(); optimizer.zero_grad(); total += loss.item()
    print(f"epoch {epoch + 1}: loss {total / len(TRAIN_FORMS):.3f}")
print(f"after fine-tuning:  recall@1 on trained wordings {recall_at_1(TRAIN_FORMS):.0%}, on new wordings {recall_at_1(TEST_FORMS):.0%}, general questions {general_ok()}")
What you should see
epoch 1: loss 2.832
epoch 2: loss 1.536
epoch 3: loss 0.620
epoch 4: loss 0.188
after fine-tuning:  recall@1 on trained wordings 100%, on new wordings 100%, general questions 4 of 5
Reading this output
  • The loss falls from 2.8 to 0.2. A loss of 2.77 is what a model gets when it is guessing among 16 pages (the natural logarithm of 16), so it started from nothing and learned the mapping in four passes.
  • Trained wordings: 6% to 100%. Expected; the model saw those.
  • New wordings: 6% to 100%. This is the result that matters. "ticket mentions RTO, please advise" was never in the training data, and it now finds the right page. The model did not memorise sentences; it learned what each code means and moved its vector next to the page that explains it.
  • General questions: 4 of 5 before, 4 of 5 after. Fine-tuning on a narrow task can damage what a model already knew (catastrophic forgettinglater · 3.23, Lesson 3.23). Here 96 examples and four passes did no harm to this small check. Always measure it; with more data, more passes or a higher learning rate it can go the other way.

What made this work with so little data is that the task is narrow and the signal is clean: sixteen facts, each repeated in six wordings. Real projects have thousands of pages and messier pairs, which is why the recipe above spends most of its effort on collecting pairs and choosing negatives. And remember the last step: after fine-tuning, every stored vector is out of date. Vectors from the old and the new model live in different spaces, so the whole corpus must be embedded again before the new model is used for search.

Check your mental model
  • ✗ "Fine-tuning is the first fix for poor retrieval."
    ✓ Try hybrid search, reranking and better chunking first; they are cheaper.
  • ✗ "After fine-tuning, only new documents need re-embedding."
    ✓ All stored vectors must be recomputed with the new model.
  • ✗ "More training pairs are always better."
    ✓ Quality and hard negatives matter more than volume.

Solutions

SolutionP1 · Temperature sharpens

A lower temperature makes the softmax sharper, so the loss concentrates on the hardest negatives, the ones scored closest to the positive. Too low makes training unstable; tune it.

SolutionB1 · Easy negatives teach little

Random negatives are already far from the positive, so the loss is small and the model learns nothing about fine distinctions. Mine hard negatives: passages on the same topic that do not answer the query.

SolutionD1 · Overfitting and leakage

The model memorized training pairs, or test questions leaked into training. Hold out questions (by document, not just by question), evaluate on them, use more varied data, and stop earlier.

SolutionM1 · Measure before you switch

Held-out questions from documents not used in training; recall@k and nDCG against the base model and the current production model; then a full re-embed into a new index, compared side by side before switching an alias.

Check your understanding

Explain the mechanismHow are embedding models fine-tuned, and when is it worth it?

Worked answer. With contrastive learning: pairs of a query and a relevant passage, trained so the pair scores higher than negatives in the batch (InfoNCE), with hard negatives mined from the corpus. Worth it when a domain's vocabulary or notion of relevance differs from general data and the eval shows a retrieval gap that hybrid search and reranking do not close.

A plausible wrong answer. "Fine-tune whenever retrieval is bad." Cheaper fixes come first.

Follow-ups. Where do you get training pairs?

Debug a failureA fine-tuned embedding model performs worse in production than in the eval. Why?

Worked answer. Production queries differ from the training and eval distribution (shorter, more Hinglish, more typos), the index was built with a different model version, or documents were embedded without the same preprocessing. Compare query and document preprocessing, and sample production queries into the eval.

A plausible wrong answer. "Fine-tuning does not work." Distribution mismatch is the usual cause.

Follow-ups. How would you collect production pairs safely?

Defend a designFine-tune an embedding model, or add a reranker?

Worked answer. A reranker first: no re-indexing, and it often gives a larger precision gain. Fine-tune when recall at the candidate stage is the problem (the right passage is not in the top 50 at all), which a reranker cannot fix. Measure both.

A plausible wrong answer. "Fine-tuning is always better because it is custom." It is more work and requires re-embedding everything.

Follow-ups. How would you combine both?

Check your understanding

Q1What does contrastive training teach an embedding model?

Each query is pulled towards its relevant passage and pushed away from the others. Hard negatives carry most of the signal.

Q2The right passage is not even among the top 50 candidates. Which fix addresses that?

A reranker can only reorder what the first stage found. When recall at the candidate stage is the problem, the retriever has to improve.
