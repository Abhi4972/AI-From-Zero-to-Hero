In plain words first
The idea in one line

Before LLaVA-OneVision (Li et al., August 2024) the open-VLM world had separate lineages: LLaVA-1.5 for single images, multi-image models like Mantis and VILA, video models like Video-LLaVA and Video-LLaMA. Each won its benchmark and failed at the others. LLaVA-OneVision argued a single curriculum could train one model to dominate all three scenarios, and that the emergent task-transfer effects (single-image skills exported to video, multi-image reasoning exported to single-image) beat the sum of specialists. The problem

In plain words first

Early open vision-language models specialised: one handled single photos, another compared several images, a third watched videos. LLaVA-OneVision trains one model for all three. It keeps the language model's input roughly the same size in every case: one image is cut into high-resolution tiles, several images get one view each, and video frames are pooled down to fewer tokens. Training starts with single images to build perception, then mixes in multi-image and video data. This lesson explains the token budget and the curriculum. It then runs LLaVA-OneVision's real preprocessing code (configuration and tokenizer files only, no weights) to count how many visual tokens each kind of input actually costs. No model is trained.

Image, multi-image, and video each stress a model differently.

Single-image wants high-resolution tokens (AnyRes, ~2880 visual tokens) to catch OCR and fine detail. Budget per sample: one image, 2880 tokens.

Multi-image wants several images at moderate resolution (~576 tokens each) so reasoning across images fits in context. Budget per sample: 4-8 images, 576 each, 2300-4600 tokens.

Video wants many frames at low resolution (~196 tokens per frame after pooling) to capture temporal dynamics. Budget per sample: 8-32 frames, 196 each, 1600-6200 tokens.

If you train separate models, you pick one budget. If you train one model, you need the budget to scale sensibly across scenarios without blowing context.

Pre-OneVision, the default answer was "train one scenario, ignore the others." Video-LLaVA retrofitted video onto an image model with extra training stages. LLaVA-NeXT added multi-image support with tiling. None handled all three cleanly.

Idea 1 · The OneVision token budget

LLaVA-OneVision does not fix one exact token count. It balances the maximum visual-token count per sample so the three scenarios land in the same range, roughly 6,000 to 9,000 tokens, allocated differently per scenario:

  • Single image: AnyRes-Max-9 (up to 9 tiles + one base view), each 384x384 view giving 729 tokens from SigLIP SO400M. Maximum: 729 * (1 + 9) = 7290 tokens.
  • Multi-image: each image at 384 with no tiling, 729 tokens with no pooling. Up to 12 images → 8748 tokens.
  • Video: up to 32 frames at 384 with 2x2 bilinear pooling → 196 tokens per frame. Total: 32 * 196 = 6272 tokens.

The allocation keeps the maximum totals in the same band, so no scenario dominates the context or the gradient. The encoder produces different geometry per scenario, but the LLM consumes a similar budget. The code/main.py planner below uses a smaller toy budget of 4096 to show the same balancing logic.

Idea 2 · The three-stage curriculum

LLaVA-OneVision trains in stages:

  1. Alignment (stage 1). Only the projector trains, on 558K image–caption pairs, as in LLaVA-1.5.
  2. High-quality knowledge (stage 1.5). The whole model trains on about 4M high-quality, mostly synthetic, detailed captions and documents.
  3. Single-image instruction tuning (stage 2, part 1). About 3.2M single-image samples at high resolution (AnyRes). This builds perception, OCR and fine-grained understanding.
  4. OneVision instruction tuning (stage 2, part 2). About 1.6M samples mixing single images, multiple images and video, continuing from the single-image model.

The order is deliberate: the paper builds strong single-image skills first and then transfers them to multi-image and video data, which is much scarcer.

Idea 3 · Why curriculum works

Single-image training builds the perceptual base. Patch tokens carry fine-grained visual features; the LLM learns to integrate them with text. Multi-image and video introduce structural challenges (which image is which, what happened first) that are hard to learn without a strong perceptual base.

A plausible reason: if all scenarios are mixed from the start, single-image data is a smaller share of each batch, so perception may be learned less thoroughly while the model fits the structure of multi-image and video prompts.

The curriculum aims for perception strength from the single-image stage, then compositional and temporal reasoning from the OneVision stage, without losing either.

Idea 4 · Emergent cross-scenario skills

The LLaVA-OneVision paper reports three emergent capabilities:

  1. Multi-camera reasoning. Trained on multi-image + video separately; at inference, asked to reason about a multi-camera driving scene. The model correctly integrates the views despite never seeing that exact format in training.
  2. Set-of-mark prompting. User annotates objects in an image with numbered marks; the model reasons about "what is mark 3 doing relative to mark 7." Trained on neither marks nor annotation; learned from the combination of spatial grounding + multi-image reference.
  3. Screenshot agent. Given an iPhone screenshot, the model describes the screen and plans the next tap, a GUI-agent task it was not specifically trained for.

The paper presents these as emergent: combinations of skills learned from different scenarios, shown as qualitative examples rather than benchmark results.

Idea 5 · Visual-token pooling

The token budget requires pooling. OneVision uses bilinear interpolation on the 2D patch grid: SigLIP's 27x27 = 729 patches per 384-px frame become 14x14 = 196 (2x factor), which is the video setting. Pooling is done in patch-grid space, not token space, to preserve locality.

The choice of pooling factor per scenario is itself a hyperparameter. Less pooling = more tokens = richer representation. More pooling = fewer tokens = more frames / images fit.

The same idea as a formula

One view from SigLIP at 384 px with 14-px patches: ⌊384/14⌋2=272=729 tokens.

Single image, AnyRes with a grid of g tiles (at most 9 in the paper's AnyRes-Max-9) plus a base view:

nimage​≈729(g+1)(+ one newline token per row of the tile grid).

Video: each frame's 27×27 grid is pooled bilinearly by 2 to ⌈27/2⌉2=142=196 tokens, so T frames cost

nvideo​=196T (+1).

Budget rule: choose g, the number of images and T so that each scenario's maximum stays in a similar range (about 6,000–9,000 tokens in the paper).

Worked example
Three requests, similar budgets
  • One large photo with a 3×3 grid: 729×(9+1)=7,290 tokens, plus 81 row-newline tokens in the Hugging Face implementation: 7,371.
  • Video, 32 frames: 32×196=6,272, plus one newline: 6,273.
  • Twelve images at one 729-token view each, the paper's multi-image setting: 12×729=8,748.
  • The three maxima are within about 1.4× of each other, so no scenario dominates the context during training.
Check your mental model
  • ✗ "OneVision gives every image the same number of tokens."
    ✓ A single image gets high-resolution tiles, multiple images get fewer tokens each, and video frames are pooled.
  • ✗ "Pooling video frames throws away the frames."
    ✓ It keeps every sampled frame but averages neighbouring patches, trading spatial detail for temporal coverage.
  • ✗ "The library always follows the paper's budget."
    ✓ Check the processor: the Hugging Face implementation tiles every image, even in multi-image prompts (measured below).

See it drawn
Visual tokens per scenario, from the real processor

LLaVA-OneVision's Hugging Face processor, from the 0.5B model's configuration and tokenizer (no weights), counts the visual tokens the language model would receive for single images of three sizes, four images at two sizes, and videos of 8 and 32 frames. A few seconds.

import numpy as np
from PIL import Image
from transformers import AutoConfig, AutoProcessor, logging
logging.set_verbosity_error()

# LLaVA-OneVision's real processor (config and tokenizer files only, no weights): visual tokens per scenario
repo = "llava-hf/llava-onevision-qwen2-0.5b-ov-hf"
proc, cfg = AutoProcessor.from_pretrained(repo), AutoConfig.from_pretrained(repo)
print(f"SigLIP at {cfg.vision_config.image_size} px, {cfg.vision_config.patch_size}-px patches -> "
      f"{(cfg.vision_config.image_size // cfg.vision_config.patch_size) ** 2} tokens per view; "
      f"{len(cfg.image_grid_pinpoints)} AnyRes grids up to {cfg.image_grid_pinpoints[-1]} px\n")

def visual_tokens(content, **inputs):
    text = proc.apply_chat_template([{"role": "user", "content": content}], add_generation_prompt=True)
    ids = proc(text=text, return_tensors="pt", **inputs).input_ids[0]
    return int((ids == cfg.image_token_index).sum() + (ids == cfg.video_token_index).sum())
photo = lambda w, h: Image.new("RGB", (w, h), (90, 140, 200))
ask = {"type": "text", "text": "Describe."}
rows = [("1 image, 384 x 384", [{"type": "image"}, ask], dict(images=photo(384, 384))),
        ("1 image, 1024 x 768", [{"type": "image"}, ask], dict(images=photo(1024, 768))),
        ("1 image, 2304 x 2304 (largest grid)", [{"type": "image"}, ask], dict(images=photo(2304, 2304))),
        ("4 images, 384 x 384 each", [{"type": "image"}] * 4 + [ask], dict(images=[photo(384, 384)] * 4)),
        ("4 images, 1024 x 768 each", [{"type": "image"}] * 4 + [ask], dict(images=[photo(1024, 768)] * 4)),
        ("video, 8 frames", [{"type": "video"}, ask], dict(videos=[np.zeros((8, 384, 384, 3), np.uint8)])),
        ("video, 32 frames", [{"type": "video"}, ask], dict(videos=[np.zeros((32, 384, 384, 3), np.uint8)]))]
print(f"{'input':<38}{'visual tokens':>14}{'per image / frame':>19}")
for label, content, inputs in rows:
    n = visual_tokens(content, **inputs)
    k = 4 if label.startswith("4 ") else int(label.split()[1]) if label.startswith("video") else 1
    print(f"{label:<38}{n:>14,}{n / k:>19,.0f}")

Reading this output

Even a small image gets tiled. A 384 × 384 image fits one SigLIP view (729 tokens), yet the processor returns 1,485. It adds a base view and a one-tile grid, plus 27 row-newline tokens. A 1024 × 768 photo gets a larger grid: 4,725 tokens.

The cap is AnyRes-Max-9. A 2304 × 2304 image hits the largest grid; tiles beyond nine are pooled down, and the total stops at 7,371: 729 for the base view, 6,561 for a 3 × 3 grid's worth of tiles, and 81 newlines. That matches the paper's single-image maximum of about 7,300 tokens.

Multi-image prompts are not reduced here. The paper's multi-image setting gives each image a single 729-token view. The Hugging Face processor tiles every image instead: four 384-px images cost 5,940 tokens, and four 1024 × 768 photos 18,900. The model accepts the input, but it is far beyond the budget it was trained with. Downscale, or give the processor a smaller grid setting, before sending many images.

Video follows the budget exactly. Every frame is pooled from 27 × 27 to 14 × 14, so 196 tokens: 1,569 for 8 frames and 6,273 for 32, the paper's video maximum plus one newline token.

Idea 6 · LLaVA-OneVision-1.5

The 2025 follow-up (LLaVA-OneVision-1.5, arXiv 2509.23661) is "fully open" in training data, model weights, and code. It keeps the ViT–MLP–LLM design but changes the parts: a RICE-ViT encoder, a projector that merges 2×2 neighbouring patches, Qwen3 language models, an 85M-pair mid-training set and a 22M-sample instruction set. The 8B model outperforms Qwen2.5-VL-7B on 18 of 27 benchmarks.

Idea 7 · Contrast with Qwen2.5-VL

Qwen2.5-VL (Lesson 12.09) makes different choices. It uses M-RoPE and dynamic FPS instead of fixed pooling. Its budget scales with input — a 1-minute video uses more tokens than a 5-second video. LLaVA-OneVision fixes the budget and scales the pooling. Both work; they trade configurability for predictability.

Use it: the same idea with real libraries

code/main.py is a curriculum and budget planner for a OneVision-style VLM. Given a token budget per sample and a target scenario mix (say 40% single-image, 30% multi-image, 30% video), it:

  • Allocates resolution, pooling factor, and frames per scenario.
  • Checks that every scenario fits within the shared budget.
  • Reports expected token count, LLM FLOPs, and which scenarios are under-tokenized.
  • Prints a stage-by-stage training schedule.

Use it to plan a OneVision fine-tune or to sanity-check a VLM deployment's per-request cost.

Industry practice
What's current (2024–2026)
  • One model for images, multiple images and video is now the norm: Qwen2.5-VL and Qwen3-VL, InternVL3, Gemma 3 and LLaVA-OneVision-1.5 all handle the three scenarios.
  • Fully open recipes: LLaVA-OneVision-1.5 releases data, code and weights; its 8B model beats Qwen2.5-VL-7B on 18 of 27 benchmarks.
  • Token budgets per request are explicit knobs in production: maximum pixels per image, frames per second, maximum frames, and pooling or merging factors.
  • Video tokens are compressed aggressively: 2×2 pooling or merging per frame is common, with frame sampling set by fps (Lesson 12.9).

Sources: LLaVA-OneVision (arXiv 2408.03326), LLaVA-OneVision-1.5 (arXiv 2509.23661), Hugging Face LLaVA-OneVision documentation, Qwen2.5-VL technical report (arXiv 2502.13923).

Recap
What to keep from this lesson
  • One model, three scenarios: single image, multiple images, video.
  • Keep the visual-token budget similar across scenarios: tiles for one image, one view per image for many, pooling for video.
  • 729 tokens per 384-px view; 196 per pooled video frame.
  • Train single-image first, then mix in multi-image and video.
  • Check what your processor actually does; budgets live in preprocessing.

Ship it

This lesson produces outputs/skill-onevision-budget-planner.md. Given a target task distribution and a per-sample budget, it emits the AnyRes factor, per-frame pooling, video frame count, and curriculum stage weights. Use this whenever you train or fine-tune a unified-scenario VLM.

Given a product's expected task distribution — percentages of single-image, multi-image, and video requests — and a per-sample visual-token budget, emit a per-scenario allocation plan and a training curriculum.

Produce:

1. Per-scenario config. Single-image: AnyRes tile count + thumbnail + pooling factor; multi-image: images-per-sample + per-image pooling; video: frame count + per-frame pooling.
2. Token budget balance. Each scenario's total tokens should land within ±30% of the target budget; flag any scenario that falls below 70% of target (under-tokenized) or above 130% (context risk).
3. Curriculum plan. Three stages (SI → OV → TT) with data weights. For the TT stage, use the user's product mix.
4. Expected emergent skills. Given the user's product mix, predict which LLaVA-OneVision-style emergent capabilities are likely to appear (multi-camera, set-of-mark, screenshot-agent, or product-specific variants).
5. Training-data ballpark. Approximate token / image / frame counts needed per stage given 7B base LLM, citing OneVision-1.5 data scale.

Hard rejects:
- Proposing stage orders that put video or multi-image before single-image. OneVision shows this loses 2-4 MMMU.
- Allocating all budget to video when the product is 80% single-image. Waste, not balance.
- Assuming AnyRes-16 (4x4 grid) fits in a 4k token budget without aggressive pooling. It does not.

Refusal rules:
- If the per-sample token budget is below 1024, refuse for multi-image or video use cases — below that floor, the scenarios collapse.
- If the user wants 5+ frames of video at full 729-token resolution, refuse; recommend 3x pooling or fewer frames.
- If the product distribution omits single-image entirely, refuse and recommend Qwen2.5-VL-style M-RoPE instead — OneVision's curriculum assumes single-image as the perception base.

Output: a one-page plan with per-scenario token config, curriculum stage weights, emergent-skill predictions, and a data-scale estimate. End with pointers to arXiv 2408.03326 (OneVision) and arXiv 2509.23661 (OneVision-1.5 fully open).

Exercises

  1. Your product supports 80% single-image, 10% multi-image (2-4 images), 10% video (8-16 frames). Design the token budget. Where would you put the extra budget you save from not doing heavy multi-image?

  2. Read LLaVA-OneVision Section 4.3 (emergent capabilities). Propose a fourth emergent skill the curriculum would likely unlock but the paper did not report.

  3. Swap the curriculum order — train multi-image first, then single-image, then video. Predict which benchmarks degrade and why.

  4. The paper reports video benchmarks trained on only 8 frames per sample. Does that generalize to 30-second videos at inference? What breaks first — the token budget or the temporal reasoning?

  5. Bilinear pooling of 24x24 patches to 12x12 is a 2x reduction per dimension, so 4x fewer tokens. Implement the pooling in stdlib Python and verify that the mean over each 2x2 block matches the bilinear output.

Solutions

SolutionP1 · 1,485 for a small image, 18,900 for four photos

1,485 tokens for a single 384 × 384 image: a base view and a one-tile grid of 729 each, plus 27 row-newline tokens. That is about twice what the image needs, because the processor always tiles. Four 1024 × 768 photos cost 18,900 tokens (4,725 each), more than double the paper's multi-image maximum of about 8,700. Budgets are enforced in preprocessing, so measure what your processor actually produces.

SolutionB1 · Ten photos overflow the budget

Each 4032 × 3024 photo is tiled to the largest grid, about 7,000 tokens, so ten photos produce about 70,000 visual tokens. That is roughly ten times the budget the model was trained on. It may exceed the context limit you serve with, and it multiplies prefill time and KV-cache memory (Lesson 12.3). Even when it fits, the model rarely saw prompts like this in training, so quality on "what changed" questions can drop. Instead, resize each photo so it gets one view (or a small grid), which is closer to the paper's multi-image setting. Cap the number of images per request, or describe pairs of photos and then compare the descriptions. Then count visual tokens in your request logs, as the run above does.
