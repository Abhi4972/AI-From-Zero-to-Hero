In plain words first
The idea in one line

A large model takes minutes to go from cold to serving: a 70B model on a fresh node needs roughly 3-8 minutes before the first token. In a true serverless world, that is not a warm-up — it is an outage. Mitigations operate at five layers: pre-seeded node images (Bottlerocket on AWS, dual-volume arch), model streaming (NVIDIA Run:ai Model Streamer, native in vLLM), GPU memory snapshots (Modal checkpoints, up to 10x faster restart), warm pools (min_workers=1), tiered loading (ServerlessLLM's NVMe→DRAM→HBM pipeline, 10-200x latency reduction), plus a bonus sixth pattern, live migration that moves input tokens (KB) rather than KV cache (GB). Modal publishes 2-4s cold starts as a floor; Baseten 5-10s default, sub-second with pre-warming. This lesson teaches you to measure, budget, and stack the five layers.

Terms you'll hear
Term What people say What it actually means
Cold start "the big pause" Time from request to first token on a fresh replica
Warm pool "always-on minimum" min_workers >= 1 to keep at least one replica ready

min_workers "warm replicas" Serverless minimum keep-alive count
Scale-to-zero "full serverless" No cost when idle; accept full cold-start tax

The problem

In plain words first

A cold start is the wait when a request arrives and no copy of the model is running: a GPU machine must be found, the software image downloaded, tens of gigabytes of weights loaded into GPU memory and the engine started. For a 70B model that can take several minutes. Scaling to zero (running nothing when nobody is using the model) saves money but makes the next user pay that wait. The fixes attack each step: machine images with the model already on disk, streaming weights onto the GPU while loading, GPU snapshots that restore a running model in seconds, and warm pools, which keep one copy always running at the cost of paying for it all day.

Your serverless LLM endpoint scales to zero overnight. At 8 a.m. traffic spikes. The first request waits while:

  1. Karpenter provisions a GPU node: 45-60s.
  2. The container pulls a 30 GB image with weights: 120-300s.
  3. The engine loads weights into HBM: 45-120s depending on model size and storage speed.
  4. vLLM or TRT-LLM initializes CUDA graphs, KV cache pool, tokenizer: 10-30s.

Total: 220-510s (roughly 3-8 minutes) before one token comes back. Your SLA is 2s. You ship a warm-pool (min_workers=1) and the problem seems to vanish — but now you pay for one idle GPU 24x7. If your service has 5 products each with one warm replica, that's 5 × 24 × 30 = 3,600 GPU-hours/month whether or not a single user called.

Cold-start mitigation is how to keep the serverless economics while approximating the latency of always-on.

Idea 1 · Layer 1 — pre-seeded node images (Bottlerocket)

On AWS, Bottlerocket's dual-volume architecture separates OS from data. Snapshot the data volume with your container image pre-pulled; reference the snapshot ID in your EC2NodeClass. New nodes boot with weights already on local NVMe — steps 2 and part of 3 vanish. Works with Karpenter natively. Typical savings: 2-4 minutes per cold start for large models.

Equivalent on GCP: custom VM images with pre-baked container layers. On Azure: managed disk snapshots with the same pattern.

Idea 2 · Layer 2 — model streaming (Run:ai Model Streamer)

Instead of loading the full file before answering the first request, stream weights into GPU memory layer-by-layer and start processing as soon as the first transformer block is resident. The NVIDIA Run:ai Model Streamer ships native in vLLM 2026. Works with S3, GCS, and local NVMe. Cuts weight-load time roughly in half for large models by overlapping I/O with compute setup.

Idea 3 · Layer 3 — GPU memory snapshots (Modal)

Modal takes a checkpoint of the GPU state (weights, CUDA graphs, KV cache region) after first load. Subsequent restarts deserialize directly into HBM — 10x faster than re-initializing. This is the closest thing to "boot a warm GPU in 2 seconds." Trade-off: snapshots are per-GPU-topology, so if Karpenter migrates you to a different SKU, you re-checkpoint.

Idea 4 · Layer 4 — warm pools (min_workers=1)

Simplest mitigation: keep one replica always ready. Cost is one GPU's hourly rate 24x7. The arithmetic is brutal on small models (you pay $0.85-$1.50/hr to avoid a 30s cold start) and kind to large ones (pay $4/hr to avoid a 5-minute cold start). The SLA threshold where warm pools become mandatory: typically TTFT P99 < 60s on a 70B+ model.

Idea 5 · Layer 5 — tiered loading (ServerlessLLM)

ServerlessLLM treats storage as a hierarchy: NVMe (fast but big), DRAM (medium but tiered), HBM (tiny but instant). Weights are pre-loaded to DRAM; load-on-demand into HBM. Paper reports 10-200x latency reduction on cold loads versus naive disk-to-HBM. Production adoption is early but integrations with vLLM exist.

Idea 6 · Layer 6 — live migration (bonus pattern)

When a node becomes unavailable (spot eviction, node drain), traditional pattern is cold-start another replica and drain request queue. Live migration moves the input tokens (kilobytes) to a destination that has the model loaded and recomputes KV cache on the destination. Recomputation is cheaper than transferring GB of KV cache over the network. Applicable to disaggregated deployments.

Idea 7 · The warm-pool math

For a service with P99 TTFT SLA of 2s, the question is not "warm pool yes/no" but "how many warm replicas, and which paths get them."

  • High-value interactive paths (live chat, voice agent): min_workers=1-2.
  • Background batch paths (nightly classification): scale-to-zero accepted, 5-10 minute cold start tolerable.
  • Premium tier: min_workers per tenant with dedicated capacity.

Idea 8 · Measure before optimizing

Idea 9 · Numbers you should remember

  • Modal cold start: 2-4s (with GPU snapshots).
  • Baseten default cold start: 5-10s; sub-second with pre-warming.
  • Raw 70B cold start: 3-8 minutes.
  • Run:ai Model Streamer: ~2x weight-load speedup.
  • ServerlessLLM tiered loading: 10-200x latency reduction (paper numbers).

Worked example
Is one warm replica worth it?

A warm H100 replica costs $4.50 an hour, $3,240 a month. Without it, every request that arrives after the model has scaled down waits 328 s (5.5 minutes).

  1. At 1 request an hour, the model is cold for almost every request: about 20 cold starts a day. With a budget of 5 tolerated slow requests a day, 15 are over budget; at a premium product, each is a lost user. The warm replica is worth it.
  2. At 10 requests an hour, the model rarely scales down: about 2 cold starts a day, under budget. The warm replica buys little.
  3. The decision is about how often traffic gaps are longer than the scale-down timer, not about average traffic.

Which statements are right?

  • ✓ Pre-seeded node images remove the image pull, the largest step for big models.

  • ✓ GPU memory snapshots can restore a loaded model in a few seconds.
  • ✗ Cold-start time is mostly the GPU node starting up. For a 70B model, image pull and weight loading take most of the time.

Part 1 of 3 · Phase, total_for_stack

"""Cold-start mitigation path simulator — stdlib Python.

Models a 70B model cold-start with different mitigation stacks:
  RAW              : no mitigations (nominal baseline)
  PRE_SEEDED       : + Bottlerocket pre-seeded node image
  STREAMER         : + NVIDIA Run:ai Model Streamer
  GPU_SNAPSHOT     : + Modal-style GPU snapshots
  WARM_POOL        : min_workers=1 (no cold start at all on warm path)

Reports per-layer seconds and totals. Also computes warm-pool break-even.
"""

from __future__ import annotations

from dataclasses import dataclass


@dataclass
class Phase:
    name: str
    raw_sec: float
    pre_seeded_sec: float    # 0 if eliminated
    streamer_sec: float      # replaces raw if streamer active
    snapshot_sec: float      # replaces all if snapshot active


PHASES_70B = [
    Phase("node provision",   50.0, 50.0,  50.0,  0.5),
    Phase("image pull",      180.0,  0.0, 180.0,  0.0),
    Phase("weights to HBM",   75.0, 75.0,  35.0,  0.0),
    Phase("engine init",      20.0, 20.0,  20.0,  2.0),
    Phase("first forward",     3.0,  3.0,   3.0,  0.5),
]


def total_for_stack(stack: set[str]) -> float:
    seconds = 0.0
    for phase in PHASES_70B:
        if "gpu_snapshot" in stack:
            seconds += phase.snapshot_sec
        elif "streamer" in stack and "pre_seeded" in stack:
            used = phase.pre_seeded_sec
            if phase.name == "weights to HBM":
                used = phase.streamer_sec
            seconds += used
        elif "pre_seeded" in stack:
            seconds += phase.pre_seeded_sec
        elif "streamer" in stack:
            seconds += phase.streamer_sec if phase.name == "weights to HBM" else phase.raw_sec
        else:
            seconds += phase.raw_sec
    return seconds

Part 2 of 3 · report_stack, warm_pool_break_even, main

def report_stack(label: str, stack: set[str]) -> None:
    total = total_for_stack(stack)
    mins = total / 60
    print(f"{label:20}  {total:6.1f} s  ({mins:4.1f} min)  stack={sorted(stack) if stack else '{baseline}'}")


def warm_pool_break_even(gpu_hourly: float, cold_seconds: float, sla_tolerated_drops_per_day: int) -> None:
    print("\n" + "=" * 80)
    print("WARM POOL BREAK-EVEN")
    print("=" * 80)
    print(f"GPU cost: ${gpu_hourly:.2f}/hr  |  cold start: {cold_seconds:.0f}s  |  drop budget: {sla_tolerated_drops_per_day}/day\n")
    warm_monthly = gpu_hourly * 24 * 30
    print(f"Warm pool (min_workers=1) monthly cost: ${warm_monthly:.2f}")
    print()
    print(f"{'Req/hr':>8}  {'Expected cold starts/day':>24}  {'Drops over budget':>20}  {'Warm better?':>15}")
    for rate in (1, 5, 10, 25, 50, 100, 250):
        cold_starts_per_day = 24 / max(rate, 1) if rate < 1 else 1
        cold_starts_per_day = min(20, max(1, int(24 * 3600 / (rate * 3600))))
        drops = cold_starts_per_day
        warm_better = "yes" if drops > sla_tolerated_drops_per_day else "no"
        print(f"{rate:>8}  {cold_starts_per_day:>24}  {max(0, drops - sla_tolerated_drops_per_day):>20}  {warm_better:>15}")


def main() -> None:
    print("=" * 80)
    print("COLD START MITIGATION: 70B model on fresh H100 node")
    print("=" * 80)
    print(f"{'Stack':20}  {'Total':>8}             Stack composition")
    print("-" * 80)

    report_stack("RAW",                      set())
    report_stack("+ PRE_SEEDED",             {"pre_seeded"})
    report_stack("+ STREAMER",               {"streamer"})
    report_stack("+ PRE_SEEDED + STREAMER",  {"pre_seeded", "streamer"})
    report_stack("+ GPU_SNAPSHOT",           {"gpu_snapshot"})

    print("\n(WARM_POOL avoids cold start entirely on the warm path; cost is 24x7 GPU rental)")

    warm_pool_break_even(gpu_hourly=4.50, cold_seconds=328, sla_tolerated_drops_per_day=5)

Given model size, SLA (TTFT P99), traffic shape (steady vs bursty), and budget posture, produce a cold-start mitigation plan.

Produce:

1. Cold-start budget. Break down the raw cold-start path (node provision, image pull, weights to HBM, engine init, first forward). Use 2026 nominal seconds for the stated model size.
2. Layer selection. Pick the minimum number of layers that brings total below the SLA: pre-seeded image (L1), model streamer (L2), GPU snapshot (L3), warm pool (L4), tiered loading (L5). Justify each layer against the specific phase it attacks.
3. Warm-pool sizing. State `min_workers` for the primary path. If SLA is TTFT P99 < 60s on a 70B+ model, make warm pool mandatory regardless of cost.
4. Cost estimate. Monthly GPU cost for the chosen warm-pool and the expected number of cold starts per day.
5. Tail policy. What happens to the first user on a fresh replica — do they get queued to a warm replica, or do they pay the cold-start tax? Name a specific policy (e.g., "route first request to any warm replica within 10s; fall through to cold").
6. Failure mode. What happens if a warm replica dies mid-session. Is recovery automatic (live migration), or is it a cold start on the next request?

Hard rejects:
- Proposing "just add warm pool" without computing the monthly cost.
- Claiming a mitigation without a specific phase it attacks (e.g., "use Bottlerocket" without saying it eliminates the 180s image pull).
- Ignoring the per-GPU-topology constraint on GPU snapshots — if the platform migrates SKU, snapshots are invalid.

Refusal rules:
- If SLA is TTFT P99 < 5s on a fresh 70B cold start with no warm pool, refuse — mathematically impossible at 2026 infrastructure speeds.
- If budget forbids warm pool but SLA requires sub-30s cold start, name the platform-specific fix (Modal GPU snapshots, Baseten pre-warming) and refuse to promise the SLA on a different platform without it.
- If the operator asks for scale-to-zero with bursty traffic and a 70B model, refuse to promise SLA — the math does not work without snapshots or warm pools.

Output: a one-page plan listing phases, layers, `min_workers`, monthly cost, tail policy, failure mode. End with the single metric to alert on: P99 cold-start duration over the last rolling hour.

Solutions

SolutionP1 · Break-even request rate

In code/main.py the warm replica costs $3,240 a month. At 1 request an hour there are about 20 cold starts a day, 15 over the drop budget, so the warm replica wins; from about 5 requests an hour the model rarely goes cold and the drops stay within budget. The break-even sits between 1 and 5 requests an hour for this scale-down timer.

SolutionP3 · Weights from NVMe

70B in BF16 is 140 GB. At 7 GB/s: 140 / 7 = 20 s to read, plus GPU transfer and allocation, so roughly 25–30 s. In FP8 (70 GB) about 10–15 s. Streaming overlaps this with the first forward passes.

SolutionB1 · Twelve warm replicas

Most of those tools have long idle gaps, so a warm replica each is paid for and unused. Better: group the tools onto one shared server (several small models, or LoRA adapters on one base), keep one warm replica for the few latency-critical ones, and let the rest scale to zero with pre-seeded images and a GPU snapshot so their cold start is seconds, not minutes.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designYour model service runs as a plain Deployment with an autoscaler on CPU use. During a traffic spike the autoscaler added replicas late, kept adding them while the new pods were still loading weights, and a liveness probe restarted the busiest pod in the middle of the spike. Redesign the scaling and the probes.

Level 3 of 4 · about 15 minutes to answer well.

Short answer. Scale on the engine's own signals, not on CPU: the count of waiting requests and the KV cache usage say that a server is saturated long before CPU does. Give the startup probe a window longer than your measured cold start, so that a loading pod is neither sent traffic nor restarted, and make the liveness probe cheap, so that a busy server does not lose its busiest pod to a probe that waited in the queue. Keep the weights and the compile cache on persistent storage, so that a new replica is ready in a fraction of the time.

Why CPU is the wrong signal.

GPU load is not CPU load. A saturated engine shows waiting requests above zero and cache usage near one while the CPU looks calm. The vLLM manual says this directly about the plain Deployment: it routes at random and scales on the wrong signal. The routing layers that the manual lists read vllm:num_requests_waiting, vllm:num_requests_running and vllm:kv_cache_usage_perc to pick a replica, and an autoscaler should read the same series.

Read the signals in pairs.

Reading Meaning
waiting above 0, cache usage below 0.9 the batch size or the token budget limits admission, not memory
waiting above 0, cache usage near 1 the pool limits admission, so add memory or replicas
slow first token with nothing waiting long prompts or a slow tokenizer, not a capacity problem
preemptions with long answers running requests grow until the pool runs out

The second row is a reason to add a replica, because the pool is full. On the first row, raise the batch limit or the token budget first, while the pool has room. If the queue stays after that, or the limit is already where the latency target needs it, add a replica, because each replica brings its own batch limit and token budget.

Probes that match a slow start.

The manual's example gives the startup probe 90 checks at 10 second intervals, which is 15 minutes, and notes that its own machine took about 8 minutes for a first start. Set the window from your measured cold start. For readiness, send one short real request, which proves the engine can generate, or use the ready endpoint on an engine that has one. For liveness, use a cheap health path. The SGLang manual turns generation off in the health endpoint, because a probe that generates waits in the queue under load, times out after 20 seconds, and marks a busy server unhealthy. In one incident each failed probe also left an orphan request in the scheduler, so the probes added to the load they were meant to detect.

Stop the overshoot.

New pods take minutes to load. The autoscaler sees the signal still high and adds more. Give it a stabilization window at least as long as the cold start, cap the replicas added per step, and shorten the cold start itself: weights on local disk, the compile cache on a persistent volume, and a preload before the server takes traffic. The cold start lesson adds the warm pool for the interactive path, so that the first replica is never a cold one.

Scale down without losing work.

Remove the pod from the load balancer, send SIGTERM to the main process only, and set a grace period at least as long as the longest request at the output cap. A forced kill, or a signal to the whole process group, drops every running request.

Plausible wrong answers.

  • "Scale on GPU utilization instead of CPU." Utilization can read high while requests wait and low while the pool is full. The queue and the cache usage are the signals the engine exposes for this.
  • "Make the liveness probe stricter so that bad pods restart faster." Under load a strict probe restarts healthy, busy pods. The fix is a cheap probe and a long startup window.
  • "Add replicas faster to beat the spike." Replicas that take minutes to load add nothing during the spike and cost money after it. Shorten the cold start and keep a warm margin.

Follow-ups an interviewer may ask.

  • (level 3) Which pair of readings says the pool is the bottleneck, not the batch limit? Expected: waiting requests above zero with cache usage near one. With cache usage below 0.9, the batch size or the token budget limits admission instead.
  • (level 3) Why does a generating health probe hurt under load? Expected: its request waits in the queue like any other, times out, and marks a busy server unhealthy. In one incident each failed probe also left an orphan request behind.
  • (level 4) How do you keep the autoscaler from overshooting during a cold start? Expected: a stabilization window at least as long as the measured cold start, a cap on replicas added per step, and a shorter cold start from persistent weights and compile caches.
  • (level 4) What does a scale-down need so that no request is lost? Expected: remove the pod from the load balancer, send SIGTERM to the main process only, and a grace period at least as long as the longest request at the output cap.

Estimate itA pod serving an MoE model on a unified-memory machine took about eight minutes from start to ready. Break that time into its parts, say which parts a restart can skip, and estimate what a warm restart looks like on the same machine.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Most of the time was the weight load. The manual's log shows about 330 seconds to copy 57 GiB of weights into memory on that machine, one tensor at a time from a file-backed page. The engine init took 127.54 seconds, and it holds the two CUDA graph captures of 39 and 38 seconds and a compile share of 18.67 seconds. A restart reuses the compile cache and nothing else, so a warm restart on that machine is only a little shorter than the cold one, unless the weights are staged in host memory or a process snapshot exists, which a field report took from a cold start of 695 seconds to 9.6 seconds.

The parts, from the startup log.

Phase Measured Where it is logged
weight load 56.93 GiB in about 330 seconds the model loading line
engine init, profile, KV cache, warmup, with both graph captures 127.54 seconds, of which compilation 18.67 the init engine line
first graph capture, inside engine init 39 seconds, 1.17 GiB the first graph capturing line
second graph capture, inside engine init 38 seconds, 0.31 GiB the second graph capturing line

The two captures finish before the init line, so they are part of its 127.54 seconds. Do not add them to it.

The server reported ready about eight minutes after it read its arguments. The load alone is more than two thirds of it.

Why the load is slow on this machine.

Each tensor is copied from the memory-mapped weights file into the GPU allocation. On this platform an open issue measured about 1.7 ms per tensor copied from the file view, against about 0.2 ms for a copy that starts in host memory. The release that the manual pins saved about 25 seconds with an indexed lookup of expert names, and the per-tensor copy cost stays. The manual's advice: keep the weights on local NVMe, not on a network mount, and start the server once and keep it running.

What a restart skips.

The compile cache lives under the engine's cache directory. Keep it on a persistent volume, and a later start reads it, so the compile share shrinks. SGLang points all of its kernel caches into one directory for the same reason, and the manual mounts it on a volume that survives the pod. The graph captures and the weight load repeat on every start. So the honest estimate for a warm restart on this machine is the cold start minus the compile share, which is still several minutes.

Getting under a minute.

The lesson on cold starts maps each phase to a layer: a pre-seeded image removes the image pull, model streaming roughly halves the weight load, and a GPU memory snapshot restores the loaded state about ten times faster than a reload. The SGLang manual quotes a field report with the same shape on a different engine and eight GPUs: a cold start of 695 seconds with 531 of them in weight loading, 88 seconds with kernel caches kept, and 9.6 seconds with a process checkpoint and the weights staged in host memory. Below a minute means a snapshot or staged weights, not a faster disk.

What the number sets.

The Kubernetes example in the vLLM manual gives the startup probe checks at 10 second intervals across a 15 minute window, and tells you to set the window from your own measured cold start. An autoscaler needs a stabilization window at least as long, and the interactive path needs a warm replica, because no scale-out helps inside an eight-minute window.

Plausible wrong answers.

  • "The compile is the slow part, use eager mode." The compile share was 18.67 seconds of an eight-minute start, and eager mode costs decode speed on every request afterwards.
  • "A faster GPU loads faster." The load was bound by the copy path from the file view, not by the GPU.
  • "Restart often to pick up configuration changes." Each restart pays the full load. The manual's advice is to start once and keep the server running.

Follow-ups an interviewer may ask.

  • (level 3) Which phase dominates on this machine, and why? Expected: the weight load at about 330 seconds, because each tensor is copied from a file-backed page, which is slow on this platform.
  • (level 3) What does a persistent compile cache save on a restart? Expected: the compile share of the engine init, 18.67 seconds here. The weight load and the graph captures remain.
  • (level 4) How do you get the restart under a minute? Expected: a process checkpoint or GPU memory snapshot with the weights staged in host memory, which the field report took to 9.6 seconds. A faster disk alone does not get there.
  • (level 4) What does an eight-minute start imply for the probes and the autoscaler? Expected: a startup probe window longer than eight minutes, a stabilization window at least as long, and a warm replica for the interactive path.

Defend a designYou run three tiers on a serverless GPU platform: paid users on a live chat, trial users on the same chat, and a nightly batch pipeline. Design the warm-pool policy per tier, show the arithmetic behind it, and say what you would measure after a month to revisit it.

Level 4 of 4 · about 18 minutes to answer well.

Short answer. Give the paid chat one or two warm replicas, because its first-token target cannot absorb a cold start of minutes on a large model. Give trial users a smaller margin, or let them ride on the paid pool's spare capacity, and let the batch pipeline scale to zero, because it tolerates a cold start of several minutes. The arithmetic is the hourly GPU price times the idle hours against the requests that would miss the target during a cold start, and after a month you compare the measured utilization, the cold-start count and the missed-target count per tier.

The arithmetic the lesson gives.

A warm replica costs one GPU hour every hour. One replica per product is a full month of GPU hours whether anyone calls, and the lesson's example of five products with one warm replica each comes to 3,600 GPU-hours a month idle. The lesson calls the trade brutal on small models, where you pay 0.85 to 1.50 dollars an hour to avoid a 30 second start, and kind on large ones, where about 4 dollars an hour avoids a 5 minute start. Its threshold for a mandatory warm pool: a first-token target at P99 under 60 seconds on a model of 70B or more.

The policy per tier.

Tier Policy Why
paid live chat one to two warm replicas the lesson's high-value interactive path, where a cold start is an outage
trial chat zero warm, or overflow into the paid pool at lower priority the loss is a conversion, which you can measure, against a month of GPU hours
nightly batch scale to zero the lesson accepts a cold start of 5 to 10 minutes on background paths

The lesson's exercise asks exactly this split and asks for the math. The paid tier is decided by the SLA. The batch tier is decided by its tolerance. The trial tier is the real decision, and it is an experiment: the conversion loss from a cold start on the first session against the price of an idle GPU.

Make the policy cheaper by shrinking the start.

Every mitigation layer moves a tier toward zero. A pre-seeded node image removes the image pull, model streaming halves the weight load, a GPU memory snapshot restores the loaded state in a fraction of the time, and tiered loading keeps weights in host memory. The lesson's table takes a cold start of 328 seconds to about 15 seconds. With a 15 second start, the trial tier can scale to zero with a small loss, and the paid pool can hold one replica instead of two.

Match the billing to the tier.

The warm replicas run at high utilization, which is where per-minute billing beats per-token, above about 30 percent sustained utilization in the economics lesson. Trial bursts and the overnight batch sit below that line, so per-token or a batch tier at about half the serverless rate fits them.

What to measure after a month.

  • Utilization per tier, hour by hour.
  • Cold starts per day and their duration.
  • Requests that missed the first-token target, and whether they fell inside a cold start.
  • Trial conversions for sessions that hit a cold start against sessions that did not.
  • The break-even request rate per tier from the lesson's simulator, against the measured rate.

Plausible wrong answers.

  • "Warm replicas for every tier, the cost is small." One replica per product is a month of GPU hours each. Five products idle come to thousands of hours.
  • "Scale trial to zero, those users are free." A cold start of minutes on the first trial session is a lost conversion. Measure it before you decide.
  • "Keep the batch pipeline warm so that it finishes earlier." Batch tolerates minutes. A warm GPU for it is paid idle time for the rest of the day.

Follow-ups an interviewer may ask.

  • (level 3) Why not give trial users the same warm pool as paid users? Expected: a warm replica costs a month of GPU hours whether trial traffic arrives or not. The decision is the conversion loss from a cold start against that cost, and the month of measurement answers it.
  • (level 4) How does a 15 second cold start change the policy? Expected: tiers that tolerate seconds scale to zero, so the warm pool shrinks to the paths with targets of a second or two.
  • (level 4) Which signal says a warm replica count is too low? Expected: the share of requests that miss the first-token target during scale-outs, together with the cold-start count per day.

Weigh a trade-offYour serverless endpoint scales to zero overnight. The first request in the morning waits minutes while a 70B model loads, and the product wants the first token within two seconds. One engineer wants a replica that never sleeps. Another calls that a GPU burning money all night. Settle it.

Short answer. Both are right, and the decision is arithmetic per path. A warm replica costs one GPU hour every hour whether anyone calls or not, and it removes a cold start of several minutes for a large model. An interactive path with a tight first-token target on a large model needs the warm replica, while a small model with a cold start of seconds, or a background path that tolerates minutes, scales to zero. Then shrink the cold start itself, so that fewer paths need a warm replica at all.

What a cold start is made of.

The lesson's anatomy for a 70B model on a fresh node: node provision 45 to 60 seconds, image pull 120 to 300 seconds, weights into GPU memory 45 to 120 seconds, engine init 10 to 30 seconds. The sum is 220 to 510 seconds, which is 3 to 8 minutes before one token. The vLLM manual measured one part of that on its own machine: 330 seconds to load 57 GiB of weights.

The warm-pool arithmetic.

The lesson calls the arithmetic brutal on small models and kind on large ones. You pay 0.85 to 1.50 dollars an hour to avoid a 30 second start on a small model, and about 4 dollars an hour to avoid a 5 minute start on a large one. Five products with one warm replica each are 3,600 GPU-hours a month, called or not. The lesson's threshold: a warm pool becomes mandatory when the first-token target at P99 is under 60 seconds on a model of 70B or more.

Tier the paths.

Path Policy
live chat, voice agent one or two warm replicas
nightly classification, batch scale to zero, a cold start of minutes is fine
premium tenant dedicated warm capacity

Shrink the cold start.

Five layers, each removing a phase: a pre-seeded node image removes the image pull, model streaming halves the weight load, a GPU memory snapshot restores the loaded state in a fraction of the time, warm pools hide the rest, and tiered loading keeps weights in host memory. The lesson's table takes a 328 second cold start to about 15 seconds with the layers stacked, a reduction of 22 times. The vLLM manual adds the operational half: keep the weights on local disk, keep the compile cache on a persistent volume, and measure a cold and a warm start for every new image.

Plausible wrong answers.

  • "Keep one warm replica everywhere, it is the simple answer." It is one GPU hour every hour per product. Five products idle all night cost thousands of GPU hours a month.
  • "Scale to zero everywhere and let the first user wait." A first-token wait of minutes on an interactive path is an outage, not a wait.
  • "A bigger GPU loads faster." The load is bound by the storage and the copy path. The fix is where the weights live and whether a snapshot exists.

  • (level 3) Name two mitigations that remove whole phases of the cold start. Expected: a pre-seeded node image removes the image pull, and a GPU memory snapshot removes most of the weight load and the init.
