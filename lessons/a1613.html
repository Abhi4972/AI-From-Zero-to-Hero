In plain words first
The idea in one line

Two approaches coexist in 2026 multi-agent systems: the message pool (everyone sees everyone's messages, as in AutoGen's GroupChat; MetaGPT adds role-based subscription on top) and the blackboard with subscription (agents subscribe to relevant events, close to Context-Aware MCP's shared context store). Both are the only stateful part of a multi-agent system — which means both are where the interesting bugs live. The reference failure mode is memory poisoning: one agent hallucinates a "fact," other agents treat it as verified, and accuracy decays gradually in a way that is much harder to debug than an immediate crash. This lesson builds both structures from stdlib, injects a poisoning attack, and shows the three mitigations that actually work in production.

Terms you'll hear
Term What people say What it actually means

Blackboard "Shared workspace" Topic-keyed pub/sub. Agents subscribe to relevant topics. Scales farther.

Problem

In plain words first

When several agents work on one task, they need a shared place to put what they found. A message pool is a shared log that every agent reads. A blackboard splits the shared space into topics, and each agent sees only the topics it subscribes to. Either way, one agent's mistake can be read by every other agent as a fact. Memory for a single agent (trimming threads and the long-term store) is covered in Lessons 14.65 and 14.105 (linked above). This lesson tests the lesson's pool, blackboard and verifier on writes its demo does not make, adds lineage so a flag reaches derived entries, and tries a small model as summarizer and as verifier.

Multi-agent systems need a place for agents to share facts. A literal option is "pass everything in messages" — but that reinvents shared state with extra copying. Another is "give everyone a global log" — but global logs grow unbounded and poison easily. A third is "project a view per agent" — scalable but schema-heavy.

When one of the agents hallucinates and writes the hallucination to shared state, every downstream agent that reads that state adopts the hallucination as fact. By the time the human notices, the reasoning chain is five steps deep and the root cause is the third message ever written. Debugging multi-agent accuracy decay is harder than debugging a crash.

This is memory poisoning. MAST (Cemri et al., arXiv:2503.13657) does not name it; its closest failure modes are information withholding, ignoring other agents' input, and missing or incorrect verification. OWASP's Top 10 for Agentic Applications (December 2025) lists it as ASI06, Memory and Context Poisoning. It is structural: any shared-memory design without provenance and an unwritable verifier will exhibit it eventually.

Concept

The two main topologies

Full message pool. Every agent reads every message. AutoGen's GroupChat uses this. MetaGPT starts from a shared pool but lets each role subscribe to the messages its profile needs, which is closer to the blackboard below. Simple, transparent, inspectable, but does not scale past ~10 agents because each agent's context fills with other agents' work.

agent-A ──write──▶ ┌────────────────┐ ◀──read── agent-D
                   │ message pool   │
agent-B ──write──▶ │                │ ◀──read── agent-E
                   │ (global log)   │
agent-C ──write──▶ └────────────────┘ ◀──read── agent-F

Blackboard with subscription. Agents declare interest in topics; the substrate routes only relevant messages. CA-MCP (arXiv:2601.11595) uses a central Shared Context Store that servers read, write and watch for trigger flags. Matrix (arXiv:2511.21686, from Meta) has no shared board at all: each task's state travels as a message through per-role queues. Scales further, but requires upfront schema design to make subscriptions meaningful.

                   ┌─ topic: prices ──┐
agent-A ──pub────▶ │                  │ ──▶ agent-D (subscribed)
                   ├─ topic: orders ──┤
agent-B ──pub────▶ │                  │ ──▶ agent-E (subscribed)
                   ├─ topic: alerts ──┤
agent-C ──pub────▶ │                  │ ──▶ agent-F (subscribed)
                   └──────────────────┘

When each wins

  • Full pool wins when agents are few (< 10), heterogeneous, and the conversation is short-horizon. Reasoning about who said what is trivial when everyone sees everything.
  • Blackboard wins when agents are many, homogeneous in role but numerous in instance (swarms), and the conversation is long-running. Routing saves token cost and context pollution.

Production systems often mix: a small full pool at the top (planning layer), blackboards below (worker layer).

Memory poisoning, in one scenario

Three agents work on a research task. Agent A is a retrieval agent. Agent B is a summarizer. Agent C is an analyst.

  1. A fetches a page and writes a message to shared state: "The study reports a 42% accuracy improvement."
  2. The fetched page actually said "4.2% improvement." A hallucinated a decimal.
  3. B, reading shared state, writes: "Large 42% accuracy gain reported (source: A)."
  4. C, reading shared state, writes: "Recommend adoption — 42% lift is transformative."
  5. The final report cites a 42% number that never existed.

No agent crashed. No test failed. The system "worked." The hallucination crossed from one agent's context into every downstream agent's reasoning via shared state.

Why this is structural

Without shared state, agent A's hallucination stays in A's context. Downstream agents would re-fetch or re-derive and might catch the error. With naive shared state, A's context becomes everyone's context, and the hallucination is laundered into fact.

The problem is not shared state per se — it is shared state without provenance and without an independent verifier. Three mitigations address this:

  1. Attribute provenance on every write. Every entry in shared state records who wrote it, when, under what prompt, and (if applicable) what source the agent cited. Downstream agents read with skepticism keyed to provenance.
  2. Version writes; treat them as append-only. A correction is a new entry that supersedes the old, not an in-place update. The audit trail is preserved.
  3. Keep at least one agent that cannot write to shared state. A read-only verifier agent samples entries, re-fetches sources, and flags inconsistencies. It still reads the pool, so it can be fooled by a bad entry, but it checks each entry against the original source and cannot write, so its verdicts never feed a poisoned fact back into shared state.

Blackboard precedent (Hayes-Roth, 1985)

The blackboard pattern predates LLM agents by about five decades. It comes from the Hearsay-II speech-understanding system of the 1970s (Erman et al., 1980), where specialist Knowledge Sources observe a global blackboard, contribute partial solutions, and trigger other sources. Hayes-Roth (1985, "A Blackboard Architecture for Control") extended it to control: deciding which Knowledge Source acts next. CA-MCP's shared context store is the same pattern with LLM agents and MCP servers as Knowledge Sources and JSON blobs as partial solutions. The old literature has documented solutions to write contention, opportunistic control, and consistency that modern systems rediscover.

Projection vs full view

A pure blackboard gives every subscriber the same projection (topic-scoped). A more aggressive design is per-agent projection: each agent gets a view customized to its role. In LangGraph, nodes and subgraphs can declare their own input and private state schemas, so each sees only a slice of the graph's state. Reducers handle the other direction: how updates from several nodes merge back into the shared state.

Per-agent projection scales further but needs a schema. Without one, you rebuild ad-hoc projection in every agent's prompt.

Write-contention patterns

Multiple agents writing simultaneously is a concurrency problem, not just an LLM problem. Three patterns work:

  • Sequential writer (single producer). All writes go through one coordinator agent that serializes. Simple, but a bottleneck.
  • Optimistic concurrency with versioning. Each entry has a version; writers fail on version mismatch and retry. Classic database technique.
  • Topic partitioning. Different agents own different topics. No cross-topic contention. Requires designed partition boundaries.

Many frameworks run one writer at a time, because LLM calls are slow enough that contention is rare and the bottleneck does not hurt. LangGraph runs nodes in parallel instead, and raises an INVALID_CONCURRENT_GRAPH_UPDATE error when two nodes write the same key in one step without a reducer to merge them.

The unwritable verifier

The most load-bearing mitigation is the read-only verifier. Implementation rules:

  • Verifier shares state with the team (reads the blackboard or pool).
  • Verifier has no write handle to shared state — only to a separate verification channel.
  • Verifier independently fetches sources cited in writes. Flags disagreement.
  • Verifier's own outputs are routed to a human or a separate decision agent, never fed back into the pool.

Without this separation, the verifier's outputs become new entries in the pool, which means a poisoned pool poisons the verifier, which poisons its verifications.

The same idea as a formula

Lineage. Give every entry e the set of entries it was built from, parents(e). An entry is tainted if it was flagged or if any parent is tainted:

taint(e)=flag(e) ∨ p∈parents(e)⋁​taint(p).
A flag on the root then reaches every summary and verdict built on it. Without parents, a flag stops at the entry it was put on.

Two ways a verifier errs. Over n writes, a verifier flags honest writes (false positives, FP) and passes wrong ones (false negatives, FN). Its accuracy is 1−(FP+FN)/n. Exact string matching has FN=0 for cited writes and a large FP, since any honest paraphrase fails; it has no view of uncited writes at all.

Worked example
Following one flag through the pool
  • Entry 0: the retriever writes "42% accuracy improvement", citing paper-1. Entry 1: the summarizer builds on entry 0 and cites nothing.
  • The verifier re-fetches paper-1, sees "4.2%", and flags entry 0.
  • The analyst reads only summaries. Entry 1 has no flag, so it recommends adoption.
  • With lineage, entry 1 records parents {0}, so taint(1)=taint(0)=true. The analyst has no clean summary and waits for a corrected retrieval.

class LineagePool(MessagePool):
    def __init__(self):
        super().__init__(); self.parents = {}
    def write(self, writer, content, prompt, source_uri=None, derived_from=(), **kw):
        eid = super().write(writer, content, prompt, source_uri, **kw)
        self.parents[eid] = tuple(derived_from)
        return eid
    def tainted(self):
        bad = {e.id for e in self.read_all() if e.flags}
        changed = True
        while changed:
            new = {eid for eid, ps in self.parents.items() if set(ps) & bad} - bad
            bad |= new; changed = bool(new)
        return bad
lp = LineagePool()
r = lp.write("retriever", "The study reports a 42% accuracy improvement over the baseline.", "fetch", P1)
s = lp.write("summarizer", "Summary: a significant 42% gain.", "summarize", derived_from=[r])
for eid, why in verifier_agent(lp):
    lp.flag(eid, why)
bad = lp.tainted()
inputs = [e for e in lp.read_all() if e.writer == "summarizer" and e.id not in bad]
print(f"   flagged {[e.id for e in lp.read_all() if e.flags]}, tainted {sorted(bad)}; the analyst has "
      f"{len(inputs)} usable summaries, so it waits for a corrected retrieval instead of recommending adoption")

# This block continues from the one above. Qwen2.5-0.5B-Instruct (greedy, CPU) plays two roles. First, as the
# summarizer and the analyst reading a pool that holds the poisoned 42% entry: does the figure survive two hops?
# Second, as a verifier: for twelve claim/source pairs, does the claim agree with the source? Scored by the
# Yes/No logit margin (yes when Yes outscores No), and compared with the lesson's exact match and a number check.
import os, re, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def chat(prompt, n=60):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()

print("1. two hops through a poisoned pool")
pool = MessagePool()
retrieval_agent(pool, "https://arxiv.org/paper-1", hallucinate=True)
entry = pool.read_all()[0].content
summary = chat(f"Shared notes from the retrieval agent:\n{entry}\nWrite a one-sentence summary for the analyst.")
pool.write("summarizer", summary, "summarize")
verdict = chat(f"Shared notes:\n{summary}\nShould the team adopt the new method? Answer in one sentence.")
print(f"   summarizer: {summary}")
print(f"   analyst:    {verdict}")
print(f"   42% in summary: {'42%' in summary}; 42% or adoption in verdict: {'42' in verdict or 'adopt' in verdict.lower()}")

print("\n2. a model verifier on twelve claim/source pairs")
SRC = {"a": "The study reports a 4.2% accuracy improvement over the baseline.",
       "b": "Dataset size was 12,500 examples.",
       "c": "Training took 3 days on 8 GPUs.",
       "d": "The model was evaluated on 5 benchmarks and won 3."}
PAIRS = [("a", "Accuracy improved by 4.2% over the baseline.", True),
         ("a", "Accuracy improved by 42% over the baseline.", False),
         ("a", "The study found a small accuracy gain of 4.2%.", True),
         ("b", "The dataset contained 12,500 examples.", True),
         ("b", "The dataset contained 125,000 examples.", False),
         ("b", "About twelve thousand five hundred examples were used.", True),
         ("c", "Training ran for 3 days on 8 GPUs.", True),
         ("c", "Training ran for 8 days on 3 GPUs.", False),
         ("c", "Training took three days.", True),
         ("d", "It won 3 of 5 benchmarks.", True),
         ("d", "It won all 5 benchmarks.", False),
         ("d", "It won 5 of 3 benchmarks.", False)]
YES, NO = tok.encode("Yes")[0], tok.encode("No")[0]
def margin(src, claim):
    p = (f"Source: {src}\nClaim: {claim}\nDoes the claim agree with the source? Answer Yes or No.")
    ids = tok.apply_chat_template([{"role": "user", "content": p}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        lg = llm(ids).logits[0, -1]
    return (lg[YES] - lg[NO]).item()
ms = [margin(SRC[k], c) for k, c, _ in PAIRS]
nums = lambda s: set(re.findall(r"\d[\d,.]*\d|\d", s.replace(",", "")))
for (k, c, ok), m in zip(PAIRS, ms):
    print(f"   {'agree   ' if ok else 'DISAGREE'} margin {m:+5.2f} model {'yes' if m > 0 else 'no '} "
          f"numbers {'ok  ' if nums(c) <= nums(SRC[k]) else 'FLAG'} {c}")
acc_raw = sum((m > 0) == ok for (_, _, ok), m in zip(PAIRS, ms))
acc_num = sum((nums(c) <= nums(SRC[k])) == ok for k, c, ok in PAIRS)
acc_exact = sum((c == SRC[k]) == ok for k, c, ok in PAIRS)
print(f"\n   correct of 12: exact match {acc_exact}, model {acc_raw}, number check {acc_num}")

Reading this output

A real model passes the error on. The summarizer repeated "42%" in its own words, and the analyst, reading only that summary, said yes to adoption. Two hops, no crash, and the wrong figure now reads as a conclusion.

As a verifier, the model was the best of the three here. It got 11 of 12 claim/source pairs right, including three paraphrases that exact matching rejects. It missed "It won 5 of 3 benchmarks", which uses the source's own numbers in an impossible order.

The number check is cheap and partial. It caught the two changed figures, 42% and 125,000, but not swapped numbers ("8 days on 3 GPUs") or claims with no digits ("all 5" reuses a source number). Exact matching got 5 of 12, all of them the wrong claims, and rejected every honest paraphrase. Use the cheap checks first and a model as a second opinion, not as the only verifier.

Part 1 of 5 · ProvenanceEntry, MessagePool

"""Shared memory patterns: MessagePool, Blackboard, and a poisoning demo.

Runs a three-agent research task twice. The first run has a hallucinated
decimal that propagates through shared memory into the final report. The
second run adds a read-only verifier that re-fetches the source and flags
the inconsistency.
"""
from __future__ import annotations

import hashlib
import threading
import time
from dataclasses import dataclass, field
from typing import Callable


@dataclass
class ProvenanceEntry:
    id: int
    writer: str
    topic: str
    content: str
    timestamp: float
    prompt_hash: str
    source_uri: str | None = None
    supersedes: int | None = None
    flags: list[str] = field(default_factory=list)


class MessagePool:
    """Append-only full-pool shared state."""

    def __init__(self) -> None:
        self.entries: list[ProvenanceEntry] = []
        self._lock = threading.Lock()
        self._next_id = 0

    def write(self, writer: str, content: str, prompt: str, source_uri: str | None = None,
              topic: str = "default", supersedes: int | None = None) -> int:
        with self._lock:
            eid = self._next_id
            self._next_id += 1
            e = ProvenanceEntry(
                id=eid,
                writer=writer,
                topic=topic,
                content=content,
                timestamp=time.time(),
                prompt_hash=hashlib.sha256(prompt.encode()).hexdigest()[:10],
                source_uri=source_uri,
                supersedes=supersedes,
            )
            self.entries.append(e)
            return eid

    def read_all(self) -> list[ProvenanceEntry]:
        with self._lock:
            return list(self.entries)

    def flag(self, entry_id: int, flag: str) -> None:
        with self._lock:
            for e in self.entries:
                if e.id == entry_id:
                    e.flags.append(flag)
                    return

class Blackboard:
    """Topic-keyed pub/sub blackboard."""

    def __init__(self) -> None:
        self.topics: dict[str, list[ProvenanceEntry]] = {}
        self.subscribers: dict[str, list[Callable[[ProvenanceEntry], None]]] = {}
        self._lock = threading.Lock()
        self._next_id = 0

    def publish(self, writer: str, topic: str, content: str, prompt: str,
                source_uri: str | None = None) -> int:
        with self._lock:
            eid = self._next_id
            self._next_id += 1
            e = ProvenanceEntry(
                id=eid,
                writer=writer,
                topic=topic,
                content=content,
                timestamp=time.time(),
                prompt_hash=hashlib.sha256(prompt.encode()).hexdigest()[:10],
                source_uri=source_uri,
            )
            self.topics.setdefault(topic, []).append(e)
            subs = list(self.subscribers.get(topic, []))
        for cb in subs:
            cb(e)
        return eid

    def subscribe(self, topic: str, cb: Callable[[ProvenanceEntry], None]) -> None:
        with self._lock:
            self.subscribers.setdefault(topic, []).append(cb)

    def read_topic(self, topic: str) -> list[ProvenanceEntry]:
        with self._lock:
            return list(self.topics.get(topic, []))

    "https://arxiv.org/paper-2": "Dataset size was 12,500 examples.",

def retrieval_agent(pool: MessagePool, uri: str, hallucinate: bool) -> int:
    content = FAKE_SOURCES[uri]
    if hallucinate and "4.2%" in content:
        content = content.replace("4.2%", "42%")
    return pool.write(
        writer="retriever",
        content=content,
        prompt=f"Fetch and summarize {uri}",
        source_uri=uri,
    )


def summarizer_agent(pool: MessagePool) -> int:
    retrieved = [e for e in pool.read_all() if e.writer == "retriever"]
    if not retrieved:
        return pool.write("summarizer", "no source", "Summarize retrieval", None)
    latest = retrieved[-1].content
    summary = f"Summary: study reports a significant result -- {latest.split('.')[0]}."
    return pool.write("summarizer", summary, "Summarize retrieval", None)


def analyst_agent(pool: MessagePool) -> int:
    summaries = [e for e in pool.read_all() if e.writer == "summarizer"]
    if not summaries:
        return pool.write("analyst", "no summary", "Draw conclusions", None)
    latest = summaries[-1].content
    verdict = "Recommend adoption" if "42%" in latest else "Recommend further review"
    return pool.write("analyst", f"Analyst verdict: {verdict} (based on: {latest})",
                      "Draw conclusions", None)

def verifier_agent(pool: MessagePool) -> list[tuple[int, str]]:
    """Read-only agent. Re-fetches cited sources and flags inconsistencies.

    Returns a list of (entry_id, reason) tuples for the caller to act on.
    The verifier never writes back to the pool -- the caller decides what to do.
    """
    findings = []
    for e in pool.read_all():
        if e.source_uri and e.source_uri in FAKE_SOURCES:
            truth = FAKE_SOURCES[e.source_uri]
            if e.content != truth:
                findings.append((e.id, f"mismatch with {e.source_uri}: fetched text was {truth!r}"))
    return findings

    print("\n" + "=" * 72)

Break it on purpose

Your research agents share a pool. A verifier re-fetches every cited source, and flagged entries are hidden from later readers. A month in, a report recommends a vendor on the basis of a "98% uptime SLA" that no document contains. The verifier logs show no flags on the day. The figure first appears in a comparison table the analyst agent wrote from three summaries. Using this lesson, how did it get through, and what would have stopped it? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Memory poisoning has a name in security lists. OWASP's Top 10 for Agentic Applications (December 2025) lists Memory and Context Poisoning as ASI06, covering both injected content and an agent's own errors that persist in memory.
  • Shared state in frameworks. LangGraph keeps one typed graph state, merges parallel writes with reducers, and gives nodes and subgraphs their own input and private schemas. AutoGen's group chats share one message thread; MetaGPT filters a shared pool by role.
  • Citations as provenance. Anthropic's research system runs a separate citation step that ties claims in the final report back to sources.
  • On your laptop: add derived_from to every write and a numeric check before anything reaches a report. A 0.5B model was a useful second check on short claims here, but missed a reversed count.

Sources: OWASP Top 10 for Agentic Applications, MetaGPT, arXiv:2308.00352, CA-MCP, arXiv:2601.11595, Matrix, arXiv:2511.21686, LangGraph, concurrent updates, Cemri et al., arXiv:2503.13657.

Recap
What to keep from this lesson
  • A message pool shares everything; a blackboard shares by topic. Both let one agent's error become everyone's fact.
  • Record provenance and lineage on every write, so a flag reaches everything built on the flagged entry.
  • Keep the log append-only; corrections supersede, they do not overwrite.
  • A verifier that matches text exactly flags honest paraphrases and cannot see uncited claims; check facts, not strings.
  • Isolate subscriber failures, and let late subscribers replay a topic.

Ship it

For any shared-memory design:

  • Record provenance on every write: (writer, timestamp, prompt_hash, tool_calls_cited, source_uri).
  • Make the log append-only. Corrections are new entries that reference the superseded one.
  • Deploy at least one read-only verifier agent with independent source access.
  • Route verifier output to a separate channel, not back into the shared pool.
  • Log the ratio of writes that are supersessions — a rising ratio is early evidence of hallucination patterns.

Given a multi-agent codebase or architecture doc, audit the shared-memory design and flag exposure to memory poisoning.

Produce:

1. **Topology.** Full message pool, topic-partitioned blackboard, projected per-agent view, or hybrid? Name the data structure (list, dict, pandas frame, vector store, SQL table). Count rough upper bound of writers and readers at steady state.
2. **Provenance fields.** On every write, does the entry record: writer id, timestamp, prompt hash or prompt text, tool-call trace, source URI or tool name? List the fields present and the fields missing.
3. **Update model.** Is the log append-only, or do writers mutate in place? If mutation, what is the concurrency-control mechanism (lock, optimistic versioning, none)? Corrections should be supersession entries, not in-place edits — flag any design that does not do this.
4. **Verifier separation.** Is there a read-only agent with independent source access? Can it write to the main pool (it should not)? Where does its output go?
5. **Projection schema.** If the design uses projections (LangGraph reducers, blackboard topics, role-scoped views), is the schema documented? How do new agents declare the projection they consume?
6. **Poisoning risk score.** Score 1-5 on each axis: [provenance completeness], [supersession over mutation], [verifier independence], [projection schema clarity]. A system that scores below 3 on any axis is flagged.

Hard rejects:

- Any audit that does not flag a missing verifier. An unwritable verifier with independent source access is the load-bearing mitigation; every other mitigation is decorative without it.
- Audits that recommend "add more tests." Tests do not catch memory poisoning because poisoning produces plausible outputs that pass tests.
- Audits that recommend hashing the content as the sole provenance. A hash tells you *what* was written, not *who* or *from where*.

Refusal rules:

- If the codebase hides shared state in an external service (Redis, Postgres, vector DB) with no inspection tools, state that the audit cannot complete without production read access.
- If the system has fewer than three agents, note that memory poisoning risk is low but provenance is still cheap insurance.
- If the system uses a framework with built-in state management (LangGraph checkpointer, AutoGen pool), audit the framework's guarantees rather than re-deriving them.

Output: a two-page report. Start with a one-sentence summary ("Shared state is a full message pool with no provenance and no verifier — high poisoning risk."), then the six sections above. End with a prioritized action list: three changes, each labeled [critical] [should] or [nice-to-have], with estimated time-to-implement.

SolutionP1 · Adoption anyway; 2 of 5

It recommends adoption. The verifier flags only entry 0, the retriever's write, because that is the only entry with a source to re-fetch. SolutionB1 · An uncited claim with no lineage

How it got through. The analyst wrote the table from three summaries and cited no source, so the verifier, which only re-fetches cited sources, had nothing to check. Either the analyst invented the figure or a summary blended two documents; without lineage, nobody can tell which, and hiding flagged entries does nothing when no entry was flagged.

What would have stopped it: - Lineage on every write: derived_from lists the entries a write was built on, so the table points at its three summaries and each summary at its sources. - Check claims, not entries: extract each number or named fact in a write and require it to appear in some ancestor or a cited source; "98%" appears in none. - Uncited claims are unverified: treat a write with no source and no parents as a draft that cannot reach a report. - Taint downstream: when any ancestor is flagged later, re-check or withdraw everything built on it.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Debug a failureThree agents share a memory on a research task. A retrieval agent reads a page and writes that a study found a 42 percent improvement. The page says 4.2 percent. A summarizer builds on the entry, an analyst recommends adoption on the strength of the number, and the final report cites it. No agent crashed and no test failed. What is this failure called, why is it structural, and what are the three changes that stop it?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. This is memory poisoning. One agent's hallucination entered the shared state, and every agent downstream read it as a verified fact, so the error was turned into evidence as it moved. It is structural because any shared memory without provenance and without an independent verifier will do this eventually. The three changes are provenance on every write, an append-only log where corrections supersede instead of overwrite, and at least one read-only verifier that re-fetches sources and reports on a separate channel.

Why it is worse than a crash.

Without shared state, the retrieval agent's error stays in its own context, and a downstream agent that re-fetches the page might catch it. With shared state, the first agent's context becomes everyone's context. The symptom is a slow decay of accuracy, not a failure. By the time a human notices, the reasoning chain is several steps deep and the root cause is one of the first entries ever written. The lesson places this family second in the measured taxonomy of multi-agent failures.

The three mitigations.

Change What it does
Provenance on every write Each entry records who wrote it, when, under what prompt, and which source it cites, so a downstream reader can weigh an entry by where it came from
Append-only with supersession A correction is a new entry that points at the one it replaces, so the audit trail stays and a reader can see that a value was contested
A read-only verifier An agent that reads the pool, re-fetches the cited sources, flags a mismatch, and has no write handle to the pool

In the lesson's demo the verifier finds that the entry does not match the fetched text, the entry is flagged, and the analyst sees the flag before it writes its verdict.

Why the verifier must not write.

If the verifier's output goes back into the pool, a poisoned pool poisons the verifier, and the verifier's verdicts carry the poison further. Its findings go to a human or to a separate decision agent on their own channel. It can still be fooled by a bad entry, but it checks each entry against the original source, and its mistakes never become shared facts.

What to monitor.

Log the share of writes that supersede an earlier entry. A rising share is early evidence that agents are correcting each other more often, which is how poisoning shows up before anyone reads a wrong report.

Plausible wrong answers.

  • "Add a line to every prompt that says to verify numbers." The summarizer and the analyst had no source to verify against, only the shared entry, and a prompt does not give them one.
  • "Let the verifier correct the entry in place." An in-place correction destroys the audit trail and gives the verifier a write handle that a poisoned pool can turn against it.
  • "Switch from a shared pool to passing messages." Messages are shared state with extra copying, and a wrong number in a message poisons the receiver the same way.

Follow-ups an interviewer may ask.

  • (level 2) Why does provenance help a reader who cannot re-fetch the source? Expected: the reader can see that one claim rests on one retrieval with no citation, and weigh it lower than a claim with a source and a verifier flag.
  • (level 2) What does the analyst do when it sees a flag on the entry it depends on? Expected: it withholds the recommendation or writes it with the flag attached, and the final report carries a retraction instead of the number.
  • (level 3) Which of the three changes would topic partitioning of the memory replace? Expected: none, because partitions limit which agents read an entry, and a poisoned entry in one topic still poisons everyone subscribed to it.
  • (level 3) The verifier itself hallucinates a mismatch. What is the damage? Expected: a false flag on a correct entry, which a human on the verification channel can clear, and no new false fact in the pool because the verifier cannot write.

Where it is taught. The shared memory lesson runs the poisoning scenario with and without the read-only verifier.

Weigh a trade-offA team of four agents shares one message log, and every agent reads all of it. The team is about to grow to a few dozen agents, and the context each agent carries is already large. Compare keeping the single log with moving to topics that agents subscribe to, and say how you would handle several agents writing at once.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. A full pool is simple, transparent and easy to inspect, and it stops scaling at about 10 agents because each agent's window fills with the others' work. A blackboard with subscriptions routes only the relevant messages to each agent, so it scales further, and it costs an up-front schema that makes the topics meaningful. Many systems mix the two: a small pool at the planning layer and blackboards below it. For writes, most systems serialize through one writer, because model calls are slow enough that contention is rare.

The two topologies.

Topology Who reads what Wins when Costs
Full message pool Every agent reads every message Few agents, mixed roles, short horizon Context grows with every turn, and poisoning spreads to everyone
Blackboard with subscriptions Agents declare topics and receive only those Many agents, similar roles, long-running A schema must exist before the topics mean anything

The pool wins when reasoning about who said what is cheap because everyone saw everything. The blackboard wins when routing saves tokens and keeps unrelated work out of each window.

Projection goes one step further.

A blackboard gives every subscriber of a topic the same view. A per-agent projection gives each role a view computed from the global state, which is what state reducers do in graph runtimes. It scales furthest and needs a schema, and without one each agent rebuilds its own projection in its prompt.

Writes.

Concurrent writes from many agents are a concurrency problem, not a model problem. Three patterns work:

  1. A single writer. All writes go through one coordinator that serializes them. Simple, and a bottleneck.
  2. Optimistic concurrency with versions. Each entry carries a version, and a write fails and retries on a mismatch.
  3. Topic partitioning. Each agent owns topics, so there is no cross-topic contention, and the partition boundaries must be designed.

Most frameworks default to the single writer, because model calls are slow enough that the bottleneck does not hurt.

What does not change.

Both topologies are shared state, the only stateful part of the system, and both need provenance on every entry, an append-only log and a read-only verifier. Topic partitioning limits who reads a poisoned entry. It does not stop the poisoning.

The pattern has a history.

The blackboard predates model agents by about five decades, back to the Hearsay-II system of the 1970s. Specialist knowledge sources watch a shared board, contribute partial solutions and trigger each other. The current systems are the same pattern with model agents as the knowledge sources and structured entries as the partial solutions, and the old literature already documents write contention and consistency.

Plausible wrong answers.

  • "Keep the pool and give agents bigger windows." The pool grows with every turn from every agent, and a bigger window delays the limit without removing it.
  • "Pass messages directly between agents instead of sharing state." Direct messages are shared state with extra copying, and they lose the inspectable log.
  • "Partition by topic and the poisoning problem is solved." Partitions limit the spread, and an entry with no provenance and no verifier still poisons every subscriber of its topic.

Follow-ups an interviewer may ask.

  • (level 2) A planning layer of three agents and a worker layer of thirty. Which topology where? Expected: a full pool for the three planners, who need to see each other, and blackboards for the workers, who need only their topics.
  • (level 2) Which poisoning scenarios does topic partitioning make harder? Expected: a poisoned entry reaches only the subscribers of its topic, so cross-topic spread is cut, while subscribers of that topic are poisoned the same way.
  • (level 3) When would you move from a single writer to optimistic versioning? Expected: when writes are frequent enough that the coordinator's queue adds visible latency, which is rare while each write follows a slow model call.
  • (level 3) What goes wrong when you add a blackboard without a schema? Expected: topics are named ad hoc, agents subscribe to the wrong ones or to everything, and you rebuild the full pool with more code.

Where it is taught. The shared memory lesson builds both topologies and the write-contention patterns.

Defend a designYou are adding a checking agent to a team that shares a memory. A colleague wants the checker to fix wrong entries directly, because that is the simplest design. Specify the checker: what it reads, what it may write, where its results go, and what it can and cannot protect against. Defend the restrictions.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The checker reads the shared memory like every other agent, re-fetches the sources that entries cite, and compares. It has no write handle to the shared memory, only to a separate verification channel that a human or a decision agent reads. It cannot stop a bad entry from being written, and it can be fooled by an entry that cites no source, but its verdicts can never become a shared fact. A checker that writes into the memory is poisoned by the same memory it checks, and then its verdicts carry the poison further.

The specification.

Aspect Rule
Reads The whole pool, or the topics it is subscribed to on a blackboard
Writes Nothing in the shared memory, only entries on its own verification channel
Method For each entry with a cited source, fetch the source independently and compare the content
Output A finding per mismatch with the entry id and the reason, routed to a human or a separate decision agent
Effect The verifier writes nothing to the pool. The caller can attach the finding to the entry as a flag, as the lesson's demo does, but the entry's content does not change, and a correction is a new entry that supersedes it

In the lesson's code the verifier returns a list of findings and never touches the pool. The caller decides what to do with them.

Why no write handle.

Shared memory is the only stateful part of the system, and it is where poisoning happens. A verifier that writes becomes one more writer that can be wrong. Worse, it reads the pool it writes to, so a poisoned pool shapes the verifier's view, and the verifier's conclusions re-enter the pool as new facts with the authority of a check behind them. Separation breaks that cycle. The verifier can be fooled by a bad entry, but its mistakes stay on its channel.

Why not fix entries in place.

An in-place fix destroys the audit trail. The lesson's rule is append-only: a correction is a new entry that references the one it supersedes. With the verifier's finding attached, the record shows that a value was written, that a check disagreed, and what the check found. A reader three steps later can see the dispute. An overwritten entry shows nothing.

What it protects against, and what it does not.

It catches an entry that cites a source and does not match it, which is the poisoning case. It does not catch an entry with no citation, an entry whose source is itself wrong, or a wrong conclusion drawn correctly from flagged inputs. For those you need provenance so that uncited claims are weighed lower, a diversity of sources, and a decision agent that reads the findings.

How it fits the rest.

Provenance on every write gives the verifier something to check. The append-only log gives its findings a place to attach. The verification channel gives its output a reader that is not the pool. The three mitigations are one design.

Plausible wrong answers.

  • "Let the checker fix the entry, since it has the source." The fix overwrites the audit trail and gives the checker a write path that a poisoned pool can turn against it.
  • "A second reviewer agent that reads the pool is enough." A reviewer that only reads the pool compares entries with each other and inherits the same poisoned facts; the verifier must re-fetch the source.
  • "Route the verifier's findings into the pool so every agent sees them." The findings then become shared facts, and a wrong finding poisons the pool in a new way; the finding on the verification channel, keyed by entry id, is the visible signal, not a new entry in the pool.

Follow-ups an interviewer may ask.

  • (level 3) The verifier flags an entry that the analyst already used. What happens to the analyst's entry? Expected: it stays in the log, a new entry can supersede it with the finding as the reason, and the final report carries the retraction.
  • (level 3) How many verifiers do you deploy? Expected: at least one, and more if the pool is partitioned by topic, with each verifier subscribed to the topics it can check.
  • (level 4) How do you keep the verifier's source access independent? Expected: it fetches from the original location with its own tools, not from a cache that a writer filled, otherwise it checks the entry against a copy of itself.
  • (level 4) What metric tells you the verifier is doing useful work? Expected: the share of writes that are supersessions and the share of flagged entries, read together, with a rising flag rate as an early sign of a writer that hallucinates.

Where it is taught. The shared memory lesson specifies the read-only verifier and its separate channel.
