Why this came about

A language model only gives probabilities; something else must choose the words. Early neural systems picked the most likely word each time, or used beam search (keep the few best partial sentences), which suited translation but made open-ended text dull and repetitive. In 2018 Angela Fan and colleagues proposed top-k sampling, and in 2019 Ari Holtzman and colleagues described "neural text degeneration" and proposed nucleus (top-p) sampling: sample, but only from the smallest set of words that covers most of the probability. Together with temperature, these are the dials every LLM API exposes. Meanwhile, the KV cache became the key trick that makes generation fast, and its memory use one of the main costs of serving LLMs.

In plain words first
Choosing the next word

At each step the model hands you a ranked list: " refund" 36%, " new" 9%, " replacement" 5%, and thousands more. You could always take the top word (safe but repetitive), or roll a weighted die (varied but sometimes odd). Temperature makes the die more or less fair: low temperature favours the top words even more, high temperature evens things out. Top-k and top-p cut off the long tail of unlikely words before rolling, so you never pick something absurd. Then the chosen word is added to the text, and the model is asked again.

Step 1 · Next-token probabilities from a real model

Until now the models were ones you trained yourself. This lesson uses GPT-2, a real pretrained model small enough for a laptop (about 500 MB, downloaded on first run). Give it the start of a sentence and it returns a score for every one of its 50,257 tokens being next. The code loads the model, turns the scores into probabilities and prints the most likely continuations.

import time
import torch
import torch.nn.functional as F
from transformers import GPT2LMHeadModel, GPT2TokenizerFast

tokenizer = GPT2TokenizerFast.from_pretrained("gpt2")
model = GPT2LMHeadModel.from_pretrained("gpt2")
model.eval()

def next_token_probs(text):
    ids = tokenizer(text, return_tensors="pt")["input_ids"]
    with torch.no_grad():
        logits = model(ids).logits[0, -1]          # logits for the token after the last one
    return logits

logits = next_token_probs("I would like to return this item and get a")
probs = F.softmax(logits, dim=-1)
top = probs.topk(8)
for p, i in zip(top.values, top.indices):
    print(f"{tokenizer.decode([int(i)])!r:<16} {p:.3f}")
print(f"the top 8 cover {top.values.sum():.0%}; the other {len(probs) - 8:,} tokens share the rest")

Step 2 · Greedy decoding

The simplest strategy: always take the most likely token, append it, repeat.

def greedy(prompt, n_tokens=40):
    ids = tokenizer(prompt, return_tensors="pt")["input_ids"]
    for _ in range(n_tokens):
        with torch.no_grad():
            logits = model(ids).logits[0, -1]
        next_id = logits.argmax()                   # the single most likely token
        ids = torch.cat([ids, next_id.view(1, 1)], dim=1)
    return tokenizer.decode(ids[0])

print(greedy("Dear customer, we are sorry that your order"))
What you should see
Dear customer, we are sorry that your order was not received. Please try again later. View all New York Stock Exchange Q&A

Loading ... Loading ...

Quotes are not sourced from all markets and may be delayed up to 20

Greedy decoding is deterministic (same input, same output) and often fine for short, factual answers. For longer text it tends to produce the blandest possible continuation and to fall into loops: here GPT-2 small drifts into web-page boilerplate, including a repeated "Loading ...". Once a phrase is likely, repeating it keeps it likely. This is the "degeneration" that motivated sampling.

Step 3 · Temperature, top-k and top-p

Temperature divides the logits before softmax (Lesson 1.25). Below 1 sharpens the distribution; above 1 flattens it:

for t in [0.5, 1.0, 1.5]:
    p = F.softmax(logits / t, dim=-1)
    top = p.topk(4)
    shown = ", ".join(f"{tokenizer.decode([int(i)])!r} {v:.2f}" for v, i in zip(top.values, top.indices))
    print(f"temperature {t}: {shown}")

Top-k keeps only the k most likely tokens. Top-p (nucleus sampling) keeps the smallest set of top tokens whose probabilities add up to at least p, so it adapts: when the model is confident, few tokens survive; when it is unsure, many do.

def filter_logits(logits, top_k=0, top_p=1.0):
    logits = logits.clone()
    if top_k > 0:
        kth = logits.topk(top_k).values[-1]
        logits[logits < kth] = float("-inf")                       # drop everything below the k-th best
    if top_p < 1.0:
        sorted_logits, order = logits.sort(descending=True)
        cum = F.softmax(sorted_logits, dim=-1).cumsum(dim=-1)
        remove = cum - F.softmax(sorted_logits, dim=-1) >= top_p   # tokens after the nucleus is already full
        logits[order[remove]] = float("-inf")
    return logits

for label, kw in [("no filter", {}), ("top-k 10", {"top_k": 10}), ("top-p 0.5", {"top_p": 0.5}), ("top-p 0.9", {"top_p": 0.9})]:
    kept = torch.isfinite(filter_logits(logits, **kw)).sum().item()
    print(f"{label:<10} tokens still allowed: {kept:,}")
What you should see
no filter  tokens still allowed: 50,257
top-k 10   tokens still allowed: 10
top-p 0.5  tokens still allowed: 4
top-p 0.9  tokens still allowed: 524
Reading this output
  • With no filter, all 50,257 tokens remain possible, including absurd ones; over a long text, some will eventually be drawn.
  • Top-k 10 keeps exactly 10, however spread out the probabilities are.
  • Top-p 0.5 needs only a few tokens here, because " refund" alone has 36%. Top-p 0.9 needs many hundreds: after "get a", the model spreads the remaining probability over a long list of plausible words.
  • cum - softmax >= top_p marks a token for removal if the tokens before it already reached p. This keeps the token that crosses the line, so the kept set always has at least one token.

Step 4 · Sampling in practice

Hugging Face's generate implements all of this. Fix the random seed to get repeatable samples:

prompt_ids = tokenizer("Dear customer, we are sorry that your order", return_tensors="pt")["input_ids"]
for seed in [0, 1, 2]:
    torch.manual_seed(seed)
    out = model.generate(prompt_ids, do_sample=True, temperature=0.8, top_p=0.9, max_new_tokens=25,
                         pad_token_id=tokenizer.eos_token_id)
    print(f"seed {seed}:", repr(tokenizer.decode(out[0][prompt_ids.shape[1]:])))

Other controls you will meet in APIs: max tokens (a hard limit on output length), stop sequences (end generation when a given string appears), frequency and presence penalties (discourage repeating tokens), and a seed. Even at temperature 0, hosted APIs are not always perfectly repeatable, because tiny numerical differences on GPUs can change which token is on top (Lesson 11.19).

Step 5 · The KV cache

The greedy loop in Step 2 called the model on the whole text at every step. But in a causal model, the keys and values of earlier tokens never change when new tokens are added (they cannot see the future). So they can be computed once and kept: the KV cache. Each step then processes only the one new token. Hugging Face does this by default; turn it off to see the difference:

def timed_generate(use_cache, n=60):
    torch.manual_seed(0)
    start = time.perf_counter()
    model.generate(prompt_ids, do_sample=False, max_new_tokens=n, use_cache=use_cache,
                   pad_token_id=tokenizer.eos_token_id)
    return time.perf_counter() - start

with_cache, without_cache = timed_generate(True), timed_generate(False)
print("generation with the KV cache was faster:", with_cache < without_cache)

n = 1000
print(f"token positions processed for {n} new tokens: without cache {n * (n + 1) // 2:,}, with cache {n:,}")
What you should see
generation with the KV cache was faster: True
token positions processed for 1000 new tokens: without cache 500,500, with cache 1,000

The exact timings depend on your machine (which is why the code prints a yes/no), but without the cache the work grows with the square of the output length. The price of the cache is memory: for every token in the context, every layer stores a key and a value for each key/value head.

def kv_cache_gb(tokens, n_layers=32, n_kv_heads=8, head_dim=128, bytes_per_number=2, users=1):
    """Llama-3-8B-like defaults: 32 layers, 8 key/value heads (grouped-query attention), bf16."""
    per_token = 2 * n_layers * n_kv_heads * head_dim * bytes_per_number      # 2 = one key + one value
    return per_token, per_token * tokens * users / 1e9

per_token, _ = kv_cache_gb(1)
print(f"KV cache per token: {per_token:,} bytes ({per_token / 1024:.0f} KB)")
for tokens, users in [(8_000, 1), (128_000, 1), (8_000, 32)]:
    print(f"{tokens:>7,} tokens x {users:>2} users: {kv_cache_gb(tokens, users=users)[1]:5.1f} GB")
print(f"without grouped-query attention (32 key/value heads): {kv_cache_gb(128_000, n_kv_heads=32)[1]:.1f} GB at 128,000 tokens")

Reading this output
  • An 8B model's weights need 16 GB in bf16 (Lesson 3.20). One user with a full 128,000-token context needs another 16.8 GB of KV cache, as much as the weights.
  • Serving 32 users at once, each with 8,000 tokens, needs about 34 GB of cache. In serving, the KV cache, not the weights, usually decides how many users fit on a GPU.
  • Grouped-query attention (several query heads sharing one key/value head, Lesson 7.18) cuts the cache by four times here, which is why nearly every recent model uses it. Serving engines such as vLLMlater · 3.25 manage cache memory in pages to waste less of it (Lesson 14.137).
The same idea as a formula
  • greedy: x_{t+1} = argmax_v p(v | x_{≤t})
  • temperature: p_T(v) = softmax(z / T)_v
  • top-k: keep the k largest z_v; top-p: keep the smallest set S of top tokens with Σ_{v∈S} p(v) ≥ p; renormalise, then sample
  • KV cache size: 2 × layers × KV heads × head size × bytes × tokens × users
  • work to generate n tokens: without a cache ∝ n²/2 positions processed, with a cache ∝ n
Check your mental model
  • ✗ "Temperature 0 makes the model more accurate."
    ✓ It makes it more consistent. If the most likely token is wrong, greedy decoding is consistently wrong.
  • ✗ "Top-p 0.9 means the model is 90% sure."
    ✓ It means sampling is restricted to the top tokens that together hold 90% of the probability, however many that takes.
  • ✗ "The KV cache stores the generated text."
    ✓ It stores each layer's keys and values for every token so far, numbers that are much larger than the text itself.

Practice
Apply it

Using kv_cache_gb, a 70B-class model has 80 layers, 8 key/value heads and a head size of 128. How much KV cache does one user with a 32,000-token conversation need in bf16? (Solution X1.)

Solutions

SolutionP1 · Temperature and top-p together

Fewer. Temperature 0.5 sharpens the distribution, so the top few tokens hold much more of the probability, and fewer are needed to reach 0.9. You can check with torch.isfinite(filter_logits(logits / 0.5, top_p=0.9)).sum(). Temperature and top-p interact; APIs usually apply temperature first, then the filters.

SolutionM1 · A repetition penalty

A penalty of 1.3 lowers the scores of tokens that already appeared, so exact loops usually disappear. It can also push the model away from words it legitimately needs to repeat (names, "the", product terms), making text awkward. Penalties are a blunt tool; better models and sampling usually matter more.

SolutionX1 · A 70B-class model

Per token: 2 × 80 × 8 × 128 × 2 = 327,680 bytes (320 KB). For 32,000 tokens: about 10.5 GB for one user, on top of about 140 GB of bf16 weights. Ten such users need another 105 GB, which is why long conversations on large models are expensive to serve.

Recap
  • A model gives probabilities; a decoding strategy chooses the token, appends it and repeats.
  • Greedy decoding always takes the top token: consistent, but prone to repetition in long text.
  • Temperature sharpens or flattens the distribution; top-k and top-p remove the unlikely tail before sampling.
  • Low temperature suits extraction and tool calls; moderate temperature with top-p suits chat; higher temperature suits brainstorming.
  • The KV cache keeps earlier tokens' keys and values so each step processes one new token; its memory grows with context length and users and often limits serving.
