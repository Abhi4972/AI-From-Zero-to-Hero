Why this came about

As agents ran in production, incidents became routine: loops, bad answers, cost spikes. AgentOps borrowed incident practice from site reliability engineering (triage, replay, post-mortems) and adapted it to agents.

In plain words first
From an alert to a fix, with evidence

When an agent misbehaves in production, AgentOps is the routine for handling it: triage the alert, find affected runs, replay a failing trace to reproduce it, identify the stage that failed, fix and test the fix against the replay, then add the case to the evaluation set and write up what happened. Good traces and replay tools turn incidents into tests.

Lesson 14.145 showed how to instrument an LLM application. This lesson is about operating an agent once it is live: what to look at every morning, what should wake someone up, how to find the one run in ten thousand that went wrong, and what to do in the first five minutes of an incident. The word for this practice is AgentOps. It is ordinary site reliability engineering, with one addition: the thing you are operating makes decisions, so you must observe its decisions as well as its latency.

Four layers of signals

Layer What it tells you Examples Where it comes from
Outcomes Is the agent doing the job? Task success per intent, escalation rate, user override rate, complaints, refunds reversed Online evals on sampled traces, business systems, feedback (Lesson 14.144)
Behavior Is it doing the job the right way? Steps per run, repeated calls, tools used per intent, policy denials, approval rate, unverified claims Trace analysis, policy decision logs (Lesson 14.138)
Cost and latency Can we afford it, and do users wait? Cost per successful task, tokens per run, cache hit rate, time to first token, p95 task time Spans with usage attributes, gateway logs (Lesson 14.142)
Infrastructure Are the parts up? Provider errors and rate limits, tool error rates and latency, queue depth, worker saturation Gateway, tool services, runtime metrics (Lesson 14.136, Lesson 14.141)

Most teams start at the bottom because infrastructure metrics are easy. Start at the top instead. An agent can be green on every infrastructure metric while confidently telling customers the wrong thing; only the outcome and behavior layers catch that.

Tip
Put the release on every span

Tag each trace with the release bundle (prompt, model, tool and policy versions, Lesson 14.147), the tenant, the intent and the outcome. Without the release tag you cannot answer the first question of every incident: "what changed?"

Traces are the source of truth

A trace per run, in the shape of the OpenTelemetry GenAI conventions (Lesson 14.145), is what makes everything else possible: one invoke_agent span for the run, with chat spans for model calls and execute_tool spans for tool calls beneath it. Three operating decisions matter:

  • Sampling. Keep every trace for errors, escalations, policy denials, cost outliers and the first days of a new release (tail sampling, decided after the run ends). Sample the healthy rest.
  • Content capture. Prompts and tool results contain personal data. Store them where access is controlled and retention is short, or redact them at the collector, and record that choice (Lesson 15.26).
  • Linking. Carry the trace ID into tickets, approvals and the business record ("refund R-88 was issued by run r-0204"), so a complaint can be traced back to the decisions that caused it.

Hands-on · Triage a day of runs

The first job every morning is to find the runs that went wrong in ways no error message reports. The script below generates 300 synthetic runs in the shape of OpenTelemetry GenAI spans (in production you would query your tracing backend), with release 0.5 introduced at run 200. It flags loops, step-budget breaches, runs that ended without an answer and cost outliers, and computes an error rate per tool.

import random, statistics
from collections import Counter, defaultdict

# Synthetic spans in the shape of the OpenTelemetry GenAI conventions: one invoke_agent span per run,
# with chat and execute_tool child spans. In production these come from your tracing backend.
def make_runs(n=300, seed=11):
    rng, runs = random.Random(seed), []
    for i in range(n):
        version = "0.4" if i < 200 else "0.5"
        spans, cost = [], 0.0
        steps = rng.randint(2, 6)
        looping = rng.random() < 0.03
        for s in range(steps if not looping else 14):
            tok_in = 2_000 + 900 * s
            spans.append({"gen_ai.operation.name": "chat", "gen_ai.usage.input_tokens": tok_in,
                          "gen_ai.usage.output_tokens": 150, "status": "ok"})
            cost += tok_in * 3e-6 + 150 * 15e-6
            tool = "get_order" if looping else rng.choice(["get_order", "search_kb", "issue_refund", "get_order"])
            err = None
            if tool == "search_kb" and version == "0.5" and rng.random() < 0.35:
                err = f"TimeoutError: search_kb exceeded 8000 ms (shard {rng.randint(1, 9)})"
            elif rng.random() < 0.02:
                err = f"HTTP 503 from orders-api request {rng.randint(10**5, 10**6)}"
            spans.append({"gen_ai.operation.name": "execute_tool", "gen_ai.tool.name": tool,
                          "args": "A-1001" if looping else f"A-{rng.randint(1000, 1999)}",
                          "status": "error" if err else "ok", "error": err})
        runs.append({"run_id": f"r-{i:04d}", "version": version, "spans": spans, "cost_usd": cost,
                     "final": not looping})
    return runs

def triage(runs, step_budget=10):
    findings = defaultdict(list)
    costs = sorted(r["cost_usd"] for r in runs)
    p99 = costs[int(len(costs) * 0.99) - 1]
    tool_calls, tool_errors = Counter(), Counter()
    for r in runs:
        calls = [(s["gen_ai.tool.name"], s["args"]) for s in r["spans"] if s["gen_ai.operation.name"] == "execute_tool"]
        for (tool, _), s in zip(calls, [s for s in r["spans"] if s["gen_ai.operation.name"] == "execute_tool"]):
            tool_calls[tool] += 1
            tool_errors[tool] += s["status"] == "error"
        if max(Counter(calls).values()) >= 3:
            findings["loop: same tool and arguments 3+ times"].append(r["run_id"])
        if len(calls) > step_budget:
            findings[f"over step budget ({step_budget})"].append(r["run_id"])
        if not r["final"]:
            findings["ended without a final answer"].append(r["run_id"])
        if r["cost_usd"] >= p99:
            findings["cost at or above p99"].append(r["run_id"])
    print(f"{len(runs)} runs | median cost ${statistics.median(costs):.3f} | p99 ${p99:.3f}")
    for f, ids in sorted(findings.items(), key=lambda kv: -len(kv[1])):
        print(f"  {len(ids):3} runs  {f:42} e.g. {', '.join(ids[:3])}")
    for tool in sorted(tool_calls):
        rate = tool_errors[tool] / tool_calls[tool]
        flag = "  <-- investigate" if rate > 0.05 else ""
        print(f"  tool {tool:13} {tool_calls[tool]:4} calls, error rate {rate:5.1%}{flag}")

runs = make_runs()
triage(runs)

Hands-on · Error signatures, and what changed

Raw error messages contain order numbers, shard IDs and request IDs, so ten thousand errors look like ten thousand different problems. Normalizing them into signatures groups them, and splitting the counts by release answers "what changed?" in one line.

import re

def signature(msg: str) -> str:
    """Normalize an error into a signature: drop numbers, IDs and quoted values."""
    msg = re.sub(r"[0-9a-f]{8}-[0-9a-f-]{27}", "<uuid>", msg)
    msg = re.sub(r"\b[A-Z]-\d{4}\b", "<order>", msg)
    msg = re.sub(r"\d+", "<n>", msg)
    return msg

by_sig = {}
for r in runs:
    for s in r["spans"]:
        if s.get("error"):
            sig = signature(s["error"])
            e = by_sig.setdefault(sig, {"count": 0, "versions": Counter(), "example": r["run_id"]})
            e["count"] += 1; e["versions"][r["version"]] += 1
for sig, e in sorted(by_sig.items(), key=lambda kv: -kv[1]["count"]):
    new = "  NEW in 0.5" if not e["versions"].get("0.4") else ""
    print(f"{e['count']:4}  {sig:58} versions {dict(e['versions'])}  e.g. {e['example']}{new}")
What you should see
  29  TimeoutError: search_kb exceeded <n> ms (shard <n>)        versions {'0.5': 29}  e.g. r-0204  NEW in 0.5
  19  HTTP <n> from orders-api request <n>                       versions {'0.4': 15, '0.5': 4}  e.g. r-0006

The orders-API errors are old noise spread across both releases. The search_kb timeouts exist only in 0.5, so the release introduced them, perhaps a longer query or a new index. That is a rollback decision you can make in minutes (Lesson 14.147), before anyone has worked out the root cause.

Hands-on · Replay a bad run exactly

A user complains that the agent said their refund was completed when it was not. Re-running the conversation against live systems will not reproduce it: the model samples differently, the knowledge base is up again and the order has moved on. Instead, replay the run: feed the agent the tool results the trace recorded, in order, and check that it asks for the same things. The bug then reproduces every time, and the fix can be proven against the same evidence before it ships.

import json

# A recorded run: every model decision and tool result, as the trace stored them.
RECORDED = {
    "run_id": "r-0204", "version": "0.5", "user": "Where is my refund for A-1077?",
    "steps": [
        {"tool": "get_order", "args": {"order_id": "A-1077"}, "result": {"status": "refund_requested", "amount": 2499}},
        {"tool": "search_kb", "args": {"query": "refund timeline"}, "result": {"error": "TimeoutError: search_kb exceeded 8000 ms"}},
    ],
    "final": "Your refund of INR 2,499 was completed today.",
}

def agent(user, call_tool, version):
    """The agent's decision logic for this intent (in a real system, the model plus its prompt)."""
    order = call_tool("get_order", {"order_id": "A-1077"})
    policy = call_tool("search_kb", {"query": "refund timeline"})
    if "error" in policy:
        if version == "0.5":                      # the bug: the error path still claims success
            return f"Your refund of INR {order['amount']:,} was completed today."
        return (f"Your refund of INR {order['amount']:,} is in progress. I can't check the usual "
                f"timeline right now; I'll message you as soon as I can.")
    return f"Your refund of INR {order['amount']:,} is in progress: {policy['text']}"

def replay(recorded, version):
    """Re-run the agent against the recorded tool results. No live systems are touched,
    and a mismatch in what the agent asks for is itself a finding."""
    log = iter(recorded["steps"])
    def call_tool(name, args):
        step = next(log)
        assert (name, args) == (step["tool"], step["args"]), f"diverged: asked {name}{args}, recorded {step['tool']}"
        return step["result"]
    return agent(recorded["user"], call_tool, version)

def claims_unverified_success(answer, recorded):
    """A code check: 'completed' requires a tool result that says completed."""
    seen = json.dumps([s["result"] for s in recorded["steps"]])
    return "completed" in answer and '"completed"' not in seen

for v in ["0.5", "0.6-fix"]:
    out = replay(RECORDED, v)
    print(f"{v:8} -> {out}")
    print(f"{'':8}    unverified success claim: {claims_unverified_success(out, RECORDED)}")
What you should see
0.5      -> Your refund of INR 2,499 was completed today.
            unverified success claim: True
0.6-fix  -> Your refund of INR 2,499 is in progress. I can't check the usual timeline right now; I'll message you as soon as I can.
            unverified success claim: False

Release 0.5 turned a knowledge-base timeout into a false claim of success; the fix says what is known and what is not. The claims_unverified_success check is a few lines of code, and it now belongs in the eval suite (Lesson 14.144) and in an online check on live traces, so this class of failure cannot come back silently. With a real model, replay the recorded model outputs too when you need an exact reproduction, or replay only the tool results and run the model several times to see how often the failure occurs.

Alerts: what pages, and what waits

Signal Page someone now Ticket for business hours
Harmful action or data exposure detected (policy violation, PII in output, unapproved write) Yes, always
Task success error budget burning fast (Lesson 14.145 burn-rate alerts) Yes Slow burn
A tool or provider failing for most runs Yes, if there is no fallback If degraded mode is working
Loop or step-budget breaches above baseline Yes
Cost per successful task above budget If the spend cap is about to trip Otherwise
New error signature after a release Yes, and check the canary (Lesson 14.147)
Override or escalation rate drifting up Yes, with a sample of runs to read

Page on what users and the business feel; everything else is a ticket. An agent team that pages on every tool timeout learns to ignore pages.

Incident response for agents

Agent incidents have one feature ordinary incidents lack: the system may still be acting while you investigate. So the first minutes are about stopping harm, not finding the cause.

Severity Agent examples Response
SEV1 Wrong or unauthorized actions in the world (payments, deletions, messages), data leaking to the wrong user Kill switch or disable the affected tools now; page the owner and security; preserve evidence
SEV2 Wrong answers at scale, an intent failing broadly, a runaway spend Roll back the release or route the intent to people; communicate a workaround
SEV3 Degraded quality or latency with a working fallback Fix in hours; watch the error budget

The first five minutes of a SEV1 or SEV2:

  1. Stop the bleeding. Use the controls you built before launch: the kill switch, per-tool disable flags, routing an intent to people, or rolling back the release bundle (Lesson 14.138, Lesson 14.147). Prefer the narrowest control that stops the harm.
  2. Preserve the evidence. Pin the traces, approvals and policy logs for affected runs so retention does not delete them.
  3. Find the blast radius. Query traces for every run with the same signature, release and tool, and list the affected users and records. Agents act on many records; the list is the input to remediation.
  4. Communicate. Tell support what users will see and what to say; for data or money, involve the people who own those obligations.
  5. Remediate the effects, not only the cause: reverse the duplicate refunds, contact the users who received wrong information.

Postmortems that ratchet

Run a blameless postmortem for every SEV1 and SEV2. For agents, add three questions to the usual timeline, root cause and actions:

  • Which check would have caught this before release? Add it to the eval suite (Lesson 14.144), so the release gate now blocks this failure.
  • Which control would have contained it sooner? A tighter permission, an approval, a lower spend cap or a narrower kill switch (Lesson 14.138).
  • Which signal would have shown it earlier? An online check, a new alert or a dashboard panel.

Each answer becomes a permanent rule, test or hook: the same ratchet that Lesson 14.67 applies to harnesses, applied to operations.

Lab P6 · Run it like a service
  1. Export a day of traces from your agent (or the capstone) and run the triage script on them. Write down the top three findings and one action for each.
  2. Add error signatures to your dashboard, split by release.
  3. Pick one run with negative feedback and replay it from its recorded tool results. Write a code check that detects the failure and add it to your eval suite.

Solutions

SolutionP1 · Stop the bleeding

Disable the refund tool or capability with a kill switch (Lesson 14.133), then investigate. Containment comes before diagnosis.

SolutionB1 · Replay needs traces

Which tools were called, with what arguments, what context the model had, and where the behavior diverged. Keep traces to replay runs.

SolutionD1 · Nondeterminism in replay

Not necessarily: the model's sampling, changed data or tool results can differ. Replay with recorded tool results and fixed parameters, run several times, and test the specific failure.

SolutionM1 · A runbook

Detect from alerts or reports; contain with the kill switch; diagnose from traces (tool results, policy retrieval, prompt version); fix and add eval cases; communicate to affected customers; write a blameless postmortem.

Explain the mechanismWhat is AgentOps?

Worked answer. Operating agents in production: monitoring behavior and quality, triaging failures by category, replaying runs from traces, managing incidents with runbooks and kill switches, and turning every failure into tests and fixes. A plausible wrong answer. "Monitoring uptime." Agents can be up and wrong.
