In plain words first
The idea in one line

A language model produces tokens. A program takes actions. The gap between those two is the tool interface: a contract that lets the model request an action and the host execute it. Every 2026 stack — function calling on OpenAI, Anthropic, and Gemini; MCP's tools/call; A2A's task parts — is a different encoding of the same four-step loop. This lesson names the loop and shows the minimum machinery to run it.

Terms you'll hear
Term What people say What it actually means
Tool "A thing the model can call" A triple of name + JSON-Schema-typed input + executor function
Function calling "Native tool use" Provider-level API support for emitting structured tool calls instead of prose
Tool call "The model's request to act" A JSON payload with id, name, arguments emitted by the model
Tool result "What the tool returned" The executor's output, wrapped in a tool role message with matching id
Parallel tool calls "Many calls at once" Multiple call objects in one model turn, independent and orderable by id
Strict mode "Guaranteed JSON" Constrained decoding that forces the model's output to validate against the declared schema
Pure tool "Read-only tool" No side effects; safe to re-run
Consequential tool "Action tool" Mutates external state; requires gate, audit, or user confirmation
Four-step loop "The tool-call cycle" describe → decide → execute → observe
Host "Agent runtime" The program that holds the tool registry, calls the model, and runs the executor

The problem

In plain words first

A language model can only write text. To check today's weather or send an email, it needs a program to act for it. A tool interface is the agreement between the two. The program tells the model which tools exist: a name, a description and the shape of the arguments. The model answers either in words or with a request such as "call get_weather with city = Tokyo". The program checks the request, runs the tool, and gives the result back to the model, which then answers or asks for another tool. That four-step loop (describe, decide, execute, observe) is the same in OpenAI's, Anthropic's and Google's APIs and in MCP. This lesson runs the loop with a real 0.5B open model on a laptop CPU, including the ways it goes wrong: a call written as prose, an unnecessary call, and an email that waits for the user's permission. No model is trained.

An LLM emits a probability distribution over the next token. That is the entire output surface. If you ask a chat model "what is the weather in Bengaluru right now," it can write a plausible sentence, but it cannot dial into a weather API. The sentence might be right by coincidence or three days stale.

Closing that gap is the purpose of the tool interface. The host program — your agent runtime, Claude Desktop, ChatGPT, Cursor, or a custom script — advertises a list of callable tools to the model. The model, when it decides an action is needed, emits a structured payload naming a tool and its arguments. The host parses that payload, runs the tool for real, and feeds the result back. The loop continues until the model decides no more calls are needed.

The first version of this contract shipped in June 2023 as OpenAI's "functions" parameter. Anthropic previewed tool use with Claude 2.1 (November 2023) and shipped tool_use content blocks in 2024. Gemini's API launched with functionDeclarations in December 2023. Every provider now exposes the same shape: a JSON-Schema-typed tool list in, a JSON-payload tool call out. The Model Context Protocol (November 2024) generalized the contract so one tool registry serves every model. A2A (announced April 2025, v1.0 in March 2026) layered the same primitive for agent-to-agent delegation.

The four-step loop is the invariant underneath all of these. Everything else in Phase 13 is an elaboration.

Idea 1 · Step one: describe

The host declares each tool to the model with three fields. The fourth part, the executor, stays on the host side and never reaches the model.

  • Name. A stable, machine-readable identifier. get_weather, not "weather thing".
  • Description. A one-paragraph natural-language brief. "Use when the user asks about current conditions for a specific city. Do not use for historical data."
  • Input schema. A JSON Schema object (draft 2020-12) describing the tool's arguments.

The model receives the list. Modern providers serialize these declarations into the system prompt using a provider-specific template, so you as the caller only deal with the structured form.

Idea 2 · Step two: decide

Given the user's message and the available tools, the model chooses one of three behaviors.

  1. Answer directly in text. No tool call.
  2. Call one or more tools. Emit structured call objects. Parallel calls are on by default on OpenAI (parallel_tool_calls), Anthropic (turn off with disable_parallel_tool_use) and Gemini, so the model can emit several calls in one turn.
  3. Refuse. Decline in plain text. OpenAI's structured outputs report a refusal in a separate refusal field, so code can tell it apart from a valid result.

A tool call payload has three stable fields: a call id, a tool name, and a JSON arguments object. The id exists so the host can correlate the later result with the specific call, which matters when parallel calls come back out of order.

Idea 3 · Step three: execute

The host receives the call, validates arguments against the declared schema, and runs the executor. Invalid arguments mean the model hallucinated a field or used the wrong type — a very common failure mode on weak models. Production hosts do one of three things on invalid arguments: fail fast and surface the error to the model, repair the JSON with a constrained parser, or retry the model with the validation error included in the prompt.

The executor itself is ordinary code. Python, TypeScript, a shell command, a database query. It produces a result, which is usually a string but can be any JSON value or a structured content block (text, image, or resource reference in MCP). The result must be serializable.

Idea 4 · Step four: observe

The host appends the tool result to the conversation (as a tool role message with matching id) and re-invokes the model. The model now has the tool output in context and can produce a final answer or request more calls. This continues until the model stops emitting calls or the host hits a safety limit on iteration count.

The same idea as a formula

The loop. Let mt​ be the conversation at turn t and f the model. Each turn the model returns either text or a list of calls ci​=(idi​,namei​,argsi​):

f(mt​,T)∈{text}∪{[c1​,…,ck​]},mt+1​=mt​+[c1​,…,ck​]+[r1​,…,rk​],
where T is the tool list and ri​=run(ci​) if argsi​ validates against the tool's schema, or an error message otherwise. The loop stops at the first text answer or at t=Tmax​.

Errors compound. If each call is well-formed with probability p, a task that needs k calls gets through with no bad call with probability pk. With one retry after a validation error, each call fails only if both attempts fail:

P(task)=pkwithout retries,(1−(1−p)2)kwith one retry.

Describe costs tokens on every request: extra=∑tools​tokens(name + description + schema), paid once per model call, so once per turn of the loop.

Worked example
Ten calls, one retry, and the price of describing
  • p=0.95, a task with k=10 calls: 0.9510≈0.60. Four tasks in ten hit at least one bad call.
  • With one retry: each call fails with probability 0.052=0.0025, so 0.997510≈0.975.
  • In the run below, two short tools add 252 prompt tokens to every request. A 4-turn loop pays that 4 times: 1,008 tokens. Twenty tools of about 120 tokens each would add about 2,400 tokens to every turn.
  • A bound of Tmax​=5 turns caps the cost of a confused model at 5 model calls, however long it keeps calling tools.
Check your mental model
  • ✗ "The model runs the tool."
    ✓ The model only writes a request; the host validates it, runs the code and reports back.
  • ✗ "The executor's code is sent to the model."
    ✓ Only the name, description and schema are; the executor stays on the host.
  • ✗ "If the reply contains JSON, the model made a tool call."
    ✓ A call counts only in the format the host parses (here <tool_call> tags); JSON in prose is a format error to repair.
  • ✗ "A model with tools will use them only when needed."
    ✓ Small models call tools eagerly; the descriptions and the host's checks have to compensate.
Predict before you run

A 0.5B open model gets two tools, get_weather and send_email, and four questions: Tokyo's weather, a comparison of two cities, an email to send, and the capital of France. Which ones will it handle correctly? (Solution P1.)

See it drawn
The four-step loop with a real model

Qwen2.5-0.5B-Instruct (about 1 GB, runs on a laptop CPU) receives the tool list through its chat template. The host parses <tool_call> blocks, validates the arguments with jsonschema, refuses to run the consequential send_email without user confirmation, runs the rest, and returns the results as tool messages. Greedy decoding, at most 5 turns. About 40 seconds on CPU.

import json, re, torch, jsonschema
from transformers import AutoTokenizer, AutoModelForCausalLM, logging
logging.set_verbosity_error(); torch.manual_seed(0)

M = "Qwen/Qwen2.5-0.5B-Instruct"                   # a small open model trained for tool calls
tok = AutoTokenizer.from_pretrained(M); model = AutoModelForCausalLM.from_pretrained(M).eval()

# Step 1, describe: name + description + JSON Schema go to the model; the executor stays on the host.
WEATHER = {"Bengaluru": 28, "Tokyo": 12, "Zurich": 4}           # degrees Celsius
def weather(city, units="celsius"):
    c = WEATHER.get(city, 20)
    return {"city": city, "temp": c if units == "celsius" else round(c * 9 / 5 + 32, 1), "units": units}
TOOLS = {
    "get_weather": dict(
        description="Get the current temperature for a city. Use for questions about weather now.",
        schema={"type": "object", "properties": {"city": {"type": "string"},
                "units": {"type": "string", "enum": ["celsius", "fahrenheit"]}}, "required": ["city"],
                "additionalProperties": False},
        run=lambda a: weather(**a),
        consequential=False),
    "send_email": dict(
        description="Send an email to a person. Use only when the user asks to send a message.",
        schema={"type": "object", "properties": {"to": {"type": "string"}, "body": {"type": "string"}},
                "required": ["to", "body"], "additionalProperties": False},
        run=lambda a: {"sent": True}, consequential=True)}
specs = [{"type": "function", "function": {"name": n, "description": t["description"], "parameters": t["schema"]}}
         for n, t in TOOLS.items()]

def model_turn(messages):                          # Step 2, decide: the model writes text or a tool call
    ids = tok.apply_chat_template(messages, tools=specs, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = model.generate(ids, max_new_tokens=120, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()

def run(user, max_turns=5):
    messages = [{"role": "user", "content": user}]
    print(f"USER: {user}")
    for turn in range(1, max_turns + 1):        # circuit breaker
        reply = model_turn(messages)
        calls = re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", reply, re.S)
        if not calls:
            print(f"  turn {turn} MODEL (final answer): {reply}"); return
        messages.append({"role": "assistant", "content": reply})
        for raw in calls:                        # Step 3, execute: parse, validate, gate, run
            try:
                call = json.loads(raw); tool = TOOLS[call["name"]]
                jsonschema.validate(call["arguments"], tool["schema"])
            except Exception as e:
                result = {"error": f"invalid call: {type(e).__name__}: {str(e).splitlines()[0][:80]}"}
            else:
                if tool["consequential"]:
                    result = {"error": "needs user confirmation; not executed"}
                else:
                    result = tool["run"](call["arguments"])
            print(f"  turn {turn} MODEL calls: {raw}\n         HOST returns: {json.dumps(result)}")
            messages.append({"role": "tool", "content": json.dumps(result)})   # Step 4, observe
    print("  stopped: turn limit reached")

for q in ("What's the weather in Tokyo right now?", "Is it warmer in Bengaluru or in Zurich?",
          "Email bob@example.com that the meeting moved to 3pm.", "What is the capital of France?"):
    run(q); print()

Reading this output

Tokyo: a correct call with a choice nobody asked for. The model called get_weather with valid arguments, but picked Fahrenheit on its own; the schema allowed it and the description gave no default. The host converted, and the answer (53.6 °F) is right but not what most users want. Descriptions and schema defaults steer these choices.

The comparison: a call written as prose. The model explained that it would call get_weather and printed the call as a JSON code block, outside the <tool_call> tags the host parses. The host saw no call, treated the text as the final answer, and the reply ran out at the 120-token limit. This is the "JSON in prose" failure from Idea 7, on the second question.

The email: the gate works. The call was well-formed, but send_email is consequential, so the host refused to run it without confirmation and said so. The model passed that on, though it also asked for the address it already had: small models misread tool results too.

The capital of France: an unnecessary call. The answer needs no tool, yet the model called get_weather for Paris and added the temperature to a correct answer. Harmless here; with a paid or slow tool it is wasted time and money.

One question out of four went exactly right. Frontier models do much better, but every one of these failure kinds occurs in production, which is why the host validates, gates and bounds the loop.

What "describe" sends, and repairing a format error

This block continues from the one above. It prints the prompt text the chat template builds from the two tools and counts its tokens. Then it reruns the comparison question with one change to the host: a reply that contains a call written as prose is sent back with an instruction to use the proper format. About 15 seconds.

# Continues from the block above: tok, model, specs, TOOLS, model_turn and run are defined.
import json, re

# What "describe" really sends: the chat template turns the tool list into prompt text.
plain = tok.apply_chat_template([{"role": "user", "content": "Hi"}], add_generation_prompt=True, tokenize=False)
with_tools = tok.apply_chat_template([{"role": "user", "content": "Hi"}], tools=specs, add_generation_prompt=True, tokenize=False)
n = lambda s: len(tok(s)["input_ids"])
print(f"prompt tokens without tools: {n(plain)}, with 2 tools: {n(with_tools)} "
      f"(+{n(with_tools) - n(plain)} on every request)")
print("\nwhat the model reads before the user's message:\n")
print(with_tools.split("<|im_start|>user")[0].strip())

# Repair: a reply that holds JSON outside <tool_call> tags is a format error, not an answer.
def run_with_repair(user, max_turns=5):
    messages = [{"role": "user", "content": user}]
    print(f"\nUSER: {user}")
    for turn in range(1, max_turns + 1):
        reply = model_turn(messages)
        calls = re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", reply, re.S)
        if not calls and '"arguments"' in reply:             # looks like a call, wrong format
            print(f"  turn {turn} MODEL wrote a call as prose -> HOST asks for the proper format")
            messages += [{"role": "assistant", "content": reply},
                         {"role": "user", "content": "Do not describe tool calls. Emit each call inside "
                          "<tool_call></tool_call> tags, one per tool call."}]
            continue
        if not calls:
            print(f"  turn {turn} MODEL (final answer): {reply[:300]}"); return
        messages.append({"role": "assistant", "content": reply})
        for raw in calls:
            call = json.loads(raw); result = TOOLS[call["name"]]["run"](call["arguments"])
            print(f"  turn {turn} MODEL calls: {raw}\n         HOST returns: {json.dumps(result)}")
            messages.append({"role": "tool", "content": json.dumps(result)})
    print("  stopped: turn limit reached")

Reading this output

Describing tools costs 252 tokens per request. The chat template pastes each tool's JSON into a system message inside <tools> tags, followed by an instruction to answer with <tool_call> blocks. The model has no other knowledge of the tools: wording in the description is all it can go on.

The repair fixes the format. After the host's correction ("emit each call inside <tool_call> tags"), the model makes a proper call on the next turn.

It does not fix the reasoning. The model fetched only Zurich's temperature and then answered about Zurich alone; the comparison with Bengaluru never happened. Format repair is cheap and worth doing, but it cannot make a small model plan a two-call task. Bigger models, clearer descriptions, or a host that checks whether the question was answered are the next steps.

Idea 5 · The trust split

Tools come in two flavors that matter for safety.

  • Pure. Read-only, deterministic, no side effects. get_weather, search_docs, get_current_time. Safe to call speculatively.
  • Consequential. Mutates state, spends money, touches user data. send_email, delete_file, execute_trade. Must be gated.

Meta's "Agents Rule of Two" (October 2025) says a single agent session should combine at most two of: untrusted input, access to sensitive data or systems, and the ability to change state or communicate externally. The tool interface is where you enforce that rule — by rejecting calls, requiring user confirmation, or escalating scopes. See Phase 13 · 15 for the full security chapter and Phase 14 · 09 for agent-level permission policies.

Idea 7 · Why not just prompt the model to emit JSON?

"Ask the model to reply in JSON" was the pre-function-calling pattern. It fails often enough to matter, rarely on frontier models and far more on small ones (the 0.5B model below does it on its second question). Failure modes include missing braces, trailing commas, hallucinated fields, wrong types, and JSON wrapped in prose. You then need a JSON repair pass, a retry, or a constrained decoder.

Native function calling is better for three reasons. First, the provider trains the model on the exact call shape, so well-formed calls are the norm. Second, the call payload sits in its own protocol slot, not inside free-text — so a tool call never leaks into the user-visible reply. Third, providers can enforce schema compliance with constrained decoding (OpenAI's strict: true, Anthropic's strict tool use, Gemini's response schemas); in strict mode the arguments are guaranteed to validate.

Phase 13 · 02 walks the three provider APIs side by side. Phase 13 · 04 goes deep on structured outputs.

Idea 8 · Circuit breakers

The loop terminates when the model stops emitting calls or the host hits a maximum turn count. Production hosts set such a bound, commonly between 5 and 25 turns; the OpenAI Agents SDK, for example, stops after 10 turns unless you raise max_turns.

The alternative — unbounded loops — shows up every six months as "agent spent $400 in API calls overnight" post-mortems. Do not ship without a bound.

Industry practice
What's current (2024–2026)
  • The same loop in every major API: OpenAI (Responses API function tools), Anthropic (tool_use and tool_result blocks) and Google Gemini (functionDeclarations) all take JSON Schema tool lists and return calls with an id, a name and arguments.
  • Strict modes guarantee valid arguments: OpenAI's strict: true and Anthropic's strict tool use constrain decoding so the arguments always match the schema.
  • MCP 2026-07-28 is the current revision of the Model Context Protocol: stateless, with tool lists that one server offers to any MCP-capable client (Lessons 13.6–13.14).
  • Agent SDKs run the loop for you: the OpenAI Agents SDK, the Claude Agent SDK and LangGraph handle parsing, tool execution and turn limits (max_turns), and leave confirmation gates to you.
  • Laptop-sized tool calling: Qwen2.5 and Qwen3 models from 0.5B to 4B, and Llama 3.2 1B/3B, support tool calls through their chat templates; expect more format errors than from frontier models, as the run shows.

Sources: OpenAI function calling, Anthropic tool use, Claude strict tool use, Gemini function calling, MCP specification 2026-07-28, Meta: Agents Rule of Two.

Recap
What to keep from this lesson
  • Describe, decide, execute, observe: the loop behind every tool API and MCP.
  • The model sees name, description and schema; the host keeps the executor.
  • Validate every call before running it; return errors to the model so it can retry.
  • Gate consequential tools behind user confirmation.
  • Always bound the loop with a turn limit.

Ship it

This lesson produces outputs/skill-tool-interface-reviewer.md. Given a draft tool definition (name + description + schema + executor outline), the skill audits it for loop fitness: is the name machine-stable, is the description a complete usage brief, does the schema use JSON Schema 2020-12 correctly, and is the pure-vs-consequential classification explicit.

---
name: tool-interface-reviewer
description: Audit a tool definition (name + description + JSON Schema + executor outline) for loop fitness before it ships to an LLM.
version: 1.0.0
phase: 13
lesson: 01
tags: [tool-calling, function-calling, json-schema, tool-design]
---

Given a proposed tool definition, review it against the four-step loop (describe, decide, execute, observe) and flag loop-breaking defects before the tool reaches a model.

Produce:

1. Name audit. Is the name `snake_case`, stable across versions, and unambiguous? Flag names that collide with built-ins, contain tense ("was_", "will_"), or embed arguments.
2. Description audit. Does the description read as a complete usage brief? Require the two-sentence shape: "Use when X. Do not use for Y." Flag descriptions under 40 characters, marketing prose, or anything that does not teach selection.
3. Schema audit. Is the schema valid JSON Schema 2020-12? Every field typed? `required` list explicit? Enums used for closed value sets? Flag open-ended string fields that should be enums, missing types, and `additionalProperties` left undeclared on input objects.
4. Executor audit. Is the executor deterministic given arguments? Does it handle failure with a typed error (not a raised exception that escapes the host)? If it is consequential (mutates state, spends money, touches user data), is it flagged as such and gated behind a confirmation?
5. Classification. State whether the tool is pure or consequential and why. A consequential tool without a gate is an immediate reject.

Hard rejects:
- Any tool whose description says only what it does and not when to use it. The model needs the "when" for step two.
- Any schema with an untyped field. The validator cannot do its job.
- Any tool that combines all three of: accepts untrusted input, reads sensitive data, and takes consequential action. Violates Meta's Rule of Two.
- Any tool whose executor raises unhandled exceptions on bad input. The host should not need a try/except around every call.

Refusal rules:
- If the tool definition is missing a schema, refuse. Route to Phase 13 · 04 first.
- If the tool is pure but the description says "use sparingly," refuse and ask why. Pure tools should be cheap to re-run.
- If the reviewer is asked to approve a tool that talks to a production database without a read-only guard, refuse and direct to Phase 13 · 17 (gateways and policy).

Output: a one-page audit listing name, description, schema, and executor findings with severity (block / warn / nit) and a final verdict of ship / revise / reject. End with a one-line rewrite suggestion for any reject, if feasible.

Solutions

SolutionP1 · One right, one half-right, one gated, one unnecessary call

Only Tokyo went right, and even there the model chose Fahrenheit unasked. The comparison failed on format: the call was written as JSON in prose, which the host does not parse. The email was a correct call that the host correctly refused to run without confirmation. The capital of France got a correct answer plus an unnecessary weather call.

The pattern is typical of small models: they know the call format but apply it unreliably, call tools too eagerly, and lose track of multi-step questions. The host's checks (parsing only the official format, schema validation, confirmation gates, a turn limit) are what keep these errors from turning into wrong actions.

SolutionB1 · The loop never ends on its own

Without a turn limit the loop never ends on its own: every result asks for another call, and the model obliges. Cost grows faster than the number of turns, because each turn resends the whole conversation. If each turn adds a tokens, turn t sends about t⋅a tokens and T turns send about a⋅T2/2: 100 turns cost about 50 times as much as 10, not 10 times. Latency grows the same way, and the user waits for nothing.

What the host should do:

  • A hard turn limit (5 to 25 is typical), after which it stops and reports what it has.
  • A budget in tokens or money per task, checked every turn.
  • Loop detection: the same tool called with the same arguments twice in a row is almost always a loop; stop or return an error that says so.
  • Honest tool results: a paginated tool should return a cursor and say how much is left, so the model (or the host) can decide when enough is enough.
