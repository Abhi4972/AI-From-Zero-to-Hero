In plain words first
The idea in one line

The session is going to end. The work is not. The handoff packet is the artifact that turns "the agent worked for an hour" into "the next session is productive in the first minute." Build it on purpose, not as an afterthought.

Terms you'll hear
Term What people say What it actually means
Handoff packet "Session summary" Generated artifact carrying the seven fields, both markdown and JSON
Next action "What to do first" The one concrete step that starts the next session
Feedback trim "Log summary" Last K records plus every non-zero exit
Status report "What we did" A document missing next_action; useful, but not a handoff
Verdict pointer "Receipt" Path to the verification + review reports for traceability

The problem

In plain words first

A handoff is the packet one session leaves for the next: what changed, which commands ran, what failed and why, the open risks, and the first concrete next step. Without one, the next session repeats the same failed attempts. The lesson's point is that handoffs should be generated from recorded artifacts (state, feedback, verdict, review), not written from memory at the end of a long session. State files and resume are covered in Lessons 14.6 and 14.13 (linked above); this lesson ends a real session mid-task and measures what each kind of handoff gives the next one.

The session ends. The agent says "great, we made progress." The next session opens. The next agent asks "where did we leave off?" The first agent's answer is gone. The next agent rediscovers, re-runs the same commands, re-asks the human the same questions, and burns thirty minutes recovering the last thirty seconds of the previous session.

The cost of a bad handoff is paid every session for the life of the task. The fix is a packet generated automatically at session end: what changed, why, what was tried, what failed, what is left, what to do first next time.

The idea

Idea 1 · Seven fields every handoff carries

Field Question it answers
summary One paragraph of what was done
changed_files The diff at a glance
commands_run What was actually executed
failed_attempts What was tried and why it did not work
open_risks What could bite next session, with severity
next_action The first concrete step next session takes
verdict_pointer Path to the verification + review reports

The next_action field is the load-bearing one. A handoff with everything except next_action is a status report, not a handoff.

Idea 2 · Handoffs are generated, not written

A hand-written handoff is a handoff that gets skipped on a hard day. The generator reads the workbench artifacts and emits the packet. The agent's job is to leave the workbench in a state the generator can summarize, not to write the summary.

Idea 3 · Two forms: human-readable and machine-readable

handoff.md is what the human reads. handoff.json is what the next agent loads. Both come from the same source artifacts. If they diverge, the JSON wins.

Idea 4 · Feedback log trimming

The full feedback_record.jsonl may be hundreds of entries. The handoff carries only the last K plus every entry with a non-zero exit. The next session loads the full log if it needs to, but the packet stays small.

Idea 5 · Leave a clean state

A handoff describes the work. A clean state makes the work resumable. They are not the same thing. A perfect handoff.md is worthless if the next session opens to a half-applied diff, a temp file the agent forgot, a stray branch, and tests that error before they even run. The next agent then spends its first ten minutes cleaning up after the last one instead of building, and the cost compounds every session for the life of the task.

So the session does not end when the feature works. It ends when the workbench is in a state the generator can summarize and the next session can trust. Cleanup is its own phase, run before the handoff, and it is a check, not a habit, because a habit is the thing that gets skipped on a hard day.

Check Clean means Dirty blocks because
Working tree Every change committed or explicitly stashed with a note A half-applied diff looks like intentional work to the next agent
Temp artifacts No *.tmp, scratch dirs, debug prints, or commented-out blocks left behind Stray files pollute the diff and the next agent's mental model
Tests Green, or red with the failure named in open_risks A silent red test is a trap the next session steps in
Feature board feature_list.json status reflects reality (Phase 14 · 36) A stale board sends the next session to work that is already done
Branch On the expected branch, no detached HEAD, no orphan branches Wrong branch means the next session's first commit lands in the wrong place

The cleanup phase emits a clean_state.json of blocking issues; an empty list is the precondition the handoff generator asserts before it writes a packet. A handoff built on a dirty tree is not a handoff, it is a forwarded mess. The two artifacts pair: cleanup proves the workbench is safe to leave, the handoff proves the next session knows where to start.

The same idea as a formula

Repeated work. If session 1 tried k approaches that failed, and session 2 does not know them, each of its attempts repeats a known failure with probability about q (the chance the model's first idea is one already tried). Its expected wasted attempts before something new are about q/(1−q); a handoff that lists the failures lowers q only if the model uses it.

Fidelity. A handoff field is faithful if it can be checked against a record. A generated handoff has fidelity 1 for every field it derives (commands, exit codes, blockers); a model-written summary can drop or invent any of them, and nothing checks.

Worked example
Three handoffs for one stuck task
  • Session 1 tried largest twice. Both times the model renamed the function, so the test failed with ImportError: cannot import name 'largest'.
  • No handoff: session 2's single attempt hits the same ImportError.
  • Model-written handoff: about 800 characters about the attempts. It never names the ImportError and has no next step. Session 2 fixes it anyway.
  • Generated handoff: commands, two failed attempts, the ImportError as an open blocker, the next action. Session 2 fixes it too. Across three stuck tasks: none 0 of 3, either handoff 2 of 3.
Check your mental model
  • ✗ "The next session can work it out from the code."
    ✓ Without a handoff it repeated the same failure on all three tasks.
  • ✗ "Ask the agent to summarise its session."
    ✓ Its notes left out every error that happened; nothing checks what they say.
  • ✗ "A generated handoff is a status report."
    ✓ Only with a next action and the failed attempts does it become a handoff.
  • ✗ "Handoffs are for humans."
    ✓ The machine-readable half is what the next agent session reads.

# A session that ends mid-task, and what the next one is told. Session 1: Qwen2.5-0.5B-Instruct (greedy, CPU)
# gets two attempts at each of four bugs; every attempt's test result is recorded. Then three handoffs for the
# unfinished tasks: none, one written by the model ("summarise what you did for the next session"), and one
# generated by the lesson's generate_handoff (code/main.py) from the recorded artifacts. Here: what each
# handoff actually contains, checked against the record.
import os, pathlib, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import WorkbenchSnapshot, generate_handoff
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

BUGS = [("largest", "def largest(xs):\n    return min(xs)\n", "assert largest([3, 9, 2]) == 9 and largest([-5, -2]) == -2"),
        ("to_fahrenheit", "def to_fahrenheit(c):\n    return c * 9 / 5\n", "assert to_fahrenheit(100) == 212 and to_fahrenheit(0) == 32"),
        ("is_leap", "def is_leap(y):\n    return y % 4 == 0\n", "assert is_leap(2000) and not is_leap(1900) and is_leap(2024)"),
        ("average", "def average(xs):\n    return sum(xs) / len(xs)\n", "assert average([2, 4]) == 3 and average([]) == 0")]
work = pathlib.Path(tempfile.mkdtemp())

def chat(prompt, n=150):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

def attempt(name, code, extra=""):
    text = chat(f"This Python function has a bug.\n{code}\n{extra}Return only the corrected function in a ```python block.")
    m = re.search(r"```(?:python)?\n(.*?)```", text, re.S)
    fix = (m.group(1) if m else code).strip() + "\n"
    (work / f"{name}.py").write_text(fix)
    (work / f"test_{name}.py").write_text(f"from {name} import {name}\n{next(t for n, _, t in BUGS if n == name)}\n")
    p = subprocess.run([sys.executable, f"test_{name}.py"], cwd=work, capture_output=True, text=True, timeout=30)
    err = p.stderr.strip().splitlines()[-1] if p.returncode else ""
    return fix, p.returncode, err

SESSION1 = {}
for name, code, _ in BUGS:
    tries, extra = [], ""
    for _ in range(2):
        fix, rc, err = attempt(name, code, extra)
        tries.append((fix, rc, err))
        if rc == 0:
            break
        extra = f"Your last attempt failed: {err}\n"
    SESSION1[name] = tries
    print(f"{name:<14} session 1: " + ", ".join("pass" if rc == 0 else f"fail ({err[:40]})" for _, rc, err in tries))

OPEN = [n for n, tries in SESSION1.items() if tries[-1][1] != 0]
print(f"\nunfinished when session 1 ends: {OPEN}\n")
HANDOFFS = {}
for name in OPEN:
    tries = SESSION1[name]
    feedback = [{"command": f"python test_{name}.py", "exit_code": rc, "stderr": err} for _, rc, err in tries]
    snap = WorkbenchSnapshot(task_id=f"T-{name}", state={"next_action": f"fix {name} so test_{name}.py passes",
                             "blockers": [err for _, rc, err in tries if rc]},
                             verdict={"passed": False, "findings": [{"severity": "block", "detail": "acceptance failed"}]},
                             review={"verdict": "not reviewed", "total": 0}, feedback=feedback,
                             diff_summary={"touched": [f"{name}.py"]})
    generated, _ = generate_handoff(snap)
    model_written = chat(f"You worked on fixing {name}. Your attempts:\n" + "\n".join(f"```python\n{f}```" for f, _, _ in tries) +
                         "\nWrite a short handoff note for the next session: what you tried, what failed, and what to do next.", n=160)
    HANDOFFS[name] = {"none": "", "model-written": model_written.strip(), "generated": generated}
    errors = [err for _, rc, err in tries if rc]
    for kind, text in HANDOFFS[name].items():
        if kind == "none":
            continue
        has_err = all(e.split(":")[0] in text for e in errors)
        has_next = "next" in text.lower()
        print(f"{name:<14} {kind:<14} {len(text):>4} chars   names the failing error: {has_err!s:<6} has a next step: {has_next}")

Part 1 of 3 · WorkbenchSnapshot, HandoffPayload, trim_feedback, derive_risks

"""Generate a handoff packet from workbench artifacts.

Reads state, verdict, review, and feedback (here stubbed in-memory),
writes handoff.md for humans and handoff.json for the next agent.

Run: python3 code/main.py
"""

from __future__ import annotations

import json
from dataclasses import asdict, dataclass, field
from pathlib import Path

HERE = Path(__file__).parent
TAIL_K = 5


@dataclass
class WorkbenchSnapshot:
    task_id: str
    state: dict[str, object]
    verdict: dict[str, object]
    review: dict[str, object]
    feedback: list[dict[str, object]]
    diff_summary: dict[str, list[str]]


@dataclass
class HandoffPayload:
    task_id: str
    summary: str
    changed_files: list[str]
    commands_run: list[str]
    failed_attempts: list[str]
    open_risks: list[dict[str, str]]
    next_action: str
    verdict_pointer: dict[str, str]
    feedback_tail: list[dict[str, object]] = field(default_factory=list)


def trim_feedback(records: list[dict[str, object]]) -> list[dict[str, object]]:
    tail = records[-TAIL_K:]
    nonzero = [r for r in records if r.get("exit_code") not in (0, None)]
    out: list[dict[str, object]] = []
    seen: set[int] = set()
    for r in tail + nonzero:
        key = id(r)
        if key in seen:
            continue
        seen.add(key)
        out.append(r)
    return out


def derive_risks(snapshot: WorkbenchSnapshot) -> list[dict[str, str]]:
    risks: list[dict[str, str]] = []
    for f in snapshot.verdict.get("findings", []) or []:
        if isinstance(f, dict) and f.get("severity") in ("warn", "block"):
            risks.append({"severity": str(f.get("severity")), "detail": str(f.get("detail"))})
    for blocker in snapshot.state.get("blockers") or []:
        risks.append({"severity": "warn", "detail": f"open blocker: {blocker}"})
    raw_total = snapshot.review.get("total", 10)
    try:
        safe_total = int(raw_total)
    except (TypeError, ValueError):
        safe_total = 10
    if safe_total < 7:
        risks.append({"severity": "warn", "detail": f"review total {raw_total} below 7"})
    return risks

def generate_handoff(snapshot: WorkbenchSnapshot) -> tuple[str, HandoffPayload]:
    next_action = str(snapshot.state.get("next_action") or "no next_action recorded; needs human")
    payload = HandoffPayload(
        task_id=snapshot.task_id,
        summary=f"task {snapshot.task_id}: review={snapshot.review.get('verdict')}, gate={snapshot.verdict.get('passed')}",
        changed_files=snapshot.diff_summary.get("touched", []),
        commands_run=[str(r.get("command")) for r in snapshot.feedback],
        failed_attempts=[
            f"{r.get('command')} -> exit {r.get('exit_code')}"
            for r in snapshot.feedback
            if r.get("exit_code") not in (0, None)
        ],
        open_risks=derive_risks(snapshot),
        next_action=next_action,
        verdict_pointer={
            "verdict": f"outputs/verification/{snapshot.task_id}.json",
            "review": f"outputs/review/{snapshot.task_id}.json",
        },
        feedback_tail=trim_feedback(snapshot.feedback),
    )

    def _bullets(items: list[str]) -> list[str]:
        return items or ["- none"]

    md_lines = [
        f"# Handoff: {payload.task_id}",
        "",
        f"**Summary.** {payload.summary}",
        "",
        "## Changed files",
        *_bullets([f"- `{f}`" for f in payload.changed_files]),
        "",
        "## Commands run",
        *_bullets([f"- `{c}`" for c in payload.commands_run]),
        "",
        "## Failed attempts",
        *_bullets([f"- {f}" for f in payload.failed_attempts]),
        "",
        "## Open risks",
        *_bullets([f"- [{r['severity']}] {r['detail']}" for r in payload.open_risks]),
        "",
        "## Next action",
        f"{payload.next_action}",
        "",
        "## Receipts",
        f"- verdict: `{payload.verdict_pointer['verdict']}`",
        f"- review:  `{payload.verdict_pointer['review']}`",
    ]
    return "\n".join(md_lines) + "\n", payload


def main() -> None:
    snapshot = WorkbenchSnapshot(
        task_id="T-001",
        state={
            "active_task_id": None,
            "blockers": ["awaiting decision on rate-limit window"],
            "next_action": "open PR with current diff and request review",
        },
        verdict={"passed": True, "findings": [{"severity": "warn", "detail": "off-scope: README.md"}]},
        review={"verdict": "pass", "total": 8},
        feedback=[
            {"command": "pytest", "exit_code": 0},
            {"command": "ruff check .", "exit_code": 0},
            {"command": "pytest test_signup.py", "exit_code": 1},
            {"command": "pytest test_signup.py", "exit_code": 0},
        ],
        diff_summary={"touched": ["app/signup.py", "tests/test_signup.py", "README.md"]},
    )

    md, payload = generate_handoff(snapshot)
    (HERE / "handoff.md").write_text(md)
    (HERE / "handoff.json").write_text(json.dumps(asdict(payload), indent=2) + "\n")
    print(md)

Production patterns in the wild

Codex CLI, Claude Code, and OpenCode each ship a different compaction story; the structured handoff packet sits on top of all three.

Compaction strategies vary; the packet schema does not. Codex CLI's POST /v1/responses/compact is a server-side opaque AES blob (fast path for OpenAI models); the fallback is a local "handoff summary" appended as a _summary user-role message. Claude Code runs five-stage progressive compaction at 95% of context. OpenCode does timestamp-based message hiding plus a 5-heading LLM summary. Three different mechanisms, same need: serialize what survives compression into a portable artifact. The packet is that artifact.

Fresh-session handoff is not compaction. Compaction extends a session; handoff closes one cleanly and starts the next. The Hermes Issue #20372 framing (April 2026) is right: when in-place compression starts degrading, the agent should write a compact handoff, end the session, and resume in fresh context. The packet is what makes that transition cheap. The mistake is to keep compressing until quality collapses; the fix is to budget for an early, clean handoff.

One active handoff per branch and topic. Multi-agent coordination breaks down on stale handoffs more than on bad model output. Always include branch, last_known_good_commit, and a status of active | superseded | archived. Stale handoffs are archived; only the active one drives the next session. This is the difference between handoff-as-notes and handoff-as-state.

Wrap up before 50-75% context, not at the wall. The hand-written-pattern playbook (CLAUDE.md + HANDOVER.md) reports best results when the session ends at 50-75% context budget instead of 95%. The packet generator runs cleanly before compression artifacts pollute the source state. Cheap to write while context is intact; expensive when the model is already losing its place.

Use it: the same idea with real libraries

Production patterns:

  • Session-end hook. The runtime fires the generator when the user closes the chat. The packet goes into outputs/handoff/<session_id>/.
  • PR template. The generator's markdown is also a PR body. Reviewers read it without opening five other files.
  • Cross-agent handoff. Build with one product (Claude Code), continue with another (Codex). The packet is the lingua franca.

The packet is small, regular, and cheap to produce. The cost saving compounds with every session.

Break it on purpose

Your overnight agent writes a friendly "progress summary" at the end of each session, and the morning session starts from it. Every few days the morning session redoes something the night session already tried and abandoned, and once it re-applied a migration that had been rolled back. Using this lesson, what is wrong with the handoff and what should replace it? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Progress files and git history are the usual handoff in long-running coding agents: Anthropic's harness has each session read a progress file and the git log before starting, and end by committing and updating the progress file.
  • Generated summaries from traces and checkpoints (LangGraph state, OpenAI Agents SDK sessions, Claude Agent SDK session resume) replace free-form recaps in many frameworks; free-text summaries remain for people.
  • Context compaction inside one session (summarising old turns) is the same problem at a smaller scale, and the same rule applies: keep failures, decisions and next steps verbatim, summarise the rest.
  • On your laptop: the generator is standard-library Python over JSON files.

Sources: Anthropic, Effective harnesses for long-running agents, Claude Agent SDK sessions.

Recap
What to keep from this lesson
  • Every session ends with a handoff; the next one starts from it.
  • Generate handoffs from records; free-text recaps drop the failures.
  • Failed attempts and a concrete next action are the load-bearing fields.
  • Keep a human-readable and a machine-readable form.
  • Leave a clean state: committed work, closed or explicit tasks.

Ship it

outputs/skill-handoff-generator.md produces a generator tuned to a project's artifact paths, an end-of-session hook that runs it, and a handoff.json schema the next agent reads on startup.

outputs/skill-handoff-generator.md

---
name: handoff-generator
description: Generate end-of-session handoff packets from workbench artifacts, producing both human-readable Markdown and machine-readable JSON keyed to the seven canonical fields.
version: 1.0.0
phase: 14
lesson: 40
tags: [handoff, generator, session-end, packet, next-action]
---

Given a workbench (state, verdict, review, feedback log, diff), produce a session-end handoff generator wired into the agent runtime.

Produce:

1. `tools/generate_handoff.py` exposing `generate_handoff(snapshot) -> (markdown, payload)`.
2. `outputs/handoff/<session_id>/handoff.md` and `handoff.json`.
3. `handoff.schema.json` covering the seven required fields and the feedback tail format.
4. Session-end hook script that runs the generator and refuses to close the session if any field is missing.
5. `docs/handoff.md` listing the seven fields, their sources, and the trimming policy.

Hard rejects:

- A handoff without a `next_action`. Status reports masquerading as handoffs poison the next session.
- A generator that hand-writes the summary. The agent's job is to leave the workbench in a generatable state.
- A markdown packet that diverges from the JSON. JSON is the source; markdown is a render of JSON.
- A feedback tail longer than 30 entries. The full log is in version control; the packet must stay small.

Refusal rules:

- If the verification report is missing, refuse to generate the packet. A handoff without a verdict is a wish.
- If the review report is missing and a human reviewer was expected, refuse and require the review pass first.
- If the diff summary is empty but the session ran longer than 5 minutes, surface the anomaly before generating; suspect a wedged session rather than a real no-op.

│   ├── handoff.md
│   └── handoff.json
├── tools/generate_handoff.py

Solutions

SolutionP1 · Any handoff beats none

Either handoff, against none: with no handoff session 2 repeats a known failure on all three tasks; with the model-written or the generated handoff it fixes two of three. The generated one is the one you can trust, because every line comes from the record, while the model's notes omitted every error that occurred.

SolutionB1 · A recap is not a record

The morning session starts from a recap written by the model, which keeps the narrative and drops what matters: abandoned approaches, rollbacks and why they happened. Nothing checks it against what really ran.

Replace it with a generated handoff built from the session's records: the commands run with exit codes, failed attempts with their errors, the verification and review verdicts, open blockers, state changes such as applied and rolled-back migrations, and one explicit next action; plus the git log. Keep the model's prose only as an optional summary for people. Have the morning session read the machine-readable handoff first, and make irreversible steps (migrations) check the current state before running.

Explain the mechanismAt the end of each session your agent writes a paragraph that says what it did. The next session still spends its first half hour finding out where things stand. What is missing from the end-of-session artifact, and how do you produce it so that it is never skipped?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. The paragraph is a status report, and a handoff needs seven fields: a summary, the changed files, the commands run, the failed attempts, the open risks, the next action and a pointer to the verification and review reports. The next action is the most important field, because it makes the first step of the next session deterministic. Generate the packet from the workbench artifacts instead of asking the agent to write it, and run a cleanup check first so that the packet describes a tree the next session can trust.

The seven fields.

Field Question it answers
summary What was done, in one paragraph
changed_files The diff at a glance
commands_run What was executed, from the feedback records
failed_attempts What was tried and why it did not work
open_risks What can hurt the next session, with a severity
next_action The first concrete step the next session takes
verdict_pointer The path to the verification and review reports

A packet with every field except next_action is a status report. It is useful, but the next session still has to decide what to do first.

Generated, not written.

A hand-written handoff is the thing that gets skipped on a hard day. The generator reads the state file, the verification report, the review report and the feedback log, and emits the packet in two forms. handoff.md is for the human. handoff.json is for the next agent. If they disagree, the JSON wins. The agent's job is to leave the workbench in a state the generator can summarize.

Trim the log.

The feedback log can hold hundreds of records. The packet carries only the last K plus every record with a non-zero exit. The next session loads the full log if it needs it.

Leave a clean state.

A perfect packet is useless if the next session opens on a half-applied diff, a stray temp file, a wrong branch and tests that error before they run. Cleanup is its own phase, and it is a check, not a habit. The working tree is committed or stashed with a note. No temp artifacts remain. Tests are green, or red with the failure named in the open risks. The feature board matches reality. The branch is the expected one. The cleanup phase emits a list of blocking issues, and an empty list is the precondition the generator asserts before it writes.

Plausible wrong answers.

  • "Ask the agent to write a detailed summary at the end." A written summary is skipped when the session ends badly, and it is the bad sessions that need the handoff most.
  • "The chat history is the handoff." The history is trimmed or gone, and the next session cannot replay an hour of chat in its first minute.
  • "A green verification report is enough to resume." The report proves the task state, not the tree state, and a dirty tree costs the next session its first ten minutes.

Follow-ups an interviewer may ask.

  • (level 1) Why does the JSON win when the two forms disagree? Expected: the next agent loads the JSON, so the machine-readable form is the one that drives the next session.
  • (level 2) Which failed attempts belong in the packet? Expected: every record with a non-zero exit, with the retry chain visible, so that the next session does not repeat a known dead end.
  • (level 2) What is the difference between a handoff and the state file? Expected: the state file is read on every turn and holds where the agent is, while the handoff is generated once at session end and tells the next session where to start.
  • (level 3) Two sessions on two branches each wrote a handoff. How does the next session pick one? Expected: each packet carries a branch, a last known good commit and a status of active, superseded or archived, and only the active packet for this branch drives the session.

Weigh a trade-offA long coding session has used most of its context window. The runtime offers to summarize the older turns and keep going. Your teammate wants to let it run to the limit, because compaction is automatic. When do you compact, when do you end the session, and what do you measure to choose?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Compaction extends a session, and a handoff closes one cleanly and starts the next in fresh context. Compaction is fine while the compressed history still carries what the task needs, but quality decays as compression stacks up. The lesson's guidance is to end the session with a generated handoff at 50 to 75 percent of the budget, not at the wall, because the packet is cheap to write while the context is intact and expensive when the model is already losing its place.

Two different operations.

Operation What it does What it costs
Compaction Compresses the history in place and continues the same session Each pass loses detail, and the losses stack up
Fresh-session handoff Writes a packet, ends the session, and resumes in a new context A clean break, with the cost of generating and loading the packet

Runtimes implement compaction in different ways: a server-side opaque summary, a local summary appended as a user message, a progressive multi-stage compression near the top of the window, or a timestamp-based hiding of old messages plus a short summary. The mechanism varies. The need is the same. Whatever survives compression must be serialized into a portable artifact, and that artifact is the handoff packet.

Why not run to the wall.

A runtime that compacts at 95 percent compacts a context that is already full of compression artifacts. The packet generator then summarizes degraded state. The mistake is to keep compressing until quality collapses. The fix is to budget for an early, clean handoff. A session that ends at 50 to 75 percent still has the intact history, the real command records and a clear next action.

Make the choice measurable.

  • Track the context fraction at which the session ends, and compare task outcomes across the two ranges.
  • Count how many times a session was compacted before it ended, and correlate with review findings.
  • Read the handoff packets: a packet with a vague next_action is a sign that the generator ran too late.

One active handoff per branch.

Multi-agent work breaks on stale handoffs more than on bad output. Each packet carries the branch, the last known good commit and a status of active, superseded or archived. Only the active packet drives the next session.

Plausible wrong answers.

  • "Compaction is automatic, so let the runtime handle it." Automatic compaction decides when to compress, not whether the compressed state is still good enough to work from.
  • "End every session as early as possible to be safe." Each handoff costs a packet and a reload, so the target is a range, not a minimum.
  • "A longer context window removes the problem." A larger window delays the wall, and the quality decay from stacked compression is the same.

Follow-ups an interviewer may ask.

  • (level 3) Why is a fresh session better than a third compaction? Expected: compression losses stack up, while a fresh session starts from the packet, the state file and the repo, which are the system of record.
  • (level 3) What must be true of the tree before the handoff runs? Expected: the cleanup check passes, so the tree is committed or stashed with a note, no temp files remain, tests are green or named as risks, and the branch is right.
  • (level 4) The handoff is cheap, but the next session has to rebuild its working context. How do you keep that cost down? Expected: the packet lists the exact artifacts the next session must load before it acts, and the router points at them, so the session loads the state, the board and the active contract and nothing else.
  • (level 4) Two coding agent products are used on one task, one after the other. What makes the transition work? Expected: the packet schema, because the JSON form is product-neutral and both runtimes read the same fields.
