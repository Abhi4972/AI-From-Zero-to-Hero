In plain words first
The idea in one line

Five metrics decide whether an inference deployment is working. TTFT is prefill plus queue plus network. TPOT (often reported as ITL, though tools disagree on whether ITL counts the first token) is the memory-bound decode cost per token. End-to-end latency is TTFT plus TPOT times output length. Throughput is tokens per second aggregated across the fleet. But the one that matters for product is goodput — the fraction of requests that met every SLO simultaneously. High throughput at low goodput means you are processing tokens that never reach users on time. Reference numbers for Llama-3.1-8B-Instruct on TRT-LLM in 2026: mean TTFT 162 ms, mean TPOT 7.33 ms, mean E2E 1,093 ms. Always report P50, P90, P99 — never just mean. And watch the measurement trap: GenAI-Perf excludes TTFT from ITL calculation, LLMPerf includes it; two tools disagree on TPOT for the same run.

Terms you'll hear
Term What people say What it actually means
TTFT "time to first token" Queue + network + prefill; dominated by prefill at long prompts
TPOT "time per output token" Memory-bound decode cost per token after first
ITL "inter-token latency" Same as TPOT in most tools (not all — see GenAI-Perf)
E2E "end to end" TTFT + TPOT * output_len; response-side network on top
Throughput "tok/s" Fleet efficiency; useless without latency percentiles
Goodput "SLO-met rate" Fraction of requests meeting every SLO constraint simultaneously
P99 "tail" 1-in-100 worst-case latency; the user experience metric
SLO multi-constraint "the joint" AND of all three latency bounds; a request fails if any one is violated
GenAI-Perf vs LLMPerf "the tool trap" Tools disagree on whether ITL includes TTFT

The problem

In plain words first

"How fast is the model?" has several answers, and each one hides different problems. TTFT (time to first token) is how long a user waits before anything appears; long prompts and queues make it worse. TPOT or ITL (time per output token, inter-token latency) is the gap between streamed tokens once they start. E2E latency is the whole request. Throughput is tokens per second across all users, which says the fleet is busy but not that anyone is happy. Goodput is the share of requests that met every target at once: first token fast enough, tokens steady enough, whole answer quick enough. Latency is uneven, so you describe it with percentiles: P50 is the typical request, P99 the slowest 1%, and P99 is what users remember.

"Our throughput is 15,000 tokens per second." So what? If 40% of requests blew past 2 seconds end-to-end, users abandoned the session. Throughput alone does not tell you whether the product works.

Inference has multiple axes of latency and each one fails differently. Prefill is compute-bound and scales with prompt length. Decode is memory-bound and scales with batch size. Queuing delay is an operational problem. Network is a physical-distance problem. You need distinct metrics for each, and you need percentiles, and you need a single composite that says "did the user get what they expected" — that is goodput.

Idea 1 · TTFT — time to first token

TTFT = queue_time + network_request + prefill_time

Prefill dominates when prompts are long. On Llama-3.3-70B FP8 on H100, a 32k prompt takes ~800 ms of pure prefill. Queue time is scheduler behavior under load. Network request is wire time including TLS. TTFT is the latency the user sees before anything streams back.

Idea 2 · TPOT / ITL — inter-token latency

Many names for one quantity. TPOT (time per output token), ITL (inter-token latency), decode latency per token — all the same. It is the time between consecutive streamed tokens after the first.

TPOT = (decode_forward_time + scheduler_overhead) / tokens_produced

On the same Llama-3.3-70B H100 stack with chunked prefill, TPOT mean ~7 ms. Without chunked prefill, during a long prefill on a neighboring sequence, TPOT can spike to 50 ms. Watch P99, not mean.

Idea 3 · E2E latency

E2E = TTFT + TPOT * output_tokens + network_response

For long outputs (>500 tokens), E2E is TPOT-dominated. For short outputs with long prompts, E2E is TTFT-dominated. Report output-length-conditioned E2E.

Idea 4 · Throughput

throughput = total_output_tokens / elapsed_time

Aggregate metric. Tells you fleet efficiency. Does not tell you individual-request health.

Idea 5 · Goodput — the metric you actually care about

goodput = fraction of requests meeting (TTFT <= a) AND (TPOT <= b) AND (E2E <= c)

The SLO is a multi-constraint. A request is "good" only if every constraint held. Goodput is the share. Some papers and dashboards report goodput as a rate instead: requests per second that meet every SLO. Multiply the share by the request rate to convert. High throughput at 60% goodput is failure. Lower throughput at 99% goodput is the target.

In 2026, goodput is the metric used in MLPerf Inference v6.0 submissions and in internal SLA tracking at AI platform providers.

Idea 6 · Why mean is the wrong statistic

LLM latency distributions are right-skewed. A decode batch with one long-prefill neighbor can ship 500 tokens with TPOT ~7 ms and 20 tokens with TPOT ~60 ms. Mean TPOT is 9 ms. P99 TPOT is 65 ms. Users hit the P99 regularly — that is why they leave.

Always report the triple (P50, P90, P99). For user experience, P99 is the one you optimize.

Idea 7 · Reference numbers — Llama-3.1-8B-Instruct on TRT-LLM, 2026

  • mean TTFT: 162 ms
  • mean TPOT: 7.33 ms
  • mean E2E: 1,093 ms
  • P99 TPOT: varies 10-25 ms depending on chunked-prefill configuration.

These are the published NVIDIA reference points. They change with model size (70B would show 3-5x), hardware (H100 vs B200 ~3x), and load.

Idea 8 · The measurement trap

Two of the most-used 2026 benchmark tools disagree on TPOT for the same run:

  • NVIDIA GenAI-Perf: excludes TTFT from the ITL calculation. ITL starts from token 2.
  • LLMPerf: includes TTFT. ITL starts from token 1.

For a request with TTFT 500 ms and 100 output tokens in 700 ms total decode, GenAI-Perf reports ITL = 700/99 = 7.07 ms, LLMPerf reports ITL = 1200/100 = 12.00 ms. Tool choice changes the number.

Always state which tool. Always publish the definition.

Idea 9 · Constructing an SLO

A reasonable consumer-facing SLO for a 70B chat model in 2026:

  • TTFT P99 <= 800 ms.
  • TPOT P99 <= 25 ms.
  • E2E P99 <= 3 s for <300-token outputs.
  • Goodput target >= 99%.

Enterprise SLOs tighten TTFT (200-400 ms) and loosen E2E. The point is to write them down, measure all three, and track goodput as a single composite.

Idea 10 · How to measure

  • Run real traffic or realistic synthetic (LLMPerf with --mean-input-tokens 800 --stddev-input-tokens 300 --mean-output-tokens 150).
  • Target 2x peak concurrency for the benchmark run.
  • Run 30-50 iterations, take percentiles of the combined sample.
  • Publish with tool name, tool version, model, hardware, concurrency, prompt distribution.

Worked example
One request, two tools

A request has TTFT = 500 ms, then 99 more tokens over 700 ms (100 output tokens, 1,200 ms in total).

  1. GenAI-Perf measures from the second token: ITL = 700 / 99 ≈ 7.07 ms.
  2. LLMPerf spreads the whole time over all tokens: 1,200 / 100 = 12.00 ms.
  3. Same request, 70% apart. A dashboard that switched tools would show a "regression" that never happened.
  4. Check E2E: 500 + 7.07 × 99 ≈ 1,200 ms. Both tools agree on E2E; they disagree on how to split it.

Part 1 of 3 · RequestTrace, synth_workload

"""Toy goodput calculator — stdlib Python.

Simulate a population of LLM requests with realistic right-skewed latency,
apply a multi-constraint SLO, compute goodput, and show the GenAI-Perf
vs LLMPerf TPOT calculation divergence on the same trace.
"""

from __future__ import annotations

import random
import statistics
from dataclasses import dataclass


@dataclass
class RequestTrace:
    queue_ms: float
    prefill_ms: float
    decode_ms_per_token: list[float]      # per-token decode latency
    output_tokens: int

    @property
    def ttft_ms(self) -> float:
        return self.queue_ms + self.prefill_ms

    @property
    def e2e_ms(self) -> float:
        return self.ttft_ms + sum(self.decode_ms_per_token)

    def tpot_llmperf(self) -> float:
        """LLMPerf: include TTFT in ITL calculation."""
        return self.e2e_ms / self.output_tokens

    def tpot_genaiperf(self) -> float:
        """GenAI-Perf: ITL starts from token 2."""
        if self.output_tokens <= 1:
            return 0.0
        return sum(self.decode_ms_per_token) / (self.output_tokens - 1)


def synth_workload(n: int = 1000, seed: int = 7, tail_spike_rate: float = 0.02) -> list[RequestTrace]:
    rng = random.Random(seed)
    traces = []
    for _ in range(n):
        prompt_len = rng.choice([128, 256, 512, 2048, 8192])
        output_tokens = rng.randint(50, 300)
        queue = rng.expovariate(1 / 40.0)           # avg 40 ms queue
        prefill = prompt_len * 0.05                 # ~50 us per input token
        decode_base = 7.0                            # 7 ms mean TPOT
        decodes = []
        for _ in range(output_tokens):
            t = max(1.5, rng.gauss(decode_base, decode_base * 0.15))
            if rng.random() < tail_spike_rate:
                t *= rng.uniform(3, 8)              # tail spike
            decodes.append(t)
        traces.append(RequestTrace(queue, prefill, decodes, output_tokens))
    return traces

Part 2 of 3 · percentiles, report_latency, goodput, main

def percentiles(values: list[float], ps: list[float]) -> list[float]:
    s = sorted(values)
    return [s[min(len(s) - 1, int(p * len(s)))] for p in ps]


def report_latency(label: str, traces: list[RequestTrace]) -> None:
    ttft = [t.ttft_ms for t in traces]
    tpot_llm = [t.tpot_llmperf() for t in traces]
    tpot_nv = [t.tpot_genaiperf() for t in traces]
    e2e = [t.e2e_ms for t in traces]

    p50_ttft, p90_ttft, p99_ttft = percentiles(ttft, [0.5, 0.9, 0.99])
    p50_tpot, p90_tpot, p99_tpot = percentiles(tpot_nv, [0.5, 0.9, 0.99])
    p50_e2e, p90_e2e, p99_e2e = percentiles(e2e, [0.5, 0.9, 0.99])

    print(f"{label}")
    print("-" * 76)
    print(f"  TTFT (ms)     P50={p50_ttft:7.1f}  P90={p90_ttft:7.1f}  P99={p99_ttft:7.1f}  mean={statistics.mean(ttft):7.1f}")
    print(f"  TPOT (ms)     P50={p50_tpot:7.2f}  P90={p90_tpot:7.2f}  P99={p99_tpot:7.2f}  mean={statistics.mean(tpot_nv):7.2f}")
    print(f"  E2E  (ms)     P50={p50_e2e:7.1f}  P90={p90_e2e:7.1f}  P99={p99_e2e:7.1f}")
    print(f"  Tool trap     GenAI-Perf mean TPOT={statistics.mean(tpot_nv):6.2f}  "
          f"LLMPerf mean TPOT={statistics.mean(tpot_llm):6.2f}  "
          f"delta={statistics.mean(tpot_llm) - statistics.mean(tpot_nv):+5.2f} ms")


def goodput(traces: list[RequestTrace], slo_ttft: float, slo_tpot: float,
            slo_e2e: float) -> float:
    good = 0
    for t in traces:
        if t.ttft_ms <= slo_ttft and t.tpot_genaiperf() <= slo_tpot and t.e2e_ms <= slo_e2e:
            good += 1
    return good / len(traces)


def main() -> None:
    print("=" * 78)
    print("TOY GOODPUT CALCULATOR: inference SLOs and the measurement trap")
    print("=" * 78)
    print()

    traces = synth_workload(n=2000)
    report_latency("Synthetic workload (2000 requests)", traces)
    print()

    slos = [
        ("loose   TTFT<800 TPOT<25 E2E<3000", 800, 25, 3000),
        ("target  TTFT<500 TPOT<15 E2E<2000", 500, 15, 2000),
        ("tight   TTFT<300 TPOT<10 E2E<1500", 300, 10, 1500),
    ]
    print("Goodput under three SLO profiles")
    print("-" * 76)
    for label, t1, t2, t3 in slos:
        g = goodput(traces, t1, t2, t3)
        tag = "  SHIPPABLE" if g >= 0.99 else ("  DEGRADED" if g >= 0.95 else "  FAILING")
        print(f"  {label}  goodput={g:6.2%}{tag}")

    print()
    print("=" * 78)
    print("KEY FINDING")
    print("-" * 78)
    print("  Mean TPOT ~7 ms looks great. P99 TPOT ~25-40 ms tells the real story.")
    print("  Tighten the SLO and goodput collapses from 99% -> 80%+. Users feel P99.")
    print("  GenAI-Perf vs LLMPerf disagree by ~1 ms on mean TPOT, cite the tool.")

What to keep from this lesson

You find where throughput stops rising, where the latency SLO breaks, what FP8 gives, and whether a smaller prefill chunk helps.

Task

Write five helper functions and answers().

  1. gains(ys) returns a float array of length $n - 1$. Entry $i$ is $y_{i+1} / y_i - 1$.
  2. saturation_point(xs, ys, min_gain=0.05) finds the first step $i$ with gain strictly below min_gain. It returns xs[i], the last level before that step. If no step has a gain below min_gain, it returns xs[-1].
  3. largest_within(xs, ys, limit) returns the largest x whose y is less than or equal to limit. If no y meets the limit, it returns None.
  4. pct_change(new, old) returns $100 \cdot (new - old) / old$.
  5. ranges_overlap(a, b) takes two dicts with the keys "min" and "max". It returns True when $a_{min} \le b_{max}$ and $b_{min} \le a_{max}$.

Then do the experiment in answers(). Use the helpers.

  1. Change the concurrency from 1 to 64 in LOAD["default"]. Measure output_throughput. Report the saturation point with min_gain = 0.05 as saturation_default.
  2. Do step 1 again for LOAD["fp8"]. Report saturation_fp8.
  3. In LOAD["default"], measure p99_ttft_ms at each concurrency. Report the largest concurrency with p99_ttft_ms within SLO["ttft_ms"] as slo_concurrency_default.
  4. In LOAD["default"], measure goodput_rps. Report the concurrency with the highest goodput as best_goodput_concurrency_default. If two levels have the same goodput, use the lower concurrency.
  5. At concurrency 32, divide the FP8 output_throughput by the default output_throughput. Report the ratio as fp8_speedup_c32.
  6. Change the prefill chunk from the default (4096 tokens) to 1024 tokens. Compare MIXED["chunk-1024"] with MIXED["default"] at the same rate. Use the "median" field. Report the mean over the three rates of pct_change in median_ttft_ms as chunk_ttft_change_pct. Report the same mean for output_throughput as chunk_throughput_change_pct. The new value is the chunk 1024 value. The old value is the default value.
  7. For each rate, test if the seed ranges of median_ttft_ms for the two settings overlap. Report the number of rates with an overlap as chunk_overlap_rates.

Your code
Common mistakes the checks catch
  • Compares the absolute difference of throughput with min_gain, not the relative gain.
  • Tests the SLO against the median TTFT, not the p99 TTFT.
  • Divides the change by the new value, not by the old value.
  • Returns the level after the low gain step, not the level before it.
  • Uses a strict less than, so a value equal to the limit fails the SLO.
  • Uses strict comparisons, so ranges that touch at one point do not overlap.
Hint 1

Convert ys to a numpy float array. The slice values[1:] holds each new value and the slice values[:-1] holds the value before it.

Hint 2

In saturation_point, step i goes from xs[i] to xs[i + 1]. When that step has a low gain, the useful level is xs[i], not xs[i + 1].

Hint 3

Use column(rows, key) from support.py to get one list for each metric. For the MIXED rows, read row["median_ttft_ms"]["median"] for the value and pass the whole inner dict to ranges_overlap.

Hint 4

The SLO question uses the p99 TTFT, not the median TTFT. Goodput counts the requests that meet the SLO, so its best level can be higher than the level where the p99 still meets the SLO.

Reference solution and notes
import numpy as np

from support import LOAD, MIXED, SLO, column


def gains(ys):
    values = np.asarray(ys, dtype=float)
    return values[1:] / values[:-1] - 1.0


def saturation_point(xs, ys, min_gain=0.05):
    steps = gains(ys)
    for i, gain in enumerate(steps):
        if gain < min_gain:
            return xs[i]
    return xs[-1]


def largest_within(xs, ys, limit):
    best = None
    for x, y in zip(xs, ys):
        if y <= limit and (best is None or x > best):
            best = x
    return best


def pct_change(new, old):
    return 100.0 * (new - old) / old


def ranges_overlap(a, b):
    return a["min"] <= b["max"] and b["min"] <= a["max"]


def answers():
    default = LOAD["default"]
    fp8 = LOAD["fp8"]
    xs = column(default, "concurrency")
    base = MIXED["default"]
    chunk = MIXED["chunk-1024"]
    goodput = column(default, "goodput_rps")
    ttft_changes = [pct_change(c["median_ttft_ms"]["median"], b["median_ttft_ms"]["median"]) for b, c in zip(base, chunk)]
    throughput_changes = [pct_change(c["output_throughput"]["median"], b["output_throughput"]["median"]) for b, c in zip(base, chunk)]
    return {
        "saturation_default": float(saturation_point(xs, column(default, "output_throughput"))),
        "saturation_fp8": float(saturation_point(column(fp8, "concurrency"), column(fp8, "output_throughput"))),
        "slo_concurrency_default": float(largest_within(xs, column(default, "p99_ttft_ms"), SLO["ttft_ms"])),
        "best_goodput_concurrency_default": float(xs[int(np.argmax(goodput))]),
        "fp8_speedup_c32": fp8[5]["output_throughput"] / default[5]["output_throughput"],
        "chunk_ttft_change_pct": float(np.mean(ttft_changes)),
        "chunk_throughput_change_pct": float(np.mean(throughput_changes)),
        "chunk_overlap_rates": float(sum(ranges_overlap(b["median_ttft_ms"], c["median_ttft_ms"]) for b, c in zip(base, chunk))),
    }

What the numbers say

The default model saturates at concurrency 32. From 32 to 64 the output throughput falls from 270.11 to 250.85 tokens per second. The median TTFT rises from 2,970 ms to 18,349 ms in the same step. The default KV pool has room for 24,094 tokens, so at 64 requests the scheduler cannot admit all of them and the queue grows.

The FP8 run does not saturate inside the sweep. FP8 weights and an FP8 KV cache leave room for 142,369 tokens, about six times the default pool. At concurrency 32 the FP8 run gives 1.88 times the throughput of the default run.

Throughput, the SLO and goodput are three different answers

The p99 TTFT meets the 1,000 ms SLO only up to concurrency 4. The goodput is highest at concurrency 16. The throughput saturates at 32. A capacity plan that uses only throughput picks a level where the goodput is 0. This is the point of the goodput lesson: report the share of requests that meet every SLO, not the token rate.

The chunk result is not a result

The 1024 token chunk changed the median TTFT by about 3 percent and the throughput by about minus 3 percent. The seed ranges overlap at all three rates. A change inside the seed spread is not a measured effect. On this card the workload was more than the GPU could serve, so the queue, not the chunk size, set the TTFT.

Where this goes next

The same reading applies to any sweep: a saturation rule, an SLO bound and a seed range check. The SGLang serving cheat sheet and the inference load testing lessons use these steps on other engines.

Given a workload (model, hardware, target concurrency, user-facing interaction type — streaming chat / one-shot / voice / agent), produce a goodput-based SLO gate for CI/CD.

Produce:

1. SLO spec. Three thresholds: TTFT P99 bound, TPOT P99 bound, E2E P99 bound. Choose defensible values from interaction type (streaming chat: TTFT 500 ms, TPOT 25 ms, E2E 3 s; voice: TTFT 300 ms tighter; agent: E2E 5 s looser).
2. Benchmark recipe. Tool choice (LLMPerf or GenAI-Perf — state the one you pick and why). Prompt distribution (mean + stddev of input and output tokens). Concurrency sweep (25%, 50%, 100%, 150% of target).
3. Goodput calculation. Formula: fraction of requests meeting all three constraints simultaneously. Target >= 99% for production, >= 95% for canary.
4. Percentile reporting. For every metric, report P50, P90, P99 (never mean alone). Annotate means only for sanity check.
5. Tool trap note. State whether the tool includes or excludes TTFT from ITL. Fix the definition before comparing across teams.
6. Gating logic. CI passes if goodput >= target AT target concurrency. Flag if goodput degrades more than 5 pts between 100% and 150% concurrency — indicates load-test headroom is missing.

Hard rejects:
- Gating on throughput alone. Refuse and require goodput.
- Reporting mean without P99. Refuse.
- Omitting tool name and tool version. Refuse.
- Benchmarking only at target concurrency; always do the sweep.

Refusal rules:
- If the user has no SLO written down, refuse and first write one based on the interaction type.
- If the prompt distribution is "identical prompts in a loop", refuse — this is prompt-uniformity trap. Require realistic synthetic.
- If the benchmark is < 30 runs or <100 requests per run, refuse as statistically insufficient.

Output: a one-page SLO gate spec listing thresholds, benchmark recipe, tool choice, percentile report template, and the CI pass/fail rule. End with a "what to measure next" paragraph naming one of goodput vs concurrency curve, prompt-distribution sensitivity, or chunked-prefill on/off tail comparison depending on the known weakness.

Solutions

SolutionP1 · Tightening the TPOT limit

In the visual above, tightening the TPOT limit from 30 to 15 ms changes nothing: the healthy 99% sit near 7 ms and the slow 1% near 63 ms, so goodput stays at 99% either way. In the script, the "target" profile tightens TTFT, TPOT and E2E together and goodput falls to about 76%, mostly from the TTFT and E2E limits. Tightening one limit only matters if requests sit between the old and new values.

SolutionB1 · Three mistakes

(1) 50 requests cannot give a meaningful P99: that is the single slowest request. Use thousands, over 30–50 runs. (2) Identical 100-token prompts hide the real mix: long prompts cause the prefill stalls users see. Use a realistic distribution of input and output lengths. (3) Production load is higher: benchmark at about twice peak concurrency. Also say which tool and which ITL definition the number uses.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismA teammate posts in the team channel that the server does 255 tokens per second. Is that a result? What would you ask for, and what single number tells you where to stop adding users?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. It is a slogan, not a result, because a throughput number without the latency that came with it describes nothing a user feels. Ask for the concurrency, the median and P99 first token and time per token at that concurrency, the client and the temperature, and the clock. Goodput is the number that sets the limit: the requests per second, or the share of requests, that met every latency target at once, and on the manual's GB10 the BF16 server's goodput was highest at a cap of 4 while its throughput kept rising to a cap of 64.

The same server, two loads.

The 255 came from the manual's own capture. The same server gave that throughput with a median time to first token of 0.8 s at one load and 3.9 s at another:

Cap Output tok/s Median TTFT P99 TTFT Median TPOT
1 175.15 162.98 ms 270.18 ms 4.38 ms
8 255.63 785.79 ms 2180.87 ms 22.52 ms
32 252.74 3917.54 ms 8262.86 ms 93.61 ms

From a cap of 8 to 32 the throughput fell about 1 percent, the median first token got 5 times slower, and the median time per token got 4.2 times slower. The server had no idle compute left to give; new users only waited for a share of the same steps.

Goodput.

Goodput is the share of requests, or the rate of requests per second, that met every latency bound at the same time: the first token under a limit, the time per token under a limit, and the end-to-end time under a limit. A request that misses any one of them is not good. The lesson's rule: high throughput at 60 percent goodput is failure, and lower throughput at 99 percent goodput is the target.

The manual's target was a first token under 1 s and a mean time per token under 100 ms. On the GB10 with Qwen3-30B-A3B:

Cap BF16 goodput BF16 median TPOT FP8 goodput FP8 median TPOT
4 0.44 req/s 71.01 ms 0.80 req/s 38.60 ms
8 0, up to 0.04 in one seed 102.21 ms 1.07 req/s 54.96 ms
16 0 154.24 ms 1.10 req/s 81.90 ms
32 0 201.91 ms 0 104.12 ms

BF16 goodput was highest at a cap of 4. At a cap of 8 the median request took longer than 100 ms per token, so at least half of the requests missed the target, and goodput was 0, up to 0.04 in one seed, while throughput at that cap was 74.11 tokens per second and still rising. FP8 held the target up to a cap of 16. Choose the cap from goodput at your own target, and use the throughput curve only to explain it.

Why the mean is the wrong statistic.

The lesson gives the shape: a decode batch with one long prefill neighbour can ship most tokens near 7 ms per token and a few near 60 ms, so the mean reads 9 ms while the P99 reads 65 ms, and users hit the P99 regularly. Report the median, the P90 and the P99 together. The tools also disagree on the definition: for a request with a 500 ms first token and 100 output tokens over 700 ms of decode, one tool that excludes the first token reports 7.07 ms per token and one that includes it reports 12.00 ms. State the tool and the definition with every number.

Where the knee is, and who enforces it.

A closed loop never falls behind, because each client waits for its answer before it sends the next request. A fixed arrival rate does not wait. Under a fixed rate the GB10 BF16 server already had a median time per token of 177.5 ms at 0.5 requests per second and met the target for only 0.07 requests per second, while FP8 met the target for every request up to 1 per second and fell to 0.17 at 2. Enforce the knee outside the engine, in the client or the gateway, because the engine's own admission limit comes from memory and sat at 4096 running requests on that server, far above the knee.

The floor behind one number.

The lesson shows where the time per token comes from on an L4: one decode step reads 16.41 GB of weights, which takes at least 54.7 ms at 300 GB/s, and the measured step took 60.16 ms. A target of 100 ms per token leaves little room on that card for an 8B model in BF16, which is why the pool and the precision matter before the scheduler does.

Plausible wrong answers.

  • "255 tokens per second is the capacity of the server." The same server gave that throughput with a median time to first token of 0.8 s at one load and 3.9 s at another; the number without its latency is not a result.
  • "Add users until throughput stops rising, then stop." On the GB10 the BF16 throughput kept rising to a cap of 64 while goodput was 0 or close to it from a cap of 8; the latency target, not the throughput curve, sets the limit.
  • "Report the mean time per token." The distribution is right-skewed, so a mean of 9 ms can hide a P99 of 65; report the median, P90 and P99.
  • "The engine's own admission limit protects the users." The engine's limit comes from memory, which runs out long after latency is unacceptable; enforce the knee in the client or the gateway.

Follow-ups an interviewer may ask.

  • (level 1) Which numbers go next to a throughput figure? Expected: the concurrency or request rate, and the median and P99 of the first token and of the time per token at that point, with the client, temperature and clock as context.
  • (level 2) Goodput fell to zero at a cap of 8 while throughput still rose. How can both be true? Expected: the server wrote more tokens per second, but the median request took longer than 100 ms per token, so at least half of the requests missed the target and almost none met every bound; throughput counts tokens and goodput counts requests that arrived on time.
  • (level 3) Why is the mean the wrong statistic for the time per token? Expected: the distribution has a long right tail; a batch with one long prefill neighbour can ship most tokens near 7 ms and a few near 60, so the mean reads 9 ms while the P99 reads 65, and users hit the P99 regularly.
  • (level 4) Two tools report different time per token for the same run. Why, and what do you do? Expected: one excludes the first token from the inter-token calculation and the other includes it, 7.07 against 12.00 ms in the lesson's example; state the tool and the definition with every number, and keep one tool for every run you compare.

Weigh a trade-offYou serve a chat model on one GPU. A load sweep shows output throughput that still rises at a cap of 64 concurrent requests, so the team wants to set the cap to 64. The product needs the first token in under one second and a steady stream of text after it. Which cap do you pick, and how do you defend it?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Pick the cap from goodput, not from throughput. Goodput counts only the requests that meet every latency target, so it falls to zero long before throughput stops rising. On the sweep in the SGLang manual, BF16 goodput was highest at a cap of 4 and was 0 from a cap of 8. Use the throughput curve only to explain the choice.

Why throughput hides the knee.

A large KV pool lets the server admit more requests. On the GB10 in the manual, the pool held 234,600 tokens, so BF16 throughput still rose at a cap of 64. More admitted requests share each decode step, so each request gets fewer tokens per second. Throughput measures the server. Latency measures the user.

Define the target first.

The manual counts a request as good when its first token comes in under 1 s and its mean time per token is under 100 ms. Write the target down before the sweep. A goodput number without its target means nothing.

Read the sweep.

Cap BF16 goodput BF16 median TPOT FP8 goodput FP8 median TPOT
4 0.44 req/s 71.01 ms 0.80 req/s 38.60 ms
8 0 102.21 ms 1.07 req/s 54.96 ms
16 0 154.24 ms 1.10 req/s 81.90 ms
32 0 201.91 ms 0 104.12 ms

At a cap of 8, the median BF16 request already takes more than 100 ms per token. Throughput at that cap is 74.11 tok/s and still rising. FP8 holds the target up to a cap of 16. So the answer depends on the build: about 4 for BF16 and about 16 for FP8 on this machine.

Defend it.

  • Run three seeds per point and show the band, so that a reviewer can see the gaps are real.
  • Reset the prefix cache before each run. A warm cache makes the first token look fast.
  • A cap is a closed loop. Real users arrive on their own clock, so also run an open-loop sweep with a request rate and check goodput there.

Plausible wrong answers.

  • "Set the cap where throughput peaks." The throughput curve had no peak inside the sweep, and every BF16 request missed the target from a cap of 8.
  • "Use the median TTFT alone." A median can hide a slow half of the requests, and the time per token can fail while the first token is fast.
  • "Report goodput from one run." One run can be wrong for reasons you never see, so use three seeds and report the range.

Follow-ups an interviewer may ask.

  • (level 2) What is the difference between throughput and goodput? Expected: throughput counts all tokens or requests per second; goodput counts only the requests that met every latency target.
  • (level 3) Why can a closed-loop cap never show a growing queue? Expected: each client waits for its answer before it sends the next request, so the server never receives more work than it finishes.
  • (level 3) FP8 holds the target at a cap of 16 and BF16 does not. What do you check before you switch the build? Expected: output quality on your own eval, and the KV pool size, because FP8 frees memory for a larger pool.
  • (level 4) The GPU gets hot at high load. How does that change your sweep? Expected: record the GPU clock and the thermal state with every run, and let the GPU cool to a fixed temperature before each run.
