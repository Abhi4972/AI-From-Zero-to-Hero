The idea in one line

Chat history is volatile. The repo is durable. The workbench stores agent state in versioned files so the next session, the next agent, and the next reviewer all read from the same source of truth.

The problem

In plain words first

Repo memory is the agent's state written into the repository: which task is active, which files it touched, what it assumed, what blocks it, what comes next. Two things keep that file trustworthy. A schema (JSON Schema) defines its shape, so a malformed write is refused instead of saved. An atomic write (write a temporary file, flush it to disk, then rename it over the old one) means a crash leaves either the old state or the new one, never half of each. Neither guarantees that the content is true. This lesson lets a small model write its own state updates and checks them both ways, then crashes a process in the middle of a write.

The agent finishes a session. The chat closes. The next session opens and asks where to start. The model says "let me check the files," reads stale notes, and re-does work that was already complete. Or worse, it rewrites a finished file because no one told it the file was finished.

The workbench fix is repo memory: state lives in JSON files in the repo, written under a schema, persisted atomically, diff-friendly in code review. Chat is a transient feed; the repo is the system of record.

The idea

Idea 1 · What belongs in repo memory

Belongs Does not belong
Active task id Raw chat transcripts
Touched files this session Token-level reasoning traces
Assumptions the agent made "The user seemed frustrated"
Open blockers Sampled completions
Next action Vendor-specific model ids

The test is durability: would this be useful three months from now in a CI rerun? If yes, repo. If no, telemetry.

Idea 2 · Schema-first state

JSON Schema is the contract. Without it, every agent invents new fields, every reviewer learns a new shape, and every CI script has to special-case past versions. With it, a bad write is a refused write.

The schema covers:

  • Required keys.
  • Allowed status values.
  • Forbidden values (e.g. null for arrays).
  • Pattern constraints (task ids match T-\d{3,}).
  • Version field for migrations.

Idea 3 · Atomic writes

State writes need to survive partial failures: write to a tempfile, fsync, rename over the target. The state file is the source of truth; a half-written one is worse than no file at all.

Idea 4 · Migrations

When the schema changes, ship a migration script next to the schema bump. The state file carries a schema_version field; the manager refuses to load a file from a version it cannot migrate.

The same idea as a formula

Three properties, three mechanisms. For a state update s′ after an event e:

valid shape: schemas′∈S​​true content: derived, not written by the models′=f(s,e)​​no torn writes: atomic renamedisk∈{s,s′}​​
A schema checks the first only. If the model writes s′ itself, the second can fail with a perfectly valid file. Atomicity is about the third: after a crash the file holds the old or the new state, never a mixture.

Torn writes. A plain write of b bytes interrupted after k<b bytes leaves a prefix of the new state, almost never valid JSON. With write-to-temp then rename, the rename is a single filesystem operation on the same disk, so readers see either version.

Worked example
When valid is not true
  • Start: T-007 active, app.py touched, next action "run the tests for T-007".
  • Event: "the tests for T-007 passed and T-007 is done". The model writes active_task_id: "T-007" and next_action: "done". The schema accepts it; the next session would still think T-007 is in progress.
  • Event: "also edited test_app.py". The model replaces the list with ["test_app.py"], dropping app.py. Valid, and now the reviewer will not look at app.py.
  • Across six events: 6 of 6 valid, 2 of 6 right. The fix is to have the harness apply events to the state with code (touched_files.append(...), active_task_id = None), and use the model only for free-text fields.

A model writes its own state

Qwen2.5-0.5B-Instruct (greedy, CPU) writes the new agent_state.json for six events. Each answer goes through the lesson's validate(..., STATE_SCHEMA), and a small check per event tests the content (task cleared when done, blocker recorded on failure, both files kept). About 1 minute.

# Who writes the state file? Agents are often told to "update agent_state.json" themselves. Here
# Qwen2.5-0.5B-Instruct (greedy, CPU) gets the current state, the field rules in plain words, and what
# happened this turn, and writes the new state. Each result goes through the lesson's schema validator
# (code/main.py: validate against STATE_SCHEMA), and a few facts are checked against what really happened.
import copy, json, os, re, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import STATE_SCHEMA, validate, SchemaError
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

START = {"schema_version": 1, "active_task_id": "T-007", "touched_files": ["app.py"], "assumptions": [],
         "blockers": [], "next_action": "run the tests for T-007"}
RULES = ("Fields: schema_version (always 1), active_task_id (like T-007, or null when no task is active), "
         "touched_files (list of paths), assumptions (list of strings), blockers (list of strings), next_action (string). "
         "No other fields.")
EVENTS = [  # (what happened, a check on the new state that must hold)
    ("The tests for T-007 passed and T-007 is done.", lambda s: s.get("active_task_id") is None),
    ("The tests failed: AssertionError in test_signup. Still working on T-007.", lambda s: s.get("active_task_id") == "T-007" and len(s.get("blockers", [])) >= 1),
    ("Also edited test_app.py while working on T-007.", lambda s: "test_app.py" in s.get("touched_files", []) and "app.py" in s.get("touched_files", [])),
    ("Assumed passwords must be at least 8 characters for T-007.", lambda s: any("8" in a for a in s.get("assumptions", []))),
    ("Switched to task T-012: add rate limiting.", lambda s: s.get("active_task_id") == "T-012"),
    ("Blocked on T-007: need the product owner to confirm the password rule.", lambda s: len(s.get("blockers", [])) >= 1),
]

def update(state, event):
    prompt = (f"Current agent_state.json:\n{json.dumps(state)}\n{RULES}\nThis turn: {event}\n"
              "Return the new agent_state.json as JSON only.")
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=160, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

RESULTS = []
print(f"{'this turn':<62}{'schema':<40}{'facts'}")
for event, fact in EVENTS:
    text = update(START, event)
    m = re.search(r"\{.*\}", text, re.S)
    try:
        new = json.loads(m.group()) if m else None
        validate(new, STATE_SCHEMA); schema = "valid"
    except (json.JSONDecodeError, TypeError) as e:
        new, schema = None, "not JSON"
    except SchemaError as e:
        schema = f"REJECTED: {str(e)[:36]}"
    ok = new is not None and fact(new)
    RESULTS.append((event, text, new, schema, ok))
    print(f"{event[:60]:<62}{schema:<40}{'right' if ok else 'WRONG'}")
print(f"\nvalid {sum(r[3] == 'valid' for r in RESULTS)}/6, facts right {sum(r[4] for r in RESULTS)}/6, "
      f"valid AND right {sum(r[3] == 'valid' and r[4] for r in RESULTS)}/6")

Reading this output

Every update is valid; most are wrong. All six answers pass the lesson's schema validator, but only two get the facts right. After "T-007 is done" the model keeps T-007 active and writes next_action: "done". After a test failure it records no blocker. After "also edited test_app.py" it replaces app.py with test_app.py instead of adding it. After the assumption about 8-character passwords, assumptions stays empty.

Even the passes are shaky. For the blocked task the model records the product-owner blocker, but also invents a "security_review" blocker and clears the active task. The content checks here are small; a real one would catch that too.

The schema did its job: it guarantees a shape every reader can rely on. It cannot know what happened this turn. Only the harness, which saw the event, can update those fields correctly.

A crash in the middle of a write

This block continues from the one above. A child process rewrites a valid state file and is killed partway: with a plain write after half the bytes, and with the lesson's atomic_write after the temp file is written and fsynced but before the rename. The parent then loads each file with the lesson's StateManager.

# A crash in the middle of a state write. A child process starts rewriting agent_state.json and dies halfway
# (os._exit, as on a kill -9 or power loss). Once with a plain write, once with the lesson's atomic_write
# (temp file, fsync, rename), where the child dies just before the rename. The parent then loads the file with
# the lesson's StateManager. Continues from the block above.
import pathlib, subprocess, sys, tempfile, textwrap
from main import StateManager

work = pathlib.Path(tempfile.mkdtemp())
CHILD = textwrap.dedent('''
    import json, os, sys
    sys.path.insert(0, sys.argv[3])
    path, mode = sys.argv[1], sys.argv[2]
    new = json.dumps({"schema_version": 1, "active_task_id": "T-008", "touched_files": ["api.py"] * 200,
                      "assumptions": [], "blockers": [], "next_action": "write tests for T-008"}, indent=2)
    if mode == "plain":
        f = open(path, "w"); f.write(new[: len(new) // 2]); f.flush()
        os._exit(1)                                    # dies with half the new state written
    import main
    real_replace = os.replace
    os.replace = lambda *a: os._exit(1)                # dies after writing and fsyncing the temp file, before the rename
    main.atomic_write(__import__("pathlib").Path(path), new)
''')
(work / "child.py").write_text(CHILD)
for mode in ("plain", "atomic"):
    state_path = work / f"{mode}_state.json"
    StateManager(state_path, STATE_SCHEMA).commit(START)          # a good state from the last turn
    code = subprocess.run([sys.executable, str(work / "child.py"), str(state_path), mode, os.getcwd()]).returncode
    try:
        loaded = StateManager(state_path, STATE_SCHEMA).load()
        result = f"loads fine: active_task_id={loaded['active_task_id']}, next_action={loaded['next_action']!r}"
    except (json.JSONDecodeError, SchemaError) as e:
        result = f"BROKEN: {type(e).__name__}: {str(e)[:60]}"
    leftovers = [p.name for p in work.iterdir() if p.name.startswith(state_path.name + ".")]
    print(f"{mode:<7} write, child exit code {code}: {result}")
    print(f"        {state_path.stat().st_size} bytes on disk; leftover temp files: {leftovers or 'none'}")

        1480 bytes on disk; leftover temp files: none

Reading this output

The plain write leaves a broken file. The child died after writing half of the new state: 1,480 bytes that end mid-string, so StateManager.load() raises JSONDecodeError. The previous, good state is gone too; the next session has nothing to resume from.

The atomic write leaves the old state intact. The child wrote and fsynced the whole new state to a temporary file, then died before the rename. The real file still holds the last good state (T-007, "run the tests for T-007"), which loads and validates. The cost is a leftover temp file (atomic_state.json. plus a random suffix), which a startup sweep should delete.

"""Schema-first agent state with atomic writes.

Writes JSON Schema files for `agent_state.json` and `task_board.json`,
implements a tiny stdlib validator that handles the subset we need
(required, type, enum, pattern, items), and a StateManager with
temp-and-rename writes so a partial failure cannot corrupt the file.

Run: python3 code/main.py
"""

from __future__ import annotations

import json
import os
import re
import tempfile
from pathlib import Path
from typing import Any

HERE = Path(__file__).parent
WORK = HERE / "workdir"


STATE_SCHEMA: dict[str, Any] = {
    "$id": "agent_state.schema.json",
    "type": "object",
    "required": ["schema_version", "active_task_id", "touched_files", "next_action"],
    "properties": {
        "schema_version": {"type": "integer", "enum": [1]},
        "active_task_id": {"type": ["string", "null"], "pattern": r"^(T-\d{3,}|)$"},
        "touched_files": {"type": "array", "items": {"type": "string"}},
        "assumptions": {"type": "array", "items": {"type": "string"}},
        "blockers": {"type": "array", "items": {"type": "string"}},
        "next_action": {"type": "string"},
    },
}


BOARD_SCHEMA: dict[str, Any] = {
    "$id": "task_board.schema.json",
    "type": "array",
    "items": {
        "type": "object",
        "required": ["id", "goal", "owner", "acceptance", "status"],
        "properties": {
            "id": {"type": "string", "pattern": r"^T-\d{3,}$"},
            "goal": {"type": "string"},
            "owner": {"type": "string", "enum": ["builder", "reviewer", "human"]},
            "acceptance": {"type": "array", "items": {"type": "string"}},
            "status": {"type": "string", "enum": ["todo", "in_progress", "done", "blocked"]},
        },
    },
}


class SchemaError(Exception):
    pass


def _check_type(value: Any, types: str | list[str]) -> bool:
    type_list = [types] if isinstance(types, str) else types
    for t in type_list:
        if t == "object" and isinstance(value, dict):
            return True
        if t == "array" and isinstance(value, list):
            return True
        if t == "string" and isinstance(value, str):
            return True
        if t == "integer" and isinstance(value, int) and not isinstance(value, bool):
            return True
        if t == "null" and value is None:
            return True
    return False

Part 2 of 4 · validate, atomic_write, StateManager

def validate(value: Any, schema: dict[str, Any], path: str = "$") -> None:
    if "type" in schema and not _check_type(value, schema["type"]):
        raise SchemaError(f"{path}: expected {schema['type']}, got {type(value).__name__}")
    if "enum" in schema and value not in schema["enum"]:
        raise SchemaError(f"{path}: {value!r} not in {schema['enum']}")
    if "pattern" in schema and isinstance(value, str) and not re.match(schema["pattern"], value):
        raise SchemaError(f"{path}: {value!r} does not match /{schema['pattern']}/")
    if isinstance(value, dict):
        for key in schema.get("required", []):
            if key not in value:
                raise SchemaError(f"{path}: missing required field {key!r}")
        properties = schema.get("properties", {})
        unexpected = sorted(set(value.keys()) - set(properties.keys()))
        if unexpected:
            raise SchemaError(f"{path}: unexpected fields {unexpected}")
        for key, sub in properties.items():
            if key in value:
                validate(value[key], sub, f"{path}.{key}")
    if isinstance(value, list) and "items" in schema:
        for idx, item in enumerate(value):
            validate(item, schema["items"], f"{path}[{idx}]")


def atomic_write(path: Path, content: str) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    fd, tmp_name = tempfile.mkstemp(prefix=path.name + ".", dir=path.parent)
    try:
        with os.fdopen(fd, "w") as fh:
            fh.write(content)
            fh.flush()
            os.fsync(fh.fileno())
        os.replace(tmp_name, path)
    except Exception:
        Path(tmp_name).unlink(missing_ok=True)
        raise


class StateManager:
    def __init__(self, state_path: Path, schema: dict[str, Any]):
        self.state_path = state_path
        self.schema = schema

    def load(self) -> Any:
        raw = json.loads(self.state_path.read_text())
        validate(raw, self.schema)
        return raw

    def commit(self, state: Any) -> None:
        validate(state, self.schema)
        atomic_write(self.state_path, json.dumps(state, indent=2) + "\n")

def main() -> None:
    WORK.mkdir(exist_ok=True)
    schema_dir = WORK / "schemas"
    schema_dir.mkdir(exist_ok=True)
    (schema_dir / "agent_state.schema.json").write_text(json.dumps(STATE_SCHEMA, indent=2) + "\n")
    (schema_dir / "task_board.schema.json").write_text(json.dumps(BOARD_SCHEMA, indent=2) + "\n")

    state_path = WORK / "agent_state.json"
    board_path = WORK / "task_board.json"

    mgr = StateManager(state_path, STATE_SCHEMA)
    board_mgr = StateManager(board_path, BOARD_SCHEMA)

    initial_state = {
        "schema_version": 1,
        "active_task_id": None,
        "touched_files": [],
        "assumptions": [],
        "blockers": [],
        "next_action": "pick next task",
    }
    initial_board = [
        {
            "id": "T-001",
            "goal": "validate /signup payloads",
            "owner": "builder",
            "acceptance": ["pytest -x test_app.py::test_signup_rejects_short_password"],
            "status": "todo",
        }
    ]
    mgr.commit(initial_state)
    board_mgr.commit(initial_board)

    state = mgr.load()
    board = board_mgr.load()
    state["active_task_id"] = board[0]["id"]
    state["next_action"] = "read existing /signup handler"
    mgr.commit(state)

    print("state:", json.dumps(mgr.load(), indent=2))
    print("board:", json.dumps(board_mgr.load(), indent=2))

    bad = dict(state)
    bad["active_task_id"] = "T-bogus"
    try:
        mgr.commit(bad)
    except SchemaError as exc:
        print("rejected bad write:", exc)

Production patterns in the wild

Four patterns turn the lesson's minimum into something a multi-agent monorepo can survive.

Atomic temp-and-rename is not optional. A March 2026 Hive project bug report documents the failure mode cleanly: state.json was written via write_text() and exceptions were caught and silenced. Partial writes left sessions resuming against corrupt state with no signal. The fix is always: tempfile.mkstemp in the same directory as the target, write, fsync, os.replace (atomic rename on POSIX and Windows). This lesson's atomic_write does exactly that.

Idempotency keys on every non-idempotent tool call. If an agent crashes after calling a tool but before checkpointing the result, recovery retries the tool call. Safe for reads; dangerous for emails, DB inserts, file uploads. The pattern: log every tool call ID before execution into a pending_calls.jsonl. On retry, check for the ID; if present, skip the call and use the cached result. Anthropic and LangChain both call this out in 2026 guidance; LangGraph's checkpointer persists pending writes for the same reason.

Separate large artifacts from state. Don't store CSVs, long transcripts, or generated files in agent_state.json. Save the artifact as a separate file (or upload to object storage) and keep only the path in state. Checkpoints stay small and fast; the artifacts grow independently.

Event sourcing for audit, snapshots for resume. Append to an event log (state.events.jsonl) on every mutation; periodically snapshot to state.json. Resume reads the snapshot, then replays any events after the snapshot's timestamp. This costs more disk but lets you replay agent decisions verbatim — essential when debugging long-horizon runs. Postgres uses the same log plus checkpoint idea at the storage layer with its WAL, though at a much lower level than application events.

Schema migrations or refuse to load. The schema_version integer is the contract. When the manager loads a file at an unknown version, it refuses to read. Ship a migration script next to the schema bump; tools/migrate_state.py runs idempotently on every startup.

Use it: the same idea with real libraries

In production:

  • LangGraph checkpointers. Same idea, different storage. The checkpointer persists graph state to SQLite, Postgres, or a custom backend. The schema this lesson teaches is what you reach for when the checkpointer dies and you need to read state by hand.
  • Letta memory blocks. Persistent blocks with structured schemas (Phase 14 · 08). Same discipline scoped to long-running personas.
  • OpenAI Agents SDK session store. Pluggable backends, schema-aware. The state file in this lesson is the local-file backend.
Break it on purpose

An agent framework stores each session's state in state.json and lets the model rewrite the whole file after every turn. Users report agents that "forget" files they edited and reopen finished tasks, but the state always passes schema validation. Using this lesson, explain and redesign the update path. (Solution B1.)

Industry practice
What's current (2024–2026)
  • Checkpointers in agent frameworks (LangGraph's SQLite and Postgres savers, lesson 14.13; Temporal histories; OpenAI Agents SDK sessions) store state as structured records written by code, with the model's messages as one field among many.
  • Schema validation with JSON Schema or Pydantic is standard at state boundaries; structured outputs from model APIs reduce invalid JSON but do not make content correct.
  • Atomic file updates (temp file, fsync, os.replace) are the standard recipe for single-writer files; databases (SQLite in WAL mode) are the usual step up when several processes write.
  • On your laptop: everything here is CPU-only and runs in a temp folder.

Sources: JSON Schema, Python os.replace, SQLite write-ahead logging, LangGraph persistence.

Recap
What to keep from this lesson
  • State holds durable facts: task, files, assumptions, blockers, next action.
  • A schema refuses malformed state; it cannot spot false state.
  • Derive structured fields from events in code.
  • Write atomically: temp file, fsync, rename.
  • Sweep leftover temp files and migrate old versions on startup.

Given a repo and the agent product running inside it, produce schema-first state files for the workbench.

Produce:

1. `schemas/agent_state.schema.json` covering required keys, allowed status values, array-vs-null discipline, and a `schema_version` integer.
2. `schemas/task_board.schema.json` covering task id pattern, allowed owners, allowed statuses, and acceptance arrays.
3. `tools/state_manager.py` exposing `load`, `commit`, and `update` with temp-and-rename atomic writes.
4. `tools/migrate_state.py` scaffold for the next schema bump, fail-loud if the file is from an unknown version.
5. `agent_state.json` and `task_board.json` seeded at `schema_version: 1` and a fresh backlog.

Hard rejects:

- A schema without a `schema_version` field. Migrations are not optional.
- Allowing `null` where an array is expected. `null` is a write-time bug masquerading as data.
- A writer that uses plain `open(path, "w")`. Atomic writes only; partial files corrupt the source of truth.
- Storing tokens, raw chat transcripts, or PII inside state. State is for repo-relevant facts.

Refusal rules:

- If the repo has no version control, refuse to ship state files. Atomic writes plus git diff is the durability story.
- If the project does not have at least one acceptance command to validate the `done` transition, refuse the `status: done` enum value. Adding `done` without an acceptance check is theater.
- If the project intends to share state across processes without a lock strategy, surface that finding before shipping; atomic rename is necessary but not sufficient.

Output structure:

```
<repo>/
├── agent_state.json
├── task_board.json
├── schemas/
│   ├── agent_state.schema.json
│   └── task_board.schema.json
└── tools/
    ├── state_manager.py
    └── migrate_state.py
```

Exercises

  1. Add a last_human_touch timestamp. Refuse any agent write within five seconds of a human edit.
  2. Extend the validator to support oneOf so a task can be either a build task or a review task with different required fields.
  3. Add a schema_version field and write the migration from v1 to v2 (rename blockers to risks).
  4. Move the storage backend from a local file to SQLite. Keep the StateManager API identical.
  5. Run two agents against the same state file with a 50 ms write race. What goes wrong and how does the atomic rename save you?

Solutions

SolutionP1 · Six valid, two right

All six are valid and two are right. The schema accepts every answer, but the model keeps a finished task active, drops a touched file, and forgets to record a failure and an assumption. Validity is about shape; whether the state is true depends on who writes it, and here it was written from a one-sentence summary by a small model.

SolutionB1 · Valid, wrong and model-written

The model is rewriting structured facts from memory each turn, so it drops entries (touched files), forgets transitions (tasks marked done) and invents others, while keeping the JSON shape valid. Schema validation cannot catch any of it.

Redesign: treat state as the result of events. The harness records events it observes (file written, test run with exit code, task closed by the verification gate) and applies them in code: append to touched_files, set active_task_id to null on a verified close, append failures to blockers. The model may propose free-text fields (assumptions, next action), which are validated and stored, but never the structured ones. Keep an append-only event log so state can be rebuilt or audited, write state atomically, and add invariant checks (a done task cannot be active; touched files only grow within a task).

Read the codeAn agent workbench persists its state between sessions with this code. Review it. What can go wrong, what does the lesson's writer do instead, and what else belongs around the write? python def save_state(path, state): try: path.write_text(json.dumps(state)) except Exception: return

Level 4 of 4 · about 12 minutes to answer well.

Short answer. Two faults. A crash in the middle of the write leaves a truncated file that the next session loads as corrupt state, and the silent except hides it, so the agent resumes against garbage with no signal. The lesson's writer creates a temp file in the same directory, writes, syncs to disk and renames over the target, so the file on disk is either the old version or the new one. Around it belong a schema check that refuses a bad state before it is written, a version field with a migration path, and idempotency keys for tool calls that are not safe to repeat.

The two bugs.

The lesson points at a bug report from an open-source project in March 2026 with this exact shape: the state file was written with a plain text write and exceptions were caught and silenced. Partial writes left sessions resuming against corrupt state with no signal. The first bug is the non-atomic write. The second is the except clause that turns a loud failure into a quiet one.

The atomic writer.

  1. Create a temp file with tempfile.mkstemp beside the target, inside its directory.
  2. Write the content.
  3. fsync so the bytes reach the disk.
  4. os.replace the temp file over the target, which is an atomic rename on POSIX and on Windows.

A reader sees the old file or the new file, never a mix.

Schema first.

The state file carries a contract: required keys, an enum of allowed status values, forbidden values such as null for an array, a pattern for task ids, and a schema_version integer. The manager validates before it writes, so a bad write is a refused write, and it refuses to load a file at a version it cannot migrate. A migration script ships with every schema bump and runs idempotently on startup.

Around the write.

  • Idempotency keys. If a crash lands between a tool call and its checkpoint, recovery retries the call. Fine for a read; dangerous for an email or a database insert. Log a started record with the call id before execution and a completed record with the result after it. On retry, a call with a completed record is skipped and its stored result is used. A call with only a started record may or may not have run, so reconcile it first, for example by asking the target system whether that idempotency key was applied, before you repeat or skip it.
  • Small state, separate artifacts. Transcripts, generated files and data sets live in their own files or in object storage; the state holds only the paths.
  • Event log plus snapshot. Append every mutation to an event log and snapshot the state on a schedule; resume reads the snapshot and replays later events, which also lets you replay agent decisions when debugging.

What belongs in the file.

The active task id, the files touched this session, the assumptions made, open blockers and the next action. Not raw transcripts, reasoning traces, sampled completions or vendor model ids. The test is whether the entry would be useful three months from now in a CI rerun.

Plausible wrong answers.

  • "Catch the exception and keep going, the next write will fix it." The silent except is the second bug; it hides a truncated file that the next session loads.
  • "Write to a temp file, then copy it over the target." A copy can be interrupted too; the atomic step is the rename.
  • "Store the full transcript in the state so nothing is lost." Transcripts are telemetry, not durable state; keep the file small and keep artifacts in separate files with only their paths in state.

Follow-ups an interviewer may ask.

  • (level 3) Why does the temp file live in the same directory as the target? Expected: so the final step is a rename on the same filesystem and stays atomic; the lesson's recipe is a temp file beside the target, write, sync, replace.
  • (level 4) An agent crashes after a tool call and before the checkpoint. What goes wrong on recovery, and what fixes it? Expected: the call is retried, which is dangerous for an email or an insert; log a started record with the call id before execution and a completed record with the result after it; reuse the result of a completed call, and reconcile a call that has only a started record before you repeat it.
  • (level 4) Two agents write the same state file within 50 ms. What does the atomic rename save, and what does it not? Expected: it prevents a torn file, so each reader sees one complete version; it does not stop the second write from replacing the first, which needs coordination between the writers.
  • (level 4) What belongs in the state file and what does not? Expected: the active task, touched files, assumptions, blockers and the next action; not transcripts, reasoning traces, completions or vendor model ids, and large artifacts only by path.
