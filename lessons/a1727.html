In plain words first
The idea in one line

Traditional FinOps breaks on LLM spend. Costs are token-transactions, not resource-uptime. Tags don't map — an API call is a transaction, not an asset. Engineering decisions (prompt design, context window, output length) are financial decisions. The 2026 playbook has three attribution dimensions to instrument on day one: per-user (user_id) for seat pricing and expansion, per-task (task_id + route) for product surface cost and prioritization, per-tenant (tenant_id) for unit economics and renewal. The problem

In plain words first

FinOps is the practice of knowing who spends what in the cloud and keeping it under control. LLM calls make that hard: the provider's bill shows tokens and dollars, not which customer, feature or user caused them. So you attribute cost yourself: every call carries a user ID, a task or route name and a tenant (customer) ID, and you join those tags to the token counts. It also helps to split tokens into layers: the prompt you wrote, tool results fed back in, conversation memory, and the model's answer, because each is fixed in a different way. Then you enforce: rate limits per tenant, daily spend caps, and an automatic kill switch when a tenant's spend is wildly above its normal level. Finally, you judge cost per outcome (per resolved ticket, per completed task), not per million tokens.

Your bill says $40,000. You don't know: - Which tenant spent it. - Which product feature drove it. - Whether any individual user was abusive. - Whether prompt bloat, tool calls, or memory amplification was the culprit.

Tag-and-aggregate on provider-side works for cloud resources (EC2, S3) where tags propagate to line items. LLM API calls do not auto-tag — you have to stamp user/task/tenant at the call site and carry through. Retroactive attribution always misses edge cases.

Idea 1 · Three attribution dimensions

Per-user (user_id): who is costing what. Drives seat pricing, expansion conversations, identifies power users.

Per-task (task_id + route): which product surface costs what. Drives feature prioritization, kill-expensive-features decisions.

Per-tenant (tenant_id): which customer is profitable. Drives unit economics, renewal pricing, tier thresholds.

Instrument all three at call site on day one. Retroactive is always worse.

Idea 2 · Four token layers

Layer Example Typical % of total
Prompt system + user input 40-60%
Tool tool-call results fed back 20-40% (agent workloads)
Memory prior conversation / retrieved docs 10-30%
Response model output 10-30%

Bucketing all four together makes optimization blind. Break them out in your attribution schema.

Idea 3 · Enforcement ladder

  1. Rate limit per tenant. 2-3x expected peak. Return 429 with Retry-After. Tenant sees friction; no surprise bill.

  2. Daily spend cap per tenant. 1.5-3x contracted ceiling. Trigger: tighten rate limit + alert customer-success.

  3. Kill switch on spend z-score > 4 relative to tenant baseline. Auto-pause tenant; page on-call; escalate to ops + CS.

Idea 4 · Attribution patterns

  • Tag-and-aggregate: stamp metadata headers; aggregate later. Simple; rough.
  • Telemetry joiner: join traces to billing via trace IDs. Highest accuracy. What mature teams do.
  • Sampling + extrapolation: sample 5-10%, multiply. Cost-effective for rough spend; misses tails.
  • Model-based allocation: regression to infer cost driver. For legacy data without tags.
  • Event-sourced: cost as events in a stream (Kafka / Kinesis). Real-time.
  • Real-time streaming: dashboard updates sub-second.

Idea 5 · Cost per X is the unit metric

$/M tokens is vendor speak. Product metrics:

  • Cost per resolved support ticket.
  • Cost per generated article.
  • Cost per successful agent task.
  • Cost per user-session-minute.

Tie cost to a product outcome. Otherwise optimization is unanchored.

Idea 7 · The compounded-savings stack

Stack: cache + batch + route + gateway. With all four: - Cache L2 (Phase 17 · 14): ~10x cheaper input. - Batch (Phase 17 · 15): 50% off. - Route to cheap model (Phase 17 · 16): 60% cost reduction. - Gateway efficiency (Phase 17 · 19): redundancy + retries.

Best-case stacked: ~5-10% of naive baseline. Most teams have 2-3 levers engaged; few stack all four.

Idea 8 · Numbers you should remember

  • Attribution dimensions: per-user, per-task, per-tenant.
  • Four token layers: prompt, tool, memory, response.
  • Kill switch: spend z-score > 4.
  • Unit metric: cost per resolved query, not $/M tokens.
  • Stacked optimizations: ~5-10% of baseline possible.

The same idea as a formula

Spend anomaly score. For a tenant with daily spend history mean μ and standard deviation σ, today's spend x gives

z=σx−μ​

A kill switch at z>4 fires on spend far outside the tenant's own normal range, rather than on an absolute dollar figure that suits one tenant and not another.

Worked example
Cost per resolved ticket

A support assistant spent $12,000 last month on 300,000 conversations; 180,000 ended with the ticket resolved without a human.

  1. Cost per conversation: $12,000 / 300,000 = $0.04.
  2. Cost per resolved ticket: $12,000 / 180,000 ≈ $0.067.
  3. A cheaper model cuts spend to $7,000 but resolution drops to 120,000: cost per resolved ticket ≈ $0.058, slightly better, but 60,000 more tickets now reach human agents, each costing far more than $0.07.
  4. The unit metric (cost per resolved ticket, plus the human cost of escalations) shows the "cheaper" model costs more overall. Token prices alone would have hidden that.
Check your mental model

Which statements are right?

  • ✓ LLM API calls do not carry your tags; you stamp them at the call site.
  • ✗ Cost per million tokens is the metric to optimize. Tie cost to an outcome (per ticket, per task), or optimization has no anchor.
  • ✓ In agent workloads, tool results fed back can be 20–40% of tokens.
  • ✗ A single global spend cap protects every tenant fairly. Caps and anomaly thresholds should follow each tenant's contract and baseline.

A z-score kill switch
import statistics
history = [14.2, 15.8, 13.1, 16.4, 15.0, 19.6, 12.7, 14.9, 16.1, 13.8, 21.0, 11.5, 15.3, 14.6]
mu, sd = statistics.mean(history), statistics.stdev(history)
print(f"baseline: mean ${mu:.2f}, sd ${sd:.2f}")
for today in (25, 31, 40, 120):
    z = (today - mu) / sd
    action = "KILL SWITCH: pause tenant, page on-call" if z > 4 else ("alert customer success" if z > 2.5 else "ok")
    print(f"today ${today:6.2f}: z = {z:5.1f} -> {action}")

Reading this output

With this tenant's spread (about $2.50), $25 is already well outside its normal range and $31 would trip a z > 4 kill switch. A flat cap of, say, $100 a day would not have fired until something far worse. Thresholds relative to each tenant's own baseline catch abuse early without punishing big customers whose normal spend is high.

Part 1 of 3 · TenantPolicy, TenantState, simulate_day

"""Multi-tenant LLM FinOps simulator with enforcement ladder — stdlib Python.

Three-tier enforcement:
  1. rate limit per tenant
  2. daily spend cap per tenant
  3. kill switch on spend z-score > 4
"""

from __future__ import annotations

from dataclasses import dataclass, field
import random
import statistics


@dataclass
class TenantPolicy:
    contracted_daily_usd: float
    rate_limit_per_min: int
    spend_cap_multiplier: float = 2.0
    kill_z_score: float = 4.0


@dataclass
class TenantState:
    spend_today_usd: float = 0.0
    minute_count: int = 0
    daily_history: list = field(default_factory=list)
    paused: bool = False


TENANTS = {
    "tenant_A_normal":  (TenantPolicy(100.0, rate_limit_per_min=120), TenantState(), 1.0),
    "tenant_B_growing": (TenantPolicy(50.0,  rate_limit_per_min=60),  TenantState(), 2.5),
    "tenant_C_abusive": (TenantPolicy(20.0,  rate_limit_per_min=40),  TenantState(), 25.0),
}


def simulate_day(day: int, verbose: bool) -> None:
    for name, (policy, state, traffic_mult) in TENANTS.items():
        if state.paused:
            continue
        requests = int(100 * traffic_mult * random.uniform(0.8, 1.3))
        tokens_per_req = int(random.gauss(600, 150))
        cost_per_req = (tokens_per_req / 1e6) * 10.0
        total_spend = requests * cost_per_req
        state.spend_today_usd += total_spend

        if state.spend_today_usd > policy.contracted_daily_usd * policy.spend_cap_multiplier:
            if verbose:
                print(f"  [cap breach] {name}: ${state.spend_today_usd:.2f} > cap ${policy.contracted_daily_usd * policy.spend_cap_multiplier:.2f} → tighten rate + alert CS")

        if len(state.daily_history) >= 5:
            mean = statistics.mean(state.daily_history)
            sd = statistics.stdev(state.daily_history) or 1
            z = (state.spend_today_usd - mean) / sd
            if z > policy.kill_z_score:
                state.paused = True
                if verbose:
                    print(f"  [KILL SWITCH] {name}: z={z:.2f} on spend ${state.spend_today_usd:.2f} (baseline ${mean:.2f} ± ${sd:.2f}) → auto-pause + page on-call")

Part 2 of 3 · main

def main() -> None:
    print("=" * 95)
    print("FINOPS ENFORCEMENT: three tenants over 10 days, abusive tenant triggers kill switch")
    print("=" * 95)
    random.seed(7)

    for day in range(1, 11):
        print(f"\nDay {day}:")
        simulate_day(day, verbose=True)
        for name, (policy, state, _) in TENANTS.items():
            status = "PAUSED" if state.paused else "active"
            print(f"  {name}: spend=${state.spend_today_usd:7.2f}, contract=${policy.contracted_daily_usd:.2f}  [{status}]")
            state.daily_history.append(state.spend_today_usd)
            if not state.paused:
                state.spend_today_usd = 0.0
    print("\nRead: rate limits throttle; caps trigger alerts; kill switch catches blow-ups.")

Solutions

SolutionB1 · Untagged spend

Without tags they can only describe the spend by model and by time of day, and guess. Some reconstruction is possible by joining call timestamps to application logs, but it will be rough. Today: add tenant_id, user_id, task_id and route to every call (headers through the gateway, or span attributes), and break token counts into prompt, tool, memory and response. Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismFinance asks for the cost per million tokens as the key metric for the model service. You push back. What metric do you propose instead, and what must every call record so that you can compute it?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. Propose a cost per product outcome: per resolved ticket, per generated article, per successful agent task or per session minute. A price per million tokens is the vendor's unit, and it says nothing about whether the spend produced anything. To compute the outcome metric, stamp every call at creation with the user id, the task id with its route, and the tenant id, split the tokens into prompt, tool, memory and response, and join the cost to the outcome event.

Why the token price misleads.

A cheaper model that needs twice the tokens per task costs more per task. A prompt change that cuts tokens and lowers the resolution rate raises the cost per resolved ticket while the token dashboard goes green. The lesson's rule is to tie cost to a product outcome, because an optimization without that anchor has no direction.

Three attribution dimensions.

Dimension Key What it answers
per user user_id who costs what, for seat pricing and abuse
per task task_id and route which product surface costs what
per tenant tenant_id which customer is profitable

Instrument all three at the call site on day one. A provider line item carries none of them, and retroactive tagging always misses cases.

Four token layers.

Layer Typical share
prompt, the system text and the user input 40 to 60 percent
tool, the results fed back into the context 20 to 40 percent on agent workloads
memory, the prior turns and retrieved documents 10 to 30 percent
response, the model output 10 to 30 percent

One bucket hides which layer drives the spend, so you cannot pick the lever.

The record on every call.

The trace carries the trace id, the three dimension keys, the four layer counts, the cost, and two flags, one for a cached input and one for a batch call. The most accurate attribution pattern joins these traces to the billing export by trace id, which the lesson calls the telemetry joiner.

Plausible wrong answers.

  • "Tokens are what we pay for, so tokens are the metric." They are the vendor's unit. The business pays for outcomes, and a cheaper token can mean a more expensive task.
  • "Tag the cloud bill by team like any other resource." A model call is a transaction, not an asset. The line item has no team on it unless the call stamped one.
  • "Per-tenant cost is enough." Per-task shows which feature to fix and per-user shows abuse. The lesson instruments all three.

Follow-ups an interviewer may ask.

  • (level 1) Why does the token price alone mislead? Expected: it says nothing about tokens per outcome. A cheaper model that needs twice the tokens per task costs more per task.
  • (level 2) Why split the tokens into four layers? Expected: one bucket hides whether prompt bloat, tool results, memory or output drives the spend, so you cannot choose the right fix.
  • (level 2) Why stamp the call at creation instead of tagging the bill later? Expected: the provider line item has no user, task or tenant on it, and retroactive attribution always misses cases.
  • (level 3) Which attribution pattern is the most accurate, and what does it need? Expected: the telemetry joiner, which joins trace ids to billing. It needs the trace id on every call and a billing export with the same key.
