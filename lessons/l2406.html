Why this came about

Neural networks are old; what changed around 2012 was compute. Graphics cards (GPUs), built to colour millions of pixels at once for video games, turned out to be ideal for the matrix multiplications at the core of networks. In 2012 AlexNet, trained on two gaming GPUs, won the ImageNet image-recognition competition by a wide margin, and deep learning took off. Since then the compute used to train the largest models has grown roughly four- to fivefold per year, and a big part of the engineering of modern AI is squeezing more useful arithmetic out of each chip: lower-precision numbers, careful memory use, and splitting work across thousands of GPUs.

In plain words first
A kitchen with many cooks

A CPU is like a kitchen with a few master chefs: each can cook anything, quickly, one dish after another. A GPU is like a kitchen with ten thousand assistants who can each only chop, but all chop at the same time. Making one complicated dish? Use the chefs. Chopping a mountain of onions? The assistants win by a mile. Training and running neural networks is a mountain of onions: billions of identical multiply-and-add steps.

Step 1 · Counting the arithmetic

Multiplying an (m × k) matrix by a (k × n) matrix does m × n × k multiplications and about as many additions: 2 × m × n × k floating-point operations (FLOPs). A layer with d_in inputs and d_out outputs, applied to one input vector, is 2 × d_in × d_out FLOPs: two per weight. So a whole model costs about 2 × (number of parameters) FLOPs per token to run.

def matmul_flops(m, k, n):
    return 2 * m * k * n

print(f"one 768 x 3072 layer, one token: {matmul_flops(1, 768, 3072):,} FLOPs")
print(f"same layer, 1,000 tokens at once: {matmul_flops(1000, 768, 3072):,} FLOPs")

for name, params in [("GPT-2 small", 124e6), ("an 8B model", 8e9), ("a 70B model", 70e9)]:
    print(f"{name:<12} about {2 * params:.1e} FLOPs per generated token")
What you should see

A modern data-centre GPU (an NVIDIA H100, say) can do roughly 10¹⁵ FLOPs per second in 16-bit arithmetic. On paper that is over 60,000 tokens per second for an 8B model. Real generation is much slower, for a reason Step 5 explains: memory, not arithmetic, is usually the bottleneck.

Step 2 · Why GPUs

Even on a CPU, the gap between doing arithmetic one number at a time in Python and handing a whole array to optimised code is huge:

import time
import numpy as np

n = 120
A, B = np.random.default_rng(0).normal(size=(n, n)), np.random.default_rng(1).normal(size=(n, n))

start = time.perf_counter()
C = [[sum(A[i, k] * B[k, j] for k in range(n)) for j in range(n)] for i in range(n)]   # pure Python loops
loop_seconds = time.perf_counter() - start

start = time.perf_counter()
C2 = A @ B                                                                           # NumPy: optimised, parallel code
numpy_seconds = time.perf_counter() - start

print("same answer:", np.allclose(C, C2))
print("NumPy was more than 100 times faster:", loop_seconds / numpy_seconds > 100)
What you should see
same answer: True
NumPy was more than 100 times faster: True

On a typical laptop the loops take around a second and NumPy well under a millisecond: thousands of times faster (the exact ratio depends on your machine, which is why the code prints a yes/no instead). NumPy uses the CPU's vector instructions and several cores. A GPU takes the same idea much further, with thousands of cores and special tensor cores that multiply small blocks of matrices in one step, and very fast memory next to them. That is why PyTorch code that moves tensors .to("cuda") (Lesson 3.16) can run tens to hundreds of times faster than on a CPU.

Step 3 · Number formats: range versus precision

Every number in a model takes space and time to move. Using fewer bits per number means less memory and faster arithmetic, but each format makes a different trade-off between range (how big or small a number can be) and precision (how finely it can distinguish nearby values):

import torch

for dtype in [torch.float32, torch.float16, torch.bfloat16]:
    info = torch.finfo(dtype)
    print(f"{str(dtype):<15} bits {info.bits}   largest {info.max:.3g}   step just above 1: {info.eps:.3g}")

print()
for dtype in [torch.float32, torch.float16, torch.bfloat16]:
    big = torch.tensor(70000.0, dtype=dtype).item()
    plus_one = (torch.tensor(256.0, dtype=dtype) + 1).item()
    third = torch.tensor(1 / 3, dtype=dtype).item()
    print(f"{str(dtype):<15} 70000 -> {big:<8}  256 + 1 -> {plus_one:<6}  1/3 -> {third}")
What you should see
torch.float32   bits 32   largest 3.4e+38   step just above 1: 1.19e-07
torch.float16   bits 16   largest 6.55e+04   step just above 1: 0.000977
torch.bfloat16  bits 16   largest 3.39e+38   step just above 1: 0.00781

torch.float32   70000 -> 70000.0   256 + 1 -> 257.0   1/3 -> 0.3333333432674408
torch.float16   70000 -> inf       256 + 1 -> 257.0   1/3 -> 0.333251953125
torch.bfloat16  70000 -> 70144.0   256 + 1 -> 256.0   1/3 -> 0.333984375
Reading this output
  • float32 handles all three cases well. It was the standard for training until about 2017.
  • float16 overflows: its largest number is 65,504, so 70,000 becomes inf. Large activations or gradients in float16 training can overflow, which is why float16 training needs a trick called loss scaling.
  • bfloat16 ("brain float", from Google) keeps float32's range (70,000 is fine, stored as 70,144) but has very little precision: 256 + 1 = 256, because the gap between neighbouring bfloat16 numbers near 256 is 2. Training mostly tolerates that, and bfloat16 is today's standard format for training and running LLMs.
  • In practice, training uses mixed precision: the big matrix multiplications run in bfloat16, while a float32 master copy of the weights collects the small updates, which would otherwise be rounded away (as the +1 was).

Newer GPUs add fp8 (one byte, used for parts of training and serving the largest models) and even 4-bit floating-point formats. The direction of travel is clear: fewer bits per number, used carefully.

Step 4 · Quantisation: storing weights as small integers

To run a trained model, you can go further and store weights as 8-bit or 4-bit integers plus a scale factor, called quantisation. Each weight becomes a whole number from −127 to 127 (8 bits) or −7 to 7 (4 bits), and is multiplied back by the scale when used.

torch.manual_seed(0)
w = torch.randn(4096) * 0.02                  # 4,096 weights of a typical size

def quantise(w, bits, group=None):
    levels = 2 ** (bits - 1) - 1              # 127 for 8 bits, 7 for 4 bits
    if group:                                 # one scale per group of weights
        g = w.reshape(-1, group)
        scale = g.abs().max(dim=1, keepdim=True).values / levels
        return (torch.round(g / scale).clamp(-levels, levels) * scale).reshape(-1)
    scale = w.abs().max() / levels            # one scale for the whole tensor
    return torch.round(w / scale).clamp(-levels, levels) * scale

for label, bits, group in [("8-bit, one scale", 8, None), ("4-bit, one scale", 4, None), ("4-bit, one scale per 32 weights", 4, 32)]:
    back = quantise(w, bits, group)
    err = (back - w).abs().mean() / w.abs().mean()
    print(f"{label:<32} average error {err.item():.1%} of a typical weight")
What you should see
8-bit, one scale                 average error 1.0% of a typical weight
4-bit, one scale                 average error 18.3% of a typical weight
4-bit, one scale per 32 weights  average error 10.2% of a typical weight

8-bit is nearly lossless here. 4-bit with a single scale for all 4,096 weights is crude, because the one largest weight sets the step size for everyone. Giving each group of 32 weights its own scale nearly halves the error, at the cost of storing the extra scales. Real 4-bit methods (GPTQlater · 3.21, AWQlater · 3.21, the GGUFlater · 10.39 formats used by llama.cpplater · 10.39 and Ollamalater · 10.39) use groups like this plus cleverer rounding, and a good 4-bit version of a model usually performs close to the original. That is how an 8B model runs on a laptop (Lesson 10.39).

Step 5 · Memory: the real bottleneck

To run a model, its weights must fit in the GPU's memory: parameters × bytes per parameter. To generate each token, every weight must be read from memory once, so generation speed is usually limited by memory bandwidth (how many bytes per second can be read), not by arithmetic. To train, you need far more (Lesson 3.15): gradients, the optimiser's two running averages per weight (Lesson 3.17), and a float32 master copy, about 16 bytes per parameter with AdamW in mixed precision, before counting activations.

def weights_gb(params, bytes_per_param):
    return params * bytes_per_param / 1e9

print(f"{'model':<10}{'float32':>10}{'bf16':>10}{'int8':>10}{'4-bit':>10}{'train (AdamW)':>16}")
for name, p in [("1B", 1e9), ("8B", 8e9), ("70B", 70e9)]:
    row = [weights_gb(p, b) for b in (4, 2, 1, 0.5)]
    print(f"{name:<10}" + "".join(f"{v:>8.1f}GB" for v in row) + f"{weights_gb(p, 16):>14,.0f}GB")
What you should see
model        float32      bf16      int8     4-bit   train (AdamW)
1B             4.0GB     2.0GB     1.0GB     0.5GB            16GB
8B            32.0GB    16.0GB     8.0GB     4.0GB           128GB

Reading this output
  • An 8B model needs 16 GB in bfloat16: one 24 GB gaming GPU can run it. In 4-bit it needs 4 GB, which fits on a laptop.
  • A 70B model needs 140 GB in bfloat16 (two 80 GB data-centre GPUs) but 35 GB in 4-bit, which fits on one 48 GB card.
  • Add memory for the KV cachelater · 7.21, the stored attention values for every token of the conversation so far, which grows with context length and the number of users (Lessons 11.28 and 7.21).
  • Training even the 8B model needs about 128 GB just for weights, gradients and optimiser state: more than one GPU. That is why fine-tuninglater · 10.36 usually uses LoRAlater · 3.22, which trains a small set of extra weights instead of all of them (Lesson 14.133).

Step 6 · The cost of training

The rule of thumb from Lesson 3.15: training costs about 6 FLOPs per parameter per training token (2 for the forward pass, 4 for the backward pass). With the GPU's speed and a realistic utilisation (about 40% of the peak is good in practice), you get GPU-hours:

def training_gpu_hours(params, tokens, gpu_flops=989e12, utilisation=0.40):
    """989e12 is roughly an H100's peak for 16-bit matrix maths."""
    flops = 6 * params * tokens
    return flops, flops / (gpu_flops * utilisation) / 3600

print(f"{'run':<22}{'total FLOPs':>12}{'H100 hours':>14}")
for name, p, t in [("1B on 2T tokens", 1e9, 2e12), ("8B on 15T tokens", 8e9, 15e12), ("70B on 15T tokens", 70e9, 15e12)]:
    flops, hours = training_gpu_hours(p, t)
    print(f"{name:<22}{flops:>12.1e}{hours:>14,.0f}")
What you should see
run                    total FLOPs    H100 hours
1B on 2T tokens            1.2e+22         8,426
8B on 15T tokens           7.2e+23       505,561
70B on 15T tokens          6.3e+24     4,423,660

These are lower bounds. Meta reported about 1.3 million H100 hours for Llama 3 8B and 6.4 million for Llama 3 70B (2024); real runs lose time to restarts, slower phases and experiments. At a few dollars per GPU-hour, pretraining a frontier-scale model costs tens to hundreds of millions of dollars, which is why most teams start from a pretrained model and adapt it (Chapters F7 and 11).

Step 7 · Many GPUs at once

A big model does not fit on one GPU, and a big training run would take years on one. Work is split in a few standard ways, often combined:

Technique What is split When it is used
Data parallelism each GPU has the whole model and trains on different batches; gradients are averaged whenever the model fits on one GPU
FSDP / ZeRO weights, gradients and optimiser state are sharded across GPUs and gathered when needed the usual way to train models too big for one GPU
Tensor parallelism each layer's matrices are split across the GPUs in one server very large layers; also used to serve big models
Pipeline parallelism different layers live on different GPUs very deep models spread over many servers

You do not need to implement these; libraries such as PyTorch FSDP, DeepSpeed and the serving engines in Lesson 14.112 do. But they explain the hardware words you will hear: GPUs inside one server are linked by very fast connections (such as NVLink), and servers by fast networks, because these methods constantly exchange data.

The same idea as a formula
  • matrix multiplication (m × k) @ (k × n): 2mkn FLOPs
  • inference: ≈ 2N FLOPs per token for a model with N parameters
  • training: ≈ 6ND FLOPs for N parameters and D training tokens
  • memory for weights: N × bytes per parameter (4 fp32, 2 bf16, 1 int8 or fp8, 0.5 for 4-bit)
  • training with AdamW in mixed precision: ≈ 16N bytes, plus activations
  • symmetric quantisation: q = round(w / s), s = max|w| / (2^(b−1) − 1), ŵ = q · s
Check your mental model
  • ✗ "A bigger GPU always makes my chatbot answer faster."
    ✓ Generation speed is mostly limited by how fast weights can be read from memory. More memory bandwidth, smaller (quantised) weights or batching many users together help most.
  • ✗ "Lower precision always ruins accuracy."
    ✓ bfloat16 is the standard for training, and good 4-bit quantisation loses little for running models. Range problems (float16 overflow) and very crude quantisation are the real risks.
  • ✗ "If a GPU can run a model, it can fine-tune it."
    ✓ Full training needs roughly eight times the memory of bf16 inference. That gap is why LoRA and QLoRA exist.

Exercises

Predict before you run

In bfloat16, what is torch.tensor(1000.0, dtype=torch.bfloat16) + 3? (Hint: bfloat16 has 8 bits of precision, so between 512 and 1024 the gap between neighbouring numbers is 4.) (Solution P1.)

Make it your own

Use weights_gb to find the largest model that fits in 4-bit on a laptop GPU with 12 GB of memory, keeping 3 GB free for the KV cache and everything else. (Solution M1.)

Practice
Apply it

A team wants to fine-tune a 3B model fully (not LoRA) with AdamW in mixed precision. Roughly how much memory do the weights, gradients and optimiser state need, and does that fit on one 80 GB GPU? (Solution X1.)

Solutions

SolutionP1 · Rounding in bfloat16

1000 + 3 = 1003, which bfloat16 cannot store; neighbouring representable numbers near 1000 are 4 apart (..., 996, 1000, 1004, ...), so it rounds to 1004 (the nearest). Small additions to large numbers get rounded, sometimes to nothing: the reason training keeps a float32 master copy of the weights.

SolutionM1 · Fitting a laptop

12 − 3 = 9 GB for weights. At 0.5 bytes per parameter, that is 9 / 0.5 = 18 billion parameters. In practice 4-bit files also store scales and keep some layers at higher precision, so models up to about 14B are a comfortable fit, and 8B models leave plenty of room for long contexts.

SolutionX1 · Full fine-tuning memory

16 bytes × 3 billion = 48 GB before activations. It fits on one 80 GB GPU if activations are kept modest (small batches, shorter sequences, or activation checkpointing, which recomputes activations instead of storing them). A 7B or 8B model (112 to 128 GB) would not fit on one GPU, so it needs sharding across several GPUs or LoRA.

Recap
  • A matrix multiply costs 2mkn FLOPs; running a model costs about 2 FLOPs per parameter per token, training about 6 per parameter per token.
  • GPUs run thousands of identical multiply-adds in parallel, which is exactly what neural networks need.
  • float16 risks overflow; bfloat16 keeps the range with less precision and is the training standard; mixed precision keeps a float32 master copy.
  • Quantisation stores weights as small integers plus scales; 8-bit is nearly lossless and grouped 4-bit is good enough to run large models on small hardware.
  • Memory decides what you can run (weights plus KV cache) and train (about 16 bytes per parameter); large training runs split work across many GPUs.
