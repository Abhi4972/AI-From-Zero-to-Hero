Why this came about

MCP connects agents to tools, but agents also needed to talk to each other and to user interfaces. Google introduced A2A (Agent2Agent) in April 2025, later donated to the Linux Foundation, and the AG-UI protocol appeared for streaming agent events to front ends, forming a protocol stack.

In plain words first
Plugs for tools, for other agents, and for screens

MCP connects an agent to tools. A2A (Agent2Agent) connects an agent to other agents: each publishes a card describing what it can do, and others send it tasks. AG-UI connects an agent to a user interface: a standard stream of events (text, tool calls, state changes) a front end can render. Together they form a protocol stack, each layer solving a different connection problem.

Which protocol connects what

Protocol Connects Governed by
MCP Agent → tools and data Agentic AI Foundation (Linux Foundation)
A2A (Agent2Agent) Agent → other agents, across vendors Linux Foundation
AG-UI (Agent-User Interaction) Agent → user interface Open source, started by CopilotKit
ACP (Agent Client Protocol) Code editor → coding agent Open source, started by Zed
AP2, ACP (Agentic Commerce), UCP Agents → payments and checkout FIDO Alliance; OpenAI and Stripe; Google and retailers

Watch the acronyms: "ACP" has meant three things. IBM's Agent Communication Protocol merged into A2A in August 2025; Zed's Agent Client Protocol is for editors; OpenAI and Stripe's Agentic Commerce Protocol is for checkout.

A2A: agents talking to agents

A2A lets an agent built by one team or vendor delegate work to another agent it knows nothing about internally. Google announced it in April 2025 and donated it to the Linux Foundation in June 2025, with AWS, Cisco, Microsoft, Salesforce, SAP and ServiceNow as founding members. Version 1.0 of the specification was published in March 2026.

Core ideas:

  • Agent Card: a JSON document at /.well-known/agent-card.json describing the agent: name, skills, endpoints, supported input and output types, and security schemes. Version 1.0 added signed agent cards (JWS) so callers can verify who published them.
  • Messages and parts: text, files and structured data.
  • Tasks: long-running work with a task lifecycle: submitted, working, input-required, auth-required, completed, failed, canceled, rejected. Results arrive as artifacts.
  • Transports: JSON-RPC over HTTP, gRPC and HTTP+JSON (REST); streaming over Server-Sent Events; push notifications (webhooks) for very long tasks.
  • Opacity: the caller sees neither the other agent's prompts, tools nor memory, only its card and its outputs. That is the point: agents can be owned by different companies.

import asyncio, threading, time
import uvicorn
from starlette.applications import Starlette
from a2a.server.agent_execution import AgentExecutor, RequestContext
from a2a.server.events import EventQueue
from a2a.server.request_handlers import DefaultRequestHandler
from a2a.server.routes import create_agent_card_routes, create_jsonrpc_routes
from a2a.server.tasks import InMemoryTaskStore
from a2a.helpers.proto_helpers import new_text_message, get_message_text
from a2a.types import AgentCard, AgentCapabilities, AgentInterface, AgentSkill, SendMessageRequest, Role
from a2a.client import create_client

ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

class OrdersAgent(AgentExecutor):
    """The agent's logic. An agent from any framework in Chapters 6 and 7 can sit inside execute()."""
    async def execute(self, context: RequestContext, event_queue: EventQueue) -> None:
        text = context.get_user_input()
        found = [f"{o} is {s}" for o, s in ORDERS.items() if o in text] or ["No order ID found."]
        await event_queue.enqueue_event(new_text_message("; ".join(found), context_id=context.context_id))

    async def cancel(self, context: RequestContext, event_queue: EventQueue) -> None:
        raise NotImplementedError

card = AgentCard(
    name="ShopKart Orders Agent", description="Looks up ShopKart order status.", version="1.0.0",
    supported_interfaces=[AgentInterface(url="http://127.0.0.1:8766/", protocol_binding="JSONRPC",
                                         protocol_version="1.0")],
    capabilities=AgentCapabilities(streaming=False),
    default_input_modes=["text/plain"], default_output_modes=["text/plain"],
    skills=[AgentSkill(id="order_status", name="Order status", description="Status of an order by ID",
                       tags=["orders"], examples=["Where is A-1001?"])],
)
handler = DefaultRequestHandler(agent_executor=OrdersAgent(), task_store=InMemoryTaskStore(), agent_card=card)
app = Starlette(routes=[*create_agent_card_routes(card), *create_jsonrpc_routes(handler, rpc_url="/")])
threading.Thread(target=uvicorn.run, args=(app,), kwargs={"port": 8766, "log_level": "warning"}, daemon=True).start()
time.sleep(1.5)

async def ask_remote_agent():
    client = await create_client("http://127.0.0.1:8766")          # fetches and reads the agent card first
    request = SendMessageRequest(message=new_text_message("Where is A-1002?", role=Role.ROLE_USER))
    async for response in client.send_message(request):
        print(response.WhichOneof("payload"), "->", get_message_text(response.message))

asyncio.run(ask_remote_agent())
What you should see
message -> A-1002 is processing

This agent answered with a single message. For long work, the executor would enqueue a task, then status updates and artifacts; the client can stream them or receive a push notification when done. Leave out protocol_version on the interface and the SDK warns that the card is not spec-compliant.

Long-running work: tasks, status updates and artifacts

Real delegations take time and sometimes need more input. The agent then returns a task and streams its lifecycle: working with progress messages, input-required when it needs something from the caller, an artifact with the result, and completed. TaskUpdater handles the bookkeeping.

from a2a.server.tasks import TaskUpdater
from a2a.helpers.proto_helpers import new_text_part, new_task_from_user_message
from a2a.types import TaskState

class RefundAgent(AgentExecutor):
    """A remote agent that works on a task, may ask for input, and returns an artifact."""
    async def execute(self, context: RequestContext, event_queue: EventQueue) -> None:
        task = context.current_task or new_task_from_user_message(context.message)
        await event_queue.enqueue_event(task)                                     # state: submitted
        updater = TaskUpdater(event_queue, task.id, task.context_id)
        await updater.start_work(new_text_message("Checking eligibility...", context_id=task.context_id, task_id=task.id))
        await asyncio.sleep(0.1)                                                  # real work: tools, models, people
        if "A-" not in context.get_user_input():
            await updater.requires_input(new_text_message("Which order ID?", context_id=task.context_id, task_id=task.id))
            return                                                                # the caller replies on the same task
        await updater.add_artifact([new_text_part("Refund approved: INR 2,499 to UPI")], name="refund-decision")
        await updater.complete()

    async def cancel(self, context: RequestContext, event_queue: EventQueue) -> None:
        raise NotImplementedError

refund_card = AgentCard(
    name="ShopKart Refunds Agent", description="Decides refund requests.", version="1.0.0",
    supported_interfaces=[AgentInterface(url="http://127.0.0.1:8767/", protocol_binding="JSONRPC", protocol_version="1.0")],
    capabilities=AgentCapabilities(streaming=True),
    default_input_modes=["text/plain"], default_output_modes=["text/plain"],
    skills=[AgentSkill(id="refund", name="Refund decision", description="Decide a refund", tags=["refunds"])])
refund_handler = DefaultRequestHandler(agent_executor=RefundAgent(), task_store=InMemoryTaskStore(), agent_card=refund_card)
refund_app = Starlette(routes=[*create_agent_card_routes(refund_card), *create_jsonrpc_routes(refund_handler, rpc_url="/")])
threading.Thread(target=uvicorn.run, args=(refund_app,), kwargs={"port": 8767, "log_level": "warning"}, daemon=True).start()
time.sleep(1.5)

async def delegate(text: str):
    client = await create_client("http://127.0.0.1:8767")
    async for r in client.send_message(SendMessageRequest(message=new_text_message(text, role=Role.ROLE_USER))):
        kind = r.WhichOneof("payload")
        if kind == "task":
            print("  task", TaskState.Name(r.task.status.state))
        elif kind == "status_update":
            st = r.status_update.status
            print("  status", TaskState.Name(st.state), get_message_text(st.message) if st.HasField("message") else "")
        elif kind == "artifact_update":
            art = r.artifact_update.artifact
            print("  artifact", art.name, "->", art.parts[0].text)

asyncio.run(delegate("Refund A-1002, it arrived broken"))
asyncio.run(delegate("I want a refund"))

The second request stopped in input-required: the caller answers by sending another message with the same task ID, and the agent continues. For work that takes hours, register a push notification webhook instead of holding a stream open, and use a durable task store (DatabaseTaskStore) so tasks survive restarts.

In production
A2A in production

Treat a remote agent like any external service: verify its Agent Card (signed cards where available), authenticate both ways, set timeouts on every task, and make your requests idempotent so a retried task does not act twice. Long tasks need push notifications or polling with backoff, and an owner on both sides; a task stuck in working forever is the A2A equivalent of a hung API call.

MCP or A2A?

Use MCP when Use A2A when
You want a capability: run this query, fetch this file You want an outcome from someone else's agent: "resolve this claim"
The caller's agent should decide every step The remote agent should plan and decide on its own
You own both sides or the server is a thin wrapper over an API The other side is a separate team or company with its own models and policies
Calls are short Work may take minutes or days and need input or authorization mid-way

Many systems use both: an orchestrator calls tools over MCP and delegates whole jobs to partner agents over A2A. Frameworks support A2A natively: Google ADK, Strands, Microsoft Agent Framework, Pydantic AI, and LangGraph through Agent Server.

AG-UI: agents talking to front ends

Every chat UI needs the same stream: run started, text chunks, tool calls, state updates, run finished. AG-UI standardizes it as typed events, so any front end (CopilotKit, custom React, mobile) can drive any back end that emits them.

from ag_ui.core import (RunStartedEvent, TextMessageStartEvent, TextMessageContentEvent, TextMessageEndEvent,
                        ToolCallStartEvent, ToolCallArgsEvent, ToolCallEndEvent, RunFinishedEvent)
from ag_ui.encoder import EventEncoder

def agent_run(thread_id: str, run_id: str):
    """What an AG-UI back end streams for one agent turn: lifecycle, a tool call, then text."""
    yield RunStartedEvent(thread_id=thread_id, run_id=run_id)
    yield ToolCallStartEvent(tool_call_id="t1", tool_call_name="get_order_status")
    yield ToolCallArgsEvent(tool_call_id="t1", delta='{"order_id": "A-1002"}')
    yield ToolCallEndEvent(tool_call_id="t1")
    yield TextMessageStartEvent(message_id="m1", role="assistant")
    for chunk in ["A-1002 ", "is ", "processing."]:
        yield TextMessageContentEvent(message_id="m1", delta=chunk)
    yield TextMessageEndEvent(message_id="m1")
    yield RunFinishedEvent(thread_id=thread_id, run_id=run_id)

encoder = EventEncoder()                                     # Server-Sent Events by default
for event in agent_run("thread-42", "run-1"):
    print(encoder.encode(event).strip())

The protocol also defines state snapshots and deltas (shared state between UI and agent), reasoning events, sub-agent events and custom events. In practice you rarely write these by hand: adapters for LangGraph, Google ADK, Microsoft Agent Framework, Pydantic AI, CrewAI, Mastra and others emit them from your agent's own stream.

Bridging a real agent stream to AG-UI

In practice an adapter turns your agent's own stream into AG-UI events. Here is the core of such an adapter for any OpenAI-compatible stream (the lab's mock server, Lesson 6.1), including a state delta that tells the UI what changed (as a JSON Patch), so a side panel can show "orders looked up" without parsing text.

import json
from mockllm import start
from openai import OpenAI
from ag_ui.core import StateSnapshotEvent, StateDeltaEvent, ToolCallResultEvent

llm = OpenAI(base_url=start(), api_key="mock")
TOOLS = [{"type": "function", "function": {"name": "get_order_status", "description": "Order status",
          "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}}]

def stream_turn_as_agui(user_text: str, thread_id: str = "thread-42", run_id: str = "run-2"):
    """Translate one agent turn (model stream, tool call, model stream) into AG-UI events."""
    yield RunStartedEvent(thread_id=thread_id, run_id=run_id)
    yield StateSnapshotEvent(snapshot={"orders_checked": []})
    messages = [{"role": "user", "content": user_text}]
    for step in range(3):
        stream = llm.chat.completions.create(model="mock-model", messages=messages, tools=TOOLS, stream=True)
        calls, text_started = {}, False
        for chunk in stream:
            delta = chunk.choices[0].delta if chunk.choices else None
            if delta and delta.content:
                if not text_started:
                    yield TextMessageStartEvent(message_id=f"m{step}", role="assistant"); text_started = True
                yield TextMessageContentEvent(message_id=f"m{step}", delta=delta.content)
            for tc in (delta.tool_calls or []) if delta else []:
                calls.setdefault(tc.index, {"id": tc.id, "name": tc.function.name, "args": ""})["args"] += tc.function.arguments or ""
        if text_started:
            yield TextMessageEndEvent(message_id=f"m{step}")
        if not calls:
            break
        messages.append({"role": "assistant", "content": None, "tool_calls": [
            {"id": c["id"], "type": "function", "function": {"name": c["name"], "arguments": c["args"]}} for c in calls.values()]})
        for c in calls.values():
            yield ToolCallStartEvent(tool_call_id=c["id"], tool_call_name=c["name"])
            yield ToolCallArgsEvent(tool_call_id=c["id"], delta=c["args"])
            yield ToolCallEndEvent(tool_call_id=c["id"])
            order = json.loads(c["args"])["order_id"]
            result = f"{order} is {ORDERS.get(order, 'not found')}"
            yield ToolCallResultEvent(message_id=f"r{step}", tool_call_id=c["id"], content=result)
            yield StateDeltaEvent(delta=[{"op": "add", "path": "/orders_checked/-", "value": order}])
            messages.append({"role": "tool", "tool_call_id": c["id"], "content": result})
    yield RunFinishedEvent(thread_id=thread_id, run_id=run_id)

for event in stream_turn_as_agui("Where is A-1001?"):
    e = json.loads(encoder.encode(event).removeprefix("data: "))
    e.pop("toolCallId", None); e.pop("threadId", None); e.pop("runId", None)               # trim random ids for display
    print(e["type"], {k: v for k, v in e.items() if k not in ("type", "messageId")})

A front end subscribed to this stream can show a "checking order A-1001" card while the tool runs, render the reply word by word, and keep a live list of checked orders from the state deltas. Serve the generator from an HTTP endpoint with text/event-stream, and the same UI works with any back end that emits AG-UI.

Generative UI goes one step further: the agent sends a description of UI components (an approval card, a form, a chart) and the front end renders them. Google's A2UI (declarative UI descriptions) and MCP Apps (interactive HTML in sandboxedlater · 10.3 frames) are the two main specifications.

In production
AG-UI in production

The common failures are on the connection, not the agent: streams cut by proxies that buffer or time out, clients that reconnect and lose state, and UIs that show tool calls the user should not see. Send state snapshots periodically so a reconnecting client can recover, filter internal events before they reach the browser, and keep approvals server-side so a modified client cannot approve its own actions.

Coding agents and commerce

  • Agent Client Protocol (ACP): connects code editors (Zed, JetBrains IDEs, Neovim and others) to coding agents (Claude Code, Gemini CLI, Codex and others) over JSON-RPC, the way the Language Server Protocol connects editors to language tools. Deep Agents supports it.
  • Agentic Commerce Protocol (OpenAI and Stripe, September 2025): checkout inside an AI surface, with a shared payment token so the agent never sees card details.
  • AP2, Agent Payments Protocol (Google, September 2025; moved to the FIDO Alliance in April 2026): proves a user authorized a purchase, through signed mandates (intent, cart and payment).
  • UCP, Universal Commerce Protocol (Google with Shopify, Walmart, Target and others, January 2026): discovery, cart and checkout between agents and merchants.
Industry practice
Standardize at the seams, not inside

Experienced platform teams adopt protocols where systems meet: MCP between agents and tools, A2A between independently owned agents, AG-UI or a similar event schema between back end and UI, OpenTelemetrylater · 12.13 for traces. Inside one team's agent, plain function calls are simpler and faster. A protocol at an internal seam you control adds network hops and failure modes without adding interoperability.

Solutions

SolutionP1 · Which protocol connects what

A2A: it connects agents across organizations, each keeping its own tools and model. MCP connects an agent to tools and data; AG-UI connects an agent to a front end.

SolutionB1 · Agents need more than text

Progress during tool calls, state updates and approval requests: the interface cannot show "checking your order" or ask for confirmation. AG-UI standardizes these events so front ends and agents interoperate.

SolutionD1 · Long-running tasks

As a task: the caller creates a task, the partner returns a task ID and status, and the caller polls or receives updates (streaming or push notifications). Do not hold one request open for minutes.

SolutionM1 · Richer events

Emit a tool-call start with the tool name, a tool-call end with a short result, text deltas, then a state snapshot and a run-finished event. Keep raw tool arguments out of user-visible events.

Check your understanding

Explain the mechanismHow do MCP, A2A and AG-UI fit together?

Worked answer. MCP connects an agent to tools, resources and prompts. A2A connects agents to other agents, possibly across organizations, with agent cards for discovery and tasks for long-running work. AG-UI connects an agent to a user interface with a stream of run, text, tool and state events. One system can use all three.

A plausible wrong answer. "They compete." They connect different pairs.

Follow-ups. When would you not use A2A between your own agents?

Debug a failureTwo agents connected by A2A disagree about task status. What do you check?

Worked answer. The task's state history on both sides, retries that created duplicate tasks, and whether updates were missed (no push notifications, polling too rarely). Use idempotent task creation and treat the remote side's status as the source of truth.

A plausible wrong answer. "The protocol is unreliable." Usually the client handles retries badly.

Follow-ups. How do you authenticate agents to each other?

Defend a designUse A2A between agents inside one team's system?

Worked answer. Usually not: inside one system, agents are functions, subgraphs or tools (Lesson 6.16), with shared tracing and no network boundary. A2A is for agents owned by different teams or companies, where discovery, authentication and independent deployment matter.

A plausible wrong answer. "Yes, protocols make everything cleaner." A network protocol inside one process adds latency and failure modes.
