Why this came about

Training a model became easy long before evaluating one did. With a few lines of configuration anyone can produce a fine-tuned model and a falling loss curve, and the hard question moved to what happens afterwards: is it better than what we had, where does it fail, and why? Teams that fine-tune successfully report spending most of their effort on evaluation sets, error analysis and data repair, and very little on training settings. This lesson is that part of the work, on the model you trained two lessons ago, which scored 100% on validation and 42.5% on the test set.

In plain words first
Marking the exam paper properly

A single score is like a single exam mark. It tells you whether there is a problem and nothing about what the problem is. A good teacher looks at which questions were missed, what was written instead of the right answer, and whether the student misread the instructions. Then the teacher changes what is taught, not how loudly. Evaluating a fine-tune is the same: split the score up, read the wrong answers, check that the model is being asked in the way it was taught, and fix the training material.

Step 1 · Look past the average

The test score of the fully fine-tuned model was 42.5% fully correct. Split it by the true intent of each ticket, and by field:

from ft_data import *
from ft_model import *
train_rows, val_rows, test_rows = build()
model = load("shopkart-ft/full")                       # the fully fine-tuned model saved in Lesson 11.14

results = []
for row in test_rows:
    out = reply(model, to_messages(row, with_answer=False))
    results.append((row, out, score(out, row["label"])))

print(f"{'true intent':<14}{'tickets':>8}{'intent':>8}{'order_id':>10}{'urgent':>8}{'all correct':>13}")
for intent in INTENTS:
    sub = [s for row, out, s in results if row["label"]["intent"] == intent]
    mean = lambda k: sum(s[k] for s in sub) / len(sub)
    print(f"{intent:<14}{len(sub):>8}{mean('intent'):>8.0%}{mean('order_id'):>10.0%}{mean('urgent'):>8.0%}{mean('all_correct'):>13.0%}")

The average hid two very different situations. Order numbers and urgency are right on every test ticket in every class: that part of the task is solved. The whole problem is the intent, and even there one class is perfect while the other four are mostly wrong. A model that is 100% right on one class and poor on the rest is not "42% accurate"; it is doing something specific, and the next step is to find out what.

Step 2 · Read what it says instead

For every ticket with the wrong intent, count which intent the model gave, and read a few:

from collections import Counter
mistakes = Counter()
for row, out, s in results:
    if s["valid_json"] and not s["intent"]:
        mistakes[(row["label"]["intent"], json.loads(out).get("intent"))] += 1
print("true intent -> predicted intent : count")
for (true, pred), n in mistakes.most_common():
    print(f"  {true:<13}-> {pred:<13}: {n}")
print()
shown = set()
for row, out, s in results:
    key = row["label"]["intent"]
    if not s["intent"] and key not in shown:
        shown.add(key)
        print(f"[{key}] {row['text']}\n    model said: {json.loads(out).get('intent') if s['valid_json'] else out}")

Now the behaviour is clear. When the model does not recognise a phrasing, it almost always answers order_status. That is why order_status scored 100% in Step 1: not because the model understands those tickets better, but because that is its default guess. The examples show why the guess is tempting: the test phrasings mention an order number and a product, as most order_status training tickets do, and say "refund", "cancel" or "exchange" in words the model never saw ("reimbursed", "drop this order", "trade this").

A second finding: for other tickets the model sometimes invents an intent that is not one of the five (pay, payable). Nothing in a language model limits it to your list of labels.

Reading this output
Two fixes that do not involve training
  • Constrain the output. Validate the reply against the allowed values and treat anything else as a failure to be retried or escalated (Lesson 11.2). Serving systems can also force the output to follow a JSON schema while it is generated (constrained decoding), which makes an invented label impossible.
  • Use confidence. A model that is unsure spreads its probability across several labels. Reading the probability of the chosen intent token lets you send low-confidence tickets to a person or to a larger model. This is a cascade, and it is how small tuned models are usually deployed (Lesson 14.114).

Step 3 · Is the model being asked the way it was trained?

Before blaming the data, rule out the commonest cause of "it worked in training and not in production": the input format. Evaluate the same model on tickets it handles perfectly, changing only how the prompt is built:

def no_system(row):
    return [{"role": "user", "content": row["text"]}]

def other_system(row):
    return [{"role": "system", "content": "You are a helpful assistant."}, {"role": "user", "content": row["text"]}]

def raw_reply(model, text, max_new_tokens=40):
    """Skip the chat template completely: just the ticket text, as a plain string."""
    enc = tok(text, return_tensors="pt")
    with torch.no_grad():
        out = model.generate(**enc, max_new_tokens=max_new_tokens, do_sample=False, pad_token_id=tok.pad_token_id)
    return tok.decode(out[0, enc["input_ids"].shape[1]:], skip_special_tokens=True)

def short(scores):
    return f"valid JSON {scores['valid_json']:>4.0%}   order_id {scores['order_id']:>4.0%}   all correct {scores['all_correct']:>4.0%}"

sample = val_rows[:20]
print("exactly as trained        ", short(evaluate(model, sample)))
print("system message left out   ", short(evaluate(model, sample, no_system)))
print("a different system message", short(evaluate(model, sample, other_system)))
raw = [score(raw_reply(model, row["text"]), row["label"]) for row in sample]
print("no chat template at all   ", short({k: sum(s[k] for s in raw) / len(raw) for k in raw[0]}))
print("\nwithout the template the model writes:", repr(raw_reply(model, sample[0]["text"]))[:90])
What you should see
exactly as trained         valid JSON 100%   order_id 100%   all correct 100%
system message left out    valid JSON 100%   order_id 100%   all correct 100%
a different system message valid JSON 100%   order_id 100%   all correct 100%
no chat template at all    valid JSON   0%   order_id   0%   all correct   0%

without the template the model writes: ", no late fees, and no hassle.\n\nI'm looking forward to seeing you soon,\n\n[Your Name]"

Two results, and they teach different things.

The system message made no difference here. Every training example had the same system message, so it carried no information and the model learned to ignore it; you saw the same thing in Lesson 3.23, when the model answered a geography question in JSON with no system message at all. Do not rely on this. A model fine-tuned with several different system messages, or less heavily, depends on them, and the safe rule is unchanged: send in production exactly what you trained on.

Without the chat template the model is useless. The same weights, given the ticket as plain text, continue it as if it were the start of a letter, and not one reply is JSON. The markers <|im_start|>user, <|im_end|> and <|im_start|>assistant are how the model knows that a question has ended and its answer should begin.

Template mismatches are easy to cause without noticing, because serving tools apply a chat template for you and may not use yours:

Where it goes wrong What happens
The serving tool has its own template for the model, or a default one The model sees markers it was not trained on; quality drops a little or a lot
The generation prompt (the final <|im_start|>assistant) is missing The model continues the user's message instead of answering
The end-of-turn token is not set as a stop token The model answers correctly, then keeps generating
A beginning-of-text token is added twice Subtle quality loss
You trained on raw strings but serve with a chat endpoint (or the reverse) Like the last row of the output above

The test is always the same: print the exact string or token ids that reach the model in production, and compare them with what apply_chat_template produced in training.

Step 4 · An experiment: variety against volume

The diagnosis from Steps 1 and 2 is that the training data has too few ways of saying each thing. That is a claim, and claims should be tested. Train three models that differ only in their data, and score all three on the same 40 test tickets (whose phrasings are in none of the training sets):

experiments = [("320 tickets, 2 phrasings per intent", dict(n_train=320, phrasings=2)),
               ("320 tickets, 8 phrasings per intent", dict(n_train=320, phrasings=8)),
               (" 80 tickets, 8 phrasings per intent", dict(n_train=80, phrasings=8))]
for name, settings in experiments:
    rows, _, _ = build(**settings)
    tuned = load()                                       # a fresh copy of the base model each time
    train(tuned, rows, steps=40, lr=5e-5, log_every=1000)   # a short full fine-tune; the loss is near zero by step 40 (Lesson 11.14)
    s = evaluate(tuned, test_rows)                       # always the same 40 unseen-phrasing test tickets
    print(f"{name}:  intent {s['intent']:.0%}   all correct {s['all_correct']:.0%}", flush=True)
    if settings == dict(n_train=320, phrasings=8):
        tuned.save_pretrained("shopkart-ft/varied"); tok.save_pretrained("shopkart-ft/varied")   # keep the best one for Lesson 11.17
What you should see
step   1  train loss 1.8534
320 tickets, 2 phrasings per intent:  intent 30%   all correct 30%
step   1  train loss 2.0908
320 tickets, 8 phrasings per intent:  intent 90%   all correct 90%
step   1  train loss 1.8180
 80 tickets, 8 phrasings per intent:  intent 68%   all correct 65%

Ignore the step 1 lines, which are the training function reporting its first step. Read the other three lines as an experiment.

  • Same volume, more variety (first line against second): with 320 tickets in both cases, going from 2 to 8 phrasings per intent took the test score from 30% to 90%. Nothing about the model, the training settings or the number of examples changed.
  • A quarter of the volume, with variety (third line): 80 varied tickets beat 320 uniform ones by a wide margin.

The model, the code and the hyperparameters were never the problem. No learning rate would have turned 30% into 90%. This is what practitioners mean by "fine-tuning is a data problem", and it is the reason Lesson 7.25 spent so long on the dataset.

Watch out
How sure are these numbers?

The test set has 40 tickets, so each ticket is worth 2.5 points, and a different random seed would move each result by a few points (Lesson 2.14). A jump from 30% to 90% is far outside that noise. A difference of 5 points between two settings would not be, and you would need a larger test set, or several runs with different seeds, before believing it. Size your test set for the smallest difference you care about.

Step 5 · Where things stand, and the decision

Every result from the workshop, on the same test tickets:

Approach Test, all correct What it costs to run Notes
Base 135M model, instructions only 0% Tiny Cannot produce the format
Base 135M model, five examples in the prompt 15% Tiny, but 7 times the prompt tokens Format fixed, content wrong
Full fine-tune, 4 phrasings per intent 42.5% Tiny Memorised its training phrasings
LoRA on all linear layers, 4 phrasings 60% Tiny Generalised better from the same data
Full fine-tune, 8 phrasings per intent 90% Tiny Better data, half the training steps
A large hosted model with a good prompt not measured here; expect high Hundreds of times more per ticket The alternative to beat

Is 90% good enough? That is not a modelling question. It depends on what a wrong route costs (a refund request sent to the wrong queue is delayed; a cancellation missed may ship an unwanted parcel), on what the current process achieves, and on whether errors can be caught downstream. Usual next steps from here:

  1. Replace templates with real tickets, labelled by a large model and reviewed by people (Lesson 7.25, Step 8). Real variety is far greater than ten phrasings.
  2. Add the hard cases on purpose: two requests in one ticket, no order number, mixed Hindi and English, sarcasm, tickets that are not requests at all.
  3. Constrain the intent to the allowed list, and route low-confidence tickets to a larger model.
  4. Measure the large-model alternative on the same test set, and compare cost at your volume (Lesson 3.25).

A debugging checklist

Symptom Most likely causes What to do
Great validation score, poor test or production score Training data lacks variety; leakage between training and validation Error analysis as in Steps 1 and 2; add varied and real examples; deduplicate
Worked in the notebook, poor when served Chat template or system message differs; quantisation; wrong stop token Compare the exact input strings; evaluate the served model on the test set
Correct answer followed by extra text End-of-turn token missing from the labels or the stop list Include it in training targets; set stop tokens
Output not in the allowed set Nothing constrains a language model's output Validation with retry; constrained decoding; more examples of edge cases
Loss does not fall Learning rate too low; labels all masked; weights frozen Print trainable parameter count and a batch of labels; raise the rate
Loss jumps or is nan Learning rate too high; bad examples (empty, enormous) Lower the rate; add warm-up and clipping; inspect the longest and shortest examples
Loss near zero immediately The answer is visible in the prompt; duplicates Check encode; check for leakage
Training loss falls, validation loss rises Overfitting Fewer epochs; more data; lower LoRA rank; early stopping
The model lost general abilities Catastrophic forgetting Fewer steps; LoRA; mix in general examples; regression tests
Results change between runs Small test set; sampling at generation time Fix seeds; evaluate with greedy decoding; larger test set
Good on average, bad for one group or language That group is rare in the training data Per-group scores (Lesson 10.35); targeted data

The order in which to spend effort, from experience across many teams: data first (coverage, correctness, format), then how long you train (stop when validation stops improving), then the learning rate, and only then method details such as LoRA rank.

Check your mental model
  • ✗ "One accuracy number describes a model."
    ✓ Split it by class and by field, and read the errors. The average here hid one perfect class and four failing ones.
  • ✗ "If the score is low, train longer or tune the learning rate."
    ✓ First find out what is wrong. Here more variety in the data tripled the score with the same settings and half the steps.
  • ✗ "The fine-tuned model will only output the labels I trained it on."
    ✓ It can produce any text. Validate or constrain the output.
  • ✗ "A model that works in my notebook will work the same when served."
    ✓ Only if the served input, token for token, matches the training format.

Practice
Apply it

A team's fine-tuned support model scores 94% on their evaluation set. After release, agents report that it handles billing questions badly. The evaluation set has 500 examples sampled at random from last year's tickets, of which 12 are about billing. What is wrong with the evaluation, and what would you change? (Solution X1.)

Solutions

SolutionP1 · One phrasing per intent

Expect a score at or below the 2-phrasing result, close to what you would get by always answering one intent (20% for five balanced classes, plus whatever the default class contributes). With a single sentence pattern per intent, the model has learned five strings and nothing about meaning. Which default it picks depends on which training pattern the test phrasings most resemble on the surface.

SolutionM1 · Constraining the output

pred = json.loads(reply(...)); pred["intent"] = pred["intent"] if pred.get("intent") in INTENTS else "other". The invented intents all occurred on other tickets, so mapping them to other makes those tickets correct: other improves by several tickets and the overall score by a few points, at no training cost. The larger failure, defaulting to order_status, is untouched, because those outputs are valid labels. Constraints fix invalid outputs, not wrong ones.

SolutionX1 · An evaluation set that hides a group

Twelve billing examples cannot measure billing quality: one error moves that group's score by 8 points, and the overall 94% would barely change if all twelve were wrong. Random sampling reproduces the frequency of topics, not their importance. Build the set by stratified sampling: a minimum number per category (say 50), including rare but costly ones; report scores per category with a minimum bar for each; and add every production failure to the set as it is found (Lesson 14.115).

Recap
  • Break scores down by class and by field, and read the wrong answers. Averages hide default guesses and invented labels.
  • Check the format: the chat template is a hard requirement, and what reaches the model in production must match training exactly.
  • A controlled experiment showed that variety in the training data, not volume or settings, decided generalisation: 30% to 90% with the same number of tickets.
  • Constrain outputs and use confidence to catch what the model cannot do.
  • Debug in the order data, training length, learning rate, method details, and size the test set for the differences you need to see.

Check your understanding

Q1A fine-tuned classifier scores 100% on one class and about 30% on the other four. What is the most likely explanation?

A default guess is always right for its own class and wrong for the rest; the confusion counts confirm it.

Q2In the variety experiment, 80 varied tickets beat 320 uniform ones. What is the lesson?

Extra examples that repeat the same patterns add little; new patterns add a lot.

Q3A fine-tuned model answers perfectly in your notebook but writes rambling text when served. What do you check first?

Compare the exact prompt string that reaches the model in each place; a template or stop-token mismatch is the usual cause.
