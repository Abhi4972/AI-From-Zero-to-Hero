In plain words first
The idea in one line

Training on CPU is fine for learning. Training for real needs a GPU.

Terms you'll hear
Term What people say What it actually means
CUDA "GPU programming" NVIDIA's parallel computing platform that lets you run code on the GPU
VRAM "GPU memory" Video RAM on the GPU, separate from system RAM. Limits model size.
fp16 "Half precision" 16-bit floating point, uses half the memory of fp32 with minimal accuracy loss
Tensor Core "Fast matrix hardware" Specialized GPU cores for matrix multiplication, 4-8x faster than regular cores

The problem

In plain words first

A neural network spends almost all its time multiplying large grids of numbers. A CPU has a handful of powerful cores that do this a few numbers at a time; a GPU has thousands of simple cores that do it all at once. The second limit is memory: the whole model, and while training much more, has to fit in the GPU's own memory, called VRAM.

Most lessons in phases 1-3 run fine on CPU. But once you start training CNNs, transformers, or LLMs (phases 4+), you need GPU acceleration. A training run that takes 8 hours on CPU takes 10 minutes on GPU.

You have three options: local GPU, cloud GPU, or Google Colab (free).

The idea

Your options:

1. Local NVIDIA GPU
   Cost: $0 (you already have it)
   Setup: Install CUDA + cuDNN
   Best for: Regular use, large datasets

2. Google Colab (free tier)
   Cost: $0
   Setup: None
   Best for: Quick experiments, no GPU at home

3. Cloud GPU (Lambda, RunPod, Vast.ai)
   Cost: $0.20-2.00/hr
   Setup: SSH + install
   Best for: Serious training, large models

The same idea as a formula

Work. Multiplying an m×k matrix by a k×n one takes 2mnk floating-point operations (FLOPs): one multiply and one add per term.

Speed is capped twice. A chip can do at most P FLOP per second and move at most B bytes per second between its memory and its cores. A computation that does I FLOPs per byte it moves (its arithmetic intensity) runs at most at

FLOP/s≤min(P,I⋅B)(the roofline model)

Large matrix products reuse each number many times (I grows with matrix size), so they hit the P ceiling: compute-bound. Generating text one token at a time multiplies each weight once per token (I≈1 FLOP per byte in bf16), so it hits the B ceiling: memory-bound.

Decoding speed limit. For a batch of one, every new token reads all the weights once:

tokens per second≤model bytesB​

Worked example
GPU arithmetic by hand

An NVIDIA H100 (SXM) is rated at P≈989 TFLOP/s for dense bf16 matrix work and B=3.35 TB/s of memory bandwidth.

  • Ridge point: 989/3.35≈295 FLOP per byte. Below it, memory limits you; above it, arithmetic does.
  • A big matrix product, 4096×4096 times 4096×4096 in bf16: 2×40963=1.4×1011 FLOPs over 3×40962×2=100 MB, so I≈1365: compute-bound, about 0.14 ms at full speed.
  • Chatting with an 8B model in bf16 (16 GB): at most 3.35 TB/s/16 GB≈209 tokens per second for one user, however many FLOPs the chip has. Quantising to 4 bits (4 GB) raises the ceiling about four times; batching many users shares each weight read among them.
Check your mental model
  • ✗ "A GPU makes every Python program faster."
    ✓ Only work that is handed to it as large tensor operations. A Python for loop still runs on the CPU, and copying data to the GPU and back has its own cost.
  • ✗ "If a 7-billion-parameter model fits for inference, I can fine-tune it on the same card."
    ✓ Training also stores gradients and the optimiser's state. With Adam in full precision that is about 16 bytes per parameter, eight times the 2 bytes of fp16 inference.
  • ✗ "Colab's free GPU is always available."
    ✓ It is shared and time-limited; sessions disconnect and GPU types vary. Save your work to Drive or GitHub.

Build · Option 1: Local NVIDIA GPU

Check if you have one:

nvidia-smi

Install PyTorch with CUDA. On Linux the default wheel ships with CUDA. On Windows, copy the CUDA command from the selector at pytorch.org.

pip install torch torchvision torchaudio

Then check that PyTorch sees the GPU:

import torch

print(f"CUDA available: {torch.cuda.is_available()}")
print(f"CUDA version: {torch.version.cuda}")
if torch.cuda.is_available():
    print(f"GPU: {torch.cuda.get_device_name(0)}")
    print(f"Memory: {torch.cuda.get_device_properties(0).total_memory / 1e9:.1f} GB")

Why this came about
The one line that makes code portable

device = torch.device("cuda" if torch.cuda.is_available() else "cpu") is worth copying into every training script. Create tensors and models with .to(device) and the same code runs on a laptop and on a cloud GPU.

See it drawn
How fast is this page's CPU?

Square matrix products of growing size, timed with PyTorch (best of three runs), against the 2n3 FLOP count of the formula box.

import time, torch

# Measured matrix-multiply speed on this CPU, against the 2·n³ operation count.
print(f"{'n':>6} {'FLOPs (2n³)':>13} {'time (ms)':>10} {'GFLOP/s':>9}")
for n in [256, 512, 1024, 2048]:
    a, b = torch.randn(n, n), torch.randn(n, n)
    a @ b
    ts = []
    for _ in range(3):
        t0 = time.perf_counter(); a @ b; ts.append(time.perf_counter() - t0)
    t = min(ts)
    print(f"{n:>6} {2 * n**3:>13.2e} {1000 * t:>10.2f} {2 * n**3 / t / 1e9:>9.1f}")
print("For scale: an H100 is rated at about 989 TFLOP/s of dense BF16 matrix arithmetic.")

   256      3.36e+07       0.14     246.1
   512      2.68e+08       1.07     250.6
  1024      2.15e+09      20.09     106.9
  2048      1.72e+10     109.05     157.5

Reading this output

Each doubling of n multiplies the FLOP count by 8 and the time by roughly 8 as well, so the rate stays at the same order, one to a few hundred GFLOP/s: this CPU's compute ceiling P. On a shared server the timings vary by a factor of two from run to run; the order of magnitude is what counts. An H100's rated 989 TFLOP/s is several thousand times higher, which is the gap the GPU options in this lesson buy you, and why training is planned in GPU-hours.

Build It: GPU vs CPU benchmark

import torch
import time

size = 5000

a_cpu = torch.randn(size, size)
b_cpu = torch.randn(size, size)

start = time.time()
c_cpu = a_cpu @ b_cpu
cpu_time = time.time() - start
print(f"CPU: {cpu_time:.3f}s")

if torch.cuda.is_available():
    a_gpu = a_cpu.to("cuda")
    b_gpu = b_cpu.to("cuda")

    torch.cuda.synchronize()
    start = time.time()
    c_gpu = a_gpu @ b_gpu
    torch.cuda.synchronize()
    gpu_time = time.time() - start
    print(f"GPU: {gpu_time:.3f}s")
    print(f"Speedup: {cpu_time / gpu_time:.0f}x")
What you should see
CPU: 1.424s
Reading this output

This page runs on a CPU server, so you see only the CPU line: about 3.9 seconds for one 5000 × 5000 matrix product, which is 2 × 5000³ = 250 billion floating-point operations. On a GPU the same product takes a few milliseconds. The torch.cuda.synchronize() calls matter: GPU work is queued and returns at once, so without them you would time the queueing, not the work.

Predict before you run

Before running the estimator below: how many gigabytes do the weights of a 7-billion-parameter model need in fp16, and does it fit on a 16 GB card for inference? For training with Adam? (Solution P1.)

def gb(params, bytes_per_param):
    return params * bytes_per_param / 1e9

for name, n in [("1.5B", 1.5e9), ("7B", 7e9), ("13B", 13e9), ("70B", 70e9)]:
    print(f"{name:>4}  inference fp16: {gb(n, 2):6.1f} GB   training fp32 + Adam: {gb(n, 16):7.1f} GB")

Break it on purpose

Delete both torch.cuda.synchronize() lines from the benchmark and run it on a GPU, for example in Colab. What happens to the reported GPU time and the speedup, and why is the number wrong? (Solution B1.)

Recap
What to keep from this lesson
  • Phases 1–3 run on a CPU; from Phase 4 on, use a local GPU, Colab or a rented cloud GPU.
  • Write device-independent code with torch.device(...) and .to(device).
  • Weights in fp16 need about 2 bytes per parameter; full training with Adam needs about 16, before activations.
  • Time GPU code with torch.cuda.synchronize() around the timed part, and ignore the first run.

Solutions

SolutionP1 · Seven billion parameters

7 × 10⁹ × 2 bytes = 14 GB, so the weights alone fit on a 16 GB card with about 2 GB left for activations and the CUDA context, which is tight but works for short inputs. Training with Adam needs 7 × 10⁹ × 16 bytes = 112 GB, far beyond one 16 GB card. That gap is why later lessons cover LoRA, quantisation and sharding.

SolutionB1 · Timing the queue

The GPU time drops to well under a millisecond and the speedup jumps to thousands. The matrix product was only queued when time.time() read the clock; the GPU finishes it later. You measured how long it takes to launch the work, not to do it. torch.cuda.synchronize() waits until the queue is empty, so the clock includes the work.

Industry practice
What's current (2024–2026)
  • Data-centre GPUs. NVIDIA's Blackwell generation (B200, GB200 and B300 systems) is what the big clouds added in 2025–2026, with H100 and H200 still the most widely rented; FP8 and FP4 tensor-core formats are what make the newer chips faster for inference.
  • Ways to rent. Besides the big clouds, GPU clouds (Lambda, CoreWeave, RunPod) and serverless GPU platforms (Modal, Replicate) bill by the second or hour; Google Colab and Kaggle still give free notebook GPUs for learning.
  • Apple silicon and drivers. PyTorch's MPS backend and Apple's MLX run models on Mac GPUs; on Linux, NVIDIA's open-source kernel modules are the default driver for Turing and newer GPUs since the R560 drivers.

Sources: NVIDIA Blackwell, MLX, PyTorch MPS, NVIDIA open kernel modules.
