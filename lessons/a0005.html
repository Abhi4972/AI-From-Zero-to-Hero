The problem

In plain words first

A notebook is a document made of cells. When you run a code cell, it is sent to a kernel, a Python process that stays alive between cells and remembers every variable. That memory is what makes notebooks fast to explore with, and it is also their main trap: what the kernel remembers depends on the order you clicked, not the order on the page.

Every AI paper, tutorial, and Kaggle competition uses Jupyter notebooks. They let you run code in pieces, see outputs inline, mix code with explanations, and iterate fast. If you try to learn AI without notebooks, you're doing math homework without scratch paper.

But notebooks have real traps. People use them for everything, including things they're terrible at. Knowing when to use a notebook and when to use a script will save you from debugging nightmares later.

The idea

A notebook is a list of cells. Each cell is either code or text.

The kernel is a Python process running in the background. When you run a cell, it sends the code to the kernel, which executes it and sends back the result. All cells share the same kernel, so variables persist between cells.

That "whatever order you click" part is both the superpower and the foot-gun.

The same idea as a formula

The kernel holds a state S: every variable, import and object currently in memory. Running cell c is a function from one state to the next, S→fc​(S). If you run cells c1​,c2​,…,ck​ in that order, starting from an empty kernel,

Sk​=fck​​(⋯fc2​​(fc1​​(∅))⋯)

The result depends on the order and the number of times you ran each cell, not on the order the cells appear in the file. The notebook file stores the code and the last outputs, not the history of runs, so the only state another reader can reproduce is the one from running every cell once, top to bottom, from a fresh kernel.

Worked example
Three cells by hand

Cells: (1) x = 10, (2) x = x * 2, (3) y = x + 1.

  • Top to bottom, 1, 2, 3: x=20, y=21.
  • Run cell 2 twice by accident, 1, 2, 2, 3: x=40, y=41. The file looks identical.
  • Then re-run cell 1 to "reset": x=10, but y is still 21, left over from before. Any output that uses both now mixes two histories.
Check your mental model
  • ✗ "The notebook on screen is the program."
    ✓ The program is whatever the kernel ran, in the order you ran it. A cell you deleted can still have left a variable behind.
  • ✗ "If it runs on my machine, it runs for my colleague."
    ✓ Only if it runs top to bottom on a fresh kernel. Use Restart & Run All before you share it.
  • ✗ "%timeit is Python."
    ✓ Lines starting with % or ! are instructions to Jupyter (IPython). Paste them into a .py script and you get a SyntaxError.

Step 3 · Cell types

Code cells run Python and show the output:

import numpy as np
data = np.random.randn(1000)
data.mean(), data.std()
What you should see
(np.float64(0.0021407501030937352), np.float64(0.9874740472549776))

Output: (0.0032, 0.9987)

Markdown cells render formatted text. Use them to document what you're doing and why. Supports headers, bold, italic, LaTeX math ($E = mc^2$), tables, and images.

Reading this output

The run on this page printed different numbers from the (0.0032, 0.9987) in the text, and your run will differ again: np.random.randn draws new random numbers each time. The mean is close to 0 and the standard deviation close to 1 because the numbers come from a standard normal distribution. Add np.random.seed(0) at the top of the cell to get the same numbers every run.

Step 4 · Magic commands

These aren't Python. They're Jupyter-specific commands that start with % (line magic) or %% (cell magic).

Time your code:

%timeit np.random.randn(10000)
What you should see
238 us +- 51.3 us per loop (mean +- std. dev. of 7 runs, 1,000 loops each)

Output: 45.2 us +/- 1.3 us per loop

%%time
total = sum(i * i for i in range(2_000_000))
What you should see
CPU times: user 87.5 ms, sys: 0 ns, total: 87.5 ms
Wall time: 145 ms

Output: Wall time: 2.34 s

%timeit runs the code many times and averages. %%time runs it once. Use %timeit for microbenchmarks, %%time for training runs.

Enable inline plots:

%matplotlib inline

Every plt.plot() or plt.show() now renders directly in the notebook.

Install packages without leaving the notebook:

!pip install scikit-learn

The ! prefix runs any shell command.

Check environment variables:

%env CUDA_VISIBLE_DEVICES=0
%env CUDA_VISIBLE_DEVICES
What you should see
env: CUDA_VISIBLE_DEVICES=0
'0'
Predict before you run

%timeit reported a time per loop for np.random.randn(10000). Will [random.gauss(0, 1) for _ in range(10000)] be faster or slower, and by roughly how much? (Solution P1.)

%timeit np.random.randn(10000)
import random
%timeit [random.gauss(0, 1) for _ in range(10000)]
What you should see
153 us +- 5 us per loop (mean +- std. dev. of 7 runs, 10,000 loops each)
3.11 ms +- 502 us per loop (mean +- std. dev. of 7 runs, 100 loops each)
Break it on purpose

Make three cells: x = 1, then y = x + 1, then print(y). Run all three, then change the first cell to x = 100 without running it and run the third cell again. Then use Kernel > Restart & Run All. What does print(y) show each time, and why? (Solution B1.)

See it drawn
Four run orders, one notebook

The three cells of the worked example, executed with Python's exec the way a kernel does, in four different orders.

# A notebook's state is whatever the cells you ran, in the order you ran them, left behind.
cells = {1: "x = 10", 2: "x = x * 2", 3: "y = x + 1"}
def run(order):
    state = {}
    for c in order:
        exec(cells[c], {}, state)
    return state
for order in [(1, 2, 3), (1, 3), (1, 2, 2, 3), (1, 2, 3, 1)]:
    s = run(order)
    print(f"run cells {order}: x = {s['x']}, y = {s.get('y')}")
print("Same file, four different states: 'Restart and run all' is the only order a reader can reproduce.")
What you should see
run cells (1, 2, 3): x = 20, y = 21
run cells (1, 3): x = 10, y = 11
run cells (1, 2, 2, 3): x = 40, y = 41
run cells (1, 2, 3, 1): x = 10, y = 21
Same file, four different states: 'Restart and run all' is the only order a reader can reproduce.
Reading this output

The same three cells give four different states. The last line is the dangerous one: x=10 and y=21 can never both come from running the file top to bottom, yet nothing in the notebook shows it. That is why "Restart and run all" (or jupyter nbconvert --execute in CI) is the test that a notebook really works.

Step 5 · Display rich output inline

Notebooks auto-display the last expression in a cell. But you can control it:

import pandas as pd

df = pd.DataFrame({
    "model": ["Linear", "Random Forest", "Neural Net"],
    "accuracy": [0.72, 0.89, 0.94],
    "training_time": [0.1, 2.3, 45.6]
})
df
What you should see

           model  accuracy  training_time
0         Linear      0.72            0.1
1  Random Forest      0.89            2.3
2     Neural Net      0.94           45.6

This renders a formatted HTML table, not a text dump. Same with plots:

import matplotlib.pyplot as plt

plt.figure(figsize=(8, 4))
plt.plot([1, 2, 3, 4], [1, 4, 2, 3])
plt.title("Inline Plot")
plt.show()

The plot appears right below the cell. This is why notebooks dominate AI work. You see the data, the plot, and the code together.

The rule: explore in notebooks, ship in scripts.

A common workflow in AI: 1. Explore data in a notebook 2. Prototype your model in the notebook 3. Once it works, move the code to .py files 4. Import those .py files back into the notebook for further experiments

Common traps

Out-of-order execution. You run cell 5, then cell 2, then cell 7. The notebook works on your machine but breaks when someone runs it top to bottom. Fix: Kernel > Restart & Run All before sharing.

Hidden state. You delete a cell but the variable it created is still in memory. The notebook looks clean but depends on a ghost cell. Fix: Restart the kernel regularly.

Memory leaks. Loading a 4GB dataset, training a model, loading another dataset. Nothing gets freed. Fix: del variable_name and gc.collect(), or restart the kernel.

Recap
What to keep from this lesson
  • A notebook is cells plus a kernel that keeps state between them, in the order you ran them.
  • % and %% are Jupyter magics (%timeit, %%time, %env); ! runs a shell command.
  • The last expression in a cell is displayed: dataframes as tables, figures as plots.
  • Explore in notebooks, ship in scripts, and Restart & Run All before sharing.

Solutions

SolutionP1 · NumPy against a Python loop

Much slower: compare the two lines in the output above. The NumPy line is measured in microseconds and the list comprehension in milliseconds, about 20 times slower on this page's busy server and often 50 or more on a quiet laptop. The list comprehension calls a Python function 10,000 times. NumPy draws all 10,000 numbers in one call to compiled code, with no Python step per number. That gap is why AI code is written as operations on whole arrays.

SolutionB1 · State you can't see

After the edit, print(y) still prints 2: the kernel only knows the x = 1 you ran, and the new text in the first cell has not been executed. After Restart & Run All it prints 101, because every cell runs in page order on a fresh kernel. The notebook on screen and the state in memory had drifted apart; Restart & Run All puts them back together.

Industry practice
What's current (2024–2026)
  • Notebooks with assistants built in. Google Colab (Gemini), VS Code and JupyterLab extensions generate and fix cells from a prompt; review generated code as you would a colleague's.
  • Notebooks inside the data platform. Databricks, Snowflake and BigQuery notebooks run next to the warehouse, so analysis does not copy data to a laptop; they are the usual production notebook in enterprises.
  • Reactive notebooks. marimo stores notebooks as plain Python files and re-runs dependent cells automatically, avoiding the hidden-state problem of out-of-order execution; Jupyter (JupyterLab 4, Notebook 7) remains the standard format.

You diagnose Jupyter notebook problems. When someone describes an issue, identify the cause and give the fix.

Common issues and fixes:

**Kernel crashes:**
- Out of memory: The dataset or model is too large. Fix: reduce batch size, load data in chunks with `pd.read_csv(path, chunksize=10000)`, use `del variable` then `gc.collect()`, or switch to a machine with more RAM.
- Segfault from native library: Usually a version mismatch between numpy/torch/tensorflow and the system libraries. Fix: create a fresh virtual environment and reinstall.
- Kernel dies silently: Check the terminal where Jupyter is running for the actual error message. The notebook UI often hides it.

**Display problems:**
- Plots not showing: Add `%matplotlib inline` at the top of the notebook. If using JupyterLab, try `%matplotlib widget` for interactive plots (requires `ipympl`).
- DataFrame shows as text instead of HTML table: Make sure the dataframe is the last expression in the cell, not inside a `print()` call. `print(df)` gives text, just `df` gives the rich table.
- Images not rendering: Use `from IPython.display import Image, display` then `display(Image(filename="path.png"))`.
- LaTeX not rendering in markdown: Check for missing dollar signs. Inline: `$x^2$`. Block: `$$\sum_{i=0}^n x_i$$`.

**Memory issues:**
- Notebook uses too much RAM: Variables persist across all cells. Run `%who` to see all variables. Delete large ones with `del var_name` and run `import gc; gc.collect()`.
- Memory keeps growing: You are probably reassigning large variables without freeing the old ones. Restart the kernel (Kernel > Restart) to clear everything.
- Loading multiple large datasets: Use generators or chunked reading. `pd.read_csv(path, chunksize=N)` returns an iterator instead of loading everything at once.

**Execution issues:**
- Notebook works for me but not others: Cells were run out of order. Fix: Kernel > Restart & Run All. If it fails, you have a hidden dependency on a deleted or reordered cell.
- Cell runs forever (hanging): The code might be waiting for input (`input()`), stuck in an infinite loop, or blocked on a network request. Interrupt with Kernel > Interrupt (or press `I` twice in command mode).
- Import errors after pip install: The package installed in a different Python than the kernel is using. Fix: run `!pip install package` inside the notebook, or check `!which python` matches your environment.

**Colab-specific:**
- Session disconnected: Free Colab times out after 90 minutes of inactivity. Save work to Google Drive or download files.
- GPU not available: Runtime > Change runtime type > select GPU. If all GPUs are busy, try again later or use Colab Pro.
- Files disappeared: Colab wipes the filesystem between sessions. Mount Google Drive for persistent storage: `from google.colab import drive; drive.mount('/content/drive')`.

Diagnostic steps:
1. What is the exact error message? (Check both the notebook and the terminal)
2. Does the issue happen after restarting the kernel and running all cells top to bottom?
3. How much data are you loading? (`df.info()` for dataframes, `tensor.shape` and `tensor.dtype` for tensors)
4. What environment are you using? (Local JupyterLab, VS Code, Colab)
5. Were packages installed in the same environment as the kernel? (`!which python` and `import sys; sys.executable`)
