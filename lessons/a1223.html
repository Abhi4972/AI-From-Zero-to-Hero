In plain words first
The idea in one line

Traditional RAG parses PDFs into text, splits into chunks, embeds chunks, stores vectors. Every step loses signal: OCR drops chart data, chunking breaks table rows, text embeddings ignore figures. ColPali (Faysse et al., July 2024) asked the simpler question: why extract text at all? Embed the page image directly via PaliGemma, use ColBERT-style late interaction for retrieval, and keep all the layout, figures, fonts, and formatting signal the document carries. On its own benchmark, ViDoRe, ColPali scored 81.3 nDCG@5 against 67.0 for the best text pipeline; VisRAG, a related design, reported 20–40% better end-to-end answers than text RAG

Terms you'll hear
Term What people say What it actually means
Late interaction "ColBERT-style" Retrieval using per-token or per-patch embeddings + MaxSim, not a single doc vector
MaxSim "Max-over-patches" For each query token, pick the highest-similarity document token; sum across query
Bi-encoder "Single-vector" One vector per document; faster but loses granularity
Multi-vector "Many-vectors-per-doc" Store $N_p$ vectors per document / page; storage cost grows but recall improves
Patch embedding "Page feature" One vector per image patch from a VLM encoder, cached per page
ViDoRe "Vision doc bench" ColPali's benchmark suite for visual document retrieval
PQ quantization "Product quantization" Split each vector into sub-vectors and store a codebook index for each; shrinks storage many times at some cost in accuracy

The problem

In plain words first

The usual way to search PDFs (text RAG) first turns each page into text with OCR, cuts the text into chunks and stores one vector per chunk. Charts, table layout and badly scanned pages get lost on the way. ColPali skips the text step: a vision-language model looks at the page image and produces many small vectors, one per patch of the page. A question is also turned into one vector per word piece. Each word piece then finds its best-matching patch, and the page's score is the sum of those best matches. This is called late interaction, or MaxSim, from ColBERT. The price is storage, because each page has about a thousand vectors instead of one. This lesson explains ColBERT, ColPali and their relatives. It then runs a real 256M-parameter ColPali-family model (ColSmol) against OCR plus a text embedder on rendered pages, and measures how much pooling and binary quantization shrink the index. No model is trained.

Text-RAG on PDFs throws away most of the document. A financial report's Q3 revenue growth is usually in a chart; a medical report's findings are in annotated images; a legal contract's signature block is a layout fact, not a text fact.

The text-RAG pipeline:

  1. PDF → text via OCR / pdftotext.
  2. Text → 300-500 token chunks.
  3. Chunk → bi-encoder embedding (one vector).
  4. User query → embedding → cosine similarity → top-k chunks.
  5. Chunks + query → LLM.

Five lossy steps. Charts not captured. Tables broken across chunks. Multi-column layout flattens. Figure annotations disappear.

ColPali's fix: skip OCR, embed the page image directly. Use ColBERT-style late interaction for retrieval so the model can attend to fine-grained patches at query time.

Idea 1 · ColBERT (2020)

ColBERT (Khattab & Zaharia, arXiv:2004.12832) is a text retrieval method. Instead of one vector per document, it produces one vector per token. At query time:

  • Query tokens get their own embeddings (Nq​ vectors).
  • Document tokens get embeddings (Nd​ vectors, typically cached).
  • Score = sum over query tokens of max over document tokens of cosine similarity: ∑i​maxj​cos(qi​,dj​).

This is the MaxSim operation. Each query token "picks" its best-matching document token. The final score is the sum.

Pros: strong recall, handles term-level semantics. Cons: Nd​ vectors per document, storage expensive.

Idea 2 · ColPali

ColPali (Faysse et al., arXiv:2407.01449) applies the ColBERT pattern to images.

  • Each page is encoded by PaliGemma-3B at 448×448 pixels: SigLIP's 1,024 patch embeddings pass through the language model together with a short text prompt, and a linear layer projects every output to 128 dimensions. That is about 1,030 vectors per page (Np​).
  • Each user query (text) is encoded into query-token embeddings: Nq​ vectors.
  • Score = ∑i​maxj​cos(qi​,pj​), i.e., MaxSim over query-text-tokens and page-image-patches.
  • Retrieve top-k pages by total score.

At document-ingestion time: embed every page with PaliGemma, store all patch embeddings. At query time: embed the query tokens, compute MaxSim against all stored page embeddings, return top-k pages.

Pros: on ViDoRe, 81.3 nDCG@5 against 67.0 for the best text pipeline (OCR plus image captions, embedded with BGE-M3), and indexing needs no OCR or layout step. Each patch vector captures local layout and content.

Cons: storage. 1,030 vectors × 128 dimensions × 2 bytes is about 256 KB per page, against about 1.5 KB for one 768-dimensional vector in 16 bits. Mitigated by token pooling (merging similar vectors), quantization (int8 or binary) and compressed multi-vector indexes such as ColBERTv2's PLAID.

The same idea as a formula

Bi-encoder (one vector per page): s(q,d)=cos(eq​,ed​).

Late interaction (MaxSim). With unit vectors q1​,…,qNq​​ for the query and d1​,…,dNd​​ for the page:

s(q,d)=i=1∑Nq​​1≤j≤Nd​max​qi⊤​dj​.
Each query vector keeps only its best match; the page needs a good match for every part of the query, anywhere on it.

Cost per page: Nq​⋅Nd​ dot products of dimension D. Storage per page: Nd​⋅D⋅b bytes for b-byte values, or Nd​⋅D/8 bytes in binary (the sign of each dimension).

Token pooling replaces the Nd​ page vectors by Nd​/f cluster means (pool factor f), with no retraining.

nDCG@5, ViDoRe's metric, for one relevant page found at rank r:

nDCG@5={1/log2​(r+1)0​r≤5r>5.​

Worked example
MaxSim by hand, and what it costs
  • A 3-vector query against page A: best matches 0.9, 0.2, 0.3, so s=1.4. Against page B: 0.5, 0.5, 0.5, so s=1.5. B wins: it matches every part of the query moderately, while A matches one part very well and misses the rest.
  • ColPali page: 1,030×128×2 bytes =263,680 bytes, about 256 KB. In binary: 1,030×16=16,480 bytes, about 16 KB.
  • A 20-vector query against a 1,135-vector ColSmol page: 20×1,135=22,700 dot products of 128 dimensions, about 2.9M multiply-adds. A bi-encoder with 384 dimensions needs 384: about 7,600 times less.
  • nDCG@5 if the right page comes 1st: 1. 3rd: 1/log2​4=0.5. 6th: 0.
Check your mental model
  • ✗ "ColPali runs OCR and embeds the text."
    ✓ It embeds the page image; there is no OCR step anywhere.
  • ✗ "MaxSim averages the similarity of all patches."
    ✓ Each query vector takes only its single best patch; the page score is the sum of those maxima.
  • ✗ "Shrinking a multi-vector index needs a new model."
    ✓ Token pooling and binary quantization are applied at indexing time, to the same vectors.
  • ✗ "Vision retrieval replaces the generator."
    ✓ It returns pages; a VLM still has to read them to answer.

Vision retrieval against OCR plus text retrieval

Ten pages are rendered with Pillow: a bar chart, tables, notices, invoices, a roadmap and four look-alike distractors. One page is degraded like a bad scan. Text RAG reads each page with Tesseract and embeds the text with bge-small (one vector per page). Vision RAG embeds each page image with ColSmol-256M (vidore/colSmol-256M, about 0.5 GB, loaded with Sentence Transformers' MultiVectorEncoder) and scores with MaxSim. About a minute and a half on a 2-core CPU.

import time
import numpy as np, torch, pytesseract
from PIL import Image, ImageDraw, ImageFont, ImageFilter
from sentence_transformers import MultiVectorEncoder, SentenceTransformer

F = "/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf"
font = lambda s: ImageFont.truetype(F, s)

def page(title, lines=(), table=(), bars=(), boxes=()):
    im = Image.new("RGB", (850, 1100), "white"); d = ImageDraw.Draw(im)
    d.text((60, 60), title, font=font(38), fill="black")
    for i, l in enumerate(lines):
        d.text((60, 170 + 44 * i), l, font=font(28), fill="black")
    for i, (k, v) in enumerate(table):
        d.text((80, 180 + 60 * i), k, font=font(28), fill="black"); d.text((520, 180 + 60 * i), v, font=font(28), fill="black")
        d.line((60, 225 + 60 * i, 790, 225 + 60 * i), fill="gray")
    for i, (label, v) in enumerate(bars):          # values only as bar heights
        x = 110 + i * 170
        d.rectangle((x, 900 - v * 10, x + 100, 900), fill=(40, 90, 160))
        d.text((x + 5, 915), label, font=font(24), fill="black")
    for i, b in enumerate(boxes):
        d.rectangle((60, 180 + 170 * i, 790, 300 + 170 * i), outline="black", width=3)
        d.text((90, 220 + 170 * i), b, font=font(32), fill="black")
    return im

def bad_scan(im, seed=0):                          # skewed, blurred, noisy: OCR gives up (Lesson 12.22)
    im = im.convert("L").rotate(3, expand=True, fillcolor=255).filter(ImageFilter.GaussianBlur(1))
    a = np.asarray(im, float) + np.random.default_rng(seed).normal(0, 40, (im.size[1], im.size[0]))
    return Image.fromarray(np.clip(a, 0, 255).astype(np.uint8)).convert("RGB")

pages = [  # pages 0-5 answer the queries; 6-9 are look-alike distractors
    page("Quarterly revenue by region", bars=(("North", 42), ("South", 18), ("East", 65), ("West", 31))),
    page("Headcount by department", table=(("Department", "People"), ("Engineering", "120"), ("Sales", "45"), ("Finance", "12"))),
    page("Office relocation notice", lines=("From 1 June our London team moves to", "8 Dock Street, Canary Wharf.",
                                            "The old building closes on 31 May.")),
    bad_scan(page("Fire evacuation procedure", lines=("When the alarm sounds, leave by the", "nearest exit. Do not use the lifts.",
                                                      "Meet at the assembly point in the car park."))),
    page("Invoice INV-2026-0042", lines=("Bill to: Northwind Garden Supplies", "Cordless drill x3    $567.00", "Total due            $1,022.40")),
    page("Product roadmap 2026", boxes=("Q1: Mobile app", "Q2: Offline mode", "Q3: Single sign-on")),
    page("Quarterly revenue by product", bars=(("Drills", 50), ("Saws", 22), ("Gloves", 9), ("Bits", 35))),
    page("Fire extinguisher inspection log", table=(("Floor", "Last checked"), ("Ground", "3 Feb"), ("First", "3 Feb"), ("Second", "4 Feb"))),
    page("Invoice INV-2026-0043", lines=("Bill to: Contoso Builders", "Safety gloves x40    $250.00", "Total due            $300.00")),
    page("Headcount plan 2027", table=(("Department", "Target"), ("Engineering", "150"), ("Sales", "60"), ("Finance", "14"))),
]
queries = ["which region brought in the most revenue", "how many engineers do we have now",
           "new office address after the move", "what to do when the fire alarm sounds",
           "amount due for Northwind Garden Supplies", "when will single sign-on ship"]

# Text RAG: OCR every page, one bge-small vector per page.
ocr = [pytesseract.image_to_string(p) for p in pages]
bge = SentenceTransformer("BAAI/bge-small-en-v1.5", device="cpu")
P = bge.encode(ocr, normalize_embeddings=True)
Q = bge.encode(["Represent this sentence for searching relevant passages: " + q for q in queries], normalize_embeddings=True)
text_scores = Q @ P.T

# Vision RAG: ColSmol-256M embeds each page image as many 128-d vectors; MaxSim scores them.
t0 = time.time()
col = MultiVectorEncoder("vidore/colSmol-256M", device="cpu")
doc_emb = col.encode_document(pages, batch_size=1)      # one page at a time keeps memory low
q_emb = col.encode_query(queries)
vis_scores = col.similarity(q_emb, doc_emb).float().numpy()
print(f"ColSmol-256M: {len(pages)} pages, {tuple(doc_emb[0].shape)} vectors each; "
      f"query 0 -> {tuple(q_emb[0].shape)}; {time.time() - t0:.0f} s on CPU")
print(f"OCR words per page: {[len(t.split()) for t in ocr]}")

rank = lambda s, i: int((s[i] > s[i][i]).sum()) + 1
top = lambda s, i: int(np.argmax(s[i]))
print(f"\n{'query':<42}{'OCR+bge':>8}{'ColSmol':>9}   rank of the right page (top pick if wrong)")
for i, q in enumerate(queries):
    rt, rv = rank(text_scores, i), rank(vis_scores, i)
    note = lambda r, s: f"{r}" if r == 1 else f"{r} (p{top(s, i)})"
    print(f"{q:<42}{note(rt, text_scores):>8}{note(rv, vis_scores):>9}")
for name, s in (("OCR+bge", text_scores), ("ColSmol", vis_scores)):
    r = [rank(s, i) for i in range(len(queries))]
    print(f"{name:<8} recall@1 {np.mean([x == 1 for x in r]):.0%}   MRR {np.mean([1 / x for x in r]):.2f}")

Each page becomes 1,135 vectors. ColSmol turns every 850×1100 page into 1,135 vectors of 128 dimensions (image tiles plus a short prompt), and a short question into about 20. Indexing 10 pages took a little over a minute on a 2-core CPU, so a laptop can index a few thousand pages an hour; a GPU is much faster.

OCR reads nothing from the bad scan. Tesseract finds 8 to 23 words on each clean page and 0 on the degraded fire-evacuation page. Text RAG cannot retrieve a page whose text it never saw. Its top pick for the fire question is page 7, the clean "Fire extinguisher inspection log", which shares the word "fire". The right page comes third.

The image retriever still finds it. ColSmol ranks the degraded page first: blurred, rotated and noisy text is still recognisable as an evacuation notice to a model that looks at the pixels.

Neither fell for the other distractors. "How many engineers do we have now" picked the current headcount over the 2027 plan, and the Northwind invoice over the Contoso one, in both systems. Clean, short pages are easy for text RAG too; the gap opens where text extraction fails.

Ten pages prove the mechanism, not the size of the gain. Use a benchmark such as ViDoRe, or better your own pages and questions, to measure how much vision retrieval helps.

Shrinking the index without retraining

This block continues from the one above and reuses its page and query vectors. It stores the real ColSmol vectors in float32, bf16 and binary form, and pools them by Ward clustering at factors 2, 3 and 4. For each version it checks whether the right pages still rank first and how closely the scores follow the uncompressed ones. Then it scales the storage to a million pages. A few seconds.

# Continues from the block above: pages, queries, doc_emb, q_emb and vis_scores are already defined.
import numpy as np, torch
from scipy.cluster.hierarchy import linkage, fcluster

D = [e.float().numpy() for e in doc_emb]                 # one (n_vectors, 128) array per page, unit length
Qv = [q.float().numpy() for q in q_emb]

def maxsim(q, d):                                        # sum over query vectors of the best page vector
    return (q @ d.T).max(axis=1).sum()

def evaluate(docs, qs=Qv, sim=maxsim):
    S = np.array([[sim(q, d) for d in docs] for q in qs])
    ranks = [int((S[i] > S[i][i]).sum()) + 1 for i in range(len(qs))]
    return S, ranks

def pool(d, factor):                                     # token pooling: Ward clustering, then cluster means
    labels = fcluster(linkage(d, "ward"), t=max(1, len(d) // factor), criterion="maxclust")
    m = np.stack([d[labels == c].mean(0) for c in np.unique(labels)])
    return m / np.linalg.norm(m, axis=1, keepdims=True)

def binary_sim(q, d):                                    # 1 bit per dimension: sign agreement
    return ((np.sign(q) @ np.sign(d).T) / q.shape[1]).max(axis=1).sum()

full, r_full = evaluate(D)
n = D[0].shape[0]
print(f"one page: {n} vectors x 128 dims")
print(f"\n{'index':<28}{'bytes/page':>11}{'vectors':>9}{'right page ranks':>22}{'score corr.':>12}")
rows = [("float32", D, maxsim, 4 * 128), ("bfloat16", D, maxsim, 2 * 128), ("binary (1 bit/dim)", D, binary_sim, 16)]
for f in (2, 3, 4):
    rows.append((f"bf16, pooled x{f}", [pool(d, f) for d in D], maxsim, 2 * 128))
rows.append(("binary, pooled x3", [pool(d, 3) for d in D], binary_sim, 16))
for name, docs, sim, bytes_per_vec in rows:
    S, r = evaluate(docs, sim=sim)
    nv = np.mean([len(d) for d in docs])
    corr = np.corrcoef(S.ravel(), full.ravel())[0, 1]
    print(f"{name:<28}{nv * bytes_per_vec:>11,.0f}{nv:>9.0f}{str(r):>22}{corr:>12.3f}")

# What a million pages would need, and what brute-force MaxSim would cost per query.
pages_n, nq = 1_000_000, Qv[0].shape[0]
print(f"\nfor {pages_n:,} pages:")
for name, per_page in (("one 384-d float32 vector per page (bge-small)", 384 * 4),
                       ("one 2,304-d 16-bit vector per page (VisRAG)", 2304 * 2),
                       ("ColSmol, bfloat16", n * 128 * 2), ("ColSmol, binary", n * 16),
                       ("ColSmol, binary, pooled x3", n / 3 * 16)):
    print(f"  {name:<48}{per_page * pages_n / 1e9:>8.1f} GB")
flops = 2 * nq * n * 128 * pages_n
print(f"brute-force MaxSim, one {nq}-vector query: {flops / 1e12:.1f} TFLOP "
      f"(about {flops / 1e11:.0f} s at 100 GFLOP/s on a laptop CPU)")

Reading this output

Binary vectors keep the ranking. Storing only the sign of each dimension cuts a page from 290,560 bytes (bf16) to 18,160, 16 times less. All six right pages still rank first, and the scores correlate 0.956 with the full ones.

Pooling barely moves the scores. Merging similar vectors by Ward clustering keeps the correlation at 0.999 or more even at factor 4 (283 vectors per page). Neighbouring patches of a page, such as blank margin or a run of text, carry nearly the same vector, so their mean loses little.

Together: 48 times smaller. Binary plus pooling at factor 3 stores a page in 6,048 bytes, with correlation 0.948 and every right page still first. On a small, easy set every method ranks perfectly; on a real corpus, measure the recall loss before choosing a setting.

At a million pages, storage and compute decide the design. bf16 ColSmol vectors need about 290 GB, binary 18 GB, binary and pooled 6 GB, against 1.5 GB for one bge-small vector per page. Brute-force MaxSim over a million pages is about 5.8 trillion operations per query, roughly a minute on a laptop CPU. So large systems first find a few hundred candidate pages cheaply, then score only those with MaxSim.

Idea 3 · ColQwen2 and ColSmol

ColQwen2 (illuin-tech, 2024) swaps PaliGemma for Qwen2-VL-2B with dynamic resolution, so the number of vectors follows the page's size and shape; it scores higher on ViDoRe. ColQwen2.5 followed in 2025.

ColSmol is the smaller-scale variant for local / edge use: built on SmolVLM-256M or -500M with LoRA adapters, trained on the same 127k query-page pairs. The 256M version runs on a laptop CPU (measured below).

Idea 4 · VisRAG

VisRAG (Yu et al., arXiv:2410.10594) is a different variant: it pools each page into a single 2,304-dimensional vector (about 4.5 KB) from MiniCPM-V 2.0, by position-weighted mean pooling, and retrieves with ordinary cosine search. Its paper reports in-domain MRR@10 of 77.9 against 76.5 for ColPali, and 20–40% better end-to-end answers than text-based RAG.

The trade-off: many vectors per page for fine-grained matching, one vector per page for cheap search at scale. Which one wins on quality depends on the documents and the queries; test both on your own pages.

Idea 5 · M3DocRAG

M3DocRAG (Cho et al., arXiv:2411.04952) extends multi-modal retrieval to multi-page multi-document reasoning. ColPali retrieves pages across documents (its M3DocVQA benchmark has 3,368 PDFs with 41,005 pages), and Qwen2-VL 7B answers from up to 4 retrieved page images. An inverted-file index (Faiss IVF) cut retrieval from 21 s to 1.8 s per query over those 40k pages.

Idea 6 · ViDoRe — the benchmark

ColPali's companion benchmark. Visual Document Retrieval Evaluation. Its tasks reuse academic visual QA sets (DocVQA, InfoVQA, TAT-DQA, ArxivQA, TabFQuAD) and add practical topics (energy, government reports, healthcare, AI, sustainability). Metric: nDCG@5.

ColPali scored 81.3 average nDCG@5 on ViDoRe; the best text pipeline scored 67.0, and OCR with BM25 65.5. ViDoRe V2 (2025) added longer, harder queries over larger document sets, on which all scores are much lower.

Idea 7 · The end-to-end RAG pipeline

For a vision-native RAG:

  1. Ingest: PDF → page images → PaliGemma encoding → store all patch embeddings.
  2. Query: user text → query-token embeddings → MaxSim against all indexed pages → top-k pages.
  3. Generate: top-k page images + query → VLM (Qwen2.5-VL or Claude) → answer.

No OCR anywhere. Figures, charts, fonts, layout all flow into the answer.

Idea 8 · Storage math

A 50-page financial report with ColPali's 1,030 vectors per page and 128-dim embeddings:

  • ColPali: 50 × 1,030 × 128 × 2 bytes (bf16) ≈ 13 MB; with binary quantization (1 bit per dimension) about 0.8 MB.
  • Text-RAG: 50 chunks * 768-dim * 4 bytes = ~150 kB.

ColPali in bf16 takes about 86 times the storage of the float32 text vectors. Binary quantization plus token pooling at factor 3 brings it to under 2 times (measured on real ColSmol vectors below), usually tolerable.

Idea 9 · When text-RAG still wins

  • Pure-text documents with no layout signal (wiki articles, chat logs). Text-RAG is simpler and storage-cheaper.
  • Multi-million-page archives where storage dominates cost.
  • Strict regulatory requirements demanding extractable OCR text alongside the retrieval.

For visually rich documents (financial reports, scientific papers, slides, manuals, scanned forms), vision-native retrieval tends to win in 2026; measure it on your own pages.

Break it on purpose

A team indexes one million pages with a ColPali-family model, stores every vector in bf16 and scores each query with brute-force MaxSim over all pages. What happens to memory and latency, and how do production systems avoid it? (Solution B1.)

Industry practice
What's current (2024–2026)
  • ColPali-family retrievers are used in production document search: ColQwen2 (2B, fits an 8 GB laptop GPU in bf16) and ColQwen2.5 (3B, more comfortable in 8-bit on such a card) for quality, ColSmol (256M and 500M) for CPUs and edge devices. They load through the colpali-engine library or Sentence Transformers' MultiVectorEncoder, as above.
  • Vector databases with multi-vector fields: Vespa, Qdrant and Weaviate can store several vectors per document and score them with MaxSim, usually as a reranking stage after a cheaper first search.
  • Index compression: token pooling (about a third of the vectors at factor 3, no retraining) and binary quantization are standard ways to cut multi-vector storage.
  • Single-vector alternatives: VisRAG-style pooled page vectors and hosted multimodal embedding APIs (such as Cohere Embed v4 and Voyage's multimodal models) embed a page image as one vector, at a fraction of the storage.
  • Harder benchmarks: ViDoRe V2 (2025) uses longer, more realistic queries over larger document sets; retrieval scores there are far below V1's.

Sources: ColPali (arXiv 2407.01449), VisRAG (arXiv 2410.10594), M3DocRAG (arXiv 2411.04952), token pooling (Answer.AI), ViDoRe V2, colSmol-256M model card, illuin-tech/colpali.

Recap
What to keep from this lesson
  • Text RAG loses charts, layout and badly scanned pages before retrieval even starts.
  • ColPali embeds the page image as about a thousand patch vectors; no OCR.
  • MaxSim: each query vector takes its best patch; the page score is the sum.
  • Multi-vector indexes are large; pooling and binary quantization shrink them a lot.
  • Single-vector page embeddings (VisRAG) trade fine matching for cheap search.
  • Retrieval finds pages; a VLM reads them to answer.

6. Migration path from text-RAG. How to A/B, when to fully cutover.

Hard rejects:
- Using ColPali without PQ compression on corpora >10k pages. Storage explodes.
- Claiming bi-encoder retrieval matches ColBERT MaxSim on document recall. It does not on ViDoRe.
- Recommending text-RAG for charts + tables workloads. Text-RAG loses most of the signal.

Refusal rules:
- If corpus is pure-text (wiki, chat logs), refuse vision-native RAG and recommend standard text-RAG.
- If retrieval SLA <100ms, prefer VisRAG (bi-encoder) over ColPali MaxSim.
- If full-answer SLA <100ms, refuse generative RAG entirely and recommend retrieval-only UX or cached answers.
- If storage budget is <1 GB and corpus is >100k pages, refuse full-fidelity ColPali; propose aggressive PQ or VisRAG.

Solutions

SolutionP1 · Only the image retriever finds the bad scan

Only ColSmol. Tesseract read 0 words from the bad scan, so the text retriever had nothing to match and put the clean "Fire extinguisher inspection log" first; the right page came third. ColSmol, which embeds the pixels, ranked the scanned page first.

Neither fell for the other distractors: the current headcount beat the 2027 plan and the Northwind invoice beat the Contoso one in both systems. Clean, short text pages are easy for text RAG too. The gap appears where text extraction fails: bad scans, charts with no text values, layout that carries meaning. That is ColPali's argument, and why you should measure on your own documents before choosing.

SolutionB1 · Hundreds of gigabytes and a minute per query

Memory: at about 1,135 vectors per page, 128 dimensions and 2 bytes, a million pages need about 290 GB of vectors (ColPali's 1,030 vectors: about 260 GB). That does not fit in RAM on one ordinary server, let alone a laptop. Latency: brute-force MaxSim compares every query vector with every page vector, about 5.8 trillion operations for a 20-vector query, around a minute on a CPU and still noticeable on a GPU. Every query also has to stream the whole index through memory.

Production systems split the work:

  • Shrink the index: binary quantization (16 times smaller) and token pooling (about 3 times at factor 3) cut 290 GB to about 6 GB, with little loss in this lesson's run; check recall on your data.
  • Retrieve candidates cheaply, then rerank: a first stage finds a few hundred likely pages with an approximate index (inverted-file clustering as in M3DocRAG, which cut 21 s to 1.8 s per query over 40k pages; PLAID-style centroid search; or one pooled vector per page). Full MaxSim scores only those candidates.
  • Use a database built for it: Vespa, Qdrant and Weaviate store multi-vector fields and run MaxSim as a reranking step.
