In plain words first
The idea in one line

A modern MCP server does not remember a handshake. It validates the metadata on every request, runs one handler, and returns one typed result.

Terms you'll hear
Term Meaning
Stateless server Handles each request from its own metadata without protocol-session memory
server/discover Mandatory modern method that advertises versions and capabilities
Complete result Successful modern result with resultType: "complete"
Cacheable result Discovery, list, or resource-read result with ttlMs and cacheScope
Deterministic list Same logical registry produces the same item order
Server identity Recommended io.modelcontextprotocol/serverInfo in result _meta
Tool error Valid tool call that returns content with isError: true
Protocol error Invalid JSON-RPC or MCP request returned through error

The problem

In plain words first

An MCP server is a small program that answers a few kinds of requests: list your tools, call a tool, list your resources, read one, list your prompts, render one, and server/discover. In modern MCP each request arrives complete with its own version and capabilities, so the server's main loop is simple. It reads one message, checks it, handles it, and writes one reply. Every successful reply is marked resultType: "complete" and names the server. List replies also say how long they may be cached. This lesson builds that server. It first writes it in a few lines with the official Python SDK and inspects what the SDK generates (schemas, annotations, cache hints). It then runs an interoperability test: the official SDK client talks to the lesson's own hand-written, standard-library server.

A server that stores client capabilities after the first message is easy to build and hard to operate. The same process may serve sequential clients. A remote request may land on a different worker. A stale capability declaration can leak behavior across authorization boundaries.

MCP 2026-07-28 solves the protocol part of that problem by making every request self-describing. Your application can still keep durable notes, jobs, or explicit state handles. What it cannot keep is hidden protocol state that changes how a later request is decoded.

This lesson builds a notes server twice. The Python and TypeScript versions use only their standard libraries for the protocol core. Both expose the same methods and enforce the same wire contract.

Idea 1 · The modern dispatch loop

read one JSON-RPC line
parse the envelope
if it is a notification, do not respond
validate params._meta for this request
route by method
wrap success with resultType and serverInfo
write one JSON-RPC response line
forget request-scoped metadata

Three stdio rules still matter:

  • Write only JSON-RPC messages to stdout. Send diagnostics to stderr.
  • Delimit messages with a newline and flush each response.
  • Exit promptly when stdin reaches EOF.

The process lifetime is a transport lifetime. It is not a modern MCP session.

Idea 2 · Request validation

Every request must have:

{
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "notes-client",
        "version": "1.0.0"
      }
    }
  }
}

The first two fields are required. clientInfo is recommended. Validate a present identity shape, but do not treat it as authentication.

If the version is unsupported, return code -32022 with requested and supported. Missing request metadata is invalid params, code -32602. Never fill missing fields from a previous call.

Idea 3 · Mandatory discovery

Modern servers must implement server/discover. A complete discovery result includes supported modern versions, capabilities, optional instructions, cache hints, and server identity in result _meta:

{
  "resultType": "complete",
  "supportedVersions": ["2026-07-28"],
  "capabilities": {
    "tools": {"listChanged": false},
    "resources": {"listChanged": false, "subscribe": false},
    "prompts": {"listChanged": false}
  },
  "ttlMs": 3600000,
  "cacheScope": "public",
  "_meta": {
    "io.modelcontextprotocol/serverInfo": {
      "name": "notes-server",
      "version": "2.0.0"
    }
  }
}

Discovery does not unlock the server. A client may call tools/list without calling discovery because tools/list already carries the same request metadata.

Idea 4 · Tools

tools/list returns a deterministic list of tool descriptors. Stable ordering improves response caching and keeps model context stable. The result also requires ttlMs and cacheScope.

tools/call returns content blocks and isError. Use a JSON-RPC error when the protocol envelope or method parameters are invalid. Use isError: true when a valid tool invocation runs but the tool itself fails.

Tool annotations remain hints, not enforcement:

  • readOnlyHint
  • destructiveHint
  • idempotentHint
  • openWorldHint

The host should use them for confirmation and presentation. The server must still enforce real authorization.

Idea 5 · Resources

resources/list returns stable URI descriptors. resources/read returns typed contents. Both are cacheable in 2026-07-28, so both include ttlMs and cacheScope.

Use cacheScope: "private" for user-specific note data. A shared cache must not reuse a private response across authorization contexts.

Modern change delivery does not use resources/subscribe. A client opens subscriptions/listen and requests resourceSubscriptions or list-change categories. Lesson 13.12 builds that flow.

Idea 6 · Prompts

prompts/list is cacheable and deterministic. prompts/get renders a named prompt with arguments. The rendered prompt result is complete, but it is not one of the cacheable list or read results that requires cache hints.

Idea 7 · Every successful result is typed

The examples use one wrapper for every success:

def complete(payload):
    return {
        "resultType": "complete",
        **payload,
        "_meta": {SERVER_INFO_KEY: SERVER_INFO},
    }

List, read, and discovery handlers add ttlMs plus cacheScope. Centralizing this wrapper prevents one handler from silently omitting modern result fields.

The same idea as a formula

One wrapper for every success. For a handler h and a request r:

reply(r)=complete(h(r))=h(r)∪{resultType:"complete", _meta.serverInfo}∪only for discover, lists and reads{ttlMs,cacheScope}​​.

Deterministic lists. If a list handler returns L(R) for registry R, then for any reordering π(R) of the same items,

L(π(R))=L(R),
so equal registries give byte-identical replies and identical cache keys. Sorting by name, or keeping a fixed definition order, both satisfy it.

Annotations are hints. With ro = readOnlyHint and d = destructiveHint, a host might ask for confirmation when ¬ro∨d; the server still authorises every call whatever the hints say.

Worked example
Cache hints and annotations for the notes server
  • tools/list marked ttlMs: 3600000, cacheScope: public: the tool list is the same for every user and changes only on deploy, so any client or gateway may reuse it for an hour.
  • resources/read marked ttlMs: 0, cacheScope: private: note bodies belong to one user and change at any time, so nothing is reused.
  • notes_search is readOnlyHint: true: a host can run it without asking. notes_create is not read-only (but not destructive): a cautious host asks once. A notes_delete would be destructiveHint: true, and should also check authorization inside its executor.
Check your mental model
  • ✗ "The server keeps a session per client after discovery."
    ✓ Discovery is optional and unlocks nothing; every request is checked on its own.
  • ✗ "destructiveHint: false means the server allows the call."
    ✓ Annotations guide the host's UI; the server must still authorise.
  • ✗ "Any successful reply needs ttlMs and cacheScope."
    ✓ Only discovery, the list methods and resources/read; tools/call and prompts/get do not.
  • ✗ "Printing debug output is harmless."
    ✓ On stdio, stdout carries the protocol; debug text there corrupts the stream. Use stderr.

See it drawn
The notes server with the official SDK

MCPServer from the MCP Python SDK 2.x, with tool annotations, a notes://{note_id} resource template, a prompt, and server-wide cache hints. The SDK's Client connects in-process (the same protocol, no subprocess) and exercises every primitive. About a second.

import asyncio, json
from mcp import Client
from mcp.server import MCPServer
from mcp.server.caching import CacheHint
from mcp.types import ToolAnnotations

# The lesson's notes server, written with the official SDK instead of by hand.
NOTES = {"n1": "Buy A4 paper", "n2": "Call Priya about the invoice"}
mcp = MCPServer("notes-server", version="2.0.0",
                instructions="Use tools for note actions, resources for note bodies, prompts for reviews.",
                cache_hints={"tools/list": CacheHint(ttl_ms=3_600_000, scope="public"),
                             "resources/read": CacheHint(ttl_ms=0, scope="private")})

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=True))
def notes_search(query: str) -> list[str]:
    """Use when the user wants notes containing a word. Do not use to create notes."""
    return sorted(k for k, t in NOTES.items() if query.lower() in t.lower())

@mcp.tool(annotations=ToolAnnotations(readOnlyHint=False, destructiveHint=False, idempotentHint=False))
def notes_create(text: str) -> str:
    """Use when the user wants to save a new note."""
    key = f"n{len(NOTES) + 1}"; NOTES[key] = text
    return key

@mcp.resource("notes://{note_id}", mime_type="text/plain")
def note_body(note_id: str) -> str:
    """The full text of one note."""
    return NOTES[note_id]

@mcp.prompt()
def review_notes(topic: str) -> str:
    """Ask the model to review all notes about a topic."""
    return f"Review my notes about {topic} and list open actions."

async def main():
    async with Client(mcp) as c:                       # in-process: the same protocol, no subprocess
        print("negotiated:", c.protocol_version, "| server:", c.server_info.name, c.server_info.version)
        tools = await c.list_tools()
        print(f"\ntools/list  ttlMs={tools.ttl_ms} cacheScope={tools.cache_scope}")
        for t in tools.tools:
            a = t.annotations
            print(f"  {t.name:<14} readOnly={a.read_only_hint} destructive={a.destructive_hint} "
                  f"input={json.dumps(t.input_schema['properties'])} output={json.dumps(t.output_schema)[:60]}")
        r = await c.call_tool("notes_search", {"query": "priya"})
        print(f"\ntools/call notes_search -> {r.structured_content}  isError={r.is_error}")
        r = await c.call_tool("notes_create", {"text": "Order toner"})
        print(f"tools/call notes_create -> {r.structured_content}")
        tmpl = await c.list_resource_templates()
        print(f"\nresource templates: {[t.uri_template for t in tmpl.resource_templates]}")
        body = await c.read_resource("notes://n2")
        print(f"resources/read notes://n2 -> {body.contents[0].text!r}  ttlMs={body.ttl_ms} cacheScope={body.cache_scope}")
        p = await c.get_prompt("review_notes", {"topic": "invoices"})
        print(f"\nprompts/get review_notes -> [{p.messages[0].role}] {p.messages[0].content.text}")

asyncio.run(main())

Reading this output

The SDK negotiated 2026-07-28 and named the server (notes-server 2.0.0), with no handshake code in the server.

Schemas came from the type hints. query: str became {"type": "string"} in the input schema, and the return type list[str] produced an output schema ({"result": {"items": {"type": "string"}}}), so each call also returns structuredContent: {'result': ['n2']} for the search, {'result': 'n3'} for the new note. The docstrings became the descriptions the model reads.

Interop: the SDK client against the hand-written server

The lesson's own server in code/main.py uses only the standard library. Here the official SDK client launches it over stdio and lists tools, resources and prompts, calls a tool, and makes two bad calls. If a hand-written server passes this, it speaks the same protocol as the reference implementation. About 2 seconds.

# Interop test: the official SDK client talks to this lesson's hand-written, stdlib-only server (code/main.py).
import asyncio, pathlib, sys
from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client

SERVER = pathlib.Path("main.py")                    # the lesson's code/main.py (run from the code folder)

async def main():
    params = StdioServerParameters(command=sys.executable, args=[str(SERVER)])
    async with Client(stdio_client(params, errlog=sys.__stderr__)) as c:   # server stderr -> real stderr
        print("SDK client -> stdlib server:", c.protocol_version, "|", c.server_info.name, c.server_info.version)
        tools = await c.list_tools()
        print("tools:", [t.name for t in tools.tools], f"ttlMs={tools.ttl_ms} cacheScope={tools.cache_scope}")
        res = await c.list_resources()
        print("resources:", [str(r.uri) for r in res.resources])
        prompts = await c.list_prompts()
        print("prompts:", [p.name for p in prompts.prompts])
        r = await c.call_tool("notes_list", {})
        print(f"call notes_list -> isError={r.is_error} {r.content[0].text[:110]!r}")
        r = await c.call_tool("notes_create", {})
        print(f"call notes_create with no arguments -> isError={r.is_error} {r.content[0].text!r}")
        bad = await c.call_tool("notes_missing", {})
        print(f"call notes_missing -> isError={bad.is_error} {bad.content[0].text[:80]!r}")

asyncio.run(main())

Idea 8 · No server-initiated requests

A modern server may send notifications related to a client request, or notifications on a client-opened subscriptions/listen stream. It must not send its own JSON-RPC request.

When a handler needs sampling, elicitation, or roots input, it returns an input_required result. The client fulfills the embedded input requests and retries the original method with a new request id. Lesson 13.13 covers that Multi Round-Trip Request pattern.

Idea 9 · Explicit legacy compatibility

A dual-era server may also implement the 2025-11-25 handshake on a clearly separate legacy branch. It chooses modern behavior when required modern _meta fields are present and legacy behavior when it receives initialize.

Do not put a 2026-07-28 request through the legacy handshake path. Do not stamp modern resultType fields onto legacy initialization results. The code in this lesson is deliberately modern-only so its invariants stay visible.

Industry practice
What's current (2024–2026)
  • Official SDKs generate most of a server for you: the Python SDK 2.x (MCPServer, decorators for tools, resources and prompts, cache_hints), TypeScript, Go, Java, Kotlin, C#, Rust and others, all serving MCP 2026-07-28 and 2025-era clients.
  • Higher-level frameworks: FastMCP (the independent project), and server support inside agent frameworks, add auth, middleware and deployment helpers.
  • Conformance and interop testing: run your server against the official clients and the MCP Inspector, as the second run does here, before publishing it (Lesson 13.36).
  • Deployment: stdio for local tools launched by the client; Streamable HTTP for remote servers (Lesson 13.10), where statelessness lets any worker serve any request.

Recap
What to keep from this lesson
  • Read one message, validate its _meta, route, wrap, reply, forget.
  • server/discover is mandatory; it advertises versions and capabilities but gates nothing.
  • Every success has resultType and server identity; lists and reads add cache hints.
  • Lists come back in a deterministic order.
  • Tool annotations are hints; authorization happens in the server.
  • On stdio, stdout is for protocol messages only.

Given a domain, produce a modern MCP server plan. Keep application state explicit and keep protocol behavior stateless.

Produce:

1. Primitive split. Define atomic tools, URI-addressed resources, and useful prompts. Omit a primitive when the domain has no honest use for it.
2. Discovery result. Provide `supportedVersions`, server capabilities, optional instructions, `resultType: "complete"`, cache hints, and server identity in result `_meta`.
3. Request validator. Require protocol version and client capabilities in every `params._meta`. Validate recommended client identity when present. Return `-32022` with requested and supported versions on a mismatch.
4. Result wrapper. Add `resultType: "complete"` and server identity to every success. Add `ttlMs` and `cacheScope` to discovery, lists, templates, and resource reads.
5. Ordering policy. Define a stable sort key for every list response.
6. State policy. Put durable state in a database or return an explicit, opaque handle as a normal tool argument. Never hide state in a protocol session.
7. Compatibility boundary. If legacy support is required, isolate a `2025-11-25` initialize adapter. Select it only for legacy traffic and test both eras independently.

Hard rejects:

- A modern server whose first valid method must be `initialize`.
- Reusing capabilities, identity, or version from an earlier request.
- Returning `Mcp-Session-Id` on modern HTTP traffic.
- Returning list or resource-read results without cache hints.
- Treating annotations as authorization controls.
- Sending an independent JSON-RPC request from the server.

Refusal rules:

- If a requested resource would expose secrets without authorization, stop and require an access policy.
- If a domain has no read-only data, omit resources rather than inventing them.
- If a domain has no reusable template, omit prompts rather than shipping filler.

Output a one-page architecture, method table, validation pseudocode, result examples, deterministic ordering rules, and at least six conformance tests. End with the boundary between application state and protocol state.

Exercises

  1. Remove capabilities from one request and prove the server does not reuse the previous request's declaration.
  2. Reverse the TOOLS, PROMPTS, and note insertion order. Confirm all list results remain stable.
  3. Add a destructive notes_delete tool and require an authorization check inside the executor. Keep destructiveHint as a UX hint only.
  4. Add resources/templates/list with ttlMs, cacheScope, and deterministic ordering.
  5. Build a separate legacy adapter for 2025-11-25. Add tests proving a modern request never enters it.

Solutions

SolutionP1 · Schemas from type hints, and "private, don't cache" for the note

From the type hints and docstrings alone, the SDK generated each tool's input schema (query and text as strings, with titles), an output schema from the return type, and the descriptions. Calls therefore return structuredContent as well as text.

The resource read said ttlMs=0 and cacheScope=private, because the server's cache_hints marked resources/read that way: a note is one user's data and may change at any moment. The tool list, by contrast, was public for an hour.

SolutionB1 · A corrupted stream

On the stdio transport, stdout is the protocol stream: the client reads it line by line and parses every line as a JSON-RPC message. loaded 3 notes is not JSON, so the client gets a parse error on the first line. Depending on the client, it logs and skips the line, or treats the server as broken and disconnects; either way, a debug print can make a working server look dead.

The fix: write diagnostics to stderr (print(..., file=sys.stderr) or a logger configured for stderr), which clients show in their logs. For structured diagnostics in production, use OpenTelemetry (Lesson 13.25); MCP 2026-07-28 deprecates the protocol's own Logging feature in favour of exactly these two.
