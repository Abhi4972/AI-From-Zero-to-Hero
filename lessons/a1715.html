In plain words first
The idea in one line

Every major provider ships an async batch API with a 50% discount and ~24-hour turnaround. OpenAI, Anthropic, Google, and most of the inference platforms (Fireworks batch tier, Together batch) implement the same pattern. Stack batch with prompt caching and overnight pipelines drop to ~10% of synchronous-uncached cost. The rule is brutally simple: if it tolerates hours of latency, it belongs on batch. Content generation pipelines, document classification, data extraction, report generation, bulk labeling, catalog tagging — anything tolerant of 24-hour latency is money left on the table until it moves to batch. The 2026 production pattern is to triage every new LLM workload into three lanes: interactive (synchronous with caching), semi-interactive (async queue with fallback), batch (overnight, cached input stacked). Workloads that pretend to be interactive but tolerate minutes of latency waste most.

The problem

In plain words first

A batch API lets you upload many requests at once, usually as a file with one request per line, and collect the answers later. The provider promises results within 24 hours (often a few hours) and charges half price, because it can run your work when its GPUs would otherwise sit idle. Batch suits anything whose real deadline is "by morning": nightly summaries, labelling, classification, report drafts. It stacks with prompt caching: a system prompt shared by every request is billed at the cache-read rate, and then halved again. The hard part is not technical. Teams call a workload "real-time" because it runs in production, when its users would never notice a delay of hours.

Your team ships a nightly report generation pipeline. 50,000 documents, summarize each, cluster the summaries, draft an executive brief. Running synchronously it takes 4 hours at $2,000/night. You hear about batch APIs.

The batch gets you 50% off. You also enable prompt caching on the system prompt (shared across all 50k calls). Stacked, the bill drops to $180/night — ~9% of baseline. Same pipeline, three config changes.

Batch is the cheapest lever in the LLM cost toolkit that nobody pulls. The reason is mostly organizational: teams think "real-time" when the SLA actually is "by morning." This lesson is about not leaving 90% of the bill on the table.

Idea 1 · The three batch APIs

OpenAI Batch API: JSONL file upload with a list of requests. Promised 24-hour turnaround (usually ~2-8 hours in practice). 50% discount on input and output tokens. /v1/batches endpoint. Cache-eligible inputs also get cached-input pricing on top.

Anthropic Message Batches: JSONL upload. 24-hour turnaround. 50% discount. Supports cache_control — cache writes are explicit, reads happen automatically within the batch.

Google Vertex AI Batch Prediction: BigQuery or GCS input. Similar 50% discount for Gemini. Integrates with Vertex pipelines.

Idea 2 · Semantic: asynchronous, not slow

Batch is "I promise to return within 24 hours" — not "this will take 24 hours." Typical P50 is 2-6 hours. Provider schedules your batch during off-peak windows when GPU inventory is underutilized.

Idea 3 · Stack with caching

A 50k-document summarization with the same 4K-token system prompt:

  • Synchronous uncached: 50000 × ($input × 4000 + $output × 200) at full rates.
  • Synchronous cached: system prompt cached after first write; remaining 49999 get 10x cheaper input.
  • Batch cached: all of the above plus 50% discount on both read and write.

The stack: batch + cache = ~10% of sync uncached bill. Any workload that runs overnight and has a shared system prompt should use this.

Idea 4 · Workload triage

Interactive — user waits for the response. TTFT matters. Synchronous call with prompt caching. Cannot batch.

Semi-interactive — user submits a task, checks back in minutes. Async queue with fallback to sync if batch not available. Think moderate-volume RAG indexing.

Batch — user expects results "by morning" or "by end of day." Content pipelines, classification at scale, offline analysis. Always batch, always stack caching.

Common mistake: classifying everything as interactive because the pipeline is production. Production is not a latency spec — SLA is.

Idea 5 · The partial-interactivity trap

Some features look interactive but tolerate 5-10 minutes. Example: a nightly customer health report with "refresh" button. User clicks refresh; wait 10 minutes is fine. Team ships it as synchronous. 50 concurrent refreshes cost 10x what batched-and-delivered-via-email would cost.

The question to ask: "What does 24-hour mean for this user?" If the answer is "they wouldn't notice," batch it.

Idea 6 · The output-schema trap

Batch file formats differ per provider:

  • OpenAI: JSONL, one request per line.
  • Anthropic: JSONL, one message per line; response format embedded.
  • Vertex: BigQuery table or GCS prefix with TFRecord.

Writing "one batch client" across providers means adapter code per provider. Gateways that advertise multi-provider batch (Portkey, LiteLLM some tiers) still thin-wrap the raw format.

Idea 7 · Numbers you should remember

  • Batch discount across providers: 50% flat on input + output.
  • Turnaround SLA: 24 hours guaranteed, 2-6 hours typical P50.
  • Stacked batch + cached input: ~10% of sync uncached cost.
  • Workload triage rule: if 24h latency acceptable, always batch.

Worked example
Where the "10% of the bill" comes from, and when it does not

50,000 documents. Each request: a 4,000-token shared system prompt, 2,000 tokens of document, 200 output tokens. Input $3/M, output $15/M, cached input 0.1×, batch 0.5×.

  1. Synchronous, no cache: input 50,000 × 6,000 × $3/M = $900; output 50,000 × 200 × $15/M = $150; total $1,050.
  2. Cache the 4,000-token prefix: prefix input falls from $600 to about $60, so the total is about $510 (49%).
  3. Batch on top halves everything: about $255, or 24% of the original.
  4. The "~10%" figure needs the shared prefix to be most of every request. With a 4,000-token prefix and a 2,000-token document, a third of the input stays at full rate, so 24% is the floor here. Your own ratio of shared to unique tokens decides the saving.

Part 1 of 3 · cost_sync, cost_sync_cache, cost_batch, cost_batch_cache

"""Batch vs synchronous cost simulator — stdlib Python.

Models a 50k-document pipeline across four configurations:
  SYNC              : no discount, no cache
  SYNC + CACHE      : system prompt cached after first call
  BATCH             : 50% discount, no cache
  BATCH + CACHE     : stacked (~10% of SYNC bill)
"""

from __future__ import annotations


BASE_INPUT = 3.00
BASE_OUTPUT = 15.00
CACHED_INPUT = 0.30
CACHE_WRITE_5MIN = 1.25 * BASE_INPUT
BATCH_DISCOUNT = 0.50


def cost_sync(docs: int, prefix_tokens: int, per_doc_tokens: int, out_tokens: int) -> float:
    cost = 0.0
    for _ in range(docs):
        cost += (prefix_tokens / 1e6) * BASE_INPUT
        cost += (per_doc_tokens / 1e6) * BASE_INPUT
        cost += (out_tokens / 1e6) * BASE_OUTPUT
    return cost


def cost_sync_cache(docs: int, prefix_tokens: int, per_doc_tokens: int, out_tokens: int) -> float:
    cost = (prefix_tokens / 1e6) * CACHE_WRITE_5MIN
    for i in range(docs):
        if i > 0:
            cost += (prefix_tokens / 1e6) * CACHED_INPUT
        cost += (per_doc_tokens / 1e6) * BASE_INPUT
        cost += (out_tokens / 1e6) * BASE_OUTPUT
    return cost


def cost_batch(docs: int, prefix_tokens: int, per_doc_tokens: int, out_tokens: int) -> float:
    return cost_sync(docs, prefix_tokens, per_doc_tokens, out_tokens) * BATCH_DISCOUNT


def cost_batch_cache(docs: int, prefix_tokens: int, per_doc_tokens: int, out_tokens: int) -> float:
    return cost_sync_cache(docs, prefix_tokens, per_doc_tokens, out_tokens) * BATCH_DISCOUNT

Part 2 of 3 · run, main

def run(label: str, docs: int, prefix: int, per_doc: int, output: int) -> None:
    sc = cost_sync(docs, prefix, per_doc, output)
    scc = cost_sync_cache(docs, prefix, per_doc, output)
    bc = cost_batch(docs, prefix, per_doc, output)
    bcc = cost_batch_cache(docs, prefix, per_doc, output)
    print(f"\n{label}")
    print(f"  docs={docs}, prefix={prefix}, per_doc={per_doc}, output={output}")
    print(f"  SYNC            : ${sc:10.2f}  (baseline)")
    print(f"  SYNC + CACHE    : ${scc:10.2f}  ({scc/sc*100:5.1f}% of baseline)")
    print(f"  BATCH           : ${bc:10.2f}  ({bc/sc*100:5.1f}% of baseline)")
    print(f"  BATCH + CACHE   : ${bcc:10.2f}  ({bcc/sc*100:5.1f}% of baseline)")


def main() -> None:
    print("=" * 80)
    print("BATCH API ECONOMICS — stack batch with prompt caching for ~10% of sync bill")
    print("=" * 80)
    run("Nightly doc summarization (50k docs)",
        docs=50_000, prefix=4000, per_doc=2000, output=200)
    run("Content classification (200k items, short per item)",
        docs=200_000, prefix=1500, per_doc=300, output=50)
    run("Large report draft (small N, heavy per item)",
        docs=1_000, prefix=6000, per_doc=15_000, output=2000)

Given a workload (name, user expectation for latency, traffic volume, shared prompt structure), produce a triage + cost plan.

Produce:

1. Lane. Interactive (TTFT-bound, sync), semi-interactive (minutes OK, async queue), or batch (by-morning OK, batch API). Justify with the specific user expectation.
2. Current cost. Compute monthly cost at current configuration (sync, no cache, etc.).
3. Target cost. Compute cost after recommended config (batch + cache or sync + cache). Express as % of current.
4. Migration plan. Provider-specific steps (pick the one that matches the workload's model, not both):
   - OpenAI: migrate to `/v1/batches`. Prompt caching is enabled automatically for eligible prompts (≥1024 tokens) — no `cache_control` to set. Optionally pass `prompt_cache_key` for tighter attribution.
   - Anthropic: migrate to Message Batches. Cache reuse requires explicit `cache_control` blocks (e.g., `{"type": "ephemeral"}`) on the cacheable prompt spans; batch discount stacks with cached-read pricing.
   - Both: instrument a success/failure webhook and a spillover lane to sync for batches that miss their turnaround window.
5. Risk. What if the batch turnaround is 20 hours at P99? Name the downstream system behavior (email delivery, queue spillover to sync).
6. Observable. Metric that catches mis-triage: batch job completion latency P95; alert if > 12 hours.

Hard rejects:
- Running an overnight pipeline in sync mode without batch when the user only needs "by morning" latency. Refuse — call out the ~90% leaked spend.
- Promising batch for anything with a sub-15-minute user expectation. Refuse — batch SLA is 24h.
- Ignoring prompt caching on a batch workload with shared system prompt. Refuse — the stacked discount is the point.

Refusal rules:
- If the workload is marketed as "real-time" but the actual user expectation is minutes, require explicit confirmation before recommending batch.
- If the workload targets a provider without prompt caching in batch (e.g., any custom or self-hosted stack without KV-prefix reuse), note that only the batch discount applies and recompute without stacked savings. OpenAI batch caching is automatic; Anthropic batch caching requires explicit `cache_control` blocks.
- If the workload has strict latency SLA (e.g., P99 < 60s) refuse batch outright — it belongs on a different lane.

Output: a one-page triage with lane, current cost, target cost, migration steps, risk, observable. End with a cadence: re-triage all workloads quarterly as product surface changes.

Solutions

SolutionP1 · 100k documents, 3K prefix, 500 output

Per document, with the prices above and the per-document content set to 2,000 tokens: synchronous ≈ 5,000 × $3/M + 500 × $15/M = $0.0225; with cache and batch ≈ (300 + 2,000) × $3/M × 0.5 + 500 × $15/M × 0.5 ≈ $0.0072. Across 100,000 documents: about $2,250 against $720, a saving of about 68%. The output tokens are the part caching cannot touch.

SolutionB1 · Refresh in ten minutes

The real requirement is semi-interactive: "within ten minutes". Put refresh requests on a queue, submit them as a batch (or a rate-limited async job), cache the shared prompt, and show "your report is being prepared" with a notification when it lands. Precompute the common reports nightly by batch so most clicks are instant.

Explain the mechanismA team runs its nightly report pipeline through the same synchronous endpoint as the chat product, because the pipeline is production. How do you classify model workloads, and where does this one belong?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. Sort every workload by the latency its user accepts, not by where it runs. Interactive work has a user waiting for the first token and stays synchronous with prompt caching, and semi-interactive work returns in minutes through an async queue. Anything whose user can wait for the full promise belongs on the batch API, which gives a 50 percent discount with a return promised within 24 hours and typical in a few hours. The nightly report is batch when a return at the 24-hour limit still meets its deadline, or when a synchronous fallback covers a late batch.

The three lanes.

Lane The user The path
interactive waits for the first token synchronous, with prompt caching
semi-interactive submits and checks back in minutes async queue, with a synchronous fallback
batch expects the result by morning or end of day batch API, with cached input stacked on top

The misclassification.

The lesson's rule is blunt: production is not a latency spec, the SLA is. The common mistake is to call everything interactive because it runs in production. Its cousin is the partial-interactivity trap: a report with a refresh button that users happily wait ten minutes for, shipped as a synchronous call. The lesson puts 50 concurrent refreshes at 10x the cost of the same report batched and delivered by mail.

What batch promises.

A return within 24 hours, with a typical return of a few hours, because the provider runs the batch when its capacity is idle. The lesson calls this asynchronous, not slow.

Stack it with caching.

A nightly pipeline shares one system prompt across every call. Cache that prefix, run the pipeline on batch, and the lesson's arithmetic lands near 10 percent of the synchronous uncached cost. Its opening example takes a nightly pipeline from a four-hour synchronous run to a batch run at about 9 percent of the bill with three configuration changes.

The other trap.

Batch file formats differ per provider, so one batch client needs an adapter per provider, and a gateway that advertises multi-provider batch still wraps the raw formats.

Plausible wrong answers.

  • "It runs in production, so it is interactive." Production is where it runs. The lane comes from the latency the user accepts.
  • "Batch means the answer takes a day." The promise is within a day. The typical return is a few hours.
  • "A 50 percent discount is not worth the complexity." On a shared prefix it stacks with caching to about a tenth of the synchronous cost, which the lesson calls the cheapest lever that nobody pulls.

Follow-ups an interviewer may ask.

  • (level 1) Which question sorts a workload into a lane? Expected: what a wait of a day means to this user. If they would not notice, it is batch.
  • (level 2) A user clicks refresh on a health report and waits ten minutes without complaint. Which lane? Expected: semi-interactive at most, and batch if the report can arrive by mail. Shipping it synchronous is the partial-interactivity trap.
  • (level 2) Why does the lesson call batch asynchronous rather than slow? Expected: the promise is a return within a day, and the typical return is a few hours, because the provider runs it when capacity is idle.
  • (level 3) What breaks when you write one batch client for two providers? Expected: the file formats differ, so you need an adapter per provider.

Estimate itA nightly pipeline summarizes 50,000 documents, and every call opens with the same system prompt. It runs synchronously against a provider for four hours and costs about 2,000 dollars a night. Estimate what the same job costs on the batch API with the system prompt cached, and say when you would move it onto your own GPU instead.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Batch gives a flat 50 percent discount on input and output tokens, and the cached system prompt makes the repeated input about ten times cheaper after the first write. Stacked, the lesson's worked example lands at about 180 dollars a night, near 9 percent of the synchronous bill, from three configuration changes. Move the job to your own GPU when it runs every night at high utilization and the shared prefix is short, so that neither discount has much to work on, and size that run by raising concurrency until the output stops growing.

The three bills.

The lesson writes the synchronous uncached bill as the document count times the input and output tokens of each call at full rates, with a shared prompt of about 4000 tokens and an output of about 200 tokens per document.

  1. Synchronous, uncached. Every call pays for the full prompt and the full output.
  2. Synchronous, cached. The system prompt is written once, and the remaining 49999 calls read it at about a tenth of the input price.
  3. Batch, cached. Everything above, plus the 50 percent discount on the reads, the write and the output.

The lesson's conclusion: batch plus cache comes to about 10 percent of the synchronous uncached bill, and its worked pipeline goes from 2,000 dollars a night to about 180.

What the estimate hides.

  • Output tokens take the batch discount only. Caching reuses the prompt's attention state and does nothing for generated tokens, so a job with long outputs and a short prompt saves much less.
  • The first call of a batch pays the cache write premium. Against tens of thousands of reads, it is noise. If the batch runs longer than the cache lifetime, the one-hour variant with its 2x write is worth it once the reads pass five.
  • Check the usage fields on a sample of the results. A batch whose requests all missed the cache shows writes and no reads, and then the second discount never happened.
  • The return is promised within 24 hours and typical within a few hours. A night is shorter than the promise, so the morning deadline holds only on the typical return. Submit the batch a day ahead, or keep a synchronous fallback for a late batch.

When your own GPU wins.

The lesson's exercise asks for the shared-prefix length at which batch plus cache beats a reserved GPU running overnight. Your own GPU wins when three things hold: the job keeps a reserved GPU busy every night, the shared prefix is short, so there is little to cache, and the outputs are long, so the batch discount is the only lever on the provider side. Data residency can decide it on its own.

How to size the self-hosted run.

The vLLM manual's recipe for an offline job: pass the whole prompt list to the offline engine class in one call, or run the batch command on a file of requests, and raise the concurrency until the output stops growing. On its card, the output grew to 273.9 tokens per second at 32 concurrent requests and fell to 241.4 at 64, because the pool filled and the GPU throttled. Raise the token budget above 8,192 for throughput, because a slow first token costs nothing when nobody waits, and watch the running count against the cache usage to see which limit binds.

Plausible wrong answers.

  • "Batch alone gets you to a tenth of the cost." Batch alone halves the bill. The other factor is the cached shared prompt.
  • "Caching saves the same on output as on input." The cache reuses the prompt's attention state. Every output token is generated and billed in full, less the batch discount.
  • "Batch is too slow for a nightly job." The promise is a day and the typical return is hours. Submit a day ahead, or keep a synchronous fallback for the rare late batch.

Follow-ups an interviewer may ask.

  • (level 3) Which of the two discounts applies to output tokens? Expected: only the batch discount. Caching lowers the price of repeated input and does nothing for generated tokens.
  • (level 3) The first call in each batch pays a cache write premium. Does that change the estimate? Expected: not at this volume. One write at a quarter more, against tens of thousands of reads at a tenth of the price.
  • (level 4) When does a reserved GPU beat batch plus cache? Expected: when the job keeps the GPU busy every night, the shared prefix is short and the outputs are long, so the two discounts have little to work on. The lesson's exercise computes the break-even prefix length.
  • (level 4) How do you find the right concurrency for the job on your own GPU? Expected: pass the whole list to the offline engine or the batch command, raise concurrency until the output tokens per second stop growing, and raise the token budget. The manual's card peaked near 32 concurrent requests.
