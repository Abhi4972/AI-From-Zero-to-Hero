FakeAnthropic (Lesson 3.1's appendix) implements the documented caching rules: writes at breakpoints, reads by looking back for earlier entries, a 512-token minimum, and a five-minute lifetime (with advance_clock, which exists only in the stand-in). Its token counts are rough estimates. The real thing runs the real SDK.

Why this came about

As prompts grew, with long system instructions, tool lists and documents repeated on every call, teams paid again and again to process the same text. In 2024 providers introduced prompt caching, which reuses the work on an unchanged beginning of the prompt and charges much less for it. It turned prompt layout into a cost decision.

The problem: the same 1,300 tokens, on every call

ShopKart's support prompt carries its whole policy section, about 1,300 tokens, and every question resends it:

from fake_claude import FakeAnthropic          # the labeled stand-in (Lesson 3.1's appendix)

MODEL = "claude-sonnet-5-5"
POLICY = "\n".join(f"Policy {i}: " + text for i, text in enumerate([
    "Refunds reach UPI in 2 days and cards in 5 to 7 business days.",
    "Damaged items are refundable within 30 days of delivery, with photos.",
    "Orders above INR 499 ship free; express delivery costs INR 99 in 40 cities.",
    "Cash on delivery is available up to INR 10,000, with a INR 30 fee.",
    "Cancel any order before dispatch from the Orders page; after dispatch, start a return.",
] * 12, start=1))                                       # a long, fixed policy section, about 1,300 tokens
SYSTEM = "You are ShopKart support. Answer only from these policies.\n" + POLICY

client = FakeAnthropic()
def ask(question, system=SYSTEM, **kw):
    r = client.messages.create(model=MODEL, max_tokens=300, system=system,
                               messages=[{"role": "user", "content": question}], **kw)
    u = r.usage
    return (u.input_tokens, getattr(u, "cache_creation_input_tokens", 0), getattr(u, "cache_read_input_tokens", 0))

for q in ["How long does a UPI refund take?", "Is COD available?", "Can I cancel after dispatch?"]:
    print("uncached, written, read =", ask(q))
What you should see
uncached, written, read = (1300, 0, 0)
uncached, written, read = (1296, 0, 0)
uncached, written, read = (1299, 0, 0)

Each call pays for the full prompt again, and the model processes it again before writing the first token (prefill, Lesson 1.2). For a support desk answering thousands of questions a day, the fixed part of the prompt is most of the bill. Prompt caching lets the provider keep the processed prefix and reuse it.

In plain words first
Not paying twice for the same opening pages

Many requests start with the same long text: the same system prompt, the same tool descriptions, the same reference document. Prompt caching lets the provider keep its work on that unchanged beginning (the prefix) for a few minutes, so later requests that start the same way are cheaper and start answering sooner. It only helps if the start is exactly the same, so stable text goes first and anything that changes, such as the user's question or today's date, goes last.

Idea 1 · Automatic caching, and why it misses here

The simplest switch is one top-level field:

client = FakeAnthropic()                    # a fresh stand-in, so nothing is cached yet
for q in ["How long does a UPI refund take?", "Is COD available?", "Can I cancel after dispatch?"]:
    print("uncached, written, read =", ask(q, cache_control={"type": "ephemeral"}))   # automatic: breakpoint on the last block
What you should see
uncached, written, read = (0, 1303, 0)
uncached, written, read = (0, 1299, 0)
uncached, written, read = (0, 1302, 0)

Every call wrote to the cache, and none read from it. That is the documented behavior, not a bug: a cache entry is written at a breakpoint, and with automatic caching the breakpoint is the request's last block, here the question. Each entry is "the system prompt plus this question". The next request has the same system prompt but a different question, so no earlier entry is a prefix of it. Writing costs more than normal input (1.25 times for the default five-minute cache), so this made every call slightly more expensive.

Idea 2 · Put the breakpoint where the shared part ends

Mark the end of the system prompt instead:

client = FakeAnthropic()
CACHED_SYSTEM = [{"type": "text", "text": SYSTEM, "cache_control": {"type": "ephemeral"}}]   # a breakpoint after the system prompt

for q in ["How long does a UPI refund take?", "Is COD available?", "Can I cancel after dispatch?"]:
    print("uncached, written, read =", ask(q, system=CACHED_SYSTEM))
What you should see
uncached, written, read = (15, 1288, 0)
uncached, written, read = (11, 0, 1288)
uncached, written, read = (14, 0, 1288)

The first call wrote the system prompt to the cache; the next two read it, and only the question was processed normally. The usage fields tell you exactly what happened, and the total input is always their sum:

Field Tokens that were Price relative to normal input
input_tokens After the last breakpoint, not cached 1
cache_creation_input_tokens Written to the cache 1.25 (5-minute) or 2 (1-hour)
cache_read_input_tokens Read from the cache 0.1 on most models; 0.05 on Opus 5.5 and Sonnet 5.5; 0.025 on Fable 5.1 and Mythos 5.1

The cache key is the exact content of everything before the breakpoint, in the order tools, then system, then messages. Change one character anywhere in that prefix, including the tool definitionslater · 3.1, and it is a different entry.

Idea 3 · Conversations: let the breakpoint move

In a conversation, the shared part grows every turn, which is exactly where automatic caching works:

history, client = [], FakeAnthropic()
for turn, q in enumerate(["How long does a UPI refund take?", "And for cards?", "Thanks. Can I cancel?"], start=1):
    history.append({"role": "user", "content": q})
    r = client.messages.create(model=MODEL, max_tokens=300, system=SYSTEM, messages=history, cache_control={"type": "ephemeral"})
    history.append({"role": "assistant", "content": r.content[0].text})
    u = r.usage
    print(f"turn {turn}: uncached {u.input_tokens:>3} | written {u.cache_creation_input_tokens:>4} | read {u.cache_read_input_tokens:>4}")
What you should see
turn 1: uncached   0 | written 1303 | read    0
turn 2: uncached   0 | written   35 | read 1303
turn 3: uncached   0 | written   38 | read 1338

Turn 2 read everything turn 1 wrote, and wrote only the new exchange; turn 3 did the same. When the request's breakpoint has no entry yet, the API looks back block by block (up to 20 positions) for one an earlier request wrote. In long agent runs, where a turn adds many blocks, add a second explicit breakpoint so the lookback window does not miss the last write. A request can have at most four breakpoints.

Measure it: what it saves, and when it saves nothing

Caching changes the price of input tokens: writing to the cache costs a little more than normal, and reading from it costs a small fraction. Whether that is a saving depends on how often the same prefix is reused. The arithmetic below prices one thousand calls that share a 1,290-token prefix, with and without caching:

PRICE = 3.00 / 1_000_000                  # illustrative input price per token (USD); output tokens are not affected
MULT = {"uncached": 1.0, "written": 1.25, "read": 0.05}   # Sonnet 5.5's documented multipliers for 5-minute caching

def input_cost(uncached, written, read):
    return PRICE * (uncached * MULT["uncached"] + written * MULT["written"] + read * MULT["read"])

calls = 1000
plain = calls * input_cost(1300, 0, 0)
cached = input_cost(10, 1290, 0) + (calls - 1) * input_cost(10, 0, 1290)
print(f"{calls} questions: ${plain:.2f} without caching, ${cached:.2f} with it ({1 - cached / plain:.0%} less)")
What you should see
1000 questions: $3.90 without caching, $0.23 with it (94% less)

The saving comes from three things: the fixed part is most of each prompt, the reads are cheap, and the requests are frequent enough to keep the entry alive. Remove any one and the saving shrinks or disappears:

  • Too short: prompts below the model's minimum (512 tokens on the current models, more on some older ones) are not cached at all, and no error tells you so.
  • Too rare: an entry lives five minutes, refreshed each time it is read. Requests further apart than that pay to write again:
client.advance_clock(301)                 # stand-in only: six minutes pass with no requests
print("after 6 quiet minutes:", ask("Is COD available?", system=CACHED_SYSTEM))
print("right after:          ", ask("Is COD available?", system=CACHED_SYSTEM))
What you should see
after 6 quiet minutes: (11, 1288, 0)
right after:           (11, 0, 1288)

The one-hour lifetime ("ttl": "1h") costs twice the normal price to write; it pays off when the gap between requests is between five minutes and an hour. - Nothing shared: if every request differs from the first token, there is nothing to reuse.

Caching also cuts time to first token, because the cached prefix is not processed again, which matters most for long prompts.

In production
Prompt caching in production
  • Order the prompt for caching: stable content first (tool definitions, instructions, policies, long documents), variable content last (the user's details, the time, the question).
  • Watch the hit rate: log cache_read_input_tokens against the cacheable total for every request. A drop after a deploy usually means a change made the prefix vary.
  • Changing tools invalidates everything: tool definitions come first, so adding or reordering a tool, or changing tool_choice or images, breaks the cache for what follows. Mid-conversation system messages (Lesson 2.1) are appended at the end, so they do not.
  • Other providers: OpenAI caches long prefixes automatically and reports usage.input_tokens_details.cached_tokens; Gemini offers implicit caching and explicit cached content; Bedrock supports cache points on supported models. Names and prices differ, so check each.

The real thing

The same breakpoint through the real SDK. It ran against the local test server described in Lesson 3.1, which applies the stand-in's caching rules:

import anthropic

client = anthropic.Anthropic()                         # reads ANTHROPIC_API_KEY from the environment
for q in ["Is COD available?", "Can I cancel after dispatch?"]:
    r = client.messages.create(model=MODEL, max_tokens=300, messages=[{"role": "user", "content": q}],
                               system=[{"type": "text", "text": SYSTEM, "cache_control": {"type": "ephemeral"}}])
    u = r.usage
    print(f"uncached {u.input_tokens} | written {u.cache_creation_input_tokens} | read {u.cache_read_input_tokens}")
What you should see
uncached 11 | written 1288 | read 0
uncached 14 | written 0 | read 1288

With a real model the numbers are exact token counts. The first request after a deploy, or after five quiet minutes, always writes.

import datetime
clock = iter(datetime.datetime(2026, 11, 4, 10, m, 0) for m in range(0, 60, 7))
debug_client = FakeAnthropic()

def ask_with_time(question):
    system = [{"type": "text", "text": f"Current time: {next(clock):%Y-%m-%d %H:%M}\n" + SYSTEM,   # the bug is on this line

Make it your own

Write cost_report(usages), which takes a list of (uncached, written, read) usages and returns the total input cost and the cache hit rate. (Solution M1.)

Solutions

SolutionP1 · Only the system prompt is reused

Turn 2 would read the system prompt (about 1,290 tokens) and process the rest normally: turn 1's question and answer plus the new question, a few dozen uncached tokens, with nothing written beyond the system prompt. For a short chat that is nearly as good. For a long conversation or an agent run with large tool results, the uncached history grows every turn, which is why conversations use a moving breakpoint.

SolutionB1 · Below the minimum

The prompt is far below the model's minimum cacheable length, so the API processes it normally and ignores the marker, without an error. You notice only by checking the usage fields: both cache fields are zero. Alert when requests marked for caching report zero written and zero read.

SolutionD1 · Variable content at the front

The time is part of the prefix before the breakpoint, and it changes on every request, so every request is a different cache entry: written, never read. Move variable content after the breakpoint, here into the user message:

clock = iter(datetime.datetime(2026, 11, 4, 10, m, 0) for m in range(0, 60, 7))
fixed_client = FakeAnthropic()

def ask_with_time(question):
    r = fixed_client.messages.create(model=MODEL, max_tokens=300, system=CACHED_SYSTEM,
                                     messages=[{"role": "user", "content": f"(Current time: {next(clock):%Y-%m-%d %H:%M})\n{question}"}])
    return r.usage.cache_creation_input_tokens, r.usage.cache_read_input_tokens

for q in ["Is COD available?", "How long does a UPI refund take?", "Can I cancel?"]:
    print("written, read =", ask_with_time(q))

written, read = (1288, 0)
written, read = (0, 1288)
written, read = (0, 1288)

The general rule: anything that changes per request, such as time, user name, account details or retrieved documents, goes after the last breakpoint, or behind a breakpoint of its own placed after the stable part.

SolutionM1 · A cost report
def cost_report(usages):
    """Total input cost of a list of (uncached, written, read) usages, and the cache hit rate."""
    total = sum(input_cost(*u) for u in usages)
    cacheable = sum(w + r for _, w, r in usages)
    hit_rate = sum(r for _, _, r in usages) / cacheable if cacheable else 0.0
    return round(total, 6), f"{hit_rate:.0%}"

fresh = FakeAnthropic()
client = fresh
usages = [ask(q, system=CACHED_SYSTEM) for q in ["Is COD available?", "Can I cancel?", "Refund time?"]]
print(cost_report(usages))

(0.005309, '67%')

The hit rate here is the share of cacheable tokens that were read rather than written. Two of three requests hit, so 67%. In production, compute it per prompt version and per customer segment, because a single bad template can hide in an average.

Check your understanding

Explain the mechanismHow does prompt caching work, and what does it save?

Worked answer. The provider stores the processed state of a prompt prefix, keyed by its exact content up to a breakpoint, for a short time (five minutes by default on Claude, refreshed on each hit, or an hour). A later request with the same prefix reads it instead of processing it again. Reads cost a small fraction of normal input, between 0.025 and 0.1 times depending on the model, and writes cost a little more than normal. It saves input cost and time to first token for long, stable prefixes that are reused often. Output tokens are unaffected.

A plausible wrong answer. "It caches the model's answers." It caches the processed prompt prefix; the answer is generated fresh each time.

Follow-ups. Why does the order of tools, system prompt and messages matter?

Debug a failureAfter a release, LLM costs rose 40% with the same traffic. What do you check?

Worked answer. The cache hit rate, from cache_read_input_tokens per request, before and after the release. If it fell, something made the prefix vary: a timestamp or user detail moved into the system prompt, tool definitions that are now generated in a different order, a new tool, or a changed tool_choice. Diff two consecutive requests' prefixes to find the first difference, then move variable content after the breakpoint. Also check whether the release made prompts longer, or moved traffic to a model with different pricing.

A plausible wrong answer. "The provider raised prices." Possible, but check your own usage fields first; they show exactly which tokens were billed at which rate.

Follow-ups. How would you add a test that fails if the cacheable prefix changes between two requests?

Defend a designIs prompt caching worth designing for from the start?

Worked answer. Yes, when the application sends long, stable context repeatedly, which describes most agents and support systems: tool definitions, instructions and policies are large and identical across requests. Designing for it is mostly ordering (stable first, variable last) and monitoring the hit rate, which costs little. It is not worth contorting a prompt for when prompts are short, traffic is sparse, or every request is unique, and it never replaces making the prompt shorter.

A plausible wrong answer. "Always cache everything." Writes cost more than normal input, so caching content that is never reused raises the bill.
