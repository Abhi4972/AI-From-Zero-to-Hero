Why this came about

Agents on AWS rely on much more than the AI services: SageMaker for custom models (since 2017), data and AI services, CloudWatch for observability and IAM for security. Production designs combine them.

In plain words first
The rest of AWS around the agent

Beyond agents, AWS offers SageMaker for training and hosting your own models, ready-made AI services (speech, text extraction, translation), observability through CloudWatch and tracing, and security through IAM roles, private networking and encryption. A production agent uses several of these together.

SageMaker AI: the ML platform

Amazon SageMaker AI is AWS's platform for building, training and serving your own models. (In 2024 AWS renamed the original service "SageMaker AI" and made "SageMaker" the name of a broader data and AI platform, with SageMaker Unified Studio as one workspace for data, analytics and ML.)

Use Bedrock when an available model does the job; use SageMaker AI when you train, need a model Bedrock does not serve, or need full control of the serving stack. An agent calls a SageMaker endpoint like any other tool:

import io, json, datetime
import boto3
from botocore.stub import Stubber
from botocore.response import StreamingBody

session = boto3.Session(region_name="ap-south-1")
_stubs = {}
def offline(client, operation: str, response: dict):
    """Lab mode: queue a recorded response instead of calling AWS. Delete the call to go live."""
    if id(client) not in _stubs:
        _stubs[id(client)] = Stubber(client)
        _stubs[id(client)].activate()
    _stubs[id(client)].add_response(operation, response)

smr = session.client("sagemaker-runtime")
body = b'{"fraud_probability": 0.07}'
offline(smr, "invoke_endpoint", {"Body": StreamingBody(io.BytesIO(body), len(body)), "ContentType": "application/json"})

def fraud_score(order_id: str, amount: float) -> float:
    """A tool the agent calls before approving a refund: our own model on a SageMaker endpoint."""
    r = smr.invoke_endpoint(EndpointName="shopkart-fraud-v3", ContentType="application/json",
                            Body=json.dumps({"order_id": order_id, "amount": amount}))
    return json.loads(r["Body"].read())["fraud_probability"]

print("fraud score:", fraud_score("A-1001", 2499.0))
What you should see
fraud score: 0.07

comprehend = session.client("comprehend")
offline(comprehend, "detect_pii_entities", {"Entities": [
    {"Score": 0.99, "Type": "PHONE", "BeginOffset": 16, "EndOffset": 26},
    {"Score": 0.98, "Type": "EMAIL", "BeginOffset": 30, "EndOffset": 46}]})

def redact(text: str) -> str:
    """Mask PII before text reaches a log or a model (Lesson 10.1)."""
    found = comprehend.detect_pii_entities(Text=text, LanguageCode="en")["Entities"]
    for e in sorted(found, key=lambda e: e["BeginOffset"], reverse=True):
        text = text[:e["BeginOffset"]] + f"[{e['Type']}]" + text[e["EndOffset"]:]
    return text

print(redact("Call me back on 9876543210 or ravi@example.com about A-1001"))

Textract Queries turn a scanned document into named fields, which is exactly the shape an agent tool should return. The confidence score decides what a person must check:

textract = session.client("textract")
offline(textract, "analyze_document", {"Blocks": [
    {"BlockType": "QUERY", "Id": "q1", "Query": {"Text": "What is the order number?", "Alias": "order_id"},
     "Relationships": [{"Type": "ANSWER", "Ids": ["a1"]}]},
    {"BlockType": "QUERY_RESULT", "Id": "a1", "Text": "A-1002", "Confidence": 98.1},
    {"BlockType": "QUERY", "Id": "q2", "Query": {"Text": "What is the invoice total?", "Alias": "total"},
     "Relationships": [{"Type": "ANSWER", "Ids": ["a2"]}]},
    {"BlockType": "QUERY_RESULT", "Id": "a2", "Text": "INR 7,499.00", "Confidence": 96.4},
    {"BlockType": "QUERY", "Id": "q3", "Query": {"Text": "What is the delivery date?", "Alias": "delivered"},
     "Relationships": [{"Type": "ANSWER", "Ids": ["a3"]}]},
    {"BlockType": "QUERY_RESULT", "Id": "a3", "Text": "21/10/2026", "Confidence": 61.0}]})

def read_invoice(bucket: str, key: str, min_confidence: float = 80.0) -> dict:
    """An agent tool: pull named fields from a scanned invoice, flagging low-confidence answers for review."""
    r = textract.analyze_document(
        Document={"S3Object": {"Bucket": bucket, "Name": key}}, FeatureTypes=["QUERIES"],
        QueriesConfig={"Queries": [{"Text": "What is the order number?", "Alias": "order_id"},
                                   {"Text": "What is the invoice total?", "Alias": "total"},
                                   {"Text": "What is the delivery date?", "Alias": "delivered"}]})
    blocks = {b["Id"]: b for b in r["Blocks"]}
    fields, review = {}, []
    for b in r["Blocks"]:
        if b["BlockType"] != "QUERY":
            continue
        answer = blocks[b["Relationships"][0]["Ids"][0]]
        fields[b["Query"]["Alias"]] = answer["Text"]
        if answer["Confidence"] < min_confidence:
            review.append(b["Query"]["Alias"])
    return {"fields": fields, "needs_review": review}

print(read_invoice("shopkart-claims", "uploads/A-1002-invoice.pdf"))
What you should see
{'fields': {'order_id': 'A-1002', 'total': 'INR 7,499.00', 'delivered': '21/10/2026'}, 'needs_review': ['delivered']}

The delivery date came back at 61% confidence, so the claims agent asks a person (or the customer) to confirm it instead of deciding a refund window on a guess. A multimodal model can read the same invoice; Textract is the cheaper, more consistent choice at thousands of documents a day, and it returns per-field confidence and coordinates for audit. Bedrock Data Automation combines both approaches for documents, images, audio and video with output schemas you define.

Observability and logging for generative AI on AWS

Each service answers a different question. You will usually turn on all of them.

Question Service What to switch on
What did the agent do, step by step? AgentCore Observability in the CloudWatch generative AI observability console Turn on CloudWatch Transaction Search once per account; add aws-opentelemetry-distro (ADOT) and run with opentelemetry-instrument. Spans land in the agent's log group or aws/spans
What exactly was sent to and returned by the model? Bedrock model invocation logging Account-level setting that writes full requests and responses to CloudWatch Logs and/or S3
How are models performing overall? CloudWatch metrics (namespace AWS/Bedrock) Built in: Invocations, InvocationLatency, InputTokenCount, OutputTokenCount, InvocationThrottles, client and server errors, by model
Who called which API, when? AWS CloudTrail Management events by default; add data events for runtime calls you must audit

How is cost spread across teams? Cost Explorer, cost allocation tags, application inference profiles Tag profiles per team, app or tenant
Are guardrails firing? Guardrail metrics and traces GuardrailPolicyType dimensions; alert on spikes

Agents not hosted on AgentCore (on Lambda, ECS, EKS or outside AWS) can still use AgentCore Observability: use the ADOT Lambda layer or SDK and set the environment variables in the AgentCore documentation. Invocation logs contain full prompts, so treat them like the traces in Lesson 14.120: KMS-encrypted, access-restricted, with a retention period, and redacted where policy demands it.

Cost attribution with application inference profiles

An application inference profile is a named, tagged wrapper around a model. You call the profile's ARN instead of the model ID, and every token used through it is billed under its tags. Create one for the support agent in production:

offline(bedrock, "create_inference_profile", {"inferenceProfileArn":
        "arn:aws:bedrock:ap-south-1:123456789012:application-inference-profile/abc123xyz", "status": "ACTIVE"})
profile = bedrock.create_inference_profile(
    inferenceProfileName="shopkart-support-prod",
    modelSource={"copyFrom": "arn:aws:bedrock:ap-south-1:123456789012:inference-profile/global.anthropic.claude-sonnet-placeholder-v1:0"},
    tags=[{"key": "team", "value": "support"}, {"key": "env", "value": "prod"}, {"key": "cost-center", "value": "cx-114"}])
print("call this instead of the model ID:", profile["inferenceProfileArn"])
What you should see
call this instead of the model ID: arn:aws:bedrock:ap-south-1:123456789012:application-inference-profile/abc123xyz

Activate the tags as cost allocation tags in Billing, and Cost Explorer splits Bedrock spend by team and environment. Give each agent its own profile so a runaway agent shows up as a line item (Lesson 14.117).

Batch inference for offline work

Nightly summaries, enrichment and eval runs belong in batch inference: you put JSONL records in S3, Bedrock processes them asynchronously at a discount to on-demand prices (check the pricing page for the model you use), and writes results back to S3:

records = [{"recordId": f"T-{i}", "modelInput": {
              "anthropic_version": "bedrock-2023-05-31", "max_tokens": 120,
              "messages": [{"role": "user", "content": f"Summarize complaint {i} in one line: ..."}]}}
           for i in range(3)]
print(json.dumps(records[0])[:100], "...")                 # one JSON object per line in s3://.../input.jsonl

modelInput is the model's native request body (here, the Anthropic Messages format), and recordId matches each output line back to its input. Least privilege is easiest to get right when you test the policy before attaching it. The IAM policy simulator evaluates a policy against the actions and resources an agent might attempt. This policy lets the support agent call one approved inference profile, only with the required guardrail, and read one knowledge base:

AGENT_POLICY = {
    "Version": "2012-10-17",
    "Statement": [
        {"Sid": "InvokeApprovedProfileOnly", "Effect": "Allow",
         "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],   # Converse uses these too
         "Resource": "arn:aws:bedrock:ap-south-1:123456789012:application-inference-profile/abc123xyz",
         "Condition": {"StringEquals": {"bedrock:GuardrailIdentifier":
                       "arn:aws:bedrock:ap-south-1:123456789012:guardrail/gr-support:3"}}},
        {"Sid": "RetrieveFromPolicyKB", "Effect": "Allow", "Action": "bedrock:Retrieve",
         "Resource": "arn:aws:bedrock:ap-south-1:123456789012:knowledge-base/KB12345678"},
    ]}

iam = session.client("iam")
offline(iam, "simulate_custom_policy", {"EvaluationResults": [
    {"EvalActionName": "bedrock:InvokeModel", "EvalResourceName": "arn:aws:bedrock:ap-south-1:123456789012:application-inference-profile/abc123xyz", "EvalDecision": "allowed"},
    {"EvalActionName": "bedrock:InvokeModel", "EvalResourceName": "arn:aws:bedrock:ap-south-1::foundation-model/some-unapproved-model", "EvalDecision": "implicitDeny"},
    {"EvalActionName": "bedrock:DeleteKnowledgeBase", "EvalResourceName": "arn:aws:bedrock:ap-south-1:123456789012:knowledge-base/KB12345678", "EvalDecision": "implicitDeny"}]})

result = iam.simulate_custom_policy(
    PolicyInputList=[json.dumps(AGENT_POLICY)],
    ActionNames=["bedrock:InvokeModel", "bedrock:DeleteKnowledgeBase"],
    ResourceArns=["arn:aws:bedrock:ap-south-1:123456789012:application-inference-profile/abc123xyz",
                  "arn:aws:bedrock:ap-south-1::foundation-model/some-unapproved-model",
                  "arn:aws:bedrock:ap-south-1:123456789012:knowledge-base/KB12345678"],
    ContextEntries=[{"ContextKeyName": "bedrock:GuardrailIdentifier", "ContextKeyType": "string",
                     "ContextKeyValues": ["arn:aws:bedrock:ap-south-1:123456789012:guardrail/gr-support:3"]}])
for r in result["EvaluationResults"]:
    print(f"{r['EvalDecision']:13} {r['EvalActionName']:28} {r['EvalResourceName'].split(':')[-1]}")
What you should see
allowed       bedrock:InvokeModel          application-inference-profile/abc123xyz
implicitDeny  bedrock:InvokeModel          foundation-model/some-unapproved-model
implicitDeny  bedrock:DeleteKnowledgeBase  knowledge-base/KB12345678

The bedrock:GuardrailIdentifier condition means the agent's calls fail unless they carry the approved guardrail, so a code change that drops the guardrail breaks loudly instead of silently. Put simulations like these in CI next to your infrastructure code, and add a service control policy at the organization level that denies unapproved models in every account.

Industry practice
Operating checklist for an AWS agent going to production
  1. Transaction Search and ADOT on; one trace per conversation, session ID propagated.
  2. Model invocation logging to S3 with KMS and lifecycle rules; CloudWatch copy only where you query it.
  3. Alarms on InvocationThrottles, server errors, latency p95, guardrail interventions and daily token spend.
  4. Online evaluations sampling live sessions; a batch evaluation gating every release.
  5. One IAM role and one application inference profile per agent; guardrail enforced by policy.
  6. PrivateLink endpoints for Bedrock, AgentCore and S3; no public egress from the agent unless a tool needs it.
  7. Quotas reviewed (tokens per minute per model and Region), with cross-Region profiles or Priority tier for peaks.
In production
Operating costs and risks that surprise AWS teams

SageMaker real-time endpoints bill while idle, so a forgotten test endpoint is a monthly line item; use serverless or asynchronous inference for spiky traffic and tag every endpoint. Model invocation logs contain full prompts and responses, which makes them both your best debugging tool and a store of personal data: encrypt them with KMS, restrict access and set retention. CloudWatch Logs ingestion and storage costs grow with verbose agent logs; sample routine traces and keep full content for errors and flagged runs.

Solutions

SolutionP1 · ML and GenAI stacks

SageMaker for training and serving the churn model; Bedrock and AgentCore for the agent. They share data stores, IAM, CloudWatch and security services.

SolutionB1 · Least privilege in IAM

Any manipulation of the agent can read or write any bucket. Scope the role to the buckets and actions it needs, and use resource policies.

SolutionD1 · Observability wiring

Whether the OpenTelemetry instrumentation is installed and configured with the right exporter, IAM permissions to write traces, and the region. Test with a single traced call.

SolutionM1 · Controls by layer

VPC endpoints and private access; scoped IAM roles; KMS encryption and Macie for sensitive data; Bedrock Guardrails; CloudTrail and CloudWatch alarms.

Explain the mechanismHow do AWS's ML, AI services and observability fit an agent system?

Worked answer. SageMaker for custom ML, AI services (Textract, Comprehend, Transcribe and others) for specific tasks, Bedrock for models, AgentCore for agents, CloudWatch and X-Ray for observability, and IAM, KMS, Macie and GuardDuty for security. An agent system combines several, governed by IAM.

A plausible wrong answer. "Bedrock does everything." It is one part of the stack.

Follow-ups. When would you use Textract instead of a vision model?

Debug a failureAn agent works in one region and fails in another. What do you check?

Worked answer. Model availability and inference profiles per region, service quotas, VPC endpoints and IAM conditions on region. Many failures are availability or quota differences.

A plausible wrong answer. "The code is region-specific." Usually configuration is.

Follow-ups. How would you design for regional failover?

Defend a designAWS-native AI services or open-source tools on AWS?

Worked answer. Native services for managed operations, integration with IAM and compliance; open-source on containers for portability and control. Mix by component: managed models and storage, open-source frameworks.

A plausible wrong answer. "All native for simplicity." Lock-in and cost grow with every service.

Bedrock is for using models; SageMaker AI is for building and running your own.

Interface endpoints keep traffic on the AWS network.
