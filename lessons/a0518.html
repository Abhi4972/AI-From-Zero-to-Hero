The problem

In plain words first

There are about 7,000 languages, and labelled training data exists for a handful of them. Multilingual models are trained on text in around a hundred languages at once, with one shared vocabulary of word pieces and one shared network. Because the network keeps seeing the same meanings expressed in different languages, sentences with the same meaning end up with similar internal representations whatever the language. That makes cross-lingual transfer possible: teach a task with English examples and the model can often do it in Hindi or Swahili. It works unevenly, though. Languages far from the training mix get less model capacity and are chopped into more, smaller pieces by the shared tokenizer. This lesson explains the shared space and the "curse of multilinguality", measures the tokenizer tax on real parallel sentences, tests whether translations really land close together, and runs zero-shot classification across several languages with a model that never saw a label in most of them.

English has billions of labeled examples. Urdu has thousands. Maithili has almost none. Any practical NLP system that serves a global audience has to work on the long tail of languages where task-specific training data does not exist.

Multilingual models solve this by training one model on many languages simultaneously. The shared representation lets the model transfer skills learned in high-resource languages to low-resource ones. Fine-tune the model on English sentiment analysis, and it produces surprisingly good sentiment predictions on Urdu out of the box. That is zero-shot cross-lingual transfer, and it has reshaped how NLP ships to the world.

This lesson names the tradeoffs, the canonical models, and the one decision that trips up teams new to multilingual work: picking a source language for transfer.

The idea

Shared vocabulary. Multilingual models use a SentencePiece or WordPiece tokenizer trained on text from all target languages. The vocabulary is shared: the same subword unit represents the same morpheme across related languages. anti- in English and Italian gets the same token.

Shared representation. A transformer pretrained on masked language modeling across many languages learns that semantically similar sentences in different languages produce similar hidden states. mBERT, XLM-R, and NLLB all exhibit this. Embeddings for "cat" in English cluster near "chat" in French and "gato" in Spanish, and so do full-sentence embeddings.

Zero-shot transfer. Fine-tune the model on labeled data in one language (usually English). At inference, run it on any other language the model supports. No target-language labels needed. Results are strong for typologically related languages and weaker for distant ones.

Few-shot fine-tuning. Add 100-500 labeled examples in the target language. Accuracy usually closes much of the gap to the English baseline on classification tasks (how much depends on the language and task), and it is one of the most cost-effective levers in multilingual NLP.

The same idea as a formula

Why a shared space appears. Masked-language-model pretraining on many languages uses one vocabulary and one set of weights. Shared pieces (numbers, names, cognates such as "information", "información") and shared structure give the model a reason to reuse the same directions for the same meanings, and parallel sentences end up close: cos(E(xen​),E(xfr​))≈1 for a sentence and its translation. Sentence-embedding models such as paraphrase-multilingual-MiniLM-L12-v2 are additionally trained so that a translation maps to the same vector as its source (Reimers and Gurevych, 2020).

Aligning two monolingual spaces. Before multilingual pretraining, Mikolov et al. (2013) found that word vectors trained separately for two languages are related by a nearly linear map. With X,Y∈Rd×n holding the vectors of n dictionary pairs, the best orthogonal map (orthogonal Procrustes) is

W∗=argW⊤W=Imin​∥WX−Y∥F​=UV⊤,where UΣV⊤=SVD(YX⊤)

Orthogonality keeps distances, so the map only rotates one space onto the other.

Zero-shot classification as entailment. An NLI model gives P(entail∣premise,hypothesis). For a text x and labels ℓ1​..ℓK​, score each label with the hypothesis "This text is about ℓk​" and predict argmaxk​P(entail∣x,h(ℓk​)). Train the NLI model on English (or a few languages), and the shared space carries it to others.

Fertility of a tokenizer on a language is tokens per word; for parallel sentences, the ratio #tokens(xen​)#tokens(xlang​)​ measures the extra cost of the same content.

The curse of multilinguality (Conneau et al., 2020): with model size fixed, adding languages first helps low-resource languages (more shared signal) and then hurts all of them, because each language's share of the model's capacity shrinks. Bigger models and larger vocabularies (XLM-V) push the turning point out.

Worked example
Procrustes in two dimensions

Two English word vectors x1​=(1,0), x2​=(0,1) and their French counterparts y1​=(0,1), y2​=(−1,0): the French space is the English one rotated by 90°.

  • X=(10​01​), Y=(01​−10​), so YX⊤=Y.
  • Y is already orthogonal, so its SVD is U=Y, Σ=I, V=I, and W∗=UV⊤=Y.
  • Check: W∗x1​=(0,1)=y1​ and W∗x2​=(−1,0)=y2​. A new English word x=(0.6,0.8) maps to (−0.8,0.6), its predicted French neighbourhood.

With real vectors the fit is not exact: the residual ∥W∗X−Y∥ is larger for distant language pairs, because their spaces are less isomorphic.

Check your mental model
  • ✗ "A multilingual model is equally good in all its languages."
    ✓ Quality follows pretraining data; low-resource languages get less capacity and worse tokenization.
  • ✗ "Zero-shot transfer means no target-language data was ever involved."
    ✓ No labelled target data. The model's pretraining included unlabelled text in the target language, and that is what makes transfer work.
  • ✗ "Token counts are a cosmetic difference."
    ✓ They set context length, cost and latency per sentence, and more pieces per word means each piece carries less meaning.

The source-language decision (2026 research)

Most teams default to English as the fine-tuning source. Recent research (2026) shows this is often wrong.

Language similarity often predicts transfer quality better than raw corpus size, though a 2025 study across 266 languages (Blaschke et al.) found the effect depends on the task and on whether the target language was in the model's pretraining data. For Slavic targets, German or Russian often beat English. For Indic targets, Hindi often beats English. The qWALS similarity metric (2026, based on World Atlas of Language Structures features) quantifies this. LANGRANK (Lin et al., ACL 2019) is a separate, earlier method that ranks candidate source languages from a combination of linguistic similarity, corpus size, and genetic relatedness.

Practical rule: if your target language has a typologically close high-resource relative, try fine-tuning on that one first, then compare to English fine-tune.

Step 1 · zero-shot cross-lingual classification

from transformers import AutoTokenizer, AutoModelForSequenceClassification
import torch

# The lesson's original model is a 2.2 GB XLM-R-large NLI checkpoint; this run uses a smaller multilingual NLI model (0.56 GB)
nli_id = "MoritzLaurer/mDeBERTa-v3-base-xnli-multilingual-nli-2mil7"
tok = AutoTokenizer.from_pretrained(nli_id)
model = AutoModelForSequenceClassification.from_pretrained(nli_id).eval()
ENTAIL = model.config.label2id["entailment"]       # label order differs between NLI models: look it up


def classify(text, candidate_labels, hypothesis_template="This text is about {}."):
    scores = {}
    for label in candidate_labels:
        hypothesis = hypothesis_template.format(label)
        inputs = tok(text, hypothesis, return_tensors="pt", truncation=True)
        with torch.no_grad():
            logits = model(**inputs).logits[0]
        entail_score = torch.softmax(logits, dim=-1)[ENTAIL].item()
        scores[label] = entail_score
    return dict(sorted(scores.items(), key=lambda x: -x[1]))


print(classify("I love this product!", ["positive", "negative", "neutral"]))
print(classify("मुझे यह उत्पाद पसंद है!", ["positive", "negative", "neutral"]))
print(classify("J'adore ce produit !", ["positive", "negative", "neutral"]))

Step 2 · multilingual embedding space

from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")

pairs = [
    ("The cat is sleeping.", "Le chat dort."),
    ("The cat is sleeping.", "El gato está durmiendo."),
    ("The cat is sleeping.", "Die Katze schläft."),
    ("The cat is sleeping.", "The dog is barking."),
]

for eng, other in pairs:
    emb_eng = model.encode([eng], normalize_embeddings=True)[0]
    emb_other = model.encode([other], normalize_embeddings=True)[0]
    sim = float(np.dot(emb_eng, emb_other))
    print(f"  {eng!r} <-> {other!r}: cos={sim:.3f}")

Translations land close in embedding space. A different English sentence lands further. This is what makes cross-lingual retrieval, clustering, and similarity work.

Step 3 · few-shot fine-tuning strategy

from transformers import TrainingArguments, Trainer
from datasets import Dataset


def few_shot_finetune(base_model, base_tokenizer, examples):
    ds = Dataset.from_list(examples)

    def tokenize_fn(ex):
        out = base_tokenizer(ex["text"], truncation=True, max_length=128)
        out["labels"] = ex["label"]
        return out

    ds = ds.map(tokenize_fn)
    args = TrainingArguments(
        output_dir="out",
        per_device_train_batch_size=8,
        num_train_epochs=5,
        learning_rate=2e-5,
        save_strategy="no",
    )
    trainer = Trainer(model=base_model, args=args, train_dataset=ds)
    trainer.train()
    return base_model

For 100-500 target-language examples, num_train_epochs=5 and learning_rate=2e-5 are the safe defaults. Higher learning rates on a small target-language set can erase what the model knew about other languages (catastrophic forgetting), so it fits the few examples and loses its cross-lingual generality.

Evaluation that actually works

  • Per-language accuracy on held-out sets. Not aggregated. The aggregate hides the long tail.
  • Benchmark against monolingual baseline. For languages with enough data, a monolingual model trained from scratch sometimes beats the multilingual one. Test.
  • Entity-level tests. Named entities in the target language. Multilingual models often have weak tokenization for scripts far from Latin.
  • Cross-lingual consistency. Same meaning in two languages should produce the same prediction. Measure the gap.

Do translations really land close together?

For each language, 200 English sentences must find their own translations among 200 candidates by cosine similarity (bitext retrieval). Done with the lesson's multilingual MiniLM and, for contrast, the English-only all-MiniLM-L6-v2.

multi = SentenceTransformer("sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2")
mono = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
print(f"{'':10s}{'multilingual MiniLM':>22s}{'English-only MiniLM':>22s}")
acc = {}
for lang, ps in pairs.items():
    ps = ps[:200]
    row = []
    for enc in (multi, mono):
        E = enc.encode([e for e, _ in ps], normalize_embeddings=True, batch_size=32)
        X = enc.encode([x for _, x in ps], normalize_embeddings=True, batch_size=32)
        row.append(float(np.mean((E @ X.T).argmax(1) == np.arange(len(ps)))))

Industry practice
What's current (2024–2026)
  • Multilingual LLMs cover far more languages. Qwen3 (2025) reports support for 119 languages and dialects, Gemma 3 over 140, and Cohere's Aya Expanse targets 23 languages; prompting such a model in the target language is now a strong zero-shot baseline.
  • Multilingual embeddings in production. BGE-M3, multilingual-e5 and the API embedding models (OpenAI, Cohere, Gemini) retrieve across languages with one index, which is how most multilingual RAG is built.
  • XLM-R is still the workhorse encoder for fine-tuned multilingual classification and NER in high-volume systems.

The tokenization tax (what goes wrong for low-resource languages)

Multilingual models share one tokenizer across all their languages. That vocabulary is trained on a corpus dominated by English, French, Spanish, Chinese, German. For any language outside the dominant set, three taxes compound silently:

  • Fertility tax. Low-resource language text tokenizes into far more tokens per word than English. With an English-centric tokenizer, a Hindi sentence can need several times the tokens of its English translation (about 6 times with GPT-2's, and about 15 times for Tamil, measured under "Use it"); multilingual tokenizers shrink the gap but rarely close it. That 3-5x eats your context window, training efficiency, and latency.
  • Variant recovery tax. Every typo, diacritic variant, Unicode normalization mismatch, or case variation becomes a cold-start unrelated sequence in embedding space. The model cannot learn orthographic correspondences that a native speaker takes as obvious.
  • Capacity spillover tax. Taxes 1 and 2 consume context positions, layer depth, and embedding dimensions. What remains for actual reasoning is systematically smaller than what a high-resource language gets from the same model.

The practical symptom: your model trains normally on Hindi, the loss curve looks right, eval perplexity looks reasonable, and production outputs are subtly wrong. Morphology collapses mid-sentence. Rare inflections stay unrecoverable. You cannot data-scale your way out of a broken tokenizer.

Mitigations: pick a tokenizer with good coverage for your target language (XLM-V's 1M-token vocabulary is a direct fix); verify tokenization fertility on held-out target text before training; use byte-level fallback (SentencePiece byte_fallback=True, GPT-2-style byte-level BPE) for truly long-tail scripts so nothing is ever OOV.

Recap
What to keep from this lesson
  • One vocabulary and one network across ~100 languages produce a shared space where translations land close together.
  • Cross-lingual transfer: train with labels in one language, apply in others; a few hundred target examples help a lot.
  • Zero-shot classification can be posed as entailment; template wording matters.
  • Tokenizers tax non-dominant languages with more pieces per sentence: measure fertility before choosing a model.
  • Fixed capacity spread over many languages hurts each (the curse of multilinguality); evaluate per language, never only in aggregate.

Exercises

  1. Easy. Run the zero-shot classification pipeline on 10 sentences per language across English, French, Hindi, and Arabic. Report accuracy on each. You should see strong French, decent Hindi, variable Arabic.
  2. Medium. Use paraphrase-multilingual-MiniLM-L12-v2 to build a cross-lingual retriever over a small mixed-language corpus. Query in English, retrieve documents in any language. Measure recall@5.
  3. Hard. Compare English-source and Hindi-source fine-tuning for a Hindi classification task. Use 500 target-language examples for few-shot fine-tuning under both regimes. Report which source produces better Hindi accuracy and by how much. This is the LANGRANK thesis in miniature.

Solutions

SolutionP1 · Surprisingly few, with both models

Only 23% with the multilingual MiniLM, and 8% with the English-only one. The multilingual model aligns translations well for the roughly 50 languages it was trained on with parallel data (85 to 95% for French, German, Chinese, Arabic and Hindi in the same run), but Tamil was not one of them. The English-only model cannot read Tamil script meaningfully at all. "Multilingual" is a list of specific languages, and the list for a fine-tuned model can be shorter than for its pretrained backbone.

SolutionB1 · It scores contradiction instead of entailment

With index 2, each "score" is the probability that the text contradicts "This text is about {label}". The ranking turns upside down: a clearly positive review contradicts "the sentiment is negative" strongly, so "negative" gets the highest score and is predicted. Nothing errors and the numbers look like confident probabilities, which is what makes this bug dangerous. Always read the label order from model.config.label2id, as the rewritten code does.
