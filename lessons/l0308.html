About the model on this page
The "models" on this page are scripted stand-ins

Every function whose name ends in _model, and the planner, solver and replanner, are plain Python with fixed rules. They stand where a real model call would go, so each trace is identical on every run and you can study the control flow of each pattern. The tools, the executor, the checker and the search are real code. Lesson 14.3 showed how to connect the same loops to a real model API.

Why this came about

The first tool-using models answered in one shot and failed on anything needing several steps. In 2022 the ReAct paper showed that letting a model alternate between a short written thought, one action and the observation that came back solved multi-step questions far more reliably. But ReAct calls the model after every single step, and on long tasks it can wander or lose the goal. Through 2023 researchers proposed fixes, each trading something: plan-and-execute and ReWOO plan first to save calls; Reflexion has the model learn from a failed attempt; Tree of Thoughts and LATS search over several lines of reasoning; CodeAct has the model write code instead of single tool calls. Since 2024, reasoning models (Lesson 10.14) do much of this planning internally, so these patterns matter today mainly as ways to structure the code around a model: where it is called, what it sees, and what checks it.

In plain words first
Asking for directions at every corner, or planning the trip

There are two ways to drive to an unfamiliar address. You can stop at every corner and ask which way next: slow, but you recover easily from a closed road. Or you can plan the whole route before leaving: fast, but if a road is closed the plan is useless until you re-plan. Agents face the same choice. Reacting step by step adapts well and costs many model calls; planning first is cheaper and easier to review, and needs a way to notice surprises. Two more ideas sit on top: checking your work against something concrete before handing it in (reflection), and trying several routes on paper and keeping the best (search).

The task for this lesson

One customer question that needs several lookups and a little arithmetic. Three tools, each a plain function:

ORDERS = {
    "SK-48213": {"item": "mixer", "price": 2499, "status": "delivered"},
    "SK-48377": {"item": "kettle", "price": 1299, "status": "packed"},
    "SK-48502": {"item": "yoga mat", "price": 899, "status": "shipped"},
}
CUSTOMERS = {"C-1001": ["SK-48213", "SK-48377", "SK-48502"]}
POLICY = {"packed": {"can_cancel": True, "fee": 0}, "shipped": {"can_cancel": True, "fee": 100},
          "delivered": {"can_cancel": False, "fee": 0}}

def list_orders(customer_id):
    return CUSTOMERS.get(customer_id, [])

def get_order(order_id):
    return ORDERS.get(order_id, "not found")

def cancel_policy(status):
    return POLICY.get(status, "unknown status")

TOOLS = {"list_orders": list_orders, "get_order": get_order, "cancel_policy": cancel_policy}
QUESTION = "I am customer C-1001. Which of my orders can I still cancel, and how much would I get back in total?"

def work_out(orders, policies):
    """The final reasoning step, shared by every pattern below: turn looked-up facts into an answer."""
    ok = [(oid, o["price"] - policies[o["status"]]["fee"]) for oid, o in orders.items() if policies[o["status"]]["can_cancel"]]
    return f"You can cancel {' and '.join(oid for oid, _ in ok)}. You would get Rs {sum(r for _, r in ok):,} back."

The correct answer needs: the customer's orders, each order's status and price, the cancellation rule for each status, and a sum. The work_out function is the last reasoning step; every pattern below must gather the facts it needs.

Step 1 · ReAct: think, act, observe, repeat

In ReAct the model is called once per step. Each call sees the question and everything that has happened so far, writes a short thought, and chooses one action. Your code runs the action and appends the observation. This is the agent loop of Lesson 14.3 with the model's reasoning made visible.

def react_model(question, steps):
    """Stand-in for a language model following a ReAct prompt: read everything so far, decide ONE next step."""
    seen = {(s["action"], s["args"]): s["observation"] for s in steps}
    order_ids = seen.get(("list_orders", "C-1001"))
    if order_ids is None:
        return {"thought": "I need to know which orders this customer has.", "action": "list_orders", "args": "C-1001"}
    for oid in order_ids:
        if ("get_order", oid) not in seen:
            return {"thought": f"I have not looked at {oid} yet.", "action": "get_order", "args": oid}
    orders = {oid: seen[("get_order", oid)] for oid in order_ids}
    for o in orders.values():
        if ("cancel_policy", o["status"]) not in seen:
            return {"thought": f"What is the rule for a {o['status']} order?", "action": "cancel_policy", "args": o["status"]}
    policies = {o["status"]: seen[("cancel_policy", o["status"])] for o in orders.values()}
    return {"thought": "I have every fact I need.", "answer": work_out(orders, policies)}

def run_react(question, model, max_steps=10):
    steps, read = [], 0
    for call in range(1, max_steps + 1):
        read += len(question) + sum(len(str(s)) for s in steps)        # every call re-reads the whole history
        decision = model(question, steps)
        print(f"call {call}  Thought: {decision['thought']}")
        if "answer" in decision:
            print(f"        Answer: {decision['answer']}")
            return call, read
        observation = TOOLS[decision["action"]](decision["args"])
        print(f"        Action: {decision['action']}({decision['args']!r})  ->  Observation: {observation}")
        steps.append({**decision, "observation": observation})
    return max_steps, read

calls, read = run_react(QUESTION, react_model)
print(f"\nReAct: {calls} model calls, {read:,} characters read by the model in total")

ReAct: 8 model calls, 5,232 characters read by the model in total

Eight model calls for one question. Notice the last line: every call re-reads the whole history, so the text the model reads grows with each step. The total grows roughly with the square of the number of steps (Lesson 14.7 measured this as cost). In exchange, ReAct never committed to anything in advance: had list_orders returned five orders, or one, it would simply have carried on.

Reading this output
Reading this trace
  • Thought lines are text the model writes for its own benefit: stating what is missing before choosing an action makes the next action better (Lesson 10.14). With reasoning models this happens in a hidden thinking phase and you see only the action.
  • One action per call is the classic form. Modern APIs let a model request several tool calls in one turn (Lesson 14.5), which would let it fetch the three orders together and cut the calls from eight to four.
  • The loop stops when the model returns an answer, or at max_steps. The limit is enforced by your code, never by the model (Lesson 14.1).

Step 2 · Plan-and-execute: decide the steps once

If the steps can be known in advance, ask the model once for a plan, let ordinary code execute it, and ask the model once more to write the answer from the results. The plan here is a small data structure; steps can refer to the results of earlier steps:

def planner(question):
    """Stand-in for ONE model call that writes the whole plan before anything runs."""
    return [{"id": "orders", "tool": "list_orders", "args": ["C-1001"]},
            {"id": "details", "tool": "get_order", "for_each": "orders"},            # run once per item of an earlier result
            {"id": "rules", "tool": "cancel_policy", "for_each_field": ("details", "status")}]

def execute(plan):
    """Plain code runs the plan. No model calls here."""
    results = {}
    for step in plan:
        if "for_each" in step:
            results[step["id"]] = {x: TOOLS[step["tool"]](x) for x in results[step["for_each"]]}
        elif "for_each_field" in step:
            source, field = step["for_each_field"]
            values = {r[field] for r in results[source].values() if isinstance(r, dict)}
            results[step["id"]] = {v: TOOLS[step["tool"]](v) for v in sorted(values)}
        else:
            results[step["id"]] = TOOLS[step["tool"]](*step["args"])
        print(f"  ran {step['id']:<8} -> {results[step['id']]}")
    return results

def solver(question, results):
    """Stand-in for ONE model call that reads all the results and writes the answer."""
    return work_out(results["details"], results["rules"])

plan = planner(QUESTION)                                # model call 1
print("plan:", [s["id"] for s in plan])
results = execute(plan)                                 # tool calls only
answer = solver(QUESTION, results)                      # model call 2
print(answer)
read = len(QUESTION) + len(QUESTION) + len(str(results))
print(f"\nPlan-and-execute: 2 model calls, {read:,} characters read by the model in total")

Two model calls instead of eight, and the model read about a ninth of the text. The plan is also something a person, or a policy check, can read and approve before anything runs, which matters when steps have consequences. This is the idea behind the "plan mode" of coding agents and the to-do lists that long-running agents keep (Lesson 14.13).

Reading this output
ReWOO: a plan with no way back

The planner above wrote for_each steps because it could not know how many orders there would be. A stricter variant, ReWOO (reasoning without observation), writes every tool call up front with placeholders such as #E1 for "the result of step 1", runs them all, and solves. It uses the fewest tokens of any pattern, because the model never re-reads observations between steps. Its weakness is in the name: it cannot react to what the tools return. Use it for fixed lookups, such as "fetch these five fields and summarise them".

Step 3 · When the plan meets a surprise

Plans are written before the facts are known. Here the customer has a brand-new order that the order system has not synced yet:

CUSTOMERS["C-1001"].append("SK-49001")                  # the customer has a new order, but the order system has not synced it yet

def needs_replan(results):
    return [oid for oid, r in results["details"].items() if r == "not found"]

results = execute(planner(QUESTION))
missing = needs_replan(results)
print("\nsurprise:", missing, "not found")
try:
    print(solver(QUESTION, results))
except Exception as error:
    print("solver without a check fails:", type(error).__name__, error)

def replanner(question, results, problem):
    """Stand-in for a model call that revises the plan after a surprise."""
    results["details"] = {oid: r for oid, r in results["details"].items() if oid not in problem}
    return results, f"Note: I could not find {', '.join(problem)}; it may be too new. "

results, note = replanner(QUESTION, results, missing)   # model call 3, only because something went wrong
print(note + solver(QUESTION, results))
CUSTOMERS["C-1001"].remove("SK-49001")
What you should see
  ran orders   -> ['SK-48213', 'SK-48377', 'SK-48502', 'SK-49001']
  ran details  -> {'SK-48213': {'item': 'mixer', 'price': 2499, 'status': 'delivered'}, 'SK-48377': {'item': 'kettle', 'price': 1299, 'status': 'packed'}, 'SK-48502': {'item': 'yoga mat', 'price': 899, 'status': 'shipped'}, 'SK-49001': 'not found'}
  ran rules    -> {'delivered': {'can_cancel': False, 'fee': 0}, 'packed': {'can_cancel': True, 'fee': 0}, 'shipped': {'can_cancel': True, 'fee': 100}}

surprise: ['SK-49001'] not found
solver without a check fails: TypeError string indices must be integers, not 'str'
Note: I could not find SK-49001; it may be too new. You can cancel SK-48377 and SK-48502. You would get Rs 2,098 back.

The executor ran the plan faithfully and one lookup came back not found. A solver that assumes every step succeeded crashes (or, worse with a real model, confidently reports on an order it knows nothing about). The fix has two parts: code that checks each step's result against what the plan expected, and a re-plan call that is made only when something is off. Here re-planning drops the missing order and tells the customer. That third model call was spent only because it was needed, which is the practical advantage over ReAct.

Step 4 · Reflection needs something to reflect on

Reflection means checking a draft and revising it. The research version, Reflexion, stores a short written lesson from a failed attempt and retries with it. Whether reflection helps depends almost entirely on what the model is given to reflect on:

def draft_model(question):
    """Stand-in for a model's first attempt: right orders, but it forgot the return fee on the shipped order."""
    return {"orders": ["SK-48377", "SK-48502"], "refund": 1299 + 899}

def revise_model(question, draft, feedback):
    """Stand-in for a model asked to improve its draft. It can only fix what the feedback points at."""
    if "fee" in feedback:
        return {"orders": draft["orders"], "refund": draft["refund"] - 100}
    return dict(draft)                                   # vague feedback: same answer again

def checker(draft):
    """Real code, not a model: recompute the refund from the tools and compare."""
    expected = sum(ORDERS[o]["price"] - POLICY[ORDERS[o]["status"]]["fee"] for o in draft["orders"])
    if draft["refund"] != expected:
        return f"Refund should be {expected}, not {draft['refund']}: check the fee on shipped orders."
    return "ok"

draft = draft_model(QUESTION)
print("draft                     :", draft)
print("after 'please improve it' :", revise_model(QUESTION, draft, "Review your answer and improve it."))
feedback = checker(draft)
print("checker says              :", feedback)
final = revise_model(QUESTION, draft, feedback)
print("after concrete feedback   :", final, "| checker:", checker(final))
What you should see
draft                     : {'orders': ['SK-48377', 'SK-48502'], 'refund': 2198}
after 'please improve it' : {'orders': ['SK-48377', 'SK-48502'], 'refund': 2198}
checker says              : Refund should be 2098, not 2198: check the fee on shipped orders.
after concrete feedback   : {'orders': ['SK-48377', 'SK-48502'], 'refund': 2098} | checker: ok

"Please improve it" changed nothing, because it told the model nothing it did not already believe. The checker recomputed the refund from the tools, found a mismatch of exactly Rs 100, and said where to look. With that, one revision fixed it. The stand-in exaggerates for clarity, but the pattern is what studies and production teams report: self-critique with no new information mostly restates the draft, and sometimes talks the model out of a correct answer.

Good sources of a concrete signal, roughly from strongest to weakest:

Signal Example
Executing something Run the tests; run the SQL and inspect the rows; call the API in dry-run mode
A rule in code Recompute the total; validate against a schema; check every cited passage exists
Retrieved evidence Does each claim appear in the documents that were retrieved? (Lesson 14.27)
A second model with a rubric A grader that scores tone, completeness and policy points and must quote the problem (Lesson 14.115)
The same model, same prompt, "are you sure?" Weak: no new information

Lesson 14.8 built this as the evaluator-optimiser workflow. The rule to remember is that the evaluator must be able to see something the writer could not.

Step 5 · Search: try several plans, keep the best

ReAct and plan-and-execute follow one line of reasoning. Tree of Thoughts and LATS (language agent tree search) explore several: generate a few candidate next steps, score each partial result, keep the most promising, and repeat. The task below shows why that can matter. Three coupons can be applied to a Rs 2,400 basket, and the order changes the result:

COUPONS = {
    "PCT20": lambda price: price * 0.80,                                   # 20% off
    "FLAT300": lambda price: price - 300 if price >= 2000 else None,       # Rs 300 off, only on Rs 2,000 or more
    "FLAT100": lambda price: price - 100,
}

def propose(state):
    """Stand-in for a model proposing next moves: every coupon not used yet."""
    return [c for c in COUPONS if c not in state["used"]]

def apply(state, coupon):
    new_price = COUPONS[coupon](state["price"])
    if new_price is None:
        return None                                                        # coupon does not apply here
    return {"used": state["used"] + [coupon], "price": new_price}

def search(start_price, beam_width):
    """Keep the best `beam_width` partial plans at each depth; expand each; repeat."""
    beam, evaluated = [{"used": [], "price": start_price}], 0
    for depth in range(len(COUPONS)):
        candidates = []
        for state in beam:
            for coupon in propose(state):
                nxt = apply(state, coupon)
                evaluated += 1
                candidates.append(nxt if nxt else state)                   # an invalid coupon leaves the state as it was
        beam = sorted(candidates, key=lambda s: s["price"])[:beam_width]   # the evaluator here is simply the price
    return beam[0], evaluated

for width in (1, 2, 6):
    best, evaluated = search(2400, width)
    print(f"beam width {width}: {' then '.join(best['used']):<32} -> Rs {best['price']:,.0f}   ({evaluated} states evaluated)")
What you should see
beam width 1: PCT20 then FLAT100               -> Rs 1,820   (6 states evaluated)
beam width 2: FLAT300 then PCT20 then FLAT100  -> Rs 1,580   (9 states evaluated)
beam width 6: FLAT300 then PCT20 then FLAT100  -> Rs 1,580   (16 states evaluated)

With a beam width of 1 the search is greedy: it takes the 20% coupon first because that gives the biggest immediate saving, and then the Rs 300 coupon no longer applies. Keeping the two best states at each depth finds the order that saves Rs 240 more. Keeping all six finds the same answer and evaluates almost twice as many states. In a real agent every "state evaluated" is at least one model call to propose it and often another to score it, so search multiplies cost by the beam width times the depth.

Reading this output
When search is worth it

Search pays off when three things are true: a wrong early choice is expensive to undo, partial results can be scored reliably (here, the price; in coding, the tests), and you can afford many times the cost of a single run. That describes some coding, theorem-proving and planning problems. It does not describe most business agents, where a reasoning model in a plain loop is the better first choice, and where actions on real systems cannot be tried and undone. Reasoning models perform a form of this search internally during their thinking phase, at a price you pay in thinking tokens.

Step 6 · CodeAct: let the model write the loop

Every pattern so far spends model calls on control flow: "now fetch the next order". A model that can write code can express the whole control flow in one reply. In CodeAct, the tools are functions and the model's action is a short program that calls them:

def codeact_model(question):
    """Stand-in for ONE model call that answers by writing a short program that calls the tools."""
    return '''
orders = {oid: get_order(oid) for oid in list_orders("C-1001")}
rules = {o["status"]: cancel_policy(o["status"]) for o in orders.values()}
ok = {oid: o["price"] - rules[o["status"]]["fee"] for oid, o in orders.items() if rules[o["status"]]["can_cancel"]}
result = f"You can cancel {' and '.join(ok)}. You would get Rs {sum(ok.values()):,} back."
'''

code = codeact_model(QUESTION)                           # model call 1 (and only)
namespace = {"__builtins__": {"sum": sum}, **TOOLS}      # the program may use the three tools and sum(), nothing else
exec(code, namespace)                                    # NEVER do this with real model output outside a sandbox
print(namespace["result"])
print(f"\nCodeAct: 1 model call, {len(QUESTION):,} characters read; the loop over orders ran in code")
What you should see
You can cancel SK-48377 and SK-48502. You would get Rs 2,098 back.

CodeAct: 1 model call, 100 characters read; the loop over orders ran in code

One model call, and the loop over orders, the lookups and the arithmetic all ran as ordinary code. The intermediate results never passed through the model's context at all, which is why this pattern (also called programmatic tool calling or "code mode") is spreading in agents that work with many tools or large tool results. smolagents (Lesson 14.89) is built around it.

Watch out
Code written by a model must run in a sandbox

The exec call above runs a fixed string that this lesson wrote, with almost every built-in function removed. Real model output is untrusted input: it can contain mistakes, and text from a web page or document can talk a model into writing harmful code (prompt injectionlater · 15.22, Lesson 15.22). Emptying __builtins__ is not a security boundary in Python. Production systems run model-written code in an isolated sandboxlater · 15.23: a container or micro-VM with no credentials, no network except what you allow, and time and memory limits (Lesson 15.23).

Two cautions from practice. First, reasoning models have absorbed much of this: prompts that force "think step by step" or elaborate plan formats often make them worse, not better (Lesson 11.6). Try the plain loop with a strong model before adding structure. Second, every pattern adds model calls, and the only way to know whether one earned its cost is to run your evaluation set with and without it (Lesson 14.116).

The agent improvement loop

Like RAGlater · 10.37, agents improve in a loop: trace real runs, find the most common failure, apply the matching fix, re-run the evals. The table maps symptoms to fixes in the order most teams try them. Notice how often the fix is a tool, an instruction or a piece of code rather than a bigger model.

6 It forgets facts from earlier in the conversation Keep key facts (customer, order IDs, decisions) in structured state, and summarize older turns Long-term memorylater · 14.11 for facts that matter across sessions Summaries that paraphrase IDs and amounts: keep those verbatim
7 It trusts stale or wrong memories Store a source and timestamp with every memory; prefer live tool data over memory Update or expire memories instead of appending duplicates A week-old "your order shipped" memory overriding today's status
8 Answers vary between runs Structured outputs, examples for the edge cases, lower temperature where supported A fixed workflow for that path Judging consistency from single runs; use repeated runs (pass^k)

10 Long tasks drift away from the goal A plan or to-do file the agent updates and re-reads Subagentslater · 14.12 with clean contexts for isolated subtasks; checkpoints Compaction that drops the plan itself

Check your mental model
  • ✗ "Planning always improves results."
    ✓ Plans go stale. Without checks and re-planning, a plan makes the agent ignore new evidence.
  • ✗ "Self-reflection fixes mistakes reliably."
    ✓ Only when the check supplies new information: a failing test, a recomputed number, a missing citation.
  • ✗ "ReAct, plan-and-execute and Tree of Thoughts are different kinds of model."
    ✓ They are control flow around the same models: where the model is called and what it sees.
  • ✗ "Reasoning models make these patterns obsolete."
    ✓ They reduce the need for prompting tricks. Plans you can review, checks in code and step budgets still matter.
  • ✗ "CodeAct is safe if I remove the dangerous built-ins."
    ✓ Model-written code needs a real sandbox.

Solutions

SolutionP1 · One more order

ReAct makes 9 calls: one more get_order, and no extra cancel_policy because "packed" has already been looked up. Plan-and-execute still makes 2: the for_each step simply runs once more in code. The total becomes Rs 3,697 (1,299 + 799 + 1,599). The cost of ReAct grows with the size of the task; the cost of a plan grows only when the shape of the task changes.

SolutionB1 · A silent skip

The answer lists the two cancellable orders and says nothing about SK-49001. The customer, who asked about all their orders, is told a total that silently leaves one out, and nobody is alerted that the order system is behind. A crash is visible and gets fixed; a silently wrong answer is repeated to every affected customer. Surprises should be surfaced: to the model (re-plan), to the user (a note), and to your logs.

SolutionD1 · Reflection without a signal

"Improve it" gives the model no new information, so it rewrites in place. It rarely finds errors it could not see the first time. Reflection helps when the critique carries a concrete signal: a failing test, a schema error, a policy check, a missing citation. Use the improvement loop instead: read the failing traces, label why each failed, and fix the cause (context, tools, instructions), measured on the evaluation set. If a check exists for the common failure, run it and feed its message back, as Step 4 does.

SolutionM1 · A wider tree

There are now 24 orders in which to apply four coupons. Beam width 2 may or may not contain the best path, depending on how the intermediate prices rank: a path that looks third-best after one step is dropped even if it would have won. Compare with search(2400, 24). No beam width short of "everything" is guaranteed, which is why search needs a scoring function that predicts final quality, not only current quality, and why wider beams buy reliability with cost.

SolutionX1 · Matching patterns to tasks

(a) A workflow or ReWOO: a fixed query and a summary; check that the ten amounts in the summary match the query result. (b) ReAct with a reasoning model: each finding decides the next lookup; add a step budget and require the answer to cite the records it used. (c) Any loop plus reflection with execution as the signal: run the query on a sample database and feed errors or suspicious results back (Lesson 14.35). (d) Search, or better, an optimisation library called as a tool: the score (total cost) is exact, and a solver will beat a language model at combinatorics.

Check your understanding

Explain the mechanismCompare ReAct, plan-and-execute and reflection.

Worked answer. ReAct interleaves reasoning with tool calls and observations, deciding one step at a time; it adapts well, costs a model call per step, and can wander. Plan-and-execute writes a plan first and has code execute it, which is cheaper, more predictable and reviewable, and needs checks plus re-planning when steps fail. Reflection critiques an output and revises it; it helps when the critique has a concrete signal, such as tests or a rubric. Modern reasoning models do much of this internally, so the patterns now mostly shape the harnesslater · 14.13 around the model.

A plausible wrong answer. "They are different model architectures." They are prompting and control patterns over the same models.

Follow-ups. Where does a reasoning model's internal thinking replace these patterns?

Debug a failureAn agent's plans look good but it often stops before finishing. What do you check?

Worked answer. The stop conditions: step limits and budgets that are too tight, a planner that marks steps done without checking results, or a final step that is skipped when a tool returns an error. Read traces of unfinished runs, check whether each step's success condition was verified, and add a final check that the goal is met before answering.

A plausible wrong answer. "The model is lazy." Stopping early is almost always a limit or a missing success check.

Follow-ups. How would you make "goal met" checkable?

Defend a designShould every agent have a planner?

Worked answer. No. Short tasks with one or two tool calls do better with a plain loop; a planner adds a call and a structure that must be kept in sync with reality. Planners pay off for long, multi-step tasks where order matters and progress must be visible, especially across context resets (Lesson 14.13). Decide with evaluations on the actual tasks.

A plausible wrong answer. "Yes, planning always improves reasoning." It improves some long tasks and slows down short ones.

Follow-ups. How would you show a plan to the user, and when would you not?

Recap
  • ReAct calls the model once per step and re-reads the whole history each time: most adaptable, most expensive.
  • Plan-and-execute spends one call on a plan and one on the answer; code runs the steps. Add checks and a re-plan step for surprises. ReWOO is the same with no way to adapt.
  • Reflection works when the check gives the model new, concrete information.
  • Search keeps several partial plans alive; it needs a reliable score and multiplies cost.
  • CodeAct replaces many small tool-call turns with one program, and requires a sandbox.
  • Start with a plain loop and a strong model; add a pattern only when your evaluation set shows it helps.
