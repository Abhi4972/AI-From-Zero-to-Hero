Why this came about

Agent costs surprised many teams, because each task makes several calls and resends growing context. Cost engineering, measuring cost per task and applying caching, routing and step reduction, became a standard discipline.

In plain words first
Paying for what you use, knowingly

Agent cost is the sum of every model call (input and output tokens, with the input re-sent each step) plus tools and infrastructure. Cost engineering measures cost per successful task, then pulls the big levers: fewer steps, shorter inputs, caching repeated prefixes, cheaper models where they are good enough, and limits that stop runaway runs.

Cost is per run, not per call

An agent run makes several model calls, and each call re-reads the system prompt, tool definitions and a growing history. That is why agents cost 5 to 50 times more than a single chat answer, and why the levers below are mostly about not re-reading tokens.

from dataclasses import dataclass

@dataclass
class Price:                     # USD per million tokens; illustrative numbers, check your provider's price list
    input: float
    output: float
    cached_input: float          # cache reads are typically ~10% of the input price

STRONG = Price(input=3.00, output=15.00, cached_input=0.30)
SMALL = Price(input=0.25, output=1.25, cached_input=0.025)

def run_cost(p: Price, steps: int, system_tokens: int, history_growth: int, output_per_step: int,
             cache_hit: float) -> float:
    """Cost of one agent run: every step re-reads the system prompt plus a growing history."""
    total = 0.0
    for step in range(steps):
        history = step * history_growth
        cached = system_tokens * cache_hit                    # the stable prefix can be cached
        fresh = system_tokens - cached + history
        total += (cached * p.cached_input + fresh * p.input + output_per_step * p.output) / 1e6
    return total

base = dict(steps=6, system_tokens=6000, history_growth=800, output_per_step=300)
scenarios = {
    "strong model, no caching": run_cost(STRONG, cache_hit=0.0, **base),
    "strong model, prompt caching": run_cost(STRONG, cache_hit=0.9, **base),
    "small model, prompt caching": run_cost(SMALL, cache_hit=0.9, **base),
}
for name, c in scenarios.items():
    print(f"{name:30} ${c:.4f} per run   ${c * 100_000:,.0f} per 100k runs")

# A cascade: try the small model; escalate to the strong one when the small one is not confident
def cascade_cost(share_escalated: float) -> float:
    small = scenarios["small model, prompt caching"]
    strong = scenarios["strong model, prompt caching"]
    return small + share_escalated * strong                   # escalated runs pay for both attempts

for share in (0.1, 0.3, 0.6):
    print(f"cascade, {share:.0%} escalated:        ${cascade_cost(share):.4f} per run")
What you should see
strong model, no caching       $0.1710 per run   $17,100 per 100k runs
strong model, prompt caching   $0.0835 per run   $8,352 per 100k runs
small model, prompt caching    $0.0070 per run   $696 per 100k runs
cascade, 10% escalated:        $0.0153 per run
cascade, 30% escalated:        $0.0320 per run
cascade, 60% escalated:        $0.0571 per run

Prompt caching halved the cost without changing a word of the output. A cascade is cheap only if few requests escalate: at 60% escalation it costs almost as much as using the strong model always, plus extra latency. Measure the escalation rate before adopting one.

The levers, roughly in order of payoff

Lever How Watch out
Prompt caching Keep the stable prefix (instructions, tools, documents) identical and first; dynamic content last Any change early in the prompt (a timestamp!) breaks the cache
Shorter context Trim and summarize history, return compact tool results, retrieve less but better Losing facts the agent needs
Fewer steps Better tools that do more per call; parallel tool calls; plan once Over-merged tools are harder for models to use
Right-size models Small models for routing, extraction and formatting; strong models where reasoning matters Validate per step on evals
Reasoning effort Use low effort or no extended thinking where it adds nothing Hard steps degrade quietly
Batch APIs Offline work (evals, enrichment, summaries) through batch endpoints, typically at about half price Hours of latency
Caching answers Exact and semantic caches for repeated questions (Lesson 14.111) Wrong or stale answers
Provisioned throughput or committed use Discounts for steady, predictable volume Paying for idle capacity
Self-hosting At very high, steady volume (Lesson 14.112) Operations cost and quality

Latency follows the same levers: fewer sequential model calls, smaller contexts, streaming, parallel tools, and prefix caching (which also cuts time to first token).

Hands-on · Shorter context: compact tool results

The cheapest token is one the model never reads. Tool results are the usual culprit: an internal API returns everything it knows, and that blob then sits in the context for every remaining step of the run:

import json

def est_tokens(text: str) -> int:
    return len(text) // 4                      # rough rule for English; use your tokenizer for real numbers

order_api_response = {   # what the internal API returns
    "order": {"id": "A-1001", "status": "SHIPPED", "status_code": 40, "created_at": "2026-10-20T10:31:22.123Z",
              "updated_at": "2026-10-22T08:02:11.004Z", "customer": {"id": "C-42", "segment": "gold", "kyc": "done",
              "addresses": [{"type": "home", "line1": "12 MG Road", "city": "Pune", "pin": "411001"}] * 2},
              "items": [{"sku": f"SKU-{i}", "title": "Steel bottle 1L", "qty": 1, "price_inr": 499,
                         "warehouse": "PNQ-2", "hsn": "7323"} for i in range(6)],
              "shipment": {"carrier": "BlueDart", "awb": "BD123456789IN", "eta": "2026-10-24",
                           "events": [{"ts": "2026-10-22T08:02:11Z", "code": "PICKED", "loc": "PNQ-2"}] * 8},
              "audit": [{"by": "system", "action": "update", "ts": "2026-10-22T08:02:11Z"}] * 10}}

def compact(resp: dict) -> str:
    """Return only what the model needs, in plain words, with names instead of codes."""
    o = resp["order"]
    return (f"Order {o['id']}: shipped via {o['shipment']['carrier']}, arriving {o['shipment']['eta']}. "
            f"{len(o['items'])} items, total INR {sum(i['price_inr'] * i['qty'] for i in o['items'])}.")

raw, small = json.dumps(order_api_response), compact(order_api_response)
STEPS_AFTER = 4                                 # the result stays in context for the rest of the run
for label, text in (("raw JSON", raw), ("compact", small)):
    t = est_tokens(text)
    print(f"{label:9} ~{t:5,} tokens, re-read {STEPS_AFTER} more times: ~{t * (STEPS_AFTER + 1):6,} input tokens per run")
print("compact text:", small)
What you should see
raw JSON  ~  591 tokens, re-read 4 more times: ~ 2,955 input tokens per run
compact   ~   20 tokens, re-read 4 more times: ~   100 input tokens per run
compact text: Order A-1001: shipped via BlueDart, arriving 2026-10-24. 6 items, total INR 2994.

A thirtyfold reduction, and usually better answers: the model no longer has to find three useful fields among audit logs and status codes. Anthropic's tool-writing guidance recommends exactly this (return meaningful, compact context; offer a response_format parameter for "concise" versus "detailed" when the model sometimes needs more). The character-count estimate is rough; count with your provider's tokenizer or the usage field for real numbers.

In production
Cost cuts that backfire
  • A cheaper model that retries more: more failed tool calls and clarifications can make the cheap model cost more per resolved task. Always compare cost per successful outcome, not per call.
  • Over-trimmed context: dropping history saves tokens and causes the agent to ask the user again. Trim tool results first, pinned facts last.
  • Caching personal answers: savings on paper, privacy incident in practice.
  • Batch for interactive work: users wait hours. Batch only work nobody is waiting for.

Hands-on · Right-size models with a router

A router sends each request to the cheapest model likely to handle it. Choosing its threshold is a measurement, not a guess: label a sample with whether each model succeeds, then trace the quality and cost of every threshold:

import random

random.seed(1)
# A labeled sample: for each request, a difficulty score from a cheap router, and whether each model solves it
SAMPLE = []
for _ in range(1000):
    hard = random.random() < 0.25
    score = min(1.0, max(0.0, random.gauss(0.7 if hard else 0.3, 0.15)))       # the router's difficulty estimate
    SAMPLE.append({"score": score, "small_ok": random.random() < (0.55 if hard else 0.96),
                   "strong_ok": random.random() < (0.93 if hard else 0.98)})
COST = {"small": 0.004, "strong": 0.060}       # USD per run

def evaluate(threshold: float) -> tuple[float, float]:
    ok, spend = 0, 0.0
    for r in SAMPLE:
        use_strong = r["score"] >= threshold
        ok += r["strong_ok"] if use_strong else r["small_ok"]
        spend += COST["strong" if use_strong else "small"]
    return ok / len(SAMPLE), spend / len(SAMPLE)

print(f"{'policy':16} {'quality':>8} {'cost/run':>9}")
for label, t in [("always small", 1.01), ("route at 0.65", 0.65), ("route at 0.50", 0.50), ("route at 0.35", 0.35), ("always strong", -0.01)]:
    q, c = evaluate(t)
    print(f"{label:16} {q:8.1%} {c:9.4f}")
What you should see
policy            quality  cost/run
always small        85.5%    0.0040
route at 0.65       92.1%    0.0141
route at 0.50       95.3%    0.0218
route at 0.35       96.1%    0.0323
always strong       96.7%    0.0600

Routing at 0.50 keeps 95.3% quality, within 1.4 points of always using the strong model, at about a third of the cost. Whether those points are worth $0.04 per run is a product decision; this table is what makes it a decision instead of an argument. Routers can be a small classifier, an embedding similarity to known-hard examples, or the small model's own confidence; RouteLLM and the gateways in Lesson 14.111 provide ready-made ones.

Hands-on · Batch what does not need an answer now

Evaluations, enrichment, nightly summaries and backfills do not need a reply in seconds. Batch APIs take a file of requests and return results within hours, typically at about half price:

import json, pathlib

tickets = [{"id": f"T-{i}", "text": f"Customer says order A-10{i:02d} arrived damaged."} for i in range(3)]
with pathlib.Path("summaries_batch.jsonl").open("w") as f:
    for t in tickets:
        f.write(json.dumps({
            "custom_id": t["id"],                                   # how you match results back
            "method": "POST", "url": "/v1/chat/completions",
            "body": {"model": "small-model", "max_tokens": 120,
                     "messages": [{"role": "system", "content": "Summarize the ticket in one line."},
                                  {"role": "user", "content": t["text"]}]}}) + "\n")
print(pathlib.Path("summaries_batch.jsonl").read_text().splitlines()[0][:110], "...")

def monthly(n_items: int, tokens_in: int, tokens_out: int, price: tuple, discount: float = 0.0) -> float:
    return n_items * (tokens_in * price[0] + tokens_out * price[1]) / 1e6 * (1 - discount)

SMALL_PRICE = (0.25, 1.25)                                          # USD per million (input, output)
n = 2_000_000                                                       # tickets summarized per month
print(f"real-time API: ${monthly(n, 700, 60, SMALL_PRICE):,.0f}/month; "
      f"batch API at 50% off: ${monthly(n, 700, 60, SMALL_PRICE, 0.5):,.0f}/month")
What you should see
{"custom_id": "T-0", "method": "POST", "url": "/v1/chat/completions", "body": {"model": "small-model", "max_to ...
real-time API: $500/month; batch API at 50% off: $250/month

That line format is OpenAI's Batch API; Anthropic's Message Batches, Bedrock batch inferencelater · 14.138, Vertex AI batch prediction and Azure's global batch deployments take similar files. Batch runs also stay out of your real-time rate limits, which protects interactive traffic during a large backfill.

FinOps for AI

FinOps is the practice of making engineering teams accountable for cloud spend with shared data. For AI:

  • Attribution: tag every model call with team, application, feature, tenant and environment (at the gateway, Lesson 14.111), and report cost per unit of value: per resolved ticket, per report, per active user.
  • Budgets and alerts: per team and per tenant, with anomaly detection on daily spend and a hard ceiling per run.
  • Forecasting: traffic times cost per run, per model, with scenarios for model price changes.
  • Showback or chargeback: teams see (or pay) for what they use.
  • Review cadence: a monthly look at the biggest cost drivers, with the eval suite ready to test cheaper options.

The FinOps Foundation publishes guidance on managing AI spend, and its FOCUS standard for billing data helps combine costs from several cloud and AI providers in one view.

Hands-on · Unit economics from usage records

Attribution starts with one row per run, tagged with team, feature, model and outcome. From there, cost per resolved outcome falls out:

from collections import defaultdict

PRICES = {"strong-model": (3.00, 15.00), "small-model": (0.25, 1.25)}       # USD per million (input, output)
USAGE = [   # one row per agent run, as your gateway or traces record it
    {"team": "support", "feature": "order-status", "model": "small-model", "in": 9_000, "out": 600, "resolved": True},
    {"team": "support", "feature": "order-status", "model": "small-model", "in": 8_200, "out": 500, "resolved": True},
    {"team": "support", "feature": "refunds", "model": "strong-model", "in": 31_000, "out": 2_100, "resolved": True},
    {"team": "support", "feature": "refunds", "model": "strong-model", "in": 44_000, "out": 2_900, "resolved": False},
    {"team": "support", "feature": "refunds", "model": "strong-model", "in": 29_000, "out": 1_800, "resolved": True},
    {"team": "growth", "feature": "product-copy", "model": "strong-model", "in": 3_000, "out": 4_000, "resolved": True},
]

def cost(row: dict) -> float:
    pin, pout = PRICES[row["model"]]
    return (row["in"] * pin + row["out"] * pout) / 1e6

by_feature = defaultdict(lambda: {"cost": 0.0, "runs": 0, "resolved": 0})
for row in USAGE:
    f = by_feature[(row["team"], row["feature"])]
    f["cost"] += cost(row); f["runs"] += 1; f["resolved"] += row["resolved"]

HUMAN_COST_PER_RESOLUTION = 0.70          # USD; what a human-handled ticket costs, from finance
for (team, feature), f in sorted(by_feature.items(), key=lambda kv: -kv[1]["cost"]):
    per_resolved = f["cost"] / f["resolved"]
    print(f"{team:8} {feature:13} ${f['cost']:.4f} over {f['runs']} runs | ${per_resolved:.4f} per resolved "
          f"| {HUMAN_COST_PER_RESOLUTION / per_resolved:,.0f}x cheaper than a person")
What you should see
support  refunds       $0.4140 over 3 runs | $0.2070 per resolved | 3x cheaper than a person
growth   product-copy  $0.0690 over 1 runs | $0.0690 per resolved | 10x cheaper than a person
support  order-status  $0.0057 over 2 runs | $0.0028 per resolved | 247x cheaper than a person

Order status is almost free. The refunds feature costs seventy times more per resolution, partly because the failed run still has to be paid for, and it is only three times cheaper than a person. That is where to spend optimization effort, and the failed run is where to look first.

Hands-on · Catch a spend spike the day it happens

A loop bug or an abusive tenant shows up as a sudden jump in daily spend. Compare each day with a robust baseline (the median and median absolute deviation of the previous week, which one old spike cannot distort):

import statistics

daily_spend = [212, 198, 225, 205, 219, 201, 230, 214, 208, 222, 217, 203, 611, 226]   # USD per day, from billing export

def anomalies(series: list[float], window: int = 7, k: float = 5.0) -> list[tuple[int, float, float]]:
    """Flag days far above the recent median, using the median absolute deviation (robust to past spikes)."""
    flagged = []
    for i in range(window, len(series)):
        past = series[i - window:i]
        med = statistics.median(past)
        mad = statistics.median(abs(x - med) for x in past) or 1.0
        if (series[i] - med) / mad > k:
            flagged.append((i, series[i], med))
    return flagged

for day, value, typical in anomalies(daily_spend):
    print(f"day {day}: ${value} vs typical ${typical:.0f} -> alert the owner and check the top runs by cost")
What you should see
day 12: $611 vs typical $214 -> alert the owner and check the top runs by cost

Daily is the slowest useful cadence; the per-run ceiling (Lesson 14.57) and per-tenant budgets at the gateway (Lesson 14.111) stop runaway spend within minutes. AWS Cost Anomaly Detection, Azure Cost Management alerts and Google Cloud budget alerts do this for cloud bills; run your own on the gateway's per-team data, which arrives sooner and in more detail.

Industry practice
Unit economics decide what you build

Teams that keep AI programs funded report cost per business outcome next to quality: "₹4 per resolved support conversation at 92% resolution, against ₹60 for a human-handled one." That framing turns cost work into product decisions (is a cheaper model at 89% resolution better value?) and catches agents that look cheap per call but expensive per outcome.

Choose by scenario
Cost is too high: the order to work through
Step Lever Typical effect Check before you ship it
1 Measure cost per resolved outcome, per feature and per step Shows where the money goes Tags on every call (Lesson 14.111)
2 Prompt caching: stable prefix first, dynamic content last Large on agents, which are input-heavy Cache-hit rate in usage data
3 Trim context: compact tool results, summarize old turns Often the largest single cut on long runs Quality on the eval set
4 Route easy requests to a small model Large if most traffic is easy Quality per route (this lesson's router table)
5 Batch anything that can wait About half price on supported APIs Latency is acceptable for the use
6 Cache whole answers for repeated questions Depends on repetition False-hit rate on labeled pairs (Lesson 14.111)
7 Fine-tune or distill a small model for one high-volume step Large for narrow tasks Held-out eval against the current model (Lesson 14.133)
8 Provisioned capacity or self-hosting for steady load Depends on utilization Break-even utilization (Lesson 14.112)

Most teams get the bulk of their savings from steps 2 to 4 without touching model weights.

From the field
Manus: agents are input-heavy, so caching decides the bill

Manus reports an average input-to-output token ratio of about 100:1 for its agent, because every step re-reads a growing context while producing a short action. With Claude Sonnet, cached input cost 0.30 USD per million tokens against 3 USD uncached at the time, so the share of input served from cache dominated cost and also time to first token. That is why the team treats KV-cache hit rate as its key production metric, keeps prompts append-only, and avoids anything that changes the start of the prompt between steps. Solutions

SolutionP1 · Measure the cost drivers

It depends on where tokens go. Measure input versus output tokens, cacheable share and calls per task; for agents with long system prompts and tools, caching often wins first.

SolutionB1 · Cost per outcome

It can rise: more retries, longer conversations and more handoffs to people. Measure cost per resolved task, not per call.

SolutionD1 · Hidden growth

Context growth (longer histories, larger tool results), more tool loops, lower cache hit rates after a prompt change, and retries. Compare token breakdowns before and after.

SolutionM1 · A cost table

Rows for tracking, refund and FAQ conversations; columns for averages from logs; the optimization per row (caching, a smaller model for classification, trimming tool output).
