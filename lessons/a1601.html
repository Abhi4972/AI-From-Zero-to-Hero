The idea in one line

One agent hits a wall. The smart move is not a bigger agent - it is more agents.

Terms you'll hear
Term What people say What it actually means
Swarm "A hive mind of AI agents" A set of peer agents with shared state and no fixed leader. Behavior emerges from local interactions.
Orchestrator "The boss agent" An agent whose tools include spawning and managing other agents. It plans and delegates but may not do the actual work.
Coordinator "The traffic cop" A non-agent component (often just code, not an LLM) that routes messages between agents based on rules.
Consensus "The agents agree" A protocol where multiple agents must reach agreement before proceeding. Used when conflicting outputs need resolution.
Emergent behavior "The agents figured it out themselves" System-level patterns that arise from agent interactions but were not explicitly programmed. Can be useful or harmful.
Fan-out / fan-in "Map-reduce for agents" Splitting a task across parallel agents (fan-out), then combining their results (fan-in).
Message passing "Agents talk to each other" The communication mechanism between agents: structured data sent from one agent to another, replacing shared context windows.

The problem

In plain words first

A multi-agent system splits one job across several model calls, each with its own instructions and its own context, and passes messages between them. It helps when a task is too big for one context, needs different skills at different stages, or can run in parallel. It costs more tokens, and every handoff can lose information. Multi-agent systems are introduced in Lesson 14.66 (linked above). This lesson measures the context and cost trade in tokens, then tries one agent against a fan-out of readers on a real small model.

You built a single agent in Phase 14. It works. It can read files, run commands, call APIs, and reason about results. Then you point it at a real codebase: 200 files, three languages, tests that depend on infrastructure, and a requirement to research external APIs before writing code.

The agent chokes. Not because the LLM is dumb, but because the task exceeds what one agent loop can handle. The context window fills up with file contents. The agent forgets what it read 40 tool calls ago. It tries to be a researcher, a coder, and a reviewer all at once, and does all three poorly.

This is the single-agent ceiling. You hit it every time a task requires:

  • More context than fits in one window - reading 50 files blows past 200k tokens
  • Different expertise at different stages - research requires different prompting than code generation
  • Work that can happen in parallel - why read three files sequentially when you can read them simultaneously?

Idea 1 · The Single-Agent Ceiling

A single agent is one loop, one context window, one system prompt. Picture it:

┌─────────────────────────────────────────┐
│            SINGLE AGENT                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         Context Window            │  │
│  │                                   │  │
│  │  research notes                   │  │
│  │  + code files                     │  │
│  │  + test output                    │  │
│  │  + review feedback                │  │
│  │  + API docs                       │  │
│  │  + ...                            │  │
│  │                                   │  │
│  │  ██████████████████████ FULL ███  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  One system prompt tries to cover       │
│  research + coding + review + testing   │
│                                         │
│  Result: mediocre at everything         │
└─────────────────────────────────────────┘

Three things break:

  1. Context saturation - tool results pile up. By turn 30, the agent has consumed 150k tokens of file contents, command outputs, and prior reasoning. Critical details from turn 5 get lost.

  2. Role confusion - a system prompt that says "you are a researcher, coder, reviewer, and tester" produces an agent that half-researches, half-codes, and never finishes reviewing.

  3. Sequential bottleneck - the agent reads file A, then file B, then file C. Three serial LLM calls. Three serial tool executions. No parallelism.

Idea 2 · The Multi-Agent Solution

Split the work. Give each agent one job, one context window, and one system prompt tuned for that job:

┌──────────────────────────────────────────────────────────┐
│                    ORCHESTRATOR                          │
│                                                          │
│  "Build a REST API for user management"                  │
│                                                          │
│         ┌──────────┬──────────┬──────────┐               │
│         │          │          │          │               │
│         ▼          ▼          ▼          ▼               │
│   ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐  │
│   │RESEARCHER│ │  CODER   │ │ REVIEWER │ │  TESTER  │  │
│   │          │ │          │ │          │ │          │  │
│   │ Reads    │ │ Writes   │ │ Checks   │ │ Runs     │  │
│   │ docs,    │ │ code     │ │ code     │ │ tests,   │  │
│   │ finds    │ │ based on │ │ quality, │ │ reports  │  │
│   │ patterns │ │ research │ │ finds    │ │ results  │  │
│   │          │ │ + spec   │ │ bugs     │ │          │  │
│   └─────┬────┘ └────┬─────┘ └────┬─────┘ └────┬─────┘  │
│         │           │            │             │         │
│         └───────────┴────────────┴─────────────┘         │
│                          │                               │
│                     Merge results                        │
└──────────────────────────────────────────────────────────┘

Each agent has: - A focused system prompt ("You are a code reviewer. Your only job is finding bugs.") - Its own context window (not polluted by other agents' work) - A clear input/output contract (receives research notes, outputs code)

Idea 3 · Real Systems That Do This

Claude Code subagents - when Claude Code spawns a subagent with its Agent tool (called Task before v2.1.63), it creates a child agent with a scoped task. The parent keeps its context clean. The child does focused work and returns a summary. By default subagents can nest 3 layers deep and 20 can run at once.

Anthropic's Research feature - a lead agent (Claude Opus 4) plans and spawns parallel subagents (Claude Sonnet 4) that each search a different angle, then synthesises their findings. On Anthropic's internal research eval it beat a single Opus 4 agent by 90.2%, while using about 15 times the tokens of a chat.

Single-agent coding systems (SWE-bench) - many of the strongest SWE-bench results come from one agent with a shell and an editor; mini-SWE-agent, about 100 lines of Python, scores close to far more elaborate systems. Coding is a task where extra agents often add coordination cost without adding accuracy.

The counter-argument (Cognition) - the makers of Devin published "Don't Build Multi-Agents" (June 2025): parallel subagents make conflicting decisions because they do not share context, so for long coding tasks they keep one thread and compress its history instead.

Idea 4 · The Spectrum

Multi-agent is not binary. It is a spectrum:

SIMPLE ──────────────────────────────────────────── COMPLEX

 Single        Sub-         Pipeline      Team         Swarm
 Agent         agents

 ┌───┐       ┌───┐        ┌───┐───┐    ┌───┐───┐    ┌─┐┌─┐┌─┐
 │ A │       │ A │        │ A │ B │    │ A │ B │    │ ││ ││ │
 └───┘       └─┬─┘        └───┘─┬─┘    └─┬─┘─┬─┘    └┬┘└┬┘└┬┘
               │                │        │   │       ┌┴──┴──┴┐
             ┌─┴─┐          ┌───┘───┐    │   │       │shared │
             │ a │          │ C │ D │  ┌─┴───┴─┐    │ state │
             └───┘          └───┘───┘  │  msg   │    └───────┘
                                       │  bus   │
 1 loop      Parent +      Stage by    │       │    N peers,
 1 context   child tasks   stage       └───────┘    emergent
                                       Explicit      behavior
                                       roles

Single agent - one loop, one prompt. Good for simple tasks.

Subagents - a parent spawns children for focused subtasks. The parent maintains the plan. Children report back. This is what Claude Code does.

Pipeline - agents run in sequence. Agent A's output becomes Agent B's input. Good for staged workflows: research -> code -> review -> test.

Team - agents run in parallel with a shared message bus. Each has a role. An orchestrator coordinates. Good when different skills are needed simultaneously.

Swarm - many identical or near-identical agents with shared state. No fixed orchestrator. Agents pick up work from a queue. Good for high-throughput parallel tasks.

Idea 5 · The Four Multi-Agent Patterns

Pattern 1: Pipeline

Input ──▶ Agent A ──▶ Agent B ──▶ Agent C ──▶ Output
          (research)  (code)      (review)

Each agent transforms the data and passes it forward. Simple to reason about. Failure in one stage blocks the rest.

Pattern 2: Fan-out / Fan-in

                ┌──▶ Agent A ──┐
                │              │
Input ──▶ Split ├──▶ Agent B ──├──▶ Merge ──▶ Output
                │              │
                └──▶ Agent C ──┘

Split work across parallel agents, then merge results. Good for tasks that decompose into independent subtasks.

Pattern 3: Orchestrator-Worker

                    ┌──────────┐
                    │  Orch.   │
                    └──┬───┬───┘
                  task │   │ task
                 ┌─────┘   └─────┐
                 ▼               ▼
           ┌──────────┐   ┌──────────┐
           │ Worker A │   │ Worker B │
           └──────────┘   └──────────┘

A smart orchestrator decides what to do, delegates to workers, and synthesizes results. The orchestrator is itself an agent with tools for spawning workers.

Pattern 4: Peer Swarm

         ┌───┐ ◄──── msg ────▶ ┌───┐
         │ A │                  │ B │
         └─┬─┘                  └─┬─┘
           │                      │
      msg  │    ┌───────────┐     │ msg
           └───▶│  Shared   │◄────┘
                │  State    │
           ┌───▶│  / Queue  │◄────┐
           │    └───────────┘     │
      msg  │                      │ msg
         ┌─┴─┐                  ┌─┴─┐
         │ C │ ◄──── msg ────▶ │ D │
         └───┘                  └───┘

No central orchestrator. Agents communicate peer-to-peer. Decisions emerge from interaction. Harder to debug, but scales to many agents.

Idea 6 · When NOT to Use Multi-Agent

Multi-agent adds complexity. Every message between agents is a potential failure point. Debugging goes from "read one conversation" to "trace messages across five agents."

Stay single-agent when: - The task fits in one context window (under ~100k tokens of working data) - You do not need different system prompts for different stages - Sequential execution is fast enough - The task is simple enough that splitting it adds more overhead than value

The complexity cost: - Every agent boundary is a lossy compression step: agent A's full context gets summarized into a message for agent B - Coordination logic (who does what, when, in what order) is its own source of bugs - Latency increases: N agents means N serial LLM calls minimum, more if they need to talk back and forth - Cost multiplies: each agent burns tokens independently

Rule of thumb: if a task takes fewer than 20 tool calls and fits in 100k tokens, keep it single-agent.

The same idea as a formula

Context per call. Stage k of a single agent sees everything so far, ck​=s+∑j≤k​aj​, where s is the system prompt and aj​ the artifact from stage j. A specialist sees only its inputs, ck​=sk​+ink​. The largest single context grows with every stage; the largest specialist context is just the biggest single job.

Total tokens. Splitting does not make the work free. With m agents each reading its own input, total input is ∑k​ck​, and with r rounds of back-and-forth it multiplies by roughly r. Anthropic reports agents using about 4× the tokens of a chat, and multi-agent systems about 15×.

Handoff compression. If agent A reads TA​ tokens and sends a Tm​-token message, the compression ratio is TA​/Tm​. Large ratios are the point of a handoff, and also where facts get lost.

Worked example
Counting one pipeline
  • Research reads five documentation pages, about 5,000 tokens.
  • The single agent re-sends them with the code (about 5,600 tokens) and again with the code and the review (about 5,900 tokens). That is about 16,500 input tokens across three stages.
  • In the pipeline the researcher reads the same 5,000 once. The coder gets a 25-token summary plus the code (about 630), and the reviewer gets the code plus the review (about 880). That is about 6,500 tokens in all.
  • The summary compresses research 200 to 1. Anything not in those 25 tokens never reaches the coder.
Check your mental model
  • ✗ "More agents always do better."
    ✓ Anthropic's research system did; Cognition argues the opposite for coding; and here the fan-out scored 1 of 10 against the single agent's 9.
  • ✗ "Splitting saves tokens."
    ✓ It caps each agent's context. Fan-out made 90 calls where the single agent made 10, and used more tokens in total.
  • ✗ "A sub-agent's report is a faithful copy."
    ✓ The small model's reader summarised its file wrongly instead of copying the line, and the orchestrator then invented an answer.
  • ✗ "Claude Code subagents use the Task tool."
    ✓ The tool is now called Agent; it was Task before v2.1.63.

Reading this output

The single agent's context grows every stage. It carries the five pages of research into the coding stage (about 5,600 tokens) and into the review (about 5,900). The pipeline's coder sees about 630 tokens and its reviewer about 880, because each gets only what it needs.

The pipeline uses fewer input tokens here, about 6,500 against 16,500. That is because the single agent re-sends the research twice. It holds only for a one-pass pipeline: add review rounds or parallel agents and the total climbs again.

The handoff is a 200-to-1 compression. About 5,000 tokens of research become a 25-token summary. That is what keeps the coder's context clean, and also where a missed detail disappears.

At scale, tokens are money. At $3 per million input tokens and 1,000 tasks a day, a chat-sized answer costs about $6 a day, one agent about $24, and a multi-agent run at Anthropic's reported 15x about $90.

# This block continues from the one above: does splitting help a real small model? Eight project files (configs and
# notes, about 3,000 tokens in all) and ten questions, each answered by one line in one file. Qwen2.5-0.5B-Instruct
# (greedy, CPU) answers either as one agent with every file in its context, or as a fan-out: one sub-agent per file
# reports a matching line or NONE, and an orchestrator answers from the reports. Accuracy, model calls and tokens are
# counted for both. About 2 minutes.
import random, re, torch
from transformers import AutoModelForCausalLM
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

rng = random.Random(5)
SERVICES = ["auth", "billing", "search", "inventory", "checkout", "email", "reports", "gateway"]
FACTS, FILES = {}, {}
for i, svc in enumerate(SERVICES):
    port, timeout, owner = 8000 + 37 * i + rng.randint(1, 9), rng.choice([5, 10, 15, 30, 45, 60]), rng.choice(
        ["Asha", "Bruno", "Chen", "Dana", "Emeka", "Farah", "Goran", "Hana"])
    FACTS[svc] = {"port": port, "timeout": timeout, "owner": owner}
    filler = "".join(f"# note {k}: {svc} logs rotate daily and metrics go to the shared dashboard.\n" for k in range(14))
    FILES[f"{svc}.yaml"] = (f"service: {svc}\n{filler}listen_port: {port}\nrequest_timeout_seconds: {timeout}\n"
                            f"owner: {owner}\nreplicas: {rng.randint(2, 6)}\n")
QUESTIONS = [(f"What port does the {s} service listen on?", str(FACTS[s]["port"])) for s in SERVICES[:4]] + \
            [(f"What is the request timeout in seconds for the {s} service?", str(FACTS[s]["timeout"])) for s in SERVICES[4:7]] + \
            [(f"Who owns the {s} service?", FACTS[s]["owner"]) for s in ("gateway", "billing", "email")]
def chat(prompt, n=24):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True, return_tensors="pt",
                                  return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip(), ids.shape[1]
everything = "\n\n".join(f"=== {name} ===\n{body}" for name, body in FILES.items())
results = {"single agent": [0, 0, 0], "fan-out": [0, 0, 0]}       # right, model calls, input tokens
for q, ans in QUESTIONS:
    reply, t = chat(f"Project files:\n{everything}\n\nQuestion: {q} Answer with the value only.")
    r = results["single agent"]; r[0] += ans in reply; r[1] += 1; r[2] += t
    reports = []
    for name, body in FILES.items():
        rep, t = chat(f"File {name}:\n{body}\nDoes this file answer the question: {q}\n"
                      "If yes, copy the one line that answers it. If not, reply NONE.", 20)
        r = results["fan-out"]; r[1] += 1; r[2] += t
        if "none" not in rep.lower():
            reports.append(f"{name}: {rep}")
    final, t = chat("Reports from file readers:\n" + ("\n".join(reports) or "(no reports)") + f"\n\nQuestion: {q} Answer with the value only.")
    r = results["fan-out"]; r[0] += ans in final; r[1] += 1; r[2] += t
print(f"{'setup':<14} {'right':>6} {'model calls':>12} {'input tokens':>13}")
for k, (right, calls, toks) in results.items():
    print(f"{k:<14} {right:>4}/10 {calls:>12} {toks:>13,}")

The single agent got 9 of 10. All eight files fit in about 2,300 tokens, well within what even this small model can read, so it found the line and copied the value.

Step 1 · The Overloaded Single Agent

Here is a single agent trying to do everything. It has one massive system prompt and one context window holding research, code, and reviews:

type AgentResult = {
  content: string;
  tokensUsed: number;
  toolCalls: number;
};

async function singleAgentApproach(task: string): Promise<AgentResult> {
  const systemPrompt = `You are a full-stack developer. You must:
1. Research the requirements
2. Write the code
3. Review the code for bugs
4. Write tests
Do ALL of these in a single conversation.`;

  const contextWindow: string[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const research = await fakeLLMCall(systemPrompt, `Research: ${task}`);
  contextWindow.push(research.output);
  totalTokens += research.tokens;
  totalToolCalls += research.calls;

  const code = await fakeLLMCall(
    systemPrompt,
    `Given this research:\n${contextWindow.join("\n")}\n\nNow write code for: ${task}`
  );
  contextWindow.push(code.output);
  totalTokens += code.tokens;
  totalToolCalls += code.calls;

  const review = await fakeLLMCall(
    systemPrompt,
    `Given all previous context:\n${contextWindow.join("\n")}\n\nReview the code.`
  );
  contextWindow.push(review.output);
  totalTokens += review.tokens;
  totalToolCalls += review.calls;

  return {
    content: contextWindow.join("\n---\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}

Problems with this approach: - The context window grows with every stage. By the review step, it contains research notes AND code AND prior reasoning. - The system prompt is generic. It cannot be tuned for each stage. - Nothing runs in parallel.

Step 2 · Specialist Agents

Now split it. Each agent gets one job:

type SpecialistAgent = {
  name: string;
  systemPrompt: string;
  run: (input: string) => Promise<AgentResult>;
};

function createSpecialist(name: string, systemPrompt: string): SpecialistAgent {
  return {
    name,
    systemPrompt,
    run: async (input: string) => {
      const result = await fakeLLMCall(systemPrompt, input);
      return {
        content: result.output,
        tokensUsed: result.tokens,
        toolCalls: result.calls,
      };
    },
  };
}

const researcher = createSpecialist(
  "researcher",
  "You are a technical researcher. Read documentation, find patterns, and summarize findings. Output only the facts needed for implementation."
);

const coder = createSpecialist(
  "coder",
  "You are a senior TypeScript developer. Given requirements and research notes, write clean, tested code. Nothing else."
);

const reviewer = createSpecialist(
  "reviewer",
  "You are a code reviewer. Find bugs, security issues, and logic errors. Be specific. Cite line numbers."
);

Each specialist has a focused prompt. Each gets a clean context window with only the input it needs.

Step 3 · Coordinate Through Messages

Wire the specialists together with explicit message passing:

type AgentMessage = {
  from: string;
  to: string;
  content: string;
  timestamp: number;
};

async function multiAgentApproach(task: string): Promise<AgentResult> {
  const messages: AgentMessage[] = [];
  let totalTokens = 0;
  let totalToolCalls = 0;

  const researchResult = await researcher.run(task);
  messages.push({
    from: "researcher",
    to: "coder",
    content: researchResult.content,
    timestamp: Date.now(),
  });
  totalTokens += researchResult.tokensUsed;
  totalToolCalls += researchResult.toolCalls;

  const coderInput = messages
    .filter((m) => m.to === "coder")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const codeResult = await coder.run(coderInput);
  messages.push({
    from: "coder",
    to: "reviewer",
    content: codeResult.content,
    timestamp: Date.now(),
  });
  totalTokens += codeResult.tokensUsed;
  totalToolCalls += codeResult.toolCalls;

  const reviewerInput = messages
    .filter((m) => m.to === "reviewer")
    .map((m) => `[From ${m.from}]: ${m.content}`)
    .join("\n");

  const reviewResult = await reviewer.run(reviewerInput);
  messages.push({
    from: "reviewer",
    to: "orchestrator",
    content: reviewResult.content,
    timestamp: Date.now(),
  });
  totalTokens += reviewResult.tokensUsed;
  totalToolCalls += reviewResult.toolCalls;

  return {
    content: messages.map((m) => `[${m.from} -> ${m.to}]: ${m.content}`).join("\n\n"),
    tokensUsed: totalTokens,
    toolCalls: totalToolCalls,
  };
}

Each agent receives only the messages addressed to it. No context pollution. The researcher's 50k tokens of documentation reading never enter the reviewer's context.

async function compare() {
  const task = "Build a rate limiter middleware for an Express.js API";

  console.log("=== Single Agent ===");
  const single = await singleAgentApproach(task);
  console.log(`Tokens: ${single.tokensUsed}`);
  console.log(`Tool calls: ${single.toolCalls}`);

  console.log("\n=== Multi-Agent ===");
  const multi = await multiAgentApproach(task);
  console.log(`Tokens: ${multi.tokensUsed}`);
  console.log(`Tool calls: ${multi.toolCalls}`);
}

The multi-agent version uses more total tokens (three agents, three separate LLM calls) but each agent's context stays clean. The quality of each stage improves because the system prompt is specialized.

Break it on purpose

Your team replaces a working coding agent with five agents (planner, two coders, reviewer, tester) that run in parallel. Merge conflicts appear in a third of runs, the two coders pick different libraries for the same feature, and costs triple. Using this lesson, what went wrong, and when would the split have been right? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Subagents are a product feature. Claude Code's Agent tool spawns subagents with their own context and tool lists, nested up to 3 deep and 20 at once by default; the Agent SDK also has a Workflow tool for runs of dozens to hundreds of agents. OpenAI's Agents SDK has handoffs, and LangGraph and CrewAI build graphs and crews.
  • Research is the clearest win. Anthropic's Research feature uses an Opus lead with parallel Sonnet subagents and reported a 90.2% gain over a single agent on its internal eval, at about 15x the tokens of a chat.
  • Coding is contested. Cognition argues for one thread with compressed history, and strong SWE-bench scores come from single-agent scaffolds such as mini-SWE-agent.
  • On your laptop: a small local model cannot carry a long context well, but it also copies poorly between agents. Measure both setups on your own task before choosing.

Sources: Anthropic, Multi-agent research system, Cognition, Don't Build Multi-Agents, Claude Agent SDK, Subagents, mini-SWE-agent.

Recap
What to keep from this lesson
  • Split work when it exceeds one context, needs different instructions per stage, or can run in parallel.
  • Each specialist gets a smaller context, but total tokens and calls go up, often by a lot.
  • Every handoff compresses; check that the facts the next agent needs survive it.
  • Parallel agents that share no context can make conflicting decisions.
  • If a task fits in one context and one prompt, a single agent is usually better and cheaper.

Solutions

SolutionP1 · The single agent wins, with a ninth of the calls

The single agent wins, 9 of 10 against 1 of 10, and it uses 10 model calls against 90. The files fit comfortably in one context, so splitting only added handoffs. In the fan-out the reader with the right file misreported it, and the orchestrator, given no correct line, made up an answer.

The fan-out would earn its cost only if the files did not fit in one context, or if readers could run in parallel on a much larger corpus, and even then its handoffs need checking.

SolutionB1 · Parallel coders with no shared context

The task was not one that splits cleanly. Coding decisions depend on each other, and two coders working in parallel without shared context made conflicting choices, which is exactly Cognition's argument. The planner's handoff did not carry the decisions the coders needed, and every extra agent added tokens.

What would have helped: - Keep one agent for the coding thread, and use subagents only for side tasks that do not make decisions, such as searching the codebase or running tests. - Pass decisions, not just tasks: the library choice, interfaces and constraints go in every handoff. - Run the parallel version only where work is independent, such as reviewing separate files or researching separate questions. - Measure: compare accuracy, merge conflicts and cost against the single agent before switching.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismYour single agent does well on small tasks. Pointed at a codebase of 200 files in three languages, with tests that need infrastructure and an external API to research first, it stops making progress. The team proposes a model with a bigger window. What is the ceiling it hit, and would a bigger window remove it?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. The task exceeds what one loop, one window and one system prompt can carry, and a bigger window only moves one of three limits. Context saturates as tool results pile up, so details from an early turn are gone by turn 30, and one prompt that asks the model to research, code, review and test produces an agent that does each one poorly. One loop reads file A, then B, then C, with no parallelism. The fix for all three is to split the work so that each agent has one job, one window and one prompt.

Three things break.

  1. Context saturation. Tool results accumulate. By turn 30 the agent has consumed about 150k tokens of file contents, command output and its own reasoning, and the detail from turn 5 is lost. Reading 50 large files can pass a 200k window.
  2. Role confusion. A system prompt that says you are a researcher, a coder, a reviewer and a tester produces an agent that half-researches, half-codes and never finishes the review.
  3. Sequential bottleneck. The agent reads three files in three serial model calls and three serial tool executions. Nothing runs at the same time.

What a bigger window changes.

It delays the first limit and does nothing for the other two. The agent still forgets what it read 40 tool calls ago, because the problem is attention over a long history, not the hard limit. The prompt still asks one model to be four roles. The loop is still serial.

The split.

Give each agent one job, one window and one prompt tuned for that job. The researcher reads documents and outputs only the facts needed for implementation. The coder receives those facts and writes code. The reviewer receives the code and finds bugs. The researcher's reading never enters the reviewer's window, because each agent receives only the messages addressed to it.

When to stay single.

The lesson's rule of thumb: a task that takes fewer than 20 tool calls and fits in 100k tokens stays with one agent. Splitting costs more total tokens, adds coordination logic that has its own bugs, and turns debugging from reading one conversation into tracing messages across several.

Plausible wrong answers.

  • "A bigger context window solves it." The window moves one limit and leaves role confusion and the serial loop untouched.
  • "A longer, more detailed system prompt covers the roles." A single prompt that covers four roles is the cause of role confusion, not the cure.
  • "Always split, because specialists are better." Below about 20 tool calls and 100k tokens, the split adds cost and bugs for no gain.

Follow-ups an interviewer may ask.

  • (level 1) Which of the three limits does parallelism address? Expected: the sequential bottleneck only, because reading three files at once does not shrink any one window or sharpen any one prompt.
  • (level 2) Why does a specialized prompt improve each stage? Expected: a prompt that covers one role can be specific about inputs, outputs and what to ignore, while a prompt for four roles has to be generic.
  • (level 2) What is the cost that the split always adds? Expected: more total tokens, because each agent is a separate model call, plus latency and coordination logic.
  • (level 3) Where does information get lost in a multi-agent split? Expected: at every agent boundary, where one agent's full context is compressed into a message for the next.

Weigh a trade-offA team proposes a five-agent pipeline, with a planner, a retriever, a writer, a critic and a formatter, for a summarization feature that one agent handles today in a dozen tool calls. The argument is that specialists produce better output. How do you decide, and what will the pipeline cost that the slide does not show?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Keep the single agent unless the task fails one of three tests: it needs more context than one window holds, it needs different prompts at different stages, or it has work that can run at the same time. A dozen tool calls on a task that fits in one window passes none of them. The pipeline adds a lossy compression step at each of four boundaries, coordination logic that has its own bugs, at least five serial model calls of latency, and five times the token cost.

The three tests.

Test What it asks This task
Context Does the working data exceed one window, roughly 100k tokens? No, a dozen tool calls fit
Expertise Do stages need different system prompts? A summarizer and a formatter can share one prompt
Parallelism Can parts of the work run at the same time? The stages are serial

The lesson's rule of thumb is that a task under 20 tool calls and 100k tokens stays with one agent.

The hidden costs.

  • Lossy boundaries. Every message between agents compresses the sender's full context into a message. Four boundaries are four places where the detail the critic needed is gone.
  • Coordination bugs. Who runs when, in which order, with which input is new code, and it fails in new ways.
  • Latency. Five agents are at least five serial model calls, more if the critic sends work back to the writer.
  • Cost. Each agent spends its own tokens, so the bill multiplies.
  • Debugging. One conversation becomes five, and a wrong answer has to be traced across the messages between them.

When the slide would be right.

If the feature grows to summarize documents that do not fit in one window, split by document and merge. If the critic needs a prompt that argues against the writer, that is a real second role. If three sources can be read at once, fan out. Each of those is one of the three tests, and the split should match the test it passes, not add every role at once.

How to settle it.

Run both on the same task set and measure quality, latency and tokens. The lesson's comparison shows the multi-agent version using more total tokens while each stage's context stays clean. If the quality gain does not pay for the latency and the cost, the single agent wins.

Plausible wrong answers.

  • "Specialists always beat a generalist." Specialists win when the task fails one of the three tests, and this task fails none.
  • "More agents means more checks, so quality goes up." Each boundary loses information, and a critic that never sees the sources cannot check them.
  • "Token cost does not matter at our scale." Five agents multiply the bill and the latency on every request, and that is a product decision, not a detail.

Follow-ups an interviewer may ask.

  • (level 2) The critic sends the draft back to the writer. What does that do to the latency? Expected: each round adds two more serial model calls, so the loop must have a cap on rounds.
  • (level 2) Which single split would you accept first, if any? Expected: a critic with an adversarial prompt, because it is the one role that needs a different system prompt, and only if the eval shows a gain.
  • (level 3) Why is the boundary between agents described as lossy compression? Expected: the receiving agent sees only the message, not the sender's tool results and reasoning, so any detail that was not written into the message is gone.
  • (level 3) How does the choice change if the summaries must be produced under a strict latency target? Expected: serial stages are the enemy of latency, so stay single or fan out only the parts that run in parallel.
