Every Build Contains Bets

In plain words first

Every feature rests on things the team believes but has not checked: "the alert says which service failed", "engineers will trust the answer". Write each one as a statement that could turn out false, and score three things: how bad it is if false (impact), how weak the evidence is (uncertainty), and how costly it is to learn late (irreversibility). Then test the riskiest open one first, with a pass mark written down before the test runs. Design review and the practitioner playbook are covered in Zero to Agents 12.19 (linked above). This lesson maps the incident agent's assumptions from 14.48 and runs the top experiment for real.

An incident tool may depend on all of these being true:

  • alert context contains enough information to identify a service;
  • engineers trust a recommendation they did not derive themselves;
  • the desired response time matters operationally;
  • required data can be accessed without unsafe authority;
  • the workflow happens often enough to justify maintenance.

These are not implementation tasks. They are conditions for the build to be valuable, usable, feasible, and safe.

Assumption Classes

Class Question
Value Will the outcome matter enough?
Usability Can the user understand and act on it?
Feasibility Can the system produce it with available data and constraints?
Viability Can the organization sustain cost, ownership, and operation?
Safety Can it fail without unacceptable consequence?

Write assumptions as falsifiable statements. “The feature is useful” cannot be tested. “Eight of ten on-call engineers identify the correct service faster with the read-only result” can.

Risk Is Not One Number

The lab uses three dimensions from one to five:

  • Impact: damage if the assumption is false.
  • Uncertainty: weakness of current evidence.
  • Irreversibility: cost of learning after commitment.

The example score multiplies impact and uncertainty, then adds irreversibility. The formula is not universal. Its purpose is to force the team to state why one unknown should be resolved before another.

Design an Experiment, Not a Confirmation Ritual

A useful test has:

  • a claim that could be false;
  • a population or realistic sample;
  • an observable result;
  • a threshold decided before the result;
  • a next decision for pass, fail, and ambiguous evidence.

Avoid tests that only demonstrate that the team can build the idea.

Reversibility Changes Order

High-consequence, irreversible choices need earlier evidence. A read-only replay can precede a production integration. A temporary adapter can precede a data migration. A human-approved recommendation can precede automatic action.

The shape of the build should follow the shape of uncertainty.

The same idea as a formula

The lesson's score. With impact I, uncertainty U and irreversibility R, each from 1 to 5:

risk=I⋅U+R.

Here R only adds, so it breaks ties. Under I⋅U⋅R an irreversible bet dominates. Try a few rules and see whether the top item changes.

A threshold turns a test into a decision. Fix the pass mark k∗ out of n before the run. With n=10 and k∗=8, an observed 10 of 10 has a rough 95% lower bound on the true rate of about 1−3/10=70% (rule of three). That holds only for alerts like the ones sampled.

Worked example
Two rules, one top item
  • "Alert context is enough" scores I=5,U=5,R=2: 5⋅5+2=27 (lesson), 5⋅5⋅2=50 (product).
  • "The agent may roll back without approval" scores 5,4,5: 5⋅4+5=25 (lesson), 5⋅4⋅5=100 (product).
  • So the lesson's rule tests the alert first, and the product rule puts automatic rollback first. The second one is not answered by an experiment at all. It is answered by a decision: keep approval.
  • Pairwise, the rules agree on 5 of 6 orderings (83%). They disagree only on which of those two comes first.

Part 1 of 2 · Assumption, risk_score, prioritize, next_experiment, example

# Lesson program: ranks assumptions and selects the next risk-reducing experiment.
# Lesson: phases/14-agent-engineering/49-map-assumptions-and-risk/docs/en.md
# Canonical source: Boehm, Spiral Model, DOI 10.1145/12944.12948.
# Canonical source: Dardenne et al., Goal-Directed Requirements Acquisition.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Assumption:
    statement: str
    impact: int
    uncertainty: int
    irreversibility: int
    test: str
    evidence: str = ""


def risk_score(item: Assumption) -> int:
    for value in (item.impact, item.uncertainty, item.irreversibility):
        if value not in range(1, 6):
            raise ValueError("risk dimensions must be integers from one to five")
    return item.impact * item.uncertainty + item.irreversibility


def prioritize(items: list[Assumption]) -> list[dict]:
    ranked = sorted(items, key=lambda item: (-risk_score(item), item.statement))
    return [{**asdict(item), "risk_score": risk_score(item), "status": "tested" if item.evidence else "open"} for item in ranked]


def next_experiment(items: list[Assumption]) -> Assumption | None:
    open_items = [item for item in items if not item.evidence]
    return max(open_items, key=risk_score, default=None)


def example() -> list[Assumption]:
    return [
        Assumption("Engineers can identify the right service from alert context", 5, 5, 2, "Replay ten incidents with a read-only prototype"),
        Assumption("Two-minute diagnosis matters", 4, 2, 1, "Interview five incident commanders", "four of five confirmed"),
        Assumption("Automatic remediation is acceptable", 5, 4, 5, "Do not automate; test approval workflow first"),
    ]


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "assumption-map.json"
    output.write_text(json.dumps(prioritize(example()), indent=2) + "\n", encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Solutions

SolutionP1 · A clean pass on an easy sample

Yes: 10 of 10, clearing the threshold of 8. It does not hold on messier alerts. On four harder ones, where the symptom is in one service and the cause in another or outside the catalog, the model gets none right and three times names checkout-api.

The threshold was honest, but the sample was easy. A pre-registered test is only as decisive as the population it draws from.

SolutionB1 · A confirmation ritual

It was a confirmation ritual. The team wrote the demo set, so every answer was in the alert text, and no case had a cause outside the catalog or in another service than the symptom.

A real experiment draws its sample from past incident records, including cascades and infrastructure failures, and sets the threshold before the run. It also adds a "none of these" answer and scores it, and reports results by alert type. A pass on the easy type with a fail on cascades should lead to a narrower slice: answer only when the alert names a single service, and otherwise say "unknown". It should not lead to a launch.

What You Keep

Keep outputs/assumption-map.json. The next lesson uses it to choose the smallest slice that can produce decisive evidence.

Break it on purpose

A team's experiment for "the model can name the failing service" passes 20 of 20 on a demo set the team wrote, and they ship. Within a week the agent blames checkout-api for a DNS outage and for a payments timeout. Using this lesson, what was wrong with the experiment, and what should it have been? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Success criteria before the build. Anthropic's guide to defining success asks for specific, measurable criteria and a test set drawn from real cases before you tune a prompt or pick a model.
  • Pre-registered metrics and guardrails. Experimentation platforms (Statsig, Microsoft's ExP and others) require the primary metric and guardrail metrics to be declared before an experiment starts, so a result cannot be reinterpreted afterwards.
  • Read-only first. Shadow modes and replays of past traffic are the usual first test for an AI feature that will later act. Launch reviews in the Google SRE tradition gate the irreversible steps.
  • On your laptop: the map and scoring are standard-library Python. The replay runs the 0.5B model on CPU in about a minute.

Sources: Anthropic, Define your success criteria, Statsig, Experiments overview, Microsoft Research, Experimentation Platform, Google SRE book, Reliable product launches at scale.

Recap
What to keep from this lesson
  • Write assumptions as statements that could be false, by class: value, usability, feasibility, viability, safety.
  • Score impact, uncertainty and irreversibility separately; try more than one rule.
  • Write the claim, sample, observable, threshold and next decisions before the run.
  • Record whether evidence supports or rejects; "tested" is not "true".
  • The sample defines what a pass means. Test on the messy cases too.

OWCheat sheet · Outcomes, Workflows, Risks and Specs

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designYou join a team with a quarter-long roadmap for an assistant that recommends a next action to on-call engineers. The roadmap lists features in priority order. Tell me how you decide what to work on in week one, and why it may not be the first roadmap item.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. A roadmap hides uncertainty inside features. I rewrite the features as falsifiable assumptions about value, usability, feasibility, viability and safety, then score each one on impact, uncertainty and irreversibility. Week one goes to the cheapest decisive test of the highest open risk, which is often not the top roadmap item.

Features are bets.

The assistant only pays off if several conditions hold: alert context contains enough information to name a service, engineers trust a recommendation they did not derive, the response time matters operationally, the data is reachable without unsafe authority, and the workflow happens often enough to justify maintenance. None of these is an implementation task. They are conditions for the build to be worth doing.

Five classes.

Class Question
Value Will the outcome matter enough?
Usability Can the user understand and act on it?
Feasibility Can the system produce it with the available data and limits?
Viability Can the organization sustain the cost, the ownership and the operation?
Safety Can it fail without an unacceptable consequence?

An assumption has to be written so that it can be false. "The feature is useful" cannot be tested. "Eight of ten on-call engineers name the correct service faster with the read-only result" can.

Risk is three numbers, not one.

The lesson scores impact, uncertainty and irreversibility separately, each from one to five, multiplies impact by uncertainty and adds irreversibility. The formula is not sacred. Its job is to force the team to say why one unknown must be resolved before another. Irreversible, high-consequence choices need earlier evidence: a read-only replay can precede a production integration, and a human-approved recommendation can precede automatic action.

An experiment, not a confirmation ritual.

A useful test has a claim that could be false, a realistic sample, an observable result, a threshold decided before the result, and a next decision for pass, fail and ambiguous evidence. A demo that only shows the team can build the idea is not a test.

Plausible wrong answers.

  • "Build the first roadmap item; the order was agreed." Agreement on order is not evidence that the riskiest assumption holds.
  • "Ship something small and see what happens." A small build without a claim, a threshold and a next decision learns nothing.
  • "Risk is just how likely it is to fail." Impact and irreversibility change the order even when the probability is the same.

Follow-ups an interviewer may ask.

  • (level 2) The highest-risk assumption is tested and holds. What changes? Expected: it moves from open to tested with its evidence attached, and the next experiment targets the next highest open risk.
  • (level 2) Which assumption class do feature lists most often omit? Expected: safety, the question of whether the feature can fail without unacceptable consequence.
  • (level 3) The roadmap owner says the ranking already reflects risk. How do you check? Expected: compare the risk ranking with the roadmap order and explain each mismatch; where they differ, one of them is wrong about the evidence.
  • (level 3) Write a threshold that would stop the build. Expected: for example, fewer than a stated share of engineers in the replay trust the read-only recommendation enough to act on it.

Where it is taught. The assumption map lesson gives the five classes, the three risk dimensions and the shape of a decisive experiment.
