In plain words first
The idea in one line

A model is not a product. A pipeline is. The pipeline is everything from raw data to deployed prediction, and every step must be reproducible.

Terms you'll hear
Term What people say What it actually means
Pipeline "Chain of transforms + model" An ordered sequence of fitted transformers and a model, applied as one unit to prevent leakage
Data leakage "Test info leaked into training" Using information from outside the training set to build the model, inflating performance estimates
ColumnTransformer "Different preprocessing per column" Applies different pipelines to different subsets of columns, combining results
Experiment tracking "Logging your runs" Recording parameters, metrics, artifacts, and code versions for every training run
MLflow "Track and deploy models" Open-source platform for experiment tracking, model registry, and deployment
DVC "Git for data" Version control system for large data files, storing hashes in git and data in remote storage
Model registry "Model version catalog" A system that tracks model versions with stage labels (staging, production, archived)
Training/serving skew "It worked in the notebook" Differences between how data is processed during training versus inference, causing silent errors
Reproducibility "Same code, same result" The ability to get identical results from the same code, data, and configuration

The problem

In plain words first

A pipeline is the whole recipe from raw table to prediction, packaged as one object: fill gaps, scale numbers, encode categories, then the model. Fitting the pipeline learns every step from training data only, and applying it to new data reuses exactly what was learned. That one habit prevents the most common silent bug in machine learning, leakage, and it means what you deploy is exactly what you evaluated.

You have a notebook that loads data, fills missing values with the median, scales features, trains a model, and prints accuracy. It works. You ship it.

A month later, someone retrains the model and gets different results. The median was computed on the full dataset including test data (data leakage). The scaling parameters were not saved, so inference uses different statistics. The feature engineering code was copy-pasted between training and serving, and the copies diverged. A categorical column gained a new value in production that the encoder has never seen.

These are not hypothetical. They are the most common reasons ML systems fail in production. Pipelines solve all of them by packaging every transformation step into a single, ordered, reproducible object.

Idea 1 · What a Pipeline Is

A pipeline is an ordered sequence of data transformations followed by a model. Each step takes the output of the previous step as input. The entire pipeline is fitted once on training data. At inference time, the same fitted pipeline transforms new data and produces predictions.

The pipeline guarantees: - Transformations are fitted only on training data (no leakage) - The same transformations are applied at inference time - The entire object can be serialized and deployed as one artifact - Cross-validation applies the pipeline per fold, preventing subtle leakage

Idea 2 · Data Leakage: The Silent Killer

Data leakage happens when information from the test set or future data contaminates training. Pipelines prevent the most common forms.

Leaky (wrong):

import numpy as np
import pandas as pd
from sklearn.preprocessing import StandardScaler

rng = np.random.default_rng(0)                         # a small numeric table to make the snippets runnable
df = pd.DataFrame(rng.normal(size=(1000, 4)) * [1, 10, 100, 1000], columns=["a", "b", "c", "d"])
df["target"] = (df["a"] + df["b"] / 10 + rng.normal(scale=1.0, size=1000) > 0).astype(int)

X = df.drop("target", axis=1)
y = df["target"]

scaler = StandardScaler()
X_scaled = scaler.fit_transform(X)

X_train, X_test = X_scaled[:800], X_scaled[800:]
y_train, y_test = y[:800], y[800:]
print("leaky: the scaler's means include the 200 test rows:", [round(float(m), 2) for m in scaler.mean_])
What you should see
leaky: the scaler's means include the 200 test rows: [-0.0, -0.33, -4.6, 20.74]

The scaler saw test data. The mean and standard deviation include test samples. This inflates accuracy estimates.

Correct:

X_train, X_test = X[:800], X[800:]

scaler = StandardScaler()
X_train_scaled = scaler.fit_transform(X_train)
X_test_scaled = scaler.transform(X_test)
print("correct: means learned from the 800 training rows only:", [round(float(m), 2) for m in scaler.mean_])
What you should see
correct: means learned from the 800 training rows only: [-0.01, -0.65, -6.02, 18.84]

With a pipeline, you do not need to think about this. The pipeline handles it automatically.

Check your mental model
  • ✗ "Leakage only matters if you train on the test labels."
    ✓ Any statistic computed with test rows leaks: means for scaling, vocabularies, category averages, and especially feature selection. The broken exercise gets 78 percent accuracy from pure noise this way.
  • ✗ "A pipeline is just tidier code."
    ✓ Inside cross-validation it refits every step on each fold's training part, which hand-written preprocessing usually gets wrong.
  • ✗ "Saving the model is enough to reproduce a prediction."
    ✓ You need the fitted preprocessing too, plus the library versions and the data version. Saving the whole pipeline object covers the first part.

Idea 3 · sklearn Pipeline

sklearn's Pipeline chains transformers and an estimator. It exposes .fit(), .predict(), and .score() that apply all steps in order.

from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression

pipe = Pipeline([
    ("scaler", StandardScaler()),
    ("model", LogisticRegression()),
])

pipe.fit(X_train, y_train)
predictions = pipe.predict(X_test)
print(f"test accuracy: {pipe.score(X_test, y_test):.3f}")
What you should see
test accuracy: 0.835

When you call pipe.fit(X_train, y_train): 1. Scaler calls fit_transform on X_train 2. Model calls fit on the scaled X_train

When you call pipe.predict(X_test): 1. Scaler calls transform (not fit_transform) on X_test 2. Model calls predict on the scaled X_test

The scaler never sees test data during fitting. This is the whole point.

Idea 4 · ColumnTransformer: Different Pipelines for Different Columns

Real datasets have numeric and categorical columns that need different preprocessing. ColumnTransformer handles this.

from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.impute import SimpleImputer
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.model_selection import cross_val_score

rng = np.random.default_rng(1)                         # synthetic customers with gaps and text columns
n = 1000
customers = pd.DataFrame({
    "age": rng.integers(18, 80, n).astype(float), "income": rng.lognormal(10.5, 0.5, n), "score": rng.normal(600, 80, n),
    "city": rng.choice(["Pune", "Delhi", "Chennai", "Kolkata"], n), "gender": rng.choice(["f", "m"], n),
    "plan": rng.choice(["basic", "plus", "pro"], n, p=[0.6, 0.3, 0.1]),
})
customers.loc[rng.random(n) < 0.1, "income"] = np.nan  # 10 percent of incomes missing
customers.loc[rng.random(n) < 0.05, "city"] = np.nan
churn = ((customers["plan"] == "basic") & (customers["score"] < 600) | (rng.random(n) < 0.1)).astype(int)

numeric_pipe = Pipeline([
    ("impute", SimpleImputer(strategy="median")),
    ("scale", StandardScaler()),
])

categorical_pipe = Pipeline([
    ("impute", SimpleImputer(strategy="most_frequent")),
    ("encode", OneHotEncoder(handle_unknown="ignore")),
])

preprocessor = ColumnTransformer([
    ("num", numeric_pipe, ["age", "income", "score"]),
    ("cat", categorical_pipe, ["city", "gender", "plan"]),
])

full_pipeline = Pipeline([
    ("preprocess", preprocessor),
    ("model", GradientBoostingClassifier(random_state=0)),
])
scores = cross_val_score(full_pipeline, customers, churn, cv=5)
print(f"5-fold accuracy: {scores.mean():.3f} ± {scores.std():.3f}  (churn rate {churn.mean():.2f})")
What you should see
5-fold accuracy: 0.924 ± 0.017  (churn rate 0.37)

The handle_unknown="ignore" in OneHotEncoder is critical for production. When a new category appears (a city the model has never seen), it produces a zero vector instead of crashing.

Reading this output

Five-fold accuracy on the synthetic customers is computed with the whole pipeline refitted inside each fold: imputation medians, scaling statistics and the list of known cities all come from that fold's training part. With handle_unknown="ignore", a city that appears only in a validation fold becomes an all-zero one-hot row instead of an error.

Idea 5 · Experiment Tracking

A pipeline makes training reproducible, but you also need to track what happened across experiments: which hyperparameters were used, which dataset version, what the metrics were, which code was running.

MLflow is the most common open-source solution:

import mlflow

with mlflow.start_run():
    mlflow.log_param("max_depth", 5)
    mlflow.log_param("n_estimators", 100)
    mlflow.log_param("learning_rate", 0.1)

    pipe.fit(X_train, y_train)
    accuracy = pipe.score(X_test, y_test)

    mlflow.log_metric("accuracy", accuracy)
    mlflow.sklearn.log_model(pipe, "model")

Every run is recorded with parameters, metrics, artifacts, and the full model. You can compare runs, reproduce any experiment, and deploy any model version.

Weights & Biases (wandb) provides the same functionality with a hosted dashboard:

import wandb

wandb.init(project="my-pipeline")
wandb.config.update({"max_depth": 5, "n_estimators": 100})

pipe.fit(X_train, y_train)
accuracy = pipe.score(X_test, y_test)

wandb.log({"accuracy": accuracy})

Idea 6 · Model Versioning

After experiment tracking, you need to manage model versions. Which model is in production? Which is staging? Which was last week's?

MLflow's Model Registry provides: - Version tracking: Every saved model gets a version number - Stage transitions: "Staging", "Production", "Archived" - Approval workflow: Models must be explicitly promoted to production - Rollback: Switch back to a previous version instantly

Idea 7 · Data Versioning with DVC

Code is versioned with git. Data should be versioned too, but git cannot handle large files. DVC (Data Version Control) solves this.

dvc init
dvc add data/training.csv
git add data/training.csv.dvc data/.gitignore
git commit -m "Track training data"
dvc push

DVC stores the actual data in remote storage (S3, GCS, Azure) and keeps a small .dvc file in git that records the hash. When you checkout a git commit, dvc checkout restores the exact data that was used.

This means every git commit pins both the code and the data. Full reproducibility.

Idea 8 · Reproducible Experiments

A reproducible experiment requires four things:

  1. Fixed random seeds: Set seeds for numpy, random, and the framework (torch, sklearn)
  2. Pinned dependencies: requirements.txt or poetry.lock with exact versions
  3. Versioned data: DVC or similar
  4. Config files: All hyperparameters in a config, not hardcoded
import numpy as np
import random

def set_seed(seed=42):
    random.seed(seed)
    np.random.seed(seed)
    try:
        import torch
        torch.manual_seed(seed)
        torch.cuda.manual_seed_all(seed)
        torch.backends.cudnn.deterministic = True
    except ImportError:
        pass

Idea 9 · From Notebook to Production Pipeline

The typical progression:

  1. Notebook exploration: Quick experiments, visualizations, feature ideas
  2. Extract functions: Move preprocessing, feature engineering, evaluation into modules
  3. Build Pipeline: Chain transformations into a sklearn Pipeline or custom class
  4. Config management: Move all hyperparameters into a YAML/JSON config
  5. Experiment tracking: Add MLflow or wandb logging
  6. Data validation: Check schema, distributions, and missing value patterns before training
  7. Tests: Unit tests for transformers, integration tests for the full pipeline
  8. Deployment: Serialize the pipeline, wrap in an API (FastAPI, Flask), containerize

Idea 10 · Common Pipeline Mistakes

Mistake Why it is bad Fix
Fitting on full data before splitting Data leakage Use Pipeline with cross_val_score
Feature engineering outside pipeline Different transforms at train vs serve Put all transforms in the Pipeline
Not handling unknown categories Production crash on new values OneHotEncoder(handle_unknown="ignore")
Hardcoded column names Breaks when schema changes Use column name lists from config
No data validation Silently wrong predictions on bad data Add schema checks before prediction
Training/serving skew Model sees different features in prod One Pipeline object for both

The same idea as a formula

A pipeline is one function fitted on training data only. Each step has parameters learned from data (a scaler's μ,σ, an imputer's medians, a vocabulary, the model's weights). Fitting must see only the training rows:

θ=fit(Xtrain​,ytrain​),y^​test​=predictθ​(Xtest​)

Any θ computed with test rows, including inside cross-validation, where every held-out fold is a test set, lets information about the evaluation data into the model. That is leakage, and it makes the estimate optimistic.

How optimistic selection gets. Choose the s features most correlated with the label from p pure-noise features on n rows: the largest absolute correlation among p noise features is about 2ln(2p)/n​. With p=10,000 and n=50 that is about 0.63, so the "best" noise features look strongly predictive, and cross-validating only the model after that selection reports a high accuracy on data with no signal at all.

Reproducibility. A run is reproducible when its code version, data version (a content hash), configuration and random seeds are all recorded; the pipeline object itself, saved with its fitted θ, is what is deployed.

Worked example
Leakage by hand

Training values of a feature: 1, 2, 3. One test value: 10.

  • Correct: fit the scaler on the training rows: μ=2, σ=0.816 (population form). The test value becomes (10−2)/0.816=9.8: clearly unusual, as it should be.
  • Leaky: fit on all four values: μ=4, σ=3.54. The test value becomes 1.7, and the training values change too (−0.85,−0.56,−0.28). The model is trained on numbers that already "know" a large value is coming.
  • Selection leak: with 10,000 noise features and 50 rows, picking the top 20 by correlation on all 50 rows, then cross-validating, typically reports accuracy far above the true 50%; doing the selection inside each fold brings it back to about 50%.

Step 1 · Custom Transformer

The code in code/pipeline.py builds a complete ML pipeline from scratch:

class CustomTransformer:
    def __init__(self):
        self.means = None
        self.stds = None

    def fit(self, X):
        self.means = np.mean(X, axis=0)
        self.stds = np.std(X, axis=0)
        self.stds[self.stds == 0] = 1.0
        return self

    def transform(self, X):
        return (X - self.means) / self.stds

    def fit_transform(self, X):
        return self.fit(X).transform(X)

Step 2 · Pipeline from Scratch

class PipelineFromScratch:
    def __init__(self, steps):
        self.steps = steps

    def fit(self, X, y=None):
        X_current = X.copy()
        for name, step in self.steps[:-1]:
            X_current = step.fit_transform(X_current)
        name, model = self.steps[-1]
        model.fit(X_current, y)
        return self

    def predict(self, X):
        X_current = X.copy()
        for name, step in self.steps[:-1]:
            X_current = step.transform(X_current)
        name, model = self.steps[-1]
        return model.predict(X_current)

Step 3 · Cross-Validation with Pipeline

The code demonstrates how cross-validation with a pipeline prevents data leakage: the scaler is fit separately on each fold's training data.

Predict before you run

100 rows, 2,000 features of pure random noise, random labels. Pick the 20 features most correlated with the labels using all the data, then cross-validate a logistic regression on them. What accuracy do you expect? And if the selection happens inside the pipeline, refitted on each fold? (Solution P1.)

import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(0)
X_noise, y_noise = rng.standard_normal((100, 2000)), rng.integers(0, 2, 100)
X_selected = SelectKBest(f_classif, k=20).fit_transform(X_noise, y_noise)       # selection sees every row
leaky = cross_val_score(LogisticRegression(max_iter=1000), X_selected, y_noise, cv=5).mean()
honest = cross_val_score(make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression(max_iter=1000)),
                         X_noise, y_noise, cv=5).mean()
print(f"selection before CV (leaky): {leaky:.2f}")
print(f"selection inside the pipeline: {honest:.2f}")
What you should see
selection before CV (leaky): 0.78
selection inside the pipeline: 0.59
Break it on purpose

The first line of the run above is the broken version: selection outside cross-validation. Why does it look so good on data that contains no signal at all? (Solution B1.)

Save, load, predict the same

The fitted pipeline is one object, so it can be saved and loaded as one file, and a reloaded pipeline gives identical predictions, which is Exercise 3:

import joblib

full_pipeline.fit(customers, churn)
joblib.dump(full_pipeline, "churn_pipeline.joblib")
reloaded = joblib.load("churn_pipeline.joblib")
new_customers = customers.head(5).copy()
new_customers.loc[0, "city"] = "Bhopal"                       # a city never seen in training
print("identical predictions:", (reloaded.predict(new_customers) == full_pipeline.predict(new_customers)).all())
print("probabilities:", reloaded.predict_proba(new_customers)[:, 1].round(3))
What you should see
identical predictions: True
probabilities: [0.992 0.988 0.159 0.047 0.986]
Recap
What to keep from this lesson
  • Put every preprocessing step and the model in one pipeline; fit it on training data only.
  • Use ColumnTransformer for different column types; set handle_unknown="ignore" for categories.
  • Cross-validate the whole pipeline so every step is refitted per fold.
  • Track experiments (parameters, metrics, artifacts) and version data and models.
  • Save the fitted pipeline as one artifact and test that it reloads and predicts identically.

Solutions

SolutionP1 · Accuracy from nowhere

Selecting on all the data gives about 0.78; selecting inside the pipeline gives 0.59 in this run, close to the 0.5 that pure noise allows (with only 100 rows, a single run varies by about ±0.1). The leaky number looks like a real model.

SolutionB1 · The selection saw the answers

Among 2,000 random features, some will match the 100 random labels fairly well by pure chance. Choosing the 20 best matches using all rows means the features were picked because they fit the labels of the very rows later used for validation. Cross-validation then measures how well chance-fitted features predict the labels they were chosen to fit. Inside the pipeline, selection only sees each fold's training rows, so the validation rows are genuinely new, and the score falls back towards chance.

Industry practice
What's current (2024–2026)
  • scikit-learn pipelines are still the core. Pipeline and ColumnTransformer (with set_output(transform="pandas") to keep column names) package preprocessing and the model as one object that is fitted, saved and served together.
  • Orchestration and tracking. Apache Airflow 3 (April 2025) and Dagster schedule pipelines; MLflow 3 (2025) tracks runs, registers models and adds tracing and evaluation for GenAI apps; Snowflake, Databricks and Vertex AI offer managed versions.

You are an expert in building production ML pipelines. You help engineers avoid data leakage, structure reproducible experiments, and deploy models reliably.

When someone asks about ML pipelines, preprocessing, or deployment:

1. Check for data leakage first. The most common forms:
   - Fitting transformers (scaler, imputer, encoder) on the full dataset before splitting
   - Target encoding without proper cross-validation
   - Feature selection using the test set
   - Time-series data shuffled before splitting (future leaking into past)
   - Validation metrics computed on data the model saw during training

2. Verify the pipeline structure:
   - All preprocessing steps are inside the Pipeline object, not outside
   - ColumnTransformer handles different column types correctly
   - handle_unknown="ignore" is set for categorical encoders
   - Cross-validation wraps the entire pipeline, not just the model

3. Check for training/serving skew:
   - Is the same Pipeline object used for training and inference?
   - Are feature engineering steps duplicated between training and serving code?
   - Does the serving code handle missing values the same way as training?
   - Are there any features that are available at training time but not at inference time?

4. Verify reproducibility:
   - Random seeds set for all sources of randomness
   - Dependencies pinned to exact versions
   - Data versioned (DVC or similar)
   - Hyperparameters in config files, not hardcoded

Common debugging checklist:

- Model accuracy drops in production: check for training/serving skew, data drift, or leakage in the original evaluation
- Cross-validation scores are much higher than holdout: data leakage in preprocessing
- Model works on notebook but not in production: missing preprocessing steps, different library versions, or hardcoded paths
- Predictions are NaN: missing value handling failed, check imputation step
- New categories crash the model: OneHotEncoder without handle_unknown="ignore"

Pipeline design patterns:

- Always use sklearn Pipeline for sklearn models
- For deep learning, create a data module that encapsulates all preprocessing
- Log the full pipeline configuration with every experiment (MLflow, wandb)
- Serialize the entire pipeline, not just the model weights
- Version the pipeline artifact alongside the code that created it

Check your understanding

Q1What is data leakage in the context of ML pipelines?

Data leakage occurs when information that would not be available at prediction time is used during training. Example: computing the scaler's mean/std on the full dataset including test data.

Q2Why is fitting a scaler on the full dataset before splitting into train/test considered leaky?

When the scaler is fit on all data, its mean and standard deviation encode information from test samples. Training features are then shifted using test statistics, leaking future information into training.

Q3In sklearn, what is the difference between calling fit_transform and transform on a pipeline step?

fit_transform computes statistics (e.g., mean, std) from the data AND transforms it. transform applies the already-learned statistics without recomputing. On test data, you must use transform to avoid leakage.

Q4Why is a ColumnTransformer necessary for real-world datasets?

Real datasets have mixed types. Numeric columns need scaling, categorical columns need encoding. ColumnTransformer routes each column subset to the appropriate transformer within a single pipeline.

Q5A production model receives a categorical value it never saw during training ('new_category'). What should the pipeline handle?

Robust pipelines anticipate unseen categories in production. Solutions include an 'unknown' fallback for one-hot encoding, or defaulting to the global mean for target encoding.
