In plain words first
The idea in one line

A capable model is not enough. Reliable agents need a workbench: instructions, state, scope, feedback, verification, review, and handoff. Strip those away and even a frontier model produces work that is unsafe to ship.

The problem

In plain words first

A workbench (people also say harness) is everything around the model while it works: the instructions it starts with, the files it may touch (scope), real output from the commands it runs (feedback), a check that must pass before "done" counts (verification), and notes that let the next session continue (state and handoff). The model decides; the workbench decides what the model sees and what it may claim. The usual failure without one is an agent that says it finished when nothing works. This lesson gives a small model the same bug-fix tasks with and without a workbench and counts real fixes and false "done"s.

You drop a frontier model into a real repo and ask it to add input validation. It opens four files, writes plausible code, declares success, and stops. You run the tests. Two fail. A third file is touched that had nothing to do with validation. There is no record of what the agent assumed, what it tried first, or what is left to do.

The model was not wrong about Python. It was wrong about the work. It had no idea what counted as done, where it was allowed to write, what tests were authoritative, or how the next session was supposed to pick up.

This is not a model bug. It is a workbench bug. The surface around the agent is missing the parts that turn a one-shot generation into reliable, resumable engineering.

The idea

A workbench is the operating environment that wraps the model during a task. It has seven surfaces:

Surface What it carries Failure when missing
Instructions Startup rules, forbidden actions, definition of done Agent guesses what shipping means
State Current task, touched files, blockers, next action Each session restarts from zero
Scope Allowed files, forbidden files, acceptance criteria Edits leak into unrelated code
Feedback Real command output captured into the loop Agent declares success on a 400
Verification Tests, lint, smoke run, scope check "Looks good" reaches main
Review A second pass with a different role Builder marks own homework
Handoff What changed, why, what is left Next session re-discovers everything

The workbench is independent of the model. You can swap the model and keep the surfaces. You cannot swap the surfaces and keep reliability.

The loop closes on the state file, not on chat history. Chat is volatile. The repo is the system of record.

Idea 1 · Workbench versus prompt engineering

Prompting tells the model what you want this turn. A workbench tells the model how to do work across turns and across sessions. Most agent failure stories are workbench failures wearing prompt-engineering clothes.

Idea 2 · Workbench versus framework

A framework gives you a runtime (LangGraph, AutoGen, Agents SDK). A workbench gives the agent a place to work inside that runtime. You need both. This mini-track is about the second one.

Idea 3 · Reasoning from primitives, not from vendor taxonomies

There is a lot of writing on "harness engineering" right now. Addy Osmani, OpenAI, Anthropic, LangChain, Martin Fowler, MongoDB, HumanLayer, Augment Code, Thoughtworks, the walkinglabs awesome list, and a steady drumbeat of Medium and Hacker News pieces are all carrying it. They disagree on the boundary of what a harness is, what is in scope, and which vocabulary to use. We do not need to pick a side. The seven surfaces are a UX layer; underneath every workbench is the same set of distributed-systems primitives that hold up any reliable backend.

Strip the agent label off for a moment. An agent run is computation that crosses time, processes, and machines. To make that reliable you need the same primitives any production system needs.

Primitive What it is What it carries for an agent
Function Typed handler. Pure where possible. Owns its inputs and outputs. A tool call, a rule check, a verification step, a model invocation
Worker Long-lived process that owns one or more functions and a lifecycle The builder, the reviewer, the verifier, an MCP server
Trigger Event source that invokes a function Agent loop tick, HTTP request, queue message, cron, file change, hook
Runtime The boundary that decides what runs where, with what timeouts and resources Claude Code's process, LangGraph's runtime, a worker container
HTTP / RPC The wire between caller and worker Tool-call protocol, MCP request, model API
Queue Durable buffer between trigger and worker; back-pressure, retry, idempotency The task board, the feedback log, the review inbox
Session persistence State that survives crashes, restarts, model swaps agent_state.json, checkpoints, KV stores, the repo itself
Authorization policy Who can call what function with which scope Allowed/forbidden files, approval boundaries, MCP capability lists

Now map the seven workbench surfaces onto those primitives.

  • Instructions — policy + function metadata. Rules are checks (functions). The router (AGENTS.md) is policy attached to the runtime's startup.
  • State — session persistence. A keyed store the runtime reads at every step. File, KV, or DB; the persistence semantics matter, the storage backend does not.
  • Scope — authorization policy per task. Allowed/forbidden globs are an ACL. Approvals required are a permission lattice.
  • Feedback — invocation log written into a queue. Every shell call is a record, durable, replayable.
  • Verification — a function. Deterministic over inputs. Triggered on task close. Fails closed.
  • Review — a separate worker with read-only authz on builder artifacts and write-only authz on review reports.
  • Handoff — a durable record emitted by a session-end trigger. The next session's startup trigger reads it.

The agent loop itself is a worker that consumes events (user message, tool result, timer tick), calls functions (the model, then the tools the model picks), writes records (state, feedback), and emits triggers (verify, review, handoff). No mystery; the same shape as a job processor.

Idea 4 · Patterns in circulation, translated to primitives

Every popular harness pattern reduces to the eight primitives. Translation table.

Vendor or community pattern What it actually is
Ralph Loop (Claude Code, Codex, agentic_harness book) — re-inject original intent into a fresh context window when the agent tries to stop early A trigger that re-enqueues a task with a clean context; session persistence carries the goal forward
Plan / Execute / Verify (PEV) Three workers, one per role, communicating via state and a queue between phases
Harness-compute separation (OpenAI Agents SDK, April 2026) — split control plane from execution plane Restating control-plane / data-plane. Predates the agent label by decades
Open Agent Passport (OAP, March 2026) — sign and audit every tool call against a declarative policy before execution An authorization policy enforced by a pre-action worker, with a signed audit queue
Guides and Sensors (Birgitta Böckeler / Thoughtworks) — feedforward rules + feedback observability Authorization policy + verification functions + observability traces
Progressive compaction, 5-stage (Claude Code reverse engineering, April 2026) A state-management worker that runs cron-like over session persistence to keep it within a budget
Hooks / middleware (LangChain, Claude Code) — intercept model and tool calls Triggers + functions wrapped around the runtime's invocation path
Skills as Markdown with progressive disclosure (Anthropic, Flue) A function registry where the function metadata is loaded into context just-in-time
Sandbox agents (Codex, Sandcastle, Vercel Sandbox) The compute plane: a runtime with isolated filesystem, network, and lifecycle
MCP servers Workers exposing functions over a stable RPC, with capability lists as authorization

Every entry in that table is the agent community arriving at a primitive that already had a name in distributed systems and giving it a new one. Useful labels for marketing; not useful as engineering vocabulary.

Idea 5 · What the receipts actually say

The harness-over-model claim has numbers behind it now. Worth knowing, because they are also the only honest argument against "just wait for a smarter model."

  • Terminal Bench 2.0 — same model (GPT-5.2-Codex), harness changes alone took LangChain's deepagents-cli from 52.8% (just outside the top 30) to 66.5% (top 5) (LangChain, Improving Deep Agents with harness engineering, February 2026).
  • Vercel — deleted 80% of its agent's tools; success rate jumped from 80% to 100% (MongoDB).
  • Harvey — legal agents more than doubled accuracy through harness optimization alone (MongoDB).
  • 88% of enterprise AI agent projects fail to reach production. The failures cluster around runtime, not reasoning (preprints.org, Harness Engineering for Language Agents, March 2026).
  • A 2025 benchmark study across three popular open-source frameworks reported ~50% task completion; long-context WebAgent collapsed from 40-50% to under 10% in long-context conditions, mostly from infinite loops and goal loss (covered widely in early 2026 writeups).

The takeaway is not "harness wins forever." Models do absorb harness tricks over time. The takeaway is that today, the load-bearing engineering is around the model, not inside it, and the primitives that carry that load are the ones every production system has always needed.

Idea 6 · Where vendor writeups stop short

This is the part you do not need to be polite about.

  • LangChain's Anatomy of an Agent Harness walks through the core harness components: prompts, tools, hooks, sandboxes, orchestration, memory, skills, subagents, and a runtime "dumb loop." It does not name queues, workers as a deployment unit, trigger semantics, session persistence as a separate concern, or authorization policy. It treats the harness as an object you configure, not as a system you deploy.
  • Addy Osmani's Agent Harness Engineering lands the framing Agent = Model + Harness and the ratchet pattern, but stops short of saying what a harness is built out of. It reads as a stance, not a spec.
  • Anthropic and OpenAI go deepest on the surfaces but stay inside their own runtimes. The "harness-compute separation" announcement in the April 2026 Agents SDK is the first vendor piece that explicitly endorses the control-plane / data-plane split. That is a primitive idea, not a new one.
  • The agentic_harness book treats harness as a config object (Jaymin West's Agentic Engineering, chapter 6) and the strongest line in it is "the harness is the primary security boundary in an agentic system." That is just authorization policy, restated.
  • Hacker News threads keep arriving at the same place. The April 2026 thread The agent harness belongs outside the sandbox argues the harness should sit "more like a hypervisor that sits outside everything and authorises access based on context and user." That is, again, authorization policy as a separate plane.

You do not need to disagree with any of these pieces to notice the gap. They are writing UX descriptions of a system that already exists. We are writing the system. When the system is built right, the seven surfaces fall out of the primitives. When it is built wrong, no amount of AGENTS.md polish fixes the missing queue.

So when you hear "harness engineering" elsewhere, translate to primitives. Prompts and rules are policy and functions. Scaffolding is the runtime. Guardrails are authorization + verification. Hooks are triggers. Memory is session persistence. The Ralph Loop is requeue. Subagents are workers. Sandboxes are compute planes. The vocabulary changes; the engineering does not. The workbench is the agent-facing UX; the harness, in the sense that survives the next vendor reframe, is functions, workers, triggers, runtimes, queues, persistence, and policy wired together correctly.

The same idea as a formula

Two rates that a workbench changes differently. Over n runs, let c be the fraction actually completed and f the fraction that claim success while failing (false "done"). What a user experiences is roughly

trusted outcomes=c,silent failures=f.
A verification gate drives f towards 0 by refusing any finish whose checks fail. It cannot raise c by itself; that takes a model able to do the work, plus feedback it can use.

Retry budget. With a gate, an agent that fixes the task with probability q per attempt and has k attempts finishes with probability 1−(1−q)k. If q=0, every extra attempt is spent being rejected.

Worked example
Reading the five-task table
  • Prompt-only: 0 of 5 fixed, and 2 of 5 runs called finish on code that still failed its test (is_even and to_fahrenheit): c=0, f=0.4.
  • Workbench: 0 of 5 fixed, 0 false finishes: c=0, f=0. The gate rejected 12 premature finishes across three tasks.
  • So the workbench removed every false "done" and added no fixes: in all twelve runs of this lesson the model never called write_file.
  • In production terms: without the gate, 2 of 5 tickets would have been closed as fixed while broken; with it, all 5 stay visibly open for a person or a stronger model.
Check your mental model
  • ✗ "A good prompt is a workbench."
    ✓ A prompt asks; the gate, the scope check and the test runner enforce.
  • ✗ "A workbench makes a weak model capable."
    ✓ It stopped every false 'done' and produced no fixes.
  • ✗ "If the agent says it finished, check its summary."
    ✓ Run the tests and the scope check; ignore the summary.
  • ✗ "Swapping in a better model removes the need for a workbench."
    ✓ Same model, different harness, moved one agent from outside the top 30 to the top 5.
Predict before you run

A 0.5B model must fix is_even (it returns n % 2 == 1) using file tools, and must call a tool every turn, finish included. With no workbench, what will it do? With a workbench whose gate runs the tests on every finish? (Solution P1.)

One task, two harnesses, a real model

A four-file repo (the buggy app.py, test_app.py, a README and a release script). Qwen2.5-0.5B-Instruct (greedy, CPU) is constrained to call one of its tools every turn, for up to eight turns. The workbench adds a scope rule, a run_tests tool with real output, and a gate that runs the tests and the scope check on every finish. Each run is reported with the lesson's RunResult and failure_report. About 1 minute.

# The same coding task under two harnesses, with a real model. A tiny repo has a bug in app.py and a test
# file. Qwen2.5-0.5B-Instruct (greedy, CPU) must call a tool every turn: read_file, write_file or finish. Prompt-only:
# just the task. Workbench: the task plus scope (allowed files), a run_tests tool that returns real output, and
# a verification gate that runs the tests and the scope check whenever the agent says it is finished, and
# sends failures back. Each run is reported with the lesson's RunResult and failure_report (code/main.py).
import json, os, pathlib, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import RunResult, failure_report
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

REPO = {
    "app.py": 'def is_even(n):\n    """Return True if n is even."""\n    return n % 2 == 1\n',
    "test_app.py": "import unittest\nfrom app import is_even\n\nclass T(unittest.TestCase):\n    def test_even(self):\n"
                   "        self.assertTrue(is_even(4))\n    def test_odd(self):\n        self.assertFalse(is_even(7))\n\n"
                   "if __name__ == '__main__':\n    unittest.main()\n",
    "README.md": "# demo\nVersion 1\n", "scripts/release.sh": "echo release\n",
}
TASK = ("is_even in app.py returns the wrong answer. Fix it by writing the corrected app.py.\napp.py now contains:\n"
        + REPO["app.py"])
ALLOWED = ["app.py"]

def fn(name, desc, **params):
    return {"type": "function", "function": {"name": name, "description": desc, "parameters": {
        "type": "object", "properties": {k: {"type": "string"} for k in params}, "required": list(params)}}}
BASE_TOOLS = [fn("read_file", "Read a file.", path="file path"),
              fn("write_file", "Replace a file's whole content.", path="file path", content="new full content"),
              fn("finish", "Say the task is complete.", message="short summary")]
TEST_TOOL = fn("run_tests", "Run the test suite and return its output.")

def make_repo():
    root = pathlib.Path(tempfile.mkdtemp())
    for name, body in REPO.items():
        (root / name).parent.mkdir(parents=True, exist_ok=True); (root / name).write_text(body)
    return root

def run_tests(root):
    p = subprocess.run([sys.executable, "-m", "unittest", "-q", "test_app"], cwd=root, capture_output=True, text=True, timeout=30)
    return p.returncode == 0, (p.stdout + p.stderr).strip()[-400:]

def model_turn(msgs, tools):
    """One model step, constrained to start a tool call (tool_choice="required"): finish is a tool too."""
    ids = tok.apply_chat_template(msgs, tools=tools, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    prefix = '<tool_call>\n{"name": "'
    ids = torch.cat([ids, tok(prefix, return_tensors="pt")["input_ids"]], dim=1)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=200, do_sample=False)
    text = prefix + tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)
    calls = []
    for blob in re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", text, re.S):
        try:
            d = json.loads(blob); calls.append((d["name"], d.get("arguments", {}) or {}))
        except (json.JSONDecodeError, KeyError):
            pass
    return calls, text

def agent(workbench, max_turns=8):
    root = make_repo()
    result = RunResult(label="workbench" if workbench else "prompt-only",
                       surfaces_present=["instructions", "scope", "feedback", "verification"] if workbench else [])
    tools = BASE_TOOLS + ([TEST_TOOL] if workbench else [])
    system = "You are a coding agent working in a small Python repo. Use the tools."
    if workbench:
        system += (f" You may change only these files: {', '.join(ALLOWED)}. Done means: the tests in test_app.py pass "
                   "(use run_tests) and no other file changed. Call finish only when that is true.")
    msgs = [{"role": "system", "content": system}, {"role": "user", "content": TASK}]
    for _ in range(max_turns):
        calls, text = model_turn(msgs, tools)
        if not calls:
            msgs += [{"role": "assistant", "content": text}, {"role": "user", "content": "Use a tool."}]
            continue
        msgs.append({"role": "assistant", "content": "", "tool_calls": [{"type": "function", "function": {"name": n, "arguments": a}} for n, a in calls]})
        finished = False
        for name, args in calls:
            ACTIONS.setdefault(result.label, []).append(name if name != "write_file" else f"write_file({args.get('path')})")
            path = str(args.get("path", "")).lstrip("./")
            if name == "read_file":
                out = (root / path).read_text() if (root / path).is_file() else "error: no such file"
            elif name == "write_file":
                (root / path).parent.mkdir(parents=True, exist_ok=True); (root / path).write_text(str(args.get("content", "")))
                result.files_touched.append(path); out = f"wrote {path}"
            elif name == "run_tests" and workbench:
                result.tests_run = True; ok, out = run_tests(root); out = ("PASS\n" if ok else "FAIL\n") + out
            elif name == "finish":
                result.declared_success = True; finished = True
                if workbench:                                   # the verification gate
                    ok, log = run_tests(root)
                    off = [f for f in result.files_touched if f not in ALLOWED]
                    if ok and not off:
                        out = "verified"
                    else:
                        finished = False; result.declared_success = False
                        out = "rejected by the verification gate: " + ("tests fail: " + log[-200:] if not ok else "") + \
                              (f" files outside scope changed: {off}" if off else "")
                        result.notes.append("gate rejected a finish")
                else:
                    out = "ok"
            else:
                out = f"error: unknown tool {name}"
            msgs.append({"role": "tool", "content": out})
        if finished:
            break
    result.actually_passing = run_tests(root)[0]
    final = (root / "app.py").read_text().strip().splitlines()[-1].strip()
    return result, final

RUNS, ACTIONS = {}, {}
for wb in (False, True):
    res, final = agent(wb)
    RUNS[res.label] = res
    rep = failure_report(res)
    print(f"=== {res.label} ===")
    for k in ("missing_surfaces", "off_scope_writes", "tests_run", "declared_success", "actually_passing", "notes"):
        print(f"  {k}: {rep[k]}")
    print(f"  actions: {', '.join(ACTIONS.get(res.label, []))}")
    print(f"  files written: {res.files_touched}   last line of app.py: {final!r}\n")

Reading this output

Without a workbench the agent claims a fix it never made. It calls a tool named is_even (which does not exist; that is the function it was asked to fix), then finish. declared_success is True, actually_passing is False, and app.py still ends in return n % 2 == 1. The lesson's failure_report lists seven missing surfaces.

With a workbench the false claim never lands. The agent runs the tests (they fail), then calls finish seven times; the gate runs the tests each time and rejects each finish with the failing output. The bug is still there, but the run ends honestly: not done.

What did not change is the model's ability: it never wrote a file in either run.

This block continues from the one above: five one-line bugs, both harnesses, five turns each. About 3 minutes.

# Five small bug-fix tasks instead of one, both harnesses, at most five turns each. Counted per harness:
# real fixes (tests pass afterwards), false claims (finish called while the tests fail) and writes outside
# the allowed file. Continues from the block above (same agent, tools and gate).
TASKS = [
    ("is_even", 'def is_even(n):\n    return n % 2 == 1\n', "self.assertTrue(is_even(4)); self.assertFalse(is_even(7))"),
    ("largest", 'def largest(xs):\n    return min(xs)\n', "self.assertEqual(largest([3, 9, 2]), 9)"),
    ("reverse", 'def reverse(s):\n    return s\n', "self.assertEqual(reverse('abc'), 'cba')"),
    ("to_fahrenheit", 'def to_fahrenheit(c):\n    return c * 9 / 5\n', "self.assertEqual(to_fahrenheit(100), 212)"),
    ("count_vowels", 'def count_vowels(s):\n    return len(s)\n', "self.assertEqual(count_vowels('banana'), 3)"),
]
rows = []
for name, code, checks in TASKS:
    REPO["app.py"] = code
    REPO["test_app.py"] = (f"import unittest\nfrom app import {name}\n\nclass T(unittest.TestCase):\n    def test_it(self):\n"
                           f"        {checks}\n\nif __name__ == '__main__':\n    unittest.main()\n")
    TASK = f"{name} in app.py returns the wrong answer. Fix it by writing the corrected app.py.\napp.py now contains:\n{code}"
    for wb in (False, True):
        ACTIONS.clear()
        res, _ = agent(wb, max_turns=5)
        false_claim = res.declared_success and not res.actually_passing
        rejected = res.notes.count("gate rejected a finish")
        off = [f for f in res.files_touched if f not in ALLOWED]
        rows.append((name, res.label, res.actually_passing, false_claim, rejected, off, ACTIONS.get(res.label, [])))
print(f"{'task':<15}{'harness':<13}{'fixed':<7}{'false done':<12}{'finishes rejected':<19}actions")
for name, label, fixed, false_claim, rejected, off, acts in rows:
    print(f"{name:<15}{label:<13}{'yes' if fixed else 'no':<7}{'YES' if false_claim else 'no':<12}{rejected:<19}{', '.join(acts)[:60]}")
for label in ("prompt-only", "workbench"):
    r = [x for x in rows if x[1] == label]
    print(f"\n{label:<12} fixed {sum(x[2] for x in r)}/5, false 'done' {sum(x[3] for x in r)}/5, "
          f"off-scope writes {sum(len(x[5]) for x in r)}", end="")
print()

Reading this output

False "done" falls from 2 of 5 to 0. Prompt-only runs finished on broken code twice; the workbench rejected 12 premature finishes across three tasks and let none through.

Fixes stay at 0 of 5 in both. The model reads files, runs tests or calls finish, but never calls write_file, here or in the first block. Feedback only helps a model that can act on it.

That is the right expectation for a workbench. It turns silent failures into visible ones and keeps a weak agent from closing tickets falsely. Capability comes from the model; on the RTX 4060 a 3B to 7B coder model in 4-bit would make the same gate useful in the other direction, by sending its test failures back as information it can use.

Build it

code/main.py runs a tiny repo task twice. First as prompt only, then with the seven surfaces wired in. Same model, same task. The script counts which surfaces were missing on the failed run and prints a failure-mode report.

The repo task is small on purpose: add input validation to a one-file FastAPI-style handler and write a passing test.

Run it:

def stub_agent(task: RepoTask, surfaces: list[str]) -> RunResult:
    """Tiny deterministic stand-in for an LLM-backed coding agent."""
    result = RunResult(label="prompt-only" if not surfaces else "workbench")
    result.surfaces_present = list(surfaces)

    has_scope = "scope" in surfaces
    has_state = "state" in surfaces
    has_verification = "verification" in surfaces
    has_feedback = "feedback" in surfaces

    if has_scope:
        result.files_touched = [f for f in task.allowed_files]
    else:
        result.files_touched = [*task.allowed_files, "README.md", "scripts/release.sh"]
        result.notes.append("touched unrelated files because scope was missing")

    if has_feedback:
        result.tests_run = True
        result.notes.append("captured stdout/stderr/exit code from the test run")
    else:
        result.notes.append("never ran the test command, guessed at output")

    if has_verification:
        result.actually_passing = True
        result.declared_success = True
        result.notes.append("verification gate proved acceptance criteria met")
    else:
        result.declared_success = True
        result.actually_passing = False
        result.notes.append("declared success without running acceptance checks")

    if not has_state:
        result.notes.append("no state file written, next session restarts from zero")

    return result


def failure_report(result: RunResult) -> dict[str, object]:
    return {
        "label": result.label,
        "missing_surfaces": result.missing_surfaces(),
        "off_scope_writes": [
            f for f in result.files_touched if f not in {"app.py", "test_app.py"}
        ],
        "tests_run": result.tests_run,
        "declared_success": result.declared_success,
        "actually_passing": result.actually_passing,
        "notes": result.notes,
    }


def main() -> None:
    task = RepoTask(
        description="add input validation to /signup and a passing test",
        allowed_files=["app.py", "test_app.py"],
        forbidden_files=["README.md", "scripts/release.sh"],
        acceptance=["test_app.py::test_signup_rejects_short_password passes"],
    )

    prompt_only = stub_agent(task, surfaces=[])
    workbench = stub_agent(task, surfaces=WORKBENCH_SURFACES)

    print("=== prompt only ===")
    for k, v in failure_report(prompt_only).items():
        print(f"  {k}: {v}")
    print()
    print("=== workbench ===")
    for k, v in failure_report(workbench).items():
        print(f"  {k}: {v}")

    out = Path(__file__).parent.parent / "outputs" / "failure_modes.json"
    out.write_text(json.dumps(failure_report(prompt_only), indent=2) + "\n")
    print(f"\nwrote {out.relative_to(out.parent.parent.parent.parent.parent)}")

Ship it

outputs/skill-workbench-audit.md is a portable skill that audits an existing repo for the seven workbench surfaces and reports which are missing, which are partial, and which are healthy. Drop it next to any agent setup; it tells you what to fix first.

---
name: workbench-audit
description: Audit a repo for the seven agent workbench surfaces and report which are missing, partial, or healthy before any agent work begins.
version: 1.0.0
phase: 14
lesson: 31
tags: [workbench, audit, reliability, agent-engineering]

Given a repository path and the agent product that will run inside it, audit the seven workbench surfaces and produce a readiness report.

The seven surfaces:

1. Instructions: a root file the agent reads first (e.g. `AGENTS.md`), short, that routes to deeper rules.
2. State: a durable, machine-readable file that records task, touched files, blockers, next action.
3. Scope: a contract per task listing allowed files, forbidden files, acceptance criteria, rollback plan.
4. Feedback: a runner that captures command, stdout, stderr, exit code, and feeds the result back into the loop.
5. Verification: a gate that runs tests, lint, type-check, smoke run, and confirms acceptance criteria.
6. Review: a second pass with a different role, builder cannot mark its own work.
7. Handoff: an artifact that summarizes what changed, why, what is left, and the next best action.

Produce:

- A score per surface: 0 missing, 1 partial, 2 healthy. Tie each score to a file or process you observed.
- Three priorities ordered by leverage: which missing surface, if added first, removes the most failure modes.
- A `workbench_audit.json` machine-readable report plus a `workbench_audit.md` human-readable summary.
- A starter patch for the weakest surface: the smallest file change that moves the score from 0 to 1.

Hard rejects:

- "Healthy" scores without a file path or process reference. Audits without evidence rot.
- A single combined "agent config" surface. Combining surfaces hides which one failed when a task breaks.
- Skipping verification because tests are slow. If verification is not on the workbench, builders mark their own homework.

Refusal rules:

- If the repo has no test command at all, refuse the verification score and surface it as a blocking finding.
- If the repo has no version control history, refuse the handoff score and surface it as a blocking finding.
- If the agent product runs as root or with unrestricted file access, refuse the scope score until a sandbox or write list is defined.

Solutions

SolutionP1 · A false "done", then a blocked one

Without a workbench it calls a made-up tool named after the function, then finish, claiming success with the bug untouched. With the workbench it runs the tests, then keeps calling finish; the gate rejects every one because the tests still fail, so the run ends unfinished instead of falsely finished. Neither run fixes the bug.

SolutionB1 · Instructions are not a gate

The instruction to run tests is a request the agent can ignore or misread; nothing checks it. The missing surface is a verification gate: code outside the model that, whenever the agent claims completion, runs the tests (and a scope check of the changed files) itself and refuses the completion if they fail, sending the output back.

Add the gate on the finish path; mark tickets done only from the gate's verdict, never from the agent's summary; record false-completion attempts as a metric; and keep the agent's test runs as feedback, not as proof. Then recompute the dashboard from verified completions.

What the harness is made of.

The seven surfaces are a user-facing layer. Underneath them are the primitives every reliable production system already has: functions, workers, triggers, a runtime, a wire, queues, session persistence and an authorization policy. The agent loop is a worker that consumes events, calls functions, writes records and emits triggers. None of that is specific to this model generation, and none of it goes away when the model improves.

What leadership gets right.

Models do absorb harness tricks. A pattern that was a prompt trick two years ago is native now, and the thought-token scheme of the original loop became a reasoning channel. The honest claim is not that the harness wins forever. It is that today the load is around the model, and that the primitives you build to carry it are the ones you would need for any production system, model or not.

The proposal to leadership.

Build the surfaces as primitives, not as prompt text. Keep the state, the scope, the feedback, the gate and the handoff as files and checks that do not know which model is in the loop. When the next model arrives, swap it and keep the surfaces. The harness work is not a bet against the model. It is the part of the system you keep.

Plausible wrong answers.

  • "The model is the product, so the harness is overhead." The harness decided the rank on the benchmark while the model stayed the same.
  • "A longer context window will fix the goal loss." The long-context result in the lesson went the other way, with completion falling under 10 percent as context grew.
  • "Harness work is prompt engineering by another name." Prompting tells the model what you want this turn, and the harness carries the work across turns and sessions in files and checks.

Follow-ups an interviewer may ask.

  • (level 3) Which of the receipts is the weakest evidence, and why? Expected: the enterprise failure rate, because it is a survey figure without a controlled comparison, while the benchmark rank change held the model fixed.
  • (level 3) A newer model stops needing the repeat detector. What do you remove? Expected: nothing yet, because the detector is a trigger plus a function that costs little, and you remove it only when the trace data shows it never fires.
  • (level 4) How do you make the harness investment visible to leadership each quarter? Expected: run the same task set with and without the surfaces on the current model, report completion, scope violations and interventions, and show the gap.
  • (level 4) What is the one harness piece most likely to be absorbed by models next? Expected: a reasoned pick, such as self-correction on tool errors, with the argument that the model sees the observation and the surface only formats it.

Explain the mechanismA team ran a frontier model on a small repo task. The result had plausible code, two red tests, one edit in a file that had nothing to do with the task, and no note of what the model assumed or what remains. The team wants to buy a bigger model. What do you tell them?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. The model was right about the language and wrong about the work, and a bigger model does not fix that. Reliable agents need a workbench with seven surfaces around the model: instructions, state, scope, feedback, verification, review and handoff. Each symptom in the run maps to one missing surface. You can swap the model and keep the surfaces, but you cannot drop the surfaces and keep the reliability.

The seven surfaces.

Surface What it carries Failure when it is missing
Instructions Startup rules, forbidden actions, the definition of done The agent guesses what done means
State Current task, touched files, blockers, next action Every session starts from zero
Scope Allowed files, forbidden files, acceptance criteria Edits spread into unrelated code
Feedback Real command output captured into the loop The agent declares success on an error
Verification Tests, lint, smoke run, scope check "Looks good" reaches the main branch
Review A second pass with a different role The builder grades its own work
Handoff What changed, why, what is left The next session finds everything again

Map the run to the table.

  • Two red tests and a success claim: feedback and verification were missing.
  • An edit in an unrelated file: scope was missing.
  • No note of assumptions or of what remains: state and handoff were missing.
  • Nobody but the builder read the diff: review was missing.

Why not a bigger model.

The loop closes on the state file, not on the chat history. Chat is volatile. The repo is the system of record. The lesson collects the receipts: one coding agent moved from outside the top 30 to rank five on a terminal benchmark with the same model and a changed harness, and one team deleted 80 percent of its agent's tools and saw the success rate go from 80 percent to 100 percent. The load today is carried by the engineering around the model.

What a workbench is not.

It is not prompt engineering, which tells the model what you want this turn. It is not the framework, which gives you a runtime. The workbench is the place the agent works in, across turns and across sessions, inside whatever runtime you chose.

Plausible wrong answers.

  • "The model hallucinated, so pick a model that hallucinates less." The model did not know what done meant or where it could write, and no model knows that without the surfaces.
  • "Write a longer system prompt with all the rules." A prompt covers one turn, while the surfaces carry the work across turns and sessions.
  • "The framework already does this." A framework gives the agent a runtime, and the workbench is what the agent reads and writes inside that runtime.

  • (level 2) Which surface catches an agent that writes an extra file nobody asked for? Expected: scope first, because the diff check compares touched files with the contract, and then verification, which refuses the forbidden write.
  • (level 2) Why does the lesson say the loop closes on a file and not on the chat? Expected: sessions end and conversations get trimmed, so the file is the only record that the next session can trust.
  • (level 3) The lesson maps each surface to a distributed-systems primitive. What is verification? Expected: a function that is deterministic over its inputs, triggered when the task closes, and that fails closed.

Defend a designYour harness has grown to about two hundred tools across several teams. The model cannot hold all of them in context, two teams once registered the same name and the second silently replaced the first, and the success rate has fallen as the catalog grew. Design the registry and the policy for what the model sees on each turn.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Make the registry the only source of truth for what exists, what shape the arguments take and which handler runs, and surface only ten to forty tools per turn. The registry holds a typed record per tool, rejects a second registration of a name unless the caller asks to override, and validates every call against a small schema subset with pointer-shaped errors. The exposure policy loads tool metadata into context only when the task needs it, and the fewer tools the model sees, the better it calls them.

The record.

Field Purpose
name Unique, lower-case segments separated by dots
description One line shown to the model
schema A subset of JSON Schema with eight keywords
handler The callable, opaque to the validator
idempotent Lets the dispatcher decide whether a retry is safe
timeout_ms Per-tool override of the dispatcher default

The schema is data and the handler is code. Keep them apart so that validation never ends up inside handlers.

Three registry rules.

  1. No silent overwrite. register raises on a known name unless override=True. The incident in the prompt is this rule missing.
  2. Validate before dispatch. A pure, recursive walk over the schema returns Ok or a list of errors with JSON pointer paths. No coercion, no handler call, no I/O, so the validator can run again over a replay log.
  3. The registry is shape, not safety. Timeouts and sandboxing live in the dispatcher. A validated call can still misbehave.

The exposure policy.

A catalog of two hundred tools and a context that fits forty is a routing problem. Surface a subset per turn based on the task, and load the rest just in time. The workbench lesson describes the pattern as skills that are revealed step by step: a function registry whose metadata enters context only when needed. The same lesson reports a team that deleted 80 percent of its agent's tools and saw the success rate go from 80 percent to 100 percent. More tools in view means more wrong choices, longer prompts and more schema to misread.

Practical selection signals: the active scope contract, the task type on the board, the tools used in the last few turns, and an explicit request from the model for a named family. Log the exposed set per turn so that a failure can be traced to a missing tool rather than a wrong call.

What grows next.

Past about fifty tools, add $ref against a local definitions block so that shared argument shapes are written once, and additionalProperties: false so that an extra argument is an error rather than a silent drop. Both are small. Both are common.

Plausible wrong answers.

  • "Give the model the whole catalog and let it choose." The model cannot hold two hundred schemas, and success fell as the catalog grew, so the fix is fewer tools in view.
  • "Put validation in each handler, close to the code it protects." Validation inside handlers drifts per team and turns the dispatcher into a guessing game that ends in a stack trace.
  • "Allow re-registration so that teams can hot-fix a tool." A silent replace is the incident in the prompt, and a fix should pass an explicit override that shows up in review.

Follow-ups an interviewer may ask.

  • (level 3) Two teams want the same tool name for different handlers. What do you do? Expected: refuse the collision, namespace by dotted segment, and let the exposure policy pick the family the task needs.
  • (level 3) How do you prove the validator is still correct after a refactor? Expected: run it over a saved replay log of real calls, which works because it has no I/O, no clock and no globals.
  • (level 4) What breaks if the exposure policy is itself a model call? Expected: a second nondeterministic step on every turn, so the selection should be rule-based from the contract and the board, with the model allowed only to request a named family.
  • (level 4) The dispatcher retries a failed call. Which record field decides whether it may? Expected: idempotent, because a retry of a non-idempotent tool can repeat a side effect.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Every entry is a distributed-systems primitive with a new name. The re-inject loop is a trigger that re-enqueues the task with fresh context, plan-execute-verify is three workers with a queue between them, the passport is an authorization policy enforced by a pre-action worker, and compaction is a state-management worker over session persistence. Hooks are triggers around the invocation path, skills are a function registry whose metadata loads just in time, sandboxes are the compute plane, and the control-plane item is the control-plane and data-plane split that predates agents. The decks usually leave out queues, workers as the unit of deployment, trigger semantics, persistence as its own concern and authorization as a separate plane.

The eight primitives.

Primitive What it carries for an agent
Function A tool call, a rule check, a verification step, a model invocation
Worker The builder, the reviewer, the verifier, a protocol server
Trigger A loop tick, an HTTP request, a queue message, a cron, a file change, a hook
Runtime The boundary that decides what runs where, with which timeouts and resources
HTTP or RPC The wire between caller and worker, including the tool-call protocol and the model API
Queue The durable buffer with back-pressure, retry and idempotency: the task board, the feedback log, the review inbox
Session persistence The state file, checkpoints, key-value stores, the repository itself
Authorization policy Allowed and forbidden files, approval boundaries, capability lists

The translation.

Deck entry What it is
Re-inject intent when the agent stops early A trigger that re-enqueues the task with a clean context; persistence carries the goal forward
Plan, execute, verify Three workers, one per role, communicating through state and a queue between phases
A control plane apart from the execution plane The control-plane and data-plane split, decades old
A passport that signs each tool call An authorization policy enforced by a pre-action worker, with a signed audit queue
Progressive compaction A state-management worker that runs on a schedule over session persistence to keep it within a budget
Hooks and middleware Triggers plus functions wrapped around the runtime's invocation path
Skills that disclose themselves step by step A function registry whose metadata is loaded into context only when needed
Sandboxed agents The compute plane: a runtime with isolated filesystem, network and lifecycle

How the surfaces map.

Instructions are policy plus function metadata. State is session persistence. Scope is an authorization policy per task. Feedback is an invocation log written into a queue. Verification is a deterministic function triggered on task close that fails closed. Review is a separate worker with read-only access to the builder's artifacts and write-only access to review reports. Handoff is a durable record emitted by a session-end trigger and read by the next session's startup trigger.

What the decks leave out.

The lesson reads the circulating writeups and finds the same gap: they describe the harness as an object you configure, not as a system you deploy. They rarely name queues, workers as a deployment unit, trigger semantics, session persistence as a separate concern, or an authorization policy as its own plane. The strongest line in that literature, that the harness is the primary security boundary, is authorization policy restated. When the system is built from the primitives, the surfaces fall out of it. When it is built without them, no amount of instruction-file polish replaces the missing queue.

Why the translation matters.

Vocabulary changes every release cycle. The primitives do not. A team that translates each new pattern before adopting it can compare vendors on one table, spot a pattern that is two primitives wearing one name, and notice when a deck has no answer for persistence or authorization.

Plausible wrong answers.

  • "These patterns are new because agents are new." Each one has a name in distributed systems, and the agent label changes the vocabulary and not the engineering.
  • "Pick the vendor with the most patterns." More names on a deck is not more primitives covered, and the question is which of the eight are missing.
  • "A good instruction file is the harness." Instructions are policy and function metadata, one of eight, and a file cannot replace a queue or a persistence layer.

Follow-ups an interviewer may ask.

  • (level 3) Which primitive is most often missing from an agent product that otherwise looks complete? Expected: the queue, because without a durable buffer the board, the feedback log and the review inbox are chat messages that scroll away.
  • (level 3) The deck says its hooks are a security boundary. Test the claim. Expected: a hook is a trigger plus a function inside the runtime, and a security boundary is an authorization policy enforced outside the agent's reach, so ask where the policy lives and who can change it.
  • (level 4) Two vendors describe the same thing as a handoff and as a checkpoint. How do you tell? Expected: map both to persistence and triggers, and see whether the record is read by the next session's startup trigger, which makes it a handoff, or by the same session on resume, which makes it a checkpoint.
  • (level 4) What would make a ninth primitive legitimate? Expected: a capability that cannot be built from the eight, which is rare, so the first check is whether it is a shared-state flavor or a policy flavor you have not seen.
