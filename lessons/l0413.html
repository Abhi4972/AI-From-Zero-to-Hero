Why this came about

Vector search needs an embedding pipeline and can miss structure. With larger context windows and capable agents, some teams found that navigating documents directly, through tables of contents, file trees or plain text search as coding agents do, worked better for well-structured collections.

In plain words first
Reading the table of contents instead of searching

Not every retrieval needs embeddings. For structured or well-organized collections, an agent can navigate: read a table of contents or a document tree, open the relevant section, follow links, or search with plain text tools. This vectorless retrieval avoids embedding pipelines and can be more precise for long, structured documents, at the cost of more model calls.

What the term means

Vectorless RAG is retrieval-augmented generation in which no embedding similarity is used to find the context. The term became popular in 2025 with PageIndex, but it covers several older and newer ideas. What they share: they find information by structure, exact matching or model reasoning rather than by "nearest vector".

Approach How it finds context Best for
Keyword and full-text search BM25 in OpenSearch, Elasticsearch, Postgres full-text Codes, names, exact phrases; a strong baseline that is often underrated
Reasoning over a document tree An LLM reads a table of contents with summaries and navigates down to the right section Long structured documents: filings, contracts, manuals, regulations
Agentic search with tools The agent lists, greps and reads files like a developer Codebases, wikis, folders of documents

Reasoning over a document tree

PageIndex (Vectify AI, open source) builds a hierarchical "table of contents" index of a long document, with a summary at every node. At question time an LLM reads the top-level summaries, picks the branch most likely to hold the answer, and moves down level by level, like a person using a manual's contents page. Its authors report 98.7% accuracy on FinanceBench, a benchmark of questions over financial filings. That is a vendor-reported result, so verify on your own documents. The approach also leaves an explainable trail: the path it took.

Here is the core idea in 30 lines. A keyword scorer stands in for the LLM so it runs offline; the real prompt is shown.

# A tiny "table of contents" index: each node has a title, a summary and either children or text.
MANUAL = {
    "title": "ShopKart Seller Policy Manual", "summary": "Rules for sellers on ShopKart.",
    "children": [
        {"title": "1 Onboarding", "summary": "Registration, GST and KYC documents, bank account verification.",
         "children": [
             {"title": "1.1 Documents", "summary": "GSTIN, PAN, cancelled cheque.", "text": "Sellers must upload GSTIN, PAN and a cancelled cheque. Composition-scheme sellers can sell only within their state."},
             {"title": "1.2 Bank verification", "summary": "Penny-drop check of the settlement account.", "text": "A penny-drop test verifies the bank account within 24 hours."}]},
        {"title": "2 Fees and payouts", "summary": "Commission rates, fixed fees, payout cycle and deductions.",
         "children": [
             {"title": "2.1 Commission", "summary": "Category-wise commission percentages.", "text": "Electronics carry 5% commission; fashion carries 15%; books carry 8%."},
             {"title": "2.2 Payout cycle", "summary": "When sellers are paid and what is deducted.", "text": "Payouts are made 7 days after delivery, net of commission, shipping and 1% TCS."}]},
        {"title": "3 Returns and penalties", "summary": "Return windows, seller-fault returns and penalty amounts.",
         "children": [
             {"title": "3.1 Seller-fault returns", "summary": "Wrong, damaged or counterfeit items.", "text": "For wrong or damaged items the seller pays reverse shipping plus a INR 100 penalty."}]},
    ],
}

def navigate(node: dict, question: str, choose, path=()) -> tuple[str, tuple]:
    """Walk down the tree: at each level, ask `choose` which child to open. No vectors anywhere."""
    if "text" in node:
        return node["text"], path + (node["title"],)
    options = [f'{i}: {c["title"]} - {c["summary"]}' for i, c in enumerate(node["children"])]
    i = choose(question, options)                      # in production: an LLM call (prompt below)
    return navigate(node["children"][i], question, choose, path + (node["title"],))

CHOOSE_PROMPT = """You are navigating a document's table of contents to answer a question.
Question: {question}
Sections:
{options}
Reply with only the number of the section most likely to contain the answer."""

def keyword_chooser(question: str, options: list[str]) -> int:
    """Offline stand-in for the LLM: pick the option sharing the most words with the question."""
    q = set(question.lower().replace("?", "").split())
    return max(range(len(options)), key=lambda i: len(q & set(options[i].lower().replace(",", "").split())))

text, path = navigate(MANUAL, "When are sellers paid, and what is deducted from the payout?", keyword_chooser)
print(" > ".join(path))
print(text)
What you should see
ShopKart Seller Policy Manual > 2 Fees and payouts > 2.2 Payout cycle
Payouts are made 7 days after delivery, net of commission, shipping and 1% TCS.

With an LLM as the chooser, the navigator handles questions that share no words with the headings ("how much does the platform keep from an electronics sale?") by reasoning about what each section covers.

Costs to weigh: building the tree needs an LLM pass to write summaries, and each question makes one model call per tree level. It pays off for long, structured, repeatedly queried documents, and loses to vector search for broad search across thousands of short documents.

Agentic search with ordinary tools

Coding agents such as Claude Code popularized another vectorless approach: no index at all. The agent uses ls, grep and read tools on files, exactly as a developer would, and iterates. With modern models this often beats a vector index on codebases and technical wikis, because exact identifiers matter and the agent can follow references.

import pathlib, re, tempfile

root = pathlib.Path(tempfile.mkdtemp())
(root / "policies").mkdir()
(root / "policies" / "refunds.md").write_text("# Refunds\nDamaged items: refundable within 30 days.\nUPI refunds: 2 days.\n")
(root / "policies" / "cod.md").write_text("# Cash on delivery\nCOD fee: INR 30. Limit: INR 10,000.\n")

def list_files(folder: str = ".") -> list[str]:
    return sorted(str(p.relative_to(root)) for p in (root / folder).rglob("*") if p.is_file())

def grep(pattern: str) -> list[str]:
    """Return 'file:line: text' for every line matching a regular expression."""
    hits = []
    for path in list_files():
        for n, line in enumerate((root / path).read_text().splitlines(), start=1):
            if re.search(pattern, line, re.IGNORECASE):
                hits.append(f"{path}:{n}: {line}")
    return hits

def read_file(path: str, start: int = 1, end: int = 50) -> str:
    lines = (root / path).read_text().splitlines()
    return "\n".join(lines[start - 1:end])

# What an agent typically does, step by step:
print(list_files())
print(grep(r"fee|charge"))
print(read_file("policies/cod.md"))
What you should see
['policies/cod.md', 'policies/refunds.md']
['policies/cod.md:2: COD fee: INR 30. Limit: INR 10,000.']
# Cash on delivery
COD fee: INR 30. Limit: INR 10,000.

Give these three functions to any agent from the LangChain and LangGraph and Other agent frameworks, compared sections as tools, and it can answer questions over a folder with no index to build or keep in sync. The cost is more model calls per question, so it suits low-volume, high-value questions.

Step by step: vectorless retrieval you can deploy

Step 1 · Build the tree from a document's own headings

Hand-writing a table of contents does not scale. Most long documents already have structure (Markdown or HTML headings, PDF bookmarks, numbered sections), so the index can be built automatically, with an LLM writing the node summaries. Here the summary is the first sentence of each section, standing in for that model call.

SELLER_MD = """# ShopKart Seller Policy Manual
Rules for sellers on ShopKart.
## 1 Onboarding
Registration, GST and KYC documents, bank account verification.
### 1.1 Documents
Sellers must upload GSTIN, PAN and a cancelled cheque. Composition-scheme sellers can sell only within their state.
### 1.2 Bank verification
A penny-drop test verifies the bank account within 24 hours.
## 2 Fees and payouts
Commission rates, fixed fees, payout cycle and deductions.
### 2.1 Commission
Electronics carry 5% commission; fashion carries 15%; books carry 8%.
### 2.2 Payout cycle
Payouts are made 7 days after delivery, net of commission, shipping and 1% TCS.
## 3 Returns and penalties
Return windows, seller-fault returns and penalty amounts.
### 3.1 Seller-fault returns
For wrong or damaged items the seller pays reverse shipping plus a INR 100 penalty.
"""

def build_tree(markdown: str, summarize=lambda text: text.split(". ")[0].rstrip(".") + ".") -> dict:
    """Turn headings into a tree; leaves keep their text, every node gets a summary (an LLM call in production)."""
    root, stack = None, []
    for block in filter(None, re.split(r"(?m)^(?=#)", markdown.strip())):
        heading, _, body = block.partition("\n")
        level = len(heading) - len(heading.lstrip("#"))
        node = {"title": heading.lstrip("# ").strip(), "summary": summarize(body.strip()), "children": [],
                "body": body.strip()}
        while stack and stack[-1][0] >= level:
            stack.pop()
        if stack:
            stack[-1][1]["children"].append(node)
        else:
            root = node
        stack.append((level, node))
    def finish(n):                                   # leaves keep their text; inner nodes keep only summaries
        if n["children"]:
            for c in n["children"]:
                finish(c)
            del n["body"]
        else:
            n["text"] = n.pop("body"); del n["children"]
    finish(root)
    return root

TREE = build_tree(SELLER_MD)
print([c["title"] for c in TREE["children"]], "|", TREE["children"][1]["summary"])
text, path = navigate(TREE, "When are sellers paid, and what is deducted from the payout?", keyword_chooser)
print(" > ".join(path))
What you should see
['1 Onboarding', '2 Fees and payouts', '3 Returns and penalties'] | Commission rates, fixed fees, payout cycle and deductions.
ShopKart Seller Policy Manual > 2 Fees and payouts > 2.2 Payout cycle

The same navigate function from above works on the generated tree. For PDFs, PageIndex and similar tools detect the structure from the layout (and with an LLM, from the text itself when there are no headings).

Step 2 · Beam navigation with a leaf check

A greedy navigator that picks one branch per level fails when an early choice is wrong. Two standard fixes: keep the top few branches at each level (a beam), and check the leaf before answering, backtracking to the next candidate if it does not contain the answer.

def score_option(question: str, option: dict) -> int:
    """Offline stand-in for an LLM's relevance judgement on a section title and summary."""
    q = set(re.findall(r"[a-z0-9%]+", question.lower()))
    return len(q & set(re.findall(r"[a-z0-9%]+", (option["title"] + " " + option["summary"]).lower())))

def leaf_answers(question: str, text: str) -> bool:
    """Stand-in for: 'Does this passage answer the question? yes/no'."""
    q = set(re.findall(r"[a-z0-9%]+", question.lower())) - {"the", "a", "is", "what", "do", "for", "on", "how"}
    return len(q & set(re.findall(r"[a-z0-9%]+", text.lower()))) >= 2

def beam_navigate(node: dict, question: str, beam: int = 2, path=()) -> tuple[str, tuple] | None:
    if "text" in node:
        return (node["text"], path + (node["title"],)) if leaf_answers(question, node["text"]) else None
    ranked = sorted(node["children"], key=lambda c: -score_option(question, c))
    for child in ranked[:beam]:                          # explore the best `beam` branches, best first
        found = beam_navigate(child, question, beam, path + (node["title"],))
        if found:
            return found
    return None

q = "What does a seller pay for reverse shipping?"
print("greedy:", navigate(TREE, q, keyword_chooser)[1])
print("beam:  ", beam_navigate(TREE, q)[1])
What you should see
greedy: ('ShopKart Seller Policy Manual', '1 Onboarding', '1.1 Documents')
beam:   ('ShopKart Seller Policy Manual', '3 Returns and penalties', '3.1 Seller-fault returns')

The greedy navigator matched the word "seller" in the wrong place and ended in the onboarding documents; the beam navigator rejected that leaf, backtracked to the next branch, and found the penalty rule. The leaf check is also why the beam navigator can return nothing: when no leaf passes, say "not found" rather than guessing. A beam of 2 roughly doubles model calls in the worst case, which is usually still far fewer tokens than reading the whole document.

Step 3 · Long context with caching: the cost arithmetic

Cache-augmented generation skips retrieval: put the whole corpus in a cached prompt prefix and ask questions against it. Whether that is cheaper than RAG is arithmetic, so do the arithmetic.

def monthly_cost(questions: int, corpus_tokens: int, rag_context_tokens: int = 3_000, answer_tokens: int = 300,
                 price_in: float = 3.0, price_cached: float = 0.30, price_out: float = 15.0,
                 cache_writes_per_day: int = 24) -> dict:
    """USD per month. Prices per million tokens; cache writes priced as normal input here for simplicity."""
    out = questions * answer_tokens * price_out / 1e6
    cag = (questions * corpus_tokens * price_cached + cache_writes_per_day * 30 * corpus_tokens * price_in) / 1e6 + out
    rag = questions * rag_context_tokens * price_in / 1e6 + out
    return {"CAG": round(cag), "RAG": round(rag)}

for corpus in (50_000, 400_000):
    for q in (10_000, 200_000):
        print(f"corpus {corpus:>7,} tokens, {q:>7,} questions/month:", monthly_cost(q, corpus))
What you should see
corpus  50,000 tokens,  10,000 questions/month: {'CAG': 303, 'RAG': 135}
corpus  50,000 tokens, 200,000 questions/month: {'CAG': 4008, 'RAG': 2700}
corpus 400,000 tokens,  10,000 questions/month: {'CAG': 2109, 'RAG': 135}
corpus 400,000 tokens, 200,000 questions/month: {'CAG': 25764, 'RAG': 2700}

Even with cached input at a tenth of the normal price, reading the whole corpus on every question costs more than retrieving 3,000 relevant tokens, and the gap grows with corpus size. CAG wins on quality for small corpora where questions need the whole picture, and on simplicity; it rarely wins on cost. Plug in your own prices and cache lifetimes (they differ by provider).

Step 4 · Route each question to the right retriever

Teams with mature systems run several retrievers and route between them by query type, as the practice box below describes. The router is a cheap classifier; here, rules.

def choose_retriever(question: str) -> str:
    """Stand-in for a router model with few-shot examples of each type."""
    if re.search(r"\b[A-Z]-\d{4}\b|\bSKU-\d+\b|error \d+", question):
        return "keyword (exact identifiers)"
    if re.search(r"\b(how many|total|average|trend|by city|per month)\b", question, re.I):
        return "text-to-SQL (numbers live in tables, Lesson 4.16)"
    if re.search(r"\b(seller|commission|payout|penalty|onboarding)\b", question, re.I):
        return "tree navigation (the seller manual)"
    return "hybrid search (help centre)"

for q in ["Status of order A-1002?", "How many orders were late by city last month?",
          "What penalty does a seller pay for a wrong item?", "Can I return opened headphones?"]:
    print(f"{choose_retriever(q):48} <- {q}")
What you should see
keyword (exact identifiers)                      <- Status of order A-1002?
text-to-SQL (numbers live in tables, Lesson 4.16) <- How many orders were late by city last month?
tree navigation (the seller manual)              <- What penalty does a seller pay for a wrong item?
hybrid search (help centre)                      <- Can I return opened headphones?

An agent with all four retrievers as tools makes the same choice itself (agentic RAG, Lesson 14.76); a router is cheaper and more predictable when the categories are stable.

Industry practice
Embeddings are a tool, not the definition of RAG

The common thread among teams with mature RAG systems is that they choose retrieval by query type, and many end up with several retrievers behind a router: keyword for codes, vectors for paraphrases, SQL for numbers, navigation for long documents. "Vector database first" is a habit from 2023, not a requirement.

In production
Where vectorless approaches disappoint

Tree navigation depends entirely on good headings and section summaries; on documents with vague or missing headings it wanders, and every level costs a model call, so deep trees get slow. Agentic file search with grep is excellent for code and identifiers but spends many tool calls on natural-language questions. Long context with caching is simple, but the cost of every uncached question and the time to first token grow with the document. Most teams that adopt these keep a hybrid retriever as the fallback and route by question type.

Exercises

Predict before you run

Break it on purpose

Let the chooser pick a wrong branch at level 1. What happens to the answer, and how could the navigation recover? (Solution B1.)

Debugging exercise

An agent using grep and list_files answers well on code but badly on the policy PDF corpus. Why might plain-text tools fail there? (Solution D1.)

Make it your own

Add a fallback to navigate: if the leaf it reaches does not contain the question's keywords, go back one level and try the next child. (Solution M1.)

Solutions

SolutionP1 · Reasoning over structure

Four choices, so four model calls, against embedding the whole document once. Tree navigation trades calls for following the document's own structure, which helps long, well-organized documents.

SolutionB1 · Errors compound down the tree

Every later choice is inside the wrong branch, so the answer comes from the wrong section. Recover with backtracking (try the next-best branch when the leaf does not answer), or by exploring the top two branches.

SolutionD1 · Tools need text to search

PDFs must be parsed to text first, and grep matches exact words, so paraphrased questions miss. Agentic search with ordinary tools works best on well-named, text-based corpora such as code and Markdown.

SolutionM1 · Backtracking

Keep the ranked choices at each level, check the leaf, and on failure try the next-ranked sibling, with a limit on backtracks. Measure how many questions need it.

Explain the mechanismWhat is vectorless retrieval, and when does it make sense?

Worked answer. Retrieval without embeddings: navigating a document's structure with a model choosing sections, or an agent searching with tools such as grep and file listings. It suits long, structured documents and codebases where structure and exact names matter, and avoids building and maintaining an index, at the cost of more model calls per question.

A plausible wrong answer. "It replaces vector search." It complements it for some corpora.

Worked answer. Fewer levels (wider nodes with good summaries), a smaller model for choices, caching of node summaries, and a hybrid search first to narrow the starting point. Measure calls per question.

Defend a designWould you use agentic file search instead of a vector index for an internal wiki?

Worked answer. For a modest, well-organized wiki where pages have clear titles and terms, it can work well and is simple to maintain. For a large, messy wiki with paraphrased questions, a hybrid index is more reliable and cheaper per question. Test both on real questions.
