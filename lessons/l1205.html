Why this came about

Open-weight models such as Llama (2023) made self-hosting possible, and serving engines such as vLLM (2023) made it efficient through better memory management and batching. Running models yourself became an option for cost, control and privacy.

In plain words first
Renting the oven, or building your own

Calling a hosted model is renting someone else's oven; self-hosting is buying one. Running a model yourself means GPUs with enough memory for the weights and the per-request cache, a serving engine that batches many requests together, and the operations to keep it up. It can win on cost at high volume, on data control, or for fine-tuned models, and loses on effort and flexibility.

Self-hosting is cheaper only at high, steady utilization. A GPU you pay for around the clock but use 15% of the time is far more expensive per token than an API.

Step 1 · Size the memory

GPU memory holds two big things: the weights and the KV cache (the attention keys and values of every token in every active conversation). The KV cache is what limits how many users one GPU serves.

from dataclasses import dataclass

@dataclass
class ModelShape:
    name: str
    params_b: float            # billions of parameters
    layers: int
    kv_heads: int              # key-value heads (fewer than attention heads with grouped-query attention)
    head_dim: int

def weights_gb(m: ModelShape, bytes_per_param: float) -> float:
    return m.params_b * 1e9 * bytes_per_param / 1e9

def kv_cache_gb(m: ModelShape, context_tokens: int, concurrent: int, bytes_per_value: float = 2) -> float:
    per_token = 2 * m.layers * m.kv_heads * m.head_dim * bytes_per_value     # 2 = one key and one value
    return per_token * context_tokens * concurrent / 1e9

llama8b = ModelShape("Llama 3.1 8B", params_b=8.0, layers=32, kv_heads=8, head_dim=128)
llama70b = ModelShape("Llama 3.1 70B", params_b=70.6, layers=80, kv_heads=8, head_dim=128)

for m in (llama8b, llama70b):
    print(m.name)
    for label, b in (("FP16/BF16", 2), ("FP8/INT8", 1), ("INT4", 0.5)):
        print(f"  weights {label:9} {weights_gb(m, b):6.1f} GB")
    print(f"  KV cache per token     {2 * m.layers * m.kv_heads * m.head_dim * 2 / 1024:6.0f} KiB (FP16)")
    print(f"  KV cache, 32 users x 8k tokens {kv_cache_gb(m, 8192, 32):6.1f} GB")
What you should see
Llama 3.1 8B
  weights FP16/BF16   16.0 GB
  weights FP8/INT8     8.0 GB
  weights INT4         4.0 GB
  KV cache per token        128 KiB (FP16)
  KV cache, 32 users x 8k tokens   34.4 GB
Llama 3.1 70B
  weights FP16/BF16  141.2 GB
  weights FP8/INT8    70.6 GB
  weights INT4        35.3 GB
  KV cache per token        320 KiB (FP16)
  KV cache, 32 users x 8k tokens   85.9 GB

The 8B model needs about 50 GB for 32 users at 8k tokens of context: more than half of it is KV cache, not weights. That is why long contexts and many concurrent users drive serving cost, and why the techniques below exist. Modern models use grouped-query attention, with far fewer key-value heads than attention heads (8 instead of 32 here), which already shrinks the KV cache fourfold. Add 10 to 20% headroom for activations and runtime overhead.

Step 2 · Quantization, by hand

Quantization stores weights in fewer bits: each block of weights is divided by a scale, rounded to a small integer, and multiplied back at run time. Two choices decide the quality: how many bits, and how many weights share one scale. Real models also have a few outlier channels with much larger values, and those outliers are what make low-bit quantization hard:

import numpy as np

rng = np.random.default_rng(0)
W = rng.normal(0, 0.02, size=(4096, 4096)).astype(np.float32)     # one layer's weight matrix
x = rng.normal(0, 1, size=(4096,)).astype(np.float32)                # one input vector
W[:, 7] *= 40                                                        # a few outlier channels, as real models have

def quantize(w: np.ndarray, bits: int, group: int | None = None) -> np.ndarray:
    """Symmetric round-to-nearest quantization, per output row or per group of columns."""
    qmax = 2 ** (bits - 1) - 1
    shaped = w.reshape(w.shape[0], -1, group) if group else w[:, None, :]
    scale = np.abs(shaped).max(axis=-1, keepdims=True) / qmax          # one scale per row (or group)
    q = np.clip(np.round(shaped / scale), -qmax - 1, qmax)
    return (q * scale).reshape(w.shape)                                 # dequantized, to measure the error

exact = W @ x
for label, bits, group in [("INT8 per row", 8, None), ("INT4 per row", 4, None), ("INT4 groups of 128", 4, 128)]:
    approx = quantize(W, bits, group) @ x
    rel_err = np.linalg.norm(approx - exact) / np.linalg.norm(exact)
    mb = W.size * bits / 8 / 2**20
    print(f"{label:20} {mb:5.1f} MB (FP16 {W.size * 2 / 2**20:.0f} MB)  output error {rel_err:.2%}")
What you should see
INT8 per row          16.0 MB (FP16 32 MB)  output error 7.30%
INT4 per row           8.0 MB (FP16 32 MB)  output error 66.65%
INT4 groups of 128     8.0 MB (FP16 32 MB)  output error 14.82%

With one scale per row, the outlier column sets the scale for the whole row, so all the ordinary weights get squeezed into a handful of integer levels; at 4 bits that destroys the layer. Giving every 128 weights their own scale, group-wise quantization (what GPTQ and AWQ do, plus smarter rounding and outlier handling) cuts the error by more than four times at almost the same size. This toy exaggerates the errors (production methods calibrate on real data), but the lesson holds: never accept a quantized model on perplexity alone; run your own evals, especially for tool calling and structured output, which degrade first.

Step 3 · Continuous batching, simulated

A GPU produces one token for every request in the batch at each decode step, so the question is when new requests may join. Static batching waits for the whole batch to finish. Continuous batching admits a waiting request the moment any slot frees up:

import heapq

def simulate(requests: list[tuple[int, int]], max_batch: int, continuous: bool) -> tuple[int, float]:
    """requests: (arrival_step, output_tokens). One decode step produces one token for every running request.
    Returns (total steps to finish everything, mean latency in steps)."""
    waiting = sorted(requests)
    running, done, step = [], [], 0
    while waiting or running:
        can_admit = continuous or not running                    # static batching waits for the batch to drain
        while can_admit and waiting and waiting[0][0] <= step and len(running) < max_batch:
            arrival, tokens = waiting.pop(0)
            running.append([tokens, arrival])
        step += 1
        for r in running:
            r[0] -= 1
        done += [step - r[1] for r in running if r[0] == 0]
        running = [r for r in running if r[0] > 0]
    return step, sum(done) / len(done)

workload = [(0, 400), (0, 20), (0, 20), (0, 20), (2, 20), (2, 20), (4, 20), (4, 20)]   # one long, many short
for continuous in (False, True):
    steps, mean_latency = simulate(workload, max_batch=4, continuous=continuous)
    print(f"{'continuous' if continuous else 'static    '} batching: all done at step {steps}, mean latency {mean_latency:.0f} steps")
What you should see
static     batching: all done at step 420, mean latency 266 steps
continuous batching: all done at step 400, mean latency 78 steps

One 400-token request held three slots hostage under static batching: the short requests that arrived later waited for it to finish. With continuous batching they flowed through the free slots, and mean latency fell by more than three times on the same hardware. Every modern engine (vLLM, SGLang, TensorRT-LLM) does this; it is one reason a hand-rolled transformers server is so much slower than vLLM.

Step 4 · Prefix caching: why agents love it

An agent re-sends its whole context on every step: system prompt, tool definitions and the growing history. Without caching, the server recomputes all of it every time. Prefix caching keeps the KV cache of the shared prefix and computes only what is new. Hosted APIs offer the same thing as prompt caching, billed at a discount:

SYSTEM_AND_TOOLS = 6_000          # tokens: instructions plus tool definitions, identical on every call
PER_STEP_GROWTH = 800             # tokens each agent step adds (tool call plus result)
STEPS = 10

prefill_no_cache = sum(SYSTEM_AND_TOOLS + PER_STEP_GROWTH * i for i in range(STEPS))
# With prefix caching, step i only computes what is new since step i-1 (the first step computes everything).
prefill_cached = SYSTEM_AND_TOOLS + PER_STEP_GROWTH * (STEPS - 1)
print(f"prompt tokens processed over {STEPS} steps: {prefill_no_cache:,} without prefix caching, "
      f"{prefill_cached:,} with it ({1 - prefill_cached / prefill_no_cache:.0%} less prefill)")

# The same effect on a hosted API with prompt caching (illustrative prices per million input tokens)
price, cache_read, cache_write = 3.00, 0.30, 3.75                 # cache reads at 10%, writes at 125%
cost_plain = prefill_no_cache / 1e6 * price
reused = prefill_no_cache - prefill_cached
cost_cached = (reused * cache_read + prefill_cached * cache_write) / 1e6
print(f"input cost per run: ${cost_plain:.4f} uncached vs ${cost_cached:.4f} with prompt caching")
What you should see
prompt tokens processed over 10 steps: 96,000 without prefix caching, 13,200 with it (86% less prefill)
input cost per run: $0.2880 uncached vs $0.0743 with prompt caching

That is why context engineering advice says to keep the start of the prompt stable: put instructions and tool definitions first, append history, and never insert a timestamp or a per-request value near the top, which would break the cache for everything after it. Discounts and rules differ by provider (explicit cache breakpoints, minimum lengths, cache lifetimes), so check the current pricing page; the prices above are illustrative.

In production
Self-hosting surprises
  • Quantization that passes benchmarks and fails your task: tool calling and JSON output often degrade first. Re-run your own evals after every quantization or engine change.
  • Out-of-memory under real traffic: long prompts from a few users exhaust the KV cache. Set max-model-len and concurrency from the memory math in Step 1, with headroom.
  • Cold starts: loading a large model takes minutes, so scale-to-zero can make the first user wait. Keep a warm minimum and scale on queue depth.
  • Chat templates: a wrong or missing chat template makes a good model look broken. Use the template shipped with the model and test tool calling end to end.

Step 5 · The techniques inside modern inference engines

Technique What it does Effect
Continuous batching Adds and removes requests from the running batch at every step, instead of waiting for a batch to finish Much higher throughput
PagedAttention (vLLM) Stores the KV cache in fixed-size pages, like virtual memory Little memory wasted; more concurrent users
Prefix caching (vLLM's automatic prefix caching, SGLang's RadixAttention) Reuses the KV cache of a shared prompt prefix across requests Big savings for agents with long, stable system prompts and tool definitions
Quantization (FP8, INT8, INT4 via AWQ or GPTQ; GGUF for llama.cpp; FP4 on newest GPUs) Stores weights (and sometimes the KV cache) in fewer bits Fits bigger models or more users; check quality on your evals
Speculative decoding (draft models, EAGLE-style heads) A small model proposes tokens that the big model verifies in parallel Lower latency per token at the same quality
Tensor and pipeline parallelism Splits one model across several GPUs Serve models larger than one GPU
Disaggregated prefill and decode Runs prompt processing and token generation on different GPU pools Better latency and utilization at large scale
Multi-LoRA serving Serves many small fine-tuned adapters on one base model One deployment for many customized variants
Structured output (grammar-constrained decoding) Forces output to match a JSON schema or grammar Reliable tool calls from open models

Step 7 · Measure what users feel

Metric Meaning
TTFT (time to first token) Wait before anything appears; dominated by prefill and queueing
TPOT / ITL (time per output token, inter-token latency) Streaming speed once output starts
Throughput Total tokens per second across all users
Goodput Requests per second that meet your latency targets; the number to optimize
Cost per million tokens GPU cost divided by tokens actually served

Load-test with realistic prompt and output lengths and concurrency, using tools such as vLLM's benchmark scripts, GuideLLM or LLMPerf, and set targets per use case (an interactive agent needs low TTFT; a batch summarizer needs throughput).

A load test is a short script. This one runs against a fake GPU server that takes 200 ms of prefill, 20 ms per token, and serves at most four requests at a time, then reports the numbers in the table:

import asyncio, json, threading, time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import httpx

PREFILL_S, PER_TOKEN_S, MAX_BATCH = 0.20, 0.02, 4   # a fake GPU: 200 ms prefill, 20 ms per token, 4 at a time
gpu = threading.BoundedSemaphore(MAX_BATCH)

class FakeGPUServer(BaseHTTPRequestHandler):
    def log_message(self, *a): pass
    def do_POST(self):
        self.rfile.read(int(self.headers["Content-Length"]))
        self.send_response(200); self.send_header("Content-Type", "text/event-stream"); self.end_headers()
        with gpu:                                         # requests beyond the batch size wait in a queue
            time.sleep(PREFILL_S)
            for i in range(30):
                chunk = {"choices": [{"index": 0, "delta": {"content": f"tok{i} "}}]}
                self.wfile.write(f"data: {json.dumps(chunk)}\n\n".encode()); self.wfile.flush()
                time.sleep(PER_TOKEN_S)
        self.wfile.write(b"data: [DONE]\n\n")

srv = ThreadingHTTPServer(("127.0.0.1", 0), FakeGPUServer)
threading.Thread(target=srv.serve_forever, daemon=True).start()
URL = f"http://127.0.0.1:{srv.server_address[1]}/v1/chat/completions"

async def one_request(client: httpx.AsyncClient) -> dict:
    start, stamps = time.perf_counter(), []
    async with client.stream("POST", URL, json={"model": "m", "stream": True, "messages": []}) as r:
        async for line in r.aiter_lines():
            if line.startswith("data: {"):
                stamps.append(time.perf_counter())
    ttft = stamps[0] - start
    itl = (stamps[-1] - stamps[0]) / (len(stamps) - 1)
    return {"ttft": ttft, "itl": itl, "total": stamps[-1] - start, "tokens": len(stamps)}

async def load_test(concurrency: int, slo_ttft: float = 0.5) -> None:
    async with httpx.AsyncClient(timeout=30) as client:
        t0 = time.perf_counter()
        results = await asyncio.gather(*(one_request(client) for _ in range(concurrency)))
        wall = time.perf_counter() - t0
    ttfts = sorted(r["ttft"] for r in results)
    p95 = ttfts[int(0.95 * (len(ttfts) - 1))]
    good = sum(r["ttft"] <= slo_ttft for r in results)
    print(f"concurrency {concurrency:2}: TTFT p95 ~{round(p95, 1)} s, ITL ~{round(results[0]['itl'] * 1000, -1):.0f} ms, "
          f"throughput ~{round(sum(r['tokens'] for r in results) / wall / 50) * 50} tok/s, goodput {good}/{len(results)} within SLO")

for c in (1, 4, 16):
    asyncio.run(load_test(c))
What you should see
concurrency  1: TTFT p95 ~0.2 s, ITL ~20 ms, throughput ~50 tok/s, goodput 1/1 within SLO
concurrency  4: TTFT p95 ~0.2 s, ITL ~20 ms, throughput ~150 tok/s, goodput 4/4 within SLO
concurrency 16: TTFT p95 ~2.6 s, ITL ~20 ms, throughput ~150 tok/s, goodput 4/16 within SLO

Your timings will differ slightly with machine load. This is the shape every real server shows. Throughput rises with concurrency until the hardware is full, then stays flat, while queueing makes time to first token climb: at 16 concurrent users throughput is unchanged, but only 4 of 16 requests met the 0.5 s target. Goodput, not throughput, tells you the capacity of one replica, and that number sets the autoscaling threshold. (On a real GPU the inter-token latency also rises as the batch grows; this fake keeps it fixed to make the queueing visible.)

Step 8 · Self-host or call an API: the break-even

Put your measured throughput into a cost model and find the break-even utilization before deciding:

def monthly_cost_self_hosted(gpus: int, gpu_hour_usd: float, ops_overhead: float = 0.25) -> float:
    return gpus * gpu_hour_usd * 24 * 30 * (1 + ops_overhead)          # people, monitoring, spare capacity

def tokens_per_month(tokens_per_s_at_full_load: float, utilization: float) -> float:
    return tokens_per_s_at_full_load * utilization * 3600 * 24 * 30

GPU_HOUR = 2.50              # illustrative on-demand price for one 80 GB GPU
FULL_LOAD_TPS = 2_500        # measured with your load test, for your model and prompt lengths
API_PER_M = 0.60             # blended API price per million tokens for a comparable model

cost = monthly_cost_self_hosted(gpus=1, gpu_hour_usd=GPU_HOUR)
for util in (0.10, 0.30, 0.60, 0.90):
    toks = tokens_per_month(FULL_LOAD_TPS, util)
    print(f"utilization {util:4.0%}: self-hosted ${cost / toks * 1e6:5.2f} per M tokens vs API ${API_PER_M:.2f}")
breakeven = cost / (API_PER_M / 1e6) / tokens_per_month(FULL_LOAD_TPS, 1.0)
print(f"break-even utilization: {breakeven:.0%}")
What you should see
utilization  10%: self-hosted $ 3.47 per M tokens vs API $0.60
utilization  30%: self-hosted $ 1.16 per M tokens vs API $0.60
utilization  60%: self-hosted $ 0.58 per M tokens vs API $0.60
utilization  90%: self-hosted $ 0.39 per M tokens vs API $0.60
break-even utilization: 58%

With these illustrative numbers one GPU must stay busy well over half of every hour of every day before it beats the API, and real traffic has nights and weekends. Reserved or spot GPUs, bigger batches and smaller quantized models move the line; so do engineering time and the cost of the evals you must re-run on every engine upgrade. Self-hosting wins on control and data locality far more often than on price.

Industry practice
Self-hosting, honestly

Teams that self-host successfully usually do it for a narrow reason (data that cannot leave, a fine-tuned small model at very high volume, or latency at the edge), keep frontier tasks on hosted APIs behind the same gateway, and run the serving stack like any critical service: autoscaling on queue depth, capacity planning with the memory math above, and evals whenever the model, quantization or engine version changes.

From the field
Character.AI: serving cost is an architecture decision

Character.AI, one of the highest-traffic chat services, reported in June 2024 that it served around 20,000 queries per second and had cut serving cost by at least 33 times since its 2022 launch, to under one cent per hour of conversation. Its leadership attributed this to work on the attention KV cache (the memory-bound part of serving covered in this lesson), better caching of conversation state between turns, and other model and serving changes they designed together rather than separately. You will rarely redesign a model's attention yourself, but the lesson transfers to every self-hosting decision: memory for the KV cache, cache hits across turns and quantization usually decide cost more than raw GPU price. Solutions

SolutionP1 · Memory and latency

KV-cache memory (context length times concurrent requests) and the latency each user experiences. Continuous batching and paged attention help, but memory is the limit.

SolutionB1 · Quantization changes quality

Accuracy drops on some tasks (reasoning, non-English), sometimes sharply. Evaluate quantized models on your eval set before serving.

SolutionD1 · Capacity

GPU utilization, queue length, KV-cache pressure and batch sizes. Add replicas, autoscale on queue depth, and cap context length.

SolutionM1 · Memory estimate

Weights: about 16 GB. KV cache: layers × 2 × hidden size × bytes × tokens × requests; for typical 8B models with grouped-query attention, tens of GB at this load. Compute with the model's config before buying hardware.

Explain the mechanismWhen should a company self-host models?

Worked answer. When data must not leave its environment, when a smaller open model meets quality at much lower cost at high volume, when latency or customization needs it, or when vendor dependence is unacceptable. It brings GPU operations, scaling, upgrades and evaluation of every change.

A plausible wrong answer. "Always, to save money." Low volume rarely justifies the operations.
