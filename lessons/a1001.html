The problem

In plain words first

A language model cannot read letters; it reads numbers. The tokenizer is the fixed dictionary that turns text into those numbers, by cutting text into pieces called tokens and giving each piece an ID. Common words become a single token, rare words are spelled from smaller pieces, and any text at all can still be written down. The tokenizer is chosen before training and never changes, so it decides how long every text is for the model, how much a request costs, and how fairly different languages are treated. This lesson builds byte pair encoding (BPE) from scratch, compares the three main algorithms by hand, and measures six real tokenizers on the same sentence in five languages and in code.

Your LLM does not read English. It does not read any language. It reads numbers.

The gap between "Hello, world!" and [15496, 11, 995, 0] is the tokenizer. Every word, every space, every punctuation mark must be converted into an integer before a model can process it. This conversion is not neutral. It bakes assumptions into the model that cannot be undone later.

Get this wrong and your model wastes capacity encoding common words with multiple tokens. A word the tokenizer has not seen as a whole is spelled in several pieces, and text in a language it was not trained on can need four to six times as many tokens as English (the run under Use it), so the same context window holds a fraction of the meaning. The difference between "this model handles code well" and "this model chokes on Python" often comes down to how the tokenizer was trained.

Every API call you make to GPT-4 or Claude is priced per token. Every token your model generates costs compute. The fewer tokens required to represent an output, the faster the end-to-end inference. Tokenization is not preprocessing. It is architecture.

Idea 1 · Three Approaches That Failed (and One That Won)

There are three obvious ways to convert text to numbers. Two of them do not work at scale.

Word-level tokenization splits on spaces and punctuation. "The cat sat" becomes ["The", "cat", "sat"]. Simple. But what about "tokenization"? Or "GPT-4o"? Or a German compound word like "Geschwindigkeitsbegrenzung"? Word-level requires a massive vocabulary to cover every word in every language. Miss a word and you get the dreaded [UNK] token -- the model's way of saying "I have no idea what this is." English alone has over a million word forms. Add code, URLs, scientific notation, and 100 other languages and you need an infinite vocabulary.

Character-level tokenization goes the other direction. "hello" becomes ["h", "e", "l", "l", "o"]. Vocabulary is tiny (a few hundred characters). No unknown tokens ever. But sequences become extremely long. A sentence that would be 10 word-level tokens becomes 50 character-level tokens. The model must learn that "t", "h", "e" together mean "the" -- burning attention capacity on something a human learns at age three.

Subword tokenization finds the sweet spot. Common words stay whole: "the" is one token. Rare words decompose into meaningful pieces: "unhappiness" becomes ["un", "happi", "ness"]. Vocabulary stays manageable (30K to 128K tokens). Sequences stay short. Unknown tokens essentially disappear because any word can be built from subword pieces.

Every modern LLM uses subword tokenization. GPT-2, GPT-4, BERT, Llama 3, Claude -- all of them. The question is which algorithm.

Idea 2 · BPE: Byte Pair Encoding

BPE is a greedy compression algorithm repurposed for tokenization. The idea is simple enough to fit on an index card.

Start with individual characters. Count every adjacent pair in the training corpus. Merge the most frequent pair into a new token. Repeat until you reach your target vocabulary size.

Here is BPE running on a tiny corpus with the words "lower", "lowest", and "newest":

  "lowest" x2
  "newest" x6

Step 0 -- Start with characters:
  l o w e r       (x5)
  l o w e s t     (x2)
  n e w e s t     (x6)

Step 1 -- Count adjacent pairs:
  (e,s): 8    (s,t): 8    (l,o): 7    (o,w): 7
  (w,e): 13   (e,r): 5    (n,e): 6    ...

Step 2 -- Merge most frequent pair (w,e) -> "we":
  l o we r        (x5)
  l o we s t      (x2)
  n e we s t      (x6)

Step 3 -- Recount and merge (e,s) -> "es":
  l o we r        (x5)
  l o we s t      (x2)    <- 'es' only forms from 'e'+'s', not 'we'+'s'
  n e we s t      (x6)    <- wait, the 'e' before 'we' and 's' after 'we'

Actually tracking this precisely:
  After "we" merge, remaining pairs:
  (l,o): 7   (o,we): 7   (we,r): 5   (we,s): 8
  (s,t): 8   (n,e): 6    (e,we): 6

Step 3 -- Merge (we,s) -> "wes" or (s,t) -> "st" (tied at 8, pick first):
  Merge (we,s) -> "wes":
  l o we r        (x5)
  l o wes t       (x2)
  n e wes t       (x6)

Step 4 -- Merge (wes,t) -> "west":
  l o we r        (x5)
  l o west        (x2)
  n e west        (x6)

...continue until target vocab size reached.

The merge table is the tokenizer. To encode new text, apply merges in the order they were learned. The training corpus determines which merges exist, and that choice permanently shapes what the model sees.

Idea 3 · Byte-Level BPE (GPT-2, GPT-3, GPT-4)

Standard BPE operates on Unicode characters. Byte-level BPE operates on raw bytes (0-255). This gives you a base vocabulary of exactly 256, handles any language or encoding, and never produces an unknown token.

GPT-2 introduced this approach. The base vocabulary covers every possible byte. BPE merges build on top of that. OpenAI's tiktoken library implements byte-level BPE with these vocabulary sizes:

  • GPT-2: 50,257 tokens
  • GPT-3.5/GPT-4: ~100,256 tokens (cl100k_base encoding)
  • GPT-4o: 200,019 tokens (o200k_base encoding)

Idea 4 · WordPiece (BERT)

WordPiece looks similar to BPE but picks merges differently. Instead of raw frequency, it maximizes the likelihood of the training data:

BPE merge criterion:      count(A, B)
WordPiece merge criterion: count(AB) / (count(A) * count(B))

BPE asks: "Which pair appears most often?" WordPiece asks: "Which pair appears together more often than you would expect by chance?" This subtle difference produces different vocabularies. WordPiece favors merges where co-occurrence is surprising, not just frequent.

WordPiece also uses a "##" prefix for continuation subwords:

"unhappiness" -> ["un", "##happi", "##ness"]
"embedding"   -> ["em", "##bed", "##ding"]

The "##" prefix tells you this piece continues a previous token. BERT uses WordPiece with a vocabulary of 30,522 tokens. DistilBERT keeps BERT's WordPiece tokenizer; RoBERTa switched to byte-level BPE.

Idea 5 · SentencePiece (Llama, T5)

SentencePiece treats the input as a raw stream of Unicode characters, including whitespace. No pre-tokenization step. No language-specific rules about word boundaries. This makes it genuinely language-agnostic -- it works on Chinese, Japanese, Thai, and other languages where spaces do not separate words.

SentencePiece supports two algorithms: - BPE mode: same merge logic as standard BPE, applied to raw character sequences - Unigram mode: starts with a large vocabulary and iteratively removes tokens that least affect the overall likelihood. The reverse of BPE -- prune instead of merge.

Llama 2 uses SentencePiece BPE with a vocabulary of 32,000 tokens. T5 uses SentencePiece Unigram with 32,000 tokens. Note: Llama 3 switched to a tiktoken-based byte-level BPE tokenizer with 128,256 tokens.

Idea 6 · Vocabulary Size Tradeoffs

This is a real engineering decision with measurable consequences.

Concrete numbers. For a 128K vocabulary with 4,096-dimensional embeddings, the embedding matrix alone is 128,000 x 4,096 = 524 million parameters. For a 32K vocabulary, it is 131 million parameters. That is a 400M parameter difference from the tokenizer choice alone.

But larger vocabularies compress text more aggressively. Llama 3's 128K tokenizer packs 3.94 characters of English into a token against 3.17 for Llama 2's 32K one, so a paragraph of 100 Llama 2 tokens needs about 80. That means about 20% fewer forward passes during generation. For a model serving millions of requests, that is a direct reduction in compute cost.

The trend is clear: vocabulary sizes are growing. GPT-2 used 50,257. GPT-4 uses ~100K. Llama 3 uses 128K. GPT-4o uses 200K.

Idea 7 · The Multilingual Tax

Tokenizers trained primarily on English are brutal to other languages. Korean text in GPT-2's tokenizer averages 2-3 tokens per word. Chinese can be worse. This means a Korean user effectively has a context window that is half the size of an English user's -- paying the same price for less information density.

This is why Llama 3 quadrupled its vocabulary from 32K to 128K. More tokens dedicated to non-English scripts means fairer compression across languages.

The same idea as a formula

BPE starts from single bytes and repeats one greedy step: count every adjacent pair (A,B) in the training data and merge the most frequent,

(A,B)∗=arg(A,B)max​count(A,B)

The ordered list of merges is the tokenizer; encoding replays the merges in that order.

so frequent pieces that appear everywhere (like a common letter) are merged late.

found by dynamic programming (Viterbi); training starts from a large vocabulary and prunes the pieces whose removal costs the least likelihood.

Costs of a vocabulary of size V with model width d: the input embedding has Vd parameters (and the same again for the output layer unless they are tied), while a text of n characters becomes about n/c tokens, where c is the characters per token. Attention costs grow with the square of the token count, so a tokenizer that needs 4× as many tokens for a language makes the context hold a quarter as much text of it and makes attention up to 16× as expensive for the same text.

Step 1 · Character-Level Tokenizer

Start at the foundation. A character-level tokenizer maps each character to its Unicode code point. No training needed. No unknown tokens. Just a direct mapping.

class CharTokenizer:
    def encode(self, text):
        return [ord(c) for c in text]

    def decode(self, tokens):
        return "".join(chr(t) for t in tokens)

"hello" becomes [104, 101, 108, 108, 111]. Every character is its own token. This is the baseline we improve on.

Step 2 · BPE Tokenizer from Scratch

The real implementation. We train on raw bytes (like GPT-2), count pairs, merge the most frequent, and record every merge in order. The merge table is the tokenizer.

from collections import Counter

class BPETokenizer:
    def __init__(self):
        self.merges = {}
        self.vocab = {}

    def _get_pairs(self, tokens):
        pairs = Counter()
        for i in range(len(tokens) - 1):
            pairs[(tokens[i], tokens[i + 1])] += 1
        return pairs

    def _merge_pair(self, tokens, pair, new_token):
        merged = []
        i = 0
        while i < len(tokens):
            if i < len(tokens) - 1 and tokens[i] == pair[0] and tokens[i + 1] == pair[1]:
                merged.append(new_token)
                i += 2
            else:
                merged.append(tokens[i])
                i += 1
        return merged

    def train(self, text, num_merges):
        tokens = list(text.encode("utf-8"))
        self.vocab = {i: bytes([i]) for i in range(256)}

        for i in range(num_merges):
            pairs = self._get_pairs(tokens)
            if not pairs:
                break
            best_pair = max(pairs, key=pairs.get)
            new_token = 256 + i
            tokens = self._merge_pair(tokens, best_pair, new_token)
            self.merges[best_pair] = new_token
            self.vocab[new_token] = self.vocab[best_pair[0]] + self.vocab[best_pair[1]]

        return self

    def encode(self, text):
        tokens = list(text.encode("utf-8"))
        for pair, new_token in self.merges.items():
            tokens = self._merge_pair(tokens, pair, new_token)
        return tokens

    def decode(self, tokens):
        byte_sequence = b"".join(self.vocab[t] for t in tokens)
        return byte_sequence.decode("utf-8", errors="replace")

The training loop is the core of BPE: count pairs, merge the winner, repeat. Each merge reduces the total token count. After num_merges rounds, the vocabulary grows from 256 (base bytes) to 256 + num_merges.

Encoding applies merges in the exact order they were learned. This matters. If merge 1 created "th" and merge 5 created "the", encoding must apply merge 1 first so that "the" can form from "th" + "e" in merge 5.

Decoding is the inverse: look up each token ID in the vocabulary, concatenate the bytes, decode to UTF-8.

Step 5 · Vocabulary Analysis

def analyze_vocabulary(tokenizer, test_texts):
    total_tokens = 0
    total_chars = 0
    token_usage = Counter()

    for text in test_texts:
        encoded = tokenizer.encode(text)
        total_tokens += len(encoded)
        total_chars += len(text)
        for t in encoded:
            token_usage[t] += 1

    print(f"Vocabulary size: {len(tokenizer.vocab)}")
    print(f"Total tokens across all texts: {total_tokens}")
    print(f"Total characters: {total_chars}")
    print(f"Avg tokens per character: {total_tokens / total_chars:.2f}")

    print(f"\nMost used tokens:")
    for token_id, count in token_usage.most_common(10):
        token_bytes = tokenizer.vocab[token_id]
        display = token_bytes.decode("utf-8", errors="replace")
        print(f"  Token {token_id:4d}: '{display}' (used {count} times)")

    unused = [t for t in tokenizer.vocab if t not in token_usage]
    print(f"\nUnused tokens: {len(unused)} out of {len(tokenizer.vocab)}")

This reveals the Zipf distribution in your vocabulary. A few tokens dominate (spaces, "the", "e"). Most tokens are rarely used. Production tokenizers follow this distribution: common patterns become single tokens, rare ones are spelled from several pieces. (The ID numbers themselves carry no meaning; they are just row numbers in the embedding table.)

Three algorithms on one corpus

BPE and WordPiece merges learned on the same five-word corpus, and Unigram splits by Viterbi with a fixed table of piece probabilities.

import math
from collections import Counter

# A word-frequency corpus (the classic example from the Hugging Face course): word -> count
corpus = {"hug": 10, "pug": 5, "pun": 12, "bun": 4, "hugs": 5}

def learn(rule, n_merges=5):
    words = {tuple(w): c for w, c in corpus.items()}
    merges = []
    for _ in range(n_merges):
        pairs, units = Counter(), Counter()
        for w, c in words.items():
            for u in w: units[u] += c
            for a, b in zip(w, w[1:]): pairs[(a, b)] += c
        score = (lambda p: pairs[p]) if rule == "BPE" else (lambda p: pairs[p] / (units[p[0]] * units[p[1]]))
        best = max(pairs, key=lambda p: (score(p), pairs[p]))
        merges.append(f"{best[0]}+{best[1]} ({pairs[best]}x, score {score(best):.3g})")
        new = {}
        for w, c in words.items():
            out, i = [], 0
            while i < len(w):
                if i + 1 < len(w) and (w[i], w[i + 1]) == best: out.append(w[i] + w[i + 1]); i += 2
                else: out.append(w[i]); i += 1
            new[tuple(out)] = c
        words = new
    return merges, words

for rule in ("BPE", "WordPiece"):
    merges, words = learn(rule)
    print(f"{rule:<9} merges in order: " + ", ".join(merges))
    print(f"{'':<9} words now: " + "  ".join(" ".join(w) for w in words))
    print()

# Unigram (SentencePiece, T5): every piece has a probability; a word is split into the most probable sequence of pieces
p = {"h": .05, "u": .05, "g": .04, "s": .05, "b": .02, "p": .03, "n": .04, "hu": .06, "ug": .10, "un": .12,
     "hug": .15, "pu": .04, "gs": .02, "bu": .02}
def viterbi(word):
    best = [(0.0, [])] + [(-math.inf, None)] * len(word)          # best log-probability of splitting word[:i]
    for i in range(1, len(word) + 1):
        for j in range(max(0, i - 4), i):
            piece = word[j:i]
            if piece in p and best[j][1] is not None:
                score = best[j][0] + math.log(p[piece])
                if score > best[i][0]: best[i] = (score, best[j][1] + [piece])
    return best[-1]
for w in ("hugs", "pun", "bugs"):
    lp, pieces = viterbi(w)
    print(f"Unigram split of {w!r}: {pieces}  (probability {math.exp(lp):.4f})")

Industry practice
What's current (2024–2026)
  • Large byte-level BPE vocabularies. Current open models use 128K–262K vocabularies (Llama 3: 128K; Qwen2.5 and Qwen3: about 151K; Gemma 3: 262K); OpenAI's o200k encoding (GPT-4o and later) has about 200K.

  • Pre-tokenisation choices matter. Splitting digits into single characters (Llama 1, Qwen) or groups of three (cl100k, o200k) is a deliberate choice for arithmetic; byte fallback avoids unknown tokens.

Recap
What to keep from this lesson
  • BPE: merge the most frequent adjacent pair, again and again; the ordered merge list is the tokenizer.
  • WordPiece scores merges by surprise, count(AB)/(count(A)count(B)); Unigram picks the most probable split.
  • Byte-level BPE never needs an unknown token; a tokenizer that does can silently throw text away.
  • Bigger vocabularies cost embedding parameters but shorten sequences, especially for non-English text.
  • Measure tokens per character on your own data and languages before choosing a model.

# Tokenizer Selection and Implementation

When starting an LLM project, apply this decision framework for tokenizer selection.

## When to use each tokenizer

**Byte-level BPE (tiktoken):** You are building on or fine-tuning GPT-family models. You need guaranteed handling of any input byte sequence. You want no unknown tokens.

**WordPiece (Hugging Face):** You are working with BERT-family models for classification, NER, or embedding tasks. You need the "##" continuation prefix for downstream tasks that rely on word boundary signals.

**SentencePiece (BPE or Unigram):** You are training from scratch. You need language-agnostic tokenization. Your data includes CJK languages, Thai, or other scripts without whitespace word boundaries. LLaMA, T5, and most multilingual models use this.

## Vocabulary size guidelines

- 32K tokens: good default for single-language models, keeps embedding layer small
- 50K-64K tokens: better for multilingual or code-heavy models
- 100K+ tokens: only when you have massive training data and want short sequences

Larger vocabulary means shorter sequences (cheaper inference) but more parameters in the embedding matrix. For a 100K vocabulary with 4096-dimensional embeddings, the embedding layer alone is 400M parameters.

## Pre-tokenization rules that matter

1. Split on whitespace before BPE to prevent cross-word merges
2. Separate digits individually if you want the model to learn arithmetic
3. Normalize Unicode (NFC) before tokenization for consistent behavior
4. Add special tokens for your use case: `<pad>`, `<eos>`, `<bos>`, `<unk>`, and any task-specific markers

## Red flags in tokenizer behavior

- Fertility above 2.0 for your target language: the model wastes context window
- Common domain words splitting into 3+ tokens: retrain with domain data
- Inconsistent tokenization of numbers: check digit-splitting rules
- Large vocabulary with many single-use tokens: reduce vocabulary size

## Building a custom tokenizer - checklist

1. Collect representative training data (at least 1GB of text in target domain)
2. Choose algorithm: BPE for general use, Unigram for multilingual
3. Set vocabulary size based on guidelines above
4. Configure pre-tokenization: whitespace splitting, digit handling, punctuation
5. Add special tokens
6. Train using Hugging Face tokenizers library (Rust backend, fast)
7. Validate: check fertility on held-out text across all target languages
8. Test edge cases: empty string, very long input, binary data, emoji, RTL text
9. Save and version the tokenizer alongside model checkpoints

Solutions

SolutionP1 · More than 80

More than 80: GPT-2 needs 86 tokens for the Hindi sentence, about six times the 14 for English. GPT-2's byte-level BPE was trained mostly on English web text, so Devanagari characters, which take three bytes each in UTF-8, are rarely merged and often stay as single bytes. A Hindi user would get a sixth of the context and pay six times as much per sentence. GPT-4o's tokenizer needs 20 for the same sentence; a vocabulary built with more Hindi in its training data fixes most of the gap.

SolutionB1 · The round trip passes, the compression does not

The round trip still passes, because decoding just concatenates the bytes of each token, whatever the split. But "The cat sat on the mat." now takes 15 tokens instead of 7: ['T', 'h', 'e', ' c', 'at', ' s', 'at', ...]. Later merges were learned on text where earlier merges had already been applied, so they combine pieces that only exist after those earlier merges; replayed first, they find nothing to merge, and the early merges then cut the text differently. A model trained on the correct tokenization would see token sequences it has never seen. The merge order is part of the tokenizer, which is why tokenizer files store merges as an ordered list, and why a round-trip test alone does not prove a tokenizer correct: also compare token counts with the reference implementation.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. After a match the scan moves one position instead of two, so the second symbol of the match is read again: it starts the next match or is copied to the output. Matches must not share a symbol. The correct result is (300, 7): the first two sevens become one new id and the third seven stays.

What the bug does.

With a step of one after a match, the scan sees the pair at positions zero and one, emits the new id, and then looks at positions one and two, which also match. The word gains a symbol it never had, so the merged corpus is wrong and every later step counts pairs on corrupted words. Encoding at inference reuses the same function, so every text with a repeated symbol decodes to different bytes than it was given.

The fix.

        if i + 1 < len(symbols) and symbols[i] == pair[0] and symbols[i + 1] == pair[1]:
            out.append(new_id)
            i += 2

Scan from left to right and continue after the second symbol of the match. The merge loop in the tokenizers chapter is exactly this, and the practice task has a mutant for the single step that fails on [a, a, a].

Why the left-to-right rule matters.

Non-overlapping replacement from the left is a convention, and the training loop and the encoder must share it. If training merged from the left and the encoder merged from the right, the same word would get different ids in training and at inference. The merge table only works when both sides apply it the same way.

A related check.

The function returns a new tuple. It must not write into the caller's sequence, because the training loop still holds the old corpus while it builds the new one.

Plausible wrong answers.

  • "Replace the pair with a string method on the joined symbols." Ids are integers, not characters, and joining them hides the boundaries between ids.
  • "Match from the right instead." Either direction works alone, but training and inference must use the same one; left-to-right is the convention.
  • "Return a list instead of a tuple to make it faster." The words are dictionary keys and must stay hashable.

Follow-ups an interviewer may ask.

  • (level 2) What does the same bug do to the pair counts of the next training step? Expected: it counts pairs that do not exist in the real corpus, so later merges are chosen on wrong numbers.
  • (level 2) Give an input where the bug produces a correct answer. Expected: only a word with no match for the pair, such as (7, 8, 7) with (7, 7); every match leaves an extra copy of its second symbol.
  • (level 3) How does a round-trip test catch this bug? Expected: encode a string with a repeated byte, decode the ids, and compare the bytes; the extra merged symbol expands to more bytes than the input had.

Take-homeYou get a corpus as a dictionary from words, each a tuple of byte ids, to the number of times the word occurs. Write the training loop that produces an ordered list of merges, and state the three rules that make the loop deterministic. Then tell me what the loop must not do to the caller's data.

Level 2 of 4 · about 30 minutes to answer well.

Short answer. Each step counts every adjacent pair inside each word, weighted by the word frequency, picks the pair with the highest count, rewrites every occurrence of that pair into one new id, and records the merge. The three rules are: pairs never cross a word boundary, ties go to the smallest pair in tuple order, and the loop stops when no pair repeats. The input dictionary and its tuples are never changed; the loop builds a new corpus each step.

The loop.

def train(units, num_merges, first_id=256):
    merges = []
    units = dict(units)
    for i in range(num_merges):
        pairs = count_pairs(units)
        best = best_pair(pairs)
        if best is None or pairs[best] < 2:
            break
        new_id = first_id + i
        units = {apply_merge(word, best, new_id): freq for word, freq in units.items()}
        merges.append((best, new_id))
    return merges, units

The first ids are reserved for the raw bytes, so the first merge gets the next free id and each later merge gets the next one. The merge list in training order is the tokenizer. Encoding fresh text applies the same merges in the same order, so a change of order at inference decodes a different stream of ids.

Weighted counts.

A pair inside a word that occurs five times adds five to the count, not one. Counting each occurrence once makes rare long words outvote common short ones, and the merge order changes. Pairs do not cross from the end of one word to the start of the next; the word split is what keeps merges inside words and lets them generalize.

Ties and the stop rule.

Two pairs with the same count must resolve the same way on every run, so the smallest pair in tuple order wins. Without a fixed rule, dictionary order decides and two training runs on the same corpus produce different tokenizers. The loop stops early when the best count is below two, because a pair that occurs once does not compress anything and only spends vocabulary slots.

Do not change the input.

The caller's dictionary and tuples stay as they were. Clearing and refilling the dictionary in place, or rewriting tuples through a list, changes data the caller may still use. Each step builds a new dictionary from the merged words.

Plausible wrong answers.

  • "Count each pair once per word." Frequency weighting is what makes common pairs win early.
  • "Take the first pair with the maximum count." Dictionary order is not stable across inputs, so the tokenizer becomes irreproducible.
  • "Keep merging until the budget is spent." A pair that appears once gains nothing and wastes vocabulary.

Follow-ups an interviewer may ask.

  • (level 2) Why does the symbol count fall as training proceeds, and what does that do to the cost of a step? Expected: each merge shortens words, so the pair count over the corpus shrinks and later steps are cheaper.
  • (level 2) What does the tie rule protect? Expected: reproducibility; the same corpus must give the same merge list on every machine.
  • (level 3) Two words merge into the same tuple after a step. What must the new dictionary do? Expected: add their frequencies together instead of keeping only the last one.

Explain the mechanismWalk me through one training step of byte-pair encoding on a small corpus, and tell me what the trained artifact actually is.

Level 1 of 4 · about 6 minutes to answer well.

Short answer. Start with every word split into base symbols, bytes or characters. Count every adjacent pair across the corpus, weighted by how often each word appears, merge the most frequent pair into one new symbol with the next free id, rewrite every occurrence, and repeat until the vocabulary reaches the target size. The artifact is the ordered list of merges; the vocabulary follows from it, and the same list applied in the same order is what encoding uses later.

A worked step.

Corpus: "lower" 5 times, "lowest" 2 times, "newest" 6 times.

l o w e r      (x5)
l o w e s t    (x2)
n e w e s t    (x6)

pair counts: (w,e): 13   (e,s): 8   (s,t): 8   (l,o): 7   (o,w): 7   (n,e): 6   (e,r): 5
merge (w,e) -> we

l o we r       (x5)
l o we s t     (x2)
n e we s t     (x6)

Recount, and the next step sees (we,s) and (s,t) tied at 8. The lesson's implementation breaks ties by sorting on the pair itself, so two runs over the same corpus produce the same table. After enough steps "west" exists as one symbol.

The three facts the loop encodes.

  1. Frequency weighting makes the pairs of common words win early.
  2. A pre-split on whitespace and punctuation keeps merges inside a word. A word-end marker also keeps "low" as a whole word distinct from "low" as the start of "lower".
  3. The merge list is ordered. Encoding applies merges in training order, so the order is part of the artifact.

Byte level.

With bytes as the base, the first 256 ids are the byte values and merge k gets id 256 plus k. The cost of one step is linear in the corpus as a list of symbol sequences, and the sequences shrink as merges land, so a million words to ten thousand ids runs in seconds.

What you ship.

The merge table and the special-token table. The vocabulary of byte strings can be rebuilt from them.

Plausible wrong answers.

  • "BPE picks the pair that makes the most meaningful piece." It picks the most frequent pair; meaning is a side effect, and the likelihood-based variant is a different algorithm.
  • "The vocabulary is the artifact; the merge list can be discarded." Encoding needs the merges in order; the vocabulary alone does not say how to split new text.
  • "All merges are chosen at once from the initial pair counts." Each merge changes the counts, so the loop recounts after every step.

Follow-ups an interviewer may ask.

  • (level 1) Why weight pairs by word frequency instead of counting each distinct word once? Expected: the merges should serve the text the model will see, and common words appear many times.
  • (level 2) Why must a tie in pair counts be broken deterministically? Expected: two training runs on the same corpus must produce the same table, or the same text would get different ids.
  • (level 2) What happens to the encoded length of a sentence as the target vocabulary grows from 300 to 600? Expected: it falls, because more merges cover longer pieces; that curve is the compression curve.
  • (level 3) Why split the corpus into words before you count pairs? Expected: without it, merges cross word boundaries and the vocabulary fills with whole phrases that do not generalize.

Weigh a trade-offThree subword algorithms dominate: byte-pair encoding, WordPiece and Unigram. Contrast how each builds its vocabulary, tell me which one can give two different segmentations of the same word on purpose, and name the libraries you would reach for.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Byte-pair encoding merges the most frequent adjacent pair, bottom up. WordPiece also merges bottom up but scores a pair by the count of the merged piece over the product of the counts of its parts, so it prefers pairs that co-occur more than chance, and it marks continuation pieces with a double-hash prefix. Unigram works top down: it starts from a large candidate set, assigns each piece a probability, and prunes the pieces whose removal hurts the corpus likelihood least, which is why it can also sample alternative segmentations for regularization.

The criteria side by side.

BPE merge criterion:        count(A, B)
WordPiece merge criterion:  count(AB) / (count(A) * count(B))
Unigram:                    prune the piece whose removal least lowers the corpus log-likelihood

The first asks which pair appears most. The second asks which pair appears together more often than you would expect from its parts. The third asks which pieces the corpus can best do without.

Who uses what.

Algorithm Direction Marker Used by
Byte-pair encoding merge up leading space kept on word-initial pieces most decoder families, with vocabularies of 50,257, 128,256 and more
WordPiece merge up by likelihood ratio ## for continuation pieces the classic encoder with 30,522 tokens
Unigram prune down ▁ for a space when trained without pre-tokenization an encoder-decoder family with 32,000 tokens

Sampling segmentations.

A Unigram model is probabilistic at inference. It can return the most likely segmentation or sample another one, which gives subword regularization during training: the same word arrives in several forms and the model learns pieces more robustly. The merge-based algorithms are deterministic.

Libraries.

One library trains vocabularies for either the merge or the prune algorithm directly on raw text, encoding the space as a visible symbol and needing no pre-tokenization, which is why it is the default for multilingual work. A second, Rust-backed encoder is fast and matches the vocabularies of a widely used API family, but it only encodes. A third library trains and serves both algorithms in one place.

Picking.

Training a monolingual model: byte-pair encoding. Training multilingual: Unigram with a character coverage near 0.9995. Serving against an existing API vocabulary: the encoder-only library. Edge inference with a small model: Unigram with a smaller vocabulary.

Plausible wrong answers.

  • "WordPiece and byte-pair encoding give the same vocabulary on the same corpus." The criteria differ, so the merges differ; the likelihood ratio favors surprising pairs over merely frequent ones.
  • "Unigram is deterministic like the merge algorithms." It is probabilistic and can sample segmentations on purpose.
  • "The library that encodes the space as a symbol is itself an algorithm." It is a library that trains either the merge or the prune algorithm on raw text.

Explain the mechanismAt encode time a BPE tokenizer holds the complete merge table. Why does it have to replay the merges in the order they were learned, and what goes wrong when two merges could fire at the same spot?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Encoding must reproduce what training did to the same text, and training saw the merges one at a time in that order. If merge one created "th" and merge five created "the" from "th" plus "e", then "the" can only form after "th" exists. When two merges could apply at one position, the one with the lower rank, learned earlier, wins; change that rule and the same text yields different ids, so the model sees a distribution of ids it was never trained on.

The naive encoder.

def encode_bpe(word, merges):
    symbols = list(word) + ["</w>"]
    for a, b in merges:
        i = 0
        while i < len(symbols) - 1:
            if symbols[i] == a and symbols[i + 1] == b:
                symbols = symbols[:i] + [a + b] + symbols[i + 2:]
            else:
                i += 1
    return symbols

It walks the whole table for every word, so the cost is the word length times the number of merges. Correct for a merge table trained on characters, and slow.

The rank-based encoder.

The capstone version starts from the byte split and repeats: find the applicable merge with the lowest rank anywhere in the current sequence, apply it, and scan again, until no merge in the table applies. Production encoders keep the same semantics with a rank lookup and a priority queue of candidate pairs, which runs in close to linear time.

Why the rule is the contract.

The training loop and the encoder share the merge table, and that sharing is the whole contract. Training merged the most frequent pair first, so an input that contains both halves of an early merge was always merged that way in the training data. An encoder that prefers a later merge, or the longest piece, produces a segmentation the model never saw. Nothing crashes; the ids are simply different.

What special tokens do here.

Reserved strings such as the end-of-text marker are matched exactly before the merge loop runs and mapped to fixed ids. They never take part in a merge, so no table order can split or join them.

Plausible wrong answers.

  • "Greedily take the longest token in the vocabulary that matches." That is a different algorithm and gives a different segmentation from the training run.
  • "Order does not matter because merges commute." A later merge depends on the symbols that earlier merges created, so they do not commute.
  • "Sort the merges by token length." Length is not rank; a long piece may have been learned early and a short one late.

Follow-ups an interviewer may ask.

  • (level 2) Why is the naive loop slow? Expected: it scans the full merge table for every word, so the cost grows with the table size times the word length.
  • (level 3) How do production encoders get close to linear time? Expected: a rank lookup for each adjacent pair and a priority queue that always surfaces the lowest-ranked applicable merge.
  • (level 3) Two tokenizers were trained on different corpora to the same vocabulary size. Do they give the same ids? Expected: no; different corpora give different merge tables and different ranks.
  • (level 3) What test pins the order? Expected: encode a held-out word and compare with recorded ids; the capstone's tests also pin the round trip and the special-token reservation.

Explain the mechanismA customer in Korea reports that the same prompt uses up far more of the context window than the English version, and the bill is higher too. Why does this happen, and what does a model builder do about it?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. The vocabulary was trained on English-heavy text, so its merges cover English and other scripts fall back to short pieces or raw bytes. Korean averages 2 to 3 tokens per word on an older vocabulary, and non-Latin text can cost 5 to 10 times more tokens than English for the same meaning; a Chinese character is 3 bytes in UTF-8, so without merges each character is several tokens. The builder's fix is a larger vocabulary trained on multilingual data, which is why one model family grew its vocabulary from 32K to 128K.

Where the tokens go.

A byte-level tokenizer never fails, but it only compresses what it has merges for. Each Chinese character is 3 bytes, Japanese characters are 3 to 4 bytes, an emoji is 4 bytes and can take 5 tokens. If the training corpus held little of a script, the merge table has few pieces for it, and the text stays close to one token per byte.

What the customer feels.

  • The context window is a token budget, so the same document fits less often.
  • Pricing is per token, so the same request costs more.
  • Latency is per generated token, so answers in that script are slower.

The lesson's phrase is that a user of such a script effectively has a context window half the size of an English user's.

What the builder does.

  1. Train the vocabulary on a corpus that mirrors the target language mix.
  2. Grow the vocabulary so that more merges serve non-Latin scripts; the move from 32K to 128K in one family was made mainly for this.
  3. Train with a library that works on raw text without pre-tokenization, so scripts without spaces segment well.
  4. Measure fertility per language and report it with the model.

How to measure it.

Take the same 10 meaning-aligned sentences in English, Spanish, Chinese, Korean and Arabic, from one parallel corpus, tokenize each with the candidate vocabulary, and compare the average tokens per character. The ratios are the tax; with sentences that do not match, report them as a spot check only.

Plausible wrong answers.

  • "Korean is harder for the model to understand." The model sees ids; the extra cost comes from the tokenizer's merges, not from the language.
  • "Use a character-level tokenizer for Korean." Characters make every sequence longer; the fix is merges that cover the script.
  • "The model has a smaller context window for Korean." The window is the same number of tokens; the tokenizer spends more of them per word.

Read the codeTwo versions of a byte-level tokenizer's decode function came in for review. vocab maps each id to a bytes object. python def decode_a(self, ids): byte_sequence = b"".join(self.vocab[t] for t in ids) return byte_sequence.decode("utf-8", errors="replace") def decode_b(self, ids): return "".join(self.vocab[t].decode("utf-8") for t in ids) Both pass the English tests. Which one is correct for an emoji whose bytes were split across two tokens, why does the correct one always terminate, and what is errors="replace" for?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Join all the bytes first and decode once, which is what decode_a does. A multi-byte character such as an emoji, 4 bytes in UTF-8, can be split across two or more tokens, so decoding each token's bytes alone hits an incomplete sequence and raises or emits replacement characters. The join works because every id is either one of the 256 raw bytes or the concatenation of two earlier ids, so expanding ids to bytes always ends in raw bytes, and the full byte string is valid UTF-8 whenever the input was. The replace option keeps the decoder from raising when a model emits a partial character at the end of a stream.

Why the split happens.

A byte-level vocabulary starts from single bytes and learns merges from the corpus. An emoji that was rare in training may have no merge covering all 4 of its bytes, so the encoder leaves it as two tokens, perhaps 3 bytes and 1 byte. Each token on its own is not valid UTF-8. The characters of a script with 3-byte characters have the same problem whenever a merge covers part of a character.

Why the join terminates and round-trips.

The capstone states the guarantee: encode then decode returns the input bytes exactly. The decoder concatenates the byte expansion of every id in order. Because every id is a raw byte or the concatenation of two known ids, the recursive expansion bottoms out in raw bytes, and the concatenation of all tokens is the original byte string. UTF-8 decoding then recovers the text. The test suite pins the property on an unseen sentence, on a sentence with an emoji, and on a sentence that contains a literal special-token string.

Special tokens on the way out.

The capstone's decoder checks a special-token table first and appends the marker's UTF-8 bytes, then falls through to the vocabulary, and raises on an id that is in neither. That keeps a reserved id from being looked up as a merge.

What errors="replace" is for.

A model can stop in the middle of a character, or a stream can be cut between two tokens that share a character. Strict decoding raises; replace emits a replacement character and continues. In a streaming decoder the better pattern is to buffer the trailing bytes until they form a complete character, and to use replace only at the final flush.

Plausible wrong answers.

  • "Decode each token to a string and join the strings." A token can hold part of a character, and partial UTF-8 is not a string.
  • "Tell the decoder to ignore errors so nothing ever raises." Ignoring drops bytes silently and the round trip is no longer exact; the replacement character at least marks the loss.
  • "The round trip only matters for the training data." Every generated answer goes through decode, and a server that raises on an emoji drops the request.

Follow-ups an interviewer may ask.

  • (level 2) Why does decode_b pass the English tests? Expected: ASCII characters are single bytes, so no token ever holds a partial character and every piece decodes on its own.
  • (level 3) Design the streaming decoder in two sentences. Expected: accumulate bytes and emit only the longest prefix that is complete UTF-8, keeping the remainder; flush with replacement at the end of the stream.
  • (level 3) Why can a word-level tokenizer not give the round-trip guarantee? Expected: unseen words map to an unknown id, and the unknown id cannot be mapped back to the original text.
  • (level 3) What three inputs does the capstone's test suite use for the round trip? Expected: an unseen sentence, a sentence with an emoji, and a sentence containing the literal special-token string.

Explain the mechanismWhy does every current language model read subword tokens instead of whole words or single characters, and why do most of them build the vocabulary on top of raw bytes?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. A word vocabulary cannot hold every word, so each new word becomes an unknown token and the model loses the signal. Characters never fail, but they make sequences several times longer and spend attention on spelling. Subwords keep common words whole and split rare words into meaningful pieces, and starting from the 256 byte values means any input in any script encodes with zero unknown tokens.

The three options.

Level Vocabulary Failure
Word huge, and still incomplete unknown token for anything unseen; English alone has over a million word forms
Character a few hundred a 10-word sentence becomes about 50 tokens; the model relearns that t, h, e spell a word
Subword 30K to 128K none of the above; rare words split into pieces

A rare word such as "unhappiness" is 11 character tokens or 3 subword pieces: un, happi, ness. The pieces carry meaning the model can reuse.

Why bytes at the bottom.

A byte-level vocabulary treats each of the 256 byte values as a base token and learns merges on top. Any string in any encoding is a byte sequence, so nothing is ever unknown, and no language needs special handling. A well-known 50,257-token vocabulary is exactly 256 bytes plus 50,000 merges plus one special token.

Why it is architecture, not preprocessing.

The tokenizer fixes what the model sees for its whole life. A vocabulary that splits a common word into four pieces wastes context and compute on every request, and the choice cannot be undone after training. Pricing is per token and latency is per token, so the tokenizer sits in the cost model too.

Plausible wrong answers.

  • "Characters are the safest choice because nothing is ever unknown." Bytes give the same guarantee, and characters make every sequence several times longer.
  • "A bigger word list solves the unknown problem." New words, misspellings, code and other languages keep appearing; no word list is complete.
  • "A token is a word." A token can be a byte, a piece of a word, a word, or a short phrase, depending on the merges.

Follow-ups an interviewer may ask.

  • (level 1) What does fertility measure? Expected: the average number of tokens per word; 1.0 is one token per word and higher means the model works harder for the same text.
  • (level 2) Why does the unknown token disappear with byte-level vocabularies? Expected: every byte is itself a token, so any input decomposes into known tokens before any merge applies.
  • (level 2) What does a tiny vocabulary cost at inference? Expected: longer sequences, so more forward passes per answer and less text per context window.
  • (level 3) Why can you not fix a bad tokenizer after training? Expected: the embedding rows and every weight were trained against those ids; new ids have no learned meaning and old text would map differently.

Small vocabulary (e.g., character-level) means every word is many tokens, increasing sequence length and computation. Large vocabulary wastes parameters on tokens that rarely appear in training data. Most LLMs use 32K-100K tokens.

Q4What problem does byte-level fallback solve in tokenization?

With byte-level fallback, the tokenizer can fall back to raw byte values (256 possible) for any character not in the vocabulary. This guarantees complete coverage -- no input is ever 'unknown.'

Q5How does the tokenizer affect non-English language performance in LLMs?

BPE merges are learned from training data. If Japanese text is 5% of the corpus, Japanese characters get fewer merges, requiring 2-5x more tokens per word than English. This effectively shrinks the context window for non-English text.
