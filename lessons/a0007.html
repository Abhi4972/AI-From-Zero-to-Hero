Terms you'll hear
Term What people say What it actually means

The problem

In plain words first

A Docker image is a frozen copy of everything your code needs: an operating system's files, Python, CUDA libraries, your packages. A container is that image running as an isolated process on your machine. Anyone who runs the same image gets the same environment, down to the system libraries, which a virtual environment alone cannot promise.

You trained a model on your laptop with PyTorch 2.3, CUDA 12.4, and Python 3.12. Your colleague has PyTorch 2.1, CUDA 11.8, and Python 3.10. Your model crashes on their machine. Your Dockerfile works on both.

AI projects are dependency nightmares. A typical stack includes Python, PyTorch, CUDA drivers, cuDNN, system-level C libraries, and specialized packages like flash-attn that need exact compiler versions. Docker packages all of this into a single image that runs identically everywhere.

The idea

Docker wraps your code, runtime, libraries, and system tools into an isolated unit called a container. Think of it as a lightweight virtual machine, except it shares the host OS kernel instead of running its own, so it starts in seconds instead of minutes.

The same idea as a formula

An image is a stack of layers, one per FROM, RUN, COPY or ADD line. Docker caches each layer under a key computed from the key of the layer below it, the instruction itself and, for COPY, the contents of the copied files:

ki​=H(ki−1​, instructioni​, inputsi​)

Because ki​ contains ki−1​, a change at layer j changes every key from j upward. If layer i takes ti​ seconds to build, an edit that touches layer j costs

rebuild time=i≥j∑​ti​

So put slow layers that rarely change (system packages, pip install) near the bottom and fast layers that change often (your code) at the top.

Image size. The image is the sum of its layers. Deleting a file in a later layer hides it but does not shrink the image; remove temporary files in the same RUN line that created them.

Worked example
Ordering a Dockerfile by hand

Installing the requirements takes 4 minutes; copying the code takes 1 second.

  • Code first (COPY . /app, then RUN pip install): editing one line of code changes the inputs of the COPY layer, so the pip install above it in the stack reruns. Every code edit costs about 4 minutes.
  • Requirements first (COPY requirements.txt, RUN pip install, then COPY . /app): a code edit changes only the last COPY. Rebuild: about 1 second. Only editing requirements.txt costs the 4 minutes.
See it drawn
Docker's cache, simulated

The key rule of the formula box in ten lines of Python, applied to the two orderings of the worked example. The script builds each Dockerfile once, edits the app code, and lists the layers whose key changed.

import hashlib
# Docker caches each layer under a key that depends on its parent's key and its own instruction and inputs.
def build(steps, cache):
    key, rebuilt = "", []
    for instr, inputs in steps:
        key = hashlib.sha256((key + instr + inputs).encode()).hexdigest()[:12]
        if key not in cache:
            rebuilt.append(instr.split()[0] + " " + instr.split()[1][:18]); cache.add(key)
    return rebuilt
bad = [("FROM python:3.12-slim", ""), ("COPY . /app", "code-v1+reqs-v1"), ("RUN pip install -r requirements.txt", ""), ("CMD python app.py", "")]
good = [("FROM python:3.12-slim", ""), ("COPY requirements.txt /app/", "reqs-v1"), ("RUN pip install -r requirements.txt", ""),
        ("COPY . /app", "code-v1"), ("CMD python app.py", "")]
for name, steps in [("code copied first", bad), ("requirements first", good)]:
    cache = set(); build(steps, cache)
    edited = [(i, s.replace("code-v1", "code-v2")) for i, s in steps]   # you edit one line of app code
    print(f"{name:20s} rebuild after a code edit: {build(edited, cache)}")
What you should see
code copied first    rebuild after a code edit: ['COPY .', 'RUN pip', 'CMD python']
requirements first   rebuild after a code edit: ['COPY .', 'CMD python']
Reading this output

With the code copied first, the edit invalidates the COPY layer and therefore pip install above it: the slow layer reruns on every change. With the requirements copied first, the pip install key depends only on requirements.txt, which did not change, so it comes from the cache, and only the cheap layers rebuild. Docker's real keys work this way, which is why every production Dockerfile in this lesson copies the requirements before the code.

Check your mental model
  • ✗ "A container is a virtual machine."
    ✓ A VM runs its own operating system kernel. A container is an ordinary process on the host's kernel with its own view of files and network, which is why it starts in a second.
  • ✗ "The image contains the GPU driver."
    ✓ The driver stays on the host. The image carries the CUDA toolkit (the libraries); the NVIDIA Container Toolkit lets the container use the host's driver. The toolkit in the image must not be newer than the driver supports.
  • ✗ "Files I write inside a container are kept."
    ✓ They live in the container's own layer, which disappears with docker run --rm or when the container is removed. Anything worth keeping goes in a mounted volume.

Idea 1 · Why AI projects need Docker more than most

  1. GPU drivers are fragile. CUDA 12.4 code does not run on CUDA 11.8. Docker isolates the CUDA toolkit inside the container while sharing the host GPU driver through the NVIDIA Container Toolkit.

  2. Model weights are large. A 7B parameter model is 14 GB in fp16. You do not want to re-download it every time you rebuild. Docker volumes let you mount a models directory from the host.

  3. Multi-service architectures are common. A real AI application is not just a Python script. It is an inference server, a vector database for RAG, maybe a web frontend. Docker Compose orchestrates all of these with one command.

Idea 3 · Common container patterns in AI

Dev Container
  Full toolkit. Editor support. Jupyter. Debugging tools.
  Used during development and experimentation.

Training Container
  Minimal. Just the training script and dependencies.
  Runs on GPU clusters. No editor, no Jupyter.

Inference Container
  Optimized for serving. Small image. Fast cold start.
  Runs behind a load balancer in production.

Step 2 · Install NVIDIA Container Toolkit (Linux with NVIDIA GPU)

This lets Docker containers access your GPU. macOS and Windows (WSL2) users can skip this; Docker Desktop handles GPU passthrough differently on those platforms.

distribution=$(. /etc/os-release;echo $ID$VERSION_ID)
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
curl -s -L https://nvidia.github.io/libnvidia-container/$distribution/libnvidia-container.list | \
    sed 's#deb https://#deb [signed-by=/usr/share/keyrings/nvidia-container-toolkit-keyring.gpg] https://#g' | \
    sudo tee /etc/apt/sources.list.d/nvidia-container-toolkit.list

sudo apt-get update
sudo apt-get install -y nvidia-container-toolkit
sudo nvidia-ctk runtime configure --runtime=docker
sudo systemctl restart docker

Test GPU access inside a container:

docker run --rm --gpus all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi

If you see your GPU info, the toolkit is working.

Step 3 · Understand base images

Choosing the right base image saves hours of debugging.

nvidia/cuda:12.4.1-devel-ubuntu22.04
  Full CUDA toolkit. Compilers included.
  Use for: building packages that need nvcc (flash-attn, bitsandbytes)
  Size: ~4 GB

nvidia/cuda:12.4.1-runtime-ubuntu22.04
  CUDA runtime only. No compilers.
  Use for: running pre-built code
  Size: ~1.5 GB

pytorch/pytorch:2.6.0-cuda12.4-cudnn9-runtime
  PyTorch pre-installed on top of CUDA.
  Use for: skipping the PyTorch install step
  Size: ~6 GB

python:3.12-slim
  No CUDA. CPU only.
  Use for: inference on CPU, lightweight tools
  Size: ~150 MB

Predict before you read on

Step 4 · Write a Dockerfile for AI development

Here is the Dockerfile in code/Dockerfile. Walk through it:

FROM --platform=linux/amd64 nvidia/cuda:12.4.1-devel-ubuntu22.04

ENV DEBIAN_FRONTEND=noninteractive
ENV PYTHONUNBUFFERED=1

RUN apt-get update && apt-get install -y --no-install-recommends \
    software-properties-common \
    git \
    curl \
    build-essential \
    && add-apt-repository -y ppa:deadsnakes/ppa \
    && apt-get update && apt-get install -y --no-install-recommends \
    python3.12 \
    python3.12-venv \
    python3.12-dev \
    && rm -rf /var/lib/apt/lists/*

RUN update-alternatives --install /usr/bin/python python /usr/bin/python3.12 1

RUN curl -sSL https://raw.githubusercontent.com/pypa/get-pip/3b73145063be545b649ad9ca83ea8da5fc915a4f/public/get-pip.py -o /tmp/get-pip.py \
    && echo "a341e1a43e38001c551a1508a73ff23636a11970b61d901d9a1cad2a18f57055  /tmp/get-pip.py" | sha256sum -c - \
    && python /tmp/get-pip.py \
    && rm /tmp/get-pip.py \
    && update-alternatives --install /usr/bin/pip pip /usr/local/bin/pip3.12 1

RUN python -m pip install --no-cache-dir --upgrade pip setuptools wheel

RUN python -m pip install --no-cache-dir \
    torch==2.6.0+cu124 \
    torchvision==0.21.0+cu124 \
    torchaudio==2.6.0+cu124 \
    --index-url https://download.pytorch.org/whl/cu124

RUN python -m pip install --no-cache-dir \
    numpy \
    pandas \
    scikit-learn \
    matplotlib \
    jupyter \
    transformers \
    datasets \
    accelerate \
    safetensors

WORKDIR /workspace

VOLUME ["/workspace", "/models"]

EXPOSE 8888

CMD ["python"]

Build it:

docker build -t ai-dev -f phases/00-setup-and-tooling/07-docker-for-ai/code/Dockerfile .

This takes a while the first time (downloading CUDA base image + PyTorch). Subsequent builds use cached layers.

macOS / Apple Silicon (M1/M2/M3/M4): The --platform=linux/amd64 on the FROM line is what makes this build succeed on a Mac. The CUDA base image also ships an arm64 variant and Docker Desktop picks it automatically on Apple Silicon, but PyTorch publishes its cu124 wheels for x86_64 only, so the pip install torch==2.6.0+cu124 layer fails with No matching distribution found for torch==2.6.0+cu124. Pinning the platform pulls the x86_64 image and runs it under emulation: the build is slower and the container has no GPU (there is no CUDA on a Mac either way). Drop --gpus all from the docker run commands below on a Mac. For GPU work on Apple Silicon, run the lessons natively with the MPS build from Lesson 0.3 and keep this image for x86_64 Linux hosts with an NVIDIA GPU.

Run it:

docker run --rm -it --gpus all \
    -v $(pwd):/workspace \
    -v ~/models:/models \
    ai-dev python -c "import torch; print(f'PyTorch {torch.__version__}, CUDA: {torch.cuda.is_available()}')"

Run Jupyter inside the container:

docker run --rm -it --gpus all \
    -v $(pwd):/workspace \
    -v ~/models:/models \
    -p 8888:8888 \
    ai-dev jupyter notebook --ip=0.0.0.0 --port=8888 --no-browser --allow-root
Why this came about
Why the order of lines matters

Each instruction makes a layer, and Docker reuses a cached layer only if that instruction and every one above it are unchanged. So the rule is: rarely changing, slow steps first (system packages, CUDA, PyTorch), frequently changing things last (your code). The lesson's Dockerfile follows it: it never copies the project in at all, and mounts it at run time with -v $(pwd):/workspace instead.

Step 5 · Volume mounts for data and models

Volume mounts are critical for AI work. Without them, your 14 GB model downloads vanish when the container stops.

# Mount your code
-v $(pwd):/workspace

# Mount a shared models directory
-v ~/models:/models

# Mount datasets
-v ~/datasets:/data

Inside your training script, load from the mounted path:

from transformers import AutoModel

model = AutoModel.from_pretrained("/models/llama-7b")

The model lives on your host filesystem. Rebuild the container as often as you want without re-downloading.

Break it on purpose

Run the image without the -v ~/models:/models mount, download a small model into /models inside the container, exit, and start a new container from the same image. Is the model still there? Now repeat with the mount. (Solution B1.)

Step 6 · Docker Compose for multi-service AI apps

A real RAG application needs an inference server and a vector database. Docker Compose runs both with one command.

See code/docker-compose.yml:

services:
  ai-dev:
    build:
      context: .
      dockerfile: Dockerfile
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    volumes:
      - ../../../:/workspace
      - ~/models:/models
      - ~/datasets:/data
    ports:
      - "8888:8888"
    stdin_open: true
    tty: true
    command: jupyter notebook --ip=0.0.0.0 --port=8888 --no-browser --allow-root

  qdrant:
    image: qdrant/qdrant:v1.12.5
    ports:
      - "6333:6333"
      - "6334:6334"
    volumes:
      - qdrant_data:/qdrant/storage

volumes:
  qdrant_data:

Start everything:

cd phases/00-setup-and-tooling/07-docker-for-ai/code
docker compose up -d

Now your AI dev container can reach the vector database at http://qdrant:6333 by service name. Docker Compose creates a shared network automatically.

Test the connection from inside the AI container:

from qdrant_client import QdrantClient

client = QdrantClient(host="qdrant", port=6333)
print(client.get_collections())

Stop everything:

docker compose down

Add -v to also delete the qdrant volume:

docker compose down -v
Reading this output

docker compose up -d prints one line per service as it is created and started, then returns: -d runs them in the background. docker compose ps shows each service's state and ports. Inside the network Compose creates, each service is reachable by its name (qdrant), not by localhost: localhost inside the AI container means that container itself.

Step 7 · Useful Docker commands for AI work

# List running containers

# View container logs
docker logs -f <container_id>
Recap
What to keep from this lesson
  • An image is a frozen environment; a container is a running copy of it on the host kernel.
  • Order Dockerfile lines from slow and stable to fast and changing, so the cache does the work.
  • Models, datasets and code belong in mounted volumes; the container's own files are disposable.
  • GPUs need the NVIDIA Container Toolkit and --gpus all; the host driver must support the image's CUDA version.
  • Compose runs several services on one network where they find each other by service name.

Solutions

SolutionP1 · A cache thrown away

Everything from the COPY line down: the PyTorch install, the library install, and every later layer. Editing a file changes the COPY layer, which invalidates every layer after it, so a one-line change costs a multi-gigabyte reinstall. Move COPY to the end (or mount the code as a volume) and the same edit rebuilds in seconds.

SolutionB1 · A disappearing model

Without the mount the model is gone: it was written into the container's writable layer, and a new container starts again from the image. With -v ~/models:/models the files are written to ~/models on your host, so every new container sees them and nothing is downloaded twice.

Use it: the same idea with real libraries

You now have a reproducible AI development environment. For the rest of this course:

  • Use docker compose up to start your dev environment and vector database together
  • Mount your code, models, and data as volumes so nothing is lost between rebuilds
  • When a lesson requires a new Python package, add it to the Dockerfile and rebuild
  • Share your Dockerfile with teammates. They get the exact same environment.

No GPU?

Remove the --gpus all flag and the NVIDIA deploy block. The container still works for CPU-based lessons. PyTorch detects the absence of CUDA and falls back to CPU automatically.

Industry practice
What's current (2024–2026)
  • GPUs in containers. The NVIDIA Container Toolkit (--gpus all, or CDI device names) exposes the host driver to containers; images carry the CUDA user-space libraries, so one image runs on any host with a new enough driver.
  • Official inference images. vLLM, SGLang, Hugging Face TGI and NVIDIA NIM and NGC publish ready images; most production LLM serving starts from one of them rather than a hand-built Dockerfile.
  • Smaller, safer images. Multi-stage builds, uv inside the image for fast installs, non-root users and image scanning (Docker Scout, Trivy) are standard practice; Kubernetes with the NVIDIA GPU Operator runs these images at scale.

Sources: NVIDIA Container Toolkit, vLLM Docker, uv in Docker, NVIDIA GPU Operator.
