In plain words first
The idea in one line

Word2Vec gave you a vector per word. Modern embedding models give you a vector per passage, cross-lingual, with sparse, dense, and multi-vector views, sized to fit your index. Pick wrong and your RAG retrieves the wrong thing.

The problem

In plain words first

An embedding model turns a piece of text into a list of numbers, a vector, so that texts with similar meaning get nearby vectors. Search, RAG, clustering and deduplication all rest on it, and swapping one embedding model for another often changes results more than anything else in the pipeline. There are three shapes of embedding. Dense: one vector per passage. Sparse: a weight for each vocabulary word, like a learned BM25. Multi-vector: one vector per token, compared token by token. There are also practical knobs: how many numbers to keep, at what precision, and whether queries need a special prefix. This lesson explains each shape and the Matryoshka trick for shrinkable vectors, then measures on a real retrieval benchmark what a query prefix, truncation, 1-bit quantization and token-level scoring actually do.

Your RAG system retrieves the wrong passage 40% of the time. The culprit is rarely the vector database or the prompt. It is the embedding model.

Choosing an embedding in 2026 means picking across five axes:

  1. Dense vs sparse vs multi-vector. One vector per passage, or one per token, or a sparse weighted bag of words.
  2. Language coverage. Monolingual English models still win on English-only tasks. Multilingual models win when corpora are mixed.
  3. Context length. 512 tokens vs 8,192 vs 32,768, and quality often degrades well before the advertised maximum, so test with your real document lengths.
  4. Dimension budget. 3,072 floats at full precision = 12 KB per vector, so 100M vectors take about 1.2 TB before any index overhead. Matryoshka truncation to 768 dimensions cuts this 4×, and int8 or binary quantization cuts it a further 4× or 32×.
  5. Open vs hosted. Open-weight means you control the stack and data. Hosted means you trade control for always-latest.

This lesson names the tradeoffs so you can pick on evidence, not on whatever was popular last quarter.

The idea

Dense embeddings. One vector per passage (usually 384-3,072 dimensions). Cosine similarity ranks passages by semantic proximity. OpenAI text-embedding-3-large, BGE-M3 dense mode, Voyage-3. Default choice.

Sparse embeddings. SPLADE-style. A transformer predicts a weight for every vocab token, then zeros out most of them. Result is a sparse vector of size |vocab|. Captures lexical matching (like BM25) but with learned term weights. Strong on keyword-heavy queries.

Multi-vector (late interaction). ColBERTv2, Jina-ColBERT. One vector per token. Scoring with MaxSim: for each query token, find the most similar document token, sum the scores. More expensive to store and score, but wins on long queries and domain-specific corpora.

BGE-M3: all three at once. Single model outputs dense, sparse, and multi-vector representations simultaneously. Each can be queried independently; scores fuse via weighted sum. The 2026 default when you want flexibility from one checkpoint.

Matryoshka Representation Learning. Trained so the first N dimensions of the vector form a useful standalone embedding. Truncate a 1,536-dim vector to 256 dims and lose only a little accuracy for 6× less storage (OpenAI reported that text-embedding-3-large cut to 256 dimensions still beat its previous full-size model). Supported by OpenAI text-embedding-3, Cohere embed v4, Voyage 4, Jina embeddings v3 and v4, Gemini Embedding, Nomic Embed v1.5 and later.

The same idea as a formula

Dense. One vector per text, q,d∈Rk, normalised to length 1, scored by cosine s(q,d)=q⊤d. Trained contrastively (InfoNCE): for a query qi​ with its relevant passage di+​ and the other passages in the batch as negatives,

L=−log∑j​exp(qi⊤​dj​/τ)exp(qi⊤​di+​/τ)​

Sparse (SPLADE). For each input token j and vocabulary word w, the masked-LM head gives a logit zj,w​; the document's weight for w is ww​=maxj​log(1+ReLU(zj,w​)), pushed towards zero for most words by a sparsity penalty. The score is ∑w​ww​(q)ww​(d): lexical matching with learned weights and learned expansion terms.

Multi-vector (ColBERT). One unit vector per token, q1​..qm​ and d1​..dn​; each query token finds its best-matching document token:

s(q,d)=i=1∑m​jmax​qi⊤​dj​(MaxSim)

Storage grows with document length (n vectors instead of 1), which is why it is used for reranking or with heavy compression.

Matryoshka representation learning (Kusupati et al., 2022) trains the same embedding at several prefix lengths at once, LMRL​=∑m∈{64,128,256,…,k}​cm​L(q1:m​,d1:m​), so the first m coordinates are a good embedding on their own. A model trained without it spreads information across all coordinates, and truncation removes some of it.

Quantization. int8 stores each coordinate in one byte (4× smaller than float32). Binary keeps only the sign, b=sign(q), 32× smaller, with similarity by Hamming distance; a common recipe retrieves candidates with bits and rescores them with full vectors.

Worked example
MaxSim versus one pooled vector

Query tokens "apple" =(1,0) and "price" =(0,1). Document A has tokens (1,0) "apple", (0.6,0.8) "cost"; document B has one token (0.7,0.7) "fruit-market" (unit-ish vectors, rounded).

  • MaxSim A: "apple" best match 1.0; "price" best match max(0,0.8)=0.8; total 1.8.
  • MaxSim B: "apple" 0.7; "price" 0.7; total 1.4. A wins: it covers both query aspects separately.
  • Mean-pooled dense: query (0.5,0.5), A (0.8,0.4), B (0.7,0.7). Cosines: A =0.6/(0.707×0.894)=0.95; B =0.7/(0.707×0.99)=1.0. B wins.

Pooling blurs which query word each part of the document answers; MaxSim keeps that alignment, which is why late interaction helps on multi-aspect queries.

Idea 1 · The MTEB leaderboard tells a partial story

Massive Text Embedding Benchmark — 56 tasks across 8 task types at launch (2022), expanded to 100+ tasks in MTEB v2. The top of the leaderboard changes every few months; in 2025-2026 it has been held by large proprietary models (Gemini Embedding and its multimodal successor Gemini Embedding 2, among others) and large open ones (Qwen3-Embedding), with smaller open models such as the BGE family far down the list but much cheaper to run. The leaderboard is necessary but not sufficient — always benchmark on your domain.

Idea 2 · The three-tier pattern

Use case Pattern
Fast first-pass Dense bi-encoder (BGE-M3, text-3-small)
Recall boost Sparse (SPLADE, BGE-M3 sparse) + RRF fuse
Precision on top-50 Multi-vector (ColBERTv2) or cross-encoder reranker

Most production stacks use all three.

Step 1 · baseline — dense embeddings with Sentence-BERT

from sentence_transformers import SentenceTransformer
import numpy as np

encoder = SentenceTransformer("BAAI/bge-small-en-v1.5")
corpus = [
    "The first iPhone launched in 2007.",
    "Apple released the iPod in 2001.",
    "Android is an operating system from Google.",
]
emb = encoder.encode(corpus, normalize_embeddings=True)

query = "When was the iPhone released?"
q_emb = encoder.encode([query], normalize_embeddings=True)[0]
scores = emb @ q_emb
print(sorted(enumerate(scores), key=lambda x: -x[1]))
What you should see
[(0, np.float32(0.7717176)), (1, np.float32(0.75377905)), (2, np.float32(0.53911066))]

normalize_embeddings=True makes the dot product equal cosine similarity. Always set it.

Step 2 · Matryoshka truncation

def truncate(vectors, dim):
    out = vectors[:, :dim]
    return out / np.linalg.norm(out, axis=1, keepdims=True)

emb_256 = truncate(emb, 256)
emb_128 = truncate(emb, 128)

Re-normalize after truncation. Nomic v1.5, OpenAI text-3, and Voyage-4 are trained so this is lossless for the first few levels. Non-Matryoshka models (original Sentence-BERT) degrade sharply when truncated.

import random, time
import pyarrow.parquet as pq
import matplotlib.pyplot as plt
from huggingface_hub import hf_hub_download
get = lambda repo, f, rev=None: pq.read_table(hf_hub_download(repo, f, repo_type="dataset", revision=rev)).to_pylist()
docs = {d["_id"]: d["title"] + ". " + d["text"] for d in get("BeIR/scifact", "corpus/corpus-00000-of-00001.parquet")}
queries = {q["_id"]: q["text"] for q in get("BeIR/scifact", "queries/queries-00000-of-00001.parquet")}
qrels = {}
for r in get("BeIR/scifact-qrels", "default/test/0000.parquet", "refs/convert/parquet"):
    qrels.setdefault(str(r["query-id"]), set()).add(str(r["corpus-id"]))
relevant = sorted({d for s in qrels.values() for d in s})
others = random.Random(0).sample(sorted(set(docs) - set(relevant)), 1200)
doc_ids = relevant + others
corpus_text = [docs[i] for i in doc_ids]
test_q = [(qid, queries[qid]) for qid in sorted(qrels, key=int) if qid in queries]

def ndcg10(S):
    out = []
    for (qid, _), row in zip(test_q, S):
        top = [doc_ids[i] for i in np.argsort(-row)[:10]]
        dcg = sum(1 / np.log2(r + 1) for r, d in enumerate(top, 1) if d in qrels[qid])
        out.append(dcg / sum(1 / np.log2(r + 1) for r in range(1, min(len(qrels[qid]), 10) + 1)))
    return float(np.mean(out))

start = time.time()
models = {"MiniLM-L6": SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2"), "bge-small": encoder}
D = {n: m.encode(corpus_text, normalize_embeddings=True, batch_size=32) for n, m in models.items()}
Q = {n: m.encode([q for _, q in test_q], normalize_embeddings=True) for n, m in models.items()}
PREFIX = "Represent this sentence for searching relevant passages: "
Q["bge-small + prefix"] = encoder.encode([PREFIX + q for _, q in test_q], normalize_embeddings=True)
D["bge-small + prefix"] = D["bge-small"]
print(f"{len(corpus_text):,} documents, {len(test_q)} queries, encoded in {time.time() - start:.0f} s")
for n in Q:
    print(f"   {n:20s} nDCG@10 {ndcg10(Q[n] @ D[n].T):.3f}")

dims = [384, 256, 128, 64, 32]
curves = {n: [ndcg10(truncate(Q[n], k) @ truncate(D[n], k).T) for k in dims] for n in ("MiniLM-L6", "bge-small + prefix")}
bits = {}
for n in ("MiniLM-L6", "bge-small + prefix"):
    qb, db = np.where(Q[n] > 0, 1, -1), np.where(D[n] > 0, 1, -1)
    S_bin = qb @ db.T                                        # = d - 2 * Hamming distance
    S_rescored = np.full_like(S_bin, -1e9, dtype=float)
    for i, row in enumerate(S_bin):
        cand = np.argsort(-row)[:50]
        S_rescored[i, cand] = Q[n][i] @ D[n][cand].T
    bits[n] = (ndcg10(S_bin), ndcg10(S_rescored))
    print(f"{n:20s} truncated to {dims}: " + " ".join(f"{v:.3f}" for v in curves[n]))
    print(f"{'':20s} 1-bit (48 bytes per vector): {bits[n][0]:.3f};  1-bit top-50 rescored with floats: {bits[n][1]:.3f}")

fig, ax = plt.subplots(figsize=(6.5, 3.3))
for (n, c), colour in zip(curves.items(), ("#566070", "#474d9a")):
    ax.plot(dims, c, "o-", color=colour, label=f"{n}, truncated")
    ax.axhline(bits[n][0], color=colour, ls=":", lw=1)
ax.text(300, min(b[0] for b in bits.values()) - 0.02, "dotted: 1 bit per dimension, all 384", fontsize=7.5, color="#566070")
ax.set_xscale("log", base=2); ax.set_xticks(dims, [str(d) for d in dims]); ax.invert_xaxis()
ax.set_xlabel("dimensions kept"); ax.set_ylabel("nDCG@10"); ax.legend(frameon=False, fontsize=8); ax.grid(alpha=0.3)
ax.set_title("Truncating non-Matryoshka embeddings costs more than binarising them", fontsize=9)
plt.tight_layout(); plt.show()

Reading this output

bge-small beats MiniLM clearly (0.819 against 0.755 nDCG@10) at the same 384 dimensions: a newer model trained on retrieval pairs. The prefix result is a useful surprise: for bge-small-en-v1.5 the recommended query prefix lowers the score here (0.805), consistent with BAAI's note that the v1.5 models no longer need it for most retrieval; the original bge models did. The pitfall stands, reversed: check the card for your exact model version, then measure. Truncation hurts both models, gently down to 256 dimensions and then steeply (about 0.61 at 64, 0.43 to 0.45 at 32), because neither was trained Matryoshka-style. Keeping all 384 dimensions as single bits (48 bytes per vector) does better than 64 floats (256 bytes), and rescoring the 50 best bit-matches with the full vectors recovers all of MiniLM's quality and most of bge's.

Multi-vector scoring from token vectors

The idea behind ColBERT, built from bge-small's per-token output vectors: the top 50 documents from dense retrieval are rescored with the MaxSim formula. bge-small was not trained for late interaction, so this shows the mechanism, not ColBERT's quality.

start = time.time()
tok_D = encoder.encode(corpus_text, output_value="token_embeddings", batch_size=32)
tok_Q = encoder.encode([PREFIX + q for _, q in test_q], output_value="token_embeddings")
unit = lambda T: (T / T.norm(dim=1, keepdim=True)).numpy()
tok_D = [unit(t) for t in tok_D]; tok_Q = [unit(t) for t in tok_Q]
dense = Q["bge-small + prefix"] @ D["bge-small + prefix"].T
S_maxsim = np.full_like(dense, -1e9)
for i, qv in enumerate(tok_Q):
    for j in np.argsort(-dense[i])[:50]:
        S_maxsim[i, j] = (qv @ tok_D[j].T).max(axis=1).sum()
print(f"token vectors per document: mean {np.mean([len(t) for t in tok_D]):.0f}; "
      f"storage vs one vector: about {np.mean([len(t) for t in tok_D]):.0f}x  ({time.time() - start:.0f} s)")
print(f"dense nDCG@10 {ndcg10(dense):.3f};  MaxSim rerank of dense top 50: {ndcg10(S_maxsim):.3f}")
What you should see
token vectors per document: mean 329; storage vs one vector: about 329x  (172 s)
dense nDCG@10 0.805;  MaxSim rerank of dense top 50: 0.828
Reading this output

Rescoring with MaxSim over token vectors lifts nDCG@10 from 0.805 to 0.828, even though bge-small was never trained for late interaction: matching each query token to its best document token keeps information that pooling into one vector averages away (the worked example's effect). The cost is the other number: about 329 vectors per document instead of one, which is why ColBERT systems compress token vectors heavily and usually apply MaxSim to a shortlist, as here, rather than to the whole collection.

Industry practice
What's current (2024–2026)
  • Embedding models grew and went multimodal. LLM-based embedders (Qwen3-Embedding, 2025; Gemini Embedding, 2025) lead MTEB, and Gemini Embedding 2 (2026) maps text, images, video and audio into one vector space.
  • Matryoshka and quantization are standard. Most current API and open models support truncated dimensions, and vector databases offer int8 and binary storage with rescoring, the recipe measured above.
  • Multi-vector went practical. ColBERT-style late interaction is now served with heavy compression (PLAID, token pooling) and extends to documents as images (ColPali, 2024), where each page is a grid of patch vectors; Lesson 5.14's reranking stage is where it usually sits.

Sources: Matryoshka Representation Learning, Gemini Embedding 2, Qwen3-Embedding, ColPali.

Pitfalls

  • Same model for query and doc. Some models (Voyage, Jina-ColBERT) use asymmetric encoding — query and document pass through different paths. Always check the model card.
  • Missing prefix. bge-* models need "Represent this sentence for searching relevant passages: " prepended to queries. How much it matters depends on the model and data; the first experiment under "Use it" measures it for bge-small on SciFact.
  • Over-trimming Matryoshka. 1,536 → 256 is usually safe. 1,536 → 64 is not. Validate on your eval set.
  • Context truncation. Most models silently truncate inputs over their max length. Long docs need chunking (see lesson 23).
  • Ignoring latency tail. MTEB scores hide p99 latency. A 600M model might beat a 335M model by 2 points but cost 3× more per query.

Recap
What to keep from this lesson
  • Dense (one vector), sparse (learned term weights), multi-vector (one per token, MaxSim): different storage, different strengths.
  • Embedding models are trained contrastively; query and document may need different prefixes or encoders.
  • Matryoshka training makes prefixes of the vector usable; other models lose more when truncated.
  • Binary quantization with float rescoring keeps most quality at 1/32 of the storage.
  • Choose by measuring on your own data; leaderboards average away your domain.

Solutions

SolutionP1 · The 1-bit version

Keeping all 384 dimensions at one bit each loses less than truncating to 64 float dimensions (the run prints both, and rescoring the bit-based top 50 with full vectors recovers almost all of the rest). A non-Matryoshka model spreads information over every coordinate, so dropping 320 of them throws away real signal, while the sign of each coordinate preserves most of the angle between two vectors. 64 floats (256 bytes) is also more storage than 384 bits (48 bytes).

SolutionB1 · Vector length starts to count

Truncated vectors no longer have length 1, and different documents keep different shares of their length in the first few coordinates. The dot product then mixes the angle with that leftover length, so documents whose information happens to sit in the early coordinates rank higher regardless of relevance. Rankings change, and usually get worse. Re-normalising restores cosine similarity on the kept coordinates.
