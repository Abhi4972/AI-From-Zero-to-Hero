The problem

In plain words first

Git keeps a history of your project as a chain of snapshots called commits. You choose what goes into the next snapshot (git add), take it (git commit), and copy your history to GitHub (git push). A branch is just a name pointing at one commit, so trying an idea on a branch costs nothing and leaves main untouched.

You're about to write hundreds of code files across 20 phases. Without version control you will lose work, break things you can't undo, and have no way to collaborate with others.

Git is the tool. GitHub is where the code lives. This lesson covers what you need for this course and nothing more.

The idea

Three things to remember: 1. Save often (git commit) 2. Push to remote (git push) 3. Branch for experiments (git checkout -b experiment)

The same idea as a formula

Git stores every file, folder listing and commit as an object named by a hash of its contents:

id(file)=SHA-1("blob "∥size∥\0∥content)

where ∥ joins bytes. A folder (a tree) is hashed from the names and ids of what it contains, and a commit from its tree id, its parent commit's id, the author and the message. So a commit id fixes the entire history behind it: change one byte in an old file and that file's id changes, then its tree's, then every later commit's.

Why collisions do not worry anyone. SHA-1 gives 160-bit ids. For n objects with random ids, the chance that any two share an id is about n2/2161 (the birthday bound). Git can also use SHA-256 for new repositories (git init --object-format=sha256), which hardens it against deliberately constructed collisions.

Worked example
Hashing a file by hand

The file contains hello and a newline: 6 bytes.

  1. Header: blob 6 followed by a zero byte.
  2. Hash the header plus the 6 bytes with SHA-1: ce013625030ba8dba906f756967f9e9ca394464a.
  3. Git stores the object in .git/objects/ce/013625…: the first two hex digits name the folder.

Every repository in the world that contains a file with exactly these bytes stores it under this same id; that is how Git spots unchanged files instantly and why it never stores the same content twice.

See it drawn
Git's hash, recomputed

Python's hashlib against git hash-object, then the same file with one character changed.

import hashlib, subprocess, tempfile, os
# Git names every file by the SHA-1 of a short header plus its bytes. Check it against git itself.
content = b"hello\n"
ours = hashlib.sha1(b"blob %d\0" % len(content) + content).hexdigest()
with tempfile.TemporaryDirectory() as d:
    p = os.path.join(d, "f.txt"); open(p, "wb").write(content)
    theirs = subprocess.run(["git", "hash-object", p], capture_output=True, text=True).stdout.strip()
    edited = os.path.join(d, "g.txt"); open(edited, "wb").write(b"hello!\n")
    other = subprocess.run(["git", "hash-object", edited], capture_output=True, text=True).stdout.strip()
print(f"Python: {ours}\ngit:    {theirs}\nsame: {ours == theirs}")
print(f"one character changed -> {other} (nothing in common)")
n = 10**9   # a billion objects
print(f"chance of any SHA-1 collision among {n:.0e} random objects ≈ n²/2^161 = {n * n / 2**161:.1e}")
What you should see
Python: ce013625030ba8dba906f756967f9e9ca394464a
git:    ce013625030ba8dba906f756967f9e9ca394464a
same: True
one character changed -> 4effa19f4f75f846c3229b9dbdbad14eff362f32 (nothing in common)
chance of any SHA-1 collision among 1e+09 random objects ≈ n²/2^161 = 3.4e-31
Reading this output

The two ids are identical: Git really is just SHA-1 over a short header and the bytes. Adding one ! produces an unrelated id, which is how git status knows instantly which files changed, without comparing contents line by line. The collision chance for a billion objects, about 10−31, is why nobody worries about accidental clashes.

Check your mental model
  • ✗ "git commit uploads my work."
    ✓ A commit only lives on your machine until you git push it to a remote.
  • ✗ "A branch copies the whole project."
    ✓ A branch is a label on a commit. Creating one is instant, whatever the size of the repository.
  • ✗ "Adding *.pt to .gitignore removes the checkpoint I already committed."
    ✓ .gitignore only affects files Git is not tracking yet. A file already committed stays tracked until you run git rm --cached on it.

Step 2 · The daily workflow

git status
git add file.py
git commit -m "Add perceptron implementation"
git push origin main
Predict before you run

You create new.py and run git status --short, then git add new.py and run it again. What two-character code does Git show for the file each time? (Solution P1.)

Step 3 · Branching for experiments

git checkout -b experiment/new-optimizer

# ... make changes, commit ...

git checkout main
git merge experiment/new-optimizer
Reading this output

If nothing was committed to main while you worked on the branch, git merge prints Fast-forward: Git just moves the main label forward to your last commit, no merge commit needed. If both branches moved, Git creates a merge commit with two parents, and if both changed the same lines you get a conflict to resolve by hand.

Break it on purpose

Commit a file called model.pt. Then add *.pt to .gitignore, change model.pt, and run git status --short. Is the file ignored? How do you stop tracking it without deleting it from your disk? (Solution B1.)

Step 4 · Working with this course repo

You can't push to the course repo itself — only maintainers have write access. Fork it on GitHub first (the Fork button, top right) so origin points at your own copy:

git clone https://github.com/YOUR-USERNAME/ai-engineering-from-scratch.git
cd ai-engineering-from-scratch

git checkout -b my-progress
# work through lessons, commit your code
git push origin my-progress
Recap
What to keep from this lesson
  • Working directory → git add → staging area → git commit → local history → git push → GitHub.
  • Branches are cheap labels: use one per experiment and merge it back when it works.
  • Put checkpoints, datasets and secrets in .gitignore before the first commit; ignoring does not untrack.
  • You cannot push to someone else's repository; fork it and push to your copy.

Solutions

SolutionP1 · Untracked, then added

Before git add, the line is ?? new.py: untracked, Git sees the file but is not recording it. After git add, it is A new.py: added to the staging area, so it will be in the next commit.

SolutionB1 · A tracked checkpoint

Not ignored: git status --short shows M model.pt, a tracked file that was modified. .gitignore never applies to files already in the history. Run git rm --cached model.pt (the file stays on disk; git status now shows D model.pt, deleted from the index), then commit. From then on *.pt keeps it out. The old commit still contains the file, which matters if it was large or secret.

Use it: the same idea with real libraries

For this course, you need exactly these commands:

Command When
git clone Get the course repo
git add + git commit Save your work
git push Back it up to GitHub
git checkout -b Try something without breaking main
git log --oneline See what you've done

That's it. You don't need rebase, cherry-pick, or submodules for this course.

Industry practice
What's current (2024–2026)
  • AI agents open pull requests. GitHub's Copilot coding agent (generally available since September 2025) takes an assigned issue, works in a sandbox and opens a pull request for review; agents in the terminal (Claude Code, Codex CLI, Gemini CLI) commit through ordinary git. Reviewing diffs well matters more than ever.
  • Model files are not git files. The Hugging Face Hub stores models and datasets with Xet, a chunk-level storage backend that replaced Git LFS on the Hub; keep weights and data out of your code repository and reference them by repo id and revision.
  • Pre-commit checks. pre-commit hooks running Ruff (lint and format) and a secret scanner (for example gitleaks) catch problems before they reach the shared history.

Sources: Copilot coding agent GA, Xet on the Hub, pre-commit, Ruff.
