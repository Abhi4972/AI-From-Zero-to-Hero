In plain words first
The idea in one line

LLMs cannot do anything. They generate text. That is the entire capability. They cannot check the weather, query a database, send an email, run code, or read a file. Every "AI agent" you have ever seen is an LLM generating JSON that says which function to call -- and then your code actually calling it. The model is the brain. Tools are the hands. Function calling is the nervous system connecting them.

Terms you'll hear
Term What people say What it actually means
Function calling "Tool use" The model outputs structured JSON describing a function to invoke with specific arguments -- your code executes it, not the model
Tool definition "Function schema" A JSON Schema object describing a tool's name, purpose, parameters, and types -- the model reads this to decide when and how to use the tool
Tool choice "Calling mode" Controls whether the model must call a tool (required), may call a tool (auto), or must call a specific tool (named)
Parallel calling "Multi-tool" The model outputs multiple tool calls in a single turn, reducing round trips -- GPT-4o and Claude both support this
Tool result "Function output" The return value from executing a tool, sent back to the model as a message so it can use real data in its response
Argument validation "Input checking" Verifying that model-generated arguments match the expected types, ranges, and constraints before executing the tool
MCP "Tool protocol" Model Context Protocol -- the open standard (created by Anthropic, now under the Linux Foundation's Agentic AI Foundation) for exposing tools via servers that any compatible client can discover and call
Agent loop "ReAct loop" The iterative cycle of model-decides-tool, code-executes-tool, result-feeds-back until the model has enough information to respond
Tool poisoning "Prompt injection via tools" An attack where tool results contain instructions that manipulate the model's behavior -- sanitize all tool outputs
Rate limiting "Call budget" Setting a maximum number of tool calls per conversation to prevent infinite loops and runaway API costs

The problem

In plain words first

A model cannot look anything up or do anything; it can only write text. Function calling gives it a structured way to ask: you describe your functions (name, purpose, typed arguments), and instead of answering the model may reply with a call such as get_weather(city="Tokyo"). Your code checks the call, runs the function, and sends the result back; the model then answers with real data. The model never executes anything, your code does, which is why validation and allow-lists matter. This lesson builds the loop with a simulated model, then runs it for real: Qwen2.5-0.5B-Instruct, whose chat template supports tools, picks tools, fills arguments, makes parallel calls and reads results for six questions. No model is trained.

You build a chatbot. A user asks: "What's the weather in Tokyo right now?"

The model responds: "I don't have access to real-time weather data, but based on the season, Tokyo is likely around 15 degrees Celsius..."

That is a hallucination dressed in a disclaimer. The model does not know the weather. It never will. Weather changes every hour. The model's training data is months old.

The correct answer requires calling the OpenWeatherMap API, getting the current temperature, and returning the real number. The model cannot call APIs. Your code can. The missing piece: a structured protocol that lets the model say "I need to call the weather API with these arguments" and lets your code execute it and feed the result back.

This is function calling. The model outputs structured JSON describing which function to invoke with what arguments. Your application executes the function. The result goes back into the conversation. The model uses the result to produce its final answer.

Without function calling, LLMs are encyclopedias. With it, they become agents.

Idea 1 · The Function Calling Loop

Every tool-use interaction follows the same 5-step loop.

Step 1: the user sends a message. Step 2: the model receives the message along with tool definitions (JSON Schema describing available functions). Step 3: instead of responding with text, the model outputs a tool call -- a structured JSON object with the function name and arguments. Step 4: your code executes the function and captures the result. Step 5: the result goes back to the model, which now has real data to produce its final answer.

The model never executes anything. It only decides what to call and with what arguments. Your code is the executor.

Idea 2 · Tool Definitions: The JSON Schema Contract

Each tool is defined by a JSON Schema that tells the model what the function does, what arguments it takes, and what types those arguments must be.

{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "Get current weather for a city. Returns temperature in Celsius and conditions.",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {
          "type": "string",
          "description": "City name, e.g. 'Tokyo' or 'San Francisco'"
        },
        "units": {
          "type": "string",
          "enum": ["celsius", "fahrenheit"],
          "description": "Temperature units"
        }
      },
      "required": ["city"]
    }
  }
}

The description fields are critical. The model reads them to decide when and how to use the tool. A vague description like "gets weather" produces worse tool selection than "Get current weather for a city. Returns temperature in Celsius and conditions." The description is a prompt for tool selection.

Idea 3 · Provider Comparison

Every major provider supports function calling, but the API surface differs.

Provider API Parameter Tool Call Format Parallel Calls Forced Calling
OpenAI (GPT-6 family) tools function_call output items (Responses API), tool_calls[] (Chat Completions) Yes (multiple per turn) tool_choice="required"
Anthropic (Claude Opus/Sonnet/Haiku 5.5) tools content[].type="tool_use" Yes (multiple blocks) tool_choice={"type":"any"}
Google (Gemini) function_declarations functionCall Yes function_calling_config
Open-weight (Qwen, Llama, DeepSeek, Mistral) tools passed to the model's chat template Model-specific tags, e.g. <tool_call> JSON for Qwen (Hermes style) Model-dependent Serving engines (vLLM, SGLang) parse calls and support tool_choice

The closed providers have converged on near-identical JSON-Schema-based formats. Open-weight models each define their tool format in their chat template, and serving engines translate it into the OpenAI shape. For shared tools across hosts, prefer MCP (Lesson 11.14) over inline function calling: the server is the same for all of them.

Idea 4 · Tool Choice: Auto, Required, Specific

You control when the model uses tools.

Auto (default): the model decides whether to call a tool or respond directly. "What's 2+2?" -- responds directly. "What's the weather?" -- calls the tool.

Required: the model must call at least one tool. Use this when you know the user's intent requires a tool. Prevents the model from guessing instead of looking up real data.

Specific function: force the model to call a particular function. tool_choice={"type":"function", "function": {"name": "get_weather"}} guarantees the weather tool is called, regardless of the query. Use this for routing -- when upstream logic already determined which tool is needed.

Idea 5 · Parallel Function Calling

Current GPT, Claude and Gemini models, and many open-weight ones, can call multiple functions in a single turn. A user asks: "What's the weather in Tokyo and New York?" The model outputs two tool calls simultaneously:

[
  {"name": "get_weather", "arguments": {"city": "Tokyo"}},
  {"name": "get_weather", "arguments": {"city": "New York"}}
]

Your code executes both (ideally concurrently), returns both results, and the model synthesizes a single response. This cuts round trips from 2 to 1; when an agent's calls are independent, the saving grows with their number (worked example below).

The same idea as a formula

Tool selection is next-token prediction. With tool schemas T in the prompt, the model's first answer tokens choose between plain text and a call:

p(call f with args a∣x,T)=p(<tool_call>∣x,T)p(f∣…)p(a∣…,f).
The descriptions in T are prompt text, which is why wording them well changes which tool gets picked.

Latency of an agent turn with k independent calls of latencies t1​,…,tk​ and model round-trip time m:

Tsequential​=km+i∑​ti​,Tparallel​=m+imax​ti​  (one model turn, calls run concurrently).

Worked example
Three independent lookups
  • Model round trip m=1.2 s; tool latencies 0.3, 0.5 and 0.8 s.
  • Sequential: 3×1.2+(0.3+0.5+0.8)=5.2 s. Parallel: 1.2+0.8=2.0 s, 62% less.
  • The model still needs one more turn to read the results and answer, in both cases: add 1.2 s to each.
  • Tokens: every tool schema is sent with every request; with three schemas this lesson's 0.5B model sees about 415 prompt tokens for a 10-word question (measured below), almost all of it schemas and the template's tool-use instructions.
Check your mental model
  • ✗ "The model calls the API."
    ✓ The model writes a request; your code decides whether to run it, runs it and returns the result.

Idea 6 · Structured Outputs vs Function Calling

Lesson 11.3 covered structured outputs. Function calling uses the same JSON Schema machinery, but for a different purpose.

Structured outputs: force the model to produce data in a specific shape. The output is the final product. Example: extract product info from text as {name, price, in_stock}.

Function calling: the model declares an intent to execute an action. The output is an intermediate step. Example: get_weather(city="Tokyo") -- the model is requesting an action, not producing the final answer.

Use structured outputs when you want data extraction. Use function calling when you want the model to interact with external systems.

Idea 7 · Security: The Non-Negotiable Rules

Function calling is the most dangerous capability you can give an LLM. The model chooses what to execute. If your tool set includes database queries, the model constructs the queries. If it includes shell commands, the model writes them.

Rule 1: Never pass model-generated SQL directly to a database. The model can and will generate DROP TABLE, UNION injections, or queries that return every row. Always parameterize. Always validate. Always use an allowlist of operations.

Rule 2: Allowlist functions. The model can only call functions you explicitly define. Never build a generic "execute any function by name" tool. If you have 50 internal functions, expose only the 5 the user needs.

Rule 3: Validate arguments. The model might pass a city name of "; DROP TABLE users; --". Validate every argument against expected types, ranges, and formats before execution.

Rule 4: Sanitize tool results. If a tool returns sensitive data (API keys, PII, internal errors), filter it before sending it back to the model. The model will include tool results in its response verbatim.

Rule 5: Rate limit tool calls. A model in a loop can call tools hundreds of times. Set a maximum (10-20 calls per conversation is reasonable). Break infinite loops.

Idea 8 · Error Handling

Tools fail. APIs time out. Databases go down. Files do not exist. The model needs to know when a tool fails and why.

Return errors as structured tool results, not exceptions:

{
  "error": true,
  "message": "City 'Toky' not found. Did you mean 'Tokyo'?",
  "code": "CITY_NOT_FOUND"
}

The model reads this, adjusts its arguments, and retries. Models are good at self-correcting from structured error messages. They are bad at recovering from empty responses or generic "something went wrong" errors.

Idea 9 · MCP: Model Context Protocol

MCP is the open standard for tool interoperability that Anthropic created in 2024 and, in December 2025, donated to the Agentic AI Foundation under the Linux Foundation. Instead of every application defining its own tools, MCP provides a universal protocol: tools are served by MCP servers, consumed by MCP clients (like Claude Code, Cursor, ChatGPT or your application).

One MCP server can expose tools to any compatible client. A Postgres MCP server gives any MCP-compatible agent database access. A GitHub MCP server gives any agent repository access. The tools are defined once, used everywhere.

MCP is to function calling what HTTP is to networking. It standardizes the transport layer so tools become portable.

def calculator(expression, precision=2):
    allowed = set("0123456789+-*/.() ")
    if not all(c in allowed for c in expression):
        return {"error": True, "message": f"Invalid characters in expression: {expression}"}
    try:
        result = eval(expression, {"__builtins__": {}}, {"math": math})
        return {"result": round(float(result), precision), "expression": expression}
    except Exception as e:
        return {"error": True, "message": str(e)}

def get_weather(city, units="celsius"):
    key = city.lower().strip()
    if key not in WEATHER_DB:
        suggestions = [c for c in WEATHER_DB if c.startswith(key[:3])]
        return {
            "error": True,
            "message": f"City '{city}' not found.",
            "suggestions": suggestions,
            "code": "CITY_NOT_FOUND",
        }
    data = WEATHER_DB[key].copy()
    if units == "fahrenheit":
        data["temp_f"] = round(data["temp_c"] * 9 / 5 + 32, 1)
        del data["temp_c"]
    data["city"] = city
    return data

def read_file(path):
    if ".." in path or path.startswith("/"):
        return {"error": True, "message": "Path traversal not allowed.", "code": "FORBIDDEN"}
    if path not in FILE_SYSTEM:
        available = list(FILE_SYSTEM.keys())
        return {"error": True, "message": f"File '{path}' not found.", "available_files": available, "code": "NOT_FOUND"}
    content = FILE_SYSTEM[path]
    return {"path": path, "content": content, "size_bytes": len(content), "lines": content.count("\n") + 1}


def run_code(code, language="python"):
    if language != "python":
        return {"error": True, "message": f"Language '{language}' not supported. Only 'python' is available."}
    try:
        tree = ast.parse(code)
    except SyntaxError as e:
        return {"error": True, "message": f"SyntaxError: {e}", "code": "SYNTAX_ERROR"}
    unsafe_names = {"exec", "eval", "compile", "__import__", "open", "globals", "locals", "vars", "getattr", "setattr", "delattr"}
    for node in ast.walk(tree):
        if isinstance(node, (ast.Import, ast.ImportFrom)):
            return {"error": True, "message": "Forbidden operation: import is not allowed", "code": "SECURITY_VIOLATION"}
        if isinstance(node, ast.Attribute) and node.attr.startswith("__") and node.attr.endswith("__"):
            return {"error": True, "message": "Forbidden operation: dunder attribute access is not allowed", "code": "SECURITY_VIOLATION"}
        if isinstance(node, ast.Name) and node.id in unsafe_names:
            return {"error": True, "message": f"Forbidden operation: {node.id} is not allowed", "code": "SECURITY_VIOLATION"}
    try:
        local_vars = {}
        exec(code, {"__builtins__": {"print": print, "range": range, "len": len, "str": str, "int": int, "float": float, "list": list, "dict": dict, "sum": sum, "min": min, "max": max, "abs": abs, "round": round, "sorted": sorted, "enumerate": enumerate, "zip": zip, "map": map, "filter": filter, "math": math}}, local_vars)
        result = local_vars.get("result", None)
        return {"success": True, "result": result, "variables": {k: str(v) for k, v in local_vars.items() if not k.startswith("_")}}
    except Exception as e:
        return {"error": True, "message": f"{type(e).__name__}: {e}"}

A substring blocklist reads the code as text, so it misses anything the string match does not literally spell. Parsing the code into a syntax tree and walking it lets the guard reject import statements, dunder attribute access (the __class__ and __globals__ chains that reach back to the real interpreter), and unsafe builtin names by structure rather than spelling. Even so, treat this as a teaching filter, not a real boundary. Any in-process guard shares the interpreter with the code it runs, and a determined caller can still find reachable objects. Production systems run untrusted code in a separate process or container (a subprocess with dropped privileges, gVisor, Firecracker, or a hosted code runner), where an escape lands the attacker in a throwaway box instead of your service.

Step 4 · Build the Function Calling Loop

This is the core engine. It simulates the model deciding which tool to call, executes the tool, and feeds results back.

def simulate_model_decision(user_message, tools, conversation_history):
    msg = user_message.lower()

    if any(word in msg for word in ["weather", "temperature", "forecast"]):
        cities = []
        for city in WEATHER_DB:
            if city in msg:
                cities.append(city)
        if not cities:
            for word in msg.split():
                if word.capitalize() in [c.title() for c in WEATHER_DB]:
                    cities.append(word)
        if not cities:
            cities = ["tokyo"]
        calls = []
        for city in cities:
            calls.append({"name": "get_weather", "arguments": {"city": city.title()}})
        return calls

    if any(word in msg for word in ["calculate", "compute", "math", "what is", "how much"]):
        for token in msg.split():
            if any(c in token for c in "+-*/"):
                return [{"name": "calculator", "arguments": {"expression": token}}]
        if "+" in msg or "-" in msg or "*" in msg or "/" in msg:
            expr = "".join(c for c in msg if c in "0123456789+-*/.() ")
            if expr.strip():
                return [{"name": "calculator", "arguments": {"expression": expr.strip()}}]
        return [{"name": "calculator", "arguments": {"expression": "0"}}]

    if any(word in msg for word in ["search", "find", "look up", "google"]):
        query = msg.replace("search for", "").replace("look up", "").replace("find", "").strip()
        return [{"name": "web_search", "arguments": {"query": query}}]

    if any(word in msg for word in ["read", "file", "open", "cat", "show"]):
        for path in FILE_SYSTEM:
            if path.split("/")[-1].split(".")[0] in msg:
                return [{"name": "read_file", "arguments": {"path": path}}]
        return [{"name": "read_file", "arguments": {"path": "README.md"}}]

    if any(word in msg for word in ["run", "execute", "code", "python"]):
        return [{"name": "run_code", "arguments": {"code": "result = 'Hello from the sandbox!'", "language": "python"}}]

    return []


def execute_tool_call(tool_call):
    name = tool_call["name"]
    args = tool_call["arguments"]

    if name not in TOOL_REGISTRY:
        return {"error": True, "message": f"Unknown tool: {name}", "code": "UNKNOWN_TOOL"}

    tool = TOOL_REGISTRY[name]
    func = tool["function"]
    start = time.time()

    try:
        result = func(**args)
    except TypeError as e:
        result = {"error": True, "message": f"Invalid arguments: {e}"}

    elapsed_ms = round((time.time() - start) * 1000, 2)
    return {"tool": name, "result": result, "execution_time_ms": elapsed_ms}


def run_function_calling_loop(user_message, max_iterations=5):
    conversation = [{"role": "user", "content": user_message}]
    tool_definitions = [t["definition"] for t in TOOL_REGISTRY.values()]
    all_tool_results = []

    for iteration in range(max_iterations):
        tool_calls = simulate_model_decision(user_message, tool_definitions, conversation)

        if not tool_calls:
            break

        results = []
        for call in tool_calls:
            result = execute_tool_call(call)
            results.append(result)

        conversation.append({"role": "assistant", "content": None, "tool_calls": tool_calls})

        for result in results:
            conversation.append({"role": "tool", "content": json.dumps(result["result"]), "tool_name": result["tool"]})

        all_tool_results.extend(results)
        break

    return {"conversation": conversation, "tool_results": all_tool_results, "iterations": iteration + 1 if tool_calls else 0}

Step 5 · Argument Validation

Build a validator that checks tool call arguments against the JSON Schema before execution.

def validate_tool_arguments(tool_name, arguments):
    if tool_name not in TOOL_REGISTRY:
        return [f"Unknown tool: {tool_name}"]

    schema = TOOL_REGISTRY[tool_name]["definition"]["function"]["parameters"]
    errors = []

    if not isinstance(arguments, dict):
        return [f"Arguments must be an object, got {type(arguments).__name__}"]

    for required_field in schema.get("required", []):
        if required_field not in arguments:
            errors.append(f"Missing required argument: {required_field}")

    properties = schema.get("properties", {})
    for arg_name, arg_value in arguments.items():
        if arg_name not in properties:
            errors.append(f"Unknown argument: {arg_name}")
            continue

        prop_schema = properties[arg_name]
        expected_type = prop_schema.get("type")

        type_checks = {"string": str, "integer": int, "number": (int, float), "boolean": bool, "array": list, "object": dict}
        if expected_type in type_checks:
            if not isinstance(arg_value, type_checks[expected_type]):
                errors.append(f"Argument '{arg_name}': expected {expected_type}, got {type(arg_value).__name__}")

        if "enum" in prop_schema and arg_value not in prop_schema["enum"]:
            errors.append(f"Argument '{arg_name}': '{arg_value}' not in {prop_schema['enum']}")

    return errors

The loop with a real model

Qwen2.5-0.5B-Instruct with three Python functions (weather, currency conversion, calculator), turned into JSON schemas by the chat template from their type hints and docstrings. For each question: the model's tool calls, the results your code returns (allow-listed and validated), and the model's final answer. Greedy decoding. About a minute.

import json, re, torch
from transformers import AutoTokenizer, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"                     # its chat template has native tool support (Hermes-style <tool_call> tags)
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

WEATHER = {"tokyo": (18, "cloudy"), "new york": (9, "rain"), "mumbai": (31, "sunny")}
def get_weather(city: str, units: str = "celsius"):
    """Get the current weather for a city.

    Args:
        city: City name, e.g. "Tokyo"
        units: "celsius" or "fahrenheit"
    """
    t, c = WEATHER.get(city.lower(), (None, None))
    if t is None: return {"error": True, "code": "CITY_NOT_FOUND", "message": f"No data for {city!r}"}
    return {"city": city, "temp": t if units == "celsius" else round(t * 9 / 5 + 32), "units": units, "condition": c}
def convert_currency(amount: float, from_currency: str, to_currency: str):
    """Convert an amount between currencies at today's rate.

    Args:
        amount: The amount to convert
        from_currency: ISO code, e.g. "USD"
        to_currency: ISO code, e.g. "EUR"
    """
    rates = {"USD": 1.0, "EUR": 0.92, "INR": 84.0, "JPY": 150.0}
    return {"result": round(amount / rates[from_currency.upper()] * rates[to_currency.upper()], 2), "to": to_currency.upper()}
def calculate(expression: str):
    """Evaluate an arithmetic expression with + - * / and parentheses.

    Args:
        expression: e.g. "(17 * 23) + 4"
    """
    if not re.fullmatch(r"[\d\s+\-*/().]+", expression): return {"error": True, "code": "BAD_EXPRESSION"}
    return {"value": eval(expression, {"__builtins__": {}})}       # allow-listed characters only
TOOLS = [get_weather, convert_currency, calculate]
REG = {f.__name__: f for f in TOOLS}

def generate(messages):
    text = tok.apply_chat_template(messages, tools=TOOLS, tokenize=False, add_generation_prompt=True)
    ids = tok(text, return_tensors="pt").input_ids
    with torch.no_grad():
        out = model.generate(ids, max_new_tokens=120, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True), ids.shape[1]

def run(question):
    msgs = [{"role": "user", "content": question}]
    reply, n_prompt = generate(msgs)
    calls = [json.loads(c) for c in re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", reply, re.S)]
    log = [f"prompt with 3 tool schemas: {n_prompt} tokens"]
    if not calls:
        return log + [f"no tool call; answered directly: {reply.strip()[:90]!r}"]
    msgs.append({"role": "assistant", "content": "", "tool_calls": [{"type": "function", "function": c} for c in calls]})
    for c in calls:
        fn = REG.get(c["name"])                                # allow-list: unknown names are refused
        res = fn(**c["arguments"]) if fn else {"error": True, "code": "UNKNOWN_TOOL"}
        log.append(f"call {c['name']}({json.dumps(c['arguments'])}) -> {json.dumps(res)}")
        msgs.append({"role": "tool", "name": c["name"], "content": json.dumps(res)})
    final, _ = generate(msgs)
    return log + [f"final answer: {final.strip()[:120]!r}"]

for q in ["What's the weather in Tokyo right now?",
          "Convert 250 US dollars to Indian rupees.",
          "What is 17 times 23, plus 4?",
          "What's the weather in Tokyo and in Mumbai?",
          "Who wrote Pride and Prejudice?",
          "What's the weather in Atlantis?"]:
    print(f"\nQ: {q}")
    for line in run(q): print("   " + line)

Reading this output

Four of six questions went exactly right. Weather, currency and arithmetic each produced one well-formed call with the right arguments: (17 * 23) + 4 was written as an expression for the calculator instead of being computed by the model, and the answer 395 is correct. Your code, not the model, did the arithmetic and the conversion.

Parallel calls work even at 0.5B. "Tokyo and Mumbai" produced two get_weather calls in one turn, and the final answer uses both results. The model also filled in units: "celsius" on its own, a default it read from the docstring.

About 415 prompt tokens per request, for questions of about ten words. The three schemas and the template's tool instructions are sent every time, so tool definitions are a fixed cost per call. Fifty tools would cost thousands of tokens before the user has said anything (Lesson 11.5).

Not calling a tool is also a decision, and here it went wrong. For "Who wrote Pride and Prejudice?" the model correctly made no call, then claimed it had no information. The answer is Jane Austen, which a 0.5B model usually knows without tools. Having tools in the prompt can make a small model hedge on questions it would otherwise answer.

The error was returned, then misread. For Atlantis your code returned a structured error, CITY_NOT_FOUND. The model told the user it lacks access to real-time weather, which is not what the error said. Structured errors help, but you should still check what the model says about them. Some systems turn known error codes into fixed user-facing messages instead of letting the model paraphrase them.

Industry practice
What's current (2024–2026)
  • Strict tool schemas: OpenAI and Anthropic can enforce tool arguments against the JSON schema (strict: true), so arguments always parse; validation of values stays your job.
  • MCP as the tool layer: tools are packaged as MCP servers and shared across clients; the protocol is now governed by the Agentic AI Foundation.
  • Tool search for large tool sets: agents load only the definitions they need per task instead of sending hundreds of schemas on every call.
  • Server-side tools: providers run some tools themselves (web search, code execution, file search) inside the API call.

What to keep from this lesson

You are a tool definition designer for LLM function calling. I will describe what a tool should do. You will produce a complete, production-ready JSON Schema tool definition.

## Design Protocol

### 1. Analyze the Tool Purpose

Before writing the schema:

- Identify the core action (read, write, search, compute, transform)
- Determine required vs optional parameters
- Identify parameter types and constraints (enums, min/max, patterns)
- Consider error cases and what the tool should return on failure
- Determine if the tool has side effects (read-only vs mutating)

### 2. Writing the Description

The description is the most important field. The model reads it to decide when to use the tool.

Rules:
- Start with an action verb: "Get", "Search", "Create", "Calculate", "Read"
- State what the tool returns: "Returns temperature in Celsius and weather conditions"
- Mention limitations: "Only supports cities with population > 100,000"
- Keep it under 200 characters
- Do not include parameter details in the description -- those go in parameter descriptions

Bad: "A weather tool"
Good: "Get current weather for a city. Returns temperature, condition, humidity, and wind speed in metric units."

### 3. Parameter Design

For each parameter:
- Use `description` to explain what it accepts and give examples
- Use `enum` for categorical values -- never rely on the model inventing the right string
- Use `minimum`/`maximum` for numbers to prevent hallucinated extreme values
- Set `default` for optional parameters so the model knows the behavior when omitted
- Mark only truly necessary parameters as `required`

### 4. Output Format

Return the tool definition in the OpenAI `tools` format:

```json
{
  "type": "function",
  "function": {
    "name": "tool_name",
    "description": "What the tool does and what it returns.",
    "parameters": {
      "type": "object",
      "properties": {
        "param_name": {
          "type": "string",
          "description": "What this parameter accepts, e.g. 'example value'"
        }
      },
      "required": ["param_name"]
    }
  }
}
```

Also include:
- An Anthropic-format version (using `input_schema` instead of `parameters`)
- 3 example tool calls with expected arguments
- 2 error scenarios the implementation should handle

```
{description}
```

**Context (optional):**
```

```

# Function Calling Patterns

When building an LLM application that uses tools, apply this decision framework.

## When to use function calling

**Use function calling when:**
- The model needs real-time data (weather, stock prices, database queries)
- The task requires side effects (sending emails, creating records, deploying code)
- The model must choose between multiple actions based on user intent
- You are building an agent that interacts with external systems

**Use structured outputs instead when:**
- You need data extraction from text (no external calls needed)
- The output is the final product, not an intermediate step
- You have a single schema, not multiple tools to choose from

**Use both when:**
- The model calls a tool, then structures the tool result into a specific output format

## Tool design guidelines

1. **One tool, one action.** A tool named `manage_database` that handles queries, inserts, updates, and deletes is too broad. Split into `query_records`, `insert_record`, `update_record`. The model selects better with specific tools.

2. **Descriptions are prompts.** The model reads tool descriptions to decide selection. Write them like you would write instructions for a junior developer. Include what the tool returns, not just what it does.

3. **Constrain with enums.** If a parameter has 3-10 valid values, use an enum. The model will invent strings -- "celsius", "Celsius", "C", "metric" -- unless you constrain it.

4. **Fewer tools is better.** GPT-4o handles 5-10 tools well. At 20+ tools, selection accuracy drops. At 50+ tools, expect 10-15% wrong tool selection. Group related functionality or use a routing layer.

5. **Required means required.** Only mark a parameter as required if the tool literally cannot function without it. Optional parameters with good defaults reduce tool call failures.

## Provider-specific patterns

### OpenAI (GPT-4o, o3, GPT-4o-mini)

```python
tools=[{"type": "function", "function": {"name": ..., "parameters": ...}}]
tool_choice="auto"       # model decides
tool_choice="required"   # must call at least one tool
tool_choice={"type": "function", "function": {"name": "specific_tool"}}
```

- Supports parallel tool calls (multiple `tool_calls` in one response)
- Tool call IDs must be passed back with results
- `gpt-4o-mini` is 10x cheaper and handles simple tool routing well
- Structured outputs mode works with tool parameters for guaranteed schema compliance

### Anthropic (Claude 3.5 Sonnet, Claude 4 Opus)

```python
tools=[{"name": ..., "description": ..., "input_schema": ...}]
tool_choice={"type": "auto"}     # model decides
tool_choice={"type": "any"}      # must call at least one tool
tool_choice={"type": "tool", "name": "specific_tool"}
```

- Tool calls appear as content blocks with `type: "tool_use"`
- Results go in user messages with `type: "tool_result"`
- Field name is `input_schema`, not `parameters` (common migration bug)
- Supports multiple tool calls per response

### Google (Gemini 2.0 Flash, Gemini 2.0 Pro)

```python
function_declarations=[{"name": ..., "description": ..., "parameters": ...}]
function_calling_config={"mode": "AUTO"}   # or "ANY" or "NONE"
```

- Uses `function_declarations` at the top level
- Results returned via `function_response` parts
- Supports parallel function calling

### Open-source models (Llama 3, Hermes, Qwen)

- No standardized format -- varies by model and serving framework
- Hermes format (NousResearch) is the most common fine-tuned convention
- vLLM supports OpenAI-compatible tool calling for supported models
- Ollama supports basic tool calling with compatible models
- Test tool selection accuracy before production -- open models are 15-30% less accurate than GPT-4o on the Berkeley Function Calling Leaderboard

## Error handling patterns

### Return structured errors

```json
{"error": true, "message": "City 'Toky' not found. Did you mean 'Tokyo'?", "code": "NOT_FOUND", "suggestions": ["Tokyo"]}
```

Include actionable information. "Not found" is bad. "Not found, did you mean X?" is good. The model uses error messages to self-correct.

### Retry strategy

1. Tool call fails with a correctable error (typo, wrong enum value)
2. Send the error back to the model as a tool result
3. The model adjusts and retries
4. Maximum 3 retries per tool call
5. After 3 failures, return the error to the user

### Timeout handling

Set timeouts on all tool executions. 30 seconds is a reasonable default. If a tool times out, return a structured timeout error so the model can inform the user rather than hanging.

## Security checklist

| Check | Why | How |
|-------|-----|-----|
| Allowlist functions | Prevent arbitrary code execution | Only register tools the user needs |
| Validate argument types | Prevent type confusion attacks | Check types before execution |
| Sanitize string arguments | Prevent injection | Reject or escape special characters |
| Parameterize database queries | Prevent SQL injection | Never pass model-generated SQL directly |
| Filter tool results | Prevent data leakage | Remove API keys, PII, internal errors |
| Rate limit tool calls | Prevent runaway loops | Max 10-20 calls per conversation |
| Log all tool calls | Audit trail | Store tool name, arguments, result, timestamp |
| Block path traversal | Prevent file system access | Reject `..` and absolute paths in file tools |
| Sandbox code execution | Prevent system access | Use containers or restricted builtins |
| Validate return size | Prevent context stuffing | Truncate results over 10KB |

## Performance optimization

- **Parallel calls:** When the model requests multiple independent tools, execute them concurrently with `asyncio.gather()` or `concurrent.futures`
- **Caching:** Cache tool results for identical arguments within the same session (weather does not change in 60 seconds)
- **Streaming:** Stream the model's final response while tool results are being fetched
- **Tool pruning:** If context is tight, only include tool definitions relevant to the current query (use a classifier to filter)
- **Smaller models for routing:** Use `gpt-4o-mini` or `claude-haiku-4-5` for tool selection, then pass results to a stronger model for synthesis

## Common failure patterns

| Failure | Cause | Fix |
|---------|-------|-----|
| Wrong tool selected | Ambiguous descriptions | Rewrite descriptions with specific trigger words |
| Missing required args | Model forgot a parameter | Add clear examples in parameter descriptions |
| Infinite tool loop | Model keeps calling same tool | Set max iterations (5-10) and detect repeated calls |
| Hallucinated arguments | Model invents plausible but wrong values | Use enums, validate against known values |
| Tool result too large | API returned 100KB of data | Truncate or summarize before feeding back |
| Model ignores tool result | Result format confusing | Return clean JSON with clear field names |

Exercises

  2. Implement retry with error feedback. When a tool call fails (e.g., city not found), feed the error message back to the model decision function and let it correct its arguments. Track how many retries each call takes. Set a maximum of 3 retries per tool call.

  3. Build a multi-step agent. Some queries require chaining tool calls: "Read the config file and tell me what model is configured, then search the web for that model's pricing."   4. Measure tool selection accuracy. Create 30 test queries with expected tool names. Run your decision function on all 30 and measure what percentage of the time it selects the correct tool. Identify which queries cause the most confusion between tools.

  5. Implement tool call caching. If the same tool is called with identical arguments within 60 seconds, return the cached result instead of re-executing. Use a dictionary keyed by (tool_name, frozenset(args.items())). Measure cache hit rates across a conversation with 20 queries.

Solutions

SolutionP1 · No tool call for the novel, and a misread error

For "Who wrote Pride and Prejudice?" it made no tool call, which is right, since no tool fits. Its answer was still poor: it said it had no information about the author, who is Jane Austen. For Atlantis it called get_weather. The code returned {"error": true, "code": "CITY_NOT_FOUND"}. The final answer then blamed a lack of real-time weather access instead of saying the city is unknown. The selection logic worked in both cases, and the wording of the answer failed in both.

SolutionB1 · Arbitrary code execution, one prompt away

With eval(expression) and no checks, the model's call calculate({"expression": "__import__('os').listdir('.')"}) runs Python on your server, and the directory listing comes back as a "result". The model even reads it out to the user. The same channel would accept open(...), os.remove(...) or a network call. The prompt can come from a user, or from a document or web page the model has read (prompt injection, Lesson 11.12), so this is arbitrary code execution one message away.

The rules that stop it: validate arguments against a strict allow-list before executing (the lesson's calculator accepts only digits, operators and parentheses); give each tool the least capability it needs (a calculator never needs eval on raw text, so use a real expression parser); and never trust the description. Renaming the tool "Runs Python" changes what the model will try, not what the code permits. Sandbox anything that must run code, and log every call.

Weigh a trade-offYou need two things from the same model: a typed summary of a support ticket, and the ability to look up the customer's account during the conversation. A teammate wants to build both as tools. Which mechanism fits each, and why does the distinction matter?

Level 2 of 4 · about 7 minutes to answer well.

Short answer. The ticket summary is structured output: the typed data is the final product, so use the schema mode and validate it. The account lookup is a function call: the model declares an intent to act, your code executes it and feeds the result back, so the output is an intermediate step. The two share the JSON Schema machinery but differ in what happens next, and mixing them hides which outputs are data and which are actions your code runs.

Two uses of one mechanism.

Structured output Function call
What the model emits a record that matches a schema a function name and typed arguments
What happens next your code validates and stores it your code executes it and returns the result to the model
The output is the final product an intermediate step
Fits extraction, classification, typed summaries lookups, writes, anything that touches another system

The function calling lesson states the rule: use structured outputs when you want data, use function calling when you want the model to interact with an external system. The model never executes anything; it only decides what to call and with what arguments.

When tool use is the right way to get data.

The structured outputs lesson gives the exception. When the model has to choose among several schemas based on the input, for example 10 extraction schemas, tool use gives you the selection and the structure in one step. One provider also delivers its schema mode through tool use, with the schema on the tool input. In that case name the tool for the data it returns, never execute it, and route its arguments straight to the validator.

Why the distinction matters in code.

A record gets schema validation and a semantic check. An action gets argument validation, an allowlist, result sanitizing and a call budget before anything runs, because the model chose what to execute. If the summary and the lookup live in one registry, the security rules for actions either cover data they do not need to, or miss an action they should.

Plausible wrong answers.

  • "They are the same thing with different names." They share the schema machinery; one produces the final data, the other requests an action your code performs.
  • "Use function calling for everything, it is more flexible." Every tool is an executable surface with security rules; data extraction does not need one.
  • "The model runs the lookup itself." The model never executes anything; it emits a call and your code is the executor.

Follow-ups an interviewer may ask.

  • (level 2) When is tool use the right way to get structured data? Expected: when the model must pick one of several schemas from the input; the lesson's example is 10 extraction schemas, where tool use gives the selection and the structure together.
  • (level 2) In the lookup case, who runs the function? Expected: your code; the model emits the name and the arguments, and the result goes back as a message.
  • (level 3) What differs in validation between the two? Expected: data gets schema validation and a semantic check; an action gets argument validation, an allowlist and a call budget before it runs.
  • (level 3) A provider offers schema output only through tool use. How do you keep the distinction? Expected: name the tool for the data it returns, never execute it, send its arguments to the validator as the final record, and keep real actions in a separate registry.

Where it is taught. The lesson function calling separates data from action and gives the five-step loop, and the lesson structured outputs covers tool use as a way to choose among schemas.

Defend a designDesign the execution layer for an agent that can query a database, run small code snippets and read files on behalf of a user. The model decides which tool to call. What rules does the executor enforce, and what does it never do?

Level 3 of 4 · about 15 minutes to answer well.

Short answer. The executor never passes model-generated SQL or shell text straight to a system. It exposes an allowlist of named functions with typed parameters, validates every argument against the schema before execution, sanitizes tool results before they return to the model, and caps the number of calls per conversation at 10 to 20. For code, an in-process filter is a teaching aid and not a boundary; untrusted code runs in a separate process or container.

The five rules.

  1. Never pass generated SQL to the database. The model can and will produce destructive statements and injections. The lesson's exercise shapes the tool to accept a table name and filter conditions, with the tables on an allowlist and the operators restricted to a small set; your code builds the query.
  2. Allowlist the functions. The model calls only what you define. If fifty internal functions exist, expose the five the user needs. Never build a generic call-by-name tool.
  3. Validate the arguments. Check required fields, unknown fields, types and enum membership against the schema before execution; a city name can carry an injection string.
  4. Sanitize the results. A tool result goes back into the prompt verbatim, so strip keys, personal data and internal errors, and treat instructions inside a result as tool poisoning.
  5. Cap the calls. A loop can call a tool hundreds of times; 10 to 20 calls per conversation is the lesson's range, with a bounded retry count per failing call.

The file tool.

Reject any path with a parent reference or a leading slash, and return a structured error with the list of files that exist. The error shape matters: a message, a code and suggestions let the model correct its arguments; an empty response or a generic failure does not.

The code tool.

A substring blocklist reads the code as text and misses anything it does not literally spell. Parsing the code into a syntax tree lets the guard reject imports, dunder attribute access and unsafe names by structure. Even then, the guard shares the interpreter with the code it runs, and a determined caller finds reachable objects. Production runs untrusted code in a separate process with dropped privileges, in a sandbox or in a hosted runner, so an escape lands in a throwaway box.

What the model never does.

It never executes anything. It emits a name and arguments. Everything after that is your code, and every rule above lives there.

Plausible wrong answers.

  • "The model behaves, parameterize later." The model can and will generate destructive queries or injections; the rule is never to pass its SQL through.
  • "A generic run-any-function tool is simpler." The allowlist is the rule: expose the five functions the user needs, not all fifty.
  • "The code filter blocks imports, so it is safe." It shares the interpreter with the code it runs; production uses a separate process or container.

Follow-ups an interviewer may ask.

  • (level 3) Why is a substring blocklist not enough for the code tool? Expected: it matches spelling, not structure; a parsed syntax tree rejects imports, dunder access and unsafe names by shape, and even that shares the interpreter with the code.
  • (level 3) How do you shape the database tool so the model never writes SQL? Expected: accept a table name and filter conditions, allowlist the tables, restrict the operators, and build the query in your code.
  • (level 4) What is tool poisoning and where is the control? Expected: results that carry instructions to the model; sanitize every result before it returns, and strip sensitive data such as keys and internal errors.
  • (level 4) The agent loops on a failing tool. What stops it? Expected: a maximum number of calls per conversation, 10 to 20 in the lesson, structured errors that let the model fix its arguments, and a retry cap of about 3 per call.

Where it is taught. The lesson function calling states the five security rules, builds the argument validator and the file and code guards, and sets the call budget.

Explain the mechanismAn agent has eight tools and keeps calling the wrong one. The tool descriptions are one or two words each, such as "gets weather". What does the description do, and how do you rewrite one?

Level 2 of 4 · about 7 minutes to answer well.

Short answer. The model reads the description to decide when and how to call the tool, so the description is a prompt for tool selection. Rewrite it as a full sentence that says what the tool does and what it returns, for example that it gets the current weather for a city and returns the temperature in Celsius and the conditions, and describe each parameter with an example value and an enum where the set is closed. Then validate the arguments against the schema before anything executes.

What the model sees.

A tool definition is a JSON Schema contract: a name, a description, and the parameters with their types, their own descriptions, and the required list. The model never sees your code. It picks a tool and fills the arguments from this text alone, so a vague description produces worse selection than a precise one, and a parameter with an example such as a city name is filled more reliably than a bare string.

Beyond the description.

  • Tool choice. Auto lets the model decide. Required forces at least one call, which stops the model from guessing when you know a lookup is needed. A named tool forces that one, for routing when upstream logic already knows.
  • Parallel calls. Two cities in one question can come back as two calls in one turn; execute both and return both results.
  • Structured errors. Return failures as results with a message, a code and suggestions, such as the city not found and the nearest names. Models self-correct from structured errors and not from empty or generic ones.
  • A call budget. Set a maximum of 10 to 20 calls per conversation so a loop cannot run away.

Measure it.

Write a set of queries with the expected tool for each; the lesson's exercise uses 30. Run the selection and report the share that picked the right tool, and list the pairs that get confused.

Plausible wrong answers.

  • "The model infers the purpose from the function name." It reads the description; a vague one produces worse selection than a full sentence.
  • "Describe every tool in a paragraph to be safe." Definitions travel with every request; one precise sentence plus parameter descriptions is the target.
  • "Let the model call any function by name." The lesson's rule is an allowlist of the tools you define, never a generic execute-by-name tool.

Follow-ups an interviewer may ask.

  • (level 2) Where else does a description help besides the tool itself? Expected: on each parameter, with an example value and an enum where the set is closed, so the arguments come out right.
  • (level 2) The model still guesses instead of calling a tool when it should. Which setting changes that? Expected: tool choice set to required, or to a named tool when upstream logic already knows which one.
  • (level 3) How do you prove the rewrite worked? Expected: a set of test queries with expected tool names, 30 in the lesson, the share that select the right tool, and the confused pairs listed.
  • (level 3) A tool fails. What should it return so the model recovers? Expected: a structured error with a message, a code and suggestions, not an exception or an empty response.

Where it is taught. The lesson function calling gives the tool definition contract, the tool choice modes, structured errors and the selection accuracy exercise.

Check your understanding

Q1Can LLMs actually execute functions or access external systems?

LLMs generate tokens. When 'calling a function,' the model outputs JSON specifying the function name and arguments. Your application code parses this JSON, executes the actual function, and sends the result back to the model.

Q2What is a tool schema in the context of function calling?

Tool schemas describe available functions to the model: function name, parameter names and types, descriptions of what each parameter does, and what the function returns. The model uses these to decide when and how to call tools.

Q3What is the standard pattern for a multi-turn function calling loop?

The loop: (1) send user message + tool schemas, (2) model responds with a tool call request, (3) execute the function, (4) send the result back as a tool response, (5) model generates the next response or another tool call.

Q4How do you prevent infinite tool calling loops?

Without limits, a model could repeatedly call tools (e.g., searching for information it can never find). A max iteration count (e.g., 10 rounds) and total timeout prevent runaway loops in production.

Q5Why are clear, descriptive parameter names and descriptions important in tool schemas?

The model reads tool descriptions to decide what to call and how. A parameter described as 'q' vs 'search_query: The user's search terms to look up in the knowledge base' gives vastly different results.
