In plain words first
The idea in one line

Full fine-tuning a 7B model requires 56GB of VRAM. You don't have that. Neither do most companies. LoRA lets you fine-tune the same model in 6GB by training less than 1% of the parameters. This isn't a compromise -- it matches full fine-tuning quality on most tasks. The entire open-source fine-tuning ecosystem runs on this one trick.

Terms you'll hear
Term What people say What it actually means
LoRA "Efficient fine-tuning" Low-Rank Adaptation: freeze base weights, train two small matrices A and B whose product approximates the full weight update
QLoRA "Fine-tune on a laptop" Quantized LoRA: load the base model in 4-bit NF4, train LoRA adapters in fp16 on top, enabling 7B fine-tuning in 6GB VRAM
Rank (r) "How much the model can learn" The inner dimension of the A and B matrices; controls expressiveness vs. parameter count
Alpha "LoRA learning rate" Scaling factor applied to the LoRA output; $\alpha/r$ scales the adaptation's contribution to the final output
NF4 "4-bit quantization" Normal Float 4: a 4-bit data type with quantization levels at normal distribution quantiles, optimal for neural network weights
Adapter "The small trained part" The LoRA A and B matrices saved as a separate file (10-100MB), loadable on top of any copy of the base model
Target modules "Which layers to LoRA" The specific linear layers (q_proj, v_proj, etc.) where LoRA adapters are injected
Merging "Bake it in" Computing $W + (\alpha/r) \cdot BA$ and replacing the original weight, eliminating the adapter overhead at inference
Paged optimizers "Don't OOM during training" Offloading optimizer states (Adam momentum, variance) to CPU when GPU memory is exhausted
Catastrophic forgetting "Fine-tuning broke everything else" When updating all weights causes the model to lose previously learned capabilities

The problem

In plain words first

Fine-tuning changes a model's weights to teach it a behaviour: a format, a style, a narrow task. Changing all of them needs memory for the weights, their gradients and the optimiser's statistics, about 16 bytes per parameter. LoRA freezes the original weights and learns a small correction for each weight matrix, written as the product of two thin matrices, so only a fraction of a percent of the parameters train. QLoRA also stores the frozen weights in 4 bits. This lesson builds LoRA from scratch on a toy network, then measures the real numbers without training anything: adapter sizes on the actual Llama 3.1 8B architecture, the memory each method needs, an exact merge check with the PEFT library, and NF4 against plain 4-bit quantization on real SmolLM2 weights.

You have a base model. Llama 3 8B. You want it to answer customer support tickets in your company's voice. SFT is the answer. But SFT has a cost problem.

Full fine-tuning updates every parameter in the model. Llama 3 8B has 8 billion parameters. In bf16, each parameter takes 2 bytes: 16GB just to load the weights. Standard mixed-precision training with AdamW also keeps gradients, an fp32 master copy of the weights and Adam's two fp32 moments: about 16 bytes per parameter, roughly 128GB for an 8B model before activations.

No single 80GB GPU fits that; you shard it across several GPUs (Lesson 10.5) or cut the memory with 8-bit optimisers and offloading. Every experiment costs GPU-hours, and you need several to get the hyperparameters right.

Scale this to Llama 3 70B and the numbers get absurd: 140GB for the bf16 weights alone, over a terabyte of training state. You need a cluster.

There's a deeper problem too. Full fine-tuning modifies every weight in the model. If you fine-tune on customer support data, you might degrade the model's general capabilities. It's called catastrophic forgetting. The model gets better at your task and worse at everything else.

You need a method that trains fewer parameters, uses less memory, and doesn't destroy the model's existing knowledge.

Idea 1 · LoRA: Low-Rank Adaptation

Edward Hu and colleagues at Microsoft published LoRA in June 2021. The paper's insight: the weight updates during fine-tuning have low intrinsic rank. You don't need to update all 16.7 million parameters in a 4096x4096 weight matrix. The useful information in the update can be captured by a matrix of rank 16 or 32.

Here's the math. A standard linear layer computes:

y=Wx

Where W is a dout​×din​ matrix. For a 4096x4096 attention projection, that's 16,777,216 parameters.

LoRA freezes W and adds a low-rank decomposition:

y=Wx+BAx

Where B is (dout​×r) and A is (r×din​). The rank r is much smaller than d -- typically 8, 16, or 32.

For r=16 on a 4096x4096 layer: - Original parameters: 4096 x 4096 = 16,777,216 - LoRA parameters: (4096 x 16) + (16 x 4096) = 65,536 + 65,536 = 131,072 - Reduction: 131,072 / 16,777,216 = 0.78%

You're training 0.78% of that matrix's parameters. Whether that matches full fine-tuning depends on the task and on where the adapters go (next sections): on small and medium instruction-tuning datasets, LoRA on all layers usually comes close.

A is initialized with a random Gaussian. B is initialized to zero. This means the LoRA contribution starts at zero -- the model begins training from its original behavior and gradually learns the adaptation.

Idea 2 · The Scaling Factor: Alpha

LoRA introduces a scaling factor α that controls how much the low-rank update affects the output:

y=Wx+rα​⋅BAx

When α=r, the scaling is 1x. When α=2r (the common default), the scaling is 2x. This hyperparameter controls the learning rate of the LoRA path independently of the base learning rate.

Practical guidance: - α=2⋅rank is a common community convention (the original paper used α=rank in most experiments) - α=rank gives 1x scaling, conservative but stable - Higher α means larger updates per step, which can speed convergence or cause instability

The same idea as a formula

LoRA on a frozen weight W0​∈Rdout​×din​:

h=W0​x+rα​BAx,A∈Rr×din​, B∈Rdout​×r, B0​=0,
so the update ΔW=rα​BA has rank at most r and starts at zero. Trainable parameters per matrix: r(din​+dout​) instead of din​dout​.

Merging is exact algebra: W′=W0​+rα​BA gives W′x=W0​x+rα​BAx for every x.

Memory per parameter for mixed-precision AdamW: 2 (bf16 weight) + 2 (gradient) + 4 (fp32 master) + 4 + 4 (Adam moments) = 16 bytes. LoRA pays 16 bytes only for the adapter parameters and 2 bytes (or about 0.52 in NF4) for the frozen rest.

Compute: training FLOPs ≈6ND (full) and ≈4ND (LoRA, no weight gradients for W0​), for N parameters and D training tokens.

Idea 3 · Where to Apply LoRA

A transformer has many linear layers. You don't need to add LoRA to all of them. The original paper tested different combinations:

Target Layers Trainable params, Llama 3.1 8B, r=16 (counted below) What studies found
q_proj + v_proj 6.8M The original paper's default; clearly below full fine-tuning on harder tasks
q_proj + k_proj + v_proj + o_proj 13.6M Better, still attention only
All linear (attention + MLP) 41.9M Needed to match full fine-tuning (QLoRA paper; Thinking Machines' "LoRA Without Regret")

The original LoRA paper adapted only the query and value projections, and many tutorials still do. Later work found that the MLP layers matter most: the QLoRA authors needed LoRA on every linear layer to match full fine-tuning, and Thinking Machines (2025) found attention-only LoRA underperforms MLP-only LoRA even at matched parameter count. Default to all linear layers; the extra parameters are still about half a percent of the model.

Idea 4 · Rank Selection

The rank r controls the expressiveness of the adaptation:

Rank Trainable Params (per layer) Best For
4 32,768 Simple classification, sentiment
8 65,536 Single-domain Q&A, summarization
16 131,072 Multi-domain tasks, instruction following
32 262,144 Complex reasoning, code generation
64 524,288 Diminishing returns for most tasks
128 1,048,576 Rarely justified

Hu et al. showed that r=4 already captures most of the adaptation for simple tasks. r=8 and r=16 are the most common choices in practice. Going beyond r=64 rarely improves quality and starts to lose LoRA's memory advantage.

Idea 5 · QLoRA: 4-Bit Quantization + LoRA

Tim Dettmers and colleagues at the University of Washington published QLoRA in May 2023. The idea: quantize the frozen base model to 4-bit precision, then attach LoRA adapters in fp16 on top.

This changes the memory equation dramatically:

Method Weight Memory (7B) Training memory before activations (7B) GPU Required
Full fine-tune (mixed precision, AdamW) 14GB ~112GB (16 bytes/param) several 80GB GPUs, sharded
LoRA (bf16 base) 14GB ~15GB one 24-48GB GPU
QLoRA (4-bit base) ~4GB ~5GB one 16-24GB GPU

Activations come on top and grow with batch size and sequence length; gradient checkpointing (Lesson 10.34) keeps them in check. The run below computes these numbers for Llama 3.1 8B.

QLoRA makes three technical contributions:

NF4 (Normal Float 4-bit): A new data type designed specifically for neural network weights. Neural network weights follow a roughly normal distribution. NF4 places its 16 quantization levels at the quantiles of a standard normal distribution. This is information-theoretically optimal for normally distributed data. It loses less information than uniform 4-bit quantization (INT4) or standard Float4.

Double quantization: The quantization constants themselves take memory. Each block of 64 weights needs a fp32 scale factor (4 bytes). For a 7B model, that's an extra 0.4GB. Double quantization quantizes these constants to fp8, reducing the overhead to 0.1GB. Small but it adds up.

Paged optimizers: During training, optimizer states (Adam's momentum and variance) can exceed GPU memory on long sequences. Paged optimizers use NVIDIA's unified memory to automatically page optimizer states to CPU RAM when GPU memory is exhausted, and page them back when needed. This prevents OOM crashes at the cost of some throughput.

Idea 6 · The Quality Question

Does reducing parameters or quantizing the base hurt quality? What the main studies report:

  • QLoRA (Dettmers et al. 2023): with NF4, double quantization and LoRA on all linear layers, 4-bit QLoRA matched 16-bit full fine-tuning on their GLUE and Super-NaturalInstructions experiments, and 16-bit LoRA on MMLU with LLaMA models from 7B to 65B.
  • LoRA Learns Less and Forgets Less (Biderman et al. 2024): on large code and math training runs, LoRA trailed full fine-tuning, but kept more of the base model's other abilities.
  • LoRA Without Regret (Thinking Machines 2025): on small and medium post-training datasets LoRA on all layers matched full fine-tuning, with a learning rate about 10 times higher; it fell behind once the dataset outgrew the adapter's capacity, and in reinforcement learning even rank 1 was enough.

Rule of thumb: LoRA is close to full fine-tuning for behaviour and format changes on modest data, and trails it when you try to pour in large amounts of new knowledge.

Idea 9 · Merging Adapters

After training, you have two things: the frozen base model and a small LoRA adapter (typically 10-100MB). You can either:

  1. Keep them separate: Load the base model, load the adapter on top. Swap adapters for different tasks. This is how you serve multiple fine-tuned variants from one base model.

  2. Merge them permanently: Compute W′=W+(α/r)⋅BA and save the result as a new full model. The merged model is the same size as the original. No inference overhead. No adapter to manage.

For serving multiple tasks (customer support adapter, code adapter, translation adapter), keep them separate. For deploying a single specialized model, merge.

Advanced merging techniques for combining multiple adapters:

  • TIES-Merging (Yadav et al. 2023): Trims small-magnitude parameters, resolves sign conflicts, then merges. Reduces interference between adapters.
  • DARE (Yu et al. 2023): Randomly drops adapter parameters before merging and rescales the rest. Surprisingly effective at combining capabilities.
  • Task arithmetic: Simply add or subtract adapter weights. Adding a "code" adapter and a "math" adapter often produces a model good at both.

Idea 10 · When NOT to Fine-Tune

Fine-tuning is the third option, not the first.

First: prompt engineering. Write a better system prompt. Add few-shot examples. Use chain-of-thought. This costs nothing and takes minutes. If prompting gets you 80% of the way there, you probably don't need to fine-tune.

Second: RAG. If the model needs to know about your specific data (documents, knowledge base, product catalog), retrieval is cheaper and more maintainable than baking it into weights. See Lesson 06.

Third: fine-tuning. Use this when you need the model to adopt a specific style, format, or reasoning pattern that cannot be achieved through prompting. When you need consistent structured output. When you need to distill a larger model into a smaller one. When latency matters and you can't afford the extra tokens from few-shot prompting.

Step 1 · The LoRA Layer

We implement LoRA from scratch in pure PyTorch. No libraries. No magic. You'll build the LoRA layer, inject it into a model, train it, and merge the weights back.

import torch
import torch.nn as nn
import math

class LoRALayer(nn.Module):
    def __init__(self, in_features, out_features, rank=8, alpha=16):
        super().__init__()
        self.rank = rank
        self.alpha = alpha
        self.scaling = alpha / rank

        self.A = nn.Parameter(torch.randn(in_features, rank) * (1 / math.sqrt(rank)))
        self.B = nn.Parameter(torch.zeros(rank, out_features))

    def forward(self, x):
        return (x @ self.A @ self.B) * self.scaling

A is initialized with scaled random values. B is initialized to zero. The product BA starts at zero, so the model begins with its original behavior.

Step 2 · LoRA-Wrapped Linear Layer

class LinearWithLoRA(nn.Module):
    def __init__(self, linear, rank=8, alpha=16):
        super().__init__()
        self.linear = linear
        self.lora = LoRALayer(
            linear.in_features, linear.out_features, rank, alpha
        )

        for param in self.linear.parameters():
            param.requires_grad = False

    def forward(self, x):
        return self.linear(x) + self.lora(x)

The original linear layer is frozen. Only the LoRA parameters (A and B) are trainable.

Step 3 · Inject LoRA into a Model

def inject_lora(model, target_modules, rank=8, alpha=16):
    for param in model.parameters():
        param.requires_grad = False

    lora_layers = {}
    for name, module in model.named_modules():
        if isinstance(module, nn.Linear):
            if any(t in name for t in target_modules):
                parent_name = ".".join(name.split(".")[:-1])
                child_name = name.split(".")[-1]
                parent = dict(model.named_modules())[parent_name]
                lora_linear = LinearWithLoRA(module, rank, alpha)
                setattr(parent, child_name, lora_linear)
                lora_layers[name] = lora_linear
    return lora_layers

First, freeze every parameter in the model. Then walk the model tree, find linear layers matching your target names, and replace them with LoRA-wrapped versions. The LoRA A and B matrices are the only trainable parameters in the entire model.

Step 4 · Count Parameters

def count_parameters(model):
    total = sum(p.numel() for p in model.parameters())
    trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
    frozen = total - trainable
    return {
        "total": total,
        "trainable": trainable,
        "frozen": frozen,
        "trainable_pct": 100 * trainable / total if total > 0 else 0
    }

Step 5 · Merge Weights Back

def merge_lora_weights(model):
    for name, module in model.named_modules():
        if isinstance(module, LinearWithLoRA):
            with torch.no_grad():
                merged = (
                    module.lora.A @ module.lora.B
                ) * module.lora.scaling
                module.linear.weight.data += merged.T
            parent_name = ".".join(name.split(".")[:-1])
            child_name = name.split(".")[-1]
            if parent_name:
                parent = dict(model.named_modules())[parent_name]
            else:
                parent = model
            setattr(parent, child_name, module.linear)

After merging, the LoRA layers are gone. The model is the same size as the original with the adaptation baked into the weights. No inference overhead.

Reading this output

The counts are exact, and they are tiny. PEFT counts 6.8M trainable parameters for the original paper's recipe (q and v, r = 16): 0.08% of 8.03B. Because of grouped-query attention, v_proj outputs only 1,024 values, so it contributes much less than q_proj. Moving to all linear layers at the same rank gives 41.9M (0.52%), six times as many, because the three MLP matrices are the widest in the model. Even r = 64 on everything is only 2.09%.

Memory, not parameters, is the reason for LoRA. Full fine-tuning needs 128.5 GB before activations: 16 bytes for every one of 8 billion parameters. LoRA needs 16.7 GB: the frozen bf16 weights at 2 bytes each, with the 16-byte cost paid only on 42M adapter parameters. That is the difference between a multi-GPU server and one 24 GB card. QLoRA's 6.4 GB fits the base model on a laptop GPU, but activations come on top of every row in this table, and they grow with batch size and sequence length.

Adapters are small files. r = 16 on every linear layer of a 135M model is a 9.8 MB file. You can keep one base model and swap or serve many adapters.

Merging is exact. With random, non-zero adapters, so the test is not trivial, merged weights and base-plus-adapter give logits that differ by at most 9.35e-05. That is float32 rounding: W0​x+BAx and (W0​+BA)x add the same numbers in a different order. Once merged, inference costs exactly what the base model costs.

Step 6 · Simulated QLoRA Quantization

def quantize_to_nf4(tensor, block_size=64):
    blocks = tensor.reshape(-1, block_size)
    scales = blocks.abs().max(dim=1, keepdim=True).values / 7.0
    scales = torch.clamp(scales, min=1e-8)
    quantized = torch.round(blocks / scales).clamp(-8, 7).to(torch.int8)
    return quantized, scales

def dequantize_from_nf4(quantized, scales, original_shape):
    dequantized = quantized.float() * scales
    return dequantized.reshape(original_shape)

This simulates 4-bit quantization by mapping weights into 16 discrete levels within blocks of 64. Production QLoRA uses the bitsandbytes library for true NF4 on GPU.

import numpy as np, torch
from scipy.stats import norm
from transformers import AutoModelForCausalLM

# NF4, built the way the QLoRA paper describes: 16 levels at quantiles of a standard normal, scaled to [-1, 1], with an exact zero
offset = 0.9677083
pos = norm.ppf(np.linspace(offset, 0.5, 9)[:-1])            # 8 positive levels

Reading this output

NF4's levels follow the bell curve. They are packed near zero (−0.091, 0, +0.080) and spread out towards ±1, while INT4 spaces its 16 levels evenly. Trained weights are roughly normally distributed within each block, so the levels sit where the weights are.

You can see it in the usage. With INT4 the outer levels each hold 1% of the weights and the central four hold more than half. With NF4 every level holds between 2% and 10%. Each of the 16 codes carries more information, which is what "information-theoretically optimal for normal data" means in practice.

Lower error with the same 4 bits. The relative error falls from 0.1056 to 0.0934, about 12% less, on all 315 million weights. The gap is modest but free: same storage, same speed, a better choice of levels. That is why QLoRA stores the frozen base in NF4.

The scales are not free, and double quantization fixes that. One fp32 scale per 64 weights adds 0.5 bits per weight, so "4-bit" would really be 4.5. Quantizing the scales themselves to 8 bits, with one fp32 scale per 256 of them, cuts the overhead to 0.127 bits. For a 7B model that saves 0.33 GB (0.44 GB against 0.11 GB), which matters when the goal is fitting on one GPU.

Step 7 · Training Loop

def train_lora(model, data, epochs=5, lr=1e-3, batch_size=4):
    optimizer = torch.optim.AdamW(
        [p for p in model.parameters() if p.requires_grad], lr=lr
    )
    criterion = nn.MSELoss()

    losses = []
    for epoch in range(epochs):
        epoch_loss = 0.0
        n_batches = 0
        indices = torch.randperm(len(data["inputs"]))

        for i in range(0, len(indices), batch_size):
            batch_idx = indices[i:i + batch_size]
            x = data["inputs"][batch_idx]
            y = data["targets"][batch_idx]

            output = model(x)
            loss = criterion(output, y)

            optimizer.zero_grad()
            loss.backward()
            optimizer.step()

            epoch_loss += loss.item()
            n_batches += 1

        avg_loss = epoch_loss / n_batches
        losses.append(avg_loss)

    return losses

easy15 minimplement

LoRA fine-tunes a large model without a change to its weights. It keeps the weight W of a linear layer frozen and adds a small trainable path through two low rank matrices A and B. After training, you can merge the path into W, so inference costs the same as the base model.

Task

Write three functions.

  1. lora_forward(x, W, b, A, B, alpha) returns the output of the layer with the adapter.
  2. merge_lora(W, A, B, alpha) returns the merged weight.
  3. count_trainable(in_features, out_features, rank) returns the number of trainable values in A and B.

The rank r is the number of rows of A. The output of the layer is

y=xWT+b+rα​xATBT.

The merged weight is W′=W+rα​BA. With the merged weight, xW′T+b equals the output of lora_forward.

Only A and B train. W and b are frozen and do not count.

Input and output

Name Type Shape Meaning
x float array (N, in_features) one input row for each of the N examples
W float array (out_features, in_features) the frozen weight
b float array (out_features,) the frozen bias
A float array (r, in_features) the down projection of the adapter
B float array (out_features, r) the up projection of the adapter
alpha float scalar the LoRA scale numerator
in_features, out_features, rank int scalar the layer sizes and the rank
  • lora_forward returns a float array of shape (N, out_features).
  • merge_lora returns a new float array of shape (out_features, in_features).
  • count_trainable returns a Python int.

Constraints

  • 1 <= N <= 64, 1 <= in_features, out_features <= 4096 and 1 <= r <= 64.
  • The rank can be larger than in_features or out_features.
  • alpha > 0.
  • Do not change the input arrays.
  • Use numpy only.

Common mistakes the checks catch

  • Counts r times in_features times out_features, the size of a full matrix product, not of A and B.
  • Adds the adapter into W in place, so the caller's frozen weight changes.

Hint 1

Compute the base output and the adapter output apart, then add them. The base output is x @ W.T + b.

Hint 2

The rank is A.shape[0]. Do not read it from W or from x.

Hint 3

The adapter path first projects x down to r values with A, then up to out_features values with B. Multiply that path by alpha / r.

Hint 4

For the merge, B @ A has the shape of W. Return a new array. Do not add into W with +=. For the count, add the sizes of A and B.

Reference solution and notes
import numpy as np


def lora_forward(x, W, b, A, B, alpha):
    rank = A.shape[0]
    scaling = alpha / rank
    base = x @ W.T + b
    return base + scaling * ((x @ A.T) @ B.T)


def merge_lora(W, A, B, alpha):
    rank = A.shape[0]
    scaling = alpha / rank
    return W + scaling * (B @ A)


def count_trainable(in_features, out_features, rank):
    return rank * in_features + out_features * rank

Why B starts at zero

LoRA sets A to small random values and B to zero. The product BA is then zero, so the first forward pass gives the output of the base model. Training moves the layer away from the base behavior step by step.

Why the scale is alpha over r

The scale α/r keeps the size of the update about the same when you change the rank. You can try several ranks without a new learning rate. A common choice is α=2r.

Why the count is small

A full update of a 4096×4096 weight has about 16.8 million values. A rank 8 adapter has 8×(4096+4096)=65536 values. That is 0.4 percent of the full weight. The optimizer state is small for the same reason.

Shapes in the lesson code

The lesson stores A as (in_features, r) and B as (r, out_features), and computes x @ A @ B. This problem uses the shapes of the LoRA paper: A is (r, in) and B is (out, r). The two forms give the same result. The lesson code merges with (A @ B).T, which equals B @ A here.

Where this goes next

The lesson also quantizes the frozen weight to 4 bits. That is QLoRA. The adapter stays in full precision, and the merge step dequantizes W first.

# Fine-Tuning Decision Guide

Before fine-tuning, try these in order:

```
1. Prompt engineering (minutes, $0)
2. Few-shot examples in prompt (minutes, $0)
3. RAG for knowledge retrieval (days, $10-100/month)
4. Fine-tuning with LoRA/QLoRA (days, $5-50 per experiment)
5. Full fine-tuning (weeks, $100-10,000 per run)
```

Only move to the next step if the previous one is measurably insufficient.

## When to fine-tune

- Model needs a consistent output style or format that prompting cannot achieve
- You're distilling a larger model (GPT-4 quality from an 8B model)
- Latency matters and few-shot examples add too many tokens
- You need the model to reliably follow a complex reasoning pattern
- You have 1,000+ high-quality examples of the desired input-output behavior

## When NOT to fine-tune

- The model already does what you want with the right prompt
- You need the model to know facts (use RAG instead)
- You have fewer than 500 training examples (likely to overfit)
- The task changes frequently (retraining is expensive)
- You need to audit which data influenced a specific output (fine-tuning is a black box)

## Method selection

| GPU VRAM | 7B model | 13B model | 70B model |
|----------|----------|-----------|-----------|
| 16GB (T4) | QLoRA | Not feasible | Not feasible |
| 24GB (3090/4090) | QLoRA or LoRA | QLoRA | Not feasible |
| 40GB (A100) | LoRA or Full | QLoRA or LoRA | QLoRA |

## LoRA configuration checklist

1. Start with r=16, alpha=32 (safe default for most tasks)
2. Target q_proj and v_proj first (minimum viable LoRA)
3. Use learning rate 2e-4 for QLoRA, 5e-5 for LoRA fp16
4. Set lora_dropout=0.05
5. Train for 1-3 epochs (more risks overfitting)
6. Evaluate every 100 steps on a held-out set
7. Save checkpoints and pick the best by eval loss

## Common mistakes

- Training for too many epochs (overfitting after epoch 2-3 on small datasets)
- Using the same learning rate as full fine-tuning (LoRA needs higher LR)
- Forgetting to set the pad token (causes NaN losses with Llama models)
- Not freezing the base model (defeats the purpose of LoRA)
- Evaluating only on training data (always hold out 10-20% for eval)
- Skipping the prompt engineering baseline (fine-tuning a problem that prompting already solves)

## Quality verification

After training, compare on 200+ held-out examples:
1. Base model with best prompt (baseline)
2. Base model with LoRA adapter (your fine-tuned model)
3. GPT-4 or Claude with same prompt (ceiling)

If the LoRA model does not beat the prompted baseline, your training data or configuration needs work, not more compute.

## Adapter management

- Keep adapters separate for multi-task serving (swap adapters per request)
- Merge adapters into base weights for single-task deployment
- Store adapters on Hugging Face Hub (10-100MB, easy to version and share)
- Test merged model outputs match unmerged outputs before deploying
- Use TIES-Merging or DARE to combine multiple adapters into one

## Debugging training

If loss does not decrease:
1. Check learning rate (too low for LoRA, try 2e-4)
2. Verify LoRA layers are actually receiving gradients
3. Confirm base model weights are frozen
4. Check data formatting (tokenizer must match model's expected format)

If loss decreases but eval quality is bad:
1. Training data quality issue (garbage in, garbage out)
2. Overfitting (reduce epochs, increase dropout, add more data)
3. Wrong target modules (add MLP layers for complex tasks)
4. Rank too low (try r=32 or r=64)

Solutions

SolutionP1 · 6.8 million, under a tenth of a percent

6.8 million at r = 16, which is 0.08% of Llama 3.1 8B's 8.03 billion parameters. Per layer, q_proj (4096 → 4096) adds 16×(4096+4096)=131,072, and v_proj (4096 → 1024) adds 16×(4096+1024)=81,920. That is 212,992 per layer, times 32 layers = 6.82M. Grouped-query attention makes v four times narrower, so it adds less than q. PEFT's count in the run matches the hand calculation.

SolutionB1 · The model changes before it has learned anything

With B=0 at the start, ΔW=rα​BA=0, so the adapted model is exactly the pretrained model before the first step, and training starts from a known good point. With random B, ΔW is a random rank-r matrix added to every adapted layer. The model's outputs change before it has seen any data, typically for the worse, since a random perturbation of a trained network damages it. The first steps then go into undoing that noise. The merge check in the run uses random adapters on purpose, to show that merging is exact for any B; it is not how training starts. Initialising A randomly and B at zero still gives non-zero gradients for B, so learning starts immediately.

Estimate itAn attention projection in your model is a square matrix with 4,096 rows and 4,096 columns. You add a LoRA adapter of rank 16 to it. How many values does the adapter train, and what share of the frozen matrix is that? Then say what changes when you double the rank.

Short answer. The adapter is two thin matrices: A with 16 rows and 4,096 columns, and B with 4,096 rows and 16 columns. Each holds 65,536 values, so the adapter trains 131,072 parameters. The frozen matrix holds 16,777,216, so the adapter is 0.78 percent of it. A doubled rank doubles the adapter, because its size is linear in the rank.

The count.

y = W x + (alpha / r) B A x

Why so few parameters work.

The update that fine-tuning makes to a weight matrix has a low intrinsic rank. A rank of 16 or 32 captures most of it. The lesson reports LoRA at rank 16 within about one point of full fine-tuning on the benchmarks it lists.

The rank table.

Rank Parameters for one 4096 by 4096 matrix
4 32,768
8 65,536
16 131,072
32 262,144

Alpha.

The scale alpha / r sets how much the adapter output counts. With alpha equal to the rank, the scale is one; a common convention sets alpha to twice the rank. Alpha changes the effective step size, not the parameter count.

Which matrices.

The count above is one matrix. Adapters on the query and value projections of every layer are the usual start. Adding the key and output projections and the MLP layers raises quality a little and, on the lesson's 7B table, raises the count from 9.4M to 37.7M.

Plausible wrong answers.

  • "The adapter trains r squared parameters." It trains r times the sum of the two matrix sides; r squared would be a tiny block, not the two thin matrices.
  • "Doubling the rank doubles the quality." The gain flattens fast; the lesson finds rank 16 within about one point of full fine-tuning and little gain past 64.
  • "Alpha adds parameters." Alpha is a fixed scalar on the adapter output; it changes the effective step size, not the count.

Follow-ups an interviewer may ask.

  • (level 1) Why does B start at zero? Expected: the product B A is then zero, so the model starts from its original behavior and learns the change step by step.
  • (level 2) How does the count change for a matrix that is not square? Expected: A is r by the input width and B is the output height by r, so the count is r times the sum of the two sides; still linear in the rank.
  • (level 2) At what rank does the memory advantage start to fade? Expected: the lesson puts the point of diminishing returns past 64, where quality stops improving and the adapters stop being small.
  • (level 3) After training, how do you remove the cost of the second matrix product at inference? Expected: merge, compute W plus alpha over r times B A once, and save a full matrix of the original size.

Take-homeTake-home. A company wants a support assistant built from an open 8B base model. They have about 50,000 past support conversations with customer ratings, two 24 GB GPUs, and three weeks. Write the post-training plan on one page: the stages, the data for each stage, the settings you start from, what you measure after each stage, and the three failure modes you guard against.

Level 4 of 4 · about 45 minutes to answer well.

Short answer. Three stages: first, SFT with QLoRA on the top-rated conversations in one chat template with the loss masked to the assistant turns, at a low learning rate for one to three epochs with a few percent of raw text mixed in, measured by held-out instruction loss, raw-text drift and a sample read. Second, DPO against the SFT checkpoint as the frozen reference, on pairs built from high- and low-rated answers to the same prompt with a conservative beta, measured by a blind pairwise eval and the absolute chosen log-probability, not the training margin. Third, a release gate: a fixed prompt set rated blind, a refusal set, and a comparison with the base model on tasks the data never covered. The guards are catastrophic forgetting, length and agreement exploits in the ratings, and over-optimization of the preference proxy.

Stage 0: data.

  • Convert every conversation into one chat template, with a fixed system prompt.
  • SFT set: the top-rated answers, filtered for length, vocabulary diversity and a clean instruction-to-answer ratio. Tens of thousands of clean examples are enough; the reference SFT stage in the lesson used about 27,000.
  • Preference set: for prompts with both a high-rated and a low-rated answer, build prompt, chosen and rejected triples. Where the data is thin, sample the rejected side from the SFT model, so that the pairs are in-distribution for the reference. A rater or a judge must confirm that each sampled answer is worse than the chosen one before it becomes a pair, because the SFT model trained on top-rated answers and its samples can be as good. Aim for the 5,000 to 20,000 pairs where DPO works well.
  • A blind eval set of prompts never used in training, plus a forgetting set of tasks outside support, such as short code and arithmetic.

Stage 1: SFT with QLoRA.

Two 24 GB cards cannot hold a full update of this model; a 7B full update needs about 56 GB with gradients and optimizer states. QLoRA keeps the base in 4-bit and trains adapters of rank 16 on the attention projections in about 6 GB, so each card runs its own experiment.

Start from: the lesson's SFT learning rate of 2e-5 for a full update, with a higher rate for adapters as the LoRA lesson's trainer shows; one to three epochs; 2 to 5 percent raw pretraining text mixed into the batches.

Measure: held-out instruction loss, raw-text loss before and after with a budget of a 10 to 15 percent rise, exact match on the templated tasks where it applies, and a read of fifty samples.

Stage 2: DPO.

Reference: the merged SFT checkpoint, frozen. Policy: a copy with fresh adapters. Beta in the 0.1 to 0.3 range, a few epochs, and the four log-probabilities per pair over the answer tokens only.

Measure: a blind pairwise eval against the SFT model on the held-out prompts, the implicit reward margin, the absolute chosen log-probability, the response length by checkpoint, and the forgetting set again. Stop on the eval, not on the margin.

Stage 3: release gate.

  • A fixed prompt set rated blind by people, against the SFT checkpoint and the base.
  • A refusal and safety set with the expected behavior written down.
  • The forgetting set.
  • Adapters kept separate for a rollback; a merge only for the shipped artifact.

The three guards.

  1. Catastrophic forgetting: low rate, short training, a pretraining mix, and a raw-text loss budget.
  2. Exploits of the rating signal: raters liked long and agreeable answers, so watch the length and the agreement with the premise, and filter pairs where length alone separates them.
  3. Over-optimization of the proxy: the DPO ratio can be pushed off the data, so stop early on the blind eval and keep beta conservative.

Schedule.

Week one: data and SFT. Week two: DPO and the first blind eval. Week three: the gate, a second seed of the best configuration, and the rollback plan.

Plausible wrong answers.

  • "Skip SFT and run DPO on the base model." DPO needs a reference that already follows instructions; the single-stage loss is a different method, and the base model's pairs are out of distribution.
  • "Fully fine-tune the 8B model across both GPUs." A full update of a model this size needs about 56 GB with the optimizer states; two 24 GB cards hold it only with adapters and a 4-bit base.
  • "Use the star ratings as the reward and run PPO." A regression on absolute scores is the weak label the lessons warn about, and the full stack does not fit the compute or the timeline.

Follow-ups an interviewer may ask.

  • (level 3) Why DPO and not a reward model with PPO here? Expected: tens of thousands of pairs, two small GPUs and three weeks fit the DPO regime; a reward model and PPO need three loops and more memory.
  • (level 4) The ratings are one to five stars on single answers, not pairs. What changes? Expected: build pairs only where one prompt has answers at both ends of the scale, or use the unpaired loss that works on good and bad labels and keep the pairs for the eval.
  • (level 4) How do you prove that the DPO stage did not degrade the SFT behavior? Expected: the blind pairwise eval against the SFT checkpoint, the forgetting set, and the absolute chosen log-probability; a margin that grows while those fall is a stop signal.
  • (level 4) What would make you add an RL stage with a verifier? Expected: a part of the task with a checkable answer, such as a correct order number or a passing code snippet, where a binary reward and group-relative advantages give a signal the ratings do not.

Estimate itYou have one GPU with 24 GB of memory and want to fine-tune a 7B model on your own instruction data. Walk me through the memory for a full update, for LoRA and for QLoRA, and say what makes the last one fit.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. A full update of a 7B model needs about 56 GB: the weights in half precision, the gradients, and two optimizer states per parameter, all in half precision. LoRA keeps the half-precision weights but trains only small adapters, so the gradients and optimizer states shrink and the run takes about 18 GB. QLoRA stores the frozen base in 4-bit, about 3.5 GB of weights, and trains the adapters in half precision, so the run takes about 6 GB and leaves room for activations on a 24 GB card.

The memory table.

Method Weights Training total Fits on
Full update, FP16 14 GB about 56 GB before activations, which depend on the workload one 80 GB datacenter GPU
LoRA on an FP16 base 14 GB about 18 GB one 40 GB GPU
QLoRA, 4-bit base 3.5 GB about 6 GB one 24 GB consumer GPU

The 56 GB comes from two bytes per weight, two bytes per gradient, and two optimizer states per parameter; activations come on top of that. This estimate keeps the optimizer states in half precision too. Standard Adam keeps its states in FP32, so a typical full update needs more memory than this, not less. The adapters remove the gradients and the states for every frozen weight, which is the large part.

What QLoRA adds.

  1. NF4. A 4-bit type whose 16 levels sit at the quantiles of a normal distribution, which matches how weights are distributed and loses less than uniform 4-bit integers.
  2. Double quantization. Each block of 64 weights needs a scale in FP32, about 0.4 GB for a 7B model; quantizing the scales to 8 bits brings that down to about 0.1 GB.
  3. Paged optimizers. Optimizer states page to CPU memory when the GPU runs out, which trades some throughput for no out-of-memory crash from optimizer states. Activations stay on the GPU, so a long sequence can still run out of memory.

What it costs in quality.

The lesson's table puts LoRA at rank 16 within about one point of a full update, QLoRA at rank 16 a fraction behind that, and QLoRA at rank 64 level with the full update on the listed benchmarks.

What it costs in time and money.

On the lesson's cost table, QLoRA at rank 16 on a 24 GB consumer card took about 6 hours and about 5 dollars for 50,000 examples over three epochs. The full update took about 8 hours on two 80 GB datacenter GPUs and about 32 dollars. Fused kernels cut the QLoRA run to about 2.5 hours.

Plausible wrong answers.

  • "Quantize the whole model to 4-bit and fine-tune it directly." Gradients and optimizer states still need higher precision; the base stays frozen in 4-bit, and only the adapters train.
  • "QLoRA halves the quality." The lesson's table shows a loss of a fraction of a point at rank 16 and parity at rank 64.
  • "Load the base in 8-bit with LoRA; it is the same thing." Eight-bit weights take twice the memory of NF4, and the double quantization and paged optimizers are what make the 6 GB figure.

Follow-ups an interviewer may ask.

  • (level 2) Why does LoRA cut training memory so much more than it cuts weight memory? Expected: the gradients and the two optimizer states exist only for the adapter parameters, which are a fraction of a percent of the model.
  • (level 2) The adapters train in half precision while the base is 4-bit. Where does the forward pass compute? Expected: the base weights are dequantized block by block to the compute dtype for each matrix product, and the adapter path runs in half precision.
  • (level 3) When would you still pay for the full update? Expected: when the task needs changes that a low-rank update cannot express, when you have the data and the GPUs, or when the eval shows a gap that a higher rank does not close.
  • (level 3) How do you serve several QLoRA fine-tunes from one base? Expected: keep the adapters separate and load them on top of one base copy; merge only when you ship a single specialized model.

Check your understanding

Q1What is the core insight behind LoRA (Low-Rank Adaptation)?

Aghajanyan et al. showed that fine-tuning updates occupy a low-dimensional subspace. LoRA exploits this by representing the update as W + BA where B (d x r) and A (r x d) have small rank r, typically 8-64.

Q2How much memory does LoRA save compared to full fine-tuning of an 8B model?

Full fine-tuning needs gradients and optimizer states for all 8B parameters (~56GB). LoRA freezes base weights and only trains adapter matrices (~80M parameters at rank 16), needing ~6GB total.

Q3What is QLoRA?

QLoRA (Dettmers et al.) loads the frozen base model in 4-bit (NF4 quantization) while training LoRA adapters in FP16/BF16. This allows fine-tuning a 7B model on a single consumer GPU with 6GB VRAM.

Q4What does the 'rank' parameter (r) in LoRA control?

Rank r determines the size of adapter matrices A (r x d) and B (d x r). Rank 4 trains very few parameters (fast, cheap). Rank 64 trains more parameters (more expressive). Most tasks work well with rank 8-32.

Q5What happens when you merge LoRA weights back into the base model?

Since LoRA adds W_base + B*A, you can compute B*A once and add it to W_base permanently. The merged model has the same architecture and inference speed as the original, with no adapter overhead.
