In plain words first
The idea in one line

Autoregressive decoding is serial. Each token waits for the previous one. Speculative decoding breaks the chain: a cheap model drafts N tokens, the expensive model verifies all N in one forward pass. When the draft is right you paid one big forward for N generations.

Terms you'll hear
Term What people say What it actually means
Draft model "The cheap one" A smaller model that proposes candidate tokens; usually 10–50× cheaper than the verifier.
Verifier "The big one" The target model whose distribution we preserve; runs once per speculative step.
Acceptance rate ($\alpha$) "How often the draft is right" Per-token probability that the verifier accepts the draft. 0.7–0.9 typical.
Residual distribution "The rejection fallback" (q - p)_+ normalized; sampling from this on rejection preserves the verifier's distribution.
Bonus token "The free one" When all N drafts accepted, sample one more from the verifier's next-step distribution.
Medusa "Draft-less speculative" Multiple LM heads on the verifier predict positions t+1..t+k in parallel.
EAGLE "Hidden-state draft" Tiny transformer draft conditioned on the verifier's last-layer hidden states.
Lookahead decoding "Jacobi iteration" Self-speculation using a fixed-point iteration; no draft model.
Tree attention "Verify many candidates at once" Branching verification that considers several draft continuations simultaneously.
KV rollback "Undo rejected drafts" Scratch KV buffer; commit on acceptance, discard on reject.

The problem

In plain words first

A large language model writes one token per full pass through its weights, and on a GPU each pass is slow mostly because all the weights must be read from memory, not because of the arithmetic. Speculative decoding lets a small, fast model guess the next few tokens, then has the large model check all the guesses in a single pass. Guesses it agrees with are kept; at the first disagreement the large model's own choice is used instead. A clever acceptance rule makes the result exactly as if the large model had generated alone, so quality is unchanged; only the number of large-model passes drops. This lesson checks that rule with the lesson's code, then runs SmolLM2-360M with SmolLM2-135M as the drafter: the output is identical and the large model runs ten times less often, yet on this page's CPU it is only slightly faster, which shows exactly when the trick pays. Nothing is trained.

A 70B LLM sampling one token takes ~30 ms on an H100. A 3B draft model takes ~3 ms. If we let the 3B draft 5 tokens ahead, then run the 70B once to verify all 5, the total is 5×3+30=45 ms for up to 5 accepted tokens — versus 5×30 = 150 ms for straight-line generation. That is the full speculative-decoding pitch: trade a small amount of extra GPU memory (draft model) for 2–4× lower decode latency.

The trick has to preserve the distribution. Speculative sampling, introduced by Leviathan et al. (2023) and by Chen et al. concurrently, guarantees that the output sequence is identically distributed to what the big model would have produced on its own. No quality tradeoff. Just faster.

Four families of draft-verifier pairs dominate 2026 inference:

  1. Vanilla speculative (Leviathan 2023). Separate draft model (e.g., Llama 3 1B) + verifier (e.g., Llama 3 70B).
  2. Medusa (Cai 2024). Multiple decoding heads on the verifier predict positions t+1..t+k in parallel. No separate draft model.
  3. EAGLE family (Li 2024, 2025). Lightweight draft that reuses the verifier's hidden states; closer acceptance rate than vanilla; 3–4× typical.
  4. Lookahead decoding (Fu 2024). Jacobi iteration; no draft model required at all. Self-speculation. Niche but dependency-free.

Every major inference stack supports speculative decoding: vLLM, SGLang and TensorRT-LLM offer draft models and EAGLE drafts, and llama.cpp offers draft-model speculation. Whether it is switched on depends on the workload.

Idea 1 · The core algorithm

Given a verifier Mq​ and a cheaper draft Mp​:

  1. Let x1​…xk​ be the prefix already decoded.
  2. Draft: use Mp​ to autoregressively propose dk+1​,dk+2​,…,dk+N​ with draft probabilities p1​…pN​.
  3. Verify in parallel: run Mq​ once on x1​…xk​,dk+1​,…,dk+N​, getting verifier probabilities q1​…qN+1​ for positions k+1…k+N+1.
  4. Accept/reject each draft token left to right: for each i, accept with probability min(1,qi​(di​)/pi​(di​)).
  5. On first rejection at position j: sample tj​ from the "residual" distribution (qj​−pj​)+​ normalized. All drafts after j are discarded.
  6. On accepting all N: sample one extra token tN+1​ from qN+1​ (the free bonus token).

The residual distribution trick is the mathematical insight that keeps the output distributed exactly as if Mq​ had sampled from scratch.

Idea 2 · What determines speedup

Let α = expected acceptance rate per draft token. Let c = draft-to-verifier cost ratio. Per step:

  • Naive generation makes 1 big-model call per token.
  • Speculative makes 1 big-model call per (1−αN+1)/(1−α)≈1/(1−α) tokens when α is high.

Typical rule of thumb at α=0.75 and N=5: 3× fewer big-model calls. Draft cost is 5× cheap. Total wall-clock drops ~2.5×.

α depends on:

  • How well the draft approximates the verifier. Same family / same training data boosts α significantly.
  • Decoding strategy. Greedy draft against greedy verifier: high α. Temperature sampling: harder to match; acceptance drops.
  • Task type. Code and structured output accept more (predictable); free-form creative writing accepts less.

Idea 3 · Medusa — drafts without a draft model

Medusa replaces the draft model with extra output heads on the verifier. At position t:

shared trunk → hidden h_t
    ├── head_0: predict token at t+1  (standard LM head)
    ├── head_1: predict token at t+2
    ├── head_2: predict token at t+3
    ├── head_3: predict token at t+4

Each head outputs its own logits. At inference you sample from each head to get a candidate sequence, then verify with one forward pass using a tree-attention scheme that considers all candidate continuations at once.

Pros: no second model. Cons: adds trainable parameters; needs a supervised fine-tuning stage (~1B tokens); acceptance rate is a bit lower than vanilla speculative with a good draft.

Idea 4 · EAGLE — better draft by reusing hidden states

EAGLE-1/2/3 (Li et al., 2024–2025) makes the draft model a tiny transformer (typically 1 layer) that ingests the verifier's last-layer hidden states. Because the draft sees the verifier's feature representation, its predictions correlate strongly with the verifier's output distribution. Acceptance rates climb from ~0.6 (vanilla) to 0.85+. These are per-token rates on chat benchmarks, with a draft trained on matching chat data. On mixed production traffic, Phase 17 · 05 plans with 0.6 to 0.8 for EAGLE-3, and domain traffic can be lower.

EAGLE-2 (2024) made the tree of candidate continuations dynamic; EAGLE-3 (2025) fuses features from several of the verifier's layers and trains the draft on its own predictions, raising acceptance further. vLLM and SGLang support EAGLE drafts for common open models.

Idea 5 · The KV cache dance

Verification feeds N draft tokens into the verifier in one forward pass. This extends the verifier's KV cache by N entries. If some drafts are rejected, you must roll the cache back to the accepted prefix length.

Production implementations (vLLM's --speculative-config, TensorRT-LLM's LookaheadDecoder) handle this with scratch KV buffers. Write first, commit on acceptance. It's not conceptually hard, but it is fiddly.

The same idea as a formula

Why the output distribution is exactly the verifier's. Let the draft propose token x with probability p(x) and accept it with probability min(1,q(x)/p(x)). The chance of emitting x through acceptance is p(x)min(1,q(x)/p(x))=min(p(x),q(x)). A rejection happens with probability 1−∑y​min(p(y),q(y)), and then the token is drawn from the residual

r(x)=∑y​(q(y)−p(y))+​(q(x)−p(x))+​​,y∑​(q(y)−p(y))+​=1−y∑​min(p(y),q(y))

so the total probability of x is min(p(x),q(x))+(q(x)−p(x))+​=q(x). Nothing is approximated.

Acceptance rate. The probability of accepting one drafted token is α=∑x​min(p(x),q(x))=1−TV(p,q), one minus the total-variation distance between the two models. With greedy decoding, α is the chance both models pick the same token.

Tokens per verifier pass. With N drafts and the bonus token when all are accepted, the expected number of tokens per large-model pass is

E[tokens]=1+α+α2+⋯+αN=1−α1−αN+1​

Speed-up. If one draft pass costs a fraction c of a verifier pass, and verifying N+1 positions costs about as much as one position (true when the pass is memory-bound, as on GPUs):

speed-up≈(1−α)(1+Nc)1−αN+1​

When the verifier is compute-bound, as on a CPU, checking N+1 positions costs nearly N+1 times as much, and most of the gain disappears.

Worked example
Speed-ups by hand

α=0.8, N=4 drafts:

  • Tokens per verifier pass: (1−0.85)/(1−0.8)=(1−0.328)/0.2=3.36.
  • A 1B draft for a 70B verifier, c≈0.05: cost per round 1+4×0.05=1.2, speed-up 3.36/1.2=2.8×.
  • A draft that is 0.37 of the verifier (135M for 360M, the run below): cost per round 1+4×0.37=2.48, speed-up 1.35× at best, and less if verifying five positions costs more than one.
  • With α=0.5: (1−0.55)/0.5=1.94 tokens per pass; with c=0.05, 1.94/1.2=1.6×. Acceptance matters more than draft speed.

Step 1 · the rejection step

See code/main.py. We implement the core speculative-sampling algorithm (rejection step + residual distribution) with:

  • A "big model" that is a deterministic-softmax over a hand-coded distribution (so we can verify acceptance math analytically).
  • A "draft model" that is a perturbation of the big model.
  • An acceptance / rejection loop that produces the same marginal distribution as direct sampling.

def accept_or_reject(q_prob, p_prob, draft_token, u):
    ratio = q_prob / p_prob if p_prob > 0 else float("inf")
    return u < min(1.0, ratio)

u is a uniform random number. q_prob is the verifier's probability for the drafted token. p_prob is the draft model's probability. The Leviathan theorem is that this Bernoulli decision, followed by sampling from the residual on rejection, preserves the verifier's distribution exactly.

Step 2 · residual distribution

def residual_dist(q, p):
    raw = [max(0.0, qi - pi) for qi, pi in zip(q, p)]
    s = sum(raw)
    return [r / s for r in raw]

Subtract p from q element-wise, clamp negative values to zero, renormalize. Sample from this on any rejection.

Step 3 · one speculative step

def spec_step(prefix, q_model, p_model, N, rng):
    drafts = []
    p_probs = []
    ctx = list(prefix)
    for _ in range(N):
        p_dist = p_model(ctx)
        d = sample(p_dist, rng)
        drafts.append(d)
        p_probs.append(p_dist[d])
        ctx.append(d)

    q_dists = [q_model(prefix + drafts[:i]) for i in range(N + 1)]

    for i, d in enumerate(drafts):
        u = rng.random()
        q_prob = q_dists[i][d]
        p_prob = p_probs[i]
        if u < min(1.0, q_prob / p_prob if p_prob > 0 else float("inf")):
            prefix = prefix + [d]
        else:
            res = residual_dist(q_dists[i], p_model(prefix))
            prefix = prefix + [sample(res, rng)]
            return prefix
    prefix = prefix + [sample(q_dists[N], rng)]
    return prefix

Five accepted → one bonus → six tokens produced in one verifier pass.

Industry practice
What's current (2024–2026)
  • EAGLE-style drafts in serving engines. vLLM, SGLang and TensorRT-LLM support EAGLE-2/3 drafts, Medusa heads and separate draft models; providers publish EAGLE draft checkpoints for popular open models.
  • Drafting built into the model. DeepSeek-V3's multi-token prediction module can serve as a draft for speculative decoding, and several newer open models ship similar MTP heads.
  • Copying as drafting. Prompt-lookup and n-gram drafting (matching spans already in the prompt) speed up editing, RAG and code-refactoring tasks with no draft model at all; transformers supports it with prompt_lookup_num_tokens.

Sources: vLLM speculative decoding, EAGLE, SGLang, DeepSeek-V3 report, transformers assisted generation.

Recap
What to keep from this lesson
  • Draft N tokens cheaply, verify them in one pass, keep the agreeing prefix, use the verifier's correction at the first disagreement.
  • Accept with min(1,q/p) and resample from (q−p)+​: the output is exactly the verifier's distribution.
  • Tokens per pass =(1−αN+1)/(1−α), with α=∑min(p,q).
  • It pays when the verifier is memory-bound and the draft is cheap and well matched; code accepts more than prose.

Practice problem · Speculative decoding: accept, reject and resample

From the source repository: write the function, then press "Run the checks". They run as real Python in your browser (the first run loads Python, about 10 MB) and tell you which part is wrong and why. Hints open one at a time; the reference solution opens when every check passes.

hard35 minresearch

Speculative decoding makes a large model generate text faster with no change to its output. A small draft model proposes a few tokens. The large target model checks all of them in one forward pass. A rejection rule keeps the output distribution exactly equal to the distribution of the target model.

Task

Write four functions. In this problem, p is a distribution of the target model and q is a distribution of the draft model, over a vocabulary of V tokens.

  1. acceptance_rate(target, draft) returns α=∑x​min(p(x),q(x)). This is the probability that the rule accepts one draft token.
  2. residual_distribution(target, draft) returns norm(max(0,p−q)): the elementwise maximum of 0 and p−q, divided by its sum. When that sum is 0, return a copy of target as a float array.
  3. speculative_step(target_probs, draft_probs, draft_tokens, rng) runs the verify step for γ draft tokens and returns the output tokens.
  4. expected_tokens(alpha, gamma) returns the expected number of tokens of one step, (1−αγ+1)/(1−α). For α=1 it returns γ+1.

speculative_step does these steps. The order of the random draws is part of the task.

  1. For each draft token xi​, with i from 0 to γ−1, let pi​ be row i of target_probs and qi​ be row i of draft_probs.
  2. Draw u = rng.random(). When u<min(1,pi​(xi​)/qi​(xi​)), accept xi​, add it to the output, and go to the next draft token.
  3. Otherwise, draw one token with rng.choice(V, p=r), where r is the residual distribution of pi​ and qi​. Add it to the output and return the output.
  4. When all γ draft tokens are accepted, draw one bonus token with rng.choice(V, p=p_gamma) from the last row of target_probs. Add it and return the output.

Input and output

Name Type Shape Meaning
target float array (V,) a target distribution p
draft float array (V,) a draft distribution q
target_probs float array (gamma + 1, V) the target distributions at each draft position and one more
draft_probs float array (gamma, V) the draft distributions at each draft position
draft_tokens list of int length gamma the tokens that the draft model sampled
rng np.random.Generator the source of all random draws

  • acceptance_rate returns a Python float.
  • residual_distribution returns a float array of shape (V,) that sums to 1.
  • speculative_step returns a list of Python ints of length from 1 to gamma + 1.
  • expected_tokens returns a Python float.

Constraints

  • 2 <= V <= 64 and 0 <= gamma <= 8. Each row of probabilities sums to 1.
  • Each draft token has qi​(xi​)>0, because the draft model sampled it. The target probability pi​(xi​) can be 0.
  • Use only rng.random() and rng.choice(V, p=...), in the order above. Make no other draws.
  • Do not change the input arrays or the list of draft tokens.
  • Use numpy only.

Common mistakes the checks catch
  • Accepts with probability min(1, q / p), the draft over the target.
  • Computes alpha as the mean over the vocabulary of min(1, p / q), not the sum of min(p, q).
  • Uses alpha to the power gamma, not gamma + 1, so it forgets the bonus token.
  • Returns after full acceptance without the bonus token from the last target row.
  • Samples from the target distribution after a rejection, not from the residual.
  • Normalizes the absolute value of p - q in place of max(0, p - q).
Hint 1

Write acceptance_rate and residual_distribution first. Each one is a single numpy expression and a sum.

Hint 2

In the step, read the two probabilities of the draft token: target_probs[i][token] and draft_probs[i][token]. The ratio p/q can be larger than 1. Then the token is always accepted.

Hint 3

After a rejection, sample from the residual, not from p. The draft already proposed the tokens where q>p too often. The residual adds probability only where p>q.

Hint 4

When the loop ends with no rejection, the target model has one more row of probabilities, at index gamma. Sample the bonus token from that row. The number of tokens per step is then from 1 to gamma + 1.

Reference solution and notes
import numpy as np


def acceptance_rate(target, draft):
    return float(np.sum(np.minimum(target, draft)))


def residual_distribution(target, draft):
    raw = np.maximum(0.0, np.asarray(target, dtype=float) - np.asarray(draft, dtype=float))
    total = np.sum(raw)
    if total == 0.0:
        return np.array(target, dtype=float)
    return raw / total


def speculative_step(target_probs, draft_probs, draft_tokens, rng):
    out = []
    for i, token in enumerate(draft_tokens):
        p = target_probs[i][token]
        q = draft_probs[i][token]
        if rng.random() < min(1.0, p / q):
            out.append(int(token))
        else:
            residual = residual_distribution(target_probs[i], draft_probs[i])
            out.append(int(rng.choice(len(residual), p=residual)))
            return out
    last = target_probs[len(draft_tokens)]
    out.append(int(rng.choice(len(last), p=last)))
    return out


def expected_tokens(alpha, gamma):
    if alpha >= 1.0:
        return float(gamma + 1)
    return float((1.0 - alpha ** (gamma + 1)) / (1.0 - alpha))

Why the output equals the target

Take one draft token. Token x comes out in two ways. The draft proposes x and the rule accepts it, with probability q(x)min(1,p(x)/q(x))=min(p(x),q(x)). Or the rule rejects the draft token, with probability 1−α, and the residual gives x. The residual is max(0,p(x)−q(x))/(1−α), because the sum of max(0,p−q) is 1−α. The sum of the two terms is min(p,q)+max(0,p−q)=p(x). The check on the exact distribution tests this identity.

The speed

Each step calls the target model once and gives from 1 to γ+1 tokens. With independent acceptances at rate α, the mean is (1−αγ+1)/(1−α). A draft that is close to the target gives a high α. The paper shows that α is also 1−21​∥p−q∥1​, one minus the total variation distance.

The names of p and q

This problem uses the letters of the paper: p for the target and q for the draft. The lesson code uses the opposite letters. The rule is the same.

Where this goes next

The lessons on Medusa and EAGLE replace the separate draft model with extra heads on the target model. The verify step stays the same.

# Speculative Decoding Picker

Help an engineer choose between vanilla speculative, Medusa, EAGLE, or lookahead decoding, and tune `N` (draft length) for a specific workload.

## Inputs to gather

1. **Verifier model** — which LLM produces final output. Size matters (draft cost must be < verifier cost for speedup).
2. **Workload type** — code, chat, structured output, summarization. Determines acceptance rate.
3. **Sampling strategy** — greedy, low-T, high-T, beam. High-T sampling degrades acceptance.
4. **Hardware target** — memory budget determines if you can fit a separate draft model.
5. **Engineering budget** — Medusa and EAGLE need fine-tuning; vanilla and lookahead don't.
6. **Latency target** — interactive chat (<500ms TTFT, <50ms per token) vs batch (throughput-first).

## Decision rules

- **Quick start, no training**: vanilla draft with a same-family 1B–3B model. 2× typical.
- **You can fine-tune**: EAGLE-2 or EAGLE-3 using the verifier's hidden states. 3–4× typical.
- **You can fine-tune but can't run two models**: Medusa (extra heads on verifier). 2–3×.
- **No training budget, no draft model available**: lookahead decoding. 1.3–1.6×.
- **Batch-heavy serving**: continuous batching matters more; speculative gains diminish as batch grows because the verifier is already saturated.
- **High temperature or stochastic sampling**: acceptance drops sharply. Consider lower N (2–3) or disabling.
- **Structured output (JSON, code)**: acceptance is high. Push N to 7+ for max speedup.

## Tuning

- **N (draft length)**: start at 5. Measure acceptance. If α > 0.9, push to 7. If α < 0.6, drop to 3.
- **Draft temperature**: match the verifier's temperature. Mismatched draft sampling loses α.
- **Tree depth (EAGLE-2 / Medusa)**: 3–5 branches; wider trees help only at α > 0.8.
- **Draft model size**: smallest that hits α > 0.7. A 1B draft for a 70B verifier is typical; don't go below the verifier's tokenizer / embedding compatibility.

## Always flag

- Check that draft and verifier share the tokenizer. Different BPE splits break speculative guarantees.
- Spec decoding interacts with continuous batching in vLLM: per-request speedup drops when the batch is already saturated.
- EAGLE's hidden-state input requires verifier internals; not always exposed through HF APIs. Prefer vLLM or SGLang runtimes.
- Medusa heads need a supervised fine-tune on the verifier's own outputs. Data-gathering step is often the dominant cost.

## Output format

Return:

1. **Recommendation** — one strategy name and tuning parameters (e.g. "EAGLE-2, N=5, tree_depth=4").
2. **Expected speedup** — with explicit α assumption.
3. **Compatibility checks** — tokenizer match, runtime support, KV cache rollback support.
4. **Fallback plan** — if the primary strategy underperforms, what to try next.
5. **Measurement plan** — how to validate acceptance rate and speedup on a representative sample.

  2. Medium. Plot speedup (tokens per big-model forward) as a function of N for α=0.5,0.7,0.85. Identify the optimal N for each α. (Hint: expected tokens per verify call = (1−αN+1)/(1−α).)

Solutions

SolutionP1 · Same text, hardly faster here

Same text: greedy speculative decoding must reproduce the target's greedy output token for token, and it does. Faster: hardly, about 7.5 seconds against 8.8, even though the target runs only 10 times instead of 96. The draft costs about a third of the target per pass and runs for every guessed token, and on a CPU checking ten positions costs nearly ten times one, so the saved target passes are paid back in other work. On a GPU, where one large-model pass costs about the same for one position or ten and the draft is tiny, the same 10-versus-96 ratio becomes a real speed-up.

SolutionB1 · Double-counting the draft's favourites

After a rejection, sampling from q itself gives every token two chances: once through acceptance, with probability min(p,q), and again through the resample. The total probability of x becomes min(p(x),q(x))+(1−α)q(x), which is not q(x): tokens the draft over-proposes (p>q) gain probability, because their acceptance share q(x) is added to the resample share. The residual (q−p)+​ gives mass only to tokens the draft under-proposes, exactly compensating. The chi-square test from Step 5 detects the bias on a few thousand samples.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Read the codeRead this toy speculative step from the lesson. q_model is the verifier and p_model is the draft; each returns a probability vector for the next token given a prefix. python def spec_step(prefix, q_model, p_model, N, rng): drafts, p_probs = [], [] ctx = list(prefix) for _ in range(N): p_dist = p_model(ctx) d = sample(p_dist, rng) drafts.append(d) p_probs.append(p_dist[d]) ctx.append(d) q_dists = [q_model(prefix + drafts[:i]) for i in range(N + 1)] for i, d in enumerate(drafts): u = rng.random() if u < min(1.0, q_dists[i][d] / p_probs[i]): prefix = prefix + [d] else: res = residual_dist(q_dists[i], p_model(prefix)) prefix = prefix + [sample(res, rng)] return prefix return prefix + [sample(q_dists[N], rng)] Why does q_dists hold N plus 1 entries, what happens when the first draft token fails the test, and why does the residual use p_model(prefix) rather than p_probs[i]?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The verifier gives a distribution at every drafted position and one more, N plus 1 in total, because when every draft is accepted the extra distribution supplies a bonus token at no extra verifier cost. At the first rejection at position i the code samples from the residual, the positive part of the verifier's distribution minus the draft's, renormalized, appends that token and returns, so every later draft is discarded. The residual needs the draft's whole distribution at that position, a vector, and p_probs[i] kept only the scalar probability of the token that was drafted.

Why the rule is exact.

Accepting a drafted token with probability min(1, q(d) / p(d)) and otherwise sampling from (q - p) clamped at zero and renormalized gives samples distributed exactly as q. The theorem holds however poor p is: a bad draft rejects more often, and the output distribution does not move. That is the only reason the method is allowed in production. It is a latency optimization with no quality trade.

Why N plus 1 verifier distributions.

The verifier is queried on the prefix plus the first i drafts for i from zero to N. The first N distributions judge the drafts. The last one is the verifier's own next-token distribution after all N drafts; if everything was accepted it is free, and the step emits N plus 1 tokens from one verifier pass. In the toy the N plus 1 calls stand for a single batched forward pass over the prefix plus the drafts.

The rejection branch.

Return after the first rejection. Positions after it were drafted on a context that is now known to be wrong, so their verifier distributions are not for the sequence that is being generated. The step always produces at least one token, the residual sample, and at most N plus 1.

The residual needs a vector.

residual_dist(q, p) subtracts the two distributions element by element, clamps negatives to zero and renormalizes. p_probs[i] is one number, the draft's probability of the drafted token, enough for the acceptance test and not for the residual. The call p_model(prefix) recomputes the draft's full distribution at the position being corrected; in a real implementation the draft's distributions are kept from the drafting loop instead of being recomputed.

The greedy case.

At temperature zero the rule collapses to a comparison: accept if the drafted token equals the verifier's argmax, otherwise emit the argmax and stop.

How you would test it.

Run the step 10,000 times and compare the histogram of produced tokens with direct samples from q; a chi-square test passes within sampling error. Then perturb p away from q and watch the acceptance rate fall while the histogram stays put.

Plausible wrong answers.

  • "Accept a draft whenever the verifier gives it a probability above a threshold." A threshold changes the output distribution; the ratio test with the residual is what keeps it exact.
  • "On a rejection, resample from the verifier's distribution at that position." That over-weights tokens the draft already favored; the residual removes exactly that mass.
  • "Drop the bonus token to be safe." It is a sample from the verifier's own distribution and costs nothing; dropping it wastes a token per step.

Follow-ups an interviewer may ask.

  • (level 3) p_probs[i] is zero and the code divides by it. Can that happen? Expected: no, the token was sampled from p so its probability is positive; the production version still guards the division and accepts when p is zero.
  • (level 3) When does residual_dist divide by zero, and what should it return? Expected: when q is nowhere larger than p, which means the two are equal; return q itself.
  • (level 4) What does the single batched verifier pass do to the verifier's stored keys and values? Expected: it extends them by N entries, and a rejection at position j must roll the logical length back to the accepted prefix plus the correction.
  • (level 4) How many tokens does one step emit at minimum and at maximum? Expected: one, the residual sample at an immediate rejection; N plus 1 when every draft is accepted and the bonus token is sampled.

Weigh a trade-offYour creative-writing product samples at a high temperature and speculative decoding gives it no speedup at all, while the same setup flies on code completion. Explain the difference, and describe what the acceptance test becomes at temperature zero.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Acceptance depends on how often the verifier agrees with what the draft sampled. At a high temperature the target distribution is flat, the draft's samples spread across many tokens, and the acceptance ratio of verifier to draft probability falls toward one over the vocabulary size, so almost every draft is rejected and the draft's cost is paid for nothing. Code and structured output are predictable, so acceptance climbs above 0.9. At temperature zero the rule becomes a comparison: accept if the drafted token equals the verifier's most likely token, otherwise emit that token and stop.

Why temperature is the lever.

The acceptance test is u < min(1, q(d) / p(d)). When both distributions are peaked on the same token the ratio is near one and the draft is accepted. Raise the temperature and both distributions flatten: the draft now samples tokens that the verifier gives little probability, the ratios shrink, and the rejections pile up. The lesson's exercise runs the loop at a temperature of 1.5 to show the collapse, where the algorithm becomes slower than plain decoding because the draft overhead stays and the accepted tokens vanish.

Why the task matters.

Workload Measured speedup in the lesson
chat 2 to 3 times
code generation 3 to 5 times
creative writing near zero

Code and structured output have a highly predictable next token, so even an imperfect draft agrees with the verifier most of the time; the EAGLE-3 lesson puts acceptance above 0.9 on such output. Open-ended prose at a high temperature has many acceptable continuations, and the draft rarely picks the one the verifier would.

The greedy case.

With temperature zero both models are deterministic. The test reduces to argmax(q) == d: accept on a match, otherwise output argmax(q) and stop. The residual distribution is not needed, because the verifier's choice is a single token.

What to do about it.

  • Switch speculation off per request when the temperature is high, or route such requests to a plain decode pool; the EAGLE-3 lesson lists temperature-aware switching as a tuning knob.
  • Do not spend the draft on very short outputs of 1 to 5 tokens either; the overhead dominates.
  • Measure the acceptance rate per product surface and keep speculation where it pays; the production lesson's floor is about 0.55 at high concurrency.

Plausible wrong answers.

  • "Lower the temperature so speculation works." The product chose the temperature for a reason; change the decoding path for those requests, not the product.
  • "The draft is too small; use a bigger draft." Size is not the issue when the target distribution is flat; a larger draft still cannot guess which of many acceptable tokens the verifier samples.
  • "At high temperature speculation changes the output." The rejection rule keeps the output distribution exact at any temperature; what changes is the speed.

Follow-ups an interviewer may ask.

  • (level 2) What does the acceptance ratio become when the draft and the verifier agree exactly? Expected: one, so every draft is accepted and each pass yields the full draft plus the bonus token.
  • (level 3) May the draft sample at a different temperature from the verifier? Expected: yes, as long as p is the distribution the draft actually sampled from; the output still follows the verifier's distribution, but a mismatch lowers acceptance.
  • (level 3) How would you implement the switch in a serving layer? Expected: read the request's temperature and output length, and disable speculation above a temperature threshold or below a length threshold, with the thresholds set from measured acceptance.
  • (level 4) Why is the loss worse at high concurrency than the formula suggests? Expected: a rejected draft costs a verify and a re-roll that serialize under a full batch, and the batch already fills the memory bandwidth that speculation was exploiting, so the tail latency suffers.
