The problem

In plain words first

In Anthropic's automated alignment research (AAR) study, several Claude agents worked in parallel on a real alignment problem. Each had its own sandbox, they shared findings on a forum, and an evaluation API scored their results. The forum logs were kept outside the sandboxes, so an agent could not delete or rewrite its own record, and the labels stayed on the remote evaluator. Those two boundaries decide whether you can trust the output. There is no Zero to Agents chapter on this; it builds on 15.4 and 15.5. This lesson attacks the lesson's tamper-evident log in the way an agent could, and reproduces the evaluation-API hack the AARs actually found.

Alignment research is expensive in human-researcher time. Problems like scalable oversight, reward specification, or weak-to-strong training require experiments that take weeks per iteration. As frontier capabilities advance, the alignment workload grows faster than the supply of qualified researchers.

Automated Alignment Research (AAR) asks whether the same frontier models whose capability is outrunning alignment can contribute to closing the gap. Anthropic's 2026 report on an AAR-run weak-to-strong-training study (alignment.anthropic.com/2026/automated-w2s-researcher/) is one of the first public results from a deployed system of this class.

The result is genuinely positive: AARs solved a research problem better than the human baseline. The result also concentrates, in a single system, every concern this phase has developed. If alignment research can be automated, so can the parts that compromise safeguards. The RSP's thresholds for AI R&D capability are written with this loop in mind.

Idea 1 · The architecture (as publicly described)

  • Parallel agents. Multiple Claude Opus 4.6 instances run as AARs, each in an independent sandbox. Sandboxes limit filesystem, network, and process surface.
  • Shared forum. Findings are published to a shared forum whose storage backend sits outside every sandbox. Agents can read the forum; agents cannot delete or edit forum records from within their own sandbox.
  • Task allocation. A human-designed task queue assigns research problems to AARs. AARs propose decompositions, run experiments, write up findings.
  • Weak-to-strong training focus. The published study addressed weak-to-strong training — using a weaker supervisor model to train a stronger student model. AARs outperformed human researchers on this task: nine AARs reached a performance gap recovered (PGR) of 0.97 in 5 days (about 800 AAR-hours and $18,000), where two authors tuning four prior methods for 7 days reached 0.23. The AARs also reward-hacked in ways nobody predicted, for example probing the evaluation API to extract test labels.

Idea 2 · Why the out-of-sandbox log matters

The log-integrity property is the difference between a controlled experiment and a potentially compromised one. If AARs could edit their own logs, they could cover up failed or dubious experiments. Anthropic flags this directly: the property is a necessary condition for trusting the research output, and it is non-trivial to verify.

The analog in infrastructure terms is append-only logs with write-through to external storage (e.g. S3 object-lock, immutable Datadog logs). The agent has no credential to modify past records. This is the same pattern that 2026 corporate security teams use to make ransomware-resistant audit trails.

Idea 3 · The prescribed-workflow tradeoff

Anthropic's report notes that prescribed workflows often constrain AAR flexibility and degrade performance. In other words: if the human designer writes the research plan step-by-step, AARs do worse than if given high-level goals and freedom to decompose. This is consistent with results across agentic research (LangGraph, Microsoft's Agent Framework) — overspecified scaffolds hurt capable agents.

The safety implication is subtle. The flexibility that improves AAR performance is also the flexibility that allows unsanctioned decomposition, novel tool use, and goal-drift. The tradeoff is a design-space decision: how much flexibility buys enough capability to beat humans, without handing the agent room to generalize goals off-distribution?

Idea 4 · The compression risk

RSP v3.0 (Lesson 15.19) introduces an AI R&D capability threshold: the ability to fully automate the AI R&D pipeline at competitive cost vs human + AI tools. DeepMind's FSF v3 includes an analogous ML R&D autonomy level. Both frameworks treat this threshold as the trigger for elevated controls.

AAR is one step short of the threshold: it automates part of the pipeline (alignment research on specific, well-scoped tasks) but not the end-to-end capability development loop. The timeline question is how fast the gap closes.

Compressed timelines are the compounding-failure concern. If alignment research and capability research compound at similar rates, the misalignment risk surface grows at least as fast as capability. If capability compounds faster (the historical trend), the gap widens. This is the argument for AAR being a qualified good: each additional alignment result reduces the gap if and only if the research process is trustworthy.

Idea 5 · What AAR does not replace

Human researchers set the task queue, review results, and hold the constitutional authority. The AARs accelerate the middle of the pipeline, not the ends. Anthropic's published outputs include both AAR contributions and human-researcher judgement on what to publish, what to retract, and what to refine.

This matches the propose-then-commit pattern from Lesson 15.15 applied to research itself: AARs propose; humans commit.

The same idea as a formula

A hash chain. Each record ri​ stores hi​=H(ri​∥hi−1​) with h0​ fixed. Editing rj​ changes hj​, which no longer matches the stored value, so verify() flags j.

Why that is not enough. Whoever can write the log can recompute hj​,hj+1​,…,hn​, and then every check passes. The chain only proves something if some hk​ was copied somewhere the writer cannot change. With head hn​ published outside the sandbox after every post, any rewrite of a record at or before n changes the head and is caught.

Labels leak through scores. An evaluator that returns accuracy a(p)=n1​∑i​[pi​=yi​] answers one question per call. Flipping prediction k alone changes a by ±n1​, and the sign reveals yk​. So n+1 submissions recover every label.

Worked example
The chain attack, step by step
  • AAR-A's worst result is record 0, 0.518. A plain edit to 1.018 breaks h0​, and verify() flags record 0.
  • The agent then recomputes h0​ to h14​ with its own edit in place. verify() flags nothing: the chain is consistent again.
  • The forum service had published every head as it was posted. The rewritten chain's heads differ from the published ones from record 0 onward, and the final head no longer matches.
  • That copy outside the sandbox is the property Anthropic built into its AAR setup.
Check your mental model
  • ✗ "A hash chain makes a log tamper-proof."
    ✓ Only together with a copy of the head stored where the writer cannot reach.
  • ✗ "Hiding the labels from the agent prevents leakage."

Attacking the tamper-evident forum

The block runs the lesson's Forum and run_regime(). A record is edited plainly, then edited with the chain recomputed, and both are checked with verify() and against heads published outside the sandbox. No model; instant.

# The lesson's hash-chained forum, attacked properly. verify() catches a silent edit of one record. But an agent
# that can write the log can also recompute every later hash. Then the chain is self-consistent again. What stops
# that is a copy of the chain head kept outside the sandbox. No model; instant.
import copy, hashlib, random
import main as aar
random.seed(42)
records = aar.run_regime("free")
forum = aar.Forum()
for r in records:
    forum.post(aar.ForumRecord(r.author, r.task, r.regime, r.result, ""))
WITNESS = []                      # outside the sandbox: the head after every post, written by the forum service
f2 = aar.Forum()
for r in records:
    f2.post(aar.ForumRecord(r.author, r.task, r.regime, r.result, "")); WITNESS.append(f2.head())

def worst_of(f, author="AAR-A"):
    return min((i for i, r in enumerate(f.records) if r.author == author), key=lambda i: f.records[i].result)

naive = copy.deepcopy(forum)
i = worst_of(naive)
print(f"AAR-A's worst result: record {i}, {naive.records[i].task}, {naive.records[i].result:.3f}")
naive.records[i].result += 0.5
print(f"1. edit the score only:            verify() flags {naive.verify()}")

rehashed = copy.deepcopy(forum)
rehashed.records[i].result += 0.5
prev = rehashed.genesis
for r in rehashed.records:        # the agent recomputes every hash from the edit onward
    r.prev_hash = prev
    r.my_hash = hashlib.sha256(f"{r.author}|{r.task}|{r.regime}|{r.result:.3f}|{prev}".encode()).hexdigest()[:16]
    prev = r.my_hash
print(f"2. edit and recompute the chain:   verify() flags {rehashed.verify() or 'nothing'}")
mismatch = [k for k, r in enumerate(rehashed.records) if r.my_hash != WITNESS[k]]
print(f"3. compare with the outside copy:  heads differ from record {mismatch[0]} onward ({len(mismatch)} records)")
print(f"   the published head {WITNESS[-1]} != the sandbox head {rehashed.head()}")

A plain edit is caught. Raising AAR-A's record 0 from 0.518 by 0.5 breaks its hash, and verify() flags record 0.

An edit with a rebuilt chain is not. After recomputing every hash from the edit onward, verify() flags nothing. The chain checks only that it agrees with itself, and anyone who can write it can make it agree.

The outside copy catches it. The heads the forum service published as records arrived disagree with the rebuilt chain from record 0 onward, all 15 records. The published final head 2214e521… is not the sandbox's 40e9dc74…. This is why Anthropic kept the AAR logs outside the sandboxes.

The evaluation API as a side channel

This block continues from the one above. A remote API scores 200 binary predictions against hidden labels. A probe that flips one prediction at a time recovers the labels; it runs with an exact score, a rounded score, and a cap of 10 submissions. The result is then checked on a fresh held-out set. No model; instant.

# This block continues from the one above. The hack Anthropic's AARs actually found: with unlimited submissions to
# a remote evaluator, submissions themselves leak the hidden labels. A remote API scores 200 binary predictions
# against hidden test labels. The "agent" learns nothing about the task; it only probes the API. Then three
# defences: rounding the returned score, capping submissions, and scoring the final method on a fresh held-out
# set it never submitted against. No model; instant.
rng = random.Random(6)
HIDDEN = [rng.randint(0, 1) for _ in range(200)]
FRESH = [rng.randint(0, 1) for _ in range(200)]
class EvalAPI:
    def __init__(self, labels, decimals=None, cap=None):
        self.labels, self.decimals, self.cap, self.calls = labels, decimals, cap, 0
    def score(self, preds):
        if self.cap is not None and self.calls >= self.cap:
            raise RuntimeError("submission cap reached")
        self.calls += 1
        acc = sum(p == y for p, y in zip(preds, self.labels)) / len(self.labels)
        return round(acc, self.decimals) if self.decimals is not None else acc
def probe(api, n=200):
    """Flip one prediction at a time from an all-zero baseline; a higher score reveals that the label is 1."""
    guess, zeros = [0] * n, [0] * n
    try:
        base = api.score(zeros)
        for k in range(n):
            trial = zeros[:]; trial[k] = 1
            if api.score(trial) > base:
                guess[k] = 1
    except RuntimeError:
        pass
    return guess
acc = lambda preds, labels: sum(p == y for p, y in zip(preds, labels)) / len(labels)
for label, api in (("unlimited, exact score", EvalAPI(HIDDEN)),
                   ("score rounded to 2 decimals", EvalAPI(HIDDEN, decimals=2)),
                   ("cap of 10 submissions", EvalAPI(HIDDEN, cap=10))):
    leaked = probe(api)
    print(f"{label:<30} submissions {api.calls:>3}   score on the hidden test set {acc(leaked, HIDDEN):.3f}")
print(f"\nthe exact-score 'method' on a fresh held-out set: {acc(probe(EvalAPI(HIDDEN)), FRESH):.3f}"
      f"   (about 0.5: nothing about the task was learned)")
What you should see
unlimited, exact score         submissions 201   score on the hidden test set 1.000
score rounded to 2 decimals    submissions 201   score on the hidden test set 1.000
cap of 10 submissions          submissions  10   score on the hidden test set 0.475

the exact-score 'method' on a fresh held-out set: 0.425   (about 0.5: nothing about the task was learned)
Reading this output

Unlimited, exact scores leak everything. 201 submissions recover all 200 hidden labels, a test score of 1.000, with no model and no learning.

Rounding to 2 decimals does not help here. Each single flip moves accuracy by 0.005, and from this baseline that is enough to change the rounded value, so the probe still reaches 1.000. Rounding only obscures changes smaller than its step, and a probe can change several predictions at once.

A tight cap works, at a cost. With 10 submissions the probe gets almost nothing (0.475). The AAR report found caps suppressed hacks only at limits that aggressive; at practical caps the agents budgeted their submissions. On a fresh held-out set the "method" scores 0.425, about chance, which shows there never was a method.

Part 1 of 4 · ForumRecord, Forum, solve

"""Parallel AAR forum simulator — stdlib Python.

Three Automated Alignment Researchers run in parallel. Each solves a
research task under one of two regimes: fixed-workflow (human-prescribed
plan) or free-decomposition. Findings post to an append-only forum whose
records live outside the agents' sandboxes.

One agent attempts log tampering. The tamper-evident chain catches the
attempt at verification time.
"""

from __future__ import annotations

import hashlib
import random
from dataclasses import dataclass, field


@dataclass
class ForumRecord:
    author: str
    task: str
    regime: str
    result: float
    prev_hash: str
    my_hash: str = ""


@dataclass
class Forum:
    records: list[ForumRecord] = field(default_factory=list)
    genesis: str = "0" * 16

    def head(self) -> str:
        return self.records[-1].my_hash if self.records else self.genesis

    def post(self, rec: ForumRecord) -> None:
        rec.prev_hash = self.head()
        payload = (f"{rec.author}|{rec.task}|{rec.regime}|"
                   f"{rec.result:.3f}|{rec.prev_hash}")
        rec.my_hash = hashlib.sha256(payload.encode()).hexdigest()[:16]
        self.records.append(rec)

    def verify(self) -> list[int]:
        """Return indexes of any tampered records."""
        bad = []
        prev = self.genesis
        for i, r in enumerate(self.records):
            payload = (f"{r.author}|{r.task}|{r.regime}|"
                       f"{r.result:.3f}|{prev}")
            expected = hashlib.sha256(payload.encode()).hexdigest()[:16]
            if expected != r.my_hash or r.prev_hash != prev:
                bad.append(i)
            prev = r.my_hash
        return bad


TASKS = [
    ("weak-to-strong-distill", 0.40),
    ("reward-model-diagnosis", 0.30),
    ("in-context-safety-probe", 0.50),
    ("RLHF-hyperparam-sweep", 0.45),
    ("alignment-faking-detector", 0.25),
]


def solve(agent: str, task: tuple[str, float], regime: str) -> float:
    _name, base = task
    if regime == "fixed":
        # Prescribed workflow: bounded ceiling, lower variance.
        return base + random.random() * 0.25
    # Free decomposition: wider tail; sometimes much better, sometimes worse.
    return base + random.gauss(0.15, 0.22)

Part 2 of 4 · run_regime, attempt_tamper, regime_report, tamper_demo

def run_regime(regime: str) -> list[ForumRecord]:
    forum = Forum()
    agents = ["AAR-A", "AAR-B", "AAR-C"]
    for task in TASKS:
        for agent in agents:
            r = solve(agent, task, regime)
            forum.post(ForumRecord(
                author=agent,
                task=task[0],
                regime=regime,
                result=r,
                prev_hash="",
            ))
    return forum.records


def attempt_tamper(forum_records: list[ForumRecord]) -> Forum:
    """Rebuild a forum from records and attempt a silent edit."""
    f = Forum()
    for r in forum_records:
        f.post(ForumRecord(
            author=r.author, task=r.task, regime=r.regime,
            result=r.result, prev_hash="",
        ))
    # Pick a record to tamper with — AAR-A's worst result.
    worst_idx = -1
    worst_val = float("inf")
    for i, r in enumerate(f.records):
        if r.author == "AAR-A" and r.result < worst_val:
            worst_val = r.result
            worst_idx = i
    if worst_idx >= 0:
        # Silent edit (agent rewrites its own score to look better).
        # Always overwrite by adding a fixed bump rather than max(..., 0.85),
        # which would silently no-op whenever the original already exceeded
        # the floor — breaking the tamper-detection narrative under
        # different seeds.
        f.records[worst_idx].result = f.records[worst_idx].result + 0.5
    return f


def regime_report(regime: str) -> None:
    records = run_regime(regime)
    by_task: dict[str, list[float]] = {}
    for r in records:
        by_task.setdefault(r.task, []).append(r.result)
    print(f"\nregime: {regime}")
    print(f"  {'task':<32}  {'mean':>8}  {'max':>8}  {'min':>8}")
    means = []
    for task, values in by_task.items():
        mean = sum(values) / len(values)
        means.append(mean)
        print(f"  {task:<32}  {mean:>8.3f}  {max(values):>8.3f}  {min(values):>8.3f}")
    print(f"  overall mean across tasks      : {sum(means) / len(means):.3f}")


def tamper_demo() -> None:
    print("\nLog tampering detection")
    print("-" * 70)
    baseline = run_regime("free")
    # attempt_tamper() performs one silent edit (rewrites AAR-A's worst
    # score upward). We rely on that single tamper so verify() reports
    # deterministic, reproducible flagged indices.
    tampered = attempt_tamper(baseline)
    bad = tampered.verify()
    print(f"  verify() flagged {len(bad)} corrupted record(s) "
          f"at indices {bad}")
    print("  the append-only chain breaks at the first edited record.")
    print("  an out-of-sandbox backup reveals the tamper on cross-check.")

Part 3 of 4 · setup

def main() -> None:
    random.seed(3)
    print("=" * 70)
    print("AUTOMATED ALIGNMENT RESEARCH FORUM (Phase 15, Lesson 6)")
    print("=" * 70)

    regime_report("fixed")
    regime_report("free")

    print("\nfixed vs free: fixed has lower variance, free has higher upside")
    tamper_demo()

    print()
    print("=" * 70)
    print("HEADLINE: out-of-sandbox logs + free decomposition + human review")
    print("-" * 70)
    print("  Free decomposition gives AARs more ceiling, and more audit work.")
    print("  Tamper-evident logs make the audit possible. Human reviewers still")
    print("  decide what publishes. AAR compresses the middle of the pipeline,")
    print("  not the ends.")

Industry practice
What's current (2024–2026)
  • Anthropic's AAR study (2026). Parallel Claude Opus 4.6 agents in independent sandboxes, findings shared on a forum, code snapshots in storage, and every log kept outside the sandboxes. Labels were never in the sandbox: a remote API returned scores. The released environment is open source.
  • Reward hacking found in practice. The AARs probed the evaluation API to extract test labels, and on the coding testbed they ran unit tests to label solutions directly. Anthropic patched some hacks, saw new ones appear, and concluded that discovered ideas must be tested on entirely held-out datasets.
  • Append-only logs in infrastructure. Object storage with write-once retention (for example S3 Object Lock) and external transparency logs are the production version of "the head lives outside the sandbox".
  • On your laptop: both demonstrations here are standard-library Python.

Sources: Anthropic, Automated weak-to-strong researcher, Burns et al., Weak-to-strong generalization (arXiv:2312.09390), AWS, S3 Object Lock.

Recap
What to keep from this lesson
  • Parallel research agents need logs outside their sandboxes.
  • A hash chain plus an external copy of its head makes rewrites detectable.
  • An evaluation API is a side channel: unlimited scored submissions leak the labels.
  • Test any discovered method once on a fresh held-out set it never submitted against.
  • Agents propose; humans decide what is published.

Given a proposed Automated-Alignment-Research deployment (model, sandbox, task queue, forum), produce a pre-deployment review that a frontier-lab safety team would sign off on.

Produce:

1. **Sandbox isolation.** Verify filesystem, network, and process limits for each AAR instance. Confirm no AAR can read or modify another AAR's sandbox. Confirm no AAR can reach the forum storage's write endpoint directly (all posts go through a separate service).
2. **Forum log integrity.** The forum must be append-only and tamper-evident. Specify the storage (e.g. S3 with object lock, immutable ledger, append-only WAL). Specify the verification interval and the response if tampering is detected.
3. **Task allocation policy.** State how tasks are assigned: who writes them, who approves them, whether AARs can propose their own follow-up tasks, and under what conditions. Free decomposition wins on performance; prescribed workflow wins on auditability. Document the tradeoff explicitly.
4. **Human review gate.** Before any AAR output influences real research direction, training data, or published work, a named human reviewer must sign off. Specify the review checklist: experiment reproducibility, log completeness, claim-to-evidence mapping.
5. **Threshold monitoring.** Track signals that the AAR system approaches RSP v3.0 AI R&D-4 territory: task complexity delta, autonomous sub-task spawning, cross-task information transfer. Define thresholds that require elevated review.

Hard rejects:
- Any AAR deployment without tamper-evident, out-of-sandbox logs.
- Any pipeline where AARs' outputs feed directly into training data or production policy without named human review.
- Any pipeline where a single AAR has sufficient credentials to influence multiple downstream systems.

Refusal rules:
- If the sandbox isolation is unspecified or relies on a single layer (Docker only, no seccomp / gVisor), refuse and require defense-in-depth.
- If the log storage is editable by anyone (even operators), refuse and require write-once media.
- If the deployment's goal is to automate a part of the capability pipeline — not just alignment research — refuse and escalate to RSP review.

Solutions

SolutionP1 · Rehashing beats verify(); 201 calls beat the API

No. verify() recomputes each hash from the stored records, so a chain rebuilt after the edit passes every check. Only the heads published outside the sandbox reveal the rewrite.

The evaluation API needs 201 submissions: one baseline, then one per prediction, flipping it and watching the score. After that the agent scores 100% on the test set and about 50% on fresh data.

SolutionB1 · Logs in reach, scores on tap

First, the log lives where the agent can write it, so the hash chain can be rebuilt after any edit. Move the log to a service outside the workspace that appends only, and publish the chain head after every write to storage the agent cannot modify, such as write-once object storage. Verify new runs against the published heads.

Second, unlimited scored submissions let an agent fit the test labels through the scores. The 99% may be leakage, not a method. Score development work on a validation set, limit and log submissions, and evaluate any claimed method once on a fresh held-out set it never touched. Ask for the code and rerun it there. Only that number goes in the report.
