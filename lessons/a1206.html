In plain words first
The idea in one line

Real images are not 224x224 squares. A receipt is 1:3, a chart is 16:9, a medical scan might be 4096x4096, a mobile screenshot is 9:19.5. The pre-2024 VLM answer — resize everything to a fixed square — threw away the signal that makes OCR, document understanding, and high-resolution scene parsing work. NaViT (Google, 2023) showed you could pack variable-resolution patches into a single transformer batch with block-diagonal masking. Qwen2-VL's M-RoPE (2024) dropped absolute positional tables entirely. LLaVA-NeXT's AnyRes tiled high-resolution

Terms you'll hear
Term What people say What it actually means
Patch-n'-pack "NaViT-style packing" Concatenate variable-length patch sequences from different images into one batch dimension
Block-diagonal mask "Packing mask" Attention mask that confines each image's patches to attend only to themselves, not neighbors in the pack

The problem

In plain words first

A vision transformer trained on 224 × 224 squares sees every image as a 224 × 224 square. A tall receipt gets squashed, small chart labels blur away, and padding a wide image wastes compute. There are three ways around this. Tiling (AnyRes) cuts a large image into encoder-sized crops plus a small overview. Native resolution (Qwen2-VL's approach, SigLIP 2's NaFlex) feeds each image at its own aspect ratio and tells the model where every patch sits. Patch-n'-pack puts several such images into one sequence, with an attention mask that keeps them apart. This lesson compares the three and counts their token costs. It runs real LLaVA-NeXT tiling code on a tiny test model to see how many tokens each image shape costs, and checks that a packed, masked batch gives exactly the same result as encoding each image alone. No model is trained.

Transformers expect a sequence. A batch is a stack of sequences the same length. If your images are 224x224, you get 196 patch tokens every time, padding not required, job done. Train on 224, infer on 224, never think about resolution again.

The world does not cooperate. Documents are portrait (8.5x11 inches, 2:3-ish). Chart screenshots are landscape (16:9). Receipts are tall and thin (1:3). Medical imaging ships at 2048x2048 or larger. Mobile device screenshots are 1170x2532 (0.46:1).

Three pre-2024 options and why each fails:

  1. Resize to a fixed square (224x224 or 336x336). The squish distorts text and faces. The downscale destroys chart labels and OCR content. Standard practice until LLaVA-1.5.
  2. Crop to a fixed aspect ratio. You throw away most of the image, and picking the crop location is its own vision problem.
  3. Pad to the longest side. Fixes distortion but wastes 50%+ of tokens on padding for portrait images. Quadratic attention cost on all those pad tokens.

The 2024-2025 answer: let the transformer eat patches at the image's native resolution, and figure out how to pack a heterogeneous batch into one sequence without wasted compute.

Idea 1 · NaViT and patch-n'-pack

NaViT (Dehghani et al., 2023) was the paper that showed this works at scale. The idea is mechanical:

  1. For each image in the batch, compute its native patch grid at a chosen patch size (say 14).
  2. Flatten each image's patches into its own variable-length sequence.
  3. Concatenate all images' patches into one long sequence for the batch.
  4. Build a block-diagonal attention mask so image A's patches only attend within image A.
  5. Carry per-patch position information (2D RoPE or fractional position embeddings).

A batch of three images at 336x336 (576 tokens), 224x224 (256 tokens), and 448x336 (768 tokens) becomes one 1600-token sequence with a 1600x1600 block-diagonal mask. No padding. No wasted compute. The transformer handles arbitrary aspect ratios.

NaViT also introduced random token dropping during training: drop a share of each image's patches (up to about half), which both regularises and speeds training.

Idea 2 · AnyRes (LLaVA-NeXT)

LLaVA-NeXT's AnyRes is the pragmatic alternative. Given a high-resolution image and a fixed encoder (CLIP or SigLIP at 336), tile the image:

  1. Pick a grid layout from a predefined set — (1x1), (1x2), (2x1), (1x3), (3x1), (2x2), etc. — that best fits the image's aspect ratio.
  2. Tile the full image into the grid; each tile becomes a 336x336 crop.
  3. Also produce a thumbnail: the whole image resized to 336x336 as a global-context token.
  4. Encode every tile through the frozen 336-encoder. Concatenate the tile tokens + thumbnail tokens.

For a 672x672 image the 2x2 grid gives 4 × 576 = 2,304 tile tokens plus 576 for the thumbnail, 2,880 in all. The Hugging Face implementation also adds one "newline" token at the end of each row of the tile grid (48 rows here), so it hands the LLM 2,928 (measured below). Expensive but effective — the LLM sees both local detail and global context.

AnyRes is the route of choice when your encoder is frozen and only supports one resolution. It explodes token count for large images (a 1344x1344 image at 4x4 grid is 9216 + 576 ≈ 9800 tokens, which overflows an 8k LLM context before any text arrives).

Idea 3 · M-RoPE (Qwen2-VL)

Qwen2-VL introduced Multimodal Rotary Position Embedding. Instead of NaViT's fractional positions or AnyRes's tile-and-thumbnail, each patch carries a 3D position (temporal, height, width). The query/key rotations handle arbitrary H, W, and temporal length.

This gives native dynamic resolution. At inference you feed any H×W image (rounded to multiples of 28); the vision encoder, which uses 2D-RoPE, produces H/14 × W/14 patches, and each 2×2 group is merged into one token, so the LLM receives H/28 × W/28 visual tokens. In the LLM each visual token gets a (t, row, column) position and M-RoPE rotates attention accordingly. Qwen2.5-VL and Qwen3-VL continue this. InternVL3's V2PE is related: it gives visual tokens smaller, variable position increments than text tokens.

Unlike AnyRes, M-RoPE is O(H×W/P2) tokens at native resolution — no multiplicative tile overhead. Qwen2-VL's vision encoder also batches images of different sizes NaViT-style: their patches are concatenated and attention is restricted to each image with cumulative sequence lengths (cu_seqlens).

Idea 4 · NaFlex (SigLIP 2)

NaFlex is the SigLIP 2 checkpoint's native-flex mode. A single model serves several sequence lengths at inference (the paper trains on 128 to 1,024 patches per image). Each image is resized to keep its aspect ratio within the chosen patch budget, and the learned position-embedding table is resized to the image's grid. The selling point: one checkpoint, pick your token budget at inference based on the task.

For a semantic task (classification, retrieval), 256 tokens. For OCR or chart understanding, 1024 tokens. No retraining.

Idea 5 · The packing mask

The block-diagonal mask is where most implementations stumble. For a packed sequence of length N_total covering images i=0..B-1 with lengths n_i, the mask M of shape (N_total, N_total) is 1 if both indices fall in the same image's block, else 0. You can build it from a cumulative length list:

offsets = [0, n_0, n_0+n_1, ..., N_total]
M[i, j] = 1 iff there exists b where offsets[b] <= i < offsets[b+1] and offsets[b] <= j < offsets[b+1]

This is one line in PyTorch with torch.block_diag or an explicit gather. FlashAttention's variable-length path (cu_seqlens) skips the mask entirely and attends within sequences using the cumulative-length tensor directly, so it never computes the masked-out scores; the saving grows with the number of images packed together.

The same idea as a formula

Native tokens for an image of W×H pixels and patch size P: n=⌊W/P⌋⋅⌊H/P⌋; with 2×2 merging (Qwen2-VL and later), n/4 reach the LLM.

AnyRes tokens with a gw​×gh​ grid of S×S crops plus a thumbnail:

n=(gw​gh​+1)(PS​)2(before unpadding and row-newline tokens).

Packing. Images with n1​,…,nB​ tokens make one sequence of N=∑b​nb​ with mask Mij​=1 iff i and j belong to the same image. Attention work with a dense mask is N2 scores; a variable-length kernel computes only ∑b​nb2​. Padding to the longest image costs B⋅maxb​nb​ tokens instead of N.

Worked example
Three images, three strategies
  • Native, 14-px patches: 336×336 → 576 tokens, 224×224 → 256, 448×336 → 768. Packed: 1,600 tokens.
  • Padded to the longest image: 3×768=2,304 tokens, of which 704 (31%) are padding.
  • Packed attention: 5762+2562+7682=987,136 scores instead of 1,6002=2,560,000, 39%.
  • AnyRes on a 1200×400 banner: the best grid is 3 crops in a row (1008×336) plus a thumbnail, about 4×576=2,304 tokens before the row-newline tokens. The same banner at native resolution is ⌊1200/14⌋⋅⌊400/14⌋=85×28=2,380 patches, or 595 tokens after 2×2 merging.
Check your mental model
  • ✗ "AnyRes cost grows smoothly with image size."
    ✓ It jumps by whole 576-token tiles and is capped by the largest allowed grid; bigger images are downscaled to fit.
  • ✗ "Packing images into one sequence lets them share information."
    ✓ The block-diagonal mask keeps each image's attention inside its own block; the output equals separate encoding.
  • ✗ "Square resizing only loses a little sharpness."
    ✓ It distorts aspect ratios and can make small text unreadable, which is what OCR and chart questions depend on.

A tiny LLaVA-NeXT test checkpoint (random weights) with LLaVA-NeXT's real tiling settings: a 336-px encoder and grids of 336×672, 672×336, 672×672, 1008×336 and 336×1008. For six image shapes the run records tiles, the thumbnail and the visual tokens the LLM receives. It then runs the model end to end once, to check the code path; the tiny model's text output is meaningless. A few seconds.

import torch
from PIL import Image
from transformers import AutoConfig, AutoProcessor, LlavaNextForConditionalGeneration, logging
logging.set_verbosity_error()

# AnyRes on a tiny LLaVA-NeXT test checkpoint (random weights) that uses LLaVA-NeXT's real tiling settings
repo = "trl-internal-testing/tiny-LlavaNextForConditionalGeneration"
cfg = AutoConfig.from_pretrained(repo)
proc = AutoProcessor.from_pretrained(repo)
model = LlavaNextForConditionalGeneration.from_pretrained(repo).eval()
print(f"encoder input 336x336, 14-px patches -> 576 tokens per tile; allowed grids (px): {cfg.image_grid_pinpoints}\n")
print(f"{'image (w x h)':<15}{'tiles + thumbnail':>19}{'image tokens':>14}{'vs one 336 tile':>17}")
for w, h in [(336, 336), (640, 480), (672, 672), (1200, 400), (400, 1200), (2000, 2000)]:
    img = Image.new("RGB", (w, h), (120, 160, 200))
    x = proc(images=img, text="USER: <image>\nDescribe. ASSISTANT:", return_tensors="pt")
    n = int((x.input_ids == cfg.image_token_index).sum())
    tiles = x.pixel_values.shape[1] - 1                         # first crop is the global thumbnail
    print(f"{f'{w} x {h}':<15}{f'{tiles} + 1':>19}{n:>14,}{n / 576:>16.1f}x")
with torch.no_grad():
    img = Image.new("RGB", (1200, 400), (120, 160, 200))
    x = proc(images=img, text="USER: <image>\nDescribe. ASSISTANT:", return_tensors="pt")
    out = model.generate(**x, max_new_tokens=4, do_sample=False)
print(f"\nforward + generate run end to end on the 1200 x 400 input ({x.input_ids.shape[1]:,} prompt tokens); "
      f"random weights, so the output text is meaningless")

Reading this output

Even a small square costs two tiles. A 336 × 336 image should fit one tile, but LLaVA-NeXT's grid list has no 1×1 entry. The image is placed in a 336 × 672 grid, padded, and the padded half is removed again ("unpadding"). The LLM still receives 1,176 visual tokens, about twice a single tile.

Cost depends on shape, not only on size. A 640 × 480 photo uses the 2×2 grid (2,340 tokens after unpadding), and a 1200 × 400 banner the 3-in-a-row grid (2,328). The tall 400 × 1200 page uses the 3-in-a-column grid (2,376). Each picks the grid whose aspect ratio wastes the least.

The cost is capped. 672 × 672 and 2000 × 2000 both cost 2,928 tokens: the full 2×2 grid (2,304), the thumbnail (576) and one newline token per row of the tile grid (48). A 2000-px photo is simply downscaled to fit 672 px. More pixels than the largest grid buy nothing, which matters for documents with small print.

The code path works end to end. The 1200 × 400 request became a 2,341-token prompt, ran through the vision tower, the projector and the decoder, and generated tokens. The tiny model's random weights make the words meaningless. Real LLaVA-NeXT checkpoints use the same processor and counts.

See it drawn
Patch-n'-pack, verified

Three images at native size (336×336, 224×224, 448×336 with 14-px patches) are packed into one sequence and run through one multi-head attention layer. The run uses a block-diagonal mask, then no mask, and compares both with encoding each image alone. It also lists the cumulative lengths a variable-length kernel would use. Instant.

import torch, torch.nn.functional as F
torch.manual_seed(0)
# Patch-n'-pack: three images at their native sizes in one sequence, with a block-diagonal attention mask
P, D, H = 14, 64, 4
sizes = [(336, 336), (224, 224), (448, 336)]                  # (width, height) in pixels
lens = [(w // P) * (h // P) for w, h in sizes]
x = [torch.randn(1, n, D) for n in lens]                       # stand-ins for each image's patch embeddings
packed = torch.cat(x, dim=1)
seg = torch.repeat_interleave(torch.arange(len(lens)), torch.tensor(lens))
mask = seg[:, None] == seg[None, :]                            # True where attention is allowed
print(f"tokens per image {lens} -> one packed sequence of {packed.shape[1]}")
print(f"allowed attention pairs: {int(mask.sum()):,} of {mask.numel():,} ({mask.float().mean():.0%}); "
      f"padding to the longest image instead: {len(lens)} x {max(lens)} = {len(lens) * max(lens):,} tokens "
      f"({1 - sum(lens) / (len(lens) * max(lens)):.0%} padding)")

Wq, Wk, Wv = (torch.randn(D, D) / D ** 0.5 for _ in range(3))
def attend(seq, m=None):
    q, k, v = (seq @ W for W in (Wq, Wk, Wv))
    q, k, v = (t.view(1, -1, H, D // H).transpose(1, 2) for t in (q, k, v))
    return F.scaled_dot_product_attention(q, k, v, attn_mask=m).transpose(1, 2).reshape(1, -1, D)
alone = torch.cat([attend(s) for s in x], dim=1)               # each image on its own
together = attend(packed, mask)                                # all three packed, block-diagonal mask
leaky = attend(packed)                                         # packed but no mask
print(f"packed with mask vs separate: max difference {(together - alone).abs().max():.1e}")
print(f"packed without mask vs separate: max difference {(leaky - alone).abs().max():.2f}  <- images attend to each other")
cu = torch.tensor([0] + lens).cumsum(0)
print(f"cumulative lengths for variable-length kernels (cu_seqlens): {cu.tolist()}; "
      f"score entries computed {sum(n * n for n in lens):,} instead of {packed.shape[1] ** 2:,}")
What you should see
tokens per image [576, 256, 768] -> one packed sequence of 1600
allowed attention pairs: 987,136 of 2,560,000 (39%); padding to the longest image instead: 3 x 768 = 2,304 tokens (31% padding)
packed with mask vs separate: max difference 4.2e-07
packed without mask vs separate: max difference 1.30  <- images attend to each other
cumulative lengths for variable-length kernels (cu_seqlens): [0, 576, 832, 1600]; score entries computed 987,136 instead of 2,560,000
Reading this output

Packing removes padding. The three images have 576, 256 and 768 patch tokens: 1,600 packed. Padding each to the longest would need 2,304 tokens, 31% of them wasted.

The mask makes packing exact. With the block-diagonal mask, the packed result differs from encoding each image alone by 4.2e-07, which is float32 rounding. Only 39% of the score matrix is allowed: each image attends to itself.

Without the mask, images contaminate each other. The same packed sequence without a mask differs from the separate results by up to 1.30, as large as the values themselves. Every patch now attends to patches of the other two images, and nothing in the code raises an error.

Variable-length kernels skip the masked work. With the cumulative lengths [0, 576, 832, 1600] (cu_seqlens), FlashAttention-style kernels compute only the 987,136 in-image scores instead of all 2,560,000. That is how Qwen2-VL's vision encoder and NaViT-style training batch images of mixed sizes.

Idea 6 · Token budgets

Pick your strategy by task:

  • OCR / documents: 1024-4096 tokens. SigLIP 2 NaFlex at 1024, or AnyRes 3x3 + thumbnail.
  • Charts and UI: 729-1024 tokens at 384-448 native. Qwen2.5-VL dynamic resolution with max pixels cap.
  • Natural photos: 256-576 tokens is fine. The downstream LLM sees enough. Pay for tokens where content density is high.
  • Video: 64-128 tokens per frame after spatial pooling, 2-8 FPS. Lesson 12.17 covers this.

The 2026 production rule: pick a per-task max-pixels cap, encode at native aspect ratio up to that cap, pack the batch, and skip padding. Qwen2.5-VL exposes min_pixels and max_pixels for exactly this knob.

Use it: the same idea with real libraries

Break it on purpose

Industry practice
What's current (2024–2026)
  • Native resolution with pixel caps is the default in open VLMs: Qwen2.5-VL and Qwen3-VL take min_pixels / max_pixels, InternVL uses dynamic tiling with a maximum tile count, and both merge patches before the LLM.
  • Packed variable-length attention (FlashAttention varlen, PyTorch's FlexAttention and nested tensors) is standard for training on mixed resolutions.
  • SigLIP 2 NaFlex gives one encoder that serves several token budgets with aspect ratio preserved.
  • Hosted models bill by resolution: Claude counts 28×28-pixel visual tokens with a long-edge limit (2,576 px on Claude 4.7 and later), so resizing before upload controls cost (Lesson 12.1).

Sources: NaViT (arXiv 2307.06304), LLaVA-NeXT blog, Qwen2-VL (arXiv 2409.12191), SigLIP 2 (arXiv 2502.14786), Hugging Face LLaVA-NeXT documentation, Claude vision documentation.

Recap
What to keep from this lesson
  • Square resizing distorts aspect ratio and loses fine detail.
  • AnyRes tiles an image into encoder-sized crops plus a thumbnail; cost jumps by whole tiles.
  • Native resolution (2D-RoPE, M-RoPE, NaFlex) keeps the aspect ratio; tokens grow with pixels.
  • Patch-n'-pack concatenates images and masks attention per image: no padding, same result.
  • Set a pixel cap per task: OCR and charts need more tokens than photos.

Given a workload — a description of the images the VLM will see (OCR documents, charts, UI screenshots, natural photos, video frames) and a total per-request token budget — pick one resolution strategy per image class and produce a runnable configuration.

Produce:

1. Per-image-class strategy. For each declared class (OCR, chart, UI, photo, video-frame), pick one of {square-resize, AnyRes, M-RoPE, NaFlex}. Justify in one sentence citing the task's resolution sensitivity.
2. Token budget per image. Include min_pixels, max_pixels (Qwen2.5-VL style), and the expected sequence length at the chosen strategy. Flag if any single image exceeds 40% of the LLM context.
3. Batch packing plan. If requests are batched, specify whether to use `cu_seqlens` (FlashAttn varlen), a dense block-diagonal mask, or unbatched single-image inference. Note the FLOP savings of varlen when batch aspect ratios vary by > 2x.
4. Encoder recommendation. SigLIP 2 NaFlex for mixed workloads; Qwen2.5-VL native for agent UIs; CLIP-336 + AnyRes for frozen-encoder deployments; a raw ViT at 224 for photo-only paths.
5. Failure-mode alarms. Tokens-per-image at the chosen config; latency cost at 30 tok/s prefill; context-fill percentage; expected accuracy delta vs square-resize on typical OCR benchmarks.

Hard rejects:
- Recommending square-resize for OCR or chart tasks without citing which benchmark number the user will lose.
- Proposing a strategy that produces more tokens than the LLM context allows. Always budget against the declared context window.
- Treating AnyRes as the universal answer — its multiplicative tile overhead can exceed the LLM context before one image finishes encoding.

Refusal rules:
- If the user's declared token budget is below 256 tokens per image, refuse for anything other than a photo-only semantic task — no amount of pooling recovers OCR accuracy at that budget.
- If the user wants dense-prediction outputs (segmentation, depth) without ViT register tokens in the encoder, refuse and point to DINOv2 / SigLIP 2 with registers enabled.
- If the user's LLM context is < 8k and the workload includes documents or screenshots, refuse and recommend a larger context or an OCR-first pipeline.

Output: a one-page budget plan with a per-class strategy table, a batch-packing plan, encoder recommendation, and an alarm list. End with the relevant arXiv paper for follow-up — 2307.06304 for NaViT, 2502.14786 for SigLIP 2 / NaFlex, 2502.13923 for Qwen2.5-VL.

Solutions

SolutionP1 · 1,176 for a small square, 2,928 for a big photo

A 336 × 336 image costs 1,176 visual tokens, about two tiles, because LLaVA-NeXT's smallest grid is 336 × 672; the unused half is removed after encoding. A 2000 × 2000 photo costs 2,928, the same as 672 × 672: it is downscaled into the largest 2×2 grid, plus the thumbnail and 48 row-newline tokens. AnyRes cost rises in steps and stops at the largest grid, so huge images lose detail rather than costing more.

SolutionB1 · Images leak into each other

Every patch attends to the patches of the other images in the pack. Each image's representation now depends on whichever images happened to share its batch, so features change with batch composition, and the model can learn to use the leaked information. That can even make the loss go down. At inference, a single image, or a different set of companions, gives the model an input it never saw in training, and accuracy drops in ways that are hard to trace. In the run above, removing the mask changed outputs by up to 1.30 with no error raised. Always check a packed forward pass against separate ones, as the run does, and make the mask or cu_seqlens come from the same per-image lengths used to pack the sequence.
