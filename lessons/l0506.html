Why this came about

Vector RAG struggled with questions that need connections across documents or a view of the whole collection. Microsoft Research's GraphRAG (2024) built a knowledge graph from documents, summarized its communities and answered from those, sparking a family of graph-based retrieval methods.

In plain words first
Searching the map, not just the pages

Vector RAG finds passages similar to the question. It struggles with relationship questions ("which suppliers of our top products had incidents?") and whole-collection questions ("what are the main complaints this year?"). GraphRAG retrieves over a knowledge graph: local search walks out from the entities in the question, global search reads summaries of communities, and text-to-Cypher answers precise structural questions. Each adds build cost, so use it where those questions matter.

GraphRAG

Vector search answers "find passages like this question". It struggles with:

  • relationship questions: "which suppliers of our top ten products had quality incidents?"
  • global questions: "what are the main themes in this year's customer complaints?"

GraphRAG first uses an LLM to extract entities (products, suppliers, people) and relationships into a knowledge graph, then answers by traversing the graph or by reading summaries of related clusters.

Implementation Approach Notes
Microsoft GraphRAG Entity graph plus a hierarchy of community summaries. Local search starts from entities; global search map-reduces over community summaries Strong on global questions; indexing is expensive and needs tuning
LightRAG (open source) Graph plus text index, dual-level retrieval Lighter and cheaper to index
Neo4j GraphRAG, other graph databases Graph traversal and Cypher queries plus vector indexes on nodes Good when you already have or want a curated graph

Watch out
GraphRAG is a cost decision

Building the graph calls an LLM over the whole corpus, and keeping it current costs more. Use it when your eval shows relationship or global questions failing with hybrid search, and when those questions matter to the business. For many corpora, good metadata filters and SQL over extracted fields answer the same questions more cheaply.

GraphRAG from scratch

GraphRAG turns text into a knowledge graph (entities as nodes, relationships as edges) and answers by traversing it. Relationship questions ("which suppliers of our best-selling products had incidents?") need several facts joined together, which vector search over separate passages handles badly. The extraction step is normally an LLM prompt ("extract (subject, relation, object) triples"); here a pattern stands in.

import networkx as nx

SUPPLY_DOCS = [
    "MixPro Mixer is supplied by Kaveri Appliances. MixPro Mixer is a top seller.",
    "Kaveri Appliances had a quality incident: cracked jars in batch 7.",
    "AirMax Fan is supplied by Zephyr Ltd. AirMax Fan is a top seller.",
    "Zephyr Ltd passed its annual quality audit.",
    "SlimKettle is supplied by Kaveri Appliances.",
    "BrewEasy Coffee Maker is supplied by Nilgiri Home. Nilgiri Home had a quality incident: faulty thermostats.",
]
PATTERNS = [(r"(.+?) is supplied by (.+?)\.", "SUPPLIED_BY"),
            (r"(.+?) had a quality incident: (.+?)\.", "HAD_INCIDENT"),
            (r"(.+?) is a top seller\.", "TOP_SELLER")]

def extract_triples(doc: str) -> list[tuple[str, str, str]]:
    """Stands in for an LLM extraction prompt that returns (subject, relation, object) triples."""
    triples = []
    for sentence in re.split(r"(?<=\.)\s+", doc):
        for pattern, rel in PATTERNS:
            if m := re.fullmatch(pattern, sentence.strip()):
                obj = m.group(2) if m.lastindex == 2 else "yes"
                triples.append((m.group(1).strip(), rel, obj.strip()))
    return triples

G = nx.MultiDiGraph()
for i, doc in enumerate(SUPPLY_DOCS):
    for s, rel, o in extract_triples(doc):
        if rel == "TOP_SELLER":                                  # an attribute of the product, not a relationship
            G.add_node(s, top_seller=True, top_seller_source=f"supply#{i}")
        else:
            G.add_edge(s, o, rel=rel, source=f"supply#{i}")      # keep the source for citations
print(G.number_of_nodes(), "nodes,", G.number_of_edges(), "edges")

def top_sellers_with_incident_suppliers(G) -> list[tuple[str, str, str, list[str]]]:
    """Local search: a two-hop traversal from products to suppliers to incidents."""
    out = []
    for product, attrs in G.nodes(data=True):
        if not attrs.get("top_seller"):
            continue
        for _, supplier, d2 in G.out_edges(product, data=True):
            if d2["rel"] != "SUPPLIED_BY":
                continue
            for _, incident, d3 in G.out_edges(supplier, data=True):
                if d3["rel"] == "HAD_INCIDENT":
                    out.append((product, supplier, incident, sorted({d2["source"], d3["source"], attrs["top_seller_source"]})))
    return out

for row in top_sellers_with_incident_suppliers(G):
    print(row)
What you should see
9 nodes, 6 edges
('MixPro Mixer', 'Kaveri Appliances', 'cracked jars in batch 7', ['supply#0', 'supply#1'])

The answer joins three facts from two documents, with citations: MixPro Mixer is a top seller, it is supplied by Kaveri Appliances, and Kaveri had an incident. AirMax is a top seller too, but its supplier passed its audit; BrewEasy's supplier had an incident, but it is not a top seller. Hybrid search would return the right passages only if you already knew which supplier to ask about.

Global questions: communities and summaries

Microsoft's GraphRAG answers global questions ("what are the main risk themes across our suppliers?") by grouping the graph into communities, summarizing each one, then combining the summaries (map-reduce). The pieces, with networkx's community detection:

from networkx.algorithms.community import greedy_modularity_communities

undirected = nx.Graph(G)                                         # communities ignore edge direction
communities = sorted(greedy_modularity_communities(undirected), key=len, reverse=True)

def summarize_community(nodes: set[str]) -> str:
    """Stands in for: 'Summarize the entities and relationships in this community, flagging risks.'"""
    incidents = [o for s, o, d in G.edges(data=True) if d["rel"] == "HAD_INCIDENT" and s in nodes]
    products = sorted(n for n in nodes if any(d["rel"] == "SUPPLIED_BY" for _, _, d in G.out_edges(n, data=True)))
    risk = f"risk: {', '.join(incidents)}" if incidents else "no incidents"
    return f"{len(products)} product(s) {products}; {risk}"

summaries = [summarize_community(c) for c in communities]
for i, s in enumerate(summaries):
    print(f"community {i}: {s}")
# Reduce step: in production, a model reads all community summaries and writes the global answer.
risky = [s for s in summaries if "risk:" in s]
print(f"global answer: {len(risky)} of {len(summaries)} supplier clusters carry quality risk")
What you should see
community 0: 2 product(s) ['MixPro Mixer', 'SlimKettle']; risk: cracked jars in batch 7
community 1: 1 product(s) ['BrewEasy Coffee Maker']; risk: faulty thermostats
community 2: 1 product(s) ['AirMax Fan']; no incidents
global answer: 2 of 3 supplier clusters carry quality risk

Each community is a supplier and its products. The real system writes these summaries once at indexing time (the expensive part) and reuses them for every global question. Use GraphRAG when questions like these matter and your evals show hybrid search failing them; otherwise, extracting the same triples into a SQL table is often simpler (Lesson 14.35).

GraphRAG is not one technique. It is a family of ways to use a graph during retrieval, and each one helps a different kind of question. Choosing it well starts with the questions your users actually ask.

Four kinds of questions

Question type Example What plain vector RAG does The graph pattern that helps
Local "What battery does the Phone X use?" Usually fine Not needed; maybe entity lookup
Multi-hop "Which products are hit by the Shenzhen Parts recall?" Finds the recall, misses the products (they never mention Shenzhen) Expand from linked entities along relations; personalized PageRank
Global "What are the main safety themes across all tickets?" Retrieves a few similar tickets and generalizes from them Community detection plus summaries (Microsoft GraphRAG global search)
Aggregate or exact "How many products use components from suppliers in China?" Cannot count Text-to-Cypher: the model writes a query, the database counts

Hands-on · Three retrievers on multi-hop questions

The corpus is eight chunks. Facts extracted from them (as in Lesson 14.41) form a small graph, and each fact remembers its chunk. Three retrievers answer four questions, and we measure evidence recall: the share of chunks a complete answer needs that the retriever returned.

import re
import networkx as nx

CHUNKS = {
    "c1": "Shenzhen Parts recalled the BX-200 battery in March 2026 after overheating reports.",
    "c2": "The Phone X is built around the BX-200 battery and a 6.5 inch display.",
    "c3": "Earbuds Pro charge from a BX-200 cell inside the case.",
    "c4": "Acme Electronics makes the Phone X and the Earbuds Pro.",
    "c5": "Customers can return any product within 30 days for a full refund.",
    "c6": "Battery safety questions should be escalated to the product safety team.",
    "c7": "The Phone X camera upgrade shipped in the 2026 model.",
    "c8": "Acme Electronics buys batteries from Shenzhen Parts.",
}
# Entities and relations as the construction step (Lesson 5.8) would have extracted them, with the chunk each came from.
FACTS = [("Shenzhen Parts", "RECALLED", "BX-200", "c1"), ("Phone X", "USES", "BX-200", "c2"),
         ("Earbuds Pro", "USES", "BX-200", "c3"), ("Acme Electronics", "MAKES", "Phone X", "c4"),
         ("Acme Electronics", "MAKES", "Earbuds Pro", "c4"), ("Acme Electronics", "BUYS_FROM", "Shenzhen Parts", "c8"),
         ("Phone X", "HAS_FEATURE", "camera upgrade", "c7")]
KG = nx.Graph()
for a, r, b, c in FACTS:
    KG.add_edge(a, b, rel=r, chunk=c)
ENTITY_CHUNKS = {}
for a, r, b, c in FACTS:
    for e in (a, b):
        ENTITY_CHUNKS.setdefault(e, set()).add(c)

def words(t):
    return set(re.findall(r"[a-z0-9-]+", t.lower())) - {"the", "a", "of", "in", "is", "and", "by", "which", "are", "what", "who", "to", "from", "for", "after", "any", "within"}

def keyword(q, k=3):
    """Stands in for vector search: rank chunks by word overlap with the question."""
    return [c for c, _ in sorted(CHUNKS.items(), key=lambda kv: -len(words(q) & words(kv[1])))][:k]

def link_entities(q):
    return [e for e in KG if e.lower() in q.lower() or any(w in q.lower() for w in e.lower().split() if len(w) > 5)]

def graph_expand(q, k=3, hops=2):
    """Keyword hits, plus chunks behind facts within `hops` of the entities the question mentions."""
    seeds = link_entities(q)
    near = set(seeds)
    for s in seeds:
        near |= set(nx.single_source_shortest_path_length(KG, s, cutoff=hops))
    extra = sorted({c for e in near for c in ENTITY_CHUNKS.get(e, ())})
    return list(dict.fromkeys(keyword(q, k) + extra))

def ppr(q, k=4):
    """HippoRAG-style: Personalized PageRank from the question's entities, then chunks by entity score."""
    seeds = link_entities(q)
    if not seeds:
        return keyword(q, k)
    pr = nx.pagerank(KG, personalization={s: 1 for s in seeds})
    score = {c: sum(pr[e] for e in ENTITY_CHUNKS if c in ENTITY_CHUNKS[e]) for c in CHUNKS}
    return [c for c, s in sorted(score.items(), key=lambda kv: -kv[1]) if s > 0][:k]

QUESTIONS = [  # question, chunks needed to answer it fully
    ("Which products are hit by the Shenzhen Parts recall?", {"c1", "c2", "c3"}),
    ("Who makes the products hit by the Shenzhen Parts recall?", {"c1", "c2", "c3", "c4"}),
    ("Is the Phone X affected by any recall?", {"c1", "c2"}),
    ("How long do customers have to return a product?", {"c5"}),
]
for name, fn in [("keyword (vector stand-in)", keyword), ("graph expansion", graph_expand), ("personalized PageRank", ppr)]:
    recalls, sizes = [], []
    for q, need in QUESTIONS:
        got = fn(q)
        recalls.append(len(need & set(got)) / len(need)); sizes.append(len(got))
    print(f"{name:26} evidence recall {sum(recalls) / len(recalls):.2f} | chunks per question {sum(sizes) / len(sizes):.1f} | "
          + " ".join(f"{r:.2f}" for r in recalls))
What you should see
keyword (vector stand-in)  evidence recall 0.67 | chunks per question 3.0 | 0.67 0.50 0.50 1.00
graph expansion            evidence recall 1.00 | chunks per question 5.2 | 1.00 1.00 1.00 1.00
personalized PageRank      evidence recall 0.85 | chunks per question 4.0 | 0.67 0.75 1.00 1.00

Word-overlap retrieval (standing in for vector search) answers the return-policy question but finds only part of the evidence for the multi-hop questions, because the product chunks never mention Shenzhen Parts. Graph expansion follows relations two hops from the linked entities and finds everything, at the price of more chunks per question (more tokens and more noise for the model). Personalized PageRank sits in between: tighter context, ranked by closeness to the question's entities. That is the real trade-off to tune: evidence recall against context size, measured on your own question set (Lesson 14.27).

The main GraphRAG designs

Design How it retrieves Indexing cost Best for
Graph-expanded vector RAG Vector search for chunks, then add chunks linked through entities within k hops Extraction only Multi-hop questions on top of an existing RAG system
Microsoft GraphRAG: local search Start from entities matched to the query; gather their relations, claims, community reports and source text Extraction, Leiden communities, LLM summaries per community Entity-centric questions with rich context
Microsoft GraphRAG: global search Map-reduce over community summaries at a chosen level of the hierarchy Same, and summaries dominate cost "What are the themes?" questions across a whole corpus
DRIFT search (Microsoft) Starts from community information, then follows up with local searches Same as GraphRAG Questions between local and global
LazyGraphRAG (Microsoft) Defers LLM work to query time; light index, relevance tests under a budget About the same as vector RAG; Microsoft reported about 0.1% of full GraphRAG indexing cost Large or changing corpora where full GraphRAG indexing is too costly
LightRAG Graph plus vector index with low-level (entity) and high-level (theme) retrieval Lower than GraphRAG; incremental updates A lighter, open-source option
HippoRAG Personalized PageRank from query entities over an extracted graph Extraction only Multi-hop questions, single retrieval step
Text-to-Cypher The model writes a query; the database executes it A curated schema Exact, aggregate and path questions over structured graphs

Microsoft's LazyGraphRAG announcement (November 2024) also reported global-question answer quality comparable to GraphRAG global search at more than 700 times lower query cost; treat vendor numbers as direction and test on your own corpus (Microsoft Research).

Watch out
GraphRAG is mostly an indexing and maintenance decision

Full GraphRAG pays an LLM call per chunk for extraction and per community for summaries, and the summaries go stale as documents change. Before adopting it, measure on your own questions whether plain RAG with better chunking, hybrid search and reranking (Lesson 5.22) already answers them. Adopt GraphRAG for the question types that need it, not for the whole system.

Hands-on · Let the model write Cypher, safely

Text-to-Cypher is the graph version of text-to-SQL (Lesson 14.35), with the same rules: the model gets the schema (labels, relationship types, key properties) and a few examples; a guard checks the query before it runs; a read-only database user runs it with a timeout. The guard below enforces read-only queries, the schema, bounded variable-length paths, parameters instead of literals, and a row limit.

import re

ALLOWED_LABELS = {"Company", "Product", "Component", "Person"}
ALLOWED_RELS = {"MAKES", "USES", "RECALLED", "BUYS_FROM", "CEO_OF"}
WRITE = re.compile(r"\b(CREATE|MERGE|DELETE|DETACH|SET|REMOVE|DROP|LOAD\s+CSV|FOREACH)\b|\bCALL\s+(dbms|apoc\.(?!meta))", re.I)

def check_cypher(q: str, max_hops=3, max_limit=100):
    """Guard for model-written Cypher: read-only, schema-bound, bounded and parameterized."""
    problems = []
    if WRITE.search(q):
        problems.append("write or admin clause")
    for label in re.findall(r"\(\s*\w*\s*:\s*(\w+)", q):
        if label not in ALLOWED_LABELS: problems.append(f"unknown label {label}")
    for rel in re.findall(r"\[\s*\w*\s*:\s*(\w+)", q):
        if rel not in ALLOWED_RELS: problems.append(f"unknown relationship {rel}")
    for lo, hi in re.findall(r"\*(\d*)\.\.(\d*)", q):
        if not hi or int(hi) > max_hops: problems.append(f"unbounded or deep path (*{lo}..{hi})")
    if re.search(r"\*(?!\d*\.\.)", q) and "*" in q.split("RETURN")[0]:
        problems.append("variable-length path without bounds")
    if re.search(r"=\s*'[^']*'", q):
        problems.append("literal value in query; pass it as a $parameter")
    m = re.search(r"\bLIMIT\s+(\d+)", q, re.I)
    if not m or int(m.group(1)) > max_limit:
        problems.append(f"missing LIMIT <= {max_limit}")
    return problems

CANDIDATES = [
    "MATCH (s:Company {name: $supplier})-[:RECALLED]->(:Component)<-[:USES]-(p:Product) RETURN p.name LIMIT 50",
    "MATCH (s:Company)-[:RECALLED]->(c) WHERE s.name = 'Shenzhen Parts' RETURN c LIMIT 10",
    "MATCH (a:Company)-[:SUPPLIES*]->(b:Company) RETURN a, b",
    "MATCH (p:Product) DETACH DELETE p",
    "MATCH (p:Customer)-[:BOUGHT]->(x:Product) RETURN p.email LIMIT 20",
]
for q in CANDIDATES:
    issues = check_cypher(q)
    print(("RUN    " if not issues else "REJECT ") + q[:62] + ("..." if len(q) > 62 else ""))
    for i in issues:
        print("         -", i)
What you should see
RUN    MATCH (s:Company {name: $supplier})-[:RECALLED]->(:Component)<...
REJECT MATCH (s:Company)-[:RECALLED]->(c) WHERE s.name = 'Shenzhen Pa...
         - literal value in query; pass it as a $parameter
REJECT MATCH (a:Company)-[:SUPPLIES*]->(b:Company) RETURN a, b
         - unknown relationship SUPPLIES
         - variable-length path without bounds
         - missing LIMIT <= 100
REJECT MATCH (p:Product) DETACH DELETE p
         - write or admin clause
         - missing LIMIT <= 100
REJECT MATCH (p:Customer)-[:BOUGHT]->(x:Product) RETURN p.email LIMIT...
         - unknown label Customer
         - unknown relationship BOUGHT

Only the first query runs. The second embeds a literal value (pass it as a parameter, which also prevents injection when values come from users or documents); the third uses a relation that does not exist and an unbounded path that could walk the whole graph; the fourth would delete data; the fifth invents labels and asks for personal data. A pattern-based guard is the first line, not the last: also run model-written queries as a database user with read-only rights on the allowed labels, with a query timeout, and log every query with its trace (Lesson 14.121).

Making GraphRAG answers trustworthy

  • Show the path. A graph answer can cite the chain of facts ("Shenzhen Parts recalled BX-200; Phone X uses BX-200, per document d2"), which is easier to verify than a paragraph of retrieved text.
  • Keep chunks in the context. Facts lose nuance when extracted; give the model the source chunks behind the facts it uses.
  • Evaluate by question type. Build separate eval sets for local, multi-hop, global and aggregate questions, and measure evidence recall, answer correctness and cost per question for each design (Lesson 14.32).
  • Watch freshness. Re-extract changed documents and refresh summaries for communities whose members changed.

Solutions

SolutionP1 · Local against global questions

The first is local: start from specific entities and traverse. The second is global: it needs a summary across the whole graph, which community summaries provide. Vector RAG handles neither well.

SolutionB1 · Facts spread across chunks

Each chunk holds one hop; similarity to the question finds some of them but not the chain. Graph traversal connects the hops explicitly.

SolutionD1 · Summaries must be grounded

The summarizer generalized or hallucinated beyond the community's facts. Generate summaries only from the community's facts, keep references to them, and regenerate when the graph changes.

SolutionM1 · Route by question type

Classify questions as local, global or neither, route accordingly, and evaluate per type. Most real systems combine vector, graph and summary retrieval.

Check your understanding

Explain the mechanismWhat is GraphRAG, and when is it better than vector RAG?

Worked answer. GraphRAG uses a knowledge graph in retrieval: traversing from entities in the question for multi-hop and relationship questions, and community summaries for global questions about themes across a corpus. It beats vector RAG on connected questions and corpus-wide summaries, at the cost of building and maintaining the graph.

A plausible wrong answer. "GraphRAG is always better." For simple lookup questions, vector or hybrid RAG is cheaper and as good.

Follow-ups. What are the four question types in this lesson?

Debug a failureGraphRAG answers are good for old documents and poor for new ones. Why?

Worked answer. The graph and its summaries were not updated with new documents: extraction, resolution and community summaries run as batch jobs. Check freshness per source and add incremental updates (Lesson 14.44).

A plausible wrong answer. "The model forgot." The graph is stale.

Follow-ups. How would you update community summaries incrementally?

Defend a designIs GraphRAG worth its build cost for a support help center?

Worked answer. Usually not: help-center questions are mostly single-document lookups, which hybrid RAG handles. It pays off for corpora with many entities and relationships, such as supply chains, research, investigations and complex products, and for global questions. Test on a sample of real questions by type first.

A plausible wrong answer. "Yes, graphs improve every RAG system." Only for question types that need relationships.

Follow-ups. What sample would you test on?
