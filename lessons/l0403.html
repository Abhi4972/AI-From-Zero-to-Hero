Why this came about

Search engines return documents; models need short, focused passages that fit in a prompt. Early RAG cut documents into fixed-size pieces and lost meaning at the cuts, so chunking strategies that respect structure and keep context became an important design choice.

In plain words first
Cutting a book into index cards

Search works on pieces, not whole documents. Chunking cuts documents into passages small enough to be specific and large enough to make sense on their own, ideally along natural boundaries such as sections, with a little overlap and with the document's title and headings kept as metadata. Chunk size is a trade: small chunks find precise facts but lose context; large ones keep context but dilute the match.

Chunking in code

Documents are too long to put whole into every prompt, and long passages dilute the embedding. Chunking splits them into retrievable pieces. The function below does recursive chunking: paragraphs first, then sentences, until each piece is under a size limit.

# Step 2 · Chunking: split on paragraphs, then sentences, keep chunks under a size, with overlap
import re

def chunk(text: str, max_words: int = 40, overlap_sentences: int = 1) -> list[str]:
    sentences = re.split(r"(?<=[.!?])\s+", text.strip())
    chunks, current = [], []
    for s in sentences:
        if current and len(" ".join(current + [s]).split()) > max_words:
            chunks.append(" ".join(current))
            current = current[-overlap_sentences:]          # carry the last sentence into the next chunk
        current.append(s)
    if current:
        chunks.append(" ".join(current))
    return chunks

CHUNKS = []                                                 # (chunk_id, doc_id, text)
for doc_id, text in DOCS.items():
    for i, c in enumerate(chunk(text)):
        CHUNKS.append((f"{doc_id}#{i}", doc_id, c))
print(len(CHUNKS), "chunks; example:", CHUNKS[1])

Industry practice
Chunk size is a tuning knob, not a constant

Practitioners consistently report that parsing quality and chunk boundaries matter more than the choice of vector databaselater · 14.71. Start around 200 to 500 tokens with modest overlap, keep tables and code blocks whole, store the section heading with every chunk, and tune against a retrieval eval (Lesson 14.72) rather than by intuition.

In production
Chunking problems you will meet, and what to do
  • Answers quote half a rule ("refundable within 30 days" without "for damaged items"): chunks are cutting through the sentence that carries the condition. Split on headings and paragraphs first, add a small overlap, and prepend the section heading to every chunk.
  • Tables answered wrongly: fixed-size and semantic splitters cut tables into pieces that mean nothing alone. Keep each table whole (or one row per chunk with the header repeated) and convert it to Markdown before indexing.
  • Precise questions match, but the answer lacks context: chunks are too small. Rather than making every chunk bigger, match on small chunks and hand the model the parent section (small-to-big, below and in Lesson 14.75).
  • Broad questions retrieve the wrong section: chunks are too big, so one vector averages several topics. Split further or add per-section summaries as separate entries.
  • Semantic chunking was slower to ingest and not better: common. Its gains over good structure-aware splitting are often small; try it only on long, unstructured text and keep it if your eval says so.
  • Every change means a re-index: so tune chunking last, after hybrid searchlater · 5.38, headers and rerankinglater · 5.38, and compare the new index side by side with the old one on the same questions.

The chunking families used in production

The recursive splitter above is the default, and the table in the previous step names the common alternatives. Production systems use a few more, and practitioners refer to them by name. Here is the full set, grouped by what they decide: where to cut, what to index, and what to return.

Family What it decides How it works Use when Cost and watch-outs
Fixed size (sliding window) Where to cut Every N tokens, stepping forward by N minus the overlap Baselines, uniform prose Cuts mid-sentence and mid-table; overlap of 10 to 20% duplicates storage
Recursive Where to cut Try paragraph breaks, then sentences, then words until each piece fits The default for prose Ignores headings; a section can straddle two chunks
Structure-aware (Markdown / HTML header splitting) Where to cut Split on headings, keep the heading path as metadata; tables, lists and code blocks stay whole Manuals, policies, wikis, anything a parser turned into Markdown Only as good as the parser (Lesson 4.29)
Code-aware (AST splitting) Where to cut Split on function, class and method boundaries from the language's syntax tree Repositories, notebooks, SQL files Needs a parser per language (tree-sitter); giant functions still need a fallback
Semantic Where to cut Embed sentences; cut where the distance between neighbours jumps Long unstructured text with topic shifts One embedding call per sentence at ingest; gains over structure-aware are often small
Agentic (model-decided) Where to cut A model reads the document and emits boundaries and titles Messy documents with no structure, high-value corpora Slowest and most expensive; non-deterministic, so re-ingestion changes chunks
Hierarchical parent-child What to index and return Chunk at several levels (section → paragraph → sentence); every child points to its parent Long structured documents; the usual production shape More rows; needs stable IDs across levels
Sentence window What to return Index single sentences; return each hit with its k neighbouring sentences Dense technical text where one sentence holds the fact Window size is a knob; windows overlap heavily

Contextual (header or model-written context) What to index Prepend the document title, section path, or a model-written summary of where the chunk sits Almost always; the cheapest big win A model call per chunk for the written version (Lesson 14.75 measures it)
Summary-as-chunk (multi-representation) What to index and return Index a summary of each section or table; return the raw section Tables, long sections, mixed-topic documents Summaries can omit the one detail the question needs; index both

Three of these change the index shape rather than the cut, so they are worth seeing in code. All three reuse DOCS and chunk() from the previous step.

Hierarchical parent-child chunks

Index small pieces for matching; store, for each, the ID of the larger piece it came from; return the parent. The "parent" can be a paragraph, a section, or the document. This is what Bedrock Knowledge Bases call hierarchical chunking, and what Lesson 14.75 uses for small-to-big retrieval.

# Three levels: document -> chunk (from chunk()) -> sentence. Each child stores its parent's ID.
NODES = {}                                                    # node_id -> {"level", "text", "parent"}
for doc_id, text in DOCS.items():
    NODES[doc_id] = {"level": "document", "text": text, "parent": None}
    for i, c in enumerate(chunk(text)):
        cid = f"{doc_id}#{i}"
        NODES[cid] = {"level": "chunk", "text": c, "parent": doc_id}
        for j, s in enumerate(re.split(r"(?<=[.!?])\s+", c)):
            NODES[f"{cid}.{j}"] = {"level": "sentence", "text": s, "parent": cid}

def parent_of(node_id: str, level: str = "chunk") -> str:
    """Walk up until the requested level: a sentence hit comes back as its chunk (or document)."""
    while NODES[node_id]["level"] != level:
        node_id = NODES[node_id]["parent"]
    return node_id

from collections import Counter
print(Counter(n["level"] for n in NODES.values()))
hit = "refund-policy#1.0"                                     # suppose the sentence index matched this
print(hit, "->", NODES[hit]["text"])
print(parent_of(hit), "->", NODES[parent_of(hit)]["text"][:90] + "...")
print(parent_of(hit, "document"), "->", len(NODES[parent_of(hit, 'document')]["text"].split()), "words")
What you should see
Counter({'sentence': 29, 'chunk': 9, 'document': 6})

Match at the sentence level (sharp), return the chunk or the document (enough context). Which level to return is a per-corpus decision: return the chunk for FAQs, the section for manuals, and cap the total so three sentence hits in one section do not return it three times (deduplicate on the parent ID).

Sentence window

A variant that needs no hierarchy: index single sentences and, at answer time, return each hit with its neighbours. Cheaper than parents when documents have no sections.

def sentence_window(doc_id: str, sentence_index: int, window: int = 1) -> str:
    sentences = re.split(r"(?<=[.!?])\s+", DOCS[doc_id].strip())
    lo, hi = max(0, sentence_index - window), min(len(sentences), sentence_index + window + 1)
    return " ".join(sentences[lo:hi])

print(sentence_window("shipping", 3))            # the sentence "Express delivery costs INR 99..." with one neighbour each side
print(sentence_window("shipping", 3, window=0))  # the sentence alone
What you should see
Orders above INR 499 ship free. Express delivery costs INR 99 and is available in 40 cities. You can track an order from the Orders page once it is dispatched.
Express delivery costs INR 99 and is available in 40 cities.

A window of one or two sentences is usually enough for "what does this rule say" questions; it fails when the condition lives several sentences away, which is when parent-child wins.

Proposition chunks

Index facts, not passages. A model rewrites each chunk into standalone statements with pronouns resolved and context filled in; each proposition is indexed and points back to its chunk. The stand-in below does the rewrite by rule so the block runs offline; the real prompt is in the docstring.

def propositions(chunk_id: str, text: str) -> list[str]:
    """Stand-in for: 'Rewrite this passage as a list of short, self-contained statements. Resolve pronouns,
    repeat the subject in every statement, keep numbers exact, add nothing that is not in the passage.'
    The stand-in splits sentences and prefixes the document topic so each line stands alone."""
    topic = DOCS[chunk_id.split("#")[0]].split(".")[0]      # the document's first sentence is its title
    return [f"{topic}: {s.strip()}" for s in re.split(r"(?<=[.!?])\s+", text) if s.strip()]

PROPS = [(f"{cid}/p{k}", cid, p) for cid, _, text in CHUNKS for k, p in enumerate(propositions(cid, text))]
print(len(PROPS), "propositions from", len(CHUNKS), "chunks")
for pid, cid, p in PROPS[:3]:
    print(pid, "->", p)
What you should see
29 propositions from 9 chunks
refund-policy#0/p0 -> Refund policy: Refund policy.
refund-policy#0/p1 -> Refund policy: Customers can request a refund within 7 days of delivery.
refund-policy#0/p2 -> Refund policy: Damaged or defective items are always refundable, even after 7 days, if reported within 30 days.

Each proposition carries its subject, so "UPI refunds usually arrive in 2 days" is findable from "how fast is a UPI refund" without the chunk's other sentences diluting the embedding. The first proposition shows the weakness of a rule-based stand-in (a title turned into a "fact"); a model would drop it. Costs: one model call per chunk at ingest, and roughly three to five times as many index rows. Return the source chunk, not the proposition, so the answer quotes real text.

Code-aware and Markdown-header splitting, in one line each

Both are "structure-aware" with a specific parser. For Markdown, langchain_text_splitters.MarkdownHeaderTextSplitter splits on #, ##, ### and stores the heading path in each chunk's metadata, which is exactly the "section path" header that contextual chunking wants. For code, RecursiveCharacterTextSplitter.from_language(Language.PYTHON, ...) splits on class and def boundaries first; for full syntax-tree splitting, tree-sitter based splitters (for example in LlamaIndexlater · 14.124's CodeSplitter) cut at function and class nodes and fall back to lines inside oversized functions.

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter, Language

md = "# Returns\n\n## Damaged items\nReport within 30 days.\n\n## Refund timing\nUPI refunds arrive in 2 days."
for d in MarkdownHeaderTextSplitter([("#", "h1"), ("##", "h2")]).split_text(md):
    print(d.metadata, "|", d.page_content)

code = "def refund(order):\n    return order.total\n\nclass Ledger:\n    def post(self, amount):\n        self.rows.append(amount)\n"
splitter = RecursiveCharacterTextSplitter.from_language(Language.PYTHON, chunk_size=90, chunk_overlap=0)
print([c.replace("\n", "⏎") for c in splitter.split_text(code)])
What you should see
{'h1': 'Returns', 'h2': 'Damaged items'} | Report within 30 days.
{'h1': 'Returns', 'h2': 'Refund timing'} | UPI refunds arrive in 2 days.
['def refund(order):⏎    return order.total', 'class Ledger:⏎    def post(self, amount):⏎        self.rows.append(amount)']

Choosing, in order

  1. Parse well first (Lesson 4.29): structure-aware splitting needs headings and tables to exist.
  2. Default: structure-aware where there is structure, recursive where there is not, 200 to 500 tokens, 10 to 20% overlap, tables and code whole.
  3. Always add context: the heading path or title on every chunk (contextual, cheap version).
  4. Then shape the index: parent-child when precise matches lack context; sentence window for dense technical text without sections; propositions for fact-heavy prose when you can afford the ingest cost; summary-as-chunk for tables and long sections.
  5. Only with an eval (Lesson 14.77): semantic, agentic and late chunking. They are slower to ingest and their gains are corpus-specific; keep them if recall@k goes up, not because they sound advanced.

Managed services expose the same choices as settings: Bedrock Knowledge Bases offer fixed, hierarchical, semantic, none and custom (Lambda) chunking; most vector databases and frameworks ship the splitters above. The decision is yours either way.

Check your mental model
  • ✗ "Smaller chunks are always more precise."
    ✓ Too small and a chunk loses the context that makes it findable and understandable.
  • ✗ "Chunking by fixed character count is fine."
    ✓ Splitting mid-sentence or mid-table hurts; split on structure where you can.
  • ✗ "Chunks do not need metadata."
    ✓ Source, section and date are what make citations, filters and freshness possible.
  • ✗ "Parent-child chunking and semantic chunking solve the same problem."
    ✓ Semantic chunking decides where to cut; parent-child decides what to index (small) and what to return (large). You can use both.
  • ✗ "Proposition chunking replaces the chunks."
    ✓ Propositions are indexed for matching; the source chunk is still what you return and cite.

Solutions

SolutionP1 · Long sentences

It becomes a chunk of its own, over the limit, because the function splits only at sentence boundaries. Real splitters fall back to smaller separators (clauses, words) or token limits for such cases.

SolutionB1 · Conditions split from rules

The condition ("Damaged or defective items are always refundable, even after 7 days") can end up in a different chunk from the time limit ("if reported within 30 days"), so an answer quotes half a rule. Overlap and structure-aware chunking keep conditions with their rules.

SolutionD1 · One vector averages a whole chunk

A large chunk's embedding averages several topics, so a precise question matches it less sharply. Use small chunks for matching and return the larger parent section to the model (small-to-big, Lesson 14.75), and keep the eval set for both kinds of question.

SolutionM1 · Context headers

A header such as "[Refund policy]" gives every chunk the topic its sentences assume, which helps both BM25later · 5.37 and embeddings; Lesson 14.75 measures the effect as contextual retrievallater · 14.75. Keep the change only if the eval improves.

Explain the mechanismHow do you choose a chunking strategy?

Worked answer. Start from the documents' structure: split on headings and paragraphs, keep tables and code whole, add modest overlap, and store the section heading with each chunk. Choose size by the questions: precise questions want small chunks, broad ones larger. Then tune against a retrieval eval, because the right size depends on the corpus.

A plausible wrong answer. "Use 512 tokens; that is standard." A default is a starting point, not a decision.

Follow-ups. When does semantic chunking help?

Explain the mechanismExplain parent-child (hierarchical) chunking, sentence-window retrieval and proposition chunking, and when you would pick each.

Worked answer. All three separate what you match on from what you hand the model. Parent-child indexes small pieces (sentences or paragraphs), each pointing to a larger parent (section or document); you match small and return the parent, deduplicated by parent ID. Pick it for long structured documents such as manuals and policies. Sentence window indexes single sentences and returns each hit with its k neighbours; no hierarchy is needed, so it suits dense technical text without sections, and it fails when the condition sits several sentences away. Proposition chunking has a model rewrite each chunk into standalone facts, indexes the facts and returns the source chunk; it helps fact and multi-hop questions over prose at the cost of a model call per chunk and three to five times as many index rows. In every case the eval set decides: measure recall@k and answer quality before and after.

A plausible wrong answer. "They are all ways of making chunks smaller." Smaller matching units, yes, but the point is returning a larger or better-contextualized unit than you matched.

Debug a failureAnswers cite the right document but quote an incomplete rule. Why?

Worked answer. The chunk boundary cut the rule from its condition or exception. Check the stored chunks for that document: if the condition is in the next chunk, add overlap, split on structure, or retrieve neighbors of the top chunk.

A plausible wrong answer. "The model truncated the answer." The model quoted what it received.

Defend a designRe-chunking means re-indexing the whole corpus. When is it worth it?
