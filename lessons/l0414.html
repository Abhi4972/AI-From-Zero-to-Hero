Why this came about

As RAG systems went into production, wrong answers were reported without any indication of where they came from. A stage-by-stage debugging method, checking parsing, chunking, indexing, retrieval and generation in order, emerged from that experience.

In plain words first
Debug from the beginning of the pipeline

When a RAG answer is wrong, walk the pipeline in order and look at evidence at each stage: was the document parsed correctly, chunked sensibly, indexed and current, retrieved for this question, ranked near the top, and then used faithfully by the model? Checking retrieval before generation splits the problem in half quickly.

Debugging a RAG answer, stage by stage

A wrong RAG answer was broken at one of a small number of stages, and each stage leaves a different trace. Work from the input end: a fix downstream cannot repair what was lost upstream. Run the same question through each stage and look at the intermediate output before changing anything.

Symptom in the answer Stage to check What to look at Usual fix (lesson)

Keep every debugged case. Each one becomes a row in the evaluation set from Lesson 14.72, so the same failure cannot come back unnoticed.

A tracer you can run

The table says where to look. This function does the looking: it follows one question through the pipeline built in Lessons 14.70 to 5.38 and reports where the passage that holds the answer was found, and at which stage it was lost. You tell it which chunk should be found; it tells you what happened to it.

def rank_of(chunk_id, ids):
    return ids.index(chunk_id) + 1 if chunk_id in ids else None

def trace(question: str, should_find: str | None, k: int = 3) -> None:
    """Follow one question through each retrieval stage and print where the right chunk stands."""
    print(f"\nQ: {question}   (answer is in: {should_find})")
    if should_find is not None and should_find not in {cid for cid, _, _ in CHUNKS}:
        print("   NOT IN THE INDEX: check parsing, chunking and ingestion before anything else"); return
    stages = {"keyword (BM25)": search_bm25(question, k=10), "vector": search_dense(question, k=10)}
    stages["hybrid (fused)"] = search_hybrid(question, k=10)
    stages[f"reranked, top {k} go in the prompt"] = rerank(question, stages["hybrid (fused)"], k=k)
    for stage, ids in stages.items():
        r = rank_of(should_find, ids)
        print(f"   {stage:36} rank {r if r else 'not found':>9}   top: {ids[0]}")
    final = stages[f"reranked, top {k} go in the prompt"]
    if should_find is None:
        print("   VERDICT: nothing should be found; check that the answer says so instead of using", final[0])
    elif should_find in final:
        print("   VERDICT: retrieval did its job; if the answer is still wrong, the fault is in generation")
    elif should_find not in stages["keyword (BM25)"] and should_find not in stages["vector"]:
        print("   VERDICT: never retrieved by either search; look at the wording gap, the embedding model or the chunk itself")
    else:
        print(f"   VERDICT: retrieved, but ranked too low to reach the prompt; look at the reranker and at k")

trace("How long do I have to report a damaged item?", "refund-policy#0")
trace("How do I get my money back?", "refund-policy#0", k=1)
trace("Do you ship to Nepal?", None)
trace("What is the warranty on a mixer?", "warranty-electronics#0")

Reading this output

Each block is one question. Each row is one stage, with the rank at which the right chunk stood (1 is best) and which chunk came top.

  1. The damaged-item question. The right chunk is at rank 1 or 2 at every stage and is among the three sent to the model. Retrieval is fine. If the final answer were wrong, you would stop looking at search and read the prompt and the answer instead.
  2. "How do I get my money back?" with only one chunk allowed in the prompt (k=1). Vector search had the right chunk first, keyword search had it third, and after fusion and reranking it was second. With k=1 it missed the prompt. Nothing was lost in retrieval; it was ranked just too low. The cheap fix is a larger k. The better fix is to ask why the reranker prefers the other chunk.
  3. The Nepal question. Nothing in the index answers it, yet every stage still returns something, because search always returns its closest match. The tracer cannot judge the answer; it reminds you to check that the system says "I do not know" instead of answering from the shipping chunk.
  4. The warranty question. The chunk it was told to look for does not exist under that name. In a real system this is the commonest finding of all: the document was never ingested, failed to parse, or was chunked so that the answer straddles two chunks. No search setting can find what is not there.

A tracer like this takes twenty lines, and it turns "the bot gave a bad answer" into "the right chunk was at rank 4 after reranking and only 3 go in". Run it on every reported failure before touching a prompt.

From the field: what teams learn about RAG

From Jason Liu (Systematically improving RAG), the year of building authors and the Retrieval (RAG) section:

  • Measure retrieval separately from generation (recall and precision at k on a labeled set) before tuning prompts.
  • Segment your questions by type and volume; build specialized retrieval (or tools) for the large, failing segments instead of one ever-larger pipeline.
  • Hybrid search and a reranker are the default, not an optimization; keyword search alone is a strong baseline.
  • Structure and metadata beat clever chunking: titles, dates, filters and document types often matter more than chunk size.
  • Use tools, not just retrieval, for structured data: text-to-SQLlater · 14.80 over a semantic layerlater · 14.80 for numbers (Lessons 14.158 and 13.50), search for documents.
  • Agentic and vectorless retrieval (Lessons 14.76 and 14.78) help when questions need several hops or when documents have strong structure; they cost more tokens, so measure the gain.

Solutions

SolutionP1 · Retrieval before generation

First, whether the answer exists in the corpus at all; second, whether retrieval returned it for this question. Only then the prompt and the model. Most RAG failures are found in the first two.

SolutionB1 · Patches hide the cause

It fixes one question and hides the pipeline failure (a missing document, a bad chunk, a retrieval miss) that will break related questions. Fix the stage that failed, and add the question to the eval set.

SolutionD1 · Conflicting sources

Retrieval returns both an old and a new policy chunk. Check the retrieved passages and their sources and dates. Remove or mark superseded documents at ingestion, prefer the newest by metadata, and tell the model how to handle conflicts.

SolutionM1 · A stage-by-stage checklist

For each stage, the question to ask and how to see the evidence: grep the source, view the parsed text, view the chunk, run the search, print the ranking, print the final prompt, rerun generation, run the citation check. A checklist turns debugging into routine work.
