The problem

In plain words first

An observability platform is where your agent's traces go. It stores every run as a tree of spans, groups runs into sessions (one user conversation), lets you replay them, keeps versions of your prompts, and runs evaluations: checks, often done by another model (an LLM-as-judge), that score whether each answer was any good. Langfuse, Arize Phoenix and Comet Opik are the three common self-hostable ones. They all accept OpenTelemetry traces, but two vocabularies are in use (OpenTelemetry's GenAI names and Arize's OpenInference names), and an evaluation is only as good as the judge. This lesson traces the same call both ways, then runs eight real agent sessions and scores them with a reference check, the lesson's scripted judge, and a small model as judge.

OTel GenAI (Lesson 14.98) gives you the schema. You still need the platform that ingests spans, runs evaluations, stores prompt versions, and surfaces regressions. The three contenders each emphasize different parts of the lifecycle.

Idea 1 · Langfuse (MIT)

  • Vendor-reported 6M+ SDK installs a month. Acquired by ClickHouse in January 2026; still MIT-licensed and self-hostable.
  • Features: tracing, prompt management with versioning + playground, evaluations (LLM-as-judge, user feedback, custom), session replays.
  • June 2025: formerly commercial modules (LLM-as-a-judge, annotation queues, prompt experiments, Playground) open-sourced under MIT.
  • Strongest for: end-to-end observability with tight prompt-management loop.

Idea 2 · Arize Phoenix (Elastic License 2.0)

  • Deeper agent-specific evaluation: trace clustering, anomaly detection, retrieval relevancy for RAG.
  • Native OpenInference auto-instrumentation.
  • Pairs with managed Arize AX for production.
  • Has had prompt management (versions and tags) since 2025, but is mostly used as an evaluation and drift/behavioral-regression tool alongside broader platforms.
  • Strongest for: RAG relevancy, behavioral drift, anomaly detection.

Idea 3 · Comet Opik (Apache 2.0)

  • Automated prompt optimization through A/B experiments.
  • Guardrails (PII redaction, topical constraints).
  • LLM-judge hallucination detection.
  • Benchmark from Comet's own measurement (March 2025, no dataset or hardware described): Opik logs + evals in 23.44s vs Langfuse 327.15s (~14x gap) — take vendor benchmarks as directional.
  • Strongest for: optimization loop, automated experimentation, guardrail enforcement.

Idea 4 · Industry data

Per LangChain's State of Agent Engineering survey (1,340 responses, Nov–Dec 2025): 89% of organizations have some observability for their agents, about 52% run offline evaluations, and quality is the top production barrier (32% cite it).

Need Pick

Idea 6 · Where this pattern goes wrong

  • No eval strategy. Tracing without evaluation is just expensive logging.
  • Self-rolled LLM-judge without grounding. CRITIC pattern (Lesson 14.20) applies — judges need external tools for factual verification.
  • Prompt versions not tied to traces. When prod regresses, you cannot bisect to the prompt that caused it.

The same idea as a formula

Judge agreement. Score each session with a reference check ri​∈{pass,fail} and with a judge ji​. Plain agreement n1​∑i​[ji​=ri​] hides what matters, so split it:

recall on failures=#{i:ri​=fail}#{i:ji​=fail, ri​=fail}​,false-alarm rate=#{i:ri​=pass}#{i:ji​=fail, ri​=pass}​.

A judge that always says "pass" has agreement equal to the pass rate (often 80 to 95%) and a recall of zero.

Double counting. If k instrumentations each emit a span for the same model call, a dashboard that sums tokens over spans reports k times the real usage.

Worked example
Reading a judge's scorecard
  • Eight sessions; the reference check fails 2 (answers that say "Yes" to "Is it delivered?" and "Is it on the way?" when the database says shipped and processing).
  • A judge that passes everything agrees on 6 of 8, 75%, and catches 0 of the 2 failures: recall 0/2=0, false alarms 0/6=0.
  • A judge that fails 2 correct answers and passes both wrong ones agrees on 4 of 8: recall 0/2, false alarms 2/6≈33%. It looks stricter and is worse.
  • So before trusting an evaluator on a dashboard, measure its recall on known failures, not its agreement rate.
Check your mental model
  • ✗ "Tracing is evaluation."
    ✓ Traces record what happened; only an evaluation says whether it was right.
  • ✗ "An LLM judge with the facts in front of it catches wrong answers."
    ✓ A small judge with the tool result still missed both wrong answers here.
  • ✗ "Turning on two instrumentations gives more detail."
    ✓ It gives two spans per call and doubles every sum.
  • ✗ "Phoenix and Langfuse record content only if I opt in."
    ✓ OpenInference records inputs and outputs by default.

# What a platform ingests: the same chat call traced by the two instrumentation families that observability
# platforms accept. OpenTelemetry's GenAI instrumentation (lesson 14.98) and OpenInference (Arize's
# conventions, used by Phoenix; Langfuse and others accept both). The local Qwen2.5-0.5B-Instruct server
# from lessons 14.77-14.98 stands in for the model API.
import json, os, pathlib, subprocess, sys, tempfile, textwrap
work = pathlib.Path(tempfile.mkdtemp())
SERVER = r'''# qwen_server.py: Qwen2.5-0.5B-Instruct behind a minimal OpenAI-compatible /v1/chat/completions endpoint,
# so frameworks that speak that API can run on a local model. Greedy decoding; tool calls supported through
# the model's chat template (<tool_call> blocks become OpenAI tool_calls); tool_choice="required" is honoured by
# starting the reply inside a <tool_call> block. Stops by itself after LIFETIME s.
import json, os, re, sys, time, uuid, torch
from http.server import BaseHTTPRequestHandler, HTTPServer
os.environ.setdefault("HF_HUB_OFFLINE", "1")
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
LOG = os.environ.get("QWEN_LOG")
def text_of(content):
    return content if isinstance(content, str) else " ".join(p.get("text", "") for p in content or [])
def to_template(messages):
    out = []
    for m in messages:
        msg = {"role": m["role"], "content": text_of(m.get("content") or "")}
        if m.get("tool_calls"):
            msg["tool_calls"] = [{"type": "function", "function": {"name": c["function"]["name"],
                                  "arguments": json.loads(c["function"]["arguments"] or "{}")}} for c in m["tool_calls"]]
        out.append(msg)
    return out
def complete(req):
    tools = req.get("tools") or None
    ids = tok.apply_chat_template(to_template(req["messages"]), tools=tools, add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    forced = '<tool_call>\n{"name": "' if tools and req.get("tool_choice") == "required" else ""
    if forced:                                           # constrained start: the reply must be a tool call
        ids = torch.cat([ids, tok(forced, return_tensors="pt")["input_ids"]], dim=1)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=int(req.get("max_tokens") or req.get("max_completion_tokens") or 256),
                           do_sample=False)
    text = forced + tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
    calls = []
    for blob in re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", text, re.S) if tools else []:
        try:
            d = json.loads(blob)
            calls.append({"id": "call_" + uuid.uuid4().hex[:8], "type": "function",
                          "function": {"name": d["name"], "arguments": json.dumps(d.get("arguments", {}))}})
        except (json.JSONDecodeError, KeyError):
            pass
    content = re.sub(r"<tool_call>.*?</tool_call>", "", text, flags=re.S).strip() if calls else text
    if LOG:
        with open(LOG, "a") as f:
            f.write(json.dumps({"prompt_tokens": ids.shape[1], "tools": len(tools or []), "tool_calls": [c["function"] for c in calls],
                                "content": content[:200]}) + "\n")
    msg = {"role": "assistant", "content": content or None}
    if calls:
        msg["tool_calls"] = calls
    return {"id": "chatcmpl-" + uuid.uuid4().hex[:8], "object": "chat.completion", "created": int(time.time()),
            "model": req.get("model", M), "choices": [{"index": 0, "message": msg,
            "finish_reason": "tool_calls" if calls else "stop"}],
            "usage": {"prompt_tokens": ids.shape[1], "completion_tokens": out.shape[1] - ids.shape[1],
                      "total_tokens": out.shape[1]}}
class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass
    def do_GET(self):
        body = json.dumps({"object": "list", "data": [{"id": M, "object": "model"}]}).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json"); self.end_headers(); self.wfile.write(body)
    def do_POST(self):
        req = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        body = json.dumps(complete(req)).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body))); self.end_headers(); self.wfile.write(body)
port, lifetime = int(sys.argv[1]), float(sys.argv[2])
srv = HTTPServer(("127.0.0.1", port), Handler); srv.timeout = 0.5
print("ready", flush=True)
deadline = time.time() + lifetime
while time.time() < deadline:                            # bounded: one request at a time until the deadline
    srv.handle_request()

Reading this output

Two vocabularies for the same call. OpenTelemetry's span is chat qwen2.5-0.5b-instruct (CLIENT) with ten gen_ai.* attributes. OpenInference's is ChatCompletion (INTERNAL) with twenty: llm.model_name, llm.token_count.prompt, llm.system and so on. The facts agree (44 input and 40 output tokens); the names do not, so every dashboard query has to know both.

OpenInference records the conversation by default. Its span holds the full request as input.value and each message as llm.input_messages.N.message.content, customer email included, plus the reply. OpenTelemetry records none of it unless you opt in (lesson 14.98). Set OPENINFERENCE_HIDE_INPUTS and OPENINFERENCE_HIDE_OUTPUTS, or mask at the collector, before production.

Both together double the numbers. With both instrumentations on, one call produces two spans, and a dashboard summing input tokens over spans reports 88 instead of 44. Cost, rate and latency panels would all be off in the same way.

# The platform's other half: evaluating traced runs. Eight support sessions run through a real agent
# (Qwen with an order-lookup tool), traced with OpenTelemetry in this process. Each session is then scored
# four ways: a reference check against the order database, the lesson's scripted judge (code/main.py),
# and Qwen as an LLM judge without and with the tool result it should check against. Continues from above.
import contextlib, importlib, io, re
os.environ["OTEL_SEMCONV_STABILITY_OPT_IN"] = "gen_ai_latest_experimental"
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter
from opentelemetry.instrumentation.openai_v2 import OpenAIInstrumentor
exporter = InMemorySpanExporter()
provider = TracerProvider(); provider.add_span_processor(SimpleSpanProcessor(exporter))
trace.set_tracer_provider(provider)
OpenAIInstrumentor().instrument()
tracer = trace.get_tracer("support-agent")
OpenAI = importlib.import_module("openai").OpenAI      # the real openai client, pointed at the local server
client = OpenAI(base_url=URL, api_key="local")
MODEL = "qwen2.5-0.5b-instruct"
ORDERS = {"A-1001": "shipped on 20 Nov", "A-1002": "processing, not shipped yet", "A-1003": "cancelled",
          "A-1004": "delivered on 18 Nov"}
TOOLS = [{"type": "function", "function": {"name": "get_order_status",
          "description": "Return the status for an order ID such as A-1001.",
          "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}}]
# (session, question, word stem the answer must contain, the yes/no it must give if the question is yes/no)
SESSIONS = [("s01", "Where is my order A-1001?", "shipped", None), ("s02", "Has A-1002 shipped yet?", "process", "no"),
            ("s03", "What is the status of A-1003?", "cancel", None), ("s04", "Did A-1004 arrive?", "deliver", "yes"),
            ("s05", "Where is my order A-9999?", "not found", None), ("s06", "Is order A-1001 delivered already?", "ship", "no"),
            ("s07", "When will A-1003 arrive?", "cancel", None), ("s08", "Is A-1002 on the way?", "process", "no")]

def reference(answer, stem, yes_no):
    """The check a person would write from the order database: right status, and no wrong yes/no."""
    a = (answer or "").lower().strip()
    wrong = {"yes": "no", "no": "yes"}.get(yes_no)
    return "PASS" if stem in a and not (wrong and re.match(rf"{wrong}\b", a)) else "FAIL"

def lookup(order_id):
    return f"{order_id}: {ORDERS.get(order_id, 'not found')}"

def run_session(sid, question):
    msgs = [{"role": "system", "content": "You are a support agent. Look orders up with the tool, then answer in one sentence."},
            {"role": "user", "content": question}]
    tool_result = None
    with tracer.start_as_current_span("invoke_agent support_bot", kind=trace.SpanKind.INTERNAL,
                                      attributes={"gen_ai.operation.name": "invoke_agent", "gen_ai.agent.name": "support_bot",
                                                  "session.id": sid}):
        for turn in range(2):
            msg = client.chat.completions.create(model=MODEL, temperature=0, max_tokens=60, messages=msgs, tools=TOOLS,
                                                 tool_choice="required" if turn == 0 else "none").choices[0].message
            if not msg.tool_calls:
                return msg.content, tool_result
            msgs.append({"role": "assistant", "content": "", "tool_calls": [c.model_dump() for c in msg.tool_calls]})
            for call in msg.tool_calls:
                with tracer.start_as_current_span(f"execute_tool {call.function.name}", attributes={
                        "gen_ai.operation.name": "execute_tool", "gen_ai.tool.name": call.function.name}):
                    tool_result = lookup(json.loads(call.function.arguments).get("order_id", ""))
                msgs.append({"role": "tool", "tool_call_id": call.id, "content": tool_result})
    return msg.content, tool_result

def judge(question, answer, evidence=None):
    facts = f"Order database says: {evidence}\n" if evidence else ""
    prompt = (f"{facts}Customer question: {question}\nAgent answer: {answer}\n"
              "Is the agent's answer correct? Reply with one word: PASS or FAIL.")
    out = client.chat.completions.create(model=MODEL, temperature=0, max_tokens=5,
                                         messages=[{"role": "user", "content": prompt}]).choices[0].message.content
    return "FAIL" if "FAIL" in out.upper() else "PASS" if "PASS" in out.upper() else "?"

rows = []
for sid, question, stem, yes_no in SESSIONS:
    answer, evidence = run_session(sid, question)
    rows.append(dict(sid=sid, q=question, a=answer or "", ev=evidence, ref=reference(answer, stem, yes_no)))

Reading this output

The reference finds two wrong answers. s06 says "Yes" to "Is order A-1001 delivered already?" (it has only shipped) and s08 says "Yes" to "Is A-1002 on the way?" (it is still processing). Both sentences are fluent and mention the right status, which is exactly why they are hard to catch.

The lesson's scripted judge passes everything. It checks structure: no errors, a tool call, a final output, few tokens. Every session has those, so it agrees on 6 of 8 only because 6 answers happen to be right. It cannot see content.

The small LLM judge is worse than useless here. Without the tool result it fails two correct answers (s03, s07) and passes both wrong ones: 4 of 8. Given the database's answer it improves to 5 of 8 but still passes both wrong answers. Neither catches a single failure. Grounding helps a judge only if the judge can reason over the evidence; a 0.5B model cannot, and larger judges need the same check before you trust them.

Part 1 of 4 · SpanEvent, SessionSummary, TraceCollector, scripted_llm_judge

"""Stdlib trace collector + LLM-judge evaluator.

Mirrors what Langfuse / Phoenix / Opik do with richer UIs: ingest spans,
group by session, score with an LLM judge, surface failure categories.
"""

from __future__ import annotations

from collections import Counter
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class SpanEvent:
    trace_id: str
    session_id: str
    name: str
    status: str = "ok"
    attributes: dict[str, Any] = field(default_factory=dict)


@dataclass
class SessionSummary:
    session_id: str
    trace_count: int
    error_count: int
    eval_score_mean: float
    failure_reasons: Counter


class TraceCollector:
    def __init__(self) -> None:
        self.spans: list[SpanEvent] = []

    def ingest(self, span: SpanEvent) -> None:
        self.spans.append(span)

    def by_session(self) -> dict[str, list[SpanEvent]]:
        result: dict[str, list[SpanEvent]] = {}
        for span in self.spans:
            result.setdefault(span.session_id, []).append(span)
        return result


def scripted_llm_judge(session_spans: list[SpanEvent]) -> tuple[float, str]:
    errors = sum(1 for s in session_spans if s.status == "error")
    has_tool = any(s.name.startswith("tool_call") for s in session_spans)
    has_final = any(s.attributes.get("gen_ai.output.reference_id")
                    for s in session_spans)
    tokens_over = any(s.attributes.get("tokens", 0) > 2000 for s in session_spans)
    score = 1.0
    if errors:
        score -= 0.4
    if not has_final:
        score -= 0.3
    if not has_tool:
        score -= 0.1
    if tokens_over:
        score -= 0.1
    score = max(0.0, score)
    if score >= 0.8:
        verdict = "PASS"
    elif score >= 0.5:
        verdict = "WARN"
    else:
        verdict = "FAIL"
    return score, verdict

Part 2 of 4 · categorize_failures, summarize

def categorize_failures(session_spans: list[SpanEvent]) -> Counter:
    reasons: Counter = Counter()
    for span in session_spans:
        if span.status != "error":
            continue
        reason = span.attributes.get("error.reason", "unknown")
        reasons[reason] += 1
    return reasons


def summarize(collector: TraceCollector) -> list[SessionSummary]:
    summaries: list[SessionSummary] = []
    for session_id, spans in collector.by_session().items():
        score, _ = scripted_llm_judge(spans)
        summaries.append(SessionSummary(
            session_id=session_id,
            trace_count=len(spans),
            error_count=sum(1 for s in spans if s.status == "error"),
            eval_score_mean=score,
            failure_reasons=categorize_failures(spans),
        ))
    summaries.sort(key=lambda s: s.eval_score_mean)
    return summaries

Industry practice
What's current (2024–2026)
  • Langfuse (MIT) is the most widely deployed open-source option; ClickHouse acquired it in January 2026 and kept the licence and self-hosting. It takes OpenTelemetry traces from any instrumentation.
  • Arize Phoenix (Elastic License 2.0, source-available rather than OSI open source) is built on OpenInference and strong on evaluations, experiments and RAG analysis; it has prompt management too.
  • Comet Opik (Apache 2.0) focuses on evaluation, automated prompt optimisation and guardrails. LangSmith, Braintrust, Datadog LLM Observability and MLflow tracing are the common commercial or adjacent choices.
  • Practice: one instrumentation per call, content capture off by default, and evaluators calibrated against a labelled set before anyone trusts their dashboard. LangChain's survey found 89% of teams had observability but only about half ran offline evaluations.
  • On your laptop: Phoenix runs as a single Python process with SQLite; Langfuse self-hosting needs Docker with Postgres, ClickHouse and Redis, a few GB of RAM, which fits in 16 GB alongside a small model.

Sources: Langfuse joins ClickHouse, Phoenix licence, Phoenix prompts, Opik, LangChain, State of Agent Engineering, OpenInference, Comet's framework comparison.

Recap
What to keep from this lesson
  • Platforms store, group and replay traces; evaluations say whether runs were right.
  • Two span vocabularies exist; normalise them, and never instrument one call twice.
  • OpenInference captures content by default; decide where personal data may go.
  • Judge an evaluator by its recall on known failures, not by its agreement rate.
  • Structure checks and small LLM judges miss fluent wrong answers.

Given an agent runtime and product requirements, pick an observability platform and scaffold the wiring.

Decision:

1. Need prompt management + session replay in one place -> **Langfuse**.
2. Need deep RAG relevancy + drift/anomaly detection -> **Phoenix**.
3. Need automated prompt optimization + PII guardrails -> **Opik**.
4. Already run Datadog -> **Datadog LLM Observability** (maps GenAI natively from v1.37+).
5. Need ELv2-free license -> **Langfuse** (MIT) or **Opik** (Apache 2.0); avoid Phoenix for pure OSS distribution.

Produce:

1. OTel GenAI instrumentation (Lesson 23) — this is the common substrate.
2. Platform-specific SDK or OTel exporter configuration.
3. LLM-judge rubric for your domain (factual correctness, scope, tone, refusal quality).
4. Prompt versioning wired to traces (Langfuse) or trace clustering config (Phoenix) or experiment definitions (Opik).
5. Guardrails on logged content: PII redaction, secret scrubbing.
6. Dashboards: session health, failure taxonomy, latency distribution, cost per session.

Hard rejects:

- Shipping without evals. Tracing alone is expensive logging.
- Using a self-written LLM-judge with no external verification. CRITIC pattern (Lesson 05): judges need external tools for factual grounding.
- Storing PII in span bodies. Always external store + reference IDs.

Refusal rules:

- If the user asks for "one platform for everything," refuse and offer the decision above. No single platform dominates all three axes.
- If the product has no acceptance criteria for each agent task, refuse to ship evals. An LLM-judge needs a rubric; a rubric needs product decisions.
- If the user wants "no sampling, capture everything," refuse. Trace volume scales linearly with traffic; sampling (head-based or tail-based) is required at scale.

Output: `instrumentation.py`, `judge.py`, `dashboards.md`, `README.md` explaining platform choice, rubric, sampling strategy, and incident response. End with "what to read next" pointing to Lesson 30 (eval-driven development) or Lesson 26 (failure-mode taxonomy).

Solutions

SolutionP1 · None of the judges

None of them. The reference check, written from the order database, finds two wrong answers (a "Yes" to "delivered already?" and a "Yes" to "on the way?"). The scripted judge passes all eight because it looks only at span structure. Qwen as judge passes both wrong answers with or without the tool result, and fails one or two correct ones. Agreement rates of 50 to 75% hide a recall of zero on the failures that matter.

SolutionB1 · Two spans per call, content on by default

Both instrumentations patch the same OpenAI client, so each call now produces two spans, one in each vocabulary, and the cost dashboard sums tokens over both: 88 input tokens for a 44-token call. And OpenInference records inputs and outputs by default (input.value, llm.input_messages.*), so prompts with customer data now land in the trace store, where OpenTelemetry's instrumentation had kept them out.

Fix: keep one instrumentation per library (OpenInference if the platform is Phoenix, OpenTelemetry GenAI otherwise; Langfuse accepts either), or deduplicate at the collector by trace and call ID. Hide content at the source (OPENINFERENCE_HIDE_INPUTS=true, OPENINFERENCE_HIDE_OUTPUTS=true) or with a collector processor, and if content is needed, store it externally behind its own access control. Add a test that one model call yields exactly one LLM span with no message text.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Weigh a trade-offYour team must choose an observability stack for a new model service. Half the team wants an all-in-one platform with evals, prompt versions and session replays. The other half wants a thin gateway that records every call and nothing more. How do you decide, and which pattern lets you avoid the choice?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Decide on four axes: the framework you run on, the license you can accept, the budget, and whether you must self-host. A bundled development platform fits a team that iterates on prompts and needs evals tied to traces. A gateway or telemetry tool fits a team that needs portable instrumentation that does not depend on a framework. The pattern that avoids the choice is to emit OpenTelemetry spans with the GenAI conventions from every call and ship them to more than one place: a gateway for day-to-day, an eval platform for regressions, and an archive for long-term analysis.

Two categories of tool.

Development platforms bundle observability with evals, prompt management, dataset versioning and session replay. You run experiments, compare prompts and regression-test a new prompt against old winners. Gateway and telemetry tools record the prompt, the response, the tokens, the latency, the model and the cost, and they stop there.

The four axes.

Axis Question
stack one framework, a raw SDK, or several vendors
license open source only, a source-available license, or commercial
budget a free tier, a team plan, or an enterprise contract
self-host required, welcome, or never

The trap.

Instrumenting inside the agent framework ties the traces to that framework. Instrumenting at the HTTP or SDK layer is portable, so a change of framework or a second framework does not lose the history.

The glue pattern.

  1. Emit OpenTelemetry spans with the GenAI conventions from every model call.
  2. Route them to a gateway or telemetry tool for the daily view.
  3. Ship a copy to an eval platform for regressions.
  4. Archive them in a data lake for long-term analysis.

Every tool that reads the conventions can read the same spans, so the stack is a routing decision, not a rewrite.

What to insist on in either case.

  • Prompt versions tied to traces. When production regresses, you must be able to bisect to the prompt change that caused it.
  • An eval strategy. Tracing without evaluation is expensive logging.
  • A sampling policy at scale, because full retention at volume is more expensive than the calls it records.

Plausible wrong answers.

  • "Pick the tool with the most features." Features you do not use cost money and couple you. Pick on stack, license, budget and hosting.
  • "Tracing is enough, evals can come later." Traces without evals are logs with a price. A regression hides in them until a user reports it.
  • "The gateway records every call, so skip the platform." A proxy sees calls, not agent steps or sessions. It misses the multi-step traces that an agent regression needs.

Follow-ups an interviewer may ask.

  • (level 3) Why instrument at the SDK layer rather than inside the framework? Expected: framework hooks tie you to the framework. The SDK layer keeps working when you change frameworks or add a second one.
  • (level 3) What breaks when prompt versions are not tied to traces? Expected: when production regresses you cannot bisect to the prompt change that caused it.
  • (level 4) You ship the same spans to two backends. What do you check so that they agree? Expected: the same conventions version, the same sampling rules on both exporters, and one source of truth for cost attribution, so that two dashboards do not show two bills.
