Why this came about

GPT-2 (2019) was trained on 40 GB of web pages linked from Reddit, and OpenAI noticed that bigger models trained on more text kept getting better in a surprisingly regular way. In 2020 Jared Kaplan and colleagues measured this: loss falls as a smooth power law in model size, data and compute. In 2022 DeepMind's Chinchilla paper (Hoffmann and colleagues) corrected the recipe: for a fixed budget, models of the day were too big and trained on too little data; about 20 tokens per parameter was the sweet spot. Since then, the work of building a base model has become mostly a data problem: collecting, cleaning, deduplicating and mixing trillions of tokens, then spending months of GPU time on next-token prediction.

In plain words first
Read the library, then predict the next word

Pretraining is the next-token game of Lessons F5.5 and F6.4, played on a large fraction of everything ever written online, plus books, code and scientific papers. The model sees each piece of text roughly once and gets slightly better at predicting the next token each time. Because predicting text well requires knowing grammar, facts, styles, reasoning patterns and code, the model picks all of those up along the way. The result, a base model, is a superb text continuer but not yet an assistant: ask it a question and it may answer, or continue with five more questions.

Step 1 · Where the data comes from

Source What it contributes Typical issues
Web crawl (for example Common Crawl, billions of pages a month) breadth: every topic, style and language spam, boilerplate, duplicates, toxic or private content
Code (public repositories) programming ability, structured reasoning licences, secrets accidentally committed

Curated and synthetic datalater · F7.7 maths, reasoning, instruction-like text quality control, bias from the model that generated it

Scale has grown fast: GPT-2 used about 9 billion tokens, GPT-3 (2020) about 300 billion, Llama 2 (2023) 2 trillion, and Llama 3 (2024) over 15 trillion. Open datasets such as FineWeb (2024, about 15 trillion tokens of filtered Common Crawl) document their processing in detail. The steps below are simplified versions of what such pipelines do.

Step 2 · Cleaning: heuristic quality filters

Most raw web text is not worth training on: menus, cookie banners, keyword spam, and pages that repeat the same line. Simple rules remove much of it:

docs = {
    "support email": "Hi Asha, thanks for your patience. Your parcel was delayed by the weather, "
                     "and it is now out for delivery. You should receive it by 6 pm today.",
    "keyword spam": "cheap phones cheap phones best price cheap phones buy now best price cheap cheap phones",
    "menu": "Home | About | Contact | Login | Cart | Home | About | Contact",
    "short": "Click here",
    "recipe": "Boil the water, add the tea leaves and let them steep for three minutes before adding milk.",
}

def quality_checks(text):
    words = text.split()
    problems = []
    if len(words) < 8:
        problems.append("too short")
    if len(set(words)) / len(words) < 0.5:
        problems.append("too repetitive")                      # few distinct words
    if sum(c in "|#@{}<>" for c in text) / len(text) > 0.02:
        problems.append("too many symbols")
    if not any(text.rstrip().endswith(p) for p in ".!?"):
        problems.append("no sentence ending")
    return problems

for name, text in docs.items():
    problems = quality_checks(text)
    print(f"{name:<14} {'keep' if not problems else 'drop: ' + ', '.join(problems)}")
What you should see
support email  keep
keyword spam   drop: too repetitive, no sentence ending
menu           drop: too repetitive, too many symbols, no sentence ending
short          drop: too short, no sentence ending
recipe         keep

Real pipelines use dozens of such rules (the Gopher and C4 rules are well-known sets), plus classifiers trained to recognise "educational" or "high-quality" text; FineWeb-Edu, for example, used an LLM to label samples and trained a small classifier on those labels to score every page.

Step 3 · Deduplication

The web is full of copies: mirrored pages, quoted articles, templates. Duplicates waste compute and make models memorise and repeat text. Exact duplicates are found by hashing; near duplicates by comparing overlapping word sequences (shingles):

import hashlib

def fingerprint(text):
    return hashlib.sha256(" ".join(text.lower().split()).encode()).hexdigest()[:12]   # normalise spacing and case

def shingles(text, n=3):
    w = text.lower().split()
    return {" ".join(w[i:i + n]) for i in range(len(w) - n + 1)}      # every run of 3 words

def jaccard(a, b):
    return len(a & b) / len(a | b)                                  # shared / total distinct shingles

a = "Your parcel was delayed by the weather and is now out for delivery today."
b = "your parcel was delayed by the weather  and is now out for delivery today."
c = "Your parcel was delayed by heavy rain and is now out for delivery today."
d = "Boil the water, add the tea leaves and let them steep for three minutes."

print("exact duplicate (a, b):", fingerprint(a) == fingerprint(b))
for name, other in [("b", b), ("c", c), ("d", d)]:
    print(f"similarity of a and {name}: {jaccard(shingles(a), shingles(other)):.2f}")
What you should see
exact duplicate (a, b): True
similarity of a and b: 1.00
similarity of a and c: 0.50
similarity of a and d: 0.00

a and b differ only in case and spacing, so after normalising they hash the same. c changes two words and still shares half its three-word shingles (0.50), enough to count as a near-duplicate under typical thresholds of around 0.5; d is unrelated. Comparing every pair is impossible for billions of documents, so real systems use MinHash and locality-sensitive hashing to find similar pairs quickly. The same tool decides whether test questions leaked into training data (Lesson F3.5's leakage, Lesson 11.3's contamination).

Step 4 · Filtering with a language model's perplexity

A small language modellater · 1.5 trained on clean text finds clean text unsurprising. Its perplexity (Lesson F6.7) can rank documents:

import math
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

tok = AutoTokenizer.from_pretrained("gpt2")
lm = AutoModelForCausalLM.from_pretrained("gpt2")
lm.eval()

def perplexity(text):
    enc = tok(text, return_tensors="pt")
    with torch.no_grad():
        return math.exp(lm(**enc, labels=enc["input_ids"]).loss.item())

for name in ["support email", "recipe", "keyword spam", "menu"]:
    print(f"{name:<14} perplexity {perplexity(docs[name]):8.1f}")
What you should see
support email  perplexity     25.3
recipe         perplexity     24.2
keyword spam   perplexity    210.4
menu           perplexity     25.2

Natural prose scores low (about 25), and the keyword spam high (about 210): it is not how people write. But the menu scores as low as real prose, because once "Home | About | Contact" has appeared, the model easily predicts it repeating. Perplexity filters catch unnatural text well but miss repetitive boilerplate, which the rules of Step 2 caught; that is why pipelines combine several filters. Filters also have a cost: text that is unusual for the scoring model (dialects, rare languages, technical notation) can be removed unfairly, so filtering choices shape what the final model is good and bad at.

Step 5 · Scaling laws

The central empirical finding of modern AI: a model's loss falls smoothly and predictably as you add parameters (N), training tokens (D) and compute (C ≈ 6ND, Lesson F4.6). The Chinchilla paper fitted a formula of the form

L(N, D) = E + A / N^α + B / D^β

where E is the loss no model can beat (the text's own randomness), the second term shrinks as the model grows, and the third as the data grows. With a fixed compute budget you must trade size against data:

Using the constants from a 2024 re-estimate of the Chinchilla fit (Besiroglu and colleagues at Epoch AI), find the best model size for several budgets:

E0, A, B, alpha, beta = 1.82, 482.01, 2085.43, 0.3478, 0.3658

def predicted_loss(N, D):
    return E0 + A / N ** alpha + B / D ** beta

print(f"{'compute (FLOPs)':>16} {'best size':>10} {'tokens':>10} {'tokens/param':>13} {'loss':>6}")
for C in [1e21, 1e22, 1e23, 1e24, 1e25]:
    candidates = [10 ** (k / 100) for k in range(800, 1300)]          # 100 million to 10 trillion parameters
    N = min(candidates, key=lambda n: predicted_loss(n, C / (6 * n)))
    D = C / (6 * N)
    print(f"{C:>16.0e} {N / 1e9:>9.1f}B {D / 1e12:>9.2f}T {D / N:>13.0f} {predicted_loss(N, D):>6.3f}")
What you should see
 compute (FLOPs)  best size     tokens  tokens/param   loss
           1e+21       2.8B      0.06T            22  2.308
           1e+22       9.1B      0.18T            20  2.144
           1e+23      29.5B      0.56T            19  2.035
           1e+24      95.5B      1.75T            18  1.963
           1e+25     309.0B      5.39T            17  1.915
Reading this output
  • The best number of tokens per parameter stays close to 20 across budgets: Chinchilla's rule of thumb.
  • Each tenfold increase in compute buys roughly a threefold bigger model trained on roughly three times more data, and lowers the loss by a smaller amount each time: steady but diminishing returns.
  • These are predictions for one model family and dataset. The exact constants change with architecture and data quality; the shape of the curves has held up remarkably well.

Step 6 · Why real models break the rule

"Compute-optimal" means the best model for a fixed training budget. But a model is trained once and used millions of times, and a smaller model is cheaper every time it runs. So labs often train smaller models on far more data than the rule suggests:

for name, N, D in [("Chinchilla-optimal 8B", 8e9, 160e9), ("Llama 3 8B (2024)", 8e9, 15e12), ("Llama 3 70B (2024)", 70e9, 15e12)]:
    print(f"{name:<22} {D / N:>6,.0f} tokens per parameter   predicted loss {predicted_loss(N, D):.3f}")
What you should see
Chinchilla-optimal 8B      20 tokens per parameter   predicted loss 2.160
Llama 3 8B (2024)       1,875 tokens per parameter   predicted loss 2.025
Llama 3 70B (2024)        214 tokens per parameter   predicted loss 1.933

Llama 3 8B saw almost 100 times more tokens than "optimal" and keeps improving: the extra training lowers its loss well below the Chinchilla-optimal 8B, making a small model that is cheap to run much more capable. The cost is a bigger training bill, and eventually a shortage of good data, which is one reason for the growing use of synthetic data and of the later training stages (Lessons F7.2 and F7.3).

Tip
What scale buys, and what it does not

Lower loss has come with abilities that small models lack: following examples given in the prompt (in-context learninglater · 11.3, first shown clearly with GPT-3 in 2020), writing working code, solving multi-step problems. Whether some abilities appear suddenly at a certain size ("emergence") or only look sudden because of how they are measured is still debated. What scale alone does not fix: models still state falsehoods confidently, know nothing after their training data ends, and cannot act in the world. Lesson F7.4 covers these limits, and Chapters 2 to 4 the techniques that work around them.

The same idea as a formula
  • training compute: C ≈ 6ND FLOPs
  • Chinchilla loss model: L(N, D) = E + A N^(−α) + B D^(−β)
  • compute-optimal size: minimise L(N, C / 6N) over N; with α ≈ β, both N and D grow roughly as √C, giving a roughly constant ratio D/N ≈ 20
  • near-duplicate test: Jaccard(S_a, S_b) = |S_a ∩ S_b| / |S_a ∪ S_b| over word n-gram sets
Check your mental model
  • ✗ "Pretraining teaches the model to answer questions."
    ✓ It teaches next-token prediction. Answering helpfully comes from the fine-tuninglater · F7.2 stages in Lesson F7.2.
  • ✗ "More data is always better, whatever its quality."
    ✓ Quality filtering and deduplication often improve models more than adding raw text; low-quality data can make models worse.
  • ✗ "Compute-optimal models are the best models to deploy."
    ✓ They are best for a fixed training budget. For deployment, a smaller model trained on more data is often better value.

SolutionP1 · An advertising line

An empty list, []: the text is kept. It has 10 words (enough to pass the length check), no repeated words, no symbols, and ends with "!". Simple heuristics miss short promotional text; that is why pipelines also use trained quality classifiers.

SolutionM1 · Repeated lines
def repeated_lines(text, limit=0.3):
    lines = [l.strip() for l in text.splitlines() if l.strip()]
    if not lines:
        return False
    counts = {l: lines.count(l) for l in lines}
    repeated = sum(1 for l in lines if counts[l] > 1)
    return repeated / len(lines) > limit

Add if repeated_lines(text): problems.append("repeated lines") to quality_checks. Navigation menus and footers that repeat on every line of a scraped page are caught by this kind of rule.

SolutionX1 · Size against data

Both runs use about the same compute (6 × 10⁹ × 10¹² = 6 × 10²¹ and 6 × 10¹⁰ × 10¹¹ = 6 × 10²¹ FLOPs). The 1B model on 1T tokens (1,000 tokens per parameter) has a predicted loss of about 2.26; the 10B model on 100B tokens (10 tokens per parameter) about 2.18. With equal compute, the formula slightly prefers the bigger model here, as 10 tokens per parameter is closer to the optimum of about 20 than 1,000 is. But the 1B model is ten times cheaper to run afterwards.

Recap
  • Pretraining is next-token prediction on trillions of tokens of web text, code, books and papers; it produces a base model that continues text.
  • Data pipelines extract text, filter quality with rules and classifiers, remove duplicates, and mix sources; data choices shape what the model is good at.
  • Scaling laws describe loss falling smoothly with parameters, data and compute; Chinchilla found about 20 tokens per parameter optimal for a fixed training budget.
  • Deployed models are often smaller and trained far longer, trading training cost for cheaper use.
  • Scale brings new abilities but does not remove hallucinationlater · F7.4, knowledge cutoffs or the inability to act.
