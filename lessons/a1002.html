The problem

In plain words first

A working tokenizer is more than the merge algorithm. Before merging, text is cleaned up (normalised) and cut into word-sized chunks so that pieces never straddle two words. Some tokens are reserved as markers, such as "start of text" or "end of this message", and must never be produced by ordinary text. And a chat model expects a conversation laid out in one exact format, its chat template, made of those markers. This lesson builds that pipeline in Python, compares the pre-tokenisation rules of three OpenAI tokenizers, shows what normalisation does, and prints the real chat templates of three model families, including one way user text can impersonate a marker.

Your BPE tokenizer from Lesson 10.1 works on English text. Now throw Japanese at it. Or emoji. Or Python code with mixed tabs and spaces.

It breaks.

Not because BPE is wrong -- because the implementation is incomplete. A production tokenizer handles raw bytes in any encoding, normalizes Unicode before splitting, manages special tokens that never get merged, chains pre-tokenization with subword splitting, and does all of this fast enough to not bottleneck a training pipeline processing 15 trillion tokens.

GPT-2's tokenizer has 50,257 tokens. Llama 3 has 128,256. GPT-4 has roughly 100,000. These are not toy numbers. The merge tables behind those vocabularies were trained on hundreds of gigabytes of text, and the surrounding machinery -- normalization, pre-tokenization, special token injection, chat template formatting -- is what separates a tokenizer that handles "hello world" from one that handles the entire internet.

You are going to build that machinery.

Idea 1 · The Full Pipeline

A production tokenizer is not one algorithm. It is a pipeline of five stages, each solving a different problem.

Each stage has a specific job:

Stage What It Does Why It Matters
Normalize NFKC Unicode, lowercase optional, strip accents optional "fi" ligature (U+FB01) becomes "fi" (two chars). Without this, same word gets different tokens.
Pre-Tokenize Split text into chunks before BPE Prevents BPE from merging across word boundaries. "the cat" should never produce a token "e c".
BPE Merge Apply learned merge rules to byte sequences The core compression. Turns raw bytes into subword tokens.
Special Tokens Inject [BOS], [EOS], [PAD], chat template markers These tokens have fixed IDs. They never participate in BPE merges. The model needs them for structure.
ID Mapping Convert token strings to integer IDs The model sees integers, not strings.

Idea 2 · Byte-Level BPE

Lesson 10.1's tokenizer operated on UTF-8 bytes. That was the right call. But we skipped something important: what happens when those bytes are not valid UTF-8?

Byte-level BPE solves this by treating every possible byte value (0-255) as a valid token. Your base vocabulary is exactly 256 entries. Any file -- text, binary, corrupted -- can be tokenized without producing an unknown token.

GPT-2 added a trick: map each byte to a printable Unicode character so the vocabulary stays human-readable. Byte 0x20 (space) becomes the character "Ġ" in their mapping, which is why GPT-2-style vocabulary files are full of "Ġ". This is purely cosmetic. The algorithm does not care.

The real power: byte-level BPE handles every language on earth. Chinese characters are 3 UTF-8 bytes each. Japanese can be 3-4 bytes. Arabic, Devanagari, emoji -- all just byte sequences. The BPE algorithm finds patterns in these byte sequences exactly the same way it finds patterns in English ASCII bytes.

Idea 3 · Pre-Tokenization

Before BPE touches your text, you need to split it into chunks. This prevents the merge algorithm from creating tokens that span word boundaries.

GPT-2 uses a regex pattern to split text:

'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+

This pattern splits on contractions ("don't" becomes "don" + "'t"), words with optional leading spaces, numbers, punctuation, and whitespace. The leading space is kept attached to the word -- so "the cat" becomes [" the", " cat"], not ["the", " ", "cat"].

Llama 1 and 2 used SentencePiece, which needs no regex: it treats the space as an ordinary symbol ("▁") and by default still keeps pieces from crossing word boundaries. Llama 3 switched to a tiktoken-style regex like GPT-4's.

The choice matters. The regex decides, for example, whether numbers are cut into groups of three or kept whole, whether "'VE" counts as a contraction, and whether runs of spaces in code become one token (the second run under Step 6).

Idea 4 · Special Tokens

Every production tokenizer reserves token IDs for structural markers:

Token Purpose Used By
[BOS] / <s> Beginning of sequence Llama 3, GPT
[EOS] / </s> End of sequence All models
[PAD] Padding for batch alignment BERT, T5
[UNK] Unknown token (byte-level BPE eliminates this) BERT, WordPiece
<\|im_start\|> Chat message boundary start ChatGPT, Qwen
<\|im_end\|> Chat message boundary end ChatGPT, Qwen
<\|start_header_id\|>, <\|end_header_id\|> Wrap the role name of each turn Llama 3
<\|eot_id\|> End of a turn Llama 3

Special tokens are never split by BPE. They are matched exactly before the merge algorithm runs, replaced with their fixed ID, and the surrounding text is tokenized normally.

Idea 5 · Chat Templates

This is where most people get confused and most implementations break.

When you send messages to a chat model, the API accepts a list of messages:

[
  {"role": "system", "content": "You are helpful."},
  {"role": "user", "content": "Hello"},
  {"role": "assistant", "content": "Hi there!"}
]

The model does not see JSON. It sees a flat token sequence. The chat template converts messages into that flat sequence using special tokens. Every model does this differently:

Llama 3:
<|begin_of_text|><|start_header_id|>system<|end_header_id|>

You are helpful.<|eot_id|><|start_header_id|>user<|end_header_id|>

Hello<|eot_id|><|start_header_id|>assistant<|end_header_id|>

Hi there!<|eot_id|>

ChatGPT:
<|im_start|>system
You are helpful.<|im_end|>
<|im_start|>user
Hello<|im_end|>
<|im_start|>assistant
Hi there!<|im_end|>

Get the template wrong and the model produces garbage. It was trained on one exact format. Any deviation -- a missing newline, a swapped token, an extra space -- puts the input outside the training distribution.

Idea 6 · Speed

Python is too slow for production tokenization.

tiktoken (OpenAI) is written in Rust with Python bindings. HuggingFace tokenizers is also Rust. SentencePiece is C++. These achieve 10-100x speedups over pure Python.

For perspective: tokenizing 15 trillion tokens for Llama 3 pre-training at 1 million tokens per second (fast Python) would take 174 days. At 100 million tokens per second (Rust), it takes 1.7 days.

You are building in Python to understand the algorithm. In production, you would use a compiled implementation and only touch the Python wrapper.

The same idea as a formula

A tokenizer is a composition of functions:

ids=map(merge(bytes(pretok(norm(x)))))

with special tokens cut out of x first and given fixed IDs. Decoding concatenates the byte strings of the IDs and decodes UTF-8. Decoding inverts encoding exactly only if normalisation does nothing: decode(encode(x))=norm(x), which is why GPT and Llama 3 tokenizers do not normalise at all.

Bytes per character in UTF-8: 1 for ASCII, 2 for most accented Latin, Greek, Cyrillic, Arabic and Hebrew, 3 for most other scripts (Devanagari, Chinese, Japanese, Korean), 4 for emoji. With no merges a byte-level tokenizer therefore needs 3× as many tokens per Chinese character as per English letter.

Fertility = tokens ÷ words. For languages written without spaces, "words" by whitespace are meaningless; tokens per character is the fair measure.

Throughput. T tokens at r tokens per second take T/r seconds: 15 trillion tokens at 106/s is 1.5×107 s ≈ 174 days, at 108/s ≈ 1.7 days.

Worked example
Through the pipeline by hand

Input: "Don't ﬁx it." (with the single-character ligature "ﬁ", U+FB01).

  1. Normalise (NFKC): "ﬁ" → "fi". (GPT-4's tokenizer skips this step, so it sees a rare three-byte character instead; the run after Step 6 shows "ﬁnance" taking 4 tokens and "finance" 1.)
  2. Pre-tokenise (GPT-2 regex): ["Don", "'t", " fix", " it", "."]. The contraction is its own chunk and each word keeps its leading space.
  3. Bytes: " fix" → 0x20 0x66 0x69 0x78; in GPT-2's printable mapping "Ġfix".
  4. Merge: each chunk is merged on its own, so no token can contain "t f" across the boundary.
  5. Special tokens: a chat template would wrap the result, for example <|im_start|>user\n … <|im_end|>, each marker one fixed ID.

Counting bytes. "你好" is 2 characters, 6 bytes: with no merges, 6 tokens. "🔥" is 1 character, 4 bytes.

Check your mental model

    ✓ NFKC turns "x²" into "x2" and "Ⅻ" into "XII": it changes meaning, and decoding no longer gives back the original text. Most LLM tokenizers skip it.
  • ✗ "Special tokens can only come from the chat template."
    ✓ By default Hugging Face tokenizers turn the text "<|im_end|>" inside a user message into the real marker; only split_special_tokens=True treats it as ordinary text.
  • ✗ "All chat models use the same message format."

def bytes_to_tokens(text):

Step 2 · Pre-Tokenizer with Regex

Split text into chunks using the GPT-2 regex pattern. Each chunk gets tokenized independently by BPE.

import re

try:
    import regex
    GPT2_PATTERN = regex.compile(
        r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
    )
except ImportError:
    GPT2_PATTERN = re.compile(
        r"""'(?:[sdmt]|ll|ve|re)| ?[^\W\d_]+| ?\d+| ?(?:[^\s\w]|_)+|\s+(?!\S)|\s+"""
    )

def pre_tokenize(text):
    return [match.group() for match in GPT2_PATTERN.finditer(text)]

The regex module supports Unicode property escapes (\p{L} for letters, \p{N} for numbers). The standard library re module does not, so the fallback builds the same classes from \w: [^\W\d_] matches any Unicode letter and \d any Unicode digit. For production multilingual tokenizers, install regex.

Try it:

print(pre_tokenize("Hello, world! Don't stop."))
# ['Hello', ',', ' world', '!', ' Don', "'t", ' stop', '.']
What you should see
['Hello', ',', ' world', '!', ' Don', "'t", ' stop', '.']

The leading space stays attached to the word that follows it. The first word has no space before it, so its chunk is Hello. Contractions split at the apostrophe. Punctuation becomes its own chunk. BPE will never merge tokens across these boundaries.

Step 3 · BPE on Byte Sequences

The core algorithm from Lesson 10.1, but now operating on pre-tokenized chunks independently.

from collections import Counter

def get_byte_pairs(chunks):
    pairs = Counter()
    for chunk in chunks:
        byte_seq = list(chunk.encode("utf-8"))
        for i in range(len(byte_seq) - 1):
            pairs[(byte_seq[i], byte_seq[i + 1])] += 1
    return pairs

def apply_merge(byte_seq, pair, new_id):
    merged = []
    i = 0
    while i < len(byte_seq):
        if i < len(byte_seq) - 1 and byte_seq[i] == pair[0] and byte_seq[i + 1] == pair[1]:
            merged.append(new_id)
            i += 2
        else:
            merged.append(byte_seq[i])
            i += 1
    return merged

Step 4 · Special Token Handling

Special tokens need exact matching and fixed IDs. They bypass BPE entirely.

class SpecialTokenHandler:
    def __init__(self):
        self.special_tokens = {}
        self.pattern = None

    def add_token(self, token_str, token_id):
        self.special_tokens[token_str] = token_id
        escaped = [re.escape(t) for t in sorted(self.special_tokens.keys(), key=len, reverse=True)]
        self.pattern = re.compile("|".join(escaped))

    def split_with_specials(self, text):
        if not self.pattern:
            return [(text, False)]
        parts = []
        last_end = 0
        for match in self.pattern.finditer(text):
            if match.start() > last_end:
                parts.append((text[last_end:match.start()], False))
            parts.append((match.group(), True))
            last_end = match.end()
        if last_end < len(text):
            parts.append((text[last_end:], False))
        return parts

Step 5 · Full Tokenizer Class

Chain everything together: normalize, split on special tokens, pre-tokenize, BPE merge, map to IDs.

import unicodedata

class ProductionTokenizer:
    def __init__(self):
        self.merges = {}
        self.vocab = {i: bytes([i]) for i in range(256)}
        self.special_handler = SpecialTokenHandler()
        self.next_id = 256

    def normalize(self, text):
        return unicodedata.normalize("NFKC", text)

    def train(self, text, num_merges):
        text = self.normalize(text)
        chunks = pre_tokenize(text)
        chunk_bytes = [list(chunk.encode("utf-8")) for chunk in chunks]

        for i in range(num_merges):
            pairs = Counter()
            for seq in chunk_bytes:
                for j in range(len(seq) - 1):
                    pairs[(seq[j], seq[j + 1])] += 1
            if not pairs:
                break
            best = max(pairs, key=pairs.get)
            new_id = self.next_id
            self.next_id += 1
            self.merges[best] = new_id
            self.vocab[new_id] = self.vocab[best[0]] + self.vocab[best[1]]
            chunk_bytes = [apply_merge(seq, best, new_id) for seq in chunk_bytes]

    def add_special_token(self, token_str):
        token_id = self.next_id
        self.next_id += 1
        self.special_handler.add_token(token_str, token_id)
        self.vocab[token_id] = token_str.encode("utf-8")
        return token_id

    def encode(self, text):
        text = self.normalize(text)
        parts = self.special_handler.split_with_specials(text)
        all_ids = []
        for part_text, is_special in parts:
            if is_special:
                all_ids.append(self.special_handler.special_tokens[part_text])
            else:
                for chunk in pre_tokenize(part_text):
                    byte_seq = list(chunk.encode("utf-8"))
                    for pair, new_id in self.merges.items():
                        byte_seq = apply_merge(byte_seq, pair, new_id)
                    all_ids.extend(byte_seq)
        return all_ids

    def decode(self, ids):
        byte_parts = []
        for token_id in ids:
            if token_id in self.vocab:
                byte_parts.append(self.vocab[token_id])
        return b"".join(byte_parts).decode("utf-8", errors="replace")

    def vocab_size(self):
        return len(self.vocab)

Reading this output

Bytes. UTF-8 uses 1 byte per English letter, 3 per Chinese or Japanese character and 4 per emoji, so before any merges Japanese "こんにちは" is 15 tokens for 5 characters.

Pre-tokenisation. The GPT-2 regex keeps each word with its leading space (" world", " stop"), splits contractions ("'t"), and cuts "$3.14" into " $", "3", ".", "14". With the chunks fixed, merges can never cross a word boundary, and the 50 merges learned are whole words with their space: " model", " learning", " quick", " brown".

Encoding. Trained text compresses well ("The quick brown fox." is 5 tokens). Text the corpus never saw stays at one token per byte: the Chinese characters and the emoji are 24 and 12 tokens for 24 and 12 bytes. "Machine" at the start of a sentence is 6 tokens even though " Machine" with a space was merged: the two are different pieces. The special tokens are matched before merging, so "<|begin|><|user|>Hello<|end|>" becomes the fixed IDs 306 and 308, five byte tokens for "Hello", and 307.

GPT-4 comparison. Several of GPT-4's tokens display as "�": a Chinese character or emoji is 3 or 4 bytes, and GPT-4 sometimes splits those bytes across tokens, so one token alone is not valid UTF-8. The fertility table divides tokens by whitespace-separated words, which is why Chinese and Japanese show 24 and 32 "tokens per word": a whole sentence without spaces counts as one word. For such languages, measure tokens per character instead.

Reading this output

Three regexes, three splits. GPT-2 cuts "I'VE" into "I", "'", "VE" because its contraction rule only knows lower case, and keeps "1234" whole. GPT-4's cl100k recognises "'VE" case-insensitively and cuts numbers into groups of at most three digits ("123", "4"), so the same number always tokenizes the same way regardless of what follows. GPT-4o's o200k keeps "I'VE" and " Don't" as single chunks. All three treat runs of spaces specially: two spaces before "ask" become a separate " " chunk plus " ask", so the word itself still looks the same as with one space.

Normalisation. The ligature "ﬁ" makes "ﬁnance" 4 GPT-4 tokens; after NFKC it is "finance", 1 token. Full-width "ＧＰＵ" goes from 6 tokens to 1. "café" typed with a combining accent is 5 code points and 3 tokens; NFKC composes it to the usual 4 code points and 2 tokens. But NFKC also turns "x²" into "x2" and "Ⅻ" into "XII", which changes meaning, and the original can no longer be recovered by decoding. That is why GPT and Llama 3 tokenizers do not normalise and instead learn the variants as separate byte sequences.

Byte map. GPT-2 shows the space byte as "Ġ" and newline as "Ċ"; printable ASCII stays itself. " hello" is stored as "Ġhello", the form you will see in every GPT-2-style vocabulary file.

Industry practice
What's current (2024–2026)
  • Chat templates live in the tokenizer files. Hugging Face models ship a Jinja chat template, applied with apply_chat_template; inference servers (vLLM, SGLang, TGI) use the same template, and mismatches are a common source of silent quality loss.
  • Byte-level BPE with regex pre-tokenisation (tiktoken-style) is the default for current open models; o200k's regex keeps contractions and case variants together.
  • Special-token injection is handled by escaping or split_special_tokens on untrusted text, alongside instruction-hierarchy training in the model.

Recap
What to keep from this lesson
  • A tokenizer is a pipeline: normalise, pre-tokenise, byte-encode, merge, add special tokens.
  • The pre-tokeniser regex decides which pieces can ever exist (numbers, contractions, spaces).
  • Normalisation changes text; LLM tokenizers usually skip it so decoding is exact.
  • Special tokens have fixed IDs and must not be produced by untrusted text.
  • Always use the model's own chat template; formats differ and can drop parts silently.

# Production Tokenizer Builder

When building or debugging a tokenizer for an LLM project, follow this framework.

## Pipeline Checklist

Every production tokenizer needs these five stages. If one is missing, you will hit edge cases in production.

1. **Normalize** -- Apply NFKC Unicode normalization. This collapses ligatures ("fi" -> "fi"), normalizes fullwidth characters, and standardizes whitespace. Skip this and the same word gets different token IDs depending on how it was typed.

2. **Pre-Tokenize** -- Split text into chunks before BPE. Use GPT-2's regex pattern for English-centric models. Use SentencePiece's raw-byte approach for multilingual models. The choice determines whether BPE can merge across word boundaries.

3. **BPE Merge** -- Apply the learned merge table to byte sequences within each chunk. The merge table IS the tokenizer's learned knowledge. Everything else is plumbing.

4. **Special Token Injection** -- Match special tokens exactly before BPE runs. [BOS], [EOS], [PAD], chat template markers get fixed IDs. They never participate in merges.

5. **ID Mapping** -- Convert token strings to integers. The model sees integers only.

## Debugging Tokenizer Issues

**Symptom: model produces garbage on chat input**
- Check the chat template. Every model has a different format. Llama 3 uses `<|start_header_id|>` markers. ChatGPT uses `<|im_start|>` markers. A wrong template puts input outside the training distribution.

**Symptom: non-English text uses too many tokens**
- Check fertility (tokens per word). Above 2.0 means the tokenizer wastes context window on that language. Solutions: retrain with more multilingual data, increase vocabulary size, or use SentencePiece with Unigram.

**Symptom: numbers and arithmetic fail**
- Check how digits are tokenized. "1234" as one token means the model cannot do digit-level operations. Split digits individually during pre-tokenization.

**Symptom: code tokens are inefficient**
- Check how indentation is handled. GPT-2's tokenizer wastes tokens on spaces. Codex and StarCoder use special indentation tokens (4 spaces = 1 token).

## Vocabulary Size Decision

- 32K tokens: single-language, small model, limited compute. Embedding layer is 32K * d_model parameters.
- 50K-64K: multilingual or code-heavy. Good balance for most projects.
- 100K+ (GPT-4, Llama 3): only with massive training data. Shorter sequences but 100K * d_model embedding parameters.

For a 4096-dimensional model: 32K vocab = 131M embedding params. 128K vocab = 524M embedding params. That is 400M parameters just in the embedding layer.

## Speed Requirements

- Training data tokenization: use Rust-backed libraries (tiktoken, HuggingFace tokenizers). Pure Python is 10-100x slower.
- Inference tokenization: latency matters less (single sequence), but still use compiled implementations.
- Benchmark: tokenize 1GB of text and measure wall clock time. If it takes more than 60 seconds, switch to a Rust backend.

## Chat Template Validation

Before deploying any chat model, verify the template:

1. Encode a known conversation with the tokenizer
2. Decode it back to text
3. Compare character-by-character with the expected format from the model's documentation
4. Pay attention to: newlines after header tokens, spaces before content, end-of-turn markers
5. Test edge cases: empty system message, very long user message, multiple assistant turns

Getting the chat template wrong is the most common source of degraded chat model performance.

Solutions

SolutionP1 · Kept as their own chunk

Kept as their own chunk. The GPT-2 regex has a rule \s+(?!\S): a run of spaces that is not followed by a non-space character, which matches all but the last space of a run. So "Don't ask" becomes " Don", "'t", " ", " ask": the extra two spaces are one chunk, and " ask" still carries exactly one leading space, so it is the same token as in normal text. This keeps the vocabulary's words consistent and lets runs of spaces (indentation in code) become their own tokens.

SolutionB1 · Spaces get lost

Spaces disappear. text.split(" ") throws the spaces away instead of keeping them in a chunk, so they are never encoded: "Hello world" decodes to "Helloworld", and "The quick brown fox." to "Thequickbrownfox.". The round-trip test that passed for every input now fails for every input with a space. And no learned token starts with a space any more (b' model' cannot exist), so the tokenizer can no longer tell a word at the start of a text from the same word in the middle. A pre-tokeniser must split text without losing anything: every character must end up in exactly one chunk.

Take-homeDesign and implement a tokenizer for a small language model: train it on a corpus, encode fresh text, decode ids back, and reserve two special tokens for document boundaries and padding. State the guarantees the test suite must pin, and explain how the special tokens survive both training and inference without ever being merged.

Level 4 of 4 · about 45 minutes to answer well.

Short answer. The base symbols are the 256 raw bytes, so every input has an encoding before any merge and decoding always terminates in bytes. Training runs on pre-tokenized chunks that never contain the special strings, so no merge can produce or consume a special id. At inference a matcher splits the text on the special strings first, maps each one to its reserved id, and runs the merge table on the text between them in training order. The suite pins the round trip on unseen text, on text with multi-byte characters, and on text that contains a literal special string with the flag off.

The pipeline.

  1. Normalize the text to one Unicode form so that the same visible word gets the same bytes.
  2. Split on the special strings when the caller allows them, and map each match to its reserved id.
  3. Pre-tokenize the remaining text into chunks at whitespace and punctuation boundaries.
  4. Apply the merge table to each chunk's bytes in training order, with non-overlapping left-to-right replacement.
  5. Concatenate the ids.

Decoding reverses steps two to five: expand each id to its bytes, where a merged id expands to the bytes of its two parents and a reserved special id expands to the UTF-8 bytes of its string, and decode the byte string. Normalization is not reversible. A decomposed accent comes back as the composed character, so the round trip is exact only for text that is already in the normalized form.

Why pre-tokenization.

Without the split, merges cross word boundaries and the vocabulary fills with common phrases that do not generalize. The split keeps merges inside a word. The chunk boundaries also stop a merge from spanning the end of one word and the start of the next at inference, which is how training and inference stay consistent.

Special tokens.

The ids after the byte block are reserved by hand. The training loop never sees the special strings, because the corpus is split and the strings are removed before pair counting, so no merge target can be a special id and no merge can include one. At inference the encoder takes a flag. With the flag off, the characters of a special string are ordinary bytes and tokenize as such. With the flag on, the exact string maps to its reserved id and is not subject to any merge. The matcher tries longer special strings first so that one string that contains another is matched whole.

The guarantees to pin.

Guarantee Test
Round trip on unseen text encode then decode returns the exact bytes of the normalized input
Multi-byte characters a sentence with a four-byte emoji round-trips
Literal special string, flag off the string decodes back as text, not as a boundary
Special string, flag on exactly one id, the reserved one, appears
Merge order the same merge list gives the same ids on repeated encodes
Reserved range no merge in the table has a special id as a parent or a child

The compression curve.

The number of ids for a held-out sentence falls as the merge budget grows. Training with a target vocabulary of 300 and then of 600 ids on the lesson corpus shows the drop directly; that curve is the measurement that justifies the vocabulary size.

Plausible wrong answers.

  • "Add the special tokens to the corpus so the model learns them." Then they can be merged with neighbors and stop being single ids.
  • "Match special strings after the merges." The merges have already split the string into byte pieces, so the matcher never sees it.
  • "Decode by looking up a string per id in a dictionary." Ids are bytes, and a multi-byte character can be split across ids; concatenate bytes first, then decode.

Follow-ups an interviewer may ask.

  • (level 3) Why are the first 256 ids reserved for bytes rather than for the characters of the corpus? Expected: any input, including text in scripts the corpus never had, can then be encoded without an unknown token.
  • (level 4) Where do chat template markers fit in this design? Expected: they are special tokens like the boundary token, matched exactly before the merges, with fixed ids that the model was trained on; a wrong template puts the input outside the training distribution.
  • (level 4) How do you protect a deployed model from a tokenizer that drifts? Expected: hash the merge table and the special-token map, and check the hash in the pipeline before training and before serving; a different table decodes different ids.

Debug a failureA fine-tuned chat model answers well in the training notebook. The deployed service, with identical weights, returns rambling text that runs until the token limit. Where do you look first, and what do you expect to find?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. At the flat token sequence the model actually receives, not at the list of messages. A chat model was trained on one exact layout of role markers, special tokens and newlines; a missing newline, a swapped marker or an extra space puts the input outside the training distribution, and the end-of-turn token stops being predicted. Print the token ids of the same request from both paths and diff them, and check that the special tokens arrived as their reserved ids and not as the bytes that spell them.

The model never sees the JSON.

The service holds a list of role and content pairs. The model sees one flat sequence built by the chat template, which inserts markers such as a begin-of-text token, a header for each role and an end-of-turn token after each message, with specific newlines between them. Every model family lays this out differently. The template is part of the model, in the same way the vocabulary is.

The three ways it breaks.

  1. A different template. The service used a generic layout or an older version. Each message now sits in a frame the model never saw, and the end-of-turn marker it learned is absent or misplaced, so it never predicts the stop token.
  2. Special tokens spelled out. Special tokens must be matched exactly before the merge loop and mapped to fixed ids. If the service built the prompt as plain text and encoded it with the allow flag off, the marker string became ordinary bytes and pieces. The model sees text that looks like a marker and is not one.
  3. Stop token mismatch. The service stops on the generic end-of-sequence id while the model emits its end-of-turn id. Generation continues past the real end.

The check that settles it.

ids_notebook = tokenizer(chat_template(messages))
ids_service  = ids the service sent to the engine
diff the two lists; the first difference is the bug

Then decode each id back to its string and look for a marker that decoded as several pieces instead of one reserved id. If the two lists match, the input is fine and the stop token is next: compare the stop ids in the service config with the end-of-turn id that the template puts after each message.

The fix.

Use the model's own template function, pass special tokens through the reserved-id path, and configure the stop token to the id the template ends a turn with. Freeze the tokenizer file and the template together with the weights.

Plausible wrong answers.

  • "The sampling temperature is too high in the service." Temperature changes which token is picked, not whether the stop token is ever predicted; the ids differ before sampling.
  • "The fine-tune overfit." The same weights behave in the notebook; the difference is in the input layout.
  • "Trim the output on the client." That hides the symptom and the model still wastes compute on text it should not generate.

Follow-ups an interviewer may ask.

  • (level 2) What does the end-of-turn token do at inference? Expected: it is the model's signal that the answer is complete; the server must stop on that id, or generation runs to the limit.
  • (level 3) A user types the literal string of a special token into the chat box. What should happen? Expected: with the allow flag off it becomes ordinary bytes, which is the safe default for user text; with it on, the user could inject a control marker.
  • (level 3) How do you test a template implementation? Expected: build the sequence for a fixed message list and compare it id by id with the output of the model's own template code.
  • (level 4) The template is correct and the ids still differ between notebook and service. What else? Expected: a different tokenizer file version, a different normalization step, or a different setting for adding special tokens at the start; hash the tokenizer file and compare the flags.

Explain the mechanismBefore any merge runs, a production tokenizer cuts the text into chunks with a regular expression. Show me what the classic pattern does to Hello, world! Don't stop. and explain why the cut exists at all, given that the merges could run on the raw stream.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The pattern cuts the sentence into eight chunks, Hello, ,, world, !, Don, 't, stop and .: each word after the first keeps the space in front of it, contractions split at the apostrophe, and punctuation stands alone. The merges then run inside each chunk and can never join symbols across a chunk boundary. Without the cut, training learns merges that span words, the vocabulary fills with whole phrases, and the pieces generalize worse to new text.

The pattern.

'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+

In order: common contraction endings, a word with an optional leading space, a run of digits with an optional leading space, a run of punctuation, and whitespace. The \p{L} and \p{N} classes need the third-party regex module; the standard library falls back to ASCII classes, which is wrong for multilingual text.

Why the leading space travels with the word.

hello and hello are different tokens. Keeping the space on the word means a word-initial piece and a word-internal piece stay distinct, and the decoder can rebuild the spacing from the tokens alone. The same reason forces every caller to be explicit about whether a prefix space is added at the start of a prompt.

Why cut at all.

The merge loop is greedy on frequency. In a raw stream the pair "e" followed by a space followed by "t" is frequent, so the loop would happily learn a piece that ends one word and starts the next. Such pieces do not transfer: the next text has different word pairs. Cutting first keeps every merge inside a word, which is where the regularities that generalize live.

The other design.

A tokenizer that works on raw text treats the space as an ordinary symbol and lets the merge or prune algorithm find the boundaries. It needs no language rules and handles scripts without spaces, and it allows cross-word pieces, which can compress a little better and read a little worse.

The capstone's version.

A small split on whitespace and punctuation. It is enough to keep merges inside words for a small training set, and the rest of the pipeline stays the same.

Plausible wrong answers.

  • "Pre-tokenization is just splitting on spaces." The pattern also handles contractions, digits, punctuation and runs of whitespace, and it keeps the space attached to the word.
  • "The cut is cosmetic; the merges would find the same pieces." Without the cut the merges cross word boundaries and the vocabulary fills with phrases.
  • "Attach punctuation to the word it follows." Then world! and world are different pieces, and the vocabulary pays for every punctuation variant.

Follow-ups an interviewer may ask.

  • (level 2) Why does a prompt that starts without a space tokenize differently from one that starts with a space? Expected: the space is part of the word-initial token, so the first word maps to a different id; set the prefix-space behavior explicitly.
  • (level 3) Why does the regex module matter for this pattern? Expected: the Unicode letter and number classes cover scripts beyond ASCII, which the standard library's engine lacks.
  • (level 3) What is the trade in skipping the cut and running on raw text? Expected: no language rules and good behavior for scripts without spaces, against cross-word pieces that compress slightly better and are less interpretable.
  • (level 3) A tokenizer file is unchanged but ids differ between two machines. What in this stage can cause it? Expected: one machine fell back to the ASCII pattern because the regex module was missing, so the chunks differ.

Take-homeThis is a take-home we send: implement a byte-level byte-pair tokenizer with training, encoding and decoding, two reserved special tokens, and a test suite. Describe the design you would submit, the tests you would ship, and the one figure you would include in the write-up.

Level 3 of 4 · about 15 minutes to answer well.

Short answer. Reserve ids 0 to 255 for the raw bytes and a small block above them for the end-of-text and pad markers, split the corpus on whitespace and punctuation, train by counting frequency-weighted adjacent pairs and merging the top pair with a deterministic tie-break, encode by applying the lowest-ranked merge that fits until none fits, and decode by joining the byte expansions and decoding UTF-8 once. The tests pin the byte-exact round trip on an unseen sentence, on an emoji and on a literal special-token string with the allow flag on and off, plus the merge-order property and the reserved ids. The figure is the compression curve: the encoded length of a held-out sentence as the target vocabulary grows from 300 to 600.

The design.

ids 0..255        raw bytes
next few ids      <|endoftext|>, <|pad|>
then              one id per merge, in training order
  • Keep the input bytes as they are, so that the round trip is byte-exact. Compatibility normalization maps a ligature or a fullwidth letter to its plain form and is lossy, so add it only if the write-up limits the round-trip promise to normalized text.
  • Pre-split into words and punctuation so that merges stay inside a word; the regex pattern of the large production tokenizers is an optional extension.
  • Train: count adjacent pairs across the split corpus weighted by word frequency, merge the top pair into the next free id, record the merge, repeat to the target size. Break ties on the pair itself so two runs give the same table.
  • Encode: match special tokens exactly first when the allow flag is on; for ordinary text start from the bytes and repeatedly apply the lowest-ranked applicable merge.
  • Decode: special ids map to their marker strings, every other id to its bytes; join all bytes, then decode once with replacement for a partial trailing character.

The tests.

  1. Round trip on a sentence the tokenizer never saw.
  2. Round trip on a sentence with an emoji, where the character's 4 bytes may span tokens.
  3. Round trip on a sentence containing the literal end-of-text string, with the flag off it becomes bytes and with the flag on it becomes the reserved id.
  4. Merge order: a held-out word encodes to the recorded ids, and a shuffled table does not.
  5. Reserved ids never appear as merge targets and never collide with byte ids.
  6. Determinism: training twice on the same corpus gives the same table.

The figure.

Train to several target sizes, encode the same held-out sentence each time, and plot the token count against the vocabulary size. The count falls as merges cover longer pieces. A second line with the compression ratio, tokens over input bytes where 0.50 means half as many tokens as bytes, shows the same thing in a unit that transfers between corpora.

What a reviewer grades.

Correctness of the round trip, determinism, clean separation of the special-token path from the merge path, the quality of the tests, and a write-up that names the bug the candidate hit. Speed is not graded: Python at this scale finishes in well under a second, and production libraries in compiled languages are 10 to 100 times faster for the same algorithm.

Plausible wrong answers.

  • "Use Unicode code points as the base symbols." Code points number in the hundreds of thousands and leave gaps for unseen characters; bytes are 256 and complete.
  • "Decode each token to a string and join the strings." A token can hold part of a multi-byte character; join the bytes first and decode once.
  • "Skip the pre-split to get better compression." Merges then cross word boundaries and the vocabulary fills with phrases that do not transfer.

Follow-ups an interviewer may ask.

  • (level 2) Why do the raw bytes take ids 0 to 255 before anything else? Expected: every input can then be expressed in the vocabulary before any merge exists, so nothing is ever unknown.
  • (level 3) The input spells out the end-of-text marker as plain text. What does the allow flag change? Expected: off, the string is ordinary bytes and pieces; on, it maps to the reserved id and is skipped by the merge loop.
  • (level 3) Why must a tie in pair counts be broken deterministically? Expected: two runs on the same corpus must give the same table, or the same text gets different ids across machines.
  • (level 4) Replace the simple split with the production regex pattern. What do you compare? Expected: the vocabularies and the encoded lengths on the same corpus, looking at how contractions, digits and leading spaces are handled.

Debug a failureAfter a routine dependency upgrade, an evaluation score for a deployed model fell sharply. No model weights changed. Give me a diagnosis plan that starts at the tokenizer, and the control you add so it cannot happen again.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. A model trained with one vocabulary and served with another gets different ids for the same text and produces garbage, so first hash the tokenizer file in both environments and compare. If the hashes match, check the settings that change ids without changing the vocabulary: whether special tokens are added, whether a prefix space is added, and the normalization step, because a leading space or a ligature that normalizes differently moves whole tokens. Then freeze the tokenizer hash in CI and keep golden token ids for a fixed corpus so any change fails a test before it ships.

Step one: the file.

The merge table and the vocabulary are the tokenizer. A library upgrade can pull a different file, or resolve a model name to a newer revision. Compare the hash of the tokenizer file in the evaluation environment with the one the model was trained with.

Step two: the settings around the file.

Setting What changes Symptom
Add special tokens a begin-of-text id appears or disappears at the start every position shifts by one
Add prefix space the first word gets a word-initial id or a word-internal id the first token of every prompt differs
Normalization a ligature such as the two-letter "fi" becomes two characters, or a fullwidth letter becomes ASCII the same word gets different pieces in the two environments
Pre-tokenizer engine the Unicode-aware pattern falls back to ASCII classes non-Latin text splits differently

Each of these is a default that a library version can change. None of them touches the vocabulary file, so the hash alone does not catch them.

Step three: prove it.

Take a fixed sample of prompts from the evaluation. Encode them in both environments and diff the id lists. The first position that differs tells you which setting moved. Decode the differing ids to see the pieces.

The controls.

  1. Pin the tokenizer file by hash in the deployment and fail the build when it changes.
  2. Store golden token ids for a fixed corpus that covers English, non-Latin scripts, code, emoji and a prompt with a leading space; the test encodes the corpus and compares.
  3. Assert a round trip, encode then decode, on the same corpus. Compare against the text that the configured normalizer produces, and require byte-exact equality for text that the normalizer leaves unchanged.
  4. Record the tokenizer settings next to the weights, so the serving config cannot drift from the training config.

The validation plan from the lesson.

Average tokens per word on a held-out set, the unknown rate, the compression ratio and the round-trip equality. Those four numbers, tracked over time, show drift before an evaluation does.

Plausible wrong answers.

  • "The weights did not change, so the model is the same." The model is the weights and the mapping from text to ids; change the mapping and the model sees different inputs.
  • "Retrain the model on the new tokenizer." A multi-week fix for a configuration bug; restore the training-time tokenizer and settings.
  • "Lowercase everything so the normalization does not matter." That changes the ids again and throws away information the model was trained with.

Follow-ups an interviewer may ask.

  • (level 3) How does a prefix space change the ids? Expected: the space is part of the word-initial token, so with it the first word gets one id and without it another, and the shift can continue through the merges.
  • (level 3) What does the compatibility normalization do, and when is it harmful? Expected: it maps compatibility characters to their plain forms, such as a ligature to two letters or a fullwidth letter to ASCII; it is lossy, so code or text that depends on the exact form changes meaning.
  • (level 4) The hashes match and the ids still differ on non-Latin text only. What moved? Expected: the pre-tokenizer engine; the environment without the Unicode-aware module fell back to the ASCII pattern.
  • (level 4) Design the CI gate in two sentences. Expected: a test that encodes a fixed multilingual corpus and compares against stored golden ids and a stored tokenizer hash; any difference fails the build and prints the first differing position.

Check your understanding

Q1Why does a basic BPE tokenizer break on multilingual or code input?

A naive BPE implementation may not handle multi-byte Unicode characters, may merge across word boundaries incorrectly, and may not have byte-level fallback for characters outside the trained vocabulary.

Q2What is the role of pre-tokenization regex in a production tokenizer?

Pre-tokenization regex splits text into chunks (typically at word boundaries, numbers, and punctuation) so BPE merges only happen within chunks. Without this, BPE could merge 'end' with the space before the next word.

Q3What is a special token and why are tokenizers designed to handle them?

Special tokens serve structural purposes: marking document boundaries, padding sequences, indicating start/end of generation. They must be recognized and encoded as their exact IDs, not broken into subwords.

Q4How do you evaluate whether a custom tokenizer is good?

Compression ratio (bytes per token or tokens per word) measures efficiency. A good tokenizer produces fewer tokens for the same text, which means more content fits in the context window. Compare across languages and domains.

Q5Why is byte-level BPE preferred over word-level tokenization for modern LLMs?

Word-level tokenizers can't handle unseen words (producing [UNK] tokens). Byte-level BPE starts from raw bytes (guaranteeing coverage of any input) and learns merges for common sequences, balancing coverage with efficiency.
