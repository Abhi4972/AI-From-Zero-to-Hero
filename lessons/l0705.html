Why this came about

Microsoft had two agent projects: Semantic Kernellater · 7.11 for enterprise integration and AutoGenlater · 7.11 for multi-agent research. In 2025 it combined them into the Microsoft Agent Framework, for .NET and Python, tied closely to Azure.

In plain words first
Microsoft's merger of two frameworks

Microsoft Agent Framework combines ideas from Semantic Kernel (enterprise plumbing) and AutoGen (multi-agent conversations) into one framework for .NET and Python, with agents, tools, threads, middleware and graph-based workflows, and close ties to Azure. Read it as the same building blocks, with a strong enterprise and Azure focus.

What it is

The Microsoft Agent Framework (MAF) is Microsoft's open-source (MIT) framework for Python and .NET. It is the unified successor to Semantic Kernel and AutoGen: Semantic Kernel's enterprise features (telemetry, filters, connectors) and AutoGen's multi-agent patterns in one SDK, with migration guides from both. AutoGen remains available for research; new production work is directed to MAF.

Two layers:

  • Agents: an Agent wraps a chat client (OpenAI, Azure OpenAI and Foundry, Anthropic, Bedrock, Gemini, Ollama, Mistral and more) with instructions, tools, middleware and sessions.
  • Workflows: graphs of executors (agents or functions) joined by edges, with fan-out and fan-in, switch-case routing, request-and-response steps for humans, and checkpointing.

Step 1 · An agent with an approval

The same agent in Microsoft Agent Framework. A chat client talks to the model, @tool declares the tools, and Agent ties them together. cancel_order is declared with an approval mode, so the first run returns a request for approval; the second run sends the approval back and the tool executes.

import asyncio
from mockllm import start
from agent_framework import Agent, Message, tool
from agent_framework.openai import OpenAIChatCompletionClient   # Chat Completions API (OpenAIChatClient uses the Responses API)

client = OpenAIChatCompletionClient(model="mock-model", base_url=start(), api_key="mock")
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

@tool(approval_mode="always_require")              # approval mode: return a request instead of calling it
def cancel_order(order_id: str) -> str:
    """Cancel an order that has not shipped yet."""
    return f"{order_id} cancelled"

async def main():
    agent = Agent(client=client, name="ShopKartSupport", instructions="Help ShopKart customers. Be brief.",
                  tools=[get_order_status, cancel_order])
    session = agent.create_session()                                   # conversation memory
    r = await agent.run("Where are A-1001 and A-1002?", session=session)
    print("1:", r.text)

    r = await agent.run("Please cancel A-1002", session=session)
    req = r.user_input_requests[0]                                     # check this list after every run
    print("2: approval needed for", req.function_call.name, req.function_call.arguments)
    r = await agent.run(Message(role="user", contents=[req.to_function_approval_response(True)]), session=session)
    print("2:", r.text)

asyncio.run(main())
What you should see
1: Here is what I found: A-1001 is shipped; A-1002 is processing
2: approval needed for cancel_order {"order_id": "A-1002"}
2: Here is what I found: A-1002 cancelled

The tool's approval mode makes the run return a request instead of executing it. For Azure, use the Foundry or Azure OpenAI chat client with AzureCliCredential() (Microsoft Entra ID) instead of keys. An approval answers only a request recorded in the same session; stray approvals are ignored and logged, which protects against forged approvals.

Middleware has three levels: agent middleware (around a whole run), chat middleware (around each model call) and function middleware (around each tool call). It is where you add logging, policy checks, PII filtering and retries.

Step 2 · Workflows

A workflow is Agent Framework's graph. Its nodes are called executors: small async functions that receive a message, do one job, and either send a message along an edge to the next executor or produce an output. The builder connects them. A two-step example that tidies a ticket and labels it:

from agent_framework import WorkflowBuilder, WorkflowContext, executor

@executor(id="normalize")
async def normalize(text: str, ctx: WorkflowContext[str]) -> None:
    await ctx.send_message(text.strip().upper())          # send to the next executor along the edge

@executor(id="tag")
async def tag(text: str, ctx: WorkflowContext[str, str]) -> None:
    await ctx.yield_output(f"[ticket] {text}")             # produce a workflow output

async def run_workflow():
    wf = WorkflowBuilder(start_executor=normalize).add_edge(normalize, tag).build()
    result = await wf.run("  where is my parcel?  ")
    print(result.get_outputs())

asyncio.run(run_workflow())
What you should see
['[ticket] WHERE IS MY PARCEL?']

WorkflowContext[str] declares what an executor sends on; WorkflowContext[str, str] adds what it outputs. The builder also offers add_fan_out_edges, add_fan_in_edges, add_switch_case_edge_group and add_chain, plus checkpoint_storage= for resumable runs.

Orchestrations package the common multi-agent patterns as builders in agent_framework.orchestrations: SequentialBuilder (agents in a chain), concurrent (fan-out to several agents, then aggregate), handoff, group chat and Magentic (a manager agent that plans and delegates, from Microsoft Research's Magentic-One). Any agent can join any of them, and .with_request_info(...) pauses a workflow for human review.

Middleware, routing, checkpoints and orchestrations in code

Four building blocks you will combine in real MAF systems. First, function middleware that records every tool call (the same hook point is where policy checks and PII filters go):

import time
from agent_framework import function_middleware, Case, Default, InMemoryCheckpointStorage
from agent_framework.orchestrations import SequentialBuilder

TOOL_LOG = []

@function_middleware
async def log_tool_calls(context, call_next):
    """Runs around every tool call: before, call_next(), after."""
    started = time.perf_counter()
    await call_next()                                   # run the tool (or skip it to block the call)
    TOOL_LOG.append((context.function.name, dict(context.arguments), f"{(time.perf_counter() - started) * 1000:.0f} ms"))

async def middleware_demo():
    agent = Agent(client=client, name="AuditedSupport", instructions="Help ShopKart customers.",
                  tools=[get_order_status], middleware=[log_tool_calls])
    r = await agent.run("Where is A-1001?")
    print(r.text, "|", [(name, args) for name, args, _ in TOOL_LOG])

asyncio.run(middleware_demo())
What you should see
Here is what I found: A-1001 is shipped | [('get_order_status', {'order_id': 'A-1001'})]

Second, routing with a switch-case edge group in a workflow: the first matching case wins, and Default catches the rest.

@executor(id="intake")
async def intake(text: str, ctx: WorkflowContext[str]) -> None:
    await ctx.send_message(text)

@executor(id="refund_desk")
async def refund_desk(text: str, ctx: WorkflowContext[str, str]) -> None:
    await ctx.yield_output(f"refund desk <- {text}")

@executor(id="general_desk")
async def general_desk(text: str, ctx: WorkflowContext[str, str]) -> None:
    await ctx.yield_output(f"general desk <- {text}")

router = (WorkflowBuilder(start_executor=intake)
          .add_switch_case_edge_group(intake, [Case(condition=lambda t: "refund" in t.lower(), target=refund_desk),
                                               Default(target=general_desk)])
          .build())

async def route_demo():
    for text in ["I need a refund for A-1001", "Where is my parcel?"]:
        print((await router.run(text)).get_outputs())

asyncio.run(route_demo())
What you should see
['refund desk <- I need a refund for A-1001']
['general desk <- Where is my parcel?']

Third, checkpoints: give the builder checkpoint storage and every superstep is saved, so a long workflow can resume after a failure or a human pause. Use FileCheckpointStorage or a database-backed store in production.

store = InMemoryCheckpointStorage()

@executor(id="enrich")
async def enrich(text: str, ctx: WorkflowContext[str]) -> None:
    await ctx.send_message(text + " -> enriched")

@executor(id="file_ticket")
async def file_ticket(text: str, ctx: WorkflowContext[str, str]) -> None:
    await ctx.yield_output(text + " -> filed")

durable_wf = WorkflowBuilder(start_executor=enrich, checkpoint_storage=store).add_edge(enrich, file_ticket).build()

async def checkpoint_demo():
    print((await durable_wf.run("ticket T-981")).get_outputs())
    saved = await store.list_checkpoints(workflow_name=durable_wf.name)
    print(len(saved), "checkpoints saved; resume with workflow.run(checkpoint_id=..., checkpoint_storage=store)")

asyncio.run(checkpoint_demo())
What you should see
['ticket T-981 -> enriched -> filed']
3 checkpoints saved; resume with workflow.run(checkpoint_id=..., checkpoint_storage=store)

Fourth, a ready-made orchestration: SequentialBuilder passes the conversation from one agent to the next, and the last agent's reply is the output.

async def sequential_demo():
    lookup_agent = Agent(client=client, name="Lookup", instructions="Look up the order.", tools=[get_order_status])
    writer_agent = Agent(client=client, name="Writer", instructions="Write a short, friendly reply.")
    team = SequentialBuilder(participants=[lookup_agent, writer_agent]).build()
    final = (await team.run("Where is A-1002?")).get_outputs()[-1]
    print([(m.author_name, m.text[:45]) for m in final.messages])

asyncio.run(sequential_demo())
What you should see
[('Writer', 'I can check order status and cancel orders. P')]

With a real model, the writer turns the lookup agent's facts into a reply; the mock's writer has no tools, so it gives its generic answer. ConcurrentBuilder, HandoffBuilder, GroupChatBuilder and MagenticBuilder follow the same pattern (Lesson 3.11 explains when each pattern fits).

In production
Workflows and checkpoints in production

Checkpoints are only as durable as their storage: the in-memory storage in the examples is for tests, so use a persistent store before relying on resume. Keep the state you put in a workflow serializable and small; large objects make every checkpoint slow. And version workflows deliberately, because a run checkpointed by version 1 may be resumed by version 2 after a deploy.

Step 3 · The surrounding tools

  • DevUI (agent-framework-devui): a local web UI to run and inspect agents and workflows.
  • Declarative agents: define agents and workflows in YAML.
  • Hosting: Azure Functions with the Durable Task extension for long-running, durable agents; Foundry hosted agents; any container.
  • Protocols: A2Alater · 8.4 and AG-UI packages, MCPlater · 8.1 tools (stdio, streamable HTTPlater · 8.2, WebSocket).
  • Observability: OpenTelemetrylater · 12.13 built in, following the GenAI semantic conventionslater · 12.13, to Azure Monitor (Application Insightslater · 13.4) or any OTLPlater · 12.13 backend.
  • Governance: a Microsoft Purview integration package for data-security policies on prompts and responses.

Exercises

Predict before you run

Microsoft Agent Framework has agents and workflows. Which would you use for "classify the ticket, then route to billing or delivery"? (Solution P1.)

Break it on purpose

Run a workflow without checkpointing and restart the process mid-run. What is lost? (Solution B1.)

Debugging exercise

An agent with middleware logs every call, but tool calls are missing from the logs. What do you check? (Solution D1.)

Make it your own

Add an approval step to the cancel flow and show it pausing and resuming. (Solution M1.)

Solutions

SolutionP1 · Agents and workflows

A workflow: the steps and routing are known, so a graph of executors with edges is clearer than an agent deciding.

SolutionB1 · Checkpoints

The run's progress; it must restart from the beginning. Enable checkpointing for long workflows.

SolutionD1 · Middleware scope

Whether the middleware is registered for function (tool) invocation as well as agent runs.

SolutionM1 · Human in the loop

Use the framework's approval support for function calls or a request-response step in a workflow, then resume with the decision.
