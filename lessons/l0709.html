Why this came about

Research in 2024 showed that agents writing short programs, instead of one JSON tool call per step, could do more in fewer steps. Hugging Face's smolagents (late 2024) made code agents simple to try, with sandboxeslater · 15.23 to run their code safely.

In plain words first
Agents that write small programs instead of single calls

Most agents call one tool per step as JSON. smolagents popularized code agents: the model writes a short Python snippet that can call several tools, loop and filter, which the framework runs and returns. That takes fewer steps and is more expressive, but running model-written code demands a sandbox.

smolagents: agents that act in code

Best fit: research, open-model agents and code-acting agents, where a minimal, hackable library is a feature.

Hugging Face's smolagents keeps the core small. Its signature agent is the CodeAgent: instead of one JSON tool call per step, the model writes a short Python snippet that calls tools, loops and computes, which takes fewer steps on complex tasks (the CodeAct idea from Lesson 14.9). Code runs in a local restricted interpreter or, for real isolation, in E2B, Docker, Modal or WebAssembly sandboxes. ToolCallingAgent does classic tool calling.

from smolagents import ToolCallingAgent, OpenAIServerModel, tool

smol_model = OpenAIServerModel(model_id="mock-model", api_base=BASE_URL, api_key="mock")

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order.

    Args:
        order_id: An order ID like 'A-1001'.
    """
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

smol_agent = ToolCallingAgent(tools=[get_order_status], model=smol_model, verbosity_level=0)
print(smol_agent.run("Where is A-1001?"))
What you should see
Here is what I found: A-1001 is shipped

smolagents requires an Args: section in tool docstrings and ends every run with a built-in final_answer tool.

The part that is different: an agent whose actions are code

The example above used smolagents' ordinary tool-calling agent, which works like every agent so far. The library's own idea is the CodeAgent. Lesson 14.9 introduced it as CodeAct: instead of asking for one tool call and waiting for the result, the model writes a short Python program, and the library runs it. Tools are ordinary functions the program can call, so one model reply can loop over several orders, combine the results and compute an answer.

To show exactly what the library does with such a reply, the model here is a scripted stand-in that returns one prepared reply. Everything after that (finding the code, running it, calling the tool, returning the answer) is the real library.

from smolagents import CodeAgent, tool
from smolagents.models import Model, ChatMessage

ORDERS = {"A-1001": "shipped", "A-1002": "processing", "A-1003": "delivered"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order.

    Args:
        order_id: An order ID like 'A-1001'.
    """
    return ORDERS.get(order_id, "not found")

class ScriptedModel(Model):
    """Stands in for a model that has decided to solve the task with one piece of code."""
    def __init__(self, replies):
        super().__init__(); self.replies = list(replies)
    def generate(self, messages, **kwargs):
        return ChatMessage(role="assistant", content=self.replies.pop(0))

code_action = '''Thought: I can check all three orders in one loop and count them.
<code>
statuses = {oid: get_order_status(order_id=oid) for oid in ["A-1001", "A-1002", "A-1003"]}
not_delivered = [oid for oid, s in statuses.items() if s != "delivered"]
final_answer(f"{len(not_delivered)} of 3 orders are still on the way: {not_delivered}")
</code>'''
agent = CodeAgent(tools=[get_order_status], model=ScriptedModel([code_action]), verbosity_level=-1)
print(agent.run("How many of orders A-1001, A-1002 and A-1003 have not been delivered yet?"))
print("model calls:", len(agent.memory.steps) - 1)
What you should see
2 of 3 orders are still on the way: ['A-1001', 'A-1002']
model calls: 1
Reading this output

The question needed three lookups, a comparison and a count. A tool-calling agent would have needed at least two model calls (one to request the three lookups, one to read the results and answer), and the model would have done the counting in its head. Here there was one model call. The loop and the arithmetic were done by Python, which does not miscount.

Look at what the scripted reply contains: a line of reasoning, then code between <code> tags. The library extracts the code, runs it in its own small Python interpreter with the tools available as functions, and treats the call to final_answer(...) as the end of the run. If the code had printed something instead, that output would have gone back to the model as the observation for its next step.

Running code that a model wrote is the obvious risk. The library's first line of defence is that its interpreter is not ordinary Python: it allows a short list of safe modules and refuses the rest.

bad_action = '''Thought: I will look at the files on this machine.
<code>
import os
final_answer(str(os.listdir("/")))
</code>'''
recover = '''Thought: That import is not allowed. I will answer from what I know.
<code>
final_answer("I can only use the order tools, so I cannot look at files.")
</code>'''
agent = CodeAgent(tools=[get_order_status], model=ScriptedModel([bad_action, recover]), verbosity_level=-1)
print(agent.run("List the files on the server."))
blocked = [str(step.error)[:96] for step in agent.memory.steps if getattr(step, "error", None)]
print("blocked:", blocked)
What you should see
I can only use the order tools, so I cannot look at files.
blocked: ["Code execution failed at line 'import os' due to: InterpreterError: Import of os is not allowed."]
Reading this output

The first reply tried import os to list the machine's files. The interpreter refused, and the error went back to the model as an observation, exactly as a failed tool call would. The second scripted reply then gave up gracefully.

Two cautions. First, a restricted interpreter is a filter, not a wall. The smolagents documentation says plainly that it is not a security boundary, and recommends running code agents inside a real sandbox (a container or a remote sandbox service) for anything beyond experiments; Lesson 15.23 covers sandboxes. Second, the tools themselves are still the main risk: a code agent with a delete_order tool can call it in a loop.

Check your mental model
  • ✗ "Code agents are just a different output format."
    ✓ They let one step loop, branch and combine tools, which changes cost and capability.
  • ✗ "Model-written code is safe to run locally."
    ✓ Always run it in a sandbox with limited access.
  • ✗ "Code agents suit every task."
    ✓ Simple lookups are cheaper and safer as plain tool calls.

Solutions

SolutionP1 · Code as actions

Often fewer: one code block can call several tools and compute the total, where a tool-calling agent needs a round trip per call.

SolutionB1 · Sandbox generated code

The model can run arbitrary code with your server's rights. Use a sandboxed executor (a container, a remote sandbox) with limited imports and no secrets.

SolutionD1 · Allowed imports

Add the library to the allowed list if safe, or tell the model in its instructions which libraries are available.

SolutionM1 · Measure both

Code agents tend to win on multi-step computation; tool-calling agents are easier to constrain. Measure on your tasks.

Check your understanding

Explain the mechanismWhat is a code agent, and when is it better than tool calling?

Worked answer. An agent whose actions are code: it writes Python that calls tools as functions, loops and computes, executed in a sandbox. It handles multi-step logic and data manipulation in fewer steps; it needs sandboxing and is harder to constrain than a fixed set of tool calls.

A plausible wrong answer. "Code agents are unsafe, never use them." With a sandbox and limits they are practical.

Follow-ups. What would you sandbox with?

Debug a failureA code agent loops on errors in its own code. What do you change?

Worked answer. Give clear error messages back, limit steps, provide examples of correct tool usage, and keep the available functions small and documented.

A plausible wrong answer. "Use a bigger model." Better feedback and limits come first.

Defend a designCode agent or tool-calling agent for ShopKart's analytics questions?

Worked answer. A code agent in a sandbox for computations over data; tool calling for customer-facing actions where every action must be authorized individually.

A plausible wrong answer. "Code agents everywhere." Customer actions need per-call control.
