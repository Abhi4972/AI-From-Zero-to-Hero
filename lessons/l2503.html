Why this came about

The statistical turn in NLP (1990s) started from a blunt idea: ignore grammar, just count words. A spam email says "free", "winner" and "click" a lot; a sports article says "match" and "goal". In 1998, Mehran Sahami and colleagues showed that a simple word-counting classifier (naive Bayes) filtered spam well, and by the mid-2000s spam filters everywhere worked this way. For search, Karen Spärck Jones's 1972 idea of inverse document frequency (a word that appears in every document tells you nothing) became TF-IDF and later BM25later · 5.37, the ranking formula still inside most search engines, including the keyword half of the hybrid searchlater · 5.38 in Lesson 5.38.

In plain words first
Counting the words in a bag

Tip all the words of a message into a bag, shake it, and count what is inside: "refund" twice, "order" once, "damaged" once. The order is gone, but the counts still say a lot about what the message is about. A classifier learns which words point to which kind of ticket. For search, you do the same to every document and to the query, and look for documents whose counts look most like the query's, giving more weight to words that are rare (and so informative) than to words that are everywhere.

Step 1 · A dataset of support tickets

You need labelled examples. Here are 48 ways customers phrase four kinds of ticket (where is my order, refund, damaged item, account), each filled in 8 times with random order numbers, items and days, for 384 tickets:

import random

Real ticket data would come from your help desk, labelled by agents. Generated data like this has a trap, though: eight tickets from the same template are near-duplicates. If some land in training and others in testing, the test only checks memory (Lesson 2.26). So hold out whole templates: tickets from templates 2, 6 and 10 of each kind go to the test set. Those phrasings are never seen in training, which is what real new tickets are like.

test_templates = {2, 6, 10}
train = [(t, l) for t, l, tid in rows if tid not in test_templates]
test = [(t, l) for t, l, tid in rows if tid in test_templates]
X_train, y_train = [t for t, _ in train], [l for _, l in train]
X_test, y_test = [t for t, _ in test], [l for _, l in test]
print(len(X_train), "training tickets,", len(X_test), "test tickets with unseen phrasings")
What you should see

Step 2 · A bag of words

scikit-learn's CountVectorizer builds the vocabulary from the training texts and turns each text into a row of counts:

from sklearn.feature_extraction.text import CountVectorizer

vec = CountVectorizer()                           # lowercases and splits into words of 2+ letters
X_train_counts = vec.fit_transform(X_train)       # learn the vocabulary, then count
print("shape:", X_train_counts.shape, " (tickets x vocabulary words)")
print("vocabulary sample:", list(vec.get_feature_names_out()[:12]))

row = vec.transform(["my refund is not received, refund please"])
print({w: int(c) for w, c in zip(vec.get_feature_names_out(), row.toarray()[0]) if c})
print(f"non-zero entries in the training matrix: {X_train_counts.nnz} of {X_train_counts.shape[0] * X_train_counts.shape[1]:,}")
What you should see
shape: (288, 216)  (tickets x vocabulary words)
vocabulary sample: ['11', '12', '13', '14', '14646', '15', '15018', '15544', '18006', '18255', '19665', '19698']
{'is': 1, 'my': 1, 'not': 1, 'please': 1, 'received': 1, 'refund': 2}
non-zero entries in the training matrix: 2010 of 62,208
Reading this output
  • fit_transform does two things: fit learns the vocabulary from the training texts, transform turns texts into counts. New texts must only be transformed with the same vocabulary, never re-fitted (Lesson 2.26's rule about fitting preprocessing on training data only).
  • Each order number like "sk-48213" splits into "sk" and a number, and each number becomes its own column. Useless columns like that are common in raw text features.
  • The example row counts "refund" twice and the other words once. A word the vectoriser never saw in training has no column, so it is silently ignored. That is the bag of words' biggest weakness on new text.
  • Only about 3% of the matrix is non-zero. scikit-learn stores it as a sparse matrix, which keeps only the non-zero entries.

Step 3 · Train, evaluate, inspect

The counts are features; any classifier from the Machine learning from zero section can use them. Logistic regression is the standard choice:

from sklearn.linear_model import LogisticRegression
from sklearn.metrics import classification_report
from sklearn.model_selection import train_test_split

clf = LogisticRegression(max_iter=1000).fit(X_train_counts, y_train)
predicted = clf.predict(vec.transform(X_test))
print(classification_report(y_test, predicted))

# for comparison: a careless random split, where the same templates appear in both sets
a, b, c, d = train_test_split([r[0] for r in rows], [r[1] for r in rows], test_size=0.25, random_state=0)
v2 = CountVectorizer()
careless = LogisticRegression(max_iter=1000).fit(v2.fit_transform(a), c)
print("careless random split accuracy:", careless.score(v2.transform(b), d))

A linear model on word counts can be read directly: each class has one weight per word.

words = np.array(vec.get_feature_names_out())
for i, label in enumerate(clf.classes_):
    top = words[np.argsort(clf.coef_[i])[-6:][::-1]]       # the 6 words pushing hardest towards this class
    print(f"{label:<8} {list(top)}")

Step 4 · Where counting fails

The classifier works by counting words, so it has no idea of word order or of what "no" and "not" do to a sentence. Four messages chosen to expose that: two that contain the word "refund" while saying a refund is not wanted, and two that describe a problem without using any of the usual words.

for t in ["the box came smashed and the glass is in pieces",
          "no need for a refund, the replacement was fine",
          "i do not want a refund, i just want my order to arrive",
          "the courier left it at the wrong address"]:
    probs = clf.predict_proba(vec.transform([t]))[0]
    print(f"{clf.classes_[probs.argmax()]:<8} ({probs.max():.2f})  {t}")
What you should see
damaged  (0.97)  the box came smashed and the glass is in pieces
refund   (0.86)  no need for a refund, the replacement was fine
refund   (0.70)  i do not want a refund, i just want my order to arrive
damaged  (0.49)  the courier left it at the wrong address
Reading this output
  • The first is right, but partly by luck: "box" appeared in a training ticket about a crushed box. The real clues, "smashed" and "pieces", were never seen and count for nothing.
  • "No need for a refund" and "I do not want a refund" are both labelled refund. A bag of words cannot represent "no need for" or "do not want"; it sees the word "refund".
  • "Left it at the wrong address" is a delivery problem, but the model only half-guesses "damaged" (0.49): the words it knows ("address", "the", "it") point in different directions, and it cannot tell what the sentence is about.

Adding bigrams (pairs of neighbouring words, such as "not received" or "no need") as extra features captures a little word order. Use CountVectorizer(ngram_range=(1, 2)). It helps a bit, at the cost of a much larger vocabulary. The deeper fixes come later: word vectors that know "smashed" is close to "broken" (Lesson 5.33), and transformers that read words in context (the Transformers, step by step section).

Step 5 · TF-IDF and a first search engine

For search, raw counts have a problem: words like "how", "do" and "my" appear in almost every document, so they dominate the comparison. TF-IDF fixes that by weighting each count:

  • TF (term frequency): how often the word appears in this document.
  • IDF (inverse document frequency): how rare the word is across all documents, log(number of documents / documents containing the word) (scikit-learn adds 1s to avoid dividing by zero). Rare words get a high weight; words found everywhere get a low one.

Here is a tiny help centre with six FAQ entries. Each FAQ and each query becomes a TF-IDF vector, and the best answer is the FAQ with the highest cosine similarity (Lesson 1.23) to the query:

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

faqs = ["How do I track my order?", "How long does a refund take to reach my account?",
        "What should I do if my item arrived damaged?", "How do I change my delivery address?",
        "How do I reset my password?", "Can I cancel an order after it has shipped?"]

tfidf = TfidfVectorizer(stop_words="english")      # also drop common English words
faq_vectors = tfidf.fit_transform(faqs)
print("vocabulary:", list(tfidf.get_feature_names_out()))

for query in ["my order has not arrived, where can i track it", "forgot my password",
              "my item arrived damaged", "the parcel came broken"]:
    scores = cosine_similarity(tfidf.transform([query]), faq_vectors)[0]
    best = scores.argmax()
    print(f"{query!r:<50} -> {faqs[best]!r}  score {scores[best]:.2f}")
What you should see
vocabulary: ['account', 'address', 'arrived', 'cancel', 'change', 'damaged', 'delivery', 'does', 'item', 'long', 'order', 'password', 'reach', 'refund', 'reset', 'shipped', 'track']
'my order has not arrived, where can i track it'   -> 'How do I track my order?'  score 0.79
'forgot my password'                               -> 'How do I reset my password?'  score 0.71
'my item arrived damaged'                          -> 'What should I do if my item arrived damaged?'  score 1.00
'the parcel came broken'                           -> 'How do I track my order?'  score 0.00
Reading this output
  • With common words removed, the vocabulary is just the 17 content words of the FAQs. A query is matched on those words only.
  • The first three queries find the right FAQ: they share "track" and "order", "password", or "item arrived damaged".
  • "the parcel came broken" scores 0 against everything: it shares no word with any FAQ, even though "broken" means "damaged" and "parcel" means "order". The argmax of all zeros is simply the first FAQ, a meaningless answer. This vocabulary mismatch is keyword search's central weakness.
  • The fix is to compare meanings instead of words: embed the query and the FAQs with a model that places "broken" near "damaged" (Lesson 7.22), which is vector searchlater · 14.71 (Lesson 14.71). Real systems often combine both, because keyword search is better at exact terms such as order numbers and product codes: hybrid search (Lesson 5.38).

BM25, the ranking formula used by Elasticsearch, OpenSearch and most search engines, is a refined TF-IDF: repeated words count less and less (the fifth "refund" adds little), and long documents do not win just by being long. Lesson 5.37 uses it for retrieval.

Step 6 · When to use word counts today

Use Why it still works
A baseline for any text classifier trains in a second; if a large model cannot beat it, something is wrong
Keyword search (BM25) exact matches on names, codes and rare terms; no GPU needed
Explainable filters the weights show exactly which words drove a decision
Very high volume, low cost filtering millions of texts per minute on a CPU

For anything that depends on meaning, word order, or phrasings not seen before, use embeddings or a language model.

The same idea as a formula
  • bag of words: document d → vector x with xⱼ = count of word j in d
  • TF-IDF weight: tfidf(w, d) = tf(w, d) × idf(w), with idf(w) = log((1 + N) / (1 + df(w))) + 1 in scikit-learn, where N is the number of documents and df(w) the number containing w; each row is then scaled to length 1
  • cosine similarity of query q and document d: (q · d) / (‖q‖ ‖d‖)
Check your mental model
  • ✗ "A 100% test score means the classifier is excellent."
    ✓ With templated or duplicated text, a random split leaks near-copies into the test set. Split by template, customer or document.
  • ✗ "The bag of words understands negation."
    ✓ It only counts words. Bigrams help a little; transformers handle it properly.
  • ✗ "TF-IDF search finds documents with the same meaning."
    ✓ It finds documents with the same words. Synonyms score zero.

Train the classifier on CountVectorizer(ngram_range=(1, 2)) instead. How many columns does the vocabulary have now, what is the test accuracy, and is "no need for a refund" classified any differently? (Solution M1.)

Practice
Apply it

Add a seventh FAQ, "My parcel arrived broken, what now?", to faqs, refit the TF-IDF vectoriser and run the queries again. Which query changes its answer, and what does that tell you about how to write FAQ entries for keyword search? (Solution X1.)

Solutions

SolutionP1 · Order numbers in the vocabulary

"sk" gets a count of 1 (it was in training, from every order number) and "refund" a count of 1. "48213" is counted only if exactly that number appeared in a training ticket, which is unlikely; otherwise it is silently ignored. Unique identifiers make useless features, and some teams replace them with a placeholder such as <order_id> before vectorising.

SolutionM1 · Adding bigrams

The vocabulary grows from 216 to 585 columns. Test accuracy rises only slightly, to about 83%. "no need for a refund, ..." is still classified as refund: the bigram "no need" never appeared in training, so it adds nothing, while "refund" and "a refund" still pull towards the refund class. Bigrams can only help with word pairs that the training data contains.

SolutionX1 · Matching the users' words

"the parcel came broken" now matches the new FAQ, because "parcel" and "broken" are in its text. Keyword search finds what is written in the users' own words, so good FAQ entries and documents include the common phrasings and synonyms people actually use. Embedding search (Lesson 14.71) relaxes this requirement, which is a big reason it became popular.

Recap
  • A bag of words turns each text into a sparse vector of word counts; word order and meaning are thrown away.
  • Linear classifiers on word counts train in seconds and can be inspected word by word, but only know words seen in training.
  • With templated or duplicated text, split by template or source; a random split can give a meaningless 100%.
  • TF-IDF weights words by how rare they are across documents; with cosine similarity it ranks documents for a query, and BM25 refines it.
  • Word counting fails on synonyms and negation; word vectors, embeddings and transformers address that, and hybrid search combines both.
