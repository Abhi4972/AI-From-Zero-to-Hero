Why this came about

By 2020 it was clear that neither kind of search was enough alone. Keyword search missed paraphrases; embedding search missed exact terms. Adding their scores did not work, because the scores are on unrelated scales. Reciprocal rank fusion, published in 2009 for combining search engines, turned out to be a simple and robust answer: combine the positions, not the scores. At the same time, cross-encoders, models that read a question and a passage together, proved far more accurate than either method at judging relevance, but too slow to run over a whole collection. Putting the pieces in order (search wide with both methods, fuse, then rerank a short list) became the standard retrieval stack.

In plain words first
Two searches, then a careful reader

Imagine finding a document in a large office. One assistant looks for folders with your exact words on the label. Another knows roughly where each topic is kept. Each misses things the other finds, so you ask both and merge their lists, trusting most the folders that both of them picked. That is hybrid search. Then a third person actually reads the dozen folders on the merged list and puts the truly relevant ones on top. That careful reader is a reranker: much slower per folder, which is why it only ever sees the short list.

On the first and third questions both methods put the same chunk first and disagree below it. That is exactly the situation in which combining helps.

Step 2 · Why you cannot add the scores

The obvious way to combine is to add each chunk's two scores. Look at the scores themselves:

q = "what does express delivery cost"
bm25_scores = bm25.get_scores(tokenize(q))
vector_scores = minilm_vecs @ model.encode([q], normalize_embeddings=True)[0]
print("BM25 scores  :", np.round(sorted(bm25_scores, reverse=True)[:4], 2))
print("cosine scores:", np.round(sorted(vector_scores, reverse=True)[:4], 2))
What you should see
BM25 scores  : [1.61 1.55 0.35 0.32]
cosine scores: [0.77 0.47 0.38 0.21]

BM25 scores here run from 0 to about 1.6; for another query they might reach 12. Cosine similarities live between about 0 and 1. Adding them lets one method drown out the other, differently for every query. You could rescale each list to 0 to 1 first (min-max normalisation), and some systems do, with a weight between the two. It works when tuned and is fragile when the score distributions shift.

Step 3 · Reciprocal rank fusion

Reciprocal rank fusion (RRF) ignores the scores and uses only positions. A chunk at position rank in a list earns 1 / (60 + rank) from that list; its total is the sum over lists. This is the lab's hybrid search:

# Step 5 · Hybrid search with Reciprocal Rank Fusion (RRF)
def rrf(rankings: list[list[str]], k: int = 60) -> list[str]:
    """Merge ranked lists: each item scores sum(1 / (k + rank)). No score normalization needed."""
    scores = {}
    for ranking in rankings:
        for rank, item in enumerate(ranking, start=1):
            scores[item] = scores.get(item, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

def search_hybrid(query: str, k: int = 3) -> list[str]:
    return rrf([search_bm25(query, 10), search_dense(query, 10)])[:k]

Work one example by hand to see what RRF rewards:

q = "my kettle was dead out of the box"
keyword_list, vector_list = search_bm25(q, 5), search_minilm(q, 5)
print(f"{'chunk':<18}{'keyword rank':>13}{'vector rank':>13}{'RRF score':>11}")
fused = {}
for name, ranking in [("keyword", keyword_list), ("vector", vector_list)]:
    for rank, chunk_id in enumerate(ranking, start=1):
        fused.setdefault(chunk_id, {})[name] = rank
for chunk_id in rrf([keyword_list, vector_list])[:5]:
    r = fused[chunk_id]
    score = sum(1 / (60 + rank) for rank in r.values())
    print(f"{chunk_id:<18}{r.get('keyword', '-'):>13}{r.get('vector', '-'):>13}{score:>11.4f}")
What you should see
chunk              keyword rank  vector rank  RRF score
warranty#1                    1            1     0.0328
refund-policy#0               2            4     0.0318
warranty#0                    4            2     0.0318
cod#0                         3            -     0.0159
refund-policy#1               -            3     0.0159

warranty#1 is first in both lists: 1/61 + 1/61 = 0.0328. The next two chunks each have one good and one middling position and tie. Chunks that appear in only one list get a single contribution and fall to the bottom. RRF rewards agreement: a chunk both methods like beats a chunk one method loves and the other never found.

Reading this output
Why 60, and other details
  • The constant 60 comes from the original paper and is rarely changed. A smaller number makes first place count for much more than second; a larger one flattens the differences.
  • Each list can be given a weight (multiply its contribution) if evaluation shows one method deserves more trust on your data.
  • RRF works for any number of lists: keyword, several embedding models, several rewrites of the question (Lesson 14.30).
  • search_hybrid uses the stand-in search_dense so that later lessons give identical numbers everywhere. The worked example used the real model. Swap as you like.

Step 4 · A reranker: reading the question and the passage together

An embedding model reads the question and each passage separately and compares two vectors. It never sees them side by side. A cross-encoder takes the question and one passage as a single input, lets attention (Lesson 7.3) connect every question word with every passage word, and outputs one relevance score. It is much more accurate, and it cannot be precomputed: every (question, passage) pair needs its own run of the model.

So it is used only on a short list. Take the top six chunks from hybrid search and rerank them:

from sentence_transformers import CrossEncoder
import time

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L6-v2")        # 22 million parameters; reads a question and a passage together
by_id = {c[0]: c[2] for c in CHUNKS}

def rerank(query: str, chunk_ids: list[str], k: int = 3) -> list[str]:
    scores = reranker.predict([(query, by_id[c]) for c in chunk_ids])  # one forward pass per (question, passage) pair
    order = np.argsort(-scores)
    return [chunk_ids[i] for i in order[:k]]

q = "maximum order value for paying at the door"
candidates = rrf([search_bm25(q, 9), search_minilm(q, 9)])[:6]
print("hybrid order     :", candidates)
scores = reranker.predict([(q, by_id[c]) for c in candidates])
for c, s in sorted(zip(candidates, scores), key=lambda pair: -pair[1]):
    print(f"  {s:6.2f}  {c:<18} {by_id[c][:66]}...")
print("after reranking  :", rerank(q, candidates))

Hybrid search had a shipping chunk first and the right chunk, cod#0, in third place: neither search connected "paying at the door" with cash on delivery strongly enough. The reranker, reading the question next to each passage, gives cod#0 the highest score and moves it to the top. The numbers are the model's raw scores: higher means more relevant, and only their order and the gaps between them matter. cod#0 stands clearly apart, while the five irrelevant chunks are bunched together below it. A gap like that is what you look for when choosing a cut-off score.

What does that accuracy cost?

pairs = [(q, by_id[c]) for c in candidates]
start = time.time(); reranker.predict(pairs * 5); per_pair = (time.time() - start) / (len(pairs) * 5)
start = time.time(); model.encode([q] * 30); per_query = (time.time() - start) / 30
print(f"reranking: about {per_pair * 1000:.0f} ms per (question, passage) pair, so about {per_pair * 50 * 1000:.0f} ms for 50 candidates")
print(f"embedding the query: about {per_query * 1000:.0f} ms, once, however many documents there are")
What you should see
reranking: about 10 ms per (question, passage) pair, so about 502 ms for 50 candidates
embedding the query: about 2 ms, once, however many documents there are

(Your numbers depend on your processor.) Embedding the question is one small model run, however large the collection. Reranking is one run per candidate, so its cost grows with the length of the short list. This is why the usual settings are to retrieve 50 to 100 candidates and rerank them down to 5 or 10, on a GPU or a hosted reranking service where each pair takes about a millisecond.

In production you rarely host the cross-encoder yourself at first. Hosted rerankers include Cohere Rerank, Voyage rerankers, Amazon Rerank on Bedrock, Google's Ranking API and Azure AI Search's semantic rankerlater · 14.130; open models such as the BGE rerankers run on your own hardware.

In production
Rerankers: when they help and when they don't

A reranker fixes ranking problems: the right chunk is retrieved but sits at position 15. It cannot fix recall problems: a chunk that was never retrieved cannot be reranked to the top. So widen retrieval first (50 to 100 candidates), then rerank. Costs to watch: tens to hundreds of milliseconds per query, which matters for voice and chat; and rerankers that only read the chunk text, so pass the title and section too. Some teams find that a good reranker lets them use a cheaper embedding model, which is a useful trade to test.

The retrieval stack, and what to tune

Stage What it is for Typical setting
Keyword search Exact terms, codes, names Top 50 to 100
Vector search Paraphrases, meaning Top 50 to 100
Fusion (RRF) One list that both methods agree on k = 60, equal weights to start
Reranker Precise ordering of the short list Rerank 50 to 100, keep 5 to 10
Cut-off Do not pass weak results to the model A minimum reranker score, chosen on your evaluation set

Reranker choices include hosted services (Cohere Rerank, Voyage, Amazon Rerank on Bedrock, Google's Ranking API, the semantic ranker in Azure AI Search) and open models (the BGE and Qwen reranker families, and small MS MARCO cross-encoders like the one used here).

Go deeper (optional)
Between the two extremes: late interaction

ColBERT and its successors keep one vector per token instead of one per passage, and score a passage by matching each question token to its closest passage token. It is more accurate than a single vector and far cheaper than a cross-encoder, at the price of a much larger index. The same idea applied to images of pages (ColPalilater · 4.30) lets you search PDFs without parsing them (Lesson 4.30).

Check your mental model
  • ✗ "Scores from BM25 and vectors can be added."
    ✓ They are on different scales; fuse by rank, or normalise carefully and tune.
  • ✗ "A reranker searches the whole collection."
    ✓ It only reorders a short candidate list, because it needs one model run per candidate.
  • ✗ "A reranker can find a passage that retrieval missed."
    ✓ It can only reorder what it is given. Fix recall first by retrieving more candidates.
  • ✗ "Reranking always improves answers."
    ✓ Measure it; on small, clean corpora it may add delay for little gain.

Exercises

Predict before you run

A chunk ranks 1st in BM25 and 20th in vector search; another ranks 3rd in both. With RRF and k = 60, which scores higher? (Solution P1.)

Break it on purpose

Merge BM25 and vector results by adding their raw scores instead of RRF, for the three questions in Step 1. What goes wrong? (Solution B1.)

Debugging exercise

After adding a reranker, latency doubled and quality barely moved. The pipeline reranks the top 200 candidates. What do you change? (Solution D1.)

Make it your own

Add a weights argument to rrf so vector search can count twice as much as BM25. Then write search_best(query): hybrid search with search_minilm, the top six candidates reranked, the top three returned. Try it on the questions from Lessons 5.21 and 14.26. (Solution M1.)

Solutions

SolutionP1 · Consistent beats extreme

The second: 2 × 1/63 ≈ 0.0317 against 1/61 + 1/80 ≈ 0.0289. RRF rewards results that both methods rank well, which is usually what you want, and needs no score normalization.

SolutionB1 · Scores on different scales

BM25 scores are unbounded and depend on the query; cosine scores sit roughly between 0 and 1. Adding them lets BM25 dominate when a query has rare words and vanish when it has none, so the combined ranking simply follows one method or the other. Normalize carefully, or use rank-based fusion such as RRF.

SolutionD1 · Rerank fewer, better candidates

Rerank the top 20 to 50 from hybrid search, where most relevant results already are; cross-encoders cost time per candidate. Then check on the eval set whether reranking helps at all for this corpus; for a small, clean corpus it may not.

SolutionM1 · Weighted fusion and the full stack

In rrf, multiply each list's contribution by its weight before summing: scores[item] += w / (k + rank). search_best is rerank(query, rrf([search_bm25(query, 9), search_minilm(query, 9)])[:6]). Tune weights only on an evaluation set, and be wary of a weight that wins on a handful of questions: check it on new questions before keeping it.

Check your understanding

Explain the mechanismWhat is hybrid search, and why is it the default for production RAG?

Worked answer. Hybrid search runs keyword search and vector search and fuses the rankings, commonly with Reciprocal Rank Fusion. Keyword search catches exact terms; vectors catch paraphrases; their failures rarely overlap, so the fusion is more robust than either. A reranker then reorders the top candidates for precision.

A plausible wrong answer. "It averages two models." It fuses rankings from two different signals.

Follow-ups. Where does a reranker fit, and what does it cost?

Debug a failureHybrid search is worse than vector search alone on your eval. What do you check?

Worked answer. Whether BM25 is badly configured (tokenization of IDs, languages, stop words), whether the fusion weights or k are off, and whether the eval questions are mostly paraphrases where BM25 only adds noise. Look at per-question results to see where the keyword list hurts.

A plausible wrong answer. "Hybrid is always better, so the eval is wrong." Measure, then fix the weak component.

Follow-ups. How would you split the eval by question type?

Defend a designIs a reranker worth its latency and cost?

Worked answer. When the top results from hybrid search are close but not in the right order, which is common for large corpora and subtle questions: rerankers usually give the largest precision gain per change. Not when the eval shows little gain or latency budgets are tight; then improve chunking or use a smaller reranker.

A plausible wrong answer. "Always add a reranker." It adds latency to every query; justify it with the eval.

Follow-ups. How would you choose how many candidates to rerank?

Recap
  • Keyword and vector search make different mistakes, so running both and merging the lists is more robust than either.
  • Their scores are on unrelated scales. Reciprocal rank fusion merges by position: each list contributes 1 / (60 + rank).
  • A cross-encoder reranker reads the question and a passage together. It is the most accurate judge and needs one model run per candidate, so it only sees a short list.
  • The production pattern is a funnel: retrieve 50 to 100 with both methods, fuse, rerank to 5 or 10, cut off weak results.
  • A reranker fixes ordering, never recall.
