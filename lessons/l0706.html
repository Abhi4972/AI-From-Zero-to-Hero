Why this came about

Many people think of AI work as a team with roles. CrewAI (2023) made that the programming model: agents with roles and goals, tasks and a process, and later added Flows for explicit control in production.

In plain words first
A crew with roles and tasks

CrewAI describes work as a team: agents with roles and goals, tasks assigned to them, and a process (sequential or managed by a lead agent) that runs the crew. Flows add explicit, event-driven control for production. It is quick to express role-based collaboration, at the cost of less fine-grained control over each step than a graph.

CrewAI: role-based crews and event-driven flows

Best fit: quick multi-agent prototypes and business-process automation, especially for teams who think in roles ("researcher", "writer", "reviewer").

CrewAI has two layers. Crews are teams of agents, each with a role, goal and backstory, working through tasks in a sequential or hierarchical (manager-led) process. Flows are event-driven workflows (@start, @listen, @router) with typed state, persistence and human feedback, which can call crews as steps.

import os
os.environ["CREWAI_DISABLE_TELEMETRY"] = "true"   # CrewAI sends anonymous usage telemetry unless disabled
os.environ["OTEL_SDK_DISABLED"] = "true"

import mockllm
from crewai import Agent, Task, Crew, Process, LLM
from crewai.tools import tool

BASE_URL = mockllm.start()        # one mock server for this whole module (CrewAI's flows also export a `start`)
llm = LLM(model="openai/mock-model", base_url=BASE_URL, api_key="mock")   # provider/model strings
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool("get_order_status")
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

support = Agent(role="ShopKart support specialist", goal="Answer order questions accurately",
                backstory="You know ShopKart's order systems.", tools=[get_order_status], llm=llm, verbose=False)
task = Task(description="Customer asks: {question}", expected_output="A short, accurate answer", agent=support)
crew = Crew(agents=[support], tasks=[task], process=Process.sequential, verbose=False)

result = crew.kickoff(inputs={"question": "Where is A-1001?"})    # {question} is filled from inputs
print("crew:", result.raw)
What you should see
crew: Here is what I found: A-1001 is shipped

from pydantic import BaseModel
from crewai.flow.flow import Flow, start, listen, router
from crewai.events.utils.console_formatter import set_suppress_console_output
set_suppress_console_output(True)                    # hide CrewAI's progress panels so only your output shows

class TicketState(BaseModel):
    text: str = ""
    category: str = ""
    reply: str = ""

class SupportFlow(Flow[TicketState]):
    @start()
    def receive(self):
        self.state.text = "I want a refund for A-1002"

    @router(receive)                                   # its return value picks the next listener
    def classify(self):
        self.state.category = "refund" if "refund" in self.state.text.lower() else "status"
        return self.state.category

    @listen("refund")
    def handle_refund(self):
        self.state.reply = "Refund request logged."   # a crew.kickoff(...) could run here
        return self.state.reply

    @listen("status")
    def handle_status(self):
        self.state.reply = "Checking status."
        return self.state.reply

flow = SupportFlow()
print(flow.kickoff(), "|", flow.state.category)
What you should see
Refund request logged. | refund

Add @persist (from crewai.flow.persistence) to save flow state between runs.

Watch out: crews are easy to start and harder to control precisely. Keep crews small, give tasks a concrete expected_output, and use flows for anything that must happen in a fixed order. CrewAI also sells a managed platform (CrewAI AMP) for deployment and monitoring.

CrewAI's words, and what you already call them

CrewAI's vocabulary comes from offices, not from engineering, which is why business teams find it approachable. Every word maps to something you have built.

CrewAI says What it is Where you built it
Agent, with a role, goal and backstory A model with a system prompt. The three fields are joined into that prompt Lesson 11.6
Tool A function with a description and typed arguments Lesson 14.4
Task, with a description and expected_output One user message for one agent, with a statement of what a finished answer looks like Lesson 11.6
Crew with Process.sequential Prompt chaining: each task's output is context for the next Lesson 14.8
Crew with Process.hierarchical A supervisor (the "manager") that delegates tasks to the agents Lesson 14.12
Flow with @start, @listen, @router A workflow whose steps are plain functions, with routing and typed state Lessons 14.8 and 14.60
kickoff(inputs=...) Run it, filling the {placeholders} in the task descriptions Lesson 14.53

Two practical consequences follow from the table. A crew is several prompts chained together, so every agent you add is at least one more model call per run, and "researcher, writer, reviewer" for a question a single call could answer triples the cost for no gain. And expected_output is the most important field you write: it is the only place where you say what "done" means, and tasks without a precise one are where crews drift.

Check your mental model
  • ✗ "Role descriptions make agents behave like those roles."
    ✓ They shape prompts; tools, tasks and checks determine actual behaviour.
  • ✗ "Crews are cheaper because agents collaborate."
    ✓ Every agent turn is a model call; crews can be expensive.
  • ✗ "CrewAI cannot do deterministic workflows."
    ✓ Flows provide explicit control flow alongside crews.

Exercises

Predict before you run

A crew has a researcher and a writer agent with sequential tasks. How many model calls does a single run take at least? (Solution P1.)

Break it on purpose

Give every agent in the crew all tools. What happens to reliability? (Solution B1.)

Debugging exercise

A CrewAI flow produces different outputs on each run for the same input. What do you control? (Solution D1.)

Make it your own

Wrap the crew in a Flow that validates the writer's output and reruns once on failure. (Solution M1.)

Solutions

SolutionP1 · Crews multiply calls

At least one per task, usually more with tool use and the agents' reasoning. Crews are convenient but call-heavy.

SolutionB1 · Scope tools per agent

Agents choose tools less reliably and can take actions outside their role. Give each agent only its tools.

SolutionD1 · Variability

Model temperature, task descriptions and expected outputs, and structured outputs for tasks. Flows add deterministic control around crews.

SolutionM1 · Flows for control

Use a flow step after the crew to validate with a schema or rules, and loop back on failure with a limit.

Check your understanding

Explain the mechanismWhat is CrewAI's model of agents?

Worked answer. Role-based agents (role, goal, backstory, tools) collaborating on tasks in a crew with a process (sequential or hierarchical), plus Flows for event-driven, deterministic orchestration around crews. It is quick for multi-role pipelines, with less fine-grained control than graph runtimes.

A plausible wrong answer. "Crews are always better than one agent." They add calls and coordination.

Follow-ups. When would you use a Flow without a crew?

Debug a failureA hierarchical crew's manager keeps delegating the same task. What do you check?

Worked answer. Task descriptions and expected outputs that make completion unclear, and limits on iterations. Make outputs verifiable.

A plausible wrong answer. "The manager model is weak." The task definition is ambiguous.

Follow-ups. How would you cap delegation?

Defend a designCrewAI for production?

Worked answer. For multi-role content and research pipelines where speed of building matters and steps are well defined, with Flows for control. For transactional agents with approvals and strict state, a graph runtime is safer.

A plausible wrong answer. "Not production-ready." It is used in production; fit matters.

Follow-ups. What would you add before production?
