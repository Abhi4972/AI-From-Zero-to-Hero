In plain words first
The idea in one line

Passing your tests proves agreement on your tests, so equality needs a grid that reaches every edge and bytes that match after relocation masking.

The problem

In plain words first

When you rebuild a function from its machine code, a few passing tests prove little: the rebuild can agree on the inputs you tried and differ on others, often exactly where numbers overflow. This lesson's standard is stronger. Leg one runs the original and the rebuild on a large, designed grid of inputs and compares results. Leg two compiles the rebuild and compares its bytes, its relocations and the constants they point to with the original. The runs below push leg one to its limit: for a function of one 32-bit argument, every possible input can simply be tried, all 4.3 billion of them. For two arguments that is impossible, so a solver (Z3) proves equality, or finds an input where the two differ, from a formula built directly from the original machine code.

You asked rea for the function dossier of percent_change in our ledger-x86_64-O1.o fixture. Ghidra 12.1.4 returned pseudocode, and the agent wrote this C from it:

int percent_change(int before, int after) {
    if (before == 0) return 0;
    return (int)(((long)after - before) * 100 / before);
}

Four tests pass: (100, 150) gives 50, (200, 100) gives -50, (0, 5) gives 0, (50, 100) gives 100. The agent also rebuilt grade as four if statements on 90, 80, 70, and 60. Six more tests pass. The report says "verified".

That report answers none of these questions:

  • What does the original return when (after - before) * 100 does not fit in 32 bits?
  • What does the original return for a score of 110?
  • Does the rebuild compile to the same 16 bytes as the original?
  • When two compiled functions hold the same bytes, do their relocations point at the same constants?
  • Which evidence record did the rebuild come from, and did the agent read the listing or the pseudocode?
  • What status does the proof get on a host without a C compiler?

Every target in this lesson is a program we wrote and compiled. The scope and law rules from lesson 32 apply unchanged.

The decompiler saw cltd and idivl write both edx and eax and modelled a 16-byte return value with a 64-bit division. The listing in the same record says something plainer:

0x100000: TEST EDI, EDI
0x100002: JZ 0x0010000d
0x100004: SUB ESI, EDI
0x100006: IMUL EAX, ESI, 0x64
0x100009: CDQ
0x10000a: IDIV EDI
0x10000c: RET
0x10000d: XOR EAX, EAX
0x10000f: RET

Every operation is 32 bits wide. IMUL EAX, ESI, 0x64 multiplies in 32 bits and keeps the low half. CDQ sign-extends eax into edx, and IDIV EDI divides the 64-bit pair by a 32-bit divisor. A rebuild that follows the listing is 100 * (after - before) / before in int.

The grade record has the same shape. The pseudocode names a table, *(uint *)(&DAT_001000b4 + (ulong)uVar2 * 4), and an unreadable default expression built from 0x66666667. The listing shows the divide by 10 as IMUL RAX, RAX, 0x66666667, SAR RCX, 0x22, SHR RAX, 0x3f, ADD ECX, EAX. Then ADD ECX, -0x6, CMP ECX, 0x4, and JA keep tens from 6 to 10. XOR EAX, EAX before the compare is the default of 0. LEA RCX, [0x1000b4] and MOV EAX, dword ptr [RCX + RAX*0x4] read a table of five 4-byte entries.

Step 4 read those 20 bytes: 01000000 02000000 03000000 04000000 04000000. The table is 1, 2, 3, 4, 4 for tens 6, 7, 8, 9, 10. That is the switch in ledger.c, with case 10 and case 9 sharing the value 4.

Both proofs in rea's own evidence pages started from the listing and from read_bytes of constants. The DX-Ball first pseudocode was FUN_00406400(void) with no stack input, and the instruction view corrected it. Read the listing first. Cite the record id, then write the C.

Leg One: Execute and Compare

McKeeman's 1998 definition of differential testing needs "two or more comparable systems" fed "mechanically generated test cases", and treats a different result, a hang, or a crash as a bug candidate. He named the hard part: "The ugliest problem in testing is evaluating the result of a test." The original function is the oracle here. We do not need to know the right answer. We need the original and the rebuild to disagree nowhere on a grid that reaches every hazard.

Design the grid

input_grid() in code/main.py builds 92 cells. For percent_change it takes every pair from ten before values and seven after values:

before: 0, 1, -1, 3, -3, 7, 100, -100, 2147483647, -2147483648
after:  0, 5, -5, 105, 536870911, 2147483647, -2147483648

For grade it takes 22 scores: both sides of each band edge, negatives, 0, 110, and the two int limits. classify() tags each cell. Overflow has 32 cells, negative 17, boundary 14, plain 12, and zero guard 7. Negative truncation has 5, rounding 2, beyond the switch 2, and trap 1.

Each class exists for one reason. The zero guard cells check the TEST EDI, EDI branch. Negative cells check truncating division: C and idiv round toward zero, so -9 / 10 is 0 and -10 / 10 is -1. Rounding cells check that the multiply happens before the divide, so (105 - 100) * 100 / 100 is 5 and not 0. Overflow cells make (after - before) * 100 exceed 32 bits. The one trap cell makes the wrapped product equal INT_MIN with before equal to -1.

Yang, Chen, Eide, and Regehr built Csmith to generate programs with no undefined behaviour. An oracle disagreement on undefined behaviour is noise and never a bug report. Signed overflow is undefined in C. Our oracle is a compiled object with one fixed behaviour, so overflow cells are in scope. The lesson is to know which cells rest on the standard and which rest on the compiled bytes.

The driver and the trap

code/driver.c reads one cell per line from stdin and prints the inputs, the original result, and the rebuild result. build_harness() compiles the candidate with -Dpercent_change=cand_percent_change -Dgrade=cand_grade, so both versions link into one program under different names. On an x86-64 Linux host the original is the fixture object itself. On any other host it is ledger.c compiled natively, and the report records original_kind: fixture-source.

The driver installs a SIGFPE handler with sigsetjmp and siglongjmp. For before = -1 and after = 536870911, the difference is 536870912 and the 32-bit product wraps to -2147483648. On x86-64, idiv with that dividend and a divisor of -1 raises the divide error exception. The quotient does not fit in 32 bits (Intel SDM Volume 2, IDIV). The handler turns that into the recorded value trap.

On AArch64, sdiv has no trap and returns -2147483648 for the same operands. Our run on an arm64 Mac recorded exactly that. The oracle depends on the architecture, and the report says which one ran.

The report compares the model with the observed original on every cell. Zero disagreements means the model and the binary agree on every cell. The model is derived evidence and the run is observed evidence. The report keeps them in separate fields.

Leg Two: Recompile and Compare

Behaviour on a grid is one leg. The second leg asks whether the rebuild, compiled with the same compiler and flags, produces the same bytes. The DX-Ball project reported "63 matching bytes" for its helper. The TH04 project reported a 2,139-byte match. Each used the compiler of its own period. rea itself cannot do this. Its compare_functions line-diffs provider text and attaches the limitation "Assembly is opaque provider text; relocation normalization is unavailable."

Read the object

ElfObject in code/main.py reads one ELF64 relocatable object with struct.unpack_from. It checks the magic, the 64-bit class, little-endian data, e_machine 62, and e_type 1. Then it walks the section headers, the string table, .symtab, and every .rela section. In the fixture, percent_change starts at .text offset 0 with size 16 and grade at 0x10 with size 46. total starts at 0x40 with size 31 and grade_label at 0x60 with size 63.

The 16 bytes of percent_change are 85 ff 74 09 29 fe 6b c6 64 99 f7 ff c3 31 c0 c3. The function has no relocations. grade has one: offset 0x26 inside the function, type R_X86_64_PC32, symbol .rodata, addend 0x10. It belongs to the 7-byte leaq at offset 0x23, whose last four bytes are the displacement field.

Mask, then compare the records

In a RELA object the addend lives in the relocation record, and the four field bytes are zero. The candidate grade_switch.o also holds zero there. A plain byte compare passes while the two relocations name different places. mask_relocations() zeroes the field on both sides anyway, so the same method holds for REL objects and for Mach-O, where the field carries the addend.

Then prove_bytes() compares the relocation records by offset, type, and target section. The original says .rodata+0x10 and the candidate says .rodata-0x4. The addend differs because the candidate object has no labels.rel table in front of its switch table. A different addend is a different offset, not a different function.

Read the constants the relocation points at

For a PC-relative field that ends its instruction, the CPU adds the next instruction address, so the target is symbol plus addend plus 4. In the original that is .rodata+0x14, and in the candidate it is .rodata+0x0. read_table() reads five 4-byte entries there. Both hold 1, 2, 3, 4, 4.

The count five comes from the listing: CMP ECX, 0x4 with JA admits indexes 0 to 4, and [RCX + RAX*0x4] reads 4 bytes per index. CLAIMS in code/main.py records that shape for grade and records zero relocations for percent_change.

This step exists because of a bug the TH08 project documented. Its older comparison "replayed the target address into the instruction's relocation field, then compared instruction bytes without checking the floating-literal data at that address. Source 0.0 could therefore appear exact against target 128.0." The fix audited 1,548 floating-literal references and corrected twelve more. grade_case10_wrong.c is our version of that bug. Its 46 code bytes equal the original, its relocation record has the same shape, and its table is 1, 2, 3, 4, 3. Only the constant check fails it.

What rea's verifier can and cannot say

rea's verify_reconstruction takes claims that point at comparison Evidence and returns pass, fail, or unknown per claim. Its fixed limitation reads "Pass means every declared claim passed; it does not establish global implementation equivalence." A claim about a function compares provider text from compare_functions. A behavioural claim compares two recorded process captures from compare_process_captures. When a source record has incomplete call coverage, a claim about calls is unknown. Nothing inside rea compiles a rebuilt function or runs it over your input grid. The two legs in this lesson are the part rea leaves to you.

rea's obligation ledger expects a proof record with predicate_type: "rea.reconstruction-proof", operation: "verify_reconstruction_obligations", confidence: "observed", and normalized_result.passed === true. No public rea tool emits one. build_proof() in code/main.py mints it:

On a host without a C compiler the two behaviour claims are unknown, so the record says unknown even when both byte claims pass. authority is controlled-replay, because the proof comes from our own harness and not from the object file alone.

What the Research Says

Liu, Raff, and Micinski measured eight decompilation systems in nine configurations in 2026. Candidates that passed every test the benchmark includes still diverged on fuzzed inputs. The rate was 4.9 percent overall and up to 13 percent for one system. On 300 GitHub library functions and 287 CVE-grounded functions, the strongest refinement model raised Ghidra's build rate from 75 percent to 90 percent. Over the same functions the behavioural match rate fell from 74 percent to 62 percent. They traced the cause to invented fields, types, callees, and guards that replaced the visible unknowns a traditional decompiler leaves behind.

Our percent_change_wide.c is one of those invented types. The pseudocode offered a long, the rebuild kept it, and the result compiled, passed ten tests, and failed 26 overflow cells. The grade-threshold rebuild is an invented guard. Both would count as re-executable under the LLM4Decompile metric, which recompiles the output and runs the benchmark's assertions. Ghidra's own pseudo-C passed 20.12 percent of those assertions on HumanEval-Decompile.

DecompileBench measured 23,400 functions from 130 real programs. It found LLM methods 52.2 percent lower on functionality correctness than industrial decompilers, with higher understandability scores.

The three proofs the field uses are the three legs you can build. Phoenix and DREAM recompile the output and run the original program's tests. McKeeman and Csmith run generated inputs against the original with inputs kept inside defined behaviour. Ramos and Engler check two C functions with bounded symbolic execution, which proves equality on all explored paths up to an input size. This lesson builds the first two. The third is the practice lab in lesson 35's evidence ledger when a grid is too small to trust.

The same idea as a formula

Equivalence. A rebuild R equals the original F on a domain D if ∀x∈D:R(x)=F(x). For one int argument, ∣D∣=232, small enough to enumerate. For two, ∣D∣=264≈1.8×1019: at 109 comparisons per second that is about 585 years.

Proof by refutation. A solver decides whether

∃x: ¬trapF​(x)∧R(x)=F(x)
is satisfiable. Unsat means no such input exists: a proof for all 264 inputs. Sat returns a concrete counterexample.

Machine arithmetic. Bit-vector semantics wrap modulo 232: (a−b)⋅100 is computed mod232 and division truncates toward zero. So 100(a−b)≡(a−b)⋅100≡100a−100b(mod232), while dividing first, ⌊(a−b)/b⌋⋅100, is a different function.

Worked example
Why the `wide` rebuild is wrong at one input
  • The solver's counterexample is before = 42240, after = -2051050250.
  • Original, 32-bit: a−b=−2051092490; times 100 is −205109249000, which wraps modulo 232: −205109249000+48⋅232=1049181208. Divided by 42240 that is 24838.5, truncated to 24838, the original's answer (as Z3 reports).
  • wide rebuild, 64-bit: (−2051092490)×100=−205109249000 with no wrap; divided by 42240 that is −4855806.1, truncated to −4855806, which fits in 32 bits, so the cast changes nothing.
  • Same source-level formula, different arithmetic width: the rebuild is "more correct" mathematically and wrong as a copy of the binary.
Check your mental model
  • ✗ "Ten passing tests mean the rebuild is equivalent."
    ✓ Only all inputs (by enumeration or proof) do; tests sample.
  • ✗ "Exhaustive testing is always impossible."
    ✓ For one 32-bit argument it takes under a minute.
  • ✗ "A solver proof covers everything the function can do."
    ✓ It covers the model: here, the non-trapping inputs of this exact instruction sequence.
  • ✗ "A wider integer type can only make a rebuild more accurate."
    ✓ It removes the original's wrap-around, so the rebuild differs exactly where overflow happens.

Every `int`: an exhaustive leg one for `grade`

The block writes a C harness, links the original clang object (grade) with the four candidates (renamed cand_*), and loops over every 32-bit value. About 50 seconds on a 2-core CPU (21 billion calls).

# Leg one, made total: for a one-argument int function, "all inputs" is only 2^32 cases. A C harness links
# the original clang object next to the four grade candidates and compares them on every int.
import pathlib, subprocess, tempfile, time
from main import CANDIDATES, ORIGINAL_OBJECT
tmp = pathlib.Path(tempfile.mkdtemp()); names = ["switch", "table", "thresholds", "case10_wrong"]
for n in names:                                       # rename each candidate so all can link together
    (tmp / f"c_{n}.c").write_text((CANDIDATES / f"grade_{n}.c").read_text().replace("int grade(", f"int cand_{n}(", 1))
(tmp / "all.c").write_text(r'''
#include <stdio.h>
#include <stdint.h>
int grade(int);
''' + "".join(f"int cand_{n}(int);\n" for n in names) + r'''
int main(void) {
    int (*c[])(int) = {''' + ", ".join(f"cand_{n}" for n in names) + r'''};
    const char *name[] = {''' + ", ".join(f'"grade_{n}"' for n in names) + r'''};
    unsigned long long bad[4] = {0}; long long first[4] = {0};
    for (int64_t x = INT32_MIN; x <= INT32_MAX; x++) {          /* every 32-bit input, in order */
        int want = grade((int)x);
        for (int k = 0; k < 4; k++) if (c[k]((int)x) != want && bad[k]++ == 0) first[k] = x;
    }
    for (int k = 0; k < 4; k++)
        if (bad[k]) printf("%-20s differs on %llu of 4294967296 inputs, first at grade(%lld)\n", name[k], bad[k], first[k]);
        else        printf("%-20s equal to the original on all 4294967296 inputs\n", name[k]);
}
''')
exe = tmp / "exhaust"
subprocess.run(["gcc", "-O2", "-fwrapv", str(tmp / "all.c"), *[str(tmp / f"c_{n}.c") for n in names], str(ORIGINAL_OBJECT), "-o", str(exe)], check=True)
t0 = time.time(); print(subprocess.run([str(exe)], capture_output=True, text=True, timeout=230).stdout, end="")
print(f"({time.time() - t0:.0f} s for {5 * 2**32:,} calls)")

Reading this output

Two candidates are equal everywhere. The switch rebuild and the 5-entry table agree with the original on all 4,294,967,296 inputs. This is not a test result; it is a complete check of the function's domain.

The thresholds rebuild is wrong on half of all integers. It returns 4 for every score of 90 or more, while the original returns 0 from 110 upward (110/10 - 6 = 5 is past the table). That is 2,147,483,538 wrong inputs, first at 110, the first value past the original's range.

The case 10 slip is wrong on exactly 10 inputs, 100 to 109, where it returns 3 instead of 4. A random test of a few thousand scores would very likely miss all ten.

The cost is small. About 50 seconds for 21 billion calls on this 2-core machine. For any function of one 32-bit (or smaller) argument, enumeration is the strongest and simplest leg one.

Proof for `percent_change` from the machine code

This block continues from the one above. Capstone decodes the original's nine instructions; a tiny symbolic executor (only test, je, sub, imul, xor, cdq, idiv, ret) turns them into a Z3 bit-vector formula, with a trap condition for idiv. Each candidate is written in 32-bit wrap-around arithmetic, and Z3 either proves equality or returns a counterexample. About a second.

# Continues from the block above. Two arguments means 2^64 inputs: too many to enumerate, so prove it.
# A tiny symbolic executor turns the original's machine code (decoded by Capstone from the object) into a
# Z3 formula; each candidate is written with C's 32-bit wrap-around; Z3 searches for any input that differs.
import z3
from capstone import Cs, CS_ARCH_X86, CS_MODE_64, x86
from main import ElfObject
fn = ElfObject(ORIGINAL_OBJECT).function("percent_change")
md = Cs(CS_ARCH_X86, CS_MODE_64); md.detail = True
code = list(md.disasm(fn.data, 0)); print("original:", "; ".join(f"{i.mnemonic} {i.op_str}" for i in code))

def symbolic(before, after):                        # handles exactly the instructions this function uses
    traps = []
    def run(pc, reg, zf):
        reg = dict(reg)                                 # each path gets its own registers
        val = lambda op: z3.BitVecVal(op.imm, 32) if op.type == x86.X86_OP_IMM else reg[md.reg_name(op.reg)]
        for ins in code[pc:]:
            ops = ins.operands
            if ins.mnemonic == "test": zf = (val(ops[0]) & val(ops[1])) == 0
            elif ins.mnemonic == "je":
                target = next(k for k, c in enumerate(code) if c.address == ops[0].imm)
                return z3.If(zf, run(target, reg, zf), run(code.index(ins) + 1, reg, zf))
            elif ins.mnemonic == "sub": reg[md.reg_name(ops[0].reg)] = val(ops[0]) - val(ops[1])
            elif ins.mnemonic == "imul": reg[md.reg_name(ops[0].reg)] = val(ops[1]) * val(ops[2])
            elif ins.mnemonic == "xor": reg[md.reg_name(ops[0].reg)] = val(ops[0]) ^ val(ops[1])
            elif ins.mnemonic == "cdq": reg["edx"] = z3.If(reg["eax"] < 0, z3.BitVecVal(-1, 32), z3.BitVecVal(0, 32))
            elif ins.mnemonic == "idiv":
                # edx:eax / d. After cdq, edx:eax is eax sign-extended, so the 64-bit quotient equals the 32-bit
                # truncating quotient whenever it fits; it does not fit only for INT_MIN / -1, which traps.
                d = val(ops[0]); x = reg["eax"]
                traps.append(z3.And(z3.Not(zf), x == -2**31, d == -1))
                reg["eax"] = x / d                       # Z3's / on bit-vectors is signed, truncating division
            elif ins.mnemonic == "ret": return reg["eax"]
            else: raise NotImplementedError(ins.mnemonic)
    start = {"edi": before, "esi": after, "eax": z3.BitVec("eax0", 32), "edx": z3.BitVec("edx0", 32)}
    result = run(0, start, None)
    return result, z3.Or(*traps) if traps else z3.BoolVal(False)

b, a = z3.BitVecs("before after", 32)
orig, orig_trap = symbolic(b, a)
wide = lambda: z3.Extract(31, 0, (z3.SignExt(32, a) - z3.SignExt(32, b)) * 100 / z3.SignExt(32, b))
CANDS = {"percent_change_mul_first": 100 * (a - b) / b, "percent_change_split": (a * 100 - b * 100) / b,
         "percent_change_div_first": (a - b) / b * 100, "percent_change_wide": wide()}
for name, expr in CANDS.items():
    s = z3.Solver(); s.add(z3.Not(orig_trap), b != 0, expr != orig)
    if s.check() == z3.unsat: print(f"{name:<26} PROVED equal for every non-trapping input")
    else:
        m = s.model(); x, y = m[b].as_signed_long(), m[a].as_signed_long()
        print(f"{name:<26} counterexample before={x}, after={y}: original {m.eval(orig).as_signed_long()}, candidate {m.eval(expr).as_signed_long()}")
s = z3.Solver(); s.add(orig_trap)
print("the original traps (SIGFPE) on some input:", s.check() == z3.sat, "| e.g.", {k: s.model()[v].as_signed_long() for k, v in (("before", b), ("after", a))})
What you should see
original: test edi, edi; je 0xd; sub esi, edi; imul eax, esi, 0x64; cdq ; idiv edi; ret ; xor eax, eax; ret 
percent_change_mul_first   PROVED equal for every non-trapping input

Reading this output

The formula comes from the bytes. The original is the clang -O1 sequence test, je, sub, imul $100, cdq, idiv, ret, plus the xor/ret zero path; the executor follows both paths of je.

Two rebuilds are proved, not tested. 100 * (after - before) / before and (after * 100 - before * 100) / before equal the original for every non-trapping input of the 2^64: in 32-bit wrap-around arithmetic, multiplication distributes and commutes, so all three compute the same bits.

Two are refuted with concrete inputs. Dividing first loses the remainder before multiplying (the solver found a case where the original gives 0 and the rebuild 100). The wide rebuild computes in 64 bits and so never wraps: at before = 42240, after = -2051050250 the original returns 24838 and the rebuild -4855806.

The trap is part of the contract. Z3 also finds an input where the original's idiv traps (before = -1, after = 536870911: the product wraps to INT_MIN, and INT_MIN / -1 does not fit), the same case the lesson's model reports. A rebuild must trap there too, or the difference must be documented.

Solutions

SolutionP1 · Two are perfect, two are not

The switch and the table rebuilds get none wrong. The thresholds rebuild gets 2,147,483,538 wrong: every score from 110 up to INT_MAX, where it returns 4 and the original returns 0. The case 10 rebuild gets exactly 10 wrong, the scores 100 to 109, where it returns 3 instead of 4.

SolutionB1 · A proof about the wrong program

They proved that the rebuild matches the pseudocode in mathematical integers, which is a different statement from "the rebuild matches the binary".

  • The model is not the program. Pseudocode is a decompiler's hypothesis; if it invented a wider type or dropped a guard (as the wide rebuild did), the hand model has the same error, and the proof certifies it.
  • Unbounded integers remove overflow. In mathematical integers (a - b) * 100 / b never wraps, so the 64-bit rebuild and the 32-bit original look identical. The very inputs where they differ (overflow) are excluded by the model.
  • Traps disappear. Unbounded division has no INT_MIN / -1 case.

A meaningful proof models the original from its instructions with fixed-width bit-vectors and explicit trap conditions, as the second block does, or uses a tool that lifts machine code (angr, Triton).

Industry practice
What's current (2024–2026)
  • Equivalence checking tools: SMT solvers (Z3, cvc5, Bitwuzla) for bit-precise reasoning; symbolic executors such as angr, KLEE and Triton lift real machine code instead of a hand model; Alive2 checks LLVM optimizations; CBMC does bounded model checking of C (the "Ramos and Engler" style of checking two functions).
  • Differential testing at scale: libFuzzer and AFL++ run the original and the rebuild side by side; Csmith-style generators keep inputs inside defined behaviour.
  • Decompilation research (2024-2026) shows rebuilt code that passes benchmark tests but diverges on fuzzed inputs; enumeration where the domain is small and proofs where it is not close that gap.
  • On your laptop: the 2^32 sweep takes under a minute on a modern CPU (faster on the ROG than on this 2-core runner); Z3 proofs of small functions take seconds. Neither needs the GPU.

Sources: Z3, angr, KLEE, Alive2, CBMC.

Operational Rule

Write the rebuild from the listing and name the record it came from. Run it against the original over a grid that wraps every intermediate and crosses every compare constant. Recompile it with the original flags, mask the relocation fields, compare the records, and read the constants they point at. Record each claim with its evidence id, and let an unverified claim stay unknown.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designDesign the second leg of a rebuild proof: build every candidate under the compiler and flags that produced the original, then compare it with the original function. Eight candidates are on the table, among them a pair of percent_change rebuilds whose source lines are written differently, a grade candidate whose 46 code bytes and relocation shape match the original but whose case 10 returns 3, and candidates whose relocation addend differs from the original. Say what the compare does at each step, which candidate each step stops, and what a pass means.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Three steps in order: mask every relocation field by zeroing its bytes on both sides and compare the code; compare the relocation records by offset, type and target section, not by addend, because the original says .rodata+0x10 and every candidate says .rodata-0x4 and that is a different table position, not a different function; then read the bytes each relocation points at, here five 4-byte words, and compare them. The wrong-constant candidate passes the first two steps and fails only the third, 1, 2, 3, 4, 4 against 1, 2, 3, 4, 3. A pass proves that this compiler with these flags produced the same code and the same referenced data from the candidate; it does not prove that the candidate is the original source text, since the two percent_change rebuilds with different text compile to identical 16 bytes.

Where each candidate stops.

Candidate Size Masked bytes Records Table Status
percent_change_mul_first 16 and 16 equal none none pass
percent_change_split 16 and 16 equal none none pass
percent_change_wide 16 and 26 size differs none none fail
percent_change_div_first 16 and 18 size differs none none fail
grade_switch 46 and 46 equal same shape equal pass
grade_table 46 and 46 equal same shape equal pass
grade_thresholds 46 and 39 size differs 1 against 0 none fail
grade_case10_wrong 46 and 46 equal same shape differ fail

Size is a diagnostic and never an acceptance: a recorded reconstruction project reports a candidate with the right length and hundreds of differing bytes.

Why mask when the field is already zero.

In a RELA object the addend lives in the record and the four field bytes are zero on both sides, so a plain compare would pass while the two relocations name different places. Masking anyway keeps one method for REL objects and for Mach-O, where the field carries the addend. The addends differ because the original object holds another table in .rodata before the switch table and the candidate object does not.

Why read the constants.

This step exists because of a documented bug in another reconstruction project: a comparison replayed the target address into the relocation field, compared instruction bytes, and never checked the data at that address, so a source literal of 0.0 appeared exact against a target literal of 128.0 until 1,548 floating-point references were audited. The wrong-constant candidate is this fixture's version of that defect, and the table read is the audit. The count of five comes from the listing: a compare against 4 with an unsigned jump admits indexes 0 to 4, and the load reads 4 bytes per index.

What the tool's own compare can see.

The comparison tool line-diffs provider text on eight dimensions, and its assembly dimension carries two fixed limitations: exact provider text is compared without address or generated-name normalization, and assembly is opaque provider text with relocation normalization unavailable. An unchanged assembly dimension means equal text from one engine, a changed one means different text, and neither is a statement about bytes. Two copies of the same code at different addresses diff as changed. The byte-level proof is the part the tool leaves to you.

Plausible wrong answers.

  • "Equal size means equal function." Size is a diagnostic; a candidate with the right length can differ in hundreds of bytes.
  • "A byte match recovers the source." Different source text can compile to identical bytes; the match is a statement about one compiler and one set of flags.
  • "The comparison tool said unchanged, so the bytes match." It compared decompiler text with addresses inside and says so in its own limitations.

Follow-ups an interviewer may ask.

  • (level 3) Why is the addend left out when the two relocation records are matched? Expected: the addend encodes where the table sits in that object's .rodata, which depends on what else the object holds, not on what the function does.
  • (level 3) What does a changed assembly dimension in the comparison tool tell you about the two functions' bytes? Expected: nothing; it is a text diff with addresses inside, and a relocatable object against its linked image diffs as changed.
  • (level 4) Two candidates with different source text pass every byte check. What have you proved? Expected: that this compiler folded both to the same code and data, not that either is the original text; signed overflow being undefined lets the compiler merge the two multiplies.
  • (level 4) A candidate passes bytes and constants. Is behaviour settled? Expected: on the same architecture yes, since code and referenced data are equal; the trap cell still depends on the host that runs the grid, so the proof names it.

Where it is taught. The rebuild lesson builds the masking, the record compare and the table read, the proof harness section records the eight candidates, and the comparison section states the assembly limitation.

Defend a designDesign the proof record for a rebuilt function that an obligation ledger will accept. The analysis tool's own verifier grades declared claims against comparison records, and its fixed limitation reads "Pass means every declared claim passed; it does not establish global implementation equivalence"; its readiness rule says that nothing weaker than pass adds up to pass. Your CI host has no C compiler. Say what your record contains, how its id is formed, which claims it can and cannot carry from the tool, and what status it gets on that host.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Mint one evidence record of your own, since no public tool emits it, and give it predicate_type: rea.reconstruction-proof, operation: verify_reconstruction_obligations, confidence: observed, authority: controlled-replay, and a normalized_result with passed, status and a list of claims, each behavioral or structural-function with its status and the ev_ ids of the function dossiers it rests on, repeated in evidence_links. The id is ev_ plus the SHA-256 of the record without its id over sorted-key compact JSON. Aggregation is fail-closed: fail wins, then unknown, and an empty claim list is unknown. The tool's verifier can only grade a structural-function claim as same provider text on one dimension, so behaviour and bytes come from your own two legs; on a host without a compiler the behavioural claims are unknown, and the record says unknown even when both byte claims pass.

Why the tool's pass is not enough.

A structural-function claim names one of nine dimensions of a compare_functions record, and the verifier computes its status in a fixed order: any limitation makes it unknown, an observed changed makes it fail, an observed unknown or an open residual unknown makes it unknown, otherwise pass. The recorded run sent four claims and got two passes and two failures. The total claims failed although both builds came from one source line, because -O2 unrolled the loop into 62 instructions where -O1 had 13; different text does not mean different behaviour. The reverse holds too: a rebuild with a wrong constant in a lookup table prints the same assembly text, so a text claim can pass on a wrong function. Nothing in the tool runs a function or compiles one.

The two legs you run.

Leg one compiles the original and the candidate into one program under different names, runs a grid with one class per hazard, and records every cell, including a trap. Leg two recompiles the candidate with the original flags, masks the relocation fields, compares the relocation records by shape, and reads the constants they point at. Each leg produces one claim per function, and each claim links the dossier records of the function it covers. The behavioural claim without a compiler is unknown, not skipped and not passed.

Authority and id.

authority is controlled-replay, because the proof comes from a harness you ran and not from the object file alone; shipped-artifact would claim that the file by itself supports equality, which it does not. The id excludes nothing but itself: adding a claim or a run changes the content and the id, so a proof produced later on a host with a compiler is a new record, and both are kept. No public tool emits this record; the obligation ledger expects it, and you mint it.

Driving the verifier at all.

The tool's verifier is one of 65 MCP tools without a CLI command, so a stdio client sends initialize, the initialized notification and tools/call. Both dossiers and the comparison record must be in the same connection, because the verifier reads the connection's bundle, and a close clears the retained records; export the bundle before you close.

The readiness rule, copied.

A stage result of fail, unknown, unsupported, truncated or skipped never adds up to pass. That sentence is the aggregation function.

Plausible wrong answers.

  • "A pass from the verifier proves the rebuild equals the original." Its own limitation says otherwise; it compared decompiler text on one dimension.
  • "Mark the behavioural claims passed on CI since the bytes matched." Nothing weaker than pass adds up to pass; a missing run is unknown.
  • "Keep the same id after adding the run results." The id is a content hash; a changed record is a new record.

Follow-ups an interviewer may ask.

  • (level 3) Why is the authority controlled-replay and not shipped-artifact? Expected: the fact came from a run and a recompile you controlled; the file alone cannot show that two functions are equal.
  • (level 4) The verifier passed both percent_change claims while the comparison's overall status was unknown. How? Expected: each claim reads its own dimension; the unknown dimension was references, and the residual unknown it opened names only overall and references.
  • (level 4) A compiler appears on the CI host next week. What happens to the record? Expected: the behavioural claims rerun and pass, the content changes, so a new id is minted, and the earlier unknown record is kept as history.

Where it is taught. The rebuild lesson mints the record and its fail-closed aggregate, the verification section shows the four graded claims and the readiness rule, and the proof harness section runs the two legs.

Estimate itDesign the input grid that runs an original and a rebuild of percent_change(int before, int after) and grade(int score) side by side, so that every hazard the listing shows has at least one cell. Estimate how many cells you need and in which classes, and how many cells a rebuild that kept the decompiler's long will fail.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Read the hazards off the listing: a zero guard from TEST EDI, EDI, truncation toward zero for negative operands, multiply-before-divide order for rounding, a 32-bit wrap from IMUL EAX, a divide trap when the wrapped product is INT_MIN and the divisor is -1, and for grade both sides of every band edge plus scores beyond the switch. Ten before values crossed with seven after values give 70 cells, 22 scores add the rest, 92 in all: 32 overflow, 17 negative, 14 boundary, 12 plain, 7 zero guard, 5 negative truncation, 2 beyond the switch, 2 rounding, 1 trap. The long rebuild fails the overflow cells with |before| > 1, 26 of them, and a threshold rebuild of grade fails the two cells beyond the switch, so the plausible pair fails 28 of 92 while all ten naive cases pass.

One class per hazard.

Differential testing needs two comparable systems fed mechanically generated cases, and the hard part is evaluating the result. Here the original is the oracle, so the only question is where the two can disagree, and each class answers one such question. The zero guard cells take the early return. Negative cells check that -9 / 10 is 0 and -10 / 10 is -1. Rounding cells check that (105 - 100) * 100 / 100 is 5 and not 0. Overflow cells make (after - before) * 100 exceed 32 bits. The one trap cell makes the wrapped product equal INT_MIN with before equal to -1: the difference is 536870912, which wraps to -2147483648, and the divisor is -1.

Why overflow is in scope.

Signed overflow is undefined in C, and a program generator that avoids undefined behaviour does so because an oracle disagreement there is noise. This oracle is a compiled object with one fixed behaviour, so the overflow cells are in scope; the lesson is to know which cells rest on the standard and which on the compiled bytes. The listing settles it: the multiply keeps the low 32 bits, and the rebuild must too.

The host is part of the result.

On x86-64 the trap cell raises the divide error exception, because the quotient does not fit in 32 bits, and the driver turns SIGFPE into the value trap. On AArch64 sdiv has no trap and returns -2147483648. The recorded run on an arm64 host shows that value with match: true, and a run of the same grid on x86-64 records the string trap. The report names the architecture beside every row, and a proof without the host name is incomplete.

Model and run stay apart.

A Python model of the listing, with a 32-bit wrap and a C-style division, predicts each cell; the run observes it. Zero disagreements means the model and the binary agree on every cell. The model is derived evidence and the run is observed evidence, and the report keeps them in separate fields rather than rounding one into the other.

Plausible wrong answers.

  • "Ten hand-written tests cover it." They passed on both wrong rebuilds; none crossed the width or the switch bound.
  • "Fuzz it instead of a grid." Random inputs find divergence but do not name the hazard; a class per instruction tells you what a failure means and what a pass covers.
  • "Skip the divide-by-minus-one cell; nobody does that." It is the one cell whose result depends on the architecture, and the report must name the host.

Follow-ups an interviewer may ask.

  • (level 3) Why include cells whose behaviour is undefined in C? Expected: the oracle is a compiled object with one behaviour, and the listing shows the width, so the rebuild is held to the bytes and not to the standard.
  • (level 3) Of the 32 overflow cells, how many does the long rebuild pass, and why? Expected: six, those with before of 1 or -1, because the 64-bit quotient truncates back to the wrapped value by accident.
  • (level 4) The grid passes on an arm64 host. What stays unproven for x86-64? Expected: the trap cell, whose original result differs by architecture; rerun on x86-64 or mark it with the host.
  • (level 4) Extend the grid to total(const int *values, int count). Which classes appear? Expected: count 0, a negative count, one element, and sums that wrap at 32 bits, each with the listing instruction that motivates it.

Where it is taught. The rebuild lesson builds the grid and the driver, and the proof harness section records the 92 cells, the 28 mismatches and the trap row on an arm64 host.
