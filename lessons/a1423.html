The idea in one line

OpenTelemetry's GenAI SIG (launched April 2024) defines the standard schema for agent telemetry. Span names, attributes, and content-capture rules converge across vendors so agent traces mean the same thing in Datadog, Grafana, Jaeger, and Honeycomb.

The problem

In plain words first

When an agent misbehaves in production you need a record of what it did: which model it called, which tools it ran, how long each step took and what it cost. Tracing systems record that as spans: timed, named steps arranged in a tree, where a child span (a tool call) sits inside its parent (the agent run), and all the spans of one request share a trace ID. OpenTelemetry (OTel) is the open standard for traces, and its GenAI semantic conventions fix the names: what to call an agent span, which attributes say which model and provider were used, and a rule that prompts and replies are not recorded unless you opt in, because they often hold customer data. This lesson runs the real OpenTelemetry instrumentation for the OpenAI client against a local model, traces a whole agent run, and checks the spans against the conventions.

Every vendor invents their own span names. Ops teams end up building per-framework dashboards. OpenTelemetry's GenAI SIG fixes this by defining one standard the whole ecosystem targets.

Idea 1 · Span categories

  1. Model / client spans. Cover raw LLM calls. Emitted by provider SDKs (Anthropic, OpenAI, Bedrock) and framework model adapters.
  2. Agent spans. create_agent (when the agent is constructed) and invoke_agent (when it runs).
  3. Tool spans. One per tool invocation, named execute_tool {gen_ai.tool.name} (kind INTERNAL); connected to the agent span by parent-child relation.

Idea 2 · Agent span naming

  • Span name: invoke_agent {gen_ai.agent.name} if named; fallback to invoke_agent.
  • Span kind:
  • CLIENT — for remote agent services (for example AWS Bedrock Agents; the OpenAI Assistants API was the usual second example until it shut down on 26 August 2026).
  • INTERNAL — for in-process agent frameworks (LangChain, CrewAI, local ReAct).

Idea 3 · Key attributes

  • gen_ai.provider.name — anthropic, openai, aws.bedrock, google.vertex.
  • gen_ai.request.model — the model ID.
  • gen_ai.response.model — the resolved model (may differ from request due to routing).
  • gen_ai.agent.name — agent identifier.
  • gen_ai.operation.name — well-known values include chat, text_completion, embeddings, create_agent, invoke_agent, invoke_workflow and execute_tool; when one applies it must be used.
  • gen_ai.data_source.id — for RAG: which corpus or store was consulted.

Technology-specific conventions exist for Anthropic, Azure AI Inference, AWS Bedrock, OpenAI.

Idea 4 · Content capture

The default rule: instrumentations SHOULD NOT capture inputs/outputs by default. Capture is opt-in via:

  • gen_ai.system_instructions
  • gen_ai.input.messages
  • gen_ai.output.messages

Recommended production pattern: store content externally (S3, your log store), record references on spans (pointer IDs, not prose), using the gen_ai.input.messages_ref and gen_ai.output.messages_ref attributes. This is the Lesson 14.27 content-poisoning defense wired into observability.

Idea 5 · Stability

The GenAI conventions are still at Development status. In November 2026 they moved out of the main semantic-conventions repository into their own (open-telemetry/semantic-conventions-genai, first release v0.1.0), with several renames. Instrumentations that predate the newer attribute names keep the old ones unless you opt in with:

OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental

Datadog LLM Observability natively accepts spans that follow the GenAI semantic conventions 1.37 or later. Other backends (Grafana, Honeycomb, Jaeger) support the raw attributes.

Idea 6 · Where this pattern goes wrong

  • Capturing full prompts in spans. PII, secrets, customer data in traces that ops can read. Store externally.
  • No gen_ai.provider.name. Multi-provider dashboards break when attribution is missing.
  • Spans without parent links. Orphaned tool spans. Always propagate context.
  • Not setting stability opt-in. Your attributes may get renamed on backend upgrade.

The same idea as a formula

A trace is a tree. Each span s has a parent p(s) (or none, for the root), a start and an end, and all spans of one request share one trace ID. Two simple properties make a trace useful:

  • Connected: every model and tool span inside an agent run has the agent span as an ancestor. A span whose parent link was lost starts a new trace, and the agent run looks as if it never called the tool.
  • Self-time adds up: a parent's duration is its own work plus its children's, d(s)=self(s)+∑c:p(c)=s​d(c) (for children that run one after another), which is how a trace view tells you where the time went.

Content exposure. If a fraction f of prompts contain personal data and traces are kept for T days with R requests a day, inline capture puts about f⋅R⋅T sensitive records in a store that many engineers can read; external storage with references keeps the same count but moves it behind its own access control and retention.

Worked example
One agent run, as spans
  • The user asks "Where is my order A-1001?". The agent run is invoke_agent support_bot (INTERNAL: it runs in our process).
  • Inside it: chat qwen2.5-0.5b-instruct (CLIENT: a call out to a model server) returns a tool call; execute_tool get_order_status (INTERNAL) runs it; a second chat writes the answer.
  • That is 4 spans in 1 trace. Move the tool into a thread pool without passing the trace context, and it is still 4 spans, but in 2 traces: the tool span has no parent and the agent's trace shows two model calls and no tool call.
  • With 2% of 50,000 daily requests holding an email address and 30 days of retention, inline capture keeps about 0.02×50,000×30=30,000 messages with personal data in the trace store.
Check your mental model
  • ✗ "Tracing an LLM call records the prompt."
    ✓ By default, no: content is opt-in. You get model, provider, tokens and finish reason.
  • ✗ "The instrumentation knows which provider served the request."
    ✓ It knows which client was used. Our Qwen server was recorded as openai.
  • ✗ "If spans are emitted, the tree is right."
    ✓ Context must reach every thread and task, or child spans start new traces.
  • ✗ "A misconfigured upload hook fails loudly."
    ✓ Here it fell back to a no-op with only a traceback on stderr.
Predict before you run

The same chat call, with a customer's email address in the prompt, is traced five ways: with nothing set, with the latest conventions, with content capture on spans, with an upload hook, and with an upload hook whose folder does not exist. In which configurations will the email address appear in the span attributes, and in which will you find it somewhere else? (Solution P1.)

The real openai client, instrumented by opentelemetry-instrumentation-openai-v2 (2.4b0, with opentelemetry-util-genai 1.1b0; the newer 1.3b0 breaks its import), sends one request per configuration, each in a fresh process so the environment variables take effect. # Real OpenTelemetry GenAI instrumentation (opentelemetry-instrumentation-openai-v2 2.4b0) on a local model:
# Qwen2.5-0.5B-Instruct behind a small OpenAI-compatible server, the same as lessons 14.15 and 14.16.
# One chat call with a tool and a customer's email in the prompt, traced under four configurations.
import json, os, pathlib, subprocess, sys, tempfile, textwrap
work = pathlib.Path(tempfile.mkdtemp())
SERVER = r'''# qwen_server.py: Qwen2.5-0.5B-Instruct behind a minimal OpenAI-compatible /v1/chat/completions endpoint,
# so frameworks that speak that API can run on a local model. Greedy decoding; tool calls supported through
# the model's chat template (<tool_call> blocks become OpenAI tool_calls); tool_choice="required" is honoured by
# starting the reply inside a <tool_call> block. Stops by itself after LIFETIME s.
import json, os, re, sys, time, uuid, torch
from http.server import BaseHTTPRequestHandler, HTTPServer
os.environ.setdefault("HF_HUB_OFFLINE", "1")
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
LOG = os.environ.get("QWEN_LOG")
def text_of(content):
    return content if isinstance(content, str) else " ".join(p.get("text", "") for p in content or [])
def to_template(messages):
    out = []
    for m in messages:
        msg = {"role": m["role"], "content": text_of(m.get("content") or "")}
        if m.get("tool_calls"):
            msg["tool_calls"] = [{"type": "function", "function": {"name": c["function"]["name"],
                                  "arguments": json.loads(c["function"]["arguments"] or "{}")}} for c in m["tool_calls"]]
        out.append(msg)
    return out
def complete(req):
    tools = req.get("tools") or None
    ids = tok.apply_chat_template(to_template(req["messages"]), tools=tools, add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    forced = '<tool_call>\n{"name": "' if tools and req.get("tool_choice") == "required" else ""
    if forced:                                           # constrained start: the reply must be a tool call
        ids = torch.cat([ids, tok(forced, return_tensors="pt")["input_ids"]], dim=1)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=int(req.get("max_tokens") or req.get("max_completion_tokens") or 256),
                           do_sample=False)
    text = forced + tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
    calls = []
    for blob in re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", text, re.S) if tools else []:
        try:
            d = json.loads(blob)
            calls.append({"id": "call_" + uuid.uuid4().hex[:8], "type": "function",
                          "function": {"name": d["name"], "arguments": json.dumps(d.get("arguments", {}))}})
        except (json.JSONDecodeError, KeyError):
            pass
    content = re.sub(r"<tool_call>.*?</tool_call>", "", text, flags=re.S).strip() if calls else text
    if LOG:
        with open(LOG, "a") as f:
            f.write(json.dumps({"prompt_tokens": ids.shape[1], "tools": len(tools or []), "tool_calls": [c["function"] for c in calls],
                                "content": content[:200]}) + "\n")
    msg = {"role": "assistant", "content": content or None}
    if calls:
        msg["tool_calls"] = calls
    return {"id": "chatcmpl-" + uuid.uuid4().hex[:8], "object": "chat.completion", "created": int(time.time()),
            "model": req.get("model", M), "choices": [{"index": 0, "message": msg,
            "finish_reason": "tool_calls" if calls else "stop"}],
            "usage": {"prompt_tokens": ids.shape[1], "completion_tokens": out.shape[1] - ids.shape[1],
                      "total_tokens": out.shape[1]}}
class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass
    def do_GET(self):
        body = json.dumps({"object": "list", "data": [{"id": M, "object": "model"}]}).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json"); self.end_headers(); self.wfile.write(body)
    def do_POST(self):
        req = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        body = json.dumps(complete(req)).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body))); self.end_headers(); self.wfile.write(body)
port, lifetime = int(sys.argv[1]), float(sys.argv[2])
srv = HTTPServer(("127.0.0.1", port), Handler); srv.timeout = 0.5
print("ready", flush=True)
deadline = time.time() + lifetime
while time.time() < deadline:                            # bounded: one request at a time until the deadline
    srv.handle_request()
'''
(work / "qwen_server.py").write_text(SERVER)
PORT = 8600 + os.getpid() % 100
server = subprocess.Popen([sys.executable, str(work / "qwen_server.py"), str(PORT), "900"],
                          stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
assert server.stdout.readline().strip() == "ready"

CLIENT = textwrap.dedent('''
    import json, sys
    from opentelemetry import trace
    from opentelemetry.sdk.trace import TracerProvider
    from opentelemetry.sdk.trace.export import SimpleSpanProcessor
    from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter
    from opentelemetry.instrumentation.openai_v2 import OpenAIInstrumentor
    exporter = InMemorySpanExporter()
    provider = TracerProvider(); provider.add_span_processor(SimpleSpanProcessor(exporter))
    trace.set_tracer_provider(provider)
    from opentelemetry.util.genai.completion_hook import load_completion_hook
    hook = load_completion_hook()                   # "upload" hook if configured, otherwise a no-op
    OpenAIInstrumentor().instrument(completion_hook=hook)   # patches the openai client; reads the env vars now
    import importlib
    OpenAI = importlib.import_module("openai").OpenAI   # the real openai client, pointed at the local server
    client = OpenAI(base_url=sys.argv[1], api_key="local")
    tools = [{"type": "function", "function": {"name": "get_order_status",
              "description": "Return the shipping status for an order ID such as A-1001.",
              "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}},
                             "required": ["order_id"]}}}]
    client.chat.completions.create(model="qwen2.5-0.5b-instruct", temperature=0, tools=tools, messages=[
        {"role": "system", "content": "You are a support agent for an online shop."},
        {"role": "user", "content": "Hi, I am dana.k@example.com. Where is my order A-1001?"}])
    getattr(getattr(hook, "_wrapped", hook), "shutdown", lambda: None)()   # wait for pending uploads
    out = [{"name": s.name, "kind": s.kind.name, "attrs": {k: v for k, v in s.attributes.items()},
            "events": [e.name for e in s.events]} for s in exporter.get_finished_spans()]
    print(json.dumps(out, default=str))
''')
(work / "client.py").write_text(CLIENT)
URL = f"http://127.0.0.1:{PORT}/v1"
OPT = {"OTEL_SEMCONV_STABILITY_OPT_IN": "gen_ai_latest_experimental"}
CONFIGS = {
    "A default (nothing set)": {},
    "B latest conventions, content off": dict(OPT),
    "C latest conventions + content on spans": dict(OPT, OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT="span_only"),
    "D latest conventions + upload hook": dict(OPT, OTEL_INSTRUMENTATION_GENAI_COMPLETION_HOOK="upload",
                                               OTEL_INSTRUMENTATION_GENAI_UPLOAD_BASE_PATH=f"file://{work}/content"),
    "E as D, but the content folder does not exist": dict(OPT, OTEL_INSTRUMENTATION_GENAI_COMPLETION_HOOK="upload",
                                               OTEL_INSTRUMENTATION_GENAI_UPLOAD_BASE_PATH=f"file://{work}/missing"),
}
(work / "content").mkdir()                        # the upload hook writes here (a stand-in for s3:// or gs://)
EMAIL = "dana.k@example.com"
results = {}
for label, extra in CONFIGS.items():
    env = {k: v for k, v in os.environ.items() if not k.startswith("OTEL_")}
    env.update(extra)
    run = subprocess.run([sys.executable, str(work / "client.py"), URL], env=env, capture_output=True, text=True)
    if run.returncode: print(run.stderr[-2000:])
    hook_failed = "upload is not working" in run.stderr
    spans = json.loads(run.stdout.strip().splitlines()[-1])
    results[label] = spans
    s = spans[0]
    print(f"{label}\n  span name: {s['name']!r}   kind: {s['kind']}   spans: {len(spans)}")
    print(f"  provider.name = {s['attrs'].get('gen_ai.provider.name')!r}   finish = {s['attrs'].get('gen_ai.response.finish_reasons')}")
    print("  attributes (gen_ai.*):", ", ".join(sorted(k.replace('gen_ai.', '') for k in s["attrs"])))
    leaked = [k for k, v in s["attrs"].items() if EMAIL in json.dumps(v, default=str)]

    for k, v in s["attrs"].items():
        if k.endswith("_ref"):
            print(f"  {k} = .../{pathlib.Path(str(v)).parent.name}/{pathlib.Path(str(v)).name}")
    if hook_failed:
        print("  upload hook failed its start-up write test; the instrumentation fell back to a no-op hook"
              f" (exit code {run.returncode}, a traceback on stderr only)")
    print()
files = sorted(p for p in (work / "content").rglob("*") if p.is_file() and not p.name.startswith("."))
print(f"external store after D: {len(files)} files")
for p in files:
    body = p.read_text()

Reading this output

The defaults are safe. With nothing set (A) and with the latest conventions but no content capture (B), the one span is chat qwen2.5-0.5b-instruct, kind CLIENT, with the operation, model, provider, finish reason and token counts, and no message text. That is enough for latency, cost and error dashboards, and the customer's email address is nowhere in the trace.

Content capture puts personal data in the trace store. In C the full conversation is on the span as gen_ai.input.messages, email address included. Anyone who can read traces can read it, and it is kept as long as traces are.

The upload hook keeps content out of spans but not out of storage. In D the span carries only gen_ai.input.messages_ref and gen_ai.output.messages_ref, paths into a separate store; the inputs file there still contains the email. The point is separate access control and retention, not removing the data.

Two things the trace gets wrong without telling you. The provider is recorded as openai because the instrumentation sees the OpenAI client, not the Qwen model behind it; a cost dashboard keyed on provider would bill this traffic to OpenAI. And in E, the upload hook could not write to its folder, so the instrumentation quietly replaced it with a no-op: no references, no content, exit code 0, and only a traceback on stderr. A third, milder drift: the spec names the content switch OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT, while this Python instrumentation reads OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT.

# The same server, now with a whole agent run traced in this process: an invoke_agent span (by hand, with
# opentelemetry-util-genai's TelemetryHandler), chat spans (automatic, from the instrumentation) and
# execute_tool spans (by hand). The tool runs three ways: inline, in a thread pool, and in a thread pool
# with the trace context copied. Then a small checker compares span names, kinds, operation names,
# attribute names and parent links with the GenAI conventions. Continues from the block above.
import contextlib, contextvars, importlib, io, json
from concurrent.futures import ThreadPoolExecutor
for k in [k for k in os.environ if k.startswith("OTEL_")]:
    del os.environ[k]
os.environ["OTEL_SEMCONV_STABILITY_OPT_IN"] = "gen_ai_latest_experimental"
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter
from opentelemetry.instrumentation.openai_v2 import OpenAIInstrumentor
from opentelemetry.util.genai.handler import TelemetryHandler
exporter = InMemorySpanExporter()
provider = TracerProvider(); provider.add_span_processor(SimpleSpanProcessor(exporter))
trace.set_tracer_provider(provider)
OpenAIInstrumentor().instrument()
handler = TelemetryHandler()
OpenAI = importlib.import_module("openai").OpenAI      # the real openai client, pointed at the local server
client = OpenAI(base_url=URL, api_key="local")
MODEL = "qwen2.5-0.5b-instruct"
ORDERS = {"A-1001": "shipped on 20 Nov", "A-1002": "processing"}
TOOLS = [{"type": "function", "function": {"name": "get_order_status",
          "description": "Return the shipping status for an order ID such as A-1001.",
          "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}}]

def get_order_status(order_id):
    return f"{order_id}: {ORDERS.get(order_id, 'not found')}"

def traced_tool(call):
    with handler.tool(call.function.name, tool_call_id=call.id, tool_type="function"):
        return get_order_status(**json.loads(call.function.arguments))

def run_agent(question, mode):
    pool = ThreadPoolExecutor(1)
    messages = [{"role": "system", "content": "You are a support agent. Use the tool to look up orders."},
                {"role": "user", "content": question}]
    with handler.invoke_local_agent(agent_name="support_bot", request_model=MODEL):
        for turn in range(3):
            reply = client.chat.completions.create(model=MODEL, temperature=0, messages=messages, tools=TOOLS,
                                                   tool_choice="required" if turn == 0 else "auto").choices[0].message
            if not reply.tool_calls:
                break
            messages.append({"role": "assistant", "content": reply.content or "",
                             "tool_calls": [c.model_dump() for c in reply.tool_calls]})
            for call in reply.tool_calls:
                if mode == "inline":
                    result = traced_tool(call)
                elif mode == "thread pool":
                    result = pool.submit(traced_tool, call).result()
                else:                                   # copy this thread's context into the worker
                    result = pool.submit(contextvars.copy_context().run, traced_tool, call).result()
                messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return reply.content

def tree(spans):
    by_id = {s.context.span_id: s for s in spans}
    traces = {}
    for s in spans:
        traces.setdefault(s.context.trace_id, []).append(s)
    lines = []
    def walk(s, depth):
        lines.append(f"    {'  ' * depth}{s.name}  [{s.kind.name}]")
        for c in sorted((c for c in spans if c.parent and c.parent.span_id == s.context.span_id), key=lambda c: c.start_time):
            walk(c, depth + 1)
    for tid, group in traces.items():
        lines.append(f"  trace {tid:032x}"[:22] + "...")
        for root in (s for s in group if not s.parent or s.parent.span_id not in by_id):
            walk(root, 1)
    return lines

Reading this output

Run inline, the tree is what the conventions describe. One trace: invoke_agent support_bot (INTERNAL) with a chat span that asks for the tool, an execute_tool get_order_status span, and a second chat span that writes the answer. The checker finds no problems.

A thread pool silently splits the trace. Same 4 spans, same correct answer, but the tool span is in a trace of its own: OpenTelemetry keeps the current span in a context variable, and a pool's worker thread does not inherit it. In a trace viewer the agent made two model calls and never ran a tool. Copying the context into the worker (contextvars.copy_context().run) puts it back.

The lesson's own tracer does not follow the conventions it teaches. Its model spans are named chat instead of chat {model} and marked INTERNAL instead of CLIENT, its create_agent span is INTERNAL instead of CLIENT, its tool span uses the operation tool_call instead of execute_tool, and its content references use invented .reference_id attributes instead of _ref. It also never emits a tool span at all, because its scripted model never asks for the tool. A checker like this one, run in CI, catches all of these before a dashboard does.

"""Stdlib span emitter matching OpenTelemetry GenAI semantic conventions.

Emits invoke_agent INTERNAL spans, per-tool spans, chat spans for LLM calls.
Content capture is opt-in: prompts go to an external store, spans carry IDs.
"""

from __future__ import annotations

import time
from dataclasses import dataclass, field
from typing import Any


@dataclass
class Span:
    name: str
    kind: str = "INTERNAL"
    attributes: dict[str, Any] = field(default_factory=dict)
    children: list["Span"] = field(default_factory=list)
    start_ns: int = 0
    end_ns: int = 0

    @property
    def duration_ms(self) -> float:
        return (self.end_ns - self.start_ns) / 1_000_000


class ExternalContentStore:
    def __init__(self) -> None:
        self._store: dict[str, str] = {}
        self._counter = 0

    def put(self, content: str) -> str:
        self._counter += 1
        cid = f"content_{self._counter:03d}"
        self._store[cid] = content
        return cid

    def get(self, cid: str) -> str:
        return self._store.get(cid, "")

    def items(self) -> list[tuple[str, str]]:
        return sorted(self._store.items())


class Tracer:
    def __init__(self, capture_inline: bool = False,
                 content_store: ExternalContentStore | None = None) -> None:
        self.root = Span(name="__root__")
        self.stack: list[Span] = [self.root]
        self.capture_inline = capture_inline
        self.content_store = content_store or ExternalContentStore()

    def start_span(self, name: str, kind: str = "INTERNAL",
                   attributes: dict[str, Any] | None = None) -> Span:
        span = Span(name=name, kind=kind, attributes=dict(attributes or {}),
                    start_ns=time.perf_counter_ns())
        self.stack[-1].children.append(span)
        self.stack.append(span)
        return span

    def end_span(self) -> None:
        span = self.stack.pop()
        span.end_ns = time.perf_counter_ns()

    def add_content(self, span: Span, key: str, content: str) -> None:
        if self.capture_inline:
            span.attributes[key] = content[:200]
            return
        cid = self.content_store.put(content)
        span.attributes[f"{key}.reference_id"] = cid

Industry practice
What's current (2024–2026)
  • The spec: the GenAI semantic conventions now live in their own repository (open-telemetry/semantic-conventions-genai, v0.1.0 in November 2026), still at Development status, with breaking renames (for example the inference span type, token metrics and mistral as a provider name). Pin the instrumentation version and expect renames.
  • Instrumentation: OpenTelemetry's Python contrib packages (opentelemetry-instrumentation-openai-v2 and the shared opentelemetry-util-genai) emit chat spans, metrics and, on opt-in, content or content references; OpenLLMetry and OpenInference offer wider framework coverage. The OpenAI Agents SDK, Microsoft Agent Framework and others emit their own traces that map onto these names.
  • Backends: Datadog LLM Observability (conventions 1.37+), Langfuse, Arize Phoenix and Grafana accept OTLP GenAI spans; Jaeger or Grafana Tempo give you raw traces for free.
  • On your laptop: everything here runs on the CPU with an in-memory exporter. To see traces in a UI, run Jaeger's all-in-one container (a few hundred MB of RAM) and swap in the OTLP exporter.

Sources: GenAI semantic conventions repository, opentelemetry-python-contrib, Datadog: OpenTelemetry instrumentation for LLM Observability, OpenTelemetry concepts: traces.

Recap
What to keep from this lesson
  • Standard names (invoke_agent, chat {model}, execute_tool {tool}) make traces portable.
  • Content is off by default; in production, store it externally and record references.

Given an agent runtime, wire OTel GenAI semantic conventions.

Produce:

1. `invoke_agent` span per agent run. Kind CLIENT for remote agent services, INTERNAL for in-process. Name: `invoke_agent {gen_ai.agent.name}`.
2. `chat` span per LLM call with `gen_ai.operation.name=chat`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`.
3. `tool_call` span per tool invocation with `gen_ai.tool.name` and, when applicable, `gen_ai.data_source.id` (RAG corpus / memory store).
4. Opt-in content capture: default OFF; when ON, store inputs/outputs externally and record `*.reference_id` on spans.
5. Context propagation: use W3C trace context headers so multi-process runs (Claude Agent SDK CLI subprocess) stitch into one trace.

Hard rejects:

- Capturing full prompts/outputs inline by default. PII and secret leakage risk; also violates the spec.
- Missing `gen_ai.provider.name`. Multi-provider dashboards break.
- Orphan tool spans. Always set parent-child relation via active context.

Refusal rules:

- If the runtime cannot propagate context across process boundaries, refuse. Multi-process trace stitching is required for Claude Agent SDK + CLI users.
- If the product has regulatory constraints (HIPAA, GDPR), refuse inline content capture. External store with access control only.
- If the backend does not set `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental`, warn: attribute names may change on collector upgrade.

Solutions

SolutionP1 · Only with content capture on spans

Only C, content capture on spans, puts the email address in the span attributes (gen_ai.input.messages). A and B record no content at all. D records only references (gen_ai.input.messages_ref); the address is in the uploaded inputs file, which is exactly where it should be: behind separate access control and retention. E records neither, because the hook failed its start-up check and was replaced by a no-op, silently.

SolutionB1 · Orphaned tool spans

The tool spans lost their parent. A worker pool does not inherit OpenTelemetry's context, so each tool call started a new trace with no agent, no model and no request attached. Queries that join tool spans to their agent run or model (such as "tool errors by model") no longer find them, so errors appear to vanish.

Fix: capture the context when you submit work and restore it in the worker (contextvars.copy_context().run(...) in Python, or the context-aware executors and asyncio tasks, which copy context automatically). Guard: a test that runs one agent request and asserts that all spans share one trace ID and that every execute_tool and chat span has the invoke_agent span as an ancestor, plus an alert on root spans whose operation is execute_tool.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Weigh a trade-offYour trace backend can store the full prompt and completion on every model span. The support team wants it on, because they debug tickets from traces. The security team wants it off. What do you decide, and how do you still give support what they need?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Keep content capture off, which is the default the conventions recommend. Store prompts and completions in your own store, with access control and a retention period, and record a reference id on the span. Support follows the id from the trace to the content, and the trace backend never holds customer data.

What the default is.

By default a span carries timing and metrics, not prompts or completions. Content capture is opt-in through the stability opt-in variable and separate content variables. When it is on, the content lands in gen_ai.input.messages, gen_ai.output.messages and gen_ai.system_instructions, or in the content events on the span.

What goes wrong when it is on.

Prompts carry personal data, secrets and customer documents. Operators read traces, and the trace backend sets its own retention. The conventions lesson lists "capturing full prompts in spans" as the first way the pattern fails. A trace backend is also an attractive target, because it holds everything in one place.

The pattern that works.

Store the content outside the trace: in your log store or object store, under your own access control, audit log and retention. Put a reference id on the span. The lesson calls this the external-reference pattern, and it is also the defense against content poisoning, because the poisoned text never enters the telemetry store.

What support gets.

The same debugging path with one extra step: trace, span, reference id, content store. The store can redact known patterns on write and log every read. Most tickets do not need the content at all, because the span already shows the model, the tokens, the latency, the tool calls and the status.

What you give up.

A one-click view of the prompt inside the trace UI. That is the price, and it is small next to a trace backend full of customer data.

Plausible wrong answers.

  • "Turn it on, the trace backend is internal." Internal operators read traces, and the backend's retention is not your policy.
  • "Store a hash of the prompt on the span." A hash shows a repeat but gives support nothing to read. A reference id into a controlled store does both.
  • "Keep the content on the span and strip personal data with a regex." Patterns miss, and the span is still the wrong store with the wrong retention.

Follow-ups an interviewer may ask.

  • (level 2) Which spans may carry raw content when capture is on? Expected: none in production. Keep one rule, references only, so nobody has to decide per span.
  • (level 3) A developer turns capture on in staging for a day. What is the risk? Expected: staging often replays production prompts, and the backend keeps them for its retention period. Use synthetic prompts or scrub before export.
  • (level 3) How do you keep the content store from becoming the same leak? Expected: access by role, an audit log of reads, a retention period, and redaction of known patterns before the write.

Where it is taught. The conventions lesson sets the opt-in rule and the pattern of storing content outside the span, and the OpenTelemetry GenAI lesson names the content events.

Read the codeA colleague opens a review that adds tracing to the agent. The branch emits this span for every model call. Level 3 of 4 · about 12 minutes to answer well.

Short answer. The span marks a model call as INTERNAL, has no parent, and uses an old attribute name for the input tokens. It omits the provider, the output tokens, the response model and the response id, and it writes the prompt text, with a card number in it, into the trace. Fix the kind and the parent link, use the current attribute names, add the missing attributes, and move the content out of the span.

The problems, in order of damage.

Line Problem Fix
parentSpanId: "" an orphan span; no backend can show which agent step made the call pass the parent context from the invoke_agent span
kind: INTERNAL a model call crosses a process boundary CLIENT
gen_ai.content.prompt prompt text with customer data in a store that operators read capture off by default; store content outside and put a reference id on the span
gen_ai.usage.prompt_tokens the attribute was renamed; backends read gen_ai.usage.input_tokens use the current name and add gen_ai.usage.output_tokens
no gen_ai.provider.name cost and error dashboards cannot split by provider set it on every model span
no gen_ai.response.model with routing, the served model can differ from the requested alias record what the provider returned
no gen_ai.response.id no way to match the span to the provider's own log record the response id

Why the content line is the one to fight over.

The conventions say instrumentations should not capture inputs and outputs by default. Capture is opt-in through an environment variable, and the production pattern stores content in your own log store and records a pointer on the span. A prompt with a card number in a trace backend is a data leak with a retention policy you did not choose.

Why the renamed attribute will come back.

The GenAI conventions are still marked as in development, and they have renamed attributes before. Pin the conventions version you emit, set the stability opt-in, and test the attribute names of emitted spans, or the next SDK upgrade reopens this review.

Plausible wrong answers.

  • "It has a trace id and a model name, so it is fine." A trace id alone does not link the span to its parent, and a model name without a provider cannot be attributed.
  • "Keep the prompt in the span, it is useful." Prompts carry personal data and secrets into a store that operators read. The default is off, and production stores content outside the span.
  • "The two token names are synonyms." Backends read the current name. The old one lands in an unknown attribute, and the token dashboard shows nothing.

Follow-ups an interviewer may ask.

  • (level 3) Why does the empty parent matter more than the wrong kind? Expected: with no parent the span is an orphan, the trace is no longer a tree, and you cannot see which step made the call.
  • (level 3) The team needs the prompt text to debug failures. What do you offer? Expected: store prompts in a separate store with access control and put a reference id on the span, which is the pattern the conventions recommend for production.
  • (level 4) How do you keep the old attribute name from returning after an upgrade? Expected: pin the conventions version, set the stability opt-in variable, and add a test that asserts the attribute names on emitted spans.

Debug a failureAfter a routine upgrade of the tracing SDK, the token usage panels show zero for every model, while request counts and latency panels look normal. Nothing else was deployed. Where do you look first?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Look at the attribute names on the spans the service emits now. The GenAI conventions are still marked as in development, and they have renamed attributes before: the input token count moved from gen_ai.usage.prompt_tokens to gen_ai.usage.input_tokens. If the SDK emits the new name and the dashboard queries the old one, every token panel reads zero while counts and latency keep working. Pin the conventions version you emit, and set the stability opt-in so that the names do not move under you.

Why only the token panels broke.

Request counts come from the number of spans, and latency comes from span start and end times. Neither depends on an attribute name. A token panel sums one attribute by its key. A renamed key makes the sum zero, and nothing errors.

Confirm it in one minute.

Pull one raw span from after the upgrade and one from before. Compare the attribute keys. The old key is gone, and the new one carries the numbers.

Two fixes, in order.

  1. Change the dashboard queries to the new key. During the transition, sum both keys so that old and new spans show.
  2. Stop the names from moving: pin the conventions version in the emitter, set OTEL_SEMCONV_STABILITY_OPT_IN, and check the names on every SDK upgrade.

Prevent the repeat.

The capstone's tests assert that the canonical attributes are present on emitted spans. Run them on every dependency upgrade. Add an alert for the shape of this incident: token sum at zero while the request count is above zero.

Plausible wrong answers.

  • "The models stopped reporting usage." The provider responses did not change. The span emitter did.
  • "The backend lost data during the upgrade." The latency panels prove the spans arrive. Only one attribute is missing from the query's point of view.
  • "Roll the SDK back and stay there." A pinned conventions version and a test let you upgrade on purpose instead of never.

Follow-ups an interviewer may ask.

  • (level 2) Why did the count and latency panels keep working? Expected: they use span counts and span timing, which do not depend on an attribute name.
  • (level 3) How do you catch the next rename before production? Expected: a test on emitted spans that asserts the canonical attribute names, run on every dependency upgrade.
  • (level 3) Should the dashboard read both the old and the new name? Expected: yes for a transition window, as a sum of both. Then remove the old one, so that a future regression stays visible.
  • (level 4) The backend maps the attributes into its own schema. Does that protect you? Expected: only when the mapping follows the same conventions version. A mapping built for the old name shows the same zero, so test the end-to-end path.

Where it is taught. The capstone traces lesson warns that the conventions renamed attributes and tells you to pin the version, and the conventions lesson gives the stability opt-in.

Explain the mechanismYou add tracing to an agent. In one run it calls a model API twice, runs two tools inside its own process and sends one request to a tool server on another machine. Which of these operations get a CLIENT span, which get an INTERNAL span, and why does anyone care?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. A call that leaves the process gets a CLIENT span: the two model API calls and the request to the remote tool server. The agent loop step and a tool that runs in your own process get INTERNAL spans. The kind tells a backend the direction of each call, so it can show which operations left the process and which did not.

The tree for this run.

invoke_agent            INTERNAL
 ├── chat               CLIENT
 ├── execute_tool       INTERNAL
 │    └── remote call   CLIENT
 ├── execute_tool       INTERNAL
 └── chat               CLIENT

Every span shares one trace id. Each child carries the id of its parent. That is what makes the run one tree instead of six loose records.

The rule.

CLIENT marks a call across a process boundary: a model provider, a tool server, a hosted agent service. INTERNAL marks the agent's own loop steps and any tool that runs in the same process. The conventions apply the same rule to the agent span itself: an agent that runs as a remote service is CLIENT from the caller, and an in-process agent framework is INTERNAL.

The attributes that go with each kind.

Span Attributes
model call gen_ai.operation.name, gen_ai.provider.name, gen_ai.request.model, gen_ai.response.model, gen_ai.usage.input_tokens, gen_ai.usage.output_tokens, gen_ai.response.id
tool call gen_ai.tool.name, gen_ai.tool.call.id
agent run gen_ai.agent.name, gen_ai.agent.id

Why it matters.

Backends draw a waterfall from the kinds and the parent links. A CLIENT span with no response id cannot be matched to the provider log. A tool span with no parent is an orphan, and you can no longer see which agent step caused the call.

Plausible wrong answers.

  • "Every tool call is a CLIENT span." A tool that runs in your process is INTERNAL. Only the call that leaves the process is CLIENT.
  • "The kind is decoration." Backends read the kind to show direction, and the conventions set it per span category.
  • "Start a new trace for each tool call, for isolation." Separate traces lose the parent link, so you cannot see which step caused the call.

Follow-ups an interviewer may ask.

  • (level 1) What joins the spans into one tree? Expected: one shared trace id, and a parent span id on every child.
  • (level 2) The agent calls a hosted agent service instead of a local one. What kind is that span? Expected: CLIENT, because the agent runs in another process.
  • (level 2) Which attribute lets a dashboard split cost by provider? Expected: gen_ai.provider.name, and multi-provider dashboards break when it is missing.
  • (level 3) A sub-agent runs inside the same process. Does it start a new trace? Expected: no. It is a child span under the parent agent span, so the whole run stays in one trace.

Where it is taught. The OpenTelemetry GenAI lesson draws the span hierarchy, and the conventions lesson names the span categories and their kinds.
