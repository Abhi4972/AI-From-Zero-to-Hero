Why this came about

Writing a tool's JSON description by hand next to its code meant the two drifted apart. Libraries began generating the description from the function itself, its name, docstring and type hints, the same idea web frameworks such as FastAPI used for APIs. One source of truth for each tool became the norm.

The problem: two descriptions of one function

In Lessons 3.1 and 3.2 every tool was written twice: once as a Python function, and once as a JSON definition for the model. Nothing keeps the two in step. A teammate renames a parameter in a refactor, tests that call the function directly still pass, and the model keeps sending the old name:

# Continues Lesson 3.2. A teammate "tidies up" the function; nobody touches the hand-written definition
def get_order_status_v2(order_number: str) -> str:       # renamed from order_id
    return get_order_status(order_number)

drifted = dict(TOOLS, get_order_status=(TOOLS["get_order_status"][0], get_order_status_v2))
print(Agent(system=SYSTEM, tools=drifted).run("Where is my order SK-1042?"))
What you should see
Sorry, I couldn't check that: TypeError: get_order_status_v2() got an unexpected keyword argument 'order_id'

The agent survives because Lesson 3.2's call_tool turns the exception into an error result, but every order lookup now fails. The fix is to have one source of truth: generate the definition from the function.

In plain words first
One description, written once

A tool has two descriptions that must agree: the Python function your code runs, and the JSON Schema the model reads. Writing both by hand means they drift apart. Instead, read the schema out of the function: its name, its docstring and its type hints already say what it is called, what it does and what arguments it takes. A decorator can do that and register the tool, so adding a tool is writing one well-described function.

Idea 1 · Read the definition out of the function

Python refresher
Python refresher: type hints and `inspect`

def f(order_id: str, limit: int = 5) carries everything a schema needs. inspect.signature(f).parameters lists the parameters in order, each with its default (inspect.Parameter.empty when there is none). typing.get_type_hints(f) maps each name to its type. inspect.getdoc(f) returns the docstring. typing.Literal["damaged", "wrong item"] is a type that allows only those values, and typing.get_args returns them.

import inspect, typing
from typing import Literal, get_type_hints

JSON_TYPES = {str: "string", int: "integer", float: "number", bool: "boolean"}

def schema_from(fn):
    """Build a tool definition from a function's signature, type hints and docstring."""
    hints = get_type_hints(fn)
    summary, _, rest = (inspect.getdoc(fn) or "").partition("\n\n")
    arg_docs = dict(re.findall(r"^\s*(\w+): (.+)$", rest.split("Args:", 1)[1], re.M)) if "Args:" in rest else {}
    props, required = {}, []
    for name, p in inspect.signature(fn).parameters.items():
        t = hints[name]
        if typing.get_origin(t) is Literal:                        # Literal["a", "b"] becomes an enum
            spec = {"type": "string", "enum": list(typing.get_args(t))}
        else:
            spec = {"type": JSON_TYPES[t]}
        if name in arg_docs:
            spec["description"] = arg_docs[name]
        props[name] = spec
        if p.default is inspect.Parameter.empty:                   # no default: the model must supply it
            required.append(name)
    return {"name": fn.__name__, "description": " ".join(summary.split()),
            "input_schema": {"type": "object", "properties": props, "required": required, "additionalProperties": False}}

def refund_example(order_id: str, reason: Literal["damaged", "wrong item", "changed mind"], note: str = "") -> str:
    """Refund an order in full to the original payment method.

    Args:
        order_id: The order ID, for example SK-1077
        reason: Why the customer wants the refund
        note: Anything the customer added, in their words
    """

print(json.dumps(schema_from(refund_example)["input_schema"], indent=None))

Idea 2 · A decorator that registers tools

Python refresher
Python refresher: decorators

A decorator is a function that takes a function and returns a function. @tool() above def f means f = tool()(f). So tool() runs first and returns register, and register(f) runs once, when Python reads the def, not when f is called. That is why a decorator can record every tool in a registry at import time. functools.wraps(fn) copies fn's name, docstring and signature onto the wrapper, so code that inspects the wrapper still sees the original.

import functools

REGISTRY = {}                                              # name -> {"definition", "fn", "risky"}

def tool(risky=False):
    """A decorator: @tool() registers a function as a tool; its definition is generated from the function itself."""
    def register(fn):
        @functools.wraps(fn)                               # keep fn's name and docstring on the wrapper
        def wrapper(**kwargs):
            return fn(**kwargs)
        REGISTRY[fn.__name__] = {"definition": schema_from(fn), "fn": wrapper, "risky": risky}
        return wrapper
    return register

list_orders, checked_status, checked_refund = find_orders, get_order_status, issue_refund   # Lesson 3.2's functions

@tool()
def find_orders() -> str:
    """List the logged-in customer's recent orders with their items. Use it when the customer describes an order without its ID."""
    return list_orders()

@tool()
def get_order_status(order_id: str) -> str:
    """Look up the delivery status of one ShopKart order.

    Args:
        order_id: The order ID, for example SK-1042
    """
    return checked_status(order_id)

@tool(risky=True)
def issue_refund(order_id: str, reason: Literal["damaged", "wrong item", "changed mind"]) -> str:
    """Refund a delivered order in full to the original payment method.

    Args:
        order_id: The order ID, for example SK-1077
        reason: Why the customer wants the refund
    """
    return checked_refund(order_id, reason)

def agent_tools():
    """The Agent's TOOLS and risky set, both read from the registry, so they cannot drift apart."""
    return ({n: (r["definition"], r["fn"]) for n, r in REGISTRY.items()}, {n for n, r in REGISTRY.items() if r["risky"]})

tools, risky = agent_tools()
print(sorted(tools), "| risky:", risky)
print(json.dumps(tools["get_order_status"][0]))
What you should see
['find_orders', 'get_order_status', 'issue_refund'] | risky: {'issue_refund'}
{"name": "get_order_status", "description": "Look up the delivery status of one ShopKart order.", "input_schema": {"type": "object", "properties": {"order_id": {"type": "string", "description": "The order ID, for example SK-1042"}}, "required": ["order_id"], "additionalProperties": false}}

Two things changed for the better. The definition is generated, so the rename in the opening example is now impossible: rename the parameter and the schema follows it. And risk is declared on the tool itself, @tool(risky=True), with the agent's risky set read from the registry. Lesson 3.2's debugging exercise, where a typo in a separate list of names let a refund through, cannot happen this way.

Idea 3 · Check the arguments before anything runs

A schema describes valid input; it does not enforce it. Unless you use a strict mode (below), the model can send an enum value that is not in the list, misspell an argument, or leave one out. Check before the approval gate and before your function:

def validate(args, schema):
    """Check the model's arguments against the tool's input_schema. Returns a list of problems (empty = valid)."""
    problems, props = [], schema["properties"]
    problems += [f"missing required argument {r!r}" for r in schema["required"] if r not in args]
    problems += [f"unknown argument {k!r}; allowed: {sorted(props)}" for k in args if k not in props]
    for k, v in args.items():
        spec = props.get(k, {})
        if spec.get("type") == "string" and not isinstance(v, str):
            problems.append(f"{k!r} must be a string")
        if "enum" in spec and v not in spec["enum"]:
            problems.append(f"{k!r} must be one of {spec['enum']}, got {v!r}")
    return problems

class ValidatingAgent(Agent):
    def call_tool(self, c):
        if c.name in self.tools:
            problems = validate(c.input, self.tools[c.name][0]["input_schema"])
            if problems:                                   # checked before the gate and before your code runs
                return {"type": "tool_result", "tool_use_id": c.id, "is_error": True,
                        "content": "invalid arguments: " + "; ".join(problems)}
        return super().call_tool(c)

from types import SimpleNamespace as NS
support = ValidatingAgent(system=SYSTEM, tools=tools, risky=risky)
for bad in [{"order_id": "SK-1077", "reason": "broken"}, {"order": "SK-1077", "reason": "damaged"}]:
    print(support.call_tool(NS(id="toolu_x", name="issue_refund", input=bad))["content"])
What you should see
invalid arguments: 'reason' must be one of ['damaged', 'wrong item', 'changed mind'], got 'broken'
invalid arguments: missing required argument 'order_id'; unknown argument 'order'; allowed: ['order_id', 'reason']

Each message names the argument and says how to fix it, which is what lets a model correct itself on the next request (Lesson 3.1's retry). The check runs before the approval gate, so nobody is asked to approve a malformed refund.

Validation of the shape is not validation of the meaning. validate cannot know whether SK-1077 belongs to this customer, or whether it was delivered more than 30 days ago. Those checks stay in the function, where Lesson 3.1 put them.

Tool design: what makes a tool easy to use well

The model chooses and fills tools from their names, descriptions and schemas, so those are prompt text: together they are the agent-computer interface (ACI). Anthropic's guidance on writing tools for agents (Writing effective tools for agents, September 2025) comes down to a few rules:

  • Name tools for the task, not the API: find_orders, not GET_orders_v2. Namespace related tools (orders_find, orders_refund) when you have many.
  • Fewer, higher-level tools. One schedule_meeting beats list_users plus list_events plus create_event when the model would always chain them.
  • Describe when to use it and what comes back, including units, formats and limits, as you would for a new colleague.
  • Make arguments hard to get wrong: enums, IDs that come from lookup tools rather than memory, sensible defaults.
  • Return what the next step needs, not everything.
  • Errors that say how to fix the call, never an empty result that looks like "nothing found".

The fifth rule is the easiest to measure, because every byte a tool returns is re-read on every later step (Lesson 3.2). Here is the same agent with the order service's full record, then with only the fields the answer needs:

# What the order service really returns: 30-odd fields, most of them noise for this question
RAW_FIELDS = {f"internal_{k}": f"value-{k:02d}-xxxxxxxxxxxx" for k in range(28)}

def get_order_status_raw(order_id: str) -> str:
    order = json.loads(checked_status(order_id))
    return json.dumps({**order, **RAW_FIELDS, "warehouse_scan_log": ["scan"] * 20})

verbose = dict(tools, get_order_status=(tools["get_order_status"][0], get_order_status_raw))
questions = ["Where is my order SK-1042?", "Where are my running shoes?", "Has SK-1077 been delivered?"]
answers = {}
for label, toolset in [("full API record", verbose), ("only the fields needed", tools)]:
    agent = ValidatingAgent(system=SYSTEM, tools=toolset, risky=risky)
    runs = [(agent.run(q), agent.trace[-1][3]) for q in questions]
    answers[label] = [a for a, _ in runs]
    print(f"{label:<24} tokens per run: {[t for _, t in runs]}")
print("same answers both ways:", answers["full API record"] == answers["only the fields needed"])
What you should see
full API record          tokens per run: [1081, 1587, 1078]
only the fields needed   tokens per run: [719, 1225, 716]
same answers both ways: True

Identical answers, about a third fewer tokens per run. (The stand-in counts characters ÷ 4, so read the ratio.) With a real model, irrelevant fields also cost accuracy: the model has more text to misread and more chances to quote an internal field to the customer.

Problems that show up in production, and the fix for each:

Problem Fix
Two overlapping tools (search_orders and find_order); the model picks either Merge them, or say in each description when not to use it
Too many tools for one agent; tool choice gets worse as the list grows Give each specialist only its own tools (Lesson 3.11), or load definitions on demand (below)
Huge results Return a few fields by default, with a detail or limit option
An empty list on error, which the model reads as "no orders" An explicit error that says what to do next
IDs the model has to remember or invent Lookup tools, so IDs always come from data

Large tool sets. Every definition you send is read on every request. Claude's tool reference (checked 4 November 2026) documents a server-side tool search tool (tool_search_tool_regex_20251119 and tool_search_tool_bm25_20251119, no beta header listed) together with defer_loading: true on a definition, which keeps that tool out of the prompt until a search returns it, without breaking the prompt cache. It also documents allowed_callers, which lets code running in Claude's code-execution sandboxlater · 10.3 call a tool directly, so intermediate results need not pass through the model. Anthropic's Code execution with MCPlater · 8.1 post (November 2025) reports a workflow falling from about 150,000 tokens to about 2,000 that way. Both are vendor-specific. The idea behind them is not: keep definitions and intermediate results out of the context unless the model needs them.

What the library replaces

Claude's SDK has its own decorator, @beta_tool (Lesson 3.1). Compare its schema with yours:

from anthropic import beta_tool                            # the SDK's version of the same idea (no network needed)

def get_order_status_sdk(order_id: str) -> str:
    """Look up the delivery status of one ShopKart order.

    Args:
        order_id: The order ID, for example SK-1042
    """

sdk = beta_tool(get_order_status_sdk).to_dict()["input_schema"]
ours = schema_from(get_order_status_sdk)["input_schema"]
print("SDK :", json.dumps(sdk))
print("ours:", json.dumps(ours))
What you should see
SDK : {"additionalProperties": false, "properties": {"order_id": {"description": "The order ID, for example SK-1042", "title": "Order Id", "type": "string"}}, "required": ["order_id"], "type": "object"}
ours: {"type": "object", "properties": {"order_id": {"type": "string", "description": "The order ID, for example SK-1042"}}, "required": ["order_id"], "additionalProperties": false}

The same schema, plus a title per property (the SDK builds it with Pydantic). The decorator replaces schema_from and the registry. Pydantic also validates and converts the arguments before your function runs, which replaces validate. What you still own is everything the schema cannot express: ownership, business rules, which tools are risky, and how much a result returns.

Strict modes move validation to the provider. On Claude, strict: true on a tool definition makes the API enforce your schema on the model's input. On OpenAI, strict function calling requires every property to be listed as required and additionalProperties: false, so an optional argument is written as a nullable type:

def to_openai_strict(defn):
    """OpenAI strict mode: every property listed as required, optional ones made nullable, no extra properties."""
    schema = defn["input_schema"]
    props = {k: (v if k in schema["required"] else {**v, "type": [v["type"], "null"]}) for k, v in schema["properties"].items()}
    return {"type": "function", "name": defn["name"], "description": defn["description"], "strict": True,
            "parameters": {"type": "object", "properties": props, "required": list(props), "additionalProperties": False}}

print(json.dumps(to_openai_strict(schema_from(refund_example))["parameters"]))
claude_strict = {**schema_from(refund_example), "strict": True}      # on Claude, strict is a flag on the definition
print(sorted(claude_strict))
What you should see
{"type": "object", "properties": {"order_id": {"type": "string", "description": "The order ID, for example SK-1077"}, "reason": {"type": "string", "enum": ["damaged", "wrong item", "changed mind"], "description": "Why the customer wants the refund"}, "note": {"type": ["string", "null"], "description": "Anything the customer added, in their words"}}, "required": ["order_id", "reason", "note"], "additionalProperties": false}
['description', 'input_schema', 'name', 'strict']

note is now required but may be null. With strict mode on, malformed arguments stop reaching your code, which makes validate a second line of defense rather than the only one. It still earns its place, because your agent may also run on models or providers without strict support.

Solutions

SolutionP1 · Required arguments and types

required is ["customer_note"]: only the parameter without a default. include_items gets {"type": "boolean"} and limit gets {"type": "integer"}. A default means "the model may leave this out", so choose defaults that are safe when it does.

SolutionP2 · Without functools.wraps

It prints name: wrapper | docstring: None, then schema_from fails: KeyError 'kwargs'. The decorator returned wrapper, which has its own name, no docstring, and a signature of **kwargs, so every tool would be called "wrapper" with no description and no parameters. functools.wraps(fn) copies the name, docstring and signature, so inspect sees the original function through the wrapper. A model reading a tool called "wrapper" with no description would have no way to use it correctly.

SolutionD1 · Optional arguments

Optional[str] is Union[str, None], which is not a key in JSON_TYPES, so the lookup raises KeyError typing.Optional[str]. Unwrap it first:

# Solution D1: unwrap Optional[X] (which is Union[X, None]) before looking up the JSON type
def json_type(t):
    if typing.get_origin(t) is typing.Union and type(None) in typing.get_args(t):
        t = next(a for a in typing.get_args(t) if a is not type(None))
    if typing.get_origin(t) is Literal:
        return {"type": "string", "enum": list(typing.get_args(t))}
    if t not in JSON_TYPES:
        raise TypeError(f"no JSON type for {t!r}; add it to JSON_TYPES or use a simpler type")
    return {"type": JSON_TYPES[t]}

print(json_type(Optional[str]), json_type(Literal["a", "b"]), json_type(int))
try:
    json_type(dict)
except TypeError as e:
    print(e)

{'type': 'string'} {'type': 'string', 'enum': ['a', 'b']} {'type': 'integer'}
no JSON type for <class 'dict'>; add it to JSON_TYPES or use a simpler type

Use json_type(hints[name]) inside schema_from. The default of None already keeps carrier out of required. Failing with a clear TypeError for unsupported types is better than generating a schema the model cannot satisfy.

Check your understanding

Explain the mechanismHow does a framework turn a Python function into a tool the model can call?

Worked answer. It reads the function: the name becomes the tool name, the docstring becomes the description, and the parameters with their type hints become a JSON Schema of properties, with parameters that have no default listed as required. Literal types become enums. Libraries such as Claude's @beta_tool or LangChainlater · 6.2's @tool use Pydantic to build and validate that schema. A decorator registers the function when the module is imported, and at call time the framework looks the tool up by name, validates the model's arguments against the schema, calls the function, and turns its return value or exception into a tool result.

A plausible wrong answer. "The model reads the Python source code." It never sees the code, only the generated definition. That is why docstrings and parameter names matter so much.

Follow-ups. What happens with Optional or complex types? Why might two frameworks generate different schemas for the same function?

Debug a failureAfter a deploy, every call to one tool fails with "unexpected keyword argument". Nothing in the prompt changed. What happened?

Worked answer. The function's parameters and the definition the model sees have drifted apart: someone renamed a parameter in the function but the hand-written definition still uses the old name, or the other way round. The model fills in the definition, so every call carries the old name. In the short term, align the two. For the long term, generate definitions from the functions so they cannot drift. Add a start-up check that every registered tool's schema matches its function's signature, and a test that calls each tool with the arguments in its own examples.

A plausible wrong answer. "The model is hallucinating argument names; add a line to the prompt." The model is doing exactly what the definition says.

Follow-ups. How would you catch this before deploy? How do you change a tool's arguments without breaking conversations already in progress?

Defend a designA teammate wants 60 small tools that map one-to-one to your internal API. What do you propose?

Worked answer. I would push for fewer, task-shaped tools, because every definition is read on every request, and choosing among overlapping tools gets less reliable as the list grows. Group the endpoints by the jobs the agent actually does, for example find_orders, get_order_status and issue_refund rather than raw CRUD. Return only the fields the next step needs, and split the remaining tools across specialist agents. If a large catalog is unavoidable, load definitions on demand, for example with Claude's tool search and defer_loading, and measure tool-choice accuracy and tokens per run before and after.

A plausible wrong answer. "More tools give the model more flexibility." In practice they give it more ways to choose wrong, and a larger bill on every step.

Follow-ups. How would you measure tool-choice accuracy? When does a thin wrapper per endpoint make sense?
