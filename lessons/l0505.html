Five families of algorithms cover almost everything AI systems do with graphs. You rarely implement them yourself in production (graph databases and libraries ship them), but implementing each once makes it clear what it costs and when its answer can be trusted.

Family Algorithms AI use
Traversal Breadth-first (BFS), depth-first (DFS), k-hop neighborhoods Expanding retrieval context; blast radius of an outage; reachability for access control
Paths Dijkstra, A*, all shortest paths Explaining how two entities relate; cheapest route through tools or services
Centrality Degree, PageRank, betweenness, eigenvector Which entities matter most; what to summarize first; hubs that are risks
Communities Connected components, Louvain, Leiden, label propagation Topic clusters for GraphRAGlater · 14.43 global search; fraud rings; customer segments
Similarity and prediction Jaccard, Adamic-Adar, node embeddings, graph neural networks Recommendations; missing facts in a knowledge graph; entity resolution
Why this came about

Graph algorithms such as shortest paths, PageRank (1998) and community detection were developed long before AI assistants. They became newly relevant because GraphRAG uses them, for example to group related entities into communities that can be summarized.

In plain words first
Using the map's shape

Once data is a graph, its shape itself answers questions: shortest paths (how are these two connected?), centrality (who is most connected or influential?), communities (which nodes cluster together?), and link prediction (which connection is probably missing?). These algorithms run without a model and often feed it: community summarieslater · 14.43 for GraphRAG, important nodes for ranking.

Hands-on · Traversal and shortest paths

The graph below is a service dependency graph for an agent platform, with typical latency on each edge. BFS answers "what depends on postgres?" (walk the edges backwards), and Dijkstra finds the fastest route.

import heapq
from collections import deque

# A service dependency graph for an agent platform: edge weight = typical latency in ms.
EDGES = [("gateway", "router", 5), ("router", "support_agent", 8), ("router", "sales_agent", 8),
         ("support_agent", "orders_api", 40), ("support_agent", "kb_search", 120), ("support_agent", "llm", 900),
         ("sales_agent", "crm_api", 60), ("sales_agent", "llm", 900), ("kb_search", "vector_db", 30),
         ("orders_api", "postgres", 10), ("crm_api", "postgres", 15), ("kb_search", "llm", 300)]
G = {}
for a, b, w in EDGES:
    G.setdefault(a, {})[b] = w; G.setdefault(b, {})

def bfs(start):
    """Breadth-first: every node reachable from start, with its hop count."""
    hops, q = {start: 0}, deque([start])
    while q:
        n = q.popleft()
        for m in G[n]:
            if m not in hops:
                hops[m] = hops[n] + 1; q.append(m)
    return hops

def dijkstra(src, dst):
    """Cheapest path by total weight (all weights non-negative)."""
    best, prev, pq = {src: 0}, {}, [(0, src)]
    while pq:
        d, n = heapq.heappop(pq)
        if n == dst:
            break
        if d > best[n]:
            continue
        for m, w in G[n].items():
            if d + w < best.get(m, float("inf")):
                best[m], prev[m] = d + w, n; heapq.heappush(pq, (d + w, m))
    path = [dst]
    while path[-1] != src:
        path.append(prev[path[-1]])
    return best[dst], path[::-1]

print("blast radius of a postgres outage (who depends on it, by hops):")
rev = {}
for a, b, _ in EDGES:
    rev.setdefault(b, []).append(a)
seen, q = {"postgres": 0}, deque(["postgres"])
while q:
    n = q.popleft()
    for m in rev.get(n, []):
        if m not in seen:
            seen[m] = seen[n] + 1; q.append(m)
print("  ", {k: v for k, v in sorted(seen.items(), key=lambda kv: kv[1]) if k != "postgres"})
print("reachable from gateway:", len(bfs("gateway")) - 1, "services")
print("fastest path gateway -> vector_db:", dijkstra("gateway", "vector_db"))
What you should see
blast radius of a postgres outage (who depends on it, by hops):
   {'orders_api': 1, 'crm_api': 1, 'support_agent': 2, 'sales_agent': 2, 'router': 3, 'gateway': 4}
reachable from gateway: 9 services
fastest path gateway -> vector_db: (163, ['gateway', 'router', 'support_agent', 'kb_search', 'vector_db'])

A postgres outage reaches both agents in two hops and the gateway in four, which is the list of things to alert, degrade or route around (Lesson 14.113). Dijkstra picks the path through kb_search, and the path itself is the explanation. BFS costs time proportional to the edges it visits; Dijkstra adds a priority queue, so roughly edges times log nodes. Both are cheap on sparse graphs and dangerous on unbounded ones, which is why production traversals always carry a depth or cost limit (Lesson 14.44).

Hands-on · Ranking, communities and link prediction

PageRank scores a node by the scores of the nodes pointing to it: a random walker follows edges and occasionally jumps to a random node; the share of time spent at each node is its rank. Personalized PageRank jumps back only to chosen seed nodes, so it ranks everything by closeness to the seeds. This is the retrieval step in HippoRAG (NeurIPS 2024), which builds a knowledge graph from documents and ranks passages by personalized PageRank from the entities in the question; its authors report single-step retrieval that matches or beats iterative retrieval such as IRCoT while being 10 to 30 times cheaper (Gutiérrez et al.).

Louvain and Leiden find communities by grouping nodes so that edges inside groups are dense compared with what chance would give (modularity). Leiden fixes a weakness of Louvain (communities that are internally disconnected) and is what Microsoft's GraphRAG uses to build its hierarchy of community summaries (Lesson 14.43).

import networkx as nx

def pagerank(edges, d=0.85, iters=50, personalize=None):
    """Power iteration. With `personalize`, random jumps return to those nodes only
    (Personalized PageRank, the retrieval step in HippoRAG)."""
    nodes = sorted({x for e in edges for x in e})
    out = {n: [b for a, b in edges if a == n] for n in nodes}
    jump = {n: (1 / len(personalize) if n in personalize else 0) for n in nodes} if personalize \
        else {n: 1 / len(nodes) for n in nodes}
    pr = dict(jump)
    for _ in range(iters):
        new = {n: (1 - d) * jump[n] for n in nodes}
        for n in nodes:
            targets = out[n] or nodes                     # dangling nodes spread evenly
            for m in targets:
                new[m] += d * pr[n] / len(targets)
        pr = new
    return pr

# A small knowledge graph of facts (undirected for ranking: both directions).
facts = [("Priya", "Phone X"), ("Meera", "Phone X"), ("Arjun", "Earbuds"), ("Phone X", "Acme Electronics"),
         ("Earbuds", "Acme Electronics"), ("Phone case", "Shenzhen Parts"), ("Priya", "Phone case"),
         ("Acme Electronics", "Shenzhen Parts"), ("Shenzhen Parts", "battery recall 2026"),
         ("Phone X", "warranty policy"), ("Earbuds", "warranty policy")]
und = facts + [(b, a) for a, b in facts]
pr = pagerank(und)
ref = nx.pagerank(nx.DiGraph(und), alpha=0.85)
print("top entities by PageRank:", [n for n, _ in sorted(pr.items(), key=lambda kv: -kv[1])[:3]])
print("matches networkx:", all(abs(pr[n] - ref[n]) < 1e-4 for n in pr))

ppr = pagerank(und, personalize={"Meera"})
ranked = [n for n, _ in sorted(ppr.items(), key=lambda kv: -kv[1]) if n != "Meera"][:4]
print("what matters for a question about Meera:", ranked)

H = nx.Graph(facts)
communities = nx.community.louvain_communities(H, seed=7)
print("communities:", sorted(sorted(c) for c in communities))
print("betweenness, top 2:", [n for n, _ in sorted(nx.betweenness_centrality(H).items(), key=lambda kv: -kv[1])[:2]])
def jaccard(a, b):
    na, nb = set(H[a]), set(H[b])
    return len(na & nb) / len(na | nb)
print(f"link prediction, Priya-Meera Jaccard {jaccard('Priya', 'Meera'):.2f} | Priya-Arjun {jaccard('Priya', 'Arjun'):.2f}")
What you should see
top entities by PageRank: ['Phone X', 'Shenzhen Parts', 'Earbuds']
matches networkx: True
what matters for a question about Meera: ['Phone X', 'Acme Electronics', 'Earbuds', 'warranty policy']
communities: [['Acme Electronics', 'Shenzhen Parts', 'battery recall 2026'], ['Arjun', 'Earbuds', 'warranty policy'], ['Meera', 'Phone X', 'Phone case', 'Priya']]
betweenness, top 2: ['Acme Electronics', 'Phone X']
link prediction, Priya-Meera Jaccard 0.50 | Priya-Arjun 0.00

The from-scratch PageRank matches networkx. Personalized from Meera, the ranking surfaces her phone, its maker and the related warranty policy: a relevance ranking with no embeddings at all. Louvain splits the graph into a supply-chain cluster, an earbuds cluster and a phone cluster, which is exactly the kind of grouping GraphRAG summarizes. Betweenness finds the brokers between clusters (Acme Electronics), the nodes whose failure or compromise disconnects the most paths. And Priya and Meera share half their neighbors while Priya and Arjun share none, the simplest form of link prediction ("customers like you bought").

Tip
Algorithms answer different questions about "important"

Degree says "has many connections", PageRank "is connected to important things", betweenness "sits between groups". A product can top degree (bought by everyone) and score low on betweenness (bought only by one segment). Choose the measure that matches the decision.

Embeddings and graph neural networks, briefly

Node embeddings (DeepWalk, node2vec) turn each node into a vector by running random walks and training a word2vec-style model on them, so nodes that appear in similar neighborhoods get similar vectors; they plug into the vector tools of Lesson 14.29. Knowledge graph embeddings (TransE, RotatE and others) learn vectors for entities and relations so that missing facts can be predicted. Graph neural networks (GCN, GraphSAGE, GAT) learn by passing messages between neighbors and are strong for fraud detection, recommendations and molecule property prediction.

For most LLM applications, reach for them only after the simpler tools: an LLM with a graph query tool or GraphRAG covers question answering, and common-neighbor scores cover many recommendation baselines. Graph neural networks pay off when you have many labeled examples of the thing to predict (fraud, churn, links) and the signal really lives in the structure.

Algorithm Cost on a graph with n nodes and m edges Practical note
BFS, DFS Proportional to n + m Always cap depth in production
Dijkstra About m log n Needs non-negative weights
PageRank m per iteration, tens of iterations Precompute offline; personalized PageRank per query is still cheap on subgraphs
Betweenness (exact) About n x m Expensive; sample source nodes on big graphs
Louvain, Leiden Close to linear in m in practice Run offline; results vary with the random seed, so fix it
Node2vec, GNNs Training cost; GPUs for large graphs Use when structure predicts a label you care about

Exercises

Predict before you run

Personalized PageRank from one product, with damping 0.85: which nodes score highest? (Solution P1.)

Break it on purpose

Run dijkstra on a graph where some edge weights are negative (a discount modeled as negative cost). What can go wrong? (Solution B1.)

Debugging exercise

Community detection puts almost every supplier in one community. What graph property is likely the cause? (Solution D1.)

Make it your own

Use Jaccard similarity on suppliers' customer sets to suggest alternative suppliers for a product, and list the top three for one supplier. (Solution M1.)

Solutions

SolutionP1 · Importance near a starting point

Nodes close to the starting product and well connected to it, because the random walk restarts at that product with probability 0.15. It is "what matters relative to this node", useful for recommendations and context selection in GraphRAG.

SolutionB1 · Dijkstra assumes non-negative weights

Dijkstra can return wrong shortest paths with negative weights, because it finalizes nodes too early. Use Bellman-Ford, or remodel so weights are non-negative.

SolutionD1 · Supernodes merge communities

A hub node (a shared logistics provider, a generic category) connects everything, so communities merge. Remove or down-weight hub edges for the analysis, or use edge types that carry meaning.

SolutionM1 · Link prediction by similarity

Compute Jaccard between the supplier's neighbor set and every other supplier's, rank, and filter by type. Similar neighborhoods suggest substitutes; validate with domain experts.

Explain the mechanismName core graph algorithms and what business questions they answer.

Worked answer. Traversal and shortest paths (exposure, routes, dependency chains), centrality such as PageRank (influence, importance), community detection (segments, fraud rings), similarity and link prediction (recommendations, missing relationships). Graph embeddings and GNNs learn representations for prediction tasks.

A plausible wrong answer. "Graph algorithms are only for social networks." They apply to any connected data.

Follow-ups. When would you use a GNN instead of an algorithm?

Debug a failurePageRank results look dominated by a few nodes that are not important to the business. Why?

Worked answer. Structural artifacts: hubs created by data modeling (a category node linked to everything), duplicated edges, or edge directions reversed. Inspect the top nodes and their edges, and run the algorithm on a projection with meaningful edges only.

A plausible wrong answer. "PageRank is wrong." It ranks the graph you gave it.

Follow-ups. How would you choose the projection?

Defend a designRun graph algorithms in the database or export to Python?

Worked answer. In the database (graph data science libraries) for large graphs and regular jobs close to the data; in Python (NetworkX, igraph) for exploration and small graphs. Export only what you need, because large exports are slow and go stale.

A plausible wrong answer. "Always NetworkX, it is easier." It does not scale to large graphs.

Follow-ups. What would you schedule as a regular job?
