Snowflake's approach is the opposite of the hyperscalers': instead of moving data to the models, it brings the models to governed data. Every AI feature runs inside the account's security boundary, under the same roles, masking policies and row access policies as the data. For a data team, that makes Snowflake the fastest place to ship a governed agent over structured and unstructured data.

Why this came about

Snowflake started as a cloud data warehouse. From 2023 it added models as SQL functions (Cortex), then managed search (Cortex Search, 2024), text-to-SQL over a semantic layer (Cortex Analyst, 2024) and an agent object that orchestrates them (Cortex Agents, 2025), and in 2026 renamed its two agent products CoWork and CoCo. The idea throughout: bring the models to governed data instead of copying data out to the models.

In plain words first
The warehouse that learned to answer questions

Everything in this lesson is an answer to one worry: "our data is governed in Snowflake, and an agent would copy it somewhere less governed". Cortex puts the model next to the data, so a question runs under the same role, masking and row-access rules as a SQL query. You will meet five pieces: AI functions (a model call as a SQL column), Cortex Search (managed retrieval), semantic views with Cortex Analyst (text-to-SQL that knows what "revenue" means), Cortex Agents (the orchestrator), and the managed MCP server (the door for outside agents such as LangGraph). The code block in this lesson runs offline against a recorded response; the SQL needs a Snowflake account.

Step 1 · Cortex AI functions: AI in SQL

AI functions are the highest-leverage AI feature in Snowflake. They turn a model call into a column expression, so one SQL statement can classify, extract or summarize millions of rows, in a dynamic table that keeps itself up to date, with no agent at all.

Function Job
AI_COMPLETE General generation, with a model, options and structured output (response_format as a JSON schema); accepts images, and in 2026 audio and video
AI_CLASSIFY Assign one or more labels from a list you provide
AI_FILTER A yes or no condition in plain language; use it in WHERE and for a semantic join
AI_AGG, AI_SUMMARIZE_AGG Aggregate many rows into one insight or summary (beyond the context window)
AI_EXTRACT Pull named fields from text or documents
AI_PARSE_DOCUMENT OCR and layout extraction from PDFs and images on a stage
AI_TRANSCRIBE Speech to text from audio and video files
AI_REDACT Remove PII from text
AI_SUMMARIZE Summarize text, images or documents
AI_EMBED, AI_MULTI_EMBED, AI_SIMILARITY Embeddings for text and images (and with AI_MULTI_EMBED audio and video), and similarity
AI_SENTIMENT, AI_TRANSLATE Sentiment by aspect, translation
AI_COUNT_TOKENS Estimate tokens before you spend them 
-- 1. Classify and extract on every new ticket, kept fresh by a dynamic table
CREATE OR REPLACE DYNAMIC TABLE support.ticket_insights
  TARGET_LAG = '15 minutes' WAREHOUSE = ai_wh AS
SELECT
  ticket_id,
  AI_CLASSIFY(body, ['late_delivery', 'damaged_item', 'refund', 'other']):labels[0]::string AS category,
  AI_SENTIMENT(body):categories[0]:sentiment::string                                        AS sentiment,
  AI_COMPLETE(
    model => 'claude-sonnet-5-5',
    prompt => CONCAT('Extract the order ID and the action the customer wants. Ticket: ', body),
    response_format => {'type': 'json', 'schema': {'type': 'object',
        'properties': {'order_id': {'type': 'string'}, 'wants': {'type': 'string'}},
        'required': ['order_id', 'wants']}}
  )                                                                                         AS fields
FROM support.tickets;

-- 2. A semantic filter and a semantic join, in plain language
SELECT t.ticket_id, p.policy_id
FROM support.tickets t
JOIN support.policies p
  ON AI_FILTER(PROMPT('Does policy {0} answer the question in ticket {1}?', p.text, t.body))
WHERE AI_FILTER(PROMPT('Is this customer threatening to leave? {0}', t.body));

-- 3. One insight across thousands of rows
SELECT city, AI_AGG(body, 'What are the top three causes of complaints? Answer in bullet points.') AS causes
FROM support.tickets JOIN shop.orders USING (order_id)
WHERE created_at > DATEADD(day, -7, CURRENT_DATE)
GROUP BY city;
Watch out
Cost control for AI functions

AI functions bill in credits per token, and a careless SELECT AI_COMPLETE(...) FROM big_table can be the most expensive query of the month. Test on LIMIT 100, estimate with AI_COUNT_TOKENS, use the smallest model that passes your evals, filter rows before calling the model, use dynamic tables so rows are processed once, and watch SNOWFLAKE.ACCOUNT_USAGE.CORTEX_AI_FUNCTIONS_USAGE_HISTORY (the standard view for function spend; CORTEX_AISQL_USAGE_HISTORY still exists for per-function detail but is slated for deprecation in January 2027), plus CORTEX_AGENT_USAGE_HISTORY and the other per-service usage views. Calling AI functions needs the USE AI FUNCTIONS account privilege and the CORTEX_USER (or AI_FUNCTIONS_USER) database role, so grant them to roles deliberately. Set budgets with alerts and per-user quotas (the only AI cost control with built-in enforcement), and restrict models with model RBAC: grant the model application roles in SNOWFLAKE.MODELS (CORTEX-MODEL-ROLE-ALL, or one role per model). The older CORTEX_MODELS_ALLOWLIST account parameter is being retired (behavior change bundle 2026_07; fully retired in January 2027), so do not build new controls on it.

Step 2 · Cortex Search for documents

Cortex Search is managed hybrid retrieval: it embeds your text, keeps a vector and keyword index fresh as the source table changes, and reranks results (Lessons 14.70 to 5.38 as one SQL statement).

-- Parse PDFs on a stage into text, then chunk it
CREATE OR REPLACE TABLE docs.policy_chunks AS
SELECT relative_path,
       c.value::string AS chunk
FROM DIRECTORY(@docs.policy_stage),
     LATERAL FLATTEN(SNOWFLAKE.CORTEX.SPLIT_TEXT_RECURSIVE_CHARACTER(
         AI_PARSE_DOCUMENT(TO_FILE('@docs.policy_stage', relative_path), {'mode': 'LAYOUT'}):content::string,
         'markdown', 1500, 200)) c;

CREATE OR REPLACE CORTEX SEARCH SERVICE docs.policy_search
  ON chunk
  ATTRIBUTES relative_path
  WAREHOUSE = ai_wh
  TARGET_LAG = '1 hour'
  AS SELECT chunk, relative_path FROM docs.policy_chunks;

-- Try it from SQL (SEARCH_PREVIEW is for testing: string literals only, higher latency; agents and apps use the REST or Python API)
SELECT PARSE_JSON(SNOWFLAKE.CORTEX.SEARCH_PREVIEW('docs.policy_search',
  '{"query": "refund for a damaged mixer", "columns": ["chunk", "relative_path"], "limit": 3}')):results;

Step 3 · Semantic views and Cortex Analyst for metrics

Text-to-SQL fails when the model guesses what "revenue" or "late" means. A semantic view is a schema-level object that defines tables, relationships, dimensions, facts and metrics with business names, synonyms and verified example queries. Cortex Analyst uses it to write correct SQL, and the same definitions serve BI tools, so humans and agents get the same number.

CREATE OR REPLACE SEMANTIC VIEW shop.orders_sv
  TABLES (
    orders    AS shop.orders    PRIMARY KEY (order_id) WITH SYNONYMS ('purchases'),
    customers AS shop.customers PRIMARY KEY (customer_id)
  )
  RELATIONSHIPS (orders (customer_id) REFERENCES customers)
  FACTS (orders.order_value AS amount_inr)
  DIMENSIONS (
    orders.city       AS delivery_city WITH SYNONYMS ('location'),
    orders.order_date AS order_date,
    customers.tier    AS loyalty_tier
  )
  METRICS (
    orders.late_deliveries AS COUNT_IF(orders.delivered_at > orders.promised_at)
      COMMENT = 'Orders delivered after the promised date',
    orders.gmv AS SUM(orders.order_value) WITH SYNONYMS ('revenue', 'sales')
  )
  COMMENT = 'ShopKart orders for operations and finance questions'
  AI_SQL_GENERATION 'Use late_deliveries for any question about delays. Amounts are in INR.'
  AI_VERIFIED_QUERIES (
    late_by_city AS (
      QUESTION 'Which cities had the most late deliveries last week?'
      SQL 'SELECT * FROM SEMANTIC_VIEW(shop.orders_sv DIMENSIONS orders.delivery_city METRICS orders.late_deliveries)'
    )
  );

AI_SQL_GENERATION gives Cortex Analyst standing instructions; AI_VERIFIED_QUERIES stores question-and-SQL pairs an analyst has checked. Analyst prefers a verified query when the question matches, and reports it in its response (verified_query_used), which is how you tell a checked answer from a generated one.

Semantic View Autopilot (GA 2026) drafts semantic views from your query history and existing BI models, and the Open Semantic Interchange initiative aims to make these definitions portable across tools. Add verified queries for the questions that matter most; they are the evaluation set for Analyst.

Step 4 · Cortex Agents

A Cortex Agent is a schema object that holds the orchestration model, instructions, tools and limits. Cortex plans, calls tools (Analyst for numbers, Search for documents, your procedures for actions), reflects on results and answers with citations, charts and tables. The same agent serves CoWork, your app (through the REST API), Teams and Slack integrations, and outside agents (through MCP).

CREATE OR REPLACE AGENT shopkart.agents.ops_analyst
  COMMENT = 'Operations questions over orders and policies'
  PROFILE = '{"display_name": "ShopKart Ops Analyst"}'
  FROM SPECIFICATION
  $$
  models:
    orchestration: auto

  orchestration:
    budget:
      seconds: 60
      tokens: 32000

  instructions:
    orchestration: "Use orders_analyst for any number, count or trend. Use policy_search for rules and policies. Use order_lookup when the user gives an order ID."
    response: "Answer in two or three sentences, then show the table. Cite policy documents by file name."
    sample_questions:
      - question: "Which cities had the most late deliveries last week?"

  tools:
    - tool_spec:
        type: "cortex_analyst_text_to_sql"
        name: "orders_analyst"
        description: "Order metrics: late deliveries, GMV, by city, date and loyalty tier"
    - tool_spec:
        type: "cortex_search"
        name: "policy_search"
        description: "ShopKart refund, return and delivery policies"
    - tool_spec:
        type: "generic"
        name: "order_lookup"
        description: "Look up one order's status, items and delivery dates by order_id."
        input_schema:
          type: "object"
          properties:
            order_id: {type: "string", description: "Order ID like A-1001"}
          required: ["order_id"]

  tool_resources:
    orders_analyst:
      semantic_view: "shopkart.shop.orders_sv"
      execution_environment: {type: "warehouse", warehouse: "AGENT_WH"}
    policy_search:
      search_service: "shopkart.docs.policy_search"
      max_results: "5"
      id_column: "relative_path"
    order_lookup:
      type: "function"
      identifier: "shopkart.ops.order_lookup"
      execution_environment: {type: "warehouse", warehouse: "AGENT_WH"}
  $$;

GRANT USAGE ON AGENT shopkart.agents.ops_analyst TO ROLE ops_analysts;

Custom tools are UDFs or stored procedures; the spec above attaches a UDF (type: "function", the documented form). Write actions such as a refund belong in a stored procedure with its own checks (amount limits, idempotency keys); Snowsight lets you attach a procedure as a custom tool, and since the YAML keys for procedure-backed tools are not shown in the docs we checked (UNVERIFIED), build those in Snowsight and copy the spec it generates. Agents run with the caller's role (for REST calls, the X-Snowflake-Role header or the user's default role), and the budget caps orchestration time and tokens, not the tools' own work.

Your application calls the agent with the Agent Run API, which streams server-sent events: status updates, tool calls, tool results, text deltas, tables, charts and a final response event. Authenticate with OAuth or a programmatic access token (PAT) bound to a least-privileged role; the agent then sees only what that role can see. Synchronous runs time out after 15 minutes; background: true (with a thread) allows 6 hours.

import io, json, os
import requests, urllib3

class Recorded(requests.adapters.BaseAdapter):
    """Lab mode: answer HTTP calls from recordings instead of calling Snowflake. Remove the mount to go live."""
    def __init__(self, routes: dict):
        super().__init__()
        self.routes, self.calls = routes, []
    def send(self, request, **kwargs):
        self.calls.append((request.method, request.path_url))
        body, ctype = next(v for (m, frag), v in self.routes.items() if m == request.method and frag in request.url)
        raw = urllib3.HTTPResponse(body=io.BytesIO(body.encode()), headers={"Content-Type": ctype},
                                   status=200, preload_content=False)
        return requests.adapters.HTTPAdapter().build_response(request, raw)
    def close(self): pass

def sse(events):
    """Encode recorded events the way Snowflake streams them."""
    return "".join(f"event: {name}\ndata: {json.dumps(data)}\n\n" for name, data in events)

RECORDED_RUN = sse([
    ("metadata", {"metadata": {"role": "assistant", "message_id": 42, "run_id": "run-1"}}),
    ("response.status", {"status": "planning", "message": "Planning the next steps"}),
    ("response.tool_use", {"content_index": 0, "tool_use_id": "tu_1", "type": "cortex_analyst_text_to_sql",
                           "name": "orders_analyst", "input": {"query": "late deliveries by city last week"}}),
    ("response.tool_result", {"content_index": 1, "tool_use_id": "tu_1", "type": "cortex_analyst_text_to_sql",
                              "name": "orders_analyst", "status": "success", "content": [{"type": "json", "json": {
        "sql": "SELECT city, COUNT(*) AS late FROM orders WHERE delivered_at > promised_at GROUP BY city ORDER BY late DESC"}}]}),
    ("response.text.delta", {"content_index": 2, "text": "Bengaluru had the most late deliveries (412), "}),
    ("response.text.delta", {"content_index": 2, "text": "followed by Pune (230)."}),
    ("response", {"role": "assistant", "status": "completed", "content": [
        {"type": "text", "text": "Bengaluru had the most late deliveries (412), followed by Pune (230)."}]}),
])

ACCOUNT_URL = "https://shopkart-in.snowflakecomputing.com"            # your account URL
http = requests.Session()
http.mount("https://", Recorded({("POST", "/agents/OPS_ANALYST:run"): (RECORDED_RUN, "text/event-stream")}))
http.headers.update({"Authorization": f"Bearer {os.environ.get('SNOWFLAKE_PAT', 'offline')}",
                     "Content-Type": "application/json", "Accept": "text/event-stream"})

def run_agent(question: str, thread_id: int = 0, parent_message_id: int = 0):
    """Call a Cortex Agent and yield (event, data) pairs as they stream in."""
    url = f"{ACCOUNT_URL}/api/v2/databases/SHOPKART/schemas/AGENTS/agents/OPS_ANALYST:run"
    body = {"thread_id": thread_id, "parent_message_id": parent_message_id,
            "messages": [{"role": "user", "content": [{"type": "text", "text": question}]}]}
    with http.post(url, json=body, stream=True, timeout=900) as r:
        r.raise_for_status()
        event = None
        for line in r.iter_lines(decode_unicode=True):
            if line.startswith("event: "):
                event = line[len("event: "):]
            elif line.startswith("data: "):
                yield event, json.loads(line[len("data: "):])

answer = []
for event, data in run_agent("Which cities had the most late deliveries last week?"):
    if event == "response.status":
        print("status:", data["status"])
    elif event == "response.tool_use":
        print("tool:", data["name"], data["input"])
    elif event == "response.tool_result":
        print("sql:", data["content"][0]["json"]["sql"][:60], "...")
    elif event == "response.text.delta":
        answer.append(data["text"])                    # stream these to the user as they arrive
    elif event == "error":
        raise RuntimeError(data["message"])
print("answer:", "".join(answer))

Industry practice
Lessons from Cortex Agent projects
  • Semantic views decide quality. Most wrong answers trace back to a missing metric definition, synonym or relationship, not to the model. Invest there first, and keep verified queries as your eval set.
  • One agent per domain, with a sharp description per tool, beats one agent with every tool. CoWork lets users pick the agent.
  • Roles are the guardrail. Run each agent under a role that sees only what its users may see; masking and row access policies then apply to every tool call automatically.
  • Write actions go through procedures with their own checks (amount limits, idempotency keys), not through free-form SQL.
  • Budget limits (budget.seconds, budget.tokens) stop runaway plans; tune them from traces.

Step 5 · The managed MCP server: Snowflake for any agent

A Snowflake-managed MCP server exposes Cortex Search, Cortex Analyst, Cortex Agents, SQL execution and your procedures as MCP tools, so LangGraph, Claude, OpenAI Agents SDK, ADK, Strands or CoCo can use governed Snowflake data without custom code (Lesson 13.46).

CREATE OR REPLACE MCP SERVER shopkart.agents.shopkart_mcp
  FROM SPECIFICATION $$
  tools:
    - name: "policy-search"
      title: "ShopKart policy search"
      type: "CORTEX_SEARCH_SERVICE_QUERY"
      identifier: "shopkart.docs.policy_search"
      description: "Search refund, return and delivery policies"
    - name: "orders-analyst"
      title: "Order metrics"
      type: "CORTEX_ANALYST_MESSAGE"
      identifier: "shopkart.shop.orders_sv"
      description: "Ask questions about orders, late deliveries and GMV"
    - name: "ops-agent"
      title: "Ops analyst agent"
      type: "CORTEX_AGENT_RUN"
      identifier: "shopkart.agents.ops_analyst"
      description: "Hand a whole operations question to the Cortex Agent"
    - name: "read-sql"
      title: "Run a read-only query"
      type: "SYSTEM_EXECUTE_SQL"
      description: "Run one SELECT against the ShopKart schema"
      config: {read_only: true, query_timeout: 60, warehouse: "AGENT_WH"}
  $$;
-- Endpoint: https://<account_url>/api/v2/databases/SHOPKART/schemas/AGENTS/mcp-servers/SHOPKART_MCP
-- (use hyphens, not underscores, in the account hostname; MCP clients have trouble with underscores)

Clients authenticate with Snowflake OAuth (the default) or external OAuth from your IdP (OAUTH_AUTHORIZATION_SERVER); every tool call runs with the connecting user's default role, or a role the client requests with a session:role:<name> scope. Access to the server does not grant access to its tools: each tool needs its own grant (USAGE on the search service, SELECT on the semantic view, USAGE on the agent). Other tool types are GENERIC for UDFs and procedures (needs a config with type, warehouse and input_schema) and CODING_AGENT; when a server includes CORTEX_AGENT_RUN or CODING_AGENT, Snowflake adds ASYNC_AGENT_RUN_STATUS, AGENT_RUN_RESULT and ASYNC_AGENT_RUN_CANCEL for background runs. Tool annotations (readOnlyHint and friends) are hints for clients, not security controls.

Step 6 · CoWork and CoCo

CoWork is where most business users meet Snowflake agents: they pick an agent, ask in natural language, and get answers with tables, charts and artifacts they can save and share (GA June 2026). It adds Deep Research (GA July 2026, with web research since October), automations (GA September 2026), user skills (preview), document generation (GA October 2026) and an iOS app (GA July 2026). Administrators choose which agents appear, and access follows Snowflake roles.

CoCo is the agent for builders: it writes and explains SQL and Python, builds pipelines, creates semantic views and agents, diagnoses failed queries and cost spikes, and runs automations from the CLI and Snowsight. It respects the user's role (with an optional restricted session scope) and is a practical way to scaffold everything in this lesson.

Watch out
Cross-region inference and residency

Some models are not hosted in every region. If CORTEX_ENABLED_CROSS_REGION allows it, Snowflake may process a request in another region (data is not stored there). For an Indian account under DPDP or RBI rules (Lesson 15.26), decide this deliberately, document it, and restrict the allowed regions or models rather than leaving the default.

In production
Production issues teams hit with Cortex
  • Search results lag the data: a Cortex Search service refreshes according to its target lag, so new documents are not searchable immediately. Set the lag to what the use case needs and monitor refresh status.
  • Model availability by Region: not every model runs in every Snowflake Region; cross-Region inference must be enabled by an account administrator for models outside your Region, which is a data-residency decision, not a technical toggle.
  • Semantic views that try to cover everything: one huge semantic view lowers Cortex Analyst accuracy. Keep each one to a domain, with descriptions, synonyms, sample values and verified queries.
  • Agents without budgets: orchestration loops consume credits and time. Set the agent's orchestration budget and timeout, and watch the agent usage history views.
  • Credit attribution: AI usage lands in account-level usage views; tag warehouses and services per team so costs can be charged back.

Exercises

Predict before you run

The recorded run calls orders_analyst with the query "late deliveries by city last week". Which semantic-view objects must exist for Analyst to write that SQL, and which event carries the SQL back? (Solution P1.)

Break it on purpose

Grant USAGE ON AGENT to a role that has no SELECT on the semantic view's tables. Ask a metric question. What happens, and which layer refused? (Solution B1.)

Debugging exercise

A Cortex Search service returns stale documents for ten minutes after an upload, and the data team says "the index is broken". What do you check first? (Solution D1.)

Make it your own

Attach the Text2SQL validator from Lesson 14.80 around Analyst's SQL in a LangGraph graph: Analyst writes, the validator injects the tenant filter and row cap, a person approves unverified SQL, a read-only role executes. (Solution M1.)

Solutions

SolutionP1 · What Analyst needs

A table alias for orders with delivery_city as a dimension, late_deliveries as a metric (and ideally a synonym "delays"), and a date dimension for "last week". The SQL arrives in the response.tool_result event (content[0].json.sql); the prose answer arrives as response.text.delta events.

SolutionB1 · The role refused, not the agent

The agent plans the tool call, Analyst writes the SQL, and execution fails with an authorization error because the caller's role cannot read the tables. The agent reports the tool failure. Nothing in the agent or semantic view can widen access; only a grant can.

SolutionD1 · Target lag

The service's TARGET_LAG: a one-hour lag means an upload can take up to an hour to be searchable. Check the service's refresh status before suspecting the index; lower the lag only if the use case needs it, since refreshes cost warehouse credits.

SolutionM1 · Analyst inside a guarded graph

A node calls POST /api/v2/cortex/analyst/message with the semantic view and the question; if the response is a suggestions block, interrupt() with the options; otherwise run validate from Lesson 14.80 on sql.statement (allowlist, tenant filter, row cap); if confidence.verified_query_used is null, interrupt() for approval; execute with a read-only role and STATEMENT_TIMEOUT_IN_SECONDS on the warehouse; summarize from the rows only, disclosing empty or truncated results.

Explain the mechanismHow would you build an agent over data in Snowflake, and what does Cortex give you that a hand-built agent does not?

Worked answer. A semantic view (metrics, dimensions, synonyms, verified queries) for Cortex Analyst, a Cortex Search service over documents, and a Cortex Agent that orchestrates both plus UDFs or procedures for actions, with an orchestration budget. Users reach it in CoWork or through the Agent Run API; outside agents through the managed MCP server. What you get for free: execution under the caller's role (so masking and row access policies apply to every tool call), managed hybrid retrieval, a semantic layer shared with BI, usage views and budgets, and observability in Snowsight. What you still own: the semantic view's quality, evaluation on verified queries, and any write action's checks.

A plausible wrong answer. "Export the tables to a vector database and build RAG." It copies governed data out of the governance boundary and loses the semantic layer.

Follow-ups. Where do most Analyst errors come from? How do you keep an agent inside a credit budget?

Debug a failureA Cortex Agent answers a revenue question with a different number than the finance dashboard. Walk me through it.

Worked answer. Read the SQL in the response.tool_result event. Usually the semantic view's metric differs from the dashboard's definition (gross versus net, a missing filter), or the agent picked a synonym that maps to another metric. Fix the semantic view, add a verified query for the exact question, and add it to the evaluation set. If the SQL is right and the numbers differ, check the role: masking or row access policies may hide rows from the agent's role that the dashboard's service account sees.

A plausible wrong answer. "Lower the temperature." Definitions, not sampling, cause this.

Follow-ups. How would you catch this before release?

Defend a designCortex Agents or LangGraph on top of Snowflake?

Worked answer. Cortex Agents when the work is mostly questions over governed Snowflake data and documents: Analyst and Search are built in, roles apply automatically, data never leaves, and business users get it through CoWork. LangGraph when you need custom control flow, long-running stateful workflows with approvals, many non-Snowflake tools, or a model outside Snowflake's catalog. The common hybrid: Cortex as governed data tools (through the managed MCP server) inside a LangGraph orchestrator that handles the broader workflow, hosted in Snowpark Container Services if the data must stay inside the account.

A plausible wrong answer. "Always LangGraph, for flexibility." Flexibility you do not need costs you the governance and the semantic layer you get for free.
