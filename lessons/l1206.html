Why this came about

Agents act on behalf of users, which created a classic security problem: an agent with broad access can be tricked into acting for the wrong person (the confused deputy). Identity, delegated permissions and governed tool platforms became essential parts of production agent design.

In plain words first
Every action has an owner

An agent acts on someone's behalf, so every tool call must answer: who is the agent, which user is it acting for, and is that user allowed to do this? A tool platform centralizes the answers: tools are registered with owners and risk levels, credentials are issued per user and per call with narrow scopes, permissions are checked in code at each call, and every action is logged.

Agents fail safely when their permissions are designed, and dangerously when their permissions are inherited. The common pattern in early deployments is the dangerous one: the agent runs with a developer's personal token, a static API key in an environment variable, or an over-privileged service account. Every tool call then carries more rights than the task needs, nobody can tell the agent's actions from a person's, and a single prompt injection or confused plan can use all of them.

From the field
A valid key deleted production

Speakeasy's Sagar Batchu tells the story of a coding agent that tried to fix a problem in staging and deleted a production database and its backup instead. It did this with valid credentials: nothing was hacked, and every individual permission check passed. His conclusion for regulated industries is a control layer in which every action is tied to an identity, checked against policy in real time, never allowed to exceed its owner's rights, and recorded for compliance (talk, AI Engineer, 21 min). Keycard's Kamil Potrec lists what proper agent authentication requires: per-agent identity, delegation, short-lived scoped credentials, federation with legacy systems, policy and audit, and he compares SDK-based and gateway-based ways to keep credentials out of the agent's reach (talk, 19 min).

Who is acting: three identities on every call

Identity Question it answers Example
Subject (the user, or the business owner of a background job) On whose behalf? Priya, support agent, tenant shopkart-in
Actor (the agent, as a registered workload) Which software is doing it? refund-agent version 0.4, registered by payments-ai
Session (the run) Which task, approved by whom? Run r-8812, refund approved by Priya at 10:42

The credential presented to a tool should carry all three. OAuth 2.0 Token Exchange (RFC 8693, introduced in Lesson 15.25) is the standard way: the agent exchanges the user's token for a new, short-lived token whose sub is the user and whose act (actor) claim names the agent. The tool, or the gateway in front of it, sees both and can decide accordingly.

The effective permission of the call is the intersection of three sets:

  1. what the user is allowed to do (their own role and data),
  2. what the agent is allowed to do (its declared purpose and scopes in the registry),
  3. what this task needs (the scopes requested for this run).

An agent should never be able to do something the user could not do themselves, and a user should not gain powers by asking an agent.

Hands-on · Delegated, scoped, short-lived credentials

A delegated credential is a short-lived token that lets the agent act for one user, with a subset of that user's rights, for one purpose. The code below mints and verifies a token the way a token-exchange service would. Real systems use signed JWTs and a standard OAuth server; the logic is the same: intersect scopes, bind the audience, set a short expiry, and name the actor.

import base64, hashlib, hmac, json

SIGNING_KEY = b"demo-only-signing-key"   # a real service uses asymmetric keys from a KMS

USERS = {"priya": {"tenant": "shopkart-in", "scopes": {"orders:read", "refunds:write", "customers:read"}},
         "dev-ravi": {"tenant": "shopkart-in", "scopes": {"orders:read", "db:admin"}}}
AGENTS = {"refund-agent": {"owner": "payments-ai", "scopes": {"orders:read", "refunds:write"}},
          "fixit-agent": {"owner": "platform", "scopes": {"db:admin", "orders:read"}}}

def b64(d: dict) -> str:
    return base64.urlsafe_b64encode(json.dumps(d, sort_keys=True).encode()).decode().rstrip("=")

def exchange(user: str, agent: str, requested: set, audience: str, now: int, ttl: int = 300) -> str:
    """Token exchange: the user delegates to the agent, for one audience, for a few minutes."""
    granted = USERS[user]["scopes"] & AGENTS[agent]["scopes"] & requested
    if not granted:
        raise PermissionError(f"no overlap between {user}, {agent} and the requested scopes")
    claims = {"sub": user, "act": {"sub": agent}, "tenant": USERS[user]["tenant"], "aud": audience,
              "scope": sorted(granted), "iat": now, "exp": now + ttl}
    body = b64(claims)
    sig = hmac.new(SIGNING_KEY, body.encode(), hashlib.sha256).hexdigest()[:32]
    return f"{body}.{sig}"

def verify(token: str, audience: str, needed: str, now: int) -> dict:
    body, sig = token.rsplit(".", 1)
    if not hmac.compare_digest(sig, hmac.new(SIGNING_KEY, body.encode(), hashlib.sha256).hexdigest()[:32]):
        raise PermissionError("bad signature")
    claims = json.loads(base64.urlsafe_b64decode(body + "=" * (-len(body) % 4)))
    if claims["aud"] != audience:
        raise PermissionError(f"token is for {claims['aud']}, not {audience}")
    if now >= claims["exp"]:
        raise PermissionError("token expired")
    if needed not in claims["scope"]:
        raise PermissionError(f"scope {needed} not granted (has {claims['scope']})")
    return claims

t = exchange("priya", "refund-agent", {"orders:read", "refunds:write", "customers:read"}, "payments-api", now=1_000)
c = verify(t, "payments-api", "refunds:write", now=1_060)
print("granted:", c["scope"], "| sub:", c["sub"], "| act:", c["act"]["sub"], "| expires in", c["exp"] - 1_060, "s")
for label, args in [("wrong audience", ("orders-api", "orders:read", 1_060)),
                    ("expired", ("payments-api", "refunds:write", 1_400)),
                    ("scope the agent lacks", ("payments-api", "customers:read", 1_060))]:
    try:
        verify(t, *args)
    except PermissionError as e:
        print(f"{label:22} -> denied: {e}")
try:
    exchange("priya", "fixit-agent", {"db:admin"}, "orders-db", now=1_000)
except PermissionError as e:
    print(f"{'user lacks db:admin':22} -> denied: {e}")
What you should see
granted: ['orders:read', 'refunds:write'] | sub: priya | act: refund-agent | expires in 240 s
wrong audience         -> denied: token is for payments-api, not orders-api
expired                -> denied: token expired
scope the agent lacks  -> denied: scope customers:read not granted (has ['orders:read', 'refunds:write'])
user lacks db:admin    -> denied: no overlap between priya, fixit-agent and the requested scopes

Two things to notice. customers:read was requested and Priya has it, but the refund agent's registered purpose does not include it, so it is not granted. And Priya cannot hand the fixit agent db:admin because she does not have it herself: the agent cannot exceed its user.

Watch out
Keep credentials out of the model's reach

The model should never see a token, key or password, in its context, in a tool result or in a file it can read. Hold credentials in the runtime or the gateway and attach them to outgoing calls there. Anything in context can be repeated, logged, or extracted by an injected instruction.

Hands-on · A policy decision point in front of every tool call

Scopes say what is possible. Policy says what is allowed now, given the arguments, the environment, the amount and the risk. Put a policy decision point (PDP) between the harness and the tools, ideally in the gateway so every framework gets it. It returns one of three answers, always with a reason: allow, deny, or require approval.

from dataclasses import dataclass

@dataclass
class Call:
    agent: str
    tool: str
    effect: str          # read, write, external, destructive
    env: str             # dev, staging, prod
    args: dict
    user_role: str = "support"

RULES = [
    # (name, condition, decision, reason) - evaluated in order; the first match wins
    ("no-destructive-prod", lambda c: c.effect == "destructive" and c.env == "prod", "deny",
     "destructive actions in production are never automated"),
    ("env-mismatch", lambda c: c.args.get("target_env") not in (None, c.env), "deny",
     "the call targets a different environment than the task"),
    ("refund-limit", lambda c: c.tool == "issue_refund" and c.args.get("amount_inr", 0) > 5000, "approve",
     "refunds over 5,000 INR need a person"),
    ("external-send", lambda c: c.effect == "external" and c.args.get("recipients", 1) > 20, "approve",
     "bulk sends need review"),
    ("writes-in-prod", lambda c: c.effect == "write" and c.env == "prod" and c.agent not in ("refund-agent",), "approve",
     "this agent is not approved for unattended writes in production"),
    ("default-allow", lambda c: True, "allow", "within policy"),
]

def decide(c: Call):
    for name, cond, decision, reason in RULES:
        if cond(c):
            return decision, name, reason

calls = [
    Call("refund-agent", "get_order", "read", "prod", {"order_id": "A-1001"}),
    Call("refund-agent", "issue_refund", "write", "prod", {"order_id": "A-1001", "amount_inr": 1200}),
    Call("refund-agent", "issue_refund", "write", "prod", {"order_id": "A-1002", "amount_inr": 18000}),
    Call("fixit-agent", "drop_database", "destructive", "prod", {"db": "orders", "target_env": "prod"}),
    Call("fixit-agent", "restore_backup", "write", "staging", {"db": "orders", "target_env": "prod"}),
    Call("notify-agent", "send_email", "external", "prod", {"recipients": 4500}),
]
for c in calls:
    d, rule, why = decide(c)
    print(f"{d.upper():7} {c.agent:13} {c.tool:15} [{rule}] {why}")
What you should see
ALLOW   refund-agent  get_order       [default-allow] within policy
ALLOW   refund-agent  issue_refund    [default-allow] within policy
APPROVE refund-agent  issue_refund    [refund-limit] refunds over 5,000 INR need a person
DENY    fixit-agent   drop_database   [no-destructive-prod] destructive actions in production are never automated
DENY    fixit-agent   restore_backup  [env-mismatch] the call targets a different environment than the task
APPROVE notify-agent  send_email      [external-send] bulk sends need review

The fourth and fifth calls are the Speakeasy incident in miniature: the credentials would have worked, but the policy knows the task is about staging and refuses anything aimed at production, and it never lets an agent destroy production data unattended. Real deployments express these rules in a policy enginelater · 14.131 such as Open Policy Agent or Cedar, version them with the agent, and test them like code.

The tool platform: registry and gateway

When more than one team builds agents, tools become a shared platform. Run it like one:

Capability What it does Why it matters
Tool registry Every tool has an owner, a versioned contract (Lesson 14.109), an effect class, a risk tier and scopes Reviews happen once per tool, not once per agent
Review and approval New tools and breaking changes pass security and owner review before agents can see them Stops "temporary" admin tools reaching production agents
MCP gateway One entry point for agents to reach tools: authentication, token exchange, policy, rate limits, logging Every framework gets the same controls (Lesson 14.111 covers the gateway family)
Per-agent allow-lists Agents see only the tools their declared purpose needs Smaller tool lists are both safer and more accurate
Rate limits and quotas per tool Caps calls per agent, per user, per minute A looping agent cannot hammer a downstream system
Tool fingerprinting Pins the exact tool definitions an agent was evaluated with (Lesson 16.28) Detects a tool whose description or schema changed silently
Kill switches per tool Disables one tool for all agents in seconds The fastest containment in an incident (Lesson 14.121)

Hands-on · An audit log the agent cannot rewrite

Compliance teams ask two questions after an incident: what happened, and can you prove the record is complete? A hash chain answers the second. Each entry stores the hash of the previous one, so editing or deleting any entry breaks every hash after it. Store the log outside the agent's reach, and anchor the latest hash somewhere separate (a write-once bucket, a ledger table) every few minutes.

import hashlib, json

def append(log, event):
    prev = log[-1]["hash"] if log else "0" * 64
    body = json.dumps(event, sort_keys=True)
    log.append({"event": event, "prev": prev, "hash": hashlib.sha256((prev + body).encode()).hexdigest()})

def verify_chain(log):
    prev = "0" * 64
    for i, e in enumerate(log):
        expect = hashlib.sha256((prev + json.dumps(e["event"], sort_keys=True)).encode()).hexdigest()
        if e["prev"] != prev or e["hash"] != expect:
            return f"broken at entry {i}"
        prev = e["hash"]
    return f"intact ({len(log)} entries, head {prev[:12]})"

audit = []
append(audit, {"run": "r-8812", "sub": "priya", "act": "refund-agent", "tool": "get_order", "decision": "allow"})
append(audit, {"run": "r-8812", "sub": "priya", "act": "refund-agent", "tool": "issue_refund", "amount_inr": 1200, "decision": "allow"})
append(audit, {"run": "r-8813", "sub": "dev-ravi", "act": "fixit-agent", "tool": "drop_database", "decision": "deny"})
print("before:", verify_chain(audit))
audit[1]["event"]["amount_inr"] = 120          # someone "corrects" the record
print("after edit:", verify_chain(audit))
What you should see
before: intact (3 entries, head 17fbd27a06dc)
after edit: broken at entry 1

The standards behind these ideas

The code above uses plain Python so that each idea is visible. In a real platform the same ideas arrive as standards and products, and it helps to know the names when you read a vendor's documentation.

Idea in this lesson Standard or tool you will meet What it is
Proving who a user is OpenID Connect (OIDC) A sign-in layer on top of OAuth 2.0. It gives your app an ID token that says who the user is.
A token for one audience, with scopes OAuth 2.0 and 2.1 The framework for scoped, short-lived access tokens. MCP's authorization (Lesson 16.27) is built on it.
An agent acting for a user OAuth token exchange (RFC 8693) Swaps the user's token for a narrower one that names both the user (sub) and the agent acting for them (act).
An identity for a workload, not a person SPIFFE and SPIRE; cloud workload identity Short-lived, automatically rotated identities for services and agents, so that no long-lived secret sits in a config file.
Rules by role Role-based access control (RBAC) Permissions attached to roles such as "support agent".
Rules by attributes Attribute-based access control (ABAC) Permissions decided from attributes of the user, the resource and the request, such as tenant, amount or time of day.
Policy outside the code Open Policy Agent (Rego), Cedar Languages and engines for a policy decision point. Bedrock AgentCore Policy (Lesson 14.131) uses Cedar.
A log that shows tampering Hash-chained or append-only logs; write-once storage Each entry includes a hash of the one before it, or the store refuses edits.

Exercises

Predict before you run

The agent calls the order API with a service account that can read all orders. A customer asks about "my orders". What should the call use instead? (Solution P1.)

Break it on purpose

Store tool credentials in the agent's prompt so it can pass them to tools. What leaks? (Solution B1.)

Debugging exercise

An audit cannot tell which user caused an agent's refund. What is missing in the tool platform? (Solution D1.)

Make it your own

Design the permission model for ShopKart's tools: who can call each tool, with which scope, and which need approval. (Solution M1.)

Solutions

SolutionP1 · Act as the user

A token scoped to the signed-in customer (delegated access, on-behalf-of), so the API enforces that the customer sees only their orders.

SolutionB1 · Secrets out of the context

Credentials can be echoed in answers, logs and traces, and extracted by injection. Keep secrets in the tool layer, never in the model's context.

SolutionD1 · Identity in every call

The user's identity propagated to tools and logged with each action, alongside the agent and session IDs.

SolutionM1 · A permission matrix

Rows for tools, columns for roles (customer, support agent, supervisor), cells with scope (own orders, all orders) and approval rules. Enforce in the tool layer.

Check your understanding

Explain the mechanismHow should identity and permissions work for agent tools?

Worked answer. Authenticate the user, propagate their identity to tools with scoped, short-lived tokens (delegation), authorize each call in the tool layer by user and policy, keep secrets out of the model's context, give the agent its own identity for auditing, and log who did what through which agent.

A plausible wrong answer. "Give the agent an admin account and good instructions." Instructions do not enforce permissions.

Follow-ups. What is the confused deputy problem?

Debug a failureAn agent's tool calls fail with 403 for some users only. What do you check?

Worked answer. Those users' roles and scopes, token audience and expiry, and whether delegation is configured for their identity provider. Compare a working and failing token.

A plausible wrong answer. "The API is flaky." Permission failures are deterministic.

Follow-ups. How would you test permissions across roles?

Defend a designOne shared tool platform for all agents, or tools per agent?

Worked answer. A shared platform for common tools with central identity, policy and logging, and agent-specific tools owned by their teams on the same platform. It avoids each team reinventing authorization.

A plausible wrong answer. "Per agent, for speed." Then permissions drift and audits are impossible.

Follow-ups. What would the platform's API look like?
