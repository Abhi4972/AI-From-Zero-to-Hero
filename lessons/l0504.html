Why this came about

Much knowledge lives only in documents, and extracting entities and relations from text used to need custom models for each domain. From 2023, language models made general extraction feasible, but brought their own errors, so validation, entity resolution and provenance became essential steps.

In plain words first
Drawing the map from text

Most knowledge is in documents, not tables. Building a graph from text means a model extracts entities and relationships under a fixed schema, then you validate them, resolve different mentions of the same thing into one node ("Acme Corp", "ACME", "Acme Corporation"), and keep provenance: which passage each fact came from. Extraction is the expensive and error-prone part, so measure its quality before trusting the graph.

Hands-on · Extract facts from text under a schema

The extractor below uses patterns so that it runs offline and gives the same answer every time; in production the same function is an LLM call that receives the schema and a few examples and returns structured output (Lesson 11.2). Everything after extraction is identical either way.

import json, re, difflib

# 1. The schema comes first: what the graph may contain, and the questions it must answer.
SCHEMA = {
    "entities": {"Company", "Product", "Person", "Component"},
    "relations": {  # relation: (allowed source type, allowed target type)
        "MAKES": ("Company", "Product"), "SUPPLIES": ("Company", "Company"),
        "USES": ("Product", "Component"), "CEO_OF": ("Person", "Company"),
        "RECALLED": ("Company", "Component"),
    },
}
DOCS = {
    "d1": "Acme Electronics makes the Phone X. Acme Electronics' CEO is Rina Shah.",
    "d2": "Shenzhen Parts Ltd supplies Acme. The Phone X uses the BX-200 battery.",
    "d3": "In March 2026 Shenzhen Parts recalled the BX-200 battery.",
    "d4": "ACME Electronics makes the Earbuds Pro. The Earbuds Pro use the BX-200 battery.",
}

def extract(doc_id, text):
    """Stands in for an LLM call with a JSON schema. In production: give the schema and a few
    examples in the prompt, request structured output, and keep the source chunk with every fact."""
    rules = [(r"(.+?) makes the (.+?)[.,]", "MAKES"), (r"(.+?) supplies (.+?)\.", "SUPPLIES"),
             (r"(?:The )?(.+?) uses? the (.+?)[.]", "USES"), (r"(.+?)' CEO is (.+?)\.", "CEO_OF*"),
             (r"(?:In \w+ \d{4} )?(.+?) recalled the (.+?)\.", "RECALLED")]
    out = []
    for sent in re.split(r"(?<=\.) ", text):
        for pat, rel in rules:
            m = re.match(pat, sent)
            if m:
                a, b = m.group(1).strip(), m.group(2).strip()
                if rel == "CEO_OF*":
                    rel, a, b = "CEO_OF", b, a                      # reverse direction
                out.append({"source": a, "relation": rel, "target": b, "doc": doc_id, "text": sent})
                break
    return out

raw = [t for d, txt in DOCS.items() for t in extract(d, txt)]
print(len(raw), "raw facts, e.g.", json.dumps({k: raw[1][k] for k in ("source", "relation", "target", "doc")}))
What you should see
7 raw facts, e.g. {"source": "Rina Shah", "relation": "CEO_OF", "target": "Acme Electronics", "doc": "d1"}

Seven facts from four short documents, each with the document it came from. Notice the spellings: "Acme Electronics", "Acme", "ACME Electronics", and "Shenzhen Parts" with and without "Ltd". An LLM extractor produces exactly this kind of variation, plus occasional facts that break the schema.

Hands-on · Validate, resolve and load with provenance

The extractor's output is a list of proposed facts, and some will be wrong. To show the checks working, the first two lines add two deliberately bad facts of the kind a model produces. Then three steps run in order: validate each fact against the schema's allowed relations and types, resolve different spellings of the same company into one node, and load what survives, keeping for every edge the documents it came from.

# 2. Validate against the schema. Models make type errors; reject them before they enter the graph.
raw.append({"source": "BX-200 battery", "relation": "MAKES", "target": "Acme", "doc": "d2", "text": "(model error)"})
raw.append({"source": "Acme Electronics", "relation": "PARTNERS_WITH", "target": "Shenzhen Parts", "doc": "d2", "text": "(model error)"})

def typed(fact):
    if fact["relation"] not in SCHEMA["relations"]:
        return None, f"unknown relation {fact['relation']}"
    st, tt = SCHEMA["relations"][fact["relation"]]
    return (st, tt), None

# 3. Entity resolution: one node per real-world thing, however the text spelled it.
SUFFIXES = re.compile(r"\b(ltd|limited|inc|pvt|electronics)\b\.?", re.I)
def key(name):
    return re.sub(r"[^a-z0-9 ]", "", SUFFIXES.sub("", name.lower().replace("'s", ""))).strip()

canonical, aliases = {}, {}
def resolve(name, etype):
    k = (etype, key(name))
    if k in canonical:
        aliases[canonical[k]].add(name)
        return canonical[k]
    close = difflib.get_close_matches(k[1], [c[1] for c in canonical if c[0] == etype], n=1, cutoff=0.85)
    if close:
        canonical[k] = canonical[(etype, close[0])]
    else:
        canonical[k] = name                      # first spelling seen becomes the canonical name
    aliases.setdefault(canonical[k], set()).add(name)
    return canonical[k]

nodes, edges, rejected = {}, {}, []
def merge(fact):
    """MERGE semantics: create if absent, else attach the new evidence. Safe to run twice."""
    types, err = typed(fact)
    if err:
        rejected.append(err); return
    a, b = resolve(fact["source"], types[0]), resolve(fact["target"], types[1])
    if any(nodes.get(n, t) != t for n, t in [(a, types[0]), (b, types[1])]):
        rejected.append(f"type clash: {fact['source']} -{fact['relation']}-> {fact['target']}"); return
    nodes[a], nodes[b] = types
    edges.setdefault((a, fact["relation"], b), set()).add(fact["doc"])   # provenance: which documents say so

for _ in range(2):                               # loading twice must not duplicate anything
    for f in raw:
        merge(f)
print(f"{len(nodes)} nodes, {len(edges)} edges; rejected: {sorted(set(rejected))}")
for (a, r, b), docs in sorted(edges.items()):
    print(f"  ({a}:{nodes[a]})-[{r}]->({b}:{nodes[b]})  sources {sorted(docs)}")
print("aliases merged:", {k: sorted(v) for k, v in aliases.items() if len(v) > 1})
What you should see
6 nodes, 7 edges; rejected: ['type clash: BX-200 battery -MAKES-> Acme', 'unknown relation PARTNERS_WITH']
  (Acme Electronics:Company)-[MAKES]->(Earbuds Pro:Product)  sources ['d4']
  (Acme Electronics:Company)-[MAKES]->(Phone X:Product)  sources ['d1']
  (Earbuds Pro:Product)-[USES]->(BX-200 battery:Component)  sources ['d4']
  (Phone X:Product)-[USES]->(BX-200 battery:Component)  sources ['d2']
  (Rina Shah:Person)-[CEO_OF]->(Acme Electronics:Company)  sources ['d1']
  (Shenzhen Parts Ltd:Company)-[RECALLED]->(BX-200 battery:Component)  sources ['d3']
  (Shenzhen Parts Ltd:Company)-[SUPPLIES]->(Acme Electronics:Company)  sources ['d2']
aliases merged: {'Acme Electronics': ['ACME Electronics', 'Acme', 'Acme Electronics'], 'Shenzhen Parts Ltd': ['Shenzhen Parts', 'Shenzhen Parts Ltd']}

Two invented facts are rejected: a relation the schema does not have, and a battery that "makes" a company. Three spellings of Acme and two of Shenzhen Parts become one node each, and every edge lists the documents that support it. Loading twice changed nothing, which is what makes incremental updates and retries safe (the same idempotency rule as Lesson 14.111).

Watch out
Entity resolution can merge things that differ

Stripping "Electronics" merged "Acme" into "Acme Electronics" here, which is right for this corpus and wrong if Acme Foods exists. In production: normalize conservatively, match within the same entity type, use stronger keys where you have them (tax IDs, product codes, email domains), send uncertain matches (similarity between two thresholds) to a review queue, and keep an alias table so merges can be undone.

Hands-on · Measure quality, then answer the question

Before anyone relies on the graph, compare it with a small set of facts that a person has checked by hand. Precision is the share of the graph's facts that are right; recall is the share of the true facts that the graph contains. The code computes both, lists what was missed, and then uses the graph for the question that started the lesson.

# 4. Measure the graph against a small hand-checked sample before anyone relies on it.
GOLD = {("Acme Electronics", "MAKES", "Phone X"), ("Acme Electronics", "MAKES", "Earbuds Pro"),
        ("Rina Shah", "CEO_OF", "Acme Electronics"), ("Shenzhen Parts Ltd", "SUPPLIES", "Acme Electronics"),
        ("Phone X", "USES", "BX-200 battery"), ("Earbuds Pro", "USES", "BX-200 battery"),
        ("Shenzhen Parts Ltd", "RECALLED", "BX-200 battery"), ("Earbuds Pro", "MADE_IN", "India")}
got = set(edges)
tp = len(got & GOLD)
print(f"precision {tp / len(got):.2f} | recall {tp / len(GOLD):.2f} | missed: {sorted(GOLD - got)}")
orphans = [n for n in nodes if not any(n in (a, b) for a, _, b in edges)]
single_source = sum(len(d) == 1 for d in edges.values())
print(f"orphan nodes {len(orphans)} | facts with a single source {single_source} of {len(edges)}")

# 5. The question the graph exists for: which products are affected by the recall, and who makes them?
recalled = {b for a, r, b in edges if r == "RECALLED"}
affected = sorted({a for a, r, b in edges if r == "USES" and b in recalled})
makers = sorted({a for a, r, b in edges if r == "MAKES" and b in affected})
print("affected products:", affected, "| makers to notify:", makers)
What you should see
precision 1.00 | recall 0.88 | missed: [('Earbuds Pro', 'MADE_IN', 'India')]
orphan nodes 0 | facts with a single source 7 of 7
affected products: ['Earbuds Pro', 'Phone X'] | makers to notify: ['Acme Electronics']

Precision is perfect on this sample and recall misses one fact, because the schema has no MADE_IN relation: a schema gap, not an extraction error, and the fix is a schema decision. Every fact has a single source, which is a risk worth tracking: facts confirmed by several documents deserve more trust. Finally the competency question is answered by two hops: recalled component, products that use it, and their maker.

Facts that change: time in the graph

Real facts expire: a supplier changes, a CEO leaves, a price changes. Two practices keep a graph truthful:

  • Validity intervals on edges (valid_from, valid_to): a new fact closes the old one instead of overwriting it, so you can still answer "what was true when the order shipped?"
  • Record time (when the system learned the fact), separate from validity. Together they make the graph bi-temporal, the model used by Graphiti, the temporal knowledge graph behind Zep's agent memory (Lesson 14.45 builds a small one).

Exercises

Predict before you run

extract reads "Acme Pvt Ltd supplies the mixer motor". What should it output under the schema, and with what provenance? (Solution P1.)

Break it on purpose

Skip typed validation and load whatever the model extracts. A sentence mentions "Mumbai supplies the motor". What enters the graph? (Solution B1.)

Debugging exercise

"Acme Pvt. Ltd." and "ACME Private Limited" became two nodes. Using key and resolve, fix it. (Solution D1.)

Make it your own

Add a confidence score to each extracted fact and load only facts above a threshold, sending the rest to a review queue. (Solution M1.)

Solutions

SolutionP1 · Facts with sources

A fact like (Acme Pvt Ltd, SUPPLIES, mixer motor) with entity types, the document ID, the sentence, and the extraction time. Without provenance, wrong facts cannot be traced or removed.

SolutionB1 · Schema validation

A City node acting as a supplier, a fact the schema should reject. Validate entity and relation types against the schema before loading, and send violations to review.

SolutionD1 · Normalize before matching

Normalize names (case, punctuation, legal suffixes) in key, match on identifiers when available, and use fuzzy matching with a review threshold for the rest. Merges should be logged and reversible.

SolutionM1 · Confidence gates

Ask the extractor for a confidence, or combine signals (schema validity, repetition across documents, source reliability), and gate loading on it. Track the review queue's size and approval rate.

Check your understanding

Explain the mechanismHow do you build a knowledge graph from text?

Worked answer. Extract entities and relations under a fixed schema with an LLM, validate types, resolve entities against existing nodes (normalization, identifiers, fuzzy matching), merge with provenance for every fact, and review low-confidence facts. Evaluate extraction against labeled documents. Text adds coverage to structured sources but needs more checks.

A plausible wrong answer. "Ask the model to output a graph." Without a schema, validation and resolution, the graph becomes noisy and duplicated.

Follow-ups. How do you measure extraction quality?

Debug a failureThe graph has many near-duplicate entities. Where in the pipeline do you look?

Worked answer. Entity resolution: the normalization rules, missing identifiers, and the matching threshold. Sample duplicates to see why they did not match, then fix the rules and run a merge job with logging.

A plausible wrong answer. "Ask the model to deduplicate the whole graph." Systematic rules and identifiers are cheaper and auditable.

Follow-ups. How would you make merges reversible?

Defend a designLLM extraction or a classic NER pipeline?

Worked answer. LLMs for flexible schemas, varied documents and relations, with validation; classic NER and rules for high-volume, narrow extraction where cost and consistency matter. Many pipelines use rules or small models for entities and an LLM for relations.

A plausible wrong answer. "LLMs for everything." At scale, cost and inconsistency matter.
