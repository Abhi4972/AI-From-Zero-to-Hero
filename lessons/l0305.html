Why this came about

Agents that kept their state in memory lost everything on a crash, and could not wait for a person to approve an action. Saving the loop's state after every step, an idea from workflow engines and database transactions, made long runs recoverable and made human approval possible.

The problem: a run lives only in memory

Everything a run knows sits in the local variable messages inside run(). Two ordinary events break that. A deploy restarts the process halfway through a run. And an approval takes a supervisor an hour, while Lesson 14.57's approve must answer instantly. Here is the first one:

For a read that is waste. For a write it is how customers get charged twice, which Lesson 14.59's idempotency keys only partly cover.

Python refresher
Python refresher: what JSON can store

json.dumps handles dictionaries, lists, strings, numbers, booleans and None, and nothing else. Objects returned by an SDK (content blocks, response objects) must be converted to plain dictionaries first. pathlib.Path("runs") / "run-1.json" builds a file path, and .write_text / .read_text save and load it.

In plain words first
A saved game and a signature

If the agent's state lives only in memory, a crash or restart loses the run, and the agent cannot wait for a person's approval for hours. So the state of the loop (the messages, the step, what is pending) is saved after every step, keyed by a run ID. A run can then resume after a crash, and a risky action can stop, wait for a person's decision and continue later from the saved state.

Idea · The loop's state is data

Everything the loop needs to continue fits in one dictionary: the messages, the step count, the tokens used, a status, and any decisions people have made. Save it after every step and the loop can stop anywhere and resume anywhere.

import pathlib
from types import SimpleNamespace as NS
RUNS = pathlib.Path("runs"); RUNS.mkdir(exist_ok=True)

def as_dict(b):
    """Content blocks from the SDK or the stand-in, as plain JSON that can be saved."""
    if isinstance(b, dict): return b
    if b.type == "text": return {"type": "text", "text": b.text}
    return {"type": "tool_use", "id": b.id, "name": b.name, "input": b.input}

def decision_key(name, args):
    return f"{name}:{json.dumps(args, sort_keys=True)}"

class DurableAgent(IdempotentAgent):
    """The loop's state is data, saved after every step. A run can stop, wait for a person, and resume anywhere."""
    def save(self, state):
        (RUNS / f"{state['run_id']}.json").write_text(json.dumps(state, indent=1))

    def load(self, run_id):
        return json.loads((RUNS / f"{run_id}.json").read_text())

    def start(self, run_id, question, **kw):
        state = {"run_id": run_id, "status": "running", "step": 0, "used": 0, "decisions": {},
                 "messages": [{"role": "user", "content": question}]}
        self.save(state)
        return self.resume(run_id, **kw)

    def resume(self, run_id, crash_before_tools_at_step=None):
        state = self.load(run_id)
        self.run_id = run_id                                   # the same idempotency keys after a restart
        self.approve = lambda name, args: state["decisions"].get(decision_key(name, args), {}).get("approved", False)
        msgs = state["messages"]
        while state["status"] == "running":
            if msgs[-1]["role"] == "assistant":                # its tools have not run yet: run them, do not ask again
                calls = [NS(**b) for b in msgs[-1]["content"] if b["type"] == "tool_use"]
            else:
                if state["step"] >= self.max_steps:
                    state.update(status="stopped", answer="Stopped: step limit reached. A person will follow up."); break
                r = client.messages.create(model=MODEL, max_tokens=500, system=self.system,
                                           tools=[d for d, _ in self.tools.values()], messages=msgs)
                state["step"] += 1
                state["used"] += r.usage.input_tokens + r.usage.output_tokens
                if r.stop_reason != "tool_use":
                    state.update(status="done" if r.stop_reason == "end_turn" else "stopped", answer=r.content[-1].text); break
                msgs.append({"role": "assistant", "content": [as_dict(b) for b in r.content]})
                self.save(state)                               # checkpoint: the request is recorded before anything runs
                if crash_before_tools_at_step == state["step"]:
                    raise Crash("the pod was restarted by a deploy")
                calls = [b for b in r.content if b.type == "tool_use"]
            waiting = [as_dict(c) for c in calls if c.name in self.risky and decision_key(c.name, c.input) not in state["decisions"]]
            if waiting:                                        # nobody has decided yet: stop here and wait
                state.update(status="waiting_for_approval", pending=waiting); break
            msgs.append({"role": "user", "content": self.call_tools(calls)})
            self.save(state)                                   # checkpoint: the results are recorded
        self.save(state)
        return state

    def decide(self, run_id, approved, by, note=""):
        """Called by your approval screen, minutes or days later, in any process."""
        state = self.load(run_id)
        for c in state.pop("pending"):
            state["decisions"][decision_key(c["name"], c["input"])] = {"approved": approved, "by": by, "note": note}
        state["status"] = "running"
        self.save(state)
        return self.resume(run_id)

Three things make resume correct:

Detail Why
Save right after recording the model's request, before running tools After a crash, the request is on disk, so resuming runs its tools instead of asking the model again
If the last saved message is the assistant's, run its tools first That is exactly the state a crash before tools leaves behind
Keep run_id stable across restarts Lesson 14.59's idempotency keys come out the same, so a write repeated after a crash is recognized

Approvals that wait

With state on disk, an approval stops being a function call and becomes a state. When a risky call arrives with no decision, the run saves itself as waiting_for_approval with the pending call, and returns at once. The customer can be told the truth (a person is reviewing it) and no thread sits blocked.

# An approval that takes a person an hour: the run waits as data, not as a blocked thread
BANK.clear(); EXECUTED.clear(); lost_reply["next_call"] = False

The names were checked in the installed packages on 4 November 2026 (langgraph 1.2.18 with langgraph-checkpoint 4.3.1, openai-agents 0.24.0). In all of them, you still own where state is stored and for how long, what a person sees before deciding, who may decide, and what happens to runs nobody decides on.

What changes in production: store checkpoints in a database, not on local disk, so any replica can resume a run. Encrypt them, because they hold the whole conversation, personal data included. And give them a retention period like any other customer record (Lesson 15.26).

Check your mental model
  • ✗ "Checkpoints are only for crashes."
    ✓ They also make approvals, replays and debugging possible.
  • ✗ "A resumed run continues mid-function."
    ✓ It continues from the last saved step; anything that step had started may happen again.
  • ✗ "Approval can be a prompt instruction ('ask before refunding')."
    ✓ Approval must be enforced in code: the action does not run until the decision exists.

Solutions

SolutionP1 · Resume after a crash before tools

Three model requests (two before the crash, one after) and two tool executions (find_orders before the crash, get_order_status after). The second request is not repeated because it was saved before the crash, and resume sees an assistant message whose tools have not run. If the crash had come after the tools ran but before the results were saved, resume would run them again. That is harmless for reads, and for writes it is why the run_id and its idempotency keys must stay the same across restarts.

SolutionP2 · Saving SDK objects

TypeError: Object of type _Block is not JSON serializable (with the real SDK, the class is TextBlock or ToolUseBlock). Convert blocks to dictionaries before saving, as as_dict does. The real SDKs' blocks are Pydantic models, so block.model_dump() also works. Store the plain form, never pickled objects, so a checkpoint can be read by a newer version of your code.

SolutionD1 · A rejection the model never hears about

decide records approved: False, and on resume approve returns False. Agent.call_tool cannot tell "nobody decided" from "a person said no", so it returns its generic "needs a person's approval" error, and the model, reasonably, tells the customer to wait. Distinguish the two cases and say who decided and why:

# Solution D1: a rejection is a decision, and the model should be told who made it and why
class ClearDecisions(DurableAgent):
    def call_tool(self, c):
        state = self.load(self.run_id)
        d = state["decisions"].get(decision_key(c.name, c.input))
        if c.name in self.risky and d and not d["approved"]:
            return {"type": "tool_result", "tool_use_id": c.id, "is_error": True,
                    "content": f"declined by {d['by']}: {d['note']}"}
        return super().call_tool(c)

agent = ClearDecisions(system=SYSTEM, tools=work_tools, risky=risky)
agent.start("run-mixer-3", "My mixer arrived broken last week. Can I get a refund?")
print(agent.decide("run-mixer-3", approved=False, by="priya@shopkart.in", note="outside the 30-day window for damage")["answer"])

Sorry, I couldn't check that: declined by priya@shopkart.in: outside the 30-day window for damage

The model now knows the refund was declined and the reason, and can explain it to the customer. Error messages are part of the interface to the model: make them as specific as you would for a colleague.

SolutionM1 · Approvals that expire
# Solution M1: runs that wait too long are closed, with a message the app can send to the customer
from datetime import datetime, timedelta, timezone

def expire_waiting(now, max_wait=timedelta(hours=48)):
    closed = []
    for f in sorted(RUNS.glob("*.json")):
        state = json.loads(f.read_text())
        if state["status"] == "waiting_for_approval" and now - datetime.fromisoformat(state["waiting_since"]) > max_wait:
            state.update(status="expired", answer="Your request was not reviewed in time. Please contact us and we will pick it up.")
            f.write_text(json.dumps(state, indent=1)); closed.append(state["run_id"])
    return closed

state = DurableAgent(system=SYSTEM, tools=work_tools, risky=risky).start("run-mixer-4", "My mixer arrived broken last week. Can I get a refund?")
state["waiting_since"] = "2026-11-01T10:00:00+00:00"          # in real code, set when the run starts waiting
(RUNS / "run-mixer-4.json").write_text(json.dumps(state, indent=1))
print(expire_waiting(now=datetime(2026, 11, 4, 10, 0, tzinfo=timezone.utc)))

['run-mixer-4']

In real code, set waiting_since in resume when the status becomes waiting_for_approval, run expire_waiting on a schedule, and notify the customer and the queue owner. A run that nobody decides on is a support ticket nobody answered.

Check your understanding

Explain the mechanismHow do you make an agent survive a crash in the middle of a run?

Worked answer. Treat the run's state as data and checkpoint it after every step: the messages, the step count, budgets used, status and any pending decisions. Save right after recording the model's request and again after the tool results, keyed by a stable run ID. On restart, load the checkpoint: if the last message is a tool request whose results were not saved, run those tools, and otherwise call the model. Keep the run ID stable so idempotency keys for writes come out the same, and the provider recognizes a repeated write. Frameworks do this with checkpointers (LangGraphlater · 14.101) or saved run state (the OpenAI Agents SDK), and durable-execution engines do it for whole workflows.

A plausible wrong answer. "Catch the exception and retry the whole run." It repeats every model call and tool call, costs double, and repeats writes.

Follow-ups. Where do you store checkpoints? What if the code changes between the crash and the resume? How long do you keep them?

Debug a failureApproved refunds sometimes never complete. The approval screen shows "approved". What do you check?

Worked answer. Follow one run end to end. Did decide save the decision and set the status back to running, and did anything actually call resume afterwards? A common cause is an approval written to a database that no worker picks up, or a resume that failed and was not retried. Then check the resume itself: does it find the pending tool request and run it, or does it call the model again and get a different plan? Fix it by making the decision and the resume one step, or queue the resume durably, alert on runs that sit "approved but not running", and add a test that approves a run from a separate process.

A plausible wrong answer. "The model must have ignored the approval." The model never sees the approval unless your code resumes the run and runs the tool.

Follow-ups. How would you show the customer what is happening while the run waits? How do you stop two workers resuming the same run at once?

Defend a designWhy not keep the agent's thread blocked while it waits for the approval?

Worked answer. Approvals take minutes to days. A blocked thread holds memory and a connection, does not survive a deploy or a crash, and caps how many runs can wait at once. Saving the run as a waiting state and resuming it when the decision arrives frees all of that, survives restarts, lets any replica continue the run, and leaves an audit trail of who decided what. Blocking is fine only inside a single interactive session where a person answers in seconds, and even then I would rather use the same mechanism everywhere.

A plausible wrong answer. "Use a longer timeout." It just postpones the failure, and a deploy still drops every waiting run.

Follow-ups. What does the customer see while the run waits? What happens if the order changes while it waits, for example the customer cancels it?
