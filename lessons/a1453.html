Three Different Questions

In plain words first

Prototype, pilot and production answer different questions. A prototype asks whether the idea works at all, on recorded or fake data, and can be thrown away. A pilot asks whether it works safely for a named group with real data, limited authority and a way back. Production is when the organisation takes ongoing responsibility: an SLO, someone on call, security review, monitoring and a retirement plan. The risk is stage drift, where a prototype gains users, data or authority without gaining an owner. What production means and the readiness review are covered in Lesson 14.108, and pilot-to-value in 14.2 (linked above). This lesson stages the incident agent's next steps and makes the stage enforceable in code.

Stage Primary question
Prototype Can this mechanism produce the evidence at all?
Pilot Does it work safely with a bounded real audience and real conditions?
Production Can we own it continuously at the promised reliability and risk level?

A prototype can be technically complete and still be disposable. A pilot can use production data while remaining limited in audience and authority. Production begins when the organization accepts ongoing responsibility.

Prototype

Use a prototype when the unknown does not require real users or real data. Keep it:

  • discardable;
  • isolated;
  • narrow in behavior;
  • explicit about the learning question;
  • free of false operational guarantees.

Do not optimize architecture before the mechanism earns another stage.

Pilot

Use a pilot when the unknown requires real behavior, realistic data, or a real workflow, but consequence or readiness is not yet compatible with broad release.

A pilot needs:

  • a named audience;
  • a human owner;
  • bounded duration and authority;
  • audit and rollback;
  • outcome and guardrail thresholds;
  • exit criteria for expand, revise, or stop.

Production

Production needs more than deployment:

  • service level objective;
  • on-call and incident ownership;
  • security and privacy review;
  • cost and capacity controls;
  • rollback and recovery;
  • continuous monitoring;
  • a retirement path.

Stage Drift

Prototype code becomes dangerous when it acquires users, data, or authority without acquiring ownership. Mark prototype and pilot boundaries in configuration, access control, telemetry, and documentation. A warning banner is not enough.

The stage should be observable from the system itself.

The same idea as a formula

The lesson's rule as logic. With real users u, real data d, consequence c (1 to 5), reversibility r and operational readiness o:

stage=⎩⎨⎧​prototypeproductionpilot​¬u∧¬d(u∨d)∧o∧r∧c≤3otherwise.​

Counting the space. There are 2⋅2⋅5⋅2⋅2=80 input combinations. Prototype takes the 20 where u=d=false. Production takes 3⋅3⋅1⋅1=9: three ways to have real users or data, three consequence levels, reversible and ready. The other 51 are pilot. Any irreversible step, and any step with c≥4, stays in pilot forever.

Worked example
The incident agent's four steps
  • The 20-alert replay has no real users or data, so it is a prototype, which fits 14.52's "ambiguous, replay 20 more".
  • The evidence-on-approvals trial has a real team and real data, but operations are not ready, so it is a pilot.
  • Posting the diagnosis to every channel is real, c=2, reversible and ready, so it is production, with SLO, on-call and monitoring.
  • Running the rollback after approval is real and ready, but c=5 and irreversible, so it is a pilot, and it can never be anything else under this rule.

# This block continues from the one above. Make the stage observable from the system itself. (1) A data client
# that reads its stage from config and refuses what the stage does not allow (Exercise 3). (2) A drift check over
# eight weeks of a "prototype" service's telemetry, generated as a stand-in. (3) A pilot behind a flag, switched
# off, with a rollback receipt that proves the old behaviour is back (Exercise 5). No model; instant.
import hashlib, json, time
POLICY = {   # stage -> what the data client allows
    "prototype": {"sources": {"recorded"}, "write": False, "users": None},
    "pilot": {"sources": {"recorded", "production-read"}, "write": False, "users": {"team-pay-oncall"}},
    "production": {"sources": {"recorded", "production-read", "production-write"}, "write": True, "users": "all"},
}
class StageError(PermissionError):
    pass
class DataClient:
    def __init__(self, config):
        self.stage, self.audit = config["stage"], []
    def read(self, source, user):
        rule = POLICY[self.stage]
        ok = source in rule["sources"] and (source == "recorded" or rule["users"] in (None, "all") or user in rule["users"])
        self.audit.append({"stage": self.stage, "op": "read", "source": source, "user": user, "allowed": ok})
        if not ok:
            raise StageError(f"{self.stage} may not read {source} for {user}")
        return f"data from {source}"
    def write(self, target, user):
        ok = POLICY[self.stage]["write"]
        self.audit.append({"stage": self.stage, "op": "write", "target": target, "user": user, "allowed": ok})
        if not ok:
            raise StageError(f"{self.stage} may not write {target}")
print("(1) one data client, three stages")
for stage in ("prototype", "pilot", "production"):
    client = DataClient({"stage": stage})
    row = []
    for op, args in (("read", ("recorded", "dev")), ("read", ("production-read", "team-pay-oncall")),
                     ("read", ("production-read", "someone-else")), ("write", ("deploys", "team-pay-oncall"))):
        try:
            getattr(client, op)(*args); row.append("ok")
        except StageError:
            row.append("refused")
    print(f"   {stage:<11} recorded:{row[0]:<8} prod-read(pilot team):{row[1]:<8} prod-read(other):{row[2]:<8} write:{row[3]}")

print("\n(2) drift check on a service registered as 'prototype'")
WEEKS = [  # week, distinct users, data sources touched, owner on call?
    (1, 2, {"recorded"}, False), (2, 3, {"recorded"}, False), (3, 6, {"recorded"}, False),
    (4, 14, {"recorded", "production-read"}, False), (5, 31, {"recorded", "production-read"}, False),
    (6, 58, {"recorded", "production-read"}, False), (7, 90, {"production-read"}, False), (8, 120, {"production-read"}, False)]
REGISTERED = "prototype"
for week, users, sources, owner in WEEKS:
    flags = []
    if not sources <= POLICY[REGISTERED]["sources"]:
        flags.append(f"touches {sorted(sources - POLICY[REGISTERED]['sources'])}")
    if users > 10 and not owner:
        flags.append(f"{users} users and no on-call owner")
    print(f"   week {week}: {users:>3} users  {'DRIFT: ' + '; '.join(flags) if flags else 'within prototype bounds'}")

print("\n(3) pilot behind a flag, then rolled back")
FLAGS = {"attach_evidence_to_approval": True}
def approval_request(incident):
    body = {"incident": incident, "ask": "approve roll back?"}
    if FLAGS["attach_evidence_to_approval"]:
        body["evidence"] = {"service": "payments", "deploy": "d-311", "source": "catalog lookup"}
    return body
before = approval_request("INC-200")
FLAGS["attach_evidence_to_approval"] = False
after = approval_request("INC-200")
baseline = {"incident": "INC-200", "ask": "approve roll back?"}
digest = lambda d: hashlib.sha256(json.dumps(d, sort_keys=True).encode()).hexdigest()[:12]
receipt = {"flag": "attach_evidence_to_approval", "from": True, "to": False, "at": "pilot day 14",
           "behaviour_before": digest(before), "behaviour_after": digest(after), "baseline": digest(baseline),
           "restored": digest(after) == digest(baseline), "data_to_clean_up": "none: the pilot wrote no state"}
print("   " + json.dumps(receipt))

Reading this output

The stage is enforced, not announced. One DataClient reads its stage from config. The prototype reads only recorded data. The pilot also reads production data, but only for the named pilot team, and never writes. Production allows everything, and every attempt is written to the client's audit list.

Drift shows up in week 4. The service registered as a prototype starts reading production data and passes 10 users with no on-call owner. By week 8 it has 120 users. The check flags it from telemetry the system already emits, four weeks before anyone would notice.

The rollback has a receipt. Switching the flag off makes the approval request's hash match the baseline (restored: true), and the receipt records that the pilot left no state to clean up.

Part 1 of 2 · BuildDecision, choose_stage, required_controls, plan, examples

# Lesson program for selecting prototype, pilot, or production controls.
# Read: phases/14-agent-engineering/53-prototype-pilot-or-production/docs/en.md
# Reference: Boehm, A Spiral Model of Software Development and Enhancement, 1988.
# Reference: Fagerholm et al., Building Blocks for Continuous Experimentation, 2014.
# Run this file to generate outputs/stage-decisions.json.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class BuildDecision:
    unknown: str
    real_users_required: bool
    real_data_required: bool
    consequence: int
    reversible: bool
    operational_readiness: bool


def choose_stage(decision: BuildDecision) -> str:
    if not 1 <= decision.consequence <= 5:
        raise ValueError("consequence must be from one to five")
    if not decision.real_users_required and not decision.real_data_required:
        return "prototype"
    if not decision.operational_readiness or decision.consequence >= 4 or not decision.reversible:
        return "pilot"
    return "production"


def required_controls(stage: str) -> list[str]:
    controls = {
        "prototype": ["synthetic or recorded inputs", "discardable implementation", "learning question"],
        "pilot": ["limited audience", "rollback", "human owner", "audit trail", "exit criteria"],
        "production": [
            "service level objective",
            "on-call owner",
            "security review",
            "cost and capacity controls",
            "rollback",
            "recovery",
            "continuous monitoring",
            "retirement path",
        ],
    }
    if stage not in controls:
        raise ValueError("unknown stage")
    return controls[stage]


def plan(decision: BuildDecision) -> dict:
    stage = choose_stage(decision)
    return {"stage": stage, "decision": asdict(decision), "required_controls": required_controls(stage)}


def examples() -> list[BuildDecision]:
    return [
        BuildDecision("Can the service be identified from an alert?", False, False, 2, True, False),
        BuildDecision("Will engineers trust the recommendation?", True, True, 4, True, False),
        BuildDecision("Can the workflow meet its SLO?", True, True, 2, True, True),
    ]


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "stage-decisions.json"
    output.write_text(json.dumps([plan(item) for item in examples()], indent=2) + "\n", encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Solutions

SolutionP1 · Prototype, pilot, production, pilot

Prototype for the 20-alert replay, pilot for the approval trial, production for posting the diagnosis everywhere, and pilot for running the approved rollback.

Nine of 80 combinations reach production: real users or data, consequence 1 to 3, reversible and operationally ready. Under this rule, consequence 4 and 5 and every irreversible step stay in pilot permanently. That is the case to argue about when you adapt it.

SolutionB1 · A prototype that became production by drift

The prototype acquired users, production data and authority (a personal token on the deploy API) without acquiring an owner. It became production by drift, with none of production's controls: no SLO, no on-call, no security review, no retirement path.

Three controls would have shown it in week one: - Register the stage in config, with a data client that refuses production sources for a prototype. The personal token would never have worked. - Add a drift check over the telemetry it already emits, flagging production reads, or more than a handful of users with no on-call owner. - Make credentials service-scoped and issue them per stage, so the only way to reach production data is to pass the pilot gate with a named owner.

What You Keep

Keep outputs/stage-decisions.json. It records why each stage is justified and which controls must exist before the next one.

Break it on purpose

An engineer's weekend prototype, a chatbot over the incident wiki, is shared in a channel. Two months later 150 people use it, it reads the production deploy API with the engineer's personal token, and it is down during an outage with nobody on call. Using this lesson, what failed, and which controls would have made the drift visible in week one? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Production readiness reviews. Google SRE's engagement model gates new services with a readiness review covering SLOs, monitoring, capacity and on-call, before operational ownership changes hands.
  • Flags and kill switches. Feature-flag standards such as OpenFeature, and the vendors that implement them, put pilots behind flags with targeting, so a pilot is limited to a named audience and can be switched off without a deploy.
  • Risk-tiered AI governance. NIST's AI Risk Management Framework, which many organisations use for AI systems, ties the depth of controls to impact. Higher-consequence uses get more oversight, documentation and monitoring before broad use.
  • On your laptop: the stage rule, the stage-aware data client, the drift check and the rollback receipt are standard-library Python.

Sources: Google SRE book, The evolving SRE engagement model, OpenFeature, NIST AI Risk Management Framework.

Recap
What to keep from this lesson
  • Choose the stage by the question: does it work, is it safe in the real world, can we own it?
  • Each stage has required controls; production is ownership, not deployment.
  • Put the stage in config and access control, and refuse what the stage does not allow.
  • Watch for drift: users, data or authority growing without an owner.
  • A rollback ends with a receipt: the old behaviour is restored and the leftover state is accounted for.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Debug a failureYou discover that a weekend prototype you shared internally is now used every day by another team, with production data, and someone just reported an outage to you. Walk me through what went wrong before this moment and what you do in the first week.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The system drifted across stages. It gained users, data and authority without gaining ownership, and nothing in the system itself marked it as a prototype. In the first week I make the stage observable in configuration, access control, telemetry and documentation, cut the production data path until a named owner accepts it, and decide with that team whether the right next stage is a bounded pilot or a stop.

Three stages ask three questions.

Stage Primary question
Prototype Can this mechanism produce the evidence at all?
Pilot Does it work safely with a bounded real audience and real conditions?
Production Can we own it continuously at the promised reliability and risk level?

These are learning environments, not levels of polish. A prototype can be technically complete and still be disposable. Production begins when the organization accepts ongoing responsibility.

What went wrong.

The prototype was built for one question and had no false operational guarantees, which was right. The failure was stage drift: it acquired an audience, real data and the authority to affect another team's work, and nobody acquired ownership. A warning banner would not have prevented this. The stage has to be enforced by the system: a configuration flag that blocks production data, access control that limits the audience, telemetry that shows who uses it, and documentation that says what it is.

The first week.

  1. Stop the bleeding: block the production data path with a technical control, not a message.
  2. Name the stage in the system so anyone can see it.
  3. Meet the other team with the pilot requirements: a named audience, a human owner, bounded duration and authority, audit and rollback, outcome and guardrail thresholds, and exit criteria for expand, revise or stop.
  4. Decide. If no one will own it, the honest outcome is a stop, and the evidence it produced still counts.

What production would require.

A service level objective, on-call and incident ownership, security and privacy review, cost and capacity controls, rollback and recovery, continuous monitoring, and a retirement path. Deployment is not production. Ownership is.

Plausible wrong answers.

  • "Add a banner that says prototype." A banner does not stop data, users or authority from flowing in.
  • "Harden the prototype into the product since people already use it." Prototype code earned another stage only if the evidence says so; usage is not that evidence.
  • "Shut it down with no discussion." The evidence it produced is real; the decision owner needs options, not a surprise.

Follow-ups an interviewer may ask.

  • (level 3) The other team says the outage shows the tool is valuable. How do you answer? Expected: value is a reason to run a bounded pilot with an owner, not a reason to keep an unowned system on production data.
  • (level 3) Which technical control would have prevented the drift? Expected: a configuration or access control that refuses production data unless the stage is set to pilot or production by an owner.
  • (level 4) What is the first operational responsibility that makes a build production? Expected: someone accepts an on-call or incident ownership commitment; before that, the system has users but no owner.
  • (level 4) The team wants to skip the pilot and go straight to production. What evidence would justify that? Expected: low consequence, operational readiness, and measured outcome and guardrail results from a bounded real audience.
