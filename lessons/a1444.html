Why Agent Plans Fail

In plain words first

A plan is a small graph. Each work item says what changes, which repository lines justify it, what it waits for, and which command proves it is done. From that graph you get the order (waves: items in the same wave can run together), a check before any edit (missing receipts, unknown dependencies, cycles), and a way to resume after an interruption. System-design method and estimates are covered in Zero to Agents 12.3 (linked above). This lesson asks a small model for plans, runs them through the lesson's validator, and then executes a hand-written plan across two sessions.

Weak plans repeat the request in future tense:

  1. Update the API.
  2. Add tests.
  3. Update documentation.

Nothing in that list says what was found, why those files are correct, which contract changes first, or what can happen concurrently. An agent can follow every step and still create rework.

A strong plan makes five commitments for each work item:

Commitment Purpose
Identifier Stable reference for dependencies and handoff
Change The smallest behavior or contract change
Evidence Repository facts that justify the change
Dependencies Work that must be true first
Proof The exact check that closes the item

Plan the Contract Before Its Implementations

When multiple surfaces depend on the same behavior, define the behavior first. Tests, implementation, documentation, and integration can then share one contract instead of inventing four versions.

The graph exposes safe concurrency. Implementation and documentation can proceed together after the contract is fixed. Integration waits for both.

Evidence Changes the Plan

Repository evidence is not decoration. It should be capable of changing the work:

  • An existing helper removes a planned new abstraction.
  • A compatibility test forces a migration step.
  • A deployment constraint moves a schema change into another task.
  • A public response type changes the order of implementation and documentation.

If the evidence cannot change the plan, it is probably not evidence for that decision.

Design for Interruption

Coding-agent sessions end unexpectedly. A resumable plan has work items small enough that another session can determine:

  • which item is complete;
  • which proof ran;
  • which artifacts changed;
  • which dependencies are now unblocked;
  • what the next safe item is.

Do not encode state only in checked boxes inside a chat. Store the plan next to the work.

Plan Validation

Reject the plan before execution when:

  • an identifier is duplicated;
  • a work item has no evidence;
  • a work item has no proof;
  • a dependency names an unknown item;
  • the graph contains a cycle;
  • the first irreversible action occurs before the relevant uncertainty is resolved.

The first five checks are mechanical. The last requires judgment and should be called out explicitly.

The same idea as a formula

Waves are levels of the graph. An item's wave is one more than the deepest wave among its dependencies:

w(i)=1+j∈deps(i)max​w(j),w(i)=1 if deps(i)=∅.

A cycle has no finite w, which is why execution_waves() stops on one.

Parallel time is the sum of the slowest item per wave. With durations ti​,

Tserial​=i∑​ti​,Twaves​=k∑​i∈Wk​max​ti​.

The number of waves is the length of the longest dependency chain, the critical path of PERT and CPM. No amount of parallel work makes the plan shorter than that chain.

Worked example
The lesson's four items
  • Dependencies: implementation and docs need contract; integration needs both. Waves: [contract], [docs, implementation], [integration].
  • Say contract takes 5 minutes, implementation 20, docs 10 and integration 5. Serial: 5+20+10+5=40. By waves: 5+max(20,10)+5=30.
  • The critical path is contract → implementation → integration, 30 minutes. Speeding up docs saves nothing; speeding up implementation does.
  • Add a cycle, say contract depends on integration, and no item ever has all its dependencies done. validate() reports the cycle before anything runs.
Check your mental model
  • ✗ "validate() passing means the plan is good."
    ✓ It checks structure only. A plan whose proof is the word "None" and whose receipts point nowhere passed it.
  • ✗ "Any receipt that names a real line is evidence."
    ✓ The line must support the claim. A real line number on an unrelated line is still decoration.
  • ✗ "The proof is a description of the result."
    ✓ The proof is a command or observation someone else can run.
  • ✗ "A checked box in chat records progress."
    ✓ Store the plan and its state next to the work. Session 2 resumed from two files.

def chat(prompt, n=500, k=1, temp=0.7):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    torch.manual_seed(0)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=k > 1, temperature=temp if k > 1 else None,
                           top_p=0.95 if k > 1 else None, top_k=None, num_return_sequences=k)
    return [tok.decode(o[ids.shape[1]:], skip_special_tokens=True) for o in out]

def receipt_ok(ev):
    m = re.match(r"\s*([\w./-]+):(\d+)", str(ev))
    return bool(m) and m.group(1) in REPO and 1 <= int(m.group(2)) <= len(REPO[m.group(1)].splitlines())

def to_items(text):
    m = re.search(r"```(?:json)?\s*\n(.*?)(?:```|$)", text, re.S)
    data = json.loads(m.group(1) if m else text)
    if isinstance(data, dict):
        data = [data] if "id" in data else next((v for v in data.values() if isinstance(v, list)), [data])
    as_tuple = lambda v: tuple(str(x) for x in v) if isinstance(v, list) else ((str(v),) if v else ())
    return [WorkItem(str(d.get("id", "")), str(d.get("change", "")), as_tuple(d.get("evidence")),
                     as_tuple(d.get("depends_on")), str(d.get("proof") or "")) for d in data if isinstance(d, dict)]

def prove(item):
    cmd = item.proof.split("  (")[0]
    p = subprocess.run(cmd, shell=True, cwd=root, capture_output=True, text=True, timeout=60)
    expect_fail = "expected to FAIL" in item.proof
    return (p.returncode != 0) if expect_fail else (p.returncode == 0), p.returncode

STATE = root / "plan-state.json"
lock = threading.Lock()
def record(item_id, **kw):
    with lock:
        state = json.loads(STATE.read_text()) if STATE.exists() else {}
        state.setdefault(item_id, {}).update(kw)
        STATE.write_text(json.dumps(state, indent=1))

class Interrupted(Exception):
    pass

def run_item(item, cut_after_edit=False, docs_code="email_taken"):
    record(item.id, status="started")
    edit(item.id, docs_code)
    record(item.id, status="edited")
    if cut_after_edit:
        raise Interrupted(item.id)
    ok, rc = prove(item)
    record(item.id, status="proved" if ok else "proof failed", proof=item.proof.split("  (")[0], exit_code=rc)
    return item.id, ok

# Lesson program for evidence-based planning and dependency scheduling.
# Read: phases/14-agent-engineering/44-plan-from-evidence/docs/en.md
# Reference: PERT, U.S. Navy Special Projects Office, 1958.
# Reference: CPM, Kelley and Walker, Eastern Joint Computer Conference, 1959.
# Run this file to generate outputs/evidence-plan.json.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class WorkItem:
    id: str
    change: str
    evidence: tuple[str, ...]
    depends_on: tuple[str, ...]
    proof: str


def validate(items: list[WorkItem]) -> list[str]:
    issues: list[str] = []
    ids = [item.id for item in items]
    if len(ids) != len(set(ids)):
        issues.append("work item ids must be unique")
    known = set(ids)
    has_unknown_dependency = False
    for item in items:
        if not item.evidence:
            issues.append(f"{item.id} has no repository evidence")
        if not item.proof.strip():
            issues.append(f"{item.id} has no proof command")
        missing = sorted(set(item.depends_on) - known)
        if missing:
            has_unknown_dependency = True
            issues.append(f"{item.id} depends on unknown items: {', '.join(missing)}")
    if not has_unknown_dependency:
        try:
            execution_waves(items)
        except ValueError as error:
            issues.append(str(error))
    return issues


def execution_waves(items: list[WorkItem]) -> list[list[str]]:
    known = {item.id for item in items}
    for item in items:
        missing = sorted(set(item.depends_on) - known)
        if missing:
            raise ValueError(f"{item.id} depends on unknown items: {', '.join(missing)}")
    remaining = {item.id: set(item.depends_on) for item in items}
    waves: list[list[str]] = []
    completed: set[str] = set()
    while remaining:
        ready = sorted(item_id for item_id, deps in remaining.items() if deps <= completed)
        if not ready:
            cycle = ", ".join(sorted(remaining))
            raise ValueError(f"dependency cycle among: {cycle}")
        waves.append(ready)
        completed.update(ready)
        for item_id in ready:
            del remaining[item_id]
    return waves


def plan_document(items: list[WorkItem]) -> dict:
    issues = validate(items)
    return {
        "status": "ready" if not issues else "blocked",
        "issues": issues,
        "waves": execution_waves(items) if not issues else [],
        "items": [asdict(item) for item in items],
    }

Use It with a Coding Agent

Ask the agent to produce the plan before it changes files. Review the plan for three things:

  1. Every path and behavior claim has a repository receipt.
  2. Every item has one clear completion proof.
  3. The graph delays expensive or irreversible work until the uncertainty it depends on is resolved.

Approve the plan, not a vague promise to be careful.

Exercises

  1. Add a migration item that requires explicit human approval.
  2. Create a cycle and explain the hidden product disagreement behind it.
  3. Split one item that has two proof commands.
  4. Add a work item that can run in the second wave without touching either existing branch.
  5. Render the plan as Markdown while keeping JSON as the source of truth.

Solutions

SolutionP1 · Structure passes; substance does not

One of four passed validate(), and it was the worst plan: a single item whose receipts point at no real line and whose proof is the string None. The other three were rejected because they used file names as dependencies. Only one plan had a proof you could run.

The validator does what it promises, a structural check. Whether receipts support claims and proofs are commands is a second check, and you have to write it.

SolutionB1 · Contract first, proof per item

The plan named three activities and no contract. It should have started with a contract item: the exact behaviour, meaning 409 with {"code": "email_taken", "message": ...} and 201 kept for new accounts. That item needs receipts (the create_account return line, the envelope rule in docs/api.md) and a proof that the new test is red.

The implementation and docs items both depend on the contract, so they run in the same wave against the same code name. Each has its own proof: the unit tests for the code, and a docs check that every error code the code returns is documented. Integration waits for both. With that plan, the docs worker's duplicate_email would have failed its proof in wave 2, before any release.

What You Keep

Keep outputs/evidence-plan.json. It becomes the delegation contract in the next lesson.

Break it on purpose

An agent posts a plan: "1. Update create_account to reject duplicates. 2. Add tests. 3. Update docs." The plan is approved. Two parallel workers take items 1 and 3; the docs worker documents a duplicate_email code, while the implementation returns email_taken. Tests pass, the docs are wrong, and nobody notices for a release. Using this lesson, what should the plan have contained? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Plans as files next to the work. Anthropic's long-running harness keeps a JSON feature list in which each feature starts failing and is marked passing only after testing, plus a progress file and git commits. A new session reads them first.
  • Plan, then approve. Claude Code's plan mode proposes a plan without editing until you approve it. Its task list then tracks the items through the session.
  • Tasks from specs. GitHub Spec Kit derives tasks.md from the plan and marks which tasks can run in parallel. Kiro's tasks.md holds discrete, trackable tasks tied to its requirements.
  • On your laptop: execution_waves() and the resume logic are standard-library Python. The model step runs on CPU with the 0.5B model.

Sources: Anthropic, Effective harnesses for long-running agents, Claude Code, Common workflows, GitHub Spec Kit, Kiro, Specs.

Recap
What to keep from this lesson
  • Each work item: id, change, evidence, dependencies, proof.
  • Waves come from the dependency graph; the critical path bounds the time.
  • Put the contract first, so parallel workers share one version of it.
  • validate() checks structure. Check receipts and proofs against the repo yourself.
  • Keep plan and state on disk, so the next session knows what was proved.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismYour session ends without warning in the middle of a multi-step change, and a colleague picks it up the next morning. What must they be able to find, and where?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. They need to see which items are done, which proof ran for each one, which files changed, which dependencies are now unblocked, and what the next safe item is. That state lives next to the work, in the repository, as small items with explicit proof, not as checked boxes inside a chat.

Design for interruption.

Sessions end unexpectedly. A resumable plan has work items small enough that another person, or another agent, can determine the state of each one from the artifacts alone. The five things they must be able to read:

  • which item is complete;
  • which proof ran and what it returned;
  • which artifacts changed;
  • which dependencies are now unblocked;
  • what the next safe item is.

Why chat is the wrong place.

A checked box in a conversation says that someone believed an item was done. It does not say which command proved it or which files it touched. The next person either trusts the box or redoes the work. A plan stored next to the code, with one identifier per item and the proof command written down, lets them verify instead of trust.

The habit.

I stop at item boundaries when I can. When I cannot, the plan still shows the last proof that passed, so the resume point is the first item whose proof has not run.

Plausible wrong answers.

  • "Write a summary message at the end of the session." The session can end before the summary; the state must exist as the work proceeds.
  • "The git log is enough." Commits show what changed, not which proof ran or which item is next.
  • "Only the person who started can finish it." That is the failure the plan should prevent.

Follow-ups an interviewer may ask.

  • (level 1) Where do you keep the plan? Expected: in the repository next to the work, as the source of truth, with any rendering such as a Markdown view generated from it.
  • (level 2) An item is marked done but has no proof recorded. What does the colleague do? Expected: treat it as not done and run its proof; a box without proof is a belief.
  • (level 2) Why does item size matter for resumption? Expected: a small item either finished or did not; a large half-done item forces the next person to reconstruct where it stopped.

Debug a failureA teammate, or a coding agent, hands you this plan for a change to a public API: update the endpoint, add tests, update the documentation. They want approval to start. What do you ask for before you say yes, and what would make you reject the plan outright?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. That list repeats the request in future tense. I ask for five things on each item: a stable identifier, the smallest change, the repository facts that justify it, the items it depends on, and the exact check that closes it. I reject a plan with a duplicate identifier, an item without evidence or proof, a dependency on an unknown item, a cycle, or an irreversible step scheduled before the uncertainty it depends on is resolved.

Why the three-line plan fails.

Nothing in it says what was found in the repository, why those files are the right ones, which contract changes first, or what can run at the same time. Someone can complete every line and still create rework.

The five commitments.

Commitment Purpose
Identifier A stable reference for dependencies and handoff
Change The smallest behavior or contract change
Evidence Repository facts that justify the change
Dependencies Work that must be true first
Proof The exact check that closes the item

Order by dependency, not by prose.

When several surfaces depend on one behavior, the contract comes first. Tests, implementation and documentation then share one definition instead of inventing four. A dependency graph also shows safe concurrency: implementation and documentation can proceed together after the contract is fixed, and the integration gate waits for both.

Evidence must be able to change the plan.

An existing helper removes a planned abstraction. A compatibility test forces a migration step. A deployment constraint moves a schema change into another task. If a piece of evidence cannot change the plan, it is decoration, not evidence.

The rejection list.

The first five checks are mechanical: duplicate identifiers, items without evidence, items without proof, unknown dependencies, cycles. The last check needs judgment: does the first irreversible action, such as a migration or a public release, happen before the relevant uncertainty is resolved? I call that one out explicitly in the review.

Plausible wrong answers.

  • "Trust the author and review the result instead." Rework found at review time costs more than a plan rejected before editing.
  • "A longer plan is a better plan." Length adds nothing; evidence and proof on each item do.
  • "Dependencies are obvious from the order of the list." Prose order hides which steps can run together and which must wait.

Follow-ups an interviewer may ask.

  • (level 2) One item lists two proof commands. What do you do? Expected: split it into two items, because one item needs one clear completion proof.
  • (level 2) Two items depend on each other. What does that usually hide? Expected: an unresolved product or design disagreement; the cycle is the symptom, the missing decision is the cause.
  • (level 3) The plan sits in a chat thread as checked boxes. Why is that a problem? Expected: a session can end at any moment, and another person cannot see which proof ran or which item is now unblocked; the plan belongs next to the work.
  • (level 3) A migration item needs a human approval. How do you express that in the graph? Expected: as an explicit item with the approval as its proof, which every dependent item waits for.
