In plain words first
The idea in one line

Lesson 10.20 named the six architectural knobs every open model turns. DeepSeek-V3 (December 2024, 671B parameters total, 37B active) turns all six and adds four more: Multi-Head Latent Attention, auxiliary-loss-free load balancing, Multi-Token Prediction, and DualPipe training. This lesson reads DeepSeek-V3's architecture top to bottom and derives every parameter count from the published config. By the end you can explain why the 671B/37B ratio is the right bet and why MLA + MoE together beat either alone at the frontier.

Terms you'll hear
Term What people say What it actually means
MLA "Multi-Head Latent Attention" Compress K and V into a shared low-rank latent (kv_lora_rank, typically 512), decompress per head on-the-fly; KV cache stores only the latent
kv_lora_rank "MLA compression dim" The size of the shared latent for K and V; DeepSeek-V3 uses 512
First k dense layers "Early layers stay dense" The first few MoE-model layers skip the MoE router and run a dense MLP for stability
num_experts_per_tok "Top-k routing" How many routed experts fire per token; DeepSeek-V3 uses 8
Shared experts "Always-on experts" Experts that process every token regardless of routing; DeepSeek-V3 uses 1
Auxiliary-loss-free routing "Bias-adjusted load balance" Per-expert bias terms adjusted during training to keep expert load balanced without adding a loss term
MTP module "Extra prediction head" Transformer block predicting $t+2$ from $h^{(1)}$ and $E(t+1)$; denser training, free speculative-decoding draft
DualPipe "Bidirectional pipeline" Training schedule that overlaps forward/backward compute with cross-node all-to-all
Active parameter ratio "Sparsity" active_params / total_params; DeepSeek-V3 hits 5.5%
FP8 training "8-bit training" Training storage and many compute ops in FP8; roughly halves memory vs BF16 at a small quality cost

The problem

In plain words first

DeepSeek-V3 (December 2024) is a 671-billion-parameter model of which only 37 billion work on any one token: each layer holds 256 small expert networks and a router sends every token to 8 of them. Its attention is also different: instead of caching keys and values for every head, it caches one small compressed vector per token (Multi-Head Latent Attention, MLA) and rebuilds what each head needs from it. Add a load-balancing trick without an extra loss, multi-token prediction (Lesson 10.25) and the DualPipe schedule (Lesson 10.26), and you have the blueprint many later open models copy. This lesson runs the lesson's calculator, counts every tensor of the real model from its config, simulates the load balancing, and checks MLA's cache and its "absorbed" attention with Hugging Face's own DeepSeek-V3 code. No model is trained.

DeepSeek-V3 is the first frontier open model whose architecture is meaningfully different from the Llama family. Llama 3 405B is "GPT-2 with six knobs turned." DeepSeek-V3 is GPT-2 with all six knobs plus four more. Reading the Llama 3 config is a warmup for reading the DeepSeek config, but the deep structure — the shape of the attention block, the routing logic, the training-time objective — is different enough that you need a separate walkthrough.

The payoff of learning it: DeepSeek-V3's open-weights release shifted what "frontier capability" means in open models. The architecture is the blueprint many 2026 training runs are copying. Understanding it is table stakes for any role that touches frontier LLM training or inference.

Idea 1 · The invariant core, again

DeepSeek-V3 is still autoregressive. It still stacks decoder blocks. Each block still has attention plus MLP plus two RMSNorms. It still uses SwiGLU in the MLP. It still uses RoPE. Pre-norm. A separate input embedding and output head (not tied, as in Llama 3). Same baseline as every Llama or Mistral.

Idea 2 · The twist: MLA instead of GQA

From Phase 10 · 14 you know GQA shrinks the KV cache by sharing K and V across groups of Q heads. Multi-Head Latent Attention (MLA) goes further: K and V are compressed into a shared low-rank latent representation (the kv_lora_rank), then decompressed per head on the fly. The KV cache stores only the latent: 512 numbers per token per layer, plus one 64-number key that carries the RoPE position and is shared by all heads, against 2 × 8 × 128 = 2,048 numbers for a GQA layer with 8 KV heads.

At 128k context, DeepSeek-V3 with MLA (one shared latent c^{KV} per token per layer; K and V are both derived from this latent via up-projections that can be absorbed into the subsequent matmul):

kv_cache = num_layers * kv_lora_rank * max_seq_len * bytes_per_element
         = 61 * 512 * 131072 * 2
         = 7.6 GB

A hypothetical GQA baseline (Llama 3 70B shape, 8 KV heads, head dim 128) would pay:

kv_cache = 2 * 61 * 8 * 128 * 131072 * 2
         = 30.5 GB

Both results are in GiB (2³⁰ bytes). Counting the 64-number RoPE key that MLA also caches, the MLA cache is 61 × 576 × 131,072 × 2 bytes = 8.6 GiB, 3.6× smaller than the Llama-3-70B-style GQA cache at 128k context.

The tradeoff: MLA adds a decompression step per attention computation (per head). The extra compute is small compared to the bandwidth saved. Net win for long-context inference.

Idea 3 · The routing: auxiliary-loss-free load balancing

MoE routers decide which top-k experts process each token. A naive router concentrates too much work on a few experts, leaving others idle. Standard fix: add an auxiliary loss term that penalizes load imbalance. This works but slightly degrades main-task performance.

DeepSeek-V3 introduces an auxiliary-loss-free scheme. Per-expert bias terms are added to the router logits, adjusted during training by a simple rule: if expert e is overloaded, decrease bias_e; if underloaded, increase it. No extra loss term. Training stays clean. Expert load stays balanced.

Two details matter. The bias only decides which experts are chosen; the gate weights that mix the chosen experts' outputs come from the unbiased affinities. And the bias step is small (γ = 0.001 for the first 14.3T tokens, then 0). DeepSeek-V3 also keeps a tiny sequence-wise balance loss (α = 0.0001) against extreme imbalance within single sequences. In the report's ablations, models balanced this way score better than the same models balanced with an auxiliary loss.

Idea 4 · The MTP: denser training + free draft

From Phase 10 · 18 you know DeepSeek-V3 adds D=1 MTP module that predicts the token two positions ahead. At inference, the trained module is repurposed as a speculative-decoding draft with 85–90% acceptance. At training, each hidden state is supervised on D+1 = 2 targets, providing a denser signal.

Parameters: 14B on top of the 671B main. Overhead: 2.1%.

Idea 5 · The training: DualPipe

From Phase 10 · 19 you know DualPipe is a bidirectional pipeline that overlaps forward and backward chunks with cross-node all-to-all comms. At DeepSeek-V3's 2,048-H800 scale, its main job is hiding the expert-parallel all-to-all traffic, which would otherwise take about as long as the computation.

Idea 6 · The config, field by field

Here is the DeepSeek-V3 config (simplified):

hidden_size: 7168
intermediate_size: 18432   (dense MLP hidden size, used on first few layers)
moe_intermediate_size: 2048 (expert MLP hidden size)
num_hidden_layers: 61
first_k_dense_layers: 3    (first 3 layers use dense MLP)
num_attention_heads: 128
num_key_value_heads: 128   (formally equal to num_heads under MLA, but
                           the real compression is in kv_lora_rank)
kv_lora_rank: 512          (MLA latent dimension)
num_experts: 256            (MoE expert count per block)
num_experts_per_tok: 8      (top-8 routing)
shared_experts: 1           (always-on shared expert per block)
max_position_embeddings: 163840
rope_theta: 10000.0
vocab_size: 129280
mtp_module: 1               (1 MTP module at depth 1)

Parse it (the real file names some fields differently: first_k_dense_replace, n_routed_experts, n_shared_experts, num_nextn_predict_layers; it also sets q_lora_rank: 1536 for compressed queries, qk_rope_head_dim: 64 and YaRN scaling with factor 40, all used after Use it):

  • hidden_size=7168: embedding dimension.
  • num_hidden_layers=61: total block depth.
  • first_k_dense_layers=3: the first 3 blocks use a dense MLP of size 18432. The remaining 58 use MoE.
  • num_attention_heads=128: 128 query heads.
  • kv_lora_rank=512: K and V are compressed to this latent dimension and decompressed per head.
  • num_experts=256, num_experts_per_tok=8: each MoE block has 256 experts, routes top-8.
  • shared_experts=1: on top of the 256 routed experts, 1 always-on expert contributes to every token. Think of it as a "dense floor" that ensures every token gets something reliable.
  • moe_intermediate_size=2048: each expert's MLP hidden size. Smaller than the dense MLP because there are 256 of them.

Idea 7 · Parameter accounting

The full calculation lives in code/main.py. The headline:

  • Embedding: vocab * hidden = 129280 * 7168 = ~0.93B.
  • First 3 dense blocks: attention with MLA (~84M per block in the calculator's simplified count) + dense SwiGLU MLP (3 * 7168 * 18432 = ~396M per block) + norms. About 1.4B total.
  • 58 MoE blocks: attention with MLA (~84M) + 256 routed experts (3 * 7168 * 2048 = ~44M apiece) + 1 shared expert (~44M) + router + norms. About 11.4B per block, including all experts. About 661B for the 58 MoE blocks.
  • MTP module: the published module is 14B. The calculator uses a dense stand-in of ~0.8B.

Grand total: the calculator lands at ~664B against the published 671B for the main model. The Hugging Face checkpoint is 685B because it adds the 14B MTP module on top of the 671B. The remaining ~1% gap comes from simplifications: the calculator skips the decoupled RoPE dimensions in MLA, the untied output head, and a few small tensors. Counting every tensor of the real model (after Use it) gives 671.03B, with 187M of attention per layer rather than 84M.

Active parameters per forward:

  • Attention: 84M per layer * 61 = ~5.1B (all layers fire).
  • MLP active: first 3 layers dense (3 * 396M = ~1.2B), 58 MoE layers each active with 8 routed + 1 shared expert (9 * 44M = ~396M per layer, ~23B total). About 24B in all.
  • Embedding + norms: ~0.9B.
  • Total active: ~30B from the calculator against the published 37B. Most of the gap is attention: full MLA, with its RoPE dimensions and wider query and key heads, is larger than the simplified count. The MTP module does not count toward the 37B.

Idea 8 · The 671B / 37B ratio

18x sparsity ratio (active params are 5.5% of total). At its release it was among the sparsest open MoE models; later ones go further (Llama 4 Maverick runs 17B of 400B, Kimi K2 32B of 1T). Mixtral 8x7B at ratio 13/47 (28%) is much denser. Llama 4 Maverick at ratio 17B/400B (4.25%) is comparable. The DeepSeek bet: at frontier scale, more experts with lower activation ratio produces better quality per active-FLOP.

Idea 10 · The follow-on: R1, V4

DeepSeek-R1 (2025) is a reasoning-training run on the V3 backbone. R1 uses the same architecture. What changed is the post-training recipe (large-scale RL on verifiable tasks), not the pretraining architecture.

DeepSeek-V3.2 (2025) keeps V3's architecture and adds DSA (DeepSeek Sparse Attention), the successor to NSA from Phase 10 · 17. DeepSeek-V4 (April 2026: V4-Pro with 1.6T parameters, 49B active, and V4-Flash with 284B, 13B active, both with a 1M-token context) goes further, with a new hybrid of compressed and sparse attention and a new residual scheme (hyper-connections), beyond the scope of this lesson.

The same idea as a formula

MLA. For token t with hidden state ht​, cache only

ctKV​=WDKVht​∈R512,ktR​=RoPE(WKRht​)∈R64.
Head i's key and value are rebuilt as kt,i​=[WiUK​ctKV​;ktR​] and vt,i​=WiUV​ctKV​.

Absorption. The content part of a score is qs,i⊤​WiUK​ctKV​=(WiUK⊤​qs,i​)⊤ctKV​: multiply the query by WiUK⊤​ once and attend directly over the cached latents. Likewise WiUV​ folds into the output projection.

Cache per token: L(dc​+dR​) numbers for MLA, 2Lnkv​dh​ for GQA.

Routing. Affinity st,e​=σ(ut⊤​ee​); choose the top 8 of st,e​+be​; gate weights gt,e​=st,e​/∑e′∈top​st,e′​ use s, not s+b. After each step, be​←be​−γsign(loade​−load).

Active parameters $= $ attention + dense MLPs $+ \tfrac{8}{256}\,$routed experts + shared experts + output head.

Worked example
DeepSeek-V3's attention and cache
  • Per layer: qa​ 7168×1536 (11.0M), qb​ 1536×128⋅192 (37.7M), kva​ 7168×576 (4.1M), kvb​ 512×128⋅256 (16.8M), o 128⋅128×7168 (117.4M): 187M.
  • Cache per token and layer: 512+64=576 numbers, 1,152 bytes in BF16; over 61 layers 68.6 KB.
  • A GQA layer with 8 heads of 128 caches 2×8×128=2,048 numbers, 3.6× more; caching V3's own 128 heads decompressed would be 128×(192+128)=40,960 numbers, 71× more.
  • Experts: $256 \times 3 \times 7168 \times 2048 = 11.27$B per MoE layer, 58 layers: 654B, the bulk of the 671B. Per token only 8 run: 20.4B.

Reading this output

The calculator gets the shape right and the details wrong. It lands at 664.5B total and 30.4B active against the published 671B and 37B because its attention count is 84M per layer, less than half of MLA's real 187M (the next run counts every tensor): it misses the compressed-query matrices, the 64 RoPE dimensions of every query head and the 128 × 128 → 7,168 output projection. Over 61 layers that is about 6.3B, most of the gap in both totals; the missing output head (0.93B) explains most of the rest.

Its cache figure leaves out MLA's 64-number RoPE key: 7.6 GiB at 128K instead of 8.6 GiB, so "75% savings" against GQA is really 72%. The what-ifs show the trade-offs correctly in direction: halving the latent halves the cache; 512 experts double the total parameters but leave the active ones unchanged; top-16 routing keeps the total but adds about 20B active parameters per token, which is compute on every token.

from transformers import AutoConfig, AutoModelForCausalLM
transformers.logging.set_verbosity_error()

print("A. DeepSeek-V3 built from its published config on the meta device (shapes only)")
cfg = AutoConfig.from_pretrained("deepseek-ai/DeepSeek-V3")
with torch.device("meta"):
    model = AutoModelForCausalLM.from_config(cfg)
groups = {"embedding": 0, "output head": 0, "attention (MLA)": 0, "dense MLPs (layers 0-2)": 0,
          "routed experts": 0, "shared experts": 0, "routers": 0, "norms": 0}
for n, p in model.named_parameters():
    k = ("embedding" if "embed_tokens" in n else "output head" if n.startswith("lm_head") else
         "attention (MLA)" if ".self_attn." in n else "routed experts" if ".experts." in n else

for name, b in rows:
    print(f"  {name:<40} {b / 1024:8.1f} KB/token   {b * 131072 / 2**30:7.1f} GiB at 128K")
print()

print("C. Auxiliary-loss-free balancing: a bias per expert, nudged by the sign of its load (gamma = 0.001)")
rng = np.random.default_rng(0)
E, k, T = 64, 8, 4096
pref = rng.normal(0, 1, E) * 0.5                     # some experts are systematically preferred
bias = np.zeros(E)
for step in range(301):
    x = rng.normal(0, 1, (T, E))
    s = 1 / (1 + np.exp(-(x + pref)))                # sigmoid affinities, as in DeepSeek-V3
    chosen = np.argsort(-(s + bias), 1)[:, :k]       # the bias only changes WHICH experts are chosen
    load = np.bincount(chosen.ravel(), minlength=E) / (T * k / E)
    if step in (0, 30, 100, 300):
        g = np.take_along_axis(s, chosen, 1); g /= g.sum(1, keepdims=True)    # gate weights from s, without the bias
        print(f"  step {step:>3}: busiest expert {load.max():.2f}x its fair share, idlest {load.min():.2f}x, "
              f"mean gate weight of the top choice {g.max(1).mean():.3f}")
    bias -= 0.001 * np.sign(load - 1)                # overloaded: lower the bias; underloaded: raise it

import torch, transformers
from transformers import AutoConfig, AutoModelForCausalLM
transformers.logging.set_verbosity_error()
torch.manual_seed(0)

# DeepSeek-V3's real attention shapes in a 2-layer model with random weights (no checkpoint is loaded):
# full-size MLA (hidden 7168, 128 heads, latent 512 + 64), small dense MLPs and a 1,000-token vocabulary to fit in memory.
cfg = AutoConfig.from_pretrained("deepseek-ai/DeepSeek-V3")
cfg.num_hidden_layers, cfg.first_k_dense_replace, cfg.intermediate_size, cfg.vocab_size = 2, 2, 512, 1000
cfg.quantization_config = None
model = AutoModelForCausalLM.from_config(cfg, dtype=torch.bfloat16).eval()
attn = model.model.layers[0].self_attn
print(f"attention parameters per layer: {sum(p.numel() for p in attn.parameters()) / 1e6:.1f}M")

T = 256
with torch.no_grad():
    out = model(torch.randint(0, 1000, (1, T)), use_cache=True)
cache = out.past_key_values
lay = cache.layers[0]

Reading this output

Hugging Face's current DeepSeek-V3 code caches exactly what MLA promises: per layer, a 256×512 tensor (the latent cKV, stored in the cache's "keys" slot as a single head) and a 256×64 tensor (the shared RoPE key, in the "values" slot). That is 1,152 bytes per token per layer in BF16; decompressed keys and values for all 128 heads would be 81,920 bytes, 71 times more. The per-head keys and values are rebuilt from the latent for each attention call.

The second part checks the absorption trick with this layer's own weights. Scoring the queries against keys decompressed per head, and instead multiplying each query by the head's key matrix once and scoring it directly against the 512-number latents, give the same table up to 10−5, float rounding on scores of size about 3. With absorption, decoding never materialises per-head keys: the 128 heads attend over the same 576-number cache, which is what FlashMLA does in vLLM and SGLang. The weights here are random; the check is about shapes and algebra, which do not depend on training.

Solutions

SolutionP1 · The latent: 1,152 bytes

The compressed latent: per layer the cache holds a 512-number latent and a 64-number RoPE key for each token, 576 numbers or 1,152 bytes in BF16, the same for all 128 heads. The per-head keys and values (192 + 128 numbers for each of 128 heads, 81,920 bytes) are rebuilt from the latent at every attention call and never stored. Over 61 layers that is 68.6 KB per token, 8.6 GiB for a 128K-token conversation.

SolutionB1 · The bias leaks into the output

The bias leaks into the model's output. The bias exists only to shift which experts are chosen, and it keeps changing during training in response to load, not to what helps the loss. If it also scaled the gate weights, an expert whose bias was raised to attract tokens would also get a larger say in every token's output, and an expert lowered to shed load would be muted even when it is the right one; the output would change every step for reasons unrelated to the data, and the router could no longer express "this expert matters a lot for this token". In the simulation the top choice's gate weight stays about 0.14 because the mixing uses the unbiased scores. DeepSeek-V3 uses the biased scores for top-k selection only.
