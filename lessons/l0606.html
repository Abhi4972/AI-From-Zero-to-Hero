Why this came about

Teams kept forking create_agent to add trimming, retries, approvals or model switching. Following the pattern web frameworks used for decades, LangChain 1.0 added middleware: hooks around each model and tool call, so behaviour can be added without rewriting the loop.

The problem: the agent loop needs hooks

The plain create_agent loop from Lesson 14.55 cancels an order the moment a customer asks. Production agents need more than the loop: a person approving risky actions, a cap on how many model calls a run may make, history that is summarized before it overflows the context window, personal data kept away from the model. In Lesson 14.3 you added risky and approve hooks to your own Agent class for this. Middleware is LangChain's set of hooks around the loop, and a library of ready-made ones.

Idea 1 · Where middleware runs

Middleware is code that runs at fixed points of the agent loop: before the model is called, around the model call, around each tool call, and after the model replies. The four small functions below do nothing except print a line when they run. Attach them to an agent, ask one question, and the printout shows you the order of the hooks.

from langchain.agents import create_agent
from langchain.agents.middleware import before_model, after_model, wrap_model_call, wrap_tool_call

@before_model
def count_messages(state, runtime):
    print(f"  before_model   | {len(state['messages'])} messages so far")

@wrap_model_call
def time_model(request, handler):
    response = handler(request)                         # the actual model call happens here
    print(f"  wrap_model_call| model returned {len(response.result[-1].tool_calls)} tool call(s)")
    return response

@after_model
def after(state, runtime):
    print(f"  after_model    | last message is {type(state['messages'][-1]).__name__}")

@wrap_tool_call
def log_tool(request, handler):
    print(f"  wrap_tool_call | {request.tool_call['name']}({request.tool_call['args']})")
    return handler(request)

agent = create_agent(chat, tools=[get_order_status], middleware=[count_messages, time_model, after, log_tool])
print(agent.invoke({"messages": [{"role": "user", "content": "Where is A-1002?"}]})["messages"][-1].content)
What you should see
  before_model   | 1 messages so far
  wrap_model_call| model returned 1 tool call(s)
  after_model    | last message is AIMessage
  wrap_tool_call | get_order_status({'order_id': 'A-1002'})
  before_model   | 3 messages so far
  wrap_model_call| model returned 0 tool call(s)
  after_model    | last message is AIMessage
Here is what I found: A-1002 is processing

Read the output as a timeline. Each model call is surrounded by before_model, wrap_model_call (which receives a handler; calling it is the model call) and after_model. Each tool call runs inside wrap_tool_call. There are also before_agent and after_agent, which run once per invocation. Every built-in middleware below is made of these hooks:

Hook Runs Typical use
before_agent, after_agent Once per invoke Load or save per-user data, final checks
before_model Before every model call Trim or summarize history, redact input
wrap_model_call Around every model call Retries, fallbacks, choosing a model or tools per call, dynamic prompts
after_model After every model call Approval of tool calls, limits, output checks
wrap_tool_call Around every tool call Retries, timing, error handling, logging

Hooks can also change things, not just watch: a before_model hook can return {"messages": ...} to update the state, and a wrap_model_call hook can change request (its messages, tools or model) before calling handler.

There are two shapes of hook, and the difference explains most of what follows:

In plain words first
Checkpoints on a road, and wrappers around a call
  • Node-style hooks (before_agent, before_model, after_model, after_agent) are checkpoints the agent passes: your function sees the state and may return changes to it, or a jump. What they return is saved in the agent's state.
  • Wrap-style hooks (wrap_model_call, wrap_tool_call) wrap one call, like a decorator (Lesson 0.16). Your function gets the request about to be sent and a handler that performs it; you may change the request, call the handler, retry it, or skip it. Changes to the request affect that call only and are not saved.

The same loop in plain Python, with the hook points marked, shows where each runs:

def call_model(messages):                        # stands in for the real model
    return "TOOL:lookup" if len(messages) == 1 else "Here is your answer."

def plain_agent(user_text, before_model=None, wrap_model=None):
    messages = [user_text]
    while True:
        if before_model: before_model(messages)                        # node-style: sees the state
        call = wrap_model(call_model) if wrap_model else call_model    # wrap-style: wraps the call
        reply = call(messages)
        messages.append(reply)
        if not reply.startswith("TOOL:"):
            return messages
        messages.append(f"result of {reply[5:]}")                       # run the tool

def log_size(messages):
    print(f"[before_model] {len(messages)} messages")

def wrapped(inner):                                                     # receives the "handler"
    def wrapper(messages):
        reply = inner(messages)                                         # the real call happens here
        print(f"[wrap_model] model replied {reply!r}")
        return reply
    return wrapper

print(plain_agent("Where is A-1002?", before_model=log_size, wrap_model=wrapped))
What you should see
[before_model] 1 messages
[wrap_model] model replied 'TOOL:lookup'
[before_model] 3 messages
[wrap_model] model replied 'Here is your answer.'
['Where is A-1002?', 'TOOL:lookup', 'result of lookup', 'Here is your answer.']

wrap_model(call_model) returning a wrapper @wrap_model_call, receiving request and handler

Idea 2 · Human approval: pause, decide, resume

Some tools should not run until a person agrees. HumanInTheLoopMiddleware names those tools. When the model asks for one, the run stops and returns a description of the pending call. Your application shows it to a person and then resumes the same run with their decision. Because the run has to be found again later, the agent needs a checkpointer and a thread ID. Watch a cancellation pause and then continue:

from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

guarded = create_agent(chat, tools=[get_order_status, cancel_order], checkpointer=InMemorySaver(),
                       middleware=[HumanInTheLoopMiddleware(interrupt_on={"cancel_order": True})])
cfg = {"configurable": {"thread_id": "customer-42"}}

out = guarded.invoke({"messages": [{"role": "user", "content": "Please cancel A-1002"}]}, cfg, version="v2")
request = out.interrupts[0].value
print("paused for:", request["action_requests"][0]["name"], request["action_requests"][0]["args"])
print("allowed:   ", request["review_configs"][0]["allowed_decisions"])
print("next step: ", guarded.get_state(cfg).next)
What you should see
paused for: cancel_order {'order_id': 'A-1002'}
allowed:    ['approve', 'edit', 'reject', 'respond']
next step:  ('HumanInTheLoopMiddleware.after_model',)

The model asked to cancel; HumanInTheLoopMiddleware stopped the run in its after_model hook, before the tool ran, and returned an interrupt describing the request. The checkpointer saved the state, and next shows where the run will continue. Nothing is waiting in memory: the decision can come minutes or days later, from another process, such as an approval dashboard. You resume by invoking the same thread with a Command:

out = guarded.invoke(Command(resume={"decisions": [{"type": "reject", "message": "Customer must confirm by phone first"}]}),
                     cfg, version="v2")
print(out.value["messages"][-2].content)
print(out.value["messages"][-1].content)

cfg2 = {"configurable": {"thread_id": "customer-43"}}
guarded.invoke({"messages": [{"role": "user", "content": "Please cancel A-1002"}]}, cfg2, version="v2")
out = guarded.invoke(Command(resume={"decisions": [{"type": "approve"}]}), cfg2, version="v2")
print(out.value["messages"][-1].content)
What you should see
User rejected the tool call for `cancel_order` with reason: Customer must confirm by phone first
Here is what I found: User rejected the tool call for `cancel_order` with reason: Customer must confirm by phone first
Here is what I found: A-1002 cancelled

A rejection becomes a ToolMessage with your reason, so the model can tell the customer what happens next; an approval runs the tool. This is Lesson 14.6's waiting_for_approval and decide, built on LangGraphlater · 14.60's interrupt and Command, which Lesson 14.63 uses directly.

In plain words first
Two places, two people

Approval needs two decisions, by two people, at two times. At setup, the developer writes the policy in interrupt_on: which tools pause, and which answers a reviewer may give. At run time, the reviewer decides each case, and that answer goes into Command(resume=...).

The policy, one entry per tool:

interrupt_on value Meaning
False, or the tool left out Never pause
True Pause, and allow all four decisions
{"allowed_decisions": [...]} Pause, and allow only those
{..., "when": fn} Pause only when fn(request) returns True for this call
{..., "description": "..."} The text the reviewer sees

The reviewer's four decisions:

Decision Shape What the model sees
approve {"type": "approve"} The tool's real result
edit {"type": "edit", "edited_action": {"name": "cancel_order", "args": {...}}} The result of the edited call, plus a note that a reviewer changed it
reject {"type": "reject", "message": "..."} An error result: "User rejected the tool call..."
respond {"type": "respond", "message": "..."} Your text as a successful result, as if the tool returned it

Never use respond to deny: the model would believe the action succeeded. It is for tools that ask the customer a question, where the reviewer's reply is the answer.

The resume shape depends on interrupt_mode. The default, "batched", is what you just used: one pause per model turn, whose value lists every gated call under action_requests, answered with {"decisions": [...]}, one decision per action, in the same order. With "per_call", each gated call is its own pause, answered by interrupt ID. A when function narrows the gate to the risky calls, here high-value orders only:

HIGH_VALUE = {"A-1002"}

def high_value(request) -> bool:                         # request.tool_call has name, args and id
    return request.tool_call["args"]["order_id"] in HIGH_VALUE

per_call = create_agent(chat, tools=[cancel_order], checkpointer=InMemorySaver(), middleware=[
    HumanInTheLoopMiddleware(interrupt_on={"cancel_order": {"allowed_decisions": ["approve", "reject"],
                                                            "when": high_value}},
                             interrupt_mode="per_call")])

for order in ["A-1003", "A-1002"]:
    c = {"configurable": {"thread_id": f"pc-{order}"}}
    out = per_call.invoke({"messages": [{"role": "user", "content": f"Please cancel {order}"}]}, c, version="v2")
    if not out.interrupts:
        print(order, "-> no pause:", out.value["messages"][-1].content)
        continue
    pause = out.interrupts[0]
    print(order, "-> paused:", {k: pause.value[k] for k in ("type", "name", "args")})
    out = per_call.invoke(Command(resume={pause.id: {"type": "approve"}}), c, version="v2")   # keyed by ID
    print(order, "-> after approval:", out.value["messages"][-1].content)
What you should see
A-1003 -> no pause: Here is what I found: A-1003 cancelled
A-1002 -> paused: {'type': 'tool_approval', 'name': 'cancel_order', 'args': {'order_id': 'A-1002'}}
A-1002 -> after approval: Here is what I found: A-1002 cancelled
Reading this output
  • A-1003 is not in HIGH_VALUE, so when returned False and the tool ran without a pause.
  • A-1002 paused. In per-call mode the interrupt's value describes one call: type ("tool_approval"), name, args, plus tool_call_id and description.
  • The resume maps that interrupt's ID to one decision. In batched mode the same answer would be {"decisions": [{"type": "approve"}]}. Mixing up the two shapes is the most common approval bug.
  • when runs again on resume, so it must give the same answer for the same call: no clocks or lookups that can change.

Idea 3 · Limits that end a run gracefully

Lesson 14.3's loop had a step limit so that a confused agent could not run for ever. The middleware version is a pair of counters: one for model calls, one for tool calls. With exit_behavior="end" the run stops cleanly with what it has so far, without raising an error. Here the limit is set to one model call, so that you can see it trigger:

from langchain.agents.middleware import ModelCallLimitMiddleware, ToolCallLimitMiddleware

capped = create_agent(chat, tools=[get_order_status],
                      middleware=[ModelCallLimitMiddleware(run_limit=1, exit_behavior="end")])
for m in capped.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})["messages"]:
    print(f"{type(m).__name__:12} | {m.content or m.tool_calls[0]['name']}")
What you should see
HumanMessage | Where is A-1001?
AIMessage    | get_order_status
ToolMessage  | A-1001 is shipped
AIMessage    | Model call limits exceeded: run limit (1/1)

With run_limit=1 the agent ran the tool but was not allowed a second model call, so the middleware ended the run with a message instead of raising. exit_behavior="error" raises instead, which suits batch jobs where a half-answered run should fail loudly. thread_limit caps calls across a whole conversation, and ToolCallLimitMiddleware does the same for one tool or for all of them. Compare recursion_limit (Lesson 14.55), which counts graph steps and always raises.

Idea 4 · Summaries before the context overflows

Lesson 11.8 compacted long conversations by hand. SummarizationMiddleware does it in before_model: when the history passes a trigger, older messages are replaced by a summary written by a model you choose, and the most recent ones are kept as they are.

from langchain.agents.middleware import SummarizationMiddleware

long_chat = create_agent(chat, tools=[get_order_status], checkpointer=InMemorySaver(),
                         middleware=[SummarizationMiddleware(chat, trigger=("messages", 6), keep=("messages", 2))])
cfg3 = {"configurable": {"thread_id": "long"}}
for q in ["Where is A-1001?", "Where is A-1002?", "Where is A-1001 now?"]:
    msgs = long_chat.invoke({"messages": [{"role": "user", "content": q}]}, cfg3)["messages"]
    print(f"{len(msgs)} messages | first: {msgs[0].content[:48]!r}")
What you should see
4 messages | first: 'Where is A-1001?'
4 messages | first: 'Here is a summary of the conversation to date:\n\n'
4 messages | first: 'Here is a summary of the conversation to date:\n\n'

The thread stays at four messages: a summary, then the recent turn. The lab rig's "summary" is its fixed sentence; a real model writes one, guided by a default prompt that asks for the session's intent, decisions, artifacts and next steps. Triggers can be a message count, a token count, or a fraction of the model's context window. The middleware never splits a tool call from its result, which would break the conversation (Lesson 14.2's rule).

Idea 5 · Personal data never reaches the model

PIIMiddleware finds personal data in the messages, such as an email address, and replaces it before the request leaves your process. To prove that it works, a second small middleware prints exactly what the model is about to receive:

from langchain.agents.middleware import PIIMiddleware

@wrap_model_call
def show_request(request, handler):
    print("model sees:", next(m.content for m in request.messages if m.type == "human"))
    return handler(request)

private = create_agent(chat, tools=[get_order_status], middleware=[PIIMiddleware("email", strategy="redact"), show_request])
private.invoke({"messages": [{"role": "user", "content": "Where is A-1001? Mail me at ravi@example.com"}]})
What you should see
model sees: Where is A-1001? Mail me at [REDACTED_EMAIL]
model sees: Where is A-1001? Mail me at [REDACTED_EMAIL]

The email address was replaced before the first model call (it prints twice because the agent made two model calls, both with the redacted text). Strategies are redact, mask (keep the last characters), hash and block (raise). Built-in detectors cover email, credit card, IP, MAC address and URL; you can pass your own regex or function, for example for Indian phone numbers or PAN numbers. Because redaction changed the message in the state, the original address is not saved in checkpoints either. Lesson 15.21 covers what pattern-based detection misses.

The order of middleware

When several middleware wrap the same call, the order of the list matters. The first one listed is the outermost: it sees the request first and the response last, like the layers of an onion. Three tagging functions make the nesting visible:

def tag(name):
    @wrap_model_call(name=f"tag_{name}")       # middleware names must be unique
    def mw(request, handler):
        print(f"  {name} in")
        response = handler(request)
        print(f"  {name} out")
        return response
    return mw

ordered = create_agent(chat, tools=[], middleware=[tag("A"), tag("B")])
ordered.invoke({"messages": [{"role": "user", "content": "hello"}]})
What you should see
  A in
  B in
  B out
  A out

The first middleware in the list is the outermost: its before_* hooks run first and its after_* hooks run last, like nested function calls. Order is a design decision. Put redaction before anything that logs messages, or the log holds the personal data. Put retries inside fallbacks, so a model is retried before you give up on it. Put approval where it sees the final tool calls.

Two more changes in LangChain 1.5 are worth knowing. SummarizationMiddleware accepts summarizer=, a separate model or function for writing summaries, so you can summarise with a cheap model. And the Decisions API (langchain_core.decisions) gives typed answers to questions such as yes/no (Noul), pick one (Choice) or rate (Score); the router and auto-mode middleware are built on it, and you can write your own guard on top of it. Both middlewares are beta: pin your version and test them on your own traffic.

Make it your own

Build careful, an agent that redacts emails, caps model calls at four per run, and pauses before cancel_order with only approve and reject allowed. Check what the saved state holds for the customer's message. (Solution M1.)

Solutions

SolutionP1 · Parallel calls add one message per call

1, then 4: the question, the model's turn with two tool calls, and two ToolMessages. It is 4 rather than 3 because each parallel call gets its own result message; there are still only two model calls.

SolutionB1 · A pause needs somewhere to wait

Pausing means saving the state and stopping; resuming means loading it. With no checkpointer, nothing was saved, so Command(resume=...) has nothing to continue and LangGraph raises RuntimeError: Cannot use Command(resume=...) without checkpointer. Any agent that can interrupt needs a checkpointer and a thread ID, and in production a database checkpointer (Lesson 14.62), because a deploy restarts the process.

SolutionD1 · Resume the thread that paused

The dashboard resumes approval-99, a thread that never ran, so LangGraph starts a new run there with no messages, and the model call fails. The customer's thread, customer-99, is still waiting. The interrupt belongs to the thread that paused, so the approval request must carry that thread's ID:

def approve(thread_id):
    cfg = {"configurable": {"thread_id": thread_id}}                      # resume the thread that paused
    return guarded.invoke(Command(resume={"decisions": [{"type": "approve"}]}), cfg, version="v2")

print(approve("customer-99").value["messages"][-1].content)
print("customer-99 now at:", guarded.get_state(support_cfg).next)

Here is what I found: A-1002 cancelled
customer-99 now at: ()

In production, store the thread ID with each pending approval, and alert on approvals that wait longer than your service level.

Explain the mechanismHow does human approval work in a LangChain agent?

Worked answer. HumanInTheLoopMiddleware runs after each model call. If the reply contains a call to a tool configured for review, it raises a LangGraph interrupt with the requested actions and the allowed decisions. The checkpointer saves the state and the run returns. Later, any process invokes the same thread with Command(resume={"decisions": [...]}); the middleware applies each decision: approve runs the tool, edit runs it with new arguments, reject sends the reason back to the model as a tool result, respond answers the model directly.

A plausible wrong answer. "The agent waits in a loop until someone approves." Nothing waits in memory; the run ends and is resumed from the checkpoint, which is why it survives restarts.

Follow-ups. What must be stored with each pending approval? How would you time out an approval?

Debug a failureAfter adding a logging middleware, customer emails appear in your logs, even though PII redaction is on. Why?

Worked answer. Middleware order. The logging middleware is earlier in the list than the redaction middleware, so its before_model hook (or its wrap_model_call, before calling the handler) sees the messages before redaction. The first middleware in the list is the outermost. Move redaction first, or log only after the handler returns, and add a test that sends a fake email and checks the logs.

A plausible wrong answer. "PII detection missed the email." The detector worked; the log read the message before it ran.

Follow-ups. Which other middleware would you put before logging?

Defend a designWould you put guardrails, retries and approvals in middleware, or in a gateway and a separate service?

Worked answer. Both, by scope. Organization-wide policies that apply to every model call, such as provider fallbacks, budgets, rate limits and basic content filters, belong in a gateway (Lesson 14.108), so every app gets them. Anything that depends on the agent's state belongs in middleware: approval of a specific tool call, limits per run or thread, summarizing this conversation, redaction before this agent's model sees the text. Approvals also need a service outside the agent to collect decisions and resume threads.

A plausible wrong answer. "All in middleware, so the agent is self-contained." Then every team reimplements, and drifts on, the same organization policies.

Follow-ups. How would you test that an approval rule cannot be bypassed?
