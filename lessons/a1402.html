In plain words first
The idea in one line

ReAct interleaves thought and action in one stream. ReWOO separates them: one big plan up front, then execute. 5x fewer tokens, +4% accuracy on HotpotQA, and you can distill the planner into a 7B model. Plan-and-Execute generalized it; Plan-and-Act scaled it to web navigation.

The problem

In plain words first

In the agent loop of lesson 14.1 the model decides one step at a time, and every step re-sends everything so far. ReWOO ("reasoning without observation") splits the work differently. A planner writes the whole plan at once, with placeholders such as #E1 for results it has not seen yet. Workers then run the tools in order, filling in each placeholder; they are ordinary code, not model calls. Finally a solver reads the plan and the evidence and writes the answer. Two model calls instead of one per step, and a plan you can check before anything runs. This lesson builds it with scripted parts, then puts a real small model in the planner and solver seats and compares its token bill with the step-by-step loop.

ReAct's interleaved thought-action-observation loop is simple and flexible, but each tool call has to carry the full prior context — including every previous thought. Token usage grows quadratically with depth. Worse: when a tool fails mid-loop, the model has to re-derive the whole plan from the error observation.

ReWOO (Xu et al., arXiv:2305.18323, May 2023) noticed this and made a bet: plan the whole thing up front, fetch evidence in parallel, compose the answer at the end. One LLM call to plan, N tool calls for evidence (can be parallel), one LLM call to solve. The trade is less flexibility (the plan is static) for much better token efficiency and clearer failure modes.

Idea 1 · The three roles

Planner:  user_question -> [plan_dag]
Workers:  [plan_dag]     -> [evidence]        (tool calls, possibly parallel)
Solver:   user_question, plan_dag, evidence -> final_answer

Planner produces a DAG. Each node names a tool, its arguments, and which earlier nodes it depends on (references like #E1, #E2). Workers execute nodes in topological order. Solver stitches everything together.

Idea 2 · Why 5x fewer tokens

ReAct grows prompt length linearly with step count. At step 10, the prompt contains thought 1 plus action 1 plus observation 1 plus thought 2 plus action 2 plus observation 2, and so on. Each intermediate step also redundantly includes the original prompt.

ReWOO pays one planner prompt (large), N small worker prompts (each just the tool call, no chain), and one solver prompt. On HotpotQA the paper measures ~5x fewer tokens while scoring +4 absolute accuracy.

Idea 3 · Why it is more robust

If worker 3 fails in ReAct, the loop has to reason out of the error mid-stream. In ReWOO, worker 3 returns an error string; the solver sees it in context with the original plan and can degrade gracefully. Failure localization is per-node, not per-step.

Idea 4 · Planner distillation

The paper's second result: because the planner does not see observations, you can fine-tune a 7B model on planner outputs from a 175B teacher. The small model handles planning; the big model is not needed at inference. This is now standard — many 2026 production agents use a small planner and a big executor or vice-versa.

Idea 5 · Plan-and-Execute (2023)

The LangChain team's May 2023 post, inspired by BabyAGI and the Plan-and-Solve paper, gave the idea a pattern name: Plan-and-Execute. Up-front planner emits a step list, executor runs each step, an optional replanner can revise after observing results. This is closer to ReAct than ReWOO (the replanner brings observations back into planning) but preserves the token savings.

Idea 6 · Plan-and-Act (Erdogan et al., arXiv:2503.09572, ICML 2025)

Plan-and-Act scales the pattern to long-horizon web and mobile agents. The key contribution is synthetic plan data: a labeled trajectory generator produces training data where the plan is explicit. Planner and executor models fine-tuned on this data reached 57.58% success on WebArena-Lite and 81.36% (text only) on WebVoyager, state of the art when the paper appeared in 2025, on long tasks where a single ReAct trajectory tends to lose its way.

Idea 7 · When to pick which

Pattern When
ReAct Short tasks, unknown environment, need reactive exception handling
ReWOO Structured tasks with known tools, token-sensitive, parallelizable evidence
Plan-and-Execute Like ReWOO but with replanning after partial execution
Plan-and-Act Long-horizon (>30 steps), web/mobile/computer-use
Tree of Thoughts Search is worth paying for (Lesson 14.4)

Anthropic's Dec 2024 guidance: start with the simplest. If the task is one tool call plus a summary, do not build ReWOO. If the task is a 40-step research assignment, do not do ReAct alone.

The same idea as a formula

ReAct re-reads its history. With a first prompt of P0​ tokens, Δ tokens added per step and k tool steps plus a final answer:

ReAct prompt tokens=t=0∑k​(P0​+tΔ)=(k+1)P0​+Δ2k(k+1)​.

ReWOO reads each thing once. With a planner prompt Pplan​, about c generated tokens per plan line, a solver prompt with a fixed part S0​ and about e tokens per evidence line:

ReWOO tokens≈Pplan​+kc+S0​+ke,
linear in k. The tools run in between without any model tokens.

Dependency order. A plan is a DAG; step j can run once every #Ei​ it references has run. Steps on the same level have no dependencies on each other and can run in parallel.

Worked example
From the run below to a ten-step task
  • The ReAct run's two prompts were 240 and 282 tokens: P0​=240, Δ=42.
  • Ten tool steps plus an answer: 11⋅240+42⋅210⋅11​=2640+2310=4950 prompt tokens.
  • The ReWOO planner wrote 3 plan lines in 60 tokens, so c≈20; its prompt is 245 tokens. The solver prompt went from 96 (1 step) to 153 (3 steps), so e≈28.5 and S0​≈67.5.
  • Ten steps: 245+10⋅20+67.5+10⋅28.5≈798 tokens.
  • 4950/798≈6: the same order as the paper's 5x on HotpotQA. At three steps the gap is small (1.19x below); it grows with the square of the step count.
Check your mental model
  • ✗ "ReWOO's workers are model calls."
    ✓ They are plain tool calls; only the planner and solver use the model.
  • ✗ "A plan that parses is a plan that runs."
    ✓ Validate it first: every line parsed, every tool exists, every reference points to an earlier step.
  • ✗ "ReWOO is always better."
    ✓ The plan is fixed before any result is seen. When step 2 depends on what step 1 found in a way you cannot write as #E1, use ReAct or add a replanner.
  • ✗ "The solver can only use the evidence."
    ✓ It is a model: given too little evidence, it fills the gap from memory, as the first run below shows.

# ReWOO with a real model as Planner and Solver (Qwen2.5-0.5B-Instruct, greedy, CPU). The planner
# prompt follows the ReWOO paper's format; the Workers are the lesson's run_workers and tools.
import os, re, time, torch
os.environ.setdefault("HF_HUB_OFFLINE", "1")            # the model is already in the local cache
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
from main import Plan, PlanStep, ToolRegistry, run_workers, fake_search, rounded_million
M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
USAGE = []                                               # (role, prompt tokens, new tokens)
def chat(role, text, max_new=150):
    ids = tok.apply_chat_template([{"role": "user", "content": text}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=max_new, do_sample=False)
    USAGE.append((role, ids.shape[1], out.shape[1] - ids.shape[1]))
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()

PLANNER = """For the following task, make plans that can solve the problem step by step. For each plan, indicate which external tool together with tool input to retrieve evidence. You can store the evidence into a variable #E that can be called by later tools. (Plan, #E1, Plan, #E2, Plan, ...)

Tools can be one of the following:
search[input]: looks up a short fact on the web. Input is a search query.
round_million[input]: rounds a number written in the input to whole millions.

For example,
Task: How many people live in the largest city of Japan, rounded to millions?
Plan: Find the largest city of Japan. #E1 = search[largest city of Japan]
Plan: Find the population of that city. #E2 = search[population of #E1]
Plan: Round the population. #E3 = round_million[#E2]

Begin! Each Plan should be followed by only one #E.
Task: {task}"""
SOLVER = """Solve the following task. To help you, plans and the evidence each one produced are given below. Answer in one short sentence.

{plans}
Task: {task}
Response:"""
STRICT = re.compile(r"Plan:\s*(.*?)\s*#E(\d+)\s*=\s*(\w+)\[(.*?)\]")              # the paper's exact format
TOLERANT = re.compile(r"Plan:\s*(.*?)\s*#E(\d+)\s*=\s*(\w+)\s*\[([^\]\n]*)\]?\s*$", re.M)  # space before [, missing ]
def parse(text, pattern):
    steps, plans = [], []
    for desc, n, tool, arg in pattern.findall(text):
        key = "query" if tool == "search" else "text"
        steps.append(PlanStep(f"E{n}", tool, {key: arg})); plans.append(desc)
    return Plan(steps), plans

def validate(text, plan, names):
    """Before running anything: every Plan line parsed, tools exist, references point backwards."""
    problems = []
    if text.count("Plan:") != len(plan.steps):
        problems.append(f"{text.count('Plan:')} Plan lines but {len(plan.steps)} parsed steps")
    seen = set()
    for s in plan.steps:
        if s.tool not in names: problems.append(f"{s.id}: unknown tool {s.tool}")
        for ref in re.findall(r"#(E\d+)", str(s.args)):
            if ref not in seen: problems.append(f"{s.id}: refers to {ref} before it exists")
        seen.add(s.id)
    return problems or ["ok"]
def solve(descs, plan, evidence):
    plans = "\n".join(f"Plan: {d}\n#{s.id} = {s.tool}[{list(s.args.values())[0]}]\nEvidence: {evidence[s.id]}"
                      for d, s in zip(descs, plan.steps))
    return chat("solver", SOLVER.format(plans=plans, task=TASK), max_new=60)

tools = ToolRegistry(); tools.register("search", fake_search); tools.register("round_million", rounded_million)
TASK = "What is the population of the capital of France, rounded to millions?"
started = time.perf_counter()
raw = chat("planner", PLANNER.format(task=TASK))
print("PLANNER OUTPUT\n" + "\n".join("  " + l for l in raw.splitlines()))
for name, pattern in (("strict parser (paper format)", STRICT), ("tolerant parser", TOLERANT)):
    plan, descs = parse(raw, pattern)
    print(f"\n== {name}: {len(plan.steps)} steps; validation: {'; '.join(validate(raw, plan, {'search', 'round_million'}))}")
    evidence = run_workers(plan, tools)                 # the lesson's Workers: no model call
    for s in plan.steps:
        print(f"  {s.id}: {s.tool}({s.args}) -> {evidence[s.id]}")
    print(f"  SOLVER: {solve(descs, plan, evidence)}")
print("\nTOKENS (real, Qwen tokenizer)")
for role, p, n in USAGE:
    print(f"  {role:<8} prompt {p:>4}  generated {n:>3}")
print(f"seconds {time.perf_counter() - started:.0f}")

Reading this output

The plan is right; the format is not. The planner copies the example's shape: capital, then population of #E1, then round #E2. But line 2 lacks its closing ] and line 3 has a space before [. The paper's strict pattern parses only line 1.

The validator catches it; the solver would not. "3 Plan lines but 1 parsed steps" is reported before any tool runs. Without that check the run continues with one piece of evidence ("Paris"), and the solver fills the gap from memory: "approximately 2.4 million", a number that appears nowhere in the evidence.

A tolerant parser recovers the plan. Accepting a space before [ and a missing ] at the end of the line gives all three steps. The lesson's run_workers substitutes #E1 and #E2 (the printed arguments show the placeholders; the results show they were filled: "population of Paris" found 11.2 million) and the solver answers 11 million, which is what the evidence says. Two model calls in total, the planner's 245-token prompt and the solver's 153.

Part 1 of 4 · PlanStep, Plan, ToolRegistry, resolve_references, topological, run_workers, REFERENCE_RE

"""Toy ReWOO — Planner, Workers, Solver. Stdlib only.

Demonstrates the decoupled pattern from Xu et al. (arXiv:2305.18323):
  1. Planner emits a DAG of (tool, args) steps with references (#E1, #E2, ...).
  2. Workers run each step in topological order.
  3. Solver composes the final answer from question + plan + evidence.

Compare run_rewoo() vs run_react() at the bottom for token-use intuition.
"""

from __future__ import annotations

import re
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class PlanStep:
    id: str
    tool: str
    args: dict[str, Any]


@dataclass
class Plan:
    steps: list[PlanStep]


class ToolRegistry:
    def __init__(self) -> None:
        self._tools: dict[str, Callable[..., str]] = {}

    def register(self, name: str, fn: Callable[..., str]) -> None:
        self._tools[name] = fn

    def dispatch(self, name: str, args: dict[str, Any]) -> str:
        fn = self._tools.get(name)
        if fn is None:
            return f"error: unknown tool {name!r}"
        try:
            return fn(**args)
        except Exception as e:
            return f"error: {type(e).__name__}: {e}"


REFERENCE_RE = re.compile(r"#E(\d+)")


def resolve_references(value: Any, evidence: dict[str, str]) -> Any:
    if not isinstance(value, str):
        return value
    return REFERENCE_RE.sub(lambda m: evidence.get(f"E{m.group(1)}", m.group(0)),
                            value)


def topological(plan: Plan) -> list[PlanStep]:
    resolved: list[PlanStep] = []
    known: set[str] = set()
    pending = list(plan.steps)
    while pending:
        progress = False
        rest: list[PlanStep] = []
        for step in pending:
            refs = REFERENCE_RE.findall(str(step.args))
            if all(f"E{r}" in known for r in refs):
                resolved.append(step)
                known.add(step.id)
                progress = True
            else:
                rest.append(step)
        if not progress:
            raise RuntimeError("cyclic plan or unresolved reference")
        pending = rest
    return resolved


def run_workers(plan: Plan, tools: ToolRegistry) -> dict[str, str]:
    evidence: dict[str, str] = {}
    for step in topological(plan):
        bound_args = {k: resolve_references(v, evidence) for k, v in step.args.items()}
        evidence[step.id] = tools.dispatch(step.tool, bound_args)
    return evidence

Part 2 of 4 · ScriptedPlanner, ScriptedSolver, fake_search, rounded_million, ReWOORun, run_rewoo, run_react_mock

class ScriptedPlanner:
    def __init__(self, plan: Plan) -> None:
        self.plan = plan

    def plan_for(self, question: str) -> Plan:
        return self.plan


class ScriptedSolver:
    def __init__(self, answer_template: str) -> None:
        self.template = answer_template

    def solve(self, question: str, plan: Plan, evidence: dict[str, str]) -> str:
        return self.template.format(**evidence)


def fake_search(query: str) -> str:
    if "capital of france" in query.lower():
        return "Paris"
    if "population of paris" in query.lower():
        return "11.2 million metro"
    if "capital of germany" in query.lower():
        return "Berlin"
    return f"no result for {query!r}"


def rounded_million(text: str) -> str:
    m = re.search(r"([0-9]+\.?[0-9]*)", text)
    if not m:
        return "unknown"
    return f"{round(float(m.group(1)))} million"


@dataclass
class ReWOORun:
    question: str
    plan: Plan
    evidence: dict[str, str] = field(default_factory=dict)
    answer: str = ""
    planner_chars: int = 0
    worker_chars: int = 0
    solver_chars: int = 0


def run_rewoo(question: str, planner: ScriptedPlanner,
              tools: ToolRegistry, solver: ScriptedSolver) -> ReWOORun:
    plan = planner.plan_for(question)
    planner_chars = len(question) + sum(len(s.tool) + len(str(s.args))
                                        for s in plan.steps)
    evidence = run_workers(plan, tools)
    worker_chars = sum(len(str(s.args)) + len(v) for s, v in zip(plan.steps,
                                                                 evidence.values()))
    answer = solver.solve(question, plan, evidence)
    solver_chars = len(question) + worker_chars + len(answer)
    return ReWOORun(question=question, plan=plan, evidence=evidence,
                    answer=answer,
                    planner_chars=planner_chars, worker_chars=worker_chars,
                    solver_chars=solver_chars)


def run_react_mock(question: str, tools: ToolRegistry,
                   trajectory: list[tuple[str, dict[str, Any]]]) -> int:
    prompt_chars = len(question)
    total = 0
    history_chars = 0
    for name, args in trajectory:
        total += prompt_chars + history_chars + len(name) + len(str(args))
        obs = tools.dispatch(name, args)
        history_chars += len(name) + len(str(args)) + len(obs) + 40
    total += prompt_chars + history_chars
    return total

    for k, v in run.evidence.items():
        print(f"  {k} -> {v}")
    print(f"\nFINAL: {run.answer}")

    react_chars = run_react_mock(
        run.question, tools,
        [("search", {"query": "capital of France"}),
         ("search", {"query": "population of Paris"}),
         ("round_million", {"text": "11.2 million metro"})])
    rewoo_chars = run.planner_chars + run.worker_chars + run.solver_chars
    print("\nTOKEN INTUITION (chars, approximate)")
    print(f"  react total  : {react_chars}")
    print(f"  rewoo total  : {rewoo_chars}")
    print(f"  ratio        : {react_chars / max(rewoo_chars, 1):.2f}x")
    print("\npaper claim: ~5x fewer tokens on HotpotQA. toy approximates the shape.")

Use it: the same idea with real libraries

LangGraph ships Plan-and-Execute as a tutorial recipe (a custom graph), while LangChain's create_agent (formerly LangGraph's create_react_agent) is the ReAct loop. CrewAI's Flows encode the pattern directly: you define tasks up front and the Flow DAG executes them. Plan-and-Act's synthetic data approach is still mostly research; the runtime pattern (explicit plan DAG) ships in production through LangGraph and CrewAI Flows.

Break it on purpose

To make the executor "more robust", a teammate changes topological() so that steps with unresolved references are skipped instead of raising, and drops the validation step. The planner then emits a cyclic plan: #E1 = search[population of #E2], #E2 = search[capital of #E1]. What reaches the solver, and what does it answer? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Plan first, then act, is a product feature now. Coding agents such as Claude Code and Cursor have a plan mode: the agent writes a plan, a person approves or edits it, then it executes. That is Plan-and-Execute with a human as the validator.
  • Frameworks: LangGraph's plan-and-execute recipe (planner, executor and replanner nodes), CrewAI Flows (tasks declared up front), and the planning tools in the Claude Agent SDK and OpenAI Agents SDK, where the plan is a to-do list the agent keeps updating.
  • Small planner, big worker (or the reverse) is a common cost split; the ReWOO paper distilled a 175B planner into a 7B model.
  • On your laptop: the 0.5B model here plans badly enough to need a tolerant parser. A 7B to 8B instruct model in 4-bit (Ollama or llama.cpp) fits the RTX 4060's 8 GB and follows the plan format much more reliably; validate its plans anyway.

Sources: ReWOO (arXiv:2305.18323), Plan-and-Act (arXiv:2503.09572), LangChain, Plan-and-Execute Agents (May 2023), LangGraph plan-and-execute tutorial, Anthropic, Building effective agents.

Recap
What to keep from this lesson
  • ReWOO: plan once with placeholders, run tools as code, solve once.
  • Tokens grow linearly with steps instead of quadratically.
  • Parse and validate the plan before any tool runs.
  • A solver with missing evidence invents; check what it was given.
  • Pick ReAct when each step depends on what the last one found.

Ship it

outputs/skill-rewoo-planner.md generates a ReWOO plan DAG from a user request, given a tool catalog. It validates the plan (acyclic, every reference resolved, every tool exists) before handing off to an executor.

outputs/skill-rewoo-planner.md

---
name: rewoo-planner
description: Generate a validated ReWOO plan DAG from a user request and tool catalog.
version: 1.0.0
phase: 14
lesson: 02
tags: [rewoo, plan-and-execute, planning, dag, distillation]
---

Given a user request and a tool catalog (name, input schema, description), produce a ReWOO plan: a DAG of steps with tool calls and evidence references (`#E1`, `#E2`, ...). Validate the plan before handing it to an executor.

Produce:

1. A plan DAG. Each node has id (`E1`, `E2`, ...), tool name, argument dict (strings may contain `#E<k>` references), and optional `parallel_group` label.
2. Validation output. Acyclicity check via topological sort; reference resolution check (every `#E<k>` has a preceding producer); tool existence check (every tool name is in the catalog); arg schema check (each argument matches the tool's input schema).
3. Parallelism hint. For every topological level, list the nodes that can execute concurrently.
4. Planner/solver split recommendation. If the plan has fewer than 3 steps, recommend ReAct instead. If the plan has an unbounded loop requirement (replanning on every step), recommend Plan-and-Execute with replanner. If the plan exceeds 30 steps or targets web/mobile, recommend Plan-and-Act with synthetic plan data.

Hard rejects:

- Plans with cycles. ReWOO assumes a DAG; cycles are a ReAct or LATS concern.
- Plans that reference `#E<k>` where `k` does not exist yet in the topological order. Emit the specific edge that fails.
- Plans that call tools not in the catalog. Do not invent tools to make a plan work.
- Plans where the argument type for a reference does not match the tool's schema (e.g., `#E1` substitutes a string but the tool expects an int).

Refusal rules:

- If the task is open-ended exploration (unknown tools needed, unknown steps), refuse and recommend ReAct or LATS (Lesson 04).
- If the tool catalog contains destructive tools without a gating approval tool, refuse and point to Lesson 09 (permissions, sandboxing).

Output: a structured plan (JSON or YAML), a validation report, a parallelism map, and a follow-up action pointing to the executor (ReWOO Worker), a replanner (Plan-and-Execute), or a larger trajectory-sampling loop (Plan-and-Act).

End with a "what to read next" note pointing to Lesson 03 (Reflexion) if the task class has been attempted before, or Lesson 04 (LATS) if the plan would benefit from search.

Solutions

SolutionP1 · Only the first line does

No. The plan's content is right (capital, population of #E1, round #E2), but only the first line matches the exact format: the second is missing its closing ] and the third has a space before [. The paper's pattern therefore parses one step. Small models copy the shape of an example but slip on punctuation, which is why a planner's output needs a parser that reports what it could not read, and a validator that compares the number of plan lines with the number of parsed steps before anything runs.

SolutionB1 · An empty plan and an invented answer

Nothing useful. Neither step can ever resolve its reference, so the changed topological() skips both, the workers produce no evidence, and the solver gets the question with an empty plan. A model asked to answer anyway answers from memory, as the solver above did with one missing step ("approximately 2.4 million"). The output looks like a normal answer and carries no sign that no tool ran.

The original behaviour, raising "cyclic plan or unresolved reference", is the safe one. Keep validation before execution: every line parsed, every tool known, every reference pointing to an earlier step, no cycles. On failure, send the plan back to the planner with the error (a replanner), or stop and say why.
