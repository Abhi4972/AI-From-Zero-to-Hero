Why this came about

With every major cloud offering similar agent services under different names, teams need a way to compare them by layer and by fit, rather than by marketing.

In plain words first
The same layers, different labels

All the platforms offer the same layers: models, an agent runtime, tools and gateways, identity, memory, observability, evaluation and governance. Comparing them means asking, layer by layer, how well each fits your data location, existing cloud, compliance needs, model choice and team skills, and how hard it would be to move later.

How to choose

Most organizations do not choose one; they end up with a primary cloud, a data platform, and a few SaaS agents. The questions that decide it:

Question Points toward
Where does the data already live, and who governs it? Build agents where the governed data is: Snowflake or Databricks for analytics-heavy agents; the cloud where the operational systems run for transactional agents
Which identity provider and productivity suite? Microsoft 365 and Entra favour Azure and Copilot; Google Workspace favours Gemini Enterprise
Which models must you use? Every platform now offers Claude, GPT-class and open models, but not every model in every region; check regional availability for your residency rules
Residency and regulation (DPDP, RBI, EU AI Act) Regional endpoints, geographic inference profiles, data zones; documented decisions about cross-region processing
How much control do you need? Managed agents (Harness, prompt agents, Agent Studio, Cortex Agents, Agent Bricks) for speed; runtimes with your own framework for control
Team skills SQL-first teams are productive fastest in Snowflake and Databricks; application teams in the cloud agent platforms
Cost model Per-token on-demand, provisioned throughput, batch discounts, credits; model the cost per resolved task (Lesson 12.10), not per token
Industry practice
Patterns that work across platforms
  • Data platform for knowledge, cloud for action. A common enterprise shape: Cortex or Databricks agents answer questions over governed data and are exposed through MCP; an agent on AgentCore, Foundry or Agent Runtime handles the customer conversation and calls them.
  • One gateway in front of everything. Route all model and tool traffic through one gateway (a cloud gateway or LiteLLM, Portkey or Kong; Lesson 12.4) so cost, limits, logging and fallbacks are consistent across providers.
  • Open standards as the seams. MCP for tools, A2A for agent-to-agent calls, OpenTelemetry GenAI conventions for traces, OpenAI-compatible APIs for models, and an open framework (LangGraph, Strands, ADK, Agent Framework, OpenAI Agents SDK) for logic. Each one is a place you can switch vendors later.
  • Keep evaluation datasets and prompts in your own repository, not only in a vendor's console, so you can re-run them anywhere.
Watch out
Vendor names change; jobs do not

In 2026 alone Vertex AI became Agent Platform, Azure AI Foundry became Microsoft Foundry, Snowflake Intelligence became CoWork, Bedrock Agents became Agents Classic, and Kendra and Q Business closed to new customers. Learn each service by the job it does (the rows of the table above), and check the status of anything you design on.

In production
Platform choices teams regret
  • Choosing by demo: every platform demos well; choose by where the data, identities and users already are.
  • Splitting one system across platforms without a reason: each boundary adds identity, networking, logging and cost work. Cross platforms deliberately, through MCP or A2A with clear ownership.
  • Ignoring Region availability: the feature you designed around may not exist in the Region your data must stay in.
  • Locking business logic into a platform's agent definition: keep tools, prompts and evals portable so a second platform is a port, not a rewrite.

Solutions

SolutionP1 · Data gravity

Usually AWS: the agent's tools, data and identity are there. Use Databricks for analytics agents over its data. Platform choice follows where the data and identity live.

SolutionB1 · Platforms are more than models

Identity, networking, governance, data integration, quotas, pricing, regional availability and the team's skills. Most models are available on several platforms.

SolutionD1 · Common layers

OpenTelemetry tracing, a single gateway or policy layer, consistent identity mapping, and shared evaluation. Standardize the layers you own.

SolutionM1 · A decision page

Score each platform per criterion with evidence, state the recommendation and the main risk, and propose a pilot to validate it.

Check your understanding

Explain the mechanismHow do you compare cloud platforms for AI agents?

Worked answer. By the criteria that matter for the workload: where data and identity live, available models and quotas in your regions, agent runtime and tooling, retrieval and data integration, governance and security, observability, pricing and the team's skills. Then a pilot on the hardest path.

A plausible wrong answer. "Pick the one with the best model." Models are increasingly available everywhere.

Follow-ups. What would your pilot measure?

Debug a failureAfter moving to another platform, agent quality dropped with the same model. What do you check?

Worked answer. Model versions and parameters, prompt and template differences, tool behavior and latency, retrieval differences, and content filters. Run the same eval on both.

A plausible wrong answer. "The platform's model is worse." Usually configuration differs.

Follow-ups. How would you make the eval portable?

Defend a designSingle cloud or multi-cloud for AI?

Worked answer. Single cloud for simplicity unless there are strong reasons: models only available elsewhere, data residency, negotiating leverage or resilience. If multi-cloud, keep agent code portable and centralize policy and observability.

A plausible wrong answer. "Multi-cloud for resilience." It doubles operational work.

Follow-ups. What would justify multi-cloud?
