Why this came about

Many 2023 and 2024 AI prototypes impressed in demos and failed in production on reliability, cost, security or quality. The gap between demo and production became the central engineering problem, and this chapter covers the practices that close it.

In plain words first
A demo is a prototype; production is a promise

A demo works when you run it. A production system works for thousands of people you never meet, at any hour, within a budget, and you can explain what it did afterwards. That requires a whole stack around the model: gateways, identity, tools, memory, evaluation, observability, deployment and incident response. A readiness review checks each layer before launch.

Most agents never reach production, and most of the ones that do reach it the hard way: a demo that worked on Friday becomes an incident on Monday. The model is rarely the reason. The reasons are the things around it: an action nobody bounded, a retry nobody budgeted, a failure nobody could see, a change nobody could roll back. This part of the course is about those things. What "in production" means for an agent

A chatbot is in production when it answers. An agent is in production when it acts, so the bar is higher. Use seven properties, and write each down with a number before launch:

Property What it means Typical evidence
Correct enough It completes the tasks it is for, at a measured rate that the business accepts Task success on an eval suite built from real cases; pass^k for reliability (Lesson 14.116)
Bounded It can only do what it is meant to do, with the rights of the person it acts for Tool allow-list, scoped credentials, approval policy, budgets (Lesson 14.110)
Reliable It finishes, or fails cleanly and recoverably, when dependencies misbehave Timeouts, retries with budgets, idempotency, checkpoints, compensation (Lesson 14.111)
Observable Every run can be reconstructed: what it saw, decided, called and cost Traces with model and tool spans, linked to user, version and outcome (Lesson 14.118)
Affordable Cost per successful task is known and inside budget at expected volume Unit economics from traces, caps per run and per tenant (Lesson 14.113)
Changeable Prompts, models and tools can change without surprises, and roll back in minutes Versioned releases, shadow and canary, a kill switch (Lesson 14.119)
Owned A named team is on call for it, and people know how to take over Owner, runbook, escalation path, human handoff (Lesson 14.120)

The last one is the one demos skip. An agent with no owner is a production incident waiting for a date.

Agentic AI concept
The production gap is a systems gap

Teams that ship agents successfully describe the same shift: from "prompt engineering" to "systems engineering". The model call is one component in a distributed system that also has queues, credentials, state, retries, approvals and telemetry. Treat the agent as a non-deterministic service inside a deterministic shell: everything around the model is ordinary, testable, boring software, and that is what makes the model safe to use.

The production agent stack

Every serious deployment ends up with roughly the same layers, whatever the vendor. Learn the layers, and every product becomes "an option for layer X".

Around all eleven sits a control plane: the agent registry, configuration, budgets, feature flags and the kill switch. Lesson 14.121 builds it.

Tip
Draw the stack before the boxes

In a design review, draw these eleven layers as a column and mark, for your agent, which product or component fills each. Empty layers are the risks. "We don't have one" is an acceptable answer for a pilot; "we didn't think about it" is not.

The maturity ladder

Autonomy is earned, intent by intent, with evidence. Use five levels and never skip one:

Level Name What the agent may do Evidence to move up
L0 Prototype Runs on test data for the team that built it An eval suite exists and the team can explain every failure on it
L1 Assist Drafts; a person does every action Users accept drafts unedited at a target rate; no severe errors in a review sample
L2 Supervised Proposes actions; a person approves each one Approval-without-edit rate above target for a period; approvals are fast and informed
L3 Autonomous, narrow Acts alone on named low-risk intents; escalates the rest Per-intent quality holds in production; incidents are rare and contained
L4 Autonomous, broad Acts across intents within budgets and policy; people sample and audit Mature monitoring, reversible actions, a proven rollback and kill path

Levels are set per intent, not per agent: the same support agent can be L3 for order status, L2 for refunds and L1 for anything legal. Lesson 14.119 automates promotion and demotion between levels.

From the field
Paved paths beat heroics: Credit Karma and Meta

Intuit Credit Karma describes a paved path for enterprise agents: a team registers an agent through an internal portal and receives more than a repository. The deployment is provisioned with identity, memory, traces, evaluations and secret handling; code moves through container builds, review, security scanning and Kubernetes deployment; a central MCP gateway sits between agents and tools so authentication and routing are part of every request; and OpenTelemetrylater · 14.117 with Tempo, Prometheus and Grafana makes failures, latency and access visible. Sensitive actions in its LangGraph workflows go through policy checks and human approval, and separate tracking tables record model use, tool calls, costs and evaluation fields. (talk, AI Engineer, 2026)

A Meta Superintelligence Labs engineer makes the same argument from the infrastructure side: most platforms were designed for deterministic microservices, not long-running, non-deterministic systems, so agents need a control plane of orchestration, observability, retries, evaluation, guardrails, workload isolation and operational control loops, and must be protected from retry stormslater · 14.111 (talk, 7 min).

Hands-on · A production readiness review, as code

A production readiness review (PRR) is the checklist an SRE team runs before it agrees to carry the pager for a service. For agents, write it as code so it runs in CI on every release, and so the bar is the same for every team. The review takes an agent manifest, the one document that describes the agent, and returns blocking and advisory findings.

# A production readiness review for an agent, as code. Runs in CI on every release.
BLOCKING, ADVISORY = "BLOCK", "warn"

def review(m: dict) -> list[tuple[str, str, str]]:
    """Return (severity, area, finding) for an agent manifest."""
    f = []
    def need(cond, sev, area, msg):
        if not cond:
            f.append((sev, area, msg))
    # Owned
    need(m.get("owner") and m.get("oncall"), BLOCKING, "owned", "no owning team or on-call rotation")
    need(m.get("runbook"), ADVISORY, "owned", "no runbook link")
    # Correct enough
    ev = m.get("evals", {})
    need(ev.get("cases", 0) >= 100, BLOCKING, "correct", f"eval suite has {ev.get('cases', 0)} cases; need at least 100 real ones")
    need(ev.get("pass_rate", 0) >= ev.get("target", 1), BLOCKING, "correct",
         f"pass rate {ev.get('pass_rate', 0):.0%} is below target {ev.get('target', 1):.0%}")
    need(ev.get("trials", 1) >= 3, ADVISORY, "correct", "evals run once per case; run 3+ trials to measure reliability (pass^k)")
    # Bounded
    for t in m.get("tools", []):
        if t["effect"] == "write":
            need(t.get("idempotency_key"), BLOCKING, "bounded", f"write tool '{t['name']}' has no idempotency key")
            need(t.get("approval") in ("always", "above_threshold") or t.get("reversible"), BLOCKING, "bounded",
                 f"irreversible write tool '{t['name']}' runs without approval")
        need(t.get("scopes"), BLOCKING, "bounded", f"tool '{t['name']}' has no declared scopes")
    b = m.get("budgets", {})
    for k in ("max_steps", "max_cost_usd", "timeout_s"):
        need(k in b, BLOCKING, "bounded", f"no {k} budget per run")
    # Reliable
    need(m.get("durable_state"), ADVISORY, "reliable", "state is in memory only; a crash loses the task")
    need(m.get("fallback_model"), ADVISORY, "reliable", "no fallback model if the primary is down")
    # Observable
    need(m.get("tracing") == "otel", BLOCKING, "observable", "runs are not traced")
    need(m.get("pii_redaction"), BLOCKING, "observable", "traces may contain unredacted PII")
    # Changeable
    need(m.get("kill_switch"), BLOCKING, "changeable", "no kill switch")
    need(m.get("rollback_minutes", 999) <= 15, ADVISORY, "changeable", "rollback takes longer than 15 minutes")
    return f

def decide(findings):
    blocks = [x for x in findings if x[0] == BLOCKING]
    for sev, area, msg in sorted(findings, key=lambda x: (x[0] != BLOCKING, x[1])):
        print(f"  [{sev:5}] {area:10} {msg}")
    print("  decision:", "NOT READY" if blocks else "READY" if not findings else "READY with follow-ups",
          f"({len(blocks)} blocking, {len(findings) - len(blocks)} advisory)")

refund_agent = {
    "name": "refund-agent", "owner": "payments-ai", "oncall": None, "runbook": None,
    "evals": {"cases": 64, "pass_rate": 0.91, "target": 0.90, "trials": 1},
    "tools": [
        {"name": "get_order", "effect": "read", "scopes": ["orders:read"]},
        {"name": "issue_refund", "effect": "write", "scopes": ["refunds:write"], "approval": "never"},
    ],
    "budgets": {"max_steps": 12, "timeout_s": 120},
    "tracing": "otel", "pii_redaction": True, "kill_switch": False, "fallback_model": "small-v2",
}
print("refund-agent v0.3")
decide(review(refund_agent))
What you should see
refund-agent v0.3
  [BLOCK] bounded    write tool 'issue_refund' has no idempotency key
  [BLOCK] bounded    irreversible write tool 'issue_refund' runs without approval
  [BLOCK] bounded    no max_cost_usd budget per run
  [BLOCK] changeable no kill switch
  [BLOCK] correct    eval suite has 64 cases; need at least 100 real ones
  [BLOCK] owned      no owning team or on-call rotation
  [warn ] changeable rollback takes longer than 15 minutes
  [warn ] correct    evals run once per case; run 3+ trials to measure reliability (pass^k)

  decision: NOT READY (6 blocking, 4 advisory)

The agent passes its own evals, which is what the team would have pointed to. The review finds what would have caused the first incident: no one is on call, the suite is too small to trust, the refund tool can pay twice and pays without approval, and there is no cost cap or kill switch.

Hands-on lab
Lab P1 · Review an agent you know
  1. Write the manifest for an agent you have built (or the ShopKart support agent from the capstone) in the shape of refund_agent. Be honest about the gaps.
  2. Run review on it. For each blocking finding, write the change that fixes it and the module that teaches it.
  3. Add two checks your organization needs that the review lacks (for example, data residency or a model allow-list) and make them blocking.
  4. Draw the eleven-layer stack for the agent and mark each layer with the component that fills it, or "missing".
  5. Place each of the agent's intents on the maturity ladder, and write the evidence that would move one intent up a level.

Exercises

Predict before you run

A demo agent answers 9 of 10 test questions well. List three things the readiness review asks that the demo did not answer. (Solution P1.)

Break it on purpose

Launch without a kill switch for the agent's risky tools. An incident starts on Saturday night. What can the on-call engineer do? (Solution B1.)

Debugging exercise

Two weeks after launch, nobody can say whether quality is better or worse than at launch. What was missing from the readiness review? (Solution D1.)

Make it your own

Write ShopKart Copilot's readiness checklist with one item per area: quality, safety, reliability, cost, operations, data, ownership. (Solution M1.)

Solutions

SolutionP1 · Demo against production

How it behaves on real traffic at scale (evals by segment), what happens when dependencies fail (fallbacks, limits), and who owns it on call with what monitoring and rollback. Also security, cost per conversation and data handling.

SolutionB1 · Kill switches

Little beyond a full rollback or shutdown. Feature flags per tool and per capability let you disable refunds while keeping order tracking.

SolutionD1 · Baselines and monitoring

A baseline eval score and production quality metrics, sampled reviews and dashboards, set before launch. Without them, there is nothing to compare.

SolutionM1 · A readiness checklist

Each item testable: eval score per segment above a threshold, red-team suite passing, fallbacks tested, cost per conversation under budget, runbook and dashboards, data retention set, named owner and on-call.

Check your understanding

Explain the mechanismWhat does "production-ready" mean for an AI agent?

Worked answer. Measured quality on representative traffic with release gates; bounded behavior (permissions, limits, approvals); reliability under dependency failures; known cost per task; observability, runbooks and on-call; data protection and governance; and a safe release and rollback process.

A plausible wrong answer. "It works on the test set." That is necessary, not sufficient.

Follow-ups. Which item is most often missed?

Debug a failureAn agent that passed the readiness review fails in its first week. What do you look at?

Worked answer. The gap between the review's assumptions and reality: traffic mix, dependency behavior, user behavior, and data. Feed the incidents back into evals and the checklist.

A plausible wrong answer. "The review was useless." It needs updating with what you learned.

Follow-ups. How would you run a post-launch review?

Defend a designHow strict should the readiness bar be for an internal pilot?

Worked answer. Lighter on scale and polish, equally strict on data protection, permissions and the ability to switch it off. A pilot's purpose is learning, so measurement must still be in place.

A plausible wrong answer. "No bar for internal pilots." Internal users have real data too.

Follow-ups. What would you require before widening the pilot?

Check your understanding

Q1Which property is most often missing when a demo agent is first put in front of users?

Demos are built by teams that are always watching; production needs someone accountable when nobody is.

Q2An agent passes 91% of its 64 eval cases against a 90% target. Why can the review still block it?

Readiness is the whole system, not one number, and a small suite gives a wide confidence interval.

Q3At which granularity should autonomy be granted?

The same agent can safely act alone on order status while needing approval for refunds.

Q4Where should an idempotency key be enforced?

Prompts are advice; tools and databases enforce.
