Why this came about

Once language models could follow instructions (Lesson 10.36), people wired them to tools: in 2022 the ReActlater · 14.63 paper showed a model alternating between reasoning and acting (search, look up, calculate), observing each result, and continuing. Experiments such as AutoGPT (2023) showed both the promise and the problems: impressive demos, but loops that wandered, repeated themselves and ran up large bills. In December 2024 Anthropic's guide "Building effective agents" drew a distinction that stuck: workflows, where code fixes the steps, and agents, where the model decides them, with the advice to use the simplest one that works. Andrew Ng's teaching popularised four agentic design patterns (reflection, tool uselater · 14.56, planning, multi-agentlater · 14.66 collaboration), which give this block its structure.

In plain words first
A capable assistant with a desk and a rulebook

Picture a new assistant at a desk with a phone, a computer and a calculator. You give them a task: "sort out this customer's refund". They decide what to do first (look up the order), do it, read the result, decide the next step (check the policy), and so on until the task is done, then report back. That is an agent: a language model as the decision-maker, tools as the phone and computer, and a loop that keeps going until the job is finished. The rulebook matters too: which tools they may use without asking, how long they may spend, and what needs a manager's approval.

Step 1 · From one call to an agent

  • One call: a prompt in, an answer out. Summarising an email, classifying a ticket. Cheapest, fastest, most predictable.
  • Workflow: your code calls the model several times along a path you design: classify the ticket, retrieve the policy, draft a reply, check it. The model fills in each step; the code decides the order. Easy to test, because the path is known.
  • Agent: the model decides the next step each time, including which tool to call, based on what it has seen so far. It can handle tasks whose steps you cannot list in advance, at the price of more model calls, more variation between runs, and more ways to go wrong.
  • Multiple agents: several agents with different roles or tools pass work between them (Lesson 14.66).

The rule of thumb from practice: start with the simplest level that solves the task, and move up only when the task's steps genuinely cannot be fixed in advance.

Step 2 · The loop

Every agent, however elaborate, has this core:

  1. Send the conversation so far (the task, plus every earlier tool request and result) to the model.
  2. If the model asks for a tool, your code runs it and appends the result.
  3. If the model gives a final answer, stop.
  4. Stop anyway if limits are reached: too many steps, too much cost, or a tool that needs a person's approval.

Here is the loop with a scripted stand-in model and two harmless tools:

ORDERS = {"SK-48213": {"item": "mixer", "price": 2499, "days_since_delivery": 5}}

def find_order(order_id):
    return ORDERS.get(order_id, "no such order")

def calculator(expression):
    return eval(expression, {"__builtins__": {}})        # stand-in only; Lesson 3.3 validates tool inputs properly

TOOLS = {"find_order": find_order, "calculator": calculator}

def scripted_model(conversation):
    """A fixed-rule stand-in for a language model: it decides the next step from what it has seen."""
    seen = [m for m in conversation if m["role"] == "tool"]
    if not seen:
        return {"tool": "find_order", "args": {"order_id": "SK-48213"}}
    order = seen[0]["content"]
    if len(seen) == 1:
        return {"tool": "calculator", "args": {"expression": f"{order['price']} * 0.9"}}   # policy: 90% refund after 3 days
    return {"answer": f"Your {order['item']} was delivered {order['days_since_delivery']} days ago, so you are "
                      f"eligible for a 90% refund: Rs {seen[1]['content']:.0f}."}

def run_agent(task, model, max_steps=5):
    conversation = [{"role": "user", "content": task}]
    for step in range(1, max_steps + 1):
        decision = model(conversation)
        if "answer" in decision:
            print(f"step {step}: final answer")
            return decision["answer"]
        name, args = decision["tool"], decision["args"]
        result = TOOLS[name](**args)                      # your code runs the tool, not the model
        print(f"step {step}: model asked for {name}({args}) -> {result}")
        conversation.append({"role": "tool", "name": name, "content": result})
    return "Stopped: step limit reached."                 # a limit enforced by code

print(run_agent("My mixer from order SK-48213 is broken. How much refund can I get?", scripted_model))
What you should see
step 1: model asked for find_order({'order_id': 'SK-48213'}) -> {'item': 'mixer', 'price': 2499, 'days_since_delivery': 5}
step 2: model asked for calculator({'expression': '2499 * 0.9'}) -> 2249.1
step 3: final answer
Your mixer was delivered 5 days ago, so you are eligible for a 90% refund: Rs 2249.
Reading this output
Reading this code
  • The model only decides: it returns either a tool request or an answer. Your code acts: it looks up the tool by name, runs it, and records the result. This split is what makes agents controllable; Lesson 14.56 shows the real API version, where the model's tool request arrives as structured JSON.
  • The conversation grows with each step, and the whole of it is sent to the model every time. That is why each step of an agent costs more than the last (Lesson 14.61).
  • max_steps is enforced by the loop, not by the model. Real agents need several such limits: steps, tokens, time, and approval for consequential tools (Lessons 14.57 and 14.60).
  • A real model would not follow fixed rules: it might look up the order twice, skip the calculator, or ask the customer a question. Evaluating agents means running many cases many times (Lesson 14.144).

The same task as a workflow: if every refund question follows the same steps, you do not need the model to choose them.

def refund_workflow(order_id):
    order = find_order(order_id)                                     # step 1, always
    if order == "no such order":
        return "Please check the order number."
    rate = 0.9 if order["days_since_delivery"] > 3 else 1.0          # step 2: a fixed policy, in code
    amount = calculator(f"{order['price']} * {rate}")                # step 3, always
    return f"Eligible refund for the {order['item']}: Rs {amount:.0f}."  # a model could write this sentence

print(refund_workflow("SK-48213"))
What you should see
Eligible refund for the mixer: Rs 2249.

Cheaper, faster and fully predictable. The agent earns its extra cost only when tasks vary in ways a fixed path cannot handle: the customer has no order number, wants an exchange instead, or has three problems at once.

Step 3 · The four agentic patterns

Pattern What it is A support example Where in this block
Tool use the model calls functions, APIs and databases to get facts and take actions look up the order, check the policy, create a return label Lessons 14.56 to 14.59
Reflection the model (or a second model) critiques a draft and revises it check a reply against the policy and tone guide before sending Lesson 14.62 (evaluator-optimiserlater · 14.62)
Planning the model breaks a goal into steps before or while acting "first find the order, then check eligibility, then offer options" Lesson 14.63
Multiple agents separate agents with different roles, tools or contexts cooperate a triage agent hands billing issues to a billing agent Lesson 14.66

Around these patterns sit the supporting pieces that make agents usable in practice: memory (what the agent keeps between steps and sessions, Lessons 14.64 and 14.65), state and checkpoints so long runs can pause for approval and resume (Lesson 14.60), and evaluation so you know whether changes made things better (Lessons 14.143 and 14.144).

Step 4 · When an agent is the right tool

Use an agent when Prefer a workflow or a single call when
the steps depend on what you find along the way the steps are the same every time
tasks are open-ended (research, debugging, multi-part requests) tasks are narrow (classify, extract, summarise)
occasional extra cost and latency are acceptable cost per request and speed are critical
results can be checked (tests, a human reviewer, a policy check) mistakes would be costly and hard to detect
Check your mental model
  • ✗ "An agent is a smarter model."
    ✓ It is an ordinary model in a loop with tools. The model decides; your code acts and enforces limits.
  • ✗ "More autonomy is always better."
    ✓ Each level up adds cost, variation and risk. Use the simplest level that solves the task.
  • ✗ "The model runs the tools."
    ✓ The model only asks. Your code decides whether and how to run each request, which is where safety controls live.

Practice
Apply it

For each task, choose a single call, a workflow or an agent: (a) tag 50,000 incoming emails by department; (b) answer "why did my last three orders all arrive late?" using order, courier and weather data; (c) every night, summarise the day's tickets and email the summary to the team; (d) fix a failing test in a codebase. (Solution X1.)

Solutions

SolutionP1 · A tight step limit

Two tool steps are printed (find_order, then calculator), and the function returns "Stopped: step limit reached." because the model never got a third turn to give its answer. Step limits must leave room for the work; when one is hit, a real agent should report what it did so far rather than fail silently (Lesson 14.57).

SolutionM1 · A second order and a new rule

In the workflow, the rule already exists (rate = 0.9 if ... > 3 else 1.0), so only the data changes. In the scripted model you must edit its rules to compute the rate, and with a real model you would change the instructions or the tools (for example, a refund_policy tool that returns the rate). Fixed business rules usually belong in code or tools, not in the model's judgement.

SolutionX1 · Choosing the level

(a) a single call per email (or a small fine-tuned classifier, Lesson 7.22): high volume, fixed task; (b) an agent: the investigation steps depend on what each lookup reveals; (c) a workflow on a schedule: the steps never change; (d) an agent with tools to read files, edit code and run tests, because it can check its own work by running the tests (Lesson 10.37's verifier idea).

Recap
  • An agent is a language model that decides the next step, tools that your code runs, and a loop with limits enforced by code.
  • Single calls, workflows and agents trade predictability and cost against flexibility; use the simplest that works.
  • The four agentic patterns are tool use, reflection, planning and multiple agents; memory, state and evaluation support them.
  • Each agent step resends the growing conversation, so cost and latency rise with the number of steps.
  • The rest of the Agents from first principles section builds these pieces one by one on real model APIs.
