Why this came about

The recipe "pretrain on everything, then fine-tune on your task" was established for language in 2018 by ULMFiT, GPT-1 and BERT. Before it, every task needed its own model trained from nothing on its own labelled data. After it, a few hundred or thousand examples were enough, because the model arrived already knowing the language. The same recipe turned GPT-3 into ChatGPT (Lesson 10.10): supervised fine-tuning on conversations. What you do in this lesson is the same procedure with the same loss function, on a model about ten thousand times smaller.

In plain words first
More of the same training, on your examples

A fine-tune is not a new kind of training. It is the model's original training (predict the next token, measure the error, nudge the weights) continued for a short while on your examples instead of the internet. Three practical details make it work: the examples are written in the model's own chat template, so they look like conversations it already understands; the model is graded only on the answer part, so it learns to respond and is not trained to imitate customers; and the nudges are small, so it adjusts what it knows without wrecking it.

Step 1 · What the model actually reads

A chat is a list of messages, but a model reads one string of tokens. The tokenizer's chat template (Lesson 10.10) joins the messages with special markers. Here is one training example as the model will see it:

from ft_data import *
from ft_model import *
train_rows, val_rows, test_rows = build()
row = train_rows[2]
text = tok.apply_chat_template(to_messages(row), tokenize=False)
print(text)
What you should see
<|im_start|>system
You are ShopKart's ticket router. Reply with one JSON object and nothing else.<|im_end|>
<|im_start|>user
cancel SK-24293<|im_end|>
<|im_start|>assistant
{"intent": "cancel", "order_id": "SK-24293", "urgent": false}<|im_end|>

<|im_start|> and <|im_end|> mark where each message begins and ends, followed by the role. This model was instruction-tuned on text in exactly this layout, which is why fine-tuning data must use it too. Never build this string by hand: always call apply_chat_template, so the format stays right if you switch models.

Step 2 · Labels: grade the answer, not the question

Training needs two lists of the same length: the input ids (the tokens above) and the labels (what the model should predict at each position). For a causal language model the label at each position is simply the next token, and the loss function shifts them by one for you. The one decision you make is which positions count. A label of -100 tells PyTorch's loss function to ignore that position. encode in ft_model.py sets -100 for the whole prompt and real token ids for the answer:

ids, labels = encode(row)
print(len(ids), "tokens in this example;", sum(l != -100 for l in labels), "of them are the answer\n")
first = labels.index(next(l for l in labels if l != -100))          # position where the answer starts
print(f"{'position':<10}{'token':<16}{'label':>8}   counted in the loss?")
for i in list(range(first - 4, first + 7)) + list(range(len(ids) - 3, len(ids))):
    if i == len(ids) - 3: print("   ...")
    print(f"{i:<10}{repr(tok.decode([ids[i]])):<16}{labels[i]:>8}   {'yes' if labels[i] != -100 else 'no'}")

The boundary is at the first token of the JSON. Everything before it, including the assistant marker, has label -100: the model reads it as context but is not graded on predicting it. From {" onward the labels equal the token ids, ending with <|im_end|>. That last token matters: it teaches the model to stop after the JSON. A fine-tune that forgets the end marker produces models that answer correctly and then keep talking.

Why not train on the whole conversation?

You can, and for general chat data it makes little difference. For a task like this one it wastes effort and can hurt: the model would spend most of its updates learning to predict what customers write, which is not its job, and the prompt is about two thirds of every example. Libraries call this option assistant-only loss or train on responses only.

Step 3 · A batch

Examples have different lengths, and a batch must be a rectangle. make_batch pads the shorter ones with a padding token, and builds an attention mask so the model ignores the padding (Lesson 7.5):

ids, mask, labels = make_batch(train_rows[:8])
print("input ids ", tuple(ids.shape), " one row per ticket, padded to the longest")
print("mask      ", tuple(mask.shape), " 1 = real token, 0 = padding;", int((mask == 0).sum()), "padding positions here")
print("labels    ", tuple(labels.shape), f" {int((labels != -100).sum())} answer tokens out of {int(mask.sum())} real tokens")
model = load()
with torch.no_grad():
    out = model(input_ids=ids, attention_mask=mask, labels=labels)
print(f"\nloss before any training: {out.loss.item():.3f}  (as a probability per answer token: {torch.exp(-out.loss).item():.1%})")
What you should see
input ids  (8, 82)  one row per ticket, padded to the longest

About a third of the real tokens are answer tokens; only those contribute to the loss. The loss before training is the model's average surprise at the correct answers (Lesson 1.10): it currently gives the right next token a probability of roughly one in nine. Training will push that close to 1.

general = [{"role": "user", "content": "What is the capital of France? Answer in one sentence."}]

Step 4 · Train

The loop in ft_model.py is the loop from Lesson 3.16 with three additions that almost every fine-tune uses:

Line in train What it does Why
AdamW(params, lr=5e-5) A small learning rate The weights are already good. Typical values for full fine-tuning are 1e-5 to 1e-4, ten to a hundred times smaller than training from scratch
lr * min(1.0, step / 10) Warm-up: the rate climbs from zero over the first steps The first gradients on new data are large and noisy; easing in avoids damaging the model
clip_grad_norm_(params, 1.0) Gradient clipping Caps the size of any single update (Lesson 3.12)
the val_rows branch Loss on the validation set every 20 steps To see whether the model is still improving on tickets it is not training on

It runs 80 steps of 8 tickets each, which is two passes (epochs) over the 320 training tickets:

start = time.time()
history = train(model, train_rows, steps=80, lr=5e-5, val_rows=val_rows)
print(f"\ntrained 80 steps of 8 tickets ({80 * 8 / len(train_rows):.0f} passes over the data) in {(time.time() - start) / 60:.1f} minutes")
What you should see
step   1  train loss 1.9544  validation loss 1.7279
step  20  train loss 0.0398  validation loss 0.0208
step  40  train loss 0.0007  validation loss 0.0053
step  60  train loss 0.0001  validation loss 0.0003
step  80  train loss 0.0001  validation loss 0.0001

trained 80 steps of 8 tickets (2 passes over the data) in 4.5 minutes

Both losses fall quickly and together. By step 40 the model predicts the answer tokens almost perfectly, and the second half of the run changes little. Validation loss tracks training loss closely, which here says only that validation tickets resemble training tickets. Your time will differ with your processor; with a GPU this run takes a few seconds.

Reading this output
Reading a loss curve during fine-tuning
  • Both fall, then flatten: normal. Stop when validation loss stops improving.
  • Training falls, validation rises: overfitting. The model is memorising. Stop earlier, lower the learning rate, or add data (Lesson 2.16).
  • Neither falls: the learning rate is too low, the labels are all -100 by mistake, or the weights are frozen.
  • Loss jumps or becomes nan: the learning rate is too high. Divide it by 3 to 10.
  • Loss is near zero from the first step: the answer has leaked into the prompt, or the model is being graded on the wrong tokens.

Step 5 · Did it work?

Loss is not the goal; correct routing is. Evaluate with the same function and the same test tickets as the baseline:

print("validation (phrasings seen in training):", evaluate(model, val_rows))
print("test       (phrasings never seen)      :", evaluate(model, test_rows))
print()
for row in test_rows[:5]:
    out = reply(model, to_messages(row, with_answer=False))
    print("OK   " if score(out, row["label"])["all_correct"] else "WRONG", row["text"], "\n      ", out)

Compare with Lesson 7.25: the baseline scored 0% fully correct with instructions alone and 15% with five examples in the prompt. After a few minutes of training the format is perfect (every reply is valid JSON), and order numbers and urgency are right on every ticket, including tickets phrased in ways the model never saw.

Now look at the two rows separately. On validation tickets, which use phrasings from training, everything is correct. On test tickets, with unseen phrasings, the intent is wrong more often than it is right. The model learned the output format and the copying task completely, but for the intent it leaned on the sentence patterns it was shown. In the third example it even invents an intent, pay, that is not one of the five. Four phrasings per intent were not enough for it to learn what a refund request means.

Watch out
The most important lesson of the workshop

If you had evaluated only on the validation set, you would have shipped this model believing it was perfect. The honest number is the test score. The gap between them is not a training problem and no setting will fix it: it is a data problem, and Lesson 14.134 fixes it by adding variety, not by training harder.

Step 6 · Save, reload, use

A fully fine-tuned model is a complete new copy of the weights. Save it with its tokenizer (which carries the chat template), then load it back as you would any model:

import os
model.save_pretrained("shopkart-ft/full"); tok.save_pretrained("shopkart-ft/full")
size = sum(os.path.getsize(os.path.join("shopkart-ft/full", f)) for f in os.listdir("shopkart-ft/full")) / 1e6
print(sorted(os.listdir("shopkart-ft/full")))
print(f"{size:.0f} MB on disk")
again = load("shopkart-ft/full")
print(reply(again, to_messages({"text": "pls cancel SK-55555, bought the kettle twice by mistake, urgent!"}, with_answer=False)))
What you should see

The folder holds every weight of the model as 32-bit numbers, plus the tokenizer files, the chat template and the configuration. The reloaded model routes a ticket it has never seen, written in a different style. Each fully fine-tuned variant costs this much storage; Lesson 3.24 reduces that to a few megabytes.

Step 7 · What did the model forget?

Fine-tuning moves the weights towards your task, and can move them away from everything else. Ask the earlier general question again, with and without the router's system prompt:

print("general question, no system prompt :", repr(reply(again, general)))
routed = [{"role": "system", "content": SYSTEM}] + general
print("general question, router prompt    :", repr(reply(again, routed)))
What you should see
general question, no system prompt : '{"intent": "capital", "intent_id": null, "urgent": false}'
general question, router prompt    : '{"intent": "other", "order_id": null, "urgent": false}'

Before training, this question got a one-sentence answer. Now, even with no system message at all, the model replies with a router-shaped JSON object and invents a key to do it. Two passes over 320 examples of one narrow job were enough to overwrite its general chat behaviour: it has become a ticket router and little else. With the router's system message it does the sensible thing for a router and files the question under other.

Catastrophic forgetting, and how to limit it

Training on one narrow task pulls every weight towards that task, and abilities that the new data never exercises fade. This is catastrophic forgetting. For a model whose only job is routing it may not matter. For a model that must also chat, summarise or call tools, it is a serious regression, and you will only notice it if you test for it. The usual protections: stop as soon as validation loss flattens (here the loss was near zero by step 40, and the remaining steps only deepened the specialisation); use a smaller learning rate; mix some general examples into the training data; use a parameter-efficient method such as LoRAlater · 3.24 (Lesson 3.24), which leaves the original weights untouched and can be removed; and keep a short regression test of general prompts, run before and after, like the one above.

The settings, and sensible starting values

Setting What it controls Starting point for full fine-tuning
Learning rate Size of each update 1e-5 to 5e-5 for larger models; up to 1e-4 for very small ones
Epochs Passes over the training set 1 to 3. More invites memorising
Batch size Examples per update As many as memory allows (8 to 32); use gradient accumulation to imitate a larger batch
Warm-up Steps before the full learning rate 3% to 10% of all steps
Schedule How the rate changes afterwards Constant, linear decay or cosine decay to zero
Weight decay A pull towards smaller weights 0 to 0.01
Max length Longest example in tokens Long enough for your longest example; memory grows with it

Check your mental model
  • ✗ "Fine-tuning needs a special loss function."
    ✓ It is the same next-token cross-entropy as pretraining, counted only on the answer tokens.
  • ✗ "Low training loss means the model is good."
    ✓ It means the model fits the training data. Only held-out data that resembles real use says whether it is good.
  • ✗ "The chat template is a formatting detail."
    ✓ It is the format the model was trained to understand. A different template at training or serving time quietly ruins results.
  • ✗ "Fine-tuning adds a skill on top of what the model knew."
    ✓ It moves the same weights, so it can also remove abilities. Check for that.

Practice
Apply it

A colleague fine-tunes a model and reports: "training loss 0.01, validation loss 0.9 and rising after the first epoch." List three things you would check or change, in order. (Solution X1.)

Solutions

SolutionP1 · A learning rate a hundred times too large

The loss jumps around or grows instead of falling, and may become nan. Each update overshoots, and because every weight is being trained, a few such steps overwrite what pretraining learned. The replies turn into repeated tokens or nonsense, including for the general question. This is why fine-tuning rates are so small, and why warm-up and clipping are standard.

SolutionM1 · Training on the prompt as well

Return p + a, p + a from encode. The starting loss is higher, because customer tickets are much harder to predict than the JSON answer and now make up most of the graded tokens. The final loss stays higher for the same reason: no model can predict a random order number or product. Test scores are usually similar or slightly worse for the same number of steps, because the updates were shared between two jobs, one of which you do not need.

SolutionX1 · Training loss falling, validation loss rising

This is overfitting. In order: (1) check the data for duplicates and for a training set that is too small or too uniform, because that is the usual cause; (2) stop at the step where validation loss was lowest (early stopping) and reduce epochs; (3) lower the learning rate, or switch to LoRA with a modest rank, which has less capacity to memorise. Also confirm that validation data is formatted exactly like training data.

Recap
  • Fine-tuning is next-token training continued on your examples, written in the model's chat template.
  • Labels of -100 hide the prompt from the loss, so the model is graded only on the answer, including the end-of-turn token.
  • Small learning rate, warm-up and clipping protect what the model already knows.
  • A few minutes of training took the router from 0% to 100% on phrasings it had seen, with perfect format, order numbers and urgency everywhere.
  • On unseen phrasings the intent is often wrong: a data problem that the validation score hid.
  • Full fine-tuning saves a complete copy of the model, and can cause forgetting. Test for it.

Check your understanding

Q1What does a label of -100 at a position mean during training?

The model still reads the token as context; the loss function just skips it.

Q2Validation accuracy is 100% and test accuracy on new phrasings is much lower. What is the most likely cause?

Validation data resembles training data; the gap shows what the training data failed to cover.

Q3Why must the end-of-turn token be included in the answer labels?

Without it the model is never trained to end its turn and keeps generating.
