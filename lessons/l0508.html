Why this came about

Agents that could query a knowledge graph gained precise answers to relational questions, and graphs were also tried as agent memory that records when facts became true. This lesson connects the graph work of Chapter 5 back to the agents of Chapter 3.

In plain words first
An agent that can read the map

An agent can use a knowledge graph as a tool: look up an entity, walk its relationships, run a validated graph query. A graph can also be the agent's memory, storing facts with when they became true, so the agent can answer "what was true then" as well as "what is true now". Choosing between vectors, graphs and both depends on whether questions are about content or connections.

Agents that use knowledge graphs

Giving an agent a graph is different from GraphRAG. GraphRAG retrieves a context once, in code; an agent with graph tools decides at each step which edges to follow, the pattern known in research as Think-on-Graph (ICLR 2024), where the model explores the graph and keeps the most promising paths. It is slower and costs more calls, and it pays off for questions whose path you cannot predict.

# An agent that uses a knowledge graph through tools, the "think on graph" pattern:
# at each step it looks at the edges around its current entities and decides which to follow.
KG = {("Shenzhen Parts", "RECALLED", "BX-200"), ("Phone X", "USES", "BX-200"), ("Earbuds Pro", "USES", "BX-200"),
      ("Acme Electronics", "MAKES", "Phone X"), ("Acme Electronics", "MAKES", "Earbuds Pro"),
      ("Acme Electronics", "BUYS_FROM", "Shenzhen Parts"), ("Phone X", "HAS_FEATURE", "camera upgrade"),
      ("Acme Electronics", "LOCATED_IN", "Pune"), ("Rina Shah", "CEO_OF", "Acme Electronics")}

def neighbors(entity):
    """Tool 1: edges touching an entity, as (relation, direction, other)."""
    return sorted([(r, "out", b) for a, r, b in KG if a == entity] + [(r, "in", a) for a, r, b in KG if b == entity])

def plan(question, frontier_edges):
    """Stands in for the model: keep only edges whose relation helps the question.
    A real agent asks the model to choose, with the question and the candidate edges in the prompt."""
    useful = {"RECALLED", "USES", "MAKES"}       # what a model would judge relevant to "who makes ... recall"
    return [e for e in frontier_edges if e[1] in useful]

def explore(question, start, max_calls=6):
    frontier, path, calls, seen = [start], [], 0, {start}
    while frontier and calls < max_calls:
        nxt = []
        for ent in frontier:
            calls += 1
            for rel, d, other in neighbors(ent):
                edge = (ent, rel, other) if d == "out" else (other, rel, ent)
                if edge not in path and plan(question, [edge]):
                    path.append(edge)
                    if other not in seen:
                        seen.add(other); nxt.append(other)
        frontier = nxt
    return path, calls

path, calls = explore("Who makes the products hit by the Shenzhen Parts recall?", "Shenzhen Parts")
for a, r, b in path:
    print(f"  {a} -[{r}]-> {b}")
makers = sorted({a for a, r, b in path if r == "MAKES"})
print(f"answer: {makers} | tool calls {calls} | edges kept {len(path)} of {len(KG)}")
What you should see
  Shenzhen Parts -[RECALLED]-> BX-200
  Earbuds Pro -[USES]-> BX-200
  Phone X -[USES]-> BX-200
  Acme Electronics -[MAKES]-> Earbuds Pro
  Acme Electronics -[MAKES]-> Phone X
answer: ['Acme Electronics'] | tool calls 5 | edges kept 5 of 9

The agent follows only relations that serve the question and ignores the CEO, the location and the camera feature: five of nine edges, in five tool calls, and the path doubles as the explanation of the answer. In production, the planner is the model; bound it with a tool-call budget, a depth limit and a cap on neighbors returned per call (Lesson 5.7 shows why), and log the path with the trace.

Graph memory that knows about time

Lessons 3.9 and 3.10 covered memory types. A graph is a natural form for semantic memory (facts about the user and the world), and time is what makes it correct: people move, preferences change, and old facts are still needed to explain old decisions.

from datetime import date

class TemporalMemory:
    """Agent memory as a temporal graph: every fact has the period it was true in the world
    (valid_from, valid_to) and when the system learned it (recorded). New facts close old ones."""
    def __init__(self): self.facts = []
    def add(self, s, r, o, valid_from, recorded, exclusive=True):
        if exclusive:                                      # e.g. a customer has one current city
            for f in self.facts:
                if f["s"] == s and f["r"] == r and f["valid_to"] is None and f["o"] != o:
                    f["valid_to"] = valid_from
        self.facts.append({"s": s, "r": r, "o": o, "valid_from": valid_from, "valid_to": None, "recorded": recorded})
    def as_of(self, s, r, when):
        return [f["o"] for f in self.facts if f["s"] == s and f["r"] == r and f["valid_from"] <= when
                and (f["valid_to"] is None or when < f["valid_to"])]

m = TemporalMemory()
m.add("Priya", "LIVES_IN", "Pune", date(2024, 1, 1), recorded=date(2024, 2, 3))
m.add("Priya", "PREFERS", "UPI", date(2024, 2, 3), recorded=date(2024, 2, 3))
m.add("Priya", "LIVES_IN", "Bengaluru", date(2026, 6, 1), recorded=date(2026, 7, 15))   # learned late
print("lives in, today:", m.as_of("Priya", "LIVES_IN", date(2026, 11, 3)))
print("lives in, when the March 2026 order shipped:", m.as_of("Priya", "LIVES_IN", date(2026, 3, 10)))
print("history kept:", [(f["o"], str(f["valid_from"]), str(f["valid_to"])) for f in m.facts if f["r"] == "LIVES_IN"])
What you should see
lives in, today: ['Bengaluru']
lives in, when the March 2026 order shipped: ['Pune']
history kept: [('Pune', '2024-01-01', '2026-06-01'), ('Bengaluru', '2026-06-01', 'None')]

The new city closes the old fact instead of overwriting it, so the agent answers "today" and "in March" correctly, and the history explains why a March delivery went to Pune. Note the record date: the move was learned in July, so any decision made in June used Pune in good faith, which matters when you audit an agent's past behavior. Graphiti, used by Zep, implements this bi-temporal model for agent memory at scale.

Choosing the structure

Situation Structure Why
Known steps, known order A workflow graph with few branches Predictable, testable, cheap
Known steps, unknown order or repetition A graph with a model-driven router node and a loop, with a step budget Flexibility where it is needed, fixed shape elsewhere
Open-ended exploration of connected facts An agent with graph tools under a budget The path cannot be predicted
Facts about users that change Temporal graph memory Correct now and auditable later
Several teams' agents cooperating A graph of agents with typed handoffs (Lesson 12.17) Ownership and contracts per edge

Exercises

Predict before you run

explore(question, start, max_calls=6) uses a model to pick which edges to follow. For a question needing a 4-hop path, how many model calls does it need at minimum, and what happens if the budget is 3? (Solution P1.)

Break it on purpose

Give the agent a tool that runs arbitrary Cypher written by the model, with write access. What can go wrong? (Solution B1.)

Debugging exercise

A graph-memory agent says a supplier is "currently" approved, but approval ended last month. Using "Graph memory that knows about time", fix the model of time. (Solution D1.)

Make it your own

Add a paths(a, b, max_depth) tool for the agent, and compare the number of model calls with explore on a two-entity question. (Solution M1.)

Solutions

SolutionP1 · Exploration budgets

At least four, one per hop. With a budget of 3, it stops one hop short and must say the path was not found within its budget.

SolutionB1 · Least privilege for graph tools

The model can write or delete data, or run unbounded queries. Give read-only, parameterized tools (neighbors, paths with depth limits) and validate any generated query.

SolutionD1 · Facts need validity intervals

Store when each fact became true and stopped being true (valid-from and valid-to), and query "as of" a date. Overwriting facts loses history; never-ending facts give stale answers.

SolutionM1 · The right tool reduces calls

A path tool answers "how are A and B connected" in one call instead of step-by-step exploration. Give agents tools that match common question shapes.

Check your understanding

Explain the mechanismHow do agents use knowledge graphs?

Worked answer. Through tools: lookups, neighbors, path finding and safe parameterized queries, letting the agent explore relationships step by step; and as memory, where the agent writes facts with time validity and reads them later. The graph gives agents structured, traceable context; the agent decides which relationships to follow.

A plausible wrong answer. "The agent loads the whole graph into its context." Graphs are too large; tools retrieve what is needed.

Follow-ups. How do you stop an agent from wandering in a large graph?

Debug a failureA graph-exploring agent uses many calls and still misses the answer. What do you change?

Worked answer. Better tools (a path tool instead of one-hop neighbors), better starting points (entity linking from the question), summaries of neighborhoods to choose from, and a call budget with an honest fallback. Read traces to see where choices went wrong.

A plausible wrong answer. "Allow more calls." More wandering, same misses.

Follow-ups. What would you put in the neighbor summaries?

Defend a designGraph memory or vector memory for an agent?

Worked answer. Graph memory when facts are relationships that change over time and must be traced, such as customers, suppliers, approvals and dependencies; vector memory for loose notes and episodes retrieved by similarity. Some systems combine them: entities and relations in a graph, text snippets in a vector store.

A plausible wrong answer. "Vector memory is enough." It cannot answer "as of last month" or follow relationships reliably.

Follow-ups. How would you test temporal correctness?
