Why this came about

Companies ended up with many teams calling many models, each with its own keys, costs and failure modes. AI gateways emerged in 2023 and 2024 to centralize access, cost control, logging and failover, and model routing followed to send each request to the right model.

In plain words first
One front door for every model call

When many teams call many models, an AI gateway sits in between: one place for keys, rate limits, logging, cost tracking, caching, safety filters and failover. Model routing chooses which model serves each request, for example a cheap one for simple requests and a strong one for hard ones, or a backup when the main provider is down.

Why a gateway

Without one, every team holds its own provider keys, picks its own models, and nobody knows what the company spends or sends to whom. An AI gateway (or LLM gateway) is a proxy that every model call goes through. It gives you, in one place:

Capability What it does
One API, many providers Applications call one OpenAI-style endpoint with a model alias; the gateway translates to Bedrock, Azure, Vertex, Anthropic, OpenAI or self-hosted models
Routing and fallbacks Primary and backup deployments, cross-region and cross-provider failover, load balancing, latency- or cost-based routing
Keys and access Provider keys stay in the gateway; teams get their own virtual keys with allowed models
Budgets and limits Spend limits per team, key or user; request and token rate limits
Caching Exact-match and semantic caches
Guardrails Central input and output checks (Lesson 10.1)
Logging and cost attribution Every call, tokens and cost tagged by team, app and user, exported to your observability stack
Policy Approved models only, data-residency rules, PII handling

It is also the cleanest seam for changing models: swap the deployment behind an alias, run evals, and no application code changes.

LLM gateway, MCP gateway, agent gateway: one control plane

The terms overlap, so it helps to separate the traffic each one governs:

Gateway Traffic it governs Typical policies Covered in
LLM gateway (or AI gateway, model gateway) Application or agent → model providers Routing, fallbacks, virtual keys, budgets, token limits, caching, PII redaction, logging This lesson
MCP gateway Agent → tool servers Server allowlists, per-agent tool allowlists, auth to backends, tool-definition pinning, audit Lesson 8.3
Agent gateway Agent → agent (A2A) and front end → agent (AG-UI) Agent registry, identity, task limits, routing between agents Lesson 8.4

In 2026 these are converging into one control plane: Azure API Management, Kong, agentgateway, Bedrock AgentCore Gateway and Google's Agent Gateway each cover more than one kind of traffic, and enterprise platform teams increasingly run a single policy layer for models, tools and agents. The design principle is the same for all three: every call from an agent to anything outside it passes one point where identity, policy, cost and audit are enforced.

Step 1 · A teaching-sized gateway

Fifty lines show what the products do inside:

import time, hashlib, json
from mockllm import start
from openai import OpenAI, APIConnectionError

PROVIDERS = {"primary": OpenAI(base_url="http://127.0.0.1:9/v1", api_key="x", max_retries=0, timeout=2),  # down
             "backup": OpenAI(base_url=start(), api_key="x")}
ROUTES = {"support-model": [("primary", "big-model"), ("backup", "mock-model")]}   # alias -> ordered deployments
PRICE_PER_1K = {"big-model": 0.010, "mock-model": 0.002}                          # USD per 1,000 tokens, illustrative
BUDGET_USD = {"team-support": 5.00, "team-intern": 0.0001}
spent, cache, log = {}, {}, []

def chat(tenant: str, alias: str, messages: list[dict]) -> str:
    if spent.get(tenant, 0) >= BUDGET_USD.get(tenant, 0):
        raise PermissionError(f"{tenant} is over budget")
    key = hashlib.sha256(json.dumps([tenant, alias, messages]).encode()).hexdigest()   # tenant is part of the key
    if key in cache:
        log.append({"tenant": tenant, "alias": alias, "deployment": "cache", "cost": 0.0})
        return cache[key]
    for provider, model in ROUTES[alias]:
        try:
            t0 = time.perf_counter()
            r = PROVIDERS[provider].chat.completions.create(model=model, messages=messages)
            cost = r.usage.total_tokens / 1000 * PRICE_PER_1K[model]
            spent[tenant] = spent.get(tenant, 0) + cost
            log.append({"tenant": tenant, "alias": alias, "deployment": f"{provider}/{model}",
                        "ms": round((time.perf_counter() - t0) * 1000), "cost": round(cost, 6)})
            cache[key] = r.choices[0].message.content
            return cache[key]
        except APIConnectionError:
            log.append({"tenant": tenant, "alias": alias, "deployment": f"{provider}/{model}", "error": "connection"})
    raise RuntimeError("all deployments failed")

msgs = [{"role": "user", "content": "Hello"}]
chat("team-support", "support-model", msgs)
chat("team-support", "support-model", msgs)                 # identical request: served from cache
chat("team-intern", "support-model", msgs)                  # spends its tiny budget
try:
    chat("team-intern", "support-model", [{"role": "user", "content": "Hi again"}])
except PermissionError as e:
    print("blocked:", e)
for row in log:
    print({k: v for k, v in row.items() if k != "ms"})

Notice the waste: every request still tries the dead primary first. Real gateways add a cooldown (circuit breaker): after a few failures, skip that deployment for a while.

Here is that circuit breaker, the standard fix. It has three states: closed (send traffic), open (skip the deployment until a cooldown ends) and half-open (let one trial request through to see whether it has recovered):

class CircuitBreaker:
    """closed: use it.  open: skip it until the cooldown ends.  half-open: allow one trial request."""
    def __init__(self, failures_to_open: int = 2, cooldown_s: float = 30):
        self.failures_to_open, self.cooldown_s = failures_to_open, cooldown_s
        self.failures, self.opened_at = 0, None
    def state(self, now: float) -> str:
        if self.opened_at is None:
            return "closed"
        return "half-open" if now - self.opened_at >= self.cooldown_s else "open"
    def record(self, ok: bool, now: float) -> None:
        if ok:
            self.failures, self.opened_at = 0, None
        else:
            self.failures += 1
            if self.failures >= self.failures_to_open or self.state(now) == "half-open":
                self.opened_at = now

breakers = {"primary": CircuitBreaker(), "backup": CircuitBreaker()}
DEPLOYMENTS = [("primary", "big-model"), ("backup", "mock-model")]

def routed_chat(messages: list[dict], now: float) -> str:
    trail = []
    for provider, model in DEPLOYMENTS:
        state = breakers[provider].state(now)
        if state == "open":
            trail.append(f"{provider}:skipped")
            continue
        try:
            PROVIDERS[provider].chat.completions.create(model=model, messages=messages)
            breakers[provider].record(True, now)
            trail.append(f"{provider}:ok")
            return " -> ".join(trail)
        except APIConnectionError:
            breakers[provider].record(False, now)
            trail.append(f"{provider}:failed({state})")
    return " -> ".join(trail) + " -> all failed"

clock = 0.0                                       # a fake clock keeps the demo deterministic
for step in range(4):
    print(f"t={clock:>4.0f}s ", routed_chat([{"role": "user", "content": "Hi"}], clock))
    clock += 5
clock = 40                                        # past the 30 s cooldown: one trial request goes to primary
print(f"t={clock:>4.0f}s ", routed_chat([{"role": "user", "content": "Hi"}], clock))
print(f"t={clock + 1:>4.0f}s ", routed_chat([{"role": "user", "content": "Hi"}], clock + 1))
What you should see
t=   0s  primary:failed(closed) -> backup:ok
t=   5s  primary:failed(closed) -> backup:ok
t=  10s  primary:skipped -> backup:ok
t=  15s  primary:skipped -> backup:ok
t=  40s  primary:failed(half-open) -> backup:ok
t=  41s  primary:skipped -> backup:ok

After two failures the primary was skipped, so requests stopped paying the timeout. At 40 seconds one trial request found it still down, and the breaker opened again straight away. Production gateways track breakers per deployment and per error type: a 429 (rate limited) deserves a short cooldown and maybe a different region; a 400 (bad request) should not open the breaker at all, because the next deployment will reject it too.

In production
Gateway pitfalls seen in production
  • The gateway becomes the outage: one instance, no health checks, and every agent stops when it does. Run it highly available, with its own SLOslater · 12.7, and keep a documented emergency bypass.
  • Added latency on every call: heavy plugins (PII scanning, logging of full payloads) on the hot path. Measure the gateway's own overhead and move slow work off the request path.
  • Streaming broken by the proxy: buffering turns token streams into one late response. Test streaming through the gateway, not only directly.
  • Fallbacks that change behavior silently: traffic shifts to a different model during an incident and quality drops. Log the model that actually served each call and evaluate every fallback (Lesson 6.2).
  • Budgets that cut off a critical flow: a hard limit hits the support agent at peak. Alert well before the limit and set separate budgets for critical and experimental traffic.

Step 2 · LiteLLM's router, in code

LiteLLM (open source) is the most widely used self-hosted gateway. Its Router gives an application fallbacks, retries, cooldowns and load balancing; its proxy server adds keys, budgets, logging and a UI for a whole company.

from litellm import Router

healthy = start()                                     # a working "provider"
broken = "http://127.0.0.1:9/v1"                      # nothing listens here: a provider outage

router = Router(
    model_list=[
        {"model_name": "support-model",                                   # the name your app calls
         "litellm_params": {"model": "openai/mock-model", "api_base": broken, "api_key": "x"}},
        {"model_name": "support-model-fallback",
         "litellm_params": {"model": "openai/mock-model", "api_base": healthy, "api_key": "x"}},
    ],
    fallbacks=[{"support-model": ["support-model-fallback"]}],            # try this when the primary fails
    num_retries=1, timeout=5,
)
r = router.completion(model="support-model", messages=[{"role": "user", "content": "Hello"}])
print(r.choices[0].message.content)
print("served by fallback:", r._hidden_params.get("api_base") == healthy)
What you should see
I can check order status and cancel orders. Please share your order ID, like A-1002.
served by fallback: True

Several deployments can share one model_name; the router then load-balances across them (routing_strategy options include simple shuffle, least busy, latency-based and cost-based).

The proxy takes the same ideas as configuration:

# config.yaml for the LiteLLM proxy (run: litellm --config config.yaml)
model_list:
  - model_name: support-model
    litellm_params:
      model: bedrock/anthropic.claude-sonnet-model-id     # placeholder: use your Bedrock model or inference profile ID
      aws_region_name: ap-south-1
  - model_name: support-model
    litellm_params:
      model: azure/my-gpt-deployment
      api_base: os.environ/AZURE_API_BASE
      api_key: os.environ/AZURE_API_KEY
router_settings:
  routing_strategy: latency-based-routing
litellm_settings:
  num_retries: 2
  fallbacks: [{"support-model": ["cheap-model"]}]
  cache: true
  cache_params: {type: redis, host: os.environ/REDIS_HOST}
general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY        # admin key; teams get virtual keys
  database_url: os.environ/DATABASE_URL            # Postgres, for keys, budgets and spend logs

Teams then get virtual keys with their own models and budgets (POST /key/generate with models, max_budget and budget_duration), and applications point any OpenAI-compatible SDK at the proxy URL.

Cost attribution is the feature finance asks about first. LiteLLM computes the response cost (response_cost) for every call from its price table (or from prices you set per deployment, as here), and a callback can attribute it to a team from request metadata:

import litellm
from litellm import Router
from litellm.integrations.custom_logger import CustomLogger
from mockllm import start
base = start()
SPEND = {}
class SpendTracker(CustomLogger):
    def log_success_event(self, kwargs, response_obj, start_time, end_time):
        team = (kwargs.get("litellm_params", {}).get("metadata") or {}).get("team", "unknown")
        SPEND[team] = SPEND.get(team, 0) + (kwargs.get("response_cost") or 0)
litellm.callbacks = [SpendTracker()]
router = Router(model_list=[{"model_name": "support-model",
  "litellm_params": {"model": "openai/mock-model", "api_base": base, "api_key": "x",
                      "input_cost_per_token": 3e-6, "output_cost_per_token": 15e-6}}])
for team in ["support", "support", "marketing"]:
    r = router.completion(model="support-model", messages=[{"role":"user","content":"Hello"}], metadata={"team": team})
    print(team, r.usage.total_tokens, r._hidden_params.get("response_cost"))
import time; time.sleep(0.5)
print({k: round(v, 6) for k, v in SPEND.items()})
What you should see
support 70 0.00045000000000000004
support 70 0.00045000000000000004
marketing 70 0.00045000000000000004
{'support': 0.0009, 'marketing': 0.00045}

50 input tokens at $3 per million plus 20 output tokens at $15 per million is $0.00045 per call. Success callbacks run in a background thread, hence the short sleep before reading the totals. The proxy does this attribution for you per virtual key, team and user, and stores it in its database for the spend dashboards.

Step 3 · A gateway as a service: virtual keys, limits and redaction

Applications should not know provider keys exist. Here is a gateway as an HTTP service that any OpenAI SDK can call: it authenticates virtual keys, enforces each team's model allowlist and a tokens-per-minute limit, redacts personal data before the request leaves, and holds the only real provider key:

import re, threading, time
import uvicorn
from fastapi import FastAPI, Header, HTTPException, Request
from openai import OpenAI
import openai
from mockllm import start

UPSTREAM = OpenAI(base_url=start(), api_key="provider-key-held-only-by-the-gateway")
VIRTUAL_KEYS = {"vk-support-7f3a": {"team": "support", "models": {"support-model"}, "tpm": 140},
                "vk-intern-19c2": {"team": "intern", "models": {"cheap-model"}, "tpm": 1000}}
ALIASES = {"support-model": "mock-model", "cheap-model": "mock-model"}
PII = [(re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"), "<EMAIL>"), (re.compile(r"\b[6-9]\d{9}\b"), "<PHONE>")]
usage_window: dict[str, list[tuple[float, int]]] = {}       # key -> [(timestamp, tokens)]
forwarded: list[str] = []

app = FastAPI()

@app.post("/v1/chat/completions")
async def chat(request: Request, authorization: str = Header(default="")):
    key = authorization.removeprefix("Bearer ").strip()
    vk = VIRTUAL_KEYS.get(key)
    if vk is None:
        raise HTTPException(401, "unknown key")
    body = await request.json()
    if body["model"] not in vk["models"]:
        raise HTTPException(403, f"model {body['model']} is not allowed for team {vk['team']}")
    now = time.time()
    recent = [(t, n) for t, n in usage_window.get(key, []) if now - t < 60]
    if sum(n for _, n in recent) >= vk["tpm"]:
        raise HTTPException(429, "tokens-per-minute limit reached", headers={"Retry-After": "60"})
    for m in body["messages"]:                                      # input guardrail: redact before it leaves
        for pattern, label in PII:
            m["content"] = pattern.sub(label, m["content"])
    forwarded.append(body["messages"][-1]["content"])
    r = UPSTREAM.chat.completions.create(model=ALIASES[body["model"]], messages=body["messages"])
    usage_window[key] = recent + [(now, r.usage.total_tokens)]
    return r.model_dump()

threading.Thread(target=uvicorn.run, args=(app,), kwargs={"port": 8791, "log_level": "warning"}, daemon=True).start()
time.sleep(1.5)

def ask(key, model, text):
    client = OpenAI(base_url="http://127.0.0.1:8791/v1", api_key=key, max_retries=0)
    try:
        r = client.chat.completions.create(model=model, messages=[{"role": "user", "content": text}])
        return f"ok ({r.usage.total_tokens} tokens)"
    except openai.APIStatusError as e:
        return f"{e.status_code}: {e.response.json()['detail']}"

print(ask("vk-support-7f3a", "support-model", "Where is A-1001? I'm ravi@gmail.com, 9876543210"))
print(ask("vk-intern-19c2", "support-model", "Hello"))
print(ask("vk-stolen-0000", "support-model", "Hello"))
print(ask("vk-support-7f3a", "support-model", "Where is A-1002?"))
print(ask("vk-support-7f3a", "support-model", "And A-1003?"))
print("provider saw:", forwarded[0])
What you should see
ok (70 tokens)
403: model support-model is not allowed for team intern
401: unknown key
ok (70 tokens)
429: tokens-per-minute limit reached
provider saw: Where is A-1001? I'm <EMAIL>, <PHONE>

Every rule a platform team cares about lives in one place: the intern key cannot reach the expensive model, a made-up key gets nothing, the support team hit its token limit on the third call and got a standard 429 with Retry-After (which the OpenAI SDK's retry logic understands), and the provider never saw the customer's email or phone number. Limits on tokens, not just requests, matter for LLM traffic, because one request can cost a thousand times more than another. Production gateways keep these counters in Redis so every gateway replica sees the same totals.

Watch out
Pin and verify your gateway

The gateway holds every provider credential, so it is the most valuable target in the stack. LiteLLM itself was hit by a supply-chain attack in March 2026 (Lesson 10.3). Pin exact versions with hashes, build images from a reviewed lockfile, keep provider keys in a secrets manager, and restrict the gateway's network egress to the providers it needs.

Step 4 · Semantic caching, measured honestly

An exact-match cache only helps when users send identical requests. A semantic cache reuses an answer when a new question means the same thing, judged by embedding similarity. It can cut cost sharply on FAQ-style traffic, and it can also serve confidently wrong answers:

from sklearn.feature_extraction.text import TfidfVectorizer

CORPUS = ["How do I reset my password?", "Forgot my password, what now?", "How do I reset my UPI PIN?",
          "Where is my order?", "How long do refunds take?", "When will I get my money back?"]
vec = TfidfVectorizer(analyzer="char_wb", ngram_range=(3, 5)).fit(CORPUS)   # a weak stand-in for an embedding model

class SemanticCache:
    """Reuse an answer when a new question means the same thing. Scoped per tenant; strict threshold."""
    def __init__(self, threshold: float):
        self.threshold, self.entries = threshold, {}          # tenant -> list of (vector, question, answer)
    def get(self, tenant: str, question: str):
        q = vec.transform([question]).toarray()[0]
        best = max(self.entries.get(tenant, []), key=lambda e: float(q @ e[0]), default=None)
        if best is not None and float(q @ best[0]) >= self.threshold:
            return best[2], best[1], round(float(q @ best[0]), 2)
        return None
    def put(self, tenant: str, question: str, answer: str):
        self.entries.setdefault(tenant, []).append((vec.transform([question]).toarray()[0], question, answer))

for threshold in (0.35, 0.60):
    sem = SemanticCache(threshold)
    sem.put("shopkart", "How do I reset my password?", "Use 'Forgot password' on the login page.")
    print(f"threshold {threshold}")
    for q in ["Forgot my password, what now?", "How do I reset my UPI PIN?"]:
        hit = sem.get("shopkart", q)
        print(f"  {q!r:35} ->", f"HIT (matched {hit[1]!r}, score {hit[2]})" if hit else "miss")
    print("  other tenant ->", sem.get("other-co", "How do I reset my password?"))
What you should see
threshold 0.35
  'Forgot my password, what now?'     -> miss
  'How do I reset my UPI PIN?'        -> HIT (matched 'How do I reset my password?', score 0.45)
  other tenant -> None
threshold 0.6
  'Forgot my password, what now?'     -> miss
  'How do I reset my UPI PIN?'        -> miss
  other tenant -> None

At the looser threshold, the cache answered a UPI PIN question with password instructions, and it never matched the real paraphrase. A good embedding model ranks paraphrases much higher than this lexical stand-in, but near-misses like "reset password" and "reset UPI PIN" stay close for every model. So: evaluate a semantic cache on labeled pairs (same meaning and different meaning) like any classifier; scope entries by tenant and, for personal answers, by user; expire entries when content changes; and keep it off for anything permission-dependent or time-sensitive.

In production
Semantic caching: where it helps, where it hurts

It helps on high-volume FAQ-style traffic with stable answers (store hours, return windows), and it hurts anywhere the answer depends on who is asking or when: order status, balances, eligibility. Scope cache entries by tenant and, for personal answers, by user; set short lifetimes for anything that changes; invalidate when the source document changes; and measure the false-hit rate on labeled question pairs before turning it on.

Industry practice
Gateways are platform infrastructure

Platform teams that run agents for many product teams usually make the gateway mandatory: no direct provider keys in applications. It turns cost attribution, model allowlists, residency and incident response (one switch to reroute away from a failing provider) into properties of the platform instead of per-team discipline. The trade-off is a new critical dependency, so run it highly available, with its own SLOs, and keep a documented emergency bypass.

From the field
Uber's GenAI Gateway: one door for every team

Uber's machine-learning platform team built a GenAI Gateway (2024) as the single entry point for all large language model use at Uber, across external vendors and Uber-hosted open models. It mirrors the OpenAI API, so teams use standard clients and frameworks such as LangChain and LlamaIndex unchanged. Requests pass through a PII redactor that replaces sensitive values with placeholders before they reach third-party vendors and restores them in the response; every call is authenticated, metered and logged for cost attribution, security audits and quality evaluation, and each use case is reviewed by the security team before it gets access. At the time of the write-up it served close to 30 customer teams and about 16 million queries a month. Source: Uber Engineering.

Predict before you run

A gateway routes simple questions to a small model and hard ones to a large model. What is the main risk, and how do you measure it? (Solution P1.)

Break it on purpose

Configure fallbacks to a different provider without evaluating that provider. An outage happens. What do users see? (Solution B1.)

Debugging exercise

Costs are rising but no team admits to increased usage. How does a gateway answer the question? (Solution D1.)

Make it your own

Write a gateway policy for ShopKart: routing rules, fallbacks, budgets per team, rate limits and logging. (Solution M1.)

Solutions

SolutionP1 · Routing errors

Misrouted hard questions get worse answers. Measure quality by route on the eval set, and monitor escalations from the small model.

SolutionB1 · Untested fallbacks

Different behavior: formats, tool use and quality change silently. Evaluate every fallback model and log which model served each call.

SolutionD1 · Attribution

Per-team keys or virtual keys with usage logging, budgets and dashboards. The gateway is where attribution happens.

SolutionM1 · A gateway policy

Default model per use case, a cheaper model for classification, fallback provider on 5xx and timeouts only, monthly budgets per team with alerts, rate limits per key, and request logs with redaction.

Check your understanding

Explain the mechanismWhat does an AI gateway do?

Worked answer. It sits between applications and model providers: one API, authentication and per-team keys, routing and fallbacks, rate limits and budgets, caching, guardrails, logging and cost attribution. Examples include LiteLLM, cloud API gateways with AI policies and commercial gateways.

A plausible wrong answer. "It is just a proxy." Its policies are the point.

Follow-ups. Where should guardrails run: gateway or application?

Debug a failureAfter introducing a gateway, streaming stopped working. What do you check?

Worked answer. Whether the gateway buffers responses, supports server-sent events for that provider, and passes stream options through. Test streaming through the gateway path.

A plausible wrong answer. "Streaming is not compatible with gateways." Most support it when configured.

Follow-ups. How would you test it in CI?

Defend a designBuild or buy an AI gateway?

Worked answer. Buy or adopt open source for the common features; build only the policies unique to you. A gateway is infrastructure many teams depend on, so reliability and maintenance matter more than features.

A plausible wrong answer. "Build, it is just a proxy." Then you maintain provider adapters forever.

Follow-ups. What would you require from a gateway vendor?
