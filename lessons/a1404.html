In plain words first
The idea in one line

A single chain-of-thought trajectory has no room to backtrack. ToT (Yao et al., 2023) turns reasoning into a tree with self-evaluation on each node. LATS (Zhou et al., 2024) unifies ToT with ReAct and Reflexion under Monte Carlo Tree Search. Game of 24 goes from 4% (CoT) to 74% (ToT); LATS hits 92.7% pass@1 on HumanEval.

The problem

In plain words first

A model reasoning step by step commits to its first idea; if that idea is wrong, everything after it is wrong too. Tree of Thoughts (ToT) turns reasoning into a search: at each step propose several next steps, score each one, keep the most promising, and back up from dead ends. LATS does the same with Monte Carlo tree search, the method behind game-playing programs, and lets real tool results and written reflections guide it. Everything depends on the scoring step, the value function: if it cannot tell a promising partial answer from a hopeless one, the search is no better than guessing. This lesson builds both searches on the Game of 24 (combine four numbers with + − × ÷ to make 24), then measures how good two value functions really are, including a real model's.

Chain-of-thought is a linear walk. If the first step is wrong, every subsequent step works on a bad premise. On Game of 24 (use four digits with + − × ÷ to make 24), GPT-4 CoT hits 4% accuracy. The model picks the wrong subexpression early and cannot recover.

What reasoning needs is the ability to propose multiple candidates, evaluate them, pick the promising ones, and backtrack when dead ends appear. That is search. Tree of Thoughts and LATS are the two canonical formulations.

Idea 1 · Tree of Thoughts (Yao et al., NeurIPS 2023)

Each node is a coherent intermediate step ("a thought"). Each node can expand to K child thoughts. The LLM self-evaluates each node with a scoring prompt. Search explores the tree — BFS, DFS, or beam.

                     (root: "find 24 from 4 6 4 1")
                    /               |            \
           ("6 - 4 = 2")    ("4 + 1 = 5")    ("4 * 6 = 24")  <- Score: HIGH
              /   \              |                  |
          ...    ...          ...                finish

Self-evaluation is the load-bearing piece. The paper shows three variants: sure / likely / impossible classification, 1..10 numeric score, and vote among candidates. All three beat CoT substantially on Game of 24 (4% -> 74% with GPT-4).

Idea 2 · LATS (Zhou et al., ICML 2024)

LATS unifies ToT, ReAct, and Reflexion under MCTS. The LLM plays three roles:

  • Policy: propose candidate next actions (ReAct-style).
  • Value function: score a partial trajectory (ToT-style self-eval).
  • Self-reflector: on failure, write a natural-language reflection (Reflexion-style) and use it to reseed future rollouts.

Environment feedback (observations) mixes into the value function so the search is informed by real tool results, not just model opinions. Results at paper time: HumanEval pass@1 92.7% with GPT-4 (SOTA), WebShop average 75.9 with GPT-3.5 (approaching gradient-based fine-tuning).

Idea 3 · MCTS, minimally

Four phases per iteration:

  1. Select — walk from root to a leaf using UCT (upper confidence bound for trees).
  2. Expand — generate K children via the policy.
  3. Simulate — rollout from a child using the policy, score the leaf with the value function (or environment reward).
  4. Backpropagate — update visit counts and value estimates up the path.

UCT formula: Q(s, a) + c * sqrt(ln N(s) / N(s, a)). First term is exploitation; second is exploration. Tune c per task.

Idea 4 · The cost reality

Search explodes tokens. ToT on Game of 24 generated about 5.5k tokens per puzzle and cost US$0.74 with GPT-4, more than 100 chain-of-thought samples together (US$0.47), so roughly a hundred times one chain. LATS is similar. This is not free; reserve search for:

  • Tasks where a single trajectory is demonstrably insufficient (Game of 24, complex code).
  • Tasks where wall-clock is less important than correctness.
  • Tasks with a cheap, reliable value function (unit tests for code, explicit target for math).

If your task has a single right answer and a noisy evaluator, search often makes things worse — it finds a "good-scoring" wrong answer.

Idea 5 · 2026 positioning

Most production agents do not run LATS. They run ReAct with tool-grounded verification (CRITIC, Lesson 14.5). Search shows up in specialized niches:

  • Coding agents that run tests as the value function (HumanEval-style).
  • Deep-research agents that explore multiple query paths.
  • Planning-heavy workflows inside LangGraph subgraphs.

AlphaEvolve (Lesson 14.11) is the 2025 extreme: evolutionary search over code, machine-checkable fitness, frontier gains (48 multiplications for 4×4 complex-valued matrices, the first improvement on Strassen's 1969 method in 56 years).

The same idea as a formula

Beam search with a value function. From the states Sd​ kept at depth d, expand every next step and keep the b best by the value function V:

Sd+1​=topb​{s′:s′∈children(s), s∈Sd​}  ranked by V(s′).

UCT for MCTS. At node s, pick the child a maximising

Q(s,a)+cN(s,a)lnN(s)​​,
the average reward so far plus a bonus for rarely tried children; c trades exploring against exploiting.

How good is a value function? Its AUC is the probability that a randomly chosen good state scores higher than a randomly chosen bad one (ties count half):

AUC=P(V(s+)>V(s−)).
1.0 is a perfect ranking; 0.5 is a coin flip; below 0.5 is worse than random.

Worked example
Is a random beam enough for 4 6 4 1?
  • After one step there are 19 distinct states, and 3 of them can still reach 24.
  • A random value function keeps 8 of the 19; the chance that none of the 3 good states is among them is (816​)/(819​)=12870/75582≈0.17.
  • So random keeping finds a good state 83% of the time, and keeps 8⋅3/19≈1.3 good states on average.
  • A value function earns its cost only if it beats this. The lesson's heuristic keeps the state "24 and 4 and 1" first because it contains 24, yet no way remains to use the 4 and the 1 and still end at 24.
Check your mental model
  • ✗ "Search always beats one chain of thought."
    ✓ Only when the value function ranks states better than chance; otherwise it is expensive guessing.
  • ✗ "A state that already shows the target is nearly done."
    ✓ In the Game of 24 every number must be used; "24 with 4 and 1 left over" is a dead end.
  • ✗ "The model can judge its own partial work."
    ✓ Small models in particular judge poorly; measure the judge against ground truth before trusting it.
  • ✗ "MCTS returns the answer."
    ✓ It returns the best leaf it found; check that the leaf is a complete, valid solution.

# The value function is the load-bearing piece. For the lesson's puzzle, every state after one step is
# labelled by exact search (can 24 still be reached using all the numbers?), then scored by the
# lesson's heuristic and by a real model used the way ToT uses it ("sure / likely / impossible").
import itertools, os, time, torch
from fractions import Fraction as Fr
os.environ.setdefault("HF_HUB_OFFLINE", "1")            # the model is already in the local cache
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
from main import NUMBERS, TARGET, Node, value as lesson_value

def steps(state):
    """All (description, next state) pairs: any two numbers, any order, + - * /. Exact fractions."""
    out = []
    for i, j in itertools.permutations(range(len(state)), 2):
        a, b = state[i], state[j]; rest = [state[k] for k in range(len(state)) if k not in (i, j)]
        for op, v in (("+", a + b), ("-", a - b), ("*", a * b), ("/", a / b if b else None)):
            if v is not None and not (op in "+*" and i > j):           # skip mirror duplicates
                out.append((f"{a}{op}{b}={v}", tuple(sorted(rest + [v], reverse=True))))
    return out
def solutions(state, trace=()):
    if len(state) == 1:
        return [trace] if state[0] == TARGET else []
    return [s for d, nxt in steps(state) for s in solutions(nxt, trace + (d,))]
def reachable(state):
    return bool(solutions(state))

start = tuple(sorted(map(Fr, NUMBERS), reverse=True))
sols = solutions(start)
print(f"numbers {NUMBERS}: {len(sols)} exact solutions using every number once, e.g.")
for s in sorted(set(sols))[:3]:
    print("   " + ", ".join(s))
first = {}
for desc, nxt in steps(start):
    first.setdefault(nxt, desc)
states = list(first)
truth = {s: reachable(s) for s in states}
print(f"\n{len(states)} distinct states after one step; {sum(truth.values())} can still reach 24")

M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
VALUE = ("Evaluate if the given numbers can reach 24 using each number exactly once with + - * / "
         "(sure/likely/impossible).\n10 14: 10 + 14 = 24. sure\n11 12: 11 + 12 = 23, 12 - 11 = 1, 11 * 12 = 132. impossible\n"
         "4 4 10: 10 - 4 = 6, 6 * 4 = 24. sure\n1 3 3: 1 * 3 * 3 = 9, (1 + 3) * 3 = 12. impossible\n"
         "5 7 8: 5 + 7 + 8 = 20, (8 - 5) * 7 = 21. likely\n{nums}:")
WORDS = [tok.encode(" " + w)[0] for w in ("sure", "likely", "impossible")]
def llm_value(state):
    """ToT's value prompt, read from one forward pass: P(sure) + 0.5 P(likely), renormalised over the three words."""
    nums = " ".join(str(x) if x.denominator == 1 else f"{x.numerator}/{x.denominator}" for x in state)
    ids = tok(VALUE.format(nums=nums), return_tensors="pt")["input_ids"]
    with torch.no_grad():
        logits = llm(ids).logits[0, -1]
    p = torch.softmax(logits[WORDS], 0).tolist()
    return p[0] + 0.5 * p[1]
started = time.perf_counter()
heur = {s: lesson_value(Node(state=tuple(float(x) for x in s), trace=[])) for s in states}
model = {s: llm_value(s) for s in states}
secs = time.perf_counter() - started
def auc(score):
    pos = [score[s] for s in states if truth[s]]; neg = [score[s] for s in states if not truth[s]]
    return sum((p > n) + 0.5 * (p == n) for p in pos for n in neg) / (len(pos) * len(neg))
def kept(score, k=8):
    top = sorted(states, key=lambda s: -score[s])[:k]
    return sum(truth[s] for s in top)
print(f"\n{'value function':<30}{'AUC':>6}{'solvable in its top 8':>24}")
print(f"{'lesson heuristic (near 24)':<30}{auc(heur):>6.2f}{kept(heur):>24}")
print(f"{'Qwen 0.5B, ToT value prompt':<30}{auc(model):>6.2f}{kept(model):>24}")
print(f"{'random':<30}{0.5:>6.2f}{8 * sum(truth.values()) / len(states):>24.1f}  (expected)")
print(f"\nmodel calls {len(states)}, {secs / len(states):.2f} s each")
print("lesson heuristic's top 3:", [(first[s], round(heur[s], 3), truth[s]) for s in sorted(states, key=lambda s: -heur[s])[:3]])

Part 1 of 4 · Node, evaluate, expand, value, NUMBERS, TARGET, OPS

"""Toy Tree-of-Thoughts BFS and LATS MCTS on a stylized arithmetic search.

Task: given integers [4, 6, 4, 1], find an expression using +, -, *, / that
evaluates to 24. This mirrors the Game of 24 benchmark from Yao et al.

ToT is a BFS with a prompted value function. LATS is MCTS over the same
search space with UCT selection.

Stdlib only; no LLM. Value function is symbolic (distance from 24).
"""

from __future__ import annotations

import itertools
import math
import random
from dataclasses import dataclass, field


NUMBERS = [4, 6, 4, 1]
TARGET = 24
OPS = ["+", "-", "*", "/"]


@dataclass
class Node:
    state: tuple[float, ...]
    trace: list[str]
    visits: int = 0
    value_sum: float = 0.0
    children: list["Node"] = field(default_factory=list)

    @property
    def q(self) -> float:
        return self.value_sum / self.visits if self.visits else 0.0


def evaluate(a: float, op: str, b: float) -> float | None:
    if op == "+":
        return a + b
    if op == "-":
        return a - b
    if op == "*":
        return a * b
    if op == "/":
        return a / b if b != 0 else None
    return None


def expand(node: Node) -> list[Node]:
    children: list[Node] = []
    state = node.state
    if len(state) < 2:
        return children
    for i, j in itertools.combinations(range(len(state)), 2):
        for op in OPS:
            a, b = state[i], state[j]
            v = evaluate(a, op, b)
            if v is None:
                continue
            remaining = [s for k, s in enumerate(state) if k not in (i, j)]
            new_state = tuple(sorted(remaining + [v], reverse=True))
            step = f"{a}{op}{b}={v}"
            children.append(Node(state=new_state, trace=node.trace + [step]))
    return children


def value(node: Node) -> float:
    if len(node.state) == 1:
        result = node.state[0]
        return 1.0 if abs(result - TARGET) < 1e-6 else -abs(result - TARGET) / 100.0
    best_distance = min(abs(v - TARGET) for v in node.state)
    return -best_distance / 100.0

Part 2 of 4 · tot_bfs, uct, select, simulate, backprop, mcts, _all_leaves

def tot_bfs(root: Node, max_expansions_per_level: int = 8,
            max_depth: int = 3) -> tuple[Node | None, int]:
    frontier = [root]
    expansions = 0
    for _ in range(max_depth):
        scored: list[tuple[float, Node]] = []
        for node in frontier:
            for child in expand(node):
                expansions += 1
                scored.append((value(child), child))
                if value(child) > 0.99:
                    return child, expansions
        scored.sort(key=lambda p: p[0], reverse=True)
        frontier = [n for _, n in scored[:max_expansions_per_level]]
    best = max(frontier, key=value) if frontier else None
    return best, expansions


def uct(parent: Node, child: Node, c: float = 1.4) -> float:
    if child.visits == 0:
        return float("inf")
    return child.q + c * math.sqrt(math.log(parent.visits) / child.visits)


def select(node: Node) -> Node:
    while node.children:
        node = max(node.children, key=lambda ch: uct(node, ch))
    return node


def simulate(node: Node, depth: int, rng: random.Random) -> float:
    current = node
    for _ in range(depth):
        options = expand(current)
        if not options:
            break
        current = rng.choice(options)
    return value(current)


def backprop(path: list[Node], reward: float) -> None:
    for n in path:
        n.visits += 1
        n.value_sum += reward


def mcts(root: Node, iterations: int, rng: random.Random) -> tuple[Node, int]:
    expansions = 0
    for _ in range(iterations):
        path = [root]
        cur = root
        while cur.children:
            cur = max(cur.children, key=lambda ch: uct(cur, ch))
            path.append(cur)
        if cur.visits > 0 and len(cur.state) > 1:
            cur.children = expand(cur)
            expansions += len(cur.children)
            if cur.children:
                cur = cur.children[0]
                path.append(cur)
        reward = simulate(cur, depth=max(0, 3 - len(cur.trace)), rng=rng)
        backprop(path, reward)
    best_leaf = max(_all_leaves(root), key=value, default=root)
    return best_leaf, expansions


def _all_leaves(node: Node) -> list[Node]:
    if not node.children:
        return [node]
    out: list[Node] = []
    for ch in node.children:
        out.extend(_all_leaves(ch))
    return out

Use it: the same idea with real libraries

LangGraph ships ToT-style exploration as subgraph patterns; LangGraph's LATS tutorial is the reference implementation, and LlamaIndex has a LATS agent package (llama-index-agent-lats). For most 2026 production agents this pattern lives behind an if task_complexity > threshold: use_search() gate — see the evaluator-optimizer pattern in Lesson 05.

Break it on purpose

A team ships LATS for a coding agent and uses the model's own 1-to-10 score of each partial program as the value, because running tests is slow. The scores look sensible in demos. What does the search optimise, and what should the value be? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Search lives where checking is cheap. Coding agents generate several candidate patches and keep the ones that pass tests; AlphaEvolve and its open counterparts (OpenEvolve, ShinkaEvolve) search over programs with an automatic score.
  • Reasoning models moved much of the search inside the model. OpenAI's o-series, Claude's extended thinking, Gemini thinking models and DeepSeek-R1 explore and backtrack in their own reasoning tokens, so explicit ToT over a frontier model is rarer than in 2023.
  • Best-of-n with a verifier (sample several answers, keep the one a checker or reward model prefers) is the common production form of "search", in LangGraph map-reduce graphs and evaluation pipelines alike.
  • On your laptop: value calls are single forward passes, so a 0.5B model scores about three states per second on a CPU and far faster on the RTX 4060; the limit is the judge's quality, as this lab shows, not speed.

Sources: Tree of Thoughts (arXiv:2305.10601), LATS (arXiv:2310.04406), LangGraph LATS tutorial, AlphaEvolve (Google DeepMind), OpenEvolve, DeepSeek-R1 (arXiv:2501.12948).

Recap
What to keep from this lesson
  • ToT and LATS turn reasoning into search over partial solutions.
  • The value function decides everything; measure it (AUC) against ground truth.
  • A value no better than chance makes search cost more for nothing.
  • Prefer values from real checks: tests, exact rules, tool results.
  • Confirm the returned leaf is a complete, valid answer.

Given a task shape (single-answer / multi-answer / open-ended), a token budget, and an available evaluator (scalar test / heuristic / self-eval), produce a search strategy recommendation with concrete parameters.

Produce:

1. Decision. One of: linear ReAct, beam ToT (with beam width k), BFS ToT (with max depth), DFS ToT with pruning, MCTS LATS (with iterations and UCT c), evolutionary search (only if evaluator is programmatic and checkable).
2. Parameters. For every strategy, concrete numeric defaults: beam width, depth cap, branching factor K, rollouts per level, UCT c (default 1.4), timeout.
3. Value function. Specify exactly what scores a node. Options: unit-test pass rate, numeric distance to target, prompted LLM score with format (sure/likely/impossible or 1..10 or vote), or environment reward.
4. Token budget estimate. Worst-case tokens = branching_factor ^ depth * avg_prompt_tokens. Show the number. If it exceeds the user's budget, recommend a cheaper strategy.
5. Failure modes. For each chosen strategy, list the top-two failure modes and their mitigations (e.g. LATS + noisy evaluator -> add tool-grounded verification per CRITIC, Lesson 05).

Hard rejects:

- Recommending search when the evaluator is unreliable (self-eval only, no ground truth). Fall back to ReAct + CRITIC.
- Setting branching factor K higher than 5 without a compelling reason. K=3-5 is the paper default; K=10 explodes cost.
- Applying LATS to chat-style tasks. Search does not help conversational Q&A with no programmatic target.
- Evolutionary search without a machine-checkable fitness. AlphaEvolve is only interesting when fitness is programmatic (run tests, measure speed, verify theorem).

Refusal rules:

- If token budget < 5x single-trajectory cost, refuse search and recommend ReAct + Reflexion (Lesson 03).
- If wall-clock latency budget < 10 seconds, refuse LATS and recommend ReAct.
- If the task is pure information retrieval, refuse search and recommend ReWOO (Lesson 02).

Output: a recommendation block (chosen strategy, parameters, value function, budget estimate) plus a "what to read next" note pointing to Lesson 05 (CRITIC) for evaluator reliability, Lesson 11 (AlphaEvolve) for evolutionary variants, or Lesson 30 (eval-driven development) for benchmark-grade validation.

Exercises

  1. Run the toy LATS with UCT c=0.1 vs c=2.0. What changes in the trace?

Solutions

SolutionP1 · Neither does

Neither. The lesson's heuristic has an AUC of 0.41 and keeps 1 good state in its top 8; the model has an AUC of 0.21 and keeps none; random keeping would hold 1.3 on average. The heuristic is misled by states that contain 24 but cannot use the remaining numbers; the 0.5B model cannot do the arithmetic its value prompt asks about.

SolutionB1 · Search that optimises the judge

It optimises the model's opinion, not correctness. MCTS is good at finding whatever the value function rewards, so it will find partial programs that look finished and well commented, and that the model scores 9 out of 10, whether or not they work. The more search budget, the more reliably it finds such "good-scoring wrong answers", as the toy's 6 × 4 = 24 shows on a small scale.

Use a value grounded in execution: the fraction of unit tests passed, compile and type-check results, or a test run on the partial program where possible. LATS's own HumanEval result used test feedback as part of its value. If tests are slow, run a fast subset during search and the full suite only on the final candidates.
