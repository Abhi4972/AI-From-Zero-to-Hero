About the model on this page
Two kinds of stand-in on this page

The unit tests use ScriptedChatModel, a fake model defined below that replays replies you write. The scoring example uses the lab rig (Lesson 6.1) as the "model under test". Neither is a language model; the point of this lesson is testing everything around the model.

from langchain.agents import create_agent
from langchain.tools import tool
from langchain_core.messages import AIMessage

ORDERS = {"A-1001": "shipped", "A-1002": "processing"}
calls_made = []

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    calls_made.append(order_id)
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"
Why this came about

Testing code that calls a model is slow, costly and non-deterministic, and debugging an agent without seeing its steps is guesswork. Fake models for tests, callbacks and LangSmith tracing (2023) were developed to make LLM applications testable and observable.

The problem: tests that call a model are slow, costly and flaky

A test that calls a real model costs money, takes seconds, and can fail because the model worded something differently. But most agent bugs are not about wording: a tool is not registered, a result is not matched to its call, a middleware is in the wrong order, an approval is never resumed. Those bugs can be tested with a fake model that returns replies you script, so the test checks your code and nothing else. Quality, whether the real model chooses well, is a separate question for evals.

LangChain ships fake chat models. The obvious one fails with an agent:

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel

script = [AIMessage("", tool_calls=[{"name": "get_order_status", "args": {"order_id": "A-1001"}, "id": "call_1"}]),
          AIMessage("A-1001 has shipped.")]
agent = create_agent(GenericFakeChatModel(messages=iter(script)), tools=[get_order_status])
try:
    agent.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})
except NotImplementedError:
    print("NotImplementedError, raised by GenericFakeChatModel.bind_tools")
What you should see
NotImplementedError, raised by GenericFakeChatModel.bind_tools

create_agent binds the tools to the model before its first call, and GenericFakeChatModel does not implement bind_tools.

In plain words first
A stand-in actor for rehearsals

Tests that call a real model are slow, cost money and change their answers from run to run. So tests replace the model with a scripted stand-in that returns exactly the replies you wrote, the way a director rehearses with a stand-in actor. Then the test checks what your code did with those replies: which tools ran, with what arguments, in what order. Callbacks and tracing are the recording side: a callback is a function LangChain calls at each event (model start, tool end), and a trace in LangSmith is the full recording of a run.

Idea 1 · A scripted model that accepts tools

A test should not depend on what a real model happens to say today. A scripted model is a stand-in that replays a list of replies you wrote in advance, including the tool calls. This small class adds one method to LangChain's fake chat model so that create_agent accepts it. The agent built on it behaves the same way on every run:

class ScriptedChatModel(GenericFakeChatModel):
    """Replays a fixed list of AIMessages, and accepts tools so create_agent can use it."""
    def bind_tools(self, tools, **kwargs):
        return self                                       # the script already says which tools are called

def scripted(*replies):
    return ScriptedChatModel(messages=iter(list(replies)))

agent = create_agent(scripted(*script), tools=[get_order_status])
state = agent.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})
print([f"{m.type}: {m.content or m.tool_calls[0]['name']}" for m in state["messages"]])
print("tool called with:", calls_made)
What you should see
['human: Where is A-1001?', 'ai: get_order_status', 'tool: A-1001 is shipped', 'ai: A-1001 has shipped.']
tool called with: ['A-1001']

The fake returned the scripted tool call, the real tools node ran your real tool, and the fake returned the scripted answer. Everything except the model's choices was real, which is exactly what a unit test should exercise.

Idea 2 · Tests that check behavior, not wording

With the model scripted, a test can assert what the agent did: which tool it called, with which arguments, what the tool returned and what reached the user. These are ordinary pytest functions. Note what they do not check: the exact wording of a real model's reply, which changes from run to run.

def test_looks_up_the_order_it_was_asked_about():
    calls_made.clear()
    agent = create_agent(scripted(*script), tools=[get_order_status])
    state = agent.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})
    assert calls_made == ["A-1001"]
    tool_msg = next(m for m in state["messages"] if m.type == "tool")
    assert tool_msg.content == "A-1001 is shipped"
    assert state["messages"][-1].content == "A-1001 has shipped."

def test_unknown_order_reaches_the_model_as_a_result():
    agent = create_agent(scripted(
        AIMessage("", tool_calls=[{"name": "get_order_status", "args": {"order_id": "A-9999"}, "id": "c"}]),
        AIMessage("I couldn't find that order.")), tools=[get_order_status])
    state = agent.invoke({"messages": [{"role": "user", "content": "Where is A-9999?"}]})
    assert "not found" in next(m for m in state["messages"] if m.type == "tool").content

for test in [test_looks_up_the_order_it_was_asked_about, test_unknown_order_reaches_the_model_as_a_result]:
    test()
    print("passed:", test.__name__)
What you should see
passed: test_looks_up_the_order_it_was_asked_about
passed: test_unknown_order_reaches_the_model_as_a_result

The assertions check what matters: which tool ran with which arguments, what result went back, and what the run ended with. Run them with pytest like any other tests; they take milliseconds, so they can run on every commit. Good candidates: every tool's error path, approval and resume (Lesson 6.6), limits, and anything your middleware changes.

Idea 3 · Callbacks: record what a run did

A callback handler receives events from every component in a run: model start and end, tool start and end, chain steps, errors. Pass it in config, and it sees the whole run:

from langchain_core.callbacks import BaseCallbackHandler

class RunRecorder(BaseCallbackHandler):
    """Records what a run did: model calls, tools, and timing, for logs or a cost table."""
    def __init__(self):
        self.events = []
    def on_chat_model_start(self, serialized, messages, **kw):
        self.events.append(("model", f"{len(messages[0])} messages in"))
    def on_tool_start(self, serialized, input_str, **kw):
        self.events.append(("tool", f"{serialized['name']} {input_str}"))
    def on_tool_end(self, output, **kw):
        self.events.append(("tool result", str(getattr(output, "content", output))))

rec = RunRecorder()
agent = create_agent(scripted(*script), tools=[get_order_status])
agent.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]}, {"callbacks": [rec]})
for kind, detail in rec.events:
    print(f"{kind:12} | {detail}")
What you should see
model        | 1 messages in
tool         | get_order_status {'order_id': 'A-1001'}
tool result  | A-1001 is shipped
model        | 3 messages in

on_llm_end (not shown) receives the model's result with its usage, which is how a handler builds a cost table per run (Lesson 3.6). Tracing tools such as LangSmith and Langfuse are, underneath, callback handlers that send these events to a server. For streaming UIs, astream_events yields the same events as an async stream (Lesson 6.15).

Idea 4 · Tracing with LangSmith

LangSmith is LangChain's hosted (or self-hosted) platform for traces, datasets, evaluations and prompt versions. Tracing needs no code changes, only environment variables:

export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=...            # from your LangSmith settings
export LANGSMITH_PROJECT=shopkart-support

Every chain, agent and graph run is then sent as a trace: a tree of runs, one per model call, tool call and step, with inputs, outputs, tokens, latency and errors. Your own functions join the tree with @traceable:

from langsmith import traceable

@traceable(run_type="retriever", name="search_help_center")
def search(query: str) -> list[str]:
    ...

(This workspace has no LangSmith key, so these were not run here.) What to read in a trace, in order: the final messages the model received (was the right context there?), each tool call's arguments and result, where the time went, and which step failed. The run_name, tags and metadata from Lesson 6.3 make traces searchable by customer or prompt version. If your organization uses another tracing tool, Langfuse, Arize Phoenix and OpenTelemetrylater · 12.13-based tools (Lesson 12.13) also read LangChain's callbacks.

Measure it: score the agent's tool use

Unit tests check your wiring with a fake. To check the agent's choices, run it against the model you will deploy on questions with known correct tool use, and score each run's trajectory, the tools it called:

CASES = [   # question, the order IDs a correct run must look up
    ("Where is A-1001?", ["A-1001"]),
    ("Where are A-1001 and A-1002?", ["A-1001", "A-1002"]),
    ("hello", []),
]

def trajectory_score(run_agent):
    passed = 0
    for question, expected in CASES:
        calls_made.clear()
        run_agent(question)
        ok = sorted(calls_made) == sorted(expected)
        passed += ok
        print(f"  {'pass' if ok else 'FAIL'} | {question:30} | looked up {sorted(calls_made)}")
    return passed / len(CASES)

from mockllm import start                                  # the lab rig stands in for the model under test
from langchain.chat_models import init_chat_model
rig = init_chat_model("openai:mock-model", base_url=start(), api_key="mock")
candidate = create_agent(rig, tools=[get_order_status])
print("score:", trajectory_score(lambda q: candidate.invoke({"messages": [{"role": "user", "content": q}]})))
What you should see
  pass | Where is A-1001?               | looked up ['A-1001']
  pass | Where are A-1001 and A-1002?   | looked up ['A-1001', 'A-1002']
  pass | hello                          | looked up []
score: 1.0

The scorer compares the order IDs looked up, ignoring order (and prints them sorted), because the two tool calls run side by side and can finish in either order. With a real model, run each case several times; a case that passes four times out of five is a reliability problem (pass^k, Lesson 12.12). LangSmith runs the same idea at scale: a dataset of examples, an evaluator per check, and an experiment per agent version, so two versions can be compared on the same examples. The open-source agentevals package provides trajectory-match evaluators.

Check your mental model
  • ✗ "Tests should check the model's exact wording."
    ✓ Check behavior: which tools ran, with what arguments, and properties of the answer.
  • ✗ "A scripted model tests the model."
    ✓ It tests your code around the model. Model quality is measured by evaluations on real calls.
  • ✗ "Tracing changes what the agent does."
    ✓ It only records; the run is the same with or without it.

Debugging exercise
Debugging exercise: the second test always fails

Each test passes on its own; together, the second one fails.

shared = scripted(*script)                                    # one fake model for the whole test file

def test_a():
    create_agent(shared, tools=[get_order_status]).invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})

def test_b():
    create_agent(shared, tools=[get_order_status]).invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})

for t in (test_a, test_b):
    try:
        t()
        print(t.__name__, "passed")
    except Exception as e:
        print(t.__name__, "failed:", type(e).__name__, str(e)[:60])

What it printed:

test_a passed
test_b failed: RuntimeError generator raised StopIteration

Find the cause and fix it. (Solution D1.)

Make it your own

Write a test that scripts the model asking for a tool that does not exist (delete_order), and checks that the agent sends an error result back to the model instead of crashing. (Solution M1.)

Solutions

SolutionP1 · The script runs out

The fake is an iterator; a third call finds it empty and the run fails with a StopIteration-based error. That is a feature: a test that makes more model calls than expected should fail. Script exactly the calls the test expects.

SolutionB1 · It fails at the first call

At invoke: create_agent only stores the model, and binds the tools when the model node first runs. So the traceback points into the model node, not your setup code. Errors that appear only at run time are the reason to have a test that actually invokes the agent.

SolutionD1 · One script, shared by two tests

Both tests share one fake whose iterator holds two replies. The first test used both, so the second found it empty. Shared state between tests is the bug, not the agent. Build a fresh fake inside each test, as scripted(...) does in Idea 2, or with a pytest fixture.

SolutionM1 · An unknown tool becomes an error result
def test_refuses_unknown_tool_names_from_the_model():
    agent = create_agent(scripted(
        AIMessage("", tool_calls=[{"name": "delete_order", "args": {"order_id": "A-1001"}, "id": "c"}]),
        AIMessage("Sorry, I can't do that.")), tools=[get_order_status])
    state = agent.invoke({"messages": [{"role": "user", "content": "Delete A-1001"}]})
    tool_msg = next(m for m in state["messages"] if m.type == "tool")
    assert tool_msg.status == "error", tool_msg
    print("error result sent to the model:", tool_msg.content[:70])

test_refuses_unknown_tool_names_from_the_model()
print("passed")

error result sent to the model: Error: delete_order is not a valid tool, try one of [get_order_status]
passed

The tools node did not crash: it returned an error ToolMessage naming the valid tools, so a real model can correct itself (Lesson 3.3's rule). This test protects that behavior from future changes.

Check your understanding

Explain the mechanismHow do you test an LLM agent?

Worked answer. In layers. Unit tests with a scripted fake model check the code around the model: tools, argument validation, error results, middleware, limits, approval and resume; they are fast and deterministic, so they run on every commit. Integration tests with the real model check a small set of critical paths. Evals run the agent with the real model on a labeled question set, several times per case, scoring outcomes and trajectories, and gate releases (Lesson 12.11). Production traces then feed new cases back into the set.

A plausible wrong answer. "You cannot unit-test agents because the model is nondeterministic." Only the model is; everything around it can be tested deterministically.

Follow-ups. What would you assert in a test for human approval?

Debug a failureA trace shows the right tool was called, but the answer is wrong. Where do you look next?

Worked answer. At the tool's result in the trace, then at the exact messages of the final model call. If the result was wrong or empty, the bug is in the tool or its data. If the result was right but the model ignored or misread it, look at how it was formatted (a large JSON blob, a missing unit), whether the conversation was summarized or trimmed before the call, and whether the system prompt conflicts with it. Then add the case to the eval set before fixing it.

A plausible wrong answer. "Switch to a bigger model." Possibly, but only after the trace shows the input was right and the model still failed.

Follow-ups. How would you find similar failures across thousands of traces (Lesson 12.14)?

Defend a designShould every agent test use the real model?

Worked answer. No. Real-model tests are slow, cost money and fail for reasons unrelated to the change being tested, so teams start ignoring them. I keep wiring tests on fakes, a short real-model smoke test for critical paths, and quality in evals that run on a schedule and before releases, where variation is expected and measured. The fake tests catch most regressions in our own code; evals catch the model's.

A plausible wrong answer. "Fakes test nothing real." They test all the code you wrote, which is where most bugs are.

Follow-ups. How do you keep fake scripts in sync with the real model's tool-call format?
