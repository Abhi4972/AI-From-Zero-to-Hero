Why this came about

Claude Code (2025) showed how effective a well-built harness could be. Anthropic released its engine as the Claude Agent SDK, so developers could build their own agents with the same file, command, permission and subagent capabilities.

In plain words first
A ready-made harness you can import

The Claude Agent SDK packages the harness behind Claude Code as a library: an agent that can read and write files, run commands, search, use MCPlater · 16.4 servers and subagents, with permission controls and hooks. Instead of building the loop and harness yourself, you configure it. It suits agents that work in a workspace (code, documents, data) and need strong guardrailslater · 15.21 on what they may touch.

Claude Agent SDK: the Claude Code harness as a library

Best fit: agents that work on files, code, shells and long tasks: coding agents, operations runbooks, research and document agents.

The Claude Agent SDK (Python and TypeScript) exposes the harness behind Claude Code: built-in tools for reading, writing and editing files, running shell commands, searching and fetching the web; automatic context compaction; subagents; skills; hooks (PreToolUse, PostToolUse and others); permission modes; sessions you can resume or fork; and MCP servers, including ones defined in-process. It runs the Claude Code engine underneath, so it needs that installed and works with Claude models (through Anthropic's API, Amazon Bedrock, Google Vertex AI or Microsoft Foundrylater · 14.130).

# Not run in this course's sandbox: it needs the Claude Code engine and an API key.
import asyncio
from claude_agent_sdk import query, ClaudeAgentOptions, tool, create_sdk_mcp_server

@tool("get_order_status", "Return the shipping status for an order ID", {"order_id": str})
async def claude_order_status(args: dict) -> dict:
    return {"content": [{"type": "text", "text": f"{args['order_id']} is shipped"}]}

options = ClaudeAgentOptions(
    system_prompt="Help ShopKart customers with orders.",
    mcp_servers={"shopkart": create_sdk_mcp_server(name="shopkart", tools=[claude_order_status])},  # in-process MCP
    allowed_tools=["mcp__shopkart__get_order_status"],     # nothing else is allowed without asking
    max_turns=5,
)

async def claude_main():
    async for message in query(prompt="Where is A-1001?", options=options):
        print(message)

In depth: permissions, hooks, subagents and sessions

The Claude Agent SDK's power is its built-in tools: it can read and edit files and run shell commands. So most of the work of using it safely is deciding what it may do. These are the controls, with names checked against claude-agent-sdk 0.2.178 (not run here: the SDK drives the Claude Code engine, which needs an API key):

The SDK applies the checks in a fixed order (checked against the SDK's permissions documentation in November 2026): hooks first, then deny rules, ask rules, the permission mode, allow rules, and last your can_use_tool function. Three things follow from that order, and each one surprises people:

  • allowed_tools approves; it does not restrict. Tools you leave off the list still exist. A call to one of them falls through to the permission mode and then to can_use_tool. To take a tool away from the model, name it in disallowed_tools.
  • A call that is approved early never reaches can_use_tool. In the example below, Bash is in allowed_tools, so only_reports_folder is never asked about a shell command. That is why the dangerous-command check is a PreToolUse hook: hooks run before everything else, on every call.
  • A deny rule wins in every mode, and allowed_tools does not limit bypassPermissions. That mode approves every tool that is not denied, listed or not.

For an agent that runs with nobody watching, pair a short allowed_tools list with permission_mode="dontAsk": listed tools run, and anything that would have asked a person is refused.

from claude_agent_sdk import (ClaudeAgentOptions, ClaudeSDKClient, HookMatcher, AgentDefinition,
                              PermissionResultAllow, PermissionResultDeny)

async def only_reports_folder(tool_name, tool_input, context):
    """can_use_tool: called before any tool not already allowed or denied."""
    path = tool_input.get("file_path", "")
    if tool_name in ("Write", "Edit") and not path.startswith("/srv/shopkart/reports/"):
        return PermissionResultDeny(message="Only files under reports/ may be changed")
    return PermissionResultAllow()

async def block_dangerous_bash(input_data, tool_use_id, context):
    """A PreToolUse hook: inspect a tool call and deny it before it runs."""
    command = input_data["tool_input"].get("command", "")
    if "rm -rf" in command or "curl" in command:
        return {"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny",
                                       "permissionDecisionReason": "Not allowed in the ShopKart runbook agent"}}
    return {}

options = ClaudeAgentOptions(
    system_prompt="You are ShopKart's operations runbook agent.",
    cwd="/srv/shopkart",
    allowed_tools=["Read", "Grep", "Glob", "Bash"],          # pre-approved tools
    disallowed_tools=["WebFetch"],                            # never available
    permission_mode="default",                                # others: dontAsk, acceptEdits, plan, auto, bypassPermissions
    can_use_tool=only_reports_folder,
    hooks={"PreToolUse": [HookMatcher(matcher="Bash", hooks=[block_dangerous_bash])]},
    agents={"log-reader": AgentDefinition(description="Reads and summarizes service logs",
                                          prompt="Summarize errors in the logs you are given.",
                                          tools=["Read", "Grep"])},   # a subagent with fewer tools
    setting_sources=[],                                       # do not load settings from the machine it runs on
    max_turns=20,
    max_budget_usd=2.0,
)

async with ClaudeSDKClient(options=options) as client:       # multi-turn; query() is for one-shot tasks
    await client.query("Why did last night's refund export fail?")
    async for message in client.receive_response():
        print(message)

permission_mode The default for everything else: ask (default), refuse instead of asking (dontAsk), accept edits, plan only, let a classifier decide (auto), or bypass plan for read-only analysis; dontAsk for unattended agents; never bypassPermissions outside a sandbox

sandbox, cwd, add_dirs Where it can act Containing file and shell access
max_turns, max_budget_usd How long and how expensive a run may be Runaway protection

Two production rules. Run it in a container or sandbox with only the files and network it needs, because a shell tool can do anything the process can (Lesson 15.23). And set setting_sources explicitly: by default the engine can load settings, memory files and tools from the machine it runs on, which makes behavior depend on whoever's laptop or server it is.

Solutions

SolutionP1 · Nobody to ask

Bash is not pre-approved, so the default mode wants to ask for permission, and in a service there is no person to ask: the call is denied (or the run stops waiting, depending on how the host handles permission prompts). Decide permissions in code for services: pre-approve what is safe, deny the rest, and use can_use_tool to route the rest to an approval system.

SolutionD1 · Settings from the machine

The engine loaded settings from the server's environment: user or project settings files, a memory file such as CLAUDE.md, or MCP servers configured there. Set setting_sources=[] (or only the sources you intend, such as the project's), pass tools and MCP servers explicitly, and run in a clean container so the agent's behavior is defined by your code, not the host.

SolutionM1 · An audit hook

Register hooks={"PostToolUse": [HookMatcher(hooks=[audit])]} (no matcher means every tool), where audit(input_data, tool_use_id, context) writes the tool name, a redacted copy of tool_input, the result's size and status, the session ID and a timestamp to your log, and returns {}. Redact with the same rules as Lesson 14.56, before writing.

Check your understanding

Explain the mechanismWhat is the Claude Agent SDK, and how is it different from a framework like LangGraph?

Worked answer. It is the agent harness behind Claude Code as a library: a ready-made loop with built-in file, shell, search and web tools, context compaction, subagents, skills, hooks, permission controls and resumable sessions, driving Claude models. LangGraph is a runtime for graphs you design. The SDK gives a capable general agent you constrain; LangGraph gives building blocks you assemble. Coding, operations and document agents fit the SDK; business workflows with custom control flow fit LangGraph.

A plausible wrong answer. "It is the Anthropic API client." That is the anthropic package; the Agent SDK runs a full agent with tools.

Follow-ups. How would you give it ShopKart-specific tools?

Defend a designWould you let a Claude Agent SDK agent run shell commands in production?

Worked answer. Only inside a sandbox built for it: a container with only the needed files, no credentials beyond the task's, restricted network egress, a pre-approved command list, a PreToolUse hook that blocks dangerous patterns, audit logs, turn and budget limits, and approval for anything that changes production. Without that isolation, no; the model's instructions can be influenced by the content it reads (Lesson 15.22), so permissions must not depend on the model behaving.

A plausible wrong answer. "Yes, the model is safe." Safety comes from the sandbox and permissions, not from trusting the model.
