Why this came about

Multi-agent customer service and triage needed agents to pass conversations between each other, and teams needed to see every step to debug them. Handoffs and built-in tracing were central to the Agents SDK's design for exactly those reasons.

In plain words first
Passing the baton, and seeing every step

A handoff passes the conversation to another agent that takes over, like transferring a call to a specialist. Run context carries your application's data (the signed-in user, connections) to tools without showing it to the model. Streaming shows progress, and built-in tracing records every model call, tool call and handoff for debugging. These are the same ideas as LangGraph's handoffs, context and traces.

Step 4 · Handoffs and agents as tools

Two agents. triage is given handoffs=[refunds], which the SDK shows to the model as a tool named transfer_to_refunds. When the model calls it, the SDK switches agents: refunds takes over the conversation and writes the reply. The result tells you which agent finished the run.

refunds = Agent(name="refunds", instructions="Handle refund requests.", model=model,
                handoff_description="Questions about refunds")
triage = Agent(name="triage", instructions="Route the customer to the right desk.", model=model,
               handoffs=[refunds])                          # exposed to the model as a transfer_to_refunds tool

r = asyncio.run(Runner.run(triage, "I want my refunds sorted"))
print(r.last_agent.name, "|", r.final_output)
What you should see
refunds | You are now with the refunds desk. How can I help?

A handoff passes the whole conversation to another agent, which then talks to the user. The alternative, refunds.as_tool(...), calls an agent like a function and returns only its answer to the caller, keeping control with the orchestrator. Use handoffs for "transfer me to the right team" and agents-as-tools for "ask a specialist and come back".

In production
Handoffs in production

A handoff passes the whole conversation by default, including earlier tool calls the next agent does not need. Use a handoff input filter (the SDK ships helpers such as remove_all_tools in agents.extensions.handoff_filters) to keep the receiving agent's context clean. Watch for agents handing a conversation back and forth, and prefer agents-as-tools when the orchestrator must keep control and combine answers.

Step 5 · Run context, structured output, hooks and streaming

Three features turn a demo into a service. Run context is a typed object you pass to Runner.run(context=...); tools and dynamic instructions receive it, but the model never sees it, so it is the right place for the signed-in customer, a database handle or feature flags. Structured output (output_type=) makes final_output a validated Pydantic object. Lifecycle hooks let you log, time or meter every step.

from dataclasses import dataclass
from pydantic import BaseModel
from agents import RunHooks

@dataclass
class Customer:                       # your app's object; the model never sees it
    customer_id: str
    tier: str
    orders: dict

@function_tool(name_override="get_order_status")
def my_order_status(ctx: RunContextWrapper[Customer], order_id: str) -> str:
    """Return the shipping status for one of this customer's orders, like 'A-1001'."""
    if order_id not in ctx.context.orders:                 # authorization from context, not from the prompt
        return f"{order_id} does not belong to this customer"
    return f"{order_id} is {ctx.context.orders[order_id]}"

class Reply(BaseModel):
    answer: str
    needs_human: bool

typed_agent = Agent[Customer](
    name="support", model=model, tools=[my_order_status], output_type=Reply,
    instructions=lambda ctx, agent: f"Help a {ctx.context.tier}-tier customer. Be brief.")   # dynamic instructions

ravi = Customer("C-42", "gold", {"A-1001": "shipped"})
r = asyncio.run(Runner.run(typed_agent, "Where is B-2002?", context=ravi))
print(type(r.final_output).__name__, r.final_output)
print("usage:", r.context_wrapper.usage.requests, "requests,", r.context_wrapper.usage.total_tokens, "tokens")

class StepLogger(RunHooks):
    async def on_tool_start(self, context, agent, tool):
        print("  tool start:", tool.name)
    async def on_tool_end(self, context, agent, tool, result):
        print("  tool end:  ", tool.name, "->", result)
    async def on_agent_end(self, context, agent, output):
        print("  agent end: ", agent.name)

plain_agent = Agent[Customer](name="support", instructions="Help.", model=model, tools=[my_order_status])
asyncio.run(Runner.run(plain_agent, "Where is A-1001?", context=ravi, hooks=StepLogger()))

async def stream_it():
    run = Runner.run_streamed(plain_agent, "Where is A-1001?", context=ravi)
    async for event in run.stream_events():               # also raw token deltas: "raw_response_event"
        if event.type == "run_item_stream_event":
            print("  event:", event.name)
    print("final:", run.final_output)

asyncio.run(stream_it())
What you should see
Reply answer='B-2002 does not belong to this customer' needs_human=False
usage: 2 requests, 140 tokens
  tool start: get_order_status
  tool end:   get_order_status -> A-1001 is shipped
  agent end:  support
  event: tool_called
  event: tool_output
  event: message_output_created
final: Here is what I found: A-1001 is shipped

The check that B-2002 belongs to someone else happened in code, using the customer from the run context, so no prompt injectionlater · 15.24 can talk the agent past it. usage adds up every model request in the run; log it per run to watch cost. A UI usually streams raw_response_event token deltas to the screen and uses the item events to show "looking up your order..." states.

Hosted tools and MCPlater · 16.26 round out the toolset:

  • Hosted tools run on OpenAI's side when using OpenAI models: WebSearchTool, FileSearchTool (over vector stores), CodeInterpreterTool, ComputerTool, ImageGenerationTool, plus ShellTool and ApplyPatchTool for coding agents.
  • MCP: connect local servers with MCPServerStdio (from agents.mcp), remote ones with MCPServerStreamableHttp, or let OpenAI's platform call a remote server with HostedMCPTool.

Step 6 · Test it without a model

The SDK ships a scripted model for unit tests:

from agents.testing import ScriptedModel, function_call, assistant_message

def test_agent_looks_up_the_order():
    scripted = ScriptedModel([
        [function_call("get_order_status", {"order_id": "A-1001"}, call_id="c1")],   # step 1: call the tool
        [assistant_message("A-1001 has shipped.")],                                 # step 2: answer
    ])
    test_agent = Agent(name="support", model=scripted, tools=[get_order_status])
    result = asyncio.run(Runner.run(test_agent, "Where is A-1001?"))
    tool_outputs = [i.output for i in result.new_items if i.type == "tool_call_output_item"]
    assert tool_outputs == ["A-1001 is shipped"]
    assert result.final_output == "A-1001 has shipped."

test_agent_looks_up_the_order()
print("test passed")
What you should see
test passed

The scripted model is also how you test failure paths that a real model produces only occasionally. This one keeps calling the same tool forever; max_turns is the circuit breaker:

from agents import MaxTurnsExceeded

stuck = ScriptedModel([[function_call("get_order_status", {"order_id": "A-1001"}, call_id=f"c{i}")]
                       for i in range(10)])                 # a model that never stops calling tools
looping_agent = Agent(name="looper", model=stuck, tools=[get_order_status])
try:
    asyncio.run(Runner.run(looping_agent, "Where is A-1001?", max_turns=3))
except MaxTurnsExceeded as e:
    print("stopped:", e)
What you should see
stopped: Max turns (3) exceeded

Set max_turns on every production run (the default is 10), and catch MaxTurnsExceeded to hand off to a person instead of failing silently. Pair it with an error_handlers entry or a fallback answer so the customer always gets a reply.

Step 7 · Tracing and running in production

Tracing is on by default and sends every agent run, model call, tool call, handoff and guardrail to the Traces view in the OpenAI platform. You can add your own processors with add_trace_processor, or replace the default with set_trace_processors, to send spans to Langfuse, LangSmith, Arize, Datadog, Braintrust or any OpenTelemetrylater · 14.145 backend (most publish an integration). Set set_tracing_disabled(True) where data must not leave your environment, and check your organization's data-retention settings.

A trace processor is a small class with six methods. This one prints each finished span, which shows how an agent used as a tool nests inside its caller. The orchestrator here is scripted, so the run is fully predictable:

from agents.tracing import TracingProcessor, set_trace_processors

class PrintSpans(TracingProcessor):
    def on_trace_start(self, trace): print("trace:", trace.name)
    def on_trace_end(self, trace): pass
    def on_span_start(self, span): pass
    def on_span_end(self, span):
        data = span.span_data
        if data.type in ("agent", "function"):              # also: generation, handoff, guardrail, turn
            print(f"  {data.type:8} {data.name}")
    def shutdown(self): pass
    def force_flush(self): pass

set_tracing_disabled(False)
set_trace_processors([PrintSpans()])                         # replaces the default OpenAI exporter

specialist = Agent(name="orders-specialist", instructions="Look up orders.", model=model,
                   tools=[get_order_status])
lead = Agent(name="lead", instructions="Delegate order questions to the specialist.",
             model=ScriptedModel([
                 [function_call("ask_orders_specialist", {"input": "Where is A-1001?"}, call_id="c1")],
                 [assistant_message("The specialist says A-1001 has shipped.")]]),
             tools=[specialist.as_tool(tool_name="ask_orders_specialist",
                                       tool_description="Ask the orders specialist a question")])

print(asyncio.run(Runner.run(lead, "Where is A-1001?")).final_output)
set_trace_processors([])
set_tracing_disabled(True)
What you should see
trace: Agent workflow
  function get_order_status
  agent    orders-specialist
  function ask_orders_specialist
  agent    lead
The specialist says A-1001 has shipped.

Spans finish inside out: the specialist's tool call, then the specialist, then the tool call that wrapped it, then the lead. That nesting is what lets you see which agent spent the tokens and time in a multi-agent run. To export to a backend instead of printing, use its integration or an OpenTelemetry processor; use add_trace_processor to keep OpenAI's dashboard as well.

The SDK is a library, so you host it like any Python service: a container behind FastAPI, a queue worker, AWS Lambda, Cloud Run, or a managed agent runtime such as Bedrock AgentCore. For long-running work, the sandboxlater · 15.25 harness and its snapshots, or a durable engine (Temporal publishes an official Agents SDK integration), keep runs alive across failures.

Exercises

Predict before you run

Triage hands off to refunds, which has output_type=RefundDecision. What type is result.final_output, and which agent is result.last_agent? (Solution P1.)

Break it on purpose

Give the refunds agent a handoff back to triage, and triage a handoff to refunds, with instructions that each should hand off when unsure. Ask an ambiguous question. What stops the run? (Solution B1.)

Debugging exercise
Debugging exercise: the specialist knows too much

After a handoff, the refunds agent quotes a delivery address that only appeared in an earlier tool result of the triage agent. The team did not want specialists to see earlier tool output. Find the cause and the fix. (Solution D1.)

Make it your own

Write a test that runs the triage agent against the lab rig with tracing disabled, and asserts that "I want my refunds sorted" ends with the refunds agent as last_agent. (Solution M1.)

Solutions

SolutionP1 · The last agent's type

final_output is a RefundDecision instance, because the agent that produced the final answer, refunds, declares that output type; last_agent is the refunds agent. Code that reads final_output must know which agent finished, or check its type, when different agents have different output types.

SolutionB1 · Max turns

The agents can hand the conversation back and forth, and each handoff is a turn, so the run stops at max_turns with a MaxTurnsExceeded error. Give each agent a clear scope, make one of them the place where unsure cases end (often a person), and set max_turns deliberately.

SolutionD1 · Handoffs pass the whole history by default

A handoff passes the whole conversation, including earlier tool calls and results, to the next agent. Use a handoff input filter, for example handoff(refunds, input_filter=handoff_filters.remove_all_tools) from agents.extensions, to pass only what the specialist needs. The same question appears in LangGraph as what state a subgraph shares (Lesson 14.107).

SolutionM1 · A routing test

Build the agents on the lab rig's model, call set_tracing_disabled(True), run Runner.run(triage, "I want my refunds sorted"), and assert result.last_agent.name == "refunds". The rig's rule calls transfer_to_refunds when the message mentions refunds, so the test checks your handoff wiring; routing quality with a real model belongs in evals.

Check your understanding

Explain the mechanismHow do handoffs and agents-as-tools differ in the Agents SDK?

Worked answer. A handoff transfers the conversation: the next agent receives the history (filterable) and talks to the user from then on, which suits triage to a specialist. An agent as a tool (agent.as_tool) is called like a function: the calling agent sends an input, gets the result back and stays in charge, which suits delegating a sub-question. Handoffs share more context and give up control; agents-as-tools keep control and context smaller.

A plausible wrong answer. "They are the same; as_tool is just older." They give different control and context behavior.

Follow-ups. Which would you use for a translation step?

Debug a failureTraces show long runs with many handoffs between two agents. What is wrong?

Worked answer. The agents' scopes overlap, so each decides the other should answer. Read both agents' instructions and handoff descriptions, which the model uses to choose; make them disjoint, add a rule for unclear cases, and lower max_turns so loops fail fast. Then evaluate routing on labeled questions.

A plausible wrong answer. "The model is confused; use a bigger one." The instructions are ambiguous; a bigger model may loop less often but still loop.

Follow-ups. How would you detect ping-pong handoffs in production metrics?

Defend a designIs the Agents SDK's built-in tracing enough for production?

Worked answer. It is a good default: every run, model call, tool call, handoff and guardrail appears as spans, sent to OpenAI's dashboard or to other backends through trace processors. For production I would also export to the organization's observability stack (OpenTelemetry-based tools, Lesson 14.145), control what data is recorded (sensitive inputs), and link traces to business events such as tickets and refunds.

A plausible wrong answer. "Yes, no other tooling is needed." Data governance and cross-system correlation usually require more.

Follow-ups. How would you stop customer data from reaching an external tracing backend?
