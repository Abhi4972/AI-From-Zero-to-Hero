The system

ShopKart's support desk, built from this block's pieces:

Build it

The whole desk is one file. It is long, so read it in the order of the table above: the redact node, the triage router, the tracking agent, the refund subgraph, the FAQ node, and at the bottom the few lines that wire them into one graph with a checkpointer and a store. Nothing in it is new; every piece comes from the lesson named in the table.

import re, sqlite3, os
from dataclasses import dataclass
from typing import Literal
from mockllm import start                                         # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.tools import tool
from langchain_core.messages import AIMessage, HumanMessage
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.types import interrupt, Command
from langgraph.runtime import Runtime
from langgraph.store.memory import InMemoryStore
from langgraph.checkpoint.sqlite import SqliteSaver

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock")
ORDERS = {"A-1001": ("shipped", 1200), "A-1002": ("processing", 899), "A-1077": ("delivered", 7999)}
FAQ = {"refund": "Refunds reach UPI in 2 days and cards in 5 to 7 business days. [refund-policy.md]",
       "cod": "Cash on delivery has a INR 30 fee and is available up to INR 10,000. [cod.md]"}
REFUNDS_SENT = set()                                              # stands in for the payment provider's idempotency check

@dataclass
class Customer:
    customer_id: str
    tier: Literal["gold", "silver"]

class Support(MessagesState, total=False):
    route: str
    order_id: str
    amount: int
    outcome: str

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    status = ORDERS.get(order_id, ("not found", 0))[0]
    return f"{order_id} is {status}"

tracking_agent = create_agent(chat, tools=[get_order_status], name="tracking",
                              system_prompt="You track ShopKart orders. Be brief.")

def last_text(state):
    return state["messages"][-1].content

def redact(state):                                                # guardrail: no emails reach any model (Lesson 6.6)
    m = state["messages"][-1]
    clean = re.sub(r"\S+@\S+", "[email]", m.content)
    return {} if clean == m.content else {"messages": [HumanMessage(clean, id=m.id)]}   # same id: replace

def triage(state, runtime: Runtime[Customer]):
    text = last_text(state).lower()
    if "hindi" in text:
        runtime.store.put(("customers", runtime.context.customer_id), "language", {"value": "Hindi"})
    route = "refund" if "refund" in text and re.search(r"[A-Z]-\d{4}", last_text(state)) else \
            "tracking" if re.search(r"[A-Z]-\d{4}", last_text(state)) else "faq"
    return {"route": route}

def faq(state, runtime: Runtime[Customer]):
    text = last_text(state).lower()
    answer = next((a for k, a in FAQ.items() if k in text), "Let me connect you with a colleague.")
    pref = runtime.store.get(("customers", runtime.context.customer_id), "language")
    prefix = "[in Hindi] " if pref and pref.value["value"] == "Hindi" else ""
    return {"messages": [AIMessage(prefix + answer)]}

def find_order(state):
    oid = re.search(r"[A-Z]-\d{4}", last_text(state)).group()
    return {"order_id": oid, "amount": ORDERS.get(oid, ("not found", 0))[1]}

def approve(state, runtime: Runtime[Customer]):
    limit = 10000 if runtime.context.tier == "gold" else 5000
    if state["amount"] <= limit:
        return {"outcome": "auto-approved"}
    decision = interrupt({"order_id": state["order_id"], "amount": state["amount"], "limit": limit})
    return {"outcome": "approved" if decision["approved"] else f"declined: {decision.get('note', '')}"}

def issue_refund(state):
    if not state["outcome"].endswith("approved"):
        return {"messages": [AIMessage(f"I can't refund {state['order_id']} ({state['outcome']}).")]}
    REFUNDS_SENT.add(state["order_id"])                           # idempotent: a repeat adds nothing
    return {"messages": [AIMessage(f"Refund of INR {state['amount']:,} for {state['order_id']} is on its way.")]}

rb = StateGraph(Support, context_schema=Customer)
for name, fn in [("find_order", find_order), ("approve", approve), ("issue_refund", issue_refund)]:
    rb.add_node(name, fn)
rb.add_edge(START, "find_order"); rb.add_edge("find_order", "approve")
rb.add_edge("approve", "issue_refund"); rb.add_edge("issue_refund", END)
refund_flow = rb.compile()

sb = StateGraph(Support, context_schema=Customer)
for name, node in [("redact", redact), ("triage", triage), ("tracking", tracking_agent),
                   ("refund", refund_flow), ("faq", faq)]:
    sb.add_node(name, node)
sb.add_edge(START, "redact"); sb.add_edge("redact", "triage")
sb.add_conditional_edges("triage", lambda s: s["route"], ["tracking", "refund", "faq"])
for name in ["tracking", "refund", "faq"]:
    sb.add_edge(name, END)

if os.path.exists("support.db"):
    os.remove("support.db")
desk = sb.compile(checkpointer=SqliteSaver(sqlite3.connect("support.db", check_same_thread=False)), store=InMemoryStore())
print("nodes:", [n for n in desk.get_graph().nodes if not n.startswith("__")])
What you should see
nodes: ['redact', 'triage', 'tracking', 'refund', 'faq']

Read the build top to bottom and notice what is not there: no loop for the agent (the tracking node is a whole agent), no saving code (the checkpointer), no retry or approval plumbing (interrupt and the threads), and no customer ID in any node's arguments: it comes from runtime.context, which the application fills from the signed-in user.

Run a day at the desk

Now use it the way customers would. Two customers, on separate threads, ask about an order, ask for refunds of different sizes, and ask a policy question. The helper say sends one message and returns either the reply or a note that the run is paused for approval:

def say(thread, customer, text):
    cfg = {"configurable": {"thread_id": thread}, "recursion_limit": 25}
    out = desk.invoke({"messages": [{"role": "user", "content": text}]}, cfg, context=customer, version="v2")
    if out.interrupts:
        return f"(paused for approval: {out.interrupts[0].value})"
    return out.value["messages"][-1].content

ravi, meera = Customer("C-42", "silver"), Customer("C-77", "gold")
print("1:", say("ravi-1", ravi, "Where is A-1002? I'm ravi@example.com"))
print("2:", say("ravi-1", ravi, "How long does a refund take? Reply in Hindi please"))
print("3:", say("ravi-2", ravi, "What is the fee for COD?"))
print("4:", say("ravi-1", ravi, "I want a refund for A-1001"))
print("5:", say("ravi-1", ravi, "I want a refund for A-1077"))
print("5:", desk.invoke(Command(resume={"approved": True}), {"configurable": {"thread_id": "ravi-1"}}, context=ravi)["messages"][-1].content)
print("6:", say("meera-1", meera, "I want a refund for A-1077"))

2: [in Hindi] Refunds reach UPI in 2 days and cards in 5 to 7 business days. [refund-policy.md]
3: [in Hindi] Cash on delivery has a INR 30 fee and is available up to INR 10,000. [cod.md]
4: Refund of INR 1,200 for A-1001 is on its way.

Six turns, each exercising a lesson. 1: the tracking agent answered with the email already redacted. 2: the FAQ answered with its source and saved the Hindi preference. 3: a new thread for the same customer still answered in Hindi, from the store. 4: a small refund was approved automatically. 5: a refund above the silver limit paused; the approval came back as a Command and the refund completed. 6: the same amount for a gold customer, whose limit is higher, needed no approval.

Tests

Finally, the tests that would run on every change. They use the scripted model from Lesson 14.99, so they need no network and give the same result every time. Each one checks one piece of wiring: that the tracking agent calls the right tool, that a refund above a silver customer's limit pauses for approval, and that redaction replaces the stored message.

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel

class ScriptedChatModel(GenericFakeChatModel):                   # from Lesson 6.8
    def bind_tools(self, tools, **kwargs):
        return self

def test_tracking_agent_looks_up_the_order():
    fake = ScriptedChatModel(messages=iter([
        AIMessage("", tool_calls=[{"name": "get_order_status", "args": {"order_id": "A-1077"}, "id": "t1"}]),
        AIMessage("A-1077 was delivered.")]))
    agent = create_agent(fake, tools=[get_order_status])
    msgs = agent.invoke({"messages": [{"role": "user", "content": "Where is A-1077?"}]})["messages"]
    assert next(m for m in msgs if m.type == "tool").content == "A-1077 is delivered"

def test_silver_refund_over_limit_pauses():
    g = rb.compile(checkpointer=SqliteSaver(sqlite3.connect(":memory:", check_same_thread=False)))
    out = g.invoke({"messages": [HumanMessage("refund A-1077")]}, {"configurable": {"thread_id": "t"}},
                   context=Customer("C-1", "silver"), version="v2")
    assert out.interrupts and out.interrupts[0].value["limit"] == 5000

def test_redaction_replaces_the_message():
    out = redact({"messages": [HumanMessage("mail me at a@b.com", id="m1")]})
    assert out["messages"][0].content == "mail me at [email]" and out["messages"][0].id == "m1"

for t in [test_tracking_agent_looks_up_the_order, test_silver_refund_over_limit_pauses, test_redaction_replaces_the_message]:
    t(); print("passed:", t.__name__)

Solutions

SolutionP1 · Trace one turn

redact replaces the email; triage sees "refund" and an order ID and routes to refund; find_order finds INR 899; approve auto-approves it under the silver limit, so there is no interrupt; issue_refund sends it and replies. Saved: the redacted message, the route, the order ID, the amount, the outcome and the reply, as checkpoints on the new thread. Nothing goes to the store, because no preference was stated.

SolutionB1 · Order is a security property

Every turn still gets an answer, but triage and anything it calls now see the original message, and if triage saved anything or logged it, the email leaks. The saved thread still ends up redacted, so the audit's email count stays 0, which is exactly why the order bug is easy to miss: the audit checks the wrong place. Guardrails go first, and tests should check what each node received, not only what was saved.

SolutionD1 · Input is not a resume

Sending input to a waiting thread starts a new run from START. Each thread's new message went through redact and triage again; if it was routed to the refund flow, it paused at a new interrupt, and if not, it was answered as a new question. Either way, no interrupt was answered, so no refund was sent. The job must resume each thread with Command(resume={"approved": True}) (or command={"resume": ...} over the API), using the stored thread ID, and should log the interrupt it answered.

SolutionM1 · A returns route

Add "returns" to the router (when the text contains "return" and an order ID), a node that looks up the status and replies "Return started for …" only when it is delivered, and an edge from it to END. Test it like test_redaction_replaces_the_message: call the node directly with a delivered order and with a processing one, and assert on the reply. Then add a routing test that sends both messages through triage.

Check your understanding

Explain the mechanismWhat is the difference between LangChain and LangGraph, and how do they fit together?

Worked answer. LangChain is the component layer: chat model integrations, messages, prompts, tools, structured output, retrievers, and create_agent with middleware. LangGraph is the runtime underneath: a graph of nodes over a typed state, with checkpoints, interrupts, streaming, subgraphs and durable executionlater · 14.140. create_agent returns a LangGraph graph, so a team can start with LangChain's agent and drop to LangGraph when it needs custom control flow, using the same components inside its nodes. LangSmith is the separate platform for tracing, evaluation and deployment.

A plausible wrong answer. "LangGraph replaced LangChain." They are layers; LangChain 1.x agents run on LangGraph.

Follow-ups. Which LangChain pieces would you still use inside a hand-written LangGraph graph?

Explain the mechanismWalk through what happens, step by step, when a LangGraph agent with a checkpointer handles one user message.

Worked answer. The caller invokes the graph with the new message and a thread ID. The checkpointer loads the thread's last state, and the add_messages reducer appends the message. The model node calls the model with the history and bound tools; a checkpoint is saved. The conditional edge sees tool calls and goes to the tools node, which runs them in parallel and appends ToolMessages; another checkpoint. Back to the model, which answers without tool calls; the edge goes to END and the final state is saved and returned. Middleware hooks run around the model and tool calls, and an interrupt at any point saves the state and returns its payload instead.

A plausible wrong answer. "The agent keeps the conversation in memory between calls." The process keeps nothing; the checkpointer loads and saves it per thread.

Follow-ups. How many checkpoints does that run write, and what is in each?

Debug a failureUsers of a LangGraph chat app sometimes see another user's earlier messages. What do you check?

Worked answer. Thread identity first: how the app chooses the thread ID. A constant, a reused ID, or one derived from something users share, such as a session cookie that is not per user, puts two users on one thread. Then the store's namespaces, which must include the user ID from authentication. Then caching or streaming layers that might mix responses. I would reproduce it with two test users, check which thread each request used in the traces, and add a test that two users never share a thread or a namespace.

A plausible wrong answer. "The model remembered the other user." Models keep nothing between calls; the state was shared.

Follow-ups. How would you clean up after the leak was fixed?

Debug a failureA LangGraph workflow sends duplicate emails after deploys. Why, and how do you fix it?

Worked answer. A deploy stops runs mid-node, and on resume the interrupted node runs again from its start. If the email is sent inside a node that then does more work, or before an interrupt, it is sent again. Put the send in its own node so that it is checkpointed as soon as it finishes, make it idempotent with a key the email service or an outbox table checks, and record that it was sent in state. Test it by failing the step after the send.

A plausible wrong answer. "Checkpoints should prevent repeats." They prevent repeating finished nodes, not the inside of an unfinished one.

Follow-ups. How would graceful shutdown during deploys reduce this?

Defend a designWould you choose LangGraph for a new production agent? What are the alternatives and trade-offs?

Worked answer. For an agent that needs durable state, human approval, streaming and some custom control flow, yes: those are LangGraph's core, they are hard to build well, and the code is portable across hosting options. The trade-offs are another abstraction to learn and debug, version churn in a fast-moving ecosystem, and the commercial platform being separate from the open-source library. Alternatives: a provider SDK such as the OpenAI Agents SDK or the Claude Agent SDK for simpler agents tied to one provider, a workflow engine such as Temporal for long cross-service processes, or plain code with a checkpoint table for small agents. I would decide with a spike that builds our hardest path, approval and resume, in the top two candidates (Lesson 14.127).

A plausible wrong answer. "Frameworks are unnecessary; just write the loop." The loop is easy; durable pauses, resumes, parallel tool calls and streaming are not.

Follow-ups. What would you pin and test to manage upgrades?

Defend a designcreate_agent with middleware, or a custom StateGraph, for ShopKart's desk?

Worked answer. Both, in layers, as in this capstone: the desk is a custom graph, because its control flow is ours (guardrail first, routing, a refund workflow with business rules and an approval), and the specialists inside it are create_agent agents, because a model choosing among a few tools is exactly what that loop does well. If the whole desk were one agent with a few tools, I would use create_agent alone with approval and limit middleware, and move to a custom graph only when a requirement did not fit the middleware hooks.

A plausible wrong answer. "One giant agent with every tool and a long prompt." It is simpler to start, but harder to control, test and secure as rules grow.

Follow-ups. Which parts of the desk would you evaluate separately?

Explain the mechanismWhy LangGraph? What does it give you that a while loop does not?

Worked answer. A while loop is fine until the agent must survive a crash, pause for days for an approval, run steps in parallel and merge their results, stream progress, be replayed from any step for debugging, or be composed with other agents. LangGraph gives all of these on one model: typed state with reducers, nodes and edges including cycles, checkpoints per thread, interrupt and Command, stream modes, subgraphs, retry and cache policies, and a server runtime. The loop's logic is small; durable, observable, controllable execution is what you would otherwise rebuild.

A plausible wrong answer. "It makes agents smarter." The model's intelligence is unchanged; the runtime makes behavior controllable.

Follow-ups. Name a case where you would not use LangGraph.

Explain the mechanismCompare LangGraph with the OpenAI Agents SDK, CrewAI and a workflow engine such as Temporal.

Worked answer. LangGraph is a low-level, provider-neutral runtime: you design the graph, and get checkpoints, interrupts and streaming. The OpenAI Agents SDK is higher level and smaller: agents, handoffs, guardrails and sessions with less control-flow design, best with OpenAI models. CrewAI organizes role-based agents into crews and flows, quick for multi-role pipelines with less fine-grained control. Temporal is a general durable workflow engine for long, cross-service processes; it is not LLM-specific, and an agent can run as an activity inside it. Choose by how much control flow you must own and how long-lived and cross-service the process is.

A plausible wrong answer. "They all do the same thing." They sit at different levels of abstraction.

Follow-ups. How would you combine LangGraph and Temporal?

Debug a failureAn agent works in a notebook, and in production half the approvals never complete. Walk through your investigation.

Worked answer. Check how approvals resume: the thread ID must be the paused thread's, built from the user, and the resume must be a Command, not new input. Check persistence: a database checkpointer shared by all workers, not InMemorySaver per process. Check deploys: renamed nodes or state keys break old checkpoints. Check timeouts: pending approvals without SLAs or reminders. Then add a dashboard of threads waiting at an interrupt, with their age.

A plausible wrong answer. "The approvers are slow." Possibly, but the common causes are plumbing.

Follow-ups. How would you migrate pending approvals across a breaking deploy?
