Why this came about

Agents that ran in memory lost everything on a crash or redeploy. LangGraph built in checkpointers from the start, borrowing durable execution from workflow engines, so every step is saved and runs can resume, be inspected and be replayed.

The problem: runs outlive processes

A refund run waits for an order service that is down, or for a person's approval that comes tomorrow. Meanwhile the process restarts for a deploy. In Lesson 3.5 you wrote run state to JSON files after every step so that a run could resume; in Lesson 6.9 your engine appended checkpoints to a list. LangGraph does this for every graph with a checkpointer: after every step, the whole state, what runs next and some metadata are saved, grouped by thread.

The idea in plain words

In plain words first
Autosave with named save slots

A checkpointer saves a copy of the state after every step, the way a game autosaves. The thread ID is the name of the save slot: call the graph again with the same thread ID and it loads that slot and carries on; a new thread ID is a new game. Each saved copy is a checkpoint.

The whole idea in plain Python:

saved = {}                                        # thread_id -> list of snapshots

def run_turn(thread_id, user_text):
    history = saved.get(thread_id, [[]])[-1]      # load the latest snapshot, or start empty
    history = history + [f"user: {user_text}"]
    saved.setdefault(thread_id, []).append(history)          # snapshot after step 1
    history = history + [f"bot: reply to {user_text!r}"]
    saved[thread_id].append(history)                          # snapshot after step 2
    return history

run_turn("chat-1", "I want a refund")
print(run_turn("chat-1", "It is order A-1077"))  # same thread: the earlier turn is loaded
print(run_turn("chat-2", "It is order A-1077"))  # new thread: starts empty
print(len(saved["chat-1"]), "snapshots for chat-1")

['user: I want a refund', "bot: reply to 'I want a refund'", 'user: It is order A-1077', "bot: reply to 'It is order A-1077'"]
['user: It is order A-1077', "bot: reply to 'It is order A-1077'"]

What LangGraph adds is everything hard to write yourself: real databases, the full history for going back (Idea 4), and records of unfinished work so a crashed or paused run can continue (Idea 3 and Lesson 6.13). A checkpoint holds the whole state, not just messages: every key, what runs next, and metadata.

Idea 1 · A checkpointer and a thread

Compile the same kind of graph with a checkpointer and it saves the state after every step. The saves are filed under a thread ID that you pass with each call. Run the graph, then ask for the saved state of that thread: everything the run produced is still there, along with which node would run next.

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

class RefundState(TypedDict, total=False):
    msg: str
    intent: str
    order: dict
    done: str

CALLS = []                                   # which nodes actually ran, to see what a resume repeats
SERVICE = {"down": False}

def classify(state):
    CALLS.append("classify")
    return {"intent": "refund" if "refund" in state["msg"].lower() else "other"}

def lookup(state):
    CALLS.append("lookup")
    if SERVICE["down"]:
        raise ConnectionError("order service unavailable")
    return {"order": {"id": "A-1077", "amount": 7999}}

def refund(state):
    CALLS.append("refund")
    return {"done": f"refunded INR {state['order']['amount']:,}"}

def build(checkpointer):
    b = StateGraph(RefundState)
    for name, fn in [("classify", classify), ("lookup", lookup), ("refund", refund)]:
        b.add_node(name, fn)
    b.add_edge(START, "classify"); b.add_edge("classify", "lookup")
    b.add_edge("lookup", "refund"); b.add_edge("refund", END)
    return b.compile(checkpointer=checkpointer)

graph = build(InMemorySaver())
cfg = {"configurable": {"thread_id": "refund-A-1077"}}
graph.invoke({"msg": "I want a refund for A-1077"}, cfg)

snap = graph.get_state(cfg)
print("values:", snap.values)
print("next:  ", snap.next, "| step:", snap.metadata["step"])
What you should see
values: {'msg': 'I want a refund for A-1077', 'intent': 'refund', 'order': {'id': 'A-1077', 'amount': 7999}, 'done': 'refunded INR 7,999'}
next:   () | step: 3

get_state returns a snapshot of the thread's latest checkpoint: the state's values, the nodes that will run next (none: the run finished), and metadata such as the step number. The thread ID in config chooses the thread; one thread per conversation or per case is the usual design (Lesson 6.5 used one per customer conversation).

Idea 2 · The history of a thread

The checkpointer keeps every save, not only the latest. get_state_history returns them newest first. Each one records which step it was, which node was due to run next, and what the state held at that moment:

for snap in graph.get_state_history(cfg):                    # newest first
    print(f"step {snap.metadata['step']:>2} | next {str(snap.next):14} | keys {sorted(snap.values)}")
What you should see
step  3 | next ()             | keys ['done', 'intent', 'msg', 'order']
step  2 | next ('refund',)    | keys ['intent', 'msg', 'order']
step  1 | next ('lookup',)    | keys ['intent', 'msg']
step  0 | next ('classify',)  | keys ['msg']
step -1 | next ('__start__',) | keys []
Reading this output

Read it from the bottom up to replay the run: - step -1, next ('__start__',), no keys: the input arrived but is not in the state yet. - step 0, next ('classify',): the input was written into the state (msg); classify is due. - steps 1 and 2: each node finished and added its key (intent, then order); next names the node due after it. - step 3, next (): refund finished; nothing is left to run.

next is the column to read when debugging: empty means the run finished; a node name means it stopped before that node, because it crashed or is waiting for a person.

One checkpoint per step, newest first: before anything ran (step -1), and after each node. This is what makes LangGraph runs debuggable after the fact: for any run, you can see the state at every step, not just the end.

Idea 3 · Crash, then resume in a new process

Now the order service is down, and the checkpoints go to a database file:

import os, sqlite3
from langgraph.checkpoint.sqlite import SqliteSaver

if os.path.exists("refunds.db"):
    os.remove("refunds.db")
CALLS.clear()
SERVICE["down"] = True

durable = build(SqliteSaver(sqlite3.connect("refunds.db", check_same_thread=False)))
cfg2 = {"configurable": {"thread_id": "refund-A-2001"}}
try:
    durable.invoke({"msg": "I want a refund for A-2001"}, cfg2)
except ConnectionError as e:
    print("run failed:", e)

snap = durable.get_state(cfg2)
print("saved values:", snap.values)
print("next:", snap.next, "| error:", snap.tasks[0].error)
print("ran so far:", CALLS)
What you should see
run failed: order service unavailable
saved values: {'msg': 'I want a refund for A-2001', 'intent': 'refund'}
next: ('lookup',) | error: ConnectionError('order service unavailable')
ran so far: ['classify', 'lookup']

The run failed in lookup. The checkpoint after classify was saved, and the snapshot records that lookup is next and why it failed. Now the service comes back, and a new process, with a new graph object and only the database in common, continues the thread:

SERVICE["down"] = False
restarted = build(SqliteSaver(sqlite3.connect("refunds.db", check_same_thread=False)))   # a new process, same database

print(restarted.invoke(None, cfg2)["done"])                     # None: no new input, continue the thread
print("ran in total:", CALLS)
What you should see
refunded INR 7,999
ran in total: ['classify', 'lookup', 'lookup', 'refund']

Invoking with None as input means "no new input, continue this thread". classify did not run again; lookup ran a second time, now successfully, and the run finished. That is durable execution: a run's progress survives failures and restarts, and only unfinished work is redone. In production the database is Postgres (PostgresSaver from langgraph-checkpoint-postgres, which needs setup() once to create its tables), or the platform's built-in persistence (Lesson 6.17).

Idea 4 · Time travel: go back and branch

A reviewer finds that the refund amount should have been INR 4,999. Go back to the checkpoint before refund, correct the state there, and run from that point:

history = list(graph.get_state_history(cfg))
before_refund = next(s for s in history if s.next == ("refund",))
print("going back to step", before_refund.metadata["step"], "with order", before_refund.values["order"])

forked = graph.update_state(before_refund.config, {"order": {"id": "A-1077", "amount": 4999}})   # a corrected amount
print(graph.invoke(None, forked)["done"])
print("checkpoints in the thread now:", len(list(graph.get_state_history(cfg))))
What you should see
going back to step 2 with order {'id': 'A-1077', 'amount': 7999}
refunded INR 4,999
checkpoints in the thread now: 7

update_state writes a new checkpoint that branches from the old one (a fork); the original history is kept, which is why the thread now has more checkpoints. Invoking with the fork's config runs only what came after that point. Uses: replaying a failed production run from just before the failure with a fix, testing "what if the tool had returned this", and letting a person correct an agent's state before it continues.

What to keep in state

Checkpoints save the state after every step, so the state's contents decide the cost and the risk:

  • Keep: what the run must remember after a pause: messages, decisions, IDs, results of expensive steps.
  • Do not keep: database connections, clients and secrets (pass them as context, Lesson 6.11), and large blobs such as files or images (store them elsewhere and keep a reference).
  • Serialization: values must be serializable by the checkpointer's serializer, which handles JSON types, LangChain messages, Pydantic models and dataclasses. Checkpointers can encrypt state at rest with an encrypted serializer.
  • Retention: every step of every thread is stored; plan deletion of old threads, both for cost and for data-protection rules (Lesson 10.4).

Debugging exercise
Debugging exercise: two refunds for one order

A refund node sends money and then writes an accounting entry. The ledger was briefly down, the run was resumed, and finance reports a double refund.

CHARGES = []
LEDGER = {"up": False}

def refund_and_record(state):
    CHARGES.append(state["order"]["id"])                       # sends money to the customer
    if not LEDGER["up"]:
        raise ConnectionError("ledger unavailable")            # then writes the accounting entry
    return {"done": "refunded and recorded"}

b = StateGraph(RefundState)
b.add_node("lookup", lookup); b.add_node("refund", refund_and_record)
b.add_edge(START, "lookup"); b.add_edge("lookup", "refund"); b.add_edge("refund", END)
pay = b.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "pay-1"}}
try:
    pay.invoke({"msg": "refund"}, c)
except ConnectionError:
    pass
LEDGER["up"] = True
pay.invoke(None, c)
print("money sent for:", CHARGES)

What it printed:

money sent for: ['A-1077', 'A-1077']

Explain exactly why the money was sent twice, and redesign the nodes. (Solution D1.)

Make it your own

Use update_state to replay the refund of Idea 4 with a different amount, then print the thread's history and point out the two branches. (Solution M1.)

Solutions

SolutionP1 · The failed node runs again, from its start

refund and the fourth node. The last checkpoint was saved after lookup, so the resume starts at refund, from the beginning of the node; LangGraph cannot resume halfway through a function. Anything refund did before the crash, it does again, which is the problem in the debugging exercise.

SolutionB1 · Nothing was saved

Without a checkpointer, the state lives only during the run and is gone when invoke returns, so there is no thread to look up, and LangGraph raises ValueError: No checkpointer set. You also lose resume, approvals and time travel. Any graph that must survive a restart, pause, or be debugged later needs a checkpointer.

SolutionD1 · A node is the unit of retry

The money was sent, then the same node failed on the ledger. The last checkpoint was before the node, so the resume ran the whole node again and sent the money a second time. Two fixes, best together: put each side effect in its own node, so a later failure does not repeat it, and make the side effect itself idempotent with a key the payment provider checks (Lesson 3.4).

CHARGES.clear(); LEDGER["up"] = False
SENT = set()

def send_refund(state):
    key = f"refund:{state['order']['id']}"                      # an idempotency key (Lesson 3.4)
    if key not in SENT:                                         # the payment provider checks this in real life
        SENT.add(key); CHARGES.append(state["order"]["id"])
    return {}

def record(state):
    if not LEDGER["up"]:
        raise ConnectionError("ledger unavailable")
    return {"done": "refunded and recorded"}

b = StateGraph(RefundState)
b.add_node("lookup", lookup); b.add_node("send_refund", send_refund); b.add_node("record", record)
b.add_edge(START, "lookup"); b.add_edge("lookup", "send_refund"); b.add_edge("send_refund", "record"); b.add_edge("record", END)
pay = b.compile(checkpointer=InMemorySaver())
c = {"configurable": {"thread_id": "pay-2"}}
try:
    pay.invoke({"msg": "refund"}, c)
except ConnectionError:
    pass
LEDGER["up"] = True
print(pay.invoke(None, c)["done"], "| money sent for:", CHARGES)

refunded and recorded | money sent for: ['A-1077']

Durable execution makes resuming easy; it does not make side effects safe. That part is always the node's job.

SolutionM1 · Fork and inspect

Call graph.update_state(before_refund.config, {"order": {"id": "A-1077", "amount": 2999}}), invoke with the returned config, then print get_state_history(cfg). You will see two checkpoints with next ('refund',) at step 2 and two final checkpoints, one with INR 7,999 and one with the new amount; each checkpoint's parent_config shows which checkpoint it came from. The original run is untouched, which is what makes forking safe for investigation.

Check your understanding

Explain the mechanismWhat does a LangGraph checkpointer do, and what does it enable?

Worked answer. After every step, it saves the graph's state, the next nodes to run, pending writes and metadata, keyed by thread ID. That enables conversation memory across calls, resuming after a failure or restart from the last completed step, pausing for human input and resuming later, inspecting the state at every step of a past run, and forking from an earlier checkpoint to replay with changes. In production it is backed by a database such as Postgres.

A plausible wrong answer. "It caches model calls." It saves the graph's state; caching model responses is a separate feature.

Follow-ups. What should never be put in checkpointed state?

Debug a failureAfter a resume, a customer got two confirmation emails. What happened, and how do you prevent it?

Worked answer. The email was sent inside a node that then failed, or was interrupted, before the node finished. A resume reruns the whole node, so the email went out again. Prevent it by putting each external side effect in its own node at the end of what it depends on, by making side effects idempotent with a key the receiving system checks, and by recording "sent" in state immediately after the side effect. Then test the failure by making the step after the side effect fail.

A plausible wrong answer. "LangGraph replayed the whole run." Only the unfinished node was rerun; the node design caused the duplicate.

Follow-ups. How would you handle a side effect that cannot be made idempotent?

Defend a designDurable execution in LangGraph checkpoints, or a workflow engine such as Temporal?

Worked answer. LangGraph's checkpoints when the durability needed is the agent's own: conversation state, pauses for approval, resume after a crash, replay for debugging, all inside one graph. A workflow engine when the process spans many services, needs retries with timers over days, strict exactly-once activity semantics and mature operational tooling, or the organization already runs one; the agent can then run as an activity inside it (Lesson 12.8). They also combine: a Temporal workflow that calls a LangGraph agent per step.

A plausible wrong answer. "Checkpoints make LangGraph exactly-once." They make progress durable; side effects can still repeat unless nodes are idempotent.

Follow-ups. Where would the approval wait live in each design?
