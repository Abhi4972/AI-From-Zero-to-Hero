The problem

In plain words first

RLHF needs a separate reward model and a fragile reinforcement-learning loop. DPO (direct preference optimisation) gets to the same goal with an ordinary training loss: for each pair of answers where people preferred one, nudge the model so that, compared with the frozen starting model, the preferred answer becomes relatively more likely than the rejected one. The maths behind it shows that the model's own probabilities, divided by the starting model's, act as a hidden reward model, so no separate one is needed. This lesson runs the lesson's DPO code, computes exactly how the DPO loss weights each pair and why both answers can become less likely while the loss improves, and measures a real DPO-trained model's implicit reward on human preference data. No model is trained.

You built an RLHF pipeline in Lesson 07. Three stages. Three models. The SFT model, the reward model, and the policy model optimized with PPO. The reward model alone required thousands of human preference pairs and a separate training loop. PPO required careful tuning of the KL coefficient, learning rate, clip ratio, and number of epochs.

In practice, PPO training is notoriously unstable. Small hyperparameter changes cause the training to diverge. The reward model is an imperfect proxy for human preferences, and the policy finds ways to exploit its weaknesses. The KL penalty helps but requires its own tuning -- too low and you get reward hacking, too high and the model barely learns.

This complexity is why most open-source models struggled with RLHF for years after InstructGPT was published. The three-stage pipeline is fragile. Each stage has its own failure modes, and errors compound.

In May 2023, Rafael Rafailov, Archit Sharma, and colleagues at Stanford published "Direct Preference Optimization: Your Language Model is Secretly a Reward Model." The key insight: you don't need a separate reward model. The optimal reward function is mathematically determined by the language model's own token probabilities. You can skip the reward model entirely and optimize the language model directly on preference pairs.

DPO reduces RLHF to a single supervised learning step. One model. One loss function. One training loop. No reinforcement learning. Zephyr-7B, one of the first models to use DPO at scale, matched or beat models trained with full RLHF on several benchmarks. Meta used DPO, rather than PPO, for Llama 3's preference stage.

Idea 1 · The Key Insight

RLHF optimizes this objective:

maximize:E[R(x,y)]−β⋅KL(π∥πref​)

where R is the reward model, π is the policy, πref​ is the reference model, and β is the KL coefficient.

The DPO paper showed that this objective has a closed-form optimal solution. For any reward function R, the optimal policy is:

π∗(y∣x)=πref​(y∣x)⋅exp(R(x,y)/β)/Z(x)

where Z(x) is a normalizing constant. Rearranging:

R(x,y)=βlogπref​(y∣x)π∗(y∣x)​+βlogZ(x)

This is the breakthrough. The reward is expressed entirely in terms of the policy model's probabilities and the reference model's probabilities. You don't need to train a separate reward model. The reward is implicit in the probability ratio.

Substituting this into the Bradley-Terry preference model:

P(yw​>yl​∣x)​=sigmoid(R(x,yw​)−R(x,yl​))=sigmoid(β(logπref​(yw​∣x)π(yw​∣x)​−logπref​(yl​∣x)π(yl​∣x)​))​

The Z(x) terms cancel because both responses condition on the same prompt x. What's left is a function of only the policy model's log-probabilities and the reference model's log-probabilities on the preferred and rejected responses.

Idea 2 · The DPO Loss

LDPO​=−logsigmoid(β(logπref​(yw​∣x)π(yw​∣x)​−logπref​(yl​∣x)π(yl​∣x)​))

Let's unpack each piece:

  • yw​ = preferred (winning) response
  • yl​ = rejected (losing) response
  • x = prompt
  • π = current model (being trained)
  • πref​ = reference model (frozen SFT checkpoint)
  • β = temperature parameter controlling deviation from reference (typically 0.1 to 0.5)

The ratio log pi(y|x) / pi_ref(y|x) is the log-probability ratio. When this ratio is positive, the current model assigns higher probability to response y than the reference does. When negative, the current model assigns lower probability.

The DPO loss pushes the model to increase the log-probability ratio for preferred responses and decrease it for rejected responses. The beta parameter controls how aggressively the model can deviate from the reference -- small beta means large deviations are allowed, large beta keeps the model close to the reference.

Idea 3 · Why DPO is Simpler

DPO needs two models in memory during training -- the current model and the frozen reference. RLHF needs three or four: the policy, the reference, the reward model, and optionally a value function baseline. For a 70B model, each copy takes 140GB in FP16. The memory savings from eliminating the reward model are substantial.

Idea 4 · When DPO Beats RLHF

Small datasets. With 5,000-20,000 preference pairs, DPO often matches or exceeds RLHF. The reward model in RLHF needs enough data to generalize -- with limited data, it overfits and produces unreliable reward signals. DPO bypasses this problem by not needing a reward model at all.

Limited compute. DPO requires roughly one-third the compute of full RLHF (one training loop instead of three). For teams without large GPU clusters, this is the practical choice.

Rapid iteration. Want to try 10 different preference datasets to see which produces the best model? DPO lets you run each experiment in hours. RLHF requires retraining the reward model for each dataset.

Idea 5 · When RLHF Beats DPO

Large-scale training. At the scale of GPT-4 or Claude, RLHF's separate reward model can capture more nuanced preference signals. The reward model acts as a learned loss function that adapts to complex quality criteria.

Complex reward signals. When "better" involves multiple dimensions (helpfulness, harmlessness, honesty), a reward model can learn this multi-objective tradeoff. DPO treats each preference pair as a binary signal -- one is better, one is worse -- without modeling why.

Iterative alignment. RLHF pipelines can generate new responses with the current policy, have humans rate them, and retrain the reward model in an online loop. DPO works on a fixed dataset of preference pairs. Constitutional AI (Anthropic's approach) uses this iterative property of RLHF extensively.

Idea 6 · Beyond DPO: KTO, ORPO, SimPO

DPO inspired a family of simplified alignment methods.

KTO (Kahneman-Tversky Optimization, 2024): You don't even need pairs. KTO works with unpaired feedback -- just label each response as "good" or "bad" without comparing it to an alternative. This dramatically simplifies data collection. Instead of showing annotators two responses and asking "which is better?", you show one response and ask "is this good?" The loss function applies loss aversion from prospect theory: bad responses are penalized more than good responses are rewarded.

ORPO (Odds Ratio Preference Optimization, 2024): Combines SFT and alignment in a single training step. Instead of first doing SFT then DPO, ORPO modifies the SFT loss to include a preference signal. The loss has two terms: a standard next-token prediction loss on preferred responses, plus an odds ratio term that increases the gap between preferred and rejected response probabilities. One training loop instead of two.

SimPO (Simple Preference Optimization, 2024): Eliminates the reference model entirely. Instead of computing log-probability ratios against a frozen reference, SimPO uses the average log-probability of the response (normalized by length) as the implicit reward. This saves memory (no reference model needed) and simplifies training. The length normalization prevents the model from favoring shorter responses.

The trend is clear: each method eliminates one more piece of complexity. RLHF needed a reward model and PPO. DPO eliminated both. KTO eliminated paired data. ORPO eliminated the separate SFT stage. SimPO eliminated the reference model. The alignment tax -- the compute and complexity cost of going from a base model to an aligned model -- keeps dropping.

Idea 7 · Real DPO Deployments

Zephyr-7B (HuggingFace, October 2023): Mistral 7B base, SFT on UltraChat (200K examples), then DPO on UltraFeedback (60K preference pairs). Zephyr-7B-β scored 7.34 on MT-Bench, the highest 7B chat model at the time and above Llama 2 Chat 70B's 6.86, a model ten times its size trained with full RLHF.

Llama 3 (Meta, 2024): Post-training ran several rounds of SFT, rejection sampling with a reward model, and DPO; the reward model chose the data, DPO did the preference training, and no PPO was used.

Tülu 3 (Allen AI, November 2024): SFT, then DPO on about 270,000 preference pairs (many generated and judged by models), then RL with verifiable rewards, all with open data and code.

The same idea as a formula

Starting from the KL-regularised RLHF objective (Lesson 9.9), the optimal policy satisfies r(x,y)=βlogπref​(y∣x)π∗(y∣x)​+βlogZ(x). Plugging this implicit reward into Bradley–Terry cancels Z(x) and gives

LDPO​=−logσ(βh),h=logπref​(yw​)πθ​(yw​)​−logπref​(yl​)πθ​(yl​)​

with all probabilities conditioned on the prompt x and each logπ(y) the sum of the reply's token log-probabilities.

Gradient. ∇θ​L=−βσ(−βh)[∇logπθ​(yw​)−∇logπθ​(yl​)]: each pair is weighted by σ(−βh), close to 1 when the model still prefers the wrong answer and close to 0 once it clearly prefers the right one.

What it does not constrain. Only the difference h appears: the loss can fall while logπθ​(yw​) decreases, as long as logπθ​(yl​) decreases faster.

Variants. IPO replaces −logσ with a squared loss toward a fixed margin; SimPO drops πref​ and uses length-normalised log-probabilities with a target margin; KTO uses unpaired good/bad labels.

Worked example
A DPO step by hand

A pair with summed log-probabilities (policy, then reference): chosen −40.0 and −42.0; rejected −35.0 and −36.0. β=0.1.

  • Log-ratios: chosen −40.0−(−42.0)=+2.0; rejected −35.0−(−36.0)=+1.0.
  • h=2.0−1.0=1.0; βh=0.1.
  • Loss =−logσ(0.1)=−log0.525=0.644; gradient weight σ(−0.1)=0.475.
  • The implicit rewards are β×2.0=0.2 and β×1.0=0.1: the model "prefers" the chosen reply by 0.1 reward units.

Note that the rejected reply is more likely than the chosen one in absolute terms (−35 against −40): it is shorter. DPO only cares about the change relative to the reference.

Larger β. With β=0.5 the same pair gives βh=0.5, loss 0.474; the same change in log-probabilities counts five times as much, so training stops sooner and stays closer to the reference.

Step 2 · Sequence Log-Probability

The DPO loss requires computing the total log-probability of a response given a prompt. This means running the model on the full (prompt + response) sequence and summing the log-probabilities of each response token.

def tokenize_sequence(text, vocab_size=256):
    return [min(t, vocab_size - 1) for t in list(text.encode("utf-8"))]


def compute_sequence_log_prob(model, prompt_tokens, response_tokens, max_seq_len=128):
    full_sequence = prompt_tokens + response_tokens
    if len(full_sequence) > max_seq_len:
        full_sequence = full_sequence[:max_seq_len]

    if len(full_sequence) < 2:
        return 0.0

    input_ids = np.array(full_sequence[:-1]).reshape(1, -1)
    target_ids = np.array(full_sequence[1:])

    logits = model.forward(input_ids)
    logits = logits[0]

    max_logits = logits.max(axis=-1, keepdims=True)
    log_probs = logits - max_logits - np.log(
        np.exp(logits - max_logits).sum(axis=-1, keepdims=True)
    )

    prompt_len = len(prompt_tokens)
    response_start = max(0, prompt_len - 1)
    response_end = len(target_ids)

    if response_start >= response_end:
        return 0.0

    response_log_probs = log_probs[response_start:response_end, :]
    response_targets = target_ids[response_start:response_end]

    total_log_prob = 0.0
    for i, target in enumerate(response_targets):
        total_log_prob += response_log_probs[i, target]

    return total_log_prob

This function is the workhorse of DPO. For each preference pair, it runs four times: model on preferred response, model on rejected response, reference on preferred response, reference on rejected response. That's 4 forward passes per training example versus RLHF's generation + reward scoring + value estimation + PPO update. Simpler, faster, more stable.

Step 3 · The DPO Loss

The core of the paper in code. One function. One loss. No reward model.

def sigmoid(x):
    return np.where(
        x >= 0,
        1.0 / (1.0 + np.exp(-x)),
        np.exp(x) / (1.0 + np.exp(x))
    )


def dpo_loss(policy_logprob_preferred, policy_logprob_rejected,
             ref_logprob_preferred, ref_logprob_rejected, beta=0.1):
    preferred_ratio = policy_logprob_preferred - ref_logprob_preferred
    rejected_ratio = policy_logprob_rejected - ref_logprob_rejected

    logit = beta * (preferred_ratio - rejected_ratio)

    loss = -np.log(sigmoid(logit) + 1e-8)

    preferred_reward = beta * preferred_ratio
    rejected_reward = beta * rejected_ratio

    return loss, {
        "preferred_ratio": float(preferred_ratio),
        "rejected_ratio": float(rejected_ratio),
        "logit": float(logit),
        "implicit_preferred_reward": float(preferred_reward),
        "implicit_rejected_reward": float(rejected_reward),
        "reward_margin": float(preferred_reward - rejected_reward),
    }

The preferred_ratio and rejected_ratio are the log-probability ratios from the DPO derivation. When the current model assigns higher probability to the preferred response (relative to the reference) and lower probability to the rejected response, the logit is positive and the loss is low. The training signal pushes the model in exactly this direction.

The implicit_preferred_reward and implicit_rejected_reward are the rewards that the DPO loss implicitly assigns. You can extract them to verify that training is working -- the margin between preferred and rejected rewards should increase over training.

Step 4 · DPO Training Loop

A standard supervised training loop. No PPO. No reward model. Just forward passes and gradient updates.

def copy_model_weights(source, target):
    target.embedding.token_embed = source.embedding.token_embed.copy()
    target.embedding.pos_embed = source.embedding.pos_embed.copy()
    target.ln_f.gamma = source.ln_f.gamma.copy()
    target.ln_f.beta = source.ln_f.beta.copy()
    for s_block, t_block in zip(source.blocks, target.blocks):
        t_block.attn.W_q = s_block.attn.W_q.copy()
        t_block.attn.W_k = s_block.attn.W_k.copy()
        t_block.attn.W_v = s_block.attn.W_v.copy()
        t_block.attn.W_out = s_block.attn.W_out.copy()
        t_block.ffn.W1 = s_block.ffn.W1.copy()
        t_block.ffn.W2 = s_block.ffn.W2.copy()
        t_block.ffn.b1 = s_block.ffn.b1.copy()
        t_block.ffn.b2 = s_block.ffn.b2.copy()
        t_block.ln1.gamma = s_block.ln1.gamma.copy()
        t_block.ln1.beta = s_block.ln1.beta.copy()
        t_block.ln2.gamma = s_block.ln2.gamma.copy()
        t_block.ln2.beta = s_block.ln2.beta.copy()


def dpo_train(policy_model, reference_model, preference_data,
              num_epochs=5, lr=5e-6, beta=0.1, max_seq_len=128):
    print(f"DPO Training: {len(preference_data)} pairs, {num_epochs} epochs, "
          f"lr={lr}, beta={beta}")
    print()

    losses = []
    margins = []

    for epoch in range(num_epochs):
        epoch_loss = 0.0
        epoch_margin = 0.0
        num_examples = 0

        indices = np.random.permutation(len(preference_data))

        for idx in indices:
            pair = preference_data[idx]

            prompt_tokens = tokenize_sequence(pair["prompt"])
            preferred_tokens = tokenize_sequence(pair["preferred"])
            rejected_tokens = tokenize_sequence(pair["rejected"])

            pi_logprob_w = compute_sequence_log_prob(
                policy_model, prompt_tokens, preferred_tokens, max_seq_len
            )
            pi_logprob_l = compute_sequence_log_prob(
                policy_model, prompt_tokens, rejected_tokens, max_seq_len
            )
            ref_logprob_w = compute_sequence_log_prob(
                reference_model, prompt_tokens, preferred_tokens, max_seq_len
            )
            ref_logprob_l = compute_sequence_log_prob(
                reference_model, prompt_tokens, rejected_tokens, max_seq_len
            )

            loss, metrics = dpo_loss(
                pi_logprob_w, pi_logprob_l,
                ref_logprob_w, ref_logprob_l, beta
            )

            update_direction = 1.0 if metrics["logit"] < 0 else -0.1
            for block in policy_model.blocks:
                block.ffn.W1 += lr * update_direction * np.random.randn(*block.ffn.W1.shape) * 0.01
                block.ffn.W2 += lr * update_direction * np.random.randn(*block.ffn.W2.shape) * 0.01

            epoch_loss += loss
            epoch_margin += metrics["reward_margin"]
            num_examples += 1
            losses.append(float(loss))
            margins.append(metrics["reward_margin"])

        avg_loss = epoch_loss / max(num_examples, 1)
        avg_margin = epoch_margin / max(num_examples, 1)

        print(f"  Epoch {epoch + 1}/{num_epochs} | Loss: {avg_loss:.4f} | "
              f"Avg Margin: {avg_margin:.4f}")

    return policy_model, losses, margins

The training loop is refreshingly simple compared to RLHF. For each preference pair: compute four log-probabilities (two models, two responses), plug them into the DPO loss, compute the gradient, update the policy. No generation step. No reward model inference. No advantage estimation. No clipping.

Step 5 · Compare DPO vs RLHF

Measure the implicit reward margins and log-probability shifts to compare DPO against the RLHF model from Lesson 07.

def evaluate_preference_accuracy(model, reference_model, preference_data, beta=0.1, max_seq_len=128):
    correct = 0
    total = 0

    for pair in preference_data:
        prompt_tokens = tokenize_sequence(pair["prompt"])
        preferred_tokens = tokenize_sequence(pair["preferred"])
        rejected_tokens = tokenize_sequence(pair["rejected"])

        pi_w = compute_sequence_log_prob(model, prompt_tokens, preferred_tokens, max_seq_len)
        pi_l = compute_sequence_log_prob(model, prompt_tokens, rejected_tokens, max_seq_len)
        ref_w = compute_sequence_log_prob(reference_model, prompt_tokens, preferred_tokens, max_seq_len)
        ref_l = compute_sequence_log_prob(reference_model, prompt_tokens, rejected_tokens, max_seq_len)

        preferred_reward = beta * (pi_w - ref_w)
        rejected_reward = beta * (pi_l - ref_l)

        if preferred_reward > rejected_reward:
            correct += 1
        total += 1

    return correct / max(total, 1)

Direct preference optimization (DPO) trains a language model on pairs of responses. A person preferred one response of each pair and rejected the other. DPO needs no separate reward model. The log probability ratio between the policy and a frozen reference model acts as the reward.

Task

Write three functions. Each input holds one sequence log probability for each pair in a batch of N pairs.

  1. implicit_reward(policy_logprob, ref_logprob, beta) returns the implicit reward r=β(logπ(y∣x)−logπref​(y∣x)) for each pair.
  2. dpo_loss(...) returns the mean DPO loss over the batch.
  3. dpo_grad(...) returns the gradient of that mean loss with respect to the two policy log probabilities.

Let rw​ be the implicit reward of the preferred response and rl​ the implicit reward of the rejected response. The margin of pair i is zi​=rw,i​−rl,i​. The loss is

L=N1​i=1∑N​−logσ(zi​),σ(z)=1+e−z1​.

The gradient of L with respect to the preferred policy log probability of pair i is −βσ(−zi​)/N. The gradient with respect to the rejected policy log probability is +βσ(−zi​)/N. The reference log probabilities are constants.

Input and output

All four log probability arguments have the same order of names in dpo_loss and dpo_grad: policy_logprob_preferred, policy_logprob_rejected, ref_logprob_preferred, ref_logprob_rejected.

Name Type Shape Meaning
policy_logprob float array (N,) log probability of a response under the policy
ref_logprob float array (N,) log probability of the same response under the reference
policy_logprob_preferred float array (N,) policy log probability of each preferred response
policy_logprob_rejected float array (N,) policy log probability of each rejected response
ref_logprob_preferred float array (N,) reference log probability of each preferred response
ref_logprob_rejected float array (N,) reference log probability of each rejected response
beta float the strength of the reference constraint, above 0
  • implicit_reward returns a float array of shape (N,).
  • dpo_loss returns a Python float.
  • dpo_grad returns a tuple (grad_preferred, grad_rejected) of two float arrays of shape (N,).

Constraints

  • 1 <= N <= 1000 and 0 < beta <= 10.
  • A log probability can be as small as -5000. The margin can be as large as several thousand in either direction. The loss and the gradient must stay finite and exact.
  • Do not add a small constant inside a log. Use a stable form of −logσ(z).
  • Do not change the input arrays.
  • Use numpy only.

Your code
Common mistakes the checks catch
  • Multiplies the margin by beta a second time, so the loss uses beta squared.
  • Computes the loss as minus log of sigmoid plus 1e-8, so very large margins give wrong losses.
  • Weights the gradient by sigmoid of the margin, not sigmoid of minus the margin.
  • Subtracts the reference log probabilities in place, so the caller's policy array changes.
  • Sums the pair losses and gradients and does not divide by N.
  • Computes the reward as the reference log probability minus the policy log probability.
Hint 1

Compute the two implicit rewards first. The margin of each pair is the preferred reward minus the rejected reward.

Hint 2

−logσ(z)=log(1+e−z). The numpy function np.logaddexp(0.0, -z) computes this value without overflow for any z.

Hint 3

The derivative of log(1+e−z) with respect to z is −σ(−z). The margin changes by β when the preferred policy log probability changes by 1, and by −β for the rejected one. Divide by N because the loss is a mean.

Hint 4

For a stable sigmoid, use σ(x)=exp(−log(1+e−x)), which is np.exp(-np.logaddexp(0.0, -x)).

import numpy as np


def sigmoid(x):
    return np.exp(-np.logaddexp(0.0, -x))


def implicit_reward(policy_logprob, ref_logprob, beta=0.1):
    return beta * (np.asarray(policy_logprob, dtype=float) - np.asarray(ref_logprob, dtype=float))


def dpo_logits(policy_logprob_preferred, policy_logprob_rejected, ref_logprob_preferred, ref_logprob_rejected, beta=0.1):
    preferred_reward = implicit_reward(policy_logprob_preferred, ref_logprob_preferred, beta)
    rejected_reward = implicit_reward(policy_logprob_rejected, ref_logprob_rejected, beta)
    return preferred_reward - rejected_reward


def dpo_loss(policy_logprob_preferred, policy_logprob_rejected, ref_logprob_preferred, ref_logprob_rejected, beta=0.1):
    logit = dpo_logits(policy_logprob_preferred, policy_logprob_rejected, ref_logprob_preferred, ref_logprob_rejected, beta)
    return float(np.mean(np.logaddexp(0.0, -logit)))


def dpo_grad(policy_logprob_preferred, policy_logprob_rejected, ref_logprob_preferred, ref_logprob_rejected, beta=0.1):
    logit = dpo_logits(policy_logprob_preferred, policy_logprob_rejected, ref_logprob_preferred, ref_logprob_rejected, beta)
    weight = sigmoid(-logit) * beta / logit.size
    return -weight, weight

Why the policy is a reward model

The objective of RLHF has a closed form optimum: π∗(y∣x)∝πref​(y∣x)exp(r(x,y)/β). Solve it for r and you get r=βlog(π∗/πref​) plus a term that depends only on the prompt. The preference model of Bradley and Terry uses only the difference of two rewards for the same prompt, so that term cancels. The result is a loss on the policy alone.

What the gradient does

The gradient pushes up the preferred log probability and pushes down the rejected one. The weight is σ(−z)=σ(rl​−rw​). A pair that the model already ranks well gets a small weight. A pair that the model ranks wrong gets a weight near 1. The paper shows that this weight is what keeps DPO stable. Without it, the model loses quality.

The numerical trap

The lesson adds 1e-8 inside the log. That caps the loss of a very wrong pair at about 18.4 and makes the loss of a very good pair about 1e-8, not 0. np.logaddexp gives the exact value in both directions.

The role of beta

A small β lets the policy move far from the reference before the loss saturates. A large β makes the loss sensitive to small changes in the log ratio. The lesson measures this in its beta sensitivity analysis.

## Method-Specific Configuration

### SFT

- **When to stop**: After 1-3 epochs or when validation loss stops decreasing
- **Key hyperparameter**: Learning rate (1e-5 to 5e-5, lower for bigger models)
- **Critical detail**: Mask instruction tokens in the loss
- **Gotcha**: More than 3 epochs causes memorization; mix in 2-5% pre-training data

### RLHF (PPO)

- **When to use**: You have 20K+ comparison pairs, need multi-objective alignment, or want iterative online learning
- **Key hyperparameters**: KL coefficient (0.01-0.05), PPO clip ratio (0.1-0.3), learning rate (5e-6 to 3e-5)
- **Critical detail**: Reward model should be >= policy model size
- **Gotcha**: PPO is unstable; monitor KL divergence and reward curves continuously

### DPO

- **When to use**: You have preference pairs and want a simpler pipeline than RLHF
- **Key hyperparameter**: Beta (0.1-0.5; lower = more deviation from reference allowed)
- **Critical detail**: Reference model must be a frozen copy of the SFT checkpoint
- **Gotcha**: Very sensitive to beta; run a sweep over [0.05, 0.1, 0.2, 0.5]

### KTO

- **When to use**: You only have "good" or "bad" labels without pairwise comparisons
- **Key hyperparameter**: Beta (same as DPO), loss aversion multiplier (1.5x on bad responses)
- **Critical detail**: Needs roughly balanced good/bad examples (40-60% split)
- **Gotcha**: Without pairs, the gradient signal is weaker; may need more data than DPO

### ORPO

- **When to use**: You want to skip SFT entirely and go straight from base to aligned
- **Key hyperparameter**: Lambda (weight of the preference term vs SFT term)
- **Critical detail**: Needs both instruction labels AND preference pairs in one dataset
- **Gotcha**: Combined objective can be hard to balance; if SFT loss dominates, alignment is weak

### SimPO

- **When to use**: Memory-constrained setup where you can't hold a reference model
- **Key hyperparameter**: Beta, gamma (length normalization exponent)
- **Critical detail**: Length normalization prevents the model from favoring short responses
- **Gotcha**: Without a reference model anchor, the model can drift further; monitor carefully

## Evaluation Protocol

After alignment, evaluate across these dimensions:

1. **Preference win rate**: Compare aligned model vs SFT model on 200+ test prompts with human judges. Target: > 60% win rate.
2. **Benchmark retention**: MMLU, HumanEval, or domain-specific benchmarks. Should not drop > 5% from SFT baseline.
3. **MT-Bench or AlpacaEval**: Standard alignment quality benchmarks. Compare against published baselines.
4. **Safety evaluation**: Test against adversarial prompts, jailbreaks, and harmful request categories.
5. **Response diversity**: Measure entropy of responses across 100 prompts. Low entropy = mode collapse.

| Symptom | Cause | Method-Specific Fix |
|---------|-------|-------------------|
| Verbose, padded responses | Reward model / implicit reward favors length | DPO: increase beta. RLHF: add length penalty. SimPO: adjust gamma. |
| Model agrees with everything | Sycophancy from preference data bias | Add preference pairs where the correct response disagrees with the user |

Debug a failureDuring a DPO run the loss falls and the reward margin that the trainer logs grows every epoch. Yet the model's samples get shorter and less fluent, and the policy now gives the chosen training answers a lower probability than they had under the reference. Explain the mechanism and what you change.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The DPO loss cares only about the difference of two log ratios. It can lower the probability of the chosen answer as long as the rejected answer falls faster, and the margin still grows. This is the degraded chosen response failure: the policy moves probability mass away from both training answers, often toward short degenerate outputs. Log the absolute chosen log-probability, add a penalty on downward moves of the chosen term as the behavior-preserving variant does or switch to a loss with a bounded margin, and keep a generation eval next to the margin.

Why the margin can lie.

The DPO gradient pushes the chosen log ratio up and the rejected log ratio down, but only their difference enters the loss. If the rejected answers are easy to suppress, the cheapest way to grow the margin is to suppress them hard while the chosen answers drift down too. The implicit reward gap is also unbounded: a weak preference can produce an arbitrarily large gap. Nothing in the loss asks the policy to keep generating the chosen answers.

What you log.

  • The absolute chosen log-probability under the policy, per epoch, next to the margin. The capstone's margin function reports the difference; add the chosen term alone.
  • Sample lengths and a small generation eval. A margin that grows while samples degrade is the signature.
  • The KL to the reference. The move away from both answers shows up as a growing distance.

The fixes.

  1. A penalty on downward moves of the chosen log-probability. The behavior-preserving variant of the family adds that one correction and reports a gain over plain DPO on reasoning tasks.
  2. A bounded margin. The identity-mapping variant replaces the log sigmoid with a squared error on a target of one over two beta, so the gap and the preference strength stay proportional.
  3. A conservative beta and early stopping, chosen against a generation eval, not against the training margin.
  4. Better pairs. Pairs where both answers are rare under the reference produce arbitrary implicit rewards; filter them.

Why this is still over-optimization.

Direct alignment methods remove the explicit reward model, not the proxy. The quantity they optimize is a ratio against the reference, and that ratio can be pushed to places the preference data never covered. The same peak-and-collapse curve that reward models show appears here across KL budgets.

Plausible wrong answers.

  • "The margin grows, so training works; the samples are a decoding problem." The margin can grow while both answers lose probability; the generation eval is the objective, not the margin.
  • "Raise beta until the samples recover." A higher beta slows the drift but does not change the direction of the gradient on the chosen term; the penalty on that term does.
  • "Train more epochs; the chosen probability will come back." The loss has no term that rewards a higher chosen probability on its own, so more epochs push further the same way.

Follow-ups an interviewer may ask.

  • (level 3) How does a reference-free, length-normalized loss change the picture? Expected: it scores the average log-probability per token with a margin, which removes the length bias and the reference, but it also removes the anchor, so drift needs its own guard.
  • (level 4) Which variant do you pick when preference strengths vary widely across pairs? Expected: the bounded one; it keeps the gap proportional to the preference, so strong pairs do not saturate the loss and weak pairs do not blow up.
  • (level 4) Does a lower beta help here? Expected: no; a lower beta lets the policy move further from the reference for the same margin, which makes the degradation worse.

Explain the mechanismDPO is often described as RLHF without a reward model. Walk me through where the reward went. Start from the RLHF objective with its KL term and end at the loss you would implement.

Level 2 of 4 · about 12 minutes to answer well.

Short answer. The penalized objective has a closed-form optimum: the optimal policy equals the reference policy times the exponential of reward over beta, normalized per prompt. Invert it and the reward equals beta times the log ratio of policy to reference, plus a term that depends on the prompt alone. Put that reward into the Bradley-Terry preference probability and the prompt-only term cancels, because both answers share the prompt. What is left is a loss in the policy's own log-probabilities: minus the log sigmoid of beta times the difference of the two log ratios.

The derivation in four lines.

optimum:  pi*(y|x) = pi_ref(y|x) * exp( r(x,y) / beta ) / Z(x)
invert:   r(x,y) = beta * log( pi*(y|x) / pi_ref(y|x) ) + beta * log Z(x)
BT:       P(y_w > y_l | x) = sigmoid( r(x,y_w) - r(x,y_l) )
loss:     -log sigmoid( beta * [ log pi(y_w|x)/pi_ref(y_w|x) - log pi(y_l|x)/pi_ref(y_l|x) ] )

The log Z term depends on the prompt alone, so it is the same for the chosen and the rejected answer and drops out of the difference.

What you compute per pair.

Four sequence log-probabilities: the policy and the reference on the chosen answer, and both on the rejected answer. Each is the sum of next-token log-probabilities over the answer tokens only, with the prompt positions masked. The reference runs under no gradient.

The implicit reward.

beta * (log pi(y|x) - log pi_ref(y|x)) is the reward that DPO assigns to an answer. Log the margin between the chosen and the rejected implicit rewards; it should grow during training. The gradient on the chosen log-probability is -beta * (1 - sigmoid(z)), negative for every z, so training pushes the chosen answer up and the rejected answer down.

Where the KL went.

No KL term appears in the loss. The constraint is structural: a large move from the reference makes the log ratio large, the sigmoid saturates, and the gradient fades. Beta sets how far the policy may move. The DPO lesson gives 0.1 to 0.5 as the range and 0.1 to 0.3 as the usual sweet spot. A small beta allows large moves and risks degenerate answers; a value near 1.0 pins the policy to the reference.

What it saves.

Two models in memory instead of three or four, and one supervised loop instead of PPO. For a 70B model each copy takes 140GB in FP16, so the reward model you never load is a large saving.

Plausible wrong answers.

  • "DPO has no reference model, that is the point." It removes the reward model and PPO; the frozen reference stays in the loss, and the methods that drop it are a later variant.
  • "DPO maximizes the probability of the chosen answer." It maximizes the margin of two log ratios; the chosen absolute probability can fall as long as the rejected falls faster.
  • "Beta is a learning rate." Beta scales the implicit reward and sets how far the policy may move from the reference; the optimizer step size is a separate setting.

Follow-ups an interviewer may ask.

  • (level 2) Why must the policy start as a copy of the reference? Expected: the derivation treats the optimum as the reference plus a learned shift, and a copy makes every implicit reward start at zero.
  • (level 2) What does a positive log ratio mean? Expected: the policy now gives that answer a higher probability than the reference does.
  • (level 3) Why does the derivation need both answers to share one prompt? Expected: the partition term depends on the prompt only; with different prompts it would not cancel, and the implicit rewards would not be comparable.
  • (level 4) Which assumptions of the derivation fail in practice? Expected: that the optimum is reachable, that the pairs are in-distribution for the reference, and that the reference is the true anchor; each later method in the family repairs one of them.

When DPO wins.

When the full stack wins.

  • Several quality dimensions at once, such as helpfulness, harmlessness and honesty. A reward model learns the trade-off; DPO sees each pair as one binary signal.
  • An online loop: sample from the current policy, rate, retrain the reward model, continue. DPO works on a fixed set.
  • A reward model you can reuse for best-of-N sampling or as a judge at decode time.
  • The largest scales, where a separate reward model has captured more nuance in published pipelines.

The practical path.

Start with DPO. Switch to the full stack when the eval plateaus. Several production pipelines run both: the full stack first for broad alignment, DPO after it for targeted refinement.

Read the code and find what is wrong. python policy = TinyGPT(config) reference = policy def sequence_log_prob(model, prompt_ids, completion_ids): ids = torch.cat([prompt_ids, completion_ids]) logits = model(ids[:-1].unsqueeze(0))[0] log_probs = logits.log_softmax(-1) targets = ids[1:] return log_probs[torch.arange(len(targets)), targets].sum() def dpo_loss(prompt, chosen, rejected, beta=0.1): pi_w = sequence_log_prob(policy, prompt, chosen) pi_l = sequence_log_prob(policy, prompt, rejected) ref_w = sequence_log_prob(reference, prompt, chosen) ref_l = sequence_log_prob(reference, prompt, rejected) z = beta * ((pi_l - ref_l) - (pi_w - ref_w)) return -torch.nn.functional.logsigmoid(z)

Level 2 of 4 · about 12 minutes to answer well.

Short answer. Three things. The reference is the same object as the policy, so both log ratios are zero by construction and the loss is a constant with no gradient; build the reference as a separate copy, freeze it, and run it under no gradient. The margin has the wrong sign, so once the aliasing is fixed the trainer promotes the rejected answer. The log-probability also sums over the prompt positions, which the capstone masks out.

Bug 1: the reference is the policy.

reference = policy binds a second name to one module. Every forward pass through reference uses the current policy weights, so pi_w - ref_w and pi_l - ref_l are exactly zero, and the loss is a constant. The optimizer sees a zero gradient. A deep copy alone is not enough either: the reference needs requires_grad=False on every parameter, its forward passes belong under torch.no_grad(), and the policy must start from the same weights, for example with policy.load_state_dict(reference.state_dict()).

Bug 2: the margin has the wrong sign.

The loss is minus the log sigmoid of beta times the chosen log ratio minus the rejected log ratio. The code subtracts in the other order. The gradient with respect to the chosen log-probability must be negative, so that raising it lowers the loss. With the reversed sign, the trainer lowers the chosen answer and raises the rejected one. A unit test that checks the gradient sign on one pair catches this.

Observation 3: the prompt is in the sum.

sequence_log_prob sums over every position, the prompt included. With one shared prompt, the prompt terms cancel in the margin, so the value is right. But the trainer computes and backpropagates through positions that carry no preference signal, and the cancellation breaks when a long sequence is cut at a maximum length. Start the sum at the first answer position, as the capstone does.

How to test the fix.

  • The loss on one pair falls when you raise the chosen log-probability by hand.
  • The reference log-probabilities are identical between epochs.
  • The mean chosen minus rejected margin under the policy grows over training.

Plausible wrong answers.

  • "Lower the learning rate; the loss is flat because the steps are too small." The gradient is exactly zero while the reference aliases the policy; no step size fixes that.
  • "The sign does not matter, the optimizer finds the direction." The sign decides which answer the trainer promotes; reversed, it trains the model to prefer the rejected answers.
  • "Replace the sum with a mean to stabilize the loss." That turns the objective into a length-normalized variant; it is a design choice, not the fix for a constant loss.

Follow-ups an interviewer may ask.

  • (level 2) After the fix, how do you confirm that the reference never moves? Expected: assert that no reference parameter requires a gradient, and compare its log-probabilities on a fixed pair before and after an epoch.
  • (level 3) Why does every pair start at the same loss before training? Expected: the policy equals the reference, so both log ratios are zero and the sigmoid sits at one half; the margin grows from there.
  • (level 3) The margin grows, but the generated answers get worse. What do you log next? Expected: the absolute chosen log-probability; DPO can push it down as long as the rejected falls faster.
  • (level 4) Would you keep the prompt positions if the two answers had different prompts? Expected: no, and the loss would be wrong anyway; the derivation needs one prompt per pair, because the partition term cancels only then.

The DPO derivation assumes paired data, an SFT reference that is the true anchor, in-distribution pairs, and a preference that maps to an unbounded log-odds. Each member of the family drops or repairs one of these.

The reasoning for each team.

  1. Clicks are plentiful and unpaired. Forcing them into pairs throws away most of the data; the unpaired loss uses every label.
  2. In plain DPO a long winner has a more negative log-probability by construction, so the gap grows for the wrong reason and the policy learns length. Normalizing by length removes the incentive. Without a reference, drift needs a guard of its own.
  3. The single-stage loss trains the base model to follow instructions and to prefer the chosen answer at once; the likelihood term keeps it anchored where DPO used the reference.
  4. In DPO a near coin-flip pair and a unanimous pair both push toward an unbounded gap. The bounded loss keeps the gap proportional to the preference strength.

What every team keeps.

A held-out eval with generation, early stopping, and a check on the absolute chosen log-probability. None of these losses escapes over-optimization; they move where it bites.

How to decide in practice.

Run the candidates on one battery and pick per task. The lesson's point is that the best loss for math reasoning has no reason to be the best loss for safety.

Plausible wrong answers.

  • "Convert the clicks into pairs by matching a good and a bad answer for the same prompt." It keeps only prompts with both labels and invents comparisons the raters never made; the unpaired loss uses the labels as they are.
  • "Truncate the long winners so that the pairs are balanced." That destroys the answers people preferred; the fix is in the loss normalization, not in the data.
  • "Use DPO everywhere and tune beta per team." Beta cannot create pairs, remove a reference, bound a gap or supply an SFT stage; each of those is a different loss.

Follow-ups an interviewer may ask.

  • (level 3) The clicks team also has a small paired set. Combine them? Expected: yes; train with the unpaired loss on the clicks and validate on the pairs, or weight the two losses; the pairs are the cleaner signal for the eval.
  • (level 3) Why does removing the reference save memory, and what does it cost? Expected: one model in memory instead of two; the cost is no anchor, so the policy can drift, and the margin term and early stopping carry that job.
  • (level 4) A team runs DPO and watches the probability of its chosen answers drop while the margin grows. Which row applies, and why is it not a tuning problem? Expected: the chosen-preserving variant; the gradient of plain DPO cares only about the difference, so no beta fixes the direction.
  • (level 4) How do you argue to a skeptic that these losses still over-optimize? Expected: the published curves of gold reward against KL for direct methods show the same peak and collapse as reward-model pipelines; the implicit reward queries out-of-distribution samples, and KL regularization does not stabilize it.

Check your understanding

Q1What is the main advantage of DPO over RLHF?

RLHF requires training a reward model separately, then running PPO optimization. DPO folds both steps into a single training objective that directly optimizes the language model on preference pairs.

Q2What role does the reference model play in DPO?

The DPO loss compares log probabilities under the trained policy and the reference (usually SFT) model. The reference model constrains how far the policy can drift, preventing reward hacking without explicit KL tuning.

Q3What does the beta parameter in DPO control?

Beta scales the implicit KL divergence penalty. Beta=0.1 allows the model to diverge significantly from the reference (potentially better but riskier). Beta=0.5 keeps it close (safer but less learning).

Q4How does DPO implicitly represent a reward model?

Rafailov et al. showed that the closed-form solution of the RLHF objective expresses the reward as a function of the policy's log-probabilities relative to the reference. DPO optimizes this directly, implicitly learning the reward.

Q5When might RLHF still be preferred over DPO?

DPO is offline (fixed preference data). RLHF allows online data collection where the reward model scores new generations, discovering reward-hacking patterns. A standalone reward model is also useful for evaluation and other policies.
