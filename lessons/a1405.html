In plain words first
The idea in one line

Self-Refine (Madaan et al., 2023) uses one LLM in three roles — generate, feedback, refine — in a loop. Average gain: +20 absolute on 7 tasks. CRITIC (Gou et al., 2023) hardens the feedback step by routing verification through external tools. In 2026 this pattern ships in every framework as "evaluator-optimizer" (Anthropic) or a guardrail loop (OpenAI Agents SDK).

Terms you'll hear
Term What people say What it actually means
Self-Refine "LLM that fixes itself" Generate -> feedback -> refine loop in one model, with history
CRITIC "Tool-grounded verification" Replace feedback with an external verifier (search, code, calc, tests)
Evaluator-Optimizer "Anthropic workflow pattern" Two roles — evaluator scores, optimizer revises — looped to convergence
Output guardrail "Post-hoc check" OpenAI Agents SDK validator that runs after an agent produces output
Verify step "Critique phase" The load-bearing decision: grounded or self-rated
Refine history "What the model already tried" Prior outputs + critiques prepended to refine prompt; drop and quality collapses
Rubber-stamp loop "Self-agreement failure" Same-prompt critique returns "looks good"; fix with structurally different prompts

The problem

In plain words first

A first draft is often almost right. Self-Refine asks the model to do what a careful person does: write an answer, read it back critically, and fix what it finds, repeating until the critic is satisfied. The catch is that the same model that made a mistake is often blind to it, and says "looks fine". CRITIC changes one thing: the checking step goes through a tool (a search engine, a calculator, a code interpreter, a test suite), so the critique rests on something outside the model. This lesson builds both with scripted parts, then runs them with a real small model on six word problems, where the tool is a Python interpreter running a program the model writes.

An agent produces an answer that is almost right. Maybe a line of code has a syntax error. Maybe a summary is too long. Maybe a plan misses an edge case. What you want is: the agent critiques its own output, then fixes it.

Self-Refine shows this works with a single model, no training data, no RL. But there is a catch: LLMs are bad at self-verification on hard facts. CRITIC names the fix — route the verify step through external tools (search, code interpreter, calculator, test runner).

Together these two papers define the 2026 default for iterative improvement: generate, verify (externally when possible), refine, stop when the verifier passes.

Idea 1 · Self-Refine (Madaan et al., NeurIPS 2023)

One LLM, three roles:

generate(task)            -> output_0
feedback(task, output_0)  -> critique_0
refine(task, output_0, critique_0, history) -> output_1
feedback(task, output_1)  -> critique_1
refine(task, output_1, critique_1, history) -> output_2
...
stop when feedback says "no issues" or budget exhausted.

Key detail: refine sees the full history — all prior outputs and critiques — so it does not repeat mistakes. The paper's ablations also show that the feedback must be specific: generic or no feedback gives much smaller gains.

Headline: +20 absolute improvement averaged across 7 tasks (math, code, acronym, dialog) including GPT-4. No training, no external tools, single model.

Idea 2 · CRITIC (Gou et al., arXiv:2305.11738, v4 Feb 2024)

Self-Refine's weakness: the feedback step is an LLM scoring itself. For factual claims this is unreliable (a hallucination often looks convincing to the model that produced it). CRITIC replaces feedback(task, output) with verify(task, output, tools) where tools includes:

  • A search engine for factual claims.
  • A code interpreter for code correctness.
  • A calculator for arithmetic.
  • Domain-specific verifiers (unit tests, type checkers, linters).

The verifier produces a structured critique grounded in tool results. The refiner then conditions on this critique.

Headline: CRITIC outperforms Self-Refine on factual tasks because the critique is grounded. On tasks without external verifiers (creative writing, formatting), CRITIC reduces to Self-Refine.

Idea 3 · The stop condition

Two common shapes:

  1. Verifier passes. External test returns success. Preferred when available (unit tests, type checker, guardrail assertion).
  2. No feedback issued. Model says "the output is fine." Cheaper but unreliable; pair with a max-iteration cap.

2026 default: combine them. "Stop if verifier passes OR model says fine AND iterations >= 2 OR iterations >= max_iterations."

Idea 4 · Evaluator-Optimizer (Anthropic, 2024)

Anthropic's Dec 2024 post names this as one of the five workflow patterns. Two roles:

  • Evaluator: scores the output and produces a critique.
  • Optimizer: revises the output given the critique.

Loop until the evaluator passes. This is Self-Refine/CRITIC in Anthropic's framing. A practical engineering detail: make the evaluator's prompt substantially different from the optimizer's, so the model does not just rubber-stamp its own work.

Idea 5 · OpenAI Agents SDK output guardrails

OpenAI Agents SDK ships this pattern as "output guardrails." A guardrail is a validator that runs on the final output of an agent. If the guardrail trips (raises OutputGuardrailTripwireTriggered), the output is rejected and the agent can retry. Guardrails can call tools (CRITIC-style) or be pure functions (Self-Refine-style).

Idea 6 · 2026 pitfalls

  • Rubber-stamp loops. Same model doing generation and critique with the same prompt style converges on "looks good to me." Use structurally different prompts, or a smaller cheap model for critique.
  • Over-refinement. Each refine pass adds latency and tokens. Budget 1-3 passes; after that, escalate to human review.
  • CRITIC on trivial tasks. If there is no external verifier, CRITIC degenerates to Self-Refine; do not pay the latency for a stub verifier.

The same idea as a formula

The loop. For task x, output yt​, feedback ft​ and the history Ht​={(y0​,f0​),…,(yt​,ft​)}:

y0​=G(x),ft​=C(x,yt​),yt+1​=R(x,Ht​),
stopping when ft​ says "no issues" or t=Tmax​. Self-Refine uses the model for C; CRITIC uses C(x,yt​)=critique(x,yt​,tool(x,yt​)).

What a critic is worth. For a critic, the two numbers that matter are its catch rate (how often it flags a wrong answer) and its false-alarm rate (how often it flags a right one). If a fraction q of first answers are wrong and the refinement fixes a flagged wrong answer with probability r+​ and breaks a flagged right one with probability r−​, one round changes accuracy by

Δacc=q⋅catch⋅r+​−(1−q)⋅false alarm⋅r−​.
A critic that never flags anything gives Δ=0; a noisy one can make things worse.

Worked example
The two critics below, in that formula
  • First answers: 5 of 6 right, so q=1/6.
  • Self-Refine's critic said "no issues" every time: catch rate 0, false alarms 0, so Δ=0. Accuracy stays 5/6.
  • CRITIC's program disagreed with three answers: the wrong one (#3) and two right ones (#1, #4). Catch rate 1, false-alarm rate 2/5.
  • Over its two rounds the refinement fixed #3 (r+​=1) and in the end broke both #1 and #4 (r−​=1): Δ=61​⋅1⋅1−65​⋅52​⋅1=61​−62​=−61​.
  • 5/6 becomes 4/6, as the run shows. The tool computed correctly; the program it ran was wrong.
Check your mental model
  • ✗ "A model can check its own answer."
    ✓ It often approves its own mistakes; the critic below approved a wrong answer without comment.
  • ✗ "Any tool makes the critique trustworthy."
    ✓ Only if the tool's input is right. A model-written program can be as wrong as the model's answer.
  • ✗ "More refinement rounds are always better."
    ✓ Each round can break a correct answer; budget one to three and stop when an independent check passes.
  • ✗ "CRITIC and Self-Refine are different loops."
    ✓ Same loop; only the source of the critique differs.

Self-Refine with a real model

Qwen2.5-0.5B-Instruct (greedy, CPU) solves each problem, critiques its solution with a separate prompt, and refines with the full history if the critic finds a problem, for at most two rounds. The known answers are used only to score the table, never inside the loop. About 80 seconds.

# Self-Refine with a real model: Qwen2.5-0.5B-Instruct (greedy, CPU) solves six word problems, critiques
# its own answer, and refines with the whole history, stopping when its critic says "no issues" or after
# two refinements. The answers are checked against known values only for this report, never in the loop.
import os, re, subprocess, sys, time, torch
os.environ.setdefault("HF_HUB_OFFLINE", "1")            # the model is already in the local cache
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
CALLS = [0]
def chat(text, max_new=220):
    ids = tok.apply_chat_template([{"role": "user", "content": text}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=max_new, do_sample=False)
    CALLS[0] += 1
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
PROBLEMS = [
    ("A shop sells pencils at 3 for 1 dollar. How many dollars do 27 pencils cost?", 9),
    ("Tom has 48 marbles. He gives a quarter of them to his sister and then 5 to a friend. How many marbles does he have left?", 31),
    ("A train travels at 60 km per hour for 2.5 hours, then at 40 km per hour for 1.5 hours. How many km does it travel in total?", 210),
    ("A box holds 12 eggs. How many boxes are needed to pack 100 eggs?", 9),
    ("Anna reads 15 pages a day. Her book has 290 pages and she has already read 65. How many more days until she finishes?", 15),
    ("A shirt costs 40 dollars. It is discounted by 15%, then 10% tax is added to the discounted price. What is the final price in dollars?", 37.4),
]
def answer_of(text):
    m = re.findall(r"(?:Answer:?\**:?\s*\$?|boxed\{)(-?[\d,]*\.?\d+)", text)    # also "**Answer:** 81", \boxed{81}
    m = m or re.findall(r"(-?\d[\d,]*\.?\d*)", text)             # no answer line: the last number written
    return float(m[-1].replace(",", "").rstrip(".")) if m else None
SOLVE = ("Solve the problem in at most five short lines of plain text (no LaTeX), then end with a line "
         "'Answer: <number>'.\nProblem: {p}")
FEEDBACK = ("Here is a solution to a problem.\nProblem: {p}\nSolution:\n{s}\n\nCheck each step. If everything "
            "is correct, reply exactly 'no issues'. Otherwise describe the mistake in one or two sentences.")
REFINE = ("Problem: {p}\nEarlier attempts and the feedback on each:\n{h}\nWrite a corrected solution in at most five "
          "short lines of plain text (no LaTeX), then end with a line 'Answer: <number>'.")
def self_refine(p, rounds=2):
    sol = chat(SOLVE.format(p=p)); history, trail = [], [answer_of(sol)]
    for _ in range(rounds):
        fb = chat(FEEDBACK.format(p=p, s=sol), max_new=60)
        if "no issues" in fb.lower():
            return trail, "critic: no issues"
        history.append(f"Attempt: {sol}\nFeedback: {fb}")
        sol = chat(REFINE.format(p=p, h="\n\n".join(history))); trail.append(answer_of(sol))
    return trail, "budget"
fmt = lambda a: "none" if a is None else (f"{a:g}")
started = time.perf_counter(); results = {}
print(f"{'problem':<10}{'truth':>7}  {'answers, attempt by attempt':<30}{'stopped because'}")
for k, (p, truth) in enumerate(PROBLEMS, 1):
    trail, why = self_refine(p); results[k] = (trail, truth)
    print(f"{'#' + str(k):<10}{truth:>7g}  {' -> '.join(fmt(a) for a in trail):<30}{why}")
first = sum(t[0] is not None and abs(t[0] - tr) < 1e-6 for t, tr in results.values())
last = sum(t[-1] is not None and abs(t[-1] - tr) < 1e-6 for t, tr in results.values())
print(f"\ncorrect: first attempt {first}/6, after Self-Refine {last}/6   model calls {CALLS[0]}   {time.perf_counter() - started:.0f} s")

The critic approved everything. For all six problems the self-critique said "no issues" after the first attempt, so Self-Refine never refined. Five answers were right; #3 (the train) was 70 instead of 210, and the critic approved it too. This is the rubber-stamp loop from Idea 6: the same model, asked whether its own work is right, says yes.

The loop itself cost little. Twelve model calls, two per problem. A critic that never objects is cheap and useless: accuracy is 5/6 before and after.

Getting a number out of a small model is its own problem. Even with "end with a line 'Answer: '", it wrote **Answer:** 9, \boxed{15} or "the answer is $9.", so the extractor accepts several forms and falls back to the last number.

CRITIC: the check goes through an interpreter

This block continues from the one above. The verifier is now a tool: the model writes a Python program for the problem, a fresh interpreter runs it, and if the printed number disagrees with the solution's answer, that disagreement (with the program) becomes the critique. About three minutes.

# CRITIC: the verify step goes through a tool. The model writes a short Python program for the problem;
# the interpreter runs it; if its result disagrees with the solution's answer, that disagreement (with
# the program and its output) is the critique for one refinement. Continues from the block above.
PROGRAM = ("Write a short Python program that computes the answer to this problem and prints only the number. "
           "Reply with one ```python block.\nProblem: {p}")
def run_program(text):
    m = re.search(r"```(?:python)?\n(.*?)```", text, re.S)
    code = m.group(1) if m else text
    r = subprocess.run([sys.executable, "-c", code], capture_output=True, text=True, timeout=10)
    out = (r.stdout.strip().splitlines() or [""])[-1]
    try:
        return float(out), code
    except ValueError:
        return None, code
def critic(p, rounds=2):
    sol = chat(SOLVE.format(p=p)); trail, log = [answer_of(sol)], []
    tool, code = run_program(chat(PROGRAM.format(p=p), max_new=150))   # greedy: the same program every round
    for _ in range(rounds):
        ans = trail[-1]
        if tool is None:
            log.append("program failed"); return trail, log, "verifier unusable"
        if ans is not None and abs(tool - ans) < 1e-6:
            log.append(f"program says {tool:g}"); return trail, log, "verifier agrees"
        log.append(f"program says {tool:g}")
        fb = (f"A Python program for this problem printed {tool:g}, but your answer was {fmt(ans)}.\n"
              f"Program:\n{code.strip()}\nFind which one is wrong.")
        sol = chat(REFINE.format(p=p, h=f"Attempt: {sol}\nFeedback: {fb}")); trail.append(answer_of(sol))
    return trail, log, "budget"
started, CALLS[0], crit = time.perf_counter(), 0, {}
print(f"{'problem':<10}{'truth':>7}  {'answers':<18}{'verifier':<36}{'stopped because'}")
for k, (p, truth) in enumerate(PROBLEMS, 1):
    trail, log, why = critic(p); crit[k] = (trail, truth)
    print(f"{'#' + str(k):<10}{truth:>7g}  {' -> '.join(fmt(a) for a in trail):<18}{'; '.join(log):<36}{why}")
ok = lambda t, tr: t is not None and abs(t - tr) < 1e-6
print(f"\ncorrect after CRITIC {sum(ok(t[-1], tr) for t, tr in crit.values())}/6   "
      f"model calls {CALLS[0]}   {time.perf_counter() - started:.0f} s")
wrong_ok = sum(1 for t, tr in results.values() if not ok(t[-1], tr))
print(f"Self-Refine's critic said 'no issues' on {wrong_ok} wrong answer(s) of {wrong_ok}")

#1              9  9 -> 81           program says 81; program says 81    verifier agrees
#2             31  31                program says 31                     verifier agrees

Reading this output

The tool caught the real mistake. For #3 the program printed 210, the solution said 70, and after one refinement with that critique the answer became 210.

It also overturned two correct answers. For #1 the program computed 27 × 3 = 81 (it misread "3 for 1 dollar" as 3 dollars each) and for #4 it computed 100 // 12 = 8 (rounding down boxes). The interpreter ran the programs correctly; the programs were wrong. The refinement trusted the tool and changed 9 to 81, and 9 to 8 on the second round. Final accuracy 4/6, worse than not refining.

So "tool-grounded" means "grounded in whatever the tool was given". Here the model wrote the check, so the check shares the model's blind spots. CRITIC's paper results come from tools whose inputs are less in the model's hands (search results, a calculator on extracted expressions, given test cases). Each program was generated once per problem: with greedy decoding a second request would return the same program.

Build it

code/main.py implements Self-Refine and CRITIC on a toy task: produce a short bullet list given a topic. The verifier checks format (3 bullets, each under 60 chars). CRITIC adds an external "fact verifier" that penalizes known hallucinations.

Components:

  • generate — scripted producer.
  • feedback — LLM-style self-critique.
  • verify_external — CRITIC-style grounded verifier.
  • refine — rewrites output given history.
  • Stop condition — verifier passes or max 4 iterations.

Part 1 of 3 · Attempt, generate, feedback_self, verify_external, refine, KNOWN_WRONG_FACTS

"""Toy Self-Refine and CRITIC loop.

Task: produce a 3-bullet summary under 60 chars per bullet that does not contain
known factual errors. Self-Refine uses LLM-style self-critique; CRITIC routes
verification through an external fact list.
"""

from __future__ import annotations

from dataclasses import dataclass, field


KNOWN_WRONG_FACTS = [
    "paris is the capital of germany",
    "mt everest is in europe",
    "the sun orbits the earth",
]


@dataclass
class Attempt:
    iteration: int
    output: str
    critique: str
    verified: bool


def generate(topic: str, history: list[Attempt]) -> str:
    if not history:
        return (
            "- Paris is the capital of Germany\n"
            "- Mt Everest is in Europe\n"
            "- Water boils at 100C"
        )
    last = history[-1]
    if "germany" in last.critique.lower():
        return (
            "- Paris is the capital of France\n"
            "- Mt Everest is in Europe\n"
            "- Water boils at 100C"
        )
    if "everest" in last.critique.lower():
        return (
            "- Paris is the capital of France\n"
            "- Mt Everest is in Asia\n"
            "- Water boils at 100C at sea level"
        )
    return history[-1].output


def feedback_self(output: str) -> tuple[str, bool]:
    if "Germany" in output and "Paris" in output:
        return "first bullet reads wrong, double-check capital", False
    if "Europe" in output and "Everest" in output:
        return "second bullet's continent looks off to me", False
    return "no issues", True


def verify_external(output: str) -> tuple[str, bool]:
    text = output.lower()
    for fact in KNOWN_WRONG_FACTS:
        key = fact.split(" is ")[0] if " is " in fact else fact
        if "paris" in text and "germany" in text:
            return f"verifier: 'paris is the capital of germany' contradicts reference data", False
        if "everest" in text and "europe" in text:
            return f"verifier: 'mt everest is in europe' contradicts reference data", False
    if len([l for l in output.splitlines() if l.startswith("-")]) != 3:
        return "verifier: expected 3 bullet lines", False
    if any(len(l) > 60 for l in output.splitlines()):
        return "verifier: bullet exceeds 60 chars", False
    return "verifier: ok", True


def refine(topic: str, prev: str, critique: str, history: list[Attempt]) -> str:
    return generate(topic, history)

Part 2 of 3 · run_loop, print_run

def run_loop(topic: str, use_critic: bool, max_iters: int = 4) -> list[Attempt]:
    history: list[Attempt] = []
    output = generate(topic, history)
    verify = verify_external if use_critic else (lambda o: feedback_self(o))
    for i in range(1, max_iters + 1):
        critique, ok = verify(output)
        history.append(Attempt(i, output, critique, ok))
        if ok:
            break
        output = refine(topic, output, critique, history)
    return history


def print_run(label: str, history: list[Attempt]) -> None:
    print(f"\n{label}")
    print("-" * 60)
    for a in history:
        tag = "OK " if a.verified else "..."
        print(f"  iter {a.iteration} {tag} critique: {a.critique}")
        for line in a.output.splitlines():
            print(f"    {line}")


def main() -> None:
    print("=" * 70)
    print("SELF-REFINE and CRITIC: Phase 14, Lesson 05")
    print("=" * 70)

    hist_self = run_loop("world facts", use_critic=False)
    print_run("Self-Refine (self-critique only)", hist_self)

    hist_critic = run_loop("world facts", use_critic=True)
    print_run("CRITIC (external verifier)", hist_critic)

    def summary(hist: list[Attempt]) -> str:
        return "passed" if hist and hist[-1].verified else "did not converge"

    print()
    print(f"Self-Refine ended: {summary(hist_self)}  after {len(hist_self)} iters")
    print(f"CRITIC    ended: {summary(hist_critic)}  after {len(hist_critic)} iters")
    print()
    print("Observation: CRITIC's verifier is grounded against reference data; a")
    print("self-critic can fail to flag its own confident-sounding hallucination.")

Use it: the same idea with real libraries

Anthropic's evaluator-optimizer is this pattern in Claude-friendly language. OpenAI Agents SDK's output guardrails are CRITIC-shaped (guardrails can call tools). LangGraph ships a reflection node that reads like Self-Refine. Google's Gemini 2.5 Computer Use adds a per-step safety evaluator that is a CRITIC variant: every action is verified before commit.

Break it on purpose

To make the CRITIC loop "decisive", a teammate changes the refine step to always replace the answer with the program's result whenever they disagree. Using the table above, what would the final accuracy be, and what kind of verifier would make that rule safe? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Evaluator-optimizer loops in production are mostly CRITIC-shaped, with checks that do not come from the model: coding agents run the test suite, type checker and linter after each edit and feed failures back; structured-output pipelines re-ask on schema validation errors.
  • Guardrails as verifiers: the OpenAI Agents SDK's input and output guardrails, LangChain middleware and Guardrails AI validators reject an output and trigger a retry.
  • LLM-as-judge remains common for things no tool can check (tone, helpfulness), with a different model or a rubric, and calibrated against human labels before it gates anything.
  • On your laptop: the 0.5B model rubber-stamps itself and writes wrong programs. A 7B to 8B coding model in 4-bit on the RTX 4060 writes far better verification programs, but the rule stays: prefer checks you wrote over checks the model wrote.

Sources: Self-Refine (arXiv:2303.17651), CRITIC (arXiv:2305.11738), Anthropic, Building effective agents, OpenAI Agents SDK guardrails, Guardrails AI.

Recap
What to keep from this lesson
  • Generate, critique, refine, stop: one loop for Self-Refine and CRITIC.
  • A model judging itself tends to approve its own mistakes.
  • Tool-grounded critique is only as good as the tool's input.
  • Count catches and false alarms; a noisy critic lowers accuracy.
  • Prefer independent checks: tests, reference data, schemas.

Given a task, an iteration budget, and what verifier is available (tool-grounded or self-eval only), emit prompts and a stop policy for an evaluator-optimizer loop.

Produce:

1. Generator prompt. Deterministic producer for the first output. State the task, output format, and constraints explicitly.
2. Evaluator/verifier prompt. If tools are available (search, code run, tests, calculator, type check), specify how to call them and how to produce a structured critique (JSON with: pass/fail, violations[], suggested_fixes[]). If only self-eval is available, explicitly flag the Self-Refine rubber-stamp risk and use a structurally different prompt style (e.g., adversarial "find at least one flaw").
3. Refiner prompt. Must reference prior outputs and critiques (history). State that "do not repeat a failure mode flagged in prior iterations" is mandatory.
4. Stop policy. The conjunction: verifier passes OR (self-eval says fine AND iterations >= 2) OR iterations >= max_iterations. Never single-condition.
5. Observability hooks. Log each iteration as an OpenTelemetry GenAI span (evaluate, optimize) per Lesson 23 so the full refine trajectory is auditable.

Hard rejects:

- Same prompt for generator and critic. Rubber-stamp risk — the model agrees with itself.
- No iteration cap. Infinite refine loops burn tokens; always cap at 4 by default.
- Verifier prompt that asks for freeform prose feedback. Structured JSON only — pass/fail plus itemized violations.
- Dropping history from the refiner prompt. Paper shows quality collapses without it.

Refusal rules:

- If the task has no verifier and no way to build one, refuse CRITIC and note that Self-Refine is the weaker option available — warn the user about rubber-stamp risk.
- If max_iterations >= 10, refuse and recommend re-architecting the task. Refine-to-convergence beyond 3-4 passes is usually a signal the generator prompt is wrong.
- If the verifier calls destructive tools (shell, git write), refuse and require a sandbox boundary (Lesson 09).

Output: a single configuration block with all prompts, stop policy, and tool list, plus a "what to read next" note pointing to Lesson 16 (OpenAI Agents SDK guardrails), Lesson 12 (Anthropic evaluator-optimizer), or Lesson 30 (eval-driven agent development) based on the deployment target.

  3. Implement a "generator-critic on different models" variant: big model generates, small model critiques. Does it beat same-model?

Solutions

SolutionP1 · All six, including the wrong one

On all six. The self-critique replied "no issues" (or close to it) every time, so no refinement ran. One of the six answers was wrong (#3, 70 instead of 210) and went straight through. A model asked to check its own reasoning tends to re-read the same reasoning and agree with it; that is why Self-Refine's critic should at least use a different prompt, and why CRITIC moves the check to a tool.

SolutionB1 · Trust the program only if it is trustworthy

Accuracy would be 4/6 here as well: #3 becomes 210 (right), #1 becomes 81 and #4 becomes 8 (both wrong). The rule makes the program the final authority, so the result is exactly as good as the model's programs. It also hides the disagreement instead of reporting it.

Replacing the answer with the verifier's result is safe only when the verifier is independent of the model and trusted: hand-written unit tests, an exact rule, reference data, or a calculator applied to quantities extracted from the problem by code you control. When the verifier is itself model-generated, treat a disagreement as a reason to look again (or ask a person), not as a verdict.
