In plain words first
The idea in one line

Lesson 7.16 proved the math: the Leviathan rejection rule preserves the verifier's distribution exactly. This lesson is the training-stack view of 2026 production speculative decoding. EAGLE-3 turned the draft model from a cheap approximation into a purpose-built tiny network trained on the verifier's own hidden states, then added a training-time test loop that aligns its train and inference distributions. Result: 3× to 6.5× end-to-end speedup, accepted per-token rates above 0.9 on chat, no distributional tradeoff. Every production inference stack

Terms you'll hear
Term What people say What it actually means
Leviathan rule "min(1, q over p)" Bernoulli accept/reject with probability min(1, q(d)/p(d)), preserves the verifier distribution exactly when you sample from the residual on rejection
Residual distribution "(q minus p) plus, normalized" (q - p)_+ clamped at zero and renormalized — the correct distribution to sample from on rejection
Acceptance rate α "how often the draft is right" Expected per-token Bernoulli-success probability under the rejection rule; governs all speedup math
EAGLE-1 "hidden-state draft" Tiny transformer draft conditioned on the verifier's last-layer hidden state (Li et al., 2024)
EAGLE-2 "dynamic draft tree" EAGLE-1 plus a tree of candidate continuations scored with tree attention in one verifier pass
EAGLE-3 "training-time test" Drops the feature-prediction loss, trains on direct token prediction with the draft fed its own outputs during training
Training-time test (TTT) "exposure bias fix" Run the draft autoregressively during training so train and test input distributions match — the direct analog of scheduled sampling
KV rollback "undo rejected drafts" Bookkeeping that resets the verifier's KV cache to the accepted-prefix length after a rejection
Bonus token "the free one" When all N drafts accept, sample one extra from q_{N+1} at no additional verifier cost
Tree attention "verify many candidates at once" Attention with a non-causal mask that respects the topology of a draft tree; computes q_i for every node in the tree in one forward pass

The problem

In plain words first

A big language model writes one token per forward pass, and each pass is slow mainly because all its weights must be read from memory. Speculative decoding lets a small, fast draft guess the next few tokens; the big model then checks all the guesses in one pass. A clever accept/reject rule keeps exactly the guesses the big model would have produced at the same rate, and replaces the first wrong one with a correct sample, so the output is identical in distribution to running the big model alone, only faster. How much faster depends almost entirely on one number: the acceptance rate α, how often the big model agrees with the draft. EAGLE-3, the 2025 state of the art, is a tiny draft network that reads the big model's own hidden states so that α is high. This lesson runs the lesson's simulator, computes the theory exactly, and measures α between two real models (SmolLM2 135M drafting for SmolLM2 360M) on chat, code and list prompts. No model is trained.

Autoregressive decoding on a 70B model runs at maybe 35 tokens per second on one H100 (in FP8, so that the 70 GB of weights fit). The GPU is nowhere near saturated. Memory bandwidth is the ceiling: every token loads 70B of weights from HBM, does one step of arithmetic, and produces one float. The compute units sit mostly idle.

Speculative decoding turns that into a throughput problem you can actually solve. A cheap draft proposes N tokens in N small forward passes. The verifier runs once on the prefix plus all N drafts. If the verifier's distribution at position i agrees with the draft (in a statistical sense we will make precise), we accept; if not, we reject and sample a correction from the residual distribution. A single big-model forward produces up to N+1 accepted tokens instead of one.

The theorem that matters is Leviathan, Kalman, Matias (ICML 2023): the output distribution is identical to what sampling from the verifier directly would have produced. Not approximately. Identically. This is the entire reason speculative decoding is acceptable in production — it is a pure latency optimization with no quality tradeoff.

What Lesson 7.16 gave you was the math. What this lesson gives you is the training stack. A good draft is worth 2× more speedup than a cheap draft. EAGLE, EAGLE-2, and EAGLE-3 (Li et al., 2024–2025) turned "draft = smaller version of the same model" into a precise engineering discipline. In 2026, production inference servers support EAGLE-3 drafts for most popular open models.

Idea 1 · The invariant: Leviathan rejection sampling

Let p(t) be the draft's distribution for the next token given some prefix, and q(t) be the verifier's. Sample a draft token d ~ p. Accept with probability min(1, q(d) / p(d)). On reject, sample from the residual distribution (q - p)_+ / ||(q - p)_+||_1. The resulting samples are distributed according to q. This is true regardless of how bad p is — the worse it is, the more often you reject, but the output remains exact.

Stack N of these calls back to back using one verifier forward pass on prefix + d_1 + ... + d_N. The verifier returns q_1, q_2, ..., q_{N+1} simultaneously. Walk left to right. On the first rejection at position j, sample from residual(q_j, p_j) and stop. On full acceptance, sample one bonus token from q_{N+1}.

Idea 2 · What determines speedup

Let α be the expected acceptance rate per drafted token. Let c = cost(draft) / cost(verifier) be the cost ratio. The expected number of accepted tokens per verifier forward is:

E[accepted]=1−α1−αN+1​

The expected total wall time per accepted token is (N * c + 1) / E[accepted]. Minimize that with respect to N and you get the sweet spot. For α = 0.8, c = 0.05 the formula gives a speedup of about 3× from N ≈ 5 upward (best at 8, 3.1×). For α = 0.95, c = 0.02 it keeps improving to very long drafts (5.3 tokens per call at N = 5, about 10× at N ≈ 30). Real systems use far shorter drafts, because the formula assumes independent acceptances and a verifier whose cost does not grow with N (see the exact computation after Build it).

The single biggest lever is α. Going from α = 0.6 (vanilla draft) to α = 0.9 (EAGLE-3) at fixed N = 5 takes you from 2.4 expected tokens per verifier forward to 4.7. Nearly 2× more throughput from the same verifier.

Idea 3 · The two-year progression

Vanilla speculative (Leviathan, 2023). Draft model is an independently trained smaller LLM from the same family. Easy to wire up, α ≈ 0.6, speedup around 2× at best.

EAGLE-1 (Li et al., 2024). Draft is a tiny transformer — typically one or two layers — that takes the verifier's last-layer hidden state as input and predicts the next token directly. Because the draft sees the verifier's feature representation, its distribution is much closer to the verifier's. α climbs to 0.7–0.8.

EAGLE-2 (Li et al., 2024). Adds a dynamic draft tree: instead of proposing a single sequence of N tokens, propose a small tree of candidates, score each with the verifier in one forward pass (tree attention), and walk the highest-probability path. Draft length becomes adaptive per step. α per accepted-path token climbs above 0.85.

EAGLE-3 (Li et al., 2025, NeurIPS). Two more changes. First, drop the feature-prediction loss entirely — EAGLE-1/2 trained the draft to match the verifier's hidden states, which caps how much data helps. EAGLE-3 trains directly on token prediction. Second, training-time test (TTT): during draft training, feed the draft's own previous predictions back as inputs over multiple steps, the same way it operates at inference. This aligns the train and test distributions and stops error accumulation. Measured speedup: up to 6.5× on chat, 38% throughput improvement at batch 64 in SGLang on H100.

Idea 4 · KV cache rollback

Verification extends the verifier's KV cache by N entries in one pass. If rejection happens at position j, the cache contents past position j-1 are now wrong. Two common implementations: write to a scratch buffer and commit on acceptance (vLLM, TensorRT-LLM), or keep a physical KV cache plus a logical length and truncate on reject. Either way, the rollback cost is bytes per layer per head, which is negligible next to the forward-pass cost.

For EAGLE-2 tree search, the verifier runs attention with a non-causal mask that respects tree topology. The engineering is fiddly but the computation is a standard flash-attention call with a custom mask.

The same idea as a formula

For a draft distribution p and target q over the vocabulary, draw d∼p and accept with probability min(1,q(d)/p(d)); on rejection draw from r=(q−p)+​/∥(q−p)+​∥1​.

Acceptance rate. α=∑t​p(t)min(1,p(t)q(t)​)=∑t​min(p(t),q(t))=1−TV(p,q).

Exactness. The probability of emitting t is min(p(t),q(t))+(1−α)r(t). Where q(t)≥p(t) this is p(t)+(q(t)−p(t))=q(t); where q(t)<p(t) it is q(t)+0. So the output is exactly q.

Tokens per verifier call with N drafts and independent acceptances: E[tokens]=∑k=0N​αk=1−α1−αN+1​ (the accepted drafts plus one correction or bonus token).

Speedup with draft cost c per token relative to one verifier pass: S=1+NcE[tokens]​.

Worked example
α = 0.8, N = 5, c = 0.05 by hand
  • Tokens per verifier call: 1+0.8+0.64+0.512+0.410+0.328=3.69.
  • Cost of one round: one verifier pass plus five draft passes, 1+5×0.05=1.25.
  • Speedup: 3.69/1.25=2.95×.
  • With N=1: 1.8/1.05=1.71×. With N=10: (1−0.811)/0.2=4.57 tokens for cost 1.5, 3.05×: the gain flattens because 0.8k shrinks fast.
  • If the verifier pass itself cost more for longer drafts (at large batch it does), the best N would be shorter.

Step 1 · the rejection rule

See code/main.py. This is the full Leviathan speculative loop with all the pieces: draft-of-N, verifier parallel pass, per-position rejection, residual sampling, bonus token, KV rollback, and empirical verification that the output distribution matches direct sampling from q.

def accept(q_prob, p_prob, u):
    if p_prob <= 0:
        return True
    return u < min(1.0, q_prob / p_prob)

Step 2 · residual distribution

def residual(q, p):
    raw = [max(0.0, qi - pi) for qi, pi in zip(q, p)]
    s = sum(raw)
    if s == 0:
        return list(q)
    return [r / s for r in raw]

Step 3 · a full speculative step

The spec_step function drafts N tokens from p, then verifies all of them in one parallel q evaluation. For each drafted token it applies the rejection rule, and on the first rejection it samples the correction from the residual. If everything accepts, it emits a bonus token from q_{N+1}.

Step 4 · KV rollback bookkeeping

The simulator tracks a logical kv_length per worker. On acceptance of k drafts, kv_length += k. On a rejection at position j, the cache is already written past j, but the logical length is set to prefix_length + j + 1 — one past the correction token. Subsequent reads truncate to the logical length.

Step 5 · the Leviathan check

Run 50,000 speculative steps. Count the empirical distribution of accepted tokens. Compare to 50,000 direct samples from q. The chi-square statistic should be well under the critical value. The theorem passes in practice.

Step 6 · speedup vs. α

Sweep the draft quality by perturbing p away from q at different amplitudes. Measure α, then plot expected tokens per verifier call as a function of α and N. The code prints a table showing how EAGLE-3-class draft quality (α ≈ 0.9) unlocks 4–5 tokens per verifier call.

The theory, computed exactly

A: the output distribution of one speculative step, computed rather than sampled, for a deliberately bad draft. B: the best draft length and speedup for each acceptance rate and draft cost. C: why the same average α can give different speedups. D: what batching does to the gain on a memory-bound 70B verifier.

import numpy as np

def E_acc(a, N):                      # expected tokens per verifier call, i.i.d. acceptance
    return N + 1 if a >= 1 else (1 - a ** (N + 1)) / (1 - a)

print("A. The output of one speculative step is exactly q (computed, not sampled)")
q = np.array([0.30, 0.22, 0.15, 0.10, 0.08, 0.07, 0.05, 0.03])
p = np.array([0.05, 0.05, 0.05, 0.05, 0.10, 0.20, 0.25, 0.25])      # a deliberately bad draft
acc = np.minimum(1, q / p)                                          # accept probability per draft token
alpha = (p * acc).sum()
res = np.maximum(q - p, 0); res /= res.sum()
out = p * acc + (1 - alpha) * res
print(f"  draft p : {np.round(p, 3)}")
print(f"  output  : {np.round(out, 3)}")
print(f"  largest |output - q| = {np.abs(out - q).max():.1e}")
print(f"  acceptance rate alpha = sum(p*min(1,q/p)) = {alpha:.3f};  sum(min(p,q)) = {np.minimum(p, q).sum():.3f};"
      f"  1 - total variation = {1 - 0.5 * np.abs(p - q).sum():.3f}")
print()

print("B. Best draft length N and speedup, from (1 + N*c) / E[accepted]   (c = draft cost / verifier cost)")
cs = [0.02, 0.05, 0.1, 0.3]
print("  alpha " + "".join(f"{f'c={c}':>16}" for c in cs))
for a in [0.6, 0.7, 0.8, 0.9, 0.95]:
    row = f"  {a:<5} "
    for c in cs:
        Ns = np.arange(1, 41)
        t = np.array([(1 + N * c) / E_acc(a, N) for N in Ns])
        row += f"{f'N={Ns[t.argmin()]} {1 / t.min():.2f}x':>16}"
    print(row)
print(f"  alpha 0.6 vs 0.9 at N=5: {E_acc(0.6, 5):.2f} vs {E_acc(0.9, 5):.2f} tokens per verifier call")
print()

print("C. Same average alpha, different speedup: easy and hard stretches come in runs")
easy, hard, f = 0.98, 0.40, 0.7
mean = f * easy + (1 - f) * hard
print(f"  70% of positions have alpha {easy}, 30% have {hard}: mean alpha {mean:.3f}, N = 5")
print(f"  positions independent (mixed at random)   : {E_acc(mean, 5):.2f} tokens per call (formula with the mean)")
print(f"  whole drafts easy or hard (runs of text)  : {f * E_acc(easy, 5) + (1 - f) * E_acc(hard, 5):.2f} tokens per call")
print()

print("D. Batching eats the gain: 70B verifier in FP8 on one H100, alpha 0.9, N = 5, draft cost ignored")
W, BW, F = 70e9, 3.35e12, 1979e12 / 2    # bytes of weights, HBM bytes/s, dense FP8 FLOP/s at a realistic 50%
flop_tok = 2 * 70e9
def step(tokens):                           # one forward over `tokens` tokens: limited by memory or by compute
    return max(W / BW, tokens * flop_tok / F)
print(f"  {'batch':>5} {'plain ms/step':>14} {'spec ms/step':>13} {'speedup':>8}")
for B in [1, 8, 32, 64, 128, 256]:
    plain = step(B) / B                      # time per generated token
    spec = step(B * 6) / (B * E_acc(0.9, 5))
    print(f"  {B:>5} {step(B) * 1e3:>14.1f} {step(B * 6) * 1e3:>13.1f} {plain / spec:>7.2f}x")

Reading this output

A. Even with a terrible draft (α = 0.43: it puts most probability on the target's least likely tokens), the computed output distribution equals q to 3×10−17, rounding error. The three expressions for α agree: acceptance probability, ∑min(p,q) and one minus the total variation distance. A bad draft costs speed, never quality.

B. Under the textbook cost model the best N grows quickly with α and falls with draft cost: at α = 0.9 it is 19 drafts for a 2% draft (6.4×) but 5 for a 30% draft (1.9×), roughly the cost of using a model a third the size of the target as the draft. Production systems use 3 to 7 drafts because the model's assumptions break: acceptances are not independent, and the verifier's pass costs more as N grows. Raising α from 0.6 to 0.9 at N=5 takes tokens per call from 2.4 to 4.7.

C. α alone does not determine the speedup. With the same average of 0.806, independent positions give 3.74 tokens per call, while text that comes in easy and hard stretches (boilerplate, then a hard word) gives 4.49: a fully easy draft goes all the way, a hard one fails early either way. Measure tokens per verifier call (the "acceptance length" EAGLE papers report) on real traffic rather than estimating it from α.

D. On an idealised roofline (a 70B model in FP8 on one H100, half of peak compute), one forward pass takes 21 ms whatever the batch until compute catches up. At batch 1 to 8, checking 6 tokens per sequence is free, and the speedup is the full 4.7×. At batch 64 the verifier must process 384 tokens per pass and becomes compute-bound, and the gain shrinks to 1.8×; beyond about 100 sequences speculative decoding is slower than plain decoding. That is why the EAGLE-3 paper reports 1.38× throughput at batch 64 in SGLang (while EAGLE-1 lost throughput there), and why servers switch speculation off or shorten drafts under heavy load.

When to reach for speculative decoding:

  • Any interactive chat workload where p50 latency matters more than peak throughput.
  • Code generation and structured output (JSON, SQL). α is above 0.9 because the target distribution is highly predictable.
  • Long-form generation (thousands of tokens). The amortized speedup keeps paying.

When not to:

  • Very small models (< 3B). The draft is not that much cheaper than the verifier.
  • Tiny batch-1 CPU deployments. Memory overhead of the draft model may not be worth it.
  • High-temperature creative sampling, where α often drops (measure it: in the real-model run below, chat at temperature 1 did not drop).

Reading this output

SmolLM2-135M agrees with SmolLM2-360M much more on structured text than on free text. On the planets list and the palindrome function, α is 0.94 to 0.98, and N=5 would give 5.4 to 6 tokens per verifier call, close to the maximum of 6. On the advice prompt α is about 0.78, giving about 3.5 tokens per call. The draft has the same tokenizer and training data as the target but a third of the parameters, which is roughly the "vanilla" draft of the table above.

The hardest code tokens are in the prose around the code (" whether", "Here", " works"), not in the code itself: once the function is started, both models predict it the same way.

Temperature did not lower α here. For chat, greedy agreement (0.73, where any disagreement on the top token is a rejection) is lower than the soft acceptance at temperature 1 (0.79), because sampling accepts a draft token in proportion to the overlap of the two distributions. For code and lists α falls slightly with temperature (0.98 to 0.96). Whether high temperature hurts depends on the models and the text, so measure it.

The "tokens/call" column computes the expected chain at every starting position from the measured per-position α; "formula" plugs the average α into (1−α6)/(1−α). They differ by up to 0.45 tokens (the list prompt), part C of the previous run in practice. Here the prefix is the target's greedy answer at every temperature; with sampling, the text and so α would vary from run to run.

What's current (2024–2026)
  • EAGLE-3 drafts in production servers: vLLM (--speculative-config with "method": "eagle3"), SGLang (with SpecForge for training drafts) and TensorRT-LLM; published EAGLE-3 checkpoints exist for Llama 3.x, Qwen3 and DeepSeek models.

Recap
What to keep from this lesson
  • Draft N tokens cheaply, verify in one pass, accept with min(1, q/p), resample from (q − p)₊.
  • The output is exactly the target's distribution.
  • α = Σ min(p, q); tokens per call = (1 − α^(N+1)) / (1 − α).
  • EAGLE raises α with a tiny draft that reads the target's hidden states; EAGLE-3 adds feature fusion and training-time test.
  • Gains are largest at small batch and on predictable text (code, lists); measure α on your own traffic.

Given a production inference target (verifier model, batch size, sequence length profile, target p50/p99 decode latency, accelerator, expected alpha range from telemetry, task mix), recommend a speculative-decoding strategy and tuning parameters. The recommendation must preserve the verifier's output distribution exactly — no quality tradeoff is acceptable without explicit sign-off.

Produce:

1. Draft family. Pick from vanilla, Medusa, EAGLE-1, EAGLE-2, EAGLE-3, or lookahead. Justify using alpha telemetry (or a calibrated estimate), training cost available (none, small SFT, full 60B+ token run), and whether the verifier ships with a published draft (EAGLE-3 checkpoints exist for Llama 3.1/3.3, DeepSeek-V3, Qwen 2.5, Qwen 3).
2. Draft length N. Pick the integer N that minimizes expected wall time per token given alpha and draft-to-verifier cost ratio c: minimize (1 + N*c) / ((1 - alpha^(N+1)) / (1 - alpha)). Show the work for three candidate N values around the optimum.
3. Tree search parameters if EAGLE-2/3. Pick tree depth and branching factor to stay within memory budget. Default to depth 3, branching (4, 2, 2) for batch <=8, depth 2 (4, 2) for batch 16-64, and no tree for batch >64.
4. Temperature gating. When temperature > 0.8, alpha collapses. Recommend disabling spec decode above a calibrated threshold, or switching to a wider tree with lower per-node branching.
5. KV rollback plan. Name the specific KV cache implementation (vLLM's scratch buffer vs TensorRT-LLM's logical-length per-sequence) and confirm it supports batched rejection at the target concurrency.

Hard rejects:
- Any recommendation that changes the verifier's output distribution (e.g., approximate spec-decode, relaxed rejection).
- Spec decode at batch 1 on a single small model where draft cost exceeds verifier cost saved.
- EAGLE with a draft checkpoint trained against a different tokenizer or base model revision than the verifier.
- Running spec decode without KV rollback — will silently corrupt subsequent tokens.

Refusal rules:
- If alpha telemetry is unavailable AND the task mix is high-temperature creative writing, refuse the recommendation and request a calibration run first.
- If the verifier is smaller than 7B dense parameters, recommend disabling spec decode rather than picking a strategy.
- If the serving stack does not support the chosen draft family (e.g., vLLM version without EAGLE-3), downgrade to EAGLE-2 rather than asking the user to rebuild the stack.

Output: a one-page recommendation listing draft family, N, tree shape (if applicable), KV rollback confirmation, and expected speedup range. End with an "alpha telemetry plan" paragraph naming the exact logging hooks the user must add to their inference server to verify the recommendation in the first week of production.

Solutions

SolutionP1 · Chat, about 3 to 3.5 tokens per call

The advice prompt (chat): α ≈ 0.78 at temperature 0.7 to 1 and 0.73 for greedy decoding, giving 3 to 3.5 tokens per verifier call with N=5, against 5.4 to 6 for the code and list prompts. Open-ended text has many plausible continuations, and a small draft distributes its probability differently from the target among them; code and lists are highly constrained, so both models put almost all their probability on the same next token. This is why speculative decoding helps most on code, structured output and repetitive text.

SolutionB1 · The output drifts toward the draft

The output is no longer q. With residual sampling, the probability of emitting token t is min(p(t),q(t))+(1−α)r(t)=q(t). Sampling the correction from q instead gives min(p(t),q(t))+(1−α)q(t). For the bad draft of the exact computation (α = 0.43), the target's most likely token (0.30) would be emitted with probability 0.05+0.57×0.30=0.22, and its least likely (0.03) with 0.03+0.57×0.03=0.047: the output is pulled toward the draft wherever the draft is too confident. The residual exists precisely to add back the probability that acceptance under-delivered. Step 1's χ² test would catch this with enough samples, which is why it belongs in every speculative-decoding implementation's tests.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Debug a failureTwo changes shipped in one week: the target model moved to its next version, and a new customer whose traffic is mostly code was routed onto the same cluster. Speculative decoding has been on for months. Since then the mean inter-token latency fell 25 percent, the P99 rose 15 percent, and throughput at the usual concurrency is down. Diagnose it.

Level 4 of 4 · about 12 minutes to answer well.

Short answer. Both changes attack acceptance. The draft head was trained against the previous target version, so its distribution drifted and more drafts reject; the code traffic shifts the input distribution away from the general chat data the head was trained on, where acceptance falls into the 0.4 to 0.6 band. A rejected draft costs a verify and a re-roll, two passes that serialize under a full batch, which is exactly a tail that worsens while the mean still improves. Read acceptance per traffic slice and per target version from the engine's speculative metrics, retrain or roll back to a head aligned with the new target, and gate speculation per request class.

Why mean and tail move in opposite directions.

Most requests still accept most drafts, so their inter-token latency falls and the mean improves. The requests that reject early pay the draft steps, the verify and a second target pass for the correction, and under a full batch those passes queue behind each other. The tail is where the rejected requests live. Watch P99, not P50.

Cause one: a draft one version behind.

A hidden-state draft is trained to predict a specific target's next token from that target's features. A new target version changes the features and the distribution, and the draft's agreement with it drops. The capstone's first exercise is to measure this degradation and to build the alert for it.

Cause two: a domain the head never saw.

A head trained on general chat sits at 0.6 to 0.8 acceptance there and at 0.4 to 0.6 on code, medical or legal traffic. Code tokens are predictable for a draft trained on code, and poorly predicted by one that was not. Below an acceptance of about 0.55 at high concurrency speculation is net negative, so the new customer may have pushed the cluster under the floor.

The diagnosis.

  1. Pull accepted draft tokens and proposed draft tokens per request from the engine, divide the first by the second, and split by target version and by customer or request class. One number for the whole cluster hides both causes.
  2. Compare the chat slice before and after the upgrade: if it fell, the version drift is real.
  3. Compare the code slice against the chat slice at the same version: if it sits far lower, the domain shift is real.
  4. Confirm the tail story by bucketing P99 by acceptance; the slow tail should be the low-acceptance slice.

The fix.

  • Retrain the head against the new target version, or roll the target back until the aligned head is ready.
  • Route the code customer to a plain decode pool, or train a code-specific head; the training job is light next to fine-tuning the target.
  • Gate speculation per request class on measured acceptance, with an n-gram or draft-free fallback below the floor.
  • Alert on acceptance per slice so the next version bump cannot ship without the draft.

Plausible wrong answers.

  • "Increase the draft length to win back throughput." More drafts at low acceptance are mostly rejected and their cost is still paid; the tail gets worse.
  • "Turn speculation off everywhere." The chat slice may still pay; gate by slice and fix the head.
  • "The new target is just slower; speculation has nothing to do with it." A plain-decode benchmark of the new target settles that in minutes, and the mean improving while the tail worsens points at rejections.

Follow-ups an interviewer may ask.

  • (level 3) Why can the mean improve while throughput falls? Expected: the accepted requests get faster, but the rejected ones consume two target passes each, and at a full batch that extra work displaces other requests.
  • (level 4) Design the alert in two sentences. Expected: compute acceptance per slice and per target version over a short window and compare against the baseline recorded at rollout; page when a slice crosses the floor or drops a fixed share from its baseline.
  • (level 4) What is the fallback when acceptance drops on one slice only? Expected: switch that slice to an n-gram draft or to plain decoding while the head is retrained, and keep speculation where it still pays.
  • (level 4) How does this change your release process? Expected: a target upgrade ships together with a draft trained against it, and the benchmark that gates the release reports acceptance and P99 per slice.

Explain the mechanismWalk the line from a separate small draft model to the current generation of hidden-state drafts. What limitation did each step remove, and why does feeding the draft the verifier's internal features help so much?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. A separate small model from the same family accepts around 0.6 of its tokens, because its distribution drifts from the verifier's. The first hidden-state draft replaces it with a one or two layer network that reads the verifier's last-layer features, so the draft starts from the verifier's own representation and acceptance rises to 0.7 to 0.8. The second generation proposes a tree of candidates and verifies every branch in one pass with a tree-shaped attention mask, lifting acceptance per accepted-path token above 0.85. The third drops the feature-matching loss, trains on direct token prediction, and feeds the draft its own previous outputs during training, which removes exposure bias and reaches 0.88 to 0.92.

The progression.

Generation Draft Acceptance Training cost
Separate small model an independently trained smaller model 0.55 to 0.70 none
Extra heads on the verifier several output heads predicting positions ahead 0.65 to 0.75 about 1B supervised tokens
First hidden-state draft one transformer layer on the verifier's last hidden state 0.70 to 0.80 about 60B tokens
Dynamic draft tree the same plus a tree of candidates 0.80 to 0.88 about 60B tokens
Multi-layer features plus training-time test fuses several verifier layers; trained on its own outputs 0.88 to 0.92 about 60 to 200B tokens

Why the hidden state helps.

A separate draft re-derives from raw tokens what the verifier has already computed. The verifier's last hidden state at position t is a rich summary of the prefix, and a tiny network that reads it predicts the verifier's next token far better than a small model that reads only the token ids. The draft becomes a reader of the verifier instead of an imitation of it.

What the tree adds.

A linear chain of drafts dies at the first miss. A tree proposes several candidates at each depth, grows wider where the draft is uncertain and stays narrow where it is confident, and the verifier scores every node in one forward pass with a mask that lets each node attend only to its ancestors. The longest accepted path wins. Verification cost barely moves, because it is still one forward pass.

What the third generation fixes.

The earlier hidden-state drafts were trained to match the verifier's features, which capped how much extra data could help. The third generation trains on token prediction directly, and during training it feeds the draft its own previous predictions over several steps, the way it runs at inference. That aligns the training inputs with the inference inputs and stops error accumulation, the same fix that scheduled sampling gave sequence models. The paper reports up to 6.5 times end-to-end on chat and a 38 percent throughput gain at a batch of 64 on a production engine.

The draft is only as good as its traffic.

A general-purpose draft head trained on chat data drops to 0.4 to 0.6 acceptance on code, medical or legal traffic. A domain-specific head recovers it, and training one is a light job next to fine-tuning the verifier.

Plausible wrong answers.

  • "A larger separate draft model is the main lever." Alignment with the verifier matters more than size; a one-layer draft on hidden states beats a far larger independent model.
  • "The hidden-state draft changes the verifier's output distribution to gain acceptance." The rejection rule keeps the output exact; the draft only changes how often it is right.
  • "A tree needs one verifier pass per branch." All branches are verified in one pass under the tree mask.

Follow-ups an interviewer may ask.

  • (level 3) Why did matching the verifier's features cap the first generations? Expected: the feature loss asks the draft to reproduce hidden states rather than predict tokens, so more training data stopped helping; the third generation trains on tokens.
  • (level 3) What is exposure bias in this setting? Expected: the draft was trained on teacher-forced verifier inputs and run on its own outputs; the mismatch compounds over the draft steps.
  • (level 4) What does the tree cost? Expected: a non-causal attention mask that follows the tree topology, extra stored keys and values for the tree nodes, and scheduler complexity; the verifier still runs once.
  • (level 4) How do you compare the extra-heads design with the hidden-state draft? Expected: no second model to deploy and simpler serving, against a somewhat lower acceptance and a supervised fine-tuning stage on the verifier.
