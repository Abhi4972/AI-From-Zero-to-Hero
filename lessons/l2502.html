Why this came about

A neural network needs a fixed list of symbols, each with its own row in the embedding table (Lesson 3.19). Early systems used whole words, but any word not seen in training (a new product name, a typo, "deliveries" when only "delivery" was seen) became an unknown symbol. Characters avoid that but make sequences very long. In 2016 Rico Sennrich and colleagues adapted an old data-compression trick from 1994, byte-pair encoding, to learn a vocabulary of word pieces: common words become one token, rare words are spelled out from smaller pieces. OpenAI's GPT-2 (2019) applied it to raw bytes, so any text in any language can be encoded. Variants of this scheme are used by almost every language model today.

In plain words first
Building a vocabulary of handy pieces

Imagine writing messages using a box of rubber stamps. With only single-letter stamps you can write anything, but slowly. With a stamp for every whole word, you write fast but you need millions of stamps and still lack one for a new word. The practical answer: single letters, plus stamps for the most useful pieces, such as "the", "ing", " delivery", " customer". BPE decides which pieces deserve a stamp by finding the pairs of pieces that appear next to each other most often, and gluing them into a new stamp, again and again.

Step 1 · Three ways to cut text

Unit Vocabulary size Sequence length New or rare words
Characters (or bytes) tiny (about 256 bytes) very long, which costs compute (Lesson 7.18) always fine
Words huge (millions, with names and typos) short fail: "unknown word"
Subwords chosen: 50,000 to 200,000 moderate (about 4 characters per token in English) spelled from pieces

Subwords give most of the benefit of both. Common words are single tokens; rare words are split into a few known pieces; and in the worst case, any text can still fall back to single bytes.

Step 2 · Text is stored as bytes

Computers store text as bytes (numbers from 0 to 255) using the UTF-8 encoding. English letters take one byte each; accented letters, other scripts and emoji take two to four:

for s in ["order", "café", "नमस्ते", "📦"]:
    b = s.encode("utf-8")
    print(f"{s!r:<10} {len(s)} characters -> {len(b):>2} bytes: {list(b)}")
What you should see
'order'    5 characters ->  5 bytes: [111, 114, 100, 101, 114]
'café'     4 characters ->  5 bytes: [99, 97, 102, 195, 169]
'नमस्ते'   6 characters -> 18 bytes: [224, 164, 168, 224, 164, 174, 224, 164, 184, 224, 165, 141, 224, 164, 164, 224, 165, 135]
'📦'        1 characters ->  4 bytes: [240, 159, 147, 166]

The Hindi word for "hello" has 6 characters (letters and vowel signs) but 18 bytes, three bytes each. A tokeniser that starts from bytes, as GPT-2 and its successors do, can encode any text at all, but scripts that need more bytes start out at a disadvantage unless the tokeniser learned good merges for them (Step 5).

Step 3 · Byte-pair encoding from scratch

The training algorithm is short:

  1. Split the training text into words, each keeping the space in front of it (" courier"), so that pieces never cross word boundaries.
  2. Start with every word as a list of single characters.
  3. Count every pair of neighbouring tokens inside words. Merge the most frequent pair into a new token everywhere.
  4. Repeat for as many merges as you want. The list of merges, in order, is the tokeniser.

Try it first:

Now in code, on the same training text:

import re
from collections import Counter

text = ("the courier took the parcel to the customer. the customer was out, so the courier left the parcel "
        "with the neighbour. then the customer called to thank the courier, and the courier thanked the customer. "
        "the other parcels went out the next morning.")

def split_words(s):
    """Words keep the space in front of them; punctuation becomes its own piece."""
    return re.findall(r" ?[a-z]+| ?[^a-z ]+", s)

words = [list(w) for w in split_words(text)]       # each word starts as a list of characters
print(len(words), "words, e.g.", split_words(text)[:6])

def count_pairs(words):
    counts = Counter()
    for w in words:
        counts.update(zip(w, w[1:]))                # neighbouring pairs inside each word
    return counts

def merge_word(w, pair):
    """Replace every occurrence of the pair in one word with the merged token."""
    out, i = [], 0
    while i < len(w):
        if i < len(w) - 1 and (w[i], w[i + 1]) == pair:
            out.append(w[i] + w[i + 1])
            i += 2
        else:
            out.append(w[i])
            i += 1
    return out

merges = []
for step in range(1, 31):
    pair, n = count_pairs(words).most_common(1)[0]   # the most frequent pair
    words = [merge_word(w, pair) for w in words]
    merges.append(pair)
    if step <= 8 or step % 10 == 0:
        total = sum(len(w) for w in words)
        print(f"merge {step:>2}: {pair[0]!r:>8} + {pair[1]!r:<6} -> {pair[0] + pair[1]!r:<10} seen {n:>2} times, text is now {total} tokens")
What you should see
49 words, e.g. ['the', ' courier', ' took', ' the', ' parcel', ' to']
merge  1:      't' + 'h'    -> 'th'       seen 18 times, text is now 229 tokens
merge  2:     'th' + 'e'    -> 'the'      seen 15 times, text is now 214 tokens
merge  3:      ' ' + 'the'  -> ' the'     seen 13 times, text is now 201 tokens
merge  4:      ' ' + 'c'    -> ' c'       seen  9 times, text is now 192 tokens
merge  5:      'e' + 'r'    -> 'er'       seen  8 times, text is now 184 tokens
merge  6:      'o' + 'u'    -> 'ou'       seen  7 times, text is now 177 tokens
merge  7:      't' + 'o'    -> 'to'       seen  7 times, text is now 170 tokens
merge  8:     'ou' + 'r'    -> 'our'      seen  5 times, text is now 165 tokens
merge 10:  ' cour' + 'i'    -> ' couri'   seen  4 times, text is now 157 tokens
merge 20:    ' pa' + 'r'    -> ' par'     seen  3 times, text is now 121 tokens
merge 30:     ' n' + 'e'    -> ' ne'      seen  2 times, text is now 96 tokens
Reading this output
  • The first merges glue the most common pairs: "t" + "h", then "th" + "e", then " " + "the". After three merges, the most frequent word in the text, " the", is a single token.
  • Each merge shrinks the text: from 247 characters to 96 tokens after 30 merges. Real tokenisers are trained on billions of words and do 50,000 to 200,000 merges.
  • Counter.update(zip(w, w[1:])) counts pairs: zip(w, w[1:]) pairs every element with the next one. most_common(1) returns the top pair and its count; ties go to the pair seen first, which makes the result repeatable.
  • !r in an f-string prints a value with quotes, so you can see the spaces inside tokens.

To encode new text, split it into words and apply the learned merges in the order they were learned:

def encode(s):
    tokens = []
    for w in split_words(s):
        pieces = list(w)
        for pair in merges:
            pieces = merge_word(pieces, pair)
        tokens += pieces
    return tokens

for s in ["the customer thanked the courier", " thermometer", "parcels", " parcels"]:
    print(f"{s!r:<36} -> {encode(s)}")
What you should see
'the customer thanked the courier'   -> ['the', ' customer', ' ', 'th', 'an', 'k', 'e', 'd', ' the', ' courier']
' thermometer'                       -> [' the', 'r', 'm', 'o', 'm', 'e', 't', 'er']
'parcels'                            -> ['p', 'a', 'r', 'c', 'e', 'l', 's']
' parcels'                           -> [' parcel', 's']
Reading this output
  • Words that were common in training ("the", " customer", " courier") come out as single tokens. "thanked" appeared only once, so it is spelled out in small pieces.
  • " thermometer" was never seen, yet it is encoded fine, from the pieces " the", "r", "m" and so on. There is no "unknown word".
  • "parcels" and " parcels" are encoded differently: the learned pieces include a leading space (" par", " parcel"), so the same word without a space in front uses different, smaller pieces. Real tokenisers behave the same way, which is why a stray space at the end of a prompt can subtly change a model's output.

Finally, each token gets an ID number, the row it will use in the embedding table:

vocab = sorted(set(text)) + ["".join(p) for p in merges]       # single characters first, then merges
token_to_id = {t: i for i, t in enumerate(vocab)}
ids = [token_to_id[t] for t in encode("the courier")]
print("vocabulary size:", len(vocab))
print("ids:", ids, "-> decoded:", "".join(vocab[i] for i in ids))
What you should see
vocabulary size: 54
ids: [25, 34] -> decoded: the courier

Decoding is just looking the IDs up and joining the pieces. Real tokenisers work on bytes rather than characters (so they need the 256 byte values as their starting vocabulary), use a more careful pre-splitting rule, and add a few special tokens such as <|endoftext|> that mark boundaries between documents or chat messages (Lesson 10.36). Otherwise this is the algorithm.

Step 4 · Real tokenisers

tiktoken is OpenAI's tokeniser library. It includes the GPT-2 tokeniser (50,257 tokens), cl100k_base (about 100,000, used by GPT-3.5 and GPT-4) and o200k_base (about 200,000, used by GPT-4o and later OpenAI models). Other model families ship their own tokenisers, but they work the same way.

Reading this output

Byte-pair encoding (BPE) Start from bytes; repeatedly merge the most frequent neighbouring pair (Step 3) GPT models, Llama, Mistral, Qwen, most recent language models A word-initial space is part of the token, shown as Ġ or a leading space
WordPiece Like BPE, but each merge is chosen to raise the likelihood of the training text most BERTlater · 7.22 and its relatives, many embedding modelslater · 7.22 and rerankerslater · 5.38 Pieces inside a word start with ##, as in refund, ##able
Unigram (in the SentencePiece library) Start from a large candidate vocabulary and prune it, keeping the pieces that explain the text best T5, Gemma, many multilingual and speech models Treats text as a raw stream with no pre-splitting on spaces, which suits languages such as Japanese, Chinese and Thai; a word-initial space is shown as ▁

All three give subword tokens and behave alike in use. What you must remember is that a tokeniser belongs to its model: the same text gives different ids, and a different number of tokens, under each one. Always count tokens with the tokeniser of the model you will call.

import tiktoken

encoders = {name: tiktoken.get_encoding(name) for name in ["gpt2", "cl100k_base", "o200k_base"]}
for name, enc in encoders.items():
    print(f"{name:<12} vocabulary {enc.n_vocab:,}")

enc = encoders["o200k_base"]
ids = enc.encode("Where is my order?")
print(ids)
print([enc.decode([i]) for i in ids])

Reading this output
  • Ordinary English is cheap: about one token per word, plus punctuation.
  • " strawberry" is a single token. The model never sees the letters inside it, only one ID, which is why models used to miscount the letter r in it: the information has to be learned indirectly.
  • Numbers are cut into chunks of up to three digits, and not aligned to place value ("123", "456", "78"). Arithmetic on long numbers is harder for a model than it looks, which is one reason agents call a calculator tool instead (the Agents from first principles section).
  • Hindi in Latin letters ("Mera order kab aayega?") is split into odd pieces, because there was less of it in the training data.
  • Hindi in Devanagari costs GPT-2 29 tokens, many of them partial bytes (shown as �), but only 8 with o200k_base, whose larger vocabulary learned pieces for many more languages. The same sentence can cost several times as much, and use up the context windowlater · 10.42 several times faster, depending on the tokeniser and language.

Step 5 · Why tokens matter in practice

Tokens are the unit of everything you pay for and every limit you hit: price is per token, the context window is counted in tokens, and speed is tokens per second. So it is useful to know roughly how many tokens a piece of ordinary text is. Count them for a typical customer message:

paragraph = ("Your order SK-48213 has been dispatched and will arrive by Friday. If you are not at home, "
             "the courier will leave the parcel with a neighbour or at the nearest pickup point.")
n_words = len(paragraph.split())
n_tokens = len(encoders["o200k_base"].encode(paragraph))
print(f"{n_words} words, {n_tokens} tokens, {n_tokens / n_words:.2f} tokens per word, {len(paragraph) / n_tokens:.1f} characters per token")
What you should see
32 words, 38 tokens, 1.19 tokens per word, 4.6 characters per token
Where tokens show up Why
Price APIs charge per input and output token (Lesson 10.42)
Context window the limit on how much text a model can take is in tokens, not words or pages
Speed the model generates one token at a time (Lesson 0.15), so long answers take longer
Quirks letters inside a token are invisible; numbers are chunked; trailing spaces change the split
Fairness languages with poorer tokenisation pay more for the same content

A useful rule of thumb for English: one token is about three-quarters of a word, or about four characters. Always measure with the model's own tokeniser when it matters.

The same idea as a formula
  • BPE training: repeat k times: (a, b) = argmax over pairs of count(a, b); replace every adjacent a, b with the new token ab
  • vocabulary size = base symbols (256 bytes) + number of merges + special tokens
  • compression ratio = characters (or bytes) ÷ tokens; about 4 characters per token for English with modern tokenisers
Check your mental model
  • ✗ "A language model reads words."
    ✓ It reads token IDs. Common words are single tokens; others are several pieces, and the model never sees the letters inside a token directly.
  • ✗ "Bigger vocabularies are always better."
    ✓ They shorten sequences (cheaper, more fits in context) but add rows to the embedding and output layers (Lesson 3.19) and make rare tokens harder to learn. Vocabulary size is a trade-off.
  • ✗ "A tokeniser has to be trained together with the model."
    ✓ It is trained separately, before the model, by counting pairs in text. The model then learns an embedding for each token ID.

Exercises

Predict before you run

With the 30 merges learned in Step 3, how many tokens will encode("the courier thanked the customer") produce? (Solution P1.)

Make it your own

Increase the number of merges in Step 3 from 30 to 80. Merging stops being useful once every pair occurs only once, so add a check that stops the loop when the top count is 1. What do the last merges look like, and why are they less useful? (Solution M1.)

Practice
Apply it

Use encoders["o200k_base"] to count the tokens in a paragraph you wrote recently, in English and, if you can, in another language you know. Compute tokens per word for each. (Solution X1.)

Solutions

SolutionP1 · Counting tokens

10 tokens: ['the', ' courier', ' ', 'th', 'an', 'k', 'e', 'd', ' the', ' customer']. "the", " courier", " the" and " customer" are single tokens; " thanked" falls apart into six pieces because " thanked" appears only once in the training text (and " thank" once more), too rarely for its pieces to be merged within 30 steps.

SolutionM1 · More merges

Add if n < 2: break after finding the top pair. With this small text, the loop stops at step 34: after 33 merges, no pair appears twice any more. The last merges glue pieces that appear exactly twice, such as ' ' + 'th', ' th' + 'an' and ' than' + 'k', building up the rare word " thanked", which will rarely help on new text. Real tokenisers face the same diminishing returns, which is one reason vocabularies stop at 50,000 to 200,000.

SolutionX1 · Your own text

For English you should see about 1.2 to 1.4 tokens per word. Many other languages, especially those written in non-Latin scripts, use more tokens per word, though modern tokenisers such as o200k_base have narrowed the gap considerably. When you build for users in several languages, measure token counts in each before estimating cost.

Recap
  • Language models read token IDs; tokens are usually subwords, a compromise between characters (long sequences) and words (huge vocabulary, unknown words).
  • Text is stored as UTF-8 bytes; starting from bytes means any text can be encoded.
  • BPE learns a vocabulary by repeatedly merging the most frequent neighbouring pair; the ordered list of merges is the tokeniser.
  • Real tokenisers (GPT-2, cl100k_base, o200k_base) have 50,000 to 200,000 tokens; English averages about four characters per token.
  • Tokens explain prices, context limits and quirks such as letter counting, chunked numbers and higher costs for some languages.
