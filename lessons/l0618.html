The failing services are plain functions that raise on purpose. Retries, timeouts, handlers and caching are the real LangGraph features.

import asyncio
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import RetryPolicy, CachePolicy, Command
from langgraph.errors import NodeError

class Refund(TypedDict, total=False):
    order_id: str
    amount: int
    status: str
    log: list
Why this came about

Agents in production met flaky APIs, slow tools and partial failures. LangGraph added declarative retries, timeouts, error handlers and caching per node, bringing reliability patterns from distributed systems into the graph.

The problem: one flaky service fails the whole run

ShopKart's refund workflow calls a payment service that fails now and then, an order service that sometimes hangs, and a courier API that can be down for an hour. In Lesson 3.4 you wrote retry loops with backoff, deadlines and an idempotency key around each call. In a LangGraph graph, each of those is a setting on a node, so the policy is visible in the graph definition and applied the same way every time.

In plain words first
Plans for when things go wrong

Every outside service fails sometimes. Each failure needs its own response, the way a careful person handles a bad phone line: retry if the line dropped, wait a little longer each time; hang up after a timeout; when retries run out, an error handler does something sensible instead of crashing; a saga undoes steps already done when a later step fails; a cache avoids paying twice for the same work; and a graceful ending stops before a step limit with the best answer so far.

Idea 1 · Retry the errors a retry can fix

A RetryPolicy attached to a node tells LangGraph to run the node again when it raises one of the listed errors, waiting a little longer each time. The node below fails twice with a connection error and then succeeds, so the policy has something to do:

attempts = {"n": 0}

def call_payments(state):
    attempts["n"] += 1
    if attempts["n"] < 3:
        raise ConnectionError("payment service unavailable")          # fails twice, then works
    return {"status": f"refund of INR {state['amount']:,} sent"}

fast_retry = RetryPolicy(max_attempts=4, initial_interval=0.01, backoff_factor=2.0, jitter=False,
                         retry_on=ConnectionError)                     # only errors a retry can fix
graph = (StateGraph(Refund)
         .add_node("call_payments", call_payments, retry_policy=fast_retry)
         .add_edge(START, "call_payments").add_edge("call_payments", END).compile())

print(graph.invoke({"order_id": "A-1077", "amount": 7999}), "| attempts:", attempts["n"])
What you should see
{'order_id': 'A-1077', 'amount': 7999, 'status': 'refund of INR 7,999 sent'} | attempts: 3

The node failed twice with a ConnectionError, and LangGraph ran it again after a short wait each time (initial_interval, multiplied by backoff_factor after each failure, capped by max_interval; jitter adds randomness so many runs do not retry at the same moment). The third attempt succeeded. The important argument is retry_on: a dropped connection may work a second later, but a bad request never will. By default LangGraph retries most exceptions except obvious programming errors; be explicit for anything with side effects.

Idea 2 · When retries run out: an error handler

Some failures will not pass however often you retry. For those, a node can name an error handler: a function that receives the state and the error, and returns a Command that updates the state and chooses where the run goes next. Here a rejected payment routes to a node that tells the customer, and the run finishes normally:

def charge_back(state):
    raise RuntimeError("payment gateway rejected the request")

def on_payment_failure(state, error: NodeError) -> Command:
    return Command(update={"status": f"{error.node} failed ({type(error.error).__name__}); customer told, ticket opened"},
                   goto="notify")

def notify(state):
    return {"log": [f"notified customer: {state['status']}"]}

graph = (StateGraph(Refund)
         .add_node("charge_back", charge_back, retry_policy=fast_retry, error_handler=on_payment_failure)
         .add_node("notify", notify)
         .add_edge(START, "charge_back").add_edge("notify", END).compile())
print(graph.invoke({"order_id": "A-1077", "amount": 7999}))
What you should see
{'order_id': 'A-1077', 'amount': 7999, 'status': 'charge_back failed (RuntimeError); customer told, ticket opened', 'log': ['notified customer: charge_back failed (RuntimeError); customer told, ticket opened']}

A RuntimeError is not in retry_on, so there was no retry; the error handler received the state and a NodeError (which node failed, and the exception), and returned a Command that recorded what happened and moved on to notify. The run finished with a useful state instead of an exception. Handlers are where you decide between "tell the customer", "try another route" and "park it for a person".

Idea 3 · Timeouts, and why sync nodes cannot have them

A hanging service is worse than a failing one: the run waits forever. Try a timeout on an ordinary function:

import time

def slow_lookup(state):
    time.sleep(2)
    return {"status": "found"}

try:
    StateGraph(Refund).add_node("slow_lookup", slow_lookup, timeout=0.1).add_edge(START, "slow_lookup").compile()
except ValueError as e:
    print("ValueError:", str(e).split(" because")[0])
What you should see
ValueError: Node timeouts are only supported for async nodes

LangGraph refuses at compile time, because Python cannot safely stop a running synchronous function from the outside. Make the node async, and the timeout works, with the same error handler mechanism:

async def slow_lookup(state):
    await asyncio.sleep(2)                                  # an order service that hangs
    return {"status": "found"}

def on_timeout(state, error: NodeError) -> Command:
    return Command(update={"status": f"lookup timed out ({type(error.error).__name__}); try again later"}, goto=END)

graph = (StateGraph(Refund)
         .add_node("slow_lookup", slow_lookup, timeout=0.2, error_handler=on_timeout)
         .add_edge(START, "slow_lookup").add_edge("slow_lookup", END).compile())
print(asyncio.run(graph.ainvoke({"order_id": "A-1077"})))
What you should see
{'order_id': 'A-1077', 'status': 'lookup timed out (NodeTimeoutError); try again later'}

For synchronous code, set a timeout on the client inside the node instead (the HTTP library's or the SDK's timeout), so the call itself gives up.

Idea 4 · The saga: undo what already happened

A return takes three steps: reserve a pickup slot, send the refund, book the courier. If the courier fails after the refund was sent, stopping is the worst outcome: money gone, nothing collected. A saga gives the failing step a handler that runs compensating actions for the steps before it, in reverse order:

done = []
def reserve_return_slot(s): done.append("slot reserved");     return {"log": ["slot R-1"]}
def refund_payment(s):      done.append("refund sent");       return {"log": ["refund RF-1"]}
def book_pickup(s):         raise ConnectionError("courier API down")

def undo_everything(state, error: NodeError) -> Command:
    undone = [f"undo: {step}" for step in reversed(done)]  # compensate in reverse order
    return Command(update={"status": "return cancelled, refund reversed", "log": undone}, goto=END)

import operator
from typing import Annotated
class Saga(TypedDict, total=False):
    status: str
    log: Annotated[list, operator.add]

graph = (StateGraph(Saga)
         .add_node("reserve_return_slot", reserve_return_slot)
         .add_node("refund_payment", refund_payment)
         .add_node("book_pickup", book_pickup, retry_policy=RetryPolicy(max_attempts=2, initial_interval=0.01, jitter=False),
                   error_handler=undo_everything)
         .add_edge(START, "reserve_return_slot").add_edge("reserve_return_slot", "refund_payment")
         .add_edge("refund_payment", "book_pickup").add_edge("book_pickup", END).compile())
out = graph.invoke({"log": []})
print(out["status"]); print(out["log"])
What you should see
return cancelled, refund reversed
['slot R-1', 'refund RF-1', 'undo: refund sent', 'undo: slot reserved']

Each compensation must itself be safe to repeat (Lesson 3.4's idempotency), because a crash during the undo will run it again on resume (Lesson 6.12).

Idea 5 · Cache expensive nodes

If a node is expensive and gives the same answer for the same input, give it a CachePolicy. LangGraph then stores the node's result, keyed by its input, and skips the node while the entry is fresh. The list lookups records every real execution, so you can count how many calls the cache saved:

from langgraph.cache.memory import InMemoryCache

lookups = []
def policy_lookup(state):
    lookups.append(state["order_id"])                       # an expensive call: a search or a model
    return {"status": f"policy for {state['order_id']}: refundable"}

graph = (StateGraph(Refund)
         .add_node("policy_lookup", policy_lookup, cache_policy=CachePolicy(ttl=300))
         .add_edge(START, "policy_lookup").add_edge("policy_lookup", END)
         .compile(cache=InMemoryCache()))
for oid in ["A-1077", "A-1077", "A-1078", "A-1077"]:
    graph.invoke({"order_id": oid})
print("node ran for:", lookups)
What you should see
node ran for: ['A-1077', 'A-1078']

Four runs, two node executions: the second and fourth runs for A-1077 reused the cached result, keyed by the node's input. ttl (seconds) sets how long a result stays valid; pass a key_func to choose what the key is built from. Cache only nodes whose output depends on their input alone, such as a policy lookup or a classification, never one with side effects.

Idea 6 · End gracefully before the recursion limit

The recursion limit (Lesson 6.11) stops a runaway loop with an exception. Sometimes you would rather wrap up with the best answer so far. A RemainingSteps key is a managed value: LangGraph fills it with the number of steps left, and a router can act on it:

from langgraph.managed import RemainingSteps

class Search(TypedDict, total=False):
    tries: int
    answer: str
    remaining_steps: RemainingSteps                         # filled in by LangGraph, never by your nodes

def search(state):
    return {"tries": state.get("tries", 0) + 1}             # never finds anything, to show the ending

def route(state):
    if state["remaining_steps"] <= 2:                       # nearly out of steps: wrap up instead of crashing
        return "best_effort"
    return "search"

def best_effort(state):
    return {"answer": f"I could not confirm this after {state['tries']} searches; a colleague will follow up."}

graph = (StateGraph(Search).add_node("search", search).add_node("best_effort", best_effort)
         .add_edge(START, "search").add_conditional_edges("search", route, ["search", "best_effort"])
         .add_edge("best_effort", END).compile())
print(graph.invoke({}, {"recursion_limit": 8}))
What you should see
{'tries': 6, 'answer': 'I could not confirm this after 6 searches; a colleague will follow up.'}

With a limit of 8, the loop searched six times and then ended with an honest message rather than a GraphRecursionError.

Idea 7 · Long work: idle timeouts and heartbeats

A hard timeout is the wrong tool for work that is slow but healthy, such as exporting thousands of orders. LangGraph 1.2 adds TimeoutPolicy with two limits: run_timeout, a hard cap that never resets, and idle_timeout, which resets every time the node shows progress. Writes, stream output and callbacks count as progress, and a node can say so itself with runtime.heartbeat():

from langgraph.types import TimeoutPolicy
from langgraph.runtime import Runtime
from langgraph.errors import NodeTimeoutError

async def export_orders(state, runtime: Runtime):
    for chunk in range(4):                       # long work that reports progress
        await asyncio.sleep(0.15)
        runtime.heartbeat()                      # "still alive": resets the idle timer
    await asyncio.sleep(5)                       # then it hangs, with no heartbeat
    return {"status": "exported"}

graph = (StateGraph(Refund)
         .add_node("export_orders", export_orders, timeout=TimeoutPolicy(idle_timeout=0.4, run_timeout=3))
         .add_edge(START, "export_orders").compile())
try:
    asyncio.run(graph.ainvoke({"order_id": "batch-7"}))
except NodeTimeoutError as e:
    print("NodeTimeoutError:", str(e).split(" (elapsed")[0])
What you should see
NodeTimeoutError: Node 'export_orders' exceeded its idle timeout of 0.400s without making progress

Four chunks of 0.15 seconds each passed, because every heartbeat reset the 0.4-second idle timer; the hang after them was caught 0.4 seconds later, long before the 3-second hard cap. A NodeTimeoutError goes to the retry policy and then to the error handler like any other failure. Use refresh_on="heartbeat" in the policy when only your own heartbeats should count as progress.

Idea 8 · Stop cleanly for a deploy: drain

A deploy sends your process a shutdown signal while runs are in the middle of their work. Killing them leaves each run wherever it was. LangGraph 1.2 lets a run stop at the next superstep boundary instead: pass a RunControl to the run, and call request_drain() from your shutdown handler. The run saves a checkpoint, raises GraphDrained, and resumes later from exactly that point:

import operator
from typing import Annotated
from langgraph.runtime import RunControl
from langgraph.errors import GraphDrained
from langgraph.checkpoint.memory import InMemorySaver

def step(name):
    async def node(state):
        await asyncio.sleep(0.2)
        return {"log": [name]}
    return node

class Nightly(TypedDict, total=False):
    log: Annotated[list, operator.add]

saver = InMemorySaver()
nightly = (StateGraph(Nightly).add_node("fetch", step("fetch")).add_node("reconcile", step("reconcile"))
           .add_node("report", step("report")).add_edge(START, "fetch").add_edge("fetch", "reconcile")
           .add_edge("reconcile", "report").add_edge("report", END).compile(checkpointer=saver))
cfg = {"configurable": {"thread_id": "nightly-2026-11-22"}}

async def main():
    control = RunControl()
    asyncio.get_running_loop().call_later(0.3, control.request_drain, "deploy")   # a SIGTERM handler would do this
    try:
        await nightly.ainvoke({"log": []}, cfg, control=control)
    except GraphDrained as e:
        state = nightly.get_state(cfg)
        print("GraphDrained:", e.reason, "| saved:", state.values["log"], "| next:", state.next)
    out = await nightly.ainvoke(None, cfg)               # after the deploy, on any worker
    print("resumed:", out["log"])

asyncio.run(main())
What you should see
GraphDrained: deploy | saved: ['fetch', 'reconcile'] | next: ('report',)
resumed: ['fetch', 'reconcile', 'report']

The drain was requested while reconcile was running. LangGraph let that step finish, saved the checkpoint, and stopped before report. The resumed run, which in production starts on a new worker after the deploy, ran only report. Drain needs a checkpointer, and it waits for the current step, so give nodes timeouts shorter than your platform's shutdown grace period.

In production
Reliability in production
  • Retry stormslater · 12.7: retries multiply across layers. A model client retrying 6 times inside a node retrying 3 times inside middleware retrying 2 times makes 36 calls for one failure. Retry in one layer, usually the outermost that knows whether the step is safe to repeat.
  • Graceful shutdown: on deploys, stop taking new runs and call request_drain() on every running run, so each stops at a step boundary with a checkpoint; resume them on the new workers (Lesson 12.8).
  • Bulkheads: cap parallel work per run (max_concurrency in config) and rate-limit model calls so one big job cannot use the whole provider quota.
  • Dead-letter queues: unrecoverable runs must be recorded with their thread ID, so a person can fix the cause and re-run from the last checkpoint (the modify exercise). Alert on the queue's growth.

Debugging exercise: one bad refund, four attempts

sent = []

Make it your own

Solutions

SolutionP1 · Backoff adds up

0.01 + 0.02 = 0.03 seconds before the third attempt. With the defaults, 0.5 + 1.0 = 1.5 seconds; a fourth attempt would wait another 2 seconds. Long backoffs keep a run (and its worker) busy, so for waits of minutes, end the run and resume it later instead (Lesson 6.12).

SolutionB1 · Synchronous code cannot be cancelled safely

A synchronous Python function cannot be interrupted from outside without risking corrupted state, so LangGraph cannot honor a timeout on it, and it says so when the graph is built rather than letting you believe the node is protected. Make the node async, or put the timeout on the client the node calls.

SolutionD1 · Retry only what a retry can fix

retry_on=Exception retried a validation error that will fail every time, so the node ran four times, and every side effect before the error ran four times too (here sent recorded four sends). Retry only transient errors:

sent.clear()
graph = (StateGraph(Refund).add_node("send_refund", send_refund, retry_policy=fast_retry)   # ConnectionError only
         .add_edge(START, "send_refund").add_edge("send_refund", END).compile())
try:
    graph.invoke({"order_id": "A-1077", "amount": 0})
except ValueError as e:
    print("ValueError:", e)
print("send_refund ran", len(sent), "time")

ValueError: refund amount must be positive
send_refund ran 1 time
SolutionM1 · A dead-letter queue for every node
dead_letters = []

def to_dead_letter(state, error: NodeError) -> Command:
    dead_letters.append({"node": error.node, "error": repr(error.error)[:80], "order_id": state.get("order_id")})
    return Command(update={"status": "parked for a person to re-run"}, goto=END)

def always_down(state):
    raise ConnectionError("ledger unavailable")

builder = StateGraph(Refund).set_node_defaults(retry_policy=fast_retry, error_handler=to_dead_letter)  # every node
graph = builder.add_node("record", always_down).add_edge(START, "record").add_edge("record", END).compile()
print(graph.invoke({"order_id": "A-1080"}))
print(dead_letters)

{'order_id': 'A-1080', 'status': 'parked for a person to re-run'}
[{'node': 'record', 'error': "ConnectionError('ledger unavailable')", 'order_id': 'A-1080'}]

set_node_defaults applies the policy and the handler to every node unless a node sets its own. In production, write the dead letter to a table with the thread ID, so a fix can be followed by resuming the run from the checkpoint before the failed node.

Check your understanding

Explain the mechanismHow do you make a LangGraph workflow resilient to failing services?

Worked answer. Per node: a RetryPolicy with backoff, jitter and an explicit retry_on list of transient errors; timeouts on async nodes or on clients; an error handler that returns a Command to recover, notify, compensate or park the run; caching for expensive pure nodes. Across the graph: checkpoints so runs resume after crashes, RemainingSteps or limits so loops end gracefully, idempotent side effects so retries and resumes are safe, and a dead-letter queue for runs nothing can fix.

A plausible wrong answer. "Wrap the whole invoke in a try/except and retry it." That repeats completed steps and their side effects.

Follow-ups. When would you use a saga instead of a retry?

Debug a failureA provider outage turned into a 40-times spike in requests to that provider. Why?

Worked answer. Retries at several layers multiplied: the SDK's own retries, a node RetryPolicy, and middleware or application retries. Keep retries in one layer, use backoff with jitter, add a circuit breaker that stops calling a failing provider for a while (Lesson 3.4), and fall back or fail fast when it is open.

A plausible wrong answer. "Increase max_attempts so more requests succeed." That makes the storm bigger.

Follow-ups. Which layer should own retries in a LangGraph agent?

Defend a designError handlers in the graph, or exceptions handled by the caller?

Worked answer. In the graph when recovery is part of the business process: notifying the customer, compensating earlier steps, routing to a person. The decision is then checkpointed and visible in traces. Leave to the caller only failures the graph cannot handle meaningfully, such as configuration errors, which should fail loudly.

A plausible wrong answer. "Never let a graph fail; handle everything." Hiding bugs as handled states makes them harder to find.

Follow-ups. How would you test an error handler?

Check yourself

  • Add a RetryPolicy that retries only connection errors, and show it working.
  • Add a timeout to an async node and recover with an error handler.
  • Write a saga that undoes two steps when the third fails.
  • Cache a pure node, and end a loop with RemainingSteps.
