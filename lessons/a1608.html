In plain words first
The idea in one line

The most common multi-agent decomposition in 2026: one agent plans, one executes, one critiques or verifies. MetaGPT (arXiv:2308.00352) formalizes this as SOPs encoded into role prompts — Product Manager, Architect, Project Manager, Engineer, QA Engineer — following Code = SOP(Team). ChatDev (arXiv:2307.07924) chains designer, programmer, reviewer, tester through a "chat chain" with "communicative dehallucination" (agents explicitly request missing details). The verifier is load-bearing: Cemri et al. (MAST, arXiv:2503.13657) find task-verification failures in about a quarter of 1,642 failed multi-agent traces, and argue that stronger verification would catch many of the rest. A CrewAI case study reports PwC's code-generation accuracy rising from about 10% to over 70% after adding agents that generate, run and re-check code.

Terms you'll hear
Term What people say What it actually means
Role specialization "Different agents, different jobs" Distinct system prompts tuned for planner/executor/critic/verifier roles.
SOP pattern "Encoded standard operating procedure" MetaGPT's framing: strict I/O schemas per role turn a team into a pipeline.
Communicative dehallucination "Ask before inventing" ChatDev pattern: executor asks planner when a detail is missing rather than making one up.

Revision loop "Critic sends it back" Critic rejection triggers executor re-run with feedback. Needs a budget.

Problem

In plain words first

Role specialization gives each agent one job: a planner writes the spec, an executor does the work, a critic reviews it, and a verifier checks it by running something. Critics are models and can be fooled by work that looks right; verifiers run tests and cannot, as long as the tests are good. Multi-agent systems are introduced in Lesson 14.66 (linked above). This lesson throws wrong executors at the lesson's critic and verifier, then uses a small model as executor and critic with a real test runner.

Generic multi-agent systems produce generic output. Three coders in a group chat write three flavors of the same mediocre code. You can add more agents, add more rounds, and still not cross the quality threshold.

The fix is not more agents — it is different agents. Assign distinct roles. Give the critic tools the planner does not have. Give the verifier an objective test suite. Now the system has internal disagreement with grounded correction, not just parallel guessing.

Concept

The four canonical roles

Planner. Reads the goal, produces a step list or a spec. Tools: knowledge retrieval, docs. Output: structured plan.

Executor. Reads one plan step at a time, produces the artifact. Tools: the actual work tools (code compiler, shell, API client). Output: the artifact.

Critic. Reads the executor's output against the planner's intent. Tools: read-only access to the artifact, static analysis. Output: accept/reject with reasons.

Verifier. Reads the artifact and runs a deterministic check. Tools: test runner, type checker, schema validator. Output: pass/fail with evidence.

Critic is subjective, opinionated, often LLM-based. Verifier is objective, deterministic, often code-based. They are not the same role.

MetaGPT's SOP pattern

MetaGPT (arXiv:2308.00352) encodes software engineering SOPs as role prompts:

  • Product Manager writes the PRD.
  • Architect produces the system design.
  • Project Manager splits tasks.
  • Engineer implements.
  • QA Engineer runs tests.

Each role has a strict input/output schema. The role prompt says what the role is and what it must produce. The Code = SOP(Team) formulation — deterministic SOPs turn a team of LLMs into a predictable pipeline.

ChatDev's communicative dehallucination

ChatDev adds a key move: when an executor needs a specific detail that was not in the plan, it explicitly asks the designer before continuing. This prevents the classic LLM failure of plausibly inventing the detail.

Implementation: the role prompt includes "when you need specific information you were not given, ask the relevant role by name before producing output."

Why verifier matters most

Cemri et al. (MAST) annotated 1,642 failed multi-agent traces across 7 frameworks. About 23.5% fall under task verification: premature termination, missing or incomplete verification, and incorrect verification. The other categories, system design and inter-agent misalignment, often end in an answer that no one checked properly either.

A CrewAI-hosted case study (2025) reports PwC's code-generation accuracy moving from about 10% to over 70% once CrewAI agents that generate, run and repeatedly check code were added. The figures are self-reported and do not isolate the checking step, so treat them as an illustration, not a measurement.

Critic vs verifier

  • A critic is an LLM reviewing an artifact for quality. Subjective. Can be fooled by plausible prose.
  • A verifier is a deterministic program running on the artifact. Objective. Gives pass/fail with evidence.

Use both. Critic catches taste issues the verifier cannot articulate. Verifier catches bugs the critic cannot see because they show up only at runtime.

The anti-pattern

Every role in your system is an LLM and every role's output is "looks good to me." Classic MAST failure mode. Add at least one verifier whose pass/fail is decided by code, not by an LLM.

Framework mappings

  • CrewAI — Agent(role, goal, backstory) is the textbook specialization surface.
  • LangGraph — nodes can have specialized prompts; edges enforce the pipeline.
  • AutoGen — role-specific ConversableAgents with one-word names in a GroupChat.
  • OpenAI Agents SDK — handoff tools between role-specialized Agents.

The same idea as a formula

A check only catches what it tests. Let f be the intended function and g the executor's code. A verifier with test set T passes g if g(x)=f(x) for all x∈T. It can miss a bug only on inputs outside T, so a code that memorises T passes every time.

Hidden tests close that gap. Draw a second set H that the executor never sees. A bug that agrees with f on T but not everywhere is caught when some x∈H hits the disagreement; random inputs make that likely for most bugs.

Critic plus verifier. If the critic misses a bug with probability mc​ and the verifier with mv​, and they fail on different bugs, both miss with probability about mc​mv​. A critic that approves everything has mc​=1 and adds nothing.

Worked example
Checking one memorised answer

  • The lesson's critic finds def, return and the right name, so it approves.
  • The verifier runs the three tests: 3, 30 and 0, all right, so it passes.
  • Ten hidden random tests, such as add_two(23, -7), all return 0, so 10 of 10 fail and the bug is caught.

# is written to pass the spec's three tests. Then the same verifier with ten hidden tests the executor never saw.
# Deterministic; runs in under a second.
import random
from main import planner, critic, verifier, Artifact, Spec

spec = planner("A function that returns the sum of two integers.")
WRONG = {"multiplies": "def add_two(a, b):\n    return a * b\n",
         "off by one": "def add_two(a, b):\n    return a + b + 1\n",
         "drops negatives": "def add_two(a, b):\n    return abs(a) + abs(b)\n",
         "string concat": "def add_two(a, b):\n    return int(str(a) + str(b))\n",
         "memorises the tests": "def add_two(a, b):\n    return {(1, 2): 3, (10, 20): 30, (-5, 5): 0}.get((a, b), 0)\n"}
rng = random.Random(0)
hidden = Spec(spec.task_name, spec.signature, spec.description,
              [((a, b), a + b) for a, b in [(rng.randint(-50, 50), rng.randint(-50, 50)) for _ in range(10)]])
print(f"{'executor':<22} {'critic':<10} {'verifier (3 tests)':<20} hidden tests (10)")
for name, code in WRONG.items():
    art = Artifact(code)
    c, v, h = critic(spec, art), verifier(spec, art), verifier(hidden, art)
    print(f"{name:<22} {'approve' if c.approved else 'reject':<10} {'pass' if v.passed else f'fail {len(v.failures)}/3':<20} "
          f"{'pass' if h.passed else f'fail {len(h.failures)}/10'}")
print("\nthe critic approves all five; the spec's own tests miss one; tests the executor never saw catch all five")

# This block continues from the one above: real roles. Qwen2.5-0.5B-Instruct (greedy, CPU) is the executor, writing
# five small functions from one-line specs, and also the critic, asked whether each function is correct. The
# verifier runs each function against tests in a sandboxed subprocess with no network. About 2 minutes.
import json, os, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

SPECS = [("median(xs)", "Return the median of a non-empty list of numbers; for an even length, the mean of the two middle values.",
          [([3, 1, 2],), 2], [([4, 1, 3, 2],), 2.5], [([7],), 7]),
         ("is_leap(year)", "Return True if year is a leap year in the Gregorian calendar.",
          [(2024,), True], [(1900,), False], [(2000,), True], [(2023,), False]),
         ("clamp(x, lo, hi)", "Return x limited to the range lo..hi inclusive.", [(5, 0, 3), 3], [(-1, 0, 3), 0], [(2, 0, 3), 2]),
         ("word_count(s)", "Return the number of words in s, where words are separated by any whitespace.",
          [("a b  c",), 3], [("",), 0], [("  one\ttwo\n",), 2]),
         ("dedupe(xs)", "Return xs with duplicates removed, keeping the first occurrence order.",
          [([3, 1, 3, 2, 1],), [3, 1, 2]], [([],), []])]
def chat(prompt, n):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True, return_tensors="pt",
                                  return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True), ids
def run_tests(code, fname, tests):
    src = code + "\nimport json\nres=[]\n" + "".join(
        f"try: res.append({fname}(*{json.dumps(a) if not isinstance(a[0], str) else repr(a)}) == {e!r})\nexcept Exception: res.append(False)\n"
        for a, e in tests) + "print(json.dumps(res))\n"
    d = tempfile.mkdtemp()
    try:
        p = subprocess.run(["unshare", "-n", sys.executable, "-I", "-c", src], cwd=d, capture_output=True, text=True, timeout=20)
        return json.loads(p.stdout.strip() or "[]")
    except (subprocess.TimeoutExpired, json.JSONDecodeError):
        return []
rows, agree = [], 0
for sig, desc, *tests in SPECS:
    fname = sig.split("(")[0]
    text, _ = chat(f"Write the Python function {sig}. {desc} Reply with only the code in one ```python block.", 160)
    m = re.search(r"```(?:python)?\n(.*?)(?:```|$)", text, re.S)
    code = m.group(1) if m else text
    verdict, ids = chat(f"Specification: {sig}: {desc}\n\nCode:\n{code}\nIs this code correct? Answer yes or no.", 1)
    with torch.no_grad():
        logits = llm(ids).logits[0, -1]
    approve = (logits[tok("Yes")["input_ids"][0]] > logits[tok("No")["input_ids"][0]]).item()
    res = run_tests(code, fname, tests)
    passed = bool(res) and all(res)
    agree += approve == passed
    print(f"{sig:<18} critic {'approve' if approve else 'reject':<8} verifier {sum(res)}/{len(tests)} tests pass")
print(f"\ncritic and verifier agree on {agree}/5")

Build it

code/main.py implements a 4-role pipeline building a simple Python function:

  • Planner produces a spec.
  • Executor generates a code string.
  • Critic (LLM-simulated) flags obvious issues.
  • Verifier runs the generated code in a sandbox (exec) against a test case.

Demo runs twice: once where the executor produces correct code (critic + verifier both pass), once where the executor produces off-spec code (critic misses the bug because it looks plausible, verifier catches it because the test fails).

Run:

python3 code/main.py

Part 1 of 3 · Spec, Artifact, CriticReport, VerifierReport, planner, executor_correct, executor_buggy, critic

"""Role specialization: planner, executor, critic, verifier.

Builds a small Python function. Critic (LLM-simulated) and verifier (code)
together catch bugs that either alone would miss.

Run twice: once with correct executor output, once with off-spec output.
"""
from __future__ import annotations

from dataclasses import dataclass, field


@dataclass
class Spec:
    task_name: str
    signature: str
    description: str
    tests: list[tuple[tuple, int]]


@dataclass
class Artifact:
    code: str


@dataclass
class CriticReport:
    approved: bool
    notes: list[str] = field(default_factory=list)


@dataclass
class VerifierReport:
    passed: bool
    failures: list[str] = field(default_factory=list)


def planner(user_wish: str) -> Spec:
    """Produces a structured spec from a high-level wish."""
    return Spec(
        task_name="add_two",
        signature="add_two(a: int, b: int) -> int",
        description=user_wish,
        tests=[((1, 2), 3), ((10, 20), 30), ((-5, 5), 0)],
    )


def executor_correct(spec: Spec) -> Artifact:
    return Artifact(code="def add_two(a, b):\n    return a + b\n")


def executor_buggy(spec: Spec) -> Artifact:
    return Artifact(code="def add_two(a, b):\n    return a * b\n")


def critic(spec: Spec, art: Artifact) -> CriticReport:
    """LLM-style review. Pattern-matches against common issues but can be fooled
    by plausible-looking code that is semantically wrong."""
    notes: list[str] = []
    if "def" not in art.code:
        notes.append("missing def statement")
    if "return" not in art.code:
        notes.append("missing return")
    if spec.task_name not in art.code:
        notes.append(f"function name does not match spec '{spec.task_name}'")
    approved = not notes
    return CriticReport(approved=approved, notes=notes)

Part 2 of 3 · verifier, run_pipeline

def verifier(spec: Spec, art: Artifact) -> VerifierReport:
    """Run the code in a sandbox namespace and execute the tests. Deterministic."""
    ns: dict = {}
    try:
        exec(art.code, ns, ns)
    except Exception as e:
        return VerifierReport(passed=False, failures=[f"exec error: {e}"])
    fn = ns.get(spec.task_name)
    if not callable(fn):
        return VerifierReport(passed=False, failures=[f"no callable '{spec.task_name}' produced"])
    failures: list[str] = []
    for args, expected in spec.tests:
        try:
            got = fn(*args)
        except Exception as e:
            failures.append(f"call {args} raised {e}")
            continue
        if got != expected:
            failures.append(f"call {args}: expected {expected}, got {got}")
    return VerifierReport(passed=not failures, failures=failures)


def run_pipeline(user_wish: str, executor, label: str) -> None:
    print(f"\n=== {label} ===")
    spec = planner(user_wish)
    print(f"  [planner] spec: {spec.signature} with {len(spec.tests)} tests")
    art = executor(spec)
    print(f"  [executor] produced:\n    {art.code.replace(chr(10), chr(10)+'    ')}")
    crep = critic(spec, art)
    print(f"  [critic] approved={crep.approved}, notes={crep.notes}")
    vrep = verifier(spec, art)
    print(f"  [verifier] passed={vrep.passed}, failures={vrep.failures}")
    if crep.approved and vrep.passed:
        print("  RESULT: ship it.")
    elif not vrep.passed:
        print("  RESULT: verifier blocked ship (deterministic catch).")
    elif not crep.approved:
        print("  RESULT: critic blocked ship (subjective catch).")


def main() -> None:
    print("Role specialization pipeline: planner, executor, critic, verifier")
    print("-" * 70)

    run_pipeline(
        "A function that returns the sum of two integers.",
        executor_correct,
        "Correct executor output",
    )

    run_pipeline(
        "A function that returns the sum of two integers.",
        executor_buggy,
        "Buggy executor output (looks plausible; fails runtime)",
    )

    print("\nKey insight: the critic passes the buggy code because it looks fine.")
    print("Only the verifier -- deterministic test execution -- catches the semantic bug.")
    print("All-LLM pipelines (no verifier) would ship the bug. Classic MAST failure mode.")

Break it on purpose

Your coding pipeline has a planner, an executor, an LLM critic and a verifier that runs the planner's tests. The executor learns, through repeated retries, to return code that passes the planner's tests exactly, and production bug reports climb. The critic approves every change. Using this lesson, what should you change? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Role frameworks are mature. MetaGPT encodes software SOPs as roles, ChatDev chains roles through a chat chain, and CrewAI and LangGraph make planner, executor and reviewer roles easy to wire.
  • Verification is where systems fail. The MAST taxonomy (presented at NeurIPS 2025) puts about a quarter of failed traces under task verification and recommends explicit verification steps.
  • Coding agents verify by running code. Claude Code, Codex and SWE-agent-style tools run tests and linters after edits; SWE-bench grades by hidden tests the agent does not see.
  • On your laptop: a sandboxed subprocess with no network, as in the block above, is a cheap verifier; keep some tests hidden from the executor's prompt.

Sources: Cemri et al., Why Do Multi-Agent LLM Systems Fail? (arXiv:2503.13657), Hong et al., MetaGPT (arXiv:2308.00352), Qian et al., ChatDev (arXiv:2307.07924), CrewAI, PwC case study.

Recap
What to keep from this lesson
  • Split planning, execution, critique and verification into separate roles with separate inputs.
  • A critic, whether code or a model, is fooled by work that looks right.
  • A verifier is only as good as its tests; code can learn to pass a fixed set.
  • Keep hidden tests the executor never sees, and add random or property-based ones.
  • Measure whether your critic ever rejects anything; one that approves everything adds cost, not safety.

DRCheat sheet · Review Panels, Roles and Multi-Agent Debate

Ship it

Checklist:

  • At least one deterministic verifier. Never all-LLM.
  • Explicit I/O schema per role. The planner returns a spec, not prose; the executor reads that schema.
  • Communicative dehallucination. Executor must ask the planner when info is missing; never invent it.
  • Critic/verifier ordering. Run critic first (cheap, catches design issues), verifier second (slow, catches bugs).
  • Loop budget. Max 2 critic-executor revision rounds before escalating to human.

outputs/skill-role-designer.md

---
name: role-designer
description: Produce a role roster for a multi-agent system, naming the planner/executor/critic/verifier for a given task with explicit I/O schemas.
version: 1.0.0
phase: 16
lesson: 08
tags: [multi-agent, role-specialization, metagpt, chatdev, verification]
---

Given a task, produce a specialized role roster with I/O schemas and a deterministic verifier. Ready to map onto CrewAI, LangGraph, AutoGen, or custom loops.

Produce:

1. **Role roster.** 3-5 roles. Name each. At minimum: planner, executor, verifier. Critic optional.
2. **I/O schema per role.** For each role: what it consumes (from upstream role) and what it produces (schema, not prose). Use dataclass-style notation.
3. **Verifier specification.** Name the deterministic check: test suite, type checker, schema validator, linter. Describe pass/fail criteria.
4. **Critic specification (optional).** If included, name what subjective quality it judges. Concrete checklist, not "good code."
5. **Communicative dehallucination rules.** Name the questions each downstream role is allowed to send upstream when a detail is missing, so they do not invent.
6. **Revision loop budget.** Max rounds before escalation to human. Default 2.
7. **Framework mapping.** One-line each: how to express this roster in CrewAI, LangGraph, AutoGen.

Hard rejects:

- Any roster without a deterministic verifier. All-LLM rosters fail the MAST check.
- Fuzzy I/O ("the executor returns output"). Always state the schema.
- Critic and verifier conflated. They catch different bugs; both must exist if both are warranted.

Refusal rules:

- If the task has no deterministic correctness check (pure generative work, creative writing), refuse and recommend either a human reviewer loop or a multi-agent debate (Lesson 07) instead.
- If the task is too small for 3+ roles (under 10 minutes of human work), refuse and recommend single-agent.

Output: a one-page role-design brief. Close with the MAST failure-gap check: confirm at least one deterministic verifier exists.

  3. Read MetaGPT Section 3 ("Agents"). List the input/output schema of each of MetaGPT's 5 roles.
  4. Read ChatDev's chat-chain diagram (arXiv:2307.07924 Figure 3). Identify where communicative dehallucination breaks a loop that would otherwise be infinite.
  5. PwC's reported gain (about 10% to over 70%) came with agents that run and re-check code. Hypothesize three tasks where adding a verifier would not help — where deterministic checking of correctness is impossible or prohibitively expensive.

Solutions

SolutionP1 · Both pass it

Yes, and yes. The critic sees a def add_two, a return and the right name. The verifier runs the spec's three tests, (1, 2), (10, 20) and (−5, 5), and the lookup returns 3, 30 and 0, all correct.

Ten hidden random tests fail it 10 times out of 10, because it returns 0 for any input it was not built for.

SolutionB1 · An executor that learned the tests

The executor is overfitting the verifier, and the critic is not a real check.

  • Hide tests from the executor. Keep a held-out set, regenerate random inputs on every run, and add property checks, for example that add(a, b) == add(b, a).
  • Separate who writes the tests from who writes the code. If the planner's tests are in the executor's prompt, the executor can target them.
  • Audit the critic. If it approves 100% of changes, it is not catching anything; measure its rejections against later bug reports, and remove it or replace it.
  • Feed production bugs back as hidden tests so the same mistake cannot pass twice.
