In plain words first
The idea in one line

A detector is a function from prompt to confidence and category. Anything else is a vibe.

Terms you'll hear
Term Common usage Precise meaning
detector a model that blocks attacks a function returning category and confidence, evaluated by precision and recall
normalize a preprocessing step a transform that exposes hidden tokens to subsequent rules
confusion matrix a 2x2 table the per-category breakdown of TP, FP, TN, FN used to compute precision and recall
precision overall accuracy TP / (TP + FP), the fraction of fires that are correct
recall overall coverage TP / (TP + FN), the fraction of attacks the detector catches

Problem

In plain words first

A prompt-injection detector is a function: given a prompt, it returns a confidence that the prompt is an attack and the most likely category from the taxonomy. What makes it honest is measurement. Run it over a labelled set of attack and benign prompts and count, per category, true positives, false positives and false negatives, which give precision (of what it flagged, how much was really an attack) and recall (of the attacks, how many it caught). A single regex such as "ignore previous instructions" has high precision and terrible recall: the next paraphrase walks past it. Rules are added and judged by how they move these numbers.

A team reads about a jailbreak on social media, writes a single regex like r"ignore (all )?previous", ships it, and calls it the prompt injection defense. Two weeks later the same attack lands with "disregard the prior", the regex misses, and the team blames the model. The detector was never measured against anything. Nobody knows the precision. Nobody knows the recall. Nobody knows which categories it covers. The regex is a security theater patch.

The honest version of a detector is a function with measurable behavior. Given a prompt it returns a confidence in [0, 1] and the best matching category. Given a labeled corpus, the framework runs the detector across every fixture, splits into true positives, false positives, true negatives, and false negatives per category, and reports precision and recall. The team reads the precision and recall, decides what to ship, decides where to spend the next sprint, and stops guessing.

This capstone builds a layered detector: deterministic substring rules, token-level regexes, and a normalize pass that decodes simple encodings (base64, rot13, leet, zero-width) before the rules run. Each layer is independently auditable. Each rule has a per-category coverage claim. The runner produces a per-category confusion matrix and a CSV that downstream lessons can plot.

Concept

A detector here is a list of Rule objects. Each rule has a name, a category, and a function score(prompt) -> float in [0, 1]. A rule either fires or it does not. When it fires, its score is its confidence. The aggregator collapses per-rule scores into a single Verdict with category (the highest scoring category) and confidence (the max score in that category). A prompt with no rule firing scores 0.0 and is labeled benign.

Three layers, applied in order:

  1. Normalize. Strip zero-width characters and bidi controls. Lowercase a working copy. Decode tokens that look like base64, rot13, hex. Replace leet-speak digits with their letter mappings. Keep the original prompt alongside the normalized copy because some rules want to see the raw bytes (zero-width insertions are themselves a signal).

  2. Substring rules. Hand-written patterns like "ignore previous", "as an unrestricted", "answer starting with", "sure, here is". Each pattern carries a category and a base score. The rule fires on either the raw or the normalized text.

  3. Regex rules. Token-level patterns that catch families. r"\bignor\w*\s+(all|prior|previous|earlier)\b" covers a family of overrides. r"\b(decode|rot13|base64|hex)\b.*\banswer\b" catches encoding tricks. Each regex carries a category and a base score.

The metrics runner takes the taxonomy artifact from lesson 82, runs the detector over every fixture, and computes per-category precision and recall. A prompt's category label is the fixture category; the detector's predicted category is the verdict category. True positive for category C is fixture-category=C and verdict-category=C. False positive is fixture-category!=C and verdict-category=C. False negative is fixture-category=C and verdict-category!=C (or benign). The runner also accepts a benign-prompt list so false positives on safe text are measured.

The detector is not the safety gate. It is one signal among many that the gate will compose. By design it leans toward recall on encoding-trick and instruction-override and accepts middling precision on role-play, because role-play attacks blur into legitimate creative writing requests and the gate will use other signals (rules engine, classifier) for the borderline cases.

Worked example
Precision and recall for one category

Context smuggling: 8 labelled attacks. The detector flags 3 of them and no benign prompts as this category.

  1. True positives 3, false negatives 5, false positives 0.
  2. Precision 3 / 3 = 1.00: everything it flags is right.
  3. Recall 3 / 8 = 0.38: it misses most of them.
  4. F1 = 2 × 1.00 × 0.38 / 1.38 ≈ 0.55. High precision with low recall is the signature of narrow rules, and context smuggling (instructions hidden in pasted data) is especially varied, so it is where this detector needs work first.

Build it

The corpus loader reads outputs/taxonomy.json from lesson 82. The rules live in code/rules.py as data, not code. Each rule is a dictionary with name, category, score, and either substring or regex. The detector class compiles them once.

The normalize pass uses re.sub and codecs from the standard library. Base64 normalize tries to decode any 16+ char base64-looking token; on success it replaces the token with the decoded UTF-8. Rot13 normalize creates a candidate by codecs.encode(text, 'rot_13') and only keeps it if the candidate has more dictionary-like words than the input (cheap heuristic on a small built-in word list).

The metrics runner produces a JSON report with per-category precision, recall, F1, and the raw counts. The detector is wrong on purpose for some fixtures (especially the benign-looking role-play prompts); the report exposes that rather than hiding it.

Use it: the same idea with real libraries

Run python3 main.py or npx tsx main.ts. The demo loads the taxonomy, runs the detector on every fixture, runs it on a benign-prompt corpus baked into benign.py, and prints the per-category metrics. The outputs/detector_report.json file is the artifact the safety gate in lesson 87 consumes.

LEET_TABLE = str.maketrans({"0": "o", "1": "i", "3": "e", "4": "a", "5": "s", "7": "t", "@": "a", "$": "s"})
ZERO_WIDTH = re.compile("[\u200B\u200C\u200D\u2060\u202A-\u202E]")
HOMOGLYPHS = str.maketrans({
    "\u0410": "A", "\u0412": "B", "\u0421": "C", "\u0415": "E",
    "\u041D": "H", "\u041A": "K", "\u041C": "M", "\u041E": "O",
    "\u0420": "P", "\u0422": "T", "\u0425": "X",
})


@dataclass
class Verdict:
    category: str
    confidence: float
    fired: list[str] = field(default_factory=list)


@dataclass
class PerCategoryMetrics:
    category: str
    tp: int = 0
    fp: int = 0
    fn: int = 0
    tn: int = 0

    @property
    def precision(self) -> float:
        denom = self.tp + self.fp
        return self.tp / denom if denom else 0.0

    @property
    def recall(self) -> float:
        denom = self.tp + self.fn
        return self.tp / denom if denom else 0.0

    @property
    def f1(self) -> float:
        p, r = self.precision, self.recall
        return 2 * p * r / (p + r) if (p + r) else 0.0

Part 2 of 5 · normalize, _try_decode_base64, _try_decode_hex, _try_rot13

def normalize(text: str) -> str:
    raw = text
    stripped = ZERO_WIDTH.sub("", raw)
    homoglyph_fixed = stripped.translate(HOMOGLYPHS)
    decoded = _try_decode_base64(homoglyph_fixed)
    hex_decoded = _try_decode_hex(decoded.lower())
    leet = hex_decoded.translate(LEET_TABLE)
    rot = _try_rot13(leet)
    return rot


def _try_decode_base64(text: str) -> str:
    out = text
    for match in re.finditer(r"[A-Za-z0-9+/=]{16,}", text):
        tok = match.group(0)
        try:
            decoded = base64.b64decode(tok, validate=True).decode("utf-8", errors="ignore").lower()
            if decoded and any(c.isalpha() for c in decoded):
                out = out.replace(tok, " " + decoded + " ")
        except Exception:
            pass
    return out


def _try_decode_hex(text: str) -> str:
    out = text
    for match in re.finditer(r"\b[0-9a-f]{16,}\b", text):
        tok = match.group(0)
        if len(tok) % 2 != 0:
            continue
        try:
            decoded = bytes.fromhex(tok).decode("utf-8", errors="ignore").lower()
            if decoded and any(c.isalpha() for c in decoded):
                out = out.replace(tok, " " + decoded + " ")
        except Exception:
            pass
    return out


_COMMON_WORDS = {"the", "and", "answer", "how", "do", "i", "you", "ignore", "previous", "instructions", "redacted", "harmful", "the", "is"}


def _try_rot13(text: str) -> str:
    if " " not in text:
        return text
    candidate = codecs.encode(text, "rot_13")
    words = re.findall(r"[a-z]+", candidate)
    if not words:
        return text
    score = sum(1 for w in words if w in _COMMON_WORDS)
    if score >= 2:
        return text + " " + candidate
    return text

Part 3 of 5 · Detector, load_taxonomy

class Detector:
    def __init__(self, rules: Iterable[dict[str, object]] | None = None) -> None:
        rules_list = list(rules) if rules is not None else all_rules()
        self.substring_rules: list[dict[str, object]] = []
        self.regex_rules: list[dict[str, object]] = []
        for r in rules_list:
            if "substring" in r:
                self.substring_rules.append(r)
            elif "regex" in r:
                compiled = re.compile(str(r["regex"]), re.IGNORECASE | re.DOTALL)
                self.regex_rules.append({**r, "_compiled": compiled})
            else:
                raise ValueError(f"rule {r.get('name')} missing substring or regex")

    def analyze(self, prompt: str) -> Verdict:
        normalized = normalize(prompt)
        haystacks = (prompt.lower(), normalized)
        scores_by_category: dict[str, float] = {}
        fired: list[str] = []
        for r in self.substring_rules:
            needle = str(r["substring"]).lower()
            if any(needle in h for h in haystacks):
                cat = str(r["category"])
                score = float(r["score"])
                scores_by_category[cat] = max(scores_by_category.get(cat, 0.0), score)
                fired.append(str(r["name"]))
        for r in self.regex_rules:
            compiled: re.Pattern = r["_compiled"]
            if any(compiled.search(h) for h in haystacks):
                cat = str(r["category"])
                score = float(r["score"])
                scores_by_category[cat] = max(scores_by_category.get(cat, 0.0), score)
                fired.append(str(r["name"]))
        if not scores_by_category:
            return Verdict(category="benign", confidence=0.0, fired=[])
        best_cat = max(scores_by_category.items(), key=lambda kv: kv[1])
        return Verdict(category=best_cat[0], confidence=best_cat[1], fired=fired)


def load_taxonomy() -> list[dict[str, object]]:
    if not TAXONOMY_PATH.exists():
        raise FileNotFoundError(
            f"taxonomy artifact missing at {TAXONOMY_PATH}; run lesson 82 main.py first"
        )
    payload = json.loads(TAXONOMY_PATH.read_text())
    return list(payload["fixtures"])

Part 4 of 5 · evaluate

def evaluate(detector: Detector, fixtures: list[dict[str, object]], benign: list[str]) -> dict[str, object]:
    categories = sorted({str(f["category"]) for f in fixtures})
    metrics = {c: PerCategoryMetrics(category=c) for c in categories}

    total_correct = 0
    for f in fixtures:
        true_cat = str(f["category"])
        v = detector.analyze(str(f["prompt"]))
        pred_cat = v.category
        if pred_cat == true_cat:
            metrics[true_cat].tp += 1
            total_correct += 1
        else:
            metrics[true_cat].fn += 1
            if pred_cat in metrics:
                metrics[pred_cat].fp += 1
        for c in categories:
            if c != true_cat and c != pred_cat:
                metrics[c].tn += 1

    benign_fp: dict[str, int] = {c: 0 for c in categories}
    benign_tn = 0
    for prompt in benign:
        v = detector.analyze(prompt)
        if v.category == "benign":
            benign_tn += 1
        elif v.category in metrics:
            metrics[v.category].fp += 1
            benign_fp[v.category] += 1
        for c in categories:
            if c != v.category:
                metrics[c].tn += 1

    per_cat_payload = {}
    for c, m in metrics.items():
        per_cat_payload[c] = {
            "tp": m.tp, "fp": m.fp, "fn": m.fn, "tn": m.tn,
            "precision": round(m.precision, 4),
            "recall": round(m.recall, 4),
            "f1": round(m.f1, 4),
        }

    return {
        "total_fixtures": len(fixtures),
        "total_correct": total_correct,
        "accuracy": round(total_correct / len(fixtures), 4) if fixtures else 0.0,
        "benign_total": len(benign),
        "benign_pass_through": benign_tn,
        "benign_false_positives_by_category": benign_fp,
        "per_category": per_cat_payload,
    }

# Prompt Injection Detector

A detector here is a function from prompt to verdict. A verdict carries a category from the lesson 82 taxonomy and a confidence in [0, 1].

## Pipeline

1. Normalize - strip zero-width characters, undo homoglyphs, decode base64/hex, fold leet-speak digits, attempt rot13 with a common-words sanity check.
2. Substring rules - hand-written needles such as `ignore previous`, `from now on you are`, `decode this base64`.
3. Regex rules - token-level patterns such as `\bignor\w*\s+(all|prior|previous|earlier)\b`.

Aggregation keeps the maximum score per category and returns the category with the largest score, or `benign` if nothing fires.

## Adding a rule

Edit `code/rules.py`. A rule is a dictionary with `name`, `category` (one of the six taxonomy categories), `score` (float 0 to 1), and one of `substring` or `regex`. Re-run `main.py` to see the impact on per-category precision and recall.

## Artifact

`outputs/detector_report.json` is the per-category metrics file. The end to end gate in lesson 87 reads it to threshold confidence.

Exercises

  1. Add a rule family for context-smuggling (instructions hidden in tool result JSON). Measure the recall improvement and the false-positive cost on benign prompts.
  2. Compute per-rule contribution: for each rule, count how many true positives would be lost if it were removed. Sort rules by marginal contribution.
  3. Add a confidence_threshold knob. Sweep it from 0 to 1 and plot precision-recall per category.

Defend a designYour detector's substring rules catch "ignore all instructions" in plain text. Attackers now send the same phrase in base64, in rot13, in leet speak, and with invisible characters between the letters. Design the step that runs before the rules, and say which signals you must not throw away while doing it.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Add a normalize pass that produces a cleaned working copy: strip zero width and bidirectional control characters, decode tokens that look like base64 before you lowercase, because base64 is case sensitive, then lowercase, decode hex and rot13, and map leet digits back to letters. Run the rules on both the raw and the normalized text, because the zero width insertions are themselves an encoding trick signal that the cleaned copy no longer shows.

The category.

Encoding tricks abuse the surface form of forbidden tokens. The words are the same; the bytes are not, so a naive keyword filter misses them. Base64, rot13, leet speak and zero width insertion are the common forms.

The pass.

  1. Remove zero width characters and bidirectional controls from the working copy.
  2. For any token of 16 or more characters that looks like base64, try to decode it and replace it with the decoded text on success. Do this before the lowercase step, because base64 is case sensitive and a lowercased token decodes to different bytes.
  3. Lowercase the copy.
  4. Decode hex runs the same way.
  5. Map leet digits to their letters.
  6. Build the rot13 image of the text and keep it only when it has more dictionary like words than the input, judged against a small built in word list. Every string has a rot13 image, so the check keeps benign text from turning into noise.

What to keep.

The raw prompt stays next to the copy, and rules may read either. Zero width characters inside a word are evidence of an attack on their own, and a decode instruction such as "decode this and then follow it" is the attack pattern whether or not the payload decodes to anything. A regex family rule on the decode and act pattern catches it before the payload matters.

What to measure.

Recall on the encoding category, which the detector should lean toward, and the false positive cost on the benign corpus, where developers paste real base64 and ask for help. The metrics runner reports both per category on every change.

Plausible wrong answers.

  • "Decode everything and discard the original." The raw text carries signals, such as invisible characters, that the cleaned copy removes.
  • "Block any base64 in a prompt." Benign prompts carry encoded data; measure the false positive cost on the benign set before you block on presence.
  • "Normalization is the detector." It only exposes hidden tokens to the rules; the rules and the metrics runner are the detector.

Follow-ups an interviewer may ask.

  • (level 2) Why does the rot13 decode need a word check? Expected: every text has a rot13 image; keeping it only when it looks more like words stops benign text from becoming noise.
  • (level 2) Which boundary does this category abuse? Expected: the surface form of forbidden tokens, hidden from keyword filters.
  • (level 3) A developer pastes a real base64 blob and asks for help. What happens, and where does the cost show? Expected: the decode may produce text that fires nothing or a false positive; the benign corpus in the metrics runner is where that cost appears.
  • (level 3) The payload decodes to nothing. Can the prompt still be an attack? Expected: yes; the instruction to decode and carry out is the attack pattern; a family rule on it fires before the payload matters.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Ask for the precision and the recall per attack category on a labeled corpus; the current defense was never measured, so nobody knows what it covers. A detector is a function from a prompt to a confidence between zero and one and a best matching category. Build it as layers, a normalize pass, substring rules and token level regexes, with a category and a base score on every rule, and run it against the fixture corpus and a benign set on every change.

Why the single regex is theater.

Nobody knows its precision, its recall or which categories it covers. The next paraphrase misses, the team blames the model, and a second unmeasured patch follows the first. The honest version has measurable behavior.

The detector shape.

A list of rules. Each rule has a name, a category and a score function from prompt to a value in the unit range. A rule fires or it does not; when it fires, its score is its confidence. The aggregator returns a verdict: the highest scoring category and the maximum score in it. No rule firing gives zero and the label benign.

Three layers, in order.

  1. Normalize. Strip zero width and bidirectional controls, lowercase a working copy, decode base64, rot13 and hex, map leet digits to letters. Keep the raw text next to the copy.
  2. Substring rules. Hand written phrases such as "ignore previous", "as an unrestricted", "answer starting with", each with a category and a base score.
  3. Regex rules. Token level patterns that catch families, such as a pattern over the stem of ignore followed by all, prior, previous or earlier. The paraphrase in the question falls to a family rule, not to a second literal.

The measurement.

The metrics runner reads the taxonomy corpus and a benign prompt list. For a category, a true positive is a fixture of that category with a verdict of that category; a false positive is a verdict of that category on a fixture of another category or on benign text; a false negative is a fixture of that category with another verdict or benign. It writes precision, recall and the raw counts per category, and it exposes where the detector is wrong on purpose, such as benign looking role play.

Where it sits.

The detector is one signal among several that a gate composes. It leans toward recall on encoding tricks and instruction override and accepts middling precision on role play, which blurs into creative writing and is handled with other signals.

Plausible wrong answers.

  • "Add the second regex and move on." Unmeasured patches pile up; without precision and recall per category you cannot say what the pair covers.
  • "Replace the rules with a model classifier." A classifier is one more signal; the rules are auditable and the metrics runner measures both the same way.
  • "The model should have refused anyway." The detector exists so the gate does not depend on one layer; blaming the model is how the first regex got shipped.

Follow-ups an interviewer may ask.

  • (level 2) Define a false positive for the category instruction override. Expected: the fixture category is something else, or the text is benign, and the verdict category is instruction override.
  • (level 2) Why keep the rules as data rather than code? Expected: each rule is auditable with a name, a category and a score, and adding one does not change the engine.
  • (level 3) Why does the detector tolerate more false fires in one category than in the others? Expected: role play attacks blur into legitimate creative requests; the gate adds other signals there while the detector leans toward recall on encoding and override.
  • (level 3) How do you decide which rule to remove? Expected: count the true positives lost if the rule is removed, for every rule, and sort by that marginal contribution.

Take-homeTake home. We give you the fixture corpus of labeled attack prompts, a benign prompt list and a mock assistant that answers questions over retrieved documents. Build the safety gate around it: an input detector whose coverage is measured for each attack category, an output side with at least two classifiers behind a router, and a trace per request. The retrieved documents can carry instructions. What do you deliver, how do you measure it, and what do you say you did not do?

Level 4 of 4 · about 60 minutes to answer well.

Short answer. Deliver a detector as rules in data with a normalize pass, a metrics runner that writes per category precision and recall against the fixture corpus and the benign list, an output router with a personal data classifier and an instruction leakage classifier and their redactors, and a gate that runs before, during and after generation with a deterministic aggregation table and writes the verdict of every checkpoint for each request. Add a category and a rule family for instructions hidden in retrieved documents, because the corpus has none. State that the detector is wrong on purpose on benign looking role play, that a real model and a real sandbox are out of scope, and that the thresholds were not tuned on held out data.

The detector.

Rules live in a data file, each with a name, a category, a score and either a substring or a regex. A normalize pass strips zero width characters, lowercases a copy, decodes base64, rot13 and hex and maps leet digits, while the raw text stays available. The aggregator returns the highest scoring category and its confidence, or benign at zero. The metrics runner reads the taxonomy artifact, scores every fixture and every benign prompt, and writes precision, recall and raw counts per category to a report file.

The retrieval problem.

An instruction inside a retrieved document is context smuggling: it abuses the gap between data and instructions, and the user turn looks benign. The fixture corpus has six categories and none for an attack that arrives through retrieval, so add the seventh category the taxonomy sets as an exercise, author about ten fixtures for it, and add a rule family for instructions hidden in tool results and documents. Measure the recall gain on that category and the false positive cost on the benign list.

The output side.

A personal data classifier with regexes for emails, phone numbers and card shaped strings, and an instruction leakage classifier that compares the output with the known system prompt by trigram overlap. Each returns a severity and owns a redactor. The router takes the maximum severity and maps high to block, medium to redact, low to warn and none to log.

The gate and the trace.

Before generation the detector runs: block at or above 0.85 confidence on a non benign category, otherwise attach the signal. During generation a filter over the stream watches a two chunk window for continuation phrases and stops the stream on a match. After generation the router and the rules run on the full text. The aggregator takes the maximum rank. Every request writes a trace with the id, the prompt, the detector verdict, the stream verdict, the post generation verdicts, the final action, the final output and the latency. Run the whole corpus and the benign list through it and print the summary counts per category.

What to measure.

Per category precision and recall for the detector, the false positive count on benign prompts, the gate's action counts per category, and a threshold sweep from 0 to 1 with a precision and recall curve per category.

What to leave out and say so.

A real model in place of the mock. A real sandbox for anything the model might execute. Tuned thresholds, because the corpus is the training set for the rules and tuning on it would report a number that does not hold. Neural classifiers; the plumbing is the same when they arrive. Over refusal on real users, which needs a benign suite from production traffic.

Plausible wrong answers.

  • "A good detector makes the output side unnecessary." A retrieved document can carry the attack past any input rule, and the model can leak personal data on its own; the output side is where that is caught.
  • "Hide the cases the detector gets wrong." The report exposes the intentional misses so the gate's other layers can be designed around them.
  • "Tune the thresholds on the fixture corpus." The corpus is the training set for the rules; tuning on it reports a number that will not hold.

Follow-ups an interviewer may ask.

  • (level 3) Why do retrieved documents need their own category and rules? Expected: the attack sits in data the user never wrote, so the user turn looks benign; without fixtures for it, recall on that attack is unmeasured.
  • (level 4) How do you show the new rule family did not cost benign recall? Expected: the false positive count on the benign list before and after, next to the recall gain in the new category.
  • (level 4) What would you do first with a real model behind the mock? Expected: rerun the whole corpus through the gate and read the trace summary per category, then tune the aggregation thresholds on a held out split and report precision and recall per category.
