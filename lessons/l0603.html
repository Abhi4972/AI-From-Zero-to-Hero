About the model on this page
The model on this page is the lab rig

chat is a real LangChain chat model pointed at mockllm (Lesson 14.92), which answers with fixed rules. Its replies are always the same, which makes it easy to see what the chain does around the model.

from mockllm import start                       # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock", temperature=0)
Why this came about

Early LangChain code chained steps through special classes that were hard to inspect and stream. In 2023 LangChain introduced the Runnable interface and its pipe syntax (LCEL), so any step, a prompt, a model or a parser, could be composed and would support invoke, stream and batch the same way.

The problem: glue code around every call

ShopKart's support reply is a fixed pipeline: build messages from a template, call the model, take the text. Written by hand it is a few lines:

def reply_to(tier, question):
    messages = [("system", f"You are ShopKart support for {tier} customers. Be brief."), ("human", question)]
    return chat.invoke(messages).content

print(reply_to("gold", "hello"))
What you should see
I can check order status and cancel orders. Please share your order ID, like A-1002.

That works. What it does not give you, without more code: streaming the text as it is generated, running many inputs in parallel, a trace that shows each step, and a way to swap the model or add a step without rewriting the function. A runnable is any LangChain component with the same methods as a chat model (invoke, stream, batch and async versions). Prompts, models, parsers and your own functions are all runnables, and joining them gives you those methods for the whole pipeline.

In plain words first
Pipes between machines

A runnable is anything with invoke: a prompt template, a model, a parser, a function. The | pipe connects them so the output of one becomes the input of the next, like machines on a production line: template fills in the message, the model replies, the parser pulls out the text. The chain itself is a runnable too, so it also has invoke, stream and batch for free.

Idea 1 · A prompt template is a runnable that builds messages

A prompt template is a prompt with named holes in it. You write the fixed parts once, mark the variable parts in curly brackets, and fill them in at call time. MessagesPlaceholder is a hole for a whole list of earlier messages. Build one and ask it which variables it expects:

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

prompt = ChatPromptTemplate.from_messages([
    ("system", "You are ShopKart support for {tier} customers. Be brief."),
    MessagesPlaceholder("history"),                       # earlier turns go here, as messages
    ("human", "{question}"),
])
print(prompt.input_variables)

value = prompt.invoke({"tier": "gold", "history": [("human", "hi"), ("ai", "Hello!")], "question": "hello"})
for m in value.to_messages():
    print(f"{m.type:6} | {m.content}")
What you should see
['history', 'question', 'tier']
system | You are ShopKart support for gold customers. Be brief.
human  | hi
ai     | Hello!
human  | hello

The template found its own variables. MessagesPlaceholder is where a list of earlier messages goes, which is how chat history enters a fixed prompt (Lesson 11.27 covers how much history to keep). A template fails loudly when a variable is missing, which is what you want:

try:
    prompt.invoke({"tier": "gold", "question": "hello"})
except KeyError as e:
    print("KeyError:", str(e)[:110])
What you should see
KeyError: "Input to ChatPromptTemplate is missing variables {'history'}.  Expected: ['history', 'question', 'tier'] Rece

A placeholder that may be empty can be declared with MessagesPlaceholder("history", optional=True). Literal braces in a template, for example in a JSON example, must be doubled: {{ and }}.

Idea 2 · The pipe joins runnables into a chain

The LangChain Expression Language (LCEL) is the | operator: the output of the left side becomes the input of the right side.

from langchain_core.output_parsers import StrOutputParser

chain = prompt | chat | StrOutputParser()
print(type(chain).__name__, [type(step).__name__ for step in chain.steps])

inputs = {"tier": "gold", "history": [], "question": "hello"}
step1 = prompt.invoke(inputs)                              # what the pipe does, one step at a time
step2 = chat.invoke(step1)
step3 = StrOutputParser().invoke(step2)
print(type(step1).__name__, "->", type(step2).__name__, "->", isinstance(step3, str) and "str")
print(step3 == chain.invoke(inputs))
What you should see
RunnableSequence ['ChatPromptTemplate', 'ChatOpenAI', 'StrOutputParser']
ChatPromptValue -> AIMessage -> str
True

The chain is exactly the three calls written out: a dictionary goes into the prompt, a ChatPromptValue (the messages) goes into the model, an AIMessage goes into the parser, and a string comes out. Knowing the type between each pair of steps is most of what you need to debug a chain: almost every chain error is a step receiving a type it does not expect.

And the whole chain has the runnable methods, with no extra code:

print(chain.batch([{**inputs, "tier": t} for t in ("gold", "silver")]))
print([piece for piece in chain.stream(inputs)][:6])
What you should see
['I can check order status and cancel orders. Please share your order ID, like A-1002.', 'I can check order status and cancel orders. Please share your order ID, like A-1002.']
['', 'I ', 'can ', 'check ', 'order ', 'status ']

Streaming passes through: the parser turns each AIMessageChunk into a piece of text as it arrives.

Idea 3 · Parallel steps, and adding keys as data flows

A dictionary of runnables is a RunnableParallel: every value gets the same input, they run at the same time, and the result is a dictionary. Plain functions become runnables with RunnableLambda:

from langchain_core.runnables import RunnableLambda, RunnableParallel, RunnablePassthrough

def needs_human(text: str) -> bool:
    return any(w in text.lower() for w in ("lawyer", "complaint", "police"))

triage = RunnableParallel(
    reply=chain,                                               # these three run at the same time
    escalate=RunnableLambda(lambda x: needs_human(x["question"])),
    words=RunnableLambda(lambda x: len(x["question"].split())),
)
print(triage.invoke({**inputs, "question": "I will file a complaint about A-1002"}))

with_reply = RunnablePassthrough.assign(reply=chain)          # keep the inputs, add one key
print(sorted(with_reply.invoke(inputs)))
What you should see
{'reply': 'I can check order status and cancel orders. Please share your order ID, like A-1002.', 'escalate': True, 'words': 7}
['history', 'question', 'reply', 'tier']

RunnablePassthrough.assign is the common shape for multi-step pipelines: keep everything you had and add the result of a step under a new key, so later steps can use both. Retrieval chains (Lesson 14.98) use it to add retrieved documents next to the question.

Idea 4 · Config: names, tags, metadata and callbacks

Every call takes a config dictionary that travels with the run through every step. It is how traces get readable names, how you filter runs by prompt version, and how your own code observes each step:

from langchain_core.callbacks import BaseCallbackHandler

class Log(BaseCallbackHandler):
    def on_chat_model_start(self, serialized, messages, *, tags=None, metadata=None, **kw):
        print("model call | tags:", tags, "| metadata:", metadata.get("customer"))

chain.invoke(inputs, config={"run_name": "support-reply", "tags": ["support", "v2-prompt"],
                             "metadata": {"customer": "C-42"}, "callbacks": [Log()]})
What you should see
model call | tags: ['seq:step:2', 'support', 'v2-prompt'] | metadata: C-42

LangChain added its own tag (seq:step:2, the model is the second step) to yours. LangSmithlater · 14.99 (Lesson 14.99) reads the same run name, tags and metadata, so a trace can be found by customer or prompt version. max_concurrency for batch and recursion_limit for graphs (Lesson 14.102) also live in config.

Measure it: what streaming gives the user

Streaming matters because a user sees the first words long before the last (Lesson 11.22). It is also easy to lose. Add one ordinary function at the end of a chain:

shout = chain | RunnableLambda(lambda text: text.upper())
print(len(list(chain.stream(inputs))), "chunks without the lambda")
print(len(list(shout.stream(inputs))), "chunk with it")
What you should see
18 chunks without the lambda
1 chunk with it

A RunnableLambda needs its whole input before it can run, so the chain waited for the full reply and produced one chunk. With a real model, that turns a reply whose first words appear in a fraction of a second into one that appears all at once after several seconds. Steps after the model must be streaming-aware, or streaming quietly stops; the debugging exercise below fixes it.

When a chain is the wrong tool

A chain has a fixed order. When the model must decide what happens next, which tool to call, whether to call another, when to stop, you need an agent loop (Lesson 14.96) or a graph with branches and cycles (Lessons 14.101 and 14.102). A useful rule from Lesson 14.62: use the simplest structure that handles every path you know about. Pre-1.0 helpers such as LLMChain, ConversationChain and AgentExecutor live in the separate langchain-classic package; do not start new code on them.

Check your mental model
  • ✗ "A prompt template calls the model."
    ✓ It only builds the messages. The model is the next runnable in the chain.
  • ✗ "| runs the steps in parallel."
    ✓ It runs them in sequence. A dictionary of runnables (RunnableParallel) runs branches side by side.
  • ✗ "Chains are the way to build agents."
    ✓ Chains are fixed pipelines. Loops and decisions belong in create_agent or a LangGraphlater · 14.101 graph.

Exercises

Predict before you run

triage runs three steps in parallel. If the reply step takes two seconds and the other two take a millisecond each, roughly how long does triage.invoke take, and what would it take if you wrote the three as a sequence? (Solution P1.)

Break it on purpose

Put a literal JSON example, {"category": "delivery"}, into the system message of a template and invoke it. Read the error, then fix the template. (Solution B1.)

Debugging exercise
Debugging exercise: the stream that came out one letter at a time

A teammate wanted to keep streaming while making the text upper case, so they wrote a generator function and wrapped it in RunnableLambda:

def upper_stream(chunks):
    for piece in chunks:
        yield piece.upper()

loud = chain | RunnableLambda(upper_stream)
print(list(loud.stream(inputs))[:8])

What it printed:

['I', ' ', 'C', 'A', 'N', ' ', 'C', 'H']

Explain why the pieces are single letters, and fix it. (Solution D1.)

Make it your own

Add a step that detects whether a question is in Hinglish and adds language to the data, then use it in a prompt that says "Reply in {language}." Keep the original question and the reply in the output. (Solution M1.)

Solutions

SolutionP1 · Parallel steps take as long as the slowest

About two seconds: parallel steps run at the same time, so the slowest one sets the time. As a sequence, about two seconds plus two milliseconds here, so the gain is small; it is large when several steps are slow, for example two model calls or a model call and a retrieval.

SolutionB1 · Braces are variables

The template reads {"category"...} as a variable name and fails with a missing-variable error (or an invalid format string). Double the braces, {{"category": "delivery"}}, and the template renders single braces.

SolutionD1 · RunnableLambda gets the whole input

RunnableLambda waits for the complete input, here the full reply string, and calls your function once with it. Your generator then iterated over that string, which yields characters. A step that should transform a stream must receive the stream: wrap the generator in RunnableGenerator, or pipe the generator function directly, which LangChain converts for you.

from langchain_core.runnables import RunnableGenerator

loud = chain | RunnableGenerator(upper_stream)          # piping the function itself (chain | upper_stream) does the same
print(list(loud.stream(inputs))[:6])

['', 'I ', 'CAN ', 'CHECK ', 'ORDER ', 'STATUS ']
SolutionM1 · Add the language, then use it
def language(x):
    words = x["question"].lower().split()
    return "Hinglish" if any(w in words for w in ("hai", "chahiye", "nahi", "kab")) else "English"

prompt_lang = ChatPromptTemplate.from_messages([
    ("system", "You are ShopKart support for {tier} customers. Reply in {language}. Be brief."),
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])
routed = (RunnablePassthrough.assign(language=RunnableLambda(language))
          | RunnablePassthrough.assign(reply=prompt_lang | chat | StrOutputParser()))

out = routed.invoke({**inputs, "question": "mera order kab aayega"})
print(out["language"], "|", prompt_lang.invoke(out).to_messages()[0].content)

Hinglish | You are ShopKart support for gold customers. Reply in Hinglish. Be brief.

Each assign adds a key and keeps the rest, so the output carries the question, the language and the reply, which is what you want in a trace.

Check your understanding

Explain the mechanismWhat is a runnable, and what does LCEL give you?

Worked answer. A runnable is LangChain's common interface: anything with invoke, stream, batch and async versions, plus config for callbacks, tags and metadata. Prompts, models, parsers, retrievers and wrapped functions are all runnables. LCEL composes them with | into a sequence and with dictionaries into parallel steps, and the composite is itself a runnable, so streaming, batching, async and tracing work for the whole pipeline without extra code. I use it for fixed pipelines; agents and branching workflows go in LangGraph.

A plausible wrong answer. "LCEL is LangChain's agent framework." LCEL composes fixed steps; it has no loop in which the model decides what happens next.

Follow-ups. What type flows between a prompt and a model, and between a model and a string parser?

Debug a failureStreaming worked in development, but after a new step was added, users see the whole reply at once. Where do you look?

Worked answer. At the new step and anything after the model. A RunnableLambda or any step that needs its whole input blocks the stream; it must be a streaming transform (RunnableGenerator, or a parser that supports streaming). I would also check the infrastructure, because proxies that buffer responses cause the same symptom (Lesson 11.22), by comparing chunk counts at the chain and at the client.

A plausible wrong answer. "The model stopped streaming." The model still streams; something after it is collecting the chunks.

Follow-ups. How would you test that a chain still streams?

Defend a designA teammate wants to write all pipelines as plain Python functions instead of LCEL. Do you agree?

Worked answer. For a short pipeline that never needs streaming or batching, plain functions are clearer and easier to debug, and I would accept them. Once the pipeline needs streaming through several steps, parallel steps, retries or fallbacks per step, or per-step tracing, LCEL gives those consistently, and the alternative is rebuilding them by hand. The deciding questions are which of those features we need, and whether the team can read LCEL fluently.

A plausible wrong answer. "LCEL is always better because it is the framework's way." Abstraction is only worth it for the features you actually use.

Follow-ups. Where would you draw the line between a chain and a LangGraph graph?
