The examples use LangGraph's in-memory store and SQLite, so they run anywhere. The text says where Postgres or the Agent Server does the same job in production.

Why this came about

Lesson 14.71 put an agent behind your own API. The next problems appear only with traffic: a second worker process, a second customer, a customer who sends two messages before the first answer arrives. LangGraph's savers and stores do not know about users or workers; they store what you give them. These rules came from teams running agents as multi-user services in 2025 and 2026, and several of them were collected and measured in the AI Engineering from Scratch LangChain manual.

The problem: a graph that is correct, run by a service that is not

Your agent passes every test. In production, two requests for the same conversation reach two worker processes and both write to one checkpoint chain. A memory tool built its store prefix from a user ID that a client sent, and a crafted ID listed everyone's memories. A customer typed "also, cancel the other order" while the first run was still calling tools. None of this is in the graph; all of it is in how the service runs the graph.

In plain words first
One booking clerk per file

A travel agency keeps one paper file per customer. Two clerks must never work on the same file at once, so the file gets a "taken" slip, and if a clerk goes home sick the slip is removed. Files of different customers sit in labelled drawers, and the clerk reads the label from the customer's ID card, not from what the customer says. And when a customer phones again while their booking is being made, the office needs a rule: wait, replace, or drop the second call.

Idea 1 · One run per thread, across workers

Within one process, a lock in memory is enough. With several processes, the lock must live where every process can see it, and it must be released when a process dies. Here is the pattern with a SQLite table, where a primary key refuses a second holder:

import os, sqlite3, threading, time

db_path = "locks.db"
if os.path.exists(db_path):
    os.remove(db_path)
sqlite3.connect(db_path).execute("create table if not exists running (thread_id text primary key)")

def try_lock(thread_id):
    db = sqlite3.connect(db_path, timeout=5)
    try:
        with db:
            db.execute("insert into running values (?)", (thread_id,))   # refused if the thread is taken
        return True
    except sqlite3.IntegrityError:
        return False

def unlock(thread_id):
    with sqlite3.connect(db_path) as db:
        db.execute("delete from running where thread_id = ?", (thread_id,))

results = []
def request(worker):
    if not try_lock("thread-77"):
        results.append("409 busy")                      # tell the client to wait or retry
        return
    try:
        time.sleep(0.2)                                 # the graph run would happen here
        results.append("200 ran")
    finally:
        unlock("thread-77")

workers = [threading.Thread(target=request, args=(name,)) for name in ("A", "B")]
for w in workers: w.start()
for w in workers: w.join()
print("two requests at once:", sorted(results))
results.clear(); request("B")
print("a request afterwards:", results)
What you should see
two requests at once: ['200 ran', '409 busy']
a request afterwards: ['200 ran']

One request ran and the other was refused with a 409, which the client turns into "still working on your last message". The weakness of this table is the crash case: a worker that dies holding the row leaves the thread locked until someone deletes it. In production on Postgres, use an advisory lock instead: pg_try_advisory_lock(hashtextextended(thread_id, 0)) on a connection the worker holds for its locks. Postgres releases it automatically when that worker's session ends, so a crashed worker frees its threads with no timer. Two details matter: hold lock connections outside the pool your checkpointer uses, or many held locks starve checkpoint writes; and an advisory lock can be taken again by the same session, so also track held thread IDs inside the worker.

Adding workers buys availability, not speed, when the model server is the bottleneck. Measure where the time goes (Lessons 11.21 and 14.109) before adding processes.

Idea 2 · Double texting: a new message while a run is going

The lock answers "never run twice at once". It does not say what to do with the second message. LangGraph's Agent Server (Lesson 14.67) makes this a per-request choice, the multitask strategy of a run:

Strategy What happens to the run in progress What happens to the new message Use it for
reject Continues Refused with an error Forms and workflows where a second message is a mistake
enqueue Continues Runs after it, on the updated thread Chat, where every message should be answered in order (a common default for chat front ends)
interrupt Stops at its next step; its progress is kept Runs now, seeing what the first run did "Also, cancel the other order"
rollback Stops and is deleted as if it never ran Runs now on the state before it "Sorry, wrong order number"

With your own service (Lesson 14.71), you implement the same choice around your lock: reject is the 409 above, enqueue is a per-thread queue, and interrupt uses RunControl.request_drain() (Lesson 14.68) on the running run before starting the new one. Whatever you choose, a side effect that already happened stays happened, so interrupt and rollback need the idempotency keys of Lesson 14.74.

Idea 3 · Keep users apart: the store, the savers and the approver

A checkpointer stores threads by ID, and a store stores items by namespace. Neither knows who a user is. Two users' memories in one store:

from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
store.put(("users", "u-ravi", "memories"), "m1", {"text": "prefers UPI refunds"})
store.put(("users", "u-asha", "memories"), "m1", {"text": "lives in Pune"})

def memories_for(user_id):                                  # user_id must come from your auth, never from the model
    return [item.value["text"] for item in store.search(("users", user_id, "memories"))]

print("u-ravi:", memories_for("u-ravi"))
print("search on ('users',):", [i.value["text"] for i in store.search(("users",))])
print("namespaces under ('users',):", store.list_namespaces(prefix=("users",)))
What you should see
u-ravi: ['prefers UPI refunds']
search on ('users',): ['prefers UPI refunds', 'lives in Pune']
namespaces under ('users',): [('users', 'u-asha', 'memories'), ('users', 'u-ravi', 'memories')]

A search is a prefix match. Build the namespace from the full user ID, and any code path that searches a shorter prefix sees everyone. So: take the user ID from the authenticated request and pass it to tools through the run context (ToolRuntime.context, Lesson 14.69), never as a tool argument the model fills in; refuse IDs that are empty or contain wildcard characters; and never expose list_namespaces or a raw search to users. The same goes for threads: keep your own table of which user owns which thread, check it on every route, and answer 404 (not 403) for someone else's thread, so the response does not confirm that the ID exists.

Four other defaults to change before a multi-user launch:

Boundary The default Change it to
Loading checkpoints The loader rebuilds the classes a checkpoint row names LANGGRAPH_STRICT_MSGPACK=true, and a checkpoint database only your service can write (Lesson 14.74)
Tool approvals HumanInTheLoopMiddleware batches all calls of one model turn into one review interrupt_mode="per_call" (LangChain 1.4.6 and later): one review per call, answered by interrupt ID, with edits validated against the tool's schema so an edit cannot turn one tool into another
MCPlater · 16.4 servers MCPAdapter starts a local script when given a Path Never build the target from user input; a bare string is treated as a URL and refused if it is not one, so keep it that way (Lesson 14.69)
Tracing Traces hold prompts, tool arguments and results Redact before tracing (Lesson 14.117), and check which runs actually leave the machine; the LangChain manual found that tracing_context(enabled="local") still sent agent runs to LangSmith, while enabled=False sent none

And the approver is a separate identity: the customer who owns a thread must not be the person who approves its refund.

Idea 4 · What the framework costs

Running an agent through create_agent and LangGraph adds planning, merging and checkpointing around each model call. Measured against a hand-written loop on the same model, the AI Engineering from Scratch manual found about 5 ms per model call and no extra tokens; on the course lab rig, a two-call agent run took about 10 ms outside the model, and 10.3 ms with an in-memory checkpointer. A real model call takes hundreds or thousands of milliseconds, so the framework is rarely where the cost is. The costs that grow are elsewhere:

Cost Why it grows What to do
Input tokens per call Every call resends the whole thread Summarise or trim (Lesson 14.64); cache the stable prefix (Lesson 11.4)
Checkpoint storage Every checkpoint holds the full message list DeltaChannel, retention policies (Lesson 14.74)
Harness prompts A Deep Agent sends its tool and planning instructions on every call Use the simplest harness that passes your evals (Lesson 14.70)
A failing trace endpoint Retries and timeouts on telemetry slow every run Send traces asynchronously, with a short timeout and a sample rate

To price a conversation, measure token counts per turn on your real traffic, multiply by the provider's prices, and add storage and compute; do not estimate from the number of messages (Lesson 14.114).

In production
Running it for real
  • Workers: one lock per thread across processes (advisory locks on Postgres), a per-thread queue or strategy for double texting, and graceful drain on shutdown.
  • Isolation: owner check on every thread route, user ID from auth into the run context, store namespaces built server-side.
  • Safe defaults: strict msgpack loading, per-call approvals, no user-controlled MCP targets, redacted traces.
  • Budget: alert on tokens per conversation and checkpoint bytes per thread, not only on errors.

Exercises

Predict before you run

In Idea 3, what does store.search(("users", "u-ra")) return, and why does that make a "starts with" user-ID check dangerous? (Solution P1.)

Break it on purpose

In Idea 1, remove the finally: unlock(...) and make the request raise an exception after taking the lock. What happens to every later request for that thread, and how does a Postgres advisory lock avoid it? (Solution B1.)

Make it your own

Write enqueue for Idea 1: when a thread is busy, put the request on a per-thread list and run it when the current run finishes, in order. (Solution M1.)

Solutions

SolutionP1 · Prefixes match whole parts

An empty list: namespaces match by whole tuple elements, and "u-ra" is not the element "u-ravi". The danger is in your code, not the store: if a route accepted a user ID and searched ("users",) when the ID was empty, or built a shorter prefix by mistake, it would return everyone's items. Validate the ID and build the full namespace in one function that every tool uses.

SolutionB1 · A lock that outlives its holder

The row stays in the table, so every later request for thread-77 gets "409 busy" forever, until someone deletes the row. A Postgres advisory lock belongs to the database session that took it, so when the worker process dies, its connection closes and Postgres frees the lock at once. With a table lock you need a lease: store a timestamp, and let another worker take a lock older than the longest possible run.

SolutionM1 · A queue per thread
from collections import defaultdict, deque

queues = defaultdict(deque)
done = []

def submit(thread_id, message):
    queues[thread_id].append(message)
    if not try_lock(thread_id):
        return "queued"                             # the worker holding the lock will run it
    try:
        while queues[thread_id]:
            done.append(queues[thread_id].popleft())   # run the graph for this message
    finally:
        unlock(thread_id)
    return "ran"

try_lock("thread-9")                                 # pretend a run is in progress
print(submit("thread-9", "also cancel A-1002"), "| waiting:", list(queues["thread-9"]))
unlock("thread-9")
print(submit("thread-9", "thanks"), "| answered in order:", done)

queued | waiting: ['also cancel A-1002']
ran | answered in order: ['also cancel A-1002', 'thanks']

A real service keeps the queue in the database next to the lock, so a message survives a crash, and the worker that releases the lock checks the queue before letting go.

Check your understanding

Defend a designYour agent service needs to scale. Do you add uvicorn workers or not?

Worked answer. First find the bottleneck. If the model server or provider rate limit is the ceiling, more workers add availability and failover but not throughput; scale the model side or reduce tokens instead. If CPU-bound work in your service is the ceiling, workers help. Either way, more workers need a cross-process lock per thread (a Postgres advisory lock) and a database-backed queue for double texting, because in-memory locks no longer protect a thread.

A plausible wrong answer. "Yes, more workers always mean more requests per second." Not when every request waits on the same model server.

Follow-ups. How would you measure where the time goes?

Debug a failureA customer reports seeing another customer's preferences in a reply. Where do you look?

Worked answer. At how the store namespace and the thread ID reach the code. Check that the user ID comes from authentication into the run context, not from a tool argument or the request body; that every store access builds the full namespace in one shared function; that no tool can search a shorter prefix; and that every thread route checks ownership. Then search the traces for the tool call that read the wrong namespace.

A plausible wrong answer. "The model hallucinated it." Possible, but a real cross-user leak must be ruled out first.
