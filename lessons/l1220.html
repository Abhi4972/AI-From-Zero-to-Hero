LLMOps, evaluation and model customization

MidWhat is different about LLMOps compared with MLOps?

You usually do not train the model; you version prompts, tools, retrieval settings and model choices. Outputs are open-ended, so evaluation needs judges and human review, not only accuracy. Behavior is non-deterministic, so you test consistency. Cost and latency vary per request with tokens. Observability centres on traces of multi-step runs. Safety and security are part of every release.

SeniorHow do you know a prompt or model change did not make things worse?

A regression set that gates CI (near 100% expected), capability evals to track improvements, several trials per case to measure consistency, judges calibrated against experts, and an online comparison after release: canary or shadow traffic, online judge scores, user feedback, cost and latency. Change one thing at a time, and keep a rollback.

SeniorHow do you cut an agent's cost by half without hurting quality?

Measure first: cost per resolved task broken down by model, step and tool. Then prompt caching (stable prefix), routing easy requests to smaller models (with evals proving they pass), trimming tool definitions and tool outputs, fewer steps through better tools, batch APIs for offline work, semantic caching for repeated questions, and provisioned capacity for steady load. Re-run evals after each change.

MidWhat do you put on an agent's dashboard?

Error rate, p50 and p95 latency and time to first token, steps and tool calls per run, tokens and cost per run and per tenant, escalation and approval rates, guardrail blocks, online judge scores and user feedback, retrieval no-result rate. Alert on SLO breaches, cost spikes and quality drops. Every metric links back to traces.

JuniorWhat is the difference between pass@k and pass^k?

pass@k is the probability that at least one of k attempts succeeds; it suits tasks where you can pick the best attempt, such as code checked by tests. pass^k is the probability that all k attempts succeed; it measures consistency, which is what a customer-facing agent needs. An agent with 80% per-attempt success has pass@3 of about 99% but pass^3 of about 51%.

MidHow do you build a trustworthy LLM-as-judge?

One judge per failure mode, a binary verdict against a written rubric, the evidence included (context, tool results, policy), and calibration against 50 to 100 human labels, reporting true-positive and true-negative rates or Cohen's kappa. Control known biases: swap positions in pairwise comparisons, check verbosity bias, and avoid judging with the same model family when comparing models. Re-calibrate whenever the judge prompt or model changes, and correct production pass rates for the judge's known error rates.

MidWhat is error analysis, and why do it before writing evals?

Reading a sample of real traces and noting the first thing that went wrong in each (open coding), then grouping the notes into a failure taxonomy and counting (axial coding). It tells you which failures matter and what to measure; generic metrics such as "helpfulness" rarely point to a fix. Evals written from observed failures catch regressions that actually hurt users.

MidWhat would you put in an agent's trace?

A root span per run with user, tenant, session, release ID and outcome; a child span per model call with model, token counts, latency and finish reason; per tool call with name, arguments (redacted), result size, errors and duration; spans for retrieval, guardrail decisions, approvals and handoffs. Follow the OpenTelemetry GenAI semantic conventions so any backend can read them, make content capture opt-in and redacted, and keep 100% of errors and negative-feedback runs when sampling.

SeniorHow do you roll out a new model version safely?

Pin the current model version. Run the full offline suite (regression, capability, safety, cost and latency) on the candidate, several trials each. Shadow it on real traffic to compare outputs and costs, then canary it to a small share behind a flag with online judges, error and cost alerts, and an automated rollback rule. Watch for behavior changes in tool calling and refusal rates, not only quality averages. Keep the old version one switch away until the new one has run a full business cycle.

MidHow do you serve an open model efficiently?

Use an inference engine such as vLLM or SGLang: continuous batching, paged KV cache, prefix caching, quantization (FP8 or INT4 with group-wise methods such as AWQ or GPTQ, after checking quality on your evals), speculative decoding for latency, and tensor parallelism for large models. Size GPU memory for weights plus KV cache at your context length and concurrency. Load-test with realistic traffic and track time to first token, inter-token latency and goodput, and autoscale on queue depth.

Seniorp95 latency of your agent is 14 seconds and the target is 6. Where do you start?

Break the 14 seconds down from traces: model time per call, number of sequential calls, tool time, queueing. Then work from the biggest item: remove sequential model calls (do fixed steps in code, merge steps), run independent tools in parallel, move routing and extraction to a small fast model, lower reasoning effort where it adds nothing, keep the prompt prefix stable for caching to cut time to first token, and stream progress so the wait feels shorter. Re-measure p95 after each change; averages hide the slow tail.

System design rounds

Lessons 14.107 and 14.122 teach system design in depth: the nine-step method, estimation, latency and availability budgets, the reference architecture and worked designs. The short version, for when you have to design on the spot:

  1. Clarify the users, the tasks, the actions allowed, volume, latency and the cost of a wrong answer.
  2. Define success as metrics: task success, pass^k, latency, cost per task, safety thresholds.
  3. Choose the shape: workflow, single agent, or multi-agent, and why.
  4. Design knowledge and tools: retrieval, structured data, tool list with risk levels.
  5. Add safety: guardrails, approvals, permissions, Rule of Two.
  6. Plan operations: evals in CI, tracing, monitoring, rollout and rollback, cost controls.
  7. Discuss trade-offs and what you would do next.
DesignDesign a customer-support agent for an e-commerce company with 50,000 conversations a day.

Clarify intents (order status, returns, refunds, policies) and the actions allowed. Shape: a router workflow sends simple intents to deterministic flows and the rest to one agent with order, refund and escalation tools; policies through hybrid RAG. Safety: refunds above a threshold need approval; injection screening on any customer-provided text; PII redaction in logs. Scale: stateless agent workers behind a gateway with caching and model routing; durable execution for refunds. Ops: regression evals with pass^3 gates, online judges on a sample, dashboards for resolution rate, handoff rate, p95 latency and cost per resolved conversation. Trade-off: more automation versus escalation rate; move the boundary as evidence accumulates.

DesignDesign an internal research agent that writes reports from company documents and the web.

Orchestrator with parallel research subagents (breadth justifies multi-agent), each with a clear sub-question, search tools (internal search with permissions, web search) and a token budget; a citation step that checks every claim against a source; a writer that produces the report from the collected notes. Long-running: checkpoint after each subagent, store notes in files, allow resume. Evaluate with a rubric judge (accuracy, citations, completeness, source quality) on 20 to 50 real research questions, plus human review. Security: web content is untrusted, so the research agents get no write tools.

DesignDesign a text-to-SQL analytics agent for business users.

A semantic layer (metrics, dimensions, joins, synonyms, verified queries) is the core; the agent writes SQL against it, shows the SQL, runs it under the user's role so masking and row policies apply, and explains results with a chart. Add clarifying questions for ambiguous terms, a query cost limit, and read-only credentials. Evaluate on verified question-and-SQL pairs by comparing result sets, not SQL text. On Databricks this is Genie; elsewhere, your own agent over dbt or Cube metrics.

DesignDesign an agent that triages and resolves IT helpdesk tickets.

Clarify: ticket volume, categories (password resets, access requests, hardware, outages), systems it can act on, and what must stay human. Shape: a classifier routes tickets; deterministic automations handle the top categories (password reset through the identity provider's API with verification); an agent with read tools (knowledge base, monitoring, CMDB) drafts resolutions for the rest; access grants go through an approval workflow with the requester's manager. Safety: least-privilege service identities per tool, no free-form shell, approval for anything that changes access. Ops: measure auto-resolution rate, reopen rate, time to resolve, and escalations; evaluate drafts with a judge calibrated on resolved tickets. Trade-off: automation rate versus reopen rate.

DesignDesign a voice agent for appointment booking at a hospital chain.

Clarify: languages (Hindi, English, regional), call volume, booking rules, and what is out of scope (medical advice). Architecture: telephony into a streaming speech pipeline (speech-to-text, LLM, text-to-speech) or a speech-to-speech realtime model, with a target of under about 800 milliseconds from the end of the caller's speech to the start of the reply; barge-in support; tools for doctor schedules and bookings with confirmation read back before committing. Safety: no diagnosis, immediate handoff for emergencies, identity verification before revealing appointments, consent and recording notices, PII redaction in transcripts. Ops: task completion, handoff rate, latency percentiles per turn, word error rate on names and dates, and sampled human review.

DesignDesign a coding agent for your company's internal repositories.

Clarify: tasks (bug fixes, tests, upgrades, reviews), languages, CI, and who merges. Harness: the agent works in an isolated sandbox with a clone of the repository, tools to read and search files, edit, run tests and linters, and open a pull request; never push to protected branches. Context: repository instructions files, code search, and the issue; subagents for exploration to keep the main context clean. Safety: no production credentials, network allowlist for package registries, secrets scanning on output, human review required for merge. Evaluate on a set of past issues with their merged fixes and tests (SWE-bench style), and track PR acceptance rate and review comments in production.

DesignDesign a document-processing agent for insurance claims.

Clarify: document types (claim forms, invoices, medical bills, photos), volume, turnaround, and the decisions it may make. Pipeline: classify documents, extract fields with a layout-aware parser plus a model with a schema, validate against policy data and business rules, flag fraud signals, and route: straight-through for simple claims within limits, human adjuster review with a prepared summary for the rest. Every extracted value carries its source page and confidence; low confidence goes to review. Ops: field-level accuracy against adjuster corrections, straight-through rate, turnaround, and fairness checks across customer groups because this affects financial outcomes (likely high-risk under the EU AI Act if used in the EU).

DesignDesign a multi-tenant agent platform for 30 product teams.

Paved road rather than a shared agent: an AI gateway (model access, virtual keys, budgets, routing, logging), a tool registry of approved MCP servers behind an MCP gateway with per-agent allowlists, a managed runtime or a deployment template with durable execution, standard OpenTelemetry tracing into one backend, an evaluation service with CI integration and release gates, guardrail defaults, a prompt registry, and an AI system register fed automatically from the gateway. Tenancy: isolation of data, memory, caches and indexes per tenant; cost attribution per team. Success: time for a new team to ship a governed agent, and the share of model traffic through the gateway.

Check your understanding

Q1In a system design round, what should you define right after clarifying requirements?

Metrics guide every later decision and show how you would know you succeeded.

Q2Someone asks "multi-agent or single agent?". What makes a strong answer?

Decision, conditions, trade-off, measurement.

Q3An agent succeeds 80% of the time per attempt. What are its pass@3 and pass^3?

pass@3 = 1 - 0.2³; pass^3 = 0.8³. Customer-facing agents need the second.

Q4Which answer to "how do you stop the agent issuing refunds it shouldn't?" is a red flag?

Prompts guide; code enforces.
