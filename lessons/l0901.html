Why this came about

Models gained vision in 2023, so they could read images and scanned documents directly, not just text extracted by separate OCR tools. Document extraction, a long-standing business problem, became one of the most practical multimodal uses, with new challenges in checking accuracy field by field.

In plain words first
Reading documents with eyes, not just text

Many documents are images: scanned invoices, photos of receipts, forms, charts. Vision-capable models can read them directly, and with structured output can extract fields such as total, date and supplier. The hard part is accuracy per field: a valid-looking result can still have one wrong digit, so production systems check fields with rules (totals add up, dates are plausible) and send low-confidence cases to a person.

How this connects

Step 1 · Extract to a schema, and validate with business rules

The goal is not text but fields: invoice number, GSTIN, line items, totals. Define them as a schema, extract into it (a model call with structured outputs in production; regular expressions here), then apply checks a schema cannot express: does the arithmetic add up, is the GSTIN well formed?

from pydantic import BaseModel, Field, model_validator

class Line(BaseModel):
    item: str
    qty: int
    rate: float
    amount: float

class Invoice(BaseModel):
    number: str = Field(pattern=r"^SK-INV-\d+$")
    gstin: str = Field(pattern=r"^\d{2}[A-Z]{5}\d{4}[A-Z][1-9A-Z]Z[0-9A-Z]$")    # the 15-character GSTIN format
    lines: list[Line]
    subtotal: float
    gst: float
    total: float

    @model_validator(mode="after")
    def arithmetic(self):
        problems = []
        if any(abs(l.qty * l.rate - l.amount) > 0.01 for l in self.lines):
            problems.append("a line amount is not qty x rate")
        if abs(sum(l.amount for l in self.lines) - self.subtotal) > 0.01:
            problems.append("lines do not add up to the subtotal")
        if abs(self.subtotal + self.gst - self.total) > 0.01:
            problems.append("subtotal + GST is not the total")
        if problems:
            raise ValueError("; ".join(problems))
        return self

def extract(text: str) -> dict:
    """Stands in for a model call with Invoice as the response schema."""
    num = lambda s: float(s.replace(",", ""))
    field = lambda label: re.search(rf"{label}: (\S+)", text).group(1)
    lines = [{"item": m[0].strip(), "qty": int(m[1]), "rate": num(m[2]), "amount": num(m[3])}
             for m in re.findall(r"^(.+?) (\d+) ([\d,]+\.\d\d) ([\d,]+\.\d\d)$", text, re.M)]
    total = lambda label: num(re.search(rf"^{label} ([\d,]+\.\d\d)$", text, re.M).group(1))
    return {"number": field("Invoice No"), "gstin": field("Seller GSTIN"), "lines": lines,
            "subtotal": total("Subtotal"), "gst": total("GST 18%"), "total": total("Total")}

invoice = Invoice.model_validate(extract(text))
print(invoice.number, invoice.gstin, len(invoice.lines), "lines, total", invoice.total)

tampered = extract(text) | {"total": 5288.46}                       # an OCR misread, or a fraudulent edit
try:
    Invoice.model_validate(tampered)
except ValueError as e:
    print("rejected:", e.errors()[0]["msg"])

rejected: Value error, subtotal + GST is not the total

Arithmetic and format checks are the cheapest, most reliable accuracy control in document AI: they catch OCR misreads, model hallucinations and tampered documents alike, without any second model. Route failures to a human review queue instead of guessing.

In production
Extraction problems seen in production
  • Plausible but wrong values: a model reads "7,499" as "7,449" or invents a missing date. Validate with business rules (totals add up, dates are in range, IDs exist) and route failures to a person.
  • Confidence that means nothing: some services return calibrated confidence per field; most models do not. Measure accuracy per field on labeled samples instead of trusting a self-reported score.
  • New document layouts: a vendor changes its invoice template and accuracy drops overnight. Monitor field-level validation failures per document source.
  • Cost at volume: vision models per page add up fast; use OCR or a prebuilt extractor for the common formats and a model for the rest.

Step 2 · Send images to a vision model

When the text layer is missing or the layout matters (stamps, handwriting, photos of receipts, charts), send the page as an image to a multimodal model, a vision-language model. Every provider accepts images inside the message content, with slightly different shapes. The lab draws a receipt with Pillow and builds each format.

from PIL import Image, ImageDraw

img = Image.new("RGB", (420, 220), "white")
draw = ImageDraw.Draw(img)
for y, line in enumerate(["KAVERI KIRANA STORE, PUNE", "Bill No 8812   21-10-2026", "Atta 5kg        1   289.00",
                          "Toor Dal 1kg    2   318.00", "TOTAL               607.00", "Paid via UPI"]):
    draw.text((20, 20 + y * 30), line, fill="black")
buf = io.BytesIO(); img.save(buf, format="PNG")
b64 = base64.b64encode(buf.getvalue()).decode()
print("image bytes:", len(buf.getvalue()))

instruction = "Extract store, bill number, date, line items and total as JSON."
openai_msg = {"role": "user", "content": [
    {"type": "text", "text": instruction},
    {"type": "image_url", "image_url": {"url": f"data:image/png;base64,{b64}", "detail": "high"}}]}
anthropic_msg = {"role": "user", "content": [
    {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": b64}},
    {"type": "text", "text": instruction}]}
gemini_contents = [{"role": "user", "parts": [
    {"inline_data": {"mime_type": "image/png", "data": b64}}, {"text": instruction}]}]

    parts = m.get("content") or m.get("parts")

Practical rules that hold across providers: images are billed by size (resize to what the task needs; a receipt rarely needs 4K), PDFs can often be sent directly as documents (Anthropic, Gemini and Bedrock accept PDF input; each page costs roughly an image plus its text), put the instruction after the image for long documents, and ask for structured output with the schema from Step 2.

The request itself is the normal chat call. Against the course's mock server (Lesson 14.92), which ignores the image but accepts the format:

Step 3 · Measure field-level accuracy

Document extraction is evaluated per field, not per document, because one wrong digit in a GSTIN matters more than a misspelled item name. Build a set of documents with known values, extract, and report accuracy for each field.

GOLD_DOCS = []
for i, lines in enumerate([[("Steel Jar 1.5L", 3, 449.0)], [("MixPro 750W Mixer Grinder", 1, 3499.0), ("Spatula", 4, 99.0)],
                           [("AirMax Table Fan", 2, 1899.0)]]):
    path, number = f"/tmp/inv_{i}.pdf", f"SK-INV-20{i}"
    make_invoice(path, number, "29AAACS9876K1Z2", lines)
    subtotal = sum(q * r for _, q, r in lines)
    GOLD_DOCS.append((path, {"number": number, "gstin": "29AAACS9876K1Z2", "n_lines": len(lines),
                             "total": round(subtotal * 1.18, 2)}))

def field_accuracy(extractor) -> dict:
    scores = {"number": 0, "gstin": 0, "n_lines": 0, "total": 0}
    for path, gold in GOLD_DOCS:
        got = extractor("\n".join(p.extract_text() for p in PdfReader(path).pages))
        predicted = {"number": got["number"], "gstin": got["gstin"], "n_lines": len(got["lines"]), "total": got["total"]}
        for f in scores:
            scores[f] += predicted[f] == gold[f]
    return {f: f"{v}/{len(GOLD_DOCS)}" for f, v in scores.items()}

def careless_extract(text: str) -> dict:
    """A plausible bug: only the first table row is read."""
    out = extract(text)
    return out | {"lines": out["lines"][:1]}

print("extractor:        ", field_accuracy(extract))
print("careless extractor:", field_accuracy(careless_extract))
What you should see
extractor:         {'number': '3/3', 'gstin': '3/3', 'n_lines': '3/3', 'total': '3/3'}
careless extractor: {'number': '3/3', 'gstin': '3/3', 'n_lines': '2/3', 'total': '3/3'}

A document-level "it worked" would have hidden the missing line item. In production, sample real documents across vendors and formats, label them, and track field accuracy and the human-review rate over time; a new vendor's invoice layout shows up as a drop in one field.

Industry practice
What document AI teams learn the hard way
  • Validation beats model choice. Arithmetic checks, format checks (GSTIN, PAN, dates) and cross-field rules catch more errors than switching to a bigger model.
  • Measure per field and per vendor or template, and keep a human review queue for anything that fails validation or has low confidence.
  • Keep the source page next to every extracted value, so reviewers and auditors can see where it came from.
  • Version prompts and schemas together: a schema change is a model-output change and needs the eval set rerun.
  • Watch cost per page: route easy, digital documents to the text layer and only hard ones to a vision model.

Exercises

Predict before you run

field_accuracy scores each field separately. If an extractor gets 9 of 10 fields right on every invoice, what share of invoices are entirely correct? (Solution P1.)

Break it on purpose

Trust the vision model's extracted total without the business-rule check. What kind of error gets through? (Solution B1.)

Debugging exercise

careless_extract scores well on clean scans and badly on phone photos. Using Step 3, what do you add to the evaluation? (Solution D1.)

Make it your own

Add a confidence threshold: send an invoice to review when any required field is missing or fails validation, and measure the review rate. (Solution M1.)

Solutions

SolutionP1 · Per-field against per-document

Possibly none: if one field is wrong on every invoice, per-field accuracy is 90% and per-document accuracy is 0%. Report both, and weight fields by business impact.

SolutionB1 · Plausible but wrong

Misread digits, a subtotal taken for the total, or a hallucinated value that looks valid. Cross-check totals against line items and tax, and route mismatches to review.

SolutionD1 · Segment by input quality

Segments by source (scan, photo, digital PDF), with per-segment accuracy, so averages do not hide failures. Add photos with glare, rotation and crops, which is what users send.

SolutionM1 · Route uncertainty to people

The goal is high accuracy on what is auto-processed and a manageable review rate. Track both; tighten or loosen rules based on errors found in review.

Check your understanding

Explain the mechanismHow do you build reliable document extraction with vision models?

Worked answer. Define a schema, extract with a vision-capable model using structured output, validate every field with business rules (formats, check digits, arithmetic), measure field-level and document-level accuracy on a labeled set segmented by document type and quality, and route failures to review. Choose between a vision model and OCR plus a text model by accuracy and cost on your documents.

A plausible wrong answer. "Vision models read documents perfectly." They misread and occasionally invent values.

Follow-ups. When is OCR plus a text model better?

Debug a failureExtraction accuracy fell for one supplier's invoices. What do you check?

Worked answer. Whether that supplier changed its template, whether its documents are now scanned differently, and which fields fail. Add samples of the new template to the eval set and adjust prompts or rules.

A plausible wrong answer. "The model got worse." The inputs changed.

Follow-ups. How would you detect template changes automatically?

Defend a designA document AI service or a general vision model for invoices?

Worked answer. A specialized document service for high volume, standard document types and its accuracy guarantees; a general vision model for varied documents, custom fields and fast iteration. Decide on your labeled set, with cost per document and review rate.

A plausible wrong answer. "The newest general model is best." Specialized services may win on standard forms.

Follow-ups. What would your labeled set contain?
