What is real and what is a stand-in

The splitter, vector store, retriever and chain are the real libraries. The embedding model is the Retrieval (RAG) section's offline LSA embedder (TF-IDF reduced with SVD) behind LangChain's interface, so the code runs without a key; real embedding models find paraphrases far better. chat is the lab rig (Lesson 14.51), which ignores the context, so this lesson checks what goes into the prompt rather than the wording of answers.

Why this came about

RAG pipelines need many interchangeable parts: loaders, splitters, embedding models, vector stores and retrievers. LangChain grew a large set of integrations for each, so a pipeline could swap one part for another without rewriting the rest.

The problem: a pipeline you built once, for one store

In the Retrieval (RAG) section you wrote a chunker, an embedder, a search function and a prompt that cites sources, all for one in-memory index. Moving to pgvector, OpenSearch or a managed vector database would mean rewriting the search code. LangChain defines an interface for each stage, so the stages can be swapped one at a time. Here is the same ShopKart help center as LangChain documents:

A Document is text plus metadata. Metadata is what lets you cite a source, filter by topic or tenant (Lesson 14.28), and trace a wrong answer back to the passage that caused it, so put it on documents at load time. Document loaders (for PDFs, web pages, Notion, S3 and hundreds more, mostly in langchain-community and partner packages) produce the same Document objects; Lesson 4.22 covers parsing quality, which matters more than the loader.

In plain words first
An open-book exam

Retrieval-augmented generation (RAG) turns a closed-book exam into an open-book one: before answering, find the few pages that matter and put them in front of the model. LangChain splits the job into swappable parts: a splitter cuts documents into chunks, an embedding model turns text into numbers so similar meanings are close, a vector store keeps and searches those numbers, and a retriever is anything you can ask for relevant chunks. You built each part by hand in the Retrieval (RAG) section; here each becomes a component you can swap without rewriting the rest.

Idea 1 · Split documents, keep their metadata

LangChain's splitters do the chunking of Lesson 14.25. Their useful extra is that every chunk keeps the metadata of the document it came from (the source, and here the start position), which is what citations and filters need later. Split the help-centre pages and look at three chunks:

from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=160, chunk_overlap=0, separators=["\n\n", "\n", ". ", " "],
                                          keep_separator="end", add_start_index=True)
chunks = splitter.split_documents(docs)
print(len(chunks), "chunks")
for c in chunks[:3]:
    print(c.metadata, "|", c.page_content)
What you should see
14 chunks
{'source': 'refund-policy.md', 'topic': 'payments', 'start_index': 0} | Refund policy. Customers can request a refund within 7 days of delivery.
{'source': 'refund-policy.md', 'topic': 'payments', 'start_index': 73} | Damaged or defective items are always refundable, even after 7 days, if reported within 30 days.
{'source': 'refund-policy.md', 'topic': 'payments', 'start_index': 170} | Refunds go back to the original payment method within 5 to 7 business days. UPI refunds usually arrive in 2 days.

RecursiveCharacterTextSplitter is Lesson 14.25's recursive chunking: try the first separator, and split further with the next only when a piece is still over chunk_size. Two things to notice. chunk_size counts characters by default, not tokens; use RecursiveCharacterTextSplitter.from_tiktoken_encoder(...) to count tokens. And every chunk kept its document's metadata, plus a start_index, so a citation can point to the exact place in the source.

Idea 2 · Embeddings behind an interface

Every embedding model in LangChain has the same two methods: embed_documents for the texts you index and embed_query for a question. Anything with those two methods can be plugged into any vector store. To show how little is needed, this class wraps the small offline embedder from the Retrieval (RAG) section in that interface:

import numpy as np
from langchain_core.embeddings import Embeddings
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.decomposition import TruncatedSVD
from sklearn.pipeline import make_pipeline

class LSAEmbeddings(Embeddings):
    """The Chapter 4 offline embedder behind LangChain's Embeddings interface. Swap for OpenAIEmbeddings,
    BedrockEmbeddings, GoogleGenerativeAIEmbeddings or a local sentence-transformers model."""
    def __init__(self, corpus):
        self.model = make_pipeline(TfidfVectorizer(stop_words="english", ngram_range=(1, 2)),
                                   TruncatedSVD(n_components=8, random_state=0)).fit(corpus)
    def embed_documents(self, texts):
        v = self.model.transform(texts)
        v[np.linalg.norm(v, axis=1) == 0] = 1.0                # no known words: a neutral vector, not zeros
        return (v / np.linalg.norm(v, axis=1, keepdims=True)).tolist()
    def embed_query(self, text):
        return self.embed_documents([text])[0]

embeddings = LSAEmbeddings([c.page_content for c in chunks])
print(len(embeddings.embed_query("refund")), "numbers per vector")
What you should see
8 numbers per vector

The interface is two methods: embed_documents for chunks and embed_query for questions. Every integration (OpenAIEmbeddings, BedrockEmbeddings, GoogleGenerativeAIEmbeddings, HuggingFaceEmbeddings, CohereEmbeddings) implements the same two, so swapping models is one line. Remember Lesson 14.26's rule: vectors from different models are not comparable, so a new model means re-embedding every chunk.

Idea 3 · A vector store, and searching it

A vector store takes documents and an embedding model, stores the vectors, and answers "which documents are closest to this text?". InMemoryVectorStore keeps everything in a Python list, which is enough for learning; the same calls work on pgvector, Qdrant, OpenSearch and the rest. Search it twice, the second time with a metadata filter:

from langchain_core.vectorstores import InMemoryVectorStore

store = InMemoryVectorStore.from_documents(chunks, embeddings)
for doc, score in store.similarity_search_with_score("How long does a UPI refund take?", k=2):
    print(f"{score:.2f} | {doc.metadata['source']} | {doc.page_content[:60]}")

only_orders = store.similarity_search("How long does a UPI refund take?", k=2, filter=lambda d: d.metadata["topic"] == "orders")
print([d.metadata["source"] for d in only_orders])
What you should see
0.97 | refund-policy.md | Refund policy. Customers can request a refund within 7 days 
0.72 | shipping.md | Shipping and delivery. Metro cities get delivery in 2 to 3 d
['shipping.md', 'shipping.md']

InMemoryVectorStore is for learning and tests. Production stores implement the same methods: PGVector (langchain-postgres), OpenSearchVectorSearch, ElasticsearchStore, QdrantVectorStore, PineconeVectorStore, Azure AI Search, Vertex AI Vector Search and others. The second search used a metadata filter: only orders documents were searched, so the refund question got shipping passages. Filters are how permissions are enforced at retrieval time (Lesson 14.28). Each store has its own filter syntax (a function here, a dictionary or a query language elsewhere), which is the one part of the code that does not port unchanged.

Idea 4 · A retriever, and a chain that cites

A retriever is the runnable form of search: a question in, documents out. That lets it sit in a chain:

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

retriever = store.as_retriever(search_kwargs={"k": 2})       # a runnable: question in, documents out

def format_docs(found):
    return "\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in found)

rag_prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer only from the context, and cite the [source] you used.\n\nContext:\n{context}"),
    ("human", "{question}"),
])
rag = {"context": retriever | format_docs, "question": RunnablePassthrough()} | rag_prompt | chat | StrOutputParser()

question = "How long does a UPI refund take?"
print(rag_prompt.invoke({"context": format_docs(retriever.invoke(question)), "question": question}).to_messages()[0].content)
print("answer:", rag.invoke(question)[:40])
What you should see
Answer only from the context, and cite the [source] you used.

Context:
[refund-policy.md] Refund policy. Customers can request a refund within 7 days of delivery.
[shipping.md] Shipping and delivery. Metro cities get delivery in 2 to 3 days; other pin codes take 4 to 7 days.
answer: I can check order status and cancel orde

Read the first printout, not the answer: it is the exact system message the model receives, with each passage tagged by its source, which is what makes Lesson 14.27's citation check possible. The dictionary at the start of rag is a RunnableParallel (Lesson 14.53): the question goes both to the retriever and straight through.

Idea 5 · A retrieval tool for an agent

Give an agent a retrieval tool and it decides when to search and what to search for, which is agentic RAG (Lesson 14.31). response_format="content_and_artifact" returns two things: text for the model, and the documents themselves for your code, attached to the ToolMessage but never sent to the model:

from langchain.tools import tool

@tool(response_format="content_and_artifact")
def search_help_center(query: str):
    """Search ShopKart's help center. Returns passages with their source file."""
    found = retriever.invoke(query)
    return format_docs(found), found                      # text for the model, documents for your code

msg = search_help_center.invoke({"type": "tool_call", "id": "call_1", "name": "search_help_center",
                                 "args": {"query": "express delivery price"}})
print(type(msg).__name__, "|", msg.content.splitlines()[0][:70])
print("artifact:", [d.metadata["source"] for d in msg.artifact])
What you should see
ToolMessage | [shipping.md] Orders above INR 499 ship free. Express delivery costs I
artifact: ['shipping.md', 'shipping.md']

The artifact is how your application shows citations, checks that an answer's sources were actually retrieved, or logs which documents each answer used, without asking the model to repeat them.

Measure it: does the change help?

The the Retrieval (RAG) section question set, scored by whether the right document comes back:

GOLD = [   # the labeled questions from Lesson 4.7, scored here by source document
    ("My mixer arrived broken two weeks ago, can I still get my money back?", "refund-policy.md"),
    ("How long does a UPI refund take?", "refund-policy.md"),
    ("Do I pay for shipping on a 600 rupee order?", "shipping.md"),
    ("Can I stop an order that hasn't left the warehouse yet?", "cancellation.md"),
    ("Is there an extra charge if I pay cash when it arrives?", "cod.md"),
    ("I forgot my password", "account.md"),
    ("The TV was dead when it came out of the box", "warranty.md"),
    ("What does faster delivery cost?", "shipping.md"),
]

def hit_rate(r):
    return sum(any(d.metadata["source"] == want for d in r.invoke(q)) for q, want in GOLD) / len(GOLD)

for name, r in [("similarity k=1", store.as_retriever(search_kwargs={"k": 1})),
                ("similarity k=3", store.as_retriever(search_kwargs={"k": 3})),
                ("mmr k=3", store.as_retriever(search_type="mmr", search_kwargs={"k": 3, "fetch_k": 8}))]:
    print(f"{name:15} hit rate {hit_rate(r):.2f}")

k3 = store.as_retriever(search_kwargs={"k": 3})
for q, want in GOLD:
    got = [d.metadata["source"] for d in k3.invoke(q)]
    if want not in got:
        print("missed:", q, "->", got)
What you should see
similarity k=1  hit rate 0.88
similarity k=3  hit rate 0.88
mmr k=3         hit rate 0.88
missed: My mixer arrived broken two weeks ago, can I still get my money back? -> ['cancellation.md', 'shipping.md', 'cod.md']

Three retrievers, the same score. Retrieving three passages instead of one, or diversifying them with MMR (maximal marginal relevance), did not fix the one miss, because the miss is not about how many passages come back: the LSA embedder cannot connect "money back" and "broken" with "refundable" and "damaged". Changing k would only add tokens to every prompt. The fixes that address this kind of miss are hybrid search with keywords and reranking (Lesson 5.22), query rewriting (Lesson 14.30) and a real embedding model. That is the habit the Retrieval (RAG) section teaches: measure the change on the same questions before keeping it.

Check your mental model
  • ✗ "A retriever returns only relevant chunks."
    ✓ It returns the top k by similarity, relevant or not. Measure, filter and grade.
  • ✗ "Splitting loses the source."
    ✓ Each chunk keeps its metadata, which is how answers cite where they came from.
  • ✗ "Changing the embedding model is a one-line change."
    ✓ Every stored vector must be recomputed with the new model; mixing models gives meaningless scores.

What the library replaces

You wrote in the Retrieval (RAG) section LangChain gives you
DOCS with an ID per document Document with metadata, and loaders that produce them
chunk() (Lesson 14.25) RecursiveCharacterTextSplitter, and splitters for Markdown, HTML, code and tokens
embedder.fit_transform (Lesson 14.26) The Embeddings interface, with one integration per provider
search_dense over a NumPy array A VectorStore with similarity search, filters and MMR, the same interface for every store
Building the context string with sources A retriever in a chain, or a retrieval tool with artifacts

What it does not replace: parsing documents well, choosing chunk boundaries, hybrid search and reranking tuned on your eval set, and permission filters you have tested. Hybrid search, rerankers and other advanced retrievers exist as LangChain integrations, but which ones help is still decided by measurement.

Solutions

SolutionP1 · One chunk per document

Six: every document is under 1,000 characters, so none is split. Retrieval then returns whole documents, so a citation can only point to a document, not a passage, and each prompt carries more text that is not the answer. Small chunks give precise matches; Lesson 14.30's small-to-big retrieval matches on small chunks and passes the model the larger section.

SolutionB1 · An empty result looks like "no documents"

A filter on a missing key matches nothing, so the search silently returns an empty list. In a permission filter, a typo in a key, or a tenant ID written under a different name, either hides everything, which looks like "no relevant documents", or, with a filter written the other way round, hides nothing. Test permission filters with known documents for each role (Lesson 14.28), and alert when a retrieval that normally returns results returns none.

SolutionD1 · split_text drops metadata

split_text takes plain text and returns plain strings, so the chunks never had a source, and from_texts stored them without metadata. Joining all documents first also lets a chunk cross from one document into the next. Split the documents themselves:

store2 = InMemoryVectorStore.from_documents(splitter.split_documents(docs), embeddings)

Then each chunk carries its source and topic again. Add a test that every stored chunk has a source.

SolutionM1 · Let the agent choose the topic
from typing import Literal

@tool(response_format="content_and_artifact")
def search_topic(query: str, topic: Literal["payments", "orders", "products", "account"] | None = None):
    """Search ShopKart's help center, optionally only one topic: payments, orders, products or account."""
    keep = (lambda d: d.metadata["topic"] == topic) if topic else None
    found = store.similarity_search(query, k=2, filter=keep)
    return format_docs(found), found

for args in [{"query": "refund timing"}, {"query": "refund timing", "topic": "orders"}]:
    msg = search_topic.invoke({"type": "tool_call", "id": "c", "name": "search_topic", "args": args})
    print(args, "->", [d.metadata["source"] for d in msg.artifact])

{'query': 'refund timing'} -> ['refund-policy.md', 'shipping.md']
{'query': 'refund timing', 'topic': 'orders'} -> ['shipping.md', 'shipping.md']

Because topic is a Literal, the tool's schema lists the allowed values, so the model can only choose a real topic. A topic filter chosen by the model is a relevance aid only; permission filters must come from the signed-in user, never from the model's arguments (Lesson 15.22).

Check your understanding

Explain the mechanismWalk through LangChain's retrieval components and what each one is for.

Worked answer. Loaders turn sources into Document objects with text and metadata. Text splitters cut documents into chunks and copy the metadata to each chunk. An Embeddings implementation turns chunks and queries into vectors. A VectorStore stores the vectors with their documents and supports similarity search, metadata filters and MMR. A retriever wraps search as a runnable, so it fits in a chain or behind a tool. Every stage is an interface, so the embedding model or the store can change without rewriting the others.

A plausible wrong answer. "The vector store does the retrieval quality; pick the best one." The store mostly decides scale, filtering and operations. Quality comes from parsing, chunking, the embedding model, hybrid search and reranking.

Follow-ups. Which part of the pipeline does not port unchanged between stores?

Debug a failureAfter moving from the in-memory store to pgvector, answers got worse. What do you check?

Worked answer. That the same embedding model, with the same settings, embedded both the chunks and the queries; a different model or dimension makes the vectors incomparable. Then the distance metric (cosine against inner product on unnormalized vectors), any approximate-index parameters such as HNSW's search width (Lesson 14.29), and filters translated into the new store's syntax. I would rerun the same eval set against both stores, and compare the top results per question to find where they diverge.

A plausible wrong answer. "pgvector is less accurate than the in-memory store." Exact search gives the same results anywhere; the difference is in configuration.

Follow-ups. How would you migrate an index without downtime (Lesson 14.26)?

Defend a designWould you build a production RAG system on LangChain's retrieval components?

Worked answer. For the plumbing, often yes: the interfaces are thin, the store integrations save real work, and retrievers fit into chains and agents. I keep the parts that decide quality, parsing, chunking rules, hybrid fusion, reranking and permission filters, in code I own and test, because those are tuned to our data. If the team needs ingestion pipelines with many connectors and index management, LlamaIndexlater · 14.88 (Lesson 14.88) or a managed search service may fit better; the deciding factor is the eval set, not the framework.

A plausible wrong answer. "Frameworks are only for prototypes; write everything by hand." Writing your own store clients adds code without improving retrieval.

Follow-ups. What would your retrieval eval look like before launch?
