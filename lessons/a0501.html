The problem

In plain words first

Before a computer can learn anything from text, the text has to be cut into pieces it can count. Tokenization decides where one piece ends and the next begins ("don't" is one piece or two?). Stemming chops word endings by rule so that "connect", "connected" and "connecting" count as the same thing, even if the result ("connect", but also "univers" for "university") is not a real word. Lemmatization looks words up properly ("ran" becomes "run", "better" becomes "good") but needs to know whether the word is a verb, a noun or an adjective. Each choice changes what the model sees.

A model cannot read "The cats were running." It reads integers.

Every NLP system opens with the same three questions. Where does a word start. What is the root of the word. How do we treat "run", "running", "ran" as the same thing when it helps, and as different things when it doesn't.

Get tokenization wrong and the model learns from garbage. If your tokenizer treats don't as one token but do n't as two, the training distribution splits. If your stemmer collapses organization and organ to the same stem, topic modeling dies. If your lemmatizer needs part-of-speech context but you don't pass it, verbs get treated as nouns.

This lesson builds the three preprocessing steps from scratch, then shows how NLTK and spaCy do the same work so you can see the tradeoffs.

The idea

Three operations. Each has a job and a failure mode.

Tokenization splits a string into tokens. "Token" is deliberately vague because the right granularity depends on the task. Word-level for classical NLP. Subword for transformers. Character for languages without whitespace.

Stemming chops suffixes with rules. Fast, aggressive, dumb. running -> run. organization -> organ. That second one is the failure mode.

Lemmatization reduces a word to its dictionary form using grammar knowledge. Slower, accurate, needs a lookup table or morphological analyzer. ran -> run (needs to know "ran" is past tense of "run"). better -> good (needs to know comparative forms).

Rule of thumb. Stem when speed matters and you can tolerate noise (search indexing, rough classification). Lemmatize when meaning matters (question answering, semantic search, anything the user will read).

The same idea as a formula

Word frequencies are extremely uneven. Rank the distinct words of a corpus by frequency; Zipf's law says the r-th most frequent appears about

f(r)≈rsf(1)​,s≈1

times: the top few hundred words make up about half of all tokens, while most distinct words appear once or twice.

The vocabulary keeps growing. Heaps' law: after reading n tokens, the number of distinct words is about V(n)=Knβ with β≈0.4–0.6. Ten times more text gives roughly three times more distinct words, so a word-level vocabulary never closes, which is why modern models use subword tokens (Lesson 5.4 onwards).

What stemming and lemmatisation do to counts. Both map several surface forms to one key, so they shrink V and pool the counts of rare forms, helping count-based models (bag of words, TF-IDF) on small data. A stemmer is a fixed set of rules: Porter's step 1a rewrites sses → ss, ies → i, keeps ss, and drops a final s. A lemmatiser is a lookup keyed by (word, part of speech): (were, VERB) → be.

Tokenisation as a function. A tokenizer maps a string to a sequence, text↦(t1​,…,tn​); every later count, vector and model input depends on it, so the same tokenizer must be used at training and at inference.

Step 1a only strips plural s, so "running" survives it. The lemmatizer turns "were" into "be" and "running" into "run" only when they are tagged as VERBs (the -ing fallback is for verbs): the POS tag decides the lemma. That is why Step 4 calls the missing tagger "the missing piece".

Check your mental model
  • ✗ "Stemming and lemmatization are two speeds of the same thing."
    ✓ Stemming applies suffix rules and can merge unrelated words; lemmatization maps to dictionary forms and needs the part of speech. "Use it" shows Porter turning "organization", "organ" and "organic" into the same stem.
  • ✗ "Tokenizing English is just splitting on spaces."
    ✓ Contractions, abbreviations ("U.S."), numbers with units ("3pm"), emails and URLs all need decisions, and libraries make different ones.
  • ✗ "Normalising more is always better for a classifier."
    ✓ Every merge loses information ("organ" is not "organization"), and preprocessing must be identical at training and inference.

Step 1 · a regex word tokenizer

The simplest useful tokenizer splits on non-alphanumeric characters while keeping punctuation as its own tokens. Not perfect, not final, but it runs in one line.

import re

def tokenize(text):
    return re.findall(r"[A-Za-z]+(?:'[A-Za-z]+)?|[0-9]+|[^\sA-Za-z0-9]", text)

Three patterns in order of precedence. Words with optional inner apostrophe (don't, it's). Pure numbers. Any single non-whitespace non-alphanumeric character as a standalone token (punctuation).

>>> tokenize("The cats weren't running at 3pm.")
['The', 'cats', "weren't", 'running', 'at', '3', 'pm', '.']

Failure modes to notice. 3pm splits to ['3', 'pm'] because we alternated between letter runs and digit runs. Good enough for most tasks. URLs, emails, hashtags all break. For production, add patterns before the general ones.

Step 2 · a Porter stemmer (step 1a only)

The full Porter algorithm has five phases of rules. Step 1a alone covers the most frequent English suffixes and teaches the pattern.

def stem_step_1a(word):
    if word.endswith("sses"):
        return word[:-2]
    if word.endswith("ies"):
        return word[:-2]
    if word.endswith("ss"):
        return word
    if word.endswith("s") and len(word) > 1:
        return word[:-1]
    return word

>>> [stem_step_1a(w) for w in ["caresses", "ponies", "caress", "cats"]]
['caress', 'poni', 'caress', 'cat']
Checked

This session was run when the page was built: every result above is exactly what Python prints.

Read the rules top-down. The ies -> i rule is why ponies -> poni, not pony. Real Porter has step 1b that would fix it. Rules compete. Earlier rules win. The order matters more than any single rule.

Step 3 · a lookup-based lemmatizer

Lemmatization proper needs morphology. A tractable teaching version uses a small lemma table and a fallback.

LEMMA_TABLE = {
    ("running", "VERB"): "run",
    ("ran", "VERB"): "run",
    ("runs", "VERB"): "run",
    ("better", "ADJ"): "good",
    ("best", "ADJ"): "good",
    ("cats", "NOUN"): "cat",
    ("cat", "NOUN"): "cat",
    ("were", "VERB"): "be",
    ("was", "VERB"): "be",
    ("is", "VERB"): "be",
}

def lemmatize(word, pos):
    key = (word.lower(), pos)
    if key in LEMMA_TABLE:
        return LEMMA_TABLE[key]
    if pos == "VERB" and word.endswith("ing"):
        return word[:-3]
    if pos == "NOUN" and word.endswith("s"):
        return word[:-1]
    return word.lower()

>>> lemmatize("running", "VERB")
'run'
>>> lemmatize("cats", "NOUN")
'cat'
>>> lemmatize("better", "ADJ")
'good'
>>> lemmatize("watched", "VERB")
'watched'
Checked

The last case is the key teaching moment. watched is not in our table and our fallback only handles ing. Real lemmatization covers ed, irregular verbs, comparative adjectives, plurals with sound changes (children -> child). This is why production systems use WordNet, spaCy's morphologizer, or a full morphological analyzer.

Step 4 · pipe them together

def preprocess(text, pos_tagger=None):
    tokens = tokenize(text)
    stems = [stem_step_1a(t.lower()) for t in tokens]
    tags = pos_tagger(tokens) if pos_tagger else [(t, "NOUN") for t in tokens]
    lemmas = [lemmatize(word, pos) for word, pos in tags]
    return {"tokens": tokens, "stems": stems, "lemmas": lemmas}

The missing piece is a POS tagger. Phase 5 · 07 (POS Tagging) builds one. For now, default everything to NOUN and acknowledge the limitation.

Use it: the same idea with real libraries

NLTK and spaCy ship the production versions. A few lines each.

NLTK

import nltk
nltk.download("punkt_tab")
nltk.download("wordnet")
nltk.download("averaged_perceptron_tagger_eng")

from nltk.tokenize import word_tokenize
from nltk.stem import PorterStemmer, WordNetLemmatizer
from nltk import pos_tag

text = "The cats were running."
tokens = word_tokenize(text)
stems = [PorterStemmer().stem(t) for t in tokens]
lemmatizer = WordNetLemmatizer()
tagged = pos_tag(tokens)


def nltk_pos_to_wordnet(tag):
    if tag.startswith("V"):
        return "v"
    if tag.startswith("J"):
        return "a"
    if tag.startswith("R"):
        return "r"
    return "n"


lemmas = [lemmatizer.lemmatize(t, nltk_pos_to_wordnet(tag)) for t, tag in tagged]

word_tokenize handles contractions, Unicode, edge cases your regex misses. PorterStemmer runs all five phases. WordNetLemmatizer needs the POS tag translated from NLTK's Penn Treebank scheme to WordNet's abbreviation set. The translation wiring above is the bit most tutorials skip.

spaCy

import spacy

nlp = spacy.load("en_core_web_sm")
doc = nlp("The cats were running.")

for token in doc:
    print(token.text, token.lemma_, token.pos_)

spaCy hides the whole pipeline behind nlp(text). Tokenization, POS tagging, and lemmatization all run. Faster than NLTK at scale. More accurate out of the box. The tradeoff is that you cannot easily swap individual components.

When to pick which

Situation Pick
Teaching, research, swapping components NLTK
Production, multi-language, speed matters spaCy
Transformer pipeline (you'll tokenize with the model's tokenizer anyway) Use tokenizers / transformers and skip classical preprocessing

The two failure modes nobody warns you about

Most tutorials teach the algorithms and stop. Two things will bite a real preprocessing pipeline, and they are almost never covered.

Reproducibility drift. NLTK and spaCy change tokenization and lemmatizer behavior between versions. Even today the tools disagree: NLTK and spaCy split can't into ca + n't, while this lesson's regex keeps it whole (see "Use it"), and an upgrade can move such splits just as silently. Your model was trained on one distribution. Inference now runs on a different one. Accuracy quietly degrades and nobody knows why. Pin library versions in requirements.txt. Write a preprocessing regression test that freezes expected tokenization of 20 sample sentences. Run it on every upgrade.

Training / inference mismatch. Train with aggressive preprocessing (lowercase, stopword removal, stemming), deploy on raw user input, watch performance crater. This is the single most common production NLP failure. If you preprocess during training, you must run the identical function during inference. Ship preprocessing as a function inside the model package, not as a notebook cell the serving team rewrites.

Reading this output

The tokenizers disagree on almost every hard case. The lesson's regex keeps "can't" whole but shreds "U.S.", the email and the URL; NLTK splits "ca" + "n't" and breaks the URL into pieces; spaCy keeps the email and URL whole and splits "3pm". None is "right"; what matters is using the same one everywhere. Porter merges "organization", "organ" and "organic" (and three "gener-" words) into one stem, which is the noise you accept for its speed. WordNet only lemmatizes "running" or "better" correctly when told the part of speech. On Emma, stemming shrinks the vocabulary by over a third, lemmatizing with the default noun tag by much less, because it only merges plurals and other noun forms.

Recap
What to keep from this lesson
  • Tokenization defines the units; every library makes different choices on contractions, numbers, emails and URLs.
  • Stemming strips suffixes by rule: fast, but can merge unrelated words; rule order matters.
  • Lemmatization maps to dictionary forms and needs the part of speech to be right.
  • Normalisation trades information for a smaller vocabulary; measure the trade-off on your data.
  • Pin library versions and apply identical preprocessing at training and inference.

Solutions

SolutionP1 · Raw > lower > lemma > stem

Raw tokens give the most distinct items, lower-casing removes the capitalised duplicates, noun lemmatization merges plurals and similar forms, and Porter stemming shrinks the vocabulary the most, by over a third relative to lower-cased words (the printed counts). The stemmer's extra shrinkage is partly real merging ("walks", "walked", "walking") and partly the collisions shown above.

SolutionB1 · Rule order decides everything

With the plain s rule first, every word ending in s loses just that letter before the more specific rules are checked: "caresses" becomes "caresse", "ponies" becomes "ponie", and "caress" becomes "cares", a different word. Only "cats" comes out the same as before. The specific suffixes (sses, ies, ss) must be tested before the general one; that ordering is most of what the Porter algorithm is.

Industry practice
What's current (2024–2026)
  • LLM pipelines skip stemming. Subword tokenizers (Lesson 5.4) replaced stemming and lemmatisation as preprocessing for neural models; normalising Unicode (NFKC) and whitespace is still worth doing.
  • Search engines still stem. Elasticsearch, OpenSearch and Lucene analysers apply language-specific stemmers and stop-word lists for keyword (BM25) search, which is half of most hybrid search systems.
  • spaCy and Stanza remain the standard libraries for tokenisation, lemmas and sentence splitting in production NLP pipelines.

Example input: "I'm classifying 10k customer support emails into 8 categories. English. Accuracy matters more than latency."

Example output:

- Tokenization: spaCy `en_core_web_sm`. Better edge-case handling than regex; faster than NLTK at 10k docs.
- Preprocessing: lemmatize, do not stem. Category classifiers benefit from merged inflections; stemming is too aggressive and hurts rare classes.
- Calls: `nlp = spacy.load("en_core_web_sm")`; `[t.lemma_ for t in nlp(text) if not t.is_punct]`.
- Failure to test: contractions with apostrophes in customer slang (e.g., `"aint'"`, `"y'all'd"`) — sample 20 real messages and confirm tokens match expectations before training.

Exercises

  1. Easy. Extend tokenize to keep URLs as single tokens. Test: tokenize("Visit https://example.com today.") should produce one URL token.
  2. Medium. Implement Porter step 1b. If a word contains a vowel and ends in ed or ing, remove it. Handle the double-consonant rule (hopping -> hop, not hopp).
  3. Hard. Build a lemmatizer that uses WordNet as a lookup table but falls back to your Porter stemmer when WordNet has no entry. Measure accuracy on a tagged corpus against plain WordNet and plain Porter.
