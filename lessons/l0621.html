import os, sqlite3, json, warnings
from mockllm import start                                # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langchain.tools import tool
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.types import Command

warnings.filterwarnings("ignore")
chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock")
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

@tool
def cancel_order(order_id: str) -> str:
    """Cancel a ShopKart order that has not shipped yet."""
    return f"{order_id} cancelled"
Why this came about

Some companies cannot use a hosted agent service and need agents inside their own APIs and infrastructure. This lesson builds the serving layer by hand with FastAPI, showing what the platform would otherwise provide.

The problem: you need the API without the platform

Lesson 14.86's Agent Server gives you threads, runs, interrupts and streaming over HTTP. Some teams cannot use it: the platform team runs everything on its own FastAPI stack, the license or data rules do not fit, or the agent is one feature inside an existing service. Then you build the thin service yourself. The hard parts are not the HTTP routes; they are durable state, approvals that resume the right run, and making sure one customer can never reach another's conversation.

In plain words first
Building the counter yourself

Agent Server gives you a ready-made service. Sometimes you need your own: your company's API conventions, an existing web app, or a platform you already run. Then your web framework (FastAPI here) receives requests, checks who is calling, picks the right thread for that customer, calls the compiled graph, and streams the result back. Everything Agent Server did for you becomes a few lines you own, which is the point and the cost.

Idea 1 · An agent behind your own API

This is a complete small service: a FastAPI application with two routes in front of the agent from Lesson 14.75. One route takes a customer's message and runs the agent; the other takes a person's decision on a paused action and resumes the run. Conversations are saved in SQLite, so they survive a restart. Read the two route functions first; the rest is set-up.

from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel

if os.path.exists("support.db"):
    os.remove("support.db")
agent = create_agent(chat, tools=[get_order_status, cancel_order],
                     middleware=[HumanInTheLoopMiddleware(interrupt_on={"cancel_order": True})],
                     checkpointer=SqliteSaver(sqlite3.connect("support.db", check_same_thread=False)))
USERS = {"token-ravi": "C-42", "token-meera": "C-77"}            # your identity provider in real life

def customer_for(authorization: str) -> str:
    customer = USERS.get(authorization.removeprefix("Bearer "))
    if not customer:
        raise HTTPException(401, "unknown token")
    return customer

def thread(customer: str, conversation: str) -> dict:
    return {"configurable": {"thread_id": f"{customer}:{conversation}"}}   # threads are scoped to the customer

class Message(BaseModel):
    text: str

class Decision(BaseModel):
    approve: bool
    reason: str = ""

app = FastAPI()

@app.post("/conversations/{conversation}/messages")
def send(conversation: str, msg: Message, authorization: str = Header()):
    cfg = thread(customer_for(authorization), conversation)
    out = agent.invoke({"messages": [{"role": "user", "content": msg.text}]}, cfg, version="v2")
    if out.interrupts:
        req = out.interrupts[0].value["action_requests"][0]
        return {"status": "needs_approval", "action": req["name"], "args": req["args"]}
    return {"status": "answered", "reply": out.value["messages"][-1].content}

@app.post("/conversations/{conversation}/decision")
def decide(conversation: str, d: Decision, authorization: str = Header()):
    cfg = thread(customer_for(authorization), conversation)
    if not agent.get_state(cfg).next:
        raise HTTPException(409, "nothing is waiting for a decision")
    decision = {"type": "approve"} if d.approve else {"type": "reject", "message": d.reason}
    out = agent.invoke(Command(resume={"decisions": [decision]}), cfg, version="v2")
    return {"status": "answered", "reply": out.value["messages"][-1].content}

Two routes cover a conversation with approvals. A message runs the agent; if the agent pauses for approval, the route returns the pending action instead of a reply. A decision resumes the paused run with a Command (Lesson 14.82). Calling it as a client would:

from fastapi.testclient import TestClient

api = TestClient(app)
ravi = {"Authorization": "Bearer token-ravi"}
print(api.post("/conversations/1/messages", json={"text": "Where is A-1002?"}, headers=ravi).json())
print(api.post("/conversations/1/messages", json={"text": "Please cancel A-1002"}, headers=ravi).json())
print(api.post("/conversations/1/decision", json={"approve": True}, headers=ravi).json())
What you should see
{'status': 'answered', 'reply': 'Here is what I found: A-1002 is processing'}
{'status': 'needs_approval', 'action': 'cancel_order', 'args': {'order_id': 'A-1002'}}
{'status': 'answered', 'reply': 'Here is what I found: A-1002 cancelled'}

The checkpointer is a database, so a paused cancellation survives a deploy, and the decision can come from another worker. In production, use PostgresSaver (or AsyncPostgresSaver with an async service), and move long runs to a background worker so the HTTP request does not wait for the whole agent.

Idea 2 · Keep customers apart

The thread ID is built from the authenticated customer and the conversation, never from the URL alone:

meera = {"Authorization": "Bearer token-meera"}
r = api.post("/conversations/1/decision", json={"approve": True}, headers=meera)       # same conversation id
print(r.status_code, r.json())
r = api.post("/conversations/1/messages", json={"text": "hi"}, headers={"Authorization": "Bearer nope"})
print(r.status_code, r.json())
What you should see
409 {'detail': 'nothing is waiting for a decision'}
401 {'detail': 'unknown token'}

Meera used Ravi's conversation number and found nothing to approve, because her requests address C-77:1, not C-42:1. An unknown token is refused before the agent runs. This is the same rule as memory namespaces (Lesson 14.83): identity comes from authentication, and every key that stores customer data includes it. On Agent Server, the equivalent is a custom auth handler (@auth.authenticate to identify the user, @auth.on to add an owner filter to threads), configured in langgraph.json.

Idea 3 · Front ends and the v3 event stream

LangGraph 1.2 added stream_events(version="v3"), which returns a run object with separate views over one event stream, instead of filtering chunks by mode yourself:

plain = create_agent(chat, tools=[get_order_status])
stream = plain.stream_events({"messages": [{"role": "user", "content": "Status of A-1002?"}]}, version="v3")
for i, message in enumerate(stream.messages, start=1):        # one entry per model call
    tokens = list(message.text)                                # the call's text, token by token
    print(f"model call {i}: {len(tokens)} tokens: {''.join(tokens)!r}")
print("final:", stream.output["messages"][-1].text)
What you should see
model call 1: 0 tokens: ''
model call 2: 8 tokens: 'Here is what I found: A-1002 is processing '
final: Here is what I found: A-1002 is processing

The first model call produced no text, because it only asked for a tool; the second streamed the answer. Other views include values (state snapshots), tool_calls, subgraphs, interrupts and output. In langgraph 1.2.24 this API prints a warning that it is experimental, so pin your version if you adopt it, and keep the stable stream modes of Lesson 14.84 for code that must not change.

Two things to know before you build on it. First, read each view as it arrives. A loop that reads all of a reasoning model's thinking before it starts reading the answer will show the answer only at the end, even though its tokens arrived on time; the LangChain manual measured an answer appearing about 9 seconds late this way. Read views concurrently, or iterate the raw events. Second, from langchain-core 1.7 (October 2026) a streaming tool call arrives as tool-call-delta events that carry only the new part of the arguments, where older versions repeated all the arguments so far. Upgrade clients before servers: Python clients need langchain-core 1.6.13 or later, and the JavaScript framework packages (@langchain/react and its siblings) 1.2.6 or later.

For React front ends, LangGraph's useStream hook (from @langchain/langgraph-sdk/react) connects to an Agent Server or a compatible API, and gives the component the messages as they stream, the thread, interrupts waiting for approval, a submit function and loading state:

const thread = useStream({ apiUrl: "https://support.shopkart.example", assistantId: "support" });
thread.submit({ messages: [{ type: "human", content: "Where is A-1002?" }] });
// thread.messages updates token by token; thread.interrupt holds a pending approval

LangChain's Agent Chat UI is a ready-made interface built on it, useful for internal tools and testing.

Idea 4 · Tests in CI: record once, replay forever

Tests that call a real model are slow and flaky; tests with hand-written scripts (Lesson 14.77) drift from what the real model does. A cassette records the real model's replies once and replays them in CI:

from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langchain_core.messages import messages_to_dict, messages_from_dict

class Replay(GenericFakeChatModel):
    def bind_tools(self, tools, **kwargs):
        return self

# 1. Record once, against the real model (here the lab rig), and save the model's replies.
live = create_agent(chat, tools=[get_order_status])
recorded = live.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})
json.dump(messages_to_dict([m for m in recorded["messages"] if m.type == "ai"]), open("cassette.json", "w"))

# 2. In CI, replay them: no network, no cost, the same model behavior every time.
replies = messages_from_dict(json.load(open("cassette.json")))
replayed = create_agent(Replay(messages=iter(replies)), tools=[get_order_status])
again = replayed.invoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})
print("recorded:", recorded["messages"][-1].content)
print("replayed:", again["messages"][-1].content)
print("tool ran again during replay:", [m.content for m in again["messages"] if m.type == "tool"])
What you should see
recorded: Here is what I found: A-1001 is shipped
replayed: Here is what I found: A-1001 is shipped
tool ran again during replay: ['A-1001 is shipped']

The replay used no network, but your tools ran again, so the test still checks your code. Re-record when you change the model or the prompt, and review the new cassette like code.

Idea 5 · Evals as a pull-request gate

The last check before a change is merged: run a fixed set of questions with known answers through the agent, compute the share it gets right, and fail the build if that share is under a threshold. Three cases are enough to show the mechanism; a real gate has dozens, drawn from past failures.

CASES = [("Where is A-1001?", "A-1001 is shipped"), ("Where is A-1002?", "A-1002 is processing"),
         ("Where are A-1001 and A-1002?", "A-1002 is processing")]
THRESHOLD = 0.9


def eval_gate(agent) -> bool:
    passed = sum(expected in agent.invoke({"messages": [{"role": "user", "content": q}]})["messages"][-1].content
                 for q, expected in CASES)
    score = passed / len(CASES)
    print(f"eval: {passed}/{len(CASES)} = {score:.0%} (gate {THRESHOLD:.0%}) ->", "PASS" if score >= THRESHOLD else "FAIL")
    return score >= THRESHOLD

ok = eval_gate(create_agent(chat, tools=[get_order_status]))
# In CI: sys.exit(0 if ok else 1), so a pull request that lowers the score cannot be merged.
What you should see
eval: 3/3 = 100% (gate 90%) -> PASS

Run the eval suite in CI on every pull request that touches prompts, tools, models or retrieval, and fail the build below the threshold. For real models, compare against the main branch's score on the same cases with several runs per case (Lesson 14.118), rather than a fixed threshold alone, so noise does not block merges and regressions do not slip through.

Debugging exercise
Debugging exercise: anyone can approve anyone's cancellation

After a refactor, support staff report that a customer approved a cancellation in someone else's conversation:

def thread_buggy(customer: str, conversation: str) -> dict:
    return {"configurable": {"thread_id": conversation}}             # the bug is on this line

thread = thread_buggy
meera = {"Authorization": "Bearer token-meera"}
api.post("/conversations/7/messages", json={"text": "Please cancel A-1002"}, headers=ravi)
print("Meera approves Ravi's cancellation:", api.post("/conversations/7/decision", json={"approve": True}, headers=meera).json())

What it printed:

Meera approves Ravi's cancellation: {'status': 'answered', 'reply': 'Here is what I found: A-1002 cancelled'}

Find the bug, explain why it is a security incident, and fix it. (Solution D1.)

Make it your own

Add a GET /conversations/{conversation}/pending route that returns the action waiting for approval, if any, using the thread's state. (Solution M1.)

Solutions

SolutionP1 · A second message starts a new run

Sending new input to a paused thread starts a new run (Lesson 14.82), which pauses again with a second interrupt; the first pending decision is effectively abandoned. The service should check agent.get_state(cfg).next before running a new message and either reject it ("a decision is pending"), queue it, or cancel the pending action explicitly: the double-texting choice from Lesson 14.86.

SolutionB1 · No cassette, no test

open("cassette.json") raises FileNotFoundError, so the test fails. That is the right outcome: CI must never fall back to calling the real model silently. Commit cassettes, and make recording an explicit command run by a person.

SolutionD1 · The thread ID forgot the customer

thread_buggy builds the thread ID from the conversation number alone, so /conversations/7 is the same thread for every customer, and Meera resumed Ravi's paused run. It is a security incident because one customer acted on another's order, and could also read their conversation. Scope every thread to the authenticated identity:

def thread(customer: str, conversation: str) -> dict:
    return {"configurable": {"thread_id": f"{customer}:{conversation}"}}

api.post("/conversations/8/messages", json={"text": "Please cancel A-1002"}, headers=ravi)
print("Meera:", api.post("/conversations/8/decision", json={"approve": True}, headers=meera).status_code)
print("Ravi: ", api.post("/conversations/8/decision", json={"approve": True}, headers=ravi).json()["status"])

Meera: 409
Ravi:  answered

Add a test with two customers for every route, and review all code that builds thread IDs and store namespaces.

SolutionM1 · A pending-approval route

Read state = agent.get_state(cfg); if state.next is empty, return {"pending": None}; otherwise take the interrupt from state.tasks[0].interrupts[0].value["action_requests"][0] and return its name and arguments. Scope cfg with the same thread(customer_for(authorization), conversation) helper, so the route cannot reveal another customer's pending action.

Explain the mechanismHow would you serve a LangGraph agent from your own API?

Worked answer. A web framework such as FastAPI with routes for messages and decisions, a database checkpointer (Postgres), thread IDs built from the authenticated user and the conversation, interrupts returned to the client as pending actions and resumed with Command(resume=...), streaming over server-sent events from the graph's stream, and background workers for long runs. Plus tracing, rate limits and the double-texting policy. Agent Server provides most of this; building it yourself is for when it does not fit.

A plausible wrong answer. "Wrap agent.invoke in a POST route." That works until the first approval, deploy or second message.

Follow-ups. How would you stream tokens from a FastAPI route?

Debug a failureUsers occasionally see another user's conversation history. Where do you look?

Worked answer. At how thread IDs are built and where they come from: from authentication, never from the URL or the client alone; then caching layers that might key responses without the user; then store namespaces. Reproduce with two test users on the same conversation number, and add that as a permanent test.

A plausible wrong answer. "The model leaked memory." The model has no memory; the application shared a thread.

Follow-ups. How would you detect cross-tenant access in logs?

Defend a designRecord-and-replay cassettes or live model calls in CI?

Worked answer. Cassettes for the tests that run on every commit: fast, free, deterministic, still exercising your tools and wiring. Live calls in a scheduled eval job and before releases, where the real model's behavior is the thing under test and variation is measured. Re-record cassettes when the model or prompt changes, and review the diff.

A plausible wrong answer. "Always live, to test the real thing." Then CI is slow, costly and flaky, and people start ignoring it.

Follow-ups. How do you know a cassette has gone stale?
