Why this came about

Agents built prompt-first behaved unpredictably and were hard to review. Teams began writing specifications first, with contracts for tools, budgets and failure handling, the same discipline as other critical software.

In plain words first
A specification before the code

Designing a production agent starts with writing down what it must and must not do: its users, the tasks it handles, its tools and their permissions, the shape of its inputs and outputs, its budgets for cost and time, and how each likely failure is handled. That specification becomes the contract for building, testing and reviewing the agent.

Most production incidents with agents were designed in. Nobody decided what the agent must never do, so nothing stopped it; nobody decided what "done" meant, so it stopped too early or never; a tool returned 40,000 rows, so the context overflowed. These decisions are cheap on a whiteboard and expensive in an incident review. This lesson is the whiteboard.

The agent spec: one page, decided before code

The spec is the agent's charter. It is short, it is versioned with the code, and every reviewer reads it first. A good spec answers twelve questions:

# Question Example (a refund agent) Why it matters later
1 Who are the users, and through which channel? Support staff in the helpdesk; customers via chat for status only Identity, latency budget, tone, who can approve
2 Which intents are in scope? Order status, refund eligibility, refund under 5,000 INR, address change before dispatch Eval suite shape; routing
3 What is explicitly out of scope? Legal threats, chargebacks, account deletion These become escalations and refusal tests
4 What is the autonomy level per intent? Status L3, refund L2, address change L2 (Lesson 14.105) Approval design, release plan
5 What may it never do? Refund twice for one order; refund above order value; change a dispatched order Hard rules become hooks and tool checks, not prompt lines
6 Which tools, with which effects? get_order (read), issue_refund (write, money), notify (write, external) Risk tiers, scopes, approvals (Lesson 14.110)
7 Which data may it see, and whose? The requesting customer's orders only; no card data Delegated identity; redaction; tenant isolation
8 What does success mean, as numbers? 90% correct resolution on the suite; under 2% wrong refunds; p95 under 60 seconds The release gate (Lesson 14.116)
9 What are the budgets per run? 12 steps, 0.40 USD, 120 seconds Runaway loops and bills
10 When does it escalate, to whom, with what? Uncertain, out of scope, or angry customer: to tier 2 with a handoff summary Handoff quality (Lesson 14.120)
11 What happens when a dependency is down? Orders API down: say so, create a callback ticket, never guess Degraded modes (Lesson 14.111)
12 Who owns it? Payments AI team; on-call rotation; product owner Incidents, changes, sunsetting
Tip
Write the "never" list first

Questions 3 and 5 are the ones teams skip and regret. Each "never" line should map to something that enforces it: a tool argument check, a policy rule, a hook, a database constraint. If you cannot name the enforcer, the line is a hope, not a rule.

Choose the shape with the least autonomy that works

Lesson 14.8 covers the patterns. In production, decide the shape per intent, and prefer the most deterministic shape that meets the quality bar:

If the intent is... Shape Why
Fixed steps every time (status lookup, form filling) A workflow: code calls the model for the fuzzy step only Cheapest, fastest, easiest to test and audit
A few known paths chosen by the request A router to small workflows or narrow agents Each path is evaluated and released separately
Open-ended, but within one domain and toolset A single agent with a bounded loop Flexible without coordination costs
Several distinct skills, contexts or permissions Specialists behind a supervisor, or handoffs Separate contexts and scopes; each specialist testable (Lesson 14.12)
Long, verifiable work (code, research, migrations) An agent inside a harness with a spine and a verifier Finishes across context windows (Lesson 14.13)
From the field
Factory and Two Sigma: shape and scope follow purpose

Factory describes the multi-agent architecture behind its coding product as three roles: an orchestrator, workers and validators, connected by validation contracts and structured handoffs, with adversarial verification. It argues for serial over parallel execution where work depends on earlier results, and for choosing the model per role (talk, 19 min). Two Sigma's John Feminella lists, among five controls for giving agents real autonomy, tool access that follows an agent's declared purpose: the purpose in the spec decides the tools, not the other way round (talk, 19 min).

Tool contracts: the agent-computer interface, hardened

Lesson 14.4 covers tool design for model accuracy. Production adds a second reader: the systems the tool touches. A production tool contract has eight parts:

Part Rule Failure it prevents
Name and description One verb, one object; say when to use it and when not to The model picking a near-duplicate tool
Typed arguments Enums for closed sets, formats for IDs and dates, bounds for amounts Hallucinated values that pass as strings
Effect class Declare read, write, external (sends something out) or destructive Approvals and retries applied to the wrong tools
Idempotency Writes take an idempotency key; the tool returns the original result on a repeat Double refunds after a retry or resume
Bounded output Page, truncate and summarize; never return unbounded rows Context overflow and cost spikes
Actionable errors Errors say what went wrong and what to do next, in words the model can act on Retry loops on errors that will never succeed
Dry run Writes support dry_run=true to preview the effect Approvals without a clear picture of the change
Version and owner Contracts are versioned; breaking changes get a new version A tool that changed shape silently breaking agents

The linter below checks tool definitions against these rules. Run it in CI next to your MCP server or tool registry.

import re

TOOLS = [
    {"name": "get_order", "description": "Look up one order by its ID. Use before any refund or address change.",
     "effect": "read", "params": {"order_id": {"type": "string", "pattern": r"^[A-Z]-\d{4}$"}},
     "max_items": 1, "version": "1.2", "owner": "orders-team"},
    {"name": "search_orders", "description": "Search orders.", "effect": "read",
     "params": {"query": {"type": "string"}}, "version": "1.0", "owner": "orders-team"},
    {"name": "issue_refund", "description": "Refund an order, fully or partly. Never refund more than the order total.",
     "effect": "write", "params": {"order_id": {"type": "string", "pattern": r"^[A-Z]-\d{4}$"},
                                   "amount_inr": {"type": "number", "minimum": 1, "maximum": 5000},
                                   "reason": {"type": "string", "enum": ["damaged", "late", "wrong_item", "other"]}},
     "idempotency": "order_id", "dry_run": True, "errors": {"OVER_LIMIT": "Amount exceeds the order total; ask the customer."},
     "version": "2.0", "owner": "payments"},
    {"name": "refund_order", "description": "Refunds orders", "effect": "write",
     "params": {"id": {"type": "string"}, "amount": {"type": "string"}}, "version": "0.9"},
    {"name": "delete_customer", "description": "Delete a customer record.", "effect": "destructive",
     "params": {"customer_id": {"type": "string"}}, "idempotency": "customer_id", "version": "1.0", "owner": "crm"},
]

def lint(tools):
    issues = []
    words = {t["name"]: set(re.split(r"[_\W]+", t["name"])) for t in tools}
    for t in tools:
        n, p = t["name"], t["params"]
        if len(t["description"].split()) < 6:
            issues.append((n, "description too short to say when to use it"))
        if t["effect"] in ("write", "destructive", "external"):
            if not t.get("idempotency"):
                issues.append((n, "write without an idempotency key"))
            if not t.get("dry_run"):
                issues.append((n, "write without a dry_run preview"))
            if not t.get("errors"):
                issues.append((n, "no documented, actionable errors"))
        if t["effect"] == "destructive":
            issues.append((n, "destructive tool exposed to an agent: require approval or remove"))
        if t["effect"] == "read" and "max_items" not in t:
            issues.append((n, "read tool with unbounded output"))
        for arg, spec in p.items():
            if spec["type"] == "string" and not (spec.get("enum") or spec.get("pattern")) and arg not in ("query", "reason_text"):
                issues.append((n, f"argument '{arg}' is a free string; add a pattern or enum"))
            if arg in ("amount", "amount_inr") and spec["type"] != "number":
                issues.append((n, f"argument '{arg}' should be a number with bounds"))
        if not t.get("owner"):
            issues.append((n, "no owning team"))
        for other in tools:                       # same effect and a shared noun: likely near-duplicates
            shared = (words[n] & words[other["name"]]) - {"get", "search", "list"}
            if other["name"] < n and other["effect"] == t["effect"] and shared:
                issues.append((n, f"overlaps with '{other['name']}': the model may confuse them"))
    return issues

for name, msg in lint(TOOLS):
    print(f"{name:16} {msg}")

refund_order is the tool most teams have somewhere: added early, loosely typed, never removed, and now a near-duplicate of the real refund tool. Delete it or hide it from the agent; an agent cannot misuse a tool it never sees.

Where state lives

An agent run touches four kinds of state. Mixing them up is the root of many production bugs:

State Lives in Example Rule
Conversation The context window and transcript What the user said, recent tool results Disposable; can be summarized or truncated
Run state A durable store owned by the runtime (checkpoints) Step reached, plan, pending approval, idempotency keys used Survives crashes; one writer; versioned schema
Memory A memory store with provenance (Lesson 14.11) Customer prefers email; resolved issue history Written deliberately, scoped per user or tenant, expirable
System of record The business system (orders, CRM, ledger) Refund issued, address changed The truth. The agent reads it before acting and never infers it from the transcript

The most common mistake is treating the transcript as the system of record: "I already refunded this" because the transcript says so, when the refund call actually timed out. Always re-read the system of record before a write, and let idempotency keys make the write safe to repeat.

Failure mode and effects analysis, for agents

FMEA is an engineering method from aerospace and automotive: list how each part can fail, score each failure for severity, likelihood and detectability (1 to 5, where 5 is worst and for detectability means "hard to notice"), multiply into a risk priority number (RPN), and fix from the top. It fits agents well because their failures are many, varied and easy to overlook.

FAILURES = [
    # (component, failure mode, effect, severity, likelihood, detectability, mitigation)
    ("issue_refund", "called twice after a timeout", "customer refunded twice", 4, 3, 4, "idempotency key enforced by the payments API"),
    ("model", "invents an order total", "wrong refund amount", 4, 2, 3, "amount must come from get_order; bounds check in the tool"),
    ("retrieval", "returns an outdated refund policy", "promise the policy no longer allows", 3, 3, 4, "policy version on every chunk; freshness check"),
    ("loop", "repeats the same lookup forever", "cost spike, user waits", 2, 3, 2, "step budget and repeated-call detection"),
    ("chat input", "prompt injection in a customer message", "agent follows attacker instructions", 5, 2, 4, "untrusted input never selects tools with money effects; approval above threshold"),
    ("orders API", "down for 20 minutes", "agent guesses order status", 3, 2, 2, "explicit degraded mode: say unavailable, create callback"),
    ("handoff", "escalation without context", "customer repeats everything", 2, 4, 3, "structured handoff packet (Lesson 12.16)"),
    ("model upgrade", "provider changes model behavior", "silent quality drop", 3, 3, 4, "pinned versions; re-run evals before any upgrade (Lesson 12.15)"),
]
ranked = sorted(FAILURES, key=lambda f: -(f[3] * f[4] * f[5]))
print(f"{'RPN':>4}  {'component':13} {'failure':40} mitigation")
for comp, mode, effect, s, l, d, fix in ranked:
    print(f"{s * l * d:>4}  {comp:13} {mode:40} {fix}")
top = [f for f in ranked if f[3] * f[4] * f[5] >= 40]
print(f"\n{len(top)} failure modes at RPN 40 or more must have a mitigation built and tested before launch.")

Two lessons hide in the ranking. Detectability matters as much as severity: a double refund that nobody notices for a week scores higher than a loud outage. And most mitigations are not prompts: they are keys, bounds, versions and budgets.

Hands-on lab
Lab P2 · Design before you build
  1. Write the twelve-question spec for an agent you plan to build. Keep it to one page.
  2. Run the tool linter on your real tool definitions (export them from your framework or MCP server). Fix every finding or write down why not.
  3. Draw the four kinds of state for one run of your agent and name the store for each.
  4. Run an FMEA with at least ten failure modes. Take the top three and write the mitigation, the test that proves it works, and the module that teaches it.
  5. Ask a colleague to attack the spec: what is out of scope that users will ask for anyway, and what "never" line has no enforcer?
Check your mental model
  • ✗ "Agents are too unpredictable to specify."
    ✓ Behaviour, limits, tools and failure handling can all be specified and tested.
  • ✗ "Failure modes are found in production."
    ✓ List them in the design and decide each response in advance.
  • ✗ "The prompt is the specification."
    ✓ The prompt implements part of it; permissions, budgets and tests implement the rest.

Exercises

Predict before you run

The agent's spec says "answer refund questions". Rewrite it as a contract with inputs, outputs, allowed actions and failure behavior. (Solution P1.)

Break it on purpose

Leave failure modes out of the design. A tool times out. What does the agent do? (Solution B1.)

Debugging exercise

An agent passes its evals but users complain it is "unhelpful". The spec has no definition of helpful. Fix the spec. (Solution D1.)

Make it your own

Write a failure-mode table for the refund flow: failure, detection, behavior, test. (Solution M1.)

Solutions

SolutionP1 · Specs as contracts

Inputs: a customer message and the signed-in customer. Outputs: an answer citing policy, or a handoff. Allowed actions: read orders, start refunds up to INR 5,000 with approval above. Failure: say what is unknown and hand off.

SolutionB1 · Design for failure

Whatever the model improvises: retry endlessly, apologize vaguely or invent an answer. Specify behavior per failure (timeout, empty result, permission denied) and test each.

SolutionD1 · Measurable success criteria

Define success per task: resolved without handoff, correct policy cited, steps completed. Measure it, and add the complaints' cases to evals.

SolutionM1 · A failure-mode table

Rows such as order not found, payment service down, amount over limit, conflicting policies, injection in the message; each with how it is detected, what the agent does and the test that proves it.

Explain the mechanismHow do you design a production agent?

Worked answer. Start from the task and its success criteria, write a contract (inputs, outputs, allowed actions, limits), choose the least autonomous structure that works, design tools and permissions, list failure modes with behavior and tests, and define evals and observability before building.

A plausible wrong answer. "Pick a framework and start prompting." The design decides more than the framework.

Follow-ups. Where do approvals belong in the design?

Debug a failureAn agent's behavior differs between two teams' expectations. What is missing?

Worked answer. A written contract that both agreed on. Write it, align it with evals, and treat changes to it as reviewed changes.

A plausible wrong answer. "Prompt tweaks will fix it." The disagreement is about the spec.

Follow-ups. Who should own the spec?

Defend a designIs writing a spec worth it for a fast-moving AI team?

Worked answer. Yes, a short one: it aligns people, defines evals and makes failures discussable. It should be a page, updated as you learn, not a long document.

A plausible wrong answer. "Specs slow us down." Rework from unclear goals is slower.
