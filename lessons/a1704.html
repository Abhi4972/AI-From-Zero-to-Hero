In plain words first
The idea in one line

Modern serving-engine throughput rests on three compounding defaults, not a single trick. PagedAttention is always on. Continuous batching injects new requests into the active batch between decode iterations. Chunked prefill slices long prompts so decode tokens never starve. Turn all three on and a Llama 3.3 70B FP8 on one H100 SXM5 pushes 2,200-2,400 tok/s at 128 concurrent — roughly 25% above vLLM's own default and 3-4x a naive PyTorch loop. This lesson reads the scheduler and attention kernel of vLLM — the reference engine for all three techniques — at a level you can diagram, and ends with a toy continuous batcher in code/main.py that schedules prefill and decode the way vLLM does.

The problem

In plain words first

A model server answers many users at once by putting their requests into one batch and running them through the model together. The hard part is that requests have different lengths and arrive at different times. vLLM, the most used open-source server, does three things to keep the GPU full of useful work. PagedAttention stores each request's KV cache (the keys and values the model remembers for earlier tokens) in small fixed-size blocks, the way an operating system pages memory, so little is wasted. Continuous batching lets requests join and leave the batch after every generated token instead of waiting for the slowest one. Chunked prefill cuts a long prompt into slices so it does not freeze everyone else's output while it is read.

A naive PyTorch serve loop runs one request at a time: tokenize, prefill, decode until EOS, return. At one user this works. At one hundred, it is a queue of patient people. The obvious fix — static batching — pads every request to the longest prompt in the window, pads every decode to the longest expected output, and stalls the whole batch on the slowest sequence. You pay for padding you never use, and fast requests wait for slow ones.

vLLM solves three problems at once. PagedAttention stops KV cache fragmentation from eating 60-80% of GPU memory the way classic contiguous allocation does. Continuous batching lets requests join and leave the batch between each decode iteration, so the batch is always full of real work. Chunked prefill breaks a 32k-token prompt into ~512-token slices that interleave with decode, so a long prompt does not freeze every decode token on the GPU.

The 2026 production default is all three on. You need to understand what each one does because the failure modes are all on the scheduler, not the model.

Idea 1 · PagedAttention as a virtual memory system

A KV cache is num_layers × 2 × num_heads × head_dim × seq_len × bytes_per_element per sequence. For Llama 3.3 70B at 8192 tokens, that is roughly 1.25 GB per sequence in BF16. If you pre-reserve 8192 slots for every request but the average request only uses 1500 tokens, you waste roughly 82% of the HBM you reserved. Classic batching pays this waste.

PagedAttention borrows the idea from OS virtual memory. KV cache is not contiguous per sequence. It is allocated in fixed-size blocks (default 16 tokens). Each sequence has a block table that maps its logical token positions to physical block IDs. When a sequence grows past its allocated blocks, one more block is added. When it finishes, its blocks return to the pool.

Fragmentation drops from 60-80% (classic) to under 4% (PagedAttention). You do not enable PagedAttention with a flag — it is the only allocator vLLM ships. The knob is --gpu-memory-utilization (default 0.9), which tells vLLM how much HBM to reserve for KV blocks after loading weights and activations.

Idea 2 · Continuous batching at the iteration level

The old "dynamic batching" waited for a window (say 10 ms) to fill a batch, then ran prefill + decode + decode + decode until every sequence finished. Fast sequences left early and sat idle while the GPU finished the slow ones.

Continuous batching operates between each decode step. Call the set of running sequences the RUNNING list. At each iteration:

  1. Any sequence in RUNNING that just hit EOS or max_tokens is removed.
  2. The scheduler looks at the waiting queue. If there are free KV blocks, it admits new sequences (prefill or resumed).
  3. The forward pass runs on whatever is now in RUNNING, emitting one new token per sequence.

The batch size is never padded to a fixed number. Sequences at different positions in their output share one fused forward. In 2026 vLLM this is called the V1 scheduler. The key invariant: the scheduler runs once per decode iteration, not once per request.

Idea 3 · Chunked prefill protects the ITL tail

Prefill is compute-bound. A 32k-token prompt on Llama 3.3 70B takes ~800 ms of pure prefill on one H100. While prefill runs, decode tokens for every other sequence in the batch wait. In a serving loop, the first-token latency (TTFT) of one long prompt becomes the inter-token latency (ITL) blip for dozens of other users.

Chunked prefill splits prefill into fixed-size chunks (default 512 tokens) and schedules each chunk as a unit. Between chunks the scheduler can advance decode sequences by one token. You trade a small absolute prefill latency hit (a few ms per chunk) for much lower decode-time jitter. P99 ITL under mixed load drops from ~50 ms to ~15 ms in published benchmarks.

Idea 4 · The three defaults interact

All three features assume each other. PagedAttention gives the scheduler a fine-grained KV resource to trade against. Continuous batching needs that fine-grained resource so admitting a new sequence does not force a global reshuffle. Chunked prefill is a decision the scheduler makes on the same RUNNING list — it is one more scheduler policy, not a separate system.

You do not need to know every flag. You need to know what the scheduler optimizes: goodput under KV-block budget, subject to chunked prefill slicing.

Idea 5 · Check the compatibility matrix

Check every feature combination against the compatibility matrix for your exact vLLM version before enabling all of them at once, because what composes changes between releases. In v0.18.0 the feature matrix marks speculative decoding as compatible with chunked prefill and prefix caching, and the speculative-decoding page lists two known incompatibilities: pipeline parallelism through v0.15.0, and draft-model speculation through v0.10.0. For the draft method itself, the 2026 default is often EAGLE-3 ("method": "eagle3"), covered in Phase 17 · 05.

Idea 6 · Numbers you should remember

  • Llama 3.3 70B FP8, H100 SXM5, 128 concurrent, all three on: 2,200-2,400 tok/s.
  • Same model, default vLLM (no chunked prefill): ~1,800 tok/s.
  • Same model, naive PyTorch forward loop: ~600 tok/s.
  • KV fragmentation waste under PagedAttention at production load: <4%.
  • P99 ITL under mixed load: ~15 ms with chunked prefill, ~50 ms without.

Idea 7 · What the scheduler looks like

while True:
    finished = [s for s in RUNNING if s.is_done()]
    for s in finished: release_blocks(s); RUNNING.remove(s)

    while WAITING and have_free_blocks_for(WAITING[0]):
        s = WAITING.pop(0)
        allocate_initial_blocks(s)
        RUNNING.append(s)

    # schedule prefill chunks + decode in one batch
    batch = []
    for s in RUNNING:
        if s.in_prefill:
            batch.append(next_prefill_chunk(s))   # e.g. 512 tokens
        else:
            batch.append(decode_one_token(s))     # 1 token

    run_forward(batch)                            # one fused GPU call

The same idea as a formula

KV cache per sequence. For a model with L layers, Hkv​ key-value heads of size d, stored in b bytes per number, a sequence of n tokens needs

KV bytes=2⋅L⋅Hkv​⋅d⋅n⋅b

The 2 counts keys and values. Reserving nmax​ tokens per request when it uses only n wastes the fraction 1−n/nmax​ of that reservation.

Worked example
Waste from reserving the maximum

Llama 3.3 70B has 80 layers and 8 KV heads of size 128. In BF16 (b=2), one token needs 2 × 80 × 8 × 128 × 2 = 327,680 bytes, about 0.33 MB.

  1. Reserving 8,192 tokens per request: 8,192 × 0.33 MB ≈ 2.7 GB per request.
  2. A request that really uses 1,500 tokens fills 1,500 / 8,192 ≈ 18% of it; 82% is wasted.
  3. With 16-token blocks, the same request takes ⌈1500 / 16⌉ = 94 blocks = 1,504 slots: 4 slots of waste, about 0.3%.

That difference in waste is the room continuous batching uses to fit more requests on one GPU.

Use it: the same idea with real libraries

code/main.py simulates a vLLM-style scheduler with toggleable features. Run it to see:

  • NAIVE mode: one request at a time, no batching.
  • STATIC mode: pad and wait, classic batching.
  • CONTINUOUS mode: iteration-level admission and release.
  • CONTINUOUS + CHUNKED mode: prefill slices interleaved with decode.

The output shows total throughput (tokens per virtual second), TTFT mean, and P99 ITL. The CONTINUOUS + CHUNKED row should dominate on mixed traffic.

Part 1 of 5 · Request

"""Toy continuous-batching scheduler — stdlib Python.

Simulates four serving modes on the same workload:
  NAIVE            : one request at a time, no batching
  STATIC           : pad to batch boundary, wait for slowest
  CONTINUOUS       : iteration-level admit/release
  CONTINUOUS+CHUNK : continuous + chunked prefill (512-token slices)

Reports throughput (tok / virt-sec), mean TTFT, and P99 ITL so you can
reproduce the shape of the vLLM benchmarks without a GPU. Pedagogical:
the latency constants are illustrative, not measured.
"""

from __future__ import annotations

from dataclasses import dataclass, field
from collections import deque
import random
import statistics


FORWARD_LATENCY_PER_TOKEN = 0.0005   # 0.5 ms per decode token in the batch
PREFILL_LATENCY_PER_TOKEN = 0.00004  # prefill ~12x cheaper per token than decode
BATCH_OVERHEAD = 0.0002              # fixed overhead per forward call
CHUNK_SIZE = 512
KV_BLOCK_SIZE = 16
KV_BLOCKS_AVAILABLE = 1800           # toy KV block budget


@dataclass
class Request:
    req_id: int
    prompt_len: int
    output_len: int
    arrived_at: float
    prefilled: int = 0
    generated: int = 0
    ttft: float | None = None
    last_token_at: float | None = None
    itl_samples: list[float] = field(default_factory=list)

    @property
    def in_prefill(self) -> bool:
        return self.prefilled < self.prompt_len

    @property
    def done(self) -> bool:
        return self.generated >= self.output_len

    def blocks_needed(self) -> int:
        total = self.prompt_len + self.output_len
        return (total + KV_BLOCK_SIZE - 1) // KV_BLOCK_SIZE

Part 2 of 5 · make_workload, report, simulate_naive, simulate_static

def make_workload(n: int = 60, seed: int = 7) -> list[Request]:
    rng = random.Random(seed)
    reqs = []
    now = 0.0
    for i in range(n):
        now += rng.expovariate(40.0)   # ~40 req/s arrival
        prompt_len = rng.choice([128, 256, 512, 2048, 8192])
        out_len = rng.randint(50, 300)
        reqs.append(Request(i, prompt_len, out_len, now))
    return reqs


def report(label: str, reqs: list[Request], sim_end: float) -> None:
    ttfts = [r.ttft - r.arrived_at for r in reqs if r.ttft is not None]
    itls = [dt for r in reqs for dt in r.itl_samples]
    total_out = sum(r.generated for r in reqs)
    throughput = total_out / sim_end if sim_end else 0
    mean_ttft = statistics.mean(ttfts) * 1000 if ttfts else 0
    p99_itl = sorted(itls)[int(0.99 * len(itls)) - 1] * 1000 if itls else 0
    print(f"{label:28}  throughput={throughput:6.0f} tok/s   "
          f"mean_TTFT={mean_ttft:6.1f} ms   "
          f"P99_ITL={p99_itl:5.1f} ms   finished={sum(r.done for r in reqs)}/{len(reqs)}")


def simulate_naive(reqs: list[Request]) -> float:
    """One at a time. Prefill the whole prompt, then decode until done."""
    now = 0.0
    for r in reqs:
        if now < r.arrived_at:
            now = r.arrived_at
        now += r.prompt_len * PREFILL_LATENCY_PER_TOKEN + BATCH_OVERHEAD
        r.prefilled = r.prompt_len
        r.ttft = now
        r.last_token_at = now
        for _ in range(r.output_len):
            prev = r.last_token_at
            now += FORWARD_LATENCY_PER_TOKEN + BATCH_OVERHEAD
            r.generated += 1
            r.itl_samples.append(now - prev)
            r.last_token_at = now
    return now


def simulate_static(reqs: list[Request], batch: int = 16) -> float:
    """Group into fixed batches; wait for the slowest to finish."""
    now = 0.0
    i = 0
    while i < len(reqs):
        window = reqs[i:i + batch]
        i += batch
        now = max(now, max(r.arrived_at for r in window))
        pad_prompt = max(r.prompt_len for r in window)
        pad_output = max(r.output_len for r in window)
        now += pad_prompt * PREFILL_LATENCY_PER_TOKEN + BATCH_OVERHEAD
        for r in window:
            r.prefilled = r.prompt_len
            r.ttft = now
            r.last_token_at = now
        for _ in range(pad_output):
            prev_now = now
            now += FORWARD_LATENCY_PER_TOKEN * len(window) / 16 + BATCH_OVERHEAD
            for r in window:
                if r.generated < r.output_len:
                    r.generated += 1
                    r.itl_samples.append(now - prev_now)
                    r.last_token_at = now
    return now

Part 3 of 5 · simulate_continuous

def simulate_continuous(reqs: list[Request], chunked: bool) -> float:
    waiting = deque(sorted(reqs, key=lambda r: r.arrived_at))
    running: list[Request] = []
    blocks_used = 0
    now = 0.0
    while waiting or running:
        if waiting and running and now < waiting[0].arrived_at and not running:
            now = waiting[0].arrived_at
        while waiting and waiting[0].arrived_at <= now:
            r = waiting[0]
            if blocks_used + r.blocks_needed() > KV_BLOCKS_AVAILABLE:
                break
            blocks_used += r.blocks_needed()
            running.append(waiting.popleft())
        if not running:
            if not waiting:
                break
            now = waiting[0].arrived_at
            continue

        batch_tokens = 0
        prefill_work = 0
        decoded: list[Request] = []
        for r in running:
            if r.in_prefill:
                remaining = r.prompt_len - r.prefilled
                take = min(CHUNK_SIZE if chunked else remaining, remaining)
                r.prefilled += take
                prefill_work += take
                if r.prefilled >= r.prompt_len:
                    r.ttft = now + prefill_work * PREFILL_LATENCY_PER_TOKEN
            else:
                decoded.append(r)
                batch_tokens += 1

        dt = (prefill_work * PREFILL_LATENCY_PER_TOKEN
              + batch_tokens * FORWARD_LATENCY_PER_TOKEN
              + BATCH_OVERHEAD)
        now += dt
        for r in decoded:
            prev = r.last_token_at or r.ttft or now
            r.generated += 1
            r.itl_samples.append(now - prev)
            r.last_token_at = now
            if r.ttft is None:
                r.ttft = now

        finished = [r for r in running if r.done]
        for r in finished:
            blocks_used -= r.blocks_needed()
            running.remove(r)
    return now

Part 4 of 5 · main

def main() -> None:
    print("=" * 80)
    print("TOY vLLM SCHEDULER: four modes on the same 60-request workload")
    print("=" * 80)

    base = make_workload()
    w1 = [Request(r.req_id, r.prompt_len, r.output_len, r.arrived_at) for r in base]
    end = simulate_naive(w1)
    report("NAIVE", w1, end)

    w2 = [Request(r.req_id, r.prompt_len, r.output_len, r.arrived_at) for r in base]
    end = simulate_static(w2)
    report("STATIC (batch=16, padded)", w2, end)

    w3 = [Request(r.req_id, r.prompt_len, r.output_len, r.arrived_at) for r in base]
    end = simulate_continuous(w3, chunked=False)
    report("CONTINUOUS (no chunk)", w3, end)

    w4 = [Request(r.req_id, r.prompt_len, r.output_len, r.arrived_at) for r in base]
    end = simulate_continuous(w4, chunked=True)
    report("CONTINUOUS + CHUNKED", w4, end)

    print()
    print("Read the CONTINUOUS+CHUNKED row. That is what vLLM ships as default.")
    print("The gap between STATIC and CONTINUOUS is the whole reason vLLM exists.")

Reading this output

The script's STATIC row beats CONTINUOUS on throughput, the opposite of real vLLM. Its cost model is why: FORWARD_LATENCY_PER_TOKEN charges 0.5 ms for each sequence in a decode step, so a step for 64 sequences costs 64 times a step for one, and the main advantage of batching disappears. Break it on purpose

An engineer turns off chunked prefill because "it makes TTFT worse for our long prompts". Throughput is unchanged, but users on short chats complain that answers now stall mid-sentence. What happened? (Solution B1.)

Recap
What to keep from this lesson
  • PagedAttention allocates KV cache in 16-token blocks, cutting waste from most of the reservation to a few per cent.
  • Continuous batching admits and releases requests after every token.
  • Chunked prefill slices long prompts so decode keeps moving: better P99 ITL, not better throughput by itself.
  • Batching pays because a decode step's cost is dominated by reading weights, shared by the whole batch.
  • KV bytes per token = 2 · layers · KV heads · head size · bytes per number.

- Diagnosing without the four core metrics (TTFT, ITL, throughput, concurrency). Refuse and ask for the metric set.

Solutions

SolutionP1 · STATIC against CONTINUOUS

In this toy the gap goes the wrong way: STATIC reaches about 4,000 tokens/s, CONTINUOUS under 900, because each decode step costs 0.5 ms per sequence and continuous mode is also capped by the KV block budget. On a real GPU, with near-constant step cost, continuous batching wins on decode efficiency: finished sequences leave immediately and new ones take their place instead of padding.

SolutionP4 · Fragmentation waste

(a) Contiguous allocation at 8,192 tokens with a mean use of 1,500 wastes about 1 − 1,500 / 8,192 ≈ 82% of reserved KV memory. (b) With 16-token blocks, each request wastes on average half a block, 8 tokens of about 1,500, roughly 0.5%.

SolutionB1 · Stalls mid-sentence

Without chunked prefill, each long prompt's prefill runs as one large step, and every decode sequence waits for it. Short chats see their tokens stop for hundreds of milliseconds whenever a long prompt arrives: the P99 inter-token latency jumps. Turn chunked prefill back on and, if long-prompt TTFT matters, raise the chunk size a little.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismMost explanations of continuous batching describe a prefill phase and a decode phase that take turns on the GPU. Describe what the vLLM scheduler does in one step instead. Where does chunked prefill come from in that design, and where do you read the value that controls it?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The scheduler asks the same question of every request: how many tokens does it still need to compute? Each step has a budget of tokens, set by --max-num-batched-tokens, and the running requests take their next token first. Waiting prompts fill the rest of the budget, so a long prompt is split over several steps, and chunked prefill needs no extra mechanism.

One question for every request.

A new request needs all of its prompt tokens. A running request needs one token, or more with speculative decoding. No prefill phase and no decode phase exist in the code, only a count of tokens still to compute.

The order inside a step.

  1. Each running request gets the tokens it needs, up to the budget.
  2. Waiting requests are admitted while budget and room remain. --max-num-seqs caps the running requests.

A prompt that does not fit the rest of the budget gets a part now and the rest in later steps. That is chunked prefill, and it is on by default because the budget design needs nothing else to support it.

The default depends on the memory that vLLM reads.

GPU memory that vLLM reads Budget, vllm serve Budget, LLM class --max-num-seqs, both
160 GiB or more 16,384 16,384 1,024
70 GiB or more, but not an A100 8,192 16,384 1,024
less, or unknown 2,048 8,192 256

The unified-memory machine in the manual has 121.69 GiB that the CPU and the GPU share, and its log still shows 2,048, the value for a small or unknown GPU. Read the value that your server uses before you change it. At 0.31.0 the log does not print the budget under its own name; find compile_ranges_endpoints in the engine config line, and the largest number in that list is the budget.

Why decode goes first.

Running requests come first so that a user who already sees a stream keeps seeing it. A new prompt waits for what is left. A smaller budget gives a smoother stream; a larger one gives a faster first token for long prompts. The small default of 2,048 is a choice for the stream.

Why one budget.

One budget for every kind of work keeps the scheduler simple. Prefix caching only lowers the count of tokens to compute. Speculative decoding only raises the count for a running request. The same loop serves all of them. The cost is that one number decides the balance between the first token and the stream, and no single value suits every workload.

The lesson's toy scheduler uses a fixed 512-token chunk. The real engine has no separate chunk size at 0.31.0: the chunk is what is left of the budget in that step.

Plausible wrong answers.

  • "Chunked prefill is a flag you turn on." It follows from the budget: a prompt that does not fit the rest of the budget gets part now and the rest later, so it is on by default and has no separate mechanism.
  • "New prompts go first so that the first token comes fast." Running requests take their tokens first so that a user who sees a stream keeps seeing it; a new prompt waits for the budget that is left.
  • "The budget is 2,048 on every GPU." It depends on the memory that vLLM reads: 2,048 below 70 GiB, 8,192 at 70 GiB or more, and 16,384 at 160 GiB or more, and the offline LLM class uses larger values.

Follow-ups an interviewer may ask.

  • (level 2) Prefix caching is on, and a request with a 2,048-token prompt finds 1,024 tokens in the cache. What does the scheduler count for it? Expected: 1,024 tokens still to compute; the cache only lowers the count, and the same loop serves the request.
  • (level 3) A server with 121.69 GiB of unified memory logs a budget of 2,048. Why not 8,192? Expected: the default comes from the memory that vLLM reads, and the unified machine reads as small or unknown, so it gets the small value; read compile_ranges_endpoints before you change it.
  • (level 4) Speculative decoding is on with three draft tokens. How does the budget rule change? Expected: it does not; a running request now needs more than one token per step, so its count rises, and the budget is spent in the same order.

Where it is taught. Why one token budget replaces a prefill phase and the long prompts section give the rule and the defaults, and the serving engine internals lesson has the toy scheduler.

Explain the mechanismExplain how vLLM keeps the KV cache in GPU memory. Why does it not give each request its own buffer, how does it recognize a prompt it has seen before, and what happens when the memory runs out?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The KV cache is one pool of 16-token blocks, and a request takes blocks one at a time as it grows, mapped by a small block table. A buffer per request wastes memory twice: on length that the request never reaches, and on gaps between requests of different sizes. Each full block gets a hash that is chained with the hash of the block before it, so one hash names a whole prefix, and a new request walks its chain and stops at the first miss. When no block is free, the scheduler preempts the newest request and computes it again later.

Blocks, not buffers.

At startup vLLM splits the cache into blocks of 16 tokens and keeps all of them in one pool. The blocks of a request do not need to be next to each other. A block table maps the token positions of the request to block numbers. The original paper called this PagedAttention, after the way an operating system pages memory.

The lesson gives the size of the waste that this removes. A classic allocator that reserves the full length for every request loses 60 to 80 percent of the memory to fragmentation. With blocks the waste stays under 4 percent. For a 70B model at 8192 tokens, one reserved sequence is about 1.25 GB in BF16, and a request that uses 1500 tokens wastes about 82 percent of it.

The hash chain.

When a block fills, vLLM hashes its tokens together with the hash of the block before it. The chain means that one hash names a whole prefix, not only 16 tokens. The hash also covers the other inputs that change the keys and values: the LoRA adapter, the images in the prompt, and an optional salt for each request. A new request computes the same chain over its prompt and looks each hash up in a map. Every block before the first miss is a hit and needs no compute. Only full blocks are cached, so the tail of a prompt below 16 tokens is always computed.

Since version 0.11 the hash is SHA-256 by default. A faster hash exists, and the documentation warns that a collision could return the wrong blocks or leak data between tenants.

Eviction.

A block that no request uses goes to a free list and keeps its hash. A later request with the same prefix can still use it. When vLLM needs a new block, it takes the head of the free list, the block unused the longest. Only then does the old content go away. So the cache is the pool: no separate cache memory exists, and a busy server keeps fewer old prefixes than an idle one.

When memory runs out.

A running request needs a new block every 16 tokens. If none is free, the scheduler preempts a request. Under the default first-come policy it picks the newest running request, frees all of its blocks, and puts it back at the head of the waiting queue. When the request runs again, vLLM computes its tokens again from the start. Older versions could also copy blocks to CPU memory and back; the current engine only recomputes, because the documentation judges that cheaper. The cost shows as a longer time for the preempted request and in the vllm:num_preemptions counter.

Hybrid models.

A model with sliding-window or state-space layers does not keep one entry per token in every layer. Each kind of layer gets its own group with its own page size and its own rule for a hit. The groups share one pool.

Plausible wrong answers.

  • "vLLM swaps preempted requests to CPU memory." Older versions could; the current engine only recomputes, because the documentation judges the recompute cheaper, and the cost shows in the time of that request and in the preemption counter.
  • "The prefix cache has its own memory budget." The cache is the pool; a freed block keeps its hash on the free list until a new block is needed, so a busy server keeps fewer old prefixes than an idle one.
  • "A block hash covers only its own 16 tokens." It is chained with the hash of the block before it, so one hash names a whole prefix, and it also covers the adapter, the images and the salt.

Follow-ups an interviewer may ask.

  • (level 2) Every request starts with the same 25 tokens. How many of them come from the cache? Expected: 16, one full block; the last 9 tokens are computed on every request because only full blocks are cached.
  • (level 3) Two tenants send the same system prompt. What can one learn about the other, and what field stops it? Expected: they share blocks, so the timing of one tenant can reveal what the other sent; a cache_salt per tenant goes into the hash, so the two never share a block.
  • (level 4) Under the default policy, which request does vLLM preempt when no block is free, and what does it cost? Expected: the newest running request; all of its blocks are freed, it goes to the head of the waiting queue, and its tokens are computed again from the start, which the preemption counter records.

Where it is taught. How the block pool manages KV memory explains the pool, the token budget section covers preemption, and the serving engine internals lesson gives the fragmentation numbers.

Explain the mechanismA user sends a chat request to a serving engine and the answer streams back, slowly at first and then word by word. Describe what the GPU does from the moment the request arrives until the last token. Name the phases, and name the numbers you would put on a dashboard for each of them.

Level 1 of 4 · about 6 minutes to answer well.

Short answer. A request has two phases. Prefill reads the whole prompt in one pass and writes its keys and values into the KV cache, so the GPU is busy with math. Decode then writes one token per request per step, and each step reads all the weights to do it, so the GPU waits for memory. Four numbers measure them: TTFT for the wait before the first token, TPOT and ITL for the stream, and output tokens per second for the whole server.

Prefill.

Prefill handles many prompt tokens in one step. The keys and values of every prompt token go into the KV cache. The step does a lot of math for each byte it reads, so it is compute bound. A long prompt makes the first token late.

Decode.

Decode makes one new token for each running request in each step. The step reads all the model weights once to do that, whatever the batch size. The step moves many bytes for little math, so it is memory bound. This is why a bigger batch is almost free per step on a dense model: the weights are read once for all the requests in the step.

The four numbers.

Number What it measures Who feels it
TTFT the wait from the request to the first token, mostly queue time and prefill the person who waits for the answer to start
TPOT the mean time between tokens after the first one the person who reads a long answer
ITL each gap between two tokens; its P99 shows the worst stalls the person who sees the stream stop and start
Throughput output tokens per second for all users together the person who pays for the GPU

Report the four together. A throughput number alone hides the latency that the users feel.

What load does to them.

The manual measured Qwen/Qwen3-30B-A3B with vLLM 0.31.0 from one user to 64 users at once:

Users at once Median TTFT Median TPOT Output tokens per second
1 257 ms 32.3 ms 29.5
64 965 ms 243.8 ms 239.3

With 64 users the server wrote about eight times as many tokens per second. Each user waited almost four times as long for the first token, and each token took about 7.5 times longer. A busy server is cheaper per token and slower for each user. Every tuning choice moves one of these four numbers and costs another.

One scheduler, not two stages.

The engine does not run the two phases as separate stages. In vLLM, each scheduler step has one token budget. Running requests get their next decode token first. The rest of the budget goes to prompt tokens, in chunks. A prefill is only a request with many tokens left to compute.

Plausible wrong answers.

  • "Throughput is the number to optimize, and the rest follows." Throughput is what the GPU owner pays for; the users feel TTFT and the gaps between tokens, and at 64 users the manual's server wrote eight times the tokens while each user waited about 7.5 times longer per token.
  • "Prefill and decode run as two separate stages inside the engine." The vLLM scheduler has one token budget per step; running requests get a decode token first and prompt chunks fill the rest, so the two phases mix in one step.
  • "TPOT and ITL are the same number." TPOT is the mean time per output token for one request; ITL is each gap between two tokens, and its P99 shows the stalls that the mean hides.

Follow-ups an interviewer may ask.

  • (level 1) Which of the four numbers matters most to someone who reads a long answer? Expected: TPOT, the mean gap between tokens, together with the P99 ITL for the worst stalls.
  • (level 2) Why is decode bound by memory and prefill by math? Expected: a decode step reads every weight to make one token per request, so the bytes moved dominate; a prefill step handles hundreds of prompt tokens per pass, so the math per byte is high.
  • (level 3) In the manual's run, 64 users got about eight times the output of one user. Why do the cost per token and the wait per user move in opposite directions? Expected: each decode step reads the weights once for all running requests, so more requests share one read; each request then waits for a longer step.
  • (level 4) The lesson describes a prefill phase and a decode phase. What does the vLLM scheduler have instead? Expected: one token budget per step; running requests take their next token first and prompt chunks fill the rest, so a prefill is a request with many tokens left to compute.
