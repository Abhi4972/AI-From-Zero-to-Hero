In plain words first
The idea in one line

An agent calls five tools, three MCP servers, and two sub-agents. You need one trace across all of it. The OpenTelemetry GenAI semantic conventions (still at Development status; since v1.42 in June 2026 they live in their own semantic-conventions-genai repository) are the 2026 standard, natively supported by Datadog, Langfuse, Arize Phoenix, OpenLLMetry, and AgentOps. This lesson names the required attributes, walks the span hierarchy (agent → LLM → tool), and ships a stdlib span emitter you can plug into any OTel exporter.

The problem

In plain words first

When an agent is slow or wrong, you need to see what happened inside one run: which model calls it made, how many tokens each used, which tools it called, and how long each MCP server took. Tracing gives you that. A trace is a tree of timed steps called spans, all sharing one trace id. OpenTelemetry (OTel) is the open standard for traces and metrics, and its GenAI conventions fix the names: a model call is a chat span with attributes such as gen_ai.usage.input_tokens, a tool call is an execute_tool span, an agent run is an invoke_agent span. When the agent calls an MCP server in another process, the trace id travels inside the request so the server's span joins the same tree. Prompts and answers are not recorded unless you switch that on, because they may hold private data. This lesson traces a real Qwen tool call across two processes with the OTel SDK.

A debug from February 2026: user reports "my agent sometimes takes 30 seconds to respond; other times 3 seconds." No traces. Logs show the LLM call, but not the tool dispatch, not the MCP server round-trip, not the sub-agent. You guess. Eventually you find: one MCP server occasionally hangs on a cold-start.

Without end-to-end tracing, you cannot find this. OTel GenAI fixes it.

The conventions settled in 2025-2026 under the OpenTelemetry semantic-conventions group. They define shared attribute names so Datadog, Langfuse, Phoenix, OpenLLMetry, and AgentOps all parse the same spans. Instrument once; ship to any backend.

Idea 1 · Span hierarchy

invoke_agent {agent}          (INTERNAL, or CLIENT for a remote agent)
 ├── chat {model}             (CLIENT; INTERNAL for an in-process model)
 ├── execute_tool {tool}      (INTERNAL)
 │    └── tools/call {tool}   (MCP: CLIENT span here, SERVER span in the server)
 ├── chat {model}             (CLIENT)
 └── invoke_agent {subagent}  (INTERNAL or CLIENT)

The whole thing nests under one trace id. Span ids link the parent-child relationships.

Idea 2 · Required attributes

Per the 2025-2026 semconv:

  • gen_ai.operation.name — "chat", "text_completion", "embeddings", "execute_tool", "invoke_agent".
  • gen_ai.provider.name — "openai", "anthropic", "google", "azure_openai".
  • gen_ai.request.model — requested model string (e.g. "gpt-4o-2024-08-06").
  • gen_ai.response.model — the model actually served.
  • gen_ai.usage.input_tokens / gen_ai.usage.output_tokens.
  • gen_ai.response.id — provider response id for correlation.

For tool spans:

  • gen_ai.tool.name — tool identifier.
  • gen_ai.tool.call.id — the specific call id.
  • gen_ai.tool.description — tool description (optional).

For agent spans:

  • gen_ai.agent.name / gen_ai.agent.id / gen_ai.agent.description.

Idea 3 · Span kinds

  • SpanKind.CLIENT for calls crossing a process boundary (LLM provider, MCP server).
  • SpanKind.INTERNAL for the agent's own loop steps and tool execution.

Idea 4 · Opt-in content capture

By default, spans carry metrics and timing — not prompts or completions. Large payloads and PII are off by default. Instrumentations turn content on with a switch such as OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true (the exact name and values vary by library), and many use OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental to emit the newest attribute shapes. Review carefully before enabling in prod.

Idea 5 · Events on spans

When content capture is on, it is recorded on the gen_ai.client.inference.operation.details event (older drafts used gen_ai.content.prompt and gen_ai.content.completion events, now replaced):

  • gen_ai.input.messages: the messages sent, as structured role/parts JSON.
  • gen_ai.output.messages: the messages the model returned, including tool calls.
  • gen_ai.system_instructions: the system prompt, kept separate.

A separate gen_ai.evaluation.result event records evaluation scores. Events are time-ordered within a span for detailed replay.

Idea 6 · Exporters

OTel spans export to:

  • Jaeger / Tempo. OSS, on-prem.
  • Langfuse. LLM-observability-specific; visualizes token usage.
  • Arize Phoenix. Evals + tracing combined.
  • Datadog. Commercial; natively parses gen_ai.* attributes.
  • Honeycomb. Column-oriented; query-friendly.

All speak OTLP, the wire format. Your code does not care.

Idea 7 · Propagation across MCP

When an MCP client calls a server, it puts the W3C trace context in the request's params._meta under the unprefixed keys traceparent, tracestate and baggage. This works the same on stdio and Streamable HTTP. The convention comes from the OTel MCP semantic conventions and is documented in the MCP specification by SEP-414 (Final). The official Python SDK 2.x injects it on the client and extracts it on the server automatically; the server span becomes a child of the client span.

Idea 8 · Metrics

Alongside spans, the GenAI semconv defines metrics:

  • gen_ai.client.token.usage — histogram.
  • gen_ai.client.operation.duration — histogram.
  • gen_ai.execute_tool.duration — histogram.
  • gen_ai.client.operation.time_to_first_chunk, gen_ai.invoke_agent.duration and, for self-hosted inference, gen_ai.server.time_to_first_token and gen_ai.server.time_per_output_token.
  • MCP adds mcp.client.operation.duration and mcp.server.operation.duration.

Use these for dashboards that do not need per-call detail.

Idea 9 · AgentOps layer

AgentOps (founded 2024) specializes in GenAI observability. It wraps popular frameworks (LangGraph, Pydantic AI, CrewAI) to emit OTel spans automatically. Useful if your stack uses a supported framework; use manual instrumentation otherwise.

The same idea as a formula

A trace is a tree. Every span s has a trace id T(s), its own id and a parent id p(s). For one agent run,

T(s)=T(root)∀s,duration(s)≥c:p(c)=s∑​duration(c)(for children that run one after another).
The gap between a span and its children is time spent in the span's own code: in an execute_tool span, it is the host's work around the MCP call.

Token usage adds up across spans. For the chat spans C of one run,

input tokens=c∈C∑​gen_ai.usage.input_tokens(c),
and each later call usually re-sends the whole conversation, so input tokens grow with each turn even when the new text is short.

Propagation. A traceparent value has four fields: version-traceid-parentid-flags, for example 00- then 32 hex digits of trace id, -, 16 hex digits of the caller's span id, -01 (sampled). The receiver starts its span with that parent.

Worked example
Reading one trace
  • The run is invoke_agent notes-assistant, 7.5 s.
  • First chat span: 185 input tokens (the question plus the tool schema in the template), 21 output tokens, finish reason tool_call, 2.6 s.
  • execute_tool search_notes, 36 ms, contains the SDK's client span MCP send tools/call search_notes (4 ms), which contains the server process's span tools/call search_notes (1 ms). The server span has the same trace id because the client sent traceparent in _meta.
  • Second chat span: 249 input tokens (the conversation now includes the tool call and its result), 36 output tokens, 4.2 s.
  • So almost all the time is model generation (6.8 of 7.5 s); the tool path is about 0.5% of the run. Total tokens: 434 in, 57 out.
Check your mental model
  • ✗ "The GenAI semantic conventions are stable, so names will not change."
    ✓ In 2026 they are at Development status; pin your instrumentation version.
  • ✗ "Traces include the prompts by default."
    ✓ Content is off by default; turn it on deliberately and redact.
  • ✗ "Stdio MCP servers cannot join a trace because there are no HTTP headers."
    ✓ Trace context travels in params._meta (traceparent), on any transport.
  • ✗ "A span per tool call is enough; metrics are redundant."
    ✓ Metrics such as gen_ai.client.token.usage aggregate cheaply for dashboards and alerts; spans are for single-run detail.

One agent run traced across two processes

The OTel SDK records spans in memory (a real service would use an OTLP exporter). Qwen2.5-0.5B-Instruct decides to call search_notes; the tool runs in an MCP server started as a subprocess over stdio, which exports its own spans to a file. The block merges both sets and prints the tree. About 15 seconds on a laptop CPU (model load plus two generations).

# One agent run traced with the OpenTelemetry SDK: invoke_agent -> chat -> execute_tool -> MCP client -> MCP server.
import asyncio, json, re, torch, uuid
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter
exporter = InMemorySpanExporter()                       # in production: an OTLP exporter to a collector
provider = TracerProvider(); provider.add_span_processor(SimpleSpanProcessor(exporter)); trace.set_tracer_provider(provider)
tracer = trace.get_tracer("notes-agent")
from opentelemetry.trace import SpanKind
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as tlog
from mcp import Client
from mcp.client.stdio import stdio_client, StdioServerParameters
import sys
tlog.set_verbosity_error(); torch.manual_seed(0)

M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); model = AutoModelForCausalLM.from_pretrained(M).eval()
SERVER = r'''
import json
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor, SpanExporter, SpanExportResult
class FileExporter(SpanExporter):              # a stand-in for the OTLP exporter the server would really use
    def export(self, spans):
        with open("server_spans.jsonl", "a") as f:
            for s in spans: f.write(json.dumps({"name": s.name, "kind": s.kind.name, "trace": s.context.trace_id,
                "id": s.context.span_id, "parent": s.parent.span_id if s.parent else None,
                "start": s.start_time, "end": s.end_time, "attrs": dict(s.attributes)}) + "\n")
        return SpanExportResult.SUCCESS
p = TracerProvider(); p.add_span_processor(SimpleSpanProcessor(FileExporter())); trace.set_tracer_provider(p)
from mcp.server import MCPServer
notes = MCPServer("notes", log_level="WARNING")
@notes.tool()
def search_notes(query: str) -> str:
    """Search the user's saved notes by keyword and return matching notes."""
    return json.dumps([{"title": "Q3 offsite", "text": "Offsite moved to 14 October, Goa."}])
notes.run()
'''
open("notes_server.py", "w").write(SERVER); open("server_spans.jsonl", "w").close()
SPECS = [{"type": "function", "function": {"name": "search_notes", "description": "Search the user's saved notes by keyword and return matching notes.",
          "parameters": {"type": "object", "properties": {"query": {"type": "string", "description": "keyword to search for"}}, "required": ["query"]}}}]

def chat(messages):                                     # one model call = one `chat {model}` span
    with tracer.start_as_current_span(f"chat {M}", kind=SpanKind.INTERNAL) as s:   # in-process model: INTERNAL, remote API: CLIENT
        ids = tok.apply_chat_template(messages, tools=SPECS, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
        with torch.no_grad(): out = model.generate(ids, max_new_tokens=60, do_sample=False)
        text = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
        s.set_attributes({"gen_ai.operation.name": "chat", "gen_ai.provider.name": "local.transformers",
                          "gen_ai.request.model": M, "gen_ai.response.model": M,
                          "gen_ai.usage.input_tokens": ids.shape[1], "gen_ai.usage.output_tokens": out.shape[1] - ids.shape[1],
                          "gen_ai.response.finish_reasons": ["tool_call" if "<tool_call>" in text else "stop"]})
        return text

async def run(question):
    with tracer.start_as_current_span("invoke_agent notes-assistant", kind=SpanKind.INTERNAL,
                                      attributes={"gen_ai.operation.name": "invoke_agent", "gen_ai.agent.name": "notes-assistant"}):
        messages = [{"role": "user", "content": question}]
        async with Client(stdio_client(StdioServerParameters(command=sys.executable, args=["notes_server.py"]), errlog=sys.__stderr__)) as mcp:
            for _ in range(3):
                reply = chat(messages)
                calls = re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", reply, re.S)
                if not calls: return reply
                messages.append({"role": "assistant", "content": reply})
                for raw in calls:
                    call, call_id = json.loads(raw), "call_" + uuid.uuid4().hex[:8]
                    with tracer.start_as_current_span(f"execute_tool {call['name']}", kind=SpanKind.INTERNAL,
                            attributes={"gen_ai.operation.name": "execute_tool", "gen_ai.tool.name": call["name"],
                                        "gen_ai.tool.call.id": call_id, "gen_ai.tool.type": "extension"}):
                        r = await mcp.call_tool(call["name"], call["arguments"])   # the SDK adds a CLIENT span and _meta.traceparent
                    messages.append({"role": "tool", "content": r.content[0].text})
        return "(turn limit)"

answer = asyncio.run(run("Search my notes for offsite."))
print("answer:", answer, "\n")
# Merge the agent's spans with the spans the server process exported, then print the tree.
class S:  # a tiny common shape for both sources
    def __init__(self, name, kind, trace_id, sid, parent, start, end, attrs, proc):
        self.name, self.kind, self.trace, self.id, self.parent, self.start, self.end, self.attrs, self.proc = name, kind, trace_id, sid, parent, start, end, attrs, proc
spans = [S(s.name, s.kind.name, s.context.trace_id, s.context.span_id, s.parent.span_id if s.parent else None,
           s.start_time, s.end_time, dict(s.attributes), "agent") for s in exporter.get_finished_spans()]
spans += [S(d["name"], d["kind"], d["trace"], d["id"], d["parent"], d["start"], d["end"], d["attrs"], "server")
          for d in map(json.loads, open("server_spans.jsonl"))]
spans.sort(key=lambda s: s.start); by_id = {s.id: s for s in spans}
def depth(s): return 0 if s.parent not in by_id else 1 + depth(by_id[s.parent])
print("trace ids across both processes:", {format(s.trace, "032x")[:16] + "..." for s in spans})
SHOW = ("gen_ai.usage.input_tokens", "gen_ai.usage.output_tokens", "gen_ai.tool.call.id", "gen_ai.response.finish_reasons", "mcp.method.name")
for s in spans:
    if s.attrs.get("mcp.method.name") in ("server/discover", "tools/list") : continue      # connection housekeeping
    d = depth(s); keep = {k.split(".", 1)[1]: v for k, v in s.attrs.items() if k in SHOW}
    print(f"{'  ' * d}{s.name:<{50 - 2 * d}} {s.proc:<6} {s.kind:<8} {(s.end - s.start) / 1e6:7.0f} ms  {keep}")

Reading this output

The model called the tool. Qwen answered the request with a search_notes call, the server returned the note, and the second model call wrote the answer from it.

One trace id across two processes. The set of trace ids has a single entry, although the server ran in a separate Python process and exported its spans separately. The SDK client wrote traceparent into the request's _meta, and the SDK server read it and used it as the parent.

The tree shows who waited for whom. Under execute_tool search_notes is the SDK's CLIENT span MCP send tools/call search_notes, and under that the server's SERVER span. The two connection-setup requests (server/discover, tools/list) are hidden to keep the tree short.

The chat spans carry the numbers that matter. The first used 185 input tokens and stopped with tool_call; the second used 249 input tokens because the conversation now includes the call and its result. Almost all the wall time is in the two chat spans; the MCP round trip takes milliseconds. If this agent were slow, the trace says where to look.

# Continues from the block above. Metrics from the same run, and opt-in content capture with redaction.
import os, re
from opentelemetry.sdk.metrics import MeterProvider
from opentelemetry.sdk.metrics.export import InMemoryMetricReader
reader = InMemoryMetricReader(); meter = MeterProvider(metric_readers=[reader]).get_meter("notes-agent")
tokens = meter.create_histogram("gen_ai.client.token.usage", unit="{token}")
op_dur = meter.create_histogram("gen_ai.client.operation.duration", unit="s")
tool_dur = meter.create_histogram("gen_ai.execute_tool.duration", unit="s")
for s in spans:                                   # in a real service you record these where the span ends
    if s.attrs.get("gen_ai.operation.name") == "chat":
        base = {"gen_ai.operation.name": "chat", "gen_ai.request.model": s.attrs["gen_ai.request.model"]}
        tokens.record(s.attrs["gen_ai.usage.input_tokens"], {**base, "gen_ai.token.type": "input"})
        tokens.record(s.attrs["gen_ai.usage.output_tokens"], {**base, "gen_ai.token.type": "output"})
        op_dur.record((s.end - s.start) / 1e9, base)
    if s.proc == "agent" and s.attrs.get("gen_ai.operation.name") == "execute_tool":
        tool_dur.record((s.end - s.start) / 1e9, {"gen_ai.tool.name": s.attrs["gen_ai.tool.name"]})
for m in reader.get_metrics_data().resource_metrics[0].scope_metrics[0].metrics:
    for p in m.data.data_points:
        labels = {k.replace("gen_ai.", ""): v for k, v in p.attributes.items() if k != "gen_ai.request.model"}
        print(f"{m.name:<34} {str(labels):<52} count={p.count} sum={p.sum:.3f} {m.unit}")

# Content is off by default. When an operator opts in, record it as an event and redact first.
SECRET = [(re.compile(r"[\w.+-]+@[\w-]+(?:\.[\w-]+)+"), "<email>"), (re.compile(r"\bsk-[A-Za-z0-9]{8,}"), "<api-key>")]
def redact(t):
    for rx, sub in SECRET: t = rx.sub(sub, t)
    return t
def record_content(span, messages, output):
    if os.environ.get("OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT", "false").lower() != "true": return
    span.add_event("gen_ai.client.inference.operation.details", {
        "gen_ai.input.messages": json.dumps([{"role": m["role"], "parts": [{"type": "text", "content": redact(m["content"])}]} for m in messages]),
        "gen_ai.output.messages": json.dumps([{"role": "assistant", "parts": [{"type": "text", "content": redact(output)}]}])})
msgs = [{"role": "user", "content": "Email the offsite date to priya@example.com, my key is sk-live12345678."}]
print()
for flag in ("false", "true"):
    os.environ["OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT"] = flag; exporter.clear()
    with tracer.start_as_current_span(f"chat {M}") as sp: record_content(sp, msgs, "Sent the date to priya@example.com.")
    ev = exporter.get_finished_spans()[0].events
    print(f"capture={flag:<5} events={len(ev)}", *(f"\n   {k}: {v}" for e in ev for k, v in e.attributes.items()))

Reading this output

Metrics aggregate the run. gen_ai.client.token.usage has one series per token type: 2 input samples summing to 434 tokens and 2 output samples summing to 57. gen_ai.client.operation.duration sums the two model calls in seconds, and gen_ai.execute_tool.duration has the one tool call. These are what a dashboard or an alert uses, across thousands of runs.

Content is absent unless switched on. With the switch off, the span has no events. With it on, one gen_ai.client.inference.operation.details event appears, holding gen_ai.input.messages and gen_ai.output.messages as structured JSON.

Redaction happens before recording. The email address and the API key are replaced with <email> and <api-key> in both input and output. Once a secret reaches a tracing backend, it is copied, indexed and retained; scrubbing it at the source is the only reliable place.

Use it: the same idea with real libraries

code/main.py emits OTel-shaped spans to stdout (in OTLP-JSON-like format) for an agent that calls an LLM, dispatches two tools, and makes one MCP round-trip. No real exporter — the lesson focuses on the span shape and attribute set. Paste the output into an OTLP-compatible viewer or just read it.

What to look at:

  • Trace id is shared across all spans.
  • Parent-child links are encoded via parentSpanId.
  • Required gen_ai.* attributes are populated.
  • Content capture is off by default; one scenario turns it on via env var.
Break it on purpose

Industry practice
What's current (2024–2026)
  • OTel GenAI semantic conventions: Development status; at v1.42 (June 2026) they moved to the semantic-conventions-genai repository, which also holds the MCP conventions. gen_ai.provider.name replaced the older gen_ai.system.
  • Instrumentation used in production: OpenTelemetry's own opentelemetry-instrumentation-openai-v2 and related packages, OpenLLMetry (Traceloop), OpenInference (Arize), Pydantic Logfire, and framework hooks in LangChain/LangGraph, the OpenAI Agents SDK and Google ADK.
  • MCP: SEP-414 documents traceparent in _meta; the official Python SDK 2.x creates client and server spans and propagates context automatically, as the run above shows.
  • Backends that read gen_ai.*: Datadog, Grafana Tempo, Honeycomb, Langfuse, Arize Phoenix, New Relic and others, all through OTLP.
  • On your laptop: the OTel SDK costs almost nothing; local backends such as Jaeger or Phoenix run in Docker. The model here is 0.5B in float32 on the CPU; on the RTX 4060 it would run in bf16 in well under a second per turn.

Sources: OTel GenAI semconv repository, OTel GenAI conventions explained (Dash0, Sep 2026), SEP-414, W3C Trace Context.

Recap
What to keep from this lesson
  • One trace per run: invoke_agent → chat → execute_tool → MCP client → MCP server.
  • Required on model spans: gen_ai.operation.name and gen_ai.provider.name; record model, token usage and finish reasons.
  • MCP carries traceparent in params._meta, so even stdio servers join the trace.
  • Metrics for dashboards, spans for single runs.
  • Content capture is opt-in; redact before recording and limit retention.
  • The conventions are still Development status: pin versions.

Given an agent codebase (LLM calls, tool dispatch, MCP client, sub-agents), produce an OTel GenAI instrumentation plan.

Produce:

1. Span hierarchy. Root `agent.invoke_agent` (INTERNAL) and children: `llm.chat` (CLIENT), `tool.execute` (INTERNAL), `mcp.call` (CLIENT), `subagent.invoke` (INTERNAL).
2. Attribute checklist per span. `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.usage.*`, `gen_ai.tool.name`, `gen_ai.agent.name`.
3. Propagation rule. Inject W3C traceparent on every remote call; for MCP stdio use `_meta.traceparent` as an interim field.
4. Content capture policy. Off by default; document which env var enables; name PII risks.
5. Exporter choice. Jaeger / Tempo / Langfuse / Phoenix / Datadog / Honeycomb; OTLP as the wire.

Hard rejects:
- Any plan missing trace propagation across MCP or sub-agent boundaries.
- Any plan with content capture on by default. Leaks prompts and PII.
- Any plan that emits arbitrary custom attributes without the `gen_ai.` or explicit vendor prefix.

Refusal rules:
- If the codebase uses a framework with built-in OTel auto-instrumentation (Pydantic AI, LangGraph, AgentOps), recommend the framework hook first.
- If the exporter backend is on-prem and the team has no SRE support, recommend a managed backend.
- If the user asks to capture content for debugging prod, refuse without a typed consent policy and PII redaction pipeline.

Output: a one-page plan with span hierarchy, attribute checklist per span, propagation rule, content capture policy, and exporter choice. End with the top metric to alert on (typically p95 `gen_ai.client.operation.duration`).

Exercises

  1. Run code/main.py. Count the spans and identify which is CLIENT vs INTERNAL.

  2. Turn on content capture (env var) and confirm a gen_ai.client.inference.operation.details event with gen_ai.input.messages and gen_ai.output.messages appears. Note the implications for PII.

  3. Add the tool-execution metric gen_ai.execute_tool.duration and emit it as a histogram sample per call.

  4. Propagate a traceparent from a parent agent span into an MCP request's _meta.traceparent field. Verify the MCP server would see the same trace id.

  5. Read the OTel GenAI semconv spec. Identify one attribute listed in the semconv that this lesson's code does NOT emit. Add it.

Solutions

SolutionP1 · Same trace, under the tool span

Yes. The SDK client puts the current trace context into the request's params._meta as traceparent, and the server, in its own process, starts its tools/call search_notes SERVER span with that context as its parent. So the server span appears in the same trace, under the client span MCP send tools/call search_notes, which is itself under execute_tool search_notes.

Most of the time goes to the two chat spans: generating tokens with a 0.5B model on a CPU takes seconds, while the MCP round trip takes a few milliseconds.

SolutionB1 · Debug switches become data leaks

Prompts and answers now flow into a system built for operational data, not for personal or secret data. Every user's messages, including emails, account numbers or pasted API keys, are stored for 90 days and visible to every engineer, which may break privacy law, contracts and the company's own data rules. Traces are also exported and copied (to vendors, to test environments), so the data spreads.

Instead:

  • Turn content capture on only for a short window, a small sample, or specific test accounts, and turn it off again.
  • Redact at the source (emails, keys, numbers) before the event is recorded, as in the block above.
  • Send content to a separate, access-controlled store with short retention, and keep only ids and metrics in the general backend.
  • Prefer reproducing the problem with an evaluation set over capturing real user content.
