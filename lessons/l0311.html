Why this came about

As agents took on bigger jobs, a single agent with many tools and long instructions started to confuse them. Splitting work among specialists, as human organizations do, produced multi-agent designs in 2023 and 2024 (supervisors, handoffs, crews). Experience also showed their cost, so choosing when to split became part of the skill.

In plain words first
A team instead of one overloaded person

One agent with many tools and long instructions starts to confuse them. Multi-agent designs split the work among specialists, each with short instructions and its own tools, coordinated by a supervisor that delegates, by handing the conversation from one agent to the next, or by a router. The price is more model calls, more latency and information lost at every hand-over, so a single well-equipped agent is the default and splitting needs a reason.

Single agent or multiple agents?

The steps later in this lesson build every multi-agent pattern in code. This section is the decision that comes first: do you need more than one agent at all?

This is the most debated design question in the field, and two well-known engineering posts take opposite sides:

  • Anthropic, How we built our multi-agent research system (June 2025): a lead agent spawns parallel subagents for breadth-first research. It beat a single agent by 90.2% on their internal research evaluation, but used many times more tokens (roughly 15 times a normal chat in their measurements). In their analysis, the number of tokens spent explained about 80% of the difference in results. Multi-agent pays when the task is valuable, highly parallel, and exceeds one context window.
  • Cognition, Don't Build Multi-Agents (June 2025, from building the coding agent Devin, where every edit depends on the others): splitting work across agents loses context, and subagents make conflicting decisions. Their principles: share full context, and remember that "actions carry implicit decisions". They prefer a single long-running agent with context compression.

Both are right in their domain, and they agree more than they disagree: share full context or isolate cleanly, give every subagent a precise objective, output format and boundaries, scale the effort to the task (an early version of Anthropic's system spawned 50 subagents for simple queries), and do not split work whose parts must agree with each other. A practical synthesis:

Prefer one agent when Consider several agents when
Steps depend on each other's decisions (writing code, editing one document) Subtasks are independent and parallel (researching ten companies)
The context fits one window with compression The material far exceeds one window
You need consistent decisions Different parts need different permissions, models or owners
Cost matters more than speed Speed and breadth justify several times the tokens

Multi-agent patterns

Pattern How it works Watch out for
Supervisor / orchestrator A coordinator delegates to specialists and combines results The coordinator is a bottleneck and an extra model call per hop
Agents as tools (subagents) The main agent calls a specialist like a function and gets back a short answer Return summaries, not raw dumps
Handoff / swarm The active agent transfers the conversation to another Global control is harder; log every handoff
Hierarchical Supervisors of supervisors Rarely needed; latency compounds
Blackboard architecture (shared state) All agents read and write one shared state Conflicting writes; need clear ownership
Debate / voting Several agents answer and a judge or majority decides Expensive; use for high-stakes decisions

Step 1 · A minimal agent class to compose

Every pattern below composes the same unit: an agent with a name, instructions, tools and a bounded loop. Each run writes to a shared trace, so you can see which agent did what.

import asyncio, inspect, json, time
from dataclasses import dataclass, field
from typing import Callable
from mockllm import start
from openai import OpenAI

client = OpenAI(base_url=start(), api_key="mock")
TRACE: list[dict] = []                                     # one trace across every agent in the system

def tool_schema(fn: Callable) -> dict:
    params = inspect.signature(fn).parameters
    return {"type": "function", "function": {
        "name": fn.__name__, "description": inspect.getdoc(fn) or "",
        "parameters": {"type": "object", "properties": {n: {"type": "string"} for n in params},
                       "required": list(params)}}}

def mock_model(messages, tools):
    """Call the mock endpoint; swap in any real Chat Completions endpoint."""
    r = client.chat.completions.create(model="mock-model", messages=messages, tools=tools or None)
    return r.choices[0].message, r.usage.total_tokens

@dataclass
class Agent:
    name: str
    instructions: str
    tools: list[Callable] = field(default_factory=list)
    model: Callable = mock_model
    max_steps: int = 6

    def run(self, task: str, context: list[dict] | None = None) -> str:
        registry = {t.__name__: t for t in self.tools}
        messages = [{"role": "system", "content": self.instructions}, *(context or []),
                    {"role": "user", "content": task}]
        for _ in range(self.max_steps):
            msg, tokens = self.model(messages, [tool_schema(t) for t in self.tools])
            TRACE.append({"agent": self.name, "tokens": tokens,
                          "tools": [c.function.name for c in msg.tool_calls or []]})
            if not msg.tool_calls:
                return msg.content
            messages.append(msg.model_dump(exclude_none=True))
            for call in msg.tool_calls:
                result = registry[call.function.name](**json.loads(call.function.arguments))
                messages.append({"role": "tool", "tool_call_id": call.id, "content": str(result)})
        return f"[{self.name} stopped at its step limit]"

ORDERS = {"A-1001": "delivered 3 days ago", "A-1002": "processing"}

def get_order_status(order_id: str) -> str:
    """Return the status of an order ID like 'A-1001'."""
    return f"{order_id} {ORDERS.get(order_id, 'not found')}"

orders_agent = Agent("orders", "You answer questions about order status.", tools=[get_order_status])
print(orders_agent.run("Where is A-1002?"))
print(TRACE)
What you should see
Here is what I found: A-1002 processing
[{'agent': 'orders', 'tokens': 70, 'tools': ['get_order_status']}, {'agent': 'orders', 'tokens': 70, 'tools': []}]

Step 2 · Agents as tools: the supervisor pattern

The most common and most controllable pattern: a supervisor keeps the conversation and calls specialists as if they were tools. Each specialist runs in its own clean context and returns a short answer, so the supervisor's context stays small. This is what the OpenAI Agents SDK calls agent.as_tool(), Strands calls agents as tools, ADK calls AgentTool, and LangGraph builds as a supervisor graph.

POLICIES = {"damaged": "Damaged items: full refund within 30 days of delivery."}

def lookup_policy(topic: str) -> str:
    """Return the ShopKart policy for a topic such as 'damaged'."""
    return POLICIES.get(topic, "no policy found")

policy_agent = Agent("policy", "You answer policy questions with the exact policy text.", tools=[lookup_policy],
                     model=lambda m, t: scripted(m, "lookup_policy", {"topic": "damaged"}))

def scripted(messages, tool_name, args):
    """A stand-in model that calls one tool, then answers with its result (the shape a real model returns)."""
    from types import SimpleNamespace as NS
    if messages[-1]["role"] == "tool":
        return NS(content=messages[-1]["content"], tool_calls=None, model_dump=lambda **k: {}), 60
    call = NS(id="c1", function=NS(name=tool_name, arguments=json.dumps(args)))
    return NS(content=None, tool_calls=[call],
              model_dump=lambda **k: {"role": "assistant", "tool_calls": [
                  {"id": "c1", "type": "function", "function": {"name": tool_name, "arguments": json.dumps(args)}}]}), 60

def ask_orders_agent(question: str) -> str:
    """Ask the orders specialist about the status of an order."""
    return orders_agent.run(question)

def ask_policy_agent(question: str) -> str:
    """Ask the policy specialist what ShopKart's rules say."""
    return policy_agent.run(question)

def supervisor_model(messages, tools):
    """Stands in for the supervisor's model: delegate to both specialists at once, then combine."""
    from types import SimpleNamespace as NS
    results = [m["content"] for m in messages if m["role"] == "tool"]
    if results:
        return NS(content="Combined answer: " + " | ".join(results), tool_calls=None, model_dump=lambda **k: {}), 80
    calls = [NS(id="s1", function=NS(name="ask_orders_agent", arguments='{"question": "Status of A-1001?"}')),
             NS(id="s2", function=NS(name="ask_policy_agent", arguments='{"question": "Refund rule for damaged items?"}'))]
    dump = {"role": "assistant", "tool_calls": [{"id": c.id, "type": "function",
            "function": {"name": c.function.name, "arguments": c.function.arguments}} for c in calls]}
    return NS(content=None, tool_calls=calls, model_dump=lambda **k: dump), 80

TRACE.clear()
supervisor = Agent("supervisor", "Coordinate specialists; answer the customer.",
                   tools=[ask_orders_agent, ask_policy_agent], model=supervisor_model)
print(supervisor.run("A-1001 arrived damaged. Can I get a refund?"))
for step in TRACE:
    print(" ", step)
What you should see
Combined answer: Here is what I found: A-1001 delivered 3 days ago | Damaged items: full refund within 30 days of delivery.
  {'agent': 'supervisor', 'tokens': 80, 'tools': ['ask_orders_agent', 'ask_policy_agent']}
  {'agent': 'orders', 'tokens': 70, 'tools': ['get_order_status']}
  {'agent': 'orders', 'tokens': 70, 'tools': []}
  {'agent': 'policy', 'tokens': 60, 'tools': ['lookup_policy']}
  {'agent': 'policy', 'tokens': 60, 'tools': []}
  {'agent': 'supervisor', 'tokens': 80, 'tools': []}

Six model calls for one answer, against two for a single agent with both tools. The supervisor pattern is worth it when specialists need different instructions, tools, models or permissions, or when their raw outputs would flood the supervisor's context. The supervisor never saw the order record or the policy lookup, only the two summaries.

Step 3 · Handoffs: transferring the conversation

In a handoff (the swarm pattern), the active agent transfers the conversation itself to another agent, which then talks to the user directly. It suits support desks: triage hands over to refunds, refunds may hand back. Handoffs are tools named transfer_to_<agent>; calling one changes which agent is active.

The mock model calls transfer_to_refunds when the user mentions refunds, the way a real model would after reading the tool descriptions.

@dataclass
class Conversation:
    """Who is active, and the shared history every agent sees."""
    active: str
    history: list[dict] = field(default_factory=list)
    handoffs: list[str] = field(default_factory=list)

AGENTS = {
    "triage":  "You are ShopKart triage. Transfer refunds questions to refunds, delivery questions to delivery.",
    "refunds": "You are the refunds desk. Check eligibility, then open a refund request.",
    "delivery": "You are the delivery desk. Track parcels.",
}
HANDOFF_TOOLS = {name: [{"type": "function", "function": {
    "name": f"transfer_to_{other}", "description": f"Hand the conversation to the {other} desk.",
    "parameters": {"type": "object", "properties": {}}}} for other in AGENTS if other != name] for name in AGENTS}

def handle(conv: Conversation, user_text: str, max_handoffs: int = 3) -> str:
    conv.history.append({"role": "user", "content": user_text})
    for _ in range(max_handoffs + 1):
        messages = [{"role": "system", "content": AGENTS[conv.active]}, *conv.history]
        msg = client.chat.completions.create(model="mock-model", messages=messages,
                                             tools=HANDOFF_TOOLS[conv.active]).choices[0].message
        handoff = next((c for c in msg.tool_calls or [] if c.function.name.startswith("transfer_to_")), None)
        if not handoff:
            conv.history.append({"role": "assistant", "content": msg.content})
            return f"[{conv.active}] {msg.content}"
        target = handoff.function.name.removeprefix("transfer_to_")
        if target in conv.handoffs[-2:]:                       # A -> B -> A ping-pong guard
            return f"[{conv.active}] Let me get a person to help you with this."
        conv.handoffs.append(conv.active)
        conv.history += [msg.model_dump(exclude_none=True),
                         {"role": "tool", "tool_call_id": handoff.id, "content": f"Transferred to {target}."}]
        print(f"  handoff: {conv.active} -> {target}")
        conv.active = target
    return "[system] Too many transfers; escalating to a person."

conv = Conversation(active="triage")
print(handle(conv, "I need help with refunds for my mixer"))
print("now active:", conv.active, "| history length:", len(conv.history))
What you should see
  handoff: triage -> refunds
[refunds] You are now with the refunds desk. How can I help?
now active: refunds | history length: 4

The refunds agent saw the full history, including why the customer was transferred, so the customer does not have to repeat themselves. Two guards matter in production: a cap on handoffs per turn, and ping-pong detection (A hands to B, which hands straight back). Log every handoff with its reason; misrouted handoffs are the most common multi-agent bug.

Step 4 · How much context does each agent get?

Cognition's argument against multi-agent systems is about context: agents that do not share what others know make inconsistent decisions. Anthropic's research system shows the fix: give each subagent a precise brief. There are three choices, with very different costs:

conversation = [{"role": "user", "content": f"Turn {i}: " + "details about my order and preferences " * 20}
                for i in range(12)]

def tokens(messages): return sum(len(m["content"]) // 4 for m in messages)

full = conversation                                                     # 1. everything the parent saw
summary = [{"role": "user", "content": "Customer: gold tier, prefers Hindi, order A-1001 damaged, wants refund."}]
brief = [{"role": "user", "content": json.dumps({                        # 3. a structured brief
    "objective": "Decide refund eligibility for order A-1001",
    "facts": {"order_id": "A-1001", "issue": "damaged on arrival", "delivered_days_ago": 3},
    "constraints": ["Use policy v2026-09", "Do not contact the customer"],
    "output": "eligible: yes/no, reason, policy clause"})}]

for name, ctx in (("full history", full), ("summary", summary), ("structured brief", brief)):
    print(f"{name:17} ~{tokens(ctx):5} tokens per subagent call")
What you should see
full history      ~ 2364 tokens per subagent call
summary           ~   17 tokens per subagent call
structured brief  ~   68 tokens per subagent call
Choice Use when Risk
Full history The subagent must act consistently with everything said (handoffs to a desk that talks to the user) Expensive; distraction from irrelevant turns
Summary The subagent needs the gist Lossy; the summarizer decides what matters
Structured brief Delegated, well-defined subtasks (research, checks, extraction) You must know what the subtask needs

Anthropic's lesson from its research system applies to all of them: tell each subagent the objective, the output format, the tools to use and the boundaries of its task, or subagents duplicate work and leave gaps.

In production
Context sharing mistakes

Passing the full transcript to every subagent feels safe but costs tokens on every hop and distracts the subagent with irrelevant turns; passing only a one-line task loses constraints the user stated earlier ("no COD", "deliver after 6 pm"). The production pattern is a structured brief plus a short list of pinned facts and constraints, and a structured result back. When a specialist must talk to the user directly (a handoff), give it the full conversation.

Step 5 · Parallel fan-out, with a budget

Breadth-first tasks (researching several suppliers, checking many documents) are where multi-agent systems earn their cost: subagents work in parallel, each in a clean context, and a lead agent merges the results. Two controls are essential: a concurrency limit and a shared budget across all subagents.

class Budget:
    """A token budget shared by every agent in one task."""
    def __init__(self, limit: int):
        self.limit, self.used = limit, 0
    def spend(self, n: int, who: str):
        if self.used + n > self.limit:
            raise RuntimeError(f"budget exceeded by {who}: {self.used + n} > {self.limit}")
        self.used += n

async def research(subquestion: str, budget: Budget, sem: asyncio.Semaphore) -> str:
    async with sem:                                          # at most N subagents at once
        await asyncio.sleep(0.2)                             # stands in for a few model and tool calls
        budget.spend(1500, who=subquestion)
        return f"{subquestion}: done"

async def lead(question: str, subquestions: list[str], limit: int, max_parallel: int = 3):
    budget, sem = Budget(limit), asyncio.Semaphore(max_parallel)
    t0 = time.perf_counter()
    results = await asyncio.gather(*(research(s, budget, sem) for s in subquestions), return_exceptions=True)
    ok = [r for r in results if isinstance(r, str)]
    failed = [str(r) for r in results if isinstance(r, Exception)]
    return {"ok": len(ok), "failed": failed, "tokens": budget.used, "seconds": round(time.perf_counter() - t0, 1)}

suppliers = [f"supplier {c}" for c in "ABCDEF"]
print(asyncio.run(lead("Compare six mixer suppliers", suppliers, limit=12000)))
print(asyncio.run(lead("Compare six mixer suppliers", suppliers, limit=6000)))
What you should see
{'ok': 6, 'failed': [], 'tokens': 9000, 'seconds': 0.4}
{'ok': 4, 'failed': ['budget exceeded by supplier E: 7500 > 6000', 'budget exceeded by supplier F: 7500 > 6000'], 'tokens': 6000, 'seconds': 0.4}

Six subtasks ran in two waves of three (0.4 seconds instead of 1.2). With the smaller budget, the last two were refused instead of silently overspending; the lead agent can now answer with partial results and say what is missing. Anthropic reported that early versions of its research system spawned 50 subagents for simple queries; effort-scaling rules in the lead's prompt ("simple fact: one agent, 3 to 10 tool calls; comparison: 2 to 4 subagents") fixed it.

Step 6 · Shared state without chaos

When agents collaborate on one artifact (a plan, a case file, a report), they share state: a blackboard. Two rules prevent the classic failure of agents overwriting each other: each key has one owner, and writes use optimistic concurrency (a write states the version it read, and fails if someone wrote since).

class Blackboard:
    def __init__(self, owners: dict[str, str]):
        self.owners, self.data, self.version = owners, {}, 0

    def read(self) -> tuple[dict, int]:
        return dict(self.data), self.version

    def write(self, agent: str, key: str, value, read_version: int):
        if self.owners.get(key) != agent:
            raise PermissionError(f"{agent} may not write '{key}' (owner: {self.owners.get(key)})")
        if read_version != self.version:
            raise RuntimeError(f"stale write by {agent}: read v{read_version}, board is v{self.version}")
        self.data[key] = value
        self.version += 1

board = Blackboard(owners={"eligibility": "policy", "refund_amount": "finance", "message": "writer"})
_, v = board.read()
board.write("policy", "eligibility", "eligible (damaged, day 3 of 30)", v)
_, v = board.read()
board.write("finance", "refund_amount", 2499, v)
for attempt in (lambda: board.write("writer", "refund_amount", 0, board.version),
                lambda: board.write("writer", "message", "Your refund of INR 2,499 is approved.", v)):
    try:
        attempt()
    except (PermissionError, RuntimeError) as e:
        print("blocked:", e)
print(board.read())
What you should see
blocked: writer may not write 'refund_amount' (owner: finance)
blocked: stale write by writer: read v1, board is v2
({'eligibility': 'eligible (damaged, day 3 of 30)', 'refund_amount': 2499}, 2)

The writer tried to change an amount it does not own, then tried to write a message based on an old read. In a real system the stale write triggers a re-read and a retry. LangGraph's state with reducers (the LangChain and LangGraph section) and Agent Framework's typed workflow state solve the same problem.

Step 7 · Debate and judging for high-stakes answers

For decisions where a wrong answer is expensive, have independent agents answer, then a judge compares them against a rubric. It is the voting pattern from Lesson 14.8 with reasons attached.

CANDIDATES = {
    "agent_a": {"answer": "Refund INR 2,499", "cites": ["policy 4.2"], "checked_order": True},
    "agent_b": {"answer": "Offer a replacement", "cites": [], "checked_order": False},
}

def judge(candidates: dict) -> tuple[str, dict]:
    """Score each answer on an explicit rubric; in real code a judge model applies it, calibrated against humans."""
    rubric = {"cites policy": lambda c: bool(c["cites"]), "verified the order": lambda c: c["checked_order"]}
    scores = {name: sum(test(c) for test in rubric.values()) for name, c in candidates.items()}
    best = max(scores, key=scores.get)
    return best, scores

winner, scores = judge(CANDIDATES)
print(scores, "->", CANDIDATES[winner]["answer"])
What you should see
{'agent_a': 2, 'agent_b': 0} -> Refund INR 2,499

When the candidates agree, you gain confidence; when they disagree, you have found a case worth a human's attention. Use it sparingly: it multiplies cost.

Evaluating and operating multi-agent systems

What to measure Why
Routing and handoff accuracy A wrong specialist wastes the whole turn
Subagent calls and tokens per task Multi-agent cost grows fast; watch the distribution, not just the mean
Redundant work (two subagents doing the same search) The sign of poor briefs
End-to-end task success, graded on the final outcome Different agent paths can reach a correct answer; grade the outcome, not the path
Ping-pong and depth incidents Guards firing means a prompt or routing problem
In production
Multi-agent problems seen in production, and the usual fix
  • The supervisor routes to the wrong specialist: specialists' descriptions overlap. Write each one as "handles X, not Y", and evaluate routing accuracy on its own.
  • Subagents redo each other's work: briefs were vague. Give every subagent an objective, an output format, the tools it may use and what to leave alone.
  • Agents contradict each other: they were working on parts that had to agree (Cognition's point). Merge them back into one agent, or pass the shared decisions explicitly.
  • Cost explodes: every handoff re-reads context. Cap subagent count per task and pass compact summaries, not whole transcripts.
  • Nobody can debug a failure: give the whole task one trace ID and log each agent's brief and result.
Industry practice
Lessons from teams running multi-agent systems in production
  • Start with a single agent and add specialists only when an eval shows a gain, and keep the single-agent version as a baseline (OpenAI's guide and Anthropic's research post agree on this).
  • Supervisors beat swarms for control; handoffs are best where a human-like desk transfer is the actual user experience.
  • Every subagent gets a brief (objective, output format, tools, boundaries) and returns a compact, structured result.
  • Give the whole task one budget and one trace ID, so cost and debugging work across agents.
  • Checkpoint the lead agent so a long multi-agent run can resume after a failure instead of restarting (Lesson 14.114).

From the field
Klarna: automation rate is not the only metric

In February 2024 Klarna announced that its AI assistant had handled 2.3 million customer conversations in its first month, doing work it equated to about 700 agents. In May 2025 its CEO said the cost-focused approach had produced lower-quality service, and Klarna began recruiting human support staff again, positioning human support as part of its quality offering. The lesson for architects: design escalation to people from day one, track resolution quality and customer satisfaction alongside deflection, and widen automation per intent only where quality holds. Solutions

SolutionP1 · Count the hidden calls

At least five: the supervisor's first call (asking both specialists), each specialist's own calls (one or two each, depending on whether it calls a tool), and the supervisor's final call that combines the answers. Multi-agent systems multiply calls, which is why this lesson says to split only when one agent fails.

SolutionB1 · Ping-pong

The agents hand the conversation back and forth until a turn or step limit stops the run. Give each agent a clear, non-overlapping scope, a default owner for mixed questions, and a limit on handoffs.

SolutionD1 · Context lost at the boundary

Agents-as-tools pass only what the caller writes in the tool argument, so "refund timeline?" lost the payment method. Make the supervisor pass a self-contained request ("Refund timeline for a UPI payment on order A-1002"), or pass the relevant facts as structured arguments. Test boundaries with questions that depend on earlier turns.

SolutionM1 · Three specialists and a safe default

Add ask_delivery_agent, extend the supervisor's tool list and instructions with the delivery scope, and add an "unclear" route that hands off to a person with the conversation attached. Evaluate routing on labeled questions, including unclear ones.

Check your understanding

Explain the mechanismWhen should you use multiple agents instead of one?

Worked answer. When one agent fails for structural reasons: too many tools to choose well, conflicting instructions across domains, different permissions or models per domain, context that overflows, or independent parallel work. Patterns include a supervisor with specialists (agents as tools), handoffs between peers, and parallel workers with an aggregator. Each boundary adds calls, latency and a place to lose context, so start with one agent.

A plausible wrong answer. "Multiple agents are always more capable." They are more complex; capability comes from tools, context and models.

Follow-ups. How do you evaluate a multi-agent system?

Debug a failureA multi-agent system is slow. Where does the time go?

Worked answer. Into sequential model calls: supervisor, specialist, maybe a second specialist, then the supervisor again. Read a trace's timeline: run independent specialists in parallel, give the supervisor enough information to route in one call, use a smaller model for routing, and stream progress to the user. If most questions touch one specialist, route directly instead of through a supervisor.

A plausible wrong answer. "Use a faster model everywhere." The structure, not the model, sets the number of sequential calls.

Follow-ups. How would you measure the cost of each boundary?

Defend a designSupervisor or handoffs for a support desk?

Worked answer. Handoffs when a conversation moves between desks and the specialist should talk to the customer directly, like a phone transfer. A supervisor when one voice should stay in charge, combining specialists' answers and enforcing policy in one place. For ShopKart I would start with one agent, then a supervisor routing to a refund workflow and a tracking agent (Lesson 14.72), because refunds need tight control.

A plausible wrong answer. "Handoffs, because they are simpler." They are simpler to wire and harder to control.

Follow-ups. How do you keep policy consistent across specialists?

Check your understanding

Q1When does a multi-agent design tend to pay off?

Breadth-first, parallel work is the classic win; tightly coupled work is the classic loss.

Q2What is the main difference between agents as tools and a handoff?

One delegates a task; the other transfers control.

Q3Why give subagents a structured brief rather than the full history?

Precise briefs were one of Anthropic's main lessons from its research system.

Q4What does the ping-pong guard in the handoff loop prevent?

Cap handoffs and detect A-to-B-to-A transfers.

Q5In a blackboard design, what prevents an agent from overwriting another agent's work based on an old read?

The same idea as database concurrency control.

Q6A research task fans out to subagents. What two controls should always be in place?

Without them, cost and rate-limit failures grow with every subagent.
