Why this came about

When models first became available, getting good results depended heavily on wording, and "prompt engineering" became a skill of its own. Techniques such as clear roles, examples (few-shot prompting) and explicit output formats emerged from that period. Reasoning models changed some of the advice, so this lesson covers what still holds.

In plain words first
Writing a brief for a very literal colleague

A prompt is a brief for a colleague who is extremely capable, has no context about your company, and takes every word literally. Good prompts say who the assistant is, what it must achieve, which tools to use when, the rules it must follow and the shape of the answer, in that order, with stable text first. Examples show the format better than descriptions do. Reasoning models need less step-by-step instruction and more clarity about the goal and the constraints.

From prompt engineering to context engineering

Prompt engineering is writing good instructions. Context engineering is the larger job of deciding everything the model sees at each step: instructions, tool definitionslater · 14.56, retrieved documents, memories, conversation history and tool results. In agents, most failures are context failures: the right fact was missing, buried, or contradicted by something else in the window.

Industry practice
What the model labs say
  • Anthropic (Effective context engineering for AI agents) frames context as a scarce budget: find "the smallest possible set of high-signal tokens" that gets the job done, because quality degrades as context grows (context rot).
  • OpenAI's prompting guides for its GPT-5 models stress being explicit and consistent: contradictory instructions waste reasoning effort as the model tries to reconcile them.
  • Google's prompt engineering guide recommends showing examples, giving the model a role, and stating the output format precisely.

See a prompt change the answer

Before the anatomy of a long production prompt, see the effect in its smallest form. This uses the small open model from Lesson 10.36, running on your own computer, so every output below is real and you can change any line and run it again. (No stand-in is involved here; the first run downloads the model.)

The helper sends one conversation to the model. The system prompt goes first, with the role system; the customer's message goes last, with the role user (Lesson 11.18).

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

name = "HuggingFaceTB/SmolLM2-360M-Instruct"       # the small open model from Lesson F7.2; about 720 MB on first download
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

def ask(user, system=None, examples=(), max_new_tokens=60):
    """One chat call to the local model. Greedy decoding, so the output is the same on every run."""
    messages = [{"role": "system", "content": system}] if system else []
    for question, answer in examples:                # worked examples go in as earlier turns of the conversation
        messages += [{"role": "user", "content": question}, {"role": "assistant", "content": answer}]
    messages.append({"role": "user", "content": user})
    ids = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt", return_dict=True)
    with torch.no_grad():
        out = model.generate(**ids, max_new_tokens=max_new_tokens, do_sample=False)
    return tok.decode(out[0, ids["input_ids"].shape[1]:], skip_special_tokens=True).strip()

question = "My mixer arrived with a cracked jar. What should I do?"
SHOP = "You are a support agent for ShopKart, an online shop. "
prompts = {
    "no system prompt": None,
    "role + length":    SHOP + "Answer in one short sentence.",
    "role + format":    SHOP + "Answer with exactly three numbered steps, each under ten words.",
    "role + context":   SHOP + "Policy: damaged items are refunded in full within 7 days of delivery. Answer in two short sentences.",
}
for label, system in prompts.items():
    print(f"[{label}]\n{ask(question, system)}\n")
What you should see
[no system prompt]
If your mixer has a cracked jar, it's not a big deal. It's a common issue that many people face. The key is to not use the mixer until it's fixed. Here's what you can do:

1. **Check the Instructions**: The manufacturer of your mixer should have

[role + length]
Contact the manufacturer's customer service for a replacement or repair.

[role + format]
1. Check the jar for any damage and clean it thoroughly.
2. Replace the jar with a new one and return it to the store.
3. Contact the store to report the issue and request a replacement.

[role + context]
I'd say, "Contact customer service immediately to report the issue and request a refund."
Reading this output

The customer's question never changed. Only the system prompt did.

  • No system prompt. The model has no idea who it is speaking for. It answers as a general assistant: long, generic, and it runs out of its 60 tokens in the middle of a list. It even reassures the customer that a cracked jar is "not a big deal".
  • Role + length. One sentence, as asked. But look at what it says: "contact the manufacturer". The model was told it works for ShopKart and still sent the customer elsewhere, because nothing in the prompt says what ShopKart does about damaged goods.
  • Role + format. Three numbered steps, as asked. The shape is right and the advice is still improvised.
  • Role + context. One line of policy in the prompt, and the answer changes from "contact the manufacturer" to "request a refund". The model did not get smarter; it was given the fact it needed.

That last step is the main lesson of this chapter. Instructions control the shape of an answer. Only context (facts the model cannot know: your policies, your data, the customer's order) makes the answer right. A 360-million-parameter model follows instructions loosely, as you can see from the quotation marks and "I'd say" in the last reply; large hosted models follow them far more closely, but they are just as ignorant of your refund policy until you put it in the prompt.

Examples in the prompt: zero-shot and few-shot

There are two ways to tell a model what you want: describe it, or show it. A prompt with instructions and no worked examples is called zero-shot. A prompt that includes a few worked examples is called few-shot ("shot" is an old machine-learning word for an example). In a chat API, examples are usually written as earlier turns of the conversation: a user message with the input, then an assistant message with the ideal output.

The test below asks the model to sort twelve customer messages into four categories, first with instructions only, then with four examples added. It counts two different things: whether the reply is one of the four allowed words, and whether it is the right one.

LABELS = ["refund", "delivery", "payment", "other"]
SYSTEM = "Classify the customer's message. Reply with exactly one word from this list: refund, delivery, payment, other."
TEST = [("Where is my parcel? It was due on Monday.", "delivery"), ("I was charged twice for one order.", "payment"),
        ("The kettle stopped working, I want my money back.", "refund"), ("Do you sell gift cards?", "other"),
        ("The courier marked it delivered but I got nothing.", "delivery"), ("My card was declined but the money left my account.", "payment"),
        ("Please return my money for the damaged lamp.", "refund"), ("What are your office hours?", "other"),
        ("Package is stuck in Mumbai for a week.", "delivery"), ("Why is there an extra fee on my bill?", "payment"),
        ("I'd like a refund for order A-1002.", "refund"), ("Can I change my account email?", "other")]
EXAMPLES = [("My order has not arrived yet.", "delivery"), ("I paid but the order shows unpaid.", "payment"),
            ("This blender is faulty, give me my money back.", "refund"), ("Do you have a mobile app?", "other")]

def run(examples):
    replies = [ask(message, SYSTEM, examples, max_new_tokens=6) for message, _ in TEST]
    clean = [r.lower().strip(" .") for r in replies]
    valid = sum(c in LABELS for c in clean)                              # did it reply with one of the four words?
    correct = sum(c == gold for c, (_, gold) in zip(clean, TEST))        # and was it the right one?
    return replies, valid, correct

for label, examples in [("zero-shot (instructions only)", ()), ("few-shot (four examples)    ", EXAMPLES)]:
    replies, valid, correct = run(examples)
    print(f"{label}  valid label {valid:2d}/12   correct {correct}/12")
    print("   first four replies:", replies[:4])
What you should see
zero-shot (instructions only)  valid label  4/12   correct 2/12
   first four replies: ['Delivery', 'I apologize for the inconvenience.', 'Refund', 'Yes, I sell gift cards']
few-shot (four examples)      valid label 12/12   correct 5/12
   first four replies: ['payment', 'other', 'refund', 'other']
Reading this output
  • Zero-shot. The instruction said "reply with exactly one word from this list". The model did that for only 4 of 12 messages. For the rest it started chatting: "I apologize for the inconvenience", "Yes, I sell gift cards". Code that expected one of four words would have broken eight times.
  • Few-shot. With four examples, every one of the 12 replies is a valid label. The examples fixed the format completely, which the instruction alone could not do. This is the most dependable effect of examples, and it holds for large models too.
  • Still only 5 of 12 correct. The examples did not make this small model good at the task. It now answers in the right form and often picks the wrong label ("other" for nearly everything). Format is a prompting problem. Accuracy on a task the model finds hard is a model problem, solved by a stronger model (Lesson 11.27) or by fine-tuning (Lesson 7.25, where this same kind of task goes from 15% to 90%).

Two habits follow. Measure "is the output usable?" separately from "is it right?", because they have different fixes. And when a model ignores a format instruction, add two or three examples before you add more words.

Let code search for a better prompt

You have now improved a prompt by hand twice: by adding examples, and by choosing which examples to add. Both were guesses followed by a measurement. A program can make the guesses. Prompt optimization means writing several candidate prompts, scoring each one on a set of questions with known answers, and keeping the best. The score decides, not your opinion of the wording.

The code continues from the few-shot experiment above. It tries three versions of the instruction, each with four different sets of examples, on a new development set of twelve tickets. The twelve tickets you used earlier are kept aside as the test set, so that the winner is judged on tickets the search never saw (Lesson 2.26's rule, applied to prompts).

import random

DEV = [("My parcel is three days late.", "delivery"), ("The app charged my card two times.", "payment"),
       ("The toaster is broken, I want a refund.", "refund"), ("Do you deliver on Sundays?", "delivery"),
       ("Where can I read your privacy policy?", "other"), ("Refund me for the torn shirt please.", "refund"),
       ("My UPI payment failed but the amount was debited.", "payment"), ("How do I delete my account?", "other"),
       ("The tracking page has not changed since Friday.", "delivery"), ("I returned the shoes, when do I get my money?", "refund"),
       ("There is a charge I do not recognise.", "payment"), ("Do you have a store in Pune?", "other")]
INSTRUCTIONS = {
    "original":  SYSTEM,
    "defined":   ("Classify the customer's message as one word. refund: wants money back. delivery: where a parcel is or when it "
                  "comes. payment: charges, fees, failed or double payments. other: anything else. Reply with the one word only."),
    "question":  "Which one word fits the customer's message best: refund, delivery, payment or other? Reply with that word only.",
}
POOL = EXAMPLES + [("Why was I billed a convenience fee?", "payment"), ("The driver left my box at the wrong house.", "delivery"),
                   ("I want my money back for the cracked plate.", "refund"), ("Is there a student discount?", "other")]

def accuracy(system, examples, dataset):
    replies = [ask(m, system, examples, max_new_tokens=6).lower().strip(" .") for m, _ in dataset]
    return sum(r == gold for r, (_, gold) in zip(replies, dataset))

random.seed(0)
candidates = []
for iname, system in INSTRUCTIONS.items():                    # every instruction, with four sets of examples
    candidates.append((iname, "first four", EXAMPLES))
    for trial in range(2):
        candidates.append((iname, f"random four #{trial + 1}", random.sample(POOL, 4)))
    candidates.append((iname, "all eight", POOL))

results = []
for iname, ename, examples in candidates:
    score = accuracy(INSTRUCTIONS[iname], examples, DEV)      # score each candidate on the development set
    results.append((score, iname, ename, examples))
    print(f"{iname:<9} + {ename:<15} dev {score:2d}/12")

best = max(results, key=lambda r: r[0])
print(f"\nbest on dev: {best[1]} + {best[2]} ({best[0]}/12)")
print(f"hand-written prompt on the test set: {accuracy(SYSTEM, EXAMPLES, TEST)}/12")
print(f"best prompt on the test set:         {accuracy(INSTRUCTIONS[best[1]], best[3], TEST)}/12")

original  + random four #2  dev  7/12
original  + all eight       dev  8/12
defined   + first four      dev  6/12
defined   + random four #1  dev  8/12
defined   + random four #2  dev  9/12
defined   + all eight       dev  8/12

question  + all eight       dev 10/12

best on dev: question + first four (10/12)

Reading this output
  • The search found a prompt you would not have picked. The winning instruction is the plainest of the three, a one-line question. The careful version with a definition for every label scores lower with the same examples (6 against 10). With a small model, shorter often wins, and only the measurement shows it.
  • It holds on tickets the search never saw. On the test set the hand-written prompt gets 5 of 12, as it did earlier in this lesson, and the selected prompt gets 9. If the test score had stayed at 5, the search would only have fitted the development set.
  • The same instruction ranges from 6 to 10. With the "question" instruction, one random set of four examples scores 6 and another set scores 10. Which examples you include matters as much as the wording, which is why the search varies both.
  • Twelve tickets is a small ruler. A difference of one or two tickets is noise at this size. Trust the direction (5 against 9), and use a few hundred labelled cases before you believe a ranking of close candidates (Lesson 14.118).
How this connects
  • This loop is what a prompt optimizer runs for you. DSPy (Lesson 14.102) takes a metric and a set of examples and searches instructions and demonstrations in this way. Its newer optimizers also use a model to read the failures and propose the next rewrite, where this code only tried the candidates you wrote.
  • It needs the same three things as every other improvement in this course: a dataset with known answers, a metric, and a held-out set. Lesson 11.26 turns the winning prompt into a versioned asset with tests, so that the next model upgrade can be checked against it.

Anatomy of a production system prompt

The experiments above used one-line system prompts. A production prompt has the same ingredients, written out in full and kept in order. This is the ShopKart support agent's:

SYSTEM = """\
<role>
You are the order-support agent for ShopKart, an Indian e-commerce company.
You help customers with order status, delivery problems and refunds.
</role>

<context>
- Today's policies: refunds within 7 days of delivery; damaged items always refundable.
- Amounts are in INR. Customers may write in English, Hindi or Hinglish; reply in their language.
</context>

<instructions>
1. Always look up the order before answering anything about it.
2. Never promise a delivery date the tools did not return.
3. Refunds above INR 5,000 need human approval: call request_refund, do not say it is done.
4. If a request is outside orders, delivery or refunds, say so and offer the help page.
</instructions>

<tool_guidance>
- get_order_status: use for any question that mentions an order ID.
- request_refund: only after get_order_status shows the order exists.
</tool_guidance>

<output_format>
Short paragraphs, no markdown tables. End with the next step the customer should expect.
</output_format>

<examples>
Customer: mera order A-1002 kab aayega?
Agent (after looking it up): Aapka order A-1002 abhi processing mein hai. Dispatch hote hi SMS aayega.
</examples>
"""
print(len(SYSTEM.split()), "words")
Part Why it is there
Role Sets domain, tone and boundaries in one line
Context Facts the model cannot know: policies, units, audience
Instructions Numbered rules, each testable. Each rule should exist because an eval caselater · 14.134 failed without it.
Tool guidance When to use which tool. This is where agents most often go wrong.
Output format How the answer will be shown or parsed
Examples A few representative cases (few-shot prompting). They are the strongest signal you can give, so make them varied and correct.

XML-style tags are not magic, but they give the model clear section boundaries and let you refer to sections ("follow the rules in <instructions>"). Claude models are trained to respect them; other models handle them well too.

Watch out
Prompts are not a security boundary

"Never reveal customer data" in a prompt reduces risk but does not enforce anything. Enforce permissions in code, tools and the database (Lesson 15.24).

Prompting reasoning models

Reasoning models (Lessons 10.37 and 10.45) think before they answer, and they are prompted differently from older chat models:

Habit from older models With reasoning models
"Think step by step" Unnecessary and sometimes harmful; the model already reasons. Set the reasoning effort (low, medium, high) instead
Long, prescriptive procedures State the goal, the constraints and what "done" looks like; let the model plan
Many few-shot examples Fewer, high-quality examples; too many can over-constrain the plan
Prompt asks for the reasoning in the answer Ask for a concise answer; reasoning is returned separately (or summarized) by the API
Contradictory rules tolerated Contradictions waste reasoning tokens as the model tries to reconcile them; make rules consistent

Dynamic few-shot examples: choose the examples per question

You saw above that examples fix the output format. They also steer what the model does, but only when they resemble the question in front of it. Examples are the strongest signal in a prompt, but a fixed set wastes tokens on examples unlike the current question. Dynamic few-shot selection keeps a bank of good examples and picks the few most similar to each input (the same retrieval idea as Chapter 4, applied to examples; the code below uses the TF-IDF similarity of Lesson 5.32).

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

EXAMPLES = [
    {"q": "Where is my order A-1001?", "a": "Call get_order_status, then give the status and next step."},
    {"q": "mera order kab aayega", "a": "Reply in Hinglish. Ask for the order ID if it is missing."},
    {"q": "The mixer arrived broken, I want my money back", "a": "Damaged items are always refundable; start request_refund."},
    {"q": "Can I change my delivery address?", "a": "Only before dispatch; check status first."},
    {"q": "Cancel order A-1002 please", "a": "Check it has not shipped, then confirm before cancelling."},
    {"q": "Do you sell iPhones?", "a": "Out of scope: point to the product search page."},
]
vectorizer = TfidfVectorizer(ngram_range=(1, 2)).fit([e["q"] for e in EXAMPLES])
bank = vectorizer.transform([e["q"] for e in EXAMPLES])

def pick_examples(question: str, k: int = 2) -> list[dict]:
    """Return the k examples most similar to the question."""
    scores = cosine_similarity(vectorizer.transform([question]), bank)[0]
    return [EXAMPLES[i] for i in scores.argsort()[::-1][:k]]

def few_shot_block(question: str) -> str:
    return "\n".join(f"<example>\nCustomer: {e['q']}\nApproach: {e['a']}\n</example>" for e in pick_examples(question))

print(few_shot_block("my mixer arrived broken, can I change it?"))
What you should see
<example>
Customer: The mixer arrived broken, I want my money back
Approach: Damaged items are always refundable; start request_refund.
</example>
<example>
Customer: Can I change my delivery address?
Approach: Only before dispatch; check status first.
</example>

The second pick is a near miss: "change" matched the address example, not an exchange. Keyword similarity is shallow, which is why production systems select examples with embeddings and keep the bank curated. In production, embed examples with the same model as your RAGlater · 10.42 index, and keep the bank curated from traceslater · 14.57 that were reviewed as good. LangChainlater · 14.71's example selectors and DSPy's optimizers (Lesson 14.102) automate this.

Exercises

Predict before you run

pick_examples("Cancel A-1003, it hasn't shipped yet") with k=2: which two examples come back, and why might the second one be a poor choice? (Solution P1.)

Break it on purpose

Delete rule 3 ("Refunds above INR 5,000 need human approval…") from SYSTEM. Which kind of customer message would now produce a dangerous reply, and what test would have caught the deletion? (Solution B1.)

Debugging exercise
Debugging exercise: the examples override the rules

After adding a dynamic few-shot example "Customer: refund my 12,000 rupee TV / Approach: Refund it right away", the agent started promising large refunds without approval, although rule 3 is still in the prompt. Explain why, and fix the example bank. (Solution D1.)

Make it your own

Add a <refusals> section to SYSTEM listing what the agent must not do (share another customer's data, change prices, give legal advice), each with the reply to give instead, and one example of a refusal. (Solution M1.)

Solutions

SolutionP1 · Similar words, not similar intent

The cancellation example ("Cancel order A-1002 please") comes first. The second is whichever example shares the most remaining words, likely the address-change example ("Only before dispatch") through "shipped"/"dispatch" overlap, or the order-status one through "order". TF-IDF matches words, not meaning, so the second pick can teach an irrelevant approach. Use embeddings for selection (Lesson 14.129), and keep the bank small and distinct.

SolutionB1 · Rules exist because of failures

A message asking for a refund above INR 5,000 would now get "your refund is done" instead of a request for approval. A test set with one case per rule, run on every prompt change (Lesson 11.26), catches it: each rule should have at least one eval case that fails without it.

SolutionD1 · Examples are the strongest signal

Models follow examples more closely than instructions, so a wrong example teaches the wrong behavior even when a rule forbids it. Remove or correct the example ("Approach: above INR 5,000, call request_refund and say approval is needed"), review every example against the rules, and add an eval case for the conflict. Examples should demonstrate the rules, never contradict them.

SolutionM1 · Refusals with replacements

Each refusal needs a replacement, or the model improvises: for example "Another customer's order: say you can only discuss orders on this account." Add one example showing a polite refusal and the next step. Then add eval cases for each refusal, including rephrased and Hinglish versions, because refusals fail on paraphrases first.

Explain the mechanismWhat goes into a production system prompt?

Worked answer. A role, the context the model cannot know (policies, units, audience), numbered testable instructions, guidance on when to use each tool, the output format, and a few varied, correct examples. Structure with clear sections, for example XML-style tags, so rules can be referenced and updated. Each instruction should exist because an eval case needed it, and the prompt is versioned and tested like code (Lesson 11.26).

A plausible wrong answer. "A clever one-paragraph persona." Personas set tone; behavior comes from rules, context, tool guidance and examples.

Follow-ups. How is prompting a reasoning model different?

Debug a failureA model ignores one instruction in a long system prompt. What do you try?

Worked answer. Check that the instruction does not conflict with an example or another rule, and that it is specific and testable ("never promise a date the tools did not return" rather than "be accurate"). Check where it sits: put critical rules in a clearly labeled section and near related tool guidance. Add an example demonstrating it. Then measure on eval cases before and after, because a fix that helps one case can hurt others.

A plausible wrong answer. "Write it in capital letters and repeat it." Emphasis can help a little, but conflicts and vagueness are the usual causes.

Follow-ups. When would you move a rule out of the prompt and into code?

Defend a designShould business rules live in the prompt or in code?

Worked answer. Rules that must always hold, such as approval limits, permissions and refund eligibility, belong in code, as tool validation or middleware (Lessons 14.58 and 14.75), with the prompt describing them so the model plans correctly. Rules about tone, wording and how to explain things belong in the prompt. A rule only in the prompt will eventually be broken by a paraphrase or an injection (Lesson 15.24).

A plausible wrong answer. "Everything in the prompt, it is easier to change." Easier to change, and easier to bypass.
