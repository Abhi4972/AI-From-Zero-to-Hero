Why this came about

Production agents met every failure distributed systems know, plus new ones such as loops and invalid tool calls. Reliability engineering adapted timeouts, retries, fallbacks, circuit breakers and graceful degradation to agents.

In plain words first
Assume every part will fail sometimes

Models time out, providers have outages, tools return errors, agents loop. Reliability engineering plans a response for each: timeouts and retries with backoff for temporary failures, fallbacks for outages, idempotency so retries are safe, circuit breakers to stop hammering a broken service, limits on steps and spend, and graceful degradation so users get a useful partial answer instead of an error.

A web request that fails is retried and forgotten. An agent task that fails halfway may have charged a card, sent an email and reserved stock, and then stopped. Agents run longer, touch more systems and take actions with side effects, so ordinary reliability engineering matters more for them, not less. The good news is that almost none of it is new: it is distributed-systems practice applied to a non-deterministic caller.

Timeouts, retries and the retry storm

Every call an agent makes needs a timeout. Without one, a hung tool holds the run, its context and its quota forever. With one, the next question is whether to retry, and here agents make a classic failure worse.

A retry storm happens when a dependency slows down or fails, every caller retries immediately, and the retries multiply the load on exactly the system that is struggling. Agents amplify it in two ways: a single task makes many calls, and a model that sees an error often decides on its own to try again, on top of whatever retries the code does. The dependency recovers, the backlog of retries arrives at once, and it falls over again.

The patterns that prevent it:

Pattern What it does Rule of thumb
Timeout Bounds every call Set per tool from its p99, not a global default
Retry only what can succeed Retries 429, 503 and timeouts; never 400 or 403 Actionable errors from tools make this decision easy (Lesson 14.134)
Exponential backoff with jitter Spreads retries out in time Double the wait each try, add randomness, cap it
Retry budget Caps retries as a share of first attempts, per client 10 to 25% of requests; beyond that, stop retrying and back off
Adaptive rate limit (backpressure) Clients slow down when they see errors, and queue instead of sending Halve the send rate on failure, add one on success (AIMD, as in TCP)
Circuit breaker After many failures, fail fast for a while instead of calling Open on error rate over a window; probe before closing
One retry layer Retries happen in exactly one place Tell the model "the system retries for you" and do not let it loop on errors

The simulation below runs 1,800 agent tasks of three tool calls each against a service that is down for 90 seconds and can serve 8 calls a second. The naive client retries at once, up to five times. The hardened client queues work behind an adaptive rate limit, backs off with jitter, keeps each task's checkpoint and gives up only after a deadline.

import random
from collections import deque

def simulate(policy, seconds=900, arrivals_per_s=2, steps=3, capacity=8, outage=(300, 390), seed=7):
    """Agent tasks of `steps` tool calls each hit one downstream service. It serves nothing during
    the outage, and at all times rejects calls above `capacity` per second (overload)."""
    rng = random.Random(seed)
    tasks, due, queue = [], {}, deque()       # due[t]: tasks ready to call at second t
    s = {"calls": 0, "useful": 0, "done": 0, "failed": 0, "half_done": 0, "waits": []}
    limit = capacity                           # hardened: adaptive client-side rate limit (AIMD)
    for t in range(seconds + 1200):
        if t < seconds:
            for _ in range(arrivals_per_s):
                tasks.append({"step": 0, "tries": 0, "start": t}); due.setdefault(t, []).append(len(tasks) - 1)
        ready = due.pop(t, [])
        rng.shuffle(ready)
        if policy == "naive":
            callers = ready
        else:                                  # backpressure: queue the excess instead of sending it
            queue.extend(ready)
            callers = [queue.popleft() for _ in range(min(int(limit), len(queue)))]
        cap = 0 if outage[0] <= t < outage[1] else capacity
        served, failures = 0, 0
        for tid in callers:
            k = tasks[tid]
            s["calls"] += 1
            if served < cap:
                served += 1; s["useful"] += 1; k["step"] += 1; k["tries"] = 0
                if k["step"] == steps:
                    s["done"] += 1; s["waits"].append(t - k["start"])
                else:
                    due.setdefault(t + 1, []).append(tid)
                continue
            failures += 1; k["tries"] += 1
            if policy == "naive":
                if k["tries"] <= 5:
                    due.setdefault(t + 1, []).append(tid)            # retry at once
                else:
                    s["half_done" if k["step"] else "failed"] += 1    # give up wherever it got to
            elif t - k["start"] > 900:
                s["half_done" if k["step"] else "failed"] += 1        # deadline: escalate to a person
            else:
                due.setdefault(t + min(2 ** k["tries"], 32) + rng.randint(0, 3), []).append(tid)  # backoff + jitter
        if policy == "hardened":               # additive increase, multiplicative decrease
            limit = max(1, limit / 2) if failures else min(capacity * 2, limit + 1)
    return s

total = 900 * 2
for p in ["naive", "hardened"]:
    s = simulate(p)
    w = sorted(s["waits"])
    print(f"{p:9} completed {s['done'] / total:6.1%} | failed {s['failed']:3} | half-done {s['half_done']:3} | "
          f"calls per useful call {s['calls'] / s['useful']:.2f} | p95 task time {w[int(len(w) * .95)]:3} s")
What you should see
naive     completed  90.2% | failed 172 | half-done   4 | calls per useful call 1.23 | p95 task time   2 s
hardened  completed 100.0% | failed   0 | half-done   0 | calls per useful call 1.04 | p95 task time 152 s

The naive client loses about one task in ten, and a few of those stopped halfway with side effects already done. The hardened client loses none and wastes fewer calls, at a price you must design for: during and after the outage, tasks wait in the queue, so the slowest 5% take minutes. That is the honest trade-off. A user would rather hear "your refund is queued and will finish in a few minutes" than receive a half-done refund, so pair backpressure with a status message and an expected time (Lesson 14.148).

Tip
Tell the model who retries

If the harness retries a failed tool call, say so in the tool result ("temporarily unavailable; the system will retry; continue with other work or wait"). Otherwise the model may retry on its own, re-plan around a transient error or give up. One retry layer, in code, is easier to reason about than two, one of them a language model.

Side effects: idempotency, checkpoints and sagas

Three patterns, used together, make multi-step actions safe.

  1. Idempotency keys. Every write carries a key derived from the business action (order and refund sequence, not a random UUID per attempt). The system of record stores the key and returns the original result on a repeat. A retry, a resume after a crash or a model that calls the tool twice then does no harm.
  2. Checkpoints. The runtime records each completed step durably before starting the next (Lesson 14.140 covers durable executionlater · 14.140 with LangGraph checkpointers, Temporal and DBOS). A crashed run resumes from its last checkpoint, and idempotency makes repeating the step in flight safe.
  3. Sagas with compensation. When a multi-step change fails partway, undo the completed steps in reverse order with compensating actions: refund the charge, release the stock, cancel the shipment label. A saga does not give you a database transaction across systems; it gives you a defined way back.
class Ledger:
    """A system of record that enforces idempotency keys."""
    def __init__(self):
        self.done, self.effects = {}, []
    def apply(self, key, effect):
        if key in self.done:
            return self.done[key], "replayed"
        self.effects.append(effect); self.done[key] = f"ok:{effect}"
        return self.done[key], "applied"

def run_saga(order, ledger, checkpoint, fail_at=None):
    steps = [("reserve_stock", "release_stock"), ("charge_card", "refund_card"),
             ("create_shipment", "cancel_shipment"), ("notify_customer", None)]
    for name, undo in steps:
        if name in checkpoint:                      # completed before a crash: skip, do not repeat
            continue
        if name == fail_at:
            print(f"  {name} failed: compensating {len(checkpoint)} completed step(s)")
            for done_name in reversed(list(checkpoint)):
                comp = dict(steps)[done_name]
                result, how = ledger.apply(f"{order}:{comp}", comp)
                print(f"    {comp:16} {how}")
                del checkpoint[done_name]
            return "rolled back"
        result, how = ledger.apply(f"{order}:{name}", name)
        checkpoint[name] = result                   # durable in a real runtime
        print(f"  {name:16} {how}")
    return "completed"

ledger = Ledger()
print("Run 1, shipment service down:")
print("  ->", run_saga("A-1001", ledger, {}, fail_at="create_shipment"))
print("Run 2, crash after charging, then resume:")
cp = {}
for name in ["reserve_stock", "charge_card"]:       # the first two steps ran, then the process died
    ledger.apply(f"A-1002:{name}", name); cp[name] = "ok"
print("  (process crashed; resuming from checkpoint", list(cp), ")")
print("  ->", run_saga("A-1002", ledger, cp))
print("Run 3, the model calls the whole task again by mistake:")
print("  ->", run_saga("A-1002", ledger, {}))
print("effects in the ledger:", ledger.effects)

Run 1 ends with no money taken and no stock held. Run 2 resumes without charging twice. Run 3 is the case prompts cannot prevent: the model starts the whole task again, and every step replays harmlessly because the keys are business keys. The ledger shows each effect exactly once.

Watch out
Some actions cannot be compensated

An email cannot be unsent and a payment to an outside bank may not be reversible. Order the saga so that irreversible steps come last, after everything that can fail has succeeded, and put an approval before them when the stakes are high (Lesson 14.148). The Citibank-Revlon payment error described in Lesson 14.148 is the case where the irreversible step came with a confusing interface.

Degraded modes: fail cleanly and tell the truth

When a dependency is down, an agent has three bad options (hang, guess, or fail silently) and one good one: degrade on purpose. Decide each degraded mode in the spec (question 11 in Lesson 14.134):

Dependency down Degraded mode What the user hears
Primary model Gateway falls back to a second provider or a smaller model, with a stricter scope Nothing, or "replies may be shorter right now"
All models Static answers for top intents; a ticket for the rest "Our assistant is unavailable; we have logged your request as T-4411"
A read tool (orders API) Say what is unknown; offer a callback "I can't see order status right now; I'll message you when I can"
A write tool (payments) Queue the action durably; confirm when done "Your refund is queued and will complete within the hour"
Retrieval index Answer only from tools and structured data; refuse policy questions "I can't check the policy right now; a colleague will follow up"

Never let the agent fill the gap with a guess. An agent that invents an order status during an outage turns an availability incident into a trust incident.

Reliability objectives for agents

Write service level objectives for what users experience, not only for the infrastructure. A service level objective (SLO) is a target you commit to, stated as a number over a period: "95% of refund requests are resolved correctly within two minutes, measured over 30 days". The gap between the target and perfection is the error budget: at 95%, one request in twenty may fail before the objective is broken. The budget turns reliability into something you can spend and track: while there is budget left you can ship changes, and when it is burning fast you stop and fix. Lesson 14.145 shows how to measure SLOs from traces and alert on the burn rate. For agents, write SLOs like these:

Indicator Definition Example objective
Task success rate Tasks completed correctly, per intent, from evals and sampled production review 95% for order status, 90% for refunds, over 28 days
Clean failure rate Failed tasks that ended in escalation or a queued action, never half-done 100% of failures clean
Time to complete p95 from request to final answer or action, per intent Status under 10 s; refunds under 2 min
Escalation rate Tasks handed to a person Under 15%, and every escalation has a complete handoff
Cost per successful task Model and tool cost, divided by successes Under 0.30 USD for refunds

Use error budgets exactly as for any service (Lesson 14.145): when the budget is burning, freeze risky changes and spend the time on reliability.

Hands-on lab
Lab P4 · Break it on purpose
  1. Wrap your agent's tools with a fault injector: 5% timeouts, 2% 503s, and one 60-second outage. Measure task success, half-done tasks and calls per useful call.
  2. Add backoff with jitter, a retry budget and an adaptive limit. Measure again and write down the latency you paid for the reliability.
  3. Turn one multi-step action into a saga with compensations. Crash the process between steps and show the resume repeats nothing.
  4. Write the degraded mode for each dependency in your spec, and an eval case that proves each one says the truth.
  5. Write three SLOs for your agent and the alert that fires when each budget is burning (Lesson 14.146).

  • ✗ "Retries handle all failures."
    ✓ Only temporary ones; permanent errors need handling, and retries must be safe to repeat.
  • ✗ "A fallback model is a drop-in replacement."
    ✓ Its quality and behaviour differ; evaluate it.

Exercises

Predict before you run

The model provider has 99.9% availability and the order API 99.5%. If the agent needs both for every answer, what is the best availability the agent can have? (Solution P1.)

Break it on purpose

Retry failed model calls immediately and without limit. A provider has a partial outage. What happens? (Solution B1.)

Debugging exercise

During an incident, the agent kept answering, but from a degraded fallback model, and nobody knew. What was missing? (Solution D1.)

Make it your own

Define SLOs for ShopKart Copilot: availability, latency (time to first token and total), and quality, each with how it is measured. (Solution M1.)

Solutions

SolutionP1 · Availability multiplies

About 99.4% (0.999 × 0.995), worse than either. Fallbacks, caching and degraded modes are how you raise it.

SolutionB1 · Retry storms

Retries multiply load on the struggling provider and on your quotas, making the outage worse and costs higher. Use exponential backoff with jitter, limits, circuit breakers and fallbacks (Lesson 14.59).

SolutionD1 · Visible degradation

Logging and alerting on which model served each request, and a dashboard of fallback rates. Degradation should be a known state, not a silent one.

SolutionM1 · SLOs for an agent

Availability of answered requests, p95 time to first token and p95 total time, and a quality SLO from sampled evaluations or resolution rate. Each with an error budget and alerts.

Check your understanding

Explain the mechanismHow do you engineer reliability for an agent?

Worked answer. Set SLOs for availability, latency and quality; design for dependency failures with timeouts, retries with backoff, circuit breakers, fallbacks and degraded modes; make tools idempotent; limit runs; monitor and alert on error budgets; and rehearse incidents.

A plausible wrong answer. "Use a reliable provider." Your agent's reliability is the product of all its dependencies.

Follow-ups. What is a degraded mode for a support agent?

Debug a failurep99 latency is ten times the median. Where do you look?

Worked answer. Long tails: retries, tool calls to slow backends, long contexts, rare loops, and queueing. Trace the slowest requests and fix the common cause.

A plausible wrong answer. "Add more servers." Tail latency is usually per-request behavior.

Follow-ups. How would you cap the tail?

Defend a designShould agent quality be an SLO?

Worked answer. Yes, measured by sampled evals or outcome metrics, because users experience wrong answers as failures. It is noisier than availability, so use rolling windows and clear thresholds.

A plausible wrong answer. "Only availability and latency are SLOs." Then a confidently wrong agent is "healthy".

Follow-ups. How would you alert on quality?

Q1What turns a short dependency outage into a long one?
