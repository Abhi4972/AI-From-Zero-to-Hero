The idea in one line

Four orchestration patterns recur across 2026 frameworks: supervisor-worker, swarm / peer-to-peer, hierarchical, debate. Anthropic's guidance: "It's about building the right system for your needs." Start simple; add topology only when a single agent plus five workflow patterns is insufficient.

The problem

In plain words first

When a system has several specialist agents, something has to decide which one handles each request. Orchestration patterns are the ways to arrange that decision. A supervisor (a router) reads the request and dispatches it. In a swarm, agents pass the request among themselves (a handoff) until one keeps it. A hierarchy stacks routers: first pick a department, then a team. Every one of these patterns rests on one capability: an LLM making a correct routing decision. This lesson measures that decision with a small model on twelve support tickets, under each pattern.

Teams reach for "multi-agent" before they need it. Four patterns recur across frameworks; once you can name them, you can pick the right one — or skip topology entirely.

Idea 1 · Supervisor-worker

  • A central routing LLM dispatches to specialist agents.
  • Decides: loop back to self, hand off to specialist, terminate.
  • Specialists do not talk to each other; all routing goes through the supervisor.

Frameworks: LangGraph create_supervisor, Anthropic orchestrator-workers, CrewAI Hierarchical Process.

2026 LangChain recommendation: do supervision through direct tool calls rather than create_supervisor. Gives finer context engineering control — you decide exactly what each specialist sees.

Idea 2 · Swarm / peer-to-peer

  • Agents hand off directly via a shared tool surface.
  • No central router.
  • Lower latency than supervisor (fewer hops).
  • Harder to reason about (no single point of control).

Frameworks: LangGraph swarm topology, OpenAI Agents SDK handoffs (when all agents can hand off to all others).

Idea 3 · Hierarchical

  • Supervisors managing sub-supervisors managing workers.
  • Implemented as nested subgraphs in LangGraph; nested crews in CrewAI.
  • Scales to large agent populations at the cost of operational complexity.

When you need it: when a single supervisor's context budget cannot hold descriptions of all specialists.

Idea 4 · Debate

  • Parallel proposers + iterative cross-critique (Lesson 14.102).
  • Not really orchestration — more verification — but shows up as a topology choice in frameworks.

Idea 5 · Autonomous crews vs deterministic flows

CrewAI formalizes two deployment modes:

  • Flow for deterministic event-driven automation (recommended starting point for production).
  • Crew for autonomous role-based collaboration.

This is orthogonal to the four patterns above but maps to topology: Flow is typically supervisor or hierarchical; Crew is typically supervisor with an LLM router.

Idea 6 · Anthropic's guidance

"Success in the LLM space isn't about building the most sophisticated system. It's about building the right system for your needs."

Decision order:

  1. Single agent + workflow patterns (Lesson 14.49) — start here.
  2. Supervisor-worker — when you have 2-4 specialists.
  3. Swarm — when latency matters more than reasoning clarity.
  4. Hierarchical — only when supervisor context budget fails.
  5. Debate — when accuracy matters more than cost.

Idea 7 · Where this pattern goes wrong

  • Topology-first thinking. "We need multi-agent" before identifying what problem multi-agent solves.
  • Bouncing handoffs in swarm. A -> B -> A -> B. Use hop counters.
  • Fake hierarchy. Three layers because "enterprise"; two actual teams. Collapse.

The same idea as a formula

Routing calls per request. A supervisor makes 1 routing call; a hierarchy with d levels makes d; a swarm makes one call per hop, up to a hop limit H, so between 1 and H.

Accuracy compounds. If each routing decision is right with probability a, a d-level hierarchy routes correctly with probability about ad, and a swarm that needs h correct handoffs with about ah. With a=0.9: supervisor 0.9, two levels 0.81, three handoffs 0.73. Extra structure has to make each decision much easier to pay for itself.

Position bias is a router whose choice depends on the order of the options. Test it by permuting the list: an unbiased router picks the same team for the same ticket whatever the order.

Worked example
Reading one router's errors
  • Twelve tickets, three per team. The supervisor picks refunds for all twelve: 3 of 12 right, exactly the tickets that happen to be refunds.
  • Reverse the team list and the same supervisor picks account, now listed first, 9 times out of 12, and gets 6 right.
  • A router that flips with the order of its menu is not reading the ticket. The fix belongs in the router (a stronger model, a classifier, or embeddings; lesson 14.49), not in the topology.
  • Expected cost at this router quality: a swarm with a≈0.25 per handoff almost never ends in the right place, whatever its hop limit.

Supervisor and swarm, every decision made by a model

Qwen2.5-0.5B-Instruct (greedy, CPU) is the supervisor and every swarm member. Each ticket gets one supervisor call; in the swarm, each ticket starts at a team other than the right one, and each team answers KEEP or names a team to hand it to, up to four hops. About 1 minute.

# Supervisor versus swarm with a real model as every router. Twelve support tickets, four specialists
# (refunds, bugs, sales, account). Supervisor: one routing call picks the specialist. Swarm: the ticket
# starts at a specialist on duty (never the right one), and each specialist either keeps it or hands it to a named
# peer, up to four hops. Qwen2.5-0.5B-Instruct (greedy, CPU) makes every decision.
import os, re, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()
CALLS = {"n": 0}
def ask(prompt):
    CALLS["n"] += 1
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=6, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip().lower()

SPECIALISTS = {"refunds": "money back for orders or invoices", "bugs": "crashes, errors and broken features",
               "sales": "prices, quotes and buying more seats", "account": "logins, passwords and profile settings"}
TICKETS = [
    ("I need a refund for invoice 47.", "refunds"), ("The app crashes when I press Ctrl-C.", "bugs"),
    ("Do you offer volume pricing for 200 seats?", "sales"), ("I can't log in after resetting my password.", "account"),
    ("You charged me twice this month, please return one payment.", "refunds"),
    ("Exporting to PDF gives error 500.", "bugs"), ("Can I get a quote for the enterprise plan?", "sales"),
    ("How do I change the email on my profile?", "account"), ("The order arrived broken and I want my money back.", "refunds"),
    ("Search returns nothing since the last update.", "bugs"), ("What does the Pro plan cost per year?", "sales"),
    ("My two-factor code is never accepted.", "account"),
]
NAMES = list(SPECIALISTS)
def pick(text, allowed):
    hits = [n for n in allowed if n.rstrip("s") in text]
    return hits[0] if hits else None

def supervisor(ticket):
    menu = "\n".join(f"- {n}: {d}" for n, d in SPECIALISTS.items())
    return pick(ask(f"Route this support ticket to one team.\nTeams:\n{menu}\nTicket: {ticket}\nAnswer with the team name only."), NAMES), 1

def swarm(ticket, start, max_hops=4):
    here, path = start, [start]
    for _ in range(max_hops):
        others = ", ".join(n for n in NAMES if n != here)
        reply = ask(f"You are the {here} team ({SPECIALISTS[here]}). Ticket: {ticket}\n"
                    f"If this ticket is for your team, answer KEEP. Otherwise answer the team to hand it to: {others}.")
        if "keep" in reply:
            return here, path
        nxt = pick(reply, [n for n in NAMES if n != here])
        if nxt is None:
            return here, path
        here = nxt; path.append(here)
    return here, path                                    # hop limit reached: whoever holds it now

rows = []
for i, (ticket, truth) in enumerate(TICKETS):
    c0 = CALLS["n"]; sup, _ = supervisor(ticket); c_sup = CALLS["n"] - c0
    c0 = CALLS["n"]; sw, path = swarm(ticket, start=NAMES[(i + 1) % 4]); c_sw = CALLS["n"] - c0   # starts at a wrong team
    rows.append(dict(ticket=ticket, truth=truth, sup=sup, sw=sw, path=path, c_sup=c_sup, c_sw=c_sw))
print(f"{'ticket':<52}{'truth':<9}{'supervisor':<12}{'swarm path'}")
for r in rows:
    print(f"{r['ticket'][:50]:<52}{r['truth']:<9}{str(r['sup']):<12}{' -> '.join(r['path'])}")
bounce = sum(any(r['path'][k] == r['path'][k + 2] for k in range(len(r['path']) - 2)) for r in rows)
print(f"\n{'':<12}{'correct':>8}{'routing calls':>15}")
print(f"{'supervisor':<12}{sum(r['sup'] == r['truth'] for r in rows):>6}/12{sum(r['c_sup'] for r in rows):>15}")
print(f"{'swarm':<12}{sum(r['sw'] == r['truth'] for r in rows):>6}/12{sum(r['c_sw'] for r in rows):>15}")
print(f"swarm tickets that bounced back to a team they had left (A -> B -> A): {bounce}; "
      f"kept by the first team on duty: {sum(len(r['path']) == 1 for r in rows)}")

Reading this output

The supervisor always says refunds. Every ticket, crash reports and password problems included, goes to refunds, the first team in its list. It is right on 3 of 12, exactly the refund tickets.

The swarm keeps everything. Each ticket started at a wrong team, and in 11 of 12 cases that team answered KEEP; the twelfth hopped once, to another wrong team. 0 of 12 reach the right team. No ticket bounced back and forth, because almost nothing moved at all.

The calls are cheap; the decisions are not. 12 routing calls for the supervisor and 13 for the swarm. The pattern changed how many decisions were made, not whether they were right.

Position bias, examples and a hierarchy

This block continues from the one above. The supervisor runs again with its team list reversed, then with one example ticket per team, and a two-level hierarchy (money or technical, then the team) runs with examples at both levels. About 1 minute.

# Why the routers failed, and two fixes. (1) Position bias: the same supervisor prompt with the team list
# reversed. (2) A supervisor shown one example ticket per team. (3) A two-level hierarchy (money or
# technical first, then the team), also with examples, which costs two routing calls per ticket.
# Continues from the block above.
def supervisor_with(ticket, order, examples=False):
    menu = "\n".join(f"- {n}: {SPECIALISTS[n]}" for n in order)
    shots = ("Examples:\nTicket: Please return my payment for order 9. -> refunds\nTicket: The editor freezes when I paste. -> bugs\n"
             "Ticket: How much is the Team plan? -> sales\nTicket: I forgot my username. -> account\n") if examples else ""
    return pick(ask(f"Route this support ticket to one team.\nTeams:\n{menu}\n{shots}Ticket: {ticket}\nAnswer with the team name only."), NAMES)

GROUPS = {"money": ["refunds", "sales"], "technical": ["bugs", "account"]}
def hierarchical(ticket):
    g = ask("Is this support ticket about money (refunds, prices) or technical (crashes, logins)?\n"
            "Examples: 'Refund my order' -> money. 'The app freezes' -> technical. 'Price for 10 seats?' -> money. "
            f"'Can't sign in' -> technical.\nTicket: {ticket}\nAnswer money or technical.")
    group = "money" if "money" in g else "technical"
    a, b = GROUPS[group]
    return supervisor_with(ticket, [a, b], examples=True) or a

results = {}
for label, f in [("supervisor, team list reversed", lambda t: supervisor_with(t, NAMES[::-1])),
                 ("supervisor + one example per team", lambda t: supervisor_with(t, NAMES, examples=True)),
                 ("hierarchy (group, then team) + examples", hierarchical)]:
    c0 = CALLS["n"]
    picks = [f(t) for t, _ in TICKETS]
    results[label] = (picks, CALLS["n"] - c0)
print(f"{'':<42}{'correct':>8}{'routing calls':>15}   picks")
for label, (picks, calls) in results.items():
    ok = sum(p == t for p, (_, t) in zip(picks, TICKETS))
    common = max(set(picks), key=picks.count)
    print(f"{label:<42}{ok:>6}/12{calls:>15}   most often: {common} ({picks.count(common)}/12)")

supervisor, team list reversed                 6/12             12   most often: account (9/12)
supervisor + one example per team              3/12             12   most often: refunds (12/12)

Reading this output

The supervisor is reading its menu, not the ticket. With the list reversed it picks account, now first, for 9 of 12 tickets. Its 6 correct answers come mostly from the bias landing on account tickets.

Examples did not help this model. With one example ticket per team, the supervisor still sends all twelve to refunds. The two-level hierarchy uses 24 calls and sends all twelve to account: two weak decisions in a row are no better than one.

The lesson for real systems: measure the router on a labelled set, permute its options, and fix it (a stronger model, a classifier or embeddings, as in lesson 14.49) before arranging agents around it. With a router this weak no topology can work.

Part 1 of 3 · classify, supervisor_worker, swarm

"""Four orchestration patterns: supervisor, swarm, hierarchical, debate.

Same three-intent task (refund / bug / sales) handled four ways. Measure
op count per pattern to see cost trade-offs.
"""

from __future__ import annotations

from collections import Counter
from dataclasses import dataclass, field
from typing import Any, Callable


def classify(text: str) -> str:
    t = text.lower()
    if "refund" in t:
        return "refund"
    if "crash" in t or "error" in t or "bug" in t:
        return "bug"
    if "pricing" in t or "quote" in t:
        return "sales"
    return "sales"


SPECIALISTS: dict[str, Callable[[str], str]] = {
    "refund": lambda t: f"refund handled: {t[:30]}",
    "bug":    lambda t: f"bug logged: {t[:30]}",
    "sales":  lambda t: f"quote sent: {t[:30]}",
}


def supervisor_worker(tasks: list[str]) -> tuple[list[str], int]:
    trace: list[str] = []
    ops = 0
    for task in tasks:
        ops += 1
        label = classify(task)
        trace.append(f"supervisor -> {label}")
        specialist = SPECIALISTS[label]
        ops += 1
        trace.append(f"  {label}: {specialist(task)}")
    return trace, ops


def swarm(tasks: list[str]) -> tuple[list[str], int]:
    trace: list[str] = []
    ops = 0
    for task in tasks:
        current = list(SPECIALISTS)[0]
        hops = 0
        while hops < 3:
            ops += 1
            label = classify(task)
            if current == label:
                trace.append(f"swarm[{current}]: {SPECIALISTS[current](task)}")
                break
            trace.append(f"swarm[{current}] handoff -> {label}")
            current = label
            hops += 1
    return trace, ops

Part 2 of 3 · hierarchical, debate

def hierarchical(tasks: list[str]) -> tuple[list[str], int]:
    trace: list[str] = []
    ops = 0
    for task in tasks:
        ops += 1
        top_label = "customer_ops" if classify(task) != "sales" else "commercial"
        trace.append(f"top -> {top_label}")
        ops += 1
        sub_label = classify(task)
        trace.append(f"  {top_label} -> {sub_label}")
        specialist = SPECIALISTS[sub_label]
        ops += 1
        trace.append(f"    {sub_label}: {specialist(task)}")
    return trace, ops


def debate(tasks: list[str]) -> tuple[list[str], int]:
    trace: list[str] = []
    ops = 0
    for task in tasks:
        proposals: list[str] = []
        for debater in ("alpha", "beta", "gamma"):
            ops += 1
            label = classify(task)
            proposals.append(label)
            trace.append(f"{debater} proposes {label}")
        ops += 1
        convergent = Counter(proposals).most_common(1)[0][0]
        specialist = SPECIALISTS[convergent]
        ops += 1
        trace.append(f"debate converges -> {convergent}: {specialist(task)}")
    return trace, ops


def main() -> None:
    print("=" * 70)
    print("ORCHESTRATION PATTERNS: Phase 14, Lesson 28")
    print("=" * 70)

    tasks = [
        "I need a refund for invoice 4711",
        "the CLI crashes on ctrl-c",
        "do you offer volume pricing?",
    ]

    for name, fn in (
        ("supervisor-worker", supervisor_worker),
        ("swarm",             swarm),
        ("hierarchical",      hierarchical),
        ("debate",            debate),
    ):
        trace, ops = fn(tasks)
        print(f"\n--- {name}  ops={ops} ---")
        for line in trace:
            print(f"  {line}")

    print()
    print("supervisor: cleanest. swarm: shortest. hierarchical: deepest.")
    print("debate: most expensive. pick topology AFTER picking the problem.")

Break it on purpose

A team moves its support bot from a supervisor to a swarm of specialists "to cut latency" and sees misrouted tickets jump. Their logs show most tickets never leave the first agent. Using this lesson, why, and what would you check before choosing any topology? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Supervisors as tool calls. LangChain now recommends building supervisors directly with tool calls (each specialist exposed as a tool) rather than its langgraph-supervisor library, for finer control of what each specialist sees.
  • Handoffs are first-class in the OpenAI Agents SDK, LangGraph swarms and Microsoft Agent Framework; production teams add hop limits and log every handoff, because silent bounces and dead ends are common.
  • Routers in practice are often not LLM calls at all: embedding or small fine-tuned classifiers decide the common cases cheaply, and an LLM handles only ambiguous requests (lesson 14.49).
  • Anthropic's advice still holds: start with one agent and simple workflows, and add multi-agent structure only when a measured limit (context, specialisation, parallelism) requires it.
  • On your laptop: the routing calls here take about a second each on the CPU. On the RTX 4060 a 3B to 7B model in 4-bit routes far more accurately; measure it on these twelve tickets before trusting it.

Sources: langgraph-supervisor README, LangChain multi-agent guide, OpenAI Agents SDK handoffs, Anthropic, Building effective agents.

Recap
What to keep from this lesson
  • Every orchestration pattern is only as good as its routing decisions.
  • Test routers for position bias by permuting their options.
  • Swarm members tend to keep what they are given; cap hops and log handoffs.
  • More levels mean more calls and compounding errors.
  • Choose the topology after measuring the router on real requests.

Given a product domain and a task class, pick the minimal topology.

Decision:

1. 1 agent + workflow patterns (Lesson 12) suffice? -> don't use topology at all.
2. 2-4 specialists with distinct responsibilities? -> **supervisor-worker**.
3. Latency-critical and specialists can cleanly hand off? -> **swarm**.
4. 10+ specialists, supervisor context budget failing? -> **hierarchical**.
5. Accuracy matters more than cost, multi-proposer + critique helps? -> **debate** (Lesson 25).

Produce:

1. The chosen topology scaffold.
2. Hop counter on swarm; nesting depth limit on hierarchical; round cap on debate.
3. Observability hooks per handoff or per step (OTel GenAI spans, Lesson 23).
4. A "why this, not that" README section.

Hard rejects:

- Calling 3 LLM calls in sequence "multi-agent." That's a prompt chain.
- Swarm without hop counter. Bouncing is a certainty.
- Hierarchical that bottoms out at 1 specialist per branch. Flatten.

Refusal rules:

- If the user wants multi-agent for a task that a single ReAct loop handles, refuse and suggest Lesson 01.
- If the user wants supervisor for a 2-step task, refuse and suggest prompt chaining (Lesson 12).
- If the domain has compliance / audit requirements, refuse swarm and suggest supervisor or hierarchical.

Output: topology scaffold + README with decision rationale. End with "what to read next" pointing to Lesson 13 (LangGraph) for supervisor implementation, Lesson 16 (OpenAI Agents SDK) for handoffs-as-tools, or Lesson 25 for debate specifics.

Exercises

Solutions

SolutionP1 · Neither does well

Neither does well, and the supervisor wins on a technicality: it sends every ticket to refunds, the first team listed, so it gets the 3 refund tickets right (3 of 12). The swarm gets 0 of 12, because each team keeps whatever it is given (11 of 12 tickets never move). Both failures are routing decisions, not topology.

SolutionB1 · Nobody hands off

In a swarm, every agent must recognise that a request is not its own and hand it on. Small or generalist agents tend to accept whatever they receive, so the first agent on duty keeps most tickets, and misroutes rise. The supervisor at least made one explicit choice per ticket.

Before choosing a topology, measure the routing decision itself on a labelled sample of real tickets: accuracy per team, position bias (permute the options), and, for a swarm, how often agents correctly decline. Add hop limits and handoff logging. If latency is the goal, a fast classifier or embedding router in front of the specialists usually cuts it more than removing the supervisor does.
