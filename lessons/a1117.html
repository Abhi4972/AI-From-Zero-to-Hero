In plain words first
The idea in one line

Every framework sells the same demo (research agent builds a report) and hides the same bug (state schema fights with the orchestration layer). Pick the framework whose abstractions match the shape of your problem; everything else is glue you write twice.

Terms you'll hear
Term What people say What it actually means
Orchestration "How the agents coordinate" The layer that decides which node/role/agent runs next.
Durable state "Resume after a restart" State that survives process death, attached to a checkpoint or session store.
LLM-selected routing "Let the model decide" A planner LLM picks the next step each turn; flexible but pays tokens on every decision.
Explicit routing "Developer decides" A Python function or static edge picks the next step; cheap and auditable.
Crew "A CrewAI team" Roles + tasks + process (sequential or hierarchical) bound into a single runnable.

Team (Agno) "Multi-agent Agno" Route / coordinate / collaborate mode over a set of agents.
StateGraph "LangGraph's graph" Typed-state, node, conditional-edge, checkpointer abstraction.

The problem

In plain words first

Agent frameworks are libraries that handle the plumbing around model calls: keeping state, deciding which step runs next, calling tools, retrying, logging. Each one is built around a different picture of an agent. LangGraph uses a graph of steps, CrewAI a team of roles, AutoGen a chat between agents, Agno a single agent with tools. A framework fits well when its picture matches your problem, and fights you when it does not. This lesson compares them on the questions that decide real projects: where state lives, who decides the next step, what you can observe, and what it costs. Then it measures two of those costs: letting a model choose every route against routing in plain code, and how much time the orchestration itself adds. No model is trained.

You have a task that needs more than one LLM call. Maybe it is a research workflow (plan, search, summarize, cite). Maybe it is a code-review pipeline (parse diff, critique, patch, validate). Maybe it is a multi-turn assistant that books flights, writes emails, and files expense reports. You pick a framework.

Three days later, you discover the framework's abstractions leak. CrewAI gives you roles but fights you when the "researcher" needs to hand a structured plan to the "writer." AutoGen gives you chat between agents but has no first-class state so your checkpoint is a pickle of a conversation log. LangGraph gives you a state graph but forces you to name every transition before you know what the agent will do. Agno gives you a single-agent abstraction that screams when you try to fan out to three concurrent workers.

The fix is not "pick the best framework." It is to match the framework's core abstraction to the shape of your problem. This lesson draws that map.

The idea

Four frameworks show four different core abstractions. The 2026 landscape has more, and they follow the same patterns: the OpenAI Agents SDK, the Claude Agent SDK, Google's Agent Development Kit, Pydantic AI, and Microsoft Agent Framework. Agent Framework reached 1.0 in April 2026 as the successor to AutoGen and Semantic Kernel for new work; AutoGen itself receives bug fixes and security patches.

Framework Core abstraction Best fit Worst fit
LangGraph StateGraph — typed state, nodes, conditional edges, checkpointer. Workflows with explicit state and human-in-the-loop interrupts; production agents needing time-travel debugging. Loose, role-driven brainstorming where the topology is unknown.
CrewAI Crew — roles (goal, backstory), tasks, process (sequential or hierarchical). Role-playing or persona-driven workflows with a short linear/hierarchical plan. Anything stateful beyond the crew's turn history; complex branching.
AutoGen (maintenance; successor: Microsoft Agent Framework) ConversableAgent pair — two or more agents that speak in turns until an exit condition. Multi-agent dialogue (teacher-student, proposer-critic, actor-reviewer) where the thinking emerges from the chat. Deterministic workflows with a known DAG; anything needing durable state across restarts.
Agno Agent — a single LLM + tools + memory, composable into teams. Fast-to-build single agents and lightweight teams; strong multi-modality and built-in storage drivers. Deep, explicitly-branched graphs with custom reducers.

Idea 1 · What "abstraction" actually means

A framework's core abstraction is the thing you draw on the whiteboard when you pitch the architecture.

  • LangGraph → you draw a graph. Nodes are steps, edges are transitions, and the state object at every point is typed. The mental model is a state machine.
  • CrewAI → you draw an org chart. Each role has a job description and a manager routes tasks. The mental model is a small team of specialists.
  • AutoGen → you draw a Slack DM. Two agents message each other; a third joins if you need a moderator. The mental model is chat.
  • Agno → you draw a single box with tools hanging off it. Put boxes next to each other for a team. The mental model is "agent with batteries included."

Idea 2 · The state question

State is where most framework choices break down in production.

  • LangGraph. Typed state (TypedDict or Pydantic model), per-field reducers, first-class checkpointer (SQLite/Postgres/Redis). Resume, interrupt, and time-travel are free. (See Phase 11 · 16.)
  • CrewAI. Inside a crew, state flows as strings between tasks via the context field, or structured through output_pydantic. For durable, typed state use CrewAI Flows: a Pydantic state model, @start / @listen / @router steps, and @persist, which saves the state after each step and resumes a run by its ID.
  • AutoGen. State is the chat history and any user-defined context. Conversation transcripts persist; arbitrary workflow state does not unless you write adapters.
  • Agno. Built-in storage drivers (SQLite, Postgres, Mongo, Redis, DynamoDB) attached to an Agent via storage= — conversation sessions and user memories persist automatically. Not a full graph checkpointer; a session store.

Idea 3 · The branching question

Every non-trivial agent branches. Who decides the branch matters.

  • LangGraph — you decide, via conditional edges. Routing is a Python function with named branches. Branches are first-class in the compiled graph; the checkpointer records which branch was taken.
  • CrewAI — the manager decides in hierarchical mode; in sequential mode you decide at build time. Routing is implicit in the task list; there is no first-class "if" outside the manager's prompt.
  • AutoGen — the agents decide via chat. Branching is emergent from who speaks next. GroupChatManager selects the next speaker; you can hand-write a speaker_selection_method but the default is LLM-driven.
  • Agno — the agent decides by which tool to call next. Teams have a coordinator/router/collaborator mode; branching beyond that is the developer's responsibility.

Idea 4 · The observability question

  • LangGraph — OpenTelemetry via LangSmith or any OTel exporter. Every node transition is a trace span; checkpoints double as replayable traces. LangSmith is the first-party option; Langfuse/Phoenix also have adapters.
  • CrewAI — first-class OpenTelemetry since late-2025; integrations with Langfuse, Phoenix, Opik, AgentOps.
  • AutoGen — OpenTelemetry integration via autogen-core; AgentOps and Opik have connectors. Tracing granularity is per-agent-message, not per-node.
  • Agno — built-in monitoring=True flag plus OpenTelemetry exporters; tight integration with Langfuse for session traces.

Idea 5 · Cost and latency

All four frameworks add per-call overhead (framework logic, validation, serialization). Rough order of increasing overhead: Agno ≈ LangGraph < CrewAI ≈ AutoGen. The difference is dominated by how much extra LLM routing the framework does. CrewAI's hierarchical manager spends tokens deciding who goes next; AutoGen's GroupChatManager likewise. LangGraph only spends tokens where you write llm.invoke. Agno's single-agent path is thin.

When cost per run matters, prefer explicit routing (LangGraph edges, AutoGen speaker_selection_method) over LLM-selected routing.

The same idea as a formula

The price of letting the model route. A run with D routing decisions, each made by a model call with a p-token prompt and an o-token answer, at input and output prices cin​ and cout​ per token:

extra cost per run=D(pcin​+ocout​),extra latency≈D×tmodel call​.
Explicit routing (a Python function or a static edge) costs about zero in both.

A hybrid router uses the model only when the rules are unsure. If rules cover a share h of inputs, the extra cost drops to (1−h)D(pcin​+ocout​), and accuracy becomes h⋅accrules​+(1−h)⋅accmodel on the rest​.

Framework overhead per step, torch​, matters only relative to the work inside the step: torch​+tmodel​torch​​.

Worked example
A manager agent on 10,000 runs a day
  • A hierarchical crew in which the manager makes D=5 routing decisions per run, each with a 1,500-token prompt (role descriptions plus history) and a 20-token answer, on Claude Sonnet 5.5 at \$2 / \$10 per million tokens.
  • Per decision: $1{,}500 \times 2 \times 10^{-6} + 20 \times 10 \times 10^{-6} = \$0.0032$. Per run: $5 \times 0.0032 = \$0.016$.
  • At 10,000 runs a day: \$160 a day, about \$4,800 a month, just to decide who goes next. At around a second per call, it also adds 5 seconds to every run.
  • With rules covering 80% of decisions and the model handling the rest: \$32 a day and 1 second.
Check your mental model
  • ✗ "The best framework is the one with the most features."
    ✓ The best fit is the one whose core abstraction (graph, roles, chat, single agent) matches the problem's shape.
  • ✗ "Frameworks are slow."
    ✓ Orchestration code takes milliseconds; model calls take hundreds of milliseconds or more. The cost lies in extra model calls the framework makes for you.
  • ✗ "Letting the model route is always smarter."
    ✓ It is more flexible but pays a model call per decision, and it can be worse than a few rules (measured below).

Who should choose the next step?

24 support tickets with a human-assigned queue (billing, technical, account), routed four ways. Keyword rules in plain Python. Qwen2.5-0.5B-Instruct picking every route, with queue descriptions in the prompt. bge-small-en-v1.5 comparing each ticket with the queue descriptions. And rules first, with the model called only when no single rule matches. About 30 seconds on CPU.

import re, time, torch
from transformers import AutoTokenizer, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name, padding_side="left")
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

# 24 support tickets with the queue a human would pick
TICKETS = [
 ("I was charged twice for my March invoice.", "billing"), ("Please refund my annual plan, I cancelled on day 2.", "billing"),
 ("Your pricing page says $12 but my card shows $15.", "billing"), ("How do I download a receipt for my expense report?", "billing"),
 ("Can I pay by bank transfer instead of card?", "billing"), ("The payment failed but the money left my account.", "billing"),
 ("Why did my bill go up this month?", "billing"), ("I need a VAT number on the paperwork you sent me.", "billing"),
 ("The API returns a 500 error on every POST.", "technical"), ("The app crashes when I open the settings tab.", "technical"),
 ("Exports have been stuck at 99% since yesterday.", "technical"), ("Webhooks stopped arriving after your update.", "technical"),
 ("Search is very slow, 20 seconds per query.", "technical"), ("The CSV import mangles accented characters.", "technical"),
 ("Dark mode makes the chart labels unreadable.", "technical"), ("My sync job silently skips half the files.", "technical"),
 ("Please change the email on my account.", "account"), ("How do I add a teammate to my workspace?", "account"),
 ("I want to delete my account and all my data.", "account"), ("I can't reset my password, the link has expired.", "account"),
 ("Transfer ownership of the workspace to my colleague.", "account"), ("Turn on two-factor authentication for everyone.", "account"),
 ("My name is misspelled on my profile.", "account"), ("Someone else seems to be logged in as me.", "account"),
]
QUEUES = ["billing", "technical", "account"]

# 1) explicit routing: a few lines of Python, zero tokens
RULES = {"billing": r"charg|refund|pric|invoice|receipt|pay|bill|vat", "technical": r"error|crash|slow|bug|api|stuck|import|webhook",
         "account": r"account|password|email|teammate|two-factor|profile|ownership"}
def rule_route(text):
    hits = [q for q, rx in RULES.items() if re.search(rx, text.lower())]
    return hits[0] if len(hits) == 1 else None          # None = no rule matched, or several did

# 2) LLM-selected routing: the model reads the ticket and names a queue
def llm_route(texts):
    prompts = [tok.apply_chat_template([{"role": "system", "content": "Route the support ticket to exactly one queue.\n"
               "billing: charges, payments, refunds, invoices, prices, receipts.\n"
               "technical: bugs, errors, crashes, slow or broken features.\n"
               "account: login, passwords, profile, users, permissions, security settings.\n"
               "Reply with the queue name only."}, {"role": "user", "content": t}],
               tokenize=False, add_generation_prompt=True) for t in texts]
    enc = tok(prompts, return_tensors="pt", padding=True)
    with torch.no_grad():
        g = model.generate(**enc, max_new_tokens=4, do_sample=False)
    outs = [tok.decode(x[enc.input_ids.shape[1]:], skip_special_tokens=True).strip().lower() for x in g]
    return [next((q for q in QUEUES if q in o), o) for o in outs], int(enc.attention_mask.sum())

# 3) a semantic router: embed the ticket, pick the nearest queue description (no generation)
from sentence_transformers import SentenceTransformer
emb = SentenceTransformer("BAAI/bge-small-en-v1.5")
DESC = {"billing": "charges, payments, refunds, invoices, prices, receipts, bills",
        "technical": "bugs, errors, crashes, slow or broken features",
        "account": "login, passwords, profile, users, permissions, security settings"}
D = emb.encode(list(DESC.values()), normalize_embeddings=True)
def emb_route(texts):
    return [QUEUES[int(i)] for i in (emb.encode(list(texts), normalize_embeddings=True) @ D.T).argmax(1)]

texts, gold = zip(*TICKETS)
t = time.time(); llm, n_tok = llm_route(texts); llm_s = time.time() - t
rules = [rule_route(x) for x in texts]
t = time.time(); sem = emb_route(texts); sem_s = time.time() - t
hybrid = [r if r else l for r, l in zip(rules, llm)]          # rules first, the model only when no single rule fits
acc = lambda pred: sum(p == g for p, g in zip(pred, gold))
fallback = sum(r is None for r in rules)

print(f"{len(TICKETS)} tickets, 3 queues\n")
print(f"{'router':<34}{'correct':>9}{'LLM calls':>13}{'prompt tokens':>15}")
print(f"{'rules only (unmatched = wrong)':<34}{acc(rules):>6}/24{0:>13}{0:>15}")
print(f"{'LLM picks every route':<34}{acc(llm):>6}/24{24:>13}{n_tok:>15}")
print(f"{'embedding similarity (bge-small)':<34}{acc(sem):>6}/24{0:>13}{0:>15}")
print(f"{'rules, LLM only when unsure':<34}{acc(hybrid):>6}/24{fallback:>13}{round(n_tok * fallback / 24):>15}")
print(f"\nLLM routing took {llm_s:.1f} s for 24 tickets on CPU ({llm_s / 24 * 1000:.0f} ms each, batched); "
      f"the embedding router {sem_s * 1000:.0f} ms for all 24; the rules microseconds")
print(f"\nthe LLM router said 'technical' for {llm.count('technical')} of 24 tickets")
print("tickets where the rules or the embeddings disagree with the human label:")
for x, g, r, l, e in zip(texts, gold, rules, llm, sem):
    if r != g or e != g:
        print(f"  {x[:50]:<50} human={g:<9} rules={str(r):<9} emb={e:<9} llm={l}")

Reading this output

The small model lost to six lines of rules. Given the queue descriptions, Qwen2.5-0.5B said "technical" for 23 of the 24 tickets. It got 8 right, about what always guessing one queue would score. A frontier model would do far better on these tickets. One thing would not change: every route costs a model call, here about 1,950 prompt tokens for 24 decisions plus a few hundred milliseconds each on this CPU.

The rules look better than they are. They got 20 of 24, but they were written after reading these tickets, which flatters them. They also fail in a telling way: they abstain (no rule or several rules matched) instead of guessing. New tickets with new wording ("the money left my account") will slip past them more often.

The embedding router got 22 of 24 with no generation at all. Comparing each ticket with one-line queue descriptions takes about 100 ms for all 24. It missed "Exports stuck at 99%" and "CSV import" (both technical), which it sent to billing. This is the "semantic router" pattern: cheap, fast, and good when queues differ by topic.

Rules first, the model only when unsure, also reached 22 of 24. The model was called 4 times instead of 24, about a sixth of the tokens. That is the shape most production routers end up with: explicit code for the cases you understand, and a model, embeddings or a human for the rest.

What the orchestration itself costs

The same three-step pipeline (plan, search, write) with no model inside, run 300 times as plain function calls, as a LangGraph graph, and as a graph with a checkpointer. The result is compared with one routing decision from the run above. A few seconds.

import operator, time
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver

# the same three-step pipeline (plan -> search -> write) with no model inside, so only orchestration is timed
def plan(s):   return {"log": ["plan"]}
def search(s): return {"log": ["search"]}
def write(s):  return {"log": ["write"]}

def plain(query):                                   # plain Python: three function calls
    s = {"query": query, "log": []}
    for step in (plan, search, write):
        s["log"] = s["log"] + step(s)["log"]
    return s

class S(TypedDict):
    query: str
    log: Annotated[list, operator.add]
def build(checkpointer=None):
    g = StateGraph(S)
    for f in (plan, search, write): g.add_node(f.__name__, f)
    g.add_edge(START, "plan"); g.add_edge("plan", "search"); g.add_edge("search", "write"); g.add_edge("write", END)
    return g.compile(checkpointer=checkpointer)
graph, saved = build(), build(InMemorySaver())

def per_run(fn, n=300):
    fn(-1); t = time.perf_counter()
    for i in range(n): fn(i)
    return (time.perf_counter() - t) / n * 1000
runs = {
    "plain Python": per_run(lambda i: plain("q")),
    "LangGraph, no checkpointer": per_run(lambda i: graph.invoke({"query": "q", "log": []})),
    "LangGraph + InMemorySaver": per_run(lambda i: saved.invoke({"query": "q", "log": []}, {"configurable": {"thread_id": str(i)}})),
}
print("orchestration time per 3-step run (no model calls):")
for k, ms in runs.items(): print(f"  {k:<28} {ms:8.3f} ms")
print(f"\ncheckpoints written per run: {len(list(saved.get_state_history({'configurable': {'thread_id': '0'}})))}")
model_ms = llm_s / 24 * 1000                         # from the routing run above: one decision, amortised over a batch of 24
print(f"one LLM routing decision in the run above: about {model_ms:.0f} ms, "
      f"{model_ms / runs['LangGraph + InMemorySaver']:,.0f}x the whole graph's overhead")

Reading this output

Plain Python costs nothing. Three function calls take about a microsecond.

A LangGraph run adds under a millisecond for three steps: building the state, applying reducers, choosing edges. A checkpointer adds a few milliseconds more, because it serialises the state at every step (5 checkpoints for 3 steps: the input, the start, and one per node). Exact timings vary between runs; the orders of magnitude do not.

Next to a model call, both are rounding errors. One small-model routing decision on this CPU took far longer than the whole graph, checkpoints included. A hosted model call is typically hundreds of milliseconds to seconds. Choosing a framework for speed is rarely the right concern. What makes one framework expensive is the extra model calls it makes for you: a manager choosing the next speaker, a planner re-planning, a critic reviewing every turn. Count those.

Idea 6 · Interoperability

  • LangGraph ↔ LangChain tools, retrievers, LLMs. First-class MCP adapter (tools imported as MCP servers).
  • CrewAI ↔ tools inherit from BaseTool; LangChain tools, LlamaIndex tools, and MCP tools all adapt in. Crew-to-crew delegation via allow_delegation=True.
  • AutoGen → FunctionTool wraps any Python callable; MCP adapter available. (AG2 is a separate, community-run fork of the original AutoGen; Microsoft Agent Framework supports MCP and is adding the A2A protocol.)
  • Agno → @tool decorator or BaseTool subclass; MCP adapter; tools can be shared across agents and teams.

The Skill

You can explain, in one sentence, why a given framework is right for a given agent problem.

Pre-build checklist:

  1. Draw the shape. Is this a graph (typed state, named transitions)? A role play (specialists hand off work)? A chat (agents talk until done)? A single agent with tools?
  2. Decide who branches. Developer-decided branching → LangGraph. Manager-agent-decided → CrewAI hierarchical. Chat-emergent → AutoGen. Tool-call-decided → Agno.
  3. Check the state budget. Do you need resume-from-checkpoint? Time-travel? Human interrupts mid-run? If yes, LangGraph is the default; Agno sessions cover conversation-scoped state.
  4. Check the cost budget. LLM-selected routing costs extra tokens per turn. If the agent runs thousands of times a day, prefer explicit routing.
  5. Budget the framework overhead. Every framework is another dependency. If the task is two LLM calls and a tool, write 30 lines of plain Python; no framework is cheaper than no framework.

Refuse to reach for a framework before you can draw the graph, the org chart, the chat, or the agent box. Refuse to pick one that forces you to fight its state model for the thing you actually need.

The Decision Matrix

Problem shape Preferred framework Why
Workflow DAG with typed state, human approvals, long-running LangGraph First-class state, checkpointer, interrupts, time-travel.
Research / writing pipeline with distinct roles CrewAI (sequential) or LangGraph subgraphs Role-per-task is cheap to express in CrewAI; scale up with LangGraph when branching gets complex.
Proposer-critic or teacher-student dialogue AutoGen, or Microsoft Agent Framework for new projects Agent-to-agent chat is its native shape (group chat and handoff orchestrations in Agent Framework).
Single agent with tools, sessions, memory Agno Thinnest setup, built-in storage and memory.
Thousands of parallel fanouts with reducers LangGraph + Send Parallel dispatch with per-field reducers for merging (others offer concurrent orchestration with less control over the merge).
Quick prototype, no framework commitment Plain Python + provider SDK No framework is the fastest framework.

Recap
What to keep from this lesson
  • Match the framework's core abstraction to the problem: graph, roles, chat, or single agent.
  • Ask where state lives and whether a run can resume, pause for a human, and be replayed.
  • Decide who branches: code (cheap, auditable) or a model (flexible, paid per decision).
  • Orchestration overhead is milliseconds; extra model calls are the real cost.
  • For two calls and a tool, plain Python is the cheapest framework.

Solutions

SolutionP1 · Embeddings and rules beat the small model

The embedding model and the hybrid tied at 22 of 24. The keyword rules got 20 of 24 (they abstain on 4 tickets), and the 0.5B model only 8 of 24, because it called almost everything "technical". Two caveats keep this honest. The rules were written by someone who had read the tickets. And a much larger model would route these easily, so the lesson is not that models cannot route. It is that model routing must be measured, it costs a call per decision, and cheap alternatives are often as good.

SolutionB1 · A manager is a model call on every handoff

Every handoff now goes through a manager model call that reads the role descriptions, the task list and the work so far. A three-task sequential crew makes no routing calls. The hierarchical version makes at least three, often more when the manager delegates, checks and re-delegates. Each call carries a growing prompt. The worked example above puts five such decisions at about $0.016 per run on Claude Sonnet 5.5. Consistency also drops: a model choosing the order can choose differently on two runs with the same input, so the same request can follow different paths. That makes failures harder to reproduce and evaluations noisier. Use hierarchical mode when the order really cannot be known in advance, and log the manager's decisions so you can see where the tokens go.
