In plain words first
The idea in one line

Modern MCP has no handshake and no protocol session. Each request must carry enough metadata to be understood, authorized, routed, and retried on its own.

Terms you'll hear
Term Meaning
Stateless protocol Every request supplies the metadata needed to interpret it
Request metadata Version, client capabilities, and recommended client identity in params._meta
server/discover Mandatory server method for versions, capabilities, instructions, and identity
resultType Discriminator on every successful modern result

The problem

In plain words first

The Model Context Protocol (MCP) is a standard way for an AI application (the client) to use tools and data offered by a separate program (the server). Messages are JSON-RPC: a request with an id and a method name, and a reply with the same id. Since the 2026-07-28 revision, MCP is stateless. There is no opening handshake and no session, so every request carries its own protocol version and client capabilities, and the server answers each one on its own. A server offers tools (actions), resources (data) and prompts (templates). This lesson explains the message format and the life of one request. It then runs a real MCP server written with the official Python SDK and talks to it in raw JSON-RPC, so you can see exactly what goes over the wire, including the errors and the older handshake that 2025-era clients still use.

An MCP server can receive two consecutive requests from different clients, with different capabilities, on the same process or HTTP worker. If the server remembers what the previous request declared, it can apply the wrong permissions or return the wrong wire shape.

MCP 2026-07-28 removes that ambiguity. The protocol core is stateless. A server must decide how to handle the current request from the current request, not from connection history.

This changes the mental model. The old sequence was connection first, handshake second, operations third. The modern sequence is simpler:

  1. The client sends a self-describing request.
  2. The server validates that request's version and capabilities.
  3. The server handles the method.
  4. The server returns a typed result or a JSON-RPC error.

The next request repeats the same process from scratch.

Idea 1 · Server primitives

MCP servers expose three primary primitives:

  1. Tools are model-controlled actions, discovered with tools/list and invoked with tools/call.
  2. Resources are URI-addressed data, discovered with resources/list and retrieved with resources/read.
  3. Prompts are reusable templates, discovered with prompts/list and rendered with prompts/get.

Roots, sampling, and logging remain in the 2026-07-28 schema for compatibility, but they are deprecated. New implementations should use explicit tool or resource inputs for roots, direct model-provider APIs for sampling, and stderr or OpenTelemetry for logging. Elicitation remains available through Multi Round-Trip Requests, where a server returns an input request and the client retries the original operation. A modern server never starts an independent JSON-RPC request.

Idea 2 · JSON-RPC envelopes

MCP uses JSON-RPC 2.0:

  • Request: {jsonrpc, id, method, params}
  • Response: {jsonrpc, id, result} or {jsonrpc, id, error}
  • Notification: {jsonrpc, method, params} with no id

The request id correlates one response. It does not create a protocol session.

Idea 3 · Required request metadata

Every modern request carries a _meta object inside params:

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "course-client",
        "version": "1.0.0"
      }
    }
  }
}

The protocol version and client capabilities are required. Client identity is recommended. It is self-reported display and debugging data, not a security credential.

The server must not infer any of these values from an earlier request, a stdio process, an HTTP connection, or a transport header alone.

Idea 4 · Complete results and server identity

Every successful modern result includes resultType. A normal final result uses "complete". Servers should also identify themselves in result metadata:

{
  "jsonrpc": "2.0",
  "id": 7,
  "result": {
    "resultType": "complete",
    "tools": [],
    "ttlMs": 30000,
    "cacheScope": "public",
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "notes-server",
        "version": "1.0.0"
      }
    }
  }
}

tools/list, resources/list, prompts/list, resources/templates/list, resources/read, and server/discover are cacheable results. They include ttlMs and cacheScope. A safe default is ttlMs: 0 and cacheScope: "private". List items should have deterministic ordering so equivalent responses produce stable cache keys and stable model context.

Idea 5 · Discovery without a handshake

Every modern server must implement server/discover. The client may call it before another method to retrieve:

  • supportedVersions
  • server capabilities
  • optional usage instructions
  • server identity in result _meta
  • cache hints

Discovery is useful, but it is not a gate. A client can send tools/list first because that request already carries its protocol version and capabilities.

If the requested version is unsupported, the server returns JSON-RPC code -32022 with:

{
  "requested": "2027-01-01",
  "supported": ["2026-07-28"]
}

The client selects a mutually supported modern version and retries with a new JSON-RPC request id.

Idea 6 · One request lifecycle

Trace a modern request in this order:

  1. Parse one JSON-RPC envelope.
  2. Confirm jsonrpc is "2.0", an id exists, method is a string, and params is an object.
  3. Require the version string and capability object in params._meta; malformed or missing metadata is -32602.
  4. At an HTTP boundary, compare the version, method, and applicable name headers with the body. A mismatch is -32020 even when one of the two version values is unsupported.
  5. After equality is established, reject a matched but unsupported version with -32022.
  6. Check required capabilities, then route by method and validate method-specific arguments.
  7. Authenticate and authorize the concrete operation before its handler runs.
  8. Return a complete result with server identity.
  9. Forget request-scoped protocol metadata.

That order prevents two components from interpreting different calls. A gateway must not authorize Mcp-Name: notes.read while the origin executes params.name: notes.delete. It also keeps malformed input, header confusion, version negotiation, capability failure, authorization, and handler failure as distinct evidence.

Closing stdin or an HTTP response ends transport activity. It does not terminate a protocol session because modern MCP has no protocol session.

The same idea as a formula

Stateless means a function of the request alone. For a server S and requests r1​,r2​,… on any connection,

S(rn​∣r1​,…,rn−1​)=S(rn​),
so the answer cannot depend on what earlier requests declared. Everything S needs (version v, capabilities C, method, arguments) is inside rn​.

Checks in a fixed order. With V the set of supported versions:

malformed or missing (v,C)⇒−32602,header=body⇒−32020,v∈/V⇒−32022 with (requested,supported),
then capability checks, authorization, and only then the handler.

Caching a list result. A result fetched at time t0​ with hint ttlMs may be reused at time t if

t−t0​<ttlMsand the reuser is allowed by cacheScope (private:same authorization context only).

Worked example
Tracing four requests
  • tools/list with version 2027-01-01: well-formed, but v∈/{2026-07-28} → -32022, data {"requested": "2027-01-01", "supported": ["2026-07-28"]}. The client retries with a new id and a supported version.
  • tools/list without clientCapabilities: the version is fine, but the envelope is incomplete → -32602, even if the previous request on the same pipe had capabilities.
  • tools/list answered with ttlMs: 30000, cacheScope: "public": any client may reuse it for 30 s. With ttlMs: 0, cacheScope: "private" (the safe default, and what the SDK returns), nobody may reuse it.
  • tools/call for an unknown tool: the protocol request is fine, so the answer is a normal result with isError: true, text the model can read.

A real MCP server, spoken to in raw JSON-RPC

A two-tool notes server is written with the official MCP Python SDK (mcp 2.x, which implements MCP 2026-07-28) and launched as a subprocess on the stdio transport. The client is plain Python writing one JSON-RPC message per line, so every byte on the wire is visible. About 2 seconds.

import json, subprocess, sys, tempfile, textwrap, pathlib

# A real MCP server, written with the official Python SDK (v2, MCP 2026-07-28), saved to a file.
SERVER = textwrap.dedent('''
    from mcp.server import MCPServer
    mcp = MCPServer("notes-server")
    NOTES = {"n1": "Buy paper", "n2": "Call Priya"}

    @mcp.tool()
    def search_notes(query: str) -> list[str]:
        """Use when the user wants to find a note by a word it contains."""
        return [t for t in NOTES.values() if query.lower() in t.lower()]

    @mcp.tool()
    def add_note(text: str) -> str:
        """Use when the user wants to save a new note."""
        NOTES[f"n{len(NOTES) + 1}"] = text
        return f"saved n{len(NOTES)}"

    mcp.run()                       # stdio transport: JSON-RPC messages, one per line
''')
path = pathlib.Path(tempfile.mkdtemp()) / "notes_server.py"
path.write_text(SERVER)
proc = subprocess.Popen([sys.executable, str(path)], stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                        stderr=subprocess.DEVNULL, text=True)

META = {"io.modelcontextprotocol/protocolVersion": "2026-07-28",
        "io.modelcontextprotocol/clientCapabilities": {},
        "io.modelcontextprotocol/clientInfo": {"name": "course-client", "version": "1.0.0"}}
def rpc(id_, method, params):
    msg = {"jsonrpc": "2.0", "id": id_, "method": method, "params": params}
    proc.stdin.write(json.dumps(msg) + "\n"); proc.stdin.flush()
    reply = json.loads(proc.stdout.readline())
    return msg, reply
def show(msg, reply, keep=None):
    print("-> " + json.dumps(msg)[:230])
    r = reply.get("result", reply.get("error"))
    if keep: r = {k: r[k] for k in keep if k in r}
    print("<- " + json.dumps({k: v for k, v in reply.items() if k not in ("result", "error")} |
                             {"result" if "result" in reply else "error": r})[:600] + "\n")

# 1. Discovery: no handshake, just a request that carries its own metadata.
show(*rpc(1, "server/discover", {"_meta": META}), keep=["resultType", "supportedVersions", "capabilities", "_meta"])
# 2. tools/list: a cacheable result with resultType, ttlMs and cacheScope.
msg, reply = rpc(2, "tools/list", {"_meta": META})
show(msg, reply, keep=["resultType", "ttlMs", "cacheScope", "_meta"])
print("   tools:", [(t["name"], list(t["inputSchema"]["properties"])) for t in reply["result"]["tools"]], "\n")
# 3. tools/call: a different request, interpreted on its own.
show(*rpc(3, "tools/call", {"name": "search_notes", "arguments": {"query": "priya"}, "_meta": META}),
     keep=["resultType", "content", "structuredContent", "isError"])
proc.stdin.close(); proc.wait(timeout=10)

Reading this output

No handshake. The very first message is server/discover, and it is answered directly. The request carries its own version, capabilities and client identity in params._meta; the reply says which versions the server supports (2026-07-28), what it offers (tools, resources, prompts) and who it is, in _meta under io.modelcontextprotocol/serverInfo.

Every result says what kind it is. All three replies carry "resultType": "complete". The other value, input_required, is for Multi Round-Trip Requests (Lesson 13.12).

The two tools come back in the order they were defined, a deterministic order as the spec asks, with input schemas generated from the Python type hints (query, text).

A tool result has two forms. content is text for the model ("Call Priya"); structuredContent is the same data as JSON for programs ({"result": ["Call Priya"]}), generated from the function's return type list[str].

Reading this output

Version and envelope problems are protocol errors. An unsupported version gets -32022 with exactly the data the spec requires: the requested version and the supported list. A request missing its capabilities, or with no _meta at all, gets -32602, even though earlier requests on the same pipe were complete. The server keeps no memory of them: that is statelessness, enforced.

clientInfo is optional. Without it the call still succeeds ("saved n3"): identity is recommended for debugging, not required.

Tool problems are results, not errors. Arguments that fail the tool's schema and an unknown tool name both come back as normal results with isError: true and a message the model can read and act on. Since 2025-11-25 the spec asks for exactly this, so the model can correct itself.

The old handshake still works, on its own connection. A fresh connection that starts with initialize for 2025-11-25 gets the legacy treatment: version negotiated once, and tools/list without _meta answered in the 2025 format, without resultType. The SDK keeps the two eras apart, as Idea 7 describes.

Idea 7 · Explicit legacy compatibility

Versions through 2025-11-25 use initialize, notifications/initialized, connection-scoped capabilities, and, on earlier Streamable HTTP, optional protocol sessions. That behavior is still relevant when a dual-era client talks to an old server.

Keep the eras separate. A modern request is identified by the required per-request metadata. A legacy connection is selected only through the documented fallback path. Do not send initialize as the default for a 2026-07-28 server.

“Stateless” therefore has an era-specific meaning. In 2026-07-28, it is a protocol invariant: every ordinary request is independently interpretable and no MCP session exists. In versions through 2025-11-25, initialization and negotiated capabilities belong to a connection, so a compatibility adapter may retain that legacy connection state. A dual-era implementation is not one permissive state machine. It is a stateless modern core beside an isolated legacy adapter, with an explicit selection decision before either parser runs.

Neither meaning forbids durable application state. A workflow, task, or draft can live behind an opaque handle in a shared store. The client sends that handle as ordinary input, and every replica authenticates and authorizes its use. Protocol context must not leak into that store as a substitute for the removed session.

Industry practice
What's current (2024–2026)
  • MCP 2026-07-28 is the current revision: stateless requests with _meta envelopes, server/discover, resultType on every result, cache hints on list results, Multi Round-Trip Requests instead of server-initiated requests; Roots, Sampling and Logging deprecated.
  • Official SDKs implement it and still serve 2025-era clients: the Python SDK 2.x (MCPServer, Client, used here) and the TypeScript, Go, Java, C# and Rust SDKs.
  • Clients: Claude (desktop, web, Claude Code), ChatGPT, VS Code, Cursor and many agent frameworks connect to MCP servers; the clients adapt MCP tool lists to whichever model API they call.
  • Governance: MCP is developed in the open, with SEPs (specification enhancement proposals) and a 12-month deprecation window for removed features.

Given a sequence of MCP JSON-RPC envelopes, audit each message independently against MCP `2026-07-28`. Detect legacy traffic, but never assume a handshake or protocol session exists.

Produce:

1. Message annotation. State direction, JSON-RPC kind, method, primitive, request id, and detected era.
2. Modern metadata check. For every request, verify `params._meta.io.modelcontextprotocol/protocolVersion` and `params._meta.io.modelcontextprotocol/clientCapabilities`. Record whether recommended `clientInfo` is present.
3. Result check. Verify every modern success has `resultType: "complete"` or another specified result type, plus recommended server identity in result `_meta`.
4. Discovery and version check. Verify modern servers implement `server/discover`. Interpret `-32022` as modern evidence and check `data.requested` plus `data.supported`.
5. Cache check. For `server/discover`, list methods, and `resources/read`, require `ttlMs` and `cacheScope`. Flag nondeterministic list ordering.
6. Direction check. Reject server-initiated JSON-RPC requests in modern traffic. Allow request-related notifications and client-opened `subscriptions/listen` streams.
7. Compatibility check. Label `initialize` and `notifications/initialized` as legacy only. Do not require them in modern traffic.

Hard rejects:

- Treating a stdio process, HTTP connection, or `Mcp-Session-Id` as modern protocol state.
- Inferring client capabilities from an earlier request.
- Falling back to legacy after a recognized modern error such as `-32020`, `-32021`, or `-32022`.
- Accepting a modern success without `resultType`.

Refusal rules:

- If the transcript is not JSON-RPC 2.0, stop and identify the incompatible envelope.
- If asked to silently rewrite evidence, refuse. Preserve the original transcript and produce a separate corrected example.

Output one line per message in arrival order:

```text
[request/modern/tools] id=7 tools/list metadata=valid
```

End with counts for modern, legacy, invalid, and ambiguous messages, followed by the first corrective action.

Exercises

  1. Change one request's protocol version to 2027-01-01. Confirm the error code is -32022 and the data advertises the supported version.
  2. Remove io.modelcontextprotocol/clientCapabilities from the second request. Confirm the server does not reuse capabilities from the first request.
  3. Reverse the in-memory tool registry. Confirm tools/list still returns the same deterministic order.
  4. Change cacheScope from public to private. Explain which authorization contexts may reuse the response in each case.
  5. Add an optional clientInfo omission test. The request should remain valid because client identity is recommended, not required.

Solutions

SolutionP1 · No handshake, and "don't cache" by default

No handshake: server/discover was the first message, and every request carried its own version and capabilities. The server never asked for initialize.

The tools/list result said ttlMs: 0 and cacheScope: "private": the official SDK's default is "do not reuse". That is the safe choice when the author has not thought about caching; a server whose tool list is the same for everyone and rarely changes can raise ttlMs and mark it public.

SolutionB1 · Someone else's tool list

Users see each other's tool lists. The gateway caches by URL alone, so whichever user's tools/list arrived first is served to everyone for the cache lifetime. If the list depends on the user's permissions, another user may see admin tools they cannot use (confusing at best), or the model may be offered tools for an account that is not theirs. If the gateway also routes calls by the cached list, the confusion reaches execution.

Two fixes are needed, one on each side:

  • The server must tell the truth: results that differ by user are cacheScope: "private". Only lists identical for every caller may be public.
  • The gateway must respect scope: private results are cached only per authorization context (user, token, tenant), with the key including that context, and never beyond ttlMs.

Authorization still happens on every tools/call regardless of what any cache says, so a stale list can never grant access by itself.

Debug a failureA gateway in front of an MCP server authorizes each tools/call by reading the Mcp-Name header and checking it against the caller's role. The origin server behind it executes params.name from the JSON body. An attacker sends Mcp-Name: notes.read with a body whose params.name is notes.delete. The gateway also rejects an unsupported MCP-Protocol-Version before it looks at anything else. Walk through what happens, and give the validation order you would ship.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. The gateway approves a read while the origin runs a delete, because two components decide from two different fields. Ship one fixed order: validate the JSON-RPC and metadata types, compare every mirrored header with the body, and only after equality is proven check whether the matched version is supported. A disagreement is HTTP 400 with -32020 even when one of the two version values is unsupported, so the request dies before a backend is selected, a role is checked or a rate-limit token is spent.

The mirrored headers.

Header Must equal
MCP-Protocol-Version params._meta.io.modelcontextprotocol/protocolVersion
Mcp-Method the JSON-RPC method
Mcp-Name params.name, or params.uri for resources/read

Header names are case-insensitive. Header values are case-sensitive. A non-ASCII or unsafe name travels as the =?base64?{value}?= sentinel, and the server decodes it before the comparison.

The order and the codes.

  1. Parse one envelope. Confirm jsonrpc is "2.0", an id exists on a request (a notification has none), method is a string and params is an object.
  2. Require the version string and the capability object in params._meta. Missing or malformed metadata is -32602.
  3. Compare each mirrored header with the body. A mismatch is HTTP 400 with -32020, even when one value is unsupported.
  4. With equality established, reject a matched but unsupported version with HTTP 400 and -32022, with data exactly {"supported":["2026-07-28"],"requested":"<actual>"}.
  5. Check required capabilities, route by method, validate method-specific arguments.
  6. Authenticate and authorize the concrete operation before its handler runs.
  7. Return a complete result with server identity, then forget the request-scoped metadata.

An unknown method is HTTP 404 with -32601. A notification has no id and receives no JSON-RPC body; an accepted one gets 202 with an empty body.

Why the order matters.

Each step leaves a distinct piece of evidence: malformed input, header confusion, version negotiation, capability failure, authorization and handler failure stay separate. Checking version support before header equality mixes two classes and lets a crafted header reach a decision. Validating routing before policy closes the gap in which one component authorizes the body while another routes by the header.

What the gateway does after validation.

Authorization still comes from the authenticated principal and resource policy, not from the header and not from clientCapabilities. The sequence is: authenticate the transport credential, validate version, headers and shape, check capability compatibility, then authorize the principal against the exact verb, resource and normalized arguments, and only then execute or request user input.

Plausible wrong answers.

  • "Trust the header, because the gateway routes on it." The body is what executes. The two must be proven equal before either is used for a decision.
  • "Check version support first so that bad clients fail fast." A mismatch must return -32020 even when a version is unsupported; support is checked only after equality.
  • "Header values are case-insensitive like header names." Values are case-sensitive, and a name that differs in case is a different name.

Follow-ups an interviewer may ask.

  • (level 3) Header and body both say version 2027-01-01. Which response? Expected: HTTP 400 with -32022 and data {"supported":["2026-07-28"],"requested":"2027-01-01"}.
  • (level 3) Mcp-Name carries a resource URI with non-ASCII characters. How does the server compare it? Expected: the client sends the exact base64 UTF-8 sentinel, and the server decodes it before comparing with params.uri.
  • (level 4) Why must the mismatch check run before a rate-limit token is consumed? Expected: a rejected request should cost nothing and leave its own evidence; otherwise an attacker spends quota or triggers policy against the wrong object.
  • (level 4) The attacker's request also carries a valid bearer token. Does that change the outcome? Expected: no; the wire validation fails first, and authentication tells you who sent a malformed request, not that it may run.

Where it is taught. The fundamentals lesson gives the lifecycle order, the transports lesson defines the mirrored headers, and the security lesson places routing before policy.

Explain the mechanismA colleague ports an MCP server from the 2025 revision. The port keeps the initialize handshake and stores the client's declared capabilities on the connection object for later requests. All the old tests pass. What breaks under the current revision, and where does the metadata have to live instead?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The current revision has no handshake and no protocol session. A server that remembers capabilities from an earlier message can apply the wrong permissions or the wrong wire shape to the next request, which may come from another client on the same process or land on another worker. Every request carries io.modelcontextprotocol/protocolVersion and io.modelcontextprotocol/clientCapabilities in params._meta, and the server validates them on each request and forgets them after it answers.

The request is the unit of interpretation.

{
  "jsonrpc": "2.0",
  "id": 7,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {"name": "course-client", "version": "1.0.0"}
    }
  }
}

The version and the capabilities are required. clientInfo is recommended, self-reported, and never a credential. The server must not infer any of these from an earlier request, a stdio process, an HTTP connection or a transport header alone.

What the server returns.

Every successful result includes resultType: "complete" and should carry io.modelcontextprotocol/serverInfo in its _meta. The list results, resources/read and server/discover also carry ttlMs and cacheScope, with deterministic ordering so that equal results give stable cache keys.

Discovery is a method, not a gate.

Every server must implement server/discover. It returns supportedVersions, capabilities, optional instructions and server identity. A client may call it first, but it may also send tools/list at once, because that request already carries its metadata.

The error codes that replace negotiation.

Case Code
metadata missing or malformed -32602
header disagrees with body at an HTTP boundary -32020
version matched but unsupported -32022, with requested and supported

The client picks a mutually supported version from supported and retries with a new request id.

Keep the eras apart.

Revisions through 2025-11-25 use initialize, notifications/initialized and connection-scoped capabilities. A dual-era server may keep that path as an isolated legacy adapter that it selects only when it receives initialize. It never routes a current request through the handshake path and never stamps resultType onto legacy results.

Application state is still allowed.

A workflow or a draft can live behind an opaque handle in a shared store. The client sends the handle as an ordinary argument, and every replica authenticates and authorizes its use. Protocol context must not leak into that store as a substitute for the removed session.

Plausible wrong answers.

  • "Stateless means the server cannot keep any state at all." Durable application state behind an explicit handle is allowed. Only hidden protocol context is removed.
  • "Send initialize first to be safe with every server." A current server must not receive initialize by default. Legacy is a documented fallback for a pinned peer.
  • "The connection identifies the client, so one capability check per connection is enough." Two clients can share one process or HTTP worker in sequence, and a remote request can land on any replica.

Follow-ups an interviewer may ask.

  • (level 2) Is clientInfo required, and can you authorize on it? Expected: it is recommended, not required; it is display and debugging data and never a credential.
  • (level 2) A client sends tools/list without calling server/discover. Does the server reject it? Expected: no; the request carries its version and capabilities, so discovery is not a gate.
  • (level 3) What does closing stdin or ending an HTTP response terminate? Expected: transport activity only; there is no protocol session to end, and the next request must still describe itself.
  • (level 4) Where does a multi-step workflow keep its state now? Expected: behind a server-minted opaque handle in a shared durable store, returned as a normal result, bound to the authenticated principal, expired, and authorized on every use.
