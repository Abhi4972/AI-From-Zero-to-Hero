In plain words first
The idea in one line

Scaling multi-agent systems to thousands of concurrent runs requires durable execution — work queues plus checkpoints, so any worker can resume any run after any crash, provided lease handling, idempotent side effects, and deterministic replay are in place. LangGraph's runtime is the reference example: it writes a checkpoint after each super-step keyed by thread_id (Postgres by default); worker crashes release a lease and another worker resumes. Agents can sleep indefinitely waiting for human input. MegaAgent (arXiv:2408.09955) ran a per-agent producer-consumer queue with three states (Idle / Processing / Response) and two-layer coordination (intra-group chat + inter-group admin chat). Fiber/async beats thread-per-job for LLM streaming: threads sit idle 99% of the time waiting for tokens, fibers cooperatively yield on I/O. Counterpoint: Ashpreet Bedi's "Scaling Agentic Software" argues for FastAPI + Postgres + nothing else until load proves otherwise — simple architectures go further than expected. This lesson builds a durable checkpoint log, a per-agent work queue with state transitions, an async-vs-thread demo, and lands the pragmatic "start simple" rule.

Problem

In plain words first

In production, agent runs last minutes or hours, workers crash, and load spikes. Durable execution saves each run's state after every step (a checkpoint), so any worker can pick the run up where it stopped. Two more things make that safe: side effects that can be repeated without harm (idempotency), and only one worker owning a run at a time (a lease). Durable execution, scaling and multi-agent platforms are covered in Lessons 14.114, 14.115 and 14.124 (linked above). This lesson breaks the lesson's checkpoint store in the two ways production does, measures what threads cost, and checkpoints a small real agent.

A prototype multi-agent system works on one laptop with three agents in an in-memory event loop. You move to production:

  • Agents sometimes run for hours (long research, human-in-the-loop waits).
  • Worker processes crash. Restarting loses state.
  • Peak load is 10x average; you need horizontal scaling.
  • Users pay per agent-run; you need exactly-once semantics for charging.

The in-memory event loop does none of these. You need a durable execution layer underneath. The 2026 canonical options are:

  1. A workflow engine with checkpoints (Temporal, LangGraph runtime).
  2. A message queue with a state store (Postgres + SQS/RabbitMQ).
  3. Actor-model frameworks (MegaAgent's producer-consumer per agent).
  4. Hand-rolled FastAPI + Postgres (Bedi's argument).

This lesson builds a miniature of each.

Concept

Durable execution, the pattern

A durable-execution engine persists the full program state after each "step" (super-step, in LangGraph's language). On crash:

worker crashes mid-step
  -> lease timeout
  -> another worker picks up the thread_id
  -> resumes from last checkpoint
  -> no duplicate side effects

Requirements for this to work:

  • Serializable state. All agent state has to be persistable. Function closures with live database connections do not survive.
  • Deterministic resume. Given the same state and same inputs, the agent produces the same actions (or defers to an external deterministic oracle for LLM calls).
  • Idempotent side effects. External calls (tool calls, payments) must be idempotent or use a deduplication key.

LangGraph writes a checkpoint after each super-step; Temporal writes after each activity; Restate uses event-sourced journals. All three implement the same pattern.

A checkpoint-per-step runtime

LangGraph's runtime is the worked example: each agent has a thread_id; state is a typed dict; each super-step writes a row to the checkpoints table. On resume, the runtime replays from the last checkpoint, not from scratch. Agents can interrupt() waiting for human input; the runtime persists and releases the worker. When input arrives, any worker can resume.

This is a widely used production design in 2026. One cost to know: full snapshots of append-only state, such as a growing message list, make total checkpoint storage grow with the square of the number of steps; LangChain added delta channels in May 2026 that store per-step diffs with a full snapshot every K steps.

MegaAgent's per-agent queue

arXiv:2408.09955 describes MegaAgent, a system that organises LLM agents into groups without predefined procedures; its largest experiment, a national policy simulation, ran 590 agents. Architecture:

agent i:
  state ∈ {Idle, Processing, Response}
  in_queue   <- messages addressed to agent i
  out_queue  -> replies + side effects

coordinators:
  intra-group chat  (agents in the same group)
  inter-group admin chat  (high-level routing)

The two-layer coordination lets intra-group conversation happen densely while inter-group traffic stays sparse, because only admin agents talk across groups. In the Processing state an agent batches its queued messages into one model call, and in Response it checks its output before sending.

Async vs thread-per-job

LLM calls are I/O-bound. A thread waiting for the next token is idle almost all the time. Each OS thread reserves a stack (8 MB of virtual memory by default on Linux) and uses some tens of kilobytes of resident memory, plus scheduler overhead; at 10,000 concurrent calls that adds up.

Fibers (Python asyncio, Go goroutines, Rust tokio) cooperatively yield on I/O, and each costs only a few kilobytes. The same 10,000 calls fit comfortably in one process. At LLM-agent scale, async is not an optimization — it is the architecture.

Exception: CPU-bound post-processing (embedding, tokenizer tricks) still wants threads or processes. Separate your I/O layer from your CPU layer.

Bedi's counterpoint

"Scaling Agentic Software" (Ashpreet Bedi of Agno, April 2026) argues that most teams over-engineer before they have measured load: "One FastAPI process. One Postgres database." may be enough for a multi-agent product with auth, persistence and observability, with queues, Redis or separate vector stores added only when load proves the need. The pragmatic default:

  • FastAPI + Postgres.
  • Each agent run is a row; state updated in-place with optimistic concurrency.
  • Background jobs via pg_notify or a simple Celery worker.
  • Retry policy in application code.

Bedi leaves the breaking point to load tests rather than a number; measure your own. Upgrade when you see it failing.

The rule: adopt durable-execution frameworks when you hit a concrete problem that simple architectures cannot solve. Premature adoption burns time on ceremonies that do not pay off.

Exactly-once semantics

For paid agent runs, you need "exactly-once effective" (at-least-once delivery + idempotent consumer). The engineering moves:

  • Dedup key per run. Include it in every side-effect call.
  • Outbox pattern. Side effects write to a table first, then a separate process executes them. Both steps idempotent.
  • Compensating transactions. When a side effect succeeds but its tracking write fails, schedule a compensate.

These are database-engineering patterns, not LLM-specific. The LLM tax is only that LLM calls are slow; everything else is standard distributed systems.

Rainbow deployment

Anthropic's multi-agent research system uses "rainbow deployments": multiple versions of the agent runtime run concurrently so long-running agents do not have to be killed on every code deploy. Canary new versions on a slice of traffic; retire old versions when their agents finish.

This is standard for long-running stateful systems; the 2026 adaptation is that agents can live for hours, so deployment cycles must accommodate.

The canonical production checklist

  • Durable state (checkpoints, snapshots, or outbox + replayable log).
  • Idempotent side effects.
  • Async I/O layer for LLM calls.
  • At-least-once delivery with dedup.
  • Rainbow/canary deployment for stateful workloads.
  • Observability: per-agent traces, super-step audit, retry counter.

The same idea as a formula

Exactly-once effect. Delivery is at least once, so a step may run k≥1 times. A side effect e applied with key κ is idempotent if

apply(e,κ)k=apply(e,κ)for all k≥1.
The key must be stable across retries, for example (run id, step number), not a fresh random id per attempt.

Checkpoint growth. If state is an append-only list that gains about d bytes per step, the full snapshot after step t is about td, and storing every snapshot costs

t=1∑T​td=2T(T+1)​d,
against Td for deltas. The ratio, (T+1)/2, grows with the length of the run.

Worked example
A charge that happens twice
  • Steps are numbered 1 to 3. Step 2 of run-7 bills the customer 10, then the worker crashes before writing the checkpoint for step 2.
  • The last checkpoint is step 1, so the new worker re-runs step 2 and bills 10 again.
  • Total billed: 40 for three steps of 10, while the checkpoint says 30.
  • With the key (run-7, 2) recorded by the payment service, the retry is recognised and the total is 30.
Check your mental model
  • ✗ "Resuming from the last checkpoint means no duplicate side effects."

  • ✗ "Two workers on one thread will raise an error."
    ✓ The lesson's INSERT OR REPLACE silently overwrote worker A's step; a lease or a plain INSERT would have caught it.

Breaking the lesson's checkpoint store the way production does

The lesson's CheckpointStore and AgentQueue: a side effect before a crash, two workers resuming one thread, the queue's throughput, and the memory of 2,000 waiting threads against 2,000 asyncio tasks. Runs in about 2 seconds.

# The lesson's CheckpointStore, AgentQueue and async/thread demo (imported from main.py), tested on the three
# things durable execution must also get right: side effects across a crash, two workers on one thread, and what
# a thread really costs. Runs in about 2 seconds.
import asyncio, os, sqlite3, tempfile, threading, time
from main import CheckpointStore, AgentQueue, AgentState

def db():
    f = tempfile.NamedTemporaryFile(suffix=".db", delete=False); f.close(); return f.name

print("1. a side effect, then a crash before the checkpoint is written")
for dedup in (False, True):
    path = db(); store = CheckpointStore(path); charges = []; seen = set()
    def charge(key, amount):
        if dedup and key in seen:
            return
        seen.add(key); charges.append(amount)
    def worker(crash_after_charge_at=None):
        last = store.latest("run-7"); step, state = (last[0] + 1, last[1]) if last else (0, {"billed": 0})
        while step < 3:
            charge(("run-7", step), 10)                         # e.g. bill the customer for this step
            if step == crash_after_charge_at:
                raise RuntimeError("crash between the side effect and the checkpoint")
            state["billed"] += 10; store.write("run-7", step, dict(state)); step += 1
    try:
        worker(crash_after_charge_at=1)
    except RuntimeError:
        pass
    worker()
    print(f"   dedup key {'on ' if dedup else 'off'}: customer charged {sum(charges)} for 3 steps of 10 (checkpoint says {store.latest('run-7')[1]['billed']})")
    os.unlink(path)

print("\n2. two workers resume the same thread at once (no lease)")
path = db(); s1, s2 = CheckpointStore(path), CheckpointStore(path)
s1.write("t-9", 0, {"notes": ["plan"]})
step_a, st_a = s1.latest("t-9"); step_b, st_b = s2.latest("t-9")
s1.write("t-9", step_a + 1, {"notes": st_a["notes"] + ["worker A: searched papers"]})
s2.write("t-9", step_b + 1, {"notes": st_b["notes"] + ["worker B: drafted intro"]})
print(f"   final state: {s1.latest('t-9')[1]}; worker A's step was overwritten without an error (INSERT OR REPLACE)")
conn = sqlite3.connect(path)
try:
    conn.execute("INSERT INTO checkpoints VALUES (?, ?, ?)", ("t-9", 1, "{}")); conn.commit()
except sqlite3.IntegrityError as e:
    print(f"   a plain INSERT would have refused the second write: IntegrityError: {e}")
os.unlink(path)

print("\n3. the per-agent queue: one message per three steps")
q = AgentQueue("agent-a")
for i in range(6):
    q.enqueue({"task": i})
steps = 0
while q.in_queue or q.state != AgentState.IDLE:
    q.step(); steps += 1
print(f"   6 messages took {steps} steps; each pass through processing handles one message (MegaAgent batches the queue)")

print("\n4. what 2,000 waiting threads and 2,000 waiting tasks cost")
def mem():
    d = dict(l.split(":", 1) for l in open("/proc/self/status") if l.startswith(("VmRSS", "VmSize")))
    return int(d["VmRSS"].split()[0]) / 1024, int(d["VmSize"].split()[0]) / 1024
r0, v0 = mem()
stop = threading.Event()
ths = [threading.Thread(target=stop.wait) for _ in range(2000)]
t0 = time.perf_counter()
for t in ths:
    t.start()
t_start = time.perf_counter() - t0
r1, v1 = mem(); stop.set()
for t in ths:
    t.join()
print(f"   threads: started in {t_start:.2f} s; resident memory +{r1 - r0:.0f} MB, virtual +{v1 - v0:.0f} MB "
      f"(+{(r1 - r0) * 1024 / 2000:.0f} KB resident each)")
async def tasks():
    ev = asyncio.Event(); ra, va = mem()
    ts = [asyncio.create_task(ev.wait()) for _ in range(2000)]
    await asyncio.sleep(0); rb, vb = mem(); ev.set(); await asyncio.gather(*ts)
    return rb - ra, vb - va
dr, dv = asyncio.run(tasks())
print(f"   asyncio tasks: resident memory +{dr:.0f} MB, virtual +{dv:.0f} MB")

The crash billed the customer twice for one step. Without a dedup key the total was 40 for three steps of 10, while the checkpoint said 30: step 2's charge ran before the crash and again on resume. With the key (run, step), the retry was ignored and the total was 30.

Two workers lost a step without an error. Both read step 0 and both wrote step 1. The lesson's INSERT OR REPLACE kept worker B's note and silently dropped worker A's. A plain INSERT on the same primary key raised an IntegrityError, which is the behaviour you want; a lease would stop the second worker from starting at all.

The queue handles one message per three steps. Six messages took 18 steps, because each message goes through processing and response on its own. MegaAgent's Processing state batches everything queued into one model call.

# This block continues from the one above. A small real agent on the lesson's CheckpointStore: Qwen2.5-0.5B-Instruct
# (sampled, temperature 0.8, CPU) writes an 8-step trip plan, one short step per super-step, and the full message
# history is checkpointed after every step, as LangGraph does by default. We measure how the checkpoints grow,
# then crash after the model call in step 4 and resume, once re-calling the model and once replaying a journal of
# recorded model outputs. About 1 minute.
import os, json, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def llm_step(messages, seed):
    ids = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    torch.manual_seed(seed)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=40, do_sample=True, temperature=0.8, top_k=0, top_p=1.0)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()

STEPS = 8
observed = {}
def run(store, journal, crash_at=None, seed_base=0):
    last = store.latest("trip")
    step, state = (last[0] + 1, last[1]) if last else (0, {"messages": [
        {"role": "system", "content": "You plan a 2-day trip to Lisbon, one short step at a time."}]})
    while step < STEPS:
        msgs = state["messages"] + [{"role": "user", "content": f"Step {step + 1} of {STEPS}: one sentence."}]
        key = f"trip:{step}"
        if journal is not None and key in journal:
            reply = journal[key]                              # replay the recorded model output
        else:
            reply = llm_step(msgs, seed=seed_base + step)
            observed[key] = reply                             # what the model said, for the comparison below
            if journal is not None:
                journal[key] = reply                          # in production the journal is durable, like the checkpoint
        if step == crash_at:
            raise RuntimeError("crash after the model call, before the checkpoint")
        state = {"messages": msgs + [{"role": "assistant", "content": reply}]}
        store.write("trip", step, state); step += 1
    return state

f = tempfile.NamedTemporaryFile(suffix=".db", delete=False); f.close()
store = CheckpointStore(f.name)
run(store, journal=None)
rows = store.conn.execute("SELECT super_step, length(state_json) FROM checkpoints WHERE thread_id='trip' ORDER BY super_step").fetchall()
sizes = [n for _, n in rows]; deltas = [sizes[0]] + [b - a for a, b in zip(sizes, sizes[1:])]

        pass

    after = final["messages"][8]["content"]
    print(f"   {name:19s} same step-4 text as before the crash: {before == after}")
    print(f"      before: {before[:80]!r}")

Reading this output

Snapshots grow with the run. Each checkpoint holds the whole history, from 322 bytes after step 1 to 2,229 after step 8. Storing all eight took 9,973 bytes against 2,229 as deltas, 4.5 times more after only 8 steps. The ratio keeps growing, which is why LangChain's 200-turn workload went from 5.3 GB to 129 MB with deltas.

Re-calling a sampled model changes the run. After the crash in step 4, the new worker called the model again and got a different sentence ("Be sure to check the weather forecast") from the one the crashed worker had produced ("Don't miss out on exploring the city"). Anything downstream that already saw the first version now disagrees with the record.

Replaying the journal keeps the run consistent. With model outputs recorded as they are produced, the resumed worker reused the original text. That is what Temporal does with activity results; for agents, record every model and tool result with its step.

"""Production scaling demo: checkpoints, queues, async vs threads.

All stdlib. CheckpointStore uses SQLite. AgentQueue is a per-agent state
machine with 3 states. async vs threads benchmark runs 500 concurrent
simulated LLM calls.
"""
from __future__ import annotations

import asyncio
import enum
import json
import os
import sqlite3
import tempfile
import threading
import time
from dataclasses import dataclass, field


# ---------- CheckpointStore ----------

class CheckpointStore:
    def __init__(self, path: str) -> None:
        self.conn = sqlite3.connect(path)
        self.conn.execute("""
            CREATE TABLE IF NOT EXISTS checkpoints (
                thread_id TEXT NOT NULL,
                super_step INTEGER NOT NULL,
                state_json TEXT NOT NULL,
                PRIMARY KEY (thread_id, super_step)
            )
        """)

    def write(self, thread_id: str, super_step: int, state: dict) -> None:
        self.conn.execute(
            "INSERT OR REPLACE INTO checkpoints (thread_id, super_step, state_json) VALUES (?, ?, ?)",
            (thread_id, super_step, json.dumps(state)),
        )
        self.conn.commit()

    def latest(self, thread_id: str) -> tuple[int, dict] | None:
        row = self.conn.execute(
            "SELECT super_step, state_json FROM checkpoints WHERE thread_id = ? ORDER BY super_step DESC LIMIT 1",
            (thread_id,),
        ).fetchone()
        if row is None:
            return None
        return row[0], json.loads(row[1])


def run_agent_with_checkpoint(store: CheckpointStore, thread_id: str,
                              start: int = 0, crash_at: int | None = None, goal: int = 5) -> int:
    """Run a tiny 5-step agent; optionally crash at a given step."""
    restored = store.latest(thread_id)
    if restored:
        super_step, state = restored
        super_step += 1
    else:
        super_step = 0
        state = {"counter": start}

    while state["counter"] < goal:
        if crash_at is not None and super_step == crash_at:
            print(f"    worker crashes at super_step={super_step}")
            raise RuntimeError("simulated crash")
        state["counter"] += 1
        store.write(thread_id, super_step, dict(state))
        super_step += 1
    return state["counter"]

class AgentState(enum.Enum):
    IDLE = "idle"
    PROCESSING = "processing"
    RESPONSE = "response"


@dataclass
class AgentQueue:
    agent_id: str
    state: AgentState = AgentState.IDLE
    in_queue: list[dict] = field(default_factory=list)
    out_queue: list[dict] = field(default_factory=list)

    def enqueue(self, msg: dict) -> None:
        self.in_queue.append(msg)

    def step(self) -> None:
        if self.state == AgentState.IDLE and self.in_queue:
            self.state = AgentState.PROCESSING
        elif self.state == AgentState.PROCESSING:
            msg = self.in_queue.pop(0)
            self.out_queue.append({"reply_to": msg, "body": f"{self.agent_id} processed {msg}"})
            self.state = AgentState.RESPONSE
        elif self.state == AgentState.RESPONSE:
            self.state = AgentState.IDLE


def demo_queue() -> None:
    print("\n" + "=" * 72)

    a.enqueue({"task": "write summary"})
    print(f"  initial: {a.state.value}  in_queue={len(a.in_queue)}")

async def bench_async(n: int) -> float:
    t0 = time.perf_counter()
    await asyncio.gather(*(sim_llm_call_async() for _ in range(n)))
    return time.perf_counter() - t0


def bench_threads(n: int) -> float:
    t0 = time.perf_counter()
    threads = [threading.Thread(target=sim_llm_call_sync) for _ in range(n)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    return time.perf_counter() - t0

Break it on purpose

Your research-agent platform checkpoints every step to Postgres and retries crashed runs automatically. Support reports that some customers received the same report email twice, a few runs show sections that contradict each other, and the checkpoints table has grown to 400 GB in a month for 50,000 runs. Using this lesson, what are the three causes, and what would you change? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Durable runtimes for agents. LangGraph's runtime checkpoints each super-step and resumes on any worker; Temporal, Restate and DBOS offer durable workflows that agent frameworks build on.
  • Smaller checkpoints. LangChain's delta channels (May 2026) store per-step diffs; on a 200-turn coding agent, storage fell from 5.3 GB to 129 MB.
  • Start simple, measure, then grow. Agno's Ashpreet Bedi argues one FastAPI process and one Postgres database go a long way; the outbox pattern and idempotency keys make that setup safe for side effects.
  • On your laptop: SQLite and asyncio are enough to build and test all of this; record model outputs with each step, and key every side effect by run and step.

Sources: LangChain, The runtime behind production deep agents, LangChain, delta channels, Bedi, Scaling Agentic Software, MegaAgent (arXiv:2408.09955), Anthropic, Multi-agent research system.

Recap
What to keep from this lesson
  • Checkpoint after each step so any worker can resume any run.
  • Everything after the last checkpoint runs again: key side effects by run and step.
  • Give each run a lease, and make checkpoint writes fail on conflict instead of overwriting.
  • Record model outputs in the journal; re-calling a sampled model on resume changes the run.
  • Full snapshots of growing state cost quadratic storage; store deltas past a few dozen steps.

Ship it

Canonical production hardening:

  • Start simple (Bedi's rule). FastAPI + Postgres until you measure it failing.
  • Instrument everything before optimizing. Per-run latency histogram, per-step time, retry count, failure categorization.
  • Outbox pattern for side effects. Especially payments and external API calls.
  • Rainbow deploys. Never kill in-flight agent runs during deploys.
  • Adopt durable-execution engines (Temporal / LangGraph / Restate) when you hit specific problems: hour-long human-in-the-loop waits, cross-region coordination, complex retry/compensation policies.
  • Async for the I/O layer. Threads only for CPU-bound post-processing.

Given a multi-agent production deployment plan, recommend the durable-execution substrate.

Produce:

1. **Load profile.** Concurrent agent-runs (p50, p99). Per-run duration (seconds to hours). Fraction of runs requiring human-in-the-loop waits. Deploy frequency.
2. **State profile.** Size of per-run state (KB to MB). Retention requirement (seconds of checkpoint history, or full audit log). Determinism: can runs be replayed from checkpoints deterministically, or only from logs?
3. **Side-effect profile.** Which side effects need exactly-once (payments, external APIs, email)? Which can tolerate at-least-once (pure tool reads)? Outbox pattern needed for exactly-once.
4. **Recommendation tier.**
   - Tier 1 (Bedi's rule): FastAPI + Postgres. Under ~100 concurrent runs, sub-hour durations, simple retries.
   - Tier 2: LangGraph runtime or Temporal. Hour-long runs, interrupt/resume, structured retries.
   - Tier 3: Custom with outbox + event sourcing. Specialized needs, high throughput, strict audit.
5. **Deploy model.** Single version or rainbow/canary? Rainbow required for long-running stateful workloads.
6. **Async / thread boundary.** Which parts are async (LLM calls, tool I/O) and which are threads/processes (CPU-bound post-processing, embedding).
7. **Observability.** Per-run traces, super-step audit, retry counter. Storage for traces (separate from checkpoint store).

Hard rejects:

- Recommending Temporal for a 10-concurrent-run prototype. Ceremony cost > value.
- Thread-per-job LLM call architectures. I/O-bound + 1MB/thread does not scale.
- Designs without outbox pattern for paid side effects. Duplicate charges are expensive.
- Single-version deploys for multi-hour agent runs. Users lose state on every code push.

Refusal rules:

- If load is unknown and untested, recommend Tier 1 plus load testing. Premature optimization burns time.
- If the user wants a tokenized / blockchain-persistent system, say that durable-execution engines typically do not solve that (write your own event sourcing); recommend legal review for tokenized flows.
- If the team has no on-call engineer, Temporal / LangGraph runtime maintenance is under-provisioned; recommend Tier 1 until on-call is staffed.

Output: a two-page brief. Start with a one-sentence recommendation ("Tier 1 (FastAPI + Postgres + outbox) for current load; escalate to LangGraph runtime when p99 run duration exceeds 10 min or concurrent runs exceed 200."), then the seven sections above. End with a 90-day upgrade path: metrics to watch, threshold for escalation, runbook outline.

Exercises

  3. Simulate a rainbow deploy: two concurrent runtime versions; route half of new thread_ids to each; confirm that in-flight threads on the old version are not interrupted.
  4. Read LangGraph's runtime doc (linked below). Identify which features of the runtime would take the longest to replicate in a hand-rolled FastAPI + Postgres version. Is that a reason to adopt, or can you defer?
  5. Read MegaAgent (arXiv:2408.09955) Section 3. The two-layer coordination (intra-group + inter-group admin chat) is explicit. Sketch how you would map this to a message queue with two queue families.

Solutions

SolutionP1 · 40, not 30

40. The last checkpoint is step 1, so the new worker re-runs step 2 from the start and bills again. The run did 30 of work, the checkpoint says 30, and the customer paid 40. The same happened in the run above. A key of (run id, step), checked by the payment service, turns the second charge into a no-op.

SolutionB1 · Retries, re-sampling and snapshots

Duplicate emails. Retries re-run every step after the last checkpoint, including the send. Fix: an idempotency key per (run, step) on the email call, or an outbox table that a separate sender drains exactly once.

Contradictory sections. A resumed run calls the model again for the step it was on, gets a different sample, and continues from text that earlier steps or other workers never saw. Concurrent retries without a lease can also interleave two workers on one run. Fix: journal every model and tool output with the step, replay them on resume, and hold a lease per run.

400 GB of checkpoints. Full snapshots of a growing history cost storage roughly quadratic in run length. Fix: store deltas with periodic full snapshots, expire old checkpoints after a run completes, and keep large artifacts out of the state.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designYour multi-agent prototype runs in one process with an in-memory event loop. In production, runs last hours while they wait for human input, worker processes crash and lose everything, peak load is ten times the average, and users are charged per run so a retried side effect is a double charge. Design the layer that goes under the agents, and say what you would build first.

Level 3 of 4 · about 15 minutes to answer well.

Short answer. Put a durable execution layer under the agents: persist the full run state after each step under a run id, so that when a worker crashes its lease expires and any other worker resumes from the last checkpoint. That needs serializable state, a deterministic resume, and idempotent side effects. For the charge, use a deduplication key per run and an outbox so that side effects are written as intent first and executed once, use asynchronous I/O for the model calls, and deploy new versions beside old ones so that in-flight runs are never killed. Build the simplest version first, a web service with a relational database, and adopt a workflow engine when a measured problem demands it.

The resume path.

worker crashes mid-step
  -> lease times out
  -> another worker picks up the run id
  -> resumes from the last checkpoint
  -> no duplicate side effect

Three requirements make this work:

  1. Serializable state. Everything the agent holds must be persistable. A closure with a live database connection does not survive a crash.
  2. Deterministic resume. Given the same state and the same inputs, the agent takes the same actions, or defers to a recorded result for the model calls.
  3. Idempotent side effects. Every external call carries a key, or writes to a table first and is executed by a separate process.

Graph runtimes write a checkpoint after each step under a thread id. Workflow engines write after each activity. Event-sourced runtimes keep a journal. The pattern is the same.

The waiting run.

A run that waits hours for a human must not hold a worker. The runtime persists the run, releases the worker, and any worker resumes when the input arrives. That is what makes the checkpoint the unit of the system rather than the process.

Exactly once, effectively.

At-least-once delivery plus an idempotent consumer is the only kind of exactly-once you get.

Move What it does
Deduplication key per run Included in every side-effect call so a retry is recognized
Outbox Intent is written to a table, and a separate executor performs it and marks it done
Compensating transaction When the effect succeeded and the tracking write failed, schedule the reverse

These are database patterns. The only agent-specific tax is that model calls are slow.

Concurrency.

Model calls are I/O bound, and a thread waiting for the next token is idle 99 percent of the time. At 10,000 concurrent calls, threads reserve about 80 GB of virtual address space for stacks and hundreds of megabytes of resident memory, plus scheduler overhead, while cooperative fibers fit easily in one process. Use asynchronous I/O for the model layer and threads or processes only for CPU-bound work such as embedding.

Deploys.

Long-running stateful agents cannot be hot-swapped. Run several versions of the runtime at once, send a slice of new runs to the new version, and retire the old version when its runs finish.

What to build first.

The lesson's counterpoint is that most teams over-engineer before they measure. A web service and a relational database, with each run as a row, optimistic concurrency on the state, a simple background worker and application-level retries, carries more load than most teams expect; measure where it breaks for your workload. Adopt a durable-execution engine when you hit a concrete problem the simple design cannot solve: hour-long waits at scale, cross-region coordination, or complex compensation policies.

Plausible wrong answers.

  • "Retry the whole run from the start when a worker dies." That repeats every side effect that already happened, which is the double charge in the prompt.
  • "Use a thread per run; it is simpler." Threads idle while they wait for tokens, and at ten thousand concurrent calls the stacks alone exhaust memory.
  • "Adopt a workflow engine on day one to be safe." The simple design carries about a hundred concurrent runs, and the engine's ceremony costs time until a measured problem pays for it.

Follow-ups an interviewer may ask.

  • (level 3) Why is the model call the hard part of deterministic resume? Expected: it is not deterministic, so the resume must replay the recorded result of the call rather than make it again.
  • (level 3) What does the lease do? Expected: it marks a run as owned by one worker for a bounded time, so a crash frees the run for another worker without two workers running it at once.
  • (level 4) How do you test the outbox? Expected: run the same side effect twice through the executor and assert one external call, then crash the executor between the effect and the mark and assert that the compensation or the idempotent redo leaves one effect.
  • (level 4) Which feature of a workflow engine is hardest to replicate by hand, and is that a reason to adopt it? Expected: a reasoned pick such as durable timers for hour-long waits or compensation policies, with the rule that adoption follows a measured failure of the simple design.

Estimate itA swarm runtime uses one thread per in-flight model call. At peak it holds about 10,000 calls at once. Estimate the memory the threads take before any work is done, say what those threads are doing most of the time, and say what you would change.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Each thread reserves a stack (8 MB of virtual memory by default on Linux) and holds tens of kilobytes resident, so 10,000 threads reserve about 80 GB of address space and a few hundred megabytes of RAM before the first token arrives. Those threads are idle about 99 percent of the time, waiting for the next token from a model service. Move the model calls to cooperative fibers through asynchronous I/O, where the same 10,000 calls fit in one process, and keep threads or processes only for CPU-bound work such as embeddings.

The estimate.

Quantity Value
Resident memory per waiting thread (measured in "Use it") about 16 KB, plus 8 MB of reserved virtual stack
Concurrent calls 10,000
Resident memory for the threads about 160 MB, and about 80 GB of reserved address space

That is the cost of holding the calls open, not of doing anything with them. A model call is I/O bound. The thread sends a request and then waits for tokens, and it is idle for about 99 percent of its life.

What fibers change.

Cooperative fibers yield on I/O instead of holding a stack while they wait. In the lesson's demo, 500 concurrent simulated 50 ms calls finish in about 0.055 s with asyncio and about 0.09 s with threads; the bigger difference is memory, about 16 KB resident and 8 MB of reserved stack per waiting thread against a few hundred bytes per asyncio task. At agent scale, asynchronous I/O is the architecture, not an optimization.

The exception.

CPU-bound post-processing wants threads or processes: embedding, tokenizer tricks, anything that computes rather than waits. Separate the I/O layer from the CPU layer and give each its own concurrency model.

How this fits the rest of the runtime.

The asynchronous layer handles the calls in flight. Durability is a separate concern: a checkpoint per step under a run id so that a crash of the process loses the in-flight calls and nothing else, and any worker resumes from the last checkpoint. Peak load at ten times the average is a reason for both: fibers to hold the calls cheaply, and queues with leases to spread them across workers.

Plausible wrong answers.

  • "Add memory until the threads fit." Memory for idle stacks is waste, and the next peak needs more, while fibers remove the cost.
  • "Make the threads smaller with a reduced stack size." A smaller stack is still a stack per idle call, and the idle time stays at 99 percent.
  • "Use fibers for everything, including embeddings." A CPU-bound step on the cooperative loop blocks every waiting call, so the CPU layer keeps threads or processes.

Follow-ups an interviewer may ask.

  • (level 2) Why does the thread count matter more than the request count? Expected: each thread holds a stack whether or not it is doing work, so memory scales with concurrency, not with throughput.
  • (level 2) What breaks if you run the embedding step on the asynchronous loop? Expected: a CPU-bound task blocks the loop, so every waiting call stalls behind it, which is why CPU work goes to threads or processes.
  • (level 3) The memory fits after the change. What is the next limit? Expected: the model service's rate limits and the queue depth, so the runtime needs back-pressure and a lease per run rather than more concurrency.
  • (level 3) How do you prove the change before you ship it? Expected: run the lesson's comparison on your own call shape, measure wall-clock and peak memory for both versions at the same concurrency, and keep the numbers next to the decision.
