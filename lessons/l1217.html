Why this came about

Large companies ended up with many agents built by many teams, each reinventing identity, tools and evaluation. Internal agent platforms and registries emerged to provide those once, and to govern how agents call each other.

In plain words first
From one agent to an agent platform

When many teams build many agents, shared needs appear: a registry of agents and tools, common identity and permissions, gateways, evaluation and observability, and rules for how agents call each other. A platform provides these once so each team does not rebuild them, and multi-agent systems at scale depend on it to stay understandable and safe.

One agent in production is a product. Fifty agents across a company are a distributed system and an organizational problem. This lesson covers both: how systems of agents fail and how to make them hold together, and the shared platform that lets many teams ship agents without each team relearning every lesson in this part.

Why multi-agent systems fail

Researchers at UC Berkeley studied the traces of popular multi-agent frameworks and published MAST, the Multi-Agent System Failure Taxonomy, with 14 failure modes in three groups (Cemri et al., "Why Do Multi-Agent LLM Systems Fail?"; code and annotated traces). Their central finding is that most failures come from system design and coordination, not from the underlying model being too weak.

Group Failure modes The design answer
Specification issues Disobeying the task specification; disobeying the role specification; step repetition; loss of conversation history; being unaware of termination conditions Precise specs per agent (Lesson 14.106); explicit stop conditions and step budgets (Lesson 14.13); state outside the conversation
Inter-agent misalignment Conversation reset; failing to ask for clarification; task derailment; information withholding; ignoring another agent's input; a mismatch between reasoning and action Structured handoffs with contracts (below); one owner of the plan; clarification as an explicit tool
Task verification Premature termination; no or incomplete verification; incorrect verification Independent verifiers with their own criteria; outcome checks in code (Lesson 14.116)

Read the first column as a checklist for design reviews: for each mode, where in your system is it prevented or detected?

Tip
Fewer agents first

Before splitting work across agents, check that one agent with good tools and a good harness cannot do it (Lesson 14.12). Multi-agent systems earn their cost when work truly parallelizes (research across many sources), when roles need different permissions or models, or when an independent verifier is worth its price. They cost more tokens, more latency and more ways to fail.

Coordination patterns

Pattern How it works Good for Watch for
Orchestrator and workers One agent plans and delegates; workers return structured results; the orchestrator decides Research, complex tasks with separable parts The orchestrator becomes a bottleneck and a single point of failure
Pipeline Fixed stages, each an agent or code, passing typed outputs Document processing, content workflows Errors propagate silently between stages unless every handoff is checked
Maker and checker One agent produces, an independent one verifies against criteria Code, analysis, anything with checkable outputs Checkers that share the maker's blind spots; give them different context or models
Choreography Agents react to events on a bus, with no central plan Loosely coupled teams' agents, long-running business processes Untraceable decisions; needs strong event contracts and tracing across agents

Hands-on · Handoffs as contracts

Most multi-agent bugs are silent handoff failures: one agent passes along a vague, untyped or stale result and the next one builds on it confidently. Treat every handoff like an API: a schema, required provenance and a freshness limit, checked in code before the next agent sees it.

from datetime import datetime, timedelta

NOW = datetime(2026, 11, 3, 10, 0)
# A contract for what the research agent must hand to the writer agent.
CONTRACT = {"fields": {"claim": str, "value": float, "unit": str, "source": str, "as_of": datetime},
            "max_age": timedelta(days=7)}

def check_handoff(msg, contract=CONTRACT):
    problems = []
    for name, typ in contract["fields"].items():
        if name not in msg or msg[name] in (None, ""):
            problems.append(f"missing {name}")
        elif not isinstance(msg[name], typ):
            problems.append(f"{name} should be {typ.__name__}")
    if isinstance(msg.get("as_of"), datetime) and NOW - msg["as_of"] > contract["max_age"]:
        problems.append(f"stale: as of {msg['as_of']:%d %b}, older than {contract['max_age'].days} days")
    return problems

handoffs = [
    {"claim": "Q3 revenue", "value": 412.5, "unit": "INR crore", "source": "erp.finance.q3_close", "as_of": NOW - timedelta(days=1)},
    {"claim": "Q3 churn", "value": "about 4%", "unit": "%", "source": "", "as_of": NOW - timedelta(days=2)},
    {"claim": "active stores", "value": 1840.0, "unit": "stores", "source": "crm.accounts", "as_of": NOW - timedelta(days=40)},
]
for h in handoffs:
    p = check_handoff(h)
    print(f"{h['claim']:14} {'ACCEPT' if not p else 'REJECT: ' + '; '.join(p)}")
What you should see
Q3 revenue     ACCEPT
Q3 churn       REJECT: value should be float; missing source
active stores  REJECT: stale: as of 24 Sep, older than 7 days

The second result is a string where a number should be and has no source, so the writer agent would have quoted "about 4%" with nothing behind it. The third is real but forty days old. Rejected handoffs go back to the producing agent with the reason, which is cheaper than finding the error in a report the CFO has already read. Contracts also make multi-agent traces readable, because every hop has a known shape.

From the field
Multi-agent systems that ship

Factory's Luke Alvoeiro describes the architecture behind its coding droids: an orchestrator, workers and validators; validation contracts and structured handoffs; adversarial verification; a preference for serial over parallel steps when work interacts; and a model chosen per role (The Multi-Agent Architecture That Actually Ships, 19 min). Databricks' Sandipan Bhaumik argues that 50 agents are a distributed-systems problem, with silent handoff failures, stale data and untraceable decisions as the typical faults, and data contracts plus a deliberate choice between orchestration and choreography as the cure (talk, 26 min).

The paved path: an agent platform

When several teams build agents, each one rebuilds identity, gateways, tracing, evals and approvals, differently and with gaps. A paved path (a platform that makes the safe way the easy way) prevents that:

Hands-on · A registry that blocks unsafe deploys

The registry is where the platform enforces its rules. Each agent declares an owner, a purpose and its tools; the check below blocks deploys that lack the basics and flags tools that do not fit the declared purpose.

REGISTRY = [
    {"agent": "support-copilot", "owner": "cx-platform", "purpose": "customer support",
     "tools": ["get_order", "search_kb", "issue_refund"], "evals": True, "budget": True, "kill_switch": True},
    {"agent": "finance-close-helper", "owner": "fin-eng", "purpose": "month-end reconciliation",
     "tools": ["read_ledger", "propose_journal", "send_email"], "evals": True, "budget": False, "kill_switch": True},
    {"agent": "growth-experiment-7", "owner": None, "purpose": "marketing copy",
     "tools": ["generate_copy", "read_crm", "export_customers"], "evals": False, "budget": False, "kill_switch": False},
]
# Which tools each declared purpose may use: tool access follows purpose, not convenience.
ALLOWED = {"customer support": {"get_order", "search_kb", "issue_refund", "create_ticket"},
           "month-end reconciliation": {"read_ledger", "propose_journal"},
           "marketing copy": {"generate_copy", "read_style_guide"}}

def paved_path_check(a):
    issues = []
    if not a["owner"]: issues.append("no owner on call")
    for k in ["evals", "budget", "kill_switch"]:
        if not a[k]: issues.append(f"no {k.replace('_', ' ')}")
    extra = sorted(set(a["tools"]) - ALLOWED[a["purpose"]])
    if extra: issues.append(f"tools outside purpose: {extra}")
    return issues

for a in REGISTRY:
    issues = paved_path_check(a)
    status = "compliant" if not issues else "BLOCK DEPLOY" if len(issues) > 2 else "fix before next release"
    print(f"{a['agent']:21} {status:23} {'; '.join(issues)}")
What you should see
support-copilot       compliant               
finance-close-helper  fix before next release no budget; tools outside purpose: ['send_email']
growth-experiment-7   BLOCK DEPLOY            no owner on call; no evals; no budget; no kill switch; tools outside purpose: ['export_customers', 'read_crm']

The finance helper can propose journal entries but has also been given email, which its purpose does not need: an exit for data that nobody decided to open (Lesson 15.22). The growth experiment has no owner, no evals and access to customer exports for writing marketing copy: exactly the agent that causes an incident and has nobody to page. Run the check in the deploy pipeline, so compliance is the default rather than a review meeting.

Teams and governance

  • A platform team owns the paved path as a product, with internal users and a roadmap. Its success measure is how fast product teams ship safe agents, not how many requests it approves.
  • Product teams own their agents end to end: spec, evals, on-call and outcomes.
  • Risk tiers set the review. Low-risk agents on the paved path deploy without a meeting; high-risk ones (money, health, legal, customer data at scale) get a design review and a sign-off from the people who own those risks (Lesson 15.25).
  • Shared learning. Postmortems, eval cases and new failure checks go into the shared platform so every team benefits from each incident (Lesson 14.118).
From the field
Paved paths in practice

Credit Karma's platform registers an agent through a portal that provisions identity, memory, traces, evals and secrets; deploys it as a scanned container on Kubernetes; routes tools through a central MCP gateway; and keeps tracking tables for model use, tool calls, cost and eval results (talk, 29 min). LinkedIn's agent platform, built on LangGraph, standardized a Python service framework, asynchronous messaging between agents, layered memory and a central skill registry (How LinkedIn Built Their First AI Agent for Hiring with LangGraph). Uber's GenAI Gateway put every model call behind one door with redaction, metering and logging (Lesson 14.108).

Solutions

SolutionP1 · Why platforms

Duplicated tool integrations and auth, inconsistent security and logging, and no shared evaluation or cost visibility. A platform offers shared tools, identity, gateway, observability and eval infrastructure.

SolutionB1 · Agent sprawl

Hidden dependencies, cascading failures, unclear ownership and runaway costs. Require registered agents with contracts, owners, limits and observability.

SolutionD1 · Fan-out costs

How many agent calls each request triggers, loops between agents, and duplicated context. Add budgets per workflow and trace the fan-out.

SolutionM1 · An agent registry

These fields make each agent discoverable, auditable and operable; tie registration to deployment so unregistered agents cannot run.

Explain the mechanismWhat does an internal agent platform provide?

Worked answer. Shared building blocks: model gateway, tool platform with identity and permissions, memory and retrieval services, observability, evaluation infrastructure, governance (registry, risk tiers) and deployment. Teams build agents on it, focusing on their domain.

A plausible wrong answer. "A framework everyone must use." Platforms provide services; frameworks can vary.

Follow-ups. What would you build first?

Debug a failureTeams avoid the platform and build their own. Why?

Worked answer. It is slower, missing features, or harder to use than going direct. Talk to teams, prioritize their blockers, offer paved paths with good defaults, and measure adoption.

A plausible wrong answer. "Mandate it." Mandates without value create workarounds.

Follow-ups. What would you measure?

Defend a designCentralize agent building in one team or let product teams build?

Worked answer. Product teams build, because they know the domain; a platform team provides shared services and guardrails. A central team building every agent becomes a bottleneck.

A plausible wrong answer. "Centralize for quality." Quality comes from shared standards and evals.

Follow-ups. How would you share learnings across teams?
