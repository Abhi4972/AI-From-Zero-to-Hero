The problem

In plain words first

This lesson puts all the workbench pieces from 14.32 to 14.40 together and asks one question: on a small real app, does the same model do better inside the workbench than with a plain prompt? The workbench run gets a scope contract, an acceptance check it must pass, feedback from each failed run, a gate and a handoff; the prompt-only run edits and says "done". Harnesses and long-running loops are covered in Lessons 14.111 and 14.67 (linked above). The lesson's own main.py scripts both runs; here they run for real with a small model, and the numbers come out messier, and more useful.

A demo on a toy task convinces no one. The case for the workbench is made when a real-feeling task on a real-feeling repo lands in production with fewer failures, fewer reverts, and a packet the next session can use.

This lesson ships that real-feeling repo and runs the same task through both pipelines. The result is a before/after report you can hand to a skeptic.

The idea

Idea 1 · The sample app

A minimal FastAPI-style handler in sample_app/:

  • app.py with /signup (no validation yet).
  • test_app.py with one happy-path test.
  • README.md and scripts/release.sh as forbidden-zone bait.

Idea 2 · The task

Add input validation to /signup: reject passwords shorter than 8 characters, return 422 with a typed error envelope. Add a test that proves the new behavior.

Idea 3 · The two pipelines

Prompt-only:

  1. Read the README.
  2. Read app.py.
  3. Edit files.
  4. Claim done.

Workbench-guided:

  1. Run init script (Lesson 14.35).
  2. Read scope contract (Lesson 14.36).
  3. Read state (Lesson 14.34).
  4. Edit allowed files only.
  5. Run acceptance command via feedback runner (Lesson 14.37).
  6. Run verification gate (Lesson 14.38).
  7. Run reviewer (Lesson 14.39).
  8. Generate handoff (Lesson 14.40).

Idea 4 · The five outcomes measured

Outcome Why it matters
tests_actually_run Most "tests passed" claims are unverifiable
acceptance_met The test that proves the goal must be the test that ran
files_outside_scope Scope creep is the dominant silent failure
handoff_quality The next session pays for or benefits from this
reviewer_total Qualitative judgment on top of the gate

The same idea as a formula

How sure can a few runs make you? With n tasks and k passes, the pass rate is p^​=k/n with standard error

SE=np^​(1−p^​)​​.

When k=0, use the rule of three: the 95% upper bound on the true rate is about 3/n. With n=3 that bound is 1, which tells you nothing.

What is worth claiming. A difference between two pipelines is believable only when it is larger than about 2SEA2​+SEB2​​. Measures that are checked on every run, such as "were the tests run?", "did it write outside scope?" and "did it know it failed?", need no statistics. The run either did it or did not.

Worked example
Vercel's 4 of 5 against 5 of 5
  • Before: p^​=0.8 on n=5, so SE=0.8⋅0.2/5​≈0.18. The 95% range is roughly 45% to 100%.
  • After: 5 of 5. The rule of three gives a lower bound of only about 1−3/5=40%.
  • The success-rate change is inside the noise. The speed and token savings (275 s to 77 s, about 37% fewer tokens) were measured on every query, so they are the stronger evidence.
  • Same reading for this lesson: 0 of 3 against 1 of 3 passes is a hint, not a result. "Tests run 0 of 3 against 3 of 3" is a fact about the pipelines.
Check your mental model
  • ✗ "The scripted report proves the workbench works."
    ✓ main.py hard-codes both outcomes. It shows the report format, not a measurement.
  • ✗ "The workbench makes a weak model succeed."
    ✓ Here it lifted passes only from 0 to 1 of 3. What it guaranteed was that every failure was known.
  • ✗ "Prompt-only always writes outside scope."
    ✓ In these runs it never did. Scope creep is a risk the contract removes, not a certainty.
  • ✗ "Use the workbench for everything."
    ✓ On a trivial task it cost about 6 times the time. Keep the cheap path for tasks a check can verify afterwards.

# The same three tasks on the lesson's sample app, run for real with Qwen2.5-0.5B-Instruct (greedy, CPU) through
# both pipelines. Prompt only: README and app.py in, one call, every file it returns is written, it claims done.
# Workbench: a scope contract (edit only signup, no imports) that the harness enforces, the acceptance check committed
# as a test and run after each attempt with its error fed back (up to 3), a gate, and a handoff packet. The same
# acceptance check scores both. About 3 minutes.
import json, os, pathlib, re, subprocess, sys, tempfile, time, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
from dataclasses import asdict
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import SAMPLE_APP_PY, SAMPLE_TEST_PY, ALLOWED, TaskOutcome
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()
CALLS = {"n": 0}

def chat(prompt, n=320):
    CALLS["n"] += 1
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

TASKS = {
    "short password": ('Reject passwords shorter than 8 characters: return {"status": 422, "error": {"code": '
                       '"password_too_short", "message": "password must be at least 8 characters"}}.',
                       'out = signup("x@y.co", "short")\nassert out["status"] == 422 and out["error"]["code"] == "password_too_short", out\n'
                       'assert signup("a@b.co", "longenough")["status"] == 200\n'),
    "duplicate email": ('Reject an email that already signed up: return {"status": 409, "error": {"code": '
                        '"email_taken", "message": "email already registered"}}.',
                        'assert signup("a@b.co", "longenough")["status"] == 200\n'
                        'out = signup("a@b.co", "longenough")\nassert out["status"] == 409 and out["error"]["code"] == "email_taken", out\n'),
    "invalid email": ('Reject an email without "@": return {"status": 422, "error": {"code": "invalid_email", '
                      '"message": "email must contain @"}}.',
                      'out = signup("nobody", "longenough")\nassert out["status"] == 422 and out["error"]["code"] == "invalid_email", out\n'
                      'assert signup("a@b.co", "longenough")["status"] == 200\n'),
}
FORMAT = ("Reply with every file you change, each as a line `FILE: <path>` followed by the full new file in a "
          "```python block.")

def fresh_repo():
    root = pathlib.Path(tempfile.mkdtemp())
    (root / "sample_app" / "scripts").mkdir(parents=True)
    (root / "sample_app" / "__init__.py").write_text("")
    (root / "sample_app" / "app.py").write_text(SAMPLE_APP_PY)
    (root / "sample_app" / "test_app.py").write_text(SAMPLE_TEST_PY)
    (root / "README.md").write_text("# sample app\n\nSignup service. Release with scripts/release.sh.\n")
    (root / "sample_app" / "scripts" / "release.sh").write_text("#!/usr/bin/env bash\necho release\n")
    return root

def parse_files(text):
    files = {}
    for m in re.finditer(r"(?:FILE:\s*`?([\w./-]+)`?\s*\n)?```(?:\w+)?\n(.*?)(?:```|$)", text, re.S):
        path, body = m.group(1), m.group(2)
        if not path:
            path = "sample_app/app.py" if "def signup" in body else "sample_app/test_app.py" if "def test" in body else None
        if path:
            path = path if path.startswith("sample_app/") or path == "README.md" else f"sample_app/{path}"
            files[path] = body.rstrip() + "\n"
    return files

def run_py(root, code):
    (root / "_check.py").write_text("from sample_app.app import signup\n" + code)
    p = subprocess.run([sys.executable, "_check.py"], cwd=root, capture_output=True, text=True, timeout=30)
    (root / "_check.py").unlink()
    return p.returncode, (p.stderr.strip().splitlines() or [""])[-1]

def happy_test_passes(root):
    p = subprocess.run([sys.executable, "-c", "import sample_app.test_app as t; [getattr(t, f)() for f in dir(t) if f.startswith('test_')]"],
                       cwd=root, capture_output=True, text=True, timeout=30)
    return p.returncode == 0

def score(pipeline, root, touched, tests_run, handoff):
    accept_rc, accept_err = run_py(root, TASKS[CURRENT][1])
    new_test = "422" in (root / "sample_app/test_app.py").read_text() or "409" in (root / "sample_app/test_app.py").read_text()
    out_of_scope = [p for p in touched if p not in ALLOWED]
    rubric = 4 * (accept_rc == 0) + 2 * happy_test_passes(root) + 2 * new_test + 2 * (not out_of_scope)
    return TaskOutcome(pipeline, tests_run, accept_rc == 0, out_of_scope, handoff, rubric), accept_err

def prompt_only(task):
    root = fresh_repo()
    text = chat(f"Repository README:\n{(root / 'README.md').read_text()}\nsample_app/app.py:\n```python\n{SAMPLE_APP_PY}```\n"
                f"Task: {task}\nAlso add a test for it. {FORMAT}")
    files = parse_files(text)
    for path, body in files.items():
        (root / path).parent.mkdir(parents=True, exist_ok=True); (root / path).write_text(body)
    return score("prompt-only", root, list(files), False, "missing")

def splice_signup(app_text, fn):
    head = app_text.split("def signup", 1)[0]
    return head + fn.strip() + "\n"

def workbench(task, region="signup"):
    root = fresh_repo()
    accept = TASKS[CURRENT][1]
    # the spec's acceptance check is committed as a test, so the next session runs the same command
    (root / "sample_app/test_app.py").write_text(SAMPLE_TEST_PY + "\n\ndef test_acceptance():\n" +
                                                  "".join(f"    {l}\n" for l in accept.splitlines()))
    if region == "signup":
        contract = ("Scope contract: edit only the function signup in sample_app/app.py. USERS is a module-level dict "
                    "that already exists; keep using it. Standard library only. ")
        shown = "def signup" + (root / "sample_app/app.py").read_text().split("def signup", 1)[1]
        ask = "Return only the new signup function in a ```python block."
    else:
        contract = "Scope contract: edit only sample_app/app.py; keep USERS and signup unchanged. Standard library only. "
        shown = (root / "sample_app/app.py").read_text()
        ask = "Return the full new sample_app/app.py in a ```python block."
    feedback, refused, extra = [], [], ""
    for attempt in range(3):
        text = chat(f"{contract}\n```python\n{shown}```\nTask: {task}\n{extra}{ask}")
        m = re.search(r"```(?:python)?\n(.*?)(?:```|$)", text, re.S)
        code = m.group(1) if m else ""
        mods = re.findall(r"^\s*(?:import|from)\s+(\w+)", code, re.M)
        bad = [m for m in mods if m not in sys.stdlib_module_names]
        if bad or (region == "signup" and "def signup" not in code):
            refused.append(f"attempt {attempt + 1}: " + (f"imports {bad[0]}" if bad else "no signup function"))
            rc, err = 1, "refused by the scope contract: " + (f"{bad[0]} is not in the standard library" if bad else "return the signup function")
        else:
            app = root / "sample_app/app.py"
            app.write_text(splice_signup(app.read_text(), code) if region == "signup" else code.rstrip() + "\n")
            shown = code if region == "signup" else app.read_text()
            rc, err = run_py(root, accept)
        feedback.append({"attempt": attempt + 1, "command": "acceptance", "exit_code": rc, "stderr": err})
        if rc == 0 and happy_test_passes(root):
            break
        extra = f"Your last version failed: {err}\n"
        if err.split(":")[0].endswith("Error") and not err.startswith(("AssertionError", "refused")):
            extra += "signup raised an exception; the task says to return the error dict instead of raising. "
        extra += "Fix it. "
    gate = feedback[-1]["exit_code"] == 0 and happy_test_passes(root)
    handoff = {"task": CURRENT, "gate_passed": gate, "feedback": feedback, "refused": refused,
               "next_action": "none" if gate else f"fix: {feedback[-1]['stderr']}"}
    (root / "handoff.json").write_text(json.dumps(handoff, indent=2))
    outcome, err = score("workbench", root, ["sample_app/app.py", "sample_app/test_app.py"], True, "full packet")
    return outcome, err, len(feedback), refused, handoff

RESULTS = {}
print(f"{'task':<16} {'pipeline':<12} {'tests run':<10} {'accepted':<9} {'out of scope':<34} {'rubric':<7} detail")
for CURRENT, (task, _) in TASKS.items():
    t0 = time.time(); po, po_err = prompt_only(task); t_po = time.time() - t0
    t0 = time.time(); wb, wb_err, attempts, refused, _ = workbench(task); t_wb = time.time() - t0
    RESULTS[CURRENT] = {"prompt_only": asdict(po), "workbench": asdict(wb), "attempts": attempts, "refused": refused,
                        "seconds": (round(t_po), round(t_wb))}
    for o, err, det in ((po, po_err, f"{t_po:.0f}s"), (wb, wb_err, f"{attempts} attempt(s), {t_wb:.0f}s, refused: {', '.join(refused) or 'nothing'}")):
        print(f"{CURRENT:<16} {o.pipeline:<12} {o.tests_actually_run!s:<10} {o.acceptance_met!s:<9} "
              f"{str(o.files_outside_scope):<34} {o.reviewer_total:<7} {det}")
        if not o.acceptance_met:
            print(f"{'':<29}acceptance error: {err[:70]}")

Reading this output

Prompt-only fails all three, and nobody knows. Each time the model raises a ValueError instead of returning the error envelope the task asked for. The pipeline never runs a test, so it reports "done" three times. It never touched the README or the release script, so the scope creep in the lesson's script did not happen here.

The workbench passes one of three, and knows about the other two. duplicate email passes on its third attempt. The other two still raise ValueError after three rounds of feedback. The 0.5B model cannot use the hint, but the gate fails and the handoff records the exact error. The harness also refused two attempts that returned no signup function.

The rubric needs care. Both pipelines get 2 points for a new test. The workbench earns those because the harness committed the acceptance check, not because the model wrote a test. Read the five outcomes, not the total.

Reading this output

The trivial task fails in both pipelines. Prompt-only takes one call and 4 seconds and writes 'Sign up handler.' instead of 'Signup handler.', then claims done. The workbench takes three calls and about 23 seconds. Each attempt drops the signup function, so its packet ends with an ImportError and a next action instead of a false "done".

That is the honest false negative. On a task a cheap check can verify afterwards, the full loop costs about 6 times the time. A better cheap path is prompt-only plus one acceptance run.

Scripted against measured. The script says the workbench meets acceptance and scores 9 against 3. Measured, only "tests run, 0 against 3" matches it exactly. Acceptance is 0 against 1, scope creep is 0 for both, and the rubric averages are close (4.0 against 5.3). The structural outcomes held up. The success numbers did not.

"""Run the same task on a sample app twice: prompt-only vs workbench-guided.

Both pipelines are scripted (no LLM) so the measurement is reproducible.
Writes before-after-report.md and comparison.json next to this file.

Run: python3 code/main.py
"""

from __future__ import annotations

import json
from dataclasses import asdict, dataclass, field
from pathlib import Path

HERE = Path(__file__).parent
SAMPLE = HERE / "sample_app"


SAMPLE_APP_PY = '''"""Minimal signup handler. Treat as production-ish for this exercise."""

USERS: dict[str, str] = {}


def signup(email: str, password: str) -> dict[str, object]:
    USERS[email] = password
    return {"status": 200, "email": email}
'''

SAMPLE_TEST_PY = '''from sample_app.app import signup


def test_signup_happy_path():
    out = signup("a@b.co", "longenough")
    assert out["status"] == 200
'''


@dataclass
class TaskOutcome:
    pipeline: str
    tests_actually_run: bool
    acceptance_met: bool
    files_outside_scope: list[str] = field(default_factory=list)
    handoff_quality: str = "missing"
    reviewer_total: int = 0


ALLOWED = {"sample_app/app.py", "sample_app/test_app.py"}
FORBIDDEN = {"sample_app/scripts/release.sh"}


def run_prompt_only() -> TaskOutcome:
    """Edits a couple of files, never runs the test, claims done."""
    touched = ["sample_app/app.py", "README.md", "sample_app/scripts/release.sh"]
    return TaskOutcome(
        pipeline="prompt-only",
        tests_actually_run=False,
        acceptance_met=False,
        files_outside_scope=[p for p in touched if p not in ALLOWED],
        handoff_quality="missing",
        reviewer_total=3,
    )


def run_workbench() -> TaskOutcome:
    """Reads scope, edits inside scope, runs acceptance through feedback, gates, reviews, hands off."""
    touched = ["sample_app/app.py", "sample_app/test_app.py"]
    return TaskOutcome(
        pipeline="workbench-guided",
        tests_actually_run=True,
        acceptance_met=True,
        files_outside_scope=[p for p in touched if p not in ALLOWED],
        handoff_quality="full packet",
        reviewer_total=9,
    )

def write_report(po: TaskOutcome, wb: TaskOutcome) -> None:
    lines = [
        "# Before / After: Agent Workbench on a Real Repo",
        "",
        "Same task. Same sample app. Two pipelines.",
        "",
        "| Outcome | Prompt only | Workbench |",
        "|---------|-------------|-----------|",
        f"| tests_actually_run | {po.tests_actually_run} | {wb.tests_actually_run} |",
        f"| acceptance_met | {po.acceptance_met} | {wb.acceptance_met} |",
        f"| files_outside_scope | {len(po.files_outside_scope)} | {len(wb.files_outside_scope)} |",
        f"| handoff_quality | {po.handoff_quality} | {wb.handoff_quality} |",
        f"| reviewer_total (/10) | {po.reviewer_total} | {wb.reviewer_total} |",
        "",
        "## Read",
        "",
        "Prompt only writes outside scope, claims done without running the acceptance command, "
        "leaves no handoff, and scores low on review. Workbench keeps writes in scope, runs the "
        "acceptance command through the feedback runner, passes the verification gate, and ships "
        "a handoff packet the next session loads on startup.",
    ]
    (HERE / "before-after-report.md").write_text("\n".join(lines) + "\n")


def write_sample() -> None:
    SAMPLE.mkdir(exist_ok=True)
    (SAMPLE / "app.py").write_text(SAMPLE_APP_PY)
    (SAMPLE / "test_app.py").write_text(SAMPLE_TEST_PY)
    (SAMPLE / "README.md").write_text("# sample app\n\nForbidden zone for agent tasks.\n")
    (SAMPLE / "scripts").mkdir(exist_ok=True)
    (SAMPLE / "scripts" / "release.sh").write_text("#!/usr/bin/env bash\necho release\n")


def main() -> None:
    write_sample()
    po = run_prompt_only()
    wb = run_workbench()

    for outcome in (po, wb):
        print(f"=== {outcome.pipeline} ===")
        for k, v in asdict(outcome).items():
            print(f"  {k}: {v}")
        print()

    write_report(po, wb)
    (HERE / "comparison.json").write_text(
        json.dumps({"prompt_only": asdict(po), "workbench": asdict(wb)}, indent=2) + "\n"
    )

Production patterns in the wild

The skeptic's question is "how much does the workbench actually help?" The 2026 numbers say a lot more than the explanation.

Terminal Bench Top-30 to Top-5 on the same model. On Terminal Bench 2.0, harness changes alone took LangChain's deepagents-cli from 52.8% (just outside the top 30) to 66.5% (top 5) with the same model, GPT-5.2-Codex (LangChain, Improving Deep Agents with harness engineering, February 2026). Same model. Different surfaces.

Vercel 80% to 100% by deleting tools. Vercel replaced most of its text-to-SQL agent d0's specialised tools with file access and bash; on 5 benchmark queries success went from 4/5 to 5/5, average time from 275 s to 77 s and tokens down about 37% (December 2025). Smaller tool surface, sharper scope, fewer ways to fail. Negative space wins.

Harvey 2x accuracy via harness alone. Legal agents more than doubled their accuracy through harness optimization, no model change.

88% of enterprise AI agent projects fail to reach production. The preprints.org Harness Engineering for Language Agents paper (March 2026) traces the failures to runtime, not reasoning: stale state, brittle retries, overgrown context, poor recovery from intermediate mistakes.

Long-context collapse. WebAgent baseline 40-50% success drops to under 10% in long-context conditions, mostly from infinite loops and goal loss. The Ralph Loop and the handoff packet exist to absorb that.

False negatives still exist. Single-step factual tasks, one-line lints, formatter runs, anything the model has memorized verbatim — these run faster prompt-only. The benchmark should enumerate them honestly so the workbench is not framed as overkill.

The takeaway is not "harness wins forever." Models do absorb harness tricks over time. The takeaway is that today, the engineering load sits in the seven surfaces, and the numbers prove it.

Industry practice
What's current (2024–2026)
  • Harness A/B on public benchmarks is how teams argue for their workbench. LangChain kept GPT-5.2-Codex fixed and changed only the harness, taking deepagents-cli from 52.8% to 66.5% on Terminal Bench 2.0.
  • Fewer, sharper surfaces. Vercel's d0 text-to-SQL agent swapped most of its tools for file access and bash. On 5 queries it ran 3.5 times faster with about 37% fewer tokens.
  • Workbenches in CI at scale. Cloudflare's code review runs up to seven specialised reviewers plus a coordinator inside CI, sized by risk tier. In its first 30 days it did 131,246 review runs over 48,095 merge requests, at an average of $1.19 per review.
  • On your laptop: this A/B runs on CPU in about 4 minutes with the 0.5B model. A 7B coding model in 4-bit quantization (about 4 to 5 GB) should fit the RTX 4060's 8 GB through llama.cpp or Ollama, and is the next step for more passes. Expect noisy rates either way: report the per-run facts.

Sources: LangChain, Improving Deep Agents with harness engineering, Vercel, We removed 80% of our agent's tools, Cloudflare, Orchestrating AI Code Review at scale.

Recap
What to keep from this lesson
  • Run the same tasks through both pipelines, and score both with the same acceptance check.
  • Per-run facts (tests run, scope kept, failure known) beat pass rates from a handful of tasks.
  • A scripted comparison shows the report shape. It measures nothing.
  • The workbench's main gift to a weak model is knowing when it failed.
  • List the false negatives honestly: trivial tasks pay the overhead.

RMCheat sheet · Agent workbench habits at a glance

Ship it

outputs/skill-workbench-benchmark.md is a portable evaluation harness that runs any agent product through both pipelines against a project's own sample app and reports the five outcomes.

outputs/skill-workbench-benchmark.md

---
name: workbench-benchmark
description: Run the same task through prompt-only and workbench-guided pipelines on a project's own sample app and emit a five-outcome before/after report.
version: 1.0.0
phase: 14
lesson: 41
tags: [benchmark, before-after, evaluation, workbench, sample-app]
---

Given a repo, an agent product, and a small sample app, produce a portable evaluation harness that compares prompt-only against workbench-guided pipelines.

Produce:

1. `eval/sample_app/` — a minimum-viable sample app drawn from the project's domain.
2. `eval/run_prompt_only.py` and `eval/run_workbench.py` that each take a task description and return a `TaskOutcome`.
3. `eval/report.py` that runs both pipelines and writes `before-after-report.md` plus `comparison.json`.
4. CI workflow that fails when workbench outcomes regress on a fixed task suite.
5. `docs/benchmark.md` explaining the five outcomes and what counts as a regression.

Hard rejects:

- A benchmark with only one pipeline. Comparison is the whole point.
- Outcomes phrased as percentages without a denominator. Always report `n / m`.
- A sample app the agent product was trained on. Use a domain-tuned fixture.
- Reports that hide false negatives. Tasks where prompt-only was faster must be enumerated.

Refusal rules:

- If the project has no acceptance command, refuse to ship the benchmark. There is nothing to measure.
- If the workbench pipeline takes more than 3x the prompt-only pipeline on the median task, surface that finding; the workbench needs simplification, not the model.
- If the harness cannot run offline, refuse to wire it into CI. Network flakiness will corrupt the comparison.

Output structure:

```
<repo>/
├── eval/
│   ├── sample_app/
│   ├── run_prompt_only.py
│   ├── run_workbench.py
│   └── report.py
├── outputs/eval/
│   ├── before-after-report.md
│   └── comparison.json
├── docs/benchmark.md
└── .github/workflows/benchmark.yml
```

Solutions

SolutionP1 · Few passes, and no scope creep

Very few. Prompt-only passed none: it raised a ValueError each time and never found out. The workbench passed one of three (duplicate email, on its third attempt). Neither pipeline wrote outside scope: prompt-only had no reason to touch the README or the release script, and the workbench refused only attempts that left out signup. With three tasks, 0 against 1 is not a measured difference. "Tests run 0 of 3 against 3 of 3" and "failure known 0 of 3 against 3 of 3" are.

SolutionB1 · Hard-coded numbers are not a benchmark

Those numbers come from code/main.py, which hard-codes both outcomes, so the slide measures nothing. Run on the next model, it would print the same 9 and 3. "Out-of-scope writes 2" is also what the script asserts, not what a model did. In the real runs here, neither pipeline wrote outside scope.

Instead, the benchmark runs real tasks from your repo through both pipelines with the model under test. It scores both with the same acceptance check, and reports the per-run facts (tests run, acceptance met, files outside scope, failure known, time and calls) with n and a confidence range for any rate. It also lists the false negatives, the tasks where prompt-only plus one check was enough. Rerun it whenever the model or the harness changes.
