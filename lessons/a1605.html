In plain words first
The idea in one line

One lead agent plans and delegates; specialized workers execute in parallel contexts and report back. This is the pattern behind Anthropic's Research system (Claude Opus 4 as lead, Sonnet 4 as subagents), measured at +90.2% over single-agent Opus 4 on internal research evals. Anthropic's engineering post reports that 80% of the variance on BrowseComp is explained by token usage alone — multi-agent wins largely because each subagent gets a fresh context window. This lesson builds the supervisor pattern from the primitives and covers the 2026 engineering lessons from production deployments.

Terms you'll hear
Term What people say What it actually means
Supervisor "Lead agent" An orchestrator agent that plans, delegates, and synthesizes. Does not do the work itself.
Worker "Subagent" A focused agent invoked by the supervisor with narrow scope and its own context window.
Orchestrator-worker "Supervisor pattern" Same thing, different name. The 2026 literature uses both.
Fresh context "Clean window" A worker's context starts from its system prompt and assigned question, not the lead's history.
Rainbow deployment "Gradual rollout" Long-running stateful agents need versioned drain-and-replace, not blue-green.

Problem

In plain words first

In the supervisor (or orchestrator-worker) pattern, a lead agent splits a job into parts, hands each part to a worker with a fresh context, often in parallel, and then combines the results. It is how Anthropic's Research feature works. Multi-agent systems and LangGraph subgraphs are covered in Lessons 14.66 and 14.107 (linked above). This lesson breaks the lesson's lead with a failing and a slow worker, then times real model calls run in parallel on a CPU.

Research is the prototypical task that single-agent systems fail. You ask "what changed in multi-agent systems between 2023 and 2026?" A single agent reads five papers sequentially, fills half its context with their text, and then has to reason about all of them together. It forgets the first paper by the time it reaches the fifth. It cannot parallelize.

The supervisor pattern fixes this: one lead agent plans the search, delegates each sub-question to a worker, and synthesizes. Each worker gets its own 200k-token window for a narrow question. The lead never sees the raw papers — only the worker summaries.

Anthropic's production Research system reports +90.2% on internal research evals vs a single Opus 4. The same post notes that 80% of the BrowseComp variance is explained by token usage alone. Fresh context per subagent is the main mechanism.

Concept

The pattern

                 ┌──────────────┐
                 │   Lead       │  plans, decomposes,
                 │  (Opus 4)    │  synthesizes
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ Worker1 │  │ Worker2 │  │ Worker3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         fresh       fresh        fresh
         context     context      context

The lead never reads the raw materials. The workers never see each other's work until the lead synthesizes. Each arrow is a handoff with a narrow artifact.

Why it wins

Three mechanisms:

  1. Fresh context per subagent. A worker exploring "FIPA-ACL heritage" does not carry the 40k tokens the lead spent planning. It gets a 200k window for one question.
  2. Specialization via prompt. The lead's prompt is "decompose and synthesize," not "research." Each worker's prompt is narrow: "find what changed in X." Focused prompts produce focused outputs.
  3. Parallelism. Workers run concurrently. Wall-clock time is roughly max(worker_times) + plan + synthesis, not sum(worker_times).

Engineering lessons (Anthropic 2025)

The Anthropic post lists several production lessons that are still 2026-relevant:

  • Scale effort to query complexity. Simple queries: one agent, 3-10 tool calls. Complex queries: 10+ agents. The lead must estimate this, not the caller.
  • Broad then narrow. Decompose into broad sub-questions first, then spawn more workers per sub-question if the answer warrants depth.
  • Rainbow deployments. Agents are long-running and stateful. Traditional blue-green does not work. Anthropic uses rainbow: gradual rollout of new versions while old ones drain.
  • Token usage dominates. Anthropic reports agents using about 4× the tokens of a chat and multi-agent systems about 15×, so a multi-agent run costs roughly 4× a single agent. Only run it when the task value justifies the cost.

The graph-native turn

LangGraph originally shipped a langgraph-supervisor library with a high-level create_supervisor helper. In 2025 LangChain moved the recommendation to implementing the supervisor pattern via tool-calling directly, because tool calls give more control over what the supervisor sees (context engineering). The library still works; the docs now recommend the tool-calling form.

The failure modes

  • Lead hallucinates the plan. If the lead generates sub-questions that do not decompose the real question, workers do precise research on the wrong target.
  • Workers over-explore. Without explicit scope boundaries, workers drift beyond their assigned sub-question and pollute the synthesis step.
  • Synthesis conflicts. Two workers return contradictory facts. The lead must either re-ask (add a round) or note the disagreement explicitly. Silent picking of one side is the worst failure: the user never knows disagreement happened.

When supervisor is wrong

  • Sequential tasks. If step 2 literally needs step 1's output, parallelism buys nothing. Use a pipeline (CrewAI Sequential, LangGraph linear graph).
  • Simple queries. Single-agent handles them faster and cheaper. Use the lead's "scale effort" check before spawning workers.
  • Strict determinism. Supervisor uses LLM-selected delegation. Static graphs are better when audit/replay matter more than adaptability.

The same idea as a formula

Wall clock. With n workers taking times t1​,…,tn​, sequential runs take ∑i​ti​ and parallel runs take maxi​ti​ plus planning and synthesis. The speed-up is

maxi​ti​∑i​ti​​≤n,
reached only when workers take equal time and do not compete for anything. One slow worker sets the pace for all of them.

Shared hardware. If workers wait on the network, they overlap. If they run on the same c CPU cores, each gets about c/n of them, and the speed-up falls toward 1.

A deadline turns waiting into a decision. With deadline D, the lead synthesises from {i:ti​≤D} and must say which parts are missing.

Worked example
Timing one plan
  • Three workers take 0.3 s, 1.5 s and fail at once. Sequentially that would be about 1.8 s.
  • In parallel, the lesson's lead waits for the slowest: 1.5 s. It drops the failed part silently, so the answer has 2 sections.
  • With a 0.6 s deadline, the careful lead returns at 0.6 s with one section, and two lines saying which parts are missing and why.
  • On a 2-thread CPU, three real model calls take 6.8 s one after another and 6.1 s in parallel: a 1.12× speed-up, not 3×.
Check your mental model
  • ✗ "Parallel workers make the run n times faster."
    ✓ Only if they wait on the network or run on separate hardware. On one CPU the speed-up was 1.12×.
  • ✗ "If a worker fails, the answer just has less in it."
    ✓ The lesson's lead drops it with no note, so the reader cannot tell a section is missing.
  • ✗ "Multi-agent costs about 15× a single agent."
    ✓ Anthropic's 15× is against a chat; against a single agent it is about 4×.
  • ✗ "The lead can wait for every worker."
    ✓ Without a deadline, one slow worker sets the wall clock for the whole run.

class CarefulLead(Lead):
    def run(self, query, timeout=0.6):
        t0 = time.time()
        subs = self.plan(query)
        results, errors = [None] * len(subs), {}
        def work(i, sq):
            try:
                results[i] = WorkerResult(sq, main.fake_web_fetch(sq), 800, 0.0)
            except Exception as e:
                errors[i] = f"{type(e).__name__}: {e}"
        threads = [threading.Thread(target=work, args=(i, sq), daemon=True) for i, sq in enumerate(subs)]
        for th in threads: th.start()
        deadline = t0 + timeout
        for th in threads: th.join(max(0.0, deadline - time.time()))
        lines = []
        for i, sq in enumerate(subs):
            topic = sq.split(" -- ")[1]
            if results[i]: lines.append(f"   - {topic}: ok")
            elif i in errors: lines.append(f"   - {topic}: MISSING ({errors[i]})")
            else: lines.append(f"   - {topic}: MISSING (no result within {timeout} s)")
        return lines, round(time.time() - t0, 2)
lines, wall = CarefulLead(Trace()).run("What changed in multi-agent systems 2023 to 2026?")
print(f"\n2. a lead with a 0.6 s deadline that reports gaps: wall clock {wall} s")
print("\n".join(lines))

Reading this output

Three parallel calls were barely faster. On this machine's 2 CPU threads, three model calls took 6.8 s one after another and 6.1 s in three threads, a 1.12× speed-up against the ideal 3×. Each call uses the same cores, so running them together mostly makes them share.

The answers did not change. Greedy decoding gives the same three answers either way, which is a useful check that parallelism did not alter results.

The lesson's speed-up comes from waiting. Its workers sleep 0.3 s to stand in for a web fetch, and waiting overlaps perfectly. Real workers that call a hosted API overlap the same way; workers that share one local CPU do not.

Build it

code/main.py implements a supervisor of three parallel workers using threading. The lead decomposes a query into sub-questions, workers run concurrently on each sub-question, and the lead synthesizes. No real LLMs — the workers are scripted to simulate fetch-and-summarize.

Key structure:

  • Lead.plan(query) splits a query into 3 sub-questions.
  • Worker.run(sub_q) returns a fake summary (could be any tool-using agent in production).
  • Lead.run(query) kicks off workers in threads, joins, and synthesizes.

Run:

Part 1 of 3 · WorkerResult, TraceEntry, Trace, fake_web_fetch, Worker

"""Supervisor / Orchestrator-Worker pattern (Anthropic Research style).

Lead agent decomposes a query, spawns workers in parallel threads, synthesizes.
No real LLM calls -- workers are scripted fetch-and-summarize simulations.

The point is the wall-clock win from parallel subagents, plus the pattern.
"""
from __future__ import annotations

import threading
import time
from dataclasses import dataclass, field


@dataclass
class WorkerResult:
    sub_question: str
    summary: str
    tokens_spent: int
    wall_time: float


@dataclass
class TraceEntry:
    worker_id: int
    event: str
    t: float
    sub_question: str = ""


@dataclass
class Trace:
    entries: list[TraceEntry] = field(default_factory=list)
    _lock: threading.Lock = field(default_factory=threading.Lock)

    def log(self, worker_id: int, event: str, sub_question: str = "") -> None:
        with self._lock:
            self.entries.append(
                TraceEntry(worker_id=worker_id, event=event, t=time.time(), sub_question=sub_question)
            )


def fake_web_fetch(query: str) -> str:
    """Simulate web fetch + summarization latency."""
    time.sleep(0.3)
    return f"Summary for '{query}': 3 key findings from 5 sources."


class Worker:
    def __init__(self, worker_id: int, trace: Trace) -> None:
        self.worker_id = worker_id
        self.trace = trace

    def run(self, sub_question: str, results: list[WorkerResult | None], idx: int) -> None:
        start = time.time()
        self.trace.log(self.worker_id, "start", sub_question)
        summary = fake_web_fetch(sub_question)
        elapsed = time.time() - start
        results[idx] = WorkerResult(
            sub_question=sub_question,
            summary=summary,
            tokens_spent=800,
            wall_time=elapsed,
        )
        self.trace.log(self.worker_id, "done", sub_question)

Part 2 of 3 · Lead, render_trace

class Lead:
    """Supervisor. Plans, spawns workers in parallel, synthesizes."""

    def __init__(self, trace: Trace) -> None:
        self.trace = trace

    def plan(self, query: str) -> list[str]:
        """Decompose. Real lead uses an LLM; this splits by heuristic."""
        return [
            f"{query} -- historical origins",
            f"{query} -- state of the art 2026",
            f"{query} -- open problems",
        ]

    def synthesize(self, query: str, results: list[WorkerResult]) -> str:
        ok = [r for r in results if r is not None]
        parts = [f"- {r.sub_question}: {r.summary}" for r in ok]
        return f"Answer to '{query}':\n" + "\n".join(parts)

    def run(self, query: str) -> tuple[str, dict]:
        t0 = time.time()
        sub_questions = self.plan(query)
        self.trace.log(worker_id=-1, event="plan", sub_question=str(len(sub_questions)))

        results: list[WorkerResult | None] = [None] * len(sub_questions)
        threads: list[threading.Thread] = []
        for i, sq in enumerate(sub_questions):
            w = Worker(worker_id=i, trace=self.trace)
            th = threading.Thread(target=w.run, args=(sq, results, i))
            threads.append(th)
            th.start()

        for th in threads:
            th.join()

        self.trace.log(worker_id=-1, event="synthesize")
        synthesis = self.synthesize(query, [r for r in results if r is not None])
        total_wall = time.time() - t0
        total_tokens = sum((r.tokens_spent for r in results if r is not None)) + 1200
        return synthesis, {
            "wall_clock_seconds": round(total_wall, 3),
            "total_tokens": total_tokens,
            "worker_count": len(sub_questions),
        }


def render_trace(trace: Trace, t0: float) -> None:
    for e in trace.entries:
        rel = round(e.t - t0, 3)
        sq = f" | {e.sub_question}" if e.sub_question else ""
        tag = "LEAD" if e.worker_id == -1 else f"W{e.worker_id}"
        print(f"  +{rel:>5}s  {tag:>4}  {e.event}{sq}")


def main() -> None:
    print("Supervisor / Orchestrator-Worker demo")
    print("-" * 42)

    trace = Trace()
    t0 = time.time()
    lead = Lead(trace=trace)
    answer, stats = lead.run("What changed in multi-agent systems 2023 to 2026?")

    print("\nTrace (+seconds relative to plan start):")
    render_trace(trace, t0)

    print("\nFinal synthesis:")
    print("  " + answer.replace("\n", "\n  "))

    print("\nStats:")
    for k, v in stats.items():
        print(f"  {k}: {v}")

    print("\nSequential baseline would be ~0.9s (3 * 0.3s).")
    print("Parallel actual is ~0.35s. That's the supervisor win.")

Industry practice
What's current (2024–2026)
  • Anthropic's Research feature is the reference design: an Opus lead with parallel Sonnet subagents, reported at +90.2% over a single agent on an internal eval, with token use explaining about 80% of BrowseComp variance.
  • Supervisors as tool calls. LangChain now recommends building the supervisor from tool calls rather than the older create_supervisor helper; the Claude Agent SDK spawns subagents through its Agent tool, with caps on depth, concurrency and spend.
  • Serving decides the speed-up. Hosted APIs run workers on separate hardware. Local servers such as vLLM and llama.cpp batch concurrent requests on one GPU, which helps much more than threads on a CPU.
  • On your laptop: with an RTX 4060, run workers through a local server that batches requests, rather than loading a model per thread; on CPU, parallel workers mostly wait for each other.

Sources: Anthropic, Multi-agent research system, LangChain, Supervisor via tool calling, Claude Agent SDK, Subagents, vLLM.

Recap
What to keep from this lesson
  • A lead plans, workers run in fresh contexts, and the lead synthesises.
  • Parallel speed-up is capped by the slowest worker and by shared hardware.
  • Give the lead a deadline and make it say which parts are missing and why.
  • Multi-agent costs about 4× a single agent in tokens; use it when the task is worth it.
  • Measure your own speed-up; a CPU shared by every worker gives almost none.

Ship it

Checklist before deploying a supervisor pattern:

  • Model pairing. Lead on a reasoning-tier model (Opus class, o3 class). Workers on a faster, cheaper model (Sonnet, o4-mini).
  • Worker timeout. Any worker that exceeds 2× median runtime gets killed; the lead either re-spawns with narrower scope or proceeds without it.
  • Token cap per worker. Hard limit (say 10× the expected synthesis input) prevents a runaway worker from blowing the budget.
  • Observability. Trace the lead's plan, each worker's tool calls, and the synthesis. This is the basis for any post-hoc debugging.
  • Rainbow rollout. Stateful long-running agents need gradual version transition, not hot swap.

---

Given a user query that benefits from parallel subagent research, produce a supervisor-pattern design ready to wire into any framework (LangGraph, OpenAI Agents SDK, CrewAI Hierarchical).

Produce:

1. **Complexity estimate.** Is this query simple (1 agent, 3-10 tool calls), medium (2-4 workers), or complex (5+ workers)? Justify in one sentence using Anthropic's scale-effort heuristic.
2. **Lead system prompt.** Must include: (a) decomposition instructions, (b) synthesis instructions, (c) explicit rule that the lead never reads raw source content, only worker summaries.
3. **Worker system prompts.** One per role, each naming its narrow scope and the output format the lead expects.
4. **Sub-question decomposition rules.** How does the lead split the query? Broad-first-then-narrow, or direct decomposition? What disqualifies a sub-question (overlap with another, too broad)?
5. **Synthesis template.** Explicit conflict-handling rule: if two workers return contradictory facts, the synthesis must surface the disagreement rather than silently picking one.
6. **Model pairing.** Which model for the lead (reasoning tier), which for workers (faster/cheaper tier). Explain the tradeoff.
7. **Observability requirements.** Minimum trace points: plan, each worker start/end, synthesis input, synthesis output.

Hard rejects:

- Any design where the lead does tool-use itself. Lead only plans and synthesizes.
- Worker prompts that permit scope drift (e.g., "research anything related to X" without a bound).
- Synthesis templates that hide conflicts.

Refusal rules:

- If the query is simple (estimated under 10 tool calls total), refuse the design and recommend single-agent instead. Cite the Anthropic 15× token cost finding.
- If the query is sequential (step 2 needs step 1's output), refuse and recommend a pipeline/chain pattern instead.
- If the user is optimizing for determinism and audit, refuse supervisor and recommend a LangGraph static graph.

Output: one-page design brief. Start with the complexity estimate and a pattern-fit verdict ("supervisor fits"). Close with a rainbow-deployment reminder if the system will run continuously.

Exercises

  1. Run code/main.py, then modify the lead to spawn 5 workers instead of 3. Observe the wall-clock effect. At what worker count does spawn overhead exceed parallel savings in this demo?
  2. Implement a worker timeout: kill any worker that runs longer than 0.5 seconds and have the lead synthesize the remaining results. What observability do you need to know a worker was cut?
  3. Add a conflict-detection step to the lead's synthesis: if two workers return contradictory answers, the lead notes the disagreement rather than picking one. How do you detect contradiction without calling an LLM?

Solutions

SolutionP1 · As slow as the slowest, and one section silently gone

About 1.5 s, the time of the slowest worker, because the lead joins every thread with no timeout. The answer has 2 of the 3 sections: the failed worker's slot stays None and is filtered out, and nothing in the answer says so.

A lead with a deadline returns on time and lists what is missing, with the reason for each.

SolutionB1 · Waiting for every worker

The lead waited for every worker and synthesised whatever came back, so one hung provider set the latency, and failures vanished.

The lead should: - Set a deadline per run and synthesise from what arrived by then. - Report gaps: list each planned part that is missing and why (timed out, failed, empty). - Retry narrowly: re-spawn one failed part with a smaller scope or another provider, if time allows. - Plan fewer workers for simple questions. Eight workers for every question multiplies tokens and the chance that one of them stalls.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Take-homeTake-home. Design a research system in which one lead agent plans and several workers search in parallel, for a product where users ask open questions and expect a cited answer. Deliver a design document with the lead and worker prompts in outline, the shared memory, the failure modes you expect and the mitigation for each, the operational limits, and the cost model. Say what you would cut if the budget were halved.

Level 4 of 4 · about 60 minutes to answer well.

Short answer. The lead decomposes the question into sub-questions, scales the number of workers to the question's complexity, and synthesizes the worker summaries without reading raw sources. Each worker has a fresh context, an explicit scope, a timeout at about twice the median runtime and a token cap. Shared memory carries provenance on every entry, is append-only, and is checked by a read-only verifier that re-fetches sources and reports on its own channel. Every outbound call sits behind a circuit breaker, the system is deployed with versions side by side, and the cost model states up front that the pattern spends about 15 times the tokens of a single agent.

The lead.

  • Prompt outline: decompose, delegate, synthesize, never research directly.
  • Scale effort to the query: a simple question gets one agent and a few tool calls, and a complex one gets more than ten workers. The lead estimates this, not the caller.
  • Decompose broad first, then spawn deeper workers where a sub-answer warrants it.
  • Synthesis with provenance: every claim in the answer names the worker and the source it came from.
  • Conflict handling: when two workers return contradictory facts, re-ask with a narrower question or surface the disagreement, never pick in silence.

The workers.

  • Prompt outline: one sub-question, the sources to prefer, what is out of scope, the output shape.
  • Fresh context per worker, so the lead's planning tokens never enter a worker's window.
  • A timeout at about twice the median worker runtime, after which the lead re-spawns with a narrower scope or proceeds without the result.
  • A hard token cap per worker, on the order of ten times the expected synthesis input, so one runaway worker cannot spend the budget.

Shared memory.

  • Every entry carries the writer, the timestamp, the prompt hash and the source it cites.
  • The log is append-only; a correction supersedes and references the entry it replaces.
  • A read-only verifier re-fetches cited sources, flags mismatches, and writes only to a verification channel that the lead and a human read.
  • Monitor the share of writes that are supersessions as an early sign of a hallucinating writer.

Failure modes and mitigations.

Expected failure Mitigation
The lead decomposes the wrong question Log the decomposition and compare it with the user's question before workers start
Workers over-explore Explicit scope, timeout and token cap
Two workers disagree Detect by canonicalized claims per sub-question; re-ask or surface
Memory poisoning Provenance, append-only, read-only verifier
Retry storm against a search or fetch service Circuit breakers that open at 5 to 10 percent error rate and capped retry budgets
Silent wrong answer A golden set of questions with known answers, run weekly, and sampled human review

Operations.

  • Trace the lead's plan, each worker's tool calls and the synthesis, so that a wrong answer can be traced to a worker and a source.
  • Deploy new versions beside old ones and let long-running questions finish on the version they started on.
  • Run the failure-mode audit each quarter on a sample of about 1000 traces and rank mitigations by failures removed.

Cost model.

State the measured multiplier: the pattern costs about 15 times the tokens of a single agent, and about 80 percent of the quality variance on a browsing benchmark is explained by token usage. Report tokens and wall-clock beside answer quality for every question class.

With half the budget.

Keep the lead's scaling rule and raise the complexity that a question must reach before the lead adds workers, so that more questions go to one agent. Keep provenance and the verifier, because they are cheap and they protect the cited answer. Cut worker count per question before you cut the verifier, and cut debate rounds entirely.

What we grade.

The outlined prompts, the memory schema with provenance fields, the failure table with one mitigation per row, the three operational limits with the reason for each number, and a cost section that shows the multiplier rather than hiding it.

Plausible wrong answers.

  • "Give every worker the full conversation so it has context." That spends the fresh-context advantage and copies the lead's planning into every window.
  • "Let the lead resolve conflicts by picking the better-written answer." A silent pick hides the disagreement from the user, and the design must re-ask or surface it.
  • "Skip the verifier, because the lead already reads the worker summaries." The lead compares summaries with each other, not with the sources, and shared summaries can share a hallucination.

Follow-ups an interviewer may ask.

  • (level 3) Why does the lead never read raw sources, even to check a worker? Expected: its window is for planning and synthesis, and the check belongs to the verifier, which re-fetches the source without writing to the pool.
  • (level 3) A worker returns a summary with no source. What does the design do with it? Expected: provenance marks the entry as uncited, the lead weighs it lower, and the verifier cannot check it, so the answer either omits it or labels it.
  • (level 4) Which one component would you keep if you could keep only one beyond the lead and the workers? Expected: the read-only verifier with provenance, because a cited answer that is wrong is the failure the product cannot survive.
  • (level 4) How do you know the system is still working next quarter? Expected: the golden set run weekly, the supersession and flag rates, the agreement rate across parallel workers, and the quarterly audit.

Debug a failureIn a lead-and-workers research system, two workers answered overlapping sub-questions with numbers that contradict each other. The final report contains one of the numbers and no mention of the other. The user found the second number in a source and asks why the report hid it. Where did the system fail, and what do you change?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The lead resolved a synthesis conflict by picking one side in silence, which the lesson calls the worst failure in this pattern, because the user never learns that a disagreement happened. Two upstream causes made it likely: the decomposition gave two workers the same ground, and no worker had a scope that stopped it from drifting into the other's territory. The fix is a lead that detects contradiction between worker outputs and either re-asks with a narrower question or writes the disagreement into the answer, plus provenance on every synthesized claim.

Three failure modes in the pattern.

Failure What happened here
The lead hallucinates the plan Sub-questions overlapped, so two workers researched the same fact
Workers over-explore A worker without a scope boundary drifted past its question into another's
Synthesis conflict Two contradictory facts arrived, and the lead picked one without a note

The third is the one the user saw. The first two made it happen.

Detect the conflict without a model.

The lesson asks how to detect contradiction without a model call. Canonicalize the claims: extract each number with its unit and the entity it describes, key it by sub-question, and compare. Two different values under one key is a conflict. For non-numeric claims, flag a key only when the two workers state different claims. Different cited sources alone are not a conflict. Let the lead handle a flagged key.

What the lead does with a conflict.

  1. Re-ask. Spawn a worker on a tighter question aimed at the disagreement, which adds a round.
  2. Surface it. Write both values into the answer with their sources and say that they disagree.
  3. Never pick in silence. A chosen value with no note is the failure in the prompt.

Prevent the overlap.

Decompose broad first and narrow later, and give each worker an explicit scope in its prompt: the sub-question, what is out of scope, and the sources to prefer. Add a worker timeout at about twice the median runtime and a token cap per worker, so that a worker that wanders is cut and the lead re-spawns with a narrower question or proceeds without it.

Provenance on the synthesis.

Each claim in the final answer carries the worker and the source it came from. That makes the hidden second number impossible, because a claim with two sources shows two values, and it makes the post-mortem a read of the trace instead of a guess.

Plausible wrong answers.

  • "Add a rule to the lead's prompt that says be careful with numbers." The lead did not know a conflict existed, and a prompt does not compare worker outputs.
  • "Trust the worker with the higher confidence." Confidence is not correctness, and the user still never learns that a disagreement happened.
  • "Run three workers per sub-question and take the majority." A majority can be wrong together, it triples the cost, and the overlap that caused the conflict stays in the plan.

Follow-ups an interviewer may ask.

  • (level 3) Why is a silent pick worse than a wrong pick with a note? Expected: a noted disagreement lets the reader check the sources, while a silent pick presents an unresolved fact as settled.
  • (level 3) The re-ask adds a round and the latency target is tight. What do you do? Expected: surface the disagreement in the answer instead of re-asking, and record the key for a later run.
  • (level 4) How do you test the conflict detector? Expected: feed it worker outputs with a planted contradiction on one key and matching values on others, and assert that exactly that key is flagged.
  • (level 4) The two workers agree and are both wrong. What catches that? Expected: nothing in the lead, because agreement is not correctness, so an independent verifier with its own source access has to check the claim.

Where it is taught. The supervisor pattern lesson names the synthesis conflict and the worker timeout and token cap.

Explain the mechanismA research system with one lead agent and several worker agents beat a single agent on an internal evaluation by a wide margin. Explain the mechanism, and say which single variable explains most of the gain.

Level 1 of 4 · about 6 minutes to answer well.

Short answer. The lead plans and decomposes the question, each worker gets a fresh window for one narrow sub-question, and the lead synthesizes the worker summaries without ever reading the raw sources. Three mechanisms carry the gain: fresh context per worker, a narrow prompt per role, and workers that run at the same time. The variable that explains most of it is total token usage, which the lesson's source puts at 80 percent of the variance on one browsing benchmark. A worker that does not carry the lead's planning tokens has room to read.

The shape.

The lead receives the question, splits it into sub-questions, and sends one to each worker. Each worker starts from its own system prompt and its sub-question, not from the lead's history. The workers return summaries. The lead never sees the raw material, only the summaries, and writes the answer from them.

The three mechanisms.

  1. Fresh context. A worker on one sub-question does not carry the tens of thousands of tokens the lead spent planning. It has a full window for its question. The lesson's figure is a 200k window per worker against the 40k the lead already used.
  2. Specialization by prompt. The lead's prompt says decompose and synthesize. Each worker's prompt says find what changed in one thing. Narrow prompts produce narrow, usable outputs.
  3. Parallelism. Workers run concurrently, so wall-clock time is about the longest worker plus planning plus synthesis, not the sum of all workers.

The gain and its price.

The lesson reports a gain of 90.2 percent over the single agent on the internal evaluation, and a cost of about 15 times the tokens of a single agent. The same source says that about 80 percent of the variance on one browsing benchmark is explained by token usage alone. The pattern wins because it spends more tokens where they help, not because the lead is clever.

Operational lessons that come with it.

Scale the effort to the question: a simple query needs one agent and a few tool calls, and a complex one may need more than ten workers, and the lead must estimate that. Decompose broad first, then go deeper where an answer warrants it. Long-running stateful agents need a gradual deployment where old versions drain, not a hot swap.

Plausible wrong answers.

  • "The lead is a bigger model, so it is smarter." The gain tracks token usage, and the workers do the reading; a bigger lead alone changes nothing about context.
  • "Multi-agent is cheaper because workers are small." It costs about 15 times the tokens, and it is worth it only when the task value covers that.
  • "Give the lead the raw sources too, so it can check the workers." That fills the lead's window with what the workers already read and removes the fresh-context advantage.

Follow-ups an interviewer may ask.

  • (level 1) Why does the lead not read the raw sources? Expected: so that its window stays free for planning and synthesis, and so that each source is read once by the worker who owns it.
  • (level 2) When does the pattern lose to a pipeline? Expected: when step two needs step one's output, because then there is no parallel work and the extra agents only add tokens.
  • (level 2) What does the lead do when two workers disagree? Expected: it re-asks or notes the disagreement in the answer, and never picks one side in silence.
  • (level 3) A worker drifts beyond its sub-question. What stops it? Expected: an explicit scope in its prompt, a timeout at about twice the median worker runtime, and a token cap, after which the lead re-spawns with a narrower question or proceeds without it.

Where it is taught. The supervisor pattern lesson builds the lead and the parallel workers and reports the measured gain.
