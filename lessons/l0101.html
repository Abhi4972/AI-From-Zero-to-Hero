Why this came about

Language models did not start as chat assistants. They grew out of models trained to predict the next piece of text, and that origin explains their units: everything is measured in tokens, and every request has a fixed reading limit. When companies started paying for models through APIs from 2020 onward, tokens also became the unit of cost, so understanding them is the first step to understanding both what a model can do and what it costs.

In plain words first
Words are cut into pieces, and you pay per piece

A model does not read letters or whole words. It reads tokens: pieces of text, often a word or part of one ("refund" might be one token, "unrefundable" three). Everything is measured in tokens: the context window is how many tokens fit in one request, counting the input and the answer, and providers charge per token, with output tokens usually costing several times more than input tokens. Because the API remembers nothing between calls, a chat resends its whole history every turn, so the input grows with every message. That single fact explains most of an agent's bill.

Tokens: the unit of everything

Models read and write tokens, chunks of text produced by a tokenizer (most use byte-pair encoding, BPE). In English one token is roughly four characters, or three-quarters of a word. Other scripts often need more tokens for the same meaning: the same sentence in Hindi or Tamil can cost two to three times as many tokens as in English, depending on the tokenizer. Code, JSON and numbers are also token-hungry.

Tokens drive three things you care about:

What How tokens drive it
Cost Providers charge per million input tokens and per million output tokens. Output usually costs several times more than input. Cached input costs much less.
Latency Reading input (prefill) is fast and parallel. Writing output (decode) happens one token at a time, so long answers are slow. Lesson 1.2 measures both.
Limits The context window caps input plus output together. A separate max output tokens setting caps the answer.

Estimate before you build. This function is all you need for a first budget:

def run_cost(input_tokens: int, output_tokens: int, cached_tokens: int = 0,
             in_price: float = 3.0, out_price: float = 15.0, cached_price: float = 0.3) -> float:
    """Dollar cost of one model call. Prices are per million tokens; check your provider's price page."""
    fresh = input_tokens - cached_tokens
    return (fresh * in_price + cached_tokens * cached_price + output_tokens * out_price) / 1_000_000

# An agent turn: 6 model calls, each re-reading a 4,000-token prompt plus growing history
calls = [(4000 + 600 * i, 300) for i in range(6)]
no_cache = sum(run_cost(i, o) for i, o in calls)
with_cache = sum(run_cost(i, o, cached_tokens=4000) for i, o in calls)
print(f"per turn: ${no_cache:.4f} without caching, ${with_cache:.4f} with the prompt prefix cached")
print(f"per 100,000 turns a month: ${no_cache * 100_000:,.0f} vs ${with_cache * 100_000:,.0f}")
What you should see
per turn: $0.1260 without caching, $0.0612 with the prompt prefix cached
per 100,000 turns a month: $12,600 vs $6,120

Agents multiply calls, and every call re-reads the history. That is why prompt cachinglater · 2.4 and short histories are the first cost levers (Lesson 12.10).

In production
Token surprises in production
  • Languages cost differently: Hindi, Tamil and other Indic scripts, code and long numbers often take several times more tokens per word than English. Estimate cost and context limits with your real traffic, not English samples.
  • The invisible tokens: tool definitionslater · 3.1, system promptslater · 2.1 and retrieved chunks are input on every call. An agent with 40 tools can spend thousands of tokens before the user's question.
  • Silent truncation: a response cut off at max_tokens looks like a complete but wrong answer, and an input over the limit may be trimmed by the framework. Check the stop reason on every call and alert on length stops.
  • Count with the provider's usage field, not word counts or a different model's tokenizer.

Why some text costs more: byte-pair encoding in miniature

How this connects
You have seen this before

Lesson F5.2 builds byte-pair encoding step by step and explains every line. This section is a compact version of the same algorithm, used here for one engineering question: why does the same message cost more tokens in some languages than in others? If you did Lesson F5.2, read the output and the paragraph under it, and skip the code. If you skipped the foundations, the code below is short enough to follow on its own.

Models read tokens, produced by a tokenizer trained with byte-pair encoding (BPE): start from characters, and repeatedly merge the most frequent adjacent pair into a new token. Frequent words become single tokens; rare words and scripts the tokenizer saw less often split into many pieces.

from collections import Counter

def train_bpe(corpus: list[str], merges: int) -> list[tuple[str, str]]:
    """Learn merge rules: repeatedly join the most frequent adjacent pair of symbols."""
    words = Counter(tuple(w) + ("</w>",) for line in corpus for w in line.split())
    rules = []
    for _ in range(merges):
        pairs = Counter()
        for word, freq in words.items():
            for a, b in zip(word, word[1:]):
                pairs[(a, b)] += freq
        if not pairs:
            break
        best = max(pairs, key=pairs.get)
        rules.append(best)
        merged = {}
        for word, freq in words.items():
            out, i = [], 0
            while i < len(word):
                if i < len(word) - 1 and (word[i], word[i + 1]) == best:
                    out.append(word[i] + word[i + 1]); i += 2
                else:
                    out.append(word[i]); i += 1
            merged[tuple(out)] = freq
        words = merged
    return rules

def tokenize(text: str, rules) -> list[str]:
    tokens = []
    for w in text.split():
        word = list(w) + ["</w>"]
        for a, b in rules:                               # apply merges in the order they were learned
            i = 0
            while i < len(word) - 1:
                if word[i] == a and word[i + 1] == b:
                    word[i:i + 2] = [a + b]
                else:
                    i += 1
        tokens += word
    return tokens

corpus = ["where is my order", "my order is late", "where is the refund", "refund my order please"] * 50
rules = train_bpe(corpus, merges=40)
for text in ["where is my order", "my refund is late", "मेरा ऑर्डर कहाँ है"]:
    toks = tokenize(text, rules)
    print(f"{len(toks):2} tokens | {text}")
What you should see
 4 tokens | where is my order
 4 tokens | my refund is late
19 tokens | मेरा ऑर्डर कहाँ है

The English sentences the tokenizer was trained on compress to about one token per word; the Hindi sentence, never seen in training, falls apart into single characters. Production tokenizers are trained on far more languages, but the effect is the same in degree: text in Indian languages often costs noticeably more tokens than the same message in English, so measure token counts per language when you budget (most providers expose a count-tokens endpoint, and tiktoken counts OpenAI tokens locally).

Check your mental model
  • ✗ "A token is a word."
    ✓ It is a piece of text from the model's vocabulary; on average about three quarters of an English word, and more pieces per word in many other languages.
  • ✗ "The model remembers earlier messages, so only the new one is sent."
    ✓ The whole conversation is sent every time; input tokens grow turn by turn.
  • ✗ "A bigger context window means I can stop worrying about context."
    ✓ Long inputs cost more, answer more slowly, and models use the middle of a long context less well.

Exercises

Predict before you run

Using run_cost, a conversation of 10 turns resends a 1,500-token system prompt and a growing history. Which grows faster with the number of turns: input or output tokens, and why? (Solution P1.)

Break it on purpose

Estimate tokens as words for a Hindi message. How wrong can the estimate be? (Solution B1.)

Debugging exercise

train_bpe with too few merges produces tokens that are mostly single characters. What does that do to sequence length and cost? (Solution D1.)

Make it your own

Extend run_cost to report the cost of a 20-turn conversation with and without prompt caching of the system prompt. (Solution M1.)

Solutions

SolutionP1 · Input dominates long conversations

Input: every turn resends the system prompt and the whole history, so input grows roughly with the square of the number of turns, while output grows linearly. That is why caching and history management matter (Lessons 2.4 and 2.8).

SolutionB1 · Tokens are not words

Very wrong: tokenizers trained mostly on English split Hindi and other scripts into many more tokens per word, so cost and context use can be several times the word count. Measure with the provider's tokenizer or token-counting API.

SolutionD1 · Vocabulary size trade-off

Sequences get long, so the same text costs more tokens and attention is more expensive. More merges give longer tokens and shorter sequences, at the cost of a bigger vocabulary.

SolutionM1 · Cost over a conversation

Sum input and output per turn, with the cached part at the read multiplier after the first turn (Lesson 2.4). The difference grows with turns and prompt size.

Check your understanding

Explain the mechanismWhat is a token, and why does it matter to engineers?

Worked answer. A token is the unit a model reads and writes, a piece of a word produced by a tokenizer such as byte-pair encoding. Context windows, prices, rate limits and latency are all counted in tokens, so token counts drive cost, speed and how much fits in a request. Different languages and content (code, numbers) tokenize differently.

A plausible wrong answer. "A token is a word." Often less, and in some languages far less.

Debug a failureCosts for the Hindi version of a product are three times the English version's for the same traffic. Why?

Worked answer. Tokenization: Hindi text uses more tokens per word with most tokenizers, so prompts and replies cost more. Compare token counts per message, consider models with better multilingual tokenizers, and shorten prompts.

A plausible wrong answer. "Hindi users write more." Check tokens, not words.

Follow-ups. How would you budget for multilingual products?

Defend a designShould you choose a model by its context window size?

Worked answer. Only as a constraint: the window must fit your largest real request with margin. Beyond that, quality, cost per token, latency and how well the model uses long context matter more. Most requests should be far smaller than the window.

A plausible wrong answer. "Bigger window is always better." You pay for what you send, and quality drops on very long inputs.
