In plain words first
The idea in one line

Production agents run on six runtime shapes: request-response, streaming, durable execution, queue-based background, event-driven, and scheduled. Pick the shape before you pick the framework. Observability is load-bearing at every shape.

Terms you'll hear

Streaming "SSE / WS" Progressive output; better UX; latency observable per chunk
Durable execution "Resume from failure" Checkpointed state; restart at last step

The problem

In plain words first

The same agent can be served in different runtime shapes. In request-response the caller waits for the whole answer in one HTTP request. Streaming sends the answer piece by piece as it is written. A queue (background jobs) accepts the work, returns at once, and lets workers finish it later, with retries for failures and a dead-letter queue (DLQ) for jobs that keep failing. Durable execution saves progress after each step so a restarted job continues where it stopped. The right shape depends on how long the work takes and whether it changes things in the world. This lesson times a real model under the first two shapes and runs refund jobs through three kinds of queue worker.

Production agents fail in ways a Jupyter notebook doesn't surface: network timeouts at step 37, user hangs up mid-voice call, cron job dies on machine reboot, background worker runs out of memory. The runtime shape determines which failures are survivable.

Idea 1 · Request-response

  • Synchronous HTTP. User waits for completion.
  • Only viable for short tasks (<30s).
  • Stacks: Agno (Python + FastAPI), Mastra (TypeScript + Express/Hono/Fastify/Koa).
  • Observability: standard HTTP access logs + OTel spans.

Idea 2 · Streaming

  • SSE or WebSocket for progressive output.
  • LiveKit extends this to WebRTC for voice/video (Lesson 14.22).
  • Stacks: any framework with streaming support + a frontend that handles SSE/WS.
  • Observability: per-chunk timing, first-token latency, tail latency.

Idea 3 · Durable execution

  • State checkpointed after every step; auto-resumes on failure.
  • AutoGen v0.4 actor model isolates failures to one agent (Lesson 14.14).
  • LangGraph's core differentiator (Lesson 14.13).
  • Essential when step count is unknown and recovery cost is high.

Idea 4 · Queue-based / background

  • Job enters a queue, workers pick up, results flow back via webhooks or pub/sub.
  • Essential for long-horizon agents (dozens-to-hundreds of steps per task, per Anthropic's computer use announcement).
  • Stacks: Celery (Python), BullMQ (Node), SQS + Lambda (AWS), custom.
  • Observability: queue depth, per-job latency distribution, DLQ size.

Idea 5 · Event-driven

  • Agents subscribe to triggers: new email, PR opened, cron fire.
  • Claude Managed Agents covers this out of the box (Lesson 14.17).
  • CrewAI Flows (Lesson 14.15) structures event-driven deterministic workflows.
  • Observability: trigger source, event-to-start latency, agent latency.

Idea 6 · Scheduled

  • Cron-shaped agents that run periodically.
  • Combine with durable execution so a failing nightly run resumes next tick.
  • Stacks: Kubernetes CronJob + a durable framework; hosted (Render cron, Vercel cron).

Idea 7 · 2026 deployment patterns

  • CrewAI Flows for event-driven production.
  • Agno stateless FastAPI for Python microservices.
  • Mastra server adapters (Express, Hono, Fastify, Koa) for embedding.
  • Pipecat Cloud / LiveKit Cloud for managed voice (Lesson 14.22).
  • Claude Managed Agents for hosted long-running async.

Idea 8 · Observability is load-bearing

Without OpenTelemetry GenAI spans (Lesson 14.23) plus a Langfuse/Phoenix/Opik backend (Lesson 14.24), you cannot debug a multi-step agent that failed at step 40. This is not optional for production. It's the difference between "we debug fast" and "we replay from scratch with more logging."

Idea 9 · Where production runtimes fail

  • Wrong shape choice. Picking request-response for a 5-minute task. Users hang up; workers pile up; retries compound.
  • No DLQ. Queue workers without dead-letter. Failed jobs vanish.
  • Opaque background work. Background agent runs without trace export. Failures are invisible until the user reports them.
  • Skipping durable state. Any run > 30 seconds where you can't afford to restart needs durable execution.

The same idea as a formula

What the user waits for. With time to first token t0​ and a generation rate of r tokens per second, an answer of n tokens is complete at T=t0​+n/r. Request-response shows nothing until T; streaming shows the first words at t0​.

Timeouts. A gateway with a total timeout τ fails every request with T>τ. For a stream, proxies usually apply an idle timeout to the gap between chunks, maxi​(ti+1​−ti​)≤τ, so a long answer survives as long as it keeps flowing.

Retries and side effects. If a job with a side effect is retried k times after the side effect already happened, it happens k+1 times, unless the effect is idempotent (repeating it with the same key changes nothing) or the job resumes after the completed step.

Worked example
When each shape breaks
  • On this CPU the model writes about 13 words a second after a first token at about 0.15 s.
  • An 81-word explanation takes about 6 s: past a 3 s gateway as a plain request (a 504 while the model keeps working), fine as a stream, where no gap is longer than 0.2 s.
  • A 200-word plan takes about 16 s. Streaming still works, but a person watching for 16 s is the limit of what a synchronous shape should ask; minutes-long agent runs belong in a queue.
  • Refund job A-16 fails at its email step three times. Retrying the whole job refunds the customer 3 times before it reaches the dead-letter queue; with an idempotency key or a checkpoint, once.
Check your mental model
  • ✗ "Streaming makes the model faster."
    ✓ Total time is the same; the user sees progress from the first token.
  • ✗ "Retrying a failed job is always safe."
    ✓ Only if its side effects are idempotent or skipped on resume.
  • ✗ "The dead-letter queue means nothing happened."
    ✓ A job can reach it after doing real, repeated damage.
  • ✗ "A request that timed out stopped running."
    ✓ The model often keeps generating for nobody, costing compute.

Request-response versus streaming, timed

Qwen2.5-0.5B-Instruct (greedy, CPU) answers three requests while a streamer timestamps every piece of text. The block reports the first token, the full answer, and what each shape delivers behind a 3-second gateway: a total timeout for plain requests, an idle timeout for streams. About 30 seconds.

# Request-response versus streaming with a real model. Qwen2.5-0.5B-Instruct (greedy, CPU) answers three
# requests of different lengths. For each we time the first token and the whole answer, then put a 3-second
# gateway timeout in front, as a load balancer or API gateway would. A plain request must finish within it;
# a stream only has to keep sending (an idle timeout), which is how proxies usually treat open streams.
import os, threading, time, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, TextIteratorStreamer, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def stream(prompt, max_new_tokens):
    """Yields (seconds since start, text piece) as the model writes."""
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    streamer = TextIteratorStreamer(tok, skip_prompt=True, skip_special_tokens=True)
    t0 = time.perf_counter()
    th = threading.Thread(target=llm.generate, kwargs=dict(input_ids=ids, max_new_tokens=max_new_tokens,
                                                           do_sample=False, streamer=streamer))
    th.start()
    for piece in streamer:
        yield time.perf_counter() - t0, piece
    th.join()

REQUESTS = [("What is the capital of Portugal? One word.", 8),
            ("Explain in three sentences what a message queue is.", 90),
            ("Write a step-by-step plan, about 200 words, for migrating a web app to a new database.", 260)]
TIMEOUT = 3.0
print(f"{'request':<44}{'first token':>12}{'full answer':>13}{'words':>7}   (gateway timeout {TIMEOUT:.0f} s)")
for prompt, n in REQUESTS:
    pieces = list(stream(prompt, n))
    first = next(t for t, p in pieces if p.strip())
    total = pieces[-1][0]
    text = "".join(p for _, p in pieces)
    before = "".join(p for t, p in pieces if t <= TIMEOUT)
    rr = "full answer" if total <= TIMEOUT else "504, nothing (the model keeps working for nobody)"
    gap = max(b[0] - a[0] for a, b in zip([(0.0, "")] + pieces, pieces))
    st = (f"full answer, words arriving from {first:.2f} s; longest silence {gap:.2f} s" if gap <= TIMEOUT
          else f"cut after {len(before.split())} words")
    print(f"{prompt[:42]:<44}{first:>11.2f}s{total:>12.1f}s{len(text.split()):>7}")
    print(f"{'':<44}request-response: {rr}")
    print(f"{'':<44}streaming:        {st}")

Reading this output

The first token is fast for every request, about 0.15 s, because it depends on reading the prompt, not on the length of the answer. Total time grows with the answer: 0.4 s for one word, about 6 s for 81 words, about 16 s for 203.

Request-response fails as soon as the answer is long. Behind a 3-second gateway the short answer arrives, and the other two become 504 errors. The model keeps generating after the gateway gives up, so the compute is spent and the user gets nothing.

Streaming delivers all three. Words start arriving at about 0.15 s and never pause for more than a fifth of a second, so an idle timeout never fires. The 16-second plan still makes the user watch for 16 seconds; for agent runs that take minutes, the right shape is a background job with progress updates.

Retries, side effects and the dead-letter queue

This block continues from the one above but needs no model. Six refund jobs use the lesson's Job and its retry policy (three attempts, then the dead-letter queue). Each job refunds the order, then emails a confirmation; the email fails once for two jobs and always for one. Three workers differ only in how they retry.

# Background jobs with side effects. Six refund jobs go through a queue with the lesson's retry policy
# (code/main.py: retry until the third attempt, then the dead-letter queue). Each job has two steps:
# issue the refund at the payment provider, then email a confirmation. The email service fails once for two
# jobs and always for one. Three workers: retry the whole job (as the lesson's QueueRuntime does), retry with
# an idempotency key at the provider, and resume from a checkpoint of completed steps (durable execution).
from collections import Counter, deque
from main import Job

ORDERS = ["A-11", "A-12", "A-13", "A-14", "A-15", "A-16"]
FLAKY = {"A-12": 1, "A-14": 1, "A-16": 99}            # email failures before success (99 = never succeeds)

class Provider:
    def __init__(self, idempotent):
        self.refunds, self.keys, self.idempotent = Counter(), set(), idempotent
    def refund(self, order, key):
        if self.idempotent and key in self.keys:
            return "already done"                       # same key: the provider returns the first result
        self.keys.add(key); self.refunds[order] += 1
        return "refunded"

def run_queue(mode):
    provider, mail_fails, done_steps = Provider(idempotent=(mode == "idempotency key")), Counter(), {}
    queue = deque(Job(jid=f"j{i + 1}", payload=o) for i, o in enumerate(ORDERS))
    dlq, attempts = [], 0
    while queue:
        job = queue.popleft(); job.attempt += 1; attempts += 1
        steps = done_steps.setdefault(job.jid, set()) if mode == "checkpoint" else set()
        try:
            if "refund" not in steps:
                provider.refund(job.payload, key=job.jid); steps.add("refund")
            if "email" not in steps:
                if mail_fails[job.payload] < FLAKY.get(job.payload, 0):
                    mail_fails[job.payload] += 1
                    raise RuntimeError("email service unavailable")
                steps.add("email")
        except RuntimeError:
            if job.attempt < 3:
                queue.append(job)
            else:
                dlq.append(job)
    dup = {o: n for o, n in provider.refunds.items() if n > 1}
    return attempts, sum(provider.refunds.values()), dup, [j.payload for j in dlq]

print(f"{'worker':<24}{'attempts':>9}{'refunds issued':>16}   {'refunded more than once':<36}dead letters")
for mode in ["retry the whole job", "idempotency key", "checkpoint"]:
    attempts, total, dup, dlq = run_queue(mode)
    print(f"{mode:<24}{attempts:>9}{total:>16}   {str(dup or '-'):<36}{dlq}")
print(f"\n6 orders need exactly 6 refunds. A-16's email never works, so its job ends in the dead-letter queue")
print("in every mode; what differs is how many times its customer was refunded on the way there.")

Reading this output

All three workers make the same attempts (ten) and send the same job, A-16, to the dead-letter queue. Their dashboards would look identical.

Retrying the whole job repeats the refund. A-12 and A-14 were refunded twice and A-16 three times: 10 refunds for 6 orders. The failure was in the email step, after the money had moved, and each retry started again from the refund. The lesson's QueueRuntime retries this way, safe only because its toy jobs have no side effects.

Either fix gives exactly 6 refunds. An idempotency key (here the job id) makes the provider return the first result instead of refunding again; a checkpoint of completed steps makes the retry skip the refund. Real systems use both: checkpoints for efficiency, idempotency keys for when the checkpoint itself is lost.

Part 1 of 3 · _agent_fn, request_response, streaming, Job, QueueRuntime

"""Four production runtime shapes: request-response, streaming, queue, event.

Same agent logic, four different outer shells. Stdlib only.
"""

from __future__ import annotations

from collections import deque
from dataclasses import dataclass, field
from typing import Any, Callable, Iterable


def _agent_fn(input_text: str) -> list[str]:
    steps = [
        f"parse: {input_text[:40]}",
        f"plan: 3-step plan",
        f"step 1: search",
        f"step 2: read",
        f"final: answered {input_text[:20]}",
    ]
    return steps


def request_response(input_text: str) -> str:
    steps = _agent_fn(input_text)
    return steps[-1]


def streaming(input_text: str) -> Iterable[str]:
    for step in _agent_fn(input_text):
        yield step


@dataclass
class Job:
    jid: str
    payload: str
    attempt: int = 0


@dataclass
class QueueRuntime:
    queue: deque[Job] = field(default_factory=deque)
    dlq: list[Job] = field(default_factory=list)
    fail_rate: int = 0
    counter: int = 0

    def enqueue(self, payload: str) -> str:
        self.counter += 1
        jid = f"j{self.counter:03d}"
        self.queue.append(Job(jid=jid, payload=payload))
        return jid

    def worker(self, fail_policy: Callable[[Job], bool]) -> list[tuple[str, str]]:
        results: list[tuple[str, str]] = []
        while self.queue:
            job = self.queue.popleft()
            job.attempt += 1
            if fail_policy(job) and job.attempt < 3:
                self.queue.append(job)
                results.append((job.jid, "retry"))
                continue
            if fail_policy(job):
                self.dlq.append(job)
                results.append((job.jid, "DLQ"))
                continue
            steps = _agent_fn(job.payload)
            results.append((job.jid, steps[-1]))
        return results

Part 2 of 3 · EventBus

@dataclass
class EventBus:
    subscribers: dict[str, list[Callable[[str], str]]] = field(default_factory=dict)

    def subscribe(self, event_type: str, handler: Callable[[str], str]) -> None:
        self.subscribers.setdefault(event_type, []).append(handler)

    def publish(self, event_type: str, payload: str) -> list[tuple[str, str]]:
        results: list[tuple[str, str]] = []
        for handler in self.subscribers.get(event_type, []):
            results.append((event_type, handler(payload)))
        return results

    rt.enqueue("long job B")
    rt.enqueue("long job C")

    def fail_b(job: Job) -> bool:

    for jid, status in results:
        print(f"  {jid}: {status}")
    print(f"  queue: {len(rt.queue)}   dlq: {len(rt.dlq)}")

    print("\n4. event-driven (subscriber pattern)")
    bus = EventBus()

    def on_pr_opened(payload: str) -> str:
        return f"ran checks on {payload}"

    def on_memory_consolidate(payload: str) -> str:
        return f"consolidated {payload}"

    bus.subscribe("pr.opened", on_pr_opened)
    bus.subscribe("memory.consolidate", on_memory_consolidate)

    for evt, res in bus.publish("pr.opened", "#123 add feature"):
        print(f"  {evt} -> {res}")
    for evt, res in bus.publish("memory.consolidate", "session_001"):
        print(f"  {evt} -> {res}")

    print("\n5. scheduled (cron stand-in)")
    schedule = [
        ("02:00", "memory.consolidate"),
        ("03:00", "eval.nightly"),
    ]
    for when, event in schedule:
        print(f"  {when}: would fire {event}")

Use it: the same idea with real libraries

  • Request-response for chat-style UX.
  • Streaming for progressive responses.
  • Durable for long-horizon tasks.
  • Queue for batch / async / long-running.
  • Event for agent reactivity.
  • Cron for housekeeping (memory consolidation, evals, cost reports).
Break it on purpose

An agent that books travel runs as a background job: it reserves a hotel, books a flight and emails the itinerary. After an email-provider outage, finance finds dozens of customers with two or three identical hotel reservations, although the job dashboard shows each booking job either succeeded once or ended in the dead-letter queue. Industry practice
What's current (2024–2026)
  • Durable execution is now standard for long agent runs: LangGraph checkpointers (lesson 14.13), Temporal and similar workflow engines (OpenAI's Agents SDK and others ship Temporal integrations), Restate, Inngest and cloud services such as AWS Step Functions save each step and resume after failures.
  • Hosted agent runtimes (Claude Managed Agents, the OpenAI and Google agent platforms, AWS Bedrock AgentCore) run long sessions in the background with sandboxes and state, so teams build less queue plumbing themselves.
  • Idempotency keys are the norm at payment and booking APIs (Stripe, Adyen and most others accept one per request), and agent tools that cause side effects should pass one derived from the job and step.
  • Streaming with server-sent events or WebSockets is the default for interactive agents; long runs report progress by events or webhooks instead of holding a request open.
  • On your laptop: everything here is CPU-only. A local queue with retries needs nothing more than Redis (or SQLite) and a worker process; Temporal's development server runs in one binary.

Sources: LangGraph durable execution, Temporal, Stripe idempotent requests, AWS ALB idle timeout.

Recap
What to keep from this lesson
  • Match the shape to the duration: seconds stream, minutes queue.
  • Plain requests die at gateway timeouts; streams survive while they flow.
  • Retries repeat side effects unless they are idempotent or checkpointed.
  • Dead-letter queues hide damage done on the way in.
  • Trace every step of background work, or failures stay invisible.

Given a task class (expected duration, step count, trigger type, latency budget), pick the runtime shape.

Decision:

1. < 30s, user waits -> **request-response**.
2. Progressive UX or voice -> **streaming**.
3. Minutes to hours, user doesn't wait -> **queue-based**.
4. Reactive to external events -> **event-driven**.
5. Periodic housekeeping -> **cron**.
6. Any of the above where restart cost is high -> add **durable execution**.

Produce:

1. The shape scaffold in your stack.
2. Observability: OTel GenAI spans (Lesson 23), backend wired (Lesson 24).
3. For queue: DLQ + retry policy + queue depth metric.
4. For event: explicit subscriber registry + replay path.
5. For cron: lock file or distributed lock to prevent overlapping runs.
6. For durable: checkpointer backend + resume semantics.

Hard rejects:

- Synchronous HTTP for a 5-minute task. Users hang up; workers pile up.
- Queue-based without DLQ. Failed jobs vanish.
- Background work without trace export. Failures invisible until users complain.
- "No durable state, we'll just retry." Long horizons must checkpoint.

Refusal rules:

- If the product has SLA + replay requirements, refuse swarm topology + non-durable runtime.
- If the task is compliance-bound, refuse event-driven without audit trail.
- If the user wants cron + no lock, refuse. Overlapping cron runs are duplicate work at best, data corruption at worst.

Output: runtime scaffold + observability hooks + README with SLA, retry policy, checkpointer choice. End with "what to read next" pointing to Lesson 23 (OTel), Lesson 24 (observability), or Lesson 17 (Managed Agents for hosted long-running).

Solutions

SolutionP1 · Plain requests fail; streams survive

The one-word answer succeeds both ways. The 80-word explanation (about 6 s) and the 200-word plan (about 16 s) fail as plain requests, with a 504 after 3 s while the model keeps working. As streams all three succeed: the first words arrive in about 0.15 s and the gaps between pieces stay far below 3 s, so the gateway's idle timeout never fires.

SolutionB1 · Retried bookings

The jobs were retried from the start after the email step failed. Each retry reserved the hotel (and possibly the flight) again, then failed at the email again, so a job that "succeeded once" on its final attempt, or ended in the dead-letter queue, left one reservation per attempt behind. The dashboard counts job outcomes, not side effects.

Fix: make every side-effecting step idempotent, passing a key derived from the job and step (for example job-123:reserve-hotel) to the hotel and flight APIs; checkpoint completed steps so retries resume after them (durable execution); move non-essential steps such as email out of the critical path (a separate job or event); and add a reconciliation check that compares reservations per booking with the expected count, alerting on duplicates. For jobs already in the dead-letter queue, review their side effects before replaying them.
