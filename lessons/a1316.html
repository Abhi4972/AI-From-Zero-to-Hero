In plain words first
The idea in one line

A remote MCP request is stateless, but its authorization is not anonymous. Bind every credential to the issuer that created it and every token to the resource that receives it.

Terms you'll hear
Term Meaning
Protected-resource metadata RFC 9728 document that identifies the resource and authorization servers
CIMD HTTPS metadata document whose URL is the OAuth client identifier
DCR Deprecated dynamic client enrollment retained for compatibility
application_type native or web, used to validate redirect URI rules
PKCE Verifier and S256 challenge that protect an intercepted authorization code
iss RFC 9207 authorization response issuer identifier

Step-up New consent and token issuance for an additional current-operation scope
Issuer-bound credentials Registration and token records isolated by exact authorization server issuer

The problem

In plain words first

A remote MCP server that can read private notes must know who is calling and what they agreed to. MCP uses OAuth for this. The user signs in at an authorization server, which gives the client an access token. The client then sends that token with every request to the MCP server, and the server checks it. Several details make this safe. PKCE ties the sign-in to the client that started it, so a stolen code is useless. The iss check makes sure the answer came from the expected authorization server. The audience check makes sure a token meant for one server cannot be used at another. Scopes limit what the token allows. The 2026-07-28 revision also prefers Client ID Metadata Documents (a URL that identifies the client) over dynamic registration. This lesson runs the sign-in flow with real signed tokens and three attacks. It then puts the official SDK's protected MCP endpoint in front of five different tokens.

A remote MCP server may read private records, write external systems, or trigger costly work. Authentication tells it who presented a credential. Authorization must also answer:

  • Which authorization server issued the credential?
  • Which MCP resource is the token for?
  • Which client and redirect URI completed the flow?
  • Which operations did the user approve?
  • Does this exact request still fit that approval?

The 2026-07-28 authorization profile hardens client enrollment and issuer handling. It prefers Client ID Metadata Documents, deprecates Dynamic Client Registration, requires the right application_type on DCR, validates RFC 9207 issuer responses, and forbids credential reuse across issuers.

These rules complement the stateless core. They do not restore a core handshake or Mcp-Session-Id.

Idea 1 · Know the three roles

  • MCP client: sends requests on behalf of a resource owner.
  • MCP resource server: accepts the access token and serves the MCP endpoint.
  • Authorization server: authenticates the resource owner, collects consent, and issues tokens.

The resource server and authorization server can be operated together, but keep their identifiers and validation responsibilities separate.

Idea 2 · Authorization applies to HTTP

The MCP authorization specification applies to HTTP-based transports. A local stdio server runs under the process and operating-system trust boundary. Do not add a fake browser OAuth flow to stdio merely for symmetry.

For remote Streamable HTTP, send the bearer token in the Authorization header on every request. Never place it in the URL.

Idea 3 · Start with protected-resource metadata

The resource server publishes RFC 9728 metadata:

{
  "resource": "https://notes.example.com/mcp",
  "authorization_servers": ["https://auth.example.com"],
  "scopes_supported": ["notes:delete", "notes:read", "notes:write"]
}

The client starts from the MCP resource URL, fetches this document, selects an advertised authorization server, and then fetches that server's OAuth or OpenID Connect metadata.

Preserve the resource path when constructing the RFC 9728 well-known URL. For the resource https://notes.example.com/mcp, this lesson uses https://notes.example.com/.well-known/oauth-protected-resource/mcp. Dropping the /mcp suffix can select metadata for a different protected resource on the same origin.

Do not guess the authorization server from a hostname. Do not follow an issuer discovered from an unvalidated error body. Keep a policy for which issuers the client is willing to trust.

Idea 4 · Verify authorization server metadata

The metadata should expose endpoints and supported controls:

{
  "issuer": "https://auth.example.com",
  "authorization_endpoint": "https://auth.example.com/authorize",
  "token_endpoint": "https://auth.example.com/token",
  "code_challenge_methods_supported": ["S256"],
  "authorization_response_iss_parameter_supported": true,
  "client_id_metadata_document_supported": true
}

Require S256 for PKCE. Record the exact issuer string. That exact value becomes the key for registration and token storage.

Idea 5 · Follow the registration priority

Use pre-registered client information when the client already has an explicit relationship with the selected issuer. Otherwise prefer Client ID Metadata Documents when the authorization server advertises support. Use DCR only as the deprecated compatibility fallback, then prompt for client information if none of those mechanisms is available.

Idea 6 · Prefer Client ID Metadata Documents

A Client ID Metadata Document gives the authorization server an HTTPS URL that is both the client identifier and the location of its metadata:

{
  "client_id": "https://client.example.com/oauth/metadata.json",
  "client_name": "Notes desktop client",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:8765/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"]
}

The authorization server fetches and validates the document. The client_id must be an HTTPS URL with a path, and the value inside the document must equal that URL exactly. The required document fields are client_id, client_name, and redirect_uris. application_type appears in this example but is not a CIMD requirement. Its new mandatory use is specifically the DCR path.

Treat fetching the document as an SSRF-sensitive operation. Resolve and validate the destination, reject loopback, private, link-local, and otherwise disallowed addresses, re-check after redirects and DNS changes, limit redirects, bytes, and time, require JSON, and cache only according to validated HTTP cache controls. Treat client_name and other display fields as untrusted text.

CIMD removes the need to mint a fresh dynamic identifier for every first contact. It does not remove redirect URI validation, issuer policy, or user consent.

Idea 7 · DCR is a compatibility path

Dynamic Client Registration remains available for older authorization servers, but it is deprecated for new MCP implementations.

When using DCR, declare application_type:

{
  "client_name": "Notes desktop client",
  "application_type": "native",
  "redirect_uris": ["http://127.0.0.1:8765/callback"],
  "grant_types": ["authorization_code"],
  "response_types": ["code"]
}
  • Desktop, mobile, command-line, and loopback clients use native.
  • Remotely hosted browser applications use web and remote HTTPS redirects.

Omitting the field can default to web in an OpenID Connect registration implementation and make a legitimate loopback redirect fail.

Keep DCR code behind an explicit fallback decision. Do not silently fall back after an arbitrary CIMD validation failure. That could turn a security failure into a weaker enrollment path.

Idea 8 · Bind credentials to the issuer

Store issuer-minted enrollment material under the exact issuer:

issuer_credentials[issuer] = pre_registered_or_dcr_client
tokens[(issuer, resource)] = access_token

If protected-resource discovery changes from https://auth-one.example to https://auth-two.example, re-evaluate trust. Never send the first issuer's client secret, DCR client id, registration access token, refresh token, or access token to the second. Pre-registered and DCR clients must use credentials issued for the new issuer.

A CIMD client id is different because it is a self-hosted HTTPS URL, not a credential minted by an authorization server. The same CIMD URL is portable: a new trusted issuer fetches and validates the document without DCR re-registration. Authorization responses and tokens are still validated and stored under the new issuer.

Idea 9 · Authorization code with PKCE

The interactive flow is:

  1. Generate a high-entropy code_verifier.
  2. Derive the S256 code_challenge.
  3. Send the authorization request with exact client_id, redirect_uri, scope, code_challenge, and resource.
  4. Receive an authorization response containing code and, when provided, iss.
  5. Validate iss against the exact recorded issuer before using any response field.
  6. Exchange the code with code_verifier, the same redirect URI, and the same resource.
  7. Store the resulting token under (issuer, resource).

The resource parameter from RFC 8707 appears in both authorization and token requests. It identifies the canonical MCP server URI.

Idea 10 · Validate iss exactly

RFC 9207 prevents an authorization response from one issuer being confused with a response from another.

When iss is present, compare it to the recorded issuer without case folding, trailing-slash changes, default-port removal, or percent-encoding normalization. On mismatch, do not act on the code or even display attacker-controlled error details from that response.

An authorization server that includes iss advertises authorization_response_iss_parameter_supported: true. Current clients still validate a present iss even when that advertisement is missing.

Idea 11 · Validate audience at the MCP server

The resource server accepts only tokens issued for itself:

token.issuer == configured_authorization_server
token.audience == canonical_mcp_resource

Invalid, expired, wrong-issuer, or wrong-audience tokens receive 401. The MCP server must not accept or transit a token meant for another service.

The same idea as a formula

PKCE (S256). The client picks a random verifier v (43–128 characters) and sends only

c=BASE64URL(SHA256(v))
with the authorization request. The token request must present v; the server recomputes c. A thief who intercepts the code but not v would have to find v′ with SHA256(v′)=SHA256(v): infeasible. A random 64-character URL-safe verifier carries about 64×6=384 bits of entropy.

What the MCP server accepts. A token t is accepted for a request needing scopes Q only if

verifykey​(t)∧t.iss=I∧t.aud=R∧now<t.exp∧Q⊆t.scope,
with I the configured issuer and R the server's canonical resource URI. Failures of the first four give HTTP 401; a valid token with too few scopes gives 403 insufficient_scope, which tells the client what to ask for (step-up).

Worked example
One sign-in and five tokens
  • Normal flow: verifier → challenge → code → token. The token says iss = https://auth.example.com, aud = https://notes.example.com/mcp, scope = notes:read, valid 600 s.
  • Stolen code, wrong verifier: the challenge does not match → invalid_grant. Replaying the same code: codes are single-use → invalid_grant.
  • Mix-up: the authorization response says iss = https://evil-as.example → the client stops before redeeming anything.
  • At the MCP server: a token for calendar.example.com (wrong audience), an expired token and a token from another issuer → 401. A valid token with only notes:write → 403, "Required scope: notes:read".
Check your mental model
  • ✗ "PKCE is only for public clients without secrets."
    ✓ OAuth 2.1 and MCP require it for every authorization-code flow.
  • ✗ "Any valid token from our authorization server works on any of our MCP servers."
    ✓ Each server accepts only tokens whose audience is its own resource URI.
  • ✗ "A gateway can forward the user's token to the backend services it calls."
    ✓ No token passthrough: each hop gets its own token for its own audience.
  • ✗ "Stdio servers need OAuth too."
    ✓ MCP authorization applies to HTTP; a local stdio server runs inside the OS trust boundary.
Predict before you run

An attacker intercepts the authorization code but not the client's PKCE verifier and tries to redeem it. Then the real client redeems the same code twice. Then an authorization response claims to come from a different issuer. Which of these yields a token? (Solution P1.)

See it drawn
Authorization code with PKCE, iss checking, and three attacks

A toy authorization server with the real checks: single-use codes bound to client, redirect URI and resource; S256 PKCE; RS256-signed JWT access tokens (PyJWT and cryptography) with issuer, audience, subject, scope and expiry; and an iss in every authorization response (RFC 9207). The client uses a Client ID Metadata Document URL as its client id. Instant.

import base64, hashlib, secrets, time, jwt
from cryptography.hazmat.primitives.asymmetric import rsa

ISSUER, RESOURCE = "https://auth.example.com", "https://notes.example.com/mcp"
CLIENT_ID = "https://client.example.com/oauth/client-metadata.json"   # a Client ID Metadata Document URL
REDIRECT = "http://127.0.0.1:33418/callback"
signing_key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=").decode()

# --- authorization server (a toy, but with the real checks) -----------------------------------
codes = {}
def authorize(client_id, redirect_uri, code_challenge, method, resource, scope):
    assert method == "S256", "only S256 PKCE"
    code = secrets.token_urlsafe(24)
    codes[code] = dict(client_id=client_id, redirect_uri=redirect_uri, challenge=code_challenge,
                       resource=resource, scope=scope, used=False)
    return {"code": code, "iss": ISSUER}                    # RFC 9207: the response names its issuer
def token(code, code_verifier, client_id, redirect_uri, resource):
    c = codes.get(code)
    if not c or c["used"]: return {"error": "invalid_grant", "why": "unknown or reused code"}
    c["used"] = True                                        # codes are single-use, even after a failure
    if (c["client_id"], c["redirect_uri"], c["resource"]) != (client_id, redirect_uri, resource):
        return {"error": "invalid_grant", "why": "client, redirect or resource differs"}
    if b64(hashlib.sha256(code_verifier.encode()).digest()) != c["challenge"]:
        return {"error": "invalid_grant", "why": "PKCE verifier does not match the challenge"}
    now = int(time.time())
    at = jwt.encode({"iss": ISSUER, "aud": resource, "sub": "user-42", "client_id": client_id,
                     "scope": c["scope"], "iat": now, "exp": now + 600}, signing_key, algorithm="RS256")
    return {"access_token": at, "token_type": "Bearer", "expires_in": 600}

# --- client ------------------------------------------------------------------------------------
def client_flow(tamper=None):
    verifier = secrets.token_urlsafe(48)                    # 64 characters, kept by the client only
    challenge = b64(hashlib.sha256(verifier.encode()).digest())
    resp = authorize(CLIENT_ID, REDIRECT, challenge, "S256", RESOURCE, "notes:read")
    if tamper == "mixup": resp["iss"] = "https://evil-as.example"
    if resp["iss"] != ISSUER:                               # mix-up defence: before redeeming the code
        return "client refuses: iss in the response is not the issuer it started with"
    if tamper == "stolen_code": verifier = secrets.token_urlsafe(48)   # attacker has the code, not the verifier
    out = token(resp["code"], verifier, CLIENT_ID, REDIRECT, RESOURCE)
    if tamper == "replay": out = token(resp["code"], verifier, CLIENT_ID, REDIRECT, RESOURCE)
    return out

ok = client_flow()
claims = jwt.decode(ok["access_token"], signing_key.public_key(), algorithms=["RS256"], audience=RESOURCE,
                    issuer=ISSUER)
print("normal flow -> access token for", claims["aud"], "| scope", claims["scope"], "| sub", claims["sub"],
      "| expires in", claims["exp"] - claims["iat"], "s")
for t in ("stolen_code", "replay", "mixup"):
    print(f"{t:<12}-> {client_flow(t)}")
What you should see
normal flow -> access token for https://notes.example.com/mcp | scope notes:read | sub user-42 | expires in 600 s
stolen_code -> {'error': 'invalid_grant', 'why': 'PKCE verifier does not match the challenge'}
replay      -> {'error': 'invalid_grant', 'why': 'unknown or reused code'}
mixup       -> client refuses: iss in the response is not the issuer it started with
Reading this output

The normal flow yields a narrow token. It names its issuer, its audience (https://notes.example.com/mcp), its subject, the single scope notes:read, and a 600-second lifetime. Nothing in it would let it be used at another server.

A stolen code is useless without the verifier. The attacker's token request fails with "PKCE verifier does not match the challenge": the authorization server only ever saw the SHA-256 of the real verifier.

Codes are single-use. Redeeming the same code a second time fails ("unknown or reused code"), even for the legitimate client. A server should also revoke tokens already issued from a code that is replayed.

Mix-up is stopped by the client. When the authorization response names a different issuer than the one the client started with, the client refuses before sending the code anywhere.

An MCPServer with a JWT token_verifier and AuthSettings (issuer, resource URL, required scope notes:read, token-resource validation) serves Streamable HTTP through Starlette's TestClient under https://notes.example.com. It is called without a token, its protected-resource metadata is fetched, and five tokens are tried. A couple of seconds.

# Continues from the block above: ISSUER, RESOURCE, CLIENT_ID, signing_key and client_flow are defined.
import json, time, jwt
from starlette.testclient import TestClient
from mcp.server import MCPServer
from mcp.server.auth.provider import AccessToken
from mcp.server.auth.settings import AuthSettings
from mcp.server.transport_security import TransportSecuritySettings

class JWTVerifier:                                      # the resource server checks every token itself
    async def verify_token(self, token):
        try:
            c = jwt.decode(token, signing_key.public_key(), algorithms=["RS256"], issuer=ISSUER,
                           options={"verify_aud": False})      # audience is checked via `resource` below
        except jwt.PyJWTError:
            return None
        return AccessToken(token=token, client_id=c["client_id"], scopes=c["scope"].split(),
                           expires_at=c["exp"], resource=c["aud"], subject=c["sub"])

srv = MCPServer("notes", log_level="WARNING", token_verifier=JWTVerifier(), auth=AuthSettings(
    issuer_url=ISSUER, resource_server_url=RESOURCE, required_scopes=["notes:read"], validate_token_resource=True))
@srv.tool()
def search(query: str) -> list[str]:
    """Use to find notes."""
    return ["Call Priya"]

def mint(**over):
    now = int(time.time())
    c = {"iss": ISSUER, "aud": RESOURCE, "sub": "user-42", "client_id": CLIENT_ID, "scope": "notes:read",
         "iat": now, "exp": now + 600, **over}
    return jwt.encode(c, signing_key, algorithm="RS256")

body = {"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "search", "arguments": {"query": "x"},
        "_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", "io.modelcontextprotocol/clientCapabilities": {}}}}
H = {"Accept": "application/json, text/event-stream", "Content-Type": "application/json",
     "MCP-Protocol-Version": "2026-07-28", "Mcp-Method": "tools/call", "Mcp-Name": "search"}
app = srv.streamable_http_app(json_response=True, transport_security=TransportSecuritySettings(
    enable_dns_rebinding_protection=True, allowed_hosts=["notes.example.com"]))
with TestClient(app, base_url="https://notes.example.com") as c:
    r = c.post("/mcp", content=json.dumps(body), headers=H)
    print(f"no token                 -> {r.status_code}  WWW-Authenticate: {r.headers.get('www-authenticate')}")
    meta = c.get("/.well-known/oauth-protected-resource/mcp")
    print(f"protected-resource metadata -> {meta.status_code} {meta.json()}\n")
    cases = [("token from the real flow", client_flow()["access_token"]),
             ("token for another server", mint(aud="https://calendar.example.com/mcp")),
             ("expired token", mint(iat=1, exp=2)),
             ("token without notes:read", mint(scope="notes:write")),
             ("token from another issuer", jwt.encode({"iss": "https://evil-as.example", "aud": RESOURCE,
                                                        "exp": int(time.time()) + 600}, signing_key, algorithm="RS256"))]
    for label, tok in cases:
        r = c.post("/mcp", content=json.dumps(body), headers={**H, "Authorization": f"Bearer {tok}"})
        detail = r.json()["result"]["content"][0]["text"] if r.status_code == 200 else \
                 (r.headers.get("www-authenticate") or r.text)[:95]
        print(f"{label:<25}-> {r.status_code}  {detail}")

Reading this output

No token: a challenge that says where to go. The SDK answers 401 with WWW-Authenticate: Bearer ... resource_metadata="https://notes.example.com/.well-known/oauth-protected-resource/mcp". Fetching that URL returns RFC 9728 metadata: the resource, its authorization server and its scopes. That is how a client discovers whom to ask.

The token from the real flow works. HTTP 200 and the tool's result.

Wrong audience, expired and foreign-issuer tokens are rejected with 401. All three are well-formed, and two are even signed by the right key; the checks on issuer, audience (the SDK's validate_token_resource) and expiry still refuse them.

Too little scope gets 403, not 401. A valid token with only notes:write gets insufficient_scope and "Required scope: notes:read": the client should run a new authorization asking for that scope (step-up), not retry with the same token.

Idea 12 · Request the smallest current scope

Start with the scope needed now. If a later tool requires more, the server returns 403 with an authoritative scope challenge:

WWW-Authenticate: Bearer error="insufficient_scope",
  scope="notes:delete",
  resource_metadata="https://notes.example.com/.well-known/oauth-protected-resource/mcp"

The client explains the new permission, obtains consent, performs a new authorization flow with the combined scope set, and retries the MCP request with a new JSON-RPC id.

Do not assume the challenged scope is a subset of scopes_supported. The challenge is authoritative for the current operation.

Idea 13 · Authorization and the stateless MCP wire

An authorized tool call still carries the complete current request envelope:

POST /mcp
Authorization: Bearer <access-token>
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: notes.delete

{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "notes.delete",
    "arguments": {"id": "note-7"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "oauth-lesson-client",
        "version": "1.0.0"
      }
    }
  }
}

The token authorizes the principal. The request metadata negotiates protocol behavior. Neither substitutes for the other.

Validate the wire in a fixed order: JSON-RPC and metadata types, header and body equality, then protocol support. A routing or version-header mismatch returns HTTP 400 with -32020. If header and body agree on an unsupported version, return HTTP 400 with -32022 and data exactly {"supported":["2026-07-28"],"requested":"<actual>"}. An unknown method returns HTTP 404 with -32601.

Every request error, including 401 invalid token and 403 insufficient scope, is a JSON-RPC error envelope with the original request id. Structured recovery information belongs in optional error data; WWW-Authenticate remains an HTTP response header. A notification has no id, so it receives no JSON-RPC body. An accepted HTTP notification returns 202 with an empty body.

The server implements server/discover and advertises tools, so it also implements the mandatory tools/list method. Its tool descriptors have stable names, descriptions, and object-root inputSchema values. The list is deterministic and returns resultType, server identity metadata, a bounded ttlMs, and cacheScope. Discovery and a user-independent tool list can be available before authorization. Apply normal policy and private caching if either varies by principal.

Idea 14 · No token passthrough

An MCP server must not forward the client's MCP access token to a downstream API. Obtain a separate downstream token with the right audience or use an explicit token-exchange design. Audience validation only works when services refuse tokens minted for someone else.

Idea 15 · Refresh tokens

Refresh tokens are optional. When issued, store them confidentially and key them by issuer and resource. Do not assume they exist. Rotate them when the authorization server supports rotation and detect reuse of invalidated values.

Use it: the same idea with real libraries

Map the simulator objects to production components:

  • ResourceServer.protected_resource_metadata becomes the RFC 9728 endpoint.
  • AuthorizationServer.metadata becomes RFC 8414 or OpenID Connect discovery.
  • Client.enroll becomes CIMD resolution plus an explicit DCR compatibility branch.
  • Issuer-minted client credentials and tokens_by_issuer_resource become encrypted records. A CIMD URL may remain portable while its authorization results remain issuer-bound.
  • ResourceServer.handle becomes middleware that validates current MCP headers, token, and tool scope before dispatch while keeping every request error in a matching JSON-RPC envelope.

Industry practice
What's current (2024–2026)
  • MCP authorization in 2026-07-28: OAuth 2.1 with PKCE, RFC 9728 protected-resource metadata, RFC 8707 resource indicators, RFC 9207 iss validation (clients must check a present iss), Client ID Metadata Documents preferred, Dynamic Client Registration deprecated (with application_type required when used), credentials bound to their issuer.
  • SDK support: the Python SDK 2.x MCPServer(token_verifier=..., auth=AuthSettings(...)) serves protected-resource metadata and returns WWW-Authenticate challenges with resource_metadata and insufficient_scope, as shown.
  • Identity providers used with remote MCP servers include Auth0, Okta, Microsoft Entra ID, Keycloak and WorkOS; clients like Claude and VS Code run the browser sign-in flow.
  • Step-up: servers request more scope only when an operation needs it (insufficient_scope with the required scope), instead of asking for everything up front.

Sources: MCP authorization, MCP 2026-07-28 changelog, RFC 9207, RFC 9728, RFC 7636 (PKCE).

Recap
What to keep from this lesson
  • Three roles: client, MCP resource server, authorization server.
  • Discover via protected-resource metadata; prefer CIMD; DCR only as a fallback.
  • Authorization code with S256 PKCE, single-use codes, and resource in both requests.
  • Check iss before redeeming; bind credentials and tokens to their issuer.
  • The MCP server checks signature, issuer, audience, expiry and scope on every request.
  • Never pass a user's token through to another service.

Given a remote HTTP MCP server and its tool list, design the complete authorization boundary.

## Required inputs

- Canonical MCP resource URI and protected-resource metadata location.
- Allowed authorization server issuers.
- Client runtime: native or web, with exact redirect URIs.
- Tool-to-scope mapping and consequential operations.
- Token, refresh, and credential-storage constraints.
- Legacy authorization servers that lack CIMD, if any.

## Produce

1. Resource metadata. Draft RFC 9728 `resource`, `authorization_servers`, and `scopes_supported`. Preserve the resource path after the well-known segment, such as `https://notes.example.com/.well-known/oauth-protected-resource/mcp` for `https://notes.example.com/mcp`.
2. Issuer policy. State exact allowed issuers, metadata validation, change handling, and RFC 9207 `iss` comparison.
3. Enrollment. Use pre-registration when available, otherwise prefer a Client ID Metadata Document. Its HTTPS URL with a path is the `client_id`; require exact redirect URIs and treat display metadata as untrusted. `application_type` is optional here.
4. DCR fallback. If required, label it deprecated, declare `application_type`, and define the precise condition that allows fallback. Do not downgrade after a generic CIMD security failure.
5. Credential keys. Store pre-registered and DCR credentials under issuer and tokens under `(issuer, resource)`. Forbid reuse across issuers. State that a self-hosted CIMD URL is portable and does not require DCR re-registration when a trusted issuer changes.
6. PKCE flow. Require S256, exact redirect URI, authorization response issuer validation, and the same resource in authorization and token requests.
7. Scope model. Map every tool to its minimum scope. Treat the current `WWW-Authenticate` scope challenge as authoritative.
8. Step-up experience. Identify the additional scope, user explanation, consent point, new authorization, and retry with a fresh MCP request id.
9. Resource-server checks. Implement advertised `tools/list` with valid object-root schemas, deterministic order, result type, server identity, and cache hints. Validate issuer, audience, expiry, scope, current MCP headers, and request metadata before tool dispatch.
10. Token hygiene. Bearer header only, no query token, no token passthrough, confidential refresh storage, and rotation plan.
11. Error contract. Preserve every request id in a JSON-RPC error envelope, including OAuth failures. Require HTTP 400 `-32020` for header mismatch before the HTTP 400 `-32022` version support check, exact supported and requested data, HTTP 404 `-32601` for unknown methods, and 202 with an empty body for accepted notifications.
12. Transport boundary. Label parsed-body examples as in-process protocol models and attach them to Lesson 09's complete Streamable HTTP adapter for JSON Content-Type and JSON plus SSE Accept validation.

## Hard rejects

- DCR presented as the preferred new enrollment mechanism.
- DCR without `application_type`.
- Reusing issuer-minted registration credentials, access tokens, or refresh tokens after the issuer changes. A self-hosted CIMD URL is the portable exception, not an issuer-minted secret.
- Normalizing an authorization response `iss` before comparison.
- Missing PKCE S256 or missing `resource` in authorization and token requests.
- Accepting a token for another audience or forwarding the MCP token downstream.
- Using `clientInfo`, `serverInfo`, capabilities, or a removed protocol session as authentication.
- Adding OAuth to local stdio solely to imitate remote HTTP.
- Dropping the protected resource path when constructing the RFC 9728 metadata URL.
- Returning a plain-text or ad hoc object for an MCP request error instead of a JSON-RPC envelope with the same id.

## Output format

Return sections named Resource, Issuers, Enrollment, Credential Store, PKCE Flow, Scope Matrix, Step-Up, Server Validation, Token Hygiene, and Compatibility. End with the exact event that forces issuer review and, for issuer-minted clients, re-enrollment.

Exercises

  1. Add refresh-token rotation and reject reuse of the previous refresh token.
  2. Add an issuer allowlist. On issuer change, reuse only a portable CIMD URL; refuse all prior issuer-minted credentials and tokens.
  3. Add an expiry to authorization codes and confirm a late exchange fails.
  4. Build a web client variant with a remote HTTPS redirect and compare its DCR metadata to the native client.
  5. Add a second resource under the same issuer. Confirm its access token cannot be used at the first resource.

Solutions

SolutionP1 · None of them

None of them. The stolen code fails PKCE (the attacker cannot produce the verifier whose hash the server stored), the second redemption fails because codes are single-use, and the mix-up response is refused by the client itself because its iss does not equal the issuer the client started with. Only the first, normal redemption produced a token.

SolutionB1 · One token, four doors

The backends accept a token that was never meant for them. Because they check only signature and expiry, the user's gateway token works at all three, so a compromised or buggy gateway, or anyone who steals that one token, can call every backend directly with the user's full rights. The audit logs show the user, not the gateway, and the backends cannot tell which client actually acted. It also violates the consent the user gave: they approved access to the gateway's resource, not to three other servers.

What each hop should do:

  • Each backend validates audience: accept only tokens whose aud (resource) is its own canonical URI, plus issuer, expiry and scope.
  • The gateway gets its own tokens: for each backend, obtain a token with that backend as the audience, by token exchange (RFC 8693) or the gateway's own client credentials with delegated scopes, and never forward the inbound token.
  • Scopes shrink at each hop to what that backend call needs.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designYou deploy a remote MCP server that accepts tokens from two authorization servers, one for staff and one for partners. Design the client enrollment, the per-request token validation and the key handling so that three things hold: a token minted for a sibling MCP server is refused, a signing key rotation causes no outage, and a client steered to a hostile token endpoint never hands over its authorization code.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Publish RFC 9728 protected-resource metadata that names both issuers, and treat that list as the issuer allow-list. Enroll a client with its pre-registered credentials when it has an explicit relationship with that issuer, otherwise with a Client ID Metadata Document when the issuer advertises support, and use deprecated dynamic registration only as an explicit fallback with the correct application_type. On every request validate the pinned iss, an aud equal to this server's canonical resource URI, exp and the scope the tool needs; answer 401 for an invalid token and 403 with insufficient_scope for a valid token that lacks the scope. Refresh the JWKS on a schedule and re-fetch once on an unknown kid, and let the client record the issuer before it redirects and compare the RFC 9207 iss in the authorization response exactly before it redeems the code.

Discovery and the deployment gate.

The client starts from the MCP resource URL, fetches the RFC 9728 document, selects an advertised authorization server and fetches its RFC 8414 metadata. Keep the resource path when you build the well-known URL: a resource served at the path /mcp resolves to /.well-known/oauth-protected-resource/mcp on the same host. Before trusting an issuer, check the metadata mechanically: S256 must be advertised or you stop, response_types_supported is ["code"], and at least one enrollment path exists.

Enrollment priority.

Path When Note
pre-registered client an explicit relationship with that issuer exists credentials keyed by issuer
Client ID Metadata Document the issuer advertises support the HTTPS URL with a path is the client_id and the document's client_id equals it
dynamic registration neither of the above deprecated; declare native or web; never a silent fallback after a CIMD failure

Fetching a CIMD is an SSRF-sensitive operation for the issuer. Store issuer-minted credentials under the exact issuer and access tokens under (issuer, resource). If discovery moves from one issuer to another, re-evaluate trust and never send the first issuer's secret, registration token or tokens to the second. A CIMD URL is portable because it is self-hosted, not minted.

Validation on every request.

token.iss in protected_resource_metadata.authorization_servers
token.aud == canonical MCP resource URI
token.exp in the future
required scope present

A missing aud is a rejection, never a wildcard. The replay walkthrough: a token for notes.example.com presented to tasks.example.com passes the issuer check and fails the audience check, and the server returns 401 with WWW-Authenticate: Bearer error="invalid_token" and a resource_metadata pointer. The spec calls this access-token privilege restriction. Never forward the inbound token to a downstream API; obtain a separate downstream token.

Rotate at the issuer, refresh at the server.

The issuer rotates by publishing the next key before retiring the previous one, so two keys at once is the steady state. The resource server only refreshes: a scheduled job overwrites cache[issuer] = {keys, fetched_at}, and a token with an unknown kid triggers one synchronous re-fetch and then fails if the key is still missing. Never wire the cache miss to rotate-and-mint: the new key still does not match, and attacker-chosen kid values become a key-creation denial of service.

The mix-up defense lives in the client.

A hostile authorization server can steer a client to redeem an honest issuer's code at the attacker's token endpoint. PKCE does not stop it, because the client hands its code_verifier to whatever endpoint it was steered to. The client records the expected issuer before redirecting and compares the returned iss as a plain string, with no case folding, slash or port normalization, before it sends the code anywhere.

Declared failure policy.

Failure Behavior
scheduled JWKS refresh fails, known kid still cached continue only within a declared stale-on-error window
unknown kid and the one refresh fails reject
introspection unavailable for an opaque token fail closed; never convert a network error into active: true
issuer metadata changes unexpectedly stop new enrollment and token acquisition

Plausible wrong answers.

  • "Any token from our own identity provider is fine." A token minted for a sibling server passes the issuer check; only the audience check refuses it.
  • "Fetch the JWKS once at boot." The validator rejects every token after the next rotation until a restart; refresh on a schedule and once on a miss.
  • "Fall back to dynamic registration when CIMD validation fails." A security failure must not select a weaker enrollment path; the fallback is an explicit configuration decision.

Follow-ups an interviewer may ask.

  • (level 3) Why is a per-connection token check not enough? Expected: there is no protocol session; every request carries its own bearer token and is validated on its own.
  • (level 3) A scope step-up is needed for one tool. What does the server return? Expected: 403 with WWW-Authenticate: Bearer error="insufficient_scope" naming the scope and the resource_metadata URL; the client obtains consent and retries with a new request id.
  • (level 4) Two concurrent step-ups produce two tokens with different scopes. Which does the validator use? Expected: the token presented on the request, never a lookup of "the user's current scope", which would open a time-of-check race.
  • (level 4) The partner issuer changes its issuer URL in discovery. What may the client reuse? Expected: only a portable CIMD URL; prior issuer-minted credentials, registration tokens and access tokens are refused, and the client re-enrolls.
