In plain words first
The idea in one line

A mid-sized e-commerce agent's monthly LLM cost jumps from $1,200 to $4,800 after its team enables an "order-tracking" skill. That is not a pricing bug. That is an agent that found a new loop and kept spending inside it. The defence is a stack of limits: per-request max_tokens, per-task token and dollar budgets, per-day/month caps, iteration caps, tiered model routing, prompt caching, context windowing, HITL checkpoints on expensive actions, kill switches on budget breach. Anthropic's Claude Agent SDK ships two of them directly, max_turns and max_budget_usd; Microsoft's open-source Agent Governance Toolkit (April 2, 2026) adds policy enforcement, circuit breakers and a kill switch around agents. Financial velocity limits — e.g. cut access on >$50 in 10 minutes — catch loops faster than monthly caps.

The problem

In plain words first

Every turn of an agent costs money, and an agent stuck in a loop keeps spending until something stops it. A cost governor is that something: a set of limits at different scales, such as tokens per call, turns per session, dollars per session, dollars per minute and dollars per month. Each limit catches a different failure, so you need several. Reliability and cost engineering for agents are covered in Lessons 14.139 and 14.142 (linked above). This lesson runs the lesson's governor on more failure shapes, then meters a real model's agent loop to see which caps would fire.

Autonomous agents spend real money on every turn. A chatbot's bad output is a bad reply; an agent's bad loop is a bill. The industry-documented term for the failure mode is "Denial of Wallet" — the agent keeps reasoning, keeps tool-calling, keeps billing, and nothing stops it because nothing was designed to.

The fix is not one number. It is a stack of limits at different time scales and granularities: per-request, per-task, per-hour, per-day, per-month. A well-designed stack catches a runaway loop within minutes, a slow leak within hours, and a bad release within a day. The same stack keeps a budget at all when the agent is long-horizon and autonomous.

This is an engineering lesson: the math is trivial, the discipline is where teams fail. The limits below are standard practice; the Claude Agent SDK exposes two of them as options, and the rest you build around the agent.

Idea 1 · The cost-governor stack

  1. max_tokens per request. Simple. Prevents any one call from emitting an unbounded completion.
  2. Per-task token budget. Across the whole run, do not exceed N tokens. Hard stop at the cap.
  3. Per-task dollar budget. Same as tokens but in currency. max_budget_usd in Claude Code.
  4. Per-tool call cap. No more than N WebFetch calls, N shell_exec calls, etc.
  5. Iteration cap (max_turns). Total agent loop iterations; prevents infinite reasoning loops.
  6. Per-minute / per-hour / per-day / per-month cap. Rolling windows. Catches leaks at different time scales.
  7. Financial velocity limit. E.g., "if spend exceeds $50 in 10 minutes, cut access." Catches loop-based burn before monthly caps fire.
  8. Tiered model routing. Default to a smaller model; escalate to a larger one only when a classifier judges the task warrants it.
  9. Prompt caching. System prompt and stable context stored in provider cache; re-sent tokens are billed at a fraction of the normal input price (a tenth on Anthropic's API, after a one-time write that costs more).
  10. Context windowing. Compaction / summarization to keep the active context below a threshold; direct token-cost reduction.
  11. HITL checkpoints on expensive actions. Before an action known to be expensive (long tool call, large download, a costly model upgrade), require a human tap.
  12. Kill switch on budget breach. Session aborts when any cap fires. Cap is recorded; requires a separate re-enable path.

Idea 2 · Why the stack, not one cap

A single monthly cap catches a runaway agent only after the wallet is gone. A single per-request cap catches nothing at the session level. Different failure modes require different time scales:

  • Runaway loop (agent stuck in a 5-second retry): caught by velocity limit.
  • Slow leak (agent doing ~2x expected work per task): caught by daily cap.
  • Bad release (new version uses 5x tokens): caught by weekly / monthly cap.
  • Legitimate surge (real demand, not a bug): caught by hour / day cap with clear log.

Idea 3 · A harness budget surface

The Claude Code Agent SDK exposes (public docs):

  • max_turns — iteration cap.
  • max_budget_usd — dollar cap; session aborts on breach.
  • allowed_tools / disallowed_tools — tool allowlist and denylist.
  • Hook points before tool use for custom cost-accounting.

Combine with the permission-mode ladder (Lesson 15.10). An auto-mode session without max_budget_usd is ungoverned autonomy: auto mode's classifier judges whether an action is safe, not what it costs. Both caps are off unless you set them, and a session that hits one ends with an error_max_turns or error_max_budget_usd result.

Idea 4 · EU AI Act, OWASP Agentic Top 10

Microsoft's Agent Governance Toolkit maps its controls to the OWASP Top 10 for Agentic Applications and to regulatory frameworks including the EU AI Act. For a high-risk system under the AI Act, record-keeping (Article 12) and human oversight (Article 14) are legal duties. Spending caps are not required by law, but they sit in the same control layer as the logs and the oversight.

Idea 5 · The $1,200 → $4,800 pattern

The story as the lesson tells it (we could not find it in Microsoft's published material, so treat it as an illustration): an e-commerce agent whose monthly cost quadrupled after a new tool was added. The tool allowed the agent to poll order status during every session. No loop detection. No per-tool cap. No alert on week-over-week growth. The fix was a per-tool cap plus a daily-growth alert. The template holds whatever its source: every new tool surface is a new potential loop; every new tool needs its own cap and its own alert. The second code block below rebuilds this month and shows which layers notice.

The same idea as a formula

Each layer has its own stopping time. A run stops at T=minℓ​Tℓ​, the first layer ℓ to fire. Which layer that is depends on the failure's shape, which is why one cap is not enough.

A velocity limit compares a rate to a threshold. A turn costing c dollars every s seconds spends at

r=s60c​ dollars a minute,
and the limit fires when r>v. The lesson's normal turn gives r0​=60×0.0075/30=0.015, and its limit is v=0.03=2r0​. Anything that doubles the normal rate trips it, a loop or a busy day.

Re-sent context grows quadratically. If turn 1 sends T0​ input tokens and each turn adds Δ, turn k sends T0​+(k−1)Δ, and n turns send

k=1∑n​(T0​+(k−1)Δ)=nT0​+Δ2n(n−1)​.
A loop's cost per turn rises as it runs. Caching bills the repeated prefix at about 0.1×, which cuts the quadratic term but does not remove it.

Worked example
Counting one month
  • The fleet: 270 sessions a day, 20 turns each, 2,500 tokens a turn at the lesson's price of 0.003 dollars per 1,000 tokens. One session costs 20×2.5×0.003=0.15 dollars, a day 40.50, a month about 1,215.
  • A polling tool adds 60 turns to every session. One session costs 80×2.5×0.003=0.60, a day 162, a month 4,860: the same quadrupling.
  • Per session nothing looks wrong: 80 turns is under the 200-turn cap, 0.60 is far under the 50-dollar session cap, and the spend rate per minute has not changed.
  • A daily alert compares today with the last 7 days: day 11 spends 162 against an average of 40.50, four times as much, so it fires the first day.
Check your mental model
  • ✗ "A tight velocity limit only stops loops."
    ✓ It stops anything that doubles the normal spend rate. The lesson's limit also ends a legitimate session running at 3x pace after 2 turns.
  • ✗ "Per-session caps protect the monthly bill."
    ✓ A tool that adds polling to every session raises the bill 4x while every session stays inside every cap.
  • ✗ "A loop costs the same every turn."
    ✓ Each turn re-sends the whole context, so input grows every turn and the total grows quadratically.
  • ✗ "Prompt caching makes re-sent tokens free."
    ✓ Cached reads cost about a tenth of the input price, and the first write costs more than a normal send.

# The lesson's simulate() and Governor (imported from main.py) on three more trajectories, then a month of a whole
# fleet of sessions. Part 1 asks which layer fires first, and whether one fires on traffic that is not a bug. Part 2
# adds a tool that makes every session poll, the shape of the $1,200 -> $4,800 story, and asks which layer notices.
# Deterministic arithmetic; runs in under a second.
import main
from main import Governor, simulate, NORMAL_TURN_TOKENS, DOLLARS_PER_KTOK

PROFILES = {   # name: (tokens on turn t, seconds per turn)
    "polling loop at turn 30": (main.turn_cost, 30),
    "bad release, 5x tokens":  (lambda t: 5 * NORMAL_TURN_TOKENS, 30),
    "busy day, 3x the pace":   (lambda t: NORMAL_TURN_TOKENS, 10),
    "slow leak, 1.8x tokens":  (lambda t: int(1.8 * NORMAL_TURN_TOKENS), 30),
}
print("1. one session, the lesson's layered stack")
for name, (cost, pace) in PROFILES.items():
    main.turn_cost = cost
    simulate(Governor(seconds_per_turn=pace), name)
main.turn_cost = PROFILES["polling loop at turn 30"][0]

print("\n2. a fleet for 30 days: 270 sessions a day, 20 turns each; a polling tool ships on day 11")
SESSIONS, TURNS, PACE = 270, 20, 30
POLL_TURNS = 60                                   # the new tool: each session polls order status 60 more times
def session(day, per_tool_cap=None):
    polls = POLL_TURNS if day >= 11 else 0
    if per_tool_cap is not None:
        polls = min(polls, per_tool_cap)
    turns = TURNS + polls
    dollars = turns * NORMAL_TURN_TOKENS / 1000 * DOLLARS_PER_KTOK
    rate = NORMAL_TURN_TOKENS / 1000 * DOLLARS_PER_KTOK / (PACE / 60)    # $/min, the same every turn
    g = Governor()
    fired = [n for n, hit in (("max_turns", turns >= g.max_turns), ("max_budget_usd", dollars >= g.max_budget_usd),
                              ("velocity_limit", rate > g.velocity_usd_per_min)) if hit]
    return dollars, turns, fired

for label, cap in (("no per-tool cap", None), ("per-tool cap: 3 polls a session", 3)):
    daily, fired_any, spent, cap_day, alert_day = [], set(), 0.0, None, None
    for day in range(1, 31):
        d, turns, fired = session(day, cap)
        fired_any |= set(fired)
        daily.append(SESSIONS * d)
        spent += daily[-1]
        if cap_day is None and spent >= 2000:
            cap_day = day
        if alert_day is None and day > 7 and daily[-1] > 1.5 * sum(daily[-8:-1]) / 7:
            alert_day = day
    print(f"   {label}: session {turns} turns ${d:.2f}; per-session layers fired: {sorted(fired_any) or 'none'}")
    print(f"      day 1-10 ${sum(daily[:10]):,.0f}, day 11-30 ${sum(daily[10:]):,.0f}; as a 30-day month: "
          f"${30 * daily[0]:,.0f} -> ${30 * daily[-1]:,.0f}")
    when = lambda d: f"on day {d}" if d else "never"
    print(f"      monthly cap $2,000 trips {when(cap_day)}; alert 'today > 1.5x the last 7 days' fires {when(alert_day)}")

Reading this output

The velocity limit catches the loop, the bad release and a busy day alike. The polling loop stops at turn 39 after 0.46 dollars, as in the lesson. A release that uses 5x the tokens stops at turn 2. So does a legitimate busy day at 3x the pace with normal turns: the lesson's limit of 0.03 dollars a minute is only twice the normal rate, so any session running twice as fast trips it.

A slow leak slips under it. At 1.8x the tokens, the rate is 0.027 dollars a minute, just under the limit. Only the 200-turn cap stops it, which every long session hits anyway.

Per-session layers miss a fleet-wide change. With the polling tool, a session runs 80 turns and costs 0.60 dollars, and no per-session layer fires. The month goes from 1,215 to 4,860 dollars at the new rate. A 2,000-dollar monthly cap trips on day 20, ten days late. An alert on "today above 1.5x the last 7 days" fires on day 11, the first day.

A per-tool cap removes most of the cost. Capping polls at 3 a session keeps sessions at 23 turns and 0.17 dollars, and the month at 1,397 dollars. That is 15% more than before, so the growth alert stays quiet.

# This block continues from the one above: a real agent loop, metered. Qwen2.5-0.5B-Instruct (greedy, CPU) answers
# customer requests with two tools, check_order and reply_to_customer, then with an order-tracking skill's instruction
# added. The order system never changes its answer, and its message invites another check.
# Then the skill as a poller that re-runs the agent until the status is final. Real token counts are priced, and each
# cap is replayed on the trace to see where it would have stopped. About 2 minutes.
import json, os, re, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def fn(name, desc, **params):
    return {"type": "function", "function": {"name": name, "description": desc, "parameters": {
        "type": "object", "properties": {k: {"type": "string", "description": v} for k, v in params.items()}, "required": list(params)}}}
TOOLS = [fn("check_order", "Look up the shipping status of an order", order_id="the order number"),
         fn("reply_to_customer", "Send the final answer to the customer and end the task", message="the reply")]
FORCED = '<tool_call>\n{"name": "'
def step(messages):
    ids = tok.apply_chat_template(messages, tools=TOOLS, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    ids = torch.cat([ids, tok(FORCED, return_tensors="pt")["input_ids"]], dim=1)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=60, do_sample=False)
    text = FORCED + tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)
    m = re.search(r"<tool_call>\s*(\{.*?\})\s*(?:</tool_call>|$)", text, re.S)
    try:
        d = json.loads(m.group(1)); name, args = d["name"], d.get("arguments", {}) or {}
    except (AttributeError, json.JSONDecodeError, KeyError, TypeError):
        name, args = "malformed", {}
    return name, args, ids.shape[1], out.shape[1] - ids.shape[1]

STATUS = "order 4417: status pending (label created). Tracking updates every few minutes; check again for the latest status."
SKILL = (" Order-tracking skill: only reply to the customer once the order status is final (shipped or delivered);"
         " while it is pending, keep checking.")
def run(task, skill=False, max_turns=20):
    messages = [{"role": "system", "content": "You are a support agent for an online shop. Use the tools to answer the customer."
                 + (SKILL if skill else "")},
                {"role": "user", "content": task}]
    trace = []                                 # (tool, args, input tokens, output tokens)
    for turn in range(1, max_turns + 1):
        name, args, n_in, n_out = step(messages)
        trace.append((name, json.dumps(args, sort_keys=True), n_in, n_out))
        if name == "reply_to_customer":
            break
        result = STATUS if name == "check_order" else "error: unknown tool"
        messages += [{"role": "assistant", "content": "", "tool_calls": [{"type": "function", "function": {"name": name, "arguments": args}}]},
                     {"role": "tool", "name": name, "content": result}]
    return trace

for task, skill in (("Has my order 4417 shipped yet?", False), ("Please tell me as soon as my order 4417 ships.", False),
                    ("Has my order 4417 shipped yet?", True)):
    trace = run(task, skill)
    calls = [t[0] for t in trace]
    print(f"{task!r}{' + skill' if skill else ''}: {len(trace)} turns, " + ", ".join(f"{c} x{calls.count(c)}" for c in dict.fromkeys(calls))
          + ("" if calls[-1] == "reply_to_customer" else ", still going when the observation stopped"))

print("\nthe skill as a scheduled poller: it re-runs the agent every 5 minutes until the status is final")
IN, OUT = 3 / 1e6, 15 / 1e6                    # $ per token: $3 and $15 per million (a Sonnet-class list price)
hour = [run("Has my order 4417 shipped yet?") for _ in range(12)]
cost = [sum(t[2] * IN + t[3] * OUT for t in tr) for tr in hour]
replies = [json.loads(tr[-1][1]).get("message", "") for tr in hour]
print(f"   one hour: 12 sessions of {len(hour[0])} turns, {sum(len(tr) for tr in hour)} model calls, ${sum(cost):.4f}; "
      f"the customer got {len(replies)} replies, {len(set(replies))} distinct")
print(f"   one order for a day: ${sum(cost) * 24:.2f}; 270 pending orders: ${sum(cost) * 24 * 270:,.0f} a day")

print("\nreplaying each cap on that hour:")
cum = [sum(cost[:k + 1]) for k in range(12)]
RULES = {"max_turns = 8 (per session)": lambda k: len(hour[k]) >= 8,
         "max_budget_usd = $0.02 (per session)": lambda k: cost[k] >= 0.02,
         "velocity $0.03/min (per session, 1 min)": lambda k: cost[k] / 1 > 0.03,
         "check_order(4417) at most 3 an hour (per order)": lambda k: k + 1 > 3,
         "same reply sent 3 times (per customer)": lambda k: replies[:k + 1].count(replies[k]) >= 3}
for label, rule in RULES.items():
    at = next((k + 1 for k in range(12) if rule(k)), None)
    print(f"   {label:<48} " + (f"fires at session {at}, after ${cum[at - 1]:.4f}" if at else "never fires"))

t0, step_up = hour[0][0][2], hour[0][1][2] - hour[0][0][2]
print(f"\nif the agent had looped inside one session instead: input starts at {t0} tokens and grows {step_up} a turn,")
for n in (10, 50, 200):
    tokens = n * t0 + step_up * n * (n - 1) // 2
    new = t0 + (n - 1) * step_up                       # tokens sent for the first time: written to the cache at 1.25x
    print(f"   {n:>3} turns: {tokens:>9,} input tokens, ${tokens * IN:.3f}; with the prefix cached (reads at 0.1x) ${(new * 1.25 + (tokens - new) * 0.1) * IN:.3f}")

Reading this output

This model does not loop by itself. In all three runs, including the one with the skill's "keep checking while pending" instruction, it calls check_order once and replies. A stronger instruction-follower is more likely to obey "keep checking" literally, so do not count on this.

The loop came from the code around it. Re-run every 5 minutes, the agent makes 24 model calls in an hour for 0.032 dollars, and the customer gets 12 replies, all identical. At that rate one order costs 0.76 dollars a day, and 270 pending orders cost about 206 dollars a day.

Per-session caps see nothing. Each session is 2 turns and under a cent, so max_turns, max_budget_usd and a per-session velocity limit never fire. The caps that fire are scoped to the order or the customer: at most 3 checks of order 4417 an hour stops it at session 4, and "the same reply 3 times" at session 3.

Inside one session, a loop costs more every turn. Input starts at 264 tokens and grows 67 a turn, so 200 turns send 1.39 million input tokens, 4.16 dollars. With the repeated prefix read from the cache at 0.1x, the same loop costs about 0.46 dollars.

code/main.py simulates an agent run with and without a layered cost-governor stack. The simulated agent drifts into a polling loop after some turns; the layered stack catches it within the velocity window while a single monthly cap would not fire until days later.

The whole of code/main.py follows in parts. Each part runs on this page, in order, in one Python session; the last part does what python3 code/main.py does.

Part 1 of 4 · turn_cost, Governor, Run

"""Layered cost-governor simulator — stdlib Python.

Simulates an agent that drifts into a polling loop after 30 turns. Compares
three configurations:

  1. no caps: unbounded spend
  2. monthly cap only: catches eventually, spends a lot first
  3. layered stack: per-request + iteration + velocity limit + monthly cap

Metrics: turns executed, total tokens, total dollars, trigger that fired.
"""

from __future__ import annotations

from dataclasses import dataclass, field


# ---------- Simulated run profile ----------

NORMAL_TURN_TOKENS = 2_500
LOOP_TURN_TOKENS = 8_000
LOOP_STARTS_AT = 30

# $/token (input+output blended) for a Sonnet-class model, mid-2026 rates
DOLLARS_PER_KTOK = 0.003


def turn_cost(turn: int) -> int:
    return LOOP_TURN_TOKENS if turn >= LOOP_STARTS_AT else NORMAL_TURN_TOKENS


# ---------- Governor ----------

@dataclass
class Governor:
    max_tokens_per_request: int = 10_000
    max_turns: int = 200
    max_budget_usd: float = 50.0
    velocity_usd_per_min: float = 0.03       # cut off above this rolling rate
    velocity_window_min: float = 10.0
    monthly_cap_usd: float = 500.0

    enable_request_cap: bool = True
    enable_iter_cap: bool = True
    enable_velocity: bool = True
    enable_session_cap: bool = True
    enable_monthly_cap: bool = True

    # per-minute turn rate (seconds per turn) for the simulator
    seconds_per_turn: float = 30.0


@dataclass
class Run:
    turns: int = 0
    tokens: int = 0
    dollars: float = 0.0
    history: list[tuple[float, float]] = field(default_factory=list)  # (minute, dollars-at-that-minute)
    stopped_by: str = ""


EPSILON_MIN = 1e-9

def velocity_exceeded(run: Run, gov: Governor, now_min: float) -> bool:
    if not run.history:
        return False
    cutoff = now_min - gov.velocity_window_min
    window = [(t, d) for (t, d) in run.history if t >= cutoff]
    if not window:
        return False
    start_min, start_dollars = window[0]
    window_dollars = run.dollars - start_dollars
    # Use the actual elapsed time inside the window, not the nominal
    # window width. During warm-up (now_min < velocity_window_min) this
    # stops the rate being under-reported.
    elapsed = max(now_min - start_min, EPSILON_MIN)
    rate = window_dollars / elapsed
    return rate > gov.velocity_usd_per_min


def simulate(gov: Governor, label: str) -> Run:
    run = Run()
    now_min = 0.0

    for turn in range(1, 10_001):
        tok = turn_cost(turn)
        if gov.enable_request_cap and tok > gov.max_tokens_per_request:
            tok = gov.max_tokens_per_request
        run.turns = turn
        run.tokens += tok
        run.dollars += (tok / 1000.0) * DOLLARS_PER_KTOK
        now_min += gov.seconds_per_turn / 60.0
        run.history.append((now_min, run.dollars))

        if gov.enable_iter_cap and turn >= gov.max_turns:
            run.stopped_by = "max_turns"
            break
        if gov.enable_session_cap and run.dollars >= gov.max_budget_usd:
            run.stopped_by = "max_budget_usd"
            break
        if gov.enable_velocity and velocity_exceeded(run, gov, now_min):
            run.stopped_by = "velocity_limit"
            break
        if gov.enable_monthly_cap and run.dollars >= gov.monthly_cap_usd:
            run.stopped_by = "monthly_cap"
            break

    if not run.stopped_by:
        run.stopped_by = "ran out of simulated turns"

    print(f"  {label:<24}  turns={run.turns:>5}  tokens={run.tokens:>8,}  "
          f"dollars=${run.dollars:>7.2f}  stopped_by={run.stopped_by}")
    return run

Break it on purpose

A nightly job uses your agent to triage 500 support tickets, one agent session per ticket, each with max_budget_usd set to 5 dollars. One night a bad prompt change makes every session run to just under its cap, and the morning bill is about 2,400 dollars. No cap fired. Using this lesson, what was missing? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Session caps are built in. The Claude Agent SDK has max_turns and max_budget_usd (both off unless set; a breach ends the run with an error_max_* result), and Claude Managed Agents has session budgets. The OpenAI Agents SDK stops a run after max_turns.
  • Fleet caps live at the gateway. Proxies such as LiteLLM put budgets and rate limits on each API key, team or user. This is where per-day spend, velocity limits and growth alerts across many sessions belong.
  • Caching is a cost control. Anthropic bills cache reads at a tenth of the input price, so a stable system prompt and tool list cut a long loop's input bill. Order the prompt so the stable part comes first.
  • Governance toolkits sit around agents. Microsoft's Agent Governance Toolkit (open source, April 2026) adds runtime policy, circuit breakers and a kill switch, mapped to the OWASP Top 10 for Agentic Applications.
  • On your laptop: a local model costs no API money, but the same caps apply to time. Cap turns and wall-clock minutes for a model served on the RTX 4060, or a loop holds the GPU all night.

Sources: Claude Agent SDK, Configure your agent, Anthropic, Prompt caching, Microsoft, Agent Governance Toolkit, LiteLLM, Budgets and rate limits.

Recap
What to keep from this lesson
  • Stack limits at several scales: per call, per session, per tool, per minute, per day and per month.
  • Set velocity limits from the measured normal rate with headroom, or a busy day looks like a loop.
  • Per-session caps cannot see a change that makes every session a little more expensive; alert on daily growth across the fleet.
  • Give every new tool its own cap; a polling tool is a loop waiting to happen.
  • Loops get more expensive every turn, because the context is re-sent each time.

Given a proposed agent deployment, audit its cost-governor stack against the twelve-layer reference and flag which layers are missing, under-tuned, or over-tuned.

Produce:

1. **Layer inventory.** For each of the twelve reference layers (per-request cap, per-task token budget, per-task dollar budget, per-tool cap, iteration cap, per-minute/hour/day/month rolling caps, velocity limit, tiered routing, prompt caching, context windowing, HITL checkpoints, kill switch), state whether it is configured, and at what value.
2. **Failure-mode mapping.** For each time-scale failure (runaway loop, slow leak, bad release, legitimate surge), name the specific layer that catches it and how fast.
3. **Tool-specific caps.** List every tool the agent can call. For each, name a per-session cap and a reason. Any tool without an explicit cap is an open loop.
4. **Alert thresholds.** Separate from caps: at what spend rate does a human get paged? The e-commerce pattern ($1,200 → $4,800) is a growth problem, caught by a day-over-day or week-over-week alert, not by a monthly cap.
5. **Kill-switch path.** When a cap fires, what happens? Clean abort, rollback, alert, re-enable procedure. Confirm the kill switch is external to the agent (the agent cannot edit its own cap).

Hard rejects:
- Any autonomous deployment without a per-task dollar budget.
- Any unattended long-horizon run without a velocity limit.
- Tool surfaces with no per-tool cap on a new (<30 days) tool addition.
- Kill switches the agent itself can modify.
- Monthly cap as the only cap (every other time scale is unguarded).

Refusal rules:
- If the user cannot price a worst-case run on today's model prices, refuse and require a costed estimate.
- If the proposed budget exceeds the organization's acceptable loss on a single mistake, refuse and require a lower cap.
- If the user treats the Auto Mode classifier (Lesson 10) as a replacement for budgets, refuse. The classifier is orthogonal to cost; both layers are required.

Output format:

Return a cost-governor audit with:
- **Layer table** (layer name, configured y/n, value)
- **Failure-mode coverage** (4 rows: loop / leak / release / surge)
- **Per-tool caps** (tool, cap, reason)
- **Alert thresholds** (rate, owner, channel)
- **Kill-switch path** (trigger, action, re-enable procedure)
- **Readiness** (production / staging / research-only)

Solutions

SolutionP1 · A busy day trips the velocity limit; the fleet change trips nothing

The busy day: the velocity limit fires after 2 turns. Normal turns cost 0.0075 dollars. At one every 10 seconds the rate is 0.045 dollars a minute, above the lesson's limit of 0.03. The session ends after 2 turns and a cent, though nothing is wrong. Set velocity limits from the measured normal rate with real headroom, and scope them to match: per session for loops, per fleet for surges.

The polling tool: no per-session layer notices. Sessions grow to 80 turns and 0.60 dollars, under every per-session cap, and the per-minute rate does not change. Only fleet-level checks see it: a daily-growth alert on day 11, or a monthly cap ten days later. A per-tool cap of 3 polls stops most of the extra cost at the source.

SolutionB1 · Five hundred sessions under five caps

Every limit was per session, and the failure was spread across 500 sessions. Each one stayed just under its 5-dollar cap, so the job as a whole had no limit: 500 times about 4.80 dollars is about 2,400.

The missing layers: - A per-job budget, for example 150 dollars for the whole night's run, checked before each new session starts. - A velocity limit across sessions: a nightly job that normally spends about 50 dollars an hour should be cut off and someone paged at, say, 3x that. - A growth alert, so tonight's cost per ticket is compared with last week's. - A canary for prompt changes: run the new prompt on 20 tickets first and compare cost per ticket before running all 500.

The session cap still matters, because it stops any one ticket from looping forever. It just cannot see the total.
