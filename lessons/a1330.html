In plain words first
The idea in one line

A registry entry tells you what a publisher declared. Production admission proves what you fetched, what you observed, what you approved, and what you can safely restore.

The problem

In plain words first

The official MCP Registry is a public list of MCP servers: who published them, which version, and where the code or endpoint lives. It checks that a publisher owns its name, but it is not a security review, and it does not decide what your company may run. Admitting a server safely means joining several pieces of evidence: the name really belongs to the verified publisher; the downloaded package is exactly the declared one (same digest); the live server exposes exactly the tools you reviewed; the record is still active. After admission the work continues: if a running server's tools change, it is quarantined; if a version goes bad, you roll back to an earlier approved one; and every decision goes into a log that shows if anyone edits it. This lesson queries the live Registry and PyPI, then runs the lesson's admission controller against real SDK servers.

You find com.example/inventory in a registry. Its description looks right. Its package exists. The server answers server/discover.

That is not one fact. It is a chain of facts from different authorities:

  1. A publisher authenticated for a namespace submitted a record.
  2. A package registry served an artifact with a specific identity and digest.
  3. A running endpoint reported a protocol version, capabilities, tools, and diagnostic server information.
  4. Your organization decided that this exact combination was allowed.

Collapsing those facts into “it is in the registry, so trust it” creates a supply chain blind spot. A valid publication can still be deprecated. A package tag can point at an unexpected artifact if you do not pin its digest. A server can add a destructive tool after review. A rollback can silently choose a version that was never admitted.

The fix is an admission controller with evidence at every boundary.

The Registry Is an Index, Not Your Approval System

The official MCP Registry stores server metadata. Its server.json record names a server version and declares one or more packages or remote endpoints. Publication rules add namespace authentication, package ownership checks, restricted registry rules, and a narrow publisher metadata location.

Those controls answer publication questions. Your production policy still answers deployment questions:

Boundary Question Evidence owner
Namespace Was the publisher allowed to use this name? Registry authentication plus your verified namespace input
Record What did the publisher declare for this version? Immutable server.json digest
Execution source Which package or remote endpoint will execute? Declared source fields, verified ownership result, transport, and trusted digest
Runtime What does the endpoint expose now? server/discover and tool descriptors
Admission Did your policy approve this exact set? Local pin and ledger entry
Operations Is it still safe, and what can replace it? Drift checks, status sync, health, and rollback route

The Registry schema version and the MCP protocol version are independent. A record may use the published 2025-12-11 server schema while the live server supports MCP 2026-07-28. Never infer one from the other.

Seven Controls in One Admission Decision

1. Namespace verification

Official Registry names use authenticated namespaces. A verified domain can map to a reversed domain prefix. For example, control of example.com can establish com.example/*.

Do not accept a string prefix check:

server_name.startswith("com.example")

That also accepts com.exampleevil/tool. Split the name at /, require a non-empty slug, and compare the namespace segment exactly. More importantly, pass the verified namespace into admission from the authentication result. Do not derive trust from the untrusted record.

GitHub-backed namespaces and domain-backed namespaces use different authentication paths. Normalize either path into one admission input: the exact verified namespace string.

2. Provenance join

For a package record, the declaration and fetched artifact must join on explicit fields:

  • package registry type
  • package identifier
  • package version
  • verified ownership result
  • downloaded artifact digest

Also validate the declared package transport. A record with only a remote endpoint is valid and must not be rejected for lacking a package. For a remote source, join the declared URL and transport type to independently verified endpoint ownership and a digest of the trusted connection or deployment evidence.

The lesson code supports both source kinds and hashes the selected source together with the Registry source, server name, Registry version, record digest, and evidence digest. The resulting provenance digest is a compact pointer to the full evidence set. It is not a substitute for retaining the evidence.

Never accept a digest supplied only by the artifact you are trying to verify. Calculate it at a trusted fetch boundary, or receive it from a package service whose verification result you validate.

3. Pin the decision, not only the version

Registry versions are unique publication identifiers. Published metadata is immutable. A changed record requires a new version. Semantic versioning is recommended, but the Registry does not require it and does not accept version ranges.

This means ^1.4 is not an admission pin. Neither is “latest.” A useful pin contains:

{
  "server": "com.example/inventory",
  "version": "1.0.0",
  "recordDigest": "...",
  "source": {"kind": "package", "registryType": "pypi"},
  "sourceDigest": "...",
  "toolsetDigest": "...",
  "provenanceDigest": "...",
  "registryStatus": "active"
}

Pinning several layers lets you identify which boundary changed. A record digest change under the same Registry version is a Registry integrity failure. A source digest change under the same package coordinate or remote deployment is an execution-source integrity failure. A toolset digest change is runtime drift.

4. Live drift detection

Admission should observe the server that will actually receive traffic. Call server/discover, list or otherwise obtain the exposed tool descriptors through your trusted path, and verify:

  • 2026-07-28 is in supportedVersions
  • all locally required capabilities are present
  • every tool descriptor has the required identity and schema surface
  • the normalized descriptor digest matches the admitted pin on later checks

The optional result _meta["io.modelcontextprotocol/serverInfo"] value is self-reported display, log, and debugging context. Record it as diagnostic evidence, but never use it to establish namespace, package ownership, endpoint ownership, admission, or any other security decision. A direct serverInfo alias outside _meta is not the contract field and should not be promoted into diagnostic evidence.

Normalize only fields whose order has no meaning. The sample sorts the tool list by stable name before hashing, so a harmless list-order change does not cause drift. It does not discard descriptor fields. A new tool, changed schema, changed description, or new annotations changes the pin.

The sample treats malformed descriptors and any descriptor digest change as drift, quarantines the pin, removes its active route, and blocks that version as a rollback target. A production policy may allow an editorial change only through a new review, because descriptions influence model tool selection. “Cosmetic” metadata can alter agent behavior.

5. Registry status is live state

The Registry API attaches a response-level _meta object beside each server record. Registry-managed fields live under _meta["io.modelcontextprotocol.registry/official"]. Pass the response _meta object to admission and read _meta["io.modelcontextprotocol.registry/official"].status. A direct _meta.status value is not the official wire shape. Do not confuse response metadata with the publication record's own _meta. Status can be:

  • active: returned by default and eligible for local admission
  • deprecated: still discoverable with a warning, but no longer a safe automatic choice
  • deleted: hidden by default while its historical record remains available through deleted or incremental views

Sync status after admission. If an active version becomes deprecated or deleted, quarantine its pin and stop routing new work to it. Keep the evidence. Deletion from the default listing is not permission to erase your audit trail.

Publisher-provided custom metadata belongs only under _meta.io.modelcontextprotocol.registry/publisher-provided in a publication record. Registry-managed response metadata is separate. Do not let a publisher set its own official status.

6. Rollback means route restoration

An immutable publication is not edited during rollback. Rollback selects a previously admitted, currently eligible pin and changes the active route.

A safe target must:

  1. Have a completed admission record.
  2. Still have an active Registry status under your policy.
  3. Not be quarantined by runtime or security evidence.
  4. Still resolve to the pinned package and live descriptor set.
  5. Pass current health checks.

The sample focuses on the first three conditions. A real reconciler should re-fetch the package and re-check the live endpoint before activation.

7. Append an admission ledger

An admission database says what is active. A ledger explains why.

Each sample entry contains a sequence, time, event, server, version, outcome, reasons, evidence, the previous entry hash, and its own hash. Changing an older outcome breaks verification of that entry and every later link.

This is tamper-evident, not magically tamper-proof. Anchor periodic ledger heads in a separate trust domain, such as signed release metadata or write-once storage. Restrict who can append. Keep authorization tokens, package credentials, tool arguments, and private endpoint data out of evidence.

The same idea as a formula

Admission is a conjunction of joins. For record R with name n, verified namespace v, fetched artifact a, declared digest d and live tool set T,

admit(R)=(ns(n)=v)∧(sha256(a)=d)∧status(R)=active∧reviewed(T),
and the pin stores h(R), h(a) and h(canonical(T)).

Drift. At any later time, healthy⟺h(canonical(Tlive​))=hpin​(T); otherwise quarantine and stop routing.

A hash chain. Ledger entry ei​ stores Hi​=h(bodyi​∥Hi−1​) with H0​=GENESIS. Editing bodyj​ changes the recomputed Hj​, which no longer matches the stored one, and every Hi>j​ depends on it, so verification fails from j on.

Worked example
Admitting, drifting and rolling back
  • Admit com.example/inventory 1.0.0 and 1.1.0: both names are inside the verified namespace com.example, both are active, both live tool sets are pinned. Active route: 1.1.0.
  • A record for 1.2.0 arrives, but the authenticated publisher is com.exampleevil. com.exampleevil/... would pass a startswith("com.example") check; the exact namespace comparison rejects it.
  • Version 1.1.0 is redeployed with an extra inventory_delete tool, same version number. The live digest no longer equals the pin → drifted, quarantined, route removed.
  • Rollback to 1.1.0 is refused (quarantined); rollback to 1.0.0 succeeds. The ledger has 7 linked entries; editing entry 5 breaks verification.
Check your mental model
  • ✗ "If a server is in the official Registry, it is approved."
    ✓ The Registry proves publication facts; your admission policy decides deployment.
  • ✗ "Checking the name starts with our domain proves ownership."
    ✓ Compare the namespace segment exactly, against the verified identity, not the record.
  • ✗ "The same version number means the same tools."
    ✓ A redeploy can change tools without a new version; pin and re-check the live descriptors.
  • ✗ "An append-only log cannot be changed."
    ✓ A hash chain makes edits detectable; anchor its head elsewhere so it cannot be rewritten wholesale.

Provenance against the live Registry and PyPI

Pages through the Registry API (opaque cursors, bounded), finds records whose package is on PyPI, reads PyPI's metadata for that exact version, checks the mcp-name: ownership marker the Registry requires in the package description, downloads the artifact itself, and compares its SHA-256 with the digest PyPI reports. It needs the network and the live data changes, so the block is not run on this page; the output below was recorded on 25 November 2026. The servers are simply the first package-backed records the Registry returned, not recommendations.

# Provenance join against the live official MCP Registry and PyPI: find package-backed records,
# check the PyPI ownership marker, download the artifact at our own fetch boundary, and compare digests.
import hashlib, httpx, re
from main import namespace_matches, registry_status
REG = "https://registry.modelcontextprotocol.io/v0.1/servers"
http = httpx.Client(timeout=30, follow_redirects=True)

found, cursor, pages = [], None, 0
while len(found) < 3 and pages < 8:                       # bounded paging; cursors are opaque
    page = http.get(REG, params={"limit": 100, **({"cursor": cursor} if cursor else {})}).json(); pages += 1
    for item in page["servers"]:
        for pkg in item["server"].get("packages", []):
            if pkg.get("registryType") == "pypi": found.append((item, pkg))
    cursor = page["metadata"].get("nextCursor")
    if cursor is None: break
print(f"scanned {pages} pages; package-backed PyPI records found: {len(found)}\n")

for item, pkg in found[:3]:
    name, ver = item["server"]["name"], item["server"]["version"]
    meta = http.get(f"https://pypi.org/pypi/{pkg['identifier']}/{pkg['version']}/json").json()
    marker = re.search(r"mcp-name:\s*(\S+)", meta["info"].get("description") or "")
    files = sorted(meta["urls"], key=lambda f: f["size"])[:1]          # smallest artifact for the demo
    blob = http.get(files[0]["url"]).content if files else b""
    ours = hashlib.sha256(blob).hexdigest()
    print(f"{name} {ver}  (registry status: {registry_status(item['_meta'])})")
    print(f"   package      pypi:{pkg['identifier']}=={pkg['version']}  versions match: {pkg['version'] == ver}")
    print(f"   ownership    README marker mcp-name: {marker.group(1) if marker else None}  matches: {bool(marker) and marker.group(1) == name}")
    print(f"   artifact     {files[0]['filename'] if files else '-'} ({len(blob):,} bytes)")
    print(f"   digest       ours {ours[:16]}...  PyPI {files[0]['digests']['sha256'][:16] if files else '-'}...  equal: {bool(files) and ours == files[0]['digests']['sha256']}")
    ns = name.split("/")[0]
    print(f"   namespace    exact match to '{ns}': {namespace_matches(name, ns)}; look-alike '{ns}evil' accepted: {namespace_matches(name.replace(ns, ns + 'evil', 1), ns)}\n")

Reading this output

Package-backed records are a minority. It took six pages of 100 records to find three PyPI-backed servers; most current Registry entries point at remote endpoints instead, which need a different provenance check (endpoint ownership and deployment evidence).

Each join passes for these three. The package version equals the record version; the PyPI description carries the mcp-name: marker with exactly the Registry name, which is how the Registry checked package ownership; the artifact we downloaded hashes to the digest PyPI reports.

Know what each check proves. The digest match proves the bytes we hold are the bytes PyPI serves for that release, nothing more: it says nothing about whether the code is safe. The ownership marker proves the PyPI project and the Registry name are controlled by the same publisher, not that the publisher is trustworthy. Review, scanning and pinning are still yours to do.

Exact namespace comparison accepts the real namespace and rejects the same name with evil appended, which a startswith check would accept.

The lesson's admission controller fed by real SDK servers

RegistryAdmissionController from code/main.py gets its live view from MCPServer instances through the SDK client (server/discover identity plus tools/list). The block admits two versions, rejects a namespace mismatch, detects a same-version redeploy, rolls back, and verifies the hash-chained ledger before and after an edit. About a second.

# The lesson's admission controller (code/main.py) fed by real SDK servers: admit two versions from their
# live discovery, catch a redeploy that adds a tool, roll back, and check the tamper-evident ledger.
import anyio, itertools
from mcp import Client
from mcp.server import MCPServer
from main import (RegistryAdmissionController, sample_record, evidence_for, OFFICIAL_META_KEY,
                  SERVER_INFO_KEY, PROTOCOL_VERSION)

def inventory(version, with_delete=False):
    s = MCPServer("com.example/inventory", version=version, log_level="WARNING")
    @s.tool()
    def inventory_get(sku: str) -> str:
        """Fetch one inventory item"""
        return sku
    if with_delete:
        @s.tool()
        def inventory_delete(sku: str) -> str:
            """Delete one inventory item"""
            return sku
    return s
async def live_view(server):                              # what the controller sees: discovery plus the tool list
    async with Client(server) as c:
        tools = [t.model_dump(by_alias=True, exclude_none=True) for t in (await c.list_tools()).tools]
        return {"resultType": "complete", "supportedVersions": [PROTOCOL_VERSION], "capabilities": {"tools": {"listChanged": False}},
                "tools": tools, "_meta": {SERVER_INFO_KEY: {"name": c.server_info.name, "version": c.server_info.version}}}
live = lambda *a: anyio.run(live_view, inventory(*a))

clock = (f"2026-11-25T10:00:{n:02d}+00:00" for n in itertools.count())
ctl = RegistryAdmissionController(clock=lambda: next(clock))
active = {OFFICIAL_META_KEY: {"status": "active"}}
show = lambda label, d: print(f"{label:<48} allowed={d.allowed!s:<5} {'; '.join(d.reasons)}")
show("admit 1.0.0", ctl.admit(sample_record("1.0.0"), active, "com.example", evidence_for("1.0.0"), live("1.0.0")))
show("admit 1.1.0", ctl.admit(sample_record("1.1.0"), active, "com.example", evidence_for("1.1.0"), live("1.1.0")))
show("admit 1.2.0, publisher verified as com.exampleevil", ctl.admit(sample_record("1.2.0"), active, "com.exampleevil", evidence_for("1.2.0"), live("1.2.0")))
print("active version:", ctl.active.get("com.example/inventory"))
show("live check 1.1.0 (unchanged)", ctl.check_live("com.example/inventory", "1.1.0", live("1.1.0")))
show("live check 1.1.0 after redeploy (+delete tool)", ctl.check_live("com.example/inventory", "1.1.0", live("1.1.0", True)))
print("active version:", ctl.active.get("com.example/inventory"))
show("rollback to 1.1.0", ctl.rollback("com.example/inventory", "1.1.0", "retry"))
show("rollback to 1.0.0", ctl.rollback("com.example/inventory", "1.0.0", "restore last good release"))
print("active version:", ctl.active.get("com.example/inventory"))
print(f"\nledger: {len(ctl.ledger.entries)} entries, verifies: {ctl.ledger.verify()}")
for e in ctl.ledger.entries: print(f"   #{e['sequence']} {e['event']:<11} {e['version']:<6} {e['outcome']:<10} {e['entryHash'][:20]}...")
ctl.ledger.entries[4]["outcome"] = "healthy"                 # someone edits history
print("after editing entry #5 in place, verifies:", ctl.ledger.verify())

Reading this output

Admission pins what the live server shows. Versions 1.0.0 and 1.1.0 are admitted from their real discovery identity and tool list; 1.1.0 becomes active. The 1.2.0 record names com.example/..., but the publisher's verified namespace is com.exampleevil, so it is rejected.

A same-version redeploy is caught. The first live check of 1.1.0 is healthy. After the redeploy adds inventory_delete, the canonical tool digest differs from the pin: the controller marks 1.1.0 drifted, quarantines it and removes the active route (active version: None). No version number changed, which is why live checks matter.

Rollback moves the route, carefully. Rolling back to the quarantined 1.1.0 is refused; rolling back to 1.0.0, still active and never drifted, succeeds. A real reconciler would also re-check 1.0.0's package and live descriptors right before switching.

The ledger is tamper-evident. Seven entries, each hashing its body and the previous entry's hash, verify. Changing entry 5's outcome to "healthy" breaks verification. Anchoring the latest hash somewhere the operator cannot rewrite is what stops someone from recomputing the whole chain.

Build it

The runnable controller is in code/main.py. It uses only the Python standard library.

Start with the finite demonstration:

cd phases/13-tools-and-protocols/30-mcp-registry-supply-chain-and-drift
python3 code/main.py
npx tsx code/main.ts

The demonstration performs five operations:

  1. Admit 1.0.0 with matching namespace, package provenance, protocol, capabilities, and tools.
  2. Admit 1.1.0 and make it active.
  3. Observe an unexpected delete tool at runtime.
  4. Observe the Registry status for 1.1.0 become deprecated.
  5. Restore routing to the still-admitted 1.0.0 pin.

Expected shape:

{
  "admitted": [true, true],
  "driftAllowed": false,
  "rollbackAllowed": true,
  "activeVersion": "1.0.0",
  "ledgerValid": true
}

Read the implementation in this order:

  1. namespace_for_domain() and namespace_matches() establish exact naming authority.
  2. digest() and normalized_tools() produce deterministic evidence.
  3. RegistryAdmissionController.admit() joins publication, provenance, runtime, and policy.
  4. check_live() compares a new observation with the pin.
  5. observe_registry_status() quarantines versions whose Registry state changes.
  6. rollback() activates only a previously admitted eligible target.
  7. AdmissionLedger.verify() detects changes to recorded history.

Use it: the same idea with real libraries

Put the controller between discovery and routing:

Registry sync -> artifact verifier -> live discovery -> admission controller -> route table
                                               |                 |
                                               v                 v
                                          evidence store    admission ledger

Use separate identities for these jobs. A Registry sync worker needs read access to metadata. An artifact verifier needs package fetch access. A route reconciler needs permission to activate an approved pin. None of them needs every credential.

Make rollout state explicit. “Approved” means the evidence passed policy. “Active” means the route currently selects it. “Quarantined” means it cannot receive new work. “Superseded” means another admitted version is active. Do not encode all four meanings in one Boolean.

Run admission before exposing a server in tools/list. Otherwise a client can discover a tool during the gap between publication and policy evaluation.

Practice Lab

Extend the controller with a two-person approval gate.

Requirements:

  • Store approvals as signed evidence references, not mutable names in the pin.
  • Require two different reviewer identities for a toolset that contains a tool with destructiveHint: true.
  • Reject duplicate reviewer identities.
  • Preserve the original admission attempt in the ledger when approval is incomplete.
  • Add tests for zero, one, duplicate, and two distinct approvals.
  • Do not log signatures, credentials, or full private tool arguments.

Success means a destructive tool cannot become active until both identities approved the exact record, package, and toolset digests.

Break it on purpose

A platform team auto-installs any Registry server whose name starts with io.github.ourcompany, installs latest from npm at deploy time, and marks a server approved forever once it passed review. List the holes. (Solution B1.)

Industry practice
What's current (2024–2026)
  • The official MCP Registry (registry.modelcontextprotocol.io) is in preview: metadata only, server.json records with schema versions such as 2025-12-11, namespaces proven through GitHub, DNS or HTTP, package ownership markers (for PyPI, mcp-name: in the package description), statuses active, deprecated and deleted under _meta, and a recommendation that hosts consume downstream registries that add curation and scanning.
  • Downstream registries and catalogs used in production include GitHub's MCP registry, Docker's MCP Catalog, Smithery and enterprise registries in Azure API Center and similar products; most add security scanning, signing or allowlists on top.
  • Supply-chain practice: pin exact versions and digests, prefer signed artifacts (Sigstore for PyPI and npm provenance), and re-verify live tool descriptors continuously (Lesson 13.15).
  • On your laptop: admission and drift checks are cheap; run them in CI and at gateway start-up.

Sources: MCP Registry about, Official Registry requirements, Registry API, PyPI JSON API.

Recap
What to keep from this lesson
  • The Registry is an index of publication facts, not your approval system.
  • Admit by joining exact namespace, artifact digest, status and reviewed tools; pin all of them.
  • Keep checking: live drift quarantines, status changes quarantine.
  • Roll back by moving the route to an earlier, still-eligible pin.
  • Log every decision in a hash chain and anchor it elsewhere.

Solutions

SolutionP1 · Quarantined; only 1.0.0 can take over

The live check finds that the tool set no longer matches the pin, so 1.1.0 is marked drifted and quarantined, and its active route is removed: new work goes nowhere until someone acts, which is the safe default. Rolling back to 1.1.0 is refused because it is quarantined. Rolling back to 1.0.0 is accepted, because it was admitted, is still active in the Registry, and was never quarantined.

SolutionB1 · A prefix, a moving target and a permanent yes
  • Prefix trust: io.github.ourcompany-evil/... or io.github.ourcompanyx/... starts with the same text. Compare the namespace segment exactly, and take the namespace from verified authentication, not from the record.
  • latest at deploy time: the code that runs is not the code that was reviewed, and two deploys can run different code. A compromised maintainer account or a malicious release (as with the LiteLLM PyPI releases in March 2026) flows straight into production. Pin exact versions and artifact digests.
  • Approved forever: a server can change its tools without a version bump, a version can be deprecated or deleted in the Registry, and new vulnerabilities appear. Re-check live descriptors and Registry status continuously, quarantine on drift, and expire approvals.
  • Auto-install from the public feed: the Registry itself recommends consuming a curated downstream registry; auto-installing from the raw index skips review entirely.
  • No ledger: without a recorded decision chain nobody can tell later why a server ran, who approved it, or what changed.

Production Failure Modes

Failure Why it happens Required response
Name looks valid but namespace was never authenticated Policy trusted record text Reject until a trusted namespace verifier supplies the exact prefix
Same package coordinate returns new bytes Mutable upstream or compromised distribution Stop activation, retain both digests, investigate the fetch boundary
“Latest” changes without review Floating selection escaped the pin Resolve only exact admitted versions and digests
New tool appears after approval Runtime drift or a different deployment Quarantine the route and capture a fresh descriptor observation
Deprecated version remains active Status sync is missing or delayed Reconcile status on a schedule and before activation
Deleted record disappears from default sync Client requested only active records Use incremental or deleted-aware reconciliation and preserve local history
Rollback target was never admitted Route control and approval state are disconnected Refuse rollback and run a new admission for the target
Ledger verifies locally after an attacker rewrites all entries Hash chain has no external anchor Publish signed ledger heads to a separate trust domain
Evidence contains bearer tokens or tool arguments Logging copied whole requests Redact at collection time and store only the minimum proof

Operational Rule

Publication answers “can this identity publish this name?” Admission answers “will we execute this exact artifact and expose this exact behavior?” Keep those decisions separate, pin every join, and make rollback choose evidence rather than memory.
