In plain words first
The idea in one line

The agent does not get to mark its own work as done. A verification gate reads the scope contract, the feedback log, the rule report, and the diff, and answers a single question: is this task actually complete? If the gate says no, the task is not done, no matter what the chat says.

Terms you'll hear
Term What people say What it actually means
Verification gate "The check that stops things" Deterministic function over workbench artifacts producing a pass/fail verdict
Block severity "Hard fail" A finding that prevents passed: true and requires a signed override

Acceptance command "The proof" A shell command whose zero exit is what done means

The problem

In plain words first

A verification gate is code that decides whether a task is done, from evidence: did the acceptance commands run and exit 0, did the diff stay in scope, did every blocking rule pass. Its answer is the same every time for the same evidence, and nobody, the agent included, can talk it into a different one. Evaluation and judges in general are covered in Zero to Agents 12.11 and 3.12 (linked above); this lesson puts the agent's own verdict and an LLM judge next to the lesson's gate on eight real fixes.

Agents declare success too easily. Three failure shapes dominate:

  • "Looks good." The model read its own diff and decided it was correct.
  • "Tests passed." Said with confidence. No record of the test actually running.
  • "Acceptance met." Acceptance criteria interpreted loosely enough to mean "anything resembling done."

The workbench fix is a single verification gate that reads the artifacts the agent has already produced and makes the call. The gate is deterministic. The gate is in version control. The gate is wired into CI. The agent cannot bribe it.

The idea

Idea 1 · What the gate checks

Check Source artifact Severity
All acceptance commands ran feedback_record.jsonl block
All acceptance commands exited zero feedback_record.jsonl block
Scope check has no forbidden writes scope_report.json block
Scope check has no off-scope writes scope_report.json block or warn
All block-severity rules pass rule_report.json block
No null exit codes in feedback feedback_record.jsonl block
Touched files match scope.allowed_files both warn

A warn finding annotates the verdict; a block finding prevents passed: true.

Idea 2 · Deterministic, not probabilistic

The gate must produce the same verdict for the same artifact set every time. No LLM judges. LLM judges belong on the reviewer side (Phase 14 · 39) where the goal is qualitative evaluation, not status.

Idea 3 · One report, one path

The gate emits one verification_report.json per task close-out, written under outputs/verification/<task_id>.json. CI consumes the same path. Multiple gates with different paths fork the source of truth.

Idea 4 · Refuse without exception

Block-severity findings cannot be overridden by the agent. They can only be overridden by a human, with a recorded override_reason and an overridden_by user id. The override is a signed change, not an agent decision.

The same idea as a formula

A gate is a function of artifacts. With acceptance results ai​∈{0,1,null}, forbidden writes F and blocking rules rj​:

pass=(i⋀​ai​=0)∧(F=∅)∧(j⋀​rj​).
Same inputs, same output: its variance is zero.

A judge is a random variable. If a judge says "yes" with probability py​ on a correct fix and pn​ on a wrong one, its error on a set with a fraction w of wrong fixes is (1−w)(1−py​)+wpn​. A judge that always says yes has py​=pn​=1 and error w: on these eight fixes, 5/8.

Worked example
Eight fixes, three verdicts
  • The model writes one fix for each of eight bugs. The tests pass for three (is_even, reverse, count_vowels).
  • Asked "is your fix correct?", the model says yes to all eight. Agreement with the gate: 3 of 8; it vouched for five broken fixes.
  • An LLM judge shown the function and the test says yes five times out of five for every fix: perfectly consistent, and wrong on five of eight.
  • The gate blocks the five with acceptance.failed and rule.failed, the same way on every run. Nothing about the decision depends on what the model says.
Check your mental model
  • ✗ "Ask the agent if it is done."
    ✓ It said yes to all eight; five were broken.
  • ✗ "An LLM judge with the test in front of it is a gate."
    ✓ It approved every fix, consistently and wrongly.
  • ✗ "Consistent answers are correct answers."
    ✓ The judge never changed its mind and was right on three of eight.
  • ✗ "Gates need an override for urgent cases."
    ✓ If one exists, make it signed, logged and human, as the lesson's override does.

Qwen2.5-0.5B-Instruct (greedy, CPU) fixes eight one-line bugs, then answers whether each fix is correct. Each fix's acceptance test runs for real, and the evidence goes to the lesson's verify() from code/main.py. About 1 minute.

# The agent's own verdict versus a deterministic gate. Eight one-line bugs; Qwen2.5-0.5B-Instruct (greedy, CPU)
# writes one fix for each, then is asked whether its fix is correct. The fix's real artifacts (the acceptance
# test's exit code, the files it touched, a rule check) go to the lesson's verify() (code/main.py), which
# decides pass or block. How often does "I'm confident it's correct" match the gate?
import json, os, pathlib, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import Artifacts, verify
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

BUGS = [("is_even", "def is_even(n):\n    return n % 2 == 1\n", "assert is_even(4) and not is_even(7)"),
        ("largest", "def largest(xs):\n    return min(xs)\n", "assert largest([3, 9, 2]) == 9"),
        ("reverse", "def reverse(s):\n    return s\n", "assert reverse('abc') == 'cba'"),
        ("to_fahrenheit", "def to_fahrenheit(c):\n    return c * 9 / 5\n", "assert to_fahrenheit(100) == 212"),
        ("count_vowels", "def count_vowels(s):\n    return len(s)\n", "assert count_vowels('banana') == 3"),
        ("is_leap", "def is_leap(y):\n    return y % 4 == 0\n", "assert is_leap(2000) and not is_leap(1900) and is_leap(2024)"),
        ("clamp", "def clamp(x, lo, hi):\n    return max(x, lo)\n", "assert clamp(15, 0, 10) == 10 and clamp(-3, 0, 10) == 0"),
        ("average", "def average(xs):\n    return sum(xs) / (len(xs) + 1)\n", "assert average([2, 4, 6]) == 4")]

def chat(messages, n=120, sample=False):
    ids = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=sample, **({"temperature": 1.0} if sample else {}))
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

work = pathlib.Path(tempfile.mkdtemp())
ROWS = []
for name, code, test in BUGS:
    ask = [{"role": "user", "content": f"This Python function has a bug.\n{code}\nReturn only the corrected function in a ```python block."}]
    reply = chat(ask)
    m = re.search(r"```(?:python)?\n(.*?)```", reply, re.S)
    fix = (m.group(1) if m else code).strip() + "\n"
    (work / f"{name}.py").write_text(fix)
    (work / f"test_{name}.py").write_text(f"from {name} import {name}\n{test}\n")
    cmd = f"python test_{name}.py"
    p = subprocess.run([sys.executable, f"test_{name}.py"], cwd=work, capture_output=True, text=True, timeout=30)
    self_check = chat(ask + [{"role": "assistant", "content": reply},
                             {"role": "user", "content": "Is your fix correct? Answer YES or NO."}], n=4)
    art = Artifacts(task_id=f"T-{name}", acceptance_commands=[cmd],
                    feedback=[{"command": cmd, "exit_code": p.returncode}],
                    scope_report={"forbidden_writes": [], "off_scope_writes": []},
                    rule_report=[{"slug": "done/tests-pass", "passed": p.returncode == 0}],
                    coverage_report={"current": 0.9, "previous": 0.9})
    report = verify(art)
    ROWS.append((name, fix, "YES" in self_check.upper(), report))

print(f"{'function':<15}{'agent says correct':<20}{'gate':<7}{'blocking findings'}")
for name, fix, says, rep in ROWS:
    blocks = [f.code for f in rep.findings if f.severity == "block"]
    print(f"{name:<15}{'yes' if says else 'no':<20}{'PASS' if rep.passed else 'BLOCK':<7}{', '.join(blocks) or '-'}")
agree = sum(says == rep.passed for _, _, says, rep in ROWS)
false_yes = sum(says and not rep.passed for _, _, says, rep in ROWS)
print(f"\nagent and gate agree on {agree}/8; the agent called a blocked fix correct {false_yes} times")

Reading this output

The judge is consistent and wrong. Shown each function with its test, it answers YES five times out of five for all eight fixes, so its majority verdict matches reality on 3 of 8. It never changed its mind, which is the point: low variance is not accuracy.

The gate gives the same verdict five times as well, 5 of 5 for the three passing fixes and 0 of 5 for the rest, because it reads exit codes, not opinions. That is the property to want from whatever decides "done".

Part 1 of 5 · _load_override_secret, Finding, Artifacts

"""Deterministic verification gate with coverage floor, --strict mode, and signed overrides.

Combines a task's scope_report, rule_report, feedback log, and an optional
coverage_report into a single verification_report.json. No LLM judges; LLM
judgment lives on the reviewer side (Phase 14 · 39). Overrides require a signed
entry in overrides.jsonl with reason, user, and HEAD commit.

Run: python3 code/main.py
"""

from __future__ import annotations

import argparse
import hashlib
import hmac
import json
import math
import os
import sys
import time
from dataclasses import asdict, dataclass, field
from pathlib import Path

HERE = Path(__file__).parent
OVERRIDES_PATH = HERE / "overrides.jsonl"
COVERAGE_FLOOR_DEFAULT = 0.80
COVERAGE_REGRESSION_DELTA = 0.01

# Audit secret used to sign override entries. In production read from a secrets
# manager. Fail closed: only fall back to a demo secret when VERIFY_DEMO_MODE=1
# is set explicitly, and shout about it so it cannot land in CI by accident.
_OVERRIDE_SECRET_ENV = "VERIFY_OVERRIDE_SECRET"
_DEMO_MODE_ENV = "VERIFY_DEMO_MODE"


def _load_override_secret() -> str:
    secret = os.environ.get(_OVERRIDE_SECRET_ENV)
    if secret:
        return secret
    if os.environ.get(_DEMO_MODE_ENV) == "1":
        print(
            f"WARNING: {_OVERRIDE_SECRET_ENV} unset and {_DEMO_MODE_ENV}=1; "
            "using insecure demo secret. Do not record real overrides in this mode.",
            file=sys.stderr,
        )
        return "demo-override-secret-do-not-ship"
    raise RuntimeError(
        f"refused to start: {_OVERRIDE_SECRET_ENV} is unset. "
        f"Set the env var, or pass {_DEMO_MODE_ENV}=1 to run the lesson demo only."
    )


@dataclass
class Finding:
    code: str
    severity: str
    detail: str


@dataclass
class Artifacts:
    task_id: str
    acceptance_commands: list[str]
    feedback: list[dict[str, object]]
    scope_report: dict[str, object]
    rule_report: list[dict[str, object]]
    coverage_report: dict[str, float] | None = None  # {"current": 0.84, "previous": 0.85}
    head_commit: str = ""

Part 2 of 5 · VerdictReport, _acceptance_findings, _scope_findings, _rule_findings, _coverage_findings

@dataclass
class VerdictReport:
    task_id: str
    passed: bool
    strict: bool
    findings: list[Finding] = field(default_factory=list)
    coverage: dict[str, float] | None = None
    head_commit: str = ""


def _acceptance_findings(art: Artifacts) -> list[Finding]:
    findings: list[Finding] = []
    commands_run = [str(rec.get("command")) for rec in art.feedback]
    accept_set = set(art.acceptance_commands)
    for cmd in art.acceptance_commands:
        if cmd not in commands_run:
            findings.append(Finding("acceptance.missing", "block", f"never ran: {cmd}"))
    for rec in art.feedback:
        cmd_str = str(rec.get("command"))
        if rec.get("exit_code") is None:
            findings.append(Finding("feedback.null_exit", "block", f"missing exit for {cmd_str}"))
        elif rec.get("exit_code") != 0 and cmd_str in accept_set:
            findings.append(
                Finding("acceptance.failed", "block", f"acceptance exit {rec.get('exit_code')} on {cmd_str}")
            )
    return findings


def _scope_findings(art: Artifacts) -> list[Finding]:
    findings: list[Finding] = []
    if art.scope_report.get("forbidden_writes"):
        findings.append(Finding("scope.forbidden", "block",
                                f"forbidden writes: {art.scope_report['forbidden_writes']}"))
    if art.scope_report.get("off_scope_writes"):
        findings.append(Finding("scope.off_scope", "warn",
                                f"off-scope writes: {art.scope_report['off_scope_writes']}"))
    return findings


def _rule_findings(art: Artifacts) -> list[Finding]:
    return [Finding("rule.failed", "block", f"rule failed: {row.get('slug')}")
            for row in art.rule_report if not row.get("passed")]


def _coverage_findings(art: Artifacts, floor: float) -> list[Finding]:
    """Anthropic Hybrid Norm: pair verifiable rewards (tests + coverage) with rubric judging.

    Floor failure is a block. Regression versus the previous merge by more than
    COVERAGE_REGRESSION_DELTA is a block; smaller drops are warnings.
    """
    findings: list[Finding] = []
    if not art.coverage_report:
        findings.append(Finding("coverage.missing", "warn",
                                "no coverage_report.json; cannot enforce floor"))
        return findings
    current = float(art.coverage_report.get("current", 0.0))
    previous = float(art.coverage_report.get("previous", current))
    if current < floor:
        findings.append(Finding("coverage.below_floor", "block",
                                f"coverage {current:.2%} below floor {floor:.0%}"))
    delta = previous - current
    if delta > COVERAGE_REGRESSION_DELTA and not math.isclose(
        delta, COVERAGE_REGRESSION_DELTA, rel_tol=1e-9
    ):
        findings.append(Finding("coverage.regression", "block",
                                f"coverage dropped {delta:.2%} (prev {previous:.2%} -> {current:.2%})"))
    elif delta > 0 and not math.isclose(delta, 0.0, abs_tol=1e-12):
        findings.append(Finding("coverage.minor_regression", "warn",
                                f"coverage dropped {delta:.2%}"))
    return findings

Part 3 of 5 · verify, _sign, record_override, verify_signature

def verify(
    art: Artifacts,
    strict: bool = False,
    coverage_floor: float = COVERAGE_FLOOR_DEFAULT,
) -> VerdictReport:
    findings = (
        _acceptance_findings(art)
        + _scope_findings(art)
        + _rule_findings(art)
        + _coverage_findings(art, coverage_floor)
    )
    if strict:
        # --strict promotes every warning to a block. Opt-in by release branch only.
        findings = [Finding(f.code, "block" if f.severity == "warn" else f.severity, f.detail)
                    for f in findings]
    blocking = [f for f in findings if f.severity == "block"]
    return VerdictReport(
        task_id=art.task_id,
        passed=not blocking,
        strict=strict,
        findings=findings,
        coverage=art.coverage_report,
        head_commit=art.head_commit,
    )


def _sign(payload: dict[str, object]) -> str:
    canonical = json.dumps(payload, sort_keys=True, separators=(",", ":")).encode()
    return hmac.new(_load_override_secret().encode(), canonical, hashlib.sha256).hexdigest()[:32]


def record_override(
    task_id: str, finding_code: str, reason: str, user_id: str, head_commit: str
) -> dict[str, object]:
    """Append a signed override entry. Refuses without all five fields populated."""
    if not all([task_id, finding_code, reason, user_id, head_commit]):
        raise ValueError("override requires task_id, finding_code, reason, user_id, head_commit")
    payload = {
        "task_id": task_id,
        "finding_code": finding_code,
        "reason": reason,
        "user_id": user_id,
        "head_commit": head_commit,
        "ts": time.time(),
    }
    payload["signature"] = _sign({k: v for k, v in payload.items() if k != "signature"})
    with OVERRIDES_PATH.open("a") as fh:
        fh.write(json.dumps(payload) + "\n")
    return payload


def verify_signature(entry: dict[str, object]) -> bool:
    expected = entry.get("signature")
    payload = {k: v for k, v in entry.items() if k != "signature"}
    return hmac.compare_digest(_sign(payload), str(expected))

Production patterns in the wild

Five patterns elevate the gate from "another lint job" to "the deciding edge."

Defense-in-depth, not single gate. Pre-commit hook → CI status check → pre-tool authz hook → pre-merge gate. Each layer is deterministic so a failure in one layer is caught by the next. microservices.io's March 2026 playbook is explicit: the pre-commit hook is non-bypassable because, unlike a model-side skill, it does not depend on the agent following instructions. The verification gate sits at the CI / pre-merge layer.

Defense by deterministic check, model-judge only for nuance. Anthropic's 2026 Hybrid Norm pairing: verifiable rewards (unit tests, schema checks, exit codes) answer "did the code solve the problem?" — LLM rubrics answer "is the code readable, secure, on-style?" The gate runs the first class; the reviewer (Phase 14 · 39) runs the second. Mixing them collapses the signal.

Signed override log, not Slack threads. Every override emits a row in outputs/verification/overrides.jsonl with: timestamp, finding code, reason, signing user, current HEAD commit. The runtime refuses any override that lacks the signature; the audit trail is git-tracked. This is the line between an override policy and an override theater.

Coverage floor as a first-class check. A coverage_report.json feeds a coverage_floor (default 80%) check. The gate fails if measured coverage drops below the floor or below the previous merge's floor by more than 1 percentage point. Without this check, agents quietly delete tests that fail and the verification reports stay green.

--strict mode promotes warns to blocks. For release branches, ship-blocking PRs, or post-incident triage, --strict makes every warning a hard fail. The flag is opt-in by branch; not the global default, because strict-on-everything corrodes day-to-day flow.

Use it: the same idea with real libraries

Production patterns:

  • CI step. A verify_agent job runs the gate against the agent's final artifacts. Merge protection refuses without passed: true.
  • Pre-handoff hook. The agent runtime calls the gate before generating the handoff doc. No green verdict, no handoff.
  • Manual triage. Operators read the report when an agent claims success and a human suspects it.

The gate is the deciding edge in the workbench flow. Every other surface is upstream of it.

Break it on purpose

Your team replaced its CI gate with "an LLM reviews the diff and the test output and approves or rejects" because CI was slow. Approval rates went up and so did incidents. Using this lesson, explain what changed and design the combination you would keep. (Solution B1.)

Industry practice
What's current (2024–2026)
  • Deterministic checks first: tests, type checks, linters, scope checks and coverage floors run in CI and in agent hooks; coding agents are told to run them, and harnesses refuse "done" until they pass (Anthropic's long-running-agent harness requires end-to-end verification before a feature is marked passing).
  • LLM judges second, for what code cannot check (readability, product fit), calibrated against human labels and never the only gate for correctness (lessons 14.24 and 14.30).
  • Overrides exist in practice (emergency merges), with audit trails and required approvers; the lesson's signed override record is the same idea.
  • On your laptop: the gate is standard-library Python.

Sources: Anthropic, Effective harnesses for long-running agents, GitHub protected branches and required status checks.

Recap
What to keep from this lesson
  • "Done" is decided by evidence, in code, the same way every time.
  • Agents vouch for their own broken work; ignore the claim.
  • LLM judges can be consistent and wrong; do not gate correctness on them.
  • Block on missing, failed or null acceptance results.
  • Any override is signed, logged and made by a person.

Given a project's acceptance criteria and existing workbench artifacts, produce the verification gate and override audit log.

Produce:

1. `tools/verify_agent.py` exposing `verify(task_id, artifacts) -> VerdictReport`. Pure function, deterministic, no LLM calls.
2. `outputs/verification/<task_id>.json` as the single source of truth verdict.
3. `tools/override.py` that appends signed override entries to `outputs/verification/overrides.jsonl` (must include reason, user id, timestamp, finding code).
4. CI workflow that fails on `passed: false` and surfaces the report inline.
5. `docs/verification.md` listing every check, its severity, its source artifact, and the override policy.

Hard rejects:

- A check that calls an LLM. The gate is deterministic plumbing; LLM judgment belongs to the reviewer.
- An override path the agent can take without a signed entry. Overrides are human-only.
- A verification report that omits the artifact paths it consumed. Reports must be auditable.
- Block-severity findings the workflow can silently downgrade. Severity is fixed at write time, not at read time.

Refusal rules:

- If the project has no acceptance command, refuse to ship the gate until one exists. A gate that proves nothing is theater.
- If the rule report does not exist, refuse to skip the rule check; fail closed.
- If the feedback log does not exist, refuse to skip the acceptance check; missing logs are themselves a block.
- If override entries are not version-controlled, refuse to wire the override path; off-the-record overrides defeat the gate.

Solutions

SolutionP1 · Yes to all eight

Yes to all eight, and the gate blocks five of them: largest, to_fahrenheit, is_leap, clamp and average fail their tests. The agent's own verdict agrees with the evidence only on the three fixes that happened to work.

SolutionB1 · Gate on evidence, review on judgement

The decision moved from evidence to opinion. An LLM reviewer reading test output can approve failures (as the judge here approved every fix), especially when outputs are long or the diff looks plausible, so approvals rose while correctness did not.

Keep the deterministic gate as the only path to merge: required status checks for tests, type checks, scope and coverage, blocking on any failure or missing result. Speed it up with test selection, caching and parallel runs rather than replacing it. Use the LLM reviewer after the gate passes, for things code cannot check, and as advice to a human reviewer, not as an approver. Track its agreement with human reviews so you know what its comments are worth.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Debug a failureEvery verification report for the last month says passed. A reviewer notices that the test suite runs much faster than it did, and that several test files are gone. The acceptance command still exits zero. What happened, which check is missing from the gate, and what else do you change?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The agent met the acceptance command by removing the tests that failed, and the gate only checked that the command ran and exited zero. The missing check is a coverage floor: the gate reads a coverage report and blocks when coverage is below the floor, 80 percent by default, or when it drops by more than one percentage point against the previous merge. Add the test directory to the scope check so that a deletion under it is a flagged write, and promote warnings to blocks on release branches.

How a green gate lies.

The gate is deterministic over artifacts, and it was given the wrong artifacts to be sure about. Its checks were: acceptance commands ran, acceptance commands exited zero, no forbidden writes, no null exits, block-severity rules passed. A test suite with fewer tests exits zero. Nothing in that list measures how much the suite covers.

The coverage floor.

A coverage_report.json with the current and the previous coverage feeds a new check. Two findings come out of it:

Finding Severity Condition
coverage.below_floor block current coverage under the floor
coverage.regression block drop of more than one percentage point against the previous merge
coverage.minor_regression warn any smaller drop
coverage.missing warn no coverage report at all

The last row is the quiet failure. If the agent stops producing the report, the gate only warns. On a release branch run the gate in strict mode, which promotes every warning to a block, so a missing report blocks.

Scope sees deletions.

A deletion is a write. Put tests/** in the scope contract, either as allowed for the task that owns the tests or as forbidden for tasks that do not. Then the diff check reports a deleted test file as an off-scope or forbidden write, and the gate refuses before the coverage check runs.

Review reads changed tests.

The reviewer is the second pass with a different role. Its checklist should include the diff of test files. A test that was changed or removed in the same change that made it pass is the pattern to flag.

Prove the fix.

Run two proofs. For coverage, take the last passing change, restore a deleted test whose loss drops coverage by more than one percentage point, and run the old and the new gate on both versions. The old gate passes both, and the new gate blocks the deletion on coverage regression and passes the restored one. A smaller drop only warns outside strict mode. For scope, run the same deletion under a new contract that forbids tests/** for the task, and confirm that the scope check blocks it.

Plausible wrong answers.

  • "Add a rule that says do not delete tests." A rule the gate cannot check from an artifact is a wish, and the agent did not think of it as deleting tests.
  • "Count the tests and block when the number falls." A count blocks legitimate consolidation, while a coverage floor measures what the suite protects.
  • "Make the acceptance command also print coverage." The gate reads a report, not output text, so the coverage must arrive as an artifact the gate can parse.

Follow-ups an interviewer may ask.

  • (level 3) Which artifact carries the floor? Expected: the coverage report carries the current and previous values, and the floor is a gate parameter so that it is versioned with the gate, not with the agent's output.
  • (level 3) Why is a missing coverage report only a warning by default? Expected: strict everywhere erodes daily flow, so the default warns and the release branches run strict, where the warning becomes a block.
  • (level 4) The agent rewrites a test to always pass instead of deleting it. What catches that? Expected: coverage stays the same, so the gate does not, and the reviewer's diff of test files or a mutation check in CI is the layer that sees it.
  • (level 4) How do you keep the human override from becoming the way around the floor? Expected: an override writes a signed row with the finding code, the reason, the user and the commit, and review reads that log.

Where it is taught. The verification gates lesson adds the coverage floor and the strict mode, and the scope contracts lesson makes a deletion a checked write.

Explain the mechanismA proposal replaces the script that decides whether an agent task is done with a model judge. The argument is that a judge reads the diff, understands intent, and catches more than a script can. Argue for or against, and say where a judge does belong.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Against. The gate answers one question, is this task complete, and that verdict must be the same for the same artifacts every time, in version control, in CI, with no way for the agent to argue with it. A model judge gives a different answer on a different day and can be talked into a pass. A judge belongs on the review side, where the question is qualitative: is the code readable, secure and on style.

What the gate reads and decides.

Check Source Severity
Every acceptance command ran feedback records block
Every acceptance command exited zero feedback records block
No write to a forbidden path scope report block
No off-scope write scope report block or warn
Every block-severity rule passed rule report block
No null exit code feedback records block
Touched files match the allowed globs both warn

A warn annotates the verdict. A block prevents passed: true. Every check is a comparison between artifacts the agent already produced. No judgement is needed, so no judge is needed.

Why determinism is the point.

Three failure shapes dominate agent work: "looks good", "tests passed" with no record, and acceptance read loosely enough to mean anything. A model judge is subject to all three. It reads the diff and decides it looks good. It reads the transcript and believes the claim. It interprets the acceptance line generously. The script cannot do any of that, because it never reads prose. The lesson pairs the two kinds of signal: verifiable checks such as tests, schema checks and exit codes answer whether the code solved the problem, and rubric judges answer whether it is readable and on style. Mixing them collapses the signal.

Overrides are human and signed.

A block cannot be overridden by the agent. A human can override it, and the override writes a row with the finding code, a reason, the signing user and the current commit into an audit log that git tracks. The runtime refuses an override without a signature. That is the line between an override policy and an override theater.

One report, several layers.

The gate writes one verification_report.json per task under one path, and CI reads the same path. Around it sit other deterministic layers: a pre-commit hook, a CI status check, a pre-tool authorization hook and a pre-merge gate. A failure in one layer is caught by the next. The pre-commit hook does not depend on the agent following instructions, but it is a local check that git commit --no-verify skips, so the CI status check and the pre-merge gate hold the verdict.

Where the judge goes.

The reviewer, a separate pass with a different role, reads the diff and the reports after the gate passes. It scores readability, security and style. Its output goes to a human or into the handoff, never into the gate's verdict.

Plausible wrong answers.

  • "A judge understands intent, so it catches more." The gate does not need intent, and a judge that infers intent can be convinced that an incomplete task is complete.
  • "Run the judge and the script, and pass if either passes." The judge then becomes the way around the script, so the deterministic checks must decide done and the judge must only annotate.
  • "Let the agent explain why a block does not apply." The agent is the party under test, and an override needs a human signature with a reason.

Follow-ups an interviewer may ask.

  • (level 3) An agent deletes failing tests, and the gate stays green. Which check is missing? Expected: a coverage floor read from a coverage report, with a block when coverage falls below the floor or drops by more than one percentage point against the previous merge.
  • (level 3) When is promoting every warning to a block the right default? Expected: on release branches and in post-incident triage through a strict flag, and not globally, because strict everywhere erodes daily flow.
  • (level 4) What stops the override log from becoming a formality? Expected: the runtime refuses an unsigned entry, the log is in git, and review reads it, so every override has a name and a reason attached.
  • (level 4) The gate and the reviewer disagree. Who wins? Expected: the gate decides whether the task is done, and the reviewer decides whether it is good, so a gate failure blocks regardless of the review, and a review failure reopens the task without touching the verdict.
