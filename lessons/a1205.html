In plain words first
The idea in one line

LLaVA (April 2023) is the most copied multimodal architecture on the planet. It replaced BLIP-2's Q-Former with a single linear projection, replaced Flamingo's gated cross-attention with plain token concatenation, and trained on 158k visual-instruction samples generated by GPT-4 from text-only captions. Any practitioner who built a VLM between 2023 and 2026 built some variant of LLaVA. LLaVA-1.5 swapped in an MLP projector and a 336px encoder. LLaVA-NeXT added AnyRes tiling for high-resolution input. LLaVA-OneVision unified image, multi-image, and video in one recipe.

Terms you'll hear
Term What people say What it actually means

Image token " placeholder" Prompt marker replaced by N projected visual tokens before inference
Visual instruction tuning "LLaVA stage 2" Training on GPT-4-generated (image, instruction, response) triplets
Stage 1 alignment "Projector pretraining" Freeze ViT and LLM, train projector with LM loss on captions
AnyRes "Multi-crop tiling" Split high-res image into a tile grid and concatenate each tile's visual tokens

Vision encoder freeze "Backbone locked" CLIP weights do not update in stage 1, sometimes not in stage 2 either
ShareGPT4V "Better captions" 1M dense captions generated by GPT-4V, used for higher-quality alignment
VQA "Visual question answering" Task of answering a free-form question about an image
Prismatic VLMs "Design-space paper" Karamcheti 2024 ablation systematically testing projector and data choices

The problem

In plain words first

LLaVA is the simplest way to make a chat model see. A frozen image encoder (CLIP ViT-L/14) turns a photo into 576 patch vectors. A small two-layer network, the projector, maps each one to the width of the language model's word embeddings. The prompt has one placeholder, <image>, and those 576 vectors are pasted where it stands, so the language model reads the picture as 576 extra "words" before the question. Training happens in two steps: first only the projector learns, on image captions; then the language model is tuned on visual question-and-answer conversations. This lesson follows the recipe and runs the real pipeline, from placeholder to generated tokens, on a tiny test model with LLaVA-1.5's exact shapes. Only the code is being checked, so its random weights are fine. No model is trained.

BLIP-2's Q-Former (Lesson 12.03) compresses an image to 32 tokens. Clean, efficient, good for benchmarks. But it has two problems.

First, the Q-Former is trainable but its loss is not the final task. Stage 1 trains ITC+ITM+ITG. Stage 2 trains LM loss. The queries learn some intermediate representation that the LLM then has to decode. Information is lost in the bottleneck.

Second, the Q-Former takes 188M params, and at LLaVA's 2023 scale you had to co-design it with your target LLM. Change the LLM, retrain the Q-Former. Change the vision encoder, retrain. Every combination was a separate R&D project.

The LLaVA answer was embarrassing in its simplicity: take the ViT's 576 patch tokens, pass each through a 2-layer MLP (1024 → 4096 → 4096), and dump all 576 into the LLM's input sequence. No bottleneck. No stage 1 pretraining on weird objectives. Just train the MLP on a direct LM loss.

Where does the data come from? LLaVA's second insight: use GPT-4 (text-only) to generate instruction data. Feed GPT-4 the COCO caption and bounding-box data for an image, ask it to produce conversations, descriptions, and complex reasoning questions. 158k instruction-response turns for free. No human annotation.

The result: a VLM that ran on 8 A100s for one day, beat Flamingo on MMMU, and shipped an open checkpoint the community could extend. By late 2023 it had spawned 50+ forks.

Idea 1 · The architecture

LLaVA-1.5 at 7B: - Vision encoder: CLIP ViT-L/14 @ 336 (frozen during stage 1, optionally unfrozen stage 2). - Projector: 2-layer MLP with GELU activation, 1024 → 4096 → 4096. - LLM: Vicuna-7B v1.5 (a 13B variant uses Vicuna-13B; later forks moved to Llama-3.1-8B).

Forward pass on an image + text prompt:

img -> ViT -> 576 patches of dim 1024
patches -> MLP -> 576 tokens of dim 4096
prompt: system + "<image>" placeholder + user question
replace <image> token with the 576 projected tokens
feed the full sequence to the LLM
decode response

The image occupies 576 tokens of the LLM context. At 2048 context, that leaves 1472 tokens for text. At 32k context, it is a rounding error.

Idea 2 · Stage 1: projector alignment

Freeze ViT. Freeze LLM. Train only the 2-layer MLP. Dataset: 558k image-caption pairs (LAION-CC-SBU). Loss: language modeling on the caption, conditioned on the projected image tokens.

In a single epoch at batch 128 this is done in a few hours. The projector learns to map ViT-space to LLM-space. No task-specific supervision.

Idea 3 · Stage 2: visual instruction tuning

Keep the projector trainable. Unfreeze the LLM (usually fully, sometimes LoRA). The original LLaVA trained on 158k visual-instruction samples; LLaVA-1.5 used a 665k mixture that adds academic VQA data and ShareGPT text conversations.

The instruction data is the trick. Liu et al. generated it by: 1. Take a COCO image. 2. Extract the text description (5 human captions + bounding-box list). 3. Send to GPT-4 with three prompt templates: - Conversation: "Generate a back-and-forth dialogue between a user and assistant about this image." - Detailed description: "Give a rich, detailed description of the image." - Complex reasoning: "Ask a question that requires reasoning about the image, then answer it." 4. Parse GPT-4's output into (instruction, response) pairs.

None of this touches the image directly — only the text description. GPT-4 hallucinates plausible image content. Some noise, but it worked: 158k turns was enough to unlock dialogue.

The same idea as a formula

The projector. For each patch feature fi​∈Rdv​ from the second-to-last ViT layer (the [CLS] token is dropped):

hi​=W2​GELU(W1​fi​+b1​)+b2​,W1​∈Rd×dv​, W2​∈Rd×d,
with dv​=1024 and the LLM width d=4096 for LLaVA-1.5-7B.

The sequence the LLM reads: the prompt's embeddings with the ⟨image⟩ slot replaced by h1​,…,h576​.

The training loss is next-token cross-entropy on the answer tokens only:

L=−t∈answer∑​logpθ​(yt​∣y<t​,h1:576​,question),
with stage 1 updating only W1​,b1​,W2​,b2​ and stage 2 also the LLM's weights θ.

Worked example
Counting LLaVA-1.5-7B
  • Grid: 336/14=24, so 242=576 patch tokens, plus [CLS] = 577; [CLS] is dropped.
  • Projector: 1024⋅4096+4096+4096⋅4096+4096=4,198,400+16,781,312=20,979,712 parameters.
  • One image plus a 20-token question: about 600 tokens before the answer. With LLaVA-1.5's 2,048-token training length, three images would already use 1,728.
  • In stage 2, a training sample of 605 tokens with an 11-token answer contributes loss on 11 tokens: the other 594 (prompt and image slots) are masked.
Check your mental model
  • ✗ "LLaVA's image tokens are words from the vocabulary."

  • ✗ "Stage 1 teaches the model to answer questions."
    ✓ Stage 1 only aligns the projector with the LLM's input space on captions; stage 2 teaches dialogue.

The LLaVA pipeline, stage by stage

A tiny test checkpoint with LLaVA-1.5's geometry: ViT at 336 px with 14-px patches, an MLP projector and a Llama-style decoder, with random weights and 2.4M parameters. The run follows one Imagenette photo through processor, vision tower, projector and generation. It checks the hand-filled embeddings against the library's own image features, then reads the real LLaVA-1.5-7B configuration. The tiny model is there to check the code path, so its generated words are meaningless. A few seconds.

import torch
from datasets import load_dataset
from transformers import AutoConfig, AutoProcessor, LlavaForConditionalGeneration, logging
logging.set_verbosity_error()

# The LLaVA-1.5 pipeline, stage by stage, on a tiny test checkpoint (random weights, 2.4M parameters) that has
# LLaVA-1.5's exact geometry: CLIP-style ViT at 336 px with 14-px patches, an MLP projector, a Llama-style decoder.
repo = "trl-internal-testing/tiny-LlavaForConditionalGeneration"
cfg = AutoConfig.from_pretrained(repo)
proc = AutoProcessor.from_pretrained(repo)
model = LlavaForConditionalGeneration.from_pretrained(repo).eval()
image = load_dataset("Multimodal-Fatima/Imagenette_validation", split="validation")[0]["image"].convert("RGB")

prompt = "USER: <image>\nWhat is in this photo? ASSISTANT:"
x = proc(images=image, text=prompt, return_tensors="pt")
n_img = int((x.input_ids == cfg.image_token_index).sum())
print(f"1. prompt with one <image> placeholder -> {x.input_ids.shape[1]} tokens, of which {n_img} are image slots")
print(f"   pixels {tuple(x.pixel_values.shape)}: {image.size[0]}x{image.size[1]} photo resized and cropped to 336x336")

with torch.no_grad():
    vis = model.model.vision_tower(x.pixel_values, output_hidden_states=True)
    feats = vis.hidden_states[cfg.vision_feature_layer]            # LLaVA reads the second-to-last ViT layer
    print(f"2. vision tower: {len(vis.hidden_states) - 1} layers; layer {cfg.vision_feature_layer} output {tuple(feats.shape)} "
          f"= [CLS] + 24x24 patches")
    feats = feats[:, 1:]                                            # 'default' strategy drops [CLS]
    proj = model.model.multi_modal_projector(feats)
    print(f"3. projector (Linear-GELU-Linear) {tuple(feats.shape)} -> {tuple(proj.shape)}: one LLM-width vector per patch")
    emb = model.get_input_embeddings()(x.input_ids)
    slots = (x.input_ids == cfg.image_token_index)
    emb[slots] = proj.reshape(-1, proj.shape[-1])                   # what the model does internally
    ref = model.model.get_image_features(pixel_values=x.pixel_values, vision_feature_layer=cfg.vision_feature_layer,
                                         vision_feature_select_strategy=cfg.vision_feature_select_strategy)
    ref = ref.pooler_output if hasattr(ref, "pooler_output") else ref
    ref = torch.cat(list(ref)) if isinstance(ref, (list, tuple)) else ref.reshape(-1, proj.shape[-1])
    print(f"4. {int(slots.sum())} image slots filled with projector outputs; "
          f"matches the library's own image features: {torch.allclose(emb[slots], ref, atol=1e-5)}")
    out = model.generate(**x, max_new_tokens=8, do_sample=False)
print(f"5. generate runs end to end: {out.shape[1] - x.input_ids.shape[1]} new tokens "
      f"({proc.decode(out[0, x.input_ids.shape[1]:])!r}: random weights, so the words are meaningless)")

real = AutoConfig.from_pretrained("llava-hf/llava-1.5-7b-hf")
v, t = real.vision_config, real.text_config
print(f"\nreal LLaVA-1.5-7B, same pipeline: {(v.image_size // v.patch_size) ** 2} image tokens of width {v.hidden_size} "
      f"-> projector -> width {t.hidden_size}; projector = {v.hidden_size * t.hidden_size + t.hidden_size + t.hidden_size ** 2 + t.hidden_size:,} parameters")

   pixels (1, 3, 336, 336): 500x487 photo resized and cropped to 336x336
2. vision tower: 2 layers; layer -2 output (1, 577, 16) = [CLS] + 24x24 patches
3. projector (Linear-GELU-Linear) (1, 576, 16) -> (1, 576, 16): one LLM-width vector per patch

Reading this output

One placeholder becomes 576 slots. The prompt is 18 text tokens long, but the processor expands <image> into 576 image-token ids, so the model receives 594 tokens. The photo (500 × 487 pixels) is resized and cropped to 336 × 336 first.

The vision features come from the second-to-last layer. LLaVA reads layer −2 of the ViT, not the final one, and drops the [CLS] token: 577 vectors become the 576 patch vectors. The LLaVA authors found the penultimate layer works better than the last, which is tuned to CLIP's contrastive objective.

The projector keeps one vector per patch. No compression: 576 in, 576 out, each now as wide as the language model's embeddings (16 in this tiny model, 4,096 in LLaVA-1.5-7B).

The hand-built sequence matches the library. Writing the projector outputs into the image slots by hand gives exactly the library's own image features (True). This is the whole multimodal mechanism: after this step the language model just sees a sequence of vectors.

Generation runs; the words are noise. The test checkpoint has random weights, so "Fish Ky abort…" means nothing. It confirms that the code path works end to end. The real LLaVA-1.5-7B has the same 576 tokens and a 21M-parameter projector from width 1,024 to 4,096.

What the training would update

The same tiny model computes the loss masking of visual instruction tuning: which tokens are supervised and what the loss is with and without masking. Then the real LLaVA-1.5-7B is built on the meta device to count trainable parameters in stages 1 and 2. Nothing is trained. A few seconds.

import torch
from transformers import LlavaForConditionalGeneration
# uses proc, model, cfg, image and real from the run above

# Visual instruction tuning: which tokens the loss is computed on. Only the assistant's answer is supervised;
# the system text, the question and the 576 image slots get label -100 (ignored by the cross-entropy).
prompt = "USER: <image>\nWhat is in this photo? ASSISTANT:"
answer = " A man holding a large fish on a boat.</s>"
x = proc(images=image, text=prompt + answer, return_tensors="pt")
n_prompt = proc(images=image, text=prompt, return_tensors="pt").input_ids.shape[1]
labels = x.input_ids.clone()
labels[:, :n_prompt] = -100
print(f"sequence {x.input_ids.shape[1]} tokens: {n_prompt} masked (system, question, 576 image slots), "
      f"{int((labels != -100).sum())} supervised answer tokens")
with torch.no_grad():
    masked = model(**x, labels=labels).loss
    everything = model(**x, labels=torch.where(x.input_ids == cfg.image_token_index, -100, x.input_ids)).loss
print(f"loss on the answer only: {masked:.3f}; on every text token: {everything:.3f} (random weights: both near ln(vocab) = "
      f"{torch.log(torch.tensor(float(model.config.text_config.vocab_size))):.3f})")

# Which parameters train in each stage (requires_grad), counted on the real LLaVA-1.5-7B built on the meta device
with torch.device("meta"):
    big = LlavaForConditionalGeneration(real)
def trainable(stage):
    for n, p in big.named_parameters():
        p.requires_grad = ("multi_modal_projector" in n) or (stage == 2 and ("language_model" in n or "lm_head" in n))
    return sum(p.numel() for p in big.parameters() if p.requires_grad)
total = sum(p.numel() for p in big.parameters())
for stage, what in [(1, "projector only"), (2, "projector + LLM")]:
    n = trainable(stage)
    print(f"stage {stage} ({what}): {n / 1e6:,.0f}M of {total / 1e9:.2f}B parameters trainable ({n / total:.1%})")
What you should see
sequence 605 tokens: 594 masked (system, question, 576 image slots), 11 supervised answer tokens
loss on the answer only: 10.340; on every text token: 10.374 (random weights: both near ln(vocab) = 10.375)
stage 1 (projector only): 21M of 7.06B parameters trainable (0.3%)
stage 2 (projector + LLM): 6,760M of 7.06B parameters trainable (95.7%)
Reading this output

Most of a training sample is not supervised. The sample is 605 tokens: 594 for the system text, the question and the 576 image slots, all with label −100, and 11 for the answer. Only those 11 positions produce a loss. The model is taught to answer, not to predict its own prompt or the image.

With random weights the two losses are almost equal, both close to ln(vocabulary size) = 10.375, the loss of a uniform guess. In a trained model they differ a lot. Prompt text is often predictable boilerplate, and including it would dilute the signal from the answer.

The two stages touch very different amounts of the model. In stage 1 only the projector trains: 21M of 7.06B parameters, 0.3%. That is why alignment takes hours. In stage 2 the language model is unfrozen too: 6.76B, 95.7%. Only the 0.3B vision tower stays frozen. This is where the GPU cost and the risk of damaging the language model's text skills lie, which is why many fine-tuning projects use LoRA in stage 2.

Idea 4 · Why the community copied this

  • No stage-1-specific losses to tune. LM loss throughout.
  • Projector trains in hours, not days.
  • LLM can be swapped (LLaVA-Llama2, LLaVA-Mistral, LLaVA-Llama3) by retraining just the projector.
  • Visual-instruction data pipeline uses GPT-4 and is cheap to regenerate for a new domain.

Idea 5 · LLaVA-1.5 and LLaVA-NeXT

LLaVA-1.5 (October 2023) added: - Academic-task data (VQA, OKVQA, RefCOCO) mixed into instruction tuning. - Better system prompt. - A 2-layer MLP projector in place of the original single linear layer, and CLIP ViT-L/14 at 336px (576 tokens) in place of 224px (256 tokens). Training sequences stayed at 2048 tokens. - A grid-splitting HD variant in the paper, which LLaVA-NeXT later shipped as AnyRes.

LLaVA-NeXT (January 2024) added: - AnyRes: split high-res images into a 2x2 or 1x3 grid of 336x336 crops, plus one global low-res thumbnail. Each crop becomes 576 tokens. A 2x2 grid plus the thumbnail gives about 2880 visual tokens per image. A 1x3 grid has fewer crops, so it costs fewer tokens. OCR and chart tasks jumped. - Better instruction data mixture with ShareGPT4V (high-quality GPT-4V captions). - Stronger base LLMs (Mistral-7B, Yi-34B).

Idea 7 · The comparison to Q-Former

Q-Former (BLIP-2) MLP (LLaVA)
Visual tokens per image 32 576 (base) or about 2880 (AnyRes, 2x2 grid)
Trainable params 105M (inference model; 188M with the stage-1 text path) 21M projector (LLaVA-1.5-7B), plus the LLM in stage 2
Stage 1 loss ITC+ITM+ITG LM only
LLM drop-in Requires retrain Swap with minimal retrain
Multi-image Awkward Natural (concat)
Video Awkward Natural (per-frame concat)
Token budget Small Large

MLP wins on simplicity and token flexibility. Q-Former wins on token budget. By late 2023 the token budget was no longer the binding constraint (LLM contexts grew to 32k-128k+) and simplicity dominated.

Idea 8 · The prompt format

A chat between a curious human and an artificial intelligence assistant. The assistant gives helpful, detailed, and polite answers to the human's questions. USER: <image> Describe this image in detail. ASSISTANT: The image shows ...

<image> is a placeholder token. Before tokenization, it is replaced with the 576 visual tokens (or about 2880 with a 2x2 AnyRes grid). Tokenizer sees a slightly longer sequence than it was trained on, but the LLM handles the novel input because stage 1 taught it to.

Idea 9 · Parameter economy

LLaVA-1.5-7B breakdown: - CLIP ViT-L/14 @ 336: 303M (frozen stage 1, often unfrozen stage 2). - Projector (2 linear layers, 1024 → 4096 → 4096): 20,979,712 parameters (21.0M). - Vicuna-7B v1.5 (a Llama-2-7B fine-tune): 6.74B, including its embeddings and output layer. - Total: 7.06B parameters. Trainable in stage 1: 21M (0.3%); in stage 2: 6.76B (95.7%), everything except the vision tower (measured below).

Training cost: the LLaVA-1.5 paper reports about one day on a single 8×A100 node for the full two-stage recipe. One day, one node, reproducible. That is why LLaVA spread.

Industry practice
What's current (2024–2026)
  • LLaVA's shape is the default open-VLM shape: vision encoder → MLP projector (with patch merging) → LLM, in Qwen2.5-VL and Qwen3-VL, InternVL, LLaVA-OneVision, Gemma 3 and SmolVLM.
  • Encoders and LLMs are usually unfrozen in later stages: current recipes train the projector first, then tune everything (often including the vision encoder) on large instruction mixtures.
  • Instruction data comes from strong VLMs, not text-only GPT-4: ShareGPT4V-style captions, synthetic OCR, chart and document data, and curated mixtures such as The Cauldron and LLaVA-OneVision's data.
  • Training libraries support this out of the box: Hugging Face TRL's SFT trainer handles vision-language models and masks prompts.

Sources: LLaVA (arXiv 2304.08485), LLaVA-1.5 (arXiv 2310.03744), LLaVA-OneVision (arXiv 2408.03326), Hugging Face LLaVA documentation, TRL SFT trainer.

Recap
What to keep from this lesson
  • LLaVA = frozen ViT + MLP projector + LLM; image patches become 576 input vectors.
  • The <image> placeholder is replaced by projected patch features before the LLM runs.
  • Stage 1 trains only the projector on captions; stage 2 tunes the LLM on instructions.
  • Loss is computed on answer tokens only.
  • Simplicity won: swap the LLM, retrain a 21M projector, and you have a new VLM.

Ship it

This lesson produces outputs/skill-llava-vibes-eval.md. Given a LLaVA-family checkpoint, it runs a 10-prompt vibes-eval suite (3 captioning, 3 VQA, 2 reasoning, 2 refusal) and reports a human-readable scorecard. Not a benchmark; a smoke test to confirm the projector and LLM are connecting well.

outputs/skill-llava-vibes-eval.md

---
name: llava-vibes-eval
description: Run a 10-prompt vibes-eval on a LLaVA-family VLM and produce a human-readable scorecard.
version: 1.0.0
phase: 12
lesson: 05
tags: [llava, vlm, vibes-eval, instruction-tuning]
---

Given a LLaVA-family VLM (LLaVA-1.5, LLaVA-NeXT, LLaVA-OneVision, or a community fork) and a test image set, run a 10-prompt smoke test covering captioning, VQA, reasoning, refusal, and format compliance. Produce a scorecard that confirms the projector and LLM are connecting correctly.

Produce:

1. Ten prompts with expected-behavior descriptions:
   - Three captioning (short, detailed, creative).
   - Three VQA (counting, color, presence of object).
   - Two reasoning (compare two regions, cause-and-effect).
   - Two refusal (private individual, PII-identifying).
2. Per-prompt score. Pass / partial / fail with one-line justification.
3. Overall pattern diagnosis. If captioning passes but VQA fails, suspect stage-2 data mix. If detailed captioning shows hallucination, suspect insufficient ShareGPT4V-style data. If refusals fail, flag a safety-data gap.
4. Resolution check. Run one OCR-requiring prompt at 336x336 base and again at AnyRes; note the delta. Low-res failure is expected; high-res failure means AnyRes is mis-configured.
5. Suggested follow-up. Three specific training-data additions the caller could run if specific categories fail.

Hard rejects:
- Scoring VLMs on benchmark numbers without also running the vibes suite. Benchmarks can be gamed; vibes reveal real deployment readiness.
- Conflating hallucination with stylistic verbosity. Flag specifically which objects are invented vs merely elaborately described.
- Claiming a pass on reasoning prompts without checking the reasoning chain, not just the final answer.

Refusal rules:
- If the caller asks to vibes-eval a proprietary VLM (Gemini, Claude, GPT-5V) without API access, refuse — the test needs actual inference.
- If the target use case is medical diagnosis or legal advice, refuse — vibes-eval is not a certification and must not be used for high-stakes domains.
- If no images are provided, refuse — the test is image-grounded by definition.

Output: a scorecard with 10 rows (prompt, image, expected, actual, pass/partial/fail), an overall pattern diagnosis, and a three-item follow-up list. End with a "what to read next" paragraph pointing to Lesson 12.06 (AnyRes) for resolution-related failures or Lesson 12.07 (ablations) for data-mixture tuning.

Solutions

SolutionP1 · 594 tokens, 576 from the image

594 tokens, of which 576 are image slots: the 24 × 24 patch grid of a 336-px image with 14-px patches. The text ("USER:", the question, "ASSISTANT:" and special tokens) is only 18 tokens. A single image costs more context than most questions about it, and five images cost 2,880 tokens. That is why later models merge patches or tile carefully (Lesson 12.6).

SolutionB1 · The model learns to predict its own prompts

The loss now also rewards predicting the system prompt and the user's question. Those are the same few templates in every sample, so they are easy to learn and quickly reach a low loss. They then make up a large share of the gradient, while the answers, the part you care about, get a smaller share. The finished model can drift into generating user-style text: continuing with "USER: …" turns, repeating the template, or asking itself questions. Its loss curve also looks better than its answers are. Mask everything except the assistant's tokens (labels −100), as the run above does. Libraries such as TRL do this with an assistant-only loss option. Check a decoded batch to confirm that only the answers are supervised.

Estimate itA product manager asks how much of the context window one image uses in a LLaVA-style model with a 336-pixel encoder. Give the number, say where it comes from, and say how it changes with high-resolution tiling or with a query-based bridge.

Level 1 of 4 · about 8 minutes to answer well.

Short answer. One image costs 576 tokens: the encoder cuts the 336-pixel image into 14-pixel patches, a 24 by 24 grid, and the projector passes every patch token through. In a 2048-token context that leaves 1472 tokens for text; at 32k or 128k it is a small share. Tiling multiplies it: a 2 by 2 grid of 336-pixel crops plus one global thumbnail gives about 2880 tokens per image, and a 1 by 3 grid plus the thumbnail gives fewer, because it has one crop less. A query-based bridge compresses any image to a fixed 32 tokens, and a resampler to 64.

Where the count comes from.

336 / 14 = 24 patches per side
24 x 24 = 576 patch tokens
each token: 1024 wide from the encoder, 4096 wide after the projector

The earlier 224-pixel encoder gave 256 tokens. The move to 336 pixels raised the count to 576, and the training sequences stayed at 2048 tokens.

What it costs in context.

Context One image
2048 576 tokens, leaving 1472 for text
32k a small share
128k a rounding error

Tiling for high resolution.

Documents and charts need more pixels. The tiling scheme splits the image into a 2 by 2 or 1 by 3 grid of 336-pixel crops, adds one low-resolution global view, and concatenates the tokens of every crop: about 2880 visual tokens per image for the 2 by 2 grid, and fewer for the 1 by 3 grid, which has one crop less. Reading and chart scores jumped with it.

The compressing bridges.

A query-based bridge uses a fixed set of 32 learned query vectors that cross-attend to the patch tokens, so any image becomes 32 tokens. A resampler with 64 latents does the same at 64. The price is a bottleneck: the language model never sees the raw patches.

How many tokens you need.

The ablations in the recipes lesson put the sweet spot for most tasks at 576 to 1024 visual tokens per image, 64 as too few for reading text, and 2048 or more as useful only for documents and charts. The token count explains more of the variance in benchmark scores than the connector architecture does.

Plausible wrong answers.

  • "An image costs one token, the placeholder." The placeholder is replaced by one embedding per patch token before the forward pass; the encoder grid sets the count.
  • "Higher resolution is free because the encoder is fixed." More patches means more visual tokens in the language model's sequence, and the language model's compute grows with them.
  • "The connector decides the quality, so pick the bridge first." At a fixed token count the connector barely matters; the token count and the encoder matter more.

Follow-ups an interviewer may ask.

  • (level 1) Why does a higher input resolution raise the token count? Expected: the patch size is fixed, so more pixels per side means more patches per side, and the count grows with the square of the side.
  • (level 2) Which tasks justify the tiling cost? Expected: text in images, charts and documents; general scene questions gain little from it.
  • (level 2) When does the 32-token bridge win? Expected: when the token budget binds, as with long video or many images per prompt; for one image in a long context the compression buys little.
  • (level 3) How do you size the budget for video? Expected: tokens per frame times frames, so a compressing bridge or heavy frame sampling is the only way to fit minutes of video; count the tokens before you pick the bridge.

Where it is taught. The LLaVA lesson counts the tokens per image and per tiled image, the BLIP-2 lesson explains the fixed-count bridge, and the recipes lesson gives the token budget ablations.

Take-homeTake-home. You get a frozen vision encoder that emits 197 tokens of width 768 per image and a frozen text embedding table of width 512. Build the smallest module that lets the two talk, train it on paired samples, and ship tests that prove it works. Describe the design, the loss, how you train it, and the tests.

Level 2 of 4 · about 30 minutes to answer well.

Short answer. Pool the 197 image tokens to one vector, pass it through a two-layer MLP, 768 to 1024 to 512 with a GELU between, and compare it with the mean-pooled caption embedding through a cosine alignment loss, one minus the cosine. Train only the MLP, about 1.3M parameters, with the encoder and the table frozen, for a few hundred steps over a few dozen pairs. The tests: the output shape equals the text width, the frozen parts have no trainable parameters, the loss is zero on identical vectors and two on opposite vectors, a gradient reaches the projector after one backward pass, and the loss at the last step is lower than at the first.

Design.

image tokens (B, 197, 768) -> pool -> (B, 768)
MLP: Linear(768, 1024) -> GELU -> Linear(1024, 512) -> (B, 512)
caption ids -> frozen table -> mean over tokens -> (B, 512)
loss = 1 - cos(image_emb, text_emb)

Pooling: the first token is the simplest choice; a mean over the 196 patch tokens is the alternative, and the exercise compares them. Two layers, because one linear map cannot bend the space; the GELU gives the one bend that aligns the two bases.

Parameters.

Layer Shape Parameters
first linear 768 by 1024 768 times 1024, plus 1024
GELU 0
second linear 1024 by 512 1024 times 512, plus 512

About 1.3M in total, next to an encoder of 86M. Both big parts have requires_grad=False on every parameter.

Training loop.

  • Build 32 synthetic pairs from a seed when no dataset is allowed, and cycle them.
  • One optimizer over the projector parameters only.
  • Run 200 steps and print the loss every 25 steps. The capstone's run falls from about 1.07 to about 0.80.
  • Print the final cosine per pair.

Tests.

  1. The projector output shape matches the configured output width.
  2. The frozen text table and the frozen vision encoder have zero parameters that require a gradient.
  3. The cosine loss is 0 on identical vectors and 2 on anti-parallel vectors.
  4. A gradient reaches the projector weights after one backward pass.
  5. The loss at step 200 is lower than at step 0.

What you ship.

The projector weights are the only new artifact. At inference the encoder still runs its forward pass, then the projector, and the output lands in the text space. The same shape appears in every open adapter model: pool, project, train alone.

The next step, for the discussion.

The per-pair cosine aligns direction; a contrastive batch loss would also push each image away from the other captions in the batch. For a decoder that grounds each word, cross-attention from text queries into the 197 image tokens replaces the pooled vector; that is the following capstone.

Plausible wrong answers.

  • "Fine-tune the encoder as well; it is only 86M parameters." The take-home gives frozen parts for a reason: a few dozen pairs cannot teach the encoder anything, and the test that checks the frozen table would fail.
  • "Use a single linear layer; it is enough for a rotation." The two bases differ by more than a rotation; the non-linearity is what lets one bend close the gap.
  • "Skip the tests; the loss went down." The loss can fall through a shape bug or a leak into the frozen parts; the tests pin the contract that the loss alone cannot.

Follow-ups an interviewer may ask.

  • (level 2) Why cosine and not mean squared error? Expected: alignment means the same direction in the joint space, not equal vectors; cosine is scale-invariant, so the projector is not punished for a norm the text table happens to have.
  • (level 2) What does a learned temperature on the cosine change? Expected: a sharper or flatter loss surface; too small gives noisy gradients and too large plateaus high, as the exercise shows.
  • (level 3) The capstone's run stops near 0.80 after 200 steps. Is that a floor? Expected: no; it is the loss of one run at 200 steps. The projector has 1024 hidden units for 32 pairs, so more steps or a different rate can push the loss lower; on natural pairs, the encoder features set how far the alignment can go.
  • (level 3) How does this module relate to a query-based bridge? Expected: that bridge ends in the same kind of projection to the text width; the difference is that it first compresses the tokens through learned queries instead of pooling.

Where it is taught. The projection capstone specifies the module, the loss, the loop and the five tests, and the cross-attention fusion capstone is the step after it.

Explain the mechanismIn the first training stage of most open vision-language models, both the vision encoder and the decoder are frozen, and only the small projector learns. A junior engineer asks why anyone would train the smallest part first instead of the parts that matter. Answer them.

Level 1 of 4 · about 8 minutes to answer well.

Short answer. The two big parts already work: the encoder represents images, and the language model writes text. What is missing is a translation between their two vector spaces, and that translation is small. Training only the bridge costs a few hundred steps on one GPU, cannot damage either pretrained part, and gives the language model inputs it can read before anyone unfreezes it. Unfreezing the language model comes in the second stage, once the bridge produces tokens that look like language.

What the projector is.

A two-layer MLP: linear, GELU, linear. The capstone's head maps 768 to 1024 to 512 and holds about 1.3M parameters next to an encoder of 86M. The reference open recipe's head maps 1024 to 4096 to 4096, about 22M parameters next to a 303M encoder and a 7B language model.

Why the frozen big parts are the point.

  • Stability. Gradients from a few thousand noisy pairs would overwrite features that the encoder learned from hundreds of millions of images.
  • Cost. The alignment stage of the reference recipe trains on 558k caption pairs in a few hours at a batch of 128. The capstone's version drives its loss from about 1.07 to about 0.80 in 200 steps.
  • A clean signal. With both big parts fixed, the loss moves only through the bridge, so you can read whether the two spaces align.
  • Swappability. Change the language model and retrain the bridge; the encoder stays.

What the loss is.

The reference recipe uses the language-modeling loss on the caption, conditioned on the projected image tokens. The capstone uses a per-pair cosine alignment loss, one minus the cosine between a pooled image vector and a mean-pooled caption embedding, so that the dynamics stay visible; a contrastive batch version is the next lesson.

What comes after.

Stage two unfreezes the language model, fully or through adapters, keeps the bridge trainable, and trains on instruction data. A bridge that was never aligned first gives the language model noise at the start of that stage.

The other kind of bridge.

A query-based bridge with a fixed set of learned vectors compresses the image to a fixed token count. It is larger, 188M parameters in the original, and it still trains with the backbones frozen; the principle is the same.

Plausible wrong answers.

  • "Train the encoder; it is the part that sees." It already sees, and a small dataset cannot teach it more than it loses by overwriting features; the missing part is the translation.
  • "The projector is too small to carry an image." It does not carry the image; it maps tokens that already encode the image into the space the language model reads.
  • "Freezing is only a memory trick." Memory is one gain; the larger ones are stability, a clean training signal, and the ability to swap the language model.

Follow-ups an interviewer may ask.

  • (level 1) What does a frozen parameter mean in code? Expected: requires_grad=False, so the optimizer never sees it, and no memory goes to its gradient or optimizer state.
  • (level 2) Why pool the image tokens before the cosine loss in the capstone? Expected: the caption side is one vector, so the image side needs one vector too; the first token or the mean over all tokens are the usual choices.
  • (level 2) One linear layer would be smaller still. Why two? Expected: a single linear map can rotate and rescale but cannot bend; the GELU between two layers gives the one non-linear bend that aligns contrastive vision features to language embeddings.
  • (level 3) What breaks if you skip the alignment stage and start with instruction tuning with everything unfrozen? Expected: the language model receives unaligned inputs, and its gradients on a small set damage its text ability; the two stages exist to give it readable inputs first.

Where it is taught. The projection capstone trains the bridge alone with a cosine loss, the LLaVA lesson gives the two-stage recipe and its parameter counts, and the BLIP-2 lesson explains the frozen-backbone economics.

Explain the mechanismDraw the standard architecture of a vision-language model that answers questions about an image. Name its three parts, say what each one contributes, and say which part you would expect to train when a team fine-tunes on a few thousand labelled images.

Level 1 of 4 · about 8 minutes to answer well.

Short answer. A vision encoder, a projector and a language model. The encoder, a pretrained vision transformer, turns the image into patch tokens. The projector, a small two- to four-layer MLP or a query-based bridge, maps those tokens into the language model's embedding space, where they replace a placeholder token in the prompt. The decoder language model reads image tokens and text tokens as one sequence and writes the answer; in most fine-tunes the encoder and the language model stay frozen or get adapters, and the projector is where the training happens.

The three parts.

  1. Vision encoder. A pretrained vision transformer, contrastively trained or self-supervised, produces one token per patch. With a 336-pixel input and a 14-pixel patch, the reference model gets 576 tokens of width 1024.
  2. Projector. A two-layer MLP with a GELU between the layers, from the encoder width to the language model width, 1024 to 4096 to 4096 in the reference model. The capstone's toy head, 768 to 1024 to 512, has about 1.3M parameters.
  3. Language model. A decoder-only model that receives the projected image tokens in place of an image placeholder and the text tokens after them, then generates text.

How the pieces meet.

The prompt holds a placeholder image token. Before the forward pass, the embeddings at those positions are overwritten with the projected vision tokens, and the batch is padded so that every sample has the same count. The language model sees one sequence; nothing else about it changes.

Who trains.

  • Stage one, alignment: freeze the encoder and the language model, and train the projector on image and caption pairs with the language-modeling loss on the caption. The capstone's version uses a cosine alignment loss between a pooled image vector and a caption vector, and that loss falls from about 1.07 to about 0.80 in 200 steps with only the projector moving.
  • Stage two, instruction tuning: unfreeze the language model, often through adapters, keep the projector trainable, and train on image, question and answer triples.
  • Large pretraining on interleaved image and text data sits between them in frontier recipes and is out of reach for a small team.

Why the projector is enough.

The encoder already represents the image, and the language model already reasons in words. The projector's job is to express one in the vocabulary of the other, which a small bend of the space can do. The capstone's encoder has 86M parameters and its projector about 1.3M; training only the projector means a few hundred steps on one GPU.

Plausible wrong answers.

  • "The language model looks at pixels through cross-attention into the image." In this pattern the image enters as tokens in the input sequence; cross-attention bridges are a different family.
  • "Fine-tune the vision encoder first; it is the part that sees." The encoder is pretrained and frozen in stage one; the projector is where a small team's training budget goes.
  • "The projector must be a large network to carry the image." It is a two-layer MLP far smaller than the encoder in the capstone, and it trains in minutes.

Follow-ups an interviewer may ask.

  • (level 1) Why does the projector need two layers and not one? Expected: one linear layer rotates and scales; the non-linearity between two layers lets the map bend, which is enough to align contrastive vision features to a language model's embeddings.
  • (level 2) What does the language model see where the image was? Expected: a run of embeddings, one per projected patch token, in place of the placeholder; the model treats them as tokens with no special handling.
  • (level 2) What does a bridge with a fixed set of learned queries change? Expected: it compresses the patch tokens to a fixed count, which saves context at the cost of a bottleneck; the MLP keeps every patch.
  • (level 3) Which part sets the ceiling on reasoning quality? Expected: the language model; the encoder can only feed it, so a larger language model lifts the benchmarks more than a cleverer bridge.
