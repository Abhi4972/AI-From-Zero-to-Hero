Vertical Means Evidence End to End

In plain words first

A slice is the smallest piece of real work that can change your decision. It runs through the actual workflow end to end, but narrowly: a few users, real data, read-only. First list the proof the slice must produce (the riskiest open assumptions from 14.49). A slice that does not produce all of it is out, however cheap it is. Only then compare the eligible slices by value, evidence, effort and consequence, and write down in advance what you will do if it fails. Getting from pilot to value is covered in Lesson 14.162 (linked above). This lesson picks the incident agent's next slice, builds the diagnosis half and checks it against its stop rule.

A useful slice crosses the minimum real workflow needed to observe an outcome. It can be narrow in users, data, duration, and capability. It should not be narrow by removing the exact uncertainty you need to test.

Examples:

  • A read-only replay across ten real incidents tests service identification and operator trust.
  • A polished dashboard on synthetic data may test comprehension but not data feasibility.
  • A production auto-remediator tests everything at once with unacceptable consequence.

Define Required Proof First

Take the highest-risk open assumptions and turn them into a required proof set. A candidate slice is eligible only if it covers that set.

Then compare eligible slices on:

Dimension Direction
Outcome value More is better
Uncertainty reduced More is better
Effort Less is better
Consequence Less is better
Reversibility More is better

The lab’s score is intentionally simple. The eligibility gate matters more than the arithmetic.

Common False Minimums

  • The UI-only minimum: removes the data and operational uncertainty.
  • The infrastructure-only minimum: proves technical possibility without user value.
  • The happy-path minimum: omits the exception that creates most risk.
  • The demo minimum: produces a persuasive artifact but no repeatable measurement.
  • The platform minimum: builds reusable machinery before one workflow earns it.

Add a Stop Rule

Before implementation, write what happens if the slice fails:

  • abandon the outcome;
  • change the target user or situation;
  • test a different mechanism;
  • collect better evidence;
  • narrow authority further.

If every result leads to “keep building,” the slice is not an experiment.

The same idea as a formula

Eligibility first, then a score. With required proof set P and a slice that proves S, the slice is eligible only if P⊆S. Among eligible slices the lesson scores

score=E+κ⋅CV+U​,κ={0.52​reversibleirreversible​

with value V, uncertainty reduced U, effort E and consequence C. The gate is a hard filter, and the score only ranks what passes it.

A stop rule needs precision and coverage. On n cases a diagnosis answers a and gets r right. Then precision =r/a and abstention =1−a/n. Abstaining on everything gives no wrong answers and no help, so the rule needs a bound on both.

Worked example
The chosen slice and the cheap pair
  • Replay, abstain and attach evidence: V=4,U=5,E=3,C=1, reversible, so 3+0.59​=2.571. It is eligible.
  • Approval template alone: 1.56​=4.0, the highest score, but it proves only one of the two required items, so it is ineligible.
  • The template plus 10 more replays as one plan: 2.57​=2.8, eligible. It beats the agent slice, and half of it needs no agent at all.
  • Auto-rollback: 10+2⋅59​=0.45. It is eligible on paper and last on consequence.

This block continues from the one above. The 14 alerts from 14.49 go to Qwen2.5-0.5B-Instruct (greedy, CPU) under three policies, plus a fourth that uses only the gate's catalog lookup. Precision and abstention are compared with the stop rule. About 1 minute.

# This block continues from the one above. Build the diagnosis half of the chosen slice and check it against the
# stop rule. The 14 alerts from 14.49 (10 easy, 4 cascades or outside the catalog) go to Qwen2.5-0.5B-Instruct
# (greedy, CPU) three ways: always answer; asked to say "unknown" when unsure; and always answer behind a gate
# that abstains unless the alert points at exactly one catalog service with no cause elsewhere. A fourth column
# drops the model: the gate's own catalog lookup. About 1 minute.
import os, re, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()
CATALOG = {"checkout-api": ("checkout-",), "payments": ("pay-", "card processor"), "inventory": ("inv-", "stock"),
           "search": ("srch-",), "auth": ("auth-", "log in", "login")}
ALERTS = [("HighLatency service=checkout-api p99=2.4s", "checkout-api"), ("ErrorRate service=payments 5xx=7%", "payments"),
          ("PodCrashLooping service=inventory pod=inv-5d8f", "inventory"), ("HighLatency service=search p99=1.9s", "search"),
          ("TokenErrors service=auth invalid_signature=320/min", "auth"), ("PodCrashLooping pod=pay-7f9c namespace=prod", "payments"),
          ("HighMemory pod=srch-2a1b namespace=prod 93%", "search"), ("Users report they cannot log in", "auth"),
          ("Card processor timeouts rising", "payments"), ("Stock counts negative for 40 products", "inventory"),
          ("Checkout errors: upstream card processor timeouts", "payments"), ("DNS resolution failures across prod namespace", "none"),
          ("HighLatency service=checkout-api, caused by inv-5d8f slow queries", "inventory"), ("Login page slow after search deploy", "none")]
catalog_text = "\n".join(f"- {k}: matches {', '.join(v)}" for k, v in CATALOG.items())

def ask(alert, allow_unknown):
    tail = " If you are not sure, answer unknown." if allow_unknown else ""
    ids = tok.apply_chat_template([{"role": "user", "content": f"Service catalog:\n{catalog_text}\n\nAlert: {alert}\n"
                                    f"Which service is failing? Answer with the service name only.{tail}"}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=10, do_sample=False)
    ans = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).lower()
    return next((s for s in CATALOG if s in ans), "unknown")

CAUSAL = re.compile(r"caused by|upstream|after .* deploy|across", re.I)
def hits(alert):
    return {s for s, keys in CATALOG.items() if s in alert.lower() or any(k in alert.lower() for k in keys)}
def gate(alert):
    """Answer only if the alert points at exactly one catalog service and names no cause elsewhere."""
    return len(hits(alert)) == 1 and not CAUSAL.search(alert)

MODES = {"always answer": lambda a: ask(a, False),
         "asked to say unknown": lambda a: ask(a, True),
         "gate, then answer": lambda a: ask(a, False) if gate(a) else "unknown",
         "gate alone, no model": lambda a: next(iter(hits(a))) if gate(a) else "unknown"}
print(f"{'alert':<44} {'record':<13} " + " ".join(f"{m:<21}" for m in MODES))
answers = {m: [] for m in MODES}
for alert, truth in ALERTS:
    row = []
    for m, f in MODES.items():
        a = f(alert); answers[m].append(a)
        row.append(f"{a + (' ok' if a == truth else ' x' if a != 'unknown' else ''):<21}")
    print(f"{alert[:42]:<44} {truth:<13} " + " ".join(row))
print()
for m, ans in answers.items():
    answered = [(a, t) for a, (_, t) in zip(ans, ALERTS) if a != "unknown"]
    right = sum(a == t for a, t in answered)
    prec = right / len(answered) if answered else 0
    abstain = 1 - len(answered) / len(ALERTS)
    verdict = ("meets the stop rule" if prec >= 0.9 and abstain <= 0.5 else
               "precision below 90%: narrow further" if prec < 0.9 else "abstains too often: fix alert labels first")
    print(f"{m:<22} answered {len(answered):>2}/14, right {right:>2}, precision {prec:.0%}, abstains {abstain:.0%}  -> {verdict}")

Reading this output

Always answering: 50% precision. The model gets the clearly labelled alerts right, but with this catalog wording it also blames checkout-api for auth token errors, "cannot log in" and negative stock. It blames checkout-api for every cascade too.

"Say unknown if unsure" is worse: 40%. The model abstains on 9 of 14, including all five alerts that carry a service label, and is still wrong on 3 of its 5 answers. A prompt does not make the model calibrated.

The gate alone meets the stop rule. The gate abstains on the four cascades and answers the 10 alerts that point at one service. Behind the gate the model still misreads three of them (70%). The gate's own catalog lookup gets all 10 right (100%, abstaining 29%). The decisive evidence came from a rule table, so this slice does not need the model yet.

# Lesson program for selecting the smallest evidence-producing slice.
# Read: phases/14-agent-engineering/50-choose-the-smallest-testable-slice/docs/en.md
# Reference: Boehm, A Spiral Model of Software Development and Enhancement, 1988.
# Reference: Lenarduzzi and Taibi, MVP Explained, 2016.
# Run this file to generate outputs/slice-decision.json.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Slice:
    name: str
    outcome_value: int
    uncertainty_reduced: int
    effort: int
    consequence: int
    reversible: bool
    proves: tuple[str, ...]


def score(item: Slice) -> float:
    if item.effort < 1:
        raise ValueError("effort must be positive")
    risk_penalty = item.consequence * (2 if not item.reversible else 0.5)
    return round((item.outcome_value + item.uncertainty_reduced) / (item.effort + risk_penalty), 3)


def choose(items: list[Slice], required_proof: set[str]) -> Slice:
    candidates = [item for item in items if required_proof <= set(item.proves)]
    if not candidates:
        raise ValueError("no slice proves the required assumptions")
    return max(candidates, key=lambda item: (score(item), -item.effort, item.name))


def decision(items: list[Slice], required_proof: set[str]) -> dict:
    selected = choose(items, required_proof)
    return {
        "required_proof": sorted(required_proof),
        "selected": {**asdict(selected), "score": score(selected)},
        "alternatives": [{**asdict(item), "score": score(item)} for item in items if item != selected],
    }


def example() -> list[Slice]:
    return [
        Slice("read-only incident replay", 4, 5, 2, 1, True, ("service-identification", "operator-trust")),
        Slice("production auto-remediation", 5, 4, 10, 5, False, ("service-identification", "operator-trust")),
        Slice("dashboard mockup", 2, 2, 1, 1, True, ("operator-trust",)),
    ]


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "slice-decision.json"
    output.write_text(json.dumps(decision(example(), {"service-identification", "operator-trust"}), indent=2) + "\n", encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Solutions

SolutionP1 · Only the lookup meets it

Only the gate's own lookup, with no model: 10 of 10 right on the alerts it answers, abstaining on the 4 cascades (29%). Always answering scores 50%, "say unknown" 40% (abstaining 64%), and the gate in front of the model 70%. The 0.5B model misreads even single-service alerts when the catalog is written as match keys.

The stop rule's verdict for every model policy is "narrow further". For the lookup it is "meets the rule". The smallest slice that proves service identification on these alerts is a table.

SolutionB1 · The UI-only minimum

It was the UI-only minimum, combined with the demo minimum. Synthetic alerts removed the data and access uncertainty, which was the risky part: can the system reach deploy records and name the service on real alerts? The polish produced persuasion, not measurement.

The first slice should have been a read-only replay over real past incidents, using the real deploy records and catalog, with no UI beyond a printed answer. Its required proof is service identification on messy alerts and data access. Its stop rule should cover precision, abstention and the share of incidents where deploy records are missing. A UI comes after those pass.

What You Keep

Keep outputs/slice-decision.json. It records why this slice is the smallest one that can change the decision.

Break it on purpose

For "help on-call diagnose faster", a team's first slice is a polished chat UI over synthetic alerts. The demo goes well, leadership approves a quarter of work, and the first real incident shows the agent cannot reach the deploy records. Using this lesson, which false minimum was this, and what should the first slice have been? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Workflows before agents. Anthropic's agent guidance recommends the simplest pattern that works, often a fixed workflow or a single call. Agents come only when they clearly improve the outcome. The lookup that beat the model here is the same advice at small scale.
  • Reversible slices behind flags. Feature-flag systems (the OpenFeature standard, and vendors that implement it) let a slice reach a few users and be switched off without a deploy.
  • Canaries and staged rollout. The Google SRE workbook's canarying practice sends a small share of real traffic to the new path, compares it with the old, and rolls back automatically on regression.
  • On your laptop: slice scoring and the stop-rule check are standard-library Python. The diagnosis step runs the 0.5B model on CPU.

Sources: Anthropic, Building effective agents, OpenFeature, Google SRE workbook, Canarying releases, Lenarduzzi and Taibi, MVP Explained (arXiv:1609.07592).

Recap
What to keep from this lesson
  • Write the required proof before scoring any slice.
  • A slice that skips a required proof is out, however high it scores.
  • Prefer reversible, read-only slices; consequence counts double when irreversible.
  • Write the stop rule before the build, with bounds on precision and on coverage.
  • Check whether the decisive part needs the model at all.
