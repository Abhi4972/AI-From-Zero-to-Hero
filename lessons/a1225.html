The problem

In plain words first

A computer-use agent operates software the way a person does. It looks at a screenshot, decides what to do, and outputs an action such as "click at (298, 301)" or "type Tokyo". A harness carries the action out and takes a new screenshot, and the loop repeats until the task is done. This capstone brings Phase 12 together: reading the screen (high-resolution vision), deciding (an LLM with tools), pointing at the right pixel (grounding), remembering earlier steps (memory) and measuring success (benchmarks). The lesson drives a real headless browser through a mock flight booking with a JSON action loop, including a click that goes wrong and is recovered. It then measures how click precision and screenshot size decide whether small buttons get hit, and what a 20-step task costs in context. No model is trained or downloaded; a scripted policy stands in for the VLM.

A booking-site workflow: "find me a flight to Tokyo for April 15, aisle seat under $800, book it."

A multimodal agent needs to:

  1. Take a screenshot of the browser.
  2. Parse the screenshot + URL + goal into a plan.
  3. Emit a structured action: click (at x,y), type "Tokyo" (at element E), scroll down, select (radio button).
  4. Apply the action to the browser.
  5. Observe the new state (next screenshot).
  6. Repeat until the task is done.

Each step is a multimodal VLM call. The VLM output must be parseable JSON. Errors compound across steps, so recovery matters.

Idea 1 · GUI grounding — the primitive

GUI grounding is: given a screenshot and a natural language instruction, output the (x, y) coordinate to click (or other action).

SeeClick (Cheng et al., arXiv:2401.10935) was an early open result at scale: it fine-tunes Qwen-VL on automatically collected web, mobile and desktop GUI data to output click coordinates as plain text tokens, and introduced the ScreenSpot grounding benchmark. Works.

CogAgent (arXiv:2312.08914), an 18B model, added a 1120×1120 high-resolution image branch for dense UIs and reported state-of-the-art results at the time on web (Mind2Web) and Android (AITW) navigation.

Ferret-UI (Apple, arXiv:2404.05719) focuses on mobile UIs: it splits elongated phone screens into sub-images so small elements stay visible, and is trained on referring and grounding tasks over iOS and Android screens.

Output format is usually JSON:

{"action": "click", "x": 384, "y": 220, "element_desc": "Search button"}

The element_desc helps recovery: if coordinates drift between screenshots, the semantic hint lets the system re-ground.

Idea 2 · Action schemas

A typical action schema has 6-10 action types:

  • click: (x, y)
  • type: (text, x?, y?)
  • scroll: (direction, amount)
  • drag: (x0, y0, x1, y1)
  • select: (option_index)
  • hover: (x, y)
  • navigate: (url)
  • wait: (ms)
  • done: (success, explanation)

The agent emits one action per step. The browser wrapper executes and returns the new state.

Idea 3 · Screenshot-only vs accessibility-tree

Two input modes:

  • Screenshot-only: full image, no structural info. Most general; works on any app.
  • Accessibility tree: structured DOM / iOS accessibility info. Much more reliable for grounding; works where the tree is available.
  • Hybrid: both, with the tree as a reliable grounder for atomic actions and the screenshot for semantic context.

Production agents use hybrid when possible. Browser automation (Selenium + accessibility) always has the tree; desktop apps sometimes do.

Idea 4 · Long-horizon memory

A 20-step workflow generates 20 screenshots. The VLM's context fills up fast. Three compression strategies:

  • Summary-chain: after every 5 steps, summarize what has happened, drop old screenshots.
  • Skip-frame: keep the first, last, and every 3rd screenshot.
  • Tool-recorded log: execute actions, keep a text log of what was done; don't re-look at old screenshots.

Anthropic's computer-use documentation suggests a mix: keep the last few screenshots (three, for example) and prune older ones in batches so prompt caching keeps working, while the history of actions stays in the context as text. Simpler, more reliable.

The same idea as a formula

Scaling coordinates. If the screen is W×H and the model sees it scaled by s<1, a point (x′,y′) in the image is

(x,y)=(sx′​,sy′​) on the screen,
and an error of σ′ pixels in the image becomes σ=σ′/s on the screen.

Hitting a target. A click aimed at the centre of a w×h target, with independent Gaussian error σ in each axis, lands inside with probability

P=erf(22​σw​)erf(22​σh​).

Context per step. With screenshots of S tokens, T text tokens per step, and the last k screenshots kept, the request at step t is

nt​=min(t,k)S+tT,and an N-step task sends t=1∑N​nt​ tokens in total.

Worked example
A close icon, a half-size screenshot and 20 steps
  • A 16-pixel close icon, click error σ=8 px: P=erf(16/22.6)2=erf(0.71)2=0.682≈0.47. Half the clicks miss.
  • The same model looking at a half-size screenshot: σ=8/0.5=16 px on the screen, P=erf(0.35)2=0.382≈0.15.
  • A 140 × 44 button at σ=16: erf(3.09)⋅erf(0.97)=1.00⋅0.83≈0.83. Big targets forgive.
  • A 1280 × 800 screenshot is ⌈1280/28⌉⋅⌈800/28⌉=46⋅29=1,334 tokens. Keeping all 20 with 150 text tokens per step: the last request is 20⋅1,334+20⋅150=29,680 tokens, and the 20 requests together 1,484⋅(1+2+⋯+20)=311,640.
Check your mental model
  • ✗ "The model clicks on elements."
    ✓ It outputs coordinates (or an element reference); the harness clicks. A screenshot that is out of date gives coordinates that are out of date.
  • ✗ "If the click raised no error, the action worked."
    ✓ Check the expected change on the page; a click on empty space succeeds silently.
  • ✗ "Sending a smaller screenshot only loses detail."
    ✓ It also multiplies every pixel of pointing error by the scale factor.
  • ✗ "A good agent finishes the whole task by itself."
    ✓ Consequential steps such as paying, sending or deleting wait for the user's confirmation.

A JSON action loop in a real browser

A mock flight-booking site runs in headless Chromium through Playwright. The policy is a fixed plan standing in for the VLM; at each step it finds its target in the accessibility tree (hybrid grounding) and emits a JSON action: click with coordinates, or type. The harness validates the action, executes it, checks that the page changed as expected, and re-grounds by the action's element_desc if not. The agent stops at the review page and asks for confirmation instead of paying. About 2 seconds.

import json, math
from playwright.sync_api import sync_playwright

# A mock flight-booking site: search form -> results -> seat choice -> review (stop before paying).
SITE = """<html><body style="font-family:sans-serif;margin:40px">
<div id="banner"></div>
<h1>SkyFares</h1>
<div id="app">
 <label>From <input aria-label="From"></label> <label>To <input aria-label="To"></label>
 <label>Date <input aria-label="Date" placeholder="YYYY-MM-DD"></label>
 <button onclick="search()">Search flights</button>
</div>
<script>
const FL = [["SF 101", "08:10", 912], ["SF 205", "13:45", 760], ["SF 317", "22:30", 695]];
function search() {
  const to = document.querySelector('[aria-label=To]').value, d = document.querySelector('[aria-label=Date]').value;
  document.getElementById('app').innerHTML = '<h2>Flights to ' + to + ' on ' + d + '</h2>' + FL.map(f =>
    '<div style="margin:12px 0">' + f[0] + ' departs ' + f[1] + ' - $' + f[2] +
    ' <button onclick="pick(\\'' + f[0] + '\\',' + f[2] + ')">Select ' + f[0] + '</button></div>').join('');
  // A cookie banner appears late and pushes the page down by 90 pixels.
  setTimeout(() => document.getElementById('banner').innerHTML =
    '<div style="height:70px;background:#fe9;padding:10px">We use cookies. <button>Accept</button></div>', 300);
}
function pick(f, p) {
  document.getElementById('app').innerHTML = '<h2>' + f + ', $' + p + '</h2><p>Choose a seat</p>' +
    '<label><input type=radio name=s aria-label="Window seat"> Window</label> ' +
    '<label><input type=radio name=s aria-label="Aisle seat"> Aisle</label> <button onclick="review()">Continue</button>';
  window.choice = [f, p];
}
function review() {
  const s = document.querySelector('[aria-label="Aisle seat"]').checked ? 'Aisle' : 'Window';
  document.getElementById('app').innerHTML = '<h2>Review booking</h2><p>' + window.choice[0] + ', ' + s +
    ' seat, total $' + window.choice[1] + '</p><button>Pay and book</button>';
}
</script></body></html>"""

ACTIONS = {"click": {"x", "y", "element_desc"}, "type": {"text", "element_desc"}, "done": {"success", "explanation"}}
def validate(a):                       # reject anything that is not a well-formed action
    keys = ACTIONS.get(a.get("action"))
    return keys is not None and keys <= set(a)

W, H = 1280, 800
def screenshot_tokens(w=W, h=H):       # 28 x 28-pixel visual tokens (Lesson 12.1)
    return math.ceil(w / 28) * math.ceil(h / 28)

def ground(page, role, name):          # hybrid grounding: find the element in the accessibility tree, click its centre
    box = page.get_by_role(role, name=name, exact=True).bounding_box()
    return round(box["x"] + box["width"] / 2), round(box["y"] + box["height"] / 2)

# The "policy" stands in for the VLM: a fixed plan for this goal, grounded from the tree at each step.
GOAL = "Flight to Tokyo on 2026-04-15, aisle seat, under $800. Stop before paying."
PLAN = [("type", "textbox", "From", "London"), ("type", "textbox", "To", "Tokyo"),
        ("type", "textbox", "Date", "2026-04-15"), ("click", "button", "Search flights", None),
        ("click", "button", "Select SF 205", None), ("click", "radio", "Aisle seat", None),
        ("click", "button", "Continue", None)]

with sync_playwright() as p:
    page = p.chromium.launch().new_page(viewport={"width": W, "height": H})
    page.set_content(SITE)
    log, step = [], 0
    for kind, role, name, text in PLAN:
        step += 1
        x, y = ground(page, role, name)
        if kind == "click" and name == "Select SF 205":
            page.wait_for_timeout(400)          # the model "thinks"; meanwhile the banner arrives...
        a = {"action": kind, "x": x, "y": y, "element_desc": f"{role} '{name}'"} if kind == "click" else \
            {"action": "type", "text": text, "element_desc": f"{role} '{name}'"}
        assert validate(a), a
        if kind == "type":
            page.get_by_role(role, name=name, exact=True).click(); page.keyboard.type(text)
            ok = page.get_by_role(role, name=name, exact=True).input_value() == text
        else:
            before = page.locator("body").aria_snapshot()
            page.mouse.click(a["x"], a["y"])        # ...so this click lands on stale coordinates
            page.wait_for_timeout(100)
            ok = page.locator("body").aria_snapshot() != before
            if not ok:                              # recovery: nothing changed, so re-ground by element_desc and retry
                log.append(f"{step:>2} {json.dumps(a)} -> no change on screen; re-grounding")
                a["x"], a["y"] = ground(page, role, name)
                page.mouse.click(a["x"], a["y"]); page.wait_for_timeout(100)
                ok = page.locator("body").aria_snapshot() != before
        page.screenshot()                           # the next observation
        log.append(f"{step:>2} {json.dumps(a)} -> {'ok' if ok else 'FAILED'}")
    review = page.get_by_role("heading", level=2).inner_text(), page.locator("p").first.inner_text()
    done = {"action": "done", "success": True, "explanation": f"{review[0]}: {review[1]}. Waiting for the user to confirm payment."}
    assert validate(done)
    print("goal:", GOAL, "\n")
    print("\n".join(log))
    print(f"{step + 1:>2} {json.dumps(done)}")
    print(f"\nfinal page, accessibility tree:\n{page.locator('body').aria_snapshot()}")
    print(f"\neach {W}x{H} screenshot costs about {screenshot_tokens()} visual tokens")

Reading this output

Every action is a small, checkable JSON object. Typing steps carry the text and a description of the field; click steps carry pixel coordinates plus element_desc. The harness rejects anything outside the schema before touching the page, and checks each typed field's value afterwards.

Step 5 goes wrong, silently. The agent grounded "Select SF 205" at (298, 190) while the results page was fresh. Then the cookie banner arrived and pushed the content 111 pixels down. The click at (298, 190) landed on empty space: no error, no exception, just no effect.

The check catches it, and element_desc fixes it. The harness compares the accessibility tree before and after each click. Nothing changed, so it looks the element up again by its description, finds it at (298, 301), and clicks there. A screenshot-only agent would have to take a new screenshot and ground again, which is the same idea at higher cost.

The agent stops before paying. The final tree shows the review page ("SF 205, Aisle seat, total $760") and a "Pay and book" button it did not press. The done action reports what it found and hands the payment decision to the user.

Each look at the screen costs 1,334 tokens at 1280 × 800, which is why memory strategy matters (next run).

How precise must a click be, and what does memory cost?

Four targets on a 2560 × 1440 page, from a 16-pixel close icon to a large card. 400 clicks per setting are aimed at each target's centre with Gaussian error, and the browser itself reports what was hit (elementFromPoint). The error is applied either to a full-size screenshot or to one sent at half size. Then the context cost of a 20-step task under three memory strategies. About a second.

import math, numpy as np
from playwright.sync_api import sync_playwright

# 1. How precise must a click be? Four targets on a 2560x1440 screen, hit-tested by the real browser.
PAGE = """<body style="margin:0;width:2560px;height:1440px;font-family:sans-serif">
<button id="close" style="position:absolute;left:400px;top:200px;width:16px;height:16px;padding:0">x</button>
<button id="icon" style="position:absolute;left:800px;top:200px;width:32px;height:32px">*</button>
<button id="button" style="position:absolute;left:1200px;top:200px;width:140px;height:44px">Search flights</button>
<div id="card" style="position:absolute;left:1700px;top:150px;width:400px;height:240px;border:1px solid #888">Flight card</div>
</body>"""
rng = np.random.default_rng(0)
with sync_playwright() as p:
    page = p.chromium.launch().new_page(viewport={"width": 2560, "height": 1440})
    page.set_content(PAGE)
    targets = {t: page.locator("#" + t).bounding_box() for t in ("close", "icon", "button", "card")}
    def hit_rate(tid, sigma_real, n=400):
        b = targets[tid]
        cx, cy = b["x"] + b["width"] / 2, b["y"] + b["height"] / 2
        pts = (np.array([cx, cy]) + rng.normal(0, sigma_real, (n, 2))).tolist()
        ids = page.evaluate("pts => pts.map(([x, y]) => (document.elementFromPoint(x, y) || {}).id)", pts)
        return np.mean([i == tid for i in ids])
    print("share of clicks that land on the target, for a model whose click error is sigma pixels")
    print("in the screenshot it sees (2560x1440 screen sent at full size, or scaled to 1280x720)\n")
    print(f"{'target':<36}" + "".join(f"{f'sigma {s}':>10}" for s in (2, 4, 8, 16)))
    for tid, label in (("close", "16 px close icon"), ("icon", "32 px icon"), ("button", "140 x 44 button"), ("card", "400 x 240 card")):
        for scale, note in ((1.0, "full size"), (0.5, "sent at half size")):
            row = [hit_rate(tid, s / scale) for s in (2, 4, 8, 16)]   # an error of s pixels in a half-size image is 2s on screen
            print(f"{label + ', ' + note:<36}" + "".join(f"{r:>10.0%}" for r in row))

# 2. What a 20-step episode costs in context, for three memory strategies.
SHOT = math.ceil(1280 / 28) * math.ceil(800 / 28)    # one 1280x800 screenshot
TEXT = 150                                           # goal, action JSON and short notes per step
def request_tokens(step, keep):                      # size of the request sent at this step
    shots = step if keep is None else min(step, keep)
    return shots * SHOT + step * TEXT
print(f"\none 1280x800 screenshot = {SHOT} tokens; {TEXT} text tokens per step")
print(f"{'memory strategy':<40}{'step-20 request':>16}{'all 20 requests':>17}")
for name, keep in (("keep every screenshot", None), ("keep the last 3 screenshots + text log", 3),
                   ("text log + current screenshot only", 1)):
    last = request_tokens(20, keep); total = sum(request_tokens(s, keep) for s in range(1, 21))
    print(f"{name:<40}{last:>16,}{total:>17,}")

Reading this output

Small targets need precise pointing. For the 16-pixel close icon, 94% of clicks land with a 4-pixel error, 48% with 8 pixels and 18% with 16. The 140 × 44 button still gets 84% at 16 pixels, and the large card 100% everywhere. The measured numbers match the erf formula above.

A half-size screenshot doubles the error. The same model error, made on a 1280 × 720 copy of a 2560 × 1440 screen, becomes twice as many pixels on the real screen: the close icon drops from 94% to 48% at σ = 4, the 32-pixel icon from 92% to 49% at σ = 8. Saving tokens on screenshots costs accuracy on small targets. A zoom action (crop a region and look again at full resolution) gets precision back where it is needed.

Keeping every screenshot gets expensive fast. At step 20 the request holds 29,680 tokens, and the 20 requests together send 311,640. Keeping the last 3 screenshots plus a text log cuts the total to about a third (107,538); keeping only the current screenshot plus the log, to under a fifth (58,180). Prompt caching lowers the price of the repeated part, which is why Anthropic suggests pruning in batches rather than every step.

Idea 5 · Visual tool use

ChartAgent (arXiv:2510.04514) introduces visual tool use for chart understanding: crop, zoom, OCR, call external detection. The agent can output "crop to region (100, 200, 300, 400) then call OCR" as a tool call. The tool returns text; the VLM continues reasoning.

This pattern generalizes: set-of-mark prompting, region annotation, and external detection tools all fit the same "output a tool call, receive a structured response" schema.

Idea 6 · The 2026 benchmarks

  • ScreenSpot-Pro (2025). GUI grounding in professional desktop software: 1,581 instructions across 23 applications on high-resolution screens, where the average target covers 0.07% of the screen. At release GPT-4o scored 0.8% and the best grounding model 18.9% (OS-Atlas-7B), 48.1% with a planner that zooms in; specialised grounding models have since climbed much higher.
  • VisualWebArena (2024). 910 visually grounded web tasks on classifieds, shopping and Reddit-style sites. At release the best agent (GPT-4V with set-of-marks) succeeded on 16.4% of tasks; humans on 88.7%.
  • AgentVista (arXiv:2602.23166, 2026). 209 hard tasks on real images across 7 categories, solved with web search, image search, page visits and a code interpreter: a visual tool-use benchmark rather than GUI control. Best in its paper: Gemini 3 Pro 27.3%; the best open model, Qwen3-VL-235B, 12.9%.
  • OSWorld (2024). 369 tasks in real desktop operating systems, where humans succeed on about 72% and the best agent at release on about 12%. On its corrected version, OSWorld-Verified, the best reported agents in 2026 exceed 80%.
  • WebArena / WebShop. Earlier web benchmarks over HTML and text, still used for comparison.

Idea 7 · Why it's still hard

Agent performance bottlenecks:

  1. Visual grounding at fine scale. "Click the small X" fails often at mobile resolution.
  2. Long-horizon planning. After 10 actions, the agent drifts from the goal.
  3. Error recovery. When a click fails (wrong button), detecting + recovering is rarely trained data.
  4. Cross-page context. Jumping between tabs or long forms loses state.

Research directions: memory architectures, explicit replanning, multimodal verification (screenshot match for action success).

Industry practice
What's current (2024–2026)
  • Computer-use APIs from the model vendors: Anthropic's computer use tool (screenshot, click, type, scroll, zoom), OpenAI's computer-use model, and Google's Gemini computer use model each take screenshots and return actions for your harness to execute. The vendors recommend modest screen sizes (Anthropic suggests about 1024 × 768 to 1366 × 768), a sandboxed VM, an allowlist of sites and human confirmation for consequential actions.
  • Browser harnesses with accessibility trees: Playwright (used here) and the Playwright MCP server give agents the page's accessibility snapshot alongside or instead of screenshots; open-source libraries such as browser-use build agents on top.
  • Open GUI models: UI-TARS (2B to 72B) and the Qwen2.5-VL and Qwen3-VL families ground clicks and run agent loops; the 2B–3B sizes fit an 8 GB laptop GPU, 7B in 4-bit.
  • Prompt injection from the screen: text on a web page can try to give the agent orders. Treat everything on screen as data, confirm consequential steps with the user, and keep credentials away from the model.

Sources: Claude computer use tool, OSWorld, VisualWebArena (arXiv 2401.13649), ScreenSpot-Pro (arXiv 2504.07981), AgentVista (arXiv 2602.23166), SeeClick (arXiv 2401.10935).

Recap
What to keep from this lesson
  • The loop: screenshot (and tree) → model → JSON action → harness → new screenshot.
  • Validate every action against the schema; verify every effect on the page.
  • Keep an element description with each click so a stale coordinate can be re-grounded.
  • Small targets need precise clicks; downscaled screenshots multiply the error; zoom helps.
  • Keep a text log and only the last few screenshots.
  • Stop and ask before consequential actions; treat on-screen text as data.

Solutions

SolutionP1 · The click hits empty space, and only a check notices

The click lands on empty space. The agent computed (298, 190) from the page as it was. The banner then pushed the results 111 pixels down, so the button was now at (298, 301). Clicking empty space raises no error, so an agent that does not check would carry on as if it had selected the flight.

The harness noticed because it compares the page's accessibility tree before and after every click: nothing changed. It then re-grounded the same element_desc, "button 'Select SF 205'", in the current tree and clicked the new centre.

The check here is "did anything change". If the stale click had landed on "Select SF 101" instead, the page would have changed, to the wrong flight. A stronger check compares the result with what the action was meant to do (the heading should now say SF 205) and, if it is wrong, goes back before continuing.

SolutionB1 · Every click lands in the top-left quarter

The model's coordinates are in the 1280 × 720 image. Executed unscaled on the 2560 × 1440 screen, each click lands at half the intended x and y: every click falls in the top-left quarter of the screen. A "Pay" button the model sees at (1000, 600), really at (2000, 1200), is never pressed; whatever sits at (1000, 600) on the real screen is pressed instead. It may be harmless, or it may be another button, and nothing raises an error.

To make this class of bug impossible to miss:

  • One conversion function, used for every action: store the scale factor with each screenshot and map image coordinates to screen coordinates in one place (as Anthropic's documentation does with get_scale_factor).
  • Bounds checks: reject coordinates outside the image the model was shown.
  • Verify every action's effect (as in the first run), so a click that lands somewhere unexpected stops the loop.
  • A calibration test: click a known element on a test page at both resolutions and assert that the right element was hit.
  • Prefer element references from the accessibility tree where the app has one; coordinates only where it does not.
