Why this came about

Prototype agents assumed tools always answered quickly and correctly. Production quickly showed slow APIs, failures and duplicated actions after retries. Patterns from distributed systems, timeouts, retries with backoff and idempotency keys, were adapted so agents could act on real systems safely.

The problem: tools are slow, and sometimes fail

So far every tool answered instantly and never failed. Real ones are network calls. The carrier's tracking API takes 0.3 seconds, and about one call in three fails for a moment with a 503. Two customers ask about two orders each:

# Continues Lesson 3.3. The carrier's tracking service: 0.3 s per call, and it sometimes fails for a moment
import time, random

class TransientError(Exception):
    """A failure worth retrying: a timeout, a 429 or a 503."""

calls_seen = {}                                            # a fixed failure pattern, so every run of this page is identical
def carrier_status(order_id: str) -> str:
    time.sleep(0.3)
    n = calls_seen[order_id] = calls_seen.get(order_id, 0) + 1
    if n % 3 == 2:                                         # about one call in three fails briefly
        raise TransientError("carrier API returned 503 Service Unavailable")
    return checked_status(order_id)

slow_tools = dict(tools, get_order_status=(tools["get_order_status"][0], carrier_status))
agent = ValidatingAgent(system=SYSTEM, tools=slow_tools, risky=risky)
for customer in ("first", "second"):
    started = time.perf_counter()
    text = agent.run("Where are SK-1042 and SK-1077?")

Python refresher
Python refresher: exceptions are classes

class TransientError(Exception) makes a new kind of error. except TransientError: catches only that kind, and the subclasses of it, and lets every other exception through. That is how the code below tells "try again" failures apart from "this will never work" failures: by type, not by parsing error messages.

In plain words first
Errands that run late, fail or happen twice

Real tools are slow and sometimes fail. Several independent errands should run at the same time, each with a deadline. A failure the model can work around ("order not found") goes back to it as a result, not as a crash. Temporary failures get retried, waiting longer each time. And any tool that changes something must be safe to run twice, because retries and restarts will run it twice: an idempotency key lets the receiving system recognise and ignore the repeat.

Idea 1 · Parallel calls, each with a deadline

Lesson 14.57 left two hooks in Agent: call_tools, which runs one turn's calls, and execute, the line that calls your function. RobustAgent overrides both.

import hashlib
from concurrent.futures import ThreadPoolExecutor, TimeoutError as Deadline

class RobustAgent(ValidatingAgent):
    deadline_s = 1.0                                       # per tool call, including retries
    attempts = 3                                           # for transient errors only
    pool = ThreadPoolExecutor(max_workers=8)
    jitter = random.Random(42)                             # seeded here so the page is repeatable

    def call_tools(self, calls):
        """Run one turn's calls in parallel. Results come back in request order, matched by tool_use_id."""
        futures = [self.pool.submit(self.call_tool, c) for c in calls]
        results = []
        for c, f in zip(calls, futures):
            try:
                results.append(f.result(timeout=self.deadline_s))
            except Deadline:
                results.append({"type": "tool_result", "tool_use_id": c.id, "is_error": True,
                                "content": f"{c.name} did not answer within {self.deadline_s} s; try again later"})
        return results

    def execute(self, name, args):
        """Retry transient failures with exponential backoff and full jitter; never retry other errors."""
        for attempt in range(1, self.attempts + 1):
            try:
                return self.tools[name][1](**args)
            except TransientError:
                if attempt == self.attempts:
                    raise
                time.sleep(self.jitter.uniform(0, 0.05 * 2 ** attempt))   # 0-0.1 s, then 0-0.2 s

calls_seen.clear(); calls_seen["SK-1077"] = 1               # the next call for SK-1077 will fail once
agent = RobustAgent(system=SYSTEM, tools=slow_tools, risky=risky)
print(agent.run("Where are SK-1042 and SK-1077?"))
print("calls to the carrier for SK-1077:", calls_seen["SK-1077"] - 1, "(one failed, one retried)")
What you should see
Order SK-1042 is out for delivery, expected today by 8 pm. Order SK-1077 was delivered on 2 November.
calls to the carrier for SK-1077: 2 (one failed, one retried)

Trace what happens for the two-order question:

  1. run (unchanged from 3.2) gets two tool_use blocks and calls call_tools.
  2. call_tools submits call_tool for each block to the pool. Both start at once, so two 0.3-second calls take about 0.3 seconds, not 0.6.
  3. Each call_tool validates, checks the gate, then calls execute.
  4. execute calls the carrier. For SK-1077 the first attempt raises TransientError, so it sleeps a random 0 to 0.1 seconds and tries again, and the second attempt succeeds.
  5. call_tools collects the results in request order with f.result(timeout=...). A call still running after its deadline becomes an error result, so the turn always has one result per request (Lesson 14.56's rule).

Two details matter in production. Backoff (waiting longer after each failure) gives a struggling service room to recover. Jitter (a random part of the wait) stops a thousand clients that failed together from retrying together, which is how a short outage becomes a long one (the retry stormlater · 14.114 in Lesson 14.114).

Measure it: the same failures, three ways

The three agents from this lesson face the same faults: a slow service and one that fails now and then. Ten customers each ask about two orders. For every agent the code counts how many of the ten got a complete answer and how long the runs took, so the effect of each technique shows up as a number:

# Same inputs, before and after: ten customers ask about two orders each
def trial(agent_cls, runs=10):
    calls_seen.clear()                                     # the same failure pattern for every agent
    ok, seconds = 0, 0.0
    for _ in range(runs):
        a = agent_cls(system=SYSTEM, tools=slow_tools, risky=risky)
        t0 = time.perf_counter()
        text = a.run("Where are SK-1042 and SK-1077?")
        seconds += time.perf_counter() - t0
        ok += "Sorry" not in text
    return ok, seconds / runs

class ParallelOnly(RobustAgent):
    attempts = 1

for name, cls in [("one at a time, no retries", ValidatingAgent), ("parallel, no retries", ParallelOnly),
                  ("parallel, deadline, retries", RobustAgent)]:
    ok, avg = trial(cls)
    print(f"{name:<28} answered fully {ok}/10, average {avg:.1f} s")

Idea 2 · Retried writes need idempotency keys

A read can be retried freely. A write cannot. Suppose the payment provider makes the refund, and then the connection drops before the reply reaches you. Your code sees a transient error and retries, as it should:

# A write whose reply gets lost: the payment provider refunds, then the connection drops before we hear back
import itertools
BANK = {}                                                  # refunds the payment provider actually made
lost_reply = {"next_call": True}

def bank_refund(order_id: str, reason: str, idempotency_key: str = None) -> str:
    if idempotency_key in BANK:                            # the provider has seen this key: same result, no new refund
        return json.dumps({**BANK[idempotency_key], "note": "already refunded"})
    record = {"order_id": order_id, "refund_id": f"R-{len(BANK) + 901}", "amount": ORDERS[order_id]["price"], "status": "refund issued"}
    BANK[idempotency_key or record["refund_id"]] = record
    if lost_reply["next_call"]:
        lost_reply["next_call"] = False
        raise TransientError("connection reset after the request was sent")
    return json.dumps(record)

pay_tools = dict(tools, issue_refund=(tools["issue_refund"][0], bank_refund))
question = "My mixer arrived broken last week. Can I get a refund?"

BANK.clear(); lost_reply["next_call"] = True
RobustAgent(system=SYSTEM, tools=pay_tools, risky=risky, approve=lambda n, a: True).run(question)
print("retry without a key:", len(BANK), "refunds:", [r["refund_id"] for r in BANK.values()])

RUN_IDS = itertools.count(1)
class IdempotentAgent(RobustAgent):
    def run(self, question):
        self.run_id = f"run-{next(RUN_IDS)}"
        return super().run(question)

    def execute(self, name, args):
        fn = self.tools[name][1]
        if "idempotency_key" in inspect.signature(fn).parameters:      # the same key on every retry of this call
            key = hashlib.sha256(f"{self.run_id}|{name}|{json.dumps(args, sort_keys=True)}".encode()).hexdigest()[:16]
            args = {**args, "idempotency_key": key}
        return super().execute(name, args)

BANK.clear(); lost_reply["next_call"] = True
print(IdempotentAgent(system=SYSTEM, tools=pay_tools, risky=risky, approve=lambda n, a: True).run(question))
print("retry with a key:   ", len(BANK), "refund: ", [r["refund_id"] for r in BANK.values()])
What you should see
retry without a key: 2 refunds: ['R-901', 'R-902']
Refund R-901 of INR 3,899 for order SK-1077: refund issued.
retry with a key:    1 refund:  ['R-901']

Without a key, the retry refunded the customer twice. With a key, the provider recognized the second request and returned the first result. An idempotency key is a value that is the same on every retry of one logical operation and different for every new one. Here it is a hash of the run, the tool and its arguments. Real payment and messaging APIs accept one (often as an Idempotency-Key header) for exactly this reason. Where an API does not, store the key with the record yourself and check it before writing. Never let the model choose the key: it must come from your code, or a model that repeats a request would also repeat its key and silently suppress a legitimate second refund.

What the library replaces

For your own tools, tenacity packages the retry loop as a decorator:

from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception_type

@retry(stop=stop_after_attempt(3), wait=wait_random_exponential(multiplier=0.05, max=1),
       retry=retry_if_exception_type(TransientError), reraise=True)
def carrier_status_with_tenacity(order_id: str) -> str:
    return carrier_status(order_id)

calls_seen.clear(); calls_seen["SK-1077"] = 1
print(carrier_status_with_tenacity("SK-1077"), "| calls made:", calls_seen["SK-1077"] - 1)
What you should see
{"order_id": "SK-1077", "item": "mixer grinder", "price": 3899, "status": "delivered", "delivered_on": "2 November"} | calls made: 2

stop_after_attempt, wait_random_exponential and retry_if_exception_type are the three decisions execute made by hand. For model calls, the SDK clients already retry: anthropic 2.4.0 and openai 3.43.0 retry connection errors, 429s and 5xx responses twice by default, with backoff, and wait up to 10 minutes for a response. Ten minutes is far too long for a customer chat, so set the timeout:

import anthropic, openai

# and openai 3.43.0) and waits up to 10 minutes by default. For an interactive agent, set both deliberately.

oai = openai.OpenAI(max_retries=3, timeout=30.0)

What changes with real tools: timeouts should be set inside each HTTP client as well as around the call, because Python cannot stop a running thread (Lesson 14.56), so a timed-out call keeps using a worker until it returns. And transient failures come in bursts, so measure retry rates per tool in your traces before you choose attempt counts.

Check your mental model
  • ✗ "Errors should stop the agent."
    ✓ Return recoverable errors as tool results so the model can adapt; stop only on errors it cannot fix.
  • ✗ "Retrying is always safe."
    ✓ Only for idempotent actions or with an idempotency key; otherwise a retry can refund twice.
  • ✗ "Running tools one after another is simpler and just as fast."
    ✓ Independent calls in parallel finish in the time of the slowest one.

Debugging exercise: answers about the wrong orders

A teammate wanted results "as soon as they are ready" and wrote FastestFirst. In testing every answer looked right, but in production customers occasionally get the status of a different order. Run the check below, explain the bug, and say why the testing missed it. (Solution D1.)

from concurrent.futures import as_completed

def staggered(order_id: str) -> str:                       # SK-1042's carrier is slower today
    time.sleep(0.3 if order_id == "SK-1042" else 0.1)
    return checked_status(order_id)

class FastestFirst(RobustAgent):
    def call_tools(self, calls):
        futures = [self.pool.submit(self.call_tool, c) for c in calls]
        done = [f.result() for f in as_completed(futures)]  # "collect results as soon as they are ready"
        return [{**r, "tool_use_id": c.id} for c, r in zip(calls, done)]

Make it your own
Make it your own: a circuit breaker

When the carrier is down for minutes, retrying every call just adds load and latency. Write a Breaker that, after 3 consecutive transient failures, stops calling the service for 2 seconds and fails fast with a clear message, then lets calls through again. (Solution M1.)

Solutions

SolutionP1 · One worker

About 0.6 seconds: with one worker, the pool runs the two calls one after the other, so parallel code gives sequential timing. Pool size is a capacity decision: too small serializes your agent, too large lets one agent flood a slow service. Size it per tool, from that service's rate limits.

SolutionP2 · Retrying a permanent error

RobustAgent calls the carrier once and returns the LookupError at once. RetryEverything calls it three times, with backoff in between, and the customer gets exactly the same answer, about three times later. Retrying a permanent error adds latency and load and never changes the result. Retry only errors you have classified as transient; everything else goes straight back to the model as an error result.

SolutionD1 · Results paired by completion order

as_completed yields futures in the order they finish. The code zips those results with calls, which are in the order they were requested, so when SK-1042's carrier is slower, SK-1077's result is labeled with SK-1042's tool_use_id. The model then reads one order's status as the other's. Testing missed it because every test tool answered instantly, and in the same order. The fix is to pair each result with its own call: submit one future per call and read them in request order, as RobustAgent.call_tools does, or keep a {future: call} dictionary if you really need completion order. Test concurrency with tools whose delays you control.

SolutionM1 · A circuit breaker
# Solution M1: a circuit breaker that stops calling a failing service for a while
class Breaker:
    def __init__(self, threshold=3, cool_off_s=2.0):
        self.threshold, self.cool_off_s, self.failures, self.open_until = threshold, cool_off_s, 0, 0.0

    def call(self, fn, **args):
        if time.monotonic() < self.open_until:
            raise TransientError(f"circuit open: the service failed {self.threshold} times in a row; not calling it for {self.cool_off_s:.0f} s")
        try:
            out = fn(**args)
        except TransientError:
            self.failures += 1
            if self.failures >= self.threshold:
                self.open_until = time.monotonic() + self.cool_off_s
            raise
        self.failures = 0
        return out

def always_down(order_id: str) -> str:
    time.sleep(0.05)
    raise TransientError("carrier API returned 503 Service Unavailable")

breaker = Breaker()
for attempt in range(5):
    try:
        breaker.call(always_down, order_id="SK-1042")
    except TransientError as e:
        print(f"call {attempt + 1}: {e}")

call 1: carrier API returned 503 Service Unavailable
call 2: carrier API returned 503 Service Unavailable
call 3: carrier API returned 503 Service Unavailable
call 4: circuit open: the service failed 3 times in a row; not calling it for 2 s
call 5: circuit open: the service failed 3 times in a row; not calling it for 2 s

After three failures the breaker opens and fails fast without calling the service, which protects both the customer's wait and the struggling service. A production breaker also lets a single trial call through after the cool-off (the "half-open" state) and keeps one breaker per service, shared across runs. Wire it in by calling breaker.call(fn, **args) inside execute.

Check your understanding

Explain the mechanismExplain exponential backoff with jitter, and why both parts matter.

Worked answer. After a transient failure you wait before retrying, and the wait grows with each attempt, for example 0.1, 0.2, then 0.4 seconds, capped. That gives an overloaded service time to recover instead of hitting it again at once. Jitter makes each wait random within that range. Without it, every client that failed at the same moment retries at the same moment, and the synchronized wave knocks the service over again. Full jitter, a random wait between zero and the cap, spreads the load best. Retry only transient errors, a bounded number of times, inside a deadline the user can live with.

A plausible wrong answer. "Retry immediately three times." It turns a brief overload into a sustained one, and it multiplies traffic exactly when the service can least handle it.

Debug a failureCustomers report being refunded twice, and only during an incident with the payment provider. What happened?

Worked answer. During the incident, refund requests succeeded on the provider's side but the replies timed out, so the agent's retry logic sent them again and each retry made a new refund. The fix is an idempotency key per logical refund, generated by our code from the run and the call, sent with every retry and stored with the record, so the provider (or our own table) returns the first result instead of acting twice. Then reconcile the duplicates from the provider's records, and add a test that simulates a lost reply.

A plausible wrong answer. "Turn off retries for the refund tool." That trades double refunds for missing ones: a customer whose reply was lost now never hears back, and an agent or a person retries by hand anyway.

Follow-ups. Where would you store idempotency keys, and for how long? What if the model itself asks for the refund twice in one run?

Defend a designWhy run a turn's tool calls in parallel, and when would you not?

Worked answer. When the model asks for several independent lookups in one turn, running them concurrently makes the turn as slow as its slowest call instead of the sum of all of them. In the example that halved latency. I would run them sequentially when one call's result changes whether another should run, when two calls write to the same record, or when a downstream service has a low rate limit. And I would cap concurrency per tool. The model's batching is a hint, not a guarantee that the calls are independent, so the decision lives in code, per tool.

A plausible wrong answer. "Always parallelize, it's free speed." It is not free for writes to the same record, for rate-limited services, or when results must be applied in order.

Follow-ups. How do you keep result ordering correct? How would you do the same with asyncio instead of threads (Lesson 14.66)?
