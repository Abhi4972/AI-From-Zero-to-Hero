This capstone reads three real systems side by side. Anthropic's Research system is a lead agent that sends subagents to search in parallel. MetaGPT and ChatDev give agents fixed roles from a software process and pass documents between them. OpenClaw and Moltbook show what happens when hundreds of thousands of personal agents meet on one network. Multi-agent engineering is a young discipline. The production references are few, and each covers a different part of the space. Reading them one at a time is useful; comparing them as a set is more useful. This lesson treats three canonical 2026 case studies as an end-to-end reading list, pins the common patterns, and maps the framework landscape so you can make framework choices from knowledge, not marketing.

Concept

Anthropic Research system

The production supervisor-worker case. Claude Opus 4 plans and synthesizes; Claude Sonnet 4 subagents research in parallel. Published engineering post: https://www.anthropic.com/engineering/multi-agent-research-system.

Key measured results:

  • +90.2% improvement over single-agent Opus 4 on internal research evals.
  • 80% of BrowseComp variance explained by token usage alone — multi-agent wins largely because each subagent gets a fresh context window.
  • About 15x the tokens of a chat (single agents use about 4x).
  • Rainbow deployment because agents are long-running and stateful.

Design lessons codified:

  1. Scale effort to query complexity. Simple fact-finding → 1 agent with 3-10 tool calls. Direct comparisons → 2-4 subagents with 10-15 calls each. Complex research → more than 10 subagents.
  2. Broad first, then narrow. Subagents do wide searches; lead synthesizes; follow-up subagents do targeted deeps.
  3. Rainbow deploys. Keep old runtime versions alive until their in-flight agents finish.
  4. Verification is built in. A separate citation agent ties the final report's claims to sources, and the team evaluated outputs with an LLM judge plus human testers, who caught failures such as preferring SEO-farm sources.

This is the reference case for supervisor-worker topology (Phase 16 · 05) at production scale.

MetaGPT / ChatDev

The production SOP-role-decomposition case. Cover arXiv:2308.00352 (MetaGPT) and arXiv:2307.07924 (ChatDev).

MetaGPT encodes software-engineering SOPs as role prompts: Product Manager, Architect, Project Manager, Engineer, QA Engineer. The paper's framing: Code = SOP(Team). Each role has a narrow, specialized prompt; inter-role handoffs carry structured artifacts (PRD docs, architecture docs, code).

ChatDev's contribution: communicative dehallucination. Agents request specifics before answering — a designer agent asks the programmer what language is intended before sketching UI, rather than guessing. The paper reports this reduces hallucination in multi-agent pipelines measurably.

MacNet (arXiv:2406.07155) extends ChatDev to more than 1,000 agents arranged in directed acyclic graphs. Each edge pairs an instructing agent with an assistant agent, and solutions flow along the topological order. The paper reports a collaborative scaling law: quality rises in a logistic curve as agents are added, and irregular topologies did better than regular ones.

Design lessons:

  1. Structure matters more than size. A tight 5-role SOP team beats a 50-agent unstructured group.
  2. Handoff contracts in writing. Artifacts passed between roles follow a schema.
  3. Communicative dehallucination is a cheap, load-bearing pattern.
  4. DAGs scale further than chat. When the flow is knowable, encode it.

This is the reference case for role specialization (Phase 16 · 08) and structured topology (Phase 16 · 15).

OpenClaw / Moltbook ecosystem

The production population-scale case. Timeline:

  • Nov 2025: Clawdbot (Peter Steinberger's local ReAct-loop coding agent) ships.
  • Jan 2026: renamed twice in a few days (Clawdbot → Moltbot around January 26-27 after trademark complaints, then Moltbot → OpenClaw).
  • Jan 28, 2026: Matt Schlicht launches Moltbook, an agent-only social network for OpenClaw agents; about four days later a database misconfiguration exposes 1.5M agent API keys. It claimed about 2.8M registered agents by March, with far fewer active.
  • Mar 2026 (2026-03-10): Meta acquires Moltbook.
  • Feb 2026: OpenAI hires Peter Steinberger. Mar 2026: China moves to restrict OpenClaw at government agencies, state firms and banks.
  • Mar 2026: OpenClaw crosses 247k GitHub stars.

This is what multi-agent looks like when you put millions of agents on a shared substrate:

  • Emergent activity. Agents post, reply and form communities with little human direction; how much of it is autonomous rather than prompted by owners is disputed.
  • Prompt-injection risks at population scale. A malicious post that agents read can carry instructions to thousands of agents with tool access, and Moltbook's early breach exposed keys that would let anyone post as those agents.
  • State-level regulatory response. Within weeks of launch, regulation reaches the ecosystem.

The design lessons from this case are partly technical, partly governance:

  1. Multi-agent at population scale is a new regime. Individual-system best practices (verification, role clarity) still apply but are not sufficient.
  2. Prompt injection is the new XSS. Treat agent profiles and cross-agent messages as untrusted input by default.
  3. Regulation is faster than design cycles. Plan for it.
  4. Open-source + viral scale compounds. 247k stars in ~4 months is unusual; design for deploy-burst-load.

See OpenClaw Wikipedia and CNBC / Palo Alto Networks reporting for ecosystem detail. For the technical underpinnings, the Clawdbot / OpenClaw repos expose the local ReAct loop; Moltbook's public posts reveal the social-graph architecture on top.

The common patterns across all three cases

  1. Orchestrator + workers (Anthropic explicit supervisor, MetaGPT PM-as-supervisor, OpenClaw individual agents + network effects).
  2. Structured handoff contracts (Anthropic subagent task descriptions, MetaGPT PRD/architecture docs, OpenClaw A2A artifacts).
  3. Verification as first-class role (Anthropic's citation agent and evaluations, MetaGPT's QA Engineer; OpenClaw has none built in, which is part of its security story).
  4. Scaling is topology + substrate, not just more agents (rainbow deploys, MacNet DAGs, population-scale substrates).
  5. Cost is material (about 15x the tokens of a chat for Anthropic's system, per-role token use in MetaGPT, per-model API costs paid by each OpenClaw owner).
  6. Security posture is explicit (Anthropic's sandboxing, MetaGPT's role restrictions, OpenClaw's prompt-injection as known attack surface).

Choosing a reference for your next project

  • Production research / knowledge task → Anthropic Research. Fresh-context subagents win.
  • Engineering / tool-chain workflow → MetaGPT / ChatDev. Roles + SOPs + handoff contracts.
  • Network-effect social product → OpenClaw / Moltbook. Substrate + emergent economy.
  • Classic enterprise automation → CrewAI or LangGraph (production leader, stable runtime).

The 2026 state-of-the-art summary

Where the field is in April 2026:

  • Frameworks are converging. MCP + A2A support is table stakes. Handoff semantics are the remaining design choice.
  • Evaluation is hardening. SWE-bench Pro, MARBLE, STRATUS mitigation benchmarks. Pro is the current contamination-resistant reality check.
  • Production failure rates are measurable (Cemri 2025 MAST; 41-86.7% on real MAS). The field is out of the "looks great in demo" era.
  • Cost is the central engineering constraint. Token cost per task, wall-clock per interaction, rainbow-deploy overhead. Multi-agent wins on accuracy but loses on cost — and that trade is the business decision.
  • Regulation is a near-term input, not a background concern. Jurisdictions are moving faster than individual deploy cycles.

The same idea as a formula

Token cost of a design. If a chat uses c tokens per task, Anthropic reports agents at about 4c and its multi-agent research system at about 15c. For T tasks at price π per token, a multi-agent run is worth it when

Δvalue per task>(15−1)cπ,
the extra value per task must beat the extra tokens.

A rule that ignores an input. A decision rule f(x1​,…,xk​) uses input xj​ only if some setting of the others makes f change when xj​ changes. Testing every combination, or a sample of them, shows which inputs a rule really reads.

Asking costs too. If an agent asks a clarifying question with probability qm​ when details are missing and qc​ when they are not, the useful signal is qm​−qc​; a rule that always asks has qm​=qc​=1 and adds a round trip to every task.

Worked example
Pricing one research query
  • Suppose a chat answer takes 5,000 tokens. A single agent uses about 20,000 and the multi-agent system about 75,000.
  • At 10 dollars per million tokens, that is 0.05, 0.20 and 0.75 dollars per query.
  • Over 10,000 queries a month the multi-agent system costs about 5,500 dollars more than a single agent.
  • It pays off if better answers are worth more than about 55 cents per query, which is plausible for research a person would otherwise do, and not for simple lookups.

Asking before answering, on a small model

This block continues from the one above. Qwen2.5-0.5B-Instruct (greedy, CPU) gets 8 requests that are missing an essential detail and 4 complete ones, with a plain system prompt and with one that tells it to ask one question first when something is missing. About 1 minute.

# This block continues from the one above. ChatDev's "communicative dehallucination": before answering, an agent
# asks for the details it is missing. Qwen2.5-0.5B-Instruct (greedy, CPU) gets 8 requests that leave out
# something essential and 4 that are complete, with a plain system prompt and with one that tells it to ask one
# question first when details are missing. Does it ask when it should, and only then? About 1 minute.
import os, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

MISSING = ["Write the function that converts the amounts.",
           "Book the meeting room for the team.",
           "Translate the contract.",
           "Send the report to the client.",
           "Resize the images for the website.",
           "Fix the bug in the login page.",
           "Schedule the backup.",
           "Make the chart for the board meeting."]
COMPLETE = ["Write a Python function that returns the sum of a list of integers.",
            "Convert 5 kilometres to miles.",
            "List the planets of the solar system in order from the Sun.",
            "Reverse the string 'agent' and give the result."]
SYSTEMS = {"plain": "You are a helpful agent on a team.",
           "ask first": ("You are a helpful agent on a team. If the request is missing a detail you need to do it "
                         "correctly, reply with exactly one short question asking for that detail and nothing else. "
                         "If nothing is missing, just do the task.")}
def reply(system, user):
    ids = tok.apply_chat_template([{"role": "system", "content": system}, {"role": "user", "content": user}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=40, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
asks = lambda text: "?" in text.split("\n")[0][:200]
for name, system in SYSTEMS.items():
    rm = [reply(system, u) for u in MISSING]; rc = [reply(system, u) for u in COMPLETE]
    print(f"{name:9s}: asked a question on {sum(map(asks, rm))}/8 incomplete requests and on {sum(map(asks, rc))}/4 complete ones")
    print(f"   e.g. {MISSING[2]!r} -> {rm[2][:90]!r}")
    print(f"        {COMPLETE[1]!r} -> {rc[1][:90]!r}")
What you should see
plain    : asked a question on 5/8 incomplete requests and on 0/4 complete ones
   e.g. 'Translate the contract.' -> "I'm sorry, but I need more information to translate the contract. Could you please provide"
        'Convert 5 kilometres to miles.' -> 'To convert kilometers to miles, you can use the conversion factor that 1 kilometer is appr'
ask first: asked a question on 8/8 incomplete requests and on 3/4 complete ones
   e.g. 'Translate the contract.' -> 'What specific details or context are you referring to when asking about translating a cont'
        'Convert 5 kilometres to miles.' -> 'What is 5 kilometers in miles?'
Reading this output

Without instructions, the model sometimes asked. With the plain prompt it asked a question on 5 of 8 incomplete requests, such as "Translate the contract." (which language?), and on none of the 4 complete ones.

With the rule, it asked every time. The ask-first prompt raised questions on all 8 incomplete requests, but also on 3 of 4 complete ones; asked to convert 5 kilometres to miles, it replied "What is 5 kilometers in miles?". The rule removed the guessing and added a pointless round trip to most complete requests.

Make the rule checkable. ChatDev's pattern works when the missing detail can be named. Give agents a list of required fields per task type, check them in code, and only send the clarifying question when a field is actually missing.

Part 1 of 3 · Design, map_to_case

"""Case-study mapper: pick the closest 2026 reference for a proposed design.

Stdlib only. Scripted mapping from design attributes to one of three case
studies (Anthropic Research, MetaGPT/ChatDev, OpenClaw/Moltbook) and the
framework-of-choice recommendation.
"""
from __future__ import annotations

from dataclasses import dataclass


@dataclass
class Design:
    name: str
    task_type: str          # "research" | "engineering" | "population" | "automation"
    n_agents_expected: int
    verification_required: bool
    runtime_duration_hours: float
    roles_distinct: bool
    user_facing_network: bool


CASES = {
    "anthropic_research": {
        "name": "Anthropic Research (supervisor-worker)",
        "patterns": ["fresh-context subagents", "orchestrator synthesis",
                     "rainbow deployment", "verification role"],
        "framework": "Anthropic Claude Agent SDK or LangGraph",
        "citation": "https://www.anthropic.com/engineering/multi-agent-research-system",
    },
    "metagpt_chatdev": {
        "name": "MetaGPT / ChatDev (SOP role-decomposition)",
        "patterns": ["role prompts encode SOP", "structured artifact handoffs",
                     "communicative dehallucination", "DAG routing at scale"],
        "framework": "CrewAI or MetaGPT reference impl",
        "citation": "arXiv:2308.00352 (MetaGPT), arXiv:2307.07924 (ChatDev), arXiv:2406.07155 (MacNet)",
    },
    "openclaw_moltbook": {
        "name": "OpenClaw / Moltbook (population-scale substrate)",
        "patterns": ["local ReAct loop", "agent-to-agent social graph",
                     "emergent economy", "prompt-injection threat model"],
        "framework": "custom substrate + MCP + A2A",
        "citation": "https://en.wikipedia.org/wiki/OpenClaw",
    },
}

FRAMEWORK_LANDSCAPE = [
    ("LangGraph", "production", "structured graph + checkpointing + HITL"),
    ("CrewAI", "production", "role-based crews; Sequential/Hierarchical"),
    ("AG2", "community maintenance", "GroupChat + speaker selection"),
    ("Microsoft Agent Framework", "RC (Feb 2026)", "orchestration patterns + enterprise"),
    ("OpenAI Agents SDK", "production", "Swarm successor; tool-return handoffs"),
    ("Google ADK", "production (Apr 2025)", "A2A-native; Google Cloud"),
    ("Anthropic Claude Agent SDK", "production", "agent + Research extension"),
]


def map_to_case(d: Design) -> str:
    if d.task_type == "population" or d.user_facing_network:
        return "openclaw_moltbook"
    if d.task_type == "engineering" or d.roles_distinct:
        return "metagpt_chatdev"
    if d.task_type == "research":
        return "anthropic_research"
    if d.verification_required and d.runtime_duration_hours >= 1:
        return "anthropic_research"
    return "anthropic_research"

Part 2 of 3 · print_case, print_landscape

def print_case(key: str) -> None:
    case = CASES[key]
    print(f"\n  closest case study: {case['name']}")
    print(f"  patterns to copy:")
    for p in case["patterns"]:
        print(f"    - {p}")
    print(f"  recommended framework: {case['framework']}")
    print(f"  citation: {case['citation']}")


def print_landscape() -> None:
    print("\n" + "=" * 78)
    print("FRAMEWORK LANDSCAPE: April 2026")
    print("=" * 78)
    print(f"  {'framework':30s} {'status':22s} {'best for':30s}")
    for name, status, best_for in FRAMEWORK_LANDSCAPE:
        print(f"  {name:30s} {status:22s} {best_for:30s}")
    print("\n  every major framework ships MCP support; most ship A2A.")
    print("  protocol compatibility is no longer a differentiator -- handoff semantics are.")


def main() -> None:
    designs = [
        Design("research-assistant", "research", 6, True, 2.0, False, False),
        Design("codegen-team", "engineering", 5, True, 1.0, True, False),
        Design("agent-marketplace", "population", 1000, False, 24.0, False, True),
        Design("internal-automation", "automation", 3, True, 0.5, True, False),
    ]

    print("=" * 78)
    print("CASE-STUDY MAPPER: proposed designs → closest 2026 reference")
    print("=" * 78)

    for d in designs:
        print(f"\ndesign: {d.name!r}")
        print(f"  type={d.task_type}  n_agents={d.n_agents_expected}  "
              f"verification={d.verification_required}  hours={d.runtime_duration_hours}")
        case_key = map_to_case(d)
        print_case(case_key)

    print_landscape()

    print("\nTakeaways:")
    print("  pick a case study first; adapt the design to match its known trade-offs.")
    print("  every 2026 framework supports MCP; most support A2A -- choose on handoff semantics.")
    print("  production-grade multi-agent needs: verification, cost accounting, rainbow deploys.")

Break it on purpose

Your team is asked to build a "research agent for the sales team" and copies Anthropic's design: an Opus-class lead with ten parallel subagents for every request. Most requests turn out to be "what is our list price for X" and "who owns account Y". Costs are twelve times the single-agent pilot, and answers are no better. Separately, the agents read customer emails that sometimes contain instructions. Using this lesson, what went wrong, and what would you build instead? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Orchestrator-worker is the default production shape. Anthropic's research system, Claude Code's subagents and most framework examples use a lead agent with workers that get fresh context.
  • Frameworks have settled. LangGraph, CrewAI, the OpenAI Agents SDK, Google ADK and Microsoft Agent Framework (1.0 in April 2026) all support MCP, and most support A2A.
  • Population-scale agents arrived fast. OpenClaw and Moltbook went from launch to a Meta acquisition and Chinese restrictions in under four months, with security, not capability, as the main story.
  • On your laptop: a small model can run a lead-and-worker loop for practice, but keep routing, checks and clarification rules in code, and match effort to the request.

Sources: Anthropic, Multi-agent research system, MetaGPT (arXiv:2308.00352), ChatDev (arXiv:2307.07924), MacNet (arXiv:2406.07155), TechRadar, Moltbook explained, Bloomberg, China curbs OpenClaw.

Recap
What to keep from this lesson
  • Anthropic's research system: a lead with parallel subagents, about 15x chat tokens, effort scaled to the query.
  • MetaGPT and ChatDev: roles from a process, documents as handoffs, and asking before guessing.
  • OpenClaw and Moltbook: at population scale, security and identity dominate.
  • Check that a decision rule actually reads the inputs it claims to.
  • A clarification rule needs tuning in both directions: ask when details are missing, not every time.

MFCheat sheet · Eval Farms and Multi-Agent Case Studies

Ship it

Starter rules for production multi-agent in 2026:

  • Start from a case study, not from scratch. Pick the closest of Anthropic Research / MetaGPT / OpenClaw and adapt.
  • Adopt MCP + A2A. Portability across frameworks is valuable; protocol support is free.
  • Measure against SWE-bench Pro or your internal Pro-equivalent. Verified is contaminated.
  • Pay the verification tax. An independent verifier adds tokens and latency (measure how much on your own workload) and buys correctness you can measure.
  • Rainbow deploy long-running agents. Expect multi-hour agent runs to be routine.
  • Read the AAAI 2026 multi-agent bridge program papers and the MAST follow-ups. The discipline is moving fast.

Given a proposed multi-agent system design, pick the closest canonical 2026 case study and adapt.

Produce:

1. **Design fingerprint.** Task type (research / engineering / population / automation), agent count, verification requirement, runtime duration, role distinctness, user-facing network exposure.
2. **Closest case study.**
   - **Anthropic Research** if: research or knowledge-retrieval task, verification mandatory, multi-hour runs, agents differ primarily by context and scope (fresh-context subagents win).
   - **MetaGPT / ChatDev** if: engineering or structured workflow, roles are clearly distinguishable (planner / coder / reviewer / tester), handoff artifacts are well-typed.
   - **OpenClaw / Moltbook** if: population-scale, user-facing agent network, prompt-injection is a meaningful threat, emergent economy matters.
3. **Patterns to copy.** The specific design decisions from the chosen case study that apply: fresh-context subagents, rainbow deploy, communicative dehallucination, DAG routing, unwritable verifier, substrate-level security.
4. **Framework recommendation.** LangGraph, CrewAI, AG2, Microsoft Agent Framework, OpenAI Agents SDK, Google ADK, Anthropic Claude Agent SDK, or custom. Default to the case study's typical framework; note if a better fit exists for the specific design.
5. **Anti-patterns from the case.** Things the reference case found NOT to work. Avoid in the new design.
6. **Cost projection.** Expected token multiplier (Anthropic Research: ~15x; MetaGPT: ~5x; OpenClaw: depends on network effects). Expected wall-clock and dollar cost range.
7. **Evaluation approach.** Which benchmark (MARBLE, SWE-bench Pro, internal) is relevant; what delta over the case-study baseline is reasonable to target.

Hard rejects:

- Designs that ignore verification when the task has correctness requirements. Every case study pays the verification tax.
- Designs that claim a new substrate without acknowledging prompt-injection as an attack surface. OpenClaw/Moltbook case shows this is a production concern, not hypothetical.
- "Revolutionary" claims that do not map to any case study. Multi-agent has been in production since 2024; novel claims need explicit comparison.
- Designs that skip MCP or A2A adoption without justification. Protocol support is table stakes.

Refusal rules:

- If the design has no clear task type, recommend scoping the task before picking a case study. "Multi-agent for everything" is not a design.
- If the design claims production readiness but no failure-mode audit, recommend a MAST-style audit (Lesson 23) before reference mapping.
- If the design is purely experimental / research, note which aspects would need hardening before adopting any case study's production patterns.

Output: a two-page brief. Start with a one-sentence summary ("Closest case study: MetaGPT / ChatDev. Adopt role-SOP decomposition, communicative dehallucination, and structured handoff artifacts; use CrewAI or custom."), then the seven sections above. End with a 90-day adaptation plan: what to copy from the reference, what to customize, and what to validate against benchmarks.

Exercises

  1. Read the Anthropic Research system post end-to-end. Identify three design decisions that would change if you replaced Opus 4 with a smaller model (e.g., Haiku 4).

  4. Read about OpenClaw and Moltbook. Pick one specific failure mode that emerged at population scale that would not appear in a 5-agent system. How would you engineer against it?
  5. Pick your current multi-agent project. Which of the three case studies is the closest reference? Which design decisions from that case study have you NOT yet adopted? Write down one you will adopt this quarter.

Solutions

SolutionP1 · OpenClaw, and none of them

OpenClaw / Moltbook, and none of them. map_to_case checks task_type == "population" or user_facing_network first, so any user-facing design maps to the population-scale case, whatever its size. n_agents_expected is never read, and the branch that reads verification_required and runtime_duration_hours returns the same case as the default, so they never change the answer either.

SolutionB1 · The wrong case study for the request mix

What went wrong. The request mix was lookups, which Anthropic's own guidance gives one agent and a few tool calls. Copying the complex-research setup for every request multiplied tokens without improving answers. And customer emails are untrusted input: instructions inside them can steer agents with tool access, the population-scale lesson from OpenClaw in miniature.

What to build instead: - Route by effort: a classifier or rules send lookups to a single agent with CRM and price-list tools, and only open-ended research to the lead-and-subagents path. - Measure per path: cost and accuracy for each request type, against the single-agent pilot. - Treat emails as data: strip or quote them, never execute instructions from them, and limit which tools an agent reading email can call. - Ask when needed: for account questions with ambiguous names, ask one clarifying question instead of guessing.
