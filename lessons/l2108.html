Why this came about

AI libraries adopted Python's type system because a model has to be told exactly what shape of data to send and return. Type hints, Pydantic models and JSON Schema became the common language between your code and a model, so this lesson teaches the Python features the rest of the course relies on.

The problem: the libraries assume more Python than the tutorials teach

From the next lesson on, the code uses features that beginner Python courses often skip. LangGraphlater · 14.79's state is a TypedDict with Annotated reducers, tools are functions wrapped by decorators, structured outputlater · 11.19 is Pydantic, streaming is generators, and parallel tool callslater · 14.56 use async. None of it is hard, but reading library code is slow until these are familiar. Each section below shows one feature, what it prints, and where the course uses it.

Type hints, TypedDict and Annotated

A type hint is a label that says what kind of value a variable or parameter is meant to hold, such as order_id: str. Python itself does not enforce hints, but AI libraries read them: they are how a library learns what your data looks like. A TypedDict describes a dictionary with fixed keys, Literal lists the only allowed values, and Annotated attaches extra information to a type. Run this and look at what the hints contain:

from typing import TypedDict, Annotated, Literal
import operator

class Order(TypedDict):                    # a dict with a declared shape: what LangGraph state looks like
    order_id: str
    status: Literal["processing", "shipped", "delivered"]

order: Order = {"order_id": "A-1001", "status": "shipped"}
print(order["status"], "|", Order.__annotations__)

Log = Annotated[list, operator.add]        # a type plus extra information that a library can read
print(Log.__metadata__)                    # LangGraph reads this to know how to merge updates (Lesson 6.10)
What you should see
shipped | {'order_id': <class 'str'>, 'status': typing.Literal['processing', 'shipped', 'delivered']}
(<built-in function add>,)

Type hints are labels: Python does not enforce them at run time, but tools, editors and libraries read them. TypedDict declares which keys a dictionary has; Literal limits a value to a few strings; Annotated attaches extra information to a type without changing it. LangGraph reads the annotations of your state class to learn its keys and reducers (Lesson 14.79), and LangChainlater · 14.71 reads a function's hints to build a tool's schema (Lessons 14.58 and 14.73).

Dataclasses and Pydantic

Two ways to define a small class that mostly holds data. A dataclass writes the __init__ for you and nothing more. A Pydantic model also checks the data when the object is created, and raises an error that says exactly which field was wrong. That checking is why every agent frameworklater · 14.70 uses Pydantic for anything that comes from a model. Compare the two:

from dataclasses import dataclass, field
from pydantic import BaseModel, Field, ValidationError

@dataclass
class Customer:                            # a small class with defaults; no validation
    customer_id: str
    tier: str = "silver"
    tags: list = field(default_factory=list)

print(Customer("C-42"))

class Refund(BaseModel):                   # a class that validates its data (Lessons 2.2 and 6.4)
    order_id: str = Field(pattern=r"^[A-Z]-\d{4}$")
    amount: int = Field(gt=0)

print(Refund(order_id="A-1001", amount="1200"))   # "1200" is converted to 1200
try:
    Refund(order_id="1001", amount=0)
except ValidationError as e:
    print([err["loc"][0] for err in e.errors()], "failed validation")
What you should see
Customer(customer_id='C-42', tier='silver', tags=[])
order_id='A-1001' amount=1200
['order_id', 'amount'] failed validation

A dataclass is a small class with an automatic constructor and printout, and no checking: use it for internal records and run context (Lesson 14.80). A Pydantic model validates and converts data when it is created: the string "1200" became the number 1200, and a malformed ID and a zero amount were rejected with errors naming the fields. Use Pydantic wherever data comes from outside your code: model outputs (Lesson 11.19), tool arguments (Lesson 14.73) and API requests (Lesson 14.90).

JSON and JSON Schema: how your Python is described to a model

A model never sees your Python; it only sees text. So whenever a library tells a model about a tool's arguments, or asks for an answer of a fixed shape, it first translates your Python into two standard text formats. Knowing them makes outputs like {'title': 'Order Id', 'type': 'string'} readable, and they appear in almost every lesson from 2.2 on.

In plain words first
A filled-in form, and the blank form
  • JSON is data as text: {"order_id": "A-1001", "amount": 1200}. It is how data travels between your code, model providers and web APIs.
  • JSON Schema is a description of data as text: "an object whose order_id is a string matching this pattern, and whose amount is a whole number above 0". It is the blank form with its labels and rules, not the data.
import json

order = {"order_id": "A-1001", "amount": 1200, "gift": False, "note": None}
text = json.dumps(order)                           # Python dict -> JSON text
print(text)
print(type(text).__name__, "->", type(json.loads(text)).__name__)   # and back

class A(BaseModel):
    x: int

print(A.model_json_schema())                       # Pydantic writes the JSON Schema for you
What you should see
{"order_id": "A-1001", "amount": 1200, "gift": false, "note": null}
str -> dict
{'properties': {'x': {'title': 'X', 'type': 'integer'}}, 'required': ['x'], 'title': 'A', 'type': 'object'}
Reading this output
  • JSON looks like a Python dictionary but is a string; False and None become false and null, and strings always use double quotes. When a model "returns JSON", it returns a string like this.
  • From the two-line class A, Pydantic generated the whole schema: 'type': 'object' (a class is an object), 'properties' (one entry per field), 'type': 'integer' (from int), 'required': ['x'] (no default), and two 'title' keys made from the field and class names. title is only a label; you never write it.

The Refund class above, as the schema a model would receive:

print(json.dumps(Refund.model_json_schema(), indent=1))

str, int, float, bool, list[str] "type": "string", "integer", "number", "boolean", "array" Yes
Literal["refund", "delivery"] "enum": ["refund", "delivery"] Yes: it picks one of them
Field(gt=0), ge=, le=, lt= "exclusiveMinimum", "minimum", "maximum", "exclusiveMaximum" Yes: it stays in range

Field(description="...") "description": "..." Yes, most of all: your instruction for the field

The field name "title" Barely; libraries often strip it before sending

The schema goes to the model; the model's answer comes back as JSON text, and the same class turns it into a checked object:

r = Refund.model_validate_json('{"order_id": "A-1001", "amount": 1200}')   # JSON text -> object
print(repr(r), "|", r.model_dump(), "|", r.model_dump_json())             # object -> dict -> JSON text
What you should see
Refund(order_id='A-1001', amount=1200) | {'order_id': 'A-1001', 'amount': 1200} | {"order_id":"A-1001","amount":1200}

That round trip is the whole idea behind structured output (Lesson 11.19) and tool calling (Lessons 14.56 and 14.73).

Check your mental model
  • ✗ "The model reads my Python class."
    ✓ It reads the JSON Schema Pydantic generated from it.
  • ✗ "title tells the model what a field means."
    ✓ description does; title is a label made from the name.
  • ✗ "A tool's schema describes what it returns."
    ✓ Only its inputs. Describe the result in the docstring if the model needs to know.

Functions as values, and decorators

In Python a function is a value like any other: you can pass it to another function, store it in a list, or return it. A decorator uses this. It is a function that takes a function and returns a new one, usually the original with something added. The @name line above a def applies it. Frameworks use decorators constantly (@tool, @app.get), so it helps to have built one:

import functools, time

def apply_twice(fn, x):                    # functions are values: pass them, store them, return them
    return fn(fn(x))
print(apply_twice(lambda n: n * 10, 3))

def timed(fn):                             # a decorator takes a function and returns a new one
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)
        took = time.perf_counter() - start
        print(fn.__name__, "took", "under 0.1 s" if took < 0.1 else "over 0.1 s")
        return result
    return wrapper

@timed                                     # the same as: get_status = timed(get_status)
def get_status(order_id: str) -> str:
    """Return a fake status."""
    return f"{order_id} is shipped"

print(get_status("A-1001"), "|", get_status.__name__, "|", get_status.__doc__)
What you should see
300
get_status took under 0.1 s
A-1001 is shipped | get_status | Return a fake status.

A function can be passed to another function and returned from one. A decorator is a function that takes a function and returns a new one, applied with @ above a definition. functools.wraps keeps the original's name and docstring, which matters because libraries read them: @tool builds a tool's name and description from exactly these (Lesson 14.73). When you see @tool, @entrypoint, @before_model or @traceable, read it as "this function, wrapped with extra behavior".

async and await

Much of an agent's time is spent waiting: for a model, for an API, for a database. Asynchronous code lets one program wait for several things at once. An async def function can pause at an await and let other work run. asyncio.gather starts several of them together. Three lookups that each take 0.2 seconds finish in about 0.2 seconds in total, not 0.6:

import asyncio

async def lookup(order_id: str, seconds: float) -> str:
    await asyncio.sleep(seconds)           # waiting without blocking: other tasks run meanwhile
    return f"{order_id} done"

async def main():
    start = asyncio.get_running_loop().time()
    results = await asyncio.gather(lookup("A-1001", 0.2), lookup("A-1002", 0.2), lookup("A-1003", 0.2))
    took = asyncio.get_running_loop().time() - start
    print(results, "| three 0.2 s waits took", "under 0.3 s" if took < 0.3 else "longer")

asyncio.run(main())
What you should see
['A-1001 done', 'A-1002 done', 'A-1003 done'] | three 0.2 s waits took under 0.3 s

async def defines a function that can pause at await while it waits, letting other work run meanwhile. asyncio.gather started three lookups together, so three 0.2-second waits took about 0.2 seconds, not 0.6. This is how parallel tool calls and concurrent requests stay fast (Lesson 14.59), and why some LangGraph features, such as node timeouts, need async nodes (Lesson 14.87). Async methods in the libraries start with a: ainvoke, astream, abatch.

Generators and with-blocks

Two small features that appear in almost every AI library. A generator is a function that hands out its results one at a time with yield, which is how streamed model output reaches your code. A with-block runs set-up code on the way in and clean-up code on the way out, even if an error happens in between; it is how files, connections and timers are opened and closed safely.

def stream_words(text: str):
    for word in text.split():
        yield word                         # a generator hands out one value at a time (Lesson 2.3)

pieces = stream_words("Refunds reach UPI in 2 days")
print(next(pieces), next(pieces), "|", list(pieces), "|", list(pieces))   # a generator is used up once read

class Timer:
    def __enter__(self):                   # runs at the start of the with-block
        print("open connection")
        return self
    def __exit__(self, *exc):              # runs at the end, even after an error
        print("close connection")
        return False

with Timer():
    print("use it")
What you should see
Refunds reach | ['UPI', 'in', '2', 'days'] | []
open connection
use it
close connection

A generator yields values one at a time, which is exactly what streaming is: for chunk in model.stream(...) reads a generator (Lessons 11.20 and 14.84). A generator can be read only once; the second list(pieces) was empty, a common streaming bug. A with block runs setup and cleanup around your code, even when an error happens: the SDK's messages.stream(...) and database connections use it.

Reading a signature

A function's signature is its first line: the name, the parameters and their types. Library documentation is mostly signatures, so being able to read one is a practical skill. This example has every part you will meet: required parameters, a Literal, a bare * (everything after it must be passed by name), a default value, an optional type and **extra, which collects any additional named arguments.

import inspect
from typing import Literal

def create_ticket(customer_id: str, topic: Literal["refund", "delivery"], *, urgent: bool = False,
                  tags: list[str] | None = None, **extra) -> dict:
    return {"customer_id": customer_id, "topic": topic, "urgent": urgent, "tags": tags or [], **extra}

print(inspect.signature(create_ticket))
print(create_ticket("C-42", "refund", urgent=True, channel="chat"))
try:
    create_ticket("C-42", "refund", True)  # urgent is keyword-only: after the *
except TypeError as e:
    print("TypeError:", e)
What you should see
(customer_id: str, topic: Literal['refund', 'delivery'], *, urgent: bool = False, tags: list[str] | None = None, **extra) -> dict
{'customer_id': 'C-42', 'topic': 'refund', 'urgent': True, 'tags': [], 'channel': 'chat'}
TypeError: create_ticket() takes 2 positional arguments but 3 were given

Everything after a lone * must be passed by name, which libraries use to keep calls readable (model.invoke(messages, config=...)). **extra collects any other named arguments, which is how many LangChain classes pass settings through to a provider. When a call fails with a TypeError, compare it with inspect.signature or the library's reference.

Exercises

Predict before you run

Refund(order_id="A-1001", amount=1200.7): does Pydantic accept it, convert it, or reject it? (Solution P1.)

Break it on purpose

Remove @functools.wraps(fn) from timed, and print get_status.__name__ and get_status.__doc__. Why would that break a tool decorated with both @tool and @timed? (Solution B1.)

Debugging exercise
Debugging exercise: a stream that shows nothing

A UI prints the reply as it streams, then saves it:

pieces = stream_words("Refunds reach UPI in 2 days")
for p in pieces:
    show(p)
save(" ".join(pieces))      # saves an empty string

Why is the saved reply empty, and how do you fix it? (Solution D1.)

Make it your own

Change main in the async example to look up ten orders with at most three at a time, using asyncio.Semaphore. (Solution M1.)

Solutions

SolutionP1 · Pydantic refuses to lose information

It rejects it: Pydantic converts "1200" to 1200 because no information is lost, but converting 1200.7 to an integer would drop the fraction, so it raises a validation error ("Input should be a valid integer, got a number with a fractional part"). Strict modelater · 14.58 (model_config = {"strict": True}) would reject the string too.

SolutionB1 · Lost names and docstrings

Without wraps, the wrapped function is called wrapper and has no docstring. A tool built from it would be named wrapper with no description, and LangChain refuses a tool without one (Lesson 14.73). Libraries depend on the metadata decorators preserve.

SolutionD1 · A generator is used up

The for loop consumed every piece, so the generator was empty when join read it. Keep the pieces as they pass: shown = [], then shown.append(p) inside the loop, and save " ".join(shown). The streaming SDKs solve the same problem with get_final_message() (Lesson 11.20) and chunk addition (Lesson 14.71).

SolutionM1 · Limit concurrency

Create limit = asyncio.Semaphore(3) and wrap the lookup: async def limited(oid): async with limit: return await lookup(oid, 0.2). Then await asyncio.gather(*(limited(f"A-{1000 + i}") for i in range(10))) runs at most three at once, taking about four rounds of 0.2 seconds. This is what max_concurrency does for batch (Lesson 14.71) and what protects provider quotas (Lesson 14.116).

Check your understanding

Explain the mechanismWhy do LLM frameworks rely so heavily on Python type hints?

Worked answer. Because hints are machine-readable: a library can turn a function's parameters into a JSON Schema for a tool, a TypedDict into a graph's state channels, an Annotated reducer into merge behavior, and a Pydantic model into a structured-output schema and a validator. The same declaration serves the model, the runtime and your editor, so you write the shape of your data once.

A plausible wrong answer. "Python enforces types at run time." It does not; libraries such as Pydantic do, where they choose to.

Follow-ups. What is the difference between a dataclass and a Pydantic model?

Debug a failureAn async agent service is slow under load even though each request mostly waits on the model. What do you check?

Worked answer. Whether something blocks the event loop: a synchronous call (a sync HTTP client, time.sleep, CPU-heavy parsing) inside an async function stops every other request while it runs. Use async clients (ainvoke), run blocking work in a thread pool, and check that the server runs enough workers.

A plausible wrong answer. "Async is slower than threads." Async is fast for waiting; it is slow only when the waiting is done with blocking calls.

Follow-ups. How would you find a blocking call?

Defend a designShould a team write its agent code with full type hints?

Worked answer. Yes. The libraries read them, so hints are part of the behavior, not just documentation: tool schemas, state reducers and output validation come from them. They also let a type checker catch wrong state keys and arguments before a run. The cost is small; the main risk is hints that lie, so run a type checker in CI.

A plausible wrong answer. "Hints are optional style." In these libraries they change what the code does.

Follow-ups. Which type checker would you run, and where?
