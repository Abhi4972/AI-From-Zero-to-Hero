In plain words first
The idea in one line

A vision encoder converts an image into tokens. An MLP projector maps those tokens into the LLM's embedding space. A language model does the rest. That pattern, ViT-MLP-LLM, underlies almost every open VLM today.

The problem

In plain words first

A vision-language model (VLM) is a chatbot that can look at pictures. It has three parts. An image encoder (a ViT, often from CLIP or SigLIP) turns the picture into a few hundred or thousand vectors, one per patch. A small projector network converts those vectors into the same format as the language model's word embeddings. The language model then reads the "image words" followed by your question, and writes the answer word by word. Because the language model is fluent, it can also be fluently wrong about the picture; checking answers against the image is part of using VLMs well.

CLIP (Phase 4 Lesson 4.18) gives you a shared embedding space for images and text, which is enough for zero-shot classification and retrieval. It cannot answer "how many red cars are in this image?" because CLIP does not generate text — it only scores similarities.

Vision-Language Models (VLMs) — Qwen3-VL, InternVL3.5, LLaVA-Next, GLM-4.6V — bolt a CLIP-family image encoder to a full language model. The model sees an image plus a question and generates an answer. The strongest open-weight VLMs now report scores close to leading closed models on many multimodal benchmarks (MMMU, MMBench, DocVQA, ChartQA, MathVista, OSWorld).

The trio of pieces (ViT, projector, LLM) is the standard. The differences between models are in which ViT, which projector, which LLM, the training data, and the alignment recipe. Once you understand the pattern, swapping any component is mechanical.

Idea 1 · The ViT-MLP-LLM architecture

  1. Vision encoder — a pretrained ViT (CLIP-L/14, SigLIP, DINOv3, or a fine-tuned variant). Produces patch tokens.
  2. Projector — a small module (2-4 layer MLP, or a Q-former) that maps vision tokens into the LLM's embedding dimension. It is the only part trained from scratch, so it is always trained; how much of the encoder and LLM is also unfrozen depends on the stage (Idea 3).
  3. LLM — a decoder-only language model (Qwen3, Llama, Mistral, GLM, InternLM). Reads the vision + text tokens in sequence, generates text.

All three pieces are trainable in principle. In practice the first stage trains only the projector, which is cheap; later stages usually unfreeze the LLM and often the encoder too, which is where most of the compute goes.

Worked example
How many tokens is a picture?

A ViT with 14-pixel patches on a 448 × 448 image produces (448/14)2=322=1,024 patch tokens. Many VLMs then merge neighbouring tokens (a 2 × 2 merge gives 256) before the projector, because every image token costs the language model as much as a word: it takes part in attention for the whole answer. High-resolution inputs are often cut into tiles, each encoded separately, so one photo can cost a thousand tokens or more. The small VLM under "Use it" prints its count: about a thousand image tokens for one 500 × 461 photo, against about 20 for the question.

Check your mental model
  • ✗ "The LLM sees the pixels."
    ✓ It sees projected vectors placed where the <image> tokens were. It never sees pixels, which is one reason fine details like small text can be lost.
  • ✗ "A fluent answer is a grounded answer."
    ✓ The language model will write a confident sentence whether or not the image supports it. "Use it" shows a small VLM naming the wrong instrument.
  • ✗ "The projector is a big part of the model."
    ✓ It is usually tiny: about 7M of the 228M parameters in the model under "Use it".

Idea 2 · DeepStack

Vanilla projection uses only the last ViT layer. DeepStack (Qwen3-VL) samples features from multiple ViT depths and stacks them. Deeper layers carry high-level semantics; shallower layers carry fine-grained spatial and textural information. Feeding both into the LLM closes the gap between "what does the image contain" (semantics) and "where exactly" (spatial grounding).

Idea 3 · Three training stages

Modern VLMs train in stages:

  1. Alignment — freeze ViT and LLM. Train only the projector on image-caption pairs. Teaches the projector to map vision space into language space.
  2. Pre-training — unfreeze everything. Train on large-scale interleaved image-text data (500M+ pairs). Builds the model's visual knowledge.
  3. Instruction tuning — fine-tune on curated (image, question, answer) triples. Teaches conversational behaviour and task formats. This is what turns a "vision-aware LM" into a usable assistant.

Most LoRA fine-tunes target stage 3 with a small labelled dataset.

Idea 5 · Visual agents

Qwen3-VL-235B was reported at release among the strongest models on OSWorld — a benchmark for visual agents that operate GUIs (desktop, mobile, web). The model sees a screenshot, understands the UI, and emits actions (click, type, scroll). Combined with tools, it closes the loop on common desktop tasks. This is what most 2026 "AI PC" demos run under the hood.

Idea 6 · Agentic capabilities + RoPE variants

VLMs need to know when a frame is in a video. Qwen3-VL evolved from T-RoPE (temporal rotary position embeddings) to text-based time alignment — explicit timestamp text tokens interleaved with video frames. The model sees "<timestamp 00:32> frame, prompt" and can reason about temporal relationships.

Idea 7 · The alignment problem

Web-crawled image-text pairs often contain captions that are not fully grounded in the image. A VLM trained on such data learns to hallucinate — fabricate objects, misread numbers, invent relationships. In production this is the dominant failure mode.

One simple way to track it is a cross-modal error rate (CMER), a monitoring heuristic rather than a standard benchmark:

CMER = fraction of outputs where the text confidence is high but the image-text similarity (via a CLIP-family checker) is low

High CMER means the model is confidently saying things not grounded in the image. The value of such a signal is not that it fixes the model but that it lets you route suspicious outputs to human review. How well it works depends entirely on the checker; "Use it" tries one and shows its limits.

Idea 8 · Fine-tuning with LoRA / QLoRA

Full fine-tuning of a 70B VLM is out of reach for most teams. LoRA (rank 16-64) on attention + projector layers, or QLoRA with 4-bit base weights, fits on a single A100 / H100. Cost: 5,000-50,000 examples, $100-$5,000 in compute, 2-10 hours of training.

Idea 9 · Spatial reasoning is still weak

Spatial reasoning (above-below, left-right, counting, distance) remains a weak spot on dedicated benchmarks, with VLMs well below human accuracy. If your use case depends on "which object is on top of which," validate heavily — generic VLM performance is below human. Better-than-VLM alternatives for pure spatial tasks: a specialised keypoint / pose estimator, a depth model, or a detection model with box geometry post-processed.

The same idea as a formula

The pipeline. A vision encoder turns an image into N patch vectors V∈RN×dv​; a projector maps them into the language model's embedding space; the language model reads them as ordinary token embeddings next to the text:

Hv​=W2​GELU(W1​V⊤)⊤∈RN×dLLM​,input=[e(t1​),…,Hv​,…,e(tM​)]

The answer is generated as usual, p(yk​∣y<k​,Hv​,t), and the training loss is the cross-entropy on the answer tokens only.

Sequence cost. Every image token takes part in attention for the whole answer, so N image tokens and M text tokens cost attention like (N+M)2 and add N positions to the KV cache; merging 2×2 neighbouring patches before the projector divides N by 4.

Training stages. (1) Align: freeze the vision encoder and the language model, train only the projector on image–caption pairs. (2) Instruction-tune: unfreeze the language model (and often the encoder) on visual question answering and dialogue. (3) Preference or reinforcement tuning to reduce hallucination.

Fine-tuning cheaply. LoRA adds r(d+k) parameters per adapted matrix; QLoRA stores the frozen base weights in 4 bits (N/2 bytes for N parameters), so a 7B model's base weights take about 3.5 GB.

Hallucination as a metric. CMER, the fraction of answers with high text confidence but low image–text similarity, turns grounding failures into a number to monitor.

Step 1 · The projector

The part you will train most often. 2-4 layer MLP with GELU.

import torch
import torch.nn as nn


class Projector(nn.Module):
    def __init__(self, vit_dim=768, llm_dim=4096, hidden=4096):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(vit_dim, hidden),
            nn.GELU(),
            nn.Linear(hidden, llm_dim),
        )

    def forward(self, x):
        return self.net(x)

Input is a (N_patches, d_vit) token tensor. Output is (N_patches, d_llm). The LLM treats every output row as just another token.

Break it on purpose

Delete the nn.GELU() from Projector, leaving two nn.Linear layers back to back. The shapes are unchanged and the code still runs. Step 2 · Assemble ViT-MLP-LLM end-to-end

Skeleton of the forward pass for a minimal VLM. Real code uses transformers; this is the conceptual layout.

class MinimalVLM(nn.Module):
    def __init__(self, vit, projector, llm, image_token_id):
        super().__init__()
        self.vit = vit
        self.projector = projector
        self.llm = llm
        self.image_token_id = image_token_id  # placeholder token in text prompt

    def forward(self, image, input_ids, attention_mask):
        # 1. vision features
        vision_tokens = self.vit(image)                     # (B, N_patches, d_vit)
        vision_embeds = self.projector(vision_tokens)       # (B, N_patches, d_llm)

        # 2. text embeddings
        text_embeds = self.llm.get_input_embeddings()(input_ids)  # (B, M, d_llm)

        # 3. replace image placeholder tokens with vision embeds
        merged = self._merge(text_embeds, vision_embeds, input_ids)

        # 4. run LLM
        return self.llm(inputs_embeds=merged, attention_mask=attention_mask)

    def _merge(self, text_embeds, vision_embeds, input_ids):
        out = text_embeds.clone()
        expected = vision_embeds.size(1)
        for b in range(input_ids.size(0)):
            positions = (input_ids[b] == self.image_token_id).nonzero(as_tuple=True)[0]
            if len(positions) != expected:
                raise ValueError(
                    f"batch item {b} has {len(positions)} image tokens but vision_embeds has {expected} patches."
                    " Every sample in the batch must be pre-padded to the same number of image placeholder tokens.")
            out[b, positions] = vision_embeds[b]
        return out

The <image> placeholder token in the text gets replaced with real image embeddings — same pattern LLaVA, Qwen-VL, and InternVL use.

Step 3 · CMER computation

A lightweight runtime check.

import torch.nn.functional as F


def cross_modal_error_rate(image_emb, text_emb, text_confidence, sim_threshold=0.25, conf_threshold=0.8):
    """
    image_emb, text_emb: embeddings of image and generated text (normalised internally)
    text_confidence:     mean per-token probability in [0, 1]
    Returns:             fraction of high-confidence outputs with low image-text alignment
    """
    image_emb = F.normalize(image_emb, dim=-1)
    text_emb = F.normalize(text_emb, dim=-1)
    sim = (image_emb * text_emb).sum(dim=-1)        # cosine similarity
    high_conf_low_sim = (text_confidence > conf_threshold) & (sim < sim_threshold)
    return high_conf_low_sim.float().mean().item()

Treat CMER as a production KPI. Monitor it per endpoint, per prompt type, per customer. Rising CMER indicates the model is starting to hallucinate on some input distribution.

Step 4 · Toy VLM classifier (runnable)

Demonstrate the projector trains. Fake "ViT features" go in; a tiny LLM-style token predicts a class.

class ToyVLM(nn.Module):
    def __init__(self, vit_dim=32, llm_dim=64, num_classes=5):
        super().__init__()
        self.projector = Projector(vit_dim, llm_dim, hidden=64)
        self.head = nn.Linear(llm_dim, num_classes)

    def forward(self, vision_tokens):
        projected = self.projector(vision_tokens)
        pooled = projected.mean(dim=1)
        return self.head(pooled)

One can fit this on synthetic (feature, class) pairs in under 200 steps — enough to show the projector pattern works.

Use it: the same idea with real libraries

Watch out
Two notes on the code below

It loads an 8B model (about 16 GB in bfloat16), so it is shown but not run on this page; "Use it" runs the same pattern with a 256M-parameter VLM. It uses AutoModelForImageTextToText: the older AutoModelForVision2Seq name no longer exists in current transformers.

Three ways production teams use VLMs in 2026:

  • Hosted API — OpenAI Vision, Anthropic Claude Vision, Google Gemini Vision. Zero infra, vendor risk.
  • Open-source self-host — Qwen3-VL or InternVL3.5 via transformers and vllm. Full control, higher up-front effort.
  • Fine-tune on domain — load Qwen2.5-VL-7B or LLaVA-1.6-7B, LoRA on 5k-50k custom examples, serve with vllm or TGI.
from transformers import AutoProcessor, AutoModelForImageTextToText
import torch
from PIL import Image

model_id = "Qwen/Qwen3-VL-8B-Instruct"
processor = AutoProcessor.from_pretrained(model_id)
model = AutoModelForImageTextToText.from_pretrained(model_id, dtype=torch.bfloat16, device_map="auto")

messages = [{
    "role": "user",
    "content": [
        {"type": "image", "image": Image.open("plot.png")},
        {"type": "text", "text": "What does this chart show?"},
    ],
}]
inputs = processor.apply_chat_template(messages, add_generation_prompt=True, tokenize=True, return_dict=True, return_tensors="pt").to(model.device)
generated = model.generate(**inputs, max_new_tokens=256)
answer = processor.decode(generated[0][inputs["input_ids"].shape[1]:], skip_special_tokens=True)

import io, time
import pyarrow.parquet as pq
import matplotlib.pyplot as plt
from huggingface_hub import hf_hub_download
from transformers import AutoProcessor, AutoModelForImageTextToText

table = pq.read_table(hf_hub_download("Multimodal-Fatima/Imagenette_validation",
                                      "data/validation-00000-of-00001-b518380f1876c09a.parquet", repo_type="dataset"),
                      columns=["image"])
photo = lambda row: Image.open(io.BytesIO(table.column("image")[row].as_py()["bytes"])).convert("RGB")
vlm_id = "HuggingFaceTB/SmolVLM-256M-Instruct"
vlm_proc = AutoProcessor.from_pretrained(vlm_id)
vlm = AutoModelForImageTextToText.from_pretrained(vlm_id, dtype=torch.float32).eval()
for name, part in vlm.model.named_children():
    print(f"{name:13s} {type(part).__name__:26s} {sum(p.numel() for p in part.parameters()) / 1e6:6.1f}M parameters")

def ask(image, question):
    messages = [{"role": "user", "content": [{"type": "image"}, {"type": "text", "text": question}]}]
    inputs = vlm_proc(text=vlm_proc.apply_chat_template(messages, add_generation_prompt=True), images=[image], return_tensors="pt")
    with torch.no_grad():
        out = vlm.generate(**inputs, max_new_tokens=40, do_sample=False, output_scores=True, return_dict_in_generate=True)
    new_tokens = out.sequences[0, inputs["input_ids"].shape[1]:]
    probs = torch.stack([s.softmax(-1)[0, t] for s, t in zip(out.scores, new_tokens)])
    answer = vlm_proc.decode(new_tokens, skip_special_tokens=True).strip()
    n_image = int((inputs["input_ids"] == vlm.config.image_token_id).sum())
    return answer, probs.mean().item(), n_image

A grounding check

The lesson's cross_modal_error_rate needs an image embedding and a text embedding. Here OpenCLIP ViT-B/32 embeds each photo and each answer, and the function flags answers that are confident but weakly matched to the image.

clip_model, _, clip_pre = open_clip.create_model_and_transforms("ViT-B-32", pretrained="laion2b_s34b_b79k")
clip_tok = open_clip.get_tokenizer("ViT-B-32")
with torch.no_grad():
    img_emb = clip_model.encode_image(torch.stack([clip_pre(photo(r)) for r, _, _, _ in answers]))
    txt_emb = clip_model.encode_text(clip_tok([a for _, _, a, _ in answers]))
conf = torch.tensor([c for _, _, _, c in answers])

Reading this output

The check is crude, and this run shows both ways it fails. At a threshold of 0.20 the only answer flagged is "There is no cat present in the image.", which is correct: a sentence about a cat naturally has low similarity to a photo of puppies. The wrong answer, "holding a trumpet", scores 0.27 and passes, because a trumpet is close to the real brass instrument in CLIP's space. Raise the threshold to 0.25 and correct answers about the dogs get flagged too. Comparing alternatives is more informative: CLIP prefers "tuba" over "trumpet" for that photo, catching the VLM's mistake. In production, grounding checks work best as comparisons or targeted verification questions, with the threshold tuned on labelled examples, rather than one global similarity score.

Recap
What to keep from this lesson
  • VLM = vision encoder + small projector + language model; image tokens are spliced in where the <image> placeholder sits.
  • Training goes in stages: align the projector, then pre-train broadly, then instruction-tune.
  • One image costs hundreds to thousands of tokens; resolution and tiling drive cost.
  • VLMs answer fluently whether or not the image supports it; their own token probabilities do not reveal mistakes.
  • Monitor grounding with explicit checks, and validate spatial, counting and text-reading tasks on your own data.

Solutions

SolutionP1 · Two or three of five

SmolVLM gets the dog count and the absent cat right, describes the puppies mostly correctly but invents a detail, names the brass instrument wrongly, and evades the truck lettering. A 256M-parameter VLM is good at "what is in the picture" and weak at fine distinctions and reading text; larger models improve on both, but the failure types (confident misidentification, invented details) remain.

SolutionB1 · Two matrices that collapse into one

Without the activation, W2​(W1​x+b1​)+b2​=(W2​W1​)x+(W2​b1​+b2​): the two layers are exactly one linear map from 768 to 4,096 dimensions, so the extra 768×4096+4096×4096≈20 million weights buy nothing that a single 768×4096 matrix (3.1 million) could not do. The first LLaVA used just such a single linear projection; LLaVA-1.5 switched to a two-layer MLP with GELU and reported better results, which is why the MLP projector is now the default. A linear projector still works, because the language model itself is non-linear; it is simply a weaker adapter.

Industry practice
What's current (2024–2026)
  • Open VLMs in use. Qwen2.5-VL and Qwen3-VL, Gemma 3, InternVL and Llama 4's multimodal models follow the encoder → projector → LLM pattern of this lesson; vLLM and SGLang serve them with OpenAI-compatible APIs.
  • APIs. GPT, Gemini and Claude models accept images and PDFs in the same request as text, and are the usual choice for document and screenshot understanding.
  • Small VLMs on devices. Models of 1–4B parameters (SmolVLM, Gemma 3n, Qwen3-VL's small sizes) run on phones and laptops.

6. `hosting == edge` -> **MiniCPM-V-2.6** or **Qwen2.5-VL-3B** quantised to INT4.
7. `context_tokens_needed > 100K` -> **Qwen3-VL** (256K native) or **InternVL3.5**.

# CMER Monitor

Treat cross-modal alignment as a first-class production KPI.

## When to use

- Deploying any VLM endpoint that produces text grounded on images.
- Investigating reports of hallucinated responses.
- Tracking whether an input distribution shift degrades model grounding.

## Inputs

- `vlm_output`: generated text.
- `text_confidence`: mean per-token probability after softmax, in `[0, 1]`. Compute as `exp(mean(log_probs))`. Do not pass raw logits; raw logits are unbounded and `conf_threshold` assumes a probability.
- `image_embedding`: CLIP-family embedding of the image (DINOv3, SigLIP, CLIP).
- `text_embedding`: CLIP-family embedding of the generated text.
- Optional `prompt_type`: label for grouping (vqa / ocr / captioning / agent).

## Per-request computation

```python
import torch

def cmer_flag(image_emb, text_emb, text_conf, sim_thr=0.25, conf_thr=0.8):
    if image_emb.shape != text_emb.shape:
        raise ValueError(f"emb shape mismatch: {image_emb.shape} vs {text_emb.shape}")
    image_emb = image_emb / (image_emb.norm() + 1e-8)
    text_emb = text_emb / (text_emb.norm() + 1e-8)
    sim = float((image_emb * text_emb).sum())
    flagged = (text_conf > conf_thr) and (sim < sim_thr)
    return {"sim": sim, "flagged": flagged}
```

Embeddings are 1-D PyTorch tensors (`torch.float32`) from an independent CLIP-family encoder. If you use NumPy arrays, swap `.norm()` for `np.linalg.norm(...)` and cast the output accordingly.

Store `sim`, `text_conf`, `flagged`, `prompt_type`, `timestamp`, `model_version`, `request_id` to your monitoring pipeline (Prometheus, DataDog, OpenTelemetry).

## Aggregate metric

```
CMER = (flagged requests in window) / (total requests in window)
```

Report per endpoint, per prompt_type, per model version.

## Alert thresholds

- Baseline CMER: establish over 7 days of normal traffic.
- Warning: CMER >= 1.5x baseline for 1 hour.
- Critical: CMER >= 2x baseline for 30 minutes or > 15% absolute for any window.

## Dashboard panels

1. CMER over time (5-minute bucket, 7-day window).
2. CMER by prompt_type (stacked bar).
3. Distribution of `sim` per hour (histogram).
4. Top hallucinated outputs (sample 20 flagged responses per day for human review).

## Actions when CMER spikes

1. Sample the flagged requests.
2. Verify the model version has not changed inadvertently.
3. Check the input distribution (new file format? new image source? compressed differently?).
4. Route the affected traffic to human review until the spike resolves.
5. If the spike is persistent, fine-tune or replace the model; do not suppress the alert.

## Rules

- Never compute CMER using the VLM's own embeddings; use an independent encoder (DINOv3, SigLIP, or CLIP-L/14). Otherwise you are measuring the model's self-consistency, not alignment.
- Always log the raw `sim` value, not just the `flagged` bit; distribution shifts show up in the lower quartile before the flag rate changes.
- Do not ship a VLM endpoint without CMER monitoring; hallucinations are the dominant production failure mode and silent without this metric.
- For sensitive domains (medical, legal, financial), raise `sim_threshold` to 0.35 or higher; the flag condition is `sim < sim_threshold`, so a higher threshold catches more outputs as potentially ungrounded — the right default for high-stakes use.

Exercises

  1. (Easy) Run three prompts ("what is this?", "count the objects", "describe the scene") through any open VLM on five images. Score each answer as correct / partially correct / hallucinated by hand. Compute a first-pass CMER-like rate.
  2. (Medium) Fine-tune Qwen2.5-VL-3B or LLaVA-1.6-7B with LoRA (rank 16) on 500 images of a target domain with captions. Compare zero-shot vs fine-tuned MMBench-style accuracy.
  3. (Hard) Replace the VLM's image encoder with DINOv3 instead of its default SigLIP/CLIP. Re-train only the projector (frozen LLM + frozen DINOv3). Measure whether dense-prediction tasks (counting, spatial reasoning) improve.

Weigh a trade-offYou can spend your data budget on one of two things: have a strong proprietary model write captions for two million images, or pay people to describe seven hundred thousand images in detail by speaking for a minute or more about each one. Which do you choose for a new vision-language model, and what is the evidence?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Pay the people. The reference result is a model trained on 712K densely captioned images and no distilled captions that beat a much larger model on 11 of 11 benchmarks. Dense human captions carry 5 to 10 times the information of a short web caption and stay grounded in the image, while distilled captions inherit the hallucinations of the model that wrote them; about 12 percent of crawled pairs already describe things that are not in the image. Caption density beats caption quantity, which beats distillation convenience.

The evidence.

  • The dense-caption recipe: annotators described each image for one to three minutes in speech, transcribed to text, which gave 712K densely captioned images. The 72B model trained on them beat a 90B competitor on every one of 11 benchmarks. The difference was not architecture.
  • Two other datasets followed the same path with mixed human and synthetic captions, and the trend across them is that density wins.
  • The first visual instruction set was written by a text-only model from captions and boxes without seeing the image, 158k turns; it worked to unlock dialogue, with noise.

Why density beats volume.

A dense caption of 80 to 300 tokens names objects, counts, relations, text in the image and context; a web alt text names one thing. For alignment and instruction tuning the model learns from what the caption says about the image, so the information per image is the currency, not the image count.

Why distillation is risky.

The writing model does not see what it does not see. It hallucinates plausible content, and the student learns to hallucinate with the same confidence. A benchmark built from similar data does not punish it; production users do.

When distillation still has a place.

  • Bootstrapping a new domain fast, before human data arrives.
  • Generating questions and answers from a human-written caption, which keeps the grounding in the caption.
  • Filtered: score each synthetic caption against the image with a contrastive checker and drop the ungrounded tail.

What to do with the budget.

Dense human captions for the alignment and instruction stages, task-specific instruction data on top, and synthetic data only where a human caption anchors it. Measure grounding on a held-out human-labelled set, not only benchmark accuracy.

Plausible wrong answers.

  • "Two million captions beat seven hundred thousand; more data wins." The reference result beat a larger model with fewer, denser, grounded captions; volume of thin or hallucinated captions is no substitute.
  • "The strong model's captions are better than what annotators write." They are longer than web captions but not grounded; the model describes what it expects, and the student learns the same habit.
  • "Caption quality only matters for captioning tasks." The reference model gained on every benchmark, reasoning and reading included, because the alignment stage learned more about each image.

Follow-ups an interviewer may ask.

  • (level 3) Why did the speech-based collection matter? Expected: people say far more in a minute than they type, so the captions are long and specific at a cost that scales.
  • (level 3) How do you check that a synthetic caption is grounded? Expected: embed the image and the caption with a contrastive checker and flag low similarity, then read a sample; drop or rewrite the tail.
  • (level 4) How would you prove to a skeptic that the gain is data and not model size? Expected: the reference comparison beat a larger model; replicate at one size with two data mixes and the same encoder, connector and schedule.
  • (level 4) Where in the three-stage pipeline do dense captions pay most? Expected: alignment and the first instruction stage, where the projector and the language model learn what an image contains; task-specific data pays in the last stage.

Explain the mechanismYour 7B vision-language model trails a competitor on a multimodal reasoning benchmark by several points. The team's plan is a new connector design. Argue for or against, using what the ablation literature says about where the score comes from.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. Against. Across the controlled studies, swapping the connector moved a reasoning benchmark by less than a point at a fixed token count, while swapping the encoder moved it by three or more, and doubling the language model from 7B to 13B added two to four points. The reasoning ceiling of such a model is the text reasoning ceiling of its language model; the visual side can only feed it. Spend the effort on the language model size, the encoder, the token count and the data before the connector.

The decomposition.

The one study that held every axis fixed but one found that the per-image visual-token count explained about 60 percent of the variance in scores, the encoder about 20 percent, the connector about 5 percent, and everything else about 15 percent.

The language model sets the ceiling.

Going from a 7B to a 13B language model reliably added 2 to 4 points on the flagship reasoning benchmark across the papers in the lesson, and at 70B most benchmarks saturate. The reason is structural: the encoder produces features and the connector translates them, but the reasoning happens in the language model. A 7B model cannot stand in for a 70B model through a cleverer connector.

The encoder is the second lever.

Swapping the common contrastive encoder for a stronger one added 3 or more points on the reasoning benchmark in one study, and self-supervised encoders led a vision-centric benchmark by about 5 to 7 points over the common contrastive one. The 2026 default pairs a strong contrastive encoder with a self-supervised one for dense features when grounding matters.

The connector is a wash.

At a fixed token count, an MLP, a query bridge and a resampler landed within about 1 point of each other in several independent studies. The connector is a cost question about tokens, not a quality question.

What to do instead.

  1. Check the token count per image; more visual tokens up to the sweet spot helps more than any connector.
  2. Check the encoder and the resolution schedule.
  3. Check the data: detailed human captions beat distilled synthetic captions at the same token count.
  4. If the gap is in reasoning, the honest fix is a larger language model, and the budget question follows.

Plausible wrong answers.

  • "The connector is where the modalities meet, so it must matter most." Its measured share is about 5 percent of the variance; the token count and the encoder dominate.
  • "A better connector lets a small language model reason like a large one." The reasoning ceiling is the language model's; no bridge adds reasoning the language model does not have.
  • "More visual tokens always help." They help up to the sweet spot and then give diminishing returns at a growing compute cost; the gain is in the token count, not in the architecture that emits them.

Follow-ups an interviewer may ask.

  • (level 2) Why does a bigger language model help a visual task? Expected: the benchmark asks for reasoning over what the encoder saw, and the reasoning happens in the language model; the visual side sets what it knows, not how well it thinks.
  • (level 2) When would a connector change still be the right move? Expected: when the token budget binds, because then the connector decides how many tokens you can afford, which is the axis that matters most.
  • (level 3) Which benchmarks move with the encoder and which do not? Expected: vision-centric benchmarks, counting and grounding, move with a self-supervised encoder, by about 5 to 7 points in one study; the reasoning benchmark also moves, by 3 or more points for a stronger contrastive encoder, so the encoder matters for both kinds.
  • (level 3) Design the smallest ablation that settles this for your model. Expected: hold the data, the encoder, the token count, the resolution schedule and the training schedule fixed, swap the language model size in one run and the connector in another, and compare both with the baseline on the same eval.

Defend a designDesign a vision-language model for an on-device mobile assistant that reads the phone screen and taps, types and scrolls. Keep the language model at about 2B parameters. Choose the encoder, the bridge, the resolution plan and the data mix, justify each choice with the ablation evidence, and name the capability you would guard against over-promising.

Level 4 of 4 · about 20 minutes to answer well.

Short answer. Encoder: the stronger contrastive encoder at native resolution, with a self-supervised encoder's features concatenated for a dense spatial signal, because the encoder explains about 20 percent of the variance and self-supervised features lead vision-centric tests. Bridge: a two-layer MLP, since the connector explains about 5 percent, with features from several encoder depths stacked so that fine position reaches the language model. Resolution: a ramp from low to high, with dynamic resolution up to about 1280 pixels on the long side, because screens are text-dense and reading gains most from pixels. Data: dense human descriptions of screens plus grounded action traces, not distilled captions; and guard the promise on spatial relations, where general models score 50 to 60 percent and the agent must hit the right element every time.

Constraints first.

A 2B language model sets a low reasoning ceiling: a larger language model adds points on reasoning benchmarks, and this design cannot grow it. So every other axis must carry more, and the task must be framed as perception plus short actions, not long reasoning.

Encoder.

Choice Why
The strong contrastive encoder at native resolution adds 3 or more points over the common one in the ablations; native resolution keeps screen text legible
Concatenated self-supervised features lead vision-centric benchmarks by 5 to 7 points over the contrastive one; UI grounding is vision-centric
Features from several encoder depths deep layers carry semantics and shallow layers carry fine position; stacking both tightens grounding, which an agent that taps needs

Bridge.

A two-layer MLP. The connector explains about 5 percent of the variance at a fixed token count, and the MLP is the simplest to retrain when the encoder or the language model changes. The token count is the knob that matters: screens are documents, so budget toward the upper end of the 576 to 1024 sweet spot, and above it for dense screens.

Resolution schedule.

Start low and ramp. Flat low-resolution training plateaus; a ramp trains faster and ends higher. Dynamic resolution with a minimum of 256 and a maximum near 1280 pixels on the long side handles the range of screen densities, and the document-reading gains of 3 to 5 points from splitting apply to screens.

Data mix.

  • Dense human descriptions of screens: what is on the screen, where, and what is interactive. Dense human captions beat distillation across the board in the reference comparison.
  • Grounded action traces: screenshot, instruction, the element and the action, with coordinates. The visual-agent benchmark that frontier models lead has this shape.
  • Task-specific instruction data for the app families you ship to.
  • Synthetic data only where a human description anchors it, filtered for grounding.

The capability to guard.

Spatial relations. General models score 50 to 60 percent on above, below, left, right and counting, and an agent that taps the wrong element fails the task. Build the eval from real screens with the exact element-selection questions, measure it before any promise, and keep a verification step in the agent loop: read the screen back after the action and check the state.

Serving on the device.

A 2B language model and a strong encoder at a high resolution still need the visual token budget counted per screen; measure the latency per step at your resolution before you set the schedule.

Plausible wrong answers.

  • "Use a query-based bridge to save tokens on the device." It caps the tokens at a count too low for dense screen text, and the ablations put 64 tokens as too few for reading; spend tokens here and save elsewhere.
  • "Generate the screen descriptions with a strong proprietary model." Distilled descriptions inherit hallucinations, and an agent that taps a hallucinated element fails; dense human descriptions won the reference comparison.
  • "A 2B model with a great encoder matches a 70B agent." The language model sets the reasoning ceiling; frame the task as perception plus short actions and verify each step, instead of promising long reasoning.

Follow-ups an interviewer may ask.

  • (level 3) Why stack shallow and deep encoder layers for an agent and not for a captioner? Expected: a captioner needs semantics; an agent needs where exactly, which the shallow layers carry and the last layer blurs.
  • (level 4) The language model is fixed at 2B. Which axis do you lean on hardest, and what is its limit? Expected: resolution and token count, because screens are text-dense; the limit is the latency per step on the device, which the token count sets.
  • (level 4) How do you make the agent robust to being wrong about an element? Expected: a read-back after each action that compares the new screen with the expected state, and a stop when they do not match; the model's own confidence is not a safe signal.
  • (level 4) What does the ablation evidence not tell you about this design? Expected: it comes from general benchmarks on datacenter GPUs; the device latency, the UI domain and the action format need your own ablation, one axis per run.

Weigh a trade-offA warehouse team wants a general vision-language model to answer "which shelf is the item on" and "is the box on top of or under the pallet" from camera frames. They plan to ship as soon as a demo works on ten images. What do you tell them?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. Spatial relations are the weak spot of today's general-purpose vision-language models: on benchmarks of above and below, left and right, counting and distance they score about 50 to 60 percent, below human level. A demo on ten images proves nothing about that distribution. Build a labelled eval of a few hundred frames with the exact questions first, measure the model, and compare it with a specialised detection or depth model whose box geometry you post-process; if the general model stays, fine-tune it on the task and keep a human-review route for low-confidence answers.

Why the general model struggles.

The model sees projected patch tokens and reasons in language. It learned what is in an image from caption pairs that rarely say where exactly. The lesson's figure for spatial reasoning benchmarks is 50 to 60 percent, and its recommended alternatives for pure spatial tasks are a keypoint or pose estimator, a depth model, or a detector with the box geometry post-processed.

What a real eval looks like.

  • A few hundred frames from the warehouse cameras, not stock photos, with the two question types written the way the operators will ask them.
  • Labels from two people, with the agreement measured.
  • A split by lighting and camera position, because the demo images will not cover them.
  • A confusion matrix per question type, not one accuracy number.

The alternatives.

Approach Strength Cost
Detector plus box geometry exact image-plane above, under, left and right from coordinates labels for the object classes; no language interface
Depth model plus detector distance and stacking calibration per camera
General VLM, zero-shot any question in plain language weak on spatial relations; hallucination risk
General VLM, fine-tuned a plain-language interface with the domain learned 5,000 to 50,000 labelled examples and hours of GPU time

If the VLM stays.

Fine-tune with low-rank adapters on the attention and projector layers, which the lesson sizes at rank 16 to 64 on one datacenter GPU for 2 to 10 hours. Then monitor hallucination in production: a cross-modal error rate flags answers where the text confidence is high but the image-text similarity is low, and routes them to review.

What to tell them.

Ship a measured system, not a demo. Ten images is a smoke test. The eval decides between the detector route and the fine-tuned model, and the hallucination monitor stays whichever route wins.

Plausible wrong answers.

  • "The demo worked on ten images, so it works." Ten images cannot cover the cameras, the lighting or the relation types; the benchmark figure for this kind of question is near a coin flip for some relations.
  • "A bigger VLM will fix spatial reasoning." Size lifts language reasoning more than geometry; the lesson's advice for pure spatial tasks is a specialised model.
  • "Fine-tune on the demo images." Tens of examples teach nothing and overfit; the fine-tuning route needs thousands of labelled frames and an eval that is separate from them.

Follow-ups an interviewer may ask.

  • (level 2) Why does a model that captions well fail at which object is on top? Expected: captions describe content, not geometry; the training pairs rarely contain precise relations, and fine position fades as the language model reasons over projected tokens.
  • (level 2) What does the detector route lose? Expected: the plain-language interface and the open vocabulary; it answers only the relations you compute from boxes, for the classes you labelled.
  • (level 3) How many frames does the eval need, and how do you decide? Expected: enough that each question type and each camera condition has tens of examples; a few hundred in total is the floor, and you grow it where the confusion matrix is unstable.
  • (level 3) How does a stronger encoder change the picture? Expected: self-supervised encoders carry more dense spatial features and lead vision-centric benchmarks; swapping the encoder and retraining the projector is the lesson's hard exercise for these tasks.

Defend a designYour deployed vision-language model answers questions about product photos. Support tickets say that it invents objects and misreads numbers, but the offline benchmark score is fine. Design the production monitoring and the response plan.

Level 3 of 4 · about 15 minutes to answer well.

Short answer. Treat hallucination as a production metric, not as a model property. Score every answer with a cross-modal error rate: embed the image and the generated text with an independent contrastive checker, and flag outputs where the text confidence is high but the image-text similarity is low. Track that rate per endpoint, per prompt type and per customer, alert on a rise, and route the flagged answers to human review instead of to the user. The team that introduced the metric cut its hallucination rate by about 35 percent this way, without a model change.

Why the benchmark does not see it.

About 12 percent of the image and text pairs in crawled training data describe things that are not fully in the image. A model trained on them learns to say plausible things the image does not support, and benchmarks built from the same kind of data reward plausibility. In production the inputs are your photos, your questions and your numbers, and this failure is the dominant one.

The metric.

def cross_modal_error_rate(image_emb, text_emb, text_confidence, sim_threshold=0.25, conf_threshold=0.8):
    image_emb = F.normalize(image_emb, dim=-1)
    text_emb = F.normalize(text_emb, dim=-1)
    sim = (image_emb * text_emb).sum(dim=-1)
    high_conf_low_sim = (text_confidence > conf_threshold) & (sim < sim_threshold)
    return high_conf_low_sim.float().mean().item()

The text confidence is the mean per-token probability of the answer. The checker is a contrastive image-text model that is independent of the generator. The two thresholds come from your own data: calibrate them on a labelled sample of grounded and hallucinated answers.

The dashboard.

  • The rate per endpoint, per prompt type and per customer, over time.
  • The rate split by image source and resolution, because a new camera or a new upload path shifts it.
  • A sample of flagged answers for a weekly read, with the label a reviewer gave.
  • An alert on a rise above a baseline window.

The response plan.

  1. Route. A flagged answer goes to a review queue, or returns a hedged response that shows the image region, not a confident wrong number. An answer whose numbers fail the text-recognition check also goes to the review queue, even when the whole-image rate does not flag it.
  2. Read. The weekly sample tells you which prompt types fail: numbers, counts, small text.
  3. Fix at the data level. Add grounded examples for the failing prompt types, and tiling or a higher resolution for small text and numbers.
  4. Re-measure with the same metric before and after each change.

Limits of the metric.

A contrastive checker scores whole-image similarity, so it misses a wrong digit in an otherwise matching description. Pair it with task checks: parse the numbers in the answer and compare them with a text-recognition pass, or ask the model for the region it read and check that the region is not empty.

Plausible wrong answers.

  • "Raise the benchmark score and the hallucinations will go away." The benchmark rewards plausible text; the production failure is confident text the image does not support, which the benchmark does not measure.
  • "Add a system prompt that says do not hallucinate." The model does not know when it hallucinates; a prompt does not create grounding, and only a measurement and a review route reduce the harm.
  • "Block every answer with a low image-text similarity." Low similarity with low confidence is often a right answer about a hard image; the signal is high confidence with low similarity.

Follow-ups an interviewer may ask.

  • (level 3) Why an independent checker and not the model's own confidence? Expected: the model is confident when it hallucinates, which is the failure; the checker gives a second opinion that does not share the generator's blind spots.
  • (level 3) How do you set the two thresholds? Expected: label a few hundred answers as grounded or not, sweep the thresholds, and pick the pair that catches most hallucinations at a review load the team can afford.
  • (level 4) The rate rises for one customer only. What do you check? Expected: their image source: resolution, lighting, a new product line with text the model misreads; the per-customer split exists for that reason.
  • (level 4) How do you decide between a model change and a routing change? Expected: routing is cheap and immediate and protects users today; a model change needs grounded data and a re-measurement; do both in that order and let the metric arbitrate.

Explain the mechanismDraw the standard architecture of a vision-language model that answers questions about an image. Name its three parts, say what each one contributes, and say which part you would expect to train when a team fine-tunes on a few thousand labelled images.

Level 1 of 4 · about 8 minutes to answer well.

Short answer. A vision encoder, a projector and a language model. The encoder, a pretrained vision transformer, turns the image into patch tokens. The projector, a small two- to four-layer MLP or a query-based bridge, maps those tokens into the language model's embedding space, where they replace a placeholder token in the prompt. The decoder language model reads image tokens and text tokens as one sequence and writes the answer; in most fine-tunes the encoder and the language model stay frozen or get adapters, and the projector is where the training happens.

The three parts.

  1. Vision encoder. A pretrained vision transformer, contrastively trained or self-supervised, produces one token per patch. With a 336-pixel input and a 14-pixel patch, the reference model gets 576 tokens of width 1024.
  2. Projector. A two-layer MLP with a GELU between the layers, from the encoder width to the language model width, 1024 to 4096 to 4096 in the reference model. The capstone's toy head, 768 to 1024 to 512, has about 1.3M parameters.
  3. Language model. A decoder-only model that receives the projected image tokens in place of an image placeholder and the text tokens after them, then generates text.

How the pieces meet.

The prompt holds a placeholder image token. Before the forward pass, the embeddings at those positions are overwritten with the projected vision tokens, and the batch is padded so that every sample has the same count. The language model sees one sequence; nothing else about it changes.

Who trains.

  • Stage one, alignment: freeze the encoder and the language model, and train the projector on image and caption pairs with the language-modeling loss on the caption. The capstone's version uses a cosine alignment loss between a pooled image vector and a caption vector, and that loss falls from about 1.07 to about 0.80 in 200 steps with only the projector moving.
  • Stage two, instruction tuning: unfreeze the language model, often through adapters, keep the projector trainable, and train on image, question and answer triples.
  • Large pretraining on interleaved image and text data sits between them in frontier recipes and is out of reach for a small team.

Why the projector is enough.

The encoder already represents the image, and the language model already reasons in words. The projector's job is to express one in the vocabulary of the other, which a small bend of the space can do. The capstone's encoder has 86M parameters and its projector about 1.3M; training only the projector means a few hundred steps on one GPU.

Plausible wrong answers.

  • "The language model looks at pixels through cross-attention into the image." In this pattern the image enters as tokens in the input sequence; cross-attention bridges are a different family.
  • "Fine-tune the vision encoder first; it is the part that sees." The encoder is pretrained and frozen in stage one; the projector is where a small team's training budget goes.
  • "The projector must be a large network to carry the image." It is a two-layer MLP far smaller than the encoder in the capstone, and it trains in minutes.

Follow-ups an interviewer may ask.

  • (level 1) Why does the projector need two layers and not one? Expected: one linear layer rotates and scales; the non-linearity between two layers lets the map bend, which is enough to align contrastive vision features to a language model's embeddings.
  • (level 2) What does the language model see where the image was? Expected: a run of embeddings, one per projected patch token, in place of the placeholder; the model treats them as tokens with no special handling.
  • (level 2) What does a bridge with a fixed set of learned queries change? Expected: it compresses the patch tokens to a fixed count, which saves context at the cost of a bottleneck; the MLP keeps every patch.
  • (level 3) Which part sets the ceiling on reasoning quality? Expected: the language model; the encoder can only feed it, so a larger language model lifts the benchmarks more than a cleverer bridge.
