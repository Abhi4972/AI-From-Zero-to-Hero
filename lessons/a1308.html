In plain words first
The idea in one line

A modern MCP client repeats its contract on every request. Its hardest compatibility decision is knowing when an old server is truly old and when a modern server is reporting a correctable error.

Terms you'll hear
Term Meaning
Peer Client-side record for one server transport and its discovered data
Protocol era Modern per-request metadata or legacy initialization semantics
Discovery probe Initial server/discover used to identify the stdio era
Recognized modern error Error that proves modern behavior and forbids legacy fallback
Legacy allowlist Operator configuration permitting one bounded compatibility probe for a pinned peer
Positive legacy evidence Valid, correlated initialize result for an explicitly supported legacy revision
Merged namespace Canonical tool names across all active peers
Collision policy Prefix or reject rule for duplicate tool names
Era cache Selected modern or legacy behavior stored for one transport peer
Transport recovery Restart or reconnect, rediscover, relist, and retry safely with a new id

The problem

In plain words first

An AI application usually connects to several MCP servers at once: notes, a CRM, a file system. The client side has three jobs. First, find out what each server speaks: modern MCP (2026-07-28, no handshake) or the older 2025 protocol with its initialize handshake. Second, merge all the servers' tools into one list for the model, even when two servers both offer a tool called search. Third, send each call to the server that owns the tool. This lesson covers each job and the safety questions inside them, such as when an error really means "old server" and when it does not. It then runs a host that merges two real SDK servers with a name collision and routes calls between them, and watches the official client choose an era for a modern, a legacy and a too-new server. No model is trained.

An agent host usually talks to more than one MCP server. It must discover each server, merge tool catalogs, resolve duplicate names, route calls, and recover from transport failure.

The 2026-07-28 revision makes the steady state simpler because each request is self-contained. Compatibility makes startup more subtle. A client may encounter:

  • a modern server that supports the preferred version;
  • a modern server that returns a recognized version or header error;
  • a legacy server that has never heard of server/discover;
  • a legacy server that stays silent until it receives initialize.

Treating every probe error as legacy is dangerous. A malformed modern request, an overloaded server, a dead process, and an old server can all produce the same timeout or connection close. Those signals are ambiguous. The client must combine explicit operator intent with positive protocol evidence before it chooses the legacy era.

Idea 1 · A peer, not a protocol session

Keep one transport peer record for each server process or endpoint:

  • transport handle or send function;
  • selected protocol era and version;
  • last discovered server capabilities;
  • last deterministic tool list;
  • pending request ids for correlation;
  • transport health.

This is client bookkeeping. It is not protocol session state. On modern MCP, the server still receives current version and capabilities on every request.

Idea 2 · Build every modern request from scratch

def modern_request(request_id, method, params, version, capabilities):
    return {
        "jsonrpc": "2.0",
        "id": request_id,
        "method": method,
        "params": {
            **params,
            "_meta": {
                "io.modelcontextprotocol/protocolVersion": version,
                "io.modelcontextprotocol/clientCapabilities": capabilities,
                "io.modelcontextprotocol/clientInfo": CLIENT_INFO,
            },
        },
    }

Do not attach metadata once to a connection object and assume it reached the wire. Stamp and inspect the final serialized request.

Idea 3 · Modern discovery

server/discover returns supported versions, server capabilities, instructions, cache hints, and recommended server identity. A client chooses the highest mutually supported modern version.

Discovery is optional for a modern-only client, but it is recommended on stdio. Some legacy servers accept an operation before initialization, so sending tools/list first can produce an ambiguous success. server/discover creates a clean era boundary.

Idea 4 · The stdio compatibility probe

A dual-era stdio client sends server/discover with its preferred modern metadata before any other request. There are three outcome classes:

  1. DiscoverResult. The server is modern. Select a mutually supported version and continue with per-request metadata.
  2. Recognized modern error. The server is modern. For -32022, choose from data.supported and retry with a new request id. For header or capability errors, correct the request. Do not send initialize.
  3. Ambiguous signal. An unrecognized JSON-RPC error, timeout, connection close, or empty response does not identify an era. Fail closed unless that exact peer is configured for legacy compatibility.

Recognized modern protocol errors include:

  • -32020 HeaderMismatch
  • -32021 MissingRequiredClientCapability
  • -32022 UnsupportedProtocolVersion

Recognized modern errors remain modern even when the peer is on the legacy allowlist. Once a server proves that it understands the modern error vocabulary, sending initialize would be a downgrade.

Do not treat -32601 as positive legacy evidence. It only makes an explicitly allowlisted peer eligible for one legacy probe. The same rule applies to a timeout, connection close, or empty response. The official Python SDK 2.x makes a more permissive choice in mode="auto": any JSON-RPC error from the probe, except a version mismatch with no common modern version, falls back to initialize (the second run below shows it). The stricter allowlist in this lesson is a policy for hosts that cannot afford a silent downgrade.

Worked example
Three servers, three verdicts
  • Modern server: server/discover answers with supportedVersions: ["2026-07-28"]. Vc​∩Vs​={2026-07-28}, so $v^* = $ 2026-07-28 and every later request carries it.
  • Legacy server: server/discover gets -32601 (method not found). That is ambiguous: a modern server with a bug could say the same. Only an allowlisted peer gets one initialize probe; a valid result naming 2025-11-25 selects the legacy era.
  • Future server: -32022 with supported: ["2027-01-01"]. Vc​∩Vs​=∅: fail. The error proves the server is modern, so falling back to initialize would be a downgrade.
  • Collision: notes and crm both offer search. Sorted, crm comes first and keeps search; the notes tool becomes notes__search, still routed to notes as search.
Check your mental model
  • ✗ "Any error from server/discover means the server is old."
    ✓ Timeouts, crashes and unknown errors are ambiguous; recognised modern errors prove the server is modern.
  • ✗ "The client must keep a session per server."
    ✓ It keeps bookkeeping (era, tool list, transport); the protocol itself has no session.
  • ✗ "When two servers have the same tool name, the later one can replace the earlier."
    ✓ Silent overwrite hides where a model's action goes; prefix or reject.
  • ✗ "Any prefix will do."
    ✓ The merged names go to a model API, which allows only letters, digits, _ and -.

A host that merges two servers and routes calls

Two MCPServer instances (notes with search and add_note, crm with its own search) are connected in-process with the SDK's Client. The host merges their sorted tool lists with prefix-on-collision, checks every canonical name against the model APIs' character rule, and routes two calls. About a second.

import asyncio, json, re
from contextlib import AsyncExitStack
from mcp import Client
from mcp.server import MCPServer

# Two independent servers. Both expose a tool called `search`.
notes, crm = MCPServer("notes"), MCPServer("crm")
@notes.tool()
def search(query: str) -> list[str]:
    """Use to find notes containing a word."""
    return [n for n in ("Call Priya", "Buy paper") if query.lower() in n.lower()]
@notes.tool()
def add_note(text: str) -> str:
    """Use to save a new note."""
    return "saved"
@crm.tool()
def search(query: str) -> list[str]:
    """Use to find customers by name."""
    return [c for c in ("Priya Sharma (CUST-0042)", "Lee Wong (CUST-0101)") if query.lower() in c.lower()]

async def main():
    async with AsyncExitStack() as stack:
        peers = {name: await stack.enter_async_context(Client(srv)) for name, srv in (("notes", notes), ("crm", crm))}
        registry = {}                                   # canonical name -> (peer, local name)
        for peer in sorted(peers):                      # sorted: the merge never depends on startup order
            listed = await peers[peer].list_tools()
            for tool in sorted(listed.tools, key=lambda t: t.name):
                # "peer__tool": model APIs accept only [a-zA-Z0-9_-] in tool names, so no "/" or "."
                canonical = tool.name if tool.name not in registry else f"{peer}__{tool.name}"
                if canonical != tool.name:
                    print(f"collision: '{tool.name}' from {peer} exposed as '{canonical}'")
                registry[canonical] = (peer, tool.name)
        print("\nwhat the model sees -> where the call goes")
        for canonical, (peer, local) in registry.items():
            ok = bool(re.fullmatch(r"[a-zA-Z0-9_-]{1,64}", canonical))
            print(f"  {canonical:<14} -> {peer}: tools/call name={local!r}   valid model-API name: {ok}")

        async def route(canonical, args):               # routing is a pure lookup
            peer, local = registry[canonical]
            r = await peers[peer].call_tool(local, args)
            return r.structured_content["result"]
        print("\nmodel calls 'search' with priya      ->", await route("search", {"query": "priya"}))
        print("model calls 'notes__search' with priya ->", await route("notes__search", {"query": "priya"}))

asyncio.run(main())

Reading this output

The collision was detected and resolved by policy. Both servers declare search. Peers are merged in sorted order, so crm comes first and keeps the plain name; the notes server's tool is exposed as notes__search. Sorting makes the outcome the same on every start, whatever order the connections happen to finish in.

The model sees canonical names; servers see their own. The routing table maps notes__search back to the notes server under its declared name search. All three canonical names pass the model APIs' rule (letters, digits, _, -); a notes/search prefix would not.

Routing is a lookup. "search priya" went to the CRM and found the customer; "notes__search priya" went to the notes server and found the note. One caveat: a model that wanted notes but called the plain search now gets customers. If that is a risk, prefix both colliding tools or reject the collision at startup.

Era negotiation against three real processes

Three stdio servers are written to files: a modern SDK server, a 2025-era server that only knows initialize, and a "future" server that speaks only 2027-01-01. The official SDK client connects to each in mode="auto" and reports the era and version it chose, or why it refused. About 3 seconds.

# How the official SDK client chooses an era on stdio, against three servers.
import asyncio, pathlib, sys, tempfile, textwrap
from mcp import Client, StdioServerParameters
from mcp.client.stdio import stdio_client
from mcp.shared.exceptions import MCPError

d = pathlib.Path(tempfile.mkdtemp())
(d / "modern.py").write_text(textwrap.dedent('''
    from mcp.server import MCPServer
    mcp = MCPServer("modern-server")
    @mcp.tool()
    def ping_me() -> str:
        """Answer with pong."""
        return "pong"
    mcp.run()'''))
# A 2025-era server: it knows `initialize` but answers server/discover with "method not found".
(d / "legacy.py").write_text(textwrap.dedent('''
    import json, sys
    for line in sys.stdin:
        m = json.loads(line); mid = m.get("id")
        if mid is None: continue                       # notifications get no reply
        if m["method"] == "initialize":
            r = {"protocolVersion": "2025-11-25", "capabilities": {"tools": {}},
                 "serverInfo": {"name": "legacy-server", "version": "0.9"}}
        elif m["method"] == "tools/list":
            r = {"tools": [{"name": "old_tool", "inputSchema": {"type": "object"}}]}
        else:
            print(json.dumps({"jsonrpc": "2.0", "id": mid,
                              "error": {"code": -32601, "message": "Method not found"}}), flush=True); continue
        print(json.dumps({"jsonrpc": "2.0", "id": mid, "result": r}), flush=True)'''))
# A server from the future: modern, but only speaks a version this client does not know.
(d / "future.py").write_text(textwrap.dedent('''
    import json, sys
    for line in sys.stdin:
        m = json.loads(line)
        if m.get("id") is None: continue
        print(json.dumps({"jsonrpc": "2.0", "id": m["id"], "error": {"code": -32022,
              "message": "Unsupported protocol version",
              "data": {"requested": "2026-07-28", "supported": ["2027-01-01"]}}}), flush=True)'''))

def first_mcp_error(exc):
    if isinstance(exc, MCPError):
        return exc
    for inner in getattr(exc, "exceptions", ()):
        if (found := first_mcp_error(inner)):
            return found

async def connect(name):
    params = StdioServerParameters(command=sys.executable, args=[str(d / f"{name}.py")])
    try:
        async with Client(stdio_client(params, errlog=sys.__stderr__), mode="auto") as c:
            tools = await c.list_tools()
            era = "modern" if c.protocol_version >= "2026" else "legacy"
            print(f"{name:<7} -> {era} era, protocol {c.protocol_version}, tools {[t.name for t in tools.tools]}")
    except Exception as exc:                       # anyio wraps the error in (nested) exception groups
        e = first_mcp_error(exc)
        print(f"{name:<7} -> refused to connect: {e.error.code} {e.error.message} "
              f"(server supports {e.error.data['supported']})")

for name in ("modern", "legacy", "future"):
    asyncio.run(connect(name))

Idea 5 · Allowlisting is operator intent, not evidence

Legacy compatibility must be an explicit property of one pinned peer configuration:

client.add_server("archive", archive_transport, allow_legacy=True)

Bind that choice to the configured command or endpoint. Do not use a wildcard that lets an arbitrary server opt itself into weaker semantics. A peer without allow_legacy=True fails after an ambiguous discovery outcome and never receives initialize.

The allowlist grants permission to probe. It does not select the era. The client sends one initialize under a transport-enforced deadline, then requires all of the following:

  • a JSON-RPC 2.0 response with the matching request id;
  • exactly one result and no error;
  • a protocolVersion in the client's configured legacy revision set;
  • an object-valued capabilities field;
  • a serverInfo object with non-empty string name and version fields.

A timeout, connection close, error response, malformed result, mismatched id, or unsupported revision fails closed. Only a structurally valid positive result selects the legacy era. The code passes legacy_probe_timeout_ms to the transport adapter; a real stdio or HTTP adapter must enforce that deadline rather than merely record it.

Cache the selected era for the transport peer. Do not probe again before every call.

Idea 6 · Legacy is a compatibility branch

Once the bounded probe returns valid positive legacy evidence, the client uses the selected legacy version exactly as defined by that revision:

  1. Verify the response envelope and correlation id.
  2. Verify the negotiated revision is in the configured legacy set.
  3. Record validated capabilities and server identity.
  4. Send notifications/initialized only after all checks pass.
  5. Use legacy request shapes for that transport lifetime.

This branch exists for interoperability with known peers. It is not the default design for new servers or new requests. If the transport restarts or its endpoint changes, discard the peer-era cache and negotiate again.

Idea 7 · Discovering and caching tools

For each active peer, call tools/list. A modern result includes resultType, ttlMs, and cacheScope. Honor the freshness hint within the correct authorization context. Re-fetch after expiry or a subscribed list-change event.

Clients must treat a missing resultType from a legacy server as "complete". Do not require modern cache fields on a response from an earlier negotiated era.

The server should return deterministic ordering. The client should also sort before merging so local registry order does not depend on process startup timing.

Idea 8 · Collision-safe namespace merge

Two servers may both expose search. Choose a declared policy:

  1. Prefix on collision. Keep the first canonical name and expose later collisions as <server>__<tool>. Model APIs accept only letters, digits, _ and - in tool names (OpenAI's limit is 64 characters), so separators such as / or . would be rejected when the merged list is sent to the model.
  2. Reject on collision. Do not load the duplicate and surface a clear configuration error.
  3. Silent overwrite. Never use this. It hides which server receives a model-selected action.

Store both canonical and local names. The model sees the canonical name. The outgoing tools/call uses the local name the owning server declared.

Idea 9 · Routing a call

Routing is a pure lookup:

canonical tool name
  -> peer name + local tool name
  -> new JSON-RPC request id
  -> modern request metadata or explicit legacy shape
  -> matching response id

Do not send a call when its owning transport is unavailable. Reconnect or restart the transport, then re-run discovery and tools/list. Modern in-flight requests lost on a broken transport can be retried with a new JSON-RPC id when the operation's safety policy permits it.

Idea 10 · Notifications and subscriptions

Modern list and resource changes arrive only on a client-opened subscriptions/listen stream. The client sends the notification filter, waits for notifications/subscriptions/acknowledged, and correlates events with the listen request id in notification metadata.

On disconnect, open a new listen request and refetch relevant lists or resources. Modern streams do not resume with Last-Event-ID.

Idea 11 · No server-initiated requests

Modern servers do not call the client with independent JSON-RPC requests for sampling, elicitation, or roots. They return input_required, and the client retries the original request after fulfilling the embedded input requests.

Do not block the peer's response reader while fulfilling input. Preserve correlation and create a new JSON-RPC id for the retry.

The tests prove boundaries that normal demos miss:

  • modern requests repeat metadata;
  • -32022 retries modern discovery without initialization;
  • recognized modern errors never downgrade, even for an allowlisted peer;
  • timeouts, connection closes, empty responses, and unrecognized errors do not trigger initialize without an allowlist;
  • an allowlisted peer becomes legacy only after a valid, supported initialize result;
  • malformed and unsupported legacy results leave the peer unavailable;
  • a successfully selected era is cached for the transport lifetime.
Break it on purpose

A host merges tools with "last one wins": when a second server also offers delete_file, it simply replaces the first in the registry. A user adds a new, untrusted MCP server that happens to define delete_file. What can go wrong, and what should the host do instead? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Official SDK clients (Python Client, TypeScript, Go and others) probe server/discover and fall back to initialize for 2025-era servers; the Python SDK's mode setting (auto, legacy, modern) makes the policy explicit.
  • Hosts with many servers: Claude, ChatGPT, VS Code, Cursor and agent frameworks (LangChain's MCP adapters, the OpenAI Agents SDK, Pydantic AI) merge tools from several servers, usually prefixing names with the server's name.
  • Large tool catalogs push hosts to load tools on demand (tool search) instead of sending every merged tool to the model.
  • Gateways (Lesson 13.17) move merging and routing out of each host into shared infrastructure.

Sources: MCP 2026-07-28 specification, MCP server discovery, MCP versioning, MCP Python SDK.

Recap
What to keep from this lesson
  • Stamp version and capabilities on every modern request, at the point of sending.
  • Probe with server/discover; recognised modern errors are never a reason to downgrade.
  • Fall back to initialize only by explicit policy, and only after a valid legacy result.
  • Merge tool lists deterministically; prefix or reject collisions, never overwrite.
  • Route by lookup to the owning server, under the name that server declared.

Given a list of MCP server transports, produce a client harness that prefers MCP `2026-07-28` and isolates legacy compatibility.

Produce:

1. Peer configuration. Map a stable server name to a pinned command or endpoint, arguments, environment allowlist, authorization context, transport kind, and an explicit `allow_legacy` flag that defaults to false.
2. Modern request builder. Stamp protocol version, current client capabilities, and recommended client identity into every `params._meta` immediately before serialization.
3. stdio era probe. Send `server/discover` first. Accept a valid DiscoverResult, retry `-32022` at a mutually supported modern version, and treat `-32020` plus `-32021` as correctable modern errors.
4. Legacy compatibility probe. Treat an unrecognized error, timeout, connection close, or empty response as ambiguous. Send one deadline-bound `initialize` only when that exact peer has `allow_legacy: true`. Select legacy only after a correlated JSON-RPC success containing a configured legacy revision, object capabilities, and non-empty server identity. Otherwise fail closed.
5. Tool cache. Honor `ttlMs` and `cacheScope` in the negotiated authorization context. Treat absent legacy `resultType` as `"complete"`.
6. Namespace merge. Sort peers and tools. Prefix or reject collisions. Forbid silent overwrite.
7. Router. Map canonical tool names to peer plus local name, create a new request id, send the era-correct request, and verify the response id.
8. Recovery. On transport loss, fail in-flight work, restart or reconnect, repeat discovery and lists, re-open subscriptions, and retry only operations allowed by the safety policy.

Hard rejects:

- Sending modern requests without current `_meta`.
- Falling back to initialization after a recognized modern error.
- Sending `initialize` to a peer that is not explicitly allowlisted for legacy compatibility.
- Treating a timeout, connection close, empty response, unrecognized error, malformed result, or unsupported revision as proof of legacy behavior.
- Treating a process, connection, or `Mcp-Session-Id` as modern protocol state.
- Sharing a private cached list across authorization contexts.
- Silently overwriting a duplicate tool name.
- Accepting a modern success without `resultType`.

Refusal rules:

- Refuse to spawn a command outside a pinned allowlist.
- Refuse to route a tool when the owner is ambiguous.
- Refuse to retry a non-idempotent call automatically without an application idempotency key or user decision.

Output a complete Python harness, at least six conformance tests, and a startup report listing peer, selected era, selected version, cache scope, and canonical tool names.

Solutions

SolutionP1 · crm keeps search; the SDK falls back to legacy

crm keeps the plain search, because peers are merged in sorted order and "crm" sorts before "notes". The notes tool becomes notes__search; when the model calls it, the router sends search to the notes server and the note "Call Priya" comes back.

The official client treats "method not found" on server/discover as an old server: it falls back to the initialize handshake and connects in the legacy era (2025-11-25). The lesson's design would do that only for an allowlisted peer.

SolutionB1 · A hijacked action

The untrusted server takes over a dangerous action. The model keeps calling delete_file as before, but the host now routes the call to the new server, which can do anything with the path it receives: log it, delete something else, or report success without doing anything. Nothing in the model's view changed, so neither the model nor the user notices. The same trick works for any popular tool name, which makes "last one wins" an attack surface (shadowing; Lesson 13.15).

What the host should do:

  • Never overwrite: keep the first owner, and prefix or reject the newcomer, with a visible warning naming both servers.
  • Pin trust: let only trusted, configured servers own sensitive names; tools from new servers get a server prefix and start untrusted.
  • Show provenance: confirmation prompts for destructive actions should name the server that will run them.

Defend a designYour agent host launches several MCP servers over stdio. One is current. One is an old archive server that understands only initialize. One is current but slow to start. A teammate proposes a simple rule: send server/discover, and on any error or timeout send initialize. Design the startup so that the slow server is never downgraded and the archive server still works.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Treat an ambiguous signal as ambiguous. A timeout, a connection close, an empty response or an unrecognized error does not identify an era, so the client fails closed unless that exact peer is configured with allow_legacy=True. A recognized modern error such as -32022 proves the server is current and forbids initialize. For the archive peer on the allowlist, send one initialize under a transport-enforced deadline and select the legacy era only after a structurally valid positive result.

Three outcome classes for the probe.

Outcome of server/discover Meaning Next step
a DiscoverResult current server pick the highest mutually supported version and continue with per-request metadata
a recognized modern error current server correct the request or retry an advertised version; never send initialize
an ambiguous signal unknown fail closed, unless this pinned peer allows one bounded legacy probe

Recognized modern errors are -32020 HeaderMismatch, -32021 MissingRequiredClientCapability and -32022 UnsupportedProtocolVersion. They remain modern even when the peer is on the legacy allowlist, because a server that speaks the modern error vocabulary would be downgraded by initialize.

-32601 is not positive legacy evidence. It only makes an explicitly allowlisted peer eligible for one probe, and so does a timeout, a connection close or an empty response.

The allowlist is intent, not evidence.

client.add_server("archive", archive_transport, allow_legacy=True)

Bind the choice to the configured command or endpoint. A wildcard would let an arbitrary server opt itself into weaker semantics. A peer without the flag fails after an ambiguous outcome and never receives initialize.

Positive legacy evidence.

The one initialize runs under legacy_probe_timeout_ms, which a real adapter must enforce. The client then requires all of:

  • a JSON-RPC 2.0 response with the matching request id;
  • exactly one result and no error;
  • a protocolVersion in the client's configured legacy revision set;
  • an object-valued capabilities;
  • a serverInfo object with non-empty string name and version.

Anything else leaves the peer unknown and unavailable. Only after all checks pass does the client send notifications/initialized and use legacy request shapes for that transport lifetime.

After the era is chosen.

Cache the era per transport peer and do not probe before every call. When the transport restarts or the endpoint changes, discard the cache and negotiate again. Then call tools/list, sort the result before merging, and apply a declared collision policy: prefix later duplicates as <server>/<tool> or reject the duplicate with both peer names in the error. Never overwrite silently.

Why the slow server survives.

Its first probe times out, which is an ambiguous signal. It is not allowlisted, so the client marks it unavailable instead of sending initialize. A later retry of server/discover succeeds and the peer joins as a current server with the correct era.

Plausible wrong answers.

  • "Any error from discovery means the server is old." A malformed request, an overloaded server, a dead process and an old server can all produce the same timeout or close.
  • "Send initialize first; a current server will reject it." Sending initialize to a current server is a downgrade and must never be the default path.
  • "A method-not-found error proves the server is legacy." It only makes an allowlisted peer eligible for one bounded probe; the positive evidence is a valid initialize result.

Follow-ups an interviewer may ask.

  • (level 3) The allowlisted archive peer answers -32022 to discovery. Which era? Expected: current; a recognized modern error forbids the legacy probe, so choose from data.supported and retry with a new request id.
  • (level 3) The initialize probe times out. What state is the peer in? Expected: unknown and unavailable; no era is selected and notifications/initialized is never sent.
  • (level 4) A legacy server accepts tools/list before initialization. Why does that make discovery-first safer on stdio? Expected: the ambiguous success would hide the era; server/discover creates a clean era boundary before any operation.
  • (level 4) The archive process crashes and restarts. Do you reuse the cached legacy era? Expected: no; discard the peer-era cache, rediscover, relist, reopen subscriptions, and retry only safe operations with new ids.

Where it is taught. The client lesson defines the probe outcomes, the allowlist and the positive evidence checklist.
