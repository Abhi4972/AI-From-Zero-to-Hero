Why this came about

Every message and tool result in a conversation is re-sent to the model on the next call, so long conversations hit context limits and costs grow. Managing short-term memory, deciding what stays, what is condensed and what is dropped, became a core part of building agents.

In plain words first
What is in your head right now

Short-term memory is the working memory of one conversation: the messages so far, tool results, what the agent is in the middle of. It lives in the run's state and is sent to the model every turn, so it must be kept within budget by trimming, summarizing or clearing old tool results. The memory pipeline is the set of steps that decide what is kept, what is condensed and what is passed to the model on each call.

The first row is what you have had since Lesson 14.3: the list of messages. The other three rows are long-term memorylater · 14.11, kept outside the context window and brought in when needed.

This lesson builds short-term memory in code, and Lesson 14.11 builds the long-term kinds. Three design decisions apply to every memory:

  1. When to write: during the conversation (the agent calls a remember tool; immediate but adds latency) or after it (a background job extracts facts, called memory consolidation; better quality, one session late). The figure below shows both.
  2. How to scope: always put the tenant and the user in the key, so one customer can never read another's memory.
  3. How to keep it healthy: timestamps, sources, updates instead of duplicates, expiry, and a way for users to see and delete what is stored. A poisoned memory is a prompt injectionlater · 15.22 that never goes away.

The memory pipeline

Every long-term memory system, managed or not, has the same five stages:

Stage Question Typical implementation
Extract What in this conversation is worth remembering? An LLM call that turns turns into candidate facts, with a type and importance
Consolidate Is it new, an update, or a duplicate? Similarity search against existing memories, then add, update or skip
Store Where, and scoped to whom? A store keyed by tenant and user, with embeddings for search
Retrieve What is relevant to this turn? Similarity plus recency plus importance, filtered by scope
Forget What must expire or be deleted? Time-to-live, user deletion requests, decay

Step 1 · Short-term memory: a token-budgeted buffer with a running summary

Short-term memory is the current conversation. In Lesson 11.1 you saw that the API keeps nothing between calls, so "the conversation" is just a list of messages that your code resends every turn. Left alone, that list grows until it is slow, expensive and finally too long for the context window. There are only three things you can do about it: cut old messages off (cheap, and the agent forgets them completely), summarise them (costs a model call, keeps the gist), or both.

The standard design does both: it keeps the last few turns verbatim and folds older turns into a running summary, so the agent remembers the gist of a long session without paying for every word. Lesson 11.8 called this move compaction; here it becomes a reusable class.

import json, math, re, time
from dataclasses import dataclass, field

def approx_tokens(text: str) -> int:
    return max(1, len(text) // 4)

class ConversationBuffer:
    """Keep recent turns verbatim; fold older turns into a running summary when over budget."""
    def __init__(self, summarize, budget: int = 120, keep_recent: int = 4):
        self.summarize, self.budget, self.keep_recent = summarize, budget, keep_recent
        self.summary, self.turns = "", []

    def add(self, role: str, text: str):
        self.turns.append({"role": role, "content": text})
        while self._tokens() > self.budget and len(self.turns) > self.keep_recent:
            oldest = self.turns.pop(0)
            self.summary = self.summarize(self.summary, oldest)      # one cheap model call per folded turn

    def _tokens(self) -> int:
        return approx_tokens(self.summary) + sum(approx_tokens(t["content"]) for t in self.turns)

    def context(self) -> list[dict]:
        head = [{"role": "system", "content": f"Earlier in this conversation: {self.summary}"}] if self.summary else []
        return head + self.turns

def fake_summarize(summary: str, turn: dict) -> str:
    """Stands in for a summarization prompt; keeps the facts that matter."""
    facts = re.findall(r"A-\d{4}|Hindi|UPI|gold", turn["content"])
    return (summary + " " + " ".join(facts)).strip()

buf = ConversationBuffer(fake_summarize, budget=60)
for role, text in [("user", "Hi, I am a gold member and I prefer Hindi."),
                   ("assistant", "Namaste! How can I help you today?"),
                   ("user", "My order A-1001 arrived with a cracked jar, it is really disappointing."),
                   ("assistant", "I am sorry about that. I can arrange a refund for A-1001."),
                   ("user", "Please send the refund to UPI, not the card."),
                   ("assistant", "Done, the refund will go to your UPI ID within 3 days."),
                   ("user", "Also, where is A-1002?")]:
    buf.add(role, text)
print("summary:", buf.summary)
print("verbatim turns:", len(buf.turns), "| tokens:", buf._tokens())
What you should see
summary: gold Hindi A-1001
verbatim turns: 4 | tokens: 47

The first three turns were folded into the summary; the facts survived. A real summarizer is an LLM call with a prompt such as "update the summary with anything the agent will need later: facts, decisions, open questions"; it costs tokens, so fold several turns at once and run it in the background where you can.

In production
When summaries lose what mattered

Summaries paraphrase, and paraphrase is where order IDs, amounts, dates and promises get lost or changed ("about INR 2,500" for INR 2,499). Keep a small structured state next to the summary for facts that must survive verbatim (customer ID, order IDs, amounts, decisions, promises made), and have the summarizer update that state rather than prose. Test it: ask about a turn-two detail at turn twenty.

Solutions

SolutionP1 · Recent turns verbatim, older ones summarized

The most recent turns that fit in the budget are kept word for word; older turns are folded into the running summary, which is kept at the front. The model sees the summary, then the recent turns, then the new message, so recent detail is exact and older detail is compressed.

SolutionB1 · One turn bigger than the budget

A buffer that only drops whole turns either keeps the oversized turn and exceeds the budget, or drops it immediately and loses it. Better: store the large content outside the conversation (a file or a document store), keep a short reference and summary in the turn, and retrieve the details when needed.

SolutionD1 · Summaries must keep identifiers

The summarizer compressed the facts the conversation depends on. Instruct it to keep identifiers, amounts, dates and commitments verbatim, or extract them into structured state that is never summarized (the modify exercise). Then test with long conversations that refer back to early facts.

SolutionM1 · Facts outside the summary

Keep facts: dict next to summary: str, update facts with a small extraction step after each turn, and render both at the front of the context. Facts are replaced, not summarized, so the order ID from turn 2 is still exact at turn 12. LangGraph's typed state (Lesson 14.60) is the production form of the same idea.

Check your understanding

Explain the mechanismWhat is short-term memory in an agent, and how do you keep it within budget?

Worked answer. It is the context of the current conversation or task: recent messages, tool results and working state, sent with each call. Keep it within budget by keeping recent turns verbatim, summarizing older ones, clearing old tool results, keeping key facts in structured state, and moving durable facts to long-term memory. Never cut between a tool call and its result.

A plausible wrong answer. "The model remembers the conversation." The application resends it every time (Lesson 11.1).

Follow-ups. How do you test that summaries keep what matters?

Debug a failureUsers say the assistant "forgets" things mid-conversation. Where do you look?

Worked answer. At the context of the call where it forgot: whether the fact was still there, summarized away or trimmed, or buried among long tool results. Check the summarization prompt and the trimming boundary, and whether the thread or session ID changed between turns, which would start a new conversation.

A plausible wrong answer. "Use a model with a longer context window." The fact was probably removed by your code, not the window.

Follow-ups. How would you log enough to debug this without storing personal data unnecessarily?

Defend a designSummarize history, or trim it?

Worked answer. Trim when old turns rarely matter, such as short support chats, because it is cheap and exact. Summarize when the conversation builds on earlier decisions, such as long tasks and agents, and keep structured facts outside the summary so identifiers survive. Many systems do both: trim tool output aggressively, summarize dialogue.

A plausible wrong answer. "Always summarize, it keeps everything." Summaries lose detail and cost a model call.
