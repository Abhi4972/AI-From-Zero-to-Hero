Why this came about

AWS teams found that capable models could plan well on their own, and that heavy orchestration code was often unnecessary. Strands Agents (2025) took a model-driven approach: give the model tools and a prompt, and let it decide the steps, with AWS integration for production.

In plain words first
A model, tools and a prompt; the model decides the rest

Strands Agents, from AWS, leans on the model to plan: you give it a model, tools and a prompt, and its loop lets the model choose steps, with less graph-style control flow than LangGraph. It integrates closely with AWS services and deployment on AgentCore. Read it as the same loop with a different philosophy: more trust in the model, less explicit structure.

What it is

Strands Agents is an open-source SDK that AWS released in May 2025 after using it internally for products such as Amazon Q Developer and AWS Glue. Its philosophy is model-driven: give a capable model a prompt and tools and let it plan, instead of scripting the steps. Around that loop it adds production plumbing: hooks, interrupts for human approval, session managers, steering plugins, OpenTelemetrylater · 14.117 tracing, MCPlater · 16.4 and A2Alater · 16.7 support, and four multi-agent patterns. There are Python and TypeScript SDKs.

The default model provider is Amazon Bedrock, but Strands supports Anthropic, OpenAI, Gemini, LiteLLM, Ollama, llama.cpp, Mistral, Writer and others, and it routes between models with a model routerlater · 14.127.

Step 1 · Tools and an approval hook

The ShopKart agent again, in Strands. @tool and Agent(...) will look familiar by now. What is new is the hook: a small class that Strands calls at fixed moments of the loop. This one listens for the moment before a tool runs, pauses the run when the tool is cancel_order, and waits for a person's answer. It is the approval gate of Lesson 14.6 written as a plug-in.

from mockllm import start
from strands import Agent, tool
from strands.models.openai import OpenAIModel
from strands.hooks import BeforeToolCallEvent, HookProvider, HookRegistry

model = OpenAIModel(client_args={"base_url": start(), "api_key": "mock"}, model_id="mock-model")
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

@tool
def cancel_order(order_id: str) -> str:
    """Cancel an order that has not shipped yet."""
    return f"{order_id} cancelled"

class ApproveCancels(HookProvider):
    """A hook that pauses the agent before any cancellation and waits for a human."""
    def register_hooks(self, registry: HookRegistry, **kwargs) -> None:
        registry.add_callback(BeforeToolCallEvent, self.check)

    def check(self, event: BeforeToolCallEvent) -> None:
        if event.tool_use["name"] != "cancel_order":
            return
        answer = event.interrupt("cancel-approval", reason=event.tool_use["input"])   # pauses the run
        if answer != "yes":
            event.cancel_tool = "A supervisor declined the cancellation."          # the model sees this

agent = Agent(model=model, tools=[get_order_status, cancel_order], hooks=[ApproveCancels()],
              system_prompt="Help ShopKart customers with orders. Be brief.", callback_handler=None)

r = agent("Where are A-1001 and A-1002?")
print("1:", str(r).strip())
r = agent("Please cancel A-1002")
print("2:", r.stop_reason, [(i.name, i.reason) for i in r.interrupts])
r = agent([{"interruptResponse": {"interruptId": r.interrupts[0].id, "response": "yes"}}])
print("2:", str(r).strip())
print("tokens:", r.metrics.accumulated_usage)
What you should see
1: Here is what I found: A-1001 is shipped; A-1002 is processing
2: interrupt [('cancel-approval', {'order_id': 'A-1002'})]
2: Here is what I found: A-1002 cancelled
tokens: {'inputTokens': 200, 'outputTokens': 80, 'totalTokens': 280}

callback_handler=None turns off the default behavior of printing the stream to the console. For real models: BedrockModel(model_id=...) with your AWS credentials (Bedrock is the default when you pass a model ID string), AnthropicModel, OpenAIModel(model_id="gpt-5.5"), GeminiModel or LiteLLMModel.

For the common case, the built-in HumanInTheLoop intervention (from strands.vended_interventions import HumanInTheLoop) does the same approval pause without writing a hook. A session manager (FileSessionManager, S3SessionManager, or AgentCore Memory) saves the conversation and any pending interrupts, so the answer can arrive later, on a different server.

Step 2 · Structured output

Pass a Pydantic model as structured_output_model and Strands registers it as a tool the model must call, validates the arguments, and puts the object on result.structured_output. If validation fails, the error goes back to the model so it can correct itself.

from typing import Literal
from pydantic import BaseModel, Field

class Ticket(BaseModel):
    category: Literal["delivery", "refund", "account", "other"]
    urgent: bool = Field(description="True if the customer is waiting on money or a missed delivery date")

triager = Agent(model=model, system_prompt="Classify ShopKart support messages.", callback_handler=None)
r = triager("Customer says the refund never arrived.", structured_output_model=Ticket)
print(type(r.structured_output).__name__, r.structured_output)
What you should see
Ticket category='refund' urgent=False

The scripted model always answers False for booleans; a real model would mark this one urgent. The older agent.structured_output(Model, prompt) method still works but is deprecated in favor of this argument, which also works with tools in the same run.

Step 3 · Sessions, state and the context window

Two separate concerns, and Strands keeps them separate. A session manager persists the conversation and the agent's key-value state (agent state) so a new process can pick up where the last left off. A conversation manager decides what stays in the context window as the conversation grows.

import tempfile
from strands.session.file_session_manager import FileSessionManager
from strands.agent.conversation_manager import SlidingWindowConversationManager

store = tempfile.mkdtemp()                       # in production: S3SessionManager or AgentCore Memory

def support_agent(session_id: str) -> Agent:
    return Agent(model=model, tools=[get_order_status], callback_handler=None,
                 session_manager=FileSessionManager(session_id=session_id, storage_dir=store),
                 conversation_manager=SlidingWindowConversationManager(window_size=6))

first = support_agent("customer-42")
first.state.set("tier", "gold")                  # app data, saved with the session, not sent to the model
first("Where is A-1001?")

later = support_agent("customer-42")             # imagine a different server, an hour later
print("restored:", [m["role"] for m in later.messages], "| tier:", later.state.get("tier"))
for oid in ("A-1002", "A-1003", "A-1004"):
    later(f"Where is {oid}?")
print("kept in window:", len(later.messages), "messages, starting with a", later.messages[0]["role"], "turn")
What you should see
restored: ['user', 'assistant', 'user', 'assistant'] | tier: gold
kept in window: 4 messages, starting with a user turn

Each question here takes four messages (the question, the tool call, the tool result, the answer). The window allows six, but keeping six would start the context with an orphaned tool result, which models reject, so the manager trims to four. SummarizingConversationManager summarizes old turns instead of dropping them; NullConversationManager keeps everything until the model's limit.

Step 4 · Steering: rules at the moment they matter

Long system prompts full of rules get diluted as the conversation grows. Strands' steering plugins check the agent at decision points instead: before a tool runs (steer_before_tool) and after the model answers (steer_after_model). A handler returns Proceed, Guide (cancel and tell the model why) or Interrupt (ask a human).

from strands.vended_plugins.steering import SteeringHandler, Guide, Proceed

SHIPPED = {"A-1001"}

class NoCancellingShippedOrders(SteeringHandler):
    """Steer the model away from a policy violation instead of hoping the prompt prevents it."""
    async def steer_before_tool(self, *, agent, tool_use, **kwargs):
        if tool_use["name"] == "cancel_order" and tool_use["input"]["order_id"] in SHIPPED:
            return Guide(reason="Shipped orders cannot be cancelled. Offer a return instead.")
        return Proceed(reason="Policy allows it.")

steered = Agent(model=model, tools=[cancel_order], plugins=[NoCancellingShippedOrders()], callback_handler=None)
print(str(steered("Please cancel A-1001")).strip())
What you should see
Here is what I found: Tool call cancelled. Shipped orders cannot be cancelled. Offer a return instead. You MUST follow this guidance immediately.

The cancel never ran; the model received the reason and, with a real model, would offer a return instead.

Industry practice
Steering versus prompts, with numbers

In a March 2026 evaluation published by the Strands team (600 runs per approach on a customer-service task), agents using steering handlers passed 100% of cases, against 82.5% for simple instructions, 80.8% for a scripted workflow and 99.8% for a long standard-operating-procedure prompt, while using about two-thirds fewer input tokens than the SOP prompt. It is a vendor's own benchmark, but the principle generalizes: enforce rules at the point of action, in code or with a focused check, rather than by adding paragraphs to the prompt.

In production
Steering and hooks in production

Steering handlers run at every decision point, so keep them fast and deterministic: a slow handler (one that calls a model on every tool call) adds latency to every step. Make each handler's Guide message tell the model what to do instead, or it will retry the same blocked action. And log every Guide and interrupt: a rule that fires constantly is usually a sign the tool or prompt should change, not just the steering.

Step 5 · Streaming and MCP tools

stream_async yields events as they happen: text deltas (data), the tool being called (current_tool_use), each complete message, and the final result. That is what a chat UI or an SSE endpoint consumes.

import asyncio

async def stream_it():
    text = []
    streaming_agent = Agent(model=model, tools=[get_order_status], callback_handler=None)
    async for event in streaming_agent.stream_async("Where is A-1001?"):
        if "data" in event:
            text.append(event["data"])                               # token deltas, for the screen
        elif "message" in event:
            print("message:", event["message"]["role"], [next(iter(c)) for c in event["message"]["content"]])
        elif "result" in event:
            print("stop reason:", event["result"].stop_reason)
    print("streamed:", "".join(text).strip())

asyncio.run(stream_it())
What you should see
message: assistant ['toolUse']
message: user ['toolResult']
message: assistant ['text']
stop reason: end_turn
streamed: Here is what I found: A-1001 is shipped

Any MCP server becomes a set of Strands tools through MCPClient. This starts a small stdio server (built with the official mcp SDK) as a child process, lists its tools, and gives them to an agent:

import sys, pathlib
from mcp.client.stdio import stdio_client, StdioServerParameters
from strands.tools.mcp import MCPClient

pathlib.Path("orders_mcp.py").write_text('''
from mcp.server.mcpserver import MCPServer
server = MCPServer("orders")

@server.tool()
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is shipped (via MCP)"

server.run()                                    # stdio transport by default
''')

orders_mcp = MCPClient(lambda: stdio_client(StdioServerParameters(command=sys.executable, args=["orders_mcp.py"])))
with orders_mcp:                                # starts the server; stops it on exit
    mcp_tools = orders_mcp.list_tools_sync()
    print([t.tool_name for t in mcp_tools])
    mcp_agent = Agent(model=model, tools=mcp_tools, callback_handler=None)
    print(str(mcp_agent("Where is A-1001?")).strip())
What you should see
['get_order_status']
Here is what I found: A-1001 is shipped (via MCP)

For a remote server, swap stdio_client for streamablehttp_client(url, headers=...). Calls must happen inside the with block, because that is where the connection lives; for long-running services, pass the MCPClient itself in tools=[...] and Strands manages its lifecycle.

Step 6 · Four multi-agent patterns

Pattern How it works Strands API
Agents as tools An orchestrator calls specialist agents like functions Wrap an agent call in a @tool function
Swarm Agents hand work to each other autonomously, sharing context Swarm([agent_a, agent_b, ...]) with handoff and iteration limits
Graph A fixed or conditional flow between agents GraphBuilder with nodes, edges and conditions
Workflow A task list with dependencies, run in order or in parallel The workflow tool in strands-agents-tools 
from strands.multiagent import GraphBuilder

classify = Agent(name="classify", model=model, system_prompt="Classify the request.", callback_handler=None)
answer = Agent(name="answer", model=model, tools=[get_order_status], system_prompt="Answer it.", callback_handler=None)

builder = GraphBuilder()
builder.add_node(classify, "classify")
builder.add_node(answer, "answer")
builder.add_edge("classify", "answer")              # add a condition function to make it conditional
builder.set_entry_point("classify")
builder.set_max_node_executions(10)                 # always bound graphs that can loop
builder.set_execution_timeout(120)
graph = builder.build()

res = graph("Where is A-1001?")
print(res.status, [n.node_id for n in res.execution_order])
What you should see
Status.COMPLETED ['classify', 'answer']

A swarm is the autonomous counterpart: each agent gets a handoff_to_agent tool and decides who works next, sharing one context.

from strands.multiagent import Swarm

triage_agent = Agent(name="triage", model=model, system_prompt="Route requests to the right specialist.",
                     callback_handler=None)
orders_agent = Agent(name="orders", model=model, tools=[get_order_status], callback_handler=None)
swarm = Swarm([triage_agent, orders_agent], max_handoffs=5, max_iterations=6, execution_timeout=60)
res = swarm("Where is A-1001?")
print(res.status, [n.node_id for n in res.node_history])
What you should see
Status.COMPLETED ['triage']

The scripted model never calls handoff_to_agent, so triage finished the job alone. A real model would usually hand off, giving ['triage', 'orders']. The limits are the important part: max_handoffs and max_iterations stop two agents from passing a task back and forth forever, the classic swarm failure.

Step 7 · Tools, observability and deployment

  • Tools: strands-agents-tools ships ready-made tools (HTTP requests, file read and write, shell, Python REPL, calculator, use_aws for AWS APIs, retrieve for Bedrock Knowledge Bases, browser and code interpreter via AgentCore, memory backends, and agent-graph and swarm tools). Any MCP server works through MCPClient.
  • Observability: Strands emits OpenTelemetry traces and metrics natively (agent cycles, model calls, tool calls, token use). Send them to CloudWatch through AgentCore Observability, or to Langfuse, Datadog, Arize or any OTLPlater · 14.117 endpoint.

You can see exactly what it emits by installing an in-memory exporter before the agent runs. The span names and gen_ai.* attributes follow the OpenTelemetry semantic conventions for generative AI, so any OTel backend understands them:

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter

spans = InMemorySpanExporter()                   # in production: an OTLP exporter, or StrandsTelemetry()
provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(spans))
trace.set_tracer_provider(provider)

traced = Agent(name="support", model=model, tools=[get_order_status], callback_handler=None,
               trace_attributes={"customer.tier": "gold", "session.id": "customer-42"})
traced("Where is A-1001?")
for span in spans.get_finished_spans():
    print(f"{span.name:28} tokens={span.attributes.get('gen_ai.usage.total_tokens', '-')}")
What you should see
chat                         tokens=70
execute_tool get_order_status tokens=-
execute_event_loop_cycle     tokens=-
chat                         tokens=70
execute_event_loop_cycle     tokens=-
invoke_agent support         tokens=140

One invoke_agent span per request, one execute_event_loop_cycle per think-act round, a chat span per model call and an execute_tool span per tool. trace_attributes are stamped on the spans, which is how you filter traces by customer tier or session later.

  • Deployment: anywhere Python runs (Lambda, Fargate, EKS, EC2), and most commonly on Amazon Bedrock AgentCore Runtime, which hosts any framework with session isolation, identity, memory and a tool gateway (Lesson 14.125):
# app.py · wrapping a Strands agent for AgentCore Runtime (needs the bedrock-agentcore package)
from bedrock_agentcore.runtime import BedrockAgentCoreApp

app = BedrockAgentCoreApp()

@app.entrypoint
def invoke(payload: dict) -> dict:
    """AgentCore calls this for every request; the payload is your own JSON."""
    return {"answer": str(agent(payload["prompt"]))}

if __name__ == "__main__":
    app.run()                                        # serves locally on port 8080 for testing

Solutions

SolutionP1 · Model-driven loop

The model: when it replies without tool calls, the loop ends, as in Lesson 14.3. Your limits and hooks bound it.

SolutionB1 · Hooks are the control point

The cancellation runs immediately. Approval belongs in a hook or a tool wrapper, not in the prompt.

SolutionD1 · Session management

A session manager that persists conversation state per user, created per request with the user's session ID.

SolutionM1 · Typed results

Use Strands' structured output support with a Pydantic model, and validate values in code as in Lesson 11.2.
