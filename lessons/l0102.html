Why this came about

Early chat products felt slow because users waited for complete answers. Teams learned that a model's speed has two separate parts, reading the input and writing the output, and that each is tuned differently. As agents began chaining many model calls, those delays added up, so latency became a design concern rather than a detail.

In plain words first
Reading the question, then writing the answer word by word

A model's response time has two parts. First it reads the whole input at once (prefill); the longer the input, the longer before anything appears. That wait is the time to first token. Then it writes the answer one token at a time (decode); the longer the answer, the longer it takes. So a long prompt makes the start slow, and a long answer makes the whole thing slow. Streaming does not make the model faster; it shows the words as they are written, so the wait feels shorter.

Latency: two numbers, not one

A model call has two phases, and they behave very differently:

  1. Prefill (reading). The model processes your whole prompt in one pass. All prompt tokens go through the network together, in parallel, so this phase is fast: thousands of tokens per second.
  2. Decode (writing). The model writes the answer one token at a time. Each new token needs its own pass through the network, so this phase is slow: tens to a few hundred tokens per second.

A worked example with round numbers: a 4,000-token prompt at 8,000 tokens per second takes half a second to read. A 400-token answer at 80 tokens per second takes five seconds to write. The answer is a tenth the size of the prompt and takes ten times as long. That asymmetry is the single most useful fact about model latency.

How this connects
Where the speed difference comes from

Decoding is slow because each token depends on all the tokens before it, so the model cannot write them in parallel. It avoids redoing work by storing what it computed for earlier tokens in the KV cache, which Lesson 7.19 builds. You do not need the internals here, only the consequence: reading is cheap, writing is slow.

  • Time to first token (TTFT): how long until the answer starts. It grows with input length and with reasoning.
  • Output speed (tokens per second): how fast the answer streams once it starts.

A chat feels fast when TTFT is short and the answer streams. An agent feels slow because it makes several calls in sequence: five calls of 2 seconds each is a 10-second turn before any tool time. Budget latency per step, and remove steps before you optimize them.

A latency model you can reason with

Two numbers describe a model's speed: prefill throughput (prompt tokens per second, high) and decode throughput (output tokens per second, much lower). Together with a fixed overhead they predict time to first token and total time well enough for design decisions.

def latency(prompt_tokens, output_tokens, prefill_tps=8000, decode_tps=80, overhead_s=0.3, cached_tokens=0):
    """Approximate time to first token and total time for one model call."""
    ttft = overhead_s + (prompt_tokens - cached_tokens) / prefill_tps
    return round(ttft, 2), round(ttft + output_tokens / decode_tps, 2)

print("short prompt, short answer   ", latency(1_000, 100))
print("long prompt, short answer    ", latency(60_000, 100))
print("long prompt, cached prefix   ", latency(60_000, 100, cached_tokens=58_000))
print("short prompt, long answer    ", latency(1_000, 1_500))
agent_turn = [latency(4_000 + 600 * i, 150) for i in range(6)]
print("6-step agent turn, total s   ", round(sum(t for _, t in agent_turn), 1))

Three design rules follow. Output tokens are the expensive part of latency, so ask for concise answers and structured outputslater · 11.2. A long, repeated prompt is cheap only if it is cached. And agents multiply everything by the number of steps, so the fastest agent is usually the one that needs fewer model calls. The throughput numbers here are illustrative; measure your own model and provider.

Check your mental model
  • ✗ "Streaming makes the model generate faster."
    ✓ It shows tokens as they arrive; total time is the same.
  • ✗ "Latency depends mainly on the input length."
    ✓ Input length drives time to first token; output length usually dominates total time.
  • ✗ "An agent's latency is one model call."
    ✓ It is the sum of every model and tool call in the loop, so fewer steps is often the biggest win.

Exercises

Predict before you run

With latency(prompt_tokens, output_tokens), which grows the time to first token more: doubling the prompt or doubling the output? (Solution P1.)

Break it on purpose

Set a 2-second timeout on a request that generates 1,500 tokens at 50 tokens per second. What happens? (Solution B1.)

Debugging exercise

A chat feels slow although total latency is unchanged after a prompt change. What did the change likely do? (Solution D1.)

Make it your own

Use the latency model to compare a 6,000-token prompt with a 300-token output against a 500-token prompt with a 1,000-token output, and say which is faster to the first token and to the end. (Solution M1.)

Solutions

SolutionP1 · Prefill against decode

Doubling the prompt: time to first token is mostly prefill, which scales with input. Doubling the output barely changes the first token but doubles decode time, the total.

SolutionB1 · Timeouts must fit generation

It times out: generation alone takes about 30 seconds. Set timeouts from expected output length, or stream and use a time-to-first-token timeout plus a longer total timeout.

SolutionD1 · First token matters

It made the prompt longer, raising time to first token. Users feel the first token. Cache the stable prefix or shorten the prompt.

SolutionM1 · Two numbers

The long prompt has the slower first token; the long output has the slower end. Report both numbers in design discussions.

Explain the mechanismExplain prefill, decode and time to first token.

Worked answer. Prefill processes the whole input in parallel and produces the first output token; its time grows with prompt length. Decode generates the rest one token at a time, limited by memory bandwidth; its time grows with output length. Time to first token is mostly prefill plus queueing; total time adds decode.

A plausible wrong answer. "Latency is one number." It is two, with different causes and fixes.
