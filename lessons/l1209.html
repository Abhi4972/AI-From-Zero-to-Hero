Why this came about

Successful agent products hit provider rate limits and served many customers with uneven load. Capacity planning, queues and per-tenant limits became necessary to scale fairly and keep customers' data apart.

In plain words first
Many customers sharing the same kitchen

At scale, the limits are provider quotas (requests and tokens per minute), concurrency, and fairness between customers. Scaling means queueing work, controlling concurrency, giving each tenant budgets and limits so one heavy customer cannot starve the rest, and keeping each tenant's data, memory and caches strictly separate.

Scaling

  • Model calls dominate latency; run independent tool calls and sub-agents in parallel.
  • Scale workers on queue depth, not CPU: agent workers mostly wait on I/O.
  • Respect provider rate limits with client-side limiting and backoff; spread load across regions and deployments through the gateway.
  • Put per-run ceilings on steps, tokens and wall-clock time.
  • Keep conversation and workflow state in a database, never in worker memory, so any worker can continue any run.

Backoff deserves code, because the naive version (retry immediately, or every second) turns a provider's rate limit into an outage. Use exponential backoff with jitter, and obey Retry-After when the provider sends it:

class RateLimited(Exception):
    def __init__(self, retry_after: float | None):
        self.retry_after = retry_after

def call_with_backoff(fn, max_attempts: int = 5, base: float = 0.5, cap: float = 20.0, sleep=None) -> tuple:
    """Exponential backoff with full jitter; honors Retry-After when the server sends one."""
    waits = []
    for attempt in range(max_attempts):
        try:
            return fn(attempt), waits
        except RateLimited as e:
            delay = e.retry_after if e.retry_after is not None else random.uniform(0, min(cap, base * 2 ** attempt))
            waits.append(round(delay, 2))
            (sleep or (lambda s: None))(delay)                      # time.sleep in real code
    raise RuntimeError(f"gave up after {max_attempts} attempts; waited {waits}")

def provider(attempt: int) -> str:
    if attempt < 3:
        raise RateLimited(retry_after=4.0 if attempt == 2 else None)   # 429s; the third carries Retry-After
    return "ok"

random.seed(42)
print(call_with_backoff(provider))
What you should see
('ok', [0.32, 0.03, 4.0])

The first two waits are random draws below 0.5 s and 1 s ("full jitter"), so a thousand workers hitting the same 429 do not all retry at the same instant; the third wait is the 4 seconds the provider asked for. The SDKs from OpenAI and Anthropic do this for you (max_retries), and so do gateways; write it yourself for tools and internal APIs.

A web service scales with requests. An agent service scales with runs, and a run is long (seconds to hours), bursty, stateful and expensive: each one holds context, makes several model calls and may wait on tools or people. That changes the arithmetic and the architecture. Lesson 14.140 covered where agents run and how they survive crashes; this lesson is about what happens when there are many of them.

Size it before you build it

Two numbers decide most of the design:

  • Runs in flight = arrival rate x time per run (Little's law). It sets the number of workers, the memory for contexts and the connections to tools.
  • Tokens per minute at peak = arrival rate x tokens per run. It is checked against the provider's TPM quota, which is often the first thing to run out.
import math

def capacity(tasks_per_day, peak_factor, seconds_per_task, steps, input_tokens_per_step,
             output_tokens_per_step, tpm_quota, workers_per_pod=50):
    """Size an agent service for its peak hour. Little's law: work in flight = arrival rate x time in system."""
    peak_rate = tasks_per_day / 86_400 * peak_factor                      # tasks per second at peak
    in_flight = peak_rate * seconds_per_task                              # concurrent runs
    tokens_per_task = steps * (input_tokens_per_step + output_tokens_per_step)
    tpm_needed = peak_rate * 60 * tokens_per_task
    pods = math.ceil(in_flight * 1.3 / workers_per_pod)                    # 30% headroom
    return {"peak tasks/s": round(peak_rate, 2), "runs in flight": math.ceil(in_flight),
            "pods (50 workers, 30% headroom)": pods, "tokens per task": tokens_per_task,
            "TPM needed": round(tpm_needed), "TPM quota": tpm_quota,
            "quota headroom": f"{tpm_quota / tpm_needed:.2f}x"}

base = dict(tasks_per_day=60_000, peak_factor=3, seconds_per_task=40, steps=6,
            input_tokens_per_step=9_000, output_tokens_per_step=300, tpm_quota=10_000_000)
for name, change in [("today", {}), ("after launch in a second region", {"tasks_per_day": 120_000}),
                     ("plus a longer system prompt", {"tasks_per_day": 120_000, "input_tokens_per_step": 14_000})]:
    r = capacity(**{**base, **change})
    print(f"{name}:")
    print("   " + " | ".join(f"{k} {v:,}" if isinstance(v, int) else f"{k} {v}" for k, v in r.items()))

Five pods handle the doubled traffic easily; the token quota does not. A second region halves the headroom, and a system prompt that grew by 5,000 tokens takes it to less than half of what is needed, with no change in traffic. This is the most common scaling surprise with agents: prompt changes are capacity changes. Treat input tokens per step as a capacity number, review it in every release, and reserve quota (provisioned throughputlater · 14.142, committed capacity) before a launch rather than after the first 429s.

The runtime shape that scales

Concern Pattern Why
Long runs Accept the request, enqueue the run, return a run ID; stream progress to the user Web servers should not hold a socket open for minutes; queues absorb bursts (Lesson 14.140)
Bursts A durable queue in front of a pool of workers that autoscale on queue depth Scale on the work waiting, not on CPU, which idles while waiting for models
Different urgency Separate lanes: interactive, background and batch, each with its own workers and quota share A nightly batch must never slow down a customer conversation
State Run state in a durable store keyed by run ID, not in the worker's memory Any worker can resume any run; deploys do not lose work
Slow tools Bulkheads: a separate pool and timeout per slow dependency One slow tool cannot exhaust every worker (Lesson 14.139)
Quota All model traffic through the gateway, which enforces per-team and per-tenant shares Quota becomes something you allocate, not something you discover (Lesson 14.136)
Overload Admission control: reject or defer new batch work when queue age or quota use crosses a threshold; keep interactive lanes open Shedding load early keeps the service usable for the work that matters

Hands-on · Fair scheduling across tenants

In a multi-tenant agent product, one large customer's batch job can fill the queue and make every other customer wait. The simulation below runs three tenants on 20 workers. At one minute, bigco submits 900 batch runs. First-in, first-out scheduling lets that burst delay everyone; round-robin across tenants with a concurrency cap per tenant keeps the others fast.

import heapq, random
from collections import defaultdict, deque

def schedule(policy, seconds=600, workers=20, seed=3):
    """Three tenants share 20 agent workers; each run takes 20-40 s. Tenant 'bigco' floods the
    queue at second 60 with 900 batch runs; 'acme' and 'kirana' send a steady interactive trickle."""
    rng = random.Random(seed)
    arrivals = defaultdict(list)
    for t in range(seconds):
        if rng.random() < 0.25: arrivals[t].append("acme")
        if rng.random() < 0.15: arrivals[t].append("kirana")
        if rng.random() < 0.20: arrivals[t].append("bigco")
    arrivals[60] += ["bigco"] * 900
    fifo, per_tenant = deque(), defaultdict(deque)
    running, waits, active = [], defaultdict(list), defaultdict(int)
    CAP = {"acme": 8, "kirana": 8, "bigco": 10}          # per-tenant concurrency caps
    rr = deque(["acme", "kirana", "bigco"])
    for t in range(seconds + 3000):
        while running and running[0][0] <= t:            # free finished workers
            _, tenant = heapq.heappop(running); active[tenant] -= 1
        for tenant in arrivals.get(t, []):
            (fifo if policy == "fifo" else per_tenant[tenant]).append((t, tenant))
        while len(running) < workers:
            job = None
            if policy == "fifo":
                job = fifo.popleft() if fifo else None
            else:                                         # round robin over tenants with work and spare cap
                for _ in range(len(rr)):
                    tenant = rr[0]; rr.rotate(-1)
                    if per_tenant[tenant] and active[tenant] < CAP[tenant]:
                        job = per_tenant[tenant].popleft(); break
            if job is None:
                break
            start, tenant = job
            waits[tenant].append(t - start); active[tenant] += 1
            heapq.heappush(running, (t + rng.randint(20, 40), tenant))
    return waits

for policy in ["fifo", "fair"]:
    w = schedule(policy)
    cells = []
    for tenant in ["acme", "kirana", "bigco"]:
        x = sorted(w[tenant]); cells.append(f"{tenant} p95 wait {x[int(len(x) * .95)]:4} s")
    print(f"{policy:5} | " + " | ".join(cells))
What you should see
fifo  | acme p95 wait 1358 s | kirana p95 wait 1360 s | bigco p95 wait 1351 s
fair  | acme p95 wait   38 s | kirana p95 wait    9 s | bigco p95 wait 2757 s

With a single queue, the two small tenants wait more than twenty minutes for interactive work because a batch arrived first. With per-tenant queues and caps, their p95 wait drops to seconds and the tenant that sent the burst absorbs the delay. In production, put batch work in its own lane with its own quota as well, and show bigco an honest completion estimate. The same pattern applies inside one company: per-team caps at the gateway keep one team's experiment from exhausting the shared quota.

Budgets at three levels

Level Budget Enforced by When it trips
Run Steps, tokens, wall-clock time and cost per run The harness (Lesson 14.67) Stop, summarize progress, escalate or ask the user
Tenant or team Spend and quota per day or month The gateway (Lesson 14.136) Degrade to a cheaper model, defer batch work, alert the account owner
Service Total spend and quota Gateway and finance alerts (Lesson 14.142) Page; admission control sheds batch lanes first

Without run budgets, a looping agent spends a tenant's monthly budget in an afternoon. Without tenant budgets, one tenant spends everyone's.

Lever Typical effect What it can break
Prompt caching with a stable prefix Large input-cost and latency cuts on agents, which are input-heavy (Lesson 14.142, Lesson 14.163) Anything that changes the prefix: timestamps, reordered tools
Shorter context: compact tool results, prune history, load detail on demand Fewer tokens per step, better accuracy Lost facts if pruning is careless; keep the system of record as truth
Model routing: a small model for routine steps, a large one for hard ones Lower cost per task Quality on the hard tail; route by evidence from evals

What breaks at ten times the load

Ask this in every design review (Lesson 14.151). For agents the usual order is: provider quota and rate limits, then a tool or database that was sized for human traffic (agents call tools far more often than people click), then cost, then queue latency for interactive users, and only then your own servers. The fixes are the ones above, applied before the launch that needs them.

Hands-on lab
Lab P7 · Plan for ten times the load
  1. Fill in the capacity function with your agent's real numbers from traces. Find your bottleneck at today's peak and at ten times it.
  2. Split your work into lanes. Write the quota share and worker count for each.
  3. Add per-tenant (or per-team) caps to the scheduler and replay a burst from one tenant.
  4. Write the three levels of budget for your agent and what happens when each one trips.
  5. Pick the cost lever with the best payoff for your traces, apply it, and show with evals that quality held.

Solutions

SolutionP1 · Quotas are capacity

Requests get rate-limited (429s). Mitigations: request a quota increase ahead of time, spread across regions or deployments, prioritize critical traffic and degrade the rest, and cache.

SolutionB1 · Noisy neighbors

Rate limits and slow responses during the job. Separate quotas per tenant or workload, and schedule batch work off-peak.

SolutionD1 · Find the real limit

Likely the provider quota, a database, or a tool backend, not the workers. Measure where requests wait.

SolutionM1 · Tenant isolation

Per-tenant namespaces for data and memory, per-tenant quotas and budgets at the gateway, tenant ID on every trace, and noisy-tenant protections.

Check your understanding

Explain the mechanismHow do you scale an agent system?

Worked answer. Find the limiting resource (provider quotas, GPUs, tools, databases), plan capacity for peaks, isolate tenants and workloads, use queues and background runs for slow work, cache and route to cheaper models, and degrade gracefully under overload.

A plausible wrong answer. "Add more servers." Agents are usually limited by quotas and dependencies.

Follow-ups. How do you prioritize traffic under overload?

Debug a failure429 errors spike every Monday morning. What do you do?

Worked answer. Find the cause (batch jobs, a tenant, a traffic pattern), reschedule or separate it, raise quotas ahead of known peaks, and add backoff and queueing.

A plausible wrong answer. "Ask the provider for unlimited quota." Plan capacity instead.

Follow-ups. How would you forecast peaks?

Defend a designShared or dedicated capacity for a large customer?

Worked answer. Dedicated (provisioned throughput or separate quotas) when the customer needs guarantees and pays for them; shared with limits for the rest. Mixing gives predictability without wasting capacity.

A plausible wrong answer. "Shared for everyone, it is cheaper." Until the large customer degrades everyone.

Follow-ups. How would you price it?
