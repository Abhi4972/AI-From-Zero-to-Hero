In plain words first
The idea in one line

CLIP aligns image and text but cannot generate captions, answer questions, or hold a conversation. BLIP-2 (Salesforce, 2023) solved that with a small trainable bridge: 32 learnable query vectors attend over a frozen ViT's features via cross-attention, then slot directly into a frozen LLM's input stream. 188M parameters of bridge connected a ViT-g/14 to frozen LLMs as large as the 11B Flan-T5-XXL. Every adapter-based VLM through 2026 — MiniGPT-4, InstructBLIP, LLaVA's cousins — is a descendant. This lesson reads the Q-Former's architecture,

Terms you'll hear
Term What people say What it actually means
Q-Former "Querying transformer" Small transformer with 32 learnable query vectors that cross-attend to frozen ViT features
Learnable queries "Soft prompt for vision" A fixed set of parameters that serve as the query side of cross-attention; learned per model, shared across all inputs
Cross-attention "Q from here, K/V from there" Attention where query, key, and value come from different sources; how the queries pull from ViT patches
ITC "Image-text contrastive" CLIP-style loss applied to Q-Former pooled queries vs text CLS
ITM "Image-text matching" Binary classifier on hard-negative-mined pairs; forces the queries to discriminate fine-grained mismatches
ITG "Image-grounded text generation" Causal LM loss where text is generated conditioned on queries; forces queries to encode text-decodable content
Two-stage pretraining "Representation then generative" Stage 1 trains Q-Former alone (ITC/ITM/ITG); Stage 2 attaches frozen LLM and trains only the projection + Q-Former
Frozen backbone "Do not finetune" The vision encoder and LLM weights are fixed; only the bridge trains
Projection head "Linear to LLM dim" Final linear layer mapping Q-Former output to the LLM's embedding dimension
Perceiver resampler "Flamingo's version" Similar learnable-query cross-attention; Flamingo runs it once per image to make fixed latents, then reads them through gated cross-attention at every LLM layer

The problem

In plain words first

CLIP can tell which caption fits a picture, but it cannot write one. To make a language model talk about images, you have to feed it the image as something it can read: vectors in its own input space. BLIP-2 does this with a small trainable bridge called the Q-Former. 32 learned "query" vectors look at the frozen image encoder's patch features through cross-attention. They come out as 32 summary vectors, which a linear layer maps into the frozen language model's embedding space, in front of the text prompt. Only the bridge is trained, so the cost is a few percent of the full model. This lesson walks through the Q-Former and its two-stage training, counts the real BLIP-2 and LLaVA models part by part, and measures what each visual token costs a real language model. No model is trained.

You have a frozen ViT that produces 256 patch tokens of dim 1408 per image. You have a frozen 7B LLM that expects token embeddings of dim 4096. The obvious bridge — a linear layer from 1408 to 4096 — works, but feeding all 256 patch tokens into the LLM's context costs 256 extra tokens per image. Over a batch of 32 images that is 8192 tokens consumed by the visual modality alone.

The BLIP-2 question: can you compress the 256-token image representation into far fewer tokens (say 32) while preserving enough information for the LLM to caption, answer questions, and reason about the image? And can you train this bridge without touching the frozen backbones, keeping the training cost at just the bridge's parameters?

The answer: a Q-Former. 32 learnable "query" vectors that cross-attend to the ViT's patch tokens, producing a 32-token visual summary that the LLM consumes. 188M parameters total. Trained with contrastive, matching, and generative objectives before ever touching the LLM.

Idea 1 · Learnable queries

The Q-Former's core trick: instead of letting the LLM's text tokens attend to image patches, introduce a new set of 32 learnable query vectors Q and let them attend to image patches. The queries are parameters of the model — they are learned during training and the same 32 queries are used for every image.

After cross-attention, each query holds a compressed summary of the image — "describe the main object", "describe the background", "count the objects", etc. The queries do not literally specialize on semantic labels; they learn whatever encoding makes downstream losses drop.

Idea 2 · Architecture

The Q-Former is a small transformer (12 layers of width 768, initialised from BERT-base; cross-attention in every other layer) with two paths:

  1. Query path: 32 query vectors flow through self-attention (among themselves), then cross-attention over the frozen ViT's patch tokens, then FFN.
  2. Text path: a BERT-like text encoder shares the self-attention and FFN weights with the query path. Cross-attention is disabled for the text path.

At training time both paths run. The queries and text interact through shared self-attention, which means the queries can condition on text for tasks that need it (ITM, ITG). At inference time for VLM handoff, only the queries flow through, yielding 32 visual tokens.

Idea 3 · Two-stage training

BLIP-2 pretrains in two stages:

Stage 1: representation learning (no LLM). Three losses: - ITC (image-text contrastive): CLIP-style contrastive between pooled query tokens and text CLS token. - ITM (image-text matching): binary classifier — is this image-text pair a match? Hard-negative-mined. - ITG (image-grounded text generation): causal LM head on text, conditioned on the queries. Forces queries to encode text-generatable content.

Only the Q-Former trains. The ViT is frozen. No LLM involved.

Stage 2: generative learning. Attach a frozen LLM (OPT-2.7B or Flan-T5-XL, etc.). Project the 32 query outputs to the LLM's embedding dim via a small linear layer. Prepend them to the text prompt. Train only the linear projection and the Q-Former on LM loss over the concatenated prompt + image + caption sequence.

After stage 2, the Q-Former + projection is the full visual adapter. At inference: image → ViT → Q-Former → linear proj → prepended to text → frozen LLM emits output.

Idea 4 · Parameter economics

BLIP-2 with EVA-CLIP ViT-g/14 (about 1B, frozen) + OPT-6.7B (frozen) + Q-Former (trained) is about 7.8B parameters, of which only the bridge is trained. The paper counts the Q-Former as 188M, because stage 1 also uses its text path (a BERT-base text encoder). The released inference model keeps only the query path: 105M plus a 3M projection, 1.4% of the stack (measured below). Training cost reflects this: the paper's largest model trained in under 9 days on 16 A100 GPUs.

Quality: BLIP-2 beat Flamingo-80B by 8.7 points on zero-shot VQAv2 with 54 times fewer trainable parameters. The bridge works.

The same idea as a formula

Cross-attention with learned queries. Q∈R32×d are parameters; the frozen image features X∈RN×dv​ supply keys and values:

CA(Q,X)=softmax(d​(QWq​)(XWk​)⊤​)XWv​ ∈R32×d.
The output always has 32 rows, whatever N is: the image is compressed to a fixed budget.

Handoff to the LLM: H=QFormer(Q,X)Wp​ with Wp​∈Rd×dLLM​; the LLM reads [H;text tokens].

What visual tokens cost the LLM. For n visual tokens, prefill work grows about linearly in n for the weight matrices and quadratically for attention, and the KV cache grows linearly:

KV bytes=2⋅L⋅hkv​⋅dh​⋅b⋅(n+ntext​).

Worked example
Five images in one prompt
  • LLaVA-1.5 passes all 24×24=576 patch tokens per image; five images are 2,880 tokens before any text.
  • BLIP-2 passes 32 per image: 160 tokens for five images, 18 times fewer.
  • For a 7B model with full multi-head attention (L=32, 32 heads of 128, bf16), the KV cache is 2⋅32⋅32⋅128⋅2=524,288 bytes per token: about 1.5 GB for 2,880 visual tokens, 84 MB for 160.
  • The price of compression: 32 vectors must carry everything about the image. Fine detail (small text, counts, positions) is what gets lost first.
Check your mental model
  • ✗ "The 32 queries are computed from the image."
    ✓ They are parameters, the same for every image; what they read from the image is computed by cross-attention.
  • ✗ "BLIP-2 fine-tunes the language model."
    ✓ The image encoder and the LLM stay frozen; only the Q-Former and the projection train.
  • ✗ "Fewer visual tokens is always better."
    ✓ It saves context and compute, at the cost of detail; MLP projectors won once instruction data showed that the detail matters.

BLIP-2 and LLaVA, part by part

BLIP-2 (OPT-2.7B and OPT-6.7B) and LLaVA-1.5-7B are built from their published configurations on PyTorch's meta device. Parameters are counted per component: frozen vision encoder, trained bridge, frozen language model. A few seconds.

import torch
from transformers import AutoConfig, Blip2ForConditionalGeneration, LlavaForConditionalGeneration, logging
logging.set_verbosity_error()

def count(m, prefix):
    return sum(p.numel() for n, p in m.named_parameters() if n.startswith(prefix))

for repo in ["Salesforce/blip2-opt-2.7b", "Salesforce/blip2-opt-6.7b"]:
    cfg = AutoConfig.from_pretrained(repo)

Reading this output

The bridge is tiny. In BLIP-2 OPT-2.7B, the Q-Former with its 32 query vectors is 105M parameters and the projection into OPT's embedding space 2M: 107M trained out of 3.74B, 2.9%. With OPT-6.7B the bridge is the same size (only the projection grows), so the trained share falls to 1.4%. The 986M-parameter EVA-CLIP ViT-g and the language model stay frozen.

Why not 188M, as the paper says? The paper's count includes the Q-Former's text path and the heads used only in stage 1 (contrastive, matching and generation losses). The released model for generation keeps just the query path: 12 layers of width 768 with cross-attention to the image in every other layer.

LLaVA-1.5's bridge is smaller still, but sends more tokens. Its projector is a 2-layer MLP of 21M parameters. Instead of compressing, it forwards every one of the 576 patch tokens (a 24 × 24 grid from CLIP ViT-L/14 at 336 px), 18 times BLIP-2's 32. The parameter budget of the bridge says little about cost. The number of tokens it hands to the LLM says a lot, as the next run shows.

What visual tokens cost a real language model

Qwen2.5-0.5B-Instruct prefills a request made of n "visual tokens" plus 40 text tokens. The visual tokens are random vectors of the right width fed as inputs_embeds, since only their number matters for cost. n is 32 (Q-Former), 576 (LLaVA-1.5), 729 (SigLIP at 384 px) and 2,880 (five LLaVA images). The table shows prefill time on CPU and KV-cache size. About a minute.

import time, torch
from transformers import AutoModelForCausalLM, logging
logging.set_verbosity_error()
torch.manual_seed(0)
# What visual tokens cost the language model: prefill time and KV-cache size on a real 0.5B LLM.
# The "visual tokens" are random vectors of the right width, fed as inputs_embeds (only their number matters here).
lm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", dtype=torch.float32).eval()
c = lm.config
kv_per_token = 2 * c.num_hidden_layers * c.num_key_value_heads * (c.hidden_size // c.num_attention_heads) * 2   # bf16 bytes
prompt = 40                                                        # a short text question after the image tokens
print(f"{'per request':<40}{'visual tokens':>14}{'prefill (s)':>13}{'KV cache':>10}")
for label, n in [("1 image, Q-Former (BLIP-2)", 32), ("1 image, LLaVA-1.5 (24x24 patches)", 576),
                 ("1 image, SigLIP So400m @ 384", 729), ("5 images, LLaVA-1.5", 5 * 576)]:
    x = torch.randn(1, n + prompt, c.hidden_size) * 0.02
    with torch.no_grad():
        lm(inputs_embeds=x[:, :8], logits_to_keep=1)               # warm-up

    print(f"{label:<40}{n:>14,}{dt:>13.2f}{(n + prompt) * kv_per_token / 1e6:>8.1f} MB")

Reading this output

Every visual token is a token the LLM must process. Prefill time rises with the number of visual tokens: 32 Q-Former tokens are cheap, 576 LLaVA tokens cost several times as much, and five LLaVA images (2,880 tokens) cost far more again. The growth is slightly faster than linear, because attention grows with the square of the sequence. Exact timings vary between runs on a shared CPU; the ordering and the rough ratios do not.

Memory follows the same count. The KV cache grows linearly: under 1 MB for the 32-token image, about 36 MB for five LLaVA images on this small model (12 KB per token). For a 7B model with full multi-head attention it is 524 KB per token, so the five-image prompt holds about 1.5 GB of cache per request. That limits how many users a GPU can serve at once.

The trade-off BLIP-2 made. Compressing to 32 tokens makes every image cheap, and is why Q-Former-style compressors still appear where many images or long videos must fit. LLaVA's choice of passing all 576 tokens costs more, but keeps detail, and with good instruction data it won on quality. Most current models sit in between, merging neighbouring patches (2 × 2 merging turns 576 tokens into 144).

Idea 5 · InstructBLIP and the instruction-aware Q-Former

InstructBLIP (2023) extends the Q-Former with an extra input: the instruction text itself. At cross-attention time, the queries now have access to both the image patches and the instruction. The queries can specialize per-instruction ("count the cars", "describe the mood") rather than learning a single fixed summary. Benchmark gains on held-out tasks.

Idea 6 · MiniGPT-4 and the projector-only approach

MiniGPT-4 kept the Q-Former but trained only the output linear projection while freezing everything else. Cheap, but cost is quality — the queries were BLIP-2's, not yours. Good for rapid iteration, not the best architecture.

Idea 7 · Why LLaVA went simpler

LLaVA (2023, Lesson 12.05) replaced the Q-Former with a plain 2-layer MLP that projects every ViT patch token into LLM space — 576 tokens per image for a 24x24 grid, all fed to the LLM. Worse compression but lets the LLM attend over raw patches. At the time this was controversial; by late 2023 it was dominant because visual instruction data (LLaVA-Instruct-150k) proved that the MLP could be trained to preserve enough signal. The tradeoff: LLaVA's context fills faster, but it scales naturally to multi-image and video.

By 2026 the MLP projector, with patch merging when tokens are scarce, has become the default. Learned-query compressors survive where token budget matters most, such as long video and many images.

Idea 8 · Gated cross-attention: Flamingo, the ancestor

Flamingo (Lesson 12.04) predated BLIP-2 and used the same cross-attention idea but inside the frozen LLM, through gated cross-attention layers inserted between its blocks, not as a single bridge at the input. BLIP-2 showed you can compress at the input only and still work. The first Idefics (2023) was an open Flamingo-style model; Idefics2 and later moved to input tokens produced by a perceiver resampler.

Idea 9 · The 2026 descendants

  • Q-Former: BLIP-2, InstructBLIP, MiniGPT-4, and some early video-language models (Video-LLaMA) for token budget reasons.
  • Perceiver resampler: Flamingo's variant (Lesson 12.04); Idefics2 compresses each image to 64 tokens with one (Idefics3 later switched to pixel shuffle).
  • MLP projector: LLaVA, LLaVA-NeXT, LLaVA-OneVision, Cambrian-1, and most 2024–2026 open VLMs. They usually merge neighbouring patches before the MLP to save tokens (2×2 merging in Qwen2-VL and later, pixel shuffle in InternVL).
  • Linear projection of every patch: PaliGemma.

All four are valid. The deciding question is whether you are constrained on token budget or on quality-per-token.

Use it: the same idea with real libraries

code/main.py builds a stdlib Q-Former-style cross-attention:

  1. Simulate 256 image patch tokens (dim 128).
  2. Instantiate 32 learnable queries (dim 128).
  3. Run scaled-dot-product cross-attention (Q from queries, K/V from patches).
  4. Project to LLM-dim (512) via a linear layer.
  5. Output the 32 LLM-ready visual tokens.

All math in pure Python (nested loops over vectors). Toy but correct shape. The attention-weight matrix is printed so you can see which patches each query pulled from.

Industry practice
What's current (2024–2026)
  • MLP projectors with token merging are the common bridge in open VLMs: Qwen2.5-VL and Qwen3-VL merge 2×2 patches, InternVL uses pixel shuffle, LLaVA-OneVision keeps an MLP with resolution-dependent pooling.
  • Learned-query compressors live on where tokens are scarce: perceiver resamplers (Idefics2) and query-based compression in long-video models.
  • Freeze, then unfreeze: most 2024–2026 recipes train the projector first with the encoder and LLM frozen, then unfreeze the LLM (and often the encoder) for instruction tuning; the fully frozen BLIP-2 setup is now mainly a low-cost option.
  • Visual tokens dominate multimodal prompts: providers bill images per patch-token (Lesson 12.1), so token-saving bridges matter in production as well as in training.

Sources: BLIP-2 (arXiv 2301.12597), LLaVA-1.5 (arXiv 2310.03744), Idefics2 (arXiv 2405.02246), Qwen2.5-VL technical report (arXiv 2502.13923), Hugging Face BLIP-2 documentation.

Recap
What to keep from this lesson
  • A Q-Former turns any number of image patches into 32 vectors with learned queries and cross-attention.
  • A linear projection places them in the frozen LLM's input space, before the text.
  • Stage 1 aligns queries with text (contrastive, matching, generation); stage 2 teaches the LLM handoff.
  • Only about 100M parameters train; the encoder and LLM stay frozen.
  • Visual tokens cost LLM compute and KV memory; compression trades detail for budget.

- Treating Perceiver resampler as equivalent to Q-Former. Flamingo applies it at every LLM layer; BLIP-2 applies it once.

Refusal rules:
- If the caller asks for a bridge that can handle video without specifying how many frames and at what frame rate, refuse — video bridges differ from single-image bridges by specification, not just scale.
- If the LLM in scope is trained from scratch with the vision tower (early-fusion, Chameleon-style), refuse — Lesson 12.11 covers that case separately.

Solutions

SolutionP1 · About 1%, and several times the prefill

108M of 7.75B, about 1.4%: the Q-Former (105M with its 32 queries) and a 3M projection; the 986M vision encoder and the 6.66B OPT model are frozen. On Qwen2.5-0.5B, prefilling 576 visual tokens plus a 40-token question took several times as long as 32 visual tokens (about 4 times when this page was built; it varies between runs), and five LLaVA images about 30 times as long. A short request has a fixed overhead, so the ratio grows with the number of tokens.

SolutionB1 · Without stage 1, the bridge learns much less

The BLIP-2 paper tested exactly this (its Figure 5): without the stage-1 representation learning, zero-shot VQA accuracy dropped sharply for both OPT and Flan-T5, and the OPT model suffered catastrophic forgetting during stage 2. Stage 1 teaches the queries what to extract: the contrastive loss aligns them with text, the matching loss forces fine-grained comparison, and the generation loss makes them carry the information a caption needs. Skip it, and the queries start from random vectors. The language-modelling loss then has to discover visual features through a frozen LLM, which gives a weak, indirect signal. On a small dataset the bridge settles for whatever helps predict common caption words. Pretrain the bridge on image–text alignment first, or start from a released Q-Former checkpoint.

Weigh a trade-offYou are choosing the bridge between a frozen vision encoder and a language model that stays frozen, for a new product. One architect wants a query-based transformer that compresses each image to a fixed set of tokens. Another wants a plain MLP that passes every patch through. How do you decide?

Level 2 of 4 · about 12 minutes to answer well.

Short answer. Decide on the token budget, not on quality in the abstract. At a fixed number of visual tokens, the ablation studies find the connector architecture a wash, within about a point between an MLP on mean-pooled patches, a query bridge and a resampler; a full-patch MLP spends more tokens, so it sits at a different budget. The query bridge caps an image at 32 tokens whatever its resolution and costs 188M parameters plus a two-stage pretraining of its own; the MLP emits every patch, 576 for a 336-pixel image, with about 22M parameters and one language-modeling loss. Pick the compressing bridge when context binds, as with long video or many images; pick the MLP when quality per token and simplicity matter and the context is long enough.

The two bridges.

Query bridge MLP
Visual tokens per image 32, fixed 576 at 336 pixels, about 2880 with tiling
Trainable parameters, language model frozen 188M about 22M
Pretraining a representation stage with contrastive, matching and generation losses, then a generative stage the language-modeling loss throughout
Swap the language model retrain the bridge retrain a small head
Many images and video awkward, but cheap in tokens natural concatenation, expensive in tokens

What the ablations say.

Several controlled studies reached one result. At a fixed visual-token count, the connector explains about 5 percent of the variance in benchmark scores, the per-image token count about 60 percent, and the encoder about 20. An MLP on pooled patches lands within 1 point of a 32-query bridge at the same budget. So the question is how many tokens you can afford, and which encoder you use.

Why the field split.

The compressing bridge wins where the token budget binds: long video, many images in one prompt, small contexts. The MLP won the single-image case once contexts grew to 32k and beyond, because every patch stays visible to the language model and the recipe has no stage-one losses to tune. Token budgets from the ablations: 64 per image is too few for reading text, 576 to 1024 is the sweet spot for most tasks, and 2048 and above pays only for documents and charts.

Hidden costs of the query bridge.

Its queries learn an intermediate representation that the language model must then decode, so information is lost in the bottleneck. Change the language model or the encoder, and you retrain it. An instruction-aware variant feeds the instruction into the queries so that they can specialize per question, which recovers some of the loss.

A decision rule.

  1. Count the tokens per image at your resolution and multiply by the images per prompt.
  2. If it fits the context with room for text, use the MLP and spend the effort on the encoder and the data.
  3. If it does not, use a compressing bridge, and accept the retraining cost when parts change.

Plausible wrong answers.

  • "The query bridge is more advanced, so it gives better answers." At the same token count the two are within about a point; its advantage is compression, not quality.
  • "The MLP is always better because it keeps every patch." Keeping every patch costs tokens; with many images or video the context runs out before quality matters.
  • "Pick the bridge first and the encoder later." The encoder and the token count explain most of the variance; the bridge is the last knob to turn.

Follow-ups an interviewer may ask.

  • (level 2) Why does the query bridge need a pretraining stage of its own? Expected: its queries start random and must learn to pull text-relevant content from the patches before the language model can use them; the MLP starts from patches that already carry the image.
  • (level 2) What do the three stage-one losses do? Expected: contrastive alignment of pooled queries with text, a matching classifier with hard negatives, and image-grounded text generation that forces the queries to encode what text needs.
  • (level 3) A team picked the MLP and now serves ten-minute videos. What do they hit first? Expected: the context; tokens per frame times frames exceeds any window, so they need heavy frame sampling or a compressing bridge after all.
  • (level 3) If the connector barely matters, where does the quality come from? Expected: the encoder, the token count, the data mix and the resolution schedule; the recipes lesson's decomposition puts the connector last.
