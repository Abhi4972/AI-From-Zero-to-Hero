In plain words first
The idea in one line

The three frontier providers converged on the same tool-call loop in 2024 and then diverged on everything else. OpenAI uses tools and tool_calls. Anthropic uses tool_use and tool_result blocks. Gemini uses functionDeclarations and unique-id correlation. This lesson diffs the three side by side so code that ships on one provider does not break when you port it.

The problem

In plain words first

OpenAI, Anthropic and Google all run the same tool loop from Lesson 13.1, but each spells it differently. The tool list sits in a different wrapper. The model's call comes back in a different place, and OpenAI sends the arguments as a JSON string while the others send an object. The result goes back in a different kind of message, and the switches that force or forbid tool use have different names. Code written for one provider breaks on the next for these reasons alone. This lesson lines the three formats up field by field. It then builds one canonical tool with translators to each format, checks every translated piece against the providers' own Python SDK types, and converts a schema to OpenAI's strict-mode rules. No network calls and no model are needed.

The shape of a function-calling request differs by provider. Three concrete examples from 2026 production stacks:

OpenAI Chat Completions / Responses API. You pass tools: [{type: "function", function: {name, description, parameters, strict}}]. The model's response contains choices[0].message.tool_calls: [{id, type: "function", function: {name, arguments}}] where arguments is a JSON string you must parse. Strict mode (strict: true) enforces schema compliance via constrained decoding.

Anthropic Messages API. You pass tools: [{name, description, input_schema}]. The response comes back as content: [{type: "text"}, {type: "tool_use", id, name, input}]. input is already parsed (an object, not a string). You reply with a new user message containing a {type: "tool_result", tool_use_id, content} block.

Google Gemini API. In generateContent you pass tools: [{functionDeclarations: [{name, description, parameters}]}] (nested under functionDeclarations; parametersJsonSchema takes plain JSON Schema). The response arrives as candidates[0].content.parts: [{functionCall: {name, args, id}}], and you reply with {functionResponse: {name, id, response}}. Google's newer Interactions API names the same two steps function_call and function_result, linked by call_id.

Same loop. Different field names, different nesting, different string-vs-object conventions, different correlation mechanisms. A team that writes a weather agent on OpenAI pays a two-day port to Anthropic and another day to Gemini just for the plumbing.

This lesson builds a translator that unifies the three formats into one canonical tool declaration and routes at the edge. Phase 13 · 17 generalizes the same pattern into an LLM gateway.

Idea 1 · The common structure

Every provider needs five things:

  1. Tool list. Per-tool name, description, and input schema.
  2. Tool choice. Force a specific tool, forbid tools, or let the model decide.
  3. Call emission. Structured output naming the tool and arguments.
  4. Call id. Correlate the response to the right call (matters for parallel).
  5. Result injection. A message or block that ties the result back to the call.

Idea 3 · Limits you will actually hit

  • OpenAI. Up to 128 tools per request. Strict mode: every property listed in required, additionalProperties: false on every object, an object at the root (not anyOf), at most 10 levels of nesting, 5,000 properties and 1,000 enum values in total. $defs/$ref and recursive schemas are supported.
  • Anthropic. No small fixed tool cap is documented, but every definition costs prompt tokens on every call; for large catalogs Anthropic offers a tool search tool that loads definitions on demand. Strict tool use is opt-in with strict: true on the tool definition. Without it, the schema is a contract the model tends to follow, not a guarantee.
  • Gemini. parameters takes an OpenAPI 3.0-style subset of JSON Schema; parametersJsonSchema takes JSON Schema directly. Gemini 3 models also return thought signatures, which must be sent back unchanged with the conversation.

Idea 4 · tool_choice behavior

Three modes everyone supports, named differently.

  • Auto. Model picks tool or text. Default.
  • Required / Any. Model must call at least one tool.
  • None. Model must not call tools.

Plus one mode unique to each provider:

  • OpenAI. Force a specific tool by name.
  • Anthropic. Force a specific tool by name; disable_parallel_tool_use flag separates single vs multi.
  • Gemini. mode: "VALIDATED" lets the model answer in text or call a function, and constrains any call to the declared schema; allowed_function_names restricts which functions may be called.
The same idea as a formula

Translate, call, parse. For provider p, a translator Dp​ wraps the canonical tool τ in that provider's envelope, and a parser Pp​ pulls the canonical call c=(id,name,args) out of the provider's response Rp​. Portable code needs

Pp​(Rp​)=cfor every p,with args=json.loads(⋅) only for OpenAI.

Strict mode (OpenAI) as a rewrite rule. For an object schema with properties K and required set Q⊆K, strict mode needs Q=K. Each optional property k∈K∖Q of type t becomes

k:t→t∪{null},Q←K,additionalProperties←false.
"Optional" moves from "may be absent" to "always present, may be null".

Worked example
One tool, three envelopes
  • The weather tool has one required property (city) and one optional (units). OpenAI strict mode turns units into type ["string", "null"] with null added to its enum, and lists both in required.
  • The model's call get_weather(city="Tokyo") arrives as "{\"city\": \"Tokyo\"}" (a string of 17 characters) from OpenAI and as {"city": "Tokyo"} (an object) from Anthropic and Gemini. Forgetting json.loads on OpenAI, or calling it on the others, is the most common porting bug.
  • Forcing the tool: OpenAI names it in tool_choice, Anthropic uses {"type": "tool", "name": ...}, Gemini combines mode: "ANY" with allowed_function_names.
Check your mental model
  • ✗ "All three providers return tool arguments as JSON objects."
    ✓ OpenAI returns a JSON string you must parse; Anthropic and Gemini return parsed objects.
  • ✗ "Optional fields work the same in strict mode."
    ✓ OpenAI strict mode requires every field; optional ones become nullable.
  • ✗ "tool_choice: required exists everywhere."
    ✓ It is required on OpenAI, {"type": "any"} on Anthropic and mode: "ANY" on Gemini.
  • ✗ "The result goes back as a normal user message."
    ✓ It must carry the call's id: tool_call_id, tool_use_id or the functionResponse id.

See it drawn
Three envelopes, checked by the providers' own SDK types

One canonical tool is translated into OpenAI, Anthropic and Gemini declarations. Each is validated against the official Python SDKs' type definitions (openai, anthropic, google-genai), without any network call. Three hand-written responses are parsed by the SDKs' response models, reduced to one canonical call, and answered with a result message in each provider's format. A couple of seconds.

import json
from dataclasses import dataclass
from pydantic import TypeAdapter
from openai.types.chat import ChatCompletion, ChatCompletionToolParam, ChatCompletionToolMessageParam
from anthropic.types import Message, ToolParam, ToolResultBlockParam
from google.genai import types as g

@dataclass
class Tool:                                   # one canonical declaration in your own code
    name: str
    description: str
    input_schema: dict

weather = Tool("get_weather", "Use when the user asks about current weather in a city.",
               {"type": "object", "properties": {"city": {"type": "string"},
                "units": {"type": "string", "enum": ["celsius", "fahrenheit"]}},
                "required": ["city"], "additionalProperties": False})

# Translators: same content, three envelopes.
to_openai = lambda t: {"type": "function", "function": {"name": t.name, "description": t.description, "parameters": t.input_schema}}
to_anthropic = lambda t: {"name": t.name, "description": t.description, "input_schema": t.input_schema}
to_gemini = lambda t: g.Tool(function_declarations=[g.FunctionDeclaration(
    name=t.name, description=t.description, parameters_json_schema=t.input_schema)])

# Each declaration is checked against the provider SDK's own type definitions (no network).
TypeAdapter(ChatCompletionToolParam).validate_python(to_openai(weather))
TypeAdapter(ToolParam).validate_python(to_anthropic(weather))
print("declarations accepted by the openai, anthropic and google-genai SDK types\n")
for name, d in (("OpenAI", to_openai(weather)), ("Anthropic", to_anthropic(weather)),
                ("Gemini", to_gemini(weather).model_dump(exclude_none=True))):
    print(f"{name:<10}{json.dumps(d)[:150]}...")

# One response of each shape, parsed by the SDKs' response models.
oa = ChatCompletion.model_validate({"id": "chatcmpl-1", "object": "chat.completion", "created": 0, "model": "m",
    "choices": [{"index": 0, "finish_reason": "tool_calls", "message": {"role": "assistant", "content": None,
        "tool_calls": [{"id": "call_abc", "type": "function",
                        "function": {"name": "get_weather", "arguments": "{\"city\": \"Tokyo\"}"}}]}}]})
an = Message.model_validate({"id": "msg_1", "type": "message", "role": "assistant", "model": "m",
    "stop_reason": "tool_use", "usage": {"input_tokens": 1, "output_tokens": 1},
    "content": [{"type": "text", "text": "Checking."},
                {"type": "tool_use", "id": "toolu_abc", "name": "get_weather", "input": {"city": "Tokyo"}}]})
ge = g.GenerateContentResponse.model_validate({"candidates": [{"content": {"role": "model", "parts": [
    {"function_call": {"id": "fc_abc", "name": "get_weather", "args": {"city": "Tokyo"}}}]}}]})

def canonical_call(resp):                     # where the call lives, and how its arguments are typed
    if isinstance(resp, ChatCompletion):
        c = resp.choices[0].message.tool_calls[0]
        return {"id": c.id, "name": c.function.name, "args": json.loads(c.function.arguments)}   # a string!
    if isinstance(resp, Message):
        c = next(b for b in resp.content if b.type == "tool_use")
        return {"id": c.id, "name": c.name, "args": c.input}                                  # already a dict
    c = resp.candidates[0].content.parts[0].function_call
    return {"id": c.id, "name": c.name, "args": c.args}                                       # already a dict

print()
calls = {n: canonical_call(r) for n, r in (("OpenAI", oa), ("Anthropic", an), ("Gemini", ge))}
for n, c in calls.items():
    print(f"{n:<10}{c}")
print("same name and arguments everywhere:", len({json.dumps([c['name'], c['args']]) for c in calls.values()}) == 1)

# The result goes back in three different shapes, each tied to the call's id.
result = json.dumps({"city": "Tokyo", "temp": 12})
oa_msg = {"role": "tool", "tool_call_id": calls["OpenAI"]["id"], "content": result}
an_msg = {"role": "user", "content": [{"type": "tool_result", "tool_use_id": calls["Anthropic"]["id"], "content": result}]}
ge_msg = g.Content(role="user", parts=[g.Part(function_response=g.FunctionResponse(
    id=calls["Gemini"]["id"], name="get_weather", response={"result": json.loads(result)}))])
TypeAdapter(ChatCompletionToolMessageParam).validate_python(oa_msg)
TypeAdapter(ToolResultBlockParam).validate_python(an_msg["content"][0])
print("\nresult messages accepted by the SDK types:")
for n, m in (("OpenAI", oa_msg), ("Anthropic", an_msg), ("Gemini", ge_msg.model_dump(exclude_none=True))):
    print(f"{n:<10}{json.dumps(m)}")

The three declarations carry identical content. Name, description and schema are the same; only the wrapper differs: OpenAI nests them under function with parameters, Anthropic puts them at the top level with input_schema, and Gemini lists them under function_declarations, here with parameters_json_schema so the JSON Schema passes through unchanged. The parsed calls are identical. The ids differ, and they matter. call_abc, toolu_abc and fc_abc each go back with the result: as tool_call_id in a tool message, as tool_use_id in a tool_result block inside a user message, and as id in a Gemini function_response part. Gemini also wraps the result object in a response dict.

tool_choice mapping, strict mode, and caught mistakes

This block continues from the one above. It maps four tool-choice intents to each provider and validates them against the SDK types, rewrites the schema for OpenAI strict mode and checks the documented rules, and shows the SDK types rejecting two common porting mistakes. Instant.

# Continues from the block above: Tool, weather, the translators and the SDK types are defined.
import copy, json
from pydantic import TypeAdapter, ValidationError
from openai.types.chat import ChatCompletionToolChoiceOptionParam
from anthropic.types import ToolChoiceParam

# 1. tool_choice: one canonical intent, three spellings (each checked against the SDK types).
def choice(mode, name=None):
    oa = {"auto": "auto", "any": "required", "none": "none",
          "force": {"type": "function", "function": {"name": name}}}[mode]
    an = {"auto": {"type": "auto"}, "any": {"type": "any"}, "none": {"type": "none"},
          "force": {"type": "tool", "name": name}}[mode]
    ge = g.ToolConfig(function_calling_config=g.FunctionCallingConfig(
        mode={"auto": "AUTO", "any": "ANY", "none": "NONE", "force": "ANY"}[mode],
        allowed_function_names=[name] if mode == "force" else None))
    TypeAdapter(ChatCompletionToolChoiceOptionParam).validate_python(oa)
    TypeAdapter(ToolChoiceParam).validate_python(an)
    return oa, an, ge.function_calling_config.model_dump(exclude_none=True)
for mode in ("auto", "any", "none", "force"):
    oa, an, ge = choice(mode, "get_weather")
    print(f"{mode:<6} OpenAI {json.dumps(oa)}\n       Anthropic {json.dumps(an)}\n       Gemini {json.dumps(ge)}")

# 2. Strict mode on OpenAI: every property required, optional ones made nullable, no extra keys.
def strictify(schema):
    s = copy.deepcopy(schema)
    if s.get("type") == "object":
        props = s.get("properties", {})
        for k, v in props.items():
            if k not in s.get("required", []):
                v["type"] = [v["type"], "null"]          # optional -> required but may be null
                if "enum" in v:
                    v["enum"] = v["enum"] + [None]
            props[k] = strictify(v)
        s["required"] = list(props); s["additionalProperties"] = False
    return s
strict = strictify(weather.input_schema)
print("\nOpenAI strict version of the schema:\n" + json.dumps(strict))

def check_openai_strict(s, depth=1):
    """The documented limits: objects need additionalProperties false and every property required;
    at most 10 levels of nesting (5000 properties and 1000 enum values overall are not checked here)."""
    problems = []
    if depth > 10: problems.append("more than 10 levels of nesting")
    if s.get("type") == "object" or "object" in (s.get("type") or []):
        if s.get("additionalProperties") is not False: problems.append("additionalProperties must be false")
        missing = set(s.get("properties", {})) - set(s.get("required", []))
        if missing: problems.append(f"not required: {sorted(missing)}")
        for v in s.get("properties", {}).values():
            problems += check_openai_strict(v, depth + 1)
    return problems
print("original schema, strict problems:", check_openai_strict(weather.input_schema))
print("strictified schema, strict problems:", check_openai_strict(strict))

Reading this output

Four intents, three vocabularies. "Must call a tool" is "required" on OpenAI, {"type": "any"} on Anthropic and mode: "ANY" on Gemini. "Call this tool" is a named object on OpenAI and Anthropic, and ANY plus allowed_function_names on Gemini. All of them passed the SDK type checks.

Strict mode rewrites optional fields. The original schema fails OpenAI's strict rules because units is not in required. The rewritten version lists both fields, makes units nullable (type ["string", "null"], with null added to the enum) and passes. The executor must now treat null as "use the default".

The SDK types catch porting mistakes before a request is sent. An Anthropic tool declared with OpenAI's parameters field is rejected because input_schema is missing, and an OpenAI tool result without tool_call_id is rejected. Running your translated payloads through these types in a unit test costs nothing and catches the most common porting bugs.

Idea 5 · Parallel calls

OpenAI's parallel_tool_calls (on by default) emits multiple calls in one assistant message; you run them and reply with one tool message per tool_call_id. Claude also calls tools in parallel by default; disable_parallel_tool_use: true limits it to one call, and all tool_result blocks go back in a single user message. Gemini returns several functionCall parts in one turn, each with an id you echo in the matching functionResponse.

Idea 6 · Streaming

All three support streamed tool calls. The wire format differs:

  • OpenAI. Delta chunks of tool_calls[i].function.arguments arrive incrementally. You accumulate until finish_reason: "tool_calls".
  • Anthropic. Block-start / block-delta / block-stop events. input_json_delta chunks carry partial arguments.
  • Gemini. Function calls normally arrive whole in a streamed chunk. Streaming one call's arguments in pieces (stream_function_call_arguments, returned in partial_args) is a Vertex AI option; the Gemini API does not support it.

Phase 13 · 03 goes deep on parallel + streaming reassembly. This lesson focuses on the declaration and single-call shapes.

Idea 7 · Errors and repair

Invalid-argument errors look different too.

  • OpenAI (non-strict). Model returns arguments: "{bad json}", your JSON parse fails, you inject an error message and re-call.
  • OpenAI (strict). Validation happens during decoding; invalid JSON is impossible but refusal can appear.
  • Anthropic (non-strict). input may contain unexpected fields; the schema is advisory. Validate server-side. With strict: true, sampling is constrained to the schema.
  • Gemini. Unless mode: "VALIDATED" is set, arguments are not guaranteed to match the schema; validate them yourself.

Idea 8 · The translator pattern

A canonical tool declaration in your code looks like this (you pick the shape):

Tool(
    name="get_weather",
    description="Use when ...",
    input_schema={"type": "object", "properties": {...}, "required": [...]},
    strict=True,
)

Three tiny functions translate it to the three provider shapes. The harness in code/main.py does exactly this, then round-trips a fake tool call through each provider's response shape. No network required — this lesson teaches the shapes, not the HTTP.

Production teams usually let a library do this: LangChain's bind_tools, Pydantic AI's toolsets, LlamaIndex's BaseTool, or LiteLLM, which accepts OpenAI-format tools and translates them for other providers. Industry practice
What's current (2024–2026)
  • OpenAI: the Responses API returns function_call items (with call_id and string arguments) and takes function_call_output items back; Chat Completions keeps tool_calls. strict: true uses Structured Outputs for arguments.
  • Anthropic: tool_use / tool_result blocks, parallel calls by default, opt-in strict tool use, and a tool search tool for large tool catalogs.
  • Google: generateContent with functionDeclarations (and parametersJsonSchema), VALIDATED mode, thought signatures on Gemini 3; the newer Interactions API uses function_call / function_result steps.
  • Translation layers in production: LiteLLM, LangChain's bind_tools, Pydantic AI and Vercel's AI SDK accept one tool definition and handle every provider's envelope.
  • MCP removes much of this work for tools that live in servers: the client adapts MCP tool lists to whichever model API it calls (Lesson 13.6).

Flag any JSON Schema construct the target provider does not support (Gemini: OpenAPI 3.0 subset; OpenAI strict: no `$ref`, no ambiguous `oneOf`).
2. Response diff. Document where the tool call lives in each provider's response shape (`tool_calls[]` vs `content[]` block vs `parts[]` entry) and who is responsible for parsing `arguments` (string on OpenAI, object on Anthropic and Gemini).
3. `tool_choice` diff. Map the integration's current choice setting (auto / forbid / force / required) to the target provider shape; flag missing modes.
4. Limit collisions. Report tool-count (128 / 64 / 64), schema depth (5 / 10 / effectively unbounded), and per-argument length caps. Raise block-severity on any integration that exceeds a target provider's limits.
5. Strict-mode mapping. State whether strict-mode semantics are preserved on the target. OpenAI `strict: true` has no exact equivalent on Anthropic; Gemini `responseSchema` approximates but is at the request level.

Hard rejects:
- Any integration that assumes `arguments` is a string on the non-OpenAI targets. Will silently produce wrong results.
- Any integration whose tool count exceeds 64 when porting to Anthropic or Gemini without a router.
- Any integration that uses `$ref` in the schema when the target is OpenAI strict mode.

Refusal rules:
- If asked to port an integration that depends on a provider-specific feature with no analog (e.g. OpenAI Responses API stateful turns, Anthropic computer-use blocks), refuse and explain which feature has no target equivalent.
- If asked to pick a winner, refuse. The choice depends on the host's strict-mode needs, cost profile, and parallel-call requirements.

Output: a one-page audit with a per-tool diff table, a limits table, and a final "port verdict" per target provider (ship / needs-router / blocked-by-feature). End with one sentence naming the highest-leverage migration change.

Exercises

  1. Run code/main.py and verify that the three provider declaration JSONs all serialize the same underlying Tool object. Modify the canonical tool to add an enum parameter and confirm only the Gemini translator needs to handle the OpenAPI quirk.

  2. Add a ListToolsResponse parser for each provider that extracts the tool list a model returns after a list_tools or discovery call. OpenAI does not have one natively; note this asymmetry.

  3. Implement tool_choice conversion: map a canonical ToolChoice(mode="force", tool_name="x") into all three provider shapes. Then map mode="any" and mode="none". Check the lesson's diff table.

  4. Pick one of the three providers and read its function-calling guide end to end. Find one field in its schema spec that the other two do not support. Candidates: OpenAI strict, Anthropic disable_parallel_tool_use, Gemini function_calling_config.allowed_function_names.

Solutions

SolutionP1 · Identical calls, once the string is parsed

Yes, once OpenAI's argument string is parsed with json.loads: all three give get_weather with {"city": "Tokyo"}. Only the ids differ (call_abc, toolu_abc, fc_abc), and each must be echoed in that provider's result message.

None of the translated pieces in the first run was rejected, because each translator was written for its provider. The pieces most likely to go wrong in real ports are the ones in the second run: a declaration with the wrong schema field name, and a result message without the call's id. Both fail the SDK type checks immediately.

SolutionB1 · A TypeError, then a lost parallel result

json.loads(block.input) raises TypeError: the JSON object must be str, bytes or bytearray, not dict. Anthropic's input is already a parsed object; only OpenAI sends a string. The fix is to parse per provider (as canonical_call does), never in shared code.

The step that is easy to miss with parallel calls: on OpenAI each result is its own tool message, one per tool_call_id. On Anthropic, all the tool_result blocks for one assistant turn must go back together, in a single user message, each with its tool_use_id. Sending them as two separate user messages, or answering only one call, makes the API reject the request or confuses the model about which result belongs to which call. Gemini likewise expects one functionResponse per functionCall id. A port is finished only when parallel calls are tested.
