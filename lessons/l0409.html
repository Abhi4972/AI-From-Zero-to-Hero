Lesson 4.5 used vector search as a black box with nine chunks. At nine chunks, comparing the query with every vector is instant. At nine hundred million, it is the most expensive part of your system, and the index settings decide both your bill and your recall. This lesson opens the box with FAISS, the open-source library from Meta that many vector databases build on, so you can see exactly what the settings in pgvector, OpenSearch, Qdrant, Milvus, S3 Vectors or Azure AI Search are doing.

uv add faiss-cpu numpy        # tested with faiss-cpu 1.15
Why this came about

Comparing a query with every stored vector is too slow for millions of documents. Approximate nearest-neighbor indexes (HNSW, IVF, quantization), developed for image and recommendation search, were adopted by vector databases, which boomed with RAG in 2023.

In plain words first
How to find the nearest neighbors fast

Comparing a query with every stored vector is exact but slow at millions of vectors. Vector indexes trade a little accuracy for a lot of speed: graph-based indexes (HNSW) hop between nearby points, cluster-based ones (IVF) search only the closest clusters, and quantization shrinks vectors to save memory. Each has settings that move the balance between speed, memory and recall.

Step 1 · Exact search, and the ground truth for everything else

Exact (brute-force, "flat") search compares the query with every vector. It is the reference that every faster index is measured against. With normalized vectors, the inner product equals cosine similarity.

import numpy as np, faiss

faiss.omp_set_num_threads(1)                                     # single-threaded so counts are reproducible
rng = np.random.default_rng(0)
n, d, n_queries = 20_000, 64, 200
centers = rng.normal(size=(50, d)).astype("float32")              # real embeddings cluster by topic; so do these
X = (centers[rng.integers(0, 50, n)] + 0.5 * rng.normal(size=(n, d))).astype("float32")
Q = (centers[rng.integers(0, 50, n_queries)] + 0.5 * rng.normal(size=(n_queries, d))).astype("float32")
faiss.normalize_L2(X); faiss.normalize_L2(Q)                     # unit length: inner product == cosine

flat = faiss.IndexFlatIP(d)
flat.add(X)
_, TRUE = flat.search(Q, 10)                                      # exact top-10 for every query

def recall(I) -> float:
    """Share of the exact top-10 that an approximate index also returned."""
    return float(np.mean([len(set(a) & set(b)) / 10 for a, b in zip(I, TRUE)]))

print("flat index:", flat.ntotal, "vectors;", n, "comparisons per query; recall", recall(TRUE))
What you should see
flat index: 20000 vectors; 20000 comparisons per query; recall 1.0
Distance Formula idea Use when
Cosine Angle between vectors Text embeddings (the default); equals inner product after normalization
Inner product (dot) Sum of products Normalized vectors, or models trained for dot product
Euclidean (L2) Straight-line distance Some image and older models; check the model card

Use the metric the embedding model was trained with. Mixing them (L2 on vectors meant for cosine, unnormalized) quietly lowers recall.

Step 2 · IVF: search only the nearest clusters

An inverted file index (IVF) clusters the vectors with k-means into nlist lists. A query is compared with the cluster centres, then only with the vectors in the nprobe closest clusters. More probes, more recall, more work.

ivf = faiss.IndexIVFFlat(faiss.IndexFlatIP(d), d, 128, faiss.METRIC_INNER_PRODUCT)   # nlist = 128 clusters
ivf.train(X)                                                      # k-means on the data
ivf.add(X)
for nprobe in (1, 8, 32):
    ivf.nprobe = nprobe
    faiss.cvar.indexIVF_stats.reset()
    _, I = ivf.search(Q, 10)
    print(f"IVF nprobe={nprobe:2}: recall {recall(I):.3f}, ~{faiss.cvar.indexIVF_stats.ndis / n_queries:,.0f} comparisons per query")
What you should see
IVF nprobe= 1: recall 0.665, ~232 comparisons per query
IVF nprobe= 8: recall 1.000, ~1,400 comparisons per query
IVF nprobe=32: recall 1.000, ~5,213 comparisons per query

With one probe the index compares about 1% of the vectors and misses a third of the true neighbors; eight probes get essentially everything at 7% of the work. A common starting point is nlist near the square root of the number of vectors and nprobe tuned for the recall you need. IVF needs training data that looks like the data you will add, and re-training when the distribution drifts.

Step 3 · HNSW: navigate a graph

HNSW (hierarchical navigable small world) links each vector to its nearest neighbors in a layered graph. A search enters at the top layer and greedily walks toward the query, layer by layer. It is the default index in pgvector, OpenSearch, Elasticsearch, Qdrant, Weaviate, Milvus and most managed services, because it gives high recall at low latency without training.

Setting Meaning Effect
M Links per node Higher: better recall, more memory
efConstruction Candidates considered while building Higher: better graph, slower build
efSearch (ef_search) Candidates considered per query The main runtime knob: recall versus latency 
hnsw = faiss.IndexHNSWFlat(d, 16, faiss.METRIC_INNER_PRODUCT)    # M = 16
hnsw.hnsw.efConstruction = 64
hnsw.add(X)
for ef in (16, 64, 256):
    hnsw.hnsw.efSearch = ef
    faiss.cvar.hnsw_stats.reset()
    _, I = hnsw.search(Q, 10)
    print(f"HNSW efSearch={ef:3}: recall {recall(I):.3f}, ~{faiss.cvar.hnsw_stats.ndis / n_queries:,.0f} comparisons per query")
What you should see
HNSW efSearch= 16: recall 0.920, ~285 comparisons per query
HNSW efSearch= 64: recall 0.999, ~447 comparisons per query
HNSW efSearch=256: recall 1.000, ~557 comparisons per query

HNSW reaches near-perfect recall while touching about 2% of the collection, and the work grows slowly with efSearch. Its costs are memory (the graph links add to every vector) and slow, memory-hungry builds and deletes on very large collections, which is why IVF and disk-based indexes (DiskANN, used in Azure Cosmos DB and others) remain common at billion scale.

Step 4 · Quantization: smaller vectors, then rescore

Vectors are usually stored as 32-bit floats: a 1,536-dimension embedding is 6 KB, and a hundred million of them is 600 GB before any index. Quantization compresses them:

Method Size per value How Typical recall impact
float32 4 bytes None Reference
float16 / bfloat16 2 bytes Lower precision Negligible
Scalar quantization (int8) 1 byte Map each dimension's range to 256 levels Small
Product quantization (PQ) Fractions of a byte Split the vector into sub-vectors, store the nearest of 256 learned centroids for each Large without rescoring
Binary 1 bit Keep only the sign of each dimension Large without rescoring

The standard pattern is compress for the first pass, rescore with full vectors: search a compressed index for many candidates, then re-rank the shortlist with exact distances (FAISS calls it refinement; OpenSearch, Qdrant and Elasticsearch call it rescoring or oversampling).

def bytes_per_vector(index) -> float:
    return faiss.serialize_index(index).size / index.ntotal

sq8 = faiss.IndexScalarQuantizer(d, faiss.ScalarQuantizer.QT_8bit, faiss.METRIC_INNER_PRODUCT)
sq8.train(X); sq8.add(X)
pq = faiss.IndexIVFPQ(faiss.IndexFlatIP(d), d, 128, 16, 8, faiss.METRIC_INNER_PRODUCT)   # 16 sub-vectors x 8 bits
pq.train(X); pq.nprobe = 16
refined = faiss.IndexRefineFlat(pq)                              # wraps PQ and keeps full vectors to rescore a shortlist
refined.add(X)                                                   # adds to both the PQ index and the full-vector store
refined.k_factor = 10                                            # fetch 10x candidates from PQ, rescore exactly

for name, index in [("flat float32", flat), ("int8 scalar", sq8), ("IVF-PQ", pq), ("IVF-PQ + rescore", refined)]:
    _, I = index.search(Q, 10)
    print(f"{name:17} recall {recall(I):.3f}   ~{bytes_per_vector(index):6.1f} bytes per vector")
What you should see
flat float32      recall 1.000   ~ 256.0 bytes per vector
int8 scalar       recall 0.950   ~  64.0 bytes per vector
IVF-PQ            recall 0.463   ~  29.0 bytes per vector
IVF-PQ + rescore  recall 0.979   ~ 285.0 bytes per vector

int8 cuts memory by 4x for a small recall loss. PQ cuts it by 10x but, alone, finds less than half the true neighbors; rescoring a 10x shortlist with full vectors brings recall back to almost perfect. The rescoring copy can live on cheaper storage (SSD or object storage) while the compressed index stays in memory, which is how large managed services keep costs down.

Step 5 · The filtering trap

Real queries filter: this tenant's documents, this language, documents the user may read (Lesson 4.8). There are two ways to combine a filter with approximate search, and one of them silently loses results:

  • Post-filtering: find the top k, then drop those that fail the filter. If the filter is selective, few or none survive.
  • Filtered search: apply the filter during the index walk, so only matching vectors are returned. Engines support it (pgvector iterative scans, Qdrant payload indexes, OpenSearch efficient filtering, Pinecone metadata filters, FAISS ID selectors), but a graph index still struggles when very few nodes match.
  • Exact scan of the matching subset: when the filter leaves few vectors, skip the index and compare against all of them. Good engines switch to this automatically below a selectivity threshold.
tenant = rng.integers(0, 100, n)                                   # 100 tenants, about 200 vectors each
ME = 7

hnsw.hnsw.efSearch = 64
_, top = hnsw.search(Q, 10)
post = [[i for i in row if tenant[i] == ME] for row in top]      # post-filter the global top 10

mine = np.where(tenant == ME)[0]
exact_mine = faiss.IndexFlatIP(d); exact_mine.add(X[mine])
_, J = exact_mine.search(Q, 10)                                    # exact search over only this tenant's vectors
truth = [set(mine[row]) for row in J]
def filtered_recall(rows): return np.mean([len({x for x in r if x >= 0} & t) / 10 for r, t in zip(rows, truth)])

sel = faiss.IDSelectorBatch(mine.astype("int64"))
for ef in (64, 1024):
    _, pre = hnsw.search(Q, 10, params=faiss.SearchParametersHNSW(sel=sel, efSearch=ef))   # filter inside the graph walk
    print(f"filtered HNSW, efSearch={ef:4}: recall {filtered_recall(pre):.2f}")
print(f"post-filter of the global top 10: recall {filtered_recall(post):.2f}")
print(f"exact scan of the {len(mine)} matching vectors: recall 1.00 ({len(mine)} comparisons per query)")
What you should see
filtered HNSW, efSearch=  64: recall 0.35
filtered HNSW, efSearch=1024: recall 0.95
post-filter of the global top 10: recall 0.01
exact scan of the 203 matching vectors: recall 1.00 (203 comparisons per query)

With a filter that keeps 1% of the data, post-filtering returned almost nothing: a tenant would see "no results" for questions their own documents answer, the most common production vector-search bug. Filtered HNSW does better but needs a much larger efSearch, because the graph walk passes through many non-matching nodes. For a small matching set, an exact scan of those 203 vectors is both perfect and cheap. Test your store with your most selective real filters, check how it plans filtered queries, and for large tenants use separate indexes or namespaces so the problem never arises.

Step 6 · Sizing memory and cost

Before you choose a store, do the arithmetic. It decides whether the index fits in memory, which instance class you need, and whether object-storage-based stores (S3 Vectors, Turbopuffer, LanceDB on object storage) are worth their slower cold queries.

def index_memory_gb(n_vectors: int, dims: int, bytes_per_value: float = 4, hnsw_m: int = 16,
                    metadata_bytes: int = 200) -> float:
    """Rough in-memory size of an HNSW index: vectors + graph links + metadata."""
    vectors = n_vectors * dims * bytes_per_value
    graph = n_vectors * hnsw_m * 2 * 4                      # about 2*M neighbour ids of 4 bytes at the base layer
    return round((vectors + graph + n_vectors * metadata_bytes) / 1e9, 1)

for n_vec, dims, bpv, label in [(10_000_000, 1536, 4, "10M x 1536, float32"),
                                (10_000_000, 1536, 1, "10M x 1536, int8"),
                                (10_000_000, 256, 4, "10M x 256 (Matryoshka-shortened), float32"),
                                (500_000_000, 1024, 1, "500M x 1024, int8")]:
    print(f"{label:42} ~{index_memory_gb(n_vec, dims, bpv):7,.1f} GB")
What you should see
10M x 1536, float32                        ~   64.7 GB
10M x 1536, int8                           ~   18.6 GB
10M x 256 (Matryoshka-shortened), float32  ~   13.5 GB
500M x 1024, int8                          ~  676.0 GB

Two levers dominate: fewer dimensions (Matryoshka embeddings, Lesson 4.5, let you shorten vectors) and fewer bytes per dimension (quantization). Ten million documents fit comfortably on one large Postgres or OpenSearch node with either lever; half a billion needs quantization plus a distributed or disk-based store.

pgvector in production

Most teams' first production vector store is Postgres with pgvector, because it adds vectors to a database they already run, with SQL filters, joins, transactions and backups.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id          bigserial PRIMARY KEY,
  tenant_id   int      NOT NULL,
  doc_id      text     NOT NULL,
  content     text     NOT NULL,
  embedding   vector(1024) NOT NULL,          -- or halfvec(1024) for 2-byte storage
  acl_groups  text[]   NOT NULL,
  updated_at  timestamptz DEFAULT now()
);

-- HNSW index for cosine distance; m and ef_construction as in Step 3
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
CREATE INDEX ON chunks (tenant_id);

-- Query time: recall knob, and iterative scans so filters do not starve the results (pgvector 0.8+)
SET hnsw.ef_search = 80;
SET hnsw.iterative_scan = relaxed_order;

SELECT id, content, 1 - (embedding <=> $1) AS cosine_similarity
FROM chunks
WHERE tenant_id = $2 AND acl_groups && $3           -- tenant isolation and permissions inside the query
ORDER BY embedding <=> $1
LIMIT 10;

Hybrid search in Postgres pairs this with full-text search (tsvector with a GIN index, or the BM25 extensions such as ParadeDB's pg_search) and fuses the two lists with RRF in SQL or application code.

Operating a vector index

  • Version indexes and switch with an alias. Changing the embedding model, dimensions or chunking means a full re-index; build the new index beside the old one, evaluate it, then move the alias.
  • Measure recall continuously. Sample a few hundred real queries, compute the exact top-k offline, and track the index's recall against it after every parameter change or growth milestone.
  • Plan for deletes. HNSW deletions leave tombstones that degrade the graph; schedule compaction or rebuilds, and verify that deleted documents really disappear (Lesson 4.8).
  • Back up the source, not just the index. Keep chunks and embeddings in durable storage (a table or object store), so an index can always be rebuilt.
  • Watch the usual database metrics: memory headroom, p95 latency per filter type, ingestion lag, and the "no results" rate per tenant.
Industry practice
What experienced teams say about vector databases

The consistent advice from practitioners is that the choice of vector database matters less than chunking, hybrid search, filtering and evaluation. Start with the store you already operate (very often Postgres or OpenSearch, or your data platform's native search), measure recall and latency on your own data, and move to a dedicated engine only when a measured limit forces it: scale, filtering performance or cost.

In production
Design a vector index right from day one

Store chunks, metadata and embeddings in durable storage you control (a table or object store), so any index can be rebuilt. Record the embedding model and version with every vector. Put tenant and permission fields on every record and test the most selective filter you will run. Build new indexes beside old ones and switch with an alias. Track recall against exact search on a few hundred real queries, and re-check it at every growth milestone.

Solutions

SolutionP1 · The recall-latency dial

Recall rises toward exact search and latency rises, because the search explores more of the graph. The right value is the smallest that meets your recall target at your latency budget, measured against exact search as ground truth.

SolutionB1 · Quantization needs rescoring

Recall drops, because compressed distances misorder close candidates. Rescoring the top candidates with the original vectors restores most of it at a small cost, which is why production systems keep full vectors for rescoring.

SolutionD1 · The filtering trap

Filtering after the graph search discards most candidates, and the graph walk may not reach enough matching vectors. Fixes: filter during traversal (filtered HNSW), raise ef_search for filtered queries, or keep a separate index or partition for the rare category.

SolutionM1 · Size before you buy

Float32: 50M × 1,024 × 4 bytes ≈ 205 GB, plus graph overhead. 8-bit in memory: about 51 GB plus the graph, with full vectors on disk for rescoring. The difference decides between one large machine and a cluster.

Check your understanding

Explain the mechanismHow do IVF and HNSW indexes work, and what are their trade-offs?

Worked answer. IVF clusters vectors and searches only the nearest clusters (nprobe controls how many), which is memory-efficient and fast to build. HNSW builds a layered proximity graph and walks it (ef_search controls breadth), giving high recall at low latency with more memory and slower builds. Both trade recall for speed, and both are tuned against exact search.

A plausible wrong answer. "HNSW is always better." It uses more memory and handles deletes and filters less gracefully.

Follow-ups. When is exact search good enough?

Debug a failureRecall dropped after the index was rebuilt with the same data. What do you check?

Worked answer. The build and search parameters (M, ef_construction, ef_search, nlist, nprobe), the distance metric, whether vectors were normalized the same way, and whether the embedding model version changed. Compare against exact search on a sample to measure recall directly.

A plausible wrong answer. "Approximate search is random." It is deterministic enough to measure and tune.

Follow-ups. How would you monitor recall in production?

Defend a designpgvector in your existing Postgres, or a dedicated vector database?

Worked answer. pgvector when the corpus fits (millions, not billions), you want transactions, joins and permissions in one place, and the team already runs Postgres. A dedicated store for very large scale, heavy filtered search, multi-tenant isolation features or managed scaling. Measure recall and latency on your data.

A plausible wrong answer. "Dedicated vector databases are faster, so always use one." Operational simplicity often matters more at moderate scale.
