About the model on this page
What ran, and where

The server on this page is the real LangGraph development server, run locally with langgraph dev and its in-memory runtime; the client code below ran against it. The graph needs no model. LangSmith Studio and LangSmith Deployment need an account and were not used here.

Why this came about

Running a graph in a notebook is easy; serving it to many users is not. LangGraph Platform (2024), now LangSmith Deployment with Agent Server, packaged the API, persistence, queues and streaming that every team was rebuilding.

The problem: a graph in a script is not a service

Everything in this block so far ran inside one Python process. A support desk needs more: an HTTP API the website and the approval dashboard can call, threads stored in a database, runs that continue in the background after the request returns, streaming to browsers, a policy for a customer who sends a second message while the first is still running, scheduled runs, authentication, and more than one worker. You could build those around a graph yourself, with FastAPI, PostgresSaver and a task queue. LangGraph's server runtime, called Agent Server in current docs (formerly LangGraph Server), provides them for any graph.

In plain words first
From a script to a service

In a notebook, your graph lives inside one Python process and stops when you close it. As a service it must answer many users over HTTP, keep each conversation in a database, queue and stream runs, survive restarts and know who is calling. Agent Server wraps your compiled graph with all of that; Studio is a visual debugger for it, and LangSmith records traces. You supply the graph and a small configuration file.

Idea 1 · Package the graph

The refund approval graph from Lesson 14.63, in a file agent.py:

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt

class RefundState(TypedDict, total=False):
    order_id: str
    amount: int
    approved: bool
    done: str

def approval(state):
    if state["amount"] <= 5000:
        return {"approved": True}
    return {"approved": interrupt({"question": "Approve this refund?", **state})}

def finish(state):
    return {"done": f"refunded INR {state['amount']:,}" if state["approved"] else "declined"}

b = StateGraph(RefundState)
b.add_node("approval", approval); b.add_node("finish", finish)
b.add_edge(START, "approval"); b.add_edge("approval", "finish"); b.add_edge("finish", END)
graph = b.compile()                     # no checkpointer: the server provides persistence

And a langgraph.json that tells the server where the graph is:

{
  "dependencies": ["."],
  "graphs": {"refunds": "./agent.py:graph"},
  "env": {}
}

Then start a local development server:

uv add "langgraph-cli[inmem]"
langgraph dev            # API on http://127.0.0.1:2024, with an in-memory runtime and hot reload

Note the last line of agent.py: the graph is compiled without a checkpointer, because the server provides persistence for every thread. env lists environment variables or points to a .env file, which is where model API keys go; dependencies lists what to install; you can register several graphs under different IDs.

Idea 2 · Call it over HTTP

The langgraph-sdk client (Python and JavaScript) wraps the server's REST API. This ran against the local server, on port 2077:

from langgraph_sdk import get_sync_client

client = get_sync_client(url="http://127.0.0.1:2077")      # your deployment's URL (and an API key) in production
thread = client.threads.create()
run = client.runs.wait(thread["thread_id"], "refunds", input={"order_id": "A-1077", "amount": 7999})
print("paused with:", run["__interrupt__"][0]["value"])
print("next:", client.threads.get_state(thread["thread_id"])["next"])

final = client.runs.wait(thread["thread_id"], "refunds", command={"resume": True})
print("after resume:", final["done"])

for chunk in client.runs.stream(None, "refunds", input={"order_id": "A-1080", "amount": 1200}, stream_mode="updates"):
    if chunk.event == "updates":
        print("update:", chunk.data)
What you should see
paused with: {'question': 'Approve this refund?', 'order_id': 'A-1077', 'amount': 7999}
next: ['approval']
after resume: refunded INR 7,999
update: {'approval': {'approved': True}}
update: {'finish': {'done': 'refunded INR 1,200'}}

The concepts are the ones you know, now behind an API. A thread holds a conversation's checkpoints. A run executes the graph on a thread. An interrupt ends a run with its payload, and a new run with command={"resume": ...} continues it, exactly like Command(resume=...) in Lesson 14.63. Streaming offers the stream modes of Lesson 14.65 as server-sent events. runs.wait blocks until the run ends; runs.create starts a background run and returns at once, which is what an API handler should do for anything slow. The last call passed None as the thread: a stateless run with no saved history.

Idea 3 · What the server adds

Feature What it does Without the server, you build
Threads and persistence Every thread's checkpoints, in Postgres in production PostgresSaver, schema, cleanup
Background runs and a task queue Runs continue after the request; workers scale out A queue such as Celery or SQS, and workers
Double-texting strategies A new message on a busy thread is rejected, queued, interrupts the current run, or rolls it back Locks per thread and your own policy
Streaming over HTTP Server-sent events for every stream mode, with reconnection An SSE endpoint per graph
Assistants Named configurations of one graph (model, prompt, tools) without new code Config management
Store The long-term memory store (Lesson 14.64), with semantic search PostgresStore and pgvector
Cron jobs and webhooks Scheduled runs; a callback when a run finishes A scheduler and callbacks
Custom authentication A handler that checks each request and scopes threads per user Middleware and per-user filters

Idea 4 · Debugging with Studio, history and traces

LangSmith Studio connects to a running server, local or deployed, and shows the graph, each run step by step, the state at every checkpoint, and interrupts waiting for an answer; you can edit state and rerun from a checkpoint, the time travel of Lesson 14.62 with a UI. Without Studio, the same information is in the API: client.threads.get_history(thread_id) returns every checkpoint of a thread (for a run paused at approval, two snapshots: before the start, and paused at approval). With tracing on (Lesson 14.58), each run's trace shows the model and tool calls inside the nodes. The usual order when a production run goes wrong: find the thread, read its history to see where it went off course, open the trace for that step, then fork from the checkpoint before it with a fix.

Running it in production

Option What it is Fits
LangSmith Deployment, cloud Managed Agent Server, Postgres and queue; deploy from a Git repository Teams that want no infrastructure work
LangSmith Deployment, hybrid or self-hosted The same server in your own cloud account or cluster Data residency, enterprise networks
Standalone server container langgraph build produces a Docker image you run with your own Postgres and Redis Full control; check the license terms for production use
Your own service FastAPI or similar around the graph, with PostgresSaver and your own queue No platform dependency; you build Idea 3's table yourself

The deciding questions are which of Idea 3's features you need, where data must live, and who will run it. The graph code is the same in every option, which is the main reason to keep platform concerns out of nodes.

Debugging exercise
Debugging exercise: works as a script, fails on the server

A graph whose nodes call ChatAnthropic works when run as a script, but every run on the local server fails with an authentication error. The team's langgraph.json has "env": {}, and the developer exported the key in another terminal. Find the cause and fix it. (Solution D1.)

Make it your own

Solutions

SolutionP1 · Input starts a new run

Sending input to a thread starts a new run from START, as in Lesson 14.63: the graph runs again, reaches approval, and pauses with a new interrupt. Nothing is approved. Approvals must be sent as command={"resume": ...}.

SolutionB1 · At start-up

The server loads every graph listed in langgraph.json when it starts, so a missing file or a wrong attribute name fails at start-up with an error naming the path, before any request arrives. That is a useful property: a bad deploy fails at once instead of on a customer's first message. Add a CI step that imports each graph, or starts the server, before deploying.

SolutionD1 · The server has its own environment

The server process does not see variables exported in another terminal, and "env": {} gives it none, so ChatAnthropic finds no ANTHROPIC_API_KEY. Put the key in a .env file that is not committed and point langgraph.json at it with "env": ".env"; in a deployment, set it as a secret in the platform. Check the server's own log or a test run, not your shell.

SolutionM1 · Two graphs, one server

Add "tracking": "./tracking.py:graph" under graphs, restart langgraph dev, and call client.runs.wait(None, "tracking", input={"messages": [{"role": "user", "content": "Where is A-1001?"}]}). client.assistants.search() then lists both graph IDs. Each graph has its own threads; they share the server's workers and store.

Check your understanding

Explain the mechanismHow would you deploy a LangGraph agent, and what does the server runtime give you?

Worked answer. Package the graph with a langgraph.json naming it, its dependencies and its environment; test it locally with langgraph dev; then deploy it to LangSmith Deployment (cloud, hybrid or self-hosted) or run the server container myself. The runtime gives threads with persistent checkpoints, foreground and background runs with a task queue, streaming over server-sent events, interrupts and resume over the API, policies for concurrent messages on a thread, assistants for configuration variants, the long-term store, cron jobs, webhooks and pluggable authentication. The alternative is building those around the graph with FastAPI, a Postgres checkpointer and a queue.

A plausible wrong answer. "Wrap graph.invoke in a FastAPI endpoint." That works for a demo, but runs block the request, approvals have no resume path, and concurrent messages on one thread can corrupt its state.

Follow-ups. What should happen when a customer sends a second message while the first run is still going?

Debug a failureA deployed agent occasionally answers a different question from the one the customer just asked. What do you check?

Worked answer. Concurrency on the thread first: if the customer sent two messages quickly, two runs may have overlapped; check the thread's history and set an explicit double-texting strategy, such as interrupting the current run or queuing the new one. Then thread identity: the client must map each conversation to its own thread ID and never reuse one across customers. Then store namespaces (Lesson 14.64). The thread history and the trace together show which run produced the answer.

A plausible wrong answer. "The model hallucinated." The answer was right for some question; the plumbing delivered it to the wrong one.

Follow-ups. How would you test double-texting behavior before launch?

Defend a designManaged LangSmith Deployment, or self-hosting your own service?

Worked answer. Managed when the team wants to ship agents rather than run infrastructure, and the data can live in the provider's cloud or the hybrid option covers residency: queues, persistence, scaling and Studio come working. Self-hosted, the server container or my own service, when data residency, network isolation, cost at scale or an existing platform team make it the better fit; then I own upgrades, Postgres, scaling and on-call. Because the graph code is the same either way, I start where the team can move fastest and keep nodes free of platform assumptions.

A plausible wrong answer. "Always self-host to avoid lock-in." The graph is portable; the real cost of self-hosting is the platform work in Idea 3's table.
