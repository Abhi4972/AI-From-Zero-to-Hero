In plain words first
The idea in one line

The agent that wrote the code cannot grade it. A reviewer is a second loop with a different system prompt, a different goal, and read-only access to everything the builder produced. The gap between builder and reviewer is where most reliability lives.

Terms you'll hear

Soft fail "Needs revisions" Total below 7; builder gets findings to address

The problem

In plain words first

A reviewer agent is a second pass in a different role: it reads the change, the state, the test results and the gate's verdict, scores the work on a rubric, and writes a report. It cannot edit anything. Its job is what a gate cannot do: ask whether the tests prove the goal or only a weaker version of it. Human approvals and handoffs are covered in Zero to Agents 12.16 and 3.12 (linked above); this lesson tests the lesson's rubric scorer and a model in the reviewer role on six real fixes.

You ask the agent to fix a bug. It edits four files, runs the tests, and reports done. The verification gate (Phase 14 · 38) confirms acceptance ran and scope held. The gate says passed: true. You merge. Two days later you find that the fix solved the wrong half of the bug.

Acceptance is necessary, not sufficient. The reviewer asks the questions acceptance cannot ask: did this solve the right problem? Did it expand scope without flagging it? Did it document assumptions that should have been questioned? Did it leave the workbench in a state the next session can pick up?

The idea

Idea 1 · Reviewer rubric

Five dimensions, each scored 0 to 2.

Dimension Question
Problem fit Did the change solve the task as stated, not a nearby task?
Scope discipline Were edits confined to the contract or was the contract grown deliberately?
Assumptions Are all hidden assumptions written down somewhere reviewable?
Verification quality Does the acceptance command actually prove the goal, or did it prove a weaker version?
Handoff readiness Could the next session pick up cleanly from the current state?

Total out of 10. A run below 7 is a soft fail; a run below 5, or any dimension at 0, is a hard fail.

Idea 2 · The reviewer is a separate role, not a separate model

You can run the reviewer with the same model as the builder. The discipline is the role separation: different system prompt, different inputs, no write access to the diff. The change in posture is the change in signal.

Idea 3 · The reviewer cannot edit the diff

The reviewer reads the diff, the state, the feedback, the verdict. It writes a report. It does not patch the diff. If the report says "fix this," the next builder turn does the fix; the reviewer goes back to reviewing. Mixing roles defeats the gap.

Idea 4 · Reviewer rubric versus verification gate

The gate (Phase 14 · 38) checks deterministic facts: did acceptance run, did rules pass, did scope hold. The reviewer makes qualitative judgments: was this the right work, is it documented, is the handoff usable. Both are required.

The same idea as a formula

What a gate can and cannot prove. If the acceptance test checks a set of cases T and the goal requires a larger set G⊃T, a gate certifies only f(x)=y for x∈T. The reviewer's question is the gap:

unproved=G∖T.
A weak test makes the gate pass for every f that is right on T, including ones wrong on G∖T.

The rubric. Five dimensions scored 0 to 2, total S≤10: pass if S≥7 and no dimension is 0; hard fail if any is 0 or S<5. A heuristic that scores a dimension wrongly at 0 turns a correct change into a hard fail on its own.

Worked example
One fix through the gate and the reviewer
  • Task: "average(xs) must return the mean, and 0 for an empty list." The builder sees only the acceptance test, assert average([2, 4, 6]) == 4.
  • It writes sum(xs) / len(xs). The gate runs the test: exit 0, pass. The hidden full test calls average([]) and gets ZeroDivisionError.
  • The unproved part is exactly the empty-list case: G∖T={[]}. Only a reader comparing the goal with the test can spot it.
  • The model as reviewer, asked "does this test prove the whole goal?", says YES. The lesson's scorer hard-fails average, but for the wrong reason (no goal keywords in the file name) and hard-fails three correct fixes the same way.
Check your mental model
  • ✗ "Passing the gate means the task is done."
    ✓ It means the tests passed; the tests may prove less than the goal.
  • ✗ "A separate reviewer role is enough, even with the same small model."
    ✓ Here it answered YES to every question, including six it should have refused.

Qwen2.5-0.5B-Instruct (greedy, CPU) fixes six functions from their acceptance tests. Each fix runs against the weak test (the gate) and a hidden full test; the lesson's review() from code/main.py scores each run's real artifacts. About 1 minute.

# What a gate cannot see: tests that prove a weaker goal than the task. Six bug fixes by Qwen2.5-0.5B-Instruct
# (greedy, CPU), each with a weak acceptance test (the one the builder is given and the gate runs) and a
# stronger hidden test that checks the whole goal as the task states it. The lesson's review() (code/main.py) then scores each run on its five dimensions
# from the real artifacts.
import os, pathlib, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import ReviewerInputs, review
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

TASKS = [  # (name, goal, buggy code, weak acceptance test, hidden full test)
    ("is_leap", "is_leap must follow the Gregorian rules: divisible by 4, except centuries, unless divisible by 400.",
     "def is_leap(y):\n    return y % 100 == 0\n", "assert is_leap(2024)", "assert is_leap(2024) and is_leap(2000) and not is_leap(1900) and not is_leap(2023)"),
    ("clamp", "clamp(x, lo, hi) must return x limited to the range lo..hi on both sides.",
     "def clamp(x, lo, hi):\n    return x\n", "assert clamp(15, 0, 10) == 10", "assert clamp(15, 0, 10) == 10 and clamp(-3, 0, 10) == 0 and clamp(5, 0, 10) == 5"),
    ("average", "average(xs) must return the mean, and 0 for an empty list.",
     "def average(xs):\n    return sum(xs) / (len(xs) + 1)\n", "assert average([2, 4, 6]) == 4", "assert average([2, 4, 6]) == 4 and average([]) == 0"),
    ("count_vowels", "count_vowels(s) must count a, e, i, o, u in upper or lower case.",
     "def count_vowels(s):\n    return len(s)\n", "assert count_vowels('banana') == 3", "assert count_vowels('banana') == 3 and count_vowels('AEIOU') == 5"),
    ("reverse", "reverse(s) must return the string reversed.", "def reverse(s):\n    return s\n",
     "assert reverse('abc') == 'cba'", "assert reverse('abc') == 'cba' and reverse('') == ''"),
    ("largest", "largest(xs) must return the biggest number, including negative lists.", "def largest(xs):\n    return 0\n",
     "assert largest([3, 9, 2]) == 9", "assert largest([3, 9, 2]) == 9 and largest([-5, -2, -9]) == -2"),
]
work = pathlib.Path(tempfile.mkdtemp())
def run(name, test):
    (work / f"t_{name}.py").write_text(f"from {name} import {name}\n{test}\n")
    return subprocess.run([sys.executable, f"t_{name}.py"], cwd=work, capture_output=True, text=True, timeout=30).returncode

ROWS = []
for name, goal, code, weak, full in TASKS:
    ask = (f"Current code:\n{code}\nFix it so this acceptance test passes:\n{weak}\n"   # the builder works from the test, as agents often do
           "Return only the corrected function in a ```python block.")
    ids = tok.apply_chat_template([{"role": "user", "content": ask}], add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=150, do_sample=False)
    m = re.search(r"```(?:python)?\n(.*?)```", tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True), re.S)
    fix = (m.group(1) if m else code).strip() + "\n"
    (work / f"{name}.py").write_text(fix)
    gate_exit, hidden_exit = run(name, weak), run(name, full)
    inputs = ReviewerInputs(task_id=f"T-{name}", goal=goal, diff_summary={"touched": [f"{name}.py"]},
                            state={"active_task_id": None, "next_action": "pick next task", "assumptions": []},
                            feedback=[{"command": f"python t_{name}.py", "exit_code": gate_exit}],
                            verdict={"passed": gate_exit == 0, "findings": []})
    rep = review(inputs)
    ROWS.append(dict(name=name, goal=goal, fix=fix, weak=weak, full=full, gate=gate_exit == 0, correct=hidden_exit == 0, rep=rep))

print(f"{'task':<14}{'gate (weak test)':<18}{'actually correct':<18}{'lesson review':<16}{'scores (fit, scope, assumptions, verification, handoff)'}")
for r in ROWS:
    rep = r["rep"]
    print(f"{r['name']:<14}{'PASS' if r['gate'] else 'BLOCK':<18}{'yes' if r['correct'] else 'NO':<18}"
          f"{rep.verdict + ' ' + str(rep.total):<16}{[d.score for d in rep.dimensions]}")
slipped = [r["name"] for r in ROWS if r["gate"] and not r["correct"]]
print(f"\npassed the gate but wrong for the stated goal: {slipped}")
print(f"of those, the lesson's review() failed: {[r['name'] for r in ROWS if r['name'] in slipped and r['rep'].verdict != 'pass']}")

Reading this output

Every fix passes its gate; one is wrong. All six pass the weak acceptance test. Against the full goal, average fails: it divides by len(xs) and crashes on an empty list, a case the task names and the test never tries. The other five happen to be fully correct.

The lesson's scorer is noisy. It hard-fails four runs, average among them, but every one for the same reason: problem fit 0, because the goal's long words do not appear in the touched file's name. That heuristic also fails three correct fixes and passes is_leap and count_vowels only by luck. A rubric dimension computed from file names cannot judge fit; it needs to read the goal, the code and the test together.

A model in the reviewer role

This block continues from the one above. The same model, with a read-only reviewer system prompt, sees each goal, the new code and the passing test, and answers whether the test proves the goal and whether the code meets it.

# A model in the reviewer role: same model as the builder, different instructions, read-only. It sees the task
# goal, the new code, the acceptance test and its result, and answers two rubric questions: does the test prove
# the goal (verification quality), and does the code meet the goal (problem fit)? Every weak test here proves
# less than its goal, so the right answer to the first question is always NO. Continues from the block above.
REVIEWER = ("You are a code reviewer. You did not write this change and you cannot edit it. Judge it against the "
            "task goal, not against the test.")
def ask_reviewer(r, question):
    prompt = (f"Task goal: {r['goal']}\nNew code:\n{r['fix']}\nAcceptance test (passed):\n{r['weak']}\n{question} Answer YES or NO.")
    ids = tok.apply_chat_template([{"role": "system", "content": REVIEWER}, {"role": "user", "content": prompt}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=4, do_sample=False)
    return "YES" in tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).upper()

print(f"{'task':<14}{'test proves goal?':<19}{'code meets goal?':<18}{'truth: meets goal'}")
right_q1 = right_q2 = 0
for r in ROWS:
    proves = ask_reviewer(r, "Does this acceptance test prove the whole task goal?")
    meets = ask_reviewer(r, "Does the new code meet the whole task goal?")
    right_q1 += not proves; right_q2 += meets == r["correct"]
    print(f"{r['name']:<14}{'YES' if proves else 'NO':<19}{'YES' if meets else 'NO':<18}{'yes' if r['correct'] else 'NO'}")
print(f"\nreviewer right on 'does the test prove the goal': {right_q1}/6 (all six tests are weaker than their goals)")
print(f"reviewer right on 'does the code meet the goal':  {right_q2}/6")

Reading this output

The reviewer says yes to everything. Asked whether each test proves the whole goal, it answers YES six times; every one of those tests proves less (no empty list, no negatives, no 1900). Right: 0 of 6.

On "does the code meet the goal" it scores 5 of 6, but only because it says YES every time and five fixes happen to be correct; it passes average, the one that matters. Role separation does not create judgement the model lacks. A reviewer needs measuring on cases with known answers before its scores mean anything, and tools like mutation testing answer "do the tests prove the goal" more reliably than a reader.

Part 1 of 3 · ReviewerInputs, DimensionScore, ReviewReport, score_problem_fit, score_scope_discipline, score_assumptions

"""Reviewer agent stub with a five-dimension rubric.

Consumes builder artifacts (diff summary, state, feedback, verification verdict)
and emits review_report.json with per-dimension scores and a final verdict.

In production each dimension scorer calls an LLM. Here we keep them
deterministic for the lesson — the structure is what travels.

Run: python3 code/main.py
"""

from __future__ import annotations

import json
from dataclasses import asdict, dataclass, field
from pathlib import Path

HERE = Path(__file__).parent


@dataclass
class ReviewerInputs:
    task_id: str
    goal: str
    diff_summary: dict[str, list[str]]
    state: dict[str, object]
    feedback: list[dict[str, object]]
    verdict: dict[str, object]


@dataclass
class DimensionScore:
    name: str
    score: int
    note: str


@dataclass
class ReviewReport:
    task_id: str
    total: int
    verdict: str
    dimensions: list[DimensionScore] = field(default_factory=list)


def score_problem_fit(inputs: ReviewerInputs) -> DimensionScore:
    files = inputs.diff_summary.get("touched", [])
    goal = inputs.goal.lower()
    keywords = [w for w in goal.split() if len(w) > 4]
    hits = sum(any(k in f.lower() for f in files) for k in keywords)
    score = min(2, hits)
    return DimensionScore("problem_fit", score, f"keyword hits across touched files: {hits}")


def score_scope_discipline(inputs: ReviewerInputs) -> DimensionScore:
    off = inputs.verdict.get("findings", [])
    block_scope = [f for f in off if f.get("code") == "scope.forbidden"]
    if block_scope:
        return DimensionScore("scope_discipline", 0, "forbidden writes present")
    warn_scope = [f for f in off if f.get("code") == "scope.off_scope"]
    return DimensionScore("scope_discipline", 1 if warn_scope else 2, f"off-scope warnings: {len(warn_scope)}")


def score_assumptions(inputs: ReviewerInputs) -> DimensionScore:
    assumptions = inputs.state.get("assumptions") or []
    if not assumptions:
        return DimensionScore("assumptions", 1, "no assumptions recorded; either work was trivial or undocumented")
    return DimensionScore("assumptions", 2, f"{len(assumptions)} assumptions recorded")

Part 2 of 3 · score_verification, score_handoff, review

def score_verification(inputs: ReviewerInputs) -> DimensionScore:
    exits = [rec.get("exit_code") for rec in inputs.feedback]
    if any(code is None for code in exits):
        return DimensionScore("verification_quality", 0, "feedback log has missing exit codes")
    if all(code == 0 for code in exits) and exits:
        return DimensionScore("verification_quality", 2, "all feedback exit zero")
    return DimensionScore("verification_quality", 1, "mixed exit codes in feedback")


def score_handoff(inputs: ReviewerInputs) -> DimensionScore:
    if inputs.state.get("active_task_id"):
        return DimensionScore("handoff_readiness", 1, "active task not closed in state")
    if inputs.state.get("next_action"):
        return DimensionScore("handoff_readiness", 2, "next_action set, task closed")
    return DimensionScore("handoff_readiness", 0, "no next_action recorded")


SCORERS = [score_problem_fit, score_scope_discipline, score_assumptions, score_verification, score_handoff]


def review(inputs: ReviewerInputs) -> ReviewReport:
    dims = [fn(inputs) for fn in SCORERS]
    total = sum(d.score for d in dims)
    has_zero = any(d.score == 0 for d in dims)
    if has_zero or total < 5:
        verdict = "hard_fail"
    elif total >= 7:
        verdict = "pass"
    else:
        verdict = "soft_fail"
    return ReviewReport(task_id=inputs.task_id, total=total, verdict=verdict, dimensions=dims)


def main() -> None:
    clean = ReviewerInputs(
        task_id="T-001",
        goal="add input validation to signup",
        diff_summary={"touched": ["app/signup.py", "tests/test_signup.py"]},
        state={
            "active_task_id": None,
            "assumptions": ["users sign up with email + password only"],
            "next_action": "pick next task from board",
        },
        feedback=[{"command": "pytest", "exit_code": 0}],
        verdict={"passed": True, "findings": []},
    )
    wrong = ReviewerInputs(
        task_id="T-002",
        goal="add input validation to signup",
        diff_summary={"touched": ["docs/api.md"]},
        state={"active_task_id": "T-002", "assumptions": [], "next_action": ""},
        feedback=[{"command": "pytest", "exit_code": 0}],
        verdict={"passed": True, "findings": [{"code": "scope.off_scope", "severity": "warn"}]},
    )

    for case in (clean, wrong):
        report = review(case)
        out = HERE / f"review_report_{case.task_id}.json"
        out.write_text(
            json.dumps(
                {"task_id": report.task_id, "total": report.total, "verdict": report.verdict, "dimensions": [asdict(d) for d in report.dimensions]},
                indent=2,
            )
            + "\n"
        )
        print(f"task {report.task_id}: total={report.total}/10 verdict={report.verdict}")
        for d in report.dimensions:
            print(f"  {d.name:22} {d.score}  {d.note}")
        print()

Production patterns in the wild

The receipts: Cloudflare's April 2026 AI Code Review system ran 131,246 review runs across 48,095 merge requests in 5,169 repos in 30 days. Median review completed in 3 minutes 39 seconds. Up to seven specialist reviewers (security, performance, code quality, docs, release management, compliance, Engineering Codex) ran in parallel under a Review Coordinator that deduplicated findings and judged severity. Top-tier model reserved exclusively for the coordinator; specialists ran on cheaper tiers.

Four patterns make this work at scale.

Specialist pool, not one big reviewer. One reviewer with a 5-dimension rubric works for solo repos. Once the codebase has security-critical, performance-critical, and docs surfaces, split into specialists with smaller prompts. The coordinator does deduplication; the specialists never run the full rubric. Model-tier separation falls out: cheap specialists, expensive coordinator.

Bias mitigation as design requirement, not optimization. LLM judges show four reliable biases (Adnan Masood, April 2026): position bias (GPT-4 ~40% inconsistent on (A,B) vs (B,A) ordering), verbosity bias (~15% score inflation toward longer outputs), self-preference (judges prefer outputs from the same model family), authority (judges over-rate references to known authors). Mitigations: evaluate both orderings and only count consistent wins; use 1-4 scales that explicitly reward conciseness; rotate judges across model families; strip author names before scoring.

Calibration set, not vibes. A 10-20 task historical set with known correct verdicts. Run the reviewer over it on every prompt change. If agreement with the historical record falls below 80%, the rubric needs revision before the reviewer ships. This is what every team eventually rediscovers; better to start with it.

Hybrid norm with the gate. Verification gate (Phase 14 · 38) handles the deterministic checks (did acceptance run, did tests pass, did scope hold). Reviewer handles the semantic checks (was this the right work, are assumptions documented, is the handoff usable). Anthropic's 2026 guidance is explicit on this split: don't ask the reviewer to redo what the gate already proves.

Use it: the same idea with real libraries

Production patterns:

  • Claude Code subagents. A reviewer subagent runs after the builder closes a task. It posts a comment on the PR with the rubric scores.
  • OpenAI Agents SDK handoffs. Builder hands off to Reviewer on task completion. Reviewer can hand back with a list of findings or up to a human.
  • Two-model pairing. Builder runs on a faster cheaper model. Reviewer runs on a stronger model with smaller context, focused on judgment.

The reviewer is the second pair of eyes the workbench grows when humans cannot do every review themselves.

Break it on purpose

Your agent pipeline has a builder, a gate and a reviewer agent, all using the same model. Production bugs keep appearing in edge cases that "were tested", and every review report says "verification quality: 2/2". Using this lesson, what is the reviewer actually checking, and what would you change? (Solution B1.)

Industry practice
What's current (2024–2026)
  • AI code review is widely deployed (GitHub Copilot code review, CodeRabbit, Claude Code review actions and others); teams treat its comments as suggestions alongside human review and required checks, not as approval.
  • Reviewer subagents with read-only tools and their own instructions are a standard pattern in coding-agent harnesses; the role separation matters, and a stronger or different model for review catches more.
  • Test adequacy is checked with mutation testing (does any test fail when the code is deliberately broken?) and coverage, which answer "does the test prove the goal" better than any reader.
  • On your laptop: mutation testing tools such as mutmut run on small Python projects in minutes.

Sources: GitHub Copilot code review, Claude Code subagents, mutmut.

Recap
What to keep from this lesson
  • The reviewer asks what the gate cannot: do the tests prove the goal?
  • Weak tests let wrong code pass; compare tests with the stated goal.
  • Calibrate rubric heuristics; a wrong zero hard-fails good work.
  • A reviewer that always says yes adds nothing; measure it on known cases.
  • Reviewers report; they never edit.

Produce:

1. `agents/reviewer.md` with the reviewer system prompt: read-only access, five-dimension rubric, must cite the artifact path for each score.
2. `tools/reviewer.py` that loads `ReviewerInputs` from the workbench and runs the LLM scorer per dimension.
3. `outputs/review/<task_id>.json` as the canonical review report path.
4. `docs/reviewer-rubric.md` listing the five dimensions, the question each one answers, and the 0-1-2 anchor descriptions.
5. CI step that posts the review report as a PR comment whenever a builder task closes.

Hard rejects:

- A reviewer with write access to the diff. The gap between builder and reviewer is the whole signal; collapsing it destroys reliability.
- A rubric without anchor descriptions per score. "Score from 0 to 2" without anchors collapses to vibes.
- Review reports that omit citations. Every score must point at a file or trace entry.
- Sharing the builder's system prompt. Same model is fine; same prompt is not.

Refusal rules:

- If the builder produces no verification report, refuse to run the reviewer. Acceptance must hold before judgment is worth asking for.
- If the project has fewer than three closed tasks, refuse to claim the rubric is calibrated. Save the first reports as the calibration set.
- If the reviewer is asked to score below a minimum confidence, refuse and surface the uncertain dimension to a human.

Exercises

  1. Add a sixth dimension specific to your product domain. Defend why it is not absorbed by the existing five.
  2. Run the reviewer with two different system prompts (terse, verbose). Which produces a report a human is more likely to read?
  3. Add a confidence field per dimension. Refuse to ship the report when confidence in the lowest dimension is below 0.6.
  4. Build a calibration set: 10 historical task close-outs with known correct verdicts. Run the reviewer over them. Where does it disagree with the historical record?
  5. Add a "request more evidence" affordance: the reviewer can ask the builder for a specific test run before scoring. What is the right back-off so this does not loop?

Solutions

SolutionP1 · One slips through, flagged for the wrong reason

One: average passes average([2, 4, 6]) == 4 but crashes on the empty list the goal mentions. The lesson's scorer does hard-fail it, but for a reason unrelated to the bug (problem fit 0 from a keyword match on file names), and it hard-fails three correct fixes for the same reason, so its verdict carries no signal here.

SolutionB1 · A reviewer that only restates the gate

The reviewer is scoring verification quality from the gate's outputs (exit codes are zero, so 2/2), which restates the gate instead of asking whether the tests cover the goal. With the same model as the builder, it also tends to approve whatever it sees.

Change the reviewer's inputs and checks: give it the task goal and acceptance criteria and require it to list goal cases the tests do not exercise; back that with mutation testing and coverage of the changed lines, so "do the tests prove the goal" has evidence; use a stronger or different model for review, and measure the reviewer on seeded changes with known gaps. Turn every escaped edge case into a test, and require a human sign-off when the reviewer reports untested goal cases.
