The numbers that businesses ask about live in tables, not documents. "How many orders were late in Pune last week?" cannot be answered by retrieving passages; it needs a query. Text-to-SQL turns a question into SQL, runs it and explains the result. It is one of the most requested enterprise agent patterns, and one of the easiest to get dangerously wrong, so this lesson builds it with every safeguard in place. The database is SQLite, so everything runs offline; where a model writes SQL, a stand-in returns what a model would, including its typical mistakes.

Why this came about

Many business questions are about numbers stored in databases, which passages cannot answer. Models turned out to be good at writing SQL, and text-to-SQL became a major use case, along with the need to validate queries, run them safely and use semantic layers so terms mean what the business means.

In plain words first
Translating questions into SQL, carefully

For questions about numbers in a database, the model writes a query instead of reading passages: find the relevant tables, write SQL, check it, run it with read-only permissions, and explain the result. Each step guards against a known failure: wrong tables, invented columns, huge scans, or a destructive statement. A semantic layer that defines business terms such as "active customer" makes the model far more accurate.

Step 1 · A database with realistic traps

Real schemas have cryptic column names, codes instead of labels and several tables to join. The lab database has all three.

Step 2 · A semantic layer: business meaning in one place

A model that sees only ord.stat_cd and amt_inr has to guess what "revenue", "late" or "delivered" mean, and different guesses give different numbers. A semantic layer defines them once: tables with descriptions, joins, dimensions and metrics with exact SQL, plus verified queries for the most important questions. This is what Databricks metric views, dbt's semantic layer, Cube and LookML provide; here it is a dictionary.

SEMANTIC_LAYER = {
    "tables": {
        "ord": "One row per order. amt_inr is the order value in rupees. stat_cd links to stat_lkp.",
        "cust": "One row per customer, with city, loyalty tier and tenant_id.",
        "stat_lkp": "Order status codes: D delivered, C cancelled, P processing, R returned.",
    },
    "joins": ["ord.cust_id = cust.cust_id", "ord.stat_cd = stat_lkp.stat_cd"],
    "metrics": {
        "revenue":         {"sql": "SUM(ord.amt_inr)", "filter": "ord.stat_cd = 'D'",
                            "description": "Value of delivered orders only (cancelled and returned excluded)"},
        "late deliveries": {"sql": "COUNT(*)", "filter": "ord.delivered_dt > ord.promised_dt",
                            "description": "Orders delivered after the promised date"},
        "order count":     {"sql": "COUNT(*)", "filter": None, "description": "All orders"},
    },
    "synonyms": {"sales": "revenue", "gmv": "revenue", "delayed": "late deliveries", "location": "city"},
    "verified_queries": {
        "revenue by city": "SELECT cust.city, SUM(ord.amt_inr) AS revenue FROM ord JOIN cust ON ord.cust_id = cust.cust_id "
                           "WHERE ord.stat_cd = 'D' GROUP BY cust.city ORDER BY revenue DESC",
    },
}

def semantic_context(question: str) -> str:
    """Build the prompt context: only the metrics and tables the question needs (schema linking, Step 3)."""
    q = question.lower()
    for word, canonical in SEMANTIC_LAYER["synonyms"].items():
        q = q.replace(word, canonical)
    metrics = {m: d for m, d in SEMANTIC_LAYER["metrics"].items() if m in q}
    lines = [f"Metric '{m}': {d['sql']}" + (f" WHERE {d['filter']}" if d["filter"] else "") + f"  -- {d['description']}"
             for m, d in metrics.items()]
    return "\n".join(lines) or "(no metric matched; ask a clarifying question)"

print(semantic_context("What were sales by location last month?"))
What you should see
Metric 'revenue': SUM(ord.amt_inr) WHERE ord.stat_cd = 'D'  -- Value of delivered orders only (cancelled and returned excluded)

"Sales by location" became the defined revenue metric, with the rule that only delivered orders count. Without that line, a model would happily sum every order, including cancellations and returns, and report a number several times too high (Step 6 measures it), which nobody would notice until finance did.

Step 3 · Schema linking: show the model only what it needs

Enterprise warehouses have thousands of tables; putting them all in the prompt is expensive and confuses the model. Schema linking selects the relevant tables and columns first, by matching the question against table and column descriptions (with embeddings or a model call in production).

def schema_ddl(tables: list[str]) -> str:
    return "\n".join(db.execute("SELECT sql FROM sqlite_master WHERE name = ?", (t,)).fetchone()[0] for t in tables)

def link_schema(question: str) -> list[str]:
    """Pick tables whose description shares words with the question; always add tables needed for joins."""
    q = set(re.findall(r"[a-z]+", question.lower()))
    picked = [t for t, desc in SEMANTIC_LAYER["tables"].items() if q & set(re.findall(r"[a-z]+", desc.lower()))]
    if any(w in q for w in ("city", "location", "tier", "gold", "silver")) and "cust" not in picked:
        picked.append("cust")
    return picked

tables = link_schema("Which city had the most late deliveries?")
print(tables)
print(schema_ddl(tables))

Step 4 · Validate every query before it runs

Model-written SQL is untrusted input. Parse it with a real SQL parser (here sqlglot) and enforce rules on the parsed tree, not with string matching:

  • exactly one statement, and it must be a SELECT
  • only allowlisted tables
  • a row limit, added if missing
  • the caller's tenant filter, injected into the query so it cannot be forgotten or bypassed
ALLOWED_TABLES = {"ord", "cust", "stat_lkp"}

class UnsafeSQL(Exception):
    pass

def validate(sql: str, tenant_id: int, max_rows: int = 200) -> str:
    statements = sqlglot.parse(sql, read="sqlite")
    if len(statements) != 1:
        raise UnsafeSQL("exactly one statement is allowed")
    tree = statements[0]
    if not isinstance(tree, exp.Select):
        raise UnsafeSQL(f"only SELECT is allowed, got {type(tree).__name__.upper()}")
    tables = {t.name for t in tree.find_all(exp.Table)}
    if tables - ALLOWED_TABLES:
        raise UnsafeSQL(f"tables not allowed: {sorted(tables - ALLOWED_TABLES)}")
    if "cust" not in tables:                                    # tenant scoping needs the customer table
        raise UnsafeSQL("queries must join cust so they can be scoped to a tenant")
    tree = tree.where(f"cust.tenant_id = {int(tenant_id)}")      # row-level security, enforced by code
    if not tree.args.get("limit"):
        tree = tree.limit(max_rows)
    return tree.sql(dialect="sqlite")

for attempt in ["SELECT cust.city, COUNT(*) FROM ord JOIN cust ON ord.cust_id = cust.cust_id GROUP BY cust.city",
                "DROP TABLE ord",
                "SELECT * FROM ord; DELETE FROM cust",
                "SELECT * FROM sqlite_master"]:
    try:
        print("OK  ", validate(attempt, tenant_id=1))
    except (UnsafeSQL, sqlglot.errors.ParseError) as e:
        print("DENY", e)
What you should see
OK   SELECT cust.city, COUNT(*) FROM ord JOIN cust ON ord.cust_id = cust.cust_id WHERE cust.tenant_id = 1 GROUP BY cust.city LIMIT 200
DENY only SELECT is allowed, got DROP
DENY exactly one statement is allowed
DENY tables not allowed: ['sqlite_master']

Validation is one layer. The others are just as important: connect with a read-only database role that can see only the allowed schemas (so even a validator bug cannot write), and let the database enforce row-level security where it supports it (Postgres row-level security, Databricks row filters).

Step 4b · Verify the tenant filter cannot be bypassed

Step 4 injects cust.tenant_id = 1 into the outer WHERE. Before trusting it, attack it. Three queries a model (or a prompt injectionlater · 15.24) could produce:

for attempt in ["SELECT (SELECT COUNT(*) FROM cust) AS all_customers FROM cust",                 # scalar subquery
                "WITH ord AS (SELECT city, tenant_id FROM cust) SELECT ord.city FROM ord JOIN cust ON 1 = 1",   # CTE shadows a table
                "SELECT * FROM ord JOIN cust c ON ord.cust_id = c.cust_id"]:                     # alias
    try:
        safe = validate(attempt, tenant_id=1)
        rows = db.execute(safe).fetchall()
        print("LEAK?" if "all_customers" in safe or "ord.city" in safe else "OK   ", len(rows), "rows |", safe[:80])
    except (UnsafeSQL, sqlite3.Error, sqlglot.errors.ParseError) as e:
        print("ERROR", type(e).__name__, "|", str(e)[:60])
What you should see
LEAK? 30 rows | SELECT (SELECT COUNT(*) FROM cust) AS all_customers FROM cust WHERE cust.tenant_
LEAK? 200 rows | WITH ord AS (SELECT city, tenant_id FROM cust) SELECT ord.city FROM ord JOIN cus
ERROR OperationalError | no such column: cust.tenant_id

Three holes. The scalar subquery counts all 40 customers across both tenants, while the outer filter scopes only the rows it sits on (30 rows, each carrying the leaked total). The CTE named ord reads cust for both tenants, and the outer filter on the real cust cannot touch it; the row cap trims the output to 200, but every one of those rows crosses the tenant line (the full result is 40 cities × 30 rows). The alias case is not a leak but a failure: cust.tenant_id does not exist once the table is called c.

The fix: refuse CTEs, and apply the filter to every SELECT scope using the alias that scope actually uses. Any scope that does not read cust is refused, which also closes subqueries over other tables.

def validate(sql: str, tenant_id: int, max_rows: int = 200) -> str:
    """Hardened: one statement, SELECT root, allowlisted tables, no CTEs, tenant filter in every SELECT scope, row cap."""
    statements = sqlglot.parse(sql, read="sqlite")
    if len(statements) != 1 or statements[0] is None:
        raise UnsafeSQL("exactly one statement is allowed")
    tree = statements[0]
    if not isinstance(tree, exp.Select):
        raise UnsafeSQL(f"only SELECT is allowed, got {type(tree).__name__.upper()}")
    if tree.args.get("with_"):                                     # sqlglot 30 names the key with_
        raise UnsafeSQL("WITH (CTEs) is not allowed; write the query without them")
    tables = {t.name for t in tree.find_all(exp.Table)}
    if tables - ALLOWED_TABLES:
        raise UnsafeSQL(f"tables not allowed: {sorted(tables - ALLOWED_TABLES)}")
    for sel in tree.find_all(exp.Select):                          # the outer query AND every subquery
        scope = [sel.args.get("from_")] + list(sel.args.get("joins") or [])   # sqlglot 30 names the key from_
        aliases = [t.alias_or_name for part in scope if part is not None
                   for t in part.find_all(exp.Table) if t.name == "cust"]
        if not aliases:
            raise UnsafeSQL("every SELECT, including subqueries, must join cust so it can be scoped to a tenant")
        sel.where(f"{aliases[0]}.tenant_id = {int(tenant_id)}", copy=False)   # uses the alias in use
    cap = min(max_rows, int(tree.args["limit"].expression.this)) if tree.args.get("limit") else max_rows
    tree.set("limit", exp.Limit(expression=exp.Literal.number(cap)))          # min(existing, cap), never larger
    return tree.sql(dialect="sqlite")

for attempt in ["SELECT (SELECT COUNT(*) FROM cust) AS all_customers FROM cust",
                "WITH ord AS (SELECT city, tenant_id FROM cust) SELECT ord.city FROM ord JOIN cust ON 1 = 1",
                "SELECT * FROM ord JOIN cust c ON ord.cust_id = c.cust_id LIMIT 50000",
                "SELECT cust.city, COUNT(*) FROM ord JOIN cust ON ord.cust_id = cust.cust_id GROUP BY cust.city"]:
    try:
        safe = validate(attempt, tenant_id=1)
        print("OK   ", len(db.execute(safe).fetchall()), "rows |", safe[:95])
    except (UnsafeSQL, sqlite3.Error, sqlglot.errors.ParseError) as e:
        print("DENY ", str(e)[:80])
What you should see
OK    30 rows | SELECT (SELECT COUNT(*) FROM cust WHERE cust.tenant_id = 1) AS all_customers FROM cust WHERE cu
DENY  WITH (CTEs) is not allowed; write the query without them
OK    150 rows | SELECT * FROM ord JOIN cust AS c ON ord.cust_id = c.cust_id WHERE c.tenant_id = 1 LIMIT 200

The scalar subquery now counts only tenant 1 (the inner SELECT got its own filter), the CTE is refused, the alias works, LIMIT 50000 became LIMIT 200, and the ordinary query is unchanged. Keep these four in a test file and run them on every change and every sqlglot upgrade: version 30 renamed the from and with argument keys to from_ and with_, which silently breaks code that reads them. Derived tables in FROM (SELECT ... FROM (SELECT ...) t) are refused by the same rule because the outer scope sees no cust; that is a deliberate loss of some legitimate queries in exchange for a rule you can reason about.

Step 4c · Cost pre-check and a warehouse-level timeout

The next step adds a timeout inside the Python process (run_with_timeout, in Step 5), which cancels a query that runs too long. That protects this process; it does not protect the warehouse from a query that your process forgot about, or from a second client. Two more layers, both on the database side:

  • Compile before you run. EXPLAIN parses and plans without executing. On SQLite it is cheap and catches bad columns; on Snowflake, EXPLAIN USING TABULAR also reports partitionsAssigned and bytesAssigned, which is an upper-bound estimate of what the query will scan, so you can refuse anything above a budget before spending a credit.
  • A timeout the database enforces. On Snowflake, set STATEMENT_TIMEOUT_IN_SECONDS on the warehouse the agent uses (and in the session if you like; when both are set, the lowest non-zero value wins). Postgres has statement_timeout; Databricks SQL warehouses have STATEMENT_TIMEOUT as well. The agent's warehouse should also be its own, small, with a resource monitor, so a runaway query cannot starve anyone else.
def explain_check(sql: str, max_steps: int = 8) -> str:
    """Plan without running. '' means OK; otherwise a reason the writer can act on."""
    try:
        plan = db.execute(f"EXPLAIN QUERY PLAN {sql}").fetchall()
    except sqlite3.Error as e:
        return f"explain failed: {e}"
    if len(plan) > max_steps:                                       # stand-in for a cost budget (Snowflake: bytesAssigned)
        return f"plan too large: {len(plan)} steps"
    if any("SCAN ord" in row[-1] and "USING" not in row[-1] for row in plan) and "ord_dt" not in sql:
        return "full scan of ord without a date filter"             # a house rule: date-bound the big table
    return ""

"""                                                                 # not run here: needs a warehouse

Step 5 · Generate, execute, self-correct

The agent loop: build the prompt from the semantic context and linked schema, generate SQL, validate, execute with a timeout, and if anything fails, send the error back for one or two repair attempts. The generator below plays a model that makes a classic first mistake (forgetting the status-code lookup) and fixes it when shown the error.

PROMPT = """You write SQLite for ShopKart analytics. Use only these tables:
{schema}
Business definitions you MUST use:
{semantic}
Question: {question}
Return one SELECT statement and nothing else."""

def fake_llm_sql(prompt: str, attempt: int) -> str:
    """Stands in for a model. First attempt uses a column that does not exist; the repair is correct."""
    if "late deliveries" in prompt:
        if attempt == 1:
            return ("SELECT cust.city, COUNT(*) AS late FROM ord JOIN cust ON ord.cust_id = cust.cust_id "
                    "WHERE ord.delivery_status = 'late' GROUP BY cust.city ORDER BY late DESC")
        return ("SELECT cust.city, COUNT(*) AS late FROM ord JOIN cust ON ord.cust_id = cust.cust_id "
                "WHERE ord.delivered_dt > ord.promised_dt GROUP BY cust.city ORDER BY late DESC")
    return SEMANTIC_LAYER["verified_queries"]["revenue by city"]

def run_with_timeout(sql: str, seconds: float = 2.0):
    deadline = time.monotonic() + seconds
    db.set_progress_handler(lambda: 1 if time.monotonic() > deadline else 0, 10_000)   # abort long queries
    try:
        cur = db.execute(sql)
        return [d[0] for d in cur.description], cur.fetchall()
    finally:
        db.set_progress_handler(None, 0)

def ask(question: str, tenant_id: int, max_attempts: int = 3) -> dict:
    prompt = PROMPT.format(schema=schema_ddl(link_schema(question)), semantic=semantic_context(question),
                           question=question)
    for attempt in range(1, max_attempts + 1):
        sql = fake_llm_sql(prompt, attempt)
        try:
            safe = validate(sql, tenant_id)
            columns, rows = run_with_timeout(safe)
            return {"sql": safe, "columns": columns, "rows": rows, "attempts": attempt}
        except (UnsafeSQL, sqlite3.Error, sqlglot.errors.ParseError) as e:
            print(f"  attempt {attempt} failed: {e}")
            prompt += f"\n\nYour previous query:\n{sql}\nfailed with: {e}\nFix it."
    return {"error": "could not produce a valid query", "attempts": max_attempts}

result = ask("Which city had the most delayed orders?", tenant_id=1)
print(result["sql"])
print(result["columns"], result["rows"][:2], "| attempts:", result["attempts"])

Step 6 · Evaluate by execution accuracy

Two correct queries can look completely different, so comparing SQL strings is useless. Execution accuracy runs the generated query and a gold query and compares the result sets. Public benchmarks (Spider 2.0, BIRD) use the same idea; your own set of verified questions matters more.

GOLD_SQL = {
    "Which city had the most delayed orders?":
        "SELECT cust.city, COUNT(*) FROM ord JOIN cust ON ord.cust_id = cust.cust_id "
        "WHERE ord.delivered_dt > ord.promised_dt AND cust.tenant_id = 1 GROUP BY cust.city ORDER BY 2 DESC",
    "What were sales by location last month?":
        "SELECT cust.city, SUM(ord.amt_inr) FROM ord JOIN cust ON ord.cust_id = cust.cust_id "
        "WHERE ord.stat_cd = 'D' AND cust.tenant_id = 1 GROUP BY cust.city ORDER BY 2 DESC",
}

def same_result(a_rows, b_rows) -> bool:
    """Compare result sets ignoring column names; order matters only if both are sorted the same way."""
    norm = lambda rows: [tuple(round(v, 2) if isinstance(v, float) else v for v in r) for r in rows]
    return norm(a_rows) == norm(b_rows)

hits = 0
for question, gold in GOLD_SQL.items():
    got = ask(question, tenant_id=1)
    ok = "rows" in got and same_result(got["rows"], db.execute(gold).fetchall())
    hits += ok
    print(("PASS " if ok else "FAIL ") + question)
print(f"execution accuracy: {hits}/{len(GOLD_SQL)}")

naive = "SELECT cust.city, SUM(ord.amt_inr) FROM ord JOIN cust ON ord.cust_id = cust.cust_id WHERE cust.tenant_id = 1 GROUP BY cust.city"

      dict(db.execute(naive).fetchall())["Pune"], "vs", dict(db.execute(GOLD_SQL["What were sales by location last month?"]).fetchall())["Pune"])

In production
Design a text-to-SQL system right from day one
  1. Scope by domain: one curated subject area per assistant (orders, payments, marketing), not the whole warehouse.
  2. A semantic layer before prompts: table and column descriptions, synonyms, sample values for low-cardinality columns, metric definitions, and a few verified queries. This is where most accuracy comes from.
  3. Read-only execution as the user's role, with row limits, timeouts and cost limits, so permissions and masking apply automatically.
  4. Show the SQL and the assumptions with every answer, and ask a clarifying question when a term is ambiguous.
  5. An eval set of real questions with verified results, scored by comparing result sets.
  6. Logging of question, SQL, row count and user, so wrong answers can be traced and turned into new verified queries.

Business metrics computed wrongly ("active customer", "net revenue") Define each metric once in the semantic layer Verified queries for the top questions Two teams defining the same metric differently: settle it before the model sees it
Ambiguous questions answered confidently A clarifying question, or answer with stated assumptions Reject unanswerable questions with suggestions Too many clarifying questions annoy users; ask only when results would differ
Queries fail to run Validate or EXPLAIN first and feed errors back for one or two repairs Generate several candidates and keep the one that runs and passes checks Endless repair loops: cap attempts
Users do not trust the numbers Always show SQL, tables used and a plain explanation Link to the governed dashboard for the same metric A single visibly wrong number destroys adoption; start with a narrow, well-tested scope
From the field
Four companies, one pattern: narrow the context, then generate
  • Uber, QueryGPT (2024): about 1.2 million interactive queries a month on Uber's data platform. The first prototype retrieved tables and sample SQL by similarity and degraded as tables were added. The version that worked chains narrow agents: an intent agent maps the question to a business-domain workspace, a table agent proposes tables for the user to confirm, and a column-prune agent trims schemas that were 40,000 to 60,000 tokens. Evaluation uses a golden set with verified intent, tables and SQL, scoring each stage separately. In a limited release, 78% of users said it cut their query-writing time. Uber Engineering
  • Pinterest (2024): table selection by vector search over table summaries and summaries of historical queries, weighting table documentation more heavily, then an LLM picks the final tables for the user to confirm. Table search hit rate rose from 40% without documentation to about 90% with it, and first-shot acceptance of generated SQL rose from 20% to over 40%. Pinterest Engineering
  • LinkedIn, SQL Bot (2025): a knowledge graphlater · 14.83 built from table metadata, query logs, wikis and code, clustered by team, feeds an agent that retrieves context, writes SQL and fixes its own errors. Over 300 weekly users; expert review rated 53% of answers correct or close to correct on an internal benchmark, an honest number worth remembering when vendors quote 90%. Chen et al., arXiv
  • Swiggy, Hermes (India, 2026 write-up): a Slack-based analyst over the company's data warehouse. Historical SQL was explained in natural language by an LLM, indexed, and retrieved as few-shot examples; a ReAct-style orchestrator checks completeness, looks up metadata, asks clarifying questions and attaches assumptions and confidence to every answer. The team reports SQL accuracy rising from 54% to 93% across versions. InfoQ

Treat vendor and internal benchmarks as directional and build your own question set: the spread between 53% and 93% above is mostly about how narrow and well-described the data is.

Exercises

Predict before you run

The question "What was revenue last month?" goes to link_schema. Which tables should it return, and what can go wrong if it returns all of them? (Solution P1.)

Break it on purpose

Run model-generated SQL without the validation step. The model writes DELETE FROM orders WHERE .... What protects you? (Solution B1.)

Debugging exercise

Revenue answers are 18% too high. The SQL is valid. Which trap from Step 1 is likely, and where should the fix live? (Solution D1.)

Make it your own

Add a metric "net revenue" to the semantic layer (excluding cancelled orders and tax) and test it with three phrasings of the same question. (Solution M1.)

Solutions

SolutionP1 · Show only what is needed

Only the tables with revenue and dates, through the semantic layer's definition of revenue. With all tables, the prompt is long and the model may pick a similar-looking wrong column, such as gross instead of net.

SolutionB1 · Validate and restrict

Nothing, if validation is skipped and the database user can write. Parse the SQL and allow only SELECT, run with a read-only role, limit rows and time, and validate tables and columns against the schema.

SolutionD1 · Business meaning belongs in the semantic layer

Likely double counting through a join (order lines times payments) or counting cancelled orders or including tax. The fix belongs in the semantic layer's metric definition, not in a prompt instruction, so every question uses the same definition.

SolutionM1 · One definition, many phrasings

Define the metric once with its filters, expose it to the model with a description, and check that all three phrasings produce the same SQL result.

Check your understanding

Explain the mechanismWhat makes text-to-SQL hard in production, and how do you make it reliable?

Worked answer. Business meaning is not in the schema: which column is revenue, which orders count, how tables join. Reliability comes from a semantic layer that defines metrics and joins, schema linking that shows only relevant tables, validation and a read-only role, examples of good queries, and evaluation by comparing query results, not SQL text.

A plausible wrong answer. "Give the model the full schema and it will work." Large schemas and ambiguous columns cause most errors.

Follow-ups. How would you evaluate text-to-SQL?

Debug a failureText-to-SQL works on the demo database but fails on the real warehouse. Why?

Worked answer. Real schemas are larger, with cryptic names, many similar tables, and business rules in people's heads. Add a semantic layer, column descriptions, schema linking, and examples drawn from real analyst queries; test on real questions.

A plausible wrong answer. "The model is not good enough for SQL." The model lacks context the demo did not need.

Follow-ups. Where would you get example queries?

Defend a designA text-to-SQL agent or a semantic-layer product's built-in natural language interface?

Worked answer. A platform's built-in interface (for example Databricks Genie or BigQuery and Fabric data agents) when your data and metrics live there and its semantic layer covers your questions; your own agent when you need custom tools, multiple sources or tight integration. Both depend on a good semantic layer.

A plausible wrong answer. "Build your own, it is more flexible." Flexibility without a semantic layer gives wrong numbers faster.
