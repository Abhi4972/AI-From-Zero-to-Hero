In plain words first
The idea in one line

A 1-hour 4K video at 24 FPS, patched and embedded, produces on the order of 60 million tokens. A 2-hour podcast episode transcribed is 30,000 tokens. A full Blu-ray feature film, even compressed with aggressive pooling, is hundreds of thousands of tokens. Google's Gemini 1.5 (March 2024) opened this era: 1 million tokens of context in production (2 million soon after) and recall tested up to 10 million tokens in research, doing reliable needle-in-a-haystack recall over hour-long videos. LWM (Liu et al., February 2024) showed ring attention's scaling path. LongVILA and Video-XL scaled ingestion further. VideoAgent swapped raw

The problem

In plain words first

An hour of video is far more data than any model can read whole. Even at one frame per second with heavy compression it is hundreds of thousands of tokens. There are four ways around it. Use a model with an enormous context window (Gemini's approach). Spread a long sequence over many GPUs with ring attention, so each holds only a slice. Compress each clip into very few tokens before the language model sees it. Or treat the video like a database: describe each clip once, search the descriptions, and read only the clips the question needs (an "agentic" approach such as VideoAgent). This lesson explains the four paths and how to choose. It runs a working clip-retrieval step on a 2-hour video's descriptions and checks that ring attention's block-by-block computation gives exactly the same result as full attention. No model is trained.

A single frame of Qwen2.5-VL-sized patches at 384 native resolution is ~729 tokens. At 3x3 pooling that's 81 tokens per frame. A 30-minute clip at 1 FPS = 1800 frames = 145,800 tokens. Doable by 2025 open VLMs, tight. At 2 FPS, 291,600 tokens — only the biggest contexts fit.

A 2-hour movie at 1 FPS is 583k tokens. Beyond most 2026 open models; requires Gemini 2.5 Pro or pooling more aggressively.

Four scaling paths emerged.

Idea 1 · Path 1: Brute context (Gemini 1.5, Claude Opus)

Throw hardware at the problem. Scale context to millions of tokens, process everything in one forward pass. (Claude does not take video input directly; with Claude you send sampled frames as images, which is Path 3 or 4.)

Gemini 1.5 Pro launched with 1M tokens and later 2M. Its report (arXiv:2403.05530) shows near-perfect needle-in-a-haystack recall (above 99%) for text, audio and video up to millions of tokens, tested up to 10M tokens on text. Later Gemini generations keep long video as a headline feature.

Engineering: Gemini 1.5 is a sparse mixture-of-experts transformer; how its attention scales to millions of tokens is not published. Not open-source.

Idea 2 · Path 2: Ring attention (LWM, LongVILA)

Ring attention distributes long sequences across devices in a "ring" where each device holds a chunk. Attention across the full sequence happens by each device sending its chunk to the next in a ring pattern, computing partial attention, and aggregating.

LWM (Liu et al., 2024) trained a 1M-token context model this way. Per-device memory scales with the chunk each device holds, so adding devices extends the context roughly linearly. Total attention compute is still quadratic in context; the ring splits that work across devices and overlaps the key/value passing with compute.

LongVILA (arXiv:2408.10188) adapted the pattern to VLMs. 1400-frame videos at 192 tokens per frame = 268k context, trained with ring attention across 8-way parallelism.

Idea 3 · Path 3: Token compression (Video-XL, LongVA)

Cheaper than brute context: compress aggressively before the LLM sees the sequence.

Video-XL (arXiv:2409.14485) uses a visual summary token: each clip of N frames produces a single "summary" token that attends over the N. At inference, the LLM sees one summary token per clip, drastically shrinking the context.

LongVA (arXiv:2406.16852) uses "long context transfer": extend the language model's context on long text first (to about 224K tokens), then add vision. Without long-video training, it processes over 2,000 frames, more than 200K visual tokens.

Token compression trades off recall at specific timestamps for scalability. The model knows generally what happened but sometimes misses exact frames.

Idea 4 · Path 4: Agentic retrieval (VideoAgent)

Do not feed the full video to the LLM. Instead, treat the video as a database and use an LLM to query it.

VideoAgent (arXiv:2403.10517):

  1. LLM reads the question.
  2. LLM asks a retrieval tool for relevant clips ("show me segments with a cat").
  3. Tool returns matching clip timestamps.
  4. LLM reads those clips via a VLM.
  5. LLM composes the answer or asks follow-up queries.

This is the LLM-as-agent pattern applied to long video. Cheaper inference (only relevant clips encoded), harder engineering (retrieval quality becomes the bottleneck).

The same idea as a formula

Token count of a long video at f frames per second, n tokens per frame, duration D seconds: N=fDn.

Blockwise attention (ring attention's core). Split keys and values into blocks j=1,…,B. For each query block keep a running max m, denominator s and weighted sum a; for each arriving block with scores Sj​:

m′=max(m,maxSj​),s′=sem−m′+∑eSj​−m′,a′=aem−m′+eSj​−m′Vj​,
and the output is a/s, exactly the full softmax attention. Memory per device holds one BN​×BN​ block instead of N×N; total compute is unchanged.

Retrieval cost. Reading k of C clips costs k/C of the full video's tokens, plus one embedding lookup per query.

Worked example
A 2-hour video, four ways
  • Brute context at 1 fps with 72 tokens per second (Lesson 12.9's 448 × 252 setting): 7,200×72=518,400 tokens.
  • Ring attention over 8 devices: each holds 64,800 tokens of the sequence; the largest score block per step is 64 times smaller than the full matrix.
  • Compression to one summary token per second of video: 7,200 tokens.
  • Retrieval of 3 one-minute clips: 3×60×72=12,960 tokens, 2.5% of the full video, provided the right clips are found.
Check your mental model
  • ✗ "Ring attention reduces the compute of long attention."
    ✓ It splits memory and work across devices; total compute stays quadratic.
  • ✗ "Retrieval is always cheaper and just as good."
    ✓ It is far cheaper, but a missed clip means a wrong answer, and similar descriptions confuse the search.
  • ✗ "A 1M-token context means the model uses all of it equally well."
    ✓ Recall depends on position, length and distractors; measure at your own lengths.
Predict before you run

A 2-hour cooking video is indexed as 120 one-minute clip descriptions, with one unusual moment at minute 83 (the chef drops a red spatula). Will a small embedding model retrieve minute 83 for "When does the chef drop something?" and for "What colour is the spatula?" (Solution P1.)

See it drawn
Agentic retrieval over a long video

120 one-minute clip descriptions stand in for what a VLM would write while indexing a 2-hour video. They are embedded with bge-small-en-v1.5, and three questions retrieve their top-3 clips by cosine similarity. The run then compares the tokens needed to read the whole video with those for the retrieved clips. A few seconds.

import random, time
from sentence_transformers import SentenceTransformer
random.seed(0)
# The VideoAgent pattern on a 2-hour cooking-show video: describe each 1-minute clip once (here: written captions
# standing in for a VLM's descriptions), embed them, and retrieve only the clips a question needs.
topics = ["chopping onions", "boiling pasta", "making tomato sauce", "kneading dough", "grilling vegetables",
          "plating dessert", "talking to the audience", "washing dishes", "tasting the soup", "baking bread"]
captions = [f"Minute {m}: the chef is {random.choice(topics)}." for m in range(120)]
captions[83] = "Minute 83: the chef drops a red spatula on the floor and laughs."     # the needle
emb = SentenceTransformer("BAAI/bge-small-en-v1.5")
t = time.time()
index = emb.encode(captions, normalize_embeddings=True)
print(f"indexed 120 clip descriptions in {time.time() - t:.1f} s")

for q in ["When does the chef drop something?", "When is bread baked?", "What colour is the spatula?"]:
    qv = emb.encode([q], normalize_embeddings=True)[0]
    top = (index @ qv).argsort()[::-1][:3]
    print(f"\nQ: {q}")
    for i in top: print(f"   {index[i] @ qv:.3f}  {captions[i]}")

per_min = 60 * 144                       # 1 fps, 448x252 frames at 144 tokens per frame pair (Lesson 12.9) -> 72 tokens/s
print(f"\ntokens to read the whole video at 1 fps: {120 * per_min // 2:,}; to read the top-3 clips: {3 * per_min // 2:,}")

Reading this output

One question finds the needle, the other misses it. "What colour is the spatula?" retrieves minute 83 first (score 0.582), because "spatula" appears in that description. "When does the chef drop something?" does not: the top three are "plating dessert" clips (about 0.70). The small embedding model matches the general cooking phrasing better than the rarer verb "drops". A retrieval-only agent would answer this question confidently and wrongly.

Repeated content crowds the results. "When is bread baked?" returns three different "baking bread" minutes. The video has several, so the top 3 cannot cover every occurrence. Real agents need time-ordered results, deduplication or a larger k for "when" questions.

The saving is large. Reading the whole 2-hour video at 1 fps costs about 518,400 tokens; reading three retrieved one-minute clips costs 12,960, 2.5%. That is why retrieval is the practical path for very long videos, provided you improve recall. Index richer descriptions (actions as well as topics), combine text and image embeddings, query with several rephrasings, and let the agent ask follow-up searches.

See it drawn
Ring attention's block-by-block computation, verified

Attention over 4,096 tokens computed as if split across 8 devices: each device's queries see the key/value blocks one at a time, as they would arrive around a ring, with an online softmax. The run compares the result with full attention and the memory needed. Instant.

import torch
torch.manual_seed(0)
# Ring attention's core trick: attention over a long sequence computed block by block, as if each block of keys and
# values lived on a different device and arrived in turn. An online softmax makes the result exact.
N, d, devices = 4096, 64, 8
q, k, v = (torch.randn(N, d, dtype=torch.float64) for _ in range(3))
full = torch.softmax(q @ k.T / d ** 0.5, dim=-1) @ v                # needs the full N x N score matrix

chunk = N // devices
out = torch.zeros(N, d, dtype=torch.float64)
for dev in range(devices):                                          # the queries held by one device
    qi = q[dev * chunk:(dev + 1) * chunk]
    m = torch.full((chunk, 1), -float("inf"), dtype=torch.float64)  # running max
    s = torch.zeros(chunk, 1, dtype=torch.float64)                  # running softmax denominator
    acc = torch.zeros(chunk, d, dtype=torch.float64)                # running weighted sum of values
    for step in range(devices):                                     # key/value blocks arrive around the ring
        j = (dev + step) % devices
        kj, vj = k[j * chunk:(j + 1) * chunk], v[j * chunk:(j + 1) * chunk]
        sc = qi @ kj.T / d ** 0.5
        m_new = torch.maximum(m, sc.max(-1, keepdim=True).values)
        scale = torch.exp(m - m_new)
        p = torch.exp(sc - m_new)
        s = s * scale + p.sum(-1, keepdim=True)
        acc = acc * scale + p @ vj
        m = m_new
    out[dev * chunk:(dev + 1) * chunk] = acc / s

print(f"sequence {N:,} tokens split over {devices} devices of {chunk} tokens each")
print(f"blockwise result vs full attention: max difference {(out - full).abs().max():.1e}")
print(f"largest score matrix held at once: full {N * N:,} entries; per device per step {chunk * chunk:,} "
      f"({N * N // (chunk * chunk)}x smaller)")
print(f"compute is unchanged: {devices} x {devices} blocks of {chunk}x{chunk} = {devices * devices * chunk * chunk:,} scores")
What you should see
sequence 4,096 tokens split over 8 devices of 512 tokens each
blockwise result vs full attention: max difference 1.9e-16
largest score matrix held at once: full 16,777,216 entries; per device per step 262,144 (64x smaller)
compute is unchanged: 8 x 8 blocks of 512x512 = 16,777,216 scores
Reading this output

Blockwise attention is exact. Splitting the 4,096 keys and values into 8 blocks and accumulating them one at a time with an online softmax gives the same output as full attention to within 1.9e-16, float64 rounding. Nothing is approximated, which is why ring attention can train long-context models without changing what they compute.

Memory is what shrinks. Full attention needs a 16.8-million-entry score matrix. Each device here only ever holds a 512 × 512 block, 64 times smaller, and passes its keys and values on around the ring. Adding devices lets the sequence grow proportionally.

Compute does not shrink. The 64 blocks add up to the same 16.8 million scores. Ring attention spreads quadratic work over more hardware and overlaps it with communication; it does not make long attention cheaper. That is why compression and retrieval still matter.

Idea 5 · Needle-in-a-haystack benchmarks

The standard long-context test: insert a unique visual or textual marker at a random point in the video, then ask a query that requires recalling it.

Metric: Recall@k across video length and marker position.

Long-context frontier models report near-perfect video needle recall at hour scale; open models generally degrade sooner as videos get longer, and results depend heavily on how many frames and tokens per frame they are given. Treat published numbers as setup-specific and test at your own lengths.

Agentic retrieval can match or beat raw-context models on very long videos, but only when the retrieval step finds the right clips; when it misses, the answer is wrong however strong the VLM is (measured below).

Idea 6 · Which path to pick

For a 15-minute clip: an open long-context VLM with native video input usually works (Qwen3-VL has a 256K native context, for example).

For 30-minute to 1-hour content: long-context open models with reduced fps and pooling, or token-compression models such as Video-XL; hosted long-context models when quality matters most.

For 2+ hour content: VideoAgent or similar retrieval patterns. Alternatively, summarize to smaller chunks and feed hierarchical summaries.

Idea 7 · 2026 production pattern

In practice, production long-video pipelines are hybrid:

  1. Run dynamic-FPS sampling + aggressive pooling on the entire video (get a 100k-token global representation).
  2. Pass it to a long-context VLM for a global summary and per-segment descriptions.
  3. If user asks detailed questions, run agentic retrieval using the summary as an index.

This combines brute-context for global understanding and retrieval for local detail.

Industry practice
What's current (2024–2026)
  • Hosted long-context video: Gemini models accept long videos directly; for Claude, send sampled frames as images (Lesson 12.1's token costs apply per image).
  • Open long-context VLMs: Qwen3-VL (256K native context), InternVL3.5 and LongVILA-style systems handle long videos with reduced fps and per-frame merging.
  • Sequence parallelism (ring attention, Ulysses, context parallelism in Megatron and DeepSpeed) is standard for long-context training.
  • Agentic video pipelines: index clips with VLM descriptions plus speech transcripts, retrieve by text and by image embeddings, then read only the retrieved clips; this is the practical path on a laptop GPU.

Sources: Gemini 1.5 report (arXiv 2403.05530), Ring Attention (arXiv 2310.01889), LWM (arXiv 2402.08268), LongVILA (arXiv 2408.10188), LongVA (arXiv 2406.16852), Video-XL (arXiv 2409.14485), VideoAgent (arXiv 2403.10517).

Recap
What to keep from this lesson
  • Long video is hundreds of thousands of tokens even at 1 fps.
  • Four paths: huge context, ring attention, compression, agentic retrieval.
  • Ring attention is exact blockwise attention across devices; memory splits, compute does not shrink.
  • Retrieval reads a few percent of the tokens but fails when the search misses.
  • Production pipelines mix them: a compressed global pass plus retrieval for detail.

Solutions

SolutionP1 · One question finds it, the other does not

Only one. "What colour is the spatula?" retrieves minute 83 first, because the word "spatula" is in its description. "When does the chef drop something?" retrieves three "plating dessert" clips instead and misses the moment entirely. With retrieval, the answer is only as good as the search, and similar-looking descriptions and paraphrased questions are where small embedders fail.

SolutionB1 · The index cannot see

The red car never appears in the transcripts, unless someone happens to say "red car". The search returns clips where the words are similar, or nothing relevant, and the agent either says it cannot find a car or describes the wrong clip. No VLM gets to look at the right frames, because retrieval never selects them. Fix the index so it covers what is seen as well as what is said. Add VLM-written visual descriptions per clip (objects, actions, colours, on-screen text) and image embeddings of sampled frames (CLIP or SigLIP), so "red car" can match visually. Run both searches and merge the results. Then test recall on questions about visual-only events, as the run above does for the spatula.
