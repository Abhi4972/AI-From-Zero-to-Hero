Why this came about

GPT-3 (2020) could do remarkable things if you phrased the prompt cleverly, but asked a question directly it might ignore it or ramble. In 2022 OpenAI's InstructGPT paper showed a fix in three steps: fine-tune on examples of good responses written by people; collect people's comparisons of pairs of responses and train a reward model on them; then use reinforcement learning to make the model produce responses the reward model scores highly (RLHF). A 1.3-billion-parameter InstructGPT was preferred by people over the 175-billion-parameter GPT-3. ChatGPT, released in November 2022, used the same recipe. In 2023 DPO showed the preference step could be done without a separate reward model or reinforcement learning, and it became widely used for open models.

In plain words first
A well-read intern, then on-the-job training

A base model is like a brilliant new hire who has read the whole library but never worked a help desk: ask them something and they might reply, or might continue your sentence. Instruction tuning is a few weeks of shadowing: they study thousands of examples of good answers in the house format. Preference tuning is feedback from a manager: shown two of their drafts, the manager says which is better, and they learn to do more of what gets chosen. After that, the same knowledge comes out as helpful answers.

Step 1 · Same size, same knowledge, different behaviour

SmolLM2 is a family of small open models from Hugging Face, released both as a base model and as an instruct version fine-tuned from it. Give both the same request:

import torch
import torch.nn.functional as F
from transformers import AutoTokenizer, AutoModelForCausalLM

request = "How do I reset my password on a shopping website?"

base_tok = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM2-360M")
base = AutoModelForCausalLM.from_pretrained("HuggingFaceTB/SmolLM2-360M")
ids = base_tok(request, return_tensors="pt")
out = base.generate(**ids, max_new_tokens=50, do_sample=False, pad_token_id=base_tok.eos_token_id)
print("BASE MODEL:\n" + base_tok.decode(out[0][ids["input_ids"].shape[1]:], skip_special_tokens=True))
What you should see
BASE MODEL:


Reset your password on a shopping website

If you have forgotten your password, you can reset it on a shopping website.

To reset your password, you will need to:

  • Log in to your shopping website
  • Click

The base model treats the request as the title of some web page and continues it: a heading, then the start of an article. That can look helpful, but it is continuing a document, not answering you; with other prompts, base models often add more questions or drift off topic. Now the instruct model, given the request as a chat message:

chat_tok = AutoTokenizer.from_pretrained("HuggingFaceTB/SmolLM2-360M-Instruct")
chat = AutoModelForCausalLM.from_pretrained("HuggingFaceTB/SmolLM2-360M-Instruct")
messages = [{"role": "user", "content": request}]
ids = chat_tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt", return_dict=True)
out = chat.generate(**ids, max_new_tokens=80, do_sample=False, pad_token_id=chat_tok.eos_token_id)
print("INSTRUCT MODEL:\n" + chat_tok.decode(out[0][ids["input_ids"].shape[1]:], skip_special_tokens=True))
What you should see
INSTRUCT MODEL:
To reset your password on a shopping website, follow these steps:

1. Log into your account on the website.
2. Look for a "Forgot Password" or "Reset Password" link usually located in the top right corner of the website.
3. Click on this link.
4. You will be asked to enter your email address associated with your account.
5.

The instruct model answers the question, in steps. It has the same architecture and the same pretraining as the base model; the difference comes from a much smaller amount of further training on conversations. (A 360-million-parameter model is tiny by today's standards, so its advice is generic; the behaviour change is the point.)

Step 2 · Chat templates

A chat model still reads one sequence of tokens. A chat template turns the list of messages into that sequence, using special tokens to mark each turn:

messages = [
    {"role": "system", "content": "You are a helpful support agent for an online shop."},
    {"role": "user", "content": "Where is my order SK-48213?"},
]
text = chat_tok.apply_chat_template(messages, add_generation_prompt=True, tokenize=False)
print(text)
print("special tokens used:", [t for t in chat_tok.all_special_tokens if t in text])
What you should see
<|im_start|>system
You are a helpful support agent for an online shop.<|im_end|>
<|im_start|>user
Where is my order SK-48213?<|im_end|>
<|im_start|>assistant

special tokens used: ['<|im_start|>', '<|im_end|>']
Reading this output
  • Each message is wrapped in <|im_start|>role ... <|im_end|> (the "ChatML" style; Llama, Gemma and others use their own markers). These are single special tokens that never appear in normal text.
  • add_generation_prompt=True ends the text with <|im_start|>assistant, the cue for the model to write the assistant's turn. It stops when it generates <|im_end|>.
  • The system message holds standing instructions (role, rules, tone). Lesson 11.1 covers how to use the message roles through an API.
  • Using the wrong template, or none, makes a chat model behave much worse, because it was trained only on text in its own format. apply_chat_template reads the correct one from the model's files.

Step 3 · Supervised fine-tuning, and what is trained on

Supervised fine-tuning (SFT) continues training with the same next-token loss, on conversations that show the desired behaviour: questions with good answers, instructions with good completions, multi-turn dialogues. Typical datasets range from tens of thousands to a few million examples, tiny compared with pretraining. One detail matters: the model should learn to write the assistant's replies, not to imitate users. So the loss is computed only on the assistant's tokens; the rest are masked out with the label −100, which PyTorch's cross-entropy ignores.

conversation = messages + [{"role": "assistant", "content": "It left our warehouse yesterday and should arrive on Friday."}]
prompt_ids = chat_tok.apply_chat_template(messages, add_generation_prompt=True, return_dict=False)   # token ids before the reply
full_ids = chat_tok.apply_chat_template(conversation, return_dict=False)                             # the whole conversation

labels = [-100] * len(prompt_ids) + full_ids[len(prompt_ids):]       # -100 = do not train on this token
trained = [t for t in labels if t != -100]
print(f"tokens in the example: {len(full_ids)}, tokens the loss is computed on: {len(trained)}")
print("trained on:", repr(chat_tok.decode(trained)))
What you should see
tokens in the example: 50, tokens the loss is computed on: 13
trained on: 'It left our warehouse yesterday and should arrive on Friday.<|im_end|>\n'

Only the reply (and its end-of-turn token) contributes to the loss. Fine-tuning a whole model this way needs the memory of Lesson 3.20 (about 16 bytes per parameter); in practice most teams use LoRAlater · 3.24, which trains small added matrices instead (Lesson 14.139).

Step 4 · Learning from preferences

Writing perfect answers is slow; judging which of two answers is better is fast and captures things that are hard to write down, such as tone and helpfulness. Preference tuning uses many such comparisons.

RLHF, step 1: a reward model. A reward model (usually a copy of the language model with a single-number output) is trained so that the preferred answer gets a higher score. The standard Bradley–Terry model says the probability that A is preferred over B is the sigmoid of the score difference (Lesson 2.6), and the loss is the binary cross-entropy of that:

def preference_loss(score_chosen, score_rejected):
    p = torch.sigmoid(torch.tensor(score_chosen - score_rejected))   # P(chosen is preferred)
    return p.item(), -torch.log(p).item()

for chosen, rejected in [(2.0, -1.0), (0.5, 0.0), (-1.0, 1.0)]:
    p, loss = preference_loss(chosen, rejected)
    print(f"reward chosen {chosen:+.1f}, rejected {rejected:+.1f}:  P(chosen preferred) {p:.2f}  loss {loss:.2f}")
What you should see
reward chosen +2.0, rejected -1.0:  P(chosen preferred) 0.95  loss 0.05
reward chosen +0.5, rejected +0.0:  P(chosen preferred) 0.62  loss 0.47
reward chosen -1.0, rejected +1.0:  P(chosen preferred) 0.12  loss 2.13

When the reward model already ranks the pair correctly by a wide margin, the loss is small; when it ranks them the wrong way round, the loss is large and training pushes the scores apart in the right direction.

RLHF, step 2: reinforcement learning. The assistant generates answers, the reward model scores them, and an algorithm such as PPOlater · 9.10 nudges the assistant towards higher-scoring answers (Lesson 2.11's reward loop). A penalty keeps it close to the SFT model, so it cannot drift into strange text that happens to fool the reward model, a failure called reward hacking.

DPO (Direct Preference Optimisation, 2023) skips the reward model and the reinforcement learning. It trains directly on (prompt, chosen, rejected) triples, raising the probability of the chosen answer and lowering that of the rejected one, measured relative to a frozen copy of the starting model:

def dpo_loss(logp_chosen, logp_rejected, ref_chosen, ref_rejected, beta=0.1):
    """Log-probabilities of whole answers under the model being trained and under the frozen reference."""
    margin = beta * ((logp_chosen - ref_chosen) - (logp_rejected - ref_rejected))
    return -F.logsigmoid(torch.tensor(margin)).item()

print(f"start (policy = reference):         loss {dpo_loss(-40.0, -38.0, -40.0, -38.0):.3f}")
print(f"chosen more likely, rejected less:  loss {dpo_loss(-35.0, -45.0, -40.0, -38.0):.3f}")
print(f"the wrong way round:                loss {dpo_loss(-45.0, -33.0, -40.0, -38.0):.3f}")
What you should see
start (policy = reference):         loss 0.693
chosen more likely, rejected less:  loss 0.263
the wrong way round:                loss 1.313

At the start, the model equals the reference and the loss is log 2 ≈ 0.693. Making the chosen answer more likely and the rejected one less likely (relative to the reference) lowers the loss. beta controls how far the model may move from the reference. Many open models use DPO or variants of it; frontier labs use mixtures of methods.

Step 5 · Who provides the feedback, and what it aims at

Approach Feedback from Notes
RLHF human raters comparing answers expensive; raters' preferences and blind spots are learned too
RLAIF / Constitutional AI (Anthropic, 2022) an AI model judging answers against a written set of principles scales cheaply; the principles are explicit and can be inspected
Verifiable rewards automatic checks: is the maths answer right, do the tests pass? the basis of reasoning modelslater · 10.14 (Lesson 10.14)

The usual goals are summed up as helpful, honest and harmless. Preference tuning also has side effects: models can become sycophantic (agreeing with the user, flattering), because raters often prefer agreeable answers, and verbose, because longer answers can look more thorough. Recognising these tendencies is part of using models well (Lesson 10.32).

The same idea as a formula
  • SFT loss: −Σ_t m_t log p_θ(x_{t+1} | x_{≤t}) / Σ_t m_t, with m_t = 1 only on assistant tokens
  • Bradley–Terry: P(A ≻ B) = σ(r(A) − r(B)); reward-model loss = −log σ(r(chosen) − r(rejected))
  • RLHF objective: maximise E[r(y)] − β · KL(π_θ ‖ π_ref)
  • DPO loss: −log σ(β[(log π_θ(y_w) − log π_ref(y_w)) − (log π_θ(y_l) − log π_ref(y_l))])
Check your mental model
  • ✗ "An instruct model knows more than its base model."
    ✓ Nearly all knowledge comes from pretraining. Instruction and preference tuning change how that knowledge is expressed.
  • ✗ "RLHF teaches the model what is true."
    ✓ It teaches what people (or a judge modellater · 14.32) prefer. Preferred and true usually agree, but not always; sycophancy is the visible gap.
  • ✗ "The chat template is just formatting and can be skipped."
    ✓ The model was trained on exactly that format; skipping it degrades behaviour badly.

Exercises

Predict before you run

In Step 3, if you append a second user question and a second assistant reply to conversation, and mask everything except assistant replies, roughly how many of the tokens will be trained on? (Solution P1.)

Make it your own

Give the instruct model of Step 1 a system message such as "You answer in at most two sentences and always ask for the order number." and the same user request. How does the answer change? (Solution M1.)

Practice
Apply it

With dpo_loss, keep the rejected answer fixed at the reference (logp_rejected = ref_rejected = -38) and raise logp_chosen from −40 to −30 in steps of 2 (reference −40). How does the loss change, and what does beta = 1.0 instead of 0.1 do? (Solution X1.)

Solutions

SolutionP1 · Masking a longer conversation

Both assistant replies are trained on, while the system message, both user messages and all the template tokens around them are masked. For short replies, that is usually well under half of the tokens. To mask correctly in multi-turn data, compute the boundaries of each assistant turn; libraries such as TRL do this for you.

SolutionM1 · A system message

The reply typically becomes shorter and asks for the order number, because instruct models are trained to follow system instructions. Small models follow them less reliably than large ones; test any system promptlater · 11.1 on many inputs before relying on it (Lesson 11.9).

SolutionX1 · Exploring DPO

As the chosen answer's log-probability rises from −40 to −30 (relative to the reference), the margin grows from 0 to 1.0 and the loss falls from 0.693 towards about 0.31. With beta = 1.0 the same changes give margins ten times larger, so the loss falls much faster (to about 0.00005): a larger beta trusts the preference data more and lets the model move further from the reference.

Recap
  • A base model continues text; an instruct model, fine-tuned from it, answers requests. Knowledge comes mostly from pretraining.
  • Chat templates turn messages into one token sequence with special tokens marking roles and turns; models must be used with their own template.
  • Supervised fine-tuning trains on good example conversations, computing the loss only on the assistant's tokens.
  • RLHF trains a reward model on human comparisons (Bradley–Terry) and then optimises the assistant against it with a penalty for drifting; DPO optimises directly on preference pairs.
  • Feedback can come from people, from AI judges following principles, or from automatic checks; preference tuning can also introduce sycophancy and verbosity.
