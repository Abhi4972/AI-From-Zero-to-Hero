Why this came about

Prompt changes caused production incidents just like code changes, but they were often edited without review or tests. Teams began treating prompts as software artifacts, with version control, registries, evaluation sets and gradual rollout, borrowing practices from software release management.

In plain words first
Prompts are code that happens to be in English

A prompt change can break an application as surely as a code change, so prompts get the same treatment as code: stored in version control or a prompt registry, given versions, reviewed, tested against a fixed set of examples before release, and rolled out gradually. Each answer should be traceable to the prompt version that produced it.

Prompts as managed assets

  • Version prompts like code: a registry (LangSmithlater · 6.8, Langfuse, MLflow Prompt Registry, Azure and Vertex prompt management) or plain files in git, with the version recorded on every trace.
  • Change one thing at a time, and run the eval set before and after (Lesson 12.11).
  • Keep prompts model-specific. A prompt tuned for one model family may underperform on another. When you switch models, re-tune.

Step by step: from a string to a managed, tested prompt

The rest of this lesson builds the prompt machinery that production teams end up writing, one piece at a time. Every block runs offline.

Step 1 · Templates with strict variables and versions

A prompt in production is a template with variables (today's date, the customer's tier, the language), stored under a version so every trace can say exactly which prompt produced it. A strict template engine fails loudly on a missing variable instead of sending the model a prompt with a hole in it.

import hashlib, json
from datetime import date
from jinja2 import Environment, StrictUndefined

env = Environment(undefined=StrictUndefined)           # a missing variable raises instead of rendering ""

class PromptRegistry:
    """A minimal prompt registry: named, versioned templates with a content hash.
    Real ones (LangSmith, Langfuse, MLflow, cloud prompt management) add a UI, aliases and access control."""
    def __init__(self):
        self.versions: dict[str, list[dict]] = {}
        self.aliases: dict[str, int] = {}

    def register(self, name: str, template: str, note: str) -> int:
        versions = self.versions.setdefault(name, [])
        versions.append({"template": template, "note": note,
                         "sha": hashlib.sha256(template.encode()).hexdigest()[:10]})
        return len(versions)                                   # versions are numbered from 1

    def set_alias(self, name: str, alias: str, version: int):
        self.aliases[f"{name}@{alias}"] = version              # e.g. support-system@production -> 2

    def render(self, ref: str, **variables) -> tuple[str, dict]:
        name, _, alias = ref.partition("@")
        version = self.aliases[ref] if alias else len(self.versions[name])
        entry = self.versions[name][version - 1]
        text = env.from_string(entry["template"]).render(**variables)
        return text, {"prompt": name, "version": version, "sha": entry["sha"]}   # put this on the trace

registry = PromptRegistry()
registry.register("support-system", "You are ShopKart support. Today is {{ today }}. Reply in {{ language }}.",
                  note="first version")
registry.register("support-system",
                  "You are ShopKart support for {{ tier }} customers. Today is {{ today }}. Reply in {{ language }}.\n"
                  "Refunds above INR {{ refund_limit }} need human approval.",
                  note="adds tier and refund limit after eval case R-12 failed")
registry.set_alias("support-system", "production", 1)

prod, meta = registry.render("support-system@production", today=date(2026, 10, 27), language="Hindi")
print(meta, "|", prod)
latest, meta = registry.render("support-system", today=date(2026, 10, 27), language="Hindi", tier="gold", refund_limit=5000)
print(meta)
try:
    registry.render("support-system", today=date(2026, 10, 27), language="Hindi")   # forgot tier and refund_limit
except Exception as e:
    print("caught:", type(e).__name__, e)

The hash identifies the exact template text, so a trace can prove which wording ran. Production stays pinned to version 1 through the alias until version 2 passes the eval set; promoting it is a one-line alias change, and rolling back is the same line.

Step 2 · Test prompts like code

Prompt changes break things silently, so put the rendered prompt under tests that run in CI, before any model call: required sections present, no unfilled variables, a token budget, today's date injected, and the examples valid.

import re

def check_prompt(text: str, budget_tokens: int = 1500) -> list[str]:
    """Return a list of problems with a rendered system prompt; empty means it passes."""
    problems = []
    for section in ("<role>", "<instructions>", "<tool_guidance>", "<output_format>"):
        if section not in text:
            problems.append(f"missing section {section}")
    if re.search(r"\{\{.*?\}\}|\{[a-z_]+\}", text):
        problems.append("unrendered template variable")
    if approx_tokens(text) > budget_tokens:
        problems.append(f"over budget: ~{approx_tokens(text)} tokens")
    if "INR" not in text:
        problems.append("currency rule missing")
    return problems

print("SYSTEM prompt:", check_prompt(SYSTEM) or "passes")
print("version 2 prompt:", check_prompt(latest))
What you should see
SYSTEM prompt: passes
version 2 prompt: ['missing section <role>', 'missing section <instructions>', 'missing section <tool_guidance>', 'missing section <output_format>']

Static checks catch broken prompts; behavioural checks (does the agent now follow rule 3?) belong in the eval set of Lesson 12.11. Run both on every prompt change.

Industry practice
How prompt work is organized in mature teams
  • Prompts live in version control or a registry, are reviewed like code, and are deployed by alias, never edited live in production.
  • Every rule in a system prompt points to the eval caselater · 11.9 that made it necessary; rules with no failing case are candidates for deletion.
  • Domain experts edit prompts through a playground connected to the eval set (Hamel Husain's advice), so changes are judged by evidence.
  • Context is assembled by code with an explicit budget per section, and the assembled context is logged on the trace (redacted) so incidents can be replayed.

From the field
Shopify and Manus: context engineering lessons from production agents

Shopify Sidekick (August 2025): as Sidekick grew into dozens of tools, the system prompt filled with special-case rules, which the team called "death by a thousand instructions". Tool boundaries blurred past about 20 tools and became hard to reason about past 50. Their fix was just-in-time instructions: return the relevant guidance together with a tool's result, only when that tool is used, which kept the base prompt small and stable (good for prompt caching) and made behavior easier to change per feature. Shopify Engineering

Manus (July 2025), an agent that averages around 50 tool callslater · 3.1 per task with an input-to-output token ratio near 100:1: the team treats KV-cache hit rate as the most important production metric, because cached input on Claude Sonnet cost 0.30 USD per million tokens against 3 USD uncached. Their rules: keep the prompt prefix stable (no timestamps at the top), make context append-only, mask tools rather than removing them mid-run, use the file system as unlimited, restorable memory, keep a todo.md the agent rewrites to keep its goal in recent attention, leave errors in the context so the model learns from them, and vary serialization so the agent does not fall into a repetitive rut. Solutions

SolutionP1 · Missing fails, extra is ignored

The registry renders with Jinja's StrictUndefined, so the missing customer raises UndefinedError: 'customer' is undefined before any model call. The extra customer_name is silently ignored, by Jinja and by Python's str.format alike, so a misspelled variable shows up only as the missing one. LangChain's templates also raise on missing variables. To catch extras too, compare the variables passed with the template's declared variables (Jinja's meta.find_undeclared_variables) and reject unknown names.

SolutionB1 · Unversioned prompts cannot be traced

With the prompt edited in place, logs cannot say which text was live at that time, so you cannot reproduce the reply or know whether the change caused it. Give every prompt change a new version, log the version with every call (Lesson 12.13), and keep old versions so you can replay and roll back.

SolutionD1 · Test behavior, not text

The tests check the prompt's text, not the model's behavior. Add eval cases with real inputs and expected facts, here refund-timeline questions with the correct answers, run them against the new prompt with the production model, and compare with the old version before release (Lesson 12.15). Text checks are a lint; behavior checks are the test.

SolutionM1 · Rollback with an audit trail

Aliases already separate "which version is live" from the versions themselves, so a rollback is set_alias(name, alias, current - 1) plus an entry (timestamp, user, reason, from_version, to_version) in an alias log. Rollback must not delete versions, so you can roll forward again. Managed prompt hubs (LangSmith, Langfuse, MLflow, cloud prompt catalogs) offer the same with labels such as production and staging.

Check your understanding

Explain the mechanismHow do you manage prompts in production?

Worked answer. As versioned assets: templates with strict variables, stored in a registry or a prompt hub, each change a new version with an owner and a reason, the active version selected by configuration so a rollback needs no deploy, the version logged with every call, and every change gated by an eval run against the previous version. Prompts are reviewed like code, because a one-line change can alter behavior everywhere.

A plausible wrong answer. "Keep them in the code as strings." That works for small projects, but without versions in logs and eval gates you cannot debug or roll back safely.

Follow-ups. What goes in a prompt's eval suite?

Debug a failureTwo services use "the same" prompt but behave differently. What do you check?

Worked answer. Whether they actually send the same text: the versions they load, the variables they fill, the templates' whitespace and order, the model and its parameters, and anything added around the prompt, such as tools, history or retrieved context. I would log the final rendered request from both and diff them; differences are usually in the variables or the surrounding context, not the template.

A plausible wrong answer. "Models are random." Sampling varies outputs, but consistent differences point to different inputs.

Follow-ups. How would you make rendered prompts reproducible from logs?

Defend a designShould product managers edit production prompts directly?

Worked answer. Yes, through the same controls engineers use: a prompt hub with versions, review, an automatic eval run and a staged rollout, and a rollback. Domain experts often write better instructions and examples than engineers, so blocking them slows improvement; letting anyone edit live prompts without evals causes incidents. The process, not the role, is what keeps it safe.

A plausible wrong answer. "No, prompts are code." They are code-like assets, and the right answer is code-like controls, not exclusion.
