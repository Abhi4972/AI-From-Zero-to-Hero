In plain words first
The idea in one line

Quantization format is not a universal choice — it is a function of hardware, serving engine, and workload. GGUF Q4_K_M or Q5_K_M owns CPU and edge, delivered through llama.cpp and Ollama. GPTQ wins inside vLLM when you need multi-LoRA on the same base. AWQ with Marlin-AWQ kernels delivers ~741 tok/s on a 7B class model with the best Pass@1 at INT4 — the 2026 default for datacenter production. FP8 stays the middle ground on Hopper, Ada, and Blackwell — near-lossless and widely supported. NVFP4 and MXFP4 (Blackwell microscaling) are aggressive and require per-block validation. Two traps bite teams: calibration dataset must match deployment domain, and KV cache is separate from weight quantization — the AWQ lesson "my model is 4 GB now" forgets the 10-30 GB KV cache at production batch sizes.

The problem

In plain words first

Quantization stores a model's numbers with fewer bits: 8 or 4 instead of 16. Fewer bits mean a smaller model, less memory to read for each token and so faster generation, at some cost in accuracy. There are several formats, each made for a different place. GGUF files are for laptops and CPUs (llama.cpp, Ollama). AWQ and GPTQ are 4-bit formats for GPU servers; they look at sample data (a calibration set) to decide which weights matter most. FP8 is an 8-bit format that newer NVIDIA GPUs run natively, with almost no quality loss. NVFP4 and MXFP4 are 4-bit formats for Blackwell GPUs. Two traps catch most teams: quantizing the weights does not shrink the KV cache, and 4-bit models lose more on reasoning tasks than on chat.

Quantization reduces memory and HBM bandwidth, which is exactly what decode needs. An FP16 70B model is 140 GB of weights. Quantize weights to INT4 (AWQ or GPTQ) and the model is 35 GB — fits in one H100 with room for KV cache, which matters because at 128 concurrent sequences with 2k context, KV cache alone is 20-30 GB.

But quantization is not free. Aggressive quantization degrades quality, especially on reasoning-heavy tasks. Different formats work with different engines. Different hardware supports different precisions natively. The 2026 format zoo is real and you cannot copy someone else's choice — you have to pick based on your stack.

Idea 1 · The six formats

AWQ 4 Datacenter GPU production vLLM (Marlin-AWQ), TGI
FP8 8 Hopper/Ada/Blackwell datacenter vLLM, TRT-LLM, SGLang
MXFP4 4 Blackwell multi-user TRT-LLM
NVFP4 4 Blackwell multi-user TRT-LLM

Idea 2 · GGUF — the CPU/edge default

GGUF is a file format, not a quantization scheme per se — it bundles K-quant variants (Q2_K, Q3_K_M, Q4_K_M, Q5_K_M, Q6_K, Q8_0) in one container. Q4_K_M and Q5_K_M are the production defaults — near-BF16 quality at 4-5 bits. Best choice for CPU or edge serving because llama.cpp is by far the fastest CPU inference engine.

Throughput penalty in vLLM: ~93 tok/s on 7B — the format is not optimized for GPU kernels. Use GGUF when the deployment target is CPU/edge. Not otherwise.

Idea 3 · GPTQ — multi-LoRA in vLLM

GPTQ is a post-training quantization algorithm with a calibration pass. Marlin kernels make it fast on GPU (2.6x speedup vs non-Marlin GPTQ). ~712 tok/s on 7B.

The unique win: GPTQ-Int4 supports LoRA adapters in vLLM. If you are serving a base model plus 10-50 fine-tuned variants (each as a LoRA), GPTQ is your path. NVFP4 does not support LoRA yet as of early 2026.

Idea 4 · AWQ — the datacenter GPU default

Activation-aware Weight Quantization. Protects the ~1% most-salient weights during quantization. Marlin-AWQ kernels: 10.9x speedup vs naive. ~741 tok/s on 7B, best Pass@1 among INT4 formats.

Pick AWQ for new GPU serving unless you need multi-LoRA (GPTQ) or aggressive Blackwell FP4 (NVFP4).

Idea 5 · FP8 — the reliable middle

8-bit floating point. Near-lossless. Widely supported. Hopper Tensor Cores accelerate FP8 natively. Blackwell inherits. FP8 is the safe 2026 default when quality is non-negotiable (reasoning, medical, code-gen). Memory savings are half of INT4 but quality risk is far lower.

Idea 6 · MXFP4 / NVFP4 — Blackwell aggressive

Microscaling FP4. Each block of weights has its own scale factor. Aggressive but hardware-accelerated on Blackwell Tensor Cores. Halve the bytes per token versus FP8 — the economic win in Phase 17 · 07.

Caveats: - No LoRA support yet (early 2026). - Quality drop visible on reasoning-heavy workloads. - Validate on your eval set per model.

Idea 7 · The calibration trap

AWQ and GPTQ require a calibration dataset — typically C4 or WikiText. For domain models (code, medical, legal), calibrating on generic web text lets the algorithm make wrong decisions about which weights to protect. Pass@1 on HumanEval can drop several points.

The fix: calibrate on in-domain data. Hundreds of domain samples is usually enough. Test on the eval set before shipping.

Idea 8 · The KV cache trap

AWQ shrinks weights to 4 bits. KV cache is separate and stays at FP16/FP8. For a 70B model with AWQ:

  • Weights: ~35 GB (INT4 from 140 GB).
  • KV cache at 128 concurrent × 2k context: ~20 GB.
  • Activations: ~5 GB.
  • Total: ~60 GB — fits on H100 80GB.

Naively "I quantized my model to 4 GB" forgets the other 30-50 GB. Budget HBM holistically.

Separately, KV cache quantization (FP8 KV or INT8 KV) is a different choice with its own tradeoffs — it affects attention accuracy directly and is not a free win.

Idea 9 · AWQ INT4 is hazardous for reasoning

Chain-of-thought, math, code-gen with long context — these suffer visibly from aggressive quantization. AWQ INT4 loses ~3-5 points on MATH. For reasoning-heavy workloads, ship FP8 or BF16; accept the memory cost.

Idea 10 · 2026 picking guide

  • CPU/edge serve: GGUF Q4_K_M. Done.
  • GPU serve, routine chat, no LoRA: AWQ.
  • GPU serve, multi-LoRA: GPTQ with Marlin.
  • Reasoning workload: FP8.
  • Blackwell datacenter, validated quality: NVFP4 + FP8 KV.
  • Ambiguous: run a 1,000-sample eval on each candidate format.

Worked example
Does a 4-bit 70B model fit on one H100?

Llama-style 70B: 80 layers, 8 KV heads of size 128. Serve 128 users with 2,048 tokens each.

  1. Weights in AWQ INT4: 70B × 0.5 bytes = 35 GB.
  2. KV cache per token in BF16: 2 × 80 × 8 × 128 × 2 bytes ≈ 0.33 MB. For 128 × 2,048 = 262,144 tokens: about 86 GB.
  3. Total with a few GB of activations: about 125 GB. It does not fit on an 80 GB H100, even though the weights alone use less than half of it.
  4. With an FP8 KV cache the KV halves to about 43 GB: total about 82 GB, still just over. Cut concurrency to about 100, or use an H200 (141 GB).

The lesson's figure of "~20 GB of KV" is too low for this shape; do this arithmetic for your own model before choosing hardware.

Part 1 of 3 · Format, memory_breakdown

"""Toy quantization memory and throughput calculator — stdlib Python.

For a set of quantization formats and model sizes, compute:
  - weight memory
  - KV cache memory (separate, scales with concurrency and context)
  - activations memory (approximate)
  - relative decode throughput (memory-bandwidth-limited shape)

Formats are represented by effective weight bits and KV bits. Pedagogical.
"""

from __future__ import annotations

from dataclasses import dataclass


@dataclass
class Format:
    name: str
    weight_bits: float
    kv_bits: float
    engine: str
    notes: str


FORMATS = [
    Format("BF16 baseline (vLLM)",       16, 16, "vLLM",     "reference"),
    Format("GGUF Q5_K_M (llama.cpp)",     5, 16, "llama.cpp", "CPU/edge"),
    Format("GGUF Q4_K_M (llama.cpp)",     4, 16, "llama.cpp", "CPU/edge, default"),
    Format("GPTQ-Int4 + Marlin (vLLM)",   4, 16, "vLLM",     "multi-LoRA support"),
    Format("AWQ-Int4 + Marlin (vLLM)",    4, 16, "vLLM",     "best Pass@1 at INT4"),
    Format("FP8 (vLLM / TRT-LLM)",        8,  8, "multi",    "safe default reasoning"),
    Format("NVFP4 + FP8 KV (TRT-LLM)",    4,  8, "TRT-LLM",  "Blackwell aggressive"),
]


def memory_breakdown(params_b: float, fmt: Format,
                     concurrency: int = 128, ctx: int = 2048) -> dict:
    weight_gb = params_b * fmt.weight_bits / 8
    # KV cache approximation: num_layers * 2 * kv_heads * head_dim * ctx * bytes/element
    layers = 64 * (params_b / 70.0)**0.5
    kv_heads = 8
    head_dim = 128
    per_seq_kv_gb = layers * 2 * kv_heads * head_dim * ctx * (fmt.kv_bits / 8) / 1e9
    kv_total = per_seq_kv_gb * concurrency
    activations_gb = 0.05 * params_b       # rough constant
    return {
        "weight": weight_gb,
        "kv": kv_total,
        "act": activations_gb,
        "total": weight_gb + kv_total + activations_gb,
    }

Part 2 of 3 · relative_throughput, gpu_check, print_scenario, main

def relative_throughput(fmt: Format) -> float:
    """Decode is memory-bandwidth-limited. Fewer weight bytes per token = higher throughput.
    Normalize to BF16 = 1.0."""
    return 16 / fmt.weight_bits


def gpu_check(total_gb: float) -> str:
    if total_gb <= 80:
        return "H100 80GB"
    if total_gb <= 141:
        return "H200 141GB"
    if total_gb <= 192:
        return "B200 192GB"
    return "MULTI-GPU"


def print_scenario(params_b: float, concurrency: int, ctx: int) -> None:
    print(f"Model: {params_b}B params  |  concurrency {concurrency}  |  ctx {ctx}")
    print("-" * 98)
    print(f"{'format':36} {'W GB':>7} {'KV GB':>7} {'Act GB':>7} "
          f"{'Total':>7} {'fits on':>14} {'rel tput':>10}")
    for f in FORMATS:
        m = memory_breakdown(params_b, f, concurrency, ctx)
        tput = relative_throughput(f)
        print(f"{f.name:36} {m['weight']:7.1f} {m['kv']:7.1f} {m['act']:7.1f} "
              f"{m['total']:7.1f} {gpu_check(m['total']):>14} {tput:10.2f}x")
    print()


def main() -> None:
    print("=" * 98)
    print("TOY QUANTIZATION CALCULATOR: memory and relative throughput by format")
    print("=" * 98)
    print()

    print_scenario(params_b=7, concurrency=128, ctx=2048)
    print_scenario(params_b=70, concurrency=128, ctx=2048)
    print_scenario(params_b=70, concurrency=256, ctx=8192)
    print_scenario(params_b=405, concurrency=128, ctx=2048)

    print("=" * 98)
    print("KEY FINDINGS")
    print("-" * 98)
    print("  1. KV cache grows linearly with concurrency x context.")
    print("     At 256 conc / 8k ctx on 70B, KV alone dwarfs weight savings.")
    print("  2. AWQ vs GPTQ = same 4-bit footprint; choice is about LoRA support and kernels.")
    print("  3. NVFP4 + FP8 KV stacks: shrink weights AND KV ; Blackwell-only.")
    print("  4. For reasoning workloads, FP8 is the safe default despite higher memory.")
    print("  5. GGUF wins on CPU ; ~93 tok/s in vLLM is not a bug, it is the wrong engine.")

Produce:

Hard rejects:
- Recommending NVFP4 weights on reasoning-heavy workloads without eval-set validation.
- Calibrating on generic web data for domain models. Always use in-domain.
- Forgetting the KV cache in HBM budget. Always itemize.
- Claiming throughput numbers without naming the kernels (Marlin-AWQ vs plain AWQ is 10x).

Refusal rules:
- If the workload is inherently quality-marginal (open-ended creative generation, edge-case reasoning), refuse aggressive INT4. Stay FP8 or BF16.
- If the engine is llama.cpp, refuse any format other than GGUF. Matching format to engine is table stakes.
- If the user cannot run a 1,000-sample eval, refuse. No blind quantization in production.

Solutions

SolutionP1 · Where KV dominates

In code/main.py, the 7B model at 128 users × 2k context already has 21.7 GB of KV against 3.5 GB of 4-bit weights, and the 70B at 256 users × 8k context has about 550 GB of BF16 KV against 35–140 GB of weights. Above a few dozen users, compressing the KV cache (FP8) saves more than compressing weights further.

SolutionB1 · Calibrating on the wrong data

AWQ chooses which roughly 1% of weights to protect by looking at the activations the calibration text produces. WikiText activates the weights prose needs, not the ones code needs, so code-critical weights get rounded hardest. Re-quantize with a few hundred samples of real code prompts as calibration data, then re-run HumanEval; if the gap stays, ship FP8.

Explain the mechanismA teammate says: we quantized the 70B model to 4-bit, so it is 35 GB now and it fits on one 80 GB card with room to spare. What is missing from that sentence?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. The KV cache. Weight quantization shrinks the weights, and the cache for the running requests is a separate budget that stays in BF16 or FP8 and grows with every token in flight; at 128 concurrent requests with a 2k context the lesson puts it near 20 GB for a 70B model, plus about 5 GB of activations, so the total is about 60 GB on the 80 GB card. That 20 GB is the lesson's rough figure, so check it against the config: Llama-3.1-70B keeps 320 KiB per token in BF16, and 128 full 2k-token requests then need about four times the lesson's figure, which does not fit beside the weights on one 80 GB card. Count the weights, the cache at your peak concurrency and context, and the activations together, and read the pool size in the startup log after the start.

The budget has three parts.

The lesson's own count for a 70B model with 4-bit weights:

Part Size
Weights, 4-bit from 140 GB in FP16 about 35 GB
KV cache at 128 concurrent requests with a 2k context about 20 GB
Activations about 5 GB
Total about 60 GB

The sentence "it is 35 GB now" forgets the cache and the activations. Budget the card as a whole, and count the cache from the config of your model: Llama-3.1-70B keeps 320 KiB per token in BF16, so at full 2k contexts its cache alone is about four times the 20 GB in the table.

Where the cache goes.

Every token in a running request keeps its keys and values in GPU memory until the request ends. The bytes per token come from four numbers in the model config: layers times KV heads times head size times 2 for the key and the value, times the bytes per value. Qwen3-8B keeps 144 KiB per token in BF16 and Qwen3-30B-A3B keeps 96 KiB, because the KV heads decide the number and the parameter count does not. The engine gives the cache what is left after the weights and the startup profile, and the users that fit are the pool divided by the context that one user holds, prompt plus output. On the GB10 the weights of the 30B model took 56.93 GiB, 31.32 GiB was left for the cache, and at 96 KiB per token that is about 342,000 tokens.

KV quantization is its own decision.

An FP8 cache halves the bytes per token, which doubles the users at the same length. It is a separate choice from the weight format, with its own scales and its own effect on the attention values, so it needs its own accuracy check. Quantizing the weights does not shrink the cache.

How to fit more, in order of cost.

  1. Lower the maximum model length to the longest real request. This does not grow the pool, but it stops one request from claiming all of it.
  2. Use an FP8 KV cache.
  3. Use FP8 or 4-bit weights, which free memory for the cache.
  4. Use a GPU with more memory, or split the model.

Read the log.

Read two lines after every start: the weight load line and the available KV cache memory line. The pool line then gives the tokens and the maximum concurrency at the full length, which assumes that every user fills the maximum; real users hold less, so more fit.

Plausible wrong answers.

  • "The model is 35 GB, so the rest is free for users." The KV cache and the activations take their share first; at 128 concurrent requests with a 2k context the lesson puts the cache near 20 GB and the total near 60 GB.
  • "Quantizing the weights also shrinks the cache." The cache stays in its own dtype; it halves only if you quantize the cache, which is a separate choice with its own accuracy effect.
  • "The cache is small because the model is small." The bytes per token depend on the layers and the KV heads; a 30B expert model keeps 96 KiB per token and an 8B dense model 144 KiB.

Follow-ups an interviewer may ask.

  • (level 1) Which three things take memory on a serving GPU? Expected: the weights, the KV cache for the tokens in flight, and the activations with the startup working memory; the engine gives the cache what is left after the other two.
  • (level 2) What does the KV cache grow with? Expected: the number of running requests and the context that each one holds, prompt plus output, so it grows with concurrency and with length, not with the weights.
  • (level 3) Quantizing the weights to 4-bit and quantizing the cache to FP8 are different decisions. Why? Expected: the weights are a fixed cost and their quantization changes the matrix math; the cache is per token and its quantization changes the attention values directly, so it needs its own accuracy check and its own scales.
  • (level 4) Where in the startup log do you confirm that the budget held? Expected: in the weight load line, the available KV cache memory line and the pool size line with its maximum concurrency; divide the pool by prompt plus output per user rather than by the maximum length.

Where it is taught. The production quantization lesson names the trap, and Count the memory before you pick a GPU counts the cache.

Defend a designYou have twenty fine-tunes of one base model, each a LoRA adapter, and you want to serve them from one vLLM server. What do you set, what decides the cost, and what else in the server changes when LoRA is on?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Turn LoRA on at startup with --enable-lora, name the adapters with --lora-modules, and let each request pick one in its model field. Three limits set the cost: --max-loras, which defaults to 1 and caps the adapters that run in one batch, --max-lora-rank, which defaults to 16 and reserves memory for the largest rank, and --max-cpu-loras for adapters kept in CPU memory ready to load. LoRA also changes the prefix cache, because the adapter is part of every block key, so two adapters never share cached blocks, and it adds CUDA graphs per adapter, so startup takes longer and uses more memory.

Start it.

vllm serve Qwen/Qwen3-8B \
  --enable-lora \
  --lora-modules support=/adapters/support legal=/adapters/legal \
  --max-loras 4 --max-lora-rank 64

Each path is a folder in the PEFT format that most training libraries write: adapter_config.json and the weights in adapter_model.safetensors, or adapter_model.bin. A request picks an adapter by its name in the model field, and /v1/models lists the base model and each adapter. Requests for different adapters can run in the same batch. The manual ran this with Qwen3-0.6B and two public adapters of rank 8 and rank 64, and a chat request to each adapter returned HTTP 200.

Size the three limits.

Flag Default What it limits
--max-loras 1 adapters that can run in one batch on the GPU
--max-lora-rank 16 the largest adapter rank the server accepts
--max-cpu-loras not set adapters kept in CPU memory, ready to load

The default of one adapter per batch is low for a server with many adapters. Requests for a second adapter wait until the batch of the first adapter is done. Raise --max-loras to the number of adapters that are busy at the same time. Set --max-lora-rank to the largest rank of your adapters and not higher: the server reserves memory for the largest rank it accepts, and the documentation advises against a large default such as 256. Adapters in CPU memory load fast when a request names them, so size --max-cpu-loras for the adapters that are warm.

Load adapters while the server runs.

With VLLM_ALLOW_RUNTIME_LORA_UPDATING=True you can post to /v1/load_lora_adapter with a name and a path, and to /v1/unload_lora_adapter to remove it. Turn this on only when you trust every caller of the server, because the route loads files from a path that the caller gives.

What changes elsewhere.

  • The prefix cache. The adapter is part of each block key in vLLM and of the tree key in SGLang. Two adapters never share cached blocks, even for the same prompt. A shared system prompt is cached once per adapter, not once.
  • CUDA graphs. vLLM captures separate graphs for batches with an adapter. More adapters and more graph sizes add startup time and memory.
  • Names. Since 0.31 an adapter cannot have the name of a served model.

The manual did not measure the cost of the adapter count or the rank on its hardware.

Pick the base format with LoRA in mind.

The lesson's picking guide says that a 4-bit GPTQ base supports LoRA adapters in vLLM, with the fast Marlin kernels, while the microscaling 4-bit formats did not support LoRA at the start of 2026. For a base model plus many fine-tuned variants, GPTQ is the 4-bit path; AWQ is the pick when there is no LoRA, and FP8 when quality must not move.

Plausible wrong answers.

  • "One server per adapter is simpler." Each server would hold its own copy of the base model and its own pool; one base with adapters per request shares both, and requests for different adapters can run in the same batch.
  • "The default limits are fine." One adapter per batch makes requests for a second adapter wait, and a rank limit of 16 rejects a rank-64 adapter; set both from the adapters you serve.
  • "Enable runtime adapter loading so that operators can add adapters without a restart." The load route reads files from a path that the caller gives, so turn it on only when you trust every caller of the server.
  • "LoRA is free for the prefix cache because the base model is the same." The adapter changes the keys and values, so it is part of the block key, and two adapters never share cached blocks.

Follow-ups an interviewer may ask.

  • (level 2) Two tenants send the same long system prompt through two different adapters. Does the second request hit the cache? Expected: no; the adapter is part of the block key in vLLM and of the tree key in SGLang, so two adapters never share blocks even for identical tokens.
  • (level 3) Requests for the second adapter wait although the GPU is idle. Why? Expected: the adapter cap defaults to 1, so only one adapter runs in a batch and requests for another adapter wait until that batch is done; raise it to the number of adapters that are busy at the same time.
  • (level 3) Why not set the rank limit to 256 to be safe? Expected: the server reserves memory for the largest rank it accepts, so a high limit takes memory from the KV pool for adapters you do not have; set it to your largest rank.
  • (level 4) You also want 4-bit weights for the base model. Which format, and what does it rule out? Expected: a GPTQ 4-bit base, because it supports LoRA adapters in vLLM with the Marlin kernels; the microscaling 4-bit formats did not support LoRA at the start of 2026, so they are out until they do.

Where it is taught. Serve many fine-tunes with multi-LoRA gives the flags and limits, Prefix-friendly prompts notes the tree key, and the production quantization lesson pairs a 4-bit base with adapters.
