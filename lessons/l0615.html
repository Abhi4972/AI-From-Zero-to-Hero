About the model on this page
The model on this page is the lab rig

chat is a real LangChain chat model pointed at mockllm (Lesson 14.92), which streams its fixed reply word by word. The workflow tasks are plain functions.

from mockllm import start                                      # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock")

class Turn(TypedDict, total=False):
    question: str
    category: str
    reply: str
Why this came about

Agents with many steps needed to show progress, not just final text, so LangGraph added several stream modes. The Functional API (2025) followed for teams who prefer writing workflows as ordinary functions while keeping persistence and pauses.

The problem: a UI needs more than the final answer

While an agent works for ten seconds, the customer should see what it is doing ("checking your order…") and the reply as it is written, not a spinner followed by a wall of text (Lesson 11.22). A graph has several kinds of things worth streaming: what each node changed, the tokens of each model call, and progress messages you choose. LangGraph streams all of them, separately or together, through stream modes.

In plain words first
Watching the work as it happens

Streaming means receiving pieces of a run while it runs, instead of one result at the end. LangGraph can show the same run several ways, called stream modes: what each node changed, the whole state after each step, model text token by token, or progress messages you send yourself. The Functional API, the second half of this lesson, writes workflows as ordinary Python functions with the same saving and pausing.

Idea 1 · Stream modes

A small graph with two nodes: one classifies the question, one writes the reply with a model. Both also send their own progress messages through get_stream_writer(). The loop at the bottom asks for three stream modes at once and prints whatever arrives, labelled with the mode it came from:

from langgraph.config import get_stream_writer

def classify(state):
    writer = get_stream_writer()
    writer({"status": "classifying your question"})            # a custom progress event
    return {"category": "orders" if "order" in state["question"].lower() else "general"}

def respond(state):
    writer = get_stream_writer()
    writer({"status": "writing a reply"})
    return {"reply": chat.invoke(state["question"]).content}

b = StateGraph(Turn)
b.add_node("classify", classify); b.add_node("respond", respond)
b.add_edge(START, "classify"); b.add_edge("classify", "respond"); b.add_edge("respond", END)
graph = b.compile()

tokens = []
for mode, data in graph.stream({"question": "hello"}, stream_mode=["updates", "custom", "messages"]):
    if mode == "messages":
        chunk, meta = data
        tokens.append(chunk.content)
        continue
    print(f"{mode:8} | {data}")
print(f"messages | {len(tokens)} token chunks from node '{meta['langgraph_node']}': {''.join(tokens)[:40]}…")
What you should see
custom   | {'status': 'classifying your question'}
updates  | {'classify': {'category': 'general'}}
custom   | {'status': 'writing a reply'}
updates  | {'respond': {'reply': 'I can check order status and cancel orders. Please share your order ID, like A-1002. '}}
messages | 18 token chunks from node 'respond': I can check order status and cancel orde…
Reading this output
  • With a list of modes, each streamed item is a pair (mode, data), so the loop unpacks mode, data.
  • In messages mode, data is itself a pair: chunk, an AIMessageChunk holding a few new characters in .content (empty for chunks that carry tool calls), and meta, a dictionary saying where the chunk came from: langgraph_node, langgraph_step, and the model's tags if it has any.
  • custom items are exactly the dictionaries the nodes passed to writer(...).

Three modes in one stream, each item tagged with its mode:

Mode Yields Use it for
values The whole state after each step Simple UIs, debugging
updates What each node returned, keyed by node Progress, debugging, audit
messages (chunk, metadata) for every token of every model call inside nodes Showing the reply as it is written
custom Whatever nodes send with get_stream_writer() Progress messages, partial results
debug, tasks, checkpoints Detailed events about tasks and checkpoints Tooling

Notice that respond called chat.invoke, not chat.stream, and the tokens still streamed: in messages mode, LangGraph collects tokens from every model call through callbacks (Lesson 14.99). The metadata says which node each token came from, which matters as soon as a graph calls a model more than once (the debugging exercise). Add subgraphs=True to include events from graphs inside graphs (Lesson 14.107). For HTTP, each item becomes one server-sent event; the platform in Lesson 14.108 does that for you.

Choosing whose tokens you show

messages mode streams tokens from every model call in the graph: routers, graders and rewriters as well as the reply. Shown unfiltered, a customer sees internal words glued to the answer (the debugging exercise is exactly that bug). Three ways to choose, like deciding whose voice goes down the customer's phone line in a busy office:

Technique How Use it when
By node Keep chunks whose meta["langgraph_node"] is the node that writes the reply One node, one job
By tag Give the reply model a tag, init_chat_model(..., tags=["final_answer"]), and keep chunks whose meta["tags"] contain it Several models, nested graphs, models called inside tools
nostream Give internal models the special tag "nostream": they run and their results reach the state, but their tokens are never streamed Routers, graders, classifiers 
router = init_chat_model("openai:mock-model", base_url=start(), api_key="mock", tags=["nostream"])      # internal
writer_model = init_chat_model("openai:mock-model", base_url=start(), api_key="mock", tags=["final_answer"])

def route(state):
    return {"category": router.invoke(f"Classify: {state['question']}").content[:12]}

def answer(state):
    return {"reply": writer_model.invoke(state["question"]).content}

b = StateGraph(Turn)
b.add_node("route", route); b.add_node("answer", answer)
b.add_edge(START, "route"); b.add_edge("route", "answer"); b.add_edge("answer", END)
tagged = b.compile()

seen = {}
for chunk, meta in tagged.stream({"question": "hello"}, stream_mode="messages"):
    if chunk.content:
        seen.setdefault(meta["langgraph_node"], set()).update(meta.get("tags", []))
print("nodes that streamed tokens:", seen)
print("route still set:", repr(tagged.invoke({"question": "hello"})["category"]))
What you should see
nodes that streamed tokens: {'answer': {'final_answer'}}
route still set: 'I can check '

The router ran (its result is in the state) but streamed nothing, so no filter is needed for it; the reply's chunks carry the final_answer tag, which a client can filter on. Filtering by node or tag happens in your receiving code, so every client must do it; nostream is applied at the model, so every client benefits. None of this hides anything from traces or from values streaming.

One shape for every mode: version="v2"

With several modes, the chunks above are (mode, data) tuples, and their shape changes when you add subgraphs ((namespace, mode, data)). Pass version="v2" and every chunk is a dictionary with the same keys, whatever the options:

from typing import TypedDict
from langgraph.graph import StateGraph, START
from langgraph.config import get_stream_writer

class Ask(TypedDict, total=False):
    question: str
    answer: str

def look_up(state):
    get_stream_writer()({"progress": "looking up A-1002"})
    return {"answer": "A-1002 is processing"}

small = StateGraph(Ask).add_node("look_up", look_up).add_edge(START, "look_up").compile()
for part in small.stream({"question": "Where is A-1002?"}, stream_mode=["updates", "custom", "values"], version="v2"):
    print(f"{part['type']:8} ns={part['ns']}  {part['data']}")
What you should see
values   ns=()  {'question': 'Where is A-1002?'}
custom   ns=()  {'progress': 'looking up A-1002'}
updates  ns=()  {'look_up': {'answer': 'A-1002 is processing'}}
values   ns=()  {'question': 'Where is A-1002?', 'answer': 'A-1002 is processing'}

type is the mode, ns the subgraph path (empty for the top graph), and data the payload; values parts also carry any pending interrupts. New code should use version="v2"; the tuple format remains for older code. Two timing facts help when you build a UI on these modes: updates arrive as each task finishes, so a fast parallel task is not held back by a slow one, while values arrive only when the whole superstep is done (Lesson 14.115).

Idea 2 · The Functional API

Some workflows read better as plain Python than as nodes and edges: a few steps, an if, a loop. LangGraph's Functional API gives that code the same runtime: checkpoints, parallelism and interrupts.

from langgraph.func import entrypoint, task
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

CALLS = []

@task
def lookup(order_id: str) -> dict:
    CALLS.append(f"lookup {order_id}")
    return {"id": order_id, "amount": 7999 if order_id == "A-1077" else 1200}

@task
def fraud_check(order_id: str) -> str:
    CALLS.append(f"fraud_check {order_id}")
    return "clear"

@entrypoint(checkpointer=InMemorySaver())
def refund_workflow(order_id: str) -> str:
    order_f, fraud_f = lookup(order_id), fraud_check(order_id)      # tasks start at once and run in parallel
    order, fraud = order_f.result(), fraud_f.result()
    if fraud != "clear":
        return "held: fraud check"
    if order["amount"] > 5000:
        approved = interrupt({"approve_refund": order})              # the same interrupt as Lesson 6.13
        if not approved:
            return "declined"
    return f"refunded INR {order['amount']:,}"

cfg = {"configurable": {"thread_id": "fn-1"}}
first = refund_workflow.invoke("A-1077", cfg)
print("paused:", first["__interrupt__"][0].value)
print(refund_workflow.invoke(Command(resume=True), cfg))
print(sorted(CALLS))                                          # parallel tasks finish in any order
What you should see
paused: {'approve_refund': {'id': 'A-1077', 'amount': 7999}}
refunded INR 7,999
['fraud_check A-1077', 'lookup A-1077']

Two decorators. A @task is a unit of work whose result is checkpointed; calling it returns a future, so two tasks started together run in parallel, and .result() waits for one. An @entrypoint is the workflow, and gets the checkpointer. On resume, the entrypoint runs again from its first line, as a node does (Lesson 14.104), but tasks that already finished return their saved results instead of running again: the last line shows each lookup ran once, even though the workflow ran twice. So put side effects in tasks, never directly in the entrypoint.

Graph API or Functional API?

Graph API (StateGraph) Functional API (@entrypoint, @task)
Control flow Edges and routers Ordinary if, for, while
State A shared, typed schema with reducers Function arguments and return values
Checkpoints After every node After every task, plus the entrypoint's result
Visualization The graph can be drawn No graph to draw
Fits Agents, branching workflows, multi-agent systems, anything you want to see as a diagram Short workflows, adding durability to existing code

Both run on the same runtime and can be mixed: a task can call a graph, and a graph node can call an entrypoint.

def classify_with_model(state):

b = StateGraph(Turn)

Make it your own

Write batch_refunds, an entrypoint that looks up a list of orders in parallel with one task per order and returns, for each order, whether it needs approval. (Solution M1.)

Solutions

SolutionP1 · Only the unfinished task

fraud_check finished and its result was saved, so it is not run again. lookup failed, so it runs again; then the entrypoint continues. That is the Functional API's durability: completed tasks are never repeated, which is why side effects belong inside tasks.

SolutionB1 · A task belongs to a run

A task's result is saved in the current run's checkpoint, and its future is scheduled by the runtime, so outside an entrypoint or a graph there is no run to save to, and LangGraph fails with "Called get_config outside of a runnable context". To test a task's logic, test the plain function it wraps, or run it inside a small entrypoint.

SolutionD1 · messages mode streams every model call

stream_mode="messages" yields tokens from every model call inside the graph, so the classifier's tokens reached the customer before the reply's. Filter on the metadata, which names the node (you can also tag the model with with_config(tags=[...]) and filter on tags):

shown = "".join(chunk.content for chunk, meta in two_models.stream({"question": "hello"}, stream_mode="messages")
                if meta["langgraph_node"] == "respond")                 # only the reply node's tokens
print(repr(shown[:60]), "...", len(shown), "characters shown to the customer")

'I can check order status and cancel orders. Please share you' ... 85 characters shown to the customer

The same issue appears with summarization, guardraillater · 15.23 checks and any other internal model call.

SolutionM1 · One task per item
@entrypoint(checkpointer=InMemorySaver())
def batch_refunds(order_ids: list[str]) -> dict:
    orders = [o.result() for o in [lookup(i) for i in order_ids]]       # one task per order, all in parallel
    return {o["id"]: "needs approval" if o["amount"] > 5000 else "auto-refund" for o in orders}

CALLS.clear()
print(batch_refunds.invoke(["A-1077", "A-1078", "A-1079"], {"configurable": {"thread_id": "batch"}}))
print(sorted(CALLS))

{'A-1077': 'needs approval', 'A-1078': 'auto-refund', 'A-1079': 'auto-refund'}
['lookup A-1077', 'lookup A-1078', 'lookup A-1079']

The list comprehension starts every task before waiting for any, so the lookups run in parallel. For hundreds of items, consider Send in a graph (Lesson 14.107), which gives each item its own node run with its own state.

Check your understanding

Explain the mechanismWhat stream modes does LangGraph offer, and which would you use for a chat UI?

Worked answer. values for the full state after each step, updates for what each node changed, messages for model tokens with metadata about which node produced them, custom for events nodes emit with a stream writer, and debug-level modes. For a chat UI I would combine messages, filtered to the node that writes the reply, for the text, with custom or updates for progress such as "checking your order", and stream them as server-sent events.

A plausible wrong answer. "You must call model.stream inside the node to stream tokens." In messages mode LangGraph captures tokens from invoke calls too.

Follow-ups. How do you stream events from a subgraph?

Debug a failureAfter adding a guardrail model call, users see the guardrail's output flash in the chat. Why?

Worked answer. The UI streams messages mode without filtering, so tokens from every model call, including the guardrail's, are shown. Filter by metadata["langgraph_node"] or by tags so only the reply node's tokens are shown, and add a test that streams a run and checks which nodes' tokens reach the client.

A plausible wrong answer. "The guardrail model is returning its output to the user." It returns to the node; the stream filter leaked it.

Follow-ups. How would you show a "checking your request" message during the guardrail call instead?

Defend a designWhen would you choose the Functional API over a StateGraph?

Worked answer. For workflows that are naturally sequential code with a few branches, especially when adding durability and approvals to existing Python without restructuring it into nodes. I keep the Graph API for agents and anything with many branches, multiple agents or parallel fan-outs whose structure people need to see and review, because the drawn graph is documentation and the typed shared state makes those flows clearer. The runtime and its guarantees are the same.

A plausible wrong answer. "The Functional API is the new API and replaces graphs." They are two interfaces to one runtime, suited to different shapes of work.
