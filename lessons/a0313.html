In plain words first
The idea in one line

Your network compiled. It ran. It produced a number. The number is wrong and nothing crashed. Welcome to the hardest kind of debugging -- the kind where there is no error message.

Terms you'll hear
Term What people say What it actually means
Silent bug "It runs but gives bad results" A bug that produces no error but degrades model quality -- the dominant failure mode in ML
Dead ReLU "The neurons died" A ReLU neuron whose input is always negative, so it outputs 0 and receives 0 gradient permanently
Vanishing gradients "Early layers stop learning" Gradients shrink exponentially through layers, making weights in early layers effectively frozen
Exploding gradients "Loss went to NaN" Gradients grow exponentially through layers, causing weight updates so large they overflow
Gradient checking "Verify backprop is correct" Comparing analytical gradients from backprop to numerical gradients from finite differences
Overfit-one-batch "The most important debug test" Training on a single small batch to verify the model CAN learn -- if it cannot, something is fundamentally broken
LR finder "Sweep to find the right learning rate" Exponentially increasing the learning rate over one epoch and picking the rate just before loss diverges
Data leakage "Test data leaked into training" When information from the test set contaminates training, producing artificially high accuracy
Activation statistics "Monitor layer health" Tracking mean, std, and zero-fraction of each layer's output to detect dead, saturated, or exploding neurons
Gradient clipping "Cap the gradient magnitude" Scaling gradients down when their norm exceeds a threshold, preventing exploding gradient updates

The problem

In plain words first

When a neural network is wrong it usually does not crash: it trains, prints falling losses and makes confident predictions. So debugging means measuring. Check that the model can memorise one small batch, that backprop agrees with numerical gradients, that each layer's activations and gradients stay in a sensible range, and that the learning rate suits the problem. Each check rules out one family of bugs; none of them alone proves the model is right.

Traditional software crashes when it is broken. A null pointer throws an exception. A type mismatch fails at compile time. An off-by-one error produces a clearly wrong output.

Neural networks do not give you that luxury.

A broken neural network runs to completion, prints a loss value, and outputs predictions. The loss might decrease. The predictions might look plausible. But the model is silently wrong -- learning shortcuts, memorizing noise, or converging to a useless local minimum. Practitioners consistently report that most of their debugging time goes to "silent" bugs that produce no errors but degrade model quality.

The difference between a working model and a broken one is often a single misplaced line: a missing zero_grad(), a transposed dimension, a learning rate off by 10x. Andrej Karpathy's widely read "A Recipe for Training Neural Networks" (2019) makes the same point: neural network training fails silently.

This lesson teaches you to find those bugs.

Idea 1 · The Debugging Mindset

Forget print-and-pray debugging. Neural network debugging requires a systematic approach because the feedback loop is slow (minutes to hours per training run) and the symptoms are ambiguous (bad loss could mean 20 different things).

The golden rule: start simple, add complexity one piece at a time, and verify each piece independently.

Idea 2 · Symptom 1: Loss Not Decreasing

This is the most common complaint. The training loop runs, epochs tick by, and the loss stays flat or oscillates wildly.

Wrong learning rate. Too high: loss oscillates or jumps to NaN. Too low: loss decreases so slowly it looks flat. For Adam, start at 1e-3. For SGD, start at 1e-1 or 1e-2. Always try 3 learning rates spanning 10x each (e.g., 1e-2, 1e-3, 1e-4) before concluding something else is wrong.

Dead ReLUs. If a ReLU neuron receives a large negative input, it outputs 0 and its gradient is 0. It never activates again. If enough neurons die, the network cannot learn. Check: print the fraction of activations that are exactly 0 after each ReLU layer. If >50% are dead, switch to LeakyReLU or reduce the learning rate.

Vanishing gradients. In deep networks with sigmoid or tanh activations, gradients shrink exponentially as they propagate backward. By the time they reach the first layer, they are ~0. The first layers stop learning. Fix: use ReLU/GELU, add residual connections, or use batch normalization.

Exploding gradients. The opposite problem -- gradients grow exponentially. Common in RNNs and very deep networks. Loss jumps to NaN. Fix: gradient clipping (torch.nn.utils.clip_grad_norm_), lower learning rate, or add normalization.

Idea 3 · Symptom 2: Loss Decreasing But Model is Bad

The loss goes down. Training accuracy hits 99%. But test accuracy is 55%. Or the model produces nonsensical outputs on real data.

Overfitting. The model memorizes training data instead of learning patterns. Gap between training and validation loss grows over time. Fix: more data, dropout, weight decay, early stopping, data augmentation.

Data leakage. Test data leaked into training. Accuracy is suspiciously high. Common causes: shuffling before splitting, preprocessing with statistics from the full dataset, duplicate samples across splits. Fix: split first, preprocess second, check for duplicates.

Label errors. Popular benchmark test sets contain wrong labels too, about 3 percent on average and roughly 6 percent in ImageNet's validation set (Northcutt et al., 2021 -- "Pervasive Label Errors in Test Sets"). The model learns the noise. Fix: use confident learning to find and fix mislabeled examples, or use loss truncation to ignore high-loss samples.

Idea 4 · Symptom 3: NaN or Inf in Loss

The loss value becomes nan or inf. Training is dead.

Learning rate too high. Gradient updates overshoot so far that weights explode. Fix: reduce by 10x.

log(0) or log(negative). Cross-entropy loss computes log(p). If your model outputs exactly 0 or a negative probability, the log explodes. Fix: clamp predictions to [eps, 1-eps] where eps=1e-7.

Division by zero. Batch normalization divides by standard deviation. A batch with constant values has std=0. Fix: add epsilon to the denominator (PyTorch does this by default, but custom implementations might not).

Numerical overflow. Large activations fed into exp() produce Inf. Softmax is especially prone. Fix: subtract the max before exponentiating (the log-sum-exp trick).

Worked example
Reading a stuck loss

A model that knows nothing and spreads probability evenly over k classes has cross-entropy −ln(1/k)=lnk: 0.693 for 2 classes, 2.303 for 10, 6.908 for 1,000. So a loss that sits at 0.69 on a yes/no task means "the model is guessing". Bug 2 in Step 5 ends at 0.6884: its ReLUs are dead, the output layer only sees zeros, and the prediction is barely more than a coin toss.

Check your mental model
  • ✗ "A falling loss means no bug."
    ✓ In Step 5, Bug 3 (no zero_grad) has a lower loss after 20 steps than the healthy network, and the debugger calls it HEALTHY. Accumulated gradients act like an ever-growing learning rate: fast at first, unstable later.
  • ✗ "More than half the activations at zero means dead neurons."
    ✓ A ReLU zeroes every negative input, so about half its outputs are zero in a perfectly healthy layer. A dead neuron is one that is zero for every input; count those per neuron.
  • ✗ "If the gradient check passes, the model will train."
    ✓ It only proves the backward pass matches the forward pass. Wrong labels, a bad learning rate or leaked data all pass it.

Idea 5 · Technique 1: Gradient Checking

Compare your analytical gradients (from backprop) to numerical gradients (from finite differences). If they disagree, your backward pass has a bug.

Numerical gradient for parameter w:

grad_numerical=2⋅epsloss(w+eps)−loss(w−eps)​

Agreement metric (relative difference):

rel_diff=max(∣grad_analytical∣,∣grad_numerical∣,10−8)∣grad_analytical−grad_numerical∣​

If rel_diff < 1e-5: correct. If rel_diff > 1e-3: almost certainly a bug.

Idea 6 · Technique 2: Activation Statistics

Monitor the mean and standard deviation of activations after each layer during training. Healthy networks maintain activations with mean near 0 and std near 1 (after normalization) or at least bounded.

Health indicator Mean Std Diagnosis
Healthy ~0 ~1 Network is learning normally
Saturated >>0 or <<0 ~0 Activations stuck at extreme values
Dead 0 0 Neurons are dead (all zeros)
Exploding >>10 >>10 Activations growing without bound

Idea 7 · Technique 3: Gradient Flow Visualization

Plot the average gradient magnitude for each layer. In a healthy network, gradient magnitudes should be roughly similar across layers. If early layers have gradients 1000x smaller than later layers, you have vanishing gradients.

Idea 8 · Technique 4: The Overfit-One-Batch Test

The single most important debugging technique in deep learning.

Take one small batch (8-32 samples). Train on it for 100+ iterations. The loss should go to nearly zero and training accuracy should hit 100%. If it does not, your model or training loop has a fundamental bug -- do not proceed to full training.

This test catches: - Broken loss functions - Broken backward passes - Architecture too small to represent the data - Optimizer not connected to model parameters - Data and labels misaligned

This takes 30 seconds to run and saves hours of debugging full training runs.

Idea 9 · Technique 5: Learning Rate Finder

Leslie Smith (2017) proposed sweeping the learning rate from very small (1e-7) to very large (10) over one epoch while recording the loss. Plot loss vs learning rate. The optimal learning rate is roughly 10x smaller than the rate where loss starts decreasing fastest.

Best LR in this example: ~1e-3 (one order of magnitude before the steepest point).

Idea 10 · Common PyTorch Bugs

These are the bugs that waste the most collective hours in the PyTorch community:

Bug Symptom Fix
Forgetting optimizer.zero_grad() Gradients accumulate across batches, loss oscillates Add optimizer.zero_grad() before loss.backward()
Forgetting model.eval() at test time Dropout and batch norm behave differently, test accuracy varies between runs Add model.eval() and torch.no_grad()
Wrong tensor shapes Silent broadcasting produces wrong results, no error Print shapes after every operation during debugging
CPU/GPU mismatch RuntimeError: expected CUDA tensor Use .to(device) on model AND data
Not detaching tensors Computation graph grows forever, OOM Use .detach() or with torch.no_grad()
In-place operations breaking autograd RuntimeError: modified by in-place operation Replace x += 1 with x = x + 1
Data not normalized Loss stuck at random-chance level Normalize inputs to mean=0, std=1
Labels as wrong dtype Cross-entropy expects Long, got Float Cast labels: labels.long()

Idea 11 · The Master Debugging Table

The same idea as a formula

The first-step check. A K-class classifier at initialisation should predict roughly uniform probabilities, so its cross-entropy should be about lnK: 2.303 for 10 classes, 6.908 for 1,000, about 10.8 for a 50,000-token vocabulary. A much larger initial loss means badly scaled outputs; a much smaller one usually means a leak.

Gradient check. Compare the analytical gradient ga​ with a central difference gn​=2hL(θ+h)−L(θ−h)​ (in float64, h≈10−5):

rel. error=max(∣ga​∣,∣gn​∣,10−8)∣ga​−gn​∣​:<10−7 correct,10−5 to 10−3 suspicious,>10−3 wrong

ReLU kinks can cause isolated large errors when θ±h straddles 0.

Activation and gradient statistics. For each layer, track the mean and standard deviation of activations (should stay roughly constant across depth), the fraction of ReLUs that are zero for the whole batch (dead units), and the ratio of update size to weight size, ∥ηg∥/∥w∥, which is healthy around 10−3.

Overfit one batch. A correct model and training loop can drive the loss on a single small batch to almost 0 within a few hundred steps; if it cannot, the bug is in the code, not in the data or the hyperparameters.

Step 1 · The NetworkDebugger Class

A diagnostic toolkit that monitors activations, gradients, and loss curves. You will deliberately break a network and use the toolkit to diagnose each problem.

Hooks into a PyTorch model to record activation and gradient statistics per layer.

import torch
import torch.nn as nn
import math


class NetworkDebugger:
    def __init__(self, model):
        self.model = model
        self.activation_stats = {}
        self.gradient_stats = {}
        self.loss_history = []
        self.lr_losses = []
        self.hooks = []
        self._register_hooks()

    def _register_hooks(self):
        for name, module in self.model.named_modules():
            if isinstance(module, (nn.Linear, nn.Conv2d, nn.ReLU, nn.LeakyReLU)):
                hook = module.register_forward_hook(self._make_activation_hook(name))
                self.hooks.append(hook)
                hook = module.register_full_backward_hook(self._make_gradient_hook(name))
                self.hooks.append(hook)

    def _make_activation_hook(self, name):
        def hook(module, input, output):
            with torch.no_grad():
                out = output.detach().float()
                self.activation_stats[name] = {
                    "mean": out.mean().item(),
                    "std": out.std().item(),
                    "fraction_zero": (out == 0).float().mean().item(),
                    "min": out.min().item(),
                    "max": out.max().item(),
                }
        return hook

    def _make_gradient_hook(self, name):
        def hook(module, grad_input, grad_output):
            if grad_output[0] is not None:
                with torch.no_grad():
                    grad = grad_output[0].detach().float()
                    self.gradient_stats[name] = {
                        "mean": grad.mean().item(),
                        "std": grad.std().item(),
                        "abs_mean": grad.abs().mean().item(),
                        "max": grad.abs().max().item(),
                    }
        return hook

    def record_loss(self, loss_value):
        self.loss_history.append(loss_value)

    def check_loss_health(self):
        if len(self.loss_history) < 2:
            return "NOT_ENOUGH_DATA"
        recent = self.loss_history[-10:]
        if any(math.isnan(v) or math.isinf(v) for v in recent):
            return "NAN_OR_INF"
        if len(self.loss_history) >= 20:
            first_half = sum(self.loss_history[:10]) / 10
            second_half = sum(self.loss_history[-10:]) / 10
            if second_half >= first_half * 0.99:
                return "NOT_DECREASING"
        if len(recent) >= 5:
            diffs = [recent[i+1] - recent[i] for i in range(len(recent)-1)]
            if max(diffs) - min(diffs) > 2 * abs(sum(diffs) / len(diffs)):
                return "OSCILLATING"
        return "HEALTHY"

    def check_activations(self):
        issues = []
        for name, stats in self.activation_stats.items():
            if stats["fraction_zero"] > 0.5:
                issues.append(f"DEAD_NEURONS: {name} has {stats['fraction_zero']:.0%} zero activations")
            if abs(stats["mean"]) > 10:
                issues.append(f"EXPLODING_ACTIVATIONS: {name} mean={stats['mean']:.2f}")
            if stats["std"] < 1e-6:
                issues.append(f"COLLAPSED_ACTIVATIONS: {name} std={stats['std']:.2e}")
        return issues if issues else ["HEALTHY"]

    def check_gradients(self):
        issues = []
        grad_magnitudes = []
        for name, stats in self.gradient_stats.items():
            grad_magnitudes.append((name, stats["abs_mean"]))
            if stats["abs_mean"] < 1e-7:
                issues.append(f"VANISHING_GRADIENT: {name} abs_mean={stats['abs_mean']:.2e}")
            if stats["abs_mean"] > 100:
                issues.append(f"EXPLODING_GRADIENT: {name} abs_mean={stats['abs_mean']:.2e}")
        if len(grad_magnitudes) >= 2:
            first_mag = grad_magnitudes[0][1]
            last_mag = grad_magnitudes[-1][1]
            if last_mag > 0 and first_mag / last_mag > 100:
                issues.append(f"GRADIENT_RATIO: first/last = {first_mag/last_mag:.0f}x (vanishing)")
        return issues if issues else ["HEALTHY"]

    def print_report(self):
        print("\n=== NETWORK DEBUGGER REPORT ===")
        print(f"\nLoss health: {self.check_loss_health()}")
        if self.loss_history:
            print(f"  Last 5 losses: {[f'{v:.4f}' for v in self.loss_history[-5:]]}")
        print("\nActivation diagnostics:")
        for item in self.check_activations():
            print(f"  {item}")
        print("\nGradient diagnostics:")
        for item in self.check_gradients():
            print(f"  {item}")
        print("\nPer-layer activation stats:")
        for name, stats in self.activation_stats.items():
            print(f"  {name}: mean={stats['mean']:.4f} std={stats['std']:.4f} zero={stats['fraction_zero']:.1%}")
        print("\nPer-layer gradient stats:")
        for name, stats in self.gradient_stats.items():
            print(f"  {name}: abs_mean={stats['abs_mean']:.2e} max={stats['max']:.2e}")

    def remove_hooks(self):
        for hook in self.hooks:
            hook.remove()
        self.hooks.clear()

Step 2 · The Overfit-One-Batch Test

def overfit_one_batch(model, x_batch, y_batch, criterion, lr=0.01, steps=200):
    optimizer = torch.optim.Adam(model.parameters(), lr=lr)
    model.train()
    print("\n=== OVERFIT ONE BATCH TEST ===")
    print(f"Batch size: {x_batch.shape[0]}, Steps: {steps}")

    for step in range(steps):
        optimizer.zero_grad()
        output = model(x_batch)
        loss = criterion(output, y_batch)
        loss.backward()
        optimizer.step()

        if step % 50 == 0 or step == steps - 1:
            with torch.no_grad():
                preds = (output > 0).float() if output.shape[-1] == 1 else output.argmax(dim=1)
                targets = y_batch if y_batch.dim() == 1 else y_batch.squeeze()
                acc = (preds.squeeze() == targets).float().mean().item()
            print(f"  Step {step:3d} | Loss: {loss.item():.6f} | Accuracy: {acc:.1%}")

    final_loss = loss.item()
    if final_loss > 0.1:
        print(f"\n  FAIL: Loss did not converge ({final_loss:.4f}). Model or training loop is broken.")
        return False
    print(f"\n  PASS: Loss converged to {final_loss:.6f}")
    return True

Step 3 · Learning Rate Finder

def find_learning_rate(model, x_data, y_data, criterion, start_lr=1e-7, end_lr=10, steps=100):
    import copy
    original_state = copy.deepcopy(model.state_dict())
    optimizer = torch.optim.SGD(model.parameters(), lr=start_lr)
    lr_mult = (end_lr / start_lr) ** (1 / steps)

    model.train()
    results = []
    best_loss = float("inf")
    current_lr = start_lr

    print("\n=== LEARNING RATE FINDER ===")

    for step in range(steps):
        optimizer.zero_grad()
        output = model(x_data)
        loss = criterion(output, y_data)

        if math.isnan(loss.item()) or loss.item() > best_loss * 10:
            break

        best_loss = min(best_loss, loss.item())
        results.append((current_lr, loss.item()))

        loss.backward()
        optimizer.step()

        current_lr *= lr_mult
        for param_group in optimizer.param_groups:
            param_group["lr"] = current_lr

    model.load_state_dict(original_state)

    if len(results) < 10:
        print("  Could not complete LR sweep -- loss diverged too quickly")
        return results

    min_loss_idx = min(range(len(results)), key=lambda i: results[i][1])
    suggested_lr = results[max(0, min_loss_idx - 10)][0]

    print(f"  Swept {len(results)} steps from {start_lr:.0e} to {results[-1][0]:.0e}")
    print(f"  Minimum loss {results[min_loss_idx][1]:.4f} at lr={results[min_loss_idx][0]:.2e}")
    print(f"  Suggested learning rate: {suggested_lr:.2e}")

    return results

Step 4 · Gradient Checker

def _flat_to_multi_index(flat_idx, shape):
    multi_idx = []
    remaining = flat_idx
    for dim in reversed(shape):
        multi_idx.insert(0, remaining % dim)
        remaining //= dim
    return tuple(multi_idx)


def gradient_check(model, x, y, criterion, eps=1e-4):
    model.train()
    x_double = x.double()
    y_double = y.double()
    model_double = model.double()

    print("\n=== GRADIENT CHECK ===")
    overall_max_diff = 0
    checked = 0

    for name, param in model_double.named_parameters():
        if not param.requires_grad:
            continue

        layer_max_diff = 0

        model_double.zero_grad()
        output = model_double(x_double)
        loss = criterion(output, y_double)
        loss.backward()
        analytical_grad = param.grad.clone()

        num_checks = min(5, param.numel())
        for i in range(num_checks):
            idx = _flat_to_multi_index(i, param.shape)
            original = param.data[idx].item()

            param.data[idx] = original + eps
            with torch.no_grad():
                loss_plus = criterion(model_double(x_double), y_double).item()

            param.data[idx] = original - eps
            with torch.no_grad():
                loss_minus = criterion(model_double(x_double), y_double).item()

            param.data[idx] = original

            numerical = (loss_plus - loss_minus) / (2 * eps)
            analytical = analytical_grad[idx].item()

            denom = max(abs(numerical), abs(analytical), 1e-8)
            rel_diff = abs(numerical - analytical) / denom

            layer_max_diff = max(layer_max_diff, rel_diff)
            checked += 1

        overall_max_diff = max(overall_max_diff, layer_max_diff)
        status = "OK" if layer_max_diff < 1e-5 else "MISMATCH"
        print(f"  {name}: max_rel_diff={layer_max_diff:.2e} [{status}]")

    model.float()

    print(f"\n  Checked {checked} parameters")
    if overall_max_diff < 1e-5:
        print("  PASS: Gradients match (rel_diff < 1e-5)")
    elif overall_max_diff < 1e-3:
        print("  WARN: Small differences (1e-5 < rel_diff < 1e-3)")
    else:
        print("  FAIL: Gradient mismatch detected (rel_diff > 1e-3)")
    return overall_max_diff

Recap
What to keep from this lesson
  • Neural network bugs rarely crash; measure instead of waiting for an error.
  • First run the overfit-one-batch test; if a tiny batch cannot be memorised, stop and fix.
  • Gradient-check any hand-written backward pass.

The Debug Checklist (Before Full Training)

  1. Run overfit-one-batch test. If it fails, stop.
  2. Print model summary -- verify parameter count is reasonable.
  3. Run a single forward pass with random data -- check output shape.
  4. Train for 5 epochs -- verify loss decreases.
  5. Check activation statistics -- no dead layers, no explosions.
  6. Check gradient flow -- no vanishing, no exploding.
  7. Verify data pipeline -- print 5 random samples with labels.
Industry practice
What's current (2024–2026)
  • Experiment trackers are the debugger. Weights & Biases, MLflow and TensorBoard log losses, gradient norms, learning rate and sample outputs every few steps; most training bugs are found by looking at these curves.
  • Built-in checks. torch.autograd.set_detect_anomaly(True) finds the operation that produced a NaN, and the PyTorch Profiler finds slow data loading; Hugging Face Trainer logs gradient norms by default.
  • Overfit one batch first. Making the model memorise a single batch remains the standard first test in production training code.

You are a neural network debugging expert. Given a description of training behavior, diagnose the root cause and prescribe a fix.

## Input

I will describe:
- The loss curve behavior (flat, oscillating, NaN, decreasing then plateau)
- Model architecture (layers, activations, normalization)

## Diagnostic Protocol

### Step 1: Classify the Symptom

| Symptom | Category |
|---------|----------|
| Loss not decreasing at all | OPTIMIZATION FAILURE |
| Loss NaN or Inf | NUMERICAL INSTABILITY |
| Loss decreasing but model bad | GENERALIZATION FAILURE |
| Loss oscillating wildly | HYPERPARAMETER PROBLEM |
| Training works, inference wrong | EVAL MODE BUG |

### Step 2: Run the Decision Tree

**OPTIMIZATION FAILURE:**
1. Is the learning rate reasonable? (Adam: 1e-4 to 1e-2, SGD: 1e-3 to 1e-1)
2. Are gradients flowing? Check gradient magnitude per layer.
3. Are neurons alive? Check fraction of zero activations after ReLU.
4. Does the model pass the overfit-one-batch test?
5. Are parameters actually being updated? Compare weights before/after a step.

**NUMERICAL INSTABILITY:**
1. Is learning rate too high? Reduce by 10x.
2. Is there a log(0) or division by zero? Add epsilon.
3. Are activations overflowing in exp()? Use log-sum-exp trick.
4. Is batch norm getting a constant batch? Add epsilon to denominator.

**GENERALIZATION FAILURE:**
1. Is there a train/test gap? If >10% accuracy gap, overfitting.
2. Is there data leakage? Check for duplicates across splits.
3. Are labels correct? Manually inspect 20 random samples.
4. Is the test distribution different from training? Check feature distributions.

**HYPERPARAMETER PROBLEM:**
1. Run the learning rate finder to get the right order of magnitude.
2. Try batch sizes: 32, 64, 128, 256.
3. Try gradient clipping at 1.0.

**EVAL MODE BUG:**
1. Is `model.eval()` called before inference?
2. Is `torch.no_grad()` used for inference?
3. Are dropout and batch norm behaving correctly?

### Step 3: Prescribe the Fix

For each diagnosis, provide:
1. The specific code change needed
2. Expected behavior after the fix
3. How to verify the fix worked

## Output Format

```
SYMPTOM: [description]

EVIDENCE: [what confirms this diagnosis]

VERIFICATION: [how to confirm the fix worked]

```

## Common Patterns

| Architecture | Common bug | Fix |
|-------------|-----------|-----|
| Deep MLP (>5 layers) | Vanishing gradients | Add residual connections or batch norm |
| CNN | Shape mismatch after pooling | Print shapes after every layer |
| RNN/LSTM | Exploding gradients | Clip gradients to norm 1.0 |
| Transformer | Attention scores overflow | Scale by 1/sqrt(d_k) |
| Fine-tuning pretrained | Catastrophic forgetting | Use 10-100x smaller LR than pretraining |
| GAN | Mode collapse | Check discriminator accuracy, adjust training ratio |

# Neural Network Debug Checklist

Systematic debugging protocol for when training goes wrong. Work through these in order -- most bugs are caught in the first 3 steps.

## Before training (prevent bugs)

1. Print model architecture and parameter count. Does the size make sense for your data?
2. Run a single forward pass with random input. Does the output shape match your target shape?
3. Check that labels are the correct dtype (CrossEntropyLoss needs Long, BCELoss needs Float)
4. Verify data normalization: inputs should have mean near 0 and std near 1
5. Print 5 random (input, label) pairs. Do the labels match what you expect?
6. Confirm train/test split has no duplicate samples

## Overfit-one-batch test (60 seconds, catches 80% of bugs)

1. Take 8-32 samples from your training set
2. Train for 200 steps with a reasonable learning rate
3. Loss should approach 0. Training accuracy should hit 100%
4. If it fails: the bug is in your model, loss function, or training loop -- not your data or hyperparameters
5. If it passes: proceed to full training

## Loss not decreasing

1. Check learning rate. Try 3 values: current/10, current, current*10
2. Print gradient norms per layer. All zeros means dead network or detached graph
3. Check `requires_grad=True` on parameters. Check that `loss.backward()` is called
4. Check that `optimizer.zero_grad()` is called before `loss.backward()`
5. Check that `optimizer.step()` is called after `loss.backward()`
6. Verify model parameters are passed to the optimizer: `optimizer = Adam(model.parameters())`

## Loss is NaN or Inf

1. Reduce learning rate by 10x
2. Add epsilon to all log() calls: `torch.log(x + 1e-7)`
3. Add epsilon to all division: `x / (y + 1e-8)`
4. Clamp predictions: `torch.clamp(pred, 1e-7, 1 - 1e-7)` before BCE loss
5. Use `torch.autograd.detect_anomaly()` to find the exact operation
6. Check for NaN in input data: `assert not torch.isnan(x).any()`

## Loss oscillating

1. Reduce learning rate by 3-10x
2. Increase batch size (reduces gradient noise)
3. Add gradient clipping: `torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)`
4. Switch from SGD to Adam (adaptive LR per parameter)
5. Add learning rate warmup for the first 5-10% of training

## Overfitting (train acc high, test acc low)

1. Add dropout (start with p=0.1, increase to 0.5)
2. Add weight decay to optimizer: `Adam(params, weight_decay=1e-4)`
3. Reduce model size (fewer layers or narrower layers)
4. Add data augmentation
5. Use early stopping: stop when validation loss increases for 5+ epochs
6. Check for data leakage between train and test sets

## Underfitting (both train and test acc low)

1. Increase model capacity (more layers, wider layers)
2. Train for more epochs
3. Increase learning rate (carefully)
4. Remove regularization temporarily to verify the model can learn
5. Check that your model is expressive enough for the task

## Dead ReLU neurons

1. Check fraction of zero activations per layer. >50% is a problem
2. Switch to LeakyReLU(0.01) or GELU
3. Use Kaiming initialization for weights
4. Reduce learning rate (large updates can push neurons into the dead zone)
5. Add batch normalization before activation functions

## Quick reference: learning rate starting points

| Optimizer | Task | Starting LR |
|-----------|------|------------|
| Adam | Training from scratch | 1e-3 |
| Adam | Fine-tuning pretrained | 1e-5 |
| SGD + momentum | Training from scratch | 1e-1 |
| SGD + momentum | Fine-tuning pretrained | 1e-3 |
| AdamW | Transformer training | 3e-4 |

## Quick reference: batch size effects

| Batch size | Gradient noise | Memory | Generalization |
|-----------|---------------|--------|---------------|
| 8-16 | High (noisy) | Low | Often better |
| 32-64 | Moderate | Moderate | Good default |
| 128-256 | Low (smooth) | High | May need warmup |
| 512+ | Very low | Very high | Needs LR scaling |

## When nothing works

1. Simplify the model to 1 hidden layer. Does it learn?
2. Simplify the data to 100 samples. Does it overfit?
3. Replace your loss with MSE. Does it converge?
4. Replace your optimizer with SGD(lr=0.01). Does it make progress?
5. Replace your data with synthetic data (e.g., y = x[0] > 0). Does it learn?
6. If none of these work: the bug is in code you are not looking at (data loading, preprocessing, tensor shapes)

Debug a failureA run trains for hours with a smooth loss. Then, within three logging intervals, the loss jumps, becomes inf, and every value after that is NaN. The same recipe worked on a smaller model. Give your ranked list of causes, the evidence that separates them, and the changes that keep it from happening again.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. A clean run that dies late is almost always an oversized update: the peak learning rate is too high for the larger model, a rare batch produced a huge gradient, or the schedule reached its peak at a point where the model was already sensitive. The logs separate the cases: for an explosion the gradient norm spikes before the loss does, while a forward pass overflow, such as a softmax without the max shift or a normalization over a zero variance, shows a normal norm and a loss that goes to inf in one step. Fix with gradient clipping by norm at 1.0, a lower peak with warmup, and a loss computed from logits, then resume from the last good checkpoint.

Rank the causes.

  1. Update too large for this model. The debugging lesson's table: a loss that goes NaN after some steps means the learning rate is too high, and the first move is to reduce it by 10 times. The peak that was safe on the smaller model is close to the edge on the larger one. The capstone lesson advises sweeping the peak on a small model as a prior, and says the optimum shifts with size, so confirm rather than copy.
  2. One bad batch. A single outlier batch produces a gradient large enough to corrupt every weight in one step. Without clipping, nothing stops it.
  3. Schedule position. Check where the schedule was when the loss jumped. A short warmup or a peak reached at the wrong time puts the largest steps on a model that cannot take them.
  4. Forward pass overflow. An exp in a hand written softmax without the max shift, a log of zero, or a division by a zero variance in a normalization. These produce inf at once, usually at the first step, so they rank low for a run that was clean for hours, but a rare batch can trigger them late.

What the logs show.

  • The gradient L2 norm logged beside the learning rate every step. The capstone lesson's rule: a divergent run shows the norm spike before the loss does. An overflow shows a normal norm and a loss that is inf in a single step.
  • Per-layer gradient statistics. The debugging lesson flags a layer whose mean absolute gradient exceeds 100 as exploding and shows which layer went first.
  • Replay. Load the last good checkpoint, feed the batch from the failing step, and watch the norm. If that batch alone reproduces the spike, it is the trigger; if it does not, the schedule or the rate is.
  • Anomaly detection in the autograd engine, to name the operation that produced the first NaN.

Changes that prevent a repeat.

  • Clip the gradient by its global norm at 1.0 before the step. Clipping by norm keeps the direction; clipping each element does not.
  • Lower the peak and keep a warmup of 1 to 5 percent of the steps, so the largest steps arrive after the optimizer statistics settle.
  • Compute the loss from logits with a fused, stable function, and keep epsilons in logs and divisions.
  • Checkpoint often enough that a resume costs minutes, and alert on a NaN loss so the run stops at the first bad step rather than hours later.

Plausible wrong answers.

  • "Add an epsilon to the loss and restart." An epsilon fixes a log of zero at step one; a late explosion comes from the update size, and the run will die again.
  • "Halve the learning rate and hope." Halving is a guess; the lesson's move is a 10 times reduction, together with clipping and a check of the schedule position.
  • "NaN means the data has a bad row." A bad row shows in the first epoch, not after hours of clean training; replay the failing batch on the checkpoint before you blame it.

Follow-ups an interviewer may ask.

  • (level 3) What in the logs separates an oversized update from a forward pass overflow? Expected: the gradient norm rises over several steps before the loss for an explosion; an overflow shows a normal norm and a loss that goes to inf in a single step.
  • (level 4) Why clip by norm rather than by value? Expected: clipping by norm scales the whole gradient and keeps its direction; clipping each element changes the direction.
  • (level 4) Why did the recipe work on the smaller model? Expected: the peak that was safe there sits near the edge for the larger one; a sweep on the small model is a prior, and the optimum shifts with size, so verify rather than copy.
  • (level 4) What do you add so the run never dies silently again? Expected: log the gradient norm beside the learning rate each step, alert on a NaN loss, checkpoint often enough to resume, and restart with clipping and a warmup.

Debug a failureA ten class classifier trains for many epochs, and the cross-entropy loss sits at about 2.3 the whole time, on training data and on validation data. Nothing crashes. What does that number tell you, and in which order do you debug?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Minus the natural log of one tenth is about 2.3, the loss of a model that gives every class the same probability, and the lesson's table reads a loss stuck there as a uniform prediction with no usable signal. The mean alone does not say why. Run the one batch overfit test first: a failure points at the loss, the backward pass, the optimizer hookup or misaligned labels, and a pass sends you to the data path to check that labels line up with inputs. Only then look at the learning rate, the gradients and the architecture.

Reading the number.

Categorical cross-entropy on a one-hot target is minus the log of the probability of the true class. A random guess among 10 classes gives each class probability 0.1 and a loss of minus log 0.1, about 2.3. The debugging lesson's master table has this row: a loss stuck at minus log of 1 over the class count means the model predicts a uniform distribution, and the first thing to check is the data pipeline and whether labels match inputs. A model with no usable signal settles on equal logits, because that is what minimizes the expected loss over a balanced label set.

The order.

  1. Overfit one batch. Take 8 to 32 samples and train on them for a few hundred steps. The loss must go to near zero and the training accuracy to 100 percent. If it does not, the model or the loop is broken: a wrong loss, a broken backward pass, an optimizer not connected to the parameters, or inputs and labels out of step. The lesson's threshold for a pass is a final loss below 0.1.
  2. Look at the data. Print 5 random samples with their labels. Check that the shuffle keeps each input paired with its label, that inputs are normalized to mean 0 and standard deviation 1, and that labels have the integer type the loss expects.
  3. Learning rate. Try three values 10 times apart, such as 1e-2, 1e-3 and 1e-4. A rate that is far too low looks flat, but it would not sit exactly on the uniform value for many epochs.
  4. Gradients. All zeros points at dead ReLUs or a detached graph.
  5. Architecture. Only after the above: a model too small underfits, but it still beats a uniform guess on its own training data.

How this differs from a slow start.

A loss that starts near 2.3 and falls slowly is a learning rate or capacity question. A loss that holds at 2.3 for many epochs on the training set means no signal reaches the model at all.

Plausible wrong answers.

  • "Train longer, it is a slow start." A flat value at the uniform loss for many epochs means no signal, not a slow one.
  • "Make the model bigger." Capacity is not the issue when the model cannot beat a uniform guess on its own training data.
  • "Lower the learning rate." The rate changes how fast the loss moves, and here it does not move at all; check the data first.

Follow-ups an interviewer may ask.

  • (level 3) Why uniform rather than some other wrong answer? Expected: with no usable signal, equal logits minimize the expected cross-entropy over a balanced label set, and that costs the log of the class count.
  • (level 3) What does the overfit one batch test tell you here? Expected: whether the model and loop can learn at all; a healthy setup drives a small batch to near zero loss in a few hundred steps, and a failure means a broken loss, backward pass, optimizer hookup or misaligned labels.
  • (level 4) The one batch test passes and full training still sits at 2.3. Where next? Expected: the full data path, such as a shuffle that breaks the pairing of inputs and labels, or unnormalized inputs, since the model can learn when given a consistent batch.
  • (level 4) What distinguishes this symptom from a loss that starts at 2.3 and falls slowly? Expected: a slow fall is a learning rate or capacity question; a flat 2.3 for many epochs means no signal reaches the model.

Read the codeThis loop trains a small network with plain SGD at a small learning rate on a fixed batch. python for step in range(50): out = model(x) loss = criterion(out, y) loss.backward() optimizer.step() The loss falls for a few steps and then swings up and down. Read the loop, name the bug, explain the mechanism, and say where the fix goes.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. The loop never zeroes the gradients, so each backward call adds the new gradient on top of all the earlier ones. The step applies a growing sum, which acts like a learning rate that rises at every step, and the loss oscillates. Add the optimizer's zero_grad call before backward, which is where the lesson's correct loop puts it.

Why the gradient grows.

Gradient storage is an accumulator by design. A parameter used in several places sums its contributions, and a backward call adds into the stored gradient rather than replacing it. In the mini framework the Linear layer's backward does exactly that, with a plus-equals into the weight gradients, and the optimizer's zero_grad sets every gradient container back to 0.0. A framework does the same. Without the reset, step one applies g1, step two applies g1 plus g2, step three applies the sum of three, and so on. The direction stays roughly right for a while and the magnitude climbs until the updates overshoot.

The lesson's order.

zero_grad, forward, loss, backward, (clip), step, (schedule)

The debugging lesson lists a forgotten zero_grad first among the bugs that waste the most hours, with this symptom: gradients accumulate across batches and the loss oscillates. Its demo reproduces the exact loop above and reports it. The optimizers lesson adds the ordering rule for the two trailing calls: the scheduler steps after the optimizer, and swapping them is a subtle bug.

How to see it in logs.

On a fixed batch the gradient norm should fall or hold as the loss falls. With this bug it grows step after step while the loss first improves and then swings with increasing amplitude. The overfit one batch test, which this loop resembles, would fail to reach a near zero loss.

When accumulation is on purpose.

Gradient accumulation across several small batches emulates one large batch: run backward on each micro batch without zeroing, then take one step and one zero_grad for the group, with the loss scaled by the group size. That is an exercise in the framework lesson. The difference from the bug is the single step per group and the division.

Plausible wrong answers.

  • "The learning rate is too high." The rate is small; the accumulated gradient is what grows.
  • "Reset the gradients only every few steps to smooth them." That is accumulation without the division; the step size scales with the group size and the loss swings.
  • "Detach the loss each step to stop the buildup." Detaching stops the graph, not the stored gradients; the gradient buffers still hold the sum.

Follow-ups an interviewer may ask.

  • (level 3) Why do frameworks accumulate gradients instead of overwriting them? Expected: a parameter used in several places sums its contributions, and accumulation across micro batches emulates a larger batch; the reset is left to the caller.
  • (level 3) Where do clipping and the schedule go in the order? Expected: zero_grad, forward, loss, backward, clip, step, schedule; the scheduler steps after the optimizer.
  • (level 4) How would you detect this bug from logs without reading the code? Expected: the gradient norm grows step after step on a fixed batch where it should shrink or hold, and the loss oscillates with growing amplitude.
  • (level 4) When is skipping zero_grad on some steps correct? Expected: deliberate accumulation over several micro batches, with one step and one zero_grad after the group and the loss scaled by the group size.

Defend a designYou are about to launch a multi-day training run on a new architecture with a new data pipeline. Design a check that runs in about 30 seconds and must pass before the run starts. List the classes of bugs it catches and the ones it does not.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Take one small batch of 8 to 32 samples and train on it alone for a few hundred steps. The loss must fall to near zero and the training accuracy must reach 100 percent. A pass shows that the loss function, the backward pass and the optimizer hookup work, and that the model can fit this batch, but not that each input has its correct label, because a model can memorize a wrong but consistent pairing as well. It says nothing about generalization, leakage or the full data loader, so it is the first gate and not the last.

The test.

The debugging lesson calls this the single most important technique in deep learning. Fix a batch, build a fresh model and optimizer, and loop: zero the gradients, forward, loss, backward, step. Print the loss and accuracy every 50 steps. The lesson's implementation runs 200 steps and treats a final loss above 0.1 as a failure.

What a failure means.

Any of these, and the lesson lists them:

  • a loss function that does not match the output layer;
  • a broken backward pass or a detached graph;
  • an optimizer built before the model's parameters existed, so it updates nothing;
  • inputs and labels out of step;
  • an architecture too small to represent even this batch.

Each of these would also break the full run, and there it would show up hours later as a slow or flat loss with twenty possible causes. Here it shows up in seconds with five.

What a pass does not prove.

The test overfits by design, so it says nothing about generalization. A model can memorize any consistent labels, so a wrong pairing of inputs and labels inside the fixed batch also passes. It uses one batch, so a shuffle that unpairs inputs and labels across the full set, a normalization computed on the full dataset, duplicate rows across splits, or label noise can all survive it. The lesson's checklist continues after it: print the model summary and check the parameter count, run one forward pass on random data and check the output shape, train for 5 epochs and confirm the loss falls, check activation statistics for dead or exploding layers, check the gradient flow across layers, and print 5 random samples with their labels.

Make it a gate.

Run it at startup on a fixed batch, assert the final loss is below the threshold, and refuse to start the long run when it fails. Run it again whenever the architecture or the pipeline changes.

Plausible wrong answers.

  • "A passing test means the model will generalize." It proves the model can memorize one batch; generalization needs the validation curve.
  • "Skip it, the full run shows problems soon enough." The run shows a symptom hours later and the symptom fits many causes; the test isolates the loop in seconds.
  • "Use the whole training set for a few epochs instead." That is the full run; a small batch is what makes a failure unambiguous and fast.

Follow-ups an interviewer may ask.

  • (level 3) The loss on the one batch stalls well above the threshold. Name three suspects. Expected: a loss that does not match the output layer, an optimizer built before the model's parameters were created, or a model too small to fit the batch.
  • (level 3) Why 8 to 32 samples? Expected: small enough that a correct model memorizes it in a few hundred steps, so a failure is unambiguous and the test stays fast.
  • (level 4) The test passes and the full run later shows training accuracy at chance. What does the pass rule out, and what remains? Expected: the model and loop can learn, so what remains is the full data path: a shuffle that unpairs inputs and labels, or normalization computed differently for the full set.
  • (level 4) How do you turn this into a gate in a training script? Expected: run it on a fixed batch at startup, assert the final loss is below the threshold, refuse to start the long run on a failure, and rerun it whenever the architecture or pipeline changes.

Where it is taught. The debugging lesson implements the test, lists what it catches, and places it first in the pre-training checklist.

Defend a designYou inherit a model with no known good learning rate and a compute budget of a few hours. Design the procedure that picks the peak learning rate and the schedule for the run, and say what you log to defend the choice.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Run a learning rate range test first: train for about a hundred steps while the rate grows exponentially from 1e-7 toward 10 and record the loss at each rate. Take the rate where the loss falls fastest and set the peak about 10 times lower. Then run a linear warmup over 1 to 5 percent of the steps into a cosine decay with a floor near a tenth of the peak, or the 1cycle policy when the budget is short and the total step count is fixed. Log the range test curve, the schedule curve and the gradient norm beside the learning rate at every step.

Step one: measure, do not guess.

The debugging lesson's range test: save the weights, start at 1e-7, multiply the rate by a constant factor each step so it reaches about 10 after a hundred steps, record the loss, and stop when the loss turns NaN or exceeds ten times the best value seen. Restore the weights. The loss is flat at the low end, falls fastest around some rate, reaches its minimum, and diverges. The suggested peak is about 10 times below the steepest fall, which in the lesson's example puts the best rate near 1e-3 when the steepest point sits near 1e-2. The lesson's second rule covers the case where the curve is unclear: try three rates 10 times apart, such as 1e-2, 1e-3 and 1e-4, and read the loss after a few epochs.

Step two: pick the shape from the budget.

Situation Schedule Why
Total steps unknown constant, with manual drops nothing else can be computed
Hours, step count fixed 1cycle fastest convergence for a fixed budget
Moderate budget cosine, floor at a tenth of the peak safe default with no extra knobs
Days or weeks warmup plus cosine the default for large transformer runs

For a few hours with a known step count the schedules lesson points at 1cycle, which ramps from the peak over 25 up to the peak over the first half and down to the peak over 10000 in the second half. For anything longer, warmup plus cosine with a warmup of 1 to 5 percent. With an adaptive optimizer the warmup is not optional: its moment estimates are poor for the first steps.

Step three: sanity check the peak.

The schedules lesson's sensitivity run trains a few epochs at a constant rate and labels each run diverged, barely moved, learning or converged. Run it at the chosen peak and at the rates one step above and below. The peak should land in learning or converged, and the rate above it should show the first signs of trouble.

What to log.

  • The range test curve, loss against rate on a log axis, with the chosen peak marked.
  • The schedule rendered over the step axis, saved in the run directory so a reviewer can read it without running anything.
  • Per step: step, learning rate, gradient L2 norm and loss, in that order. The capstone lesson's rule is that a healthy warmup shows the norm rising with the rate and settling after the peak, and that a peak set too high shows a norm that stays high.
  • The four schedule numbers in a versioned config, with the warmup as a fraction of the total so the choice survives a longer run.

Defaults for when there is no time.

The optimizers lesson's fallback: AdamW at 3e-4 with weight decay 0.01 for an unknown model, 2e-5 for fine-tuning a pretrained one. Treat these as the starting point of the range test, not as its result.

Plausible wrong answers.

  • "Use 3e-4 for Adam, it always works." It is the lesson's starting default when nothing is known, not a result; the range test takes minutes and replaces a guess with a measurement.
  • "Pick the rate with the lowest loss in the range test." The lowest point sits next to divergence; the lesson picks about 10 times lower than the steepest fall.
  • "A constant rate is fine if it is the right one." The right rate changes during training; a constant that fits the start is too large at the end, and the lesson keeps constant rates for small models and debugging.

Follow-ups an interviewer may ask.

  • (level 3) Why set the peak below the steepest point rather than at it? Expected: the steepest point is close to where the loss starts to diverge, and a long run needs a margin; one order of magnitude lower keeps it.
  • (level 4) When do you choose 1cycle over warmup plus cosine? Expected: a short, fixed budget where the total step count is known; it converges faster for a fixed compute and needs the step count in advance.
  • (level 4) The peak is right and the loss still oscillates near the end. What do you adjust? Expected: the decay, not the peak; a schedule that ends too high leaves steps too large for the final minimum, so lower the floor or lengthen the decay.
  • (level 4) How does the model's size change the plan? Expected: sweep the peak on a smaller version first as a prior, then confirm with the range test on the full model, because the optimum shifts with size.

Check your understanding

Q1Why is neural network debugging harder than traditional software debugging?

Traditional bugs crash or throw exceptions. Neural network bugs produce a number that's just wrong -- a loss that doesn't decrease, accuracy that plateaus, or outputs that are subtly incorrect. No error message tells you what went wrong.

Q2What is the 'overfit one batch' debugging technique?

If your model can't memorize a tiny batch (e.g., 4-8 samples) to near-zero loss, something is fundamentally broken: wrong architecture, broken loss function, or incorrect training loop. This is the first diagnostic to run.

Q3Your loss is NaN after a few training steps. What is the most likely cause?

NaN loss typically comes from numerical overflow: gradients explode, weights grow unbounded, and operations like log(0) or exp(1000) produce infinity/NaN. Lower the learning rate or add gradient clipping.

Q4Your training loss decreases but validation loss stays flat from the start. What does this indicate?

If validation loss never improves, the model is either memorizing training noise (overfitting), or there's a data pipeline bug where train and validation distributions are fundamentally different.

Q5What should you check first when your loss curve is completely flat (loss doesn't decrease at all)?

A flat loss means the model isn't updating. Common causes: zero gradients (dead neurons, detached tensors), learning rate too small, or a loss function that doesn't flow gradients to the model (e.g., using .item() before .backward()).
