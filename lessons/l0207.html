Why this came about

Researchers found in 2022 that asking a model to work through intermediate steps (chain-of-thought) markedly improved its accuracy on reasoning problems, and variations such as sampling several answers and voting followed. In 2024 reasoning models began doing this internally, trained to think before answering. Knowing both explains when to ask for reasoning and when it only adds cost.

In plain words first
Showing your working

Some problems are answered better when the model works through intermediate steps before the final answer, the way a student shows their working. Techniques such as chain-of-thought, asking for several attempts and voting (self-consistency), or breaking a problem into sub-questions trade more tokens and time for accuracy. Reasoning models do much of this internally, so the techniques matter most with standard models and for making reasoning visible and checkable.

Reasoning techniques in prompts

How this connects

Lesson 10.14 explained why thinking longer helps a model, built self-consistency (voting over several sampled answers), and showed how reasoning models are trained to do this by themselves. This lesson is the prompt-writer's side of the same ideas: the named techniques people used to get that behaviour from ordinary models, what each looks like in a prompt, and which are still worth using now that reasoning is built in.

Before reasoning models, a family of prompting techniques got models to reason better, and they are still widely discussed and still useful with smaller, non-reasoning models. First, what three of them look like. The customer question is the same each time: "I ordered 3 kettles at ₹1,200 each. One arrived broken. Shipping was ₹150 for the whole order. How much should I be refunded?" (ShopKart refunds the broken item and none of the shipping, so the right answer is ₹1,200.)

A direct prompt asks for the answer and nothing else:

How much should the customer be refunded? Reply with the amount only.

A model answering in one step has to produce the first digit of the answer before it has worked anything out. Weak models often grab a visible number: ₹3,750 (the whole order) or ₹1,350 (item plus shipping).

Chain-of-thought asks the model to write its working first. The zero-shot form is one added sentence:

How much should the customer be refunded?
Work through it step by step, then give the amount on the last line as "Refund: ₹...".

Now the model writes "One kettle costs ₹1,200. One was broken, so one item is refunded. Shipping is not refunded..." and each sentence it has written is in its context when it writes the next one (Lesson 7.19: every token is predicted from all the tokens before it). The reasoning is not decoration; it is the scratch paper the answer is computed on. The few-shot form shows one or two solved examples with their working instead of the instruction.

Decomposition makes the steps explicit and separate:

Answer these in order.
1. Which items were broken, and what did each cost?
2. Is shipping refundable under the policy?
3. What is the total refund?

Split across separate model calls, with a check between them, this becomes prompt chaininglater · 14.8, the first workflow patternlater · 14.8 of Lesson 14.8.

The full family, and whether each is still worth using:

Technique What it does Still worth it?
Chain-of-thought (CoT) Show worked examples with reasoning steps, or simply add "think step by step" (zero-shot CoT) Yes for non-reasoning models on multi-step problems; reasoning models do this internally

Self-consistency is easy to reason about with a little probability, and the result is worth knowing: voting helps only when a single path is right more often than not.

from math import comb
def majority_vote_accuracy(p, n):
    """Self-consistency: sample n independent reasoning paths, take the most common answer.
    Each path is right with probability p. Worst case assumed: every wrong path gives the SAME wrong answer,
    so the right answer needs a strict majority. When wrong answers scatter, voting does even better."""
    return sum(comb(n, k) * p ** k * (1 - p) ** (n - k) for k in range(n // 2 + 1, n + 1))

for p in [0.4, 0.6, 0.75]:
    row = "  ".join(f"n={n}: {majority_vote_accuracy(p, n):.0%}" for n in [1, 5, 15])
    print(f"single path right {p:.0%} -> {row}")
What you should see
single path right 40% -> n=1: 40%  n=5: 32%  n=15: 21%
single path right 60% -> n=1: 60%  n=5: 68%  n=15: 79%
single path right 75% -> n=1: 75%  n=5: 90%  n=15: 98%

At 75% per path, 15 votes reach 98%. At 40%, voting makes things worse, because the wrong answer wins the majority more often. Self-consistency amplifies a model that is usually right; it cannot rescue one that is usually wrong, and it multiplies cost by the number of samples, so keep it for short, high-value decisions.

What to use today

Your situation Use Why
A reasoning model, or a frontier model with thinking switched on A clear goal, the constraints, and what "done" looks like. Set the reasoning effort; do not add "think step by step" The model already reasons before answering (Lesson 11.6). Extra procedure can make it worse
A small or older model on a multi-step problem Chain-of-thought, with the final answer on a marked last line that code can pick out The working gives the model somewhere to compute
A short, checkable answer where mistakes are costly (a label, an amount, yes or no) Self-consistency: three to five samples and a vote Cheap insurance, if one path is right more often than not
A long task with distinct stages Decomposition into separate calls with a check after each (Lesson 14.8) Each call is simpler, and a failure is caught where it happens
A draft that can be checked by a program (tests, a schema, a calculation) Self-refine: run the check and send the failure back The check, not the model's opinion of itself, drives the improvement
A draft with nothing to check it against One careful pass, then human review "Are you sure?" with no new information mostly produces a different answer, not a better one (Lesson 14.9)
Watch out
Visible reasoning is not a guarantee

A written chain of thought can contain a wrong step and still end in the right answer, or look flawless and end in a wrong one. Treat it as a debugging aid. What you trust is the final answer after it has been checked: by code where that is possible, by a second sample or a person where it is not.

Check your mental model
  • ✗ "More reasoning always means better answers."
    ✓ It helps on multi-step problems and adds cost and latency everywhere else.
  • ✗ "The model's written reasoning is exactly how it decided."
    ✓ It is useful evidence, not a guaranteed account of the computation.
  • ✗ "Self-consistency is free accuracy."
    ✓ It multiplies cost by the number of samples.

Make it your own

Solutions

SolutionP1 · Small gains, triple cost

majority_vote_accuracy(0.6, 3) is 0.648, about 65%: five points for three times the tokens. Worth it only for a short, high-value decision; for most calls a better prompt, a better model or a checker gives more per rupee.

SolutionB1 · Votes need comparable answers

Free text rarely repeats exactly, so there is no majority. Self-consistency needs short, checkable answers: a label, a number, a choice. For long outputs, use a judge or a checker to pick the best sample, or extract a short claim from each sample and vote on that.

SolutionD1 · Below 50%, voting amplifies the error

At p below 0.5 under the worst case (wrong answers agree), the majority is wrong more often than a single sample, as the 40% row shows. Voting amplifies whatever is most likely. Improve the single-path accuracy first (better prompt, examples, a reasoning model, decomposition), then add voting once a single path is right well over half the time.

SolutionM1 · Scattered wrong answers

Simulate it rather than solving it by hand: for each trial draw n answers, right with probability p, otherwise one of three wrong labels at random, and count how often the right label has the most votes (break ties at random). With p = 0.4 and n = 5, the right answer now wins most of the time, because the wrong votes split. That is the "voting does even better" case in the function's comment, and it is why self-consistency helps more on open questions with many possible wrong answers than on yes/no questions.

Check your understanding

Explain the mechanismWhat is chain-of-thought prompting, and does it still matter with reasoning models?

Worked answer. Chain-of-thought asks a model to write intermediate steps before the answer, through worked examples or an instruction to think step by step, which improves multi-step problems for models that do not reason by default. Reasoning models are trained to reason internally, so explicit chain-of-thought instructions add little and can hurt; with them, give the goal, constraints and success criteria, and set the reasoning effort or budget instead. It still matters for small and non-reasoning models.

A plausible wrong answer. "Always add 'think step by step'." For reasoning models that is redundant, and the extra visible reasoning costs tokens.

Follow-ups. What is self-consistency, and when does it help?

Debug a failureAdding chain-of-thought made a classifier slower and no more accurate. What now?

Worked answer. Check whether the task needs reasoning at all; single-label classification with clear categories often does not. Look at the errors: if they come from ambiguous categories, fix the label definitions and examples; if from missing information, add it to the context. Remove the reasoning step if it does not help on the eval set, or keep it only for the low-confidence cases.

A plausible wrong answer. "Make the chain longer." More reasoning does not fix unclear labels.

Follow-ups. How would you route only hard cases to a slower method?

Defend a designSelf-consistency or a better model: which would you pay for?

Worked answer. It depends on single-path accuracy and cost. Self-consistency multiplies cost by the number of samples and helps only when a single path is right well over half the time; a better model raises single-path accuracy for every call. I would measure both on the eval set and compare accuracy per unit of cost and latency. Often the answer is a better prompt or model first, and voting only for a narrow, high-value decision.

A plausible wrong answer. "Voting is always cheaper than a bigger model." Five calls to a small model can cost more than one to a larger one.
