About the model on this page
What is real and what is a stand-in

The graphs are real LangGraph. Most nodes are plain functions; the order service that fails twice is simulated with a counter. The agent in Idea 4 uses the lab rig (Lesson 14.92) as its model.

Why this came about

Agents need to choose paths and repeat steps until done. Conditional edges, loops with limits and Command gave LangGraph explicit control flow, and the agent loop itself became one small graph.

The problem: real workflows branch and repeat

The refund workflow from Lesson 14.100 is not a straight line. A question that is not about a refund goes to a person. The order service sometimes fails, so the lookup is retried, but not forever. And the agent loop itself, model then tools then model again, is a cycle that ends when the model stops asking for tools. Edges that always go to the same node cannot express any of that.

In plain words first
A dispatcher, a loop and a self-routing worker

Real workflows branch and repeat. A conditional edge is a dispatcher after a node: it reads the state and names the next node. A loop is an edge back to an earlier node with a rule to stop. A node can also route itself by returning a Command (update the state and go there). And context carries per-run values such as the customer, which never change during the run and are never saved.

Idea 1 · Conditional edges

An ordinary edge always goes to the same node. A conditional edge calls a small function, the router, which reads the state and returns the name of the node to run next. In this refund workflow a classify node records the customer's intent, and the router sends refund requests one way and everything else another:

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END


class RefundState(TypedDict, total=False):
    msg: str
    intent: str
    tries: int
    order: dict
    done: str

def classify(state):
    return {"intent": "refund" if "refund" in state["msg"].lower() else "other"}

def route_intent(state) -> Literal["lookup", "handoff"]:     # the return type lists the possible next nodes
    return "lookup" if state["intent"] == "refund" else "handoff"

def lookup(state):
    return {"order": {"id": "A-1077", "amount": 7999}}

def refund(state):
    return {"done": f"refunded INR {state['order']['amount']:,} on {state['order']['id']}"}

def handoff(state):
    return {"done": "sent to a person"}

b = StateGraph(RefundState)
for name, fn in [("classify", classify), ("lookup", lookup), ("refund", refund), ("handoff", handoff)]:
    b.add_node(name, fn)
b.add_edge(START, "classify")
b.add_conditional_edges("classify", route_intent)
b.add_edge("lookup", "refund")
b.add_edge("refund", END)
b.add_edge("handoff", END)
graph = b.compile()

for msg in ["I want a refund for A-1077", "Do you sell gift cards?"]:
    print(f"{msg:28} -> {graph.invoke({'msg': msg})['done']}")
What you should see
I want a refund for A-1077   -> refunded INR 7,999 on A-1077
Do you sell gift cards?      -> sent to a person

add_conditional_edges takes a router: a function that reads the state and returns the name of the next node. The Literal return type is not decoration: it tells LangGraph which nodes the router can choose, so compile() can check them and the drawn graph shows both branches. (Without it, pass the possible targets as a third argument, the path_map.) Keep routers pure: read the state, return a name. Work goes in nodes, where it is checkpointed and visible in traces.

Idea 2 · A loop with an exit

A conditional edge may point back to a node that has already run, which makes a loop. Every loop needs a way out. Here an order lookup fails twice before it works; the router sends the run back to try again, but only while a counter in the state is under a limit.

FAILS = {"count": 2}                                          # the order service fails twice, then works

def flaky_lookup(state):
    tries = state.get("tries", 0) + 1
    if FAILS["count"] > 0:
        FAILS["count"] -= 1
        return {"tries": tries, "order": None}
    return {"tries": tries, "order": {"id": "A-1077", "amount": 7999}}

def route_lookup(state) -> Literal["refund", "lookup", "handoff"]:
    if state["order"]:
        return "refund"
    return "lookup" if state["tries"] < 3 else "handoff"

def build(lookup_fn):
    b = StateGraph(RefundState)
    for name, fn in [("classify", classify), ("lookup", lookup_fn), ("refund", refund), ("handoff", handoff)]:
        b.add_node(name, fn)
    b.add_edge(START, "classify")
    b.add_conditional_edges("classify", route_intent)
    b.add_conditional_edges("lookup", route_lookup)            # a conditional edge back to itself: a loop
    b.add_edge("refund", END)
    b.add_edge("handoff", END)
    return b.compile()

loop_graph = build(flaky_lookup)
for update in loop_graph.stream({"msg": "I want a refund for A-1077"}, stream_mode="updates"):
    print(update)
What you should see
{'classify': {'intent': 'refund'}}
{'lookup': {'tries': 1, 'order': None}}
{'lookup': {'tries': 2, 'order': None}}
{'lookup': {'tries': 3, 'order': {'id': 'A-1077', 'amount': 7999}}}
{'refund': {'done': 'refunded INR 7,999 on A-1077'}}

The conditional edge from lookup can lead back to lookup. Two things make this loop safe. The counter is in the state, so each try sees the last one's count. And the router has an exit: after three tries, the case goes to a person. As a backstop for loops whose exit you got wrong, every run has a recursion limit, the maximum number of steps:

from langgraph.errors import GraphRecursionError

FAILS["count"] = 2
try:
    loop_graph.invoke({"msg": "I want a refund for A-1077"}, {"recursion_limit": 3})
except GraphRecursionError as e:
    print("GraphRecursionError:", str(e).split(".")[0])
What you should see
GraphRecursionError: Recursion limit of 3 reached without hitting a stop condition

The run needed five steps; a limit of three stopped it with an error instead of letting it loop. Set the limit per run in config, from the longest legitimate run plus a margin (Lesson 14.96).

Idea 3 · A node that routes itself

When the decision is made inside the node, return a Command with both the update and the next node:

from langgraph.types import Command

def classify_and_route(state) -> Command[Literal["lookup", "handoff"]]:
    intent = "refund" if "refund" in state["msg"].lower() else "other"
    return Command(update={"intent": intent}, goto="lookup" if intent == "refund" else "handoff")

b = StateGraph(RefundState)
for name, fn in [("classify", classify_and_route), ("lookup", lookup), ("refund", refund), ("handoff", handoff)]:
    b.add_node(name, fn)
b.add_edge(START, "classify")                                  # no conditional edge: the node routes itself
b.add_edge("lookup", "refund"); b.add_edge("refund", END); b.add_edge("handoff", END)
print(b.compile().invoke({"msg": "refund please, A-1077"})["done"])
What you should see
refunded INR 7,999 on A-1077

The Command[Literal[...]] return type plays the same role as the router's: it declares the possible targets. Use Command when the routing depends on work the node just did (here, the classification); use a conditional edge when routing is a separate, reusable rule. Command is also how a node hands control to another agent (Lesson 14.107) and how a run resumes after an interrupt (Lesson 14.104).

Idea 4 · The agent loop, built yourself

This is the graph create_agent built for you in Lesson 14.96:

from mockllm import start                                      # the lab rig (Lesson 6.1)
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langgraph.graph import MessagesState
from langgraph.prebuilt import ToolNode, tools_condition

ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@tool
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

chat = init_chat_model("openai:mock-model", base_url=start(), api_key="mock")
model = chat.bind_tools([get_order_status])

def call_model(state: MessagesState):
    return {"messages": [model.invoke(state["messages"])]}     # add_messages appends it

b = StateGraph(MessagesState)
b.add_node("model", call_model)
b.add_node("tools", ToolNode([get_order_status]))              # runs every tool call in the last message
b.add_edge(START, "model")
b.add_conditional_edges("model", tools_condition)              # tool calls -> "tools", otherwise -> END
b.add_edge("tools", "model")
react = b.compile()

out = react.invoke({"messages": [{"role": "user", "content": "Where are A-1001 and A-1002?"}]})
print([type(m).__name__ for m in out["messages"]], "|", out["messages"][-1].content)
What you should see
['HumanMessage', 'AIMessage', 'ToolMessage', 'ToolMessage', 'AIMessage'] | Here is what I found: A-1001 is shipped; A-1002 is processing

Three pieces. MessagesState gives you a messages key with the add_messages reducer (Lesson 14.101). ToolNode runs every tool call in the last AIMessage, in parallel, and returns one ToolMessage per call, with errors turned into results. tools_condition is the router: tool calls go to tools, anything else goes to END. The edge from tools back to model closes the loop. This is the ReAct pattern (reason, act, observe, repeat). Build it yourself when you need something create_agent's middleware cannot express, for example a node between the tools and the model that checks results against a policy.

Idea 5 · Per-run context

Some values belong to the run, not the state: who the customer is, their tier, a database connection. A context schema passes them to every node through runtime:

from dataclasses import dataclass
from langgraph.runtime import Runtime

@dataclass
class Customer:
    tier: str

def refund_limit(state, runtime: Runtime[Customer]):
    limit = 10000 if runtime.context.tier == "gold" else 5000
    amount = state["order"]["amount"]
    return {"done": "auto-refund" if amount <= limit else f"needs approval (limit INR {limit:,})"}

b = StateGraph(RefundState, context_schema=Customer)
b.add_node("lookup", lookup); b.add_node("decide", refund_limit)
b.add_edge(START, "lookup"); b.add_edge("lookup", "decide"); b.add_edge("decide", END)
policy = b.compile()
for tier in ["gold", "silver"]:
    print(tier, "->", policy.invoke({"msg": "refund"}, context=Customer(tier=tier))["done"])
What you should see
gold -> auto-refund
silver -> needs approval (limit INR 5,000)

Context is read-only and is not saved in checkpoints, so it is the right place for request-scoped values and dependencies, and the wrong place for anything the run must remember after a pause. (create_agent accepts a context_schema too, which middleware and tools can read.)

Beginners often mix up the four things a node can be handed. Think of a clerk working on one case: state is the case file being worked on; config is the envelope the job arrived in (which case number, what limits); context is the badge the clerk wears (who they act for); the store is the office filing cabinet that outlives every case.

Debugging exercise
Debugging exercise: the retry loop that never gives up

The order service is down. The workflow should hand off after three tries; instead it runs until the recursion limit:

def forgetful_lookup(state):
    tries = 1                                                  # the bug is on this line
    return {"tries": tries, "order": None}                     # the order service is down

try:
    build(forgetful_lookup).invoke({"msg": "I want a refund for A-1077"}, {"recursion_limit": 25})
except GraphRecursionError as e:
    print("GraphRecursionError:", str(e).split(".")[0])

What it printed:

GraphRecursionError: Recursion limit of 25 reached without hitting a stop condition

Find the bug. (Solution D1.)

Make it your own

Write lookup_with_backoff, a lookup node that waits longer before each retry (Lesson 14.59's exponential backoff), and run it once with a service that fails once and once with one that fails five times. (Solution M1.)

Solutions

SolutionP1 · Count every node run

Five steps: classify, lookup three times, refund. A limit of 5 is the smallest that finishes. Set the real limit with a margin, because the steps count every node, including ones you add later.

SolutionB1 · The router's options disappear

Without a return type or a path_map, LangGraph cannot know where the router may go. The drawn graph shows classify going straight to END, which is wrong, and a misspelled return value such as "lookupp" does not even raise: LangGraph logs a warning that a task "wrote to unknown channel" and the run simply ends with no answer. With the targets declared, the drawing is right and compile() checks that every declared target exists. Declare the targets, and test every branch.

SolutionD1 · The counter is reset every time

tries = 1 ignores the state, so every attempt reports the first try, the router always sees tries < 3, and the loop never reaches its exit. Read the previous value from the state:

def counting_lookup(state):
    return {"tries": state.get("tries", 0) + 1, "order": None}

print(build(counting_lookup).invoke({"msg": "I want a refund for A-1077"}))

{'msg': 'I want a refund for A-1077', 'intent': 'refund', 'tries': 3, 'order': None, 'done': 'sent to a person'}

The recursion limit did its job, turning an endless loop into an error. Add a test for the give-up path, which is the one most often wrong.

SolutionM1 · Backoff in a node
import time

def lookup_with_backoff(state):
    tries = state.get("tries", 0) + 1
    if tries > 1:
        time.sleep(0.01 * 2 ** (tries - 2))                     # 10 ms, then 20 ms: Lesson 3.4's backoff, shortened
    ok = FAILS["count"] <= 0
    FAILS["count"] -= 1
    return {"tries": tries, "order": {"id": "A-1077", "amount": 7999} if ok else None}

for failures in [1, 5]:
    FAILS["count"] = failures
    out = build(lookup_with_backoff).invoke({"msg": "I want a refund for A-1077"})
    print(f"{failures} failure(s): {out['tries']} tries -> {out['done']}")

1 failure(s): 2 tries -> refunded INR 7,999 on A-1077
5 failure(s): 3 tries -> sent to a person

Sleeping inside a node blocks that run's thread. For long waits (minutes, not milliseconds), end the run and resume it later from its checkpoint, on a schedule or when the service is back (Lesson 14.103), rather than holding a worker.

Check your understanding

Explain the mechanismHow does LangGraph express branches and loops?

Worked answer. With conditional edges: after a node runs, a router function reads the state and returns the next node's name, and a node can also return Command(goto=...) to choose for itself. A loop is a conditional edge that can lead back to an earlier node; it needs its exit condition in the state, such as a retry counter, and the recursion limit stops a run that never reaches its exit. The tool-calling agent is the standard loop: model, then tools if there are tool calls, then back to the model.

A plausible wrong answer. "LangGraph graphs are DAGs." Cycles are the point; they are what make agents and retries possible.

Follow-ups. When would you use Command instead of a conditional edge?

Debug a failureA graph sometimes ends with GraphRecursionError in production. How do you find the cause?

Worked answer. Pull the trace or the checkpoint history of a failing run and look for the repeating nodes. Then check what their exit condition reads: a counter that is not updated, a status that a failing service never changes, or an agent that keeps calling a tool because its result does not answer the question. Fix the exit, add the give-up path to tests, and set the limit from real run lengths so the error stays an alarm, not a normal outcome.

A plausible wrong answer. "Increase the recursion limit." That hides the loop and multiplies its cost.

Follow-ups. How would you alert on runs that come close to the limit?

Defend a designcreate_agent, or your own graph with ToolNode and tools_condition?

Worked answer. create_agent by default: it is the same loop, and middleware covers approval, limits, summaries and retries. My own graph when the agent needs structure the middleware hooks cannot express: a validation node between tools and model, different models for different steps, or the agent as one branch of a larger workflow. Since both are LangGraph graphs, I can start with create_agent and replace it with a custom graph later without changing callers.

A plausible wrong answer. "Build the graph yourself so you understand it." Understanding it is the point of this lesson; in production, use the maintained version unless you need something it cannot do.

Follow-ups. Where would you put a check that a refund tool's result matches the order?
