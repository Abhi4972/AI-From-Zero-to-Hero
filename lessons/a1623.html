In plain words first
The idea in one line

The reference taxonomy for 2026 is MAST (Cemri et al., NeurIPS 2025, arXiv:2503.13657), derived from 1642 execution traces across 7 state-of-the-art open-source MAS showing 41–86.7% failure rate. Three root categories, with 14 failure modes: system design issues — role ambiguity, unclear task definitions (41.77% in an earlier version of the paper); inter-agent misalignment — communication breakdowns, state desync (36.94%); task verification — missing validation, absent quality checks (21.30%). The Groupthink family, as this lesson calls it, comes from Gradient Institute's risk-analysis report (arXiv:2508.05687), which names six failure modes for governed multi-agent systems: monoculture collapse (same base model → correlated failures), conformity bias (agents reinforce each other's errors), deficient theory of mind, mixed-motive dynamics, cascading reliability failures and inter-agent communication failures. Cascading example: retry storms where a payment failure triggers order retries, which trigger inventory retries, which overwhelm inventory service (10x load in seconds — needs circuit breakers). Memory poisoning: one agent's hallucination enters shared memory, downstream agents treat it as fact; accuracy decays gradually, making root-cause diagnosis painful. STRATUS (NeurIPS 2025), a multi-agent system for cloud reliability engineering, beats earlier SRE agents by at least 1.5x on mitigation success using specialized detection, diagnosis and mitigation agents. This lesson treats failure modes as first-class engineering targets.

Problem

In plain words first

Multi-agent systems fail often, and in recognisable ways. MAST is a taxonomy of those failures from 1,642 real traces: badly specified tasks and roles, agents that misread or ignore each other, and results nobody checks. Other failures come from agents being too alike (monoculture, conformity) and from errors that spread from one service to the next (cascades), which circuit breakers contain. Specs, contracts and failure modes for a single production agent are covered in Lesson 14.134 (linked above). This lesson measures the lesson's retry-storm simulator and breaker, and tries a small model as a MAST annotator.

Multi-agent systems fail 41-86.7% of the time on real tasks (Cemri et al. measured this across 7 open-source MAS, annotating 1,642 execution traces). That is not debuggable by "just add more agents." The failures have structural causes. The MAST taxonomy gives you the categories. This lesson maps each category to a concrete detection, diagnosis, and mitigation pattern so the numbers stop looking arbitrary.

The 2026 production practice is to treat failure modes as design inputs. Your architecture is not "good enough" until you can point to each MAST category and name the mitigation you deployed.

Concept

MAST categories

Specification Problems (system design issues in MAST; 41.77% of failures in an earlier version, about 44% when the latest version's per-mode rates are added up). The agent's task was not defined tightly enough. Examples:

  • Role ambiguity: two agents both think they are the reviewer.
  • Task underspecified: "summarize this" when the user wanted a specific angle.
  • Success criteria implicit: the agent cannot tell if it succeeded.

Mitigations: - Write explicit role contracts. Each agent's prompt states what it does and what it does not do. - Acceptance tests per task. Before the agent starts, define "done looks like X." - Pre-flight spec check: a separate agent reviews the task definition before dispatch.

Coordination Failures (inter-agent misalignment; 36.94% earlier, about 32% in the latest version). Communication or state breakdowns.

Examples: - Two agents update shared state without synchronization. - Message lost between agents (queue failure, timeout). - State drift: agent A thinks the task is done; agent B is still executing.

Mitigations: - Versioned shared state with optimistic concurrency. - Explicit acknowledgment for critical messages (retry until acked). - Periodic state-sync checkpoints; detect drift early.

Verification Gaps (task verification; 21.30% earlier, about 24% in the latest version). No independent check on outputs.

Examples: - One agent claims success; no one verifies. - Chain of agents each trusts the prior's output. - Test coverage missing on the emergent composed behavior.

Mitigations: - Independent verifier agent (Lesson 16.13). Read-only, independent source access. - Explicit handoff contract: "A's output must pass checker C before B starts." - Outcome logging for post-hoc analysis.

Groupthink family (Gradient Institute, arXiv:2508.05687)

Gradient Institute's report on risk analysis for governed multi-agent systems lists six salient failure modes; this lesson groups five of them as the groupthink family (the sixth is inter-agent communication failure, close to MAST's misalignment category):

Monoculture collapse. Same base model or training data → correlated errors. When three agents share an LLM, they share its hallucinations.

Conformity bias. Agents adjust toward the loudest or most-confident peer, even when wrong.

Deficient ToM. Agents fail to model each other's beliefs; coordination falls apart (Lesson 16.18).

Mixed-motive dynamics. Agents with partially-aligned incentives drift toward compromise-middle, which satisfies no one.

Cascading reliability failures. One component's error pattern triggers error patterns in dependent components.

Cascading example — the retry storm

A classic 2026 incident pattern:

payment service fails 10% of requests
   ↓
order agent retries payment (exponential backoff but naive)
   ↓
each retry is a new order-inventory check
   ↓
inventory service sees 2x normal load
   ↓
inventory service starts timing out
   ↓
every order retries inventory check
   ↓
inventory service sees 10x normal load
   ↓
cluster goes down

The fix is classical: circuit breakers. When downstream error rate exceeds threshold, short-circuit with cached or default results. Plus capped retry budgets per request.

Circuit breakers are one of the few multi-agent failure mitigations you borrow directly from distributed systems without modification.

Memory poisoning (revisited)

From Lesson 16.13: one agent's hallucination becomes shared-memory fact; downstream agents reason on the poisoned fact. In MAST terms, this is a verification gap at the shared-memory layer.

Gradual accuracy decay is the symptom. You do not get a crash; you get slow drift that is hard to root-cause.

Mitigation: append-only log, provenance, unwritable verifier. Already covered in Lesson 13.

STRATUS — specialized agents for incident response

STRATUS (NeurIPS 2025) is a multi-agent system for site reliability engineering of cloud services. On the AIOpsLab and ITBench benchmarks it beat earlier SRE agents by at least 1.5x on mitigation success, with separate agents for:

  • Detection agent. Watches for symptom patterns (high disagreement, retry spikes, accuracy drift).
  • Diagnosis agent. Given symptoms, infers likely root cause from the MAST taxonomy.
  • Mitigation agent. Applies a fix, under a safety rule the paper calls transactional no-regression: changes that make things worse can be rolled back. Checking that symptoms clear afterwards plays the validation role.

This is SRE-style incident response; the same roles transfer to agent systems. The three roles can all be LLM agents with specialized prompts.

The failure-mode audit

A 2026 best practice is a quarterly (and per-major-release) failure-mode audit:

  1. Trace sample. Collect ~1000 real execution traces.
  2. Categorize. For each trace's failures, map to MAST + Groupthink categories.
  3. Compute failure-by-category rate. Which categories dominate your system?
  4. Rank mitigations. Which fix would eliminate the most failures?
  5. Pick 2-3 mitigations. Implement; re-audit next quarter.

The discipline is more important than the specific choices. Without audits, failures blend into noise and never get systematically addressed.

When systems fail silently

The most dangerous failure category is silent correctness failure. A system that fails loudly (crash, exception, alert) can be monitored. A system that produces plausible-but-wrong outputs cannot be detected by exception logs. This is why verification gaps are the most expensive category per failure, even though they are only about a fifth to a quarter of failures by count.

Invest in: - Sample-based human review. - Golden-dataset regression tests. - Cross-agent cross-checking on important outputs.

Failure vs slow failure

Some failures are immediate; some are slow. Immediate failures (timeout, schema mismatch, auth error) are cheap to detect. Slow failures (memory poisoning, monoculture drift, role ambiguity) are expensive to detect and prevent.

The 2026 engineering move: instrument slow-failure proxies so you can catch drift before it becomes a visible error. Agreement rate, retry rate, output-length distribution, and edit-distance between consecutive agent versions are all useful proxies.

The same idea as a formula

Retry amplification. If each call fails independently with probability p and a request retries up to r times, the expected calls per request are

E[calls]=1+p+p2+⋯+pr=1−p1−pr+1​.
For p=0.1 and r=3 that is 1.11. Storms come from feedback: if load raises p, the sum grows toward r+1=4 calls per request, and every layer that retries multiplies it again.

Circuit breaker. Open when the error rate over the last w calls exceeds θ; after a cooldown T, let one probe through (half-open) and close on success. The cooldown must be measured on the same clock as the traffic.

Category shares. If a trace can show several failure modes, shares computed per mode need not add up to 100% of traces, and a "per-category share" depends on how modes are counted.

"""Failure modes: MAST categorizer, circuit breaker, retry-storm simulator.

Stdlib only. The simulator shows how a 10% downstream error rate amplifies
through retries to 10x load without a breaker; the breaker caps it.
"""
from __future__ import annotations

import random
import time
from dataclasses import dataclass, field
from enum import Enum


# ---------- MAST categorizer ----------

MAST_CATEGORIES = {
    "spec": "Specification Problem (41.77% of failures)",
    "coord": "Coordination Failure (36.94% of failures)",
    "verify": "Verification Gap (21.30% of failures)",
}

GROUPTHINK = {
    "monoculture": "monoculture collapse (same base model → correlated errors)",
    "conformity": "conformity bias (agents align with loudest peer)",
    "tom": "deficient theory of mind (cannot model each other)",
    "mixed_motive": "mixed-motive drift (compromise-middle satisfies no one)",
    "cascade": "cascading reliability failures (retry storms)",
}


def categorize_incident(symptoms: dict) -> tuple[str, str]:
    if symptoms.get("role_conflict") or symptoms.get("task_ambiguity"):
        return "spec", MAST_CATEGORIES["spec"]
    if symptoms.get("state_drift") or symptoms.get("message_lost") or symptoms.get("sync_error"):
        return "coord", MAST_CATEGORIES["coord"]
    if symptoms.get("no_verifier") or symptoms.get("hallucination_propagation"):
        return "verify", MAST_CATEGORIES["verify"]
    return "unknown", "no MAST category matched"


def detect_groupthink(symptoms: dict) -> list[tuple[str, str]]:
    hits = []
    if symptoms.get("correlated_errors"):
        hits.append(("monoculture", GROUPTHINK["monoculture"]))
    if symptoms.get("agreement_rate_spike"):
        hits.append(("conformity", GROUPTHINK["conformity"]))
    if symptoms.get("coordination_drop_long_horizon"):
        hits.append(("tom", GROUPTHINK["tom"]))
    if symptoms.get("compromise_outputs"):
        hits.append(("mixed_motive", GROUPTHINK["mixed_motive"]))
    if symptoms.get("retry_amplification"):
        hits.append(("cascade", GROUPTHINK["cascade"]))
    return hits


# ---------- Circuit breaker ----------

class BreakerState(Enum):
    CLOSED = "closed"
    OPEN = "open"
    HALF_OPEN = "half_open"

Part 2 of 4 · CircuitBreaker, DownstreamService, simulate_retry_storm

@dataclass
class CircuitBreaker:
    failure_threshold: float = 0.5
    window_size: int = 20
    open_cooldown_s: float = 0.5
    state: BreakerState = BreakerState.CLOSED
    outcomes: list[bool] = field(default_factory=list)
    opened_at: float = 0.0

    def _error_rate(self) -> float:
        if not self.outcomes:
            return 0.0
        recent = self.outcomes[-self.window_size:]
        return 1.0 - (sum(recent) / len(recent))

    def allow(self) -> bool:
        if self.state == BreakerState.OPEN:
            if time.monotonic() - self.opened_at >= self.open_cooldown_s:
                self.state = BreakerState.HALF_OPEN
            else:
                return False
        return True

    def record(self, success: bool) -> None:
        self.outcomes.append(success)
        if self.state == BreakerState.HALF_OPEN:
            if success:
                self.state = BreakerState.CLOSED
            else:
                self.state = BreakerState.OPEN
                self.opened_at = time.monotonic()
        elif self.state == BreakerState.CLOSED:
            if self._error_rate() > self.failure_threshold and len(self.outcomes) >= self.window_size:
                self.state = BreakerState.OPEN
                self.opened_at = time.monotonic()


# ---------- Retry storm simulator ----------

@dataclass
class DownstreamService:
    base_failure_rate: float = 0.1
    load: int = 0

    def handle(self, rng: random.Random) -> bool:
        # Increased load -> increased failure (degradation model)
        effective_rate = self.base_failure_rate + (self.load * 0.02)
        effective_rate = min(effective_rate, 0.99)
        return rng.random() > effective_rate


def simulate_retry_storm(requests: int, use_breaker: bool, seed: int = 0) -> tuple[int, int, int]:
    rng = random.Random(seed)
    service = DownstreamService()
    breaker = CircuitBreaker()
    total_calls = 0
    successes = 0
    short_circuits = 0

    for _ in range(requests):
        attempts_for_req = 0
        while attempts_for_req < 4:
            if use_breaker and not breaker.allow():
                short_circuits += 1
                break
            service.load = min(total_calls // 10, 50)
            total_calls += 1
            ok = service.handle(rng)
            if use_breaker:
                breaker.record(ok)
            if ok:
                successes += 1
                break
            attempts_for_req += 1
    return total_calls, successes, short_circuits

Industry practice
What's current (2024–2026)
  • MAST as a working taxonomy. MAST and its annotated dataset (1,642 traces) are public, with an LLM-judge pipeline for labelling new traces; teams use it to sort their own failures.
  • Risk analysis for governed agent systems. Gradient Institute's report gives organisations methods to probe the six failure modes, from staged testing to red-teaming.
  • Agents for operations. STRATUS and similar SRE agents detect, diagnose and mitigate cloud incidents, with rollback as a safety rule.
  • On your laptop: circuit breakers, retry budgets and per-category failure counts are a few lines of code; use a small model only to draft labels for a human to confirm.

Recap
What to keep from this lesson
  • MAST sorts failures into system design, inter-agent misalignment and task verification, across 14 modes.
  • Retries multiply load at every layer; cap them with budgets and contain them with circuit breakers.
  • Run breakers and cooldowns on the same clock as the traffic, and test them under simulated time.
  • A failure can have several causes; label all of them, not the first rule that matches.
  • Small models are poor failure annotators; use them to draft, and check the labels.

Ship it

Failure-mode discipline in production:

  • MAST audit per quarter. Not annual. Categories shift as your system grows.
  • Circuit breakers everywhere. Each outbound call to any dependent service. Default open threshold at 5-10% error rate.
  • Golden datasets. Small, high-quality, hand-audited. Regression-test against them weekly.
  • STRATUS-style trio. Detection, diagnosis and mitigation agents monitoring production, with a check that symptoms clear after each fix and a way to roll it back. Start with the detection agent only; add diagnosis when symptoms are noisy.
  • Failure budget. Explicit SLO for failure rate by category. Exceeding budget triggers a stop-shipping conversation.

Given a multi-agent system and sampled execution traces, run a failure-mode audit.

Produce:

1. **Sample construction.** At least 200 traces from production, sampled uniformly across task types and time windows. Document sampling method and bias risks.
2. **Classification pass.** For each trace, mark `success | failure`. For failures, assign one MAST category (spec / coord / verify) and, when applicable, one or more Groupthink family tags (monoculture / conformity / tom / mixed-motive / cascade).
3. **Distribution table.** Counts and percentages by MAST category and Groupthink tag. Compare to Cemri 2025's reference distribution (41.77 / 36.94 / 21.30). Systems that skew heavily from the reference often have a specific weak layer.
4. **Top failure patterns.** Identify the 3 most-frequent specific patterns (e.g., "two agents both review"). Document reproduction steps.
5. **Mitigation ranking.** For each top pattern, propose a mitigation from the standard library: explicit role contracts, versioned shared state, independent verifier, circuit breaker, detection-diagnosis-validation (STRATUS) trio. Rank by expected failure reduction given the pattern's frequency.
6. **Risk of silent failures.** How many failures produce plausible-but-wrong outputs vs loud errors? Silent rate drives the verification-layer investment.
7. **Slow-failure proxies.** Recommend 2-3 live metrics that would surface drift before it becomes a loud error: agreement rate, retry-rate, output-length distribution, inter-agent edit distance.

Hard rejects:

- Audits without a random or stratified sample. Hand-picked failures over-represent dramatic cases and miss slow-failure drift.
- Mitigation recommendations without a baseline measurement. "Add a verifier" means nothing unless the current failure rate is known.
- Ignoring MAST-unknown incidents. If a trace does not fit a category, the taxonomy is incomplete; propose an extension rather than forcing a category.
- Claiming a quarterly audit is sufficient without operational slow-failure monitoring. Quarterly misses drift between audits.

Refusal rules:

- If traces lack per-agent attribution (who wrote what, who read what), the audit cannot distinguish coordination failures from role conflicts. Recommend adding structured per-agent logging before re-auditing.
- If the system has fewer than 50 failed traces total, the sample is too small to produce distribution estimates. Recommend longer observation window.
- If traces contain PII, mask before analysis.

Output: a three-page report. Start with a one-sentence summary ("41% spec failures, 12% coordination, 39% verification gaps, 8% unknown; top pattern is dual-reviewer conflict; highest-ROI mitigation is explicit role contracts."), then the seven sections above. End with a prioritized action list: three mitigations with estimated implementation cost and expected failure-rate reduction.

Solutions

SolutionP1 · About 1.6

About 1.6. The run made 328 calls for 200 requests, 1.64 per request. With independent failures at 10%, the expected count would be about 1.11; the extra comes from the simulated service's failure rate rising with every call. It never reaches 4, the cap, because most requests still succeed early.

SolutionB1 · A retry cascade, not a hallucination

What really happened. A cascading reliability failure. Every layer retried on its own: 5 refund attempts, each re-checked 3 times by billing, plus tickets re-opened by intake, so one failed refund could become dozens of calls. The billing database took the multiplied load, and it was shared with login, so the outage spread to customers who never touched refunds. No model output was wrong; this is a coordination and system-design failure.

What to change: - Retry budgets per request across all layers, with backoff and jitter, and only one layer allowed to retry a given call. - Circuit breakers on the payment provider and on billing, failing fast with a "refund pending" status. - Isolate shared resources: separate connection pools or databases for login and billing. - Fix the post-mortem: label causes with a taxonomy such as MAST plus cascade analysis, so the action items target retries and coupling, not the model.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designA multi-agent product has been in production for two quarters. Failures arrive as a stream of unrelated tickets and nothing gets fixed systematically. Design the audit that turns the stream into a ranked list of fixes, and say which failure class you would weight most heavily even if it is not the most frequent.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Sample about 1000 real execution traces each quarter, categorize every failure into the three root categories of the published taxonomy and the five groupthink patterns, compute the failure rate per category, rank the mitigations by how many failures each would remove, and commit to two or three for the quarter. Weight verification gaps most heavily even though they were the smallest category by count, because they are silent: a plausible wrong output produces no exception, no alert and no ticket until a human notices.

The baseline you are measured against.

The reference taxonomy was built from 1642 execution traces across 7 open-source multi-agent systems and found failure rates between 41 percent and 86.7 percent. Three root categories:

Category Share What it looks like
Specification problems 41.77 percent in an earlier version (about 44 percent in the latest) Role ambiguity, an underspecified task, implicit success criteria
Coordination failures 36.94 percent earlier (about 32 percent) Unsynchronized writes to shared state, lost messages, state drift
Verification gaps 21.30 percent earlier (about 24 percent) One agent claims success and nobody checks, each agent trusts the one before

Beside them sit the five groupthink patterns: monoculture, conformity, a missing model of each other's beliefs, compromise drift and cascading failures.

The audit, step by step.

  1. Sample. Pull about 1000 real traces, stratified by task type, not the ones that produced tickets.
  2. Categorize. Map each failure to a root category and any groupthink pattern. Two reviewers per trace until the categories are stable.
  3. Compute. Failure rate per category for your system. The published shares are a prior, not your number.
  4. Rank. For each candidate mitigation, count the failures it would have removed.
  5. Commit. Two or three mitigations for the quarter, each with an owner and a re-audit date.

The discipline matters more than the choices. Without the audit, failures blend into noise.

The mitigation menu.

  • Specification: explicit role contracts that say what an agent does and does not do, acceptance tests written before dispatch, a pre-flight check of the task definition.
  • Coordination: versioned shared state with optimistic concurrency, acknowledgments for critical messages, periodic state-sync checkpoints.
  • Verification: an independent read-only verifier with its own source access, handoff contracts that require a check before the next agent starts, outcome logging.
  • Cascades: circuit breakers on every outbound call with a default open threshold at 5 to 10 percent error rate, and capped retry budgets.

Why verification gaps weigh more.

A loud failure, a crash or a timeout, is cheap to detect. A silent correctness failure cannot be found in exception logs. That is why verification gaps are the most expensive category per failure. Invest in sample-based human review, a small hand-audited golden dataset run weekly, and cross-checks between agents on important outputs.

Catch slow failures before the audit.

Instrument proxies for drift: the agreement rate across parallel agents, the retry rate, the distribution of output lengths, and the edit distance between successive agent versions. The lesson also describes a trio of specialized agents, detection, diagnosis and validation, that improved mitigation success by 1.5 times; start with detection only and add diagnosis when the symptoms are noisy.

Make it binding.

Set a failure budget per category, an explicit objective for the rate. When a category exceeds its budget, the next release waits.

Plausible wrong answers.

  • "Fix the most frequent category first." Frequency is not cost, and the silent verification gaps cost more per failure than the loud specification problems.
  • "Audit once a year, when the system is stable." Categories shift as the system grows, and a year of unranked failures is the stream you started with.
  • "Add more agents to check each other." Agents that share a model share their blind spots, and the check that matters is an independent verifier with its own source access.

Follow-ups an interviewer may ask.

  • (level 3) Why sample traces instead of auditing tickets? Expected: tickets are the loud failures, and the silent ones never produce a ticket, so a stratified sample is the only way to see them.
  • (level 3) Which single proxy would you instrument first? Expected: agreement rate across parallel agents, because a sharp rise signals conformity and a sharp fall signals drift, and both precede visible errors.
  • (level 4) The audit finds that specification problems dominate. What is the cheapest fix? Expected: a pre-flight check of the task definition by a separate agent before dispatch, with role contracts that include what each agent does not do.
  • (level 4) How do you keep the audit from becoming a report nobody acts on? Expected: the failure budget with a stop-shipping rule, owners per mitigation, and the re-audit date on the calendar before the quarter starts.

Debug a failureA payment service starts failing about 10 percent of its requests. Within minutes the inventory service, which never failed, is down, and the order agents that call both are stalled. The payment service itself recovered on its own. Explain the chain, name the failure family, and say what you add so that it cannot repeat.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. This is a retry storm, a cascading reliability failure. The order agent retried each failed payment, each retry ran a fresh inventory check, inventory saw twice its normal load and began to time out, every order then retried the inventory check as well, and inventory saw ten times its load and fell over. The fix is classical: a circuit breaker on every outbound call that opens when the downstream error rate passes a threshold and serves a cached or default result, plus a capped retry budget per request.

The chain.

payment fails about 10 percent of requests
  -> the order agent retries payment, with backoff but no cap
  -> each retry runs a new order-inventory check
  -> inventory sees about twice its normal load
  -> inventory starts to time out
  -> every order retries the inventory check
  -> inventory sees about ten times its normal load
  -> the cluster goes down

Nothing in the chain is a model error. It is a coordination failure between components whose retry logic was written one component at a time.

The family.

The lesson's taxonomy puts this under cascading reliability failures, one of the five patterns where agents amplify each other's errors. It sits beside monoculture, conformity, a missing model of each other's beliefs, and compromise drift. Of all the mitigations in the taxonomy, the circuit breaker is one of the few you take from distributed systems without changing it.

The breaker.

State Behavior
Closed Calls pass, and the breaker records each outcome over a window
Open Calls are refused and a cached or default result is served, until a cooldown passes
Half-open One probe call passes; a success closes the breaker and a failure reopens it

The lesson's shipping default is to open at an error rate of 5 to 10 percent. In the lesson's simulation the breaker caps the amplification: the success count may fall, and the downstream survives.

The retry budget.

A breaker protects the callee. A retry budget per request protects the system from the caller: a fixed number of attempts, after which the request fails and the failure is recorded. Retries without a cap are the storm.

Detect it earlier.

Retry rate is one of the slow-failure proxies the lesson lists, with agreement rate, output-length distribution and the edit distance between agent versions. A detection agent that watches for a retry spike names the pattern before inventory falls over.

Plausible wrong answers.

  • "Add exponential backoff to the payment retries." Backoff slows the storm and does not cap it, and the inventory check still runs on every retry.
  • "Scale the inventory service to absorb the peak." The peak is ten times normal and made of wasted retries, and scaling pays for the storm instead of stopping it.
  • "This is a model problem, so improve the agent's prompt." No model decision is in the chain, and a prompt cannot see the error rate of a downstream service.

Follow-ups an interviewer may ask.

  • (level 3) Why does the inventory service fail when payment is the one with errors? Expected: the order agent's retry loop re-runs the inventory check on every payment retry, so inventory's load tracks payment's failures.
  • (level 3) What does the breaker serve while it is open? Expected: a cached or default result that the order agent can act on in a degraded mode, so the user gets a slower answer instead of none.
  • (level 4) Where does the breaker threshold belong, and who owns it? Expected: in the caller's configuration per downstream service, owned by the team that runs the caller, and reviewed when the dependency's normal error rate changes.
  • (level 4) How do you test the fix without a production incident? Expected: a simulator that injects a 10 percent failure rate downstream and measures total calls with and without the breaker, as the lesson does.
