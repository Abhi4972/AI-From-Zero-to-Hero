Context Caching and Prompt Caching

In plain words first
The idea in one line

Your system prompt is 4,000 tokens. Your RAG context is 20,000 tokens. You send both with every request. You also pay for both — every time. Prompt caching lets the provider keep that prefix warm on their side and bill you 5-10% of the normal rate on reuse (Claude and GPT-6.2 models, November 2026). Used correctly, it cuts inference cost by 50–90% and first-token latency by 40–85%.

Terms you'll hear
Term What people say What it actually means
Prompt caching "Makes long prompts cheap" Reusing a provider-side KV-cache for matching prefixes; repeated input tokens billed at 5-10% of the normal price on current Anthropic and OpenAI models.
cache_control "The Anthropic marker" Content-block attribute that declares "everything up to here is cacheable"; {"type": "ephemeral"}.
Cache write "Paying the premium" The first request that populates the cache; billed at ~1.25x input rate on Anthropic, free on OpenAI.
Cache read "The discount" Subsequent requests matching the prefix; billed at 5% (Anthropic Opus and Sonnet 5.5, OpenAI GPT-6.2) or 10% (Haiku 5.5) of the input price; Gemini discounted, see pricing.
TTL "How long it lives" Seconds the cache stays warm; Anthropic 5m default (extendable 1h), OpenAI best-effort up to 1h, Gemini user-set.
Extended TTL "1-hour Anthropic cache" {"type": "ephemeral", "ttl": "1h"}; 2x write premium but worth it for batch reuse.
Prefix match "Why my cache missed" Caches only hit when every token from the start up to the breakpoint is byte-identical.
Context caching (Gemini) "The explicit one" Google's named, storage-billed cache object; best for multi-day reuse of large corpora.

The problem

In plain words first

Before a model writes its first word it processes the whole prompt (prefill) and keeps the result, the key-value (KV) cache, in memory. If the next request starts with exactly the same text (the same system prompt, tools and examples), that work can be reused instead of repeated. Providers sell this as prompt caching: the repeated part is billed at a small fraction of the normal price and the answer starts sooner. The catch is that only an identical prefix counts: one changed token near the top and everything after it is recomputed. This lesson covers the three providers' versions, the break-even arithmetic with November 2026 prices, and then does prefix caching by hand on a real 0.5B model: it times the first token with and without a cached prefix, checks the outputs match, and shows how a timestamp at the top destroys the cache. No model is trained.

A coding agent sends the same 15,000-token system prompt to Claude on every turn of a conversation. Twenty turns at $2/M input tokens (Claude Sonnet 5.5) is $0.60 in input cost alone — before any of the user's actual messages. Multiply by 10,000 daily conversations and the bill hits $6,000/day for text that never changes.

You cannot shrink the prompt without hurting quality. You cannot avoid sending it — the model needs it on every turn. The only move is to stop paying full price for a prefix the provider has already seen.

That move is prompt caching. Anthropic shipped it in August 2024 (with a 1-hour extended-TTL variant in 2025), OpenAI automated it later that year, Google shipped explicit context caching alongside Gemini 1.5, and all three now offer it as a first-class feature on their frontier models.

The idea

The mechanic. When a request's prefix matches one from a recent request, the provider serves the KV-cache from the previous run instead of re-encoding the tokens. You pay a small write premium the first time and a large read discount every time after.

Three provider flavors in 2026.

Provider (Nov 2026) API style Price of a cache hit Write premium Default TTL Min cacheable
Anthropic Explicit cache_control markers on content blocks 5% of input (Opus 5.5, Sonnet 5.5), 10% (Haiku 5.5) 25% (5-minute cache), 100% (1-hour cache) 5 min, refreshed on each hit (1 hour optional) model-specific, see docs
OpenAI Automatic prefix detection 5% of input on GPT-6.2 Sol and Astra none best effort model-specific, see docs
Google (Gemini) Implicit caching, plus an explicit CachedContent API discounted cached tokens; explicit caches add a storage fee storage per token-hour (explicit) user-set for explicit caches model-specific, see docs

Discounts have grown with each model generation (OpenAI's went from 50% on GPT-4o-era models to 95% now), so read the pricing page of the model you use.

The invariant. All three cache prefixes only. If any token differs between requests, everything after the first differing token is a miss. Put the stable parts at the top, the variable parts at the bottom.

Idea 1 · The cache-friendly layout

[system prompt]          <-- cache this
[tool definitions]       <-- cache this
[few-shot examples]      <-- cache this
[retrieved documents]    <-- cache if reused, else don't
[conversation history]   <-- cache up to last turn
[current user message]   <-- never cache (different every time)

Violate the order — put the user message above the system prompt, interleave dynamic retrievals between few-shots — and the cache never hits.

Idea 2 · The break-even calculation

Anthropic's 25% write premium (5-minute TTL) pays for itself on the first read, because a cache read costs 0.05x on Opus 5.5 and Sonnet 5.5. 1 write + 1 read averages 0.65x cost per request (saves 35%); 1 write + 10 reads averages 0.16x (saves 84%). The 1-hour TTL charges 2x for the write, so that block needs two reads to come out ahead. Rule of thumb: cache anything you expect to reuse at least 3 times within the TTL; that clears break-even on either TTL.

The same idea as a formula

Average input cost per request for a cached prefix of P tokens reused k times after one write, relative to sending it uncached every time (k+1 requests):

cˉ(k)=k+1w+kr​,saving=1−cˉ(k),
with write multiplier w (1.25 for 5 minutes, 2 for 1 hour on Anthropic, 1 on OpenAI) and read multiplier r (0.05 on Sonnet 5.5 and GPT-6.2 Sol).

Break-even: caching wins once w+kr<k+1, that is k>1−rw−1​: k>0.26 (one read) for w=1.25, k>1.05 (two reads) for w=2.

Why the first token comes sooner: prefill work grows with the number of uncached tokens n (linearly for the projections, quadratically for attention), so a hit that leaves nnew​≪n tokens to process cuts the time to first token by roughly n/nnew​ until the per-request overhead dominates.

Worked example
A 15,000-token rubric, 20 turns, Sonnet 5.5
  • Uncached: 20×15,000=300,000 tokens at $2 per million: $0.60 per conversation.
  • Cached (5-minute TTL, refreshed by each turn): one write at 1.25x and 19 reads at 0.05x: $15{,}000 \times (1.25 + 19 \times 0.05) \times 2 \times 10^{-6} = \$0.066$, 89% less.
  • 10,000 conversations a day: from $6,000 to $660 a day for the same rubric.
  • With a timestamp above the rubric every turn is a write at 1.25x: $0.75 per conversation, more than not caching at all.
Check your mental model
  • ✗ "Prompt caching reuses old answers."
    ✓ It reuses the processed prompt (the KV cache); every answer is generated fresh, and identical to an uncached run.
  • ✗ "A similar system prompt hits the cache."
    ✓ Only an identical token prefix does; the first differing token ends the reusable part.
  • ✗ "Caching only matters for cost."
    ✓ It also cuts the time to first token, often by most of the prefill time (measured below).
Predict before you run

Two requests share a long rubric and differ only in the user's code. Recomputing everything versus reusing the cached rubric: how much faster is the first token, and will the next-token prediction be the same? (Solution P1.)

Step 1 · Anthropic prompt caching with explicit markers

import anthropic

client = anthropic.Anthropic()

SYSTEM = [
    {
        "type": "text",
        "text": "You are a senior Python reviewer. Follow the rubric exactly.\n\n" + RUBRIC_15K_TOKENS,
        "cache_control": {"type": "ephemeral"},
    }
]

def review(code: str):
    return client.messages.create(
        model="claude-opus-5-5",
        max_tokens=1024,
        system=SYSTEM,
        messages=[{"role": "user", "content": code}],
    )

The cache_control marker tells Anthropic to store the block for 5 minutes. Reuse within that window hits; reuse after expires and writes again.

Response usage fields:

response = review(code_a)
response.usage
# InputTokensUsage(
#     input_tokens=120,
#     cache_creation_input_tokens=15023,   # paid at 1.25x
#     cache_read_input_tokens=0,
#     output_tokens=340,
# )

response_b = review(code_b)
response_b.usage
# cache_creation_input_tokens=0
# cache_read_input_tokens=15023           # paid at 0.05x on Opus 5.5

Check both fields in CI — if cache_read_input_tokens stays at zero across requests, your cache keys are drifting.

Step 2 · one-hour extended TTL

For long-running batch jobs, the 5-minute default expires between jobs. Set ttl:

{"type": "text", "text": RUBRIC, "cache_control": {"type": "ephemeral", "ttl": "1h"}}

A 1-hour cache write costs 2x the base input price (instead of 1.25x for 5 minutes), so it comes out ahead after two reads and pays back fast on any batch reusing the prefix many times.

Step 3 · OpenAI automatic caching

OpenAI gives you nothing to configure. A long enough prefix that matches a recent request is billed at the cached-input price automatically (5% of the input price on GPT-6.2 Sol).

from openai import OpenAI
client = OpenAI()

resp = client.chat.completions.create(
    model="gpt-6.2-sol",
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},   # long and stable
        {"role": "user", "content": user_msg},
    ],
)
resp.usage.prompt_tokens_details.cached_tokens  # the discounted portion

Same cache-friendly layout rule applies. Two things kill OpenAI's cache that don't kill Anthropic's: changing the user field (used as a cache key component) and reordering tools.

Step 4 · Gemini explicit context caching

Gemini treats the cache as a first-class object you create and name:

from google import genai
from google.genai import types

client = genai.Client()

cache = client.caches.create(
    model="gemini-3.8-flash",
    config=types.CreateCachedContentConfig(
        display_name="rubric-v3",
        system_instruction=RUBRIC,
        contents=[FEW_SHOT_EXAMPLES],
        ttl="3600s",
    ),
)

resp = client.models.generate_content(
    model="gemini-3.8-flash",
    contents=["Review this code:\n" + code],
    config=types.GenerateContentConfig(cached_content=cache.name),
)

Gemini charges storage per token-hour for as long as an explicit cache lives, and bills cached reads at a discounted rate (see its pricing page). This is the right shape when you reuse the same giant prompt across many sessions over days.

Step 5 · measuring hit rate in production

See code/main.py for a simulated three-provider accountant that tracks write/read/miss counts and computes blended cost per 1K requests. Gate deploys on a target hit rate — most production Anthropic setups should see >80% read fraction after warmup.

See it drawn
Prefix caching by hand on a real model

Qwen2.5-0.5B-Instruct with a 60-rule review rubric as the system prompt. The run times the first token of a second request three ways: recomputing the whole prompt, reusing the KV cache of the shared prefix (what a provider's prompt cache does), and with a timestamp added above the rubric. It also checks that cached and uncached runs predict the same next token. Timings change from run to run, so the output below was recorded (about a minute on CPU).

import copy, time, torch
from transformers import AutoTokenizer, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

# a long, stable system prompt (a review rubric) and short, changing user messages
rules = [f"Rule {i}: check that every function named in section {i} has a docstring, type hints, "
         f"and a unit test covering its error path; report violations with file and line." for i in range(1, 61)]
SYSTEM = "You are a senior Python reviewer. Follow the rubric exactly.\n" + "\n".join(rules)
def prompt(system, user):
    return tok.apply_chat_template([{"role": "system", "content": system}, {"role": "user", "content": user}],
                                   tokenize=False, add_generation_prompt=True)
users = ["Review: def add(a, b): return a + b", "Review: def div(a, b): return a / b"]
full = [tok(prompt(SYSTEM, u), return_tensors="pt").input_ids for u in users]
prefix_len = next(i for i in range(min(f.shape[1] for f in full)) if full[0][0, i] != full[1][0, i])
print(f"prompt {full[0].shape[1]} tokens; the two requests share their first {prefix_len} tokens")

def first_token_time(ids, cache=None, start=0):
    t = time.time()
    with torch.no_grad():
        out = model(ids[:, start:], past_key_values=cache, use_cache=True, logits_to_keep=1)   # keep only the last position's logits
    return time.time() - t, out

# warm-up, then: no cache, and a cache holding the shared prefix (what a provider keeps for you)
first_token_time(full[0])
t_cold, _ = first_token_time(full[1])
_, pre = first_token_time(full[0][:, :prefix_len])
t_warm, out = first_token_time(full[1], cache=copy.deepcopy(pre.past_key_values), start=prefix_len)
_, ref = first_token_time(full[1])
same = torch.allclose(out.logits[0, -1], ref.logits[0, -1], atol=1e-3)
print(f"time to first token without a cache: {t_cold:.2f} s (prefill of {full[1].shape[1]} tokens)")
print(f"with the shared prefix cached:      {t_warm:.2f} s (prefill of {full[1].shape[1] - prefix_len} tokens), "
      f"{t_cold / t_warm:.0f}x faster; next-token logits identical: {same}")

# the same request with a timestamp at the very top: the shared prefix collapses
stamped = [tok(prompt(f"Current time: 2026-11-25 10:3{i}:0{i}\n" + SYSTEM, u), return_tensors="pt").input_ids
           for i, u in enumerate(users)]
p2 = next(i for i in range(min(s.shape[1] for s in stamped)) if stamped[0][0, i] != stamped[1][0, i])
print(f"\nwith a timestamp above the rubric the requests share only {p2} tokens: "
      f"{full[1].shape[1] - p2} tokens must be recomputed every time")
kv = 2 * model.config.num_hidden_layers * model.config.num_key_value_heads * (model.config.hidden_size // model.config.num_attention_heads) * 2
print(f"cache size for the shared prefix (bf16): {prefix_len * kv / 1e6:.1f} MB")

Recorded output

prompt 2360 tokens; the two requests share their first 2346 tokens
time to first token without a cache: 16.76 s (prefill of 2360 tokens)
with the shared prefix cached:      0.29 s (prefill of 14 tokens), 57x faster; next-token logits identical: True

with a timestamp above the rubric the requests share only 22 tokens: 2338 tokens must be recomputed every time
cache size for the shared prefix (bf16): 28.8 MB
Reading this output

Almost the whole prompt is shared. The two requests are 2,360 tokens long and identical for the first 2,346: the system prompt with its 60-rule rubric, plus the chat template's opening tokens. Only the 14 tokens of the user's code differ. This is the typical shape of agent and assistant traffic, and the reason prompt caching pays.

Reusing the prefix makes the first token 57 times faster. Recomputing everything took 16.76 s on this CPU. With the KV cache of the shared prefix kept from the first request, only 14 new tokens had to be processed: 0.29 s. Providers' GPUs are far faster in absolute terms, but the ratio is the same idea. Prefill work is skipped, so time to first token falls with the cached share of the prompt.

The answer does not change. The next-token logits with the cached prefix match the full recomputation (allclose is True). Caching reuses arithmetic that would have produced the same numbers; it is not an approximation and not a reused answer.

One timestamp destroys it. With "Current time: …" above the rubric, the two requests share only 22 tokens, up to the minute digit where the timestamps differ. Every one of the remaining 2,338 tokens must be recomputed, and on a provider you would pay the cache-write price for them each time.

The cache is not free to keep. 28.8 MB of keys and values for 2,346 tokens of a 0.5B model (bf16), about 12 KB per token. A 70B model with grouped-query attention needs about 320 KB per token, over 300 MB for a thousand-token prefix. That is why providers keep caches for minutes, not forever, and charge for writing them.

Pitfalls that still ship in 2026

  • Dynamic timestamps at the top. "Current time: 2026-04-22 15:30:02" at the top of the system prompt. Every request misses. Move timestamps below the cache breakpoint.
  • Tool reordering. Serialize tools in a stable order — a dict reshuffle between deploys breaks every hit.
  • Free-text near-duplicates. "You are helpful." vs "You are a helpful assistant." — one byte difference = full miss.
  • Too-small blocks. Every provider has a minimum cacheable length (it differs by model). Smaller blocks silently do not cache; check the usage fields.
  • Blind cost dashboards. Split "input tokens" into cached vs uncached. Otherwise a traffic drop looks like a cache win.

The 2026 caching stack:

Situation Pick
Agent with stable 10k+ system prompt, many turns Anthropic cache_control with 5-min TTL
Batch job reusing a prefix for 30+ minutes Anthropic with ttl: "1h"
Serverless endpoints on GPT-6.2, no custom infra OpenAI automatic (just make your prefix stable and long)

Industry practice
What's current (2024–2026)
  • Deep cache discounts: cached input at 5% of the input price on Claude Opus and Sonnet 5.5 and GPT-6.2, 10% on Haiku 5.5; Anthropic's 1-hour cache for batch and agent workloads.
  • Caching in open serving engines: vLLM's automatic prefix caching and SGLang's RadixAttention reuse KV blocks across requests that share prefixes, the self-hosted version of this lesson.
  • Agents designed around the cache: harnesses keep the system prompt, tools and earlier turns byte-identical and append only at the end; compaction (Lesson 11.14) is the moment the cache is rebuilt.
  • Cost dashboards split by cached, written and uncached tokens to see whether a cost change is traffic or cache behaviour.

Sources: Claude pricing, Claude prompt caching, OpenAI pricing, Gemini context caching, vLLM automatic prefix caching, SGLang, Zheng et al. 2024.

Recap
What to keep from this lesson
  • Providers reuse the KV cache of an identical prompt prefix: cheaper and faster.
  • Stable content first (system, tools, examples), changing content last.
  • Reads cost 5-10% of input; writes 1.25x (5 min) or 2x (1 h) on Anthropic.
  • Break-even is one read for 5-minute caches, two for 1-hour caches.
  • Watch cached-token fields; one timestamp or reordering at the top kills every hit.

Solutions

SolutionP1 · Much faster, and the same prediction

In this run the first token came 57 times faster: 0.29 s instead of 16.76 s, because only the 14 tokens after the shared 2,346-token prefix had to be processed. The next-token prediction was identical (the logits match the full recomputation). Caching changes how much work is redone, not what the model computes.

SolutionB1 · Every deploy, every request misses

Every deploy that reorders the tool list changes the prompt near its top. The cached prefix ends at the first changed token, so after each deploy every request misses until new cache entries are written, and the cost of the first request per prefix rises by the write premium. Worse, if the order changes per process or per request (a Python set of tool names, a dict built from an unordered source), different replicas send different prefixes, so the hit rate stays low all the time, not just after deploys. Serialise tools, examples and system text deterministically: sort tools by name, use a fixed JSON key order, and never put request-specific values above the cache breakpoint. Then alert on the cached-token share in the usage fields, so a regression shows up in a dashboard instead of in the bill.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Estimate itYour provider charges a 25 percent premium to write a prefix into its cache, and it bills a cache read at a tenth of the normal input price. The cache lives for five minutes. A one-hour variant costs twice the normal input price to write. How many reads does each variant need to pay off, and what rule do you give the team?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. With the five-minute cache, one write and one read average 0.675 of the normal cost per request, a saving of about 32 percent, so the cache pays off on the first read. One write and ten reads average 0.205, about 80 percent saved. The one-hour cache charges 2x for the write, so that block needs two reads before it comes out ahead. The rule: cache anything you expect to reuse at least three times inside its lifetime.

The arithmetic.

A write costs 1.25 times the normal input price, and a read costs 0.1 times it.

  • One write and one read: the two requests average 0.675 of the normal price. That is 32 percent saved on the first read already.
  • One write and ten reads: the requests average 0.205 of the normal price, about 80 percent saved.
  • The one-hour cache writes at 2 times the normal price. With one read the average sits above the normal price, and with two reads it falls below. The lesson says the one-hour block pays back fast on any batch that reuses the prefix more than five times.

Three reuses inside the lifetime clear the break-even on either variant, which is the rule the lesson gives.

What breaks the arithmetic.

  • A prefix that differs by one token on every request, because of a timestamp, a request id or a reshuffled tool list. Every request writes and none reads.
  • A block below the minimum cacheable size, which is 1,024 tokens on the provider in the lesson. A smaller block silently does not cache.
  • Requests that arrive in parallel before the first write has landed. Each one pays the write premium, and none reads.

Verify it.

Read the usage fields on every response: the tokens written to the cache and the tokens read from it. In CI, assert that the second identical request reads more than zero. On the dashboard, split input tokens into cached and uncached, or a traffic drop will look like a cache win.

Plausible wrong answers.

  • "Caching always saves money." A prefix written once and never read costs 25 percent more than no cache.
  • "Pick the one-hour cache, it lasts longer." It writes at twice the normal input price, so a block read once costs more than without the cache.
  • "Mark the whole prompt as cacheable." The user message changes every time, so the match ends at the first differing token, and a block below the minimum size does not cache at all.

Follow-ups an interviewer may ask.

  • (level 2) Why does the five-minute cache pay off on the first read? Expected: the write premium is a quarter and the read saves nine tenths, so the two together already average below the normal price.
  • (level 2) When does the one-hour cache make sense? Expected: a batch job that reuses the prefix across runs more than five minutes apart, more than five times.
  • (level 3) Input tokens are down and the bill is flat. What is wrong with the dashboard? Expected: it does not split cached from uncached input, so a drop in traffic looks like a cache win.
  • (level 3) Ten parallel requests share a prefix that nobody has cached yet. What happens to the arithmetic? Expected: all ten pay the write premium and none reads, so the cache costs more than no cache. Send one request first, then the rest.

Where it is taught. The prompt caching lesson gives the break-even arithmetic and the verification fields, and the caching economics lesson names the parallel-write trap.

Debug a failureAn agent fans out ten tool calls at once for every user question. All ten share the same long system prompt, and prompt caching is on. The bill is several times what the cache should allow, and the usage fields show cache writes on nearly all calls and almost no cache reads. What is happening?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. All ten requests reach the provider before the first one has finished writing the prefix into the cache. Each one sees a miss, each one pays the write premium, and none of them reads. The fix is sequential-first: send one request alone, let its cache write land, then fan out the other nine. It adds about one write latency to the first tool call and removes the inflation.

The mechanism.

Cache writes happen per request. The lesson puts the first write at about 300 ms after the provider sees the prompt. Requests that arrive inside that window find nothing to read, so each of them writes. Ten writes and zero reads, on every user question that finds the prefix cold. A question that arrives while an earlier write is still inside the cache lifetime reads it, so the trap shows when the questions are further apart than that lifetime. The lesson reports a bill of 5 to 10 times the expected cached cost from this pattern alone.

Read the usage fields.

Each response reports the tokens written to the cache and the tokens read from it. In this incident the written count is high on every request and the read count is near zero. That is the signature. A later sequential request with the same prefix does read, which separates this case from a prefix that never matches.

The fix.

Send the first request alone and wait for it to return. Its write has landed by then. Fan out the remaining nine, and each of them reads. The cost is about 300 ms on the first tool call. The lesson's exercise asks for the same fix without adding end-to-end latency: warm the prefix with one call at the start of the session, before the first fan-out, so the first tool call already reads.

Rule out the other cause.

A prefix that carries dynamic text looks the same in the usage fields: writes on every request, no reads ever. The lesson's example has the time to the minute, a user id and a reshuffled example order inside the system prompt. One field report moved the hit rate from 7 to 74 percent by moving that text below the cache boundary. Check the prompt template before you blame the fan-out.

Plausible wrong answers.

  • "Caching is on, so the provider should deduplicate them." Writes are per request, and the cache can be read only after the first write has landed.
  • "Shorten the system prompt." That lowers every bill a little and leaves ten writes and zero reads in place.
  • "Turn caching off, it costs more." It costs more only because of the arrival pattern. Sequential-first turns ten writes into one write and nine reads.

Follow-ups an interviewer may ask.

  • (level 2) How do you tell the fan-out trap from dynamic text in the prefix? Expected: both show writes and no reads. After the fan-out trap, a later sequential request with the same prefix reads. With dynamic text, nothing ever reads.
  • (level 3) How do you fix the fan-out without adding latency for the user? Expected: warm the prefix with one call when the session starts, so the first fan-out already reads.
  • (level 3) Does a self-hosted prefix cache have the same trap? Expected: the lesson says the self-hosted caches follow the same prefix pattern at your own compute, so measure the cached tokens on a fan-out before you assume they are shared.

Estimate itYour batch job sends the same 15,000-token rubric with each of twenty code reviews, spread over 40 minutes in uneven clusters, and some of the quiet stretches between clusters outlast the short cache. The provider bills a write at 1.25 times the input rate for a five-minute cache and at 2 times the input rate for a one-hour cache, and bills reads at one tenth of the input rate. Which cache do you pick, and show the break-even.

Level 3 of 4 · about 10 minutes to answer well.

Short answer. The five-minute cache pays for itself on the first read: a write costs 1.25 times and a read 0.1 times the normal input rate, so one write plus one read averages 0.675 times, a saving of 32 percent, and one write plus ten reads averages 0.205 times, a saving of 80 percent. Each read refreshes the five-minute lifetime, so the five-minute cache expires only in a gap longer than five minutes. This batch has such gaps, so the one-hour cache fits; its write costs 2 times the input rate and it needs only two reads to come out ahead, and twenty reviews give far more. The rule of thumb is to cache anything reused at least three times within the lifetime.

The arithmetic.

Case Cost per request against uncached
One write, five-minute cache 1.25
One read 0.1
One write plus one read, averaged 0.675, a saving of 32 percent
One write plus ten reads, averaged 0.205, a saving of 80 percent
One write, one-hour cache 2, so two reads to break even

The lifetime decides it.

Each read refreshes the five-minute lifetime. If the reviews arrive steadily over 40 minutes, every gap stays inside five minutes, the entry never expires, and the five-minute cache wins with its cheaper write. If some gaps exceed five minutes, as in this batch, each of those gaps costs a new write at the premium, and the one-hour cache holds the whole batch for one write. If instead the reviews come as a burst of a few inside one minute followed by an idle hour, each burst fits the five-minute cache and the cheaper write wins. Pick from the gaps between requests, not from the total count.

Prove it on the response.

Read the usage fields: the lesson's first request reports 15,023 tokens written at 1.25 times, and the second reports the same count read at 0.1 times with zero written. In production, gate the deploy on a read fraction above 80 percent after warmup, and split the cost dashboard into cached and uncached tokens.

Other provider shapes.

The automatic provider gives 50 percent off reads with no premium, up to an hour on a best-effort basis, so the only job is a stable prefix. The explicit cache object on the third provider is storage-billed and reads at about 25 percent of the input rate; it fits reuse of one giant prompt across days.

Plausible wrong answers.

  • "Always pick the longer cache to be safe." Its write costs 2 times the input rate against 1.25; with reuse inside five minutes the shorter cache is cheaper.
  • "The write premium makes caching a loss for short jobs." One write plus one read already saves 32 percent on the five-minute cache.
  • "Cache the user message too." It differs on every request, so it never hits; the layout leaves it below the breakpoint.

Follow-ups an interviewer may ask.

  • (level 3) Why does the five-minute cache break even on the first read? Expected: the write costs 1.25 times and the read 0.1 times, so two requests average 0.675 times the uncached cost.
  • (level 3) What does the one-hour cache need to come out ahead? Expected: two reads, because its write costs 2 times the input rate.
  • (level 4) The reviews arrive in bursts of several within a minute, then nothing for an hour. Does the answer change? Expected: yes; each burst lives inside a five-minute cache, so the cheaper write wins, and the one-hour cache would pay the 2 times write for reuse that never comes.
  • (level 4) How do you verify the saving in production rather than on paper? Expected: read the cache creation and cache read token fields on each response, gate the deploy on a read fraction above 80 percent after warmup, and split the dashboard into cached and uncached tokens.

Debug a failureYou enabled prompt caching on a 15,000-token system prompt. The usage field for cache reads stays at zero on every request, while cache creation tokens are charged every time. What do you look for, and in what order?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Something above the cache breakpoint changes on every request. Look first for a timestamp or a request id at the top of the system prompt, then for tool definitions serialized in a changing order, then for near-duplicate text that differs by a byte between code paths, and then for a block under the minimum cacheable size. The cache matches prefixes only, so the first differing token turns everything after it into a miss.

The invariant.

All the providers cache prefixes. When a request's prefix matches a recent one, the provider serves the stored key and value cache instead of encoding the tokens again, and bills a read at a fraction of the input rate. If any token differs, everything after it is a miss. The usage fields tell the story: a creation count every time and a read count of zero means the prefix never matched.

The checklist, in order.

  1. A dynamic field at the top. A current time, a request id or a session id in the first lines of the system prompt misses on every request. Move it below the breakpoint with the other per-request fields.
  2. Tool reordering. Tools serialized from a dictionary can change order between deploys or between processes; serialize them in a stable order.
  3. Near-duplicate text. Two code paths that build the prompt with a one-byte difference produce two prefixes and no hits.
  4. Too-small blocks. The explicit cache has a floor of 1,024 tokens, 2,048 on the small model; a smaller block silently does not cache.
  5. On the automatic provider, a changed user field is part of the cache key, and the prefix must still be stable and above 1,024 tokens.

The layout that hits.

System prompt, then tool definitions, then few-shot examples, then retrieved documents if they are reused, then the history up to the last turn, then the current message, which is never cached because it is different every time.

Turn it into a test.

In CI, build two requests through the production prompt builder with the same user input, compare their cacheable prefixes, send both, and assert that the cache read token count is above zero on the second. Two hand-written identical bodies would skip the timestamp or request id that the builder adds. Split the cost dashboard into cached and uncached input tokens, or a traffic drop looks like a cache win.

Plausible wrong answers.

  • "Caching is automatic, there is nothing to configure." On the explicit providers you mark the block; on the automatic one the prefix still has to be stable and above 1,024 tokens, and a changed user field or tool order breaks it.
  • "Put the user message first so the model reads it early." That places the only part that changes above everything else, and the cache never hits.
  • "Extend the TTL to one hour, the cache is expiring." Expiry would show as writes after quiet periods, not on every request; the one-hour TTL also charges 2x for the write.

Follow-ups an interviewer may ask.

  • (level 2) How do you make this a test? Expected: two requests built by the production prompt builder with the same user input, with an assertion that the cache read tokens are above zero on the second; if they stay at zero the keys are drifting.
  • (level 2) Where does the timestamp go instead? Expected: below the breakpoint, with the other per-request fields such as the user message.
  • (level 3) The block is below the minimum size. What happens? Expected: nothing is cached and nothing is reported; the floor is 1,024 tokens, and 2,048 on the small model.
  • (level 3) Input tokens fell after your change. Is that proof it works? Expected: no; split the input tokens into cached and uncached, or a drop in traffic looks like a cache win.
