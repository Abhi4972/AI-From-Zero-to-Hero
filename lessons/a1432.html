The smallest useful workbench is three files: a root instructions router, a state file, and a task board. Everything else is layered on top. If a repo cannot carry these three, no model will save it.

The problem

In plain words first

The smallest useful workbench is three files in the repo. AGENTS.md is a short router: it tells the agent where to look and how "done" is checked. agent_state.json is the system of record for where work stands: the active task, the files touched, the blockers, the next action. task_board.json is the queue of tasks with their status. Because progress lives in files, not in a chat, a new session can pick up exactly where a dead one stopped. This lesson runs a real model through five bug-fix tasks with exactly these files, then kills the session halfway and resumes it.

Most teams reach for a workbench by writing a 3000-line AGENTS.md and calling it done. The model loads it, ignores the parts it cannot summarize, and still fails on the same surfaces it always failed on.

You need the opposite. A tiny root file that routes the agent into deeper files only when relevant. Durable state the agent reads before acting and writes after. A task board that says what is in flight, what is blocked, and what is up next.

Three files. Each one with a job. Each one machine-readable enough to evolve into a real system later.

The idea

Idea 1 · AGENTS.md is a router, not a manual

A good AGENTS.md is short. It points the agent at:

  • The state file (where you are).
  • The task board (what is left).
  • The deeper rules (under docs/agent-rules.md).
  • The verification command (how to know it works).

Anything longer goes in deeper docs, loaded only when needed. Long manuals get ignored. Short routers get followed.

Idea 2 · agent_state.json is the system of record

State carries: the active task id, the touched files, the assumptions made, the blockers, and the next action. The agent reads it at every turn. The next session reads it instead of replaying chat.

State lives in a file because chat history is unreliable. Sessions die. Conversations get trimmed. The file does not.

Idea 3 · task_board.json is the queue

The task board carries every task with status todo | in_progress | done | blocked. It is the queue the agent pulls from when state is empty, and the queue you read when you want to know whether the agent is on track.

A task on the board has an id, a goal, an owner (builder, reviewer, or human), and acceptance criteria. The board is small on purpose: when it grows past a screen, you have a planning problem, not a board problem.

Idea 4 · Three files is the floor, not the ceiling

Later lessons add scope contracts, feedback runners, verification gates, reviewer checklists, and handoff packets. The three files here are what they all assume.

The same idea as a formula

Resume cost. If progress lives only in chat and a session dies after completing k of n tasks, the next session repeats up to all k (it cannot tell what was done). If progress is written to a state file after every turn, the next session repeats at most the one turn that was in flight:

reworkchat​≤k tasks,reworkstate file​≤1 turn.

Narrowing the action. A free agent choosing among m tools per turn has to get both the tool and its arguments right; a harness that fixes the sequence (read, propose a fix, test) leaves the model one job per turn. With per-decision accuracy a, a task needing d free decisions succeeds with about ad; fixing the sequence removes all but the one that matters.

Worked example
Five tasks, nine turns
  • The board starts with five todo tasks. Each turn: read agent_state.json, take the active task (or the next todo), ask the model for the corrected function, write it, run the task's test.
  • Pass: the task becomes done and the state's active task clears. Fail: the test's last error line is appended to blockers and goes back to the model; after three failures the task is blocked.
  • Here: four tasks done, largest blocked after three attempts, nine turns in all. In lesson 14.31 the same model, free to call any tool, fixed none of these bugs.
  • Kill the session after four turns: the files say T-001 done, T-002 blocked, three todo. The next session does five turns and reopens nothing.
Check your mental model
  • ✗ "The agent remembers where it was."
    ✓ Only the files remember; a new session starts from them.
  • ✗ "AGENTS.md should hold every rule."
    ✓ Keep it a short router; long manuals get skimmed.
  • ✗ "More tool freedom makes agents more capable."
    ✓ The same model fixed 4 of 5 bugs with one job per turn, and 0 of 5 with free tool choice.
  • ✗ "Blocked is a failure of the workbench."
    ✓ Blocked with a recorded reason is the workbench working.

Three files and a real model

Five buggy functions and their tests in a scratch folder, with agent_state.json and task_board.json written by the lesson's save_state and save_board. Each turn reads only those files, asks Qwen2.5-0.5B-Instruct (greedy, CPU) for the corrected function, writes it and runs the test. About 1 minute.

# A minimal workbench around a real model, using the lesson's AgentState, Task and save/load helpers
# (code/main.py). Five one-line bugs are tasks on task_board.json. Each turn the harness reads the state
# file, takes the active task, and asks Qwen2.5-0.5B-Instruct (greedy, CPU) for one thing only: the corrected
# function. It writes the file, runs the task's test, and records the result in agent_state.json: done, or a
# blocker with the test output, which goes back to the model on the next attempt (three attempts per task).
import json, os, pathlib, re, subprocess, sys, tempfile, warnings
from dataclasses import asdict
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import AgentState, Task, load_state, load_board, save_state, save_board
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

BUGS = {  # task id -> (function name, buggy code, test body)
    "T-001": ("is_even", "def is_even(n):\n    return n % 2 == 1\n", "assert is_even(4) and not is_even(7)"),
    "T-002": ("largest", "def largest(xs):\n    return min(xs)\n", "assert largest([3, 9, 2]) == 9"),
    "T-003": ("reverse", "def reverse(s):\n    return s\n", "assert reverse('abc') == 'cba'"),
    "T-004": ("to_fahrenheit", "def to_fahrenheit(c):\n    return c * 9 / 5\n", "assert to_fahrenheit(100) == 212"),
    "T-005": ("count_vowels", "def count_vowels(s):\n    return len(s)\n", "assert count_vowels('banana') == 3"),
}
root = pathlib.Path(tempfile.mkdtemp())
for tid, (name, code, test) in BUGS.items():
    (root / f"{name}.py").write_text(code)
    (root / f"test_{name}.py").write_text(f"from {name} import {name}\n{test}\nprint('ok')\n")
STATE, BOARD = root / "agent_state.json", root / "task_board.json"
save_state(STATE, AgentState(active_task_id=None))
save_board(BOARD, [Task(id=t, goal=f"{n} returns the wrong answer; fix it", owner="builder",
                        acceptance=[f"python test_{n}.py exits 0"]) for t, (n, _, _) in BUGS.items()])

def propose(name, code, blocker):
    ask = f"This Python function has a bug.\n{code}\nReturn only the corrected function in a ```python block."
    if blocker:
        ask += f"\nYour last attempt failed its test:\n{blocker}"
    ids = tok.apply_chat_template([{"role": "user", "content": ask}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=120, do_sample=False)
    text = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)
    m = re.search(r"```(?:python)?\n(.*?)```", text, re.S)
    return (m.group(1) if m else text).strip() + "\n"

def turn():
    """One workbench turn: everything the agent needs comes from the two files, nothing from memory."""
    state, board = load_state(STATE), load_board(BOARD)
    if state.active_task_id is None:
        nxt = next((t for t in board if t.status == "todo"), None)
        if nxt is None:
            return False
        nxt.status, state.active_task_id, state.blockers, state.touched_files = "in_progress", nxt.id, [], []
        state.next_action = f"fix {BUGS[nxt.id][0]}"
    task = next(t for t in board if t.id == state.active_task_id)
    name, code, _ = BUGS[task.id]
    (root / f"{name}.py").write_text(propose(name, code, state.blockers[-1] if state.blockers else ""))
    state.touched_files = [f"{name}.py"]
    p = subprocess.run([sys.executable, f"test_{name}.py"], cwd=root, capture_output=True, text=True, timeout=30)
    if p.returncode == 0:
        task.status, state.active_task_id, state.next_action = "done", None, "pick next task"
    else:
        state.blockers.append(p.stderr.strip().splitlines()[-1][:120])
        if len(state.blockers) >= 3:
            task.status, state.active_task_id, state.next_action = "blocked", None, "needs a human or a stronger model"
    save_state(STATE, state); save_board(BOARD, board)
    return True

turns = 0
while turn():
    turns += 1
print(f"{turns} turns")
for t in load_board(BOARD):
    name = BUGS[t.id][0]
    print(f"  {t.id} {name:<14} {t.status:<8} now: {(root / f'{name}.py').read_text().strip().splitlines()[-1].strip()}")
print("\nagent_state.json at the end:")
print(STATE.read_text())

Reading this output

Four of five fixed, by the same model that fixed none in lesson 14.31. is_even, reverse, to_fahrenheit and count_vowels pass their tests. The difference is the harness: instead of choosing among tools each turn (and never once choosing write_file), the model gets one job, "return the corrected function", and the harness does the reading, writing and testing.

The failure is recorded, not hidden. largest failed three attempts and is blocked with its error in the blockers list; the file still ends in return min(xs). A person or a stronger model knows exactly where to start.

The state file is small and current: no active task, the last touched file, and a next action. That is all the next session needs.

Reading this output

Session 2 starts exactly where session 1 stopped. On disk it finds T-001 done, T-002 blocked (three attempts, last error AssertionError) and three tasks still to do, so it asks the model only about reverse, to_fahrenheit (three attempts) and count_vowels.

Build it

code/main.py writes the minimal workbench into an empty repo and demonstrates a single agent turn that:

  1. Reads agent_state.json.
  2. Pulls the next task from task_board.json if state is empty.
  3. Touches a single file inside scope.
  4. Writes back updated state.

Run it:

python3 code/main.py
npx tsx code/main.ts

The script creates workdir/ next to itself, lays down the three files, runs one turn, and prints the diff. Re-run it to see how the second turn picks up where the first left off.

The whole of code/main.py follows in parts. Each part runs on this page, in order, in one Python session; the last part does what python3 code/main.py does.

Part 1 of 3 · AgentState, Task, write_initial

"""Lay down the three-file minimal agent workbench and run a single turn.

Files written:
  workdir/AGENTS.md         short router into state + board + deeper docs
  workdir/agent_state.json  active task, touched files, blockers, next action
  workdir/task_board.json   queue of tasks with status + acceptance

Run: python3 code/main.py
Re-run to see the second turn pick up where the first stopped.
"""

from __future__ import annotations

import json
from dataclasses import asdict, dataclass, field
from pathlib import Path

ROOT = Path(__file__).parent / "workdir"


AGENTS_MD = """# AGENTS.md

This repo runs with a workbench. Read these before acting:

1. `agent_state.json`: where the last session stopped.
2. `task_board.json`: what is in flight, what is next.
3. `docs/agent-rules.md`: startup, scope, definition of done (load on demand).

Definition of done: the task referenced by `agent_state.active_task_id` has
`status == "done"` on `task_board.json` and the verification command listed in
its `acceptance` has exited 0.

Verification command: `python3 -m pytest -x`
""".lstrip()


@dataclass
class AgentState:
    active_task_id: str | None
    touched_files: list[str] = field(default_factory=list)
    assumptions: list[str] = field(default_factory=list)
    blockers: list[str] = field(default_factory=list)
    next_action: str = ""


@dataclass
class Task:
    id: str
    goal: str
    owner: str
    acceptance: list[str]
    status: str = "todo"


def write_initial(state_path: Path, board_path: Path, agents_path: Path) -> None:
    if not agents_path.exists():
        agents_path.write_text(AGENTS_MD)
    if not state_path.exists():
        state_path.write_text(json.dumps(asdict(AgentState(active_task_id=None)), indent=2) + "\n")
    if not board_path.exists():
        board = [
            Task(
                id="T-001",
                goal="add input validation to /signup",
                owner="builder",
                acceptance=["pytest test_app.py::test_signup_rejects_short_password"],
            ),
            Task(
                id="T-002",
                goal="document the new /signup contract",
                owner="builder",
                acceptance=["docs/api.md mentions /signup constraints"],
            ),
        ]
        board_path.write_text(json.dumps([asdict(t) for t in board], indent=2) + "\n")

Part 2 of 3 · load_state, load_board, save_state, save_board, run_one_turn

def load_state(state_path: Path) -> AgentState:
    raw = json.loads(state_path.read_text())
    return AgentState(**raw)


def load_board(board_path: Path) -> list[Task]:
    return [Task(**t) for t in json.loads(board_path.read_text())]


def save_state(state_path: Path, state: AgentState) -> None:
    state_path.write_text(json.dumps(asdict(state), indent=2) + "\n")


def save_board(board_path: Path, board: list[Task]) -> None:
    board_path.write_text(json.dumps([asdict(t) for t in board], indent=2) + "\n")


def run_one_turn(state: AgentState, board: list[Task]) -> tuple[AgentState, list[Task]]:
    if state.active_task_id is None:
        nxt = next((t for t in board if t.status == "todo"), None)
        if nxt is None:
            state.next_action = "no work on the board, idle"
            return state, board
        nxt.status = "in_progress"
        state.active_task_id = nxt.id
        state.next_action = f"start work on {nxt.id}: {nxt.goal}"
        return state, board

    active = next((t for t in board if t.id == state.active_task_id), None)
    if active is None:
        state.active_task_id = None
        state.next_action = f"active task missing from board; resetting and picking new work"
        return state, board
    if "app.py" not in state.touched_files:
        state.touched_files.append("app.py")
        state.next_action = f"add test for {active.id} acceptance"
        return state, board

    if "test_app.py" not in state.touched_files:
        state.touched_files.append("test_app.py")
        state.next_action = f"run verification command for {active.id}"
        return state, board

    active.status = "done"
    state.active_task_id = None
    state.touched_files = []
    state.next_action = "pick next task from board"
    return state, board


def main() -> None:
    ROOT.mkdir(exist_ok=True)
    state_path = ROOT / "agent_state.json"
    board_path = ROOT / "task_board.json"
    agents_path = ROOT / "AGENTS.md"

    write_initial(state_path, board_path, agents_path)
    state = load_state(state_path)
    board = load_board(board_path)

    print("before turn:")
    print(f"  active task : {state.active_task_id}")
    print(f"  next action : {state.next_action!r}")
    print(f"  todo on board: {[t.id for t in board if t.status == 'todo']}")

    state, board = run_one_turn(state, board)
    save_state(state_path, state)
    save_board(board_path, board)

    print("\nafter turn:")
    print(f"  active task : {state.active_task_id}")
    print(f"  touched     : {state.touched_files}")
    print(f"  next action : {state.next_action!r}")
    print(f"  board status: {[(t.id, t.status) for t in board]}")

Use it: the same idea with real libraries

Inside production agent products, the same three files show up under different names:

  • Claude Code: AGENTS.md or CLAUDE.md for the router, .claude/state.json-style stores for state, hooks for the board.
  • Codex / Cursor: workspace rules for the router, session memory for state, queued tasks in the chat sidebar for the board.
  • Custom Python agent: the same files you just wrote.

The names change. The shape does not.

Production patterns in the wild

The minimum workbench survives contact with real monorepos when three patterns are layered on top of it. They are independent; pick the ones your repo actually needs.

Nested AGENTS.md with nearest-wins precedence. OpenAI ships 88 AGENTS.md files across its main repo, one per subcomponent. Codex, Cursor, Claude Code, and Copilot all walk from the working file toward the repo root and concatenate every AGENTS.md they find on the way. Sub-directory files extend the root file. Codex adds AGENTS.override.md to replace rather than extend; the override mechanism is Codex-specific and avoid it for cross-tool work. Augment Code's measurement is the line that matters: the best AGENTS.md files give a quality jump equivalent to upgrading from Haiku to Opus; the worst ones make output worse than no file at all.

Anti-patterns to refuse, even when they look like coverage. Conflicting instructions silently drop the agent from interactive to greedy mode (ICLR 2026 AMBIG-SWE: 48.8% → 28% resolve rate); number priorities instead of stacking them flat. Unverifiable style rules ("follow the Google Python Style Guide") with no enforcement command let the agent invent compliance; pair every style rule with the exact lint command. Leading with style instead of commands buries the verification path; commands first, style last. Writing for humans instead of agents wastes context budget; terseness is a feature.

Cross-tool symlinks. A single root file with symlinks (ln -s AGENTS.md CLAUDE.md, ln -s AGENTS.md .github/copilot-instructions.md, ln -s AGENTS.md .cursorrules) keeps every coding agent on the same source of truth. Nx's nx ai-setup automates this across Claude Code, Cursor, Copilot, Gemini, Codex, and OpenCode from a single config.

Break it on purpose

Two agent sessions run in parallel on the same repo, both following this lesson's workbench. After an hour the board shows a task done that nobody fixed, and another task fixed twice with conflicting edits. What went wrong with the three files, and how would you fix it? (Solution B1.)

Industry practice
What's current (2024–2026)
  • AGENTS.md is a shared convention read by many coding agents (Codex, Cursor, Jules, Amp, and others); Claude Code reads CLAUDE.md and can import other files. Both are meant to be short and to point at deeper docs.
  • State on disk is how long-running agent setups survive restarts: Anthropic's long-running-agent harness keeps a progress file and a feature list, and frameworks persist checkpoints (lesson 14.13). Task boards appear as TODO/plan files or as issue trackers the agent reads through tools.
  • Structured steps over free tool choice is common in production: many teams fix the loop (plan, edit, test, review) and let the model fill one step at a time, especially with smaller models.
  • On your laptop: these files and the loop are plain Python; any local model can sit in the propose step.

Sources: AGENTS.md, Anthropic, Effective harnesses for long-running agents, Claude Code memory.

Recap
What to keep from this lesson
  • Three files: a short router, a state file, a task board.
  • Write state after every turn; resume from files, not chat.
  • One job per turn makes a weak model useful.
  • Record blockers with evidence and stop after a fixed budget.
  • Concurrent sessions need locks or one owner per task.

Given a repo path and a short backlog, scaffold the minimum viable agent workbench.

Produce:

1. `AGENTS.md` no longer than 80 lines. It must route to: the state file, the task board, the deeper rules doc (even if empty), and the verification command. No prose tutorials in this file.
2. `agent_state.json` with these keys: `active_task_id`, `touched_files`, `assumptions`, `blockers`, `next_action`. All optional fields default to empty array or empty string, never `null` for arrays.
3. `task_board.json` as a JSON array of tasks. Each task has `id`, `goal`, `owner` (`builder` | `reviewer` | `human`), `acceptance` (list of strings), and `status` (`todo` | `in_progress` | `done` | `blocked`).
4. `docs/agent-rules.md` placeholder with a single H2 per surface so later lessons can fill it.

Hard rejects:

- `AGENTS.md` over 80 lines or under 10 lines. Too long and the agent skips it; too short and it carries no routing.
- A state file that references chat history instead of the repo. The repo is the system of record.
- A task board without `acceptance`. Tasks without acceptance criteria become "looks good" rubber stamps.
- Tasks whose `owner` is `agent` or `model`. Owners are roles, not entities.

Refusal rules:

- If the repo has no verification command, refuse to write `AGENTS.md` until one is supplied or stubbed. A router pointing at a missing gate is worse than no router.
- If the backlog has more than 12 open tasks, refuse and ask the user to split it. Boards over a screen drift into planning theater.
- If the project ships with secrets in tracked files, refuse to write the state file and surface the secret leak as a blocking finding first.

Output structure:

```
<repo>/
├── AGENTS.md
├── agent_state.json
├── task_board.json
└── docs/
    └── agent-rules.md
```

  3. Migrate task_board.json to JSON Lines so each task is a line and diffs are clean in version control.

Solutions

SolutionP1 · Four of five

Four. is_even, reverse, to_fahrenheit and count_vowels pass; largest fails three attempts and is marked blocked with its error. Same model as lesson 14.31: the gain comes from giving it one well-defined job per turn and doing the file handling and testing in the harness.

SolutionB1 · Two writers, no lock

Both sessions read and wrote the same agent_state.json and task_board.json without coordination. Each picked a task by reading the board, so both could pick the same todo task (fixed twice, conflicting edits), and one session's save could overwrite the other's (a task marked done from a stale copy of the board, or state pointing at the wrong task).

Fix: one state file per session (or per worker), with the board as the only shared file; claim a task atomically before working on it (a lock file, a compare-and-set on a status with an owner field, or a real queue or issue tracker that assigns work); write the board with optimistic concurrency (re-read, check the version, then write); and mark done only from a verification result that names the commit, so a stale writer cannot close a task it did not finish.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Weigh a trade-offA repo has a 3000-line instructions file for its coding agent. The agent follows about half of it. One engineer wants to cut it to a page. Another says that every line came from an incident and nothing can go. How do you settle it?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. Both are right about something, and the answer is a layered file set, not a shorter file. Keep a root router under about 50 lines that holds only pointers and the few hard rules. Move the rules into a rules file with one screen per category, and move the depth into topic documents that the agent loads only when a task touches them. Every rule stays, and the agent reaches any rule in at most two hops.

Why the long file fails.

The model loads the file, reads the first screen, runs out of attention budget, and acts on a fraction of what it was told. A long manual fails for the same reason a forty-page onboarding document fails. The reader skims it once and never returns to the part that mattered. Long manuals get ignored. Short routers get followed.

The three tiers.

Tier Lives in Read when Size
Router the root instructions file Every session Under about 50 lines
Rules docs/agent-rules.md Every session, at startup One screen per category
Topic docs docs/<topic>.md Only when the task touches that topic As deep as needed

The router points at the state file, the task board, the rules and the verification command. It links every topic document by path, not by description.

Two tests that keep it honest.

  • Reachability. The agent reaches any rule in at most two hops from the router. A pointer that no longer resolves is worse than a missing rule, so a broken link in the router is itself a startup violation.
  • Freshness. The router is short enough that a reviewer reads it again on every pull request. That is the only thing that stops it from growing back into the manual.

What to refuse while you trim.

The lesson lists anti-patterns that look like coverage. Conflicting instructions silently drop the agent from asking to guessing; one measurement put the resolve rate at 48.8 percent with clear instructions and 28 percent with conflicting ones. A style rule with no lint command lets the agent invent compliance, so pair every style rule with its command. Lead with commands and end with style. Write for the agent, not for a human reader, because terseness saves context.

Nested files.

Large repos keep one router per subcomponent. Tools walk from the working file to the root and concatenate every router they find, so a subdirectory file extends the root file. One large repository in the lesson carries 88 of them. Measurements in the lesson place the best files at a quality jump equal to a model upgrade, and the worst files below no file at all.

Plausible wrong answers.

  • "Cut the file to one page and delete the rest." The rules came from incidents, and deleting them repeats the incidents, so move them to tiers instead.
  • "Keep the long file, and tell the agent to read all of it." The model has an attention budget, and an instruction to read everything does not change how much it acts on.
  • "Put the file in the system prompt so that it is always in context." Being in context is not the problem; acting on it is, and a short router with pointers gets followed where a long block does not.

Follow-ups an interviewer may ask.

  • (level 2) The team keeps a rule in the router because it is important. What is the test for whether it belongs there? Expected: the router holds pointers and the few hard rules that apply to every session, and anything that applies to one kind of task goes in a topic document.
  • (level 2) How do you keep one source of truth when the team uses several coding agents? Expected: one root file and symlinks with the names each tool expects, so that every tool reads the same text.
  • (level 3) What does a lint for the workbench check? Expected: the router is under the line budget, every path it references exists, and no two rules conflict.
  • (level 3) Why does the lesson rank a dead link below a rule that was never written? Expected: the agent trusts the router, follows the pointer, finds nothing, and proceeds as if the rule did not exist, while a missing rule at least leaves no false promise.

Where it is taught. The minimal workbench lesson makes the router one of three files, and the executable constraints lesson gives the tiers and the two tests.
