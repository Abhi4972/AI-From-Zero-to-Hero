Output Is Not Outcome

In plain words first

An output is the thing you build, such as an assistant, a dashboard or a summary email. An outcome is what changes for a person: "the on-call engineer finds the failing service within two minutes". Write the outcome first, as a six-part frame (user, situation, current behaviour, desired outcome, constraints, non-goals), and keep the output out of it. Otherwise the first idea becomes the scope before anyone has checked it. Getting from pilot to value is covered in Lesson 14.165 (linked above). This lesson measures how often solution names leak into outcome statements, and how well two detectors catch them.

“Build an incident assistant” names an output. It does not say who needs it, what becomes better, or what must remain safe.

An outcome frame says:

When a production alert arrives, the on-call engineer identifies the failing service and a safe next action within two minutes, while diagnosis remains read-only and auditable.

That sentence can be satisfied by software, a runbook, a data repair, or a smaller interface change. It keeps the team attached to the result rather than the first artifact someone imagined.

The Six-Part Frame

Part Question
User Who experiences the problem directly?
Situation When and where does it occur?
Current behavior What happens today, including workarounds?
Desired outcome What observable state should improve?
Constraints Which safety, policy, cost, or compatibility limits are fixed?
Non-goals What tempting adjacent work is excluded?

Find Solution Leakage

Outcome statements leak solutions when they contain a product form, interface, model choice, framework, or architecture that has not been earned by evidence.

  • “Users receive a weekly AI summary” leaks the summary and cadence.
  • “Users understand account changes before approval” states the result.
  • “Deploy a vector database” leaks infrastructure.
  • “Relevant policy evidence is available during review” states a capability.

Constraints can name technology when compatibility truly fixes it. Record why it is fixed.

Constraints Protect the Outcome

Constraints are not implementation details. They are part of the real-world goal:

  • no production writes during diagnosis;
  • response within the incident time budget;
  • existing audit events remain authoritative;
  • no new runtime dependency;
  • accessibility behavior remains intact.

A build that reaches the outcome by violating a constraint has not reached the outcome.

Non-Goals Create a Boundary

Non-goals prevent a useful slice from turning into a platform. Good non-goals are concrete enough to reject work:

  • no automatic remediation;
  • no new alert-routing system;
  • no replacement of the incident commander;
  • no historical analytics in this slice.
The same idea as a formula

A detector is judged on both kinds of error. Over labelled statements, a leak detector has

recall=TP+FNTP​,precision=TP+FPTP​,

where TP counts leaks flagged, FN leaks missed and FP clean statements flagged.

Which error is cheaper here? A missed leak (FN) lets an output harden into scope, and costs a project. A false alarm (FP) costs a minute of a person's review. So a leak check should favour recall and route its flags to a person, not block automatically.

Worked example
Two detectors, fourteen statements
  • Seven statements leak a solution and seven do not.
  • The lesson's validate() looks for the exact proposed-output name, "incident assistant". It flags "use the incident assistant" and nothing else: recall 1/7≈14%, with no false alarms.
  • The lexicon flags all seven leaks, so recall is 7/7. It also flags "a support agent resolves…" (a human agent) and "the nightly build stays green", so precision is 7/9≈78%.
  • For a check that a person reviews, 2 false alarms are cheap and 6 missed leaks are not. The lexicon is the better first pass.

# Solution leakage, measured. Fourteen outcome statements, labelled by hand as leaking a solution or not: the four
# from the lesson, plus rewordings of the lesson's own example and two that use tech words innocently. Two detectors: the lesson's validate(), which only
# looks for the proposed output's exact name, and a small lexicon of product forms, interfaces, model and
# infrastructure words. No model; instant.
import re
from main import OutcomeFrame, validate, example
STATEMENTS = [   # (statement, leaks a solution?)
    ("Users receive a weekly AI summary", True),
    ("Users understand account changes before approval", False),
    ("Deploy a vector database", True),
    ("Relevant policy evidence is available during review", False),
    ("use the incident assistant", True),
    ("the on-call engineer uses the AI assistant to find the failing service", True),
    ("an LLM chatbot answers the on-call engineer's questions", True),
    ("a dashboard shows the failing service", True),
    ("identifies the failing service and safe next action within two minutes", False),
    ("the on-call engineer knows which service is failing before paging others", False),
    ("fewer than one in ten alerts need a second responder to find the cause", False),
    ("an agent with read-only tools proposes the next action", True),
    ("a support agent resolves the billing question in one reply", False),
    ("the nightly build stays green after every merge", False),
]
LEXICON = r"\b(ai|llm|gpt|model|agent|assistant|chatbot|bot|dashboard|app|tool|tools|api|database|vector|rag|" \
          r"summary|email|notification|ui|screen|button|plugin|microservice|kubernetes|deploy|build)\b"

def lesson_detect(text):
    frame = OutcomeFrame(**{**example().__dict__, "desired_outcome": text})
    return "desired outcome names the proposed output" in validate(frame)

def lexicon_detect(text):
    return re.findall(LEXICON, text.lower())

def score(pred):
    tp = sum(p and y for p, (_, y) in zip(pred, STATEMENTS))
    fp = sum(p and not y for p, (_, y) in zip(pred, STATEMENTS))
    fn = sum((not p) and y for p, (_, y) in zip(pred, STATEMENTS))
    return tp, fp, fn

print(f"{'statement':<74} {'leak?':<6} {'lesson':<7} lexicon")
L, X = [], []
for text, leak in STATEMENTS:
    l, x = lesson_detect(text), lexicon_detect(text)
    L.append(l); X.append(bool(x))
    print(f"{text[:72]:<74} {'yes' if leak else 'no':<6} {'flag' if l else '-':<7} {x or '-'}")
for name, pred in (("lesson validate()", L), ("lexicon", X)):
    tp, fp, fn = score(pred)
    print(f"\n{name:<18} caught {tp}/{tp + fn} leaks, {fp} false alarms")
print("\nthe lesson's example frame:", validate(example()) or "no issues",
      f"  (proposed_output = {example().proposed_output!r})")

Reading this output

validate() catches 1 of 7 leaks. It flags only "use the incident assistant", which contains the exact proposed-output name. "Uses the AI assistant", "an LLM chatbot", "a dashboard" and "an agent with read-only tools" all pass, and so does the lesson's own example frame.

The lexicon catches all 7, with 2 false alarms. "a support agent resolves…" (a person) and "the nightly build stays green" contain words from the list but name no solution. The clean outcome statements, such as "fewer than one in ten alerts need a second responder", contain none of them.

This is a small, hand-labelled set. The counts show how each detector fails, not their real rates. Exact matching fails quietly; a word list fails loudly, on cases a person can dismiss at a glance.

# This block continues from the one above. Four backlog requests that name an output. Qwen2.5-0.5B-Instruct
# (greedy, CPU) rewrites each as the lesson's six-part outcome frame, asked explicitly not to name a solution.
# Each frame goes through the lesson's validate() (with the request's output as proposed_output) and the lexicon.
# About 2 minutes.
import json, os, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def chat(prompt, n=300):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

REQUESTS = [("Build an incident assistant for on-call engineers", "incident assistant"),
            ("Add a weekly AI summary email for account owners", "weekly AI summary"),
            ("Deploy a vector database so reviewers can search policies", "vector database"),
            ("Add a chatbot to the billing page", "chatbot")]
EXAMPLE = json.dumps({k: v for k, v in example().__dict__.items() if k != "proposed_output"})
for request, output in REQUESTS:
    raw = chat(f"Feature request: {request}\nRewrite it as an outcome frame. The desired_outcome must describe an observable "
               "result for the user and must not name any product, tool, AI, interface or technology.\n"
               f"Example frame for a different request:\n{EXAMPLE}\n"
               "Return only JSON with keys user, situation, current_behavior, desired_outcome, constraints, non_goals.")
    m = re.search(r"\{.*\}", raw, re.S)
    try:
        d = json.loads(m.group(0)) if m else {}
    except json.JSONDecodeError:
        d = {}
    as_list = lambda v: [str(x) for x in v] if isinstance(v, list) else ([str(v)] if v else [])
    frame = OutcomeFrame(user=str(d.get("user", "")), situation=str(d.get("situation", "")),
                         current_behavior=str(d.get("current_behavior", "")), desired_outcome=str(d.get("desired_outcome", "")),
                         constraints=as_list(d.get("constraints")), non_goals=as_list(d.get("non_goals")), proposed_output=output)
    print(f"request: {request}")
    if not d:
        print(f"   not valid JSON: {raw.strip()[:80]!r}\n"); continue
    print(f"   user: {frame.user[:60]!r}")
    print(f"   desired_outcome: {frame.desired_outcome[:110]!r}")
    print(f"   constraints: {[c[:40] for c in frame.constraints][:3]}   non_goals: {[n[:40] for n in frame.non_goals][:3]}")
    print(f"   validate(): {validate(frame) or 'no issues'}   lexicon in desired_outcome: {lexicon_detect(frame.desired_outcome) or 'none'}\n")

Reading this output

The model leaks in two of four frames. For the summary email the outcome is "receives and summarizes weekly AI summaries". validate() misses it, because "summaries" is not the exact string "summary". For the chatbot it is "introducing a chatbot…", which both checks catch. For the vector database, the leak moved into a constraint ("vector database allows quick access"), where neither check looks.

One clean frame changed the goal. The incident frame has no product words, but its outcome is "the incident is escalated to a senior engineer". That is a different outcome, and worse than the two-minute target. No detector catches that; a person reading the frame does.

Three of four frames have no non-goals. validate() correctly refuses them as incomplete.

Part 1 of 2 · OutcomeFrame, validate, decision, example

# Lesson program for framing observable outcomes before choosing outputs.
# Read: phases/14-agent-engineering/47-outcomes-before-output/docs/en.md
# Reference: Nuseibeh and Easterbrook, Requirements Engineering: A Roadmap, 2000.
# Reference: Dardenne, van Lamsweerde, and Fickas, Goal-Directed Requirements Acquisition, 1993.
# Run this file to generate outputs/outcome-frame.json.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass
class OutcomeFrame:
    user: str
    situation: str
    current_behavior: str
    desired_outcome: str
    constraints: list[str]
    non_goals: list[str]
    proposed_output: str = ""


def validate(frame: OutcomeFrame) -> list[str]:
    issues: list[str] = []
    for name in ("user", "situation", "current_behavior", "desired_outcome"):
        if not getattr(frame, name).strip():
            issues.append(f"{name} is empty")
    if not frame.constraints:
        issues.append("constraints are empty")
    if not frame.non_goals:
        issues.append("non-goals are empty")
    if frame.proposed_output and frame.proposed_output.lower() in frame.desired_outcome.lower():
        issues.append("desired outcome names the proposed output")
    return issues


def decision(frame: OutcomeFrame) -> dict:
    issues = validate(frame)
    return {
        "status": "ready-to-discover" if not issues else "needs-framing",
        "issues": issues,
        "frame": asdict(frame),
        "next_question": f"What evidence would show that the desired outcome was achieved for the {frame.user}?",
    }


def example() -> OutcomeFrame:
    return OutcomeFrame(
        user="on-call engineer",
        situation="a production alert arrives during an incident",
        current_behavior="searches three dashboards before finding the affected service",
        desired_outcome="identifies the failing service and safe next action within two minutes",
        constraints=["read-only during diagnosis", "must preserve the audit trail"],
        non_goals=["automatic remediation", "replacing the incident commander"],
        proposed_output="incident assistant",
    )


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "outcome-frame.json"
    output.write_text(json.dumps(decision(example()), indent=2) + "\n", encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Solutions

SolutionP1 · Exact names miss most leaks

One. validate() only checks whether the exact proposed-output name, "incident assistant", appears in the desired outcome, so it catches "use the incident assistant" and misses the other six leaks.

The word list catches all seven and raises two false alarms, where "agent" is a person and "build" is a CI build. For a check whose flags a person reviews, that trade is the right way round.

SolutionB1 · Frame the ticket, not the agent

The outcome named its output ("the AI agent") and its user's tool, not the change in the ticket. A frame written first would be:

  • User: support agent.
  • Situation: a refund ticket arrives.
  • Current behaviour: it waits a median of N hours for approval.
  • Desired outcome: refund tickets under the policy limit are resolved in one contact.
  • Constraints: refunds stay within policy, and approvals remain auditable.
  • Non-goals: no change to refund policy, and no automation for other ticket types.

Writing the current behaviour would have shown that the wait was in approval, not in typing replies. Many outputs could then meet the outcome: an approval rule, a delegated limit, or an agent that drafts the approval. The model would have been one candidate among them, not the scope.

Break it on purpose

A director asks for "an AI agent for the support team". The team writes the outcome as "support agents use the AI agent to resolve tickets faster" and starts building. Three months later the agent works, but handle time is unchanged, because most tickets waited on a refund approval the agent cannot give. Using this lesson, what should the frame have said? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Start with the simplest thing that meets the outcome. Anthropic's agent guidance recommends the simplest solution first and adding agentic complexity only when it clearly improves the outcome. OpenAI's agent guide reserves agents for workflows with complex judgement, brittle rules or unstructured data.
  • Write the result before the build. Amazon's working-backwards PR/FAQ describes the customer result before any design. Jobs-to-be-done frames the progress a person is trying to make in a situation. Both are in wide use for AI features.
  • Outcome metrics in AI rollouts. Teams set a task-level outcome (resolution time, escalation rate, errors caught) and a guardrail before choosing between a prompt, a workflow, an agent or no AI at all.
  • On your laptop: the frame and both detectors are standard-library Python. The model step runs on CPU.

Sources: Anthropic, Building effective agents, OpenAI, A practical guide to building agents, Working Backwards, PR/FAQ, Christensen et al., Know your customers' jobs to be done (HBR).

Recap
What to keep from this lesson
  • Frame the outcome in six parts: user, situation, current behaviour, desired outcome, constraints, non-goals.
  • An outcome that names its output has stopped being an outcome.
  • Check for leakage with a word list and a person; exact-name matching misses most leaks.
  • Constraints may name technology only when it is truly fixed, and then say why.
  • Non-goals keep the first slice small; an empty list is a framing failure.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismA product manager asks you to build an incident assistant for the on-call team. You have one week. Before you plan any work, what do you ask, and what do you write down first?

Level 1 of 4 · about 8 minutes to answer well.

Short answer. The request names an artifact, not a result. I write an outcome frame first: who has the problem, when it happens, what they do today, which observable state must improve, which limits are fixed, and which nearby work is out of scope. Then I check the frame for a product form, a model or an architecture that no evidence supports yet.

The six parts of the frame.

Part Question I answer
User Who feels the problem directly?
Situation When and where does it happen?
Current behavior What happens today, including the workarounds?
Desired outcome Which observable state must get better?
Constraints Which safety, policy, cost or compatibility limits are fixed?
Non-goals Which tempting adjacent work is excluded?

For the on-call team, the desired outcome could read: when an alert arrives, the engineer finds the failing service and one safe next step inside the incident time budget, and the diagnosis stays read-only and auditable. A runbook, a data repair or a smaller interface change can all satisfy that sentence. The team stays attached to the result, not to the first tool someone imagined.

Leakage.

A frame leaks a solution when it contains an interface, a model choice, a framework or a storage system that evidence has not earned. "Users get a weekly summary from a model" leaks the summary and the cadence. "Users understand account changes before approval" states the result. A constraint can name a technology when compatibility really fixes it. I record why it is fixed.

Constraints and non-goals do real work.

Constraints are part of the goal. No production writes during diagnosis, a response inside the incident time budget, and no new runtime dependency all remove whole classes of solutions. Non-goals keep the first slice from growing into a platform: no automatic remediation, no new alert routing, no replacement of the incident commander.

Plausible wrong answers.

  • "Start with the interface and refine the goal later." The interface is one output. It ties the team to the first artifact before anyone knows what must improve.
  • "Constraints are implementation details for later." A build that reaches the outcome and breaks a constraint has not reached the outcome.
  • "Non-goals are optional." Without them, a useful slice grows into a platform before the first result is measured.

Follow-ups an interviewer may ask.

  • (level 1) How do you tell an outcome from an output? Expected: an outcome names an observable change for a user; an output names an artifact such as a page, a tool or a model.
  • (level 2) The manager insists on a chat interface. Where does that go in the frame? Expected: into the constraints only when policy or compatibility fixes it, with the reason written down; otherwise it waits for evidence.
  • (level 2) Name two non-goals that keep the first slice small. Expected: no automatic fix of the incident and no new alert routing, for example; each one must be concrete enough to reject work.
  • (level 3) What is the first observation that would show the desired outcome is wrong? Expected: a measured time to find the failing service that is already short, which means the frame targets a problem that does not exist.
