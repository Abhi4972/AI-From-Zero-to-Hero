In plain words first
The idea in one line

Production long-horizon agents do not run in while True. Every LLM call becomes an activity with checkpoint, retry, and replay. Temporal's OpenAI Agents SDK integration entered public preview in July 2025, and its Python version is now generally available. Claude Code scheduled tasks (launched as Routines in April 2026) run Claude Code in Anthropic's cloud on a schedule or a trigger, with no process on your machine. Sessions pause on human-input, survive deploys, and resume from the latest checkpoint keyed by thread_id. Behind the new ergonomics sits an old pattern — workflow orchestration — with one new input: LLM calls as non-deterministic activities that must be deterministically replayed on recovery.

The problem

In plain words first

An agent that runs for hours will be interrupted: a deploy, a crash, a reboot, a human who answers tomorrow. Durable execution writes every outside call (a model call, a tool call, an email) to a log before and after it runs. On restart the workflow code runs again from the top, and every call already in the log returns its logged result instead of running again. Durable execution and checkpoint-and-resume are covered in Lessons 14.140 and 14.60 (linked above). This lesson breaks the toy engine in three realistic ways, fixes it, and then puts a real model call inside it.

Consider an agent that runs for four hours. It calls three tools, prompts the user twice, and makes forty LLM calls. Halfway through, the host it is running on reboots. What happens?

  • In a naive while True loop: everything is lost. The run restarts from scratch. The three tool calls (with real side effects) execute again. The user is prompted again for things they already approved. Forty LLM calls are re-billed.
  • With durable execution: the run resumes from the most recent checkpoint. Already-completed activities are not re-executed; their results are replayed from the durable log. The user does not re-approve things they already approved. The LLM calls already made are not re-billed.

This is the same pattern workflow engines have shipped for a decade (Temporal, Cadence, Uber's Cherami). What's new is that LLM calls are now a kind of activity — non-deterministic, expensive, with side effects — and they fit this pattern cleanly.

The running theme of the lesson: long-horizon reliability decays. On METR's task suite, an agent's success rate falls roughly exponentially with how long the task takes a human, so each agent has a "half-life" (Toby Ord, 2025). Durable execution enables runs that are longer than the reliability profile supports, which is a new way to fail safely if the design is right and unsafely if the design is wrong.

Idea 1 · Activities, workflows, and replay

  • Workflow: deterministic orchestration code. Defines the sequence of activities, the branches, the waits. Must be deterministic so it can be replayed from the event log without surprising divergence.
  • Activity: a non-deterministic, potentially failing unit of work. LLM call, tool call, file write, HTTP request. Each activity is logged with its inputs and (once complete) its outputs.
  • Event log: the durable backing store. Every activity start, complete, fail, retry, and every workflow decision is recorded.
  • Replay: on recovery, the workflow code re-runs from the start; every activity that already completed returns its logged result without re-executing. Only activities that had not completed are actually run.

This is the same shape as React re-rendering against a virtual DOM, or Git rebuilding a working tree from commits. Determinism in the orchestrator is what makes durability cheap.

Idea 2 · Why LLM calls fit the pattern

LLM calls are: - Non-deterministic (temperature > 0; even temperature 0 drifts across model versions). - Expensive (money and latency). - Potentially failing (rate limits, timeouts). - Side-effectful (if they invoke tools).

This is exactly the activity profile. Wrapping every LLM call as an activity gives you retry with exponential backoff, checkpointing across restarts, and a replayable trace for debugging.

Idea 3 · Checkpoints keyed by thread_id

LangGraph, Microsoft Agent Framework, Cloudflare Durable Objects, and the Claude Agent SDK (resumable session IDs) all converged on the same API shape: a thread_id (or equivalent) identifies the session; each state transition persists to a backend (PostgreSQL default, SQLite for dev, Redis for cache); resume reads the latest checkpoint.

The backend choice matters:

  • PostgreSQL: durable, queryable, survives deploys. Default for LangGraph.
  • SQLite: local-dev only; loses data across hosts.
  • Redis: fast but ephemeral unless AOF/snapshot configured.
  • Cloudflare Durable Objects: transparently distributed; scoped by a unique key; survives for hours to weeks.

Idea 4 · Human-input as a first-class state

Propose-then-commit (Lesson 15.15) requires a durable "waiting on human" state. The workflow pauses, the external queue holds the pending request, and an approval resumes from exactly that point. Without durability this is best-effort; with it, an overnight approval arrives and the workflow picks up in the morning.

Idea 5 · Reliability falls with task length

METR measures each agent's "time horizon": the length of task, timed on human experts, that it completes half the time. Toby Ord (2025) showed that METR's success curves fit a constant failure rate per minute of task: success falls exponentially with length, and each agent has a half-life. Doubling a task's length squares the success rate. At a 4-hour half-life a 1-hour task succeeds 84% of the time and a 2-hour task 71%, so failure goes from 16% to 29%. Durable execution does not fix this; it lets you run longer than the reliability profile supports. The safe pattern is to combine durability with checkpoints that require fresh HITL on re-entry, and with budget kill switches (Lesson 15.13) that cap total compute regardless of wall-clock time.

Idea 6 · When durable execution is the wrong answer

  • Runs shorter than a few minutes with no human input. Overhead > benefit.
  • Strictly read-only information retrieval.
  • Tasks where correctness requires end-to-end within one context window (some reasoning tasks; some one-shot generation).

The same idea as a formula

Replay. Number the activities a workflow asks for i=0,1,2,… and let the log L map a position to its result. On a run, activity i returns

ai​={L[i]run it, then log L[i]​if i is logged as doneotherwise.​
Replay is correct only if the workflow code asks for the same activity at each position every time, which is why the code must be deterministic. Keying by position, not by name and arguments, lets the same call legitimately return different results (a poll).

Idempotency. A crash between "the side effect happened" and "done was logged" makes replay run that activity again. Pass the outside system a key k=(workflow id,i) and have it ignore a key it has seen: the effect then happens once however many times the activity runs.

The half-life. If every minute of work carries the same chance of a fatal error, success on a task of length t is

p(t)=2−t/h,
where h is the agent's half-life. Doubling the length squares success, p(2t)=p(t)2, so failure grows by
1−p(t)1−p(t)2​=1+p(t)≤2.
Doubling a task at most doubles its failure rate under this model; it cannot quadruple it.

Counting one crash

  • The lesson's engine on restart: fetch and summarise replay from the log, send runs again. The customer receives 2 reports.
  • The position-keyed engine passes key wf-42/2 to the outside system. The second send is answered "duplicate ignored", and the customer receives 1.
  • Half-life arithmetic, with h=4 hours: p(1)=2−1/4=0.841 and p(2)=0.8412=0.707. Failure goes from 15.9% to 29.3%, a factor of 1+0.841=1.84.
Check your mental model
  • ✗ "With an event log, retries never repeat a side effect."
    ✓ A crash inside an activity, after its effect and before "done", repeats it. Idempotency keys stop that.
  • ✗ "Matching a logged event by name and arguments is enough."
    ✓ A poll with the same arguments then returns its first answer forever. Real engines match by position in the history.
  • ✗ "Reading the clock in workflow code is harmless."
    ✓ On replay the clock reads differently and the workflow takes another branch. Read it through the engine (Workflow.now()) so the value is logged.
  • ✗ "Durable execution makes long runs reliable."
    ✓ It saves work lost to crashes, not to mistakes. Success still falls with task length.

# The lesson's engine (imported from main.py) has three gaps, each shown here against a fake outside world:
# a crash inside an activity (after its side effect, before "done" is logged), the same activity called twice with
# the same arguments, and a clock read inside workflow code. Then the fixes real engines use. Runs in under a second.
import contextlib, io, json, os, tempfile
from main import activity, fetch_docs, call_llm, reset_log

OUTBOX = []                       # the outside world: every report the customer actually received
def deliver(report, key=None):
    if key is not None and any(k == key for k, _ in OUTBOX):
        return "duplicate ignored"
    OUTBOX.append((key, report))
    return "delivered"

class HostDied(Exception):
    pass
crash = {"inside_send": False}

@activity("send_report")
def send_report(summary):
    deliver(summary)
    if crash["inside_send"]:
        crash["inside_send"] = False
        raise HostDied("host died after delivering, before 'done' was logged")
    return "sent"

def report_workflow(log, query):
    return send_report(log, call_llm(log, fetch_docs(log, query)))

quiet = contextlib.redirect_stdout(io.StringIO())    # hide the toy engine's [run]/[replay] lines
tmp = tempfile.mkdtemp()
print("1. crash inside an activity, the lesson's engine")
log = reset_log(os.path.join(tmp, "a.json"))
crash["inside_send"] = True
try:
    with quiet:
        report_workflow(log, "hello")
except HostDied as e:
    print(f"   attempt 1: {e}")
with quiet:
    report_workflow(log, "hello")
print(f"   attempt 2 resumes from the log; the customer received {len(OUTBOX)} reports")

# ---- the fix: events keyed by position in the workflow, plus an idempotency key per side effect ----
class Durable:
    """Event i is the i-th activity the workflow asks for, whatever its name or arguments."""
    def __init__(self, path, workflow_id):
        self.path, self.wf, self.pos, self.calls = path, workflow_id, 0, 0
        if not os.path.exists(path):
            json.dump([], open(path, "w"))
    def events(self):
        return json.load(open(self.path))
    def act(self, name, fn, *args, idempotent=False):
        i, self.pos = self.pos, self.pos + 1
        logged = [e for e in self.events() if e["seq"] == i]
        done = next((e for e in logged if e["status"] == "done"), None)
        if logged and logged[0]["name"] != name:
            raise RuntimeError(f"non-determinism: event {i} was {logged[0]['name']!r} in the log, the code now asks for {name!r}")
        if done:
            return done["result"]
        evs = self.events() + [{"seq": i, "name": name, "args": list(args), "status": "started"}]
        json.dump(evs, open(self.path, "w"))
        self.calls += 1
        result = fn(*args, key=f"{self.wf}/{i}") if idempotent else fn(*args)
        json.dump(evs + [{"seq": i, "name": name, "status": "done", "result": result}], open(self.path, "w"))
        return result

def send(summary, key=None):
    r = deliver(summary, key)
    if crash["inside_send"]:
        crash["inside_send"] = False
        raise HostDied("host died after delivering, before 'done' was logged")
    return r

def report_workflow2(d, query):
    docs = d.act("fetch_docs", lambda q: len(q) * 3, query)
    summary = d.act("call_llm", lambda n: f"summary({n}_docs)", docs)
    return d.act("send_report", send, summary, idempotent=True)

# This block continues from the one above: a real LLM call as an activity. Qwen2.5-0.5B-Instruct (CPU) decides
# whether a support ticket goes to a human; the workflow then acts on that decision, and the host dies before the
# run finishes. Recovery either replays the logged decision or calls the model again. Sampling at temperature 1.0,
# 4 tickets x 3 seeds. Then: does greedy decoding give the same answer at two precisions? And what does a constant
# failure rate per hour (Ord's half-life model) say about long runs? About 1 minute.
import os, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

TICKETS = ["My order arrived damaged, but I can live with it.",
           "I was charged twice this month. Please look into it when you can.",
           "The app logs me out every few hours. Annoying, not urgent.",
           "Your courier left my parcel in the rain again. Third time."]
def ask(ticket, seed, model=llm, sample=True):
    ids = tok.apply_chat_template([{"role": "user", "content": f"Support ticket: {ticket}\nShould this ticket be escalated to a human agent? Answer yes or no."}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    torch.manual_seed(seed)
    with torch.no_grad():
        out = model.generate(ids, max_new_tokens=3, do_sample=sample, temperature=1.0 if sample else None,
                             top_p=None, top_k=None)
    return "yes" if tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip().lower().startswith("yes") else "no"

def ticket_workflow(d, ticket, seed, world):
    decision = d.act("call_llm", ask, ticket, seed)
    d.act("escalate" if decision == "yes" else "auto_close", lambda: world.append(decision) or decision)
    return decision

results = {"replay": [0, 0], "call again": [0, 0]}     # [runs where the two decisions differ, tickets both escalated and closed]
print(f"{'ticket':<44} seed  first  replay  called again")
for t_i, ticket in enumerate(TICKETS):
    for seed in range(3):
        row = []
        for mode in ("replay", "call again"):
            world = []
            path = os.path.join(tmp, f"t{t_i}_{seed}_{mode[0]}.json")
            first = ticket_workflow(Durable(path, f"tk-{t_i}"), ticket, seed, world)   # host dies right after this
            if mode == "call again":
                os.remove(path)                       # no log for the LLM call: recovery asks the model again
            again = ticket_workflow(Durable(path, f"tk-{t_i}"), ticket, seed + 100, world)
            results[mode][0] += first != again
            results[mode][1] += {"yes", "no"} <= set(world)
            row.append(again)
        print(f"{ticket[:42]:<44} {seed:>4}  {first:<5}  {row[0]:<6}  {row[1]}")
for mode, (diff, both) in results.items():
    print(f"recovery by {mode:<10}: decision changed in {diff}/12 runs; {both}/12 tickets were both escalated and auto-closed")

print("\ngreedy decoding (temperature 0), the same weights at two precisions:")
llm16 = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", torch_dtype=torch.bfloat16).eval()
same = 0
for ticket in TICKETS:
    a, b = ask(ticket, 0, llm, sample=False), ask(ticket, 0, llm16, sample=False)
    same += a == b
    print(f"   {ticket[:42]:<44} float32 {a:<4} bfloat16 {b}")
print(f"   {same}/4 agree")

print("\na constant hazard: each hour of work has the same chance of a fatal mistake (Ord 2025, on METR's tasks)")
print(f"{'half-life':<10}" + "".join(f"{f'{t} h':>8}" for t in (0.5, 1, 2, 4, 8)))
for h in (1, 4):
    print(f"{f'{h} h':<10}" + "".join(f"{0.5 ** (t / h):>8.1%}" for t in (0.5, 1, 2, 4, 8)))
p1 = 0.5 ** (1 / 4)
print(f"half-life 4 h: 1 h succeeds {p1:.0%}, 2 h {p1 ** 2:.0%}; failure goes {1 - p1:.0%} -> {1 - p1 ** 2:.0%}, "
      f"x{(1 - p1 ** 2) / (1 - p1):.2f}, not x4")

Reading this output

Replaying the logged decision never changes it. Recovery from the log gave the same decision in all 12 runs, and no ticket had two conflicting actions.

Calling the model again changed one decision. For "My order arrived damaged, but I can live with it" with seed 0, the first call said no and the ticket was auto-closed; the recovery call said yes, and the same ticket was escalated too. That is 1 of 12 here, because this model answers yes to almost every ticket. On a ticket that is a closer call, re-sampling flips the decision far more often.

Greedy decoding agreed at both precisions here. All 4 tickets got the same greedy answer in float32 and bfloat16, so this small test shows no drift. That does not make greedy output a safe replay source: a different model version, library or batch can still change it, and the log costs nothing.

The half-life table. With a 1-hour half-life an 8-hour task succeeds 0.4% of the time; with a 4-hour half-life, 25%. Doubling from 1 to 2 hours at a 4-hour half-life takes failure from 16% to 29%, a factor of 1.84, not 4.

Use it: the same idea with real libraries

code/main.py implements a minimal durable-execution engine in stdlib Python. It supports:

  • @activity decorator that logs inputs and outputs to a JSON event log.
  • A workflow function that sequences activities.
  • A run_or_replay(workflow, event_log) function that replays completed activities without re-executing them.

The driver simulates a three-activity workflow, crashes halfway through, and shows (a) a naive retry re-executing everything versus (b) a replay running only the missing activity.

The whole of code/main.py follows in parts. Each part runs on this page, in order, in one Python session; the last part does what python3 code/main.py does.

Part 1 of 4 · EventLog, activity, fetch_docs

"""Minimal durable-execution engine — stdlib Python.

Models the workflow / activity / event-log pattern used by Temporal, LangGraph
checkpointing, Microsoft Agent Framework, and Claude Code Routines.

Activities are logged with inputs before execution and outputs after. A
replay of a workflow re-runs the workflow code but returns cached outputs
for activities whose event is already in the log. A crash mid-run loses
only the incomplete activity.
"""

from __future__ import annotations

import functools
import json
import os
import tempfile
from dataclasses import dataclass


# ---------- Event log ----------

@dataclass
class EventLog:
    path: str

    def __post_init__(self) -> None:
        if not os.path.exists(self.path):
            with open(self.path, "w") as f:
                json.dump([], f)

    def events(self) -> list[dict]:
        with open(self.path) as f:
            return json.load(f)

    def append(self, ev: dict) -> None:
        evs = self.events()
        evs.append(ev)
        with open(self.path, "w") as f:
            json.dump(evs, f)

    def lookup(self, name: str, args: tuple) -> dict | None:
        for ev in self.events():
            if ev["name"] == name and ev["args"] == list(args) and ev["status"] == "done":
                return ev
        return None


# ---------- Activity decorator ----------

def activity(name: str):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(log: EventLog, *args):
            hit = log.lookup(name, args)
            if hit:
                print(f"    [replay] {name}({args}) -> {hit['result']} (from log)")
                return hit["result"]
            log.append({"name": name, "args": list(args), "status": "started"})
            result = fn(*args)
            log.append({"name": name, "args": list(args),
                        "status": "done", "result": result})
            print(f"    [run]    {name}({args}) -> {result}")
            return result
        return wrapper
    return deco


# ---------- Example activities ----------

@activity("fetch_docs")
def fetch_docs(query: str) -> int:
    # Pretend to hit an API; return number of docs.
    return len(query) * 3

@activity("call_llm")
def call_llm(doc_count: int) -> str:
    # Pretend LLM call; deterministic here for pedagogy.
    return f"summary({doc_count}_docs)"


@activity("write_report")
def write_report(summary: str) -> str:
    # Pretend tool call with a side effect.
    return f"report://{summary}"


# ---------- Workflow ----------

def workflow(log: EventLog, query: str, crash_after: int = -1) -> str:
    """Three-activity workflow with an optional crash for pedagogy."""
    doc_count = fetch_docs(log, query)
    if crash_after == 1:
        raise RuntimeError("simulated crash after fetch_docs")
    summary = call_llm(log, doc_count)
    if crash_after == 2:
        raise RuntimeError("simulated crash after call_llm")
    report = write_report(log, summary)
    return report


# ---------- Driver ----------

def reset_log(path: str) -> EventLog:
    if os.path.exists(path):
        os.remove(path)
    return EventLog(path)


def count_runs(log: EventLog) -> int:
    return sum(1 for ev in log.events() if ev["status"] == "started")

def main() -> None:
    print("=" * 70)
    print("DURABLE EXECUTION (Phase 15, Lesson 12)")
    print("=" * 70)

    tmpdir = tempfile.mkdtemp()

    # Naive retry: lose the event log on crash. Every restart re-runs
    # everything.
    print("\nNaive retry (no event log persisted)")
    print("-" * 70)
    for attempt in range(1, 4):
        log = reset_log(os.path.join(tmpdir, "naive.json"))
        print(f"  attempt {attempt}:")
        try:
            crash = 2 if attempt == 1 else -1
            r = workflow(log, "hello", crash_after=crash)
            print(f"    -> result {r}")
            print(f"    -> {count_runs(log)} activity starts this attempt")
            break
        except RuntimeError as e:
            print(f"    -> crash: {e}; {count_runs(log)} activity starts wasted")

    # Durable retry: keep the event log across attempts; replay does not
    # re-execute completed activities.
    print("\nDurable retry (event log preserved across attempts)")
    print("-" * 70)
    durable_path = os.path.join(tmpdir, "durable.json")
    if os.path.exists(durable_path):
        os.remove(durable_path)

    for attempt in range(1, 4):
        log = EventLog(durable_path)
        print(f"  attempt {attempt}:")
        try:
            crash = 2 if attempt == 1 else -1
            r = workflow(log, "hello", crash_after=crash)
            print(f"    -> result {r}")
            print(f"    -> {count_runs(log)} total activity starts across attempts")
            break
        except RuntimeError as e:
            print(f"    -> crash: {e}")

    print()
    print("=" * 70)
    print("HEADLINE: durability makes long-horizon runs affordable to fail")
    print("-" * 70)
    print("  Naive retry re-executes every activity on every attempt.")
    print("  Durable retry replays completed activities from the log;")
    print("  only the missing activity actually runs. Same design used")
    print("  by Temporal, LangGraph checkpointing, Microsoft Agent")
    print("  Framework, and Claude Code Routines. The LLM call is")
    print("  just another non-deterministic activity in the log.")

Break it on purpose

Your refund agent runs as a workflow: look up the order, ask the model whether the refund is justified, then call the payments API. The payments call times out after the money moved, the activity is retried, and the customer is refunded twice. A week later a restarted run refunds a customer the model had first refused. Using this lesson, what is missing? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Workflow engines took on agents. Temporal's OpenAI Agents SDK integration (public preview July 2025, Python now generally available) runs each model and tool call as a Temporal activity. LangGraph persists every step through a checkpointer (Postgres in production, SQLite for development) keyed by thread_id.
  • Agent platforms ship the same shape. Microsoft Agent Framework workflows checkpoint and pause on a human-input request. Cloudflare Workflows and Durable Objects give per-key durable state. The Claude Agent SDK resumes a session by its ID.
  • Scheduled runs without your laptop. Claude Code scheduled tasks (launched as Routines in April 2026) run Claude Code in Anthropic's cloud on a schedule, an API call or a GitHub event.
  • Measured run lengths are growing. Anthropic reports the longest Claude Code turns (99.9th percentile) grew from under 25 to over 45 minutes between October 2025 and January 2026.
  • On your laptop: a SQLite file is a fine event log for one machine, and this lesson's engine and model run on CPU in about a minute. Use Postgres or a hosted engine once a run must survive moving between hosts.

Sources: Temporal, OpenAI Agents SDK integration, Claude Code docs, scheduled tasks, Anthropic, Measuring agent autonomy in practice, Ord, A half-life for AI agent success rates (arXiv:2505.05115).

Recap
What to keep from this lesson
  • Wrap every model call, tool call and outside write as an activity, logged before and after it runs.
  • Key logged events by position in the workflow, and keep workflow code deterministic: clocks and random values go through the engine.
  • Give every side effect an idempotency key that the outside system checks, because a crash can land between the effect and the log.
  • On recovery, replay the logged model output; calling the model again can change a decision after you acted on it.
  • Durability saves work lost to crashes, not to mistakes: success still falls with task length, so add fresh approval on resume and a budget cap.

Given a proposed long-running agent deployment (Temporal + OpenAI Agents SDK, LangGraph with PostgreSQL checkpointer, Microsoft Agent Framework, Claude Code scheduled tasks, Cloudflare Durable Objects, or an in-house equivalent), audit the design against the durable-execution pattern.

Produce:

1. **Activity inventory.** List every activity (LLM call, tool call, HTTP request, file write). For each, confirm it is wrapped as an activity with retry policy, timeout, and idempotency key. Raw LLM calls outside the activity envelope are a reliability hole.
2. **Workflow determinism.** Identify every non-deterministic read inside the workflow code (wall clock, random, external state). Each must be registered as a side-effect activity so replay returns the same value. Hidden non-determinism is the most common cause of replay drift.
3. **Checkpoint backend.** Name the backend (PostgreSQL, SQLite, Redis, Durable Objects). Confirm it survives deploys. SQLite is dev-only. Redis requires AOF or snapshot config. Cloudflare Durable Objects are transparent but require a unique key discipline.
4. **Human-input state.** Confirm pauses for HITL are a first-class workflow state, not a polling loop. The workflow should block on an external signal (approval queue, webhook, `interrupt()` primitive) that resumes exactly when the approval arrives.
5. **HITL-on-resume policy.** For any resume after a crash, state whether fresh HITL is required before executing the next activity. Without this, durable execution plus an approval granted before the crash may re-fire an approved action when the context has changed. Critical for long horizons.

Hard rejects:
- Agent SDK usage where LLM calls are not wrapped as activities.
- Checkpoint backends that do not survive a deploy.
- Workflows that embed wall clock or random without activity wrapping.
- Human-input modeled as a polling loop rather than a signal.
- Long-horizon runs (above one hour) with no HITL-on-resume policy.
- Runs with no budget kill switch (Lesson 13) layered on top of durability.

Refusal rules:
- If the user proposes a durable workflow with no explicit idempotency on side-effect activities, refuse and require idempotency keys first. Retries will double-execute otherwise.
- If the user cannot show a replay test (run workflow, crash mid-run, replay, assert no double side effects), refuse and require that test before production.
- If the user proposes a 24-hour unattended run with no HITL checkpoint, refuse. Success falls with task length (the agent half-life in this lesson), so this is a reliability problem even if durability is correct.

Output format:

Return a design-review memo with:
- **Activity table** (activity, retry policy, timeout, idempotency key)
- **Determinism audit** (non-deterministic reads and how each is handled)
- **Checkpoint backend** (name, survives-deploy y/n, replay-test status)
- **HITL state shape** (first-class state / polling / missing)
- **HITL-on-resume policy** (explicit, with rationale)
- **Readiness** (production / staging / research-only)

Solutions

SolutionP1 · Two reports, and a poll that never finishes

Two reports. The log has fetch_docs and call_llm as done and send_report only as started, so the restart replays the first two and runs send_report again. The report was already delivered, so it goes out twice. An idempotency key per side effect, checked by the outside system, brings it back to one.

The poll returns pending every time. The lesson's lookup() matches a logged event by name and arguments, so from the second poll on it returns the first poll's result without calling the job queue. Keying events by their position in the workflow fixes it: the polls return pending, pending, done.

SolutionB1 · A refund paid twice, and a refused one paid

Two things are missing.

  • An idempotency key on the payments call. The money moved, the timeout hid that, and the retry paid again. Pass a key such as the workflow ID plus the activity's position. Payment APIs such as Stripe accept one and return the first result for a repeated key.
  • Replay of the model's decision. The restarted run called the model again instead of returning the logged decision, and the new sample approved a refund the first had refused. Model calls are activities: log the output and replay it on recovery.

It also helps to require fresh approval before a money-moving step runs after a restart, since the situation may have changed while the run was down.
