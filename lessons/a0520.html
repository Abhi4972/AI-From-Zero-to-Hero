In plain words first
The idea in one line

Ask an LLM for JSON. Get JSON most of the time. In production, "most" is the problem. Constrained decoding turns "most" into "always" by editing the logits before sampling.

The problem

In plain words first

A program that calls a language model usually needs an answer in a fixed shape: one of three labels, a date in YYYY-MM-DD form, a JSON object with certain fields. Asking politely in the prompt usually works and sometimes does not, and "sometimes does not" breaks software. Constrained decoding makes invalid output impossible. At every step the model proposes scores for every possible next token, and a small checker sets the score of every token that would break the required format to minus infinity, so only allowed tokens can be chosen. This lesson writes the masking rule and shows why it also subtly changes the model's probabilities. It then builds a label constraint and a date-format constraint from scratch on GPT-2, counts how many output tokens a JSON template fixes in advance (the reason constrained decoding can be faster), and covers the libraries and vendor APIs that do this in production.

A classifier prompts an LLM: "Return one of {positive, negative, neutral}." The model returns "The sentiment is positive — this review is overwhelmingly favorable because the customer explicitly states that they ...". Your parser crashes. Your classifier's F1 is 0.0.

Free-form generation is not a contract. It is a suggestion. A production system needs a contract.

Three layers exist in 2026.

  1. Prompting. Ask nicely. "Return only the JSON object." Works most of the time on frontier models and noticeably less often on small ones; "most of the time" is the problem for software that must parse every reply.
  2. Native structured output APIs. OpenAI response_format, Anthropic tool use, Gemini JSON mode. Reliable on supported schemas. Vendor-locked.
  3. Constrained decoding. Modify the logits at every generation step so the model cannot emit invalid tokens. 100% valid by construction. Works on any local model.

This lesson builds intuition for all three and names when to reach for which.

The idea

How constrained decoding works. At each generation step, the LLM produces a logit vector over the full vocabulary (~100k tokens). A logit processor sits between the model and the sampler. It computes which tokens are valid given the current position in the target grammar — JSON Schema, regex, context-free grammar — and sets the logits of all invalid tokens to negative infinity. The softmax over the remaining logits puts probability mass only on valid continuations.

Implementations in 2026:

  • Outlines. Compiles JSON Schema or regex into a finite-state machine. Every token gets an O(1) valid-next-token lookup. FSM-based, so recursive schemas need flattening.
  • XGrammar / llguidance. Context-free grammar engines. Handle recursive JSON Schema. Near-zero decoding overhead. llguidance's maintainers report that it has powered OpenAI's JSON-Schema structured outputs since May 2025.
  • vLLM guided decoding. Built-in guided_json, guided_regex, guided_choice, guided_grammar via Outlines, XGrammar, or lm-format-enforcer backends.
  • Instructor. Pydantic-based wrapper over any LLM. Retries on validation failure. Cross-provider, but does not modify logits — it relies on retries + structured-output-aware prompts.

Idea 1 · The counterintuitive result

Constrained decoding is often faster than unconstrained generation. Two reasons. First, it shrinks the next-token search space. Second, clever implementations skip token generation entirely for forced tokens (scaffolding like {"name": " — every byte is determined).

Idea 2 · The pitfall that costs you

Field order matters. Put answer before reasoning, and the model commits to an answer before it thinks. JSON is valid. Answer is wrong. No validation catches it.

// BAD
{"answer": "yes", "reasoning": "because ..."}

// GOOD
{"reasoning": "... therefore ...", "answer": "yes"}

Schema field order is logic, not formatting.

The same idea as a formula

Masking. Let ℓt​∈R∣V∣ be the model's logits at step t and At​⊆V the tokens allowed by the grammar in its current state. Constrained decoding samples from

p′(yt​=v∣y<t​)=∑u∈At​​exp(ℓt,u​)exp(ℓt,v​)1[v∈At​]​

i.e. it sets the logits outside At​ to −∞ and renormalises over what is left.

From characters to tokens. Grammars are written over characters (a regex, a JSON Schema), but models emit tokens of several characters. For a finite-state automaton with states Q, a token v is allowed in state q if feeding all of v's characters keeps the automaton on a path that can still reach acceptance. Outlines precomputes this for every (state, token) pair once, so each step is a lookup; context-free grammars (recursive JSON) need a stack, which XGrammar and llguidance handle with precomputed masks for most tokens and runtime checks for the rest.

It changes the distribution. Masking step by step is not the same as sampling from the model's distribution restricted to valid outputs, p(y∣y∈L)∝p(y)1[y∈L]. Local renormalisation gives prefixes that are cheap now but lead to few valid continuations more weight than they deserve (Park et al., 2024, "Grammar-Aligned Decoding"). For short outputs and grammars that rarely trap the model this distortion is small; it is one reason to keep grammars permissive.

Forced tokens. When ∣At​∣=1 the next token is determined, so no model call is needed for it: the decoder can emit the scaffold of a JSON object ({"sentiment": ") without running the network.

Worked example
How masking distorts probabilities

A model must output a two-letter code that is either "ab" or "ba". Its unconstrained probabilities for the first letter are P(a)=0.6, P(b)=0.1 (and 0.3 for other letters); after "a" it gives P(b∣a)=0.05 (it mostly wanted "ac", "ad"…), after "b" it gives P(a∣b)=0.9.

  • Sequence probabilities under the model: P(ab)=0.6×0.05=0.03, P(ba)=0.1×0.9=0.09. Restricted to the valid set, the model prefers "ba": 0.09/0.12=0.75.
  • Step-by-step masking: first letter, allowed {a, b}: P′(a)=0.6/0.7=0.857, P′(b)=0.143. Second letter: only one option each, probability 1.
  • So constrained decoding outputs "ab" 86% of the time, although the model itself rates "ba" three times more likely.

The mask fixed the format and quietly reversed the model's preference. Exact approaches (resampling, or the grammar-aligned decoding of Park et al.) correct for this at extra cost.

Check your mental model
  • ✗ "Constrained decoding makes the model's answer correct."
    ✓ It makes the answer well-formed. A valid date can be the wrong date.
  • ✗ "Masking is neutral: it only removes invalid options."
    ✓ Renormalising at each step can change which valid output is most likely, as the worked example shows.
  • ✗ "JSON mode is enough."
    ✓ Plain JSON mode guarantees syntax, not your fields, types or allowed values; pass a full schema.

Step 1 · regex-constrained generation from scratch

See code/main.py for a standalone FSM implementation. The core idea in 30 lines:

def mask_logits(logits, valid_token_ids):
    mask = [float("-inf")] * len(logits)
    for tid in valid_token_ids:
        mask[tid] = logits[tid]
    return mask


def generate_constrained(model, tokenizer, prompt, fsm):
    ids = tokenizer.encode(prompt)
    state = fsm.initial_state
    while not fsm.is_accept(state):
        logits = model.next_token_logits(ids)
        valid = fsm.valid_tokens(state, tokenizer)
        logits = mask_logits(logits, valid)
        tok = sample(logits)
        ids.append(tok)
        state = fsm.transition(state, tok)
    return tokenizer.decode(ids)

The FSM tracks what parts of the grammar we have satisfied so far. valid_tokens(state, tokenizer) computes which vocabulary tokens can advance the FSM without leaving an accepting path.

Step 2 · Outlines for JSON Schema

from pydantic import BaseModel
from typing import Literal
import outlines


class Review(BaseModel):
    sentiment: Literal["positive", "negative", "neutral"]
    confidence: float
    evidence_span: str


model = outlines.models.transformers("meta-llama/Llama-3.2-3B-Instruct")
generator = outlines.generate.json(model, Review)

result = generator("Classify: 'The wait staff was attentive and the food arrived hot.'")
print(result)
# Review(sentiment='positive', confidence=0.93, evidence_span='attentive ... hot')

Zero format errors: the automaton makes invalid output unreachable. The content can still be wrong (a confident but incorrect label, an invented date), as the experiments under "Use it" show. Note also that this listing uses the Outlines 0.x API; Outlines 1.0 (2025) replaced outlines.models.transformers and outlines.generate.json with outlines.from_transformers(...) and a Generator that takes the Pydantic model as its output type.

Step 3 · Instructor for provider-agnostic Pydantic

import instructor
from anthropic import Anthropic
from pydantic import BaseModel, Field


class Invoice(BaseModel):
    vendor: str
    total_usd: float = Field(ge=0)
    line_items: list[str]


client = instructor.from_anthropic(Anthropic())
invoice = client.messages.create(
    model="claude-sonnet-5-5",
    max_tokens=1024,
    response_model=Invoice,
    messages=[{"role": "user", "content": "Extract from: 'Acme Corp $420. Widget, Gizmo.'"}],
)

Different mechanism. Instructor does not touch logits. It formats the schema into the prompt (or into the provider's tool-calling interface), parses the output, and retries with the validation error on failure, up to max_retries times. Works with any provider. Retries add latency and cost. Cross-provider portability is the selling point.

Server-side constrained decoding. Reliability parity with Outlines for supported schemas. No local model management. Locks you to the vendor.

See it drawn
Constraining GPT-2 to three labels

GPT-2 small (124M parameters, a base model with no instruction tuning) completes a classification prompt. Free decoding is compared with decoding constrained by the lesson's mask_logits to the token sequences of " positive", " negative" and " neutral" (a prefix tree over GPT-2 tokens).

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM
torch.set_num_threads(2)
gtok = AutoTokenizer.from_pretrained("gpt2")
gpt2 = AutoModelForCausalLM.from_pretrained("gpt2").eval()

def next_logits(ids):
    with torch.no_grad():
        return gpt2(torch.tensor([ids])).logits[0, -1]

labels = [" positive", " negative", " neutral"]
label_ids = [gtok.encode(l) for l in labels]
def constrained_label(prompt):
    ids, out = gtok.encode(prompt), []
    logp_total = 0.0
    while True:
        live = [l for l in label_ids if l[:len(out)] == out]
        if any(l == out for l in live):
            return gtok.decode(out).strip(), logp_total
        valid = {l[len(out)] for l in live}
        logits = next_logits(ids + out)
        masked = torch.tensor(mask_logits(logits.tolist(), valid))
        tok = int(masked.argmax())
        logp_total += torch.log_softmax(masked, -1)[tok].item()
        out.append(tok)

def free(prompt, n=12):
    ids = gtok.encode(prompt)
    with torch.no_grad():
        g = gpt2.generate(torch.tensor([ids]), max_new_tokens=n, do_sample=False, pad_token_id=gtok.eos_token_id)
    return gtok.decode(g[0, len(ids):])

reviews = [("The food arrived cold and the waiter ignored us.", "negative"), ("Absolutely wonderful evening, the staff were lovely.", "positive"),
           ("The restaurant opens at six and closes at eleven.", "neutral"), ("Worst film I have seen this year.", "negative"),
           ("A delightful, funny and moving book.", "positive")]
for text, gold in reviews:
    prompt = f"Review: {text}\nSentiment (positive, negative or neutral):"
    lab, lp = constrained_label(prompt)
    print(f"{text[:48]:50s} free: {free(prompt)!r:42s} constrained: {lab:8s} (gold {gold})")
print("tokens per label:", {l.strip(): len(t) for l, t in zip(labels, label_ids)})

Reading this output

Free decoding does what a base model does with an unfinished document: it continues it. Not one of the five free outputs is a label; most start a new line of imagined chat ("I'm not sure what to say…"), which a parser would reject. Constrained decoding always returns one of the three labels, by construction (each happens to be a single GPT-2 token, so the constraint is one masked step). Whether the label is right is a different matter: GPT-2 small gets 3 of 5, calling a complaint about cold food and a plain statement of opening hours "positive". Format and correctness are separate problems; constrained decoding solves only the first, and an instruction-tuned model, or a classifier, is what solves the second.

See it drawn
A date format from a regular expression

A character-level constraint lifted to tokens, as the formula box describes: a GPT-2 token is allowed if the text so far plus that token is still a valid prefix of the pattern \d{4}-\d{2}-\d{2} (checked with the regex module's partial matching), and generation stops when the whole pattern matches. The same is done with a permissive pattern that also allows the word "unknown".

import regex
vocab_strings = [gtok.decode([i]) for i in range(len(gtok))]
def constrained_by_pattern(prompt, pattern, max_tokens=12):
    ids, text = gtok.encode(prompt), ""
    for _ in range(max_tokens):
        valid = [i for i, s in enumerate(vocab_strings) if s and regex.fullmatch(pattern, text + s, partial=True)]
        logits = next_logits(ids)
        tok = int(torch.tensor(mask_logits(logits.tolist(), valid)).argmax())
        ids.append(tok); text += vocab_strings[tok]
        if regex.fullmatch(pattern, text):
            return text
    return text + " (stopped)"

DATE = r"\d{4}-\d{2}-\d{2}"
DATE_OR_UNKNOWN = r"(\d{4}-\d{2}-\d{2}|unknown)"
for q in ["Apollo 11 landed on the Moon on (YYYY-MM-DD):", "The Eiffel Tower opened to the public on (YYYY-MM-DD):",
          "My neighbour's cat was born on (YYYY-MM-DD):"]:
    print(f"{q:58s} strict: {constrained_by_pattern(' ' + q, DATE):12s} permissive: {constrained_by_pattern(' ' + q, DATE_OR_UNKNOWN)}")
print("true dates: Apollo 11 landing 1969-07-20; Eiffel Tower public opening 1889-05-15")

Reading this output

Every output matches the pattern, and that is all the constraint guarantees. GPT-2 small produces "1123-10-10" for the Moon landing (true: 1969-07-20) and "0000-00-00" for the Eiffel Tower (true: 1889-05-15). The third output, "1123-10-91", matches \d{4}-\d{2}-\d{2} and is not a date at all: day 91 does not exist. A regular expression describes characters, not meaning, so a schema needs semantic checks (a real date parser, value ranges) after decoding, or a grammar that encodes the ranges (month 01 to 12, day 01 to 31). The cat question has no knowable answer, yet the strict pattern forces a date: the "grammar too strict" pitfall below. Allowing "unknown" did not help here, because the model still preferred digits; leaving room for "I don't know" in the schema is necessary, not sufficient.

How much of a JSON answer is already decided?

For a small schema, the scaffold text a JSON object must contain (braces, keys, quotes, separators) is known before the model runs. Tokenized with GPT-2's tokenizer, what share of a typical answer's tokens is forced?

import json as _json
answers = [{"sentiment": "positive", "confidence": 0.93, "evidence_span": "attentive and hot"},
           {"sentiment": "negative", "confidence": 0.71, "evidence_span": "cold"},
           {"sentiment": "neutral", "confidence": 0.55, "evidence_span": "opens at six"}]
for a in answers:
    full = _json.dumps(a)
    free_parts = [str(a["confidence"]), a["evidence_span"]]
    n_free = sum(len(gtok.encode(p)) for p in free_parts) + 1          # +1: choosing among the three labels
    n_all = len(gtok.encode(full))
    print(f"{n_all:2d} tokens, of which about {n_all - n_free:2d} ({(n_all - n_free) / n_all:.0%}) are fixed by the schema:  {full}")

Reading this output

Most of each answer's tokens are scaffold: braces, key names, quotes, the colon and comma separators, and once the first letters of a label are chosen, the rest of the label. A decoder that knows the schema can emit those tokens without running the model, which is how constrained generation can be faster than free generation, as Idea 1 claims. (Exact counts depend on how a tokenizer splits the scaffold, and real engines also batch forced tokens into one forward pass.)

Industry practice
What's current (2024–2026)
  • Grammar engines got fast and standard. XGrammar and llguidance reduce per-token masking cost to microseconds for most tokens; XGrammar is the default structured-output backend in vLLM and SGLang, llguidance has powered OpenAI's JSON-Schema structured outputs since May 2025, and Outlines remains a common library.
  • Every major API offers schemas. OpenAI's structured outputs, Gemini's response schemas and Anthropic's structured outputs and strict tool use accept a JSON Schema and constrain decoding server-side; plain "JSON mode" is now the weak option.
  • Design advice from practice. Forcing rigid formats can hurt answers on reasoning-heavy tasks, so "put a reasoning field first" and permissive schemas are standard advice.

Sources: XGrammar, llguidance, OpenAI structured outputs, Outlines.

Pitfalls

  • Recursive schemas. Outlines flattens recursion to a fixed depth. Tree-structured outputs (nested comments, AST) need XGrammar or llguidance (CFG-based).
  • Huge enums. 10,000-option enum compiles slowly or times out. Switch to a retriever: predict top-k candidates first, constrain to those.
  • Grammar too strict. Force date: "YYYY-MM-DD" regex and the model cannot output "unknown" for missing dates. Model compensates by inventing a date. Allow null or a sentinel.
  • Premature commitment. See field-order pitfall above. Always put reasoning first.
  • Vendor JSON mode without schema. Pure JSON mode only guarantees valid JSON, not valid for your use case. Always provide a full schema.

Recap
What to keep from this lesson
  • Three layers: prompting (usually works), vendor schema APIs (reliable, vendor-specific), constrained decoding (valid by construction, any local model).
  • Constrained decoding sets disallowed logits to −∞ at every step; character grammars are lifted to tokens by precomputed automaton tables.
  • Masking guarantees format, not correctness, and can shift which valid output is most likely.
  • Forced scaffold tokens can be emitted without model calls, so constraints can speed generation up.
  • Keep schemas permissive (allow null or "unknown") and put reasoning fields before answer fields.

Solutions

SolutionP1 · Freely, never; constrained, always valid, right 3 times out of 5

A base model continues text rather than obeying it: none of the five free outputs was a bare label. Constrained decoding always returned one of the three words, by construction, but GPT-2 small labelled a complaint about cold food and a neutral statement of opening hours as "positive". Format and correctness are separate guarantees.

SolutionB1 · It can only emit forbidden tokens

With the mask inverted, every token the grammar allows gets −∞ and every token it forbids keeps its logit, so the sampler picks a token that breaks the format at the very first step. The automaton's transition then has no valid move: depending on the implementation it raises an error, gets stuck in a dead state, or keeps going while the output drifts arbitrarily far from the grammar. Unit-test a constraint by checking that every token it allows really advances the automaton, and that it allows at least one token in every reachable non-final state.

Debug a failureA classifier uses constrained decoding with a schema of two fields, answer and reasoning, in that order. The output is always valid JSON and the accuracy is worse than the free-text version was. What is wrong?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The field order. The model commits to the answer before it writes any reasoning, so the reasoning tokens never shape the answer, and you lose the gain that step-by-step gives. Put reasoning first and answer last; the schema stays valid, and no validator will ever flag the difference, because the order is logic and not formatting.

The pitfall.

The constrained decoding lesson calls it the pitfall that costs you. With answer first, the model writes the decision token at the first position where the grammar allows it, and the reasoning that follows is a story about a choice already made. With reasoning first, the chain comes before the decision, and the decision token is conditioned on it. Both documents validate. Only one is right.

The lesson's skill refuses any design that puts an answer or decision field before the reasoning fields.

Neighbors of the same mistake.

Schema choice What goes wrong Fix
A strict pattern for a value that can be missing, such as a date the model invents a value to satisfy the grammar allow null or a sentinel
A field left optional that matters the model omits it when it is inconvenient make it required and allow null, so the absence is explicit
Nesting four levels deep or more each level is one more place to lose the structure flatten
An enum with thousands of options the grammar compiles slowly or times out predict a short list of candidates first, then constrain to it

Why the unconstrained reply did better.

A free-text reply tends to explain before it concludes, so it had the chain by accident. The constrained schema removed it. The fix restores it on purpose.

Plausible wrong answers.

  • "Constrained decoding guarantees a correct output." It guarantees the shape; the lesson shows valid JSON with a wrong answer.
  • "Order does not matter in JSON." It does not matter to the parser; it matters to the model, which writes the fields in order.
  • "Add a check that the reasoning supports the answer." That is an eval, not a fix; the fix is to generate the reasoning first.

Follow-ups an interviewer may ask.

  • (level 2) Why can no validator catch this? Expected: both orders are valid against the schema; the harm is in what the model has seen when it writes the answer token.
  • (level 2) The schema forces a date pattern and the model fills in dates that are not in the text. Which related mistake is that? Expected: a grammar too strict for missing data; allow null or a sentinel so the model does not invent a value.
  • (level 3) A field is optional and the model leaves it out when it matters. What do you change? Expected: make it required and allow null, so the model has to state that the value is missing.
  • (level 3) The schema nests four levels deep and errors rise. What do you do? Expected: flatten, because each level of nesting is one more place to lose track of the structure.

Defend a designDesign the extraction service for purchase-order emails. The input is free text; the output is a typed record with a customer, line items and a total. Cover the schema, the enforcement mode, the retry and refusal handling, and how you prove it works before it touches the accounting system.

Level 3 of 4 · about 20 minutes to answer well.

Short answer. Write one JSON Schema 2020-12 with the constraints that matter: required fields, enums for closed sets, a minimum of zero on the total, additional properties forbidden, and any reasoning field ahead of any decision field. Run it in the provider's strict schema mode so that a response that finishes cannot have a parse error or a schema violation, check the stop reason so that a response cut at the token limit goes to the error path, and treat a refusal as a typed outcome that goes to a review queue. Prove it with a labeled set of real emails scored per field, a refusal check on inputs that must not extract, and a run beside the human process before any record is written.

The schema.

  • type, properties and required for the shape; every property listed as required, with null allowed where the source can lack a value.
  • enum for closed sets such as currency or status; minimum on the total; pattern, minLength and maxLength on identifiers; items for the line items.
  • additionalProperties: false everywhere, which blocks invented fields and which strict mode demands.
  • Field order as logic: any reasoning field before total or status, because the model commits to the first field it writes.

In Python, a Pydantic model generates this schema; the service keeps the schema as the contract and the model as its binding.

The enforcement mode.

Situation Pick
A hosted frontier model, a flat schema the provider's strict schema mode
Several providers, retries acceptable a retry library over the Pydantic model, which is portable and does not touch logits
A local model, validity required a grammar engine, finite state for a flat schema and context-free for a recursive one

Strict mode is the default here: a finished output parses and validates by construction. Two failures remain: the refusal, and a response cut at the token limit, which can still fail to parse. Check the stop reason before you read the output, and send an incomplete response to the error path.

Retry and refusal.

Outside strict mode: generate, parse, validate, inject the typed errors and retry, at most three times. More than three means the schema or the prompt is wrong for some inputs. In every mode: a refusal is a first-class outcome with a reason attached. Log it, return it typed, send it to the review queue, and never retry it, because forcing a record on an input that does not fit produces an invented record.

Proof before accounting sees a record.

  1. A labeled set of real emails with gold records; the structured outputs lesson uses 50 documents. Report exact match, accuracy per field and type compliance.
  2. A refusal check. Construct inputs that must not extract, such as a lyric, a proof or a blank email, and count refusals against invented outputs.
  3. A confidence per field from repeated extraction or token probabilities, with low-confidence records routed to a human.
  4. A schema version on every record, and a schema diff that separates breaking changes from non-breaking ones before any deploy.
  5. A side-by-side run against the human process on the labeled set, with the service writing nothing until the field-level numbers clear the bar you set with finance.

Plausible wrong answers.

  • "Prompt for JSON and parse it, the model is good." That works 85 to 95 percent of the time and fails six different ways; accounting needs the contract.
  • "Retry refusals until the model gives a record." A refusal says the input does not fit; forcing a record invents one.
  • "Validation after generation is as good as strict mode." It is reliable but pays for every retry, and a truncated output costs a turn each time.

Follow-ups an interviewer may ask.

  • (level 3) Why forbid additional properties? Expected: it blocks invented fields, and strict mode requires it everywhere.
  • (level 3) You expect to switch providers next year. Which mode do you pick? Expected: a retry library over the Pydantic model for portability, or keep the schema identical across providers so each strict mode receives the same contract.
  • (level 4) How do you version the schema once records exist? Expected: a version field on each record and a schema diff that separates breaking changes from non-breaking ones. Strict mode makes every field required, so an added field is breaking too, because the records written before it do not contain it; removed fields and changed types are breaking, and relaxed constraints are not.
  • (level 4) Which failure can this design not remove, and where does it go? Expected: a wrong value with the right type; it goes to the field-level eval and the confidence flags, and the low-confidence records go to review.

Level 1 of 4 · about 6 minutes to answer well.

Short answer. JSON mode guarantees that a finished output parses, nothing more; a response cut at the token limit can still fail, so check the finish reason first. It does not guarantee your keys, your types, your enum values or the absence of extra fields. Turn on the schema mode, where the provider takes a JSON Schema and constrains decoding to it, and keep a check on your side for the values that a schema cannot judge.

Four levels of control.

Level Guarantee Typical failure
A prompt that says "respond in JSON" none; about 90 percent valid code fences, preamble text, truncation, wrong structure
JSON mode valid syntax extra keys, wrong types, missing fields
Schema mode the output conforms to your schema a wrong value with the right type, or a refusal
Constrained decoding every token is valid for the schema the same as schema mode; this is how schema mode is built

The constrained decoding lesson is blunt about it: pure JSON mode guarantees valid JSON, not JSON that is valid for your use case, so always provide a full schema.

What strict schema mode asks of you.

The structured output lesson lists the strict mode rules: every property appears in required, additionalProperties is false everywhere, and there is no unresolved reference. A schema that breaks these is rejected at request time with a 400.

What stays with you.

Under strict enforcement two failures disappear for a response that finishes, the parse error and the schema violation. A response cut at the token limit can still fail to parse, so check the finish reason before you read it. Two more remain. The model can refuse when the input does not fit the schema, which your code treats as a typed outcome. And the model can fill a field with a value that has the right type and the wrong content; no format layer sees that.

Plausible wrong answers.

  • "JSON mode means the keys match my model." It only guarantees syntax; extra keys, wrong types and missing fields still happen.
  • "Adding 'respond in valid JSON' to the prompt is the same thing." A prompt-only approach is about 90 percent reliable and fails with fences, preambles and truncation.
  • "With schema mode I can drop validation." A schema cannot catch a wrong value with the right type; keep a semantic check.

Explain what the mask does to the probabilities, what the machine's state records, and why the loop can end up faster than unconstrained generation. python def mask_logits(logits, valid_token_ids): mask = [float("-inf")] * len(logits) for tid in valid_token_ids: mask[tid] = logits[tid] return mask def generate_constrained(model, tokenizer, prompt, fsm): ids = tokenizer.encode(prompt) state = fsm.initial_state while not fsm.is_accept(state): logits = model.next_token_logits(ids) valid = fsm.valid_tokens(state, tokenizer) logits = mask_logits(logits, valid) tok = sample(logits) ids.append(tok) state = fsm.transition(state, tok) return tokenizer.decode(ids)

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The mask sets the logit of every invalid token to negative infinity, so after the softmax those tokens carry zero probability and the sampler can only pick a token that keeps the output inside the grammar. The machine keeps the position in the grammar reached so far, and valid_tokens returns the tokens that advance it without leaving an accepting path. It can be faster because the search space shrinks, and because a position where only one token is valid needs no model call at all.

Walk the loop.

  1. Encode the prompt and start the machine in its initial state.
  2. Until the machine accepts: ask the model for the logits of the next token over the whole vocabulary.
  3. Ask the machine which token ids are valid in the current state.
  4. Replace every other logit with negative infinity; the valid ones keep their value.
  5. Sample from the masked logits, append the token, and move the machine to the next state.
  6. Decode the ids.

The piece between the model and the sampler is the logit processor. Nothing in the model changes; the edit is to one step's logits.

Where the valid set comes from.

A compiled grammar. A finite state machine built from a regex or a JSON Schema gives a constant-time lookup of the valid tokens per state. A context-free grammar engine handles recursion that a finite machine cannot express. Inference servers ship the same idea as guided decoding, with JSON, regex, choice and grammar modes.

Why it can run faster.

Two reasons from the lesson. The next-token search space shrinks. And a clever implementation skips the model call for forced tokens: when the grammar leaves exactly one valid token, such as the scaffolding of a key name, the token is appended without generation. This code does not do that yet.

What this code does not fix.

A grammar that is too strict makes the model invent a value, because no valid token lets it say unknown. A huge enum compiles slowly. A recursive schema does not fit a finite machine. And a retry library that validates after generation does none of this; it never touches the logits.

Plausible wrong answers.

  • "The mask changes the model's weights." It changes nothing in the model; it edits the logits of one step before sampling.
  • "Constrained decoding always slows generation down." The lesson calls it often faster: a smaller search space, and forced tokens that skip the model call.
  • "A retry library does the same thing." It formats the schema into the prompt and validates after the fact; it does not touch the logits.

Follow-ups an interviewer may ask.

  • (level 2) Where does valid_tokens get its answer? Expected: from the compiled grammar; a finite state machine gives a constant-time lookup per state.
  • (level 2) What does a production implementation do that this loop does not? Expected: skip forced tokens; when exactly one token is valid it is appended without a model call.
  • (level 3) Which schemas defeat a finite state machine? Expected: recursive ones, such as nested comments or a syntax tree, which need a context-free grammar engine.
  • (level 3) The grammar forces a strict date pattern and the source has no date. What does the loop produce? Expected: a well-formed invented date, because no valid token lets the model say unknown; allow null or a sentinel in the grammar.

Explain the mechanismA classifier prompt asks for one of three labels and the model answers with a paragraph, so the parser crashes. Three layers of fix exist. Explain how the strongest one works at the level of the logits, and why it is often faster than free generation, not slower.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Prompting asks nicely, a vendor's structured-output API does it on the server, and constrained decoding does it locally by editing the logits. At each step a logit processor computes which vocabulary tokens can advance the target grammar, a JSON schema, a regex or a context-free grammar compiled to a state machine, and sets every other logit to minus infinity, so the softmax puts probability only on valid continuations and an invalid output is unreachable. It can be faster because the search space shrinks and because tokens that the grammar forces, such as a fixed key name, are emitted without a model step.

The three layers.

  1. Prompting. "Return only the JSON object." The lesson puts this at about 80 percent compliance on strong models and lower on small ones. Not a contract.
  2. Native structured output. The provider runs the constraint on its side. Reliable for supported schemas; locked to that provider.
  3. Constrained decoding. The constraint runs in your own decoding loop and works with any local model.

The loop.

def generate_constrained(model, tokenizer, prompt, fsm):
    ids = tokenizer.encode(prompt)
    state = fsm.initial_state
    while not fsm.is_accept(state):
        logits = model.next_token_logits(ids)
        valid = fsm.valid_tokens(state, tokenizer)
        logits = mask_logits(logits, valid)
        tok = sample(logits)
        ids.append(tok)
        state = fsm.transition(state, tok)
    return tokenizer.decode(ids)

The state machine tracks how much of the grammar is satisfied. valid_tokens returns the vocabulary tokens that keep the machine on an accepting path; the mask sets the rest to minus infinity. The vocabulary is about 100k tokens, so the mask is computed per state ahead of time.

State machine or grammar engine.

A regex or a flat JSON schema compiles to a finite-state machine with a constant-time lookup of valid tokens per state. Recursive schemas, nested comments or a syntax tree, need a context-free grammar engine, which handles recursion at near-zero decoding overhead in current implementations. Inference servers expose both as guided decoding.

Why it can be faster.

Fewer candidate tokens means a smaller effective search at each step. More important, long stretches of the output are fully determined by the grammar: the opening brace, a quoted key, the colon. A good implementation skips the model for those tokens and only calls it where the grammar leaves a choice.

The library that does not touch logits.

A retry-based client formats the schema into the prompt, parses the output, and retries on a validation failure, 3 times by default. It works across providers, and each retry costs latency and money. It is a different mechanism, not a weaker version of the same one.

Plausible wrong answers.

  • "Constrained decoding makes the answer correct." It makes the answer valid for the grammar; a well-formed wrong answer still passes.
  • "Checking the grammar at every token makes generation slower." The valid-token sets are precomputed per state, and forced tokens skip the model, so it is often faster.
  • "Enough examples in the prompt reach full compliance." The lesson's figure for prompting alone is about 80 percent; a contract needs the logits or the server.

Follow-ups an interviewer may ask.

  • (level 2) When does a finite-state machine not suffice? Expected: for recursive schemas; the machine flattens recursion to a fixed depth, and a context-free grammar engine is needed.
  • (level 3) What does a provider's plain JSON mode guarantee, and what does it not? Expected: valid JSON syntax, not conformance to your schema; always send a full schema.
  • (level 3) How does the retry library differ from the logit processor? Expected: it never changes the model's distribution; it validates after the fact and retries, which adds latency and cost per failure.
  • (level 4) The schema has an enum with 10,000 options and compilation times out. What do you do? Expected: predict a short list of candidates with a retriever first, then constrain the decode to those.

Where it is taught. The structured outputs lesson builds the logit processor and compares the three layers.

Defend a designYou review the schema of an extraction service. It is {"answer": ..., "reasoning": ..., "date": <a strict year-month-day regex>}, enforced by constrained decoding. Compliance is perfect, yet accuracy is poor and some dates are invented. What is wrong with the design, and how do you change it?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Two faults that no validator can catch. The answer field comes before the reasoning field, so the model commits to an answer before it has reasoned, and the strict date pattern leaves no legal way to say unknown, so the model complies by inventing a date. Put reasoning first and the answer last, and allow a null or a sentinel for a missing date; field order is logic, not formatting, and a grammar that is too strict forces a confident wrong value.

Fault one: premature commitment.

Generation is left to right. With answer first, the model must emit the label before it has written a single word of analysis; the reasoning that follows is a justification of a choice already made. Swap the order and the model writes its analysis into the context that the answer is then conditioned on. The JSON is equally valid either way. Only the second way is correct.

{"reasoning": "... therefore ...", "answer": "yes"}

Fault two: a grammar with no exit.

The date regex admits only well-formed dates. When the source has no date, the model cannot output "unknown", and a mask that forbids every honest token leaves only dishonest ones. Allow null or a sentinel string in the schema and instruct the model to use it.

The other pitfalls to check in the same review.

  • Recursive schemas behind a state-machine library. The machine flattens recursion to a fixed depth; nested structures need a context-free grammar engine.
  • Huge enums. An enum of 10,000 options compiles slowly or times out; narrow the candidates with a retriever first, then constrain to those.
  • Plain JSON mode without a schema. It guarantees syntax, not your fields.

The validation plan that would have caught it.

Compliance rate is one number of four. Add semantic validity, measured with a judge or a labeled set, the field coverage rate, and latency at p50 and p99. A system with perfect compliance and poor semantic validity is exactly this case.

The rule for the team.

Refuse any schema that puts answer or decision before its reasoning fields. Refuse bare JSON mode without a schema. Flag any recursive schema that sits behind a state-machine-only library.

Plausible wrong answers.

  • "Tighten the regex so only plausible dates pass." The grammar is already the problem; a tighter one forces more invention.
  • "Add a line to the prompt asking the model to be honest." The mask forbids the honest tokens; no instruction can make the model emit a token with minus infinity logit.
  • "Validation passes, so the system works." Validation checks shape; it cannot see that the answer was committed before the reasoning or that a date was made up.

Follow-ups an interviewer may ask.

  • (level 3) How do you measure semantic validity when compliance is already perfect? Expected: a labeled sample scored by a judge or by rules on the content, tracked separately from schema compliance.
  • (level 3) The output needs a tree, such as nested comments. What changes? Expected: a state-machine library flattens recursion; move to a context-free grammar engine.
  • (level 4) The product streams the answer to the user and wants it first for latency. How do you resolve the conflict? Expected: name the trade; options are two calls, reasoning in a hidden field before a visible answer, or accepting the latency; never answer-first with the same accuracy expectation.
  • (level 4) How would the invented dates have shown up in monitoring? Expected: a field coverage rate near 100 percent on a corpus where the date is often missing is itself the alarm; compare the rate with the base rate of the field in the source.
