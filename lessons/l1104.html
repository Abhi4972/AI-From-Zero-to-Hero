Why this came about

Teams found that improving data improved models and systems more than most other changes. The data flywheel, using production feedback to build better datasets that improve the system, became a central practice for AI products.

In plain words first
Better data beats more data

The data you train or evaluate on decides what you get. Curation means collecting relevant examples, cleaning them, removing duplicates and sensitive data, labeling carefully, and balancing hard and easy cases. The data flywheel is the production loop that keeps improving it: production traces and user feedback reveal failures, failures become labeled examples, examples improve prompts, evaluations or models, and the cycle repeats.

The flywheel

Every production run is data. The data flywheel turns it into improvement: log traces with feedback → mine failures and good examples → label (people and calibrated judges) → grow the eval set → fix with prompts, tools and retrieval, or train → release through the eval gate → repeat. Most loops end at "fix with prompts and tools". Training is for the cases that remain.

Step 1 · From traces to a dataset

Your tracing store already holds what a training set needs: real inputs, the outputs your system gave, and signals about which outputs were good (user feedback, eval results). The code turns five traces into training examples in four moves: keep only the ones that passed, remove near-duplicates, mask personal data, and write the result in the chat format that fine-tuning services accept, with a pointer back to the trace each example came from.

import hashlib, json, random, re

TRACES = [   # what your tracing store holds: input, output, tool calls, feedback, eval verdict
    {"id": "t1", "input": "Where is A-1001?", "output": "A-1001 has shipped.", "feedback": 1, "eval_pass": True},
    {"id": "t2", "input": "where is A-1001 ?", "output": "A-1001 has shipped.", "feedback": 1, "eval_pass": True},
    {"id": "t3", "input": "Cancel A-1002, my number is 9876543210", "output": "A-1002 is cancelled.", "feedback": 1, "eval_pass": True},
    {"id": "t4", "input": "Do you sell insurance?", "output": "Yes, from Rs 499!", "feedback": 0, "eval_pass": False},
    {"id": "t5", "input": "Refund for a broken mixer?", "output": "Damaged items are refundable within 30 days.", "feedback": None, "eval_pass": True},
]
PHONE = re.compile(r"(?<!\d)(?:\+91[ -]?)?[6-9]\d{4}[ -]?\d{5}(?!\d)")
SYSTEM = "You are ShopKart's support assistant. Be brief and accurate."

def keep(t) -> bool:
    return t["eval_pass"] and t["feedback"] != 0           # passed evals and no thumbs-down

def norm(text: str) -> str:
    return re.sub(r"\W+", " ", text.lower()).strip()

seen, rows = set(), []
for t in filter(keep, TRACES):
    key = hashlib.sha256(norm(t["input"]).encode()).hexdigest()
    if key in seen:                                         # near-duplicate inputs teach nothing new
        continue
    seen.add(key)
    rows.append({"messages": [{"role": "system", "content": SYSTEM},
                              {"role": "user", "content": PHONE.sub("<PHONE>", t["input"])},
                              {"role": "assistant", "content": t["output"]}],
                 "source_trace": t["id"]})                  # lineage back to the trace

random.seed(7)
random.shuffle(rows)
split = max(1, int(len(rows) * 0.8))
train, val = rows[:split], rows[split:]
print(len(TRACES), "traces ->", len(rows), "examples:", len(train), "train,", len(val), "validation")
print(json.dumps(train[0])[:160], "...")
print("redacted:", [r["messages"][1]["content"] for r in rows if "<PHONE>" in r["messages"][1]["content"]])
What you should see
5 traces -> 3 examples: 2 train, 1 validation
{"messages": [{"role": "system", "content": "You are ShopKart's support assistant. Be brief and accurate."}, {"role": "user", "content": "Refund for a broken mi ...
redacted: ['Cancel A-1002, my number is <PHONE>']

The chat-format JSONL (messages with roles) is what almost every fine-tuning service accepts. Lineage (source_trace) lets you delete training examples when a customer exercises their right to erasure, and audit where a behavior came from. Make sure your terms with customers allow using their data for training before you do.

The other half: failed traces become eval cases

Step 1 used the traces that went well. The traces that went badly are worth more, because each one is a mistake your system really made. They do not go into training data. They go into the eval set, the fixed list of test questions (first met in Lesson 11.27) that every change must pass before release. For each failed trace, a person writes down what a correct answer must say and must not say. From then on, that mistake is checked automatically on every release.

The code continues from Step 1. It turns the failed trace t4 (the invented insurance offer) into an eval case, shows that the old answer fails it and a corrected answer passes, and then checks one more thing: that no question sits in both datasets.

# A person reads each failed trace and writes down what a correct answer must say and must not say.
FAILED = [t for t in TRACES if not keep(t)]                 # thumbs-down, or failed an eval
EVAL_SET = [{"id": "e-seed1", "input": "Where is A-1001?", "must_include": ["shipped"], "must_not_include": [],
             "failure": None, "source_trace": None}]        # the eval set you already had

def to_eval_case(trace, must_include, must_not_include, failure):
    return {"id": "e-" + trace["id"], "input": PHONE.sub("<PHONE>", trace["input"]),
            "must_include": must_include, "must_not_include": must_not_include,
            "failure": failure, "source_trace": trace["id"]}

EVAL_SET.append(to_eval_case(FAILED[0], must_include=["do not sell"], must_not_include=["499"],
                             failure="invented a product"))

def grade(case, answer: str) -> bool:
    a = answer.lower()
    return all(s.lower() in a for s in case["must_include"]) and not any(s.lower() in a for s in case["must_not_include"])

case = EVAL_SET[-1]
print("old answer passes:", grade(case, FAILED[0]["output"]))
print("fixed answer passes:", grade(case, "Sorry, we do not sell insurance. I can help with orders and refunds."))

# The two datasets must not share questions. An eval question the model was trained on measures memory, not skill.
eval_inputs = {norm(c["input"]) for c in EVAL_SET}
leaks = [r["source_trace"] for r in rows if norm(r["messages"][1]["content"]) in eval_inputs]
clean_rows = [r for r in rows if norm(r["messages"][1]["content"]) not in eval_inputs]
print("training examples removed because the eval set asks the same question:", leaks)
print("eval set:", len(EVAL_SET), "cases | training data:", len(clean_rows), "examples")
What you should see
old answer passes: False
fixed answer passes: True
training examples removed because the eval set asks the same question: ['t1']
eval set: 2 cases | training data: 2 examples

The last two lines are the part teams forget. Trace t1 asked "Where is A-1001?", and so does an eval case. A model fine-tuned on t1 would pass that case by memory, and the eval score would rise without the model getting any better. This is data leakage, the problem you met with train and test splits in Lesson 2.26, and the rule that prevents it is simple: when a question is in the eval set, it stays out of the training data. The check uses the same norm function as the duplicate filter, so "where is A-1001 ?" counts as the same question.

Step 2 · When to customize a model

The workshop showed how to fine-tune; this table is about whether to, and which method fits. Customize only after prompts, retrieval, tools and model choice are exhausted, and only with an eval set to prove the gain. Lesson 14.133 works through the three methods below that the workshop did not use.

Goal Method
Teach a format, style or narrow task with many examples Supervised fine-tuning (SFT), usually parameter-efficient (LoRA, QLoRA)
Make a small model behave like a large one on your task (cost and latency) Distillation: generate outputs with the large model, fine-tune the small one on them
Prefer some answers over others (tone, helpfulness) Preference tuning (DPO and variants) from pairs of better and worse answers
Improve on tasks with checkable outcomes (correct SQL, passing tests, right classification) Reinforcement fine-tuning (RFT) with a grader or verifiable reward
Add knowledge that changes Not fine-tuning: use retrieval (Chapter 4)

Costs that teams underestimate: building and cleaning data, evaluating every candidate, hosting the custom model (often provisioned capacity), and re-doing it all when a better base model ships.

Check your mental model
  • ✗ "More data always helps."
    ✓ Noisy or duplicated data can make results worse.
  • ✗ "Production data can be used as is."
    ✓ Remove personal data and check consent and licensing first.
  • ✗ "The flywheel runs by itself."
    ✓ It needs labeling, review and ownership to turn failures into improvements.

Exercises

Predict before you run

A training set has 30% near-duplicate support replies. What happens to the fine-tuned model, and what is the fix? (Solution P1.)

Break it on purpose

Use production conversations for training without filtering. What gets into the model? (Solution B1.)

Debugging exercise

The data flywheel collects thumbs-up answers for training, and the model becomes more confident but not more correct. Why? (Solution D1.)

Make it your own

Design a flywheel for ShopKart: what is logged, how examples are selected and labeled, how they enter evals and training, and how quality is checked. (Solution M1.)

Solutions

SolutionP1 · Duplicates skew training

It over-learns the repeated replies, and an eval that shares duplicates looks better than reality. Deduplicate (exact and near-duplicate), and split train and test after deduplication.

SolutionB1 · Data hygiene

Personal data, wrong agent answers, abusive messages and prompt injections. Filter for quality and policy, remove personal data, and keep only conversations with good outcomes.

SolutionD1 · Feedback is not ground truth

Users reward confident, pleasant answers, not necessarily correct ones. Verify feedback-selected examples against ground truth before training, and include corrected failures.

SolutionM1 · A flywheel with checks

Log inputs, outputs, tool calls and outcomes; select failures and uncertain cases; label them; add them to the eval set first; train only after the eval shows a gap; check for regressions before release.

Check your understanding

Explain the mechanismWhat is a data flywheel, and what makes it work?

Worked answer. A loop where production use generates data (failures, corrections, outcomes) that improves the system's evals, prompts, retrieval and models, which improves the product and brings more use. It works when data is selected for informativeness, labeled reliably, privacy-filtered, and used first to measure and only then to train.

A plausible wrong answer. "Collect everything and fine-tune on it." Unfiltered data teaches errors.

Follow-ups. What would you log to make it possible?

Debug a failureAfter retraining on new data, quality for one customer segment dropped. What do you check?

Worked answer. The new data's mix: whether that segment was under-represented or labeled differently, and whether the eval covers it. Rebalance, relabel and segment the eval.

A plausible wrong answer. "The model is worse." The data changed the balance.

Follow-ups. How would you catch this before release?

Defend a designSynthetic data or real data for training?

Worked answer. Real data for distribution and edge cases; synthetic data to fill gaps (rare intents, languages) and to scale, with quality checks and a held-out real eval. Pure synthetic training risks narrow, repetitive behavior.

A plausible wrong answer. "Synthetic is cheaper, so use it only." It inherits the generator's blind spots.

Follow-ups. How would you check synthetic data quality?

Check your understanding

Q1Where should a failed production trace go?

Good traces can become training examples. A failed trace is a mistake the system really made, so it becomes an eval case.

Q2An eval question also appears in the training data. What goes wrong?

This is data leakage. When a question is in the eval set, it stays out of the training data.
