A knowledge graph is only as good as its construction. Most failed GraphRAGlater · 5.6 projects fail here: a graph extracted with no schema, full of duplicates ("Acme", "ACME Electronics", "Acme Electronics Pvt Ltd" as three nodes), with no record of where facts came from, rebuilt from scratch every week. This lesson builds one properly.

Why this came about

Most companies already hold their entities and relationships in tables. Turning those tables into a graph is the most reliable way to start a knowledge graph, which is why construction usually begins there before attempting extraction from text.

In plain words first
Drawing the map from the spreadsheets you have

The easiest knowledge graph comes from structured data you already own: each table row becomes a node, foreign keys become edges, columns become properties. The work is deciding the model first (which questions must it answer, which node and edge types does that need), then mapping tables to it carefully, with stable IDs so repeated loads update instead of duplicating.

The construction pipeline

Step What happens The decision that matters
1. Competency questions Write the questions the graph must answer Scope: what to leave out
2. Schema (a light ontology) Entity types, relation types with allowed source and target types, key properties Fewer, well-defined types beat many vague ones
3. Structured sources Map tables and APIs to nodes and edges Stable IDs from the source system, never names
4. Unstructured sources Chunk text; extract entities and relations with an LLM under the schema Structured output, few-shot examples, the source chunk kept with each fact
5. Validation Reject facts that break the schema Types, allowed relations, required properties
6. Entity resolution Merge mentions of the same real-world thing Normalization, aliases, similarity and a review queue
7. Load Upsert nodes and edges with provenance Idempotent MERGE, so re-running is safe
8. Quality and maintenance Measure against a sample; update incrementally Precision first; deletions and changes propagate

Start from competency questions

A competency question is a question the graph must be able to answer, written before modeling. For a product-safety graph: "Which products use a recalled component?", "Who makes them?", "Which customers bought them in the last year?". Each question names entity types (Product, Component, Company, Customer) and relations (USES, RECALLED, MAKES, BOUGHT). Anything no question needs stays out of the schema. This is the ontology-engineering practice that keeps graphs small enough to be correct.

Structured data first

Most enterprise knowledge graphs get their backbone from systems of record, not from text: customers, orders, products and suppliers already have IDs and foreign keys. Map each table to a label, each row to a node keyed by its source ID, and each foreign key to an edge. Then use text extraction to add what the tables lack (a recall announcement, a contract clause, a support ticket's complaint), linked to the backbone. Facts from systems of record are more trustworthy than facts read from prose, so record the source type on every edge.

Build it: four tables to a graph

The mapping described above takes about thirty lines. The example uses pandas for the tables (Lesson F1.7) and networkx for the graph, so nothing needs to be installed or started. Three ideas from the pipeline table are visible in the code: stable identifiers, idempotent loading, and provenance.

import pandas as pd
import networkx as nx

# Four tables, as they would come out of ShopKart's order database. Keys are the usual integer and string ids.
customers = pd.DataFrame([{"customer_id": 101, "name": "Priya Sharma", "city": "Pune"},
                          {"customer_id": 102, "name": "Arjun Rao", "city": "Delhi"},
                          {"customer_id": 103, "name": "Priya Sharma", "city": "Mumbai"}])      # a second person with the same name
products  = pd.DataFrame([{"sku": "PHN-1", "name": "Phone X", "supplier_id": "S-ACME"},
                          {"sku": "EBD-2", "name": "Earbuds", "supplier_id": "S-ACME"},
                          {"sku": "CSE-3", "name": "Phone case", "supplier_id": "S-SZP"}])
suppliers = pd.DataFrame([{"supplier_id": "S-ACME", "name": "Acme Electronics", "country": "IN"},
                          {"supplier_id": "S-SZP", "name": "Shenzhen Parts", "country": "CN"}])
orders    = pd.DataFrame([{"order_id": "A-1001", "customer_id": 101, "sku": "PHN-1", "day": "2026-10-02"},
                          {"order_id": "A-1002", "customer_id": 102, "sku": "EBD-2", "day": "2026-10-05"},
                          {"order_id": "A-1003", "customer_id": 103, "sku": "CSE-3", "day": "2026-10-09"}])

G = nx.MultiDiGraph()

def merge_node(label, key, **props):
    """Create the node if it is new, otherwise update it. The id combines the label and the source key."""
    node_id = f"{label}:{key}"
    G.add_node(node_id, label=label, **props)            # add_node on an existing id updates it; it never duplicates
    return node_id

def merge_edge(a, rel, b, source):
    """One edge per (from, type, to). Every edge records which table it came from."""
    G.add_edge(a, b, key=rel, rel=rel, source=source)    # the key makes a repeated add overwrite, not duplicate

def load():
    for r in customers.itertuples(): merge_node("Customer", r.customer_id, name=r.name, city=r.city)
    for r in suppliers.itertuples(): merge_node("Supplier", r.supplier_id, name=r.name, country=r.country)
    for r in products.itertuples():
        p = merge_node("Product", r.sku, name=r.name)
        merge_edge(p, "SUPPLIED_BY", f"Supplier:{r.supplier_id}", source="products.supplier_id")     # a foreign key becomes an edge
    for r in orders.itertuples():
        o = merge_node("Order", r.order_id, day=r.day)
        merge_edge(f"Customer:{r.customer_id}", "PLACED", o, source="orders.customer_id")
        merge_edge(o, "CONTAINS", f"Product:{r.sku}", source="orders.sku")

load()
print("after one load: ", G.number_of_nodes(), "nodes,", G.number_of_edges(), "edges")
load(); load()
print("after three loads:", G.number_of_nodes(), "nodes,", G.number_of_edges(), "edges")
print("customers named Priya Sharma:", [n for n, d in G.nodes(data=True) if d.get("name") == "Priya Sharma"])
What you should see
after one load:  11 nodes, 9 edges
after three loads: 11 nodes, 9 edges
customers named Priya Sharma: ['Customer:101', 'Customer:103']
Reading this output
  • 11 nodes, 9 edges from four small tables: every row became a node, and every foreign key (a column that holds another table's key, such as orders.customer_id) became an edge.
  • Loading three times changes nothing. This is what idempotent means: running the load again has the same result as running it once. It matters because loads fail halfway, get retried, and run every night. A loader that creates a fresh node each time would triple the graph. In a graph database the same guarantee comes from MERGE in Cypher, which means "create this only if it is not already there".
  • Two different customers are both called Priya Sharma, and they stay two nodes, Customer:101 and Customer:103. That is the reason for the rule "ids from the source system, never names". A graph keyed on names would have merged a customer in Pune with a stranger in Mumbai, and every answer about either of them would be wrong.

Now the question the graph was built for. Writing the competency question first told us which nodes and edges were needed; answering it is a walk along three edges.

def customers_of_suppliers_in(country):
    """Competency question: which customers bought a product supplied from this country?"""
    found = []
    for supplier, d in G.nodes(data=True):
        if d["label"] == "Supplier" and d["country"] == country:
            for product in G.predecessors(supplier):                    # Product -SUPPLIED_BY-> Supplier
                for order in G.predecessors(product):                   # Order -CONTAINS-> Product
                    for customer in G.predecessors(order):              # Customer -PLACED-> Order
                        found.append((G.nodes[customer]["name"], G.nodes[customer]["city"], G.nodes[product]["name"], order))
    return found

print(customers_of_suppliers_in("CN"))
edge = G.get_edge_data("Product:CSE-3", "Supplier:S-SZP")["SUPPLIED_BY"]
print("how do we know the phone case comes from Shenzhen Parts?", edge["source"])
What you should see
[('Priya Sharma', 'Mumbai', 'Phone case', 'Order:A-1003')]
how do we know the phone case comes from Shenzhen Parts? products.supplier_id

The first line answers the question: one customer, the Priya Sharma in Mumbai, bought a product supplied from China. The second line is provenance: every edge carries the name of the table and column it came from, so when someone asks "how does the system know that?", there is an answer. Lesson 5.4 adds facts read from text, which are less certain than facts from tables; recording the source on every edge is what lets later code, and later readers, tell the two apart.

Check your mental model
  • ✗ "Load every table into the graph."
    ✓ Start from the questions the graph must answer and model only what they need.
  • ✗ "IDs can be generated during loading."
    ✓ Use stable keys from the source so reloads merge rather than duplicate.
  • ✗ "Graph construction is a one-off."
    ✓ Sources change; plan incremental updates.

Exercises

Predict before you run

A competency question is "Which suppliers of our top-selling products had a quality incident this year?". Which node and edge types does the graph need at minimum? (Solution P1.)

Break it on purpose

Load every table of the ERP into the graph, one node type per table. What problems does that create? (Solution B1.)

Debugging exercise

After a nightly load, supplier nodes doubled. The loader uses CREATE for every row. Fix it. (Solution D1.)

Make it your own

Write three more competency questions for ShopKart's supply graph, and list the node types, edge types and properties each needs. (Solution M1.)

Solutions

SolutionP1 · Questions define the schema

Product, Supplier and Incident nodes; SUPPLIES and HAD_INCIDENT edges; sales and dates as properties. Starting from competency questions keeps the schema to what the questions need.

SolutionB1 · Tables are not concepts

Join tables become nodes instead of edges, technical columns clutter properties, and the graph mirrors the database instead of the business concepts. Model concepts and relationships, then map tables onto them.

SolutionD1 · Idempotent loads

Use MERGE on a stable key (the supplier ID or GSTIN) so reloading updates instead of duplicating, and add uniqueness constraints so duplicates fail loudly.

SolutionM1 · Grow the schema from questions

For each question, list what must exist to answer it. Properties needed by only one question may belong in the source system, fetched when needed.

Check your understanding

Explain the mechanismHow do you build a knowledge graph from structured data?

Worked answer. Start from competency questions, design a schema (ontology) of concepts and relationships, map source tables to nodes and edges with stable keys, load idempotently with constraints, attach provenance (source and time), and test with the competency questions as queries. Structured sources come first because they are reliable; text extraction adds to them (Lesson 5.4).

A plausible wrong answer. "Convert the database to a graph." A schema designed from questions is what makes it useful.

Follow-ups. How do you keep it in sync with the sources?

Debug a failureA competency question returns fewer results than expected. What do you check?

Worked answer. Mapping gaps (rows that did not map because of missing keys or new codes), entity resolution splits, and edges that depend on data loaded later. Count nodes and edges per source against source row counts.

A plausible wrong answer. "The query is wrong." Often the data never arrived.

Follow-ups. What load checks would you run nightly?

Defend a designBuild an ontology first, or start loading data?

Worked answer. A small schema from competency questions first, then load and iterate. A large up-front ontology delays value and is often wrong; no schema at all produces a graph nobody can query reliably.

A plausible wrong answer. "Adopt an industry ontology in full." Reuse terms, but keep the schema to what your questions need.

Follow-ups. When would you adopt a standard vocabulary?
