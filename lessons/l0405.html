Why this came about

Keyword search cannot match different words with the same meaning. From 2013, word embeddings (word2vec, Lesson 5.33) showed that a neural network could place words with similar meanings close together in a space of a few hundred dimensions. In 2019, Sentence-BERT did the same for whole sentences, using a transformer trained so that sentences with the same meaning get nearby vectors. Search by meaning became practical: embed every passage once, embed each question when it arrives, and return the nearest passages. This dense retrieval became the default first step of RAG, and embedding models have improved steadily since, with larger models, many languages and longer inputs.

In plain words first
Coordinates for meaning

An embedding model turns a piece of text into a list of numbers, which you can think of as coordinates on a map with hundreds of directions instead of two. The model has been trained so that texts with similar meanings land close together. Searching by meaning is then geometry: turn the question into coordinates, and find the stored passages nearest to it. That finds "refund" for "money back" without a single shared word. It can also blur things that must be exact, such as codes and names, and it will always return its nearest neighbours even when nothing relevant exists.

Step 1 · Closeness as an angle

An embedding is a vector: a list of numbers representing a text's meaning. Two texts are compared with cosine similarity, which measures the angle between their vectors: 1 means pointing the same way, 0 means unrelated, negative means opposite. A toy example with three numbers per text:

import numpy as np

def cosine(a, b):
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

# Toy 3-number "embeddings" (real ones have 256 to 3,072 numbers)
refund   = np.array([0.9, 0.1, 0.0])
money_back = np.array([0.8, 0.2, 0.1])
shipping = np.array([0.1, 0.9, 0.2])
print(round(cosine(refund, money_back), 3), round(cosine(refund, shipping), 3))
What you should see
0.984 0.214

"Refund" is close to "money back" and far from "shipping", even though the words differ. That is the whole idea behind semantic search.

Step 2 · A real embedding model

Now the real thing. all-MiniLM-L6-v2 is a small, widely used open embedding model: a 6-layer transformer encoder (Lesson 7.22) with 22 million parameters that runs comfortably on a laptop processor. It turns any text into 384 numbers:

from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")     # 22 million parameters, about 90 MB
sentences = ["I want a refund", "Please give me my money back", "When will my parcel arrive?", "The parcel has not arrived yet"]
vectors = model.encode(sentences, normalize_embeddings=True)
print("shape:", vectors.shape, "| first five numbers of sentence 0:", np.round(vectors[0, :5], 3))
print("length of each vector:", np.round(np.linalg.norm(vectors, axis=1), 3))
What you should see
shape: (4, 384) | first five numbers of sentence 0: [-0.078  0.01   0.03   0.026  0.017]
length of each vector: [1. 1. 1. 1.]

Four sentences became a table of 4 rows and 384 columns. No single number means anything on its own; the meaning is in the direction of the whole vector. normalize_embeddings=True scales every vector to length 1, which makes cosine similarity the same as a plain dot product (Lesson 1.23).

Compare every sentence with every other:

similarity = vectors @ vectors.T                     # every sentence against every other; dot product = cosine for unit vectors
print(" " * 34 + "   ".join(f"s{i}" for i in range(4)))
for i, s in enumerate(sentences):
    print(f"s{i} {s:<30}" + " ".join(f"{v:5.2f}" for v in similarity[i]))
What you should see
                                  s0   s1   s2   s3
s0 I want a refund                1.00  0.63  0.13  0.22
s1 Please give me my money back   0.63  1.00  0.05  0.08
s2 When will my parcel arrive?    0.13  0.05  1.00  0.76
s3 The parcel has not arrived yet 0.22  0.08  0.76  1.00

The two refund sentences score 0.63 with each other without sharing a meaningful word, and the two parcel sentences score 0.76. Across the groups, similarities are near zero. This is what "captures meaning" looks like in numbers.

Reading this output
How does a model learn to do this?

An embedding model is trained on hundreds of millions of text pairs that belong together: a question and its answer, a title and its article, two phrasings of one sentence. Training pulls the vectors of each pair together and pushes them away from the other texts in the batch (contrastive learning, Lesson 7.22). Nothing tells the model what "refund" means; it learns that texts about getting money back tend to be paired with each other. Lesson 3.22 fine-tunes such a model on your own data.

Step 3 · Vector search over the chunks

Embed every chunk once (in production this happens when documents are indexed), then for each question embed it and take the chunks with the highest dot products:

minilm_vecs = model.encode([c[2] for c in CHUNKS], normalize_embeddings=True)     # done once, when documents are indexed

def search_minilm(query: str, k: int = 3) -> list[str]:
    q = model.encode([query], normalize_embeddings=True)[0]                       # done for every query
    scores = minilm_vecs @ q
    return [CHUNKS[i][0] for i in np.argsort(-scores)[:k]]

for q in ["stop my purchase", "pay when it arrives", "how long until the courier arrives", "my kettle was dead out of the box"]:
    print(f"{q!r:<38} vectors: {search_minilm(q)[0]:<16} keywords: {search_bm25(q)[0]}")
What you should see
'stop my purchase'                     vectors: cancellation#0   keywords: refund-policy#0
'pay when it arrives'                  vectors: cod#0            keywords: shipping#1
'how long until the courier arrives'   vectors: shipping#0       keywords: warranty#0
'my kettle was dead out of the box'    vectors: warranty#1       keywords: warranty#1

These are the questions keyword search could not answer in Lesson 5.37. "stop my purchase" now finds the cancellation chunk, "pay when it arrives" finds cash on delivery, and a question about the courier finds shipping. The last question works for both, because it shares the rare words "dead" and "box" with the chunk.

Reading this output
Brute force is fine, up to a point

minilm_vecs @ q compares the question with every chunk: one matrix multiplication. For a few hundred thousand chunks that still takes milliseconds. Beyond that, systems use approximate nearest-neighbour indexes such as HNSWlater · 14.74 that look at a small fraction of the vectors, and store the vectors in a vector database. Step 4 · What vector search gets wrong

Vectors measure closeness of meaning, and that causes two typical failures. Here are five error messages whose codes differ by a digit or two:

codes = ["Error E-4012: payment gateway timeout, retry after 2 minutes.", "Error E-4021: card declined by the bank.",
         "Error E-4102: address pin code not serviceable.", "Error E-4120: coupon expired.", "Error E-4201: OTP did not match."]
code_vecs = model.encode(codes, normalize_embeddings=True)

def id_tokens(text):                                   # a tokeniser that keeps codes such as e-4021 in one piece
    return re.findall(r"[a-z]+-\d+|[a-z0-9]+", text.lower())

code_bm25 = BM25Okapi([id_tokens(c) for c in codes])
for q in ["E-4021 error", "E-4210"]:
    sims = code_vecs @ model.encode([q], normalize_embeddings=True)[0]
    kw = code_bm25.get_scores(id_tokens(q))
    print(f"{q!r}")
    print(f"   vectors : {np.round(sims, 2)}  -> answers {codes[int(np.argmax(sims))][6:12]}")
    print(f"   keywords: {np.round(kw, 2)}  -> answers {codes[int(np.argmax(kw))][6:12] if kw.max() > 0 else 'nothing: no such code'}")
What you should see
'E-4021 error'
   vectors : [0.48 0.61 0.61 0.49 0.51]  -> answers E-4021
   keywords: [0.2  1.3  0.23 0.29 0.25]  -> answers E-4021
'E-4210'
   vectors : [0.2  0.34 0.37 0.3  0.4 ]  -> answers E-4201
   keywords: [0. 0. 0. 0. 0.]  -> answers nothing: no such code

For "E-4021 error", the right entry and a different one are tied at the top to two decimal places: to the embedding model these codes all look much alike. For "E-4210", a code that does not exist, vector search confidently returns its nearest neighbour, E-4201, with a similarity as high as many correct matches. Keyword search, with a tokeniser that keeps each code whole, gives an exact match in the first case and correctly finds nothing in the second.

Two rules follow, and both will come back throughout this chapter:

  • Vector search always returns something. There is no natural "no match". If the similarity of the best result is low for your model and data, treat it as "not found", and choose that threshold by measurement, not by guessing.
  • Exact identifiers belong to keyword search or filters. Order numbers, SKUs, error codes, names and dates should be matched exactly.

Step 5 · The model has a maximum input length

An embedding model reads a limited number of tokens and silently ignores the rest:

long_text = "Shipping takes 2 to 3 days in metro cities. " * 60 + "The secret return code is MANGO-42."
tokens = model.tokenizer(long_text)["input_ids"]
print(len(tokens), "tokens in the text; the model reads at most", model.max_seq_length)
q = model.encode(["what is the secret return code"], normalize_embeddings=True)[0]
whole = model.encode([long_text], normalize_embeddings=True)[0]
tail = model.encode([long_text[-200:]], normalize_embeddings=True)[0]
print(f"similarity to the whole long text: {float(whole @ q):.2f} | to its last 200 characters alone: {float(tail @ q):.2f}")
What you should see
611 tokens in the text; the model reads at most 256
similarity to the whole long text: -0.05 | to its last 200 characters alone: 0.17

The text is 611 tokens long and this model reads 256. The sentence with the code is at the very end, so it was never read, and the similarity to the question is about zero. Embedded on its own, the same ending matches. This is one of the two reasons for chunking (Lesson 14.70): a chunk must fit the embedding model's input, and one vector can only summarise so much. Newer embedding models accept 8,000 tokens or more, but a single vector for a long, mixed text is still a blurry summary.

Step 6 · The lab's stand-in embedder

The rest of this chapter's lab must run in seconds, offline, and give identical numbers on every machine. So from here on it uses a tiny stand-in instead of a neural model: LSA (latent semantic analysis), which compresses TF-IDF vectors (Lesson 5.32) with a matrix factorisation. It captures which words tend to occur together in this corpus, and nothing more.

# Step 4 · "Dense" retrieval for the rest of the lab. A real system calls an embedding model here (see the box below).
# To run offline and identically everywhere we use LSA (TF-IDF reduced with SVD), a classic way to get meaning-ish vectors.
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.decomposition import TruncatedSVD
from sklearn.pipeline import make_pipeline
import numpy as np

embedder = make_pipeline(TfidfVectorizer(stop_words="english", ngram_range=(1, 2)), TruncatedSVD(n_components=8, random_state=0))
chunk_vecs = embedder.fit_transform([c[2] for c in CHUNKS])
chunk_vecs /= np.linalg.norm(chunk_vecs, axis=1, keepdims=True)       # normalize so dot product = cosine

def search_dense(query: str, k: int = 3) -> list[str]:
    q = embedder.transform([query])[0]
    q /= np.linalg.norm(q) or 1.0
    ranked = np.argsort(-(chunk_vecs @ q))
    return [CHUNKS[i][0] for i in ranked[:k]]

How much weaker is it than the real model?

for q in ["stop my purchase", "pay when it arrives", "my kettle was dead out of the box"]:
    print(f"{q!r:<38} real model: {search_minilm(q)[0]:<16} LSA stand-in: {search_dense(q)[0]}")
What you should see
'stop my purchase'                     real model: cancellation#0   LSA stand-in: refund-policy#0
'pay when it arrives'                  real model: cod#0            LSA stand-in: refund-policy#0
'my kettle was dead out of the box'    real model: warranty#1       LSA stand-in: warranty#1

The stand-in gets the easy case and misses the two paraphrases, because it has only ever seen these nine chunks and has no idea that "purchase" relates to "order". The real model learned that from a billion sentence pairs. Tip
Swapping in a real embedding model

To use the real model in the lab, define search_dense = search_minilm. To use a hosted model, replace the embedding call; the rest of the pipeline stays the same. For example with OpenAI (not run here, needs a key):

from openai import OpenAI
client = OpenAI()

def embed(texts: list[str]) -> np.ndarray:
    resp = client.embeddings.create(model="text-embedding-3-small", input=texts)
    return np.array([d.embedding for d in resp.data])

chunk_vecs = embed([c[2] for c in CHUNKS])

On AWS use a Bedrock embedding model (Amazon Titan or Cohere Embed) through bedrock-runtime; on Google, the Gemini embedding model through google-genai; on Azure, an embedding deployment in Foundry Models. Open models such as BGE-M3, Qwen3-Embedding and nomic-embed run locally with sentence-transformers, exactly as MiniLM did above.

Choosing and using an embedding model

Question What to know
Which model? Shortlist by your languages, domain and budget, using a public benchmark such as MTEB only as a filter. Then decide on your own questions (Lesson 14.72)
How many dimensions? 384 to 1,024 is typical; up to 3,072 exists. More dimensions cost more storage and search time for a small gain. Models trained with Matryoshka learning let you keep only the first 256 or 512 numbers with little loss (Lesson 14.74)
How long can the input be? From 256 tokens to 8,000 and more. Know the limit and chunk below it
Query and document prefixes? Many models (E5, BGE, nomic, Qwen) expect a short instruction such as query: or passage: in front of the text, and score noticeably worse without it. Read the model card
Which similarity? Cosine, or dot product on normalised vectors, for almost every text model. Use the one the model was trained with
Hosted or local? A hosted API is simplest; a local model keeps data in-house and has no per-call price. Either way, embedding is far cheaper than generation
Can I change model later? Only by re-embedding every document. Vectors from different models, or different versions of one model, cannot be compared
Check your mental model
  • ✗ "Similar vectors mean a correct answer."
    ✓ They mean similar wording or topic; the passage may still not answer the question.
  • ✗ "If nothing relevant exists, vector search returns nothing."
    ✓ It always returns its nearest neighbours. You must decide what counts as too far.
  • ✗ "Any embedding model works with any stored vectors."
    ✓ Query and documents must be embedded with the same model and version.
  • ✗ "Embeddings replace keyword search."
    ✓ They complement it; hybrid search usually beats either alone.

In production
Embedding model mistakes seen in production
  • Different models for documents and queries, or a model upgrade on one side only: similarity scores become meaningless. Version the embedding model with the index and change both together.
  • Changing models in place: re-embedding a large corpus takes hours to days. Build a new index beside the old one, evaluate, then switch an alias.
  • Choosing from the leaderboard alone: an English-heavy model can look strong on MTEB and fail on Hindi or domain jargon. Test on 50 real questions per language before deciding.
  • Ignoring input limits: chunks longer than the model's maximum input are silently truncated, so the end of the chunk is never searchable.

Where the vectors are stored

In this lesson the vectors sit in a NumPy array. A real system keeps them in a vector store: a database, or a feature of one, that saves each vector with its text and metadata and can find the nearest ones quickly.

Store Choose it when
pgvectorlater · 14.74 (Postgres) You already run Postgres and have up to tens of millions of vectors. SQL joins and filters for free. The most common sensible default.
Qdrant, Weaviate, Milvus You need rich filtering, built-in hybrid search or very large scale, and can run another service
Pinecone You want fully managed, zero operations
OpenSearch, Elasticsearch You already run them for search; strong BM25 plus vectors in one engine
LanceDB, Chroma Local, embedded or prototype use
Turbopuffer, S3 Vectors Very large, cost-sensitive collections on object storage, accepting slower cold queries
Cloud-native (below) You want retrieval managed inside your cloud's security boundary

Under the hood most use approximate nearest neighbor (ANN) indexes, usually HNSW (a navigable graph), trading a little recall for large speedups. Tune them, and always measure recall against exact searchlater · 14.74 on a sample. Lesson 14.74 opens these indexes up: IVFlater · 14.74, HNSW, quantization, filtering and sizing, with code.

In production
Vector store choices that hurt later

The vector store rarely decides answer quality; operations decide whether you regret it. The usual regrets: no hybrid or keyword support, so it has to be bolted on; weak filtering, so permission and tenant filters become slow post-filters; no way to build a new index beside the old one, so every re-embedding is a risky in-place migration; and a separate system the data team cannot govern. Choose the store that already sits next to your data and permissions unless measurements say otherwise.

Predict before you run

Debugging exercise

Make it your own

Set search_dense = search_minilm and write five questions of your own about the ShopKart help pages, each phrased without the words the pages use. How many does vector search answer in its top result, and how many does search_bm25? (Solution M1.)

Solutions

SolutionP1 · Same meaning, different words

High, close to 1, because they mean the same thing. BM25 gives partial credit only for the shared words ("UPI", and "refunds" in both; "2" does not match "two", and "reach" does not match "take"). That difference is why vectors find paraphrases.

SolutionB1 · Vectors from different models are incomparable

Results become close to random. Each model has its own space: direction 17 in one has nothing to do with direction 17 in the other, even when the sizes match. Always embed queries and documents with the same model and version, store the model name with the index, and re-embed everything when you change it.

SolutionD1 · Normalization and dot products

With every chunk vector at length 1, the dot product with an unnormalised query equals the cosine multiplied by the query's length, which is the same for every chunk, so the order is unchanged. If the chunk vectors are not normalised, longer vectors get higher dot products regardless of direction, and the ranking changes. Normalise consistently, and use the metric the index expects.

SolutionM1 · Paraphrase questions

Expect vector search to answer most of them and keyword search few, because you removed the shared words on purpose. Now write five questions that quote exact figures or terms from the pages ("INR 499", "OTP") and compare again: keyword search recovers. Real question sets contain both kinds, which is the argument for Lesson 5.38.

Check your understanding

Explain the mechanismWhat is an embedding, and how does vector search find relevant passages?

Worked answer. An embedding model maps text to a vector so that texts with similar meaning are close, usually by cosine similarity. Documents are embedded once and stored; a query is embedded at search time, and the nearest vectors are returned, exactly or with an approximate index (Lesson 14.74). It finds paraphrases that keyword search misses, and blurs exact tokens such as IDs.

A plausible wrong answer. "Embeddings understand the text." They encode similarity learned in training, which can miss domain terms and negation.

Follow-ups. How are embedding models trained (Lesson 3.22)?

Debug a failureVector search returns passages about the right topic but the wrong product. What do you try?

Worked answer. Embeddings capture topic more than exact identity, so add keyword search for names and IDs (hybrid, Lesson 5.38), add metadata filters by product, and rerank the candidates. Check whether chunks carry the product name at all.

A plausible wrong answer. "Use a bigger embedding model." It may help a little; identity matching is a keyword and metadata problem.

Follow-ups. How would you add product filters from the question?

Defend a designWhich embedding model would you choose for ShopKart?

Worked answer. Shortlist by language coverage (English, Hindi, Hinglish), domain, dimension and cost, hosting needs (API or self-hosted for data residency), and benchmark scores as a filter only. Then decide on ShopKart's own eval set, because public leaderboards rarely match a specific corpus.

A plausible wrong answer. "The top of the leaderboard." Leaderboards measure other data.

Recap
  • An embedding model turns text into a vector; texts with similar meaning get vectors pointing in similar directions, measured by cosine similarity.
  • Vector search embeds chunks once and each question on arrival, and returns the nearest chunks. It bridges different words with the same meaning.
  • It blurs exact identifiers, always returns something, and ignores text beyond the model's input limit.
  • Queries and documents must use the same model; changing the model means re-embedding everything.
  • The lab continues with a small offline stand-in; a real model makes every later method work better.
