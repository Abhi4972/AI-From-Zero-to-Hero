Why this came about

LlamaIndex (2022) began as a way to connect models to private data, and grew into a framework for retrieval-centered agents. DSPy (from Stanford, 2023) took a different path: treat prompts as programs that are optimized automatically against a metric, instead of hand-tuned.

In plain words first
A data framework and a prompt compiler

LlamaIndex started as a toolkit for connecting models to your data (loading, indexing, retrieval) and now includes agents and workflows; reach for it when retrieval is the heart of the system. DSPy treats prompts as programs to optimize: you declare what each step takes and returns, give examples and a metric, and it searches for prompts or examples that score best, instead of you hand-tuning text.

LlamaIndex: data-first agents and workflows

Best fit: agents whose main job is to work over documents and data, building on LlamaIndex's ingestion, indexing and parsing (LlamaParse).

uv add llama-index-core llama-index-llms-openai-like        # tested with llama-index-core 0.14.25

import asyncio
from llama_index.llms.openai_like import OpenAILike
from llama_index.core.agent.workflow import FunctionAgent

li_llm = OpenAILike(model="mock-model", api_base=BASE_URL, api_key="mock",
                    is_chat_model=True, is_function_calling_model=True)

def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

li_agent = FunctionAgent(tools=[get_order_status], llm=li_llm, system_prompt="Help ShopKart customers with orders.")

async def li_run():
    print(str(await li_agent.run("Where are A-1001 and A-1002?")))

asyncio.run(li_run())
What you should see
Here is what I found: A-1001 is shipped; A-1002 is processing

Agents here are Workflows: event-driven steps where each step consumes one event type and emits another. FunctionAgent, ReActAgent and CodeActAgent are prebuilt; AgentWorkflow coordinates several agents with handoffs. Workflows are ephemeral by default; snapshot the context or use the DBOS-backed runtime for durability.

The part LlamaIndex is named for: an index over your documents

The agent above could have been written in any library of this chapter. What LlamaIndex adds is everything around documents. Its central object is the index: you hand it documents, and it splits them into passages (it calls them nodes), embeds each one and stores the vectors, which is the ingestion half of the pipeline you built by hand in Lesson 14.72. From an index you get a retriever, which returns the best passages for a question, or a query engine, which retrieves and then asks the model to answer from what it found.

The code builds an index over three policy snippets and retrieves from it. So that it runs offline, the embedding model is a toy that counts ten chosen words. In a real project you would pass a real embedding model (Lesson 14.71) in the same place and change nothing else.

import re
from llama_index.core import Document, VectorStoreIndex
from llama_index.core.embeddings import BaseEmbedding

VOCAB = ["refund", "damaged", "days", "delivery", "metro", "cancel", "shipped", "order", "return", "cities"]

class WordCountEmbedding(BaseEmbedding):               # a toy stand-in for a real embedding model, so this runs offline
    def _vector(self, text: str) -> list[float]:
        words = re.findall(r"[a-z]+", text.lower())
        return [float(sum(w.startswith(v[:5]) for w in words)) for v in VOCAB]   # one number per vocabulary word
    def _get_text_embedding(self, text): return self._vector(text)
    def _get_query_embedding(self, query): return self._vector(query)
    async def _aget_query_embedding(self, query): return self._vector(query)

docs = [Document(text="Damaged items can be refunded within 30 days of delivery.", doc_id="refunds"),
        Document(text="Standard delivery takes 3 to 5 days in metro cities.", doc_id="delivery"),
        Document(text="An order can be cancelled until it has shipped.", doc_id="cancel")]

index = VectorStoreIndex.from_documents(docs, embed_model=WordCountEmbedding())      # split, embed and store, in one call
for hit in index.as_retriever(similarity_top_k=2).retrieve("Can I get a refund for a damaged mixer after delivery?"):
    print(round(hit.score, 2), hit.node.ref_doc_id, "|", hit.node.get_content())

# The refund policy changes. The document keeps its ID, so the index replaces the old version instead of holding both.
docs[0] = Document(text="Damaged items can be refunded within 45 days of delivery.", doc_id="refunds")
print("changed:", index.refresh_ref_docs(docs), "| documents in the index:", len(index.ref_doc_info))
top = index.as_retriever(similarity_top_k=1).retrieve("refund for a damaged item")[0]
print(round(top.score, 2), top.node.ref_doc_id, "|", top.node.get_content())
What you should see
0.87 refunds | Damaged items can be refunded within 30 days of delivery.
0.29 delivery | Standard delivery takes 3 to 5 days in metro cities.
changed: [True, False, False] | documents in the index: 3
0.71 refunds | Damaged items can be refunded within 45 days of delivery.

The first two lines are the retriever's answer: the refund policy scores highest, and each hit knows which document it came from. The last two lines show the part that matters in production. The policy changed from 30 to 45 days, and refresh_ref_docs compared every document with what the index held, re-embedded the one that had changed (True) and left the other two alone. The index still holds three documents, and the search now returns the 45-day text.

This only works because each document was given an ID. Without one, loading the documents again adds a second copy of each, and the index starts returning the old policy beside the new one. That is the usual cause of "the assistant quotes a rule we changed last month".

DSPy: programming instead of prompting

Best fit: pipelines with a clear quality metric, where you want prompts (and few-shot examples) optimized automatically instead of hand-tuned.

DSPy (from Stanford NLP) separates what a step should do from how it is prompted. You declare a signature (inputs, outputs, a docstring), wrap it in a module (Predict, ChainOfThought, ReAct), and an optimizer (such as MIPROv2 or GEPA) searches for instructions and examples that maximize your metric on a training set. Change the model, re-run the optimizer, and the prompts adapt.

uv add dspy        # tested with 3.4.1

import dspy
from dspy.utils import DummyLM

class Triage(dspy.Signature):
    """Classify a customer message for ShopKart support."""
    message: str = dspy.InputField()
    category: str = dspy.OutputField(desc="one of: refund, status, other")
    urgent: bool = dspy.OutputField()

# DummyLM returns scripted outputs so this runs offline. Use dspy.LM("openai/gpt-5.5") or any LiteLLM string for real.
dspy.configure(lm=DummyLM([{"reasoning": "Broken item and urgent wording.", "category": "refund", "urgent": "True"}]))
triage = dspy.ChainOfThought(Triage)              # adds a reasoning field before the outputs
pred = triage(message="My mixer arrived broken, I need my money back today")
print(pred.category, pred.urgent)
What you should see
refund True

urgent came back as a real boolean: DSPy parses outputs into the declared types. The optimization step (for example dspy.MIPROv2(metric=my_metric).compile(triage, trainset=examples)) needs a real model and 20 or more labeled examples.

What a DSPy optimizer actually does

The example above ran a module without optimising it, because optimisation needs a real model. It is the part that makes DSPy different from every other library in this chapter, so here is what happens when you call an optimizer, step by step.

You supply three things: the program (the triage module), a training set (say, 40 customer messages with the correct category and urgency), and a metric (a function that returns 1 if a prediction matches the label and 0 if not).

Step What the optimizer does In plain words
1 Runs your program on the training examples and keeps the runs that the metric scores as correct Collects worked examples that are known to be right
2 Asks a model to write several candidate instructions for each step, from the signature, the code and the examples Drafts different ways of wording the prompt
3 Builds candidate prompts: one instruction plus a few of the collected examples Combines an instruction with few-shot examples (Lesson 11.25)
4 Runs each candidate on a batch of training examples and scores it with your metric Measures every candidate, instead of trusting anyone's taste
5 Uses the scores to choose which combinations to try next, and repeats Searches, spending model calls where they look most promising
6 Returns your program with the best instruction and examples filled in The "compiled" program; you save it and load it in production

The result of compiling is nothing mysterious. It is a prompt, with an instruction and a few examples, that you can print and read. What changed is how it was found: by search against a metric on your data, not by a person editing text and eyeballing three outputs.

That has three consequences worth knowing before you adopt it:

  • It needs what all evaluation needs. No labelled examples and no metric, no optimisation. Teams that already have an evaluation set (Lesson 11.19) get the most from DSPy; teams that do not must build one first, which is worth doing anyway.
  • It costs model calls. An optimisation run makes hundreds to thousands of calls. That is a one-off cost per model and per program change, paid again whenever you switch models.
  • It can overfit. Forty training examples can be fitted by a prompt that then does worse on new messages. Hold out examples the optimizer never sees, and report the score on those (Lesson 2.26 explained why).

When to reach for it: a pipeline with a clear, checkable output (a classification, an extraction, a retrieval step with known right answers), where prompts are being hand-tuned again and again as models change. When not to: open-ended writing or conversation, where no metric captures "good".

Check your mental model
  • ✗ "LlamaIndex is only a vector database wrapper."
    ✓ It covers ingestion, indexing, retrieval, agents and workflows.
  • ✗ "DSPy writes prompts for free."
    ✓ It needs a metric and examples, and its optimization runs many model calls.
  • ✗ "Optimized prompts transfer to any model."
    ✓ Re-optimize or re-evaluate when you change models.

Solutions

SolutionP1 · Different jobs

DSPy: it compiles a program by optimizing prompts and examples against a metric. LlamaIndex focuses on data ingestion, indexing and retrieval.

SolutionB1 · Small optimization sets overfit

The optimized prompts fit those examples and may generalize poorly. Use more examples and a held-out set.

SolutionD1 · Ingestion pipelines

Whether the ingestion pipeline uses document IDs and caching to update changed documents and delete removed ones.

SolutionM1 · Metrics drive DSPy

A function returning a score per example; DSPy optimizers search prompts and demonstrations to maximize it on a training set, validated on a held-out set.

Check your understanding

Explain the mechanismWhat are LlamaIndex and DSPy for?

Worked answer. LlamaIndex is a data framework for LLM applications: loaders, parsing, indexing, retrieval, query engines, agents and event-driven workflows over your data. DSPy treats prompts as programs: you declare signatures and modules, define a metric, and optimizers tune prompts and examples automatically.

A plausible wrong answer. "Both are RAG libraries." DSPy is about optimizing LM programs.

A plausible wrong answer. "DSPy does not work." The metric and data decide.
