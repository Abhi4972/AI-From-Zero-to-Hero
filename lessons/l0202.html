Why this came about

Developers first parsed model text with regular expressions and hope, and it broke constantly. Providers responded in 2023 and 2024 with JSON modes and then structured outputs, where the model is constrained to a schema you supply. That turned models into components that code can rely on, which tools and agents depend on.

The problem: code cannot read prose

ShopKart wants every support ticket routed automatically: which team (category), how urgent, and which order. The router is code, so it needs fields, not a paragraph. The obvious first try is to ask for JSON in the prompt:

import json
from fake_claude import FakeAnthropic, BadRequestError   # the labeled stand-in (Lesson 3.1's appendix)

client = FakeAnthropic()
MODEL = "claude-sonnet-5-5"
TICKETS = [
    "My order SK-1002 still hasn't arrived and I need it for a wedding tomorrow!",
    "The mixer from order SK-1001 arrived broken. I want my money back.",
    "I was charged twice for SK-1004.",
    "Your app crashes every time I open the login page.",
]

r = client.messages.create(model=MODEL, max_tokens=300, messages=[{"role": "user", "content":
    f"Classify this ticket. Reply in JSON with the fields: category, urgency, order_id.\n\n{TICKETS[0]}"}])
raw = r.content[0].text
print(repr(raw))
try:
    print(json.loads(raw))
except json.JSONDecodeError as e:
    print("json.loads failed:", e)
What you should see
'Sure! Here\'s the ticket as JSON:\n```json\n{\n  "Category": "Delivery issue",\n  "Urgency": "High",\n  "OrderId": "SK-1002"\n}\n```'
json.loads failed: Expecting value: line 1 column 1 (char 0)

repr shows the exact text, including the newlines. The model did what it was asked, in its own way: a friendly sentence, a Markdown fence, capitalized keys and free-text values ("Delivery issue", "High"). json.loads fails on the first character. Stripping the fence would get you a dictionary, but with keys and values no router expects. Every one of those is a real failure mode of "reply in JSON" prompts, and it is intermittent with a real model, which is worse: it passes your test and fails on Tuesday.

In plain words first
A form instead of a free-text box

Code cannot reliably read prose. So instead of asking the model to "answer", you give it a form to fill in: a schema saying which fields exist, their types and allowed values. The schema is written in JSON Schema (Lesson 0.23), usually generated from a Pydantic class. The model fills in the form as JSON; your code checks it against the same class, and if a value is wrong, either repairs it or asks the model again with the error.

Idea 1 · Give the API a schema

A JSON Schema describes the exact shape you want: field names, types, and the allowed values of each. With JSON outputs, you pass it in output_config.format, and the API constrains generation (constrained decoding) so the reply is JSON that matches it:

SCHEMA = {
    "type": "object",
    "properties": {
        "category": {"type": "string", "enum": ["delivery", "damaged", "billing", "technical", "other"]},
        "urgent": {"type": "boolean"},
        "order_id": {"type": "string"},
    },
    "required": ["category", "urgent", "order_id"],
    "additionalProperties": False,
}

def classify(ticket, schema=SCHEMA, max_tokens=300):
    r = client.messages.create(model=MODEL, max_tokens=max_tokens,
                               messages=[{"role": "user", "content": f"Classify this support ticket: {ticket}"}],
                               output_config={"format": {"type": "json_schema", "schema": schema}})
    return r

r = classify(TICKETS[0])
print("stop_reason:", r.stop_reason)
print("raw text:   ", r.content[0].text)
print("parsed:     ", json.loads(r.content[0].text))
What you should see
stop_reason: end_turn
raw text:    {"category": "delivery", "urgent": true, "order_id": "SK-1002"}
parsed:      {'category': 'delivery', 'urgent': True, 'order_id': 'SK-1002'}

Three things changed. The reply is the JSON and nothing else, so json.loads works. category is one of the five values in the enum, so the router can switch on it. And the API enforces required and additionalProperties: false, so no field is missing and none is invented.

Who calls what: your code builds the schema and sends it with the request; the API compiles it into a grammar and uses it while generating; your code still calls json.loads on the text block. The first request with a new schema is slower while the grammar compiles; compiled grammars are cached for 24 hours from last use.

Run all four tickets through it:

for t in TICKETS:
    print(json.loads(classify(t).content[0].text))
What you should see
{'category': 'delivery', 'urgent': True, 'order_id': 'SK-1002'}
{'category': 'damaged', 'urgent': False, 'order_id': 'SK-1001'}
{'category': 'billing', 'urgent': False, 'order_id': 'SK-1004'}
{'category': 'technical', 'urgent': False, 'order_id': 'N/A'}

Every reply parses and every category is valid. But look at the last one: the ticket names no order, and the schema says order_id is a required string, so the reply contains a string anyway: "N/A". A real model might invent a plausible-looking ID instead. A required field forces an answer. When the input may not contain a value, say so in the schema:

NULLABLE = json.loads(json.dumps(SCHEMA))                      # a copy
NULLABLE["properties"]["order_id"] = {"anyOf": [{"type": "string"}, {"type": "null"}]}

for t in TICKETS[2:]:
    print(json.loads(classify(t, NULLABLE).content[0].text))
What you should see
{'category': 'billing', 'urgent': False, 'order_id': 'SK-1004'}
{'category': 'technical', 'urgent': False, 'order_id': None}

None is something code can check. "N/A", or an invented "SK-1003", is not.

Idea 2 · Let the SDK write the schema

Writing JSON Schema by hand is tedious and easy to get wrong. A Pydantic model describes the same thing as a Python class, and the SDK's messages.parse turns it into a schema, sends it, and validates the reply into an object:

from typing import Literal
from pydantic import BaseModel, Field
from fake_claude import transform_schema          # the real SDK has this too: from anthropic import transform_schema

class Ticket(BaseModel):
    category: Literal["delivery", "damaged", "billing", "technical", "other"]
    urgency: int = Field(ge=1, le=5, description="1 = can wait, 5 = the customer is blocked")
    order_id: str | None = None

print(json.dumps(transform_schema(Ticket.model_json_schema())["properties"]["urgency"]))

r = client.messages.parse(model=MODEL, max_tokens=300, output_format=Ticket,
                          messages=[{"role": "user", "content": f"Classify this support ticket: {TICKETS[0]}"}])
print(repr(r.parsed_output))
What you should see
{"description": "1 = can wait, 5 = the customer is blocked\n\n{maximum: 5, minimum: 1}", "title": "Urgency", "type": "integer"}
Ticket(category='delivery', urgency=5, order_id='SK-1002')

The first line shows something the helper does for you. JSON outputs support only part of JSON Schema: numeric limits such as minimum and maximum, and string lengths, are not supported. The helper moves them into the field's description, where the model can read them, and then checks the original constraints itself when it validates the reply. So urgency=7 would still raise an error in your code instead of reaching the router.

Send a hand-written schema with an unsupported keyword straight to the API, and the request fails:

HAND_WRITTEN = {"type": "object", "additionalProperties": False, "required": ["urgency"],
                "properties": {"urgency": {"type": "integer", "minimum": 1, "maximum": 5}}}
try:
    classify(TICKETS[0], HAND_WRITTEN)
except BadRequestError as e:
    print("BadRequestError:", e)
What you should see
BadRequestError: schema.properties.urgency: 'minimum' is not supported in output_config.format schemas

transform_schema does what parse does internally. The fixed schema is accepted:

FIXED = transform_schema(HAND_WRITTEN)
print(json.dumps(FIXED["properties"]))
print(json.loads(classify(TICKETS[0], FIXED).content[0].text))
What you should see
{"urgency": {"type": "integer", "description": "{minimum: 1, maximum: 5}"}}
{'urgency': 5}

The constraint is now only a hint, so validate the value yourself, which is the next idea.

Idea 3 · Valid shape, wrong value: validate and repair

A schema guarantees shape, not truth. The reply below is perfectly valid JSON with an order ID in the right format, for an order that does not exist. Business rules like "the order must be on this customer's account" belong in code. When one fails, send the error back and ask again: this validate-and-repair loop is what libraries such as Instructor and Pydantic AI (Lesson 14.123) run for you.

import re
from pydantic import ValidationError, field_validator

KNOWN_ORDERS = {"SK-1001", "SK-1002", "SK-1004"}

class CheckedTicket(Ticket):
    @field_validator("order_id")
    @classmethod
    def order_exists(cls, v):
        if v is not None and v not in KNOWN_ORDERS:          # a business rule no schema can express
            raise ValueError(f"no order {v} on this account")
        return v

def scripted(replies):
    """Stands in for a model that gets a value wrong the first time: returns the next scripted JSON."""
    it = iter(replies)
    return lambda messages: next(it)

model = scripted(['{"category": "delivery", "urgency": 5, "order_id": "SK-1020"}',
                  '{"category": "delivery", "urgency": 5, "order_id": "SK-1002"}'])

def extract(ticket, max_attempts=3):
    messages = [{"role": "user", "content": f"Classify this support ticket: {ticket}"}]
    for attempt in range(1, max_attempts + 1):
        raw = model(messages)
        try:
            result = CheckedTicket.model_validate_json(raw)
            print(f"attempt {attempt}: valid")
            return result
        except ValidationError as e:
            problems = "; ".join(f"{'.'.join(map(str, err['loc']))}: {err['msg']}" for err in e.errors())
            print(f"attempt {attempt}: {problems}")
            messages += [{"role": "assistant", "content": raw},
                         {"role": "user", "content": f"Fix these problems and reply again: {problems}"}]
    raise RuntimeError(f"no valid ticket after {max_attempts} attempts")

print(repr(extract("Where is SK-1002? It was due yesterday!")))
What you should see
attempt 1: order_id: Value error, no order SK-1020 on this account
attempt 2: valid
CheckedTicket(category='delivery', urgency=5, order_id='SK-1002')

The error message names the field and the problem, which is what lets a model fix it in one retry. Cap the attempts, and count repairs in your metrics: a rising repair rate is an early warning that a prompt or model change went wrong.

One more failure no schema prevents: the reply can be cut off.

r = client.messages.create(model=MODEL, max_tokens=10,
                           messages=[{"role": "user", "content": f"Classify this support ticket: {TICKETS[0]}"}],
                           output_config={"format": {"type": "json_schema", "schema": SCHEMA}})
print(r.stop_reason, repr(r.content[0].text))
try:
    json.loads(r.content[0].text)
except json.JSONDecodeError as e:
    print("json.loads failed:", e)
What you should see
max_tokens 'Let me'
json.loads failed: Expecting value: line 1 column 1 (char 0)

The same applies to stop_reason == "refusal". Check the stop reason before you parse:

def classify_safely(ticket, schema=NULLABLE, max_tokens=300):
    r = classify(ticket, schema, max_tokens)
    if r.stop_reason != "end_turn":                       # max_tokens or refusal: the JSON may be incomplete
        return {"error": f"no usable answer (stop_reason={r.stop_reason})"}
    return json.loads(r.content[0].text)

print(classify_safely(TICKETS[0], max_tokens=10))
print(classify_safely(TICKETS[0]))
What you should see
{'error': 'no usable answer (stop_reason=max_tokens)'}
{'category': 'delivery', 'urgent': True, 'order_id': 'SK-1002'}

Measure it: the same four tickets, before and after

A claim such as "structured output is more reliable" deserves a measurement. The code sends the same four support tickets twice. The first function only asks for JSON in the prompt, as you might in a chat window, and then tries to parse whatever text comes back. The second uses the schema-enforced call from this lesson. Count how many replies can be parsed and used in each case:

def ask_nicely(ticket):
    r = client.messages.create(model=MODEL, max_tokens=300, messages=[{"role": "user", "content":
        f"Classify this ticket. Reply in JSON with the fields: category, urgent, order_id.\n\n{ticket}"}])
    return r.content[0].text

def parses(text):
    try:
        json.loads(text)
        return True
    except json.JSONDecodeError:
        return False

for name, call in [("asked nicely", ask_nicely), ("JSON outputs", lambda t: classify(t, NULLABLE).content[0].text)]:
    results = [call(t) for t in TICKETS]
    usable = [json.loads(x) for x in results if parses(x)]
    valid = [d for d in usable if d.get("category") in SCHEMA["properties"]["category"]["enum"]]
    print(f"{name:13} parses {len(usable)}/4 · category usable {len(valid)}/4")
What you should see
asked nicely  parses 0/4 · category usable 0/4
JSON outputs  parses 4/4 · category usable 4/4

With the stand-in the difference is total; with a real model, "asked nicely" usually parses most of the time, which is exactly why it gets shipped and then fails in production. When is a schema no benefit? When a person reads the answer, as in a chat reply: a schema adds an extra system prompt (more input tokens), first-request compile latency, and a format that reads worse than prose. Use it when code consumes the output.

In production
Structured output problems seen in production
  • Valid JSON, wrong values: validate values with business rules and repair, as above.
  • Unsupported schema features: providers differ on recursion, numeric limits, string patterns and optional fields. A schema that one provider accepts, another rejects with a 400 or ignores. Keep schemas flat and simple, and test each provider.
  • Forced answers: a required field makes the model produce a value when the input has none. Make such fields nullable, or add an explicit "unknown" option.
  • Enum casing: the docs note that an enum value can come back with different capitalization; compare case-insensitively when it matters.
  • Schema changes break consumers: version output schemas like an API, and log the schema version with every call.

The request the SDK actually sent carried output_config.format with type: "json_schema", additionalProperties: false added, and urgency's limits moved into its description as {maximum: 5, minimum: 1}: the transformation shown in Idea 2.

Solutions

SolutionP1 · A required field forces an answer

With SCHEMA the reply contains "order_id": "N/A", because the schema demands a string and the ticket has none. A real model might invent a plausible ID instead, which is worse because it looks valid. With NULLABLE it is None, which code can test for.

SolutionB1 · Parse only finished replies

json.loads fails with Expecting value: line 1 column 1 (char 0) because the text is a fragment ('Let me' from the stand-in; with a real model, the first part of a JSON object). classify_safely checks r.stop_reason != "end_turn" before parsing and returns an error instead. The same check catches refusals.

SolutionD1 · An unsupported keyword

JSON outputs do not support maxLength (nor minLength, minimum, maximum or multipleOf), and the API rejects the schema with a 400. Fix 1: pass the schema through transform_schema (or define it as a Pydantic model and use parse), which moves the limit into the description, and check the length in code. Fix 2: remove the keyword and enforce the limit only in your validator. Either way, the length is now your code's job, so test it.

SolutionM1 · Route by language
Language = Literal["english", "hindi", "hinglish"]

class RoutedTicket(Ticket):
    language: Language

def route(t: RoutedTicket) -> str:
    team = {"hindi": "Hindi desk", "hinglish": "Hindi desk"}.get(t.language, "English desk")
    return f"{team} · {t.category} · urgency {t.urgency}"

for text in ["Refund chahiye, SK-1001 ka mixer damaged hai", TICKETS[2]]:
    r = client.messages.parse(model=MODEL, max_tokens=300, output_format=RoutedTicket,
                              messages=[{"role": "user", "content": f"Classify this support ticket: {text}"}])
    print(route(r.parsed_output))

Hindi desk · damaged · urgency 2
English desk · billing · urgency 2

The new field changes the schema, so the first request with it pays the grammar compile time again; log the schema version so a dashboard can tell old and new replies apart.

Check your understanding

Explain the mechanismWhat does structured output guarantee, and what does it not?

Worked answer. With a schema enforced during decoding (Claude's JSON outputs, OpenAI's Structured Outputs), a reply that finishes normally is valid JSON matching the schema: required fields present, enum values from the list, no extra properties. It does not guarantee the values are true, and it does not hold when the reply is cut off at max_tokens or refused. So I check the stop reason, validate values with business rules, and make fields nullable where the input may not contain them.

A plausible wrong answer. "It guarantees correct output, so no validation is needed." It guarantees shape. An order ID in the right format can still be an order that does not exist.

Follow-ups. Why is a required field risky for data that may be missing? What does the SDK do with a minimum constraint?

Debug a failureYour ticket router occasionally crashes with a JSON decode error, even though you use a schema. What do you check?

Worked answer. The stop reason of the failing calls. If it is max_tokens, the reply was cut off mid-object, so raise the limit and check stop_reason before parsing; if it is refusal, the content does not follow the schema either. Then I check whether the code reads the right block, the text block rather than content[0] when other blocks such as thinking can come first. I add those cases to the tests.

A plausible wrong answer. "The model is ignoring the schema; add 'ONLY JSON' to the prompt." With enforced schemas the shape is not the model's choice; the cause is almost always a cut-off, a refusal or reading the wrong block.

Follow-ups. How would you alert on this before customers notice?

Defend a designNative structured output, a forced tool call, or JSON in the prompt: which do you choose?

Worked answer. Native structured output when the provider supports it for my schema: it is the most direct and the API enforces it. A tool call with a strict schema when the model also needs to choose between actions, or on a provider without native support. Prompt-only JSON with parsing and retries only as a fallback, for example on a small local model, and only with a validator in front of it. Whichever I choose, I keep the schema simple and validate values in code.

A plausible wrong answer. "Always JSON in the prompt, it works everywhere." It works most of the time, which is the problem.

Follow-ups. How do you migrate an output schema without breaking consumers?
