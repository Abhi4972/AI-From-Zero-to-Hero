In plain words first
The idea in one line

A gateway sits between your apps and model providers. Core features are provider routing, fallback, retries, rate limiting, secret references, observability, guardrails. Market split in 2026: LiteLLM is MIT OSS with 100+ providers, OpenAI-compatible, but breaks down around ~2000 RPS (8 GB memory, cascading failures in published benchmarks); best for Python, <500 RPS, dev/prototyping. The problem

In plain words first

An AI gateway is one service that sits between your applications and every model provider. Your code calls the gateway with one API (usually OpenAI's format), and the gateway picks the provider, retries on errors, falls back to another provider when one fails or rate-limits you, enforces per-team limits, fetches credentials from a vault, records cost and traces, and can apply guardrails such as removing personal data. Without it, every service carries its own copy of this logic for every provider. The trade-offs are the extra milliseconds each request spends in the gateway, how well it holds up at high request rates, its licence and whether you must run it yourself for data-residency reasons. LiteLLM, Portkey, Kong, Bifrost and Cloudflare or Vercel's gateways sit at different points of those trade-offs.

Your product calls OpenAI, Anthropic, and a self-hosted Llama. Each provider has a different SDK, error model, rate limit, and auth scheme. You want failover (if OpenAI 429s, try Anthropic), a single credential store, unified observability, and rate limits per tenant.

Reinventing this at the app layer couples every service to every provider. A gateway layer consolidates it into one process with one API (typically OpenAI-compatible) that fans out to providers.

Idea 1 · Seven core features

  1. Provider routing — OpenAI, Anthropic, Gemini, self-hosted, etc. behind one API.
  2. Fallback — on 429, 5xx, or quality failure, retry elsewhere.
  3. Retries — exponential backoff, bounded attempts.
  4. Rate limits — per-tenant, per-key, per-model.
  5. Secret references — pull credentials from vault at runtime (never in app).
  6. Observability — OTel + GenAI attributes (Phase 17 · 13) + cost attribution.
  7. Guardrails — PII redaction, jailbreak detection, allowed-topics filters.

Idea 2 · LiteLLM — MIT OSS, Python

  • 100+ providers, OpenAI-compatible, router config, fallback, basic observability.
  • Breaks down around 2000 RPS in Kong's benchmark; 8 GB memory footprint, cascading failures under sustained load.
  • Best fit: Python app, <500 RPS, dev/staging gateways, experimental routing.
  • Cost: $0 for OSS; cloud free tier exists.

Idea 3 · Portkey — control plane positioning

  • Apache 2.0 OSS as of March 2026. Guardrails, PII redaction, jailbreak detection, audit trails.
  • 20-40 ms per-request latency overhead.
  • $49/mo for production tier with retention + SLA.
  • Best fit: regulated industries needing guardrails + observability bundled.

Idea 4 · Kong AI Gateway — the scale play

  • Built on Kong Gateway (mature API gateway product, lua+OpenResty).
  • Kong's own benchmark on 12-CPU equivalent: 228% faster than Portkey, 859% faster than LiteLLM.
  • Pricing: $100/model/month, max 5 on Plus tier.
  • Best fit: already on Kong; >1000 RPS; willing to license.

Idea 5 · Bifrost (Maxim AI)

  • Automatic retries with configurable backoff.
  • Fallback to Anthropic on OpenAI 429 is a canonical recipe.
  • Newer entrant; commercial.

Idea 6 · Cloudflare AI Gateway / Vercel AI Gateway

  • Managed, zero-ops. Basic retry and observability.
  • Best fit: Edge-serving JavaScript apps on Cloudflare/Vercel.
  • Limited compared to Kong/Portkey on guardrails and rate limits.

Idea 7 · Self-hosted vs managed

Data residency is the forcing function. Healthcare and finance default self-host (LiteLLM or Portkey OSS or Kong). Consumer products default managed (Cloudflare AI Gateway) or middle-tier (Portkey managed). Hybrid: self-hosted for regulated tenant, managed for others.

Idea 8 · Latency budget

  • LiteLLM: 5-15 ms overhead typical.
  • Portkey: 20-40 ms overhead.
  • Kong: 3-8 ms overhead.
  • Cloudflare/Vercel: 1-3 ms overhead (edge advantage).

Gateway latency directly adds to TTFT. For TTFT P99 < 100 ms SLA, Kong or Cloudflare. For P99 < 500 ms, any.

Idea 9 · Rate-limit semantics matter

Simple token-bucket works up to moderate scale. Multi-tenant requires sliding-window + burst allowance + per-tenant tiering. LiteLLM ships token-bucket; Kong ships sliding-window; Portkey ships tiered.

Idea 10 · Gateway + observability + routing compose

Phase 17 · 13 (observability) + 16 (model routing) + 19 (gateways) are the same layer in production. Pick one tool that covers all three or wire them carefully: most 2026 deployments combine Helicone (observability) or Portkey (guardrails) with Kong (scale) for split roles.

Idea 11 · Numbers you should remember

  • LiteLLM: breaks at ~2000 RPS, 8 GB memory.
  • Portkey: 20-40 ms overhead; Apache 2.0 since March 2026.
  • Kong: 228% faster than Portkey, 859% faster than LiteLLM.
  • Kong pricing: $100/model/month, 5 max on Plus tier.
  • Cloudflare/Vercel: 1-3 ms overhead at the edge.

The same idea as a formula

Fallback chains. If providers fail independently with probabilities f1​,f2​,…, a chain of k succeeds unless all fail:

P(success)=1−i=1∏k​fi​

Independence is the weak assumption: a shared region, a shared upstream model or a client-side bug makes failures correlated, and the real gain is smaller.

Worked example
Three providers, honest numbers

Error rates: 3%, 2% and 2%.

  1. One provider: 97% success.
  2. Two, independent: 1 − 0.03 × 0.02 = 99.94%.
  3. Three, independent: 1 − 0.03 × 0.02 × 0.02 = 99.9988%.
  4. Now suppose a third of the first provider's failures happen during cloud-region outages that also take down the second (both in the same region). The two-provider chain then fails at least 1% of the time (0.03 × ⅓), success at most 99%, not 99.94%. Put fallbacks in a different region or cloud.
  5. Latency: each fallback adds a full failed attempt plus backoff, so fallback requests may take 2–3× longer; set a total deadline.
Check your mental model

Which statements are right?

  • ✓ A gateway's latency adds directly to time to first token.
  • ✗ LiteLLM is the right choice at any scale. It suits Python apps and moderate rates; Kong's benchmark shows it struggling near 2,000 requests per second.
  • ✓ Secrets should be fetched by the gateway at runtime, not stored in each application.
  • ✗ Fallback across providers makes failures independent. Shared regions and shared bugs keep them correlated.

N = 200_000
for overlap in (0.0, 0.3, 0.6):
    ok = 0
    for _ in range(N):
        a_fails = random.random() < 0.03
        b_fails = (random.random() < overlap or random.random() < 0.02) if a_fails else (random.random() < 0.02)

Reading this output

With independent providers the chain fails about 0.06% of the time; if 30% of the primary's failures also hit the fallback, failures rise to about 0.9%, fifteen times worse; at 60%, about 1.8%. The fallback is only as good as its independence: different region, different cloud, different model.

Part 1 of 3 · Provider, call_provider, simulate_fallback

"""AI gateway routing + fallback simulator — stdlib Python.

Models a gateway fronting OpenAI, Anthropic, and self-hosted. Injects 429/5xx
errors per provider. Compares fallback strategies.
"""

from __future__ import annotations

from dataclasses import dataclass, field
import random


@dataclass
class Provider:
    name: str
    base_latency_ms: float
    error_rate: float
    overhead_ms: float


PROVIDERS = [
    Provider("OpenAI",       180, 0.03, 0),
    Provider("Anthropic",    220, 0.02, 0),
    Provider("Self-hosted",  100, 0.05, 0),
]

GATEWAY_OVERHEAD = {
    "LiteLLM": 10,
    "Portkey": 30,
    "Kong":      5,
    "Cloudflare": 2,
}


def call_provider(p: Provider, rng: random.Random) -> tuple[bool, float]:
    if rng.random() < p.error_rate:
        return False, p.base_latency_ms * 0.3  # half-done before error
    return True, p.base_latency_ms


def simulate_fallback(gateway: str, n: int = 1000, seed: int = 7) -> dict:
    rng = random.Random(seed)
    success = 0
    total_latency = 0.0
    retries = 0
    fallback_hits = 0
    gw_ovh = GATEWAY_OVERHEAD[gateway]

    for _ in range(n):
        req_latency = gw_ovh
        done = False
        for attempt, p in enumerate(PROVIDERS):
            ok, ms = call_provider(p, rng)
            req_latency += ms
            if attempt > 0:
                fallback_hits += 1
            if ok:
                success += 1
                done = True
                break
            retries += 1
        total_latency += req_latency

    return {
        "gateway": gateway,
        "success_rate": success / n,
        "mean_latency": total_latency / n,
        "retries": retries,
        "fallback_hits": fallback_hits,
    }

Part 2 of 3 · report, main

def report(row: dict) -> None:
    print(f"{row['gateway']:12}  success={row['success_rate']*100:5.1f}%  "
          f"mean_latency={row['mean_latency']:6.0f}ms  "
          f"retries={row['retries']:4}  fallbacks={row['fallback_hits']:4}")


def main() -> None:
    print("=" * 80)
    print("AI GATEWAY FALLBACK — 3-provider chain under error injection")
    print("=" * 80)
    header = f"{'Gateway':12}  {'Success':>7}         {'mean latency':>12}  retries  fallbacks"
    print(header)
    print("-" * len(header))
    for gw in ("LiteLLM", "Portkey", "Kong", "Cloudflare"):
        report(simulate_fallback(gw))

    print("\nNotes: a single-provider target at 3% error rate → 97% success.")
    print("Two-provider fallback → 99.94% success (complement of 0.03 × 0.02).")
    print("Three-provider fallback → 99.997% success. Latency rises on fallback.")

Solutions

SolutionP1 · Reading the fallback test

In code/main.py every gateway reaches 100% success with 34 fallbacks; they differ only in mean latency (185–213 ms), which reflects each gateway's overhead. The test injects independent errors, so it shows the best case; add correlated failures to see the chain's real limit.

SolutionB1 · A single gateway at launch

(1) Run the gateway as a horizontally scaled service behind a load balancer, load-tested at twice the expected peak, or choose a gateway built for that rate (Kong, or a managed edge gateway). (2) Give applications a degraded path that does not depend on the gateway being healthy, such as a direct call to one provider with a circuit breaker, so a gateway failure does not take every feature down.

Interview questions

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Estimate itYour SLA is a P99 time to first token under 320 ms. The model alone measures 300 ms at P99. You are choosing a gateway to put in front of it. Which classes of gateway fit in the budget, and what do you do when the one you want does not?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The gateway has at most 20 ms at the tail. An edge-managed gateway at 1 to 3 ms and a high-performance gateway at 3 to 8 ms fit, a lightweight proxy at 5 to 15 ms fits with little margin, and a control-plane gateway at 20 to 40 ms does not. If you need the features of the slow one, split the roles: keep the fast gateway on the request path, run the heavy features out of band, or buy the budget back from the model with a faster first token.

The budget.

The target is 320 ms and the model takes 300 ms, so the gateway may add 20 ms, and that is at the tail. A P99 target means the gateway's own P99, not its median, and a gateway that is quick when idle can be slow under load. The sum of the two tails is a screening estimate only. Before you commit to the SLA, measure the end-to-end first-token P99 through the gateway under load.

The classes.

Class Overhead in the lesson Fits
edge-managed, zero-ops 1 to 3 ms yes
high-performance, built on a mature API gateway 3 to 8 ms yes
lightweight open-source proxy 5 to 15 ms with little margin
control plane with guardrails and audit 20 to 40 ms no

The lesson's rule of thumb matches: for a P99 under 100 ms, pick the edge or the high-performance class. For a P99 under 500 ms, any class works.

When you want the slow one.

The control-plane class brings PII redaction, jailbreak detection and audit trails. Three ways to keep them inside the budget:

  1. Split the roles. Put the fast gateway on the request path and run observability and audit off the path. The lesson notes that production deployments combine an observability tool with a scale gateway in exactly this split.
  2. Keep only what must be inline. Redaction has to run before the provider sees the prompt, so it stays on the path. Audit and tracing do not.
  3. Buy back budget from the model. Prefix caching lowers the first-token time, and a faster model tier does too.

Scale decides as well.

The lightweight proxy breaks down around 2000 requests per second with an 8 GB footprint in the published benchmark, and the lesson places it below 500 requests per second. If the traffic will grow past that, the high-performance class is the only one that fits both the latency and the scale.

Plausible wrong answers.

  • "Every gateway adds a few milliseconds, pick on features." The lesson's overheads run from 1 to 40 ms, and 40 ms is twice this budget.
  • "Put the gateway behind the model, not in front." The gateway routes and falls back before the model. Behind the model it protects nothing.
  • "Add the gateway's median to the model's P99." Two tails do not add that way. Measure the gateway's own tail under load.

Follow-ups an interviewer may ask.

  • (level 2) Why measure the gateway at P99 and not at its median? Expected: the SLA is a P99, and the gateway's tail adds to the model's tail.
  • (level 3) The slow gateway's value is PII redaction. How do you keep it inside the budget? Expected: keep the redaction inline because it must run before the provider sees the prompt, move observability and audit off the path, and then measure whether the remaining overhead fits.
  • (level 3) Traffic will triple next year. Which class survives? Expected: the lightweight proxy breaks down around 2000 requests per second, so plan the move to the high-performance class before that.

Defend a designYou add a second serving replica to double capacity. Throughput rises, but the first-token time of long chat sessions gets worse, and the cache hit rate on both servers falls. Explain the cause, and design the routing so that the second replica stops undoing the cache.

Level 3 of 4 · about 15 minutes to answer well.

Short answer. Each replica has its own KV cache, and a router that spreads requests at random or in turn sends turn five of a chat to the replica that never saw turns one to four. That replica prefills the whole history again, which is the prefix miss the cache exists to avoid. Route each conversation back to the replica that holds its prefix with a cache-aware policy that remembers which server saw which text, with a load-balance check in front of it. Then read the hit rate on the servers themselves, because the router's record is a guess.

The mechanism.

A plain Kubernetes Service spreads requests at random. The in-server data parallel controller of SGLang defaults to round robin, which ignores prefixes. Either way, a conversation's turns land on different replicas, and each replica computes the history that the other one already holds. A field report in the SGLang manual measured the damage: with turn-by-turn routing, 23 percent of input tokens were computed again. One request header that pinned each conversation to one GPU raised the cache hit rate from 64.7 to 92.1 percent and halved the median time to first token.

How a cache-aware router picks a server.

The SGLang gateway keeps one approximate radix tree per model, over the characters of the request text, so it never tokenizes to route. For each request it does three things in order:

  1. It checks balance. When the busiest server's load is more than 64 above the lightest and more than 1.5 times the lightest, the request goes to the least-loaded server.
  2. Otherwise it computes the match rate, the share of the request text that matches the tree. Above 0.3, the request goes to the server with the longest match.
  3. Below 0.3, it goes to the least-loaded server.

Every 120 seconds a background task trims each tree to at most 67,108,864 nodes. The balance check comes first on purpose: a prefix-first policy would pile every long conversation onto one hot server.

The tree is a guess.

The gateway records where it sent text. It never asks a server what it still holds, and a server can evict the prefix later. So a request can arrive at the server the tree names and still prefill. Check the hit rate on the servers themselves, from their counters over a window, and not only the routing decisions.

Pick the policy by traffic.

Cache-aware routing for chat and agent traffic, where turns share long prefixes. A power-of-two or round-robin policy for batch traffic with unique prompts, because a match rate under the threshold gives no affinity anyway. Do not put multi-turn traffic behind in-server data parallelism with its round-robin default.

The same idea in the vLLM layers.

The vLLM manual lists routers that read the engine's metrics to pick a replica, and one that also reads the KV cache events the engine publishes with --kv-events-config, so that a request goes to the replica that holds its prefix. The production stack's router keeps a session on one replica. In the gateway lesson's vocabulary, this is provider routing one level down: the AI gateway routes across providers, and the engine router routes across replicas.

Pin the router with the engine.

The SGLang manual records an incident where the same engine build gave 132,140 tokens per second with one router version and 69,767 with the next. Benchmark the router and the engine as one system, and pin both versions.

Plausible wrong answers.

  • "Add a replica and each server's hit rate stays the same." Each replica has its own cache, and random routing splits every conversation across both.
  • "Hash the user id to a server and be done." It keeps a user on one server and ignores load. The manual's gateway balances first, so a hot user cannot saturate one replica with no relief.
  • "Turn on in-server data parallelism instead of a gateway." Its default method is round robin, which ignores prefixes, which is the problem you are solving.

Follow-ups an interviewer may ask.

  • (level 3) Why does the router check load balance before the prefix match? Expected: a prefix-first policy would send every long conversation to one hot server. The imbalance test sends the request to the least-loaded server when the gap is large.
  • (level 3) Which traffic should not use the cache-aware policy? Expected: batch traffic with unique prompts. A match rate under the threshold gives no affinity, so a load-based policy does the same work with less state.
  • (level 4) One server's hit rate stays low although the gateway routes its conversations there. Why? Expected: the gateway's tree records where it sent text, not what the server still holds. The server evicted the prefix, so the request prefills. Read the server's own counters.
  • (level 4) You upgrade the router without touching the engine. What do you measure? Expected: throughput and hit rate of the router and the engine as one system, because a router change alone halved throughput in a reported incident.
