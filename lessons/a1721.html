The idea in one line

The problem

In plain words first

An evaluation checks a model on a fixed, labelled set of examples: can it do the task? An A/B test answers a different question: do real users behave better with the new version? You split users at random into group A (current) and group B (new), measure something that matters (task success, retention, cost per request), and only believe a difference that is too large to be chance. Small effects need huge samples: telling a 3.00% conversion rate from 3.06% takes over a million users per group. Several techniques help: CUPED uses each user's behaviour before the test to remove noise, sequential tests let you look at results early without fooling yourself, multiple-comparison corrections stop twenty tests from producing a "winner" by luck, and an SRM check catches broken randomization.

You hand-tuned a system prompt. It feels better. You ship it. Conversion changes by noise. You blame the metric. Or you shipped a new model and conversion didn't move — did the model degrade or was the change too small to detect? You don't know, because you shipped without an A/B.

Evals answer whether the model can do a task on a labeled set. They do not answer whether users prefer the output. Only a controlled online experiment answers that, and only if the experiment has enough power, controls for non-determinism, and corrects for multiple comparisons.

Idea 1 · Evals vs A/B tests

Evals — offline, labeled set, judge (rubric or LLM-as-judge or human). Answer: "Is the output correct / helpful / safe on this fixed distribution?"

A/B test — online, live users, randomized. Answer: "Does the new variant move the user-level metric that matters?"

Both required. Evals catch regressions before exposure; A/B confirms product impact after.

Idea 2 · What to test

  1. Prompt engineering — wording, system-prompt structure, examples. Metric: task success, user retention, cost/request.
  2. Model selection — GPT-4 vs GPT-3.5-Turbo vs Llama-OSS. Metric: accuracy (task) + cost/request + latency P99. Multi-objective.
  3. Generation parameters — temperature, top-p, max_tokens. Metric: task-specific (output diversity vs determinism).

Idea 3 · CUPED — variance reduction

Controlled-experiments Using Pre-Experiment Data. Regress out pre-period variance before comparing post-period. Typical variance reduction: 30-70%. Effective sample size goes up for free.

Implementation: both Statsig and GrowthBook implement.

Idea 4 · Sequential testing

Classical A/B assumes fixed sample size. Sequential tests ("peek-and-decide") control false-positive rate under repeated looks. Always-valid sequential procedures (mSPRT, Howard's confidence sequences) let you stop early on clear winners.

Idea 5 · Multiple-comparison corrections

Running 20 A/B tests at 95% confidence produces one false positive by chance. Bonferroni correction tightens α per-test; Benjamini-Hochberg controls false-discovery rate. GrowthBook implements both.

Idea 6 · SRM — sample ratio mismatch

Assignment hash randomizes users to variants. If 50/50 split delivers 47/53, something is broken — SRM check flags it. Both platforms implement.

Idea 7 · Statsig vs GrowthBook

Statsig: - Acquired by OpenAI for $1.1B (September 2025). Hosted, SaaS. - Sequential testing, CUPED, held-out populations. - All-in-one: feature flags + experimentation + observability. - Best fit: team already wants a bundled product, doesn't care about OpenAI ownership.

GrowthBook: - Open-source (MIT); warehouse-native (reads from Snowflake/BigQuery/Redshift directly). - Multiple engines: Bayesian, Frequentist, Sequential. - CUPED, SRM, Bonferroni, BH corrections. - Self-host or managed cloud. - Best fit: warehouse-SQL shop, data team controls the metric layer, wants OSS.

Idea 8 · Non-determinism complicates power

Same prompt produces varying outputs. Traditional power calculations assume IID observations. With LLM non-determinism, effective sample size is lower than nominal. Multiply required sample size by ~1.3-1.5x as a safety margin.

Idea 9 · Real case outcomes

  • Chatbot reward model variant: +70% conversation length, +30% retention.
  • Nextdoor subject lines: +1% CTR after reward-function refinement.
  • Khan Academy Khanmigo: iterative latency-vs-math-accuracy trade.

Idea 10 · The anti-pattern: shipping on vibes

Every senior engineer can name a feature that was shipped because "it feels better" with no A/B. Most of them regressed product metrics the team didn't notice for months. A/B is the forcing function.

  • GrowthBook: open-source MIT; Bayesian + Frequentist + Sequential.
  • CUPED variance reduction: 30-70%.
  • LLM non-determinism → +30-50% sample-size buffer.

The same idea as a formula

Sample size per group for a conversion rate. With baseline rate p, absolute lift δ, and the usual 5% significance and 80% power (zα/2​=1.96, zβ​=0.84):

n≈δ2(zα/2​+zβ​)2⋅2p(1−p)​

Halving the detectable lift quadruples the sample. LLM non-determinism adds noise; the lesson's rule of thumb is to add 30–50%.

Worked example
How many users to see a 10% relative lift?

Baseline 3% conversion; you hope for 3.3% (+10% relative, δ=0.003).

  1. p(1−p)=0.03×0.97=0.0291.
  2. n≈7.84×2×0.0291/0.0032=0.4563/0.000009≈50,700 per group.
  3. With a 40% buffer for non-determinism: about 71,000 per group, 142,000 users in total.
  4. For a +2% relative lift (3.06%): δ is 5 times smaller, so about 25 times more users: over 1.2 million per group. Most prompt tweaks are this size; only big products can measure them.
Check your mental model

Which statements are right?

  • ✓ Evals catch regressions before release; A/B tests measure user impact after.
  • ✗ Checking an A/B dashboard every day and stopping when p < 0.05 is fine. Repeated peeking inflates false positives unless you use a sequential procedure.
  • ✓ A 47/53 split in a test meant to be 50/50 signals a bug in assignment.
  • ✗ Twenty tests at 95% confidence give no false winners. You expect about one by chance; correct with Bonferroni or Benjamini-Hochberg.

The cost of peeking
import random, math
random.seed(8)
def z_test(a_hits, b_hits, n):
    p = (a_hits + b_hits) / (2 * n)
    se = math.sqrt(2 * p * (1 - p) / n) or 1
    return abs(a_hits - b_hits) / n / se

runs, peeks, per_peek, false_wins = 1000, 20, 500, 0
for _ in range(runs):
    a = b = n = 0
    for _ in range(peeks):
        a += sum(random.random() < 0.03 for _ in range(per_peek))
        b += sum(random.random() < 0.03 for _ in range(per_peek))
        n += per_peek
        if z_test(a, b, n) > 1.96:
            false_wins += 1
            break
print(f"declared a winner with no real difference: {false_wins / runs:.1%} of tests (nominal 5%)")

Part 1 of 3 · z_statistic, fixed_sample_size, simulate

"""Sequential A/B test simulator — stdlib Python.

Compares fixed-sample vs always-valid sequential testing on a binary outcome.
Illustrates CUPED-style variance reduction.
"""

from __future__ import annotations

import math
import random


def z_statistic(success_a: int, n_a: int, success_b: int, n_b: int) -> float:
    p_a = success_a / n_a if n_a else 0
    p_b = success_b / n_b if n_b else 0
    p = (success_a + success_b) / (n_a + n_b) if (n_a + n_b) else 0
    se = math.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b)) if n_a and n_b else 1
    return (p_b - p_a) / se if se > 0 else 0


def fixed_sample_size(p_baseline: float, lift: float, alpha: float = 0.05, power: float = 0.80) -> int:
    p_treat = p_baseline * (1 + lift)
    z_alpha = 1.96
    z_beta = 0.84
    p_bar = (p_baseline + p_treat) / 2
    num = (z_alpha * math.sqrt(2 * p_bar * (1 - p_bar)) +
           z_beta * math.sqrt(p_baseline * (1 - p_baseline) + p_treat * (1 - p_treat))) ** 2
    den = (p_treat - p_baseline) ** 2
    return int(num / den)


def simulate(p_a: float, p_b: float, seed: int = 7, max_n: int = 300_000) -> dict:
    rng = random.Random(seed)
    success_a = success_b = 0
    n_a = n_b = 0
    sequential_stopped_at = None
    for _ in range(max_n):
        group = rng.random() < 0.5
        if group:
            n_b += 1
            if rng.random() < p_b:
                success_b += 1
        else:
            n_a += 1
            if rng.random() < p_a:
                success_a += 1
        if n_a > 100 and n_b > 100 and sequential_stopped_at is None:
            z = z_statistic(success_a, n_a, success_b, n_b)
            # Always-valid z-boundary (mSPRT-style): grows with log(n) so Type-I stays bounded.
            # threshold(n) ≈ sqrt(2 * log(1/alpha) + log(n)) for alpha=0.05.
            n_total = n_a + n_b
            threshold = math.sqrt(2 * math.log(1 / 0.05) + math.log(n_total))
            if abs(z) > threshold:
                sequential_stopped_at = n_total
                break

    return {
        "n_a": n_a,
        "n_b": n_b,
        "p_a_observed": success_a / n_a if n_a else 0.0,
        "p_b_observed": success_b / n_b if n_b else 0.0,
        "sequential_stop_at": sequential_stopped_at,
    }

def main() -> None:
    print("=" * 80)
    print("SEQUENTIAL A/B: fixed vs always-valid, binary outcome")
    print("=" * 80)

    baseline = 0.03
    for lift in (0.02, 0.05, 0.10):
        required = fixed_sample_size(baseline, lift)
        adjusted = int(required * 1.4)  # LLM non-determinism buffer
        print(f"\nBaseline {baseline*100:.0f}%, lift +{lift*100:.0f}%:")
        print(f"  fixed sample size (traditional, 80% power, α=0.05): {required}")
        print(f"  LLM-adjusted (×1.4 for non-determinism): {adjusted}")

    print("\nSimulation: actual lift 5% (p_a=0.03, p_b=0.0315):")
    result = simulate(0.03, 0.0315)
    print(f"  final n: A={result['n_a']}, B={result['n_b']}")
    print(f"  observed: p_a={result['p_a_observed']*100:.3f}%, p_b={result['p_b_observed']*100:.3f}%")
    print(f"  sequential stop at n={result['sequential_stop_at']}")

    print("\nSimulation: actual lift 10% (p_a=0.03, p_b=0.033):")
    result = simulate(0.03, 0.033)
    print(f"  final n: A={result['n_a']}, B={result['n_b']}")
    print(f"  observed: p_a={result['p_a_observed']*100:.3f}%, p_b={result['p_b_observed']*100:.3f}%")
    print(f"  sequential stop at n={result['sequential_stop_at']}")

    print("\nSimulation: actual lift 50% (p_a=0.03, p_b=0.045), strong signal:")
    result = simulate(0.03, 0.045)
    print(f"  final n: A={result['n_a']}, B={result['n_b']}")
    print(f"  observed: p_a={result['p_a_observed']*100:.3f}%, p_b={result['p_b_observed']*100:.3f}%")
    print(f"  sequential stop at n={result['sequential_stop_at']}")

    print("\nRead: on strong signals the sequential bound fires early (the 50% lift")
    print("case above), and the returned n_a/n_b reflect samples *up to* the stop")
    print("point, not the full horizon. For small or zero effects the bound is")
    print("deliberately conservative: that is the Type-I guarantee.")

Recap
What to keep from this lesson
  • Evals before exposure, A/B tests after: both are needed.
  • Sample size grows with the inverse square of the lift you want to detect.
  • CUPED cuts variance 30–70%; use it when you have pre-period data.
  • Peek only with sequential tests; correct for many simultaneous tests; check SRM.
  • Add 30–50% to sample sizes for LLM non-determinism.

Given the feature change (prompt / model / generation parameter), baseline metrics, expected lift, and team posture (warehouse-native OSS vs bundled SaaS), produce an A/B plan.

Produce:

1. Platform. Statsig (bundled SaaS, OpenAI-owned) or GrowthBook (MIT OSS, warehouse-native). Justify.
2. Primary metric + guardrails. Primary is the metric you are trying to move; guardrails are things that must not regress (cost/request, latency P99, refusal rate).
3. Sample size. Classical power calculation × 1.4 (LLM non-determinism buffer).
4. Design. Fixed-horizon or sequential. Sequential if you expect strong signals; fixed if the change is subtle.
5. CUPED. Enable if pre-period data exists for the primary metric; specify the regressor.
6. Correction. Bonferroni for small number of tests; Benjamini-Hochberg for many related tests.
7. SRM. Require SRM check on every experiment; halt and debug if flagged.

Hard rejects:
- Shipping on vibes. Refuse — require A/B or documented no-A/B exception.
- Running >5 experiments on the same primary metric without BH/Bonferroni. Refuse — false discovery certain.
- Skipping SRM check. Refuse — assignment bugs are common.

Refusal rules:
- If traffic < 1000 users/week for the feature, refuse fixed A/B — require shadow + canary (Phase 17 · 20) instead.
- If the primary metric is subjective (e.g., "quality") without an objective proxy, require human eval in parallel.
- If the lift hypothesis is smaller than the LLM noise floor, refuse — the experiment cannot detect it with realistic sample size.

Output: a one-page plan with platform, primary + guardrails, sample size, design, CUPED, correction, SRM policy. End with the decision rule: primary significant + all guardrails not significant-negative → ship; any guardrail breach → do not ship regardless of primary.

SolutionP1 · Sample sizes from the script

SolutionB1 · A weekend with 6,000 users

A 0.1-point difference at 3% needs about 460,000 users per arm to detect; 6,000 per arm gives a result well inside the noise. A weekend is also an unusual population. They shipped noise. They should have computed the sample size first, run for whole weeks, and treated the result as inconclusive.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismYour new prompt scores higher than the old one on your labeled set. A product manager asks why you still want a randomized online test before the full launch. Give the two-minute version.

Level 1 of 4 · about 5 minutes to answer well.

Short answer. An eval tells you whether the model can do the task on a fixed, labeled distribution. A randomized test with live users tells you whether users notice and care. A prompt can win on the labeled set and move no product metric, or move it the wrong way. You need both: the eval blocks a regression before any user sees it, and the experiment confirms the product effect after.

Two different questions.

An eval runs offline on a labeled set with a judge, which can be a rubric, a model or a person. It answers: is the output correct, helpful and safe on this distribution?

An A/B test runs online with live users assigned at random. It answers: does the variant move the user-level metric that matters, such as retention or task completion?

Why one is not enough.

Every senior engineer can name a feature that shipped because it felt better, with no experiment. Many of them regressed a product metric that nobody watched for months. The eval cannot see user preference. The experiment cannot catch a regression before exposure. Each one covers the blind spot of the other.

What to test online.

The lesson names three testable axes:

  1. Prompt wording and structure. Metrics: task success, retention, cost per request.
  2. Model choice. Metrics: task accuracy, cost per request and latency P99 together.
  3. Generation parameters such as temperature and top-p. Metric: task-specific.

The order.

Eval first. Then shadow and a canary to prove the variant is stable. Then an A/B test at a 50 percent split when the variant is a distinct alternative. When it is only an improved version of the same behavior, the canary can go to 100 percent without the A/B step. Improved means that the eval showed the gain. The canary gates do not measure task completion, so the skip trusts the eval for it.

Plausible wrong answers.

  • "The eval set is larger, so it is more reliable." The eval set is fixed and labeled, and it measures correctness, not what users prefer.
  • "Run the experiment and skip the eval to save a week." Without the eval, a regression reaches users before anyone can see it.
  • "If the eval and the experiment disagree, the experiment is wrong." They measure different things. A correct answer that users dislike is a real result.

Follow-ups an interviewer may ask.

  • (level 1) Name one metric an experiment produces that an eval cannot. Expected: a user-level metric such as retention, conversion or the thumbs-down rate.
  • (level 2) The canary passed, and the experiment shows a small drop in conversion. Ship? Expected: not by default. Write the escalation criterion before the test starts, and treat a negative primary metric as a stop.
  • (level 2) When do you skip the experiment after a canary? Expected: when the new version is an improvement of the same behavior, not an alternative with a different cost curve or tone.
  • (level 3) Why does model non-determinism change the sample size? Expected: identical inputs give different outputs, so the effective sample is smaller than the nominal one. The lesson multiplies the required sample by about 1.3 to 1.5.

Where it is taught. The A/B testing lesson separates evals from experiments, and the progressive delivery lesson places the experiment after the canary.

Weigh a trade-offA product manager reads the experiment dashboard every morning and wants to end the test on the first day the variant looks significant. Twenty other experiments run this quarter under the same plan. What is wrong with it, and what do you offer instead?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. A fixed-sample test assumes one look at a sample size chosen in advance. Looking every day and stopping at the first significant result gives noise many chances to cross the line, so the false positive rate climbs. Offer a sequential test, which stays valid under repeated looks and still allows an early stop on a clear winner. Across many experiments, correct for multiple comparisons, and reduce variance with pre-experiment data so each test needs fewer samples.

The peeking problem.

Classical A/B analysis assumes the sample size is fixed before the test. Each extra look is another test, and a stop at the first significant look selects the noise. The manager's plan is not wrong because it looks often. It is wrong because it decides on a procedure that was not built for repeated decisions.

Sequential testing.

Always-valid sequential procedures, such as the mixture sequential probability ratio test and confidence sequences, control the false positive rate under repeated looks. You can check daily and stop early on a clear winner, and the error rate stays what you set. The lesson's simulator shows the fixed and the sequential boundaries side by side.

Twenty experiments.

At 95 percent confidence, 20 experiments produce about one false positive by chance. Two corrections exist. Bonferroni divides the error rate by the number of tests, which is strict. Benjamini-Hochberg controls the false discovery rate and is less conservative. Choose by the cost of one false launch against the cost of missing a real win.

Variance reduction.

CUPED regresses out the variance that pre-experiment data explains. The lesson gives a typical reduction of 30 to 70 percent, which raises the effective sample size at no cost in traffic. That is the honest way to shorten a test.

Two more checks.

A sample ratio mismatch check catches a broken assignment before you read any result. Non-determinism in model output lowers the effective sample size, so the lesson multiplies the required sample by about 1.3 to 1.5.

Plausible wrong answers.

  • "Stopping early is fine when the p-value is small." Under a fixed-sample test, a small p-value on the first day is partly selected noise. Only a sequential procedure keeps that stop valid.
  • "Run all the tests at 95 percent and ship the winners." About one winner is a false positive by chance. Correct for multiple comparisons.
  • "A longer test is always more reliable." Longer helps only if the assignment is sound. Check the sample ratio first.

Follow-ups an interviewer may ask.

  • (level 3) Bonferroni or Benjamini-Hochberg for the quarter? Expected: Bonferroni when any false launch is costly, Benjamini-Hochberg when you accept a controlled share of false discoveries in exchange for power.
  • (level 3) What does CUPED need, and what does it give? Expected: it needs a pre-period metric for each unit, and it gives a tighter estimate from the same traffic.
  • (level 4) A new model needs a larger sample than the quarter allows. What do you change? Expected: pick a primary metric with lower variance, apply CUPED, or extend the test. Do not shorten it by stopping early under a fixed-sample procedure.
