Why this came about

Users wanted agents that remember them across conversations, while long conversations outgrew context windows. LangGraph added a long-term store beside per-thread checkpoints, and middleware for trimming, summarizing and clearing context.

The problem: two kinds of memory

A checkpointer gives each thread its conversation (Lesson 14.81). That raises two problems. A thread keeps growing, and every model call resends all of it, until it no longer fits or costs too much. And some facts belong to the customer, not to one conversation: "reply in Hindi", "refunds to UPI, please". Next week's conversation is a new thread and should still know them. Lesson 14.64 called these short-term and long-term memory. LangGraph handles the first in the thread's messages and the second in a store.

In plain words

In plain words first
Your head and your notebook
  • Short-term memory is what is in your head during one meeting: what was said a minute ago, what you are halfway through. When the meeting ends, it is gone.
  • Long-term memory is the notebook you carry between meetings: a few short notes about each person ("replies in Hindi", "refunds to UPI"). You read it before the next meeting, even weeks later.

In LangGraph the "head" is the thread's state, saved by the checkpointer under a thread_id (Lesson 14.81). The "notebook" is a separate database called the store. A new thread starts with an empty head but the same notebook.

The notebook fits in plain Python, as a dictionary that outlives each conversation:

notebook = {}                                   # long-term memory: survives every conversation

def remember(customer_id, fact):                # write a note on that customer's page
    notebook.setdefault(customer_id, []).append(fact)

def recall(customer_id):                        # read that customer's page
    return notebook.get(customer_id, [])

monday = ["customer: Please talk to me in Hindi."]
remember("C-42", "Prefers replies in Hindi")

tuesday = ["customer: Hello"]                    # a new conversation: no history at all
print("Tuesday's history:", tuesday)
print("notebook for C-42:", recall("C-42"))      # ...but the notebook remembers
print("notebook for C-77:", recall("C-77"))      # and keeps customers apart
What you should see
Tuesday's history: ['customer: Hello']
notebook for C-42: ['Prefers replies in Hindi']
notebook for C-77: []

Every long-term memory system, LangGraph's included, is this notebook plus answers to four questions: whose page is it (the namespace), how to find the right note among hundreds (search by meaning), who decides when to read and write (your code or the model), and when notes are written (during or after the conversation). This lesson answers them in that order, after first dealing with the head that keeps growing.

What a memory is, and what it is not. A memory is not a saved question and answer; the checkpointer already keeps the raw conversation. A memory is a short fact distilledlater · 14.133 from conversations. From "I'm ordering a gift for my mother, please send refunds to UPI, and keep it short", three memories are worth keeping: "Buys gifts for family", "Refunds to UPI", "Prefers short replies". In one line: the checkpointer keeps what was said; the store keeps what was learned from it.

Question Options Where in this lesson

The three choices are independent: any kind of memory can be read either way and written at either time.

Idea 1 · Trim a thread without breaking it

Three turns, each with a tool call:

from langchain_core.messages import SystemMessage, HumanMessage, AIMessage, ToolMessage, trim_messages
from langchain_core.messages.utils import count_tokens_approximately

def turn(n, order, status):
    return [HumanMessage(f"Where is {order}?"),
            AIMessage("", tool_calls=[{"name": "get_order_status", "args": {"order_id": order}, "id": f"c{n}"}]),
            ToolMessage(f"{order} is {status}", tool_call_id=f"c{n}"),
            AIMessage(f"{order} is {status}.")]

history = [SystemMessage("You are ShopKart support. Be brief.")]
history += turn(1, "A-1001", "shipped") + turn(2, "A-1002", "processing") + turn(3, "A-1003", "delivered")
print(len(history), "messages,", count_tokens_approximately(history), "tokens (approximately)")
What you should see
13 messages, 186 tokens (approximately)

Keep only the most recent messages that fit in 45 tokens:

cut = trim_messages(history, max_tokens=45, strategy="last", token_counter=count_tokens_approximately)
print([type(m).__name__ for m in cut])
What you should see
['ToolMessage', 'AIMessage']

The cut fell in the middle of a turn: the kept history starts with a ToolMessage whose tool call was trimmed away, and the system message is gone. A provider rejects that conversation (Lesson 14.56's rule that every tool result follows its call). Tell the trimmer where a valid history may start:

kept = trim_messages(history, max_tokens=80, strategy="last", token_counter=count_tokens_approximately,
                     include_system=True, start_on="human")      # keep the system message; start on a human turn
print([type(m).__name__ for m in kept])
print(kept[1].content)
What you should see
['SystemMessage', 'HumanMessage', 'AIMessage', 'ToolMessage', 'AIMessage']
Where is A-1003?

include_system=True keeps the instructions, and start_on="human" drops messages until the history begins with a person's turn, so tool calls and results stay together. Token counts here are approximate; use the provider's counter when the limit is tight.

Trim the saved thread, or only what the model sees

There are two places to apply that trim, and the difference matters more than the trim itself.

In plain words first
The archive and the photocopy
  • Option A, change the saved thread. Delete old messages from the state. The checkpointer saves the shorter version, and the deleted turns are gone from the thread for good. Like shredding the old pages of a case file.
  • Option B, change only the request. Just before each model call, send a trimmed copy. The saved thread stays complete. Like photocopying the last few pages for the model while the full file stays in the archive.

Middleware (Lesson 14.75) gives you both. A @before_model hook returns state updates, so its RemoveMessage really deletes. A @wrap_model_call hook receives the request about to be sent, and request.override(messages=...) changes that one request only:

from langchain.agents import create_agent
from langchain.agents.middleware import before_model, wrap_model_call
from langchain_core.messages import RemoveMessage
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph.message import REMOVE_ALL_MESSAGES

def last_turns(messages):
    return trim_messages(messages, strategy="last", max_tokens=4, token_counter=len,   # len: count messages
                         start_on="human")

sent_sizes = []                                    # how many messages the model received, call by call

@before_model
def trim_saved(state, runtime):                    # Option A: rewrite the thread itself
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), *last_turns(state["messages"])]}

@wrap_model_call
def trim_sent(request, handler):                   # Option B: change only this request
    return handler(request.override(messages=last_turns(request.messages)))

@wrap_model_call
def spy(request, handler):
    sent_sizes.append(len(request.messages))
    return handler(request)

for label, middleware in [("A · trim the saved thread", [trim_saved, spy]),
                          ("B · trim only what is sent", [trim_sent, spy])]:
    sent_sizes.clear()
    agent = create_agent(chat, tools=[], middleware=middleware, checkpointer=InMemorySaver())
    cfg = {"configurable": {"thread_id": label}}
    for i in range(5):                             # five short turns
        agent.invoke({"messages": [{"role": "user", "content": f"question {i}"}]}, cfg)
    print(f"{label}: sent {sent_sizes}, saved {len(agent.get_state(cfg).values['messages'])}")
What you should see
A · trim the saved thread: sent [1, 3, 3, 3, 3], saved 4
B · trim only what is sent: sent [1, 3, 3, 3, 3], saved 10
Reading this output
  • sent [...] is the number of messages the model received on each of the five turns. Both options send the same, so cost and speed are the same.
  • saved is what the thread holds afterwards. Option A kept only the last few messages; the first turns are gone. Option B still holds all ten: five questions and five answers.
Option A: @before_model with RemoveMessage Option B: @wrap_model_call with request.override
What changes The stored thread Only what the model receives
Full history afterwards No Yes
Audits and replays Weakened Intact
Reversible No Yes: change the rule and the old turns are still there
Storage Smaller Grows; needs a retention policy

In regulated work, prefer Option B. In pharma, finance or healthcare you may have to show later what the system saw, said and did; deleting messages from the thread destroys part of that record. Know which built-ins behave which way: SummarizationMiddleware (Lesson 14.75) rewrites the saved thread with a summary, like Option A; context editing, next, changes only the request, like Option B.

Clear old tool results instead (context editing)

Trimming removes whole turns by age. Often the bulk is a few large tool results the model used once and keeps resending. Context editing replaces old tool results with a placeholder, by usefulness, and keeps the newest ones:

from langchain.agents.middleware import ContextEditingMiddleware, ClearToolUsesEdit
from langchain.tools import tool

@tool
def get_order_status(order_id: str) -> str:
    """Return the full tracking log for a ShopKart order ID like 'A-1001'."""
    return f"{order_id}: " + "scan event; " * 200        # a bulky result, about 600 tokens

last_request = []

@wrap_model_call
def capture(request, handler):
    last_request[:] = request.messages
    return handler(request)

agent = create_agent(chat, tools=[get_order_status], checkpointer=InMemorySaver(), middleware=[
    ContextEditingMiddleware(edits=[ClearToolUsesEdit(trigger=1000, keep=1)]),   # tiny trigger for the demo
    capture,
])
cfg = {"configurable": {"thread_id": "tracking"}}
for order in ["A-1001", "A-1002", "A-1003"]:
    agent.invoke({"messages": [{"role": "user", "content": f"Track {order}"}]}, cfg)

def tool_results(messages):
    return [m.content[:22] for m in messages if m.type == "tool"]

print("sent to model:", tool_results(last_request))
print("saved:        ", tool_results(agent.get_state(cfg).values["messages"]))
What you should see
sent to model: ['[cleared]', '[cleared]', 'A-1003: scan event; sc']
saved:         ['A-1001: scan event; sc', 'A-1002: scan event; sc', 'A-1003: scan event; sc']
Reading this output
  • Sent to the model: the two older results became [cleared]; the newest (keep=1) went in full. The tool calls themselves stay, so the conversation is still valid for the provider.
  • Saved: all three results are untouched. Context editing changes the request, not the thread.
  • Its settings: trigger is the request size in tokens at which clearing starts (default 100,000), keep how many recent results survive (default 3), exclude_tools results never to clear, and placeholder the replacement text (default "[cleared]").

Offload big results so they never enter the context

Context editing hides a result from later requests, so the model cannot look at it again without re-running the tool. Offloading stores the full result elsewhere and gives the model a short stub with an ID, plus a tool to read slices:

RESULTS = {}                                      # stands in for a file, bucket or table

@tool
def orders_report(region: str) -> str:
    """Run the daily orders report for a region. Returns a summary and a result ID."""
    rows = [{"order": f"A-{1000 + i}", "region": region, "amount": 100 + i} for i in range(5000)]
    rid = f"res_{len(RESULTS) + 1}"
    RESULTS[rid] = rows                           # 1. the full result goes to storage
    return f"{len(rows)} rows saved as {rid}. Columns: order, region, amount. First: {rows[0]}"   # 2. a stub

@tool
def read_result(result_id: str, offset: int = 0, limit: int = 5) -> str:
    """Read a slice of a saved result by its ID."""
    rows = RESULTS.get(result_id)
    return str(rows[offset:offset + limit]) if rows else "No such result."              # 3. only what is asked

print(orders_report.invoke({"region": "North"}))
print(read_result.invoke({"result_id": "res_1", "offset": 4998, "limit": 2}))
print(len(str(RESULTS["res_1"])), "characters never entered the context")
What you should see
5000 rows saved as res_1. Columns: order, region, amount. First: {'order': 'A-1000', 'region': 'North', 'amount': 100}
[{'order': 'A-5998', 'region': 'North', 'amount': 5098}, {'order': 'A-5999', 'region': 'North', 'amount': 5099}]

Technique Removes Changes the saved thread? The model can see it again?
Trimming in @before_model Old turns, by age Yes No
Trimming in @wrap_model_call Old turns, by age, per request No No (not sent), but it is still saved
Summarization (SummarizationMiddleware) Old turns, replaced by a summary Yes Only the summary
Context editing Old tool results, by usefulness No Only by re-running the tool
Offloading Large results, before they enter the context No Yes, through a read tool

Rule of thumb: trim what the model sees, not what you store, unless you have a reason to delete.

Idea 2 · The store: memory across threads

A thread's checkpoints belong to one conversation. The store is a separate place for facts that should outlive a conversation, such as a customer's language. Entries are filed under a namespace (a tuple, like a folder path) and a key. Save three facts for two customers and read one customer's facts back:

from langgraph.store.memory import InMemoryStore

store = InMemoryStore()
store.put(("customers", "C-42", "profile"), "language", {"value": "Hindi"})
store.put(("customers", "C-42", "profile"), "refund_to", {"value": "UPI"})
store.put(("customers", "C-77", "profile"), "language", {"value": "English"})

print(store.get(("customers", "C-42", "profile"), "language").value)
print({item.key: item.value["value"] for item in store.search(("customers", "C-42"))})
What you should see
{'value': 'Hindi'}
{'language': 'Hindi', 'refund_to': 'UPI'}
Reading this output
  • store.get returns an Item, not just your dictionary: .value is the dictionary you saved, and the item also carries .namespace, .key, and .created_at / .updated_at timestamps the store adds.
  • store.search(("customers", "C-42")) with no query lists every item whose namespace starts with that tuple, up to limit (default 10). That prefix rule is what makes per-customer namespaces work, and what makes a too-short namespace dangerous (the debugging exercise).
  • put with an existing key replaces the value: that is how a memory is updated.

A store holds JSON values under a namespace (a tuple, like a folder path) and a key. Namespaces are the design decision: here everything about a customer sits under ("customers", customer_id, ...), so one search returns a customer's profile and nothing else.

Idea 3 · Using the store from a graph

Compile the graph with a store, and every node can reach it through runtime.store. The customer ID comes from the run's context (Lesson 14.80), which your application fills from the signed-in user:

from dataclasses import dataclass
from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.runtime import Runtime

@dataclass
class Session:
    customer_id: str                                      # from the signed-in user, never from the model

class ChatState(TypedDict, total=False):
    msg: str
    reply: str

def remember(state, runtime: Runtime[Session]):
    if "hindi" in state["msg"].lower():                   # a model would extract this in a real system
        runtime.store.put(("customers", runtime.context.customer_id, "profile"), "language", {"value": "Hindi"})
    return {}

def answer(state, runtime: Runtime[Session]):
    pref = runtime.store.get(("customers", runtime.context.customer_id, "profile"), "language")
    lang = pref.value["value"] if pref else "English"
    return {"reply": f"[replying in {lang}] How can I help?"}

b = StateGraph(ChatState, context_schema=Session)
b.add_node("remember", remember); b.add_node("answer", answer)
b.add_edge(START, "remember"); b.add_edge("remember", "answer"); b.add_edge("answer", END)
memory_store = InMemoryStore()
bot = b.compile(checkpointer=InMemorySaver(), store=memory_store)

bot.invoke({"msg": "Please talk to me in Hindi"}, {"configurable": {"thread_id": "monday"}}, context=Session("C-42"))
for thread, customer in [("tuesday", "C-42"), ("other-customer", "C-77")]:
    out = bot.invoke({"msg": "hello"}, {"configurable": {"thread_id": thread}}, context=Session(customer))
    print(f"{thread:15} {customer} -> {out['reply']}")
What you should see
tuesday         C-42 -> [replying in Hindi] How can I help?
other-customer  C-77 -> [replying in English] How can I help?

Monday's conversation saved a preference; Tuesday's conversation, a different thread, used it; another customer was not affected. create_agent accepts store= as well, and tools can read it, for example a remember tool the model calls when the customer states a preference.

Idea 4 · Search memories by meaning

With an embedding function, the store indexes values and searches them by similarity, so the right note can be found from a question that does not share its words:

VOCAB = ["hindi", "language", "address", "deliver", "gift", "wrap", "refund", "upi", "paid"]

def tiny_embed(texts):
    """A stand-in embedding: one number per vocabulary word. Use a real embedding model in practice."""
    return [[float(w in t.lower()) + 1e-3 for w in VOCAB] for t in texts]

notes = InMemoryStore(index={"embed": tiny_embed, "dims": len(VOCAB), "fields": ["text"]})
notes.put(("customers", "C-42", "notes"), "n1", {"text": "Prefers replies in Hindi"})
notes.put(("customers", "C-42", "notes"), "n2", {"text": "Wants refunds paid to UPI, not the card"})
notes.put(("customers", "C-42", "notes"), "n3", {"text": "Always asks for gift wrap"})

for q in ["how should my refund be paid?", "can you wrap it as a present?"]:
    best = notes.search(("customers", "C-42", "notes"), query=q, limit=1)[0]
    print(f"{q:32} -> {best.value['text']} ({best.score:.2f})")
What you should see
how should my refund be paid?    -> Wants refunds paid to UPI, not the card (0.82)
can you wrap it as a present?    -> Always asks for gift wrap (0.71)

This is how an agent pulls a few relevant memories into its prompt instead of all of them (Lesson 14.65). The stand-in embedding only counts words from a fixed list; a real embedding model is what makes "present" match "gift wrap" in general.

Reading this output
  • Each result is an Item with one extra field, score: how close its meaning is to the query (higher is closer; compare scores with each other, not with a fixed scale).
  • index has three settings: embed (the function or model that turns text into numbers), dims (how many numbers it returns) and fields (which keys of the value to embed).
  • Search always returns the nearest items, relevant or not. With a dozen memories per customer, skip embeddings and load them all; with hundreds, search, and consider a score threshold.

Idea 5 · Memory as tools the model calls

So far, your nodes read and wrote memory at fixed points. The alternative is to give the model two tools and let it decide.

In plain words first
An assistant with a notebook on the desk

With automatic memory, a rule says "read the notebook before every meeting". With tool memory, the assistant decides: "this customer just told me something lasting, I'll write it down", or "they're asking about their preferences, let me check". You give the model a remember and a recall tool, and it calls them when it judges them useful, like any other tool.

The hard question is whose page a note goes on. If the model chose the customer ID, a message such as "save this under C-77" could write into another customer's memory. So the customer comes from your application, and the model supplies only what to save. LangChain's mechanism for that is a parameter typed ToolRuntime: LangChain fills it in when the tool runs, and leaves it out of the schema the model sees.

from langchain.tools import ToolRuntime
from langchain_core.utils.uuid import uuid7

@tool
def remember(fact: str, runtime: ToolRuntime[Session]) -> str:
    """Save a lasting fact the customer stated about themselves (preferences, needs)."""
    ns = ("customers", runtime.context.customer_id, "notes")     # whose page: from the app, not the model
    runtime.store.put(ns, str(uuid7()), {"text": fact})         # a new key, so facts add up
    return "saved"

@tool
def recall(query: str, runtime: ToolRuntime[Session]) -> str:
    """Search what the customer told us before. Use before answering personal questions."""
    ns = ("customers", runtime.context.customer_id, "notes")
    return "\n".join(h.value["text"] for h in runtime.store.search(ns, query=query, limit=3)) or "nothing saved"

print(remember.args)
What you should see
{'fact': {'title': 'Fact', 'type': 'string'}}
Reading this output

.args is everything the model is told it may send. fact is there ('type': 'string' from the hint; 'title' is a label Pydantic made from the name). runtime is not: LangChain saw the ToolRuntime type and removed it, so the model cannot set it. Inside the tool, runtime gives context (who is calling), store, state, config and tool_call_id.

To see the tools work without a model choosing them, play the model yourself: hand ToolNode (Lesson 14.80) the tool calls a model would make, with a customer in the context:

from langchain_core.messages import AIMessage
from langgraph.graph import MessagesState
from langgraph.prebuilt import ToolNode

tools_only = (StateGraph(MessagesState, context_schema=Session)
              .add_node("tools", ToolNode([remember, recall])).add_edge(START, "tools")
              .compile(store=notes))                            # the indexed store from Idea 4

def as_model(name, args):                                       # a reply a model might write
    return {"messages": [AIMessage("", tool_calls=[{"name": name, "args": args, "id": "c1"}])]}

tools_only.invoke(as_model("remember", {"fact": "Ships gifts to Pune"}), context=Session("C-42"))
for customer in ["C-42", "C-77"]:
    out = tools_only.invoke(as_model("recall", {"query": "where to deliver gifts"}), context=Session(customer))
    print(customer, "->", out["messages"][-1].content.splitlines()[0])
What you should see
C-42 -> Ships gifts to Pune
C-77 -> nothing saved

The same tool call gave C-42 their notes and C-77 nothing: the namespace came from the context, which your application sets from the signed-in user, so no wording in a message can redirect it.

Idea 6 · Load automatically, recall on demand

Tool memory is flexible, but the model can forget to look, or save trivia. Compare the three ways an agent can keep and reach memory:

Checkpointer Store, loaded automatically Store, through tools
Answers "Where were we in this conversation?" "What must I always know about this customer?" "Is there anything saved that might help now?"
Scope One thread All threads All threads
Triggered by The framework, every step Your code, every turn The model, when it chooses
Reliable? Yes Yes The model may skip it
Best for Continuity, crash recovery, approval pauses Language, refund method, tenant rules Long-tail facts and past episodes; "remember this" requests
Risk The thread outgrows the context Loads memory even when irrelevant Missed memories, junk saved

The checkpointer and the store are two places to keep memory; automatic loading and tools are two ways of reaching the store. Production systems use all three: a short profile loaded into every model call, and a recall tool for the rest. @dynamic_prompt (Lesson 14.75) builds the system prompt before each call, so it can read the store:

from langchain.agents.middleware import dynamic_prompt

notes.put(("customers", "C-42", "profile"), "language", {"text": "Reply in Hindi"})
notes.put(("customers", "C-42", "profile"), "refunds", {"text": "Refunds go to UPI"})

@dynamic_prompt
def load_profile(request):                                       # layer 1: every model call
    ns = ("customers", request.runtime.context.customer_id, "profile")
    lines = "\n".join(f"- {i.value['text']}" for i in request.runtime.store.search(ns, limit=5))
    return f"You are ShopKart support.\nKnown about this customer:\n{lines}"

seen = {}

@wrap_model_call
def show_prompt(request, handler):
    seen["prompt"] = request.system_message.content
    return handler(request)

agent = create_agent(chat, tools=[recall], middleware=[load_profile, show_prompt],   # layer 2: recall
                     context_schema=Session, store=notes, checkpointer=InMemorySaver())
agent.invoke({"messages": [{"role": "user", "content": "Hi"}]},
             {"configurable": {"thread_id": "t-profile"}}, context=Session("C-42"))
print(seen["prompt"])
What you should see
You are ShopKart support.
Known about this customer:
- Reply in Hindi
- Refunds go to UPI

Why two layers: automatic loading carries what must never be missed, so a skipped recall costs little; the tool lets the model search for what the current message does not obviously ask for, and rephrase when the first search misses. Never put anything critical only behind the tool.

Idea 7 · When memories are written, and how they stay clean

Hot path: during the conversation Background: after it
How The agent calls remember mid-conversation A job reads the finished thread and extracts memories
Available At once After the job runs, usually by the next conversation
Latency for the customer An extra tool call None
Quality Depends on the model noticing Better: sees the whole conversation, can merge and resolve conflicts

Production systems usually extract in the background and keep a remember tool only for explicit "remember this" requests, which the customer expects to work at once.

In plain words first
Extract, compare, decide, store
  1. Extract: give the transcript to a model with "list lasting facts, preferences, events and rules about this customer", and ask for structured output (Lesson 14.73).
  2. Compare: for each new item, search the store for similar existing memories.
  3. Decide: ask a model, with the new item and the similar old ones side by side, to add it, update an old one, delete one that is now false, or skip.
  4. Store: plain code carries out the decisions with put and delete.

The add/update/delete decision is not part of your agent's prompt. It is a separate model call inside the memory job. Lesson 14.65 builds the whole pipeline by hand.

Steps 1 to 3 are model calls with structured output. Step 4 is plain code you can test. Here it runs on the decisions a model would return after the customer said "Send refunds to my card from now on, and I no longer need gift wrap":

from typing import Literal
from pydantic import BaseModel

class Op(BaseModel):                             # one decision, as the deciding model returns it
    action: Literal["add", "update", "delete", "skip"]
    key: str | None = None                       # which existing memory, for update or delete
    text: str | None = None                      # the memory text, for add or update

def apply_ops(store, ns, ops: list[Op]) -> None:
    for op in ops:
        if op.action == "add":
            store.put(ns, str(uuid7()), {"text": op.text})
        elif op.action == "update":
            store.put(ns, op.key, {"text": op.text})    # same key: replaces, never duplicates
        elif op.action == "delete":
            store.delete(ns, op.key)

ns = ("customers", "C-42", "notes")
apply_ops(notes, ns, [Op(action="update", key="n2", text="Wants refunds paid to the card"),
                      Op(action="delete", key="n3")])
print(sorted(i.value["text"] for i in notes.search(ns, limit=20)))
What you should see
['Prefers replies in Hindi', 'Ships gifts to Pune', 'Wants refunds paid to the card']

update kept one refund preference instead of two contradictory ones; delete removed a fact that is no longer true. Without the compare-and-decide steps, the store would now say both "UPI" and "card".

LangMem, LangChain's memory library, packages this: create_manage_memory_tool and create_search_memory_tool are ready-made remember and recall tools, and create_memory_store_manager is the background extract-compare-decide-store job. Their namespaces can contain {langgraph_user_id}, filled from the run's config, so identity again comes from your application. The manager does not delete unless you set enable_deletes=True.

Check your mental model
  • ✗ "The store keeps the conversation."
    ✓ The checkpointer keeps each thread's conversation. The store keeps short memories distilled from conversations.
  • ✗ "The checkpointer only keeps the messages."
    ✓ It saves the full state at every step, including tool outputs and pending work; that is what makes resuming possible.
  • ✗ "With a recall tool the agent always finds what it needs."
    ✓ The model may not call it. Load anything critical automatically.
  • ✗ "The model decides whose memory it uses."
    ✓ The application does, through the context that tools receive in runtime.context. The model never sees it.
  • ✗ "Summarization keeps my full history."
    ✓ SummarizationMiddleware rewrites the saved thread. A wrap_model_call trim and context editing change only the request.
  • ✗ "A new memory should always be added."
    ✓ Compare it with similar ones first, then add, update, delete or skip; otherwise the store fills with duplicates and contradictions.

Production notes

  • Stores: InMemoryStore is for development; PostgresStore (with pgvector for search) or the platform's built-in store (Lesson 14.86) for production.
  • Who may write what: the namespace must come from your authentication, never from the model's arguments, or a crafted message can read or write another customer's memories (Lesson 15.24).
  • What to remember: preferences and facts the customer stated, with when they said it. Not guesses about them, and not sensitive data you have no basis to keep.
  • Deletion: a customer can ask you to delete what you know. With per-customer namespaces, that is one loop, the modify exercise.

Solutions

SolutionP1 · Whole turns, from the end

Still the last turn only: two turns plus the system message are about 130 tokens, over the limit, and the trimmer never keeps half a turn when start_on="human". At about 130 tokens or more it keeps the last two turns. The budget is spent in whole turns, which is why long tool results (Lesson 14.75's context editing) are often the better thing to cut.

SolutionB1 · Orphaned tool results

The history starts with a ToolMessage whose tool call is gone, so the provider rejects it: a tool result must follow the assistant turn that requested it. Even where a request is accepted, losing the system message removes the agent's instructions, so it silently stops following ShopKart's rules. Always keep the system message and start on a human turn.

SolutionD1 · The namespace forgot the customer

The namespace ("customers", "profile") has no customer ID, so every customer shares one profile, and the last preference saved wins for everyone. It is a privacy incident because the same mistake with an address or a phone number would show one customer's data to another. Put the customer ID, taken from your authentication context, in every namespace, as Idea 3 does, and add a test with two customers.

def forget(customer_id):
    """Delete everything stored about a customer, for a deletion request."""
    for item in memory_store.search(("customers", customer_id), limit=100):
        memory_store.delete(item.namespace, item.key)

Check your understanding

Explain the mechanismHow does LangGraph handle short-term and long-term memory?

Worked answer. Short-term memory is the thread's state, usually its messages, saved by the checkpointer and loaded on each call with the same thread ID; it is kept within budget by trimming, deleting messages or summarizing. Long-term memory is a store, separate from threads, holding JSON documents under namespaces such as a user ID; nodes and tools read and write it through the runtime, and with an index it supports semantic search. Short-term is per conversation; long-term is per user or organization, across conversations.

A plausible wrong answer. "Long-term memory means keeping the whole chat history forever." Old histories are expensive to resend and hard to search; long-term memory keeps selected facts.

Follow-ups. How do you decide what to write to long-term memory?

Debug a failureAfter trimming was added, the agent occasionally fails with a 400 error about tool results. Why?

Worked answer. The trim boundary sometimes falls between an assistant message with tool calls and its tool results, leaving results without their calls, which providers reject. Set start_on="human" (and keep the system message), or trim by whole turns, and add a test with a long history ending in a tool call. If turns are large because of tool results, clear old tool results instead of whole turns.

A plausible wrong answer. "The model is producing bad tool calls." The calls were fine; the trimming removed them.

Follow-ups. How would you trim when a single tool result is larger than the budget?

Defend a designShould an agent decide for itself what to remember?

Worked answer. Partly. The model is good at spotting candidate facts, so I let it propose memories, through a tool or an extraction step, but the application decides the namespace from authentication, filters what categories may be stored, records when and where each fact came from, and lets the customer see and delete it. Memories the model infers rather than hears ("probably price-sensitive") should not be stored as facts. Without those controls, memory becomes a source of wrong personalization and privacy risk.

A plausible wrong answer. "Yes, let the agent save anything that seems useful." Then you have unreviewed personal data with no provenance.

Follow-ups. How would you evaluate whether memory improves answers (Lesson 14.65)?
