Databricks comes at agents from the lakehouse: data, models, tools, prompts and agents are all assets in Unity Catalog, governed by the same permissions and lineage, and MLflow (which Databricks created) is the backbone for tracing, evaluation and deployment. That makes it strong for teams that want to build and measure their own agents over lakehouse data.

Why this came about

Databricks grew from Apache Spark into a data and AI platform. It added MLflow for experiment tracking (2018), Unity Catalog for governance and Agent Bricks (2025) for building agents next to the data.

In plain words first
A data platform that grew an agent toolbox

Databricks approaches agents from the data side: Agent Bricks builds and optimizes agents on your data, MLflow tracks experiments, traces and evaluations, model serving hosts models and agents, and Unity Catalog governs data, models and tools with one set of permissions and lineage. It suits teams whose data already lives there.

Step 1 · An agent in the ResponsesAgent interface

Databricks asks agents to implement MLflow's ResponsesAgent: input and output follow the OpenAI Responses format, so an agent written with any library works the same way in Model Serving, the AI Playground, the Review App, evaluation and monitoring. Model Serving endpoints are OpenAI-compatible, so the plain OpenAI SDK calls them (here, our lab server stands in).

import json, tempfile, uuid
import mlflow
from mlflow.pyfunc import ResponsesAgent
from mlflow.types.responses import ResponsesAgentRequest, ResponsesAgentResponse
from openai import OpenAI
from mockllm import start

mlflow.set_tracking_uri(f"sqlite:///{tempfile.mkdtemp()}/mlflow.db")   # in Databricks: "databricks" (the default)
mlflow.set_experiment("shopkart-dbx")
mlflow.openai.autolog()                                                # trace every model call

# Live: OpenAI(api_key=<token>, base_url="https://<workspace-host>/serving-endpoints"), model="databricks-claude-sonnet-5-5"
client = OpenAI(base_url=start(), api_key="mock")
ENDPOINT = "mock-model"
ORDERS = {"A-1001": "shipped"}
TOOLS = [{"type": "function", "function": {"name": "get_order_status", "description": "Shipping status for an order ID like 'A-1001'.",
          "parameters": {"type": "object", "properties": {"order_id": {"type": "string"}}, "required": ["order_id"]}}}]

class ShopKartAgent(ResponsesAgent):
    """Databricks' agent interface: Responses-style input and output."""

    @mlflow.trace(span_type="TOOL")
    def get_order_status(self, order_id: str) -> str:
        return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

    def predict(self, request: ResponsesAgentRequest) -> ResponsesAgentResponse:     # traced automatically
        messages = [{"role": "system", "content": "You are ShopKart's support assistant. Be brief."}]
        messages += [{"role": i.role, "content": i.content} for i in request.input]
        for _ in range(5):
            msg = client.chat.completions.create(model=ENDPOINT, messages=messages, tools=TOOLS).choices[0].message
            if not msg.tool_calls:
                return ResponsesAgentResponse(output=[self.create_text_output_item(text=msg.content, id=str(uuid.uuid4()))])
            messages.append(msg.model_dump(exclude_none=True))
            for call in msg.tool_calls:
                result = self.get_order_status(**json.loads(call.function.arguments))
                messages.append({"role": "tool", "tool_call_id": call.id, "content": result})

agent = ShopKartAgent()
r = agent.predict(ResponsesAgentRequest(input=[{"role": "user", "content": "Where is A-1001?"}]))
print("answer:", r.output[0].content[0]["text"])

mlflow.flush_trace_async_logging()                                     # traces are written in the background
trace = mlflow.search_traces(return_type="list")[0]
print("spans:", [s.name for s in trace.data.spans])
What you should see
answer: Here is what I found: A-1001 is shipped
spans: ['predict', 'Completions', 'get_order_status', 'Completions']

(MLflow also prints a few INFO lines about creating the experiment.) One trace per request, with the model calls and the tool call as child spans, captured without any tracing code in the loop. Implement predict_stream too, so users see tokens as they arrive.

Step 2 · Evaluate before you deploy

MLflow's genai.evaluate runs the agent over a dataset and scores each trace. Code scorers check facts you can compute; LLM judges (Correctness, RelevanceToQuery, RetrievalGroundedness, Safety, Guidelines with your own rules) handle the rest. Lesson 12.15 introduced the API; here it scores the agent's trace, not just its text.

from mlflow.genai.scorers import scorer

@scorer
def used_order_tool(trace) -> bool:
    """Did the agent look the order up instead of guessing?"""
    return any(span.name == "get_order_status" for span in trace.data.spans)

@scorer
def mentions_status(outputs) -> bool:
    return "shipped" in json.dumps(outputs)

data = [{"inputs": {"request": {"input": [{"role": "user", "content": "Where is A-1001?"}]}}}]
results = mlflow.genai.evaluate(
    data=data,
    predict_fn=lambda request: agent.predict(ResponsesAgentRequest(**request)).model_dump(),
    scorers=[used_order_tool, mentions_status])          # add Correctness(), Guidelines(...) with a judge model
print(dict(sorted((name, float(value)) for name, value in results.metrics.items() if name.endswith("/mean"))))
What you should see
{'mentions_status/mean': 1.0, 'used_order_tool/mean': 1.0}

MLflow prints a summary and a link to the run as well. In Databricks, keep the dataset as a Unity Catalog evaluation dataset, grow it from production traces and Review App labels, and gate deployment on it (Lesson 12.11).

Step 3 · Deploy, monitor and improve

Deployment on Databricks is two calls: log the agent to MLflow, declaring the resources it needs (the model endpoint, the functions, the search index), and then agents.deploy the logged version. This block needs a Databricks workspace, so it is marked as live-only and is not run by the course's checker.

# RUN_LIVE: in a Databricks workspace, with the databricks-agents package
import mlflow
from databricks import agents
from mlflow.models.resources import DatabricksServingEndpoint, DatabricksFunction, DatabricksVectorSearchIndex

mlflow.set_registry_uri("databricks-uc")
with mlflow.start_run():
    info = mlflow.pyfunc.log_model(
        name="agent", python_model="agent.py",                    # the file that defines ShopKartAgent and calls mlflow.models.set_model
        resources=[DatabricksServingEndpoint(endpoint_name="databricks-claude-sonnet-5-5"),
                   DatabricksFunction(function_name="shopkart.ops.get_order_status"),
                   DatabricksVectorSearchIndex(index_name="shopkart.docs.policy_index")],   # credentials are provisioned for these
        registered_model_name="shopkart.agents.support_agent")
agents.deploy("shopkart.agents.support_agent", info.registered_model_version)   # serving endpoint + Review App + monitoring

agents.deploy creates a Model Serving endpoint, turns on inference tables and tracing, and opens the Review App, where domain experts chat with the agent and label answers. Production monitoring then runs your scorers and judges on a sample of live traces, so quality shows up on a dashboard next to latency and cost. Declaring resources lets Databricks issue short-lived credentials for exactly those endpoints, functions and indexes; with on-behalf-of-user authentication, tools run with the end user's own Unity Catalog permissions instead.

Step 4 · Governed tools: Unity Catalog, AI Search, Genie and MCP

Unity Catalog functions are the Databricks way to define tools: SQL or Python functions with typed parameters and comments, governed by GRANT EXECUTE, discoverable, and reusable from any framework.

CREATE OR REPLACE FUNCTION shopkart.ops.get_order_status(order_id STRING COMMENT 'Order ID like A-1001')
RETURNS STRING
COMMENT 'Return the shipping status of a ShopKart order'
RETURN SELECT concat(order_id, ' is ', status) FROM shopkart.shop.orders o WHERE o.order_id = get_order_status.order_id;

GRANT EXECUTE ON FUNCTION shopkart.ops.get_order_status TO `support-agents`;

-- Batch AI in SQL, on the same governed tables
SELECT ticket_id,
       ai_classify(body, ARRAY('late_delivery', 'damaged_item', 'refund', 'other')) AS category,
       ai_query('databricks-claude-sonnet-5-5',
                concat('Extract the order ID and requested action as JSON: ', body),
                responseFormat => 'STRUCT<order_id: STRING, wants: STRING>')     AS fields
FROM shopkart.support.tickets;

-- Retrieval from SQL, using an AI Search index (the function keeps its old name)
SELECT * FROM vector_search(index => 'shopkart.docs.policy_index', query_text => 'refund for a damaged mixer', num_results => 3);
Tool source How agents use it
Unity Catalog functions UCFunctionToolkit in LangChain, OpenAI Agents SDK and others, or the managed MCP server for a schema
AI Search indexes Retriever tools; a Delta Sync index re-embeds when the source table changes; hybrid search and reranking available
Genie spaces A text-to-SQL tool for metric questions over curated tables and metric views, with the SQL returned for checking
Managed MCP servers One URL per Unity Catalog schema, AI Search index or Genie space, for any MCP client; Unity Catalog permissions apply
External MCP servers and APIs Registered through Unity Catalog connections, so credentials and access are governed centrally

Agent Bricks sits on top for common patterns: describe the task and point it at data, and it builds a Knowledge Assistant (cited answers over documents), an Information Extraction agent (documents to tables), a Multi-Agent Supervisor (routing across Genie spaces, agents and tools), or a custom agent, then generates evaluations and tunes prompts, models and retrieval against them, reporting the cost and quality trade-off.

AI Gateway, observability and cost

Question Databricks feature
Who may call which model, MCP server or agent, at what rate? AI Gateway: permissions, rate limits per user, group or endpoint, fallbacks to another model, traffic splitting for A/B tests
What was sent and returned? Inference tables (payload logging to a Delta table) and MLflow traces stored in Unity Catalog
Is unsafe content getting through? Gateway guardrails (safety filtering, PII detection and masking) plus your own judges
How good are the answers? MLflow production monitoring, Review App labels, evaluation runs per version
What does it cost and who used it? System tables: system.serving.endpoint_usage, system.billing.usage, plus tags and budgets
Who accessed which data? Unity Catalog audit logs and lineage from tables to features, indexes, models and agents 
-- Tokens and requests per endpoint and user over the last 7 days
SELECT u.requester, e.endpoint_name, COUNT(*) AS requests,
       SUM(u.input_token_count) AS tokens_in, SUM(u.output_token_count) AS tokens_out
FROM system.serving.endpoint_usage u
JOIN system.serving.served_entities e USING (served_entity_id)
WHERE u.request_time >= current_date() - INTERVAL 7 DAYS
GROUP BY ALL
ORDER BY tokens_in DESC;

Industry practice
Lessons from Databricks agent projects
  • Start with the evaluation dataset, not the agent: 50 real questions with expected facts, labeled by experts in the Review App. Agent Bricks and your own code both optimize against it.
  • Keep tools in Unity Catalog so they are permissioned, discoverable and shared across agents and frameworks.
  • Prefer Genie or metric views for numbers and AI Search for documents; let a supervisor route between them.
  • Turn on inference tables and production monitoring on day one; quality problems in agents surface as trends, not single failures.
  • Use Lakebase for state (checkpoints, memory, session data) so it lives next to the lakehouse under the same governance.

In production
Production issues teams hit on Databricks
  • Cold starts: serving endpoints that scale to zero make the first request wait. Keep a minimum for user-facing agents.
  • Index sync lag: Delta Sync indexes update on their pipeline schedule (triggered or continuous). Know which mode you run and how stale results can be.
  • Genie spaces with too much in scope: broad spaces answer less accurately. Curate tables, add instructions and trusted assets, and review the questions Genie gets wrong.
  • Inference tables contain personal data: they log requests and responses; apply Unity Catalog permissions, masking and retention to them like any other sensitive table.
  • Agent Bricks optimizations you have not evaluated: auto-optimized agents still need your own evaluation set before production.

Solutions

SolutionP1 · The Databricks stack

Model Serving (foundation and external models), Vector Search over Delta tables, MLflow for tracing and evaluation, Unity Catalog for governance of data, models and tools, and Agent Bricks for building common agent types.

SolutionB1 · Governed tools

Call functions on data the user should not see. Register tools as Unity Catalog functions with grants, and run agents with the user's or a scoped identity.

SolutionD1 · Eval data matches production

Whether the evaluation set reflects production traffic, whether judges are calibrated, and whether traces from production feed new eval cases.

SolutionM1 · Map the architecture

Models through Model Serving, the graph deployed as a served agent, retrieval with Vector Search, tools as Unity Catalog functions or MCP, MLflow tracing and evaluation, and AI Gateway for limits and guardrails.

Explain the mechanismWhat does Databricks offer for agents?

Worked answer. A data-centric agent platform: Agent Bricks for common agent types, Mosaic AI model serving and AI Gateway, Vector Search, MLflow for tracing, evaluation and versioning, Unity Catalog for governance of data, models and tools, and Lakebase for operational data. Agents built with LangGraph or others can be logged and served.

A plausible wrong answer. "Databricks is only for data engineering." It covers the agent lifecycle on your data.

Worked answer. Endpoint scaling configuration (minimum replicas, scale-to-zero), model serving limits, and downstream tools. Pre-warm for known peaks.

A plausible wrong answer. "Databricks cannot serve real-time." Configuration decides.

Defend a designDatabricks for agents or a separate agent platform?

Worked answer. Databricks when the agents work mostly on data already governed there, where Unity Catalog and MLflow give governance and evaluation; a separate platform when agents are mostly customer-facing applications with little data-platform work.

A plausible wrong answer. "Keep everything on one platform." Fit matters more than consolidation.
