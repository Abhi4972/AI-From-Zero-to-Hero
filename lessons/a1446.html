Corrections Are Evidence

In plain words first

Each time you correct an agent ("don't edit that file", "keep the function name"), you have found a gap in the system around it. The ratchet turns that correction into something permanent at the earliest layer that can stop it happening again: a test, a scope rule, an automated check, an example, or a human decision. A reminder in chat is only the last resort. Release discipline and the LLMOps loop are covered in Lesson 14.119 (linked above). This lesson feeds the lesson's ratchet the real corrections this course made in 14.40 to 14.45, then measures two versions of one control.

When you tell an agent “do not edit that file,” you have learned that the scope boundary was not executable. When you say “this output shape is wrong,” you have learned that an example or test was missing. When setup fails again, you have learned that environment knowledge belongs in automation.

Treat the correction as an observation about the work system, not as a prompt-writing failure.

Promote to the Earliest Effective Layer

Use this order:

Recurring failure Durable destination
Wrong result or regression Test or evaluation
Off-scope or unsafe action Scope or permission policy
Repeated setup or command mistake Automation or tool
Repeated output-format mistake Canonical example plus validator
Ambiguous local convention Instruction with a scenario check
Product disagreement Human decision record

Earlier controls are cheaper. A type that prevents an invalid state is stronger than a review comment that catches it later. A focused test is stronger than a paragraph asking the agent to remember.

The Ratchet Record

Capture:

  • symptom;
  • root cause;
  • consequence;
  • recurrence count;
  • chosen control;
  • verification for the control;
  • owner;
  • date to review or retire it.

Do not promote every one-off preference. Promote a correction when recurrence or consequence justifies permanent complexity.

Separate Cause from Symptom

“The agent edited README” is a symptom. Possible causes include:

  • the task allowed the repository root;
  • docs were implicitly considered safe;
  • the plan bundled implementation and documentation;
  • two workers had overlapping ownership.

Each cause belongs to a different control. A rule that merely repeats the symptom will fail in the next slightly different case.

Controls Also Decay

Old controls can conflict, bloat context, and encode a system that no longer exists. Every promoted rule needs a retirement check. Remove or rewrite it when:

  • the underlying architecture changed;
  • a stronger executable control replaced it;
  • the failure has not recurred across a meaningful window;
  • the control creates more friction than the risk it prevents.

The goal is not the longest instruction file. It is the smallest system that preserves hard-won judgment.

The same idea as a formula

Promote when expected cost beats upkeep. A correction recurs at rate r per month, costs c each time, and the control stops a fraction e of recurrences while costing u a month to keep: context, maintenance, friction. Promote it when

e⋅r⋅c>u.

A severe first failure (large c) clears the bar with r small. A cosmetic preference rarely does.

Fingerprints group causes, not wordings. Two causes with token sets A and B count as one when their Jaccard overlap

J(A,B)=∣A∪B∣∣A∩B∣​≥τ.

Set τ too low and unrelated failures merge. Set it too high and every paraphrase becomes its own rule.

Worked example
The rename correction
  • "The model renamed the function under test" occurred 5 times in this course's runs (r is high), and each one burned an attempt.
  • As an instruction ("keep the name"), e is near 0 for the 0.5B model. Telling it exactly what went wrong fixed 0 of 3 tasks.
  • As a preventing control (the edit tool restores the public name), a rename never reaches the test. 2 of 3 tasks were fixed, and the third failed on its real bug (average([])).
  • Paraphrases: after dropping stop words and endings, "the model renamed the function under test" is {renam, function, under, test} and "function was renamed by the model" is {function, renam}. J=2/4=0.5≥0.5, so one control. "error codes outside the contract were not checked" overlaps the error-shape group at only about 0.22, so it stays separate.

STOP = {"the", "a", "an", "was", "were", "by", "but", "not", "in", "of", "to", "had", "no", "be", "is", "model",
        "agent", "every", "before"}
STEM = lambda w: re.sub(r"(ed|d|s|ing)$", "", w)
def tokens(text):
    return {STEM(w) for w in re.findall(r"[a-z_]+", text.lower()) if w not in STOP}

def cluster(corrections, threshold=0.5):
    groups = []
    for c in corrections:
        t = tokens(c.cause)
        for g in groups:
            j = len(t & g["tokens"]) / len(t | g["tokens"])
            if j >= threshold:
                g["members"].append(c); g["tokens"] |= t; break
        else:
            groups.append({"tokens": t, "members": [c]})
    return groups

# This block continues from the one above. Promote the most frequent correction, "the model renamed the function",
# into a control, two ways: one that informs (a preflight that names the rename in the feedback) and one that
# prevents (the edit tool keeps the public name). Then rerun 14.40's three renamed bugs with
# Qwen2.5-0.5B-Instruct (greedy, CPU), two attempts each, under all three. About 2 minutes.
import ast, os, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def chat(prompt, n=150):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=False)
    return tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

BUGS = [("largest", "def largest(xs):\n    return min(xs)\n", "assert largest([3, 9, 2]) == 9 and largest([-5, -2]) == -2"),
        ("to_fahrenheit", "def to_fahrenheit(c):\n    return c * 9 / 5\n", "assert to_fahrenheit(100) == 212 and to_fahrenheit(0) == 32"),
        ("average", "def average(xs):\n    return sum(xs) / len(xs)\n", "assert average([2, 4]) == 3 and average([]) == 0")]
import pathlib
work = pathlib.Path(tempfile.mkdtemp())

def preflight(name, code):
    """The promoted control: the edited module must still define the public function, with the same arguments."""
    try:
        tree = ast.parse(code)
    except SyntaxError as exc:
        return f"your code does not parse: {exc.msg}"
    defined = [n.name for n in tree.body if isinstance(n, ast.FunctionDef)]
    if name not in defined:
        return f"you renamed the function: the test imports `{name}`, your code defines {defined or 'nothing'}. Keep the name `{name}`."
    return ""

def pin_name(name, code):
    """A stronger control: the edit tool keeps the public name, so a rename cannot reach the test."""
    try:
        tree = ast.parse(code)
    except SyntaxError:
        return code
    defs = [n for n in tree.body if isinstance(n, ast.FunctionDef)]
    if len(defs) == 1 and defs[0].name != name:
        old = defs[0].name
        return re.sub(rf"\b{re.escape(old)}\b", name, code)
    return code

def attempt(name, code, test, extra, pin=False):
    text = chat(f"This Python function has a bug.\n{code}\n{extra}Return only the corrected function in a ```python block.")
    m = re.search(r"```(?:python)?\n(.*?)```", text, re.S)
    fix = (m.group(1) if m else code).strip() + "\n"
    if pin:
        fix = pin_name(name, fix)
    (work / f"{name}.py").write_text(fix)
    (work / f"test_{name}.py").write_text(f"from {name} import {name}\n{test}\n")
    p = subprocess.run([sys.executable, f"test_{name}.py"], cwd=work, capture_output=True, text=True, timeout=30)
    return fix, p.returncode, (p.stderr.strip().splitlines() or [""])[-1]

SUMMARY = {}
for mode in ("generic feedback", "control that informs", "control that prevents"):
    fixed = 0
    for name, code, test in BUGS:
        extra, trail = "", []
        for _ in range(2):
            fix, rc, err = attempt(name, code, test, extra, pin=(mode == "control that prevents"))
            msg = preflight(name, fix) if mode == "control that informs" else ""
            trail.append("pass" if rc == 0 else ("renamed" if "cannot import" in err else err.split(":")[0]))
            if rc == 0:
                fixed += 1
                break
            extra = f"Your last attempt failed: {msg or err}\n"
        print(f"{mode:<22} {name:<14} {' -> '.join(trail)}")
    SUMMARY[mode] = fixed
    print()
print("fixed:", {k: f"{v}/3" for k, v in SUMMARY.items()})
print("\nthe promoted control, as a ratchet record:")
ctl = promote(Correction("tests could not import the fixed function", "the model renamed the function under test", 5, "lost attempts"))
print({"target (lesson)": ctl.target, "target (chosen)": "automation", "verification": "a rename never reaches the test; the rename count is logged",
       "owner": "workbench maintainer", "retire when": "the edit tool itself keeps signatures, or 30 days with no rename caught"})

# Lesson program for promoting corrections into durable controls.
# Read: phases/14-agent-engineering/46-turn-feedback-into-system/docs/en.md
# Reference: Basili, Caldiera, and Rombach, The Goal Question Metric Approach.
# Reference: Shinn et al., Reflexion, arXiv:2303.11366.
# Run this file to generate outputs/feedback-ratchet.json.
from __future__ import annotations

import hashlib
import json
import re
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Correction:
    symptom: str
    cause: str
    recurrence: int
    consequence: str


@dataclass(frozen=True)
class Control:
    target: str
    rule: str
    verification: str
    fingerprint: str
    symptom: str
    cause: str
    recurrence: int
    consequence: str


def choose_target(correction: Correction) -> str:
    text = f"{correction.symptom} {correction.cause}".lower()
    if any(word in text for word in ("incorrect output", "regression", "edge case", "bug")):
        return "test"
    if any(word in text for word in ("scope", "unrelated file", "permission")):
        return "scope"
    if any(word in text for word in ("command", "setup", "environment", "tool")):
        return "automation"
    if any(word in text for word in ("format", "pattern", "example")):
        return "example"
    return "instruction"


def normalize_cause(cause: str) -> str:
    text = cause.strip().rstrip(".").lower()
    implicit = re.fullmatch(r"(.+?) (?:was|were) implicit", text)
    if implicit:
        return f"implicit {implicit.group(1)}"
    unchecked = re.fullmatch(r"(.+?) was described but not checked", text)
    if unchecked:
        return f"unchecked {unchecked.group(1)} description"
    missing = re.fullmatch(r"(.+?) had no (.+)", text)
    if missing:
        return f"missing {missing.group(2)} for {missing.group(1)}"
    return text

Part 2 of 3 · promote, ratchet, example

def promote(correction: Correction) -> Control:
    target = choose_target(correction)
    rule = f"Prevent {normalize_cause(correction.cause)}"
    verification = {
        "test": "Run the new regression test",
        "scope": "Run the scope checker",
        "automation": "Run the setup or tool preflight",
        "example": "Compare the output with the canonical example",
        "instruction": "Run the instruction linter and scenario check",
    }[target]
    digest = hashlib.sha256(f"{target}|{rule}".encode()).hexdigest()[:12]
    return Control(
        target,
        rule,
        verification,
        digest,
        correction.symptom,
        correction.cause,
        correction.recurrence,
        correction.consequence,
    )


def ratchet(corrections: list[Correction]) -> list[Control]:
    promoted: dict[str, Control] = {}
    for correction in corrections:
        if correction.recurrence < 1:
            continue
        control = promote(correction)
        promoted[control.fingerprint] = control
    return sorted(promoted.values(), key=lambda item: (item.target, item.fingerprint))


def example() -> list[Correction]:
    return [
        Correction("Agent edited an unrelated file", "scope was described but not checked", 2, "review churn"),
        Correction("A regression escaped", "edge case had no executable example", 1, "user-visible failure"),
        Correction("Setup command failed", "environment assumptions were implicit", 3, "lost session"),
    ]


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "feedback-ratchet.json"
    output.write_text(json.dumps([asdict(item) for item in ratchet(example())], indent=2) + "\n", encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Solutions

SolutionP1 · Most land in the weakest layer

One, at most. The lesson's keyword classifier sends 8 of the 9 to "instruction" and one to "example", and none reach test, scope or automation, although that is where the course actually fixed them. Neither paraphrased pair collapses: 9 corrections become 9 controls. A token-overlap fingerprint at Jaccard 0.5 merges both pairs and leaves the rest separate.

The classifier is the weak point. A better one looks at the evidence attached to the correction (a failing test, an out-of-scope path, a command exit code), not at the words someone used.

SolutionB1 · Move rules out of the file

The file grew because every correction was promoted to the weakest layer, and nothing was ever retired. Group the lines by cause and keep one entry per cause. Then move each one to the earliest layer that can enforce it.

"Never edit README" becomes a permission deny rule or a PreToolUse hook. "Keep function names" becomes an edit-tool or preflight check. "Return the error envelope" becomes a test. "Always run tests" becomes a gate in CI.

What remains in AGENTS.md is the conventions no check can enforce, each with an owner and a retirement condition. Delete a line only after its control exists and has been seen to catch the failure. That is the lesson's rule: prove a stronger control exists before removing the prose.

What You Keep

Keep outputs/feedback-ratchet.json. It is the durable end of the Agent-Assisted Engineering path and the input to future workbench changes.

Break it on purpose

After a month of agent work, your AGENTS.md has 140 lines: "never edit README", "keep function names", "return the error envelope", "always run tests", many of them repeated in other words. Agents still break most of them, and new contributors stop reading the file. Using this lesson, how do you fix the file and the failures? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Hooks are executable controls. Claude Code hooks run your script on events such as PreToolUse, and a hook can block the call, for example an rm -rf or a write outside the allowed paths. Cursor and Codex offer similar hooks and rules.
  • Permissions as scope. Allow and deny rules for tools and paths (Claude Code settings, Codex sandbox modes) turn "don't touch that" into a boundary the agent cannot cross.
  • Failures become eval cases. Teams add each production failure from their traces to an evaluation dataset (LangSmith, Braintrust and others), so the regression is tested on every prompt or model change.
  • Memory files stay short. CLAUDE.md and AGENTS.md hold conventions that no check can enforce. Anything enforceable moves into tests, hooks or permissions.
  • On your laptop: the ratchet and the controls are standard-library Python. The model step runs on CPU.

Sources: Claude Code, Hooks, Claude Code, Identity and access (permissions), Claude Code, Memory, LangSmith, Evaluation.

Recap
What to keep from this lesson
  • A correction is evidence that the system around the agent has a gap.
  • Promote it to the earliest layer: test, scope, automation, example, human decision. An instruction comes last.
  • Prevent rather than inform where you can. Here preventing fixed 2 of 3 and informing fixed 0.
  • Group corrections by cause, not wording.
  • Every control has an owner, a check and a retirement condition.

Explain the mechanismFor the third time this month you have told a coding agent not to edit the project README during a feature change. Each time it apologized and fixed the run. Tell me what you do now, and why the fix is not a better prompt.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. A correction that lives in chat fixes one run. I treat the repeat as evidence about the work system: the scope boundary was not executable. I find the cause behind the symptom, then put a control at the earliest layer that can stop the recurrence, which here is a scope or permission policy rather than another paragraph in the instructions. The control gets an owner, a verification and a date to review or retire it.

Separate the cause from the symptom.

"The agent edited the README" is a symptom. The cause can be any of these:

  • the task allowed writes to the repository root;
  • documentation was treated as safe by default;
  • the plan bundled implementation and documentation in one item;
  • two workers had overlapping ownership.

Each cause belongs to a different control. A rule that only repeats the symptom fails in the next slightly different case.

Promote to the earliest effective layer.

Recurring failure Durable destination
Wrong result or regression Test or evaluation
Off-scope or unsafe action Scope or permission policy
Repeated setup or command mistake Automation or tool
Repeated output-format mistake Canonical example plus validator
Ambiguous local convention Instruction with a scenario check
Product disagreement Human decision record

Earlier controls are cheaper. A permission that makes the write impossible is stronger than a review comment that catches it later, and a focused test is stronger than a paragraph that asks the agent to remember.

The record.

For each promoted correction I capture the symptom, the root cause, the consequence, the recurrence count, the chosen control, how the control is verified, the owner, and a date to review or retire it. Not every one-off preference gets promoted. Recurrence or consequence has to justify permanent complexity.

Why not a better prompt.

The prompt was already clear three times. The failure is that the boundary depended on the agent reading and remembering. A policy that refuses the write does not depend on memory.

Plausible wrong answers.

  • "Add the rule in capital letters at the top of the instructions." The instruction already existed; a louder copy still depends on the agent reading it.
  • "Promote every correction so nothing is lost." Controls accumulate, conflict and bloat context; promotion needs recurrence or consequence.
  • "The agent is the problem, switch models." The boundary was not executable; a different model meets the same missing control.

Follow-ups an interviewer may ask.

  • (level 2) Two corrections use different words for the same cause. How do you keep them from becoming two rules? Expected: normalize them to a stable fingerprint of the cause, so they collapse into one control without merging unrelated failures.
  • (level 2) A first-time failure deleted customer data. Does it wait for recurrence? Expected: no; consequence weighting lets a severe first occurrence be promoted at once.
  • (level 3) When would you remove the control you added? Expected: when the architecture changed, a stronger executable control replaced it, the failure has not recurred across a meaningful window, or the control blocks more legitimate work than the risk it prevents.
  • (level 3) What is the smallest system you aim for? Expected: the smallest set of controls that preserves the hard-won judgment, not the longest instruction file.

Where it is taught. The feedback-to-system lesson gives the destination table, the ratchet record and the retirement checks.

Weigh a trade-offA team's agent instruction file has grown for a year. Rules contradict each other, the context is heavy, and nobody remembers why half of them exist. You are asked to clean it up. How do you decide what stays, what goes, and what you will not touch yet?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Every control needs a retirement condition, and retirement needs evidence like any other change. I review each rule against four questions: did the architecture or workflow it protected change, did a stronger executable control replace it, has the failure stayed away across a meaningful window, and does the rule block legitimate work more often than it prevents harm. A rule that passes none of those stays, and a rule I cannot trace to a cause gets an owner and a review date before it gets deleted.

Why the file grew.

Each rule was a correction promoted into prose. Prose is the weakest durable layer. Over a year the rules encoded a system that no longer exists, started to conflict, and now consume context on every run. The goal is not the longest instruction file. It is the smallest system that preserves hard-won judgment.

The review.

Question If yes
Did the architecture or workflow change? The rule protects a system that is gone; retire it
Did a type, a test or a permission replace it? Delete the prose and keep the executable control
Has the failure not recurred across the window? Retire it, and note the window as the evidence
Does it block legitimate work more than it prevents harm? Rewrite it narrower or retire it

Replace before delete.

For a rule that still protects a real risk, the better move is often promotion rather than retirement: a prose rule about output shape becomes an example plus a validator, a prose rule about files becomes a scope policy. I delete the sentence only after proving the stronger control exists and fires.

What I do not touch yet.

A rule with no recorded cause and no owner is a gap in the record, not a candidate for deletion. I give it an owner and a review date, and I look for the correction that created it. Deleting it because it feels old is the mistake the lesson warns against.

Guard against regrowth.

Every new control gets an owner, a verification, a review or expiry window and a retirement condition when it is created. Without that, the file fills again in a year.

Plausible wrong answers.

  • "Delete everything older than a year and see what breaks." Retirement needs evidence; a silent failure can take months to appear.
  • "Keep all of it, context is cheap." Stale rules conflict, encode a dead system and bloat every run.
  • "Rewrite the whole file from scratch." The file holds judgment that was paid for; the job is to move it to stronger layers, not to lose it.

Follow-ups an interviewer may ask.

  • (level 3) Two rules contradict each other. What do you do first? Expected: find the cause behind each; a contradiction usually means one of them protects a system or decision that changed.
  • (level 3) A rule has not fired in months. Is that enough to delete it? Expected: only if the window is meaningful for that failure and the risk it protected is still visible elsewhere; low frequency with high consequence can keep a rule alive.
  • (level 4) How do you show that a deletion was safe? Expected: the stronger control that replaced it fires on the original failure case, and the recurrence stays absent across the review window.
  • (level 4) What stops the file from growing back? Expected: a creation rule that every control carries an owner, a verification and a retirement condition, with periodic review.

Where it is taught. The feedback-to-system lesson gives the retirement checks and the feedback ratchet lesson gives the ownership and expiry fields.
