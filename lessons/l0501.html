Why this came about

Relational databases and vector search answer questions about records and passages, but struggle with questions about connections, such as how two entities are related through several steps. Graph databases (from the 2000s) and Google's Knowledge Graph (2012) made relationships first-class, and from 2024 knowledge graphs returned to prominence as a way to improve AI retrieval.

In plain words first
A map of who is connected to whom

Some questions are about connections, not passages: which suppliers serve our top products, who reports to whom, which incidents share a root cause. A graph stores things as nodes (a customer, a product, a supplier) and their relationships as edges (bought, supplies, caused), each with properties. Questions then become walks along the edges, which is natural for relationships and awkward for tables and vector search.

When a graph is the right shape

Every data model is good at some questions. A graph earns its place when the question is about connections:

Question Best fit Why
"What did Priya order last month?" Relational table A filter and a sort on one entity
"Find documents about battery overheating" Vector index Similarity of meaning
"Which customers are exposed to a supplier two steps upstream?" Graph A path of unknown length through several entity types
"Who are the most influential accounts in this fraud ring?" Graph Centrality depends on the whole network
"What are the main themes across 10,000 support tickets?" Graph plus summaries Communities of related entities (Lesson 5.6)
"How is this contract related to that lawsuit?" Graph A shortest path is the explanation

The pattern: tables are best when you know the shape of the query in advance, vectors when you need similarity, and graphs when the answer is a path or a structure. Most production AI systems use all three.

The vocabulary

Term Meaning
Node (vertex) A thing: a customer, a product, a policy section, a service
Edge (relationship) A connection between two nodes; directed (A supplies B) or undirected (A is similar to B)
Label and type The kind of node (Customer) and the kind of edge (PLACED)
Property A key-value attribute on a node or edge (city: Pune; qty: 1)
Weight A number on an edge used by algorithms: distance, latency, strength, cost
Degree How many edges touch a node; in a directed graph, in-degree and out-degree
Path, hop A sequence of edges; each edge is one hop
Cycle, DAG A path that returns to its start; a directed graph with no cycles (directed acyclic graph)
Bipartite graph Two kinds of nodes with edges only between kinds (customers and products)
Multigraph More than one edge allowed between the same pair (two different orders)

Two ways to model: property graphs and RDF

A labeled property graph (LPG) has labeled nodes and typed edges, each with properties. It is the model of Neo4j, Memgraph, Amazon Neptune (openCypher and Gremlin) and Spanner Graph, and the one most GraphRAGlater · 5.6 tools use. RDF (Resource Description Framework) stores everything as triples: subject, predicate, object, with globally unique identifiers (IRIs) and optional ontologies (RDFS, OWL) that define classes and allow reasoning. RDF is the model of the semantic web, Wikidata and many standards-driven domains (life sciences, publishing, government).

Choose When
Property graph Application data, GraphRAG, recommendations, fraud, dependency graphs; developers want a simple model and fast traversals
RDF and ontologies Data integration across organizations, shared vocabularies (schema.org, FIBO, SNOMED), formal reasoning, linked open data

Hands-on · A property graph and what a query engine does

The code builds a small ShopKart graph and implements, in a few lines, what a graph query enginelater · 7.8 does for a path pattern. The equivalent Cypher is in the docstring.

from collections import defaultdict

# A small property graph for ShopKart: labeled nodes with properties, typed directed edges.
NODES = {
    "c1": {"label": "Customer", "name": "Priya", "city": "Pune"},
    "c2": {"label": "Customer", "name": "Arjun", "city": "Delhi"},
    "c3": {"label": "Customer", "name": "Meera", "city": "Pune"},
    "o1": {"label": "Order", "total": 7999}, "o2": {"label": "Order", "total": 1299},
    "o3": {"label": "Order", "total": 2499}, "o4": {"label": "Order", "total": 7999},
    "p1": {"label": "Product", "name": "Phone X"}, "p2": {"label": "Product", "name": "Phone case"},
    "p3": {"label": "Product", "name": "Earbuds"},
    "s1": {"label": "Supplier", "name": "Acme Electronics", "country": "IN"},
    "s2": {"label": "Supplier", "name": "Shenzhen Parts", "country": "CN"},
}
EDGES = [  # (from, type, to, properties)
    ("c1", "PLACED", "o1", {}), ("c1", "PLACED", "o2", {}), ("c2", "PLACED", "o3", {}), ("c3", "PLACED", "o4", {}),
    ("o1", "CONTAINS", "p1", {"qty": 1}), ("o2", "CONTAINS", "p2", {"qty": 1}), ("o3", "CONTAINS", "p3", {"qty": 1}),
    ("o4", "CONTAINS", "p1", {"qty": 1}),
    ("p1", "SUPPLIED_BY", "s1", {}), ("p2", "SUPPLIED_BY", "s2", {}), ("p3", "SUPPLIED_BY", "s1", {}),
    ("s1", "SOURCES_FROM", "s2", {"component": "battery"}),
]

out_adj, in_adj = defaultdict(list), defaultdict(list)       # adjacency lists, both directions
for a, t, b, props in EDGES:
    out_adj[a].append((t, b)); in_adj[b].append((t, a))

def match(start_label, *steps):
    """A tiny version of what a graph query engine does for
    MATCH (x:Customer)-[:PLACED]->(:Order)-[:CONTAINS]->(:Product)-[:SUPPLIED_BY]->(s:Supplier)."""
    paths = [[n] for n, p in NODES.items() if p["label"] == start_label]
    for rel, label in steps:
        paths = [path + [b] for path in paths for t, b in out_adj[path[-1]]
                 if t == rel and NODES[b]["label"] == label]
    return paths

paths = match("Customer", ("PLACED", "Order"), ("CONTAINS", "Product"), ("SUPPLIED_BY", "Supplier"))
for p in paths:
    print(" -> ".join(NODES[n].get("name", n) for n in p))

# Triples: the same facts in the RDF-style subject-predicate-object form.
triples = [(NODES[a].get("name", a), t.lower(), NODES[b].get("name", b)) for a, t, b, _ in EDGES]
print(len(triples), "triples, e.g.", triples[-1])
What you should see
Priya -> o1 -> Phone X -> Acme Electronics
Priya -> o2 -> Phone case -> Shenzhen Parts
Arjun -> o3 -> Earbuds -> Acme Electronics
Meera -> o4 -> Phone X -> Acme Electronics
12 triples, e.g. ('Acme Electronics', 'sources_from', 'Shenzhen Parts')

Each result is a path. The match function walks adjacency lists from every Customer, keeping only edges of the right type to nodes of the right label: that is a graph query engine without the optimizer. The same twelve facts also fit the RDF triple form, which is why converting between the two models is routine.

Now the question that is awkward in SQL: which customers depend on a supplier based in China, directly or one step upstream through another supplier?

# Which customers depend, directly or one step upstream, on a supplier in CN?
# In SQL this is a chain of joins whose length is fixed in the query; in a graph it is a path pattern.
def exposed_to(country, max_upstream=2):
    hit = set()
    for path in match("Customer", ("PLACED", "Order"), ("CONTAINS", "Product"), ("SUPPLIED_BY", "Supplier")):
        frontier, seen = [path[-1]], {path[-1]}
        for _ in range(max_upstream):                       # follow SOURCES_FROM edges upstream
            if any(NODES[s]["country"] == country for s in frontier):
                break
            frontier = [b for s in frontier for t, b in out_adj[s] if t == "SOURCES_FROM" and b not in seen]
            seen.update(frontier)
        if any(NODES[s].get("country") == country for s in seen):
            hit.add(NODES[path[0]]["name"])
    return sorted(hit)

print("customers exposed to a CN supplier:", exposed_to("CN"))
print("degree of Phone X:", len(in_adj["p1"]) + len(out_adj["p1"]), "| orders containing it:",
      [o for t, o in in_adj["p1"] if t == "CONTAINS"])
What you should see
customers exposed to a CN supplier: ['Arjun', 'Meera', 'Priya']
degree of Phone X: 3 | orders containing it: ['o1', 'o4']

Only Priya buys a product supplied directly from China, but Acme Electronics sources a component from Shenzhen Parts, so every customer is exposed. In SQL, each extra upstream step is another self-join you must write in advance (or a recursive query); in a graph, the depth is a parameter. Hidden dependencies like this are why supply chains, fraud and access control are classic graph problems.

Representations and their costs

Representation Memory Fast at Slow at Used by
Adjacency list (each node keeps its neighbors) Proportional to edges Visiting neighbors, traversals Checking whether one specific edge exists, in dense graphs Most graph databases, networkx
Adjacency matrix (n x n) n² cells Edge checks; linear algebra (PageRanklater · 5.5 as matrix powers) Memory for sparse graphs Small dense graphs, GPU analytics
Edge list (rows of source, type, target) Proportional to edges Loading, storing in tables Traversal (needs an index) Files, data lakes, relational tables
Compressed sparse row (CSR) Proportional to edges, compact Read-only analytics at scale Updates Analytics engines, graph ML libraries

Real graphs are sparse (each node touches a few others out of millions), so adjacency lists and CSR dominate. Graph databases add index-free adjacency: each node points directly to its edges, so a traversal costs time proportional to the edges visited, not to the size of the database.

Check your mental model
  • ✗ "A graph is just a different database format."
    ✓ It makes relationships first-class, so multi-step connection questions become cheap walks.
  • ✗ "Every dataset should be a graph."
    ✓ Graphs pay off when the questions are about relationships; tables remain best for aggregates.
  • ✗ "Property graphs and RDF are the same."
    ✓ Both model connections; they differ in data model, query languages and tooling.

Exercises

Predict before you run

With exposed_to(country, max_upstream=2), a supplier three steps upstream is in the affected country. Is the product reported as exposed? (Solution P1.)

Break it on purpose

Model supplier relationships in a relational table and answer "all products exposed through any number of supplier tiers" with joins. What goes wrong as tiers grow? (Solution B1.)

Debugging exercise

The graph says a product has two suppliers named "Acme", one in Pune and one in Mumbai, but they are the same company. What modeling step was missed? (Solution D1.)

Make it your own

Add an edge property share (the fraction of a product's supply from each supplier) and change exposed_to to report only products with more than 30% exposure. (Solution M1.)

Solutions

SolutionP1 · Depth limits are decisions

No: the traversal stops at two hops, so third-tier suppliers are invisible. The limit is a business decision (how deep the risk analysis goes) that should be explicit and tested.

SolutionB1 · Variable-depth questions

Each extra tier needs another join, or a recursive query, and the query grows and slows. Graphs make variable-depth traversal a first-class operation, which is when a graph is the right shape.

SolutionD1 · Identity before edges

Entity resolutionlater · 5.3: the two records were not recognized as one company, so edges split between two nodes. Resolve entities on stable identifiers (a GSTIN) before loading (Lesson 5.4).

SolutionM1 · Properties on edges

Store share on SUPPLIES edges, multiply shares along a path for indirect exposure, and filter by the threshold. Edge properties are where many graph questions get their nuance.

Check your understanding

Explain the mechanismWhen is a graph the right data model?

Worked answer. When the questions are about relationships, especially of variable or unknown depth: supply chains, fraud rings, recommendations, permissions, dependencies, knowledge across documents. Property graphs put properties on nodes and edges; RDF uses subject-predicate-object triples with shared vocabularies. If questions are mostly aggregations over rows, a relational model is simpler.

A plausible wrong answer. "Whenever data has relationships." All data has relationships; graphs pay off when traversal is the question.

Follow-ups. Property graph or RDF for an enterprise knowledge graph?

Debug a failureA graph query that was fast becomes very slow after new data. What do you check?

Worked answer. Supernodes (a node with huge degree, such as a common category), unbounded traversal depth, and missing indexes on start-node lookups. Profile the query, bound the depth, and filter edges early (Lesson 5.7).

A plausible wrong answer. "Graphs do not scale." Specific patterns do not; fix the pattern.

Follow-ups. How do you find supernodes?

Defend a designA graph database for ShopKart's product catalog?

Worked answer. Only if the catalog's key questions are relational paths: compatible accessories, substitutes, supply exposure. For search and filtering by attributes, a search index and a relational store are simpler. A graph can be added beside them for the relationship questions.

A plausible wrong answer. "Graphs are the modern way to store data." They are a tool for specific questions.
