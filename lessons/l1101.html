Why this came about

GPT-style models are first pretrained on vast text to predict the next token, which gives knowledge but not helpfulness. InstructGPT (2022) showed that further training on examples of good instruction-following made models far more useful, establishing the pretraining-then-fine-tuning recipe.

In plain words first
Reading the internet, then learning to be helpful

A model is trained in stages. Pretraining reads a huge amount of text and learns to predict the next token, which gives broad knowledge and language skill but not helpfulness. Supervised fine-tuning then trains it on examples of good responses to instructions, turning a text predictor into an assistant. Later stages (Lesson 11.2) refine behaviour with feedback.

Pretraining: next-token prediction at scale

Pretraining runs the cross-entropy loss of Lesson F3.3 over trillions of tokens of text and code. The data pipeline matters as much as the model: crawl the web (Common Crawl), extract text from HTML, filter for quality with classifiers and heuristics, remove duplicates and personal data, then mix in code, math, books, papers and multilingual text in chosen proportions. Datasets such as FineWeb document this process in the open. Late in pretraining, labs often anneal on a smaller set of high-quality data, and many run mid-training (also called continued pretraining) to add long-context ability, a language or a domain before post-training.

Scaling laws describe how loss falls predictably as parameters (N), data tokens (D) and compute (C ≈ 6ND) grow. Kaplan et al. (OpenAI, 2020) found smooth power laws; Hoffmann et al. (DeepMind, 2022, "Chinchilla") showed that for a fixed compute budget, models had been too big and undertrained, and that the compute-optimal ratio is roughly 20 tokens per parameter.

import math
def chinchilla_optimal(compute_flops):
    """Hoffmann et al. 2022: for a fixed budget C = 6*N*D, loss is lowest near D = 20*N."""
    n = math.sqrt(compute_flops / (6 * 20))
    return n, 20 * n

for c in [1e21, 5.88e23, 1e25]:                     # the middle one is Chinchilla's own budget
    n, d = chinchilla_optimal(c)
    print(f"budget {c:.3g} FLOPs -> about {n / 1e9:6.1f}B parameters on {d / 1e12:6.2f}T tokens")

print(f"Llama 3 8B was trained on 15T+ tokens: {15e12 / 8e9:,.0f} tokens per parameter, far past 20,")
print("because a smaller model trained longer is cheaper to SERVE for its whole life.")

The middle line reproduces Chinchilla itself: 70B parameters on 1.4T tokens. Compute-optimal is about training cost only, though. A model is trained once and served billions of times, so labs now train small models far past 20 tokens per parameter, accepting a more expensive training run for a cheaper, faster model.

The standard measure of a language model's raw quality is perplexity: the exponential of the average cross-entropy on held-out text. Lower is better; a perplexity of 8 means the model is, on average, as uncertain as if it were choosing among 8 equally likely tokens.

import math
# Probabilities a model gave to each ACTUAL next token in a held-out sentence
confident = [0.62, 0.41, 0.88, 0.70, 0.93, 0.55]
confused  = [0.10, 0.05, 0.31, 0.12, 0.20, 0.08]
for name, probs in [("good model", confident), ("weak model", confused)]:
    loss = -sum(math.log(p) for p in probs) / len(probs)       # average cross-entropy, in nats
    print(f"{name}: loss {loss:.2f}  perplexity {math.exp(loss):5.2f}")
print("Perplexity = exp(loss): roughly how many tokens the model is torn between at each step.")
What you should see
good model: loss 0.42  perplexity  1.52
weak model: loss 2.12  perplexity  8.34
Perplexity = exp(loss): roughly how many tokens the model is torn between at each step.

Perplexity compares models with the same tokenizer on the same text; it says little about whether a chat model is helpful, which is why later stages are judged differently.

Supervised fine-tuning: learning to be an assistant

A pretrained base model continues text; asked a question, it may write more questions. Supervised fine-tuning (SFT), also called instruction tuning, trains it on example conversations written or curated by people (and increasingly by stronger models), formatted with a chat template of special tokens marking system, user and assistant turns. The loss is the same next-token loss, but computed only on the assistant's tokens: the model should learn to write answers, not to imitate users.

import numpy as np
# SFT: train on whole conversations, but only the assistant's tokens count toward the loss
tokens = ["<user>", "Where", "is", "my", "order", "?", "<assistant>", "It", "ships", "today", ".", "<end>"]
role   = ["u"] * 7 + ["a"] * 5
token_loss = np.array([2.1, 3.0, 1.2, 0.9, 1.5, 0.4, 0.1, 1.8, 2.2, 1.1, 0.3, 0.2])   # per-token cross-entropy
mask = np.array([r == "a" for r in role], dtype=float)
print(f"loss over every token      {token_loss.mean():.3f}")
print(f"loss over assistant tokens {(token_loss * mask).sum() / mask.sum():.3f}  <- what SFT optimizes")
print("trained on:", " ".join(t for t, m in zip(tokens, mask) if m))
What you should see
loss over every token      1.233
loss over assistant tokens 1.120  <- what SFT optimizes
trained on: It ships today . <end>

Quality beats quantity here: the LIMA paper (Meta, 2023) got strong assistant behavior from just 1,000 carefully chosen examples, evidence that SFT mostly teaches format and style on top of knowledge learned in pretraining. The same is true when you fine-tune: a few thousand clean, consistent examples beat a large noisy set (Lesson 11.9).

Exercises

Predict before you run

Break it on purpose

Fine-tune a model on 200 ShopKart support replies to teach it the refund policy. A month later the policy changes. What is the problem? (Solution B1.)

Debugging exercise

After fine-tuning on support replies, the model got worse at general questions. What happened, and how do you limit it? (Solution D1.)

Make it your own

Write the data spec for a supervised fine-tuning set that teaches ShopKart's reply format: sources, size, quality checks and a held-out set. (Solution M1.)

Solutions

SolutionP1 · Pretraining against fine-tuning

The base model continues text, perhaps with more quiz questions, because it learned to predict the next token of web text. The chat model answers, because supervised fine-tuning on instruction-response pairs taught it to follow instructions.

SolutionB1 · Fine-tuning is the wrong tool for facts

The old policy is baked into the weights, and changing it needs another training run; the model may also mix old and new. Put facts in retrieval or the prompt; fine-tune for style, format and behavior.

SolutionD1 · Catastrophic forgetting

Training on a narrow set shifted the weights away from general skills. Use parameter-efficient methods (LoRAlater · 11.6), mix in general data, lower the learning rate or epochs, and evaluate on general benchmarks before and after.

SolutionM1 · A data spec

Real replies rated good by reviewers, cleaned of personal data, a few thousand examples covering intents and languages, deduplicated, with a held-out set of conversations not used for training and an eval of format and correctness.

Check your understanding

Explain the mechanismHow is an LLM trained, from pretraining to a chat model?

Worked answer. Pretraining on large text corpora with next-token prediction builds knowledge and language skill; supervised fine-tuning on instruction-response examples teaches it to follow instructions; preference training (RLHF, DPO) and reinforcement learning with verifiable rewards align behavior and improve reasoning. Each stage changes behavior more than knowledge.

A plausible wrong answer. "Fine-tuning teaches the model new facts reliably." It teaches facts unevenly; behavior is what it changes well.

Follow-ups. Where does tokenization fit?

Debug a failureA fine-tuned model outputs the training format even when asked for something else. Why?

Worked answer. Overfitting to one format: training examples all had it, and no examples showed other requests. Add diverse examples, train for fewer steps, and evaluate instruction following on held-out requests.

A plausible wrong answer. "The model is broken." It learned exactly what the data showed.

Follow-ups. How many epochs would you start with?

Defend a designShould a company pretrain its own LLM?

Worked answer. Almost never: pretraining costs are enormous and frontier and open models are strong. Fine-tuning or retrieval on top of an existing model covers almost every need. Exceptions are organizations with unique data at large scale and strategic reasons to own the model.

A plausible wrong answer. "Yes, to own the IP." Fine-tuned open models give most of the control at a fraction of the cost.

Follow-ups. When would you fine-tune an open model instead of using an API?
