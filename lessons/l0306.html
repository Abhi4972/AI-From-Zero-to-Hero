Why this came about

Agents that work silently for many seconds felt broken, and their costs were hard to explain because each run made many calls. Streaming progress events and tallying tokens per run came from the need to make agents both usable and accountable.

The problem: a silent wait, and a bill nobody can explain

A three-step run takes three model round trips plus the tools. With a real model that is several seconds of a blank screen, and the customer does not know whether anything is happening. Meanwhile finance asks what a refund conversation costs, and the only number anyone has is the monthly invoice.

Both answers come from the same place: the loop already knows, step by step, what it is doing and how many tokens each request used. It just does not tell anyone.

Python refresher
Python refresher: generators

A function containing yield is a generator. Calling it runs nothing. It returns an object that produces values one at a time as you loop over it, pausing at each yield until the caller asks for the next value. That makes it a natural shape for an agent loop: the caller receives each event the moment it happens, and stopping the loop stops the agent. A generator can be consumed only once.

In plain words first
A live progress bar and an itemized bill

An agent that works silently for twenty seconds feels broken, and one whose cost nobody can explain is a budget risk. So the loop yields events as it works ("calling get_order_status", text as it is written, "done") and adds up the tokens of every model call into a cost per run. Both come from the same idea: the loop reports what it is doing, step by step, instead of only returning an answer at the end.

Idea 1 · The loop yields events

Until now run returned only when the agent had finished, so a user saw nothing for several seconds. The change is small: turn the loop into a generator (Lesson 0.21) that yields a small dictionary each time something happens: the model starts thinking, a tool is called, a tool returns, text arrives. The caller decides which of these to show.

# Continues Lesson 3.5. The loop as a stream of events: the app shows progress while the agent works
import time

class StreamingAgent(IdempotentAgent):
    def events(self, question):
        """Yield what happens, as it happens. The caller decides what to show."""
        messages, used = [{"role": "user", "content": question}], 0
        for step in range(1, self.max_steps + 1):
            yield {"type": "thinking", "step": step}
            r = client.messages.create(model=MODEL, max_tokens=500, system=self.system,
                                       tools=[d for d, _ in self.tools.values()], messages=messages)
            used += r.usage.input_tokens + r.usage.output_tokens
            yield {"type": "usage", "step": step, "input": r.usage.input_tokens, "output": r.usage.output_tokens}
            if r.stop_reason != "tool_use":
                yield {"type": "answer", "text": r.content[-1].text, "tokens": used}
                return
            calls = [b for b in r.content if b.type == "tool_use"]
            for c in calls:
                yield {"type": "tool_call", "name": c.name, "input": c.input}
            messages.append({"role": "assistant", "content": r.content})
            results = self.call_tools(calls)
            messages.append({"role": "user", "content": results})
            for c, res in zip(calls, results):
                yield {"type": "tool_result", "name": c.name, "ok": not res.get("is_error")}
        yield {"type": "answer", "text": "Stopped: step limit reached. A person will follow up.", "tokens": used}

FRIENDLY = {"find_orders": "Looking up your orders", "get_order_status": "Checking the delivery status",
            "issue_refund": "Checking whether we can refund this"}

agent = StreamingAgent(system=SYSTEM, tools=work_tools, risky=risky)
for e in agent.events("Where are my running shoes?"):
    if e["type"] == "tool_call":
        print("  ...", FRIENDLY.get(e["name"], e["name"]))
    elif e["type"] == "answer":
        print("  answer:", e["text"])
What you should see
  ... Looking up your orders
  ... Checking the delivery status
  answer: Order SK-1042 is out for delivery, expected today by 8 pm.

The loop now reports thinking, usage, tool_call, tool_result and answer events, and the caller decides what a person sees. Here it maps tool names to friendly progress lines. A web app would send the same events to the browser over server-sent events or a WebSocket, and protocols such as AG-UI standardize exactly this event stream (Lesson 16.29). Two rules keep it safe: show friendly descriptions, never raw tool inputs (they can contain other customers' IDs or internal fields), and decide in code which events are visible at all.

Streaming the final answer token by token is a separate layer: the model's reply arrives as a stream of text deltas (Lesson 11.20). In an agent you usually stream the last step's text and show progress events for the steps before it.

Idea 2 · Tokens and cost per run

Every response carries usage: input and output tokens for that request. Add them up per run and price them:

# Tokens and cost per run. EXAMPLE prices, for the arithmetic only: use your provider's current price list
PRICE_PER_MTOK = {"claude-sonnet-5-5": {"input": 3.00, "output": 15.00}}     # USD per million tokens (illustrative)

def run_cost(question, agent):
    tokens_in = tokens_out = steps = 0
    answer = ""
    for e in agent.events(question):
        if e["type"] == "usage":
            tokens_in += e["input"]; tokens_out += e["output"]; steps += 1
        if e["type"] == "answer":
            answer = e["text"]
    p = PRICE_PER_MTOK[MODEL]
    return steps, tokens_in, tokens_out, (tokens_in * p["input"] + tokens_out * p["output"]) / 1e6, answer

print(f"{'question':<46}{'steps':>6}{'in':>7}{'out':>6}{'USD':>10}")
for q in ["Where is my order SK-1042?", "Where are my running shoes?", "My mixer arrived broken last week. Can I get a refund?"]:
    BANK.clear()
    steps, ti, to, usd, _ = run_cost(q, StreamingAgent(system=SYSTEM, tools=work_tools, risky=risky))
    print(f"{q[:45]:<46}{steps:>6}{ti:>7}{to:>6}{usd:>10.5f}")

steps, ti, to, usd, _ = run_cost("Where are my running shoes?", StreamingAgent(system=SYSTEM, tools=work_tools, risky=risky))
print(f"at 10,000 such conversations a day: about USD {usd * 10_000 * 30:,.0f} a month")

The prices are illustrative, for the arithmetic. Use your provider's current price list, including its discount for cached input. The stand-in also estimates tokens as characters ÷ 4.

Three numbers worth noticing. A multi-step run costs about one and a half to two times a single lookup, because input tokens grow with every step. Output tokens are a small share of the total, so for agents the input side, and caching it, usually matters most. And a per-conversation cost times volume is the number finance actually needs; Lesson 14.117 turns it into unit economics such as cost per resolved conversation.

Idea 3 · A page that shows the events

So far the events went to print. A customer needs them in a browser. The smallest working version has two parts: a server that sends each event down an open connection as it happens, and a page that listens. The format is server-sent events, the same one the model API streams with (Lesson 11.20): one line starting data: per event, then a blank line.

The server below uses only Python's standard library, so that nothing is hidden. It serves the page at / and the event stream at /ask. The last lines read the stream with plain Python, to show exactly what a browser receives.

# A web page for the agent: the same events, sent to a browser as server-sent events
import json, threading, urllib.parse, urllib.request
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

PAGE = """<!doctype html><meta charset="utf-8"><title>ShopKart support</title>
<form><input name="q" size="50" value="Where are my running shoes?"> <button>Ask</button></form>
<ul id="log"></ul>
<script>
document.querySelector("form").onsubmit = (e) => {
  e.preventDefault();
  const log = document.getElementById("log"); log.innerHTML = "";
  const stream = new EventSource("/ask?q=" + encodeURIComponent(e.target.q.value));
  stream.onmessage = (m) => {
    const ev = JSON.parse(m.data), li = document.createElement("li");
    if (ev.type === "tool_call") li.textContent = "... " + ev.label;
    else if (ev.type === "answer") { li.textContent = ev.text; li.style.fontWeight = "bold"; stream.close(); }
    else return;
    log.appendChild(li);
  };
};
</script>"""

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        url = urllib.parse.urlparse(self.path)
        if url.path == "/":
            body = PAGE.encode()
            self.send_response(200); self.send_header("Content-Type", "text/html; charset=utf-8")
            self.send_header("Content-Length", str(len(body))); self.end_headers(); self.wfile.write(body)
        elif url.path == "/ask":
            question = urllib.parse.parse_qs(url.query).get("q", [""])[0]
            self.send_response(200); self.send_header("Content-Type", "text/event-stream")
            self.send_header("Cache-Control", "no-cache"); self.end_headers()
            for e in StreamingAgent(system=SYSTEM, tools=work_tools, risky=risky).events(question):
                if e["type"] == "tool_call":                 # send a friendly label, never the raw tool input
                    e = {"type": "tool_call", "label": FRIENDLY.get(e["name"], e["name"])}
                self.wfile.write(f"data: {json.dumps(e)}\n\n".encode()); self.wfile.flush()
        else:
            self.send_error(404)
    def log_message(self, *args): pass                       # keep the lesson's output clean

server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
url = f"http://127.0.0.1:{server.server_port}"

# What the browser receives, read here with plain Python so that you can see it
with urllib.request.urlopen(url + "/ask?q=" + urllib.parse.quote("Where are my running shoes?")) as stream:
    for line in stream:
        if line.startswith(b"data: "):
            e = json.loads(line[6:])
            if e["type"] == "tool_call": print("event:", e)
            if e["type"] == "answer": print("event: answer |", e["text"])
print("page served:", urllib.request.urlopen(url + "/").status)
server.shutdown()

Reading this output
  • The browser gets the events one at a time. Each data: line arrives as soon as the loop yields it, so the page can show "Looking up your orders" while the agent is still working. To try the page yourself, remove the last line (server.shutdown()), print url, and open it in a browser.
  • The page is thirty lines. EventSource opens the connection and calls onmessage for each event. The page adds a line for each tool call and the answer in bold, then closes the stream.
  • The server chooses what the browser sees. It replaces the tool's name and input with a friendly label. Raw tool inputs and results can hold other customers' data or internal details, so they stay on the server.
Watch out
What this small version leaves out

EventSource can only send a GET request, so the question travels in the URL, where servers and proxies log it. A real app sends the message in a POST body and reads the streamed reply with fetch. It also needs sign-in, one conversation per customer (Lesson 14.60's saved state), and a way to show an approval and send back the decision.

You rarely write this layer by hand for long. For a demo or an internal tool, Gradio's ChatInterface, Streamlit's chat elements and Chainlit give you a chat page from a Python function in a few lines. For a product, the AG-UI protocol (Lesson 16.29) standardises these events, including tool calls, approvals and shared state, so that a front-end library can render any agent that speaks it.

Industry practice
Own your control flow

The 12-Factor Agents principles (Dex Horthy of HumanLayer, 2025) argue that the most reliable production agents are mostly ordinary software with model calls in a few places. Own your prompts, own your context window, own your control flow, and treat tool calls as structured output that your code decides how to execute. That is the loop you have built in this chapter. Use frameworks for what they do well, but keep this loop in your head when you read their docs.

In production
Design an agent right from day one

The production defaults that are cheap on day one and painful to retrofit: 1. An eval set of real tasks before the first prompt, including tasks the agent must refuse or escalate. 2. The lowest autonomy that works: fixed steps in code, model judgment only where the path really varies (Lesson 14.62). 3. Few, well-described, typed tools, with permissions checked inside the tool and idempotency keys on every write. 4. Budgets per run on steps, tokens, wall-clock time and cost, with a clear message when one is hit. 5. Human approval for irreversible actions, as a state the run waits in. 6. Durable state for anything longer than one request. 7. Tracing and cost per run from the first prototype, so every bad answer leads to one inspectable run.

The real thing

With the real SDK, the final answer can be streamed token by token. This needs an API key and the live API, so it was not run on this page; the method names were checked in anthropic 2.4.0:

import anthropic

client = anthropic.Anthropic()
# Stream the final answer's text as it is generated, then read the usage once the message is complete
with client.messages.stream(model=MODEL, max_tokens=500, system=SYSTEM,
                            messages=[{"role": "user", "content": "Explain our refund policy in two sentences."}]) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)
final = stream.get_final_message()
print("\n", final.usage.input_tokens, final.usage.output_tokens)

usage on the final message is what run_cost adds up. OpenAI's Responses API streams the same way with stream=True, sending text as response.output_text.delta events. What changes with a real model: latency is real, so the time to the first visible event is what customers judge you on. Prompt caching changes the price of input tokens, so record cached and uncached input separately. And usage per request is the only trustworthy cost signal, because a provider's invoice arrives too late and too aggregated to debug a single runaway conversation.

Check your mental model
  • ✗ "Cost per run is the cost of the final answer."
    ✓ It is the sum of every model call in the loop, and the input of each call includes the whole history so far.
  • ✗ "Streaming events are only for the UI."
    ✓ The same events feed logs, traces and cost tracking.
  • ✗ "Averages are enough to watch cost."
    ✓ Watch the expensive tail: a few looping runs can dominate the bill.

Make it your own
Make it your own: a cost budget per run

Wrap the event stream so a run stops cleanly with a message once it has spent more than a given number of US dollars. Test it with a budget the run fits in and one it does not. (Solution M1.)

Solutions

SolutionP1 · Reading a generator twice

The second pass is an empty list. A generator produces its values once; after the first loop consumed them, it is exhausted. The second loop did not re-run the agent, which is what you want, since re-running would repeat model calls and tool calls. If two consumers need the events, collect them into a list, or fan them out from one loop.

SolutionD1 · Overwritten, not added

tokens_in, tokens_out = e["input"], e["output"] replaces the totals on every usage event, so only the last request is counted. Compared with the correct figures in Idea 2, it reports USD 0.00141 instead of 0.00247 for the one-lookup question (57%), and 0.00171 instead of 0.00399 for the three-step one (43%). The error grows with the number of steps, which is exactly the shape that makes multi-step agents look cheaper than they are. Use +=, and reconcile your per-run totals against the provider's usage report each week.

SolutionM1 · A cost budget per run
# Solution M1: a cost budget per run, checked as the events arrive
def with_budget(events, max_usd):
    spent, p = 0.0, PRICE_PER_MTOK[MODEL]
    for e in events:
        if e["type"] == "usage":
            spent += (e["input"] * p["input"] + e["output"] * p["output"]) / 1e6
            if spent > max_usd:
                yield {"type": "answer", "text": f"Stopped: this conversation reached its cost limit (USD {max_usd}). A person will follow up."}
                return
        yield e

for limit in (0.01, 0.003):
    last = [e for e in with_budget(agent.events("Where are my running shoes?"), limit) if e["type"] == "answer"][-1]
    print(f"limit USD {limit}: {last['text']}")

limit USD 0.01: Order SK-1042 is out for delivery, expected today by 8 pm.
limit USD 0.003: Stopped: this conversation reached its cost limit (USD 0.003). A person will follow up.

Because the budget wraps the event stream, stopping it stops the agent: no further model calls are made after the limit. In production, set budgets per conversation type from their measured cost distribution, and alert when many runs hit them, because that is usually a stuck pattern (Lesson 14.57) rather than expensive customers.

Check your understanding

Explain the mechanismHow do you show progress to a user while an agent runs several steps?

Worked answer. Make the loop emit events as it works: a step starting, a tool being called, a result arriving, the answer, and usage. In Python that is a generator, and in a service it goes to the browser over server-sent events or a WebSocket, or through a protocol such as AG-UI. The UI shows friendly progress lines for tool calls and streams the final answer's tokens as they arrive. Which events are visible, and how they are worded, is decided in code, so raw tool inputs and internal data never reach the screen.

A plausible wrong answer. "Turn on streaming in the API call." That streams the tokens of one model response. An agent's wait is mostly between responses, while tools run and the next request is sent, and token streaming shows nothing during that time.

Follow-ups. What should the user see while a run waits for an approval? How do you cancel a run from the UI?

Debug a failureYour per-conversation cost estimate is half the invoice. Where do you look?

Worked answer. Check how usage is aggregated. The usual bugs are counting only the last request of a run instead of summing all of them, missing calls made outside the main loop (retries, judges, summarizers, embeddings), and ignoring the cached-input and output price differences. Then check what the estimate excludes: failed and abandoned runs still cost money, and runs that hit limits often cost the most. Reconcile one day of per-request usage records against the provider's usage report, and alert on the gap.

A plausible wrong answer. "The provider must be overcharging." Possible, but per-request usage is the provider's own number. A mismatch almost always means your aggregation is incomplete.

Follow-ups. How would you attribute cost to features or tenants? Which single change usually cuts agent cost most?

Defend a designWhy measure cost per run from the first prototype?

Worked answer. Agent cost does not scale with traffic alone. It scales with steps per run, and steps grow when tools fail, descriptions are vague or a model gets stuck. Measuring per run from day one gives a baseline, so a regression shows up as a change in the distribution, not as a surprise invoice. It also makes design choices measurable: trimming tool results, caching prompts or routing simple questions to a cheaper path each have a visible effect on the same questions. The cost of collecting usage is a few lines of code; the cost of not having it is debugging spend from an invoice.

A plausible wrong answer. "Optimize cost after launch, once usage is known." By then nobody can tell which change made a conversation type expensive.

Follow-ups. What would you put on a cost dashboard? How do budgets per run interact with quality?
