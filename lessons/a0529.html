The problem

In plain words first

A booking assistant has to remember what the user wants while the conversation moves: "somewhere cheap in the north", then "pizza would be great", then "actually, make it moderate". Dialogue state tracking keeps a small form up to date after every user turn: one field (a slot) per thing the backend needs, such as cuisine, area, price range and party size. A slot can be filled, changed by a correction, cleared by "never mind", or left alone. If one slot is wrong at the end, the booking is wrong. This lesson builds a rule-based tracker and an LLM tracker with a validated schema, measures both turn by turn with joint goal accuracy, and shows why a schema guarantees well-formed output but not correct output.

In a task-oriented dialogue system, the user's goal is encoded as a set of slot-value pairs: {cuisine: italian, area: north, price: moderate}. Every user turn can add, change, or remove a slot. The system must read the whole conversation and output the current state correctly.

Get a single slot wrong and the system books the wrong restaurant, schedules the wrong flight, or charges the wrong card. DST is the hinge between what the user said and what the backend executes.

Why it still matters in 2026 despite LLMs:

  • Compliance-sensitive domains (banking, healthcare, airline booking) require deterministic slot values, not free-form generation.
  • Tool-use agents still need slot resolution before calling APIs.
  • Multi-turn correction is harder than it looks: "actually no, make it Thursday."

The modern pipeline: classical DST concepts + LLM extractors + structured-output guardrails.

The idea

Task structure. A schema defines domains (restaurant, hotel, taxi) and their slots (cuisine, area, price, people). Each slot can be empty, filled with a value from a closed set (price: {cheap, moderate, expensive}), or a free-form value (name: "The Copper Kettle").

Two DST formulations.

  • Classification. For each (slot, candidate_value) pair, predict yes/no. Works for closed-vocab slots. Standard pre-2020.
  • Generation. Given the dialogue, generate slot values as free text. Works for open-vocab slots. The modern default.

Metric. Joint Goal Accuracy (JGA) — the fraction of turns where every slot is correct. All-or-nothing. On MultiWOZ 2.4, the best reported results are in the low 80s: in the LDST paper's comparison, LDST (a fine-tuned 7B LLaMA) reaches 79.9% and ChatGPT 83.2%.

Architectures.

  1. Rule-based (slot regex + keyword). Strong baseline for narrow domains. Debuggable.
  2. TripPy / BERT-DST. Copy-based generation with BERT encoding. Pre-LLM standard.
  3. LDST (LLaMA + LoRA). Instruction-tuned LLM with domain-slot prompting. Comes close to ChatGPT on MultiWOZ 2.4 (79.9% against 83.2%) with an open 7B model.
  4. Ontology-free (2024–26). Skip the schema; generate slot names and values directly. Handles open domains.
  5. Prompt + structured output (2024–26). LLM with Pydantic schema + constrained decoding. 5 lines of code, production-ready.
The same idea as a formula

State. For a schema with slots s1​,…,sK​, the state after user turn t is Bt​=(v1,t​,…,vK,t​), each v a value or empty. MultiWOZ adds a special value dontcare for "any area is fine". The tracker computes Bt​=f(Bt−1​,ut​) incrementally, or Bt​=f(u1​,…,ut​) from the whole history.

Two formulations. Classification: for each slot, a softmax over its candidate values plus "none" and "dontcare",

P(vk,t​=v∣u1..t​)=softmaxv​(wv⊤​hk,t​),v∈Vk​∪{none,dontcare}

Generation: decode the value as text, P(v∣u1..t​,sk​)=∏j​P(yj​∣y<j​,u1..t​,sk​), which also handles open values such as names and times.

Metrics. Over all turns t of all dialogues,

JGA=T1​t∑​[B^t​=Bt​],slot accuracy=TK1​t∑​k∑​[v^k,t​=vk,t​]

JGA is all-or-nothing per turn, and errors persist: a wrong value stays wrong until the user changes that slot. If each turn independently introduces an error with probability ε and errors are never fixed, the state at turn t is right with probability about (1−ε)t.

Cost of regenerating the state. If each turn adds ℓ tokens and the tracker re-reads the full history every turn, a T-turn dialogue costs ℓ∑t=1T​t=ℓT(T+1)/2 tokens, quadratic in T; an incremental tracker that reads Bt−1​ and ut​ costs about T(ℓ+∣B∣).

Worked example
Why JGA is so much lower than slot accuracy

A tracker with 4 slots gets 95% of slots right on every turn, errors independent. A turn is fully right with probability 0.954=0.81. Now let errors persist: if 5% of turns introduce one error that the user never corrects, after 10 turns the state is still right with probability 0.9510=0.60. Slot accuracy stays near 95%; JGA falls to 60%.

Cost: a 20-turn chat with 30 tokens per user turn. Re-reading the history every turn reads 30×20×21/2=6,300 tokens of dialogue; reading only the previous state (about 30 tokens) and the new turn reads about 20×60=1,200.

Check your mental model
  • ✗ "If the LLM's output passes the schema, the state is right."
    ✓ The schema checks that the slots and values are allowed, not that the user said them.
  • ✗ "A new turn should produce a new state from scratch."
    ✓ Slots the user did not touch must keep their values. "For four people" changes only the party size.
  • ✗ "JGA on the final turn of each dialogue is enough."
    ✓ JGA is computed on every turn. A tracker that is wrong for three turns and right on the last would book the wrong table if the user stopped earlier.

Idea 1 · The classic failure modes

  • Co-reference across turns. "Let's stay with the first option." Needs to resolve which option.
  • Over-write vs append. User says "add Italian." Do you replace cuisine or append?
  • Implicit confirmations. "OK cool" — did that accept the offered booking?
  • Correction. "Actually make it 7 pm." Must update time without clearing other slots.
  • Coreference to previous system utterance. "Yes, that one." Which "that"?

Step 1 · rule-based slot extractor

See code/main.py. Regex + synonym dictionaries cover the canonical phrasings of a narrow domain:

SIMPLE_CUISINE_SYNONYMS = {           # the two-cuisine sketch; main.py's CUISINE_SYNONYMS has four
    "italian": ["italian", "pasta", "pizza", "italy"],
    "chinese": ["chinese", "chow mein", "noodles"],
}


def extract_cuisine_simple(utterance):
    for canonical, synonyms in SIMPLE_CUISINE_SYNONYMS.items():
        if any(syn in utterance.lower() for syn in synonyms):
            return canonical
    return None


for u in ["Somewhere that does good pizza", "I fancy noodles", "Thai food please", "No Italian, I had pasta yesterday"]:

Step 2 · state update loop

NEGATION_CLEARS = list(SLOT_EXTRACTORS)     # slots that "never mind the <slot>" may clear
is_negated = is_negation                    # main.py: a negation cue and the slot's name in the same turn


def update_state(state, utterance):
    new_state = dict(state)                 # invariant 1: slots the turn does not mention keep their values
    for slot, extractor in SLOT_EXTRACTORS.items():
        value = extractor(utterance)
        if value is not None:               # invariant 3: a new value overwrites (corrections)
            new_state[slot] = value
        elif slot in NEGATION_CLEARS and is_negated(utterance, slot):
            new_state[slot] = None          # invariant 2: explicit negation clears
    return new_state


state = {"cuisine": None, "area": None, "price": None, "people": None}
for u in ["Cheap Italian in the north.", "Actually, moderate.", "Never mind the area."]:
    state = update_state(state, u)
    print(f"{u:30} {state}")
What you should see
Cheap Italian in the north.    {'cuisine': 'italian', 'area': 'north', 'price': 'cheap', 'people': None}

Three invariants:

  • Never reset a slot the user did not touch.
  • Explicit negation ("never mind the cuisine") must clear.
  • User correction ("actually...") must overwrite, not append.

The repository's sketch referred to NEGATION_CLEARS and is_negated, which it never defined, and checked negation after extraction, so "Never mind the cuisine, any food is fine" would extract any and then clear it. The version above follows main.py: a value found in the turn wins, and negation clears only when the turn gives no new value.

import instructor

    area: Optional[Literal["north", "south", "east", "west", "center"]] = None
    price: Optional[Literal["cheap", "moderate", "expensive"]] = None
    people: Optional[int] = None

def llm_dst(history, llm):
    prompt = f"""You track the slot values of a restaurant booking across turns.
Dialogue so far:
{render(history)}

Update the state based on the latest user turn. Output only the JSON state."""
    return llm(prompt, response_model=RestaurantState)

Instructor + Pydantic guarantees the shape: every returned object has only known slots, each with an allowed value, because invalid output is sent back to the model with the validation error until it passes or a retry limit is reached. It does not guarantee the values: a perfectly valid state can contain a price the user never mentioned.

Not run here: Instructor wraps a hosted model's client. Step 4 runs the same idea locally: a Pydantic schema, a small model, and Instructor's validate-and-retry loop written out by hand.

Step 4 · JGA evaluation

def joint_goal_accuracy(predicted_states, gold_states):
    correct = sum(1 for p, g in zip(predicted_states, gold_states) if p == g)
    return correct / len(predicted_states)

Calibrate: what fraction of turns does the system get ALL slots right? On MultiWOZ 2.4 the best published systems score around 80–83%. A narrow in-domain system should do better than that on its own vocabulary, or an LLM baseline will beat it.

def run_rules(dialogue):
    state, out = dict(E), []
    for utt, _ in dialogue:
        state = update_state(state, utt); out.append(state)
    return out

def score(predict, label):
    turns = slots = joint = slot_ok = 0
    for dialogue in test_dialogues:
        for (utt, gold), pred in zip(dialogue, predict(dialogue)):
            turns += 1; joint += pred == gold
            slots += len(gold); slot_ok += sum(pred.get(k) == v for k, v in gold.items())
            if pred != gold:
                wrong = {k: (pred.get(k), v) for k, v in gold.items() if pred.get(k) != v}
                print(f"   {utt[:50]:52s} wrong (predicted, gold): {wrong}")
    print(f"{label}: joint goal accuracy {joint}/{turns} = {joint / turns:.2f}, slot accuracy {slot_ok}/{slots} = {slot_ok / slots:.2f}\n")

An LLM tracker with a validated schema

Qwen2.5-0.5B-Instruct (inference only) reads the whole dialogue each turn and writes the full state as JSON. The lesson's RestaurantState schema validates it, with one addition from the pitfalls list: values are lower-cased and "centre" mapped to "center" before validation. Invalid output is sent back once with the error, as Instructor does.

import json, re, time, torch
from typing import Literal, Optional
from pydantic import BaseModel, ValidationError, field_validator
from transformers import AutoTokenizer, AutoModelForCausalLM

class RestaurantState(BaseModel):
    cuisine: Optional[Literal["italian", "chinese", "indian", "thai", "any"]] = None
    area: Optional[Literal["north", "south", "east", "west", "center"]] = None
    price: Optional[Literal["cheap", "moderate", "expensive"]] = None
    people: Optional[int] = None

# The strict schema rejects what small models often write:
try:
    RestaurantState.model_validate({"cuisine": "Italian", "area": "centre"})
except ValidationError as err:
    print("strict schema:", err.error_count(), "errors:", [e["msg"] for e in err.errors()])

class NormalizedState(RestaurantState):
    """Same schema, plus the lesson's 'normalise everywhere' pitfall applied before validation."""
    @field_validator("cuisine", "area", "price", mode="before")
    @classmethod
    def lower(cls, v):
        if isinstance(v, str):
            v = v.strip().lower()
            return {"centre": "center", "": None, "none": None, "null": None}.get(v, v)
        return v

print("normalised schema:", NormalizedState.model_validate({"cuisine": "Italian", "area": "centre"}).model_dump())

qtok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
qlm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", dtype=torch.float32).eval()

def llm(prompt, max_new_tokens=60):
    ids = qtok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                   return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = qlm.generate(ids, max_new_tokens=max_new_tokens, do_sample=False)
    return qtok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)

SCHEMA = ('{"cuisine": one of "italian", "chinese", "indian", "thai", "any" or null, '
          '"area": one of "north", "south", "east", "west", "center" or null, '
          '"price": one of "cheap", "moderate", "expensive" or null, "people": a number or null}')

stats = {"valid first time": 0, "valid after retry": 0, "invalid, kept previous state": 0}

def llm_dst(history, previous):
    """Regenerate the whole state from the full history; validate; retry once with the error (Instructor's loop)."""
    prompt = ("You track a restaurant booking. Read the whole dialogue and output the user's current wishes "
              f"as JSON with exactly these keys: {SCHEMA}. Use null for anything not requested.\n\n"
              + "\n".join(f"User: {u}" for u in history) + "\n\nJSON:")
    for attempt in range(2):
        raw = llm(prompt)
        m = re.search(r"\{.*?\}", raw, re.S)
        try:
            state = NormalizedState.model_validate(json.loads(m.group(0) if m else raw))
            stats["valid first time" if attempt == 0 else "valid after retry"] += 1
            return state.model_dump()
        except (ValueError, ValidationError) as err:
            prompt += f"\n{raw}\n\nThat was not valid: {' '.join(str(err).splitlines()[:3])}. Output corrected JSON only:"
    stats["invalid, kept previous state"] += 1
    return previous

def run_llm(dialogue):
    state, out, history = dict(E), [], []
    for utt, _ in dialogue:
        history.append(utt)
        state = llm_dst(history, state); out.append(state)
    return out

t0 = time.time()
score(run_llm, "LLM (0.5B) + Pydantic, whole state regenerated each turn")
print(stats, f"({time.time() - t0:.0f} s)")

Reading this output

The first two lines show why the normaliser is there: the strict schema rejects "Italian" and "centre", which is exactly what this model writes; without normalisation, most of its answers failed validation in testing. With it, all 15 outputs are valid on the first try. Yet JGA is 0.27, far below the rules' 0.60, with slot accuracy 0.78. The errors are almost all invented values: a cuisine on the very first turn, "expensive" and party sizes of 4 or 5 that nobody mentioned, and any for "I don't want Chinese". A validated state is a well-formed state, not a true one. A larger model makes fewer such errors; the defences that do not depend on model size are to require evidence (the slot's words in the dialogue, as in Lesson 5.26), to combine with rules, and to confirm before acting.

Step 5 · handling correction

CORRECTION_CUES = {"actually", "no wait", "on second thought", "change that to"}


def is_correction(utterance):
    return any(cue in utterance.lower() for cue in CORRECTION_CUES)

On a detected correction, overwrite the last-updated slot rather than appending. Hard to get right without LLM help. The modern pattern: always let the LLM regenerate the whole state from history rather than incrementally updating — this naturally handles corrections.

Break it on purpose

Feed the rule-based tracker the turn "I'm not paying for anything expensive, cheap is better." Which price does it store, and why? Then try "Book for two people... no wait, four people." (Solution B1.)

Industry practice
What's current (2024–2026)
  • LLM-based tracking is the default for new systems. Production assistants keep state by having an LLM fill a schema each turn, and conversational platforms such as Rasa CALM and Google's Dialogflow CX / Conversational Agents combine LLM understanding with explicit flows and slots.
  • Tool calling is DST under another name. An agent filling a function's arguments across several turns is tracking slots against a JSON schema; structured-output modes and constrained decoding (Lesson 5.20) guarantee the shape, and evaluation still needs per-turn, per-argument checks. The remaining errors are the ones in this lesson: invented values, missed corrections and lost "don't care" values.

Sources: Rasa CALM, Dialogflow CX, OpenAI function calling, MultiWOZ 2.4.

Pitfalls

  • Full-history regeneration cost. Letting the LLM regenerate state each turn costs O(n2) total tokens. Cap history or summarize older turns.
  • Schema drift. Adding new slots post-hoc breaks old training data. Version your schema.
  • Case sensitivity. "Italian" vs "italian" vs "ITALIAN" — normalize everywhere.
  • Implicit inheritance. If the user has previously specified "for 4 people," a new request for a different time should not clear people. Always pass the full history.
  • Free-form vs closed-set. Names, times, and addresses need free-form slots; cuisines and areas are closed. Mix both in the schema.

Recap
What to keep from this lesson
  • The state is a slot-value form updated every turn: fill, overwrite on correction, clear on negation, leave untouched otherwise.
  • Score with joint goal accuracy on every turn, plus slot accuracy; errors persist, so JGA falls far below slot accuracy.
  • Rules are precise on their own vocabulary and blind outside it; LLMs cover paraphrases but invent values.
  • A schema (Pydantic, constrained decoding) guarantees valid output, not correct output; normalise case and spelling before validating.
  • Require evidence or confirmation for slots that trigger actions.

Exercises

  1. Easy. Build the rule-based state tracker in code/main.py for 3 slots (cuisine, area, price). Test on 10 hand-crafted dialogues. Measure JGA.
  2. Medium. Same dataset with Instructor + Pydantic + a small LLM. Compare JGA. Inspect the hardest turns.
  3. Hard. Implement both and route: rule-based primary, LLM fallback when rule-based emits <2 slots with confidence. Measure the combined JGA and inference cost per turn.

Solutions

SolutionP1 · Rules win here, and the LLM invents

The rules score 0.60 JGA, the 0.5B LLM 0.27. The rules fail by missing paraphrases; the LLM fails by filling slots nobody asked for (an unrequested cuisine, "expensive", party sizes of 4 or 5), which a schema cannot catch because those are allowed values. Slot accuracy (0.88 against 0.78) hides how different these failures are at the booking level.

SolutionB1 · Word order and substrings decide

extract_price checks the price words in dictionary order, cheap first, so "I'm not paying for anything expensive, cheap is better" happens to store cheap, the right answer for the wrong reason; reorder the sentence to "cheap is out, I want expensive" and it still says cheap. For "two people... no wait, four people", extract_people takes the first match, 2, even though the correction cue is present: the cue is detected by is_correction but nothing uses it. Corrections need the last mention to win, and negation needs scope.
