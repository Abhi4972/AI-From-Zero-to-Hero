Why this came about

Single-shot retrieval had no way to recover when it fetched the wrong passages. Giving retrieval decisions to an agent, which can grade results, rewrite the query, try again or say it does not know (Self-RAG and Corrective RAG, 2023 and 2024), made RAG more robust at the cost of more model calls.

In plain words first
A researcher who checks their sources

Plain RAG retrieves once and hopes. Agentic RAG adds decisions: should we search at all, are the results relevant, should we rewrite the query and try again, is the answer supported by the sources? Corrective RAG grades retrieved passages and retries or falls back when they are poor; self-checking RAG verifies the answer before showing it. Each check is a model call, so the loop needs limits.

From pipeline to agent

Classic RAG always retrieves once, then answers. Agentic RAG gives retrieval to an agent as one or more tools, so the model decides:

  • whether to retrieve at all ("hi" needs no search)
  • where to look (policies index, product catalog, SQL warehouse, web)
  • how to rephrase the query, and whether to try again
  • when it has enough evidence to answer

The trade-off is the usual one for agents: better on hard, multi-step questions; slower, costlier and less predictable on easy ones. Many production systems route easy questions to a fixed pipeline and only hard ones to the agent.

In production
What goes wrong with agentic RAG in production
  • Over-searching: the agent calls retrieval five times for a question one search would answer. Cap retrieval calls per turn, and route simple questions to the fixed pipeline before the agent sees them.
  • Loops on missing content: when the answer is not in the corpus, the agent keeps rephrasing. Give it an explicit "not found, say so" path after two or three tries.
  • Latency users notice: each retrieval round trip adds a model call. Stream a status message ("checking the refund policy...") and measure p95, not the average.
  • Inconsistent answers across runs: different search paths find different evidence. Evaluate with repeated runs (pass^k), not single runs.
  • If agentic RAG is not beating plain RAG on your eval, the usual reason is that the plain pipeline was never tuned. Go back to the Lesson 14.143 loop first.

Self-correcting retrieval

The Corrective RAG (CRAG) pattern adds a grader between retrieval and generation. Here it is with the lab's search functions and a grader you can replace with a model call:

def grade(question: str, chunk_ids: list[str]) -> bool:
    """Stand-in for an LLM grader: is any retrieved chunk relevant? A real grader asks a small model
    'Does this passage help answer the question? yes/no' for each chunk."""
    q = set(tokenize(question)) - {"the", "a", "is", "i", "my", "can", "do", "what", "how"}
    return any(len(q & set(tokenize(TEXT[c]))) >= 2 for c in chunk_ids)

def corrective_search(question: str, rewrites: list[str], max_tries: int = 3) -> tuple[list[str], list[str]]:
    tried = []
    for query in [question, *rewrites][:max_tries]:
        tried.append(query)
        hits = search_hybrid(query)
        if grade(query, hits):                                 # a real grader judges relevance to the user's question
            return hits, tried
    return [], tried                                           # nothing good: the answer step should abstain

hits, tried = corrective_search("speedy shipping price?", rewrites=["express delivery cost"])
print(tried, "->", hits)
hits, tried = corrective_search("Do you sell car insurance?", rewrites=["car insurance policy"])
print(tried, "->", hits or "abstain: no relevant sources")
What you should see
['speedy shipping price?', 'express delivery cost'] -> ['shipping#1', 'shipping#0', 'refund-policy#0']
['Do you sell car insurance?', 'car insurance policy'] -> abstain: no relevant sources

The first question failed the grader, was rewritten into the corpus's vocabulary, and succeeded. The second correctly found nothing, so the answer step should say "I don't know" instead of improvising.

Step by step: agentic retrieval in code

The blocks continue the lab from Lessons 14.144 to 14.135. Where a model makes a decision (route, rewrite, extract, verify), a small stand-in function makes the same decision deterministically and the real prompt is described in its docstring, so the control flow is visible and runnable.

Step 1 · Adaptive routing: decide whether and how to retrieve

Not every question needs retrieval, and some need several rounds. An adaptive RAG router picks the strategy per question, which saves cost on easy questions and spends it on hard ones.

def route(question: str) -> str:
    """Stands in for a small classifier model: 'none' (chit-chat), 'single' (one fact) or 'multi_hop'."""
    q = question.lower()
    if re.fullmatch(r"(hi|hello|thanks|thank you)[!. ]*", q):
        return "none"
    if re.search(r"\b(and|if|then)\b", q):
        return "multi_hop"
    return "single"

CALLS = {"retrievals": 0}
def counted_search(query: str, k: int = 3) -> list[str]:
    CALLS["retrievals"] += 1
    return search_hybrid(query, k)

for q in ["hi", "How long does a UPI refund take?",
          "If I cancel a prepaid order before dispatch, how long until the money is back on UPI?"]:
    print(f"{route(q):9} <- {q}")
What you should see
none      <- hi
single    <- How long does a UPI refund take?
multi_hop <- If I cancel a prepaid order before dispatch, how long until the money is back on UPI?

In production the router is a cheap model call with a few examples, measured on its own eval set (Lesson 14.62's routing pattern).

Step 2 · Multi-hop retrieval

A multi-hoplater · 14.150 question needs a fact from one passage to know what to search next. The cancellation policy says cancelled prepaid orders are refunded; only then do you know to look up refund timing.

def next_query(question: str, evidence: list[str]) -> str | None:
    """Stands in for: 'Given the question and the evidence so far, what should we search next?
    Reply DONE if the evidence answers the question.'"""
    text = " ".join(TEXT[c] for c in evidence).lower()
    if "refunded" in text and "upi refunds" not in text:
        return "how long do UPI refunds take"
    return None

def multi_hop(question: str, max_hops: int = 3) -> list[tuple[str, list[str]]]:
    hops, evidence, query = [], [], question
    for _ in range(max_hops):
        hits = counted_search(query, 1)
        hops.append((query, hits))
        evidence += [h for h in hits if h not in evidence]
        query = next_query(question, evidence)
        if query is None:
            break
    return hops

CALLS["retrievals"] = 0
for query, hits in multi_hop("If I cancel a prepaid order before dispatch, how long until the money is back on UPI?"):
    print(f"search {query!r} -> {hits}")
print("retrievals:", CALLS["retrievals"])
What you should see
search 'If I cancel a prepaid order before dispatch, how long until the money is back on UPI?' -> ['cancellation#0']
search 'how long do UPI refunds take' -> ['refund-policy#1']
retrievals: 2

The first hop found the cancellation rule ("cancelled prepaid orders are refunded in full"); the second used that to fetch the UPI timing ("UPI refunds usually arrive in 2 days"). Bound the hops, and log each query: the sequence of queries is the most useful debugging signal in agentic RAG.

Step 3 · Verify the answer against the evidence

Self-RAG and similar patterns check the draft answer before it is sent: split it into claims, check each claim against the retrieved passages, and revise or abstain if any is unsupported. Here the support check is word overlap; in production it is an LLM judgelater · 14.141 or an NLI model, or a platform service (Bedrock contextual grounding checkslater · 14.131, Azure groundedness detectionlater · 14.130, Google's Check Grounding API).

def claims(answer: str) -> list[str]:
    return [c.strip() for c in re.split(r"(?<=[.!?])\s+", answer) if c.strip()]

def supported(claim: str, evidence_ids: list[str], threshold: float = 0.5) -> bool:
    """Stand-in for 'Is this claim fully supported by the passages? yes/no'."""
    words = {w for w in tokenize(claim) if w not in STOP and not w.isdigit() or w in {"2", "7", "30"}}
    best = max(len(words & set(tokenize(TEXT[e]))) / max(len(words), 1) for e in evidence_ids)
    return best >= threshold

def verify(answer: str, evidence_ids: list[str]) -> list[tuple[str, bool]]:
    return [(c, supported(c, evidence_ids)) for c in claims(answer)]

evidence = ["cancellation#0", "refund-policy#1"]
draft = ("Cancelled prepaid orders are refunded in full. UPI refunds usually arrive in 2 days. "
         "You will also receive a INR 200 voucher for the trouble.")
for claim, ok in verify(draft, evidence):
    print("OK " if ok else "BAD", claim)
What you should see
OK  Cancelled prepaid orders are refunded in full.
OK  UPI refunds usually arrive in 2 days.
BAD You will also receive a INR 200 voucher for the trouble.

The voucher is a hallucination: nothing in the evidence promises it. Drop or rewrite unsupported claims before sending, and count them: the unsupported-claim rate is a production quality metric you can alert on.

Step 4 · Rewrite with the failure in view

corrective_search in the first block of this lesson takes a fixed list of rewrites. A real rewriter is a model call, and the mistake to avoid is giving it only the question: it then produces the same query twice. Give it what was tried and what came back.

def rewrite(question: str, tried: list[tuple[str, list[str]]]) -> str:
    """Stand-in for the rewrite prompt: 'The question is {question}. These queries were tried and each
    returned passages a grader judged irrelevant: {tried}. Write one new keyword query from a different angle.'
    The stand-in swaps in corpus vocabulary and drops words that already failed."""
    synonyms = {"speedy": "express", "price": "cost", "money back": "refund", "stop": "cancel", "parcel": "delivery"}
    failed_words = {w for q, _ in tried for w in tokenize(q)}
    words = [synonyms.get(w, w) for w in tokenize(question) if w not in STOP]
    fresh = [w for w in words if w not in failed_words] or words
    return " ".join(fresh) + (" policy" if len(tried) >= 2 else "")

def corrective_search_v2(question: str, max_tries: int = 3) -> tuple[list[str], list[tuple[str, list[str]]]]:
    tried, query = [], question
    for _ in range(max_tries):
        hits = search_hybrid(query)
        if grade(query, hits):                                # the stand-in grader is word overlap, so it scores the query
            return hits, tried
        tried.append((query, hits))                           # remember the query AND what it surfaced
        query = rewrite(question, tried)
    return [], tried

hits, tried = corrective_search_v2("speedy parcel price?")
for q, h in tried:
    print(f"tried {q!r} -> {h}")
print("found:", hits)
What you should see
tried 'speedy parcel price?' -> ['refund-policy#0', 'refund-policy#1', 'shipping#0']
found: ['shipping#1', 'shipping#0', 'refund-policy#0']

The first query failed the grader (the corpus never says "speedy" or "parcel"), the rewriter saw that and produced "express delivery cost", which hit. What makes the second attempt better than a blind retry is that the rewriter knows which words were already tried and what they surfaced. One more rule for the real thing: the stand-in grader is word overlap, so it must score the rewritten query, but a model grader should be shown the user's original question alongside the passages, so a rewrite that drifts away from the intent cannot pass.

Step 5 · Condense follow-up questions before retrieving

In a chat, the second question is "and how long does that take?". Retrieval on those words finds nothing useful. Rewrite it to stand alone first, using the history; this is the one model call that belongs before retrieve.

import re

def condense(history: list[str], question: str) -> str:
    """Stand-in for 'Given this history, rewrite the last question so it can be understood on its own.'
    Rule: a pronoun ('that', 'it', 'this') is replaced by the topic of the previous question."""
    if not history or not re.search(r"\b(that|it|this)\b", question, re.I):
        return question
    topic = re.sub(r"^(how do i|how do|what is|what are|can i)\s+", "", history[-1], flags=re.I).rstrip("?")
    return re.sub(r"\b(that|it|this)\b", f"'{topic}'", question, count=1, flags=re.I)

history = ["Can I stop an order that hasn't left the warehouse yet?"]
for follow_up in ["Is there a fee for that?", "What about cash on delivery?"]:
    standalone = condense(history, follow_up)
    print(f"{follow_up!r}\n  as asked  -> {search_hybrid(follow_up, 1)}\n  condensed -> {standalone!r} -> {search_hybrid(standalone, 1)}")
What you should see
'Is there a fee for that?'
  as asked  -> ['cod#0']
  condensed -> "Is there a fee for 'stop an order that hasn't left the warehouse yet'?" -> ['cancellation#0']
'What about cash on delivery?'
  as asked  -> ['cod#0']
  condensed -> 'What about cash on delivery?' -> ['cod#0']

As asked, "Is there a fee for that?" retrieves the cash-on-delivery chunk (the only one with the word "fee"), which would produce a confident wrong answer; condensed, it retrieves the cancellation policy. The second question already stood alone and was left as it was. Store the history in the agent's state or read it from the thread's messages, and condense only when the question is not self-contained, so you do not pay a model call on every turn.

Step 6 · When verification fails, regenerate once with the feedback

Step 3 drops unsupported claims. Cheaper and usually better: send the failed claims back to the writer as feedback and let it try once more; fall back only if the second draft fails too.

def write_answer(question: str, evidence_ids: list[str], feedback: str = "") -> str:
    """Stand-in for the writer. The first draft adds a promise the sources do not make; given feedback, it does not."""
    draft = ("Cancelled prepaid orders are refunded in full. UPI refunds usually arrive in 2 days. "
             "You will also receive a INR 200 voucher for the trouble.")
    if feedback:
        bad = re.findall(r"'([^']+)'", feedback)
        draft = " ".join(c for c in claims(draft) if c not in bad)
    return draft

def answer_with_check(question: str, evidence_ids: list[str]) -> dict:
    draft = write_answer(question, evidence_ids)
    bad = [c for c, ok in verify(draft, evidence_ids) if not ok]
    if not bad:
        return {"answer": draft, "regenerated": False}
    feedback = "These claims are not supported by the sources; remove or rewrite them: " + "; ".join(f"'{c}'" for c in bad)
    second = write_answer(question, evidence_ids, feedback)
    bad2 = [c for c, ok in verify(second, evidence_ids) if not ok]
    if bad2:
        return {"answer": "I can't fully confirm this; here is what the sources say.", "regenerated": True, "still_unsupported": bad2}
    return {"answer": second, "regenerated": True, "removed": bad}

print(answer_with_check("How are cancelled prepaid orders refunded?", ["cancellation#0", "refund-policy#1"]))
What you should see
{'answer': 'Cancelled prepaid orders are refunded in full. UPI refunds usually arrive in 2 days.', 'regenerated': True, 'removed': ['You will also receive a INR 200 voucher for the trouble.']}

One retry, with the exact failing sentences in the prompt, never a loop: a writer that failed twice with feedback is unlikely to pass on the third attempt, and every attempt costs tokens. Log regenerated and still_unsupported as metrics; a rising regeneration rate usually means retrieval got worse, not that the writer did.

Step 7 · A small deep-research loop

Deep research combines everything: plan sub-questions, retrieve for each in parallel, take notes with citations, and write a report whose every claim is checked. This version uses the lab corpus and the verification step from Step 3.

import asyncio

async def research(sub: str) -> dict:
    hits = await asyncio.to_thread(search_reranked, sub, 1)          # retrieval runs in parallel threads
    return {"question": sub, "source": hits[0], "note": TEXT[hits[0]].split(". ")[1] + "."}

async def deep_research(topic: str, plan: list[str]) -> str:
    notes = await asyncio.gather(*(research(s) for s in plan))
    report = " ".join(f"{n['note']} [{n['source']}]" for n in notes)
    unsupported = [c for c, ok in verify(re.sub(r"\[.*?\]", "", report), [n["source"] for n in notes]) if not ok]
    return report + ("" if not unsupported else f"\nUNSUPPORTED: {unsupported}")

plan = ["What is the refund window for damaged items?", "How fast do UPI refunds arrive?",
        "Is there a fee for cash on delivery?"]                       # in production: a planning model call
print(asyncio.run(deep_research("ShopKart refunds and payments", plan)))
What you should see
Customers can request a refund within 7 days of delivery. [refund-policy#0] Refunds go back to the original payment method within 5 to 7 business days. [refund-policy#1] COD is available for orders up to INR 10,000 in most pin codes. [cod#0]

The structure is right (parallel research, citations, verification), and the output shows why quality depends on each piece: every note is a real sentence with a valid citation, so verification passes, yet the first note gives the general 7-day window instead of the 30-day rule for damaged items, the second gives refund timing in general rather than for UPI, and the third answers a neighbouring question. Citation checks prove support, not relevance. Real deep-research agents fix this with a model that reads the whole passage and extracts the sentence that answers the sub-question, and a final review step against the plan.

From the field
LinkedIn: a graph from the tickets' own structure

LinkedIn's customer-service team built retrieval over historical support tickets as a knowledge graph rather than flat chunks (paper, 2024). Each ticket became a tree of its sections (summary, description, priority and so on), and tickets were linked by the tracker's explicit references and by title similarity. Questions were answered by finding the most similar tickets, then turning the question into a graph query (Cypherlater · 14.154 on Neo4j), with plain text retrieval as a fallback when the graph query failed. Against a flat-text baseline, retrieval MRR rose from 0.522 to 0.927, and after about six months in use by the support team, median time to resolve an issue fell by 28.6%. The lesson: the graph came from structure that already existed in the data (sections and ticket links), not from expensive entity extraction over everything. Source: Xu et al., "Retrieval-Augmented Generation with Knowledge Graphs for Customer Service Question Answering".

From the field
Uber: agents around retrieval, not instead of it

The second half of Uber's Genie redesign (Lesson 14.135) added three narrow agents around a hybrid retriever: a query optimizer that clarifies and splits questions, a source identifier that picks the likely policy documents from their titles, summaries and FAQs, and a post-processor that removes duplicate chunks and puts the rest in document order. Retrieval itself stayed hybrid (BM25 over enriched metadata plus vectors, results unioned), and an LLM judge scoring answers against expert-written references cut each evaluation round from weeks to minutes. Built on LangChainlater · 14.71 and LangGraphlater · 14.79 inside Uber's Michelangelo platform. Source: Uber Engineering, "Enhanced Agentic-RAG".

Solutions

SolutionP1 · Not every question needs search

"hi, thanks!" needs no retrieval (save a search and tokens); the COD question needs the help center. Routing also chooses between sources, such as the order database or documents.

SolutionB1 · Corrective loops need limits

It rewrites and searches forever, or until a recursion or budget limit, because the grader never passes. Limit the tries and, when they run out, answer that the information is not available.

SolutionD1 · The grader is a model too

The grader's prompt or model handles Hinglish poorly, so relevance judgments fail for those questions. Evaluate the grader on labeled pairs per language, fix its prompt or model, and log grader decisions.

SolutionM1 · Agentic RAG with two sources

The agent should look up the order, then search the refund policy, then answer with both. Check the trace for the order of calls, and add the case to the eval: multi-source questions are where agentic RAG beats a fixed pipeline.

Check your understanding

Explain the mechanismWhat is agentic RAG, and how is it different from a RAG pipeline?

Worked answer. In a pipeline, every question is retrieved once with fixed steps. In agentic RAG, a model decides whether to retrieve, which source to use, how to phrase the search, and whether the results are good enough, repeating as needed; corrective RAG adds a relevance grader and rewrites. It handles multi-part and multi-source questions better, at higher cost and latency.

A plausible wrong answer. "Agentic RAG is always better." For simple single-source questions, a pipeline is cheaper and more predictable.

Follow-ups. How would you stop an agentic RAG loop from wandering?

Debug a failureAn agentic RAG system is accurate but slow. Where do you look?

Worked answer. In traces: how many searches and grader calls each question uses, and which questions loop. Route simple questions to a single-pass pipeline, cap retries, run independent searches in parallel, and use a smaller model for grading.

A plausible wrong answer. "Use a faster model." The number of steps is the main cost.

Follow-ups. What latency budget would you set per question type?

Defend a designAgentic RAG or a fixed pipeline for ShopKart's help center?

Worked answer. A fixed hybrid pipeline for the bulk of policy questions, which are single-source and simple; an agent for questions that combine an order lookup with policy, or that need several searches. Route between them, and measure both on the eval set.

A plausible wrong answer. "All agentic, for flexibility." Flexibility costs latency on every simple question.

Follow-ups. How would you build the router?
