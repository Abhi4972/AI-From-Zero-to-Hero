In plain words first
The idea in one line

Moshi (Kyutai, 2024) is a single model that listens and speaks at the same time, with about 200 ms latency. Hibiki translates speech to speech as you talk. Both replace the ASR → LLM → TTS pipeline with one transformer over Mimi codec tokens. Hosted speech-to-speech APIs (OpenAI gpt-realtime, Gemini native audio) apply the single-model idea in production; most production voice agents still use pipelines.

The problem

In plain words first

The voice agents of Lessons 6.11 and 6.12 are pipelines: wait for the user to finish, transcribe, think, then speak. Each stage adds delay, and the agent cannot listen while it talks except through barge-in tricks. A full-duplex model removes the stages. Both people's audio is turned into codec tokens on a shared 80 ms clock (Mimi, Lesson 6.13), and one transformer reads the user's tokens and writes its own, every 80 ms, whether or not anyone is talking, so it can overlap, interrupt and say "mhm" like a person. Kyutai's Moshi is the open reference design; OpenAI's gpt-realtime and Google's Gemini native-audio models are the production speech-to-speech services. A 7B model cannot run on this page's two CPU cores, so the runs below build the exact token layout Moshi reads from real speech, and stream the Mimi codec frame by frame as a Moshi server does.

Every voice agent built from Lessons 11 + 12 has a fundamental latency floor around 300-500 ms: VAD fires, STT processes, LLM reasons, TTS generates. Each stage has its own minimum latency. You can tune and parallelize, but the pipeline shape caps you.

Moshi (Kyutai, 2024-2026) asks a different question: what if there is no pipeline? What if one model takes audio in and emits audio out directly, continuously, with text as an intermediate "inner monologue" instead of a required stage?

The answer is full-duplex speech-to-speech. Theoretical latency 160 ms (80 ms Mimi frame + 80 ms acoustic delay). Practical latency about 200 ms on a single L4 GPU (Kyutai's figure), below what a pipeline usually achieves (Lesson 6.12's worked budget was several hundred milliseconds before the first audio).

The idea

The same idea as a formula

One step of the clock. Moshi runs 12.5 steps per second, so a step is Δ=80 ms. At step t it has read the user's tokens u≤t​, its own audio tokens a<t​ and its text w<t​, and it factorises the next output as

p(wt​,at0:7​∣⋅)=p(wt​∣⋅)q=0∏7​p(atq​∣wt​,at<q​,⋅)

The temporal transformer computes the context once per step and predicts the text token wt​ first; the depth transformer then produces the product, one codebook at a time.

The acoustic delay. Codebooks q=1,…,7 are shifted by τ=1 step, so at step t the model writes the semantic token at0​ and the acoustic tokens at−11:7​. The latency floor is one frame plus the delay:

Δ+τΔ=80+80=160 ms

Tokens read. 17 streams at 12.5 steps per second is 17×12.5=212.5 tokens per second per conversation, whether anyone is talking or not.

Worked example
The budget of one full-duplex conversation

What one conversation costs, from the numbers in this lesson.

  • Temporal transformer: about 7 billion parameters, one forward pass per step. A forward pass costs about 2 FLOPs per parameter per token: 2×7×109×12.5≈175 GFLOP/s, continuously, even in silence.
  • Depth transformer: 8 short passes per step through 6 layers of width 1,024, roughly 12×6×10242≈75 million parameters per pass: 2×75×106×8×12.5≈15 GFLOP/s, under a tenth of the temporal transformer.
  • Memory traffic: serving one conversation, each step reads every weight once. In bf16, 7 billion parameters are 14 GB, so 12.5 steps per second need about 175 GB/s of memory bandwidth, more than half of the 300 GB/s NVIDIA lists for an L4. A server batches several conversations into one step, so the weights are read once for all of them.
  • Deadline: every step must finish within 80 ms, or the model falls behind real time and the user hears gaps.
Check your mental model
  • ✗ "Full-duplex means very fast turn-taking."
    ✓ There are no turns. Every 80 ms the model reads the user's tokens and writes its own, even while both are speaking; the run under Step 3 has 0.4 s of overlapping speech, which a turn-based pipeline cannot represent.
  • ✗ "The inner monologue is a transcript written after the speech."
    ✓ Within each step the text token comes first, before that frame's audio, so the words lead the sound. Most text steps are padding, because words arrive more slowly than frames.
  • ✗ "Streaming the codec frame by frame changes its tokens."
    ✓ Mimi is causal: encoding 80 ms at a time gave exactly the same tokens as encoding the whole utterance (the run under Step 2).
  • ✗ "Speech-to-speech models have replaced pipelines."
    ✓ Hosted speech-to-speech APIs are in production, but tool-heavy voice agents still mostly use pipelines, which can be swapped, logged and tested stage by stage.

Idea 1 · The Moshi architecture

Inputs. Two Mimi codec streams, both at 12.5 Hz × 8 codebooks:

  • Stream 1: user audio (Mimi-encoded, constantly arriving)
  • Stream 2: Moshi's own audio (generated by Moshi)

The transformer. A 7B-parameter Temporal Transformer processes both streams and a text "inner monologue" stream. At each 80 ms step, it:

  1. Consumes the latest user Mimi tokens (8 codebooks).
  2. Consumes the most recent Moshi Mimi tokens (8 codebooks, as produced).
  3. Generates the next Moshi text token (inner monologue).
  4. Generates the next Moshi Mimi tokens (8 codebooks via a small Depth Transformer).

All three streams — user audio, Moshi audio, Moshi text — run in parallel. Moshi can hear the user while speaking; can interrupt itself when the user interrupts; can back-channel ("mhm") without breaking its main utterance.

The depth transformer. Within a frame, the 8 codebooks are not predicted in parallel — they have inter-codebook dependencies. A small "depth transformer" (6 layers of width 1,024 in Kyutai's released configuration, against the temporal transformer's 32 layers of width 4,096) predicts them one after another within each 80 ms step. Sesame's CSM uses the same split: a large backbone for codebook 0, a small decoder for the rest.

Idea 2 · Why inner-monologue text helps

Without explicit text, the model has to implicitly model language in its acoustic stream. Moshi's insight: force it to emit text tokens alongside audio. The text stream is essentially the transcript of what Moshi is saying. This improves semantic coherence, makes it easier to swap out a language model head, and gives you transcripts for free.

Idea 3 · Hibiki: streaming speech-to-speech translation

Same architecture, trained on translation pairs. Source audio in, target-language audio out, continuously. Hibiki-Zero (Feb 2026) eliminates the need for word-level aligned training data — uses sentence-level data + GRPO reinforcement learning for latency optimization.

The paper covers five languages into English; the released 3B model translates French, Spanish, Portuguese and German into English (weights CC BY-NC-SA 4.0, non-commercial), and the authors adapt it to a new input language with under 1,000 hours of speech.

Idea 4 · The broader Kyutai stack (2026)

  • Moshi — full-duplex dialogue (French first, English well-supported)
  • Hibiki / Hibiki-Zero — simultaneous speech translation
  • Kyutai STT — streaming ASR (500 ms or 2.5 s look-ahead)
  • Kyutai Pocket TTS — 100M-param TTS runs on CPU (Jan 2026)
  • Unmute — full pipeline combining these on public servers

Kyutai reports that its STT server, used by Unmute, serves 64 simultaneous connections on one L40S GPU at 3× real time.

Idea 5 · Sesame CSM — the cousin

Sesame CSM (2025) uses a similar idea — a Llama-3 backbone with a Mimi codec head. But CSM is single-directional (takes context + text, produces speech) rather than full-duplex. It is a conversational TTS with strong "voice presence" (Sesame's term), not a full-duplex model.

Step 1 · the interface

Moshi exposes a WebSocket server that takes 80 ms chunks of Mimi-encoded audio and returns 80 ms chunks of Mimi-encoded audio. Both ways. Constantly.

# Moshi's reference server (python -m moshi.server, port 8998, GPU) speaks a tiny binary protocol over a WebSocket:
#   server -> client  b"\x00"           handshake: ready
#   both ways         b"\x01" + bytes   Opus-encoded audio (24 kHz); the SERVER runs Mimi and the LM
#   server -> client  b"\x02" + utf-8   a piece of Moshi's inner-monologue text
import asyncio, aiohttp, sphn

async def moshi_chat(mic_frames, play, url="ws://localhost:8998/api/chat"):
    opus_out, opus_in = sphn.OpusStreamWriter(24000), sphn.OpusStreamReader(24000)
    async with aiohttp.ClientSession() as session, session.ws_connect(url) as ws:
        assert (await ws.receive_bytes()) == b"\x00"
        async def send():                       # the microphone never stops, even while Moshi talks
            async for pcm in mic_frames():      # float32 PCM at 24 kHz, any chunk size
                data = opus_out.append_pcm(pcm)
                if data: await ws.send_bytes(b"\x01" + data)
        async def receive():
            async for msg in ws:
                kind, payload = msg.data[0], msg.data[1:]
                if kind == 1: play(opus_in.append_bytes(payload))
                elif kind == 2: print(payload.decode(), end="", flush=True)
        await asyncio.gather(send(), receive())

Step 2 · the full-duplex loop

# What the server does with each 80 ms of user audio (simplified from moshi/server.py):
#   codes  = mimi.encode(chunk_1920_samples)     # (1, 8, 1): user tokens for this step
#   tokens = lm_gen.step(codes)                  # temporal + depth transformer: 1 text + 8 audio tokens
#   pcm    = mimi.decode(tokens[:, 1:])          # Moshi's 80 ms of audio
#   send b"\x01" + opus(pcm) and, if the text token is a word piece, b"\x02" + text
# The reference server holds a lock: it serves ONE conversation at a time per process.

Both directions run simultaneously. Python asyncio or Rust futures are the standard transport.

Streaming the Mimi codec, as a Moshi server does

One LibriSpeech utterance, encoded by Mimi one 80 ms frame (1,920 samples) at a time with its streaming caches, compared with encoding the whole utterance at once, and timed on this page's two CPU cores.

import io, numpy as np, torch, librosa, soundfile as sf
from datasets import load_dataset, Audio
from transformers import MimiModel

libri = load_dataset("hf-internal-testing/librispeech_asr_dummy", "clean", split="validation").cast_column("audio", Audio(decode=False))
def clip(i):
    return sf.read(io.BytesIO(libri[i]["audio"]["bytes"]), dtype="float32")[0]
mimi = MimiModel.from_pretrained("kyutai/mimi").eval()
FPS, K = 12.5, 8
import time
# Stream Mimi the way a server does: one 80 ms frame (1,920 samples at 24 kHz) at a time, carrying state.
x24 = torch.tensor(librosa.resample(clip(5), orig_sr=16000, target_sr=24000))
x24 = x24[: len(x24) // 1920 * 1920]
with torch.no_grad():
    offline = mimi.encode(x24[None, None], num_quantizers=K).audio_codes[0]
    kv, pad_cache, frames, ms = None, None, [], []
    for k in range(0, len(x24), 1920):
        t0 = time.perf_counter()
        out = mimi.encode(x24[k: k + 1920][None, None], num_quantizers=K, encoder_past_key_values=kv,
                          padding_cache=pad_cache, use_streaming=True)
        kv, pad_cache = out.encoder_past_key_values, out.padding_cache
        ms.append((time.perf_counter() - t0) * 1000); frames.append(out.audio_codes[0])
    streamed = torch.cat(frames, -1)
    t0 = time.perf_counter(); mimi.decode(streamed[None]); dec_ms = (time.perf_counter() - t0) * 1000 / streamed.shape[-1]
n = min(streamed.shape[-1], offline.shape[-1])
print(f"{len(x24)/24000:.2f} s encoded frame by frame: {streamed.shape[-1]} frames (offline: {offline.shape[-1]})")
print(f"tokens identical to the offline encoding: codebook 0 {(streamed[0, :n] == offline[0, :n]).float().mean():.0%}, "
      f"all 8 codebooks {(streamed[:, :n] == offline[:, :n]).float().mean():.0%}")
print(f"CPU time per 80 ms frame: encode median {np.median(ms):.1f} ms (p95 {np.percentile(ms, 95):.1f}), "
      f"decode {dec_ms:.1f} ms  ->  the codec is {80 / (np.median(ms) + dec_ms):.1f}x faster than real time on 2 CPU cores")

Reading this output

Streaming with Mimi's caches gives exactly the same tokens as encoding the whole utterance at once (100% of all 8 codebooks), because Mimi is causal: each frame depends only on audio up to its end. Encoding one 80 ms frame takes about 24 ms on this page's two CPU cores and decoding about 7 ms per frame (timed on the whole utterance; the transformers decoder has no streaming cache, while Kyutai's moshi package streams both directions), so the codec alone runs about 2.6× faster than real time here. The expensive part of Moshi is the 7B transformer, about 175 GFLOP/s per conversation by the worked example above, which is why each conversation needs a GPU.

Step 3 · the training objective (conceptual)

For every 80 ms frame t:

  • Input: user_mimi[0..t], moshi_mimi[0..t-1], moshi_text[0..t-1]
  • Predict: moshi_text[t], then moshi_mimi[t, codebook_0..7]

Text is predicted before audio (inner monologue); audio is predicted codebook-sequential within the depth transformer.

The 17 streams, built from real speech

A "user" utterance and an "agent" reply that starts 0.4 s before the user finishes, both Mimi-encoded on one 12.5 Hz clock; the agent's words (timed by Whisper) tokenised with Moshi's own SentencePiece model as its inner monologue; acoustic codebooks delayed by one step, exactly as in Kyutai's configuration (delays = [0, 0, 1×7, 0, 1×7]).

import matplotlib.pyplot as plt
from huggingface_hub import hf_hub_download
import sentencepiece as spm
from transformers import pipeline

# A two-person exchange on one 12.5 Hz clock: the user speaks; the "agent" starts 0.4 s before the user stops.
user16, agent16 = clip(6), clip(3)
start = len(user16) / 16000 - 0.4
T = int(np.ceil((start + len(agent16) / 16000) * FPS)) + 2
def on_clock(x16, t0):
    x = np.zeros(int(T / FPS * 24000), np.float32)
    y = librosa.resample(x16, orig_sr=16000, target_sr=24000)
    x[int(t0 * 24000): int(t0 * 24000) + len(y)] = y[: len(x) - int(t0 * 24000)]
    return x
with torch.no_grad():
    user_codes = mimi.encode(torch.tensor(on_clock(user16, 0))[None, None], num_quantizers=K).audio_codes[0]
    agent_codes = mimi.encode(torch.tensor(on_clock(agent16, start))[None, None], num_quantizers=K).audio_codes[0]

# The agent's inner monologue: its words, tokenised with Moshi's own SentencePiece model, placed at the frame
# where each word starts (word times from Whisper); every other step is padding.
sp = spm.SentencePieceProcessor(model_file=hf_hub_download("kyutai/moshiko-pytorch-bf16", "tokenizer_spm_32k_3.model"))
asr = pipeline("automatic-speech-recognition", model="openai/whisper-base.en", model_kwargs={"attn_implementation": "eager"})
words = asr(agent16, return_timestamps="word")["chunks"]
PAD, EPAD = 3, 0
text = np.full(T, PAD); pos = 0
for w in words:
    f = max(int((start + w["timestamp"][0]) * FPS), pos)
    ids = sp.encode(w["text"].strip().lower())
    if f > 0 and text[f - 1] == PAD:
        text[f - 1] = EPAD                         # "a word starts next step"
    text[f: f + len(ids)] = ids[: T - f]; pos = f + len(ids)

# Moshi's 17 streams with its delays: text 0, semantic codebook 0, acoustic codebooks 1 step later.
delays = [0] + [0] + [1] * 7 + [0] + [1] * 7
streams = [text] + [agent_codes[k].numpy() for k in range(K)] + [user_codes[k].numpy() for k in range(K)]
grid = np.full((17, T + 1), -1)
for r, (s, d) in enumerate(zip(streams, delays)):
    grid[r, d: d + T] = s[:T]
print(f"{T} steps of 80 ms = {T / FPS:.1f} s;  per step the 7B model reads 17 tokens: 1 text + 8 agent + 8 user")
speaking = text[int(start * FPS): int((start + len(agent16) / 16000) * FPS)]
print(f"inner monologue: {len(words)} words -> {np.sum((text != PAD) & (text != EPAD))} text tokens; while the agent speaks "
      f"({len(speaking)} steps) {np.mean(speaking == PAD):.0%} of its text steps are PAD, {np.mean(speaking == EPAD):.0%} EPAD")
print("agent's words:", " ".join(w["text"].strip() for w in words)[:110], "...")
print("step | text token   | agent cb0 cb1 ... | user cb0 cb1 ...")
for t in [int(start * FPS) - 1, int(start * FPS), int(start * FPS) + 1, int(start * FPS) + 2]:
    tt = grid[0, t]; tok = {PAD: "PAD", EPAD: "EPAD"}.get(int(tt), sp.id_to_piece(int(tt)))
    print(f"{t:4d} | {tok:12s} | {grid[1, t]:5d} {grid[2, t]:5d} ...   | {grid[9, t]:5d} {grid[10, t]:5d} ...")

fig, ax = plt.subplots(figsize=(14, 4))
show = np.where(grid < 0, np.nan, grid % 2048).astype(float)
show[0] = np.where(grid[0] == PAD, np.nan, 1000.0)
ax.imshow(show, aspect="auto", cmap="viridis", interpolation="nearest")
ax.set_yticks(range(17)); ax.set_yticklabels(["text (inner monologue)"] + [f"agent cb{k}" for k in range(8)] + [f"user cb{k}" for k in range(8)], fontsize=7)
for sec in range(int(T / FPS) + 1):
    ax.axvline(sec * FPS, c="w", lw=0.3)
ax.axvline(start * FPS, c="r", lw=1.5, ls="--"); ax.text(start * FPS + 1, 0.3, "agent starts (0.4 s overlap)", color="r", fontsize=8)
ax.set_xlabel("step (80 ms each); white lines every second; blank = text PAD or the empty first slot of a delayed stream")
ax.set_title("What a Moshi-style model reads: 17 parallel token streams on a 12.5 Hz clock")
plt.tight_layout()

Step 4 · where Moshi wins and where it doesn't

Moshi wins:

  • Sub-250 ms end-to-end on cheap hardware.
  • Natural back-channels and interruptions.
  • No pipeline glue code.

Moshi does not win:

  • Tool calling (not trained for it; you need a separate LLM path).
  • Long reasoning (Moshi is an 8B-ish dialogue model, not Claude/GPT-4).
  • Factual accuracy on niche topics.
  • Most production enterprise use cases (still use pipelines in 2026).

Industry practice
What's current (2024–2026)
  • Hosted speech-to-speech is in production. OpenAI's gpt-realtime (GA August 2025: function calling, remote MCP servers, SIP phone calls, image input) and Google's Gemini 2.5 Flash Native Audio in the Live API (GA on Vertex AI, December 2025) are the speech-to-speech models most production teams use.
  • Pipelines remain the default for tool-heavy agents, because each stage can be swapped, logged and tested; frameworks such as LiveKit Agents and Pipecat support both pipelines and the hosted speech-to-speech APIs.
  • Open full-duplex models: Moshi (CC-BY 4.0, English) remains the open reference; Kyutai's delayed-streams STT and TTS and its Pocket TTS (100M parameters, runs on CPU) power its Unmute demo.
  • Streaming translation in products: Google Translate's live speech translation runs on Gemini's native-audio models.

Sources: Moshi, Moshi model card, Hibiki-Zero paper, Kyutai DSM, Pocket TTS, gpt-realtime, Gemini native audio, Sesame CSM.

Pitfalls

  • Limited tool calling. Moshi is a dialogue model, not an agent framework. Combine with pipeline for tools.
  • Specific-voice conditioning. Moshi uses a single trained persona; cloning is a separate training run.
  • Language coverage. French + English is excellent; others limited. Hibiki-Zero helps, but you still need training data.
  • Resource cost. A full Moshi session holds a GPU slot; not a cheap shared-tenant deploy pattern.
Recap
What to keep from this lesson
  • Full-duplex models read the user's codec tokens and write their own on a shared 80 ms clock, with no turn boundaries.
  • Per step: 17 streams (1 text + 8 own + 8 user); a big temporal transformer once, a small depth transformer per token.
  • The inner monologue (text first, mostly padding) carries the language; the acoustic delay lets the semantic token lead.
  • The codec is cheap enough to stream on a CPU; the 7B model needs a GPU per conversation.
  • In production, hosted speech-to-speech APIs or pipelines; open Moshi is the design to learn from.

Given the workload (latency target, tool-calling needs, language coverage, hardware budget, cloud vs edge), output:

1. Architecture. Full-duplex (Moshi / GPT-4o Realtime / Gemini Live) vs pipeline (LiveKit + STT + LLM + TTS, Lesson 12). One-sentence reason.
2. Model. Moshi · Hibiki · Hibiki-Zero · Sesame CSM · GPT-4o Realtime · Gemini 2.5 Live · traditional pipeline. Reason.
3. Scale. Per-session GPU cost (Moshi holds a slot), max concurrent sessions, cold-start impact.
4. Tool-calling path. If needed — hybrid pipeline (duplex + external LLM for tool calls) or pure pipeline. Explain trade-off.
5. Language coverage. Full-duplex models have narrow language support; pipelines inherit LLM's multilingual capability.

Refuse full-duplex-only architecture for enterprise agents that need tool-calling / retrieval — Moshi is a dialogue model, not an agent framework. Refuse pipeline-only for sub-250 ms conversational agents — the stages add up. Refuse Moshi for &gt; 4 concurrent sessions on one GPU — hits contention.

Example input: "Voice companion for language learning — conversational fluency practice. English + French. &lt; 250 ms responsiveness. 10k daily actives."

Example output:
- Architecture: full-duplex (Moshi). Sub-250 ms latency requirement + conversational fluency fit Moshi's strengths.
- Model: Moshi. EN + FR both well-supported. CC-BY 4.0 license.
- Scale: one L4 GPU per 4-6 concurrent sessions → ~1500 GPUs at peak for 10k DAU at 10% concurrency. Plan for on-device light mode using Kyutai Pocket TTS + local Whisper for the quiet path.
- Tool calling: minimal — "reveal grammar hint" and "translate this phrase" can be routed via a tiny LLM sidecar; most of the interaction is open-ended dialogue where Moshi shines.
- Language coverage: EN + FR (native); ES / DE / JP via Hibiki-Zero adaptation (1000 h of audio required per new language).

Solutions

SolutionP1 · Mostly padding

About half. While the agent speaks, 53% of its text steps are PAD and another 16% are EPAD markers, so roughly 70% of steps carry no word piece: 2–3 words per second, about 1.5 SentencePiece tokens per word, against 12.5 steps per second.

SolutionB1 · Semantic and acoustic at once

With no delay, at step t the depth transformer must produce codebook 1 and codebooks 2–8 of the same frame in one pass of 8 sequential predictions with no time to "see" the semantic decision reflected in the temporal context. With the one-step delay, the acoustic tokens of frame t−1 are produced after the temporal transformer has already read that frame's semantic token, so the coarse content is fixed first and the detail follows. Kyutai reports that the delay improves quality; the cost is the extra 80 ms in the 160 ms latency floor.
