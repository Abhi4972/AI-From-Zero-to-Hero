Why this came about

MCP started with local servers run as subprocesses. Remote, shared servers needed network transport and proper authentication, so the specification added Streamable HTTP and OAuth-based authorization during 2025.

In plain words first
How the plug connects, and who is allowed in

An MCP client and server can talk through a local subprocess (stdio) or over the network (Streamable HTTP). Remote servers need authentication: MCP uses OAuth, so a user grants an application limited access to a server, the way you let an app read your calendar, with tokens scoped to that server. The agent then loads the server's tools and uses them like any other tool.

How this connects

Step 2 · Serve it over HTTP, with authentication

A remote MCP server is an OAuth 2.1 resource server: it accepts access tokens issued by your identity provider for this server and checks their audience and scopes. FastMCP verifies JWTs directly:

import threading, time
import uvicorn
from fastmcp.exceptions import ToolError
from fastmcp.server.auth.providers.jwt import JWTVerifier, RSAKeyPair

keys = RSAKeyPair.generate()                               # lab only; in production use your IdP's JWKS URL
auth = JWTVerifier(public_key=keys.public_key, issuer="https://login.shopkart.example",
                   audience="shopkart-orders-mcp",         # tokens minted for a different server are rejected
                   required_scopes=["orders:read"])
secure = FastMCP("shopkart-orders", auth=auth, mask_error_details=True)   # hide internal error details

@secure.tool
def get_order_status(order_id: str) -> dict:
    """Return the shipping status for an order ID like 'A-1001'."""
    if not order_id.startswith("A-"):
        raise ToolError("Order IDs look like A-1001.")     # ToolError messages are shown even when masking
    return {"order_id": order_id, "status": "shipped"}

threading.Thread(target=uvicorn.run, args=(secure.http_app(),),
                 kwargs={"port": 8765, "log_level": "warning"}, daemon=True).start()
time.sleep(1.5)                                            # give the server a moment to start

async def call_it():
    token = keys.create_token(subject="support-agent-7", issuer="https://login.shopkart.example",
                              audience="shopkart-orders-mcp", scopes=["orders:read"])
    async with Client("http://127.0.0.1:8765/mcp", auth=token) as c:
        print((await c.call_tool("get_order_status", {"order_id": "A-1001"})).structured_content)
        try:
            await c.call_tool("get_order_status", {"order_id": "1001"})
        except Exception as e:
            print("tool error:", e)
    try:
        async with Client("http://127.0.0.1:8765/mcp") as c:      # no token at all
            await c.list_tools()
    except Exception as e:
        print("no token:", type(e).__name__)

asyncio.run(call_it())

The full MCP authorization model, for when a host must obtain the token itself:

  1. The client calls the server and gets 401 with a pointer to the server's Protected Resource Metadata (RFC 9728), which names the authorization server.
  2. The client registers (Client ID Metadata Documents or Dynamic Client Registration) and runs OAuth 2.1 with PKCE, requesting a token for this server using a resource indicator (RFC 8707), so the token's audience is this server only.
  3. The server validates issuer, audience, expiry and scopes on every request. Insufficient scope triggers step-up authorization for more.
  4. No token passthrough: a server must never forward the client's token to a downstream API. It gets its own token for that API (for example via token exchange). Passing tokens through breaks audit trails and creates a confused deputy.
In production
Authorization mistakes seen with remote MCP servers

Shared service tokens that give every user the server's full access; tokens without an audience check, accepted by any server in the company; long-lived tokens pasted into desktop configs; and servers that pass the user's token straight to downstream APIs. Each turns one leaked token or one injected instruction into broad access. Audience-bound, short-lived, per-user tokens and server-side scope checks (this step) close all four.

A complete, offline run: an Agents SDK agent, the mock model from Lesson 14.92, and an MCP server over HTTP.

from mockllm import start
from openai import AsyncOpenAI
from agents import Agent, Runner, OpenAIChatCompletionsModel, set_tracing_disabled
from agents.mcp import MCPServerStreamableHttp

orders_server = FastMCP("shopkart-orders-open")

@orders_server.tool(annotations={"readOnlyHint": True})
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is shipped"

threading.Thread(target=uvicorn.run, args=(orders_server.http_app(),),
                 kwargs={"port": 8767, "log_level": "warning"}, daemon=True).start()
time.sleep(1.5)

set_tracing_disabled(True)
model = OpenAIChatCompletionsModel(model="mock-model", openai_client=AsyncOpenAI(base_url=start(), api_key="mock"))

async def agent_with_mcp():
    async with MCPServerStreamableHttp(params={"url": "http://127.0.0.1:8767/mcp"}, name="orders",
                                       require_approval="never") as server:   # or "always" / per-tool rules
        agent = Agent(name="support", instructions="Help with orders.", model=model, mcp_servers=[server])
        print((await Runner.run(agent, "Where is A-1001?")).final_output)

asyncio.run(agent_with_mcp())
What you should see
Here is what I found: A-1001 is shipped

The agent discovered get_order_status from the server at run time; nothing about the tool was written in the agent's code.

Step 4 · The 2026-07-28 specification: MCP goes stateless

MCP versions are dates. The previous stable revision was 2025-11-25; the current one is 2026-07-28, the biggest change since launch:

Change What it means for you
Stateless core No initialize handshake and no Mcp-Session-Id. Any request can go to any server instance behind a plain load balancer. State lives in explicit handles the tool returns (for example a cart_id the model passes back).
Routing headers (Mcp-Method, Mcp-Name) Gateways and firewalls can route and apply policy without parsing the JSON body
Multi round-trip requests Elicitation returns an "input required" result with a state token; the client asks the user and calls again, possibly reaching a different server
Tasks (official extension) Long-running tool calls return a task handle; clients poll, update or cancel
MCP Apps (extension) Tools can return interactive UI rendered in sandboxedlater · 15.25 iframes
Caching hints, W3C trace context in _meta Responses carry cache lifetimes; traces connect across client, gateway and server
Deprecations Sampling, roots and protocol logging (12-month window)
Authorization hardening Issuer validation (RFC 9207), credentials bound to their authorization server, clearer discovery

The official Python SDK 2.x supports the new revision alongside older ones. Check which revisions your hosts and gateways support before switching servers to stateless-only behavior.

Here is the multi round-trip pattern in code. On the first call the tool has no answer yet, so it returns an InputRequiredResult instead of a result: the questions it needs answered, plus a small request_state to carry across rounds. The client asks the user, then calls the tool again with the answers attached. Nothing is held open on the server between the two calls, which is what lets the second call land on a different instance:

from fastmcp import Context
from fastmcp.client.elicitation import ElicitResult
from mcp import types as mt

confirm_server = FastMCP("shopkart-cancellations")

@confirm_server.tool(annotations={"destructiveHint": True})
async def cancel_order_confirmed(order_id: str, ctx: Context):
    """Cancel an order, after the user confirms."""
    answers = ctx.input_responses                    # None on the first round
    if not answers:
        return mt.InputRequiredResult(
            input_requests={"confirm": mt.ElicitRequest(params=mt.ElicitRequestFormParams(
                message=f"Really cancel {order_id}? This cannot be undone.",
                requested_schema={"type": "object", "properties": {"ok": {"type": "boolean"}},
                                  "required": ["ok"]}))},
            request_state=order_id)                  # sealed on the wire; tampering is rejected
    reply = answers["confirm"]
    if reply.action == "accept" and reply.content.get("ok"):
        return f"{ctx.request_state} cancelled"
    return f"{ctx.request_state} left unchanged ({reply.action})"

async def user_says_yes(message, response_type, params, context):
    print("host shows:", message)                    # a real host renders a dialog here
    return {"ok": True}

async def user_says_no(message, response_type, params, context):
    return ElicitResult(action="decline")

async def confirm_flow():
    for handler in (user_says_yes, user_says_no):
        async with Client(confirm_server, elicitation_handler=handler) as c:
            r = await c.call_tool("cancel_order_confirmed", {"order_id": "A-1002"})
            print(r.content[0].text)

asyncio.run(confirm_flow())
What you should see
host shows: Really cancel A-1002? This cannot be undone.
A-1002 cancelled
A-1002 left unchanged (decline)

The FastMCP client ran both rounds for you: it saw the InputRequiredResult, called your elicitation_handler, and retried with the answer. On a 2026-07-28 connection the older style, await ctx.elicit(...) in the middle of a tool, fails with "elicitation via server-initiated requests is unavailable", because there is no longer a back channel for the server to push a request on. Write new confirmation flows in the guard style above.

In production
Moving to the stateless specification

Servers that kept per-session state in memory (open carts, pagination cursors, half-finished elicitation) break when requests can land on any instance. Move that state into explicit handles the tool returns and a shared store, keep supporting older clients during the transition, and test behind a load balancer with several instances before switching.

Check your mental model
  • ✗ "stdio and HTTP servers behave differently for the model."
    ✓ The model sees the same tool definitions either way; only the connection differs.
  • ✗ "One token for all servers is fine."
    ✓ Tokens should be scoped to one server and audience, so a leak cannot be replayed elsewhere.
  • ✗ "Connecting a server means trusting all its tools."
    ✓ Load only the tools you need and gate risky ones with approval.

Make it your own

Solutions

SolutionP1 · Local against remote

Stdio runs as a local process for one host, with the user's local rights. Streamable HTTP serves many clients over the network and needs authentication (OAuth 2.1 in the specification) and per-user authorization.

SolutionB1 · Internal is not private

Anything on the network, including a compromised machine or another agent fed malicious content, can call the tools with the server's rights. Require authentication, scope tokens per user and tool, and log calls.

SolutionD1 · State belongs to the client or the backend

A stateless server does not keep session state between requests, so state stored there is lost or lands on another instance. Move the state into the request (IDs the client sends), or into a backing store keyed by user or task.

SolutionM1 · One server, many hosts

Both should present the same name, description and schema; differences in prefixes (such as mcp__server__tool) and in how results are wrapped are host choices. Test your tools in each host your users will use.

Check your understanding

Explain the mechanismHow does authentication work for remote MCP servers?

Worked answer. The server acts as an OAuth resource server: clients obtain tokens from an authorization server, and the server validates them and maps them to a user with scopes. The server then calls downstream systems as that user or with delegated rights, never with one shared super-user. Tokens should be audience-bound to the server.

A plausible wrong answer. "Use an API key in the config file." Shared keys cannot express per-user rights or be revoked per user.

Follow-ups. What is token passthrough, and why avoid it?

Debug a failureAn agent connected to a remote MCP server is slow on every call. Where do you look?

Worked answer. Connection setup per call, network distance, the server's downstream latency, and large tool lists or results. Measure each part; keep connections or sessions warm where allowed, cache tool lists, and return smaller results.

A plausible wrong answer. "MCP is slow." The protocol overhead is small; the deployment usually is not.

Follow-ups. How would you trace a call across host, server and backend?

Defend a designRun MCP servers centrally or let teams run their own?

Worked answer. A central gateway or registry for discovery, authentication, policy and logging, with servers owned by the teams that own the systems behind them. Fully central means a bottleneck; fully decentralized means unknown servers with unknown rights.

A plausible wrong answer. "Let anyone connect any server." That is how unvetted tools reach agents with real data.

Follow-ups. What would a server registry record?

Q1Why must an MCP server never pass the user's access token to a downstream API?
