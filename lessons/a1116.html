In plain words first
The idea in one line

A ReAct loop written by hand is a while True. The same loop written as an explicit graph is something you can checkpoint, interrupt, branch, and time-travel through. The agent hasn't changed. The harness around it has.

Terms you'll hear
Term What people say What it actually means
StateGraph "The LangGraph graph" The builder object you add nodes and edges to before compile.
Reducer "How the field merges" A function (old, new) -> merged applied when a node returns an update for that field; default is overwrite, add_messages appends.
Thread "A conversation ID" A thread_id string that scopes all checkpoints for one session.
Checkpoint "A paused state" A persisted snapshot of the full graph state after a node transition, keyed on (thread_id, checkpoint_id).
Interrupt "Pause for a human" interrupt() inside a node pauses and saves the state; resume with Command(resume=value). Static interrupt_before / interrupt_after breakpoints are for debugging and resume with invoke(None, config).
Time-travel "Fork from a prior step" graph.invoke(None, config_with_old_checkpoint_id) replays from that checkpoint forward.
Send "Parallel subgraph dispatch" A constructor a node can return to spawn N parallel executions of a target node.
Subgraph "A compiled graph as a node" A compiled StateGraph used as a node in another graph; preserves its own state scope.

The problem

In plain words first

An agent is a loop: the model reads the conversation, maybe asks for a tool, the tool runs, its result is added, and the model reads again. Written as a bare while True: loop, it cannot be paused for a person to approve a risky step, resumed after a crash, or rewound to try a different choice. Writing the same loop as an explicit graph fixes that: each step is a node, the arrows between steps are edges, and everything the agent knows lives in one state object that the runtime saves after every step (a checkpoint). LangGraph is the best-known library for this. This lesson builds the four-node agent graph, then runs a real one: a small local model handles a refund ticket, a human reviewer stops a wrong refund, the thread is rewound and replayed, and three short demos show the mistakes that silently lose data or repeat side effects. No model is trained.

You ship a function-calling agent. It works for three turns, then something goes wrong: the model tries a tool that returns 500, the user changes their mind mid-task, or the agent decides to refund an order without a human signing off. The while True: loop has no hooks. You can't pause it, you can't rewind it, and you can't branch off into "what if the model had picked the other tool." The moment you ship this past a demo, the agent becomes a black box that either worked or didn't.

The next step is obvious once you see it. The agent is already a state machine — system prompt plus message history plus pending tool calls plus the next action. Make the state machine explicit: nodes for "the model thinks," "a tool runs," "a human approves," and edges for the conditional transitions between them. Once the graph is explicit, the harness gets four things for free: checkpointing (save state between steps), interrupts (pause for a human), streaming (stream tokens and intermediate events), and time-travel (rewind to a prior state and try a different branch).

The reference implementation of this abstraction is LangGraph. It is not an agent framework in the LangChain sense ("here is an AgentExecutor, good luck"). It is a graph runtime with first-class state, first-class persistence, and first-class interrupts. The agent loop is something you draw, not something you hand-write.

The idea

A StateGraph has three things.

  1. State. A typed dict (TypedDict or Pydantic model) that flows through the graph. Every node receives the full state and returns a partial update, which LangGraph merges using a reducer per field — operator.add for lists that should accumulate, overwrite by default.
  2. Nodes. Python functions state -> partial_state. Each is a discrete step: "call the model," "run tools," "summarize."
  3. Edges. Transitions between nodes. Static edges go one place. Conditional edges take a router function state -> next_node_name so the graph can branch on model output.

You compile the graph. Compile binds the topology, attaches a checkpointer (optional but essential for production), and returns a runnable. You invoke it with an initial state and a thread_id. Every step of execution persists a checkpoint keyed on (thread_id, checkpoint_id).

Idea 1 · The four superpowers

Checkpointing. Every node transition writes the new state to a store (in-memory for tests, Postgres/Redis/SQLite for prod). Resume by calling the graph again with the same thread_id. The graph picks up where it paused.

Interrupts. Call interrupt(payload) inside a node and execution stops there. The checkpointer saves the state and the payload goes back to the caller, so your API can respond "awaiting approval." A later request to the same thread_id with Command(resume=value) resumes the run, and interrupt() returns value. Static breakpoints (interrupt_before=[...] or interrupt_after=[...] at compile time) still exist, but the LangGraph docs recommend them for debugging, not for human approval; they resume with invoke(None, config).

Streaming. graph.stream(state, mode="updates") yields state deltas as they happen. mode="messages" streams the LLM tokens inside model nodes. mode="values" yields full snapshots. You pick what to surface in your UI.

Time-travel. graph.get_state_history(thread_id) returns the full checkpoint log. Pass any prior checkpoint_id to graph.invoke and you fork from that point. Great for debugging ("what if the model had picked tool B instead?") and for regression tests that replay production traces.

Idea 2 · Reducers are the point

Every state field has a reducer. Most defaults are fine — a new value overwrites the old. But message lists need operator.add so new messages append instead of replacing. Parallel edges merge their updates through the reducer. If two nodes both update messages and you forgot the Annotated[list, add_messages], the second wins silently and you lose half the turn. The reducer is the only subtle thing in the library; get it right and the rest composes.

Idea 3 · The ReAct graph in four nodes

A production ReAct agent is four nodes and two edges:

  1. agent — calls the LLM with the current message history. Returns the assistant message (which may contain tool_calls).
  2. tools — executes any tool_calls in the last assistant message, appends the tool results as tool messages.
  3. A conditional edge from agent that routes to tools if the last message has tool_calls, else to END.
  4. A static edge from tools back to agent.

That is it. You get the full ReAct loop (Thought → Action → Observation → Thought → …) with checkpointing, interrupts, and streaming, in roughly 40 lines of code.

Idea 4 · StateGraph vs Send (fanout)

Send(node_name, state) lets a node dispatch parallel subgraphs. Example: the agent decides to query three retrievers at once. Each Send spawns a parallel execution of the target node; their outputs merge through the state reducer. This is how LangGraph expresses the orchestrator-workers pattern without threading primitives.

Idea 5 · Subgraphs

A compiled graph can be a node in another graph. The outer graph sees a single node; the inner graph has its own state and its own checkpoints. This is how teams build supervisor-worker agents: the supervisor graph routes user intent to a per-domain worker subgraph.

The same idea as a formula

A step. A node n reads the state s and returns a partial update u=fn​(s). Each key k of the state merges through its reducer ⊕k​:

s′[k]=s[k]⊕k​u[k],a⊕default​b=b,a⊕add​b=a+b  (list concatenation).
add_messages is concatenation that also replaces a message whose id is already present.

Parallel branches. When branches 1,…,m finish in the same step, s′[k]=s[k]⊕k​u1​[k]⊕k​⋯⊕k​um​[k]. With the default (overwrite) there is no single answer for m>1, so LangGraph raises an error instead of guessing.

Routing and checkpoints. A conditional edge is a function r(s)∈{nodes}∪{END}. The runtime saves a checkpoint ct​ after every step, so a thread is a sequence c−1​,c0​,c1​,…; replaying from cj​ adds a new branch cj​→cj+1′​→… and keeps the old one.

Worked example
One refund ticket, step by step

The run below produces these checkpoints (messages only; H = human, A = assistant, T = tool result): - c−1​: empty, next __start__. c0​: [H], next agent. - c1​: [H, A: issue_refund(A-1042, 50)], next approve: the graph is paused inside approve. - c2​: [H, A, T: "Rejected by a human reviewer…"], next agent. c3​: [H, A, T, A: a text reply], next nothing: done. - With overwrite instead of add_messages, c3​ would hold only the last assistant message; the model would not see the question on the next turn. - Each step adds one checkpoint, so four steps plus the input give 5 snapshots; a replay from c0​ that runs four more steps adds more and keeps the first five.

Check your mental model
  • ✗ "A graph makes the agent smarter."
    ✓ The model and prompts are unchanged; the graph adds pause, resume, replay and inspection around them.
  • ✗ "After interrupt() resumes, the node continues from the next line."
    ✓ The node runs again from its first line, and interrupt() returns the resume value this time.
  • ✗ "Replaying from an old checkpoint rewrites history."
    ✓ It adds a new branch; the old checkpoints stay on the thread.

Step 1 · state and nodes

from typing import Annotated, TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, AIMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import InMemorySaver

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]

def agent_node(state: State) -> dict:
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

def should_continue(state: State) -> str:
    last = state["messages"][-1]
    return "tools" if getattr(last, "tool_calls", None) else END

tool_node = ToolNode(tools=[search_web, read_file])

graph = StateGraph(State)
graph.add_node("agent", agent_node)
graph.add_node("tools", tool_node)
graph.add_edge(START, "agent")
graph.add_conditional_edges("agent", should_continue, {"tools": "tools", END: END})
graph.add_edge("tools", "agent")

app = graph.compile(checkpointer=InMemorySaver())

add_messages is the reducer that makes the message list accumulate instead of overwrite. Forgetting it is the most common LangGraph bug.

Step 2 · run with a thread

config = {"configurable": {"thread_id": "user-42"}}
for event in app.stream(
    {"messages": [HumanMessage("find the Anthropic headquarters address")]},
    config,
    stream_mode="updates",
):
    print(event)

Every update is a dict {node_name: state_delta}. Your frontend can stream these to the UI so users see "agent is thinking… calling search_web… got result… answering."

Step 3 · add a human-in-the-loop interrupt

Put an approval node on the edge into the side-effecting tools and call interrupt() inside it.

from langchain_core.messages import ToolMessage
from langgraph.types import interrupt, Command

def approve(state: State) -> Command:
    calls = state["messages"][-1].tool_calls
    decision = interrupt({"needs_approval": calls})      # pauses here; the state is checkpointed
    if decision == "approve":
        return Command(goto="tools")
    return Command(goto="agent", update={"messages": [
        ToolMessage("Rejected by a human reviewer.", tool_call_id=c["id"]) for c in calls]})

graph.add_node("approve", approve, destinations=("tools", "agent"))
# the router sends side-effecting tool calls to "approve" instead of straight to "tools"
app = graph.compile(checkpointer=InMemorySaver())

state = app.invoke({"messages": [HumanMessage("delete the production database")]}, config)
# state["__interrupt__"] holds the payload: show it to a human, then, in a later request:
app.invoke(Command(resume="approve"), config)          # or Command(resume="reject")

The state, the checkpoint, and the thread all persist across the interrupt. Nothing is in memory except during execution.

Step 4 · time-travel for debugging

history = list(app.get_state_history(config))
for snapshot in history:
    print(snapshot.values["messages"][-1].content[:80], snapshot.config)

# Fork from a prior checkpoint
target = history[3].config  # three steps back
for event in app.stream(None, target, stream_mode="values"):
    pass  # replay from that point forward

Passing None as the input replays from the given checkpoint; passing a value appends it as an update to that checkpoint's state before resuming. This is how you reproduce a bad agent run without re-running the whole conversation.

A real LangGraph agent with an approval gate

LangGraph 1.2 with InMemorySaver. The agent node is Qwen2.5-0.5B-Instruct on CPU with its native tool calling; tools are lookup_order and issue_refund. Refunds go through an approve node that calls interrupt(). The reviewer approves only a refund equal to the amount paid. After the main run, the thread is replayed from step 0 and the refund approved. About two minutes on CPU, so the output below was recorded.

import json, operator, re, time, torch
from typing import Annotated, TypedDict
from transformers import AutoTokenizer, AutoModelForCausalLM
from langchain_core.messages import AIMessage, HumanMessage, ToolMessage, AnyMessage
from langchain_core.tools import tool
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

name = "Qwen/Qwen2.5-0.5B-Instruct"                    # a real (small) model drives the agent node
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

ORDERS = {"A-1042": {"item": "ceramic lamp", "paid": 89.0, "status": "delivered, reported broken"}}
REFUNDS = []                                          # the side effect we want a human to approve

@tool
def lookup_order(order_id: str) -> str:
    """Look up an order by its ID, e.g. "A-1042"."""
    return json.dumps(ORDERS.get(order_id, {"error": "ORDER_NOT_FOUND"}))

@tool
def issue_refund(order_id: str, amount: float) -> str:
    """Refund an amount of money for an order. This moves real money."""
    REFUNDS.append((order_id, amount))
    return json.dumps({"refunded": amount, "order_id": order_id})

TOOLS = [lookup_order, issue_refund]
SCHEMAS = [{"type": "function", "function": {"name": t.name, "description": t.description,
            "parameters": t.args_schema.model_json_schema()}} for t in TOOLS]

class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]   # reducer: append, never overwrite

def to_chat(msgs):                                    # LangChain messages -> Qwen chat-template messages
    out = [{"role": "system", "content": ("You are a support agent with tools. Always call lookup_order first for any order ID the user gives, "
                                     "then call issue_refund for the amount paid if the item is broken.")}]
    for m in msgs:
        if isinstance(m, HumanMessage): out.append({"role": "user", "content": m.content})
        elif isinstance(m, ToolMessage): out.append({"role": "tool", "name": m.name, "content": m.content})
        else: out.append({"role": "assistant", "content": m.content, "tool_calls":
                          [{"type": "function", "function": {"name": c["name"], "arguments": c["args"]}} for c in m.tool_calls] or None})
    return out

def agent(state: State):
    text = tok.apply_chat_template(to_chat(state["messages"]), tools=SCHEMAS, tokenize=False, add_generation_prompt=True)
    ids = tok(text, return_tensors="pt").input_ids
    with torch.no_grad():
        g = model.generate(ids, max_new_tokens=80, do_sample=False)
    reply = tok.decode(g[0, ids.shape[1]:], skip_special_tokens=True)
    calls = [json.loads(c) for c in re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", reply, re.S)]
    n = len(state["messages"])
    return {"messages": [AIMessage(content="" if calls else reply.strip(),
            tool_calls=[{"name": c["name"], "args": c["arguments"], "id": f"call_{n}_{i}"} for i, c in enumerate(calls)])]}

def route(state: State):
    last = state["messages"][-1]
    if not last.tool_calls: return END
    return "approve" if any(c["name"] == "issue_refund" for c in last.tool_calls) else "tools"

def approve(state: State):
    calls = state["messages"][-1].tool_calls
    decision = interrupt({"needs_approval": [f'{c["name"]}({c["args"]})' for c in calls]})   # pause here, state saved
    if decision == "approve":
        return Command(goto="tools")
    return Command(goto="agent", update={"messages": [ToolMessage(f"Rejected by a human reviewer: {decision}",
                                                                   tool_call_id=c["id"], name=c["name"]) for c in calls]})

g = StateGraph(State)
g.add_node("agent", agent); g.add_node("tools", ToolNode(TOOLS)); g.add_node("approve", approve, destinations=("tools", "agent"))
g.add_edge(START, "agent")
g.add_conditional_edges("agent", route, ["tools", "approve", END])
g.add_edge("tools", "agent")
app = g.compile(checkpointer=InMemorySaver())

def show(stream):
    for ev in stream:
        for node, upd in ev.items():
            if node == "__interrupt__":
                print(f"  [paused]   waiting for a human: {upd[0].value['needs_approval']}"); continue
            for m in (upd or {}).get("messages", []):
                what = " ".join(f'{c["name"]}({json.dumps(c["args"])})' for c in m.tool_calls) if getattr(m, "tool_calls", None) else m.content[:110]
                print(f"  [{node:<7}] {type(m).__name__:<11} {what}")

cfg = {"configurable": {"thread_id": "ticket-7"}}
t = time.time()
print("run 1: the user asks for a refund")
show(app.stream({"messages": [HumanMessage("Order A-1042 arrived broken. Please refund it.")]}, cfg, stream_mode="updates"))
snap = app.get_state(cfg)
print(f"  graph stopped before {snap.next}; refunds issued so far: {REFUNDS}")

def reviewer(proposal):                                # the human: approve only a refund of the amount actually paid
    order, amount = proposal["order_id"], proposal["amount"]
    paid = ORDERS.get(order, {}).get("paid")
    return "approve" if amount == paid else f"the order was paid {paid}, not {amount}; look it up and refund the amount paid."

run = 2
while app.get_state(cfg).next and run <= 4:
    proposal = app.get_state(cfg).values["messages"][-1].tool_calls[0]["args"]
    decision = reviewer(proposal)
    print(f"\nrun {run}: the reviewer answers {decision!r} (same thread_id, a new request)")
    show(app.stream(Command(resume=decision), cfg, stream_mode="updates")); run += 1
print(f"  refunds issued: {REFUNDS}")

history = list(app.get_state_history(cfg))                 # newest first
print(f"\ncheckpoint history for thread 'ticket-7': {len(history)} snapshots")
for s in reversed(history):
    last = s.values["messages"][-1] if s.values.get("messages") else None
    print(f"  step {s.metadata['step']:>2}  next={str(s.next):<14} last message: {type(last).__name__ if last else '-'}")

before = next(s for s in history if s.metadata["step"] == 0)       # the checkpoint just before the agent first ran
print("\ntime travel: replay from step 0 (the agent runs again) and approve the $50 refund this time")
REFUNDS.clear()
show(app.stream(None, before.config, stream_mode="updates"))       # None = continue from that checkpoint
show(app.stream(Command(resume="approve"), cfg, stream_mode="updates"))
print(f"  refunds issued on the fork: {REFUNDS}")
print(f"\n({time.time() - t:.0f} s, {sum(1 for s in app.get_state_history(cfg))} checkpoints now on the thread, both branches kept)")

Reading this output

The model skipped its instructions. The system prompt says to call lookup_order first. The 0.5B model went straight to issue_refund with an amount it made up: 50, for a lamp that cost 89. Small models do this often, and large ones sometimes. The graph does not make the model better, but it decides what happens next.

The gate caught it. The router sent the refund call to approve, and interrupt() stopped the run there. get_state reports next=('approve',), and no money has moved. Run 1 ended. In a real service this is where the API answers "awaiting approval" and the process can even exit, because the state lives in the checkpointer.

The resume is a new request. Run 2 passes Command(resume=...) on the same thread_id. The approve node starts again from its first line, and this time interrupt() returns the reviewer's answer: a rejection with the correct amount. The rejection goes back to the model as a tool result. The model did not use the correction; it asked for the order ID it had been given at the start. Recovering from feedback is a model skill, and this one lacks it. The safety came from the gate, not from the model.

Five checkpoints for four steps. Step −1 is the input, then one checkpoint after each step: start, agent (paused at approve), approve, agent. Each holds the full message list, because add_messages appended at every step.

Time travel shows the counterfactual. Replaying from step 0 runs the agent again. Greedy decoding gives the same wrong proposal. This time it is approved, and the $50 refund goes through on the fork. The thread now holds 10 checkpoints and both branches. This is how you reproduce an incident: replay the exact state, change one decision, and see what would have happened.

Three mistakes the graph will not catch for you

Three tiny graphs, no model: a list field with and without a reducer, three parallel Send branches writing the same field, and a side effect placed before interrupt(). Instant.

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send, interrupt, Command
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.errors import InvalidUpdateError

# 1) A list field without a reducer: each update replaces the list
def two_steps(reducer):
    class S(TypedDict):
        log: Annotated[list, operator.add] if reducer else list
    g = StateGraph(S)
    g.add_node("plan", lambda s: {"log": ["plan written"]})
    g.add_node("act", lambda s: {"log": ["tool ran"]})
    g.add_edge(START, "plan"); g.add_edge("plan", "act"); g.add_edge("act", END)
    return g.compile().invoke({"log": ["user asked"]})["log"]
print("1. sequential updates to a list field")
print("   no reducer:         ", two_steps(False))
print("   operator.add reducer:", two_steps(True))

# 2) Fan-out with Send: three retrievers write the same field in one step
def fan_out(reducer):
    class S(TypedDict):
        query: str
        docs: Annotated[list, operator.add] if reducer else list
    g = StateGraph(S)
    g.add_node("retrieve", lambda s: {"docs": [f"{s['source']}: hit for {s['query']!r}"]})
    g.add_conditional_edges(START, lambda s: [Send("retrieve", {"query": s["query"], "source": src})
                                              for src in ("wiki", "tickets", "code")], ["retrieve"])
    g.add_edge("retrieve", END)
    try:
        return g.compile().invoke({"query": "refund policy", "docs": []})["docs"]
    except InvalidUpdateError as e:
        return f"InvalidUpdateError: {str(e).splitlines()[0][:90]}"
print("\n2. three parallel branches update the same field")
print("   no reducer:         ", fan_out(False))
print("   operator.add reducer:", fan_out(True))

# 3) On resume a node restarts from its first line: code before interrupt() runs twice
calls = []
class T(TypedDict):
    answer: str
def risky(s):
    calls.append("charged card")                    # a side effect placed BEFORE the interrupt
    ok = interrupt("approve the charge?")
    return {"answer": "done" if ok else "cancelled"}
g = StateGraph(T); g.add_node("risky", risky); g.add_edge(START, "risky"); g.add_edge("risky", END)
app = g.compile(checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "t1"}}
app.invoke({"answer": ""}, cfg)
print("\n3. side effect placed before interrupt()")
print("   after the pause: ", calls)
app.invoke(Command(resume=True), cfg)
print("   after the resume:", calls, " <- the card was charged twice")

Reading this output

1. No reducer, lost history. Without a reducer, each node's {"log": [...]} replaces the field. Two steps later only ['tool ran'] is left: the user's request and the plan are gone, and nothing raised an error. With operator.add, all three entries survive. For messages, add_messages does the same and also lets a message with an existing id replace the old one.

2. Parallel writes without a reducer fail loudly. Three Send branches all write docs in the same step. With overwrite there is no correct winner, so LangGraph raises InvalidUpdateError and tells you to use an Annotated key. With operator.add, the three results are concatenated. A loud error here is the friendly case. The silent loss in demo 1 is the dangerous one.

3. The node restarts on resume. The "charge" ran once when the node first started and paused, and again when the node restarted on resume. One approval, two charges. Anything with an effect outside the graph goes after interrupt(), in a later node, or behind an idempotency key.

Step 5 · swap the checkpointer for production

from langgraph.checkpoint.postgres import PostgresSaver

with PostgresSaver.from_conn_string("postgresql://...") as checkpointer:
    checkpointer.setup()
    app = graph.compile(checkpointer=checkpointer)

InMemorySaver is for tests. The SQLite and Postgres savers ship as separate packages (langgraph-checkpoint-sqlite, langgraph-checkpoint-postgres); Redis and other stores have their own packages. Anything that persists across restarts wants a real store.

Break it on purpose

In the approve node, send the refund yourself on the line above interrupt() (for example to log it early), so the money moves before the reviewer answers. What happens when the reviewer approves? (Solution B1.)

Recap
What to keep from this lesson
  • An agent graph: state, nodes that return partial updates, edges and routers.
  • Every list field that should grow needs a reducer (add_messages, operator.add).
  • A checkpointer saves state after each step; a thread_id names the conversation.
  • interrupt() pauses for a human; Command(resume=…) continues; the node re-runs from its top.
  • Replay from any checkpoint to debug; it forks and keeps history.

The Skill

You build agents as graphs, not as while True loops.

Before you reach for LangGraph, do a 60-second design:

  1. Name the nodes. Every discrete decision or side-effecting action is a node. "Agent thinks," "tool runs," "reviewer approves," "response streams." If you can't list them, the task is not agent-shaped yet.
  2. Declare the state. Minimal TypedDict with a reducer for every list field. Do not stuff everything into messages; hoist task-specific fields (a working plan, a budget counter, a retrieved_docs list) to the top level.
  3. Draw the edges. Static unless the next step depends on model output. Every conditional edge needs a router function with named branches.
  4. Choose a checkpointer up front. MemorySaver for tests, Postgres/Redis/SQLite for anything else. Do not ship without one — no checkpointer means no resume, no interrupt, no time-travel.
  5. Decide interrupts before tools run, not after. Approvals go on the edge into a side-effecting node so you can cancel before harm; validation goes on the edge out of the model so you can reject bad calls cheaply.
  6. Stream by default. mode="updates" for the UI, mode="messages" for token-level streaming inside model nodes, mode="values" for full snapshots during eval.

Refuse to ship a LangGraph agent that has no checkpointer. Refuse to ship one that interrupts after the side effect. Refuse to ship a messages field without add_messages as its reducer.

Exercises

  1. Easy. Implement the four-node ReAct graph above with a calculator tool and a web-search tool. Verify that list(app.get_state_history(config)) returns at least four checkpoints for a two-turn conversation.
  2. Medium. Add a planner node that runs before agent and writes a structured plan: list[str] into state. Have agent mark plan steps as done. Fail the test if plan is lost across a checkpoint resume (wrong reducer).
  3. Hard. Build a supervisor graph that routes between three subgraphs (researcher, writer, reviewer) using Send. Each subgraph has its own state and checkpointer. Add an interrupt_before=["writer"] on the outer graph so a human can approve the research brief. Confirm that time-travel from a prior checkpoint re-runs only the forked branch.

Solutions

SolutionP1 · One refund, and no learning from the correction

One refund in total, and only on the replayed branch. In the main run the 0.5B model proposed issue_refund(A-1042, 50) without looking the order up. The reviewer rejected it with the correct amount, and the model ignored the correction: it asked for the order ID instead. No money moved. On the replay from step 0 the model proposed the same $50 refund (greedy decoding is deterministic). This time it was approved, and the fork records one refund of $50. The thread keeps both histories: 10 checkpoints.

SolutionB1 · Approved once, paid twice

The refund is sent twice. The first pass through the node sends it and then pauses at interrupt(). On Command(resume="approve") LangGraph runs the node again from its first line, so it sends the refund again before interrupt() returns the approval. The third demo in the second visual shows the same thing with a card charge: ['charged card', 'charged card']. A rejection would not help either, because the money moved before anyone was asked. Keep side effects after the interrupt, ideally in their own node (tools here). Make them idempotent too, for example with a refund ID derived from the ticket, so a retry cannot pay twice.
