Why this came about

Python developers who liked Pydantic's typed models wanted the same safety for agents. Pydantic AI (late 2024) came from the Pydantic team: typed tools, typed outputs and dependency injection, in the style of FastAPI.

In plain words first
Type safety for agents

Pydantic AI, from the makers of Pydantic, treats an agent like well-typed Python: tools and outputs are typed, dependencies are injected into tools, and results are validated. If you like FastAPI-style code, it feels familiar. It covers the same loop, tools, structured output and streaming, with a strong focus on correctness and testing.

Pydantic AI: type-safe agents

Best fit: Python services where types, validation, testing and dependency injection matter, and teams already using Pydantic and FastAPI.

uv add pydantic-ai        # tested with 2.61.0

import os
os.environ["PYDANTIC_AI_NO_BANNER"] = "1"         # hides a startup banner that suggests setting up observability
from pydantic import BaseModel
from pydantic_ai import Agent, DeferredToolRequests, DeferredToolResults
from pydantic_ai.models.openai import OpenAIChatModel
from pydantic_ai.providers.openai import OpenAIProvider

pa_model = OpenAIChatModel("mock-model", provider=OpenAIProvider(base_url=BASE_URL, api_key="mock"))

class Answer(BaseModel):
    summary: str
    escalate: bool

typed_agent = Agent(pa_model, instructions="Help ShopKart customers with orders.", output_type=Answer)

@typed_agent.tool_plain                            # tool_plain: no run context needed; @agent.tool receives RunContext
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

r = typed_agent.run_sync("Where is A-1001?")
print(type(r.output).__name__, "| escalate =", r.output.escalate)
print(r.usage)
What you should see
Answer | escalate = False
RunUsage(input_tokens=100, output_tokens=40, requests=2, tool_calls=1)

r.output is a validated Answer, not text. If the model returns something invalid, Pydantic AI sends the validation error back and asks it to retry.

Approvals use deferred tools: a tool marked requires_approval=True ends the run with a list of pending calls, and you continue with your decisions.

approval_agent = Agent(pa_model, instructions="Help ShopKart customers.", output_type=[str, DeferredToolRequests])

@approval_agent.tool_plain(requires_approval=True)
def cancel_order(order_id: str) -> str:
    """Cancel an order that has not shipped yet."""
    return f"{order_id} cancelled"

r = approval_agent.run_sync("Please cancel A-1002")
print(type(r.output).__name__, [c.tool_name for c in r.output.approvals])
decisions = DeferredToolResults(approvals={c.tool_call_id: True for c in r.output.approvals})
r2 = approval_agent.run_sync(message_history=r.all_messages(), deferred_tool_results=decisions)
print(r2.output)
What you should see
DeferredToolRequests ['cancel_order']
Here is what I found: A-1002 cancelled

Dependencies: what a tool needs that the model must not choose

The tools above read ORDERS, a variable that happens to be in scope. A real tool needs a database connection, and it needs to know which customer is asking. Neither may come from the model: a model that can pass any customer_id can read any customer's orders. Dependency injection means your code hands these things to the run, and the framework hands them to each tool. You declare one type that holds them (deps_type=), pass a value on each run (deps=), and a tool reads them from its first parameter, the run context.

from dataclasses import dataclass
from pydantic_ai import RunContext

@dataclass
class ShopKartDeps:                                # everything the tools need from outside the agent
    orders: dict                                   # in production: a database connection
    customer_id: str                               # who is asking; set by your code, never by the model

deps_agent = Agent(pa_model, deps_type=ShopKartDeps, instructions="Help ShopKart customers with orders.")

@deps_agent.tool                                   # @agent.tool: the first parameter is the run context
def order_status(ctx: RunContext[ShopKartDeps], order_id: str) -> str:
    """Return the shipping status for one of this customer's orders."""
    order = ctx.deps.orders.get(order_id)
    if order is None or order["customer"] != ctx.deps.customer_id:
        return f"{order_id} not found for this customer"
    return f"{order_id} is {order['status']}"

The model sees one argument for this tool, order_id. The context parameter is left out of the schema it is sent, so the customer check cannot be talked around.

Testing an agent without calling a model

Because the tools take their data from deps, a test can pass a small fake. Because the model can be swapped for one run, the test needs no network and costs nothing. Pydantic AI ships two stand-in models. TestModel calls every tool once with made-up arguments that fit the schema, then returns text: it checks that the agent is wired together. FunctionModel lets a function you write play the model, so the test can ask for one exact tool call.

from pydantic_ai import models
from pydantic_ai.messages import ModelResponse, TextPart, ToolCallPart, ToolReturnPart
from pydantic_ai.models.function import FunctionModel
from pydantic_ai.models.test import TestModel

models.ALLOW_MODEL_REQUESTS = False                # any real model call now raises an error instead of costing money
fake_orders = {"A-1001": {"customer": "c-7", "status": "shipped"}}

# Test 1: TestModel calls every tool once with made-up arguments, then returns text. It checks the wiring.
with deps_agent.override(model=TestModel()):
    r = deps_agent.run_sync("Where is my order?", deps=ShopKartDeps(fake_orders, "c-7"))
print("tools called:", [p.tool_name for m in r.all_messages() for p in m.parts if isinstance(p, ToolCallPart)])

# Test 2: FunctionModel lets the test play the model, so it can ask for one exact tool call.
def scripted(messages, info):
    if not any(isinstance(p, ToolReturnPart) for m in messages for p in m.parts):
        return ModelResponse(parts=[ToolCallPart("order_status", {"order_id": "A-1001"})])     # first turn: call the tool
    result = [p.content for m in messages for p in m.parts if isinstance(p, ToolReturnPart)][-1]
    return ModelResponse(parts=[TextPart(result)])                                             # second turn: answer with its result

for customer in ["c-7", "c-9"]:
    with deps_agent.override(model=FunctionModel(scripted)):
        r = deps_agent.run_sync("Where is A-1001?", deps=ShopKartDeps(fake_orders, customer))
    print(customer, "->", r.output)

try:
    deps_agent.run_sync("Where is A-1001?", deps=ShopKartDeps(fake_orders, "c-7"))            # no override: this is a real call
except RuntimeError as e:
    print("blocked:", e)
models.ALLOW_MODEL_REQUESTS = True                 # switch real calls back on for the rest of the lesson
What you should see
tools called: ['order_status']
c-7 -> A-1001 is shipped
c-9 -> A-1001 not found for this customer
blocked: Model requests are not allowed, since ALLOW_MODEL_REQUESTS is False

The same question about the same order gives two answers, and the difference comes only from deps. Customer c-9 cannot read an order that belongs to c-7, whatever the model asks for. The last line is the safety net: with ALLOW_MODEL_REQUESTS = False, a test that forgets the override fails at once instead of quietly calling a paid model.

Also worth knowing: Logfire or any OpenTelemetrylater · 14.120 backend for tracing, MCPlater · 16.26 and A2Alater · 16.29 support, and durable executionlater · 14.115 (a run that survives a crash and resumes where it stopped) through Temporal, DBOS, Prefect, Restate and others.

Exercises

Predict before you run

An agent has output_type=Triage, where urgency: int = Field(ge=1, le=5). The model returns urgency=7. What does Pydantic AI do before your code sees the result? (Solution P1.)

Break it on purpose

Run an agent with a dependency type deps_type=ShopKartDeps but call agent.run_sync("Where is A-1001?") without deps=. What error do you get, and when? (Solution B1.)

Debugging exercise
Debugging exercise: a test that calls the real model

A unit test for the ShopKart agent passes locally but costs money in CI and fails when the provider is slow. The test calls agent.run_sync(...) directly. Using Pydantic AI's testing tools, how do you make it fast, free and deterministic? (Solution D1.)

Make it your own

Add a tool that needs the database from the agent's dependencies, and write a test that passes a fake database through deps. (Solution M1.)

Solutions

SolutionP1 · Validation, then a retry

Pydantic AI validates the output against Triage; urgency=7 fails the le=5 constraint, so the validation error is sent back to the model as a retry prompt, up to the agent's retry limit, before an exception reaches your code. That is Lesson 11.19's validate-and-repair loop, built in. Output validators (@agent.output_validator) add business rules to the same loop.

SolutionB1 · Missing dependencies fail when a tool needs them

The run starts without complaint. ctx.deps is then None, so the error appears only when a tool or a system-prompt function reads from it: with this lesson's order_status tool it is AttributeError: 'NoneType' object has no attribute 'orders', raised in the middle of the run. Pass deps= on every run; typed dependencies are the point, and a type checker such as mypy or pyright flags the call before it runs.

SolutionD1 · TestModel, FunctionModel and override

Use with agent.override(model=TestModel()): in the test, which calls every tool and returns schema-valid output without a network call, or FunctionModel to script exactly what the model returns. Set ALLOW_MODEL_REQUESTS = False (from pydantic_ai.models) in the test setup so any accidental real call fails loudly. Keep real-model checks in evals.

SolutionM1 · Dependencies make tools testable

Declare @dataclass class ShopKartDeps: db: OrdersDB, set deps_type=ShopKartDeps, and write the tool as def get_order_status(ctx: RunContext[ShopKartDeps], order_id: str) -> str: return ctx.deps.db.status(order_id). In the test, pass deps=ShopKartDeps(db=FakeOrdersDB({...})) with TestModel, and assert on the tool's effect. The same pattern injects HTTP clients and per-user settings.

Check your understanding

Explain the mechanismWhat does Pydantic AI add over calling a model with a Pydantic schema yourself?

Worked answer. An agent abstraction with typed dependencies injected into tools and prompts, structured outputs validated with automatic retries, output validators for business rules, model-agnostic providers, streaming of validated partial output, built-in test models, and tracing through Logfire or OpenTelemetry. It also has a graph library for multi-step workflows and supports MCP and agent-to-agent protocols.

A plausible wrong answer. "It is just Pydantic validation." Validation is one part; dependency injection and testing are what make agents maintainable.

Follow-ups. How do typed dependencies help in a multi-tenant service?

Debug a failureA Pydantic AI agent sometimes raises UnexpectedModelBehavior after several retries. What do you look at?

Worked answer. The retry messages in the trace: which field failed validation, and why. Often the schema is too strict or ambiguous for the model (an enum with unclear values, a required field the input lacks), or an output validator's rule is impossible for some inputs. Loosen or clarify the schema, make fields optional where data may be missing, and add cases to the eval set; raise the retry limit only after that.

A plausible wrong answer. "Increase retries to ten." More retries cost more and still fail on impossible cases.

Follow-ups. How would you report these failures as metrics?

Defend a designPydantic AI or LangChain's create_agent for a typed, tool-using service?

Worked answer. Pydantic AI when type safety, dependency injection and testability are the priorities and the team writes typed Python; its agents are small and explicit. create_agent when the team wants LangChain's integrations and middleware, or LangGraph's durable runtime, checkpoints and interrupts underneath. Both validate structured output. For long-running workflows with approvals, LangGraph's persistence is the stronger fit; Pydantic AI can also integrate durable execution engines.

A plausible wrong answer. "Whichever is newer." Choose by the features the service needs.

Follow-ups. How would you migrate tools between the two?
