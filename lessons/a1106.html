In plain words first
The idea in one line

Your LLM knows everything up to its training cutoff. It knows nothing about your company's docs, your codebase, or last week's meeting notes. RAG solves this by retrieving relevant documents and stuffing them into the prompt. It's the most deployed pattern in production AI. If you build one thing from this course, build a RAG pipeline.

Terms you'll hear
Term What people say What it actually means
RAG "AI that reads your docs" Retrieve relevant documents, paste them into the prompt, and generate an answer grounded in those documents
Embedding "Convert text to numbers" A dense vector representation of text where similar meanings produce similar vectors
Vector database "Search engine for AI" A data store optimized for storing vectors and finding the nearest neighbors by similarity
Chunking "Split docs into pieces" Breaking documents into smaller segments (typically 256-512 tokens) so each can be embedded and retrieved independently
Cosine similarity "How similar are two vectors" The cosine of the angle between two vectors; 1 = identical direction, 0 = orthogonal, -1 = opposite
Top-k retrieval "Get the k best matches" Return the k most similar chunks to the query from the vector store
Context window "How much text the LLM can see" The maximum number of tokens the LLM can process in a single request; retrieved chunks must fit within this
Augmented generation "Answer using given context" Generating a response using retrieved documents as context rather than relying solely on trained knowledge
TF-IDF "Word importance scoring" Term Frequency times Inverse Document Frequency; weights words by how distinctive they are within a corpus
Indexing "Preparing docs for search" The offline process of chunking, embedding, and storing documents so they can be searched at query time

The problem

In plain words first

A model only knows what was in its training data, and your company's documents were not. Retrieval-augmented generation (RAG) fixes that without touching the model: when a question arrives, search your documents for the most relevant passages, paste them into the prompt, and tell the model to answer from them and cite them. The documents can change daily, every answer can point to its source, and any model can be used. This lesson builds the pipeline from scratch (chunking, TF-IDF vectors, cosine search, prompt construction), then runs it for real: a small embedding model retrieves from an invented company handbook and a 0.5B model answers ten questions with no context, with the right passages, and with the wrong ones. No model is trained.

You build a chatbot for your company. A customer asks "What's the refund policy for enterprise plans?" The LLM responds with a generic answer about typical SaaS refund policies. The actual policy, buried in a 200-page internal wiki, says enterprise customers get a 60-day window with pro-rated refunds. The LLM has never seen this document. It cannot know what it was not trained on.

Fine-tuning is one solution. Take the LLM, train it on your internal docs, and deploy the updated model. This works but has serious problems. Fine-tuning costs thousands of dollars in compute. The model becomes stale the moment a document changes. You have no way to know which source the model drew from. And if the company acquires another product line next month, you fine-tune again.

RAG is the other solution. Leave the model untouched. When a question comes in, search your document store for relevant passages, paste them into the prompt before the question, and let the model answer using those passages as context. The document store can be updated in minutes. You can see exactly which documents were retrieved. The model itself never changes. This is why RAG is the dominant pattern in production: it's cheaper, fresher, more auditable, and works with any LLM.

Idea 1 · The RAG Pattern

The entire pattern fits in four steps:

Query -> Retrieve -> Augment prompt -> Generate. Every RAG system follows this pattern. The differences between production RAG systems are in the details of each step: how you chunk, how you embed, how you search, and how you construct the prompt.

Idea 2 · Why RAG Beats Fine-Tuning

Concern Fine-tuning RAG
Cost From a few dollars (LoRA on a small model) to $100,000+ per run, repeated for every update A small charge per query for embedding and the longer prompt, plus indexing
Freshness Stale until retrained Updated in minutes by re-indexing docs
Auditability Cannot trace answer to source Can show exact retrieved passages
Hallucination Still hallucinates freely Reduced when the right passages are retrieved; when retrieval misses, the model can still invent an answer (measured below)
Data privacy Training data baked into weights Documents stay in your vector store

Fine-tuning changes the model's weights permanently. RAG changes the model's context temporarily. For most applications, temporary context is what you want.

The case where fine-tuning wins: when you need the model to adopt a specific style, tone, format or reasoning pattern that prompting cannot achieve. For adding factual knowledge, RAG usually wins: Ovadia et al. (2023) found retrieval beat unsupervised fine-tuning for injecting new facts, and the two combine well when you need both.

Idea 3 · Embedding Models

An embedding model converts text into a dense vector. Similar texts produce vectors that are close together in this high-dimensional space. "How do I reset my password?" and "I need to change my password" produce nearly identical vectors despite sharing few words. "The cat sat on the mat" produces a very different vector.

For this lesson, we build our own simple embedding using TF-IDF. Not because TF-IDF is what production systems use, but because it makes the concept concrete: text goes in, a vector comes out, similar texts produce similar vectors.

Idea 4 · Vector Similarity

Given two vectors, how do you measure similarity? Three options:

Cosine similarity: the cosine of the angle between two vectors. Ranges from -1 (opposite) to 1 (identical). Ignores magnitude, only cares about direction. This is the default for RAG.

cosine_sim(a,b)=∥a∥⋅∥b∥dot(a,b)​

Dot product: the raw inner product. Larger vectors get higher scores. Useful when magnitude carries information (longer documents might be more relevant).

dot(a,b)=i∑​ai​bi​

L2 (Euclidean) distance: straight-line distance in the vector space. Smaller distance = more similar. Sensitive to magnitude differences.

L2(a,b)=i∑​(ai​−bi​)2​

Cosine similarity is the standard. It handles documents of different lengths gracefully because it normalizes by magnitude. When someone says "vector search," they almost always mean cosine similarity.

Idea 5 · Chunking Strategies

Documents are too long to embed as single vectors. A 50-page PDF might produce a terrible embedding because it contains dozens of topics. Instead, you split documents into chunks and embed each chunk separately.

Fixed-size chunking: split every N tokens. Simple and predictable. A 512-token chunk with 50-token overlap means chunk 1 is tokens 0-511, chunk 2 is tokens 462-973, and so on. The overlap ensures you do not split a sentence at an unlucky boundary.

Semantic chunking: split at natural boundaries. Paragraphs, sections, or markdown headers. Each chunk is a coherent unit of meaning. More complex to implement but produces better retrieval.

Recursive chunking: try to split at the largest boundary first (section headers). If a section is still too large, split at paragraph boundaries. If a paragraph is still too large, split at sentence boundaries. This is the LangChain RecursiveCharacterTextSplitter approach and it works well in practice.

Chunk size matters more than people think:

  • Too small (64-128 tokens): each chunk lacks context. "It increased 15% last quarter" means nothing without knowing what "it" refers to.
  • Too large (2048+ tokens): each chunk covers multiple topics, diluting relevance. When you search for revenue data, you get a chunk that's 10% about revenue and 90% about headcount.
  • Sweet spot (256-512 tokens): enough context to be self-contained, focused enough to be relevant.

Most production RAG systems start with 256-512 token chunks and some overlap, then tune chunk size on their own questions (Lesson 5.23 measures the strategies).

Idea 6 · Vector Databases

Once you have embeddings, you need somewhere to store and search them. Options:

For this lesson, we build a simple in-memory vector store. It stores vectors in a list and does brute-force cosine similarity search. This is equivalent to FAISS with a flat index. It scales to maybe 100,000 vectors before getting slow. Production systems use approximate nearest neighbor (ANN) algorithms like HNSW to search millions of vectors in milliseconds.

Idea 7 · The Full Pipeline

The indexing phase runs once per document (or when documents update). The querying phase runs on every user request. In production, indexing might process millions of documents over hours. Querying must respond in under a second.

The same idea as a formula

Retrieve. Score every chunk d against the query q with the embedding model E and keep the top k:

s(q,d)=cos(E(q),E(d)),Zk​(q)=topk​s(q,d).

Generate. The original RAG paper (Lewis et al. 2020) treats the retrieved passage z as a hidden variable and mixes over it:

p(y∣q)≈z∈Zk​(q)∑​p(z∣q)p(y∣q,z).
Practical systems paste all k passages into one prompt and generate once.

Measure the two halves separately. Retrieval: recall@k=∣Q∣1​∑q​1[gold passage∈Zk​(q)]. Generation: correctness and faithfulness given the retrieved context. An answer can only be right through retrieval if the passage was retrieved.

Worked example
Ten questions, top 3, about 60 tokens per passage
  • Retrieved context per question: 3×60≈180 tokens plus the instructions, far below any window.
  • If recall@3 is 0.9, at most 9 of the 10 answers can come from the documents; the tenth must be "I don't know" or a guess.
  • At k=10 on the same 10-document handbook recall is trivially 100%, and the prompt carries every document: on a real corpus of millions of chunks, k trades recall against prompt length and distraction.
  • Cost per query: one query embedding plus the extra prompt tokens; indexing is paid once per document change.
Check your mental model
  • ✗ "RAG stops hallucination."
    ✓ It gives the model the facts when retrieval finds them. When retrieval misses, the model can still answer confidently and wrongly (the third setting below).
  • ✗ "If the answer is wrong, the model is the problem."
    ✓ Check retrieval first: if the right passage was not in the top k, no model could use it.
  • ✗ "More retrieved chunks are always better."
    ✓ Extra chunks add cost and distractors (Lesson 11.5); tune k on your questions.
Predict before you run

With no context, how many of ten questions about an invented company will the 0.5B model answer correctly? With the top three retrieved passages? And with three passages that do not contain the answer, will it say "I don't know" as instructed? (Solution P1.)

Idea 8 · Real Numbers

Most production RAG systems use these parameters:

  • k = 5 to 10 retrieved chunks per query
  • Chunk size = 256 to 512 tokens with 50-token overlap
  • Context budget: 2,500-5,000 tokens of retrieved content per query
  • Total prompt: ~8,000-16,000 tokens (system prompt + retrieved chunks + conversation history + user query)
  • Embedding dimension: 384-3072 depending on model
  • Indexing throughput: 100-1,000 documents per second with API embeddings
  • Query latency: 50-200ms for retrieval, 500-3000ms for generation

Step 1 · Document Chunking

def chunk_text(text, chunk_size=200, overlap=50):
    words = text.split()
    chunks = []
    start = 0
    while start < len(words):
        end = start + chunk_size
        chunk = " ".join(words[start:end])
        chunks.append(chunk)
        start += chunk_size - overlap
    return chunks

Step 2 · TF-IDF Embeddings

We build a simple embedding function. TF-IDF (Term Frequency-Inverse Document Frequency) is not a neural embedding, but it converts text to vectors in a way that captures word importance. Frequent words in a document get higher TF. Rare words across the corpus get higher IDF. The product gives a vector where important, distinctive words have high values.

import math
from collections import Counter

def build_vocabulary(documents):
    vocab = set()
    for doc in documents:
        vocab.update(doc.lower().split())
    return sorted(vocab)

def compute_tf(text, vocab):
    words = text.lower().split()
    count = Counter(words)
    total = len(words)
    return [count.get(word, 0) / total for word in vocab]

def compute_idf(documents, vocab):
    n = len(documents)
    idf = []
    for word in vocab:
        doc_count = sum(1 for doc in documents if word in doc.lower().split())
        idf.append(math.log((n + 1) / (doc_count + 1)) + 1)
    return idf

def tfidf_embed(text, vocab, idf):
    tf = compute_tf(text, vocab)
    return [t * i for t, i in zip(tf, idf)]

Step 3 · Cosine Similarity Search

def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(x * x for x in b))
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return dot / (norm_a * norm_b)

def search(query_embedding, stored_embeddings, top_k=5):
    scores = []
    for i, emb in enumerate(stored_embeddings):
        sim = cosine_similarity(query_embedding, emb)
        scores.append((i, sim))
    scores.sort(key=lambda x: x[1], reverse=True)
    return scores[:top_k]

Step 4 · Prompt Construction

This is where the "augmented" in RAG happens. Take the retrieved chunks, format them into a prompt, and ask the LLM to answer based on the provided context.

def build_rag_prompt(query, retrieved_chunks):
    context = "\n\n---\n\n".join(
        f"[Source {i+1}]\n{chunk}"
        for i, chunk in enumerate(retrieved_chunks)
    )
    return f"""Answer the question based ONLY on the following context.
If the context doesn't contain enough information, say "I don't have enough information to answer that."

Context:
{context}

Question: {query}

Answer:"""

Step 5 · The Complete RAG Pipeline

class RAGPipeline:
    def __init__(self):
        self.chunks = []
        self.embeddings = []
        self.vocab = []
        self.idf = []

    def index(self, documents):
        all_chunks = []
        for doc in documents:
            all_chunks.extend(chunk_text(doc))
        self.chunks = all_chunks
        self.vocab = build_vocabulary(all_chunks)
        self.idf = compute_idf(all_chunks, self.vocab)
        self.embeddings = [
            tfidf_embed(chunk, self.vocab, self.idf)
            for chunk in all_chunks
        ]

    def query(self, question, top_k=5):
        query_emb = tfidf_embed(question, self.vocab, self.idf)
        results = search(query_emb, self.embeddings, top_k)
        retrieved = [(self.chunks[i], score) for i, score in results]
        prompt = build_rag_prompt(
            question, [chunk for chunk, _ in retrieved]
        )
        return prompt, retrieved

Step 6 · Generation (simulated)

In production, this is where you call the LLM API. For this lesson, we simulate generation by extracting the most relevant sentence from the retrieved context.

def simple_generate(prompt, retrieved_chunks):
    query_words = set(prompt.lower().split("question:")[-1].split())
    best_sentence = ""
    best_score = 0
    for chunk in retrieved_chunks:
        for sentence in chunk.split("."):
            sentence = sentence.strip()
            if not sentence:
                continue
            words = set(sentence.lower().split())
            overlap = len(query_words & words)
            if overlap > best_score:
                best_score = overlap
                best_sentence = sentence
    return best_sentence if best_sentence else "I don't have enough information."

RAG for real: retrieve with BGE, answer with Qwen

Ten documents of an invented company handbook and ten questions with known answers. Retrieval with bge-small-en-v1.5 (recall@3), then Qwen2.5-0.5B-Instruct answers each question three ways: closed book, with the top 3 retrieved passages, and with 3 passages that do not contain the answer. Answers are checked against the gold value by code. About a minute.

def ask(prompts):

    enc = tok(batch, return_tensors="pt", padding=True)
    with torch.no_grad():
        g = lm.generate(**enc, max_new_tokens=48, do_sample=False, pad_token_id=tok.eos_token_id)
    return [tok.decode(x[enc.input_ids.shape[1]:], skip_special_tokens=True).strip() for x in g]

Reading this output

Retrieval was perfect here: for all 10 questions the passage holding the answer was among the top 3. With only 10 short documents that is expected; on a real corpus this number is the first thing to measure, because it caps everything after it.

Closed book, 0 of 10, and never "I don't know". The model cannot know an invented company's policies, so every answer is a guess, and every guess is fluent: "typically require a response within 24 hours" for a policy that says 30 minutes. Without context, confidence tells you nothing.

With the top 3 passages, 9 of 10. The same model, same weights, now copies the right number from the passage ("a 60-day refund window, pro-rated by unused days"). Grounding did the work, not the model. Only 1 of 10 answers cited a source id even though the instructions asked for it: a small model follows the main instruction (use the context) better than the secondary one (cite), so check each instruction separately.

With the wrong passages, the failure that matters. Half the time the model obeyed and said "I don't know". In 4 of 10 it answered anyway by grabbing a number from an unrelated passage: "the Team plan guarantees a 60-day monthly uptime" splices the refund policy into the uptime question, and one answer simply repeats the refund passage. (The checker counts a gold string anywhere in the answer, so 1 of 10 counts as correct with the wrong documents.) This is why you evaluate the "retrieval failed" path explicitly: a RAG system is only as honest as its behaviour when the context does not contain the answer.

Use it: the same idea with real libraries

With a real embedding model and LLM, the code barely changes:

from openai import OpenAI

client = OpenAI()

def embed(text):
    response = client.embeddings.create(
        model="text-embedding-3-small",
        input=text
    )
    return response.data[0].embedding

def generate(prompt):
    response = client.responses.create(       # Responses API; GPT-6 models take no temperature
        model="gpt-6-luna",
        input=prompt,
    )
    return response.output_text

Or with Anthropic:

import anthropic

client = anthropic.Anthropic()

def generate(prompt):
    response = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}]
    )
    return next(b.text for b in response.content if b.type == "text")

The pipeline is the same. Swap the embedding function. Swap the generation function. The retrieval logic, chunking, prompt construction -- all identical regardless of which models you use.

For vector storage at scale, replace the brute-force search with a proper vector database:

import chromadb

client = chromadb.Client()
collection = client.create_collection("my_docs")

collection.add(
    documents=chunks,
    ids=[f"chunk_{i}" for i in range(len(chunks))]
)

results = collection.query(
    query_texts=["What is the refund policy?"],
    n_results=5
)

Chroma handles the embedding internally (it uses all-MiniLM-L6-v2 by default) and stores the vectors in a local database. Same pattern, different plumbing.

What's current (2024–2026)
  • Hybrid retrieval and reranking as the baseline: BM25 plus dense vectors, fused, then a cross-encoder or LLM reranker (Lesson 11.7).
  • Contextual chunking: prefixing each chunk with a short LLM-written description of where it sits (Anthropic's contextual retrieval), and late chunking with long-context embedders.
  • Agentic RAG: the model decides when and what to search, iterates, and checks its evidence, instead of one fixed retrieve-then-generate pass.
  • Citations as a product feature: APIs and frameworks return answers with passage-level citations, and evaluation separates retrieval recall from answer faithfulness.

Sources: Lewis et al. 2020, Karpukhin et al. 2020 (DPR), Ovadia et al. 2023, Anthropic contextual retrieval, Claude citations, BGE embeddings.

Recap
What to keep from this lesson
  • RAG = retrieve relevant chunks, put them in the prompt, generate with citations.
  • Indexing runs offline; retrieval and generation run per query.
  • Evaluate retrieval (recall@k) and generation (correct, faithful) separately.
  • Tell the model what to do when the context lacks the answer, and test that path.
  • Fine-tune for behaviour and style; retrieve for facts.

# RAG Pipeline Pattern

Every RAG system follows this pattern:

```
documents -> chunk -> embed -> store
query -> embed -> search(top_k) -> build_prompt -> generate
```

Indexing happens once per document. Querying happens on every user request.

## When to use RAG

- The LLM needs access to private or recent documents
- Fine-tuning is too expensive or too slow to update
- You need to cite sources for answers
- The knowledge base changes frequently

## When NOT to use RAG

- The answer is general knowledge the LLM already has
- The task is creative (writing, brainstorming) not factual
- You need the model to adopt a specific reasoning style (use fine-tuning)

## Implementation checklist

1. Chunk documents into 256-512 token segments with 50-token overlap
2. Embed each chunk using a consistent embedding model
3. Store embeddings in a vector database with the original text
4. At query time, embed the user's question with the same model
5. Retrieve top-k (5-10) most similar chunks via cosine similarity
6. Build a prompt: system instruction + retrieved context + user question
7. Generate the answer, grounding it in the retrieved context
8. Return the answer with source references

## Common mistakes

- Using different embedding models for indexing and querying (vectors are incompatible)
- Chunks too small (lose context) or too large (dilute relevance)
- Not including overlap between chunks (splits sentences at boundaries)
- Forgetting to re-index when documents change
- Returning retrieved chunks to the user without generating a coherent answer
- Not setting temperature=0 for factual RAG queries (higher temperature = more hallucination)

## Debugging retrieval

If the right chunks are not being retrieved:
1. Print the query embedding and verify it's non-zero
2. Check cosine similarities manually for a known-relevant chunk
3. Try rephrasing the query to match document vocabulary
4. Verify the embedding model matches between index and query time
5. Check if the relevant content was lost during chunking

## Production parameters

- Chunk size: 256-512 tokens
- Overlap: 50 tokens (10-20% of chunk size)
- Top-k: 5-10 for most use cases
- Temperature: 0 for factual answers
- Embedding model: text-embedding-3-small (cost effective) or text-embedding-3-large (higher accuracy)

Exercises

  1. Replace the TF-IDF embeddings with a simple bag-of-words approach (binary: 1 if word present, 0 if not). Compare retrieval quality on the sample documents. TF-IDF should outperform because it weights rare words higher.

  2. Experiment with chunk sizes: try 50, 100, 200, and 500 words on the same document set. For each size, run the same 5 queries and count how many return a relevant chunk in the top-3. Find the sweet spot where retrieval quality peaks.

  3. Add metadata to each chunk (source document name, chunk position). Modify the prompt template to include source attribution so the LLM cites its sources.

  4. Implement a simple evaluation: given 10 question-answer pairs, run each question through the RAG pipeline, and measure what percentage of retrieved chunks contain the answer. This is retrieval recall at k.

  5. Build a conversation-aware RAG pipeline: maintain a history of the last 3 exchanges and include them in the prompt alongside the retrieved chunks. Test with follow-up questions like "What about enterprise?" after asking about pricing.

Solutions

SolutionP1 · Context turned guesses into answers

Closed book: 0 of 10 correct, and 0 times "I don't know": ten confident guesses. With the top 3 retrieved passages: 9 of 10 correct. With three passages that lack the answer: "I don't know" 5 times, a wrong answer 4 times (often a number lifted from an unrelated passage, such as "60-day monthly uptime"), and 1 counted correct. The instruction to abstain worked half the time, which is far better than never and far from reliable.

SolutionB1 · Without an exit, the model fills the gap

Without an explicit way out, the model treats "answer using the context" as "produce an answer". Even with the line in place, 4 of 10 wrong-document answers were confident fabrications assembled from unrelated passages; remove it and expect most of the 5 "I don't know" replies to turn into answers of the same kind, moving the wrong-documents setting towards the closed-book result (all guesses). Run it to see the exact count for this model. The fixes are layered: keep the abstain instruction, check that the cited passage actually contains the answer (Lesson 11.12 covers groundedness checks), and gate on retrieval scores so very weak matches return "no relevant documents" before the model is called.

Weigh a trade-offA team is about to index a new document corpus and asks you to review the chunker. They picked semantic splitting, 1000 tokens per chunk and 20 percent overlap, because a blog post recommended it. What do you tell them?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. Start from the query type, not from a post. Factoid questions want 256 to 512 tokens, analytical or multi-hop questions 512 to 1024, and whole-section questions 1024 to 2048. Begin with recursive splitting at 512 tokens and no overlap, then measure recall at 5 on a 50-query set before you move any knob.

Why size follows the question.

A chunk must be large enough to hold the answer plus its local context, and small enough that the top k returns the answer and not noise. Too small, at 64 to 128 tokens, and a chunk says "it increased 15% last quarter" with no subject. Too large, at 2048 tokens and more, and one chunk is 10% about revenue and 90% about headcount, so its embedding points nowhere.

Query type Chunk size
Factoid 256 to 512 tokens
Analytical or multi-hop 512 to 1024 tokens
Whole-section comprehension 1024 to 2048 tokens

What the measurements say.

  • Recursive splitting at 512 tokens beat semantic splitting 69% to 54% in the chunking study.
  • Overlap gave zero measurable benefit in the sparse retrieval study, and every overlapped token is embedded and stored again, so the index cost grows with the overlap.
  • Response quality drops sharply around 2,500 tokens of context, so bigger chunks hit a cliff.
  • Semantic splitting without a minimum size produces 40-token fragments that hurt retrieval.

Pick a default without a benchmark.

Three properties decide the first chunker: the document type, the paragraph length, and whether the format carries structure. Prose with no structure gets recursive splitting. Markdown and API docs get the header splitter. Code gets a syntax-aware splitter. When in doubt, recursive splitting is the strongest single baseline.

Then measure.

Build a 50-query eval set, stratified by query type, and read recall at 5 for each candidate. Clamp every chunker with a minimum and a maximum size. Never let a chunk span two documents.

Plausible wrong answers.

  • "Semantic splitting is best because it follows meaning." It lost to recursive splitting at 512 tokens in the measured study, and it makes tiny fragments unless you set a floor.
  • "Overlap is a safety margin, keep it." The studies found that overlap often adds nothing, and it adds index cost in proportion to its size; justify any overlap with an ablation.
  • "Bigger chunks give the model more context." Quality drops around 2,500 tokens of context, and a chunk that covers many topics dilutes its own embedding.

Follow-ups an interviewer may ask.

  • (level 2) Why does the chunk size depend on the kind of question? Expected: the chunk has to contain the answer with its context, and still be small enough that the top k is about the answer and not about the surrounding noise.
  • (level 2) The corpus is markdown API documentation. What do you try first? Expected: the structural header splitter, because the format carries explicit structure; drop or merge header-only chunks.
  • (level 3) Which two guards does every chunker need, whatever the strategy? Expected: a minimum and a maximum size, because chunks of 5 tokens or 5000 tokens both break retrieval.
  • (level 3) You switch the embedding model later. What do you run again? Expected: the chunking eval, because the winner depends on the corpus and the model, and semantic splitting moves its boundaries when the model changes.

Where it is taught. The lesson chunking strategies gives the size table and the measurements, the lesson RAG explains the too-small and too-large failures, and the lesson chunking comparison picks a default from three properties.

Explain the mechanismYou write the search step of a retrieval pipeline. A teammate wants to rank chunks by the raw dot product between the query vector and each chunk vector. What do you use instead, and when is the dot product the right choice?

Level 1 of 4 · about 5 minutes to answer well.

Short answer. Use cosine similarity, which is the dot product divided by the lengths of the two vectors. It measures only the angle, so a long chunk and a short chunk compete on direction and not on size. The raw dot product is right only when the vector length carries meaning that you want to reward.

Three measures.

Measure What it does Behavior
Cosine the cosine of the angle between two vectors, from -1 to 1 ignores length, the default for retrieval
Dot product the sum of the products of each pair of values longer vectors score higher
L2 distance the straight-line distance between the two points smaller is closer, sensitive to length

Cosine normalizes by length, so chunks of different sizes compare on direction alone. When someone says vector search, they almost always mean cosine.

The code.

def cosine_similarity(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(x * x for x in b))
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return dot / (norm_a * norm_b)

The guard returns zero when a vector has no length, so an empty chunk does not divide by zero.

When the two agree.

Many embedding models return unit-length vectors, or the caller asks for normalized output. The question-answering lesson encodes with normalization on and then ranks with a plain matrix product. With unit vectors the dot product equals the cosine, so the cheaper operation gives the same order.

Plausible wrong answers.

  • "The dot product and the cosine give the same order." Only when every vector has the same length; otherwise longer vectors win on the dot product.
  • "A smaller cosine means a closer match." A larger cosine means a smaller angle; smaller is closer only for a distance such as L2.
  • "Use whatever the vector store defaults to." The measure must match how the vectors were produced and normalized, so check the embedder before the store.

Follow-ups an interviewer may ask.

  • (level 1) What do the values 1, 0 and -1 mean for cosine? Expected: the same direction, orthogonal, and opposite directions.
  • (level 2) Your embedder returns unit vectors. Does the choice still matter? Expected: no, because with unit vectors the dot product and the cosine are equal, which is why the lesson normalizes and then uses a matrix product.
  • (level 2) Why does L2 distance treat a long and a short chunk differently? Expected: it measures the straight-line distance, so a longer vector sits farther away even when it points the same way.
  • (level 3) When would you keep the raw dot product on purpose? Expected: when the model was trained so that length carries a signal, such as more content in a longer document, and you want that signal in the rank.

Where it is taught. The lesson RAG defines the three measures and the guard, and the lesson question answering ranks normalized vectors with a matrix product.

Defend a designDesign a question answering service over a company's internal documents: wikis, policies, contracts and support articles, a few hundred thousand pages, with weekly updates. Users are employees with different access rights. Walk through the pipeline, the evaluation, and the first three things you would measure in production.

Level 3 of 4 · about 30 minutes to answer well.

Short answer. Build two sides. The ingestion side parses each document, chunks it per document with a structure-aware splitter, embeds the chunks, and indexes dense vectors and a BM25 index with metadata and access labels on every chunk. The query side filters by access first, runs hybrid retrieval with rank fusion, reranks a candidate pool with a cross-encoder, and generates a cited answer with a refuse path. Prove it with a golden set labeled by domain experts and a retrieval eval that reports recall at k per query class, then measure retrieval quality weekly, faithfulness and citation correctness per turn, and cost per query in production.

Requirements first.

  • Freshness. Weekly updates mean re-indexing changed documents, not retraining a model.
  • Access. Different rights mean per-chunk labels and a filter before retrieval.
  • Audit. Answers must point at the passages they came from.
  • Scale. Several hundred thousand pages do not fit any prompt; retrieval decides what the model sees.

Ingestion.

  1. Parse each document into text and structure.
  2. Chunk per document. Start with recursive splitting at 512 tokens and no overlap; use the header splitter for markdown; clamp every chunk with a minimum and a maximum; never let a chunk span two documents.
  3. Attach metadata: source, date, version, category, author, role label, jurisdiction or business unit tag.
  4. Embed each chunk and write the vector with its payload. Build a BM25 index beside it with field weights so a title or code match counts more than a body match.

Query.

  1. Filter the candidate space by the caller's role labels before any search.
  2. Run dense and BM25 retrieval in parallel and fuse by rank.
  3. Send the top 20 to a cross-encoder and keep the top 5, the funnel the production capstone uses.
  4. Build the prompt with the stable parts first: the system prompt and the static policies, then the reranked context, then the question. The capstone targets a cache hit rate of 60 to 80 percent on that prefix, which drops the cost per query by 3 to 5 times.
  5. Generate with instructions to cite every claim and to refuse when the snippets do not answer; gate on the reranker's rank-1 score before generation and drop uncited claims after it.

Evaluation before launch.

  • A golden set of 200 question and answer pairs with citations, labeled by a domain expert, as the capstone requires.
  • Qrels in tiers: a smoke set of 20 queries in CI, a regression set of 200 nightly, a deep set of 2000 weekly.
  • Retrieval metrics per query class: recall at k first, then MRR, then nDCG if relevance is graded.
  • Answer metrics: faithfulness and relevance, judged by a model from another family.
  • A red team of 50 adversarial prompts: jailbreaks, data extraction attempts, off-domain questions and cross-unit leaks.

The first three production measurements.

  1. Retrieval quality on the golden set, weekly. The capstone alerts on a 5 percent drop. Slice it by document type and business unit.
  2. Faithfulness and citation correctness per turn. These catch the generator inventing or mis-citing while retrieval is fine.
  3. Cost and latency per query by stage. Cache hit rate, tokens per query, and the split between retrieval, in the lesson's range of 50 to 200 ms, and generation, in the range of 500 to 3000 ms.

Plausible wrong answers.

  • "Put every document into one long prompt." Hundreds of thousands of pages do not fit, and the lesson budgets 2,500 to 5,000 tokens of retrieved text per query for a reason.
  • "Tune the model on the documents every week." It cannot cite, it goes stale between runs, and it cannot enforce access rights.
  • "Vector search alone is enough." Exact identifiers, codes and names need the lexical side; run both and fuse.
  • "Ship without a labeled set, the demo works." A demo on ten documents says nothing about hundreds of thousands of pages; label the golden set first.

Follow-ups an interviewer may ask.

  • (level 3) Where does access control live? Expected: in the retrieval filter, as role labels on chunks applied before the similarity search, and never in the prompt text.
  • (level 3) A document changes on Tuesday. What is stale and for how long? Expected: its chunks, until the next re-index; re-embed only changed documents, carry the version in the metadata, and watch the gap between source updates and index updates.
  • (level 4) How do you keep the model cost down at this volume? Expected: a cache-friendly prompt with the system prompt and policies first, the reranked context next and the question last; the capstone targets a 60 to 80 percent hit rate and a 3 to 5 times lower cost per query.
  • (level 4) The golden set passes and one department still reports bad answers. What do you do? Expected: slice the eval by document type and query class, add that department's real queries to the qrels, and check whether their documents are chunked by a splitter that fits their format.

Weigh a trade-offYour chunker keeps a 100-token overlap between neighbor chunks. After the last corpus refresh the index size and the embedding bill both went up, and a teammate says the overlap must stay because it protects sentences that a boundary would cut in half. How do you settle it?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Settle it with an ablation, not an opinion. Run the same recall at 5 eval with the overlap at zero and at the current value on a stratified query set, and keep the overlap only if the number moves. The recent studies found that overlap often adds no measurable benefit, while it adds index cost in proportion to its size.

Where overlap came from.

The fixed-window baseline cuts every N tokens with no regard for sentences. The RAG lesson shows the classic layout: 512-token chunks with a 50-token overlap, so chunk 1 holds tokens 0 to 511 and chunk 2 holds tokens 462 to 973. The repeated tail makes sure a sentence cut at an unlucky point appears whole somewhere.

Why it matters less now.

A recursive splitter tries the paragraph break first, then the line break, then the sentence end, then the space. Its boundaries fall at natural breaks, so the problem that overlap solved mostly disappears. The chunking lesson lists overlap under cargo cult: the 2026 studies found zero measurable benefit in the measured case, and every overlapped token is embedded and stored twice.

The test.

  1. Keep the chunker, the embedder and the query set fixed.
  2. Run recursive splitting at 512 tokens with overlap zero and with the current overlap.
  3. Compare recall at 5 per query slice, and compare chunk counts.
  4. Keep the overlap only where a slice shows a real gain, and record the ablation next to the setting.

The chunker skill in the lesson sets overlap to zero by default and refuses an overlap above 20 percent without an ablation that shows it helps.

Plausible wrong answers.

  • "Overlap is free, embeddings are cheap." Every overlapped token is embedded and stored twice, so the index cost grows in proportion to the overlap.
  • "A blog post says 20 percent overlap." The studies found no measurable benefit in the measured case; the answer depends on your corpus, so measure it there.
  • "Remove it everywhere, no test needed." The ablation is cheap and the result is corpus dependent; a slice with real boundary losses would show up in it.

Follow-ups an interviewer may ask.

  • (level 2) Why did the fixed-window splitter need overlap? Expected: it cuts at a fixed count whatever the text, so a boundary can split a sentence; the repeated tail puts that sentence whole into the next chunk.
  • (level 2) What does a recursive splitter do instead? Expected: it splits on the paragraph, the line and the sentence separators in turn, so boundaries land on natural breaks.
  • (level 3) What rule does the chunker skill apply to overlap? Expected: default zero, and refuse any overlap above 20 percent without an ablation.
  • (level 3) The ablation shows a gain on one document type only. What do you ship? Expected: overlap for that type alone, with the ablation recorded, and a re-run when the corpus or the embedder changes.

Where it is taught. The lesson chunking strategies reports the overlap studies and sets the skill rule, and the lesson RAG shows the fixed-window layout that overlap was built for.

Explain the mechanismA product team wants an assistant that answers questions about the internal policy wiki. One engineer proposes to tune the model on the wiki pages. Another proposes to search the pages at question time and paste the matches into the prompt. Which do you pick, and in which case would you still tune the model?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. Pick retrieval for knowledge. The model never changes, the document store updates in minutes, and you can show the passages behind each answer. Tuning fits when you need a style, a tone or a reasoning pattern that a prompt cannot reach, not when you need facts.

Why retrieval wins on facts.

The lesson lines the two up on five concerns:

Concern Tuned model Retrieval
Cost a training run costs from $1,000 to more than $100,000 a query costs $0.01 to $0.10 for the embedding and the model call
Freshness stale until the next training run re-index the changed page and the next query sees it
Audit no way to trace a fact to a page the retrieved passages are visible and can be returned
Grounding the model still invents facts freely the prompt tells the model to answer only from the passages
Privacy the pages are baked into the weights the pages stay in your own store

Tuning changes the weights for good. Retrieval changes the context for one request. For facts, a temporary context is what you want.

The one case for tuning.

When the goal is how the model writes or reasons, and prompting does not get there, tuning is the right tool. A fixed voice, a house format or a reasoning habit lives in the weights better than in a long instruction.

The shape of the system.

Retrieval runs in two phases. The index phase chunks each page, embeds each chunk and stores the vectors with the text. The query phase embeds the question, finds the top k chunks, builds a prompt from them and calls the model. The lesson budgets k at 5 to 10 chunks and 2,500 to 5,000 tokens of retrieved text per query.

Plausible wrong answers.

  • "Tune the model, because then it knows the documents." The weights hold a copy that goes stale, and nothing in the output says which page a fact came from.
  • "Retrieval is always better." A fixed style, a tone or a reasoning pattern is learned better by tuning than by a prompt.
  • "Skip the search and put the whole wiki in the prompt." The lesson budgets 2,500 to 5,000 tokens of retrieved text per query; a whole wiki does not fit, and unrelated text dilutes the prompt.

Follow-ups an interviewer may ask.

  • (level 1) A policy page changes. What happens in each approach? Expected: with retrieval you re-index that page and the next answer uses the new text; with a tuned model the old fact stays until you train again.
  • (level 2) A legal reviewer asks which page an answer came from. Which approach can show it? Expected: retrieval, because the passages that went into the prompt are known and can be returned with the answer.
  • (level 2) Why is the privacy story different? Expected: with retrieval the pages stay in your store and only the matched chunks go to the model for one call; with tuning the content is inside the weights of the model you deploy.
  • (level 3) The answer is wrong even though the right passage is in the store. Which stage do you check first? Expected: retrieval, with recall at k, because the model cannot use a passage that the search did not return.

Where it is taught. The lesson RAG compares the two approaches and builds the index and query phases.

Check your understanding

Q1What does RAG stand for and what problem does it solve?

RAG retrieves relevant documents from an external knowledge base and adds them to the prompt. This gives the LLM access to up-to-date, domain-specific information without retraining.

Q2Why is RAG preferred over fine-tuning for most knowledge-grounded applications?

Fine-tuning costs thousands of dollars, produces a static model that becomes stale as documents change, and offers no source attribution. RAG updates instantly (just update the document store), costs only embedding + storage, and can cite its sources.

Q3What is the correct order of steps in a basic RAG pipeline?

Ingestion: chunk documents -> embed chunks -> store in vector DB. Query time: embed the user's query -> retrieve top-K similar chunks -> add chunks to prompt -> generate answer grounded in retrieved context.

Q4What is a common failure mode in basic RAG systems?

Semantic search finds text that 'sounds like' the query, not necessarily text that 'answers' it. A query about revenue might retrieve chunks discussing revenue strategy rather than the chunk containing the actual number.

Q5How do you evaluate RAG quality?

RAG evaluation has two parts: retrieval quality (precision/recall of retrieved chunks against ground truth) and generation quality (faithfulness to context, relevance to query, no hallucination beyond retrieved information).
