In plain words first
The idea in one line

A dense 70B transformer activates every parameter for every token. A 671B MoE activates only 37B per token and matches or beats much larger dense models on most benchmarks. Sparsity is one of the most important scaling ideas of the decade.

Terms you'll hear
Term What people say What it actually means
Expert "One FFN among many" An independent feed-forward network; parameters dedicated to a sparse slice of the FFN computation.
Router "The gate" A tiny linear layer that scores each token against each expert; top-k selection.
Top-k routing "k active experts per token" Each token's FFN computation goes through exactly k experts, weighted by gate.
Auxiliary loss "Load-balance penalty" Extra loss term that penalizes skewed expert usage.
Auxiliary-loss-free "DeepSeek-V3's trick" Balance via per-expert bias on the router's selection only; no extra gradient.
Shared expert "Always on" Extra expert through which every token passes; captures common knowledge.
Expert parallelism "Shard by expert" Distribute different experts to different GPUs; route tokens across the network.
Sparsity "Active params < total params" The ratio $k \times \text{expert size} / (E \times \text{expert size})$; 37/671 ≈ 5.5% for DeepSeek-V3.

The problem

In plain words first

In a normal (dense) transformer every token goes through every weight of the feed-forward layers, so a bigger model costs more for every single word. A Mixture-of-Experts layer replaces that one feed-forward network with many smaller ones, the experts, plus a tiny router that picks a few of them for each token. The model can then hold far more knowledge (all experts together) while each token only pays for the few experts it uses. The catches: all experts must sit in memory, and the router must not send everything to the same few experts. This lesson runs the lesson's router, then counts the real total and active parameters of Mixtral, Qwen3, gpt-oss and DeepSeek-V3 from their configuration files, times an MoE layer against dense layers on this page's CPU, and shows the bias trick DeepSeek-V3 uses to keep experts evenly loaded. Nothing is trained.

A dense transformer's FLOPs at inference equal its parameter count (times 2 for forward pass). Scale up a dense model and every token pays the full bill. By 2024 the frontier was hitting a compute wall: to be meaningfully smarter, you needed exponentially more FLOPs per token.

Mixture of Experts breaks this link. Replace each FFN with E independent experts + a router that picks k experts per token. Total parameters = E×FFN size. Active parameters per token = k×FFN size. Typical 2026 configuration: E=256, k=8. Storage scales with E, compute scales with k.

The 2026 frontier is largely MoE: DeepSeek-V3 (671B total / 37B active), Mixtral 8×22B, Qwen3's MoE models, Llama 4, Kimi K2, gpt-oss. Most of the strongest open-weights models on independent leaderboards are MoE.

The idea

Idea 1 · The FFN swap

Dense transformer block:

h = x + attn(norm(x))
h = h + FFN(norm(h))

MoE block:

h = x + attn(norm(x))
scores = router(norm(h))              # (N_tokens, E)
top_k = argmax_k(scores)              # pick k of E per token
h = h + sum_{e in top_k}(
        gate(scores[e]) * Expert_e(norm(h))
    )

Every expert is an independent FFN (typically SwiGLU). The router is a single linear layer. Each token picks its own k experts and gets a gated mixture of their outputs.

Idea 2 · The load-balancing problem

If the router puts 90% of tokens through expert 3, the other experts starve. Three fixes have been tried:

  1. Auxiliary load-balancing loss (Switch Transformer, Mixtral). Add a penalty proportional to the variance in expert usage. Works, but adds a hyperparameter and a second gradient signal.
  2. Expert capacity + token dropping (early Switch). Each expert processes at most C×N/E tokens; overflow tokens skip the layer. Hurts quality.
  3. Auxiliary-loss-free balancing (DeepSeek-V3). Add a learned per-expert bias that shifts the router's top-k selection. Bias is updated outside the training loss. No penalty on the main objective. 2024's big unlock.

DeepSeek-V3's approach: after each training step, for every expert, check if its usage is above or below the target. Nudge the bias by ±γ. Selection uses scores + bias. Expert probabilities used for gating are the raw scores unchanged. Decouples routing from expression.

Idea 3 · Shared experts

DeepSeek-V2/V3 also split experts into shared and routed. Every token passes through all shared experts. Routed experts are picked via top-k. Shared experts capture common knowledge; routed experts specialize. V3 runs 1 shared expert plus top-8 of 256 routed.

Idea 4 · Fine-grained experts

Classic MoE (GShard, Switch): each expert is as wide as a full FFN. E is small (8–64), k is small (1–2).

Modern fine-grained MoE (DeepSeek-V3, Qwen-MoE): each expert is narrower (1/8 FFN size). E is large (256+), k is larger (8+). Same total parameters, but combinations scale much faster. (8256​)≈400 trillion possible "experts" per token. Quality goes up, latency stays flat.

Idea 5 · The cost profile

Per token, per layer:

Config Active params / token Total params
Mixtral 8×22B ~39B 141B
Llama 3 70B (dense) 70B 70B
DeepSeek-V3 37B 671B
Kimi K2 (MoE) ~32B 1T

DeepSeek-V3 beats Llama 3 70B (dense) on almost every benchmark while doing fewer active FLOPs per token. More parameters = more knowledge. More active FLOPs = more compute per token. MoE decouples them.

Idea 6 · The catch: memory

All experts live on GPU regardless of which ones fire. A 671B model needs ~1.3 TB of VRAM for fp16 weights. Frontier MoE deployment requires expert parallelism — shard experts across GPUs, route tokens across the network. Latency is dominated by the all-to-all communication, not the matmul.

The same idea as a formula

The layer. For a token vector x, a router with weights Wr​ scores every expert, the top k are kept, and their outputs are mixed:

s=softmax(xWr​)∈RE,T=topk​(s),MoE(x)=e∈T∑​∑j∈T​sj​se​​FFNe​(x)

(DeepSeek-V3 uses sigmoid scores and adds always-on shared experts: MoE(x)=∑shared​FFNi​(x)+∑e∈T​ge​FFNe​(x).)

Storage against compute. With experts of width w in a model of width d, each SwiGLU expert has 3dw weights. Per MoE layer:

stored=E⋅3dw,used per token=k⋅3dw,sparsity=k/E

A model's active parameters are its total minus the unchosen experts: Nactive​=Ntotal​−LMoE​(E−k)⋅3dw. FLOPs per token follow Nactive​; memory follows Ntotal​.

Load balance. With T tokens, an expert's fair share is Tk/E. Switch Transformer's auxiliary loss is αE∑e​fe​Pe​, with fe​ the fraction of tokens routed to e and Pe​ the mean router probability for e; it is smallest when both are uniform. DeepSeek-V3 instead adds a bias be​ used only for choosing, T=topk​(s+b), while the gates still use s, and after each step moves be​←be​−γsign(loade​−Tk/E).

Combinatorics. Fine-grained routing picks one of (kE​) expert sets: (28​)=28 for Mixtral, (8256​)≈4×1014 for DeepSeek-V3.

Worked example
Mixtral 8×7B by hand

Configuration: 32 layers, d=4096, 8 experts of width 14,336, top-2, 32 query and 8 key/value heads of size 128, vocabulary 32,000.

  • One expert: $3 \times 4096 \times 14{,}336 = 176.2$M; eight per layer: 1.41B; 32 layers: 45.1B in experts.
  • Attention per layer: $2 \times 4096^2 + 2 \times 4096 \times 1024 = 41.9$M; 32 layers: 1.34B. Embeddings and head: $2 \times 32{,}000 \times 4096 = 0.26$B. Total: 46.7B.
  • Active per token: 2 of 8 experts, so subtract $32 \times 6 \times 176.2\text{M} = 33.8$B: 12.9B, about 28% of the total.
  • Memory: 46.7B in bf16 is 93 GB, the same as a dense 47B model; compute per token is that of a 13B model. The name "8×7B" overstates the size, because attention and embeddings are shared, not copied eight times.
Check your mental model
  • ✗ "An MoE with 8 experts is 8 separate models voting."
    ✓ Experts replace only the feed-forward layers; attention, embeddings and norms are shared, and routing is decided per token and per layer.
  • ✗ "Only the active parameters need GPU memory."
    ✓ Every expert must be loaded, since the next token may need any of them; MoEs save compute, not memory.
  • ✗ "Fewer FLOPs means proportionally faster."
    ✓ Gathering tokens per expert, small matrix products and (across GPUs) all-to-all communication add overhead; the CPU timing under "Use it" shows it.

Step 1 · the router

See code/main.py. A compact MoE layer in pure stdlib with:

  • n_experts=8 SwiGLU-ish experts (one linear each, for illustration)
  • top-k=2 routing
  • softmax-normalized gating weights
  • auxiliary-loss-free balancing via per-expert bias

code/main.rs is a Rust port with the same functions and demos. It uses only the standard library. The random numbers differ from Python's, but the printed conclusions are the same.

python3 code/main.py
rustc --edition 2021 -O code/main.rs -o /tmp/lesson && /tmp/lesson

def route(hidden, W_router, top_k, bias):
    scores = [sum(h * w for h, w in zip(hidden, W_router[e])) for e in range(len(W_router))]
    biased = [s + b for s, b in zip(scores, bias)]
    top_idx = sorted(range(len(biased)), key=lambda i: -biased[i])[:top_k]
    # softmax over ORIGINAL scores of the chosen experts
    chosen = [scores[i] for i in top_idx]
    m = max(chosen)
    exps = [math.exp(c - m) for c in chosen]
    s = sum(exps)
    gates = [e / s for e in exps]
    return top_idx, gates

Bias affects selection, not gate weight. That is the DeepSeek-V3 trick — bias corrects load imbalance without steering the model's predictions.

Step 2 · run 100 tokens through the router

Track which experts fire how often. Without the bias, usage is skewed. With a bias update loop (-γ for over-used experts, +γ for under-used), usage converges to a uniform distribution over a few iterations.

2026 production inference: vLLM supports MoE routing natively. SGLang has the fastest expert-parallel path. Both automatically handle top-k selection and expert parallelism.

When to pick MoE: - You want frontier quality at lower inference cost per token. - You have the VRAM / expert-parallel infrastructure. - Your workload is token-heavy (chat, code) not context-heavy (long docs).

When NOT to pick MoE: - Edge deployment — you pay full storage for any active FLOP. - Latency-critical single-user serving — expert routing adds overhead. - Small or on-device models — memory, not compute, is usually the limit there, and an MoE needs memory for all its experts.

import torch
from transformers import AutoConfig, AutoModelForCausalLM

# Count every parameter of real MoE models from their config.json (meta device: shapes only, no weights downloaded).
def moe_numbers(repo):
    cfg = AutoConfig.from_pretrained(repo)
    with torch.device("meta"):
        m = AutoModelForCausalLM.from_config(cfg)
    total = sum(p.numel() for p in m.parameters())
    E = getattr(cfg, "num_local_experts", None) or getattr(cfg, "n_routed_experts", None) or cfg.num_experts
    k = getattr(cfg, "num_experts_per_tok", None) or cfg.num_experts_per_token
    d = cfg.hidden_size
    width = getattr(cfg, "moe_intermediate_size", None) or cfg.intermediate_size
    first_dense = getattr(cfg, "first_k_dense_replace", 0)
    moe_layers = cfg.num_hidden_layers - first_dense
    per_expert = 3 * d * width                                 # gate, up and down matrices
    active = total - moe_layers * (E - k) * per_expert         # the unchosen experts do no work for this token
    return cfg, E, k, width, moe_layers, total, active

What sparsity buys on a CPU

Three feed-forward layers on 4,096 tokens of width 512, average of three runs on one CPU core: two dense SwiGLU layers and a top-4 MoE whose 32 experts together are as wide as the larger dense layer.

import time, torch, torch.nn.functional as F
torch.manual_seed(0)
torch.set_num_threads(1)                           # one core, so the timings are comparable from run to run

d, n = 512, 4096                                   # model width, tokens in the batch
X = torch.randn(n, d)

def swiglu(x, W1, W3, W2):
    return (F.silu(x @ W1) * (x @ W3)) @ W2

def make(width, count):
    s = d ** -0.5
    return [(torch.randn(d, width) * s, torch.randn(d, width) * s, torch.randn(width, d) * s) for _ in range(count)]

def moe(x, experts, router, k):
    probs = (x @ router).softmax(-1)
    gate, idx = probs.topk(k, dim=-1)               # (n, k)
    gate = gate / gate.sum(-1, keepdim=True)
    out = torch.zeros_like(x)
    for e, W in enumerate(experts):                 # gather the tokens sent to expert e, run it once, scatter back
        rows, slot = (idx == e).nonzero(as_tuple=True)
        if len(rows):
            out.index_add_(0, rows, gate[rows, slot, None] * swiglu(x[rows], *W))
    return out, idx

def timed(f):
    f(); t = time.perf_counter()
    for _ in range(3): f()
    return (time.perf_counter() - t) / 3 * 1000

dense_small = make(1024, 1)[0]                      # dense FFN, width 1024
dense_big = make(8192, 1)[0]                        # dense FFN with as many weights as the MoE below
experts = make(256, 32)                             # 32 narrow experts of width 256: 8 x 1024 = 8192 in total
router = torch.randn(d, 32) * 0.02
with torch.no_grad():
    t_small = timed(lambda: swiglu(X, *dense_small))
    t_big = timed(lambda: swiglu(X, *dense_big))
    t_moe = timed(lambda: moe(X, experts, router, 4))
    _, idx = moe(X, experts, router, 4)
load = torch.bincount(idx.flatten(), minlength=32)
weights = lambda ws: sum(w.numel() for W in ws for w in W)
print(f"{'layer':42s} {'weights':>9} {'active per token':>17} {'time, 4096 tokens':>18}")
print(f"{'dense SwiGLU, width 1024':42s} {weights([dense_small]) / 1e6:8.1f}M {weights([dense_small]) / 1e6:16.1f}M {t_small:15.1f} ms")
print(f"{'dense SwiGLU, width 8192':42s} {weights([dense_big]) / 1e6:8.1f}M {weights([dense_big]) / 1e6:16.1f}M {t_big:15.1f} ms")
print(f"{'MoE: 32 experts of width 256, top-4':42s} {weights(experts) / 1e6:8.1f}M {4 * weights(experts[:1]) / 1e6:16.1f}M {t_moe:15.1f} ms")
print(f"\ntokens per expert with a random router (ideal {n * 4 // 32}): min {load.min().item()}, max {load.max().item()}")

The MoE stores as many weights as the wide dense layer (12.6M) but runs in about 150 ms, roughly seven times faster than the wide layer's 1,000 ms; its active weights per token equal the narrow layer's (1.6M), yet it takes about 1.5 times as long as that layer's 100 ms (all on one CPU core, so the timings are stable). The extra time is routing overhead: computing the router, finding which tokens go to each of 32 experts, running 32 small matrix products instead of one big one, and adding the results back. On GPUs, fused MoE kernels shrink this overhead, and across GPUs the all-to-all exchange of tokens between devices adds its own. The load line shows that even a random router spreads tokens unevenly (447 to 595 against 512), and a trained one can be far worse.

Keeping the experts busy, DeepSeek-V3's way

A router that starts skewed (some experts favoured), 8,192 tokens from six topics, 16 experts, top-2 with sigmoid scores. After each step every expert's bias moves by ±γ towards its fair share; the bias changes which experts are chosen, never the gate values.

import numpy as np

rng = np.random.default_rng(0)
E, k, d, n = 16, 2, 64, 8192
# Tokens come from a few topics, and the router starts biased towards some experts, as it often is early in training.
centres = rng.standard_normal((6, d))
X = centres[rng.integers(0, 6, n)] + 0.5 * rng.standard_normal((n, d))
W = rng.standard_normal((d, E)) * 0.05 + np.linspace(0, 0.08, E)[None, :]
scores = 1 / (1 + np.exp(-(X @ W)))                  # DeepSeek-V3 uses sigmoid affinities
target = n * k / E

def route(bias):
    chosen = np.argsort(-(scores + bias), axis=1)[:, :k]      # the bias only changes WHICH experts are chosen
    g = np.take_along_axis(scores, chosen, 1)
    return chosen, g / g.sum(1, keepdims=True)                 # gate values use the raw scores
for gamma in (0.001, 0.02):
    bias = np.zeros(E)
    print(f"bias step gamma = {gamma}")
    for it in range(301):
        chosen, gates = route(bias)
        load = np.bincount(chosen.ravel(), minlength=E)
        if it in (0, 10, 50, 100, 300):
            print(f"  step {it:3d}: busiest expert {load.max() / target:4.2f}x the even share, idlest {load.min() / target:4.2f}x")
        bias -= gamma * np.sign(load - target)                  # over-used experts become less attractive

Reading this output

At the start the skewed router sends 1.82 times its share to the busiest expert and only 9% of its share to the idlest. With a small step, γ=0.001, the biases creep towards balance: by step 100 every expert is within 2% of its fair share and stays there. With γ=0.02 the correction overshoots and the loads freeze in a cycle with the busiest expert still at 1.49 times its share, the same failure as the lesson's demo above. DeepSeek-V3 used a small γ (0.001) for most of its training. Because the bias only reorders the candidates, the gate values that weight the chosen experts' outputs are still the router's raw scores.

Break it on purpose

In the lesson's route, compute the gates from the biased scores (biased[i]) instead of the raw scores[i]. Balance still improves and nothing crashes. What has changed about what the model computes, and why did DeepSeek-V3 keep the two apart? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Open frontier models are MoE. DeepSeek-V3 and R1, Qwen3's MoE models (for example Qwen3-30B-A3B and Qwen3-235B-A22B), Llama 4, Kimi K2 and OpenAI's gpt-oss all route each token to a few of many experts.
  • Serving engines handle the routing. vLLM, SGLang and TensorRT-LLM ship fused MoE kernels and expert parallelism; llama.cpp can keep experts in CPU memory and the shared layers on the GPU, which makes models like Qwen3-30B-A3B usable on consumer hardware.
  • Low-precision experts. gpt-oss ships its experts in 4-bit MXFP4 and DeepSeek-V3 was trained in FP8, because expert weights dominate memory.

Sources: DeepSeek-V3 report, Qwen3 blog, gpt-oss model card, vLLM, Kimi K2.

Recap
What to keep from this lesson
  • An MoE layer swaps one FFN for E experts and a router; each token uses k of them.
  • Memory follows total parameters, FLOPs follow active ones: Mixtral 46.7B/12.9B, DeepSeek-V3 671B/37.6B.
  • Routing must be balanced: auxiliary losses, capacity limits, or DeepSeek-V3's selection-only bias with a small step.
  • Sparse compute is not free: gather and scatter overhead on one device, all-to-all traffic across many.

Practice problem · Top-k MoE gating and the Switch load-balancing loss

From the source repository: write the function, then press "Run the checks". They run as real Python in your browser (the first run loads Python, about 10 MB) and tell you which part is wrong and why. Hints open one at a time; the reference solution opens when every check passes.

medium30 minresearch

A mixture of experts layer sends each token to a few experts out of many. A router gives one logit for each expert. The layer keeps the top k experts and mixes their outputs with gate weights. The Switch Transformer paper adds an auxiliary loss so that the router spreads the tokens over all experts.

Task

Write two functions.

  1. route(logits, top_k) returns the chosen experts and their gates for each token.
  2. load_balancing_loss(logits, top_k) returns the auxiliary load-balancing loss as a float.

Routing. For each token, sort the experts by logit, largest first. Keep the first k experts. When two logits are equal, the expert with the lower index comes first. The gates are a softmax over the k chosen logits only:

gt,j​=∑i∈top-k(t)​exp(zt,i​)exp(zt,j​)​

This is the same as the full softmax over all E experts, renormalized over the k chosen experts. The gates of a token sum to 1. Column j of the gates belongs to the expert in column j of top_idx.

Load-balancing loss. Let T be the number of tokens and E the number of experts.

  • fi​ is the fraction of the Tk assignments that go to expert i: the number of tokens that have i in their top k, divided by Tk.
  • Pi​=T1​∑t​pt,i​, where pt​ is the full softmax of the logits of token t over all E experts.
  • The loss is L=E∑i=1E​fi​Pi​.

With k=1 this is the loss of the paper. The loss is 1 when the router is uniform. It grows toward E when all tokens go to one expert.

Input and output

Name Type Shape Meaning
logits float array (T, E) the router logit of each token for each expert
top_k int the number of experts for each token
  • route returns a tuple (top_idx, gates).
  • top_idx is an int array of shape (T, top_k). Row t holds the chosen expert indices, largest logit first.
  • gates is a float array of shape (T, top_k).
  • load_balancing_loss returns a Python float.

Constraints

  • Do not change the input array.
  • Use numpy only.

Your code
Common mistakes the checks catch
  • Computes f_i from the mean softmax probability, not from the dispatch counts.
  • Divides the counts by T, not by T times k, so the loss grows with k.
  • Forgets the factor E in front of the sum, so a uniform router gives 1 / E.
  • Calls np.exp on the raw logits, so large logits overflow to infinity.
  • Uses the full softmax probabilities of the chosen experts as gates without renormalization.
  • Sorts the logits ascending and reverses the order, so ties go to the higher expert index.
Hint 1

Negate the logits and sort them with np.argsort. Use kind="stable" so that equal logits keep the order of their indices.

Hint 2

np.take_along_axis(logits, top_idx, axis=-1) gives the logits of the chosen experts with shape (T, k). Apply a softmax over the last axis of that array.

Hint 3

Subtract the row maximum before np.exp. The gates do not change, and np.exp cannot overflow.

Hint 4

For f, count each expert in the flattened top_idx with np.bincount and minlength=E. Divide the counts by Tk. For P, take the mean over tokens of the full softmax. The loss is E times the dot product of f and P.

Reference solution and notes
import numpy as np


def softmax(x):
    shifted = x - np.max(x, axis=-1, keepdims=True)
    exps = np.exp(shifted)
    return exps / np.sum(exps, axis=-1, keepdims=True)


def route(logits, top_k):
    order = np.argsort(-logits, axis=-1, kind="stable")
    top_idx = order[:, :top_k]
    chosen = np.take_along_axis(logits, top_idx, axis=-1)
    gates = softmax(chosen)
    return top_idx, gates


def load_balancing_loss(logits, top_k):
    T, E = logits.shape
    top_idx, _ = route(logits, top_k)
    counts = np.bincount(top_idx.reshape(-1), minlength=E)
    f = counts / (T * top_k)
    P = np.mean(softmax(logits), axis=0)
    return float(E * np.sum(f * P))

Why the loss has two factors

fi​ counts the tokens that the router really sends to expert i. A count has no gradient. Pi​ is the mean router probability, and it does have a gradient. The product fi​Pi​ lets the count choose the direction and the probability carry the gradient. An expert with many tokens gets a large fi​, so the gradient pushes its probability down.

Why the minimum is 1

When the dispatch is uniform, every fi​ is 1/E, and the loss is the sum of Pi​, which is 1. The factor E keeps this value at 1 for any number of experts. The paper scales the loss by a small coefficient, for example 0.01, and adds it to the main loss.

Gates and ties

The gates use only the chosen logits. This is the same as the full softmax divided by the probability mass of the chosen experts. A fixed tie rule makes the routing deterministic. Without it, two runs can send the same token to different experts.

Where this goes next

The lesson replaces the auxiliary loss with a per-expert bias that changes only the selection, as in DeepSeek-V3. The bias moves the top k choice, but the gates still come from the original logits. The DeepSeek-V3 lesson in phase 10 shows this design at full scale.

Solutions

SolutionP1 · Close to the narrow one, with overhead

Close to the narrow one, but not equal: about 150 ms against 100 ms for the narrow dense layer and about 1,000 ms for the wide one (one CPU core). The MoE does the multiply-adds of a width-1,024 layer per token (4 experts of width 256) while storing as many weights as the width-8,192 layer, so most of the wide layer's cost disappears. The remaining gap to the narrow layer is the price of sparsity: the router, sorting tokens by expert, 32 small matrix products and scattering the results back.

SolutionB1 · The bias leaks into the output

With gates from the biased scores, the balancing bias now changes how much each chosen expert contributes to the output, not only which experts are chosen. An expert that is under-used gets a positive bias, so whenever it is picked its output is weighted up, regardless of whether it fits the token. The load statistics, a bookkeeping signal, then shape the model's predictions, and the bias drifts with the batch mix, so the same token can be treated differently from batch to batch. DeepSeek-V3 keeps the bias for selection only so that balancing never alters the function the gates compute, which is why it needs no auxiliary loss on the main objective.
