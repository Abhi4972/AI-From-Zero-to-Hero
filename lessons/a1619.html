In plain words first
The idea in one line

Bio-inspired optimization is making an LLM comeback. LMPSO (arXiv:2504.09247) uses PSO where each particle's velocity is a prompt and the LLM generates the next candidate; works well on structured outputs (tours, math expressions, programs). Model Swarms (arXiv:2410.11163) treats each LLM expert as a PSO particle on a model-weight manifold and reports a 13.3% average gain over the strongest of 12 baselines on 9 datasets, with as few as 200 examples. SwarmPrompt (ICAART 2025) hybridizes PSO + Grey Wolf for prompt optimization. AMRO-S (arXiv:2603.12933) uses ACO-style pheromones for multi-agent LLM routing — interpretable routing evidence, a quality-gated asynchronous update that decouples inference from learning, and a 4.7x wall-clock speedup when concurrency rises from 20 to 1,000 processes. This lesson implements PSO on prompt parameter space and ACO on agent routing, measures why these classical algorithms fit the LLM era, and when they do not.

Problem

In plain words first

Particle swarm optimisation (PSO) searches by moving a population of candidate solutions toward the best ones found so far, using only a score, no gradients. Ant colony optimisation (ACO) learns which routes work by leaving "pheromone" on good choices and letting it fade over time. Both suit LLM systems where you can score an output but cannot differentiate it. There is no Zero to Agents chapter on this; it builds on Lesson 16.9 (parallel swarms). This lesson compares the lesson's PSO and router with simple baselines, then runs PSO on a real model's sampling settings.

You have a prompt that scores 62% on your task eval. You want to improve it. The naive move is gradient-free manual tweaking, which scales badly. Reinforcement learning needs reward signals and enough rollouts to train. Backprop through prompts is not really possible — the prompt is a discrete string, not a differentiable parameter.

Classical bio-inspired optimization — PSO for continuous search spaces, ACO for path selection — was designed exactly for this regime: gradient-free, population-based, cheap per evaluation. Pair them with LLMs for the gradient-free search step, and you get a surprisingly practical optimizer.

The same patterns apply to agent routing in multi-agent systems. An ACO-style pheromone trail records which agent worked best on which task-type, lets the router exploit the trail, and decays pheromones so routes can be rediscovered.

Concept

PSO refresher (Kennedy & Eberhart 1995)

Particle Swarm Optimization: population of particles in a continuous search space. Each particle has position x_i and velocity v_i. Each iteration:

v_i <- w * v_i + c1 * r1 * (p_best_i - x_i) + c2 * r2 * (g_best - x_i)
x_i <- x_i + v_i
evaluate fitness(x_i)
update p_best_i if improved
update g_best if global best

Where p_best is particle's own best, g_best is swarm's best, w, c1, c2 are inertia + cognitive + social weights, r1, r2 are random factors.

PSO on LLM outputs — LMPSO

arXiv:2504.09247 (Shinohara et al.) adapts PSO for LLM-generated structured outputs: travelling-salesman tours, Python heuristics and symbolic-regression expressions. Each particle is a candidate output. Velocity is a prompt that describes how to modify the current output toward the personal/global best. The LLM generates the new output from the velocity prompt. The "inertia" of the velocity is a prompt like "make small incremental changes."

This works well when: - The output is structured (parseable, evaluable). - Fitness is automatic (test runs, arithmetic evaluation). - Population is small (~10-30 particles) so total LLM calls stay manageable.

It does not work well when fitness needs human review — the per-iteration cost becomes prohibitive.

Model Swarms

arXiv:2410.11163 (Feng et al., ICML 2025) takes PSO off the output layer and into the model layer. Each "particle" is an expert LLM, located by its weights. The swarm moves the weights toward the collective best via a gradient-free update. Reported: 13.3% average gain over the second-strongest of 12 composition baselines on 9 datasets, working with as few as 200 examples.

The key insight is that expert models fine-tuned from one base model sit near each other in weight space, so moving and combining them (the paper uses LoRA-adapted experts) stays cheap and effective.

ACO refresher (Dorigo 1992)

Ant Colony Optimization: ants traverse a graph; each path has a pheromone trail. Ant move probabilities weight by pheromone strength. Ants that complete the task deposit pheromone proportional to solution quality. Pheromone decays over time.

AMRO-S — ACO for agent routing

arXiv:2603.12933 uses ACO for multi-agent routing. It treats routing as choosing a path through a layered graph of agents; each task type keeps its own pheromone matrix over stage-to-stage transitions, and a query's task mixture blends the matrices. Pheromones strengthen paths that produce good outputs. Key contributions:

  • Interpretable routing evidence. Pheromone strength is a human-readable signal.
  • Quality-gated asynchronous update. A small sample of requests goes into a buffer off the serving path; an LLM judge gives each trajectory a pass or fail, and only passing ones reinforce pheromones, so learning never adds serving latency.
  • Scales under load. The same workload ran 4.7x faster in wall-clock time at 1,000 concurrent processes than at 20, with GSM8K accuracy steady at about 96%; across five benchmarks it averaged 87.83 against 85.93 for the strongest routing baseline.

The quality gate matters: without it, fast-but-wrong agents accrue pheromone, and the system locks in on bad routes.

When to use PSO / ACO for LLMs

Use PSO when: - Search space is continuous or maps to continuous parameters (prompt embeddings, LoRA weights, numeric generation parameters). - Fitness is cheap and automatic. - Population can be small (10-30).

Use ACO when: - You have a routing or path-selection problem. - Decisions reinforce over time (the same task types come back). - You need interpretable evidence for routing decisions.

Do not use either when: - Fitness requires human review (too expensive per iteration). - The search space is discrete and combinatorial in a way that PSO does not cover (use genetic algorithms instead). - Real-time decisions need strict latency (PSO/ACO converge slowly relative to single-pass heuristics).

Why bio-inspired still wins

Gradient-based methods need differentiable signals. LLM outputs and routing decisions are not trivially differentiable. Pseudo-gradient methods (reinforcement-learned routers, DPO-style prompt tuners) work but need expensive training.

PSO and ACO need only an evaluator function. If you can score a candidate output or a routing decision, you can optimize over the space. That makes the bar for applicability much lower.

Practical limits

  • Population budget. N particles × T iterations × per-eval cost. For LLM evals at ~$0.02 / call, a 20-particle PSO running 50 iterations costs ~$20. Plan accordingly.
  • Exploration vs exploitation. Pheromone decay rate and PSO inertia trade off; too fast decay → forget solutions; too slow → stuck on early local optima.
  • Catastrophic drift. Both algorithms can converge and then diverge if fitness landscape shifts (new data distribution). Monitor best-fitness stability.

The same idea as a formula

PSO update. For particle i with position xi​, velocity vi​, its best pi​ and the swarm's best g:

vi​←wvi​+c1​r1​(pi​−xi​)+c2​r2​(g−xi​),xi​←xi​+vi​,
with r1​,r2​ uniform in [0,1]. The lesson uses w=0.6 and c1​=c2​=1.2.

Pheromone update. For task type t and agent a, every deposit first decays all entries, τt,a​←(1−ρ)τt,a​, then adds Δq to the chosen agent if quality q passes the gate. The router picks a with probability τt,a​/∑b​τt,b​.

Noisy fitness. If fitness is an accuracy on n questions, it moves in steps of 1/n and has standard error about p(1−p)/n​. With n=8 and p=0.5 that is 0.18, larger than most differences a search could find.

TT = ["code", "math", "writing", "planning"]; AG = list(AGENT_TASK_AFFINITY)
def run(router_kind, n=200, seed=0, drift_at=None, affinity=None, state=None):
    rng = random.Random(seed); total, log = 0.0, []
    router = state or (PheromoneRouter(TT, AG) if router_kind == "aco" else
                       {t: {a: [0.0, 0] for a in AG} for t in TT})
    for i in range(n):
        tt = TT[i % 4]
        if router_kind == "aco":
            a = router.choose(tt, rng)
        elif router_kind == "oracle":
            a = max(AG, key=lambda x: main.AGENT_TASK_AFFINITY[x][tt])
        else:                                      # epsilon-greedy bandit on mean quality, eps = 0.1
            stats = router[tt]
            a = rng.choice(AG) if rng.random() < 0.1 or any(s[1] == 0 for s in stats.values()) else \
                max(AG, key=lambda x: stats[x][0] / stats[x][1])
        q = simulate_task(a, tt, rng); total += q; log.append((tt, a))
        if router_kind == "aco":
            router.deposit(tt, a, q)
        elif router_kind == "bandit":
            router[tt][a][0] += q; router[tt][a][1] += 1
    return total / n, router, log
for kind in ("oracle", "aco", "bandit"):
    print(f"   {kind:7s} mean quality {run(kind)[0]:.3f}")

# random search get the same 16 evaluations; then each winner is re-tested on 16 new questions, next to
# greedy decoding. About 2 minutes on CPU.
import os, re, random, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def answer(a, b, temp, top_p, seed):
    ids = tok.apply_chat_template([{"role": "user", "content": f"What is {a} times {b}? Reply with only the number."}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    torch.manual_seed(seed)
    with torch.no_grad():
        kw = dict(do_sample=False) if temp is None else dict(do_sample=True, temperature=temp, top_p=top_p, top_k=0)
        out = llm.generate(ids, max_new_tokens=8, **kw)
    m = re.search(r"\d+", tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).replace(",", ""))
    return int(m.group()) if m else None

rng = random.Random(11)
TRAIN = [(rng.randint(12, 49), rng.randint(12, 49)) for _ in range(8)]
TEST = [(rng.randint(12, 49), rng.randint(12, 49)) for _ in range(16)]
calls = [0]; seen = []
def fit(x, qs=TRAIN):
    calls[0] += 1
    t, p = 0.05 + 1.45 * x[0], 0.3 + 0.7 * x[1]
    f = sum(answer(a, b, t, p, seed=1000 * calls[0] + i) == a * b for i, (a, b) in enumerate(qs)) / len(qs)
    seen.append(f)
    return f

Part 1 of 4 · Particle, fitness, run_lmpso

"""PSO for LLM parameter optimization and ACO for agent routing, stdlib only.

PSO runs on a 2D parameter space (temperature, top_k_weight) with a scripted
fitness proxy. AMRO-S simulates 3 agents handling 4 task types with a
pheromone matrix that strengthens on quality, decays over time.
"""
from __future__ import annotations

import math
import random
from dataclasses import dataclass, field


# ---------- LMPSO ----------

@dataclass
class Particle:
    x: list[float]
    v: list[float]
    p_best: list[float]
    p_best_fit: float


def fitness(x: list[float]) -> float:
    """Rastrigin-style fitness: narrow peak at (0.72, 0.40) with ripples.
    Chosen to be harder than a plain bowl so PSO convergence is visible."""
    cx, cy = 0.72, 0.40
    dx, dy = x[0] - cx, x[1] - cy
    dist2 = dx * dx + dy * dy
    ripple = 0.08 * (math.cos(8 * math.pi * dx) + math.cos(8 * math.pi * dy))
    return max(0.0, 1.0 - 6.0 * dist2 - ripple)


def run_lmpso(n_particles: int = 20, iterations: int = 30, seed: int = 0) -> list[float]:
    rng = random.Random(seed)
    w, c1, c2 = 0.6, 1.2, 1.2
    bounds = ((0.0, 1.0), (0.0, 1.0))

    particles: list[Particle] = []
    for _ in range(n_particles):
        x = [rng.uniform(*bounds[0]), rng.uniform(*bounds[1])]
        v = [rng.uniform(-0.1, 0.1), rng.uniform(-0.1, 0.1)]
        f = fitness(x)
        particles.append(Particle(x=list(x), v=v, p_best=list(x), p_best_fit=f))

    g_best = max(particles, key=lambda p: p.p_best_fit)
    g_best_x = list(g_best.p_best)
    g_best_fit = g_best.p_best_fit

    history: list[float] = [g_best_fit]

    for _ in range(iterations):
        for p in particles:
            r1, r2 = rng.random(), rng.random()
            for d in range(2):
                cognitive = c1 * r1 * (p.p_best[d] - p.x[d])
                social = c2 * r2 * (g_best_x[d] - p.x[d])
                p.v[d] = w * p.v[d] + cognitive + social
                p.x[d] += p.v[d]
                p.x[d] = max(bounds[d][0], min(bounds[d][1], p.x[d]))
            f = fitness(p.x)
            if f > p.p_best_fit:
                p.p_best = list(p.x)
                p.p_best_fit = f
                if f > g_best_fit:
                    g_best_x = list(p.x)
                    g_best_fit = f
        history.append(g_best_fit)

    return history

class PheromoneRouter:
    def __init__(self, task_types: list[str], agents: list[str],
                 decay: float = 0.05, reinforce: float = 0.2,
                 quality_threshold: float = 0.6) -> None:
        self.task_types = task_types
        self.agents = agents
        self.decay = decay
        self.reinforce = reinforce
        self.quality_threshold = quality_threshold
        self.pheromones = {t: {a: 1.0 for a in agents} for t in task_types}

    def choose(self, task_type: str, rng: random.Random) -> str:
        table = self.pheromones[task_type]
        total = sum(table.values())
        r = rng.random() * total
        upto = 0.0
        for a, p in table.items():
            upto += p
            if r <= upto:
                return a
        return self.agents[-1]

    def deposit(self, task_type: str, agent: str, quality: float) -> None:
        for a in self.agents:
            self.pheromones[task_type][a] *= (1.0 - self.decay)
        if quality >= self.quality_threshold:
            self.pheromones[task_type][agent] += self.reinforce * quality


AGENT_TASK_AFFINITY = {
    "coder": {"code": 0.9, "math": 0.5, "writing": 0.3, "planning": 0.4},
    "mathematician": {"code": 0.4, "math": 0.95, "writing": 0.2, "planning": 0.5},
    "writer": {"code": 0.2, "math": 0.2, "writing": 0.9, "planning": 0.6},
}


def simulate_task(agent: str, task_type: str, rng: random.Random) -> float:
    base = AGENT_TASK_AFFINITY[agent][task_type]
    return max(0.0, min(1.0, base + rng.uniform(-0.15, 0.15)))


def run_amro_s(n_tasks: int = 200, seed: int = 0) -> tuple[float, float, PheromoneRouter]:
    rng = random.Random(seed)
    task_types = ["code", "math", "writing", "planning"]
    agents = list(AGENT_TASK_AFFINITY.keys())

    router = PheromoneRouter(task_types, agents)
    random_router_quality = 0.0
    aco_quality = 0.0

    for i in range(n_tasks):
        tt = task_types[i % len(task_types)]

        # Random baseline
        rand_agent = rng.choice(agents)
        rq = simulate_task(rand_agent, tt, rng)
        random_router_quality += rq

        # ACO router
        aco_agent = router.choose(tt, rng)
        aq = simulate_task(aco_agent, tt, rng)
        aco_quality += aq
        router.deposit(tt, aco_agent, aq)

    return random_router_quality / n_tasks, aco_quality / n_tasks, router


def print_pheromone_table(router: PheromoneRouter) -> None:
    print(f"  {'task_type':12s} " + " ".join(f"{a:>14s}" for a in router.agents))
    for tt in router.task_types:
        row = [f"{router.pheromones[tt][a]:>14.3f}" for a in router.agents]
        print(f"  {tt:12s} " + " ".join(row))

Break it on purpose

Your team runs PSO over prompt templates for a support bot, scoring each candidate on 20 tickets judged by an LLM. After 40 iterations the best template scores 0.85 against the old one's 0.70, and it ships. A week later, live satisfaction is unchanged. The team also uses an ACO router whose pheromones have not shifted since launch, although one agent's model was upgraded. Using this lesson, what went wrong in both cases? (Solution B1.)

Industry practice
What's current (2024–2026)
  • LLMs as the search operator. LMPSO and related work use the model to propose the next candidate, not just to be scored, for structured outputs such as tours, programs and formulas.
  • Swarms over weights. Model Swarms (ICML 2025) moves LoRA-adapted experts through weight space with PSO-style updates and needs only about 200 validation examples.
  • Routing learned off the serving path. AMRO-S updates pheromones asynchronously from judged samples, so learning never slows requests.
  • On your laptop: before running PSO, measure how noisy your fitness is and compare against random search with the same budget; with a small model and a small eval set, the noise swamps the search.

Sources: Shinohara et al., LMPSO (arXiv:2504.09247), Feng et al., Model Swarms (arXiv:2410.11163), AMRO-S (arXiv:2603.12933), SwarmPrompt (ICAART 2025).

Recap
What to keep from this lesson
  • PSO and ACO need only a score, which suits LLM outputs and routing decisions.
  • Always compare against random search and a simple bandit with the same budget.
  • Noisy fitness makes the "best" candidate look better than it is; re-test winners on fresh data.
  • Pheromone routing keeps a little exploration and adapts to change; watch that it does not fade to zero.
  • Read benchmark numbers carefully: a speedup or a gain is always relative to something.

Ship it

  • Start small. 10-20 particles, 20-50 iterations. Scale up only if the convergence curve shows clear gain.
  • Log pheromones or g_best per iteration. Debugging swarm optimizers without a trail is painful.
  • Quality-gate updates. Especially for ACO routing: fast-and-wrong agents must not accrue pheromone.
  • Reset decay on distribution shift. When your eval distribution changes, aged pheromones are stale; reset or double the decay rate temporarily.
  • Cap the per-iteration cost. Emit a cost-per-iteration metric. PSO that costs $500 / iteration and gains 0.5% is not shippable.

Given an LLM or agent optimization problem, choose the right optimizer.

Produce:

1. **Problem fingerprint.** Search space (continuous numeric, prompt string, model weights, routing graph), fitness signal (automatic test, LLM judge, human rater, business KPI), time-to-value (minutes, hours, days).
2. **Optimizer choice.** PSO, ACO, genetic algorithm, DPO/RL, manual tuning. Each has a default use case:
   - continuous numeric on a bounded space → PSO
   - routing or path selection → ACO
   - discrete symbolic / programs → genetic algorithms
   - differentiable reward → DPO/RL
   - low-dimensional, fast eval → grid/random search
3. **Population sizing.** 10-30 for PSO/GA, pheromone matrix size for ACO. Budget calculation: N × T × cost-per-eval. Do not run swarms that cost more than the value they produce.
4. **Fitness + quality gate.** What function scores a candidate? For ACO routing, what quality threshold triggers pheromone deposit?
5. **Convergence monitoring.** Log g_best or pheromone stability per iteration. Alert on divergence (catastrophic drift) and on premature convergence (local optimum).
6. **Decay / exploration tuning.** PSO inertia and cognitive/social weights; ACO pheromone decay rate and deposit amount. Trade-off: low decay → stuck on early winner; high decay → no memory.
7. **Reset conditions.** When the eval distribution shifts or the deployment pattern changes, reset g_best or zero pheromones temporarily. Stale memories are worse than no memories.

Hard rejects:

- Swarm optimizers on tasks where fitness needs human review. Cost-per-iteration dwarfs budget.
- Population sizes > 50 without a clear budget justification. Diminishing returns dominate.
- Pheromone routing without a quality gate. Fast-but-wrong agents lock in.
- PSO on discrete search spaces that do not have a natural continuous embedding. Use GA or simulated annealing instead.

Refusal rules:

- If the user is trying to optimize something with no clear fitness function, recommend defining fitness first. Swarm optimizers cannot help without an evaluator.
- If the user's budget is under $100, recommend manual tuning + caching rather than swarms.
- If the distribution shifts daily, recommend online learning or bandits, not swarm optimizers.

Output: a one-page brief. Start with a one-sentence recommendation ("Use ACO with quality-gated pheromone deposits on a 3-agent × 4-task-type routing problem. Decay 0.05, threshold 0.6, 200 warmup tasks."), then the seven sections above. End with a budget estimate and a 1-week rollout plan.

Solutions

SolutionP1 · Within about 0.003

Within about 0.003. In the run, random search with 620 calls reached 1.0062 on average over 20 seeds (worst 0.9943), against PSO's 1.0094. The landscape is two-dimensional and smooth apart from a ripple, so 620 random points almost always land near the peak. PSO's advantage shows on harder, higher-dimensional problems, which is why the comparison is worth running every time.

SolutionB1 · A noisy winner and a stuck router

The PSO winner. Twenty tickets give a score with a standard error of about 0.1, and after 40 iterations of picking the maximum, the best score is inflated by that noise; an LLM judge adds its own. The 0.85 was the luckiest of many draws. Re-scoring the winner and the old template on a fresh, larger set, with human spot checks, would have shown little difference.

The router. After launch the pheromones for the upgraded agent's task types had faded to near zero for everyone but the incumbents, so the router rarely tried the new model, and the quality gate only rewards what it tries. - Keep a floor on exploration, or reset or raise decay when an agent changes. - Log pheromones per task type, and alert when a row has not moved for weeks. - Compare the router against a fixed best choice and a bandit on the same traffic.
