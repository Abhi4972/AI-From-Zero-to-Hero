In plain words first
The idea in one line

Shared-conversation orchestration puts N agents in one conversation; a selector function (LLM, round-robin, or custom) picks who speaks next. This is the archetype of emergent multi-agent conversation — agents do not know their role in a static graph, they just react to the shared pool. AutoGen GroupChat and AG2 GroupChat are the reference implementations: AutoGen v0.2's GroupChat semantics were preserved in the AG2 fork; AutoGen v0.4 rewrote it as an event-driven actor model. Microsoft announced Microsoft Agent Framework in October 2025 as the successor to AutoGen and Semantic Kernel, put AutoGen into maintenance, shipped a release candidate in February 2026 and version 1.0 on April 3, 2026. The GroupChat primitive survives in both AG2 and Microsoft Agent Framework — learn it once, use it everywhere.

Terms you'll hear
Term What people say What it actually means
GroupChat "Agents in one chat room" Shared message pool + selector function. AutoGen / AG2 primitive.
Speaker selection "Who talks next" The function that picks the next agent. Round-robin, LLM-selected, or custom.
GroupChatManager "The meeting host" AutoGen component that owns the selector and loops over turns.
ConversableAgent "The base agent" AutoGen base class; an agent that can send and receive messages.
Termination token "The 'stop' word" Sentinel string (usually TERMINATE) that ends the chat.
Hot speaker "One agent dominates" Failure mode where the selector keeps picking the same agent.

Projection "Scoped view" Role-specific view into the shared pool to prevent context bloat.

Problem

In plain words first

In a group chat, several agents share one conversation and a selector decides who speaks next: in turn (round-robin), by rules, or by asking a model. The chat stops when someone says a stop word such as TERMINATE, or after a set number of turns. Microsoft Agent Framework, which carries this pattern on from AutoGen, is covered in Lesson 14.85 (linked above). This lesson checks what the lesson's chat actually ships, adds a safer stop rule, and lets a small model be the selector.

Static graphs (LangGraph) are great when the workflow is known. Real conversations are not static: sometimes the coder asks the reviewer, sometimes the researcher, sometimes the writer. Hardcoding every possible handoff produces an edge explosion. You want agents reacting to a shared pool, with some function deciding who talks next.

That is exactly what AutoGen GroupChat does.

Concept

The shape

              ┌─── shared pool ────┐
              │   m1  m2  m3  ...  │
              └─────────┬──────────┘
                        │ (everyone reads all)
      ┌───────┬─────────┼─────────┬───────┐
      ▼       ▼         ▼         ▼       ▼
    Agent A  Agent B  Agent C  Agent D  Selector
                                           │
                                           ▼
                                  "next speaker = C"

Every agent sees every message. A selector function is invoked at each turn to pick who speaks next.

The three selector flavors

Round-robin. Fixed cycle. Deterministic. Scales linearly in N but ignores context — a coder gets the turn even when the topic is legal review.

LLM-selected. A call to an LLM that reads the recent pool and returns the best next speaker. Context-aware but slow: every turn adds an LLM call. AutoGen's default.

Custom. A Python function with whatever logic you want. Typical: LLM-selected with fallback rules (e.g., "always give the verifier the turn after the coder").

The ConversableAgent API

agent = ConversableAgent(
    name="coder",
    system_message="You write Python.",
    llm_config={...},
)
chat = GroupChat(agents=[coder, reviewer, tester], messages=[])
manager = GroupChatManager(groupchat=chat, llm_config={...})

GroupChatManager holds the selector. When an agent completes a turn, the manager calls the selector, which returns the next agent. Loop continues until a termination condition.

Termination

Three common patterns:

  • Max rounds. Hard cap on total turns.
  • "TERMINATE" token. Agents can emit a sentinel message; the manager stops when one appears.
  • Goal-reached check. A lightweight verifier runs each turn and stops the chat when done.

Lineage: forks and mergers

In early 2025, Microsoft began a major rewrite of AutoGen (v0.4) around an event-driven actor model. The community forked AutoGen v0.2's GroupChat semantics as AG2, preserving the API that early adopters had integrated.

In October 2025 Microsoft announced that AutoGen would go into maintenance mode, with its event-driven actor model carried into Microsoft Agent Framework, which merges AutoGen and Semantic Kernel (release candidate February 2026, version 1.0 April 3, 2026). The GroupChat concept survives in both tracks; the implementation details differ. AG2 is the preferred upstream for v0.2-compatible code.

When GroupChat fits

  • Emergent conversations. You do not want to pre-wire every possible next-speaker.
  • Role-mixing tasks. Coder asks researcher, researcher asks archivist, archivist asks coder back. Flow is not a DAG.
  • Exploratory problem-solving. Think "brainstorm meeting," not "assembly line."

When it fails

  • Strict determinism. The LLM selector can be inconsistent. Same prompt, different runs, different next speakers.
  • Sycophancy cascades. Agents defer to whoever spoke most confidently. Counter-prompt explicitly.
  • Context bloat. Every agent reads every message; after 10 turns the context is huge. Use projections (Lesson 16.20) to scope views.
  • Hot speakers. One agent dominates the conversation because the selector favors its specialties. Introduce speaker balance as a selector feature.

Group chat vs supervisor

Same primitives, different defaults:

  • Supervisor: one agent plans and others execute. Selector is "ask the planner what to do."
  • Group chat: all agents are peers; selector is a function over the shared pool.

Both use the four primitives from Lesson 04. Group chat defaults to LLM-selected orchestration and full-pool shared state.

The same idea as a formula

A selector is a policy over speakers. Given the pool Pt​, it returns the next speaker at+1​=σ(Pt​). A constrained selector restricts the choice to an allowed set A(at​) that depends on the last speaker:

at+1​=arga∈A(at​)max​score(a∣Pt​).
Constraints remove bad moves; they do not make the choice among the remaining ones good.

A stop rule is a predicate on the pool. "Stop when anyone says TERMINATE" is ∃m∈P:m=TERMINATE. A safer rule ties stopping to the outcome:

stop⟺TERMINATE∧approved(latest code).

Worked example
Reading one round-robin chat
  • The coder writes buggy code, return a - b. The reviewer flags it: "please fix".
  • Round-robin gives the next turn to the manager, which says "continue working".
  • The coder's policy looks at the last message from someone else, which is now the manager's, does not see the review, and says TERMINATE.
  • The chat stops after 4 messages with the buggy code as its result. The lesson's printout reports this as a normal stop.
Check your mental model
  • ✗ "Any agent saying TERMINATE means the work is done."
    ✓ Round-robin stopped on the coder's TERMINATE with the buggy code unreviewed.
  • ✗ "A guard on stopping fixes a bad selector."
    ✓ It stops a bad result from shipping; the round-robin chat then ran out its 10 turns with the bug still there.
  • ✗ "An LLM selector understands the workflow."
    ✓ Free to choose, the small model picked the manager ten times in a row.
  • ✗ "Allowed transitions make LLM selection reliable."
    ✓ They kept it to legal moves, but it chose the manager instead of the coder after every review, so the bug was never fixed.

What the lesson's group chat ships

The lesson's agents and both selectors, judged by the final code in the pool and whether the reviewer approved it. Then the same chats under a stop rule that refuses TERMINATE until the latest code is approved. Runs in under a second.

# The lesson's group chat (imported from main.py), checked on outcome rather than on who spoke: what code is in the
# pool when the chat stops? Then a stop rule that accepts TERMINATE only after the reviewer has approved the latest
# code. Deterministic; runs in under a second.
import contextlib, io
from main import AGENTS, Msg, round_robin_selector, llm_style_selector, run_groupchat

def final_code(pool):
    code = [m.content for m in pool if m.speaker == "coder" and "code:" in m.content]
    return code[-1] if code else "(none)"
def approved_latest(pool):
    last_code = max((i for i, m in enumerate(pool) if m.speaker == "coder" and "code:" in m.content), default=-1)
    return any(m.speaker == "reviewer" and "approved" in m.content for m in pool[last_code + 1:])
quiet = contextlib.redirect_stdout(io.StringIO())
print("1. what each selector ships")
for label, sel in (("round-robin", round_robin_selector), ("context-aware", llm_style_selector)):
    with quiet:
        pool = run_groupchat(AGENTS, sel, 10, label)
    print(f"   {label:<14} stopped after {len(pool)} messages by {pool[-1].speaker!r}; final code {final_code(pool)!r}; "
          f"reviewer approved it: {approved_latest(pool)}")

print("\n2. a stop rule that needs the reviewer's approval of the latest code")
def guarded_chat(selector, max_rounds=10):
    pool = []
    for _ in range(max_rounds):
        nxt = selector(pool, AGENTS)
        if nxt is None: break
        content = AGENTS[nxt].policy(pool)
        if content.strip().endswith("TERMINATE") and not approved_latest(pool):
            content = f"{nxt}: stop refused, the latest code has not been approved"
        pool.append(Msg(nxt, content))
        if content.strip().endswith("TERMINATE"): break
    return pool
for label, sel in (("round-robin", round_robin_selector), ("context-aware", llm_style_selector)):
    pool = guarded_chat(sel)
    print(f"   {label:<14} {len(pool)} messages; final code {final_code(pool)!r}; approved: {approved_latest(pool)}; "
          f"ended with TERMINATE: {pool[-1].content.endswith('TERMINATE')}")

   context-aware  stopped after 6 messages by 'manager'; final code 'revised code: return a + b'; reviewer approved it: True

Reading this output

Round-robin ships the bug. It stops after 4 messages on the coder's TERMINATE, with return a - b as the final code and no approval. The manager's turn came between the review and the coder, so the coder never saw the request to fix it.

The context-aware selector ships the fix. It sends the review back to the coder, gets return a + b, has it approved, and lets the manager stop after 6 messages.

A guarded stop rule blocks the bad result. Requiring the reviewer's approval of the latest code turns round-robin's early TERMINATE into "stop refused". The chat then runs out its 10 turns with the bug still in place, which is a visible failure instead of a silent one. The context-aware chat is unaffected.

A small model as the selector

This block continues from the one above. Qwen2.5-0.5B-Instruct (CPU) picks the next speaker by the likelihood of each name, first from all three agents and then only from the allowed transitions, under the guarded stop rule, for up to 10 messages. About 1 minute.

# This block continues from the one above: a real LLM speaker selector, which is AutoGen's default. Qwen2.5-0.5B-
# Instruct (CPU) reads the chat and picks the next speaker by the likelihood of each name, once from every agent and
# once only from the speakers allowed after the last one (AutoGen's allowed-transitions option). Each run is
# stopped by the guarded rule from the block above, at most 10 messages. About 1 minute.
import os, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

ALLOWED = {None: ["coder", "manager"], "coder": ["reviewer"], "reviewer": ["coder", "manager"], "manager": ["coder"]}
def llm_selector(constrained):
    def select(pool, team):
        options = ALLOWED[pool[-1].speaker if pool else None] if constrained else list(team)
        roster = "\n".join(f"- {a.name}: {a.role}" for a in team.values())
        chat = "\n".join(f"{m.speaker}: {m.content}" for m in pool) or "(empty)"
        ids = tok.apply_chat_template([{"role": "user", "content": f"Team:\n{roster}\n\nChat so far:\n{chat}\n\n"
                                        "Task: get a correct add(a, b) function approved. Who should speak next?"}],
                                      add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
        def lp(name):
            a = tok(name, return_tensors="pt")["input_ids"]
            with torch.no_grad():
                logits = llm(torch.cat([ids, a], dim=1)).logits[0, ids.shape[1] - 1:-1]
            return torch.log_softmax(logits, -1).gather(1, a[0].unsqueeze(1)).sum().item()
        return max(options, key=lp)
    return select
for label, constrained in (("any speaker", False), ("allowed transitions", True)):
    pool = guarded_chat(llm_selector(constrained))
    print(f"{label:<20} speakers {[m.speaker for m in pool]}")
    print(f"{'':<20} final code {final_code(pool)!r}; approved {approved_latest(pool)}; "
          f"finished with TERMINATE {pool[-1].content.endswith('TERMINATE')}")

any speaker          speakers ['manager', 'manager', 'manager', 'manager', 'manager', 'manager', 'manager', 'manager', 'manager', 'manager']
                     final code '(none)'; approved False; finished with TERMINATE False
allowed transitions  speakers ['manager', 'coder', 'reviewer', 'manager', 'coder', 'reviewer', 'manager', 'coder', 'reviewer', 'manager']
                     final code 'initial code: return a - b  (buggy)'; approved False; finished with TERMINATE False
Reading this output

Free to choose, the model picked the manager every time. Ten messages of "continue working", no code at all.

With allowed transitions, it kept to legal moves but chose badly. After each review it picked the manager over the coder, so the coder never saw the request to fix the code. Three cycles later the code was still return a - b, and the guarded stop rule correctly never let it finish.

Constraints help; they are not enough. They narrowed the choices, but the decision that mattered, sending the review back to the coder, was still the model's, and it got it wrong. A three-line rule like the lesson's context-aware selector does this job reliably.

Part 1 of 3 · Msg, Agent, coder_policy, reviewer_policy, manager_policy, round_robin_selector

"""Group chat with speaker selection -- AutoGen GroupChat in miniature.

Three agents (coder, reviewer, manager), two selector variants
(round-robin, LLM-simulated), TERMINATE-token stop condition.
"""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Callable, Optional


@dataclass
class Msg:
    speaker: str
    content: str


@dataclass
class Agent:
    name: str
    role: str
    policy: Callable[[list[Msg]], str]


def coder_policy(pool: list[Msg]) -> str:
    recent = [m for m in pool[-3:] if m.speaker != "coder"]
    last = recent[-1].content if recent else ""
    if "review" in last.lower() or "fix" in last.lower():
        return "revised code: return a + b"
    if not any(m.speaker == "coder" for m in pool):
        return "initial code: return a - b  (buggy)"
    return "TERMINATE"


def reviewer_policy(pool: list[Msg]) -> str:
    last_coder = next((m for m in reversed(pool) if m.speaker == "coder"), None)
    if last_coder is None:
        return "waiting for code"
    if "a - b" in last_coder.content:
        return "review: bug detected -- sum must be a+b, please fix"
    if "a + b" in last_coder.content:
        return "review: approved"
    return "review: unclear"


def manager_policy(pool: list[Msg]) -> str:
    approvals = [m for m in pool if m.speaker == "reviewer" and "approved" in m.content]
    if approvals:
        return "TERMINATE"
    return "manager: continue working"


AGENTS: dict[str, Agent] = {
    "coder": Agent("coder", "writes code", coder_policy),
    "reviewer": Agent("reviewer", "reviews code", reviewer_policy),
    "manager": Agent("manager", "keeps things moving", manager_policy),
}


def round_robin_selector(pool: list[Msg], team: dict[str, Agent]) -> Optional[str]:
    names = list(team.keys())
    if not pool:
        return names[0]
    idx = (names.index(pool[-1].speaker) + 1) % len(names)
    return names[idx]

Part 2 of 3 · llm_style_selector, run_groupchat, speaker_counts

def llm_style_selector(pool: list[Msg], team: dict[str, Agent]) -> Optional[str]:
    """Simulated LLM selector: picks based on recent context keywords.
    A real implementation is an LLM call with the recent pool."""
    if not pool:
        return "manager"
    last = pool[-1]
    if last.speaker == "coder":
        return "reviewer"
    if last.speaker == "reviewer":
        if "approved" in last.content:
            return "manager"
        return "coder"
    if last.speaker == "manager":
        return "coder"
    return None


def run_groupchat(
    team: dict[str, Agent],
    selector: Callable[[list[Msg], dict[str, Agent]], Optional[str]],
    max_rounds: int,
    label: str,
) -> list[Msg]:
    print(f"\n=== {label} ===")
    pool: list[Msg] = []
    trace: list[str] = []
    for _ in range(max_rounds):
        nxt = selector(pool, team)
        if nxt is None:
            break
        trace.append(nxt)
        agent = team[nxt]
        content = agent.policy(pool)
        pool.append(Msg(speaker=nxt, content=content))
        print(f"  [{nxt:8s}]: {content}")
        if content.strip().endswith("TERMINATE"):
            break
    print(f"  Selector trace: {trace}")
    print(f"  Rounds used: {len(pool)}")
    return pool


def speaker_counts(pool: list[Msg]) -> dict[str, int]:
    counts: dict[str, int] = {}
    for m in pool:
        counts[m.speaker] = counts.get(m.speaker, 0) + 1
    return counts


def main() -> None:
    print("Group chat with speaker selection -- AutoGen GroupChat shape")
    print("-" * 62)

    p_rr = run_groupchat(AGENTS, round_robin_selector, max_rounds=8, label="Round-robin")
    print(f"  Speaker counts: {speaker_counts(p_rr)}")

    p_llm = run_groupchat(AGENTS, llm_style_selector, max_rounds=8, label="LLM-style (context-aware)")
    print(f"  Speaker counts: {speaker_counts(p_llm)}")

    print("\nObservations:")
    print("  - Round-robin gives every agent an equal turn regardless of context.")
    print("  - LLM-style routes by context; reviewer only speaks after coder, etc.")
    print("  - Both terminate on TERMINATE token or max_rounds.")

Industry practice
What's current (2024–2026)
  • Microsoft Agent Framework 1.0 (April 2026) succeeds AutoGen and Semantic Kernel and keeps group-chat orchestration with pluggable managers; AutoGen itself is in maintenance.
  • AG2 keeps the v0.2 GroupChat API, including speaker_selection_method options (auto, round-robin, random, manual or a function) and allowed or disallowed speaker transitions.
  • Graphs replace free chats for fixed workflows. When the order is known, teams increasingly encode it as graph edges (LangGraph) or explicit handoffs, and keep LLM selection for genuinely open discussions.
  • On your laptop: write the selector as a function over the last message first; switch to a model only where the next speaker really depends on judgement.

Recap
What to keep from this lesson
  • A group chat is a shared pool plus a selector plus a stop rule.
  • Judge a chat by what it ships, not by who spoke.
  • Tie stopping to the outcome: approval of the latest work, not just a TERMINATE token.
  • Constrain transitions to legal moves, and still check the result.
  • Use code selectors for known workflows; a small LLM selector repeated one speaker or skipped the fix.

MACheat sheet · Multi-Agent Systems: Quick Reference

Ship it

Checklist:

  • Max rounds cap. Always. 10-20 for typical tasks.
  • Speaker-balance metric. Track turns per agent; alert when imbalance exceeds a threshold.
  • Termination token. TERMINATE or a dedicated verifier agent.
  • Projection or scoped memory. After ~10 messages, consider giving each agent only a scoped view to prevent context bloat.
  • Selector logging. For LLM-selected variants, log both the selector's input and its choice. Otherwise debugging is impossible.

outputs/skill-groupchat-selector.md

---
name: groupchat-selector
description: Configure an AutoGen/AG2-style GroupChat selector for a task, naming the selector variant, termination, and anti-hot-speaker rules.
version: 1.0.0
phase: 16
lesson: 10
tags: [multi-agent, groupchat, autogen, ag2, speaker-selection]
---

Given a task and an agent roster, produce a GroupChat configuration: selector choice, selector inputs, termination rules, and guardrails.

Produce:

1. **Selector variant.** Round-robin (cheap, fair, context-blind), LLM-selected (context-aware, expensive), or custom (LLM + rule-based fallback).
2. **Selector inputs.** If LLM-selected: recent N messages, agent specialties, turn counts. If custom: explicit rules.
3. **Termination rules.** Max rounds, TERMINATE token, goal-reached verifier, or combination.
4. **Hot-speaker mitigation.** Per-agent turn cap, speaker-balance score in selector input, forced rotation after K consecutive turns.
5. **Context bloat mitigation.** Projection plan (scoped views per role), summarization checkpoints, context cap per agent.
6. **Observability.** Log selector's input, selector's choice, per-turn agent latency.

Hard rejects:

- Any LLM-selected config without logging of selector's input/output. Debugging becomes impossible.
- Configs without a max_rounds cap.
- Symmetric chats (no specialization) on reasoning tasks — use debate (Lesson 07) instead.

Refusal rules:

- If the task has a known DAG structure, refuse GroupChat and recommend LangGraph static graph for determinism.
- If the task requires strict audit trails, refuse GroupChat; recommend LangGraph with checkpointer.
- If the agents number more than 5-6, refuse flat GroupChat and recommend nested groups or hierarchical pattern.

Output: a one-page GroupChat config brief. Close with the cost estimate (LLM-selected incurs one selector call per turn).

Solutions

SolutionP1 · Buggy code, never approved

The buggy code, return a - b, and no. The reviewer flagged it, but under round-robin the manager spoke next, and the coder, reading the manager's "continue working", said TERMINATE. The lesson's chat stops on any TERMINATE, so it ended with unapproved, wrong code, and its printout gives no warning.

SolutionB1 · TERMINATE without approval

The chat stops on a word, not on an outcome, and round-robin puts the wrong agent after the fact-check.

  • Make stopping conditional: accept TERMINATE only when the fact-checker's last verdict on the latest draft is "approved".
  • Route on content: after a fact-check that asks for changes, the next speaker must be the writer, not the editor. Use a rule or allowed transitions, not round-robin.
  • Log and test outcomes: count articles published with an open fact-check, and treat any above zero as a bug.

Weigh a trade-offFour agents, a coder, a reviewer, a tester and a researcher, share one conversation. You must decide how the next speaker is chosen on each turn. The options on the table are a fixed rotation, a model that reads the recent messages and picks, and letting the current agent name its successor. Compare them and say what you would ship with each.

Level 2 of 4 · about 10 minutes to answer well.

Short answer. A fixed rotation is deterministic and cheap, and it gives the coder the turn when the topic is a legal question. A model selector is context-aware, and it costs one extra model call per turn, picks differently on identical input, and tends to favor one agent. A handoff by the current agent keeps the routing in the prompts with no external manager, and it is the pattern that loops when two prompts disagree. Most production chats use a selector with fallback rules, a round cap, a termination signal and a log of every selection.

The three selectors.

Selector Strength Weakness
Round-robin Deterministic, no extra calls, scales linearly in agents Ignores context, so the wrong agent gets the turn
Model-selected Reads the pool and picks the best next speaker One extra call per turn, inconsistent across runs, and it can favor a hot speaker
Current agent hands off No manager, routing lives in each prompt Two prompts can form a cycle, and an injected message can force a handoff

Who decides, and where.

The difference between the second and the third is where the decision lives. In a group chat the selector sits outside the agents and reads the shared pool. In the handoff pattern the active agent decides by calling a tool that returns the next agent. A manager outside can see an alternation between two agents and break it. An agent inside the loop cannot.

What goes wrong in a group chat.

  • Nondeterminism. The same pool gives different next speakers on different runs, which hurts audit and replay.
  • Deference cascades. Agents follow whoever spoke most confidently, so the prompts must say when to disagree.
  • Context growth. Every agent reads every message, and after about 10 turns the pool is large, so give each agent a scoped view.
  • One agent dominates. The selector keeps picking the agent whose specialty matches the recent messages, so track turns per agent and alert on imbalance.

What to ship.

  1. A round cap, 10 to 20 for a typical task.
  2. A termination signal: a sentinel token from an agent, or a verifier that checks the goal each turn.
  3. A speaker-balance metric, with an alert when one agent takes too many turns.
  4. A custom selector that combines the model's pick with rules such as "the tester speaks after the coder".
  5. A log of the selector's input and its choice, because without it a wrong selection cannot be debugged.

When each one fits.

A fixed rotation fits a staged pipeline where the order is known. A model selector fits an exploratory conversation where the flow is not a graph. Handoffs fit triage, where a front agent routes a user to one specialist and the conversation is short.

Plausible wrong answers.

  • "Use the model selector, because it understands the conversation." It also adds a call per turn, picks inconsistently, and favors one agent unless rules and a balance metric constrain it.
  • "Round-robin is fair, so it is safe." Fair turns are not useful turns, and a coder speaking on a legal question wastes a round and adds noise to the pool.
  • "Let the agents decide among themselves." That is the handoff pattern, and it is the one that forms cycles and that an injected message can steer.

Follow-ups an interviewer may ask.

  • (level 2) Why does the model selector need a log of its input as well as its output? Expected: the choice depends on what the selector saw, and without the input a reviewer cannot tell whether the pick was wrong or the pool was.
  • (level 2) What does a verifier-based termination add over a sentinel token? Expected: the chat stops when a check passes, not when an agent claims it is done, which removes early termination by a confident agent.
  • (level 3) Which of the three makes prompt injection worse, and why? Expected: the handoff pattern, because the deciding tool call is made by the agent that just read the injected text, while an external selector can apply rules the agents do not control.
  • (level 3) How does a custom selector fix the hot-speaker problem without losing context awareness? Expected: let the model propose, then apply a rule that caps consecutive turns per agent and forces the verifier or a quiet agent in.
