In plain words first
The idea in one line

Basic RAG retrieves the top-k most similar chunks. That works for simple questions. It falls apart for multi-hop reasoning, ambiguous queries, and large corpora. Advanced RAG is the difference between a demo that works on 10 documents and a system that works on 10 million.

Terms you'll hear
Term What people say What it actually means
BM25 "Keyword search" A probabilistic ranking algorithm that scores documents by term frequency, inverse document frequency, and document length normalization
Hybrid search "Best of both worlds" Running semantic (vector) and keyword (BM25) search in parallel, then merging results with rank fusion
Reciprocal Rank Fusion "Merge ranked lists" Combining multiple ranked lists by summing 1/(k + rank) for each document across all lists
Reranking "Second pass scoring" Using a more expensive cross-encoder model to re-score a candidate set from initial retrieval
Cross-encoder "Joint query-document model" A model that takes a query and document as a single input, producing a relevance score; more accurate than bi-encoders but too slow for full corpus search
Bi-encoder "Independent embedding model" A model that embeds queries and documents independently; fast because embeddings are precomputed, but less accurate than cross-encoders
HyDE "Search with a fake answer" Generate a hypothetical answer to the query, embed it, and search for real documents similar to it
Parent-child chunking "Small search, big context" Index small chunks for precise retrieval but return the larger parent chunk to provide sufficient context
Metadata filtering "Narrow before searching" Filtering documents by attributes (date, source, category) before running vector search to reduce the search space
Faithfulness "Did it stay grounded" Whether the generated answer is supported by the retrieved documents, as opposed to hallucinated from the model's training data

The problem

In plain words first

Basic RAG finds passages whose embeddings sit close to the query, and close is not the same as useful. Keyword search finds exact terms (error codes, names, numbers) that embeddings blur; embeddings find paraphrases that keywords miss. Hybrid search runs both and merges the two rankings. A reranker, a slower model that reads the query and each candidate together, then reorders the shortlist. Query rewriting and HyDE fix vague questions, parent-child chunking retrieves small and returns big, and evaluation tells you which of these is actually helping. This lesson builds each piece, then measures BM25, dense retrieval, hybrid fusion and cross-encoder reranking on SciFact, a real benchmark with human relevance labels. No model is trained.

You built a basic RAG pipeline in Lesson 06. It works for straightforward questions on a small corpus. Now try these:

Ambiguous query: "What was revenue last quarter?" Semantic search returns chunks about revenue strategy, revenue projections, and the CFO's thoughts on revenue growth. All semantically similar to the word "revenue." None containing the actual number. The correct chunk says "$47.2M in Q3 2025" but uses the word "earnings" instead of "revenue." The embedding model thinks "revenue strategy" is closer to the query than "Q3 earnings were $47.2M."

Multi-hop question: "Which team had the highest customer satisfaction score improvement?" This requires finding the satisfaction scores for each team, comparing them, and identifying the maximum. No single chunk contains the answer. The information is scattered across team reports.

Large corpus problem: You have 2 million chunks. The correct answer is in chunk #1,847,293. Your top-5 retrieval pulls chunks #14, #89,201, #1,200,000, #44, and #901,333. Close in embedding space, but none containing the answer. At this scale, approximate nearest neighbor search introduces enough error that relevant results get pushed out of the top-k.

Basic RAG fails because vector similarity is not the same as relevance. A chunk can be semantically similar to a query without being useful for answering it. Advanced RAG addresses this with four techniques: hybrid search (add keyword matching), reranking (score candidates more carefully), query transformation (fix the query before searching), and better chunking (retrieve at the right granularity).

Idea 1 · Hybrid Search: Semantic + Keyword

Semantic search (vector similarity) is good at understanding meaning. "How do I cancel my subscription?" matches "Steps to terminate your plan" even though they share no words. But it misses exact matches. "Error code E-4021" might not match a chunk containing "E-4021" if the embedding model treats it as noise.

Keyword search (BM25) is the opposite. It excels at exact matches. "E-4021" matches perfectly. But "cancel my subscription" returns zero results if the document says "terminate your plan."

Hybrid search runs both, then merges the results.

BM25 (Best Matching 25) is the standard keyword search algorithm. It has been the backbone of search engines since the 1990s. The formula:

BM25(q, d) = sum over terms t in q:
    IDF(t) * (tf(t,d) * (k1 + 1)) / (tf(t,d) + k1 * (1 - b + b * |d| / avgdl))

Where tf(t,d) is the term frequency of t in document d, IDF(t) is the inverse document frequency, |d| is the document length, avgdl is the average document length, k1 controls term frequency saturation (default 1.2), and b controls length normalization (default 0.75).

In plain terms: BM25 scores documents higher when they contain query terms (especially rare ones), but with diminishing returns for repeated terms. A document with the word "revenue" 50 times is not 50x more relevant than one with it once.

Idea 2 · Reciprocal Rank Fusion (RRF)

You have two ranked lists: one from vector search, one from BM25. How do you combine them? Reciprocal Rank Fusion is the standard approach.

RRF_score(d) = sum over rankings R:
    1 / (k + rank_R(d))

Where k is a constant (typically 60) that prevents the top-ranked result from dominating.

A document ranked #1 in vector search and #5 in BM25 gets: 1/(60+1) + 1/(60+5) = 0.0164 + 0.0154 = 0.0318

A document ranked #3 in vector search and #2 in BM25 gets: 1/(60+3) + 1/(60+2) = 0.0159 + 0.0161 = 0.0320

RRF naturally balances the two signals. A document that ranks highly in both lists gets the best score. A document that ranks #1 in one list but is absent from the other gets a moderate score. This is robust because it uses ranks, not raw scores, so differences in score distributions between the two systems do not matter.

Idea 3 · Reranking

Retrieval (whether vector, keyword, or hybrid) is fast but imprecise. It uses bi-encoders: the query and each document are embedded independently, then compared. The embeddings are computed once and cached. This scales to millions of documents.

Reranking uses cross-encoders: the query and a candidate document are fed together into a model that outputs a relevance score. The model sees both texts simultaneously and can capture fine-grained interactions between them. A cross-encoder can understand that "What were Q3 earnings?" is highly relevant to a chunk containing "$47.2M in Q3" even if a bi-encoder missed the connection.

The trade-off: cross-encoders are 100-1000x slower than bi-encoders because they process the query-document pair jointly. You cannot pre-compute cross-encoder scores for a million documents. The solution: retrieve a larger candidate set (top-50 from hybrid search), then rerank with a cross-encoder to get the final top-5.

Common reranking models (late 2026): - Managed APIs: Cohere Rerank and Voyage rerank, multilingual, priced per search - Open-weight cross-encoders: bge-reranker-v2-m3, Qwen3-Reranker (0.6B to 8B), Jina rerankers - cross-encoder/ms-marco-MiniLM-L-6-v2: open-weight, 22M parameters, runs on CPU for prototyping (used below) - LLM rerankers: a general model asked to score or order the candidates; slower and costlier, sometimes better on reasoning-heavy queries - Late interaction (ColBERTv2, Jina-ColBERT): one vector per token, document vectors precomputed, so scoring a candidate is cheap while keeping token-level matching

Idea 4 · Query Transformation

Sometimes the problem is not retrieval but the query itself. "What was that thing about the new policy change?" is a terrible search query. It contains no specific terms. The embedding is vague. No retrieval system can find the right documents from this.

Query rewriting: rephrase the user's query into a better search query. An LLM can do this:

User: "What was that thing about the new policy change?"
Rewritten: "Recent policy changes and updates"

HyDE (Hypothetical Document Embeddings): instead of searching with the query, generate a hypothetical answer, embed that, and search for similar real documents.

Query: "What is the refund policy for enterprise?"
Hypothetical answer: "Enterprise customers are eligible for a full refund
within 60 days of purchase. Refunds are pro-rated based on the remaining
subscription period and processed within 5-7 business days."

Embed the hypothetical answer and search for real documents similar to it. The intuition: the hypothetical answer lives closer in embedding space to the real answer than the original question does. Questions and answers have different linguistic structures. By generating a hypothetical answer, you bridge the gap between "question space" and "answer space" in the embedding.

HyDE adds one LLM call before retrieval. This increases latency by 500-2000ms. Worth it when retrieval quality is poor on raw queries.

Idea 5 · Parent-Child Chunking

Standard chunking forces a trade-off: small chunks for precise retrieval, large chunks for sufficient context. Parent-child chunking eliminates this trade-off.

Index small chunks (128 tokens) for retrieval. When a small chunk is retrieved, return its parent chunk (512 tokens) for the prompt. The small chunk matches the query precisely. The parent chunk provides enough context for the LLM to generate a good answer.

The query "enterprise refund?" matches child chunk C2 precisely. But the prompt receives the full parent chunk P, which includes the surrounding context about processing time and submission process.

Idea 6 · Metadata Filtering

Before running vector search, filter the corpus by metadata: date, source, category, author, language. This reduces the search space and prevents irrelevant results.

"What changed in the security policy last month?" should only search documents from the last 30 days in the security category. Without metadata filtering, you search the entire corpus and might retrieve a 2-year-old security document that happens to be semantically similar.

Production RAG systems store metadata alongside each chunk: source document, creation date, category, author, version. Vector databases support pre-filtering by metadata before similarity search, which is critical for performance at scale.

Idea 7 · Evaluation

You built a RAG system. How do you know if it works? Three metrics:

Retrieval relevance (Recall@k): for a set of test questions with known relevant documents, what percentage of relevant documents appear in the top-k results? If the answer to a question is in chunk #47, does chunk #47 appear in the top-5?

Faithfulness: is the generated answer grounded in the retrieved documents? If the retrieved chunks say "60-day refund window" and the model says "90-day refund window," that is a faithfulness failure. The model hallucinated despite having the correct context.

Answer correctness: does the generated answer match the expected answer? This is the end-to-end metric. It combines retrieval quality and generation quality.

A simple faithfulness check: take each claim in the generated answer and verify it appears (in substance) in the retrieved chunks. If the answer contains a fact not in any retrieved chunk, it is likely hallucinated.

Step 1 · BM25 Implementation

import math
from collections import Counter

class BM25:
    def __init__(self, k1=1.2, b=0.75):
        self.k1 = k1
        self.b = b
        self.docs = []
        self.doc_lengths = []
        self.avg_dl = 0
        self.doc_freqs = {}
        self.n_docs = 0

    def index(self, documents):
        self.docs = documents
        self.n_docs = len(documents)
        self.doc_lengths = []
        self.doc_freqs = {}

        for doc in documents:
            words = doc.lower().split()
            self.doc_lengths.append(len(words))
            unique_words = set(words)
            for word in unique_words:
                self.doc_freqs[word] = self.doc_freqs.get(word, 0) + 1

        self.avg_dl = sum(self.doc_lengths) / self.n_docs if self.n_docs else 1

    def score(self, query, doc_idx):
        query_words = query.lower().split()
        doc_words = self.docs[doc_idx].lower().split()
        doc_len = self.doc_lengths[doc_idx]
        word_counts = Counter(doc_words)
        score = 0.0

        for term in query_words:
            if term not in word_counts:
                continue
            tf = word_counts[term]
            df = self.doc_freqs.get(term, 0)
            idf = math.log((self.n_docs - df + 0.5) / (df + 0.5) + 1)
            numerator = tf * (self.k1 + 1)
            denominator = tf + self.k1 * (1 - self.b + self.b * doc_len / self.avg_dl)
            score += idf * numerator / denominator

        return score

    def search(self, query, top_k=10):
        scores = [(i, self.score(query, i)) for i in range(self.n_docs)]
        scores.sort(key=lambda x: x[1], reverse=True)
        return scores[:top_k]

Step 2 · Reciprocal Rank Fusion

def reciprocal_rank_fusion(ranked_lists, k=60):
    scores = {}
    for ranked_list in ranked_lists:
        for rank, (doc_id, _) in enumerate(ranked_list):
            if doc_id not in scores:
                scores[doc_id] = 0.0
            scores[doc_id] += 1.0 / (k + rank + 1)
    fused = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return fused

Step 3 · Hybrid Search Pipeline

def hybrid_search(query, chunks, vector_embeddings, vocab, idf, bm25_index, top_k=5, fusion_k=60):
    query_emb = tfidf_embed(query, vocab, idf)
    vector_results = search(query_emb, vector_embeddings, top_k=top_k * 3)
    bm25_results = bm25_index.search(query, top_k=top_k * 3)
    fused = reciprocal_rank_fusion([vector_results, bm25_results], k=fusion_k)
    return fused[:top_k]

Step 4 · Simple Reranker

In production, you would use a cross-encoder model. Here we build a reranker that scores query-document relevance using word overlap, term importance, and phrase matching.

def rerank(query, candidates, chunks):
    query_words = set(query.lower().split())
    stop_words = {"the", "a", "an", "is", "are", "was", "were", "what", "how",
                  "why", "when", "where", "do", "does", "for", "of", "in", "to",
                  "and", "or", "on", "at", "by", "it", "its", "this", "that",
                  "with", "from", "be", "has", "have", "had", "not", "but"}
    query_terms = query_words - stop_words

    scored = []
    for doc_id, initial_score in candidates:
        chunk = chunks[doc_id].lower()
        chunk_words = set(chunk.split())

        term_overlap = len(query_terms & chunk_words)

        query_bigrams = set()
        q_list = [w for w in query.lower().split() if w not in stop_words]
        for i in range(len(q_list) - 1):
            query_bigrams.add(q_list[i] + " " + q_list[i + 1])
        bigram_matches = sum(1 for bg in query_bigrams if bg in chunk)

        position_boost = 0
        for term in query_terms:
            pos = chunk.find(term)
            if pos != -1 and pos < len(chunk) // 3:
                position_boost += 0.5

        rerank_score = (
            term_overlap * 1.0
            + bigram_matches * 2.0
            + position_boost
            + initial_score * 5.0
        )
        scored.append((doc_id, rerank_score))

    scored.sort(key=lambda x: x[1], reverse=True)
    return scored

import math, re, random, time, numpy as np
from collections import Counter, defaultdict
from datasets import load_dataset
from sentence_transformers import SentenceTransformer, CrossEncoder

# SciFact (BEIR): scientific claims as queries, paper abstracts as documents, human relevance labels
corpus = load_dataset("mteb/scifact", "corpus", split="corpus")
queries = {r["_id"]: r["text"] for r in load_dataset("mteb/scifact", "queries", split="queries")}
qrels = defaultdict(set)
for r in load_dataset("mteb/scifact", "default", split="test"):
    qrels[r["query-id"]].add(r["corpus-id"])
rel_docs = set().union(*qrels.values())
rng = random.Random(0)
others = [d for d in corpus if d["_id"] not in rel_docs]
docs = [d for d in corpus if d["_id"] in rel_docs] + rng.sample(others, 1700)
ids = [d["_id"] for d in docs]
texts = [(d["title"] + ". " + d["text"]) for d in docs]
qids = sorted(qrels, key=int)
qtexts = [queries[q] for q in qids]
print(f"{len(docs):,} abstracts ({len(rel_docs)} relevant to some query + 1,700 distractors), {len(qids)} test claims")

def metrics(rankings, k=10):                 # recall@10 and nDCG@10 with binary relevance
    rec, ndcg = [], []
    for q, ranked in zip(qids, rankings):
        top = [ids[i] for i in ranked[:k]]; rel = qrels[q]
        rec.append(len(set(top) & rel) / len(rel))
        dcg = sum(1 / math.log2(r + 2) for r, d in enumerate(top) if d in rel)
        idcg = sum(1 / math.log2(r + 2) for r in range(min(len(rel), k)))
        ndcg.append(dcg / idcg)
    return np.mean(rec), np.mean(ndcg)

# 1) BM25, the lesson's formula (k1 = 1.2, b = 0.75)
tokenize = lambda s: re.findall(r"[a-z0-9]+", s.lower())
dtoks = [tokenize(t) for t in texts]; N = len(dtoks); avgdl = sum(map(len, dtoks)) / N
df = Counter(w for d in dtoks for w in set(d)); tfs = [Counter(d) for d in dtoks]
def bm25(q, k1=1.2, b=0.75):
    s = np.zeros(N)
    for w in set(tokenize(q)):
        if w not in df: continue
        idf = math.log(1 + (N - df[w] + 0.5) / (df[w] + 0.5))
        for i, tf in enumerate(tfs):
            if w in tf: s[i] += idf * tf[w] * (k1 + 1) / (tf[w] + k1 * (1 - b + b * len(dtoks[i]) / avgdl))
    return s
t = time.time(); B = np.stack([bm25(q) for q in qtexts]); t_bm25 = time.time() - t

# 2) dense: bge-small-en-v1.5
enc = SentenceTransformer("BAAI/bge-small-en-v1.5", device="cpu"); enc.max_seq_length = 256
t = time.time(); D = enc.encode(texts, batch_size=32, normalize_embeddings=True); t_index = time.time() - t
t = time.time()
Q = enc.encode(["Represent this sentence for searching relevant passages: " + q for q in qtexts], normalize_embeddings=True)
S = Q @ D.T; t_dense = time.time() - t

rank_b = np.argsort(-B, axis=1); rank_d = np.argsort(-S, axis=1)
# 3) hybrid: reciprocal rank fusion of the two rankings, k = 60
def rrf(*rankings, k=60):
    out = []
    for rows in zip(*rankings):
        sc = defaultdict(float)
        for r in rows:
            for pos, i in enumerate(r[:100]): sc[i] += 1 / (k + pos + 1)
        out.append(sorted(sc, key=sc.get, reverse=True))
    return out
rank_h = rrf(rank_b, rank_d)
# 4) rerank the hybrid top 20 with a cross-encoder
ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2", device="cpu", max_length=320)
t = time.time()
rank_r = []
for q, r in zip(qtexts, rank_h):
    cand = r[:20]; sc = ce.predict([(q, texts[i]) for i in cand], batch_size=20)
    rank_r.append([cand[j] for j in np.argsort(-sc)] + r[20:])
t_ce = time.time() - t

print(f"\n{'method':38} {'recall@10':>9} {'nDCG@10':>8}   time for {len(qids)} queries")
for name, rk, tt in [("BM25 (the lesson's formula)", rank_b, f"{t_bm25:.1f} s"),
                     ("dense, bge-small (bi-encoder)", rank_d, f"{t_dense:.1f} s (+ {t_index:.0f} s to index)"),
                     ("hybrid: RRF of BM25 and dense", rank_h, "~0"),
                     ("hybrid top 20, cross-encoder reranked", rank_r, f"{t_ce:.0f} s")]:
    r, n = metrics(rk); print(f"{name:38} {r:9.3f} {n:8.3f}   {tt}")

only_d = sum(bool(qrels[q] & {ids[i] for i in rd[:10]}) and not (qrels[q] & {ids[i] for i in rb[:10]}) for q, rb, rd in zip(qids, rank_b, rank_d))

Step 5 · HyDE (Hypothetical Document Embeddings)

def hyde_generate_hypothesis(query):
    templates = {
        "what": "The answer to '{query}' is as follows: Based on our documentation, {topic} involves specific policies and procedures that define how the process works.",
        "how": "To address '{query}': The process involves several steps. First, you need to initiate the request. Then, the system processes it according to the defined rules.",
        "default": "Regarding '{query}': Our records indicate specific details and policies related to this topic that provide a comprehensive answer."
    }
    query_lower = query.lower()
    if query_lower.startswith("what"):
        template = templates["what"]
    elif query_lower.startswith("how"):
        template = templates["how"]
    else:
        template = templates["default"]

    topic_words = [w for w in query.lower().split()
                   if w not in {"what", "is", "the", "how", "do", "does", "a", "an",
                                "for", "of", "to", "in", "on", "at", "by", "and", "or"}]
    topic = " ".join(topic_words) if topic_words else "this topic"

    return template.format(query=query, topic=topic)


def hyde_search(query, chunks, vector_embeddings, vocab, idf, top_k=5):

    hypothesis_emb = tfidf_embed(hypothesis, vocab, idf)
    results = search(hypothesis_emb, vector_embeddings, top_k)
    return results, hypothesis

Step 6 · Parent-Child Chunking

def create_parent_child_chunks(text, parent_size=200, child_size=50):
    words = text.split()
    parents = []
    children = []
    child_to_parent = {}

    parent_idx = 0
    start = 0
    while start < len(words):
        parent_end = min(start + parent_size, len(words))
        parent_text = " ".join(words[start:parent_end])
        parents.append(parent_text)

        child_start = start
        while child_start < parent_end:
            child_end = min(child_start + child_size, parent_end)
            child_text = " ".join(words[child_start:child_end])
            child_idx = len(children)
            children.append(child_text)
            child_to_parent[child_idx] = parent_idx
            child_start += child_size

        parent_idx += 1
        start += parent_size

    return parents, children, child_to_parent

Step 7 · Faithfulness Evaluation

def evaluate_faithfulness(answer, retrieved_chunks):
    answer_sentences = [s.strip() for s in answer.split(".") if len(s.strip()) > 10]
    if not answer_sentences:
        return 1.0, []

    grounded = 0
    ungrounded = []
    context = " ".join(retrieved_chunks).lower()

    for sentence in answer_sentences:
        words = set(sentence.lower().split())
        stop_words = {"the", "a", "an", "is", "are", "was", "were", "and", "or",
                      "to", "of", "in", "for", "on", "at", "by", "it", "this", "that"}
        content_words = words - stop_words
        if not content_words:
            grounded += 1
            continue

        matched = sum(1 for w in content_words if w in context)
        ratio = matched / len(content_words) if content_words else 0

        if ratio >= 0.5:
            grounded += 1
        else:
            ungrounded.append(sentence)

    score = grounded / len(answer_sentences) if answer_sentences else 1.0
    return score, ungrounded


def evaluate_retrieval_recall(queries_with_relevant, retrieval_fn, k=5):
    total_recall = 0.0
    results = []

    for query, relevant_indices in queries_with_relevant:
        retrieved = retrieval_fn(query, k)
        retrieved_indices = set(idx for idx, _ in retrieved)
        relevant_set = set(relevant_indices)
        hits = len(retrieved_indices & relevant_set)
        recall = hits / len(relevant_set) if relevant_set else 1.0
        total_recall += recall
        results.append({
            "query": query,
            "recall": recall,
            "hits": hits,
            "total_relevant": len(relevant_set)
        })

    avg_recall = total_recall / len(queries_with_relevant) if queries_with_relevant else 0
    return avg_recall, results

# Advanced RAG Pattern

Basic RAG: embed query -> vector search -> top-k -> generate.
Advanced RAG: embed query + BM25 -> fuse ranks -> rerank -> top-k -> generate.

```
query -> [vector search (top-50)] -+-> RRF fusion -> reranker (top-5) -> prompt -> LLM
                                   |
query -> [BM25 search (top-50)]  --+
```

## When to upgrade from basic RAG

- Retrieval quality drops below 70% Recall@5
- Users report wrong or irrelevant answers
- Corpus grows beyond 100K chunks
- Queries use different vocabulary than documents
- Multi-hop questions fail consistently

## Implementation checklist

1. Add BM25 index alongside vector index
2. Run both searches in parallel (top-50 each)
3. Merge with Reciprocal Rank Fusion (k=60)
4. Rerank top candidates with a cross-encoder
5. Take top-5 for the final prompt
6. Add faithfulness evaluation on a test set

## Technique selection guide

- **Hybrid search**: always use in production. Costs nothing extra at query time.
- **Reranking**: use when Recall@50 is good but Recall@5 is bad. Adds 50-200ms latency.
- **HyDE**: use when queries are vague or use different vocabulary than docs. Adds one LLM call.
- **Parent-child chunks**: use when small chunks lack context but large chunks dilute relevance.
- **Metadata filtering**: use when corpus has clear categories (date, source type, department).
- **Query decomposition**: use for multi-hop questions that require information from multiple docs.

## Common mistakes

- Running BM25 and vector search with different chunk sets (they must search the same corpus)
- Using too small a candidate pool for reranking (top-10 is too few; use top-50)
- Adding HyDE for every query (only helps when vocabulary mismatch is the bottleneck)
- Not evaluating changes (measure Recall@k before and after each technique)
- Over-engineering the pipeline before measuring where it fails

## Evaluation workflow

1. Create 50+ test questions with known answer chunks
2. Measure Recall@5 and Recall@10 for each retrieval method
3. For queries where retrieval succeeds, measure faithfulness of generated answers
4. Track metrics weekly as the corpus grows
5. Investigate individual failures before adding more techniques

Solutions

SolutionP1 · Dense won; fusion and reranking added little

Dense beat BM25 at nDCG@10 (0.774 against 0.727), and on recall@10 (0.870 against 0.843). RRF fusion did not beat dense on nDCG (0.773) but raised recall@10 to 0.874, because the two methods miss different claims (18 and 23 of them). The cross-encoder rerank of the fused top 20 gave the best numbers, recall@10 0.893 and nDCG@10 0.776, for most of the run time: 501 s for 300 queries. On this benchmark each step added a little; none transformed the result.

SolutionB1 · Scores live on different scales

BM25 scores are unbounded sums that grow with query length and term rarity, while cosine similarities lie between −1 and 1 and, for a model like bge-small, mostly in a narrow band well above 0. Added with equal weights, the BM25 term is many times larger and decides the order almost alone: the "hybrid" is BM25 with a little noise. To add scores you must first put them on one scale, for example min-max or z-score normalisation per query, and then tune the weight on held-out queries. RRF avoids the problem by using only ranks, ∑1/(k+rank), which is why it is the usual choice for hybrid search in search engines and vector databases.

Explain the mechanismA retrieval pipeline uses one model to find candidate chunks and a second model to order them. Explain what each model sees as input, and why the second model does not run over the whole corpus.

Level 1 of 4 · about 6 minutes to answer well.

Short answer. A bi-encoder embeds the query and each document on their own and compares the vectors, so every document vector is computed once at index time. A cross-encoder reads the query and one document together as a single sequence and outputs one relevance score, so it can see how the two texts interact. That score costs one forward pass for each pair, so the cross-encoder runs only on a short candidate list.

Input shape.

The bi-encoder maps a text to a vector. The query vector and the document vectors live in the same space, and the rank is the cosine between them. The two encodings never see each other, so the model has to compress all that is useful about a document into one vector without knowing the question.

The cross-encoder takes [CLS] query_tokens [SEP] document_tokens [SEP] as one sequence. Attention runs across the join, so every document token can attend to every query token. The output at the first position goes into one linear head that gives one number.

Cost.

The bi-encoder embeds once and answers queries for ever. The cross-encoder runs once per pair. On a 10 million document corpus that is 10 million forward passes for one query, which no request budget allows. The advanced RAG lesson puts the gap at 100 to 1000 times slower than a bi-encoder.

Staging.

Retrieve the top N with the cheap model, then rerank N down to K with the expensive one. N is small, 50 to 200. The quality is the cross-encoder quality, capped by the recall of the first stage at N. A low N caps quality, not only latency.

The production point is a cross-encoder of about 22M parameters. Larger rerankers are kept for offline work or for a very small K.

Plausible wrong answers.

  • "The cross-encoder is a better embedding model." It does not produce an embedding; it produces one score for one query and one document.
  • "Run the cross-encoder over every chunk for the best quality." On a 10 million document corpus that is 10 million forward passes per query.
  • "A larger reranker always wins." The 22M parameter class is the production point; larger models lose more latency than they gain and are kept for offline reranking or a very small K.

Follow-ups an interviewer may ask.

  • (level 1) Which of the two outputs can you compute before any query arrives? Expected: the bi-encoder document vectors; a cross-encoder score depends on the query.
  • (level 2) What caps the quality of the two-stage pipeline? Expected: the recall of the first stage at N, because the reranker can only reorder what the retriever returned.
  • (level 2) Does the order of the two texts in the pair matter? Expected: yes, the cross-encoder is not symmetric; feed the query first, or recall collapses.
  • (level 3) A team promises a p95 under 100 ms with a 22M parameter reranker. What do you plan first? Expected: memory, because the weights take 88 MB at float32, and batching, because scoring the N candidates one by one multiplies the latency by N.

Explain the + 1 inside the logarithm, say what k1 and b control, and describe what happens to a term that appears in more than half of the documents. python idf = math.log((self.n_docs - df + 0.5) / (df + 0.5) + 1) numerator = tf * (self.k1 + 1) denominator = tf + self.k1 * (1 - self.b + self.b * doc_len / self.avg_dl) score += idf * numerator / denominator

Level 3 of 4 · about 10 minutes to answer well.

Short answer. The + 1 inside the log is the smoothed inverse document frequency: without it a term that is in most of the documents gets a negative weight, and with it the weight stays positive. k1 sets how fast repeated occurrences stop adding score, and b sets how much a long document is penalized. A term in most documents gets a weight near zero, which is the right treatment for a stop word.

The inverse document frequency.

The ratio inside the log is the number of documents without the term, plus a half, over the number with the term, plus a half. When fewer documents contain the term than not, the ratio is above one and the log is positive. When the term crosses the half-corpus line the ratio drops below one and the log alone turns negative. The + 1 keeps it positive. The capstone lesson notes that this matters for stop words, which appear in most documents, and in small corpora where one common term can cross the line.

Term frequency saturation.

The term frequency factor is tf * (k1 + 1) over tf + k1 * (...). As tf grows the factor approaches k1 + 1, so a document that repeats a term 50 times is not 50 times more relevant than one that has it once. The advanced RAG lesson defaults k1 to 1.2; the capstone lesson uses 1.5 and calls it the published recommendation, with the advice not to move it without a benchmark.

Length normalization.

b scales the length term. At b of zero, document length is ignored. At b of one, the length penalty is full. Both lessons default to 0.75: longer documents are penalized, but not linearly.

Field weights.

The capstone implements field weighting as a multiplier on term counts at index time, for example the symbol name repeated above the body. The scoring code stays the same.

Plausible wrong answers.

  • "The +1 avoids a logarithm of zero." The ratio is never zero because of the half in the numerator; the +1 keeps the weight from going negative when the term passes half the corpus.
  • "k1 is the number of results to keep." k1 is the term frequency saturation constant.
  • "A higher b favors long documents." A higher b penalizes length more; b at zero ignores length.

Follow-ups an interviewer may ask.

  • (level 3) What is the weight of a term that appears in every document? Expected: df equals the document count, the ratio inside the log is near zero, the log of about one is near zero, so the term adds almost nothing.
  • (level 3) A document repeats a query term 50 times. How does its score compare with one occurrence? Expected: it is not 50 times higher; the term frequency factor saturates toward k1 plus 1.
  • (level 4) When would you move b? Expected: up when long documents really say less per word, and down toward zero when document length has nothing to do with topic.
  • (level 4) The two lessons default k1 differently. What do you do? Expected: keep the published default unless a benchmark on your own corpus says otherwise, and tune k1 and b by re-running the eval harness rather than by intuition.

Defend a designDesign a code search service that answers questions such as "how is the upload retry budget enforced" across 10 repositories with about 2M lines of code, and that stays fresh on every push. What is different from document retrieval, and where does it break?

Level 4 of 4 · about 30 minutes to answer well.

Short answer. Chunk at syntax tree nodes, functions and classes, not at fixed windows, and give each chunk three retrievable forms: a dense code embedding, BM25 terms with the symbol name weighted above the body, and a one-sentence natural-language summary. Retrieve hybrid, rerank with a cross-encoder, and synthesize with mandatory file and line citations that a post-filter enforces. Freshness is the hard part: a push triggers a symbol-level diff so that only changed chunks re-embed and only affected cross-file edges recompute.

Why fixed windows fail on code.

A fixed window cuts an identifier in half and separates a function body from its signature. The capstone parses each file with a syntax tree parser, extracts function and class nodes, and emits one chunk per node with its repository, path, start line, end line, symbol and body. The chunk boundary is the unit the user wants cited.

Three representations per chunk.

Form Catches
Dense embedding of the code paraphrased questions about behavior
BM25 with field weights, symbol name 4, summary 2, body 1 literal symbol names and "find the function named X"
A one-sentence summary from a small cached model a user who says "authorized" when the code says check_permission

Users ask in English about code that uses other words. The summary adds the modality that neither the code embedding nor the lexical index covers.

The symbol graph.

Record edges for imports, calls and inheritance across files and repositories. At query time, expand retrieval along the edges so that a question which crosses four repositories still finds the chain from the caller to the budget configuration.

The query path.

Retrieve dense and BM25 in parallel, de-duplicate by repository, path and symbol, rerank the top 50 and keep the top 10, synthesize with a cached system prompt, and require a repository, path and line range anchor on every claim. A claim without an anchor is flagged for a re-ask or dropped.

Incremental freshness.

A push triggers a diff of changed files and changed symbols. Only chunks whose text changed re-embed. The cross-file edges of the changed chunks recompute, which covers imports, calls and inheritance, so a changed call or base class does not leave a stale edge. A deleted file or symbol removes its chunks from the dense and lexical indexes and its edges from the graph, so search cannot return it after the push. The capstone's target is a 50-file push searchable in under 60 seconds on the 2M line fleet.

Evaluation.

Label 100 cross-repository questions with gold file and line answers. Measure MRR at 10, nDCG at 10, citation faithfulness as the fraction of claims with a verifiable anchor, and p50 and p99 latency. Re-run the set weekly and alert on an MRR at 10 drop above 5 percent.

Where it breaks.

  • Generated code. Boilerplate from code generators poisons retrieval with near duplicates; flag generated chunks in the payload and down-weight them. The capstone injects 20 percent generated code to show the effect.
  • Monorepo duplication. Repeated utility code spreads the lexical signal over copies; de-duplicate by symbol.
  • The long tail. Rarely imported symbols have weak embeddings; the lexical side and the summary carry them.
  • A big push. A commit that retouches half the files is where the incremental path is tested; measure the push-to-searchable time, not only the average.

Plausible wrong answers.

  • "Chunk code every 512 tokens like prose." Fixed windows cut identifiers in half and separate a function from its signature; cut at syntax tree nodes.
  • "Re-index the whole fleet on every push." Two million lines per commit never catches up; diff at the symbol level.
  • "Citations are optional for code answers." The capstone rejects any claim without a file and line anchor; the post-filter drops or re-asks.

Debug a failureSupport agents search the knowledge base with the exact error code from a ticket, such as E-4021. The vector search returns articles about error handling in general and misses the one article that contains that code. What is happening, and what do you add?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The embedding model treats a rare code as noise, so the query vector lands near articles about errors in general and not near the one exact match. Add a lexical index with BM25 next to the vector index, run both for every query, and merge the two ranked lists with reciprocal rank fusion. The exact token wins on BM25, and the fused list puts that article first.

Two retrievers, two strengths.

Semantic search understands meaning. "How do I cancel my subscription" matches "steps to terminate your plan" with no shared word. It misses exact matches, because a code such as E-4021 carries no meaning for the model to embed.

Lexical search does the opposite. BM25 scores a document by summing, over the query terms, an inverse document frequency factor times a saturating term frequency factor with a length correction. A term that appears in few documents weighs most, so a rare code is exactly what BM25 is best at. It fails when the query and the document share no words.

Hybrid search.

Run both retrievers in parallel and fuse by rank: each document gets the sum of one over k plus its rank in each list, with k at 60. The capstone demo shows the three cases. The literal symbol query sits at BM25 rank 1 and dense rank 4, and fuses to rank 1. The paraphrased query sits at BM25 rank 6 and dense rank 1, and fuses to rank 1. The fusion wins on both query classes, so the fix for the error code does not cost the paraphrased queries.

Two details that matter.

  • Field weighting. If the codes live in a title or symbol field, repeat those tokens at index time so a title match counts more than a body match. The math stays the same.
  • Out-of-vocabulary codes. A code present in the ticket and absent from every article gets zero from BM25, because its document frequency is zero, while the dense side still returns plausible-looking neighbors. De-duplicate by document so the empty lexical side adds no stray rank contributions. Rank fusion still scores the documents that only the dense side returns, so they stay in the fused list and can rank first. Check that a retrieved article contains the code, and when none does, say that no retrieved article contains it instead of answering from the neighbors.

Plausible wrong answers.

  • "Switch to a better embedding model." A rare code has no meaning to learn; the fix is a lexical signal next to the semantic one.
  • "Lower the similarity threshold so more articles come back." More neighbors on the wrong topic do not include the one exact match.
  • "Replace the vector search with BM25." Then the queries that share no words with the article fail; run both and fuse.

Follow-ups an interviewer may ask.

  • (level 2) Why does BM25 give a rare code so much weight? Expected: the inverse document frequency factor; a term in few documents scores high and a term in most documents scores low.
  • (level 2) The code is in the ticket but in no article at all. What does each retriever return? Expected: BM25 contributes nothing for that term, and the dense retriever still returns neighbors that look plausible and are wrong, and the fusion keeps them; check that a retrieved article contains the code, and when none does, say that no retrieved article contains it.
  • (level 3) How do the paraphrased queries fare after you add the lexical index? Expected: they still win, because the fusion is rank based; in the demo the paraphrased query sat at BM25 rank 6 and dense rank 1 and fused to rank 1.
  • (level 3) The codes live in a short title field and the body is long prose. What do you tune? Expected: field weighting, which repeats the title tokens at index time so a title match counts more.

Defend a designA question asks what changed in the security policy last month. Your vector search returns a two-year-old security document because it is semantically close. Design the retrieval step so that this cannot happen, and say what else the same mechanism buys you in a regulated deployment.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Store metadata with each chunk, such as the source, the creation date, the category, the author and the version, and filter on it before the similarity search runs. For this question the filter is the security category and the last 30 days, so the old document is never a candidate. Under regulation the same pre-filter carries role labels and jurisdiction tags, so a user only retrieves chunks they are allowed to see.

Pre-filter, not post-filter.

A filter after the top k comes back can leave nothing: if every slot in the top k went to old documents, the right one never had a chance. A filter applied ahead of the search shrinks the space the similarity search runs over, which the advanced RAG lesson calls critical for performance at scale, and an excluded document cannot fill a slot. Vector stores support this as metadata pre-filtering.

Defend a designA regulated-domain assistant serves analysts in two jurisdictions from one index. In a red-team probe, a question asked under one jurisdiction returned a contract clause that belongs to the other. The reranker and the generator behave as designed. Where is the leak, how do you close it, and how do you prove that it stays closed?

Level 4 of 4 · about 15 minutes to answer well.

Short answer. The leak is in retrieval: the jurisdiction tag was not applied as a pre-filter before the similarity search, so a semantically close chunk from the other jurisdiction entered the candidate pool, and nothing downstream is built to remove it. Close it by tagging every chunk with role and jurisdiction at ingestion and filtering on both before hybrid retrieval runs. Prove it with a cross-jurisdiction probe set in the red-team suite, scored pass or fail with a severity, and run before every release.

Why downstream stages cannot save you.

The reranker orders the candidates it receives by relevance, and the leaked clause is relevant. The generator cites what it is given. The output guard scrubs personal data and blocks forbidden topics; it does not know which jurisdiction a clause belongs to. Access control has to happen before the text reaches the prompt, and the only stage that sees the whole corpus is retrieval.

The capstone order.

Filter by role and jurisdiction first. Then run dense and BM25 retrieval in parallel, fuse by rank, send the top 20 to the reranker, the top 5 to the generator, then the guards, then cite and return. The tags come from ingestion, where each chunk receives a summary, a role label and a jurisdiction tag.

Closing it.

  1. Tag at ingestion, and make ingestion refuse a chunk that has no tag.
  2. Filter before retrieval, not on the top k after it; a post-filter can leave an empty result and still lets an untagged chunk through.
  3. Treat the caller's jurisdiction as a request parameter, never as a hint in the prompt.

Proving it.

The capstone runs a pre-release red team of 50 adversarial prompts that include cross-jurisdiction leaks, scored pass or fail with a severity. Its exercise adds a second corpus slice under another jurisdiction and runs a 20-question cross-jurisdiction probe. Put that probe in the release gate for every change to ingestion or retrieval, and carry the leak count on the drift dashboard as a hard zero.

Plausible wrong answers.

  • "Add a sentence to the system prompt about the user's jurisdiction." The model cannot verify which jurisdiction a chunk belongs to; access control belongs in retrieval.
  • "Separate indexes solve it, no tags needed." Role filtering still needs labels, shared documents get duplicated, and the probe is still needed to prove the split holds.
  • "The red team passed once, so it is closed." One pass proves one build; the probe runs on every ingestion or retrieval change.

Read the codeRead this retrieval function from the chunking lesson. What problem does the two-level layout solve, what does the seen set do, and how many parents can the function return? python def retrieve_parent(child_query, mapping, encoder, top_k=3): child_embs = encoder.encode([m["child"] for m in mapping], normalize_embeddings=True) q_emb = encoder.encode([child_query], normalize_embeddings=True)[0] scores = child_embs @ q_emb top = np.argsort(-scores)[:top_k] seen, parents = set(), [] for i in top: if mapping[i]["parent_idx"] not in seen: parents.append(mapping[i]["parent"]) seen.add(mapping[i]["parent_idx"]) return parents

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Small child chunks are indexed for a precise match and the larger parent is returned for context, which removes the trade-off between a precise hit and enough surrounding text. The seen set drops a parent that several top children map to, so the prompt does not receive the same text twice. For a mapping that is not empty and a positive top_k, the function returns between one and top_k parents, fewer when children share a parent; an empty mapping or a top_k of zero returns none.

The layout.

Standard chunking forces a choice: small chunks match precisely but lack context, large chunks carry context but cover many topics. The two-level layout indexes small children and stores the parent each child came from. The chunking lesson splits parents at 2048 and children at 256 by default, and the advanced RAG lesson draws a 512-token parent with four 128-token children. A query about one detail matches one child precisely, and the prompt receives the whole parent, including the lines around the detail.

Walk the function.

  1. Encode every child and the query with normalization on, so the matrix product equals the cosine.
  2. Sort children by score and keep the top k indices.
  3. For each top child, look up its parent index; if that parent was not seen, append the parent text and mark it.
  4. Return the parents in the order of their best child.

Why de-duplicate.

Several children of one parent often match the same query, because they sit in the same section. Without the set, the prompt would receive the same parent twice or three times and waste its context budget. The lesson calls this the key insight of the pattern.

What production changes.

The function re-encodes every child on each call. A real index stores the child vectors once and only embeds the query. The two-level layout also degrades gracefully: a poor child match still returns a reasonable parent.

Plausible wrong answers.

  • "Return the parent of every top child, duplicates included." Several children map to one parent, and the repeated text wastes the context budget.
  • "Make the child as large as the parent." Then there is no precision gain; the point is a small match unit and a large context unit.
  • "The function always returns exactly top_k parents." It returns fewer when children share a parent.

Follow-ups an interviewer may ask.

  • (level 2) Why index the child and not the parent? Expected: a small chunk matches a specific question precisely, while a large chunk covers many topics and its embedding points nowhere in particular.
  • (level 2) Why a plain matrix product and no cosine? Expected: the vectors are normalized at encode time, so the dot product equals the cosine.
  • (level 3) What does this function do on every call that production code must not? Expected: it re-encodes all the children; store the child vectors once at index time and embed only the query.
  • (level 3) Two parents each have one matching child, and a third parent has three matching children below the cut. What does the function miss? Expected: it ranks by the best child only; a parent with several good children gets no extra credit unless you aggregate child scores per parent.

Weigh a trade-offYour pipeline offers three query rewriters: write a hypothetical answer and search with it, write several paraphrases and merge, or decompose it into sub-questions and merge. A user asks "what does our team do when uploads fail and the budget is gone?" Which rewriter fits, and when would each of the other two be the right pick?

Level 2 of 4 · about 9 minutes to answer well.

Short answer. Split it, because the question joins two topics with a conjunction, an upload failure and an exhausted budget, and no single chunk holds both. The hypothetical answer fits a jargon-heavy question whose words do not match the corpus vocabulary. Paraphrases fit a short question that could be asked in many equally good ways.

The three, side by side.

Rewriter What it does Wins when Loses when
Hypothetical answer the model writes a passage in the corpus voice; its embedding replaces the query vector the query and the corpus use different words the model invents an identifier that is not in the index
Paraphrases the model writes N rewrites; retrieve each; merge the lists by rank fusion any of several phrasings would have asked it better the rewrites all converge, so the merge equals one retrieval
Sub-questions the model splits the question; retrieve each part; merge the question has conjunctions or two unrelated topics the question is atomic and gets split anyway

Costs.

Each rewriter adds one model call before retrieval, and the advanced RAG lesson puts the hypothetical answer at 500 to 2000 ms extra. The retrievals after the call run in parallel, so the model call is the floor. Cache the rewriter output by a hash of the query, because many queries repeat.

Guards.

  • Cap the hypothetical to two or three sentences; longer ones collect noise, shorter ones lose the lexical signal.
  • Add an explicit diversity instruction to the paraphrase prompt, and drop near duplicates by Jaccard overlap.
  • Check that the sub-questions are distinct before the fan-out, so an atomic question returns unchanged.

Choosing per query.

The end-to-end lesson picks a strategy from heuristics on query length, conjunctions and jargon ratio. The other option is to run all three in parallel and fuse the three result sets; the cost is three model calls and one fusion.

Plausible wrong answers.

  • "Always write the hypothetical answer, it is the strongest." It bridges a vocabulary gap and does nothing for a two-topic question; an invented identifier can also hurt the lexical side.
  • "A rewriter fixes a weak retriever." It only moves the query closer to the corpus voice; a chunker that cut the answer still loses.
  • "Split every query into sub-questions." Atomic questions get over-split and come back worse than the original.

Follow-ups an interviewer may ask.

  • (level 2) What does a rewriter cost in latency? Expected: one model call before retrieval, 500 to 2000 ms for a hypothetical answer in the advanced RAG lesson, with the retrievals after it in parallel.
  • (level 2) The paraphrases come back nearly identical. What happens and what do you change? Expected: the merged list equals one retrieval; add a diversity instruction and drop near duplicates by Jaccard overlap.
  • (level 3) The splitter turns an atomic question into three parts. What is the damage and the guard? Expected: the same document comes back three times at a lower rank and the merge is worse; test that the parts are distinct before the fan-out.
  • (level 3) How does the end-to-end system choose without a human? Expected: heuristics on length, conjunctions and jargon ratio, or run all three and fuse.

Read the codeRead this fusion function from the advanced RAG lesson. Explain the + 1 in the denominator, say what the function ignores on purpose, and describe what happens to a document that appears in only one of the lists. python def reciprocal_rank_fusion(ranked_lists, k=60): scores = {} for ranked_list in ranked_lists: for rank, (doc_id, _) in enumerate(ranked_list): if doc_id not in scores: scores[doc_id] = 0.0 scores[doc_id] += 1.0 / (k + rank + 1) fused = sorted(scores.items(), key=lambda x: x[1], reverse=True) return fused

Level 2 of 4 · about 8 minutes to answer well.

Short answer. enumerate starts at zero, so the + 1 turns the index into a rank that starts at one, and the top document gets 1/61 as the published formula defines. The function drops the score that came with each document, because ranks are the comparable unit across retrievers. A document present in one list gets one contribution and no penalty for the other, so it can still place well if it ranked high where it appeared.

Walk the loop.

  1. The outer loop visits each ranked list, for example the vector list and the BM25 list.
  2. The inner loop reads each entry as a pair and discards the second element, the retriever's own score.
  3. The contribution for a document at zero-based index rank is 1.0 / (k + rank + 1), which is one over k plus the one-based rank.
  4. Contributions sum per document id across the lists.
  5. The result is sorted by the summed contribution, highest first.

What the caller does.

The hybrid search in the same lesson asks each retriever for three times the final top k, fuses the two lists and returns the first top k of the fused result. The deeper candidate lists let a document that is good in both retrievers reach the final list even when it is first in neither.

The capstone version.

The hybrid retrieval lesson adds a weights list with one multiplier per ranked list, applied to each rank contribution, and raises an error when the number of weights does not match the number of lists. It also keeps a map from document id to document so it can return documents instead of ids.

The key.

Fusion runs on the document id. Two chunks of the same document are two keys. The capstone lesson recommends de-duplication by document, because a term that is out of vocabulary for BM25 gives a zero and the dense retriever still returns noise; per-document fusion absorbs that.

Plausible wrong answers.

  • "The function averages the two scores." It never reads the scores; it sums a function of the ranks.
  • "A document missing from one list is penalized." It gets no contribution from that list, which is not a penalty; it can still rank first if it was first in the other.
  • "k is the number of results to keep." k is the decay constant in the denominator; the caller slices the fused list to the final top k.

Follow-ups an interviewer may ask.

  • (level 2) What changes if you delete the + 1? Expected: the top document gets 1/60 instead of 1/61, the curve shifts a little, and the constant no longer matches the published definition.
  • (level 2) Why does the caller fetch three times the final k from each retriever? Expected: a deeper list lets a document that ranks well in both retrievers reach the fused top k even when it is first in neither.
  • (level 3) How does the capstone version let you favor one retriever? Expected: a weights list with one multiplier per ranked list, applied to the rank contribution, with an error when the lengths differ.
  • (level 3) What is the fusion key, and why does that matter for chunks? Expected: the document id; chunks of one document are separate keys unless you de-duplicate by document, which the lesson recommends.

Explain the mechanismYou have a BM25 ranked list and a vector ranked list for the same query. An engineer proposes to merge them as alpha times the BM25 score plus one minus alpha times the cosine. What is wrong with that, and what do you do instead?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. BM25 scores are unbounded and change with the corpus, while a cosine sits between -1 and 1, so a weighted sum needs a new alpha every time you re-index. Reciprocal rank fusion merges by rank instead: each document gets the sum, over the lists, of one over k plus its rank, with k at 60. Ranks are comparable across the two retrievers, so nothing has to be calibrated.

The formula and one worked case.

A document at rank 1 in the vector list and rank 5 in the BM25 list gets 1/(60+1) + 1/(60+5) = 0.0164 + 0.0154 = 0.0318. A document at rank 3 and rank 2 gets 1/(60+3) + 1/(60+2) = 0.0159 + 0.0161 = 0.0320. The second document wins by a hair: a document that is good in both lists beats one that is first in one list and deep in the other.

What k does.

With k at 60, rank 1 contributes 1/61 and rank 10 contributes 1/70. The contribution decays slowly, so deep candidates still vote. A smaller k lets the top results dominate. A larger k flattens the curve.

Why ranks and not scores.

A linear combination of scores needs an alpha tuned per corpus, and it breaks on every re-index because the BM25 score spread moves. Ranks do not have a scale. The capstone lesson notes that the rank-based baseline has beaten score interpolation in every public TREC track since 2010, and that the production search engines that document hybrid search came to the same conclusion.

A knob that keeps the method honest.

If you have evidence that one retriever beats the other on your data, multiply its rank contribution by a weight. The rank decay shape stays and the method stays scale free.

Plausible wrong answers.

  • "Normalize both scores to a zero to one range and add them." The two distributions still differ per query and per corpus, so the tuned balance drifts after a re-index.
  • "Take the document with the highest score in either list." One unbounded BM25 score then dominates every query; ranks are the comparable unit.
  • "Fusion is only a tie-breaker between the two lists." In the demo it decides the top result on every query class; a document good in both lists beats one that is top in only one.

Follow-ups an interviewer may ask.

  • (level 2) What does the constant k control? Expected: how fast the contribution decays with rank; at 60, rank 1 gives 1/61 and rank 10 gives 1/70, so deep candidates still count.
  • (level 2) When would you lower k? Expected: when the top result of each list should dominate the fused order.
  • (level 3) You know BM25 is better on your corpus. How do you express that? Expected: a per-list weight that multiplies the rank contribution of the BM25 list; the decay shape and the scale-free property both survive.
  • (level 3) Why does the rank method survive a re-index when the weighted sum does not? Expected: ranks keep their meaning when the corpus changes, while BM25 scores and their spread move, so the tuned alpha no longer fits.

Check your understanding

Q1What is the limitation of basic top-k semantic search in RAG?

Basic semantic search matches surface-level meaning. 'What was revenue last quarter?' retrieves chunks about 'revenue strategy' (semantically similar) instead of the chunk saying '$47.2M in Q3 2025' (which uses 'earnings').

Q2What is hybrid search in the context of RAG?

BM25 catches exact keyword matches (e.g., '$47.2M' or 'Q3'). Semantic search catches meaning matches. Combining them with a reranker gives the best of both worlds: precision on specific terms plus recall on semantic variants.

Q3What does a cross-encoder reranker do in an advanced RAG pipeline?

Bi-encoder similarity (used for initial retrieval) is fast but approximate. A cross-encoder processes the full query-document pair together with cross-attention, giving much more accurate relevance scores for reranking the top candidates.

Q4What is the HyDE (Hypothetical Document Embedding) query transformation technique?

The original query 'What was Q3 revenue?' might not embed close to the answer chunk. HyDE asks the LLM to generate a hypothetical answer ('Q3 revenue was approximately...'), then uses that as the search query, which embeds closer to actual answer-containing chunks.

Q5Why does parent-child chunking improve RAG over flat chunking?

Small chunks (200 tokens) embed precisely but lack context. Large chunks (2000 tokens) have context but embed imprecisely. Parent-child uses small chunks for search accuracy but returns the parent chunk for generation context.
