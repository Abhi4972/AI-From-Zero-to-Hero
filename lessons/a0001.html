The problem

In plain words first

A development environment is the set of programs your code depends on: the operating system tools, a package manager, a language runtime such as Python, and libraries such as NumPy and PyTorch. Each layer is installed on top of the one below. When lessons break with ModuleNotFoundError or "CUDA not available", the cause is almost always one of these layers, not your code.

Tip

To run them, clone it once with git clone https://github.com/rohitg00/ai-engineering-from-scratch and run the commands from inside that folder. Everything else on this page works without it.

You're about to learn AI engineering across 500+ lessons using Python, TypeScript, Rust, and Julia. If your environment is broken, every single lesson becomes a fight against tooling instead of learning.

Most people skip environment setup. Then they spend hours debugging import errors, version conflicts, and missing CUDA drivers. We're going to do this once, properly.

The idea

An AI engineering environment has four layers:

We install bottom-up. Each layer depends on the one below it.

The same idea as a formula

Will a model fit? A model with N parameters stored at b bytes each needs

weights=N×b bytes,b=4 (fp32), 2 (bf16, fp16), 1 (int8), 0.5 (4-bit)

Running it needs more than the weights: the activations of the current batch, and for a chat model the cache of past tokens (Lesson 7.3). A margin of about 20% covers short prompts; long conversations need more.

Which Python runs? Your shell searches the folders of PATH from left to right and runs the first match. Activating a virtual environment puts .venv/bin first, so python and pip resolve there; sys.prefix then points into .venv.

Worked example
Sizing a model by hand
  • Qwen2.5-0.5B: 0.5×109×2=1 GB in bf16. Any laptop.
  • An 8-billion-parameter model such as Llama 3.1 8B: 8×2=16 GB in bf16, too much for a 16 GB laptop once the operating system takes its share; in 4-bit, 8×0.5=4 GB, which fits.
  • A 70B model in bf16: 70×2=140 GB, two 80 GB GPUs at least. In 4-bit: 35 GB, one large GPU or a 64 GB Mac.

The rule of thumb: gigabytes ≈ billions of parameters × bytes per parameter.

Check your mental model
  • ✗ "Installing a package with pip makes it available to every Python on my machine."
    ✓ It goes into whichever environment that pip belongs to. Install into one virtual environment and run another, and the import fails.
  • ✗ "No CUDA on my Mac means PyTorch is broken."
    ✓ CUDA is NVIDIA-only. On Apple Silicon, PyTorch uses the MPS backend instead, and torch.cuda.is_available() printing False is expected.
  • ✗ "I need a GPU to start."
    ✓ Every lesson in this volume runs on a laptop CPU. A GPU matters later, for training large models.

Step 2 · Python with uv

We use uv — it's 10-100x faster than pip and handles virtual environments automatically.

curl -LsSf https://astral.sh/uv/install.sh | sh

uv python install 3.12

uv venv
source .venv/bin/activate  # or .venv\Scripts\activate on Windows

uv pip install numpy matplotlib jupyter

Verify:

import sys
print(f"Python {sys.version}")

import numpy as np
print(f"NumPy {np.__version__}")
a = np.array([1, 2, 3])
print(f"Vector: {a}, dot product with itself: {np.dot(a, a)}")

Predict before you run

After uv venv and source .venv/bin/activate, what does which python print, and will python -c "import numpy" work before you run uv pip install numpy? (Solution P1.)

Why this came about
Why a virtual environment

Each project gets its own folder of packages (.venv), so upgrading NumPy for one project cannot break another. Python can tell you whether you are inside one: in a virtual environment sys.prefix (where packages go) differs from sys.base_prefix (the Python it was made from).

import sys
print("inside a virtual environment:", sys.prefix != sys.base_prefix)

Step 3 · Node.js with pnpm

For TypeScript lessons (agents, MCP servers, web apps).

curl -fsSL https://fnm.vercel.app/install | bash
fnm install 22
fnm use 22

npm install -g pnpm

node -e "console.log('Node', process.version)"

The fnm installer checks for unzip first and exits with Not installing fnm due to missing dependencies. when it is absent: on Linux it unpacks a zip archive, on macOS it installs through Homebrew. macOS ships unzip; Ubuntu, Debian, and WSL2 get it from the Step 1 apt line (sudo apt install -y unzip if you skipped that step).

macOS / Apple Silicon (M1/M2/M3/M4): If the installer stops with Error: Cannot install under Rosetta 2 in ARM default prefix (/opt/homebrew), your terminal is running under Rosetta 2 (arch prints i386) while Homebrew is a native arm64 build. Install fnm forcing arm64, wire it into your shell, then rerun the commands above from fnm install 22:

arch -arm64 brew install fnm
echo 'eval "$(fnm env --use-on-cd)"' >> ~/.zshrc
source ~/.zshrc

Step 6 · GPU Setup (If You Have One)

NVIDIA (Linux / Windows):

nvidia-smi

# Install PyTorch with CUDA
uv pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124

macOS / Apple Silicon (M1/M2/M3/M4): There is no CUDA on a Mac — that's expected, not a failure. Do not pass --index-url .../cuXXX (those wheels are Linux/Windows only, so the install fails). Install the plain build, which includes Apple's MPS (Metal) GPU backend:

uv pip install torch torchvision torchaudio

Verify (works on any platform):

import torch
print(f"CUDA available: {torch.cuda.is_available()}")           # False on macOS — expected
print(f"MPS available:  {torch.backends.mps.is_available()}")   # True on Apple Silicon
if torch.cuda.is_available():
    print(f"GPU: {torch.cuda.get_device_name(0)}")
What you should see
CUDA available: False
MPS available:  False

No GPU? No problem. Most lessons work on CPU. For training-heavy lessons, use Google Colab or cloud GPUs.

Reading this output

On this page's server the check prints CUDA available: False and MPS available: False, because it runs on a plain CPU. On an NVIDIA machine with the right PyTorch build you see True and the card's name; on an Apple Silicon Mac, MPS is True. If you have an NVIDIA card and still see False, the usual cause is a CPU-only PyTorch build: reinstall it with the --index-url .../cu124 line above.

import sys, platform, shutil, os, importlib.metadata as md
# What this page's own machine has, and how big a model its memory could hold.
print(f"Python {sys.version.split()[0]} on {platform.system()} {platform.machine()}, {os.cpu_count()} CPU cores")
for pkg in ["numpy", "torch", "transformers", "pandas"]:
    try:
        print(f"  {pkg:13s} {md.version(pkg)}")

        print(f"  {pkg:13s} not installed")
print("  uv on PATH:", shutil.which("uv") is not None, "| git on PATH:", shutil.which("git") is not None)
ram = os.sysconf("SC_PAGE_SIZE") * os.sysconf("SC_PHYS_PAGES") / 1e9
print(f"RAM: {ram:.1f} GB")
print(f"{'model size':>11} {'fp32':>8} {'bf16':>8} {'int8':>8} {'4-bit':>8}   fits in this RAM (bf16, +20%)?")
for p in [0.5e9, 3e9, 7e9, 70e9]:

Recap
What to keep from this lesson
  • An environment has four layers: system tools, package managers, language runtimes, AI libraries. Install bottom-up.
  • Use one virtual environment per project; uv venv makes it and uv pip install fills it.
  • Check the GPU with torch.cuda.is_available() (NVIDIA) or torch.backends.mps.is_available() (Apple Silicon). A CPU is enough for this volume.
  • Fix the first failed check of the verify script before looking at the next one.

Solutions

SolutionP1 · A fresh environment

which python prints the python inside your project's .venv/bin/ folder, because activation puts that folder first on your PATH. import numpy fails with ModuleNotFoundError: No module named 'numpy': a new virtual environment starts empty, whatever you installed elsewhere.

SolutionB1 · Nothing installed

ModuleNotFoundError: No module named 'numpy'. Python itself (layer 3) is fine, since the error comes from Python; the missing piece is the library layer (layer 4). Run uv pip install numpy inside the activated environment and the snippet works.

What's current (2024–2026)
  • uv is the default Python tool. Astral's uv (installer, virtual environments, lock files and Python versions in one fast binary) is now the common setup in new AI repositories, this course's included; pip and venv still work underneath.
  • Current Python. Python 3.15 (October 2026) adds a built-in sampling profiler and lazy imports; 3.14 made the free-threaded (no-GIL) build officially supported. Most AI libraries publish wheels for 3.12–3.14, so check a package's wheels before moving to the newest version.
  • Reproducible environments in the cloud. Dev containers and GitHub Codespaces give every contributor the same image, which is how many teams avoid "works on my machine" for GPU stacks.

outputs/prompt-env-check.md

---
name: prompt-env-check
description: Diagnose and fix AI engineering environment setup issues
phase: 0
lesson: 1
---

You are an AI engineering environment diagnostician. The user is setting up their development environment for an AI/ML course that uses Python, TypeScript, Rust, and Julia.

When the user describes an issue:

1. Identify which layer is broken (system, package manager, runtime, or library)
2. Ask for the output of the relevant diagnostic command
3. Provide the exact fix — not a general guide, the specific commands to run

Common issues and fixes:

- **Python version too old**: Install with `uv python install 3.12`
- **CUDA not detected (Linux/Windows + NVIDIA)**: Check `nvidia-smi`, then reinstall PyTorch with the correct CUDA version
- **macOS / Apple Silicon**: There is no CUDA on macOS — this is expected, not a failure. Do not use `--index-url .../cuXXX`; install plain `uv pip install torch torchvision torchaudio` and use the MPS (Metal) backend. Verify with `python -c "import torch; print(torch.backends.mps.is_available())"` (should print `True`)
- **Node.js missing**: Install with `fnm install 22`
- **Import errors after install**: Check you're in the right virtual environment with `which python`
- **Permission errors**: Never use `sudo pip install`, use `uv` with a virtual environment instead

Always verify the fix worked by asking the user to run the verification script:
```bash
python phases/00-setup-and-tooling/01-dev-environment/code/verify.py
```
