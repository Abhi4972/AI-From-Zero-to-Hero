In plain words first
The idea in one line

Traditional load testers were not designed for streaming responses, variable output lengths, token-level metrics, or GPU saturation. Two traps bite most teams. The GIL trap: Locust's token-level measurement runs tokenization under the Python GIL, which competes with request generation under heavy concurrency; tokenization backlog then inflates reported inter-token latency — your client is the bottleneck, not the server. The prompt-uniformity trap: identical prompts in a loop test one point on the token distribution; real traffic has variable length and diverse prefix matches. LLMPerf fixes this with --mean-input-tokens + --stddev-input-tokens. Tool mapping in 2026: LLM-specialized (GenAI-Perf, LLMPerf, LLM-Locust, guidellm) for token-level accuracy; k6 v2026.1.0 + k6 Operator 1.0 GA (Sept 2025) — streaming-aware, Kubernetes-native distributed via TestRun/PrivateLoadZone CRDs, best for CI/CD gates; Vegeta for Go constant-rate saturation; Locust 2.43.3 only with LLM-Locust extension for streaming. Load patterns: steady-state, ramp, spike (autoscaling test), soak (memory leaks).

The problem

In plain words first

A load test sends a server realistic traffic at increasing volume to find where it breaks before users do. LLM servers have two traps that make ordinary load tests lie. The prompt-uniformity trap: if every simulated user sends the same prompt, the server's prefix cache answers almost all of them from memory, and you measure a cache, not a model. The GIL trap: Python load tools such as Locust tokenize responses in the same process that sends requests, so at high concurrency the client slows down and its timing numbers include its own delays. A good LLM load test samples prompts from a realistic distribution of lengths and contents, uses a tool that does not bottleneck itself (LLMPerf, k6, GenAI-Perf, LLM-Locust), and runs four shapes of traffic: steady, ramp, spike and soak.

You k6-tested your LLM endpoint at 500 concurrent users. It held. You shipped. In production at 200 actual users the service fell over — P99 TTFT exploded, GPUs pinned.

Two things happened. First, k6 sent 500 identical prompts — your request-coalescing and prefix caching made it look like you were handling 500 concurrent decodes when you were actually handling one. Second, k6 doesn't track inter-token latency on streaming responses the way the eye experiences it; it sees one HTTP connection, not 500 tokens arriving at varying intervals.

Load testing for LLMs is its own discipline.

Idea 1 · The GIL trap (Locust)

Locust uses Python and runs tokenization client-side under the GIL. Under high concurrency the tokenizer queues behind request generation. Reported inter-token latency includes client-side tokenization backlog. You think the server is slow; it's the test harness.

Fix: LLM-Locust extension moves tokenization to separate processes, or use a compiled-language harness (k6, LLMPerf using tokenizers.rs).

Idea 2 · The prompt-uniformity trap

All known load testers let you configure one prompt. In a loop test of 10,000 iterations the exact same prompt sends each time. Server sees the same prefix every time — prefix cache hits approach 100%, throughput looks great.

Fix: sample from a prompt distribution. LLMPerf uses --mean-input-tokens 500 --stddev-input-tokens 150 — diverse lengths, diverse content.

Idea 3 · Four load patterns

  1. Steady-state — constant RPS for 30-60 min. Catches: baseline performance regressions.
  2. Ramp — linearly increase RPS from 0 to target over 15 min. Catches: capacity breakpoint, warm-up anomalies.
  3. Spike — sudden 3-10x RPS for 2 min then back. Catches: autoscaling latency, queue saturation, cold-start impact.
  4. Soak — steady-state for 4-8 hours. Catches: memory leaks, connection-pool drift, observability overflow.

Idea 4 · 2026 tool mapping

LLMPerf (Anyscale) — Python but Rust-backed tokenization. Mean/stddev prompts. Streaming-aware. Best default for performance runs.

NVIDIA GenAI-Perf — NVIDIA's reference. Uses Triton client; comprehensive metric coverage. Note its ITL excludes TTFT; LLMPerf's includes it. Two tools produce different TPOT for the same server.

LLM-Locust (TrueFoundry) — Locust extension that fixes the GIL trap. Familiar Locust DSL + streaming metrics.

guidellm — large-scale synthetic benchmarking.

k6 v2026.1.0 + k6 Operator 1.0 GA (Sept 2025): - k6 itself (Go, compiled, no GIL) added streaming-aware metrics. - k6 Operator uses TestRun / PrivateLoadZone CRDs for Kubernetes-native distributed testing. - Best for CI/CD gates and SLA testing.

Vegeta — Go, simpler than k6. Constant-rate HTTP saturation. Not LLM-aware but good for gateway / rate-limit testing.

Locust 2.43.3 stock — has the GIL trap for LLM. Only with LLM-Locust extension.

Idea 5 · SLA gate in CI

Run k6 on the PR with:

  • 30-50 iterations each at baseline RPS.
  • Gate: P50/P95 TTFT, 5xx < 5%, TPOT under threshold.
  • Break the build on breach.

Idea 6 · Realistic prompt distribution

Build from real traffic samples (if you have them) or from published distributions (e.g., ShareGPT prompts for chat, HumanEval for code). Feed the mean + stddev to LLMPerf. Avoid loop-with-one-prompt at all costs.

Idea 7 · Numbers you should remember

  • k6 Operator 1.0 GA: September 2025.
  • k6 v2026.1.0: streaming-aware metrics.
  • Typical LLMPerf run: 100-1000 requests at concurrency X.
  • Typical CI gate: 30-50 iterations per PR.
  • Four patterns: steady, ramp, spike, soak.

Worked example
What a uniform test hides

Suppose prefill costs about 0.4 ms per prompt token on a miss and the cached path about 80 ms flat.

  1. Uniform test: 500 requests, all with the same 2,000-token prompt. 499 are cache hits: TTFT about 80 ms every time. P99 = 80 ms.
  2. Realistic test: prompt lengths with mean 500 and standard deviation 150, mostly unique content. Cache hits only where a system prompt is shared; a 2,000-token unique prompt takes about 800 ms.
  3. The P99 in production is set by the long, unique prompts: about 800 ms, ten times what the uniform test reported.
  4. The same mistake hides concurrency effects: with one cached prefix there is no real prefill load, so the GPU never saturates.
Check your mental model

Which statements are right?

  • ✓ A loop over one prompt mostly measures the prefix cache.
  • ✗ Stock Locust is a good harness for streaming LLM latency at high concurrency. Its client-side tokenization runs under Python's GIL and inflates the latency it reports.
  • ✓ A soak test of 4–8 hours finds memory leaks a 10-minute test misses.
  • ✗ Load-testing at your expected peak is enough. Spike tests at 3–10× catch autoscaling and queueing failures.

Part 1 of 3 · Request, make_uniform_workload, make_realistic_workload, simulate

"""Load-test anti-pattern demonstrator — stdlib Python.

Simulates how uniform prompts inflate reported throughput via prefix-cache
and request-coalescing, while realistic distribution reveals the true ceiling.
"""

from __future__ import annotations

from dataclasses import dataclass
import random
import statistics


PREFIX_CACHE_HIT_TTFT_MS = 80
PREFIX_CACHE_MISS_TTFT_MS = 800
TPOT_MS = 15
BATCH_EFFICIENCY_SHARED_PREFIX = 0.8  # batch serves 1/0.8 = 1.25x fewer slots


@dataclass
class Request:
    prompt_tokens: int
    prefix_hash: str


def make_uniform_workload(n: int = 500) -> list[Request]:
    return [Request(2000, "single_prefix") for _ in range(n)]


def make_realistic_workload(n: int = 500, seed: int = 7) -> list[Request]:
    rng = random.Random(seed)
    reqs = []
    prefixes = [f"prefix_{i}" for i in range(80)]
    for _ in range(n):
        prompt = max(50, int(rng.gauss(500, 180)))
        reqs.append(Request(prompt, rng.choice(prefixes)))
    return reqs


def simulate(reqs: list[Request], concurrency: int) -> dict:
    cache: set[str] = set()
    ttft_samples: list[float] = []
    # serialize in groups of "concurrency"
    for i in range(0, len(reqs), concurrency):
        batch = reqs[i:i + concurrency]
        unique_prefixes = len({r.prefix_hash for r in batch})
        for r in batch:
            hit = r.prefix_hash in cache
            ttft = PREFIX_CACHE_HIT_TTFT_MS if hit else PREFIX_CACHE_MISS_TTFT_MS
            if not hit:
                cache.add(r.prefix_hash)
            ttft_samples.append(ttft)
    ttft_samples.sort()
    p50 = ttft_samples[len(ttft_samples) // 2]
    p99 = ttft_samples[int(len(ttft_samples) * 0.99) - 1]
    return {
        "n": len(reqs),
        "p50": p50,
        "p99": p99,
        "mean": statistics.mean(ttft_samples),
        "cache_hits": sum(1 for t in ttft_samples if t == PREFIX_CACHE_HIT_TTFT_MS),
    }

Part 2 of 3 · main

def main() -> None:
    print("=" * 95)
    print("PROMPT-UNIFORMITY TRAP: same test harness, different prompt distributions")
    print("=" * 95)

    for concurrency in (10, 50, 200):
        print(f"\nConcurrency = {concurrency}")
        header = f"{'Workload':22}  {'n':>5}  {'TTFT_P50':>9}  {'TTFT_P99':>9}  {'mean':>7}  cache_hits"
        print(header)
        print("-" * len(header))

        uniform = make_uniform_workload(500)
        u = simulate(uniform, concurrency)
        print(f"{'UNIFORM':22}  {u['n']:5}  {u['p50']:8.0f}ms  {u['p99']:8.0f}ms  {u['mean']:6.0f}ms  {u['cache_hits']:4}")

        realistic = make_realistic_workload(500)
        r = simulate(realistic, concurrency)
        print(f"{'REALISTIC':22}  {r['n']:5}  {r['p50']:8.0f}ms  {r['p99']:8.0f}ms  {r['mean']:6.0f}ms  {r['cache_hits']:4}")

    print("\nRead: uniform prompts make your endpoint look fast. Realistic prompts tell the truth.")
    print("LLMPerf: --mean-input-tokens + --stddev-input-tokens. Always.")

Recap
What to keep from this lesson

Solutions

SolutionP1 · Uniform against realistic

In code/main.py the gap is entirely in the tail: P50 is 80 ms for both, but P99 is 80 ms with uniform prompts and 800 ms with realistic ones, because 499 of 500 uniform requests are cache hits against 421 for the realistic mix. The concurrency levels are identical because the toy has no queueing model.

SolutionB1 · A gate that lied

(1) One fixed prompt: after the first request everything came from the prefix cache, so the gate measured cache latency. (2) No realistic length distribution: production's long prompts set the P95. A third common cause: the test ran against a warm, otherwise idle server, while production also has cold replicas and mixed traffic.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Explain the mechanismTwo engineers benchmark the same server on the same day and report numbers that differ by a few percent. Both used standard benchmark clients. Before you look at the server, what about the clients could explain the gap, and what rules would you set for the team?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The client is part of the measurement. On one vLLM server the SGLang client read a median first token 3 to 10 percent higher and an output throughput 2 to 8 percent lower than the vLLM client, the two clients sent different random prompts, and temperature 0.7 raised the time per token by 10 to 13 percent at one user against temperature 0. The rules: one client, one temperature, one prompt length distribution with the range ratio stated, a flush and a new seed per run, the clock recorded, and all of that written next to every number.

Three clients on one server.

The manual ran the SGLang client, vllm bench serve and its Rust version against one vLLM server with Qwen/Qwen3-0.6B, with a cache reset before every run and the clients alternated over two rounds. Output tokens per second at 64 users:

Temperature SGLang client vllm bench vllm bench, Rust
0 359, 348 379, 377 371, 365
0.7 331, 343 360, 363 356, 353

The two vLLM clients agreed within the noise at 1, 16 and 64 users. The SGLang client read a slower server: a median first token 3 to 10 percent higher, and at 16 and 64 users an output throughput 2 to 8 percent lower. The two clients send different prompt tokens from their random datasets, so part of a small gap can come from the prompts. Temperature 0.7 raised the median time per token over temperature 0 by 10 to 13 percent at one user and 3 to 6 percent at 16 and 64 users.

Four defaults that change the result.

The SGLang client makes choices before it measures anything:

Setting Default What it does to the result
--random-range-ratio 0.0 each length is drawn from 1 to the length you asked for, so the average prompt is about half of it
ignore_eos on every request generates exactly the output length you asked for
--request-rate inf all requests are sent at time 0, and only the concurrency cap holds them back
--warmup-requests 1 one request runs before the clock starts

The first row is the trap. With the default ratio, an input length of 512 gives an average prompt near 256 tokens, and the report says 512. Pass 1.0 or write the length distribution next to the result. With 1.0, 32 prompts of 512 tokens give an input total of 16384 in the report.

Fixed lengths form waves.

With the ratio at 1.0 every request has the same length, so requests that start together finish together and their replacements arrive together. At 16 users on the L4, fixed lengths gave a median time to first token of 1,996 ms and a P99 ITL of 82 ms; mixed lengths gave 291 ms and 300 ms. The two settings measure two different servers. Fixed lengths measure bursts, with a slow first token and smooth tokens. Mixed lengths measure steady traffic, with a fast first token and stalls in the stream. Keep 1.0 to compare two builds, and run your real length mix before you set a latency target.

The client's own queue.

The SGLang client sends every request from one Python process. A 2026 study found that such a client adds its own queue at high request rates and then reports a first token and a time per token higher than the server gave. Before you trust a number at a high rate, compare one client process with two processes that each send half the rate. The lesson names the same trap for a general load tester: tokenization under the interpreter lock in the client inflates the reported inter-token latency, and one prompt sent in a loop hits the prefix cache on almost every request and inflates the throughput.

Hand-written scripts.

One report measured 13 tokens per second for a large model on eight GPUs against 60 from a hosted API. The script counted words split on spaces and included the first-token time in the rate. A word is not a token, and TTFT is not decode time. Use the benchmark client, which counts tokens and keeps TTFT and TPOT apart.

The rules.

  1. One client, one version, named in every result.
  2. One temperature, named in every result.
  3. --random-range-ratio 1.0, or the length distribution written down.
  4. A flush and a new seed before every run, and the cached tokens recorded.
  5. The GPU clock recorded and the hot runs set aside.
  6. Throughput reported only together with the median and P99 TTFT and TPOT at the same cap.

Plausible wrong answers.

  • "Both are standard clients, so the numbers are comparable." On one server the SGLang client read 3 to 10 percent higher first-token times and 2 to 8 percent lower throughput than the vLLM client; a gap of a few percent can come from the client alone.
  • "Temperature does not change speed." Temperature 0.7 raised the median time per token 10 to 13 percent at one user and 3 to 6 percent at 16 and 64 users over temperature 0.
  • "Set the input length to 512 and the prompts are 512 tokens." With the default range ratio of 0.0 the average prompt is about 256 tokens; pass 1.0 or state the distribution.
  • "A load tester that handles HTTP handles model traffic." A generic tool sends one prompt in a loop, which hits the prefix cache almost every time, and it does not read the token gaps of a stream; use a client that samples prompt lengths and counts tokens.

Follow-ups an interviewer may ask.

  • (level 2) Why does the default range ratio describe half the work? Expected: each length is drawn from 1 to the length asked, so the average prompt is about half of it; with 1.0 every prompt has the full length and the input token total in the report confirms it.
  • (level 3) Fixed lengths gave a late first token and a steady stream, mixed lengths the opposite. Which do you use? Expected: fixed lengths to compare two builds, because they repeat exactly; your real length mix before you set a latency target, because the two shapes measure two different servers.
  • (level 3) A teammate's hand-written timing loop reads 13 tokens per second where a hosted API reads 60. What is wrong with the loop? Expected: it counted words split on spaces and included the first-token time in the rate; a word is not a token and TTFT is not decode time, so use the benchmark client.
  • (level 4) At 16 requests per second the client reports a first token you do not believe. How do you check the client itself? Expected: a single-process client adds its own queue at high rates; run two client processes that each send half the rate and compare, and record the CPU use of the client.
