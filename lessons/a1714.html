The problem

In plain words first

There are two kinds of caching for LLM calls. Prompt caching (the provider's, also called prefix caching) stores the work done reading the start of a prompt; when the next request starts with exactly the same text, that part is billed at about a tenth of the price and starts faster. Writing the cache costs a little extra once. Semantic caching (your application's) stores whole answers: before calling the model, you look for an earlier question that means nearly the same thing and, if you find one, return its answer without calling the model at all. Both only pay if your requests are built for them: the fixed parts of a prompt must come first and stay byte-for-byte identical, and parallel requests must not all race to write the same cache.

You add prompt caching to your RAG service. The bill stays flat. You measure the hit rate; it is 7%. Your prompts look static but they are not — the system prompt includes the current date formatted to the minute, a request ID, and a randomized example reorder for diversity. Every request writes a new cache entry, reads zero.

Separately, your agent runs ten parallel tool calls per user question. All ten arrive at the provider before the first cache write completes. Ten writes, zero reads. Your bill is 5-10x what "with caching" was supposed to cost.

Caching is a protocol, not a flag. Two layers, two different failure modes.

Idea 1 · L2 — provider prompt/prefix caching

Provider stores the attention KV for a cacheable prefix and reuses it on the next request that matches the prefix. You pay a write cost once, reads nearly free.

Anthropic (Claude 3.5 / 3.7 / 4 series): explicit cache_control marker in the request. You tag which blocks are cacheable. TTL: 5-minute (write costs 1.25x base) or 1-hour (write costs 2x base). Cache reads: $0.30/M on Claude 3.5 Sonnet vs $3.00/M fresh — 10x cheaper (docs.anthropic.com, as of 2026-04). Rates differ per model (Opus/Haiku published separately); always cross-check the live pricing page.

OpenAI: automatic caching for prompts ≥1024 tokens (platform.openai.com, 2026-04). No explicit flag. Cached input is roughly 10x cheaper than fresh on current gpt-4o/gpt-5 rate cards. Neither docs nor release notes publish an official hit-rate baseline; community reports cluster around 30–60% with careful prompt design. Monitor usage.cached_tokens to measure your own.

Google (Gemini): context caching via explicit API; 1M-token context means caching pays even more.

Self-hosted (vLLM, SGLang): Phase 17 · 06 covers RadixAttention — same pattern at your own compute.

Idea 2 · L1 — app-level semantic caching

Before calling the LLM at all, hash the prompt, embed it, and look for a similar cached request (cosine similarity above threshold, typically 0.95+). On hit, return the cached response. On miss, call LLM and cache the result.

Open-source: Redis Vector Similarity, GPTCache, Qdrant. Commercial: Portkey Cache, Helicone Cache.

Vendor accuracy claims refer to how often the returned cached response was semantically appropriate — not how often you hit. Production hit rates:

  • Open-ended chat: 10-15%.
  • Structured FAQ / support: 40-70%.
  • Code questions: 20-30% (small variants kill hits).
  • Voice agents repeating prompts: 50-80% (voice normalization fixed set).

Idea 3 · The parallelization anti-pattern

Your agent makes 10 tool calls in parallel. All 10 have the same 4K-token system prompt. Anthropic cache writes are per-request; the first cache-write completes around 300 ms after the provider sees the prompt. Requests 2-10 arrive in the same millisecond window and each sees cache miss. You pay 10 write premiums, 0 read discounts.

Fix: batch with sequential-first — make request 1 alone, then fire 2-10 once 1's cache has populated. Adds 300 ms to the first tool call; avoids the 5-10x bill inflation.

Idea 4 · The dynamic content anti-pattern

Your system prompt looks like:

You are a helpful assistant. The current time is 14:32:17.
User ID: abc123. Today is Tuesday...

Every request is unique. Every request writes. Zero hits.

Fix: move everything truly static to the cacheable prefix; append dynamic content after the cache boundary:

[cacheable]
You are a helpful assistant. [rules, examples, instructions]
[/cacheable]
[dynamic, not cached]
Current time: 14:32:17. User: abc123.

ProjectDiscovery moved from 7% to 74% cache hit rate this way and published the anatomy.

Idea 5 · Stack batch + cache for overnight workloads

Batch APIs (Phase 17 · 15) give 50% discount at 24-hour turnaround. Cached input on top gets you ~10x on top of that. Overnight classification, labeling, and report generation workloads can drop to ~10% of synchronous-uncached cost by stacking.

Idea 6 · Numbers you should remember

Pricing points are captured 2026-04 from the linked vendor docs and drift every few months — re-check before relying on them.

  • Anthropic cached read: $0.30/M on Claude 3.5 Sonnet, roughly 10x cheaper than fresh input (docs.anthropic.com).
  • Anthropic cache write premium: 1.25x (5-min TTL) or 2x (1-hour TTL).
  • OpenAI auto-cache: applies to prompts ≥1024 tokens; cached input priced at roughly 10% of fresh input on current rate cards (platform.openai.com).
  • Semantic cache hit rate (community-reported): ~10% open chat; up to ~70% structured FAQ; 50-80% for voice agents on a fixed prompt set. Not a vendor-documented baseline.
  • ProjectDiscovery: 7% → 74% hit rate by moving dynamic out of prefix (project blog, 2025-11).
  • Parallelization anti-pattern: typical reports of 5–10x bill inflation when N parallel requests miss the first cache write.

The same idea as a formula

Cost of a cached prefix over n requests. With a prefix of T tokens, base input price p, write multiplier w (1.25 for a 5-minute cache) and read multiplier r (about 0.1):

cost=wpT+(n−1)rpTagainstnpT without caching

Caching pays from the second request on: w+r<2.

Worked example
Ten parallel tool calls with a 4,000-token prompt

Base price $3 per million input tokens; cache write 1.25×, cache read 0.1×.

  1. No caching: 10 × 4,000 × $3/M = $0.120.
  2. Fired all at once, before the first write lands: 10 writes at 1.25× = $0.150. Caching made it more expensive.
  3. First call alone, then the other nine: 1 write + 9 reads = 4,000 × $3/M × (1.25 + 9 × 0.1) = $0.0258. About a fifth of the uncached cost.
  4. The price of the fix is about 300 ms extra on the first call.
Check your mental model

Which statements are right?

  • ✓ A timestamp at the top of the system prompt makes every request a cache miss.
  • ✗ A semantic cache's "95% accuracy" means 95% of requests hit it. It means 95% of the answers it returned were appropriate; hit rates are often 10–30% for open chat.
  • ✓ Batch APIs and prompt caching stack: the discounts multiply.
  • ✗ OpenAI requires you to mark cacheable blocks. OpenAI caches long prompts automatically; Anthropic uses explicit cache_control markers.

Use it: the same idea with real libraries

code/main.py simulates L1 + L2 caching on mixed workloads. Reports hit rates, bill, and shows the parallelization penalty.

Here is code/main.py, in 4 parts. Each part runs on this page, in order, in one Python session; the last part does what python3 code/main.py does.

Part 1 of 4 · Request, Config, make_workload

"""Two-layer caching simulator — stdlib Python.

Models L1 (semantic) + L2 (prompt-prefix) caching on a mixed workload.
Reports bill, hit rates, and the parallelization penalty.
"""

from __future__ import annotations

from dataclasses import dataclass
import random


BASE_INPUT = 3.00       # $/M input tokens (Claude Sonnet-class)
BASE_OUTPUT = 15.00     # $/M output tokens
CACHED_INPUT = 0.30     # 10x cheaper read
CACHE_WRITE_5MIN = 1.25 * BASE_INPUT  # write premium 5-min TTL
CACHE_WRITE_1HR = 2.00 * BASE_INPUT   # write premium 1-hour TTL


@dataclass
class Request:
    prompt_tokens: int
    prefix_hash: str
    is_parallel_wave: bool
    arrived_at: float


@dataclass
class Config:
    l1_enabled: bool
    l2_enabled: bool
    parallel_penalty: bool  # N parallel arrivals miss cache together
    l1_threshold: float
    l1_hit_prob: float
    ttl: str                # "5min" or "1hr"


def make_workload(n: int = 500, seed: int = 7) -> list[Request]:
    rng = random.Random(seed)
    reqs = []
    prefixes = [f"prefix_{i}" for i in range(12)]
    now = 0.0
    for i in range(n):
        # 60% individual arrivals, 40% parallel waves of 5
        if rng.random() < 0.4:
            for _ in range(5):
                reqs.append(Request(rng.choice([2000, 4000, 8000]),
                                    rng.choice(prefixes), True, now))
            now += rng.uniform(0.1, 2.0)
        else:
            reqs.append(Request(rng.choice([2000, 4000, 8000]),
                                rng.choice(prefixes), False, now))
            now += rng.uniform(0.1, 2.0)
    return reqs

Part 2 of 4 · simulate, report

def simulate(reqs: list[Request], cfg: Config) -> dict:
    l2_cache: set[str] = set()
    l2_writes = 0
    l2_reads = 0
    l1_hits = 0
    cost = 0.0
    rng = random.Random(11)

    for r in reqs:
        if cfg.l1_enabled and rng.random() < cfg.l1_hit_prob:
            l1_hits += 1
            continue

        if cfg.l2_enabled:
            if r.prefix_hash in l2_cache:
                l2_reads += 1
                cost += (r.prompt_tokens / 1e6) * CACHED_INPUT
            else:
                if cfg.parallel_penalty and r.is_parallel_wave:
                    write_cost = CACHE_WRITE_5MIN if cfg.ttl == "5min" else CACHE_WRITE_1HR
                    cost += (r.prompt_tokens / 1e6) * write_cost
                    l2_writes += 1
                else:
                    write_cost = CACHE_WRITE_5MIN if cfg.ttl == "5min" else CACHE_WRITE_1HR
                    cost += (r.prompt_tokens / 1e6) * write_cost
                    l2_cache.add(r.prefix_hash)
                    l2_writes += 1
        else:
            cost += (r.prompt_tokens / 1e6) * BASE_INPUT

        cost += (200 / 1e6) * BASE_OUTPUT

    return {
        "cost": cost,
        "l1_hits": l1_hits,
        "l2_reads": l2_reads,
        "l2_writes": l2_writes,
    }


def report(label: str, cfg: Config, reqs: list[Request]) -> None:
    res = simulate(reqs, cfg)
    print(f"{label:45}  cost=${res['cost']:7.2f}  "
          f"L1={res['l1_hits']:4}  L2_reads={res['l2_reads']:4}  L2_writes={res['l2_writes']:4}")

Part 3 of 4 · main

def main() -> None:
    print("=" * 95)
    print("PROMPT + SEMANTIC CACHING — 500 requests, Claude Sonnet-class pricing")
    print("=" * 95)
    base = make_workload()
    reqs = [Request(r.prompt_tokens, r.prefix_hash, r.is_parallel_wave, r.arrived_at) for r in base]

    report("NO CACHING",
           Config(l1_enabled=False, l2_enabled=False, parallel_penalty=True, l1_threshold=0.95, l1_hit_prob=0.0, ttl="5min"),
           reqs)
    report("L2 5-min, parallel penalty active",
           Config(l1_enabled=False, l2_enabled=True, parallel_penalty=True, l1_threshold=0.95, l1_hit_prob=0.0, ttl="5min"),
           reqs)
    report("L2 5-min, parallel fixed (serialize first)",
           Config(l1_enabled=False, l2_enabled=True, parallel_penalty=False, l1_threshold=0.95, l1_hit_prob=0.0, ttl="5min"),
           reqs)
    report("L2 1-hour + L1 semantic 30%",
           Config(l1_enabled=True, l2_enabled=True, parallel_penalty=False, l1_threshold=0.95, l1_hit_prob=0.30, ttl="1hr"),
           reqs)
    report("L2 1-hour + L1 semantic 70% (structured FAQ)",
           Config(l1_enabled=True, l2_enabled=True, parallel_penalty=False, l1_threshold=0.95, l1_hit_prob=0.70, ttl="1hr"),
           reqs)

    print("\nRead: caching is a protocol. Structure your prompts and batching for it to pay off.")

Break it on purpose

A support bot adds a semantic cache with a cosine threshold of 0.85 to save money. Its hit rate jumps to 60%, and complaints rise: users asking "how do I cancel my order" get the answer to "how do I cancel my subscription". What went wrong? (Solution B1.)

Recap
What to keep from this lesson
  • Prompt caching bills a repeated prefix at about a tenth; the first write costs a little more.
  • Put static content first, dynamic content after the cache boundary.
  • Do not fire parallel requests before the first cache write lands.
  • Semantic caching skips the model entirely; hit rates depend on how repetitive the questions are.
  • Combine batch APIs and caching for overnight work.

Given a prompt template, traffic pattern (arrival rate, parallel factor), and provider (Anthropic, OpenAI, Gemini, self-hosted vLLM), produce a cache audit.

Produce:

1. Prefix structure. Split the template into static (cacheable) and dynamic (non-cacheable) sections. Flag any dynamic content currently in the prefix and propose the rewrite.
2. TTL choice. Anthropic 5-min (1.25x write) vs 1-hour (2x write). Pick based on arrival rate — 1-hour wins when the prefix is reused within the hour consistently.
3. Parallelization audit. Count parallel requests with shared prefix. If N > 2 and parallel, require serialize-first-then-fanout pattern. Quantify the expected bill reduction.
4. Semantic cache choice. Decide if L1 is worth it. Open-ended chat: maybe not (low hit). Structured FAQ / support: yes. Set cosine threshold, start 0.95; tune downward only with response-quality evals.
5. Expected savings. Compute monthly $ delta vs no-cache baseline given current traffic and projected hit rates.
6. Observable. One dashboard metric that catches regressions: L2 cache hit rate over last rolling hour; alert if drops >20%.

Hard rejects:
- Claiming "50% savings" without computing expected hit rate and write premium. Refuse — calculate per-layer.
- Leaving dynamic content in prefix when a simple rewrite moves it out. Refuse to sign off.
- Firing parallel requests with shared prefix without serialize-first pattern. Refuse — state the 5-10x bill inflation.

Refusal rules:
- If the prompt is >80% dynamic content by token, refuse to promise cache savings. Recommend semantic caching at best.
- If semantic cache threshold is dropped below 0.85 without response-quality eval, refuse — hallucination cache risk.
- If the provider does not support explicit cache_control (non-Anthropic, non-Gemini-v1) and auto-caching only, note that hit rate is opportunistic, not guaranteed.

Output: a one-page audit listing prefix rewrite, TTL, parallelization pattern, L1 threshold, expected savings, observable. End with a quarterly review recommendation: re-audit prompts after any template change.

Solutions

SolutionP1 · Reading the five policies

In code/main.py, provider caching alone cuts the 500-request bill from $21.63 to $6.84; fixing the parallel race (serialize the first call) brings it to $5.85, reducing cache writes from 77 to 12. A semantic cache in front then removes whole calls: $4.25 at a 30% hit rate and $2.02 at 70% (structured FAQ).

SolutionB1 · Threshold too loose

At 0.85 cosine similarity, questions with the same structure but different objects ("cancel my order" and "cancel my subscription") count as matches. Raise the threshold (0.95 or more is common), include key entities (product, intent) in the cache key, and measure how often returned answers were right, not only how often the cache hit.

Debug a failureA dashboard panel shows the prefix cache hit rate of a self-hosted server at 94 percent. Over the same run, the server's counters say that it computed 104,057 prompt tokens and took 182,079 from the cache. Both readings come from one scrape of the same endpoint. Which one do you trust for a cost decision, and why do they differ?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Trust the counters. The gauge holds the hit rate of the last prefill interval that the scheduler logged, and at idle it keeps the value from the last batch, which was a shared-prefix benchmark. The counters add up every prefill token since the server started, and their ratio over the whole run is 0.636, not 0.942. For a cost decision, compute the rate from the counters over a time window.

Three kinds of series.

A gauge is a value the scheduler overwrites on each log interval. A scrape sees the latest value only. A counter is a total that only grows, and you read it as a rate over a window. A histogram is a set of counters, one per bucket, and you read percentiles from it over a window.

The two hit rates.

The gauge divides the hit tokens of one log interval by the hit tokens plus the computed tokens of that interval. When nothing runs, it keeps its last value. The counters carry the same two quantities since startup, split by mode: input for computed tokens, and device, host and storage hits for cached tokens. Over the whole run, 182,079 cached tokens against 286,136 prefill tokens in total give 0.636. The gauge at 0.942 describes the shared-prefix benchmark that ran last. Both are correct, and they answer different questions.

The windowed rate.

The HELP text of the counter gives the formula, and in PromQL it reads:

sum(rate(sglang:prefill_effective_tokens_total{mode=~".*_hit"}[5m]))
  / sum(rate(sglang:prefill_effective_tokens_total[5m]))

One caveat from the code: the hit modes add raw hit counts, so after a retraction the same tokens can count twice. The input mode excludes the re-count. The manual's run had no retractions, so its numbers are exact.

Why this is a cost question.

A hit rate decides whether you restructure prompts, add a cache-aware router or buy memory. A gauge from the last benchmark says the prompts are fine. The counters say that more than a third of the prompt tokens over the run were computed. The lesson on caching economics says the same for provider caches: measure your own hit rate from the usage fields on every response, and do not take a published figure as yours.

What to alert on.

Alert on counters and histograms over a window. Alert on a gauge only when the condition lasts for several minutes, such as queued requests above zero or token usage near one. Read the HELP text and the code before you build a panel on a metric. The manual found one utilization gauge that stays at zero at the version it pinned.

Plausible wrong answers.

  • "The gauge is the newest value, so it is the most accurate." It is a snapshot of one interval, and it keeps its last value at idle.
  • "Average the two numbers." They answer different questions, and the counters already contain the whole run.
  • "The real rate is lower, so turn the cache off." A rate of 0.636 means a third of the prompt tokens were computed. The fix is the prompt layout or the routing, not the cache.

Follow-ups an interviewer may ask.

  • (level 2) What does a gauge answer, and what does a counter answer? Expected: a gauge answers what happened in the last interval. A counter answers how much happened since the start, and a rate over a window turns it into a trend.
  • (level 3) Why can the counter-based rate overstate the hits after retractions? Expected: the hit modes add raw hit counts, so a retracted request that runs again counts its cached tokens twice, while the input mode excludes the re-count.
  • (level 3) Which gauges may page you, and under what rule? Expected: queued requests above zero and token usage near one, only when the condition holds for several minutes, never on one scrape.
  • (level 4) A panel on this server shows utilization at zero during an outage. Why? Expected: that gauge stays at zero at the pinned version because of a known regression, so the panel shows an idle fleet. Read the HELP text and the code before building on a metric.

Where it is taught. The metrics endpoint section of SGLang 101 measures the two hit rates on one server, and the caching economics lesson tells you to compute the rate from your own usage fields.
