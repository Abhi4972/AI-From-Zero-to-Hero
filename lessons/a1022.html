In plain words first
The idea in one line

Speculative decoding (Phase 10 · 15) parallelizes tokens within one sequence. Multi-agent frameworks parallelize across whole sequences but force explicit coordination (voting, sub-task splitting). Hogwild! Inference (Rodionov et al., arXiv:2504.06261) does something else: run N instances of the same LLM in parallel against a SHARED key-value cache. Each worker sees every other worker's generated tokens instantly. Modern reasoning models — QwQ, DeepSeek-R1 — can self-coordinate through that shared cache without any fine-tuning. The problem

In plain words first

A reasoning model thinking for 10,000 tokens takes minutes, because tokens come one at a time. Hogwild! Inference (2025) runs several copies of the same model at once on the same problem, all reading and writing one shared memory of what has been written so far (the attention cache). Each copy sees the others' thoughts as they appear, and capable reasoning models split the work among themselves without any training, like colleagues writing on one whiteboard. Two facts make it cheap: decoding a few sequences together costs little more than decoding one, and rotary position embeddings let a block of cached tokens be viewed at a new position without recomputing it. This lesson runs the lesson's toy, computes the speedup limits exactly, and checks both facts with a real model. No model is trained.

Modern LLMs solve hard problems by producing long chains of reasoning — 5000 tokens of step-by-step logic is common, tens of thousands of tokens happens on deep math problems. At 35 tokens/sec decode on a 70B model, 50k tokens is 24 minutes. Interactive the model is not.

Speculative decoding (Phase 10 · 15) gets you a 3-5x speedup by parallelizing within one sequence. Past that the sequential dependency of autoregressive decoding is the hard ceiling. Each new token depends on every prior token.

The obvious question: can we parallelize across sequences? Run multiple copies of the same model on the same problem, let them cooperate, have them divide the work?

Prior work: voting ensembles (run N models, pick the majority answer), tree-of-thought (branch reasoning paths and recombine), and multi-agent frameworks (assign each agent a sub-task, use a coordinator). These all help in specific task domains. They all also introduce explicit coordination machinery — voting rules, branch-and-prune logic, agent-to-agent messaging protocols.

Hogwild! Inference takes a different approach. N workers share a single KV cache. Each worker sees every other worker's generated tokens immediately, as if they were its own context. The workers — without any training or fine-tuning — figure out how to divide the work. Modern reasoning models (the paper uses QwQ-32B, Qwen3 models from 1.7B to 235B, Phi-4-Reasoning-Plus and DeepSeek-R1) can read the shared cache and say things like "I see worker 2 already handled the base case, so I'll work on the inductive step."

The speedup is workload-dependent and experimental as of April 2026. But the idea is worth knowing because it opens a new axis of inference parallelism.

Idea 1 · The setup

Initialize N worker processes, all running the same LLM. Instead of per-worker KV caches, maintain ONE shared cache. When worker i generates token t_j, the token is written into the shared cache at the next position. When worker k takes its next step, it reads the current state of the cache (which includes everything all N workers have generated so far).

At step time, workers race to write tokens. There is no per-worker position index — the cache is a single growing sequence. Order is determined by write arrival time.

Idea 2 · Why coordination emerges

The workers share a prompt. Typically something like "You are one of N instances working together on this problem. Each instance reads the shared memory and can see what other instances have written. Avoid redundant work." The prompt plus the shared cache is enough. Reasoning models read the cache, notice which parts of the problem have already been attempted, and (often but not always) pivot to unexplored parts.

The Hogwild! paper (Rodionov et al., 2025) reports observations like:

  • Workers formulate plans and communicate them to other workers via the cache.
  • Workers notice errors in other workers' reasoning and call them out.
  • Workers adapt when a plan fails and propose alternatives.
  • When prompted to check for redundancy, workers detect it and pivot.

None of this requires fine-tuning. The emergent behavior comes from the reasoning capabilities the model already has.

Idea 3 · The naming

The paper's name riffs on Hogwild! SGD (Recht et al., 2011), an asynchronous-update optimizer. The analogy: SGD's asynchronous workers all write to a shared parameter vector; Hogwild! Inference's workers all write to a shared KV cache. Both rely on empirical convergence rather than synchronization guarantees.

Idea 4 · RoPE makes this tractable

Rotary Position Embeddings (RoPE, Su et al. 2021) encode position information via rotation in the Q and K vectors. Because the attention score between a rotated query and a rotated key depends only on their relative distance, a whole block of cached entries can move to a new offset without recomputation: rotate the query instead of re-rotating every cached key. Hogwild! Inference does this once per cache block: for a query at position i_q and a block that starts at i_k in that worker's view, the query is rotated by the relative distance i_q - i_k. That is how each worker sees the shared cache blocks in its own order. The trick works for a uniform shift of a contiguous block. Moving individual tokens to different positions would change their rotations and still need recomputation.

In a learned-position or absolute-position model, Hogwild! would need cache invalidation on every concurrent write. RoPE lets the cache stay stable.

Idea 5 · Wall-time math

Let T_serial be the time for one worker to solve the problem alone. Let p be the task-level parallelizable fraction. Let c be the per-step coordination overhead (reading the extended cache, deciding what to write).

Single-worker time: T_serial. N-worker Hogwild! time, if coordination is free: T_serial * ((1 - p) + p / N). Classic Amdahl. With coordination overhead: T_serial * ((1 - p) + p / N) + c * steps_per_worker.

For a worker to be productive, c must be small relative to the per-step decode time. On reasoning models producing 5k+ tokens, the workers can afford hundreds of tokens of coordination overhead and still come out ahead. On short chat tasks, coordination dominates and Hogwild! is worse than serial.

Idea 6 · Concrete example

Reasoning problem: 10k tokens of chain-of-thought. Suppose the problem has p = 0.7 parallelizable content (different proof strategies, different case analyses) and c = 200 tokens of coordination overhead per worker. With N = 4 workers:

  • Serial time: 10000 decode steps.
  • Hogwild! time: 10000 * (0.3 + 0.7 / 4) + 200 * 4 = 10000 * 0.475 + 800 = 5550 decode steps.
  • Speedup: 10000 / 5550 = 1.8x.

That is modest, and longer problems do not raise the ceiling: as the coordination overhead amortises, the speedup approaches the Amdahl limit for 4 workers, 1 / (0.3 + 0.7/4) = 2.1×. Going beyond needs more of the task to be parallel (a larger p) or more workers. Hogwild! is the inference equivalent of thread-level parallelism in a language that lets you write multi-threaded code naturally.

Idea 7 · When to reach for Hogwild!

  • Long reasoning problems (thousands of tokens) where the task can be parallelized across independent sub-goals.
  • Reasoning models that have been trained to think step by step. Non-reasoning models do not self-coordinate well.
  • Single-node deployments with enough VRAM to hold the shared cache plus N worker processes. The cache is shared, but each worker has its own activation memory.

Idea 8 · When not to

  • Short interactive chat. Coordination overhead dominates.
  • Tasks that don't parallelize (single linear proof, single compilation). N=1 is the max.
  • Non-reasoning models. No coordination emerges.
  • Multi-node deployments. The shared cache needs very fast cross-worker synchronization. Intra-node is fine; cross-node is a latency disaster.

Idea 9 · The experimental status

As of April 2026, Hogwild! is a research method with an open-source PyTorch implementation. Production adoption has not happened. Three blockers:

  1. Shared KV cache management across concurrent processes is non-trivial engineering.
  2. Emergent coordination is task-dependent; benchmarks are still being built.
  3. The speedups are modest compared to what speculative decoding already delivers, and the two can be combined but the combined engineering is another layer.

Worth knowing. Worth experimenting with. Not yet worth betting a product on.

The same idea as a formula

Amdahl with overhead. A task of T sequential decode steps, of which a fraction p can be split among N workers, with c steps of coordination per worker done in parallel:

TN​=T((1−p)+Np​)+c,SN​=TN​T​≤(1−p)+p/N1​<1−p1​.
(If the overhead is counted once per worker, c becomes cN and adding workers can make it slower.)

Cost of a step with N workers in one batch: tstep​≈max(bandwidthweight bytes​, FLOP/sN⋅2P​): flat in N until compute catches up.

The RoPE shift. With Rm​ the rotation for position m, ⟨Rm​q,Rn+Δ​k⟩=⟨Rm−Δ​q,Rn​k⟩. A cached block encoded at positions n,n+1,… can be viewed Δ positions later by rotating the query back by Δ for that block, with no change to the cached keys.

Worked example
10,000 tokens, p = 0.7, c = 200, 4 workers
  • Serial part: 0.3×10,000=3,000 steps. Parallel part: 0.7×10,000/4=1,750 steps.
  • With the overhead done in parallel: 3,000+1,750+200=4,950 steps, a 2.02× speedup.
  • Counting the overhead once per worker (the lesson's version): 4,750+800=5,550 steps, 1.80×.
  • No overhead: 4,750 steps, 2.11×, the ceiling for 4 workers; for unlimited workers, 1/0.3=3.3×.
  • Each step decodes 4 tokens in one batch, and while decoding is memory-bound it takes about as long as decoding 1.

  • ✗ "Four workers make reasoning four times faster."
    ✓ Only the parallel part is divided; with p=0.7, four workers give at most 2.1×.
  • ✗ "N workers cost N times the GPU time per step."
    ✓ Decoding is limited by reading the weights; a small batch of workers shares one weight read (the paper: 1.8× tokens per second with 2 workers, 3.4× with 4).

Step 1 · the shared cache

code/main.py implements a toy Hogwild! simulator:

  • Two worker processes, each a deterministic "LLM" that produces one of several token categories (work-token, observe-token, coordinate-token) with known probabilities.
  • A shared cache (just a list of tokens) that both workers read and write.
  • A simple coordination logic: when a worker sees that the other has already produced enough work tokens in a category, it picks a different category.

The simulator runs for a fixed step budget and reports:

  • Total work-tokens produced.
  • Total wall time (number of worker steps).
  • Effective speedup over a single worker.
  • A trace of which worker wrote which token.

A list that both workers append to. Simple locking (Python threading.Lock) in a real implementation; we simulate with a counter.

Step 2 · the worker loop

Each worker, on each step:

  • Reads the current shared cache.
  • Decides what category of token to write based on what is already there.
  • Writes one token.

Step 3 · the coordination heuristic

If category X already has K tokens in the cache and worker's intended category is X, worker switches to category Y. This is a toy stand-in for the reasoning-model behavior of "notice this is already covered, do something else instead."

Step 4 · measured speedup

Run the simulator with N=1 worker and with N=2 workers, same total step budget. Count work-tokens produced. N=2 should produce roughly 1.5-1.8x more work-tokens because of the coordination-driven task division.

Step 5 · stress the coordination

Reduce the coordination heuristic's sensitivity. Run again. Observe that without good coordination, N=2 redundantly produces the same tokens and the speedup drops below 1. This matches the paper's observation: the trick only works if the workers have the reasoning capacity to self-coordinate.

Reading this output

Steps 1 and 2. In 200 steps one worker produces 189 work tokens; two workers write 400 tokens, of which 341 count as progress (two workers writing the same category in the same step count once), 1.80× the single worker. The "coordination" is a rule: with probability 0.8, write into the category that has fewer tokens so far. Because the second worker reads the cache after the first has written in the same step, it usually picks the other category.

Step 3. With coordination weight 0 both workers always write category A, so their tokens duplicate each other; the 1.04× is the occasional step where noise or coordination tokens break the tie, not real cooperation. At weight 1 the two always differ, and progress reaches 2.04× (slightly above 2 because the single-worker baseline loses steps to noise tokens). The toy shows the logic of the paper's claim, not evidence for it: real workers are language models deciding in text what to do.

Steps 4 and 5. The Amdahl tables add the coordination overhead once per worker, which is why 8 workers can be slower than 4 at p=0.3 and why short tasks fall below 1×. Counting the overhead as running in parallel gives higher numbers (next run).

import numpy as np

print("A. Amdahl with coordination overhead: 10,000-token task, p = 0.7")
T, p, c = 10000, 0.7, 200
print(f"  {'workers':>7} {'overhead in parallel':>21} {'overhead added up (lesson)':>27} {'no overhead (limit)':>20}")
for N in [1, 2, 4, 8, 16]:
    base = T * ((1 - p) + p / N)
    par, seq = base + (c if N > 1 else 0), base + (c * N if N > 1 else 0)
    print(f"  {N:>7} {T / par:>20.2f}x {T / seq:>26.2f}x {T / base:>19.2f}x")
print(f"  ceiling for p = 0.7 with unlimited workers: 1 / (1 - p) = {1 / (1 - p):.2f}x")
print()

print("B. Why extra workers are nearly free: one decode step of a 32B model in 4-bit on one L40S-class GPU")
W, BW, F = 32e9 * 0.5, 864e9, 181e12 * 0.5      # weight bytes, memory bandwidth, dense FP16 compute at 50%
for N in [1, 2, 4, 8, 64]:
    step = max(W / BW, N * 2 * 32e9 / F)          # read the weights once per step; compute grows with N
    print(f"  {N:>2} workers: {step * 1e3:5.1f} ms per step, {N / step:6.1f} tokens/s in total")
print("  (the paper measured 20.1, 36.3 and 68.9 tokens/s for 1, 2 and 4 workers of QwQ-32B-AWQ on an L40S)")
print()

print("C. The RoPE trick: move a cached block without recomputing its keys")
rng = np.random.default_rng(0)
d = 64
theta = 10000 ** (-np.arange(0, d, 2) / d)
def rope(v, pos):                                  # rotate each pair of dimensions by pos * theta_i
    a, b = v[0::2], v[1::2]; c_, s = np.cos(pos * theta), np.sin(pos * theta)
    out = np.empty_like(v); out[0::2] = a * c_ - b * s; out[1::2] = a * s + b * c_; return out
q, ks = rng.normal(size=d), rng.normal(size=(8, d))
qpos, old, new = 500, 100, 300                     # a block of 8 keys cached at 100..107, now viewed at 300..307
cached = np.array([rope(k, old + i) for i, k in enumerate(ks)])
recomputed = np.array([rope(k, new + i) for i, k in enumerate(ks)]) @ rope(q, qpos)
shifted_q = cached @ rope(q, qpos - (new - old))   # rotate the query by the shift instead
print(f"  scores with keys re-rotated to 300..307 : {np.round(recomputed[:4], 4)}")
print(f"  scores with old keys, query shifted back: {np.round(shifted_q[:4], 4)}")
print(f"  largest difference: {np.abs(recomputed - shifted_q).max():.1e}")

Reading this output

A. For p=0.7 the speedup is capped by Amdahl's law: 2.11× with 4 workers, 2.91× with 16 and 3.33× with unlimited workers. With 200 steps of coordination running in parallel on every worker, the numbers come close to the cap (2.02× with 4). If the overhead is added up once per worker, as the lesson's example does, more workers soon make it worse: 1.80× with 4, 1.83× with 8, 1.51× with 16. Which accounting is right depends on whether coordination tokens are produced in parallel (they usually are: each worker writes its own) or delay everyone.

B. On an L40S-class GPU, one decode step of a 32B model in 4-bit reads 16 GB of weights, about 18.5 ms, whether it decodes 1 or 8 workers' tokens: total throughput scales with the number of workers until compute catches up (around 20 here; at 64 workers the step grows to 45 ms). The paper's measurements, 20.1, 36.3 and 68.9 tokens per second for 1, 2 and 4 workers, show the same near-linear growth below this idealised ceiling.

C. Scores of a query against keys re-rotated to new positions equal those of the query rotated back by the shift against the old keys, to 2×10−14: RoPE scores depend only on the distance between positions. So a worker can view another worker's cached block at whatever position fits its own sequence by rotating its query per block, which is how Hogwild! lets each worker see the shared cache "in its own order".

Use it: the same idea with real libraries

Hogwild! integration in production as of April 2026 is research-grade. The reference implementation from Yandex, HSE University and IST Austria (NeurIPS 2025) is PyTorch-based: the workers run together as one batch on one GPU, sharing cache blocks. On an L40S with QwQ-32B in 4-bit, the paper measures 20.1 tokens per second for one worker, 36.3 for two and 68.9 for four.

Pragmatic adoption path:

  1. Profile your reasoning-task workload. Measure the fraction of tokens that are exploratory (multiple strategies, case analyses, search) vs linear.
  2. If exploration dominates, run a two-worker Hogwild! experiment. Measure wall-time improvement.
  3. If the improvement is under 1.3x, you are in the coordination-dominated regime. Revert to single-worker.
  4. If the improvement is over 1.5x, push to N=4 and measure again. Diminishing returns typically hit around N=4-8.

Combine with speculative decoding: each Hogwild! worker can independently use spec decode. The two speedups can multiply while decoding stays memory-bound (a few workers each verifying a few drafts are still a small batch), so a 3× spec decode and a 1.8× Hogwild! could give about 5.4×; at larger batches both compete for the same idle compute.

Both facts with a real model

SmolLM2-360M-Instruct. First, layer 10's own query and key projections and rotary embedding: scores of a query against a cached block re-encoded 200 positions later, and against the original cache with the query rotated back. Second, real batched decoding of 1, 2, 4 and 8 sequences of the same prompt, timed on this CPU. About 45 seconds.

import time, torch, transformers
import transformers.models.llama.modeling_llama as llama
from transformers import AutoTokenizer, AutoModelForCausalLM
transformers.logging.disable_progress_bar(); transformers.logging.set_verbosity_error()
torch.manual_seed(0)
name = "HuggingFaceTB/SmolLM2-360M-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()

print("1. The shift trick with this model's own layer 10 and rotary embedding")
attn = model.model.layers[10].self_attn
x = model.model.layers[10].input_layernorm(torch.randn(1, 9, model.config.hidden_size))   # 8 cached tokens, 1 query
hd = attn.head_dim
def rotated(states, positions):                                       # project and apply the model's RoPE at given positions
    cos, sin = model.model.rotary_emb(states, torch.tensor([positions]))
    q = attn.q_proj(states).view(1, len(positions), -1, hd).transpose(1, 2)
    k = attn.k_proj(states).view(1, len(positions), -1, hd).transpose(1, 2)
    return llama.apply_rotary_pos_emb(q, k, cos, sin)
with torch.no_grad():
    q_now, _ = rotated(x[:, 8:], [500])                               # the query at position 500
    _, k_old = rotated(x[:, :8], list(range(100, 108)))                # the block as cached, at 100..107
    _, k_new = rotated(x[:, :8], list(range(300, 308)))                # the same block re-encoded at 300..307
    q_back, _ = rotated(x[:, 8:], [500 - 200])                        # or: rotate the query back by the shift of 200
    g = attn.num_key_value_groups if hasattr(attn, "num_key_value_groups") else 1
    s_new = q_now[0, :g] @ k_new[0, 0].T
    s_trick = q_back[0, :g] @ k_old[0, 0].T
print(f"  scores of 3 query heads against the block re-encoded at 300..307 and against the old cache with a shifted query:")
print(f"  largest difference {(s_new - s_trick).abs().max():.1e} on scores of size about {s_new.abs().mean():.1f}")

print("\n2. Several workers decoding in one batch: tokens per second on this CPU")
prompt = tok.apply_chat_template([{"role": "user", "content": "Prove that the square root of 2 is irrational."}],
                                 add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
for n in [1, 2, 4, 8]:
    ids = prompt.repeat(n, 1)
    with torch.no_grad():
        model.generate(ids, max_new_tokens=4, do_sample=True, pad_token_id=tok.eos_token_id)     # warm-up
        t = time.perf_counter()
        model.generate(ids, max_new_tokens=48, min_new_tokens=48, do_sample=True, pad_token_id=tok.eos_token_id)
        dt = time.perf_counter() - t
    print(f"  {n} worker(s): {48 / dt:5.1f} steps/s, {n * 48 / dt:6.1f} tokens/s in total")

Decoding several sequences as one batch raises the total throughput, but on this CPU less than in proportion: from about 11 tokens per second for one sequence to about 20 for two, 24 for four and 34 for eight (the exact numbers vary from run to run). A CPU running a 360M model is closer to compute-bound than a GPU running a 32B model, so each extra sequence costs more here. On GPUs, where decoding is limited by memory bandwidth, the gain stays near linear for small batches, which is what makes several Hogwild! workers nearly as fast per step as one.

Break it on purpose

Use a model with learned absolute position embeddings (like GPT-2) for Hogwild!, and move each worker's cached block to a new position in another worker's view without recomputing it. What goes wrong? (Solution B1.)

Industry practice
What's current (2024–2026)

Hogwild! itself is a research method (NeurIPS 2025, open-source code); no major serving engine ships it. Parallel generation that is in production:

  • Batched sampling for reasoning: best-of-N and self-consistency (majority vote over parallel samples), served with shared-prefix caching in vLLM and SGLang (RadixAttention).
  • Speculative decoding for single-sequence latency (Lesson 10.15).

Recap
What to keep from this lesson
  • Hogwild!: N copies of one model share an attention cache and coordinate through what they write.
  • Speedup is capped by Amdahl: 1/((1 − p) + p/N), at most 1/(1 − p).
  • Extra workers are cheap while decoding is memory-bound: one weight read serves the batch.
  • RoPE lets a cached block move: rotate the query, not the keys.
  • Research stage; production uses batched sampling and voting instead.

Solutions

SolutionP1 · It grows, but less than in proportion

It grows, but less than in proportion: about 11 tokens per second for one sequence, about 20 for two, 24 for four and 34 for eight on this CPU (numbers vary between runs), so the time per step rises as sequences are added. Batching helps because the weights are read once per step for all sequences; it helps less than on a GPU because on this CPU the arithmetic itself is a large part of each step. On a GPU running a large model, decoding is memory-bound and a few workers are almost free, as the paper's 1.8× (2 workers) and 3.4× (4 workers) throughput shows.

SolutionB1 · Stale positions, wrong attention

The moved block keeps its old positions. With learned absolute position embeddings, position is added to the token's input at the bottom of the network and then mixed into every layer's keys and values; there is no simple operation on a cached key that changes its position. A block written at positions 100–107 and shown to another worker as if at 300–307 would still carry "100–107" in all its cached keys and values, so the model would see two tokens at the same position or a gap that is not there, and its attention would be wrong. The only fix is to recompute the block's keys and values at the new positions, every time the shared cache changes, which costs as much as the computation Hogwild! was meant to save. RoPE avoids this because position enters only as a rotation of the query and key right before their dot product.
