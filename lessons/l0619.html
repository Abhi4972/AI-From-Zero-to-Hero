About the model on this page
The model on this page is scripted

Each agent uses Lesson 14.58's ScriptedChatModel, which returns the tool calls and replies written in the code, so the examples show exactly what the tools and middleware do. The MCPlater · 16.4 server is real and runs as a subprocess.

from langchain.agents import create_agent
from langchain.agents.middleware import AgentState
from langchain.tools import tool, ToolRuntime
from langchain_core.messages import AIMessage, ToolMessage
from langchain_core.language_models.fake_chat_models import GenericFakeChatModel
from langgraph.types import Command
from typing_extensions import NotRequired

class ScriptedChatModel(GenericFakeChatModel):           # Lesson 6.8's scripted model
    def bind_tools(self, tools, **kwargs):
        return self

def scripted(*replies):
    return ScriptedChatModel(messages=iter(list(replies)))

def call(name, args, id="c1"):
    return AIMessage("", tool_calls=[{"name": name, "args": args, "id": id}])
Why this came about

Tools needed to update agent state, not only return text, and companies wanted to share tools across agents through MCP. LangChain added tools that return state updates, MCP adapters and more powerful middleware to meet both needs.

The problem: tools that only return text

So far every tool returned a string for the model to read. Real agents need more. A tool that identifies the customer should remember them for the rest of the conversation, so later tools use the right account without the model passing the ID around. Tools should come from the systems that own them, over MCP, not be copied into every agent. And some rules need to act on the loop itself: stop the run, count calls across the conversation, or send hard questions to a stronger model.

In plain words first
Tools that change things, tools from elsewhere, rules on the loop

So far tools only returned text. Here a tool can update the agent's state (remember the selected customer), tools can come from other teams' MCP servers instead of being copied into every agent, and middleware can act on the loop itself: stop a run, keep its own counters, or choose a different model per call.

Idea 1 · A tool that writes to the state

This tool finds a customer by email. An ordinary tool would return a sentence. This one returns a Command that does two things: it stores the customer's ID in the agent's state, and it supplies the ToolMessage the model is waiting for. A second tool then reads the ID from the state, so the model never has to repeat it.

CUSTOMERS = {"ravi@example.com": {"id": "C-42", "name": "Ravi"}}

class SupportState(AgentState):
    customer_id: NotRequired[str]                        # a key the tools can write and read

@tool
def select_customer(email: str, runtime: ToolRuntime) -> Command | str:
    """Find a customer by email and make them the active customer for this conversation."""
    cust = CUSTOMERS.get(email.lower())
    if not cust:
        return f"No customer with {email}; ask the user to check the email."
    return Command(update={
        "customer_id": cust["id"],                       # the state change
        "messages": [ToolMessage(f"Active customer: {cust['name']}", tool_call_id=runtime.tool_call_id)],
    })

@tool
def open_orders(runtime: ToolRuntime) -> str:
    """List open orders for the active customer."""
    cid = runtime.state.get("customer_id")               # read what the other tool wrote
    return f"Open orders for {cid}: A-1002" if cid else "No active customer selected."

agent = create_agent(scripted(call("select_customer", {"email": "ravi@example.com"}, "c1"),
                              call("open_orders", {}, "c2"),
                              AIMessage("Ravi, your open order is A-1002.")),
                     tools=[select_customer, open_orders], state_schema=SupportState)
out = agent.invoke({"messages": [{"role": "user", "content": "I'm ravi@example.com, what's still open?"}]})
print("customer_id:", out["customer_id"])
for m in out["messages"]:
    if m.type == "tool":
        print("tool result:", m.content)
What you should see
customer_id: C-42
tool result: Active customer: Ravi
tool result: Open orders for C-42: A-1002

ToolRuntime is a parameter LangChain fills in and hides from the model: it carries the agent's state, the tool_call_id, the run's context and the store (Lesson 14.64). select_customer returned a Command that set customer_id in the state, and open_orders read it from runtime.state. The model never saw or passed the ID, which is also safer: an ID kept in the state cannot be changed by a manipulated tool argument. The state key is declared in a custom state_schema.

runtime. field What it holds Set by
state The agent's current state, including messages and your own keys The graph
context Per-run data such as the signed-in customer (context_schema=) Your application, on each call
store Long-term memory across threads (Lesson 14.64) store= on create_agent
config The run's config, including thread_id The caller
tool_call_id The ID of this tool call The model's request
stream_writer A function that sends progress to custom streaming (Lesson 14.65) The graph

Why the ToolMessage inside the Command? Normally LangChain turns a tool's return value into a ToolMessage carrying the call's ID, which the provider requires: every tool call needs a matching result. A tool that returns a Command takes over that job, so it must include the ToolMessage itself, with runtime.tool_call_id. Leave it out and the next model call fails, which is the debugging exercise.

Idea 2 · Tools from an MCP server

How this connects
MCP in five lines, and where it is taught

The Model Context Protocol (MCP) is taught in the Protocols section; this section only uses it, so here is all you need. An MCP server is a small program that offers tools (and sometimes data and prompt templates) in a standard format. Any agent that speaks MCP can connect to the server, ask "what tools do you have?", and call them, without code written for that particular server. The team that owns a system writes its server once, and every agent in the company can use it. The connection is either a local subprocess (called stdio) or a web address.

If you would like to see a server built before you connect to one, read Lesson 16.4 first. It takes 25 minutes and needs only Lesson 14.4.

langchain.mcp connects to MCP servers and turns their tools into LangChain tools. It has been part of langchain itself since 1.4 (install langchain[mcp]) and replaces the older langchain-mcp-adapters package. Here the small server orders_server.py (shown in the solutions) runs as a subprocess over stdio:

import asyncio, warnings
from pathlib import Path
from langchain.mcp import MCPAdapter
warnings.filterwarnings("ignore", message=".*langchain.mcp.*beta")   # the namespace is still marked beta

adapter = MCPAdapter(Path("orders_server.py"))         # a Path means: start this script and talk over stdio

async def ask():
    tools = await adapter.list_tools()                 # MCP tools, converted to LangChain tools
    print("tools from the server:", [t.name for t in tools])
    agent = create_agent(scripted(call("get_order_status", {"order_id": "A-1001"}),
                                  AIMessage("A-1001 has shipped.")), tools=tools)
    out = await agent.ainvoke({"messages": [{"role": "user", "content": "Where is A-1001?"}]})
    tool_msg = next(m for m in out["messages"] if m.type == "tool")
    print("result over MCP:", tool_msg.content if isinstance(tool_msg.content, str) else tool_msg.content[0]["text"])

asyncio.run(ask())
What you should see
tools from the server: ['get_order_status']
result over MCP: A-1001 is shipped

Notice the Path(...). MCPAdapter decides the transport from what you give it: a URL string means a remote server over HTTP, a Path means a local script started as a subprocess, and you can also pass an in-process FastMCP server, a fastmcp.Client, or a dictionary of several servers. A bare string such as "orders_server.py" is refused with a ValueError, on purpose: a string read from configuration should never silently become a program your service starts.

The agent cannot tell an MCP tool from a local one; the call went to the server process and back. For a remote server, pass its URL; authentication (bearer tokens, OAuth 2.1) is configured on the adapter (Lesson 16.5). Each tool keeps the server's MCP metadata under tool.metadata["mcp"], including hints such as destructive_hint, which a policy middleware can read. Everything from Lesson 16.6 still applies: only connect servers you trust, because their tool descriptions go straight into the model's context.

Idea 3 · Stop the run from middleware

A hook can end the loop, or send it back to the model or the tools, by returning jump_to. This output check replaces a reply that contains a card number:

import re
from langchain.agents.middleware import after_model

CARD = re.compile(r"\b(?:\d[ -]?){13,16}\b")

@after_model(can_jump_to=["end"])                         # declare where this hook may jump
def block_card_numbers(state, runtime):
    last = state["messages"][-1]
    if isinstance(last.content, str) and CARD.search(last.content):
        return {"messages": [AIMessage("I can't share card details. Please check your bank app.")], "jump_to": "end"}
    return None

leaky = create_agent(scripted(AIMessage("Your card 4111 1111 1111 1111 was refunded.")), tools=[],
                     middleware=[block_card_numbers])
print(leaky.invoke({"messages": [{"role": "user", "content": "Which card got the refund?"}]})["messages"][-1].content)
What you should see
I can't share card details. Please check your bank app.

The hook must declare where it may jump (can_jump_to: "end", "model" or "tools"), which keeps the possible paths visible when the graph is built.

Idea 4 · Middleware with its own state

When one concern needs several hooks, settings or its own state keys, write a class:

from langchain.agents.middleware import AgentMiddleware, hook_config

class CallBudgetState(AgentState):
    model_calls: NotRequired[int]

class CallBudget(AgentMiddleware):
    """Count model calls in the state and stop politely after a limit."""
    state_schema = CallBudgetState                        # the middleware adds its own state key

    def __init__(self, limit: int):
        super().__init__()
        self.limit = limit

    @hook_config(can_jump_to=["end"])
    def before_model(self, state, runtime):
        used = state.get("model_calls", 0)
        if used >= self.limit:
            return {"messages": [AIMessage("Let me hand you to a colleague for this one.")], "jump_to": "end"}
        return {"model_calls": used + 1}

busy = create_agent(scripted(call("open_orders", {}, "c1"), call("open_orders", {}, "c2"), AIMessage("done")),
                    tools=[open_orders], middleware=[CallBudget(limit=2)])
out = busy.invoke({"messages": [{"role": "user", "content": "check my orders"}]})
print("model calls:", out["model_calls"], "|", out["messages"][-1].content)
What you should see
model calls: 2 | Let me hand you to a colleague for this one.

CallBudget added a model_calls key to the agent's state through its state_schema, counted in before_model, and stopped politely at the limit. Because the count is in the state, it is saved with the thread, so the budget holds across turns of a conversation, unlike a counter in a Python variable.

Idea 5 · Choose the model per call

A wrap_model_call middleware sees every request before it reaches the model and may change it, including which model handles it. This one sends messages that mention a dispute or fraud to a larger model and everything else to a small one. Both models here are scripted, and their replies say which one answered:

from langchain.agents.middleware import wrap_model_call

small = scripted(AIMessage("(small model) Your order A-1001 has shipped."))
large = scripted(AIMessage("(large model) I've reviewed the dispute and opened a case."))

@wrap_model_call
def route_by_difficulty(request, handler):
    text = request.messages[-1].content.lower()
    model = large if any(w in text for w in ("dispute", "fraud", "chargeback")) else small
    return handler(request.override(model=model))        # same request, different model

router = create_agent(small, tools=[], middleware=[route_by_difficulty])
for q in ["Where is A-1001?", "I want to dispute a charge"]:
    print(router.invoke({"messages": [{"role": "user", "content": q}]})["messages"][-1].content)
What you should see
(small model) Your order A-1001 has shipped.
(large model) I've reviewed the dispute and opened a case.

request.override(model=...) sends the same request to a different model. Routing hard or sensitive questions to a stronger model, and the rest to a cheaper one, is one of the biggest cost levers (Lesson 14.114); the same hook can change the tools or the system prompt per call. Evaluate both routes, because a misrouted hard question gets the weaker model.

Solutions

SolutionP1 · Order matters, and the tool says so

open_orders finds no customer_id in the state and returns "No active customer selected.", which the model can read and act on by asking for the email or calling select_customer. Tools that depend on state should return a clear message when it is missing, not raise.

SolutionB1 · Declare jumps, even when they work without it

In our test with langchain 1.5.2, the undeclared jump still ended the run. But the documented contract is that a hook declares where it may jump, because the agent's graph is built from those declarations: they appear as edges, they are checked, and they show up in the drawing. Code that relies on an undeclared jump depends on behavior the docs do not promise, and can break on an upgrade. Declare every jump.

SolutionD1 · Every tool call needs its result

A tool returning a Command replaces the normal result, so it must include a ToolMessage with the call's tool_call_id in messages; otherwise the model's tool call has no answer, the rule from Lesson 14.2. Add it:

@tool
def remember_language(language: str, runtime: ToolRuntime) -> Command:
    """Remember the language the customer wants."""
    return Command(update={"language": language,
                           "messages": [ToolMessage(f"Language set to {language}", tool_call_id=runtime.tool_call_id)]})

good = create_agent(scripted(call("remember_language", {"language": "Hindi"}), AIMessage("ok")),
                    tools=[remember_language], state_schema=LangState)
print(good.invoke({"messages": [{"role": "user", "content": "Hindi please"}]})["language"])

SolutionM1 · Two servers, one client

The server file the lesson uses:

from fastmcp import FastMCP

mcp = FastMCP("shopkart-orders")
ORDERS = {"A-1001": "shipped", "A-1002": "processing"}

@mcp.tool()
def get_order_status(order_id: str) -> str:
    """Return the shipping status for a ShopKart order ID like 'A-1001'."""
    return f"{order_id} is {ORDERS.get(order_id, 'not found')}"

if __name__ == "__main__":
    mcp.run(show_banner=False)

Copy it to returns_server.py with a start_return(order_id: str) -> str tool, then pass both in one configuration: MCPAdapter({"mcpServers": {"orders": {"command": sys.executable, "args": ["orders_server.py"]}, "returns": {"command": sys.executable, "args": ["returns_server.py"]}}}). await adapter.list_tools() returns tools from both, and the agent can use either. Name tools distinctly across servers, or the model cannot tell them apart.

Check your understanding

Explain the mechanismHow can a LangChain tool change the agent's state, and why would you do that?

Worked answer. The tool takes a ToolRuntime parameter, hidden from the model, which gives it the state, the tool call ID, context and store. It returns a Command(update={...}) that writes state keys and includes the ToolMessage for its call. This keeps facts such as the active customer, a selected order or a language preference in state, where other tools and middleware read them and where they are checkpointed, instead of trusting the model to pass them correctly in every call.

A plausible wrong answer. "Store it in a global variable." Globals are shared across users and lost on restarts.

Follow-ups. When would you use the store instead of state?

Debug a failureAn agent with MCP tools works locally but not in production. What do you check?

Worked answer. How the server is reached: stdio servers must be installed and launchable in the production container, remote servers need the right URL, transport and authentication, and network policies must allow the connection. Then the tool list the agent actually received (log get_tools()), and timeouts on slow servers.

A plausible wrong answer. "MCP is unreliable." The connection configuration usually differs.

Follow-ups. How would you health-check MCP servers?

Defend a designMiddleware or graph nodes for cross-cutting rules such as budgets and guardrails?

Worked answer. Middleware when the rule applies to every model or tool call of an agent built with create_agent: it is reusable, ordered, and keeps the agent definition small. Graph nodes when the rule is a step of a custom workflow, or must be visible as a node in the diagram and checkpointed as its own step. Both can coexist: middleware inside the agent node, policy nodes around it.

A plausible wrong answer. "Always nodes, middleware is magic." Middleware is ordinary hooks with clear ordering rules (Lesson 14.56).

Follow-ups. How would you test a middleware class?
