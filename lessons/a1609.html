In plain words first
The idea in one line

Contrast with supervisor: no central decider. Agents read a shared event bus, pick up work asynchronously, write results back. LangGraph has a "swarm" pattern too, though it means agents handing off to each other rather than workers pulling from a queue. Matrix (arXiv:2511.21686) represents both control and data flow as serialized messages passed through distributed queues to eliminate the orchestrator bottleneck. The tradeoff is explicit: determinism and traceability for scalability. Swarm fits tasks with many independent sub-problems; it does not fit tasks that need a single coherent plan.

Terms you'll hear
Term What people say What it actually means
Swarm architecture "Decentralized agents" Workers pull from shared queue; no central orchestrator.
Event bus "Agents subscribe to topics" Message broker that routes tasks to workers by type or content.
Starvation "Task never runs" Low-priority task never gets picked because higher-priority work arrives continuously.
Hot-spotting "One worker drowns" Load imbalance where one worker gets most tasks.
Back-pressure "Slow down the producer" Mechanism that signals upstream to stop producing when the queue fills up.
Idempotent worker "Safe to re-run" A task processed twice produces the same result. Required because workers may crash mid-run.
Durable queue "Survives crashes" Queue backed by disk or replicated storage; tasks are not lost when a worker crashes.
Matrix framework "Full message-passing swarm" Both data and control flow are serialized messages on distributed queues.

Problem

In plain words first

A swarm has no boss. Workers pull tasks from a shared queue, do them, and write results back, so fast workers simply take more tasks. It balances uneven work well and scales out easily, but there is no single place that knows what happened, and a worker that dies can lose its task unless the queue takes it back. LangGraph subgraphs and map-reduce are covered in Lesson 14.85 (linked above). This lesson kills a worker in the lesson's swarm, then schedules real, uneven model calls four ways.

Supervisor scales to a few workers. What about hundreds? The supervisor itself becomes the bottleneck: every decision about who does what funnels through one agent. One slow plan step stalls the whole system.

Swarm architectures flip the design. Instead of a central planner dispatching work, workers pick work off a shared queue. The "coordination" is baked into the event bus semantics. No orchestrator; the system scales until the queue does.

Concept

The shape

                ┌──── shared queue ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            results pool

No orchestrator. Each worker repeats: pull a task, process, write result (and optionally enqueue follow-ups).

When swarm fits

  • Many independent tasks. Scraping, transforming, classifying. Tasks do not depend on each other.
  • Variable-duration work. If some tasks take 100ms and others take 10s, a swarm balances load automatically — fast workers pull next jobs. A supervisor has to anticipate duration.
  • Throughput over determinism. You care about total completion time, not strict ordering.

When swarm fails

  • Ordered workflows. If step 3 needs step 2's output, a swarm risks step 3 firing before step 2 is done.
  • Global-plan tasks. Complex research questions benefit from a planner. A swarm of researchers produces independent facts, not a coherent report.
  • Debugging. With no central log and asynchronous work, reproducing a bug is expensive.

Matrix (arXiv:2511.21686)

Matrix is the 2025 paper that takes swarm to its natural conclusion: both control flow and data flow are serialized messages on distributed queues. No central coordinator. Fault tolerance comes from message durability. Scalability is the message broker's problem, not the system's.

Contribution: a programming model where multi-agent coordination is "what message topic does this agent subscribe to?" rather than "which agent does the supervisor pick next?" This makes the system look like a pub/sub event mesh.

Swarm in graph frameworks

LangGraph's langgraph-swarm package uses "swarm" for agents that hand control to each other through handoff tools, with the system remembering which agent was last active. That is decentralised routing between specialists, not the shared work queue built in this lesson; both drop the central supervisor.

Failure mode: starvation and hot-spotting

If all workers pull the fastest-available task, long-running tasks never get picked until they are the only ones left. Classic queue starvation.

Mitigations: - Priority queues with explicit aging (increase priority with wait time). - Worker specialization: some workers only take "long" tasks. - Back-pressure: limit how many fast tasks enter the queue.

The content-based routing link

Swarm pairs naturally with content-based routing (Lesson 16.22). Instead of a generic queue, have one queue per message type. Specialist workers subscribe only to their type. This is the basis for message-bus architectures that scale to thousands of agents.

The same idea as a formula

Makespan. With task times d1​,…,dn​ and m workers, no schedule can finish before

L=max(m1​i∑​di​, imax​di​).
A shared queue, where each free worker takes the next task, finishes within L+maxi​di​ at worst (Graham's list-scheduling bound). Sorting the queue longest-first brings it to within about 34​ of the best possible.

At-least-once delivery. A queue that takes a task back when its worker dies guarantees every task runs at least once, not exactly once. If the worker died after the side effect but before the acknowledgement, the task runs twice, so tasks must be idempotent.

Worked example
Scheduling one real workload
  • Twelve real model calls took between 0.4 s and 7.7 s, a 20× spread, and 50.6 s in total.
  • With 4 workers the lower bound is max(50.6/4,7.7)=12.6 s.
  • Fixed round-robin assignment took 15.6 s, the shared queue 14.8 s, and the queue sorted longest-first 14.3 s.
  • The lesson's queue gains less here than in its demo because round-robin happened to spread the long tasks; it gains most when assignment is unlucky, as in the lesson's pessimal case.

Killing a worker in the lesson's swarm

The lesson's Task and fake_work in two queues: the lesson's, which hands out tasks and forgets them, and one that puts a task back when its worker dies, up to three tries. One worker is killed on task 3. About 2 seconds.

# The lesson's swarm (imported from main.py) when a worker dies mid-task, as real workers do. The lesson's queue
# hands out a task and forgets it, so a crash loses it. A queue that leases tasks and takes them back on failure
# finishes every task, at the cost of possibly running one twice. Simulated tasks take 0.05 to 0.2 s; about 2 seconds.
import queue, threading, time
from main import Task, fake_work

TASKS = [Task(i, 0.2 if i % 3 == 0 else 0.05, 0) for i in range(12)]
def crashy(task, wid, crashed):
    if task.task_id == 3 and not crashed:                   # one worker's process dies on task 3, once
        crashed.add(wid)
        raise SystemExit("worker process killed")
    return fake_work(task)

def lesson_swarm(n=4):
    q, done, crashed = queue.Queue(), [], set()
    for t in TASKS: q.put(t)
    def worker(wid):
        while True:
            try: task = q.get_nowait()
            except queue.Empty: return
            try:
                crashy(task, wid, crashed)
            except SystemExit:
                return                                      # the worker is gone, and so is its task
            done.append(task.task_id); q.task_done()
    ths = [threading.Thread(target=worker, args=(i,)) for i in range(n)]
    for th in ths: th.start()
    for th in ths: th.join()
    return sorted(done)

def leased_swarm(n=4, max_tries=3):
    q, done, crashed, tries, lock = queue.Queue(), [], set(), {}, threading.Lock()
    for t in TASKS: q.put(t)
    def worker(wid):
        while True:
            try: task = q.get_nowait()
            except queue.Empty: return
            with lock: tries[task.task_id] = tries.get(task.task_id, 0) + 1
            try:
                crashy(task, wid, crashed)
            except SystemExit:
                if tries[task.task_id] < max_tries:
                    q.put(task)                             # lease expired: the task goes back on the queue
                return
            with lock: done.append(task.task_id)
    ths = [threading.Thread(target=worker, args=(i,)) for i in range(n)]
    for th in ths: th.start()
    for th in ths: th.join()
    return sorted(done), tries

got = lesson_swarm()
print(f"lesson's queue, one worker killed on task 3: finished {len(got)}/12, missing {sorted(set(range(12)) - set(got))}")
got2, tries = leased_swarm()
print(f"leased queue, same crash:                  finished {len(got2)}/12, missing {sorted(set(range(12)) - set(got2))}")
print(f"   task 3 was attempted {tries[3]} times; any task with a side effect must be safe to run twice")

def queue_makespan(durations, n=4):
    free = [0.0] * n                                     # each worker pulls the next task when it becomes free
    for d in durations:
        heapq.heapreplace(free, free[0] + d)
    return max(free)
n = 4
fixed = max(sum(times[i::n]) for i in range(n))
for label, wall in (("sequential", sum(times)), ("fixed round-robin", fixed), ("shared queue (lesson)", queue_makespan(times)),
                    ("queue, longest first", queue_makespan(sorted(times, reverse=True)))):
    print(f"   {label:<24} {wall:5.1f} s")
print(f"   lower bound (total / 4 or longest task): {max(sum(times) / n, max(times)):.1f} s")

Build it

code/main.py implements a swarm of 4 worker threads pulling from a shared queue.Queue. Tasks have variable durations (some fast, some slow). The demo contrasts:

  • Sequential baseline: one worker processes all tasks serially.
  • Fixed assignment: each task pre-assigned to a specific worker (supervisor-style).
  • Swarm: workers pull from a shared queue.

Swarm balances load automatically; fixed assignment leaves fast workers idle when their assigned task is slow.

Part 1 of 3 · Task, fake_work, run_sequential, run_fixed_assignment

"""Swarm architecture demo: workers pull from a shared queue.

Compares three scheduling strategies on a variable-duration workload:
  - sequential (1 worker processes all tasks)
  - fixed assignment (each task pre-assigned to a specific worker)
  - swarm (4 workers pull from a shared queue)

Swarm balances load automatically; fixed assignment leaves fast workers idle.
"""
from __future__ import annotations

import queue
import threading
import time
from dataclasses import dataclass


@dataclass
class Task:
    task_id: int
    duration: float
    pre_assigned: int  # for the fixed-assignment baseline


def fake_work(task: Task) -> str:
    time.sleep(task.duration)
    return f"task-{task.task_id}-done"


def run_sequential(tasks: list[Task]) -> tuple[float, dict[int, int]]:
    t0 = time.time()
    counts: dict[int, int] = {0: 0}
    for t in tasks:
        fake_work(t)
        counts[0] += 1
    return time.time() - t0, counts


def run_fixed_assignment(tasks: list[Task], n_workers: int) -> tuple[float, dict[int, int]]:
    """Each task is pre-assigned to worker id. Worker processes its tasks serially."""
    per_worker: dict[int, list[Task]] = {i: [] for i in range(n_workers)}
    for t in tasks:
        per_worker[t.pre_assigned].append(t)
    counts: dict[int, int] = {i: 0 for i in range(n_workers)}

    def worker(wid: int) -> None:
        for t in per_worker[wid]:
            fake_work(t)
            counts[wid] += 1

    t0 = time.time()
    threads = [threading.Thread(target=worker, args=(i,)) for i in range(n_workers)]
    for th in threads:
        th.start()
    for th in threads:
        th.join()
    return time.time() - t0, counts

Part 2 of 3 · run_swarm, make_tasks

def run_swarm(tasks: list[Task], n_workers: int) -> tuple[float, dict[int, int]]:
    """Workers pull from a shared queue."""
    q: queue.Queue = queue.Queue()
    for t in tasks:
        q.put(t)
    counts: dict[int, int] = {i: 0 for i in range(n_workers)}
    lock = threading.Lock()

    def worker(wid: int) -> None:
        while True:
            try:
                task = q.get_nowait()
            except queue.Empty:
                return
            fake_work(task)
            with lock:
                counts[wid] += 1
            q.task_done()

    t0 = time.time()
    threads = [threading.Thread(target=worker, args=(i,)) for i in range(n_workers)]
    for th in threads:
        th.start()
    for th in threads:
        th.join()
    return time.time() - t0, counts


def make_tasks(n_workers: int = 4) -> list[Task]:
    """8 tasks: half fast (0.1s), half slow (0.4s). Pre-assignment is pessimal:
    worker 0 gets all slow tasks, others get fast ones."""
    tasks: list[Task] = []
    for i in range(8):
        is_slow = i < 4
        tasks.append(
            Task(
                task_id=i,
                duration=0.4 if is_slow else 0.1,
                pre_assigned=0 if is_slow else (i - 3) % n_workers,
            )
        )
    return tasks


def main() -> None:
    print("Swarm architecture demo: variable-duration workload")
    print("-" * 56)
    n_workers = 4

    tasks = make_tasks(n_workers)
    total_work = sum(t.duration for t in tasks)
    print(f"{len(tasks)} tasks, 4 slow (0.4s) + 4 fast (0.1s)")
    print(f"Total work-seconds: {total_work:.2f}s")
    print(f"Ideal parallel time with {n_workers} workers: {total_work / n_workers:.2f}s")

    seq_time, seq_counts = run_sequential(tasks)
    print(f"\nSequential (1 worker):      wall={seq_time:.2f}s, counts={seq_counts}")

    fixed_time, fixed_counts = run_fixed_assignment(tasks, n_workers)
    print(f"Fixed assignment ({n_workers} workers): wall={fixed_time:.2f}s, counts={fixed_counts}")
    print("  worker 0 got all 4 slow tasks; other workers idle after their fast ones.")

    swarm_time, swarm_counts = run_swarm(tasks, n_workers)
    print(f"Swarm ({n_workers} workers):            wall={swarm_time:.2f}s, counts={swarm_counts}")
    print("  load balances automatically: slow workers finish first, fast pull next job.")

    speedup_vs_seq = seq_time / swarm_time if swarm_time > 0 else float("inf")
    speedup_vs_fixed = fixed_time / swarm_time if swarm_time > 0 else float("inf")
    print(f"\nSwarm speedup vs sequential: {speedup_vs_seq:.2f}x")
    print(f"Swarm speedup vs fixed:      {speedup_vs_fixed:.2f}x")
    print("\nTakeaway: swarm wins when duration varies and assignment is hard to predict.")
    print("Tradeoff: no central trace; debugging requires per-task IDs and durable logs.")

Break it on purpose

Your swarm of document-processing agents pulls jobs from a queue and emails each customer a summary. During a deploy, workers are killed mid-job. Some customers never get their summary, and after you add automatic re-queuing, others get two. Using this lesson, what is the full fix? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Queues do the work. Production agent fleets run on Redis, SQS, Kafka, Temporal task queues or Celery, with leases (visibility timeouts) that return a task when a worker stops responding.
  • "Swarm" means two things. OpenAI's Swarm and LangGraph's langgraph-swarm mean agents handing off to each other; Matrix (2025) and queue-based fleets mean workers pulling from shared queues.
  • Serving decides parallelism. Hosted APIs and GPU servers such as vLLM run many requests at once; on one CPU, parallel workers mostly share cores (Lesson 16.5).
  • On your laptop: Python's queue plus threads is fine for I/O-bound agents calling an API; for local models, send concurrent requests to one batching server rather than loading a model per worker.

Sources: Matrix (arXiv:2511.21686), LangGraph Swarm, Amazon SQS, visibility timeout, Graham, Bounds on multiprocessing timing anomalies (1969).

Recap
What to keep from this lesson
  • Workers pulling from a shared queue balance uneven work without a supervisor.
  • Lease tasks: a task a worker does not finish must go back on the queue.
  • Re-queuing means at-least-once; make every task safe to run twice.
  • Real model calls vary by 20× or more; sort long tasks first when you can predict them.
  • Keep a durable log per task id, because a swarm has no central trace.

Ship it

Checklist:

  • Priority queue with aging. Prevent long-task starvation.
  • Worker idempotency. A task may be pulled more than once if a worker crashes mid-run. Workers must be idempotent.
  • Durable queue. Use Kafka, Redis Streams, or a database-backed queue for production. queue.Queue is in-memory only.
  • Observability per task. Every task has a trace ID; every worker logs start/end with it.
  • Back-pressure. If the queue grows faster than workers drain it, slow the producer.

description: Decide whether a task fits a swarm (decentralized) architecture or a supervisor (centralized) one.
version: 1.0.0
phase: 16

---

Given a task and its throughput / determinism requirements, recommend swarm or supervisor and list the specific queue and guardrail choices.

Produce:

1. **Task independence check.** Are subtasks independent or do they depend on each other? Swarm only fits when independence is high.
2. **Duration distribution.** Uniform vs variable. Swarm wins mostly on variable-duration workloads.
3. **Ordering requirement.** Strict, relaxed, or none. Swarm does not preserve order; supervisor does.
4. **Debuggability need.** High (finance, medical) → supervisor. Medium → swarm with per-task trace IDs.
5. **Queue choice.** In-memory (`queue.Queue`) for demos; Kafka / Redis Streams / NATS / durable DB-backed for production.
6. **Worker design requirements.** Must be idempotent; must emit per-task trace; must handle back-pressure.
7. **Anti-starvation plan.** Priority aging, worker specialization, bounded queue.
8. **Observability plan.** Per-task IDs, start/end events, result pool schema.

Hard rejects:

- Swarm recommendation for tasks with hard ordering requirements.
- Swarm without idempotent workers.
- Swarm without durable queue in production.

Refusal rules:

- If the task has fewer than 10 independent units per second, refuse swarm and recommend supervisor. Swarm overhead is not justified at low throughput.
- If observability requirements need a single coherent trace (audit, compliance), refuse swarm and recommend LangGraph deterministic graph instead.

Output: a one-page architectural brief. Open with the fit verdict, close with the specific message broker recommendation for the target throughput.

Solutions

SolutionP1 · Eleven, then twelve with one task run twice

Eleven. The lesson's queue does not remember tasks it has handed out, so the task dies with the worker, and the other three workers drain the rest.

With a queue that takes failed tasks back, all 12 finish, and task 3 runs twice: once in the worker that was killed and once in the worker that completed it. That is at-least-once delivery.

SolutionB1 · Lost and duplicated emails

Re-queuing fixed the lost work and created duplicates; both halves need handling.

  • Lease, do not hand off. A task stays owned by the queue until the worker acknowledges it; if the worker dies or times out, it returns to the queue. That fixes the missing summaries.
  • Make the side effect idempotent. Send each email with a key such as the job id, and have the email step check whether that key was already sent. That fixes the duplicates.
  • Acknowledge after the side effect is recorded, and record it with the job id in a durable log, so a restart can tell done from not done.
  • Drain before deploys: stop taking new jobs and let workers finish, so fewer jobs are interrupted in the first place.
