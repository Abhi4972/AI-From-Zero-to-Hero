In plain words first
The idea in one line

NER found "Paris." Entity linking decides: Paris, France? Paris Hilton? Paris, Texas? Paris (the Trojan prince)? Without linking, your knowledge graph stays ambiguous.

The problem

In plain words first

Named entity recognition (Lesson 5.6) finds that "Jordan" is a name. Entity linking decides which Jordan: the basketball player, the actor, the machine-learning professor, or the country. It connects each mention to one entry in a knowledge base such as Wikidata, so that every mention of the same thing gets the same ID, and that ID brings facts with it. It works in two steps. First, look up which entries the mention's text could possibly mean (candidate generation). Then pick the one that fits the surrounding text best (disambiguation), helped by how often each candidate is meant in general. This lesson writes out the classic scoring formula and the modern embedding and generative versions. It then compares word overlap with embeddings on ambiguous sentences, shows how a popularity prior can override clear context, and shows how a system should answer "none of these" (NIL).

A sentence reads: "Jordan beat the press." Your NER tags "Jordan" as PERSON. Good. But which Jordan?

  • Michael Jordan (basketball)?
  • Michael B. Jordan (actor)?
  • Michael I. Jordan (Berkeley ML professor — yes, this confusion is real in ML papers)?
  • Jordan (the country)?
  • Jordan (Hebrew first name)?

Entity linking (EL) resolves each mention to a unique entry in a knowledge base: Wikidata, Wikipedia, DBpedia, or your domain KB. Two subtasks:

  1. Candidate generation. Given "Jordan," which KB entries are plausible?
  2. Disambiguation. Given the context, which candidate is the right one?

Both steps are learnable. Both are benchmarked. The combined pipeline has been stable for a decade — what changes is the quality of the disambiguator.

The idea

Candidate generation. Given the mention surface form ("Jordan"), look up candidates in an alias index. Wikipedia alias dictionaries cover most named entities: "JFK" → John F. Kennedy, Jacqueline Kennedy, JFK airport, JFK (movie). Typical index returns 10-30 candidates per mention.

Disambiguation: three approaches.

  1. Prior + context (Milne & Witten, 2008). P(entity | mention) × context-similarity(entity, text). Works well, fast, no training.
  2. Embedding-based (REL, BLINK). Encode mention + context. Encode each candidate's description. Pick max cosine, usually followed by a cross-encoder rerank of the top candidates. A common default from 2020 on.
  3. Generative (GENRE, 2021; LLM-based, 2023+). Decode the entity's canonical name token-by-token. Constrained to a trie of valid entity names so output is guaranteed to be a valid KB id.

End-to-end vs pipeline. Modern models (ELQ, BLINK, ExtEnD, GENRE) run NER + candidate generation + disambiguation in one pass. Pipeline systems still dominate in production because you can swap components.

The same idea as a formula

Candidate generation returns C(m)={e:(m,e)∈alias index}; candidate recall is the share of gold mentions with e∗∈C(m), the ceiling for everything after.

The commonness prior. From Wikipedia's links, how often does the anchor text m point to entity e?

P(e∣m)=∑e′​count(m→e′)count(m→e)​

Picking argmaxe​P(e∣m) alone, ignoring context, is a famously strong baseline: most mentions mean their most common sense.

Combining prior and context. A simple log-linear score:

score(e∣m,x)=λlogP(e∣m)+(1−λ)sim(ctx(x),desc(e))

with similarity from word overlap (the lesson's Jaccard) or embeddings. Milne and Witten (2008) added relatedness between candidate entities of different mentions in the same text, measured by shared Wikipedia in-links: "Bulls" and "Chicago" pull "Jordan" toward the basketball player.

Bi-encoder retrieval (BLINK, Wu et al., 2020): sim(m,e)=Em​(mention in context)⊤Ee​(entity description), trained contrastively so the right entity scores above others; entity vectors are precomputed for millions of entities, then a cross-encoder rescores the top 10 to 100.

NIL. If maxe​score(e)<τ, predict NIL: the mention's entity is not in the knowledge base. τ trades wrong links against missed links, like the FAQ threshold in Lesson 5.17.

Generative linking (GENRE): P(e∣x)=∏t​P(yt​∣y<t​,x) over the tokens of the title of e, with beam search restricted to a trie of valid titles, so the output is always a real entity.

Worked example
Prior versus context by hand

Mention "Jordan" in "Jordan's paper on variational inference won a best-paper award." Candidates with (assumed) link counts and context similarities:

candidate link count P(e∣m) logP context sim
Michael Jordan (basketball) 7,000 0.70 -0.36 0.05
Jordan (country) 2,500 0.25 -1.39 0.02
Michael I. Jordan (professor) 500 0.05 -3.00 0.60

With λ=0.5: basketball 0.5(−0.36)+0.5(0.05)=−0.155; country −0.685; professor 0.5(−3.00)+0.5(0.60)=−1.20. The prior wins and the link is wrong. With λ=0.2: basketball −0.072+0.04=−0.032; professor −0.60+0.48=−0.12; still wrong. Only at λ=0.1 does the professor win (−0.30+0.54=0.24 against −0.036+0.045=0.009). A log prior has a huge range; context signals live on a small one. This is the "popularity bias" pitfall in numbers.

Check your mental model
  • ✗ "Entity linking is NER with more labels."
    ✓ NER chooses among a few types; linking chooses among millions of entities, most of which never appear in training data, so it relies on descriptions and aliases rather than a classifier per entity.
  • ✗ "If the right entity is not found, the system made a disambiguation error."
    ✓ First check candidate recall: if the right entity was never a candidate, no disambiguator could have found it.
  • ✗ "Always link every mention."
    ✓ Many mentions refer to things not in the knowledge base; predicting NIL is a correct answer.

Idea 1 · The two measurements

  • Mention recall (candidate gen). Fraction of gold mentions where the correct KB entry appears in the candidate list. Floor for the whole pipeline.
  • Disambiguation accuracy / F1. Given correct candidates, how often the top-1 is right.

Always report both. A system with 99% disambiguation on 80% candidate recall is an 80% pipeline.

Step 1 · build an alias index from Wikipedia redirects

alias_to_entities = {
    "jordan": ["Q41421 (Michael Jordan)", "Q810 (Jordan, country)", "Q254110 (Michael B. Jordan)"],
    "paris":  ["Q90 (Paris, France)", "Q663094 (Paris, Texas)", "Q55411 (Paris Hilton)"],
    "apple":  ["Q312 (Apple Inc.)", "Q89 (apple, fruit)"],
}

Real alias tables are built from Wikipedia redirects, disambiguation pages, link anchor texts and Wikidata's "also known as" labels, millions of (alias, entity) pairs. Download them from the Wikipedia and Wikidata dumps and store them as an inverted index. (In the toy index above, the Wikidata IDs of Michael Jordan, Jordan the country, Paris, Apple Inc. and the apple fruit are the real ones; treat the others as placeholders to look up.)

Step 2 · context-based disambiguation

def disambiguate(mention, context, alias_index, entity_desc):
    candidates = alias_index.get(mention.lower(), [])
    if not candidates:
        return None, 0.0
    context_words = set(tokenize(context))
    best, best_score = None, -1
    for entity_id in candidates:
        desc_words = set(tokenize(entity_desc[entity_id]))
        union = len(context_words | desc_words)
        score = len(context_words & desc_words) / union if union else 0.0
        if score > best_score:
            best, best_score = entity_id, score
    return best, best_score

The Jaccard overlap is a toy. Replace with cosine similarity on embeddings (see code/main.py step-2 for the transformer version).

Break it on purpose

Step 3 · embedding-based (BLINK-style)

from sentence_transformers import SentenceTransformer
encoder = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

def embed_mention(text, mention_span):
    start, end = mention_span
    marked = f"{text[:start]} [MENTION] {text[start:end]} [/MENTION] {text[end:]}"
    return encoder.encode([marked], normalize_embeddings=True)[0]

def embed_entity(entity_id, description):
    return encoder.encode([f"{entity_id}: {description}"], normalize_embeddings=True)[0]

At index time, embed every KB entity once. At query time, embed the mention + context once, dot-product against the candidate pool, pick max.

Step 4 · generative entity linking (concept)

GENRE (De Cao et al., 2021) decodes the entity's Wikipedia title token by token with a sequence-to-sequence model. Constrained decoding (Lesson 5.20) over a prefix trie of all valid titles ensures only real titles can be output. Its modern descendants are LLM-prompted linkers that choose from a candidate list with structured output.

prompt = f"""Text: {text}
Mention: {mention}
List the best Wikipedia title for this mention.
Respond with JSON: {{"title": "..."}}"""

Combined with a whitelist (Outlines choice), this is the simplest EL pipeline to ship in 2026.

Step 5 · evaluate on AIDA-CoNLL

AIDA-CoNLL is the standard EL benchmark: 1,393 Reuters articles, 34k mentions, Wikipedia entities. Report in-KB accuracy (P@1) and out-of-KB NIL-detection rate.

Word overlap versus embeddings on ambiguous mentions

A small knowledge base with one-line descriptions for each candidate in the lesson's alias index, plus the Berkeley professor. Twelve test sentences, each with the intended entity. The lesson's Jaccard disambiguate and its BLINK-style embed_mention / embed_entity each choose; then a NIL threshold is applied to the embedding scores.

import re
def tokenize(t):
    return re.findall(r"[a-z0-9]+", t.lower())
kb = {"Michael Jordan": "American basketball player who won six NBA championships with the Chicago Bulls.",
      "Michael B. Jordan": "American actor known for the films Creed, Black Panther and Fruitvale Station.",
      "Michael I. Jordan": "American computer scientist and statistician at UC Berkeley, known for machine learning research.",
      "Jordan (country)": "Country in Western Asia on the east bank of the Jordan River; capital Amman.",
      "Paris, France": "Capital and largest city of France, on the Seine, home of the Eiffel Tower and the Louvre.",
      "Paris, Texas": "Small city in Lamar County in the U.S. state of Texas.",
      "Paris Hilton": "American media personality, businesswoman and socialite, heiress of the Hilton hotel family.",
      "Apple Inc.": "American technology company that makes the iPhone, Mac computers and the iOS operating system.",
      "apple (fruit)": "Edible round fruit of the apple tree, eaten raw, baked in pies or pressed into cider."}
aliases = {"jordan": ["Michael Jordan", "Michael B. Jordan", "Michael I. Jordan", "Jordan (country)"],
           "paris": ["Paris, France", "Paris, Texas", "Paris Hilton"], "apple": ["Apple Inc.", "apple (fruit)"]}
tests = [("Jordan scored 38 points as the Bulls won the NBA final.", "Jordan", "Michael Jordan"),
         ("Jordan starred as the boxer Adonis in Creed.", "Jordan", "Michael B. Jordan"),
         ("Jordan's work on graphical models shaped statistical machine learning.", "Jordan", "Michael I. Jordan"),
         ("Tourists in Jordan visit Petra and float in the Dead Sea.", "Jordan", "Jordan (country)"),
         ("Jordan signed a trade agreement with its neighbours.", "Jordan", "Jordan (country)"),
         ("We took the train to Paris to see the Louvre.", "Paris", "Paris, France"),
         ("Paris launched a new fragrance and a reality show.", "Paris", "Paris Hilton"),
         ("Paris is a small town in northeast Texas near the Oklahoma border.", "Paris", "Paris, Texas"),
         ("Apple unveiled a faster chip for its laptops.", "Apple", "Apple Inc."),
         ("She baked an apple pie with cinnamon.", "apple", "apple (fruit)"),
         ("Apple shares rose after strong iPhone sales.", "Apple", "Apple Inc."),
         ("An apple a day keeps the doctor away.", "apple", "apple (fruit)")]
desc = kb
ent_vec = {e: embed_entity(e, d) for e, d in kb.items()}
right_j = right_e = 0
emb_scores = []
for sent, mention, gold in tests:
    j, _ = disambiguate(mention, sent, aliases, desc)
    start = sent.find(mention); mv = embed_mention(sent, (start, start + len(mention)))
    sims = {e: float(mv @ ent_vec[e]) for e in aliases[mention.lower()]}
    e_best = max(sims, key=sims.get); emb_scores.append(sims[e_best])
    right_j += j == gold; right_e += e_best == gold
    print(f"{sent[:58]:60s} Jaccard: {str(j):18s} embedding: {e_best:18s} ({sims[e_best]:.2f}) {'ok' if e_best == gold else 'WRONG'}")
print(f"\ncorrect: Jaccard {right_j}/12, embedding {right_e}/12")
for sent, mention in [("Jordan Peterson gave a lecture on psychology.", "Jordan"), ("Paris Saint-Germain won the league again.", "Paris")]:
    start = sent.find(mention); mv = embed_mention(sent, (start, start + len(mention)))
    sims = {e: float(mv @ ent_vec[e]) for e in aliases[mention.lower()]}
    print(f"not in the KB: {sent!r} -> best {max(sims, key=sims.get)} at {max(sims.values()):.2f}  (lowest correct score above: {min(emb_scores):.2f})")

Reading this output

Embeddings get 11 of 12, Jaccard 9. Jaccard's failures show what word overlap really measures: "starred as the boxer Adonis in Creed" goes to Jordan the country, because the country's description shares filler words ("the", "in") with the sentence; the trade agreement goes to the basketball player; "a faster chip for its laptops" goes to the fruit. The embedding linker gets all three, matching meaning rather than words, and fails on one: "launched a new fragrance and a reality show" goes to Paris, France, a reminder that a small general-purpose encoder knows celebrities less well than cities. The last two lines are the NIL problem. "Jordan Peterson" is not in the knowledge base, yet his sentence scores 0.50 against the machine-learning professor, higher than several correct links above (the lowest is 0.32). No single threshold on this score separates "not in the KB" from "correct but weakly worded". Real systems handle NIL with a dedicated classifier, with more aliases (the full name "Jordan Peterson" would retrieve a different candidate set), or by reranking with a cross-encoder.

Industry practice
What's current (2024–2026)
  • LLMs as linkers. Prompting an LLM with the mention, its context and a short candidate list (from an alias index or a bi-encoder) is now a common production pattern; the candidate list keeps the output a valid ID, the same idea as GENRE's trie.
  • Efficient end-to-end linking. Amazon's open-source ReFinED links all mentions of a document in one forward pass using entity types and descriptions, which makes Wikidata-scale linking cheap enough for large corpora.
  • Linking grounds retrieval. Knowledge-graph RAG pipelines (Microsoft GraphRAG, Neo4j, Amazon Bedrock Knowledge Bases with Neptune) depend on resolving mentions to stable entity IDs so that facts from different documents attach to the same node.

Sources: ReFinED, BLINK, GraphRAG, Bedrock GraphRAG.

Pitfalls

  • NIL handling. Some mentions are not in the KB (emerging entities, obscure people). Systems must predict NIL instead of guessing the wrong entity. Measured separately.
  • Mention boundary errors. Upstream NER misses partial spans ("Bank of America" tagged as just "Bank"). EL recall drops.
  • Popularity bias. Trained systems over-predict frequent entities. A mention of "Michael I. Jordan" on an ML paper often links to basketball Jordan.
  • Cross-lingual EL. Mapping mentions in Chinese text to English Wikipedia entities. Requires a multilingual encoder or a translation step.
  • KB staleness. New companies, events, people are not in last year's Wikipedia dump. Production pipelines need a refresh loop.

Use it: the same idea with real libraries

The 2026 stack:

Situation Pick
General-purpose English + Wikipedia BLINK or REL
Cross-lingual, KB = Wikipedia mGENRE
LLM-friendly, few mentions/day Prompt Claude/GPT-4 with candidate list + constrained JSON
Domain-specific KB (medical, legal) Custom BERT with KB-aware retrieval + fine-tune on domain AIDA-style set
Extremely low-latency Exact-match prior only (Milne-Witten baseline)
Research SOTA GENRE / ExtEnD / generative LLM-EL

Production pattern that ships in 2026: NER → coref → EL on each mention → collapse clusters to one canonical entity per cluster. Output: one KB id per entity in the document, not one per mention.

Recap
What to keep from this lesson
  • Entity linking = candidate generation (alias index) + disambiguation (prior, context, relatedness).
  • The commonness prior P(e∣m) is a strong baseline and a source of popularity bias; its log scale can swamp context.
  • Embedding linkers compare mention-in-context with entity descriptions; a cross-encoder reranks the top candidates.
  • Predict NIL below a threshold; report candidate recall and disambiguation accuracy separately.
  • Collapse coreference clusters to one entity ID per real-world entity.

Solutions

SolutionP1 · Embeddings, 11 to 9

Jaccard only works when the sentence repeats words from the right description, and it is easily fooled by shared filler words: it sent the actor's sentence ("starred as the boxer Adonis in Creed") to the country and the laptop chip to the fruit. Embeddings capture that "graphical models" is about machine learning and "trade agreement with its neighbours" about a country. Both still make errors, and the embedding linker's one miss (Paris Hilton taken as the city) shows that its knowledge depends on its training text.

SolutionB1 · A confident-looking guess

Every candidate scores 0 overlap. The loop keeps the first candidate whose score beats the initial best_score = -1, so it returns the first entry in the alias list with score 0.0: a link chosen by list order, not evidence. Downstream code that ignores the score treats it as a real link. Return NIL when the best score is below a threshold (or exactly 0 here), and keep the score with every link.
