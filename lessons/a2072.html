In plain words first
The idea in one line

Choose isolation controls from an explicit capability requirement.

The problem

In plain words first

"Run the agent's code in a sandbox" covers a wide ladder of protections: a separate process, a restricted filesystem, a container with its own network rules, a micro virtual machine with its own kernel. Each costs more and protects against more. Picking by habit gives either too little protection or needless cost.

This project, in Rust, picks from an explicit requirement. You state four facts (is the code untrusted? are there secrets on the host? must the network be denied? is a separate kernel required?). Profiles are modelled as data listing which controls they provide. The cheapest profile that meets every requirement within a cost ceiling is chosen. And the report states what was not verified: this is a policy simulation, not proof that an operating system enforced anything.

A sandbox evidence planner mapping requested capabilities to observed runtime probes.

Write the threat requirement as booleans before selecting a runtime. Here network=true means network denial is required, and host_kernel=true means a separate kernel is required. Neither name grants access.

What you will build: Select a modeled isolation policy, inspect an optional local Docker invocation, and compare requested controls with observed harmless probes.

Where it stops: A sandbox evidence planner mapping requested capabilities to observed runtime probes. Default output is a policy simulation.

Step 3 · Select the least costly sufficient profile

Step 3 of 4 · about 2 hours · Rust

Filter insufficient profiles before comparing cost. Respect the configured cost ceiling, break ties by name, and return an explicit no-suitable-profile error. Never downgrade a required isolation control merely because the budget is too small.

Implementation boundary.

pub fn select(n:&Needs,candidates:&[Profile],budget:u32)->Result<Profile,Error>

Worked Orchard case. Before coding, review Rust ownership and Result and Docker for AI. Complete Step 2 first.

The cheapest sufficient profile may exceed the allowed budget. When kernel separation is required, budget 4 cannot silently downgrade to a container costing 3.

kernel separation required; candidates costs 1,2,3,5
budget 4 -> no sufficient profile
budget 5 -> microvm-fixture

Build and inspect. Filter by capabilities first, then cost, then stable name ordering. Return a limit error if the remaining set is empty.

def select(need, budget):
    ok = [(cost, name) for name, cost, has in profiles if all(has[k] for k, v in need.items() if v) and cost <= budget]

Step 4 of 4 · about 2 hours · Rust

Return the selected fixture and state clearly that operating-system enforcement has not been performed. List shared-kernel and enabled-network residuals from the selected controls, and reject a profile that fails the original requirements. The report is an input to deployment review.

Check your mental model

Which statements are right?

  • ✓ An insufficient profile is filtered out before costs are compared.
  • ✗ If no profile fits the budget, the selector should pick the strongest one that fits. That silently downgrades a requirement; it returns "no suitable profile".
  • ✓ A container shares the host's kernel, which the report lists as a residual risk.
  • ✗ Selecting a profile proves the sandbox is enforced. The report says runtime_verified: false; enforcement must be tested separately.

"""Choose a modeled policy; optionally verify one local Docker container boundary."""

import argparse, json, subprocess, tempfile
from pathlib import Path


def docker_args(image):
    if not image or image.startswith("-"):
        raise ValueError("explicit local image required")
    return [
        "docker",
        "run",
        "--rm",
        "--pull=never",
        "--network",
        "none",
        "--read-only",
        "--cap-drop",
        "ALL",
        "--security-opt",
        "no-new-privileges",
        "--pids-limit",
        "32",
        "--memory",
        "64m",
        "--cpus",
        "0.5",
        "--user",
        "65534:65534",
        image,
        "sh",
        "-c",
        'if touch /probe 2>/dev/null; then echo root_write=allowed; exit 2; else echo root_write=denied; fi; cat /proc/net/route; test -z "$(tail -n +2 /proc/net/route)" && echo default_route=absent',
    ]


def main():
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("requirements")
    parser.add_argument("--budget", type=int, default=3)
    parser.add_argument("--docker-image")
    parser.add_argument("--execute", action="store_true")
    args = parser.parse_args()
    with tempfile.TemporaryDirectory(prefix="sandbox-plan-") as folder:
        binary = Path(folder) / "planner"
        subprocess.run(
            [
                "rustc",
                "--edition=2021",
                str(Path(__file__).with_name("cli.rs")),
                "-o",
                str(binary),
            ],
            check=True,
            capture_output=True,
            text=True,
        )
        run = subprocess.run(
            [str(binary), args.requirements, str(args.budget)],
            capture_output=True,
            text=True,
        )
        if run.returncode:
            raise ValueError(run.stderr.strip())
        result = {
            "schema_version": 1,
            "policy": run.stdout,
            "mode": "policy_simulation",
            "runtime_verified": False,
        }
        if args.docker_image:
            if "host_kernel=true" in args.requirements:
                raise ValueError(
                    "Docker probe cannot establish independent guest kernel"
                )
            result["command"] = docker_args(args.docker_image)
            if args.execute:
                subprocess.run(
                    ["docker", "image", "inspect", args.docker_image],
                    check=True,
                    capture_output=True,
                    timeout=10,
                )
                tested = subprocess.run(
                    result["command"], capture_output=True, text=True, timeout=20
                )
                result.update(
                    mode="docker_probe",
                    runtime_verified=tested.returncode == 0,
                    returncode=tested.returncode,
                    observed=tested.stdout,
                    errors=tested.stderr,
                    residual="shared kernel; these two probes are not escape-resistance proof",
                )
        elif args.execute:
            parser.error("--execute requires --docker-image")
        print(json.dumps(result, indent=2))


if __name__ == "__main__":
    main()

            args.first()
                .ok_or_else(|| Error::Invalid("requirements required".into()))?,

            .parse::<u32>()

        plan(&request, &selected)

        Ok(out) => print!("{}", out),
        Err(e) => {

            std::process::exit(1)
        }
    }
}

Codesolution/stage1.rs (31 lines)
use super::*;
pub fn needs(text: &str) -> Result<Needs, Error> {
    let mut n = Needs {
        untrusted: false,
        secrets: false,
        network: false,
        host_kernel: false,
    };
    let mut seen = std::collections::BTreeSet::new();
    for pair in text.split(',') {
        let (k, v) = pair
            .split_once('=')
            .ok_or_else(|| Error::Invalid("key=boolean required".into()))?;
        if !seen.insert(k) {
            return Err(Error::Conflict);
        }
        let flag = match v {
            "true" => true,
            "false" => false,
            _ => return Err(Error::Invalid("true or false required".into())),
        };
        match k {
            "untrusted" => n.untrusted = flag,
            "secrets" => n.secrets = flag,
            "network" => n.network = flag,
            "host_kernel" => n.host_kernel = flag,
            _ => return Err(Error::Invalid("unknown capability".into())),
        }
    }
    Ok(n)
}

Codesolution/stage3.rs (9 lines)
use super::*;
pub fn select(n: &Needs, candidates: &[Profile], budget: u32) -> Result<Profile, Error> {
    candidates
        .iter()
        .filter(|p| p.cost <= budget && satisfies(n, p))
        .min_by(|a, b| a.cost.cmp(&b.cost).then(a.name.cmp(&b.name)))
        .cloned()
        .ok_or(Error::Limit)
}
Codesolution/stage4.rs (18 lines)
use super::*;
pub fn plan(n: &Needs, p: &Profile) -> Result<String, Error> {
    if !satisfies(n, p) {
        return Err(Error::Invalid("insufficient profile".into()));
    }
    let mut out = format!(
        "profile={} mode=policy-simulation os_isolation=false\n",
        p.name
    );
    if !p.kernel {
        out.push_str("residual=shared-host-kernel\n");
    }
    if !p.network {
        out.push_str("residual=network-not-denied\n");
    }
    out.push_str("verify=runtime-configuration-and-escape-tests\n");
    Ok(out)
}

Where the project stops

Default output is a policy simulation. --docker-image previews an invocation; --execute requires an already available local image and Docker. Only root-write and default-route probes are tested. The adapter never implements or verifies a microVM boundary.

Break it on purpose

A team runs untrusted, model-generated code in a Docker container with the host's Docker socket mounted "so it can build images". Which requirement does that break, whatever the profile name says? (Solution B1.)

Exercises

  1. Which additional requirement would make a shared-kernel container insufficient? (step 1)
  2. Why is the model not evidence that a running container has these settings? (step 2)
  3. What should change when two sufficient profiles have the same modeled cost? (step 3)

  4. If root_write becomes allowed, which runtime setting would you inspect first? (step 4)

  5. Why model profiles as booleans per control rather than as a strength ranking?

  6. When is a micro-VM worth its cost?
  7. What would runtime verification of the container profile involve?

Solutions

Solution
  1. Controls, not rankings

A ranking implies "stronger is better at everything", which is false (a profile may isolate the filesystem but allow the network). Booleans per control let the selector match exactly what is required.

Solution
  1. When a micro-VM pays

When the code is untrusted and a kernel exploit would be catastrophic (secrets, other tenants on the host). A separate kernel removes the shared-kernel residual that containers keep.

Solution
  1. Verifying a container

Inspect the actual runtime configuration (network mode, mounts, capabilities, user), then run harmless probes from inside: try to reach the network, read a host path, see host processes. Each probe must fail as the policy says.

SolutionB1 · A mounted Docker socket

The isolation of the host: control of the Docker socket lets code start privileged containers and read the host's files and secrets. The container is no longer a sandbox, whatever its profile is called.
