In plain words first
The idea in one line

Chaos engineering for LLMs is its own discipline in 2026. Prerequisites before running experiments in production: defined SLI/SLO, trace+metric+log observability, automated rollback, runbooks, on-call. Architecture has four planes: control (experiment scheduler), target (services, infra, data stores), safety (guards + abort + traffic filters), observability (metrics + traces + logs), feedback (into SLO adjustments). Guardrails are mandatory: burn-rate alerts pause experiments if daily error-budget burn > 2x expected; suppression windows + trace-ID correlation dedupe alert noise. Cadence: weekly small canary + SLO review; monthly game day + postmortem; quarterly cross-team resilience audit + dependency mapping. LLM-specific experiments: memory overload, network failures, provider outages, malformed prompts, KV cache eviction storms. Tooling: Harness Chaos Engineering (LLM-derived recommendations, blast-radius downscaling, MCP tool integration); LitmusChaos (CNCF); Chaos Mesh (CNCF Kubernetes-native).

The problem

In plain words first

Chaos engineering means breaking parts of your own system on purpose, in a controlled way, to see whether it survives as designed. You kill a server, cut a network link or make a dependency fail, and watch whether traffic reroutes, fallbacks kick in and alerts fire. LLM stacks have failure modes ordinary services do not: a provider returning "too many requests" for minutes, a KV cache that overflows under long prompts, a strange prompt that stalls the tokenizer. Chaos is only safe with guardrails. You need a defined error budget (how many failures your objective allows), a burn-rate guard that stops an experiment when it eats that budget too fast, a limited blast radius (how much traffic an experiment can touch) and a way to roll back.

Chaos testing in traditional stacks is established. LLM stacks add new failure modes. A 4K-token prompt with a poison character stalls the tokenizer for 12 seconds. An upstream provider 429s; your gateway retries; your service OOMs on retry-amplified concurrency. A KV cache eviction storm under burst load causes re-prefill cascades that saturate compute.

None of these show up in unit tests. Chaos engineering is how you discover them before users do.

Idea 1 · Prerequisites

Don't run chaos in production without:

  1. SLI/SLO — defined service-level indicators and objectives.
  2. Observability — traces, metrics, logs, wired to dashboards.
  3. Automated rollback — Phase 17 · 20 policy-flag rollback.
  4. Runbooks — structured, Phase 17 · 23.
  5. On-call — someone to respond.

Missing any means chaos becomes real incident.

Idea 2 · Four planes + feedback

Control plane — experiment scheduler (Litmus workflow, Chaos Mesh schedule, Harness UI).

Target plane — services, pods, nodes, load balancers, data stores.

Safety plane — kill switch, suppression windows, blast-radius limits, error-budget gates.

Observability plane — normal metrics + trace-ID correlation to distinguish chaos-induced from natural failures.

Feedback loop — findings feed back into SLO adjustment, runbook updates, code fixes.

Idea 3 · Guardrails are mandatory

  • Burn-rate alert: pause experiment if daily error-budget burn exceeds 2x expected.
  • Suppression windows: silence non-experiment alerts in the blast radius during experiment.
  • Trace-ID correlation: all experiment-induced errors carry a tag so on-call can dedupe.

Idea 4 · Five LLM-specific experiments

  1. Memory overload — force a KV cache preemption storm by sending long-context requests with high concurrency. Observe: does the service gracefully shed or crash?

  2. Network failure — cut connectivity between inference gateway and provider. Observe: does fallback kick in within SLA? (Phase 17 · 19)

  3. Provider outage simulation — 100% 429 from OpenAI. Observe: does routing failover to Anthropic? (Phase 17 · 16, 19)

  4. Malformed prompt — inject tokenizer-stalling payload (e.g., deeply nested unicode, huge UTF-8 codepoint). Observe: does a single request lock up a worker?

  5. KV eviction storm — force eviction by saturating vLLM block budget. Observe: does LMCache recover or does service degrade?

Idea 5 · Cadence

  • Weekly — small canary experiments in staging, maybe 5% prod.
  • Monthly — scheduled game day on a specific scenario; cross-team attendance; postmortem.
  • Quarterly — cross-team resilience audit; dependency map update.

Idea 6 · Tooling

  • Harness Chaos Engineering — commercial; AI-derived experiment recommendations; blast-radius downscaling; MCP tool integration.
  • LitmusChaos — CNCF graduated; Kubernetes workflow-based.
  • Chaos Mesh — CNCF sandbox; Kubernetes-native CRD style.
  • Gremlin — commercial; broad support.
  • AWS FIS / Azure Chaos Studio — managed cloud offerings.

Idea 7 · Starting small

First experiment: pod-kill one decode replica under steady traffic. Observe rerouting and recovery. If this works and looks safe, graduate to network chaos.

First LLM-specific experiment: inject one provider 429 for 5 minutes. Observe fallback. Most teams discover their fallback wasn't fully tested.

Idea 8 · Numbers you should remember

  • Four planes: control, target, safety, observability.
  • Burn-rate pause: 2x expected daily budget burn.
  • Cadence: weekly canary, monthly game day, quarterly audit.
  • Five LLM experiments: memory, network, provider, malformed prompt, KV storm.

The same idea as a formula

Error budget and burn rate. An objective of 1−b availability allows a failure rate b (for 99.9%, b=0.1%). If an experiment produces failure rate e on the traffic it touches, the

burn rate=be​

says how many times faster than allowed the budget is being spent. A burn rate of 30 empties a 30-day budget in a day, if it applies to all traffic.

Worked example
How much budget does a 5-minute experiment spend?

Objective 99.9% (budget 0.1% of requests). Service: 1,000 requests a minute, so 1,440,000 a day and a daily budget of 1,440 failed requests.

  1. Provider-429 experiment: touches 30% of traffic for 5 minutes = 1,500 requests; 1.5% fail = 22 failures. Burn rate on that slice: 1.5 / 0.1 = 15× (on the whole service: 0.45 / 0.1 = 4.5×).
  2. Budget spent: 22 of 1,440, about 1.5% of the day's budget.
  3. Without a working fallback, 100% of that slice fails for 5 minutes: 1,500 failures, more than the whole day's budget. That is what the burn-rate guard is for: abort within a minute and the cost stays near 300.
Check your mental model

Which statements are right?

  • ✓ Chaos in production needs SLOs, observability, automated rollback, runbooks and on-call first.
  • ✗ A high burn rate always means the experiment must stop. Burn rate on a tiny slice can be high while the total budget spent is small; combine it with blast radius.
  • ✓ Tagging experiment traffic with a trace ID lets on-call tell chaos from real incidents.
  • ✗ Unit tests catch tokenizer stalls on malformed prompts. They show up only under real traffic shapes; that is what chaos experiments are for.

Use it: the same idea with real libraries

Here is code/main.py, in 2 parts. Each part runs on this page, in order, in one Python session; the last part does what python3 code/main.py does.

Part 1 of 2 · Experiment, run_experiment, main

"""Chaos engineering runner with safety plane gates — stdlib Python.

Runs three LLM-specific experiments and applies burn-rate + blast-radius safety gates.
"""

from __future__ import annotations

from dataclasses import dataclass


ERROR_BUDGET_PER_DAY = 0.001   # 99.9% SLO
EXPECTED_ERROR_RATE = 0.0005


@dataclass
class Experiment:
    name: str
    duration_min: int
    induced_error_rate: float
    blast_radius_pct: float


EXPERIMENTS = [
    Experiment("pod kill (1 decode replica)",     5, 0.002, 0.05),
    Experiment("provider 429 fallback",           5, 0.015, 0.30),
    Experiment("malformed prompt tokenizer stall",3, 0.040, 0.10),
]


def run_experiment(e: Experiment) -> dict:
    burn_rate = e.induced_error_rate / max(EXPECTED_ERROR_RATE, 0.0001)
    paused = burn_rate > 2.0 and e.blast_radius_pct > 0.2
    return {
        "experiment": e.name,
        "duration": e.duration_min,
        "error_rate": e.induced_error_rate,
        "burn_rate_x": burn_rate,
        "blast_radius": e.blast_radius_pct,
        "paused_by_safety_plane": paused,
        "status": "ABORTED (burn-rate guard)" if paused else "COMPLETED",
    }


def main() -> None:
    print("=" * 90)
    print("CHAOS EXPERIMENT RUNNER: safety plane gates burn-rate × blast-radius")
    print("=" * 90)
    print(f"SLO error budget: {ERROR_BUDGET_PER_DAY*100:.2f}%/day")
    print(f"Expected baseline error rate: {EXPECTED_ERROR_RATE*100:.3f}%")
    print(f"Burn-rate gate: > 2.0x expected AND blast radius > 20%\n")

    header = f"{'Experiment':38}  {'mins':>4}  {'err %':>6}  {'burn×':>6}  {'blast':>6}  Status"
    print(header)
    print("-" * len(header))
    for e in EXPERIMENTS:
        r = run_experiment(e)
        print(f"{r['experiment']:38}  {r['duration']:>4}  "
              f"{r['error_rate']*100:>5.2f}%  "
              f"{r['burn_rate_x']:>5.1f}x  "
              f"{r['blast_radius']*100:>5.0f}%  "
              f"{r['status']}")

    print("\nRead: small-blast-radius experiments run to completion even at high burn rate.")
    print("Large-blast-radius + high burn → abort. Suppression windows + trace-ID tags")
    print("required to dedupe alerts during experiments.")

Solutions

SolutionP1 · Reading the experiment runner

In code/main.py the provider-429 experiment aborts (30× burn on a 30% blast radius) while the malformed-prompt experiment completes despite an 80× burn, because its blast radius is only 10%. The gate requires both a high burn rate and a large blast radius, so small experiments may run hot briefly; large ones are stopped.

SolutionB1 · Three skipped guardrails

(1) Blast radius: start with a few per cent of traffic, not all of it. (2) A burn-rate abort: stop automatically within a minute when the budget burns faster than 2× expected. (3) Staging first and an off-peak window: test the fallback where failure is cheap before testing it in production. A fourth: the fallback itself should have been verified before the experiment.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designYou run a chaos experiment in production. One model provider returns rate-limit errors for part of the fleet, so that you can watch the fallback. Alerts start to fire while it runs. Design the safety plane that keeps this from turning into an incident, and explain how on-call tells an experiment failure from a natural one.

Level 4 of 4 · about 18 minutes to answer well.

Short answer. Three guards sit in the safety plane: a burn-rate alert that pauses the experiment when the daily error-budget burn passes twice the expected rate, suppression windows that silence the non-experiment alerts inside the blast radius, and a tag on the trace id of every error that the experiment causes. On-call reads the tag. An untagged error inside the window is natural and gets the normal response.

The planes.

The lesson splits the system into a control plane that schedules the experiment, a target plane of services, pods and data stores, a safety plane with the kill switch, suppression windows, blast-radius limits and error-budget gates, and an observability plane that correlates every error with a trace id. The findings feed back into the SLO, the runbooks and the code.

The three guards.

  1. Burn-rate pause. The experiment is allowed to spend error budget, because that is what a controlled failure does. The gate fires when the daily burn exceeds 2x the expected rate, and it pauses the experiment on its own.
  2. Suppression windows. Alerts that the experiment is designed to trigger are silenced for the blast radius and the duration. Nothing outside the radius is silenced.
  3. Trace-id correlation. Every experiment-induced error carries a tag, so that on-call can separate it from natural failures without a conversation.

The kill switch is a fourth, manual control. It stops the experiment at once and belongs to on-call, not to the scheduler.

How on-call reads an alert during the window.

  • A tagged error inside the blast radius is the experiment working. It is logged, not paged.
  • An untagged error inside the window is natural. It takes the normal response.
  • An error outside the blast radius is natural, because the experiment did not touch it.
  • If the burn continues after the pause, the cause is natural, or the experiment broke something that does not recover alone. Run the incident response and roll back the last change.

What this experiment should teach.

The lesson notes that most teams discover their fallback was never fully tested. Record the time from the first rate-limit error to the first successful fallback, and compare it with the SLA. Record whether the gateway's retries amplified the load before the fallback engaged.

Size the blast radius.

Choose a share of the fleet small enough that the fallback capacity on the other providers covers it, and write that share into the experiment definition. A larger share tests more and risks a real outage when the fallback is slower than you believed.

Plausible wrong answers.

  • "Silence all alerts during the experiment." A natural incident in the same window goes unseen. Silence only the blast radius, and keep tagged errors visible.
  • "Run it in staging, so no safety plane is needed." Staging cannot show the fallback under real traffic. The safety plane is what makes production acceptable.
  • "The burn-rate alert is the kill switch." The alert pauses the experiment. The kill switch stops it at once, and it should be a separate manual control.

Follow-ups an interviewer may ask.

  • (level 3) Why gate at twice the expected burn and not at any burn? Expected: an experiment is meant to spend some budget. The gate catches the case where it spends far more than planned.
  • (level 4) The burn keeps rising after the pause. What does that tell you? Expected: the cause is natural, or the experiment broke something that does not recover on its own. Run the incident response and roll back the last change.
  • (level 4) How do you pick the blast radius for a provider outage experiment? Expected: a share small enough that the fallback capacity covers it, written into the experiment definition and reviewed with on-call.

Explain the mechanismA new team wants to run its first chaos experiment against the model service next week. What do you check for before you agree, and what goes wrong when one piece is missing?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. Five things have to be in place: service level indicators with objectives, observability with traces, metrics and logs, an automated rollback, structured runbooks and an on-call owner. Each one lets you measure the experiment, stop it or repair the damage. When one is missing, the experiment is not a test. It is an incident that you scheduled.

The five prerequisites.

  1. SLI and SLO. Without a target you cannot say whether the experiment hurt anything.
  2. Observability. Traces, metrics and logs on a dashboard. You must see the effect while it happens.
  3. Automated rollback. The policy-flag rollback from the progressive delivery lesson. A rollback that needs a redeploy is too slow for an experiment.
  4. Runbooks. Structured sections: symptom, hypothesis, verify, act. The on-call reads them under pressure.
  5. On-call. Someone who responds when the experiment finds something.

The first experiments.

Start with one pod kill of a decode replica under steady traffic, and watch the rerouting and the recovery. If that looks safe, graduate to network chaos. The first model-specific experiment is one provider returning rate-limit errors for a few minutes, to see the fallback engage. Most teams learn here that their fallback was never fully tested.

The cadence.

Weekly small experiments in staging or on a small share of production. Monthly game day on one scenario with a postmortem. Quarterly cross-team audit with a dependency map.

Plausible wrong answers.

  • "Skip the prerequisites and learn by doing." Without an SLO, a rollback and an on-call owner, the experiment is an outage that you caused on purpose.
  • "A dashboard is observability." Chaos needs traces, metrics and logs with trace-id correlation, so that you can tell experiment failures from natural ones.
  • "Run the biggest experiment first to find the biggest risk." Start with one replica kill, then grow the blast radius.

Follow-ups an interviewer may ask.

  • (level 1) Which experiment goes first, and why? Expected: kill one decode replica under steady traffic, because it tests rerouting and recovery with a small blast radius.
  • (level 2) Name one failure a generic network chaos tool cannot reproduce for a model service. Expected: a KV cache eviction storm under burst load, or a prompt that stalls the tokenizer.
  • (level 2) Why does the rollback matter more than the dashboard during an experiment? Expected: the dashboard shows the harm, and the rollback stops it. Without the rollback the harm continues until someone fixes it by hand.
  • (level 3) The team wants staging only. When is production the right place? Expected: when staging cannot reproduce the traffic shape, the cache state or the provider behavior, and only with the safety guards in place.
