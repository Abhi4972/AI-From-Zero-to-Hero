In plain words first
The idea in one line

A finding about a compiled program is a record with a hash, a confidence, an authority, and a list of what it cannot show.

The problem

In plain words first

In reverse engineering, and especially when an AI agent does it, every statement should say how it is known. "Observed" means a tool read it directly from the file or a run produced it. "Derived" means it was computed from observed facts. "Inferred" means someone, person or model, believes it. Each statement becomes a small record that names the exact file (by its hash, not its path), the tool and its version, the settings, the result and its limits. A record's id is a hash of its content, so any edit makes a new record instead of silently changing the old one. A belief becomes accepted only when observed runs confirm it, and open questions are tracked as records too. This lesson creates fresh records with Capstone and with runs of the shipped object, settles two competing predictions, and then tries to forge a result.

You ask an agent what grade in ledger-x86_64-O1.o returns for a score of 55. The agent calls rea, reads the Ghidra pseudocode, and answers 0. A reviewer asks how the agent knows. The agent has a block of text that Ghidra printed. For the default path, that text reads uVar1 = -(param_1 >> 0x1f) ^ (uint)((ulong)((long)param_1 * 0x66666667) >> 0x3f);. The bytes at that point say xor eax, eax.

The expression and the instruction both produce 0 for every input. The agent did not know that. It trusted the text because a tool produced it. A 2026 study ran three agents on 24 reverse engineering tasks (NDSS BAR 2026). It named four recurring weaknesses: training bias, over-trust in observations, context limits, and plan persistence. Another 2026 study planted text inside binaries and found that models proposed the planted unsafe action in 35 of 40 cases (arXiv 2607.12507).

rea 6.5.0 gives the agent a vocabulary for this. Every successful tool call produces one Evidence record with a confidence of observed, derived, or inferred, an authority, and a list of limitations. The packaged skill tells the agent: "Every conclusion must distinguish observations, inferences, and unknowns. Cite Evidence IDs, preserve limitations and incomplete coverage, and never imply that static analysis observed execution.".

Three things rea leaves to you. Its snapshots cache exact query results, not analysis. Its verification passes a claim when a comparison dimension is unchanged, and its own comment says that a pass "does not establish global implementation equivalence.". Its obligation ledger takes candidates only from JavaScript and managed graphs, so a native function never reaches verified through it.

This lesson builds the missing piece in plain Python. You write a ledger that stores every fact about the fixture as a record with a content hash. You make predictions about percent_change and grade, mark them inferred, and check them against runs of a test program you compile yourself. You import two real rea records and the snapshot they came from, and your ledger recomputes every hash rea wrote.

Three Words for Confidence, Five for Authority

confidence is an enum with three values, never a number. authority has five values. When a producer says nothing, rea uses shipped-artifact with observed.

Value Meaning on the fixture Records in this lesson
observed A fact read from bytes or from a run the ELF reader's section and symbol reads, the two Ghidra records, 17 host runs
derived A fact computed from observed records the switch table model, the division model, every unknown mutation
inferred An expectation that no observation states yet 18 predictions
shipped-artifact The file on disk was the source every read of ledger-x86_64-O1.o
controlled-replay A run you controlled produced the fact the host runs of harness.c
analyst-inference Your own judgement predictions and unknown mutations
historical-reference An older source tree or document none here
external-service A service outside the file and the host none here

Two confusions cost the most time. The first treats pseudocode as an observation of behaviour. It is an observation of what Ghidra printed. The second treats an empty list as proof of absence. rea's design note is strict: "Missing coverage is unknown, not absence.". The ledger in code/main.py encodes both rules.

The Record

A record has exactly sixteen fields, and rea 6.5.0 rejects any other field. code/main.py keeps the same names as rea, so a record from either side validates on the other. The sixteenth field, relationship_coverage, says how complete a list of callers or callees is. Its value is complete, partial, or unknown, or null when the operation reports no call relationships.

Field What it holds
evidence_id ev_ and 64 hex digits, a hash of the content
subject name, digest.sha256, format, architecture, local_path, or null
provider id, name, version or null
analysis_profile the provider's settings and their digest, or null, always present
predicate_type a tag, rea.analysis by default
operation, parameters the tool and its input
raw_result, normalized_result provider output and the canonical result
confidence, authority the enums above
environment id, platform, architecture, isolation, or null
limitations plain sentences
relationship_coverage status complete, partial, or unknown with diagnostics, or null
locations address, address-range, artifact-path, file-offset, file-offset-range
evidence_links the ev_ ids this record rests on

The real parameters object of the profile has 25 keys. The real limitations list has ten sentences. Keep them. A limitation is part of the content, so dropping one changes the id, and your ledger would then reject the record.

The Id Is a Hash of Content, and the Path Is Not in It

rea computes evidence_id as ev_ plus SHA-256 over the RFC 8785 canonical JSON of a projection of the record. The projection keeps the subject's digest, format, and architecture and drops name and local_path. It drops relationship_coverage when its value is null, so a record without call relationships keeps the same id as before the field existed. Everything else, including raw_result and every limitation, is hashed.

RFC 8785 sorts object keys, removes whitespace, and fixes the number and string forms. For records whose numbers are integers, Python's standard library produces the same bytes:

def canonical_json(value):
    return json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False, allow_nan=False)

code/main.py refuses floats before it hashes, because RFC 8785 and Python print some floats differently. The two rea records and the snapshot hold no floats, so the recipe reproduces every rea hash:

rea value Recomputed by code/main.py
ev_67b6d3f992eaf49a… for grade equal
ev_e88b10dc0c6400e5… for percent_change equal
profile digest 9c7f6b24be69294e… over {provider, parameters} equal
query_26122aebe9d8abae… for the grade snapshot entry equal
query_0f95ef38038d3666… for the percent_change entry equal

Why exclude the path? The same observation of the same bytes gets the same id on any machine and in any folder. The local_path in the listing above names a folder on one Mac. The id does not change when you copy the fixture to /home/you/re. rebind_subject_path() lets you show a record under a new path. It refuses when sha256, format, or architecture differ. rea 6.5.0 does the same with rebindEvidenceToTargetPath when it replays a snapshot record for a target at a new path.

validate_evidence() recomputes the id and rejects a mismatch with rea's sentence, "Evidence semantic identifier does not match its record". It also rejects a record whose analysis_profile.provider differs from its provider. The test test_tampered_id_and_mismatched_profile_are_rejected edits one line of pseudocode inside the real grade record and watches the ledger refuse it.

Derive the Table, and Say That You Derived It

The 46 bytes of grade contain four patterns that lesson 33 decoded:

Bytes Instruction Offset in grade
48 69 c0 67 66 66 66 imul rax, rax, 0x66666667 3
48 c1 f9 22 sar rcx, 34 13
83 c1 fa add ecx, -6 23
83 f9 04 77 0c cmp ecx, 4 then ja 28

A multiply by 0x66666667 followed by a shift of 34 is a signed division by 10. The file holds no 10. derive_grade_model() writes that fact as a limitation: "The divisor 10 is a derivation from the multiplier 0x66666667 and the shift 34. The file holds no 10."

The add ecx, -6 sets the first case to 6. The cmp ecx, 4 with an unsigned jump admits five cases, 6 to 10.

The lea at .text+0x33 carries the relocation with addend 0x10. A PC32 relocation measures from the end of the 4-byte displacement, so the table starts at .rodata+0x14. Five little-endian words there read 1, 2, 3, 4, 4. The switch in ledger.c returns 1 for 60 to 69, 2 for the seventies, 3 for the eighties, and 4 for 90 to 100. The compiler turned the switch into a lookup table of return values.

The resulting record ev_605106bff2d9998f… has confidence derived, and its evidence_links name the two observed records it rests on. Remove the bytes record from the ledger and the derived record has a dangling link. The figure above shows that state when you turn off ev_a467c242….

Now compare with Ghidra. Its pseudocode for the same bytes:

uint grade(int param_1)
{
  uint uVar1;
  uint uVar2;

  uVar2 = param_1 / 10 - 6;
  uVar1 = -(param_1 >> 0x1f) ^ (uint)((ulong)((long)param_1 * 0x66666667) >> 0x3f);
  if (uVar2 < 5) {
    uVar1 = *(uint *)(&DAT_001000b4 + (ulong)uVar2 * 4);
  }
  return uVar1;
}

Ghidra applied the relocation and named the table DAT_001000b4, which is .rodata+0x14 after it placed .text at 0x100000. It recovered the division by 10 and the five cases. For the default value it printed an expression that is always 0 and never says 0. The p-code in native_value_flow marks those operations is_dead: true. The record is a faithful observation of Ghidra. The meaning you read from it is derived, and the value you expect from a run is inferred.

The percent_change record shows the other failure. Ghidra's signature reads undefined1 [16] percent_change(int param_1,int param_2,ulong param_3). The source says int percent_change(int before, int after). idiv writes EDX:EAX, and the zero path leaves EDX untouched, so the decompiler inferred a 16-byte return and a third parameter. Its own native_api.return_type.confidence for grade is "low". Treat a recovered signature as the provider's inference, and record it that way.

predict() uses C semantics, not Python semantics. c_div() truncates toward zero, and wrap32() folds every intermediate into 32 bits. Python's // rounds toward negative infinity, so (3 - -7) * 100 // -7 gives -143 and the C program gives -142. Lesson 13.36 makes this grid much larger.

Each prediction opens one residual unknown. The unknown asks for observed evidence with authority controlled-replay and recommends one probe: execute_function on the host build. The next section produces that evidence. The question for the first grade claim reads "Does grade(95) == 4 hold when the compiled function runs?"

Check Them Against a Run

code/fixtures/harness.c includes ledger.c and prints one result per invocation. observe_runs() compiles it with the first of clang, cc, or gcc on your PATH and runs every input in the grid once. Each run becomes one record:

{
  "operation": "execute_function",
  "parameters": { "function": "grade", "args": [95] },
  "normalized_result": { "result": 4, "stdout": "4\n", "exit_code": 0 },
  "confidence": "observed",
  "authority": "controlled-replay",
  "environment": { "id": "host-process", "platform": "darwin", "architecture": "arm64", "isolation": "process" },
  "limitations": [
    "The run executed a host build of ledger.c, not the x86-64 object. The claim about the object rests on the shared source and on the compiler.",
    "One run observes one input. It proves nothing about other inputs."
  ]
}

The subject of a run record is the harness binary, a Mach-O arm64 file on this Mac, with its own SHA-256. The provider is course-harness with the compiler's version line, here Apple clang version 17.0.0 (clang-1700.6.3.2). The evidence_links name the source record ev_2f1e6d251543d017…, because the run and the object share ledger.c and nothing else.

Read the first limitation twice. The x86-64 object never ran on this machine. What ran was a second build of the same source for another architecture. That is still an observation, and it is the strongest one available without an emulator, so the claim passes with that sentence attached. A report that omits it has lost information the reader needs.

The 17 single-input runs all agreed with the predictions. code/fixtures/run-evidence.json holds those 17 records and the source record, exported with --record on 2026-10-13. When no compiler is present, build_ledger() imports that bundle instead of running, and the report says so in its runs field.

Promotion Rules

A claim moves from inferred to supported only through observed runs. check_claim() looks for execute_function records with the same function and arguments, compares each result with the prediction, and counts the covered inputs:

Status Condition rea's completion ledger
pass every input has an agreeing run and none disagrees pass
fail any run disagrees fail
unknown some inputs have runs, others have none unknown
unsupported no input has a run unsupported

promote_claim() is the strict form. It raises ClaimError when any id is inferred or derived. It raises when an id names a run of another function or of other arguments. It raises when the list is empty, and when the runs cover fewer inputs than the claim. The Ghidra pseudocode record and the table model both exist for grade(55), and neither can promote it. Turn off ev_7be90c0c… in the figure and watch the claim fall to unsupported while two records about grade remain.

The range claim shows the partial case. Only two of its eleven inputs, 95 and 100, appear in the run grid. check_claim() returns unknown with covered 2 of 11, and promote_claim() refuses with "2 of 11 inputs have observed runs". The ledger does not round that up.

completion_ledger() mirrors rea's EvidenceCompletionLedger. Its id is ecl_ plus the hash of its records, and complete is true only when pass equals total. The demo prints ecl_da64933ea13befed… with complete: false, because of that one range claim.

Unknowns Are Records with a Hash Chain

rea stores a residual unknown as a strict record. code/main.py keeps the same fields and the same invariants.

The id is unk_ plus SHA-256 over {domain, question, scope_digest}, with the question's whitespace collapsed to single spaces. Two analysts who ask the same question about the same file get the same id. The scope_digest is the SHA-256 of the object.

Every change is a new revision. Revision 1 has previous_revision_digest null. Every later revision names the revision_digest of the one before it, and the digest covers every field except itself. verify_unknown_chain() walks the list and recomputes each digest. It checks that each link points at the previous revision. It checks that the mutation evidence each revision names is in the ledger.

Each mutation is itself an evidence record, as rea does with provider rea-unknown-registry. Ours carries confidence derived, authority analyst-inference, and no subject. Its limitation reads "A registry mutation records what the analyst decided. It is not proof of the answer."

That is why the demo's 81 records include 36 derived mutation records: 18 openings and 18 updates.

Three invariants are enforced on every revision:

  • Only a resolved unknown carries a resolution, and only revision 1 has no predecessor.
  • A contradicted unknown names at least one contradicting id, and no id appears in both lists.
  • A verified resolution names at least one evidence id with the required confidence and authority.

The third rule is where the ledger refuses most often. rea's workflow notes say "Only qualifying observed evidence can verify a resolution.". resolve_unknown() therefore rejects the table model, rejects an observed record with authority shipped-artifact, and accepts the run record ev_f4ffbe8f922ec7fe…. The resolved revision for grade(95) is revision 2, and its previous_revision_digest is ffca840b55a8a188…, the digest of revision 1.

update_unknown() takes expected_revision and raises revision-conflict when it is stale, as rea's update_unknown tool does. The right reaction is the one rea's notes give: reread the current revision and decide again.

One unknown stays open after the demo: unk_f2eb0d7f84c80a19…, "Does grade(score) == 4 for every score from 90 to 100 hold when the compiled function runs?". Its status is investigating, its supporting ids include the two runs, and its probe still names the nine inputs without a run.

A Cache of Answers Is Not a Database of Analysis

rea has three things that look like a cache. The Ghidra target snapshot is a private copy of the input, imported with -readOnly -deleteProject and deleted on close. The in-memory AnalysisSnapshotCache holds up to 10,000 entries for one binary identity. The snapshot file holds target, binding, entries, workflow_entries, and an evidence_bundle.

The cache key is query_ plus SHA-256 over {target, binding, operation, parameters}. target is {sha256, kind, format, architecture}, and a raw-binary target also has entry_point. binding is the provider and the whole analysis profile, digest included. Change any of the 25 profile parameters, for example jump_table_evidence from typed-case-default-blocks-v1 to a v2, and the digest changes, so every key changes.

code/fixtures/rea-snapshot.json is the file rea wrote during the two runs, 142,690 bytes. rea wrote it with owner-only permissions, and the committed copy is readable by everyone. It has two entries and an evidence bundle with the same two records. AnswerCache.import_snapshot() recomputes each query_id and refuses the file when any differs. It refuses a snapshot whose target or binding differs from the active one, with rea's wording profile_mismatch. It refuses a snapshot whose format_version is not course-answer-cache-1.

Three measurements from this machine. The first grade query took 8.6 s, with a fresh Ghidra import. The percent_change query against the same snapshot took 8.5 s, because a different query is a cache miss. A third grade query took 2.1 s and returned the identical record with the identical evidence_id. The in-memory replay in rea adds the limitation "Loaded from a local REA analysis snapshot; this call did not re-run the provider.". Our lookup() adds a sentence of the same kind, so a reader can tell a replay from a fresh answer.

A mutation ends the cache. In rea 6.5.0, a rename or a comment clears the snapshot cache before rea sends the call to the provider. A failed reply cannot prove that the write rolled back, so a failed write also stops replay. A metadata import that changes the database does the same.

Why an Agent Needs This

An agent that drives rea through MCP sees the full record on every call and can cite evidence_id in its report. The research from 2026 says where that goes wrong. Over-trust in tool output was one of the four weaknesses in the NDSS BAR study. In the planted-text study, showing binary content as data alone still left 15 unsafe proposals of 40, and provenance checks with tool authorization removed them. A third study watched an agent drive Ghidra through MCP (arXiv 2606.06838). In binaries with hundreds of functions, only 10 to 15 percent received real analysis before the agent produced stubs.

The ledger answers each of these with a record, and the agent reports only what the ledger holds. A claim without an observed run is unsupported. A claim with some runs is unknown. A provider text is observed about the provider and nothing more. Give the agent the skill file in outputs/ and make the ledger the only place it writes conclusions. That holds for Claude, Cursor, Codex, OpenClaw, Hermes, or any agent that reads SKILL.md.

The same idea as a formula

Content-addressed ids. With π(r) the record's semantic projection (every field except the id and the local path) and JCS canonical JSON,

id(r)=ev_∥SHA256(JCS(π(r))).
Changing any meaningful byte gives a different id; moving the file to another path does not.

Promotion. An inferred claim c with cases {(xi​,yi​)} is promoted to pass only if

∀i ∃r∈runs:r.confidence=observed∧r.args=xi​∧r.result=yi​,and no run contradicts it.
A listing, a model or a derived table can support a claim; only a run can promote it.

Chained unknowns. Revision k of an unknown stores dk​=SHA256(bodyk​∥dk−1​), so an edit to an early revision breaks every later digest.

Worked example
Settling `grade(110)`
  • Observed: Capstone decodes the 14 instructions of grade from the shipped object. The record names the object's SHA-256, Capstone 5.0.9, and the limitation that relocated operands read as zero.
  • Inferred A: "grade(110) == 4", reading case 10: in the source. Inferred B: "grade(110) == 0", because 110/10−6=5 is past the 5-entry value table (indexes 0 to 4).
  • Promoting B with only the listing is refused: the listing does not record a run.
  • Observed runs of the shipped bytes: grade(95) = 4, grade(110) = 0. Checking: A fails (contradicted by one run), B passes (covered 1 of 1).
  • Both predictions stay in the ledger. The failed one is evidence too: it records a misreading future analysts can avoid.
Check your mental model
  • ✗ "A decompiler's output is observed evidence."
    ✓ The output text is observed; what it says the program does is derived or inferred until a run confirms it.
  • ✗ "The file path identifies the artifact."
    ✓ The SHA-256 does; the same bytes at another path are the same subject.
  • ✗ "If an id still matches after an edit, nothing changed."
    ✓ Recomputing the id after an edit creates a different record; the original id still points at the original content.
  • ✗ "A cache of past answers can stand in for analysis."
    ✓ Only if the provider and profile match exactly; otherwise it must be refused.

Fresh evidence from real tools

Builds a ledger with the lesson's create_evidence, record_prediction, check_claim and promote_claim: Capstone (AT&T) disassembles grade from the shipped clang object; two analyst predictions are recorded; the shipped object is linked unchanged into a shared library and grade is called through ctypes in a separate process. About a second.

# Fresh evidence from real tools, kept with the lesson's record format (code/main.py): Capstone reads the
# shipped object, an analyst makes two predictions, and the shipped bytes themselves are run to settle them.
import platform, subprocess, sys, tempfile, pathlib, capstone
from capstone import Cs, CS_ARCH_X86, CS_MODE_64, CS_OPT_SYNTAX_ATT
from main import (EvidenceLedger, Claim, create_evidence, subject_for_file, record_prediction, check_claim,
                  promote_claim, ClaimError, rebind_subject_path, compute_evidence_id, read_elf_sections,
                  read_elf_symbols, OBJECT_PATH, ONE_INPUT_LIMITATION)
ledger = EvidenceLedger(); subject = subject_for_file(OBJECT_PATH, "elf", "x86_64")
data = OBJECT_PATH.read_bytes(); sections = read_elf_sections(data)
grade_sym = next(s for s in read_elf_symbols(data, sections) if s["name"] == "grade")
text = sections[".text"]["offset"]; code = data[text + grade_sym["value"]: text + grade_sym["value"] + grade_sym["size"]]
cs = Cs(CS_ARCH_X86, CS_MODE_64); cs.syntax = CS_OPT_SYNTAX_ATT
listing = [f"{i.address:#x} {i.mnemonic} {i.op_str}" for i in cs.disasm(code, grade_sym["value"])]
disasm = create_evidence(subject, {"id": "capstone", "name": "Capstone", "version": capstone.__version__},
                         operation="disassemble_function", parameters={"function": "grade"}, normalized_result={"listing": listing},
                         limitations=["Linear decode of the symbol's byte range; relocated operands still read as zero."])

Use it: the same idea with real libraries

Keep one ledger per target and per investigation. Put the target's SHA-256 in every subject and the question's scope digest in every unknown. When you change tools, change the provider and let the ids diverge. When you rebuild the fixture, the subject digest changes and every old record becomes evidence about another file.

Write limitations at the moment you know them. The reader that applies no relocation says so. The run of a host build says so. The model that infers a divisor says so. A record written without its limitations looks stronger than the facts allow, and a later reader cannot repair that.

Treat every provider text as data. Strings and pseudocode from the target are text that the target controls. They never become instructions, and they never become observations of behaviour. rea 6.5.0 marks such results with _meta.provenance.untrusted_content: true. Its server instructions tell the model to treat target content as data and to report any request in it to run, install, download, or send something as a prompt-injection attempt. The marker helps, but your ledger must still keep target text out of the instructions.

Solutions

SolutionP1 · One fails, one passes, the listing promotes nothing

The prediction "grade(110) == 4" fails: an observed run of the same input contradicts it. The prediction "grade(110) == 0" passes: the run covers its only case and nothing contradicts it. The listing alone promotes neither: promote_claim accepts only observed execute_function records, and a disassembly listing, however accurate, records how the code looks, not what it returns.

SolutionB1 · A note without evidence

Almost everything that would make it reusable:

  • No subject identity: it does not say which file (by hash) it describes, so it is silently applied to the rebuilt binary, where layout, idioms and even behaviour can differ.
  • No provider or method: which tool, version and settings produced "switch on score/10"? Without that, nobody can re-check it.
  • "Verified" without evidence: verified by what? It says "A for 90+", but the runs show grade(110) = 0; the claim was never tested on the inputs where it is wrong.
  • No confidence label or limitations: a reading of the source, a decompiler's text and an observed run look the same in prose.

As records, the old findings would be tied to the old binary's hash; a new hash means they are history, not current evidence, and the agent must re-observe and re-run before claiming anything about the new build.

Industry practice
What's current (2024–2026)
  • Provenance formats: in-toto attestations and SLSA provenance (supply chain), Sigstore for signing, and W3C PROV ideas carry the same fields: subject digest, producer, parameters, time and links.
  • RE tools with evidence models: Ghidra and IDA keep analysis databases; MCP servers that wrap them for agents (for example GhidraMCP, IDA Pro MCP and the course's rea) increasingly return structured results with provenance so an agent can cite them.
  • Agents and confidence: studies of LLM-assisted reverse engineering in 2024-2026 report confident but wrong claims as the main failure, which is exactly what observed/derived/inferred labels and run-based promotion guard against.
  • On your laptop: the ledger is plain JSON and hashing; it runs instantly. Runs of real code belong in a sandbox (Lesson 13.26) when the code is not your own.

Sources: in-toto, SLSA provenance, RFC 8785 (JSON canonicalization), Capstone.

Recap
What to keep from this lesson
  • Label every statement: observed, derived or inferred, plus its authority.
  • Records name the subject by hash, the provider and profile, the result and the limitations.

Operational Rule

Record what you read, what you computed, and what you expect as three kinds of record with three words. Close an unknown with an id, never with a sentence. Replay an answer only under the exact key it was stored with, and refuse it when one version string differs.

Take-homeTake-home. Build the harness an agent uses to answer one question about a program you compiled yourself, through the analysis tool's MCP server: what does the program print for a score of 95, and where does the letter come from? Level 4 of 4 · about 60 minutes to answer well.

Short answer. Begin with the authorization note: the target is your own build, and the note still answers the five questions in writing, a lawful copy, a named purpose, facts not already available, work confined to the needed parts, and your own expression in anything you release. Plan the calls in order, open_binary, list_procedures, list_strings, analyze_function on the two functions, then read_bytes on both tables the dossiers name, and export_evidence_bundle before close_binary, with a client deadline set from a measured cold start because the first engine-backed call pays for the import. Keep a ledger with one row per claim, each row a kind among observed, derived, inferred and unknown, an evidence id and a boundary, and let the row "95 prints A" stay inferred until the two table reads turn it observed. Treat every string, name and line of pseudocode from the file as data with an address, never as an instruction.

Authorization.

Every target is a program you wrote and compiled, and the note says so with hashes. For any other program the note answers the five questions before the first command and names the purpose the law names. The tool does not check authorization; the note is yours.

Call plan and deadlines.

open_binary returns the format, kind, SHA-256 and architecture without importing anything. The first engine-backed call starts the headless import and takes seconds; later calls on the same target take milliseconds. The server allows 330,000 ms for that start, and the pinned client SDK waits 60,000 ms by default, so the client deadline is the one to set from your own first run. Ask every question before close_binary, because the project is deleted and the retained records go with it; export the bundle first so every id in the ledger stays checkable.

Text from the file is data.

Every string, symbol name, comment and line of pseudocode copied out of the target is target text. Each result that can carry such text arrives with a provenance marker that names the analysis target as untrusted; the marker tells the agent which text came from the file, and the agent still applies the rule. A 2026 study planted text inside binaries and found that models proposed the planted unsafe action in 35 of 40 cases without controls; showing the content as data alone still left 15 of 40, and provenance checks with tool authorization removed them.

Tests to ship.

  1. A stand-in server replays the recorded records for the same tool and arguments, so the loop runs with no engine installed.
  2. Every record's id recomputes from its content, and a record with one limitation removed is refused.
  3. Promotion refuses a derived or inferred id and passes only with an agreeing run under controlled-replay.
  4. The ledger marks a claim unknown when some inputs have runs and others do not, and never rounds it up.
  5. A fixture binary carries a string that reads like a command; the test asserts that the ledger holds it as a value with an address and that nothing executes.
  6. A client deadline shorter than the measured cold start produces a recorded timeout step, not a finding.

Plausible wrong answers.

  • "The pseudocode returns an entry of _labels, so the letter is observed." The access is observed; the value behind it was never read.
  • "Skip the authorization note for a file I compiled." Write it anyway; the questions answer themselves for your own build, and the habit is the control for every other file.
  • "Treat the usage text as the program's instructions to the agent." It is target text; quote it with its address and never follow it.

Explain the mechanismIn the record, the dossier for the function _grade lists callers: [] and callees: [], and its relationship_coverage.status reads complete. The agent writes "nothing calls grade". What does the record support, and what would make the agent's sentence true?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. complete means the engine returned every resolved call reference without a known read limit; the diagnostic beside it says that unresolved computed or indirect calls remain unknown. The one incoming reference is a DATA reference from the function starts table, not a call instruction, so the record supports "no resolved call instruction targets this function in this build". The design rule is that missing coverage is unknown, not absence, and the agent's sentence needs either a run or an argument that covers indirect calls, so the honest move is to record a residual unknown with the probe that would close it.

Three values and a null.

relationship_coverage states how complete the caller and callee sets are: complete, partial with its limitations and the limited direction, or unknown with a reason, and null for an operation that reports no call relationships. Provider caveats stay in limitations and do not make the coverage partial. One part of a dossier does declare its coverage in numbers: the value flow reports whether it was truncated and how many operations, inputs and edges it omitted. A zero there is a count the tool stands behind; an empty array elsewhere is a count with no such statement.

The same lesson in two other empty lists.

A bundle comparison across two builds lists ten records that are in one bundle only and classifies every one as unknown with the kind unresolved_branch, because a bundle has no marker that says it is complete. A summary view of a six-file application reports semantic_unknowns: 118 and marks its coverage unknown. Each one proves that nothing was observed, never that nothing exists.

The record for what is still open.

A residual unknown is a durable record with an unk_ id, a revision chain, a status and the evidence that would close it. The id is a hash of the domain, the question with whitespace collapsed, and the scope digest of the target, so two analysts who ask the same question about the same file get the same id, and a second record_unknown answers already-exists. Every change is a new revision that names the digest of the one before, each mutation is itself an evidence record with authority analyst-inference, and only an observed record of the required authority can mark a resolution verified. The unknown for this dossier asks whether anything calls _grade at run time, and its probe is a run or a read of the computed targets.

Plausible wrong answers.

  • "complete means every call that can happen." It means every resolved reference was returned; indirect and computed calls stay unknown.
  • "An empty list means none." It means none observed; the design rule says missing coverage is unknown.
  • "Close the unknown with a sentence in the report." A resolution needs evidence ids of the required confidence and authority, never prose.

Follow-ups an interviewer may ask.

  • (level 1) The dossier does list a single incoming reference. What is it? Expected: a DATA reference from the function starts entry, which the unwinder and crash reporter use, not a branch instruction.
  • (level 2) Why does a zero in the value-flow counts carry more weight than an empty callers array? Expected: the count is a declared statement about truncation that the tool stands behind, while the array has no completeness statement beyond resolved references.
  • (level 2) How do you write the open question down so it survives the session? Expected: record_unknown with the question, the required authority and confidence, and a recommended probe; the id derives from the question.
  • (level 3) Two analysts update the same unknown. What stops the second from overwriting the first? Expected: update_unknown takes expected_revision and answers revision-conflict when it is stale, so the second rereads the head and decides again.

Where it is taught. The coverage section defines the field and the unknown record, the agent investigation section shows the DATA reference trap, and the evidence lesson builds the revision chain.

Explain the mechanismTwo machines analyze the same object in different folders and get the same ev_ id. A colleague copies one record, deletes one limitation sentence to shorten it, and the file no longer imports. Later an untouched bundle written by an older release fails the same way. Explain all three outcomes from the id rule.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The id is a content hash: ev_ plus a SHA-256 over the RFC 8785 canonical JSON of a projection of the record, where the projection keeps the subject's digest, format and architecture, drops name and local_path, and hashes everything else, raw_result and every limitation included. So a moved file keeps its id, a dropped limitation changes the content and the validator refuses it with "Evidence semantic identifier does not match its record", and the older bundle fails because the id rule itself moved: the older release left a null relationship_coverage out of the hash and the current one hashes it, so the first record with null coverage fails evidence_integrity_mismatch. Saved evidence is not migrated; regenerate it with the release you run.

The recipe.

Canonical JSON sorts object keys, removes whitespace and fixes number and string forms. For records whose numbers are integers, a standard-library json.dumps with sorted keys and compact separators produces the same bytes, which is why a few lines of Python or Node recompute every captured id. Floats are refused before hashing, because the canonical form and the language runtime can print them differently. The analysis profile digest is a separate SHA-256 over {provider, parameters}, and a profile whose provider differs from the record's provider is rejected.

What is inside and what is outside.

A path in subject is outside the hash. A path anywhere else is inside it: two captured files failed to match because the capture kit masked a directory inside normalized_result and locations, so a record that carries a path there gets a different id on every machine. Keep paths out of results and locations in your own records. A limitation is content on purpose: dropping one makes the record look stronger than the facts allow, and a later reader cannot repair that, so the id breaks.

Rebinding without rehashing.

A record can be shown under a new path with a rebind that refuses when the digest, format or architecture differ. Snapshot replay does the same when it writes the open target's path into a stored record: the evidence_id does not change, because the path was never in it.

The error envelope.

Every error has the same five fields: code, category, message, retryable, remediation.action, and optional details. The refused bundle names the failing record by index and says which field failed. invalid_request is retryable with corrected arguments; evidence_integrity_mismatch is not.

Plausible wrong answers.

  • "Ids are random identifiers assigned at write time." They are content hashes, which is why two machines agree.
  • "Trim limitations to save context tokens." Each one is hashed. A trimmed record with the old evidence_id is refused, and the reader loses what the fact does not cover.
  • "Fix the id field so the bundle imports." The validator recomputes the hash from content, and a patched id is still a mismatch.

Follow-ups an interviewer may ask.

  • (level 2) Why leave the path out of the hash at all? Expected: the same observation of the same bytes should carry one id on any machine and in any folder; identity belongs to the content, not to where the file sits.
  • (level 3) A producer writes an absolute path into locations. What happens when a colleague imports the bundle? Expected: the unchanged bundle still imports, because the stored path hashes to the stored id; but the same observation made on the colleague's machine carries their path and gets a different id, and any edit that masks the path breaks the id. Locations hold addresses and relative artifact paths, not host paths.
  • (level 3) Why does a limitation count as content and not as a comment? Expected: without it the record claims more than the provider did, and nobody downstream can tell.
  • (level 4) How do you handle the older bundle? Expected: regenerate it with the current release, since the rule changed and ids are not migrated; never patch an id by hand.

Where it is taught. The evidence record section gives the projection and a script that recomputes ids, the errors reference shows the refused bundle, and the evidence lesson recomputes every recorded hash in Python.

Explain the mechanismAn agent asks a decompiler for grade, reads the default branch of the pseudocode, and reports "grade(55) returns 0, observed". The pseudocode line is uVar1 = -(param_1 >> 0x1f) ^ (uint)((ulong)((long)param_1 * 0x66666667) >> 0x3f); and the bytes at that point are xor eax, eax. Which of the three confidence words belongs on each claim hidden in that sentence?

Level 1 of 4 · about 6 minutes to answer well.

Short answer. Confidence is one of three words and never a number: observed is a fact read from bytes or from a run, derived is a fact computed from observed records, and inferred is an expectation that no observation states yet. The record is observed about what the decompiler printed, with authority shipped-artifact, because the file on disk was the source. That the default value is 0 is derived, from the listing's xor and from the expression, which is always 0 and never says 0. That grade(55) returns 0 when the function runs stays inferred until an execute_function record with authority controlled-replay agrees with it.

The two enums.

Value Meaning
observed read from bytes or from a run
derived computed from observed records
inferred an expectation no observation states
shipped-artifact the file on disk was the source
controlled-replay a run you controlled produced the fact
analyst-inference your own judgement
historical-reference an older tree or document
external-service a service outside the file and the host

When a producer says nothing, the record gets observed and shipped-artifact. Read observed with care: in a function dossier it means that the tool recorded what the decompiler returned, with the bytes as authority. It does not mean the pseudocode is the program's source.

The two confusions that cost the most.

The first treats pseudocode as an observation of behaviour. It is an observation of what the decompiler printed. The expression above and the instruction both produce 0 for every input, and the agent did not know that; it trusted text because a tool produced it. The second treats an empty list as proof of absence. Missing coverage is unknown, not absence.

How a claim moves.

A claim moves from inferred to supported only through observed runs: pass when every input has an agreeing run and none disagrees, fail when any run disagrees, unknown when some inputs have runs and others do not, unsupported when no input has a run. A run of a host build of the same source counts, with the limitation that the object itself never ran. That sentence travels with the claim, because a report that drops it has lost information the reader needs.

Plausible wrong answers.

  • "It is observed because a tool produced it." The tool's text is observed; the behaviour it describes is derived or inferred.
  • "Give it a confidence of ninety percent." Confidence is a category with three values, not a number.
  • "The expression is a decompiler bug." It is correct and unreadable; two spellings of one bit cancel, and the instruction says it in two bytes.

Follow-ups an interviewer may ask.

  • (level 1) Why is confidence a word rather than a probability? Expected: the three words name the kind of support, and a number would hide which kind it was.
  • (level 2) A run of the same source compiled for the host agrees with the prediction. Is the claim about the x86-64 object observed? Expected: yes, with the limitation that a host build ran and the object did not; it is the strongest observation without an emulator.
  • (level 2) Which authority does a run under your own harness receive? Expected: controlled-replay, as opposed to shipped-artifact for a read of the file.
  • (level 3) The decompiler's signature says the function returns 16 bytes and takes a third parameter. Which word? Expected: the provider's inference; the dossier marks its return-type confidence low, and the record should say so.

Where it is taught. The evidence lesson builds a ledger with the three words and five authorities, and the evidence record section shows the fields on a recorded dossier.

Debug a failureAfter a tool upgrade, a call to open_binary with the saved snapshot answers profile_mismatch, although the target's SHA-256 and the provider are unchanged. The same morning a colleague renamed one function, and later close_binary with a snapshot path failed with "Analysis snapshots are unavailable because analysis metadata may have changed". Explain both refusals, and say what a snapshot is and is not.

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The cache key is the string query_ plus a SHA-256 over the target identity, the binding, the operation and the parameters, and the binding includes the analysis profile digest over 25 parameter version strings; the upgrade moved two of those values, so the digest changed and no stored entry can match, which the import reports as profile_mismatch. A rename is a mutating call, and the session empties the cache and sets a flag before the call is dispatched, even when the reply fails, because a failed reply cannot prove that the write never reached the provider, so the export is refused and the way out is to export the evidence bundle, close without a snapshot, and reopen. A snapshot is a file of exact past answers plus their evidence bundle, not a saved provider database.

Three things called a snapshot.

The target snapshot is the private copy the launcher imports read-only and deletes on close; nothing of the analysis survives it, and every new session imports the target again. The in-memory analysis snapshot cache holds up to 10,000 entries for one target identity. The snapshot file is what close_binary writes and open_binary reads: the target identity, the provider binding, the cache entries and the session's evidence bundle. Only an exact query that qualifies can reuse a result, and a new or live query still starts the provider.

What qualifies and what a hit looks like.

A call qualifies when its operation is not stateful, names its document or address where one is implied, declares no artifact mutation, and carries a cache policy of snapshot. A hit returns without touching the provider and adds one limitation: "Loaded from a local REA analysis snapshot; this call did not re-run the provider." The replayed record is rebound to the open target's path and keeps its evidence_id, because the path is outside the hash. The lesson's measurements make the point: a first query took 8.6 s with a fresh import, a different query against the same snapshot took 8.5 s because it was a miss, and a repeat took 2.1 s and returned the identical record with the identical id.

Load is a full check.

Entries must be in canonical id order, every query id is recomputed and must match, no id appears twice, and every entry must have an evidence record in the bundle with the same profile and result. A bundle record for another target fails the whole file. The write is atomic and owner-only.

Why the order of invalidation matters.

The current release invalidates and then calls the provider; an earlier release invalidated only after a successful call. The documentation states the rule: a metadata write clears the cache of the active session even when its reply fails, since the provider can already have applied the write.

Plausible wrong answers.

  • "A snapshot is a saved project; reopen it." It holds answers to past questions, and the project is deleted on close.
  • "Patch the profile digest so the old entries match." The digest names the contract the answers were produced under; a forced match replays answers from a changed contract.
  • "A rename is metadata, so cached answers stay valid." A rename is a mutating call; the cache is emptied before dispatch and the export is refused.

Follow-ups an interviewer may ask.

  • (level 2) You cached analyze_function for one function and then asked about another. Why a miss? Expected: the parameters are part of the key, so only the exact same question replays.
  • (level 3) Why not invalidate after the mutating call succeeds? Expected: a failed reply cannot prove rollback, so a cache kept after a failure could replay an answer about a database that changed.
  • (level 3) How does a reader tell a replayed record from a fresh one? Expected: the added limitation sentence that says the provider did not re-run.
  • (level 4) What is the right action after the upgrade refusal? Expected: run the analysis again under the new profile and keep the old bundle as evidence about an old contract; never edit the digest to force a match.

Where it is taught. The snapshot section gives the key, the qualifying rules and the invalidation order, and the evidence lesson builds the same cache and refuses a bumped profile version.
