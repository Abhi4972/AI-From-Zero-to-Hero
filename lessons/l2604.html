Why this came about

In 2022 Andrej Karpathy released nanoGPT, about 300 lines that train a GPT, and a video building it from an empty file. Training a tiny model on Tiny Shakespeare became the "hello world" of language models, because it shows every moving part of real LLM training at a size that runs on a laptop. In 2024 his llm.c project reproduced the full 124-million-parameter GPT-2 in about 90 minutes on one rented server for roughly 20 dollars, a run that had cost OpenAI far more in 2019. The code in this lesson follows the same design, scaled down further.

In plain words first
Same recipe, smaller pot

Training a large language model and training this one use the same recipe: cut text into tokens, show the model chunks of text, ask it to predict every next token, measure the cross-entropy, and nudge all the weights downhill, millions of times. What differs is scale: their vocabulary has 100,000+ tokens (yours: 65 characters), their model has billions of parameters (yours: under a million), their data is trillions of tokens (yours: one million characters), and they use thousands of GPUs for months (you: a laptop for three minutes). Watching the small version learn makes the big one far less mysterious.

Step 1 · Data and model

The same data preparation as Lesson 5.13, and the GPT code of Lesson 7.8 (copied here so this lesson runs on its own):

import math
import time
import requests
import torch
from torch import nn
import torch.nn.functional as F
from dataclasses import dataclass

URL = "https://raw.githubusercontent.com/karpathy/char-rnn/master/data/tinyshakespeare/input.txt"
text = requests.get(URL, timeout=60).text
chars = sorted(set(text))
stoi = {c: i for i, c in enumerate(chars)}
itos = {i: c for c, i in stoi.items()}
data = torch.tensor([stoi[c] for c in text])
split = int(0.9 * len(data))
train_ids, val_ids = data[:split], data[split:]

@dataclass
class GPTConfig:
    vocab_size: int = 65
    block_size: int = 64          # context: 64 characters
    n_layer: int = 4
    n_head: int = 4
    d_model: int = 128

class CausalSelfAttention(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.n_head = cfg.n_head
        self.qkv = nn.Linear(cfg.d_model, 3 * cfg.d_model)
        self.proj = nn.Linear(cfg.d_model, cfg.d_model)
    def forward(self, x):
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=-1)
        q, k, v = [t.view(B, T, self.n_head, C // self.n_head).transpose(1, 2) for t in (q, k, v)]
        out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.proj(out.transpose(1, 2).contiguous().view(B, T, C))

class MLP(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.up, self.down = nn.Linear(cfg.d_model, 4 * cfg.d_model), nn.Linear(4 * cfg.d_model, cfg.d_model)
    def forward(self, x):
        return self.down(F.gelu(self.up(x), approximate="tanh"))

class Block(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.ln1, self.attn = nn.LayerNorm(cfg.d_model), CausalSelfAttention(cfg)
        self.ln2, self.mlp = nn.LayerNorm(cfg.d_model), MLP(cfg)
    def forward(self, x):
        x = x + self.attn(self.ln1(x))
        return x + self.mlp(self.ln2(x))

class GPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.cfg = cfg
        self.tok_emb = nn.Embedding(cfg.vocab_size, cfg.d_model)
        self.pos_emb = nn.Embedding(cfg.block_size, cfg.d_model)
        self.blocks = nn.ModuleList([Block(cfg) for _ in range(cfg.n_layer)])
        self.ln_f = nn.LayerNorm(cfg.d_model)
        self.head = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)
        self.head.weight = self.tok_emb.weight
    def forward(self, idx):
        T = idx.shape[1]
        x = self.tok_emb(idx) + self.pos_emb(torch.arange(T, device=idx.device))
        for block in self.blocks:
            x = block(x)
        return self.head(self.ln_f(x))

cfg = GPTConfig()
print(len(chars), "characters,", len(train_ids), "training ids")

Step 2 · Initialise, then check the first loss

PyTorch's default initialisation suits ordinary networks, but a transformer with a tied embedding table needs smaller starting weights. GPT-2 draws every weight matrix from a normal distribution with spread 0.02 and sets biases to 0:

def make_model(seed=0):
    torch.manual_seed(seed)
    model = GPT(cfg)
    for name, p in model.named_parameters():
        if p.dim() >= 2:
            nn.init.normal_(p, mean=0.0, std=0.02)    # weight matrices and embedding tables
        elif name.endswith("bias"):
            nn.init.zeros_(p)
    return model

def get_batch(ids, size, gen):
    starts = torch.randint(len(ids) - cfg.block_size - 1, (size,), generator=gen)
    x = torch.stack([ids[i:i + cfg.block_size] for i in starts])
    y = torch.stack([ids[i + 1:i + cfg.block_size + 1] for i in starts])   # next characters
    return x, y

val_x, val_y = get_batch(val_ids, 200, torch.Generator().manual_seed(1))  # a fixed validation set

@torch.no_grad()
def val_loss(model):
    model.eval()
    loss = F.cross_entropy(model(val_x).reshape(-1, cfg.vocab_size), val_y.reshape(-1)).item()
    model.train()
    return loss

model = make_model()
print(f"parameters: {sum(p.numel() for p in model.parameters()):,}")
print(f"loss before training: {val_loss(model):.3f}   (a uniform guess over 65 characters: {math.log(65):.3f})")
What you should see
parameters: 809,856
loss before training: 4.241   (a uniform guess over 65 characters: 4.174)

The first loss should be close to log(65) ≈ 4.17: an untrained model should be equally unsure about every character. This is a cheap, powerful check from Karpathy's "recipe for training neural networks". If the first loss were 20 or 80, the outputs would be wildly overconfident, and training would waste its first steps undoing that, or fail. With PyTorch's default initialisation this model starts at a loss of about 80; try it by skipping the nn.init lines.

Step 3 · Train

The loop is the one from Lesson 3.16, with the refinements of Lesson 3.12: AdamW with weight decay, a short warm-up then cosine decay of the learning rate, and gradient clipping.

STEPS, BATCH, PEAK_LR, WARMUP = 2000, 32, 3e-3, 100

def lr_at(step):
    warm = min(1.0, step / WARMUP)
    cosine = 0.1 + 0.9 * 0.5 * (1 + math.cos(math.pi * step / STEPS))   # from the peak down to 10%
    return PEAK_LR * warm * cosine

opt = torch.optim.AdamW(model.parameters(), lr=PEAK_LR, weight_decay=0.1)
gen = torch.Generator().manual_seed(0)
start = time.time()
for step in range(1, STEPS + 1):
    for group in opt.param_groups:
        group["lr"] = lr_at(step)
    x, y = get_batch(train_ids, BATCH, gen)
    loss = F.cross_entropy(model(x).reshape(-1, cfg.vocab_size), y.reshape(-1))
    opt.zero_grad()
    loss.backward()
    nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    opt.step()
    if step % 400 == 0:
        print(f"step {step:>4}  training loss {loss.item():.3f}  validation loss {val_loss(model):.3f}")
print("finished in under ten minutes:", time.time() - start < 600)

Reading this output
  • Each step trains on 32 chunks of 64 characters: 2,048 next-character predictions at once (Lesson 7.5's causal mask makes each chunk 64 examples).
  • The training loss is noisy (one random batch); the validation loss, on a fixed held-out set, is the number to watch. It is still falling at the end, so the model is not yet overfitting: it has seen each part of the training text only about 4 times on average (2,000 × 2,048 ÷ 1,003,854).
  • On this course's test machine the run took about three minutes on two CPU cores. A laptop with more cores is usually faster; a GPU would take a few seconds.
  • The peak learning rate, 3e-3, is higher than you would use for a big model; small models tolerate (and need) larger steps. With 1e-3 this run ends about 0.1 worse.

Step 4 · Write some Shakespeare

Generation works exactly like the LSTM's in Lesson 5.13, except that the model rereads the last 64 characters at every step (Lesson 7.19 shows how real systems avoid that with a KV cachelater · 7.19):

@torch.no_grad()
def generate(model, prompt="ROMEO:\n", length=400, temperature=0.8, seed=0):
    torch.manual_seed(seed)
    model.eval()
    idx = torch.tensor([[stoi[c] for c in prompt]])
    for _ in range(length):
        logits = model(idx[:, -cfg.block_size:])[0, -1]          # only the last 64 characters fit
        probs = F.softmax(logits / temperature, dim=-1)
        idx = torch.cat([idx, torch.multinomial(probs, 1).view(1, 1)], dim=1)
    model.train()
    return "".join(itos[int(i)] for i in idx[0])

print(generate(model))

Step 5 · How it compares

The validation loss above averages over every position in each 64-character chunk, including the first few, where the model has almost no context. Split it by position to see how much context helps:

@torch.no_grad()
def loss_by_position(model):
    model.eval()
    logits = model(val_x)
    per_token = F.cross_entropy(logits.reshape(-1, cfg.vocab_size), val_y.reshape(-1), reduction="none").view(val_y.shape)
    model.train()
    for lo, hi in [(1, 4), (5, 16), (17, 32), (33, 64)]:
        print(f"predicting character {lo:>2} to {hi:>2} of a chunk: loss {per_token[:, lo - 1:hi].mean():.3f}")

The code barely changes between the columns. The engineering does: data pipelines that clean and deduplicate trillions of tokens (Lessons 10.6 and 10.1), splitting the model and data across thousands of GPUs (Lesson 3.20), and keeping a months-long run stable. And a pretrained model is still only a text continuer; turning it into an assistant is the From language model to assistant section.

The same idea as a formula
  • training objective: minimise L = −(1/(B·T)) Σ_b Σ_t log p(x_{b,t+1} | x_{b,1…t}) over batches of B chunks of length T
  • sanity check at initialisation: L ≈ log V for a vocabulary of V symbols
  • learning rate: η(s) = η_max · min(1, s/s_warm) · (0.1 + 0.9 · ½(1 + cos(π s / S)))
  • tokens seen = steps × batch × context; epochs = tokens seen ÷ training tokens
Check your mental model
  • ✗ "Training an LLM needs a completely different algorithm from this."
    ✓ The objective, architecture and optimiser are the same; scale, data and engineering differ.
  • ✗ "A lower training loss means the samples will be better."
    ✓ Watch the validation loss. If training loss keeps falling while validation rises, the model is memorising the training text.
  • ✗ "The model learned Shakespeare's grammar rules."
    ✓ It learned to predict characters. Rules emerge implicitly from that objective, in whatever form helps prediction.

Exercises

Predict before you run

If you change block_size from 64 to 16 and retrain, will the validation loss be higher or lower, and roughly how close will it get to the window network of Lesson 5.13? (Solution P1.)

Make it your own

Train on a different text: download another public-domain book (for example from Project Gutenberg, saved as a .txt file) and train the same model on it. Remember to rebuild chars, stoi and itos and set vocab_size to the new number of characters. (Solution M1.)

Debugging exercise

A learner changes PEAK_LR to 1e-2 and removes the warm-up. The loss drops for a few hundred steps, then jumps to about 3.3 and stays there; samples are mostly spaces and the letter "e". What happened, and what fixes it? (Solution D1.)

Solutions

SolutionP1 · A shorter context

Higher. With 16 characters of context the model can no longer use anything further back, so it loses information about the speaker, the line and the rhythm. It still beats the 8-character window network, since 16 characters is more context and attention uses it well, but it falls behind the 64-character model. Context length is one of the most valuable resources a language model has.

SolutionM1 · Your own text

Character-level models adapt to any text: a novel gives prose and dialogue in that author's spelling; code gives code-shaped text with brackets and indentation. With a smaller text (under 500,000 characters), validation loss will stop improving sooner, so watch for overfitting and consider fewer steps or more dropout. Choose texts that are in the public domain or that you are allowed to use.

SolutionD1 · Learning rate too high

The large learning rate pushed the model into a bad state it could not recover from: it collapsed to predicting the most common characters regardless of context (a loss around 3.3 is roughly what letter frequencies alone give). Lower the peak learning rate (1e-3 to 3e-3 for a model this size), restore the warm-up, and keep gradient clipping. When a run collapses, restart from the last good checkpoint rather than hoping it recovers.

Recap
  • A small GPT trains on a laptop CPU in minutes with the same recipe as real LLMs: next-token prediction, cross-entropy, AdamW, warm-up and cosine decay, clipping.
  • Initialise weight matrices with a small spread (0.02); the first loss should be close to log of the vocabulary size.
  • Watch validation loss, not training loss, and count how many times the model has seen the data.
  • Attention over 64 characters beats counting models and the recurrent network from the Language as data: NLP foundations section.
  • Real LLMs differ in scale, data and engineering, not in the core algorithm; turning a pretrained model into an assistant is the subject of the From language model to assistant section.
