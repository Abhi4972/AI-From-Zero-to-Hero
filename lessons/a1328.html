In plain words first
The idea in one line

A tool is safe to automate only when discovery, arguments, results, pagination, and transport metadata agree on one contract.

Terms you'll hear
Term Meaning
inputSchema JSON Schema object defining accepted tool arguments
outputSchema Optional JSON Schema defining structuredContent
structuredContent Any JSON value produced by a tool result
Content block Typed text, image, audio, resource link, or embedded resource
x-mcp-header Schema annotation that mirrors a primitive argument into Streamable HTTP metadata
Opaque cursor Server-issued pagination token whose value the client does not interpret
Completion reference Prompt name or resource URI/template whose argument is being completed
Admission Client decision to expose or reject a discovered descriptor

The problem

In plain words first

An MCP tool is a promise in several parts. Its input schema says which arguments it accepts; its output schema, if it has one, says exactly what shape of data it returns; its content blocks can carry text, images, audio, links or embedded files; some arguments can be copied into HTTP headers so gateways can route without reading the body; list results come in pages marked by opaque cursors; and errors come in two kinds, protocol errors and tool errors. Each part can be broken in a way no prompt can repair. This lesson lets the official SDK serve four tools and checks what it publishes with the lesson's own contract validator, which catches a real gap. Then it compares the SDK's header encoding with the lesson's, value by value, and finds where two careful implementations disagree.

Calling a Python function is easy. Calling a remote capability through an AI host is a contract problem.

The server publishes a descriptor. The client turns that descriptor into model context and user interface. The model creates arguments. A gateway may route the request from mirrored headers. The server executes the tool. The client then decides whether the result is safe and valid enough to return to the model.

One weak boundary corrupts the whole chain.

Consider five failures:

  • The descriptor says the result is an object, but the server returns an array.
  • The client stops pagination when nextCursor is an empty string.
  • A token parameter is mirrored into an HTTP header and becomes visible to intermediaries.
  • A Unicode routing value is sent as a raw header, then the gateway and origin interpret different bytes.
  • A completion endpoint suggests a production environment to a caller who cannot access it.

None of these failures is fixed by better prompting. They require explicit protocol and application contracts.

The Contract Pipeline

Treat each tool call as five gates:

  1. Discover. Read a deterministic, paginated tool list.
  2. Admit. Validate each descriptor and apply local security policy.
  3. Invoke. Validate arguments and build transport metadata.
  4. Execute. Run the handler and classify failures correctly.
  5. Consume. Validate content blocks and structured output before model use.

The host owns the admission and consumption gates. A server cannot force a client to trust its annotations, schemas, or outputs.

JSON Schema Is a Runtime Boundary

In MCP 2026-07-28, inputSchema and outputSchema use JSON Schema. When $schema is absent, the default dialect is 2020-12.

The input schema must be a schema object. A tool with no arguments should still say exactly what it accepts:

{
  "type": "object",
  "additionalProperties": false
}

This is stricter than { "type": "object" }, which accepts arbitrary properties.

An output schema is optional. Once a server publishes one, every complete tool result commits to returning conforming structuredContent, including results with isError: true. The error flag classifies execution outcome; it does not waive the published output contract. Clients should validate the result instead of trusting the descriptor.

Structured content is any JSON value

Do not hard-code structuredContent as a dictionary. It can be:

  • an object;
  • an array;
  • a string;
  • a number;
  • a boolean;
  • null.

This tool returns an array:

{
  "name": "tag_catalog",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false
  },
  "outputSchema": {
    "type": "array",
    "items": {"type": "string"}
  }
}

Its successful result is valid:

{
  "resultType": "complete",
  "content": [
    {
      "type": "text",
      "text": "[\"contracts\", \"mcp\", \"stateless\"]"
    }
  ],
  "structuredContent": ["contracts", "mcp", "stateless"],
  "isError": false
}

For compatibility, structured results should also include serialized JSON in a text block. The text is not the validation source. structuredContent is.

A small validator still teaches the boundary

The lesson uses a deliberate JSON Schema subset because it stays inside the Python standard library. It checks the mechanisms used by the sample tools:

  • object, array, string, integer, number, boolean, and null types;
  • required properties;
  • additionalProperties: false;
  • array items;
  • enum values;
  • minimum string length.

This is not a replacement for a complete production validator. The reusable lesson is where validation happens: after discovery for descriptors, before execution for arguments, and before consumption for structured results.

Content Blocks Carry Different Costs

The content array can combine several content types.

Type Use it for Main boundary
text Human and model-readable summaries Treat text as untrusted output
image Visual evidence encoded as base64 Validate media type and size
audio Spoken or recorded output encoded as base64 Validate media type and duration limits
resource_link A URI the client may fetch later Reauthorize the later resource read
resource Data embedded directly in the result Enforce payload and content limits now

A resource link is not proof that the resource appears in resources/list. It is a reference returned by this tool call. The client still applies its resource policy when it follows the URI.

An embedded resource avoids another round trip but increases the current response size. Use links for large or independently changing artifacts. Use embedded resources for small evidence that must travel atomically with the result.

The lesson's evidence_bundle result includes all five types. The client validates each block before accepting the result.

x-mcp-header Is Routing Metadata

A property inside inputSchema may declare x-mcp-header. Over Streamable HTTP, the client mirrors that argument into Mcp-Param-{name}.

{
  "region": {
    "type": "string",
    "x-mcp-header": "Region"
  }
}

With region: "eu-west", the transport can emit:

Mcp-Param-Region: eu-west

The annotation exists so a load balancer, gateway, or policy engine can route without parsing the JSON body. It is not a place to put credentials.

The protocol constrains the annotation:

  • the header name is non-empty and follows HTTP field-name token syntax;
  • header names are unique without regard to case;
  • the property type is string, integer, or boolean;
  • number is not allowed;
  • the annotation appears only on a direct member of inputSchema.properties;
  • integer values stay within -9007199254740991 through 9007199254740991.

The location rule is syntactic and fail-closed. Walk the entire schema tree, not just the properties your validator happens to understand. Reject an annotation under a nested object's properties, a oneOf branch, items, a definition reached by $ref, or any output schema. Resolving a reference does not turn the referenced node into a direct top-level property.

This lesson adds a deployment policy: reject descriptors that mirror names such as password, secret, token, api_key, or authorization. The official specification advises server authors not to mirror sensitive parameters. A client can turn that advice into a hard admission rule.

Audit the header name, not its value. The sample code records Mcp-Param-Region while keeping eu-west out of the audit event.

Encode values before building HTTP headers

A parameter value may travel as plain text only when it is a non-empty string of visible ASCII characters from ! through ~ and does not resemble the encoding sentinel. Everything else uses this exact form:

=?base64?{Base64UTF8}?=

Base64UTF8 is standard base64 over the exact UTF-8 bytes. Do not trim, normalize, or replace the value first. Encode Unicode, empty strings, spaces, tabs, control characters, CR or LF, leading or trailing whitespace, and any value beginning with =?base64?. Encoding a sentinel-looking value again is what lets the receiver recover the literal original text instead of decoding it as transport syntax.

Booleans render as lowercase true or false. Integers render in base 10 and must stay inside the JavaScript safe integer range. Values outside that range are rejected instead of rounded by an intermediary.

The server checks the mirrored copy

Header generation is only the client half. At the Streamable HTTP boundary, the server must:

  1. find recognized Mcp-Param-* names without regard to header-name case;
  2. decode the exact base64 sentinel form when present;
  3. compare the decoded text with the corresponding JSON body argument exactly;
  4. reject a missing, duplicated, unexpected, malformed, or mismatched recognized header before dispatch.

The rejection is HTTP 400 with JSON-RPC error code -32020. Neither the body value nor its encoded header form belongs in the audit record. Record the recognized header name and the rejection category only.

code/main.py models this boundary directly. [Lesson 13.9](#a1309) covers the wider Streamable HTTP validation order, including method and protocol-version parity.

Pagination Cursors Are Opaque

MCP list operations use cursor pagination. The server selects page size and cursor format. The client gets one decision:

if result.get("nextCursor") is None:
    break
cursor = result["nextCursor"]

Do not write this:

if not result.get("nextCursor"):
    break

An empty string is a valid cursor. Truthiness would stop too early.

Clients must not decode a cursor, increment it, compare it with a prior cursor for ordering, or infer a page number. A server may sign a cursor, bind it to a catalog version, or map it to private state. That is the server's implementation detail.

The sample server deliberately returns "" after the first page. The client must send that exact value on the second request. Its trace is:

<first request with no cursor>
<second request with cursor "">

Invalid cursors produce JSON-RPC invalid params, code -32602.

Completion Is an Authorization Surface

completion/complete provides suggestions for prompt arguments and resource-template arguments. It is useful for interactive forms, but it can leak names that ordinary list methods protect.

A completion request names a reference and the argument being completed:

{
  "method": "completion/complete",
  "params": {
    "ref": {
      "type": "ref/prompt",
      "name": "deployment_review"
    },
    "argument": {
      "name": "environment",
      "value": "st"
    }
  }
}

The result returns at most 100 values and may report total plus hasMore.

Apply the same authorization boundary used by the referenced prompt or resource. An analyst in the sample receives development and staging. Only an operator can receive production.

Production completion also needs:

  • input validation;
  • caller-aware filtering;
  • request debouncing in the client;
  • rate limiting in the server;
  • bounded result counts;
  • logs that do not expose sensitive suggestion values.

Completion is assistance, not discovery bypass.

Two Error Layers

Keep protocol errors separate from tool execution errors.

Use a JSON-RPC error when the MCP request cannot be dispatched correctly:

  • unknown tool name;
  • malformed request shape;
  • missing request metadata;
  • invalid cursor.

Use a complete tool result with isError: true when the invocation reached the tool and the tool reports an actionable failure:

  • a report source is unavailable;
  • a date is outside the supported range;
  • a business rule rejects the requested operation.

Models can often repair a tool execution error. They cannot repair a server that violated its own output schema.

If the tool declares an output schema, model an actionable failure inside that schema. The sample route_report failure returns its requested region with accepted: false, alongside human-readable error text and isError: true.

The same idea as a formula

The output contract. For a tool with output schema O, every complete result r must satisfy

r.structuredContent⊨O(whether or not r.isError),
so an actionable failure is modelled inside O (for example accepted: false), not by dropping the structured part.

Header encoding. For a value v, let safe(v) mean every character is visible ASCII (0x21-0x7E) and v does not match the sentinel pattern. Then

header(v)={v=?base64?B64(UTF8(v))?=​if safe(v)otherwise.​
A server decodes, then requires $\text{decode}(\text{header}) = $ the body value, or answers 400 with -32020.

Pagination ends only on absence. A client loops while nextCursor=absent. The empty string is a cursor, so a truthiness test (if not cursor) stops one page early.

Worked example
Encoding three values by hand
  • "eu-west": every character is visible ASCII → sent as is: Mcp-Param-Region: eu-west.
  • "zürich": ü is not ASCII. UTF-8 bytes 7a c3 bc 72 69 63 68 → Base64 esO8cmljaA== → =?base64?esO8cmljaA==?=.
  • "=?base64?x?=": plain ASCII, but it looks like the sentinel, so it must be encoded too, or a server would try to decode it: Base64 of the whole string, PT9iYXNlNjQ/eD89.
  • A gateway that routes on Mcp-Param-Region must decode the same way before comparing, or "zürich" traffic goes to the wrong place.
Check your mental model
  • ✗ "structuredContent is always an object."
    ✓ In 2026-07-28 it can be any JSON value; some SDKs still wrap non-objects in {"result": ...}.
  • ✗ "With isError: true the output schema no longer applies."
    ✓ A published output schema applies to every complete result; model failures inside it.
  • ✗ "Any argument can become a header."
    ✓ Only strings, integers and booleans reachable through properties, with unique token names, and never secrets.
  • ✗ "An empty nextCursor means the list is finished."
    ✓ Only an absent cursor ends the list; "" is a valid cursor.

The SDK's tools judged by the lesson's contract checks

MCPServer derives schemas from Python type hints: a list[str] return, a Pydantic model, the same model with a wrong return value, and a list of content blocks (text, a 1x1 PNG image, a resource link, an embedded resource). Each descriptor and result goes through validate_tool_descriptor and validate_tool_result from code/main.py. About a second.

# The official SDK serves four tools; the lesson's own contract checks (code/main.py) judge what it publishes.
import asyncio, base64, logging
logging.disable(logging.ERROR)                                   # the SDK logs a traceback for the broken tool
from pydantic import BaseModel
from mcp import Client, types
from mcp.server import MCPServer
from main import validate_tool_descriptor, validate_tool_result, ContractViolation

srv = MCPServer("contracts", log_level="WARNING")
class Invoice(BaseModel):
    id: str
    total: float
@srv.tool()
def tag_catalog() -> list[str]:
    """Use to list catalog tags."""
    return ["contracts", "mcp", "stateless"]
@srv.tool()
def get_invoice(invoice_id: str) -> Invoice:
    """Use to fetch one invoice."""
    return Invoice(id=invoice_id, total=12.5)
@srv.tool()
def broken_invoice(invoice_id: str) -> Invoice:
    """Returns the wrong shape on purpose."""
    return {"id": invoice_id}                                    # no total
PNG = base64.b64encode(bytes.fromhex("89504e470d0a1a0a0000000d49484452000000010000000108060000001f15c4890000000d4944415478da63f8cfc0f01f0005000201a3f3b5d40000000049454e44ae426082")).decode()
@srv.tool()
def evidence_bundle(case_id: str) -> list[types.ContentBlock]:
    """Use to fetch evidence for a case."""
    return [types.TextContent(type="text", text=f"Evidence for {case_id}"),
            types.ImageContent(type="image", data=PNG, mime_type="image/png"),
            types.ResourceLink(type="resource_link", uri=f"evidence://{case_id}/log", name="full log"),
            types.EmbeddedResource(type="resource", resource=types.TextResourceContents(uri=f"evidence://{case_id}/summary", text="3 failed logins"))]

async def main():
    async with Client(srv) as c:
        tools = {t.name: t.model_dump(by_alias=True, exclude_none=True) for t in (await c.list_tools()).tools}
        for name, args in [("tag_catalog", {}), ("get_invoice", {"invoice_id": "A1"}),
                           ("broken_invoice", {"invoice_id": "A1"}), ("evidence_bundle", {"case_id": "C7"})]:
            d = tools[name]
            out = d.get("outputSchema", {}); shape = out.get("type", "none") + (f" {sorted(out.get('properties', {}))}" if out else "")
            r = (await c.call_tool(name, args)).model_dump(by_alias=True, exclude_none=True)
            try:
                validate_tool_descriptor(d); validate_tool_result(d, {"resultType": "complete", **r}); verdict = "contract OK"
            except ContractViolation as e: verdict = f"VIOLATION: {e}"
            print(f"{name:<16} outputSchema={shape:<22} isError={r.get('isError', False)!s:<5} "
                  f"structured={str(r.get('structuredContent'))[:38]:<40} blocks={[b['type'] for b in r['content']]}\n{'':<17}{verdict}")
asyncio.run(main())

Reading this output

Type hints become schemas. get_invoice returns a Pydantic model, so the SDK publishes an object output schema with id and total and returns matching structuredContent plus a JSON text block: contract OK.

A list is wrapped. tag_catalog returns list[str], which 2026-07-28 allows as structured content directly, but the SDK publishes an object schema with one result property and sends {"result": [...]}, plus one text block per item. It is self-consistent, so it passes; clients should still not assume structured content is always an object, because other servers send arrays.

The broken tool exposes a real gap. When broken_invoice returns the wrong shape, the SDK catches the validation error and sends isError: true with a text message and no structuredContent. The lesson's validator flags this: a tool that publishes an output schema must return conforming structured content on every complete result, errors included.

Content blocks pass one by one. evidence_bundle returns text, a base64 PNG with its MIME type, a resource link and an embedded resource; each satisfies its block rules. The resource link is only a reference: following it is a separate, separately authorized read.

Reading this output

The codecs agree on every non-empty value. Plain ASCII stays plain; zürich, a leading space, a newline and a value that looks like the sentinel are all Base64-wrapped identically, and both round-trip.

They disagree on the empty string. The SDK sends '' as is; the lesson encodes it as =?base64??=. The specification lists non-ASCII, control characters, leading or trailing whitespace and sentinel look-alikes as cases that need encoding, and says nothing explicit about the empty string. Both choices decode to "", so a server must accept either. This is exactly the kind of finding a differential test exists to surface (Lesson 13.31): file it, and keep a regression test whichever way it is settled.

Both reject the same bad annotations, with different messages: an object-typed property, a header name with a space (not an HTTP token), and two names that collide ignoring case. A client that meets such a tool must drop it from its listing.

The SDK builds the header from the listing. Only the annotated argument becomes Mcp-Param-Region, encoded; note stays in the body only.

Build it

code/main.py builds both sides of the boundary with the Python standard library.

The server implements:

  • per-request MCP metadata validation;
  • server/discover with tools and completions capabilities;
  • deterministic tools/list pagination;
  • four tool descriptors, including one that must be rejected;
  • array structured output;
  • every current tool content block type;
  • a Streamable HTTP parity gate that decodes recognized parameter headers and returns HTTP 400 plus JSON-RPC -32020 on mismatch;
  • authorized and rate-limited completion.

The client implements:

  • descriptor admission;
  • full-tree x-mcp-header placement validation and sensitive-field policy;
  • exact plain-visible-ASCII or base64 UTF-8 value encoding;
  • an opaque cursor loop that follows an empty string;
  • argument and result validation;
  • content-block validation;
  • header audit events containing names but not values.

The deliberately unsafe descriptor is teaching data. It proves that one rejected tool does not prevent valid tools from loading.

Industry practice
What's current (2024–2026)
  • 2026-07-28 tool contracts: JSON Schema 2020-12 by default, optional outputSchema with structuredContent of any JSON type, content types text, image, audio, resource_link and resource, x-mcp-header mirroring into Mcp-Param-*, and -32020 HeaderMismatch when headers and body disagree.
  • SDK support: the official Python SDK 2.x validates x-mcp-header annotations on both sides, drops invalid tools from client listings, mirrors headers, and re-validates structured results against the output schema; it still wraps non-object returns as {"result": ...}. The TypeScript and C# SDKs ship the same header encoder.
  • Gateways that route or rate-limit on mirrored headers (Lesson 13.17) must check that the protocol version requires header-body validation before trusting them.
  • On your laptop: all of this is protocol code; it runs instantly on the CPU.

Sources: Streamable HTTP, 2026-07-28, SEP-2243 HTTP standardization, Python SDK mcp.shared.inbound.

Recap
What to keep from this lesson
  • Five gates: discover, admit, invoke, execute, consume, each with its own checks.
  • Validate descriptors after listing, arguments before calling, and structured results before using them.
  • A published output schema covers error results too.
  • Mirror only safe primitive arguments into headers, encoded exactly; never secrets.
  • Loop pages until the cursor is absent; keep protocol errors and tool errors apart.

Solutions

SolutionP1 · An error without structured content

The SDK validates the return value against the model, catches the failure, and sends a complete result with isError: true, a text block "Error executing tool broken_invoice", and no structuredContent. That does not satisfy the 2026-07-28 rule: once a tool publishes an outputSchema, every complete result, including an error result, should carry structuredContent that conforms to it. The lesson's validate_tool_result reports "outputSchema requires structuredContent". A well-designed tool models its failure inside the schema (for example, an error field or accepted: false) and returns that with isError: true.

SolutionB1 · A leaked token and a missing page

The token leaks. Mirrored headers exist so intermediaries can read them: load balancers, gateways, proxies, CDNs and their logs all see Mcp-Param-Token in clear text, and many log headers by default. A secret that was safe inside the encrypted, rarely logged body is now copied into every hop's logs. Rate-limit on a non-secret identifier (a tenant id or a hashed key computed by the gateway from the authenticated identity), never on the secret itself.

The client misses data. A server may legitimately return nextCursor: "" (the sample server does). if not cursor treats the empty string as "done", so the client stops one page early and silently works with an incomplete tool list. Loop until the key is absent (while "nextCursor" in result), and send the exact cursor back.

Verify It

The lesson is complete when these statements are true:

  • tools/list returns the same logical order on repeated calls.
  • The client performs a second request when nextCursor is "".
  • The unsafe sensitive-header descriptor is excluded while other tools remain available.
  • An array passes its array output schema.
  • An object fails that same array schema.
  • Error results cannot omit or violate a published output schema.
  • Text, image, audio, resource link, and embedded resource blocks validate.
  • Header audit events contain names and no values.
  • Plain visible ASCII remains plain; Unicode, control, padded, empty, and sentinel-looking values round-trip through exact base64 UTF-8 encoding.
  • Mirrored integers outside the JavaScript safe range are rejected.
  • Annotations under oneOf, items, nested objects, $ref definitions, or output schemas are rejected during admission.
  • Case-insensitive recognized header names pass only when the decoded value exactly matches the body; missing or mismatched copies produce HTTP 400 and JSON-RPC -32020.
  • Analyst completion never returns production.
  • A tool failure uses isError: true; a malformed protocol call uses JSON-RPC error.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Read the codeA client collects the tool list of an MCP server with this loop: python tools = [] cursor = None while True: result = call("tools/list", cursor=cursor) tools.extend(result["tools"]) if not result.get("nextCursor"): break cursor = result["nextCursor"] Against one server the client sees only the first page, and the trace shows a single request. Read the code and find the bug. Then name two more things a client must never do with a cursor.

Level 2 of 4 · about 7 minutes to answer well.

Short answer. The loop tests the cursor for truthiness, and an empty string is a valid cursor. The server returned "" after its first page, the test read it as false, and the loop stopped before the second request. Stop only when nextCursor is absent or null, and send the value back exactly as received. A client must also never decode a cursor or compare two cursors for order.

The one decision a client gets.

if result.get("nextCursor") is None:
    break
cursor = result["nextCursor"]

The server chooses the page size and the cursor format. The sample server in the lesson deliberately returns "" after its first page, and the correct trace is one request with no cursor followed by one request with the cursor "".

Cursors are opaque.

Do not decode a cursor, increment it, compare it with a prior cursor, or infer a page number from it. A server may sign a cursor, bind it to a catalog version, or map it to private state. That is the server's detail and may change without notice. An invalid cursor returns JSON-RPC invalid params, -32602.

Why the bug matters.

The tool list is the first gate of the contract pipeline: discover, admit, invoke, execute, consume. A client that drops the last pages exposes a partial catalog to the model and may miss the descriptor it was asked to admit or reject. Discovery must be deterministic and complete before admission starts.

Plausible wrong answers.

  • "An empty string means no more pages." It is a valid cursor. Only absence or null ends the loop.
  • "Parse the cursor to compute the page number." The format belongs to the server and may be signed or private state.
  • "Compare the new cursor with the old one to detect a loop." Clients must not compare cursors for ordering.

Follow-ups an interviewer may ask.

  • (level 2) A page arrives with nextCursor present and an empty tools array. Do you continue? Expected: yes; continue whenever nextCursor is present and not null.
  • (level 2) A cursor looks like base64. May the client decode it to skip ahead? Expected: no; the value is opaque, and the server may sign it or bind it to a catalog version.
  • (level 3) What should a server put in a cursor so that a client cannot misuse it? Expected: a signed or server-mapped token, bound to a catalog version where needed, with an invalid or stale value rejected as -32602.
  • (level 4) What evidence proves complete paginated discovery for a gateway? Expected: the page trace, the admitted and rejected descriptor sets, and a check that repeated calls give the same logical order.
