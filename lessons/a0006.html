Dependency hell is real. Virtual environments are the cure.

Terms you'll hear
Term What people say What it actually means
Virtual environment "A venv" An isolated directory containing a Python interpreter and packages, separate from the system Python
Lockfile "Pinned dependencies" A file listing every package and its exact version, guaranteeing identical installs across machines
pyproject.toml "The new setup.py" The standard Python project configuration file, replacing setup.py/setup.cfg/requirements.txt
Transitive dependency "A dependency of a dependency" Package B depends on C; if you install A which depends on B, C is a transitive dependency of A
CUDA mismatch "My GPU isn't working" PyTorch was compiled for a different CUDA version than what your GPU driver supports

The problem

In plain words first

A Python package is installed into one folder of one Python. If every project shares that folder, upgrading a library for one project silently changes it for all of them. A virtual environment gives each project its own folder. A lockfile writes down the exact version of every package, including the ones your packages pulled in, so the same environment can be rebuilt on another machine.

You install PyTorch 2.4 for a fine-tuning project. Next week, a different project needs PyTorch 2.1 because its CUDA build is pinned. You upgrade globally, and the first project breaks. You downgrade, and the second one breaks.

This is dependency hell. It happens constantly in AI/ML work because:

  • PyTorch, JAX, and TensorFlow each ship their own CUDA bindings
  • Model libraries pin specific framework versions
  • A global pip install overwrites whatever was there before
  • CUDA 11.8 builds don't work with CUDA 12.x drivers (and vice versa)

The fix: every project gets its own isolated environment with its own packages.

The idea

The same idea as a formula

A version specifier describes a set of versions, and several specifiers joined by commas mean the intersection of their sets:

  • >=1.26 is [1.26,∞); <2.3 is (−∞,2.3); together >=1.26,<2.3 is [1.26,2.3).
  • ~=X.Y (compatible release) means >=X.Y, ==X.*; ~=X.Y.Z means >=X.Y.Z, ==X.Y.*.
  • ==2.* is every 2.x release.

A resolver has to choose one version of each package that lies in the intersection of every constraint on it, from your project and from every dependency of every dependency; it usually takes the newest. If the intersection is empty, there is no solution: that is a dependency conflict. Pre-releases (3.0.0rc1) are skipped unless you ask for them (pip install --pre, uv --prerelease allow).

A lockfile (uv.lock) records the chosen point for every package, so the next install repeats it instead of solving again.

Worked example
Intersecting constraints by hand

NumPy releases available: 1.24.4, 1.26.4, 2.0.2, 2.1.3, 2.2.6, 2.3.1.

  • Your project says numpy>=1.26,<2.3: allowed {1.26.4, 2.0.2, 2.1.3, 2.2.6}.
  • A library you use says numpy~=2.1, which is >=2.1, ==2.*: allowed {2.1.3, 2.2.6, 2.3.1}.
  • Intersection: {2.1.3, 2.2.6}. The resolver installs 2.2.6.
  • If the library said ~=2.3 instead, the intersection with <2.3 would be empty and the install would fail with a conflict, naming both requirements.
Check your mental model
  • ✗ "numpy>=1.26 in pyproject.toml means everyone gets the same NumPy."
    ✓ It means any version from 1.26 up. Today that might be 2.5, next year 3.0. Only the lockfile pins one exact version.
  • ✗ "I only depend on the four packages I listed."
    ✓ Each of them depends on others. Matplotlib alone needs nine more, and those are what usually conflict.
  • ✗ "Copy the .venv folder to share the environment."
    ✓ It contains paths and compiled files for your machine. Share pyproject.toml and the lockfile; the other person rebuilds.

Build · Option 1: uv venv (Recommended)

uv is the fastest Python package manager (10-100x faster than pip). It handles virtual environments, Python versions, and dependency resolution in one tool.

curl -LsSf https://astral.sh/uv/install.sh | sh

uv python install 3.12

cd your-project
uv venv
source .venv/bin/activate

Install packages:

uv pip install torch numpy

Create a project with pyproject.toml in one step:

uv init my-ai-project
cd my-ai-project
uv add torch numpy matplotlib
Predict before you run

In a new project, uv add numpy changes two files. In pyproject.toml it writes a line like "numpy>=2.5.5". What does it write about NumPy in uv.lock, and why are there two different kinds of line? (Solution P1.)

Build · Option 2: venv (Built-in)

If you can't install uv, Python ships with venv:

python3 -m venv .venv
source .venv/bin/activate  # Linux/macOS
.venv\Scripts\activate     # Windows

pip install torch numpy

Slower than uv, but works everywhere Python is installed.

Build · Option 3: conda (When You Need It)

Conda manages non-Python dependencies like CUDA toolkits, cuDNN, and C libraries. Use it when:

  • You need a specific CUDA toolkit version without installing it system-wide
  • You're on a shared cluster where you can't install system packages
  • A library's install instructions say "use conda"
# Install miniconda (not the full Anaconda)
curl -LsSf https://repo.anaconda.com/miniconda/Miniconda3-latest-Linux-x86_64.sh -o miniconda.sh
bash miniconda.sh -b

conda create -n myproject python=3.12
conda activate myproject

conda install pytorch torchvision torchaudio pytorch-cuda=12.4 -c pytorch -c nvidia

One rule: if you use conda for an environment, use conda for all packages in that environment. Mixing pip install into a conda env causes dependency conflicts that are painful to debug.

pyproject.toml Basics

Every Python project should have a pyproject.toml. It replaces setup.py, setup.cfg, and requirements.txt in one file.

[project]
name = "ai-engineering-from-scratch"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "numpy>=1.26",
    "matplotlib>=3.8",
    "jupyter>=1.0",
    "scikit-learn>=1.4",
]

[project.optional-dependencies]
torch = ["torch>=2.3", "torchvision>=0.18"]
llm = ["anthropic>=0.39", "openai>=1.50"]

Then install:

uv pip install -e ".[torch]"    # base + PyTorch
uv pip install -e ".[llm]"     # base + LLM SDKs
uv pip install -e ".[torch,llm]" # everything
See it drawn
What a version range accepts

pyproject.toml uses version specifiers, and the packaging library that pip and uv use can check them for you:

from packaging.specifiers import SpecifierSet
from packaging.version import Version

for spec in [">=1.26", "~=1.26", "==1.26.*"]:
    ok = [v for v in ["1.25.2", "1.26.0", "1.27.1", "2.5.4"] if Version(v) in SpecifierSet(spec)]
    print(f"{spec:9} accepts {ok}")
What you should see
>=1.26    accepts ['1.26.0', '1.27.1', '2.5.4']
~=1.26    accepts ['1.26.0', '1.27.1']
==1.26.*  accepts ['1.26.0']

~=1.26 means "1.26 or later, but still 1.x", a common way to accept fixes but not a new major version.

Reading this output

>=1.26 accepts everything from 1.26.0 up, including 2.5.4, a new major version that may break your code. ~=1.26 stops at the 1.x line, and ==1.26.* accepts only 1.26 patch releases. Libraries usually state wide ranges (so they combine with other packages) and applications pin exact versions in a lockfile.

Lockfiles

A lockfile pins every dependency (including transitive ones) to exact versions. This guarantees reproducibility: anyone who installs from the lockfile gets exactly the same packages.

# uv generates uv.lock automatically when using uv add
uv add numpy

# pip-tools approach
uv pip compile pyproject.toml -o requirements.lock
uv pip install -r requirements.lock

Commit your lockfile to git. When someone clones the repo, they install from the lockfile and get identical versions.

See it drawn
Transitive dependencies, seen directly

Every installed package records what it needs. This lists what Matplotlib pulled in on this page's server:

from importlib.metadata import version, requires

print("matplotlib", version("matplotlib"))
for r in requires("matplotlib"):
    print("  needs", r)
What you should see
matplotlib 3.11.2
  needs contourpy>=1.0.1
  needs cycler>=0.10
  needs fonttools>=4.28.2
  needs kiwisolver>=1.3.1
  needs numpy>=1.25
  needs packaging>=20.0
  needs pillow>=9
  needs pyparsing>=3
  needs python-dateutil>=2.7

None of these appear in a pyproject.toml that only lists matplotlib, yet all of them are installed, and all of them are pinned in the lockfile.

Reading this output

Each line is a constraint Matplotlib places on another package, with its own range. None of these names is in your pyproject.toml, but the resolver has to satisfy all of them, intersected with whatever your other packages ask of the same names (NumPy appears in almost every scientific package's list). The lockfile is the record of the single version it picked for each.

Common mistakes

1. Installing globally

pip install torch  # BAD: installs to system Python

source .venv/bin/activate
pip install torch  # GOOD: installs to virtual environment

Check where your packages go:

which python       # should show .venv/bin/python, not /usr/bin/python
which pip           # should show .venv/bin/pip

2. Mixing pip and conda

conda create -n myenv python=3.12
conda activate myenv
conda install pytorch -c pytorch
pip install some-other-package   # BAD: can break conda's dependency tracking
conda install some-other-package # GOOD: let conda manage everything

If you must use pip inside conda (some packages are pip-only), install all conda packages first, then pip packages last.

3. Forgetting to activate

python train.py           # uses system Python, missing packages
source .venv/bin/activate
python train.py           # uses project Python, packages found

Your shell prompt should show the environment name:

(.venv) $ python train.py

4. Committing .venv to git

echo ".venv/" >> .gitignore

Virtual environments are 200MB-2GB. They're local, not portable between machines. Commit pyproject.toml and the lockfile instead.

5. CUDA version mismatch

nvidia-smi                # shows driver CUDA version (e.g., 12.4)
python -c "import torch; print(torch.version.cuda)"  # shows PyTorch CUDA version

# These must be compatible.
# PyTorch CUDA version must be <= driver CUDA version.
Break it on purpose

Create a virtual environment and activate it. Open a new terminal tab without activating anything and run python -c "import numpy", then which python in both tabs. What do you see, and why? (Solution B1.)

Recap
What to keep from this lesson
  • One virtual environment per project (or per phase of this course); never install into the system Python.
  • pyproject.toml states what you need, as ranges; the lockfile records exactly what you got, including transitive dependencies. Commit both, never .venv.
  • uv does environments, Python versions, installs and locking in one tool; conda is for non-Python dependencies such as CUDA toolkits.
  • Check which python when imports fail, and check that PyTorch's CUDA version is not newer than your driver's.

Solutions

SolutionP1 · Two kinds of line

uv.lock gets an entry with name = "numpy" and one exact version = "2.5.5", plus the download source and file hashes. pyproject.toml records your intent, a range of acceptable versions; the lockfile records the result, the one version chosen today. Installing from the lockfile gives everyone the same bytes; resolving from pyproject.toml alone may give a newer version next month.

SolutionB1 · The tab without the environment

In the new tab which python points at the system Python (for example /usr/bin/python3 or a Homebrew path), and the import fails with ModuleNotFoundError if NumPy was only installed in the environment. Activation only changes the PATH of the terminal it ran in. Activate in every new terminal, or let your editor pick the interpreter in .venv for you.

Industry practice
What's current (2024–2026)
  • uv projects and lock files. uv init, uv add and uv lock give every project a pyproject.toml and a cross-platform uv.lock; PEP 751 standardised a pylock.toml lock-file format (2025) that tools are adopting.
  • Picking the right PyTorch build. uv pip install torch --torch-backend=auto selects the CUDA, ROCm or CPU wheel index for the machine automatically; otherwise use PyTorch's own index URL for your CUDA version.
  • Conda where native libraries matter. conda-forge and pixi remain the choice when a stack needs non-Python dependencies (CUDA toolkits, GDAL, compilers) pinned together.

Sources: uv projects, PEP 751, uv and PyTorch, pixi.
