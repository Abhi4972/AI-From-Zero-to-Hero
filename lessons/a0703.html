In plain words first
The idea in one line

One attention head learns one relation at a time. Eight heads learn eight. Heads are free. Take more of them.

Terms you'll hear

The problem

In plain words first

One attention head produces one set of weights per word, so it can follow one kind of relationship at a time: the previous word, or the subject of the verb, or an earlier mention of the same name. Multi-head attention runs several smaller heads side by side, each with its own query, key and value projections over a slice of the embedding, then joins their outputs and mixes them with one more matrix. It costs no more arithmetic than one big head. The variants that matter in practice change only the keys and values: grouped-query attention lets several query heads share one key-value head, so the memory a chatbot keeps per token (the KV cache) shrinks several times. This lesson builds the split and merge, checks PyTorch's grouped-query call, reads the real head counts and cache sizes from six production models' configuration files, and finds the "induction heads" inside GPT-2 that let it continue a pattern it has just seen, then switches them off. Nothing is trained.

A single self-attention head computes one attention matrix. That matrix captures one kind of relationship — usually the one that minimizes loss on whatever the training signal is. If your data has subject-verb agreement, co-reference, long-range discourse, and syntactic chunking all tangled together, a single head smears them into a single soft-max distribution and loses half the signal.

The fix from the 2017 Vaswani paper: run several attention functions in parallel, each with its own Q, K, V projections, and concatenate the outputs. Each head operates in a smaller subspace of dimension dmodel​/nheads​. Total parameters stay the same. Expressive power goes up.

Multi-head attention is the default every transformer in 2026 ships with. The only argument is about how many heads and whether keys and values share projections (Grouped-Query Attention, Multi-Query Attention, Multi-head Latent Attention).

The idea

Split. Take X of shape (N, d_model). Project to Q, K, V each of shape (N, d_model). Reshape to (N, n_heads, d_head) where dhead​=dmodel​/nheads​. Transpose to (n_heads, N, d_head).

Attend in parallel. Run scaled dot-product attention inside each head. Each head produces (N, d_head). The heads operate on different subspaces of the embedding and never talk during the attention computation itself.

Concatenate and project. Stack heads back to (N, d_model) and multiply by a learned output matrix W_o of shape (d_model, d_model). W_o is where heads get to mix.

Why it works. Each head can specialize without competing with the others for representational budget. Probing studies from 2019–2024 show distinct head roles: positional heads, head that attends to the previous token, copy heads, named-entity heads, induction heads (which underlie in-context learning).

The 2026 lineage of variations:

Variant Q heads K/V heads Used by
Multi-head (MHA) N N GPT-2, BERT, T5
Multi-query (MQA) N 1 PaLM, Falcon
Grouped-query (GQA) N G (e.g. N/8) Llama 2 70B, Llama 3+, Qwen 2+, Mistral
Multi-head latent (MLA) N compressed to low-rank DeepSeek-V2, V3

GQA is the modern default because it cuts KV-cache memory by a factor of N/G while keeping nearly full quality. MLA goes further by compressing K/V into a latent space, then projecting back at compute time — costs FLOPs, saves a lot more memory.

The same idea as a formula

With h heads and dk​=d/h, head i has its own WQ(i)​,WK(i)​,WV(i)​∈Rd×dk​:

headi​=softmax(dk​​(XWQ(i)​)(XWK(i)​)⊤​+M)XWV(i)​,MHA(X)=[head1​;…;headh​]WO​

Stacking the h projections side by side gives one d×d matrix each for Q, K and V, so the parameter count, 4d2 including WO​, does not depend on h; neither does the projection arithmetic. The score computation is h⋅n2dk​=n2d multiply-adds for any h.

Where heads mix. Writing WO​ as h blocks of rows, MHA(X)=∑i​headi​WO(i)​: each head writes its own contribution into the full d-dimensional output, and they add up.

Grouped-query attention. With g key-value heads, query head i uses key-value head ⌊i⋅g/h⌋. The KV cache stores, per token and layer, 2gdk​ numbers instead of 2hdk​: a reduction of h/g. MQA is g=1.

Multi-head latent attention (DeepSeek). Cache one compressed vector ct​=WDKV​xt​ of size r per token and layer (plus a small shared rotary key), and reconstruct every head's keys and values from it: kt(i)​=WUK(i)​ct​, vt(i)​=WUV(i)​ct​.

Worked example
KV-cache arithmetic by hand

Llama 3.1 8B: 32 layers, 32 query heads, 8 KV heads, dk​=128, bf16 (2 bytes).

  • Per token: 32×2×8×128×2=131,072 bytes = 128 KiB.
  • At 128k tokens: 128KiB×131,072=16 GiB, for a single conversation.
  • With full MHA (32 KV heads) it would be 4×: 64 GiB, more than the model's own 16 GB of weights.

Head size. GPT-2 small has d=768 and 12 heads: dk​=64, and its fused c_attn matrix is 768×2304 (Q, K and V side by side).

Step 1 · split heads from the single-head attention we already have

Take the SelfAttention from Lesson 7.2 and wrap it with a split/concat pair. See code/main.py for a numpy implementation; the logic is:

def split_heads(X, n_heads):
    n, d = X.shape
    d_head = d // n_heads
    return X.reshape(n, n_heads, d_head).transpose(1, 0, 2)  # (heads, n, d_head)

def combine_heads(H):
    h, n, d_head = H.shape
    return H.transpose(1, 0, 2).reshape(n, h * d_head)

One reshape and one transpose. No loop. This is exactly what PyTorch does under nn.MultiheadAttention.

Step 2 · run scaled-dot-product attention per head

Each head gets its own slice of Q, K, V. Attention becomes a batched matmul:

def mha_forward(X, W_q, W_k, W_v, W_o, n_heads):
    Q = X @ W_q
    K = X @ W_k
    V = X @ W_v
    Qh = split_heads(Q, n_heads)         # (heads, n, d_head)
    Kh = split_heads(K, n_heads)
    Vh = split_heads(V, n_heads)
    scores = Qh @ Kh.transpose(0, 2, 1) / np.sqrt(Qh.shape[-1])
    weights = softmax(scores, axis=-1)
    out = weights @ Vh                    # (heads, n, d_head)
    concat = combine_heads(out)
    return concat @ W_o, weights

On real hardware Qh @ Kh.transpose(...) is one bmm. The GPU sees a single batched matmul of shape (heads, N, d_head) × (heads, d_head, N) -> (heads, N, N). Adding heads is free.

Step 3 · Grouped-Query Attention variant

Only the key and value projections change. Q gets n_heads groups; K and V get n_kv_heads < n_heads groups and are repeated to match:

def gqa_project(X, W, n_kv_heads, n_heads):
    kv = split_heads(X @ W, n_kv_heads)       # (kv_heads, n, d_head)
    repeat = n_heads // n_kv_heads
    return np.repeat(kv, repeat, axis=0)      # (n_heads, n, d_head)

At inference this saves memory because only n_kv_heads copies live in the KV cache, not n_heads. Llama 3 70B uses 64 query heads with 8 KV heads — an 8× cache shrink.

Induction heads in GPT-2, found and switched off

Eight sequences of 50 random tokens, each repeated once. For every head: the "induction score", the attention a token in the second copy pays to the token that followed its earlier occurrence. Then the six highest-scoring heads are zeroed (their slice of the input to WO​ set to 0), and, as a control, six random other heads.

import torch, numpy as np
from transformers import GPT2LMHeadModel
torch.manual_seed(0)
lm = GPT2LMHeadModel.from_pretrained("openai-community/gpt2", attn_implementation="eager").eval()
# A random sequence of 50 tokens, then the same 50 again. Nothing in the first half predicts the next token;
# in the second half, a model that can "look up what followed last time" can predict every token.
T = 50
seq = torch.randint(1000, 20000, (8, T))
ids = torch.cat([seq, seq], dim=1)
def per_token_loss(off=()):
    hooks = []
    for l in {l for l, _ in off}:                               # zero chosen heads' outputs before W_o mixes them
        hs = [h for ll, h in off if ll == l]
        def pre(mod, args, hs=hs):
            x = args[0].clone()
            for h in hs:
                x[..., h * 64:(h + 1) * 64] = 0
            return (x,)
        hooks.append(lm.transformer.h[l].attn.c_proj.register_forward_pre_hook(pre))
    with torch.no_grad():
        o = lm(ids, output_attentions=True)
    for hk in hooks:
        hk.remove()
    logp = torch.log_softmax(o.logits[:, :-1], -1).gather(-1, ids[:, 1:, None])[..., 0]
    return -logp, o.attentions
loss, att = per_token_loss()
print(f"loss per token, first copy: {loss[:, :T - 1].mean():.2f} nats;  second copy: {loss[:, T:].mean():.2f} nats")
# Induction score: from a token in the second copy, the attention paid to the token AFTER its earlier occurrence.
A = torch.stack(att)                                           # (layers, batch, heads, 2T, 2T)
q = torch.arange(T, 2 * T); k = q - T + 1
score = A[:, :, :, q[:-1], k[:-1]].mean(dim=(1, 3))            # (layers, heads)
top = torch.topk(score.flatten(), 6)
heads = [(int(i) // 12, int(i) % 12) for i in top.indices]
print("strongest induction heads (layer, head, score):", ", ".join(f"({l},{h}) {s:.2f}" for (l, h), s in zip(heads, top.values)))
print(f"median score over all 144 heads: {score.median():.3f}")
# Switch those heads off and see what happens to in-context copying.
loss_off, _ = per_token_loss(heads)
others = [(int(i) // 12, int(i) % 12) for i in torch.randperm(144)[:6] if (int(i) // 12, int(i) % 12) not in heads]
loss_rand, _ = per_token_loss(others)
print(f"second-copy loss with the 6 induction heads off: {loss_off[:, T:].mean():.2f} nats "
      f"({len(others)} random other heads off: {loss_rand[:, T:].mean():.2f})")

On the first copy GPT-2 loses about 12 nats per token: random tokens cannot be predicted. On the second copy the loss falls to 0.2 nats, meaning it predicts almost every token correctly by copying what followed the same token earlier. from torch.nn.functional import scaled_dot_product_attention

B, n_heads, n_kv_heads, N, d_head = 1, 8, 2, 16, 64
q = torch.randn(B, n_heads, N, d_head)
k = torch.randn(B, n_kv_heads, N, d_head)

# scaled_dot_product_attention dispatches to FlashAttention on CUDA.
# For GQA, pass Q with n_heads and K, V with n_kv_heads; PyTorch handles the repeat.

ref = scaled_dot_product_attention(q, k.repeat_interleave(group, dim=1), v.repeat_interleave(group, dim=1), is_causal=True)

How many heads? Rules of thumb from production models in 2026:

Model size d_model n_heads d_head
Small (~125M) 768 12 64
Base (~350M) 1024 16 64
Large (~1B, Llama 3.2 1B) 2048 32 64
Frontier (~70B) 8192 64 128

d_head almost always lands at 64 or 128. It is the unit of how much one head can "see." Drop below 32 and heads start fighting the scaling factor dhead​​; go above 256 and you lose the "many small specialists" benefit.

In gqa_project, replace np.repeat(kv, repeat, axis=0) with np.tile(kv, (repeat, 1, 1)). The shapes are identical and the code runs. What changes, and why would a model trained with one and loaded with the other give garbage? (Solution B1.)

Industry practice
What's current (2024–2026)
  • GQA is the default in open LLMs. Llama 3, Qwen2.5 and Qwen3, Mistral, Gemma 3 and OpenAI's gpt-oss all use grouped-query attention, typically with 8 or fewer KV heads; serving engines size their KV-cache pools from these numbers.
  • MLA in production MoE models. DeepSeek-V3 and R1 and Moonshot's Kimi K2 use multi-head latent attention, and vLLM and SGLang ship optimised MLA kernels for them.
  • Head count is a kernel choice too. FlashAttention kernels are tuned for head sizes 64, 128 and 256, one reason almost every model picks one of them.

Sources: GQA, DeepSeek-V2 (MLA), Kimi K2 report, vLLM supported models, gpt-oss model card.

medium30 minresearch

Grouped-query attention (GQA) lets several query heads share one key head and one value head. The model then stores fewer keys and values in its cache. With one group, GQA is multi-query attention. With one group for each query head, GQA is standard multi-head attention. Large open models such as Llama 3 use GQA.

Task

Write three functions.

  1. repeat_kv(kv, n_heads) repeats each key or value head so that every query head has a matching head.
  2. grouped_query_attention(x, w_q, w_k, w_v, w_o, n_heads, n_kv_heads) returns the output and the attention weights of GQA self-attention.
  3. mean_pool_kv_heads(w, n_heads, n_kv_heads) turns the key or value projection of a multi-head checkpoint into a GQA projection.

Let H be n_heads, G be n_kv_heads, r=H/G and dhead​=D/H. Head h of a projected array holds the columns h⋅dhead​ to (h+1)⋅dhead​−1, in the same order. Query head h uses key and value group ⌊h/r⌋. So the first r query heads use group 0, the next r use group 1, and so on.

The steps of grouped_query_attention are:

  1. Q=xWq​, K=xWk​, V=xWv​. There are no bias terms.
  2. Split Q into H heads and split K and V into G heads each. Repeat K and V to H heads.
  3. In each head, compute softmax(Qh​KhT​/dhead​​)Vh​. The softmax is over the key axis. There is no mask.
  4. Join the H head outputs in head order, so that the result has shape (B, T, D), and multiply by Wo​.

mean_pool_kv_heads takes a projection with H heads. Group g of the result is the mean of the heads gr to gr+r−1.

All three functions raise ValueError when H is not a multiple of G.

Input and output

Name Type Shape Meaning
kv float array (B, G, T, d_head) keys or values split into G heads
x float array (B, T, D) a batch of B sequences of T tokens with D features
w_q float array (D, D) the query projection
w_k, w_v float array (D, G * d_head) the key and value projections
w_o float array (D, D) the output projection
n_heads int the number of query heads H
n_kv_heads int the number of key and value groups G
w float array (D, H * d_head) a key or value projection with H heads
  • repeat_kv returns a float array of shape (B, H, T, d_head).
  • grouped_query_attention returns a tuple (output, weights). output has shape (B, T, D). weights has shape (B, H, T, T), and weights[b, h, i, j] is the weight that query i gives to key j in head h.
  • mean_pool_kv_heads returns a float array of shape (D, G * d_head).

Constraints

  • 1 <= B <= 4, 1 <= T <= 32, 1 <= G <= H <= 16 and D is a multiple of H.
  • Divide the scores by dhead​​, not by D​.
  • Do not change the input arrays.
  • Use numpy only.

import numpy as np


def softmax(x):
    shifted = x - np.max(x, axis=-1, keepdims=True)
    exp_x = np.exp(shifted)
    return exp_x / np.sum(exp_x, axis=-1, keepdims=True)


def split_heads(x, n_heads):
    B, T, D = x.shape
    return x.reshape(B, T, n_heads, D // n_heads).transpose(0, 2, 1, 3)


def merge_heads(x):
    B, H, T, d_head = x.shape
    return x.transpose(0, 2, 1, 3).reshape(B, T, H * d_head)


def repeat_kv(kv, n_heads):
    n_kv_heads = kv.shape[1]
    if n_heads % n_kv_heads != 0:
        raise ValueError("n_heads must be a multiple of n_kv_heads")
    return np.repeat(kv, n_heads // n_kv_heads, axis=1)


def grouped_query_attention(x, w_q, w_k, w_v, w_o, n_heads, n_kv_heads):
    if n_heads % n_kv_heads != 0:
        raise ValueError("n_heads must be a multiple of n_kv_heads")
    Q = split_heads(x @ w_q, n_heads)
    K = repeat_kv(split_heads(x @ w_k, n_kv_heads), n_heads)
    V = repeat_kv(split_heads(x @ w_v, n_kv_heads), n_heads)
    d_head = Q.shape[-1]
    scores = Q @ np.swapaxes(K, -1, -2) / np.sqrt(d_head)
    weights = softmax(scores)
    return merge_heads(weights @ V) @ w_o, weights


def mean_pool_kv_heads(w, n_heads, n_kv_heads):
    if n_heads % n_kv_heads != 0:
        raise ValueError("n_heads must be a multiple of n_kv_heads")
    D, width = w.shape
    d_head = width // n_heads
    grouped = w.reshape(D, n_kv_heads, n_heads // n_kv_heads, d_head)
    return grouped.mean(axis=2).reshape(D, n_kv_heads * d_head)

Why GQA saves memory

At inference, the model keeps the keys and values of every earlier token in a cache. The size of the cache is proportional to the number of key and value heads. GQA keeps G heads in place of H, so the cache is H/G times smaller. Llama 3 70B uses 64 query heads and 8 groups, so its cache is 8 times smaller than the cache of the same model with full multi-head attention.

Why not always one group

Multi-query attention (G=1) gives the smallest cache. The paper shows that it also loses quality and can make training less stable. A small number of groups gives most of the speed of multi-query attention and a quality near that of multi-head attention.

Uptraining

The paper does not train GQA models from the start. It takes a multi-head checkpoint, mean-pools the key and value heads of each group, and trains for about 5 percent of the original steps. The paper compares mean pooling with other methods, such as the first head of each group, and mean pooling works best.

Multi-head attention runs several small attentions in parallel. Each head sees one slice of the features. The heads are then joined again and mixed by an output projection. The hard part is the reshape: a wrong axis order gives the right shape but the wrong numbers.

Task

Write three functions.

  1. split_heads(x, n_heads) turns x of shape (B, T, D) into an array of shape (B, H, T, d_head), with H = n_heads and d_head = D / H. Head h holds the columns h * d_head to (h + 1) * d_head - 1 of x, in the same order. So split_heads(x, H)[b, h, t, j] equals x[b, t, h * d_head + j].
  2. merge_heads(x) is the inverse. It turns (B, H, T, d_head) into (B, T, H * d_head), so that merge_heads(split_heads(x, H)) equals x.
  3. multi_head_attention(x, w_q, w_k, w_v, w_o, n_heads) returns the output and the attention weights of multi-head self-attention.

The steps of multi_head_attention are:

  1. Q=xWq​, K=xWk​, V=xWv​. There are no bias terms.
  2. Split Q, K and V into heads.
  3. In each head, compute softmax(Qh​KhT​/dhead​​)Vh​. The softmax is over the key axis. There is no mask.
  4. Merge the head outputs and multiply by Wo​.

import numpy as np


def softmax(x):
    shifted = x - np.max(x, axis=-1, keepdims=True)
    exp_x = np.exp(shifted)
    return exp_x / np.sum(exp_x, axis=-1, keepdims=True)


def split_heads(x, n_heads):
    B, T, D = x.shape
    if D % n_heads != 0:
        raise ValueError("d_model is not divisible by n_heads")
    d_head = D // n_heads
    return x.reshape(B, T, n_heads, d_head).transpose(0, 2, 1, 3)


def merge_heads(x):
    B, H, T, d_head = x.shape
    return x.transpose(0, 2, 1, 3).reshape(B, T, H * d_head)


def multi_head_attention(x, w_q, w_k, w_v, w_o, n_heads):
    q = split_heads(x @ w_q, n_heads)
    k = split_heads(x @ w_k, n_heads)
    v = split_heads(x @ w_v, n_heads)
    d_head = q.shape[-1]
    scores = q @ np.swapaxes(k, -1, -2) / np.sqrt(d_head)
    weights = softmax(scores)
    concat = merge_heads(weights @ v)
    return concat @ w_o, weights

Why the transpose is necessary

numpy stores an array in row-major order. A reshape keeps that order and only changes how the numbers are grouped. The reshape of (B, T, D) to (B, T, H, d_head) is safe, because it only cuts the last axis into blocks. A direct reshape to (B, H, T, d_head) groups the numbers of several tokens into one head. The shape is correct, but each head then mixes tokens with features. The transpose moves the head axis without a change to any value.

Why heads use neighbor columns

Any fixed assignment of columns to heads gives an equal model, because the projection matrices can learn any order. The block layout is the convention of the lesson and of most libraries. It matters when you load trained weights: a strided layout reads the trained weights in the wrong order.

The cost of more heads

The number of parameters does not change with H. Each head has a smaller d_head, and the scale dhead​​ changes with it. The weights tensor has shape (B, H, T, T), so memory for the weights grows with the number of heads.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Group g of the new projection is the mean of the consecutive heads g r to g r + r - 1, where r is the number of query heads per group, taken over the columns of the projection matrix. The cache holds keys and values for 8 heads instead of 64, so that memory falls by a factor of eight. The mean of several heads is not a head the model was trained with, so quality drops until a short continued training run adapts the query heads to their shared group.

The pooling.

def mean_pool_kv_heads(w, n_heads, n_kv_heads):
    if n_heads % n_kv_heads:
        raise ValueError("query heads must be a multiple of kv heads")
    D, cols = w.shape
    d_head = cols // n_heads
    r = n_heads // n_kv_heads
    grouped = w.reshape(D, n_kv_heads, r, d_head)
    return grouped.mean(axis=2).reshape(D, n_kv_heads * d_head)

The reshape puts the groups first and the heads inside a group next, because the heads of one group are consecutive blocks of columns. Reshaping as (D, r, G, d_head) pools heads that are G apart, which gives a correct shape with the wrong groups. The mean, not the sum, keeps the scale of the projected keys close to the original, so the attention scores stay in range.

The memory factor.

The cache stores one key and one value vector per layer, per head, per token. The number of query heads does not enter. Going from 64 to 8 key and value heads divides the stored bytes per token by eight, which is the example the multi-head lesson gives for a large open model. Weights fall much less, because the query and output projections are unchanged and only the key and value projections shrink.

Why it needs training.

The query heads were trained against their own key heads. After pooling, eight query heads read one averaged key head that none of them saw in training. The lesson's lineage describes converting multi-head checkpoints to grouped-query checkpoints as a recipe with a continued training step; the pooling gives a starting point close to the original, and the uptraining recovers most of the quality. Serving the pooled weights directly works, but the eval must be rerun before shipping.

What does not change.

The head size, the query projection, the output projection and the attention function itself are the same. Only the key and value projections and the repeat inside attention change, so the rest of the loader and the block are untouched.

Plausible wrong answers.

  • "Pooling is lossless since the mean preserves the average key." The individual heads are lost; the queries were trained against them, so quality drops until the model is adapted.
  • "The cache shrinks by the ratio of query heads to total heads." Only key and value heads live in the cache; the factor is the old count of key and value heads over the new count.
  • "Sum the heads so no information is lost." The sum scales the keys by the group size and pushes the scores out of the range the softmax was trained for.

Short answer. Tiling repeats the whole block of groups, so query head h reads group h modulo the number of groups. The convention is that consecutive query heads share a group: head h reads group h floor-divided by the repeat factor. Repeat each group in place along the head axis instead of tiling the block.

The two layouts.

With four query heads and two groups the repeat factor is two. The correct expansion gives the sequence of groups 0, 0, 1, 1: the first two query heads share group zero and the next two share group one. Tiling gives 0, 1, 0, 1, so heads one and two swap partners. Every head still has a key and value tensor of the right shape, which is why no shape check fails, but half the heads attend with the wrong keys.

The fix.

def repeat_kv(kv, n_heads):
    B, G, T, d_head = kv.shape
    if n_heads % G:
        raise ValueError("query heads must be a multiple of kv heads")
    r = n_heads // G
    return np.repeat(kv, r, axis=1)

np.repeat along the group axis copies each group r times next to itself, which produces the floor-division mapping. The divisibility check belongs here, because a non-integer repeat factor silently truncates and drops heads.

Why the mapping is a convention and not a choice.

The projection weights of a trained checkpoint were learned under one mapping. The multi-head lesson describes the lineage: multi-head attention with one group per head, multi-query attention with a single shared group, and the grouped form in between with the first r heads on group zero. A model converted from multi-head weights by pooling consecutive heads only works if attention reads the groups in the same consecutive order.

Why it exists.

Only G key and value heads live in the cache instead of H, so the cache shrinks by the factor H / G while quality stays close to standard multi-head attention. The lesson's example is a large open model that pairs 64 query heads against only 8 shared groups.

Plausible wrong answers.

  • "Tile and repeat give the same result when the shapes match." They give different head-to-group assignments; only one matches the trained weights.
  • "Average the groups and use one key tensor for all heads." That turns the model into multi-query attention with weights it was not trained for.
  • "The mapping does not matter because attention is permutation invariant." Attention is invariant over keys within a head, not over which key head a query head reads.

Short answer. The softmax normalizes over the query axis instead of the key axis, so each column sums to one and a query's weights no longer form a distribution over the keys. Defect one: the softmax axis.

Scores have shape batch, heads, queries, keys. Each query row must become a distribution over the keys, so the softmax runs over the last axis. Over the second-to-last axis each key column sums to one across queries instead, and the weighted sum of values no longer means "what this token attends to".

Defect two: the output projection.

Each head computes attention in its own subspace and the heads never interact during the attention computation itself. The concatenation followed by the output matrix is where the heads mix. Without it, the model's output is a stack of independent per-head results, the next layer sees a different function than the one the weights were trained for, and a loaded checkpoint produces noise.

def multi_head_attention(x, w_q, w_k, w_v, w_o, n_heads):

    K = split_heads(x @ w_k, n_heads)

Short answer. The reshape alone reinterprets memory. It keeps the bytes in order and relabels them, so the head axis cuts across tokens and features instead of slicing the feature axis. The correct split reshapes to batch, tokens, heads, head size and then transposes the token and head axes, so that head h holds a contiguous block of d_head neighbor columns for every token.

What the bug does.

Row-major memory lists features of token zero, then features of token one, and so on. Reshaping straight to batch, heads, tokens, head size slices that flat list into equal pieces. The first "head" then holds the first T times d_head numbers, which are the complete feature vectors of the first few tokens, not a slice of every token. Shapes agree. Numbers are scrambled.

The fix.

def split_heads(x, n_heads):
    B, T, D = x.shape
    if D % n_heads:
        raise ValueError("features must divide into heads")
    d_head = D // n_heads
    return x.reshape(B, T, n_heads, d_head).transpose(0, 2, 1, 3)


def merge_heads(x):
    B, H, T, d_head = x.shape
    return x.transpose(0, 2, 1, 3).reshape(B, T, H * d_head)

Reshape to batch, tokens, heads, head size first, which only splits the last axis. Then transpose so the head axis comes before the token axis. The merge is the same two operations in reverse. One reshape and one transpose, no loop; that is also what the framework version does under the hood.

The strided variant of the bug.

A second wrong version gives head h the columns h, h + H, h + 2H and so on. That slices the feature axis, so the per-head attention runs, but it does not match the convention that a head owns one contiguous block of columns, and a checkpoint trained with the standard layout no longer loads into it.

How to test it.

merge_heads(split_heads(x, H)) must return x exactly, and split_heads(x, H)[b, h, t, j] must equal x[b, t, h * d_head + j]. The second check is the one that fails for both wrong versions.

Plausible wrong answers.

  • "Reshape is the same as transpose for equal sizes." Reshape relabels memory in place; transpose reorders it.
  • "Any split works as long as merge undoes it." The attention tests and any loaded checkpoint depend on each head owning one block of neighbor columns.
  • "Loop over heads and slice columns." It is correct but slow; the reshape and transpose give the same result in two operations.

Follow-ups an interviewer may ask.

  • (level 2) Why does the round-trip test catch the plain reshape bug? Expected: merge_heads transposes the head and token axes before it reshapes, so it does not undo a plain reshape and the features come back in a different order; only a merge written as a plain reshape would hide the bug.
  • (level 2) What does the scale factor become after the split? Expected: the square root of the head size, not of the full feature dimension.
  • (level 3) After the split, how does attention run for all heads at once? Expected: as one batched matmul over the leading batch and head axes, so adding heads costs no extra kernel launches.

Defend a designDesign the attention stack of a new 70B-class decoder that must serve 128K-token contexts on a single 80 GB accelerator at batch size one. Cover the head layout, the positional scheme, the kernel, and the memory arithmetic that ties them together.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. Start from the memory, because it decides the rest. With 8 key-value heads, 80 layers and a head size of 128 in a 16-bit type, the stored keys and values cost 4096 bytes per token per layer, about 10 GiB at 32K and 40 GiB at 128K before a single weight is loaded. So the head layout is grouped-query or latent attention, the stored type is reduced to FP8 to halve those bytes, the positional scheme is rotation with base scaling so that the model reaches 128K without a position table, and the kernel is a tiled one so that the N by N scores never touch main memory. Then count again: at 16 bits the weights of a 70B-class model alone are larger than the 80 GB card, so the weights also need a 4-bit type before the cache and the activations can fit beside them.

Head layout.

Plain multi-head attention with 64 key-value heads at this scale would hold about 8 times more, about 80 GiB at 32K, which is the whole card. Grouped-query with 8 key-value heads is the production default and keeps nearly full quality. If the memory still does not close, latent attention compresses the keys and values to a low-rank vector and pays FLOPs at each step to decompress. The query heads stay at 64 with a head size of 128 in either case.

The memory table.

per token per layer = 2 * n_kv_heads * d_head * bytes
                    = 2 * 8 * 128 * 2 = 4096 bytes (4 KiB)
32K context         = about 10 GiB
128K context        = about 40 GiB

Halve the bytes per value with an FP8 cache and the 128K figure halves. Then add the weights. At 16 bits a 70B-class model needs two bytes per parameter, which is more than the whole 80 GB card before any cache is stored. At 8 bits the weights still fill most of the card. Only a 4-bit weight type leaves room for the FP8 cache at 128K and for the activations. Batch size one is the stated requirement; every additional concurrent request adds another cache.

Positional scheme.

Rotation of the queries and keys, with a base scaled for the target length through NTK-aware scaling or YaRN. It adds no parameters, encodes relative distance, and the lesson's reference family reached 128K from 8K this way. A learned table would need 128K rows and would stop there. Linear-bias attention is a valid training-time alternative with strong extrapolation, but rotation gives a cleaner knob and matches the ecosystem.

Kernel.

Attention is memory-bound from about 2K tokens, so a tiled kernel is not optional at 128K. Use the current tiled implementation for the hardware, with FP8 where the generation supports it, and keep the training kernel on the version that has a backward pass.

What to measure before committing.

  1. Perplexity at the target length and at the original short length after the long-context fine-tune.
  2. Peak memory at 128K with the quantized weights, the cache and the activations on the card, and the quality loss from the 4-bit weights.
  3. Time per token at 128K against 8K, to confirm the kernel and the cache behave linearly.

Plausible wrong answers.

  • "Use full multi-head attention for quality; memory is cheap." At 128K the full cache alone exceeds the card.
  • "The sinusoid handles any length, so the position scheme is solved." The formula extends but the model never saw those phases; rotation with base scaling is what reached 128K in practice.
  • "Skip the tiled kernel on a quality model because it changes the output." It is exact up to 16-bit reordering and it is what makes long context affordable.

Follow-ups an interviewer may ask.

  • (level 3) Why not pick linear-bias attention for its extrapolation? Expected: it is a fair choice for a new model, but rotation has the long-context tooling and a base to scale, and neither can be swapped after training.
  • (level 4) The product later asks for batch size 8 at 128K. What changes? Expected: the cache multiplies by 8, so latent attention, a smaller stored type, a shorter maximum length or more cards; the weights do not change.
  • (level 4) Grouped-query from scratch or convert a multi-head checkpoint? Expected: from scratch for a new model; conversion with a fine-tune is for existing checkpoints and needs a quality check.
  • (level 4) Where does Flash Attention stop helping? Expected: it removes the N by N traffic; it does not shrink the cache, which still grows linearly with the context, so the cache math dominates at 128K.

Explain the mechanismA paper draft shows attention heatmaps as proof that the model "reasons over the right tokens". You are the reviewer. What do you say about the heatmaps, and what would convince you that a given head does something specific?

Level 3 of 4 · about 10 minutes to answer well.

Short answer. Attention weights are a distribution over positions, and on their own they are not an explanation: for some tasks they can be permuted or replaced by arbitrary alternatives without changing the prediction, so a heatmap shows where mass went, not that it mattered. Ask for an ablation or a counterfactual, zero or shuffle the head and show that the prediction moves. The head roles that have survived probing are specific and testable: heads that attend to the previous token, copy heads, and induction heads that find an earlier occurrence of the current token and copy what followed it.

The caveat from the literature.

A 2019 study showed that on some tasks the attention distribution can be permuted, or swapped for an adversarial alternative, while the output stays the same. The lesson's rule follows: never report attention weights as evidence of reasoning without an ablation or a counterfactual check. Reviewers like heatmaps because they are easy to read; that is a reason to be careful, not a reason to accept them.

What a head can show you.

The inspection hook in the lesson's block returns the per-head weights of shape (B, H, T, T). In a trained model the patterns differ by head: some attend to the token just before, some to the start of the sequence, some spread almost uniformly. Those are descriptions. Turning a description into a claim takes an intervention.

The evidence that convinces.

  1. Ablation. Zero the head's output or replace its weights with a uniform row and measure the change in loss or in the specific prediction. A head that matters moves the number.
  2. Counterfactual input. Change the token the heatmap points at and show that the output changes in the direction the story predicts.
  3. A behavioral test for the claimed role. For an induction head, feed a random token sequence repeated twice and show that the head attends from each token to the token that followed its first occurrence, and that ablating the head removes the copying.
  4. Replication across seeds and prompts. One heatmap on one example is an anecdote.

What to write in the review.

Ask the authors to keep the heatmaps as illustration and to add the intervention results as the evidence. If the ablation does not move the prediction, the heatmap was decoration.

Plausible wrong answers.

  • "A high weight means the token caused the output." Weight shows where the lookup went; causation needs an intervention.
  • "Average the heads to get the model's attention." Heads do different things; the average hides the roles and still is not evidence.
  • "If the heatmap matches human intuition, the model reasons like a human." Agreement with intuition is not a test; the permutation result shows intuitive maps can be irrelevant to the output.

Follow-ups an interviewer may ask.

  • (level 3) A head attends almost uniformly across positions. What does that tell you? Expected: little on its own; it may carry an average or nothing, and only an ablation says which.
  • (level 3) Describe a test for an induction head in one sentence. Expected: repeat a random token sequence and check that the head attends from each token to the token after its earlier occurrence, with ablation removing the copy behavior.
  • (level 4) Why can the weights be permuted without changing the output? Expected: the values at the attended positions may carry near-identical information, other heads may be redundant, and later layers can compensate.
  • (level 4) What replaces the heatmap as the headline figure? Expected: the change in loss or in the target probability under ablation and counterfactual edits, with a band across seeds.

Where it is taught. The attention mechanism lesson states the explanation trap, the multi-head lesson lists the probed head roles, and the attention capstone exposes the weights for inspection.

Weigh a trade-offYou are choosing the attention variant for a new 70B-class decoder: full multi-head, multi-query, grouped-query, or MLA with its compressed latent. What does each one do to the memory that decoding holds per token, and what do you give up with each?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. All four keep the same number of query heads; they differ in how many key and value heads exist, and only the keys and values are stored during decoding. Multi-query shares one key-value head across every query head, the smallest cache and some quality loss. Grouped-query uses a group of key-value heads, cuts the cache by n_heads / n_kv_heads and keeps nearly full quality, which is why it is the default. Latent attention compresses keys and values to a low-rank vector and decompresses at attention time, so it saves even more memory and pays extra FLOPs.

The lineage.

Variant Query heads Key-value heads Cache cost
Multi-head N N full
Multi-query N 1 smallest, quality loss
Grouped-query N G, for example N / 8 shrinks by N / G
Multi-head latent N compressed to a low-rank latent smaller still, more compute

What the cache holds.

Per layer and per token, the stored bytes are 2 * n_kv_heads * d_head * dtype_size, where the 2 counts the key and the value. The query of a past token is never needed again, so it is not stored. A 70B-class model with 80 layers, a head size of 128 and 8 key-value heads in a 16-bit type holds 4096 bytes per token per layer, about 10 GiB for a 32K context and 40 GiB at 128K. The same model with 64 key-value heads would hold 8 times more, about 80 GiB at 32K. That is the whole memory of a large accelerator spent on one request.

The quality side.

Grouped-query keeps the query heads, so each head still asks its own question; it only shares the answers it can look up. The published work converts trained multi-head checkpoints to grouped-query with a fine-tune and reports nearly full quality. Multi-query shares a single answer set across all heads and loses more. Latent attention trades compute for memory: the latent must be projected back to keys and values on every step.

Grouped-query in code.

Only the key and value projections change. They produce n_kv_heads heads, and each is repeated to match the query heads:

def gqa_project(X, W, n_kv_heads, n_heads):
    kv = split_heads(X @ W, n_kv_heads)
    repeat = n_heads // n_kv_heads
    return np.repeat(kv, repeat, axis=0)

At inference only the n_kv_heads copies live in the cache, not the repeated ones.

The pick.

For a 70B decoder with long contexts to serve, grouped-query with a small group is the safe default. Latent attention is the choice when memory is the binding constraint and you accept the compute cost and the engineering.

Plausible wrong answers.

  • "Grouped-query reduces the compute of attention." The scores are still computed for every query head; the saving is in the stored keys and values.
  • "Multi-query is free." It shares one answer set across all heads and the lesson records a quality loss.
  • "The cache size follows the parameter count." It follows the key-value heads, the layers, the head size and the data type.

Follow-ups an interviewer may ask.

  • (level 2) Which numbers set the stored bytes per token? Expected: layers, key-value heads, head size and bytes per value, times 2 for the key and the value; the parameter count does not enter.
  • (level 3) Why does latent attention cost more compute per step? Expected: the stored latent has to be projected back to full keys and values at every decode step before the scores are computed.
  • (level 3) Can you move an existing multi-head checkpoint to grouped-query? Expected: yes, the grouped-query paper converts trained checkpoints and fine-tunes; measure quality on your own eval before you ship.
  • (level 4) The product wants 128K contexts at batch size one on a 40 GB card. Which variant and what else? Expected: grouped-query alone already fills the card at 128K, so latent attention or a smaller key-value type, and the weights still need their own memory.

Where it is taught. The multi-head attention lesson gives the variants and the grouped-query code, and the KV cache lesson does the memory arithmetic.

Explain the mechanismYou change an attention layer from one head to eight heads and keep the model width fixed. What happens to the parameter count, to the compute, and to what the layer can represent? And why do practitioners refuse to make heads narrower than about 32?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The parameters do not change: the four projections are still d_model by d_model, and the heads are only a reshape of the same matrices into slices of width d_model / n_heads. The compute stays about the same because the per-head attention runs as one batched matmul over the head axis. Each head can specialize on its own relation, and the output projection is where the heads mix. The lesson's rule of thumb keeps a head at a width of 32 or more, because a narrower head sees too few dimensions, and above 256 you lose the benefit of many small specialists, while the sqrt scaling itself keeps the score variance constant at any width.

Split, attend, combine.

def split_heads(X, n_heads):
    n, d = X.shape
    d_head = d // n_heads
    return X.reshape(n, n_heads, d_head).transpose(1, 0, 2)

def combine_heads(H):
    h, n, d_head = H.shape
    return H.transpose(1, 0, 2).reshape(n, h * d_head)

Project X to Q, K and V, split each into heads, run scaled dot-product attention per head, stack the heads back and multiply by the output matrix W_o. The GPU sees the per-head scores as a single batched matmul of shape (heads, N, d_head) times (heads, d_head, N). Adding heads adds batch entries, not weights.

Why the output projection matters.

The heads never talk during the attention step itself; they work on different subspaces. W_o, of shape (d_model, d_model), is where their outputs mix. Without it the heads could only recombine through later layers and the block would be artificially constrained.

What heads learn.

Probing work from 2019 to 2024 found distinct roles: heads that attend to the previous token, copy heads, heads that track named entities, and induction heads, the pairs that detect an earlier occurrence of the current token and copy what followed it, which underlie in-context learning. One head would have to smear all of these into one softmax.

Picking the head width.

Model size d_model n_heads d_head
Small (about 125M) 768 12 64
Base (about 350M) 1024 16 64
Large (about 1B) 2048 16 128
Frontier (about 70B) 8192 64 128

The head width lands at 64 or 128 almost every time. It is the unit of how much one head can see.

The production implementation.

One linear layer maps D to 3D and is sliced into Q, K and V. Three separate layers compute the same thing, because three matmuls by (D, D) weights equal one matmul by a stacked (3D, D) weight, but the fused layer launches one kernel instead of three.

Plausible wrong answers.

  • "More heads mean more parameters." The projections keep their size; the heads are a reshape of the same matrices.
  • "Heads exchange information while they attend." They work on separate subspaces; mixing happens only in the output projection and in later layers.
  • "Use as many heads as the width allows." Heads narrower than the lesson's rule of thumb of 32 see too little; the common widths are 64 and 128.

Follow-ups an interviewer may ask.

  • (level 2) Why is the fused QKV projection faster if the math is identical? Expected: one kernel launch and one matmul instead of three; the stacked weight gives the same result.
  • (level 3) What goes wrong if you remove the output projection? Expected: the heads can only mix through later layers, so the block loses expressive power even though the shapes still work.
  • (level 3) What is an induction head? Expected: a pair of heads that finds a previous occurrence of the current token and copies the token that followed it; the circuit behind in-context learning.
  • (level 4) Grouped-query attention keeps the query heads and shrinks something else. What and why? Expected: the key and value heads, because only they live in the decode-time cache; fewer of them cut cache memory while the query heads keep quality.

Read the codeTwo versions of a head split landed in review. X has shape (n, d) with n tokens and d features. python def split_a(X, n_heads): n, d = X.shape d_head = d // n_heads return X.reshape(n, n_heads, d_head).transpose(1, 0, 2) def split_b(X, n_heads): n, d = X.shape d_head = d // n_heads return X.reshape(n_heads, n, d_head) Both return a tensor of shape (n_heads, n, d_head) and both run without error. Which one is right, what does the other one do to the data, and what test would have caught it?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. The first version is the right one: split_a groups the d features of each token into n_heads slices of width d_head and then moves the head axis to the front. split_b reads the same memory in the wrong order: it cuts the flat buffer into n_heads equal chunks and calls each chunk a head, so one head now holds runs of consecutive tokens, a chunk can end inside a token, and the columns no longer line up with the projection that produced them. The test is the round trip: combining the split must return X exactly, and head h must equal the column slice X[:, h * d_head:(h + 1) * d_head].

What the shapes mean.

After the projection, each token's d features are the concatenation of n_heads groups of d_head features. A head is a column slice across every token. The reshape (n, n_heads, d_head) keeps each token's row intact and only regroups its columns; the transpose then puts the head axis first so that the per-head attention becomes a batched operation over heads.

Why the wrong version still runs.

Both tensors have n * d elements, so NumPy and PyTorch are happy to reinterpret the memory. A reshape of a contiguous array does not move data; it only changes how the flat buffer is indexed. split_b therefore cuts the buffer into n_heads equal chunks. When n is divisible by n_heads, head zero holds the first n / n_heads tokens with all of their features; otherwise a chunk ends inside a token. The scores inside that head compare the wrong vectors, and the model trains to something, which is why this bug can survive for weeks.

The combine must be the exact inverse.

def combine_heads(H):
    h, n, d_head = H.shape
    return H.transpose(1, 0, 2).reshape(n, h * d_head)

Transpose back first, then reshape. Reshaping directly from (h, n, d_head) to (n, h * d_head) makes the same mistake in reverse, and the output projection sees scrambled features.

The production shape contract.

With a batch dimension the intermediate tensors are (B, H, T, d_head). The head dimension sits next to the batch so that the accelerator treats the per-head attention as B * H independent problems, and d_head stays last so that Q @ K.transpose(-2, -1) contracts it. The constraint is D % H == 0.

Tests that catch it.

  1. combine_heads(split_heads(X)) == X.
  2. split_heads(X)[h] == X[:, h * d_head:(h + 1) * d_head] for every head.
  3. Single-head attention on the slice equals the head's output from the batched path.

Plausible wrong answers.

  • "Reshape and transpose are interchangeable when the shapes match." A reshape reinterprets memory and a transpose moves axes; the order decides which elements land together.
  • "If it runs and the loss falls, it is correct." The loss falls for the wrong layout too; only the round-trip and slice tests prove the layout.
  • "Each head needs its own weight matrix, so the split is irrelevant." The heads are slices of one projection; the split is what defines them.

Follow-ups an interviewer may ask.

  • (level 2) Why does a reshape never raise here? Expected: it only reinterprets a buffer with the same number of elements; the data is not checked for meaning.
  • (level 2) Why must d_head stay the last axis? Expected: the score matmul contracts the last axis of Q with the second-to-last of the transposed K.
  • (level 3) How does grouped-query attention reuse this code? Expected: split K and V into n_kv_heads heads and repeat each along the head axis n_heads // n_kv_heads times to match Q.
  • (level 3) A model trained with the wrong split reaches a decent loss. Why does that not clear the bug? Expected: the projections learned to work with the scrambled layout, but the heads no longer correspond to subspaces of the input and any pretrained weights or exported checkpoints will be wrong.
