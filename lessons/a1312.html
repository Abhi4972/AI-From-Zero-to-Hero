In plain words first
The idea in one line

Roots are deprecated in MCP 2026-07-28 and were never a security sandbox. Put scope in visible tool arguments or resource URIs, authorize it on the server, and use MRTR when a tool genuinely needs user input. The user sees the decision, the model sees the handle, and any server instance can process the retry.

Terms you'll hear
Term Meaning in 2026-07-28
Roots Deprecated informational workspace hints, not authorization or sandboxing
Explicit scope Workspace, directory, or resource handle visible in request arguments
Containment Normalized path-component check that keeps a target inside a boundary
Elicitation Client feature for obtaining user input during an MCP operation
Form mode In-band structured user input using a restricted flat schema
URL mode Out-of-band interaction for sensitive or external workflows
MRTR Stateless input-required result followed by a fresh retry
requestState Opaque state echoed exactly and integrity-checked by the server
Decline Explicit user refusal
Cancel Dismissal or incomplete interaction without approval

Two Problems That Look Similar

In plain words first

"Delete the old TPS report" raises two questions. Which files or notes is this tool allowed to touch? And which of the three matching notes did the user mean? The first is about scope and permission. Older MCP had "Roots", a list of folders the client suggested to the server, and they were never a security boundary. MCP 2026-07-28 deprecates them: scope should be a visible argument that the server checks itself. The second question needs the user. With elicitation, the server asks the user a short form question through the client ("which one, and are you sure?"), and in 2026-07-28 that request travels as an input_required round, like Sampling in Lesson 13.11. This lesson runs a delete tool that asks the user to choose and confirm, with every possible answer. It then shows why a naive path check lets a request escape its workspace.

A notes tool receives this request: "Delete the old TPS report."

The server must answer two different questions.

  1. Which workspace may this operation touch?
  2. Which of three matching notes did the user mean?

The first is scope and authorization. The second is interactive disambiguation. Mixing them leads to dangerous designs, such as treating a client-provided folder as proof that the caller may delete everything inside it.

Roots Are a Migration Surface

Earlier MCP revisions let a client advertise Roots and notify a server when the list changed. Roots were informational guidance. They did not constrain what the server process could read, did not authorize the caller, and did not create an operating-system sandbox.

MCP 2026-07-28 deprecates roots/list and notifications/roots/list_changed for new designs. Prefer one of these explicit replacements:

  • A workspaceUri or directory tool argument when scope varies per call.
  • A resource URI when the operation already targets a resource.
  • Server configuration when one deployment owns one fixed workspace.
  • A process sandbox or jailed filesystem when code must be technically unable to escape.

If an existing 2026-07-28 integration still needs roots/list during the deprecation window, the server embeds it in MRTR inputRequests. It must not send a live reverse request. That is a migration adapter; new handlers should accept explicit scope instead.

The model can see and repeat an explicit handle. Hidden transport-session scope is harder to inspect, replay, audit, and route.

The three-layer rule

An explicit URI still does not authorize itself. Enforce all three layers:

  1. Authorization: Is this authenticated principal allowed to use this workspace?
  2. Containment: Does the normalized target URI stay inside the authorized workspace boundary?
  3. Sandbox: Can the operating system stop a compromised server from escaping anyway?

The runnable server keeps an allowlist of authorized workspace URIs, normalizes percent-encoded paths, checks a real path-component boundary, and re-checks containment immediately before deletion.

Naive string-prefix checks are wrong:

allowed:   file:///work/notes
attacker:  file:///work/notes-evil/secret.md
traversal: file:///work/notes/%2e%2e/private.md

Both hostile paths start with a misleading string. Normalize first, then compare path components. A production filesystem server must also defend against symbolic-link races and platform-specific path semantics.

Elicitation Still Exists, but Delivery Changed

Elicitation is the current client feature for collecting user input during tools/call, prompts/get, or resources/read. The method name remains elicitation/create. What changed is the direction of the wire flow.

A 2026-07-28 server does not send a reverse JSON-RPC request. It returns an InputRequiredResult:

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "resultType": "input_required",
    "inputRequests": {
      "delete_choice": {
        "method": "elicitation/create",
        "params": {
          "mode": "form",
          "message": "Choose one matching note and confirm deletion.",
          "requestedSchema": {
            "type": "object",
            "properties": {
              "note_id": {
                "type": "string",
                "enum": ["note-3", "note-7", "note-14"]
              },
              "confirm": {"type": "boolean"}
            },
            "required": ["note_id", "confirm"]
          }
        }
      }
    },
    "requestState": "integrity-protected-delete-state"
  }
}

The host renders the form. The user can accept, explicitly decline, or dismiss it. The client then retries the original tools/call with a fresh id:

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "notes_delete",
    "arguments": {
      "workspaceUri": "file:///Users/alice/Documents/Notes",
      "title": "TPS report"
    },
    "inputResponses": {
      "delete_choice": {
        "action": "accept",
        "content": {"note_id": "note-14", "confirm": true}
      }
    },
    "requestState": "integrity-protected-delete-state",
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {
        "elicitation": {"form": {}}
      }
    }
  }
}

There is no protocol session between the two calls. The server verifies the echoed state, validates the response against the expected schema, checks that the selected note was in the signed candidate set, re-authorizes the workspace, re-checks containment, and then deletes.

Capability Negotiation Is Per Request

A client that supports form-mode elicitation declares:

{
  "io.modelcontextprotocol/clientCapabilities": {
    "elicitation": {"form": {}}
  }
}

An empty elicitation capability, "elicitation": {}, remains equivalent to form-only support for compatibility. Explicit "elicitation": {"form": {}} also supports form mode. A URL-only declaration, "elicitation": {"url": {}}, does not. The server must not embed a mode absent from the current request's capabilities, even if an earlier request advertised it.

Every request also carries io.modelcontextprotocol/protocolVersion. A missing or non-string version returns -32602. An unsupported string returns -32022 with exact supported and requested data. Missing or URL-only elicitation support returns -32021 with data.requiredCapabilities set to {"elicitation":{"form":{}}}.

An envelope without a JSON-RPC id is a notification. Process it without emitting a JSON-RPC success or error response. On Streamable HTTP, an accepted notification receives 202 Accepted with no body.

clientInfo should be included for diagnostics, but it is self-reported and cannot identify the user for authorization.

The server implements server/discover and returns supportedVersions, capabilities, ttlMs, and cacheScope with resultType: "complete". It does not advertise Roots for this modern design. Because it advertises tools, it also implements mandatory tools/list. That result returns the deterministic notes_delete descriptor, a valid object inputSchema, server identity metadata, and public cache hints.

Form Mode

Form mode uses a restricted JSON Schema designed for usable dialogs. The root is an object and its properties are flat primitive fields or supported enum arrays. Deeply nested objects and general-purpose document schemas do not belong in a confirmation dialog.

Use form mode for:

  • choosing one of several candidates;
  • confirming a destructive operation;
  • collecting non-sensitive preferences;
  • gathering a small number of values the user, not the model, must decide.

Do not use form mode for passwords, API keys, access tokens, or payment credentials. Those secrets would pass through the MCP client and could reach logs or model context.

The server validates the returned content again. Client-side form validation improves UX but does not create trust.

URL Mode

URL mode sends a secure web URL for an out-of-band interaction:

{
  "method": "elicitation/create",
  "params": {
    "mode": "url",
    "message": "Connect the report service to continue.",
    "url": "https://mcp.example.com/connect/report-service"
  }
}

Use it when sensitive information must go directly to a server-controlled web flow, such as third-party authorization. The client shows the full destination and obtains consent before opening it. It must not prefetch the URL.

An accept response means the user agreed to open the URL. It does not prove the external flow completed. On retry, the server checks its own state and either completes or returns another input_required result.

URL elicitation is not a replacement for authorization between the MCP client and MCP server. It is for an external interaction the MCP server needs to perform on the user's behalf. The server must bind the browser user to the same authenticated principal that began the MCP operation.

Response Branches

Treat the actions as product decisions, not aliases:

Action Meaning Safe server behavior
accept User submitted the interaction Validate content and continue
decline User explicitly refused Return a complete, non-error refusal outcome
cancel User dismissed or could not finish Stop safely and allow a later retry

Never interpret missing content as consent. Never convert decline into a repeated prompt loop.

Protecting Destructive MRTR State

The candidate list cannot live only in a prompt or unsigned Base64 value. A client controls everything it sends back.

The lesson signs a state payload containing:

  • authenticated principal;
  • originating method;
  • digest of workspaceUri and title;
  • allowed note ids shown in the form;
  • operation phase;
  • short expiry.

Before mutation, the server also checks the live note record. This catches deletion races and a target moved outside the workspace after the form was shown.

For a one-time financial or irreversible action, HMAC alone does not prevent a valid state from being replayed within its expiry. Store and consume a nonce exactly once in a replay store shared by every handler instance. The lesson injects a bounded, TTL-pruned store and holds its atomic claim while performing the in-memory deletion. A production database should couple the nonce claim and mutation in one transaction or equivalent conditional-write boundary.

Validate the interaction before claiming the nonce. A malformed response or cancel performs no mutation and leaves the state retryable until expiry. An explicit decline is terminal, so the lesson consumes the nonce without deleting anything.

The same idea as a formula

Containment. For a workspace W and a requested relative path x, let ρ(⋅) resolve .. segments and symbolic links to a real absolute path. The request is in scope only if

ρ(W/x) lies under ρ(W)(path components, not string prefix),
and the caller is authorised for W. A string-prefix test on the unresolved path fails twice: symlinks change the real target, and /ws-evil starts with /ws.

Confirmation binding. A destructive action proceeds only if

a=accept,confirm=true,choice∈C(args),principal,H(args),C,expiry match the signed state,
where C(args) is the candidate set the server offered for these arguments. decline and cancel are distinct outcomes that never delete.

Worked example
Five paths and four answers
  • notes/a.md resolves inside the workspace: allowed.
  • notes/link.md looks inside, but the link points to ../secret.txt: a string check says yes, the resolved check says no.
  • ../ws-evil/x.md normalises to /tmp/.../ws-evil/x.md, whose string starts with /tmp/.../ws: string check yes, component check no.
  • Answers to "which note, and confirm?": accept + n-102 + confirm → delete. accept + confirm = false → keep. decline → keep, the user said no. cancel → keep, the user dismissed the dialog; the host may ask again later.
Check your mental model
  • ✗ "Roots stop a server from reading outside the listed folders."
    ✓ They were hints; only the server's own checks and the OS sandbox enforce anything.
  • ✗ "Checking that the path string starts with the workspace is enough."
    ✓ Resolve .. and symlinks first, then compare path components.
  • ✗ "Accepting the form means the data is valid."
    ✓ The server validates it against the schema and re-checks it against what it offered.
  • ✗ "decline and cancel mean the same."
    ✓ Decline is an explicit no; cancel means no decision was made.

See it drawn
A delete tool that asks the user first

delete_note uses the SDK's resolver pattern: Resolve(which_note) returns an Elicit form with a typed choice and a confirmation box. On 2026-07-28 the SDK delivers it as an input_required round. Six scripted user answers exercise every branch, including a client that sends a value the form never offered. About a second.

import asyncio
from typing import Annotated, Literal
from pydantic import BaseModel, Field
from mcp import Client
from mcp.server import MCPServer
from mcp.server.mcpserver import (AcceptedElicitation, CancelledElicitation, DeclinedElicitation, Elicit,
                                  ElicitationResult, Resolve)
from mcp.types import ElicitResult

NOTES = {"n-101": "TPS report 2024 (draft)", "n-102": "TPS report 2024 (final)", "n-207": "TPS report 2025",
         "n-300": "Lunch menu"}
srv = MCPServer("notes", log_level="WARNING")

class Pick(BaseModel):                                 # the form the user sees: flat, typed fields only
    note_id: Literal["n-101", "n-102", "n-207"] = Field(description="Which note to delete")
    confirm: bool = Field(description="Yes, delete it permanently")

async def which_note(title: str) -> Elicit[Pick]:
    matches = [f"{k}: {v}" for k, v in NOTES.items() if title.lower() in v.lower()]
    return Elicit("Several notes match. Which one should be deleted?\n" + "\n".join(matches), Pick)

@srv.tool()
async def delete_note(title: str, choice: Annotated[ElicitationResult[Pick], Resolve(which_note)]) -> str:
    """Use when the user wants to delete a note by title. Asks the user if several notes match."""
    if isinstance(choice, AcceptedElicitation):
        if not choice.data.confirm:
            return "not deleted: the user did not confirm"
        if title.lower() not in NOTES.get(choice.data.note_id, "").lower():
            return "not deleted: that note does not match the request"     # re-check, never trust the form blindly
        return f"deleted {choice.data.note_id} ({NOTES.pop(choice.data.note_id)})"
    if isinstance(choice, DeclinedElicitation):
        return "not deleted: the user declined"
    return "not deleted: the user cancelled"

def user(action, content=None):                         # the client's UI, scripted for the demo
    async def answer(context, params):
        schema = params.requested_schema
        print(f"  form shown: {params.message.splitlines()[0]!r} fields={list(schema['properties'])}")
        return ElicitResult(action=action, content=content)
    return answer

async def main():
    for label, cb in (("user picks n-102 and confirms", user("accept", {"note_id": "n-102", "confirm": True})),
                      ("user picks n-101 but does not confirm", user("accept", {"note_id": "n-101", "confirm": False})),
                      ("form says n-207 (a 2025 note)", user("accept", {"note_id": "n-207", "confirm": True})),
                      ("client sends n-300 (never offered)", user("accept", {"note_id": "n-300", "confirm": True})),
                      ("user clicks Decline", user("decline")),
                      ("user closes the dialog", user("cancel"))):
        async with Client(srv, elicitation_callback=cb) as c:
            r = await c.call_tool("delete_note", {"title": "TPS report 2024"})
            print(f"{label:<40}-> {'ERROR ' if r.is_error else ''}{r.content[0].text[:110]}\n")
    print("notes left:", sorted(NOTES))

asyncio.run(main())

Reading this output

The user sees one form for every run. The server's resolver lists the matching notes in the message and asks for two typed fields, note_id and confirm. The SDK delivered it through an input_required round and resumed the tool when the client retried with the answer.

Only an explicit, valid confirmation deletes. Choosing n-102 and confirming deleted it. Choosing n-101 without ticking confirm kept it. Choosing n-207, which the form offered but which is a 2025 note, was caught by the tool's own re-check against the request ("does not match"). A client that sent n-300, a value outside the form's choices, never reached the tool: the SDK rejected the content against the schema and returned a tool error.

Decline and cancel are different, and both safe. "Declined" means the user said no; "cancelled" means they closed the dialog without deciding. Neither deletes, and the tool reports which one happened. At the end only n-102 is gone.

See it drawn
Explicit scope: a naive path check against a safe one

A real temporary folder holds a workspace, a secret file next to it, a look-alike folder ws-evil, and a symbolic link inside the workspace that points at the secret. Five requested paths are checked two ways: a string-prefix test after normalising, and a test after resolving the real path. Instant.

# Explicit scope instead of Roots: the workspace is a visible argument, and the server checks containment.
import os, pathlib, tempfile
base = pathlib.Path(tempfile.mkdtemp())
ws = base / "ws"; (ws / "notes").mkdir(parents=True)
(ws / "notes" / "a.md").write_text("note A")
(base / "secret.txt").write_text("API_KEY=...")
(base / "ws-evil").mkdir(); (base / "ws-evil" / "x.md").write_text("outside")
os.symlink(base / "secret.txt", ws / "notes" / "link.md")      # a link inside that points outside

def naive_allowed(workspace, rel):            # "is the path string under the workspace string?"
    return os.path.normpath(os.path.join(workspace, rel)).startswith(str(workspace))

def safe_allowed(workspace, rel):             # resolve symlinks and '..', then compare real paths
    p = (workspace / rel).resolve()
    return p.is_relative_to(workspace.resolve()) and p.exists()

tries = ["notes/a.md", "../secret.txt", "notes/link.md", "../ws-evil/x.md", str(base / "secret.txt")]
print(f"workspace = {ws}\n")
print(f"{'requested path':<34}{'naive check':<14}{'safe check':<12}what it really is")
for rel in tries:
    real = (ws / rel).resolve()
    print(f"{rel[-32:]:<34}{str(naive_allowed(ws, rel)):<14}{str(safe_allowed(ws, rel)):<12}"
          f"{real.relative_to(base) if real.is_relative_to(base) else real}")

Reading this output

The resolved check is right on all five paths. It allows only notes/a.md, the one file really inside the workspace.

The naive check fails twice. notes/link.md is a symbolic link inside the workspace that points at secret.txt outside it: the path string looks fine, the real target is not. ../ws-evil/x.md normalises to a path whose string starts with the workspace's string (.../ws-evil begins with .../ws), so a prefix test lets it through. Both checks catch the plain .. escape and the absolute path, which is why naive checks pass simple tests and fail in production.

This is what Roots never did for you: a server must resolve and compare real paths itself, and an OS-level sandbox is the backstop.

Build it

code/main.py demonstrates a modern notes_delete tool:

  • tools/list returns a deterministic, cacheable descriptor with the required workspace and title schema.
  • Scope is an explicit workspaceUri argument.
  • Server configuration authorizes that workspace for the lesson principal.
  • URI normalization rejects prefix confusion and encoded traversal.
  • Every destructive deletion requires form-mode elicitation.
  • The elicitation travels inside resultType: "input_required".
  • Signed requestState binds the exact candidate list and original arguments.
  • An injected replay store rejects the same accepted or declined state across server instances.
  • The retry uses a fresh request id and returns resultType: "complete".

The data store is in memory so the protocol behavior is easy to inspect. The security rules remain the same with a database.

Industry practice
What's current (2024–2026)
  • Roots deprecated in MCP 2026-07-28: pass workspaces as tool arguments or resource URIs, or configure them on the server, and enforce containment and authorization server-side.
  • Elicitation via MRTR: form mode (flat typed fields, enums with titles, defaults since 2025-11-25) and URL mode (send the user to a web page for sensitive input such as OAuth or payments, so secrets never pass through the client); 2026-07-28 removed the URL-mode completion notification in favour of retrying.
  • SDKs: the Python SDK 2.x Elicit[T] with ElicitationResult branches (AcceptedElicitation, DeclinedElicitation, CancelledElicitation) and signed requestState.
  • Hosts show elicitation forms with the requesting server's name, and must never ask for passwords or secrets in form mode.

Sources: MCP 2026-07-28 changelog, MCP elicitation, MCP 2025-11-25 changelog, MCP Python SDK.

Recap
What to keep from this lesson
  • Scope is an explicit, authorised argument; Roots were hints and are deprecated.
  • Check containment on resolved real paths, by components, not string prefixes.
  • Ask the user with elicitation, delivered as an input_required round.
  • Handle accept, decline and cancel separately; only an explicit confirmation deletes.
  • Re-validate the answer against what was offered, and bind it to principal, arguments and expiry.

outputs/skill-elicitation-form-designer.md designs the explicit scope, authorization checks, MRTR form, response branches, and state binding. It refuses to treat deprecated Roots as a sandbox or to collect secrets through form mode.

---
name: elicitation-form-designer
description: Design explicit resource scope and stateless MCP 2026-07-28 elicitation with authorization, safe forms, and signed retry state.
version: 2.0.0
phase: 13
lesson: 12

---

Design a user-input step for an MCP operation targeting protocol revision `2026-07-28`.

Produce:

1. Scope contract. Put the workspace, directory, or resource URI in visible tool arguments or server configuration. State which authenticated principals may use it.
2. Boundary checks. Define URI normalization, path-component containment, symbolic-link policy, and the operating-system sandbox.
3. Trigger condition. Name the exact ambiguity, confirmation, or external interaction that requires user input.
4. Discovery and capability gate. Return exact `supportedVersions`, capabilities, `ttlMs`, and `cacheScope` from `server/discover`. If tools are advertised, include mandatory deterministic `tools/list` descriptors with a valid object `inputSchema`, server identity metadata, and cache hints. Treat `elicitation: {}` and explicit `elicitation.form` as form support. Reject missing or URL-only support with `-32021` and `data.requiredCapabilities.elicitation.form`; use `-32022` with exact `supported` and `requested` data for an unsupported version.
5. MRTR result. Return `resultType: "input_required"` with a stable `inputRequests` key and `elicitation/create` request.
6. Interaction design. For form mode, provide a plain message and restricted flat schema. For URL mode, show the HTTPS destination and out-of-band completion rule.
7. Retry contract. Require a fresh JSON-RPC id, original method and arguments, current `inputResponses`, per-request `_meta`, and exact `requestState` echo.
   An id-less notification never receives a JSON-RPC result or error; an accepted Streamable HTTP notification receives `202` with no body.
8. Branch handling. Map `accept`, `decline`, and `cancel` to different safe outcomes.
9. State protection. Bind HMAC or authenticated encryption to the authenticated principal, original argument digest, candidate set, operation phase, expiry, and one-time nonce. Consume the nonce atomically in a bounded, TTL-pruned replay store shared by every handler instance.
10. Final revalidation. Re-check authorization, live record state, and containment immediately before mutation.

Hard rejects:

- Treating deprecated Roots as authorization, containment, or sandboxing.
- Using `roots/list` or `notifications/roots/list_changed` in a new 2026-07-28 design.
- Sending a reverse `elicitation/create` request instead of returning it through MRTR.
- Collecting passwords, API keys, access tokens, or payment credentials in form mode.
- Sending an elicitation mode absent from current per-request capabilities.
- Treating `clientInfo` as an authenticated user identity.
- Performing a destructive action before validated acceptance and final authorization checks.
- Unsigned `requestState` that carries candidates or permission-relevant data.

Refusal rules:

- Refuse repeated prompts after explicit decline.
- Refuse elicitation for a value the server can derive or validate without the user.
- Refuse a URL that contains credentials, user secrets, or a pre-authenticated bearer value.
- Refuse a request that uses hidden protocol-session state, `initialize`, or `Mcp-Session-Id`.

Output a one-page design with scope, authorization, containment, interaction mode, schema or URL, MRTR wire shape, state fields, response branches, replay policy, and final revalidation checklist.

Exercises

  1. Replace the in-memory replay store with SQLite. Use one transaction to claim the nonce and delete the note, then prove two processes cannot both commit.
  2. Add url capability negotiation and an out-of-band setup flow. Keep third-party credentials out of inputResponses.
  3. Replace the in-memory note map with a temporary SQLite database. Re-check authorization and containment inside the mutation transaction.
  4. Add a symbolic-link policy for a real filesystem implementation. Explain why URI lexical containment alone cannot stop a symlink escape.
  5. Design a 2025-11-25 adapter that maps modern MRTR handler output to legacy server-initiated elicitation. Keep it isolated from the current handler.

Solutions

SolutionP1 · Only one answer deletes

Only one: picking n-102 with confirm ticked. Every other answer keeps the notes: an unconfirmed choice, a choice that the server's re-check rejects (n-207 does not match "TPS report 2024"), a value the form never offered (n-300, rejected by schema validation before the tool runs), a decline and a cancel.

Two layers did the work: the SDK validated the answer against the form's schema, and the tool re-checked the choice against the request before deleting.

SolutionB1 · Unconfirmed, unbound, unremembered

  1. No confirmation. accept only means the user submitted the form; if the form has no explicit confirm field (or the server does not check it), a user who merely picked a note to look at loses it.

  2. No binding. The note_id from the form is trusted as is: a modified client can send any id, including one never offered or belonging to another user. The answer must be checked against the candidate set the server offered for these arguments, and the state must be bound to the authenticated principal, a hash of the arguments, the candidate set and an expiry, and integrity-protected.

  3. No memory across replicas. In 2026-07-28 the retry is a new request that may reach a different server instance, or the same one after a restart. A candidate list kept in one process's memory is simply missing there, so the server either fails or, worse, falls back to an unchecked path. The candidates belong in the signed requestState (or a shared store behind a handle).

Legacy Compatibility

For a peer pinned to 2025-11-25, roots/list, notifications/roots/list_changed, and live server-initiated elicitation/create may still exist. Label that adapter legacy. Do not allow a legacy Root list to bypass server authorization, and do not carry protocol-session assumptions into the modern handler.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designA tool that deletes notes, notes_delete, finds three notes that match the title the user gave. Design the confirmation flow under the current MCP revision: how the server asks the user to pick one and confirm, how the answer comes back, and what stops a client from answering a different question or replaying one confirmation with changed arguments.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. The server answers with a result typed input_required that embeds an elicitation/create form request listing the three candidate ids and a confirm boolean, plus an integrity-protected requestState. The client shows the form and retries the original tools/call with a new request id, echoing requestState and the inputResponses. The server signs the state over the principal, the method, a digest of the arguments, the candidate set, the phase and an expiry, verifies the echo, checks that the chosen id was in the signed set, re-authorizes the workspace and re-checks containment, and consumes a one-time nonce in a shared replay store before it deletes.

The first response.

{
  "resultType": "input_required",
  "inputRequests": {
    "delete_choice": {
      "method": "elicitation/create",
      "params": {
        "mode": "form",
        "message": "Choose one matching note and confirm deletion.",
        "requestedSchema": {
          "type": "object",
          "properties": {
            "note_id": {"type": "string", "enum": ["note-3", "note-7", "note-14"]},
            "confirm": {"type": "boolean"}
          },
          "required": ["note_id", "confirm"]
        }
      }
    }
  },
  "requestState": "integrity-protected-delete-state"
}

A current server sends no reverse JSON-RPC request. The embedded request is complete, with method and params, and its key must match the entry in inputResponses on the retry.

Capabilities are checked on this request.

The server may embed a form only when the current request's clientCapabilities support it. {"elicitation": {}} and {"elicitation": {"form": {}}} both support form mode. A URL-only declaration does not, and the server returns -32021 with data.requiredCapabilities equal to {"elicitation":{"form":{}}}. An earlier request's declaration never counts.

Form mode has limits.

The root is an object with flat primitive fields or supported enums. Use it to choose among candidates, confirm a destructive operation or collect non-sensitive preferences. Never collect passwords, API keys or payment credentials in it, because they would pass through the client and could reach logs or model context. URL mode exists for that external flow.

Three outcomes, three behaviors.

Action Meaning Server behavior
accept the user submitted the form validate the content and continue
decline the user refused return a complete, non-error refusal; consume the nonce without deleting
cancel the user dismissed or could not finish stop safely; the state stays retryable until expiry

Never read missing content as consent, and never turn a decline into a repeated prompt.

What the signed state binds.

The state holds the authenticated principal, the originating method, a digest of workspaceUri and title, the allowed note ids shown in the form, the operation phase and a short expiry. On the retry the server verifies the signature, validates the response against the schema, checks that note_id is in the signed candidate set, re-authorizes the workspace, re-checks containment, and only then mutates. A changed title cannot reuse the original state.

Why HMAC alone is not enough.

A valid state can be replayed within its expiry. Store and consume a nonce exactly once in a replay store shared by every handler instance, and hold the atomic claim while the deletion runs. A database couples the claim and the mutation in one transaction. Validate before you claim: a malformed response or a cancel claims nothing.

Plausible wrong answers.

  • "Keep the candidate list in server memory keyed by the connection." There is no session, and the retry can reach any instance. The candidates travel inside the signed state.
  • "The host validated the form, so the server can trust the content." The client controls everything it sends. The server validates the schema and the candidate set again.
  • "Ask for the user's password in the form as the confirmation." Form mode must not carry secrets. An external credential flow uses URL mode and binds the browser user to the same principal.

Follow-ups an interviewer may ask.

  • (level 3) The client declares {"elicitation": {"url": {}}} only. What does the server do? Expected: return -32021 with the required form capability in data; it must not embed a mode the current request did not declare.
  • (level 3) The user dismisses the dialog. Which action, and what happens to the state? Expected: cancel; nothing is mutated and the state stays retryable until it expires, unlike decline, which is terminal.
  • (level 4) Two server instances share the note store. How do you stop both from executing one confirmation? Expected: a shared replay store with an atomic nonce claim coupled to the mutation; the lesson's test runs two server objects against one state.
  • (level 4) A note moves outside the workspace after the form was shown. What catches it? Expected: the live record check and the containment re-check before mutation, not the signed state alone.

Where it is taught. The roots and elicitation lesson builds this flow with a replay store, and the security lesson treats requestState as hostile input.

Explain the mechanismA filesystem MCP server reads the client's Roots list once and treats any path under a root as authorized for deletion. The client advertises one workspace directory. Two delete requests arrive: one for a sibling directory whose name starts with the workspace name, and one that reaches the parent through an encoded dot-dot segment. What is wrong with this design, and how do you replace it?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Roots were informational guidance, never authorization and never a sandbox, and the current revision deprecates them. A string-prefix check accepts both hostile paths, because both begin with the workspace text. Replace the root with an explicit workspaceUri argument or a resource URI, then enforce three layers: authorize the principal for that workspace, normalize the URI and check containment by path components, and run the server under an operating-system sandbox.

What roots were.

Earlier revisions let a client advertise Roots and send notifications/roots/list_changed. A root told the server where the user was working. It did not constrain what the server process could read, did not authorize the caller, and created no operating-system boundary. The current revision deprecates roots/list for new designs.

The explicit replacements.

Situation Replacement
scope varies per call a workspaceUri or directory tool argument
the operation already targets a resource the resource URI
one deployment owns one fixed workspace server configuration
code must be unable to escape a process sandbox or jailed filesystem

The model can see and repeat an explicit handle. Hidden session scope is harder to inspect, replay, audit and route.

Three layers, every time.

  1. Authorization: may this authenticated principal use this workspace?
  2. Containment: does the normalized target stay inside the workspace boundary?
  3. Sandbox: can the operating system stop a compromised server anyway?

Why the prefix check fails.

allowed:   file:///work/notes
attacker:  file:///work/notes-evil/secret.md
traversal: file:///work/notes/%2e%2e/private.md

Both hostile paths start with the allowed text. Normalize percent-encoded segments first, then compare path components. Re-check containment right before the mutation, because a target can move after the request was validated. A real filesystem server also needs a symbolic-link policy and platform-specific path handling.

The migration adapter.

If a peer still needs roots/list during the deprecation window, the server embeds that request in an MRTR input_required result. It never sends a live reverse request. Label the adapter legacy, and never let a legacy root list bypass server authorization.

Plausible wrong answers.

  • "The client declared the root, so the server can trust the scope." A root is a self-reported hint. Authorization comes from the authenticated principal and server policy.
  • "Check startswith on the allowed URI." A sibling directory and an encoded traversal both pass. Normalize, then compare path components.
  • "An operating-system sandbox makes the authorization check unnecessary." The sandbox is the third layer for a compromised process. It does not decide which principal may touch which workspace.

Follow-ups an interviewer may ask.

  • (level 2) When is server configuration the right replacement? Expected: when one deployment owns one fixed workspace; per-call scope belongs in a workspaceUri argument.
  • (level 3) Why re-check containment immediately before the deletion? Expected: the live record can move outside the workspace between validation and mutation, and a race must not delete the wrong target.
  • (level 3) Why does lexical containment alone not stop a symlink escape? Expected: a link inside the boundary resolves to a path outside it, so the filesystem layer needs a symlink policy and resolution of the real path.
  • (level 4) A pinned legacy peer still sends roots/list. How do you serve it without weakening the modern handler? Expected: an isolated adapter that embeds the request in MRTR input requests, labelled legacy, with authorization and containment still enforced on the server.

Where it is taught. The roots and elicitation lesson states the three-layer rule and shows both hostile paths failing containment.
