The problem

In plain words first

Not every team wants a framework with graphs, crews or actors. Agno (Python) and Mastra (TypeScript) offer something lighter: an agent object with a model, instructions and tools, and a way to call it, plus storage, memory and workflows when you need them. Agno advertises that creating an agent takes microseconds and a few kilobytes, so a web server can create a fresh agent for every request. Mastra builds on the Vercel AI SDK and fits TypeScript web stacks. The useful questions are practical: does it run against my model, does it call my tools, and does its overhead matter next to the model call? This lesson builds tiny versions of both, then runs the real Agno and Mastra against the same small local model and measures their overhead.

LangGraph, AutoGen, CrewAI are framework-heavy. Teams that want "just the agent loop, fast, in my runtime" reach for Agno (Python) or Mastra (TypeScript). Both trade some of the framework-owned primitives for raw speed and a tighter fit to the surrounding stack.

Idea 1 · Agno

  • Python runtime, formerly Phi-data.
  • "No graphs, chains, or convoluted patterns — just pure python."
  • Performance targets from their docs: ~2μs agent instantiation, ~3.75 KiB memory per agent, ~23 model providers.
  • Production path: stateless session-scoped FastAPI backend. Each request starts a fresh agent; session state lives in a DB.
  • Native multimodal (text, image, audio, video, file) and agentic RAG.

The speed targets matter when you have thousands of short-lived agents per second (chat fan-in, evaluation pipelines). They matter less when one agent runs for 10 minutes.

Idea 2 · Mastra

  • TypeScript, built on Vercel AI SDK.
  • Three primitives: Agents, Tools (Zod-typed), Workflows.
  • Unified Model Router — 3,300+ models across 94 providers (March 2026).
  • Composite storage: memory, workflows, observability to different backends; ClickHouse recommended for observability at scale.
  • Apache 2.0 with ee/ directories under source-available enterprise license.
  • Server adapters for Express, Hono, Fastify, Koa; first-class Next.js and Astro integration.
  • Ships Mastra Studio (localhost:4111) for debugging.
  • 22k+ GitHub stars, 300k+ weekly npm downloads at 1.0 (Jan 2026).

Idea 3 · Positioning

Neither is trying to be LangGraph. They compete on:

  • Language fit. Agno for Python-first teams; Mastra for TypeScript-first.
  • Runtime ergonomics. Agno = near-zero overhead; Mastra = integrated with the Vercel ecosystem.
  • Observability. Both integrate with Langfuse/Phoenix/Opik (Lesson 14.24) but Mastra Studio is first-party.

Idea 4 · When to pick each

  • Agno — Python backend, many short-lived agents, strong perf requirements, FastAPI shop.
  • Mastra — TypeScript backend, Next.js / Vercel deploy, unified multi-provider model routing, Zod-typed tools.
  • LangGraph (Lesson 14.13) — when durable state and explicit graph reasoning matter more than raw speed.
  • OpenAI / Claude Agent SDK — when you want the provider's productized shape (Lessons 16–17).

Idea 5 · Where this pattern goes wrong

  • Perf-for-perf's-sake. Picking Agno because "2μs" sounds good when the workload is one slow agent call per request. Overhead is not the bottleneck.
  • Ecosystem lock-in. Mastra's Vercel-flavored integration is a plus on Vercel, a minus elsewhere.
  • Enterprise license confusion. Mastra's ee/ directories are source-available, not Apache 2.0. Read the licenses if you're planning to fork.

The same idea as a formula

Where a request's time goes. For a request that creates an agent and runs it with k model calls of tm​ each and j tool calls of tx​ each:

trequest​=tcreate​+ktm​+jtx​+tframework​.
The framework's own overhead matters only when tcreate​+tframework​ is a noticeable fraction of the whole.

Memory for many agents. Holding n live agents of b bytes each needs nb: at 4 KiB per agent, 105 concurrent agents need about 400 MB, before any conversation history.

Worked example
Does a few microseconds matter here?
  • Creating an Agno agent took under 10 microseconds below; one agent.run on the local 0.5B model took about 3.8 seconds.
  • The ratio is several hundred thousand: if creation took 1,000 times longer (10 ms), a request would still be about 99.7% model time.
  • Where it can matter: an evaluation harness that creates 106 agents and runs a cached or mocked model; at 10 µs each that is 10 s of creation, at 400 µs (Mastra below) about 7 minutes.
  • So choose by language, ecosystem and features first; measure overhead only for workloads with very many, very short runs.
Check your mental model
  • ✗ "A faster framework makes the agent faster."
    ✓ The model call dominates; framework overhead is usually a rounding error.
  • ✗ "Light frameworks lack the essentials."
    ✓ Both run tools, keep sessions and support workflows; they leave graphs and actors out.
  • ✗ "A vendor's benchmark holds on my machine."
    ✓ Measure: the numbers below are close to Agno's claims for memory, not for speed.
  • ✗ "Switching frameworks fixes tool use."
    ✓ With the same model, Agno and Mastra fail and succeed on exactly the same question.

Agno 3.2 talks to a local Qwen2.5-0.5B-Instruct server (the same OpenAI-compatible server as lessons 14.15 and 14.16) through OpenAILike. # Agno 3 on a local model, and its speed claim measured. The same local Qwen2.5-0.5B-Instruct server as
# lessons 14.15 and 14.16 (OpenAI-compatible); Agno talks to it through OpenAILike.
import os, pathlib, subprocess, sys, tempfile, time, tracemalloc
work = pathlib.Path(tempfile.mkdtemp())
SERVER = r'''# qwen_server.py: Qwen2.5-0.5B-Instruct behind a minimal OpenAI-compatible /v1/chat/completions endpoint,
# so frameworks that speak that API can run on a local model. Greedy decoding; tool calls supported through
# the model's chat template (<tool_call> blocks become OpenAI tool_calls); tool_choice="required" is honoured by
# starting the reply inside a <tool_call> block. Stops by itself after LIFETIME s.
import json, os, re, sys, time, uuid, torch
from http.server import BaseHTTPRequestHandler, HTTPServer
os.environ.setdefault("HF_HUB_OFFLINE", "1")
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
M = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(M); llm = AutoModelForCausalLM.from_pretrained(M).eval()
LOG = os.environ.get("QWEN_LOG")
def text_of(content):
    return content if isinstance(content, str) else " ".join(p.get("text", "") for p in content or [])
def to_template(messages):
    out = []
    for m in messages:
        msg = {"role": m["role"], "content": text_of(m.get("content") or "")}
        if m.get("tool_calls"):
            msg["tool_calls"] = [{"type": "function", "function": {"name": c["function"]["name"],
                                  "arguments": json.loads(c["function"]["arguments"] or "{}")}} for c in m["tool_calls"]]
        out.append(msg)
    return out
def complete(req):
    tools = req.get("tools") or None
    ids = tok.apply_chat_template(to_template(req["messages"]), tools=tools, add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    forced = '<tool_call>\n{"name": "' if tools and req.get("tool_choice") == "required" else ""
    if forced:                                           # constrained start: the reply must be a tool call
        ids = torch.cat([ids, tok(forced, return_tensors="pt")["input_ids"]], dim=1)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=int(req.get("max_tokens") or req.get("max_completion_tokens") or 256),
                           do_sample=False)
    text = forced + tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).strip()
    calls = []
    for blob in re.findall(r"<tool_call>\s*(\{.*?\})\s*</tool_call>", text, re.S) if tools else []:
        try:
            d = json.loads(blob)
            calls.append({"id": "call_" + uuid.uuid4().hex[:8], "type": "function",
                          "function": {"name": d["name"], "arguments": json.dumps(d.get("arguments", {}))}})
        except (json.JSONDecodeError, KeyError):
            pass
    content = re.sub(r"<tool_call>.*?</tool_call>", "", text, flags=re.S).strip() if calls else text
    if LOG:
        with open(LOG, "a") as f:
            f.write(json.dumps({"prompt_tokens": ids.shape[1], "tools": len(tools or []), "tool_calls": [c["function"] for c in calls],
                                "content": content[:200]}) + "\n")
    msg = {"role": "assistant", "content": content or None}
    if calls:
        msg["tool_calls"] = calls
    return {"id": "chatcmpl-" + uuid.uuid4().hex[:8], "object": "chat.completion", "created": int(time.time()),
            "model": req.get("model", M), "choices": [{"index": 0, "message": msg,
            "finish_reason": "tool_calls" if calls else "stop"}],
            "usage": {"prompt_tokens": ids.shape[1], "completion_tokens": out.shape[1] - ids.shape[1],
                      "total_tokens": out.shape[1]}}
class Handler(BaseHTTPRequestHandler):
    def log_message(self, *args):
        pass
    def do_GET(self):
        body = json.dumps({"object": "list", "data": [{"id": M, "object": "model"}]}).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json"); self.end_headers(); self.wfile.write(body)
    def do_POST(self):
        req = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        body = json.dumps(complete(req)).encode()
        self.send_response(200); self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body))); self.end_headers(); self.wfile.write(body)
port, lifetime = int(sys.argv[1]), float(sys.argv[2])
srv = HTTPServer(("127.0.0.1", port), Handler); srv.timeout = 0.5
print("ready", flush=True)
deadline = time.time() + lifetime
while time.time() < deadline:                            # bounded: one request at a time until the deadline
    srv.handle_request()
'''
(work / "qwen_server.py").write_text(SERVER)
PORT = 8600 + os.getpid() % 100
server = subprocess.Popen([sys.executable, str(work / "qwen_server.py"), str(PORT), "900"],
                          stdout=subprocess.PIPE, stderr=subprocess.DEVNULL, text=True)
assert server.stdout.readline().strip() == "ready"
BASE = f"http://127.0.0.1:{PORT}/v1"
import importlib.metadata
from agno.agent import Agent
from agno.models.openai.like import OpenAILike
ORDERS = {"A-1001": "shipped on 20 Nov", "A-1002": "processing"}
def get_order_status(order_id: str) -> str:
    """Return the shipping status for an order ID such as A-1001."""
    return f"{order_id}: {ORDERS.get(order_id, 'not found')}"
model = OpenAILike(id="qwen2.5-0.5b", base_url=BASE, api_key="local", temperature=0)
agent = Agent(model=model, tools=[get_order_status], instructions="Answer order questions in one sentence.")
print("agno", importlib.metadata.version("agno"))
for question in ("Where is my order A-1001?", "What is the status of A-1002?"):
    t0 = time.perf_counter()
    run = agent.run(question)
    calls = [t.tool_name for t in (run.tools or [])]
    print(f"{question}\n  tools: {calls}  reply: {' '.join(str(run.content).split())[:110]}  ({time.perf_counter() - t0:.1f} s)")
# The speed claim: how long does creating an agent take, and how much memory does one hold?
N = 2000
t0 = time.perf_counter()
for _ in range(N):
    Agent(model=model, tools=[get_order_status], instructions="Answer order questions in one sentence.")
create_us = (time.perf_counter() - t0) / N * 1e6
tracemalloc.start()
before = tracemalloc.take_snapshot()
keep = [Agent(model=model, tools=[get_order_status], instructions="Answer order questions in one sentence.") for _ in range(200)]
after = tracemalloc.take_snapshot()
tracemalloc.stop()
per_agent = sum(s.size_diff for s in after.compare_to(before, "filename")) / len(keep)
print(f"\ncreating an Agent: {create_us:.1f} microseconds each (mean of {N})")
print(f"memory held per Agent: {per_agent / 1024:.2f} KiB (tracemalloc, 200 agents kept alive)")
one_call = time.perf_counter(); agent.run("Where is my order A-1001?"); one_call = time.perf_counter() - one_call
print(f"one agent.run on the local model: {one_call:.2f} s, about {one_call * 1e6 / create_us:,.0f} times the creation cost")

Reading this output

Agno ran the tool on one question of two. For "What is the status of A-1002?" it called get_order_status and answered from the result. For "Where is my order A-1001?" the model said it would use the function, then asked for the order ID it had just been given, without calling anything. Same model, same failure as in lessons 14.1 and 14.16.

Creating an agent costs microseconds; holding one costs about 4 KiB. Below 10 microseconds per agent on this machine (Agno's docs quote about 2 microseconds on theirs) and roughly 3.6 to 4 KiB per live agent (their figure: about 3.75 KiB). The exact numbers vary from run to run.

The model call is hundreds of thousands of times slower. One agent.run took about 3.8 seconds; framework overhead does not show up in a request's latency.

Part 1 of 3 · AgnoAgent, AgnoSession, agno_request_handler, MastraTool, MastraAgent, MastraWorkflow, _agno_agent_fn

"""Side-by-side toys: Agno-shaped (stateless FastAPI) vs Mastra-shaped
(primitive-rich). Stdlib only; meant to show the structural difference.
"""

from __future__ import annotations

import time
from dataclasses import dataclass, field
from typing import Any, Callable


@dataclass
class AgnoAgent:
    name: str
    fn: Callable[[str], str]

    def run(self, prompt: str) -> str:
        return self.fn(prompt)


class AgnoSession:
    def __init__(self) -> None:
        self._turns: dict[str, list[str]] = {}

    def append(self, session_id: str, turn: str) -> None:
        self._turns.setdefault(session_id, []).append(turn)

    def history(self, session_id: str) -> list[str]:
        return list(self._turns.get(session_id, []))


def agno_request_handler(session: AgnoSession,
                         agent: AgnoAgent,
                         session_id: str,
                         prompt: str) -> str:
    start = time.perf_counter_ns()
    session.append(session_id, f"user: {prompt}")
    output = agent.run(prompt)
    session.append(session_id, f"assistant: {output}")
    elapsed_us = (time.perf_counter_ns() - start) / 1000
    return f"{output}  (handler {elapsed_us:.1f} us)"


@dataclass
class MastraTool:
    name: str
    input_schema: dict[str, Any]
    fn: Callable[..., str]


@dataclass
class MastraAgent:
    name: str
    instructions: str
    tools: list[MastraTool] = field(default_factory=list)

    def run(self, prompt: str, tool_calls: list[tuple[str, dict[str, Any]]]
            ) -> tuple[str, list[tuple[str, str]]]:
        trace: list[tuple[str, str]] = []
        for tool_name, args in tool_calls:
            tool = next((t for t in self.tools if t.name == tool_name), None)
            if tool is None:
                trace.append((tool_name, "error: unknown"))
                continue
            result = tool.fn(**args)
            trace.append((tool_name, result))
        output = f"{self.name} processed {len(tool_calls)} tools"
        return output, trace


@dataclass
class MastraWorkflow:
    steps: list[tuple[str, Callable[[Any], Any]]]

    def run(self, payload: Any) -> list[tuple[str, Any]]:
        trace: list[tuple[str, Any]] = []
        current = payload
        for name, fn in self.steps:
            current = fn(current)
            trace.append((name, current))
        return trace


def _agno_agent_fn(prompt: str) -> str:
    return f"[agno reply] {prompt[:40]}"

          "FastAPI is stateless.")

    print("\n2. MASTRA-shaped (Agents + Tools + Workflows)")
    search_tool = MastraTool(
        name="search",
        input_schema={"type": "object",
                      "properties": {"query": {"type": "string"}}},
        fn=_mastra_tool_fn,
    )
    mastra_agent = MastraAgent(
        name="mastra_a",
        instructions="search, summarize, cite",
        tools=[search_tool],
    )
    output, trace = mastra_agent.run(
        "research agent engineering",
        [("search", {"query": "agent engineering 2026"}),
         ("search", {"query": "BFCL V4 benchmarks"})],
    )
    print(f"  agent output: {output}")
    for tool, result in trace:
        print(f"    tool {tool}: {result}")

    workflow = MastraWorkflow(steps=[
        ("normalize", lambda p: p.strip().lower()),
        ("search", lambda p: f"found 3 results for {p}"),
        ("summarize", lambda p: f"summary: {p}"),
    ])
    print("\n  workflow run")
    for name, out in workflow.run("  Agent Engineering 2026  "):
        print(f"    {name}: {out}")

    print("\npick by stack: python+fastapi  Agno; typescript+next/vercel  Mastra.")

Break it on purpose

A team moves from LangGraph to Agno "for performance" because creating an agent is said to take microseconds. Their agent makes four model calls per request to a hosted model. After the migration, p95 latency is unchanged. Why, and what would have reduced it? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Agno (3.x, open source, with AgentOS for running agents as a FastAPI service) is a common choice for Python teams that want plain agents, teams and workflows without graph abstractions.
  • Mastra (1.0 in January 2026; about 3.7 million npm downloads of @mastra/core in the week to 24 November 2026) is the leading TypeScript agent framework, with agents, Zod-typed tools, workflows, memory, evals and Mastra Studio.
  • Other light options: Pydantic AI (typed Python agents), smolagents (agents that write code), the Vercel AI SDK's own agent loop, and the provider SDKs from lessons 14.16 and 14.17.
  • On your laptop: both frameworks run against any OpenAI-compatible local server (Ollama, llama.cpp, LM Studio) with no extra code; a 7B to 8B model in 4-bit on the RTX 4060 calls tools much more reliably than the 0.5B model here.

Recap
What to keep from this lesson
  • Agno and Mastra: agents, tools and workflows without heavy abstractions.
  • Pick by language and ecosystem first.
  • Framework overhead is tiny next to model calls; measure before optimising.

Given a stack, latency budget, required primitives, and operational shape, pick a runtime.

Decision:

1. Python + FastAPI + thousands of short-lived agents per second -> **Agno**.
2. TypeScript + Next.js/Vercel + unified multi-provider -> **Mastra**.
3. Durable state, explicit graph, resume-on-failure -> **LangGraph** (Lesson 13).
4. Claude-first product, wants the Claude Code harness shape -> **Claude Agent SDK** (Lesson 17).
5. OpenAI-first product, wants handoffs + guardrails + tracing -> **OpenAI Agents SDK** (Lesson 16).
6. Multi-agent team, actor-model concurrency, fault isolation -> **AutoGen v0.4** / **Microsoft Agent Framework** (Lesson 14).
7. Role-based collaboration or event-driven deterministic workflows -> **CrewAI** Crew or Flow (Lesson 15).
8. None of the above -> direct API calls + the stdlib loop from Lesson 01.

Produce:

- A short decision document: stack, latency target, primitives needed, observed trade-offs.
- A minimal scaffold in the chosen runtime.
- A migration plan if another runtime is in use today.

Hard rejects:

- Picking Agno or Mastra purely on "performance" when the workload is one slow call per request. Performance is rarely the bottleneck.
- Picking a TypeScript runtime in a Python monorepo without a rationale. Mixed-language agent code is an operational tax.
- Picking LangGraph for stateless short tasks. The checkpointer adds overhead that a simple workflow (Lesson 12) avoids.

Refusal rules:

- If the user wants "all five runtimes, to compare," refuse. Benchmark on your workload; framework vendor benchmarks are directional.
- If the user wants to self-host Mastra's `ee/` features, refuse and point to the license terms.
- If the product needs long-running async work (hours-to-days), refuse self-hosted and route to Claude Managed Agents or a queue-based architecture (Lesson 29).

Output: decision doc + scaffold + README. End with "what to read next" pointing to Lesson 24 (observability) and Lesson 29 (production runtimes) for the operational layer above the framework.

Solutions

SolutionP1 · No: same model, same behaviour

No. Both frameworks pass the tool's schema to the same model and run whatever it asks for. For "What is the status of A-1002?" both call the tool and answer "currently processing"; for "Where is my order A-1001?" both get a reply asking for the order ID and no tool call. Tool use is decided by the model; the framework only carries the request.

SolutionB1 · The model calls were the latency

Latency was never in agent creation. Four calls to a hosted model at, say, 0.8 to 2 seconds each make up essentially the whole request; LangGraph's overhead per request was likely milliseconds at most, and Agno's microseconds save nothing visible. The migration changed the part of the time budget that was already near zero.

What would help: fewer model calls (merge steps, route easy requests to one call), smaller and faster models for the easy steps, shorter prompts and prompt caching, streaming the final answer so the user sees text sooner, and running independent calls in parallel. Measure the time per span first (lesson 14.23) and optimise the largest one.
