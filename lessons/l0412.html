Why this came about

Judging RAG answers by eye did not scale, and word-overlap metrics did not capture correctness. Frameworks such as RAGAS (2023) introduced component metrics for retrieval and generation, often scored by a model acting as judge, so RAG systems could be tested on every change.

In plain words first
Grading the open-book exam

Evaluating RAG means checking both halves on a fixed set of questions: did retrieval bring the right passages (context precision and recall), and is the answer faithful to them and relevant to the question (faithfulness, answer relevance). Many of these are scored by a model acting as judge, which itself must be checked against human labels before you trust it.

Generation metrics

These need a judge (a model, or people) because they are about meaning. The names come from RAGAS and are now industry vocabulary:

Metric Question it answers Needs
Faithfulness (groundedness) Is every claim in the answer supported by the retrieved context? Question, answer, contexts
Answer relevance Does the answer address the question? Question, answer
Context precision Are the retrieved passages relevant, with the useful ones ranked first? Question, contexts, reference
Context recall Does the retrieved context contain everything the reference answer needs? Question, contexts, reference answer
Answer correctness Does the answer match the reference? Answer, reference

TruLens calls the first three together the RAG triad: context relevance, groundedness and answer relevance. If all three are high, the answer is very likely trustworthy.

Running RAGAS and DeepEval

Both are open-source libraries that use an LLM as the judge (LLM-as-a-judge). Code below was checked against RAGAS 0.4.3 and DeepEval 4.3 (imports and function signatures), not run against a live judge.

# RAGAS 0.4: metrics are objects you score one sample at a time (async)
import asyncio
from openai import AsyncOpenAI
from ragas.llms import llm_factory
from ragas.metrics.collections import Faithfulness, ContextRecall

judge = llm_factory("gpt-5.5", client=AsyncOpenAI())       # any capable model as the judge

async def score():
    contexts = ["Damaged or defective items are always refundable if reported within 30 days."]
    f = await Faithfulness(llm=judge).ascore(
        user_input="Can I return a mixer that arrived broken 2 weeks ago?",
        response="Yes, damaged items are refundable within 30 days.",
        retrieved_contexts=contexts)
    r = await ContextRecall(llm=judge).ascore(
        user_input="Can I return a mixer that arrived broken 2 weeks ago?",
        retrieved_contexts=contexts,
        reference="Yes. Damaged items are refundable if reported within 30 days of delivery.")
    print("faithfulness", f.value, "context recall", r.value)

asyncio.run(score())
Watch out

# DeepEval: pytest-style test cases and metrics with pass thresholds
from deepeval import evaluate
from deepeval.test_case import LLMTestCase
from deepeval.metrics import FaithfulnessMetric, ContextualRecallMetric

case = LLMTestCase(
    input="Can I return a mixer that arrived broken 2 weeks ago?",
    actual_output="Yes, damaged items are refundable within 30 days.",
    expected_output="Yes. Damaged items are refundable if reported within 30 days of delivery.",
    retrieval_context=["Damaged or defective items are always refundable if reported within 30 days."],
)
evaluate(test_cases=[case], metrics=[FaithfulnessMetric(threshold=0.8), ContextualRecallMetric(threshold=0.8)])

Step by step: a RAG evaluation harness you own

Libraries are useful, but the teams with the most reliable RAG systems own a small harness: their questions, their metrics, their judge, calibrated against their experts, running in CI. The blocks below build one over the Lessons 5.37 and 14.143 retrievers.

Step 1 · Generate a test set, including the hard cases

Start from the corpus: for each chunk, ask a model for questions that the chunk answers, then add the variations real users produce. The generator here is a stand-in that applies the same transformations a prompted model would.

import random

def generate_questions(chunk_id: str, text: str) -> list[dict]:
    """Stands in for: 'Write 2 questions a customer might ask that this passage answers. Vary the wording.'"""
    first = text.split(". ")[1] if ". " in text else text
    key = [w for w in tokenize(first) if len(w) > 4][:3]
    return [{"q": f"What does the help centre say about {' '.join(key)}?", "gold": chunk_id, "type": "direct"}]

def add_typos(q: str, rng) -> str:
    words = q.split()
    i = rng.randrange(len(words))
    w = words[i]
    words[i] = w[:-2] + w[-1] + w[-2] if len(w) > 3 else w            # swap two letters
    return " ".join(words)

rng = random.Random(3)
EVAL = []
for cid, _, text in CHUNKS:
    for item in generate_questions(cid, text):
        EVAL.append(item)
        EVAL.append({**item, "q": add_typos(item["q"], rng), "type": "typo"})
EVAL += [{"q": q, "gold": g, "type": "real"} for q, g in GOLD]                       # real user phrasing
EVAL += [{"q": "mera refund kab tak aayega UPI pe?", "gold": "refund-policy#1", "type": "hinglish"},
         {"q": "Do you deliver to Dubai?", "gold": None, "type": "unanswerable"},
         {"q": "What is your stock price?", "gold": None, "type": "unanswerable"}]
seen, deduped = set(), []
for item in EVAL:                                                                   # drop exact duplicates
    if item["q"].lower() not in seen:
        seen.add(item["q"].lower()); deduped.append(item)
EVAL = deduped
print(len(EVAL), "questions:", {t: sum(e["type"] == t for e in EVAL) for t in ("direct", "typo", "real", "hinglish", "unanswerable")})
print(EVAL[2])

Synthetic questions are a starting point; they are usually easier than real ones because they reuse the passage's words. That is why the set mixes in real phrasing, typos, Hinglish and questions with no answer. Replace synthetic items with real traffic as it arrives.

Step 2 · Per-segment metrics with confidence intervals

Averages hide failing segments, and small eval sets give noisy numbers. Report each metric per question type, with a bootstrap confidence interval (resample the questions many times and see how much the metric moves).

def bootstrap_ci(values: list[float], n: int = 2000, seed: int = 0) -> tuple[float, float]:
    r = random.Random(seed)
    means = sorted(sum(r.choice(values) for _ in values) / len(values) for _ in range(n))
    return means[int(0.025 * n)], means[int(0.975 * n)]

def evaluate_retriever(fn, items: list[dict], k: int = 3) -> dict:
    by_type = {}
    for e in items:
        if e["gold"] is None:
            continue
        by_type.setdefault(e["type"], []).append(float(e["gold"] in fn(e["q"], k)))
    overall = [v for vs in by_type.values() for v in vs]
    lo, hi = bootstrap_ci(overall)
    return {"recall@3": round(sum(overall) / len(overall), 2), "95% CI": (round(lo, 2), round(hi, 2)),
            **{t: round(sum(v) / len(v), 2) for t, v in by_type.items()}}

for name, fn in [("BM25", search_bm25), ("Hybrid", search_hybrid), ("Hybrid + rerank", search_reranked)]:
    print(f"{name:16}", evaluate_retriever(fn, EVAL))

Hybrid           {'recall@3': 1.0, '95% CI': (1.0, 1.0), 'direct': 1.0, 'typo': 1.0, 'real': 1.0, 'hinglish': 1.0}

Three findings. Hybrid and reranked retrieval reach 1.0 in every segment, while BM25 loses ground on generated and misspelled questions. BM25's interval is wide (0.76 to 1.0): with 25 answerable questions, a difference of a few points is noise, so grow the set before trusting small gains. And the Hinglish question passes only because it contains the English words "refund" and "UPI"; a question written fully in Hindi or in Devanagari script would fail with these word tokenizers (Lesson 5.38), so add those cases before you claim the system works for Indian users.

Step 3 · An LLM judge for faithfulness, and calibrating it

Generation metrics need a judge. A good faithfulness judge splits the answer into claims and checks each against the context; that is what RAGAS does internally. Whatever judge you use, do judge calibration: label a sample yourself and measure agreement. Cohen's kappalater · 14.118 measures agreement beyond chance (1.0 perfect, 0 no better than chance; above about 0.6 is usually acceptable for a judge).

from sklearn.metrics import cohen_kappa_score, confusion_matrix

def faithfulness(answer: str, context_ids: list[str]) -> float:
    """Share of claims supported by the context (uses Lesson 4.11's verifier as the judge stand-in)."""
    results = verify(answer, context_ids)
    return sum(ok for _, ok in results) / len(results)

CASES = [   # (answer, contexts, human verdict: 1 = faithful, 0 = not)
    ("Damaged items are refundable if reported within 30 days.", ["refund-policy#1"], 1),
    ("UPI refunds usually arrive in 2 days.", ["refund-policy#1"], 1),
    ("Express delivery costs INR 49 in 40 cities.", ["shipping#1"], 0),        # wrong price
    ("COD orders get a free gift.", ["cod#0"], 0),
    ("Refunds take 5 to 7 business days and include a bonus voucher.", ["refund-policy#1"], 0),
    ("You can cancel before dispatch from the Orders page.", ["cancellation#0"], 1),
    ("Warranty is three years on all appliances.", ["warranty#0"], 0),
    ("Delete your account from Settings, Privacy.", ["account#0"], 1),
]
judge = [int(faithfulness(a, ctx) == 1.0) for a, ctx, _ in CASES]
human = [h for *_, h in CASES]
print("judge:", judge)
print("human:", human)
print("kappa:", round(cohen_kappa_score(human, judge), 2))
print("confusion [[TN FP] [FN TP]]:", confusion_matrix(human, judge).tolist())
What you should see
judge: [1, 1, 1, 0, 0, 1, 0, 1]
human: [1, 1, 0, 0, 0, 1, 0, 1]
kappa: 0.75
confusion [[TN FP] [FN TP]]: [[3, 1], [0, 4]]

The judge agrees with the human on 7 of 8. Its one miss is a false positive: "INR 49" against a context that says INR 99 passes, because word overlap cannot see a wrong number. That case belongs in the judge's own test set. Real LLM judges handle numbers far better but have their own blind spots (long answers, partial support, hedged claims), so keep measuring agreement whenever the judge prompt or model changes (Lesson 14.118).

Step 4 · Measure abstention

A RAG system must say "I don't know" when the corpus has no answer, and must not say it when the answer is there. Treat abstention as a classifier and measure both errors.

def answer_or_abstain(question: str, threshold: float = 2.0) -> str | None:
    """Abstain when the best reranker score is too low (a real system also asks the model to abstain)."""
    best = max(search_hybrid(question, 5), key=lambda c: rerank_score(question, TEXT[c]))
    return None if rerank_score(question, TEXT[best]) < threshold else best

rows = [(e["q"], e["gold"] is None, answer_or_abstain(e["q"]) is None) for e in EVAL]
should = sum(s for _, s, _ in rows)
correct_abstain = sum(s and a for _, s, a in rows)
false_abstain = sum((not s) and a for _, s, a in rows)
print(f"abstained on {correct_abstain}/{should} unanswerable questions")
print(f"wrongly abstained on {false_abstain}/{len(rows) - should} answerable questions")
for q, s, a in rows:
    if (not s) and a:
        print("  false abstention:", q)
What you should see
abstained on 2/2 unanswerable questions
wrongly abstained on 1/25 answerable questions
  false abstention: What does faster delivery cost?

Both unanswerable questions were caught, at the cost of one false abstention: "faster delivery" shares no strong word with the passage about express delivery, the same vocabulary gap Lesson 14.143's query rewriting fixes. Move the threshold and watch the trade-off; then decide with the business which error is worse. For a support bot, a false abstention means a human handles the question; a missed abstention means a confident wrong answer.

Step 5 · A regression gate for CI

The harness becomes useful when it runs on every change and blocks regressions against a stored baseline.

import json, pathlib, tempfile

def gate(current: dict, baseline: dict, tolerance: float = 0.02) -> list[str]:
    """Fail on any metric that drops more than `tolerance` below the baseline."""
    return [f"{m}: {baseline[m]:.2f} -> {current.get(m, 0):.2f}" for m in baseline
            if isinstance(baseline[m], float) and current.get(m, 0) < baseline[m] - tolerance]

baseline_file = pathlib.Path(tempfile.mkdtemp()) / "rag_baseline.json"
baseline_file.write_text(json.dumps(evaluate_retriever(search_hybrid, EVAL)))       # saved from the last release

baseline = json.loads(baseline_file.read_text())
candidate = evaluate_retriever(search_bm25, EVAL)                                  # someone "simplified" retrieval
failures = gate(candidate, baseline)
print("BLOCKED:" if failures else "PASS", failures)
What you should see
BLOCKED: ['recall@3: 1.00 -> 0.88', 'direct: 1.00 -> 0.89', 'typo: 1.00 -> 0.86', 'real: 1.00 -> 0.88']

A change that looked harmless dropped recall on real and misspelled questions, and the gate caught it before users did. Store the baseline in the repository next to the eval set, and update it deliberately when a change is accepted.

Building the eval set

  1. Synthetic questions first: for each chunk, ask a model to write one or two questions that the chunk answers. That gives labeled (question, correct chunk) pairs before any users exist. Aim for retrieval recall of 80 to 90% on these before launch.
  2. Make them realistic: vary phrasing, add typos and Hinglish, add multi-part questions and questions with no answer in the corpus (to test abstention).
  3. Add real traffic after launch: sample questions from logs, especially those with negative feedback, and have experts write reference answers.
  4. Segment: tag questions by type (policy, product, order-specific, comparison) and report metrics per segment. Averages hide the segment that is failing.
  5. Re-run on every change to chunking, embeddings, prompts or models, and block releases that regress (Lesson 14.118).
In production
Eval-set mistakes that make scores lie
  • Synthetic questions that copy the chunk's wording: retrieval looks excellent because the question shares every keyword with its answer. Ask the generator to paraphrase, use synonyms and write the way customers write, and keep real questions as the majority once you have traffic.
  • No unanswerable questions: the system is never tested on saying "I don't know", which is where hallucinations hurt most.
  • A frozen set: the set stops matching what users ask. Add a sample of new production questions every month.
  • One average for everything: a 90% average can hide a 40% segment (order-specific or Hindi questions, say). Always report per segment.
  • Judges nobody checked: an LLM judge that agrees with experts 60% of the time makes every comparison noise. Calibrate first (Lesson 14.118).

From the field
Morgan Stanley and DoorDash: evals before launch, regression tests after

Morgan Stanley's wealth-management assistant answers advisors' questions from about 100,000 internal documents. According to OpenAI's case study, every use case went through an evaluation framework before deployment (graded summarization, translation and retrieval accuracy, with advisors and prompt engineers as graders), and daily regression tests run sample questions afterwards. Tuning retrieval raised the share of documents the assistant could draw on from 20% to 80%, and more than 98% of advisor teams use it. Source: OpenAI, "Morgan Stanley".

DoorDash's support assistant for delivery drivers (2024) monitors five areas with LLM judges and regex checks (retrieval correctness, response accuracy, grammar, coherence and relevance), calibrated by a human team that reviews sampled transcripts. Prompt changes must pass a promptfoo regression suite before release. Source: DoorDash Engineering, "Building a high-quality RAG-based support system".

Exercises

Predict before you run

System A scores 82% and system B 85% on 100 questions. Can you conclude B is better? What does a confidence interval tell you? (Solution P1.)

Break it on purpose

Generate the test set only from chunks, with questions written by the same model that will answer them. What bias does that create? (Solution B1.)

Debugging exercise

Faithfulness scores from an LLM judge jumped after the judge model was upgraded, with no change to the RAG system. Explain and fix. (Solution D1.)

Make it your own

Add a segment for Hinglish questions to the harness and report metrics with intervals per segment. (Solution M1.)

Solutions

SolutionP1 · Small samples, wide intervals

Not yet: on 100 questions, the 95% interval for each score is roughly plus or minus 7 to 8 points, so the difference can be noise. Use a paired comparison on the same questions, more questions, or report the interval with the score (Step 2).

SolutionB1 · Synthetic tests flatter the system

Questions mirror the chunk's wording, so retrieval is easy and the set misses real users' phrasing, typos, Hinglish and unanswerable questions. Mix in real questions, add the hard cases on purpose, and have people review a sample.

SolutionD1 · Judges drift too

The judge changed, not the system. Pin the judge model and prompt, re-calibrate against human labels after any change, and track judge agreement as a metric of its own.

SolutionM1 · Segments reveal hidden failures

Overall averages hide small groups. Tag each question with its segment, compute each metric per segment with intervals, and gate releases on the worst important segment, not just the average.

Explain the mechanismWhat are RAGAS-style generation metrics, and what do they measure?

Worked answer. Faithfulness (claims supported by the retrieved context), answer relevance (the answer addresses the question), context precision and recall (whether retrieved passages are relevant and cover the needed information), and answer correctness against references. Most use an LLM judge, so they need calibration against human labels.

A plausible wrong answer. "They measure accuracy." Faithfulness can be perfect for a wrong answer if the context was wrong.

Follow-ups. When would you trust an LLM judge?

Debug a failureYour eval shows no regressions, but users complain after a release. Why?

Worked answer. The eval set does not represent current traffic: new topics, phrasings or languages, or the failing cases were never added. Sample production questions, label them, add failures to the set, and segment by question type.

A plausible wrong answer. "Users are wrong." Users are the ground truth the eval set is meant to approximate.

Follow-ups. How would you keep the eval set fresh?

Defend a designRAGAS, DeepEval, or your own harness?

Worked answer. Libraries for standard metrics and fast setup; your own harness when you need control: your segments, your judges, intervals, and integration with your release gates. Many teams use library metrics inside their own harness. The question set matters more than the library.

A plausible wrong answer. "A library is enough; no labels needed." Without labeled data, metrics have nothing to calibrate against.
