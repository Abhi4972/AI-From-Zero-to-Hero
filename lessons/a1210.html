In plain words first
The idea in one line

Every open VLM before InternVL3 followed the same three-step recipe: take a text LLM trained on trillions of text tokens, bolt on a vision encoder, then fine-tune the seams. This works but has alignment debt — the text LLM has spent its full pretraining budget on pure text and does not natively understand visual tokens. When you add vision post-hoc, the LLM has to re-learn how to relate visual input to its text reasoning without forgetting the text. The problem

In plain words first

Most open vision-language models are built in steps: take a finished text model, attach an image encoder, train a small adapter between them, then fine-tune. The text model never saw images while it was learning language, and the later stages can wear away some of its text skills. InternVL3 (April 2025) changes the order. It starts from a pretrained image encoder and a pretrained language model like everyone else, but then trains all their parameters together in one large pretraining stage, on image and text data mixed with plain text. It also introduces V2PE, a way to let image tokens use up fewer position numbers, so long documents with many images fit. Its successor, InternVL3.5, adds deployment tricks for speed. This lesson explains these ideas. It runs InternVL3's real image preprocessing (configuration files only) and checks V2PE's position arithmetic. No model is trained or downloaded.

Post-hoc VLM training is the default. LLaVA, BLIP-2, Qwen-VL, Idefics — all take an already-pretrained LLM (Llama, Vicuna, Qwen, Mistral) and add vision. The training stages typically look like:

  1. Frozen LLM + frozen vision encoder + trainable projector, trained on caption pairs to align embeddings.
  2. Unfreeze LLM, train on instruction data (LLaVA-Instruct, ShareGPT4V).
  3. Optional task-specific fine-tune.

Three symptoms of alignment debt show up:

  • Catastrophic forgetting. The post-hoc VLM loses some text-only skill: scores on text benchmarks such as math word problems often drop after multimodal fine-tuning, which is why many recipes mix text-only data back in.
  • Answer drift. Small phrasings of the same visual question get different answers. The vision encoder connects to the LLM with weaker bindings than the LLM's own tokens.
  • Visual-text inconsistency. The VLM can describe an image correctly and then answer a question contradicting its own description. Visual tokens do not participate in the LLM's internal consistency checks the same way text does.

These symptoms are well-documented. MM1.5 Section 4 quantifies them. LLaVA-OneVision's ablations hint at them. Native pretraining is the answer.

Idea 1 · Native multimodal pretraining

InternVL3 does not start from nothing: it begins with a pretrained vision encoder (InternViT) and a pretrained language model (Qwen2.5 or InternLM3), joined by an MLP projector. What changes is the next step. Instead of first aligning a frozen LLM and then fine-tuning in stages, InternVL3 trains all parameters in one pretraining stage on a mixture of multimodal data (captions, interleaved documents, OCR, video and more) and text-only corpora. Vision tokens, text tokens and cross-modal interactions all share the same next-token loss from the start of that stage, and the text-only data keeps the language skills from eroding.

Training is a single stage for the base model; supervised fine-tuning and preference optimisation follow.

Idea 2 · V2PE (variable visual position encoding)

Qwen2-VL's M-RoPE gives visual tokens separate time, row and column positions. InternVL3's V2PE (variable visual position encoding) solves a different problem: long multimodal contexts. Text tokens advance the position index by 1, as usual. Visual tokens advance it by a smaller step δ (for example 1/2, 1/4 or 1/16), so hundreds of image tokens use up only a few positions. During training δ is sampled from a set of values; at inference a fixed δ is chosen.

The benefit: a document with dozens of images stays within the position range the language model handles well, which helps long-context multimodal tasks. RoPE works with fractional positions, so no new parameters are needed (measured below).

The same idea as a formula

Tokens per image. InternVL3 cuts an image into up to 12 tiles of 448 × 448 (plus a thumbnail when tiled). Each tile has 32×32 patches of 14 px, and pixel shuffle with ratio 0.5 merges each 2×2 block:

ntile​=(32⋅0.5)2=256,nimage​=256×(tiles+thumbnail).

V2PE positions. With text step 1 and visual step δ, a document with nt​ text and nv​ visual tokens ends at position about

pmax​≈nt​+δnv​(plus one step at each switch).

RoPE at a fractional position p: the rotation angle for frequency θi​ is simply pθi​, so δ<1 needs no new parameters.

Worked example
Forty images in one document
  • 40 images at one tile each: 40×256=10,240 visual tokens; with 41 text blocks of 400 tokens, 16,400 text tokens, 26,640 in all.
  • Plain positions (δ=1): the last token sits at position 26,639.
  • With δ=1/4: about 16,400+10,240/4=18,960, plus one extra step at each of the 80 switches: 18,989 (measured below).
  • With δ=1/16: about 17,076. The positions are those of a mostly-text document, a range the language model knows well.

Tiles and tokens in the real InternVL3 processor

InternVL3-1B's Hugging Face processor (configuration and tokenizer files, no weights) counts tiles and visual tokens for four image shapes. Then the 1B model is built on the meta device to show where its parameters sit. A few seconds.

import torch
from PIL import Image
from transformers import AutoConfig, AutoModelForImageTextToText, AutoProcessor, logging
logging.set_verbosity_error()

# InternVL3's real processor (1B model's config and tokenizer files, no weights): 448-px tiles, pixel shuffle
repo = "OpenGVLab/InternVL3-1B-hf"
proc, cfg = AutoProcessor.from_pretrained(repo), AutoConfig.from_pretrained(repo)
g = cfg.vision_config.image_size[0] // cfg.vision_config.patch_size[0]
per_tile = int((g * cfg.downsample_ratio) ** 2)
print(f"one 448-px tile: {g}x{g} patches of 14 px; pixel shuffle (ratio {cfg.downsample_ratio}) -> {per_tile} LLM tokens\n")
ask = proc.apply_chat_template([{"role": "user", "content": [{"type": "image"}, {"type": "text", "text": "?"}]}],
                               add_generation_prompt=True)
print(f"{'image (w x h)':<16}{'tiles':>7}{'LLM tokens':>12}")
for w, h in [(448, 448), (1024, 768), (1920, 1080), (800, 3000)]:
    x = proc(images=Image.new("RGB", (w, h)), text=ask, return_tensors="pt")
    print(f"{f'{w} x {h}':<16}{x.pixel_values.shape[0]:>7}{int((x.input_ids == cfg.image_token_id).sum()):>12,}")

with torch.device("meta"):
    m = AutoModelForImageTextToText.from_config(cfg)
parts = {"vision encoder (InternViT)": "vision_tower", "projector (MLP)": "multi_modal_projector", "language model": "language_model"}
sizes = {k: sum(p.numel() for n, p in m.named_parameters() if v in n) for k, v in parts.items()}

Reading this output

256 tokens per tile. A 448-px tile is a 32 × 32 grid of 14-px patches. Pixel shuffle folds each 2 × 2 block into one wider token, giving 16 × 16 = 256 tokens for the LLM. A 448 × 448 image is exactly one tile.

Cost depends on the tile grid. A 1024 × 768 photo gets 12 tiles plus a thumbnail, 13 × 256 = 3,328 tokens. A 1920 × 1080 screenshot gets 8 + 1 = 9 tiles, 2,304 tokens. A tall 800 × 3000 page gets only 4 + 1 tiles (1,280 tokens), because the grid that best matches its shape is narrow. That narrow grid may be too coarse for small text, so measure documents before trusting the defaults.

The 1B model shows what "native" starts from. InternVL3-1B is a 304M InternViT, a 4M MLP projector and a 494M language model. That is exactly the size of Qwen2.5-0.5B, the pretrained LLM it starts from. Native pretraining changes how these parts are trained together, not where they come from.

V2PE: positions for a long interleaved document

A document of 40 images (256 tokens each) and 41 text blocks (400 tokens each) gets position ids with visual steps δ = 1, 1/2, 1/4 and 1/16. Then RoPE angles are computed at a whole and a fractional position. Instant.

import torch
# V2PE: text tokens advance the position index by 1; visual tokens advance it by a smaller step delta,
# so a long interleaved document uses far fewer positions than it has tokens.
segments = []                                   # a document: 40 images (256 tokens each) with 300 words between them
for i in range(40):
    segments += [("text", 400), ("image", 256)]
segments.append(("text", 400))
n_tokens = sum(n for _, n in segments)

def positions(delta):
    pos, p = [], 0.0
    for kind, n in segments:
        step = 1.0 if kind == "text" else delta
        pos += [p + step * i for i in range(n)]
        p = pos[-1] + 1.0                       # the next segment starts one full step later
    return torch.tensor(pos)

print(f"document: {n_tokens:,} tokens ({sum(n for k, n in segments if k == 'image'):,} visual, "
      f"{sum(n for k, n in segments if k == 'text'):,} text)\n")
print(f"{'visual step delta':<20}{'last position id':>18}{'positions per token':>21}")
for delta in [1, 1 / 2, 1 / 4, 1 / 16]:
    p = positions(delta)
    print(f"{f'1/{round(1 / delta)}' if delta < 1 else '1 (plain RoPE)':<20}{p[-1].item():>18,.1f}{p[-1].item() / n_tokens:>21.2f}")

# RoPE works with fractional positions: angles are just position x frequency
d, base = 64, 10000.0
freqs = base ** (-torch.arange(0, d, 2) / d)
for pos in [3.0, 3.25]:
    print(f"\nposition {pos}: first three rotation angles {[round(a, 3) for a in (pos * freqs[:3]).tolist()]}", end="")
print("\n(the angles change smoothly, so a quarter step is a valid, distinct position)")

Reading this output

Visual tokens stop eating the position range. The document has 26,640 tokens. With ordinary positions (δ = 1) the last token sits at 26,639. With δ = 1/4 it sits at 18,989, and with δ = 1/16 at 17,076.5. That is close to the 16,400 text tokens alone, so 10,240 image tokens cost the position range of fewer than 700 text tokens. For a model whose RoPE works best within its trained length, this keeps long multimodal documents in familiar territory.

Fractional positions are ordinary RoPE. The rotation angles at position 3.25 lie between those at 3 and 4 (3.25 against 3.0 for the first frequency, 2.437 against 2.25 for the second). Nothing new is learned: only the step size changes. That is why V2PE could be trained with several δ values and used with a fixed one at inference.

The price: image tokens next to each other are now very close in position, so the model distinguishes them less by position and more by content. The InternVL3 paper chose the δ values through ablations.

Idea 3 · Visual Resolution Router (ViR)

Introduced with InternVL3.5 (August 2025), not InternVL3. Not every image patch needs the same number of tokens: a patch of sky carries less than a patch of small text. ViR is a small trained router that chooses, per image patch, how strongly to compress its visual tokens, keeping more tokens where detail matters.

The InternVL3.5 paper reports that ViR roughly halves the visual tokens with almost no loss in accuracy.

Idea 4 · Decoupled Vision-Language deployment (DvD)

Also from InternVL3.5. When you serve a large VLM, the vision encoder runs once per image but the LLM runs autoregressively for every output token. The two components have different bottlenecks (the encoder is compute-bound on big batches of patches; the LLM decode is bound by memory and KV cache). DvD puts the vision encoder and the language model on different GPUs and streams visual features between them, so each can be batched and scaled on its own.

Together, ViR and DvD account for most of the up-to-4.05× inference speedup InternVL3.5 reports over InternVL3.

Idea 5 · Single-stage vs multi-stage quality

InternVL3's main benchmark claim: InternVL3-78B scores 72.2 on MMMU, a new state of the art among open models at release (April 2025), and its report calls it highly competitive with GPT-4o, Claude 3.5 Sonnet and Gemini 2.5 Pro. The smaller models (1B to 38B) lead their size classes on many benchmarks.

The paper also reports that the native recipe keeps text performance close to that of the underlying language models, supporting the alignment-debt argument.

Idea 6 · InternVL3.5 and InternVL-U

InternVL3.5 (August 2025) adds Cascade RL (offline reinforcement learning, then online RL) for reasoning, with up to +16% on reasoning benchmarks over InternVL3, plus ViR and DvD for efficiency. The largest model is a 241B-parameter mixture of experts (InternVL3.5-241B-A28B).

InternVL-U (March 2026) is a 4B-parameter unified model: an InternVL-style understanding model with an MMDiT-based image-generation head, for understanding, reasoning, generation and editing in one model (Lesson 12.13 covers unified models).

Idea 7 · Trade-offs of native pretraining

Native pretraining is not free:

  • Compute. Joint training of all parameters on a large multimodal corpus costs much more than training a projector; it is a pretraining run, not a fine-tune.
  • Data. Interleaved image-text corpora at scale are rare. OBELICS is 141M documents; MMC4 is 571M. Text alone ships at 15T tokens. Multimodal pretraining data scarcity is a hard constraint.
  • Base-LLM reuse. A natively pretrained VLM is tied to the LLM it started from; moving to a newer LLM means repeating the joint pretraining, whereas a post-hoc recipe only retrains the adapter and the fine-tuning stages.

The bet InternVL3 makes: the alignment debt is worse than the extra training cost. Post-hoc VLMs will keep existing because they remain cheaper for most projects.

Industry practice
What's current (2024–2026)
  • InternVL3 and InternVL3.5: InternVL3 (April 2025, 1B–78B) introduced native multimodal pretraining and V2PE; InternVL3.5 (August 2025, up to 241B-A28B) adds Cascade RL, ViR and DvD with up to 4.05× faster inference.
  • Joint multimodal pretraining is spreading: Qwen3-VL and other recent families also mix text-only data into multimodal training to keep language skills.
  • Unified models from the same line: InternVL-U (March 2026, 4B) adds an MMDiT image-generation head.
  • Laptop-sized options: InternVL3-1B and 2B (and InternVL3.5-1B/2B) run on an 8 GB GPU in bf16; lower the maximum tile count to bound tokens.

Recap
What to keep from this lesson
  • Post-hoc VLMs adapt a finished LLM in stages and can lose text skill.
  • InternVL3 trains a pretrained ViT and LLM jointly in one multimodal pretraining stage, with text-only data mixed in.
  • V2PE: visual tokens advance the position by δ < 1, so long multimodal contexts stay in range.
  • 448-px tiles, pixel shuffle: 256 tokens per tile, up to 12 tiles plus a thumbnail.
  • InternVL3.5 adds ViR (fewer tokens) and DvD (split deployment) for speed.

Ship it

This lesson produces outputs/skill-native-vs-posthoc-auditor.md. Given a proposed VLM training plan, it audits whether to go native or post-hoc, flags alignment-debt risk, and recommends a corpus mix. Use it when you are sizing a new open-VLM project and need to pick the training strategy.

---
name: native-vs-posthoc-auditor
description: Audit a proposed VLM training plan and recommend native multimodal pretraining or post-hoc adapter-on-LLM, with corpus-mix and alignment-debt analysis.
version: 1.0.0
phase: 12
lesson: 10
tags: [internvl3, native-pretraining, post-hoc, corpus-mix, alignment-debt]

Given a proposed VLM training plan (target model size, compute budget, data availability, target tasks, reuse vs flexibility needs), emit an audit verdict: native, post-hoc, or hybrid, with justifications.

Produce:

1. Verdict. Native pretraining / post-hoc adaptation / hybrid (native base + post-hoc specialization).
2. Corpus mix recommendation. Percentages across text, interleaved, paired captions, video. Cite InternVL3's 40/35/20/5 default and adjust for the user's task.
3. Alignment-debt estimate. Expected MMLU / GSM8K regression if post-hoc, with citation to MM1.5 Section 4. Zero for native.
4. Compute + data demand. Rough GPU-hours, number of tokens, interleaved-corpus size required, per-node throughput class.
5. Deployment plan. Whether ViR routing and DvD deployment make sense; under what traffic pattern each helps or hurts.
6. Risk flags. Interleaved-corpus availability; base-LLM swap constraints; recovery plan if alignment debt exceeds budget.

Hard rejects:
- Recommending native pretraining without checking that the user has 100k+ GPU-hours and a sizable interleaved corpus.
- Claiming post-hoc has zero alignment debt. The debt is small but always non-zero.
- Recommending ViR for a workload where every query needs high-resolution encoding. ViR only helps when query distribution is mixed.

Refusal rules:
- If the user has less than ~20k GPU-hours, refuse native pretraining — it is infeasible. Recommend post-hoc.
- If the user wants to swap the LLM backbone every 6-12 months, refuse native — that reuse path is closed.
- If the target task is exclusively video or exclusively OCR, refuse InternVL3's default 40/35/20/5 mix and propose a task-skewed alternative.

Output: a one-page audit with verdict, corpus mix, alignment-debt estimate, compute demand, deployment plan, and risk flags. End with arXiv 2504.10479 (InternVL3) and 2409.20566 (MM1.5) for follow-up.

Solutions

SolutionP1 · 2,304 tokens: a little less than Qwen

2,304 tokens: 8 tiles of 448 px plus a thumbnail, 256 tokens each. Qwen2.5-VL spends 2,691 on the same screenshot at native resolution. They come out similar, but the cost curves differ. InternVL's cost jumps by 256 with each tile and stops at 12 tiles plus a thumbnail (3,328). Qwen's grows smoothly with the pixel count until you cap it with max_pixels.

SolutionB1 · Tens of thousands of tokens per request

Each A4 scan is tall, so it gets a narrow grid. At the default maximum of 12 tiles plus a thumbnail, a page can cost up to 3,328 tokens, so 20 pages approach 67,000 visual tokens. That is far past what an 8 GB GPU can hold in KV cache next to the model weights. The request fails with out-of-memory, or must be cut. Meanwhile the pages' small print may still be downscaled within each tile. Instead, process a few pages per request and lower the maximum tile count for pages with large text. Raise it only for pages with small print, crop to the region of interest when you can, and check visual token counts before sending, as the run above does.
