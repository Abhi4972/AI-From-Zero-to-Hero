Goal, Question, Metric

In plain words first

A metric is useful only if it can change a decision. Start from the goal, ask the questions that would show it is met, and pick one metric per question. Give each metric a contract: direction, threshold, window, source and population. Pair an outcome metric (did things improve?) with a guardrail (did a fixed limit hold?) and a counter-metric (did the cost move to someone else?). Write the pass, fail and ambiguous rules before any number exists. Evaluation in depth and the business case are covered in Zero to Agents 12.11 and 14.2 (linked above). This lesson measures the 14.50 slice for real and applies rules written in advance.

Start with a goal:

Reduce time to identify the affected service without increasing unsafe actions.

Derive questions:

  • How quickly is the correct service identified?
  • How often is the identified service correct?
  • Does diagnosis remain read-only?
  • Does the workflow increase alert dismissal or operator workload?

Then choose metrics that operationalize those questions.

A Metric Needs a Contract

Every metric needs:

Field Example
Name median_identification_seconds
Direction at most
Threshold 120
Window ten incident replays
Source replay event log
Population on-call engineers in the pilot
Kind outcome or guardrail

Without source and window, a number cannot be reproduced. Without a threshold, it cannot drive a decision.

Outcome, Guardrail, and Counter-Metric

  • Outcome metric: did the desired state improve?
  • Guardrail: did a fixed constraint remain true?
  • Counter-metric: did the local improvement shift cost or harm elsewhere?

For an incident workflow, speed is not enough. Correctness, production writes, operator workload, and missed alerts protect against a fast but unsafe result.

Offline and Online Evidence

Offline replay is useful for repeatability and edge coverage. A bounded pilot is useful for real behavior, trust, and workflow effects. Neither substitutes for the other.

Use the cheapest evidence that can answer the current decision. Do not expose real users merely because the implementation is ready.

Decide Before You Measure

Write the pass, fail, and ambiguous paths before seeing results. Otherwise the team will move the threshold to protect the build.

Example:

  • pass: correct service rate at least 0.9 and median time at most 120 seconds;
  • fail: any production write or correct rate below 0.75;
  • ambiguous: small improvement with wide variance, requiring a larger replay set.
The same idea as a formula

A rate from n cases is a range, not a point. For k successes in n trials, the Wilson 95% interval is

1+nz2​p^​+2nz2​±znp^​(1−p^​)​+4n2z2​​​,p^​=nk​, z=1.96.

Unlike p^​±1.96SE, it stays inside [0,1] and gives a sensible bound at k=n.

The size of n decides what you can prove. With a perfect record (k=n), the lower bound is n+z2n​. It clears 0.75 only when n≥3z2≈11.5, so at least 12 answered cases are needed before a "precision at least 75%" claim is possible.

Worked example
10 of 10 is not a pass yet
  • The lookup gate answered 10 alerts and got all 10 right, so p^​=1.0, above the 0.9 threshold.
  • Its Wilson lower bound is 10+3.8410​=0.722, below the 0.75 the pass rule asks for.
  • So the rule written before the run says "ambiguous: replay 20 more alerts", not "pass". Two more correct answers (n=12) would give 15.8412​=0.758 and clear it.
  • The model's 7 of 14 has an upper bound of 0.732. Even its best case is below 0.75, so the verdict is "fail" on any reading.
Check your mental model
  • ✗ "Precision 1.0 means it passed."
    ✓ On 10 cases the interval reaches down to 0.72, and the rule asked for a lower bound of 0.75.
  • ✗ "More metrics give a safer decision."
    ✓ tokens_generated is read by no rule, so it cannot change the decision. Drop it.
  • ✗ "The replay measured time to identify."
    ✓ It measured model latency (0.28 s an alert). Human time to identify needs pilot timestamps.
  • ✗ "A plan without a guardrail is just incomplete."
    ✓ It is invalid: a fast, unsafe result would pass it.

import math, re

    metrics=[
        Metric("precision_on_answered", "at-least", 0.9, "14-alert replay set from 14.49", "incident record", "outcome"),
        Metric("answer_rate", "at-least", 0.5, "14-alert replay set from 14.49", "replay log", "outcome"),
        Metric("production_writes", "at-most", 0, "every replay and pilot run", "audit log", "guardrail"),
        Metric("wrong_answers_to_undo", "at-most", 1, "14-alert replay set from 14.49", "incident record", "counter"),

# This block continues from the one above. Replay the 14 alerts from 14.49 through two candidates from 14.50: the
# 0.5B model that always answers (Qwen2.5-0.5B-Instruct, greedy, CPU) and the catalog-lookup gate with no model.
# Compute every metric from the replay, run the lesson's report(), and apply the decision rules written above,
# including a Wilson 95% interval on precision. About 30 seconds.
import os, time, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()
CATALOG = {"checkout-api": ("checkout-",), "payments": ("pay-", "card processor"), "inventory": ("inv-", "stock"),
           "search": ("srch-",), "auth": ("auth-", "log in", "login")}
ALERTS = [("HighLatency service=checkout-api p99=2.4s", "checkout-api"), ("ErrorRate service=payments 5xx=7%", "payments"),
          ("PodCrashLooping service=inventory pod=inv-5d8f", "inventory"), ("HighLatency service=search p99=1.9s", "search"),
          ("TokenErrors service=auth invalid_signature=320/min", "auth"), ("PodCrashLooping pod=pay-7f9c namespace=prod", "payments"),
          ("HighMemory pod=srch-2a1b namespace=prod 93%", "search"), ("Users report they cannot log in", "auth"),
          ("Card processor timeouts rising", "payments"), ("Stock counts negative for 40 products", "inventory"),
          ("Checkout errors: upstream card processor timeouts", "payments"), ("DNS resolution failures across prod namespace", "none"),
          ("HighLatency service=checkout-api, caused by inv-5d8f slow queries", "inventory"), ("Login page slow after search deploy", "none")]
catalog_text = "\n".join(f"- {k}: matches {', '.join(v)}" for k, v in CATALOG.items())
TOKENS = {"n": 0}
def model_answer(alert):
    ids = tok.apply_chat_template([{"role": "user", "content": f"Service catalog:\n{catalog_text}\n\nAlert: {alert}\n"
                                    "Which service is failing? Answer with the service name only."}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=10, do_sample=False)
    TOKENS["n"] += out.shape[1]
    ans = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).lower()
    return next((s for s in CATALOG if s in ans), "unknown")
CAUSAL = re.compile(r"caused by|upstream|after .* deploy|across", re.I)
def lookup(alert):
    hits = {s for s, keys in CATALOG.items() if s in alert.lower() or any(k in alert.lower() for k in keys)}
    return next(iter(hits)) if len(hits) == 1 and not CAUSAL.search(alert) else "unknown"

def wilson(k, n, z=1.96):
    if n == 0:
        return (0.0, 1.0)
    p = k / n; d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d; h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / d
    return (round(c - h, 3), round(c + h, 3))

for name, fn in (("model, always answers", model_answer), ("lookup gate, no model", lookup)):
    TOKENS["n"], t0 = 0, time.time()
    answers = [fn(a) for a, _ in ALERTS]
    secs = (time.time() - t0) / len(ALERTS)
    answered = [(a, t) for a, (_, t) in zip(answers, ALERTS) if a != "unknown"]
    right = sum(a == t for a, t in answered)
    values = {"precision_on_answered": round(right / len(answered), 3) if answered else 0.0,
              "answer_rate": round(len(answered) / len(ALERTS), 3), "production_writes": 0,
              "wrong_answers_to_undo": len(answered) - right, "tokens_generated": TOKENS["n"]}
    r = report(PLAN, values)
    lo, hi = wilson(right, len(answered))
    v = values
    if v["production_writes"] > 0 or v["precision_on_answered"] < 0.75:
        verdict = "fail"
    elif v["precision_on_answered"] >= 0.9 and v["answer_rate"] >= 0.5 and v["wrong_answers_to_undo"] <= 1 and lo >= 0.75:
        verdict = "pass"
    else:
        verdict = "ambiguous"
    print(f"{name}   ({secs:.2f} s per alert)")
    for res in r["results"]:
        print(f"   {res['name']:<24} {str(res.get('value')):<8} {'pass' if res.get('passed') else 'FAIL'}")
    print(f"   precision {right}/{len(answered)}, Wilson 95% interval {lo}-{hi}")
    print(f"   decision: {verdict}  ({DECISIONS[verdict] if verdict == 'ambiguous' else DECISIONS[verdict][:60]})\n")

n_needed = next(n for n in range(5, 200) if wilson(n, n)[0] >= 0.75)
print(f"answered alerts needed before even a perfect record clears a 0.75 lower bound: {n_needed}")

Reading this output

The model fails. It answers all 14 alerts and gets 7 right, so precision is 0.5 and there are 7 wrong answers for the on-call engineer to undo. The counter-metric catches the cost that answering everything pushes onto people. Its whole Wilson interval (0.27 to 0.73) lies below 0.75.

The lookup is ambiguous, not a pass. Every per-metric threshold passes: precision 1.0, answer rate 0.71, no wrong answers. But 10 of 10 gives a lower bound of 0.722, and the rule written beforehand asks for 0.75. So the next step is the one written down: replay 20 more alerts.

Twelve is the floor. A perfect record needs at least 12 answered alerts to clear that bound. The replay also measured latency, 0.28 s per alert for the model. That says nothing about how quickly a person identifies the service, which only a pilot can measure.

# Lesson program for deriving reproducible metrics from outcome goals.
# Read: phases/14-agent-engineering/52-design-success-metrics/docs/en.md
# Reference: Basili, Software Modeling and Measurement: The GQM Paradigm, 1992.
# Reference: Basili, Caldiera, and Rombach, The Goal Question Metric Approach.
# Run this file to generate outputs/measurement-report.json.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Metric:
    name: str
    direction: str
    threshold: float
    window: str
    source: str
    kind: str


@dataclass
class MeasurementPlan:
    goal: str
    questions: list[str]
    metrics: list[Metric]


def validate(plan: MeasurementPlan) -> list[str]:
    issues: list[str] = []
    if not plan.goal.strip():
        issues.append("goal is empty")
    if not plan.questions:
        issues.append("questions are empty")
    if not plan.metrics:
        issues.append("metrics are empty")
    kinds = {metric.kind for metric in plan.metrics}
    if "outcome" not in kinds:
        issues.append("outcome metric is missing")
    if "guardrail" not in kinds:
        issues.append("guardrail metric is missing")
    for metric in plan.metrics:
        if metric.direction not in {"at-most", "at-least"}:
            issues.append(f"{metric.name} has invalid direction")
        if not metric.source.strip() or not metric.window.strip():
            issues.append(f"{metric.name} lacks source or window")
    return issues


def evaluate(metric: Metric, value: float) -> bool:
    if metric.direction == "at-most":
        return value <= metric.threshold
    if metric.direction == "at-least":
        return value >= metric.threshold
    raise ValueError("invalid direction")


def report(plan: MeasurementPlan, values: dict[str, float]) -> dict:
    issues = validate(plan)
    results = []
    for metric in plan.metrics:
        if metric.direction not in {"at-most", "at-least"}:
            result = {"name": metric.name, "status": "invalid"}
            if metric.name in values:
                result["value"] = values[metric.name]
            results.append(result)
        elif metric.name not in values:
            results.append({"name": metric.name, "status": "missing"})
        else:
            results.append({"name": metric.name, "value": values[metric.name], "passed": evaluate(metric, values[metric.name])})
    return {"status": "valid" if not issues else "invalid", "issues": issues, "plan": asdict(plan), "results": results}

Solutions

SolutionP1 · Neither passes

Neither. The model fails: precision 0.5 on 14 answers, with 7 wrong answers to undo. The lookup gate meets every per-metric threshold (precision 1.0, answer rate 0.71, no wrong answers), but its Wilson lower bound is 0.722 on 10 answers, below the 0.75 the pass rule requires. Its verdict is "ambiguous: replay 20 more".

The interval rule exists so that a small perfect sample cannot pass on its own.

SolutionB1 · Numbers chosen after the fact

Everything that makes a number decisive was chosen after the data. The 20 cases were picked after the run, so they are a selection, not a sample. The threshold moved to match the result. A point estimate from 20 cases says nothing about the interval, and with 19 of 20 the Wilson lower bound is about 0.76. There was no counter-metric for overrides, so cost moved to the on-call engineers invisibly, and "latency down 40%" has no stated source or population.

The plan should have fixed, before the pilot: - Goal and questions. - Metrics: precision on a pre-drawn replay set of real incidents with its window; answer rate; production writes as a guardrail; and the override rate and time-to-mitigation by role as counter-metrics. - Pass, fail and ambiguous rules, with interval bounds.

Rollout follows only if the rules say pass.

What You Keep

Keep outputs/measurement-report.json. It defines the evidence gate for the prototype, pilot, or production stage.

Break it on purpose

After a pilot, a team reports "accuracy 95%, latency down 40%" and asks to roll out. You learn that accuracy came from 20 cases picked after the run, that the threshold was set at 90% once results came in, and that nobody measured how often on-call engineers overrode the agent. Using this lesson, what is wrong with the report, and what should the measurement plan have been? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Thresholds in CI. Evaluation tools such as promptfoo let each test case carry assertions with thresholds, so a prompt or model change fails the build when a metric drops below its bound.
  • Guardrail metrics in experiments. Experimentation platforms (Statsig and others) let you mark guardrail metrics that alert or block a rollout when they regress, separately from the metric being optimised.
  • SLOs as decision rules. Google SRE practice turns reliability targets into service-level objectives with an error budget. Spending the budget changes what the team does next, which is the "decide before you measure" rule in operational form.
  • On your laptop: the plan, report() and the Wilson interval are standard-library Python. The replay runs the 0.5B model on CPU.

Sources: promptfoo, Assertions and metrics, Statsig, Experiments overview, Google SRE book, Service level objectives, Anthropic, Define your success criteria.

Recap
What to keep from this lesson
  • Derive metrics from goal and questions: outcome, guardrail, counter-metric.
  • Each metric names its direction, threshold, window, source and population.
  • Write pass, fail and ambiguous rules before the run, with intervals for rates.
  • Remove metrics no rule reads.
  • Check that the source measures the claim; replay latency is not human time.

Defend a designTell me about a time you defined how a project would be judged before you had any results. What did you write down, and what did you refuse to leave open until later?

Level 2 of 4 · about 10 minutes to answer well.

Short answer. I start from the goal, derive the questions it raises, and only then pick the smallest metrics that answer them. Each metric gets a direction, a threshold, a window, a source and a population before any value is observed, and each outcome metric is paired with a guardrail and a counter-metric. Goal, question, metric.

For an incident tool the goal was to cut the time to identify the affected service without raising unsafe actions. The questions followed: how fast is the correct service found, how often is it correct, does diagnosis stay read-only, and does the workflow raise alert dismissal or operator load. The metrics made each question operational.

A metric needs a contract.

Field Example
Name median identification seconds
Direction at most
Threshold 120
Window ten incident replays
Source the replay event log
Population the on-call engineers in the pilot
Kind outcome or guardrail

Without a source and a window a number cannot be reproduced. Without a threshold it cannot drive a decision.

Three kinds of metric.

  • Outcome: did the desired state improve?
  • Guardrail: did a fixed constraint stay true?
  • Counter-metric: did the local gain shift cost or harm somewhere else?

Speed alone is not enough. Correctness, production writes, operator workload and missed alerts protect against a fast but unsafe result. A plan without a guardrail is invalid even when the outcome metrics look complete.

Decide before you measure.

The lesson's example: pass when the correct-service rate is at least 0.9 and the median time is at most 120 seconds; fail on any production write or a correct rate below 0.75; ambiguous when the gain is small with wide variance, which calls for a larger replay set. A stable correct rate between 0.75 and 0.9 matches none of the three rules, so I also write a rule for it before the replay: it does not pass, and it names the next test. Offline replay gives repeatability and edge coverage. A bounded pilot gives real behavior and trust. I use the cheapest evidence that answers the current decision and do not expose real users only because the code is ready.

Plausible wrong answers.

  • "Pick the metric after you see what the system can do." The threshold then moves to protect the build and the measurement decides nothing.
  • "One good outcome metric is enough." Without a guardrail, a fast but unsafe result passes.
  • "Run a live pilot since the implementation is ready." Readiness is not a reason to expose users; the cheapest evidence that answers the decision comes first.

Follow-ups an interviewer may ask.

  • (level 2) A metric is easy to collect but cannot change the decision. What do you do with it? Expected: remove it; measurement answers a decision, it does not decorate a dashboard.
  • (level 2) Give a counter-metric for the incident tool. Expected: review time added for the incident commander, or escalations that moved to another team.
  • (level 3) The outcome metric passes and the guardrail fails. What is the verdict? Expected: fail; a fixed constraint that broke means the outcome was not reached.
  • (level 3) Results come back ambiguous. What was already written for that case? Expected: the next step, such as a larger replay set, decided before the result so nobody argues the threshold afterwards.
