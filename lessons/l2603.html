Why this came about

The 2017 transformer combined pieces that already existed: attention (2015), residual connections (2015), layer normalisation (2016) and a plain feed-forward network, plus a way to tell the model about word order. OpenAI's GPT (2018) and GPT-2 (2019) kept only the decoder half, and GPT-2 moved the normalisation to the start of each half-block ("pre-norm"), which made deeper models train reliably. That block has barely changed since. Llama, Mistral, Qwen and the other open models swap in a few improvements (RMSNorm, rotary positions, a gated feed-forward), but if you understand GPT-2's block, you can read the code of any of them.

In plain words first
Two steps, repeated

A transformer block does two things to the list of token vectors. First, attention: tokens exchange information, so "it" can collect something from "parcel". Second, a feed-forward network: each token's vector is processed on its own by a small two-layer network, which is where much of the model's stored knowledge seems to live. Both steps are wrapped in a normalisation (keep the numbers a sensible size) and a residual connection (add the result to what was there, rather than replacing it). A GPT is that block repeated 12, 32 or 100 times, with an embedding table at the start and a prediction layer at the end.

Step 1 · Attention cannot see word order

Attention compares every token with every other by dot products. Nothing in that calculation depends on where a token sits. Shuffle the tokens and the outputs are simply shuffled the same way:

import math
import torch
from torch import nn
import torch.nn.functional as F

torch.manual_seed(0)
x = torch.randn(1, 4, 8)                              # 4 tokens, 8 numbers each
order = torch.tensor([2, 0, 3, 1])                    # a shuffled order
out = F.scaled_dot_product_attention(x, x, x)         # attention with no mask
out_shuffled = F.scaled_dot_product_attention(x[:, order], x[:, order], x[:, order])
print("shuffling the input just shuffles the output:", torch.allclose(out[:, order], out_shuffled, atol=1e-6))
What you should see
shuffling the input just shuffles the output: True

Without help, "the parcel hit the courier" and "the courier hit the parcel" would look the same. So the model is given each token's position. GPT-2 uses the simplest method: a second embedding table with one learned vector per position (0 to 1,023), added to each token's vector.

tok_emb = nn.Embedding(50_257, 8)
pos_emb = nn.Embedding(1_024, 8)
ids = torch.tensor([[464, 464]])                      # the same token ("The") twice
x = tok_emb(ids) + pos_emb(torch.arange(2))           # add position 0 and position 1
print("same token, same vector before positions:", torch.equal(tok_emb(ids)[0, 0], tok_emb(ids)[0, 1]))
print("different vectors after adding positions:", not torch.equal(x[0, 0], x[0, 1]))
What you should see
same token, same vector before positions: True
different vectors after adding positions: True

Two other methods matter:

  • Sinusoidal positions (the 2017 paper): fixed waves of different frequencies instead of a learned table, so no training is needed and any length can, in principle, be encoded.
  • Rotary position embeddings (RoPE), used by Llama, Mistral, Qwen and most current models: instead of adding anything to the token vector, rotate each query and key by an angle that grows with its position. The dot product between a rotated query and key then depends only on how far apart they are, not where they are:
def rotate(v, position, theta=0.3):
    """Rotate a 2-number vector by an angle proportional to its position."""
    a = position * theta
    R = torch.tensor([[math.cos(a), -math.sin(a)], [math.sin(a), math.cos(a)]])
    return R @ v

q, k = torch.tensor([1.0, 0.5]), torch.tensor([0.3, 1.0])
for m, n in [(3, 1), (10, 8), (50, 48), (10, 1)]:
    print(f"query at {m:>2}, key at {n:>2} (distance {m - n}): score {rotate(q, m) @ rotate(k, n):.4f}")
What you should see
query at  3, key at  1 (distance 2): score 1.1402
query at 10, key at  8 (distance 2): score 1.1402
query at 50, key at 48 (distance 2): score 1.1402
query at 10, key at  1 (distance 9): score -0.3600

The first three pairs are all two positions apart and get exactly the same score; the last pair, nine apart, gets a different one. Real RoPE does this for every pair of numbers in the query and key, each pair rotating at a different speed. Because attention then "thinks" in relative distances, RoPE models can be stretched to longer contexts than they were trained on, with some extra tricks (Lesson 7.24).

Step 2 · The two halves of a block

The feed-forward network (also called the MLP) is the two-layer network of Lesson 3.15, applied to every token separately: widen from 768 to 3,072 numbers, apply GELU, narrow back to 768. Because it sees one token at a time, all information exchange between tokens happens in attention; the MLP then works on each token's updated vector. Research suggests that much of what a model "knows" (that Paris is in France) is stored in these MLP weights.

LayerNorm (Lesson 3.18) rescales each token's vector to mean 0 and spread 1 before each half. Residual connections add each half's output back to its input, so the stream of token vectors is refined, block by block, rather than replaced. People call this running sum the residual stream.

Step 3 · A complete GPT in code

This is GPT-2's architecture, line for line (the attention layer is Lesson 7.18's, using PyTorch's fused attention):

from dataclasses import dataclass

@dataclass
class GPTConfig:
    vocab_size: int = 50_257      # tokens in the vocabulary (Lesson F5.2)
    block_size: int = 1_024       # longest context the model can read
    n_layer: int = 12             # number of blocks
    n_head: int = 12              # attention heads per block
    d_model: int = 768            # width of every token vector

class CausalSelfAttention(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.n_head = cfg.n_head
        self.qkv = nn.Linear(cfg.d_model, 3 * cfg.d_model)
        self.proj = nn.Linear(cfg.d_model, cfg.d_model)
    def forward(self, x):
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=-1)
        q, k, v = [t.view(B, T, self.n_head, C // self.n_head).transpose(1, 2) for t in (q, k, v)]
        out = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.proj(out.transpose(1, 2).contiguous().view(B, T, C))

class MLP(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.up = nn.Linear(cfg.d_model, 4 * cfg.d_model)
        self.down = nn.Linear(4 * cfg.d_model, cfg.d_model)
    def forward(self, x):
        return self.down(F.gelu(self.up(x), approximate="tanh"))   # GPT-2 uses the tanh form of GELU

class Block(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.ln1, self.attn = nn.LayerNorm(cfg.d_model), CausalSelfAttention(cfg)
        self.ln2, self.mlp = nn.LayerNorm(cfg.d_model), MLP(cfg)
    def forward(self, x):
        x = x + self.attn(self.ln1(x))           # tokens exchange information
        x = x + self.mlp(self.ln2(x))            # each token is processed on its own
        return x

class GPT(nn.Module):
    def __init__(self, cfg):
        super().__init__()
        self.cfg = cfg
        self.tok_emb = nn.Embedding(cfg.vocab_size, cfg.d_model)
        self.pos_emb = nn.Embedding(cfg.block_size, cfg.d_model)
        self.blocks = nn.ModuleList([Block(cfg) for _ in range(cfg.n_layer)])
        self.ln_f = nn.LayerNorm(cfg.d_model)
        self.head = nn.Linear(cfg.d_model, cfg.vocab_size, bias=False)
        self.head.weight = self.tok_emb.weight   # weight tying: reuse the embedding table (Lesson F4.5)
    def forward(self, idx):                      # idx: (batch, T) token ids
        T = idx.shape[1]
        x = self.tok_emb(idx) + self.pos_emb(torch.arange(T, device=idx.device))
        for block in self.blocks:
            x = block(x)
        return self.head(self.ln_f(x))           # (batch, T, vocab_size) logits

torch.manual_seed(0)
model = GPT(GPTConfig())
print(f"parameters: {sum(p.numel() for p in model.parameters()):,}")
What you should see
parameters: 124,439,808

124,439,808: exactly the size of OpenAI's GPT-2 small. Where do they sit?

cfg = model.cfg
emb = cfg.vocab_size * cfg.d_model + cfg.block_size * cfg.d_model
per_block = sum(p.numel() for p in model.blocks[0].parameters())
attn = sum(p.numel() for p in model.blocks[0].attn.parameters())
mlp = sum(p.numel() for p in model.blocks[0].mlp.parameters())
print(f"embeddings (token + position): {emb:>12,}")
print(f"one block: {per_block:,} = attention {attn:,} + MLP {mlp:,} + layer norms {per_block - attn - mlp:,}")
print(f"12 blocks: {12 * per_block:>12,}")
print(f"final layer norm: {2 * cfg.d_model:>8,}   (the output layer reuses the token embedding)")
What you should see
embeddings (token + position):   39,383,808
one block: 7,087,872 = attention 2,362,368 + MLP 4,722,432 + layer norms 3,072
12 blocks:   85,054,464
final layer norm:    1,536   (the output layer reuses the token embedding)

The MLPs hold twice as many parameters as the attention layers (8·d² against 4·d² per block). In large models, where the embedding table is a small share, this is the general rule: about two-thirds of the weights are in the feed-forward networks.

Step 4 · Load GPT-2's real weights into your code

If the architecture is really the same, OpenAI's trained weights should fit it exactly. The Hugging Face copy of GPT-2 stores some matrices transposed (it uses a layer called Conv1D where you used nn.Linear), so they are flipped with .T while copying:

from transformers import GPT2LMHeadModel, GPT2TokenizerFast

official = GPT2LMHeadModel.from_pretrained("gpt2")
sd = official.state_dict()

with torch.no_grad():
    model.tok_emb.weight.copy_(sd["transformer.wte.weight"])
    model.pos_emb.weight.copy_(sd["transformer.wpe.weight"])
    for i, b in enumerate(model.blocks):
        p = f"transformer.h.{i}."
        b.ln1.weight.copy_(sd[p + "ln_1.weight"]);  b.ln1.bias.copy_(sd[p + "ln_1.bias"])
        b.ln2.weight.copy_(sd[p + "ln_2.weight"]);  b.ln2.bias.copy_(sd[p + "ln_2.bias"])
        b.attn.qkv.weight.copy_(sd[p + "attn.c_attn.weight"].T);  b.attn.qkv.bias.copy_(sd[p + "attn.c_attn.bias"])
        b.attn.proj.weight.copy_(sd[p + "attn.c_proj.weight"].T); b.attn.proj.bias.copy_(sd[p + "attn.c_proj.bias"])
        b.mlp.up.weight.copy_(sd[p + "mlp.c_fc.weight"].T);       b.mlp.up.bias.copy_(sd[p + "mlp.c_fc.bias"])
        b.mlp.down.weight.copy_(sd[p + "mlp.c_proj.weight"].T);   b.mlp.down.bias.copy_(sd[p + "mlp.c_proj.bias"])
    model.ln_f.weight.copy_(sd["transformer.ln_f.weight"])
    model.ln_f.bias.copy_(sd["transformer.ln_f.bias"])

tokenizer = GPT2TokenizerFast.from_pretrained("gpt2")
ids = tokenizer("The capital of France is", return_tensors="pt")["input_ids"]
model.eval(); official.eval()
with torch.no_grad():
    ours, theirs = model(ids), official(ids).logits
print("same logits as the official model:", torch.allclose(ours, theirs, atol=1e-3))

probs = F.softmax(ours[0, -1], dim=-1)                # probabilities for the token after "is"
top = probs.topk(5)
print([(tokenizer.decode([i]), round(float(p), 3)) for p, i in zip(top.values, top.indices)])
What you should see
same logits as the official model: True
[(' the', 0.085), (' now', 0.048), (' a', 0.046), (' France', 0.032), (' Paris', 0.032)]

Your 60 lines, with OpenAI's numbers, produce the same predictions as the official implementation (differences are tiny floating-point rounding). The next-token probabilities are the ones you met in Lesson 0.15: GPT-2 small, a base model, thinks " the" is most likely after "The capital of France is", with " Paris" fifth. Bigger models and instruction tuning change the numbers (the From language model to assistant section), not the code.

Tip
Modern variants

Llama-style models change four details: RMSNorm instead of LayerNorm (skip subtracting the mean), RoPE instead of a position table, a gated feed-forward network (SwiGLU, three matrices instead of two), and grouped-query attention (Lesson 7.18). Mixture-of-expertslater · 7.24 models (Lesson 7.24) replace the single MLP with many expert MLPs and a router that picks a few per token. The skeleton you just wrote stays the same.

The same idea as a formula
  • input: x₀ = E_tok[ids] + E_pos[0 … T−1]
  • block l: h = x + Attn(LN₁(x)); x' = h + MLP(LN₂(h)), with MLP(z) = W₂ GELU(W₁z + b₁) + b₂, W₁ of shape (4d, d)
  • output: logits = LN_f(x_L) E_tokᵀ (with weight tying)
  • parameters per block ≈ 12d² (4d² attention + 8d² MLP); total ≈ 12·L·d² + V·d
  • RoPE: rotate each pair of query and key numbers by angle m·θᵢ at position m; then (R_m q) · (R_n k) depends only on m − n
Check your mental model
  • ✗ "Each block does something different, so a GPT is complicated."
    ✓ Every block is identical in design; only their learned numbers differ. The whole model is about 60 lines.
  • ✗ "The feed-forward network mixes information between tokens."
    ✓ It processes each token separately. Only attention moves information between positions.
  • ✗ "Position information is stored in the token embedding."
    ✓ It is added separately (learned or sinusoidal positions) or applied inside attention (RoPE). Token embeddings alone are order-blind.

Exercises

Predict before you run

Using the 12·L·d² rule, roughly how many parameters do the blocks of a model with 32 layers and d_model = 4,096 have? (Solution P1.)

Make it your own

Create GPT(GPTConfig(n_layer=24, n_head=16, d_model=1024)) and count its parameters. OpenAI's GPT-2 medium has this shape. How close is your count to its published 355 million? (Solution M1.)

Debugging exercise

After copying the weights, a colleague's torch.allclose check prints False, and their model's top prediction is gibberish. They forgot the .T on all four weight copies inside the loop. Why does the code still run without a shape error for attn.proj and fail for the others? (Solution D1.)

Solutions

SolutionP1 · A bigger model

12 × 32 × 4,096² = 12 × 32 × 16,777,216 ≈ 6.4 billion. With the embedding table (a vocabulary of 32,000 to 128,000 tokens times 4,096) this gives roughly the 7 to 8 billion parameters of Llama 2 7B or Llama 3 8B, which have exactly these dimensions (their gated MLPs and grouped-query attention shift the split a little).

SolutionM1 · GPT-2 medium

About 354.8 million (with weight tying), matching the published 355 million. The count is dominated by 24 blocks × 12 × 1,024² ≈ 302 million, plus 50,257 × 1,024 ≈ 51 million for the token embedding and about 1 million for positions.

SolutionD1 · Forgotten transposes

attn.c_proj.weight is 768 × 768, a square matrix, so its transpose has the same shape and copy_ succeeds silently, with the matrix flipped. The others are not square (768 × 2,304 and 768 × 3,072 versus PyTorch's 2,304 × 768), so copy_ raises a shape error. A square matrix copied the wrong way round is a silent bug: always compare outputs with a reference, as Step 4 does.

Recap
  • Attention is blind to order, so positions are added: learned position embeddings (GPT-2), sinusoids, or rotary embeddings (RoPE) that make attention depend on relative distance.
  • A block is x + Attention(LayerNorm(x)), then x + MLP(LayerNorm(x)): attention mixes information between tokens, the MLP processes each token.
  • A GPT is token and position embeddings, a stack of identical blocks, a final LayerNorm and an output layer, often tied to the embedding table.
  • GPT-2 small has 124,439,808 parameters; about two-thirds of the block weights are in the MLPs.
  • Loading OpenAI's weights into the hand-written model reproduces the official predictions exactly.
