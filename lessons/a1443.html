The Expensive Failure

In plain words first

Before an agent edits anything, write down what "done" means in this repo. A task frame fits on one screen: the goal as observable behaviour, a few repository facts each with a receipt (path:line), the paths the change may and may not touch, the check that proves it, and the decisions nobody has made yet. Specs, contracts and design estimates are covered in Lessons 14.134 and 14.135 (linked above). This lesson gives one vague request to a small model three ways and checks whether each answer fits the system it lands in.

“Add duplicate email protection” sounds specific. It is not. Does uniqueness belong in the API, domain service, or database? Is comparison case-sensitive? Which error shape is already public? Is a migration allowed? Which test proves the behavior?

A capable agent will fill those gaps with plausible choices. That is the dangerous case because the implementation can be clean, tested, and still incompatible with the system.

The first unit of coding-agent work is therefore not an edit. It is a task frame backed by repository evidence.

The Task Frame

A useful frame has six fields:

Field Question
Goal What observable behavior must change?
Repository facts What did you verify in code, tests, config, or history?
Allowed paths Where may the change land?
Forbidden paths What must remain untouched?
Acceptance evidence Which commands or observations prove the goal?
Unknowns Which decisions still need evidence or human judgment?

Facts need receipts. “The API uses 409 for duplicates” is not a fact until you can point to the existing test or handler. A file path and line is enough. A command result is better when behavior matters.

Reconnaissance Is a Search for Constraints

Do not read the entire repository. Search for the surfaces that constrain the change:

  1. The current behavior and its caller.
  2. The closest existing test.
  3. The public contract or serialized shape.
  4. The project instructions that govern the path.
  5. The build and verification commands.
  6. Similar completed changes that reveal local patterns.

Stop when every planned decision is either supported by evidence, explicitly delegated, or listed as an unknown. More reading after that point is often avoidance.

Unknowns Are Not Failures

An unknown is a controlled gap. An assumption is an uncontrolled answer to that gap.

Classify each unknown:

  • Discoverable: the repository or running system can answer it.
  • Decidable: the task contract gives the agent authority to choose.
  • Human: the choice changes product behavior, cost, risk, or public compatibility.
  • Deferred: the choice is outside this slice and belongs in non-goals.

The agent should continue through discoverable and delegated unknowns. It should pause at human unknowns before the choice is buried in code.

Acceptance Before Implementation

Write the proof before the patch. The proof can be:

  • a focused unit or integration test command;
  • a browser journey with a named viewport and expected state;
  • a wire request and exact response contract;
  • a performance measurement with a threshold;
  • a scope check that confirms no unrelated file changed.

“Tests pass” is not a proof plan. Name the authoritative test and the claim it supports.

The same idea as a formula

Ambiguity multiplies. If a request leaves d independent decisions open and each has ci​ plausible answers, the number of implementations that all look reasonable is

N=i=1∏d​ci​.

Only a few of them fit the system. Each fact with a receipt, and each decision made explicitly, sets one ci​ to 1.

Where "duplicate email protection" leaves room. Five decisions are open: where to check (API, service, database), what to return (raise, 400, 409), the success status (keep 201 or change it), case handling, and whether a repeat may overwrite. Even at 3, 3, 2, 2, 2 that is N=72 reasonable implementations. The repository already answers three of them: the error shape (rename), the success status (201) and case handling (normalize).

Worked example
Reading one sampled answer
  • Bare request, answer 3: the model checks store.rows and returns 409 with an error envelope. That looks right.
  • It also returns {"status": 200} for a new account, where the file says 201. The rename to 200 is one plausible choice, and it breaks every caller that expects 201.
  • The hidden checks score it 4 of 5. Only "first signup still 201" fails, which is exactly the decision the request left open and the repository had already made.
  • A frame with the fact "creation returns 201 (app/accounts.py:19)" and an acceptance test asserting 201 closes that gap before any code exists.

# "Add duplicate email protection" on a small accounts module, asked three ways of Qwen2.5-0.5B-Instruct (CPU):
# the bare request with the file; a task frame (goal, facts with line receipts, allowed and forbidden paths,
# acceptance evidence, unknowns) built with the lesson's TaskFrame and render(); and the same frame plus its
# acceptance test, written before the change. Each prompt gets 6 sampled answers (temperature 0.8, fixed seed);
# five hidden checks ask whether each fits the system it lands in. The test covers two of them. About 6 minutes.
import os, pathlib, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
from main import TaskFrame, RepositoryFact, render, validate
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

def chat(prompt, n=420, k=1):
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True,
                                  return_tensors="pt", return_dict=True)["input_ids"]
    torch.manual_seed(0)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=n, do_sample=k > 1, temperature=0.8 if k > 1 else None,
                           top_p=0.95 if k > 1 else None, top_k=None, num_return_sequences=k)
    texts = [tok.decode(o[ids.shape[1]:], skip_special_tokens=True) for o in out]
    return texts if k > 1 else texts[0]

ACCOUNTS = '''"""Account service."""


def normalize(email: str) -> str:
    return email.strip().lower()


class AccountStore:
    def __init__(self) -> None:
        self.rows: dict[str, str] = {}

    def add(self, email: str, password: str) -> None:
        self.rows[email] = password


def create_account(store: AccountStore, email: str, password: str) -> dict:
    email = normalize(email)
    store.add(email, password)
    return {"status": 201, "email": email}


def rename(names: set, old: str, new: str) -> dict:
    if new in names:
        return {"status": 409, "error": {"code": "name_taken", "message": "name already in use"}}
    names.discard(old)
    names.add(new)
    return {"status": 200, "name": new}
'''
LINES = ACCOUNTS.splitlines()
line_of = lambda s: next(i for i, l in enumerate(LINES, 1) if s in l)
L_NORM, L_409, L_ROWS = line_of("email = normalize(email)"), line_of('"status": 409'), line_of("self.rows: dict")
REQUEST = "Add duplicate email protection."
frame = TaskFrame(
    goal="create_account refuses an email that already has an account",
    allowed_paths=["app/accounts.py"], forbidden_paths=["migrations/**", "app/http.py"],
    acceptance=["python3 -m unittest tests.test_accounts"],
    facts=[RepositoryFact("Emails are stored normalized (stripped, lower-case)", f"app/accounts.py:{L_NORM}"),
           RepositoryFact("Conflicts return status 409 with an error envelope {code, message}", f"app/accounts.py:{L_409}"),
           RepositoryFact("AccountStore.rows maps email to password", f"app/accounts.py:{L_ROWS}")],
    unknowns=["Error code name: use email_taken (decided by the task owner)"])
print("frame issues:", validate(frame) or "none", "\n")
print(render(frame))

K = 6
def splice(text):
    m = re.search(r"```(?:python)?\n(.*?)(?:```|$)", text, re.S)
    fn = (m.group(1) if m else "").strip()
    fn = fn[fn.find("def create_account"):] if "def create_account" in fn else ""
    fn = fn.split("\ndef ", 1)[0].split("\n# ", 1)[0].rstrip()
    head, tail = ACCOUNTS.split("def create_account", 1)
    original, rest = tail.split("\n\n\ndef rename", 1)
    return head + (fn or "def create_account" + original) + "\n\n\ndef rename" + rest, fn

def ask(prompt):
    # both prompts get the same output contract: only create_account, spliced into the file
    texts = chat(prompt + "\nChange only create_account. Return only the new create_account function in one ```python block.",
                 n=450, k=K)
    return [splice(t) for t in texts]

CHECKS = {
    "first signup still 201": 'assert create_account(s, "a@b.co", "pw")["status"] == 201',
    "exact repeat refused (409)": 'create_account(s, "a@b.co", "pw"); assert create_account(s, "a@b.co", "pw")["status"] == 409',
    "case variant refused (409)": 'create_account(s, "a@b.co", "pw"); assert create_account(s, " A@B.co", "pw")["status"] == 409',
    "same error envelope as rename": 'create_account(s, "a@b.co", "pw"); e = create_account(s, "a@b.co", "pw")["error"]; '
                                     'assert isinstance(e["code"], str) and isinstance(e["message"], str)',
    "repeat does not overwrite password": 'create_account(s, "a@b.co", "pw"); create_account(s, "a@b.co", "other"); '
                                          'assert s.rows["a@b.co"] == "pw"',
}

def check(code):
    root = pathlib.Path(tempfile.mkdtemp()); (root / "accounts.py").write_text(code)
    res = {}
    for name, body in CHECKS.items():
        prog = "from accounts import *\ns = AccountStore()\n" + body + "\n"
        p = subprocess.run([sys.executable, "-c", prog], cwd=root, capture_output=True, text=True, timeout=30)
        res[name] = p.returncode == 0
    return res

def decisions(fn):
    if "def create_account" not in fn:
        return "no function returned"
    out = []
    if re.search(r"\bin (store\.rows|store)\b|\.rows\.get|exist|already", fn): out.append("checks for an existing email")
    codes = sorted(set(re.findall(r"\"status\":\s*(\d{3})", fn)) - {"201"})
    if codes: out.append("returns " + "/".join(codes))
    if re.search(r"raise ([A-Z]\w+)", fn): out.append("raises " + re.search(r"raise ([A-Z]\w+)", fn).group(1))
    if "normalize(" not in fn: out.append("drops normalize()")
    return ", ".join(out) or "no change"

ACCEPT_TEST = ('def test_repeat_email_is_refused():\n    store = AccountStore()\n'
               '    assert create_account(store, "a@b.co", "pw")["status"] == 201\n'
               '    out = create_account(store, "a@b.co", "pw")\n'
               '    assert out["status"] == 409 and out["error"]["code"] == "email_taken"\n')
VARIANTS = (("bare request", f"app/accounts.py:\n```python\n{ACCOUNTS}```\nRequest: {REQUEST}"),
            ("task frame", f"app/accounts.py:\n```python\n{ACCOUNTS}```\n{render(frame)}\nImplement this task frame."),
            ("frame + test", f"app/accounts.py:\n```python\n{ACCOUNTS}```\n{render(frame)}\nThe acceptance test, written "
                             f"before the change (tests/test_accounts.py):\n```python\n{ACCEPT_TEST}```\nImplement this task frame."))
for label, prompt in VARIANTS:
    results = ask(prompt)
    tally = {name: 0 for name in CHECKS}
    print(f"{label}: {K} sampled answers")
    for i, (code, fn) in enumerate(results, 1):
        res = check(code)
        for name, ok in res.items():
            tally[name] += ok
        print(f"   answer {i}: {sum(res.values())}/{len(res)} checks   {decisions(fn)}")
    print("   per check: " + ", ".join(f"{name} {n}/{K}" for name, n in tally.items()) + "\n")

def receipt(fact):
    mm = re.match(r"\s*([\w./-]+):(\d+)", fact.evidence)
    if not mm:
        return "no path:line"
    path, n = mm.group(1), int(mm.group(2))
    if not path.endswith("accounts.py"):
        return f"cites {path}, which is not in the repo"
    if not 1 <= n <= len(LINES):
        return f"line {n} does not exist ({len(LINES)} lines)"
    words = {w.lower() for w in re.findall(r"[A-Za-z_]{4,}", fact.claim)}
    near = " ".join(LINES[max(0, n - 2): n + 1]).lower()
    hits = sorted(w for w in words if w[:5] in near)
    return f"line {n}: {LINES[n - 1].strip()[:45]!r}  shares {hits or 'nothing'} with the claim"

Part 1 of 3 · RepositoryFact, TaskFrame, validate, render

# Lesson program: validates and renders a repository-backed task frame.
# Lesson: phases/14-agent-engineering/43-frame-the-task-before-code/docs/en.md
# Canonical source: Nuseibeh and Easterbrook, Requirements Engineering: A Roadmap.
# Canonical source: Yang et al., SWE-agent, arXiv:2405.15793.
from __future__ import annotations

from dataclasses import dataclass, field
from pathlib import Path


@dataclass(frozen=True)
class RepositoryFact:
    claim: str
    evidence: str


@dataclass
class TaskFrame:
    goal: str
    allowed_paths: list[str]
    forbidden_paths: list[str]
    acceptance: list[str]
    facts: list[RepositoryFact] = field(default_factory=list)
    unknowns: list[str] = field(default_factory=list)


def validate(frame: TaskFrame) -> list[str]:
    issues: list[str] = []
    if not frame.goal.strip():
        issues.append("goal is empty")
    if not frame.allowed_paths:
        issues.append("allowed paths are empty")
    if not frame.forbidden_paths:
        issues.append("forbidden paths are empty")
    if not frame.acceptance:
        issues.append("acceptance evidence is empty")
    for fact in frame.facts:
        if not fact.evidence.strip():
            issues.append(f"unsupported fact: {fact.claim}")
    overlap = sorted(set(frame.allowed_paths) & set(frame.forbidden_paths))
    if overlap:
        issues.append(f"paths are both allowed and forbidden: {', '.join(overlap)}")
    return issues


def render(frame: TaskFrame) -> str:
    issues = validate(frame)
    status = "READY" if not issues else "BLOCKED"
    lines = [f"# Task Frame: {frame.goal}", "", f"Status: {status}", "", "## Repository facts"]
    lines.extend(f"- {fact.claim} (`{fact.evidence}`)" for fact in frame.facts)
    lines.extend(["", "## Allowed paths"])
    lines.extend(f"- `{path}`" for path in frame.allowed_paths)
    lines.extend(["", "## Forbidden paths"])
    lines.extend(f"- `{path}`" for path in frame.forbidden_paths)
    lines.extend(["", "## Acceptance evidence"])
    lines.extend(f"- `{item}`" for item in frame.acceptance)
    lines.extend(["", "## Unknowns"])
    lines.extend(f"- {item}" for item in frame.unknowns)
    if issues:
        lines.extend(["", "## Blocking issues"])
        lines.extend(f"- {item}" for item in issues)
    return "\n".join(lines) + "\n"

Part 2 of 3 · example

def example() -> TaskFrame:
    return TaskFrame(
        goal="Prevent duplicate email addresses during signup",
        allowed_paths=["app/accounts.py", "tests/test_accounts.py"],
        forbidden_paths=["migrations/**", "deploy/**"],
        acceptance=["python3 -m unittest tests.test_accounts"],
        facts=[
            RepositoryFact("Account writes use AccountStore", "app/accounts.py:18"),
            RepositoryFact("Duplicate errors use status 409", "tests/test_accounts.py:44"),
        ],
        unknowns=["Whether email comparison is case-insensitive"],
    )


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "task-frame.md"
    output.write_text(render(example()), encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Use It in a Real Repository

Before asking an agent to edit:

  1. Write the goal as a behavior, not a file change.
  2. Record two or three facts with exact evidence.
  3. Name the smallest allowed path set.
  4. Name negative space explicitly.
  5. Write the command or observation that closes the task.
  6. List the decisions you have not earned yet.

The frame should fit on one screen. If it cannot, the task may contain multiple independently verifiable changes.

Exercises

  1. Frame a real bug from one of your repositories without proposing a solution.
  2. Find one claim in the frame that is actually an assumption. Replace it with evidence.
  3. Add a human unknown whose answer would change the public contract.
  4. Split one broad allowed path into the smallest safe set.
  5. Add a scope receipt to the acceptance evidence.

Solutions

SolutionP1 · The test helped most; the prose frame alone did not

The frame with its acceptance test did best. It gave the only answer that passed all five checks, and it kept the 201 success status in 5 of 6 answers. The bare request gave two near misses that both changed 201 to 200, a change nobody asked for. The prose frame alone gave no correct refusal: every answer that caught a repeat raised an exception.

With six samples per prompt these rates are noisy. The robust lesson is that the request left decisions open and the model filled them with plausible choices. An executable proof closed more of them than prose did.

SolutionB1 · The decisions were made in code, not in a frame

Nobody framed the task. Two decisions the repository had already made, creation returns 201 and conflicts return 409 with an {code, message} envelope, were left open. The agent filled them with plausible choices. The test it wrote checked its own choices, so it passed.

Before the first edit, a frame should record those two facts with receipts (the create_account return line and the existing conflict handler), allow only the service file and its test, forbid the HTTP layer and migrations, and list case handling as a decided or human unknown. Then write the acceptance test from the frame: first signup returns 201, a repeat returns 409 with email_taken, a case variant is refused, and the password is not overwritten. That test, written before the patch, would have failed the PR.

What You Keep

Keep outputs/task-frame.md. It is the input to the next lesson, where the frame becomes an evidence-backed execution plan.

Break it on purpose

An agent receives "Add duplicate email protection" and opens a pull request. The code is clean, it has a passing test, and the reviewer approves. A week later the mobile app breaks: signups now return 200, and repeats raise a 500 instead of the documented 409. Using this lesson, what was missing before the first edit, and what would have caught it? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Plan before edit is built in. Claude Code's plan mode reads files and proposes a plan, but makes no edits until you approve it. Cursor, Copilot and Codex have similar planning steps.
  • Spec-driven development. GitHub Spec Kit runs Spec → Plan → Tasks → Implement, and each phase writes a Markdown file the next one reads. Kiro's specs are requirements.md (user stories and acceptance criteria), design.md and tasks.md.
  • Receipts over recollection. Coding agents cite files and line ranges in their plans. The SWE-agent work showed that the interface the agent works through, including how it searches and views files, changes its success rate.
  • On your laptop: a frame is a text file. The validator is standard library, and the whole lesson runs on CPU.

Sources: Claude Code, Common workflows (plan mode), GitHub Spec Kit, Kiro, Specs, Yang et al., SWE-agent (arXiv:2405.15793).

Recap
What to keep from this lesson
  • Frame before editing: goal, facts with receipts, allowed and forbidden paths, acceptance, unknowns.
  • A vague request leaves many reasonable but incompatible implementations open.
  • Write the acceptance test first. It moved the small model more than prose did.
  • Check receipts against the code. A model's own frame needs checking most.
  • Stop reconnaissance when every decision is evidenced, delegated or listed as unknown.
