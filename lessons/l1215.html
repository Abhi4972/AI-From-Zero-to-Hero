Why this came about

Prompts, models and retrieval settings all change behavior, often in ways tests miss. LLMOps extended MLOps release practices (versioning, evaluation gates, gradual rollout, rollback) to every such change.

In plain words first
Releasing changes you cannot fully predict

Changing a prompt, model, tool or retrieval setting changes behaviour in ways tests may not catch. The LLMOps lifecycle treats every such change as a release: version it, evaluate it offline against the current version, roll it out gradually (shadow mode, then a small share of traffic), watch online metrics, and keep a fast way to roll back.

From MLOps to LLMOps to AgentOps

MLOps grew up around models you train: data pipelines, feature stores, training runs, model registries, drift monitoring. LLMOps keeps the discipline but moves the center of gravity: most teams do not train the model, so the things you build and change are prompts, retrieval, tools, guardrails and model choice, and quality is judged by evals rather than one accuracy number. AgentOps adds what agents bring: multi-step traces, tool side effects, approvals, long-running state and per-run cost that varies tenfold.

The lifecycle

  1. Frame: the task, the users, what "good" means, risk tier (Lesson 15.26), cost and latency budgets.
  2. Prototype: smallest thing that works, often in a notebook against a hosted model.
  3. Evaluate: build the first eval set and run error analysis (Lesson 14.143) before polishing anything.
  4. Harden: guardrails, permissions, approvals, retries, durable execution.
  5. Release: CI with eval gates, staged rollout (shadow, canary), monitoring in place before traffic.
  6. Operate: traces, dashboards, alerts, on-call, incident response, cost control.
  7. Improve: mine production traces for failures, add them to the eval set, fix, repeat: the data flywheel (Lesson 14.131).

Version the whole release

An agent's behavior depends on far more than its code. Treat all of it as one versioned release:

Component Example Where it is versioned
Code and orchestration Graph, tools, middleware Git
Prompts System prompt, tool descriptions, judge prompts Git or a prompt registry
Model and parameters claude-sonnet-... pinned version, temperature, reasoning effort Config in Git; the gateway's alias map
Retrieval Index version, embedding model, chunking settings Index alias plus config
Tools and MCP servers Server versions, tool schemas and descriptions Lockfiles and registry
Guardrails Rules, classifier versions, thresholds Config in Git
Eval sets and judges Datasets, rubrics, judge model Dataset versions

A release that changes only a prompt is still a release: it goes through the same eval gate.

Hands-on · MLflow 3 for prompts, traces and evaluation

MLflow (open source; managed in Databricks, Azure Machine Learning and Amazon SageMaker) added a GenAI layer in version 3: tracing with automatic instrumentation for many SDKs and frameworks, a prompt registry, and mlflow.genai.evaluate with scorers. It runs locally with a SQLite file:

uv add mlflow openai        # tested with mlflow 3.17.2

import tempfile
import mlflow
from mlflow.genai.scorers import scorer
from mockllm import start
from openai import OpenAI

mlflow.set_tracking_uri(f"sqlite:///{tempfile.mkdtemp()}/mlflow.db")     # local file; a tracking server in teams
mlflow.set_experiment("shopkart-support")
mlflow.openai.autolog()                                                  # trace every OpenAI SDK call automatically
client = OpenAI(base_url=start(), api_key="mock")

# 1. A versioned prompt in the registry
prompt = mlflow.genai.register_prompt(
    name="shopkart-support-system",
    template="You are ShopKart's support assistant for {{region}}. Be brief and accurate.",
    commit_message="First version")
print("registered:", prompt.name, "version", prompt.version)

# 2. A traced application function that loads the prompt by version
@mlflow.trace(span_type="AGENT")
def answer(question: str) -> str:
    system = mlflow.genai.load_prompt("prompts:/shopkart-support-system/1").format(region="India")
    r = client.chat.completions.create(model="mock-model", messages=[
        {"role": "system", "content": system}, {"role": "user", "content": question}])
    return r.choices[0].message.content

# 3. Evaluate it on a dataset with code-based scorers
@scorer
def mentions_order_id(inputs, outputs) -> bool:
    return "A-1" in outputs or "order ID" in outputs

@scorer
def is_brief(outputs) -> bool:
    return len(outputs.split()) <= 40

data = [{"inputs": {"question": "Where is my order?"}}, {"inputs": {"question": "Hello"}}]
result = mlflow.genai.evaluate(data=data, predict_fn=answer, scorers=[mentions_order_id, is_brief])
print(dict(sorted((k, float(v)) for k, v in result.metrics.items() if k.endswith("/mean"))))
traces = mlflow.search_traces(return_type="list")
print("traces recorded:", len(traces), "| spans in one:", [s.name for s in traces[0].data.spans])
What you should see
registered: shopkart-support-system version 1
{'is_brief/mean': 1.0, 'mentions_order_id/mean': 1.0}
traces recorded: 2 | spans in one: ['answer', 'Completions']

MLflow also prints a summary of the evaluation run. Start the UI with mlflow ui --backend-store-uri sqlite:///path/to/mlflow.db to browse traces, prompt versions and per-example scores. In production, use aliases (prompts:/shopkart-support-system@production) so that promoting a prompt is a registry change, gated by evals.

Promote and roll back with aliases

An alias is a movable pointer to a version. The application always loads @production; releasing a prompt means moving the pointer after the evals pass, and rolling back means moving it back:

v2 = mlflow.genai.register_prompt(
    name="shopkart-support-system",
    template="You are ShopKart's support assistant for {{region}}. Be brief, accurate, and always quote the order ID.",
    commit_message="Quote order IDs (fixes failure category 'vague answers')")
mlflow.genai.set_prompt_alias("shopkart-support-system", alias="production", version=1)
mlflow.genai.set_prompt_alias("shopkart-support-system", alias="candidate", version=v2.version)

def system_prompt(alias: str) -> str:
    return mlflow.genai.load_prompt(f"prompts:/shopkart-support-system@{alias}").format(region="India")

print("production:", system_prompt("production")[-40:])
print("candidate: ", system_prompt("candidate")[-40:])
mlflow.genai.set_prompt_alias("shopkart-support-system", alias="production", version=v2.version)   # promote
print("promoted:  ", system_prompt("production")[-40:])
mlflow.genai.set_prompt_alias("shopkart-support-system", alias="production", version=1)            # roll back
print("rolled back:", system_prompt("production")[-40:])
What you should see
production: istant for India. Be brief and accurate.
candidate:  accurate, and always quote the order ID.
promoted:   accurate, and always quote the order ID.
rolled back: istant for India. Be brief and accurate.

No code was deployed for any of those changes. In a real system, the move to production is done by the CI job after the eval gate passes, and the registry keeps who moved it and when. Applications should cache the loaded prompt for a short time (MLflow caches loads) rather than fetching it on every request. MLflow 3 can also optimize a registered prompt automatically against your scorers (mlflow.genai.optimize_prompts, which uses methods such as GEPA), and the result is just another version that goes through the same gate.

Hands-on · The release manifest

The table above becomes a file. Each release is one manifest; its fingerprint identifies exactly what ran, and a diff between two manifests tells CI which evaluations to run:

import hashlib, json
import yaml

RELEASE_V7 = yaml.safe_load("""
agent: shopkart-support
code: git:4f2a9c1
prompts: {system: shopkart-support-system@3, judge_groundedness: judge-grounded@2}
model: {alias: support-model, deployment: claude-sonnet-5-5, temperature: 0.2}
retrieval: {index: policies-2026-10-01, embedding: text-embedding-3-small, chunk_tokens: 400}
tools: {orders-mcp: 1.4.2, payments-mcp: 0.9.0}
guardrails: {injection_classifier: pg-2.1, pii: presidio-2.2, cancel_needs_approval: true}
evals: {suite: support_v4, dataset: support-golden@12}
""")
RELEASE_V8 = json.loads(json.dumps(RELEASE_V7))                          # deep copy
RELEASE_V8["prompts"]["system"] = "shopkart-support-system@4"
RELEASE_V8["retrieval"]["index"] = "policies-2026-10-20"

def fingerprint(release: dict) -> str:
    return hashlib.sha256(json.dumps(release, sort_keys=True).encode()).hexdigest()[:12]

def diff(old: dict, new: dict, path: str = "") -> list[str]:
    changes = []
    for key in sorted(set(old) | set(new)):
        a, b, p = old.get(key), new.get(key), f"{path}{key}"
        if isinstance(a, dict) and isinstance(b, dict):
            changes += diff(a, b, p + ".")
        elif a != b:
            changes.append(f"{p}: {a} -> {b}")
    return changes

EVALS_FOR = {"prompts": ["support_v4 full", "tone judge"], "retrieval": ["groundedness", "retrieval recall@5"],
             "model": ["support_v4 full", "cost and latency", "red team"], "tools": ["trajectory", "side effects"],
             "guardrails": ["red team", "false-positive rate"], "code": ["unit tests", "support_v4 fast"]}

print("v7", fingerprint(RELEASE_V7), "-> v8", fingerprint(RELEASE_V8))
changes = diff(RELEASE_V7, RELEASE_V8)
print("\n".join(changes))
needed = sorted({e for c in changes for e in EVALS_FOR.get(c.split(".")[0], [])})
print("evals to run:", needed)
What you should see
v7 f6a04d2bb432 -> v8 e27a6919cb43
prompts.system: shopkart-support-system@3 -> shopkart-support-system@4
retrieval.index: policies-2026-10-01 -> policies-2026-10-20
evals to run: ['groundedness', 'retrieval recall@5', 'support_v4 full', 'tone judge']

Stamp the fingerprint on every trace (a release.id attribute), and "which release produced this bad answer?" becomes a filter rather than an investigation. Mapping changed components to evals keeps CI fast: a re-index does not need the red-team suite, but a model change does.

Hands-on · Roll out by tenant, deterministically

Feature-flag tools make a deterministic rollout by hashing a stable key, so the same tenant always sees the same version during a rollout, and you can exempt tenants whose contracts forbid unannounced changes:

def bucket(key: str) -> float:
    """A stable number in [0, 1) for a key: the same tenant always lands in the same bucket."""
    return int(hashlib.sha256(key.encode()).hexdigest()[:8], 16) / 16**8

ROLLOUT = {"release": "v8", "percent": 10, "always": {"tenant-internal"}, "never": {"tenant-bank-a"}}

def release_for(tenant: str) -> str:
    if tenant in ROLLOUT["never"]:
        return "v7"                                       # contract or regulator says: no changes without notice
    if tenant in ROLLOUT["always"] or bucket(f"{ROLLOUT['release']}:{tenant}") < ROLLOUT["percent"] / 100:
        return ROLLOUT["release"]
    return "v7"

tenants = [f"tenant-{i:03d}" for i in range(1000)] + ["tenant-internal", "tenant-bank-a"]
on_v8 = [t for t in tenants if release_for(t) == "v8"]
print(f"{len(on_v8)} of {len(tenants)} tenants on v8; internal: {release_for('tenant-internal')}, "
      f"bank-a: {release_for('tenant-bank-a')}, tenant-042 stable: {release_for('tenant-042') == release_for('tenant-042')}")
What you should see
89 of 1002 tenants on v8; internal: v8, bank-a: v7, tenant-042 stable: True

Hashing release:tenant (not just tenant) means each release draws a fresh 10%, so the same unlucky tenants are not always the canaries. Close to 10% is what hashing gives; exact counts are not the goal, stability is. OpenFeature, Unleash, LaunchDarkly and the cloud app-configuration services do this with targeting rules, audit logs and kill switches.

The pipeline, end to end

A typical CI workflow for an agent repository ties the pieces together. The shape below is GitHub Actions; the same stages work in GitLab, Azure DevOps or Jenkins:

# .github/workflows/agent-release.yml (sketch)
on: {pull_request: {}, push: {branches: [main]}}
jobs:
  fast-checks:                         # every pull request: minutes, no real model calls
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: uv sync --locked          # exact, hash-pinned dependencies
      - run: uv run pytest tests/unit tests/evals_fast    # mocked tools, scripted model
      - run: uv run python release/diff_manifest.py --base origin/main > evals_needed.txt
  full-evals:                          # merge to main: real models, repeated runs, judges
    needs: fast-checks
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: evals                 # holds gateway keys for the eval budget only
    steps:
      - uses: actions/checkout@v4
      - run: uv run python evals/run.py --suites-from evals_needed.txt --repeats 3 --compare production
      - run: uv run python evals/gate.py --max-regressions 0 --min-pass-rate 0.9
  promote:                             # only after the gate: move aliases, start the canary
    needs: full-evals
    runs-on: ubuntu-latest
    environment: production            # requires a human approval in the GitHub UI
    steps:
      - run: uv run python release/promote.py --alias candidate --canary-percent 10

Industry practice
Build the platform after the second agent, not before the first

Platform teams that succeed usually extract a platform from the first one or two production agents rather than designing it in advance: the gateway, tracing, eval harness and deployment template that those agents needed become the paved road for the next ten. Building a large platform before any agent has shipped tends to produce components nobody uses.

In production
Release hygiene that saves incidents

Pin model versions rather than floating aliases such as "latest", so a provider update cannot change behavior overnight; schedule a re-evaluation when new versions ship instead. Record the release fingerprint on every trace. Keep the previous prompt version, index alias and model mapping one switch away, and rehearse the rollback once before you need it.

An agent's behavior is set by more than its code: the prompt, the model version, the tool definitions, the permission policy, the retrieval index and the harness settings all change what it does. Any one of them can change on a Tuesday afternoon. Shipping safely means versioning them together, gating each change by its risk, and being able to undo it in minutes. The first half of this lesson introduced the lifecycle and its tools; this half turns them into a change process for agents: a release manifest, gates and a staged rollout.

The release bundle

A release bundle is an immutable, versioned set of everything that defines behavior: prompt and its template version, model and its dated version, tool definitions and their schemas, policy (permissions, approval thresholds, budgets), retrieval configuration (index version, chunking, reranker) and harness settings (step budget, stop conditions). The bundle ID goes on every trace (Lesson 14.146). Rolling back means pointing traffic at the previous bundle, never editing a prompt in place.

Watch out
Hot-fixing a prompt in production

The fastest way to break an agent is an "urgent one-line prompt fix" applied outside the release process. It skips the eval suite, has no bundle ID, cannot be rolled back cleanly and makes the next incident's "what changed?" unanswerable. Make the safe path fast instead: a small prompt change through the eval gate and a canary should take an hour, not a week.

Hands-on · Gates follow what changed

Different changes carry different risks. A model change can alter everything; a policy change can widen what the agent is allowed to do. The plan below diffs two bundles and lists the gates the change must pass.

import hashlib, json

def fingerprint(obj) -> str:
    return hashlib.sha256(json.dumps(obj, sort_keys=True).encode()).hexdigest()[:10]

def bundle(prompt, model, tools, policy, retrieval):
    """A release bundle: everything that changes agent behavior, versioned together."""
    parts = {"prompt": prompt, "model": model, "tools": tools, "policy": policy, "retrieval": retrieval}
    return {"id": fingerprint(parts), "parts": {k: fingerprint(v) for k, v in parts.items()}, "raw": parts}

# What each kind of change must pass before it reaches users.
GATES = {
    "prompt":    ["offline eval suite", "canary 5% -> 25% -> 100%"],
    "model":     ["offline eval suite", "repeated trials (pass^k)", "cost and latency check", "shadow on live traffic", "canary 5% -> 25% -> 100%"],
    "tools":     ["tool contract tests", "offline eval suite", "canary 5% -> 25% -> 100%"],
    "policy":    ["policy unit tests", "security review if it widens access"],
    "retrieval": ["retrieval eval", "offline eval suite", "canary 5% -> 25% -> 100%"],
}

ORDER = ["tool contract tests", "policy unit tests", "retrieval eval", "offline eval suite", "repeated trials (pass^k)",
         "cost and latency check", "security review if it widens access", "shadow on live traffic", "canary 5% -> 25% -> 100%"]

def release_plan(old, new):
    changed = [k for k in old["parts"] if old["parts"][k] != new["parts"][k]]
    gates = []
    for k in changed:
        gates += [g for g in GATES[k] if g not in gates]
    gates.sort(key=ORDER.index)
    widened = [t for t in new["raw"]["tools"] if t not in old["raw"]["tools"]]
    if widened:
        gates.append(f"approval: new tools {widened} widen what the agent can do")
    return changed, gates

v12 = bundle("support-v12", "model-a-2026-05", ["get_order", "search_kb"], {"refund_limit": 5000}, "kb-index-41")
v13 = bundle("support-v13", "model-b-2026-09", ["get_order", "search_kb", "issue_refund"], {"refund_limit": 5000}, "kb-index-41")
changed, gates = release_plan(v12, v13)
print(f"bundle {v12['id']} -> {v13['id']}: changed {changed}")
for g in gates:
    print("  gate:", g)
What you should see
bundle fc302d888a -> 9cb2a9eb33: changed ['prompt', 'model', 'tools']
  gate: tool contract tests
  gate: offline eval suite
  gate: repeated trials (pass^k)
  gate: cost and latency check
  gate: shadow on live traffic
  gate: canary 5% -> 25% -> 100%
  gate: approval: new tools ['issue_refund'] widen what the agent can do

This change touches three parts at once, and one of them adds a write tool. In practice, split it: ship the model change first behind the existing tools, then add issue_refund with its own approval and evals. Smaller bundles make failures attributable.

Hands-on · Shadow mode: compare decisions on live traffic

Shadow mode sends a copy of live requests to the candidate. Its tool writes are stubbed and its replies are discarded, so users see nothing; you compare what it decided with what production decided. For agents, decisions (which tool, which arguments, escalate or not) are far easier to compare than prose, and a new write that production would not have made is the finding that matters most.

import random
from collections import Counter, defaultdict

# Shadow mode: the candidate sees a copy of live traffic and decides, but its tool writes are
# stubbed and its answers are discarded. We compare its DECISIONS with production's.
def decide(version, req, rng):
    intent, amount = req["intent"], req.get("amount", 0)
    if intent == "status":
        return ("get_order", None)
    if intent == "refund":
        if version == "prod":
            return ("issue_refund", amount) if amount <= 5000 else ("escalate", None)
        # the candidate model is more eager: it sometimes refunds above the limit
        if amount > 5000 and rng.random() < 0.3:
            return ("issue_refund", amount)
        return ("issue_refund", amount) if amount <= 5000 else ("escalate", None)
    if intent == "policy":
        return ("search_kb", None) if rng.random() < 0.97 else ("answer_from_memory", None)
    return ("escalate", None)

rng = random.Random(5)
traffic = [{"intent": rng.choices(["status", "refund", "policy", "other"], [50, 25, 20, 5])[0],
            "amount": rng.choice([499, 1299, 2499, 4999, 7999, 12999])} for _ in range(4000)]
agree, total, diffs = Counter(), Counter(), defaultdict(Counter)
WRITES = {"issue_refund"}
for req in traffic:
    p, c = decide("prod", req, rng), decide("cand", req, rng)
    total[req["intent"]] += 1
    if p == c:
        agree[req["intent"]] += 1
    else:
        diffs[req["intent"]][(p[0], c[0])] += 1
for intent in total:
    worst = diffs[intent].most_common(1)
    risky = any(c in WRITES for (_, c) in diffs[intent])
    note = f"  most common: prod {worst[0][0][0]} vs candidate {worst[0][0][1]} x{worst[0][1]}" if worst else ""
    print(f"{intent:7} agreement {agree[intent] / total[intent]:6.1%} of {total[intent]:4}{'  BLOCK: candidate adds writes' if risky else ''}{note}")
What you should see
refund  agreement  89.3% of 1023  BLOCK: candidate adds writes  most common: prod escalate vs candidate issue_refund x109
status  agreement 100.0% of 1996
policy  agreement  94.7% of  796  most common: prod answer_from_memory vs candidate search_kb x21
other   agreement 100.0% of  185

The candidate agrees on status questions but issues refunds above the 5,000 limit that production escalated: a policy violation the offline suite missed, found before a single user saw it. The policy disagreements cut the other way: there, production sometimes answered from memory and the candidate searched the knowledge base. A disagreement is a question, not a verdict, so read a sample of each kind before deciding. Two rules for shadows: stub every write (shadow traffic must never touch the world), and remember that shadows double model cost for the traffic they cover, so shadow a sample.

Canaries, flags and the kill switch

After shadow mode, a canary sends a small share of real traffic to the candidate and widens it in steps. Decide the stop rules before starting:

Stage Traffic Stop and roll back if Minimum evidence before widening
Internal Staff and test tenants Any critical eval case fails A day of use
Canary 1 5% of one low-risk tenant or intent Task success falls beyond the noise band; any new write-related error signature; cost per task up more than 20% Enough runs for the comparison test in Lesson 14.140
Canary 2 25% across tenants Same, plus escalation or override rate rising A full weekly cycle for seasonal traffic
General 100% Error budget burning (Lesson 14.146) Keep the previous bundle warm for a week

Use feature flags for capabilities (a new tool, a new intent) so they can be turned off without a release, and keep a kill switch that stops all agent actions and routes work to people. Test both regularly; a kill switch nobody has used is a hope, not a control.

Model upgrades are migrations

Provider model versions change behavior even when the vendor calls them compatible: different tool-calling habits, different verbosity, different refusals and different token use. Treat an upgrade as a migration project:

  1. Pin dated model versions in every bundle. Never point production at a floating alias such as "latest".
  2. Run the full suite with repeated trials on the new model, plus cost and latency, per intent (Lesson 14.144).
  3. Re-tune before you judge. Prompts tuned for one model often need adjustment for another; budget time for it.
  4. Shadow, then canary, as above.
  5. Watch tokens, not just price. A new model at the same list price can cost much more if it writes longer answers or takes more steps.
  6. Track deprecation dates for every pinned model, and start the migration well before the old version is retired.

Solutions

SolutionP1 · Safe releases

Review, eval gate on the held-out set and segments, safety suite, canary to a small share with monitoring, gradual rollout, and a rollback plan.

SolutionB1 · Pin versions

The provider updates the model and behavior changes without your release process. Pin model versions and upgrade deliberately with evals.

SolutionD1 · Canary signals

Quality metrics: the canary only checked errors and latency. Add sampled quality evaluation and outcome metrics to canary checks, and run it long enough.

SolutionM1 · The lifecycle

Version prompts, models, tools, indexes and configurations; test with unit tests and evals; release with canaries; monitor quality, cost and safety; roll back by switching versions; feed failures into evals.

Explain the mechanismWhat does the LLMOps lifecycle cover?

Worked answer. Versioning of every component that changes behavior (prompts, models, retrieval data, tools, configs), evaluation gates, staged releases with canaries and rollback, monitoring of quality, safety and cost, data and feedback loops, and governance records. It treats prompts and data as code-like assets.

A plausible wrong answer. "Deploying models." Most changes are prompts and data.

Follow-ups. Which component changes most often?

Debug a failureYou cannot reproduce last month's behavior. What is missing?

Worked answer. Versioning: the prompt, model, index and tool versions active then. Log versions with each request and keep old versions.

A plausible wrong answer. "Models change, accept it." Pinning and versioning make behavior reproducible.

Follow-ups. How long would you keep old versions?

Defend a designShadow testing or A/B testing for a new agent version?

Worked answer. Shadow (run the new version on copies of traffic without showing users) for risky changes and to compare outputs safely; A/B when you need user outcome measures. Often shadow first, then A/B.

A plausible wrong answer. "Always A/B." Users see a possibly worse version.

Every behavior change is a release.

Aliases decouple prompt releases from code releases.

Stability within a release, fairness across releases.

Everything that changes behavior is versioned and rolled back together.

Decisions are comparable; a new write is the risk that matters.

A shadow that writes is a second, unreviewed production.

Price per token is not cost per task.
