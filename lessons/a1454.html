Feedback Is Infrastructure

In plain words first

Every trace, failed evaluation, incident and support ticket is a signal. The ratchet turns each one into a change at the layer that owns its cause: - wrong results go to an evaluation or test; - missing facts go to the context source; - unsafe actions go to policy; - timeouts go to runtime controls; - product questions go to the backlog.

Each change has an owner, a verification and a retirement condition. 14.46 did this for coding-agent corrections; this lesson does it for the product as well. The LLMOps lifecycle is covered in Lesson 14.122 (linked above). This lesson routes the signals the incident-agent story produced in 14.48 to 14.53, closes one loop with a real regression run, and writes the decision brief the practice lab asks for.

A team can collect traces, evaluations, support tickets, and incident logs without learning from any of them. The missing mechanism is promotion: a defined path from observation to a durable change with an owner and proof.

The loop is:

  1. observe a concrete signal;
  2. connect it to an outcome, constraint, or assumption;
  3. identify the earliest system layer that owns the cause;
  4. create a bounded change;
  5. verify that recurrence becomes less likely;
  6. review whether the control should remain.

Route to the Owning Layer

Signal Destination
False positive, regression, wrong result Evaluation or test
Missing context, duplicate work, stale fact Context source or retrieval route
Unsafe action or authority gap Policy or permission boundary
Timeout, retry storm, unavailable dependency Runtime control
New product need or unresolved tradeoff Shaped backlog item

Fix the cause at the earliest effective layer. Do not add another prompt paragraph when a test or permission can make the failure impossible.

Ownership Is Part of the Control

Every ratchet action needs:

  • one owner;
  • a priority based on consequence and recurrence;
  • the artifact to change;
  • the verification that proves the change;
  • a review or expiry window;
  • a retirement condition.

An unowned improvement is an observation with better formatting.

Retire Stale Controls

Feedback systems accumulate policy. That policy can become contradictory and expensive. Review controls when:

  • architecture or workflow changes;
  • a lower-level invariant replaces a higher-level instruction;
  • the protected failure has not appeared across the chosen window;
  • the control blocks legitimate work more often than it prevents harm.

Retirement also needs evidence. Do not delete a control because it feels old.

Connect Build and Coding-Agent Feedback

The same ratchet serves both tracks:

  • Product evidence changes the outcome frame, assumptions, slice, or measurement plan.
  • Coding-agent corrections change tests, context, scope, automation, or handoff.
  • Incidents can change both the product boundary and the agent workbench.

This is why shaping the build is not a phase that ends before coding. It continues through every accepted change.

The same idea as a formula

The lesson's priority. For severity s (1 to 5) and frequency f:

priority=s⋅f.

A severity-5 event seen once scores 5, below a severity-3 nuisance seen 6 times (18). To let a severe first occurrence jump the queue (14.46's Exercise 3), add a floor:

priority′=max(s⋅f, 1[s=5]⋅Pmax​).

A control is verified when recurrence drops. On a regression suite of n cases, record the failure count before and after the change. "Wrong service named" going from 4 to 0 is the evidence the control's verification asks for.

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging

tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()
CATALOG = {"checkout-api": ("checkout-",), "payments": ("pay-", "card processor"), "inventory": ("inv-", "stock"),
           "search": ("srch-",), "auth": ("auth-", "log in", "login")}
SUITE = [("Checkout errors: upstream card processor timeouts", "unknown"), ("DNS resolution failures across prod namespace", "unknown"),
         ("HighLatency service=checkout-api, caused by inv-5d8f slow queries", "unknown"), ("Login page slow after search deploy", "unknown"),
         ("HighLatency service=checkout-api p99=2.4s", "checkout-api"), ("PodCrashLooping pod=pay-7f9c namespace=prod", "payments"),
         ("HighMemory pod=srch-2a1b namespace=prod 93%", "search"), ("ErrorRate service=payments 5xx=7%", "payments")]
# for a cascade the safe answer is "unknown": a person diagnoses it. Naming the wrong service is the failure.
catalog_text = "\n".join(f"- {k}: matches {', '.join(v)}" for k, v in CATALOG.items())
def model(alert):
    ids = tok.apply_chat_template([{"role": "user", "content": f"Service catalog:\n{catalog_text}\n\nAlert: {alert}\nWhich service "
                                    "is failing? Answer with the service name only, or unknown if the cause is unclear."}],
                                  add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=10, do_sample=False)
    ans = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True).lower()
    return next((s for s in CATALOG if s in ans), "unknown")
CAUSAL = re.compile(r"caused by|upstream|after .* deploy|across", re.I)
def lookup(alert):

    return next(iter(hits)) if len(hits) == 1 and not CAUSAL.search(alert) else "unknown"

Part 1 of 3 · Signal, RatchetAction, destination, promote

# Lesson program for routing feedback into owned, verifiable system changes.
# Read: phases/14-agent-engineering/54-build-the-feedback-ratchet/docs/en.md
# Reference: Basili, Caldiera, and Rombach, The Goal Question Metric Approach.
# Reference: Fagerholm et al., Building Blocks for Continuous Experimentation, 2014.
# Run this file to generate outputs/feedback-backlog.json.
from __future__ import annotations

import json
from dataclasses import asdict, dataclass
from pathlib import Path


@dataclass(frozen=True)
class Signal:
    source: str
    observation: str
    severity: int
    frequency: int
    owner: str
    expires_after_days: int


@dataclass(frozen=True)
class RatchetAction:
    priority: int
    destination: str
    change: str
    owner: str
    durable_artifact: str
    verification_evidence: str
    retirement_check: str


def destination(signal: Signal) -> str:
    text = signal.observation.lower()
    if any(word in text for word in ("regression", "wrong result", "false positive")):
        return "evaluation"
    if any(word in text for word in ("permission", "unsafe", "production write")):
        return "policy"
    if any(word in text for word in ("missing context", "could not find", "duplicate")):
        return "context"
    if any(word in text for word in ("timeout", "retry", "unavailable")):
        return "runtime"
    return "backlog"


def promote(signal: Signal) -> RatchetAction:
    if signal.severity not in range(1, 6) or signal.frequency < 1:
        raise ValueError("severity must be one to five and frequency positive")
    target = destination(signal)
    priority = signal.severity * signal.frequency
    durable_artifact = {
        "evaluation": "evaluations/regression-suite.json",
        "policy": "policies/authority-boundaries.json",
        "context": "context/retrieval-guidance.md",
        "runtime": "runtime/reliability-controls.json",
        "backlog": "backlog/shaped-work.json",
    }[target]
    verification_evidence = {
        "evaluation": "Record a passing regression evaluation",
        "policy": "Record a passing authority-boundary scenario",
        "context": "Record a replay with the required context present",
        "runtime": "Record a timeout and retry scenario within budget",
        "backlog": "Record review against the outcome frame",
    }[target]
    return RatchetAction(
        priority,
        target,
        f"Prevent recurrence of: {signal.observation}",
        signal.owner,
        durable_artifact,
        verification_evidence,
        f"Remove or revise after {signal.expires_after_days} days without recurrence",
    )

Part 2 of 3 · backlog, example

def backlog(signals: list[Signal]) -> list[RatchetAction]:
    actions = [promote(signal) for signal in signals]
    return sorted(actions, key=lambda item: (-item.priority, item.destination, item.change))


def example() -> list[Signal]:
    return [
        Signal("incident 184", "missing context caused duplicate service lookup", 4, 3, "platform", 90),
        Signal("pilot audit", "production write was attempted", 5, 1, "security", 180),
        Signal("evaluation run", "false positive on a stale deployment", 3, 4, "evaluation", 60),
    ]


def main() -> None:
    output = Path(__file__).resolve().parents[1] / "outputs" / "feedback-backlog.json"
    output.write_text(json.dumps([asdict(item) for item in backlog(example())], indent=2) + "\n", encoding="utf-8")
    print(output.read_text(encoding="utf-8"))

Practice Lab: Own a Decision After a Setback

Choose one workflow from your career route's portfolio project. Carry it through one decision, a small experiment, and a review. Keep the evidence in the career delivery template.

The Python lab generates example backlog actions. It does not observe users, measure an intervention, or prove career readiness. Completing its run is preparation for this exercise.

1. Establish What Happened

Record the user, task, current workflow, and the outcome you wanted to improve. Link a consented observation, a redacted support record, or a reproducible task trace. Separate what you observed from what someone reported and what you inferred.

Find a setback: a failed assumption, an unusable result, an unexpected cost, or a delayed handoff. Explain which evidence changed your understanding. A setback needs a response and a decision, not a success story written around it.

If you cannot work with users, run a clearly labeled simulation with a peer or a stated scenario. Keep simulated observations separate from real-user evidence. Do not invent interviews, approvals, adoption, or business impact.

2. Make Progress Within Your Authority

List the unknowns and choose the cheapest reversible action that could resolve the most consequential one. State what you can decide, what is bounded by an existing agreement, and what needs authorization before execution.

For example, you may prepare a redacted offline replay while waiting for permission to use customer data. Taking initiative means moving authorized work forward and making the blocked decision clear. It does not expand your access or approval rights.

3. Compare Options and Brief the Decision Owner

Write a short decision brief for someone who does not need the implementation detail. Include:

  • the user problem and the evidence that changed the plan;
  • at least two options, including a cheaper manual or no-build option where credible;
  • quality, interaction design, effort, operating cost, and risk tradeoffs;
  • your recommendation, remaining uncertainty, and the decision needed;
  • the decision owner, affected stakeholders, and the date the decision is needed.

Ask a peer to represent an affected stakeholder and challenge one tradeoff. Record the objection and how it changes, or fails to change, your recommendation. Label role-play feedback as simulated; it cannot stand in for an actual stakeholder's agreement.

4. Run a Bounded Experiment

Choose prototype, pilot, or production work based on the question you need to answer. Define the audience, data, authority, duration, rollback, and conditions for continue, change, or stop before collecting the result.

Walk through the interaction from the user's starting point to a completed task. Include an incorrect output or missing-data case. Observe whether the user can notice the failure, correct it, and recover without hidden help from you.

Count human review and correction time as part of the workflow. A faster model response can still make the complete task slower or harder to trust.

5. Compare Outcomes and Economics

Record a baseline and a follow-up using the same metric definition, task population, collection method, and comparable observation windows. Keep sample counts, exclusions, and evidence links next to the numbers. If those conditions change, explain why the comparison is limited.

Include one user outcome, one quality or safety guardrail, and total human review effort. Record the result even when it misses the target. Small or simulated samples support a bounded learning claim, not a claim of proven business impact.

Estimate cost per successfully completed task using model calls, retries, supporting services, and human review. State the labor-rate assumption and separate measured usage from estimates. Compare that cost with the manual alternative or the value assumption behind the project.

Use the existing FinOps for LLMs lesson to deepen attribution and unit economics. Changing the model is only one possible response; narrowing the workflow or retaining a manual step may be the better product decision.

6. Close the Loop

Use the predeclared criteria to recommend continue, change, or stop. If the evidence is inconclusive, name the missing observation and the next bounded test. Record the accountable decision owner's response; leave it pending if no decision has been made.

Choose one improvement to the delivery process itself: a clearer task frame, earlier user walkthrough, better review checklist, smaller agent handoff, or tighter evaluation case. Assign an owner and a review date.

At review, decide whether to keep, revise, or retire that improvement. Record the evidence for the choice. A new checklist that creates more work without preventing the target failure has not earned permanence.

Solutions

SolutionP1 · Three of seven routed correctly

Three of seven: the explicit wrong result (evaluation), the approval wait (backlog) and the timeout (runtime). The rollback attempts, the repeated tool calls, the invented owner and the prototype drift all fall through to the backlog.

The lowest priority goes to the prototype reading production data with no owner. It is severity 5 but seen once, so 5×1=5 puts it last. That is the case for a priority floor on severe signals.

SolutionB1 · Observations without owners

The meeting produces observations, not ratchet actions. None has an owning layer, an owner, an artifact, a verification or a retirement condition, so each becomes a prompt paragraph, and the prompt grows while the failures recur.

One learning done properly looks like this: - Signal: "agent named the wrong service on 4 cascade alerts (trace links)". - Layer and artifact: evaluation, evaluations/regression-suite.json, with those four alerts expecting "unknown". - Owner: the evaluation owner. - Verification: the suite run before and after the change, wrong-service count 4 → 0. - Retirement: revise after 90 days without recurrence, or when the alert schema changes.

Prose rules that a test, hook or permission can enforce move there and are deleted from the prompt.

What You Keep

Keep outputs/feedback-backlog.json as the routing example and your completed career delivery evidence as the record of your own decisions. Together they close the Product Judgment and Delivery path and inform the next outcome frame.

Break it on purpose

A team's weekly "learnings" meeting lists twenty observations from traces and incidents. Each ends with "we should be more careful about X". Six months later the same failures recur, the agent's prompt is three pages long, and nobody can say which rule protects what. Using this lesson, what is missing, and what does one learning look like when done properly? (Solution B1.)

Industry practice
What's current (2024–2026)
  • Traces to datasets to evals. LangSmith, Braintrust and similar platforms let teams add a production trace to an evaluation dataset in a click. The failure then becomes a regression case that runs on every prompt or model change.
  • Postmortems with owned actions. Google SRE's blameless postmortem culture requires action items with owners and tracking. That is the ratchet record in operational form.
  • Enforceable controls over prose. Hooks and permission rules in coding agents, and guardrails in agent SDKs, are where policy-layer signals land, so a rule is executed rather than read.
  • On your laptop: the routing, prioritising and brief are standard-library Python. The regression run uses the 0.5B model on CPU.

Sources: Google SRE book, Postmortem culture, LangSmith, Evaluation, Braintrust docs, Claude Code, Hooks.

Recap
What to keep from this lesson
  • Every signal goes to the layer that owns its cause: evaluation, context, policy, runtime or backlog.
  • Each action has an owner, a priority, an artifact, a verification and a retirement condition.
  • Check the router on real signals. Keyword routing misplaced 4 of 7.
  • Give severe first occurrences a priority floor.
  • Close the loop with evidence of reduced recurrence, and label simulated evidence in any brief.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designTell me about a project where the evidence turned against your plan. What did you do inside your own authority, and how did you present the situation to the person who had to decide?

Level 3 of 4 · about 12 minutes to answer well.

Short answer. I separate what I observed from what was reported and what I inferred, name the setback and the evidence that changed my understanding, and move the reversible work I am allowed to do while the blocked decision waits. Then I write a short brief for the decision owner: the user problem and the new evidence, at least two options including a cheaper manual or no-build option where it is credible, the tradeoffs in quality, effort, cost and risk, my recommendation with its remaining uncertainty, and the decision needed with its owner and date.

Establish what happened.

A setback is a failed assumption, an unusable result, an unexpected cost or a delayed handoff. I record the user, the task, the current workflow and the outcome I wanted, and link a consented observation, a redacted record or a reproducible trace. Simulated observations stay labeled as simulated. I do not invent interviews, approvals or adoption.

Progress inside my authority.

I list the unknowns and pick the cheapest reversible action that resolves the most consequential one. I state what I can decide, what an existing agreement bounds, and what needs authorization. Preparing a redacted offline replay while waiting for permission to use customer data is initiative. Expanding my own access is not.

The brief.

The brief is for someone who does not need the implementation detail:

  • the user problem and the evidence that changed the plan;
  • at least two options, with a cheaper manual or no-build option where it is credible;
  • the tradeoffs in quality, interaction design, effort, operating cost and risk;
  • my recommendation, the remaining uncertainty and the decision needed;
  • the decision owner, the affected stakeholders and the date the decision is needed.

I ask a peer to represent an affected stakeholder and challenge one tradeoff, and I record whether the objection changes the recommendation. Role-play stays labeled; it cannot stand in for the real stakeholder's agreement.

Close the loop.

I recommend continue, change or stop against criteria declared in advance. If the evidence is inconclusive, I name the missing observation and the next bounded test. The decision owner's response goes in the record, or stays pending if none was made. Human review and correction time count as part of the workflow: a faster model response can still make the whole task slower or harder to trust.

Plausible wrong answers.

  • "Wait for the decision before doing anything." Reversible, authorized work can move forward; only the blocked decision waits.
  • "Present the recommendation alone to keep it simple." The owner needs the options and the tradeoffs to make a decision rather than approve a conclusion.
  • "Report the measured gain and leave out the review time." The complete task includes human review and correction; a faster model can still make the task slower.

Follow-ups an interviewer may ask.

  • (level 3) Why include a no-build option whenever it is credible? Expected: narrowing the workflow or keeping a manual step can be the better decision; without that option the brief only asks for permission to continue.
  • (level 3) What goes next to each number in the outcome comparison? Expected: the sample counts, the exclusions and the evidence links, with the same metric definition and comparable windows for baseline and follow-up.
  • (level 4) A simulated walkthrough passed every step. What claim can you make? Expected: a bounded learning claim only; unobserved real-user behavior stays a named gap with the next observation needed to close it.
  • (level 4) How do you turn the setback into a change in how the team delivers? Expected: pick one process improvement with an owner and a review date, then keep, revise or retire it on evidence.

Where it is taught. The feedback ratchet lesson gives the decision brief, the authority rule and the acceptance rubric.

Defend a designYou inherit a team that collects traces, evaluation scores, support tickets and incident logs for an assistant. Nobody can name a change that any of it caused. Design the mechanism that turns those signals into improvements, and tell me how you keep it from becoming another backlog.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. The missing piece is promotion: a defined path from an observation to a durable change with an owner and proof. Each signal is connected to an outcome, a constraint or an assumption, traced to a root cause, and routed to the earliest layer that owns that cause, which is evaluation, context, policy, runtime or a shaped backlog item. Every resulting action carries one owner, a priority from consequence and recurrence, the artifact to change, the verification, a review window and a retirement condition, so the loop produces controls that are later re-examined rather than rules that only accumulate.

The loop.

  1. Observe a concrete signal.
  2. Connect it to an outcome, a constraint or an assumption.
  3. Identify the earliest system layer that owns the cause.
  4. Create a bounded change.
  5. Verify that recurrence became less likely.
  6. Review whether the control should remain.

Route to the owning layer.

Signal Destination
False positive, regression, wrong result Evaluation or test
Missing context, duplicate work, stale fact Context source or retrieval route
Unsafe action or authority gap Policy or permission boundary
Timeout, retry storm, unavailable dependency Runtime control
New product need or unresolved tradeoff Shaped backlog item

A timeout belongs to the runtime, not to the general backlog, and a wrong answer belongs to a test, not to another prompt paragraph. The cause is fixed at the earliest effective layer.

Ownership is part of the control.

An unowned improvement is an observation with better formatting. Every action gets one owner, a priority based on consequence and recurrence, the artifact to change, the verification that proves the change, a review or expiry window, and a retirement condition.

Why it is not a backlog.

A backlog stores wishes. The ratchet stores controls with proof and expiry. Controls are reviewed when the architecture changes, when a lower-level invariant replaces a higher-level instruction, when the protected failure has stayed away across the window, or when the control blocks legitimate work more than it prevents harm. Retirement needs evidence too.

Metrics close the loop.

The signals only mean something against metrics defined before the result: outcome, guardrail and counter-metric, each with a threshold, a window and a source. The ratchet then changes the outcome frame, the assumptions, the slice or the measurement plan for product evidence, and the tests, context, scope or handoff for coding-agent corrections. Incidents can change both.

Plausible wrong answers.

  • "Build a dashboard so everyone can see the signals." Visibility without promotion and ownership changes nothing.
  • "Add each lesson learned to the system prompt." Prose is the weakest layer; a permission boundary can make the unsafe action impossible, and a test can block a release that repeats the failure.
  • "Keep every control forever since it was earned." Controls decay and conflict; each one needs a retirement condition and periodic review.

Follow-ups an interviewer may ask.

  • (level 3) Two teams share the assistant and disagree on a tradeoff a signal exposes. Where does it go? Expected: to a shaped backlog item with a human decision owner; the ratchet does not resolve product disagreements by itself.
  • (level 4) How do you prioritize across many signals? Expected: by consequence and recurrence together, so a severe single event and a frequent minor one both rise above a rare minor one.
  • (level 4) What proves the loop works after a quarter? Expected: named controls that trace back to signals, verification results that show recurrence fell, and retirements with their evidence; not the volume of telemetry collected.

Where it is taught. The feedback ratchet lesson gives the routing table and the ownership fields, and the success metrics lesson gives the metric contract the signals are judged against.
