In plain words first
The idea in one line

Provider lock-in is expensive. Different tool-calling workloads suit different models. Routing gateways give one API surface, retries, failover, cost tracking, and guardrails. Three archetypes dominate 2026: LiteLLM (open-source self-hosted), OpenRouter (managed SaaS), Portkey (production-grade, open-sourced in March 2026). This lesson names the decision criteria and walks a stdlib routing gateway.

The problem

In plain words first

Applications rarely talk to one model provider directly for long. A routing layer is a small service that sits between your code and the providers. Your code asks for a name such as smart or fast; the router maps that name to real models, tries another provider when the first one fails, spreads load, counts tokens and money per team, can answer repeated questions from a cache, and can remove private data before a prompt leaves your network. LiteLLM is the common open-source choice you run yourself, OpenRouter is a hosted service with one bill for many providers, and Portkey offers both. This lesson runs LiteLLM's real Router with a failing provider and simulated responses (no paid calls), then adds a semantic cache, a privacy filter and a team budget, including the case where the cache gives a wrong answer.

Scenarios where provider routing matters:

  1. Cost. Claude Sonnet costs 3x what Haiku costs. For a triage task, Haiku is enough; for a synthesis task, Sonnet is worth it. Route per-request.

  2. Failover. OpenAI has a bad hour. Every request fails. You want automatic fallback to Anthropic without redeploying.

  3. Latency. A live chat UI needs fast time-to-first-token. A batch summarizer does not. Route by latency SLA.

  4. Compliance. EU users must stay in EU regions. Route by region.

  5. Experimentation. A/B two models on the same workload. Route by test bucket.

Hand-coding all of this per integration is repetitive. A routing gateway gives one OpenAI-compatible API and handles the rest.

Idea 1 · OpenAI-compatible proxy shape

Everyone speaks OpenAI-shape. The routing gateway exposes /v1/chat/completions, accepts the OpenAI schema, and internally proxies to Anthropic / Gemini / Cohere / Ollama / anything. The client does not care.

Idea 2 · Model aliases

Instead of a pinned snapshot id, your code says our_smart_model. The gateway maps aliases to real models. When a provider ships a new generation, you change the alias server-side; your code does not touch a thing.

Idea 3 · Fallback chains

primary: openai/gpt-5
on 5xx: anthropic/claude-sonnet-4-5
on 5xx: gemini/gemini-2.5-pro
on 5xx: refuse

Gateways define this in a config. Retries count against a budget so fallback cascades do not explode cost.

Idea 4 · Semantic caching

Identical-or-near-identical prompts hit a cache instead of the provider. Savings depend entirely on how repetitive the traffic is. Keys are embedding-based, so near-identical prompts share a cache slot, and so can prompts that look alike but mean different things (see the run below).

Idea 5 · Guardrails

Gateway-level:

  • PII redaction. Regex or ML-based pass before sending prompts.
  • Policy violations. Reject prompts with prohibited content.
  • Output filters. Scrub completions for leaks.

Portkey and Kong both ship opinionated guardrails. LiteLLM leaves them optional.

Idea 6 · Per-key rate limits

One API key = one team. Per-key budgets prevent one team from consuming the shared quota. Most gateways support this.

Idea 7 · Self-hosted vs managed trade-offs

Factor LiteLLM (self-hosted) OpenRouter (managed) Portkey (production)
Code Open source, Python Managed SaaS Open source (Mar 2026) + managed

LiteLLM wins when you have an SRE team and want data sovereignty. OpenRouter wins when you want a single subscription and no infra. Portkey wins when you need guardrails and compliance out of the box.

Idea 8 · Cost tracking

Every request carries provider, model, input_tokens, output_tokens. Multiply by per-model per-token prices (pulled from a pricing sheet the gateway maintains). Per-user / per-team / per-project aggregation.

Idea 9 · MCP plus routing

A gateway can route both LLM calls AND MCP sampling requests. When a sampling request's modelPreferences prefer a specific model, the gateway translates to the right backend. This is where Phase 13 · 17 (MCP gateway) and this lesson's routing gateway sometimes merge into one service.

Idea 10 · Routing strategies

  • Static priority. First in list; fall back on error.
  • Load balancing. Round-robin or weighted.
  • Cost-aware. Pick the cheapest model meeting latency / quality.
  • Latency-aware. Pick the fastest model in the last N minutes.
  • Task-aware. Prompt classifier routes coding to one model, summarization to another.

The same idea as a formula

Cost of one call. With token counts nin​,nout​ and per-token prices pin​,pout​,

cost=nin​pin​+nout​pout​.

Weighted load balancing. With weights wi​, deployment i gets a share wi​/∑j​wj​ of calls on average; over N calls the count varies by about Nq(1−q)​ with q the share.

Expected cost with fallback. If the primary fails with probability f and a failed attempt still costs cfail​ (often 0 for a refused connection, but the full price for a timeout after generation),

E[cost]=(1−f)c1​+f(cfail​+c2​).

Semantic cache. A prompt q reuses cached answer ak​ when cos(e(q),e(k))≥τ. A higher τ means fewer wrong reuses but fewer hits; no τ separates prompts whose embeddings are almost equal but whose meanings differ.

Worked example
Pricing one request and a weighted split
  • The fallback answer came from claude-sonnet-4-5 with 10 input and 20 output tokens. At US$3 and US$15 per million: $10 \times 3 \times 10^{-6} + 20 \times 15 \times 10^{-6} = 0.00003 + 0.0003 = \$0.00033$.
  • fast has weights 3 and 1, so Haiku should get 3/4 of 40 calls = 30, give or take 40⋅0.75⋅0.25​≈2.7. The run gets 27 and 13: a little over one standard deviation from 30, which is normal for random shuffling.
  • A Haiku call (about 10 in, 20 out tokens) costs $10 \times 10^{-6} + 20 \times 5 \times 10^{-6} = \$0.00011$; a gpt-5-mini call $10 \times 0.25 \times 10^{-6} + 20 \times 2 \times 10^{-6} \approx \$0.0000425$.
Check your mental model
  • ✗ "With a router, my code never needs to know about providers."
    ✓ Mostly true for chat calls; provider-specific features (caching controls, structured-output limits, tool quirks) still leak through.
  • ✗ "A semantic cache is a free win."
    ✓ It can return a confidently wrong answer for a prompt that looks similar but means something else.
  • ✗ "Fallback only changes which provider answers."
    ✓ It can change quality, cost, latency, data residency and tool-call format; test the whole chain.
  • ✗ "A budget check before each call stops spending exactly at the limit."
    ✓ It can overshoot by the calls in flight; reserve an estimate before calling if that matters.

# LiteLLM's Router (pinned, see "What's current"): aliases, a real failover, load balancing and cost.
# No paid calls: the healthy deployments use LiteLLM's mock_response; the "down" one points at a closed local port.
import os, collections, logging
os.environ["LITELLM_LOCAL_MODEL_COST_MAP"] = "True"          # use the price map shipped with the package, no download
import litellm
from litellm import Router
litellm.suppress_debug_info = True; logging.getLogger("LiteLLM").setLevel(logging.CRITICAL)
logging.getLogger("LiteLLM Router").setLevel(logging.CRITICAL)
import importlib.metadata, random; random.seed(0)
print("litellm", importlib.metadata.version("litellm"))
from litellm.integrations.custom_logger import CustomLogger
class Attempts(CustomLogger):                     # see every attempt the router makes, including failed ones
    def log_failure_event(self, kwargs, response_obj, start_time, end_time):
        print(f"   attempt failed: {kwargs.get('model')} -> {type(kwargs.get('exception')).__name__}")
litellm.callbacks = [Attempts()]


ok = lambda text: {"mock_response": text}
router = Router(model_list=[
    # alias "smart": primary is OpenAI, but its endpoint is down (connection refused)
    {"model_name": "smart", "litellm_params": {"model": "openai/gpt-5", "api_key": "sk-test", "api_base": "http://127.0.0.1:9/v1", "timeout": 3}},
    {"model_name": "smart-backup", "litellm_params": {"model": "anthropic/claude-sonnet-4-5", "api_key": "sk-test", **ok("Synthesis from the backup model.")}},
    # alias "fast": two healthy deployments, load-balanced
    {"model_name": "fast", "litellm_params": {"model": "anthropic/claude-haiku-4-5", "api_key": "sk-test", "weight": 3, **ok("Triage: billing.")}},
    {"model_name": "fast", "litellm_params": {"model": "openai/gpt-5-mini", "api_key": "sk-test", "weight": 1, **ok("Triage: billing.")}},
], fallbacks=[{"smart": ["smart-backup"]}], num_retries=0)

msgs = [{"role": "user", "content": "Summarize the three incident reports into one paragraph."}]
print("\ncalling alias smart:")
r = router.completion(model="smart", messages=msgs)
print(f"alias smart -> served by {r.model} | {r.choices[0].message.content}")
print(f"   tokens in/out {r.usage.prompt_tokens}/{r.usage.completion_tokens}, cost ${r._hidden_params['response_cost']:.6f}")

served = collections.Counter(); spend = collections.defaultdict(float)
for i in range(40):
    r = router.completion(model="fast", messages=[{"role": "user", "content": f"Route ticket #{i}: card charged twice."}])
    served[r.model] += 1; spend[r.model] += r._hidden_params["response_cost"]
print("\nalias fast, 40 calls, weights 3:1 ->", dict(served))
for m, c in spend.items(): print(f"   {m:<22} total ${c:.6f}")

print("\nper-token prices LiteLLM uses (USD per million, input/output):")
for m in ("claude-sonnet-4-5", "claude-haiku-4-5", "gpt-5", "gpt-5-mini"):
    c = litellm.model_cost[m]; print(f"   {m:<20} {c['input_cost_per_token'] * 1e6:5.2f} / {c['output_cost_per_token'] * 1e6:5.2f}")

Reading this output

The alias hid a real failure. The call to smart first went to gpt-5, whose endpoint refused the connection. The logger saw one failed attempt (LiteLLM reports it as an InternalServerError, a server-side class of error that triggers fallback), and the router moved to smart-backup. The caller got an answer from claude-sonnet-4-5 and did not have to change any code.

Every response carries its cost. LiteLLM priced the backup call at US$0.00033 from its bundled price map, the same number as the worked example. Those prices are a snapshot: check them against the providers' pages before relying on them.

Weights shape the split, randomly. With weights 3:1 the 40 fast calls went 27 and 13. That is near the expected 30 and 10; the exact split changes from run to run without the fixed seed.

Cheaper is not always cheaper per task. gpt-5-mini is far cheaper per token than Haiku here; whether it is good enough for the task is a quality question the router cannot answer for you.

A semantic cache, a PII guardrail and a team budget

This block continues from the one above (it reuses router). The cache embeds prompts with bge-small-en-v1.5 and reuses an answer at cosine similarity ≥ 0.90; the guardrail redacts emails and card numbers before the call; team-support has a budget of US$0.0003. About 5 seconds.

# Continues from the block above (uses `router`). A gateway's other jobs: semantic cache, PII guardrail, per-key budget.
import re
from sentence_transformers import SentenceTransformer
emb = SentenceTransformer("BAAI/bge-small-en-v1.5")

class SemanticCache:
    def __init__(self, threshold): self.t, self.keys, self.vals = threshold, [], []
    def get(self, prompt):
        if not self.keys: return None, 0.0
        v = emb.encode([prompt], normalize_embeddings=True)[0]
        sims = [float(v @ k) for k in self.keys]; i = max(range(len(sims)), key=sims.__getitem__)
        return (self.vals[i] if sims[i] >= self.t else None), sims[i]
    def put(self, prompt, answer): self.keys.append(emb.encode([prompt], normalize_embeddings=True)[0]); self.vals.append(answer)

PII = [(re.compile(r"[\w.+-]+@[\w-]+(?:\.[\w-]+)+"), "<email>"), (re.compile(r"\b(?:\d[ -]?){13,16}\b"), "<card>")]
def guard(text):
    for rx, sub in PII: text = rx.sub(sub, text)
    return text

BUDGET = {"team-support": 0.0003, "team-research": 1.00}; spent = {k: 0.0 for k in BUDGET}
cache = SemanticCache(threshold=0.90)
def gateway(key, prompt):
    prompt = guard(prompt)                                  # redact before anything leaves the building
    hit, sim = cache.get(prompt)
    if hit: return f"[cache hit, sim {sim:.3f}] {hit}"
    if spent[key] >= BUDGET[key]: return f"[429 budget exhausted for {key}]"
    r = router.completion(model="fast", messages=[{"role": "user", "content": prompt}],
                          mock_response=f"Answer to: {prompt[:48]}")
    spent[key] += r._hidden_params["response_cost"]; cache.put(prompt, r.choices[0].message.content)
    return f"[{r.model}, sim {sim:.3f}, ${spent[key]:.6f} spent] {r.choices[0].message.content}"

for key, p in [("team-support", "What is your refund policy for orders over $100?"),
               ("team-support", "what's the refund policy for orders above $100"),          # paraphrase: should hit
               ("team-support", "What is your refund policy for orders under $100?"),        # different meaning
               ("team-support", "Customer jane.doe@example.com paid with 4111 1111 1111 1111, check the charge"),
               ("team-support", "How do I reset my password?"),
               ("team-support", "Which plan includes SSO?")]:
    print(f"{key}: {p[:56]!r}\n   -> {gateway(key, p)}")

Reading this output

The first question is a miss, the paraphrase a hit. what's the refund policy for orders above $100 scores 0.980 against the cached question and reuses its answer: a call saved.

The cache also gives a wrong answer. orders under $100 scores 0.992, even higher than the true paraphrase, because one word changed and embeddings barely notice. The user gets the policy for orders over US$100. Thresholds cannot fix this; keep prompts with numbers, names or negations out of the cache, or cache only after an exact-match check on such details.

Private data never left. The email and card number were replaced with <email> and <card> before the router saw the prompt; the redacted text is what reached the model and the cache.

The budget stops the team. After three paid calls team-support had spent US$0.00033, above its US$0.0003 budget, so the last request got a 429. The check runs before each call, so spending ended slightly over the limit.

Break it on purpose

A team configures the fallback chain gpt-5 → claude-sonnet-4-5 → a self-hosted model in another country, with 3 retries per step and a 60-second timeout per attempt. During a provider outage, what can go wrong for latency, cost and compliance? (Solution B1.)

Industry practice
What's current (2024–2026)
  • LiteLLM: the most used open-source router and proxy (Python SDK plus a proxy server with virtual keys, budgets and fallbacks). Security note: on 24 March 2026 two PyPI releases, 1.82.7 and 1.82.8, were malicious credential stealers for a short window. Pin versions, verify hashes, and if either version ever touched a machine, rotate every secret on it. This lesson uses 1.111.0.
  • OpenRouter: a hosted API with hundreds of models, one bill and provider routing preferences.
  • Portkey: the full production gateway became open source on 24 March 2026, alongside its managed service.
  • Others in production: Kong AI Gateway, Cloudflare AI Gateway, Envoy AI Gateway, cloud-native options such as Amazon Bedrock and Azure AI Foundry routing.
  • On your laptop: LiteLLM can route to a local Ollama or vLLM server, for example a 4-bit 7B model on the RTX 4060 as the cheap tier with a hosted model as the fallback.

Sources: LiteLLM routing docs, LiteLLM security update, March 2026, Portkey gateway open-source announcement, OpenRouter docs.

Recap
What to keep from this lesson
  • Code asks for aliases; the router maps them to deployments.
  • Fallback chains are tried in order on failures; cap retries and timeouts.
  • Cost is tokens times price per deployment, tracked per key or team.
  • Semantic caches save calls but can return wrong answers; keep the threshold high and exclude sensitive or numeric prompts.
  • Redact personal data before the prompt leaves your network.
  • Treat the router as critical infrastructure: pin and verify its versions.

Solutions

SolutionP1 · The backup answers; roughly 30 and 10

claude-sonnet-4-5, through the fallback. The router first tries the smart deployment (gpt-5); the connection is refused, the logger records one failed attempt, and with num_retries=0 the router goes straight to the smart-backup group.

For fast, the weights 3:1 send about three quarters of the calls to Haiku: about 30 of 40, with a typical spread of two or three either way, and about 10 to gpt-5-mini. The run gives 27 and 13.

SolutionB1 · A slow, expensive, non-compliant outage

Latency explodes. If the primary hangs rather than refusing, each attempt waits up to 60 seconds, and 3 retries mean up to 4 minutes before the first fallback is even tried, then possibly another 4 minutes on the second step. Users time out long before an answer arrives. Use short connect timeouts, a small total deadline for the whole chain, and a circuit breaker that skips a provider known to be down.

Cost can double. A timeout after generation started may still be billed, and every retry of a long prompt is paid again. Retries should apply only to errors that are safe and cheap to retry.

Compliance breaks quietly. The last step sends user data to another country. If the data must stay in a region, the fallback is a violation, and it only happens during outages, when nobody is watching. Each fallback target must satisfy the same data rules as the primary, or the chain must stop and return an error.

Behaviour changes. Different models format tool calls, refusals and JSON differently, so test the full chain with the real prompts.

Interview questions

Try answering out loud first, then open one answer at a time.

Questions from real AI engineering interviews that this lesson prepares you for. Answer out loud first, then open the worked answer.

Defend a designThe CTO wants every product-critical model call to survive a full outage of one provider, with no redeploy and without doubling the bill. Design the setup: where the second provider sits, how a request moves between the two, what has to be identical on both sides, and what the design costs.

Level 4 of 4 · about 18 minutes to answer well.

Short answer. Put a gateway in front of the application with one model alias per use case, a priority list of two providers behind each alias, and a fallback rule on server errors and rate limits with a bounded retry budget. Keep the cacheable prefix layout, the tool order and the output schema identical on both providers, so that a failed-over request can hit the second provider's cache once that prefix is cached there, and still parses. The steady-state uplift is small, because the gateway sends traffic to the preferred provider most of the time, and the real price is paid in evals and prompt tests that run twice.

Why two.

The lesson on managed platforms argues that locking into one platform locks you out of most of the frontier, because the strongest model moves between vendors every few months, and that a single platform's regional outage is a product outage. Its policy is a two-provider minimum for any product-critical call. The cost uplift is negligible because the gateway routes to the better option in normal operation, and the availability gain during an outage is decisive.

The gateway in front.

The lesson on the routing layer gives the shape. Everyone speaks one API schema, so the gateway exposes one endpoint and translates behind it. Your code names an alias such as our_smart_model, and the gateway maps the alias to a concrete model on a concrete provider. Behind each alias sits a priority list: the primary, then the second provider on a server error or a rate limit, then refuse. Retries count against a budget, so that a failing primary cannot multiply the cost. The gateways lesson adds the rest of what the layer owns: rate limits per tenant, credentials pulled from a vault at runtime, observability and guardrails.

What the two sides share.

  1. The cacheable prefix layout. The rule for cross-provider fallback in the lesson on prompt caching is to keep the layout identical, so that any hit works on either side. Stable parts first, the user message last.
  2. The tool serialization order. A reshuffled tool list breaks the cache on every request.
  3. The output schema and the parser. A failover that returns a shape the application cannot parse is still an outage.
  4. The eval set. Both providers run the same regression suite on every prompt change, or the fallback path drifts without anyone noticing.

What it costs.

  • Two sets of evals and prompt regressions per release.
  • Cold caches on the second provider when the outage begins. The first requests pay the write premium, and the minimum cacheable block has to be met on both sides.
  • The gateway's own latency, from a few milliseconds to tens, depending on its class.
  • A log line per call that names the provider that served it, so that the bill splits and the failover rate is visible.

Prove it before the outage.

Inject rate-limit errors from the primary in staging and watch the traffic move. Measure the time to the first successful response on the second provider, and compare the first-token time and the cache reads during the failover with the steady state.

Plausible wrong answers.

  • "Two providers double the bill." The second provider carries traffic only during failures. The gateway routes to the preferred one the rest of the time.
  • "Tune a separate prompt per provider." Then every change ships twice and the fallback path drifts. Keep one layout and one eval set for both.
  • "Fail over on any error." A guardrail block or a schema error repeats on the second provider and doubles the cost of a request that should fail fast.

Follow-ups an interviewer may ask.

  • (level 3) Why does the second provider cost little in steady state? Expected: the gateway sends most traffic to the preferred provider. The second one carries traffic only during failures and drills.
  • (level 4) What breaks first on a failover without the identical prefix layout? Expected: the cache on the second provider misses on every request, so the outage hour costs full price and the first-token time jumps.
  • (level 4) Which failures trigger the failover, and which do not? Expected: server errors, rate limits and timeouts on the primary. Not a guardrail block or a malformed response, which would fail the same way on the second provider.
