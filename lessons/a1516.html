In plain words first
The idea in one line

Every graph-state transition persists. When a worker crashes, its lease expires and another worker picks up at the latest checkpoint. Cloudflare Durable Objects hold state across hours or weeks. Propose-then-commit (Lesson 15.15) defines a rollback plan per action. Post-action verification closes the loop. EU AI Act Article 14 makes effective human oversight mandatory for high-risk systems, and Article 12 requires automatic logs; one practical reading, this lesson's rather than the Act's, is that checkpoints must be queryable, rollbacks must be rehearsed, and the audit trail must survive a deploy. The sharp failure mode: without idempotency keys and precondition checks, a retry after a transient failure can double-execute an already-approved action. Post-action verification is what catches it.

The problem

In plain words first

A checkpoint is a saved copy of where a workflow is, so a crash costs only the step in progress. A rollback undoes a step that went wrong. The hard part is the moment between "do it" and "write down that it was done": a crash there either loses the action or repeats it. Checkpoints, threads and resume are covered in Lessons 14.60 and 14.103 (linked above). This lesson crashes the lesson's transfer at each point of its commit, then gives a small coding model checkpoints and rollback.

Durable execution (Lesson 15.12) makes a crashed agent resumable. Propose-then-commit (Lesson 15.15) makes an approved action auditable. This lesson joins them: what happens when an approved action executes partially, crashes, and resumes? When does the rollback run, and against what state?

Real systems wire this up differently:

  • LangGraph checkpoints every graph-state transition to PostgreSQL. On worker crash, the lease releases and another worker resumes at the latest checkpoint. Workflows pause on interrupt(), which itself persists.
  • Cloudflare Durable Objects hold per-key state across hours or weeks. Co-locate the computation with the storage for the approved action.
  • Microsoft Agent Framework exposes Checkpoint primitives in the workflow API; replay plus idempotency covers retries.

In every case, the combination that actually works is: idempotency key (prevents double-execute) + precondition check (state is still what we approved against) + post-action verify (the side effect actually happened) + rollback on verify-fail.

Idea 1 · Every transition persists

A graph-state transition is any step that moves the workflow from one named state to another. Naive implementations persist only at specific commit points; production implementations persist every transition. The cost (a few extra writes) is small relative to the reliability gain (replay lands anywhere, lease recovery is precise).

Idea 2 · Lease recovery

When a worker crashes, the workflow is not lost; the lease (a short-lived claim that this worker is executing this run) simply expires. Another worker picks up the latest checkpoint and resumes. The lease mechanism is what lets production systems survive rolling deploys without losing in-flight work.

Idea 3 · Idempotency plus preconditions

Idempotency alone is not enough. Consider: a workflow is approved to "transfer $100 from A to B when balance > $1000." The workflow is committed, crashes mid-execution, and resumes. If only the idempotency key is checked, and the execution resumes, the transfer runs once (correct). But consider that between crash and resume, A's balance drops to $500 via a different workflow. The idempotency check still passes; the precondition does not. Without a precondition check, we ship an overdraft.

Every consequential action needs both:

  • Idempotency key: prevents double-execute.
  • Precondition check: confirms the state is still consistent with what was approved.

Idea 4 · Post-action verification

"The tool returned 200" is not verification. Real verification re-reads the target state and confirms the side effect actually happened. Patterns:

  • Database update: UPDATE ... RETURNING * then assert the returned row matches intended state.
  • Email send: check sent-folder for the message ID after submission.
  • File write: read the file back and hash it.
  • API call: follow-up GET on the target resource.

If verify fails, the workflow is in a known-bad state. Rollback engages.

Idea 5 · Rollback plans

Every consequential action in propose-then-commit (Lesson 15.15) carries a rollback plan. Types:

  • In-band rollback: reverse the side effect directly (DELETE after INSERT, Send-correction-email after send).
  • Compensating transaction: a new action that neutralizes the original (standard SAGA pattern).
  • Out-of-band rollback: alert a human, pause the workflow, leave the bad state for investigation.

No-op rollback ("we cannot undo this") must be named in the proposal. Actions with no rollback require stronger HITL at commit time (Lesson 15.15 challenge-and-response).

Idea 6 · EU AI Act Article 14 operational reading

Article 14 requires "effective human oversight" for high-risk systems, and Article 12 requires them to keep automatic logs. The Act does not list engineering practices; one operational reading is:

  • Checkpoints are queryable by an auditor.
  • Rollbacks are rehearsed (tested end-to-end at least once).
  • The audit trail survives a deploy (checkpoint backend is not ephemeral).
  • Failed verifications are alerted on, not silently logged.

A workflow that crashes mid-commit, resumes, and completes the side effect without a verify + rollback pathway would be hard to defend as effective oversight.

Idea 7 · The sharp failure mode: the double-execute

The most common production incident in this space:

  1. Action approved, idempotency key k.
  2. Commit starts, executes, returns 200.
  3. Workflow crashes before persisting the "committed" status.
  4. Workflow resumes; sees "approved but not committed"; re-executes.
  5. Side effect fires twice.

Mitigation: persist an "in-flight" intent before execution, execute with an idempotency key, then mark "committed" only after post-action verification succeeds. If the action fires and the status write fails, you know to verify and (if necessary) re-fire. If the status write succeeds and the action fails, you verify and fire exactly once via the recovery path.

The same idea as a formula

Where the crash lands decides what you get. A commit has two writes, the status S and the effect E. A crash can land between them. - Status first (S then E): a crash between them leaves S = done with no E. The retry skips, so the effect happens at most once, possibly zero times. - Effect first (E then S): a crash leaves E with no S. The retry repeats E, so the effect happens at least once, possibly twice.

Exactly once needs a question to the outside system. Write $S = $ in-flight, perform E tagged with the transaction id x, then mark verified. On resume from in-flight, ask the system of record whether x∈ledger. Perform E only if it is absent, then mark verified:

#E=1whatever point the crash hits.

Verify on the effect's own key. Checking a shared field, such as "the last transfer id", is true only if nothing else wrote in between. Checking x∈ledger does not depend on anything else that happens.

Worked example
Crashing one transfer
  • The lesson's order writes "committed" and then moves 100. A crash between the two leaves "committed" and A at 1,500. The retry says "skipped", and the money never moved.
  • Exercise 2's order moves the money and then writes the status. A crash between them leaves A at 1,400 with no status. The retry moves it again, and A ends at 1,300.
  • In-flight plus ledger: a crash before the money leaves "in-flight" and an empty ledger, so the retry moves it once. A crash after the money leaves "in-flight" and tx-9 in the ledger, so the retry only marks it verified. A ends at 1,400 both times.
Check your mental model
  • ✗ "Marking a step done before doing it makes it safe to retry."
    ✓ It makes it safe from doubling, at the cost of sometimes never doing it.
  • ✗ "A verify check that passed in testing is a good verify check."
    ✓ The lesson's verify reads a shared field. With one concurrent transfer it rolled back a transfer that had succeeded.
  • ✗ "Rolling back is always possible."
    ✓ An inverse operation can fail too; if B had spent the money, reversing the transfer would overdraw it. Name the rollback type in the proposal and test it.
  • ✗ "An agent's retries make code better over time."
    ✓ The small model's rewrites made the file worse almost every time. Only a checkpoint before each attempt kept the working version.

Three orders of operations, each crashed after its first write and then retried: the lesson's (status first), exercise 2's (money first), and an in-flight record checked against a ledger. # The lesson's run_transfer() (imported from main.py) writes "committed" before it moves the money. Here it crashes
# at each point of the commit, then retries; the same for the opposite order (exercise 2); then for an in-flight
# record checked against a ledger on resume. Last, a verify that reads a shared field meets a concurrent transfer.
# Deterministic; runs in under a second.
import os, tempfile
import main
from main import Checkpoint, key

tmp = tempfile.mkdtemp()
def fresh():
    main.DB.clear(); main.DB.update({"balance_A": 1500, "balance_B": 200, "last_transfer_id": None})
LEDGER = []                                          # the bank's own record: one entry per transfer that happened
def move(txid, a, b, amt):
    main.persist_transfer(txid, a, b, amt); LEDGER.append(txid)

class Crash(Exception):
    pass
def mark_first(cp, txid, crash_at):                 # the lesson's order: status, then the money
    k = key(txid)
    if cp.load().get(k, {}).get("status") == "committed":
        return "skipped (already committed)"
    cp.save(k, {"status": "committed"})
    if crash_at == "after status": raise Crash
    move(txid, "A", "B", 100)
    if crash_at == "after money": raise Crash
    return "done"
def mark_after(cp, txid, crash_at):                 # exercise 2: the money, then status
    k = key(txid)
    if cp.load().get(k, {}).get("status") == "committed":
        return "skipped (already committed)"
    move(txid, "A", "B", 100)
    if crash_at == "after money": raise Crash
    cp.save(k, {"status": "committed"})
    if crash_at == "after status": raise Crash
    return "done"
def in_flight(cp, txid, crash_at):                  # status in-flight, money with the txid, verify on the ledger
    k = key(txid)
    st = cp.load().get(k, {}).get("status")
    if st == "verified":
        return "skipped (verified)"
    if st == "in-flight" and txid in LEDGER:         # resume: did it happen? ask the bank, not ourselves
        cp.save(k, {"status": "verified"}); return "resumed: found in ledger, marked verified"
    cp.save(k, {"status": "in-flight"})
    if crash_at == "after status": raise Crash
    if txid not in LEDGER:
        move(txid, "A", "B", 100)
    if crash_at == "after money": raise Crash
    cp.save(k, {"status": "verified" if txid in LEDGER else "verify-failed"})
    return "done"

print(f"{'order':<26} {'crash':<14} {'retry says':<42} transfers that happened")
for name, fn_ in (("lesson: status first", mark_first), ("exercise 2: money first", mark_after), ("in-flight + ledger", in_flight)):
    for crash_at in ("after status", "after money"):
        fresh(); LEDGER.clear()
        cp = Checkpoint(os.path.join(tmp, f"{name[:5]}{crash_at[-5:]}.json"))
        try:
            fn_(cp, "tx-9", crash_at)
        except Crash:
            pass
        said = fn_(cp, "tx-9", None)
        print(f"{name:<26} {crash_at:<14} {said:<42} {len(LEDGER)}  (A={main.DB['balance_A']})")

print("\na verify that reads last_transfer_id, while another transfer lands in between")
fresh(); LEDGER.clear()
cp = Checkpoint(os.path.join(tmp, "race.json"))
real_persist = main.persist_transfer
def persist_then_other(txid, a, b, amt):
    real_persist(txid, a, b, amt)
    if txid == "tx-10":
        real_persist("tx-other", "B", "A", 50)       # a second workflow commits before our verify runs
main.persist_transfer = persist_then_other
print(f"   lesson's run_transfer(): {main.run_transfer(cp, 'tx-10', 'A', 'B', 100, min_balance=200)}")
main.persist_transfer = real_persist
print(f"   DB after: {main.DB}")
print(f"   tx-10 was rolled back although it succeeded, and last_transfer_id now names neither transfer"
      if main.DB["last_transfer_id"] not in ("tx-10", "tx-other") else "")

# This block continues from the one above: checkpoints for a real coding agent. Qwen2.5-0.5B-Instruct (sampling at
# temperature 0.8, CPU) gets four attempts to fix a bug in a small module, rewriting the whole file each time. The
# tests run in a sandbox (no network) after every attempt. Without checkpoints every rewrite is kept; with them, the
# file is saved before each attempt and restored if fewer tests pass, the idea behind Claude Code's checkpoints and
# /rewind. About 2 minutes.
import json, os, re, subprocess, sys, tempfile, warnings
os.environ["HF_HUB_OFFLINE"] = "1"
warnings.filterwarnings("ignore")
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM, logging as hf_logging
hf_logging.set_verbosity_error(); hf_logging.disable_progress_bar()
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
llm = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct").eval()

START = '''def apply_discount(price, pct):
    """Return price after a pct percent discount, rounded to 2 decimals."""
    return round(price - price * pct, 2)

def total(items):
    """Sum of price * qty over (price, qty) pairs."""
    return sum(p * q for p, q in items)

def clamp(x, lo, hi):
    """Limit x to the range lo..hi."""
    return max(lo, min(x, hi))
'''
TESTS = r'''
import json, sys
sys.path.insert(0, ".")
res = []
def t(f):
    try: res.append(bool(f()))
    except Exception: res.append(False)
try:
    import pricing as m
    t(lambda: m.apply_discount(100, 10) == 90.0); t(lambda: m.apply_discount(19.99, 25) == 14.99)
    t(lambda: m.total([(2.5, 2), (1, 3)]) == 8.0); t(lambda: m.total([]) == 0)
    t(lambda: m.clamp(5, 0, 3) == 3); t(lambda: m.clamp(-1, 0, 3) == 0)
except Exception:
    res = [False] * 6
print(json.dumps(res))
'''
def passed(code):
    d = tempfile.mkdtemp()
    open(os.path.join(d, "pricing.py"), "w").write(code)
    try:
        p = subprocess.run(["unshare", "-n", sys.executable, "-I", "-c", TESTS], cwd=d, capture_output=True, text=True, timeout=20)
        return sum(json.loads(p.stdout.strip() or "[]"))
    except (subprocess.TimeoutExpired, json.JSONDecodeError):
        return 0
def attempt(code, seed):
    prompt = ("The test apply_discount(100, 10) == 90.0 fails. Fix the bug. Reply with the complete corrected file in one "
              "```python block.\n\n```python\n" + code + "```")
    ids = tok.apply_chat_template([{"role": "user", "content": prompt}], add_generation_prompt=True, return_tensors="pt", return_dict=True)["input_ids"]
    torch.manual_seed(seed)
    with torch.no_grad():
        out = llm.generate(ids, max_new_tokens=350, do_sample=True, temperature=0.8, top_p=None, top_k=None)
    m = re.search(r"```(?:python)?\n(.*?)(?:```|$)", tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True), re.S)
    return m.group(1) if m else ""

print(f"start: {passed(START)}/6 tests pass")
for run, seeds in (("run 1", (0, 1, 2, 3)), ("run 2", (10, 11, 12, 13))):
    for mode in ("keep every rewrite", "checkpoint + rollback"):
        code, best, history = START, passed(START), []
        for seed in seeds:
            new = attempt(code, seed)
            score = passed(new)
            if mode == "keep every rewrite" or score >= best:
                code, best = new, score
                history.append(f"{score}")
            else:
                history.append(f"{score}->rolled back to {best}")
        print(f"{run}, {mode:<22} tests after each attempt: {', '.join(history)};  final file passes {passed(code)}/6")

Use it: the same idea with real libraries

code/main.py implements a checkpointed workflow with idempotency, preconditions, verify, and rollback. The driver simulates four scenarios: clean run, retry after crash (idempotency catches), precondition fail (workflow aborts without firing), verify fail (rollback fires).

The whole of code/main.py follows in parts. Each part runs on this page, in order, in one Python session; the last part does what python3 code/main.py does.

Part 1 of 4 · persist_transfer, rollback_transfer, Checkpoint, key

"""Checkpointed workflow with idempotency, precondition, verify, rollback.

Simulates four scenarios:
  1. clean run
  2. retry after commit-crash  -> idempotency prevents double-execute
  3. precondition fail         -> workflow aborts without firing
  4. verify fail               -> rollback fires
"""

from __future__ import annotations

import hashlib
import json
import os
import tempfile
from dataclasses import dataclass


# ---------- Mini database ----------

DB = {"balance_A": 1500, "balance_B": 200, "last_transfer_id": None}


def persist_transfer(txid: str, from_acct: str, to_acct: str, amount: int) -> None:
    DB[f"balance_{from_acct}"] -= amount
    DB[f"balance_{to_acct}"] += amount
    DB["last_transfer_id"] = txid


def rollback_transfer(txid: str, from_acct: str, to_acct: str, amount: int,
                      prior_last_transfer_id: str | None) -> None:
    # Compensating transaction: restore balances and the prior transfer id.
    DB[f"balance_{from_acct}"] += amount
    DB[f"balance_{to_acct}"] -= amount
    DB["last_transfer_id"] = prior_last_transfer_id


# ---------- Checkpoint store ----------

@dataclass
class Checkpoint:
    path: str

    def __post_init__(self) -> None:
        if not os.path.exists(self.path):
            with open(self.path, "w") as f:
                json.dump({}, f)

    def load(self) -> dict:
        with open(self.path) as f:
            return json.load(f)

    def save(self, k: str, v: dict) -> None:
        # Atomic write: serialize to a sibling temp file, fsync, then
        # rename. If the process crashes mid-write, the original file
        # is still intact, so the next retry finds the previous
        # idempotency record rather than a truncated JSON blob.
        data = self.load()
        data[k] = v
        tmp_path = f"{self.path}.tmp"
        with open(tmp_path, "w") as f:
            json.dump(data, f)
            f.flush()
            os.fsync(f.fileno())
        os.replace(tmp_path, self.path)


# ---------- Workflow ----------

def key(txid: str) -> str:
    return hashlib.sha256(txid.encode()).hexdigest()[:12]

Part 2 of 4 · run_transfer

def run_transfer(cp: Checkpoint, txid: str, from_acct: str, to_acct: str,
                 amount: int, min_balance: int,
                 inject_crash_after_execute: bool = False,
                 inject_verify_fail: bool = False) -> str:
    k = key(txid)
    record = cp.load().get(k, {"status": "new"})

    # Idempotency across all terminal states. A retry of the same txid
    # after ANY terminal verdict — committed, verified, rolled-back,
    # aborted-precondition — must short-circuit to the original result
    # instead of re-executing.
    terminal_results = {
        "committed": "idempotent-skip",
        "verified": "ok",
        "rolled-back": "verify-fail-rolled-back",
        "aborted-precondition": "aborted-precondition",
    }
    if record["status"] in terminal_results:
        return terminal_results[record["status"]]

    # Precondition check: post-transfer balance must remain >= min_balance
    if DB[f"balance_{from_acct}"] - amount < min_balance:
        cp.save(k, {"status": "aborted-precondition", "txid": txid})
        return "aborted-precondition"

    # Capture prior state so rollback can restore exactly (not just invert).
    prior_last_transfer_id = DB["last_transfer_id"]

    # Record intent BEFORE the side effect, so a crash between the
    # save and persist_transfer leaves a "committed" marker the retry
    # can detect and short-circuit. We only promote to "verified" once
    # the post-action read (below) confirms the side effect landed.
    #
    # Subtle durability gap (lesson trade-off): if the process crashes
    # AFTER cp.save and BEFORE persist_transfer, a retry will see
    # status == "committed" and return "idempotent-skip" even though
    # the transfer never actually ran. Production systems close this
    # gap by either (a) carrying the idempotency key into the side
    # effect itself so the destination DB enforces exactly-once, or
    # (b) gating "committed" on a post-action read of the destination,
    # which is exactly what the verify step below does for the
    # non-crash path.
    cp.save(k, {"status": "committed", "txid": txid,
                "from_acct": from_acct, "to_acct": to_acct,
                "amount": amount,
                "prior_last_transfer_id": prior_last_transfer_id})
    persist_transfer(txid, from_acct, to_acct, amount)
    if inject_crash_after_execute:
        raise RuntimeError("simulated crash after execute")

    # Post-action verify
    if inject_verify_fail or DB["last_transfer_id"] != txid:
        rollback_transfer(txid, from_acct, to_acct, amount, prior_last_transfer_id)
        cp.save(k, {"status": "rolled-back", "txid": txid})
        return "verify-fail-rolled-back"

    cp.save(k, {"status": "verified", "txid": txid})
    return "ok"

    cp = Checkpoint(os.path.join(tmp, "cp2.json"))
    try:
        run_transfer(cp, "tx-002", "A", "B", 100, min_balance=200,
                     inject_crash_after_execute=True)
    except RuntimeError as e:
        print(f"  crash: {e}")
    # Retry after the crash
    out = run_transfer(cp, "tx-002", "A", "B", 100, min_balance=200)
    print(f"  retry result={out}  DB={DB}")

    print("\nScenario 3: precondition fails (balance would go below min)")
    print("-" * 80)
    cp = Checkpoint(os.path.join(tmp, "cp3.json"))
    out = run_transfer(cp, "tx-003", "A", "B", 10_000, min_balance=200)
    print(f"  result={out}  DB={DB}")

    print("\nScenario 4: verify fails -> rollback")
    print("-" * 80)
    cp = Checkpoint(os.path.join(tmp, "cp4.json"))
    balances_before = dict(DB)
    out = run_transfer(cp, "tx-004", "A", "B", 100, min_balance=200,
                       inject_verify_fail=True)
    balances_after = dict(DB)
    print(f"  result={out}  balances_before_after_equal="
          f"{balances_before == balances_after}")

    print()
    print("=" * 80)
    print("HEADLINE: idempotency + precondition + verify + rollback")
    print("-" * 80)
    print("  Four pieces, not one. Each covers a distinct failure class:")
    print("  idempotency -> retry-safe on crash")
    print("  precondition -> state drift between approval and commit")
    print("  verify       -> the side effect did not happen when we thought it did")
    print("  rollback     -> known-bad state restored or alerted")
    print("  Article 14 operational reading: checkpoints queryable, rollbacks")
    print("  rehearsed, audit trail survives deploys.")

Industry practice
What's current (2024–2026)
  • Graph frameworks checkpoint every step. LangGraph saves state after each super-step through a checkpointer (Postgres in production) and can resume or replay from any checkpoint in a thread.
  • Coding agents checkpoint files. Claude Code saves file snapshots before each prompt, and /rewind (or Esc twice) restores code, conversation or both. Its documented limits: changes made only by shell commands, most subagent edits and external edits are not tracked, so Git is still the real history.
  • Workflow engines retry for you. Temporal and Cloudflare Workflows retry failed steps automatically, which is why both ask for steps that are safe to repeat. Stripe-style idempotency keys on the receiving API are what make a repeated call harmless.
  • On your laptop: commit to Git before letting an agent loose, and use git stash or a branch per attempt. It is the same checkpoint-and-rollback as this lesson, and it works for any agent.

Sources: Claude Code, Checkpointing, LangGraph, Persistence, Stripe, Idempotent requests, EU AI Act, Article 12.

Recap
What to keep from this lesson
  • Status-first loses actions on a crash; effect-first repeats them. Neither is exactly once.
  • Write an in-flight record, act with the transaction id, and on resume ask the system of record whether it happened.
  • Verify on the action's own key, not a shared field another workflow can overwrite.
  • A rollback is an action too: name its type, check its precondition, and rehearse it.
  • Checkpoint before every risky agent step and restore on regression; the agent's own retries do not converge.

Given a proposed long-horizon autonomous workflow, design a rollback-rehearsal test that proves the idempotency + precondition + verify + rollback stack actually works end-to-end, and audit the checkpoint backend for regulator-readiness.

Produce:

1. **Rehearsal script.** Concrete test that (a) starts the workflow, (b) crashes it mid-commit, (c) resumes, (d) asserts the action fires exactly once, (e) injects a verify failure, (f) asserts the rollback fires and state is restored. No production workflow should run without this test having passed at least once.
2. **Idempotency audit.** Confirm the idempotency key is derived from proposal content (Lesson 15) and commit logic uses explicit execution states (`pending` -> `executing` -> `committed`/`failed`). Reserve/lock by idempotency key before the side effect, and mark `committed` only after the side effect has been verified.
3. **Precondition inventory.** List every precondition the workflow must re-check at commit time. Time-of-check vs time-of-use gaps are the most common production bug; the precondition must be evaluated at commit, not at propose.
4. **Verify inventory.** For every consequential action, name the specific read that confirms the side effect happened. "Returned 200" is not acceptable.
5. **Rollback inventory.** For every consequential action, classify the rollback as in-band, compensating transaction, or out-of-band alert. No-op rollbacks ("we cannot undo this") must be named explicitly in the proposal (Lesson 15 metadata).

Hard rejects:
- Workflows with no rehearsed rollback.
- Checkpoint backends that lose data on deploy.
- Commit paths where status is written after execution, not before.
- "Verified" states that only check the return code of the tool call.
- Precondition checks that run only at propose time, not commit time.

Refusal rules:
- If the user has not run the rehearsal script at least once in staging, refuse production rollout.
- If the user cannot produce the checkpoint store schema, refuse and require schema documentation first. Regulators want queryable state.
- If the workflow depends on an in-memory checkpoint (no persistence), refuse.

Output format:

Return a rehearsal plan with:
- **Test script outline** (steps with assertions)
- **Idempotency table** (key composition, status-write order)
- **Precondition table** (check, when evaluated, consequence)
- **Verify table** (action, read that confirms)
- **Rollback table** (action, type, target state)
- **Backend attestation** (store, survives-deploy y/n, query-ready y/n)
- **Readiness** (production / staging / research-only)

Solutions

SolutionP1 · The money never moves; a good transfer is rolled back

The money does not move. The record says "committed", so the retry returns "skipped (already committed)" and the transfer never happens. Writing the status first makes a retry safe from doubling, but a crash in the gap loses the action.

With a concurrent transfer between the move and the verify, the lesson's verify fails, because last_transfer_id now holds the other transfer's id. run_transfer() then rolls back a transfer that succeeded and sets last_transfer_id to the old value. Verify on the transfer's own record, such as a ledger entry keyed by its id.

SolutionB1 · Three hundred invoices marked sent

The checkpoint said "sent" before the email API was called. The deploy restarted workers between the two steps, and on restart each invoice was skipped because its record already said sent. The dashboard reads the checkpoint, not the email provider, so it showed every invoice as sent.

The fix: - Write "sending" (in-flight), call the email API with the invoice id as its idempotency key, and mark "sent" only after you confirm with the provider. - On resume, ask the provider whether the message for that invoice exists, and send only if it does not. - Point the dashboard at the provider's delivery records, or at a verified status, rather than at the agent's own intent. - Reconcile now: compare the 300 invoices against the provider's sent log and resend the missing ones with their idempotency keys.
