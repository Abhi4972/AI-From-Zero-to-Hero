The problem

In plain words first

SRE (site reliability engineering) is the work of keeping services up: alerts, on-call, incident response, post-mortems. Much of the first half-hour of an incident is searching: grouping error logs, checking metrics, looking at recent deploys and finding the runbook that matches. AI SRE gives that search to agents. A supervisor agent splits the incident into questions, specialist agents query logs, metrics and runbooks with their own tools, and the supervisor presents ranked hypotheses with evidence to the human on call. Agents may also act, but only inside a narrow, pre-approved set (restart a pod, revert a deploy, scale within limits). Anything broader stays with people. Two models analysing the same incident independently, and escalating when they disagree, is a cheap way to catch confident mistakes.

An on-call engineer gets paged at 3 a.m. "High error rate in checkout." They check Datadog, Loki, three runbooks, the deploy log. 30 minutes later they realize the root cause is a vLLM OOM from a KV cache spike. They restart the pod; error clears.

In 2026 the first 20 minutes of that investigation are automatable. Grouping logs by service, correlating to recent deploys, matching against runbooks — all are RAG + tool-use. A supervised agent can do first-pass triage and present a hypothesis before the human opens Datadog.

Fully autonomous remediation is a different problem. Restart pod: safe. Scale GPU pool: safe if policy allows. Re-architect the service: absolutely not. The discipline is drawing the narrow line.

Supervisor breaks the incident into sub-queries. Specialized agents have tool access (log search, PromQL, doc retrieval). Supervisor synthesizes, presents hypothesis + evidence to human. Human approves or redirects.

Idea 2 · Auto-remediation scope

Safe (narrow): restart pod, revert specific deploy, scale pool within pre-approved bounds, enable pre-approved feature flag.

Not safe (broad): change service topology, modify resource limits, deploy new code, change IAM, alter databases.

Anyone selling "set it and forget it" is overselling. The safe set grows as AI SRE matures, but the boundary is real.

Idea 3 · Adversarial evaluation (NeuBird Hawkeye)

Two models independently analyze the same incident. If they agree on root cause, confidence is high. If they disagree, escalate to human with both hypotheses visible. Simple pattern, effective filter against hallucinated root causes.

Idea 4 · Operational memory

Team turnover is the silent kill of traditional SRE — tribal knowledge leaves. AI SRE stores runbooks + post-mortems in a vector DB; agents retrieve on every new incident. When new engineers join, the AI has full history.

Idea 5 · Pre-incident prediction

MIT 2025 research: LLM trained on historical logs, GPU temperatures, API error patterns predicted 89% of outages 10-15 minutes before they happened on the test set.

Reality check: predictions without actuation are dashboards. The operational question is "when we predict, what do we do?" Pre-emptive drain? Pager? Auto-scale? The answer is policy-specific.

Idea 7 · Runbooks as code

Runbooks evolve from Confluence pages to versioned markdown with structured sections (symptom, hypothesis, verify, act). Structured runbooks feed better RAG retrieval. Start any AI-SRE rollout by turning unstructured runbooks into structured.

Idea 8 · Numbers you should remember

  • MIT early-detection: 89% of outages, 10-15 min lead time.
  • Multi-agent triage: supervisor + (logs, metrics, runbooks) + human.
  • Safe auto-remediation set: restart pod, revert deploy, scale within bounds.
  • Adversarial eval: two models independent; agreement = confidence.

Worked example
Turning a runbook into something agents can use

A Confluence page says "If checkout errors spike, it's usually the GPU box running out of memory; restart it and maybe lower the memory setting."

  1. Symptom: error rate on /checkout/generate-summary above 2% for 3 minutes, log pattern kv_cache_allocation_failed.
  2. Hypothesis: vLLM KV cache out of memory under burst concurrency.
  3. Verify: DCGM_FI_DEV_FB_USED at or above 97% in the 5 minutes before onset; preemption counter rising.
  4. Act (pre-approved): restart the affected pod; set --gpu-memory-utilization to 0.85. Escalate if errors persist 10 minutes after.

Each field is now something an agent can retrieve, test with a tool and report on, and the action is narrow enough to allow without a human.

Which statements are right?

  • ✓ Restarting a pod within pre-approved bounds is a reasonable automatic action.
  • ✗ An AI SRE agent should be allowed to change IAM roles to fix access errors. Broad changes stay with humans; the safe action set is narrow.
  • ✓ Two independent analyses that agree are more trustworthy than one confident one.
  • ✗ Predicting an outage is useful on its own. A prediction needs a policy that says what happens next: drain, page or scale.
Predict before you run

Two models each name the right root cause 80% of the time, independently, and when wrong they pick one of five wrong causes at random. Before running the code below: when they agree, how often are they right?

See it drawn
Agreement as a confidence filter
import random
random.seed(9)
def diagnose():
    return "right" if random.random() < 0.8 else f"wrong{random.randrange(5)}"
agree = agree_right = 0
N = 100_000
for _ in range(N):
    a, b = diagnose(), diagnose()
    if a == b:
        agree += 1
        agree_right += a == "right"
print(f"they agree on {agree / N:.1%} of incidents; when they agree they are right {agree_right / agree:.1%} of the time")
print(f"a single model is right 80.0% of the time; the rest ({1 - agree / N:.1%}) go to a human")
What you should see
they agree on 64.9% of incidents; when they agree they are right 98.8% of the time
a single model is right 80.0% of the time; the rest (35.1%) go to a human
Reading this output

When the two agree, they are right about 99% of the time, against 80% for one model alone; the price is that about a third of incidents go to a human because they disagree. Agreement is a strong filter only if the models' errors are independent; two copies of the same model reading the same logs will make the same mistakes.

Part 1 of 3 · AgentHypothesis, log_agent, metric_agent, runbook_agent

"""Multi-agent AI SRE triage simulator — stdlib Python.

Three specialized agents produce hypotheses; supervisor ranks by agreement.
Adversarial evaluation: disagreement escalates to human.
"""

from __future__ import annotations

from dataclasses import dataclass


@dataclass
class AgentHypothesis:
    agent: str
    root_cause: str
    confidence: float
    evidence: list[str]


def log_agent(incident: str) -> AgentHypothesis:
    # simulated: scans logs, picks most common error token
    if "checkout" in incident.lower():
        return AgentHypothesis(
            "LogAgent",
            "vLLM OOM from KV cache spike on /api/llm",
            0.78,
            ["frequency: 142 errors/min", "pattern: 'kv_cache_allocation_failed'", "node: pod-gpu-3"],
        )
    return AgentHypothesis("LogAgent", "unclear", 0.35, ["logs show no obvious pattern"])


def metric_agent(incident: str) -> AgentHypothesis:
    # simulated: PromQL query matches to known patterns
    return AgentHypothesis(
        "MetricAgent",
        "GPU memory utilization hit 98% 4 minutes before error spike",
        0.82,
        ["DCGM_FI_DEV_FB_USED >= 97% for 240s", "correlation with error onset: 0.93"],
    )


def runbook_agent(incident: str) -> AgentHypothesis:
    # simulated: vector search on runbook repo
    return AgentHypothesis(
        "RunbookAgent",
        "Matches runbook RB-017: KV cache OOM under burst concurrency",
        0.88,
        ["runbook: RB-017", "last applied: 2026-01-14", "safe action: restart pod + lower --gpu-memory-utilization to 0.85"],
    )

Part 2 of 3 · supervisor, main

def supervisor(hypotheses: list[AgentHypothesis]) -> dict:
    # group similar root causes; agreement = confidence boost
    root_causes = {}
    for h in hypotheses:
        key = h.root_cause.split(" on ")[0].split(" hit ")[0][:30]
        root_causes.setdefault(key, []).append(h)

    ranked = sorted(root_causes.items(), key=lambda kv: -sum(h.confidence for h in kv[1]))
    top_key, top_agents = ranked[0]
    adversarial_agreement = len(top_agents) >= 2
    action = "restart pod + lower --gpu-memory-utilization"  # safe action

    return {
        "top_root_cause": top_key,
        "supporting_agents": [h.agent for h in top_agents],
        "aggregated_confidence": sum(h.confidence for h in top_agents) / len(top_agents),
        "adversarial_agreement": adversarial_agreement,
        "proposed_action": action,
        "safety_gate": "human approval required" if not adversarial_agreement else "safe action auto-approved",
    }


def main() -> None:
    print("=" * 80)
    print("AI SRE TRIAGE: multi-agent investigation of a production incident")
    print("=" * 80)
    incident = "High error rate in /checkout/generate-summary, last 6 min"
    print(f"\nIncident: {incident}\n")

    hypotheses = [log_agent(incident), metric_agent(incident), runbook_agent(incident)]
    for h in hypotheses:
        print(f"[{h.agent}] confidence={h.confidence:.2f}")
        print(f"  root cause: {h.root_cause}")
        for e in h.evidence:
            print(f"  - {e}")
        print()

    decision = supervisor(hypotheses)
    print("-" * 80)
    print("SUPERVISOR")
    print("-" * 80)
    for k, v in decision.items():
        print(f"  {k}: {v}")

    print("\nNote: the supervisor only proposes narrow safe actions.")
    print("Broad changes (topology, code, IAM) always escalate to a human commander.")

Recap
What to keep from this lesson
  • Agents automate the search part of an incident: logs, metrics, deploys, runbooks.
  • Supervisor plus specialist agents; a human approves anything beyond a narrow action set.

Solutions

SolutionB1 · Confidence is not permission

The missing rule is an action allow-list: what an agent may do must be fixed in advance, independent of how confident it is. Changing connection limits across services is a broad, cross-system change and should have been proposed to a human with its evidence, not executed. Confidence decides whether to escalate, not what is permitted.

Weigh a trade-offA vendor demo shows an operations agent that repairs incidents on its own. Your director asks which actions you would let such an agent take on the model service without a person in the loop. Draw the line and defend it.

Level 3 of 4 · about 12 minutes to answer well.

Short answer. Allow a narrow set that was approved in advance: restart a pod, revert one named deployment, scale a pool inside approved bounds, and flip an approved feature flag. Keep everything that changes the shape of the system behind a person: topology, resource limits, new code, access rights and databases. The agent proposes, a person approves the judgment calls, and the safe set grows only as the agent builds a record.

The two sets.

Safe, automated Not safe, human only
restart a pod change the service topology
revert one specific deployment modify resource limits
scale a pool within pre-approved bounds deploy new code
enable a pre-approved feature flag change access rights
alter a database

What makes an action safe.

It is reversible, its blast radius is bounded in advance, and it matches a step in a runbook that a person wrote. The lesson's example incident is a KV cache spike that pushed a serving engine out of memory. A pod restart clears it, and a restart is on the safe list. Raising the memory limit might also clear it, and that change alters how every pod runs from then on, so it stays with a person.

How an action earns automation.

  1. Write the runbook in structured form: symptom, hypothesis, verify, act.
  2. Give the action a success criterion and a verify step that runs after it.
  3. Record every proposal and every human decision.
  4. Promote the action from proposed to automatic after a run of incidents where the proposal matched what the person chose.

The approval gate stays.

The architecture is a supervisor over log, metric and runbook agents, a hypothesis with evidence, a human approval, and then an action from the narrow set. Even when two independent models agree on the cause, the approval stays for anything outside the safe set. The lesson is direct about vendors who sell a system that needs no supervision: they are overselling.

Plausible wrong answers.

  • "If the agent is accurate enough, let it do everything." Accuracy on past incidents does not bound the damage of one wrong broad action.
  • "No automation until the agent is perfect." A restart and a revert are safe today, and they remove the first part of most investigations.
  • "An approval step makes the agent useless at night." The agent still does the investigation. The person approves one proposed action instead of starting from the dashboards.

Follow-ups an interviewer may ask.

  • (level 3) Why is a scale-up inside bounds safe while a resource limit change is not? Expected: the bounds were approved in advance and the action reverses cleanly. A limit change alters how every pod runs and can trigger the next incident.
  • (level 3) What has to be true before the agent may run an action unsupervised? Expected: a structured runbook, a verify step with a success criterion, an audit record, and a record of proposals that matched the human decision.
  • (level 4) The agent restarted the busiest pod during a load spike because a probe failed. Was that inside the rules? Expected: the action was allowed and the trigger was wrong. A restart under load drops the running requests, so the rule needs a condition on load and on the probe type, not only on the action.

Defend a designA model trained on your logs, GPU temperatures and error patterns predicts most outages ten to fifteen minutes before they happen. The team wants to ship it as a dashboard panel. Design what the system does with a prediction, and defend the design.

Level 4 of 4 · about 15 minutes to answer well.

Short answer. A prediction with no action is a dashboard, and nobody watches a dashboard at three in the morning. Write a policy per prediction class: page the on-call, drain the suspect node or pool before it fails, or scale within approved bounds, and record every prediction with its outcome. Start with the page, measure the precision on live incidents, and promote a class to an automatic drain only when its false alarm rate is acceptable and a person has approved that drain as a pre-approved action in the runbook.

The result and its limit.

The lesson cites a research result: a model trained on past log lines, GPU temperature readings and API error patterns predicted 89 percent of outages 10 to 15 minutes early on its test set. The lesson's reality check follows at once. Predictions without actuation are dashboards. The operational question is what you do when the prediction fires.

The design.

  1. Classify the prediction. Which failure is coming: a memory exhaustion, a thermal slowdown, a provider error burst. Attach the confidence.
  2. Map each class to an action. The lesson's safe set is narrow: restart a pod, revert a deploy, scale within pre-approved bounds. A drain is not on that list, so it needs approval before it runs on its own. Drain the pod from the load balancer and restart it before it falls over. Scale the pool within approved bounds. Page a person with the prediction and the evidence.
  3. Fit the action into the lead time. A drain plus a replacement must complete inside the ten to fifteen minutes, so the replacement has to be warm already. A cold start of a large model takes minutes and can eat the whole window.
  4. Record outcomes. Every prediction, its class, the action taken and whether the outage happened. Precision and recall per class come from this log, not from the paper.
  5. Guard the blast radius. Never run two automatic drains in the same pool at once, and never drain under a load spike without a warm spare.

Why page first.

A page costs sleep. A false drain costs capacity for the drain time. A false scale-up costs money. Until the precision per class is measured in production, the cheapest wrong action is the page. Promote a class to automatic action when its record justifies it, the same ladder the lesson uses for remediation.

Plausible wrong answers.

  • "Ship the panel and let on-call decide." At night nobody watches a panel. The lesson's point is that a prediction without an action is a dashboard.
  • "Automate the drain for every prediction from day one." A false alarm then costs capacity, and nothing has measured the false alarm rate on your traffic.
  • "The research number means we will prevent most outages." The number was on a test set. Your precision in production is unknown until you measure it.

Follow-ups an interviewer may ask.

  • (level 3) What does a false alarm cost under each policy? Expected: a page costs sleep, a drain costs capacity for the drain time, and a scale-up costs money. Pick the policy per class from that cost against the cost of the outage.
  • (level 4) The lead time is ten minutes and a replacement replica takes longer to warm. What changes? Expected: keep a warm spare or act earlier on a weaker signal. A drain with no warm replacement moves the outage instead of preventing it.
  • (level 4) How do you know the predictor still works after the service changes? Expected: track precision and recall per class on live incidents, and retrain when the input distribution shifts.

Explain the mechanismAn incident triage agent proposes a root cause for every alert. The on-call team stopped trusting it after several confident wrong answers. Which pattern from the SRE lesson raises the trust in its output, and what does the team do when the pattern says the agent is unsure?

Level 2 of 4 · about 8 minutes to answer well.

Short answer. Run two models independently on the same incident. When they agree on the root cause, confidence is high. When they disagree, the system escalates to a person with both hypotheses and their evidence visible, instead of picking one. The pattern filters invented root causes at a low cost, and the disagreement itself tells the responder that the incident is uncertain.

Adversarial evaluation.

The lesson names the pattern after a product that ships it: two models analyze the same incident on their own. Agreement is confidence. Disagreement is an escalation with both hypotheses shown. It is simple, and it is an effective filter against a confident wrong answer, because two independent analyses rarely invent the same cause.

Where it sits in the architecture.

A supervisor splits the incident into sub-queries. Specialized agents with tool access search the logs, run the metric queries and retrieve the runbooks. The supervisor assembles a hypothesis with evidence and shows it to a person, who approves or redirects. Only then does an action run, and only from a narrow approved set. The two-model check sits at the hypothesis step, before the person sees it.

What the person does on a disagreement.

Reads both hypotheses and the evidence that each one cites. Picks one, redirects the agents, or starts the manual investigation with two leads instead of none. The lesson's division of labor holds: the agent proposes hypotheses and queries, and the person makes the judgment call.

What the agents remember.

Runbooks and postmortems live in a vector store, and both models retrieve from it on every incident. Operational memory survives team turnover, and a new engineer's first incident has the full history behind it.

The limit of agreement.

Two models that share training data can agree and be wrong together. Agreement raises confidence, it is not proof. Require every hypothesis to cite the log lines and the metric queries behind it, so that the responder can check the evidence and not the eloquence.

Plausible wrong answers.

  • "Ask one model twice at temperature zero." A repeat of the same model shares its blind spots. The pattern needs independent analyses.
  • "Let an agreed hypothesis trigger the fix on its own." Agreement raises confidence. The person still approves the action, and only narrow actions are automated at all.
  • "Disagreement proves the agent is useless." It means the incident is uncertain, which is exactly when a person should look.

Follow-ups an interviewer may ask.

  • (level 2) Why is a split verdict useful to the responder? Expected: it marks the incident as uncertain and gives the responder two candidate causes with their evidence.
  • (level 3) Both models agree and both are wrong. How do you catch it? Expected: require each hypothesis to cite evidence that the responder can check, and keep the human approval before any action.
  • (level 3) What does the pattern cost? Expected: two model runs per incident plus the latency of the slower one, which is small next to the first twenty minutes of a manual investigation that the lesson says are automatable.
