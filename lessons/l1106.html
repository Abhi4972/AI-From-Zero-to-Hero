Why this came about

From 2018 to 2020, fine-tuning was how everything was done: you took BERT (Lesson 7.13), added a small output layer, and trained it on a few thousand labelled examples for each task. Then GPT-3 and its successors showed that one large model could do many tasks from a prompt alone, and for a few years most teams stopped training models. Fine-tuning came back from 2023 for three reasons. LoRAlater · 3.24 made it cheap enough to run on one consumer GPU (Lesson 3.24). Capable open-weight models (Llama, Mistral, Qwen, Gemma, Phi) gave everyone something worth tuning. And teams running millions of calls a day found that a small tuned model could match a large general one on a narrow step at a fraction of the cost and delay. Today most teams still do not fine-tune, and those that do reserve it for specific, high-volume, well-measured steps. This workshop teaches you to recognise those steps and to do the work properly.

In plain words first
Briefing a generalist, or training a specialist

A prompt is a briefing: you explain the job to a capable generalist every single time, and they do their best from the note. Fine-tuning is training: the model practises on hundreds of worked examples until the job becomes habit, so the note can be one line. A specialist is faster and cheaper per task and very consistent, but took effort to train, knows only that job, and has to be retrained when the job changes. Most problems need a better briefing or better reference material, not a specialist. This lesson is about telling the difference, and then preparing the practice material: the dataset.

Step 1 · Is fine-tuning the right tool?

Fine-tuning continues a model's training on your examples, so its weights change (Lesson 10.10 did exactly this to turn a text predictor into an assistant). That makes it good at some things and wrong for others:

What you want Does fine-tuning help? What to use
A fixed output format, followed every time Yes, very well A prompt with examples first; fine-tune if it still drifts, or to make a small model do it
A house style or tone Yes Examples in the prompt first
A narrow task done by a small, cheap, fast model Yes: this is the main production use Fine-tune, often on answers produced by a large model (distillationlater · 14.139, Lesson 14.139)
Reliable tool calling by a small or self-hosted model Yes Fine-tune on tool-call transcripts
Knowledge of your documents, prices or policies No: facts in weights go stale and cannot be cited Retrieval (the Retrieval (RAG) section)
Knowledge of today's order status No Tools (the Agents from first principles section)
General intelligence, better reasoning No: a tuned model is narrower, not smarter A stronger base model

Three questions decide whether a fine-tune is worth starting:

  1. Can you measure success? If you cannot write a program or a rubric that scores an answer, you cannot tell whether training helped.
  2. Have you measured the cheaper options? A good prompt with examples, on the best model you can afford. That number is your baseline.
  3. Is the volume or the constraint real? Fine-tuning pays for itself on steps that run very often, must be very fast, must run on your own hardware, or must be more consistent than a prompt achieves.
Tip
A useful one-line test

Prompting and retrieval change what the model reads. Fine-tuning changes how the model behaves. If the problem is missing information, give it information. If the problem is behaviour that examples in the prompt cannot fix, or cannot fix cheaply enough, fine-tune.

Step 2 · The project, and a task you can score

The workshop follows this loop over five lessons, with one running example from ShopKart, the online shop used throughout the course. Support tickets arrive as free text. Before any agent or person handles a ticket, a router must read it and produce three facts:

  • the intent: refund, order_status, cancel, exchange or other;
  • the order number, if the customer gave one;
  • whether the ticket is urgent.

The router runs on every ticket, so it must be cheap and fast, and other programs read its output, so it must be exact JSON. That is a typical fine-tuning candidate: narrow, high volume, strict format. The target looks like this:

ticket:  Stop the shipment of SK-63086, I do not want the kettle any more asap please
answer:  {"intent": "cancel", "order_id": "SK-63086", "urgent": true}

Because the answer is structured, a program can score it field by field. That scoring function is the metric, and writing it is the first real step of the project.

Step 3 · Build the dataset

Real projects get examples from logs, from people who label them, or from a large model (Step 8). To keep the workshop self-contained and repeatable, this one generates its tickets from templates: ten ways of phrasing each intent, with products, cities, order numbers and urgency filled in at random. Save this file as ft_data.py in your project folder; the next four lessons import it.

# save as: ft_data.py
import json, random

SYSTEM = "You are ShopKart's ticket router. Reply with one JSON object and nothing else."
PRODUCTS = ["mixer", "kettle", "headphones", "yoga mat", "pressure cooker", "backpack", "desk lamp", "water bottle",
            "phone case", "pair of running shoes", "toaster", "bedsheet"]
CITIES = ["Jaipur", "Pune", "Kochi", "Lucknow", "Indore", "Nagpur", "Surat", "Patna", "Mysuru", "Guwahati", "Noida", "Bhopal"]
URGENT = ["urgent!", "asap please", "I need this sorted today", "this is very urgent", "please hurry", "immediately"]
CALM = ["", "thanks", "thank you", "whenever you can", "no rush", ""]

# Ten ways of saying each intent. {p} is a product, {c} a city, {o} an order number (sometimes missing).
# The first eight are available for training; the last two are kept back for the final test.
TEMPLATES = {
    "refund": ["My {p} from order {o} arrived broken, I want my money back", "I'd like a refund for the {p} {o}",
               "the {p} stopped working after two days, refund please {o}", "Refund request for {o}: the {p} is damaged",
               "{o} poor quality {p}, I am returning it, give me my money back", "can I get my money back for the {p}? {o}",
               "Please refund {o}. The {p} was faulty on arrival", "I was charged twice for the {p} {o}, refund one payment",
               "the {p} is defective and I want to be reimbursed {o}", "{o} return the payment for this useless {p}"],
    "order_status": ["Where is my {p}? order {o}", "{o} has not arrived yet, any update on the {p}?",
                     "When will the {p} be delivered? {o}", "tracking shows nothing for {o} ({p})",
                     "Has my {p} shipped yet {o}", "It's been a week, where is order {o} with my {p}",
                     "is the {p} out for delivery today? {o}", "any news on {o}? still waiting for the {p}",
                     "delivery status of {o} please, it's the {p}", "how long until the {p} gets here {o}"],
    "cancel": ["Please cancel order {o}, I no longer need the {p}", "cancel {o}", "I ordered the {p} by mistake, cancel it {o}",
               "Stop the shipment of {o}, I do not want the {p} any more", "need to cancel my {p} order {o}",
               "Don't ship {o}. Cancel the {p}", "I changed my mind about the {p}, please cancel {o}",
               "how do I cancel {o}? it's the {p}", "call off order {o}, the {p} is not needed now",
               "{o} drop this order before it ships, no {p} for me"],
    "exchange": ["The {p} is the wrong size, can I exchange it? {o}", "I received a blue {p} instead of black, please swap it {o}",
                 "exchange the {p} from {o} for a different colour", "want to replace the {p} with a bigger one {o}",
                 "{o}: you sent the wrong model of {p}, send the right one", "Can I swap the {p} for another variant? {o}",
                 "the {p} doesn't fit, I'd like a different size {o}", "please exchange {o}, the {p} colour is not what I chose",
                 "need a replacement {p} in another size, same order {o}", "{o} trade this {p} for the smaller version"],
    "other": ["Do you deliver to {c}?", "What are your customer care hours in {c}?", "how do I change the password for my account, I live in {c}",
              "Do you have a loyalty programme for shoppers in {c}?", "Is cash on delivery available for the {p}?",
              "I want to update my delivery address to {c}", "Do you sell gift cards for a {p}?", "what is the warranty on the {p}?",
              "can I pay for the {p} in instalments?", "is there a ShopKart store in {c} where I can see the {p}"],
}
INTENTS = list(TEMPLATES)

def make_example(rng, intent, template):
    """One ticket and the JSON a perfect router would return for it."""
    has_order = "{o}" in template and rng.random() > 0.15            # some customers forget the order number
    order_id = f"SK-{rng.randint(10000, 99999)}" if has_order else None
    urgent = rng.random() < 0.3
    text = template.format(p=rng.choice(PRODUCTS), c=rng.choice(CITIES), o=order_id or "").replace("  ", " ").replace(" :", ":").strip(" :")
    text = (text + " " + rng.choice(URGENT if urgent else CALM)).strip()
    return {"text": text, "label": {"intent": intent, "order_id": order_id, "urgent": urgent}}

def build(seed=0, n_train=320, n_val=40, n_test=40, phrasings=4, dedupe=True):
    """Train and validation draw on the first `phrasings` templates of each intent; test uses the two never used for training."""
    rng = random.Random(seed)
    seen = set()
    def sample(n, lo, hi):
        rows = []
        while len(rows) < n:
            intent = INTENTS[len(rows) % 5]
            row = make_example(rng, intent, rng.choice(TEMPLATES[intent][lo:hi]))
            if dedupe and row["text"] in seen:               # never let the same ticket into two splits, or twice into one
                continue
            seen.add(row["text"]); rows.append(row)
        rng.shuffle(rows)
        return rows
    return sample(n_train, 0, phrasings), sample(n_val, 0, phrasings), sample(n_test, 8, 10)

def to_messages(row, with_answer=True):
    """The chat format every fine-tuning tool expects: a list of role/content messages."""
    msgs = [{"role": "system", "content": SYSTEM}, {"role": "user", "content": row["text"]}]
    if with_answer:
        msgs.append({"role": "assistant", "content": json.dumps(row["label"])})
    return msgs

def score(reply, label):
    """Compare one model reply with the right answer, field by field. 1 = right, 0 = wrong."""
    try:
        pred = json.loads(reply.strip())
        assert isinstance(pred, dict)
    except Exception:
        return {"valid_json": 0, "intent": 0, "order_id": 0, "urgent": 0, "all_correct": 0}
    s = {"valid_json": 1, "intent": int(pred.get("intent") == label["intent"]),
         "order_id": int(pred.get("order_id") == label["order_id"]), "urgent": int(pred.get("urgent") is label["urgent"])}
    s["all_correct"] = int(s["intent"] and s["order_id"] and s["urgent"])
    return s
Reading this output
Reading this code
  • TEMPLATES holds ten phrasings per intent. build trains on the first phrasings of them (four by default) and builds the test set from the last two, which training never sees.
  • make_example returns the ticket text and its label, the answer a perfect router would give. About one ticket in seven has no order number, so the model must learn to answer null instead of inventing one.
  • to_messages wraps a ticket in the chat format: a list of messages with a role (system, user, assistant) and content (Lesson 11.1). The assistant message holds the label as JSON text, because a language model produces text.
  • score is the metric: it parses the model's reply as JSON and compares each field with the label. all_correct is 1 only when all three fields match. A reply that is not valid JSON scores 0 everywhere.

Step 4 · Three sets, and checking for leaks

The three sets have different jobs (Lesson 2.16 introduced them):

  • The training set is what the model learns from.
  • The validation set is watched during training to decide when to stop and which settings are better. It uses the same phrasings as training but different tickets.
  • The test set is used once, at the end, to report how good the model is. Here it uses phrasings that never appear in training, because real customers will not phrase things the way your training data did.

Check the balance of the data, and check that no ticket appears in two sets:

The classes are balanced (64 tickets each), about two thirds of tickets carry an order number, and under a third are urgent. The last line shows why build checks for duplicates. Without the check, some tickets are generated twice, and a few validation tickets are exact copies of training tickets. That is leakage: the model would be "tested" on examples it has memorised, and its score would look better than it is. With real data, leakage is usually subtler (the same customer, the same conversation split across sets, near-duplicates that differ by a space), and it is the most common reason a fine-tuned model does well in evaluation and badly in production.

Step 5 · The file format every tool accepts

Fine-tuning tools and services read JSONL files: one JSON object per line, each with a messages list. Write the three sets to disk:

for name, rows in [("train", train_rows), ("val", val_rows), ("test", test_rows)]:
    with open(f"shopkart_{name}.jsonl", "w") as f:
        for row in rows:
            f.write(json.dumps({"messages": to_messages(row)}) + "\n")
print(open("shopkart_train.jsonl").readline())
What you should see
{"messages": [{"role": "system", "content": "You are ShopKart's ticket router. Reply with one JSON object and nothing else."}, {"role": "user", "content": "Do you have a loyalty programme for shoppers in Mysuru? thank you"}, {"role": "assistant", "content": "{\"intent\": \"other\", \"order_id\": null, \"urgent\": false}"}]}

Each line is one complete conversation ending in the assistant's ideal reply. This is the format used by OpenAI's fine-tuning API, Amazon Bedrock, Vertex AI, Hugging Face TRL, Unsloth and Axolotl. Two older formats still appear in public datasets and tutorials: Alpaca (instruction, input, output fields) and ShareGPT (conversations with from and value). Both carry the same information and convert to messages in a few lines.

Watch out
The format is part of the data

Every example here starts with the same system message and is written in the model's chat template. The model will learn to be a router for inputs that look like this. In production you must build the prompt in exactly the same way: the same template, the same system message, the same roles. Lesson 14.137 measures what happens when the format at serving time differs from training.

Step 6 · The baseline: no training, no examples

Before training, measure what the untrained model does. The model is SmolLM2-135M-Instruct: 135 million parameters, small enough to train on a laptop's processor in a few minutes, and already instruction-tuned so it understands the chat format. Save this second helper file as ft_model.py; it loads the model and holds the functions the whole workshop shares. Lesson 3.23 explains encode, make_batch and train line by line; for now you need load, reply and evaluate.

# save as: ft_model.py
import json, random, time, torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from ft_data import to_messages, score

BASE = "HuggingFaceTB/SmolLM2-135M-Instruct"      # 135 million parameters, about 270 MB, runs on a laptop CPU
torch.set_num_threads(2)                          # the same speed on every machine that checks this course; raise it on yours
tok = AutoTokenizer.from_pretrained(BASE)

def load(path=BASE):
    """Load a model as ordinary 32-bit numbers, which every processor handles well."""
    return AutoModelForCausalLM.from_pretrained(path, dtype=torch.float32)

def count_tokens(messages):
    """How many tokens the model reads for these messages, including the chat template's markers."""
    text = tok.apply_chat_template(messages, add_generation_prompt=True, tokenize=False)
    return len(tok(text, add_special_tokens=False)["input_ids"])

def reply(model, messages, max_new_tokens=40):
    """Generate the assistant's answer to a list of chat messages, greedily (no randomness)."""
    enc = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt", return_dict=True)
    with torch.no_grad():
        out = model.generate(**enc, max_new_tokens=max_new_tokens, do_sample=False, pad_token_id=tok.pad_token_id)
    return tok.decode(out[0, enc["input_ids"].shape[1]:], skip_special_tokens=True)

def evaluate(model, rows, messages_fn=lambda row: to_messages(row, with_answer=False)):
    """Average each score over a list of rows. Returns fractions between 0 and 1."""
    model.eval()
    totals = {}
    for row in rows:
        for k, v in score(reply(model, messages_fn(row)), row["label"]).items():
            totals[k] = totals.get(k, 0) + v
    return {k: round(v / len(rows), 3) for k, v in totals.items()}

def encode(row):
    """Token ids for prompt + answer, and labels that are -100 (ignored by the loss) everywhere except the answer."""
    prompt = tok.apply_chat_template(to_messages(row, with_answer=False), add_generation_prompt=True, tokenize=False)
    p = tok(prompt, add_special_tokens=False)["input_ids"]
    a = tok(json.dumps(row["label"]) + "<|im_end|>", add_special_tokens=False)["input_ids"]
    return p + a, [-100] * len(p) + a

def make_batch(rows):
    """Pad a list of rows to the same length. Returns input ids, attention mask and labels as tensors."""
    enc = [encode(r) for r in rows]
    width = max(len(ids) for ids, _ in enc)
    ids = torch.full((len(enc), width), tok.pad_token_id)
    labels = torch.full((len(enc), width), -100)
    mask = torch.zeros((len(enc), width), dtype=torch.long)
    for k, (i, l) in enumerate(enc):
        ids[k, :len(i)] = torch.tensor(i); labels[k, :len(l)] = torch.tensor(l); mask[k, :len(i)] = 1
    return ids, mask, labels

def train(model, rows, steps=80, lr=5e-5, batch_size=8, seed=0, log_every=20, val_rows=None):
    """A plain training loop: sample a batch, compute the loss on the answer tokens, step the optimiser."""
    params = [p for p in model.parameters() if p.requires_grad]
    opt = torch.optim.AdamW(params, lr=lr)
    rng = random.Random(seed)
    history, start = [], time.time()
    for step in range(1, steps + 1):
        model.train()
        ids, mask, labels = make_batch(rng.sample(rows, batch_size))
        for g in opt.param_groups:
            g["lr"] = lr * min(1.0, step / 10)                    # warm up over the first 10 steps
        loss = model(input_ids=ids, attention_mask=mask, labels=labels).loss
        loss.backward()
        torch.nn.utils.clip_grad_norm_(params, 1.0)
        opt.step(); opt.zero_grad()
        if step == 1 or step % log_every == 0:
            line = f"step {step:>3}  train loss {loss.item():.4f}"
            entry = {"step": step, "train": round(loss.item(), 4)}
            if val_rows:
                model.eval()
                with torch.no_grad():
                    v_ids, v_mask, v_labels = make_batch(val_rows)
                    v = model(input_ids=v_ids, attention_mask=v_mask, labels=v_labels).loss.item()
                line += f"  validation loss {v:.4f}"; entry["val"] = round(v, 4)
            history.append(entry)
            print(line, flush=True)
    model.eval()
    return history

Step 7 · The baseline with examples in the prompt

The fair comparison for fine-tuning is the best prompt you can write. Add a precise description of the fields and five solved examples, shown to the model as earlier turns of the conversation. This is few-shot prompting (Lesson 11.6):

shots = train_rows[:5]
def few_shot_messages(row):
    msgs = [{"role": "system", "content": SYSTEM + ' Use exactly the keys "intent" (one of refund, order_status, cancel, '
             'exchange, other), "order_id" (a string such as "SK-12345", or null) and "urgent" (true or false).'}]
    for s in shots:                                     # five worked examples, shown as earlier turns of the conversation
        msgs += [{"role": "user", "content": s["text"]}, {"role": "assistant", "content": json.dumps(s["label"])}]
    return msgs + [{"role": "user", "content": row["text"]}]

for row in test_rows[:3]:
    print("MODEL :", repr(reply(base, few_shot_messages(row))))
print("\nfew-shot scores on the test set:", evaluate(base, test_rows, few_shot_messages))
print(f"prompt length: {count_tokens(to_messages(test_rows[0], with_answer=False))} tokens zero-shot, {count_tokens(few_shot_messages(test_rows[0]))} tokens few-shot")

The examples fixed the format: every reply is now valid JSON with the right keys. But the content is mostly wrong. This small model picks the right intent well under half the time, and look at the order numbers in the three replies printed: the second and third are the same number, copied from one of the examples in the prompt instead of read from the ticket (the second ticket has no order number at all). Only 15% of tickets are fully correct. The prompt also grew from 53 tokens to 349, and every one of those tokens is processed, and paid for, on every single ticket.

Reading this output
What the baseline tells you
  • A much larger model would do far better with this same few-shot prompt, probably well enough to ship. That is the usual first answer, and Lesson 14.137 comes back to the comparison. The case for fine-tuning here is cost and speed at volume: a 135M model is hundreds of times cheaper to run than a frontier model, if it can be made accurate.
  • The baseline numbers are now written down: 0% fully correct zero-shot and 15% few-shot. Whatever training achieves will be compared with these, on the same 40 test tickets.

Step 8 · Where real training data comes from

Templates made this workshop repeatable, but real data is harder and matters more than any training setting.

Source How it works Watch out for
Production logs Real inputs with the outputs your current system produced, filtered to the good ones (Lesson 14.138) Personal data; training the model on your current system's mistakes
Human labels People write or correct the ideal output for real inputs Cost; labellers disagreeing: write guidelines and measure agreement
A large model as teacher A frontier model labels real inputs; you review a sample. This is distillation (Lesson 14.139) The provider's terms of use; the teacher's errors are inherited
Synthetic inputs A model writes varied inputs from a list of scenarios, personas and styles; a teacher model then labels them Low variety: generated text clusters around a few phrasings, as our templates do
Public datasets From the Hugging Face Hub and similar Licence; relevance; test sets that models have already seen

How many examples? Rough guides that practitioners report, to be confirmed by your own measurements:

  • 50 to 100 carefully chosen examples can already teach a format or a tone.
  • A few hundred to a few thousand is typical for classification, extraction and routing.
  • Tens of thousands are used for broad behaviour changes or teaching a new domain's language.
  • Quality and variety beat volume. A thousand near-identical examples teach less than a hundred varied ones. Lesson 14.137 measures this directly.

A checklist before training on any dataset:

Check your mental model
  • ✗ "Fine-tuning is how you teach a model your company's knowledge."
    ✓ It teaches behaviour and format. Knowledge that changes belongs in retrieval or tools, where it can be updated and cited.
  • ✗ "Fine-tune first, then see if it helped."
    ✓ Define the metric and measure the prompt-only baseline first; otherwise you cannot know whether training was worth it.
  • ✗ "A high validation score means the model is ready."
    ✓ Validation data looks like training data. Only a test set that resembles real use, with no leaked examples, tells you that.
  • ✗ "More training data is always better."
    ✓ More varied, correct data is better. Duplicates and near-duplicates add cost and encourage memorising.

Exercises

Predict before you run

build(phrasings=1) trains on a single phrasing per intent. Before running anything: will the training set still contain 320 different tickets? What will differ between them, and what do you expect a model trained on it to learn? (Solution P1.)

Add a sixth intent, complaint ("the delivery person was rude", "your app keeps crashing"), with ten phrasings. Rebuild the sets and check the balance. Which other parts of the two files mention the list of intents and need no change, and why? (Solution M1.)

Practice
Apply it

For each request, say whether you would reach for a prompt, retrieval, a tool, or fine-tuning, and what you would measure first: (a) "answer questions about our 400-page HR policy"; (b) "classify 2 million product reviews a day into 30 categories, on our own servers"; (c) "always reply in our brand voice"; (d) "tell customers their current loyalty-point balance". (Solution X1.)

Solutions

SolutionP1 · One phrasing, many tickets

Yes: 320 different tickets, because products, cities, order numbers and urgency phrases still vary. But every refund ticket has the same sentence skeleton. A model trained on it learns to recognise those five skeletons, and has seen nothing that tells it which words carry the meaning. Expect a near-perfect validation score and a poor test score. Lesson 14.137 runs a version of this experiment.

SolutionM1 · A sixth intent

Add a "complaint" key with ten templates to TEMPLATES. INTENTS is built from the dictionary's keys, but build uses INTENTS[len(rows) % 5], so change the 5 to len(INTENTS) to keep the classes balanced (a good example of a hard-coded number to avoid). to_messages and score need no change because they work on whatever label they are given. The few-shot prompt's list of allowed intents in Step 7 does need the new name.

SolutionX1 · Choosing the tool

(a) Retrieval: the knowledge is long, changes, and answers should cite the policy; measure retrieval recall and answer faithfulness (Lesson 14.27). (b) Fine-tuning a small model, or a classic classifier (Lesson 7.13): fixed task, huge volume, own servers; measure accuracy per category against a prompted large model on a labelled sample. (c) A prompt with examples first; fine-tune only if the voice still drifts, measured with a rubric or a judge model (Lesson 14.117). (d) A tool call to the loyalty system: this is live data, and no model should answer it from memory.

Recap
  • Fine-tuning changes a model's behaviour by continuing its training on your examples. Use it for format, style and narrow high-volume tasks, not for knowledge.
  • Start every project with a task a program can score and a measured baseline from the best prompt.
  • Data comes as chat-format JSONL: system, user and assistant messages, one conversation per line.
  • Keep three sets. The test set must resemble real use and share nothing with training; check for leaks.
  • On the ticket-routing task, the untrained 135M model scores 0% fully correct zero-shot and 15% few-shot: examples in the prompt fix the format but not the content.

Check your understanding

Q1Your support assistant gives outdated delivery prices. What is the right fix?

Prices are knowledge that changes; put them where they can be updated and cited, not in the weights.

Q2Why does the test set in this workshop use phrasings that never appear in training?

Real customers phrase things in ways your training data did not; the test must resemble that.

Q3The few-shot prompt produced valid JSON almost every time but few fully correct answers. What does that show?

Format and correctness are separate; measuring each field shows which one a change improved.
