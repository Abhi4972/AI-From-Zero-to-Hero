@@top The situation
:::plain In plain words first
A sandboxed agent exits before answering: its session database is read-only, although the mount is listed as read-write. SQLite cannot write through that particular shared-folder filesystem on this host, and the launcher insists on keeping the database there. The sandbox itself works. The case trains testing what a filesystem actually supports rather than trusting how it is listed.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A mount listed as `rw` can still refuse some operations, such as database locking.
- ✗ The sandbox is broken.
  A run started by hand inside it worked; the session store's location was the problem.
- ✓ The fix is a supported location for the store, not a rebuilt sandbox.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Test filesystem features directly; listings are not guarantees.
- Databases need locking support from their filesystem.
- Separate the component that failed from the one that hosts it.
- Report a launcher constraint as such.
:::
@@
