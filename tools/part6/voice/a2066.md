@@top The problem
:::plain In plain words first
"Tell me when this page changes" sounds like a diff. A raw HTML diff is useless: every visit changes a timestamp, a visitor counter, a navigation badge. What a person wants is "the start time moved from 14:00 to 15:00, and only one volunteer place is left".

This project builds that brief in Go. It extracts readable text blocks from HTML, skipping known noise regions; compares snapshots by counting each normalized block, so a repeated sentence that disappears once is still noticed; fetches the live page with limits and never lets a failed fetch become the new baseline; and exports a report of exact added and removed statements, with hashes of both snapshots.
:::
@@

@@end Step 2 · Compare exact text and preserve duplicates
:::visual Counting blocks, not sets
```python run
from collections import Counter
before = ["Repair afternoon", "The repair afternoon starts at 14:00 on Saturday.", "Three volunteer places are available.",
          "Bring your own tools.", "Bring your own tools."]
after  = ["Repair afternoon", "The repair afternoon starts at 15:00 on Saturday.", "One volunteer place is available.",
          "Bring your own tools.", "The side entrance has a step-free ramp."]
b, a = Counter(before), Counter(after)
print("removed:", dict(b - a)); print("added:  ", dict(a - b))
print("set view sees the tools line as unchanged:", set(before) - set(after) == {"The repair afternoon starts at 14:00 on Saturday.", "Three volunteer places are available."})
```
:::

:::read
"Bring your own tools." appeared twice before and once after. Counting blocks reports one occurrence removed; a set comparison would see the sentence on both sides and report nothing. The real changes are exact sentences, readable without any HTML: the time moved and the number of places dropped.
:::
@@

@@end Step 3 · Fetch one page without losing the baseline
:::check
Which statements are right?

- ✓ Navigation counters and footer timestamps are excluded before comparing.
- ✗ If the fetch fails, the empty result should become the new baseline.
  A failed fetch never replaces the baseline; the old snapshot stays.
- ✓ Each snapshot has a hash, so a saved baseline can be checked for corruption.
- ✗ A text diff tells you why the page changed.
  It shows what changed; the why is for a person.
:::

@@end Exercises
1. How would you handle a page where a sentence is reworded slightly every day?
2. Why validate a saved baseline's hash before comparing?
3. What noise regions would you exclude on a news site?

## Solutions

??? sol | 1. Daily rewording
Exact comparison will report it every day. Either accept that (it did change), or add a separate similarity view that pairs removed and added sentences above a threshold as "reworded", clearly labelled as a heuristic.
???

??? sol | 2. Checking the baseline
A corrupted or truncated baseline would produce a report full of false additions. Checking its hash first turns that into a clear error instead of a misleading brief.
???

??? sol | 3. News-site noise
Timestamps, "trending" and "most read" lists, ad slots, related-article rails, comment counts and cookie banners: anything that changes on every visit without changing the article.
???

??? sol | B1 · Counting duplicates
Occurrences of each sentence. Two before and one after is one removal, which a set comparison cannot see.
???
