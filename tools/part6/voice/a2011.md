@@top The problem
:::plain In plain words first
Model calls are billed per token, at different rates for input, cached input and output. Before a call you can only estimate the cost; after it, the provider reports what was actually used. A budget needs both: a cautious quote to decide whether to start, and the real usage to settle the account.

This project does that accounting in Rust with whole numbers only (nano-dollars), so no rounding can drift the total. It estimates tokens from characters, validates the provider's usage record, prices it with overflow checks, and keeps a ledger that refuses work it cannot afford.
:::
@@

@@end Step 3 · Price with checked integers
:::worked Pricing one request
Rates: input 2, cached input 1, output 5 nano-dollars per token. The provider reports 100 input tokens, of which 40 were cached, and 20 output tokens.

1. Cached tokens are part of the input, not extra: uncached input = 100 − 40 = 60.
2. Cost = 60 × 2 + 40 × 1 + 20 × 5 = 120 + 40 + 100 = **260**.
3. The quote before the call assumed no cache and the full output limit of 80: 100 × 2 + 80 × 5 = **600**.
4. Adding cached tokens on top of input (140 × 2…) is the classic double count; the validator rejects a record where cached is larger than input.
:::

:::check
Which statements are right?

- ✓ Integers avoid floating-point rounding in money totals.
- ✗ Wrapping on overflow is harmless because amounts are small.
  A wrapped sum becomes a small number, and an over-budget request would be admitted.
- ✓ A reservation exactly equal to the remaining budget is accepted.
- ✗ The character estimate is the token count.
  It is a rough, configurable ratio for a preflight warning; billing uses recorded usage.
:::
@@

@@top Run the finished project
:::predict Predict before you run
The limit is 1,000. Two small requests each quote 600 and actually cost 260 and 310. A third quotes 500 × 2 + 100 × 5 = 1,500. Which requests run, and what is spent at the end?
:::

@@end Run the finished project
:::read Reading this output
`orchard-summary` reserved 600 (0 + 600 ≤ 1,000), then settled at its actual 260, releasing 340. `orchard-check` reserved 600 (260 + 600 = 860 ≤ 1,000) and settled at 310. Spent is now 570, remaining 430. `long-report` quotes 1,500, more than the remaining 430, so it is `blocked` and the ledger is unchanged. Notice why the second request could start at all: settling the first at its actual cost freed most of its reservation.
:::

@@before Build it on your machine
:::broken
A dashboard adds `cached_tokens` to `input_tokens` before pricing. Costs look 30 to 40 percent too high on cached workloads. What is the bug, and which validation would have exposed it in tests? (Solution B1.)

:::recap What to keep from this project
- Estimate cautiously before the call; settle with recorded usage after it.
- Cached input is a subset of input, priced at its own rate.
- Use integers and checked arithmetic for money.
- Reserve before work; a rejected reservation changes nothing.
:::

@@end Exercises

## Solutions

??? sol | 1. Same characters, different tokens
Tokenizers are trained mostly on some languages and scripts. Text in a well-covered language packs many characters into each token; other scripts may need a token per character or more. A single characters-per-token ratio is a rough average, which is why it is only a preflight warning.
???

??? sol | 2. Missing input usage
Reject the record and settle conservatively (keep the full reservation) while flagging it for review. Guessing zero would make the call look free.
???

??? sol | 3. Silent wrap-around
`spent + quote` could wrap to a small number, so the check "within the limit" would pass for a huge request. Checked arithmetic turns that into an error instead.
???

??? sol | 4. What a budget planner can reuse
It can reuse the rate card, the quote function and the reservation rule. It must keep quotes (planned) and recorded usage (actual) as separate fields, and never write a quote into an actual-spend field.
???

??? sol | B1 · Double-counted cache
Cached tokens are already inside `input_tokens`. Adding them again prices them twice, once at the full rate. The rule "cached must not exceed input" plus a test with a known record (100 input, 40 cached, cost 260) would have caught it.
???
