@@top Problem
:::plain In plain words first
The last lesson composes the track's runtime pieces into one **safety gate** with three checkpoints. **Pre-generation**: the injection detector reads the prompt and passes it, blocks it, or flags it for later layers. **During generation**: a streaming filter watches tokens as they are produced and can stop the response early. **Post-generation**: the output classifiers and the rules engine produce a verdict. The gate combines everything into one final action per request (allow, warn, redact, block) and writes an **audit trace**: which layer fired, with what score, and why. It is evaluated on attack fixtures and benign prompts together, so both missed attacks and blocked users show up.
:::
@@

@@end Concept
:::worked Combining three checkpoints
A prompt is flagged (not blocked) by the pre-generation detector at 0.55 confidence as role-play. Generation proceeds.

1. During generation, no streaming rule fires.
2. Post-generation, the output classifier finds an email in the response: redact, medium.
3. The rules engine finds no violation.
4. Final action: the most severe of the layers' actions, **redact**; the trace records the pre-generation flag, the redaction and the reason. If the pre-generation confidence had been 0.9, the request would have been blocked before the model ran at all, the cheapest outcome.
:::

:::check
Which statements are right?

- ✓ High-confidence attacks are blocked before the model is called.
- ✗ A flag from the pre-generation layer always blocks the request.
  Flags are weighed by later layers; only high confidence blocks outright.
- ✓ The streaming filter can stop a response mid-generation.
- ✗ A gate that blocks no benign prompts is good enough.
  It must also be measured on how many attacks it lets through.
:::

:::predict
Before running the code below: of 50 attack fixtures, 10 are blocked, 25 redacted, 2 warned. How many attacks pass with a plain allow, and what share of attacks is that?

:::visual Reading the gate's outcome table
```python run
outcomes = {"block": 10, "redact": 25, "warn": 2, "allow": 23}      # 50 attacks + 10 benign
benign_allowed = 10
attacks_allowed = outcomes["allow"] - benign_allowed
attacks = sum(outcomes.values()) - benign_allowed
print(f"attacks: {attacks}, allowed unchanged: {attacks_allowed} ({attacks_allowed / attacks:.0%})")
print(f"attacks stopped or modified: {attacks - attacks_allowed} ({(attacks - attacks_allowed) / attacks:.0%})")
```
:::

:::read
Of the 23 "allow" outcomes, 10 are the benign prompts, so 13 of 50 attacks (26%) pass with no action at all, while 74% are blocked, redacted or warned. A headline like "0 of 10 benign prompts blocked" is true and good, but this is the other half of the report, and the per-category breakdown shows where those 13 come from.
:::

- Block early when confident; otherwise flag and weigh later.
- One final action per request, with an audit trace.
- Evaluate attacks and benign prompts together.
- Report what gets through, per category.

## Solutions

??? sol | B1 · No output checks
Without post-generation checks, any attack the input detector misses (about a third of several categories, Lesson 19.83) reaches the user unfiltered, and model mistakes such as leaking personal data or the system prompt are no longer caught (Lesson 19.85), nor are product rules enforced (Lesson 19.86). Keep the output layer and make it cheaper (smaller classifiers, rules first) rather than removing it.
