@@top The problem
:::plain In plain words first
This lesson wires the RAG track into one pipeline: **ingest** documents with the chosen chunker, **rewrite** the query, **retrieve** with hybrid search, **re-rank**, and **generate** an answer that cites the chunks it used. Every query produces a **trace** with each stage's output and latency, and the whole system is checked by an **evaluation gate**: retrieval and answer metrics on a labelled set, each with a threshold, and the demo exits with success only if all pass. That last part is what makes it shippable: the same script that demonstrates the system also refuses to ship it when quality drops.
:::

@@end Idea 3 · The self-terminating demo
:::worked A gate that barely passes
Thresholds: recall@5 ≥ 0.75, precision@1 ≥ 0.50, MRR ≥ 0.60, faithfulness ≥ 0.75, relevance ≥ 0.75.

1. Results: recall@5 1.00, precision@1 0.50, MRR 0.71, faithfulness 1.00, relevance 1.00. All pass.
2. Precision@1 sits exactly on its threshold: one more query with the wrong top chunk and the gate fails.
3. With a small query set, one query moves precision@1 by a large step (with 8 queries, 12.5 points).
4. A gate this close to the line should be read as "fragile pass": add queries to tighten the estimate before trusting it, and alert on metrics within a margin of their thresholds, not only on failures.
:::

:::visual How fragile is a pass?
```python run
import math
hits, n, threshold = 4, 8, 0.50
for label, h, m in (("now", hits, n), ("one more miss", hits, n + 1), ("one more hit", hits + 1, n + 1)):
    p = h / m
    print(f"{label:14s}: precision@1 = {h}/{m} = {p:.3f}  {'PASS' if p >= threshold else 'FAIL'}")
p = hits / n
print(f"95% interval with {n} queries: about {max(0, p - 1.96 * math.sqrt(p * (1 - p) / n)):.2f} to {min(1, p + 1.96 * math.sqrt(p * (1 - p) / n)):.2f}")
```
:::

:::read
One more miss drops precision@1 to 0.44 and the gate fails; one more hit lifts it to 0.56. With 8 queries, the 95% interval on a measured 0.50 spans roughly 0.15 to 0.85, so the gate cannot really tell a 0.4 system from a 0.6 one. The gate's design is right; its query set needs to be much larger before its verdicts mean much.
:::

@@before Ship it
:::read
The pipeline indexes 12 chunks; the traced query is rewritten (multi-query), retrieves three chunks, and produces a one-sentence answer citing `d6:0`, with re-ranking the slowest stage (about 3 ms). All five gates pass and the demo prints PASSED. Precision@1 passes at exactly its threshold (0.500 against 0.50), the fragile pass the worked example and visual describe.
:::

:::broken
A team's RAG demo passes its gate in CI, but the gate's labelled queries were written by the same engineer who tuned the chunker and prompts, using the same documents. What is the risk? (Solution B1.)
:::

:::recap What to keep from this lesson
- One pipeline: chunk, rewrite, retrieve, re-rank, generate with citations.
- Trace every stage with its output and latency.
- Gate on retrieval and answer metrics with thresholds.
- Watch the margin, not just pass or fail.
- Grow and diversify the labelled set over time.
:::

## Solutions

??? sol | B1 · Tuned on the test
The system was tuned until those queries passed, so the gate measures fit to its own examples rather than general quality, and real user questions phrased differently may fail. Keep a held-out query set written by someone else (or sampled from real traffic), never tune against it, and refresh it as documents and users change.
