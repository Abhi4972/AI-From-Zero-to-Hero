@@top The problem
:::plain In plain words first
This lesson puts the whole track together: a coding agent fixes a small bug in a multi-file Python project, and every action passes through the pieces built so far. Each tool call goes through the **gate chain**, runs in the **sandbox**, is wrapped in a **span**, adds to the **observation ledger**, and the outcome is scored by the **eval harness**. The "model" is a fixed **policy**, a five-state machine (survey, run tests, inspect, fix, verify), so the run is reproducible. That substitution is the point: the harness contract does not care whether decisions come from rules or from a language model, and integration bugs show up at the seams between components, not inside any one of them.
:::
@@

@@end What the demo asserts
:::worked Checking that the records agree
After a run, three independent records exist: the policy's step list, the spans, and the metrics.

1. Steps: read, run tests, read, write, run tests = 5 tool calls.
2. Spans: one per tool call plus one for the session = 6.
3. Counters: `read_file` 2 + `run_tests` 2 + `write_file` 1 = 5.
4. If the counter total were 6 or the spans showed a refused call that the step list does not, a component is double-counting or a refusal was not reported. Cross-checking totals like this is the integration test that unit tests of each part cannot do.
:::

:::check
Which statements are right?

- ✓ Every tool call goes through gates, sandbox, span and ledger, in that order.
- ✗ Using a fixed policy instead of a model makes the demo meaningless.
  It makes it reproducible; the harness contract is the same for a model.
- ✓ The agent stops when the tests pass after the fix.
- ✗ If each component passes its own tests, the composed system works.
  Seams between components are where integration bugs appear.
:::

:::predict
Before running the code below: a step list has 5 tool calls, but the counters total 6 and the spans include a refused `shell` call. Which records disagree, and what does that suggest?
:::

:::visual Reconciling three records
```python run
from collections import Counter
steps = ["read_file", "run_tests", "read_file", "write_file", "run_tests"]
spans = ["session"] + steps
counters = Counter(steps)

def reconcile(steps, spans, counters):
    issues = []
    if sum(counters.values()) != len(steps): issues.append(f"counter total {sum(counters.values())} != {len(steps)} steps")
    tool_spans = [s for s in spans if s != "session"]
    if Counter(tool_spans) != Counter(steps): issues.append(f"span tools {Counter(tool_spans)} != steps {Counter(steps)}")
    return issues or ["all three records agree"]

print(reconcile(steps, spans, counters))
bad_counters = counters + Counter({"read_file": 1})                 # a double-counted read
bad_spans = spans + ["shell"]                                       # a refused call with no step
print(reconcile(steps, bad_spans, bad_counters))
```
:::

:::read
The clean run reconciles. In the broken one, the check names both problems: the counters show one more call than the policy made (a double count), and the spans include a `shell` call the step list never mentions (a refusal that was traced but not reported to the policy). Neither component would fail its own tests; only comparing them finds it.
:::

@@before How this composes with the rest of Track A
:::read
The agent solves the task in five steps: it reads `src/fizz.py`, runs the tests (exit 1), reads the test file, writes the fix, and reruns the tests (pass), using 640 of its 8,000-token observation budget with no refusals. Six spans and five counted tool calls agree with the step list. One small mismatch with the text above: the policy's survey step reads the source file directly and its inspect step reads the test file, the reverse of the order described; the harness does not mind, which is itself a useful property.
:::

:::broken
To speed things up, a developer lets the policy call `run_tests` directly through `subprocess`, bypassing the harness, "because tests are harmless". What is lost? (Solution B1.)
:::

:::recap What to keep from this lesson
- Compose gates, sandbox, spans, ledger and eval into one loop.
- A deterministic policy makes the integration test reproducible.
- Cross-check steps, spans and counters after every run.
- Integration bugs live at the seams.
- Swapping the policy for a model keeps the same contract.
:::

## Solutions

??? sol | B1 · A side door around the harness
The call skips the gates (no budget or whitelist check), the sandbox (no timeout, path jail or output cap; a test suite can run arbitrary code), the span and the counters (observability now misses the slowest step), and the ledger. The run looks cheaper and safer than it is. Every action, however harmless it seems, goes through the same path.
