@@top The problem
:::plain In plain words first
One client retrying a failed request is sensible. Twenty clients retrying the same overloaded service at the same moment is a retry storm: each retry adds load exactly when the service can least take it, and a short outage turns into a long one.

This project makes the storm visible. A deterministic replay simulates many clients against a failing service on a virtual clock. Bounded exponential backoff with jitter spreads retries out. A shared retry budget caps the total number of retries across clients, and server hints such as Retry-After are honoured. Finally the same policy runs against a local HTTP service, and the counters are checked independently.
:::
@@

@@end Step 2 · Compare bounded backoff and jitter
:::visual Backoff with and without jitter
```python run
import random
from collections import Counter
def schedule(clients, base=100, cap=1600, attempts=3, jitter=True):
    times = []
    for c in range(clients):
        rng, t = random.Random(c), 0                         # deterministic per client
        for n in range(attempts):
            delay = min(cap, base * 2 ** n)
            t += rng.randint(0, delay) if jitter else delay
            times.append(t)
    return Counter(t // 10 for t in times)                   # retries per 10 ms bucket
for j in (False, True):
    b = schedule(20, jitter=j)
    print("jitter" if j else "no jitter", "-> busiest 10 ms bucket:", max(b.values()), "retries, buckets used:", len(b))
```
:::

:::read
Without jitter, all twenty clients wait exactly 100, 200 and 400 ms, so their retries land together: all 20 in the same 10 ms window, three times, three spikes. With "full jitter" (a random wait between 0 and the backoff), the same 60 retries spread across dozens of windows and the busiest holds only a few. The seed is per client, so the run is reproducible; real conclusions need several seeds, as the exercises say.
:::

@@end Step 3 · Enforce shared retry budgets and server delays
:::check
Which statements are right?

- ✓ A shared retry budget limits total retries across all clients.
- ✗ Per-client retry limits are enough to prevent a storm.
  Twenty clients each allowed three retries can still send 80 requests in total.
- ✓ A server's Retry-After delay is respected before the next attempt.
- ✗ A process-local budget protects a service used by many machines.
  It limits one process; a fleet needs a shared admission service.

@@end Run the finished project
:::read Reading this output
The simulation reports 32 calls from 20 clients: 20 first attempts plus the 12 retries the shared budget allowed, an amplification of 1.6. No call succeeded because the simulated service was still failing, and 21 calls landed in the same millisecond, the peak load the service had to absorb. The local HTTP run sends the same 32 calls, of which 12 (the retries, once the service recovered) succeed, with a lower peak of 9. Without the budget, every client would keep retrying.
:::

- Replay many clients on a deterministic clock to see aggregate load.
- Back off exponentially up to a cap, with jitter.
- Cap retries across clients with a shared budget.
- Honour server delays; retry only retryable statuses.
- Peak load and amplification answer different questions.

@@end Exercises

## Solutions

??? sol | 1. Peak against amplification
Amplification (total calls per client) says how much extra work retries created overall. The busiest millisecond says how much arrived at once, which is what knocks a service over. A policy can have low amplification and still a terrible peak.
???

??? sol | 2. Seeds
The same seed gives the same timeline exactly; another seed gives a different one. Report the distribution of peaks and amplification over many seeds before claiming one policy is better.
???

??? sol | 3. A fleet-wide budget
Each process would need to ask a central admission service (or use a shared token bucket) before retrying. Define what happens when that service is unreachable, usually "do not retry".
???

??? sol | 4. Live peaks
Live timings vary with scheduling, so the local peak is evidence that clients line up, not a measurement of any real service's capacity.
???

??? sol | B1 · Retrying forever
About 50,000 requests per second during the outage (100,000 users every 2 seconds), all hitting the service the moment it returns. Exponential backoff with jitter spreads and slows the retries; a retry budget caps how many retries are allowed at all.
???
