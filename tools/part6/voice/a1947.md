@@top The problem
:::plain In plain words first
Long training runs get interrupted, so they **checkpoint**: save enough state to continue exactly where they left off. "Enough" is more than the model weights. It is five things: model weights, optimizer state (AdamW's running averages), the learning-rate scheduler's position, the data loader's position within the epoch, and the **random number generator** states, so shuffling and dropout repeat identically. The save must be **atomic**: write to a temporary file, then rename it into place, so a crash mid-write never leaves a corrupt checkpoint where a good one was. Large models write **sharded** checkpoints, one file per part. The test of correctness is strict: a resumed run must produce exactly the same losses as an uninterrupted one.
:::
@@

@@end Idea 4 · Resume continues mid epoch
:::worked What goes wrong if one bucket is missing
A run is interrupted at step 10 of 24 and resumed.

1. **No optimizer state:** AdamW restarts its running averages at zero, so the first steps after resume are much larger than they should be: a loss spike.
2. **No scheduler state:** the learning rate restarts at warmup.
3. **No data position:** the epoch restarts, so the model sees the first examples twice and the last ones never.
4. **No RNG state:** shuffling and dropout differ, so losses after resume diverge from an uninterrupted run, which makes the bug hard to see. With all five saved, the resumed losses match the uninterrupted ones exactly.
:::

:::check
Which statements are right?

- ✓ An atomic save writes a temporary file and then renames it into place.
- ✗ Saving the model weights is enough to resume training.
  Optimizer, scheduler, data position and RNG states are needed too.
- ✓ Restoring RNG state makes shuffling and dropout repeat exactly.
- ✗ Writing directly to `checkpoint.pt` is safe if the disk is reliable.
  A crash mid-write leaves a truncated file in place of the last good one.
:::

:::visual RNG state and atomic writes
```python run
import os, pickle, random, tempfile
rng = random.Random(42)
first = [rng.random() for _ in range(3)]
saved = rng.getstate()
second = [rng.random() for _ in range(3)]
rng.setstate(saved)
replayed = [rng.random() for _ in range(3)]
print("restored stream matches:", replayed == second)

def atomic_save(obj, path):
    d = os.path.dirname(path)
    fd, tmp = tempfile.mkstemp(dir=d, suffix=".tmp")
    with os.fdopen(fd, "wb") as f:
        pickle.dump(obj, f); f.flush(); os.fsync(f.fileno())
    os.replace(tmp, path)                 # atomic on the same filesystem

with tempfile.TemporaryDirectory() as d:
    path = os.path.join(d, "ckpt.pkl")
    atomic_save({"step": 10, "rng": saved}, path)
    print("files after save:", os.listdir(d))
    print("loaded step:", pickle.load(open(path, "rb"))["step"])
```
:::

:::read
Restoring the saved state replays exactly the same numbers, which is what makes a resumed run identical to an uninterrupted one. The save leaves only the final file: the temporary file was renamed over it in one step (`os.replace` is atomic within one filesystem), so a reader ever sees either the old checkpoint or the complete new one, never half of one.
:::

@@before Ship it
:::read
Both resume demos interrupt a 24-step run at step 10, reload, and continue; the maximum loss difference against an uninterrupted run is exactly 0.0, for the single-file checkpoint and for the sharded one. Exact equality, not "close", is the right bar: any difference means some piece of state was not saved or restored.
:::

:::broken
A team keeps only the latest checkpoint and overwrites it in place every 1,000 steps. A node fails during a save at step 41,000. What have they lost, and what two practices prevent it? (Solution B1.)

:::recap What to keep from this lesson
- Save five buckets: model, optimizer, scheduler, data position, RNG.
- Write to a temporary file, fsync, then rename into place.
- Shard large checkpoints, with a manifest of the pieces.
- Test that a resumed run matches an uninterrupted one exactly.
- Keep more than one checkpoint.
:::

## Solutions

??? sol | P2 · Keeping the last K
After each successful save, list checkpoints by step and delete all but the newest K. K = 2 is the minimum (the latest might be corrupt or have been saved just before a bad divergence); 3 to 5 is common when space allows. Verify a checkpoint's checksum before deleting the older ones.
???

??? sol | B1 · One file, overwritten
The in-place write was interrupted, so the only checkpoint is now truncated, and up to 41,000 steps of progress are gone. Use atomic saves (temporary file plus rename) so a failed write never replaces a good checkpoint, and keep several recent checkpoints, verified by checksum at startup.
???
