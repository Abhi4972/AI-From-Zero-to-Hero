@@top The problem
:::plain In plain words first
When a model generates text, each new token needs one full pass through the model, and on a GPU that pass is slow mainly because all the weights must be read from memory. **Speculative decoding** uses that waiting time. A small, cheap **draft** guesses the next few tokens, and the big **target** model checks all the guesses in one pass. Every guess it agrees with is a token you got almost for free; at the first disagreement it writes the correct token and the round ends. The output is exactly what the target alone would have produced. How much you gain depends on the **acceptance rate** $\alpha$, the chance that a draft token is accepted. **EAGLE-3** is a draft head trained on the target model's own internal states, which pushes $\alpha$ up.
:::
@@

@@end Idea 8 · When not to use speculative decoding
:::math
**How many tokens does one target pass give?** Draft $K$ tokens; each is accepted with probability $\alpha$, and the round stops at the first rejection, where the target supplies one token itself. The expected number of tokens per target pass is

$$E[\text{tokens}] = 1 + \alpha + \alpha^2 + \dots + \alpha^K = \frac{1 - \alpha^{K+1}}{1 - \alpha}$$

The lesson's shortcut $1 + K\alpha$ assumes every draft token is judged independently of the ones before it. Because one rejection discards everything after it, the true figure is lower.
:::

:::worked K = 5, α = 0.7
1. Shortcut: 1 + 5 × 0.7 = 4.5 tokens per pass.
2. Correct: (1 − 0.7⁶) / (1 − 0.7) = (1 − 0.118) / 0.3 ≈ 2.94 tokens per pass.
3. With a verify overhead of 15%, speedup ≈ 2.94 / 1.15 ≈ 2.6×, not the 3.9× the shortcut gives.
4. At α = 0.4: (1 − 0.4⁶) / 0.6 ≈ 1.66 tokens per pass, about 1.4× after overhead. That is why the lesson says to switch off below α ≈ 0.55 on real traffic: the gain shrinks fast and the tail gets worse.
:::

:::check
Which statements are right?

- ✓ Speculative decoding does not change what the target model outputs.
- ✗ A higher draft length K always helps.
  Each extra draft token is accepted only if all earlier ones were, so returns fall off quickly while draft cost keeps rising.
- ✓ Mean inter-token latency can fall while P99 rises.
- ✗ α measured on general chat holds for code or medical traffic.
  A draft trained on general data often drops to 0.4–0.6 on specialist traffic.
:::

:::visual Diminishing returns from longer drafts
```python run
def tokens_per_pass(alpha, k):
    return (1 - alpha ** (k + 1)) / (1 - alpha)

for alpha in (0.4, 0.55, 0.7, 0.85):
    row = "  ".join(f"K={k}: {tokens_per_pass(alpha, k):4.2f}" for k in (2, 5, 10))
    print(f"alpha={alpha:.2f}  {row}   (shortcut at K=5: {1 + 5 * alpha:.2f})")
```
:::

:::recap What to keep from this lesson
- Decode is memory-bound, so checking several draft tokens in one pass is nearly free.
- Expected tokens per pass: $(1 - \alpha^{K+1}) / (1 - \alpha)$.
- Measure α on your own traffic; switch off or retrain the draft below about 0.55.
- Watch P99 inter-token latency, not only the mean.
- Skip it for very short outputs and for batch jobs where latency does not matter.
:::

## Solutions

??? sol | P1 · α for 2× and 3×
With the correct formula, K = 5 and 15% overhead: 2× needs about 2.3 tokens per pass, so α ≈ 0.58; 3× needs about 3.45, which requires α ≈ 0.80. With the shortcut you would think α = 0.25 and 0.5 suffice. The higher the overhead, the higher both thresholds.
???

??? sol | P2 · Blended traffic
Blended α = 0.7 × 0.7 + 0.3 × 0.4 = 0.61. Per-traffic tokens per pass at K = 5: 2.94 for chat, 1.66 for code, so the blend is 0.7 × 2.94 + 0.3 × 1.66 ≈ 2.56, still positive overall. But code requests get little benefit and more tail latency, so route code to a code-trained draft or turn speculation off for it.
???

??? sol | B1 · Mean down, P99 up
First, measure α per traffic type: code at α ≈ 0.4 produces many rejections, and each rejection adds a second pass. Second, check concurrency: at large batch sizes decode is less memory-bound, verification costs more, and the tail grows. Fixes: a domain-trained draft for code, a shorter K, or speculation only below a concurrency threshold.
