@@top Problem
:::plain In plain words first
A safety evaluation must measure two failures at once. **Under-refusal**: the assistant answers a request it should refuse. **Over-refusal**: it refuses a request it should answer, such as a chemistry homework question that merely sounds dangerous. Optimizing only the first produces an assistant that refuses everything; only the second, one that refuses nothing. This lesson builds a fixture-based evaluator with **mock policies** standing in for models, so a code change moves the metrics in a known way, and reports both rates, per category, plus **calibration** (ECE): does the policy's stated confidence in a refusal match how often refusing was right?
:::
@@

@@end Concept
:::worked Three policies, two errors
Fixtures: 50 attacks and 50 benign requests that look sensitive.

1. A strict policy refuses 44 of 50 attacks (under-refusal 12%) and answers all benign requests (over-refusal 0%).
2. A leaky policy refuses 40 attacks (under-refusal 20%), also with 0% over-refusal.
3. An over-cautious policy refuses 44 attacks and 9 benign requests (over-refusal 18%).
4. Accuracy alone ranks them strict, leaky, over-cautious, but the over-cautious policy's problem is invisible to anyone who only counts caught attacks; its users simply get fewer answers.
:::

:::check
Which statements are right?

- ✓ Over-refusal and under-refusal are measured separately.
- ✗ A policy that refuses more is always safer to deploy.
  Over-refusal is a failure too: people denied legitimate help.
- ✓ Mock policies make metric changes traceable to code changes.
- ✗ Overall accuracy is enough to compare policies.
  It mixes two different errors; report both rates.
:::

Before running the code below: which policy has the higher accuracy: one that misses 6 of 50 attacks and blocks 0 benign, or one that misses 3 attacks and blocks 8 benign?

:::visual Two error rates, one accuracy
```python run
def report(missed_attacks, blocked_benign, n_attack=50, n_benign=50):
    acc = 1 - (missed_attacks + blocked_benign) / (n_attack + n_benign)
    return acc, missed_attacks / n_attack, blocked_benign / n_benign

for name, miss, block in (("strict", 6, 0), ("cautious", 3, 8), ("leaky", 10, 0)):
    acc, under, over = report(miss, block)
    print(f"{name:9s} accuracy {acc:.2f}  under-refusal {under:.2f}  over-refusal {over:.2f}")
```
:::

:::read
The cautious policy misses fewer attacks but blocks 16% of legitimate requests, and its accuracy (0.89) is lower than the strict policy's (0.94). The leaky one ties with the cautious one on accuracy (0.90 vs 0.89) for the opposite reason. A single number cannot express that trade-off; the two rates, side by side, can.
:::

@@before Ship it
:::read
The strict policy has the best accuracy (0.95), with 12% under-refusal and no over-refusal; the leaky one under-refuses 20%; the over-cautious one refuses 17% of benign requests. Per category, the strict policy's gaps are concentrated in encoding tricks (half missed) and prefix injection (a quarter missed), which tells you where to strengthen it. The leaky policy's very low ECE (0.02) is a reminder that good calibration and good safety are different properties.
:::

:::recap What to keep from this lesson
- Measure under-refusal and over-refusal separately.
- Include benign requests that look sensitive.
- Use deterministic mock policies to test the evaluator itself.
- Break results down by attack category.
- Calibration is a separate property from safety.
