@@top Problem
:::plain In plain words first
An **issue-to-PR agent** works without anyone watching: a person labels a GitHub issue, a worker starts in a cloud sandbox, clones the repository, figures out how to build it, edits code until the tests pass, and opens a pull request explaining what it did. Because no one supervises each step, the safeguards must be structural. The agent gets a **short-lived, narrowly scoped token**; **branch protection** (not the agent's goodwill) stops pushes to `main` and force-pushes; the worker refuses diffs that touch CI workflow files; every repository has a **daily budget**; and a pull request opens only when the full test suite passes in the sandbox. The measure of success is pass rate, cost and safety on a set of real issues. Product names are a 2026 snapshot.
:::

@@end Build it
:::worked Which control stops which mistake
The agent, misled by text in an issue, tries four things.

1. **Push straight to `main`.** Stopped by branch protection on the repository; the app is not on the bypass list, so its token cannot override it.
2. **Edit `.github/workflows/deploy.yml`** to run a command in CI. The app has only read access to workflows, but GitHub permissions are not path-scoped for everything, so the worker also rejects any diff touching that folder before pushing.
3. **Open 40 pull requests in a loop.** The dispatcher's per-repo daily cap stops it at five.
4. **Print the token into the PR description.** Logs and outputs are scrubbed for secrets, and the token expires within the hour anyway.
5. Each layer is independent of the model's judgement, which is the point: the agent can be wrong and the repository stays safe.
:::

:::check
Which statements are right?

- ✓ Branch protection, not app permissions, enforces "no force-push to main".
- ✗ A green build is enough to open the pull request.
  The full test suite must pass; coverage drops get a review label.
- ✓ A per-repo daily cap limits both cost and runaway behaviour.
- ✗ A long-lived personal access token is fine inside a sandbox.
  Short-lived installation tokens limit the damage if anything leaks.
:::

:::predict
Before running the code below: an allow-list check rejects diffs that touch `.github/workflows/`. Does it catch `.github/workflows/../workflows/ci.yml`, and a file named `.GITHUB/WORKFLOWS/x.yml` on a case-insensitive filesystem?
:::

:::visual A path check that normalizes first
```python run
import posixpath
FORBIDDEN = (".github/workflows/",)
def naive(path): return not path.startswith(FORBIDDEN)
def careful(path):
    p = posixpath.normpath(path).lower()
    return not (p + "/").startswith(FORBIDDEN) and not p.startswith(FORBIDDEN) and ".." not in p.split("/")

for path in ("src/app.py", ".github/workflows/ci.yml", "src/../.github/workflows/ci.yml",
             ".GITHUB/WORKFLOWS/x.yml", "./.github/workflows/x.yml"):
    print(f"{path:35s} naive allows: {naive(path)!s:5}   careful allows: {careful(path)}")
```
:::

:::read
The naive prefix check is fooled by three spellings of the same forbidden folder: a `..` detour, upper case, and a leading `./`. Normalizing the path (resolving `.` and `..`) and comparing in lower case catches all of them. Git itself rejects some of these forms, but the worker should not depend on that; it should check the canonical path of every file in the diff.
:::

@@before Ship it
:::read
Twenty simulated tasks produce 13 pull requests and 7 failures, and every failure is the dispatcher's daily cap of five PRs per repository, not a failed fix. Two repositories hit the cap; the third opened three. The passing tasks averaged $3.20 and under six turns per PR. In a real evaluation, report capped tasks separately from failed ones, or the pass rate mixes policy limits with agent quality.
:::

:::broken
A team gives their agent's GitHub App `contents: write` and `workflows: write` "so it can fix CI configs too", and adds the app to the branch-protection bypass list "to avoid merge friction". Name the two risks. (Solution B1.)
:::

:::recap What to keep from this lesson
- Trigger by label; run in a fresh cloud sandbox with an inferred build environment.
- Short-lived, narrow tokens; branch protection enforces no direct or force pushes.
- Reject diffs touching workflow files after normalizing paths.
- Per-repo budgets and caps; full tests must pass before a PR opens.
- Report capped, failed and successful tasks separately.
:::

## Solutions

??? sol | P1 · Stabilizing a flaky test
Run the named test 50 times in the sandbox and record the failure rate and any differing outputs. Look for the usual causes: ordering assumptions, timing and sleeps, shared state between tests, unseeded randomness. Propose the smallest change that removes the cause (not a retry decorator), then rerun 50 times and include both failure rates in the PR.
???

??? sol | B1 · Write access to CI and a bypass
With `workflows: write`, a misled agent can change what CI runs, which can expose repository secrets to injected commands. On the bypass list, branch protection no longer applies to it, so a bad push can reach `main` without review. Keep workflow access read-only, propose CI changes as normal PRs for humans to review, and never add automation to the bypass list.
???
