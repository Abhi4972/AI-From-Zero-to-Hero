@@top The problem
:::plain In plain words first
An executable file is not a mystery box; it has a documented layout. Linux uses ELF, Windows uses PE/COFF, macOS uses Mach-O, and each says where the code is, which parts are writable, which functions it calls from shared libraries and where execution starts. This project builds a static inspector for all three, written defensively because binary files are untrusted input.

It is a bridge from phase 13's reverse-engineering lessons to a working tool: read headers; list sections with permissions and entropy; resolve symbols and demangle C++ names; read imports, exports, relocations and macOS chained fixups; recover strings and function starts even from stripped binaries; and publish a JSON report, an HTML byte map and a diff between two builds.
:::
@@

@@end Step 2 · Sections, segments, permissions, and entropy
:::visual Entropy in bits per byte
```python run
import math, random
from collections import Counter
def entropy(data):
    if not data: return 0.0
    n = len(data)
    return sum(-(c / n) * math.log2(c / n) for c in Counter(data).values()) + 0.0
samples = {"zero padding": bytes(256), "ASCII text": b"Hello, tally! " * 18,
           "random bytes": random.Random(0).randbytes(256)}
for name, data in samples.items(): print(f"{name:13} {entropy(data):.3f} bits/byte")
```
:::

:::read
Entropy measures how unpredictable the bytes are, from 0 (all identical) to 8 (every byte value equally likely). Zero padding scores 0, this repetitive text about 3, and random bytes about 7.2: close to the maximum of 8, which only very long random inputs reach, since 256 bytes cannot contain all 256 values evenly. Compiled code usually lands around 5 to 6.5, and compressed or encrypted data near 8, which is why a high-entropy section in an ordinary program is worth a second look. Entropy is computed only over bytes actually stored in the file: a zero-filled `.bss` section takes no file space and has nothing to measure.
:::

Which statements are right?

- ✓ Every offset read from the file is bounds-checked before it is followed.
- ✗ A stripped binary has no recoverable function starts.
  Symbols are gone, but Mach-O's function-starts table, call targets and the entry point still reveal them.
- ✓ Imports name the shared library and symbol a program calls into.
- ✗ Entropy near 8 proves a section is encrypted.
  It shows the bytes are unpredictable, which compressed data and some tables are too.

@@end Exercises
1. Why refuse big-endian and universal (fat) Mach-O files instead of guessing?
2. Why might a prologue scan find fewer functions at -O2 than at -O0?
3. What would a build diff show if a new dependency were linked in?

## Solutions

??? sol | 1. Refusing unsupported formats
Parsing them with assumptions made for little-endian 64-bit files would produce plausible but wrong numbers. A clear refusal tells the user what to do (extract one architecture first) instead of misleading them.
???

??? sol | 2. Prologues at -O2
Optimizing compilers skip frame setup in small leaf functions and interleave instructions, so the familiar "save registers, set frame pointer" pattern is often missing. At -O0 nearly every function has it.
???

??? sol | 3. A new dependency
New imports (library and symbol names), likely growth in `__text` and `__stubs`, new strings, and new function starts, each listed in the diff with sizes.
???

??? sol | B1 · An unchecked size
Python would silently return a short slice (or a huge allocation in other languages), and later code would misread it as the section's content. The project checks every offset and size against the file length and reports a format error instead.
???
