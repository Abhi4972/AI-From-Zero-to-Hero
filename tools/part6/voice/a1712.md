@@top The problem
:::plain In plain words first
**Edge inference** means running the model on the user's own device: a phone, a laptop, a browser tab or a small board such as NVIDIA Jetson. It keeps data private, works offline and removes network delay. The limit is **memory bandwidth**, how fast the device can read memory. Every generated token reads all the model's weights once, so a phone that reads 60 GB a second can never generate more than 60 GB ÷ model size tokens a second, whatever its chip's TOPS rating says. Each platform has its own route to its fastest unit: Core ML for Apple's Neural Engine, Qualcomm's QNN for Snapdragon, WebGPU for browsers, TensorRT for Jetson. Small, 4-bit models and short contexts are the rule.
:::
@@

@@end Idea 10 · Numbers you should remember
:::math
**Decode ceiling on any device.** With bandwidth $B$ and model size $S$ in bytes,

$$\text{tokens/s} \le \frac{B}{S}, \qquad \text{efficiency} = \frac{\text{observed tokens/s}}{B / S}$$

Efficiency tells you whether to fix the runtime (low efficiency) or to shrink the model (efficiency already near 100%).
:::

:::worked An 8B model on an iPhone
Llama 3.1 8B in Q4 is about 4.7 GB. An A18 phone reads about 60 GB/s.

1. Ceiling: 60 / 4.7 ≈ 12.8 tokens/s. The lesson observes about 8: efficiency 63%.
2. In BF16 (about 16 GB, more than the phone's RAM even before the OS) it could not run at all; in INT8 (about 9.4 GB) the ceiling is about 6.4 tokens/s.
3. A 3B model in Q4 (about 1.8 GB): ceiling about 33 tokens/s, fast enough for voice.
4. Context: 32k tokens of KV cache for the 8B model at FP16 is about 4 GB more, and the phone runs out of memory. Keep 4k–8k.
:::

:::check
Which statements are right?

- ✓ On edge devices, memory bandwidth sets the decode ceiling more than TOPS.
- ✗ llama.cpp on a Mac uses the Apple Neural Engine.
  Its Metal backend uses the GPU through MPS; the Neural Engine needs a Core ML conversion.
- ✓ WebLLM needs MLC-compiled weights, not GGUF.
- ✗ A 128k context is fine on a phone once the model is 4-bit.
  The KV cache grows with context and does not shrink with weight quantization.
:::

:::predict
Before running the code below: which gains more tokens per second on a 77 GB/s Snapdragon phone, quantizing an 8B model from Q4 to Q3, or switching from the 8B model to a 3B one at Q4?
:::

:::visual Bandwidth ÷ size, on three devices
```python run
devices = {"iPhone (A18)": 60, "Snapdragon 8 Gen 3": 77, "M4 MacBook Air": 120}
models = {"8B Q4": 4.7, "8B Q3": 3.6, "3B Q4": 1.8, "1B Q4": 0.7}
print(f"{'':20s}" + "".join(f"{m:>9s}" for m in models))
for dev, bw in devices.items():
    print(f"{dev:20s}" + "".join(f"{bw / size:9.1f}" for size in models.values()))
```
:::

:::read
On the Snapdragon phone, Q4 → Q3 raises the 8B ceiling from about 16 to 21 tokens/s, while a 3B Q4 model reaches about 43. Model size dominates every other choice on the edge. That is why edge products ship 1–3B models and keep 8B for laptops.
:::

- Decode ceiling = memory bandwidth ÷ model size; datacenter HBM is 30–50× faster than phone memory.
- Use each platform's own path: Core ML, QNN, WebGPU with MLC, TensorRT on Jetson.
- Choose the model size for the device first, then the 4-bit format.
- Keep context to 4k–8k on phones.
- Voice is the strongest edge use case: no network round trip.

??? sol | B1 · Long context on a mid-range phone
The KV cache grows with every token of context: at 32k tokens an 8B model's FP16 KV cache is about 4 GB, on top of a 4.7 GB model and the OS, so phones with 8 GB run out of memory. Cap context at 4k–8k (summarize older turns), and quantize the KV cache, or use a 3B model on mid-range devices.
