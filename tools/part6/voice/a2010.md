@@top The problem
:::plain In plain words first
A coding agent is a loop: look at the code, propose a change, run the tests, repeat. The dangerous parts are the tools. A file tool that follows `../` or a symlink can touch files outside the project. A patch that overwrites blindly destroys someone else's edit. A "test" tool that runs whatever command the model writes is a shell for the model. And a loop that trusts the model's "done" claims success without evidence.

This project builds each tool with a hard contract, then a loop that stops only on real evidence (the tests pass) or on a budget. The planner is a recorded list of actions, so the whole run is repeatable and inspectable.
:::
@@

@@end Step 2 · Apply exact patches with preconditions
:::worked A patch is an assertion
1. The file holds `return price + quantity`. The patch says: replace `price + quantity` with `price * quantity`.
2. The old text appears exactly once, so the replacement is unambiguous. The new content is written to a temporary file in the same folder, then moved over the original in one step, keeping its permissions.
3. If another editor already changed the line, the old text appears zero times: reject and leave the file alone.
4. If the old text appears twice, the patch is ambiguous: reject. Guessing which occurrence was meant is how agents break code.
:::

:::check
Which statements are right?

- ✓ The test tool builds its own command; model text never becomes a shell command.
- ✗ A run that reports zero tests and exits 0 counts as passing.
  No tests is no evidence; the tool treats it as a failure.
- ✓ The loop counts every action, valid or not, against the budget.
- ✗ Copying a repository into a temporary folder makes its tests safe to run.
  The tests still run as normal code with your permissions; this project only runs trusted fixtures.
:::

@@before Build it on your machine
:::broken
An agent loop marks a task complete when the model's reply contains "All tests pass". The model writes that after a run that actually printed "Ran 0 tests". Which two rules from this project would have stopped it? (Solution B1.)
:::

:::recap What to keep from this project
- Resolve paths under the workspace; reject traversal, absolute paths and symlink escapes.
- Patches require their old text exactly once; write atomically.
- The test tool owns its command, timeout and the reading of results.
- Zero tests or skipped tests are not a pass.
- Stop on evidence or budget, never on the model's claim.
:::

@@end Exercises

## Solutions

??? sol | 1. Copying is not sandboxing
The tests are code. Run from a copy, they still have your user's file, network and process access. Isolation needs an operating-system boundary: a container, a VM or a restricted user, with limits on memory, time and network.
???

??? sol | 2. The file changed underneath
The patch's old text no longer appears, so the patch is rejected and the file keeps the other editor's fix. The loop records the rejection, and the planner must look at the file again before proposing anything new.
???

??? sol | 3. Printed text is not evidence
Test code (or the model) can print anything. The tool reads the test runner's own final summary from the process it started, and requires a non-zero test count with no failures or skips.
???

??? sol | 4. Plugging in a model
Replace the recorded plan with a function that asks the model for the next action in the same structured form (tool name plus arguments). Everything else stays: the same patch precondition, the same test tool and the same rule that only a passing test run completes the task.
???

??? sol | B1 · A claimed pass
The completion rule (only the test tool's result can finish the loop) and the zero-test rule (no tests is a failure) would each have stopped it.
???
