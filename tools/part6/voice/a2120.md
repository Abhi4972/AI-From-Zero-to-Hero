@@top The situation
:::plain In plain words first
A planner polls a code-review task for an hour and times out, while the reviewer was waiting for the planner to answer a question. The wait loop only knew three stop states (completed, failed, canceled), so "input required" looked like "still running". The case trains listing every state a remote task can be in, and giving each one a branch.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A task can stop and wait for input without being finished.
- ✗ Anything that is not completed, failed or canceled means "still working".
  Interrupted states, such as input required, also stop progress.
- ✓ Answering an input-required task means sending a new message with the same task id.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- List every state a remote task can be in.
- Give interrupted states their own branch.
- Read the status message; it says what is needed.
- Time out loops that cannot see progress.
:::
@@

@@takeaways
The situation | An hour of polling a task that was waiting.
The evidence | The poll loop and the task's status.
Questions to answer first | Working, or waiting for us?
Walkthrough | The loop's stop set was incomplete.
What actually happened | Handle input-required and other interrupted states.
Wrong turns | Treating every other state as running.
The lesson to carry | Every state needs a branch.
