@@top The problem
:::plain In plain words first
An **evaluation harness** in the style of lm-eval runs a model through several **tasks**, each defined by data plus a **metric**, and writes a **leaderboard**. This lesson keeps it small and explicit: a task spec names its examples and metric; five fixture tasks cover arithmetic (exact match), running code (pass if the code produces the expected result), short generation (substring match), multiple choice, and summaries (ROUGE-L); a **model adapter** is the one interface every model must implement; and a **runner** feeds tasks through the adapter and records per-task scores and latency as JSON. Separating spec, metric and adapter is what lets you add a model or a task without touching the rest.
:::
@@

@@end Idea 5 · The runner
:::math ROUGE-L
With LCS the longest common subsequence of words between prediction and reference, of lengths $p$ and $r$:

$$P=\frac{\text{LCS}}{p},\quad R=\frac{\text{LCS}}{r},\quad \text{ROUGE-L}=\frac{2PR}{P+R}$$

Unlike word overlap, the common words must appear in the same order, though not necessarily next to each other.
:::

:::worked One summary, scored
Reference: "the cat sat on the mat". Prediction: "the cat was on a mat".

1. Longest common subsequence: "the cat on mat", 4 words.
2. Precision 4 / 6, recall 4 / 6, so ROUGE-L = 0.67.
3. Exact match would give 0, and substring match would give 0 too.
4. Each metric encodes a different idea of "correct"; the task spec, not the runner, decides which one applies.
:::

:::check
Which statements are right?

- ✓ The adapter is the only part that knows how to call a particular model.
- ✗ One metric can be used for every task.
  Arithmetic, code, choice and summary need different notions of correct.
- ✓ ROUGE-L rewards shared words in the same order.
- ✗ A perfect score on five fixture tasks shows a model is strong.
  Fixtures test the harness; real benchmarks test the model.
:::

:::predict
Before running the code below: two leaderboards differ on three tasks. Which change does a diff that sorts by absolute movement list first?
:::

:::visual Diffing two leaderboards
```python run
before = {"arithmetic": 0.80, "code-exec": 0.60, "generation": 0.90, "multiple-choice": 0.70, "summary": 0.55}
after  = {"arithmetic": 0.82, "code-exec": 0.40, "generation": 0.90, "multiple-choice": 0.78, "summary": 0.55}
moves = sorted(((t, after[t] - before[t]) for t in before), key=lambda x: -abs(x[1]))
for task, d in moves:
    flag = "  <- regression" if d < -0.05 else ""
    print(f"{task:16s} {before[task]:.2f} -> {after[task]:.2f}  ({d:+.2f}){flag}")
print(f"mean score {sum(before.values()) / 5:.3f} -> {sum(after.values()) / 5:.3f}")
```
:::

:::read
The mean barely moves (0.710 to 0.690), but the diff shows what happened: code execution fell 20 points while multiple choice rose 8. A leaderboard diff sorted by movement, with a regression flag, is the view a reviewer needs; the average alone hides the one change that matters.
:::

@@before Ship it
:::read
The harness loads five tasks and the fixture adapter scores 1.000 on all of them (5 of 5 each), with sub-millisecond latency. That is the expected result for a fixture adapter that knows the answers: it proves the runner, metrics and JSON output work end to end. Plug in a real model and the same leaderboard becomes a measurement.
:::

:::broken
A team's code-execution metric runs model-written code with `exec()` in the evaluation process and counts a task as passed if no exception is raised. Name two problems. (Solution B1.)
:::

:::recap What to keep from this lesson
- A task is data plus a metric; the spec decides which metric.
- One adapter interface per model; the runner never changes.
- Write per-task scores and latency to a leaderboard file.
- Diff leaderboards per task; flag regressions.
- Run untrusted code in a sandbox and check its output.
:::

## Solutions

??? sol | P3 · A leaderboard diff
Load both JSON files, compute the change per task, sort by absolute change, and print each with a flag for drops beyond a threshold, as the visual does; include the number of examples per task so a 20-point change on 5 examples is read as the noise it may be.
???

??? sol | B1 · Unsafe and too lenient
`exec()` in the evaluator's own process lets generated code read files, use the network or crash the harness, so it must run in an isolated subprocess with limits (Lesson 19.26). And "no exception" is not "correct": code that does nothing passes. Compare outputs or run tests against expected values.
