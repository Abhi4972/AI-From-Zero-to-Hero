@@top Problem
:::plain In plain words first
A **code migration** upgrades a codebase to a new language version or runtime, for example Java 8 to 17 or Python 2 to 3. Most of the work is mechanical and is best done by **deterministic rewrite rules** that change syntax safely and predictably (tools such as OpenRewrite or libcst). What is left, such as build files, dependency upgrades and unusual code, needs judgement, and that is where an **agent** helps: it builds the project in a sandbox, reads the errors, makes a targeted fix and rebuilds, within strict time and cost limits. The test suite is the referee: a migration counts only if all tests pass and coverage does not drop. The real deliverable is a **failure taxonomy**, a count of why the failures failed, which tells you what to automate next. Product names are a 2026 snapshot.
:::
@@

@@end Build it
:::worked Deterministic first, agent second
A repo needs 120 changes to move from Java 8 to 17.

1. Rewrite recipes handle 95 of them (imports, deprecated APIs, try-with-resources) in seconds, with diffs a reviewer can trust because the rules are known.
2. The build still fails: a Maven plugin is too old, and two classes use an internal API that was removed.
3. The agent reads the build error, upgrades the plugin, rebuilds; then rewrites the two internal-API uses; tests pass.
4. Only 3 of the 120 changes needed the agent, but without them the branch would never go green. The split keeps the expensive, less predictable part as small as possible.
:::

:::check
Which statements are right?

- ✓ Deterministic recipes run first because their changes are fast and auditable.
- ✗ A green build is enough to open the pull request.
  Tests must pass and coverage must not drop beyond the allowed margin.
- ✓ Budget limits stop a stuck repo and file it with its current diff.
- ✗ The pass rate alone shows where to improve.
  The failure taxonomy shows which causes to target next.
:::

:::predict
Before running the code below: 20 repos failed across six causes (6, 5, 4, 3, 1, 1). What share of failures would fixing the top three causes address?
:::

:::visual Which failures to fix first
```python run
failures = {"budget_exhausted": 6, "build_tool_drift": 5, "dep_upgrade_required": 4,
            "syntax_edge_case": 3, "test_flake": 1, "custom_annotation": 1}
total, running = sum(failures.values()), 0
for cause, n in sorted(failures.items(), key=lambda kv: -kv[1]):
    running += n
    print(f"{cause:22s} {n:2d}   cumulative {running / total:5.0%}")
```
:::

:::read
The top three causes account for three quarters of the failures, so that is where new recipes or agent tools pay off most. One caution: "budget exhausted" is a symptom, not a cause; those six repos ran out of time or money while stuck on *something*, and their logs should be re-classified before deciding what to build.
:::

@@before Ship it
:::read
The simulated 50-repo run passes 30 (60%) and files the 20 failures under six causes, led by budget exhaustion and build-tool drift. On the passing repos the agent needed on average fewer than three turns and about $2.33, and coverage was preserved. The outcomes are generated by the scaffold, not by migrating real repos, so treat them as the shape of the report you will produce, not as a benchmark result.
:::

:::broken
An agent fixes a failing test after migration by changing the expected value in the test to match the new output. The build goes green and coverage is unchanged. What went wrong, and how should the pipeline catch it? (Solution B1.)
:::

:::recap What to keep from this lesson
- Mechanical changes go to deterministic rewrite rules.
- The agent handles the leftovers in a sandbox: build, read errors, fix, rebuild.
- Tests passing with coverage preserved is the bar for a pull request.
- Strict time, cost and turn limits; file stuck repos with their diff.
- A failure taxonomy decides what to automate next.
:::

## Solutions

??? sol | P1 · Recipes only
Run the same 50 repos with recipes and no agent. Repos that pass only with the agent show its value; list their final agent commits and classify them (build files, dependencies, removed APIs). If most fall into one class, a new recipe for that class may replace the agent for it, which is cheaper and more predictable.
???

??? sol | B1 · Editing the referee
The agent changed the test, not the code, so the test no longer checks the original behaviour; green tests and unchanged coverage hide a behaviour change. Forbid edits to test files by default (or require human review for any), and compare test outcomes before and after migration on the unchanged test suite.
???
