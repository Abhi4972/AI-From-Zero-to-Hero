@@top The problem
:::plain In plain words first
An MCP server with 250 tools is useful and expensive: sending every tool's name, description and schema to the model on every turn can fill a large part of its context before the user has said anything. This project builds a scoped inventory server that discovers tools within a measured budget.

It generates a catalogue of 250 read-only tools, ranks tools against a query and selects only what fits a character budget (measured by actually serializing them), implements the MCP lifecycle over JSON-RPC on stdio (initialize first, then list tools page by page), audits that pagination returns every tool exactly once, and drives the real server from a typed TypeScript client.
:::
@@

@@end Step 2 · Select tools under an explicit context budget
:::visual Fit tools into a budget by measuring them
```python run
import json
def tool(kind, op):
    return {"name": f"{kind}_{op}", "description": f"{op} {kind} in the local fixture inventory",
            "inputSchema": {"type": "object", "properties": {}, "required": [], "additionalProperties": False}}
catalog = [tool(k, op) for k in ["pods", "logs", "nodes"] for op in ["count", "list", "get", "describe", "events"]]
query = {"pods", "count"}
ranked = sorted(catalog, key=lambda t: (-len(query & set(t["name"].split("_"))), t["name"]))
picked, used = [], 2                                       # "[]" brackets
for t in ranked:
    size = len(json.dumps(t)) + (1 if picked else 0)
    if used + size > 500: break
    picked.append(t["name"]); used += size
print("full catalog:", len(json.dumps(catalog)), "chars;", "picked:", picked, used, "chars")
```
:::

:::read
The fifteen-tool catalogue serializes to a few thousand characters. Ranking by query words puts `pods_count` first (two matches), then the tools with one match. The selector adds tools until the next one would cross the 500-character budget, measured on the actual JSON that would be sent, not estimated. Only two or three tools fit; the model sees the most relevant ones and can ask for more.
:::

@@end Step 4 · Audit catalog coverage through protocol pages
:::check
Which statements are right?

- ✓ A `tools/call` before `initialize` gets error -32002.
- ✗ Counting characters in the tool names is a good estimate of context use.
  Schemas and descriptions dominate; the budget is checked on the serialized JSON.
- ✓ Paging through the whole catalogue must return every tool exactly once.
- ✗ A tool failure is a JSON-RPC protocol error.
  Tool failures are reported inside a successful response; protocol errors are for protocol misuse.
:::

@@end Exercises
1. Why must the ranking break ties by name?
2. What should the server return when no tool matches the query?
3. How would you let the model ask for more tools?

## Solutions

??? sol | 1. Name tie-breaks
So the same query always yields the same selection. Without it, tools with equal scores could swap between runs and the model's behaviour would change for no visible reason.
???

??? sol | 2. No match
An empty selection with a clear note, plus a small, generic set (for example a search tool) if the design allows. Sending the whole catalogue "just in case" defeats the budget.
???

??? sol | 3. Asking for more
Expose a discovery tool (search the catalogue by words) that returns a few more definitions within the same budget, or let the client page through `tools/list` with a cursor.
???

??? sol | B1 · Sending every tool
Each turn would carry only the few tools relevant to the request, within a measured budget: shorter prompts (faster and cheaper) and fewer irrelevant options for the model to confuse.
???
