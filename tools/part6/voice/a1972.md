@@top Why an isolated subprocess
:::plain In plain words first
For code generation, an answer is right when it **passes the tests**. The **code-execution scorer** extracts the code from the model's output, runs it together with the task's tests in a separate **subprocess** with a **wall-clock timeout** and an **output cap**, refuses code that imports dangerous modules (a **denylist**), and classifies the outcome: pass, assertion failure, syntax error, timeout, or runtime error. With several samples per task, **pass@k** estimates the chance that at least one of k samples passes. The lesson is honest that a denylist is a weak barrier; real isolation needs containers or OS-level sandboxing.
:::

@@end Exit codes
:::worked Classifying five candidates
Task: implement `add(a, b)`; tests assert `add(2, 3) == 5` and `add(-1, 1) == 0`.

1. `return a + b`: both asserts pass: **pass**, score 1.
2. `return a - b`: the first assert fails: **assertion_fail**, score 0.
3. `def add(a, b) return a + b` (missing colon): **syntax_error**, caught before running.
4. `while True: pass`: killed at the timeout: **timeout**.
5. `import subprocess; ...`: refused by the denylist before running: **error**.
6. Separate outcome codes let you see *why* a model fails (syntax against logic against hanging), not just how often.
:::

:::check
Which statements are right?

- ✓ Code runs in a separate process so a crash or hang cannot take down the harness.
- ✗ A module denylist makes running untrusted code safe.
  It is easy to bypass; isolation must come from the sandbox.
- ✓ Each outcome (pass, assertion, syntax, timeout, error) is recorded separately.
- ✗ pass@10 equals 10 × pass@1.
  It is the chance at least one of 10 samples passes.
:::

:::visual Why string denylists leak
```python run
DENY = ("import subprocess", "import socket")
snippets = {
    "plain import": "import subprocess\nsubprocess.run(['ls'])",
    "dunder import": "m = __import__('sub' + 'process')\nm.run(['ls'])",
    "via os": "import os\nos.system('ls')",
}
for name, code in snippets.items():
    blocked = any(d in code for d in DENY)
    print(f"{name:14s} -> {'blocked' if blocked else 'NOT blocked'}")
```
:::

:::read
Only the literal import is caught. Building the module name at runtime, or simply using `os.system`, does the same thing and passes a string check. Inspecting the parsed code for imports is better but still bypassable. That is why the lesson treats the denylist as a tripwire for accidents and puts the real protection in the process boundary, and why production harnesses run candidates in containers with no network.
:::

All five reference cases are classified as expected: pass, assertion failure, syntax error (with the parser's message), timeout after 0.6 s, and a denied `subprocess` import. The pass@k line shows the estimator at work for a task where 1 of 10 samples passed: pass@1 = 0.10, pass@5 ≈ 0.43, pass@10 ≈ 0.67, the unbiased estimate from Lesson 19.27 rather than the naive 1 − 0.9^k.

:::broken
A harness runs candidates with `exec()` in the harness process and a 5-second `signal.alarm`. A candidate catches the alarm's exception in a bare `except:` and loops forever. What happens, and what is the fix? (Solution B1.)
:::

:::recap What to keep from this lesson
- Run candidate code in a separate process with a timeout and output cap.
- Classify outcomes: pass, assertion, syntax, timeout, error.
- Denylists catch accidents, not determined code.
- pass@k: chance at least one of k samples passes, estimated without bias.
- Real isolation: containers, no network, limited resources.
:::

## Solutions

??? sol | B1 · A timeout the candidate can swallow
In-process, the timeout is just an exception the candidate's own code can catch, so it keeps running and the harness hangs. A separate process can be killed from outside regardless of what its code does; run each candidate in a subprocess and kill it at the deadline.
