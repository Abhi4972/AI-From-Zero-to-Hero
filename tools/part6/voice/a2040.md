@@top The problem
:::plain In plain words first
Translating subtitles is not just translating sentences. Each caption has a time window, and a translation that is longer than the original may be impossible to read in three seconds. Product terms must be translated the same way every time ("map" is always "mapa"). And nobody should publish a caption file that a person has not reviewed.

This project builds a subtitle desk for WebVTT files. It parses cues and keeps their timing strings exactly, applies a reviewed glossary to translation proposals (from any source, including a model), measures reading speed per cue and flags captions that are too long for their window, and exports a translated file only when every cue has been approved.
:::
@@

@@end Step 3 · Review cue length, terminology and meaning
:::visual Reading speed per cue
```python run
cues = [("map", 3.0, "Abre el mapa."), ("marker", 3.0, "Añade un marcador."),
        ("label", 2.0, "Escribe un nombre descriptivo y completo para el marcador de tu calle.")]
CPS = 17                                                  # characters per second a viewer can read
for cid, seconds, text in cues:
    chars = sum(not ch.isspace() for ch in text); budget = int(seconds * CPS)
    print(f"{cid:6} {chars:3} chars / budget {budget:2}", "TOO LONG" if chars > budget else "ok")
```
:::

:::read
Most cues fit easily. The `label` cue lasts only two seconds, so at 17 characters per second its budget is 34 visible characters, and the proposed Spanish has 59. It is flagged for a shorter rewrite; the timing is never stretched to make it fit, because shifting one cue would push every later one out of sync with the speech.
:::
@@

@@end Step 2 · Apply a glossary to translation proposals
:::check
Which statements are right?

- ✓ Timing strings are kept exactly as in the original file.
- ✗ A long caption can be fixed by extending its end time.
  That desynchronizes it from the audio; the text is shortened instead.
- ✓ The glossary fixes leftover English terms such as "map" → "mapa".
- ✗ The desk writes the translated file as soon as proposals exist.
  It writes it only when every cue is approved.
:::

@@end Exercises
1. Why count only non-whitespace characters?
2. How would you handle a cue with styling tags such as `<b>`?
3. Where would a model fit in this desk?

## Solutions

??? sol | 1. Non-whitespace characters
Spaces take no reading effort worth counting, and different languages use them differently; counting visible characters gives a fairer, comparable budget.
???

??? sol | 2. Styling tags
Strip tags before counting (they are not read), keep them in the output, and check the translation keeps the same tags balanced.
???

??? sol | 3. A model
As a source of proposals, recorded with its name and version. Its output goes through the same glossary, the same length checks and the same human approval as any other proposal.
???

??? sol | B1 · Missing checks
The reading-speed check per cue (captions too long for their window) and the glossary (one fixed translation for each product term), plus the review gate before upload.
???
