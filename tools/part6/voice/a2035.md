@@top The problem
:::plain In plain words first
You change a search system and the average score goes up. Ship it? Not yet: an average can rise while the one query that matters most, say "how do I restore a backup", got worse. This project builds an evaluation lab for rankings that shows exactly that.

It validates rankings and graded judgments (how useful each document is for each query), computes precision and recall at a cutoff, rewards useful results near the top with reciprocal rank and NDCG, and compares two systems query by query, listing which documents moved.
:::
@@

@@end Step 3 · Reward useful evidence near the top
:::visual NDCG by hand
```python run
import math
def dcg(grades): return sum((2 ** g - 1) / math.log2(r + 2) for r, g in enumerate(grades))
judg = {"runbook": 3, "old": 0}                     # restore query: graded usefulness (0 = not useful)
for name, ranking in [("baseline", ["runbook", "old"]), ("candidate", ["old", "runbook"])]:
    got = [judg.get(d, 0) for d in ranking[:3]]
    ideal = sorted(judg.values(), reverse=True)[:3]
    print(f"{name:9} grades {got} -> NDCG {dcg(got) / dcg(ideal):.3f}")
```
:::

:::read
Both rankings contain the one useful document, the runbook, so recall is 1.0 for both. NDCG still drops from 1.0 to 0.631 when the runbook (grade 3, gain 2³ − 1 = 7) falls from rank 1 to rank 2, where its gain is divided by log₂(3) ≈ 1.58: 7 / 1.58 ≈ 4.42 out of an ideal 7. That is the point of a rank-sensitive metric: it notices that the best answer moved down.
:::
@@

@@end Step 4 · Compare systems query by query
:::check
Which statements are right?

- ✓ Precision at 3 divides by 3 even if a system returned only 2 results.
- ✗ A document with no judgment counts as irrelevant and can be ignored.
  It gets zero gain but is counted as unjudged, so gaps in labelling stay visible.
- ✓ Macro averaging gives every query equal weight.
- ✗ If the mean NDCG rises, no query got worse.
  The per-query deltas can include a regression, which the report counts separately.
:::

Mean NDCG rises from 0.813 (baseline) to 0.877 (candidate), while precision, recall and reciprocal rank means are unchanged. The `deltas` list explains the rise and what it hides: "release" +0.394 and "cafe" +0.166, but "restore" −0.369, with the before and after rankings shown (`runbook, old` became `old, runbook`). `regressions: 1`. :::recap What to keep from this project
- Validate rankings (no duplicates) and graded judgments first.
- Precision and recall have different denominators.
- Reciprocal rank and NDCG reward good results near the top.
- Count unjudged documents; zero gain is not "irrelevant".
- Compare per query and list regressions, not just means.
:::

## Solutions

??? sol | 1. A new, unjudged note
It means nobody has judged it yet, not that it is irrelevant. If a system starts returning it, its gain is zero and the unjudged count rises; judge it before trusting the comparison.
???

??? sol | 2. Larger k
More results can only add relevant documents (recall can rise), but the extra slots are often filled with weaker results, so the share of useful results among the k shown (precision) falls.
???

??? sol | 3. All gains zero
The ideal DCG is zero, so NDCG would divide by zero. Return 0 (or "undefined") explicitly and document the choice; never let it become NaN in an average.
???

??? sol | 4. Which query first
The one with the largest negative delta, here "restore", especially if it serves a critical task. Then check whether its judgments are complete.
???

??? sol | B1 · A hidden regression
The per-query deltas and the regression count, with the "restore" query at the top: NDCG for restore fell by 0.37 because the runbook moved below an old note.
???
