@@top The problem
:::plain In plain words first
A large training job runs on many ranks, and each holds a different shard of the model and optimizer, so its checkpoint is **sharded**: every rank writes its own file in parallel, and a **manifest** records the world size, the step, and each shard's file name, size and **sha256** hash. The manifest is written last, **atomically**, so it only exists once every shard is safely on disk. On resume, the loader checks the manifest against reality: same world size, every file present, every hash matching. It also **rotates** checkpoints, keeping the most recent few and deleting older ones. The lesson tests the three failure modes the schema must catch: a different world size, a corrupted shard, and a missing shard.
:::
@@

@@end Idea 4 · Why per-rank files, not one big file
:::worked Why the manifest goes last
Four ranks write shards for step 1,200; rank 2's node dies halfway through its write.

1. **Manifest first:** a manifest for step 1,200 exists, listing four shards, but rank 2's file is truncated. A resume would load it (or fail confusingly) unless every hash is checked.
2. **Manifest last:** ranks 0, 1 and 3 finish; rank 2 never does; the coordinator never writes the manifest. Resume looks for the newest *complete* checkpoint and loads step 1,100.
3. With manifest-last plus hash checks, a half-written checkpoint is invisible, and a corrupted one is rejected loudly.
4. The cost: at most one checkpoint interval of lost work.
:::

:::check
Which statements are right?

- ✓ Each rank writes its own shard file, in parallel.
- ✗ The manifest should be written first so resume knows what to expect.
  Written last, its existence proves the checkpoint is complete.
- ✓ Loading checks world size and every shard's hash.
- ✗ Rotation can safely sort checkpoints by file modification time.
  Sort by step number; times can mislead when checkpoints are copied or restored.
:::

:::visual Rotation by time or by step
```python run
written = ["step_0100", "step_0000", "step_0001", "step_0002", "step_0003", "step_0004", "step_0005", "step_0006", "step_0007"]
keep = 5
by_time = written[:-keep]                                        # oldest writes first
by_step = sorted(written, key=lambda s: int(s.split("_")[1]))[:-keep]
print("delete by write time :", by_time)
print("delete by step number:", by_step)
```
:::

:::read
Sorting by write time deletes `step_0100`, the most advanced checkpoint in the directory, because it happened to be written first; sorting by step number keeps it and deletes steps 0–3. The lesson's own rotation test shows exactly the first behaviour, which is a real bug to fix: rotation should order by the step recorded in each manifest.
:::

@@before Ship it
:::read
The sharded checkpoint for step 100 is written with four shards and their hashes, and a resume verifies a byte-for-byte round trip on every rank. Both failure tests are rejected as intended: a manifest for 4 ranks refused by an 8-rank job, and a tampered shard caught by its hash. The rotation test then writes 8 more checkpoints and keeps 5, deleting `step_0100` along with steps 0–2: the time-ordered rotation the visual warns about, which throws away the furthest-trained checkpoint.
:::

:::broken
A resume script loads whichever shard files exist and skips hash checks "because the disk is reliable". After a crash, one shard is from step 900 and the other three from step 1,000. What happens? (Solution B1.)
:::

:::recap What to keep from this lesson
- One shard per rank, written in parallel.
- The manifest (world size, step, hashes) is written last and atomically.
- On load, check world size, presence and every hash.
- Rotate by step number, keeping several recent checkpoints.
- Test the failure paths, not just the happy path.
:::

## Solutions

??? sol | P2 · Keep the last five
Parse each checkpoint's step from its manifest, sort by step, and delete all but the five highest, but only after the new checkpoint's manifest has been written and verified, so a failed save never leaves fewer than five good checkpoints.
???

??? sol | B1 · Mixed steps
The model is assembled from shards trained to different steps, so layers and optimizer states disagree; training continues from an inconsistent state, often with a loss spike or silent damage. Only load shards listed in one manifest, and verify every hash against it.
???
