@@top Problem
:::plain In plain words first
A **fine-tuning pipeline** turns a general open model into one adapted to your task and preferences, and then serves it cheaply. The stages: **clean the data** (remove duplicates, low-quality text and personal information, and make sure no benchmark test questions leaked in); **supervised fine-tuning (SFT)** on good examples; **preference tuning** (DPO, or GRPO with a checkable reward); **quantization** to shrink the model; and **serving** with tricks such as speculative decoding. The deliverable is reproducibility: one command reruns everything, and a model card records what was done. This site does not train models; the scaffold below simulates the pipeline's bookkeeping so you can see its shape, and the visual checks the one stage that is pure data work, contamination. Model and tool names are a 2026 snapshot.
:::

@@end Build it
:::worked Why contamination checks come before training
A team fine-tunes on 50,000 scraped question–answer pairs. 300 of them are near-copies of questions in the MMLU-Pro test set.

1. After training, MMLU-Pro accuracy rises by 3 points. Some of that may be real; some is the model remembering answers it saw.
2. Nobody can separate the two afterwards, because the test set is no longer a fair test of this model.
3. Before training, a check that compares every training item's word n-grams with the test sets would have flagged those 300 items in minutes.
4. So the check is a gate in the pipeline: overlap above a threshold blocks the run, and the report lists what was removed.
:::

:::check
Which statements are right?

- ✓ Deduplication and PII scrubbing happen before any training run.
- ✗ A benchmark gain after fine-tuning proves the model got better at the task.
  Leaked test items can inflate it; check contamination first.
- ✓ Quantization trades a little quality for much smaller, faster models.
- ✗ Speculative decoding changes what the model outputs.
  With exact verification, it speeds decoding without changing the output distribution.
:::

:::predict
Before running the code below: the checker compares 5-word shingles. A training item copies a test question with two words changed. Does it still get flagged at a 0.5 Jaccard threshold?
:::

:::visual A contamination check with word shingles
```python run
def shingles(text, n=5):
    w = text.lower().split()
    return {" ".join(w[i:i + n]) for i in range(len(w) - n + 1)}

def jaccard(a, b):
    return len(a & b) / len(a | b) if a | b else 0.0

test_q = "which enzyme catalyses the first committed step of fatty acid synthesis in the cytosol of animal cells"
train = {
    "exact copy": test_q,
    "two words changed": test_q.replace("first", "initial").replace("animal", "mammalian"),
    "same topic, new wording": "in animals, fatty acid synthesis begins in the cytosol; name the enzyme for the committed step",
}
T = shingles(test_q)
for name, text in train.items():
    j = jaccard(shingles(text), T)
    print(f"{name:24s} Jaccard {j:.2f}  ->  {'FLAG' if j >= 0.5 else 'ok'}")
```
:::

:::read
The exact copy scores 1.0. Changing just two words drops the score to 0.30, well below a 0.5 threshold, because each changed word breaks every 5-word shingle that contains it. A reworded question on the same topic scores 0 and passes, as it should. Real checks therefore use shorter shingles or MinHash over several shingle sizes, and a lower threshold for short questions, accepting some false flags to catch paraphrased leaks.
:::

@@before Ship it
:::read
The scaffold records each stage as an artifact with a content hash and the tool that produced it, which is what makes the pipeline reproducible and auditable. The numbers in its eval report and serving summary (+3.2 on MMLU-Pro, 74% draft acceptance, 6,400 tokens per second, $0.28 per million tokens) are **placeholders written into the code**, not measurements. In your own run, every number in the model card must come from a logged evaluation with its config and commit.

:::broken
A team reports "+9 points on MMLU-Pro after SFT on our support tickets". Their contamination check compared only exact string matches. Why should the gain be distrusted, and what check is missing? (Solution B1.)
:::

:::recap What to keep from this lesson
- Data first: dedupe, filter, scrub PII, check contamination.
- SFT on good examples, then preference tuning (DPO or GRPO).
- Quantize and serve with speculative decoding; measure speed and cost.
- One command reruns everything; every stage hashed and logged.
- A model card reports real, reproducible numbers only.
:::

## Solutions

??? sol | P4 · A contamination gate
Insert known test items into the training data and confirm the gate catches them. Run near-duplicate detection (MinHash over word shingles of a few sizes) between every training item and every test set; fail the pipeline when any item exceeds the threshold, and write the matches to a report. The demonstration that leaked items inflate scores is exactly why the gate must run before training, not after.
???

??? sol | B1 · Exact matches miss near-copies
A 9-point jump on a broad knowledge benchmark from support tickets is implausible on its own, and exact matching misses test questions that were reformatted, renumbered or lightly edited. Run near-duplicate detection with MinHash over shingles, check the answer options as well as the questions, and re-evaluate on a held-out set built after the data was collected.
???
