@@top The problem
:::plain In plain words first
Before support tickets or notes go to a model, emails, IP addresses and internal case numbers should come out. A redaction step sounds simple: find them and replace them. The details are where data leaks: two matches that overlap, a receipt that stores the very value it removed, offsets that drift after the first replacement.

This project builds a bounded redaction gate. It detects a small, stated set of patterns (emails, valid IPv4 addresses, literal strings you supply) as character spans, merges overlapping spans into one, replaces each with `[REDACTED]` using offsets from the original text, and writes a receipt that records where and what kind, but never the value.
:::
@@

@@end Step 2 · Merge complete overlap unions
:::visual Overlapping spans become one
```python run
text = "Mail ops-ORCHARD-482@example.test now"
spans = [(5, 33, "EMAIL"), (9, 20, "LITERAL")]          # the literal sits inside the email
merged = []
for s, e, k in sorted(spans):
    if merged and s < merged[-1][1]:                     # intersects the previous span
        ps, pe, kinds = merged[-1]; merged[-1] = (ps, max(pe, e), sorted(set(kinds) | {k}))
    else: merged.append((s, e, [k]))
out, pos = "", 0
for s, e, kinds in merged: out += text[pos:s] + "[REDACTED]"; pos = e
print(merged); print(out + text[pos:])
```
:::

:::read
The literal `ORCHARD-482` sits inside the email address. Replacing them separately could leave fragments ("ops-" and "@example.test") or shift offsets for the second replacement. Merging them into one span with both kinds removes the whole address in one step. Spans that only touch (one ends where the next starts) stay separate, so the receipt still counts them as two.
:::
@@

@@end Step 3 · Replace spans without leaking source values
:::check
Which statements are right?

- ✓ The receipt records offsets and kinds, never the redacted text.
- ✗ Any four dot-separated numbers are an IPv4 address.
  `999.1.1.1` is not; the detector validates with `ipaddress`.
- ✓ Offsets in the receipt refer to the original text, not the redacted one.
- ✗ This gate removes all personal data.
  It removes the stated patterns; names, addresses and free-text details pass through, and the receipt says so.
:::

:::recap What to keep from this project
- Detect a stated set of patterns as spans; validate structured ones.
- Merge intersecting spans before replacing.
- Replace using original offsets, left to right.
- Receipts record where and what kind, never the value.
- Say clearly what the gate does not catch.
:::

@@end Exercises
1. Why are adjacent spans not merged?
2. How would you add phone numbers without making false positives worse?
3. What should happen when a record has more than ten thousand characters of matches?

## Solutions

??? sol | 1. Adjacent spans
They are separate values that happen to touch, for example an email immediately followed by an IP. Keeping them separate keeps the receipt's counts accurate; merging is only needed when a character belongs to both.
???

??? sol | 2. Phone numbers
Add a narrow pattern for the formats you actually see (with country code, for example), validate digits and length, and measure on labelled samples how many order numbers or dates it wrongly catches before enabling it.
???

??? sol | 3. A huge record
Reject it with a clear error instead of processing it partially; the gate's limits exist so a single pathological record cannot exhaust memory or produce a receipt nobody can review.
???

??? sol | B1 · An audit log of secrets
The email address, into the very system it was being kept from. The receipt here stores only offsets, kinds and counts, which is enough to audit the redaction without holding the value.
???
