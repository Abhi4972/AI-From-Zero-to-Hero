@@top The problem
:::plain In plain words first
**Quantization** stores a model's numbers with fewer bits: 8 or 4 instead of 16. Fewer bits mean a smaller model, less memory to read for each token and so faster generation, at some cost in accuracy. There are several formats, each made for a different place. **GGUF** files are for laptops and CPUs (llama.cpp, Ollama). **AWQ** and **GPTQ** are 4-bit formats for GPU servers; they look at sample data (a **calibration set**) to decide which weights matter most. **FP8** is an 8-bit format that newer NVIDIA GPUs run natively, with almost no quality loss. **NVFP4** and **MXFP4** are 4-bit formats for Blackwell GPUs. Two traps catch most teams: quantizing the weights does not shrink the KV cache, and 4-bit models lose more on reasoning tasks than on chat.
:::

@@end Idea 10 · 2026 picking guide
:::worked Does a 4-bit 70B model fit on one H100?
Llama-style 70B: 80 layers, 8 KV heads of size 128. Serve 128 users with 2,048 tokens each.

1. Weights in AWQ INT4: 70B × 0.5 bytes = 35 GB.
2. KV cache per token in BF16: 2 × 80 × 8 × 128 × 2 bytes ≈ 0.33 MB. For 128 × 2,048 = 262,144 tokens: about 86 GB.
3. Total with a few GB of activations: about 125 GB. It does not fit on an 80 GB H100, even though the weights alone use less than half of it.
4. With an FP8 KV cache the KV halves to about 43 GB: total about 82 GB, still just over. Cut concurrency to about 100, or use an H200 (141 GB).

The lesson's figure of "~20 GB of KV" is too low for this shape; do this arithmetic for your own model before choosing hardware.
:::

:::check
Which statements are right?

- ✓ Quantizing weights to 4 bits leaves the KV cache at its own precision.
- ✗ AWQ calibrated on web text works just as well for a code model.
  The calibration set decides which weights get protected; calibrate on in-domain samples.
- ✓ GPTQ with Marlin kernels is the usual choice when serving one base model with many LoRA adapters.
- ✗ NVFP4 is the safe default for reasoning models.
  FP8 is; 4-bit formats lose several points on maths and long code.
:::

:::predict
Before running the code below: for the 70B model at 128 users × 2,048 tokens, which is larger, the AWQ weights or the BF16 KV cache, and by how much?
:::

:::visual Weights against KV cache
```python run
LAYERS, KV_HEADS, HEAD = 80, 8, 128
kv_per_token = lambda bytes_per: 2 * LAYERS * KV_HEADS * HEAD * bytes_per

for users, ctx in ((32, 2048), (128, 2048), (128, 8192)):
    tokens = users * ctx
    kv16, kv8 = tokens * kv_per_token(2) / 1e9, tokens * kv_per_token(1) / 1e9
    print(f"{users:4d} users x {ctx:5d} ctx: weights AWQ 35 GB | KV BF16 {kv16:6.1f} GB | KV FP8 {kv8:6.1f} GB")
```
:::

:::read
At 128 users and 2,048 tokens the BF16 KV cache, about 86 GB, is more than twice the 4-bit weights. At 8,192 tokens it reaches about 344 GB. Past a few dozen concurrent users, the KV cache, not the weights, decides how many GPUs you need, which is why FP8 KV is often worth more than squeezing weights from 8 to 4 bits.
:::

## Solutions

??? sol | P1 · Where KV dominates
In `code/main.py`, the 7B model at 128 users × 2k context already has 21.7 GB of KV against 3.5 GB of 4-bit weights, and the 70B at 256 users × 8k context has about 550 GB of BF16 KV against 35–140 GB of weights. Above a few dozen users, compressing the KV cache (FP8) saves more than compressing weights further.
???

??? sol | B1 · Calibrating on the wrong data
AWQ chooses which roughly 1% of weights to protect by looking at the activations the calibration text produces. WikiText activates the weights prose needs, not the ones code needs, so code-critical weights get rounded hardest. Re-quantize with a few hundred samples of real code prompts as calibration data, then re-run HumanEval; if the gap stays, ship FP8.
???
