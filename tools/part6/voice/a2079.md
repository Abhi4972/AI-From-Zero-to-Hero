@@top The problem
:::plain In plain words first
"Self-improving" agents are an attractive idea and an easy way to fool yourself: an agent that edits its own rules until its test score goes up has simply learned its test. This project builds a self-improving skill with the limits that make it honest.

The skill is a transparent router: an ordered list of word rules mapping support messages to a team. Labelled cases are split into development and holdout sets by a hash of their ids, with the split audited for leaks. New rules are proposed only from mistakes on the development set, and only for words that point to one label. A candidate is promoted only if it improves the untouched holdout without breaking a case that used to be right, and even then promotion waits for a person.
:::
@@

@@end Step 3 · Propose rules from development errors only
:::visual Proposing rules from mistakes
```python run
from collections import defaultdict
dev = [("invoice charged twice", "billing"), ("invoice refund pending", "billing"),
       ("password reset link expired", "access"), ("password reset email missing", "access"),
       ("email address changed", "account")]
rules = []                                                     # start empty: every case is a mistake
def route(text): return next((lab for terms, lab in rules if all(t in text.split() for t in terms)), None)
errors = [(t, lab) for t, lab in dev if route(t) != lab]
labels_of = defaultdict(set)
for t, lab in errors:
    for w in t.split(): labels_of[w].add(lab)
counts = defaultdict(int)
for t, lab in errors:
    for w in set(t.split()): counts[(w, lab)] += 1
proposals = sorted({(w, lab) for (w, lab), n in counts.items() if n >= 2 and len(labels_of[w]) == 1})
print("proposed:", proposals)
print("rejected (word points to two labels):", sorted(w for w, labs in labels_of.items() if len(labs) > 1))
```
:::

:::read
"invoice" appears in two billing mistakes and nowhere else, so it is proposed for billing; "password" and "reset" for access. "email" appears in an access message and an account message, so it points to two labels and is rejected: a rule built on it would route one of them wrongly. Proposals come only from development errors; the holdout is never looked at while proposing.
:::

@@end Step 4 · Require a separate gate before promotion
:::check
Which statements are right?

- ✓ The holdout is used only to judge a candidate, never to propose rules.
- ✗ A candidate that fixes three cases and breaks one previously correct case is promoted, because the net gain is positive.
  Any regression on a previously correct case blocks promotion.
- ✓ The development/holdout split is audited for content and group leaks.
- ✗ Passing the gate promotes the rule automatically.
  Promotion is a separate decision, after inspecting the candidate's digest.
:::

@@before Build it on your machine
:::broken
An agent improves its prompt by trying variations and keeping whichever scores best on a fixed set of 50 test questions, for 200 rounds. Its score climbs from 70 to 94 percent. On new questions it scores 68. What went wrong, and which two rules here prevent it? (Solution B1.)
:::

:::recap What to keep from this project
- Split by stable id hashing and audit the split for leaks.
- Use transparent, ordered rules you can read.
- Propose only from development errors; reject ambiguous evidence.
- Gate on an untouched holdout with zero regressions.
- Keep promotion a separate human decision.
:::

@@end Exercises

## Solutions

??? sol | 1. One thread, two messages
No. Messages from one customer thread share wording and context, so putting one in development and one in holdout leaks information. Group them (by thread) and split by group, which the split auditor checks.
???

??? sol | 2. A broad rule first
Rules are tried in order, so a broad early rule (`reset → access`) captures messages a later, precise rule (`reset invoice → billing`) was meant for. Order precise rules first, and add a test case for each shadowing you fix.
???

??? sol | 3. Repeated copies
Copies of one message would count as several errors and push its words over the proposal threshold, creating rules from what is really one example. Deduplicate before counting.
???

??? sol | 4. Freezing the next holdout
Before editing again, draw a fresh holdout (new ids, never seen during development), record its hash and the audit file, and do not open it until the next candidate is ready.
???

??? sol | B1 · Learning the test set
It overfitted the 50 questions by trying 200 variations against them. Proposing changes only from development errors and judging them on an untouched holdout (refreshed after use) prevents tuning to the test.
???
