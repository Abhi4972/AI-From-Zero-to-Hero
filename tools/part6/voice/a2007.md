@@top The problem
:::plain In plain words first
You reword a prompt to fix one complaint, and something else quietly breaks: the answer stops being valid JSON, or starts leaking a secret. Averages hide it, because the fix and the breakage cancel out.

This project is a small test suite for prompts. Each case has an id, a prompt and literal checks ("contains `source:`", "excludes `API_KEY`", "is valid JSON"). Replies are recorded once and replayed, so scoring needs no model and gives the same answer every time. Two revisions are compared case by case, and a release gate blocks the change if too few cases pass or if any case that used to pass now fails.
:::
@@

@@end Step 3 · Compare the same cases across revisions
:::worked Pairing beats averaging
| Case | Before | After | State |
|---|---|---|---|
| format | pass | fail | regressed |
| source | fail | pass | improved |
| secret | pass | pass | stable pass |

Both revisions pass 2 of 3 cases, so the pass rate is the same, 0.67. Only pairing by case id shows that the change traded a working JSON format for a citation. The gate counts regressions separately for exactly this reason.
:::

:::check
Which statements are right?

- ✓ A missing recorded reply counts as a failure, not as "skipped".
- ✗ Lowercasing replies before an `excludes` check makes it stricter.
  It changes the check: `excludes API_KEY` would now also reject `api_key`. Make such changes explicit as a separate check.
- ✓ An empty suite fails the gate; zero evidence is not zero failures.
- ✗ A release with a higher pass rate is always safe to ship.
  A higher rate can still contain a regression on a case that matters.
:::

@@before Build it on your machine
:::broken
A team sets the gate to "pass rate ≥ 0.6, any number of regressions". A change that leaks an API key in one case and fixes two formatting cases ships. What should the regression budget have been, and why? (Solution B1.)

:::recap What to keep from this project
- Validate cases first: unique ids, known check types.
- Record replies once, replay them for scoring.
- Compare revisions case by case; count regressions separately.
- Gate on a pass-rate floor and a regression budget, and fail closed when empty.
- Hash the cases and templates so the comparison can be proven later.
:::

@@end Exercises

## Solutions

??? sol | 1. A new template hash
The template hash is part of the record of what was tested. If you change the wording, the old recordings were made with a different prompt, so their hash must stop matching; otherwise you would compare new wording against old behaviour without noticing.
???

??? sol | 2. Lowercasing before excludes
Yes. `excludes API_KEY` checks for that exact text. Lowercasing makes it also reject `api_key`, which is a different, stricter contract. If you want it, add it as its own check so both results are visible.
???

??? sol | 3. Explaining a flat pass rate
Show the paired table: which case regressed, which improved, and what the regressed case protects (here, the JSON that their code parses). A flat average is not "no change"; it can be one break and one fix.
???

??? sol | 4. A check from an incident
Add a case that reproduces the incident's prompt with a check for the exact failure (for example `excludes` the leaked value). Record the reply, and store where it came from (incident id, date, model and settings) next to it, so the case can be re-recorded honestly later.
???

??? sol | B1 · A leak that shipped
The regression budget should be 0 for safety-relevant cases (and usually for all cases). Two fixes do not cancel a leak; a pass-rate floor alone lets them.
???
