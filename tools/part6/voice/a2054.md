@@top The problem
:::plain In plain words first
Agents forget everything between sessions unless something stores it. A shared memory server is that something, and it needs to be more careful than a key-value store: every memory should carry where it came from, two agents updating the same memory at once must not silently overwrite each other, and history should show what a memory used to say.

This project builds one. Memories hold an id, a namespace, text and a source locator. Writes are revisioned: an update names the revision it expects, and stale writers are rejected. Search combines word coverage with vector similarity computed by a small Rust process. The same operations are offered over REST and as MCP tools, behind a bearer token.
:::
@@

@@end Step 2 · Serialize revisioned writes
:::visual Optimistic concurrency with revisions
```python run
store = {"cache-policy": {"rev": 1, "text": "Cache entries expire after sixty seconds."}}
log = []
def update(mid, expected_rev, text):
    cur = store[mid]
    if cur["rev"] != expected_rev:
        return f"rejected: expected revision {expected_rev}, current is {cur['rev']}"
    log.append((mid, cur["rev"] + 1, text))                 # append to the log first, then change memory
    store[mid] = {"rev": cur["rev"] + 1, "text": text}
    return f"ok: now revision {store[mid]['rev']}"
print("agent A:", update("cache-policy", 1, "Cache entries expire after ninety seconds."))
print("agent B:", update("cache-policy", 1, "Cache entries expire after thirty seconds."))
print(store["cache-policy"])
```
:::

:::read
Both agents read revision 1. Agent A's update succeeds and creates revision 2. Agent B's update still says "I expect revision 1" and is rejected, instead of silently replacing A's change. B must re-read, see what A wrote, and decide. Appending to the log before changing the in-memory copy means a crash can never leave memory ahead of the log.
:::

Which statements are right?

  It is a deterministic projection of words; it captures overlap, not meaning.
- ✓ A tool failure inside an MCP call is reported with `isError` in a successful JSON-RPC response.
- ✗ An update without an expected revision should be applied as the latest write.

:::recap What to keep from this project
- Keep id, namespace, text and source together.
- Revisioned writes: name the expected revision; reject stale writers.
- Append to the log before changing memory.
- Search with explained scores; know what the vector does and does not capture.
- One boundary for REST and MCP, behind authentication.
:::

@@end Exercises
1. Why does the log make the server recoverable after a crash?
2. How would you delete a memory without losing its history?
3. What changes if two server processes write to the same log?

## Solutions

??? sol | 1. Recovery from the log
Every change was appended before it took effect, so replaying the log rebuilds exactly the state that was acknowledged. The in-memory map is just a cache of the log.
???

??? sol | 2. Deleting with history
Append a deletion event (a tombstone) with its revision and source. Searches skip deleted memories, and the history still shows what existed and when it was removed.
???

??? sol | 3. Two writers
The single-process lock no longer serializes writes. You need a file lock around append-and-check or a database with transactions; otherwise two processes can both pass the revision check.
???

??? sol | B1 · A memory without a source
The source locator and revision. A later reader could have seen where "3 pm" came from and how old it was, and checked or discarded it instead of repeating it.
???
