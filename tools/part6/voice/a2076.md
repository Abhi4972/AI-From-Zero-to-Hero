@@top The problem
:::plain In plain words first
A browser agent fills forms and clicks buttons for you. To be trustworthy it must choose actions only from what is really on the page, stop when it is done or stuck rather than looping, and prove the result with something other than its own word.

This project builds one in TypeScript and Python. It reads the page as structured observations (labels, values, disabled states, stable ids) and chooses one constrained action at a time. It observes after every action and stops on completion, a repeated state, a policy block or an exhausted budget. A separate Python checker reads the final screenshot's PNG bytes itself and counts green pixels as independent evidence of success. Finally it drives a real browser against a local fixture page.
:::
@@

@@end Step 2 · Stop on completion, stalling or budget
:::check
Which statements are right?

- ✓ An action can target only an element that exists in the current observation.
- ✗ If the page looks the same after a click, the agent should click again.
  A repeated state means it is stalled; it stops and reports.
- ✓ Disabled fields are part of the observation and cannot be filled.
- ✗ The agent's "done" action proves the form was saved.
  The screenshot check verifies it independently.
:::
@@

@@end Step 3 · Verify screenshot pixels in Python
:::worked Evidence the agent cannot fake
1. The fixture page turns fully green when the form is saved.
2. After the agent says "done", the driver saves a screenshot.
3. Python reads the file itself: checks the PNG signature and every chunk's length and CRC, decompresses the image data with a size limit, reverses the row filters, and counts pixels that are green.
4. Success requires the green fraction to pass a threshold. The agent's own claim plays no part in this check.
:::

@@before Build it on your machine
:::broken
A browser agent reports "Form submitted successfully" whenever it has clicked the submit button. A validation error appeared under the email field and nothing was saved. What independent evidence would have caught it? (Solution B1.)
:::

:::recap What to keep from this project
- Observe the page as structured data; act only on what exists.
- Observe after every action; stop on completion, stall, block or budget.
- Verify outcomes with evidence the agent cannot produce itself.
- Parse files defensively (PNG chunks, CRCs, size limits).
- Score runs against a fixture before real sites.
:::

@@end Exercises
1. Why use stable element ids rather than screen coordinates for actions?
2. How would you detect a stall when a spinner animates but nothing loads?
3. What would you check after submitting a real form instead of green pixels?

## Solutions

??? sol | 1. Ids over coordinates
Ids name the element whatever the window size, zoom or layout; coordinates break when anything moves. Observations with ids also let the policy reason about what an action targets.
???

??? sol | 2. A spinning stall
Compare structured observations, not pixels: if the form's fields, values and enabled states have not changed for N observations, the agent is stalled even if an animation keeps changing the picture.
???

??? sol | 3. Real-form evidence
A confirmation element with known text, the saved record visible on a following page, or a server-side check (the record exists through an API), never the agent's own summary.
???

??? sol | B1 · Claimed success
An observation after the click showing a confirmation (or the absence of error messages), or a verified screenshot of the success state. The validation error would have appeared in the observation and stopped the run.
???
