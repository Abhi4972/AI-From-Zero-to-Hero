@@top The problem
:::plain In plain words first
A training run reads tokens very fast, from many worker processes at once, so the tokenized corpus needs a layout that supports cheap random slices. **HDF5** can store one long, **resizable**, **chunked** array of token ids per shard: the file is divided into fixed-size chunks, and reading a slice touches only the chunks it overlaps. The write side must be careful: tokenize documents incrementally, buffer them, and append whole chunks at a time (one tiny append per document fragments the file), writing several **shards** with a recorded hash each so a crash loses at most one shard. The read side is a **sliding-window** loader that cuts fixed-length training windows out of the global token stream across shard boundaries.
:::

@@end Idea 4 · Sliding-window dataloader
:::worked Chunks touched by one window
Chunk size 4,096 tokens. A training window needs 2,049 tokens starting at global position 10,000.

1. The window covers positions 10,000 to 12,048.
2. Chunk numbers: 10,000 ÷ 4,096 = 2.44, so chunk 2; 12,048 ÷ 4,096 = 2.94, chunk 2. One chunk read.
3. A window starting at 11,500 covers 11,500 to 13,548: chunks 2 and 3, so two reads for the same amount of data.
4. When windows are much smaller than chunks, most reads touch one chunk; when chunks are smaller than windows, every read touches several. Matching chunk size to window size keeps reads cheap.
:::

:::check
Which statements are right?

- ✓ Reading a slice touches only the chunks it overlaps.
- ✗ Appending one document at a time is the safest way to write.
  It fragments the file; buffer and append in chunk-sized pieces.
- ✓ Shards with recorded hashes can be validated before training.
- ✗ Windows must stay inside one shard.
  The loader maps global positions to shards and can cross a boundary.
:::

:::predict
Before running the code below: with windows of 2,049 tokens at random starting positions, about what share of windows touch two chunks when chunks are 4,096 tokens? And when chunks are 2,048?
:::

:::visual How chunk size affects reads
```python run
import random
random.seed(5)
def chunks_touched(start, length, chunk): return (start + length - 1) // chunk - start // chunk + 1
W, N = 2049, 1_000_000
for chunk in (1024, 2048, 4096, 16384):
    reads = [chunks_touched(random.randrange(N - W), W, chunk) for _ in range(20000)]
    print(f"chunk {chunk:6d}: mean chunks per window {sum(reads) / len(reads):.2f}, max {max(reads)}")
```
:::

:::read
With 4,096-token chunks, a 2,049-token window touches 1.5 chunks on average (about half the windows cross a boundary); with 2,048-token chunks every window touches exactly 2; with 16,384 it is close to 1. Bigger chunks mean fewer reads per window but more unused data per read and worse behaviour for small random reads, which is why Exercise 4 asks you to measure the page-cache effect rather than guess.
:::

@@before Ship it
:::read
The demo writes two shards of 6,456 tokens each, records a hash and global start offset for each, validates them, and then draws ten batches of shape (4, 64). Notice that both shards have the *same* hash: the demo corpus is the same text written twice, so their tokens are identical. In a real pipeline, two identical shard hashes would be a red flag for duplicated input, exactly the kind of thing the manifest makes visible.
:::

:::broken
A writer resizes the HDF5 dataset once at the end of each shard and writes all its tokens in one call. A crash during a long shard loses every token written so far for that shard, and the file is left in an inconsistent state. What should the writer do instead? (Solution B1.)
:::

:::recap What to keep from this lesson
- Store tokens as a resizable, chunked integer array per shard.
- Buffer and append chunk-sized pieces; never one document at a time.
- Record each shard's hash and global start; validate before training.
- The loader cuts windows from the global stream, across shards.
- Match chunk size to the window size and measure reads.
:::

## Solutions

??? sol | P3 · A validate mode
Read every shard, recompute the sha256 over its token array, and compare with `shards.json`; also check that each shard's global start equals the previous start plus its token count. Exit non-zero on any mismatch so CI blocks training on corrupt or reordered data.
???

??? sol | B1 · Append and flush in chunks
Append each full buffer (one chunk) as soon as it fills, flush the file, and record progress, so a crash loses at most the unflushed buffer. Write to a temporary file and rename it into place when the shard is complete, and add the shard to the manifest only after its hash is computed.
???
