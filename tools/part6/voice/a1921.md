@@top Why the registry comes before the tool
:::plain In plain words first
A **tool registry** is the harness's single list of tools: each entry has a name, a one-line description for the model, a **schema** describing the arguments, the **handler** function to call, and operational settings such as whether retries are safe and how long to wait. Before any handler runs, the arguments the model produced are **validated** against the schema. When they are wrong, the error says exactly where, as a **JSON pointer** such as `/fields/1`, so the model can fix the call in one try. This lesson implements a small, pure subset of JSON Schema (eight keywords) and makes accidental re-registration an error, because two parts of a codebase silently registering the same tool name is a bug that takes days to find.
:::

@@end What the validator is and is not
:::worked Reading a pointer error
Schema for `db.get_user`: `id` is a required integer; `fields` is an array whose items must be one of `id`, `name`, `email`.

1. The model sends `{"id": 1, "fields": ["id", "phone"]}`.
2. The validator walks the schema: `id` is fine; `fields` is an array; item 0 is in the enum; item 1, `"phone"`, is not.
3. It returns one error: path `/fields/1`, keyword `enum`, message "value 'phone' not in ['id', 'name', 'email']".
4. Shown to the model, that error names the exact element and the allowed values, so the next call can be correct; a stack trace from inside the handler would say nothing that useful.
:::

:::check
Which statements are right?

- ✓ Validation runs before the handler, so handlers can assume well-shaped arguments.
- ✗ The validator should coerce `"42"` into `42` to be helpful.
  Silent coercion hides model mistakes; it reports a type error instead.
- ✓ Re-registering a name without `override=True` raises an error.
- ✗ Passing validation makes a call safe.
  Validation checks shape; timeouts, sandboxes and policy handle safety.
:::

:::visual A tiny recursive validator with pointer paths
```python run
def validate(value, schema, path=""):
    t = schema.get("type")
    kinds = {"object": dict, "array": list, "string": str, "integer": int}
    if t and not (isinstance(value, kinds[t]) and not (t == "integer" and isinstance(value, bool))):
        return [f"{path or '/'}: expected {t}, got {type(value).__name__}"]
    errors = []
    if t == "object":
        for name in schema.get("required", []):
            if name not in value: errors.append(f"{path}/{name}: missing required property")
        for name, sub in schema.get("properties", {}).items():
            if name in value: errors += validate(value[name], sub, f"{path}/{name}")
    if t == "array":
        for i, item in enumerate(value):
            errors += validate(item, schema.get("items", {}), f"{path}/{i}")
    return errors

schema = {"type": "object", "required": ["user"], "properties": {
    "user": {"type": "object", "properties": {"tags": {"type": "array", "items": {"type": "string"}}}}}}
for args in ({"user": {"tags": ["a", "b"]}}, {"user": {"tags": ["a", 7]}}, {}, {"user": {"tags": True}}):
    print(args, "->", validate(args, schema) or "ok")
```
:::

:::read
Each error carries the exact location: `/user/tags/1` for the integer inside the list, `/user` for the missing property, `/user/tags` for a boolean where a list should be. The path is built as the validator descends, one segment per property or index, which is all a JSON pointer is. Twenty lines cover the common cases; the lesson's version adds `enum`, string lengths and patterns.
:::

@@before Going further
:::read
The demo registers `db.get_user` and validates four argument sets. The first passes. The others each fail with one precise error: `/id` has the wrong type (a string instead of an integer); `/id` is missing; and `/fields/1` is not an allowed value. Each message names the keyword that failed, which is the information a model needs to repair its call.
:::

:::broken
A team's registry silently replaces a tool when the same name is registered twice. A plugin loads late and registers its own `files.delete` with a different schema and handler. What happens, and what would have prevented it? (Solution B1.)
:::

:::recap What to keep from this lesson
- One registry: name, description, schema, handler, retry and timeout settings.
- Validate before calling; never coerce silently.
- Errors carry JSON pointer paths and the failing keyword.
- Re-registration requires an explicit override.
- Keep the validator pure so it can be re-run on replay logs.
:::

## Solutions

??? sol | B1 · Silent override
Every later call to `files.delete` now runs the plugin's handler with the plugin's argument rules, and nothing in the logs says the tool changed; behaviour depends on load order. Rejecting re-registration by default turns that into an error at startup, and an explicit `override=True` makes intended replacements visible in code review.
