@@top The situation
:::plain In plain words first
A nightly agent job calls the same tool five times and stops. In a run nobody watches, a tool that needs permission asks, nobody answers, the ask becomes a rejection, and the model simply tries again. The repeat limit did its job by ending the loop. The case trains reading the loop as a permission problem, not raising the limit.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ In a headless run, every permission prompt becomes a rejection.
- ✗ Raising the repeat limit fixes the job.
  The model would repeat the rejected call more times; the missing permission remains.
- ✓ An explicit allow pattern for the background-agent tool lets the job run unattended.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Headless runs need explicit permissions for every tool they use.
- A repeated identical call often means a rejected one.
- Loop limits are a safety net, not a fix.
- Change one thing (the message) and check what it affects.
:::
@@
