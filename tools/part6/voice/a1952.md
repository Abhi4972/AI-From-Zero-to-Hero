@@top Why a subprocess
:::plain In plain words first
The research agent's experiments must be measured honestly and must not be able to damage the agent itself. So each experiment runs in a separate **subprocess** from an **ExperimentSpec**: the script, its parameters, a seed, a wall-clock limit and a memory cap. The runner captures **stdout and stderr**, reads metrics the script prints as JSON lines (intermediate ones while it runs, a final one at the end), records exit status, wall time and peak memory, and returns a structured result. Running the same spec with different settings produces an **ablation table**; running it twice with the same seed must produce identical metrics (**determinism**). The experiment here is a tiny mock training script.
:::

@@end Result shape
:::worked Classifying how a run ended
Four runs of the same spec.

1. Exit code 0, final metrics line present: `ok`.
2. Killed at the 30-second limit: `timeout`. Its last intermediate metrics are kept but not treated as final.
3. Exit code 1 with a traceback on stderr: `error`. The stderr tail goes into the result for debugging.
4. Exit code 0 but no final metrics line: also an error, because "it finished" is not "it measured something". Distinguishing these cases is what lets the evaluator trust every `ok`.
:::

:::check
Which statements are right?

- ✓ A subprocess crash cannot take the agent process down with it.
- ✗ A zero exit code means the experiment produced valid metrics.
  The final metrics line must also be present and parse.
- ✓ The same spec and seed must give identical metrics.
- ✗ A soft memory cap guarantees the process cannot use more memory.
  It is a check on measured usage; hard limits need OS controls.
:::

:::visual Parsing metrics from a subprocess
```python run
import json, subprocess, sys
script = r'''
import json, sys
print(json.dumps({"step": 0, "loss": 4.9}))
print(json.dumps({"step": 1, "loss": 4.4}))
print("warning: something harmless")
print(json.dumps({"final_loss": 4.0, "perplexity": 54.6}))
print("progress chatter", file=sys.stderr)
'''
proc = subprocess.run([sys.executable, "-c", script], capture_output=True, text=True, timeout=10)
records = []
for line in proc.stdout.splitlines():
    try: records.append(json.loads(line))
    except json.JSONDecodeError: pass
final = records[-1] if records and "final_loss" in records[-1] else None
print("exit code   :", proc.returncode)
print("intermediate:", [r for r in records if r is not final])
print("final       :", final)
print("stderr tail :", proc.stderr.strip())
```
:::

:::read
The two step lines are intermediate metrics; the last JSON line, which carries `final_loss`, is the final record; the warning line is skipped because it is not JSON; and stderr is kept separately. This is the runner's contract in miniature: structured lines are data, everything else is log. (The lesson's runner launches script files rather than `-c` strings, which the sandbox from Lesson 19.26 would refuse.)
:::

:::read
The base run exits 0 in about 0.1 seconds, peaks near 21 MB of memory, and reports four intermediate steps with loss falling from 4.98 to 3.60 and a final perplexity of 36.7; the stdout tail shows the raw JSON lines the metrics were parsed from. The rest of the output (an ablation over the spec's parameters) follows the same structure, so the evaluator in the next lesson can compare runs field by field.

:::broken
An experiment runner calls the experiment function directly in the agent's process "to save the subprocess overhead". One generated experiment calls `os._exit(0)` and another leaks memory until the machine swaps. What is lost? (Solution B1.)
:::

:::recap What to keep from this lesson
- One subprocess per experiment, from a written spec.
- Enforce wall-clock limits; check memory.
- Metrics are JSON lines; the last one carrying final fields is the result.
- Classify ok, timeout and error, and keep stderr tails.
- Same spec and seed, same metrics.
:::

## Solutions

??? sol | B1 · No process boundary
`os._exit(0)` ends the whole agent, not just the experiment, and a memory leak in the same process degrades the agent and every later experiment. A separate process gives isolation, a clean way to kill on timeout, and accurate per-experiment memory and time measurements; the overhead is small next to any real experiment.
