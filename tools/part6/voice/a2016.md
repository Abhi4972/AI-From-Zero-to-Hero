@@top The problem
:::plain In plain words first
Release notes are often written from memory the night before a release. This project writes them from the Git history instead, if the team uses Conventional Commits: subjects like `feat(api): add search` or `fix!: change the default`.

The care is in the details. A commit body is not a list of commits, so it must be parsed by explicit separators. `!` or a `BREAKING CHANGE:` footer must put a commit under "Breaking changes", whatever its type. Merge commits and plain prose are kept as "Other" rather than dropped. The output must be the same whatever order the records arrive in, must escape anything that could become a Markdown link, and must say exactly which revision range it came from.
:::
@@

@@end Step 2 · Classify conventional subjects
:::visual Parsing a conventional subject
```python run
import re
PAT = re.compile(r"^(?P<type>[a-z]+)(?:\((?P<scope>[^)]+)\))?(?P<bang>!)?: (?P<desc>.+)$")
for subject in ["feat(api)!: remove v1", "fix: preserve citation offsets",
                "Merge branch 'main' into docs", "feat:missing space"]:
    m = PAT.match(subject)
    print(f"{subject!r:34} ->", {k: v for k, v in m.groupdict().items() if v} if m else "Other")
```
:::

:::read
The grammar is small: type, optional scope in brackets, optional `!`, then colon and space. `feat(api)!` is parsed with its breaking mark, which later puts it under Breaking changes. The merge commit does not match and becomes Other, kept for the release editor rather than dropped. `feat:missing space` is not conventional (no space after the colon), so it is Other too: being strict here avoids guessing what an author meant.
:::
@@

@@end Step 3 · Group commits with stable ordering
:::check
Which statements are right?

- ✓ A `fix` with a `BREAKING CHANGE:` footer goes under Breaking changes.
- ✗ Splitting `git log` output on newlines gives one commit per line.
  Bodies have many lines; records need explicit separators (NUL bytes here).
- ✓ Sorting inside each group makes the notes independent of input order.
- ✗ A commit subject can be pasted into Markdown as it is.
  Brackets and parentheses can form links; the renderer escapes them.
:::

The fix appears under "Breaking changes", not "Fixes": the footer outranks the type. The feature is under "Features". The footer text is repeated under "Migration and revert review" with its commit hash, because a reader upgrading needs that sentence more than the subject. @@before Build it on your machine
:::broken
A generator classifies by type only. A `fix:` commit that removes a configuration option, with a `BREAKING CHANGE:` footer, is listed under Fixes. Users upgrade and their deployments fail. What did the generator ignore? (Solution B1.)
:::

:::recap What to keep from this project
- Parse records by explicit separators; bodies are multi-line.
- Classify with a small strict grammar; keep everything else as Other.
- Breaking takes precedence over type; surface migration footers.
- Sort within groups so the output is reproducible.
- Escape Markdown and record the exact source range and hash.
:::

@@end Exercises
1. Two runs over the same range produce different notes. What would you check first?
2. How should a `revert:` commit that reverts a feature in the same range appear?
3. Why resolve branch names to commit ids before reading the range?

## Solutions

??? sol | 1. Different notes from the same range
Compare the receipts: the resolved commit ids and the export hash. If they differ, the range moved (for example a branch name pointed elsewhere). If they match, the output depends on input order, which the per-group sort should have removed.
???

??? sol | 2. A revert inside the range
List it under the migration and revert review with the commit it reverts, and do not show the reverted feature as shipped. Whether to drop both lines entirely is an editorial choice; the receipt should make it visible either way.
???

??? sol | 3. Resolving names first
Branch and tag names move. Resolving them to immutable commit ids at the start pins the range, so the notes and their receipt describe exactly what was read even if someone pushes during the run.
???

??? sol | B1 · A breaking fix filed as a fix
The `BREAKING CHANGE:` footer. Breaking behaviour takes precedence over the type, and the footer's text belongs in the migration section where upgraders will see it.
???
