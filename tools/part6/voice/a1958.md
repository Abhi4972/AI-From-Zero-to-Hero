@@top The problem
:::plain In plain words first
A vision transformer needs image "tokens" the way a language model needs word tokens. **Patch embedding** makes them: cut the image into a grid of squares (16 × 16 pixels for a 224 × 224 image gives a 14 × 14 grid, 196 **patches**), flatten each square, and map it to a vector with one shared linear layer. In code this is usually a **Conv2d** whose kernel size and stride both equal the patch size, which computes exactly the same thing faster. A learned **CLS token** is put in front to collect a summary of the whole image, and a **2D position embedding** is added so the model knows where each patch came from. The lesson proves the convolution and the flatten-then-linear versions agree, which is the kind of equivalence check worth writing for every shortcut.
:::
@@

@@end Idea 5 · Equivalence as a sanity check
:::worked Counting tokens and parameters
Image 224 × 224 × 3, patch 16, width 768.

1. Grid: 224 / 16 = 14 per side, so 196 patches; with the CLS token the sequence is 197.
2. Each patch flattens to 16 × 16 × 3 = 768 numbers.
3. The projection is 768 → 768: 768 × 768 = 589,824 weights plus 768 biases = 590,592; the CLS token adds 768 more: 591,360 parameters in the front end.
4. A fixed sinusoidal position table adds none. Halve the patch size to 8 and the sequence grows to 785 tokens, quadrupling attention's cost, which is why patch size is a speed–detail trade-off.
:::

:::check
Which statements are right?

- ✓ A Conv2d with kernel and stride equal to the patch size equals flatten-then-linear.
- ✗ Smaller patches make the transformer cheaper.
  They make more tokens, and attention cost grows with the square of the count.
- ✓ The CLS token is prepended and gathers a whole-image summary.
- ✗ Without position embeddings the model still knows the patch layout.
  Attention ignores order; positions must be added.
:::

:::predict
Before running the code below: for images of 224, 384 and 512 pixels with patch sizes 16 and 32, how many tokens (including CLS) does each produce?
:::

:::visual Tokens per image
```python run
for size in (224, 384, 512):
    for patch in (16, 32):
        n = (size // patch) ** 2
        print(f"image {size}px, patch {patch}: grid {size // patch}x{size // patch} = {n:4d} patches, {n + 1:4d} tokens, attention pairs {(n + 1) ** 2:>9,}")
```
:::

:::read
At 224 pixels with 16-pixel patches the model handles 197 tokens and about 39,000 attention pairs; at 512 pixels the same patch size gives 1,025 tokens and over a million pairs, 27 times the attention work for 5 times the pixels. Larger patches cut cost sharply but blur fine detail, the trade-off every vision transformer configuration makes.
:::

@@before Tests
:::read
The front end turns one 224 × 224 image into 197 tokens of width 768 with 591,360 parameters, matching the worked example. The CLS token's norm (0.53) is much smaller than the patch tokens' (about 21–23), since it starts as a small learned vector and gets no position signal. The first patch's position values print as zeros: patch (0, 0) has row and column 0, and the sine half of a sinusoidal table is sin(0) = 0 there, so that is correct rather than a bug. Finally, the convolution and the unfold-plus-linear reference agree to about 3e-6, which is floating-point rounding.
:::

:::broken
A team switches from 224-pixel to 384-pixel images at fine-tuning time but keeps a *learned* position table sized for a 14 × 14 grid. What breaks, and what is the usual fix? (Solution B1.)
:::

:::recap What to keep from this lesson
- Patches are image tokens: cut, flatten, project.
- Conv2d with kernel = stride = patch size is the same projection, faster.
- Prepend a CLS token; add 2D position embeddings.
- Token count grows with the square of image size over patch size.
- Check every shortcut against a slow reference.
:::

## Solutions

??? sol | B1 · A position table for the wrong grid
At 384 pixels the grid is 24 × 24 (576 patches), but the table has only 196 rows, so the shapes do not match. Resize the learned table as a 2D image (interpolate from 14 × 14 to 24 × 24) before fine-tuning, or use a sinusoidal table that can be computed for any grid.
???
