@@top Problem
:::plain In plain words first
Classifiers catch recognizable harms. A **rules engine** enforces a product's own contracts, such as "every refusal must offer a next step" or "code answers must end with a runnable block or a stated assumption". This is the **constitutional** layer: rules live in a reviewed YAML file next to the code, and each has a **name**, a **severity**, an **explanation**, and a predicate in two parts: `applies_when` (is this rule relevant to this response?) and `violation_when` (is it broken?). Some rules come with a **fixer**, a deterministic edit that repairs the draft, which is then re-checked. Because rules are data, they can be reviewed, versioned and tested like code.
:::
@@

@@end Concept
:::worked One rule, end to end
Rule `no-empty-refusal`, severity medium: applies when the response is a refusal; violated when it offers no alternative.

1. Draft: "I can't help with that." The rule applies (it is a refusal) and is violated (no next step).
2. The engine reports: `[medium] no-empty-refusal: Refusals must offer a next step`.
3. The fixer appends a template: "…but I can explain the general principles, or point you to official documentation."
4. The engine re-checks the fixed draft; it passes. Splitting "applies" from "violated" keeps rules from firing on responses they were never meant for, such as a normal answer that happens to say "can't".
:::

:::check
Which statements are right?

- ✓ Each rule has a name, a severity, an explanation and a predicate.
- ✗ A rule that is not violated is not relevant.
  `applies_when` and `violation_when` are separate questions.
- ✓ Fixed drafts are re-checked against all rules.
- ✗ Rules should live in the prompt so the model follows them.
  They live in reviewed files and are enforced on the output.
:::

:::visual A tiny rules engine
```python run
RULES = [{
    "name": "end-with-runnable-or-assumption", "severity": "medium",
    "applies_when": lambda t: "```" in t,
    "violation_when": lambda t: not (t.rstrip().endswith("```") or t.strip().splitlines()[-1].startswith("Assumption:")),
}]
drafts = {
    "ends in code": "Here you go:\n```python\nprint(1)\n```",
    "trails off": "Here you go:\n```python\nprint(1)\n```\nThen run it and see.",
    "states assumption": "```python\nprint(1)\n```\nAssumption: Python 3.10 or newer.",
    "no code": "The answer is 42.",
}
for name, text in drafts.items():
    hits = [r["name"] for r in RULES if r["applies_when"](text) and r["violation_when"](text)]
    applies = any(r["applies_when"](text) for r in RULES)
    print(f"{name:18s} applies={applies!s:5} violations={hits}")
```
:::

:::read
Only the draft that trails off after its code block violates the rule. The draft without code is not even in scope, which is the point of the separate `applies_when`: a rule about code should say nothing about answers that contain none.
:::

@@before Ship it
:::read
Six rules load. Four demo drafts each break one rule (an empty refusal, code without a closing block or assumption, a realistic-looking email in an example, an internal library name), each is reported with its severity and explanation, and each fixer makes two edits after which the draft passes. The clean draft passes untouched. A rule set that can be demonstrated case by case like this can be reviewed by people who do not read the engine's code.
:::

:::broken
A team writes a rule "responses must not mention competitors" with `applies_when: always` and `violation_when: contains any of [list of 400 company names]`. Users asking for general industry comparisons get mangled answers. What would improve the rule? (Solution B1.)
:::

:::recap What to keep from this lesson
- Rules encode product contracts classifiers cannot.
- Each rule: name, severity, explanation, applies_when, violation_when.
- Fixers make deterministic edits; re-check afterwards.
- Keep rules in reviewed, versioned files.
- Scope rules narrowly with `applies_when`.
:::

## Solutions

??? sol | B1 · A rule with no scope
`applies_when: always` puts every response in scope, and a raw name list matches innocent uses (common words that are also company names, legitimate comparisons). Scope the rule to the contexts it is meant for (for example, product recommendations), match names precisely, and measure false positives on a sample of normal answers before enabling a fixer.
