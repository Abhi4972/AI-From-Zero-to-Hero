@@top The problem
:::plain In plain words first
No single number describes a language model, so an **evaluation pipeline** runs several, each on held-out data shaped for it. **Perplexity** measures how well the model predicts text (lower is better). **Exact match** checks whether a short answer equals the reference after normalization (lower case, punctuation removed). **Token F1** gives partial credit for overlapping words in longer answers. An **LLM-as-judge** rates answers from 1 to 5 against a rubric; here it is a local mock so the lesson runs offline. Each score is then **normalized** to 0–1 and combined with **weights** into one aggregate, and the per-task numbers stay visible next to it, because the weights are a product decision, not a fact.
:::
@@

@@end Aggregation
:::math Token F1
With $p$ predicted tokens, $g$ gold tokens and $c$ tokens in common (counting duplicates once each):

$$\text{precision}=\frac{c}{p},\quad \text{recall}=\frac{c}{g},\quad F_1=\frac{2\,\text{precision}\cdot\text{recall}}{\text{precision}+\text{recall}}$$
:::

:::worked Normalizing four scores
Raw results: perplexity 11.3, exact match 0.15, token F1 0.02, judge 1.0 out of 5.

1. Perplexity: $1 / (1 + \ln 11.3) = 1 / 3.43 ≈ 0.29$.
2. Exact match and F1 stay as they are: 0.15 and 0.02.
3. Judge: 1.0 / 5 = 0.20.
4. Weighted with 0.2, 0.3, 0.3, 0.2: 0.2 × 0.29 + 0.3 × 0.15 + 0.3 × 0.02 + 0.2 × 0.20 ≈ 0.15. Note that the judge's *minimum* score still contributes 0.04, because a 1-to-5 scale divided by 5 starts at 0.2, not 0.
:::

:::check
Which statements are right?

- ✓ Exact match normalizes case and punctuation before comparing.
- ✗ Perplexity can be compared across models with different tokenizers.
  It is per token, and tokens differ; compare only with the same tokenizer.
- ✓ Token F1 gives partial credit for overlapping words.
- ✗ The aggregate is the model's objective quality.
  It depends on chosen weights and normalizations; report the parts too.
:::

:::visual Exact match and token F1
```python run
import re
from collections import Counter
def norm(s): return re.sub(r"[^a-z0-9 ]", "", s.lower()).split()
def em(pred, gold): return float(norm(pred) == norm(gold))
def f1(pred, gold):
    p, g = norm(pred), norm(gold)
    common = sum((Counter(p) & Counter(g)).values())
    if not common: return 0.0
    precision, recall = common / len(p), common / len(g)
    return 2 * precision * recall / (precision + recall)

for pred, gold in (("Paris.", "paris"), ("the capital is paris", "Paris"), ("water boils at 100 C", "Water boils at one hundred degrees C")):
    print(f"{pred!r:26s} vs {gold!r:40s} EM {em(pred, gold):.0f}  F1 {f1(pred, gold):.2f}")
```
:::

:::read
"Paris." matches "paris" exactly after normalization. "the capital is paris" fails exact match but gets F1 0.40: full recall, low precision. The boiling-point answer is correct in meaning but shares only four words with the seven-word gold answer, so F1 is about 0.67, the kind of paraphrase where a judge model is more useful than either string metric.
:::

:::read
After five epochs, the tiny model scores perplexity 11.3, exact match 0.15, token F1 0.02 and the minimum judge score of 1, for an aggregate of 0.149. The spot checks show garbled predictions scoring 0, which makes the 0.15 exact match surprising: it comes from other items (presumably very short answers) not shown in the sample. That is a reason to always print per-item results; an aggregate cannot tell you *which* items passed.

A team reports a single aggregate score that rose from 0.61 to 0.66 after a change. On inspection, exact match fell from 0.52 to 0.40 while perplexity improved. What should the report have shown, and why does it matter? (Solution B1.)

:::recap What to keep from this lesson
- Use several metrics; each misses something the others catch.
- Normalize text before exact match; F1 gives partial credit.
- Compare perplexity only with the same tokenizer.
- Normalize, weight and aggregate, but show the parts.
- Inspect per-item results, not just averages.
:::

## Solutions

??? sol | B1 · An aggregate hiding a regression
The report should show every per-task score next to the aggregate, plus per-item diffs for the task that got worse. Here answers got less correct while the model got better at predicting text, which the weighted average turned into an apparent improvement. If correctness matters most for the product, the change is a regression whatever the aggregate says.
