@@top The problem
:::plain In plain words first
An **evaluation harness** runs an agent on a fixed set of **fixture tasks** and checks each result with a **deterministic verifier** instead of a person's glance: does a file now equal the expected content, does it match a pattern, does a test command exit successfully? It runs every task the same way every time and reports per-task results as well as totals: pass rate, latency and cost. Because agents are random, each task can be run **k** times; **pass@k** is the chance that at least one of k attempts passes, which matters when you can afford retries or let a user pick from several answers. A per-task report is what catches a change that helps one task and quietly breaks another.
:::
@@

@@end Why pass@k and not just pass@1
:::math Estimating pass@k
With $n$ attempts of which $c$ passed, the unbiased estimate of pass@k (Chen et al., 2021) is

$$\text{pass@}k = 1-\frac{\binom{n-c}{k}}{\binom{n}{k}}$$

the chance that a random group of $k$ of the $n$ attempts contains at least one pass. The simpler plug-in estimate $1-(1-c/n)^k$ treats the measured rate as exact, and overestimates pass@k when $n$ is small.
:::

:::worked Plug-in against unbiased
A task was attempted $n = 5$ times and passed $c = 2$ times. Estimate pass@3.

1. Plug-in: $p = 0.4$, so $1 - 0.6^3 = 1 - 0.216 = 0.784$.
2. Unbiased: $\binom{3}{3} / \binom{5}{3} = 1/10$, so $1 - 0.1 = 0.9$.
3. They differ by 0.12: the plug-in treats attempts as draws with replacement from an infinite pool, while the unbiased form counts which groups of 3 out of the actual 5 contain a pass.
4. With more attempts ($n$ well above $k$) the two converge; with $n = k$ the unbiased form simply asks "did any attempt pass?".
:::

:::check
Which statements are right?

- ✓ Verifiers are deterministic checks, not model judgements.
- ✗ A higher total pass rate means no task got worse.
  Per-task reports catch regressions that totals hide.
- ✓ The fixture set must stay identical across runs being compared.
- ✗ pass@k equals k times pass@1.
  It is the chance that at least one of k attempts passes.
:::

:::predict
Before running the code below: a task has 10 attempts with 3 passes. Which is larger for k = 5, the plug-in or the unbiased estimate?
:::

:::visual Two estimators of pass@k
```python run
from math import comb
def unbiased(n, c, k): return 1.0 if n - c < k else 1 - comb(n - c, k) / comb(n, k)
def plug_in(n, c, k): return 1 - (1 - c / n) ** k

for n, c in ((5, 2), (10, 3), (100, 30)):
    for k in (1, 3, 5):
        if k <= n: print(f"n={n:3d} c={c:2d} k={k}:  plug-in {plug_in(n, c, k):.3f}   unbiased {unbiased(n, c, k):.3f}")
```
:::

:::read
At k = 1 both agree exactly (the pass rate). For larger k with few attempts, the unbiased estimate is the higher one here: with 10 attempts and 3 passes, pass@5 is 0.917 unbiased against 0.832 plug-in. With 100 attempts the two are within about a percentage point. Report which estimator you used, and use enough attempts that the choice barely matters.
:::

:::recap What to keep from this lesson
- Fixture tasks with deterministic verifiers, run the same way every time.
- Report per task, not only totals.
- Run k attempts; report pass@k with the estimator named.
- Track latency and cost alongside correctness.
- Fail loudly when the task set changes.

## Solutions

??? sol | B1 · A silently shrinking suite
The 82% is over 95 tasks and the 78% over 100, so they are not comparable; if the five skipped tasks were failures, nothing improved. The harness should record the exact list of task ids (or a hash of the fixture set) in every report, refuse to compare runs whose sets differ, and fail when a fixture cannot be loaded rather than skipping it.
