@@top Problem
:::plain In plain words first
An **autonomous research agent** runs the loop of small-scale research on its own: read the literature, propose a hypothesis, write and run an experiment, check the result, and repeat, then write up the best finding and have it reviewed. Systems such as Sakana's AI Scientist do this as a **tree search**: each node is an experiment, each child changes one thing, and a budget decides how far the tree grows. The craft is not in the model but in the infrastructure: cost caps, **sandboxes** so generated code cannot touch the network or the host, checks that results are real, and an honest review step. This capstone keeps experiments small (tiny models, cheap runs) and makes safety part of the grade. Model and product names in the brief are a 2026 snapshot.
:::

@@end Build it
:::worked Best-first search on a budget
Three experiments are waiting, each with a predicted quality and cost; the budget left is $4.

1. Scores (quality per dollar): A 0.8 / $1.50 = 0.53, B 0.9 / $3.00 = 0.30, C 0.6 / $0.80 = 0.75.
2. Best-first takes C first ($0.80, $3.20 left), then A ($1.50, $1.70 left).
3. B no longer fits. Its higher quality was never tested, a deliberate trade: the search spends money where expected value per dollar is highest.
4. Each result updates the tree: if A fails its verification check (loss did not decrease, effect not isolated), its children are never expanded, which saves the rest of the budget.
:::

:::check
Which statements are right?

- ✓ Each child experiment changes one thing, so its effect can be attributed.
- ✗ Sandboxing generated code is optional if the model is well aligned.
  Generated code can be wrong or exploited; isolation is required regardless.
- ✓ A verification step catches runs that crashed or measured nothing.
- ✗ An automated reviewer ensemble proves a paper is correct.
  It filters weak drafts; it cannot replace checking the experiments.
:::

:::predict
Before running the code below: with a $5 budget and eight candidate experiments of random cost and quality, does best-first search by quality per dollar find a better result than trying experiments in random order?
:::

:::visual Best-first against random order
```python run
import random
random.seed(3)
def candidates(n=8):
    return [{"cost": round(random.uniform(0.5, 2.5), 2), "quality": round(random.random(), 2)} for _ in range(n)]

def run(order, budget=5.0):
    spent, best = 0.0, 0.0
    for c in order:
        if spent + c["cost"] > budget: continue
        spent += c["cost"]; best = max(best, c["quality"])
    return best, spent

wins = ties = 0
for trial in range(1000):
    cs = candidates()
    smart, _ = run(sorted(cs, key=lambda c: -c["quality"] / c["cost"]))
    rnd, _ = run(random.sample(cs, len(cs)))
    wins += smart > rnd; ties += smart == rnd
print(f"best-first better in {wins / 10:.1f}% of trials, tied in {ties / 10:.1f}%, worse in {(1000 - wins - ties) / 10:.1f}%")
```
:::

:::read
Ranking by quality per dollar usually finds a result at least as good as random order within the same budget, but not always: it can skip one expensive, excellent experiment in favour of several cheap, decent ones. In the toy, quality is known in advance; in a real agent it is only a prediction, so the search also needs exploration (trying some uncertain nodes) to avoid confidently funding the wrong branch.
:::

@@before Ship it
:::read
The scaffold explores a tree under a $30 budget and picks the branch with the best loss (learning rate 0.0003, loss 2.712). Read the summary critically: it reports 26 nodes explored but only $5.57 spent, the cost of the four logged experiments, so most of the "explored" nodes were proposed or scored without being run. A real report should separate proposed, run, failed and verified nodes; otherwise "26 explored" overstates the evidence.

:::broken
An agent's sandbox command is `docker run --memory=8g --cpus=2 image python exp.py`. A red-team test generates an experiment that downloads a script from the internet and runs it. Why does it succeed, and which two flags would have stopped or limited it? (Solution B1.)
:::

:::recap What to keep from this lesson
- Research as a tree: one change per child, budgeted, best-first.
- Every experiment runs in a sandbox with no network and hard limits.
- Verify results before expanding a branch.
- Writer and reviewers improve drafts; they do not certify truth.
- Ship the full trace, seeds and configs so others can reproduce it.
:::

## Solutions

??? sol | P4 · Network red team
Generate an experiment whose code calls out to an external address. Run it under `--network=none` and confirm the call fails with a network error; log the attempt with the node id. Also run it once *without* the flag in an isolated test environment to make sure the test would have detected a leak, so a passing result is meaningful.
???

??? sol | B1 · Missing isolation flags
The container has network access by default, so it can download code, and the filesystem is writable. Add `--network=none` so nothing can be fetched or sent, and `--read-only` (with a small writable scratch volume) plus `--pids-limit` to contain what the code can change and spawn. Add a wall-clock timeout as well.
???
