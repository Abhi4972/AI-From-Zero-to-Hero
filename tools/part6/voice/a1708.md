@@top The problem
:::plain In plain words first
"How fast is the model?" has several answers, and each one hides different problems. **TTFT** (time to first token) is how long a user waits before anything appears; long prompts and queues make it worse. **TPOT** or **ITL** (time per output token, inter-token latency) is the gap between streamed tokens once they start. **E2E** latency is the whole request. **Throughput** is tokens per second across all users, which says the fleet is busy but not that anyone is happy. **Goodput** is the share of requests that met *every* target at once: first token fast enough, tokens steady enough, whole answer quick enough. Latency is uneven, so you describe it with **percentiles**: P50 is the typical request, P99 the slowest 1%, and P99 is what users remember.
:::
@@

@@end Idea 10 · How to measure
:::math
**Goodput.** With SLO limits $a$, $b$, $c$,

$$\text{goodput} = \frac{\#\{\, r : \text{TTFT}_r \le a \ \wedge\ \text{TPOT}_r \le b \ \wedge\ \text{E2E}_r \le c \,\}}{\#\{\, r \,\}}$$

and $\text{E2E} = \text{TTFT} + \text{TPOT} \cdot (n_{\text{out}} - 1) + \text{network}$.
:::

:::worked One request, two tools
A request has TTFT = 500 ms, then 99 more tokens over 700 ms (100 output tokens, 1,200 ms in total).

1. GenAI-Perf measures from the second token: ITL = 700 / 99 ≈ 7.07 ms.
2. LLMPerf spreads the whole time over all tokens: 1,200 / 100 = 12.00 ms.
3. Same request, 70% apart. A dashboard that switched tools would show a "regression" that never happened.
4. Check E2E: 500 + 7.07 × 99 ≈ 1,200 ms. Both tools agree on E2E; they disagree on how to split it.
:::

:::check
Which statements are right?

- ✓ Throughput can be high while most users have a bad experience.
- ✗ Mean TPOT is a good summary for a dashboard.
  Latency is right-skewed; a 7 ms mean can sit next to a 65 ms P99.
- ✓ A request counts towards goodput only if every SLO held for it.
- ✗ Benchmark tools agree on what ITL means.
  GenAI-Perf excludes the first token, LLMPerf includes it.
:::

:::predict
Before running the code below: if 1% of requests hit a slow neighbour and their TPOT is 9 times normal, what happens to mean TPOT, and what happens to P99?
:::

:::visual A 1% tail, three statistics
```python run
import random, statistics
random.seed(3)
tpot = [random.gauss(7.0, 0.6) for _ in range(9900)] + [random.gauss(63.0, 5.0) for _ in range(100)]
tpot.sort()
pct = lambda q: tpot[int(q * len(tpot)) - 1]
print(f"mean {statistics.mean(tpot):5.1f} ms   P50 {pct(0.50):5.1f}   P90 {pct(0.90):5.1f}   P99 {pct(0.99):5.1f}   P99.5 {pct(0.995):5.1f}")
for limit in (30, 15):
    print(f"share of requests with TPOT <= {limit} ms: {sum(t <= limit for t in tpot) / len(tpot):.2%}")
```
:::

:::read
The 1% tail moves the mean only from about 7 to 7.6 ms, but P99.5 lands in the tail at about 60 ms. With exactly 1% slow requests, P99 sits right at the edge, which is why teams also watch P99.5 or P99.9. Goodput against a 15 ms TPOT limit is 99%: the tail requests fail it every time, however good the mean looks.
:::

A team reports "P99 TPOT 8 ms" to leadership, measured with LLMPerf on a load test of 50 requests with identical 100-token prompts. In production, users complain about stalls. Name three things wrong with the measurement. (Solution B1.)

:::recap What to keep from this lesson
- TTFT = queue + network + prefill; TPOT is the decode gap; E2E adds them up.
- Throughput measures the fleet; goodput measures the users.
- Report P50, P90 and P99, never the mean alone.
- State the tool and its ITL definition with every number.
- Write the SLO down (for example TTFT P99 ≤ 800 ms, TPOT P99 ≤ 25 ms) and track goodput against it.
:::

## Solutions

??? sol | P1 · Tightening the TPOT limit
In the visual above, tightening the TPOT limit from 30 to 15 ms changes nothing: the healthy 99% sit near 7 ms and the slow 1% near 63 ms, so goodput stays at 99% either way. In the script, the "target" profile tightens TTFT, TPOT and E2E together and goodput falls to about 76%, mostly from the TTFT and E2E limits. Tightening one limit only matters if requests sit between the old and new values.
???

??? sol | B1 · Three mistakes
(1) 50 requests cannot give a meaningful P99: that is the single slowest request. Use thousands, over 30–50 runs. (2) Identical 100-token prompts hide the real mix: long prompts cause the prefill stalls users see. Use a realistic distribution of input and output lengths. (3) Production load is higher: benchmark at about twice peak concurrency. Also say which tool and which ITL definition the number uses.
???
