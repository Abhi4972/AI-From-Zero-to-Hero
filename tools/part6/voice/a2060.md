@@top The problem
:::plain In plain words first
Chat answers arrive as a stream, token by token. Connections drop. A careless client either starts the answer again (and the user sees text twice), or shows the partial text as if it were complete. Two lower-level traps make it worse: a network chunk can end in the middle of a multi-byte character such as "é", or in the middle of an event.

This project builds stream recovery for server-sent events (SSE). It decodes bytes incrementally so characters and events survive any chunk boundary, applies events by stable id so a repeated event changes nothing, reconnects with the id of the last accepted event, keeps a cancelled answer as a draft, and exports a trace that can rebuild the answer exactly.
:::
@@

@@end Step 1 · Decode chunked bytes into complete events
:::visual A character split across chunks
```python run
import codecs
data = "data: Café\n\n".encode()                     # é is two bytes in UTF-8
chunks = [data[:10], data[10:]]                       # the split falls inside é
print("naive:", [c.decode(errors="replace") for c in chunks])
dec, text = codecs.getincrementaldecoder("utf-8")(), ""
for c in chunks: text += dec.decode(c)
print("incremental:", repr(text))
```
:::

:::read
"é" is two bytes in UTF-8, and the chunk boundary falls between them. Decoding each chunk separately produces replacement characters (the � symbols) where the halves should be. An incremental decoder holds the incomplete byte until the next chunk arrives and produces "Café". The same holds one level up: an event is dispatched only when its blank line arrives, never on a partial line.
:::
@@

@@end Step 3 · Handle reconnect and cancellation
:::check
Which statements are right?

- ✓ Reconnecting sends the id of the last accepted event, so the server resumes after it.
- ✗ After a reconnect, the client should clear the text and replay from the start.
  Events are applied by id; already-accepted events are ignored, so nothing is duplicated.
- ✓ A cancelled answer keeps its draft text and does not reconnect.
- ✗ A citation's URL can be inserted into the page as HTML.
  URLs are validated (no `javascript:`) and text is set with `textContent`.
:::

@@before Build it on your machine

A chat client appends every `data:` line it receives. After a reconnect the server resends event 2, and users see "é supports interrupted answers." twice. What should the client have tracked? (Solution B1.)

:::recap What to keep from this project
- Decode bytes incrementally; dispatch events only when complete.
- Apply events by stable, contiguous ids; duplicates are harmless.
- Reconnect from the last accepted id; never restart silently.
- Keep cancelled and interrupted answers visibly incomplete.
- Export accepted events so the answer can be replayed.
:::

@@end Exercises

## Solutions

??? sol | 1. A trailing data line
An event is complete only at its blank line. Dispatching the last `data:` line early could hand half a JSON object to the parser and display garbage, or fail outright.
???

??? sol | 2. A javascript: citation
Validate the URL scheme (only http and https) before creating the link, and reject the citation otherwise. Its label is inserted with `textContent`, so it cannot inject markup.
???

??? sol | 3. Abort between events
Set the status to cancelled, keep the text received so far, and do not reconnect when the user presses resume; resuming a cancelled answer would contradict their action.
???

??? sol | 4. Byte-level traces
Keep them as a separate debugging artifact. The exported trace records accepted application events, which is what is needed to rebuild the answer, not the raw bytes that were discarded.
???

??? sol | B1 · Duplicate text
The id of the last accepted event. With it, the resent event 2 is recognised as already applied and ignored, and the reconnect request asks the server to start after it.
???
