@@top The problem
:::plain In plain words first
A postmortem tells the story of an incident, and stories drift toward a cause: "the deploy broke latency". Often the evidence only shows that an alert followed a deploy. This project writes postmortems that keep the difference visible.

It reads an event ledger with stable ids and line locators, orders events into a timeline without claiming that order proves cause, requires every claim to cite real events with exact quotes, and publishes a packet where unreviewed claims and unowned follow-ups stay visible as pending.
:::
@@

@@end Step 3 · Require evidence for each claim
:::worked A citation is not a conclusion
1. Ledger: `e1` at t=0, deploy "version B started"; `e2` at t=35, alert "latency exceeded SLO".
2. The claim "An alert followed the deployment; causality is unconfirmed." cites `e1` and `e2`. Both exist and their quotes match: the citation is valid.
3. The claim "The deployment caused the latency" could cite the same events, and they would still validate. Valid citations prove the sources exist, not that they support a causal conclusion; that is the reviewer's decision.
4. A claim citing `e99` is invalid outright: the event does not exist.
:::

:::check
Which statements are right?

- ✓ Events that arrive out of order are sorted by time, with the id breaking ties.
- ✗ If one event happens before another, the first caused the second.
  Order is necessary for cause, not sufficient; the packet keeps causal claims pending.
- ✓ A follow-up action needs an owner, or it is shown as unassigned.
- ✗ The packet should hide pending claims until they are approved.
  It shows them as pending, so unfinished review is visible.
:::
@@

@@before Build it on your machine
:::broken
A postmortem says "Root cause: deploy of version B" and cites the deploy event. Weeks later a dependency outage at the same minute is found. What did the document assert that the evidence never showed, and how would this project have marked it? (Solution B1.)
:::

:::recap What to keep from this project
- Give every event a stable id and line locator.
- Order by time with an id tie-break; order is not cause.
- Claims cite real events with exact quotes.
- Causal claims stay pending until a named reviewer decides.
- Publish unfinished review and unowned actions visibly.
:::

@@end Exercises
1. Why copy the event list before sorting it?
2. A claim cites the same event twice. Should it validate?
3. How would you record a reviewer's approval so it cannot be reused for a changed ledger?

## Solutions

??? sol | 1. Copy before sorting
Another consumer may need the arrival order (for example to spot delayed log shipping). Sorting a copy keeps both views.
???

??? sol | 2. Duplicate citations
No. A claim must cite distinct events; citing one twice inflates apparent support. The validator rejects it.
???

??? sol | 3. Source-bound approval
Store the approval with the ledger's SHA-256 and the exact claim text. If either changes, the approval no longer matches and the claim returns to pending.
???

??? sol | B1 · A cause nobody showed
It asserted causation from timing. The evidence showed only that the deploy preceded the alert. Here the claim would have stayed pending, and a reviewer would have had to approve it explicitly, which is where "what else happened at that minute?" gets asked.
???
