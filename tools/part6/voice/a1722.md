@@top The problem
:::plain In plain words first
A **load test** sends a server realistic traffic at increasing volume to find where it breaks before users do. LLM servers have two traps that make ordinary load tests lie. The **prompt-uniformity trap**: if every simulated user sends the same prompt, the server's prefix cache answers almost all of them from memory, and you measure a cache, not a model. The **GIL trap**: Python load tools such as Locust tokenize responses in the same process that sends requests, so at high concurrency the *client* slows down and its timing numbers include its own delays. A good LLM load test samples prompts from a realistic distribution of lengths and contents, uses a tool that does not bottleneck itself (LLMPerf, k6, GenAI-Perf, LLM-Locust), and runs four shapes of traffic: steady, ramp, spike and soak.
:::

@@end Idea 7 · Numbers you should remember
:::worked What a uniform test hides
Suppose prefill costs about 0.4 ms per prompt token on a miss and the cached path about 80 ms flat.

1. Uniform test: 500 requests, all with the same 2,000-token prompt. 499 are cache hits: TTFT about 80 ms every time. P99 = 80 ms.
2. Realistic test: prompt lengths with mean 500 and standard deviation 150, mostly unique content. Cache hits only where a system prompt is shared; a 2,000-token unique prompt takes about 800 ms.
3. The P99 in production is set by the long, unique prompts: about 800 ms, ten times what the uniform test reported.
4. The same mistake hides concurrency effects: with one cached prefix there is no real prefill load, so the GPU never saturates.
:::

:::check
Which statements are right?

- ✓ A loop over one prompt mostly measures the prefix cache.
- ✗ Stock Locust is a good harness for streaming LLM latency at high concurrency.
  Its client-side tokenization runs under Python's GIL and inflates the latency it reports.
- ✓ A soak test of 4–8 hours finds memory leaks a 10-minute test misses.
- ✗ Load-testing at your expected peak is enough.
  Spike tests at 3–10× catch autoscaling and queueing failures.
:::

:::predict
Before running the code below: if real prompts follow a log-normal length distribution with a median of 400 tokens, what share of requests is longer than 1,500 tokens?

:::visual Sampling realistic prompt lengths
```python run
import random, math
random.seed(6)
lengths = sorted(int(random.lognormvariate(math.log(400), 0.7)) for _ in range(10_000))
pct = lambda q: lengths[int(q * len(lengths)) - 1]
print(f"P50 {pct(0.5)} tokens  P90 {pct(0.9)}  P99 {pct(0.99)}  max {lengths[-1]}")
print(f"share over 1,500 tokens: {sum(l > 1500 for l in lengths) / len(lengths):.1%}")
ttft = sorted(80 + 0.4 * l for l in lengths)        # unique prompts: no cache
print(f"TTFT P50 {ttft[4999]:.0f} ms, P99 {ttft[9899]:.0f} ms (uniform test would report 80 ms)")
```
:::

:::read
Only about 3% of prompts exceed 1,500 tokens, but they set the tail: P99 TTFT comes out several times the median. A uniform test reports none of this. Build the length distribution from your own logs (or a published set such as ShareGPT) and give the tool both the mean and the spread.
:::

@@before Ship it
:::read
Two things stand out. Uniform prompts produce 499 cache hits out of 500 and a P99 of 80 ms; realistic prompts show a P99 of 800 ms. And the three concurrency levels print identical rows: this toy does not model queueing, so it shows the uniformity trap but says nothing about capacity. A real ramp test is what finds where concurrency starts to hurt.

:::recap What to keep from this lesson
- Uniform prompts measure the cache; sample a realistic length and content distribution.
- Avoid harnesses that bottleneck themselves (stock Locust); use LLMPerf, k6, GenAI-Perf or LLM-Locust.
- Run steady, ramp, spike and soak patterns.
- Gate CI on P50/P95 TTFT, TPOT and error rate.
- State which tool you used: their ITL definitions differ.

## Solutions

??? sol | P1 · Uniform against realistic
In `code/main.py` the gap is entirely in the tail: P50 is 80 ms for both, but P99 is 80 ms with uniform prompts and 800 ms with realistic ones, because 499 of 500 uniform requests are cache hits against 421 for the realistic mix. The concurrency levels are identical because the toy has no queueing model.
???

??? sol | B1 · A gate that lied
(1) One fixed prompt: after the first request everything came from the prefix cache, so the gate measured cache latency. (2) No realistic length distribution: production's long prompts set the P95. A third common cause: the test ran against a warm, otherwise idle server, while production also has cold replicas and mixed traffic.
