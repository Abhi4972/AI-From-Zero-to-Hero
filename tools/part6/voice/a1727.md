@@top The problem
:::plain In plain words first
**FinOps** is the practice of knowing who spends what in the cloud and keeping it under control. LLM calls make that hard: the provider's bill shows tokens and dollars, not which customer, feature or user caused them. So you **attribute** cost yourself: every call carries a user ID, a task or route name and a tenant (customer) ID, and you join those tags to the token counts. It also helps to split tokens into **layers**: the prompt you wrote, tool results fed back in, conversation memory, and the model's answer, because each is fixed in a different way. Then you **enforce**: rate limits per tenant, daily spend caps, and an automatic kill switch when a tenant's spend is wildly above its normal level. Finally, you judge cost per *outcome* (per resolved ticket, per completed task), not per million tokens.
:::

@@end Idea 8 · Numbers you should remember
:::math
**Spend anomaly score.** For a tenant with daily spend history mean $\mu$ and standard deviation $\sigma$, today's spend $x$ gives

$$z = \frac{x - \mu}{\sigma}$$

A kill switch at $z > 4$ fires on spend far outside the tenant's own normal range, rather than on an absolute dollar figure that suits one tenant and not another.
:::

:::worked Cost per resolved ticket
A support assistant spent $12,000 last month on 300,000 conversations; 180,000 ended with the ticket resolved without a human.

1. Cost per conversation: $12,000 / 300,000 = $0.04.
2. Cost per resolved ticket: $12,000 / 180,000 ≈ $0.067.
3. A cheaper model cuts spend to $7,000 but resolution drops to 120,000: cost per resolved ticket ≈ $0.058, slightly better, but 60,000 more tickets now reach human agents, each costing far more than $0.07.
4. The unit metric (cost per resolved ticket, plus the human cost of escalations) shows the "cheaper" model costs more overall. Token prices alone would have hidden that.
:::

:::check
Which statements are right?

- ✓ LLM API calls do not carry your tags; you stamp them at the call site.
- ✗ Cost per million tokens is the metric to optimize.
  Tie cost to an outcome (per ticket, per task), or optimization has no anchor.
- ✓ In agent workloads, tool results fed back can be 20–40% of tokens.
- ✗ A single global spend cap protects every tenant fairly.
  Caps and anomaly thresholds should follow each tenant's contract and baseline.
:::

:::predict
Before running the code below: a tenant spends about $15 a day with a standard deviation of about $2.50. Which day's spend first passes z > 4: $25, $31 or $40?
:::

:::visual A z-score kill switch
```python run
import statistics
history = [14.2, 15.8, 13.1, 16.4, 15.0, 19.6, 12.7, 14.9, 16.1, 13.8, 21.0, 11.5, 15.3, 14.6]
mu, sd = statistics.mean(history), statistics.stdev(history)
print(f"baseline: mean ${mu:.2f}, sd ${sd:.2f}")
for today in (25, 31, 40, 120):
    z = (today - mu) / sd
    action = "KILL SWITCH: pause tenant, page on-call" if z > 4 else ("alert customer success" if z > 2.5 else "ok")
    print(f"today ${today:6.2f}: z = {z:5.1f} -> {action}")
```
:::

:::read
With this tenant's spread (about $2.50), $25 is already well outside its normal range and $31 would trip a z > 4 kill switch. A flat cap of, say, $100 a day would not have fired until something far worse. Thresholds relative to each tenant's own baseline catch abuse early without punishing big customers whose normal spend is high.
:::
