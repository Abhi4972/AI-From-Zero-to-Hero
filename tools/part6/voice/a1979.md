@@top The problem
:::plain In plain words first
**Pipeline parallelism** splits a model by layers: rank 0 holds the first block of layers, rank 1 the next, and so on, each a **stage**. A batch is cut into **micro-batches** that flow through the stages like an assembly line. At the start and end of each step some stages sit idle waiting for work; that idle time is the **bubble**. **GPipe** runs all forward passes, then all backward passes; **1F1B** interleaves one forward with one backward once the pipeline is full, which keeps the same bubble but limits how many micro-batches' activations each stage must hold. More micro-batches shrink the bubble, and stages should do equal work, since the slowest stage sets the pace.
:::
@@

@@end Idea 4 · Microbatch versus batch
:::math The bubble fraction
With $S$ stages and $M$ micro-batches, GPipe and 1F1B both leave idle a fraction

$$\text{bubble}=\frac{S-1}{M+S-1}$$

of each stage's time: $S-1$ slots to fill the pipeline at the start and to drain it at the end.
:::

:::worked Four stages, eight micro-batches
1. Forward phase: stage 0 starts micro-batch 0 at time 0; stage 3 cannot start until time 3. Stage 3 idles for 3 slots at the start.
2. Backward phase, in reverse: stage 0 waits for the gradients to come back, idling for 3 slots at the end.
3. Each stage does 2 × 8 = 16 slots of work in a schedule 2 × (8 + 3) = 22 slots long: idle 6 of 22, or 27.3%, matching (4 − 1)/(8 + 4 − 1) = 3/11.
4. With 32 micro-batches the bubble falls to 3/35 ≈ 8.6%. Smaller micro-batches are less efficient on the GPU, so M is a balance.
:::

:::check
Which statements are right?

- ✓ The bubble shrinks as the number of micro-batches grows.
- ✗ 1F1B removes the pipeline bubble.
  It keeps the same bubble but bounds activation memory.
- ✓ The slowest stage sets the pace of the whole pipeline.
- ✗ Pipeline parallelism splits each matrix multiply across ranks.
  That is tensor parallelism; pipelines split the layers.
:::

:::visual Bubble fraction by stages and micro-batches
```python run
def bubble(S, M): return (S - 1) / (M + S - 1)
for S in (2, 4, 8):
    print(f"S={S}: " + "  ".join(f"M={M:2d}:{bubble(S, M):6.1%}" for M in (1, 4, 16, 64)))
```
:::

:::read
With one micro-batch, a 4-stage pipeline is idle 75% of the time; with 16 it is 16%, and with 64 under 5%. Doubling the stages to 8 doubles the fill and drain cost, so 16 micro-batches now leave 30% idle. Deeper pipelines need proportionally more micro-batches, which means larger global batches, one reason pipeline depth is usually kept modest.
:::

## Solutions

??? sol | P1 · 1F1B
After a warm-up of S − 1 forwards, each stage alternates one forward and one backward, so at most S micro-batches' activations are alive on a stage instead of M. The schedule's length and bubble match GPipe's (S − 1)/(M + S − 1); measure peak activation memory per stage to see the difference.
???

??? sol | B1 · Unbalanced stages
Stage 1 does about five times the work of stage 0, so stage 0 waits idle most of the time and the pipeline runs at stage 1's pace. Balance by measured time per layer, for example 6 blocks per stage, putting the cheap embedding with the first blocks and the output head with the last.
???
