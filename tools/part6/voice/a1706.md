@@top The problem
:::plain In plain words first
Many requests to the same model start with the same text: the same system prompt, the same tool descriptions, the same retrieved document. Reading that shared beginning (the **prefix**) costs the same work every time. **Prefix caching** keeps the KV cache computed for a prefix and reuses it, so only the new part of each prompt needs reading. SGLang's **RadixAttention** stores cached prefixes in a **radix tree**, a tree where each path from the root spells out a sequence of tokens. A new request walks down the tree as far as its tokens match and reuses everything on that path. Two things decide how much you save: whether your prompts put the shared parts first in a fixed order, and whether the scheduler serves requests that share a branch together, so that branch stays in memory.
:::
@@

@@end Idea 7 · Interplay with vLLM
:::worked What a 2,000-token shared prefix saves
A RAG service sends 5,000 requests. Each prompt is a 2,000-token system prompt, a 500-token document (one of 10 documents) and an 80-token question.

1. Without caching: 5,000 × 2,580 = 12.9 million prompt tokens to prefill.
2. With a radix cache that keeps everything resident: the system prompt once (2,000), each document once (10 × 500 = 5,000), every question (5,000 × 80 = 400,000). About 407,000 tokens.
3. Saving: 1 − 0.407 / 12.9 ≈ 97% of prefill work.
4. If half the clients put the document *before* the system prompt, those requests share nothing with the others, and the saving for them drops to the document alone.
:::

:::check
Which statements are right?

- ✓ Your prompt template is a cache key: the order of its parts decides what can be shared.
- ✗ Prefix caching helps code completion with unique prompts.
  With no shared beginning there is nothing to reuse.
- ✓ Evicting whole branches keeps the cache shaped like the tree.
- ✗ Prefix reuse only needs a fast kernel.
  It pays only if the scheduler keeps hot branches resident instead of churning them.
:::

:::predict
Before you run the code below: if each request's three fixed parts (system, tools, context) arrive in a random order, what share of requests can reuse the full 3-part prefix of an earlier one?

:::visual Order decides what can be shared
```python run
import itertools, random
random.seed(1)
parts = ["system", "tools", "context"]
orders = [tuple(random.sample(parts, 3)) for _ in range(1000)]
seen, full_hits = set(), 0
for o in orders:
    full_hits += o in seen
    seen.add(o)
print("distinct orders seen:", len(seen), "of", len(list(itertools.permutations(parts))))
print(f"requests whose 3-part prefix was already cached: {full_hits / len(orders):.1%}")
print("same requests with a fixed order:", f"{(len(orders) - 1) / len(orders):.1%}")
```
:::

:::read
With random order there are only six possible prefixes, so most requests still find one already cached. But each of the six is a separate branch holding its own copy of the same tokens, six times the memory, and once cache pressure evicts branches, the hit rate collapses. A fixed order needs one branch. Production systems see this as the jump from about 7% to 74% hit rate after moving dynamic content out of the prefix.
:::

:::recap What to keep from this lesson
- Shared prefixes are common in RAG, agents and chat; reusing their KV cache skips most prefill.
- RadixAttention indexes cached prefixes in a radix tree and reuses the longest match.
- Fixed template order, immutable parts first, is the biggest lever.
- Cache-aware scheduling and branch-level eviction keep hot prefixes resident.
- vLLM's prefix caching narrows the gap; SGLang is radix-first throughout.

## Solutions

??? sol | P1 · FCFS against cache-aware
On the fixed-order workload there is no delta: both reach 69.1%, because the whole working set fits in the toy cache. The delta appears only under pressure, on the scrambled workload (8.4% against 26.5%), and it comes from prefill savings: cache-aware scheduling serves requests from a branch while that branch is resident.
???

??? sol | P5 · An 8% hit rate
Three likely causes: (1) dynamic content at the start of the prompt (timestamps, request IDs, user names), found by diffing two prompts token by token; (2) inconsistent ordering of system, tools and context between clients, found by grouping prompts by their first 200 tokens; (3) cache too small for the working set, found by checking eviction counts against the number of distinct prefixes.
???

??? sol | B1 · A timestamp first
The timestamp changes every second, so no two requests share even their first token, and everything after it, system prompt and tools included, cannot be reused. Move the timestamp to the end, next to the user's question, or drop seconds. The fixed parts then form a shared prefix again.
???
