@@top The situation
:::plain In plain words first
On a GPU shared with another team, a server stops at start with an error naming a maximum length of 40,960 tokens. A colleague's first fix lowers the memory fraction too. The error itself points to the real lever: the server tried to reserve room for the longest possible request, and the service never sends anything close. The case trains reading a startup failure as a question about your traffic.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ The maximum model length decides how much cache memory the server must reserve.
- ✗ Lowering the memory fraction is always the first fix on a shared GPU.
  It leaves less room for the cache; lowering the maximum length to real request sizes is the first lever.
- ✓ The limit should be the longest request the service really sends, with some margin.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Read the number in the error and find which setting produced it.
- Lower the maximum length to real traffic first.
- On a shared GPU, memory fraction and maximum length work together.
- Raise limits later only with measurements.
:::
@@
