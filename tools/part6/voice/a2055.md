@@top The problem
:::plain In plain words first
A RAG system answers from an index of documents. When a policy changes from "tokens expire after 60 minutes" to "15 minutes", or a runbook is deleted, the index must change too, or the assistant keeps confidently citing the old text. This is one of the most common real RAG failures.

This project builds a freshness pipeline. Documents are fingerprinted by normalized content. Each sync computes a full plan of inserts, updates, deletions and metadata refreshes before touching the index. The index is written atomically with a version check that rejects stale writers. And at query time, anything older than the allowed age is excluded, even if it matches perfectly.
:::
@@

@@end Step 2 · Plan inserts updates deletions and refreshes
:::visual A sync plan from fingerprints
```python run
import hashlib, unicodedata
fp = lambda t: hashlib.sha256(unicodedata.normalize("NFC", t).encode()).hexdigest()[:10]
index = {"orchard-auth": fp("Orchard guest tokens expire after 60 minutes."),
         "retired-backup": fp("Backups run nightly to the old bucket.")}
source = {"orchard-auth": "Orchard guest tokens expire after 15 minutes.",
          "restore-runbook": "Restore from the latest verified snapshot."}
plan = {"insert": sorted(set(source) - set(index)), "delete": sorted(set(index) - set(source)),
        "update": sorted(i for i in set(source) & set(index) if fp(source[i]) != index[i])}
print(plan)
print("café composed vs decomposed:", fp("café") == fp("café"))
```
:::

:::read
The new runbook is an insert, the edited token policy an update, and the retired backup note a delete: without the delete step, its old chunks would stay searchable forever. The last line shows why content is normalized before hashing: "café" typed as one character or as "e" plus a combining accent is the same text and must not look like a change.
:::
@@

@@end Step 4 · Exclude expired evidence at query time
:::check
Which statements are right?

- ✓ A document missing from the source is deleted from the index.
- ✗ Changing only a document's timestamp should trigger re-indexing.
  Unchanged content with new metadata is a refresh, not an update.
- ✓ A writer holding an old snapshot version is rejected.
- ✗ If the ingestion job ran successfully, query-time age checks are unnecessary.
  Jobs fail and lag; the query enforces freshness itself.
:::

@@before Build it on your machine

An ingestion job only adds and updates documents; it never deletes. A product was discontinued six months ago and its page removed. What does the assistant still say about it, and which plan step fixes it? (Solution B1.)

:::recap What to keep from this project
- Fingerprint normalized content; identity and content are separate keys.
- Compute the whole plan (insert, update, delete, refresh) before writing.
- Replace the index atomically, with a version check.
- Enforce freshness at query time with an injected clock.
:::

@@end Exercises

## Solutions

??? sol | 1. Two encodings of café
They are the same text to a reader. Different fingerprints would trigger needless re-indexing and could create duplicate entries for one document.
???

??? sol | 2. A partial change feed
A missing id would no longer mean "deleted". Deletions would have to arrive as explicit events, and a periodic full reconciliation would be needed to catch any that were lost.
???

??? sol | 3. A crash before rename
The temporary file is left behind and the destination still holds the last committed snapshot, which stays readable. The next run removes or overwrites the stale temporary file.
???

??? sol | 4. A future-dated document
No. A negative age means a clock or data error. Reject it or treat it as invalid; it must never become the freshest possible result.
???

??? sol | B1 · Never deleting
It keeps answering from the discontinued product's page as if it were current. The plan's delete step, which removes ids missing from the source, takes those chunks out of the index.
???
