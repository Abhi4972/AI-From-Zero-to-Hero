@@top Where the dispatcher sits
:::plain In plain words first
The **dispatcher** is the layer that actually runs a tool call: it looks the tool up in the registry, validates the arguments, calls the handler with a **timeout**, and turns whatever happens into either a result or a typed error. It also decides when to **retry**: only for errors that might go away (timeouts, transient failures), only for tools marked **idempotent** (safe to run twice), with **exponential backoff** and random **jitter** so retries do not pile up. For calls that must never run twice, the caller supplies an **idempotency key**, and a second call with the same key waits for the first one's result instead of running again. All of this lives in one place, so the loop, registry and handlers stay simple.
:::
@@

@@end Flow for one call
:::worked A retry that would charge twice
`payments.charge` has a 5-second timeout. The payment service is slow today.

1. The first call reaches the service, which takes 5.2 s to commit the charge. At 5.0 s the dispatcher times out.
2. **Without care:** the dispatcher retries; the second call also charges. The customer pays twice.
3. **Idempotency flag:** `payments.charge` is marked non-idempotent, so a timeout is returned as an error and *not* retried. The caller can check the payment's status before trying again.
4. **Idempotency key:** if a retry is wanted, the caller passes a key such as `step7:payments.charge:<args hash>`; a second call with the same key, while the first is in flight or within the cache window, receives the first call's result instead of charging again.
:::

:::check
Which statements are right?

- ✓ Schema errors are not retried, because the same input fails the same way.
- ✗ Every timeout should be retried.
  For non-idempotent tools the first call may already have taken effect.
- ✓ Jitter spreads retries so many clients do not hit a recovering service at the same moment.
- ✗ The dispatcher should derive idempotency keys from the arguments alone.
  Two different intended actions can have identical arguments; the caller supplies the key.
:::

:::predict
Before running the code below: with base delays of 0.1 s and 0.4 s for attempts 2 and 3, each multiplied by a random factor between 1 and 1.5, what is the longest a call can spend waiting between attempts?
:::

:::visual Backoff with jitter, and dedupe by key
```python run
import random
random.seed(0)
def delays(attempts=3):
    base = [0.0, 0.1, 0.4]
    return [round(b * (1 + random.uniform(0, 0.5)), 3) for b in base[:attempts]]
print("five clients' retry delays (s):")
for c in range(5): print("  client", c, delays())

charged, in_flight = [], {}
def charge(key, amount):
    if key in in_flight: return in_flight[key]            # same key: return the first result, do not run again
    charged.append(amount); in_flight[key] = f"receipt-{len(charged)}"
    return in_flight[key]
print(charge("step7:charge:abc", 40), charge("step7:charge:abc", 40), charge("step8:charge:def", 40))
print("charges actually made:", charged)
```
:::

:::read
Each client's second and third delays differ slightly, so five clients retrying together do not hit the service at the same instant; the waiting is bounded at 0.15 + 0.6 = 0.75 s in total. The idempotency part shows the guarantee: the repeated key returns the same receipt and only two charges happen for three calls, one per distinct key.
:::

@@before Going further
:::read
The demo exercises each path once: a transient failure that succeeds on the second attempt; a timeout that is reported as `timeout`; bad arguments reported as `schema` (no retry); an unknown tool reported as `not_found`; a normal call; and two calls sharing an idempotency key that both succeed while the handler runs only once. Each outcome is a typed error kind, so the plan-execute layer in the next lesson can decide what to do without parsing messages.
:::

:::broken
A team marks every tool `idempotent=True` "so transient errors always get retried". Which tools does that make dangerous, and what is the right default? (Solution B1.)
:::

:::recap What to keep from this lesson
- One layer owns timeouts, retries, dedupe and error mapping.
- Retry only retryable errors, only on idempotent tools, with backoff and jitter.
- Idempotency keys come from the caller and absorb late retries.
- Every failure is a typed error kind the loop can act on.
- Limit concurrency when fanning out calls.
:::

@@end Going further
## Solutions

??? sol | B1 · Everything idempotent
Any tool with side effects that are not safe to repeat (sending messages, payments, creating tickets, appending records) can now run twice after a timeout that hid a success. Default to `idempotent=False`, mark read-only and truly repeat-safe tools explicitly, and require idempotency keys for the rest when retries are needed.
???
