@@top Why a frozen spec
:::plain In plain words first
This lesson starts a track that builds an LLM **evaluation harness**. Its foundation is a frozen **task spec**: every eval item is one JSON line with fixed fields (task id, category, prompt, target, metric name, optional few-shot examples) and a fixed vocabulary of categories and metrics. A **validator** checks every line before anything is scored and reports problems precisely: line number, field, rule broken. Some combinations are illegal by design, such as BLEU on a multiple-choice item. The spec also defines how **few-shot examples** are rendered into the prompt and how outputs are **post-processed** (trimmed, lower-cased, answer letter extracted), so every model is scored under identical rules.
:::

@@end Post-process rules
:::worked Why validate before scoring
A 500-line task file has three bad lines: one missing its target, one with category `mcqs` (typo), one pairing `mcq` with `bleu_4`.

1. **Without validation:** the missing target crashes the scorer at line 312 after an hour of model calls; the typo silently creates a sixth category with one item; BLEU on a one-letter answer produces a meaningless 0 or 1.
2. **With validation:** all three are reported up front, with line numbers and rules, before any model is called.
3. The file is fixed in minutes, and the scores that follow are comparable with every other run that used the same spec.
4. Freezing the vocabulary is what turns "an eval" into a benchmark other people can rerun.
:::

:::visual A validator that reports every problem
```python run
import json, re
CATEGORIES = {"arithmetic", "classification", "code_exec", "mcq", "summary"}
ILLEGAL = {("mcq", "bleu_4"), ("arithmetic", "rouge_l")}
def validate(line_no, rec):
    errs = []
    if "task_id" not in rec: errs.append("missing_required task_id")
    elif not re.fullmatch(r"[A-Za-z0-9_-]+", rec["task_id"]): errs.append("bad_value task_id")
    if rec.get("category") not in CATEGORIES: errs.append(f"bad_value category={rec.get('category')!r}")
    if (rec.get("category"), rec.get("metric_name")) in ILLEGAL: errs.append("illegal_pair metric_name")
    return [f"line {line_no}: {e}" for e in errs]

lines = ['{"category": "mcq", "metric_name": "accuracy"}',
         '{"task_id": "bad id", "category": "mcq", "metric_name": "accuracy"}',
         '{"task_id": "t3", "category": "mcqs", "metric_name": "accuracy"}',
         '{"task_id": "t4", "category": "mcq", "metric_name": "bleu_4"}',
         '{"task_id": "t5", "category": "arithmetic", "metric_name": "exact_match"}']
for i, l in enumerate(lines, 1):
    print(validate(i, json.loads(l)) or f"line {i}: ok")
```
:::

:::read
Each bad line is reported with the rule it broke, and the validator keeps going after the first error so one pass finds all of them; only line 5 is clean. Reporting every problem with its line number is what makes a 500-line file fixable in one sitting.
:::

@@before Going further
:::read
The good fixture validates all 10 lines with no errors; the bad fixture fails all 10, each with its own rule: missing required field, an id that breaks the allowed pattern, an unknown category, an illegal category–metric pair, a target of the wrong type, and so on. Ten different failure modes, each caught before scoring, is the validator's coverage test.
:::

:::broken
A team adds a new metric, `semantic_sim`, by writing its scorer and using it in task files, without adding it to the spec's metric vocabulary. Validation starts rejecting their new tasks. Is the validator wrong? (Solution B1.)
:::

:::recap What to keep from this lesson
- One frozen JSONL record shape for every eval item.
- A fixed vocabulary of categories and metrics, with illegal pairs.
- Validate everything first; report line, field and rule.
- Few-shot rendering and post-processing are part of the spec.
- A frozen spec makes results comparable across runs.
:::

## Solutions

??? sol | B1 · Changing the spec on purpose
No: the validator is doing its job. A new metric is a change to the contract, so add it to the vocabulary (and its allowed categories) deliberately, bump the spec version, and note that scores from the new metric are not comparable with earlier runs. Silent extensions are exactly what the frozen spec exists to prevent.
