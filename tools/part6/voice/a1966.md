@@top The problem
:::plain In plain words first
A **bi-encoder** embeds the query and each document separately, which makes search fast because documents are embedded once in advance. A **cross-encoder** reads the query and one document *together* and outputs a relevance score, so it can notice how they relate word by word: more accurate, but far too slow to run over a whole corpus. The standard answer is two stages: the fast retriever picks the top N candidates, and the cross-encoder **re-ranks** only those, keeping the top K. This lesson trains a tiny cross-encoder on a few labelled pairs (seconds of training) to show the shape, including its main failure: a reranker trained on too little data can make the ranking worse.
:::
@@

@@end Idea 3 · Latency vs quality
:::worked The latency budget
A corpus of 1,000,000 chunks; one cross-encoder pass takes 5 ms on a GPU; the retriever takes 20 ms total.

1. Cross-encoding everything: 1,000,000 × 5 ms ≈ 83 minutes per query. Impossible.
2. Retrieve top 50, then cross-encode 50: 20 ms + 50 × 5 ms = 270 ms, or less with batching.
3. Retrieve top 10: 70 ms, but if the right chunk was ranked 25th by the retriever, the reranker never sees it.
4. N trades latency against the chance that the answer is in the candidate set at all; measure the retriever's recall@N before choosing it.
:::

:::check
Which statements are right?

- ✓ A cross-encoder reads query and document together.
- ✗ A reranker can recover documents the retriever did not return.
  It only reorders the candidates it is given.
- ✓ Re-ranking only the top N keeps latency bounded.
- ✗ A reranker trained to near-zero loss will improve rankings.
  On a tiny training set it can overfit and make rankings worse.
:::

:::predict
Before running the code below: the retriever's recall@N on a query set is 0.70 at N = 10, 0.88 at N = 50 and 0.93 at N = 200. If the reranker always puts the right chunk first when it is present, what is the end-to-end recall@1 for each N?
:::

:::visual Candidate depth sets the ceiling
```python run
recall_at_n = {10: 0.70, 50: 0.88, 200: 0.93}
ms_per_pair, retrieve_ms = 5, 20
for n, r in recall_at_n.items():
    print(f"N={n:3d}: best possible recall@1 after re-ranking {r:.2f}, latency about {retrieve_ms + n * ms_per_pair} ms unbatched")
```
:::

:::read
A perfect reranker can only reach the retriever's recall@N: 0.70 with 10 candidates, 0.93 with 200, at 40 times the reranking cost. In practice the curve flattens (here from 50 to 200 buys 5 points for 750 ms more), so N is usually set where the retriever's recall stops climbing quickly.
:::

@@before Ship it
:::read
The tiny cross-encoder's training loss falls to almost zero (0.54 to 0.0003), which already suggests memorization. The results confirm it. For "how do we abort a multipart upload", it keeps the right document first. For "centralized authorization check function", the retriever had the right document (`check_permission`, d4) first, and the reranker moved a document about *cancelling jobs* (d8) above it. It also favours d8 for the job-cancelling query, so it has learned a bias toward that document. Its scores also exceed 1, so they are not probabilities. A reranker must be evaluated against the retriever's ranking before it ships.
:::

:::recap What to keep from this lesson
- Bi-encoders retrieve fast; cross-encoders re-rank accurately.
- Re-rank only the top N candidates.
- The retriever's recall@N caps what re-ranking can achieve.
- Small rerankers overfit; compare against the retriever's own order.
- Measure latency and quality together.
:::

## Solutions

??? sol | B1 · Slow and useless reranking
Check N: re-ranking hundreds of candidates unbatched explains the latency, so batch the pairs and lower N to where the retriever's recall levels off. Check quality on a labelled set: if the reranker does not beat the retriever's order (or a general-purpose pretrained reranker), it is not worth its cost; it may be undertrained or mismatched to the domain.
