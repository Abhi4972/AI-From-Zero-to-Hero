@@top The situation
:::plain In plain words first
Pods restart in a loop exactly during traffic spikes. The liveness probe generated a token on every check, so it waited in the same queue as the users, timed out under load, and killed the busiest pod, which pushed its users onto the next one. The case trains the idea that a probe is a client: if it shares the users' queue, it fails exactly when restarting hurts most.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A liveness probe that does real work competes with user requests.
- ✗ A shorter probe timeout makes failure detection safer.
  Under load it makes healthy-but-busy pods fail the probe and restart.
- ✓ Readiness decides whether a pod receives traffic; liveness decides whether it is restarted.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- A probe is a client; do not put it in the user queue.
- Use a cheap readiness check for traffic decisions.
- Make liveness check that the process is alive, not that it can generate.
- Restarting a busy pod moves its load to the next pod.
:::
@@
