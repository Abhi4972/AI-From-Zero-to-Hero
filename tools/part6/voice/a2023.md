@@top The problem
:::plain In plain words first
"Answer with citations" is the promise of most document chatbots. A citation can mean two very different things: the quoted text really exists in the source (support), and the quoted text actually answers the question (relevance). The first can be checked by a program; the second usually needs a person.

This project builds a question-answering pipeline that keeps the two apart. Documents are split into chunks with exact offsets; chunks are ranked with an inspectable keyword score; the answerer must return an exact quote and its source, which is validated against the text; and an optional LangChain splitter is adapted so that it still produces the same exact offsets.
:::
@@

@@end Step 3 · Accept only answers grounded in retrieved spans
:::check
Which statements are right?

- ✓ An answer whose quote is not an exact substring of its cited chunk is rejected.
- ✗ A validated quote proves the answer is correct.
  It proves the words exist in the source, not that they answer the question or that the source is true.
- ✓ When retrieval returns nothing, the system abstains without calling the model.
- ✗ A framework splitter can be trusted to keep offsets.
  The adapter converts its chunks back to exact source spans and rejects any chunk whose text was rewritten.
:::
@@

It quotes "Private answers never enter the shared cache.", which does not answer the question. Both sentences share exactly one word with the question ("cache"; "expire" appears nowhere), so the tie-break picked the sentence that sorts first. The citation is perfectly supported: offsets 56 to 101 of `cache.txt`, with the file's SHA-256. And the report says so honestly: `relevance: "lexical overlap; human judgment still required"`. This is the project's point in one run: support is checkable, relevance is not, and "sixty seconds" was in the document all along under a different word.

@@before Build it on your machine
:::broken
A support bot shows answers with a green "cited" badge whenever the quote validates. Users trust the badge and act on answers like the one above. What should the badge claim, and what extra signal would catch this case? (Solution B1.)
:::

:::recap What to keep from this project
- Keep source identity, content hash and exact offsets for every chunk.
- Rank with a score you can inspect; know it misses synonyms.
- Require an exact quote and source; validate both.
- Support (the words exist) is not relevance (the words answer).
- Adapt framework components to your evidence contract, not the other way round.
:::

@@end Exercises
1. How would you make "When does cache expire?" retrieve the sixty-seconds sentence without a neural model?

3. What should the answerer do when two chunks give conflicting quotes?

## Solutions

??? sol | 1. Without a neural model
Add an explicit synonym map (`expire` → `retain`, `ttl`, `seconds`) applied to the query, or add a rule for "when" questions to prefer sentences with a time expression. Both are visible, testable policies, and both need labelled questions to check they help more than they hurt.
???

??? sol | 2. The hash
Documents change. The hash pins the citation to the exact text that was quoted, so a later reader can tell whether the source still says the same thing.
???

??? sol | 3. Conflicting quotes
Return both with their sources and mark the answer as needing review, rather than choosing one. A writer that paraphrases conflicting evidence into one sentence hides the disagreement.
???

??? sol | B1 · A misleading badge
The badge should say "quote found in source", not "answer verified". A relevance signal, such as the query terms covered by the quote or a labelled-question check, would have flagged an answer about privacy to a question about expiry.
???
