@@top The problem
:::plain In plain words first
A browser's bookmark export is a tree of folders, often years deep, with the same page saved twice under slightly different addresses. This project turns that pile into a reading path you can act on. It does four things in order: flattens the tree without forgetting which folders each link lived in; decides when two links are really the same page; ranks the pages against topics you name; and writes an HTML page plus a progress file you can edit and feed back in.

The habit it teaches: never throw information away while cleaning. The original URL, the folder path and the reason two links were merged all stay in the output, so a person can check every decision.
:::
@@

@@end Step 2 · Normalize links and explain duplicate groups
:::worked Which links are the same page?
1. `https://EXAMPLE.invalid:443/maps#intro`: the host is lower-cased to `example.invalid`, the default HTTPS port `:443` is dropped, and the fragment `#intro` is removed (it only scrolls within the page). Result: `https://example.invalid/maps`.
2. `https://example.invalid/maps#scale` normalizes to the same string, so the two bookmarks form one group, with the reason recorded.
3. `https://example.invalid/maps?view=print` keeps its query: a query can change what the server returns, so it stays a separate document.
4. `http://example.invalid/maps` stays separate too: a different scheme is a different request, and the project never guesses that they match.
:::

:::check
Which statements are right?

- ✓ Removing the fragment is safe for "same document" because the server never sees it.
- ✗ Dropping every query parameter is a safe way to merge tracking links.
  Some parameters change the page (`?view=print`, `?page=2`); removing them silently merges different documents.
- ✓ Each group keeps the original records, so the exported page can still show the address the user saved.
- ✗ Scoring a duplicate group once per saved copy is fair because the user saved it twice.
  The project scores each keyword once per group, so duplicates do not push a page up the list.
:::

@@end Run the finished project
:::read Reading this output
`imported: 12` and `documents: 11` match the prediction: one pair, `map-1` and `map-2`, collapsed into a single document. `order` is the reading path: pages sorted by topic score, highest first, ties broken by id, so the same input always gives the same order. `later-6` ("Publish a map", notes "Sharing a community map") and `map-1` ("Map basics", notes about coordinates) earn the same score, so the tie rule decides: ids sort alphabetically and `later-6` comes first. That is the point of a stated tie rule: the order is reproducible, even if it is not the order a person would pick. The HTML page and `progress.json` sit in `output/`: reorder or tick items in the browser, save the progress file, and the next run applies it.
:::

@@before Build it on your machine
:::broken
A first version merges `https://shop.invalid/item?id=7` and `https://shop.invalid/item?id=9` into one group, and the reading path silently loses a page. Which normalization step went too far? (Solution B1.)
:::

:::recap What to keep from this project
- Flatten trees but keep every ancestor folder and the original URL.
- Normalize conservatively: lower-case the host, drop default ports and fragments, keep the query.
- Record why links were merged, so a person can audit the grouping.
- Score each keyword once per group, and break ties by id for a stable order.
- Round-trip state through a small, validated progress file.
:::

@@end Exercises

## Solutions

??? sol | 1. A browser import adapter
Read the browser's own export (for example the Netscape bookmark HTML format) in a separate function that produces exactly the same folder tree the importer already accepts. Validation, URL checks and folder limits stay in one place, and the adapter can be tested on its own fixture.
???

??? sol | 2. A tracking-parameter policy
Let the user list parameter names to drop (for example `utm_source`). Apply the list during normalization, and add a receipt to each group: "merged because `utm_source` was removed by your rule". Without the explicit list, keep today's behaviour.
???

??? sol | 3. Prerequisite edges
Treat "read A before B" as a directed graph, check it has no cycles, then sort topologically. Among pages that are ready at the same time, keep the current score order. A cycle is an error that names the pages involved.
???

??? sol | 4. Merging progress after the collection changes
Match old progress to new items by id. Ids that vanished go into a "removed" list, new ids are appended unread, and a completed item whose URL changed is reported as a conflict for the user to decide, never resolved silently.
???

??? sol | B1 · Two products merged
The normalizer removed the query string. Queries can select different content, so they must stay part of the document identity; only the fragment, the default port and the host's case are safe to normalize.
???
