@@top The problem
:::plain In plain words first
API tutorials go stale. A field gets renamed, and step 2 of the tutorial now describes a response that no longer exists, but nobody notices until a reader is stuck. This project turns a tutorial into a test: it pulls out request blocks that the author marked as executable, threads values from one step into the next (create a loan, then read it by its new id), runs the requests against a local test service with timeouts, and exports results a CI system understands, pointing at the exact line of the tutorial that broke.

It never edits the tutorial itself. It drafts a correction and waits for a person to accept it.
:::
@@

@@end Step 2 · Resolve typed variables across steps
:::worked Carrying the loan id forward
1. `create-loan` sends `POST /loans` and captures `loanId` from the response's `id` field, declared as a number. The service returns `"id": 41`, so `loanId = 41`.
2. `read-loan` has the path `/loans/{{loanId}}`. Inside a longer string the placeholder is interpolated as text: `/loans/41`.
3. If a body field were exactly `"{{loanId}}"`, it would become the number `41`, not the string `"41"`: an exact placeholder keeps the captured type.
4. If `create-loan` had failed, there would be no `loanId`; later steps are skipped instead of sending `/loans/{{loanId}}` literally.
:::

:::check
Which statements are right?

- ✓ Only fences marked `request` run; ordinary code blocks in the tutorial are left alone.
- ✗ The runner may call any URL in the tutorial.
  By default only loopback addresses are allowed; a real test endpoint needs an explicit opt-in.
- ✓ A step after a failed step is reported as skipped, with no request sent.
- ✗ When an assertion fails, the runner should fix the tutorial text.
  It drafts a correction; a person accepts it before any documentation changes.
:::

:::read Reading this output
`create-loan` passes: status 201, and the `loanId` capture worked. `read-loan` fails at line 11 of the tutorial: "expected \"Neighborhood Trees\", received undefined" for `bookName`, because the service calls the field `title`. The tutorial even says it "deliberately uses an outdated field". `return-loan` is `skip`, with no request sent, because an earlier step failed. The endpoint is a local server on a random port started for the run. `output/` holds JUnit XML for CI and an HTML report showing the tutorial line next to the real request and response.

@@before Build it on your machine
:::broken
A runner retries every failed request three times. A tutorial step `POST /payments` times out once, is retried, and the test service now holds two payments. Which rule from the exercises prevents this? (Solution B1.)
:::

:::recap What to keep from this project
- Execute only blocks the author marked as executable.
- Capture values with declared types and thread them explicitly.
- Run against loopback by default, with timeouts.
- Skip dependent steps after a failure; report each step's tutorial line.
- Propose corrections; never rewrite the tutorial automatically.
:::
@@

@@end Exercises

## Solutions

??? sol | 1. Multi-file tutorials
Add the file path to each extracted step and carry it into receipts, JUnit names and the HTML report, so a failure reads "guide/loans.md:11" instead of just a line number.
???

??? sol | 2. Nullable values
Declare the type as, for example, `number|null`. Capturing `null` is then valid and explicit, and a later placeholder that receives `null` must be handled by a stated rule instead of becoming the string "null".
???

??? sol | 3. Retries for idempotent steps only
Let a step declare `retry: n`, and accept it only for GET, PUT and DELETE, which are idempotent by HTTP's definition. POST retries stay forbidden unless the API supports an idempotency key and the step sends one.
???

??? sol | 4. Review-only patches
Turn `accepted-corrections.json` into a patch file or pull request against the documentation, never a direct write. The reviewer sees the line, the old text, the proposal and the failing evidence together.
???

??? sol | B1 · A duplicated payment
Retrying a POST is not safe: the first request may have succeeded before the timeout. Allow retries only for idempotent methods, or for POSTs that carry an idempotency key.
???
