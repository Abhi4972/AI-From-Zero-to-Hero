@@top The situation
:::plain In plain words first
A laptop server dies with "Insufficient Memory" at 32 concurrent requests, while its own log says the token cache was only 5 percent used. The obvious conclusion ("the laptop is too small") is wrong. The case trains you to notice when the memory a component reports is not the memory that ran out: here, an automatic setting reserved most of the free memory for a cache, leaving nothing for the computation itself.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A cache that is nearly empty when the process dies points to memory used somewhere the cache does not count.
- ✗ Automatic memory fractions are always safe on a laptop.
  They are computed from a snapshot of free memory; other programs and activations can need more later.
- ✓ Setting the cache's share explicitly let the same benchmark finish 128 of 128 requests at concurrency 32.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- An almost empty pool at the crash means the memory went elsewhere.
- Set memory shares yourself on machines that run anything else.
- Read the pool size and the maximum token count after every change.
- Do not shrink the demo before understanding the crash.
:::
@@
