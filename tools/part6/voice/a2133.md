@@top The situation
:::plain In plain words first
A benchmark of a split prefill/decode deployment reports 240 of 240 requests successful at 8 per second. In fact the cache transfer between the two GPUs failed and the router counted empty responses as successes. The case trains distrusting a benchmark that looks perfect: check that successes contain output, and refuse runs whose numbers are physically impossible.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ An empty response counted as a success makes a benchmark lie.
- ✗ 100 percent success at a high rate proves the split design works.
  Here no request produced tokens; there is no valid result for the split under load.
- ✓ A benchmark kit should reject runs where every request has no first token.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Check that successes contain real output.
- Treat perfect results as a reason to look closer.
- Do not claim a result the run did not measure.
- Fix the tooling so it refuses impossible runs.
:::
@@
