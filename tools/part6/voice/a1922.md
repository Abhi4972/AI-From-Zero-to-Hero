@@top Why JSON-RPC stays the lingua franca
:::plain In plain words first
A harness talks to tool servers by sending small messages and getting replies. **JSON-RPC 2.0** is the simple, long-standing format for that: a **request** has an `id`, a `method` name and `params`; the **response** carries the same `id` with either a `result` or an `error`; a **notification** has no `id` and gets no reply (used for progress and logs); and a **batch** is a list of these. Over **stdio**, each message is one line of JSON ended by a newline. This lesson builds that transport by hand, including the five standard error codes, so that a broken line produces an error reply and the stream carries on instead of dying. MCP uses the same envelope, so this is what every tool call rides on.
:::
@@

@@end Notifications and asymmetric flows
:::worked Four lines, four outcomes
The client writes four lines to the server's input.

1. `{"jsonrpc":"2.0","id":1,"method":"add","params":{"a":2,"b":3}}` → `{"id":1,"result":5}`.
2. `{"jsonrpc":"2.0","id":2,"method":"add","params":{"a":2}}` → `{"id":2,"error":{"code":-32602,...}}`: invalid params.
3. `{"jsonrpc":"2.0", "id":3, "method":` (cut off) → `{"id":null,"error":{"code":-32700,...}}`: a parse error, so no id could be read.
4. `{"jsonrpc":"2.0","method":"log","params":{"msg":"hi"}}` → nothing: a notification.
5. After line 3 the server keeps reading; the client matches replies to calls by `id`, which is why replies can arrive in any order.
:::

:::check
Which statements are right?

- ✓ A parse error is answered with `"id": null`.
- ✗ The server should reply to notifications so the client knows they arrived.
  Notifications have no id; a reply could not be matched to anything.
- ✓ An exception in a handler becomes error -32603 and the loop continues.
- ✗ One malformed line means the stream is corrupt and must be closed.
  Newline framing lets the next line be parsed fresh.
:::

:::visual A minimal line-by-line server
```python run
import io, json
def handle(method, params):
    if method == "add": return params["a"] + params["b"]
    raise KeyError(method)

def serve(inp, out):
    def one(msg):
        if not isinstance(msg, dict) or msg.get("jsonrpc") != "2.0" or "method" not in msg:
            return {"jsonrpc": "2.0", "id": msg.get("id") if isinstance(msg, dict) else None, "error": {"code": -32600, "message": "invalid request"}}
        try: result = handle(msg["method"], msg.get("params", {}))
        except KeyError: result = None; err = {"code": -32601, "message": "method not found"}
        else: err = None
        if "id" not in msg: return None                         # notification: never answered
        return {"jsonrpc": "2.0", "id": msg["id"], **({"error": err} if err else {"result": result})}
    for line in inp:
        try: msg = json.loads(line)
        except json.JSONDecodeError:
            out.write(json.dumps({"jsonrpc": "2.0", "id": None, "error": {"code": -32700, "message": "parse error"}}) + "\n"); continue
        reply = [r for r in map(one, msg) if r] if isinstance(msg, list) else one(msg)
        if reply: out.write(json.dumps(reply) + "\n")

lines = ['{"jsonrpc":"2.0","id":1,"method":"add","params":{"a":2,"b":3}}',
         '{"jsonrpc":"2.0","id":2,"method":',
         '[{"jsonrpc":"2.0","id":3,"method":"add","params":{"a":1,"b":1}},{"jsonrpc":"2.0","method":"log"},{"jsonrpc":"2.0","id":4,"method":"nope"}]']
out = io.StringIO(); serve(io.StringIO("\n".join(lines) + "\n"), out)
print(out.getvalue())
```
:::

:::read
Three input lines give three output lines: the sum, a parse error with `id: null` for the cut-off line, and a batch reply with two entries, because the notification in the batch is silently dropped while the unknown method gets its own error. The stream survives the broken line in the middle, which is the property the whole framing scheme exists to guarantee.
:::

@@before Going further
:::read
The demo feeds a scripted sequence through in-memory streams and prints every reply: a result, then invalid params (-32602), method not found (-32601), an internal error (-32603) that carries the exception class in `data`, a batch reply with two results, and finally a parse error with `id: null` for a malformed line. Every code from the table appears, and the server reached the end of the input without stopping.
:::

:::broken
A server reads stdin with `sys.stdin.read()` and parses the whole input as one JSON value. It works in tests with a single request. Under a real client, nothing is ever answered. Why? (Solution B1.)
:::

:::recap What to keep from this lesson
- Requests have ids; responses echo them; notifications have none and get no reply.
- Five standard error codes; parse errors reply with a null id.
- One message per line; a bad line never poisons the stream.
- Batches reply with one entry per request, none for notifications.
- The transport knows nothing about tools; a handler does the dispatch.
:::

@@end Going further
## Solutions

??? sol | B1 · Waiting for the end of a stream that never ends
`read()` waits for end of input, but a client keeps the pipe open for the whole session, so the server never gets to parse anything. Read line by line (`for line in sys.stdin` or `readline()`), handle each message as it arrives, and flush the output after each reply.
???
