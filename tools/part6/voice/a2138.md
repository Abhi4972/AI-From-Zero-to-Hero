@@top The situation
:::plain In plain words first
When a load balancer closed a long-lived stream, the planner resent the request, and the whole test suite ran a second time, doubling the bill and hiding a flaky test. A streaming request is a command plus a view of its progress; resending repeats the command. The case trains reconnecting to the existing task instead of repeating the work.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A dropped connection ends the view, not the task.
- ✗ Resending the request is a safe way to resume a stream.
  It starts the work again.
- ✓ Subscribing to the task by id resumes watching the same run.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Separate commands from views of their progress.
- On a dropped stream, reattach to the task by id.
- Rebuild local state from the first snapshot.
- Count side effects, not just messages.
:::
@@
