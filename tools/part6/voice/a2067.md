@@top The problem
:::plain In plain words first
An agent that reads cloud metrics and logs during an incident is helpful; one that can also delete resources is a risk, especially when its plan comes from a model. The safe design separates the two: the model proposes, a deterministic validator decides what is allowed, and every call leaves a receipt.

This project builds that cloud incident reader. A plan is validated against named operations and resources before any provider call. Reads run within a step budget and an output size budget. Transient timeouts are retried and identical reads are served from a cache, each recorded in a receipt. Finally the real AWS Strands agent framework produces a plan with a local model, and the same validator checks it.
:::
@@

@@end Step 1 · Validate a scoped cloud inspection plan
:::visual The validator grants authority, not the model
```python run
ALLOWED_OPS = {"metrics.read", "logs.read"}
SCOPE = {"checkout"}
def validate(plan):
    for step in plan:
        if step["operation"] not in ALLOWED_OPS: return f"rejected: operation {step['operation']!r} not allowed"
        if step["resource"] not in SCOPE: return f"rejected: resource {step['resource']!r} out of scope"
    return "accepted"
print(validate([{"operation": "metrics.read", "resource": "checkout"}, {"operation": "logs.read", "resource": "checkout"}]))
print(validate([{"operation": "metrics.read", "resource": "checkout"}, {"operation": "instances.delete", "resource": "checkout"}]))
print(validate([{"operation": "logs.read", "resource": "billing"}]))
```
:::

:::read
A plan of two reads on `checkout` is accepted. A plan that sneaks in a delete is rejected as a whole, before the first read runs; partial execution of a bad plan is how damage happens. A read of `billing` is rejected because the incident's scope is `checkout`. The model can suggest anything; only this list of operations and resources gives permission.
:::

@@end Step 3 · Retry transient reads and reuse completed requests
:::check
Which statements are right?

- ✓ Steps are charged before an operation starts.
- ✗ A permission error should be retried in case it was transient.
  Only timeouts are transient here; a permission failure is returned after one call.
- ✓ A repeated identical read is served from cache, with a receipt saying so.
- ✗ Output size does not need a budget because reads are harmless.
  Large outputs fill the agent's context and cost money; they are budgeted too.

:::recap What to keep from this project
- The model proposes; a deterministic validator authorizes.
- Validate the whole plan before any call.
- Budget steps and output size; charge before work.
- Retry only transient failures; cache identical reads; receipt everything.
- Use the same validator around the real framework.
:::

@@end Exercises
1. Why reject the whole plan instead of skipping the bad step?
2. How would you scope the cloud credentials themselves?
3. What should a cache key include?

## Solutions

??? sol | 1. Reject the whole plan
A plan containing a forbidden step shows the model misunderstood the task; running its other steps acts on that misunderstanding. Rejecting it whole is simpler to reason about and safer.
???

??? sol | 2. Scoped credentials
Give the agent's role only read permissions on the specific resources (least privilege), so even a bug in the validator cannot delete anything. The validator and the credentials are two independent layers.
???

??? sol | 3. The cache key
The operation, the resource and every parameter that changes the result (time window, filters), in a canonical form. Two requests with different windows must never share a cached answer.
???

??? sol | B1 · Too much authority
The validator: `instances.delete` is not an allowed operation, so the plan would be rejected before any call. Read-only credentials would have stopped it a second time.
???
