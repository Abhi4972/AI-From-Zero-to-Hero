@@top The problem
:::plain In plain words first
Calling one model provider is a single point of failure. A gateway that falls back to a second provider helps, if it knows when to fall back. Retrying a rate limit (429) or a server error (5xx) on another provider makes sense. Retrying a malformed request (400) everywhere just multiplies the failure. Following a redirect could send your API key somewhere you never configured.

This project builds a small HTTP gateway in Go with explicit failure rules: validated provider URLs, a status classifier with three outcomes, one bounded attempt (size and time limits, no redirects), and a router that walks providers in order under a total attempt budget and one overall deadline, keeping each provider's credentials to itself.
:::
@@

@@end Step 2 · Classify failures without retrying everything
:::visual Which statuses allow a fallback?
```python run
def classify(status):
    if not 100 <= status <= 599: return "invalid"
    if 200 <= status <= 299: return "success"
    if status == 429 or 500 <= status <= 599: return "fallback"
    return "terminal"
for s in (204, 301, 400, 408, 429, 500, 503, 600):
    print(s, classify(s))
```
:::

:::read
2xx succeeds. 429 (rate limited) and any 5xx mean "this provider cannot serve you right now", so the next provider may. Everything else, including 400 (your request is wrong) and 408 (in this policy), is terminal: another provider would most likely fail the same way, or the request may already have had effects. 301 is terminal too, because redirects are disabled rather than followed. 600 is not a valid HTTP status at all.
:::
@@

@@end Step 3 · Send one bounded HTTP request
:::check
Which statements are right?

- ✓ An endpoint URL with `?api_key=...` is rejected, because keys belong in headers from the environment.
- ✗ Plain HTTP is fine for any provider on a private network.
  Only HTTPS, or HTTP on exactly localhost, 127.0.0.1 or ::1, is accepted.
- ✓ Each attempt is charged against the budget before it is made.
- ✗ A response body of any size is accepted if the status is 200.
  Bodies over the byte limit fail the attempt.
:::

:::recap What to keep from this project
- Validate provider endpoints before any connection.
- Classify statuses: success, fallback (429, 5xx) or terminal.
- Bound each attempt in bytes and time; never follow redirects.
- Route under a total attempt budget and one overall deadline.
- Each provider's credentials stay with that provider.
:::

@@end Exercises

## Solutions

??? sol | 1. A key in the query string
URLs end up in logs, proxies and error messages, so a key in the query leaks easily. The validator rejects queries entirely. Passing validation only means the URL is well formed; whether the service is trustworthy is the operator's decision.
???

??? sol | 2. Predicting outcomes
204 success; 301 terminal (redirects are not followed); 408 terminal in this policy; 429 fallback; 500 fallback; 600 invalid. If you later decide to retry 408, write down why the request is safe to repeat first.
???

??? sol | 3. Body limits and redirects
A body of exactly the limit is accepted, one byte more fails. A redirect returns its 3xx status as terminal, and the second test server's request count stays at zero, proving the redirect was not followed.
???

??? sol | 4. Your own providers
Copy the example config, set each provider's URL, model and the name of the environment variable that holds its key, and run the gateway with `--config` and a request file. Keys are read from the environment at startup and never written to the config.
???

??? sol | B1 · Retrying a bad request
Classify statuses: 400 is terminal, so the gateway stops after the first provider and returns the error at once.
???
