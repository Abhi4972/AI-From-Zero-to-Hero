@@top The problem
:::plain In plain words first
You want one skill available in several agents, each of which expects a slightly different folder and header format. Copying files by hand drifts; a careless installer can follow a symlink outside its folder, leave half a skill behind when a write fails, or overwrite the changes a user made to their local copy.

This project builds a careful installer. It validates the bundle's paths before touching disk, translates only the small metadata header per agent while keeping the instructions byte-for-byte, hashes the content so changes are detectable, installs atomically by staging and renaming, and refuses an upgrade that would overwrite local edits.
:::
@@

@@end Step 2 · Translate metadata and hash content
:::visual A digest that ignores file order
```python run
import hashlib, json
def digest(files):
    h = hashlib.sha256()
    for path, content in sorted(files.items()):           # sorted: insertion order cannot matter
        h.update(json.dumps([path, content]).encode())
    return h.hexdigest()[:16]
a = {"SKILL.md": "Check releases.", "references/checklist.md": "1. tests"}
b = {"references/checklist.md": "1. tests", "SKILL.md": "Check releases."}
c = dict(a, **{"references/checklist.md": "1. tests\n2. my note"})
print("a", digest(a)); print("b", digest(b)); print("c", digest(c))
```
:::

:::read
The same two files in a different order give the same digest, because paths are sorted first. Adding one line to the checklist changes it completely. Encoding each pair as JSON keeps the boundary between path and content unambiguous. A digest proves content did or did not change; it says nothing about who published it, which would need a signature.
:::
@@

@@end Step 4 · Protect edits during upgrades
:::check
Which statements are right?

- ✓ Paths with `..`, absolute paths, drive letters and backslashes are rejected before anything is written.
- ✗ Writing files one by one into the destination is atomic enough.
  A failure halfway leaves a mixed installation; staging and one rename avoids it.
- ✓ An upgrade is refused if a tracked file changed or an unmanaged file appeared.
- ✗ The digest proves the bundle came from its publisher.
  It detects changes; identity needs signatures.
:::

:::recap What to keep from this project
- Validate every relative path before touching disk.
- Translate metadata per agent; keep instructions and references byte-for-byte.
- Hash sorted path and content pairs.
- Stage, then rename; keep a backup for rollback; reject symlinks.
- Refuse upgrades over local edits.

@@end Exercises

## Solutions

??? sol | 1. Rejecting backslashes everywhere
A bundle is meant to install on any machine. On Windows `a\..\..\x` is a traversal; accepting it on Linux would make the same bundle dangerous elsewhere. Portable rules must be the strictest common subset.
???

??? sol | 2. A quote in the description
Write the header value as a quoted string with escaping (JSON-compatible double quotes), and test that the validator parses the installed header back to exactly the original description.
???

??? sol | 3. A failed write before the rename
Nothing changes for a reader: the old installation stays in place and the staging directory is removed. That is the point of staging beside the destination and renaming at the end.
???

??? sol | 4. A reviewable merge
For each tracked file: the old installed version, the user's edited version and the new source version, with a three-way diff, and an explicit choice per file. Unmanaged files are listed so the user can move them into the source bundle.
???

??? sol | B1 · Delete then copy
A missing or half-copied skill: the old one is gone and the new one is incomplete. Staging the full bundle beside the destination and renaming it in one step, with the old installation kept as a backup, means a failure leaves the previous version working.
???
