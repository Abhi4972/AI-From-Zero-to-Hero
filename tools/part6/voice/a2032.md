@@top The problem
:::plain In plain words first
"Rewrite this in plain language" is a common request to a model, and a risky one: a shorter sentence can drop a number, change it, or lose the definition of a term the reader needs. This project builds a rewrite desk where every change is checked against what must not change.

It splits the text into paragraphs and records the facts in each (numbers, protected terms). It produces a candidate rewrite per paragraph and says where the candidate came from (a recorded model proposal, or visible phrase substitutions). It compares readability and facts, flagging changed numbers and missing definitions. Only proposals a person accepts are applied; everything else keeps the original text.
:::
@@

@@end Step 3 · Compare omissions, numbers and readability measures
:::worked What the checker catches
Original p2: "A projection, a method for representing a curved surface on a flat map, introduces distortion. At this point in time, our example uses a 15% area difference."

Proposal p2: "A projection shows a curved surface on a flat map. This example uses a 10% area difference."

1. Readability improved: fewer words, shorter sentences, "at this point in time" gone.
2. Numbers: the original has 15, the proposal 10. **Numeric facts changed.**
3. Definitions: "projection" must keep its definition, "a method for representing a curved surface on a flat map". The proposal paraphrases it. **Missing required definition.**
4. Both flags appear beside the paragraph; accepting it anyway is a deliberate, recorded decision.
:::

:::check
Which statements are right?

- ✓ Every proposal states its method, so a reader knows whether a model or a rule wrote it.
- ✗ If the readability measures improve, the rewrite is better.
  Shorter text that changes a number is worse; facts are checked separately.
- ✓ Paragraphs without an accepted proposal keep their original text in the export.
- ✗ Lexical checks catch every change of meaning.
  They catch numbers and named terms; a person still reads for meaning.
:::

@@before Build it on your machine

:::recap What to keep from this project
- Record each paragraph's facts before rewriting.
- Label where each proposal came from.
- Check numbers and required definitions, not just readability.
- Apply only accepted proposals; keep the original otherwise.
- Keep a change record of every decision.
:::

@@end Exercises

## Solutions

??? sol | 1. Dates and identifiers
Add extractors for ISO dates and identifiers (for example ticket keys) to the paragraph facts, with tests where a rewrite reformats a date ("1 Oct 2026" vs "2026-10-01") so you decide whether that counts as a change.
???

??? sol | 2. A real provider adapter
Read the API key from the environment only when the user opts in, call the provider for each paragraph, and record the model name and version as the proposal's method. Keep recorded proposals for tests.
???

??? sol | 3. A meaning checklist
Add per-paragraph questions for the reviewer ("Is any condition dropped?", "Is any instruction weakened?") and record their answers. State in the interface that automatic checks cover numbers and terms only.
???

??? sol | 4. Reviewer identity and time
Accept `reviewer` and `decidedAt` in the decisions file and copy them into the change record. They are claims supplied by the author, not authentication.
???

??? sol | B1 · A dropped number
The numeric check: the original had "2" and the rewrite has no number. Nothing lexical would flag a weakened instruction without a number, such as "always" becoming "usually"; that needs a person reading for meaning.
???
