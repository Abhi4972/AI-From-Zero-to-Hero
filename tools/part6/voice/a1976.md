@@top The problem
:::plain In plain words first
Distributed training rests on four **collective operations**, each run by every process (**rank**) together. **All-reduce**: every rank ends with the sum of everyone's tensors (used to average gradients). **Broadcast**: one rank's tensor is copied to all. **All-gather**: every rank ends with all ranks' pieces concatenated. **Reduce-scatter**: the sum is computed, but each rank keeps only its own slice. This lesson builds all four on top of plain process queues and checks them against PyTorch's **gloo** backend. The central algorithm is the **ring all-reduce**: ranks pass chunks around a ring, first adding (reduce-scatter), then copying (all-gather), so each rank sends about twice the data size whatever the number of ranks.
:::

@@end Idea 3 · Verify against gloo
:::math Bytes sent per rank in a ring all-reduce
With $N$ ranks and a tensor of $T$ bytes split into $N$ chunks:

$$\text{bytes per rank}=2\,(N-1)\,\frac{T}{N}$$

$N-1$ steps of reduce-scatter and $N-1$ steps of all-gather, each sending one chunk of $T/N$ bytes. As $N$ grows, this approaches $2T$, independent of $N$.
:::

:::worked A ring of four
Four ranks hold the numbers 1, 2, 3, 4 in each of four chunk positions (chunk c on rank r holds r + 1).

1. Reduce-scatter, three steps: each rank sends one chunk to the next and adds what it receives. After three steps, each rank holds the full sum, 1 + 2 + 3 + 4 = 10, for exactly one chunk.
2. All-gather, three steps: ranks pass their finished chunks around the ring, copying instead of adding. After three steps every rank has 10 in all four chunks.
3. Each rank sent 6 chunks of size T/4: 1.5 T in total, matching 2 × 3 × T / 4.
4. A naive "send everything to rank 0, then broadcast" would make rank 0 receive 3T and send 3T: a bottleneck that grows with N.
:::

:::check
Which statements are right?

- ✓ All-reduce leaves every rank with the same summed tensor.
- ✗ Reduce-scatter leaves every rank with the full sum.
  Each rank keeps only its own slice of the sum.
- ✓ A ring all-reduce is reduce-scatter followed by all-gather.
- ✗ Ring all-reduce traffic per rank grows linearly with the number of ranks.
  It approaches 2T and stays there.
:::

:::visual A ring all-reduce simulated in one process
```python run
def ring_allreduce(data):                      # data[r][c]: rank r's value for chunk c
    n = len(data); sent = [0] * n
    for step in range(n - 1):                  # reduce-scatter
        msgs = [(r, (r - step) % n, data[r][(r - step) % n]) for r in range(n)]
        for r, c, v in msgs: data[(r + 1) % n][c] += v; sent[r] += 1
    for step in range(n - 1):                  # all-gather
        msgs = [(r, (r + 1 - step) % n, data[r][(r + 1 - step) % n]) for r in range(n)]
        for r, c, v in msgs: data[(r + 1) % n][c] = v; sent[r] += 1
    return data, sent

data, sent = ring_allreduce([[r + 1] * 4 for r in range(4)])
print("result on every rank:", data)
print("chunks sent per rank:", sent)
for n in (4, 64):
    print(f"N={n:2d}: bytes per rank for T=256 -> {2 * (n - 1) * 256 / n:.0f}")
```
:::

:::read
Every rank ends with [10, 10, 10, 10] after sending 6 chunks, as in the worked example. For a 256-byte tensor each rank sends 384 bytes with 4 ranks and 504 with 64: the cost per rank barely grows, which is why the ring is the standard algorithm for large gradient all-reduces.
:::

@@before Ship it
:::read
All four operations built on queues match gloo: broadcast and all-gather exactly, all-reduce and reduce-scatter to about 5e-7, which is floating-point rounding from summing in a different order. The measured all-reduce traffic is 384 bytes per rank, exactly 2T(N − 1)/N for T = 256 bytes and N = 4. (This demo passes tensors between processes; on this site's build machine that required switching PyTorch to file-system sharing, which does not change the results.)
:::

:::broken
A team writes its own all-reduce in which rank 0 receives every tensor, sums them, and broadcasts the result. It works with 4 GPUs but becomes the bottleneck at 64. Why? (Solution B1.)

:::recap What to keep from this lesson
- Four collectives: all-reduce, broadcast, all-gather, reduce-scatter.
- Ring all-reduce = reduce-scatter + all-gather.
- Each rank sends about 2T bytes whatever the number of ranks.
- Verify hand-built collectives against a reference backend.
- Small float differences come from summation order.

## Solutions

??? sol | P2 · A receive timeout
Wrap every queue `get` in a deadline (`get(timeout=…)`) and raise an error naming the rank and step that stalled, instead of waiting forever. A distributed job that hangs silently is much harder to debug than one that fails with "rank 2 waited 30 s for rank 1 at reduce-scatter step 2".
???

??? sol | B1 · A central bottleneck
Rank 0 must receive N − 1 full tensors and send N − 1 full tensors every step, so its traffic grows linearly with N while the others sit idle. A ring spreads the work evenly: every rank sends about 2T regardless of N.
???
