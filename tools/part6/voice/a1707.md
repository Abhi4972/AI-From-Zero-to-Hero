@@top The problem
:::plain In plain words first
The cost of each generated token depends on four choices stacked on top of each other: the **GPU generation** (NVIDIA's Hopper H100/H200 or the newer Blackwell B200/GB200), the **precision** the numbers are stored in (16-bit, 8-bit FP8 or 4-bit NVFP4), the **serving engine** (vLLM, SGLang, or NVIDIA's own TensorRT-LLM), and the **orchestration** around it (NVIDIA Dynamo splits work across GPUs). Each choice multiplies the others. Fewer bits per weight means less memory to read for every token, and reading memory is what limits generation speed. The catch: the cheapest combination only exists on NVIDIA hardware with NVIDIA's closed software, and 4-bit weights can hurt quality on reasoning tasks, so you trade portability and some accuracy for price.
:::
@@

@@end Idea 7 · The disaggregation bonus
:::math
**The memory-bandwidth ceiling for decode.** At batch size 1, generating a token reads every active weight once. With $P_{\text{active}}$ active parameters stored at $b$ bytes each and memory bandwidth $B$ bytes per second,

$$\text{tokens/s} \le \frac{B}{P_{\text{active}} \cdot b}$$

Halving $b$ (16-bit → 8-bit → 4-bit) doubles the ceiling; a mixture-of-experts model reads only its active experts, so $P_{\text{active}}$ is what counts, not the total.
:::

:::worked A 70B dense model, one request at a time
1. H100, BF16: bandwidth about 3.35 TB/s; weights 70B × 2 bytes = 140 GB, more than one 80 GB GPU holds, so it needs at least two, but the per-token read is still 140 GB. Ceiling ≈ 3,350 / 140 ≈ 24 tokens/s.
2. H100, FP8: 70 GB per token. Ceiling ≈ 48 tokens/s.
3. B200, NVFP4 weights: about 8 TB/s and 35 GB per token. Ceiling ≈ 8,000 / 35 ≈ 229 tokens/s.
4. So precision gives 2× twice over, and the hardware another 2.4×. The rest of the "7×–15×" figures quoted for Blackwell come from batching, multi-token prediction and disaggregated serving on top.
:::

:::check
Which statements are right?

- ✗ NVFP4 can be used for the KV cache too.
  Keys and values span a wide range; 4-bit KV loses too much. FP8 is the floor for KV cache.
- ✓ A mixture-of-experts model's decode speed depends on its active parameters.
- ✓ TensorRT-LLM engines are compiled for a specific GPU model.
- ✗ NVFP4 weights are safe for every workload.
  Reasoning and long-context code can lose several points; check on your own evaluation set.
:::

:::predict
A 120B mixture-of-experts model has 36B active parameters. Before running the code below: on an H100 in FP8, roughly how many tokens per second can one request get at most?
:::

:::visual The bandwidth ceiling, stack by stack
```python run
stacks = [("H100 BF16", 3.35e12, 2), ("H100 FP8", 3.35e12, 1), ("H200 FP8", 4.8e12, 1), ("B200 NVFP4", 8.0e12, 0.5)]
for name, active in (("70B dense", 70e9), ("120B MoE, 36B active", 36e9)):
    print(name)
    for label, bandwidth, bytes_per in stacks:
        print(f"  {label:11s} {bandwidth / (active * bytes_per):6.0f} tokens/s ceiling")
```
:::

:::read
For the MoE model on H100 FP8 the ceiling is about 93 tokens/s for one request, the same figure `code/main.py` prints. Each halving of bytes per weight doubles the ceiling, and the B200 adds its higher bandwidth. The script's B200 rows show more than this (about 658 and 1,280 tokens/s) because it also multiplies in the engine and multi-token-prediction gains; treat those as the vendor's claims, and the ceilings above as the physics.
:::

:::recap What to keep from this lesson
- Decode speed per request is capped by bandwidth ÷ bytes of active weights.
- Precision, hardware, engine and orchestration multiply; Blackwell + TRT-LLM + Dynamo is the cheapest stack in 2026.
- NVFP4 for weights and activations, FP8 for KV cache, FP32 for attention accumulation.
- Validate quality on your own evals before shipping 4-bit weights.
- The price is lock-in: TensorRT-LLM runs only on NVIDIA GPUs.

## Solutions

??? sol | P1 · Where the jump comes from
For the 120B MoE with 36B active, the ceilings are about 47 (H100 BF16), 93 (H100 FP8) and 444 tokens/s (B200 at 4 bits and 8 TB/s); the script reports 47, 93 and 1,280. Each precision halving gives 2×, the bandwidth 2.4×, and the script's remaining factor is engine and multi-token-prediction gains. The single largest step is the move to Blackwell with 4-bit weights.
???

??? sol | P5 · 405B at 128k context
Weights: 405B × 0.5 bytes ≈ 203 GB. KV cache for Llama 3.1 405B (126 layers, 8 KV heads of 128) in FP8: 2 × 126 × 8 × 128 × 1 byte ≈ 258 KB per token, so 128k tokens ≈ 33 GB per sequence. About 236 GB for one sequence, well within a GB200 NVL72 rack (72 GPUs, about 13 TB of HBM), and even within two B200s.
???

??? sol | B1 · KV cache in 4 bits
Most of the loss comes from the 4-bit KV cache: attention keys and values span a wide range, and rounding them to 4 bits distorts which earlier tokens get attention, which long reasoning chains depend on. Keep KV in FP8 (and the attention accumulator in FP32); if quality still drops, use FP8 weights for the reasoning model.
