@@top The problem
:::plain In plain words first
An agent with many skills must pick the right one for each request. When it picks wrong, you want to know why: which words matched, which file paths, what the tie rule was. Routing by model judgment alone gives you no such answer.

This project builds a router you can debug. Skills declare keywords, path patterns, a priority, dependencies and permissions. A request is scored with visible reasons (2 points per matched keyword, 3 per matched file path). Dependencies are ordered so prerequisites run first, with cycles caught. And the router abstains, saying "ambiguous" or "blocked", when the top scores are too close or a needed permission is missing.
:::
@@

@@end Step 2 · Score words and repository paths
:::visual Scores with reasons
```python run
import fnmatch, re
skills = {"release-review":  {"keywords": {"release", "replicas"}, "paths": ["deploy/**"]},
          "release-publish": {"keywords": {"publish", "release"}, "paths": ["dist/**"]}}
query, files = "review release replicas release", ["deploy/orchard.yaml", "deploy/orchard.yaml"]
words = set(re.findall(r"\w+", query.lower()))            # repeated words count once
for sid, s in skills.items():
    reasons = [f"keyword:{w}" for w in sorted(s["keywords"] & words)]
    reasons += [f"path:{f}" for f in sorted(set(files)) if any(fnmatch.fnmatch(f, p.replace("**", "*")) for p in s["paths"])]
    score = sum(2 if r.startswith("keyword") else 3 for r in reasons)
    print(sid, score, reasons)
```
:::

:::read
release-review scores 7: two keywords (release, replicas) at 2 each and one path at 3. Repeating "release" in the query and listing the same file twice change nothing, because words and paths are de-duplicated first; otherwise a user could raise a score by repeating themselves. release-publish matches only "release" and scores 2. (This sketch uses Python's `fnmatch` for brevity; the project implements `*` and `**` itself.)
:::

@@end Step 3 · Resolve dependencies before execution
:::check
Which statements are right?

- ✓ A dependency is planned before the skill that requires it.
- ✗ If two skills tie, the router should pick the first one alphabetically and continue.
  If the score gap is below the margin, the outcome is "ambiguous"; the tie rule only orders the explanation.
- ✓ A dependency's permissions are checked as well as the selected skill's.
- ✗ A cycle of dependencies can be broken by running each skill once.
  A cycle is rejected; there is no correct order to run it in.
:::

:::recap What to keep from this project
- Validate the skill catalogue at runtime.
- Score with explicit reasons; de-duplicate words and paths.
- Order dependencies first; reject cycles and unknown ids.
- Check permissions for the whole plan.
- Abstain with "ambiguous" or "blocked" instead of guessing.
:::

@@end Exercises

## Solutions

??? sol | 1. A name that disagrees with its folder
Reject the manifest: the directory says `release-review` and the metadata says `publish`, so the skill's identity is unclear. Making either one win silently could route requests to a skill under the wrong name.
???

??? sol | 2. Two rules for one file
No. They are two descriptions of one observation (this file was touched). Count the file once per skill, otherwise overlapping patterns inflate scores.
???

??? sol | 3. A hidden network permission
The plan includes check-tests, so its permissions are checked too. With only `read` allowed, the outcome becomes `blocked`, naming check-tests and the missing permission, even though release-review itself needs only `read`.
???

??? sol | 4. Tuning a keyword
Collect several real requests that should and should not route to the skill, adjust the keyword or weight, and check all of them, not just the one example. Keep the set as tests so a later change cannot quietly break them.
???

??? sol | B1 · Too close to call
`ambiguous`, with both ranked explanations: a 0.5 gap is below a sensible margin. The caller can then ask the user or a model to choose, instead of running the wrong skill.
???
