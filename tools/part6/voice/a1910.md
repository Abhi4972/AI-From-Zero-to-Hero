@@top Problem
:::plain In plain words first
A **multi-agent software team** splits a coding task between agents with fixed roles: an **architect** writes a plan with clear interfaces, several **coders** implement parts in parallel, each in its own git worktree and sandbox, a **reviewer** approves or requests changes, and a **tester** runs the test suite. Parallel work cuts waiting time, and each agent's context stays focused. The price is at the **handoffs**: plans the coders cannot implement, diffs that conflict, a reviewer approving a broken fix, a tester running against half-written code, and many extra tokens spent passing summaries between roles. The honest question is not "does a team work?" but "does it solve more issues **per dollar** than one good agent?". Model names are a 2026 snapshot.
:::
@@

@@end Build it
:::worked Token amplification
One issue, solved by a single agent in 20,000 tokens. The team version:

1. Architect: reads the issue and writes a plan: 9,000 tokens.
2. Four coders: each reads the plan plus its own slice and implements: 5,000 tokens each, 20,000 in total.
3. Merge, review and test: 5,000 tokens.
4. Total 34,000 tokens: an amplification of 1.7×. The team must solve at least 1.7 times as many issues as the single agent, or solve them meaningfully faster, to be worth it on cost.
:::

:::check
Which statements are right?

- ✓ Each coder works in its own worktree, so parallel edits do not overwrite each other.
- ✗ Adding coders always improves results.
  More coders means more handoffs, more merges and more tokens.
- ✓ The reviewer must not approve changes it wrote or proposed.
- ✗ Higher pass rate means better value.
  Compare cost per solved issue, not just pass rate.
:::

:::predict
Before running the code below: the team solves 7 of 10 issues at about 34,800 tokens per run; the single agent solves 5 of 10 at about 21,700. Which uses fewer tokens per solved issue?
:::

:::visual Cost per solved issue
```python run
import math
runs = {"team": (7, 10, 34_819), "single agent": (5, 10, 21_705)}
for name, (solved, tried, tokens_per_run) in runs.items():
    per_solved = tokens_per_run * tried / solved
    p = solved / tried; se = math.sqrt(p * (1 - p) / tried)
    print(f"{name:13s} pass {p:.0%} (±{1.96 * se:.0%})   tokens per solved issue {per_solved:,.0f}")
```
:::

:::read
The team has the higher pass rate, but the single agent spends fewer tokens per solved issue (about 43,000 against 50,000). And with only 10 trials, the 95% intervals on the two pass rates (roughly ±28% and ±31%) overlap heavily, so the 70% versus 50% difference could be luck. Fifty issues, as the brief asks, is the minimum for a comparison anyone should act on.
:::

@@before Ship it
:::read
One simulated issue passes review and all 412 tests after 12 handoffs and about 35,500 tokens, a quarter of them spent by the architect before any code was written. Across 10 matched trials, the team solves 7 and the single agent 5, at 1.60× the tokens per run. As the visual shows, that makes the team slightly more expensive per solved issue, and the sample is far too small to call the pass-rate difference real.
:::

:::broken
A team's reviewer approved 49 of 50 diffs. Later analysis finds that 6 approved diffs broke behaviour that the tests did not cover. What does the approval rate actually measure, and how would you test the reviewer? (Solution B1.)
:::

:::recap What to keep from this lesson
- Roles: architect, parallel coders in worktrees, reviewer, tester.
- Typed messages on a shared task board make handoffs traceable.
- Handoffs are where failures and extra tokens come from.
- Judge the team by cost per solved issue against one strong agent.
- Use enough trials to separate real differences from noise.
:::

## Solutions

??? sol | P1 · Measuring false approvals
Inject known bugs into a set of diffs (an early `return None`, an off-by-one, a removed check), mix them with clean diffs, and send all to the reviewer blind. The false-approve rate is approved buggy diffs over buggy diffs. Change the reviewer's prompt or give it test results, and re-measure on fresh injected bugs, not the ones used for tuning.
???

??? sol | B1 · Approval rate is not accuracy
A 98% approval rate only says the reviewer rarely objects; with 6 bad diffs among the approved, it missed most problems. Measure the reviewer on diffs with known defects (seeded bugs) and known-good diffs, and report its false-approval and false-rejection rates separately.
???
