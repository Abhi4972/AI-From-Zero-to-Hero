@@top The pipeline
:::plain In plain words first
This lesson glues the evaluation track together. The **runner** reads tasks in the frozen spec format, sends each prompt to a model through an **adapter** (one small interface per model), post-processes the output, scores it with the right metric (including the code-execution scorer), attaches a **calibration report**, and hands everything to the leaderboard step for normalization, bootstrap intervals and the Markdown table. Tasks run in **parallel**, each scored in a **single pass**, and the demo is **self-terminating**: it exits with an error if any stage fails. Three mock models make the run reproducible: one rule-based and correct, one biased, one noisy.
:::
@@

@@end Aggregation
:::worked What the adapter hides
Three models: a local rule-based function, a hosted API, and a model served by a different library.

1. Each needs its own client code: authentication, request format, retries, response parsing.
2. The runner should know none of it. Each adapter exposes one method, `generate(prompt) -> (text, confidence)`.
3. Adding a fourth model is one new adapter; the scorer, calibration and leaderboard code are untouched.
4. Because confidence is part of the interface, calibration can be computed for every model the same way, or marked missing when a model cannot report it.
:::

:::check
Which statements are right?

- ✓ Each model plugs in through one adapter interface.
- ✗ Running tasks in parallel changes their scores.
  Each item is scored independently; order and parallelism should not matter.
- ✓ The demo fails loudly if any stage fails.
- ✗ Two models with the same mean score are equally good.
  Calibration and per-task results can differ sharply.
:::

:::predict
Before running the code below: two models both score 3 of 10. One's confidences are 0.3 throughout; the other says 0.9 on every answer. Which has the better ECE?
:::

:::visual Same accuracy, different trustworthiness
```python run
def ece(preds):
    acc = sum(y for _, y in preds) / len(preds); conf = sum(p for p, _ in preds) / len(preds)
    return abs(acc - conf)             # one populated bin in each case
biased = [(0.3, 1)] * 3 + [(0.3, 0)] * 7
noisy = [(0.9, 1)] * 3 + [(0.9, 0)] * 7
for name, preds in (("honest 0.3", biased), ("always 0.9", noisy)):
    print(f"{name:11s} accuracy {sum(y for _, y in preds) / 10:.1f}  ECE {ece(preds):.2f}")
```
:::

:::read
Same accuracy, very different calibration: the model that says 0.3 is perfectly calibrated (ECE 0), the one that says 0.9 is off by 0.6. A leaderboard sorted only by mean would show them tied; the calibration columns are what tell a user which model's confidence can be trusted.
:::

@@before Going further
:::read
The rule-based model scores 1.00 on all 10 tasks with low calibration error. The biased and noisy models tie at a mean of 0.30, and the paired bootstrap confirms the tie (difference 0, interval −0.40 to +0.30), while both are clearly worse than the rule-based model. The calibration columns separate them: the noisy model's ECE (0.55) and Brier score (0.51) are far worse than the biased model's, the pattern in the visual. Thirty task runs take about a tenth of a second.
:::

:::broken
A team's runner catches every exception from the adapter and scores the item as 0, logging nothing. One model's API key expires mid-run. What does the leaderboard show, and what should the runner do? (Solution B1.)
:::

:::recap What to keep from this lesson
- Spec in, adapter call, post-process, score, calibrate, aggregate.
- One adapter per model; the rest of the pipeline never changes.
- Run in parallel; score each item independently.
- Report accuracy and calibration together.
- Fail loudly on infrastructure errors.
:::

@@end Going further
## Solutions

??? sol | B1 · Infrastructure failures scored as wrong answers
Every item after the key expired scores 0, so the model looks much worse than it is, and nothing says why. Distinguish model failures from infrastructure failures: record adapter errors separately, retry transient ones, and abort or mark the run incomplete when errors exceed a small threshold, instead of folding them into the score.
???
