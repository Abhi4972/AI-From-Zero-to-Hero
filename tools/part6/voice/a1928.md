@@top The problem
:::plain In plain words first
**Observability** means the harness leaves a structured record of everything it did. Two kinds of record are needed. **Traces** are made of **spans**, one per operation (a model call, a tool run, a gate decision), each with a trace id tying it to the whole session, start and end times, a status, and **attributes** named according to the OpenTelemetry **GenAI semantic conventions** (`gen_ai.request.model`, `gen_ai.usage.input_tokens`…), so any standard tool can read them. **Metrics** are running totals: a **counter** of calls per tool and a **histogram** of latencies, exposed in Prometheus text format so you can ask "what is the 95th-percentile latency of `read_file` this hour?". This lesson hand-rolls both with the standard library, writing spans as one JSON object per line.
:::
@@

@@end Why hand-rolled instead of opentelemetry-sdk
:::worked Reading a percentile from histogram buckets
A histogram keeps counts per latency bucket rather than every value. For `run_tests`: 40 calls under 50 ms, 30 more under 100 ms, 25 more under 250 ms, 5 more under 500 ms (100 calls in total).

1. The 95th percentile is the 95th call in sorted order.
2. Cumulative counts: 40 by 50 ms, 70 by 100 ms, 95 by 250 ms. So the 95th call falls exactly at the end of the 100–250 ms bucket.
3. Prometheus estimates within a bucket by linear interpolation, giving 250 ms here; for the 90th percentile it would be 100 + (90 − 70)/25 × 150 = 220 ms.
4. Bucket boundaries set the precision: with no boundary between 100 and 250 ms, nothing finer can be said.
:::

:::check
Which statements are right?

- ✓ All spans of one agent run share a trace id.
- ✗ Any attribute names will do if they are consistent.
  Standard GenAI names are what let existing tools read the traces.
- ✓ Counters only go up; histograms record distributions in buckets.
- ✗ Traces alone answer "what is the p95 latency this hour?".
  That needs aggregated metrics; traces show individual operations.
:::

:::visual Percentiles from buckets
```python run
buckets = [(50, 40), (100, 70), (250, 95), (500, 100)]      # (upper bound in ms, cumulative count)
def quantile(q, buckets):
    total = buckets[-1][1]; target = q * total; lower, below = 0, 0
    for upper, cum in buckets:
        if cum >= target:
            return lower + (upper - lower) * (target - below) / (cum - below)
        lower, below = upper, cum

for q in (0.5, 0.9, 0.95, 0.99):
    print(f"p{int(q * 100):<3d} ~ {quantile(q, buckets):6.1f} ms")
```
:::

:::read
The median comes out at about 67 ms, inside the 50–100 ms bucket; p90 at 220 ms; p95 at the 250 ms boundary; p99 at 450 ms, interpolated across the wide last bucket. Each estimate is only as fine as the buckets around it, which is why latency buckets are usually spaced roughly logarithmically and placed close together around the latencies you have promised users.
:::

:::recap What to keep from this lesson
- One span per operation, joined by a trace id.
- Use the standard GenAI attribute names.
- Counters and histograms answer aggregate questions; traces explain single runs.
- Percentiles from histograms are only as precise as the buckets.
- Keep personal data out of spans and metric labels.

## Solutions

??? sol | B1 · Personal data and exploding labels
Span attributes are copied into tracing backends with broad access and long retention, so emails and full prompts become a privacy leak; record ids or hashes and keep payloads out unless explicitly needed and protected. And a `user_id` label creates one time series per user, which multiplies storage and slows queries (high cardinality); keep labels to small fixed sets such as tool name and status.
