@@top Problem
:::plain In plain words first
Many documents are hard to read as plain text: scanned reports with rotated tables, papers full of equations, charts whose meaning is in the picture. **Vision-first retrieval** skips the error-prone step of converting pages to text (OCR). It treats each page as an image, splits it into small **patches**, and embeds every patch. A query is embedded token by token, and **late interaction** scores a page by matching each query token to its best patch and adding up those best matches (**MaxSim**), the approach of ColPali and its successors. The best pages then go to a vision-language model that answers and points to where on the page the evidence is. The cost is storage: hundreds or thousands of vectors per page instead of one, which is why pruning patches matters. Model names in the brief are a 2026 snapshot.
:::

@@end Build it
:::math MaxSim
$$s(q,d)=\sum_{i=1}^{|q|}\max_{j}\; \mathbf{q}_i\cdot\mathbf{d}_j$$

For every query token $\mathbf{q}_i$, find the page patch $\mathbf{d}_j$ it matches best, and add up those best scores. A page scores high when *each part* of the question finds some region of the page that answers it.
:::

:::worked MaxSim by hand
A query has two token vectors, q1 and q2. A page has three patches. Dot products:

| | patch 1 | patch 2 | patch 3 |
|---|---|---|---|
| q1 | 0.2 | **0.9** | 0.1 |
| q2 | **0.7** | 0.3 | 0.4 |

1. Best patch for q1: 0.9 (patch 2). Best for q2: 0.7 (patch 1).
2. Page score: 0.9 + 0.7 = 1.6.
3. A single pooled page vector would average the patches and blur both matches; MaxSim keeps each token's best local match, which is why it handles tables and charts where the answer lives in one small region.
:::

:::check
Which statements are right?

- ✓ Late interaction scores every query token against every page patch.
- ✗ Vision-first retrieval needs one vector per page.
  It stores many patch vectors per page, which is its main cost.
- ✓ Pruning low-signal patches can cut storage with little loss in ranking.
- ✗ OCR is never useful in a vision-first pipeline.
  It remains a useful extra channel for dense equations and exact text.
:::

:::predict
Before running the code below: page A is a single patch that matches both query tokens moderately; page B has three patches, two of which each match one query token strongly. Which page does MaxSim rank first, and which does a single averaged vector rank first?
:::

:::visual MaxSim against a pooled vector
```python run
def dot(a, b): return sum(x * y for x, y in zip(a, b))
def maxsim(query, page): return sum(max(dot(q, p) for p in page) for q in query)
def pooled(query, page):
    mean = lambda vs: [sum(c) / len(vs) for c in zip(*vs)]
    return dot(mean(query), mean(page))

query = [[1, 0, 0], [0, 1, 0]]                       # two query tokens: "revenue", "2024"
page_a = [[0.7, 0.7, 0]]                            # one patch that vaguely matches both tokens
page_b = [[0.95, 0, 0.1], [0, 0.95, 0.1], [0, 0, 1]] # one patch per query token
for name, page in (("page A", page_a), ("page B", page_b)):
    print(f"{name}: MaxSim {maxsim(query, page):.2f}   pooled {pooled(query, page):.2f}")
```
:::

:::read
The two methods disagree. MaxSim ranks page B first (1.90 against 1.40), because each query token finds a patch that answers it precisely. The pooled vector ranks page A first (0.70 against 0.32): averaging page B's patches mixes its two sharp matches with an irrelevant region, and the blur loses to a page that is vaguely about everything. On real documents, where the answer is often one cell of a table among dozens of other regions, that dilution is what makes single-vector retrieval miss.
:::

The toy retrieves sensible pages for each query: the handwritten lab pages for the question about handwritten figures, the chart pages for the bar-chart question. The pruning ablation is the headline: dropping half the patch vectors keeps the same top three pages (3 of 3 overlap), only swapping the order of the first two. That is the trade the brief describes, half the storage for nearly the same ranking; Exercise 2 asks where that stops being true.

:::broken
A team prunes 90% of patch vectors to save storage, measures average nDCG@5 on text-heavy pages, sees almost no drop, and ships. Users report that chart questions now fail. What did the evaluation miss? (Solution B1.)
:::

:::recap What to keep from this lesson
- Treat pages as images; embed patches; score with MaxSim.
- Late interaction keeps local matches that pooling blurs.
- Storage is the cost; prune patches and measure the cliff.
- Answer with a vision-language model that cites page and region.
- Evaluate per content type: text, tables, charts, handwriting, equations.
:::

## Solutions

??? sol | P2 · Finding the cliff
Prune at 50%, 75% and 90%, and measure nDCG@5 separately for each content type against the OCR baseline. Plot each type's curve: text pages usually tolerate heavy pruning, while charts and tables, whose evidence is concentrated in few patches, fall first. The cliff is the lowest pruning level at which any content type drops below the baseline.
???

??? sol | B1 · An average over the wrong pages
Text-heavy pages have redundant patches, so pruning hurts them little, and they dominate the average. Charts concentrate their meaning in a few patches, which aggressive pruning removes. Evaluate per content type (the brief's matrix) and set the pruning level from the most sensitive type, or prune less on pages classified as charts and tables.
???
