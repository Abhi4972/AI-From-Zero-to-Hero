@@top The problem
:::plain In plain words first
A model server answers many users at once by putting their requests into one **batch** and running them through the model together. The hard part is that requests have different lengths and arrive at different times. vLLM, the most used open-source server, does three things to keep the GPU full of useful work. **PagedAttention** stores each request's KV cache (the keys and values the model remembers for earlier tokens) in small fixed-size blocks, the way an operating system pages memory, so little is wasted. **Continuous batching** lets requests join and leave the batch after every generated token instead of waiting for the slowest one. **Chunked prefill** cuts a long prompt into slices so it does not freeze everyone else's output while it is read.
:::
@@

@@end Idea 7 · What the scheduler looks like
:::math
**KV cache per sequence.** For a model with $L$ layers, $H_{kv}$ key-value heads of size $d$, stored in $b$ bytes per number, a sequence of $n$ tokens needs

$$\text{KV bytes} = 2 \cdot L \cdot H_{kv} \cdot d \cdot n \cdot b$$

The 2 counts keys and values. Reserving $n_{\max}$ tokens per request when it uses only $n$ wastes the fraction $1 - n / n_{\max}$ of that reservation.
:::

:::worked Waste from reserving the maximum
Llama 3.3 70B has 80 layers and 8 KV heads of size 128. In BF16 ($b = 2$), one token needs 2 × 80 × 8 × 128 × 2 = 327,680 bytes, about 0.33 MB.

1. Reserving 8,192 tokens per request: 8,192 × 0.33 MB ≈ 2.7 GB per request.
2. A request that really uses 1,500 tokens fills 1,500 / 8,192 ≈ 18% of it; 82% is wasted.
3. With 16-token blocks, the same request takes ⌈1500 / 16⌉ = 94 blocks = 1,504 slots: 4 slots of waste, about 0.3%.

That difference in waste is the room continuous batching uses to fit more requests on one GPU.
:::

:::check
Which statements are right?

- ✓ Continuous batching runs the scheduler once per generated token, not once per request.
- ✗ Chunked prefill makes each long prompt finish faster.
  It makes the long prompt slightly slower; what it protects is everybody else's inter-token latency.
- ✓ `--gpu-memory-utilization` sets how much GPU memory vLLM reserves for KV blocks.
- ✗ Every vLLM feature can be switched on together in every version.
  Check the compatibility matrix for your version first.
:::

:::predict
On a GPU, one decode step for 64 sequences takes barely longer than for 1, because reading the model's weights from memory dominates. Before you run the code below, guess how much more throughput a batch of 64 gives than a batch of 1.
:::

:::visual Why batching works on a GPU
```python run
WEIGHTS_MS = 20.0          # read all weights once per decode step (memory-bound)
PER_SEQ_MS = 0.15          # extra compute per sequence in the batch

for batch in (1, 4, 16, 64, 128):
    step_ms = WEIGHTS_MS + PER_SEQ_MS * batch
    tok_per_s = batch / (step_ms / 1000)
    print(f"batch {batch:4d}: step {step_ms:5.1f} ms  ->  {tok_per_s:7.0f} tokens/s")
```
:::

:::read
Going from 1 to 64 sequences makes each step about 50% slower but produces 64 tokens instead of 1, so throughput rises about 40 times. Batching pays because the dominant cost, reading the weights, is shared. Keep this in mind when you read the toy scheduler below: it charges a fixed 0.5 ms for every token in the batch, so batching cannot pay there the way it does on a GPU.
:::

@@before Ship it
:::read
The script's STATIC row beats CONTINUOUS on throughput, the opposite of real vLLM. Its cost model is why: `FORWARD_LATENCY_PER_TOKEN` charges 0.5 ms for each sequence in a decode step, so a step for 64 sequences costs 64 times a step for one, and the main advantage of batching disappears. What the toy does show correctly is the last column: chunked prefill cuts P99 inter-token latency from about 219 ms to 66 ms, because long prompts no longer block decode steps.
:::

:::broken
An engineer turns off chunked prefill because "it makes TTFT worse for our long prompts". Throughput is unchanged, but users on short chats complain that answers now stall mid-sentence. What happened? (Solution B1.)
:::

:::recap What to keep from this lesson
- PagedAttention allocates KV cache in 16-token blocks, cutting waste from most of the reservation to a few per cent.
- Continuous batching admits and releases requests after every token.
- Chunked prefill slices long prompts so decode keeps moving: better P99 ITL, not better throughput by itself.
- Batching pays because a decode step's cost is dominated by reading weights, shared by the whole batch.
- KV bytes per token = 2 · layers · KV heads · head size · bytes per number.
:::

## Solutions

??? sol | P1 · STATIC against CONTINUOUS
In this toy the gap goes the wrong way: STATIC reaches about 4,000 tokens/s, CONTINUOUS under 900, because each decode step costs 0.5 ms per sequence and continuous mode is also capped by the KV block budget. On a real GPU, with near-constant step cost, continuous batching wins on decode efficiency: finished sequences leave immediately and new ones take their place instead of padding.
???

??? sol | P4 · Fragmentation waste
(a) Contiguous allocation at 8,192 tokens with a mean use of 1,500 wastes about 1 − 1,500 / 8,192 ≈ 82% of reserved KV memory. (b) With 16-token blocks, each request wastes on average half a block, 8 tokens of about 1,500, roughly 0.5%.
???

??? sol | B1 · Stalls mid-sentence
Without chunked prefill, each long prompt's prefill runs as one large step, and every decode sequence waits for it. Short chats see their tokens stop for hundreds of milliseconds whenever a long prompt arrives: the P99 inter-token latency jumps. Turn chunked prefill back on and, if long-prompt TTFT matters, raise the chunk size a little.
???
