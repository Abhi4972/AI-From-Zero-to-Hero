@@top The problem
:::plain In plain words first
Agent jobs (write a report, summarize an incident) take time, and workers crash. A naive queue loses jobs, runs them twice, or lets a slow worker that woke up late overwrite the result of the worker that replaced it. Durable job systems solve this with a few ideas that this project builds by hand in Go.

A job has a stable identity, so a request delivered twice is one job. A worker claims it with a lease and a version number, written to disk before work starts. Completion is accepted only from the current lease holder, so a stale worker's receipt is rejected. And the store is written atomically, with a reproducible crash between "the output exists" and "the queue knows it", so recovery can reuse the output instead of redoing the work.
:::
@@

@@end Step 3 · Finish or reclaim expired work
:::visual Leases with versions
```python run
job = {"state": "queued", "version": 0, "lease_until": 0, "owner": None}
def claim(worker, now, ttl=100):
    if job["state"] == "running" and now < job["lease_until"]: return f"{worker}: busy until {job['lease_until']}"
    job.update(state="running", version=job["version"] + 1, lease_until=now + ttl, owner=worker)
    return f"{worker}: claimed version {job['version']}"
def finish(worker, version):
    if version != job["version"]: return f"{worker}: rejected stale completion (version {version}, current {job['version']})"
    job["state"] = "completed"; return f"{worker}: completed version {version}"
print(claim("A", now=10))            # A gets version 1, lease until 110
print(claim("B", now=50))            # still leased to A
print(claim("B", now=120))           # lease expired: B gets version 2
print(finish("A", 1))                # A wakes up late
print(finish("B", 2))
```
:::

:::read
Worker A claims the job (version 1). B is refused while A's lease is valid, and gets version 2 once it expires. When A finally wakes up and reports completion for version 1, it is rejected: B now holds the job. Only B's completion for version 2 is accepted. The version number is what turns "who finished?" into a question with one answer.
:::

@@end Step 4 · Write and recover atomic snapshots
:::check
Which statements are right?

- ✓ A request delivered twice with the same identity creates one job.
- ✗ A worker may start working and record its claim afterwards.
  The claim is persisted first; otherwise a crash leaves work nobody knows is running.
- ✓ After a crash between writing the output and recording completion, recovery can reuse the output.
- ✗ Leases make jobs exactly-once across machines.
  This store is same-host and local; distributed exactly-once needs more.
:::

@@before Build it on your machine
:::broken
A queue marks a job complete whenever any worker reports success. A worker pauses for a long garbage-collection stop, its lease expires, a second worker redoes the job and sends the customer email; the first worker wakes and sends it again. Which mechanism stops the second email? (Solution B1.)

:::recap What to keep from this project
- Give retried requests one stable job identity.
- Persist a lease and version before starting work.
- Accept completion only from the current version.
- Write snapshots atomically; make crash gaps reproducible.
- Reuse verified effects on recovery instead of repeating them.
:::

@@end Exercises
1. Why must the job's input be immutable once queued?
2. What makes an effect safe to reuse on recovery?
3. How long should a lease be?

## Solutions

??? sol | 1. Immutable input
Recovery reuses an output only if it was produced from the same input. Changing the input after queueing would make an old output look valid for a request it does not answer; the input hash ties them together.
???

??? sol | 2. A reusable effect
It is complete (written atomically) and its receipt matches the job's id and input hash. Then producing it again would only waste work or, for external effects, repeat them.
???

??? sol | 3. Lease length
Longer than the job normally takes, short enough that a crashed worker's job is retried promptly. Long jobs should renew their lease periodically rather than take one very long lease.
???

??? sol | B1 · A second email
The version check: the first worker's completion carries the old version and is rejected. For external effects like email, the effect itself should also be keyed by job id (an idempotency key), so a late duplicate send is refused by the receiver.
???
