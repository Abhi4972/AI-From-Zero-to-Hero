@@top Problem
:::plain In plain words first
**Speculative decoding** makes a large model generate faster without changing what it outputs. A small, cheap **draft** model guesses the next few tokens; the large **target** model checks all of them in one forward pass and keeps the guesses up to the first one it disagrees with, then adds its own token. When the draft guesses well, each expensive pass yields several tokens instead of one. How well it guesses (the **acceptance rate**) depends on how closely the draft matches the target and on the kind of text: a draft tuned on chat may do worse on code. The serving work is in measuring this honestly: speed-up per batch size, tail latency when guesses are rejected, and cost per million tokens. Model and version names are a 2026 snapshot.
:::
@@

@@end Build it
:::math Expected speed-up
With per-token acceptance probability $\alpha$ and $k$ draft tokens per step, the expected number of tokens produced per target pass is

$$\mathbb{E}[\text{tokens}]=\frac{1-\alpha^{k+1}}{1-\alpha}$$

If one draft token costs a fraction $c$ of a target pass, the wall-clock speed-up is about $\dfrac{1-\alpha^{k+1}}{(1-\alpha)(kc+1)}$ (Leviathan et al., 2023).
:::

:::worked Picking k
Take $\alpha = 0.8$ and a draft that costs $c = 0.05$ of a target pass.

1. $k = 2$: tokens per pass $(1-0.8^3)/0.2 = 2.44$; cost factor $1 + 0.1 = 1.1$; speed-up ≈ 2.2×.
2. $k = 4$: tokens $(1-0.8^5)/0.2 = 3.36$; cost $1.2$; speed-up ≈ 2.8×.
3. $k = 8$: tokens $(1-0.8^9)/0.2 = 4.33$; cost $1.4$; speed-up ≈ 3.1×.
4. Gains flatten as $k$ grows, because later guesses are rarely reached, while their cost keeps adding up; with a costlier draft the best $k$ is smaller.
:::

:::check
Which statements are right?

- ✓ The target model verifies all draft tokens in one pass.
- ✗ Speculative decoding lowers output quality slightly.
  With exact verification the output distribution is unchanged.
- ✓ Acceptance rate depends on the traffic, so it can drift.
- ✗ Tokens per target call equals wall-clock speed-up.
  Draft cost and larger verify passes eat into it, especially at large batch sizes.
:::

:::predict
Before running the code below: with $\alpha = 0.75$ and a draft costing 5% of a target pass, which $k$ between 1 and 10 gives the largest speed-up, and does it change if the draft costs 20%?

:::visual Speed-up against draft length
```python run
def speedup(alpha, k, c):
    return (1 - alpha ** (k + 1)) / ((1 - alpha) * (k * c + 1))

for c in (0.05, 0.20):
    row = {k: speedup(0.75, k, c) for k in range(1, 11)}
    best = max(row, key=row.get)
    print(f"draft cost {c:.0%}: " + "  ".join(f"k={k}:{v:.2f}" for k, v in row.items()))
    print(f"   best k = {best}, speed-up {row[best]:.2f}x")
```
:::

:::read
With a cheap draft (5% of a pass) the curve is flat from about k = 5 to 8, peaking near 2.7× at k = 7; with a costly one (20%) the best k drops to 3 and the speed-up to about 1.7×. This is the range real systems report (2–3×), and it shows why the toy's 6× figures below are optimistic: they count target calls but give the draft no cost at all.
:::

@@before Ship it
:::read
The simulation decodes 500 tokens and shows the two levers clearly: better draft–target alignment raises acceptance, and longer drafts produce more tokens per target call, up to 6.4 at alignment 0.9 and k = 6. Notice that acceptance *falls* as k grows (from 0.88 to 0.69 at alignment 0.6), since later guesses are harder. And remember what "speedup" means here: target calls saved, with draft cost and verification overhead left out, so real wall-clock gains are much smaller, as the visual shows.
:::

:::recap What to keep from this lesson
- A cheap draft guesses; the target verifies all guesses in one pass.
- Output is unchanged; speed depends on acceptance rate.
- Expected tokens per pass: (1 − α^(k+1)) / (1 − α); draft cost limits useful k.
- Acceptance drifts with traffic: measure per domain.
- Report speed-up and p99 at several batch sizes, plus cost per million tokens.
:::

## Solutions

??? sol | P2 · Fallback on low acceptance
Track acceptance over a sliding window per traffic class. When it falls below the level where speculation pays off (from the speed-up formula with your draft's cost, often around 0.5), switch that class to an n-gram draft or to plain decoding, and switch back when a probe shows recovery. Report how often the fallback triggers and the latency it saved.
???

??? sol | B1 · Wrong batch size, wrong traffic
At batch size 32 the GPU is already busy, so the spare compute speculation relies on is gone and larger verify passes add latency. And a draft tuned on chat accepts fewer guesses on code, lowering the gain further; rejected guesses also create the tail-latency spikes. Benchmark at the production batch size on production-like traffic before enabling it.
???
