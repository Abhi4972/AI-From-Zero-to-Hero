@@top The situation
:::plain In plain words first
A request fails with HTTP 400 before any token is generated, and the ticket asks to "turn off the limit". This case trains a habit interviewers look for: when a server refuses a request, read the numbers in the error and work out who owns each one. Here one number belongs to the client (how many tokens it asked for) and one to the server (the longest request it was configured for).
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A 400 that arrives before any token streams means the request was rejected during validation, not during generation.
- ✗ Setting `max_tokens` very high is a harmless way to avoid cut-off answers.
  It must fit the server's maximum length; the right fix is a realistic value plus checking the finish reason.
- ✓ A finish reason of `length` tells the client the answer was cut.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Read both numbers in the error and assign each to its owner.
- Ask for the output length the product needs, not the maximum imaginable.
- Check the finish reason so cut answers are visible.
- Raise a server limit only after measuring real prompt plus answer lengths.
:::
@@

@@takeaways
The situation | A 400 on long answers, and a request to remove the limit.
The evidence | The error body, the startup log and the manual.
Questions to answer first | Whose number is wrong?
Walkthrough | Two numbers, two owners.
What actually happened | The client asked for more than the server allows.
Wrong turns | Removing limits closes tickets and opens incidents.
The lesson to carry | Fix the side that is wrong; keep the budget.
