@@top The problem
:::plain In plain words first
A GPU's own memory (HBM) is fast but small. When many users hold long conversations, their KV caches fill it, and the server **preempts** some requests: it throws away their cache and later reads their prompt again from scratch. Ordinary computer memory (CPU DRAM) is slower but much larger and cheaper. **KV offloading** moves cache blocks that do not fit into DRAM, so they can be copied back instead of recomputed. vLLM can do this per engine (**native CPU offload**). **LMCache** goes further: a shared cache server that several engines can read, so a prompt prefix computed on one engine can be reused by another. The **vLLM production stack** bundles the router, the engines, LMCache and monitoring for Kubernetes. Offloading costs a few per cent when memory is not under pressure.
:::
@@

@@end Idea 8 · Numbers you should remember
:::math
**Restore or recompute?** Restoring $n$ tokens of KV from DRAM takes about $n \cdot k / B_{\text{PCIe}}$, where $k$ is KV bytes per token; recomputing takes the prefill time $t_{\text{prefill}}(n)$. Offloading helps when

$$\frac{n \cdot k}{B_{\text{PCIe}}} < t_{\text{prefill}}(n)$$
:::

:::worked A preempted 2,000-token request
Llama 3.3 70B in FP8: about 0.16 MB of KV per token. Prefill of 2,000 tokens takes about 400 ms on an H100 under load.

1. KV for 2,000 tokens: about 330 MB.
2. Copy back over PCIe Gen5 at an effective 25 GB/s: about 13 ms.
3. Recompute: about 400 ms. Restoring is about 30 times faster.
4. A 300-token request: 50 MB, about 2 ms to restore, against about 40 ms to recompute; still faster, but if the server is rarely short of memory, the bookkeeping overhead (a few per cent per request) outweighs the rare saving.
:::

:::check
Which statements are right?

- ✓ Native CPU offload helps one engine; LMCache lets several engines share cached prefixes.
- ✗ Offloading is free, so turn it on everywhere.
  With little memory pressure it adds about 3–5% overhead for no benefit.
- ✓ Preemption-heavy workloads gain most: restoring beats re-reading the prompt.
- ✗ Offloading helps short contexts most.
  Under 1K tokens, recomputing is cheap and the transfer saves little.
:::

:::predict
Before running the code below: as prompt length grows, does restoring from DRAM get more or less attractive compared with recomputing?
:::

:::visual Restore against recompute
```python run
KV_BYTES = 80 * 8 * 128 * 2          # per token, FP8
PCIE = 25e9                          # bytes/s, effective
PREFILL_TOK_S = 5000                 # tokens/s of prefill on a loaded GPU
for n in (256, 1024, 2048, 8192, 32768):
    restore = n * KV_BYTES / PCIE * 1000
    recompute = n / PREFILL_TOK_S * 1000
    print(f"{n:6d} tokens: restore {restore:7.1f} ms   recompute {recompute:8.1f} ms   ratio {recompute / restore:5.1f}x")
```
:::

:::read
Both grow with length, so in this simple model the ratio stays near 30× at every size: restoring is always faster once a block has been offloaded. In practice prefill gets slower per token at long lengths (attention grows with the square of the prompt), which makes restoring even more attractive for long contexts, while for short ones the fixed per-request overhead decides.
:::

@@before Ship it
:::read
Read the numbers, not the caption. In this run LMCache avoids the most re-prefills (194) but its total time is the slowest (0.98×), and its prefill time is the highest; CPU offload gives a small gain (1.01×). The toy charges LMCache a network hop on every lookup, and with these settings that cost outweighs the reuse. The lesson's claim holds only when cross-engine reuse is large and memory pressure is high, which is why the benchmark section says "starts to help" at moderate load and shows large gains only once KV exceeds HBM.
:::

:::broken
A team enables LMCache on a single-tenant service with 600-token prompts and a GPU memory use of 55%. Throughput drops 4%. What did they misjudge? (Solution B1.)
:::

:::recap What to keep from this lesson
- Preemption under memory pressure forces expensive re-prefills.
- Offload KV blocks to CPU DRAM; restoring is far faster than recomputing.
- Native offload is per engine; LMCache shares across engines.
- Enable it for memory pressure, shared prefixes and long contexts; skip it otherwise.
- The vLLM production stack packages router, engines, LMCache and monitoring.
:::

## Solutions

??? sol | P1 · Reading the simulation
CPU offload cuts prefill from 7.75 s to 3.4 s and total time slightly; LMCache avoids more re-prefills but adds lookup cost, ending 2% slower. The break-even comes when prefixes are shared across engines and memory pressure forces frequent preemption: then each avoided re-prefill saves far more than a lookup costs.
???

??? sol | B1 · No pressure, no reuse
With GPU memory at 55%, there is little preemption, so nothing needs restoring; with one tenant and short prompts, there is little cross-engine reuse. LMCache's per-request bookkeeping and network hop are pure overhead: the 3–5% the benchmark describes. Turn it off, or keep it only for the long-context tier.
