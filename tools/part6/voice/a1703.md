@@top The problem
:::plain In plain words first
**Autoscaling** means adding or removing capacity as traffic changes. On Kubernetes, a GPU model server scales at three levels. **Nodes** are the machines with GPUs; a tool such as Karpenter adds one when work is waiting. **Scheduling** decides which machine each piece of work runs on; a big model may need 8 GPUs that must all start together, which is called **gang scheduling**. **Replicas** are copies of the model server; something must decide how many to run. The common mistake is to scale replicas on "GPU utilization", which only says whether the GPU did *any* work in each sample. A busy GPU reads 100% with one request or a hundred. Better signals measure the work itself: how many requests are queued, how full the KV cache is, how slow the first token has become.
:::

@@end Idea 7 · Numbers you should remember
:::worked Why "100% busy" says nothing about load
Two replicas each report a GPU utilization of 100%.

1. Replica A has 2 requests in flight and 0 queued. Its first token arrives in 300 ms.
2. Replica B has 40 requests in flight and 120 queued. Its first token arrives in 9 s.
3. The duty-cycle metric is identical, so an autoscaler that targets 70% utilization treats them the same: it adds replicas for both, or for neither.
4. A queue-depth rule ("add one replica per 5 queued requests") leaves A alone and adds 24 replicas' worth of demand signal for B, capped by the cluster's limit.

The duty-cycle metric saturates as soon as a GPU is used at all, which is exactly where scaling decisions start to matter.
:::

:::check
Which statements are right?

- ✗ Memory-based autoscaling works for vLLM because memory grows with load.
  vLLM reserves most of the GPU memory for KV cache at start-up, so memory reads about 90% even with one request.
- ✓ Gang scheduling stops 7 of 8 GPUs from sitting idle while the 8th is found.
- ✓ Karpenter's `WhenEmptyOrUnderutilized` consolidation can evict a running model to save money.
- ✗ One autoscaler can serve prefill and decode pods of a disaggregated deployment.
  They bottleneck on different things: prefill on the queue, decode on KV cache pressure.
:::

@@before Ship it
:::read
Look at the numbers, not the caption the script prints. The duty-cycle rule dropped 1 request but left GPUs idle for 266 minutes: once any request runs, utilization reads above 70%, so it keeps adding replicas and rarely removes them. The queue-depth rule used about a fifth of the idle time but dropped 64 requests, because it removes replicas the moment the queue empties and cannot bring them back fast enough when the next burst arrives. Neither is right as written. A production rule scales up on queue depth or TTFT, keeps a warm floor, and waits several minutes before scaling down.
:::

A team sets HPA to keep `DCGM_FI_DEV_GPU_UTIL` at 70% for its vLLM service. In the morning rush it never scales up, and TTFT climbs to 10 seconds. What is HPA seeing, and what should it watch instead? (Solution B1.)
:::

:::recap What to keep from this lesson
- Three layers: Karpenter for nodes, KAI Scheduler for gang and topology-aware placement, an application signal for replicas.
- GPU duty cycle and GPU memory are poor scaling signals for LLM servers.
- Scale on queue depth, KV cache use, P99 TTFT or goodput.
- Keep a warm floor and a slow scale-down; new GPU capacity takes minutes.
- Do not let Karpenter consolidate running GPU nodes.
:::

## Solutions

??? sol | P1 · Duty cycle against queue depth
In this simulation the duty-cycle rule drops 1 request and the queue-depth rule 64, the opposite of the lesson's claim, while duty cycle wastes about five times more idle GPU time. The difference comes from the scale-down logic: queue depth removes a replica whenever the queue is empty, so each burst meets too few warm replicas. Add a cooldown or a higher warm floor and queue depth keeps its low idle time without the drops.
???

??? sol | P4 · Signals for prefill and decode
Scale prefill pods on queue depth (requests waiting for their first forward pass), because prefill is compute-bound and its symptom is waiting. Scale decode pods on KV cache utilization, because decode is memory-bound and runs out of room for sequences before it runs out of compute.
???

??? sol | B1 · Busy is not overloaded
HPA sees 100% duty cycle from the first request onwards, which it reads as "above target", but once the replica count reaches its maximum or the metric is averaged across replicas, it cannot tell a slightly busy fleet from a drowning one. Scale on the vLLM queue length (`num_requests_waiting`) or on P99 TTFT instead, with a warm minimum.
???
