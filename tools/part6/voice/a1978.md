@@top The problem
:::plain In plain words first
With plain data parallelism, every rank keeps a full copy of everything: weights, gradients and the optimizer's state. For Adam that state is large: two running averages per parameter, plus often an fp32 **master copy** of the weights. **ZeRO** (Zero Redundancy Optimizer) removes the duplication in stages. **Stage 1** shards the optimizer state, so each of N ranks keeps 1/N of it and updates only its slice of the weights, then the slices are gathered. **Stage 2** also shards gradients; **stage 3** also shards the weights themselves. The communication trick is **reduce-scatter**: each rank receives only the summed gradient slice it owns, rather than the full all-reduced gradient it would mostly throw away.
:::
@@

@@end Idea 3 · Why reduce_scatter beats allreduce-then-shard
:::worked The memory arithmetic
A 7-billion-parameter model trained with Adam in mixed precision, on 8 GPUs.

1. Weights in 16-bit: 14 GB. Gradients in 16-bit: 14 GB. Optimizer state in fp32: master weights 28 GB + first moment 28 GB + second moment 28 GB = 84 GB.
2. Plain data parallelism: 14 + 14 + 84 = 112 GB *per GPU*, more than an 80 GB GPU holds.
3. ZeRO-1 over 8 ranks: optimizer state 84 / 8 = 10.5 GB, so 14 + 14 + 10.5 = 38.5 GB per GPU.
4. ZeRO-2 also shards gradients (1.75 GB) for 26.25 GB; ZeRO-3 shards the weights too (1.75 GB) for about 14 GB, plus temporary gathers. Each stage trades memory for more communication.
:::

:::check
Which statements are right?

- ✓ ZeRO-1 shards the optimizer state across ranks.
- ✗ ZeRO-1 reduces the memory used by the model weights.
  Weights are only sharded in stage 3.
- ✓ Reduce-scatter gives each rank just the gradient slice it owns.
- ✗ Sharding the optimizer changes the training result.
  Each slice gets the same update it would have received; results match.
:::

:::visual Memory per rank by ZeRO stage
```python run
def per_rank_gb(params_b, n, stage):
    w, g, opt = 2 * params_b, 2 * params_b, 12 * params_b      # GB, since params are in billions
    if stage >= 1: opt /= n
    if stage >= 2: g /= n
    if stage >= 3: w /= n
    return w + g + opt

for params in (1, 7, 70):
    row = "  ".join(f"stage {s}: {per_rank_gb(params, 8, s):6.1f}" for s in range(4))
    print(f"{params:3d}B params, 8 ranks -> {row} GB")
```
:::

:::read
Stage 0 (plain data parallel) needs 16 bytes per parameter on every rank: 112 GB for 7B. Stage 1 alone cuts that to 38.5 GB because the optimizer state dominates; stage 3 reaches 14 GB. For a 70B model, only stage 3 (140 GB per rank on 8 ranks) comes close to fitting, and in practice it needs more ranks too, which is why the largest models combine ZeRO-3 or FSDP with other forms of parallelism.
:::

:::read
Four ranks train for 20 steps and end with identical parameter norms (11.213242), so sharding the optimizer did not change the result. Each rank holds a 5,196-byte optimizer shard. The per-rank optimizer memory falls from 27,712 bytes with plain DDP to 12,124 with ZeRO-1, a 56% drop; it is less than the ideal 75% for four ranks because some state (here, the full-size gradient buffer and bookkeeping) is not sharded in stage 1.

:::recap What to keep from this lesson
- Adam's state (master weights, two moments) dominates training memory.
- ZeRO-1 shards optimizer state; 2 adds gradients; 3 adds weights.
- Reduce-scatter delivers each rank only its gradient slice.
- Results are unchanged; only memory and communication change.
- Activations are a separate cost ZeRO does not address.
:::

## Solutions

??? sol | P1 · ZeRO-2
After backward, reduce-scatter the gradients so each rank keeps only its own slice, and free (or zero) the rest; the optimizer updates only that slice, then an all-gather restores full weights. Measure gradient memory per rank: it should fall to about 1/N of the full gradient.
???

??? sol | B1 · Activations, not optimizer state
For a small model with a huge batch, activations stored for the backward pass dominate memory, and ZeRO does not shard them. Reduce the micro-batch and use gradient accumulation, or use activation checkpointing (recompute activations during backward).
