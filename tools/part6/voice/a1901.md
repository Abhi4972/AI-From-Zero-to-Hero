@@top Problem
:::plain In plain words first
A **coding agent** is a program that wraps a language model in a loop: it makes a **plan**, **acts** by calling a tool (read a file, search, edit, run tests), **observes** the result, and **recovers** when something fails, until the task is done or a budget runs out. The model call is the easy part. The hard parts are around it: tool output that floods the context window, a loop that never ends, commands that damage files outside the project, and a bill that grows with every turn. This capstone asks you to build the whole harness: a terminal interface, a plan the model rewrites each turn, a small set of sandboxed tools, **hooks** (scripts that run on events such as "before a tool call") for safety and logging, hard budgets, and an evaluation against a baseline. Model and product names in the brief are a 2026 snapshot; use whatever is current when you build.
:::

@@end Build it
:::worked Why tool output must be truncated
Each turn the agent sends the whole conversation so far back to the model. Suppose the plan and instructions take 3,000 tokens and each turn adds the model's reply (300 tokens) plus the tool's output.

1. Untruncated, one search that matches thousands of lines can return 2 MB of text, roughly 500,000 tokens: far past a 200,000-token window in a single turn. The run dies at that turn.
2. With a 4,000-token cap per tool call, each turn adds at most 4,300 tokens. After 40 turns: 3,000 + 40 × 4,300 = 175,000 tokens. Close to the ceiling.
3. So a long run also needs **compaction**: at, say, 150,000 tokens a hook summarizes older turns into a short block, keeping the plan and recent observations.
4. Every turn also costs money in proportion to the context it resends, so truncation and compaction are cost controls as much as reliability fixes.
:::

:::check
Which statements are right?

- ✓ The plan is rewritten in full each turn, so a crash can resume from the saved state.
- ✗ A sandbox is optional if the model is careful.
  Mistakes and prompt injection both happen; the host must be unreachable.
- ✓ A `PreToolUse` hook can block a destructive command before it runs.
- ✗ Budgets only matter for cost.
  Turn and token limits also stop loops that would never end.
:::

:::predict
Before running the code below: each turn adds a 300-token reply plus a tool output averaging about 4,000 tokens (capped at 8,000 when truncation is on), and on turn 31 one search returns 500,000 tokens. Which of three harnesses (no protection, truncation only, truncation plus compaction at 150,000 tokens) finishes 50 turns inside a 200,000-token window?
:::

:::visual Context size over a 50-turn run
```python run
import random
random.seed(1)
BASE, REPLY, CAP, WINDOW, COMPACT_AT, COMPACT_TO = 3000, 300, 8000, 200_000, 150_000, 20_000
def run(truncate, compact, turns=50):
    ctx, compactions, peak = BASE, 0, BASE
    for t in range(turns):
        out = int(random.expovariate(1 / 4000))
        if t == 30: out = 500_000                   # one runaway search
        if truncate: out = min(out, CAP)
        ctx += REPLY + out
        peak = max(peak, ctx)
        if ctx > WINDOW: return f"crashed at turn {t + 1} (context {ctx:,})"
        if compact and ctx > COMPACT_AT: ctx, compactions = COMPACT_TO, compactions + 1
    return f"finished 50 turns, peak context {peak:,}, compactions {compactions}"

for truncate, compact in ((False, False), (True, False), (True, True)):
    print(f"truncate={truncate!s:5}  compact={compact!s:5}  ->  {run(truncate, compact)}")
```
:::

:::read
Without truncation, the single runaway search kills the run at turn 31. With truncation alone the run survives that turn, but the history keeps growing and crosses the window on the very last turn. Truncation plus compaction fires once, near turn 40, and keeps the context under about 150,000 tokens for the whole run. These are the two layers the brief asks for in steps 3 and 7.
:::

:::read
The stubbed model plans three steps, runs `ls`, tries to read `README.md`, and stops after three turns, 2,700 tokens and five cents. Look at the trace: the `read_file` call **failed** (the file does not exist in the sandbox), yet the plan in the final turn marks "read and diagnose" as done. The loop recorded the error but nothing acted on it. That is exactly the "recover" surface the capstone asks you to build: a failed observation should change the plan, not be ignored.

:::recap What to keep from this lesson
- A coding agent is a plan–act–observe–recover loop around a model.
- Truncate tool output and compact history, or one turn can sink the run.
- Run every tool in a sandbox; guard destructive commands with hooks.
- Enforce turn, token and dollar budgets.
- Measure against a baseline on matched tasks: pass rate, turns and cost.
:::
