@@top Problem
:::plain In plain words first
**Retrieval over a codebase** means answering a question such as "how is the retry budget enforced?" by first finding the few code fragments that matter, across many repositories, and then letting a model answer from them with citations. Two kinds of search complement each other. **Dense** search compares embeddings, so it finds code that *means* the same thing even with different words. **Sparse** search (BM25) matches exact terms, so it finds a function by its name or a rare identifier. A **hybrid** system runs both, **fuses** the two ranked lists, and **re-ranks** the best candidates with a more careful model. Code adds its own twists: chunk at function and class boundaries rather than every N tokens, keep a graph of who imports and calls what, and re-index only what changed on each push. Model and product names in the brief are a 2026 snapshot.
:::

@@end Build it
:::math Reciprocal rank fusion
$$\text{RRF}(d)=\sum_{r\in\text{rankings}}\frac{1}{k+\text{rank}_r(d)}$$

Each list contributes more for documents it ranks high; $k$ (often 60) softens the difference between rank 1 and rank 2. Only ranks are used, so the dense and sparse scores, which live on different scales, never need to be compared directly.
:::

:::worked Fusing two lists by hand
Take $k = 60$. Dense ranks chunks A, B, C; sparse ranks C, D.

1. A: dense rank 1 only → 1/61 ≈ 0.0164.
2. C: dense rank 3 and sparse rank 1 → 1/63 + 1/61 ≈ 0.0159 + 0.0164 = 0.0323.
3. B: 1/62 ≈ 0.0161; D: sparse rank 2 → 1/62 ≈ 0.0161.
4. Fused order: C, A, then B and D tied. C wins because both searches found it, even though neither put it first alone, which is exactly the behaviour you want from fusion.
:::

:::check
Which statements are right?

- ✓ Chunking at function boundaries keeps each retrieved piece a meaningful unit.
- ✗ Dense search alone is enough for code.
  Exact identifiers and rare names are where sparse search wins.
- ✓ Reciprocal rank fusion uses ranks, so scores on different scales need no calibration.
- ✗ Every push should re-embed the whole corpus.
  Only changed chunks, and the symbol edges they affect, need updating.
:::

:::visual Reciprocal rank fusion from scratch
```python run
def rrf(*rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc in enumerate(ranking, 1):
            scores[doc] = scores.get(doc, 0) + 1 / (k + rank)
    return sorted(scores, key=lambda d: -scores[d]), scores

dense = ["catalog/search/query.rs", "client/s3client/multipart.ts", "uploader/config/budgets.yaml"]
sparse = ["auth/policy/opa.py", "auth/authz/check.py"]
order, scores = rrf(dense, sparse)
for d in order:
    print(f"{scores[d]:.4f}  {d}")
```
:::

:::read
When the lists share nothing, fusion simply interleaves them: each list's first item gets the same score (0.0164), each list's second item the same (0.0161), and so on. Both authorization files reach the top four, but tied with the dense list's wrong answers. Fusion gives each search a fair vote; it cannot judge which one is right. That is the re-ranker's job: it reads each query–chunk pair closely and breaks the ties.
:::

:::broken
A team chunks every file into fixed 512-token windows with no overlap. Users complain that answers cite half a function and miss its signature. What went wrong, and what is the fix? (Solution B1.)
:::

:::recap What to keep from this lesson
- Chunk code at function and class boundaries, with repo, path and line span.
- Run dense and sparse search together; fuse with reciprocal rank fusion.
- Re-rank the top candidates with a cross-encoder before answering.
- Require file:line citations for every claim; drop or re-ask uncited ones.
- Re-index only changed chunks and their symbol edges on each push.
:::

## Solutions

??? sol | B1 · Windows cut through functions
Fixed windows split functions at arbitrary points, so a retrieved chunk can hold a body without its signature or two halves of different functions. Parse each file (for example with tree-sitter) and chunk at function and class nodes; for very long functions, split inside the node but repeat the signature in each piece, and keep the line span so citations point at real code.
