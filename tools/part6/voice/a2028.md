@@top The problem
:::plain In plain words first
Infrastructure tools such as Terraform show a plan before they change anything: create this, update that, replace the database. Reviewers skim long plans and miss the line that matters, usually a replacement (delete and recreate) hiding among updates, or a value that will only be known after the change.

This project turns a saved plan into a short change brief. It loads the plan while masking sensitive values, classifies each action and singles out replacements, traces which resources depend on which (even through values that are still unknown), and exports a Markdown brief and a JSON impact graph, each item linked by its exact resource address.
:::
@@

@@end Step 2 · Classify create, update, replace and delete actions
:::check
Which statements are right?

- ✓ `["delete","create"]` and `["create","delete"]` are both replacements; the order says which happens first.
- ✗ An unknown sequence of actions can be treated as an update.
  The classifier rejects sequences it does not understand.
- ✓ A sensitive value is shown as `[sensitive]` even inside arrays.
- ✗ A value marked unknown can be left out of the brief.
  "Known after apply" is important review information; it is shown as `[unknown]`.
:::
@@

@@end Step 3 · Trace declared dependencies and unknown outcomes
:::worked Why the application is affected
1. `service.database` is replaced (`delete`, then `create`), size small → medium. Its `endpoint` is unknown until the new database exists.
2. `service.application` has a `database_endpoint` that references `service.database.endpoint`.
3. So the graph has an edge application → database, even though the endpoint's value is unknown. The update to replicas (1 → 2) is not the only thing happening to the application: it will also receive a new endpoint.
4. The password appears as `[sensitive]` in the brief; the raw plan fields are dropped.
:::

@@before Build it on your machine
:::broken
A plan summary bot posts "2 to change, 0 to destroy" because it counts a replacement as a change. The team approves; the database is recreated and its data is gone. Which step's rule would have surfaced the risk? (Solution B1.)
:::

:::recap What to keep from this project
- Load plans with sensitive values masked and unknowns kept.
- Classify actions strictly; replacements are their own category.
- Trace references to concrete addresses, through unknown values.
- Link every explanation to its exact resource address.
:::

@@end Exercises
1. Why keep the original action order of a replacement?
2. The plan contains a value that is both sensitive and unknown. How should the brief show it?
3. How would you flag replacements of stateful resources (databases, volumes) more loudly?

## Solutions

??? sol | 1. Original order
`create` before `delete` means the new resource exists before the old one goes, so there may be no downtime; `delete` first means a gap. The reviewer needs to know which.
???

??? sol | 2. Sensitive and unknown
As `[sensitive]`. Masking wins: whether or not the value is known yet, it must not appear, and "sensitive" already tells the reviewer it is not shown.
???

??? sol | 3. Stateful replacements
Keep a list of resource types that hold data, and give their replacements a separate "data at risk" section at the top of the brief, with the address and the reason.
???

??? sol | B1 · Replacement counted as change
Step 2 classifies `delete`+`create` as a replacement, not an update. The brief lists replacements separately, so "the database will be destroyed and recreated" would have been the first thing the team read.
???
