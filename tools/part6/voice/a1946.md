@@top The problem
:::plain In plain words first
**Gradient accumulation** lets you train with a large **effective batch** on hardware that only fits a small one. Instead of one big batch, run N small **micro-batches**, add up their gradients without updating, then take one optimizer step. Done right, the result is identical to one big batch: divide each micro-batch's loss by N, so the summed gradients equal the average over the big batch. In distributed training there is a second saving: synchronizing gradients between machines after every micro-batch is wasted work, so you skip it until the last micro-batch (**sync on the last step**). This lesson proves the equivalence numerically and measures the speed trade-off on a tiny model.
:::
@@

@@end Idea 2 · Where the cost goes
:::worked Why the loss is divided by N
A batch of 8 examples, split into 2 micro-batches of 4. Each example's gradient (one number for simplicity): 1, 3, 2, 2 | 4, 0, 1, 3.

1. Full batch: mean of all 8 = 16 / 8 = 2.
2. Micro-batch means: 8 / 4 = 2 and 8 / 4 = 2. Summing them without dividing gives 4: double the true gradient, as if the learning rate had doubled.
3. Dividing each micro-batch loss by N = 2 gives 1 + 1 = 2, the same as the full batch.
4. With unequal micro-batch sizes (say 5 and 3), dividing by N is no longer exact; weight each micro-batch by its share of examples instead.
:::

:::check
Which statements are right?

- ✓ With the loss divided by N, accumulated gradients equal the full-batch gradient.
- ✗ The optimizer steps after every micro-batch.
  It steps once per effective batch, after the last micro-batch.
- ✓ Skipping gradient sync until the last micro-batch saves communication.
- ✗ Accumulation speeds up training.
  It saves memory; each micro-batch still costs a full forward and backward.
:::

:::predict
Before running the code below: micro-batches of sizes 5 and 3 with per-example gradients averaging 2.0 and 4.0. What is the true full-batch gradient, and what does "divide by N" give?
:::

:::visual Accumulation with equal and unequal micro-batches
```python run
batches = [[1, 3, 2, 2], [4, 0, 1, 3]]
full = sum(sum(b) for b in batches) / sum(len(b) for b in batches)
naive = sum(sum(b) / len(b) for b in batches)
div_n = sum(sum(b) / len(b) / len(batches) for b in batches)
print(f"equal sizes   : full {full:.3f}  sum of means {naive:.3f}  divided by N {div_n:.3f}")

uneven = [[2.0] * 5, [4.0] * 3]
full = sum(map(sum, uneven)) / sum(map(len, uneven))
div_n = sum(sum(b) / len(b) / len(uneven) for b in uneven)
weighted = sum(sum(b) / sum(map(len, uneven)) for b in uneven)
print(f"unequal sizes : full {full:.3f}  divided by N {div_n:.3f}  weighted by examples {weighted:.3f}")
```
:::

:::read
With equal micro-batches, dividing by N reproduces the full batch exactly, while plain summing doubles it. With sizes 5 and 3, dividing by N gives 3.0, but the true average is 2.75; weighting each micro-batch by its number of examples (dividing each loss sum by the total example count) is exact. The last, partial micro-batch of an epoch is where this usually bites.
:::

@@before Ship it
:::read
The equivalence check passes: accumulated gradients and parameters match the full batch to about 1e-8, which is floating-point rounding. In the sweep, the effective batch grows from 4 to 64 at a fixed micro-batch of 4 while the loss after the same number of optimizer steps stays about the same. The number of syncs stays at 25 because sync happens once per optimizer step whatever the accumulation. Read the throughput columns with suspicion: on a tiny model on a shared CPU, the timings recorded for this page jump around by an order of magnitude between rows, so they say more about the machine than about accumulation. Exercise 1 asks for a longer run, repeated, before drawing the curve.
:::

:::broken
A training script accumulates over 8 micro-batches but forgets to call `optimizer.zero_grad()` after each optimizer step. What happens over the first few effective batches? (Solution B1.)

:::recap What to keep from this lesson
- N micro-batches, one optimizer step: a larger effective batch in the same memory.
- Divide each micro-batch loss by N (or weight by example count).
- Zero gradients after each optimizer step, not after each micro-batch.
- Sync gradients only on the last micro-batch.
- Accumulation saves memory, not compute.
:::

## Solutions

??? sol | P2 · Forgetting to divide
Run one effective batch with and without dividing by N from identical starting weights. Without division the gradients are N times larger, so the step is N times too big; the parameter difference after step 1 is about (N − 1) times the correct update, which the comparison prints directly.
???

??? sol | B1 · Gradients that never reset
Gradients keep adding up across effective batches: the second step uses the sum of two batches' gradients, the third of three, and so on, so step sizes grow and training soon diverges. Call `zero_grad()` immediately after each `optimizer.step()`, and only then.
???
