@@top The problem
:::plain In plain words first
An assistant that "handles your email" is easy to imagine and risky to build: it might group unrelated messages because they share a subject line, label a request as information, or send a reply that promises something you never agreed to.

This project builds the careful offline version. It reads exported messages with a proper MIME parser, threads them by their message-ID headers rather than subjects, triages each one with explicit phrases and shows the phrase that matched, and writes reply drafts that quote the source and leave a marked gap for your answer. Nothing is ever sent.
:::
@@

@@end Step 2 · Group references and explain the queue
:::check
Which statements are right?

- ✓ Two messages with the same subject from different senders may be unrelated.
- ✗ "Re:" in the subject is enough to join a message to a thread.
  Threads are built from `References` and `In-Reply-To` headers that point at messages in the set.
- ✓ A message that matches no triage phrase is "uncertain", not "information".
- ✗ Splitting a raw email at the first blank line gives you its body.
  MIME messages can have several parts and encodings; a parser selects the plain-text part.
:::
@@

@@end Step 3 · Create an unsent draft with a source quote
:::worked A draft that promises nothing
1. The message from Mira says: "Could you confirm whether we should print six table labels for Saturday?"
2. Triage matches the phrases "Could you" and "confirm", so the category is action, with those phrases shown as evidence.
3. The draft quotes the first source line, then a marked placeholder such as `[Your reply: decide what to commit to]`.
4. It is serialized with Python's `EmailMessage`, so headers and line endings are valid, and saved as an `.eml` file. Sending is a separate, human act.
:::
@@

@@before Build it on your machine
:::broken
An auto-reply tool answers every "action" email with "Sure, done by Friday." A message saying "Could you NOT change the labels until we confirm?" is triaged as action. What goes wrong, and which design choices here prevent it? (Solution B1.)
:::

:::recap What to keep from this project
- Parse MIME properly and keep message identity.
- Thread by reference headers, not subjects.
- Triage with explicit phrases and show the matched evidence.
- "No match" means a person looks, not "information".
- Drafts quote the source and leave the commitment to you; nothing is sent.
:::
@@

@@end Exercises
1. Why sort the exported queue by priority and then message ID?
2. How would you add an "urgent" category without hiding the existing evidence?
3. A message arrives in HTML only. What should the reader do?

## Solutions

??? sol | 1. Stable sorting
Priority puts actions first; the message ID breaks ties in a fixed way. Two exports of the same mailbox are then identical, so a diff shows only real changes.
???

??? sol | 2. An urgent category
Add explicit phrases ("today", "before 5 pm", "blocking") with their own evidence line, and show both the category and every phrase that matched. Never let one category silently replace another's evidence.
???

??? sol | 3. HTML-only mail
Convert the HTML part to text with a real HTML parser, mark the entry as "converted from HTML", and keep the original part available, because conversion can drop meaning (tables, links).
???

??? sol | B1 · A blind auto-reply
Phrase triage cannot read negation, so it labelled a "don't" request as action, and the auto-reply promised the opposite of what was asked. Here, triage only orders a review queue with its evidence shown, and drafts leave the reply to a person; nothing is sent.
???
