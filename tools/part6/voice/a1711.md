@@top The problem
:::plain In plain words first
When the same model runs in several cloud **regions** (say Virginia, Oregon and Ireland), a **router** decides which copy answers each request. A normal load balancer spreads requests evenly, which is right for stateless web servers. Model servers are not stateless: each one holds a **prefix cache**, the KV cache of prompt beginnings it has already read. A request sent to a replica that has its prefix cached skips most of the prefill and gets its first token about ten times sooner. **Cache-aware routing** sends each request to a replica that already holds its prefix. Across regions you must weigh that saving against the network round trip, and some data (such as EU health data) must never leave its region. The lesson also covers **disaster recovery**: a backup that holds the weights but not the tokenizer or the configs cannot start.
:::
@@

@@end Idea 7 · Numbers you should remember
:::math
**When is a remote cache hit worth it?** A local miss costs the full prefill $t_{\text{miss}}$. A hit in another region costs $t_{\text{hit}} + \text{RTT} + q$, where $q$ is any extra queueing there. Route remotely only when

$$t_{\text{hit}} + \text{RTT} + q < t_{\text{miss}}$$

Prefill time grows with prompt length, so long shared prompts make remote hits pay; short prompts rarely do.
:::

:::worked Virginia to Ireland
A 2,000-token prompt on Llama 3.3 70B FP8: a hit costs about 80 ms, a miss about 800 ms. The round trip from us-east-1 to eu-west-1 is about 75 ms.

1. Remote hit: 80 + 75 = 155 ms, against a local miss of 800 ms. Remote wins by 645 ms.
2. If the Irish replica has a 400 ms queue: 80 + 75 + 400 = 555 ms. Still better.
3. A 200-token prompt: miss about 80 ms, hit about 15 ms. Remote: 15 + 75 = 90 ms, worse than the local miss.
4. If the request carries EU personal health data and originates in Paris, it must stay in the EU whatever the numbers say.
:::

:::check
Which statements are right?

- ✓ Round-robin routing ignores which replica holds which prefix.
- ✗ Bedrock cross-region inference gives you cache-aware routing.
  It reroutes for capacity during pressure; it does not know about your prefixes.
- ✓ A DR backup must include the tokenizer, quantization configs and the engine's serving config.
- ✗ Routing to the region with the best cache hit is always allowed.
  Data-residency rules come first; partition routers by residency boundary.
:::

:::predict
Before running the code below: with a 75 ms round trip, at roughly what prompt length does a remote hit start to beat a local miss?
:::

:::visual Prompt length against round-trip time
```python run
MISS_MS_PER_TOKEN, HIT_MS_PER_TOKEN, RTT = 0.40, 0.04, 75   # 800 ms and 80 ms at 2,000 tokens

for tokens in (100, 200, 250, 500, 1000, 2000, 8000):
    local_miss = MISS_MS_PER_TOKEN * tokens
    remote_hit = HIT_MS_PER_TOKEN * tokens + RTT
    best = "remote hit" if remote_hit < local_miss else "local miss"
    print(f"{tokens:5d} tokens: local miss {local_miss:6.0f} ms | remote hit {remote_hit:6.0f} ms -> {best}")
```
:::

:::read
With these rates the crossover is near 210 tokens: below it, the round trip costs more than the prefill saved. Most RAG and agent prompts are far longer, so cross-region hits usually pay, unless the remote region is queueing. Replace the per-token rates with your own measurements; the shape of the decision stays the same.
:::

@@before Ship it
:::read
Global cache-aware routing lifts the hit rate from about 29% to 87% and cuts mean TTFT from 648 to 225 ms, while sending 567 requests across regions. Regional routing keeps traffic home with no cross-region cost and a modest gain. Which one you ship depends on prompt length, RTT and residency rules, not on the hit rate alone.
:::

:::broken
During a regional outage, a team fails over to its backup region. The replica starts, loads the weights from S3, and then crashes on the first request. The backup was complete as far as they knew: every `.safetensors` file was there. What was probably missing? (Solution B1.)
:::

:::recap What to keep from this lesson
- Model servers are stateful: route to the replica that holds the prefix.
- A cache hit is about 10× faster than a miss on long prompts.
- Across regions, take a remote hit only if hit + RTT + queue < local miss.
- Residency boundaries come before latency.
- DR backups need weights, tokenizer, configs and the serving manifest, and a rehearsed drill.
:::

## Solutions

??? sol | P1 · Prompt length for cross-region routing
With a miss costing about 0.4 ms per token, a hit about 0.04 ms per token and a 75 ms round trip, a remote hit wins when 0.36 × tokens > 75, so above about 210 tokens. Queueing at the remote region raises that threshold; measure your own per-token prefill cost.
???

??? sol | P2 · Hit rate from 70% to 12%
(1) The prompt template changed and dynamic content now leads the prompt: compare first tokens of two requests. (2) The router lost its KV-event feed (subscriber down or lagging): check that the event stream is current. (3) A scaling event added many cold replicas or caches were flushed: check replica count and eviction counts around the drop.
???

??? sol | B1 · Weights are not enough
Most likely the tokenizer files (`tokenizer.json` or `tokenizer.model`), the quantization config (AWQ scales or GPTQ zero-points) or the model's RoPE and chat-template settings. The engine loads weights, then fails on the first request. Back up the whole model repository plus the serving config and deployment manifest, and run a failover drill every quarter.
???
