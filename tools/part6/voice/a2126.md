@@top The situation
:::plain In plain words first
A client built for a REST service treats HTTP 2xx as success and 404 as "not visible yet, retry". Talking to an agent over JSON-RPC, it received a 200 whose body was an error ("task not found") and logged it as success. Over the REST binding the same error retried forever. The case trains decoding the protocol, not only the transport, and classifying errors by their reason.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A JSON-RPC error can arrive inside an HTTP 200.
- ✗ A 404 always means "try again soon".
  For a purged task it means stop; the error reason says which.
- ✓ One error reader for both bindings keeps behaviour consistent.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Decode the protocol, not just the HTTP status.
- Classify errors by reason: retry, re-authenticate, fix, or stop.
- Use one error reader across bindings.
- Stop after one reply for a permanent "not found".
:::
@@
