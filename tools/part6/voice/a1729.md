@@top The problem
:::plain In plain words first
A **demo interface** is a small web page and server that lets other people try your model. It must do the things a notebook never does. It **validates input** before spending a model call: size, type, allowed characters. It shows **progress**, so a slow model does not look broken, and **streams** tokens as they are produced (the usual format is Server-Sent Events, SSE). It returns **errors a stranger can act on**: what went wrong and what to do, never a stack trace. And it protects your budget once the link is shared: a **token bucket** limits how fast each client can send requests, a daily cap limits total cost, and logs keep only what you need. This lesson builds all of that with Python's standard library, then shows the same demo in Gradio and Streamlit.
:::

@@end Idea 7 · When a demo becomes a product
:::math
**The token bucket.** Each client has a bucket of capacity $C$ that refills at $r$ tokens per second. After $\Delta t$ seconds,

$$\text{tokens} \leftarrow \min(C,\ \text{tokens} + r\,\Delta t)$$

A request is accepted if at least one token is available, which then leaves the bucket. $C$ is the largest burst a client can send; $r$ is its long-run rate. When the bucket is empty, the server answers 429 with `Retry-After` set to the seconds until a token is back: $(1 - \text{tokens}) / r$.
:::

:::worked Seven quick requests against a bucket of 3
Capacity 3, refill 0.5 tokens per second; a client sends requests at t = 0, 0.1, 0.2, 0.3, 0.4, 2.5 and 4.5 s.

1. t = 0, 0.1, 0.2: the bucket goes 3 → 2 → 1 → about 0.1 (plus a tiny refill). All accepted.
2. t = 0.3: about 0.15 tokens; rejected, `Retry-After` ≈ (1 − 0.15) / 0.5 ≈ 1.7 s.
3. t = 0.4: about 0.2 tokens; rejected again.
4. t = 2.5: 0.2 + 2.1 × 0.5 ≈ 1.25 tokens; accepted, leaving 0.25.
5. t = 4.5: 0.25 + 1.0 = 1.25; accepted.
Five of seven accepted: a burst of 3, then the long-run rate of one every 2 seconds.
:::

:::check
Which statements are right?

- ✓ Browser-side `maxlength` helps honest users; the server must check again.
- ✗ Sending the input in a GET query string is fine for a demo.
  URLs end up in server and proxy logs, so private input would be logged.
- ✓ Once a stream has started with status 200, a later failure must be sent as an error event.
- ✗ Keying the rate limit on the client IP works behind a reverse proxy.
  Every request then comes from the proxy's address, so all users share one bucket.
:::

:::predict
Before running the code below: with capacity 2 and refill 1 per second, how many of seven requests sent 0.1 s apart are accepted?
:::

:::visual The demo's own validator and bucket
```python run
from main import TokenBucket, DemoError, validate_text   # the lesson's code/main.py

bucket = TokenBucket(capacity=2, refill_per_second=1.0, now=0.0)
for i in range(7):
    wait = bucket.take(now=i * 0.1)
    print(f"request {i} at t={i * 0.1:.1f}s: " + ("accepted" if wait == 0 else f"429, Retry-After {wait:.1f}s"))

for payload in ({"text": "x" * 600}, {"text": "   "}, {"text": "bad\x07char"}, {}):
    try:
        validate_text(payload)
    except DemoError as err:
        print(err.status, err.code, "|", err.hint)
```
:::

:::read
Only the two burst requests pass. The bucket refills at one token a second, so the next request could pass only around t = 1.1 s; each rejected request gets 429 with a `Retry-After` that shrinks as the refill approaches, which a well-behaved client simply obeys. Every bad input gets a status, a stable code and a hint before any model call is spent. This is exercise 1 run for you; change the two numbers and run it again.
:::

@@before Ship it
:::broken
A team shares its demo link on social media. The model call costs $0.02, the per-IP bucket allows 10 requests a minute, and the server runs behind a cloud load balancer. Overnight the bill reaches $3,000. Name two controls that failed or were missing. (Solution B1.)
:::

:::recap What to keep from this lesson
- Write the contract first: input limits, model-call cost and time, output and error shapes.
- Check in order of cost; spend the model call last.
- Show progress, stream tokens with SSE over POST, send errors as events once streaming.
- Errors carry a code, a message with numbers, a hint and a request ID.
- Public links need a per-client bucket (with the right key behind a proxy), a daily cap and careful logs.
:::

## Solutions

??? sol | P1 · Capacity 2, refill 1 per second
See the visual above: with requests 0.1 s apart, requests 0 and 1 use the burst; the bucket does not hold a full token again until about t = 1.1 s, so requests 2–6 all get 429, with `Retry-After` falling from 0.8 s to 0.4 s. Over a long run the accepted rate settles at one per second.
???

??? sol | B1 · A viral link
(1) The rate-limit key: behind the load balancer every request came from the balancer's address, so either all users shared one bucket or, if the key read a header without checking it came from the proxy, each attacker could pick a fresh key. (2) No daily usage cap, so nothing bounded total cost. A cap with a 503 and an alert at the provider would have stopped the bill at a known amount.
???

@@takeaways
The problem | A notebook is not a demo.
Idea 1 · A demo is a contract | Input, model call, output, each limited.
Idea 2 · Validate before the model runs | Cheap checks first, model call last.
Idea 3 · Show that the model is working | Disable, time, show first token.
Idea 4 · Send the output as a stream | SSE tokens over POST.
Idea 5 · Write errors that a user can act on | Code, message, hint, request ID.
Idea 6 · Share a public demo safely | Bucket, cap, token, careful logs.
Idea 7 · When a demo becomes a product | Weekly outsiders and budgets mean product.
Step 1 · The model call | A toy model that streams tokens.
Step 2 · Validation and error responses | Every failure gets a status and hint.
Step 3 · The token bucket | Burst capacity plus a refill rate.
Step 4 · The stream | Token events, then done or error.
Step 5 · The request handler | Size, token, bucket, validate, cap, call.
