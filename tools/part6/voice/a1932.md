@@top The frame
:::plain In plain words first
A model turns each token id into a vector by looking up a row of the **token embedding** matrix (one row per vocabulary entry, one column per model dimension). Ids carry no order, so a second vector tells the model each token's **position**, and the two are **added**. There are two classic ways to make position vectors. A **learned** positional embedding is another lookup table with one row per position, trained like everything else, but it cannot handle positions beyond the longest it was built for. A **sinusoidal** one is computed from sines and cosines of different frequencies; it has no parameters, works at any length, and nearby positions get similar vectors. Modern models often use other schemes (such as rotary embeddings), but these two show the trade-off.
:::
@@

@@end The composition
:::math Sinusoidal positions
For position $p$ and dimension pair $i$ in a model of width $D$:

$$PE(p,2i)=\sin\!\left(\frac{p}{10000^{2i/D}}\right),\qquad PE(p,2i+1)=\cos\!\left(\frac{p}{10000^{2i/D}}\right)$$

Low dimensions oscillate fast and distinguish neighbouring positions; high dimensions oscillate slowly and encode coarse position.
:::

:::worked Counting parameters
Vocabulary $V = 320$, width $D = 64$, maximum context 128.

1. Token embedding: $320 \times 64 = 20{,}480$ parameters.
2. Learned positions: $128 \times 64 = 8{,}192$ parameters, and position 129 simply has no row.
3. Sinusoidal positions: 0 parameters; position 129 (or 10,000) is computed by the formula.
4. The sum is a vector of size 64 per token, so the shape stays $(B, T, D)$ whichever scheme is used.
:::

:::check
Which statements are right?

- ✓ Token and position vectors are added, keeping the width D.
- ✗ A learned positional table extends to any length.
  It has one row per position up to its maximum.
- ✓ Sinusoidal embeddings need no trained parameters.
- ✗ At initialization, learned position vectors of neighbours are similar.
  They are random at first; any similarity has to be learned.
:::

:::visual Similarity between sinusoidal positions
```python run
import math
def pe(p, D=64):
    v = []
    for i in range(D // 2):
        w = p / 10000 ** (2 * i / D)
        v += [math.sin(w), math.cos(w)]
    return v
def cos(a, b): return sum(x * y for x, y in zip(a, b)) / math.sqrt(sum(x * x for x in a) * sum(y * y for y in b))

base = pe(10)
for other in (11, 12, 15, 20, 40, 100):
    print(f"cos(pos 10, pos {other:3d}) = {cos(base, pe(other)):.3f}")
```
:::

:::read
Neighbouring positions are very similar (about 0.97 for an offset of one) and similarity falls with distance, though not perfectly smoothly, because the fast-oscillating dimensions go up and down. This built-in notion of "nearby" is what the sinusoidal scheme gives for free; a learned table has to discover it from data.
:::

:::recap What to keep from this lesson
- Token embedding: one row per id; output shape (B, T, D).
- Add a position vector so order is visible.
- Learned positions: trained, but capped at the table size.
- Sinusoidal positions: free, any length, nearby positions similar.
- Check shapes and parameter counts before training.
:::

## Solutions

??? sol | B1 · Clipped positions
Every token after position 511 receives the same position vector, so the model cannot tell their order apart, and it never saw such inputs in training. Either train with the lengths you will serve, use a position scheme that extends (sinusoidal, rotary with scaling), or refuse prompts longer than the trained context.
???
