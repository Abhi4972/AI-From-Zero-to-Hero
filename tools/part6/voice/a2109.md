@@top The situation
:::plain In plain words first
Every reply takes about two seconds to start, even for a repeated question, although the 3,000-token system prompt never changes. A relay adds a new request id as the first line of that prompt. Prefix caching only reuses work for an identical beginning, so a changing first line makes every request a cache miss. Moving the id fixed it: in the measurement, from 2,161 ms to 98 ms.
:::
@@

@@before Walkthrough
:::check
Which statements are right?

- ✓ A prefix cache can reuse only the part of the prompt that is identical from the very first token.
- ✗ More cache memory or a different eviction policy would have helped.
  Nothing was cacheable; the first line changed on every request.
- ✓ Stable content first, per-session content next, per-request content last.
:::
@@

@@end The lesson to carry
:::recap What to keep from this case
- Prompt layout is part of the serving system.
- Never put a changing value at the start of a shared prefix.
- Send trace ids as metadata.
- Check the cache hit rate before tuning memory.
:::
@@
