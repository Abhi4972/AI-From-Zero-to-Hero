@@top The problem
:::plain In plain words first
After a meeting, someone writes "Alex to publish release notes by Friday" and the rest of the notes are prose. Turning that into a task list is where assistants invent things: an owner from a name mentioned nearby, a date from "next week", a commitment from a suggestion.

This project starts strictly. Only lines in an explicit format, `ACTION owner | date | task`, become actions, each with its line number. Missing owners and impossible dates become visible review flags instead of crashes or guesses. Exact duplicates merge but keep every source line. Prose that looks like a commitment can be proposed, but is labelled as a proposal. Nothing is exported until a person decides.
:::
@@

@@end Step 2 · Validate owners and calendar dates
:::visual Strict parsing with visible uncertainty
```python run
import datetime as dt
lines = ["ACTION Alex | 2026-10-02 | Publish release notes", "ACTION ? | ? | Verify migration",
         "ACTION Sam | 2026-02-30 | Book the room", "Decision: wait for review."]
for n, line in enumerate(lines, 1):
    if not line.startswith("ACTION "): continue
    owner, due, task = [p.strip() for p in line[7:].split("|")]
    flags = []
    if owner == "?": flags.append("needs_owner")
    if due == "?": flags.append("needs_date")
    else:
        try: dt.date.fromisoformat(due)
        except ValueError: flags.append("invalid_date")
    print(f"line {n}: owner={owner!r} due={due!r} task={task!r} flags={flags}")
```
:::

:::read
Only `ACTION` lines are parsed; the decision line is ignored rather than guessed at. `?` is an explicit "unknown" marker, which becomes a review flag. 30 February has the right shape but is not a date, so it is flagged invalid rather than accepted as text that "looks like" a date. Every action keeps its line number, so the checklist can point back to the notes.
:::

@@end Step 3 · Deduplicate exact commitments without losing citations
:::check
Which statements are right?

- ✓ Two ACTION lines with the same owner, date and task merge into one action with both line numbers.
- ✗ "Alex | publish notes" and "Sam | publish notes" are duplicates.
  Two people assigned the same task are two commitments.
- ✓ An action due before the stated "today" is marked overdue.
- ✗ Overdue is computed from the computer's clock.
  It is computed from an explicit `--today`, so a rerun gives the same answer.
:::

:::recap What to keep from this project
- Parse an explicit action format; keep line numbers.
- Unknown is `?` and becomes a review flag.
- Validate real calendar dates; compute overdue from a stated today.
- Merge exact duplicates, keep all citations; different owners stay separate.
- Prose-derived items are proposals; export only decided items.

## Solutions

??? sol | 1. An explicit today
Overdue then depends only on the inputs, so tests are stable and a report rerun next week still shows what was overdue on the day it was made.
???

??? sol | 2. A relative date
Flag it as an invalid date rather than resolving "Friday": which Friday depends on when the meeting was and on the reader's timezone. A reviewer can replace it with an ISO date.
???

??? sol | 3. Model proposals from prose
The same rules: every proposal cites its exact source line, is marked as a proposal, has its owner and date validated, and needs an explicit decision before export. Measure how often proposals are accepted before trusting the feature.
???

??? sol | B1 · An invented commitment
Prose becomes at most a proposal, "maybe ... next week" has no valid date, and nothing is exported without a person's decision. The suggestion would have appeared for review, flagged, not in the tracker.
???
