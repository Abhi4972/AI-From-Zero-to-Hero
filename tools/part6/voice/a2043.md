@@top The problem
:::plain In plain words first
An agent that runs many model calls needs a budget it cannot overrun. Checking "is there money left?" before each call is not enough: two queued calls can both see the same remaining money and both spend it. And the cost known before a call (a worst-case ceiling) is not the cost after (what was actually used).

This project builds the controller: integer costs, a reservation for each request before it runs, settlement afterwards that releases what was not used, and a scheduler that refuses jobs that would break the cost limit or the deadline, recording every decision.
:::
@@

@@end Step 3 · Settle actual usage and release unused budget
:::visual Reserve, then settle
```python run
limit, spent, holds = 100, 0, {}
jobs = [("index", 60, 35), ("report", 70, 40), ("extra", 60, 60)]     # id, worst-case cost, actual cost
for jid, ceiling, actual in jobs:
    if spent + sum(holds.values()) + ceiling > limit:
        print(f"{jid:6} rejected: {spent} spent + {ceiling} needed > {limit}"); continue
    holds[jid] = ceiling                                     # reserve before running
    print(f"{jid:6} reserved {ceiling}", end=" -> ")
    del holds[jid]; spent += actual                          # settle: release the hold, add the actual cost
    print(f"settled {actual}, released {ceiling - actual}, spent now {spent}")
```
:::

:::read
"index" reserves its worst case of 60, actually costs 35 and releases 25. "report" needs 70, but 35 + 70 = 105 is over the limit, so it is rejected before running. "extra" needs 60: 35 + 60 = 95 fits, it runs and costs the full 60. Final spend is 95 of 100. Notice that "extra" could run only because "index" settled below its reservation.
:::
@@

@@end Step 4 · Schedule within cost and time limits
:::check
Which statements are right?

- ✓ A reservation is counted against the budget until the request settles or is cancelled.
- ✗ If a request's actual cost exceeds its reservation, the ledger should just record the larger number.
  That is an accounting error and is reported, because the reservation was supposed to be a ceiling.
- ✓ Each request can be settled exactly once.
- ✗ This ledger is safe to share between several processes.
  It is a single-process teaching model; shared budgets need a database or a lock.
:::

:::recap What to keep from this project
- Integer costs in a stated unit.
- Reserve the worst case before running; count holds against the limit.
- Settle once with the actual cost; release the rest.
- Reject jobs that break the cost limit or the deadline, and record why.
:::

@@end Exercises
1. Why is a rejected job's reservation never created?
2. How would you budget a job whose output length is unknown?
3. What should happen when a job is cancelled halfway?

## Solutions

??? sol | 1. No reservation on rejection
A rejection must leave the ledger unchanged. Creating a hold and then removing it opens a window where another request sees less budget than really exists.
???

??? sol | 2. Unknown output length
Reserve for the maximum output tokens you allow (the ceiling), and enforce that maximum in the request. The settlement then releases whatever was not used.
???

??? sol | 3. A cancelled job
Settle it with the actual cost incurred so far (zero if the provider bills nothing for cancelled calls), release the rest, and record the cancellation as its own event.
???

??? sol | B1 · Two workers, one budget
Both start, and 35 + 60 + 60 = 155 is spent against a limit of 100. Step 2's reservation makes the second check see 35 spent plus 60 held, so it is rejected (in one process; across processes the reservation needs shared storage).
???
