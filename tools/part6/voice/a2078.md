@@top The problem
:::plain In plain words first
A decompiler turns machine code back into readable source. Commercial tools do it for whole programs; this project does it for a handful of small C functions compiled to x86-64, entirely from scratch in Python, and then proves its output is right.

It is the deepest build in the course and follows phase 13's reverse-engineering lessons step by step: read the ELF object and its relocations; decode the instructions the fixtures use; recover control flow, including a jump table; lift to an intermediate form and SSA; simplify compiler idioms (such as division by a constant done with multiplication); recover the function signature and types; structure the graph into if, while and switch; and finally recompile the emitted C and check it matches the original byte for byte, with relocations masked.
:::
@@

@@end Step 5 · Simplify and fold idioms
:::visual Division without a divide instruction
```python run
M = 0x66666667                                   # what a compiler emits for x / 10 with 32-bit ints
def div10_like_compiler(x):
    q = (x * M) >> 34                            # multiply by a "magic" constant, shift right by 34
    return q + (1 if x < 0 else 0)               # correction step for negative numbers
for x in [0, 9, 10, 95, 123456, -7, -95]:
    print(f"{x:7} / 10 = {int(x / 10):6}   magic: {div10_like_compiler(x):6}")
```
:::

:::read
Division is slow, so compilers replace `x / 10` with a multiplication by 0x66666667, a shift, and a sign correction. The results match true integer division (rounding toward zero) for positive and negative numbers. A naive decompiler would print the multiply and shift; this project's idiom-folding step recognizes the pattern and prints `param_1 / 10`, which is what the programmer wrote.
:::
@@

@@end Step 3 · Recover control flow
:::check
Which statements are right?

- ✓ A jump table's bounds check tells the decompiler how many entries are valid.
- ✗ Reading instructions linearly from the start of `.text` finds every function's code.
  Data and padding can sit between functions; recursive descent follows actual control flow.
- ✓ Relocations show which bytes are addresses to be filled in by the linker.
- ✗ If the emitted C compiles, the decompilation is correct.
  It must recompile to matching code and pass the original's tests.
:::

@@end Run the finished project
:::read Reading this output
`tenths_and_fifths` comes back as `return param_1 / 10 + param_1 / 5;`: the magic-number multiplications were folded back into divisions. `band` becomes a bounds check (`(unsigned int)param_1 <= 5`) plus a read from `lookup_0`, a recovered constant array `{5, 8, 12, 20, 20, 35}`: the compiler had turned the switch into a table, and the decompiler shows what really executes. `fold` is a do-while loop with `(esi_1 << 5) - esi_1`, the compiler's way of multiplying by 31, and `record` recovered a struct with two int fields. Names like `param_1` and `eax_1` are honest: the original names were not in the binary.
:::

@@end Exercises

## Solutions

??? sol | 1. Masking relocations
Relocation fields are placeholders the linker fills in; their bytes depend on where things land in each build. Comparing them would report differences that do not matter, so they are masked and the targets are compared separately.
???

??? sol | 2. A table, not a switch
The compiler turned the switch into an array lookup because the cases were dense. The decompiler reports what the machine code does; printing it back as a switch would be a guess about the source, not a reading of the binary.
???

??? sol | 3. What is gone
Local variable names, comments, macro names and the original formatting, plus any code the optimizer removed. Some types and structure can be inferred; those cannot.
???

??? sol | B1 · An unfolded idiom
Step 5, idiom folding: it recognizes the magic-number multiply, shift and sign correction as signed division by 10, and prints `x / 10`.
???
