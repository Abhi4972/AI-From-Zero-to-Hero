@@top The problem
:::plain In plain words first
Services tell each other about events through webhooks: an HTTP POST saying "this report was uploaded". The receiver must check that the POST really came from the sender (a signature), that it is not an old message replayed by someone else (a timestamp window), and that a retry of the same delivery is processed once. And when processing has a bug, you want to replay accepted deliveries later, deliberately, without re-accepting them as new.

This project builds such a receiver in Go: it keeps the raw request bytes, verifies an HMAC signature over the delivery id, timestamp and body, stores each accepted delivery durably before acknowledging it, answers retries as duplicates, and replays stored deliveries through an explicit command that writes processing receipts.
:::
@@

@@end Step 2 · Verify signatures and timestamp bounds
:::visual Signatures cover the exact bytes
```python run
import hmac, hashlib, json
secret = b"orchard-shared-secret"
def sign(delivery, ts, body): return "v1=" + hmac.new(secret, f"{delivery}.{ts}.".encode() + body, hashlib.sha256).hexdigest()
body = b'{"task":"review uploaded report"}'
sig = sign("delivery-1", "1770000000", body)
same_json_other_bytes = json.dumps(json.loads(body), indent=1).encode()
print("original bytes verify:", hmac.compare_digest(sig, sign("delivery-1", "1770000000", body)))
print("re-serialized JSON verifies:", hmac.compare_digest(sig, sign("delivery-1", "1770000000", same_json_other_bytes)))
```
:::

:::read
The signature covers the delivery id, the timestamp and the body's exact bytes. Parsing the JSON and serializing it again produces the same data with different whitespace, and the signature no longer matches. That is why the receiver keeps and verifies the raw bytes before decoding anything. `compare_digest` compares in constant time, so the check does not leak how many characters matched.
:::
@@

@@end Step 3 · Deduplicate retries with a durable inbox
:::check
Which statements are right?

- ✓ The delivery is written durably before the receiver returns success.
- ✗ Two deliveries with equal JSON content are the same delivery.
  Identity is the delivery id; content can legitimately repeat.
- ✓ A timestamp outside the allowed window is rejected even with a valid signature.
- ✗ Replaying a stored delivery re-runs the acceptance step.
  Replay starts a new, explicitly named processing run; transport deduplication is unchanged.
:::

@@before Build it on your machine
:::broken
A receiver parses the JSON body, re-serializes it, then verifies the signature. Every legitimate delivery fails with 401 after the sender changes its JSON library. Which rule from step 1 prevents this? (Solution B1.)
:::

:::recap What to keep from this project
- Keep the raw body; verify before decoding.
- Sign delivery id, timestamp and bytes; bound the timestamp.
- Persist before acknowledging; deduplicate by delivery id.
- Replay explicitly, with run ids and processing receipts.
:::

@@end Exercises

## Solutions

??? sol | 1. Whitespace and digests
The raw SHA-256 changes with any whitespace change, even though the JSON means the same. Signatures are over bytes, so the receiver must hash and verify the bytes it received, never a re-serialization.
???

??? sol | 2. Another provider's scheme
Each provider defines its own concatenation, header names and encoding. Implement its published rules exactly, with its test vectors, in a separate adapter; reusing this scheme would reject all their real deliveries, or worse, accept forged ones.
???

??? sol | 3. A crash before linking
The `.pending` file stays on disk, but only linked entries count as accepted deliveries. The sender's retry is then accepted normally. The design relies on hard links and fsync, so it should not be claimed for filesystems without them.
???

??? sol | 4. Downstream effects
Send `receipt.payload` to the next queue with the run id plus delivery id as the idempotency key. Exactly-once effects in other systems still need those systems to honour the key; a local receipt cannot guarantee it.
???

??? sol | B1 · Re-serializing before verifying
Preserve and verify the raw bytes first. Any change to how JSON is written changes the bytes, so verifying a re-serialization fails legitimate deliveries.
???
